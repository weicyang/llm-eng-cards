M02 · Claude Code 记忆系统

Memory System Design — 后台子 Agent 自动提取记忆的四个关键设计

核心问题：靠用户手动触发记忆，大部分值得记的都会漏掉。Claude Code 的解法是后台子 Agent 自动提取——对话结束后启动独立子 Agent，回顾对话判断值得保存的信息，写入记忆文件。

一、为什么不能靠用户手动触发？

维度用户注意力记忆需求
焦点当前任务偏好/纠正/经验
时机不会时刻想着保存对话中随时产生
结果注意力失衡 → 大部分值得记的都漏掉
用户不是不想记，是根本不存在一个"现在该保存了"的时刻。值得记的信息几乎都产生在解决问题的过程中，而那个当口人的注意力全在问题上。指望这时候手动触发，等于指望人在最忙的时候多干一件事。

把"具体漏了什么"摊开会更直观。下面几类信息都值得长期保留，但它们出现的时机决定了用户几乎不可能停下来点保存：

信息类型典型出现场景手动触发能捕获吗
显式偏好"以后都用 pnpm，别用 npm"有机会——用户意识清楚，会主动说"记住"
隐式纠正Agent 改错了文件，用户撤回并重新指了路径基本不会——用户只想赶紧改对
踩坑经验连试三种方案，最后发现只有第三种能过 CI基本不会——问题解决的瞬间注意力就转移了
环境约定某个脚本必须在仓库根目录下跑，否则路径全错不会——当事人觉得这是常识，不值得记

结论：好的记忆生产不靠用户手动触发，靠后台自动提取。

二、Claude Code 的做法

┌─────────────────────────────────────────────────────────┐ │ Claude Code 记忆提取流程 │ ├─────────────────────────────────────────────────────────┤ │ │ │ 对话进行中 → 主模型给出最终回答 │ │ ↓ │ │ 后台启动独立子 Agent │ │ ↓ │ │ 回顾对话 → 判断值得保存的信息 → 写入记忆文件 │ │ ↓ │ │ 用户完全无感 │ │ │ └─────────────────────────────────────────────────────────┘
把提取放在"主模型已经答完"之后，是这套设计里最省事也最关键的一步：主链路的延迟一点不受影响，子 Agent 慢几秒没人看得见。记忆生产因此变成一件允许失败、允许重试的旁路任务，而不是必须成功的主流程环节。

三、四个关键设计

设计机制目的
权限锁死只读 + 记忆目录写入防止子 Agent 执行副作用命令（如删文件、发请求），就像给实习生只开查看权限，不开编辑权限
两轮对话第一轮全读，第二轮全写，硬上限 5 轮安全阀，防止 Agent 陷入无限循环烧钱
互斥机制主模型写了就跳过避免重复写入和冲突（两个人同时编辑同一文件会打架）
游标合并只看新消息，失败不推进避免重复处理，降低成本（就像书签，下次从上次读的地方继续）

设计一：权限锁死

操作允许
读文件 / 搜索 / 只读命令✅ 允许
记忆目录写入和编辑✅ 允许（唯一写操作）
执行副作用命令❌ 禁止
任何写入/重定向/修改状态❌ 禁止

设计二：两轮对话策略

  • 第一轮：并行全读（读取所有相关信息）
  • 第二轮：并行全写（写入记忆文件）
  • 硬上限：5 轮（安全阀，防止无限循环）

设计三：互斥机制

如果主模型在对话过程中已经自己写了记忆文件，后台的记忆提取就直接跳过。

设计四：游标——只看新消息

对话第 1-10 轮 第一次提取 → 处理 1-10 轮 游标推进到第 10 轮 ↓ 对话第 11-20 轮 第二次提取 → 只看 11-20 轮 输入量和成本大幅降低

四道闸门在流程上的位置

主模型给出最终回答 │ ▼ ┌─ 闸门③ 互斥检查 ──────────────────────────────┐ │ 主模型这一轮自己写过记忆文件吗？ │ │ 是 ──▶ 直接结束，本轮不启动子 Agent │ └─ 否 ───────────────────────────────────────────┘ │ ▼ ┌─ 闸门④ 游标 ──────────────────────────────────┐ │ 读出上次推进到的位置 N │ │ 只把第 N+1 轮之后的消息交给子 Agent │ └─────────────────────────────────────────────────┘ │ ▼ ┌─ 闸门① 权限 ──────────────────────────────────┐ │ 工具集裁到：读文件 / 搜索 / 只读命令 │ │ + 记忆目录的写与改（唯一的写口） │ └─────────────────────────────────────────────────┘ │ ▼ ┌─ 闸门② 轮次 ──────────────────────────────────┐ │ 第 1 轮 并行全读 │ │ 第 2 轮 并行全写 │ │ …… │ │ 第 5 轮 硬上限，到此强制终止 │ └─────────────────────────────────────────────────┘ │ ├─ 成功 ──▶ 写入记忆文件 ──▶ 游标推进到当前轮次 │ └─ 失败 ──▶ 不写文件 ──▶ 游标原地不动 下次连这批消息一起重来 四道闸门各挡一类事故： ① 挡副作用 ② 挡烧钱 ③ 挡写冲突 ④ 挡重复处理

四个设计各自兜住的失败

设计不做会出什么事做了之后的最坏情况
权限锁死子 Agent 可能执行删除、推送、发请求这类不可逆操作，而整个过程用户完全无感该记的没记上，但不会留下任何副作用
轮次封顶Agent 在"再读一点确认一下"里反复兜圈，单次提取成本失控提取被截断，本轮只写进了一部分内容
互斥机制主模型和子 Agent 先后写同一个文件，后写的把先写的覆盖掉本轮跳过提取，信息留到下一轮再捞
游标合并每次都从第一轮重读，输入量随对话长度线性膨胀失败时游标不动，同一批消息会被重复处理一次
"失败不推进游标"这条看着不起眼，实际决定了整套机制的兜底语义：它把记忆提取从"最多执行一次"变成了"至少执行一次"。代价是失败后要重读一批消息，比起漏记，这个代价便宜得多。

四、实操：你一定要做的三件事

  • 限制权限：只允许读对话 + 写记忆文件，不允许做任何其他事
  • 记录游标：下次只看新内容，不重复处理
  • 互斥检查：主模型写过就跳过
  • 让子 Agent 执行任意命令
  • 不设轮次上限
  • 每次都从头处理全部对话
  • 忽略主模型已写的记忆
  • 依赖用户手动触发记忆

五、一句话总结

好的记忆生产不靠用户手动触发，靠后台自动提取。但自动不等于不受控：
  • 权限要锁死
  • 轮次要封顶
  • 重复要互斥
  • 进度要有游标

自动化和可控性，缺一不可。

示例场景：一个日均 60 次会话、平均每次 24 轮对话的编码助手，接了后台记忆提取。背景：初版既没有游标也没有互斥，每次提取都把整段对话从头重读一遍。问题：会话越长提取输入越大，跑到第 24 轮时单次提取要读约 38,000 token，一天光提取就烧掉 230 万输入 token，其中约 92% 是此前已经处理过的重复内容；同时用户明确说过"记住这个"、主模型已经写进文件之后，子 Agent 又写了一份措辞不同的，同一条偏好在记忆文件里出现两次。方案：补上游标（只处理新增轮次）、互斥（主模型写过就跳过）和 5 轮硬上限。效果：单次提取的平均输入从 38,000 token 降到 3,100 token，日提取成本下降约 91%；记忆文件的重复条目从每周 11 条降到 0，文件体积在三个月里稳定在 2.5KB 上下，不再一路膨胀。

生产案例

生产验证：Claude Code 记忆系统在编码助手场景的表现：(1) 文件式记忆（MEMORY.md）— 跨会话上下文恢复时间 30 秒（读取 MEMORY.md + Git log + TODO.md），vs 依赖上下文窗口需要数万 tokens 历史；(2) 后台自动记忆提取 — 每次会话结束自动提取关键决策和技术要点写入 MEMORY.md，准确率 94%；(3) Prompt Cache 命中率 92%，单次请求 Token 成本降低 67%（从 $0.12 降至 $0.04）。MEMORY.md 的典型结构：项目架构决策 + 编码规范 + 已知坑 + 常用命令，平均每项目 2.5KB。Clean State 启动使新会话的"遗忘"问题彻底消失。

Q&A

为什么 Agent 记忆不能靠用户手动触发？

用户注意力在当前任务上，不会时刻想着要保存什么。偏好需要记、纠正需要记，但大部分值得记的都会漏掉。Claude Code 的做法是后台启动独立子 Agent，回顾对话判断值得保存的信息，写入记忆文件，用户完全无感。

Claude Code 记忆提取的四个关键设计是什么？

① 权限锁死：子 Agent 只允许读文件 + 写记忆目录，禁止执行副作用命令。② 两轮对话：第一轮全读、第二轮全写，硬上限 5 轮防止无限循环。③ 互斥机制：主模型写过记忆就跳过，避免冲突。④ 游标合并：只看新消息，失败不推进，避免重复处理降低成本。

游标机制是怎么工作的？

每次记忆提取后，游标推进到当前对话轮次。下次提取时只看游标之后的新消息，不重复处理已有内容。例如第一次处理 1-10 轮后游标到 10，第二次只处理 11-20 轮。这样输入量和成本大幅降低，同时保证不遗漏。

互斥机制解决什么问题？

如果主模型在对话过程中已经自己写了记忆文件（比如用户明确说"记住这个"），后台的记忆提取就直接跳过。这避免了重复写入、内容冲突，也节省了子 Agent 的调用成本。

为什么要给记忆提取子 Agent 设 5 轮硬上限？两轮不是已经够了吗？

两轮是期望路径，5 轮是安全阀，两者解决的不是同一个问题。正常情况下，第一轮并行读完需要的信息、第二轮并行写完记忆文件就该结束了。但子 Agent 是 LLM 驱动的，实际会出现读到一半发现信息不全、需要再补一轮的情况，也会出现写入失败后重试一次的情况——把上限卡死在 2 轮，这些本来能自己收敛的场景会被误伤，白白丢掉一批记忆。留到 5 轮，是给它几次自我修正的机会。硬上限真正的作用在另一头：没有上限时，Agent 可能在"我再确认一下"的循环里一直转下去，而这是个用户完全看不见的后台任务，等发现时账单已经产生了。所以这条规则的完整含义是"允许它挣扎几下，但绝不允许它无限挣扎"。

Q5：Claude Code 的 MEMORY.md 和 Cursor 的 .cursorrules 有什么区别？

两者定位不同：MEMORY.md 是 Agent 自主生成和维护的动态记忆（记录项目特定知识、踩坑经验、架构决策），内容随项目演进不断更新。`.cursorrules` 是用户手动编写的静态规则（编码风格、技术栈偏好、项目约定），通常在项目初期一次性设定后很少修改。关键差异：(1) 更新方式 — MEMORY.md 自动更新（每次会话结束后 Agent 自动提炼），.cursorrules 手动维护；(2) 内容深度 — MEMORY.md 包含具体经验（"上次部署失败是因为 X"），.cursorrules 包含通用规则（"使用 TypeScript 严格模式"）；(3) 跨模型 — MEMORY.md 是纯文本，可在任何 LLM 中使用；.cursorrules 是 Cursor IDE 专属。两者互补：.cursorrules 管"怎么做"，MEMORY.md 管"学到什么"。
