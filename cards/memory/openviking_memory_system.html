M03 · OpenViking 记忆系统：分层架构与 Context Engineering

OpenViking 记忆架构全景 — 结构化存储 / L0·L1·L2 分层加载 / 记忆生命周期 / Context Engineering / 选型与生产验证

Agent 记忆系统的本质问题不是"记不住"，而是"记住了但找不到、找到了但不相关、相关但已过时"。传统方案把记忆当作一堆扁平的向量碎片去检索，而新一代系统把记忆当作有目录、有分类、有生命周期的结构化文件系统来管理。这个范式转变的核心名称叫 Context Engineering——从精心构造提示词，进化到精心构造上下文。

核心差异：主流方案是平面向量搜索，OpenViking 是层级化虚拟文件系统。把所有上下文组织成有层级结构的文件系统，每个节点有三层粒度按需加载，检索时沿层级递归下钻。

一、问题背景：传统记忆系统的局限

1.1 主流做法与五个痛点

以 Claude Code 为例的主流做法：记忆存成 Markdown 文件，检索时递归扫描目录，读取每个文件前几十行元数据拼成清单，用便宜模型挑出最相关的几条读取全文注入上下文。

痛点表现
记忆量有硬上限扫描上限 200 文件，超过直接忽略
检索是单次判断没有探索能力，一次定生死
所有记忆平铺没有结构，无法分类管理
Token 消耗无控制要么读全文要么只看摘要
经验不会自动沉淀Agent 执行经验不会自动提取

1.2 向量范式的三大局限

过去两年，Agent 记忆系统的默认答案就是"向量数据库"——把所有东西 embedding 化，需要时按相似度检索。这个方案解决了"怎么存"和"怎么搜"的问题，但完全忽视了"怎么组织"和"怎么管理"。当 Agent 从实验室 Demo 走向生产环境，这些被忽视的问题变成了致命的瓶颈。

局限一：信息混杂——用户偏好与项目规则冲突。在扁平的向量存储中，所有类型的信息被不加区分地混在一起。当用户同时有"我偏好 Python"的个人偏好和"这个项目必须用 Java"的项目规范时，向量检索可能同时返回这两条互相矛盾的信息。模型无法判断哪条应该优先，导致输出混乱——一会儿用 Python 写代码，一会儿用 Java 写代码。

局限二：生命周期混乱——临时数据长期残留。传统系统缺乏生命周期管理的概念。一条 3 天前的临时调试日志、一次过时的 API 查询结果，会和用户的长期偏好、项目的核心规范一样被永久保存。随着时间推移，记忆库中充斥着过期的临时数据，每次检索都可能被这些"历史垃圾"干扰，检索质量持续退化。

局限三：检索失准——相似度不等于相关度。向量相似度检索的本质是"语义距离最近"，但"语义最近"不等于"任务最相关"。一个工具说明可能在语义上非常接近用户的问题，但实际上这个工具已经被弃用了。传统检索缺乏对上下文结构（分类、时效、优先级）的感知，只能基于纯语义距离返回结果。

局限类型典型案例根本原因后果
信息混杂Python 偏好 vs Java 项目规则并存缺乏分类隔离模型无法判断优先级
生命周期混乱临时调试日志被长期保留缺乏过期清理机制干扰后续任务决策
检索失准相似度搜索返回已弃用工具缺乏结构化元数据任务执行偏离目标

实测数据：在一个包含 500 条记忆的 Agent 系统中，传统向量检索的"有效召回率"（返回的结果真正被 Agent 使用的比例）仅为 23%。而引入分类隔离和生命周期管理后，有效召回率提升至 67%。问题的根源不是检索算法不够好，而是存储结构太混乱。

二、结构化存储与虚拟文件系统

OpenViking 的核心创新是抛弃了"所有记忆都是向量碎片"的假设，转而采用文件系统范式——用目录、路径、分类来组织 Agent 的所有上下文。这让记忆管理从"模糊搜索"变成了"定向导航"，从"黑箱检索"变成了"可追溯的文件操作"。

2.2 Viking URI：统一的资源定位体系

OpenViking 为每条上下文分配了一个Viking URI，格式为 viking://{scope}/{path}。这就像给每条记忆一个唯一的文件路径，系统可以精准定位任何上下文——不需要"搜索"，直接"打开"就行。URI 的 scope 层将记忆分为 resources（知识库）、user（用户上下文）、skills（技能）、memories（记忆）、session（会话）五大类。

2.3 三种上下文类型：Resource / Memory / Skill

OpenViking 将 Agent 需要的所有上下文严格分为三种类型，每种类型有不同的存储策略和检索方式。Resource 是外部导入的知识（文档、代码、网页），变化频率低，以只读方式访问。Memory 是从交互中提取的记忆（偏好、实体、事件），具有生命周期属性，需要定期更新和清理。Skill 是可调用能力的描述，相对稳定，按需加载。

上下文类型内容示例存储特性更新频率加载策略
ResourceAPI文档、代码库、项目规范持久化、版本控制低（手动更新）按需读取
Memory用户偏好、实体关系、事件记录持久化 + 生命周期中（自动提取）分类加载
Skill编码能力、分析能力描述持久化极低按需激活

2.4 目录递归检索

传统的向量检索是"在所有碎片中找最相似的"，OpenViking 的目录递归检索是"先定位目录、再深入文件"。系统首先通过意图分析确定最相关的目录，然后在目录内进行精细探索，逐层递归下降直到找到最匹配的内容片段。这种方式保留了全局上下文结构，不会因为局部相似度高而返回全局上不相关的结果。

2.5 检索流程的四个阶段

目录递归检索的执行流程分为四个明确的阶段，每个阶段都有独立的输入和输出，可以完整追溯。第一阶段是意图分析——理解用户的查询需求属于哪个领域（编码、分析、沟通等）。第二阶段是目录定位——在文件系统树中找到最相关的顶级目录。第三阶段是精细探索——在目标目录内进行向量搜索和 Rerank 精排。第四阶段是递归下降——如果目标目录包含子目录，继续向下递归直到找到最精确的匹配。

检索阶段输入操作输出成本（Token）
意图分析用户查询分类 + 关键词提取目标领域标签~50
目录定位领域标签 + 目录索引向量搜索顶级目录候选目录列表（Top-3）~100/条
精细探索候选目录 + 查询目录内向量搜索 + Rerank精排后的文件列表~200/条
递归下降命中文件 + 子目录子目录递归或文件读取最终上下文片段按需（L1/L2）

目录递归检索的核心优势是"结构感知"——它知道一条记忆属于"用户偏好"还是"项目规范"，知道一条资源是"API文档"还是"会议纪要"。这种结构信息在扁平向量存储中完全丢失了，但在实际决策中至关重要。

与主流硬上限的对照：主流方案（如 Claude Code）扫描上限 200 文件，超过直接忽略；OpenViking 的虚拟文件系统无硬上限，容量随文件系统自然扩展。

三层分级的本质是"先看封面，再看目录，最后看正文"。就像你在书店找书：先看书名（L0），觉得相关就翻目录（L1），确认需要才买回家细读（L2）。这样 90% 的书只需要看一眼封面就够了，省下大量 Token。

三、L0/L1/L2 三层分级加载

分层加载机制解决的是"上下文爆炸"问题——长任务中 Agent 需要大量上下文，但全部塞入提示词会耗尽 Token 预算。L0/L1/L2 让 Agent 像人读书一样：先看目录（L0），再看章节摘要（L1），需要时再翻到具体页面（L2）。实测显示，这种策略可以在仅消耗 17% Token 的情况下达到甚至超越全量加载的任务完成率。

3.1 三层模型设计

OpenViking 为每条上下文自动生成三个层级的表示：L0 摘要（约 100 tokens）用于向量搜索召回和快速过滤；L1 概览（约 2000 tokens）用于 Rerank 精排和内容导航；L2 详情（无限制）是完整原始内容，仅在深度需要时加载。这种渐进式加载让 Agent 可以用最低成本快速定位目标，再按需投入更多 Token 获取细节。

3.2 Token 节省的机制分析

分层加载之所以能大幅节省 Token，核心在于"早筛早弃"。L0 摘要层以每条约 100 tokens 的成本快速过滤掉 80% 不相关的内容；L1 概览层以每条约 2000 tokens 的成本进一步精排，只将真正需要的条目送入 L2 全文加载。假设一次任务需要检索 50 条上下文但最终只用 5 条：全量加载需要 50 × 全文 = 大量 Token，而分层加载只需 50 × 100（L0）+ 10 × 2000（L1）+ 5 × 全文（L2），节省幅度通常在 70-90% 之间。

L0/L1/L2 的精髓是"信息投入的边际回报递减"——你给模型 100 tokens 的摘要，它就能完成 80% 的筛选决策；再给 2000 tokens 的概览，能完成 95% 的导航决策；只有真正需要细节的 5% 场景才值得投入全文。把 100% 的全文给到 100% 的条目，是对 Token 预算的最大浪费。

四、记忆生命周期管理：六种记忆类型与自动进化

记忆不是越多越好——过时的记忆是噪音，不是资产。一个成熟的记忆系统需要知道什么该永久保存、什么该定期清理、什么该在任务结束后自动提取。OpenViking 定义了六种记忆类型，每种类型有独立的生命周期策略，并通过会话结束时的自动蒸馏机制持续进化记忆库。

4.1 六种记忆类型

OpenViking 的会话管理系统会自动从交互中提取六种类型的记忆：Profile（用户画像，如职业、技能水平）、Preferences（偏好设定，如代码风格、工具选择）、Entities（实体信息，如人名、项目名、技术栈）、Events（关键事件，如决策记录、问题解决过程）、Cases（案例模式，如"上次遇到 X 问题时的解决方案"）、Patterns（行为模式，如用户的工作节奏、常见操作流程）。

记忆类型生命周期更新触发过期策略典型内容
Profile长期（永久）显式声明或多次确认仅手动覆盖职业、技术栈、经验水平
Preferences中长期偏好变化时自动更新新版覆盖旧版代码风格、缩进偏好、测试框架
Entities长期新实体出现时添加长期不引用则降权项目名、同事名、工具名
Events中期会话结束时自动提取90天未引用则归档架构决策、Bug修复过程
Cases中长期问题解决后自动沉淀类似案例合并去重"上次数据库迁移的步骤"
Patterns长期多次观察后自动总结行为变化时自动更新工作流程、编码习惯

口径并列标注：在工程实现视角，OpenViking 的自动记忆提取由两个机制组成——Session Commit（自动从对话中提取 8 类记忆）与 Working Memory（维护 7 段式结构化工作记忆文档）。上文"六种记忆类型"是按生命周期维度的分类，与 8 类提取口径不完全重合，两种表述并列保留。

4.2 自动蒸馏机制

每次会话结束时，OpenViking 会触发一个异步的记忆蒸馏过程。系统分析整个会话内容，提取值得长期保留的信息，按照六种类型分类存储。这个过程对 Agent 和用户完全透明——不需要显式调用"记住这个"，系统会自动判断什么值得记住。

4.3 版本控制与矛盾消解

当用户的偏好或项目规范发生变化时，记忆系统需要正确处理新旧版本的冲突。例如，用户从"偏好 2 空格缩进"变为"偏好 4 空格缩进"——系统不应该同时保留两条互相矛盾的记忆，而应该用新版覆盖旧版，并保留变更历史以供审计。OpenViking 在 Memory 类型上实现了简单的版本控制：新版覆盖旧版用于当前决策，但变更记录被保留在 history 目录下。

4.4 跨会话记忆共享与隔离

在复杂的生产场景中，Agent 可能同时服务多个项目或多个用户。记忆系统需要同时支持"共享"和"隔离"两个看似矛盾的需求。共享指的是：用户在项目 A 中积累的编码偏好应该自动适用于项目 B。隔离指的是：项目 A 的技术规范不应该泄露到项目 B 的上下文中。OpenViking 通过 Viking URI 的 scope 机制实现了这一点——viking://user/ 下的记忆全局共享，viking://resources/my_project/ 下的记忆仅对该项目可见。

记忆层级作用域典型内容共享策略
全局用户记忆所有项目、所有会话个人偏好、技术栈、工作习惯始终共享
项目级记忆单个项目内项目规范、架构决策、团队成员项目内共享，跨项目隔离
会话级记忆单次会话内当前任务的中间状态、临时笔记仅当前会话可见
子 Agent 记忆子 Agent 生命周期内子任务的执行上下文隔离，完成后蒸馏回父级

OpenViking 的 Claude Code 插件实测数据：在跨 3 个项目、15 次会话的长期使用中，全局用户记忆的复用率达到 87%——用户不需要在每个新会话中重复说明自己的编码偏好。同时项目级记忆的隔离成功率达到 100%——没有任何项目 A 的规范泄露到项目 B 的上下文中。子 Agent 的隔离会话机制确保了并行任务的记忆不会互相污染。

记忆蒸馏的关键洞察是"不是所有交互都值得记住"——一次随意的闲聊和一次关键的架构决策，信息价值天差地别。蒸馏引擎的核心能力是区分"噪音"和"信号"，只把信号沉淀为长期记忆。这也是为什么需要异步后台执行：判断信息价值需要完整的会话上下文，不能在对话中途做。

五、从 Prompt Engineering 到 Context Engineering：范式转变

如果说 Prompt Engineering 是"精心构造你告诉模型什么"，那么 Context Engineering 就是"精心构造模型能看到什么"。前者关注的是提示词的措辞和结构，后者关注的是整个信息环境的组织和管理。这是 Agent 系统从"玩具"走向"生产"的关键范式转变。

5.1 为什么 Prompt Engineering 不够了

Prompt Engineering 的假设是：Agent 需要的所有信息可以一次性塞入提示词中。这在短任务中可行，但在长链路、多轮交互、跨会话的生产场景中，这个假设彻底崩溃。上下文窗口有物理上限（即使 200K tokens 也会在长任务中耗尽），不同任务阶段需要不同的信息子集，而且信息的时效性和优先级在不断变化。这些问题不是"写更好的提示词"能解决的。

5.2 Context Engineering 的核心思想

Context Engineering 将 Agent 的信息环境视为一个需要主动管理的"上下文操作系统"。它关注四个核心问题：哪些信息应该被加载（选择性）、以什么粒度加载（分层性）、什么时候加载（时效性）、加载后如何组织（结构性）。Manus 团队在生产实践中发现，把文件系统直接作为 Agent 的上下文——"大小无限、天然持久、Agent 可直接操作"——是最有效的 Context Engineering 实现方式之一。

5.3 动态上下文加载：按任务阶段感知

一个成熟的 Context Engineering 系统会根据 Agent 当前所处的任务阶段动态调整加载策略。在需求分析阶段，加载用户偏好和项目背景；在工具调用阶段，加载工具说明和 API 文档；在结果复盘阶段，加载历史案例和质量标准。这种阶段感知避免了在错误的时间加载正确的信息——一条在分析阶段无关紧要的 API 细节，可能在实现阶段至关重要。

5.4 可观测性：检索轨迹的完整追溯

传统 RAG 的检索过程是一个黑箱——你不知道系统为什么返回了这些结果、漏掉了哪些结果。OpenViking 的一个关键设计是检索轨迹可视化——系统完整记录每次检索的目录浏览路径、文件定位过程、各层级的命中情况。当 Agent 的输出出现上下文相关的问题时，开发者可以像查看浏览器历史记录一样，追溯整个检索链路，精确定位是哪一步的上下文加载出了问题。

Context Engineering 不是 Prompt Engineering 的替代品，而是它的超集。一个好的提示词依然重要，但如果模型看到的整个信息环境本身就是混乱的、过时的、不相关的，再精妙的提示词也无法产出高质量的结果。Context Engineering 确保模型的"信息食谱"是健康的。

8.2 文件系统范式 vs 向量数据库范式

2026 年 Agent 记忆领域最深刻的架构转变是：向量数据库从"默认答案"降级为"仅用于 RAG 的工具"，而文件系统上升为 Agent 工作记忆的首选范式。这不是时尚的轮回，而是结构性需求决定的——Agent 的工作状态需要精确寻址、原地修改、保持顺序，这三件事文件系统天然支持，而 k-近邻索引一件都做不到。

向量数据库在 Agent 记忆场景中的三个致命缺陷。第一，模糊匹配不等于精确寻址——Agent 需要"我两步前写的那个文件"，而 k-NN 只能返回"语义最接近的向量"，可能根本不是同一个东西。第二，不支持原地修改——当一条记忆需要更新时，向量库必须重新 embedding 并 upsert，旧的向量仍然可能被检索到。第三，丢失结构信息——所有东西变成向量后，分类、层级、优先级等元信息全部丢失。

8.3 向量数据库的正确定位

向量数据库并没有"失败"——它被归位到了最适合它的场景：对大量外部语料的模糊语义检索（即传统 RAG）。当 Agent 需要在百万级文档中找到"与当前问题语义最相关的片段"时，向量检索仍然是最佳选择。但把向量检索当作 Agent 的记忆管理方案，就像用搜索引擎管理你的个人文件——能找到东西，但管理不了。

需求场景文件系统向量数据库最佳选择
当前任务的工作状态（计划、草稿、中间产物）天然适合：可寻址、可修改、有顺序不适合：k-NN 无法精确定位文件系统

大规模外部语料的模糊检索无法扩展——需要 grep 百万文档这是 RAG 的核心场景向量数据库
突破上下文窗口限制容量无限，按需加载页面内容容量足够，但召回内容仍需塞入窗口两者结合

8.4 最佳实践：混合架构

生产级 Agent 系统通常采用混合架构：文件系统管理 Agent 自身的工作记忆和结构化上下文，向量数据库管理外部知识库的语义检索。OpenViking 的实现就体现了这种混合——它用 RAGFS 文件系统管理结构化上下文，同时内置向量索引用于语义搜索召回。两者协同工作：向量搜索先在 L0 摘要层做粗召回，然后在文件系统的目录结构中做精确定位和深度加载。

2026 年的共识正在形成：向量数据库是 Agent 的"外部搜索引擎"，文件系统是 Agent 的"内部工作台"。一个成熟的 Agent 记忆系统需要两者兼备，但绝不能把两者混为一谈。OpenViking 的价值不在于它发明了什么新技术，而在于它率先把这个架构分离做对了。

8.5 技术选型决策树

在实际项目中选择记忆架构时，可以按照以下决策路径进行判断。核心原则是"按需选型"——不同类型的上下文需要不同的存储和检索机制，没有一种方案能通吃所有场景。

九、Do / Don't

  • 用层级结构组织记忆，将所有上下文按类型严格分类存储，避免混杂
  • 使用 L0/L1/L2 三层分级按需加载，控制 Token 消耗
  • 目录递归检索替代平面搜索
  • 检索轨迹可视化，保留检索日志支持事后调试
  • 自动提取 Agent 执行经验
  • 为每条记忆设置生命周期，定期清理过期数据
  • 根据任务阶段动态调整加载策略
  • 让 Agent 可以直接读写文件作为工作记忆
  • 把所有记忆都塞进向量库用相似度检索、平铺在一个目录
  • 只读全文或只看摘要，每次调用全量加载所有上下文
  • 设硬上限忽略超出部分
  • 忽略记忆的时效性，让过期数据持续干扰
  • 假设"更多信息 = 更好结果"
  • 把用户偏好和项目规范混在同一层级
  • 忽略级联更新问题
  • 让 Agent 的记忆变成只增不减的"黑箱"，不自动沉淀执行经验

十、生产案例

生产验证：OpenViking 在 10 万+ 文档的知识库场景中：(1) 三层分级加载（L0 摘要/L1 概述/L2 全文）将平均检索延迟从 800ms 降至 120ms（-85%），因为 90% 的查询只需 L0/L1 层；(2) 目录递归检索（先定位目录再检索文件）比全量向量搜索的准确率从 72% 提升至 89%（+17pp），因为缩小了搜索空间；(3) Token 消耗减少 83-96%（L0 仅 ~50 tokens vs L2 可能数千），月度 API 成本从 $1,200 降至 $180。关键设计：每个文档自动生成 L0（一句话摘要）和 L1（段落概述），存储在内存中供快速匹配。

OpenViking 记忆系统的核心创新：三层分级加载（L0 索引 ~100 tokens 常驻 → L1 摘要按需加载 → L2 全文检索获取），将检索延迟从 800ms 降至 120ms（-85%），Token 消耗减少 83-96%。本质是用"信息密度分层"解决"上下文窗口有限 vs 知识量无限"的矛盾。

Q&A

OpenViking 和主流记忆系统的核心差异是什么？

主流方案（如 Claude Code）是平面向量搜索——记忆存成 Markdown 文件，检索时扫描前几十行元数据，用便宜模型挑几条读全文。OpenViking 是层级化虚拟文件系统——有目录结构（resources/user/agent），每个节点有三层粒度（L0 摘要/L1 概述/L2 全文），检索时沿层级递归下钻，Token 成本降低 83%-96%。

三层分级加载是怎么降低 Token 成本的？

L0 层约 100 token（一句话摘要）用于快速筛选，L1 层约 2000 token（核心信息+使用场景）用于深度评估，L2 层是完整内容只在实际使用时加载。大部分时候只需要 L0+L1 就能判断是否需要加载全文，避免每次都读全文导致的 Token 浪费。

目录递归检索相比平面向量搜索有什么优势？

平面向量搜索是一次性判断，没有探索能力。目录递归检索是四步流程：全局搜索→高分目录内搜索→分数传播→收敛检测。利用了层级结构提供的先验信息，可以更精准地定位相关记忆，同时检索轨迹可视化，每一步都可追踪和诊断。

OpenViking 的目录递归检索和 RAG 的向量检索可以结合使用吗？

可以且推荐结合。两种结合方式：(1) 向量检索做全局粗筛（从所有节点中快速找到 Top 20 候选），目录递归做局部精排（沿层级结构深入验证）；(2) 目录递归先定位相关目录，目录内用向量检索精确匹配。生产数据：纯向量检索准确率 72%，纯目录递归 78%，两者结合后 89%（互补效应）。核心洞见：向量检索擅长"语义相似性"（找内容相近的），目录递归擅长"结构相关性"（找逻辑关联的），两者解决不同维度的问题。

OpenViking 目前最大的未解决问题是什么？

级联更新：当一个上游事实变化后，依赖它的下游事实能否自动更新？目前准确率只有 3%。例如用户之前说"我喜欢 Python"，后来改成"我转 Go 了"，之前基于 Python 偏好生成的下游记忆能否自动更新？OpenViking 通过层级结构部分缓解了这个问题，但仍依赖模型推理能力。

OpenViking 的 L0/L1/L2 分层加载与传统 RAG 的 chunk 分片有什么本质区别？
传统 RAG 的 chunk 分片是"把一个长文档切成多个等长大小的块"，每个块独立存储、独立检索，它们之间没有层级关系，也不代表不同的信息粒度。L0/L1/L2 是"对同一条信息生成三种不同粒度的表示"——L0 是浓缩摘要用于快速筛选，L1 是结构化概览用于导航决策，L2 是完整原文用于深度使用。关键区别在于：chunk 分片是"横向切割"（同一粒度的多个碎片），L0/L1/L2 是"纵向分层"（同一信息的不同精度）。前者丢失了全局结构，后者保留了完整上下文。
为什么 Agent 记忆需要区分六种类型？不能统一存储吗？
六种类型对应六种截然不同的生命周期策略和检索优先级。Profile（用户画像）几乎永不过期，优先级最高——模型应该始终尊重用户的技术栈偏好。Events（事件记录）有中期保质期，90 天不引用就应该归档。Cases（案例）需要去重合并——同类问题出现 5 次，应该沉淀为一个精华案例而非保留 5 条冗余记录。如果统一存储，系统无法区分"应该永久保留的用户偏好"和"应该下周清理的临时调试信息"，最终导致记忆库被过时数据淹没。
目录递归检索的计算成本是否比向量检索更高？
实际上目录递归检索的总成本通常更低。虽然它多了一个"目录定位"的步骤，但这一步可以在 L0 摘要层完成（成本极低），一旦定位到正确的目录，后续的精细搜索范围大幅缩小。传统向量检索需要在所有碎片中做全量相似度计算，当记忆库规模增大时计算量线性增长。目录递归检索通过分层剪枝，将搜索空间从 O(N) 降低到 O(log N)。OpenViking 的实测数据显示，在 500+ 条记忆的规模下，目录递归检索的延迟比全量向量检索低 40%，同时准确率高出 2.8 倍。
记忆蒸馏的"异步后台执行"会不会导致信息丢失？
设计上做了三重保障。第一，会话过程中的所有对话内容会先暂存到 Working Memory（同步写入），蒸馏引擎从 Working Memory 中提取长期记忆——即使蒸馏过程崩溃，原始对话数据仍然安全。第二，OpenViking 的 PreCompact 钩子会在上下文窗口被压缩之前强制提交当前会话记录，确保任何细节在模型遗忘之前已经被持久化。第三，蒸馏是"增量提取"而非"替换"——它只添加新的长期记忆，不会删除已有的记忆，避免了误删风险。
从 Prompt Engineering 到 Context Engineering 的转变，对开发者意味着什么？
这意味着开发者的核心技能从"写好提示词"扩展到了"设计好信息架构"。具体来说，开发者需要思考：Agent 需要哪些类型的上下文、这些上下文从哪里来、如何分类存储、什么时候加载什么粒度、过时的信息如何清理。这更像是数据库管理员（DBA）的工作而非文案撰写者的工作。Manus 团队的实践表明，Context Engineering 的投入产出比远高于 Prompt Engineering——优化信息架构带来的效果提升通常是优化提示词措辞的 3-5 倍。
文件系统范式会不会成为新的瓶颈？什么场景下它不适用？
文件系统范式在两个场景下可能不适用。第一是超大规模知识库检索——当 Agent 需要在百万级外部文档中搜索时，文件系统无法替代向量数据库的近似最近邻搜索能力，这就是为什么生产系统采用混合架构。第二是高度动态的实时数据——当信息更新频率达到毫秒级别时，文件系统的写入和索引更新可能跟不上。文件系统范式最适合的场景是 Agent 的工作记忆和结构化上下文管理——这些场景下信息量适中（数千到数万条）、需要精确寻址、需要原地修改、需要保持结构关系。
如何在现有 Agent 框架（如 LangGraph、CrewAI）中集成 OpenViking 的记忆系统？
OpenViking 提供了标准的 MCP（Model Context Protocol）Server 接口，可以作为任何支持 MCP 的 Agent 框架的记忆后端。集成步骤通常包括：安装 OpenViking 并配置 embedding 和存储后端，启动 MCP Server，在 Agent 框架中注册 OpenViking 的 MCP 工具（search、read、list、remember）。更简便的方式是使用 Claude Code 或 Codex 的 OpenViking 插件——一条命令安装，自动注册所有钩子和 MCP 服务，零代码改动。插件的写入路径是异步的，不会对对话流产生可感知的延迟。
