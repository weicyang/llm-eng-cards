A39 · 摘要压缩工程：结构化填表方案

Summary Compression — Schema 填表 vs 自由总结 + 先完整返回 vs 子 Agent 封装

一、核心问题：摘要信息丢失

Manus 联合创始人 Peak Ji 提出：结构化填表（Schema）是解决 AI 摘要信息丢失的核心方案。开放式指令（"请总结"）导致输出不稳定，而强制模型按预设模板输出可确保关键信息 100% 保留。

方案做法效果
❌ 自由总结"请总结这段对话"关键要素随机丢失
✅ 结构化填表按 Schema 模板填写（修改文件/用户目标/任务进度）关键要素保留率从随机→确定性

信息为什么会丢失

自由总结丢失信息有三个机制：(1) 近因偏差 — 模型注意力集中在最近几轮，早期关键信息（如最初提到的文件路径、约束条件）最先被稀释；(2) 指令模糊 — "请总结"没有定义什么算"重要"，模型只能按自己的先验采样，同一输入每次输出都不同；(3) 级联压缩 — 多轮场景下摘要会被再次摘要，误差逐层累积，三轮压缩后关键要素几乎丢失殆尽。

可以这样理解：自由总结像口头交接工作 — 对方记住什么是随机的；结构化填表像交接班检查表 — 哪几项必须勾选由制度决定，不依赖人的记性。工程化的本质就是把"模型自觉"替换为"系统强制"，把不可控的采样过程变成可验收的填表过程。

二、结构化填表 Schema 设计

Claude Code 的压缩 API 使用九章结构化摘要，OpenAI 推荐使用六维度摘要。核心原则：字段数量 5-9 个为宜，每个字段有类型约束。

字段类型说明示例
修改文件string[]本轮涉及的文件路径["src/main.py", "tests/test.py"]
用户目标string用户本轮的核心意图"修复登录页 500 错误"
任务进度enumnot_started/in_progress/done"in_progress"
关键决策string[]本轮做出的重要决策["选择 JWT 替代 Session"]
待解决问题string[]遗留问题["Token 过期处理未实现"]
下一步行动string下一步该做什么"实现 Token 刷新接口"
设计三原则：(1) 必要性 — 只包含后续任务真正需要的字段；(2) 类型约束 — 每个字段有明确类型，减少模型自由发挥；(3) 可验证性 — 字段值可被程序化检查（路径是否存在、状态是否合法）。

生产示例：Schema 校验流水线

某代码 Agent 的生产实现中，填表输出要过三层程序化校验：第一层类型校验（字段缺失、类型不符 → 原样重试）；第二层语义校验（文件路径必须存在于工作区、枚举值必须在合法集合内、"下一步行动"不得为空字符串）；第三层一致性校验（任务进度=done 但待解决问题非空 → 标记为可疑并升级人工审查）。线上数据：校验层每天拦截约 6% 的不合格摘要，经自动重试后最终通过率为 99.7%，剩余 0.3% 走降级路径（保留原文不压缩）。

Schema 的真正价值不在"约束输出格式"，而在让摘要变得可校验、可重试、可降级 — 自由文本无法被程序验证，表格字段可以。这就是"工程"和"提示词艺术"的分界线：前者出了问题能定位、能修复，后者出了问题只能换个说法再试一次。

三、五大压缩方法分类

Agent 上下文压缩方法可归为五大类，从轻到重：

  • 丢弃保留（滑动窗口 / 固定截断）：保留率低（只保留最近 N 轮），实现复杂度极低 → 简单聊天、非关键场景
  • 摘要重构（LLM 生成摘要替代原文）：保留率中（47-98%，取决于 Schema），复杂度中 → 多轮对话、项目管理
  • 向量检索（Embedding 存入向量库，按需召回）：保留率中高（语义匹配召回），复杂度高 → 长期记忆、知识库
  • 模型原生（KV Cache 压缩，PagedAttention 等）：保留率高（无损/近无损），复杂度极高 → 自建推理服务
  • 写入前置（关键信息提前写入外部文件/数据库）：保留率最高（完整保留），复杂度中 → 长期任务、代码 Agent

四类主流摘要压缩方案的压缩比与信息保留率量化对比（自由摘要 5-10:1 ~70% / Schema 填表 8-15:1 ~85% / 关键句提取 3-5:1 ~60% / 状态追踪 10-20:1 ~90%）见 A37 · 大模型上下文管理策略。

选择原则：简单聊天 → 丢弃保留（成本最低）；生产 Agent → 摘要重构 + 写入前置（平衡效果与成本）；自建推理 → 模型原生（最高性能但门槛最高）。

摘要重构执行流水线

生产中最常用的"摘要重构"类方法，其完整压缩流水线包含五个阶段，每个阶段都有明确的失败退路：

摘要重构压缩流水线（生产标准五阶段）: [1] 触发判断 [2] 区域划分 [3] Schema 填表 上下文 ≥ 70%? → 冻结区: 最近 5 轮 → LLM 按 6 字段模板填写 │ (原样保留, 不动) temperature=0 + few-shot 示例 否 → 跳过本轮 压缩区: 更早的历史 │ │ │ │ ▼ ▼ ▼ [5] 回写与标记 [4] 程序化校验 摘要替换压缩区 ← 路径存在? 枚举合法? 附压缩标记+时间戳 字段缺失? → 自动重试 (≤2 次) 原文归档到磁盘 仍失败 → 降级为滑动窗口截断 关键指标: 单次压缩延迟 P50 ≈ 380ms / P99 ≈ 1.2s 压缩比通常 5:1 ~ 8:1 (40K → 5~8K tokens) 压缩调用成本约占被压缩内容价值的 1/11

注意流水线的降级链方向：填表失败就退化为截断，宁可要确定性的低保留率，也不要赌博式的高保留率。生产系统中任何依赖 LLM 输出的环节都必须有一条不依赖 LLM 的退路 — 压缩器本身挂掉时，主链路必须还能继续跑。

四、水位线触发机制

什么时候触发压缩？不是"等上下文满了再压缩"（太晚），而是设置多级水位线提前触发：

四级水位线: 60% 上下文使用 → 预警（开始准备压缩） └── 动作: 标记低优先级内容，准备摘要模板 70% 上下文使用 → 轻度压缩 └── 动作: 压缩最早 30% 的对话历史为摘要 85% 上下文使用 → 重度压缩 └── 动作: 仅保留系统提示 + 最近 5 轮 + 关键摘要 100% 上下文使用 → 紧急重置 └── 动作: 生成完整摘要 → 重置上下文 → 从摘要继续

滑动窗口策略详解

滑动窗口是丢弃保留类的基线策略，但生产实现远不止"保留最近 N 轮" — 核心要解决"窗口边缘恰好切断关键信息"的问题：

滑动窗口策略（三区结构，以 128K 上下文、窗口 40K 为例）: 第1轮 第2轮 ... 第18轮 │ 第19轮 ─────── 第32轮 │ 第33轮 ... 第41轮(当前) └────── 摘要区 ──────┘ └───── 锚点区 ─────┘ └────── 滑动窗口 ──────┘ 已压缩为摘要 任务目标 / 文件清单 完整原始对话 (≈2K tokens) 钉在窗口头部 随新轮次向后滑动 (≈1K, 永不移除) 滑动规则: ① 新轮进入窗口 → 窗口最老的轮次被挤出 ② 被挤出的轮次不消失 → 进入摘要区, 增量合并进摘要 ③ 锚点区内容(用户目标/关键决策)被钉住, 只更新不移除 ④ 摘要区超过 8K → 触发二次压缩(摘要的摘要)

这套结构的本质是 冷热分层：滑动窗口存 热数据（最近对话），锚点区存 钉住数据（任务目标、关键决策），摘要区存 冷数据（压缩历史）。实测对比：朴素滑动窗口的关键要素保留率约 35%，三区结构可提升到约 80%，而实现复杂度只增加一个增量摘要调用。

Hermes 双层触发

Hermes Agent 采用 50%/85% 双触发：50% 时做轻量摘要（保留最近 10 轮完整 + 之前摘要），85% 时做深度压缩（仅保留系统提示 + 当前任务摘要 + 最近 3 轮）。双触发的优势：避免一次性大幅压缩导致信息断崖。

Claude Code Compaction API

从摘要字段设计视角看：Claude Code 的压缩 API 在上下文达到 80% 时自动触发，生成九章结构化摘要（覆盖文件变更、用户目标、任务进度、关键决策等）替代原始历史，压缩后保留"压缩标记"，Agent 知道哪些内容是摘要的、哪些是原始的。其背后的 L1 工具裁剪 → L2 尾部修剪 → L3 全局摘要三层级联机制与 Prompt Cache 经济学，详见 A37 · 大模型上下文管理策略。

水位线设计借鉴的是 水库调度：不是等大坝溢流才泄洪，而是按预警水位分级泄洪。上下文管理同理 — 每一级压缩都要为下一级预留缓冲。如果等到 100% 才处理，压缩动作本身（需要一次完整的 LLM 调用）可能已经没有 token 空间执行，陷入"太满了以至于没法压缩"的死锁。这就是为什么紧急重置这一级必须永远保留至少 10% 的空余预算。

五、六大 Agent 压缩策略对比

腾讯技术工程横向对比了七种主流 Agent 的压缩策略：

Agent压缩策略触发时机特点
Claude Code五段流水线80% 上下文结构化九章摘要 + 压缩标记
Codex CLI滑动窗口 + 摘要固定阈值保留最近 N 轮 + 历史摘要
OpenCode全量保留 + 按需检索不压缩依赖大窗口（200K+）
Cline子 Agent 隔离任务切换时每个文件/任务独立上下文
Cursor语义摘要 + 文件引用自动对话摘要 + 文件内容按需加载
Amp分层记忆多级水位线短期/中期/长期三级记忆
MemGPTOS 式虚拟内存上下文满时主存（上下文）+ 外存（文件），页式换入换出

值得单独展开的是 MemGPT 的 页式换入换出：它把上下文切成固定大小的"页"，由模型自己调用类似 page_in/page_out 的函数管理内存，操作系统换页靠缺页中断，MemGPT 换页靠模型对"我需要更早的信息"的自主判断。这条路线的难点在于换页决策本身也消耗推理能力 — 模型既当运动员又当裁判，小模型上容易顾此失彼，因此目前更多见于研究型系统而非一线生产。

趋势：从"被动压缩"（上下文满了才处理）到"主动管理"（多级水位线提前触发）。MemGPT 的 OS 式虚拟内存思路最有前瞻性——把上下文当 RAM、文件系统当硬盘，实现页式换入换出。

选择压缩策略，本质是回答三个问题：何时压（触发时机）、压什么（区域划分）、压完放哪（上下文内摘要 vs 外部文件）。上表六种 Agent 的差异只是这三问的答案组合不同 — Claude Code 选"80% 触发 + 九章填表 + 上下文内替换"，MemGPT 选"满时触发 + 页式组织 + 外存按需换入"，OpenCode 干脆选"不压、靠大窗口硬扛"。没有最优答案，只有与你的窗口大小、成本预算、任务时长最匹配的答案。

六、Trimming vs Compression

OpenAI Cookbook 将上下文管理分为两种策略：

维度Trimming（裁剪）Compression（压缩）
做法直接丢弃最早的消息用 LLM 生成摘要替代原文
信息损失高（完全丢弃）中（保留关键信息）
成本零（不需要额外调用）需额外 LLM 调用
延迟零增加 200-500ms
适用场景简单聊天、成本敏感复杂 Agent、信息敏感

混合策略：先 Compression 再 Trimming — 当上下文接近限制时，先将早期对话压缩为摘要，如果仍然超限再裁剪最老的摘要。这样既保留了关键信息，又控制了成本。

生产示例：某客服 Agent 实测：纯 Trimming 在超过 15 轮的会话中导致 19% 的"忘了前面说过的话"类投诉；改用混合策略（先把早期对话压缩成摘要，超限再裁剪最老摘要）后，投诉率降至 3%，而每会话 token 开销仅增加 8%（多一次摘要调用）。这笔账的教训：信息丢失成本（用户流失、人工接管）通常远高于 压缩调用成本，不要为了省一次 LLM 调用而牺牲记忆。

七、两套搜索策略

策略适用场景操作风险对冲
先完整返回简单搜索原始结果直接追加上下文强制写入关键洞见文件
子 Agent 封装复杂搜索高阶函数触发独立子 Agent 处理天然隔离复杂性

工程权衡

  • 简单搜索优先效率（1 次 LLM 调用），直接返回原始结果
  • 复杂搜索用子 Agent 封装，隔离复杂性，避免主 Agent 上下文被污染
  • 不立即卸载：搜索结果暂时保留，后续任务可能还需要

判断的量化标准

"简单"与"复杂"搜索的边界需要量化而不是凭感觉：结果条数 ≤ 5 且单条 ≤ 800 tokens → 先完整返回；结果条数 > 5 或需要跨文件/跨模块关联推理 → 子 Agent 封装。生产经验：把复杂搜索误判为简单搜索，主 Agent 上下文会一次性暴涨 8K+，提前触发压缩、打断任务节奏；把简单搜索误判为复杂搜索，则浪费一次子 Agent 调用（约 3-5K tokens、约 1.5s 延迟）。上下文污染 是最难察觉的隐性成本 — 它不报错，只是让模型悄悄变"笨"。

八、生产案例

生产数据：Manus Agent 系统采用结构化填表后，摘要关键要素保留率从自由总结的 47% 提升至 98%。Schema 包含 5 个核心字段（修改文件/用户目标/任务进度/待解决问题/下一步行动），每个字段有类型约束（如"修改文件"必须是路径数组）。子 Agent 封装策略在复杂搜索场景中，主 Agent 上下文占用减少 72%（从 8K tokens 降至 2.2K），同时搜索结果质量不变。先完整返回策略在简单搜索中节省了 1 次 LLM 调用（约 $0.02/次）。

案例聚焦：某 7×24 编码 Agent 的压缩改造

该 Agent 改造前平均会话 40+ 轮，上下文溢出率 23%，频繁出现"忘记前面需求"导致的返工；引入结构化填表 + 三区滑动窗口 + 双水位触发后，30 天线上数据：

指标改造前改造后变化
关键要素保留率47%98%+51pp
平均会话输入 tokens128K46K-64%
上下文溢出率23%1.8%-21.2pp
任务一次完成率71%89%+18pp
月推理成本$8,400$3,100-63%
压缩附加延迟 P99—1.2s可接受（异步触发）
关键数字解读：token 开销降 64% 不是因为"丢得更多"，而是因为"压得更准" — Schema 填表的确定性让摘要不再需要"以防万一"的冗余表述；溢出率降到 1.8% 来自双水位在 70% 提前触发，为长工具输出预留了 30% 缓冲。核算下来 压缩 ROI =（节省的 token 成本 − 压缩调用成本）/ 压缩调用成本 ≈ 11:1 — 每花 1 元做压缩，省下 11 元上下文开销。
摘要压缩的核心原则：结构化填表（Schema）比自由总结保留率从 47% 提升至 98%。本质转变：从"模型自主决定保留什么"变为"开发者决定保留什么"，从随机性变为确定性。简单搜索用先完整返回（效率高），复杂搜索用子 Agent 封装（隔离复杂性）。
  • 用 Schema 定义摘要字段（修改文件/用户目标/任务进度/待解决/下一步）
  • 每个字段有类型约束（如路径数组、枚举状态）
  • 简单搜索用先完整返回（1 次调用）
  • 复杂搜索用子 Agent 封装（上下文隔离）
  • 不要说"请总结"（模型随机决定保留什么）
  • 不要为了"全面"添加无用字段
  • 不要在简单搜索也用子 Agent（过度工程化）
  • 不要忽略字段可验证性（路径是否存在、状态是否合法）

Q&A

Q1：结构化填表为什么比自由总结好？
自由总结（"请总结"）导致模型随机决定保留什么、丢弃什么，关键信息保留率仅 47%。结构化填表（Schema）强制模型按预设字段输出（如修改文件/用户目标/任务进度），确保关键要素保留率提升至 98%。本质：从"模型自主决定保留什么"变为"开发者决定保留什么"，从随机性变为确定性。
Q2：先完整返回和子 Agent 封装怎么选？
简单搜索用"先完整返回"（1 次 LLM 调用，效率高，原始结果直接追加上下文）；复杂搜索用"子 Agent 封装"（独立子 Agent 处理，隔离复杂性，主 Agent 上下文占用减少 72%）。核心原则：效率优先，复杂隔离。风险对冲：简单搜索强制写入关键洞见文件（防止信息随上下文压缩丢失），复杂搜索天然隔离。
Q3：Schema 的字段设计有什么原则？
三条原则：(1) 必要性 — 只包含后续任务真正需要的字段（如"修改文件"、"用户目标"、"任务进度"），不要为了"全面"添加无用字段；(2) 类型约束 — 每个字段有明确类型（如"修改文件"必须是路径数组，不能是自由文本），减少模型"自由发挥"的空间；(3) 可验证性 — 字段值可以被程序化检查（如路径是否存在、状态是否合法），支持自动校验。生产经验：5 个核心字段通常足够覆盖 95% 的摘要需求。
Q4：为什么"不立即卸载"搜索结果？
搜索结果暂时保留在上下文中，因为后续任务可能还需要这些信息。立即卸载的问题：(1) 如果后续步骤需要引用之前的搜索结果，就必须重新搜索（浪费 Token 和延迟）；(2) Agent 可能在多个步骤间来回引用同一信息。正确做法：搜索结果暂时保留，在确认不再需要时（如任务完成或上下文接近窗口限制时）才卸载。配合"强制写入关键洞见文件"做双重保险 — 即使上下文被压缩，关键信息已持久化到文件。
Q5：结构化填表和 RAG 检索的关系是什么？
两者互补：(1) RAG 检索是"从知识库获取信息"（输入端），结构化填表是"压缩和保留信息"（输出端）；(2) RAG 注入的信息通过结构化填表保留关键要素，避免在后续对话中被稀释丢失。工作流：RAG 检索 → 注入上下文 → Agent 处理 → 结构化填表压缩 → 保留到下一轮。这样形成"精准获取 → 确定性保留"的闭环，解决了"获取了但后来忘了"的问题。
Q6：摘要本身也消耗 token、增加延迟，值得吗？
值得，但要算总账。一次压缩调用约消耗 2-5K tokens（输入原文 + 输出摘要），增加 200-500ms 延迟；但不压缩的代价是后续每一轮都携带完整历史，成本随轮数线性甚至平方增长。以 40 轮会话实测：不压缩的累计输入约 2.56M tokens 当量，采用压缩后约 0.95M，整体成本降约 60%。工程技巧：把压缩触发放在用户思考间隙异步执行（如等待用户输入时），附加延迟对用户完全无感，P99 的 1.2s 延迟因此不构成体验问题。
Q7：压缩后万一丢了关键信息怎么办？
三道兜底：(1) 原文归档 — 被压缩的原文写入磁盘而不是删除，Agent 发现信息缺失时可凭压缩标记按轮次号回捞原文；(2) 写入前置 — 关键信息（文件路径、用户目标、关键决策）在产生时就写入 TODO.md 等外部文件，不依赖上下文里的任何摘要，这是保留率最高（100%）的策略；(3) 主动坦白 — 系统提示明确告诉 Agent"部分历史已被压缩，若缺少细节先向用户确认，不要自行猜测"。核心原则：摘要只是第一道防线，永远不要让它成为唯一防线。
Q8：为什么不直接用 1M 长上下文模型，绕过压缩？
三个原因：(1) 成本 — 长窗口不等于便宜，1M tokens 输入按模型不同约 $1-15，40 轮会话硬扛满窗口的账单是压缩方案的 3-5 倍；(2) 中间迷失效应（lost in the middle）— 窗口装得下不代表模型用得好，中段信息的召回率显著低于首尾，压缩 + 锚点钉住反而提升有效利用率；(3) 延迟 — 100K+ tokens 的 prefill 通常需要 5-30 秒，每轮都扛满历史会让首 token 延迟彻底失控。长窗口与压缩不是对立关系：大窗口模型同样需要水位线管理，只是水位线可以划得更靠后。
