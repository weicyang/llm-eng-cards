EV07 · Agent 评估六种互补工具

Agent Evaluation — 瑞士奶酪模型：自动评估 + 生产监控 + A/B测试 + 用户反馈 + 人工审查 + 对话分析

一、为什么单一评估工具不够

评估 Agent 就像给病人做体检：只测血压（自动评估）不够，还需要验血（生产监控）、问诊（用户反馈）、专家会诊（人工审查）。单一工具只能看到问题的一面，这就是瑞士奶酪模型——每层都有洞，但多层叠加就能堵住所有漏洞。

为什么自动化评估会给你"虚假安全感"？

自动化评估的测试用例是人工设计的，覆盖不了真实世界的长尾场景。Agent 在测试集上 95 分，但生产中可能只有 60 分——因为用户会用你想不到的方式使用系统。这就是Goodhart 定律的体现：当一个指标变成目标时，它就不再是好指标。

理解评估覆盖率陷阱：自动化测试用例集通常只覆盖 60-70% 的真实场景分布。剩余 30-40% 的"暗区"只能通过其他工具发现。每个工具都有自己的覆盖特性和盲区，这就是为什么互补而非替代是关键原则。

生产监控的核心指标体系

生产监控不只是"看日志"，需要建立三层指标体系：

  • 系统层：P50/P95/P99 延迟、错误率、吞吐量（TPS）、Token 消耗量（成本监控）
  • 行为层：任务完成率、平均对话轮次、工具调用成功率、回退率（用户放弃比例）
  • 质量层：幻觉率（抽样检测）、一致性得分（同一问题多次回答的差异度）、安全违规率

告警策略建议：系统层指标用阈值告警（如 P99 > 5s），行为层指标用趋势告警（如任务完成率连续 3 天下降），质量层指标用周期性检测（如每日抽样 100 条）。

三、主流评估框架深度对比

选择评估框架不是"哪个最好"的问题，而是"哪些互补"的问题。每个框架解决评估问题的不同切面：RAGAS 专注检索质量，LangSmith 提供全链路可观测性，DeepEval 侧重 LLM-as-Judge 自动化打分，Promptfoo 面向 Prompt 工程快速迭代。

RAGAS：RAG 检索质量评估

RAGAS 提供四个核心指标：Faithfulness（忠实度：回答是否基于检索到的上下文）、Answer Relevancy（回答相关性）、Context Precision（上下文精确度）、Context Recall（上下文召回率）。它使用 LLM 自身来评估这些维度，无需人工标注数据。

LangSmith：全链路可观测性平台

LangSmith 由 LangChain 团队开发，提供从 Prompt 调试到生产监控的完整能力。核心优势是Trace 级可视化：每一步 LLM 调用、工具调用、检索操作都可追踪，快速定位"到底是哪一步出了问题"。

DeepEval：pytest 风格的 LLM 测试

DeepEval 把 LLM 评估包装成类似 pytest 的体验。内置 14+ 评估指标（包括幻觉检测、毒性检测、偏见检测等），支持 @pytest.mark.parametrize 风格的批量测试。适合需要在 CI/CD 中集成 LLM 质量门禁的团队。

Promptfoo：Prompt 工程的瑞士军刀

Promptfoo 专为 Prompt 工程优化，支持 YAML 定义测试用例、多模型并行对比（如 GPT-4 vs Claude vs Gemini）、自定义断言逻辑。核心优势是反馈延迟极短：修改 Prompt → 运行测试 → 看到结果，整个循环 < 30 秒。缺点是缺乏生产监控能力，需要与其他工具配合。

Arize Phoenix：生产级可观测性

Arize Phoenix 基于 OpenTelemetry 标准，提供从追踪到告警的完整生产监控能力。核心特性包括：Trace 级可视化（每个 LLM 调用、工具调用、检索操作的完整链路）、嵌入向量分析（发现语义漂移）、自动异常检测。与 LangSmith 的区别：Phoenix 开源且专注生产监控，LangSmith 覆盖开发到生产全流程但为闭源 SaaS。

四、组合使用策略

上线前

  • 自动化评估跑全量测试（质量门禁）
  • 人工审查高风险用例（抽样 50 条）

上线后

  • 生产监控实时告警（延迟、错误率）
  • 用户反馈收集（NPS 评分 + 投诉分析）
  • 定期 A/B 测试验证新版本

评估反馈闭环的核心思想：生产中发现的问题必须回流到测试集中。如果生产监控捕获了一个自动化测试漏掉的 case，这个 case 应该在 24 小时内被加入自动化测试集。这样测试集才能随时间进化，逐步缩小"测试通过率 vs 生产满意度"的差距。

五、生产案例与量化数据

生产数据：某客服 Agent 系统仅用自动化评估时，测试通过率 95%，但生产环境用户满意度仅 62%（虚假安全感）。引入瑞士奶酪模型后：自动化评估（CI/CD 门禁）+ 生产监控（实时告警）+ 用户反馈（NPS 追踪）+ 人工审查（高风险工单抽样 50 条/周），6 个月内用户满意度从 62% 提升至 89%。关键发现：自动化评估漏掉的 23% 边界 case 被生产监控捕获，用户反馈发现了 15 个自动化测试从未覆盖的使用场景。

案例三：医疗问诊 Agent 的评估策略

医疗场景对假阴性零容忍。该 Agent 采用最严格的五层评估：自动化评估覆盖 500+ 标准问诊场景（通过率门槛 99%）；每日人工审查 30 条高风险对话（涉及用药建议、急症判断）；生产监控实时追踪"建议就医"触发率（异常下降立即告警）；用户反馈通过随访问卷采集（回复率 42%）；季度 A/B 测试验证新模型的安全性和有效性。上线 12 个月，零重大安全事故。

示例场景：一个内部文档问答 Agent，评估集固定为上线时人工编写的 240 条用例，CI 门禁要求通过率不低于 90%。问题：连续四个迭代里，CI 通过率从 90% 一路刷到 98.3%，但工单量没有下降，用户满意度始终在 70% 上下。排查后发现是评估集过拟合：这 240 条用例半年没更新，而用户实际提问的分布已经变了——生产日志里排名前 20 的问法有 11 种在评估集里完全没有对应用例，团队每次调优都是在把已经会做的题做得更漂亮。方案：把生产监控和评估集打通，按周从真实流量里分层采样 60 条（按意图类型和会话长度分层，优先采样被追问超过两轮或触发人工转接的会话），人工标注后回流补进评估集，同时把超过 90 天未命中过失败的老用例移入回归集、不再计入主门禁通过率。效果：评估集从 240 条扩到 520 条，主门禁通过率立刻从 98.3% 掉回 81%——这个"退步"才是真实水位；三个迭代后回升到 92%，同期用户满意度从 71% 提升到 85%，人工转接率下降 38%。

评估投资回报率（ROI）的关键洞见：从上述四个案例中可以总结出一个规律——评估投入的边际收益递减。从 0 层到 2 层评估的改进最大（满意度提升 15-20%），从 2 层到 4 层改进中等（提升 10-15%），从 4 层到 6 层改进较小（提升 5-8%）。建议团队根据自身风险容忍度选择合适层数：低风险场景 2-3 层，中风险 4 层，高风险 5-6 层。

Agent 评估的核心原则：单一评估工具必然有盲区。必须用瑞士奶酪模型——多层互补，确保一层漏掉的问题被下一层捕获。自动化评估 95% 通过率 ≠ 生产环境 95% 满意度。

评估成熟度模型分为四个等级：(1) 初始级——仅有人工抽查，无系统化评估；(2) 基础级——引入自动化测试，有 CI/CD 质量门禁；(3) 进阶级——多层评估互补，建立反馈闭环；(4) 优化级——数据驱动评估策略，持续量化评估 ROI。大多数团队处于第 2 级，目标应在 6 个月内达到第 3 级。

  • 四层评估互补：自动化 + 生产监控 + 用户反馈 + 人工审查
  • 高风险场景强制人工审查（医疗/法律/资金）
  • 主动推送 NPS 评分（不依赖被动反馈）
  • 定期对比测试通过率 vs 用户满意度（发现虚假安全感）
  • 建立评估反馈闭环：生产问题 24h 内回流测试集
  • 按 Agent 类型选择核心评估框架，避免过度工具化
  • 不要只看自动化测试分数（95% 通过率 ≠ 95% 满意度）
  • 不要忽略用户反馈中的长尾场景
  • 不要用一次性评估代替持续监控
  • 不要对低风险场景做过度人工审查（浪费资源）
  • 不要同时引入 5 个以上评估框架（工具疲劳）
  • 不要将评估指标作为团队 KPI（Goodhart 定律）

Q&A

Q1：为什么不能只用自动化评估？
自动化评估存在三个致命缺陷：①测试用例覆盖不了长尾场景（用户会用你想不到的方式使用系统）；②分数高不等于真实效果好（虚假安全感——测试 95% 但生产满意度仅 62%）；③无法捕捉主观体验问题（语气、措辞、情感）。必须结合生产监控、用户反馈、人工审查等多种工具形成互补。
Q2：什么是幸存者偏差在用户反馈中的体现？
只有极端满意或极端不满意的用户会主动反馈，大量中间用户的体验被忽略。比如一个 Agent 客服系统，投诉的都是严重 bug，但大量"勉强能用但有改进空间"的用户沉默了。解决方案：主动推送 NPS 评分（而非被动等反馈）+ 分层抽样（按使用频率/场景/用户类型分组采集）。
Q3：瑞士奶酪模型在 Agent 评估中如何应用？
每层评估工具都有盲区（奶酪的洞），但多层叠加后，一层漏掉的问题会被下一层捕获。自动化评估漏掉的 23% 边界 case 被生产监控发现，监控漏掉的主观问题被用户反馈暴露，最终人工审查兜底高风险场景（医疗/法律/资金）。核心：不是追求单一工具的完美覆盖，而是多层互补确保零盲区。
Q4：A/B 测试在 Agent 评估中的局限性是什么？
三大局限：(1) 只能测已上线功能 — 无法评估未部署的新方案；(2) 周期长 — 需要足够的用户流量才能达到统计显著性（通常需要 2-4 周）；(3) 只衡量商业指标 — 无法捕捉技术质量（如推理路径合理性）。补充方案：上线前用自动化评估 + 人工审查做质量门禁，A/B 测试只做最终商业验证。Goodhart 定律的体现：当 A/B 指标变成唯一目标时，团队可能忽视指标之外的质量问题。
Q5：对话记录分析为什么能建立"工程直觉"？它和自动化评估有什么区别？
对话记录分析是人工阅读真实用户对话，发现系统性模式（如"30% 的用户在第二步放弃"说明流程设计有问题）。它和自动化评估的区别：(1) 自动化评估测已知场景（预定义测试用例），对话分析发现未知场景（用户真实使用方式）；(2) 自动化评估给分数（定量），对话分析给洞见（定性）；(3) 自动化评估可规模化，对话分析难以规模化但深度更高。建议：每周人工阅读 50 条真实对话，建立对系统行为的直觉。
Q6：RAGAS 和 DeepEval 应该怎么选？可以同时用吗？
两者定位不同且可以互补。RAGAS 专注于 RAG 检索质量评估（Faithfulness、Context Precision 等四个核心指标），适合评估"检索到的内容是否正确被使用"。DeepEval 是通用 LLM 测试框架（14+ 指标，pytest 集成），适合做 CI/CD 质量门禁。推荐组合：用 DeepEval 做全量自动化测试门禁，用 RAGAS 做 RAG 链路的深度质量分析。生产数据显示，两者组合使用时，RAG 系统的幻觉率从单独使用 DeepEval 时的 8% 降至 3%。
Q7：小团队（1-3 人）资源有限，评估的最低配置是什么？
最低配置三层：(1) 自动化评估 — 用 Promptfoo（开源、零成本）搭建 100+ 核心场景测试集，集成到 CI/CD；(2) 生产日志分析 — 每周人工抽查 20 条生产日志，关注错误和异常模式；(3) 被动反馈收集 — 在对话结束时加一个👍👎按钮（成本几乎为零）。这套最低配置能将"测试通过率 vs 满意度"差距从 35% 缩小到约 18%。等团队扩大后逐步加入生产监控和主动 NPS 采集。
Q8：如何衡量评估体系本身的有效性？
核心指标是评估差距值：测试通过率与用户满意度的差值。行业优秀水平差距 < 10%，平均水平 20-30%。监控方法：每月绘制"测试通过率 vs 用户满意度"双线图。如果差距持续扩大，说明评估体系存在盲区（通常是测试集陈旧或反馈渠道失效）。另一个信号：生产事故中有多少是评估体系完全没覆盖的（"评估盲事故"占比），目标 < 5%。
Q9：LLM-as-Judge 评估的可靠性如何？能替代人工审查吗？
LLM-as-Judge 在结构化评估任务上与人工一致性约 80-85%（如相关性、连贯性评分），但在需要领域专业知识的任务上（如医疗准确性、法律合规性）一致性降至 60-70%。建议：LLM-as-Judge 用于大规模初筛（自动化评估层），人工审查仅用于高风险 + LLM 评分低置信度的案例。这种"人机协作"模式可将人工审查量减少 60%，同时保持质量不降。
Q10：评估框架的集成会不会拖慢 CI/CD 流水线？
会，但可以优化。典型耗时：DeepEval 200 条测试约 3-5 分钟（并行执行），RAGAS 100 条评估约 2 分钟，Promptfoo 50 个 Prompt 变体约 1 分钟。优化策略：(1) 分层执行 — PR 触发快速测试（核心 50 条，< 2 分钟），merge 到 main 触发全量测试；(2) 缓存 LLM 调用结果（相同输入不重复调用）；(3) 异步执行非阻塞评估（如 RAGAS 深度分析可异步完成后通知）。实测：优化后 CI/CD 增加耗时 < 3 分钟，对开发效率影响可忽略。
