A15 · MCP Server 生产级鉴权

MCP Authentication — 三层鉴权模型、OAuth 2.1 + PKCE 核心思想、RBAC 功能权限、数据权限隔离、字段脱敏、生产案例

鉴权是三层问题：身份认证防外部攻击，功能权限防内部越权，数据权限防内部泄露。只做第一层的 MCP Server 都是裸奔。

一、鉴权是三层问题，不是一层

大多数教程把"鉴权"简化成"加个 API Key"，这是灾难的开始。真正的生产级鉴权必须分三层，每一层解决不同的问题：

层次回答的问题典型方案覆盖度
第一层：身份认证你是谁？API Key / OAuth 2.1 / mTLS大部分教程讲到
第二层：功能权限你能调哪些 Tool？RBAC / OAuth Scope偶尔提到
第三层：数据权限你能看哪些数据？租户隔离 / 行级过滤 / 字段脱敏几乎空白

真实翻车案例

这些案例说明只做第一层是远远不够的：

翻车场景根因
实习生离职带走共享 API Key，数据库被爬没有用户级身份
客服通过 Claude 查询了高管订单记录所有人看所有数据，无数据权限
A 公司的 AI 查到了 B 公司的客户列表多租户没强制注入 tenant_id

这不是理论推演，是实战总结。身份认证做好了只能防住外部攻击者（谁都能访问）；功能权限防内部越权（客服能删数据）；数据权限防内部泄露（客服能看高管数据）。功能权限和数据权限做不好，内部员工一样能把公司数据搬空。只做第一层的 MCP Server 都是裸奔。

三层不是"安全等级由低到高"，而是三种互不重叠的攻击面：身份认证挡门外的人，功能权限挡门内乱按按钮的人，数据权限挡门内按对了按钮却看到不该看的东西的人。

二、第一层：身份认证怎么选

选型三原则

  1. 本地 stdio 可以不加认证——反正只能本机调用
  2. HTTP+SSE 必须加认证——暴露端口就是暴露家门
  3. 多用户场景首选 OAuth 2.1——因为需要知道"谁在调用"

不同方案对比

方案适用场景安全级别推荐度
无认证本地 stdio，仅个人无仅限本地
静态 API Key小团队快速上线低过渡方案
动态 API Key + 轮换中型团队中推荐
OAuth 2.1（MCP 标准）企业级，多用户高生产首选
mTLS零信任架构最高高安全场景

OAuth 2.1：MCP 2025-11-05 官方标准

2025-11-05 是鉴权分水岭——MCP 正式引入 OAuth 2.1 + PKCE（强制，非可选）。这是 MCP 协议层面的重大升级。

核心思想：OAuth 2.1 + PKCE 流程

OAuth 2.1 + PKCE 流程: ┌──────────┐ ①授权请求 ┌─────────────┐ │ MCP │ ──────────────► │ Authorization│ │ Client │ │ Server │ │(Claude) │ ◄────────────── │ (你的 IdP) │ └──────────┘ ②授权码+PKCE └─────────────┘ │ │ │ ③授权码换 Access Token │ ▼ │ ┌──────────┐ │ │ MCP │ ◄── ④ Access Token ── │ │ Server │ │ └──────────┘ MCP 强制要求: Server 暴露 /.well-known/oauth-authorization-server Client 自动发现认证配置，不需手动填

身份认证方案的选择其实只在回答一个问题："出事之后能不能定位到具体的人、并且只吊销这一个人"——共享 API Key 做不到，所以它天然只能是过渡方案。

为什么是 PKCE（Proof Key for Code Exchange）？因为 MCP Client 通常是桌面应用或浏览器，无法安全存储 client_secret。PKCE 用动态生成的 code_verifier 和 code_challenge 替代 client_secret，即使授权码被拦截也无法换取 Token。

Discovery 端点：自动发现认证配置

MCP 标准要求 Server 暴露 /.well-known/oauth-authorization-server 端点，返回 OAuth 配置信息（issuer、authorization_endpoint、token_endpoint、支持的 scopes 等）。Client 启动时自动获取配置，不需要用户手动填写。

这个设计的价值在于：降低接入门槛，减少配置错误。Claude Code / CodeBuddy 等 Client 可以自动发现认证配置。

JWT 里要带什么？

JWT 是 OAuth 2.1 的 Access Token 标准格式。关键是要带上 roles 和 tenant_id 这两个字段——它们是功能权限和数据权限的基础。

  • sub：用户 ID（身份认证）
  • roles：角色列表（功能权限）
  • tenant_id：租户 ID（数据权限）
  • scope：授权范围（OAuth 标准）
  • exp：过期时间（Token 生命周期）

这些字段在 JWT 验证后注入到请求上下文，供后续权限检查使用。

OAuth 2.1 的核心价值：知道"谁在调用"，这是功能权限和数据权限的前提。没有用户级身份，后续两层都是空中楼阁。

三、第二层：功能权限 — 不同用户能调不同 Tool

核心思想：RBAC（Role-Based Access Control）

RBAC 的核心是"角色 → Tool 映射"。每个角色有一组允许的 Tool 列表，用户通过角色获得权限。

RBAC 模型: 用户 → 角色 → Tool 列表 viewer: [query_database, search_documents] user: [query_database, search_documents, create_record, update_record] admin: [query_database, search_documents, create_record, update_record, delete_record, export_data, manage_users]

功能权限最好的实现方式不是"拦住不该调的"，而是"根本不告诉模型有这个 Tool"——模型看不见的能力，它既不会误调，也不会因为被拒而反复重试。

权限检查必须在 Tool 执行前

这是最容易犯的错误——先执行业务逻辑，再检查权限。正确的做法是：权限检查失败立刻返回，不执行任何业务逻辑。

为什么？因为执行后再回滚成本高、风险大。特别是写操作，一旦执行就无法完全撤销（比如发了邮件就收不回来）。

高级技巧：动态 Tool 列表

比"展示后拦截"更优雅的方案：权限不足的 Tool 根本不展示给 AI。

实现思路：根据用户角色动态注册 Tool。viewer 只看到只读 Tool，user 看到写操作 Tool，admin 看到管理 Tool。

为什么更好？

  • AI 看到的 Tool 清单 = 能用的清单，选择更准确
  • 减少 AI 的困惑（为什么展示了但调不了？）
  • 安全审计更干净（不会出现大量权限拒绝日志）

权限不足时的错误信息

必须加 "Do not retry"，否则 AI 看到 403 会自动换参数重试，陷入死循环烧 Token。

好的错误信息示例："Permission denied: You don't have access to 'delete_record'. Do not retry. Please contact admin for access."

错误信息是 AI 行为的指挥棒。差的错误信息让 AI 死循环，好的错误信息让 AI 优雅降级。

四、第三层：数据权限 — 同一个 Tool，看不同的数据

这一层的铁律只有一句：凡是决定"能看到什么"的参数，都不能来自模型。行级过滤与字段脱敏必须由服务端拿着 Token 里的身份强制拼装，因为 Prompt 注入能改的是模型的输出，改不了服务端的上下文。

三种数据权限模型

模型做什么典型场景
租户隔离不同租户数据互不可见SaaS 多租户
行级过滤同表不同用户看不同行组织内权限分级
字段脱敏同行数据不同人看不同字段敏感数据保护

行级过滤：强制注入过滤条件

核心原则：永远不要信任 AI 传来的参数。AI 可能被 Prompt 注入诱导构造越权查询，所以过滤条件必须在服务端强制注入。

实现思路：在数据库查询前，根据用户身份强制拼接到 WHERE 条件里：

  • 多租户场景：无论传什么参数，tenant_id 永远是自己的
  • 组织内场景：普通用户只能看自己的数据，admin 可以看所有
  • 特殊规则：某些表有额外限制（如 salary_records 只有 HR 能看）

为什么不在前端做？因为前端（AI）不可信。Prompt 注入可以诱导 AI 构造恶意查询，只有服务端强制注入才能防住。

字段脱敏：按角色返回不同字段

核心思想：同一行数据，不同角色看到不同字段。比如 users 表：

角色可见字段不可见字段
adminid, name, email, phone, salary, ssn无
hrid, name, email, phone, salaryssn
userid, name, emailphone, salary, ssn
viewerid, nameemail, phone, salary, ssn

实现思路：配置表级字段可见性规则，查询结果返回前过滤字段。

注：本卡的字段脱敏是 API 响应层的按角色字段可见性过滤，面向通用 MCP Server 场景；工业级 MCP Server 的完整防护体系（参数校验、限流、审计、写保护等）另见 《A14 · 工业级 MCP Server 开发》。

双重保护：MCP 层 + 数据库层

生产级要做双重保护——MCP 层脱敏 + 数据库层也加字段级权限。为什么？因为有人可能绕过 MCP 直连数据库，MCP 层脱敏就失效了。

数据库层的字段级权限可以通过 PostgreSQL 的 Row-Level Security (RLS) 或列级权限实现。

数据权限的核心原则：AI 传来的参数永远不可信。过滤条件必须服务端强制注入，不能依赖前端（AI）传参。这与 SQL 注入防护的思路完全一致——永远不要信任外部输入。

五、生产案例深度剖析

案例一：Linear — Scope 驱动的细粒度权限

Linear 用 OAuth Scope 而非角色控制 Tool 权限。这是更细粒度的控制方式：

  • linear:read → 只读 Tool（查 Issue、查 Project）
  • linear:write → 写操作 Tool（创建 Issue、更新状态）
  • linear:admin → 管理 Tool（删除、归档、成员管理）

核心价值：最小权限默认，用户可随时撤销，全量审计。用户授权时可以精确控制 AI 能做什么。

案例二：500 人金融科技公司 — LDAP 三层映射

这是一个真实的金融科技公司案例，把 LDAP 组映射到 MCP 角色：

LDAP 组MCP 角色可用 Tool
cn=developersuser查询、创建、更新
cn=data-analystsanalyst查询、导出（脱敏数据）
cn=financefinance查询财务数据（含敏感字段）
cn=it-adminsadmin全部 Tool
cn=complianceauditor只读 + 审计日志查询

数据权限精细度：

  • 开发者只能查询自己负责的项目数据
  • 数据分析师查询用户数据时，手机号/邮箱自动脱敏为 138****8888
  • 财务可以看完整薪资，但查询会触发审计告警
  • 所有人都无法查询 ssn 字段——Gateway 层永久黑名单

上线 6 个月效果：安全审计通过率 62%→98%，AI 操作数据泄露 0 起，开发者信任度 43%→81%。

启示：三层鉴权是金融级合规的基础。只做身份认证，审计永远过不了。

案例三：独立开发者的最小可行方案

不是所有团队都需要 OAuth 2.1。对于独立开发者或小团队，最小可行方案是：

  • API Key 格式：mcp_<userId>_<signature>
  • 签名验证：用 HMAC 验证签名正确性，防篡改
  • 按订阅档位限流：free 10 次/分钟，pro 100 次/分钟，enterprise 1000 次/分钟

核心价值：1 天上线，不需要 OAuth 服务器。用户量 < 1000 用这个方案快速验证，> 1000 再迁移 OAuth 2.1。

不要过度设计。OAuth 2.1 是企业级方案，小团队先用 API Key 跑起来，验证价值后再升级。

六、生产级 MCP 鉴权检查清单

认证层（5 项）

  • 生产环境禁止无认证访问（stdio 除外）
  • API Key 放环境变量，严禁硬编码
  • 强制 HTTPS，禁止 HTTP 传 Token
  • Token 过期时间 ≤ 1 小时，带刷新机制
  • 暴露 /.well-known/oauth-authorization-server Discovery 端点

功能权限层（4 项）

  • 默认无权限，显式授权（最小权限原则）
  • DELETE/DROP 级危险操作需要额外 Scope 或角色
  • 权限检查在 Tool 执行前，不是执行后
  • 错误信息加 Do not retry，防 AI 死循环

数据权限层（4 项）

  • 多租户场景强制注入 tenant_id 过滤条件
  • 敏感字段（手机/邮箱/SSN）默认脱敏
  • MCP 层和数据库层双重字段权限（防绕过）
  • 大批量数据导出需额外审批

审计层（4 项）

  • 所有 Tool 调用写结构化日志（用户 ID、参数摘要、时间）
  • 写操作和危险操作单独审计日志
  • 审计日志写入后只读（不可篡改）
  • 定期审查 AI 的操作记录
  • 三层鉴权全做：身份认证 + 功能权限 + 数据权限
  • 数据权限在服务端强制注入
  • JWT 中携带最小信息（user_id, role）
  • 敏感操作增加审计日志
  • 只做身份认证就说"做了鉴权"（裸奔）
  • 信任 AI 传来的过滤参数
  • 把完整用户信息塞进 JWT（过大）
  • 忽略数据权限（最常见的安全漏洞）

Q&A

MCP Server 鉴权为什么是三层问题？
三层缺一不可：(1) 身份认证——你是谁？API Key/OAuth 2.1 解决；(2) 功能权限——你能调哪些 Tool？RBAC/OAuth Scope 解决；(3) 数据权限——你能看哪些数据？租户隔离/行级过滤/字段脱敏解决。只做第一层只能防外部攻击者，功能权限和数据权限做不好，内部员工一样能搬空数据。
为什么数据权限必须服务端强制注入？
AI 传来的参数永远不可信。AI 可能被 Prompt 注入诱导构造越权查询（如让 AI 查"所有用户的订单"），所以 tenant_id、user_id 这些过滤条件必须在服务端强制拼到 WHERE 里，不在前端。同时要做 MCP 层 + 数据库层双重保护，防止有人绕过 MCP 直连数据库。
MCP 2025-11-05 的 OAuth 2.1 规范有什么关键变化？
2025-11-05 是鉴权分水岭：正式引入 OAuth 2.1 + PKCE（强制，非可选），定义了 Discovery 端点（/.well-known/oauth-authorization-server）。Claude Code / CodeBuddy 等 Client 可以自动发现认证配置，不需要用户手动填。JWT 里要带 roles 和 tenant_id，这两个字段是功能权限和数据权限的基础。
什么时候用 OAuth 2.1，什么时候用 API Key？
OAuth 2.1 是企业级方案，适合多用户、需要细粒度权限控制的场景。API Key 适合独立开发者或小团队快速验证。判断标准：用户量 < 1000 先用 API Key，> 1000 再迁移 OAuth 2.1。不要过度设计，OAuth 2.1 的接入成本高（需要 IdP、JWT 验证等），小团队先用简单方案跑起来。
Q5：MCP Server 的 Token 刷新机制怎么设计？刷新失败怎么办？
OAuth 2.1 的 Token 生命周期通常 1 小时（Access Token）+ 30 天（Refresh Token）。刷新流程：(1) Client 检测到 Access Token 过期（401 响应）；(2) 用 Refresh Token 向 IdP 请求新 Access Token；(3) 如果 Refresh Token 也过期，引导用户重新登录。刷新失败处理：(1) 网络超时 → 指数退避重试（最多 3 次）；(2) Refresh Token 被撤销 → 强制重新认证；(3) IdP 不可用 → 降级为只读模式（不允许写操作）。生产建议：在 Token 过期前 5 分钟主动刷新（而非等 401），避免用户请求中断。
Q6：多租户环境下的权限体系怎么设计？有什么坑？
多租户权限设计有三个核心：(1) 数据层租户隔离——tenant_id 强制注入，数据库层行级隔离（PostgreSQL 的 Row-Level Security）；(2) 身份层租户隔离——JWT 中必须带 tenant_id，权限检查要"角色 + 租户"双重验证；(3) 配置层租户隔离——每个租户的 MCP Server 配置（Tool 列表、限流参数）独立，防止一个租户的配置影响另一个租户。坑：不要做"逻辑隔离"——在应用层靠开发者记得加 WHERE 条件，一定会漏。要靠数据库的行级安全或中间件强制注入。
