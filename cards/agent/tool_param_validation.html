A31 · 工具调用参数四层防御

Tool Parameter Validation — 格式校验 / 类型归一 / 边界守护 / 语义净化 · 契约漂移检测 · 失败处置与重试上限

工具调用的参数不是"我们自己传进去的值"，而是一段由模型生成、经过上游接口和用户内容污染的不可信输入——它可能语法完好、类型合理、范围正常，却依然带着能把系统打穿的载荷。四层防御的意义在于：每一层只回答一个问题，且回答不了的问题必须交给下一层，而不是指望某一层"顺手也管一下"。

一、参数为什么会错：三个源头

把参数错误笼统归因为"模型不靠谱"是最贵的误判——因为其中相当一部分错误里模型是完全正确的，是上游接口悄悄改了字段，或者用户内容里藏了东西。源头不同，防御手段完全不同。

一次工具调用的参数在到达执行点之前，至少经过三双手：模型的生成、上游服务的返回、用户输入的透传。三者的失效方式互不相同，却常常在日志里长成同一副模样——一条 JSONDecodeError 或者一个 500。分不清源头，就只会反复在同一层加正则。

源头典型失效随时间的变化规律该由哪一层拦
模型生成漏必填字段、字段名近义替换（city 写成 city_name）、数字写成带单位的字符串随 prompt/模型版本波动，换模型就重新分布第一层 + 第二层
上游契约字段改名、类型从 int 变 string、可选字段突然缺失、枚举新增取值低频但突发，且不通知你第一层（契约快照比对）
用户内容透传合法字段里塞入超长文本、越界数值、命令/SQL 片段、路径遍历串被主动探测时集中爆发第三层 + 第四层

值得单独强调的是约束解码——在解码的每一步用 Schema 编译出的状态机屏蔽掉所有会违反结构的 token，让模型在物理上无法输出不合规的结构。它能极大压低第一类源头的错误率，但对后两类源头完全无效：上游改字段它管不着，用户塞进合法字符串字段里的 rm -rf 它照样放行。

OpenAI 官方数据（Structured Outputs 发布说明，2024-08）：在其复杂 JSON Schema 遵循的评测上，开启 strict 的 gpt-4o-2024-08-06 得分 100%，而 gpt-4-0613 低于 40%。需要注意官方对两种模式的定性差异——JSON Mode 只保证输出是可解析的合法 JSON，不保证符合你给定的 Schema；strict 模式才提供 Schema 层面的保证。官方同时列明了它仍会失败的情形：模型拒答、触达 max tokens、内容过滤，所以即便开了 strict 也必须保留错误处理。跨模型的系统更不能把结构正确性外包给某一家的 API，自建参数校验层是必需项。

四层防御的总体形状

四层的排列不是随意的，而是按"排查成本从低到高、覆盖问题从粗到细"递进。前一层不通过就没有必要进入后一层——格式都解析不出来，谈类型转换毫无意义。

本文讲的是参数本身怎么被一层层洗干净，属于工程视角。与之相邻的一张卡是 《SEC03 · 工具调用安全》，它站在安全视角讲工具的权限管控、执行隔离与链路审计——也就是"就算脏参数漏过去了，这次调用能造成多大破坏、事后能不能查清"。两张卡在第四层的注入防御上有交集：本文关心的是"这个值怎么洗、洗不干净怎么办"，SEC03 关心的是"该不该让这个工具有能力执行它、执行了怎么留痕"。

二、第一层 · 格式校验与契约漂移

格式校验拦的是"根本读不懂"的输入，成本最低、收益最直接；但它真正的价值不在于挡住模型的手误，而在于成为上游契约变更的传感器——字段名对不上的那一刻，就是上游改了接口的那一刻。

这一层只回答三个问题：这段文本能不能解析成 JSON；解析出来的对象里必填字段是否齐全；出现的字段名是否都在约定的契约里。三个问题都很浅，但它们是后面所有层的前提。第三个问题还顺带提供了一个额外能力——检测契约漂移，即上游服务在没有通知下游的情况下改变了字段名、类型或可选性，导致原本正确的解析代码突然失效。

检查项拦住的问题常见实现漏检后的表现
可解析性截断的 JSON、多余的 Markdown 代码块围栏、尾随逗号json.loads + 前置清洗调用点抛异常，整条链路中断
必填字段齐全模型漏写 required 字段Schema required 声明下游取值得到 None，错误延后暴露
字段名合规近义改名、大小写/下划线风格漂移additionalProperties: false参数被静默忽略，工具用默认值执行
结构层级该是对象的地方给了数组、嵌套层级错位Schema 类型声明 + 嵌套深度上限遍历逻辑越界或死循环
字段名未知即告警上游契约漂移契约快照 + 差异比对接口改了没人知道，直到大面积报错

示例场景：一个出行助手的天气工具对接第三方 API，契约里写的是 temperature: 25（数值，摄氏度）。某次上游发版后，同一个字段变成了 temp: "25度"——字段名改了，类型从数值变成字符串，还多了单位后缀。问题：解析层按 temperature 取值，取到 None 后进入格式化逻辑抛异常；因为工具调用被编排器包了自动重试，同一个必然失败的请求被重试 3 次，故障期间该工具的错误率从基线 0.3% 涨到 100%，而告警只报了"天气工具异常"，排查方向一开始完全偏在自己的代码上。方案：把契约固化成一份 Schema 快照随代码一起版本管理，每次响应做字段集合比对：出现未知字段名或缺失已知字段，立刻按"契约漂移"单独打一类告警（区别于普通业务异常），并对已知的旧字段名保留一个显式的兼容映射层。同时给这类必然失败的错误加上不可重试标记。效果：下一次上游改字段时，告警在首个请求就点名"出现未知字段 temp、缺失字段 temperature"，定位从小时级压到分钟级，且无效重试被消除。

契约漂移的检测机制

上游响应 / 模型参数 │ ├──→ 字段集合 S_actual │ 契约快照（随代码版本管理） │ └──→ 字段集合 S_expected │ ▼ 集合差异比对 │ ┌────────────┼────────────┐ ▼ ▼ ▼ S_actual 两者相等 S_expected 有余项 有缺项 │ │ │ ▼ ▼ ▼ 未知字段 正常放行 必填缺失 → 拒绝 │ 可选缺失 → 补默认值 ▼ 「契约漂移」告警（独立告警类别，不混入业务异常） │ ▼ 兼容映射层：temp → temperature，剥离单位后缀 （显式、有注释、有下线计划，不做模糊匹配）

Schema 声明式校验与手写校验的取舍

这一层有两种写法：用 JSON Schema / Pydantic / Zod 声明结构，让库去校验；或者在函数入口手写 if 判断。二者不是优劣关系，而是各自擅长不同的约束类型。

维度声明式 Schema手写校验
结构与类型约束擅长，且能直接喂给约束解码，让模型少犯错能做但冗长，容易漏分支
跨字段不变量受限（如"结束时间必须晚于开始时间"多数 Schema 表达不了）擅长，一行代码即可
错误信息质量结构化、可直接回喂给模型做修复取决于自己写得多细
与模型 API 的耦合各家对 JSON Schema 支持是子集：minLength/maxLength/minItems 与复杂正则常被排除，且要求逐层 additionalProperties: false、嵌套与属性数量有上限无耦合，服务端完全自主
随契约演进的维护成本低，Schema 是单一事实来源高，校验逻辑散落在各调用点

正确的组合是：用 Schema 声明所有能声明的结构约束，并把同一份 Schema 同时用于约束解码和服务端校验；Schema 表达不了的跨字段规则和业务不变量，用手写校验补在后面。绝不能因为开了约束解码就删掉服务端校验——那等于把系统的安全边界搬到了模型供应商的实现里。

三、第二层 · 类型归一

类型错误是四层里最阴的一层：它不报错。字符串 "100" 和数字 100 在日志里长得一模一样，程序会带着错误的类型一路跑到底，直到某个索引失效或某次加法变成拼接才暴露，而那时已经离现场很远了。

类型归一指的是在参数进入业务逻辑之前，把每个字段强制转换成契约声明的目标类型，转换失败即视为校验失败。它的目标不是"容错"，而是消除同一字段在系统内部存在多种运行时表示的可能。

示例场景：一个客服 Agent 的订单查询工具接收 user_id 参数，上游用户中心的返回值时而是数字 10087、时而是字符串 "10087"，取决于走的是缓存还是主库。问题：数据库里 user_id 是 bigint 且建了索引，但查询层直接把参数原样拼进条件；当传入字符串时发生隐式类型转换，索引失效，单次查询从 8ms 退化到 1.9s，全表扫描把连接池占满，同一时段该工具的 P99 从 40ms 涨到 6s 以上。方案：在工具入口做一次强制归一——user_id 一律转成 int，转换失败直接拒绝并返回结构化错误；同时在慢查询监控里对"同一 SQL 模板出现两种参数类型"单独打点。效果：类型统一后索引恢复命中，该工具 P99 回到 45ms 以内，且此后任何上游类型漂移都会在入口被拒绝而不是渗入查询层。

字段语义常见输入形态归一目标推荐策略
数值量（金额、数量）100 / "100" / "100.0" / "100元"int / Decimal严格转换；带单位后缀视为失败，不做剥离猜测
标识符（ID、订单号）10087 / "10087" / "010087"统一选一种并全局一致优先 string，避免前导零丢失与精度溢出

宽松转换的代价

类型归一最容易走偏的地方是"越宽松越稳"。把 "100元" 剥离单位当成 100、把 "是" 当成 true、把 "1,2" 切成两个元素，短期内确实让失败率下降，但代价是三重的：错误被掩盖后无法统计，上游契约漂移彻底失去可见性；猜测规则本身会在边缘输入上猜错（"1,200" 是一个数还是两个数）；一旦有人依赖了这种宽松，它就再也收不回来了。

转换规则要写成一张能被穷举的映射表，而不是一串"尽量试试看"的分支。区分"确定的等价表示"（"100" 与 100）和"需要猜测的表示"（"100元"）：前者归一，后者拒绝并让上游或模型改正。

# 严格归一：只接受确定的等价表示
def to_int(v, field):
    if isinstance(v, bool): raise Invalid(field, "bool 不可当数值")
    if isinstance(v, int): return v
    if isinstance(v, str) and v.strip().lstrip("-").isdigit():
        return int(v.strip())
    raise Invalid(field, f"期望整数，实际 {type(v).__name__}: {v!r}")

注意这段代码里对 bool 的显式排除。在 Python 里 isinstance(True, int) 为真，True 会被静默转成 1——这类语言层面的类型陷阱，是手写校验最值得存在的地方，Schema 通常表达不了。

四、第三层 · 边界守护

类型对了不代表值合理。1000 是一个完美的整数，作为年龄却是荒谬的；1000000 作为购买数量能把库存刷成负数。边界守护就是给每个参数装上护栏，把"语法正确但业务荒谬"的取值挡在外面。

这一层的关键认知是：边界不只是防御恶意输入，更是给系统的资源消耗设上限。一个没有上限的 page_size、一个没有元素数上限的批量数组，本质上是把系统的内存和数据库连接的控制权交给了调用方。

边界类型约束对象示例缺失后果
数值区间年龄、数量、金额、比例年龄 ∈ [0,150]；数量 ∈ [1,999]库存/余额被刷成负数，业务不变量被破坏
字符串长度搜索词、备注、名称搜索词 ≤ 128 字符超长文本挤占上下文窗口，或触发下游截断
集合规模批量 ID 数组、多路查询批量 ID ≤ 50 个单次请求放大成上千次下游调用
返回量上限limit / page_size硬上限 1000 行，超限截断并显式标记一次查询把全表拉进模型上下文
时间跨度报表起止时间跨度 ≤ 90 天扫描量与耗时不可控，慢查询拖垮库
递归/嵌套深度嵌套过滤条件、目录遍历深度 ≤ 5栈溢出或指数级展开

示例场景：一个电商下单工具的 quantity 参数只做了类型校验没做边界校验。问题：有人构造出数量为 1,000,000 的下单请求，库存扣减是先扣后校验，直接把 SKU 库存写成负数；由于库存服务对负库存没有约束，超卖状态又被同步给了下游的履约与结算，人工回滚涉及数百条脏数据，且扣减事务的长时间锁等把该表的写入 QPS 打到接近 0。方案：在参数层给 quantity 加 [1, 999] 的硬区间，同时在数据库层给库存字段加 CHECK (stock >= 0) 约束作为最后的物理屏障，两层都不依赖对方。效果：越界请求在入口被拒绝并计入安全打点；即便参数层未来出现漏洞，数据库约束也保证脏数据无法落库——这也是分层防御的意义：任何单层都可能被绕过，但同时绕过两层的概率极低。

边界值该配在哪里

边界不应该硬编码在校验函数里。生产上更可维护的做法是把边界作为工具定义的一部分声明出来，让校验层、文档、以及给模型看的工具描述共用同一份声明。这样做有个额外好处：模型看到 quantity: 1-999 的描述后，越界生成的概率本身就会下降——第三层的最好状态是很少被触发。

  • 每个数值参数都显式声明区间，没有"默认无限制"的字段
  • 返回量上限做成服务端硬上限，调用方只能调小不能调大
  • 业务不变量在数据库层再加一道约束（如 stock >= 0）
  • 越界请求单独打点，观察是模型跑偏还是有人在探测
  • 把越界值静默夹到合法区间（min(quantity, 999)），用户拿到的结果与请求不一致却毫不知情
  • 只在前端限制范围，服务端不校验
  • 边界写死在代码里，与工具描述、文档三处不一致
  • 先执行副作用再校验边界

五、第四层 · 语义净化

前三层问的都是"这个值形状对不对"，第四层问的是"这个值会不会被下游当成指令执行"。城市名 北京; rm -rf / 是一个长度合规、类型正确的字符串——它的问题不在形状，而在于它将被拼进 shell 命令。

语义净化指的是在格式、类型、范围都合规之后，进一步判断参数值的内容是否会在下游被解释成可执行的语法结构，并把这种可能性消除掉。它针对的是拼接这个动作：只要参数值会被拼进另一种语言的语句里——SQL、shell 命令、文件路径、URL、模板——它就有被解释成语法结构而非数据的风险。

这张表最重要的一列是"根治手段"。参数化查询之所以是根治而非缓解，是因为它把值与语句结构在协议层就分开了——值无论长什么样都只能是值，不可能变成语法。凡是存在这类结构性隔离手段的场景，都不应该退而依赖字符过滤。

白名单收敛与黑名单追赶

白名单收敛是指不去枚举"哪些取值危险"，而是先把参数的取值空间压缩到业务真正需要的最小集合，集合之外的一切默认拒绝。它与黑名单的根本差别在于失效方向：白名单漏配会误拒合法请求（吵，但安全），黑名单漏配会放过攻击（安静，但致命）。

黑名单思路（追赶式，永远滞后） 允许全部取值空间 │ 逐个减去已知的攻击特征 ▼ ['"; -- UNION DROP …] ← 特征库 │ ▼ 剩余空间依然巨大 ─── 新绕过手法出现 ─── 补正则 ─── 循环 （无 DROP 关键词的 ` OR 1=1 ` 直接穿过） 白名单思路（收敛式，一次到位） 先把取值空间压到业务真正需要的极小集合 │ ├── 字段名 → 枚举（order_id / status / created_at） ├── 操作符 → 枚举（= / > / < / IN） ├── 值 → 类型 + 区间 + 长度 │ ▼ 取值空间小到可以穷举 ─── 未知形态默认拒绝 │ ▼ 黑名单特征库降级为「兜底 + 攻击可观测性」，不再是主防线

顺序反过来就会陷入无穷的追赶：先建白名单把空间压小，再用黑名单兜底并统计攻击尝试；而不是先靠黑名单挡，指望正则写得足够全。判断标准很朴素——如果你的防御能否生效取决于攻击者是否用了你见过的写法，那它就还不是防线。

另一个容易被忽略的点：语义净化的位置应当尽量靠近拼接点。在入口做一次全局过滤看似省事，但同一个值拼进 SQL 和拼进 shell 的危险字符集完全不同，全局过滤要么过宽（漏）要么过严（把正常的 O'Brien 这类值也拒了）。按工具类型分别净化，才能既准又不误伤。

需要澄清与相邻卡的边界：本层解决的是"值本身怎么洗干净、洗不干净就拒绝"。而"这个工具是否本就不该拥有执行 shell 的权限"、"执行时是否跑在隔离沙箱里"、"读取类工具与外发类工具之间是否存在链式升级"这类问题，属于权限与隔离设计，见 《SEC03 · 工具调用安全》。参数校验做得再好也无法弥补一个权限过大的工具；反过来，权限收得再紧，脏参数依然能在授权范围内造成业务数据错乱。两者必须同时存在。

六、工程账：开销、处置与重试上限

四层防御的总开销通常在毫秒量级，和一次工具调用的网络往返相比可以忽略；真正贵的从来不是校验本身，而是校验失败后的处置策略——一次让模型重新生成参数，成本是一整轮推理。

重试上限该定多少

重试的收益衰减极快：第一次重试携带了新信息（具体哪个字段错、期望什么），修复率高；第二次开始信息量不再增加，模型往往在同一处反复出错。行业实践中常见的默认值是最多 2–3 次，且在结构约束到位的管道里重试率通常能压到 2% 以下，对平均成本的影响不到百分之几。真正的成本失控出现在两种情况：没有上限，以及把不可修复的失败（如注入被拦）也送去重试——后者每次都必然再次失败，纯属白烧 token。

重试预算要按"整个任务"而不是"单次调用"来记。单次调用限 2 次、任务内 20 次工具调用，最坏情况就是 40 轮额外推理。给任务级别设一个总的校验重试配额，超了就整体失败并上报，比在每个调用点各自限次安全得多。

  • 同一份 Schema 同时驱动约束解码与服务端校验
  • 错误信息结构化并点名字段与期望值，便于回喂
  • 按失败原因分流：可改正的重生成，不可改正的直接拒
  • 重试配额按任务累计，并在超限时上报而非静默失败
  • 四层各自打点，观察错误在层间的分布迁移
  • 因为开了约束解码就删掉服务端校验
  • 把注入、越权类失败也送给模型重试
  • 用"再试一次"当兜底，不设次数上限
  • 校验失败只记一行日志、不区分错误类别
  • 把复杂回溯正则放在长字符串的必经路径上

Q&A

开了 OpenAI 的 strict Structured Outputs，四层校验是不是可以砍掉前两层？
不能。约束解码解决的是"模型生成的结构不合规"这一个源头，它在解码时屏蔽违规 token，所以对字段缺失、类型错误这类问题确实极其有效。但参数错误还有另外两个源头：上游接口的契约漂移和用户内容透传，约束解码对这两者完全无能为力——上游把 temperature 改成 temp，模型侧的 Schema 约束一点也管不到。此外各家 API 对 JSON Schema 的支持只是子集，长度限制、复杂正则等约束往往被忽略，跨字段不变量更是表达不了。还有一个现实原因：一旦你的系统需要同时支持多家模型，硬保证就不存在了（例如 Anthropic 侧的 strict 语义被标注为忽略）。把结构正确性外包给某一家供应商的实现，等于把系统边界交给了别人的版本更新。
为什么类型归一要严格拒绝而不是尽量宽松地转换？
宽松转换的短期收益是失败率下降，长期代价是三重的。第一，猜测规则会在边缘输入上猜错，"1,200" 到底是一个数还是两个数没有确定答案，猜错的结果是静默的语义错误而不是报错。第二，宽松转换掩盖了上游的问题，你再也不知道有多少请求本来是不合规的，契约漂移彻底失去可见性。第三，宽松一旦上线就收不回来，会有调用方开始依赖它。合理的做法是区分"确定的等价表示"和"需要猜测的表示"："100" 与 100 在任何语境下都等价，可以归一；"100元" 需要剥离单位，属于猜测，应该拒绝并让上游改正。
越界的参数为什么不能直接夹到合法区间？
因为静默夹取会让用户拿到与请求语义不符的结果，且完全无感。用户请求买 1,000,000 件，系统夹成 999 件并下单成功，这既不是用户想要的，也没有任何一方知道发生了偏差。更麻烦的是它污染了监控：越界请求本来是一个重要信号（可能是模型跑偏，也可能有人在探测边界），被夹取后在指标上表现为完全正常的成功调用。正确做法是拒绝并返回明确的错误，同时对越界事件单独打点。唯一可以接受截断的是返回量上限这类只读场景，但也必须在结果里显式标记"已截断"，让上层和模型都知道数据不完整。
本文和《SEC03 · 工具调用安全》在注入防御上重复了吗？边界怎么划？
不重复，视角不同。本文是工程视角，关心的是参数值本身怎么被逐层洗干净：能不能解析、类型对不对、范围合不合理、值会不会被下游当作语法结构执行；失败之后是拒绝、修复还是让模型重生成，以及各自的成本。SEC03 是安全视角，关心的是这次调用被允许做什么：工具的权限该怎么授予与收敛、执行时是否跑在隔离环境里、读取类工具与外发类工具之间的链式升级怎么检测、事后审计能不能还原整条链路。两者的交集只在第四层：本文讲怎么用白名单收敛取值空间、用参数化查询做结构隔离，SEC03 讲这类工具本身该不该拥有对应的执行能力、以及被绕过后如何限制爆炸半径。实践中两者必须同时存在——参数洗得再干净也弥补不了一个权限过大的工具，权限收得再紧，脏参数仍能在授权范围内把业务数据搞乱。
让模型重新生成参数的重试次数应该定多少？
单次调用 2–3 次是合理起点，但更重要的是配额记在哪里。重试的收益衰减很快：第一次重试携带了新信息（哪个字段错、期望什么范围），修复率最高；第二次之后信息量不再增加，模型常在同一处反复犯错，继续重试只是烧 token。同时必须按失败原因分流——注入被拦、权限不足、上游契约漂移这些失败模型自己改不了，送去重试每次都必然再失败。另一个容易踩的坑是配额的粒度：如果只限制单次调用，一个包含 20 次工具调用的任务最坏可能产生 40 轮额外推理，所以应该给任务级别设一个累计的校验重试配额，超限就整体失败并上报。
四层的顺序能调换吗？比如先做语义净化再做格式校验？
不建议调换，顺序本身承载了两个设计意图。一是依赖关系：格式都解析不出来的时候，谈不上对某个字段做类型转换或注入检测，因为你甚至拿不到字段。二是成本递增：前面的层耗时更低、覆盖的错误更多，把便宜的检查放在前面能让大部分坏输入在最低成本处被挡掉，尤其是语义净化里的正则匹配是四层中最贵的一项，让它只处理已经通过前三层的输入是明显更划算的。此外顺序还影响错误信息的质量：先做格式校验，报出的错误是"缺少字段 quantity"这种可直接回喂给模型的信息；如果顺序打乱，很可能报出一个语义层的错误，而真实原因只是 JSON 少了一个括号。
为什么说注入检测用的正则本身可能是个风险点？
用于匹配攻击特征的正则常常写得很复杂，带嵌套量词和多重可选分支。这类正则在遇到特定构造的长输入时会发生灾难性回溯，匹配耗时从微秒退化到秒甚至更久，于是校验层自己变成了拒绝服务的入口——攻击者不需要绕过你的检测，只需要让检测跑得足够慢。缓解方式有几个：先用长度上限把输入截短再匹配，因为超长输入本来就该被第三层拦掉；能用字符集判断的就不要用正则（判断"是否只含字母数字和连字符"不需要复杂表达式）；给正则匹配设超时或使用线性时间的正则引擎。更根本的解法还是回到白名单收敛——当取值空间被压到可穷举的枚举时，根本不需要在长字符串上跑复杂正则。
契约漂移的告警为什么要和普通业务异常分开？
因为两者的处置路径完全不同。普通业务异常通常指向自己的代码或数据，排查方向是本地日志、最近的发布、依赖的资源；契约漂移指向的是上游服务改了接口，排查方向是对方的变更记录，需要联系的是另一个团队。如果两者混在同一类告警里，值班的人只会看到"某工具错误率飙升"，第一反应必然是查自己刚发的版本，而真实原因在别人的系统里，这个方向性错误往往要消耗掉大量排查时间。把字段集合比对的结果做成独立告警类别，让告警直接说出"出现未知字段 temp、缺失字段 temperature"，定位就从推理变成了阅读。附带的好处是这类告警天然自带修复方案——补一个显式的兼容映射，并给它安排下线计划。
