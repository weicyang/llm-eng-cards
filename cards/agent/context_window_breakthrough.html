A38 · 突破上下文窗口限制

Context Window Breakthrough — 双阶段工作流、外部记忆系统、增量循环三原则 — 让 AI Agent 连续工作一周不丢上下文

核心思想：用「硬盘换内存」—— 将记忆负担从昂贵的上下文窗口转移到廉价持久的文件系统，每轮任务结束后主动清空上下文，通过读取外部文件恢复状态。

一、问题场景：让 AI 连续写代码一周

核心挑战：「假设让你设计一个能连续工作一周的 AI Agent，你怎么解决 Context Window 不够用的问题？」

这不是理论问题。真实场景中，一个复杂功能可能需要 50+ 轮对话才能完成，而 LLM 的上下文窗口（即使 128K）也会在多轮交互后被填满。关键挑战：

挑战表现后果
记忆丢失早期对话中的关键决策被截断Agent 重复已完成的工作
Token 爆炸长会话消耗大量 Token成本飙升，延迟增大
质量下降上下文过长导致注意力稀释代码质量随对话推进而下降
状态混乱多任务交织导致进度不清跳过步骤或重复操作

这四个挑战看起来是四个问题，其实是同一件事的四种表现：Agent 把"任务进行到哪一步"这个状态存在了一个会被挤掉、会被稀释、还要按量收费的地方。换个说法——它把工作记忆当成了持久存储用。只要状态还住在上下文窗口里，这四个问题就只能被缓解，不能被消除。

二、解决方案核心架构

2.1 双阶段工作流

将 Agent 的工作拆分为两个阶段，职责分离：

┌─────────────────────────────────────────────────────┐ │ Phase 1: 初始化智能体 (Initializer Agent) │ │ • 仅运行一次 │ │ • 搭建脚手架：配置环境 / 初始化 Git / 建立进度表 │ │ • 不写业务代码 │ └────────────────────────┬────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────┐ │ Phase 2: 编码智能体 (Coding Agent) │ │ • 增量循环模式 │ │ • 每次只处理一个功能单元 │ │ • 完成后清空上下文，从外部文件恢复状态 │ └─────────────────────────────────────────────────────┘

为什么要分离？初始化和编码是两种完全不同的任务。混在一起会让编码智能体的上下文被初始化细节污染。分离后，编码智能体可以保持「干净」的上下文。

2.2 外部记忆系统（The "Disk"）

这是整个方案的核心创新：用文件系统替代上下文窗口作为长期记忆。

组件作用类比
持久化日志记录所有尝试与错误施工日志
Git 版本控制保存完整代码历史工程变更记录
功能清单文件明确记录任务状态（Todo/Done）里程碑检查表
关键洞察：上下文窗口是「内存」—— 快但贵且有限；文件系统是「硬盘」—— 慢但便宜且无限。聪明的系统把热数据放内存、冷数据放硬盘。

三、增量循环三原则

三条原则各自砍掉了一种"必须记住"的负担：环境即记忆让 Agent 不用记住做过什么，串行让它不用记住别人在改什么，测试驱动让它不用记住代码是不是对的。三条合起来，每轮真正需要装进上下文的就只剩"下一步做什么"——这才是清空上下文之后还能继续干活的前提。

原则一：环境即记忆

通过文件系统而非上下文窗口存储历史。Agent 启动时，先读取外部文件恢复状态，而非依赖上一轮对话的残留。

每轮任务启动时的恢复动作: 1. 读取 PROGRESS.md -> 知道做到哪一步 2. 读取 TODO.md -> 知道还有哪些未完成项 3. 读取最近变更记录 -> 知道刚刚改了什么 4. 基于这三份外部记忆决定下一步 关键点: 不是依赖“上轮还记得什么” 而是依赖“外部文件明确记录了什么”

原则二：串行优于并行

接力式任务传递，避免多 Agent 冲突。不启动多个 Agent 并行工作，而是让一个 Agent 按顺序处理任务。

方式优点缺点
并行多 Agent理论上更快冲突多、状态同步复杂、调试困难
串行单 Agent状态简单、可控、易调试单任务执行
在上下文受限的场景下，串行的可控性远比并行的速度更重要。一个稳定推进的 Agent 胜过三个互相冲突的 Agent。

原则三：测试驱动开发

先写测试再编码，用编译器报错替代模糊记忆。Agent 不需要「记住」代码是否正确——跑一下测试就知道了。

测试驱动循环: 运行测试 | +--> 有失败 --> 按失败信息修改代码 | +--> 再次运行测试 | +--> 全部通过 --> 才进入提交阶段 判断权交给测试框架 而不是交给 Agent 的主观“自我感觉正确”
这本质上是把"Agent 需要判断代码是否正确"的认知负担，转移给了"测试框架"这个确定性工具。Agent 只需要读懂测试输出，不需要自己推理代码逻辑。

四、关键创新点

4.1 硬盘换内存

将记忆负担从昂贵的大模型上下文转移到廉价持久的文件系统。

存储方式成本容量速度持久性
上下文窗口极高（Token 计费）有限（128K）极快会话结束即丢
文件系统几乎为零无限较快永久保存

强制清空之所以敢做，是因为清空前已经把该留的东西写进文件了；默认失败假设之所以必要，是因为清空之后 Agent 对上一轮的印象只剩文件里那几行字，它没有资格"觉得"代码是对的。三个创新点是一套连锁设计：硬盘换内存提供了存放处，强制清空逼着状态必须落盘，默认失败假设保证落盘的是验证过的事实而不是自我感觉。

4.2 强制清空机制

每轮任务结束后主动清空上下文，通过读取外部文件恢复状态。这是反直觉的设计——我们通常希望保留更多上下文，但这里故意丢弃。

传统思路：尽可能保留上下文 → 上下文越来越长 → 质量下降 + 成本飙升 本方案思路：每轮清空 → 从文件恢复 → 上下文始终干净 → 质量稳定 + 成本可控

4.3 默认失败假设

Agent 预设自己代码会失败，直到测试通过才提交。这避免了 Agent 的「过度自信」——LLM 常常认为自己的代码是正确的，即使有明显 bug。

默认失败假设的工作原则是：先假设代码不可靠，再用测试去证明它可靠。只有证据充分时才提交，而不是“先提交，回头再看”。

六、生产级实现要点

外部记忆文件结构

文件作用为什么必要
PROGRESS.md记录当前做到哪一步防止 Agent 每轮重新理解整体任务
DECISIONS.md记录关键设计取舍避免下轮推翻上轮已经确认的方案
ERRORS.md记录踩坑和修复防止同一个错误被重复犯
CONTEXT.md记录本轮关键上下文让上下文恢复更快、更稳定
TODO.md维护任务分解与状态保证下一步动作明确，不靠临场猜测

五个文件的分工可以按"防止哪一类重复劳动"来记：PROGRESS 防重复理解任务，TODO 防重复选择下一步，DECISIONS 防推翻已定方案，ERRORS 防重复踩同一个坑，CONTEXT 让状态恢复这一步本身足够便宜。少哪一个，清空上下文后就会在对应的地方付一次学费——其中 DECISIONS 缺失的代价最大，因为推翻方案往往要连带作废好几轮已经完成的代码。

每轮循环的完整流程

┌─ 每轮循环 ──────────────────────────────────────────┐ │ │ │ 1. 读取外部文件恢复状态 │ │ ├── PROGRESS.md → 做到哪了 │ │ ├── TODO.md → 下一步做什么 │ │ └── git log → 最近改了什么 │ │ │ │ 2. 执行一个功能单元 │ │ ├── 写测试 → 写代码 → 跑测试 │ │ └── 测试通过 → git commit │ │ │ │ 3. 更新外部文件 │ │ ├── PROGRESS.md → 更新进度 │ │ ├── DECISIONS.md → 记录本轮决策 │ │ └── ERRORS.md → 记录遇到的错误 │ │ │ │ 4. 清空上下文 → 回到步骤 1 │ │ │ └─────────────────────────────────────────────────────┘

Q&A

为什么不能直接用更大的上下文窗口（如 1M Token）来解决问题？
三个原因：(1) 成本——Token 按量计费，1M Token 的会话成本是 128K 的 8 倍；(2) 注意力稀释——即使窗口够大，LLM 对中间位置信息的注意力仍然稀疏（Lost in the Middle 问题）；(3) 质量退化——长上下文会导致推理质量下降，模型更容易「走神」。外部记忆系统从根本上解决了这三个问题。
每轮清空上下文不会丢失重要信息吗？
不会，因为重要信息已经持久化到外部文件中了。清空的是「工作记忆」（类似人脑的短期记忆），而「长期记忆」（类似人脑的长期记忆）保存在文件系统里。每轮开始时，Agent 通过读取文件恢复需要的上下文，这比让 LLM 自己从超长上下文中「回忆」更可靠。
串行执行会不会太慢？
在上下文受限的场景下，串行是最优选择。并行多 Agent 会引入状态同步、冲突解决等复杂问题，这些问题的处理成本往往超过并行带来的速度收益。而且「连续写代码一周」的瓶颈不在单次执行速度，而在持续稳定输出——串行保证了每一轮的质量。
默认失败假设会不会让 Agent 过于保守？
不会。默认失败假设不等于不行动，而是「行动后验证」。Agent 仍然会大胆写代码，但不会盲目自信——它会通过测试来验证代码正确性。这实际上让 Agent 更大胆，因为即使写错了，测试会立即发现问题，修复成本很低。
这个方案只适用于编码场景吗？
不，任何需要长时间连续工作的 Agent 场景都适用。核心模式是通用的：(1) 外部记忆持久化；(2) 定期清空上下文；(3) 从文件恢复状态。可以应用于文档写作、数据分析、研究调研等场景。关键是根据场景设计合适的外部记忆文件结构。
如何保证外部记忆文件本身不会变得太大？
两个策略：(1) 结构化存储——PROGRESS.md 只保留最新状态，历史记录归档到单独文件；(2) 定期压缩——每完成一个大阶段，用 LLM 对历史日志做摘要压缩，只保留关键决策和结论。外部记忆也需要「垃圾回收」。
