A54 · 多 Agent 负载均衡与任务调度

任务复杂度建模 / 异构 Agent 容量归一 / 预期负载最优派发 / 分层探针与熔断半开 / 过载降级与调度器高可用

传统负载均衡建立在两个假设上：请求差不多重，后端差不多强。在多 Agent 系统里这两个假设同时崩掉——所以第一步不是挑算法，而是把"任务有多重"和"节点还剩多少"变成同一个单位的数字。

一、两个失效的假设

轮询（Round Robin）和最少连接数（Least Connections）能统治 Web 负载均衡二十年，靠的不是算法精妙，而是它们赖以生存的两个前提在 Web 世界基本成立：同一个接口的请求耗时方差不大（几十到几百毫秒），后端机器是同规格批量采购的。在这两个前提下，"平均发牌"和"真实均衡"几乎是同一件事。

把同一套东西搬到多 Agent 系统上，两个前提同时失效。一次 Agent 调用的耗时可以从 300 毫秒（缓存命中的简单分类）跨到 90 秒（开了深度思考、串了五轮工具调用的研究型任务），跨度是两三个数量级；而 Agent 池往往是拼凑出来的——有的挂着本地 GPU 跑开源模型，有的只是薄薄一层壳去调云端 API，有的还额外背着向量库和浏览器沙箱。方差跨数量级的时候，"平均分配请求数"和"公平分配压力"是两件毫不相干的事。

传统负载均衡的隐含假设Web 场景为何成立多 Agent 场景为何崩掉
请求成本同质同接口耗时方差在一个数量级内Token 数从 200 到 100k，耗时跨 2~3 个数量级
后端能力同质同规格机器、同镜像部署本地 GPU / 云 API / 带外部依赖的 Agent 混编
请求无状态会话放在 Redis，打哪台都一样会话上下文与 Prompt 缓存有强节点亲和性
后端容量是硬上限连接数打满就拒绝，边界清晰上游 API 配额、显存、排队深度是三条不同的软上限

1.1 两种典型的失效方式

轮询的失效方式是灌爆慢节点。它对后端的实际状态一无所知，一个已经排了 12 个任务的 Agent 和一个空闲的 Agent 在它眼里没有区别，于是慢节点的队列只会越来越长，最终触发上游超时——而超时重试又会按同样的轮次再灌一遍。

最少连接数看起来聪明一些，它至少看得见"手上有几个活"，失效方式是被任务粒度欺骗：一个正在处理 80k token 长文摘要的 Agent 计数是 1，一个刚接了五个短分类请求的 Agent 计数是 5，于是下一个大任务被派给了那个真正忙得喘不上气的节点。它数的是任务条数，而真正稀缺的是算力和显存。

还有一个更隐蔽的问题：Prompt 缓存亲和性——同一段系统提示词和历史对话如果连续落到同一个推理实例，其 KV 缓存可以直接复用，省下的是这段前缀的全部 prefill 计算与对应的输入 Token 费用。纯粹追求负载均匀的调度器会把同一会话的连续请求打散到不同节点，均衡是达到了，代价是每次都重新预填一遍长上下文。在多 Agent 系统里，"均衡"从来不是唯一目标，它要和亲和性、优先级、成本一起被权衡。

轮询假设每个请求都是一颗一样的米粒，所以数米粒就够了。Agent 世界里飞过来的是米粒和西瓜混在一起，你必须先称重，再决定扔给谁。

二、任务复杂度建模：给任务称体重

调度的第一块基础设施是任务复杂度建模——在任务真正执行之前，用可观测的输入特征预估它将消耗多少资源，输出一个可比较的分值。这件事之所以可行，是因为大模型推理的成本结构相当规整，并不是黑箱。

2.1 为什么输出比输入贵得多

一次大模型调用的耗时由两个阶段构成，它们的性能瓶颈完全不同。Prefill（预填充）阶段把整段输入一次性算成 KV 缓存，是可以高度并行的大矩阵乘法，受算力（compute-bound）约束，吞吐很高；Decode（解码）阶段逐个 token 自回归生成，每生成一个 token 都要把模型权重和 KV 缓存重新读一遍，受显存带宽（memory-bound）约束，几乎无法靠并行加速。

预计耗时 ≈ 输入Token数 / Prefill吞吐 + 输出Token数 × 单Token生成时延(TPOT)

这个结构直接决定了复杂度打分里的权重分配：同样 1000 个 token，放在输出侧的成本通常是输入侧的一个数量级以上。所以"按输入长度排序任务"是常见的误判——一个 200 token 输入、要求生成 8000 token 报告的任务，比一个 20k token 输入、只要求回答"是/否"的任务重得多。

把四类特征加权求和后，不要线性映射到 1~10 分，而要按历史分位数映射：因为任务成本是重尾分布，线性映射会让 95% 的任务挤在 1~2 分区间，分值失去区分度。用分位数映射后，"5 分"稳定表示"比一半的任务重"，调度阈值才有意义。

2.3 预估精度只需要够用

复杂度预估不需要准，只需要能把重任务和轻任务分进不同的桶。调度决策本质是排序，排序只依赖相对大小；把 3 分的任务估成 4 分毫无影响，把 9 分的任务估成 2 分才是灾难。所以建模的重点应该放在"不要低估重任务"上——预估偏保守（宁可高估）比追求无偏更符合工程利益，因为低估的代价是节点被打爆，高估的代价只是稍微浪费一点容量。

复杂度分不是预言，是分桶。你要的不是"这个任务会花 4.7 秒"，而是"这个任务属于重量级，别扔给那个已经在喘的节点"。

三、容量归一：把异构 Agent 放进同一把秤

任务称完体重，接下来要给每个 Agent 量出"还能扛多少"。这一步的难点在于异构：CPU 使用率对一个纯调 API 的 Agent 毫无意义（它 90% 时间在等网络，CPU 接近 0，但配额可能已经用满），显存占用对一个云端 Agent 也无从采集。

其中在途复杂度总和是最值得投入的一个指标：它把"手上有几个活"升级成"手上活的总重量"，正是最少连接数缺的那一块。实现上就是派发时把任务复杂度分加到目标 Agent 的计数器上，回调完成时减掉。

3.2 容量归一：用基准任务集校准

不同 Agent 的能力要换算成同一个单位——把复杂度分的量纲反过来用，定义容量为"每秒能消化的复杂度点数"。校准方式是基准任务集：准备一组覆盖轻中重三档的标准任务，在节点上线时（以及每次模型或硬件变更后）跑一遍，测出实际吞吐，得到该节点的容量点数。这样一台 8 卡机和一个云 API 通道就有了可比较的数字。

3.3 为什么必须是"预期"负载，而不是"当前"负载

如果只看当前负载，多个并发的派发决策会在同一瞬间看到同一个空闲节点，然后一起扑上去——这就是羊群效应，也是所有基于陈旧指标的调度算法的通病。指标采集有周期（假设 2 秒），这 2 秒内可能已经派发了几百个任务，而调度器眼里的负载还是 2 秒前的快照。

解决办法有两个，通常一起用。一是本地预扣：派发瞬间就把复杂度加到本地维护的在途计数上，不等远端指标回传，这样后续决策立刻能看到"这个节点刚被塞了一个大任务"。二是二选一（Power of Two Choices）：随机抽两个候选节点，只在这两个之间选负载更低的那个。这个策略的价值在于它对陈旧信息有天然的鲁棒性——最坏情况是选到了次优节点，而不是像"全局选最优"那样把所有请求都推向同一个已经过期的"最闲"节点。

调度器看到的永远是过去的世界。所以它不该赌"我知道谁最闲"，而该赌"我随手挑两个，其中较闲的那个大概不会太糟"。

4.1 推模型与拉模型的分水岭

前面所有讨论都属于推模型：调度器预估成本、观察状态、主动把任务塞给某个节点。它的全部风险集中在一件事上——预估错了就派错了。拉模型反过来：任务统一进队列，Agent 处理完手上的活就自己来取下一个。它天然免疫复杂度预估失准，因为"我现在有空"这个信号不需要预估，是节点自己的事实。

代价也很明确：拉模型下调度器失去了对派发时机的控制，很难实现"这个大任务必须给 GPU 节点""同一会话优先复用缓存"这类约束——因为是节点先举手，不是调度器先挑人。工程上常见的折中是分类队列 + 拉取：按任务类型和重量分成若干队列（如 gpu-heavy / api-light / batch），每个 Agent 只订阅它有能力消费的队列，在队列内部用拉取模式自然均衡。这样硬约束由队列划分表达，均衡由拉取保证，两边的好处都拿到了一部分。

推模型是"我猜你行"，拉模型是"你说你行"。猜不准的时候，就把选择权交回给干活的人。

五、健康感知：活着不等于好用

调度器手里的 Agent 名单必须持续刷新，否则再精妙的算法也只是在往坟墓里投任务。传统健康检查只回答"进程在不在"，而 LLM Agent 有一整类传统检查完全看不见的故障：它活着，但变傻了——上游模型被静默降级、提示词模板被人改坏、工具凭证过期、上下文被污染后开始胡乱调用工具。进程健康、端口通畅、CPU 正常，输出全是垃圾。

L1 用"连续 3 个周期失联"而不是"单次超时"来判死，是为了容忍网络抖动——单次误判会把一个健康节点摘掉，摘掉后剩余节点负载上升，容易引发连环误判。L2 的设计有两条硬约束：探针任务必须幂等且无副作用（绝不能真的下单、真的写库），而且必须有可验证的期望输出，否则它只能证明"有响应"，退化成一个昂贵的 L1。

5.2 熔断状态机的三个细节

第一个细节是最小请求数门槛：窗口内只有 2 个请求、其中 1 个失败，失败率 50% 达标，但这是小样本噪声。不设门槛的熔断器会在低流量时段疯狂误触发。第二个细节是半开的并发限制：半开状态只允许极少量探测请求通过，否则冷却期积压的流量会在开闸瞬间一次性涌向刚刚恢复的节点，把它二次打死。第三个细节是冷却时间指数延长：如果半开探测再次失败，下一轮冷却时间应该翻倍，而不是固定 10 秒——对一个已经彻底挂掉的节点每 10 秒探一次，是持续的无效开销。

5.3 重试：退避、抖动与预算

重试是必要的，但重试也是把小故障放大成雪崩的最常见路径。三件事必须一起做：

  • 指数退避：等待时间随重试次数翻倍（1s → 2s → 4s），给下游留出恢复窗口。只做退避不做抖动仍然危险——同一时刻失败的请求会在同一时刻重试。
  • 随机抖动：在退避基础上叠加随机量。工程上常用"完全抖动"，即从 [0, 2^n × base] 区间均匀取值，把重试洪峰彻底摊平成一条平线。
  • 重试预算：全局限制重试请求占总请求量的比例（典型上限 10%）。这是最容易被忽略却最关键的一道闸——它保证"下游全挂"时重试带来的额外压力有硬上限，而不是随失败率线性膨胀。
示例场景 · 跨层重试放大：一个三层链路——网关调编排器、编排器调 Agent、Agent 调工具——每层都"很合理"地配了最多 3 次重试。工具侧发生一次持续 30 秒的抖动，最坏情况下单个用户请求向工具发起的调用次数是 3×3×3 = 27 次，也就是说工具在故障期间承受的压力是正常流量的 27 倍，一次本可自愈的抖动被重试自己变成了持续过载。修正方式是只在最靠近故障的一层重试（这里是 Agent 调工具那一层），上层只做超时和熔断、不做重试；同时给这一层配 10% 的重试预算，把最坏放大倍数从 27 倍压到 1.1 倍。

存活探针问的是"你还有呼吸吗"，功能探针问的是"你还会做题吗"。LLM Agent 最贵的故障是第二个问题答错，而第一个问题一切正常。

六、过载、失准与调度器自身

前五节假设系统整体容量是够的，只是分配需要优化。真正的生产事故往往发生在容量不够的那一刻——这时调度器的职责从"选最优"切换成"保住一部分"。

6.1 队列积压时按截止时间丢弃

队列长度超过阈值就返回"系统繁忙"是一种粗糙但有效的保护。更精细的做法是按截止时间调度：每个任务入队时带上它的时延预算（比如用户交互类 8 秒、批处理类 5 分钟），调度器在出队时先检查"这个任务就算现在开始执行也已经来不及了吗"，来不及的直接丢弃并快速失败。

这个策略的价值在于避免无效功：严重积压的 FIFO 队列会出现最坏局面——队头的任务已经等了 20 秒，上游早就超时断连了，Agent 却还在认认真真为它计算，算完的结果没人接收；而后面每个任务都重复这个命运，于是系统 100% 满载、0% 有效产出。反直觉的应对是过载时切到后进先出：既然排在前面的注定超时，不如优先服务刚到的请求，至少保证一部分请求能在预算内完成。

过载档位触发条件（示例阈值）动作用户感知
L0 正常队列等待 P95 < 1s按预期负载最优派发无
L1 收紧队列等待 P95 > 3s暂停非核心任务派发，重任务改路由到小模型答案质量略降
L2 丢弃过期队列长度 > 容量×5出队时丢弃已超时延预算的任务；切 LIFO部分请求快速失败
L3 入口限流队列长度 > 容量×10入口直接拒绝，返回重试时间建议明确的繁忙提示

6.2 预估失准的闭环校准

复杂度预估一定会失准，重要的是让它随时间变准。做法是把每次任务的预估值与实际消耗都记下来，按任务类型分组计算误差比（实际/预估）的移动平均，作为该类型的校准系数回填到打分公式里。这样"生成周报"这类被系统性低估的任务，会在几百次执行后自动获得一个 1.6 倍的修正。

还需要一道运行时兜底：任务实际消耗一旦超过预估的若干倍（比如 3 倍），说明这次预估彻底失效，应当立即触发处理——要么中止（对有超时预算的交互任务），要么把这个节点标记为"已超载"暂停向它派发新任务，防止一个被严重低估的任务在节点上持续挤占资源。

6.3 调度器自己不能是单点

故障模式后果对策
调度器进程崩溃派发完全停摆调度逻辑无状态化，多副本 + 前置负载均衡
在途计数丢失重启后误判所有节点空闲，瞬间灌爆计数放外部存储（Redis/etcd），并设置慢启动预热
多副本决策打架同一节点被多个副本同时选中共享在途计数 + 用 P2C 替代全局选最优
注册表脑裂已下线节点仍在接收任务注册项带 TTL 自动过期，节点主动续租
指标通道故障拿不到负载数据，无法打分降级为加权轮询，而不是停止派发

最后一行是整节最重要的一条原则：调度器的所有依赖都必须可降级。指标采集挂了就退回加权轮询，复杂度模型不可用就退回最少连接数，注册表不可用就用本地缓存的上一份名单。一个"信息不全就不敢派发"的调度器，比一个"信息不全就退回笨办法"的调度器危险得多——前者会把一次监控故障升级成一次全站不可用。

  • 把在途负载按任务复杂度加权，而不是数任务条数
  • 容量用基准任务集校准，模型或硬件变更后重新校准
  • 派发瞬间本地预扣复杂度，不等指标回传
  • 功能探针必须无副作用且有可验证的期望输出
  • 熔断器设最小请求数门槛，半开限制并发探测数
  • 只在最靠近故障的那一层重试，并配重试预算
  • 过载时按时延预算丢弃注定超时的任务，避免无效功
  • 指标通道故障时降级为轮询，绝不停止派发
  • 拿 max_tokens 当输出预估，导致所有任务被普遍高估
  • 把复杂度分线性映射到 1~10，让 95% 任务挤在低分区
  • 用"全局选最优"配 2 秒周期的陈旧指标，制造羊群效应
  • 只靠进程存活判断健康，看不见"活着但变傻"
  • 单次心跳超时就摘节点，一次抖动引发连环误判
  • 指数退避不加抖动，失败请求整齐列队再次冲击
  • 每一层都独立配 3 次重试，把故障放大成 27 倍压力
  • 调度器在内存里维护在途计数，重启即误判全员空闲
💡 知识要点：这张卡讲的是"任务怎么分、分给谁"这一件事的完整链路——称重、量容量、选节点、判健康、过载兜底。多 Agent 系统的其余治理面（通信拓扑怎么选、协议怎么分层组合、跨 Agent 状态怎么同步和断点恢复、可观测闭环怎么搭）是另一个正交的话题，见 《A48 · 多 Agent 生产治理》：A48 是多 Agent 治理的全景地图，本文只钻其中"调度"这一格，把它挖到能落地的深度。当同一批任务争抢的不是算力而是同一个外部工具或资源时，问题从"负载均衡"变成"并发仲裁"，见 《A55 · 多 Agent 工具调用冲突仲裁》。

容量够的时候，调度器的工作是选最优；容量不够的时候，它的工作是决定谁被放弃。第二种能力才是生产系统真正被考验的那一半。

Q&A

最少连接数已经能感知负载了，为什么在 Agent 场景还不够？
因为它数的是任务条数，而多 Agent 系统里稀缺的资源是算力、显存和 Token 配额，两者之间没有稳定的换算关系。一个正在处理 80k token 长文摘要的 Agent 计数是 1，一个刚接了五个短分类的 Agent 计数是 5，最少连接数会把下一个大任务派给前者——而前者才是真正忙得喘不上气的。修正方式是把计数换成"在途复杂度加权和"：派发时把任务的复杂度分加到目标节点的计数器上，完成时减掉。这一步改动很小，但它把"数米粒"变成了"称重量"，是从 Web 式负载均衡跨到 Agent 调度的最短路径。
预估任务复杂度时，为什么输出 Token 的权重要比输入高一个数量级？
因为大模型推理的两个阶段瓶颈完全不同。预填充阶段把整段输入一次算成 KV 缓存，是可并行的大矩阵乘法，受算力约束，吞吐很高；解码阶段逐个 token 自回归生成，每个 token 都要重新读一遍模型权重和 KV 缓存，受显存带宽约束，几乎无法并行加速。所以同样 1000 个 token，出现在输出侧的成本通常是输入侧的一个数量级以上。这直接推翻了"按输入长度排任务"的直觉：一个 200 token 输入、要生成 8000 token 报告的任务，远比一个 20k token 输入、只答"是/否"的任务重。
复杂度预估注定不准，这套方案还成立吗？
成立，因为调度决策本质是排序，排序只依赖相对大小而不是绝对精度。把 3 分估成 4 分对结果毫无影响，只有把 9 分估成 2 分才是灾难，所以建模的目标应该是"不要低估重任务"，宁可整体偏保守。此外有三道补救：一是闭环校准，记录每类任务的预估与实际之比，用移动平均回填校准系数；二是运行时兜底，实际消耗超过预估 3 倍就中止任务或暂停向该节点派发；三是最终退路，把推模型换成拉模型——任务进队列，Agent 空了自己来取，"我现在有空"是节点自己的事实，根本不需要预估。
为什么"全局选最负载最低的节点"反而可能比随机二选一更差？
因为调度器看到的负载永远是过去的快照。指标采集有周期，假设 2 秒，这 2 秒内可能已经派发了几百个任务，而调度器眼里的数据还是 2 秒前的。此时"全局选最优"意味着所有并发决策都指向同一个"最闲"节点，一起把它灌爆，这就是羊群效应。随机二选一（Power of Two Choices）只在随机抽到的两个候选间比较，最坏结果是选到次优节点，不会出现全体涌向同一个过期最优解的情况，因此对陈旧信息有天然鲁棒性。工程上还应叠加本地预扣：派发瞬间就把复杂度记到本地在途计数上，不等远端指标回传。
为什么 Agent 需要"业务心跳"这一层，普通存活检查差在哪？
因为 LLM Agent 有一整类"进程健康但输出是垃圾"的故障：上游模型被静默降级、提示词模板被人改坏、工具凭证过期、上下文被污染后开始乱调工具。这些情况下端口通畅、CPU 正常、存活探针全绿，调度器却在源源不断地把任务投进一个只会产出错误答案的节点。功能探针的做法是定期让节点执行一个固定的小任务，并校验输出的结构和已知答案，这样才能捕捉"变傻"。设计上有两条硬约束：探针任务必须幂等且完全无副作用，绝不能真的下单写库；必须有可验证的期望输出，否则它只能证明"有响应"，退化成一个昂贵的存活检查。
重试的三件套——退避、抖动、预算，各自防的是什么？
退避防的是"追着打"：失败往往意味着下游过载，立刻重试只会加剧过载，等待时间随次数翻倍是给下游留恢复窗口。抖动防的是"整齐列队"：同一时刻失败的一批请求，如果退避时长完全相同，就会在同一时刻一起重试，形成周期性的二次洪峰，所以要在退避区间内随机取值把洪峰摊平。预算防的是"总量失控"：前两者只管单个请求的节奏，不管系统总的重试量；全局限制重试占总请求量的比例（典型 10%）之后，即使下游全挂，额外压力也有硬上限。三者之外还有一条常被忽略的原则——只在最靠近故障的那一层重试，否则三层各自 3 次会把压力放大到 27 倍。
队列严重积压时，为什么后进先出可能比先进先出更好？
因为先进先出在严重积压时会陷入 100% 满载、0% 有效产出的最坏局面：队头任务已经等了远超时延预算的时间，上游早就超时断连，Agent 却还在为它认真计算，算完的结果没人接收；后面每个任务重复同样的命运，系统所有算力都花在生产没人要的结果上。后进先出优先服务刚到的请求，这些请求的时延预算还没用完，至少能保证一部分成功返回。更完整的做法是给每个任务带上时延预算，出队时先判断"就算现在开始也来不及吗"，来不及的直接丢弃快速失败，把算力留给还救得回来的请求。这是过载保护的核心思路：宁可明确放弃一部分，也不要让所有请求一起失败。
调度器本身怎么做到不成为单点，最容易踩的坑是什么？
基本做法是调度逻辑无状态化、多副本部署、前置一层普通负载均衡，Agent 注册表和在途计数放到 Redis 或 etcd 这类外部存储，注册项带 TTL 由节点主动续租以避免脑裂。最容易踩的坑是把在途计数留在进程内存里：调度器重启后计数归零，它会认为所有节点都空闲，然后在几秒内把积压流量一次性灌进去——一次例行发布就变成一次全站抖动，正确做法是计数外置并配合慢启动预热。另一个坑是"信息不全就不敢派发"：指标通道故障时应该降级为加权轮询，复杂度模型不可用时退回最少连接数，注册表不可用时用本地缓存的上一份名单，绝不能停止派发，否则一次监控故障会被升级成一次业务不可用。
