一、MCP 概述与 Client-Server 架构

MCP 的本质：一个标准化的"工具 USB 接口"。Function Calling 解决"LLM 怎么调工具"，MCP 解决"工具怎么被发现、描述、访问和安全管理"——就像 USB 统一了外设接口一样。

MCP 解决的核心问题是"M×N 集成"：10 个 AI 应用 × 20 个数据源 = 200 个定制集成。有了 MCP，变成 10 个 Client + 20 个 Server = 30 个组件，集成成本从乘积降为加和。

核心设计哲学：MCP（Model Context Protocol）由 Anthropic 于 2024 年 11 月发布，是一个开放标准协议，旨在解决 LLM 应用的"工具集成碎片化"问题。它定义了统一的通信格式、安全模型和生命周期管理，让任何 AI 应用都能即插即用地接入各种工具和数据源。其架构包含三个角色：MCP Host（用户直接交互的 LLM 应用）、MCP Client（Host 内部的协议客户端，管理与 Server 的连接）、MCP Server（提供工具/资源/提示词的服务端）。一个 Host 可以同时连接多个 Server（如同时连接 GitHub + 数据库 + 文件系统），每个 Server 独立运行、互不干扰。Client 和 Server 之间通过 JSON-RPC 2.0 协议通信，支持双向调用（Client→Server 和 Server→Client）。

MCP 不是 Function Calling 的替代品，而是建立在其上的标准化层。Function Calling 是"LLM 怎么调工具"（底层机制），MCP 是"工具怎么被发现、描述、访问"（通信协议）。实际流程：Client 通过 MCP 获取工具列表 → 转换为 Function Calling 格式 → LLM 选择工具 → Client 通过 MCP 转发调用 → Server 执行并返回结果。

二、JSON-RPC 2.0 协议深度解析

JSON-RPC 2.0 是 MCP 的"通信语言"——所有 Client 和 Server 之间的交互都通过 JSON-RPC 消息进行。它的设计哲学是"简单、双向、可扩展"，支持请求-响应和通知两种模式。

消息类型对比

消息类型方向是否需要响应用途示例
RequestClient → Server✅ 需要响应（有 id）调用工具、获取资源、获取工具列表调用 create_issue 工具
ResponseServer → Client—（匹配 Request 的 id）返回请求结果返回创建的 Issue ID
Notification双向❌ 无需响应（无 id，fire-and-forget）状态更新、事件通知Server 通知"工具列表已更新"、初始化确认
ErrorServer → Client—返回错误信息工具执行失败，返回错误码和消息

JSON-RPC 消息结构

每个 JSON-RPC 消息都包含四个核心字段：jsonrpc（协议版本，固定为"2.0"）、method（方法名称）、params（参数，可选）、id（请求 ID，用于匹配响应）。Request 消息必须有 id，Notification 消息没有 id（因为不需要响应）。

关键特性：JSON-RPC 2.0 的 Notification 机制是 MCP 的"实时通知通道"——Server 可以在工具列表变化、资源更新时主动通知 Client，而不需要 Client 轮询。这种"推送模式"比"轮询模式"更高效（减少无效请求）且更实时（变化立即通知）。但 Notification 是"尽力而为"的——如果 Client 断开连接，期间的通知会丢失，Client 重连后需要重新同步状态。

三、四大能力原语深度解析

MCP Server 通过四种原语暴露能力：Tools（工具，可执行的操作）、Resources（资源，可读取的数据）、Prompts（提示词模板，可复用的 prompt）、Sampling（反向推理请求，Server 请求 Client 的 LLM 生成文本）。四者组合覆盖了 LLM 与外部世界交互的所有场景——读数据（Resources）、做操作（Tools）、用模板（Prompts）、反向推理（Sampling）。

四大原语的设计充分考虑了安全——Tools 由 LLM 调用（需人类审批），Resources 由应用层读取（只读），Prompts 由用户选择，Sampling 需用户确认。每一步都有人类控制点。

Tools：动作原语

Tools 是最常用的原语——LLM 决定调用哪个工具、传什么参数，Server 执行后返回结果。Tools 是"动词"，代表可执行的操作（如 create_issue、run_query、send_email）。每个 Tool 都有明确的 JSON Schema 定义参数结构，LLM 根据 Schema 生成正确的参数。Tools 可能有副作用（发消息、执行查询、创建文件），LLM 通过 Function Calling 决定是否调用，但执行前需人类审批。

Resources：数据原语

Resources 让 LLM 能"看到"外部数据（如文件内容、数据库表结构），但不会修改数据。Resources 是"名词"，代表可读取的数据源。与 Tools 的关键区别：Tools 有副作用（如创建 Issue），Resources 是只读的（如读取文件）。Resources 支持两种访问方式：直接读取（resources/read）和订阅更新（resources/subscribe）。Resources 由应用层决定何时读取并附加到 LLM context，LLM 不能主动请求。

Prompts：模板原语

Prompts 允许 Server 提供预定义的提示词模板，Host 可以直接使用而不用每次手写 prompt。类似 Slash Commands——用户选择后展开为完整 prompt。例如 GitHub Server 可以提供"代码审查"prompt 模板（接受 diff 参数），数据库 Server 可以提供"SQL 生成"prompt 模板（接受 schema 和自然语言描述）。Prompts 实现了 prompt 的标准化和复用。

Sampling：唯一的反向原语

Sampling 是唯一反向的原语——Server 请求 Client 的 LLM 做推理（如自动分类日志级别、生成异常报告）。安全约束：必须经用户批准，Server 不能无限制调用 LLM，防止 token 滥用。

四大原语的协同模式

实际场景中四大原语常协同工作：① 先通过 Resources 读取数据（如数据库 schema），② 再用 Prompts 生成分析 prompt（如"根据以下 schema 生成 SQL 查询"），③ 最后用 Tools 执行操作（如 run_query 执行生成的 SQL）。这种"读数据→生成方案→执行操作"的模式覆盖了 90% 的 Agent 工作流。

  • Tools 用于有副作用的操作（创建、修改、删除）
  • Resources 用于只读数据访问（查询、读取）
  • Prompts 用于标准化常用工作流（代码审查、Bug 分析）
  • 每个 Tool 提供清晰的 JSON Schema 参数定义
  • 敏感 Tools 标记为"需要用户确认"
  • 用 Tools 做只读查询（应该用 Resources）
  • 用 Resources 做写操作（违反只读语义）
  • 把所有操作都做成 Tools（缺乏语义区分）
  • Tool 参数不用 JSON Schema（LLM 无法正确传参）
  • 敏感操作不设确认机制（安全风险）
生产案例：某企业 Agent 平台接入 MCP 后，工具集成时间从"每个工具 2~3 周"（定制 API 开发）降至"每个工具 1~2 天"（实现 MCP Server）。平台已接入 47 个 MCP Server，提供 312 个 Tools、89 个 Resources、23 个 Prompts。最活跃的 Server 是"内部知识库 Server"（日均调用 12,000 次），其次是"JIRA Server"（日均调用 8,500 次）和"数据库 Server"（日均调用 6,200 次）。

四、传输层设计：stdio / HTTP+SSE / Streamable HTTP

MCP 支持三种传输方式：stdio（标准输入输出，本地首选，零配置、安全）、Streamable HTTP（远程推荐方案，替代旧的 HTTP+SSE）、HTTP+SSE（遗留远程方案）。选择哪种传输方式取决于部署场景——本地开发用 stdio（简单高效），生产远程部署用 Streamable HTTP（支持分布式）。

stdio 传输机制

stdio 模式下，MCP Server 作为子进程运行，Host 通过 stdin 发送 JSON-RPC 消息，通过 stdout 接收响应。每条消息以换行符分隔。优点是零网络开销、实现简单；缺点是只能单机使用、不支持多 Host 共享同一 Server。

SSE + HTTP 传输机制

SSE 模式下，Client 通过 HTTP POST 发送请求，Server 通过 SSE 推送响应和通知。SSE（Server-Sent Events）是单向推送通道（Server→Client），HTTP POST 是请求通道（Client→Server）。这种"双通道"设计支持双向实时通信。生产环境必须使用 TLS 加密（HTTPS），防止数据窃听和篡改。

Streamable HTTP 传输机制

Streamable HTTP 是 MCP 新一代远程传输推荐方案（替代旧的 HTTP+SSE）：Client 通过单一 POST /mcp 端点发送 JSON-RPC 请求，Server 按需返回普通响应或升级为 SSE 流，支持 HTTP 认证与会话管理，适合远程服务与生产环境。旧的 HTTP+SSE 方式（SSE 通道 + HTTP POST 双端点）已标记为遗留方案，仅用于遗留系统。

五、安全机制：三层模型与六层防护

MCP 的安全模型基于"最小权限原则"——每个 Server 只暴露必要的 Tools 和 Resources，Host 可以控制哪些 Server 对 LLM 可见。敏感操作（如删除文件、发送邮件）必须设为"需要用户确认"（human-in-the-loop）。核心原则：用户始终在控制回路中（Human-in-the-loop），不允许 LLM 自主执行危险操作。类似浏览器的安全模型——Client 和 Server 互不完全信任。

传输层安全

本地 stdio 模式天然安全（进程隔离，无网络暴露）。远程 SSE 模式必须使用 TLS 加密（HTTPS），防止数据窃听和中间人攻击。Server 应验证 Client 的身份（如 API Key 或 OAuth Token），防止未授权的 Client 接入。

权限层安全

Host 配置 Server 白名单，只有白名单中的 Server 才能被 LLM 调用。每个 Server 只暴露最小必要的 Tools（如数据库 Server 只暴露 run_query，不暴露 drop_table）。权限配置应遵循"最小权限原则"——LLM 只能访问完成任务所需的最小工具集。

操作层安全

敏感操作（如删除文件、发送邮件、执行 SQL DDL）应设为需要用户确认（human-in-the-loop）。MCP 协议支持 Server 标记某些 Tools 为 requiresConfirmation，Host 在调用前弹出确认框。用户确认后才会执行操作，防止 LLM 自主执行危险操作。

生产案例：某金融 Agent 平台在接入 MCP 后，通过三层安全机制防止了 3 次潜在安全事故：① LLM 尝试调用 drop_table 工具（未在白名单中，被权限层拦截）；② LLM 尝试删除用户数据（标记为 requiresConfirmation，用户拒绝确认）；③ 外部 Server 尝试未授权接入（API Key 验证失败，被传输层拦截）。平台已安全运行 180 天，处理 230 万次 Tool 调用，零安全事故。

六、MCP vs Function Calling vs 定制 API

MCP 不是唯一的工具集成方案——Function Calling（单个 LLM API 的特性）和定制 API（为每个工具写专用集成代码）各有适用场景。MCP 的优势在于"标准化"和"可复用"，但实施成本高于 Function Calling。二者不是替代关系，而是互补——MCP 在上层（标准化发现/通信/安全），Function Calling 在下层（LLM 调用工具的底层机制）。

维度MCPFunction Calling定制 API
层次应用级协议（独立标准）模型级 API（LLM 特性）应用级（专用集成）
标准化✅ 开放标准，跨 LLM 通用❌ 每个 LLM API 格式不同❌ 每个工具定制开发

Q&A（10 题）

MCP 和 Function Calling 的本质区别是什么？为什么需要 MCP？能否一起用？
本质区别在"层次"和"目的"。Function Calling 是单个 LLM API 的特性（如 OpenAI 的 tools 参数），是 LLM API 层面的"工具调用机制"——LLM 生成 JSON 表示要调用什么函数，但每个 LLM 的格式不同（OpenAI vs Anthropic vs Google）。MCP 是一个独立的协议标准，是应用层面的"通信协议"——定义了 LLM 应用（Host）如何通过统一接口连接外部工具服务器（Server），工具如何被发现、描述、访问和安全管理，跨 LLM 通用。需要 MCP 的核心原因是"M×N 问题"：10 个 AI 应用 × 20 个数据源 = 200 个集成；有 MCP 后变成 10 + 20 = 30 个组件。类比 LSP 对 IDE 的意义——写一个 Language Server 所有 IDE 都能用。二者是互补关系，可以一起用：MCP 在上层（标准化发现/通信/安全），Function Calling 在下层（LLM 调用工具的底层机制），MCP Server 内部可以使用任何 LLM API 的 Function Calling 能力。
MCP 支持哪些传输方式？如何选择合适的传输方式？
三种传输方式：① stdio（标准输入输出），用于本地进程间通信，Server 作为子进程运行，通过 stdin/stdout 交换 JSON-RPC 消息，零配置、零网络开销，延迟 < 1ms，天然安全（进程沙箱）；劣势是无法远程。② HTTP+SSE（Server-Sent Events + HTTP POST），旧的远程方案，支持跨机器、跨网络调用，延迟 10~100ms，需要 TLS 加密。③ Streamable HTTP，新一代远程推荐方案（替代 HTTP+SSE）：POST /mcp 单一端点 + 可选 SSE 流，支持 HTTP 认证与会话管理，适合远程服务与生产环境。选择原则：开发调试阶段一律用 stdio（最简单），生产环境本地工具继续用 stdio，需要远程访问的服务切换到 Streamable HTTP。新项目不要用旧的 HTTP+SSE 方式。混合部署：核心 Server 用 stdio 部署在 Host 同机器，外部 Server 用远程方式连接。JSON-RPC 2.0 是统一的底层消息格式，各传输方式的消息内容完全一致。
如何开发一个 MCP Server？需要多少代码？
MCP 提供了 Python 和 TypeScript SDK，核心步骤：① 定义 Tools（名称、描述、参数 JSON Schema）；② 实现 Tool 处理函数；③ 启动 Server 监听连接。一个最简 Server 约 50 行代码（Python SDK）。最快方式是 Python 的 FastMCP：①安装 pip install mcp；②用 FastMCP("name") 初始化；③用 @mcp.tool() 装饰器定义工具（docstring 自动变描述，类型注解生成 schema）；④用 @mcp.resource("uri://...") 定义资源；⑤运行 mcp.run() 启动 stdio 传输。TypeScript 用 McpServer SDK：server.tool(name, desc, zodSchema, handler)，schema 用 zod 定义，适合和前端/VS Code 扩展集成。开发后在 Claude Desktop / Cursor 配置中添加 server 即可使用。推荐使用官方 SDK（而非自己实现协议），SDK 已封装 JSON-RPC 通信、Tool 注册、错误处理等基础设施。stdio 开发/调试首选，生产用 Streamable HTTP。
MCP Server 之间能互相调用吗？为什么？
MCP 协议本身不支持 Server 间直接通信（避免循环调用和权限传递问题）。如果需要 Server 间协作，应通过 Host 层编排：Host 调用 Server A 获取结果，再调用 Server B 使用该结果。这种"星型拓扑"（所有通信都经过 Host）保持了架构的清晰性和安全性——Host 可以控制所有交互，防止 Server 间形成不受控的调用链。如果 Server 间需要频繁协作，考虑将相关功能合并到同一个 Server 中。
MCP 的四大原语各自的使用场景是什么？
①Tools 是最常用的——Server 暴露的可执行函数，由 LLM 决定是否调用（需人类审批），适用于有副作用的操作（发消息、创建文件）；②Resources 是只读数据源——由应用层决定何时读取，适用于向 LLM 提供上下文（项目文档、配置文件）；③Prompts 是预定义提示模板——类似 Slash Commands，用户选择后展开为完整 prompt，适用于标准化工作流（代码审查模板）；④Sampling 是唯一的反向原语——Server 请求 Client 的 LLM 做推理，适用于 Server 需要 AI 辅助的场景（如日志分类），但必须经用户批准。
MCP 的 Prompts 原语有什么实际用途？使用频率高吗？
Prompts 允许 Server 提供预定义的提示词模板，Host 可以直接使用而不用每次手写 prompt。实际用途：① GitHub Server 提供"代码审查"prompt 模板（接受 diff 参数，生成审查意见）；② 数据库 Server 提供"SQL 生成"prompt 模板（接受 schema 和自然语言描述，生成 SQL 查询）；③ 文档 Server 提供"摘要生成"prompt 模板（接受长文档，生成摘要）。使用频率相对较低（约 5%），但在标准化工作流（如代码审查、Bug 分析）中非常有价值——它确保了所有用户都使用相同的 prompt 格式，提高了一致性和可维护性。
MCP 的能力协商机制有什么好处？
初始化时 Client 和 Server 互相交换支持的功能列表——只有双方都声明的功能才激活。好处：①向前兼容——新版功能，老版 Client 没声明则自动跳过，不报错；②渐进式采用——Server 可以只实现部分功能；③安全控制——Host 可选择不声明某些能力（如不支持 Sampling 则 Server 无法请求 LLM）。保证兼容的机制：protocolVersion 用于大版本跳跃；能力字段的嵌套结构允许同一功能有不同子特性级别。这个设计直接借鉴了 LSP 的成功经验。
MCP 的安全机制够吗？如何应对 LLM 自主执行危险操作、防止恶意 Server？
MCP 的安全机制（三层模型、六层防护）覆盖了大部分安全场景。关键防线：①传输安全（stdio 进程隔离 / HTTPS TLS 加密防止数据窃听）；②认证（OAuth 2.0 / API Key，远程 Server 必须认证 Client 身份）；③授权（Server 白名单防止未授权接入，Server 只暴露允许的操作）；④人类审批（高风险工具调用需用户确认，human-in-the-loop 防止 LLM 自主执行危险操作）；⑤输入校验（JSON Schema）；⑥速率限制（防止 LLM 过度调用工具）。防止恶意 Server：Client 和 Server 互不完全信任（类似浏览器安全模型）；Host 应审核 Server 的 description 和 schema（可能有欺骗性）；社区 Server 建议沙箱执行（Docker 容器）；Sampling 请求也需用户批准。对于高风险操作（如金融交易、数据删除），建议额外增加：操作审计日志（记录所有 Tool 调用）、频率限制（防止 LLM 短时间内大量调用）、异常检测（监控 Tool 调用模式，发现异常告警）。安全是持续的过程，需要定期审计和更新策略。
MCP Server 的性能如何？会成为瓶颈吗？
MCP Server 的性能取决于两个因素：① 协议开销（JSON-RPC 序列化/反序列化 + 网络传输），② Tool 执行时间（如数据库查询、API 调用）。协议开销很小（JSON-RPC 消息通常 < 10KB，序列化耗时 < 1ms），不是瓶颈。真正的瓶颈是 Tool 执行时间——如果某个 Tool 需要调用慢速外部 API（如 3 秒响应），该 Tool 的延迟就是 3 秒。优化策略：① 异步执行（Tool 返回任务 ID，Client 轮询结果）；② 结果缓存（相同参数不重复执行）；③ 并行调用（多个无依赖 Tool 同时执行）。生产环境监控每个 Tool 的 P95 延迟，超过 5 秒的 Tool 需要优化。
MCP 和 LangChain 的 Tool 系统是什么关系？
LangChain 的 Tool 系统是应用内部的工具抽象（定义了 Tool 的接口和调用方式），MCP 是跨应用的工具集成协议（定义了 Host 如何连接外部 Server）。二者可以互补：LangChain 应用可以作为 MCP Host，通过 MCP 协议连接外部 Server 获取工具；MCP Server 返回的 Tools 可以转换为 LangChain 的 Tool 对象，供 Agent 使用。这种组合实现了"LangChain 做 Agent 逻辑，MCP 做工具集成"——LangChain 负责推理链和状态管理，MCP 负责连接外部工具服务器。
