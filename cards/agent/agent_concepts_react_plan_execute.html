A10 · Agent 概念、原理与构建模式

LLM 的局限 → Agent 的定义 → ReAct 模式 → 系统提示词设计 → 代码实现 → Plan-and-Execute 模式

Agent 的本质是"LLM 当大脑 + 工具当手脚 + 主程序当神经系统"——模型负责想和决定，主程序负责调度执行，循环跑起来就能自主完成任务。

一、从 LLM 到 Agent — 为什么需要 Agent

LLM 的核心局限

大模型（如 GPT-4o、DeepSeek）回答问题能力强，但有两个根本性缺陷：

  • 无法感知外界环境 — 不主动给信息，模型无法自行查看文件、数据库或网络
  • 无法改变外界环境 — 模型只能输出文本，不能写文件、执行命令、调用 API

举例：让 GPT-4o 写贪吃蛇游戏，它能给代码，但"把代码写入文件"这步必须你自己来。如果你已有贪吃蛇代码想让模型改写，也必须你手动复制粘贴给它。

Agent = LLM + 工具

Agent（AI Agent）的本质：给大模型接上"感官和四肢"，让它能自主感知和改变外部环境。

组件类比作用
LLM🧠 大脑推理、决策、生成
工具（Tools）🤖 感官+四肢读写文件、执行命令、搜索网络
Agent 主程序⚙️ 神经系统串联模型与工具的执行循环
Agent 不是一个新模型，而是一种架构模式：LLM 做大脑 + 工具做手脚 + 主程序做调度 = 能自主完成复杂任务的智能程序。

LLM 只会"说"，Agent 能"做"——分水岭就是有没有能改变外部环境的工具和一个执行循环。

Agent 的典型应用场景

Agent 类型代表产品核心能力
编程 AgentCursor、Claude Code自动读写代码、运行终端、调试
搜索 AgentManus自动搜索、浏览网页、整理报告
办公 Agent各类 PPT/Excel Agent自动操作 Office 软件

二、ReAct 模式 — Agent 最核心的运行模式

ReAct 是什么

ReAct（Reasoning and Acting，思考与行动）是目前使用最广泛的 Agent 运行模式，由 2022 年 10 月的论文提出，至今仍是主流。

ReAct = Reasoning + Acting：想一步、做一步、看一步，如此循环直到任务完成。

ReAct 核心循环

用户提交任务 ↓ ┌─── Thought（思考） ─── 模型分析当前状态，决定下一步 │ ↓ │ Action（行动） ────── 模型请求调用某个工具 │ ↓ │ Observation（观察） ── 工具执行结果返回给模型 │ ↓ │ （循环，直到任务完成） │ ↓ └── Final Answer ──────── 模型认为任务完成，输出最终答案

四个核心标签

标签英文含义示例
Thought思考模型分析当前状态，判断下一步"用户需要贪吃蛇游戏，我先写 HTML 文件"
Action行动请求调用工具（注意是请求）"调用 write_to_file('index.html', content)"
Observation观察工具执行结果返回"写入成功"
Final Answer最终答案任务完成，输出结果"贪吃蛇游戏已完成，三个文件已创建"
大模型本身不能调用工具，只能"请求调用"。真正执行工具的是 Agent 主程序。这个区别非常重要：模型输出 Action 标签 → Agent 主程序解析 → 执行对应函数 → 返回 Observation（观察，即工具执行后返回给模型的结果）。

三、ReAct 系统提示词设计

ReAct 模式不是靠模型训练实现的，而是靠系统提示词（System Prompt）。系统提示词相当于给模型安排了一个"迷你剧本"，模型会严格按照剧本执行。

系统提示词就是 Agent 的"演出剧本"——ReAct 不是训练进模型的，而是写进提示词里，模型照着剧本演。

系统提示词五大组成部分

部分作用关键内容
① 职责描述定义 Agent 的角色和运行规则"你需要将任务分解为多个步骤，每步先 Thought 再 Action..."
② 示例用 few-shot（少量示例，通过示范教会模型输出格式）示例教模型格式埃菲尔铁塔高度的完整 Thought→Action→Observation→Final Answer 示例
③ 可用工具列出可调用的工具及参数read_file、write_to_file、run_terminal_command
④ 注意事项约束模型行为"每次只调用一个工具"、"确保路径正确"
⑤ 环境信息提供运行时上下文当前操作系统、项目目录、文件列表
系统提示词 = 角色定义 + 运行规则 + 示例 + 工具清单 + 环境信息。它决定了 Agent 的每一步该怎么走，是 ReAct 模式的核心。

系统提示词与用户任务的关系

规范做法是系统提示词和用户任务分开传给模型（System Message vs User Message）。但部分模型（如 DeepSeek 网页版）不支持分开提交，此时可以合并为一条消息，大多数情况下也能正常运行。

四、ReAct Agent 代码实现

核心架构

┌──────────────────────────────────────────────────┐ │ Agent 主程序 │ │ │ │ 1. 构建 messages = [system_prompt, user_task] │ │ 2. while True: │ │ a. response = call_model(messages) │ │ b. 提取 thought，打印 │ │ c. if response contains "Final Answer": │ │ return final_answer │ │ d. 提取 action (工具名 + 参数) │ │ e. result = execute_tool(action) │ │ f. 打印 observation │ │ g. messages.append(observation) │ │ h. 回到步骤 a │ └──────────────────────────────────────────────────┘

关键代码逻辑

  • 工具列表：read_file、write_to_file、run_terminal_command — 工具就是普通函数
  • 模型调用：采用同步返回（非流式），简化代码复杂度
  • 安全机制：运行终端命令前会询问用户确认（因为终端命令有破坏性）
  • 循环终止：检测到 Final Answer（最终答案，模型判断任务完成时输出的终止信号）标签时退出 while 循环

Agent 主程序说白了就是一个 while 循环：调模型 → 解析 Action → 执行工具 → 把结果喂回模型，直到出现 Final Answer。

五、Plan-and-Execute 模式 — 先规划再执行

ReAct 是"边想边做"，而 Plan-and-Execute 是"先规划全局，再逐步执行"。LangChain 提出的这套模式在很多复杂任务中表现更好。

Plan-and-Execute 像"项目经理带工程师"：Plan 模型定计划，执行 Agent 干活，Replan 模型复盘修订。

四个核心模块

模块职责类比
Plan 模型接收用户问题，生成初始执行计划📋 项目经理
Replan 模型根据执行结果动态调整计划📋 项目经理（修订版）
执行 Agent执行计划中的单个步骤（可以是 ReAct Agent）🔧 工程师
Agent 主程序串联整个 Plan → Execute → Replan 循环⚙️ 调度中心

运行流程

用户提问 → Agent 主程序 → Plan 模型 → 生成执行计划 [Step1, Step2, Step3] ↓ ┌─── 循环开始 ──────────────────────┐ │ 1. 取当前计划的第一步 │ │ 2. 发给执行 Agent 执行 │ │ 3. 执行结果加入历史记录 │ │ 4. Replan 模型根据结果生成新计划 │ │ - 删除已完成的步骤 │ │ - 用实际数据替换占位符 │ │ - 或返回 Final Answer │ │ 5. 如果还有步骤 → 回到 1 │ └────────────────────────────────────┘

模拟示例：查询澳网冠军家乡

轮次执行步骤执行结果Replan 后的新计划
第 1 轮查询当前日期2025年[查2025年澳网男单冠军, 查冠军家乡]
第 2 轮查2025年澳网男单冠军辛纳[查辛纳的家乡]
第 3 轮查辛纳的家乡意大利圣坎迪多所有步骤完成 → Final Answer
Plan-and-Execute 内部嵌套了执行 Agent（Agent 套 Agent），执行 Agent 可以用 ReAct 模式，也可以用其他模式。Plan-and-Execute 只关心"能否完成步骤"，不关心内部怎么实现。

六、Agent 开发最佳实践

  • 系统提示词用模板 + 占位符，动态填充环境信息
  • 工具函数保持单一职责（一个函数做一件事）
  • 危险工具（如终端命令）执行前让用户确认
  • 用 few-shot 示例教会模型输出格式
  • 将 Observation 追加到 messages 列表，保持上下文连续
  • 不要在系统提示词中塞太多无关信息
  • 不要让模型自己执行工具（模型只能请求）
  • 不要省略安全确认直接执行破坏性操作
  • 不要一次性给模型太多工具（选择困难）
  • 不要忽略 Observation 的格式（模型依赖格式解析）

最佳实践的核心就一句话：让模型只管决策，让主程序负责执行与安全把关——各司其职。

高频问答

什么是 AI Agent？它和普通 LLM 应用有什么区别？
AI Agent 是在大模型基础上增加了工具调用能力的智能程序，能够自主感知和改变外部环境。核心区别：普通 LLM 应用只能输出文本，Agent 能自主读写文件、执行命令、调用 API，形成"思考→行动→观察"的闭环。Agent = LLM（大脑）+ Tools（感官和四肢）+ 主程序（调度循环）。
ReAct 模式的核心流程是什么？为什么叫 ReAct？
ReAct 是 Reasoning and Acting 的缩写。核心流程是四步循环：Thought（模型思考）→ Action（请求调用工具）→ Observation（观察工具结果）→ 循环或 Final Answer。关键特点：①模型只能请求调用工具，不能直接执行；②每次观察后模型重新思考是否继续；③循环直到模型返回 Final Answer。这个模式由 2022 年论文提出，至今仍是 Agent 最主流的运行模式。
ReAct 模式是通过模型训练实现的吗？
不是。ReAct 模式主要通过系统提示词（System Prompt）实现，而非模型训练。系统提示词定义了模型的角色、运行规则、可用工具和环境信息，相当于给模型安排了一个"迷你剧本"。模型会严格按照提示词中定义的格式输出 Thought/Action/Observation/Final Answer 标签。这意味着换一个模型，只要支持系统提示词，就能实现 ReAct。
ReAct 和 Plan-and-Execute 模式有什么区别？各自适合什么场景？
ReAct 是"边想边做"，每一步根据当前状态决定下一步行动，适合简单任务和少量工具调用。Plan-and-Execute 是"先全局规划，再逐步执行"，包含 Plan 模型（生成计划）、Replan 模型（动态调整计划）和执行 Agent（执行单步），适合复杂多步骤任务。主要区别：①策略不同（即时决策 vs 全局规划）；②模型调用次数不同（每轮1次 vs 每轮2次）；③Plan-and-Execute 内部嵌套了执行 Agent（Agent 套 Agent）。Manus 和 Claude Code 中都能看到 Plan-and-Execute 的影子。
Agent 中"模型请求调用工具"和"模型调用工具"有什么本质区别？
这是一个关键的设计区分。模型只能输出"我想调用 write_to_file 工具，参数是 xxx"（请求），真正执行工具函数的是 Agent 主程序。这种分离设计的好处：①安全性 — 主程序可以在执行前做权限检查、用户确认；②可控性 — 主程序可以限制工具调用频率、添加日志；③灵活性 — 同样的模型输出，不同主程序可以有不同执行策略。如果让模型直接调用工具，就失去了安全控制和审计能力。
为什么 Agent 在运行终端命令前通常需要用户确认？
终端命令具有不可逆的破坏性（如 rm -rf、数据库操作），而模型的推理并不总是正确的。用户确认是一个安全兜底机制：①防止模型误判执行危险命令；②让用户对关键操作有感知和控制权；③生产环境中可以作为审批流的一部分。目前主流编程 Agent（如 Cursor、Claude Code）都在终端命令执行前设置了确认机制。
