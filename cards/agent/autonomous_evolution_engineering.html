A65 · Agent 自主进化工程路径

五大工程维度 / 六阶段闭环 / 经验提取与能力固化 / 四级受控发布

系统不会因为执行次数变多而自然进化——进化是一项工程能力：执行经验必须被提取为带证据链的候选、固化为带版本的资产、再经过四级受控发布，才算真正进入系统能力。

一、从自主规划到自主进化

今天大多数 LLM Agent 本质上仍是"一次性问题求解器"，业界的痛点可以概括为四件事：

静态知识模型的知识在训练完成那一刻就被冻结
上下文有限上下文窗口再长也有边界
重复犯错今天教会它的东西，明天还会再错一遍
训练昂贵每一次想让它变强，都得重跑一遍昂贵的训练

所谓自主进化（Self-Evolution），指的就是让 Agent 在与环境交互的过程中自动积累经验、提炼能力、并在后续任务中复用与提升，把"越用越强"从口号变成可交付的工程属性。

但必须先做一个关键区分：自主规划不等于自主进化。自主规划决定的是"当前任务的下一步动作"，它运行在任务内循环里，输出是动作序列，会话一结束一切归零；自主进化决定的是"哪些改进可以进入系统的下一个版本"，它运行在系统外循环里，输出是持久化的能力资产。前者消耗上下文，后者积累资产；前者失败损失一次任务，后者失败污染所有后续任务。研究界对自我改进机制的分类也印证了这一点：更新模型权重的路线慢而持久，而更新脚手架（Prompt、记忆、工具、工作流）的路线快、便宜且可回滚——工程上可落地的自主进化，主要发生在脚手架层。

维度自主规划自主进化
决策对象当前任务的下一步动作哪些改进进入下一系统版本
时间尺度秒~分钟（任务内）天~月（版本间）
输出物动作序列、工具调用Memory / Skill / Workflow 资产
生命周期随会话结束而消失跨任务、跨会话持久存在
失败代价损失一次任务污染所有后续任务
验证方式任务结果本身独立评测 + 影子 + 灰度

把两者串起来的是一条六阶段闭环：设计 → 执行 → 测试 → 优化 → 发现 → 进化。设计阶段产出契约化目标，执行阶段状态化地跑任务，测试阶段收集外部证据，优化阶段修复本次任务的缺陷，发现阶段从多次执行中识别稳定模式（经验提取），进化阶段把验证过的经验固化为资产并受控发布——发布后的资产又注入下一轮的设计阶段，闭环由此成立。缺任何一段，系统都只是"跑了很多次"而不是"进化了"。

┌──────────────────────────────────────────────┐ │ 新资产回注下一轮设计（闭环） │ ▼ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ ① 设计 │───▶│ ② 执行 │───▶│ ③ 测试 │ │ │ 契约化目标 │ │ 状态化运行 │ │ 外部证据 │ │ └──────────┘ └──────────┘ └────┬─────┘ │ │ │ ┌──────────┐ ┌──────────┐ ┌────▼─────┐ │ │ ⑥ 进化 │◀───│ ⑤ 发现 │◀───│ ④ 优化 │ │ │ 受控发布 │ │ 经验提取 │ │ 修复缺陷 │ │ └────┬─────┘ └──────────┘ └──────────┘ │ └── Memory / Skill / Workflow 资产 ──────────────┘

为什么"系统不会因执行次数自然进化"？因为执行本身只产生日志，不产生能力。从日志到能力中间隔着四个工程环节：提取（跨轨迹识别稳定模式）、验证（证据链 + 反例 + 可重跑的验证方法）、固化（分流进 Memory/Skill/Workflow 并版本化）、受控发布（四级门禁加熔断）。缺了提取，日志只是数据囤积；缺了验证，偶发事件会污染长期记忆；缺了发布，改进无法安全进入生产；缺了回滚，每次进化都是单向门。

研究证据：Voyager 证明了"技能积累"路线的复利效应。Voyager（NVIDIA/Caltech 等，2023）是首个 LLM 驱动的终身学习 Agent，在 Minecraft 中用"自动课程 + 技能库 + 迭代式提示"三件套持续探索：相比 ReAct、Reflexion、AutoGPT 等基线，它获得的独特物品种类达 3.3 倍、移动距离 2.3 倍、解锁科技树关键节点最快 15.3 倍，且是唯一解锁到钻石工具层级的方法；学到的技能库还能迁移到全新世界中从零解决新任务。但要注意——Voyager 身处的是可控沙盒，失败成本为零；生产环境有真实用户、真实费用与不可逆副作用，所以生产系统的进化必须加上"受控"二字。

规划回答"下一步做什么"，进化回答"下一个版本留下什么能力"——前者消耗上下文，后者积累资产，这是两个完全不同的回路。

二、受约束规划与持续执行

2.1 受约束规划：目标必须是一份契约

进化的第一块地基是受约束规划：交给 Agent 的目标不能是一句愿望，必须是一份四要素契约——范围限定、验收标准、执行预算、停止条件。没有边界的任务会让 Agent 在无关模块里漫游、用无限步数换取微弱进展，最后留下一堆无法判定成败的中间产物；契约的作用是把"做完了吗"变成一个可以机械判定的问题，这是后续一切验证的前提。

以"修复登录超时问题"为例，一份合格的契约长这样：范围限定为仅修改认证模块，不碰网关与用户中心；验收标准为接口行为不变 + 全量回归测试通过；执行预算为最多 20 步工具调用；停止条件为连续 3 次尝试未产生新证据即转人工。四个要素各自堵死一类失控：范围限定防扩散，验收标准防自欺，执行预算防漫游，停止条件防死循环。

契约要素示例值工程作用缺失的后果
目标范围限定仅修改认证模块圈定可改动的代码/资源边界Agent 漫游无关模块，副作用扩散
验收标准接口行为不变 + 回归测试通过把"完成"变成可机械判定Agent 自称完成，实则未验证
执行预算最多 20 步工具调用限制成本与时间上限无限重试烧钱，任务无限拉长
停止条件3 次无新证据即转人工识别并终止无效循环死循环、重复同一失败动作

2.2 持续执行：六类运行时状态必须结构化落盘

长任务的执行状态不能只存在于上下文窗口里。进程会被 OOM 杀死、模型服务会 503、部署会滚动重启，任何一次中断都不应该让所有进展清零。工程上需要结构化保存六类运行时状态：

任务计划当前分解到第几步
产物修改记录改了哪些文件 / 记录
工具调用结果每次调用的入参与返回
测试与证据结果验收标准的逐项判定
预算消耗已用步数 / Token / 费用
经验候选池本次执行中浮现的模式线索

这六类状态既是断点恢复的依据，也是事后经验提取的原材料。

支撑持续执行的有三个机制：检查点（Checkpoint，把完整执行状态快照到持久存储，恢复时从最近的已知良好点继续）、事件日志（Event Sourcing，把每次状态迁移写成只追加的不可变事件，可精确重放、可审计）、幂等 Key（由任务 ID + 步骤 + 参数哈希派生的唯一标识，让下游系统对重复请求去重）。这正是持久化执行（Durable Execution）的三支柱：事件溯源让执行历史而非代码成为唯一事实源，确定性重放让新 worker 从头跑代码却不再真正调用外部系统，幂等性让重放区间里的写操作天然去重。三者分工明确：检查点决定从哪恢复，事件日志决定哪些已经发生，幂等 Key 决定重放时副作用是否安全。

任务执行 ──▶ 每一步: [LLM 输出 / 工具调用] │ ├─ 写事件日志 (append-only, 结果只记一次) ├─ 写操作携带幂等 Key (task_id:step:hash) └─ 关键节点写 Checkpoint (完整状态快照) │ ──── 崩溃 / OOM / 滚动重启 ──── │ ▼ 恢复: 读最近 Checkpoint ──▶ 重放其后的事件日志 │ ├─ LLM 输出从日志取, 绝不重新付费调用 └─ 幂等 Key 去重: 已完成的副作用变 no-op
机制解决的问题粒度局限
Checkpoint 快照崩溃后不必从零重跑每个关键步骤后一次最后一次快照后的工作会重放
事件日志精确恢复 + 审计 + 分叉回放每次状态迁移一条事件实现复杂，需区分"观测事件"与"权威结果"
幂等 Key重放/重试不产生重复副作用每个有副作用的工具调用只覆盖写操作，读操作天然幂等

幂等 Key 的典型派生方式是"任务 ID : 步骤号 : SHA256(参数指纹)"——同一步骤同样参数在任何重试/重放中永远生成同一个 Key，下游据此把重复的写请求去重成 no-op。幂等 Key 的完整工程设计（意图驱动的 Key 组成、状态机单向约束、幂等表持久化屏障、生产监控指标）见 A59 · AI Agent 幂等性设计，幂等性与重试/失败处理的配合见 A60 · Agent 系统失败处理策略。

有一个必须澄清的概念：Checkpoint 不等于 Durable Execution。检查点像游戏存档，能让你从上一关继续，但如果在"领取奖励后、存档前"断电，重进游戏可能又领一次奖励。同理，Agent 在"邮件已发出、状态还没写回"的窗口里崩溃，光有 Checkpoint 的调度器会从头重跑整条链路，客户就收到两封邮件。所以检查点之外还必须有幂等边界：这封邮件发过没有？用的哪个幂等 Key？上游返回的 message id 是什么？查不到状态时该重试、转人工还是标记 unknown——这些都要显式设计。

为什么值得为这些机制投入工程量？算一笔账：单步成功率 99.5% 听起来很高，但 7 步流水线整体成功率只剩 0.995⁷ ≈ 96.5%，20 步的 Agent 任务只剩 ≈ 90.5%。长链路执行中失败是统计必然，问题从来不是"会不会中断"，而是"中断之后是恢复还是重来"。

生产案例：一次 OOM 如何烧掉双倍账单。某团队的批处理 Agent 一次要审 50 个 PR，运行到第 14 个时撞上模型服务限流（429），紧接着容器 OOM 被杀。由于没有任何持久化，重跑意味着第 1~13 个 PR 的 LLM 调用全部重付一遍——单次事故直接让该任务的 LLM 账单翻倍，而且重跑走的路径还可能与原来不同，产生二次写操作。另一个典型案例是运行 40 分钟、已执行 11 次工具调用的重构 Agent，在 worker 进程崩溃后一切归零：建好的计划、已改的文件、付过费的 8 次 LLM 调用全部蒸发。这两类事故的修复方案完全相同——每步结果写入事件日志、写操作携带幂等 Key、关键节点打 Checkpoint——改造后崩溃从"任务作废"降级为"从断点续跑的普通事件"。

检查点决定"从哪恢复"，事件日志决定"发生过什么"，幂等 Key 决定"重放是否安全"——三者合起来，才把崩溃从事故变成普通事件。

三、经验提取：从失败到稳定模式

3.1 从轨迹到带证据的候选

执行留下了日志和状态，不等于留下了经验。把全部会话记录直接塞进长期记忆是最常见的错误——噪声、偶发事件和过时信息会一起沉淀下去，形成记忆污染，此后每次决策都被错误先验带偏。经验提取要做的是从多条执行轨迹中识别稳定模式：比如"仓库级回归测试漏跑"这一失败模式在 5 个失败任务中出现了 3 次，且每次都伴随相同的日志特征，它才具备成为经验的资格。

还有一个容易被忽略的来源：失败轨迹比成功轨迹更值得挖。只从成功运行中总结工作流的做法，会漏掉学习的第一原材料。Google 的 ReasoningBank 框架专门从失败经验中蒸馏"反事实信号与陷阱"，把错误提炼成预防性教训——例如不是学会"点击加载更多按钮"这样的程序性动作，而是学会"先验证当前页面标识符，避免落入无限滚动陷阱"这样的策略性护栏。配合 LLM-as-judge 对轨迹自评再提取，且对评判噪声有相当的鲁棒性，这条"检索 → 提取 → 整合"的持续闭环已被证明能同时提升成功率与执行效率。

模式被识别后先写成经验候选（ExperienceCandidate）——注意是"候选"，它还没有资格进入任何资产库。一个合格的候选必须包含五个要素，缺任何一个都不允许进入固化流程：

要素内容作用缺失的后果
问题描述触发该经验的任务特征与现象定义"什么时候适用"检索时无法匹配，经验沦为死数据
独立证据链≥2 条独立轨迹的日志/测试结果排除单次巧合偶发事件被误当规律
适用范围明确的任务类型/模块/环境边界限定泛化半径局部结论被误用到全局
反例说明已知的不适用场景防止过度泛化边界外强行套用，引入新故障
验证方法可重跑的验证步骤或评测用例让经验可被证伪经验无法复核，只能盲信

3.2 统计判定：模式够不够"稳定"是一道数学题

"出现了 3 次"只是直觉判断，工程上必须把"稳定"变成可计算的门槛。经验提取的统计判定通常包含三道关：

第一道：频次与共现关

候选模式必须在 ≥2 条相互独立的轨迹中出现（同一任务的三次重试不算独立证据），且模式特征与失败结果的共现率要显著高于基线。如果"漏跑回归"在失败任务中出现率 60%、在成功任务中只有 5%，这个差异才有提取价值。

第二道：样本量关

任何"加入该经验后成功率提升"的结论，都必须在冻结的留出集上对照测量，且每臂样本量要足够——经验法则是至少 50 个数据点以上才谈得上判断，否则观测到的差异大概率是抽样噪声。在线评分本身是有噪声的抽样，晋级判据应该是候选对锁定基线的评分差值的显著性检验（如 Mann-Whitney U 检验，Netflix 的 Kayenta 金丝雀分析即用此法），而不是看绝对分数。

第三道：显著性与容忍带关

判据写成公式即"候选分 − 基线分 ≥ 容忍带下限 且 p 值 < 0.05"。注意基线必须是锁定的（如过去 7 天生产基线），不能是随时漂移的活数据，否则比较失去锚点。

晋级判据: ΔScore = Score(候选) − Score(锁定基线)
通过条件: ΔScore ≥ 容忍带 且 显著性检验 p < 0.05 且 样本量 ≥ 50/臂

五要素加三道统计关的本质，是把"经验"从观点变成可证伪的命题。证据链回答"这不是巧合"，适用范围与反例共同圈定泛化半径，验证方法与统计判据保证未来任何时候都能复核它是否仍然成立。

为什么"验证后才入库"值得坚持：Voyager 的消融实验。Voyager 的技能库只收录通过自我验证的程序，这个看似保守的设计在消融实验中得到了回报：移除技能库后，Agent 在相同迭代预算内的物品获取与科技树推进全面崩落，150 轮迭代内甚至追不上带技能库版本早期几个小时的进度——没有质量门槛的经验积累，堆出来的不是能力而是负担。

没有证据的经验是观点，没有验证的能力是负担——经验提取的价值不在"记下来"，而在"敢淘汰"。

四、能力固化：三类资产沉淀

4.1 三种资产各司其职

验证通过的经验候选按性质分流到三种资产，这是技能库式终身学习在工程上的落地形态：稳定事实进 Memory、可复用方法进 Skill、强制步骤进 Workflow。分流的判据只有一句话——"这条经验在下次任务中扮演什么角色"：是背景知识、是可选工具、还是必须遵守的流程。

验证通过的经验候选（五要素 + 统计判定） │ ┌────────────┼────────────────┐ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ 稳定事实 │ │ 可复用方法 │ │ 强制步骤 │ │ → Memory │ │ → Skill │ │ → Workflow │ │ 注入上下文 │ │ 按需检索调用│ │ 编排层强制 │ │ 过时即覆盖 │ │ 版本化管理 │ │ 不给自由度 │ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘ └───── 全部进入四级受控发布流水线 ─────┘
资产类型存什么典型例子更新方式生效方式
Memory（事实）稳定的环境与领域事实"本仓库回归命令是 make reg-all"事实变化时覆盖写任务开始时注入上下文
Skill（方法）可复用的解题方法/代码片段"超时排查：先抓慢查询再查连接池"版本化新增/合并/废弃按需检索，组合调用

4.2 Skill 规范：接口、版本、失败处理

三种资产的工程要求不同。Memory 追求新鲜度，过时事实比没有事实更危险；Workflow 追求确定性，一旦固化就由编排层强制执行，不给模型自由发挥的空间；Skill 的要求最完整，一份合格的 Skill 规范必须包含三项：

规范要求具体含义工程实现
明确输入/输出接口像函数签名一样可被调用方校验声明前置条件、入参格式、返回结构

失败处理机制技能执行失败时的降级与上报路径超时/异常分支、重试上限、人工升级

在资产运营层面，技能库的日常操作收敛为三类：新增（Add）、语义合并（Merge，保留技能身份、并集更新内容、递增版本号）、废弃（Discard），防止技能库无限膨胀、检索命中率持续下滑。一些前沿框架还引入了基于效用的治理：按环境反馈估计每条记忆的上下文相关效用，用它驱动"价值感知检索"，并周期性提升有用记忆、移除有害条目，形成"读—写—评估—治理"的完整生命周期。

技能以什么形态存在也很关键。主流实践正在收敛到带元数据头的 Markdown/代码文件：元数据声明名称、版本、输入输出接口与适用条件，正文是方法描述或可执行代码。这种形态的好处是人与模型都能直接读、diff 和评审工具天然可用、回滚就是 git revert。Voyager 是这条路线的早期验证：只有通过自我验证的代码才会入库，检索用技能描述的 Embedding 完成，新技能在旧技能之上组合生长——技能因此是时序扩展、可解释、可组合的，能力复利式增长同时缓解了灾难性遗忘。

检索同样要"按需"而非"全量"。在 SciWorld、AlfWorld 等终身学习环境里，把经验基组织为"事实—情景—技能"三库并按需主动检索的 PROACTAGENT，相比被动检索基线取得了最高 32% 的成功率相对提升，交互轮次平均减少超过 33%——固化的资产不仅要存得住，还要在该用时才取用，全量注入上下文会同时推高成本与噪声。

分流的判据只有一句话：这条经验下次是当背景、当工具还是当纪律——答案分别对应 Memory、Skill 与 Workflow。

五、受控进化：四级发布与熔断

5.1 四级流水线：每一级回答不同的问题

资产固化完成不等于可以上线。任何新 Skill、新 Prompt、新 Workflow 在本质上都等同于一次软件发布，而且比传统发布更危险——Agent 的行为是非确定性的，坏版本不会抛异常，它会按时返回 HTTP 200，只是答案更差。传统金丝雀靠错误率与 p99 延迟做晋升判断，而这两种信号对"流畅但错误"的回答完全失明。因此进化必须走四级流水线：独立评测（held-out eval）→ 影子运行（shadow）→ 灰度发布（canary）→ 正式启用（active），通不过任何一道门就原地止步。

四级之间不可互相替代。held-out 评测集再大也只是离线快照，无法覆盖真实流量的长尾分布；Shadow 用真实输入换来零风险的质量信号，但因为没有人真正看到候选的输出，它永远给不出"用户结果"信号；Canary 是唯一能买到真实用户反馈的层级，代价是让一小部分用户真实暴露。跳过 Shadow 的团队会带着质量回归上线，跳过 Canary 的团队会在永远无法收敛的离线数字上瘫痪。

反面教材：一次"离线全绿"的翻车。某团队用 6 周完成模型迁移，离线评测全部达标，周三上午 10 点直接切换 100% 流量。中午 12 点，账单 Agent 的函数调用准确率下跌 9 个点；下午 2 点，客服 Agent 的拒答率上升 7 个点，值班团队被迫从网关紧急回滚。事后复盘的结论只有三条：离线评测集低估了真实流量分布、没有分群在线监控、没有灰度门。离线分数与生产表现之间，隔着一条只有真实流量能填平的沟。

5.2 影子与灰度的指标设计

影子运行阶段要注意成本与评分两件事：镜像全部流量意味着约一倍的推理成本，预算有限时可以按采样率镜像（mirror 变体，把成本压到 N%）；评分必须"挂"在与基线相同的请求上下文中对比（score attached on the span），否则就是拿苹果比橘子。灰度发布阶段的流量分配要按稳定的用户/会话 ID 哈希分流，而不能按请求随机——否则同一个会话中途换模型，会话内的交叉污染会毁掉整个实验。放量应按分层 cohort（如按租户等级分层）进行，每一档暂停观察后再晋级。

更关键的是：传统运维指标必须补上"质量信号"这一环。做法是在 1%~10% 的采样流量上跑在线质量评分（LLM-as-judge 或护栏指标），把评分本身作为熔断与晋升的触发器——这是从 Web 服务金丝雀照搬到 Agent 系统时最容易漏掉的一环。评判器本身要先校准，工程目标是与人工判断的 Spearman 相关 ≥ 0.80。

5.3 六大工程特性验收清单

五个工程维度共同支撑六个可验收的特性：契约化、状态化、可验证、可积累、可发布、可恢复。它们不是口号而是逐条可以拿证据核对的检查项，维度与特性的支撑关系如下——每个 ● 代表一个验收点，任何一个 ● 缺失，对应维度就没有闭环。

落地时最常见的误区，是以为"系统在跑就是在进化"。对照六特性可以清楚看到四类"假进化"：

数据囤积只存日志不提取
记忆污染只提取不验证
裸奔发布有资产不灰度
单向门有发布无回滚

对小团队的务实建议是先闭合最小回路：选一个高频失败模式，为它走一遍完整的"提取候选 → 五要素验证 → 固化为一个 Skill → shadow 对比 → 5% canary → 全量"，用这一个闭环建立工具链与验收习惯，再逐步把其他失败模式纳入。

落地效果参考。某客服 Agent 团队围绕"售后政策问答"跑通了完整闭环：4 个月里从失败轨迹中固化出 12 个 Skill、3 个 Workflow，全部经四级发布上线。对照锁定基线的评估显示：一次解决率从 61% 提升到 78%，平均会话成本下降 23%，风险动作（如越权承诺退款）从每周平均 5 次降为 0。值得注意的是，这些数字全部来自灰度对照而非前后简单对比——没有对照组，"进化了多少"本身就不可验证。
  • 开工前先写四要素目标契约，范围与停止条件缺一不可
  • 六类运行时状态全部结构化持久化，崩溃后凭日志恢复
  • 每个经验候选必须带独立证据链、适用范围与反例
  • 新资产一律走 shadow + canary，按评分差值显著性晋级
  • 熔断指标与回滚动作在发布前就配置好，而非出事后现补
  • 别把会话日志不加筛选地直接写进长期记忆
  • 别因为一次成功就把局部做法升级为全局规则
  • 别只用错误率和延迟做熔断——坏 Agent 返回的是 200
  • 别在离线评测达标后直接切换 100% 流量
  • 别按请求随机分流——会话中途换模型会污染实验

验收进化能力只需要回答一个问题：系统今天处理没见过的任务，是否比六个月前更好——而且你能拿出完整证据链。

Q&A

为什么系统不会因为执行次数增多而自然进化？到底缺了哪些环节？
因为执行本身只产生日志，不产生能力。从日志到能力中间隔着四个工程环节：提取（跨轨迹识别稳定模式）、验证（证据链 + 反例 + 可重跑的验证方法 + 统计判定）、固化（分流进 Memory/Skill/Workflow 并版本化）、受控发布（四级门禁加熔断）。缺了提取，日志只是数据囤积；缺了验证，偶发事件会污染长期记忆；缺了发布，改进无法安全进入生产；缺了回滚，每次进化都是单向门。只有四个环节全部在线，"执行次数"才能转化为"系统能力"，否则系统跑一年也只是把同样的错误重复了一万遍。
自主规划和自主进化的本质区别是什么？
两者的决策对象与时间尺度完全不同。自主规划回答"当前任务的下一步动作是什么"，运行在任务内循环，输出是动作序列，会话结束即消失，失败只损失一次任务。自主进化回答"哪些改进可以进入系统的下一个版本"，运行在版本间的外循环，输出是持久化的 Memory/Skill/Workflow 资产，失败会污染所有后续任务。一个形象的类比：规划是员工在当天的工作决策，进化是组织把经验写进操作手册——前者每天都在发生，后者需要评审与发布流程。两者必须分开建设，用规划系统做进化会让未验证的经验直接生效，用进化的重流程做规划则会让每次决策都慢得不可用。
经验提取为什么要做统计判定？只看"出现次数"不行吗？
出现次数只是直觉，无法排除抽样噪声。工程上要过三道关：一是频次与共现关，候选模式必须在至少 2 条相互独立的轨迹中出现，且与失败结果的共现率显著高于基线（同一任务的三次重试不算独立证据）；二是样本量关，"加入经验后成功率提升"的结论必须在冻结留出集上对照测量，每臂至少约 50 个数据点才谈得上判断；三是显著性关，晋级判据是候选对锁定基线的评分差值通过显著性检验（如 Mann-Whitney U 检验，p 值小于 0.05），而不是看绝对分数，因为在线评分本身是有噪声的抽样，且基线必须锁定，不能是随时漂移的活数据。
Checkpoint 和 Durable Execution 是一回事吗？事件日志和幂等 Key 怎么配合？
不是。Checkpoint 像游戏存档，能保存状态让你从某点继续，但它不保证外部副作用不会重复——如果在"邮件已发出、状态还没写回"的窗口崩溃，光有检查点的调度器会从头重跑，客户收到两封邮件。完整的 Durable Execution 有三支柱：事件溯源（每次状态迁移写成只追加事件，执行历史是唯一事实源）、确定性重放（恢复时新进程从头跑代码，但外部调用从日志取结果而不真正执行）、幂等性（写操作携带任务 ID + 步骤 + 参数哈希派生的 Key，重复请求被下游去重成 no-op）。典型组合是：事件日志作为权威账本，定期 Checkpoint 作为恢复加速点，幂等 Key 覆盖两者之间可能重放的区间。
经验存进 Memory 就够了，为什么还要分 Memory/Skill/Workflow 三种资产？
因为三类经验在下次任务中扮演的角色不同，混存会让每类都发挥不好。稳定事实（如"本仓库回归命令是 make reg-all"）是背景知识，适合放 Memory，按需注入上下文，过时即覆盖；可复用方法（如"超时排查三步法"）是可选工具，适合做成 Skill，带输入输出接口和版本号，按语义检索调用；强制步骤（如"合并前必须跑仓库级回归"）是纪律，必须做成 Workflow 由编排层强制执行，不能依赖模型自觉。如果全部塞进 Memory，事实会与方法混在一起导致检索噪声，强制步骤也会退化为"模型看心情遵守的建议"。分流的判据只有一句话：这条经验下次是当背景、当工具还是当纪律。
影子运行和灰度发布回答的问题有何不同？可以省略其中一个吗？
两者产生的是不同信号，不是同一信号的不同风险档位。Shadow 把真实请求镜像一份给候选版本，输出只记录不返回用户，用户风险为零，回答"候选在真实流量分布上行为合理吗"——但它永远给不出用户结果信号，因为没人真的看到输出。Canary 把 1%~20% 的真实流量交给候选服务，回答"在真实用户面前它至少不差于旧版吗"，是唯一能买到真实用户结果的层级。跳过 Shadow，等于让候选第一次接触真实分布就直面用户，质量回归直接变成事故；跳过 Canary，则永远停留在离线与镜像信号上，而离线分数与真实用户表现之间隔着分布差异这条沟。两者都不可省。
熔断机制应该监控哪些指标？为什么错误率和延迟不够？
至少四项：任务成功率（对比基线低于约 3 个百分点且持续即熔断）、单位任务成本（高于基线约 20% 熔断，防止进化带来费用失控）、风险动作次数（越权写操作、资金类动作出现一次即熔断，零容忍）、执行时长 P95（高于基线约 50% 熔断，P95 恶化常是死循环的前兆）。错误率和延迟不够的根本原因是：Agent 的质量回归通常不表现为报错，而是按时返回 HTTP 200 加一个流畅但错误的答案，传统金丝雀控制器认识的所有信号对此全部失明。因此还需要在 1%~10% 的采样流量上跑在线质量评分（LLM-as-judge，先校准到与人工判断相关 ≥0.80），把评分本身作为熔断与晋级信号。
小团队想落地六阶段闭环，第一步应该做什么？
先闭合最小回路，而不是一次建完五个维度。具体做法：挑一个高频且模式清晰的失败（例如某类反复出现的漏跑回归），人工整理出它的证据链，写成五要素齐全的经验候选，固化为一个带版本号与输入输出接口的 Skill；然后搭最简的两级门禁——先在冻结评测集上确认无回归，再用影子流量对比新旧版本的质量评分，达标后放 5% 灰度并配好成功率与风险动作两项熔断。这一个闭环跑通，团队就同时拥有了状态持久化、经验提取、资产管理和受控发布的最小工具链，之后再逐个把其他失败模式纳入、把 Shadow/Canary 做精。反过来，一上来就想建全量经验库和完整发布平台的团队，通常会在第一个月因为看不到闭环收益而放弃。
