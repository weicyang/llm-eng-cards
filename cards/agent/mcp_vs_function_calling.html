A25 · Function Calling 与 MCP 的关系

Function Calling 概念 → 协议细节 → 代码实现 → 与 MCP 的作用环节对比 → 同一链路共存

一个管"嘴"，一个管"手"：Function Calling 教模型如何"点菜"，MCP 教 Host 如何"上菜"。两者作用在同一条链路的不同环节，所以谁也替代不了谁。

一、Function Calling：被名字误导的概念

Function Calling（函数调用）是 AI 领域最容易被望文生义的概念之一。看名字像是"模型去调用函数"，但真相是：模型从头到尾没有执行过任何函数，它只是告诉调用方"我想调用某个函数，参数是这些"。

Function Calling 这个名字是 AI 圈最大的"虚假宣传"——模型从来没有"Calling"过任何东西，它只是说了一句"我想调这个"。

1.1 两种视角：模型 vs 模型 API

视角定义关注点
模型模型能从候选工具列表中选择工具、提取参数、解析结果训练能力（模型是否具备这种智能）
模型 APIAPI 能传递工具列表、返回选择结果接口规范（大部分人实际关注的是这一层）

由于绝大多数场景对接的是模型 API 而非模型本体，所以我们默认讨论的 Function Calling 指的是 API 层的协议规范：工具怎么传进去、选择结果怎么返回来、执行结果怎么送回去。

1.2 Function Calling 作用在链路的哪一段

┌──────┐ ┌───────────────────┐ ┌───────────┐ │ 用户 │ ─────→ │ Host │ ─────→ │ 模型 API │ └──────┘ │ (Mark Chat/Cline) │ ←───── │ (GPT-4o) │ └────────┬──────────┘ └───────────┘ │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ 本地函数 │ │ HTTP API │ │MCP Server│ └──────────┘ └──────────┘ └──────────┘ ◀──── Function Calling 管这一段 ────▶ （Host ↔ 模型 API 双向约定） ◀──── 工具具体怎么执行，FC 不管 ────▶ （本地调用 / HTTP / MCP 都可以）
关键认知：Function Calling 只约束"Host ↔ 模型 API"这一段——工具列表怎么下发、选择结果怎么上行、执行结果怎么回传。至于 Host 内部到底怎么执行这个函数（本地调用、发 HTTP 请求、还是走 MCP 协议），Function Calling 完全不关心，也管不着。

模型只有"建议权"：它可以建议"调用 search"，但调不调、怎么调、谁来调，全是 Host 说了算。

二、协议细节：tools 下行，tool_calls 上行

Function Calling 的完整协议其实就三个动作：请求时带上菜单（tools）、返回时给出点菜单（tool_calls）、第二次请求时上菜（role:"tool"）。

下行是菜单，上行是点菜单，二次请求是上菜——一顿饭三个动作，协议的全部就是这三个动作。

2.1 第一次请求：下发工具列表

{
  "model": "gpt-4o",
  "messages": [{"role": "user", "content": "纽约明天的天气怎么样？"}],
  "tools": [{"type": "function", "function": {
    "name": "search", "description": "搜索网络获取信息",
    "parameters": {"type": "object", "properties": {
      "query": {"type": "string", "description": "搜索内容"}},
      "required": ["query"]}}}],
  "stream": false
}

其中 parameters 字段遵循 JSON Schema（一种描述 JSON 结构的标准规范）：它告诉模型这个工具有一个 query 参数、字符串类型、必填。模型据此生成参数，而不是自由发挥。

2.2 第一次返回：模型给出点菜单

{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "function": {"name": "search",
                     "arguments": "{\"query\": \"纽约明天天气\"}"}
      }]}]
}

2.3 第二次请求：回传工具执行结果

{"messages": [
  {"role": "user", "content": "纽约明天的天气怎么样？"},
  {"role": "assistant", "tool_calls": [...]},
  {"role": "tool", "content": "...搜索结果..."}
]}

2.4 协议核心字段速查

字段方向含义易错点
tools请求下行工具列表，每个工具含 name/description/parameters工具越多，token 消耗越大
parameterstools 内部JSON Schema，约束参数类型与必填项描述写得含糊，模型填参就不准
tool_calls返回上行模型选择的工具 + arguments可能一次返回多个 tool_calls
argumentstool_calls 内部JSON 字符串，需 json.loads 解析不是对象！还可能是非法 JSON
role:"tool"第二次请求携带工具执行结果回传给模型必须与 tool_calls 一一对应

arguments 是字符串而不是对象——这是新手踩的第一个坑：拿到 tool_calls 后必须先 json.loads(arguments) 才能得到真正的参数。

三、五步核心流程：模型调用两次，工具执行一次

用户："纽约明天天气怎么样？" │ ▼ ┌───────────────────────────────────────────────┐ │ ① Host 调用模型 API（用户问题 + tools 列表） │ └─────────────────────┬─────────────────────────┘ ▼ ┌───────────────────────────────────────────────┐ │ ② 模型返回 tool_calls：search(query="纽约天气")│ └─────────────────────┬─────────────────────────┘ ▼ ┌───────────────────────────────────────────────┐ │ ③ Host 执行工具（模型完全不参与） │ └─────────────────────┬─────────────────────────┘ ▼ ┌───────────────────────────────────────────────┐ │ ④ Host 再次调用模型 API（附 role:"tool" 结果）│ └─────────────────────┬─────────────────────────┘ ▼ ┌───────────────────────────────────────────────┐ │ ⑤ 模型总结工具结果，输出最终答案 │ └───────────────────────────────────────────────┘

Function Calling 的本质是"先想、再做、后总结"——模型被调用两次（选工具一次、总结一次），工具执行一次，Host 全程跑腿。

3.1 与代码的对应关系（process_user_query）

步骤操作关键变量
①将用户问题加入 history，调用 call_modelself.history, first_model_response
②从返回中提取 tool_calls（工具名 + 参数）message.tool_calls
③调用 execute_tool 执行工具tool_result
④将工具结果加入 history，再次调用模型call_model_after_tool_execution
⑤提取最终答案并返回final_message

3.2 生产案例：arguments 解析攻防战

背景：某内部客服机器人接入了 12 个 Function Calling 工具，日均处理 8000+ 次调用。
问题：模型偶尔在 arguments 中输出非法 JSON（尾逗号、未转义引号），失败率 2.7%，相当于每天约 200 个用户请求直接报错，日志里全是 JSONDecodeError。
方案：三层兜底——先按 JSON Schema 校验参数完整性；json.loads 失败时降级为宽松解析（json5）；仍失败则把错误信息回传给模型让它重新填参并自动重试一次。
效果：工具调用失败率从 2.7% 降到 0.2%，首次调用成功率从 97.3% 提升到 99.8%，客服侧工具相关投诉归零。

四、执行权在谁手里：模型点菜，Host 做菜

理解 Function Calling 的关键，是理解三个角色的分工：

角色身份职责执行函数？
模型GPT-4o、Claude 等选择工具、提取参数、总结结果否，只负责"点菜"
HostMark Chat、Cline、Cursor解析 tool_calls、执行工具、回传结果给模型是，真正的"厨师"
工具本地函数 / HTTP API / MCP Server提供能力，返回数据被 Host 执行

Host（宿主程序）就是那个面向用户、编排全局的应用程序——它一边对接模型，一边对接工具。模型给出的 tool_calls 只是一个"请求"，Host 可以执行它、拒绝它、也可以修改参数后再执行。

执行权始终在 Host 手里，这是整个 AI 工具链安全性的根基：模型可能幻觉出不存在的工具、可能填出危险参数——Host 必须校验后再执行，绝不能当"传声筒"。这也解释了为什么模型对工具的执行方式"毫不知情"：执行细节完全被 Host 屏蔽了。

模型只有建议权，Host 才有执行权。谁掌握执行权，谁就掌握安全——这是"聊天机器人"和"Agent"的分界线。

五、MCP 与 Function Calling：互补，不是替代

有了前四节铺垫，两者的关系已经呼之欲出：Function Calling 管"Host ↔ 模型 API"段，MCP 管"Host ↔ Server"段。两段路，两套协议，各干各的活。

┌────────────────────────────────────────────────────┐ │ Host（Mark Chat） │ │ │ │ ┌──────────────┐ ┌────────────────────┐ │ │ │ 模型调用模块 │ │ 工具执行模块 │ │ │ │ call_model() │ │ execute_tool() │ │ │ └──────┬───────┘ └─────────┬──────────┘ │ └─────────┼────────────────────────────┼────────────┘ │ │ Function Calling MCP （tools 下行 / tool_calls 上行） （tools/list · tools/call） │ │ ▼ ▼ ┌───────────────┐ ┌───────────────────┐ │ 模型 API │ │ MCP Server │ │ （GPT-4o 等） │ │ （天气/搜索/数据库）│ └───────────────┘ └───────────────────┘

5.1 六个维度的对比

维度Function CallingMCP
协议段Host ↔ 模型 APIHost ↔ MCP Server
规定内容工具列表格式、选择结果格式、结果回传工具发现（tools/list）、工具调用（tools/call）
与模型关系直接相关，依赖模型的训练能力无直接关系，模型甚至不知道 MCP 存在
执行函数？否（只请求调用）是（Host 通过它实际调用 Server）
典型传输HTTPS（模型 API）STDIO / HTTP+SSE
关系互补，不是替代——可在同一链路中共存
核心结论：Function Calling 规定模型如何请求调用工具，MCP 规定 Host 如何实际调用工具，两者完全不重叠。一个完整的 Agent 链路可以（而且通常确实）同时使用两者——模型通过 Function Calling 选工具，Host 通过 MCP 调工具。

5.2 同一链路共存：Mark Chat 改造实录

做法非常简单：Function Calling 协议部分一行不动，只把 execute_tool 的内部实现换成 MCP 调用：

def execute_tool(self, tool_name, arguments):
    # 原来：直接调本地函数 / HTTP 接口
    # 现在：统一走 MCP Client
    result = self.mcp_client.call_tool(
        tool_name, json.loads(arguments))
    return result.content
背景：Mark Chat 早期把 15 个工具全部硬编码在 execute_tool 里，一个工具一个 if-else 分支。
问题：每加一个工具都要改 Host 代码并重新部署，单个工具接入要半天；同一份工具代码在 3 个项目里复制粘贴，改一个 bug 要同步三处。
方案：把工具层改造为 MCP Client（Host 内部负责连接 MCP Server 的组件），工具实现为独立的 MCP Server，Function Calling 协议部分保持不变。
效果：新工具接入从半天缩短到 10 分钟（写好 Server + 配置一行）；3 个项目共用同一套 Server；工具相关 bug 减少 60%。

FC 是 Host 与模型之间的翻译官，MCP 是 Host 与工具之间的翻译官。两个翻译官说的是不同的语言，上的不同的班，互不抢活。

六、选型实践：什么场景用什么组合

场景推荐方案理由
自建聊天机器人，2-3 个简单工具只用 Function Calling链路最轻，不必引入额外协议
工具多、需要跨项目复用FC + MCP工具写一次，多个 Host 都能用
想用社区现成工具生态FC + MCP直接接入生态里的 MCP Server，零开发
模型不支持 FC提示词工程 + MCP让模型输出 XML/JSON，Host 解析后调 MCP
第四行正是 Cline 的做法（见 A24 抓包分析）：模型不走 Function Calling 协议，而是在回复中输出 XML 格式的工具调用标签，Host 解析后再调用 MCP Server。这说明 MCP 并不依赖 Function Calling——只要 Host 能解析出模型的"意图"，就能接上 MCP。
  • 把 Function Calling 当"模型侧协议"、MCP 当"工具侧协议"来分段理解
  • 工具层封装成 MCP Server，隔离模型协议变更带来的影响
  • 执行前校验 arguments（json.loads + Schema 校验）
  • 换模型时只适配 FC 格式，工具层一行不动
  • 不要问"FC 和 MCP 哪个更好"——它们不是替代关系
  • 不要把工具硬编码在 Host 里，否则每加一个都要改代码重部署
  • 不要信任模型输出的 JSON，非法 arguments 在生产中必然出现
  • 不要把所有工具都塞给模型，工具列表本身也消耗 token

别追新概念，看链路。链路只有两段：模型段和工具段，各有一套协议——看清了段，任何新概念都能秒懂。

Q&A

Function Calling 和 MCP 是什么关系？为什么不是替代关系？
两者是互补关系，作用在链路的不同环节：①Function Calling 作用于 Host ↔ 模型 API 环节，规定工具列表如何传给模型、模型如何返回选择结果、工具执行结果如何返回给模型；②MCP 作用于 Host ↔ Server 环节，规定 Host 如何发现和调用外部工具。两者完全不重叠：Function Calling 管"模型怎么选工具"，MCP 管"Host 怎么调工具"。它们可以在同一个链路中同时使用——模型通过 Function Calling 选择工具，Host 通过 MCP 调用工具。
Function Calling 协议的请求和返回格式是什么？
请求包含 4 个核心字段：model（模型名）、messages（历史消息列表）、tools（工具列表，每个工具包含 name/description/parameters，其中 parameters 遵循 JSON Schema 规范）、stream（是否流式）。返回中的关键部分是 tool_calls，包含模型选择的工具名和 arguments（JSON 字符串格式的参数）。注意：模型只是请求调用，不是真正执行。第二次请求时将工具结果以 role:"tool" 消息加入 messages，模型据此给出最终答案。
Function Calling 的 5 步核心流程是什么？
①调用模型 API：将用户问题 + 工具列表发给模型；②提取工具选择：从模型返回的 tool_calls 中提取工具名和参数；③执行工具：调用 execute_tool 获取结果；④再次调用模型 API：将工具执行结果加入 messages 重新请求模型；⑤返回最终答案：模型根据工具结果总结答案。这个流程中，模型调用两次 API：第一次选择工具，第二次根据工具结果给出答案。中间的工具执行由 Host 完成，模型不参与。
为什么 arguments 是 JSON 字符串而不是直接的对象？
主要有两个原因：①模型的输出本质是文本流，tool_calls 是从生成的文本中解析出来的，保持字符串形式最贴合生成机制，也方便流式输出（stream 模式下 arguments 可以逐字增量返回）；②字符串的协议兼容性更好——不同模型的参数结构可能有细微差异，留给 Host 自行解析更灵活。代价是 Host 必须多做一次 json.loads(arguments)，而且要做好解析失败的预案：模型偶尔会输出非法 JSON（尾逗号、漏引号），生产环境必须做宽松解析或重试兜底。
模型不支持 Function Calling 怎么办？还能用 MCP 吗？
能，两者是独立的事。Function Calling 是模型 API 的能力，MCP 是 Host 的能力——模型甚至不知道 MCP 的存在。模型不支持 FC 时，常见做法是提示词工程：把工具列表和调用格式写进系统提示词（如 Cline 的 XML 标签），让模型按约定文本输出调用意图，Host 解析后再执行工具；工具层依然可以走 MCP。这也正是 Cline 能用各种模型接 MCP Server 的原因："模型侧协议"可以自定义，"工具侧协议"用 MCP 统一就行。
如何让 Function Calling 和 MCP 在同一链路中共存？
修改 execute_tool 函数的实现即可。原来的 execute_tool 可能直接调用 HTTP 接口或 SDK，改为内部启动一个 MCP Client，通过 MCP 协议连接 MCP Server 来获取工具执行结果。这样：①模型仍然通过 Function Calling 协议选择工具和提取参数；②Host 在 execute_tool 中通过 MCP 协议实际调用工具；③工具结果按照 Function Calling 协议格式返回给模型。两个协议各司其职，互不干扰。这种架构使工具调用标准化（MCP），同时保持与模型交互的灵活性（Function Calling）。
既然 MCP 已经标准化工具调用了，为什么还需要 Function Calling？
因为 MCP 解决不了"模型怎么决定调哪个工具"的问题。MCP 标准化的是 Host 与 Server 之间的工具发现和调用，但模型仍然需要一种方式知道"有哪些工具可用、每个工具要什么参数"，并表达"我想调哪个"——这正是 Function Calling 干的事。即使接了 MCP，Host 也要先从 MCP Server 拉取工具列表，转换成 tools 格式，再通过 Function Calling（或等效的提示词协议）传给模型。换句话说，MCP 统一了"手脚"，FC 统一了"嘴"，一个完整的 Agent 两样都少不了。
