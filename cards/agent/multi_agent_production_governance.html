A48 · 多 Agent 生产治理

通信模式与协议选型 / 状态同步与断点恢复 / 任务优先级与负载均衡 / 可观测与迭代优化闭环

单个 Agent 的智能决定系统上限，而治理基础设施决定它能否活着进入生产——通信可靠、状态可恢复、资源可隔离、行为可观测，缺任何一环，多 Agent 系统都会在生产环境里以指数速度崩塌。

一、治理全景：可靠性不会自动变强

把一个任务交给多个 Agent 协作，直觉上"人多力量大"，但生产数据给出的答案恰恰相反。2026 年的行业统计显示，AI Agent 在真实计算机操作任务上的单步成功率约为 66%（2024 年初这个数字只有 12%），而约 89% 的企业级 Agent 项目从未真正进入生产，单个项目的沉没成本在 15 万到 80 万美元之间。瓶颈几乎不在模型本身，而在协调（coordination）——Agent 之间如何传递任务、共享状态、分摊资源、互相校验。

这里说的治理，指的就是围绕多 Agent 系统搭建的一整套工程基础设施，业界一般称之为 编排（Orchestration）——即对多个 Agent 的规划、分发、状态管理、容错与质量运维进行统一控制的中间层。它通常由四个相互咬合的域构成：通信（消息怎么可靠送达）、状态（进度怎么不丢不错）、调度（任务给谁、什么时候给）、观测（系统到底在干什么、干得怎么样）。

1.1 可靠性的乘法衰减

多步协作最反直觉的一点是：端到端可靠性不是各环节的平均值，而是各环节成功率的乘积。一个三步任务链，若每步成功率 70%，端到端成功率只有 0.7³ ≈ 34%；加到四步就跌破 24%。这就是为什么生产环境中的多步 Agent 系统失败率普遍落在 70%~95% 区间——不是模型太笨，而是误差在链条上复利累积。同时，多 Agent 运行的 Token 消耗可达单 Agent 的 15 倍（Anthropic 多智能体研究系统的实测数据），只有当每个环节都可靠时，这笔溢价才花得值。

生产观察 · 可靠性乘法：某调研汇总了多起企业级 Agent 落地数据：单步成功率 66% 听起来不错，但三步链的端到端成功率只剩 34%，四步链低于 24%。对应的行业后果是：约 89% 的企业 Agent 从未上线，Gartner 预测到 2027 年底将有超过 40% 的 agentic AI 项目因成本失控、价值不清和风险管控薄弱而被取消。结论：提升多 Agent 系统价值的杠杆不在"更强的模型"，而在缩短链条、加入校验层、让每一步可重试可恢复。

多 Agent 系统的可靠性是乘法不是加法：每多一个协作环节，就多乘一个小于 1 的系数。治理的全部工作，就是把这些系数一个个推向 1。

二、通信模式：三种经典拓扑的取舍

Agent 之间的协作拓扑，决定了消息怎么走、故障往哪扩散、系统好不好调试。生产中最常见的有三种模式：主从模式、对等协商模式、层级委托模式。它们不是先进与落后的关系，而是控制力、扩展性、调试难度三个旋钮上的不同档位。

2.1 主从模式：控制力最强，代价是单点

一个"大脑"级别的主控 Agent 统一接收任务、拆解并分发给执行 Agent，所有结果再汇聚回主控。它的优点是逻辑清晰、权限集中、易于监控和审计——这也是它成为默认起手式的原因。缺点是主控是天然的单点故障：主控一挂，整个系统瘫痪。生产上的补救手段是给主控做主备切换（见第四节的检查点机制），或者把主控做成无状态节点、把任务队列外置，让任何一个副本都能接管。

2.2 对等协商模式：解耦最彻底，行为最难预测

各 Agent 地位平等，通过共享的 消息总线——即发布/订阅中间件，发送方只管发、不关心谁消费——实现彻底解耦。新 Agent 随时加入而不影响现有模块，扩展性最好。代价是系统行为变得难以预测和调试：没有人拥有全局视角，订阅关系错配或某个 Agent 疯狂发消息，就可能引发 消息风暴（消息量指数级放大、队列堆积、全体 Agent 互相拖累）。对等模式必须配套流量配额、死信兜底和全链路追踪，否则出问题时无从下手。

2.3 层级委托模式：为复杂任务而生的树状结构

当任务复杂度高到一个"大脑"装不下时，采用树状分层：顶层战略规划 Agent 把宏观目标拆解后委托给中层，中层继续细分下放给底层执行 Agent，结果逐级向上汇报。同层之间通常不直接通信，而是通过共同上级协调。好处是分工明确、天然支持任务并行，且每一层的上下文负担都更小；挑战在于层级间传递有累积延迟，且上层的决策质量会直接污染下层——顶层拆错一个子任务，整条子树都在做无用功。2026 年流行的"协调者 + 专业子 Agent"编排（规划、研究、编码、评审各司其职）本质上就是两到三层的层级委托。

三、协议选型：分层组合，没有银弹

拓扑决定消息怎么走，协议决定消息长什么样。评估一个通信协议，生产上通常看六个维度：性能（延迟与吞吐）、可靠性（丢失率与顺序保证）、可扩展性、易用性、安全性、生态成熟度。结论先行：没有任何单一协议能同时满足所有场景，成熟系统都是分层组合——不同层用各自最合适的协议。

3.2 Agent 原生协议：MCP 管工具，A2A 管协作

2024 年底开始，一批为 Agent 而生的协议快速成熟，其中最重要的是 MCP 与 A2A，它们解决的是两个正交的问题：

  • MCP（Model Context Protocol）：Anthropic 于 2024 年 11 月发布，2025 年 12 月捐赠给 Linux 基金会。它标准化的是 Agent 与工具/数据源的"纵向"连接——工具能力如何描述、参数如何传入、结果如何返回。生态数据：公开 MCP 服务器超过 1 万个，Python/TypeScript SDK 月下载量约 9700 万次。2026 年 7 月的规范修订还把协议核心改为无状态，请求可以落在负载均衡后的任意实例上，对生产部署非常友好。
  • A2A（Agent-to-Agent Protocol）：Google 于 2025 年发起，2026 年 3 月发布 v1.0，已有 150+ 组织在生产使用。它标准化的是 Agent 与 Agent 的"横向"协作：通过 Agent Card——部署在约定 URL 的能力自描述文件——实现互相发现，然后进行任务委派、多轮协商与上下文交换。传输层支持 JSON-RPC/HTTP、SSE、gRPC 与 webhook，长任务有完整的有状态生命周期。
  • ACP / ANP：前者是 REST 风格的企业内 Agent 消息层，后者面向跨组织的开放 Agent 网络，生态成熟度目前低于前两者，选型时建议观望或作为二期规划。

标准化的价值用一道算术题最直观：10 个 Agent 加 20 个工具，若每对组合都写定制集成，需要 200 条适配代码；改为"每个 Agent 实现一次协议客户端、每个工具实现一次协议服务端"，只需 30 个实现。Agent 数量越多，协议的复利越明显。

MCP 像 USB——把 Agent 接到工具上；A2A 像以太网——把 Agent 接到别的 Agent 上。两种线都要买，混用才是错误。

四、状态同步：结构化、版本化与可恢复

多 Agent 系统里，状态是比消息更脆弱的东西：几十个 Agent 并发上报进度，消息会乱序、节点会宕机、流程会中断。生产级状态同步的设计可以拆成四层：结构化状态模型 → 可靠异步传输 → 检查点恢复 → 上报压力优化。

4.1 结构化状态模型 + 版本号

状态数据必须结构化，至少包含任务 ID、执行 Agent、阶段、进度、时间戳，以及最容易被忽略的 版本号。异步网络中消息乱序是常态而非异常：第 5 步的"已完成"可能比第 4 步的"进行中"先到。没有版本号，接收方只能用"最后到达者赢"的朴素策略，状态就会被过期消息反复污染。正确做法是每条状态携带单调递增的版本号，接收端只接受版本号更大的更新，旧消息直接丢弃——这就是分布式系统里经典的"拒绝陈旧写入"。

4.2 可靠传输：ACK、心跳与死信队列

传输层用异步消息队列，配套三件套：

  • ACK 确认机制：消费方处理成功后显式回执，未收到 ACK 的消息由队列重投，防止消息丢失；
  • 心跳包：主控定期检查各 Agent 心跳，连续三次未收到即判定宕机并剔除，避免把新任务派给失效节点，同时触发该节点未完成任务的重新分配；
  • 队列本身要高可用：集群部署、开启持久化、主节点故障可快速切换；配置合理的重试次数，重试耗尽的失败消息进入 死信队列（DLQ）留待人工排查，而不是无限重试放大故障。

4.3 检查点：把"崩溃重跑"变成"断点续跑"

对长流程多 Agent 任务，仅有消息级可靠还不够——进程本身也会挂。检查点（Checkpoint）机制在每个执行步骤完成后，把当前完整状态（任务上下文、各 Agent 产出、待执行队列）连同唯一线程 ID 和版本哈希序列化到持久存储。崩溃后系统重启，按线程 ID 找回最近的检查点，从断点继续而不是从零开始。注意恢复语义的细节：恢复通常是"重放崩溃的那个节点"而非"从下一行代码继续"，因此被重放的步骤必须保证幂等（重复执行不产生重复副作用），比如写库前先查重、调用外部接口带唯一请求号。

生产案例 · 没有检查点的代价：一个文献综述 Agent 执行 30 步的长任务，在第 25 步调用模型时遭遇服务 502 错误。由于状态只存在于内存，进程崩溃后前 24 步的 Token 费用和时间投入全部作废，只能从头重跑——同类长任务的有效成本被放大了数倍。引入数据库后端的检查点机制后（每步完成即持久化快照），同样的崩溃只需重放第 25 步，恢复时间从"重新排队跑完全程（小时级）"降到约 2 分钟，长任务的综合成本下降超过 80%。这也是行业共识："约八成 Agent 项目失败，不是模型不够强，而是状态管理从第一天就走错了路。"

4.4 上报压力优化：合并与抽样

当 Agent 数量达到成百上千，高频状态上报本身会成为系统瓶颈。两个标准手段：一是合并上报，把多个子任务的状态打包成一条消息批量发送，摊薄网络与序列化开销；二是抽样上报，对进度类高频信号（如百分比推进）按比例抽样，只保证关键节点（开始、失败、完成）全量上报。配合使用，可在不损失关键信息的前提下把上报流量压到原来的十分之一量级。

五、优先级与负载均衡：选"最合适的"

消息能可靠送达、状态能断点恢复之后，下一个问题是：任务该给谁、什么时候给。朴素的轮询在生产中几乎必然失效——它看不见任务轻重的差异，也看不见各 Agent 忙闲的差异。生产级调度由两部分组成：任务侧的优先级管理与 Agent 侧的负载均衡。

5.1 优先级：三维打分而非单一队列

"用一个优先级队列"只是答案的开头，真正的问题是分数从哪来。可行的做法是建立三维评估模型：

维度含义打分示例
业务重要性该任务对核心业务的影响权重核心交易链路 9~10 分，内部报表 2~3 分
时间敏感性有无截止时限、超时是否作废实时客服 10 分，夜间批处理 1 分
资源消耗预计占用算力 / Token / 时长重消耗任务适当降权，避免长期霸占

综合分 = 加权求和后入队排序。更关键的是动态调整：当系统负载越过阈值（例如整体 CPU 持续高于 80%、队列积压超限时），调度器自动下调非核心任务的优先级甚至暂停派发，优先保住核心任务的执行带宽——这是"过载保护"，不是"任务丢弃"，被压制的任务留在队列里等待恢复。

5.2 负载均衡：画像、动态权重与约束匹配

负载均衡的进化路径是：轮询 → 加权 → 状态感知。生产做法分三步：

  • 任务分类与 Agent 画像：把任务按算力消耗、是否需 GPU、时延要求等特性分类；给每个 Agent 建立画像（硬件配置、擅长任务类型、历史成功率），让调度器"心中有数"；
  • 动态权重打分：Agent 的实时得分 = 基础能力分 × 当前负载系数（CPU 使用率、队列长度越低系数越高），任务优先派给得分最高者；
  • 约束匹配：先过滤出满足硬性要求的候选（如"需要 GPU"），再在候选中挑最空闲的，实现精准调度而非盲目撒网。
调度策略决策依据优点局限
轮询顺序实现极简、绝对公平完全无视忙闲与任务差异
最少连接活跃任务数比轮询更贴近真实负载不区分任务轻重
加权打分能力画像 + 实时负载兼顾能力与忙闲需要维护画像与权重调参
约束匹配 + 打分硬约束过滤后打分支持 GPU / 模型 / 地域等硬需求实现复杂度最高

5.3 韧性配套：舱壁、熔断与退避重试

调度之外，还需要三道防线防止"一个坏任务/坏节点拖垮全局"：

  • 舱壁模式（Bulkhead）：为特别耗资源的任务类型（典型如模型推理）单独分配线程池/进程池，像船舱隔板一样隔离资源，单类任务被打满也不影响其他任务；
  • 熔断器（Circuit Breaker）：持续监控各 Agent（及外部工具）的成功率，连续失败超过阈值即触发熔断，暂时停止向其派发新任务，经过一段冷却与试探后再半开放行。这能把故障节点的爆炸半径限制在它自身；
  • 指数退避重试：失败后每次等待时间翻倍并叠加随机抖动，避免所有失败者同一时刻重试形成二次洪峰；重试耗尽进死信队列。

最后一招是结果缓存：对重复出现的请求，把 Agent 执行结果缓存并设置过期时间，重复查询直接命中，既省钱又快，同时显著削减需要调度的任务总量。

生产案例 · 大促级联故障与健康感知调度：某电商客服 Agent 系统在促销日遭遇典型级联故障：09:00 流量激增 10 倍，09:15 库存查询工具响应从 200ms 恶化到 3s，09:30 由于工具调用顺序是硬编码的，Agent 仍按原顺序排队等待，超时率飙到 60%，09:45 订单工具因等不到库存数据被阻塞，10:00 系统雪崩、人工降级。复盘结论：调度必须"状态感知"。改造为健康感知的动态调度后（实时探测下游健康度、失败即熔断并切换备用路径），对 40+ 套类似系统的调研汇总显示：工具调用成功率从 65%~75% 提升到 85%~92%，平均任务完成时间从 8~15s 降到 3~6s，失败重试率从 35%~45% 降到 12%~18%，资源利用率从 40%~55% 提升到 70%~85%。

轮询回答的是"轮到谁了"，负载均衡回答的是"现在谁最合适"。前者是发牌，后者是调度——生产的每一次派发都应该是一次带约束的最优选择。

六、可观测与迭代优化闭环：把黑盒变成白盒

前四节解决的是"系统不崩"，这一节解决的是"系统持续变好"。多 Agent 系统的优化本质只有一句话：把不可预测的黑盒，变成可测量、可定位、可迭代的白盒。完整闭环是五步：全量记录 → 量化指标 → 定位瓶颈 → 实施优化 → A/B 验证。

6.1 为什么传统监控不够：指标全绿，答案是错的

传统应用监控测量的是延迟、错误率、CPU、状态码——这些指标对确定性系统足够，因为"行为错误"几乎总伴随"基础设施异常"。但 Agent 系统打破了这个假设：一个子 Agent 幻觉出一个不存在的市场数据，父 Agent 原封不动地传播给用户，此时链路上每个服务的延迟、吞吐、错误率全部正常，所有仪表盘都是绿的，只有答案是错的。所以多 Agent 可观测必须额外覆盖：回答质量（幻觉率）、工具调用成功率与失败模式、推理链的逻辑一致性、Token 成本与业务价值的比值。

生产案例 · 遥测盲区与推理循环：一项针对 Agent 遥测的研究给出了两个扎心的数字：① 仅使用通用分布式追踪标准（含其 GenAI 扩展）时，14 类典型 Agent 故障中只能检测到 6 类，故障检出率仅 42.9%——推理循环、护栏绕过、规划失败、记忆污染等 8 类故障完全不可见；② 在 112 个真实软件工程任务上的分析显示，约 75% 的 Agent 失败源于推理循环问题（反复打转、自我重复），而补齐规划、推理、委派、记忆等专用追踪维度后，检出率达到 100%，基于遥测的干预使修复率提升 8.3 个百分点。结论：可观测性不是锦上添花，它直接决定你能修什么。

6.2 记录什么：三支柱与全链路追踪

可观测性的底座是三支柱：分布式追踪（一次请求扇出为多次模型调用、工具调用、子 Agent 委派，用树状 span 保留因果链——"为什么调了这个工具"必须可回放）、指标（聚合视图与告警）、结构化日志（每条记录带 trace_id、agent_id、输入输出、Token 数与成本，保证可复现）。在此之上，核心指标体系按四类设定基线：

指标类别代表指标典型基线 / 阈值
质量任务成功率、幻觉率、工具调用成功率、重试率成功率 > 95%；重试率持续上升即预警
性能端到端延迟、首 Token 时间（TTFT）、推理链深度响应 < 10s；链深度异常加深 = Agent 在挣扎
成本每次执行的 Token 消耗（输入/输出分列）、按 Agent 归因给每个 Agent 设 Token 预算，超限告警
业务任务完成率、人工干预频率、用户反馈评分人工干预率上升是质量劣化的领先指标

6.3 三类高频优化动作

① 上下文管理：对话历史无限增长会撑爆上下文、推高成本、稀释注意力。对策是滑动窗口只保留最近若干轮，或用向量检索按需提取最相关的历史片段，把上下文从"全量"变成"按需"。

② 语义缓存：自然语言问法千变万化，基于哈希的精确匹配缓存在 LLM 流量上命中率通常不足 5%，而把查询转成向量、按相似度命中的 语义缓存能接住所有"换了个说法的同一个问题"。相似度阈值是核心旋钮：生产上常用 0.85~0.95，闭域问答（客服、政策查询）可放宽到 0.88~0.92，开放域助手则收紧；某高频重复问答场景实测阈值设到 0.94 时，命中即直返，既保证答案不会张冠李戴，又拦下了大部分重复推理。

生产案例 · 语义缓存的成本账：以日请求 10 万条的客服系统为例，不做缓存时每天向模型服务支付约 1450 美元（年约 53 万美元）。引入语义缓存后，典型 LLM 流量的命中率可达 40%~60%（对比哈希缓存 <5%）：按 50% 命中率计算，年支出从约 53 万美元降至约 26.5 万美元，年省约 26.4 万美元，而缓存基础设施（嵌入计算 + 向量索引，单次嵌入耗时仅 2~5ms）每月成本不足 500 美元。命中时响应还从秒级降到毫秒级——省钱与提速同时发生。

③ 工具容错：外部工具调用失败按指数退避重试（最多三次、间隔递增加抖动），连续多次失败触发熔断保护，防止一个坏工具把整条链路拖死——与第五节的调度防线是同一套思想，只是作用点从"Agent 节点"移到了"工具依赖"。

6.4 用 A/B 测试收尾，闭环才成立

每一项优化（换了上下文策略、加了缓存、调了提示词）都必须通过 A/B 测试验证真实效果：新旧版本分流并行运行，对比成功率、延迟、成本、人工干预率。没有验证环节的优化只是猜测；有了验证环节，"观测 → 定位 → 优化 → 验证"才构成可以持续转动的飞轮。

┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ ① 全量记录 │──▶│ ② 量化指标 │──▶│ ③ 定位瓶颈 │──▶│ ④ 实施优化 │ │ 追踪/日志 │ │ 质量/性能/ │ │ 哪个Agent? │ │ 上下文裁剪? │ │ 成本归因 │ │ 成本/业务 │ │ 哪类工具? │ │ 语义缓存? │ └────────────┘ └────────────┘ └─────┬──────┘ │ 熔断重试? │ ▲ │ └──────┬─────┘ │ ▼ ▼ │ ┌────────────────────────────┐ └───────────────────────────│ ⑤ A/B 验证 → 达标则全量上线 │ └────────────────────────────┘
  • 第一天就接入全链路追踪与结构化日志，给每条记录带 trace_id 与成本字段
  • 给每个 Agent 设定 Token 预算与成功率基线，超限自动告警
  • 长任务默认开启检查点；被重放的步骤保证幂等
  • 用版本号拒绝陈旧状态，用心跳三连缺失判定节点死亡
  • 语义缓存按业务域设阈值，上线后持续监控误命中率
  • 每项优化都走 A/B 验证再全量
  • 不要只看延迟和错误率就宣布系统健康——答案质量必须单独度量
  • 不要硬编码工具调用顺序和固定轮询派发，它们看不见运行时状态
  • 不要让失败无限重试，重试必须有退避、有上限、有死信出口
  • 不要把非核心任务和核心链路放进同一个资源池
  • 不要在没有指标基线之前做优化，那等于蒙眼调参
  • 不要期望单一协议通吃所有层

可观测性不是给系统装摄像头，而是给它装神经：你无法优化你看不见的东西，而多 Agent 系统里最贵的成本，永远花在你看不见的那部分。

Q&A

为什么多 Agent 系统的可靠性会随步骤数"乘法衰减"？工程上怎么破？
端到端成功率等于各步骤成功率的乘积：每步 70% 成功率，三步链只剩 0.7³≈34%，四步链跌破 24%，这就是生产环境多步 Agent 失败率高达 70%~95% 的数学根源。破解手段有四个方向：缩短链条（能一步做的不拆三步）；为关键步骤加独立校验层（由专门的评审者把关后再向下传播）；让每一步可重试、可断点恢复，把"整链重跑"降级为"单步重放"；以及用全链路追踪快速定位拉低乘积的那一步，集中火力优化它。
主从、对等协商、层级委托三种通信模式，分别什么时候选？
看三个变量：任务复杂度、扩展需求、团队的调试能力。任务类型固定、规模中小、需要强审计，选主从模式，代价是必须为主控做主备或无状态化改造以消除单点；系统事件驱动、模块频繁增删、需要彻底解耦，选对等协商 + 消息总线，但必须配套流量配额与全链路追踪来对冲消息风暴和调试困难；任务复杂度高、需要规划与分工（如研究报告、代码流水线），选层级委托的树状结构，接受层级间累积延迟和"上层决策污染下层"的风险。没有最优拓扑，只有与故障承受力匹配的拓扑。
MCP 和 A2A 的分工是什么？可以只用其中一个吗？
两者解决正交问题：MCP 标准化 Agent 与工具/数据源的纵向连接（工具能力描述、参数传入、结果返回），A2A 标准化 Agent 与 Agent 的横向协作（通过 Agent Card 互相发现、任务委派、多轮协商、共享任务状态）。工具是输入输出明确的原语，Agent 是会推理、维护状态的自主体，两类对端需要不同协议。只用一个通常不够：只上 MCP 解决了"Agent 会用工具"，但 Agent 之间的委派与协商仍要写定制集成；只上 A2A 则每个 Agent 接工具仍是烟囱式适配。成熟架构是分层组合：Agent 互操作走 A2A，Agent 接工具走 MCP，前端走 WebSocket，边缘走 MQTT。
状态同步中，版本号到底防的是什么？没有它会怎样？
防的是异步网络下的消息乱序。多条状态更新并发在途时，"第 5 步已完成"可能先于"第 4 步进行中"到达；若接收端采用"最后到达者赢"的朴素覆盖策略，迟到的旧消息会把新状态改回去，导致进度回退、已完成任务被重新派发等诡异现象。正确做法是每条状态携带单调递增版本号，接收端只接受版本号严格更大的更新，其余直接丢弃。同理，检查点恢复也依赖版本哈希来确认快照新旧。没有版本化的分布式状态，等于让所有节点拿过期记忆互相争辩。
任务优先级管理，只上一个优先级队列够吗？
不够，优先级队列只是数据结构，生产要回答的是三个衍生问题。第一，分数从哪来——用业务重要性、时间敏感性、资源消耗三个维度加权打分，而不是拍脑袋定 P0/P1。第二，负载变了怎么办——当整体 CPU 持续高于 80% 或队列积压超限时，自动下调非核心任务优先级，为核心任务保留执行带宽，这是过载保护而非丢弃。第三，重资源任务怎么隔离——用舱壁模式给模型推理这类任务单独分配线程池，防止单一任务类型占满全局资源。再配合指数退避重试和死信队列兜底失败任务，才构成完整的优先级治理。
重试、退避、熔断三者是什么关系？各自防什么？
三者是针对"失败"的递进防线。重试解决偶发抖动（网络闪断、瞬时超时）；指数退避是重试的纪律——每次等待翻倍并加随机抖动，避免大量失败者同一时刻重试形成二次洪峰，通常设上限如最多三次；熔断解决的是持续性故障——当某节点/工具连续失败超过阈值，说明重试也救不回来，此时直接停止派发新请求，冷却试探后再半开放行，把故障的爆炸半径限制在故障者自身。一句话：重试救抖动，退避防洪峰，熔断断传染。重试耗尽仍失败的消息进死信队列留证，而不是继续消耗系统。
多 Agent 系统的可观测性应该从哪些指标开始建？
按四类建基线，优先级从高到低：质量类（任务成功率、工具调用成功率、幻觉抽检率）——它回答"系统做对了吗"，是多 Agent 监控与传统监控最大的差异点，因为基础设施全绿时答案仍可能是错的；成本类（每次执行的 Token 消耗、按 Agent 归因、预算告警）——多 Agent 运行有约 15 倍的 Token 溢价，不归因就无法控费；性能类（端到端延迟、首 Token 时间、推理链深度）——链深度异常加深往往是 Agent 陷入循环的早期信号；业务类（人工干预频率、用户反馈）——人工干预率上升是质量劣化的领先指标。先有基线再谈优化，否则一切调参都是蒙眼。
语义缓存的相似度阈值应该怎么定？设高了或设低了会怎样？
阈值是命中率与准确率的交换旋钮。设得过低（如 0.8 以下），语义不同的问题会误命中，返回张冠李戴的答案，属于质量事故；设得过高（如 0.98），几乎只有原句复现才命中，缓存形同虚设，退回哈希缓存 <5% 的命中率。生产常用区间是 0.85~0.95，并按业务域细分：闭域问答（客服、FAQ、政策查询）答案空间窄、改述可预期，可用 0.88~0.92 换取更高命中；开放域助手问题发散、错答代价高，应收紧到 0.95 左右。上线后必须持续监控误命中率与命中率两个指标做微调，某些高频重复问答场景收紧到 0.94 附近常能取得较好平衡。
