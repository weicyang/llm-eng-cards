A07 · 工作流编排

Workflow Orchestration — LangGraph StateGraph、Checkpointer、条件路由、并行执行、Dify 可视化编排、错误处理、DAG 编排

工作流编排的本质：将复杂 AI 任务分解为有序的节点图——每个节点做一件事，边定义节点间的执行顺序和条件分支。类比流水线：原材料进入 → 加工 → 质检 → 包装 → 出厂，每一步都有明确的状态和转换规则。

一、工作流编排概述

Workflow vs Agent：Workflow 是预定义的确定性流程（检索→排序→生成），Agent 是 LLM 动态决策的自主循环（思考→行动→观察）。实际系统中两者经常混合——外层用 Workflow 编排主流程，内层某些节点是 Agent。

主流编排框架对比

框架核心概念适用场景特点
LangGraphStateGraph（有向图）复杂 Agent、多步工作流内置持久化、条件分支、循环
LlamaIndex Workflow事件驱动RAG 管线轻量、与 LlamaIndex 深度集成
Dify可视化画布低代码/无代码场景拖拽式编排，内置 RAG
Haystack Pipeline组件管道企业文档处理类型安全、企业级

Workflow vs Agent 选型

维度WorkflowAgent
流程预定义、确定性LLM 动态决策
可预测性高（同样输入 → 同样路径）低（LLM 每次可能不同）
灵活性低（需要预定义所有分支）高（适应未知场景）
调试容易（可视化执行路径）困难（动态决策链）
适用RAG 管线、ETL、审批流研究、探索、开放式任务
黄金法则：能用确定性代码的不用 LLM，能用 Workflow 的不用纯 Agent。混合使用是最佳实践——外层 Workflow 编排主流程，内层某些节点是 Agent（需要动态推理的环节）。

二、LangGraph StateGraph

LangGraph 的核心思想：把工作流建模为有向图。State 是全局状态（所有节点共享），Node 是处理步骤（函数），Edge 是节点间的连接。用 TypedDict 定义 State Schema 确保类型安全。

核心概念

概念说明类比
State图的全局状态（TypedDict 定义 schema）Redux store
Node一个处理步骤（函数），接收 State 返回更新字段微服务
Edge节点间的固定连接路由规则
Conditional Edge基于状态的条件路由（运行时决定下一个节点）if/else 分支
Reducer同一字段被多节点更新时的合并策略Git merge 策略
LangGraph StateGraph 执行流程: START → [Node A: 分类意图] │ Conditional Edge ┌─────┼──────┐ ▼ ▼ ▼ [Node B] [Node C] [Node D] (搜索) (代码) (对话) │ │ │ └─────┼──────┘ ▼ [Node E: 综合结果] │ ▼ END 关键特性: · State 在所有节点间共享（TypedDict 保证类型安全） · Node 只返回需要更新的字段（不需要返回完整 State） · Conditional Edge 用函数返回值选择下一个节点 · Reducer 控制并发更新同一字段的合并策略
Node 设计原则：每个节点"单一职责"——做好一件事。节点间通过 State 传递数据，不用全局变量。Node 函数接收完整 State，只返回需要更新的字段（增量更新），不需要返回完整 State。

三、Checkpointer 与状态持久化

Checkpointer 是生产级 Workflow 的必备——在每个节点执行后将完整 State 序列化存储。有了它才能断点续跑、时间旅行和人工审批。类比游戏的"自动存档"——随时可以从任意存档点重新开始。

三种核心能力

能力说明应用场景
断点续跑从最近的 checkpoint 恢复执行服务重启、网络中断
Time Travel回退到任意历史步骤，修改 State 后重新执行调试（Agent 第 5 步做错了 → 回退到第 4 步换路径）
Human-in-the-Loop在关键节点暂停，等待人工审批后继续敏感操作（部署、数据迁移）需人工确认

Time Travel 是 LangGraph 的杀手级功能：查看完整执行历史，回退到某一步，修改输入后用不同策略重新执行。这让复杂 Agent 的调试变得可行——不再需要从头开始复现问题。

Human-in-the-Loop 通过 interrupt() 函数实现：在关键节点前暂停图执行，将当前状态展示给人类，等待审批后注入人类决策结果继续执行。生产环境中，高风险操作（发邮件、部署、数据库写入）都应该走 HITL 审批。

三种能力看似不同，实际共用同一套机制：Checkpointer 每步落一份 State 快照，"续跑""回退""审批"只是从快照里恢复的三种不同姿势。

Checkpointer：一份快照，撑起三种能力 执行时的写入路径 ─────────────────────────────────────────────────────── START │ ▼ Node A ──► 返回增量字段 ──► 合并进 State │ │ │ ▼ │ 写 checkpoint #1 │ { thread_id, step: 1, state: {...} } ▼ Node B ──► 合并 ──► 写 checkpoint #2 │ ▼ Node C ──► 合并 ──► 写 checkpoint #3 │ ▼ END 存储：MemorySaver（开发） SQLite（单机生产） PostgreSQL（分布式生产） 三种恢复姿势 ─────────────────────────────────────────────────────── ① 断点续跑（进程挂了） 进程重启 ──► 按 thread_id 取最新 checkpoint #2 ──► 从 Node C 继续，前两步不重跑 场景：服务重启、网络中断 ② Time Travel（第 5 步做错了） 取 checkpoint #4 ──► 人工改写 State 里的字段 ──► 从第 5 步用不同策略重新执行 收益：调试不必从头复现，直接在出错点前一步下手 ③ Human-in-the-Loop（这一步不能自动做） Node C 前调用 interrupt() │ ├──► 写 checkpoint ＋ 挂起，进程可以完全退出 │ ├──► 把当前 State 展示给人 │ └──► 人给出决策 ──► 注入 State ──► 从 Node C 继续 场景：发邮件、部署、数据库写入 thread_id 隔离会话，step_number 定位时点 —— 多个会话并行跑同一张图，互不干扰。
Checkpointer 选型：开发用内存（MemorySaver），单机生产用 SQLite，分布式生产用 PostgreSQL。每个 checkpoint 关联 thread_id（会话标识）和 step_number（步骤编号），支持多会话并行。

四、条件路由与并行执行

条件路由让 LLM 成为"路由器"——根据用户意图动态选择不同的处理路径。并行执行通过 Fan-out/Fan-in 模式让多个独立节点同时运行，总延迟从 N×T 变为 max(T)。

条件路由

Conditional Edge 用函数返回值选择下一个节点——函数可以调用 LLM 做意图分类，根据分类结果路由到不同的处理节点。也可以组合多个条件：重试次数过多 → 放弃；质量评分好 → 结束；需要更多信息 → 继续检索。

并行执行模式

Fan-out / Fan-in 解决"分支数已知"的并行，Send API 解决"分支数运行时才知道"的并行，而无论走哪条路，多个分支写同一个 State 字段时都要靠 Reducer 决定怎么合并。

模式结构说明
Fan-out一个节点 → 多个并行节点同时搜索 Web/DB/Docs
Fan-in多个并行节点 → 一个汇总节点合并多源搜索结果
Send API运行时动态决定并行数量根据任务列表创建并行分支

Reducer 是并行结果合并的关键——用 Annotated[list, lambda a, b: a + b] 实现多源结果自动追加。当多个并行节点同时更新同一个字段时，Reducer 决定如何合并（覆盖 / 追加 / 自定义逻辑）。

并行的三种形态：分支从哪来、结果怎么并 【静态 Fan-out / Fan-in】分支数写死在图里 ┌──────────────┐ │ Node Router │ └───────┬──────┘ ┌──────────────────┼──────────────────┐ ▼ ▼ ▼ [搜 Web 0.9s] [搜 DB 1.0s] [搜 Docs 0.8s] │ │ │ └──────────────────┼──────────────────┘ ▼ ┌──────────────┐ │ Node Merge │ ◄── Fan-in 汇聚点 └──────────────┘ 串行总延迟 ＝ 0.9 ＋ 1.0 ＋ 0.8 ＝ 2.7s 并行总延迟 ＝ max(0.9, 1.0, 0.8) ＝ 1.0s ──► 只对"彼此无依赖"的节点成立，有依赖的强行并行只会拿到半成品 【Send API】分支数运行时才知道 ┌──────────────┐ │ Planner │ ──► 生成 N 个子任务 └───────┬──────┘ （N 图定义时未知） │ Send(worker, task_i) × N ┌──────────┬───────┴───────┬──────────┐ ▼ ▼ ▼ ▼ worker#1 worker#2 worker#3 … worker#N └──────────┴───────┬───────┴──────────┘ ▼ Merge ──► 静态图做不到这件事：边的数量不能依赖运行时数据 【Reducer】三条分支同时写 results 字段，怎么办 默认行为（无 Reducer）：后写的覆盖先写的 results ＝ [web] ──┐ results ＝ [db] ──┼──► 最终只剩一个，另两个静默丢失 results ＝ [docs] ──┘ （并行编排最常见的隐性 bug） 声明 Reducer：Annotated[list, lambda a, b: a + b] results ＝ [web] ＋ [db] ＋ [docs] ──► [web, db, docs] 三路结果都在 Reducer 可选策略： 追加 a ＋ b 多源检索结果汇总 覆盖 b 只保留最新状态（如当前重试次数） 自定义 去重 / 取最高分 合并前先做质量筛选

子图组合

将复杂流程封装为可复用的子图——类似"函数调用"，主图调用子图，子图有独立的状态。优势：①模块化（复杂流程拆分为可管理的单元）②复用（同一子图可在多个主图中使用）③独立测试（子图可以单独调试）。

Send API 的价值：实现动态并行——运行时才知道需要多少个并行分支。例如 Planner 生成了 5 个子任务，就动态创建 5 个 worker 节点并行执行。这在静态图中无法实现。

五、LlamaIndex Workflow 与 Dify

两个替代方案各有优势：LlamaIndex Workflow 用事件驱动模型（更函数式、更轻量），适合 RAG 管线；Dify 用可视化画布（低代码/无代码），适合业务人员快速搭建 AI 工作流。

Dify 可视化编排

Dify 是开源 LLM 应用开发平台，提供拖拽式节点编辑器。内置节点类型：LLM、知识库检索、代码执行、HTTP 请求、条件分支、循环、变量聚合。核心优势：低代码（业务人员也能构建）、内置 RAG（文档上传+分块+检索一站式）、一键部署（API/Chatbot/嵌入式组件）。

选型建议：RAG 为主、不需要复杂状态管理 → LlamaIndex Workflow；多 Agent 协作、需要状态持久化 → LangGraph；团队有非技术人员参与、快速原型验证 → Dify。实际中可以混合使用——用 Dify 做面向业务用户的简单应用，用 LangGraph 做面向开发者的复杂系统。

六、错误处理与性能优化

错误处理：五层策略

工作流中的错误处理按五层策略逐级兜底：自动重试（指数退避 1s→2s→4s，最多 3 次，应对 API 超时/速率限制）→ 降级（主模型不可用时切备选模型，如 GPT-4o → GPT-4o-mini）→ 跳过（非关键步骤标记失败继续后续节点）→ 回退（回到上一个 checkpoint 重新执行）→ 人工兜底（通过 interrupt() 暂停等待处理）；不要静默失败——记录、通知、标记。完整的失败处理方法论（错误翻译、隐性失败检测、检查点回滚、缝合交付、生产级可靠性架构）见 A60 · Agent 系统失败处理策略。

Workflow 设计模式

模式结构适用场景
管道模式A → B → C → D线性数据处理
分支模式A → {B, C, D} → E并行处理后汇总

  • 不要用全局变量传数据（用 State，保证可追踪性）

Q&A

LangGraph 的 StateGraph 和 Checkpointer 是怎么工作的？

StateGraph 将工作流建模为有向图：①用 TypedDict 定义全局 State Schema，所有节点共享；②每个 Node 是函数，接收当前 State 返回要更新的字段；③Edge 和 Conditional Edge 定义节点间连接；④Reducer 决定同一字段被多节点更新时如何合并。Checkpointer 在每个节点执行后序列化存储完整 State（SQLite/PostgreSQL），支持：①断点续跑；②Time Travel（回退到任意历史步骤修改后重新执行）；③Human-in-the-Loop（在 interrupt 点暂停，等人工审批后继续）。

Workflow 和 Agent 应该如何选择？可以混合使用吗？

选择依据：①任务流程可预定义（如 RAG 管线）→ Workflow（确定性高、可靠、好调试）；②任务流程需 LLM 动态决策（如"帮我调试 bug"）→ Agent（灵活、适应性强）。混合使用是最佳实践：外层 Workflow 编排主流程，内层某些节点是 Agent。LangGraph 天然支持——一个节点可以是普通函数（确定性），也可以是 create_react_agent（动态决策），甚至可以是子图（嵌套 Workflow）。原则：能用确定性代码的不用 LLM，能用 Workflow 的不用纯 Agent。

LangGraph 和 LlamaIndex Workflow 该选哪个？

核心区别在编程模型：LangGraph 是图驱动（显式定义节点和边），LlamaIndex Workflow 是事件驱动（步骤通过事件连接）。LangGraph 优势：内置 Checkpointer、原生 Fan-out/Fan-in、多 Agent 预构建组件。LlamaIndex Workflow 优势：更轻量、与 LlamaIndex 生态深度集成、事件驱动更函数式。选型：RAG 为核心、不需要复杂状态管理 → LlamaIndex Workflow；多 Agent 协作、需要状态持久化 → LangGraph。两者也可以共存——用 LlamaIndex 做 RAG 节点，嵌入 LangGraph 的大图中。

Workflow 中如何实现可靠的错误处理和重试？

五层策略：①节点级重试（指数退避 1s→2s→4s，只重试可恢复错误）；②模型降级（GPT-4o 挂了切 GPT-4o-mini）；③图级回退（Checkpointer 回退到上一个健康状态）；④人工兜底（interrupt() 暂停执行）；⑤跳过（非关键步骤标记失败继续后续）。Workflow 特有实现要点：每个节点 try/except 包裹，错误写入 State；条件路由检查 errors 数量（过多时走"终止"分支）；最终输出标记 quality_flag；所有错误发告警。更系统的失败处理方法论见 A60 · Agent 系统失败处理策略。

Dify 等可视化编排和 LangGraph 代码编排怎么选？

Dify 适合：①有非技术人员参与；②标准 RAG 场景（内置完整管线）；③快速原型。LangGraph 适合：①需要复杂状态管理；②多 Agent 协作；③自定义节点逻辑；④严格版本控制。混合策略：用 Dify 做面向业务用户的简单应用（客服、文档问答），用 LangGraph 做面向开发者的复杂系统（Code Agent、多 Agent）。原则：工具为任务服务——不要为了用"高级"工具而增加不必要的复杂度。

并行节点同时更新 State 的同一个字段，会发生什么？怎么防？

如果没有为这个字段声明 Reducer，默认行为是覆盖——三条分支各返回一份 results，最终 State 里只留下一份，另外两份被静默丢弃。这是并行编排里最难发现的一类 bug：图跑完了、没有报错、结果看起来也合理，只是少了三分之二的检索来源，通常要等到有人质疑"为什么 Web 结果从来没出现过"才被发现。防法是在 State Schema 上把合并语义显式写出来，例如用 Annotated[list, lambda a, b: a + b] 让多源结果自动追加。选哪种 Reducer 取决于字段语义：多源检索结果用追加；重试次数、当前阶段这类"只有最新值有意义"的字段用覆盖；需要去重或只保留最高分的场景写自定义合并函数。还有两个配套习惯值得养成：一是给每条并行分支的产出带上来源标记（哪个节点、什么时候产生的），合并后仍能追溯；二是在 Fan-in 节点里断言分支数量与预期一致，数量不对就直接标记 quality_flag 而不是让流程继续往下走——静默失败比报错难查得多。
