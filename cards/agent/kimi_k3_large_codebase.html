A69 · Kimi K3 与百万行级代码库改造

KDA 长上下文 / 2.8T MoE / Agent 读核改核 / 搜索代替塞全库 / 测试当裁判

编程 Agent 在前端仓库里好看，往往是因为文件短、反馈快、改错了刷新就知道。数据库内核是另一物种：百万行、隐式不变量、一次改错能腐化存储格式。K3 的价值是把「长程读代码」做成默认能力，不是让你把 177 万行一次性贴进提示词。

一、前端 demo 和数据库内核不是同一类任务

标题里的「不止前端夯」针对的是一种舆论：模型演示总在 React 页面、Todo List、小工具上打转。把同一套 Agent 丢进约 177 万行的数据库源码（SQLite/PostgreSQL 这一量级的 C 内核），失败模式完全不同：符号跨几十个文件、buffer 生命周期靠注释和测试守护、没有热重载。

维度典型前端仓库数据库内核
反馈环刷新浏览器，秒级编译 + 回归，分钟到小时
错误可见性页面白了立刻知道静默腐数据，过天才爆
上下文形态少量 TS/CSS大量 C、平台宏、生成代码
Agent 幻觉代价改错组件改错 pager / WAL 协议
177 万行不是「模型窗口够大就能全读」。即便 K3 标称 100 万 token 上下文，源码按 2–4 字符/token 粗算，也只能同时「盯住」其中一小片。能打内核，靠的是检索式阅读，不是把仓库当一篇文章。

前端夯的是生成速度；内核夯的是「找对文件再敢改」。窗口变大，只是少找几次，不是取消查找。

二、K3 凭什么敢碰百万行

Kimi K3（Moonshot 2026 旗舰，约 2.8T 总参、104B 激活、原生多模态、1M 上下文）把长程编程写进产品定位：KDA（Kimi Delta Attention，混合线性注意力，用来压长序列成本）降低长窗口开销，Attention Residuals 补回质量。对 Agent 来说，这意味着一次会话里能留下更多 grep 结果、编译日志和补丁草稿，而不那么快被摘要冲掉。

K3 对大仓库的「体力」来自三层 模型层 1M 窗口 + 长程指令遵循（少忘当前任务） 工具层 grep / 读文件 / 编译 / 跑测试（Claude Code / Kimi Code / Codex） 纪律层 小补丁、可回滚、测试当裁判 缺任何一层： 只有大窗口 → 会读，不会验证 只有工具 → 200K 模型中途丢目标 只有热情 → 一次 refactor 整仓，无法 review
能力数字对改内核的含义
上下文1,048,576 tokens能同时摊开「调用链 + 测试 + 报错」
激活参数~104B / 2.8T MoE单 token 成本低于同级稠密巨兽
默认思考reasoning_effort 可调内核改动应偏高，避免随手 refactor
K3 可通过 Kimi Code，或 OpenAI 兼容接口接到 Codex / Claude Code（kimi-k3 + Moonshot base URL）。模型换了，仓库工作流（搜索、测试、commit）应该保持不变。把验收命令写进 AGENTS.md 比写进聊天更抗压缩：新会话仍能读到「怎样才算完成」。
1M 窗口的账单会随日志变长而涨。回灌失败日志时截到「从报错到栈顶」即可，不要把整个 make 的无关并行任务输出也塞进去，否则既贵又挤掉不变量。内核任务优先保留：编译器第一处 error、相关测试名、当前 diff。

把这三样当成窗口的「保底配置」，其余文件按 grep 结果按需 Read。这样 1M 才是缓存，而不是把仓库当一篇文章。

任务卡上的允许文件列表，就是这次 Read 的上限。

K3 降低的是「读得动多长的现场」的成本，不是「不用测试」的成本。

三、改造大仓库的工作流

可执行的顺序几乎总是：锁定不变量 → 用搜索定位符号 → 读调用点 → 最小补丁 → 编译 → 跑相关测试 → 对照行为。这和马克那期「稳定交付」是同一套纪律，只是裁判从「页面点得动」换成了「make test / 存储格式没变」。

一次会话不要并行三条不相关的内核改动。长窗口会让 Agent 把三件事的符号搅在一起，review 成本比手写还高。视频标题里的 177 万行是仓库体积，不是一次 diff 的体积：成功的改动通常是几十到几百行，外加一条能复现的测试。

一次内核向改造 1. 写清不变量（WAL 兼容？页大小？SQL 方言？） 2. rg / grep 找符号，不要先全局阅读 3. 读 3–7 个关键文件，而不是 700 个 4. 补丁只动一条因果链 5. 编译 + 目标测试 6. 失败日志原样回灌 Agent 7. git commit 一个逻辑变更
步骤Agent 做人做
不变量写成 AGENTS.md / 任务卡拍板哪些绝对不能破
定位grep、读文件看它是不是找错子系统
修改小 diffreview 存储/并发相关行
验收跑测试抽测真实负载、崩溃恢复
先给「禁止改动的文件/协议」清单，再让 K3 动手。每次只交一个能编译的 commit。
「帮我重构整个存储引擎」。没有测试地图的内核重构，是在用 1M 窗口加速翻车。

大仓库改造的单位是「可编译的因果链」，不是「一次聊完 177 万行」。

四、1M 窗口也装不下全部源码

这是必须写进卡片的反直觉：1M context 仍然远小于整仓。正确用法是 Agentic Search（用 grep/glob/读文件在原始树上交互，而不是先把全库 embed 再问一句）。这和 Claude Code 不用 RAG 搜代码是同一哲学：代码检索的分辨率在精确字符串和结构，不在「语义差不多的 chunk」。

有效工作集 ≪ 仓库总行数
窗口预算优先给：当前 diff + 失败日志 + 不变量 + 少量关键实现
塞进上下文的东西该不该
当前失败的测试输出要，原文
目标函数及其 2 层调用点要
整份 sqlite3.c 一次性粘贴不要，挤掉裁判信号
无关平台后端不要，除非报错点名
Embedding RAG 对自然语言文档有用，对内核 C 代码容易「语义相近、调用关系完全错」。大窗口模型更容易让人误以为可以放弃 grep。窗口是缓存，不是目录。

窗口变大以后，更要吝啬：多出来的 token 留给日志和测试，不要留给「我把仓库读完了」的错觉。

五、验收：编译、测试、行为对照

内核没有「看起来能跑」。最低验收是：编译通过、官方/模块测试绿、改动前后的存储文件仍能被旧二进制打开（如果你承诺兼容）。Agent 会谎报完成——长时执行那期已经用 443 个带验收标准的任务说明过。这里的验收标准必须是命令，不是「我觉得重构更清晰了」。

建议把验收写成一张表，贴进 AGENTS.md，让 K3 只能引用命令而不是形容词。编译失败要把完整日志回灌，不要摘要成「有个 link error」。兼容性测试至少覆盖：旧库文件可打开、一组固定 SQL 结果哈希不变、崩溃恢复能从 WAL 起来。

验收层命令/产物未通过时
编译make / 构建脚本退出码 0原文日志回灌，禁止自称完成
回归官方测试子集或目标模块测试禁止扩 scope，先修红灯
兼容旧库文件 + 固定 SQL 哈希回滚补丁，检查存储格式
人抽测崩溃恢复、并发、性能手测记进禁区，下一轮禁止再动
裁判层级（越往下越贵，越不能省） 编译器 ← 语法 / 链接 单测/回归 ← 明确断言 兼容性 ← 旧库文件、旧 SQL 人 ← 崩溃恢复、性能、 concurrent 手测 Agent 只允许在「测试命令输出」上自称完成
K3 的长上下文让「带着完整编译失败日志继续修」变得现实：不必把错误摘要成两句话。这比「一次生成 177 万行的新内核」有用得多。生产价值在修循环，不在第一稿。

能证明改对了的，永远是旧测试和新失败日志，不是模型的自信。

Q&A

为什么说「前端夯」不能外推到数据库内核？
前端的反馈环短、错误可见、状态多在内存。内核改的是持久化协议和并发不变量，错一次可能无声损坏文件。Agent 在前端仓库里的高成功率，大量来自「改完立刻看见」。到了 177 万行 C，看见对错的周期变成编译和回归。必须换工作流：搜索、小补丁、测试裁判，而不是同一套「生成整个页面」的习惯。
K3 的 1M 窗口是不是可以把整仓塞进去？
不能。1M token 只覆盖仓库的一个工作集。正确用法是 grep 定位后再读少量文件，把省下的窗口留给测试输出和补丁。把 sqlite 合并文件整份粘贴会挤掉最有用的失败日志。大窗口是为了少丢失现场，不是为了取消文件系统。
改内核该用 RAG 还是 grep？
优先 grep/glob/精确读文件。代码的关键是符号和调用关系，向量召回容易给出「主题相近但完全不是这条执行路径」的文件。RAG 更适合文档和工单。K3 接进 Claude Code 或 Kimi Code 时，应保持 Agent 搜索，而不是先建一套代码向量库再问。
怎样把 K3 接到现有编程 Agent？
Kimi Code 可直接切模型；也可以用 Moonshot 的 OpenAI 兼容接口，在 Codex / Claude Code 里把 model 设为 kimi-k3。换模型不应换纪律：仍要 AGENTS.md、测试命令、小 commit。K3 提供更长的现场记忆，不提供「可以不写验收」的特权。
什么样的任务适合让 K3 改数据库源码？
边界清楚、有测试、不破坏存储兼容的局部改动：修一个优化器分支、补一种 SQL 方言的解析、加日志。不适合：没有回归网的存储格式升级、一次性重写锁协议。人先划禁区，Agent 再在许可区内搜索和打补丁。
怎样判断 Agent 是真改对了还是在表演？
只看它能否指出具体测试命令和退出码。若只能说「已经更清晰/更高效」，按未完成处理，把失败日志原文丢回去。内核场景下，兼容性测试（旧文件可打开）比主观 code review 更能抓住静默破坏。模型的长上下文正好用来装这些日志，而不是装自我评价。
为什么不要在一次会话里并行改多个子系统？
长窗口会把优化器、锁、VACUUM 的符号留在同一现场，Agent 容易交叉打补丁，review 成本高于手写。177 万行是仓库体积，成功的 diff 通常只有几十到几百行。一次一张任务卡、一个 commit，失败了只回滚这一张，才是长上下文该配合的工作方式。
K3 的 MoE 对改代码有什么实际影响？
2.8T 总参、约 104B 激活，意味着单 token 成本低于同级稠密巨兽，长日志回灌才负担得起。它不改变测试纪律：激活参数再大，也不会替你跑 make test。推理强度（reasoning_effort）在内核改动上应偏高，避免随手 refactor。省下的钱应花在多轮「日志→补丁→再测」，而不是一次生成整仓。
人 review 时该盯哪里？
优先看禁区附近：pager、WAL、文件头、锁协议。Agent 在许可区内的样板修改可以抽测。存储格式和崩溃恢复必须人手测，因为测试子集未必覆盖你的真实库文件。任务卡上的「禁止改」清单，就是 review 的目录，而不是把 177 万行重新读一遍。
