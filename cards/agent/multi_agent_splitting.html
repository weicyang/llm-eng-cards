A45 · 多 Agent 拆分：以上下文边界为依据

Multi-Agent Splitting — 以上下文为中心的拆分原则 vs 按职能拆分的陷阱 / 红绿灯法则 / 量化评估框架

多 Agent 拆分的核心洞察是：子 Agent 存在的首要目的是隔离上下文，而非模拟人类组织角色。按职能拆分（PM/Dev/QA）模仿人类公司结构，但会导致上下文切断和传话游戏；按上下文拆分（Feature Agent / Infra Agent）让每个 Agent 内部信息自给自足，通信成本最小化。

一、两种拆分思维深度对比

按职能拆分是人类组织的历史惯性——公司部门就是这么设的，所以直觉上觉得 Agent 也应该这么拆。但 Agent 不是人，它没有"专业背景"和"职业经验"，它的核心瓶颈是上下文窗口的容量和注意力分配。

二、红绿灯法则：判断拆分边界的实操框架

红绿灯法则是判断"这个任务是否应该拆成独立 Agent"的快速决策工具。绿灯模式意味着上下文可以被真正隔离，红灯模式意味着拆分只会增加通信成本而没有收益。

绿灯模式（可以拆）：

  • 独立的研究路径：如"搜索学术论文"和"爬取竞品数据"完全独立，无需共享上下文
  • 拥有清晰接口的组件：输入输出可以用 JSON Schema 严格定义，不需要解释内部逻辑
  • 黑盒验证任务：输入一组测试用例，输出通过/失败，不需要知道实现细节
  • 不同工具集的任务：安全扫描用 SAST 工具，性能分析用 Profiler，工具完全不重叠
  • 可并行执行的子任务：多个独立的数据分析任务可以同时运行

红灯模式（不要拆）：

  • 同一工作的连续阶段：规划→实现→测试是同一任务的三个阶段，拆开后每个阶段都需要完整上下文
  • 紧密耦合的组件：如前端 UI 和后端 API 的设计必须同步，拆开后需要频繁沟通
  • 需要持续共享状态的任务：如多个 Agent 同时修改同一个数据模型
  • 需要频繁解释背景的任务：如果需要反复同步"为什么这么做"，说明不该拆
  • 简单任务：单 Agent 就能完成，拆分只增加复杂性和 Token 成本

判断标准的量化指标

黄金判断：凡是需要频繁解释背景的，就不该拆。只有当上下文可以被真正隔离时，拆分才是有效的。用四个量化指标验证：(1) 上下文独立完成率 > 90%（不需要问其他 Agent）；(2) 每任务通信次数 ≤ 2 次；(3) 工具集重叠度 < 30%；(4) 并行收益 > 通信成本。满足 3/4 条以上才是好的拆分。

三、上下文隔离的五大实践模式

"以上下文为中心"不是抽象原则，它有五种具体的落地模式。每种模式适用于不同的场景，选择哪种取决于任务的上下文依赖关系图。

模式一：领域隔离

按业务领域拆分 Agent，每个 Agent 负责一个独立的业务领域。例如电商系统中，"用户管理 Agent"负责注册、登录、权限，"商品管理 Agent"负责上架、定价、库存。两个领域共享的信息极少（仅用户 ID 和商品 ID），上下文几乎完全隔离。

模式二：工具隔离

按工具集拆分 Agent，每个 Agent 只持有完成特定任务所需的最小工具集。这是代码审查系统的典型做法：安全 Agent 只持有 SAST 扫描工具，性能 Agent 只持有 Profiler 工具，规范 Agent 只持有 Linter 工具。工具集不重叠，Agent 之间无需共享上下文。

模式三：阶段聚合

将同一任务的所有阶段（设计→实现→测试→部署）聚合到一个 Agent 中，而非拆成多个 Agent。这是最容易犯错的地方——很多团队直觉上想按阶段拆分，但每个阶段都需要完整理解上下文（"为什么要这样设计？""代码为什么用这种模式？"），拆分后通信成本远大于并行收益。

模式四：数据分区

当数据集过大、单 Agent 上下文窗口放不下时，按数据分区拆分。例如处理 1000 篇文档时，拆成 5 个 Agent 各处理 200 篇，最后由汇总 Agent 合并结果。每个分区 Agent 的上下文完全独立（处理不同的文档），只在最后汇总时需要同步。

模式五：关注点分离

按关注点（Concern）拆分——业务逻辑、数据访问、安全策略分别由不同 Agent 处理。这种模式适合企业级系统，其中安全策略和合规要求由专门的 Agent 强制执行，业务 Agent 无需关心安全细节。

四、拆分质量的量化评估框架

"好拆分"和"坏拆分"不能只靠直觉判断——需要量化指标来评估。五个核心指标可以系统性地衡量拆分方案的质量。

拆分质量分 = 0.3×上下文闭环度 + 0.2×工具聚焦度 + 0.2×通信效率 + 0.15×独立可测性 + 0.15×部署独立性

五大评估指标

指标定义好（绿灯）差（红灯）
上下文闭环度Agent 独立完成任务无需外部上下文的比例> 90%< 60%
工具聚焦度Agent 工具集围绕同一类任务的集中程度工具类型单一混合工具（安全+性能+规范）
通信效率每个任务平均 Agent 间通信次数1-2 次5+ 次
独立可测性能否为每个 Agent 单独编写测试用例可以独立 Mock 和测试依赖外部 Agent 太多
部署独立性能否单独更新某个 Agent 而不影响其他可以独立部署接口耦合严重
生产经验：满足 4/5 条以上指标即为好的拆分。某 SaaS 平台的多 Agent 系统在优化拆分方案后：上下文闭环度从 55% 提升至 93%，每任务通信次数从 7 次降至 1.5 次，工具选择错误率从 15% 降至 3%，端到端任务完成时间缩短 40%。

"通信 Token > 任务 Token"的诊断方法

当 Agent 拆分不合理时，Agent 之间需要频繁同步上下文（"我做了什么""为什么这么做""接下来你需要知道什么"），这些通信开销的 Token 消耗可能超过实际执行任务的 Token。诊断方法：记录每次任务的总 Token 消耗，拆分为"任务 Token"（Agent 执行实际工作）和"通信 Token"（Agent 间同步信息）。如果通信 Token 占比 > 50%，说明拆分边界有问题。

五、从单 Agent 到多 Agent 的渐进迁移路径

不要一上来就设计多 Agent 架构。遵循"单 Agent → 加工具 → 加 Agent"的渐进路径，只有在前两步无法满足需求时才引入多 Agent。过早拆分是多 Agent 系统最常见的失败原因。

四步迁移路径

步骤操作判断标准（进入下一步）
Step 1单 Agent + 少量工具，跑通核心流程核心流程可用，但发现上下文溢出或工具选择错误
Step 2单 Agent + 更多工具，优化 Prompt 和工具描述工具数 > 15 个，工具选择错误率 > 10%
Step 3识别拆分点，按上下文隔离原则拆出第一个独立 Agent找到上下文可独立运作的子任务群
Step 4逐步增加 Agent，每次只拆一个，观测效果拆分后通信次数 ≤ 2，工具选择错误率下降
行业数据：Anthropic 的生产指南明确指出："Start with one agent, add tools, then add agents only when necessary"。LangChain 的调研显示，65% 的 AI 领导者认为 Agent 系统复杂性是最大障碍。VentureBeat 的研究发现生产级多 Agent 系统的规模化成功率不到 25%——失败的主要原因不是技术不行，而是过早引入多 Agent 导致协调复杂度过高。正确的路径是先让单 Agent 在工具选择上失败，再用多 Agent 解决这个问题。
  • 以上下文隔离为原则拆分 Agent，确保拆分后各 Agent 上下文独立
  • 遵循"单 Agent → 加工具 → 加 Agent"的渐进路径
  • 用量化指标评估拆分质量（上下文闭环度、通信效率等）
  • 按"任务种类"切分（川菜厨师、粤菜厨师），而非按"工序阶段"切分
  • 拆分后每个 Agent 的工具集和上下文应该高度聚焦
  • 每次只拆一个 Agent，观测效果后再进行下一步
  • 模仿人类组织结构拆分 Agent（PM/Dev/QA 模式）
  • 频繁需要解释背景的拆分（传话游戏模式）
  • 上下文无法隔离时强行拆分
  • 为了"多智能体"而拆分简单任务
  • 一上来就设计多 Agent 架构（过早优化）
  • 只看 Agent 数量不看通信成本

六、生产案例与效果量化

案例一：代码审查系统重构

某代码审查 Agent 从单 Agent 拆分为 3 个专业 Agent 后：(1) 安全 Agent（SAST 扫描上下文）— 漏洞检出率从 67% 提升至 92%（专注安全规则，上下文不被代码逻辑干扰）；(2) 性能 Agent — 瓶颈定位准确率从 54% 提升至 88%（独立的性能分析上下文窗口）；(3) 规范 Agent — 编码规范覆盖率从 71% 提升至 95%。拆分前单 Agent 工具数 22 个，拆分后每个 Agent 平均 7 个工具，工具选择错误率从 15% 降至 3%。

案例二：SaaS 平台智能客服

某 SaaS 平台的客服系统最初按"职能"拆分（问答 Agent、工单 Agent、退款 Agent），导致严重的上下文切断问题——用户在问答中描述的问题，工单 Agent 不知道背景，需要用户重复描述。重构为按"用户旅程"拆分（新用户引导 Agent、使用问题 Agent、账户管理 Agent）后，每个 Agent 内聚了该旅程阶段的所有能力（问答+工单+退款），用户满意度从 62% 提升至 89%，平均处理时间从 12 分钟降至 5 分钟，重复描述率从 45% 降至 8%。

Q&A（8 题）

多 Agent 为什么不能按职能/角色拆分？
按职能拆分（PM/Dev/QA）模仿人类公司结构，但 Agent 不是人——它没有"专业背景"，它的核心瓶颈是上下文窗口。按职能拆分会导致上下文切断：QA 不知道 Dev 为什么这么写，需要反复解释背景。通信 Token 可能大于任务 Token（生产数据：按职能拆分时通信占比 65%，按上下文拆分时仅 15%），形成"传话游戏"。正确做法是以上下文为中心拆分，把依赖同一套信息的任务聚合在一起。
怎么判断一个任务是否应该拆成独立 Agent？
用红绿灯法则四步决策：(1) 上下文隔离测试 — 拆开后每个 Agent 能否独立完成任务而不需要问其他 Agent"这是什么意思"？(2) 通信频率预估 — 拆开后每个任务平均通信次数 ≤ 2 次？(3) 工具集重叠度 — 两个 Agent 的工具集重叠 < 30%？(4) 并行收益评估 — 并行节省的时间 > 通信开销？满足 3/4 条以上才是好的拆分。核心判断：凡是需要频繁解释背景的，就不该拆。
"以上下文为中心"具体怎么落地？
五种实践模式：(1) 领域隔离 — 按业务领域拆分（如用户/商品/订单），领域间共享极少；(2) 工具隔离 — 按工具集拆分（如安全/性能/规范），工具不重叠；(3) 阶段聚合 — 同一任务的所有阶段（设计→开发→测试）聚合到一个 Agent，内部闭环；(4) 数据分区 — 大数据集按分区拆分，每个分区独立处理；(5) 关注点分离 — 按系统关注点拆分（业务/安全/合规）。关键是让每个 Agent 内部上下文闭环，对外只暴露清晰接口。
"通信 Token > 任务 Token"是什么问题？怎么诊断？
当 Agent 拆分不合理时，Agent 之间需要频繁同步上下文（"我做了什么""为什么这么做""接下来你需要知道什么"），这些通信开销的 Token 消耗可能超过实际执行任务的 Token。诊断方法：记录每次任务的总 Token 消耗，拆分为"任务 Token"和"通信 Token"。生产数据：按职能拆分时总 Token 1000、通信占 65%；按上下文拆分时总 Token 600、通信占 15%。好拆分不仅通信比例低，总 Token 也更少——因为减少了解释背景的冗余消耗。
怎么判断一个 Agent 拆分方案是"好拆分"还是"坏拆分"？
五个量化指标：(1) 上下文闭环度 — Agent 独立完成任务无需外部上下文的比例 > 90%？(2) 工具聚焦度 — 工具是否围绕同一类任务？混合工具说明没拆干净；(3) 通信效率 — 每任务平均通信 1-2 次是好的，5+ 次说明耦合太紧；(4) 独立可测性 — 能否单独写测试用例？不能说明依赖外部 Agent 太多；(5) 部署独立性 — 能否单独更新某个 Agent 而不影响其他？满足 4/5 条以上就是好的拆分。生产经验：满足全部 5 条的系统，端到端任务完成时间平均缩短 40%。
什么时候不应该拆分成多 Agent？
五种场景不该拆：(1) 简单任务 — 单 Agent 就能完成，拆分只增加复杂性和 Token 成本（约 15 倍）；(2) 同一工作的连续阶段 — 规划→实现→测试是同一任务的三个阶段，每个阶段都需要完整上下文；(3) 紧密耦合组件 — 如前端 UI 和后端 API 设计必须同步；(4) 需要持续共享状态 — 多个 Agent 同时修改同一数据模型会引入一致性风险；(5) 上下文无法隔离 — 如果需要反复解释背景，说明不该拆。判断标准：拆分后的并行收益是否大于协调成本。
从单 Agent 迁移到多 Agent 应该遵循什么路径？
四步渐进迁移：(1) 单 Agent + 少量工具 — 跑通核心流程，记录上下文溢出和工具选择错误的场景；(2) 单 Agent + 更多工具 — 优化 Prompt 和工具描述，当工具数 > 15 且错误率 > 10% 时考虑拆分；(3) 识别拆分点 — 按上下文隔离原则，找出可独立运作的子任务群（如安全扫描 vs 代码开发），拆出第一个独立 Agent；(4) 逐步增加 — 每次只拆一个 Agent，观测通信次数 ≤ 2、工具错误率下降后再拆下一个。行业数据：过早引入多 Agent 是生产系统失败的主要原因（成功率不到 25%）。
按"任务种类"拆分和按"处理阶段"拆分有什么区别？
按"任务种类"拆分（如安全 Agent、性能 Agent、规范 Agent）：每个 Agent 专注于一个独立维度，使用不同的工具集，上下文完全隔离，可以并行执行。按"处理阶段"拆分（如分析 Agent → 修复 Agent → 验证 Agent）：每个阶段都需要理解完整的代码上下文（"为什么要分析这个问题？""修复方案为什么选这个？""验证标准是什么？"），拆开后通信成本极高。类比：按菜系拆分（川菜厨师 vs 粤菜厨师）可以并行工作，按工序拆分（备菜 vs 炒菜 vs 装盘）每步都需要知道"这道菜最终要什么样"。
