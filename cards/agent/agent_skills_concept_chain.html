A28 · Agent Skills 概念体系

Prompt → Command → System Prompt → Metadata → Reference/Script → Skill 完整概念链 → Skill vs MCP vs Workflow

Skill 不是一项新发明，而是 Prompt 一路演化的终点——一个以文件夹形式存在、可以按需加载、自带参考资料和脚本的"结构化系统提示词"。理解这条六步概念链，就能明白它为什么出现、以及它和 MCP/Workflow 各管哪一段。

一、从 Prompt 到 Skill：六步概念链

Agent Skills 不是凭空冒出来的新词。它是从最基础的 Prompt（发给模型的一段指令文本，是让人工智能干活的唯一入口）出发，被一个个具体痛点逼出来的。每一步演化都在解决上一步留下的问题，理解这条链，Skill 的本质就不言自明。

┌──────────────────────────────────────────────────────────┐ │ ① Prompt 一句话指令："帮我写简历" │ └──────────────┬───────────────────────────────────────────┘ ↓ 痛点：长提示词每次都要手敲 ┌──────────────────────────────────────────────────────────┐ │ ② Command /resume 一键替换出固定内容 │ └──────────────┬───────────────────────────────────────────┘ ↓ 痛点：放在 User Prompt 里模型不够听话 ┌──────────────────────────────────────────────────────────┐ │ ③ System Prompt 高优先级指令（CLAUDE.md/.cursorrules） │ └──────────────┬───────────────────────────────────────────┘ ↓ 痛点：多场景全量塞入 → Token 爆炸 ┌──────────────────────────────────────────────────────────┐ │ ④ Metadata 文件开头短描述，先匹配再加载正文 │ └──────────────┬───────────────────────────────────────────┘ ↓ 痛点：单个文件仍然太大，还需要执行代码 ┌──────────────────────────────────────────────────────────┐ │ ⑤ Reference/Script 按需读资料 + 按需跑脚本 │ └──────────────┬───────────────────────────────────────────┘ ↓ 打包成可复用的完整方案 ┌──────────────────────────────────────────────────────────┐ │ ⑥ Skill 文件夹 = 可动态加载的结构化系统提示词 │ └──────────────────────────────────────────────────────────┘
步骤概念解决了什么问题本质
①Prompt让 AI 干活的入口一句话指令
②Command（快捷命令）长提示词不用每次手敲快捷键替换固定内容
③System Prompt（系统提示词）让 AI 更听话高优先级指令，遵循效果优于 User Prompt
④Metadata（元数据）多场景不混在一起文件开头的短描述，用于按需匹配
⑤Reference / Script单个文件太大、需要拆分与执行按需加载的资料和按需执行的代码
⑥Skill（技能）打包成可复用的完整方案文件夹 = 动态加载的系统提示词

这条链的每一步都是被"上一步的痛点"逼出来的：太长 → Command，不听话 → System Prompt，场景太多 → Metadata，文件太大 → Reference/Script，要复用 → Skill。

二、六个概念逐层拆解

2.1 Prompt 与结构化提示词

最基础的一句"帮我写简历"效果很差，模型不知道你要什么格式。于是人们在提示词里加入详细规则——姓名居中、经历用表格、项目按 STAR 法则展开——这就变成了结构化提示词。效果好了，但新的问题随之出现：这份提示词可能有上千字，每次都手敲一遍既慢又容易漏。

2.2 Command — 快捷替换

Claude Code 等工具支持把常用提示词固化成文件，用短命令（如 /resume）快速调出。它的本质非常朴素：用快捷键替换一段固定内容，省去的只是打字时间，提示词本身并没有变聪明。

2.3 System Prompt — 让 AI 更听话

同样的要求，放在 System Prompt 里比放在 User Prompt 里遵循效果好得多——模型在训练时被引导优先服从系统级指令。各客户端为此提供了专门的载体文件：

客户端系统提示词载体作用范围
Claude CodeCLAUDE.md项目级 / 全局级
Cursor.cursorrules / .cursor/rules项目级规则文件
Claude Desktop设置中的自定义指令全部会话

2.4 Metadata — 按需匹配的目录

当场景多起来（简历、周报、邮件、SQL 审查……），不可能把所有系统提示词全塞进上下文。做法是给每个文件开头加一段短描述，也就是 metadata，AI 客户端只把这些"目录条目"发给模型做场景匹配，命中后才加载对应文件的完整内容。核心价值只有一个词：省 Token。

---
name: resume-writer
description: 按目标岗位定制简历并导出 PDF，
  用户提到"简历""求职"时触发。
---
（下面是完整指令正文……）

2.5 Reference 与 Script — 拆文件与跑代码

单个文件仍然太大时（比如"写简历"要区分产品、开发、算法三种岗位手册），就继续向下拆分：把子资料放进 references/ 文件夹，客户端用 cat 等命令按需读取，不用的文件一个 Token 都不消耗。既然能读文件，自然也就能执行代码——把 Python 脚本放进 scripts/ 文件夹，在提示词中写清触发条件，模型就能在合适时机调用它（如生成 Word 后导出 PDF）。

Skill = 目录（metadata）+ 正文（instruction）+ 附录（reference）+ 工具箱（script），四件套缺一不可，但每次只带上需要的那几件。

三、Skill 的目录结构与渐进式加载

渐进式披露（Progressive Disclosure）是 Skill 运行机制的核心：信息分层暴露，模型只在需要的那一层才付出 Token 成本。下面以视频中的 resume-writer 为例看完整流程。

文件夹结构： ~/.claude/skills/ └── resume-writer/ ├── skill.md ← 入口（metadata + instruction） ├── references/ │ ├── product.md ← 产品岗参考 │ ├── developer.md ← 开发岗参考 │ └── algorithm.md ← 算法岗参考 └── scripts/ └── export_pdf.py ← Word → PDF 导出脚本 运行时加载流程： 用户："帮我写个开发岗简历 PDF" ↓ 客户端只上报所有 Skill 的 metadata（每个几十 Token） ↓ 模型判断命中 resume-writer → 告知客户端 ↓ 客户端将 skill.md 全文注入 System Prompt ↓ 模型按指令读取 references/developer.md（其余两个不读） ↓ 模型执行 scripts/export_pdf.py 生成 PDF ↓ 最终结果返回用户

3.1 Token 账本：按需加载省在哪

加载策略计算过程每轮固定开销
全量预载 10 个 Skill10 × 2,000 Token20,000 Token
Metadata + 命中 1 个全文10 × 50 + 2,0002,500 Token（-87%）
再按需读 1 个 Reference2,500 + 8003,300 Token（-83%）

关键在于：Reference 是被读取的，内容进入上下文、消耗 Token；而 Script 是被执行的，客户端只拿运行结果，代码本身几乎不占 Token。两者都是条件触发——在 skill.md 中写明"提到岗位 → 读对应手册""提到 PDF → 执行导出脚本"，不满足条件就绝不加载。

Skill 的加载像查字典：先看目录（metadata），翻到那一章（skill.md），需要佐证再查附录（reference）——没人会把整本字典念一遍。

案例 · 编码助手的提示词瘦身： 背景：某团队的编码助手内置 12 个场景化提示词（代码审查、周报、SQL 优化等），早期全部拼进 System Prompt 常驻。 问题：每轮对话固定携带约 24,000 Token，首 Token 延迟高达 4.1 秒，月度 API 账单中超过一半花在重复携带的静态文本上。 方案：改造为 Skill 结构——12 个 skill.md 只暴露 metadata（平均 55 Token），命中后才注入全文，公共资料拆进 references/ 按任务类型读取。 效果：每轮固定开销降至约 660 Token（-97%），首 Token 延迟降到 1.6 秒，月度成本下降约 55%。

四、Skill vs MCP vs Workflow

三者经常被放在一起比较，因为它们都在回答同一个大问题——"怎么让 AI 完成一件多步骤的事"，但各自负责的层次完全不同。

维度SkillMCPWorkflow
本质操作经验 / 流程指南工具调用协议低代码流水线
类比📖 操作手册🔧 工具 + 手🏭 生产线
流程确定时机运行时由模型驱动N/A（只管工具调用）设计阶段已确定
灵活性高（模型动态决策）N/A低（固定流程）

需求："让 AI 完成一件多步骤的事" │ ├─ 步骤完全固定、可以穷举？ │ 是 → Workflow（N8N / Dify 拖拉拽，确定性优先） │ 否 ↓ ├─ 需要调用外部系统 / API？ │ 是 → 接 MCP Server（先解决"有没有工具"） │ ↓ └─ 需要模型自己决定顺序与分支？ 是 → 写 Skill（再解决"怎么组合工具"） 组合用法：Skill 里编排 MCP 工具 ≈ 大模型驱动的 Workflow
典型场景首选方案理由
每天固定流程的报表生成Workflow步骤确定，要的是稳定而非灵活
查天气、读数据库MCP纯工具能力，无需流程编排
写简历、代码审查流程Skill有判断分支的操作经验

一句话记牢：MCP 给大脑配手和工具，Skill 教大脑怎么用这些工具，Workflow 是提前画死的流水线。Skill 可以粗略理解为大模型驱动的 Workflow——编排权从预设规则交给了模型。

五、生产实践与最佳实践

案例 · resume-writer Skill 落地实测： 背景：一位开发者把"简历定制"做成 Skill，包含 180 行指令的 skill.md、3 个岗位 Reference 和 1 个导出脚本。 问题：此前每次把 3,000 字提示词整段粘贴进对话框，模型经常漏掉"导出 PDF"这一步，一次成功率只有约 70%。 方案：指令、资料、脚本三分离——触发条件写进 metadata，岗位手册放进 references/ 按需读取，导出动作交给 scripts/export_pdf.py 强制执行。 效果：单次任务平均消耗约 3,400 Token（此前全量约 8,900），PDF 一次成功率提升到 100%，端到端约 45 秒。

5.1 Skill 设计检查清单

检查项合格标准
description 是否写清触发条件模型只看 metadata 就能判断该不该用
skill.md 是否保持精简超长内容拆进 references/，入口只留索引
确定性操作是否脚本化生成 PDF、上传文件等交给 script，不靠模型"记住"
触发条件是否明确"提到 X → 读某文件 / 执行某脚本"写死在指令里
  • 把反复粘贴的长提示词沉淀成 Skill
  • metadata 里写清"什么场景触发"
  • 大资料拆成多个 Reference 按需加载
  • 确定性步骤（导出、上传）写成 Script
  • 不要把所有资料堆进 skill.md 正文
  • 不要在 description 里写模糊的"万能助手"
  • 不要让模型靠记忆执行关键步骤（该跑脚本就跑脚本）
  • 不要给一次性任务建 Skill（直接 Prompt 即可）

判断要不要做 Skill 的信号很简单：同一段提示词你已经复制粘贴超过三次，就该把它文件夹化了。

Q&A

Agent Skill 的完整概念链是什么？从 Prompt 到 Skill 经历了哪些演化？
完整链条是六步：Prompt（一句话指令）→ Command（快捷替换长提示词）→ System Prompt（高优先级指令，让模型更听话）→ Metadata（文件开头短描述，用于多场景按需匹配）→ Reference/Script（拆分大文件并支持执行代码）→ Skill（打包为文件夹形式的动态系统提示词）。每一步都针对上一步的痛点：太长所以用 Command，不听话所以升级为 System Prompt，场景太多所以引入 Metadata，文件太大所以拆 Reference/Script，要跨项目复用所以打包成 Skill。理解这条链就能明白，Skill 本质上就是"可以按需加载的结构化系统提示词"。
Skill、MCP 和 Workflow 三者的核心区别是什么？
Skill 是操作经验和流程指南，本质是结构化的系统提示词，教模型"怎么做"；MCP 是工具调用协议，本质是通信标准，解决"有没有工具可用"；Workflow 是预定义流水线，步骤在设计阶段就被固定下来。关键区别有三点：其一，Skill 的执行流程由模型在运行时动态决策，Workflow 在设计时就已确定；其二，MCP 只负责工具能否被调用，Skill 负责工具如何组合使用；其三，Skill 内部既可以编排 MCP 工具，也可以编排本地 Script。一个不精确但好记的说法是：Skill ≈ 大模型驱动的 Workflow。
Metadata 在 Skill 中起什么作用？为什么它能节省 Token？
Metadata 是 skill.md 文件开头的短描述（通常是 name + description），作用类似一本书的目录。用户发出请求时，客户端只把所有 Skill 的 metadata 而非完整内容发给模型，模型据此判断命中哪个 Skill，客户端再加载那个 Skill 的全文。省 Token 的原理很直观：假设 10 个 Skill 平均各 2,000 Token、metadata 各 50 Token，全量预载每轮要花 20,000 Token，按需加载只要 500 + 2,000 = 2,500 Token，节省约 87%。Skill 越多，这个差距越夸张。
Reference 和 Script 在 Skill 中分别是什么？加载方式有何不同？
Reference 是按需加载的参考资料，放在 references/ 文件夹；Script 是按需执行的代码脚本，放在 scripts/ 文件夹。两者的加载方式有本质差异：Reference 是被"读取"的，客户端用 cat 等命令把文件内容送进模型上下文，会消耗 Token；Script 是被"执行"的，客户端只运行并取回结果，代码本身几乎不占 Token。两者都是条件触发的——需要在 skill.md 中写明触发规则，例如"提到岗位 → 读取对应岗位手册""提到上传 → 执行 upload.py"，不满足条件就绝不加载。这也是 Skill 能做到"轻装上阵"的关键设计。
为什么说 Skill 可以理解为"大模型驱动的 Workflow"？
因为两者做的是同一件事——逻辑编排，即把多个步骤组合成完整流程，区别只在流程何时确定。Workflow（如 N8N、Dify）在设计阶段通过拖拉拽确定固定路径，运行时严格按预设执行，确定性强但灵活性低；Skill 的流程由模型在运行时动态决策，模型根据用户输入和中间结果自主选择下一步——要不要加载某个 Reference、要不要执行某个 Script。本质上，Skill 把"流程编排"的决策权交给了模型，而 Workflow 把决策权留给了预设规则。所以把 Skill 叫作"大模型驱动的 Workflow"抓住了要害，只是要记住它的执行路径是概率性的而非确定的。
Skill 和 RAG 都是"按需给模型喂资料"，区别在哪里？
两者确实都用了"按需加载"的思想，但喂的东西和触发方式不同。RAG 喂的是事实性知识（文档、网页、数据库内容），靠向量检索的语义相似度自动召回，模型并不知道资料库里有什么；Skill 喂的是操作性知识（怎么做某件事的流程与规则），靠 metadata 的显式描述由模型主动选择。换个说法：RAG 是"开卷考试的参考书"，Skill 是"老师傅的操作手册"。实践中两者经常配合——Skill 规定流程，流程中某一步需要查私域资料时再走 RAG 检索。
什么信号出现时，应该把一段提示词升级成 Skill？
有几个明确的信号：第一，同一段提示词被反复复制粘贴三次以上，说明它已经具备了复用价值；第二，提示词长到需要滚动才能看完，说明它该拆成 instruction + reference 的结构；第三，任务里出现"必须执行的确定性步骤"（如导出 PDF、上传文件），说明需要 Script 来兜底而不是指望模型记住；第四，同一套方法论要服务多个场景（不同岗位、不同部门），说明需要 metadata 做按需匹配。反过来，一次性的、三言两语就能说清的任务，直接写 Prompt 即可，没必要为了"用 Skill 而用 Skill"增加维护成本。
