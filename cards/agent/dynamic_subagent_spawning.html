A47 · 主 Agent 动态派生子 Agent

单 Agent 天花板 / 三代架构演进 / agent tool 派生机制 / 三大工程铁律 / 生产级防线

动态派生的本质是"以空间换时间、以隔离换可控"——主 Agent 开出 N 个全新的上下文窗口去并行装载单窗口装不下的信息，每个窗口独立跑完自己的循环，最后只把最压缩的一条结论交回来。

一、单 Agent 的三重绝症

所谓动态派生（Dynamic Spawning），是指主 Agent 在运行过程中根据需要，随时通过一次工具调用创建一个全新的子 Agent——子 Agent 数量不是设计时写死的，而是任务推进中"长"出来的。要理解它为什么出现，先看单个 Agent 独自扛任务时会撞上的三堵墙。

第一堵墙是上下文爆炸。一个典型的真实场景：让 Agent 分析 75 家公司二十年间的核心技术演进，相关资料多达几十万份文档，而主流模型的上下文窗口只有 20 万 token 左右——信息量与窗口容量之间差着数量级。即使窗口装得下，窗口被填满到约 75%~92% 时系统会触发自动压缩，早期的关键约束和细节就在一次次有损摘要里悄悄丢失。第二堵墙是串行瓶颈：所有子任务排队经过同一条推理线程，墙钟时间随任务数线性增长，500 个文件的迁移要一个文件一个文件地啃。第三堵墙是全能陷阱：同一个 Agent 既要规划、又要检索、还要审查自己的产出，单一提示词扮演 N 种角色，每一种都不够专业，而且"规划"和"执行"挤在同一个窗口里互相污染。

Anthropic 在构建其多智能体研究系统时把这种困境概括为一句话：当智能达到一定门槛后，继续堆强单个个体的收益，远低于把任务分给一组可并行的个体。他们的内部分析还揭示了一个更根本的规律：在复杂检索类任务上，token 消耗量本身就能解释约 80% 的性能差异（加上工具调用次数与模型选择可解释 95%）——单 Agent 的性能天花板，本质上是它"能花出去的 token 总量"的天花板。动态派生就是把"能花的 token"从一个窗口扩展为 N 个窗口的工程手段。

但也要先泼一盆冷水：拆分不是免费的。Cognition（Devin 团队）在《Don't Build Multi-Agents》中记录的反例同样真实——当决策被过度分散、上下文在 Agent 之间传递不充分时，多个 Agent 会做出互相矛盾的隐式决定，系统反而比单 Agent 更糟。所以正确的姿势不是"要不要派生"的二选一，而是先确认任务满足派生的准入条件。

准入判断：什么样的任务才配得上派生

准入条件可以收成四条，且必须同时成立。信息量超过单窗口，或所需推理步数远超单 Agent 预算，这是容量条件；任务能切成相互独立的子任务（广度检索、批量同构处理、多视角审查），这是并行条件；任务价值足以覆盖约 15 倍的 token 开销，这是经济条件；各子任务的决策不需要实时共享全量上下文，这是耦合条件。四条里任何一条不成立，都应该先留在单 Agent 方案里——实测数据显示，步骤少于 4 步且无可并行项的流程，多 Agent 版本花 3 倍的 token 却拿不到任何质量提升。

二、架构演进的三个阶段

多 Agent 协作架构走过三代，每一代解决的都不是同一个问题。第一代以微软 AutoGen 为代表，是对话驱动协作：把系统拆成 Assistant Agent（负责生成方案）和 User Proxy Agent（负责执行与确认），两个角色通过多轮对话来回推进。它的贡献是证明了"分工对话"可行，但协作介质是对话本身——计划散落在聊天记录里，话题容易漂移，收敛全靠运气。

第二代是 Anthropic 提出的 Orchestrator-Workers（编排器-工人）模式：编排器即负责拆解任务、分发子任务并汇总结果的中心节点。编排器先静态地把大任务拆成子任务，再分发给一批并行 Worker，最后聚合。这一代有了明确的中心指挥，但 Worker 的数量与分工在设计时就固定了，任务中途冒出的新方向无法临时加派人手。

第三代以 Claude Code 为代表：主 Agent 在 while-true 主循环中，通过一个专门的 agent tool（Task 工具）在运行时动态派生子 Agent。主 Agent 每一轮循环都重新观察任务状态表，决定"现在需要再开几个子 Agent、各自干什么"，子 Agent 数量随任务需要动态增减。Anthropic 在 2026 年发布的 Dynamic Workflow 更进一步：让主 Agent 直接写出一段编排脚本来调度上百个并行子 Agent，并引入独立的验证 Agent 做对抗性交叉审查。

为什么第三代一定要"动态"？因为静态拆解有一个无法回避的假设：编排器在开工前就能看清全部子任务。而研究、大规模迁移、全库审计这类任务的特征恰恰是"边做边发现"——某个子 Agent 的中间发现可能要求开辟全新的调查方向。Claude Code 团队还观察到，长时间在单一上下文里工作的模型会出现三种特定退化：代理惰性（复杂任务做到一半就宣布完成，比如 50 项安全检查只做了 35 项）、自我偏好偏差（让模型审查自己的产出时倾向于给好评）和目标漂移（多轮压缩后逐渐忘记原始约束）。把任务切成多个独立上下文的子 Agent，正是同时对抗这三种退化的手段。

生产案例 · Anthropic 研究系统：Anthropic 用 Claude Opus 4 作主 Agent、Claude Sonnet 4 作子 Agent 构建的多智能体研究系统，在内部研究评测上比单个 Opus 4 高出 90.2%；并行运行 3~5 个子 Agent 并把复杂查询切分为独立调查方向后，复杂研究任务的耗时缩短约 90%（小时级降到分钟级）。代价同样直白：多 Agent 系统的 token 消耗约为普通对话的 15 倍——只有任务价值足够高时才划算。
生产案例 · Claude Code Dynamic Workflow：Anthropic 公开的标志性案例是把 Bun 运行时约 75 万行代码从 Zig 迁移到 Rust，动态工作流编排数百个并行子 Agent，11 天完成，测试通过率 99.8%。相关复盘给出的判断是：整套架构里真正属于"AI 决策"的逻辑只占约 1.6%，其余约 98.4% 都是调度、隔离、恢复、验证等基础设施工程——动态派生系统的难度从来不在模型，而在模型之外的工程。

三代架构的分水岭不是"能不能协作"，而是"计划由谁持有、计划能不能在运行时生长"——从对话协商，到静态拆解，再到主循环里边看状态边派生。

三、派生机制：状态表、工具孵化、隔离运行

把"动态派生"拆开，核心机制只有三件事：中心化的任务状态表、工具调用式的孵化、完全隔离的运行环境。三者缺一，派生就会退化成混乱。

中心化任务状态表：全局唯一的事实源

任务状态表是整个系统的"唯一大纲"：每个子任务一行，带状态标记（待分配 / 进行中 / 已完成）和独占的数据域。主 Agent 每一轮循环先读表——哪些任务还空着、哪些在做、哪些做完了——再决定派生谁；子 Agent 完成后只把结果写回自己那一行。状态表解决了多 Agent 系统的头号混乱源：没有它，子 Agent 不知道别人做到哪了，重复劳动和漏项都靠猜。Anthropic 的研究系统甚至把研究计划直接存到外部 Memory 里，因为计划本身也可能超过 20 万 token 的窗口——状态必须落在上下文之外，这是中心化状态表的深层理由。

工具调用孵化：一次 agent tool 调用 = 一个新生命

派生的动作本身被设计成一次普通的工具调用。以 Claude Code 为例，其核心工具只有八个：Bash、Read、Edit、Write、Grep、Glob、TodoWrite，以及负责派生的 Task 工具。主 Agent 在循环中生成一个 Task 调用，参数里携带任务定义与必要上下文，运行时随即孵化出一个全新的子 Agent 实例。这次调用要经过权限门的 Deny-First 检查（默认拒绝、白名单放行），子 Agent 可用的工具、模型档位、甚至是否在独立的 git worktree 里工作，都可以在派生时逐一指定——派生参数就是子 Agent 的"出生契约"。

隔离运行：子 Agent 是一个全新的宇宙

每个子 Agent拥有完全独立的四件套：独立的实例 ID、独立的消息历史、独立的上下文窗口、独立的工具权限。这种上下文隔离——即子 Agent 的窗口与主 Agent、与其他子 Agent 完全不相通——是整个架构的支点：它让每路调查不会被别路的中间产物污染，也让主 Agent 的窗口免于被过程信息淹没。子 Agent 看不到主 Agent 的对话记录，也看不到其他子 Agent 的存在；它跑完自己的完整循环后，只有最终摘要会返回给主 Agent，中间的所有推理与工具调用都不会回流。Anthropic 把这种设计的意义概括为"关注点分离"：不同的工具、不同的提示词、不同的探索轨迹，消除了路径依赖，让每路调查都能独立深入。而主 Agent 的窗口因此始终只装"结论级"信息，保持可继续调度的轻盈状态。

Claude Code 的早期设计把隔离做到了极致：Task 工具派生的子 Agent 嵌套深度为 1——子 Agent 不能再派生子 Agent，且只回传摘要。2026 年的新版本把嵌套上限放宽到 5 层，用 SubagentStop 钩子在子 Agent 收尾时对输出做质量门禁，但仍然坚持"隔离 + 摘要回传"这两条底线。这说明业界的共识不是"要不要隔离"，而是"隔离到什么深度"。

派生一个子 Agent，等于开一本全新的空白笔记本，只在扉页写三行字：要做什么、以什么为依据、按什么格式交卷——其余什么都不给。

四、三大铁律：收敛、扁平、状态中心化

动态派生赋予系统"随时开新线程"的能力，也同时打开了三种失控的大门：说太多（子 Agent 回传冗余撑爆主上下文）、生太多（子 Agent 无限繁衍成死循环）、手太长（多个子 Agent 写同一份数据互相覆盖）。三大铁律就是对这三种失控的物理约束——注意是物理约束，写在运行时里强制执行，而不是写在 Prompt 里祈祷模型遵守。

铁律一：收敛重于发散

子 Agent 天然是发散的：它读了 300 个文件、调了 50 次工具、产生了 3 万 token 的过程记录。如果这些全部回流主 Agent，20 个并行子 Agent 就是 60 万 token，主上下文瞬间爆炸。工程解法是强制结构化收敛：扇出（主 Agent 一次性派生多个子 Agent 并行开工）的每一路，回程都必须经过同一个收敛口——子 Agent 的输出必须符合预定义的格式（结论 + 关键事实 + 引用来源），长度被硬性限制，实践中常见的约束是单份摘要不超过 200 token。Anthropic 的说法一针见血：搜索的本质是压缩——子 Agent 的全部价值，就是把海量信息压缩成主 Agent 窗口装得下的那几行最关键的 token。收敛层通常还会叠加一道质量门禁：输出不达标的子 Agent 被打回重写，而不是让脏数据进入汇总。

铁律二：扁平优于嵌套

如果允许子 Agent 再派生子 Agent，系统就获得了指数的繁殖能力：每层派生 3 个，5 层就是 243 个实例，而每一层委派都在压缩传递上下文——传到第 3~4 层时，最深层的 Agent 拿到的信息往往已经不足以完成准确的工作。更糟的是失败传播：子 Agent B 返回一个"看似合理但错误"的结果，父 Agent A 把它当作已验证的事实继续推理，幻觉就沿着调用链向上放大。工程解法是物理限流：全局最大并发数封顶（常见取值如 20），嵌套深度强制为 1 或最多 5，并在每台执行节点上设资源预算——没有背压控制，单机一次性拉起 50 个 Agent 可以在几秒内把内存打爆。

铁律三：状态中心化

并行写是多 Agent 系统最隐蔽的杀手。N 个 Agent 之间潜在的并发交互数是 N(N-1)/2：5 个 Agent 有 10 个潜在冲突对，10 个 Agent 就是 45 个。工程解法有两条：原子级任务划分——每个子任务的输入输出边界清晰到不可能与他人重叠；独占数据域标记——状态表里的每一行只有一个 owner，子 Agent 只能写自己那一行，跨行读取必须走明确的合并策略（如最后写入胜出或多数表决）。

生产事故案例 · 第一个坏掉的是状态存储：某团队的多 Agent 系统在 AWS EKS 上稳定运行 6 个月、日均处理 14,000+ 个工作流，第一个崩溃的组件不是模型，而是上下文存储——两个研究型子 Agent 同时把分析结果写入同一个全局 key，后者直接覆盖前者，下游汇总 Agent 基于残缺数据产出自相矛盾的报告。修复方案是为每个 Agent 提供作用域隔离的快照加显式合并策略。同一系统中另一个教训：编排器在单节点一次性派生 50 个 Agent 且没有任何背压控制，进程几秒内 OOM。

另一个必须警惕的失败模式是级联幻觉：一个真实的案例链条是——知识检索子 Agent 幻觉出"退款窗口已从 30 天延长到 60 天"并给出可信的生效日期，策略子 Agent 基于这个假前提确认客户符合条件，主 Agent 最终自信地给出了错误承诺。幻觉穿过三层 Agent，每一层都信任上一层的输出，最后以"已验证事实"的姿态出现在用户面前。防御手段是：主 Agent 对子 Agent 的结论不做无条件信任，关键事实回源抽查、为回传结果附加置信度分数、必要时引入独立的验证 Agent 做对抗性审查。

多 Agent 系统的死法只有三种：说太多、生太多、手太长——三大铁律不是最佳实践建议，是让系统活下来的物理定律。

五、生产级防线：限流、重试、可观测与评估

铁律保证了架构不失控，但要让动态派生系统真正跑在生产环境，还需要四条防线：预算控制防止单个子 Agent 烧穿资源，幂等重试保证失败可恢复，全链路追踪让问题可归因，评估体系让质量可度量。

预算控制：步数与墙钟双闸门

每个子 Agent 派生时都带着两份预算：最大推理步数与墙钟超时。超预算的子 Agent 被强制终止，其任务在状态表里回退为"待分配"，等待重新派发。生产环境还有一组经验信号值得监控：交接延迟超过 30 秒通常意味着接收方 Agent 在重新探索上游已完成的工作——上下文传递不完整；工具调用保真度低于 80%（反复失败或参数幻觉）意味着 Agent 对工具的理解已经漂移，需要刷新工具说明。这两个信号比错误率更早暴露问题，因为 Agent 的质量退化往往不报错，而是按时返回一个流畅但错误的答案。

幂等重试与断点恢复

子 Agent 失败是常态而非异常：上游 API 限流、模型超时、工具报错都会发生。重试的前提是幂等——子任务携带由任务 ID + 步骤 + 参数哈希派生的幂等键，幂等重试的意思是重复执行同一个子任务时，下游能识别出重复并把副作用去重为零，否则重试一次就多发一封邮件、多创建一条记录。在会话层面，系统应支持从失败点恢复而非整体重来：把每次状态迁移写成只追加的事件日志（如 JSONL），中断后重放日志即可回到断点。Anthropic 在生产化其研究系统时，正是把"从失败点续跑"和"工具失败不整体停摆"列为最先落地的两项能力。

全链路追踪：一根 trace_id 串起所有派生

多 Agent 系统的调试难度来自轨迹分裂：一个最终错误可能源于三层之外某个子 Agent 的中间产物。唯一可行的方案是分布式追踪——主 Agent 派生子 Agent 时把 trace_id 随派生参数传下去，每个子 Agent 的每次工具调用都是一个子 span，最终形成一棵完整的调用树。全链路追踪的"全"字是关键：只要有哪怕一层派生没有传播 trace 上下文，这棵树就断了，"问题出在哪个 Agent 的哪一步"就只能靠猜。

评估体系：LLM-as-Judge 与 Golden Dataset

派生系统的输出质量无法靠单元测试穷举，业界通行两条腿：LLM-as-Judge，即用一个更强的模型对每次最终输出按完整性、准确性、结构质量等维度打分，作为在线质量信号（先校准到与人工判断相关性 ≥ 0.80 再投入使用）；Golden Dataset 回归，即维护一组冻结的历史任务与标准答案，每次改动编排逻辑或提示词后全量回归，确认系统是在进化而不是漂移。没有这两条腿，所谓"优化"只是在掷骰子。

回到全文的核心结论：多 Agent 系统的价值从来不是打造一个超级个体，而是组织一支分工明确的团队。模型的随机性无法消除，但可以通过铁律与防线把它约束成可控的生产力。会写 Prompt 的人很多，能设计出"抗混沌架构"——在模型随时可能犯傻的前提下依然稳定收敛的系统——才是这个领域的真正分水岭。

Q&A

动态派生和静态的 Orchestrator-Workers 拆解，本质区别是什么？
区别在于计划能不能在运行时生长。静态拆解假设编排器在开工前就能看清全部子任务，Worker 的数量和分工在设计时固定，执行中冒出的新方向没有编制可以承接；动态派生则由主 Agent 在每一轮循环中读取任务状态表，根据当前进展临时决定再派生几个子 Agent、各自干什么，子 Agent 数量是任务推进过程中长出来的。对"边做边发现"的任务（开放式研究、大规模迁移、全库审计），静态拆解会在中途失效；但对子任务边界完全已知的流水线，静态拆解反而更省编排开销。
为什么主 Agent 只看子 Agent 的摘要，不让它看完整过程？这不是丢信息吗？
这是刻意的信息压缩，不是信息丢失。子 Agent 的过程记录动辄数万 token，如果回流主 Agent，20 个并行子 Agent 就能把主上下文直接撑爆，整个编排循环随之瘫痪——这正是"收敛重于发散"铁律要防的事。真正有价值的信息在摘要里已经保留：结论、关键事实和引用来源，且摘要受长度与格式契约约束，主 Agent 拿到的是可机械解析、可直接写入状态表的结构化结果。至于细节，并没有真的丢——子 Agent 的完整轨迹留在事件日志和 trace 里，人需要追责或调试时随时可以翻出来，只是不让它进入主 Agent 的决策上下文。
应不应该允许子 Agent 再派生子 Agent？
默认不应该，确有需要时才有限放开。无限制的嵌套派生带来三重灾难：实例数指数级膨胀（每层 3 个、5 层即 243 个）；上下文随每一层委派被压缩一次，传到第 3~4 层时最深层 Agent 拿到的信息已不足以准确干活；失败与幻觉沿调用链向上放大且极难归因。Claude Code 的早期设计干脆把嵌套深度锁死为 1——子 Agent 不能再派生；2026 年的新版本放宽到深度上限 5，但同时配了并发封顶、出口质量门禁和全链路追踪作为配套。工程上的经验是：先把扁平结构跑到极限，只有当任务天然具备递归结构（例如目录树的逐层扫描）时才放开嵌套，且深度、并发、预算一个都不能少。
多 Agent 的 token 开销约为单路对话的 15 倍，怎么判断一个任务值不值得上？
用三个准入条件做联合判断，三者缺一就不上。第一，任务价值足够高，产出的收益能覆盖 15 倍成本——Anthropic 的明确结论是多 Agent 只在"高价值任务"上经济可行；第二，任务可并行拆分，存在多个相互独立的调查方向或同构子任务，例如广度检索、批量文件迁移、多视角审查，串行强耦合的任务拆了只会白付协调开销；第三，信息量确实超过单个上下文窗口，或需要远超单 Agent 的步数预算才能完成。反过来，步骤少于 4 步、无需并行的流程应该老实用单 Agent：实测中一条 3-Agent 流水线要消耗 29,000 token，而等价单 Agent 方案只要 10,000，多付的三倍买不到任何收益。
子 Agent 回传一个自信但错误的结论，主 Agent 怎么防？
核心原则是"结果回来时是声明，不是事实"，具体有三层防线。第一层是选择性回源验证：不追求逐条全验（太贵），而是对影响最终输出的关键事实做抽查，比如子 Agent 报告了某个政策条款，就回源检索一次确认；第二层是置信度分流：要求子 Agent 回传时附带置信度分数，低置信结论强制触发验证，高置信结论直接放行，用验证成本换延迟；第三层是结构性对抗：让验证与生成由不同的子 Agent 承担，甚至引入专门的验证 Agent 做对抗性审查，避免"自己审自己"的自我偏好偏差。一个反面教材值得记住：某客服系统中检索子 Agent 幻觉出"退款窗口已延长到 60 天"，三层 Agent 逐级信任，最终以已验证事实的姿态给了用户错误承诺。
中心化任务状态表和让 Agent 之间自由对话协商，差别在哪？
差别在"事实的唯一性"。自由对话模式下，计划与进度散落在多对多的聊天记录里，每个 Agent 对全局的理解都是局部且有版本的，谁做到哪了、哪些任务还空着全靠互相问，重复劳动、漏项和话题漂移是必然产物——这正是第一代 AutoGen 对话驱动架构的主要痛点。状态表模式则规定全局只有一份大纲：每个子任务一行，带状态标记和唯一 owner，主 Agent 每轮循环读表决策，子 Agent 只写自己那一行。它带来三个性质：决策依据唯一（不存在版本分歧）、冲突面有界（每行只有一个写者）、进度可观测（人和监控系统都能直接读表）。代价是灵活性略低——所有交互必须走表的协议，但这正是可控性买来的方式。
如果资源有限，第一批只能建三条防线，应该选哪三条？
选"步数/墙钟双预算"、"摘要强制限长的收敛层"和"一根贯穿全链路的 trace_id"。理由按止血优先级排：双预算是保命闸，子 Agent 死循环和 token 烧穿是动态派生系统最先发生的事故，没有它任何一次失控都能直接打穿账单；收敛层是主循环的存活条件，不限长的回传会让主上下文在几个并行批次内溢出，编排能力归零，而且这条防线实现成本极低——一份输出格式契约加长度校验即可；全链路追踪是事后止血的唯一手段，多 Agent 系统的错误往往来自三层之外某个中间产物，没有 trace 树，排障就是纯粹的猜测。幂等重试、评估体系、背压限流虽然也重要，但它们防的是"变坏"，前三条防的是"猝死"。
已有的单 Agent 系统想引入动态派生，需要推倒重写吗？
不需要，而且不建议。动态派生是在原有主循环上加装三样东西，不是换架构：第一，把任务的进度从"模型脑子里的隐式状态"搬进一张显式的中心化状态表，这一步不改任何执行逻辑，先让进度可见；第二，在工具集里加一个派生工具（agent tool），先只允许派生一种最同构的子任务（例如"检索并摘要一个信息源"），把出生契约、摘要限长、双预算这些约束都封装在这个工具的运行时里；第三，把 trace_id 的传播接进现有日志体系。原有的单 Agent 循环保持不变，作为不满足准入条件任务的默认路径。按这个顺序加装，每一步都可独立验证、独立回滚；反过来推倒重写的团队，通常会在第一条防线上就把工期耗尽。
