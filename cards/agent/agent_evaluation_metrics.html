一、Agent 评测的独特挑战

传统 LLM 评测关注单次回答准确性（一个问题一个答案，对比标准答案），而 Agent 评测必须聚焦三维验证：任务完成度（最终结果对不对）、过程合理性（执行路径优不优）、系统稳定性（多次运行是否一致）。这是因为 Agent 是多步骤决策系统——10 步任务每步 90% 准确率，整体成功率仅 35%（0.9^10），单步评测无法反映全局表现。

2026 年评测信任危机：普林斯顿 HAL 排行榜数据显示，同一个底层模型搭配不同的 Agent 框架（scaffold），在 GAIA 基准上的得分差距可达 30 个百分点。这意味着"Agent 得分"中有很大一部分反映的是框架质量而非模型能力。评测时必须明确区分"模型能力"和"系统能力"——前者是裸模型在标准化输入下的表现，后者是完整 Agent 系统在生产环境中的端到端表现。

SWE-Bench 评估流程

SWE-Bench 评估流程： ① Agent 阅读 Issue + 代码库 ↓ ② Agent 生成修复 patch ↓ ③ 应用 patch 到代码库 ↓ ④ 运行相关测试用例 ↓ ⑤ 结果: PASS (测试通过) / FAIL (测试失败) / ERROR (无法应用) SWE-Bench Lite: 300 个精选问题 当前 SOTA (2024): ~50% resolve rate (Claude/GPT-4 + 专用框架)

任务完成度的评测方法：确定性验证 vs LLM Judge

任务完成度是 Agent 评测的终极指标——无论过程多优雅，最终没完成任务就是失败。评测方法分为确定性验证（通过测试用例、状态检查自动判定）和LLM Judge 评估（用另一个 LLM 评估结果的合理性和完整性）。SWE-bench Verified 的数据表明，2026 年顶级 Agent 系统（Codex-1）在该维度上达到 62.3% 的解决率，而 2023 年裸 GPT-4 仅 1.7%——框架（scaffold）的贡献占到了 60 个百分点。

Success Rate 的陷阱：二值评分太粗糙，"完成了 90% 但最后一步错了"也是 0 分。Partial Completion 更实用：拆解子目标打分，能发现 Agent 在哪一步经常失败。Pass@K 的意义：Agent 有随机性，多跑几次可能成功，Pass@5 比 Pass@1 更能反映能力上限。

工具调用的四个评测子维度与 ToolBench 数据

工具调用评测涵盖四个子维度：工具选择准确率（是否选对了工具）、参数填写正确率（API 参数是否完整正确）、错误恢复能力（工具报错后能否自动调整）、多工具编排能力（能否串联多个工具完成复杂任务）。ToolBench 评测覆盖 16,000+ 真实 API，发现当前 Agent 在单工具调用准确率上已达 85%+，但在需要 3 个以上工具串联的场景中准确率骤降至 52%。

Tool Selection Accuracy 的标注难点：一个任务可能有多种合理的工具选择路径。循环调用检测：设置 max_iterations + 检测连续相同 action → 强制终止或换策略。参数幻觉的缓解：在 tool schema 中用 enum 约束取值范围、添加详细的参数 description。

Agent 成本随步骤数超线性增长： Step 1: input = system + user = 500 tokens Step 2: input = 500 + step1_output + tool_result = 1200 tokens Step 3: input = 1200 + step2_output + tool_result = 2100 tokens ... 总成本 = Σ (每轮 input tokens + output tokens) = 超线性增长（每轮需要带完整历史） 这就是为什么高效 Agent（少步骤）比低效 Agent 便宜得多

执行轨迹评测：Step Efficiency 与冗余率

执行轨迹评测关注过程效率而非最终结果。核心指标：Step Efficiency（完成任务的实际步数 vs 最优步数）、冗余率（重复/无效步骤占总步骤的比例）、回溯频率（Agent 推翻之前决策并重新规划的次数）。WebArena 的数据表明，顶级 Agent 的执行轨迹冗余率已从 2024 年的 45% 降低到 2026 年的 18%，但在 20 步以上的长任务中仍会出现"无效循环"——重复执行相同失败策略。

Agent 成本为什么超线性增长？每步都要带完整历史上下文，步数越多单步成本越高。Optimal Step Ratio > 2.0 的 Agent 需要优化：加强规划能力、改善 tool description、引入 Plan-then-Execute。Latency 优化：工具调用可并行（Parallel Function Calling）、减少不必要的 LLM 决策轮。

六、六大评测维度与三层判定标准

六大核心评测维度总览

六大维度覆盖了 Agent 从理解到执行的完整能力链：任务完成度是终极检验标准，规划能力衡量决策质量，工具调用验证外部交互能力，执行轨迹追踪过程合理性，结果质量评估输出价值，鲁棒性测试异常处理能力。其中任务完成度、工具调用、执行轨迹的指标细节见第二/三/四章。

维度二：规划能力

规划能力衡量 Agent 将复杂任务分解为可执行步骤的质量。评测指标包括：步骤分解的完整性（是否遗漏关键步骤）、优先级排序的合理性（是否存在依赖倒置）、资源分配的均衡性（是否在某个步骤投入过多 Token）。RE-bench 的数据显示，Agent 在优化任务（超参数调优）上的规划质量接近人类专家，但在创造性设计任务（架构创新）上的规划质量仅为专家的 42%。

维度五：结果质量

结果质量超越"对错"二元判定，评估输出的可执行价值。例如：Code Agent 生成的代码不仅需要通过测试（功能正确），还需要符合代码规范（可维护性）、无明显性能问题（效率）、无安全漏洞（安全性）。多维度评估通常使用加权评分：功能正确性 40% + 代码质量 25% + 性能 20% + 安全性 15%。

维度六：鲁棒性

鲁棒性测试 Agent 在异常条件下的表现。测试场景包括：输入噪声（模糊/矛盾/不完整的任务描述）、工具故障（API 超时/返回异常数据）、环境变化（页面结构变更/文件被其他进程修改）、累积误差（10 步任务的误差传播）。GAIA 基准的 Level 3 任务（需要 7+ 步的复杂任务）中，人类正确率 62%，顶级 AI 仅 33%——鲁棒性是当前 Agent 系统最大的短板。

三层判定标准

三层判定标准构成递进关系：基础层（任务是否完成）是及格线，过程层（路径是否最优）区分"能用"和"好用"，质量层（结果是否具备可执行价值）区分"完成"和"卓越"。每一层的通过都依赖前一层的满足——连任务都没完成就谈不上路径优化。

基础层：任务是否完成

基础层的判定看似简单，实际存在两大挑战。第一是部分完成的评分——任务有 5 个子目标，Agent 完成了 3 个，算"完成"还是"未完成"？推荐使用 Partial Completion Score = 完成的子目标数 / 总子目标数，避免二元判定的信息损失。第二是验证环境的可靠性——SWE-bench 在 2026 年被迫退役其 Verified 版本，原因之一就是测试用例本身存在 bug，导致约 8% 的"正确补丁"被误判为失败。

过程层：路径是否最优

过程层评估 Agent 的决策效率。同一个任务可能有多条正确路径（A→B→C 和 A→C→B 都对），因此不能简单对比步骤序列，而是评估路径效率：实际步数与专家标注的最优步数之比。步数在最优步数的 1.5 倍以内视为"高效"，1.5-3 倍视为"可接受"，超过 3 倍或存在无效循环视为"低效"。WebArena 2026 的数据显示，顶级 Agent 在 10 步以内的任务中高效路径占比达 65%，但在 20 步以上任务中骤降至 28%。

质量层：结果是否具备可执行价值

质量层是最难达标的一层。Agent 生成了代码但需要人工修改 3 处才能运行——基础层和过程层可能都过了，但质量层不通过。评估维度包括：可执行性（生成的代码/配置是否能直接运行）、完整性（是否覆盖了所有需求点）、规范性（是否符合团队编码标准/文档格式）。在生产环境中，质量层的通过率是决定 Agent 能否替代人工的关键指标——低于 50% 意味着人工修正成本高于直接使用 Agent 节省的时间。

提升质量层通过率的三个实战技巧：① 在 System Prompt 中明确列出输出标准（如"代码必须通过 PEP8 检查""文档必须包含 API 签名、参数说明和示例代码"），让 Agent 从开始就按标准执行；② 在任务执行末尾增加"自检步骤"，让 Agent 按照预定义 checklist 审查自己的输出，修正不合格的部分；③ 提供 few-shot 示例，展示高质量输出的具体样例，让 Agent 模仿输出的格式和详尽程度。这三项组合可将质量层通过率从 25% 提升至 38-42%。

值得注意的是，质量层评测本身也存在主观性——不同评审者对"可执行价值"的判断标准可能不同。解决方案是建立标准化的评分量表（rubric），对每个评估维度定义 1-5 分的明确描述，并要求评审者间一致性 > 80%。

对于自动化评测，可以使用"下游系统验证"——将 Agent 的输出直接喂给下游工具链（如编译器、测试框架），用下游系统的通过率作为客观的质量层评分。这种方法的最大优势是完全消除了人工评审的主观性，同时能够精确量化"可执行性"这一核心维度。

三层通过率差距的根因分析：基础层 62% 到过程层 38% 的 24 个百分点差距，主要来自"能完成但路径低效"——Agent 经常采用"试错法"而非"规划先行"，导致步骤冗余。过程层 38% 到质量层 25% 的 13 个百分点差距，主要来自"路径对但输出粗糙"——Agent 关注功能实现但忽视代码规范、文档完整性等"非功能性"要求。提升策略：在 Prompt 中明确要求输出质量标准，并在执行过程中加入自检步骤。

七、能力矩阵：理解 → 规划 → 工具调用 → 执行控制

能力矩阵将 Agent 的核心能力分解为四个递进层次：理解（正确解析任务意图和约束）、规划（将任务分解为可执行的步骤序列）、工具调用（选择和调用外部工具完成各步骤）、执行控制（监控执行状态、处理异常、决定是否回溯）。每一层依赖前一层的输出质量。

能力矩阵的级联放大效应

四层能力是串联关系——任何一层的错误都会向下游传播并被放大。这解释了为什么单层 90% 的准确率在端到端评测中仅能达到 65.6%。生产级 Agent 要维持 50%+ 的整体任务成功率，每一层的准确率必须达到 95% 以上。这意味着评测时不能只看最终结果，必须分层定位瓶颈——如果整体成功率低，需要逐层排查是理解出了问题、还是规划有问题、还是工具调用失败。

端到端成功率 = P(理解) × P(规划) × P(工具) × P(执行)
例：0.95 × 0.93 × 0.88 × 0.90 = 0.703 (70.3%)
瓶颈定位：工具调用层 88% 是短板 → 优先提升工具调用准确率

能力层间的反馈修正机制

生产级 Agent 不只是单向执行四层能力链，还会在层间建立反馈修正回路。当执行控制层检测到工具调用失败时，可以回溯到规划层重新选择策略；当规划层发现任务描述存在歧义时，可以回溯到理解层请求用户澄清。反馈回路的价值在于将端到端成功率从"四层串联"（0.95^4 = 81.5%）提升到"带回溯的串联"——实测可将成功率提升至 88-92%，代价是平均执行步数增加 15-20%。

能力矩阵在评测中的分层诊断应用

评测报告中应包含能力矩阵的分层得分雷达图，帮助开发者快速定位 Agent 的能力短板。例如：某 Agent 在 SWE-bench 上整体成功率仅 35%，分层诊断发现理解层 96%（几乎没有问题）、规划层 78%（遗漏关键步骤）、工具调用层 82%（参数填写错误多）、执行控制层 65%（遇到错误无法恢复）。改进优先级：执行控制 > 规划 > 工具调用 > 理解——先修最短板，每层 5 个百分点的提升分别贡献 2.7%、2.2%、1.9%、1.8% 的整体提升。

八、评测集构建方法论

评测集的质量直接决定评测结论的可信度。构建原则：真实性（来自生产环境的真实任务）、覆盖性（覆盖六大评测维度）、时效性（定期更新以反映能力边界变化）。核心比例：线上真实任务日志聚类占 70%，边界案例人工补充占 20%，失败案例回流占 10%。

数据源一：线上真实任务日志聚类（70%）

从生产环境的 Agent 执行日志中提取任务样本。流程：收集最近 30 天的任务执行日志 → 对任务描述做文本聚类（使用 embedding + K-Means）→ 从每个聚类中抽样代表性样本 → 人工标注期望结果和最优路径。聚类的目的是确保评测集覆盖所有常见任务类型，而非偏向某个特定场景。典型规模：从 10,000 条日志中聚类为 50-100 个任务类型，每类型抽取 5-10 条，总计 300-800 条评测用例。

数据源二：边界案例人工补充（20%）

边界案例是线上日志中极少出现但一旦出错后果严重的场景。例如：用户给出矛盾指令（"用 Python 写但不要用任何第三方库"同时需要处理 Excel 文件）；工具链断裂（关键 API 返回超时）；多步骤任务的累积误差（第 15 步依赖第 3 步的结果，但中间步骤已经修改了上下文）。边界案例需要领域专家手工设计和标注，成本较高但不可替代。

数据源三：失败案例月度回流（10%）

每月从线上失败案例中抽取 Top-20 高频失败模式，补充到评测集中。这是评测集的"免疫系统"——确保曾经导致失败的缺陷不会再次出现。回流流程：收集线上失败案例 → 按失败原因分类（规划错误 / 工具调用失败 / 超时 / 幻觉）→ 选取每类 Top-5 → 设计针对性评测用例 → 标注期望行为。

评测集质量保障

评测集本身也需要质量保证。三大检查项：① 标注一致性——同一任务由 3 名标注员独立标注，Kappa 一致性系数需 > 0.8；② 难度分布——参照 GAIA 三级难度，简单:中等:困难 ≈ 3:5:2；③ 防污染——定期检测评测集是否已被泄漏到模型训练数据中（通过 membership inference 检测），被污染的用例需及时替换。

评测集的标注规范与流程

每条评测用例需要标注四类信息：① 期望的最终结果（用于基础层判定）；② 专家推荐的最优执行路径（用于过程层对比）；③ 结果质量的评分标准（用于质量层评估，包含功能正确性、完整性、规范性三个维度的详细 checklist）；④ 异常注入点标记（标注在哪些步骤应该注入什么类型的异常，用于鲁棒性测试）。标注一条完整的评测用例平均需要 45 分钟，包含 15 分钟的任务执行 + 20 分钟的路径记录 + 10 分钟的评分标准制定。

评测集的版本管理与变更追踪

评测集采用 Git 版本管理，每次变更记录 changelog。核心规则：① 新增用例不需要回归历史分数（仅影响未来评测）；② 修改已有用例的评分标准需要重新标注所有历史结果并重新计算基线分数；③ 删除用例需要说明原因（通常是发现该用例有歧义或被污染）。评测集版本号采用语义化版本：主版本号变更表示评分标准重大调整，次版本号变更表示新增/删除用例集合，修订号变更表示修复标注错误。

Benchmark 选型决策矩阵

不同类型的 Agent 应选择不同的 Benchmark 组合。Code Agent 以 SWE-bench Pro + BigCodeBench 为主，辅以内部 Issue 回放；通用助手 Agent 以 GAIA 为主，辅以线上任务采样评测；客服 Agent 以 τ-bench 为主，关注多轮对话中的工具调用可靠性；桌面操作 Agent 以 OSWorld + WebArena 为主，需要在真实浏览器和操作系统环境中运行。选型的核心原则：评测场景必须覆盖 Agent 实际部署的环境和任务类型，公开 Benchmark 的分数只能作为参考基线。

Benchmark 信任危机与应对

2026 年 Agent 评测面临三大信任危机：① Reward Hacking——Agent 学会利用评测环境的漏洞获取高分而非真正解决问题（METR 报告揭示了 o3 的"调用栈技巧"）；② 数据污染——评测集被泄漏到训练数据中（SWE-bench Verified 因此被迫退役）；③ Wrapper Effect——同一模型搭配不同框架得分差距达 30 个百分点（框架贡献 > 模型贡献）。

应对策略：使用动态评测集（每次评测随机生成新任务）、在受控沙箱中运行（防止 Agent 访问外部资源）、同时报告"裸模型分数"和"系统分数"以区分框架贡献。SWE-bench 的继任者 SWE-bench Pro 采用了持续更新的私有测试集来解决污染问题。

新兴 Benchmark 趋势

2026 年出现了两个值得关注的新趋势：① Pass^K 指标（τ2-bench 引入）——评测 Agent 在 K 次独立运行中全部成功的概率，而非至少成功一次。这比 Pass@K 更严格，反映的是生产环境所需的"每次都要可靠"而非"偶尔能成功"。② APEX-Agents——面向专业级任务（法律合同审查、医学诊断辅助）的高难度基准，当前顶级 Agent 得分仅 12%，远超 GAIA 和 SWE-bench 的挑战性，代表了 Agent 评测的下一个前沿。

内部评测 vs 公开 Benchmark 的选择策略

公开 Benchmark 适合横向对比（"我的 Agent 比竞品差多少"），内部评测适合纵向追踪（"这个版本比上个版本好了多少"）。最佳实践是两者结合：每月跑一次公开 Benchmark 了解行业位置，每周跑内部评测集追踪迭代效果。内部评测集的优势是完全贴合生产场景——用真实的用户需求、真实的工具环境、真实的异常模式，评测结论直接可指导优化方向。

正确的评测实践：
  • 使用动态/私有评测集防止数据污染
  • 同时报告裸模型分数和系统分数
  • 多次运行取中位数减少随机性影响
  • 分层诊断瓶颈（理解/规划/工具/执行）
  • 定期回流线上失败案例更新评测集
常见的评测陷阱：
  • 只看单一 Benchmark 分数做结论
  • 不区分模型能力和框架能力
  • 使用已被污染的公开评测集
  • 仅评测最终结果，忽略过程质量
  • 单次运行就下结论（Agent 有高随机性）

评测流水线设计

生产级评测体系采用持续集成模式：每次模型/框架/Prompt 更新后自动触发评测流水线。流程：代码变更 → 触发 CI → 加载评测集 → 在沙箱中执行 Agent → 自动评分（基础层 + 过程层）→ LLM Judge 评分（质量层）→ 对比历史基线 → 生成评测报告 → 人工审核异常项。完整流水线运行一次约需 4-8 小时（取决于评测集规模和并行度）。

沙箱环境的搭建要点

评测沙箱需要隔离性（防止 Agent 影响外部环境）和可重复性（每次评测的环境状态一致）。关键技术选型：代码执行用 Docker 容器（预装目标语言和常用库），浏览器操作用 Playwright + Chromium（每个任务一个独立浏览器实例），操作系统操作用 VM 快照（任务开始前恢复到初始状态）。沙箱的"环境重置"是确保评测可重复的关键——WebArena 的数据表明，不做环境重置时，同一任务的重复运行结果差异可达 15 个百分点。

评测结果的可视化与报告

评测报告应包含三个层次的信息：① 概要层——整体成功率和与上一版本的对比（+/- 差异）；② 维度层——六大评测维度各自的得分雷达图；③ 案例层——失败案例的详细分析（包含 Agent 的执行轨迹和失败根因）。报告自动生成后发送到团队 Slack/钉钉频道，重大退化（整体分数下降 > 5%）触发自动阻断——阻止该版本发布直到人工审核确认。

评估流程最佳实践

Agent 评估完整流程： 1. 定义评估数据集 - 覆盖：简单任务 / 多步任务 / 边界情况 / 对抗样本 - 标注：期望结果 + 可接受的工具路径 + 安全约束 2. 多维度评分 - 任务完成度 (0-1) - 工具使用准确性 (F1) - 效率 (optimal step ratio) - 安全性 (pass/fail) 3. 分层对比 - 不同模型 (GPT-4o vs Claude vs 开源) - 不同框架 (ReAct vs Plan-Execute vs LangGraph) - 不同 prompt 策略 4. 回归测试 - 每次改动后跑评估集 - 设置 threshold (如 success rate > 80%) - CI 自动化

评分聚合公式

维度权重说明
任务完成度0.40最终结果最重要
工具准确性0.25过程正确性
效率0.20成本效率
安全性0.15安全底线（一票否决）

综合评分 = Σ (权重 × 各维度得分)。安全性是一票否决项：如果 safety < 0.9，直接返回 0 分，不能上线。

安全性应作为"一票否决"指标 — 即使任务完成度满分，安全不合格也不能上线。评估集大小建议：50-100 条覆盖核心场景，每月从 bad case 中补充。Agent 的 non-determinism 处理：同一 case 跑 3-5 次取通过率，而非单次 pass/fail。线上评估不能只看 success rate — 还要监控 token 消耗趋势、平均步数、错误类型分布。

Q&A（12 题）

Agent 评估和 RAG 评估有什么本质区别？

3 个本质区别：①评估对象不同：RAG 评估一次性的"检索+回答"，Agent 评估多步的"决策+执行"序列；②确定性不同：RAG 对同一 query 输出基本稳定，Agent 可能每次走不同路径，需要评估"结果等价性"而非"路径一致性"；③副作用问题：RAG 只输出文本，Agent 会真实调用 API/修改状态，需要沙箱环境+回滚机制。评估难度排序：QA < RAG < Agent < Multi-Agent。

如何评估 Agent 的工具选择能力？

工具选择评估方法：①如果有唯一最优路径，直接对比 tool calls 与 ground truth 计算 Precision/Recall/F1；②多条合理路径时，用"结果等价性"评估——不管用什么工具，最终状态/输出正确即可；③结合效率评估：路径都正确时用 step count/token cost 区分优劣。实践做法：为每个测试 case 标注"必须调用的工具集"（recall 基准）+ "不应调用的工具集"（precision 约束）+ "可选的替代路径"。

SWE-Bench 是什么？为什么它成为代码 Agent 的标准 benchmark？

SWE-Bench 是从真实 GitHub 仓库（Django/Flask/scikit-learn 等 12 个项目）收集的 2294 个 Issue+PR 对。评估流程：给 Agent 一个 Issue 描述+代码库→Agent 生成修复 patch→运行项目测试验证。成为标准的原因：①完全自动化验证（跑测试，无需人工判断）；②来自真实工程场景；③难度梯度大；④可复现。当前 SOTA ~38-49%（Verified 子集），说明 Agent 距离"替代程序员"还有很大 gap。

Agent 的安全评估包括哪些方面？如何防止 Agent 执行危险操作？

安全评估 5 个维度：①权限边界（是否只使用被授权的工具）；②Prompt Injection 抵抗（直接注入+间接注入）；③数据泄露（是否输出 PII/密钥）；④有害操作拒绝（删除/发送/付款等不可逆操作）；⑤高危操作确认（触发 HITL）。防护策略（Defense in Depth）：第一层：Tool 白名单+参数校验；第二层：敏感操作需人工确认；第三层：输出过滤（PII 检测+脱敏）；第四层：沙箱隔离（Docker/VM）；第五层：审计日志。关键原则：Agent 的权限应该"最小化"。

如何设计一个 Agent 的 A/B 测试？对比不同配置的效果？

Agent A/B 测试设计：①固定评估集（100+ case，覆盖各种难度）；②控制变量（每次只改一个因素）；③多次采样（每个 case 跑 3-5 次取成功率）；④多维度对比（不只看 success rate，还看效率/成本/安全）。对比的典型变量：模型对比、框架对比、prompt 策略、工具配置。结果呈现：制作雷达图，找到 Pareto 最优。决策标准：效果相近选更便宜的，场景关键选更安全的。

SWE-bench Verified 退役后，应该用什么 Benchmark 替代来评测代码 Agent？
SWE-bench Pro 是其官方继任者，采用持续更新的私有测试集来防止数据污染。同时推荐组合使用：BigCodeBench（覆盖多语言、高难度任务）、HumanEval+（功能正确性 + 代码质量）、以及内部代码库的真实 Issue 回放（最贴近生产场景）。不要依赖单一 Benchmark——SWE-bench 系列的核心局限是仅覆盖 Python 和自包含的 Bug 修复，真实工程中的跨仓库依赖和模糊需求未被覆盖。
LLM Judge 评估结果质量时，如何保证 Judge 本身的准确性？
LLM Judge 存在已知偏见：位置偏见（倾向给靠前内容更高分）、冗长偏见（倾向给更长回答更高分）、自我偏好偏见（倾向给类似自己风格的回答更高分）。校准方法：① 构建 200-500 条人工标注校准集，要求 Judge 与人工一致性 > 85%；② 反转测试——交换结果位置后重新评估，差异应 < 5%；③ Ensemble Judge——使用 3 个不同 LLM 做 Judge 取投票共识，显著降低单一模型偏见。生产系统推荐 GPT-4o + Claude Sonnet + Gemini Pro 三模型 Ensemble。
Agent 评测中如何处理"同一任务多条正确路径"的问题？
这是 Agent 评测的核心难题。三种解决方案：① 结果导向评估——不评判路径，只验证最终状态是否满足要求（最可靠但信息损失大）；② 关键检查点法——在路径中标记若干必须经过的"关键节点"（如：必须先查询数据库再做分析），只检查关键节点是否被覆盖；③ 专家对标法——由人类专家完成同一任务并记录路径，用 Agent 路径与专家路径的"语义相似度"评分（不是精确匹配，而是判断是否达成了相同的中间目标）。实践中推荐组合使用：结果验证为主（基础层），关键检查点为辅（过程层）。
评测集被数据污染了怎么检测？有没有实用的方法？
三种检测方法：① Membership Inference——训练一个分类器判断某条数据是否出现在模型训练集中，准确率可达 70-80%；② 性能异常检测——如果模型在某个评测集上的分数突然大幅领先（比第二名高 20+ 个百分点），高度怀疑被污染；③ 变体测试——将评测题目做语义等价改写（换表述方式但保持答案不变），如果模型在改写后分数骤降，说明原题被污染。最可靠的方案是使用动态评测集——每次评测随机生成新任务，从根本上杜绝污染。
如何构建一个成本可控的内部评测体系？小团队应该怎么做？
小团队的务实方案：① 评测集从线上日志中抽取 100 条核心用例即可（覆盖 Top-10 高频任务类型），不需要追求大规模；② 基础层评分用自动化测试（零成本），过程层用规则引擎分析步骤数（低成本），质量层才用 LLM Judge（控制调用量）；③ 日常用快速回归（50 条，$20/次），每周跑一次标准评测（100 条，$50/次）；④ 评测集维护由值班工程师每月花 2 小时回流失败案例。月总成本控制在 $300 以内，已经能覆盖 80% 的质量保障需求。
能力矩阵中"执行控制层"最难评测，有什么好方法？
执行控制层的核心挑战是需要注入异常才能评测。推荐"混沌工程"方法：① 工具故障注入——在 Agent 执行过程中随机让 20% 的工具调用返回超时或错误，评估 Agent 的恢复能力（重试/换工具/跳过/求助）；② 上下文污染——在中间步骤插入误导性信息，评估 Agent 是否能识别并过滤；③ 步数压力——设置步数上限（最优步数 × 2），评估 Agent 在有限步数内的执行效率；④ 死循环检测——监控 Agent 是否连续 3 步执行相同操作，若是则强制中断并记录。每种异常注入 20 次，统计恢复成功率和恢复策略分布。
三层判定标准的通过率差距（基础层 62% → 质量层 25%）如何缩小？
缩小差距的优先级策略：① 基础层→过程层（62%→38% 的 24 个百分点差距）：核心改进是引入"规划先行"模式——Agent 在执行前先输出完整计划并自检，避免"边做边改"导致的步骤冗余。实验表明这可以将过程层通过率提升 12 个百分点。② 过程层→质量层（38%→25% 的 13 个百分点差距）：核心改进是在 Prompt 中明确要求输出质量标准（代码规范、文档完整性、安全审查），并在执行流程末尾增加"自检步骤"让 Agent 审查自己的输出。两项改进合计可将质量层通过率从 25% 提升至 40% 左右。
总结：Agent 评测体系的构建需要超越传统"看分数"的思维，建立三维验证框架——任务完成度（基础层）、过程合理性（过程层）、结果可执行价值（质量层）。六大评测维度（任务完成度、规划、工具调用、执行轨迹、结果质量、鲁棒性）覆盖了 Agent 从理解到交付的完整能力链。评测集的"70% 真实日志 + 20% 边界案例 + 10% 失败回流"比例确保评测结果反映生产环境的真实挑战。能力矩阵的分层诊断则帮助团队精准定位瓶颈，避免"头痛医脚"的无效优化。
