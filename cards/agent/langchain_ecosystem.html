A06 · LangChain 生态全景

LCEL / LangGraph / LangSmith — 从原型到生产的完整工具链

LangChain 不只是一个库——它是一个从原型到生产的完整生态系统。按复杂度选工具：简单管道用 LCEL，Agent 用 LangGraph，观测用 LangSmith。

一、LangChain 全景

LangChain 生态的六大组件：

组件定位核心功能
langchain-core基础抽象层Runnable 接口、消息类型、回调系统
LCEL链式编排语言管道符串联模型/检索器/Prompt 模板
LangGraph有状态 Agent 编排状态图、循环、条件分支、持久化
langchain-community第三方集成700+ 模型/向量库/工具的适配器
LangSmith可观测性平台Trace、评估、Prompt 管理、A/B 测试
LangServe部署工具一键部署为 REST API + Playground
按需使用：不要安装整个 langchain 包。按需引入 langchain-core、langgraph、具体集成包，减少依赖和版本冲突风险。

二、LCEL：链式表达式语言

用管道符 | 把 AI 组件像乐高一样拼在一起——输入流过每个组件，逐步被加工成输出。

LCEL 的核心思想：所有组件都实现 Runnable 接口（invoke / stream / batch），通过管道符串联成 Chain。

RAG Chain 数据流

LCEL RAG Chain 数据流: 用户问题 │ ▼ ┌──────────────┐ │ Retriever │ 向量检索 → Top-K 文档片段 └──────┬───────┘ │ ▼ ┌──────────────┐ │Prompt Template│ 文档 + 问题 → 填充到模板 └──────┬───────┘ │ ▼ ┌──────────────┐ │ LLM │ Prompt → 生成回答 └──────┬───────┘ │ ▼ ┌──────────────┐ │Output Parser │ 原始文本 → 结构化输出 └──────────────┘

LCEL 三大优势

优势说明
原生流式链中任何组件都支持 streaming，Token 级流式输出自动传播
自动批处理batch() 方法自动并行处理多个输入，无需手写并发逻辑
自动重试内置重试和降级机制，LLM 调用失败时自动重试
LCEL 适用边界：适合线性管道（DAG 结构）——输入 → 处理 → 输出，没有循环。如果任务需要循环（如 ReAct Agent）、条件分支、或持久化状态，应该使用 LangGraph。

三、Agent 与 Tool Calling

LangChain 的 Agent = LLM + Tools + 决策循环——LLM 决定用什么工具，工具返回结果，LLM 再决定下一步。

创建 Agent 的核心要素

要素说明
Tool包含名称、描述和执行函数。描述质量直接影响工具选择准确率
bind_tools把 Tool 列表绑定到 LLM，让模型知道有哪些工具可用
create_react_agent创建 ReAct 模式 Agent：思考 → 选工具 → 执行 → 观察 → 继续
Tool 描述的重要性：Tool 的描述就是给 LLM 看的"说明书"。模糊的描述（"搜索一些东西"）会导致 LLM 误选工具。好的描述应该明确说明：这个工具做什么、输入什么、返回什么、什么时候该用。类似于写好函数的 docstring。

四、LangGraph：有状态 Agent 编排

当 LCEL 的线性管道不够用时——LangGraph 用状态图让你构建循环、分支、可恢复的复杂 Agent。

核心抽象：StateGraph

概念说明
State整个图的共享状态（TypedDict），所有节点读写同一个状态对象
Node处理节点，接收 State 并返回更新
Edge节点间的连接，支持条件路由（根据状态动态决定下一个节点）
Checkpointer持久化引擎，每次节点执行后自动保存快照。支持断点续跑和 Time Travel

LangGraph vs LCEL

能力LCELLangGraph
循环❌ 不支持✅ Agent 可反复思考和行动
条件分支有限✅ 根据状态动态路由
状态持久化❌✅ 中断后可恢复
Human-in-the-Loop❌✅ 关键节点暂停等待人类确认
LangGraph ReAct Agent 状态图: ┌──────────────┐ │ Agent Node │ LLM 分析状态，决定下一步 └──────┬───────┘ │ 条件路由 ┌────┴────┐ ▼ ▼ ┌────────┐ ┌─────┐ │ Tool │ │ END │ 无需更多工具 → 输出最终答案 │ Node │ └─────┘ └────┬───┘ │ 结果写入 State └──────► 回到 Agent Node（循环）

五、Memory 系统

LangGraph 的记忆系统从简单的消息列表进化到三层记忆架构——短期、长期、语义。

三层记忆模型

记忆层存储内容生命周期典型用途
短期记忆（Checkpoint）当前会话完整状态单次会话中断恢复、Time Travel
长期记忆（Store）跨会话持久化信息永久用户偏好、学习成果
语义记忆长期记忆的向量索引永久语义检索"上次类似问题"
三层记忆在一次对话中的读写路径 ────────────────────────────────────────────────────── 用户消息 │ ▼ ┌─────────────────────────────────────────────┐ │ 组装上下文 │ │ ├─ 短期记忆 Checkpoint ← 当前会话完整 State │ │ ├─ 长期记忆 Store ← 按 user_id 取偏好 │ │ └─ 语义记忆（向量索引）← 检索"上次类似问题" │ └──────────────────┬──────────────────────────┘ │ 超出预算？ ├─ 滑动窗口：只留最近 N 条 ├─ Token 限制：按 Token 数裁剪 └─ 摘要压缩：旧消息 → LLM 摘要 ▼ ┌──────────────┐ │ Agent Node │ └──────┬───────┘ │ 节点执行完 ┌──────────────┼────────────────────┐ ▼ ▼ ▼ Checkpointer 值得跨会话保留？ 产生新结论 写快照 → 写入 Store → 写入向量索引 （断点续跑、 （用户偏好、 （供语义检索） Time Travel） 学习成果） ────────────────────────────────────────────────────── 会话结束：Checkpoint 随会话过期，Store 与语义索引长存

上下文管理策略

策略方式适用场景
滑动窗口保留最近 N 条消息简单对话（N=20）
Token 限制按 Token 数裁剪长对话
摘要压缩LLM 将旧消息压缩为摘要超长对话
实际生产系统通常组合使用多种策略：短期用滑动窗口，跨会话用长期记忆 Store，复杂检索用语义记忆。

六、LangSmith：可观测性与评估

LangSmith 是 LLM 应用的"调试器 + 质量仪表盘"——看到每一步的输入输出，知道哪里出了错。

LangSmith 解决 LLM 应用的核心痛点：不透明。一个 Agent 执行了 5 次工具调用，最终给了错误答案——是哪一步出了问题？没有 LangSmith，你只能猜测。

核心功能

功能说明
Trace完整记录每次调用全链路——LLM 输入/输出、工具调用、耗时、Token 消耗
Evaluation对 Trace 结果运行评估器（准确性、相关性、毒性等），生成质量报告
Prompt HubPrompt 版本管理，像 Git 管理代码一样管理 Prompt，支持 A/B 测试和回滚
Online Evaluation生产环境持续评估，对线上流量自动采样，质量退化时报警
实际价值：不只是"看看日志"——LangSmith 让你能复现任意一次线上调用（Trace → 测试用例）、对比不同 Prompt 版本效果、发现生产 bad case 并定向修复。是 LLM 应用从 demo 到 production 的关键基础设施。

七、LangServe：一键部署

把 LangChain/LangGraph 应用变成 API——一行配置，自动获得 REST 接口 + Playground。

LangServe 将任何实现了 Runnable 接口的组件自动暴露为 REST API，附带：

流式输出（SSE）、输入验证（Pydantic Schema）、内置 Playground、LangSmith 自动集成。

LangGraph Platform 是 LangServe 的升级版，专门用于部署 LangGraph 应用。提供 Cron 任务（定时执行 Agent）、Webhook（事件触发 Agent）、持久化存储等生产级功能。

八、竞品对比

LangChain 不是唯一选择——LlamaIndex 更擅长 RAG，Dify 更擅长低代码，Haystack 更擅长管道。

LangChain 生态使用准则

按需使用

不要安装整个 langchain 包。按需引入 langchain-core、langgraph、具体集成包。

尽早接入 LangSmith

从开发第一天就开启 Trace。早期数据能帮你快速定位 Prompt 和工具定义的问题。

强行用 LCEL 做 Agent

LCEL 适合线性管道。需要循环和状态 → LangGraph。不要强行用 Chain 实现复杂逻辑。

过度依赖抽象层

理解底层 API（OpenAI SDK、向量库原生接口）后再用 LangChain 包装，出了问题能更快定位。

核心要点：LangChain 生态的核心价值是标准化接口（Runnable）和全链路覆盖（从编排到部署到观测）。选择组件时按复杂度分层：简单管道用 LCEL，Agent 用 LangGraph，观测用 LangSmith。同时保持对底层 API 的理解，避免被抽象层"黑箱"困住。

Q&A

什么时候该从 LCEL 换成 LangGraph？
判断标准只有一条：任务是不是单向流过去就结束。LCEL 表达的是 DAG，输入经过检索、模板、模型、解析器一路向前，没有回头路，所以做 RAG 问答、批量摘要这类线性管道最顺手，还能白拿流式和批处理。一旦任务需要"模型看了工具结果再决定下一步"这种循环，或者需要根据状态选择不同分支、需要中断后恢复、需要在关键节点插入人工确认，LCEL 就得靠外层 while 循环硬凑，状态散落在 Python 变量里没法持久化。这时候换 LangGraph，把状态显式建模成 State，循环和分支交给条件边，Checkpointer 负责持久化。经验做法是：先用 LCEL 写原型，等发现自己开始手写循环了，就是该迁移的信号。
Runnable 接口到底解决了什么问题？
它把生态里几百个异构组件统一成同一种调用形态。模型、检索器、Prompt 模板、输出解析器本来各有各的 API，串起来就得写一堆胶水代码；实现 Runnable 之后，它们都提供 invoke、stream、batch 三个方法，于是可以用管道符直接拼接，任意两个组件的接缝都是同一种。更实际的收益在于能力自动传播：链里任何一环支持流式，整条链就支持流式；调用 batch 时框架自动并行，不用自己写并发；重试和降级也统一在这一层。代价是抽象层遮住了底层调用细节，出问题时要能穿透到原始 API 去看，这也是为什么建议先懂 OpenAI SDK 再用 LangChain 包装。
为什么 Tool 的描述写不好，Agent 就一定不稳？
因为工具选择这一步完全由模型读描述来做决策，描述就是模型唯一能看到的说明书。写成"搜索一些东西"，模型无法区分它和另一个检索类工具的边界，就会在两个工具之间反复横跳，或者在根本不该调工具的时候调用。合格的描述要讲清四件事：这个工具做什么、需要什么输入、返回什么结构、什么情况下该用它（最好连"什么情况下不要用"也写上）。可以按写 docstring 的标准要求自己。工具数量多的时候还要注意描述之间的区分度，功能相邻的两个工具如果描述雷同，再好的模型也选不对。
LangGraph 的三层记忆分别在什么场景下用？
短期记忆是 Checkpoint，存的是当前会话的完整状态快照，每执行完一个节点就落一次，生命周期跟着会话走。它的价值在中断恢复和 Time Travel——Agent 跑到第七步崩了，可以从第六步的快照接着跑，也可以回退到任意一步重放。长期记忆是 Store，跨会话持久化用户偏好、历史结论这类信息，生命周期是永久的。语义记忆是在长期记忆之上加向量索引，用来回答"我以前是不是处理过类似的问题"。生产系统一般三层都用：会话内靠 Checkpoint，跨会话读 Store，需要模糊召回时走语义检索。
上下文管理的三种策略怎么选？
滑动窗口最简单，只保留最近 N 条消息，N 取 20 左右适合客服问答这类上下文依赖不强的对话，缺点是窗口外的信息直接丢失。Token 限制比条数限制更精确，按实际 Token 预算裁剪，适合消息长短差异大的长对话，避免几条超长消息就把窗口撑爆。摘要压缩是让模型把旧消息滚动压成摘要再拼回上下文，能在有限窗口里保住远期信息，但每次压缩都是一次额外的模型调用，既加延迟又有信息失真风险，只在超长会话里用。实践中通常是组合：近期消息保原文，远期消息压成摘要，真正的长期事实写进 Store。
为什么建议开发第一天就接入 LangSmith，而不是上线前再补？
LLM 应用最难受的地方是不透明——Agent 调了五次工具最后答错了，没有 Trace 就只能靠猜是哪一步坏的。LangSmith 把每次调用的输入输出、工具调用、耗时和 Token 消耗完整记下来，问题定位从猜测变成翻记录。早期接入的额外价值是数据积累：开发期的 bad case 可以直接转成测试用例，等到要对比两个 Prompt 版本时手里已经有真实样本，而不是临时造几条。上线后还能开 Online Evaluation 对线上流量采样评估，质量退化时报警。等到上线前才补，等于把最需要观测的探索期完整错过。
项目里到底该不该用 LangChain，还是自己拿原生 SDK 写？
看你需要的是标准化接口还是控制力。项目要接多家模型、多个向量库，或者要频繁替换组件，LangChain 的适配层能省掉大量胶水代码，LangGraph 的状态图和 Checkpointer 也不是随手就能写好的。反过来，如果只调一家模型做一件确定的事，引入整套抽象只会增加排障路径。折中做法是按需引入而不是装整个 langchain 包：只拿 langchain-core、langgraph 和用得到的集成包，减少依赖冲突。另外框架选型不是非此即彼——项目九成是 RAG 可以考虑 LlamaIndex，非开发者搭原型 Dify 更快，微软技术栈的企业用 Semantic Kernel 集成更省事。
