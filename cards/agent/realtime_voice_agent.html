文字 Agent 慢一秒，用户只是觉得慢；语音 Agent 慢五百毫秒，用户会以为你没听见，然后重复、加大音量、抢话——于是下一轮的输入本身就坏了。语音链路里延迟不是体验指标，它是正确性指标。

把一个已经跑通的文字 Agent 接上语音，通常会得到一个"每句话都能答对、但没人愿意用第二次"的东西。原因不在模型，而在于语音是一条硬实时链路：它有一个由人类对话本能设定的、不可协商的时间窗口，窗口一破，用户的行为会立刻改变，而改变后的行为会反过来把链路的输入搞坏。这条正反馈是语音工程独有的，文字界面里根本不存在。

本文只讲语音这条链路独有的工程约束，集中在三件事上：延迟预算怎么端到端分配、打断（barge-in）的契约怎么定、状态机怎么切分。通用的流式传输机制——五层链路的结构、断流与重连、增量渲染——不在这里重复，见 ST17 · 大模型流式传输五层方案与生产实战；传输层选型见 P02 · WebSocket 与 SSE 技术对比。同样，Function Calling 与 ReAct 的通用范式在 Agent 板块已有多张专卡，本文只讲它们在语音场景下多出来的那几条约束。

一、语音把延迟从体验问题变成正确性问题

先把那个时间窗口的来源交代清楚，因为后面所有的预算分配都以它为锚。它不是产品经理定的，也不是竞品对标出来的，而是一个跨语言的人类行为常数。

200 毫秒这个数字从哪来

Stivers 等人发表在 PNAS 上的跨语言研究（2009）测量了十种互不相关的语言里的对话轮次交接，发现轮次之间的间隔存在一个稳定的众数，大致落在 200 毫秒量级，且这个模式跨文化、甚至跨手语存在，只有轻微的语言间偏移。同一批数据还给出了另一半结论：什么算"迟了"是有文化校准的——丹麦语和老挝语里 200 毫秒还被主观判为"及时"，日语和泽套语里同样的间隔就已经偏慢了。后续综述普遍把超过 700 到 800 毫秒的间隔标注为会被听者解读成犹豫、勉强甚至冒犯的区间。

这里有一个容易被忽略的机制细节：人类之所以能做到 200 毫秒，不是因为反应快，而是因为预测——听者在对方说完之前就已经根据句法、韵律和语义预判了结束点，并提前准备好了自己的回应。人类不是在"检测到静音后开始组织语言"，而是在"预判到即将结束时开始组织语言"。这一点对工程有直接启示：任何"等静音—再开始处理"的串行实现，先天就比人类慢一个准备周期，而这正是后面要讲的激进端点判定与预生成想要补回来的东西。

沉默在两条链路里的含义完全不同

文字界面有一整套廉价的带外回执手段：消息气泡的"已送达"、"对方正在输入"、骨架屏、光标闪动、进度条。这些东西的工程成本几乎为零，但它们承担了一个极重要的语义功能——把"系统在工作"和"系统没收到"这两种状态区分开。用户看到"正在输入"，就知道等下去是有意义的，于是愿意等一两秒。

语音链路把这套手段全部拿走了。在一通电话或一次语音对话里，你没有第二条通道可以低成本地说"我收到了，正在想"。唯一的输出通道就是音频本身，而音频通道在你还没准备好内容时只能输出静默。于是沉默成了一个二义信号：它既可能表示"在思考"，也可能表示"没听见"，而用户默认按后者理解。

同一个"1.2 秒没有输出"，在两条链路里的含义完全不同 【文字链路】 用户发出问题 │ ▼ ┌──────────────────────────────────────────┐ │ 界面立刻回执：已送达 / 对方正在输入… │ ← 一个近乎免费的 │ 骨架屏 / 光标闪动 / 进度条 │ 带外"我收到了" └──────────────────────────────────────────┘ │ 用户的判断：系统在干活，等着就行 ▼ 1.2 秒后首字出现 —— 完全可接受 【语音链路】 用户说完最后一个字 │ ▼ ┌──────────────────────────────────────────┐ │ （静 默） │ ← 没有任何带外通道 │ 没有"正在输入"，没有进度条， │ 可以先回执一声 │ 唯一的输出通道正好也是"沉默"本身 │ └──────────────────────────────────────────┘ │ 用户的判断：它没听见 / 断线了 / 我说得不清楚 ▼ 用户的动作：重复一遍 → 提高音量 → 换个说法 → 抢话 │ ▼ 链路收到的输入变成：重复语句 / 两人叠音 / 半句 + 半句 │ ▼ ★ 延迟超支不只是"慢"，它污染了下一轮的输入 ★

文字链路里延迟只影响"这一轮用户等了多久"，语音链路里延迟会改变"下一轮用户说什么"。前者是体验退化，可以线性地忍；后者是输入污染，会非线性地放大成识别错误、语义错乱和对话崩溃。

所以预算必须端到端分配，而不是逐段优化

这条正反馈决定了语音链路的优化方式跟文字链路根本不同。文字链路可以逐段优化：谁慢就治谁，各段独立改进，收益能叠加。语音链路不行，因为它有一个全局硬上限——用户感知到的那个 200 到 300 毫秒窗口是端到端的，链路里任何一段多花的时间，都是从别人的额度里抢的。

实践中最常见的失败不是某一段特别慢，而是每一段都"只慢了一点点"：端点判定用了默认的 500 毫秒静音阈值，STT 等了完整的最终化结果才往下传，LLM 用了个更聪明但首字更慢的模型，TTS 等整句文本齐了才开始合成，网络走了一趟跨区域的 HTTP 长连接。每段看起来都在"正常范围"，加起来就是两秒半。没有任何一段该被问责，但产品是坏的。这就是为什么下一节要先把预算表列出来——不列表，就没人知道自己超支了。

二、300 毫秒预算怎么拆

把端到端目标定在 300 毫秒左右，然后倒推每一段能花多少。下面这张表是一个可用的起点，具体数字随供应商、部署方式和语言而变，但结构不变：每一段都必须有明确额度和超时兜底，不能有"能跑多快跑多快"的段。

从"用户说完最后一个字"到"用户听到第一声"的预算瀑布 用户说完最后一个字 │ │ ① 端点判定（VAD + EOT） 50 ~ 150 ms ← 波动最大、最易超支 │ 判断"这句说完了没" 切早=打断用户 │ 切晚=整链变慢 ▼ ┌────────────────────────────────────────────────────────┐ │ ② STT 最终化 50 ~ 100 ms │ │ 增量结果其实早就有了， │ │ 这里付的是"确认不再改"的钱 │ └────────────────────────────────────────────────────────┘ │ │ ┌── 可与 ① ② 重叠：用增量结果提前预热 LLM ▼ ▼ ┌────────────────────────────────────────────────────────┐ │ ③ LLM 首 token（TTFT） 100 ~ 200 ms │ │ 注意是首 token，不是整句 │ └────────────────────────────────────────────────────────┘ │ │ ┌── 可与 ③ 重叠：首句一到就送去合成 ▼ ▼ ┌────────────────────────────────────────────────────────┐ │ ④ TTS 首包（TTFB） 50 ~ 80 ms │ └────────────────────────────────────────────────────────┘ │ │ ⑤ 网络往返 / 抖动缓冲 20 ~ 50 ms ▼ 用户听到第一声 串行相加： 270 ~ 580 ms ← 上界已经破窗 重叠之后： 200 ~ 300 ms ← 目标区间 ★ 结论：300 毫秒不是靠每段都快做到的， 是靠 ②③④ 三段互相重叠做到的 ★

这张图最要紧的信息在最后两行：串行实现的上界必然破窗，能不能达标取决于重叠做得好不好。把各段预算相加得到 270 到 580 毫秒，下界勉强够、上界远远超标；而三处重叠——用 STT 增量结果预热 LLM、LLM 首句一到就送 TTS、TTS 边收边播——能把有效链路压回目标区间。所以设计语音链路时，第一个该问的问题不是"哪段能再快 20 毫秒"，而是"哪两段本来可以并行，我却让它们串行了"。

端点判定是最容易被低估的那一段

五段里波动最大、也最容易被忽略的是第一段。端点判定（endpointing，或称 EOT / end-of-turn detection）要回答一个本质上无解的问题：用户是说完了，还是只是在句中停顿想词？

最朴素的做法是固定静音阈值：检测到连续 N 毫秒没有语音能量就认为说完了。这个方案的问题是它把一个语义问题当成了能量问题，于是无论 N 取多少都是错的：

静音阈值后果典型表现
取小（200-300 ms）句中停顿被误判为说完用户说"我想查一下……嗯……上个月的账单"，系统在第一个停顿处就抢答了
取大（700-1000 ms）整条链路的起跑线被推后用户明明说完了，还要干等近一秒才看到系统开始反应
取中（500 ms）两头的问题都保留一部分大多数默认配置所在的位置，也是大多数语音产品体验平庸的原因之一

更好的做法是把它变回语义问题：语义端点判定用一个轻量模型看已识别出的文本，判断这句话在句法和语义上是否已经完整，再结合韵律特征（句尾音高走向、语速变化）给出结束概率。"我想查一下"在语义上明显未完，即使后面跟了 800 毫秒静音也该继续等；"帮我查上个月的账单"已经完整，200 毫秒静音就足以确认。

这一步之所以值得单独投入，是因为它是唯一一段既能省时间又能提准确率的优化：语义端点判定同时降低了误抢答率和平均等待时长，而后面几段的优化基本都是在延迟和质量之间做交换。回到上一节那个人类对话的机制——人靠预测而非检测来实现 200 毫秒，语义端点判定就是把"检测静音"换成"预判结束"的工程近似。

三个把预算买回来的手法

其一，TTS 边收边播。不要等 LLM 把整句甚至整段生成完再送去合成。按标点或语义边界切出第一个短句就立刻送 TTS，音频首包一到就开始播。这样用户听到的第一声取决于"首句生成时间"，而不是"整段生成时间"，两者可以差好几倍。代价是句间可能出现衔接不自然，需要在切分点选择上做打磨。

其二，让 LLM 的第一句刻意短。在系统提示里明确要求首句是一个短的承接句，把长内容放到后面。这不只是话术技巧——它直接压缩了从"首 token"到"首个可合成完整句"的距离。一句"好的，我看一下您上个月的账单"能立刻出声，而一句以复杂从句开头的长回答会让 TTS 一直等不到可切分点。

其三，用 STT 增量结果预热 LLM。STT 在最终化之前早就有增量假设了。可以在端点判定还没确认时，就拿当前的增量文本去做预填充（prefill），把 KV Cache 先建起来；一旦端点确认、文本最终化，只需补上最后的差异部分就能开始解码。这把第 ③ 段的一部分挪到了第 ① ② 段的时间窗里。代价是增量文本可能被改写，导致预热白费，需要按改写概率决定预热的激进程度。

不要问"我能不能让每段都更快"，要问"我让哪两段白白串行了"。语音链路达标靠的是重叠，不是靠单段极限优化；而唯一值得先砸资源的单段优化是端点判定，因为它是少数能同时改善延迟和准确率的地方。

三、级联式与端到端语音的分歧

上一节的预算表隐含了一个前提：链路是由 STT、LLM、TTS 三个独立组件拼起来的。这叫级联式（cascaded）架构，是目前绝大多数生产语音 Agent 的形态。但还有另一条路：端到端语音模型（speech-to-speech），音频进、音频出，中间不落地成文本。两条路的差别不只是延迟，而是你愿意用多少可控性去换多少自然度。

两条链路的信息流与各自丢掉的东西 【级联式：STT → LLM → TTS】 音频 ──▶ STT ──▶ 文本 ──▶ LLM ──▶ 文本 ──▶ TTS ──▶ 音频 │ │ │ │ │ └─ 韵律由 TTS 重新"猜"出来 │ └─ 可注入业务逻辑 / 工具调用 / 审计日志 │ 每一步都是可读的文本，可观测、可回放 └─ ★ 语气、情绪、重音、犹豫、音量在这里被丢掉 ★ 转成文本后，"行啊。"和"行……啊？"完全等价 延迟：三段叠加，且每段都要等上一段有可用输出 可控：高。文本是通用接口，什么都能插进去 【端到端：speech-to-speech】 音频 ─────────────▶ 单一语音模型 ─────────────▶ 音频 │ ├─ 韵律、情绪、重音全程保留，回应可以带语气 ├─ 延迟更低：不必等文本最终化再启动下一段 │ └─ ★ 中间没有文本落点 ★ 业务规则往哪插？审计记什么？ 出错了怎么复现？工具调用怎么约束？ 延迟：低。少了两次模态转换和两次"等齐" 可控：低。你失去了那个可以随手插桩的文本接口

级联丢掉的是副语言信息

级联架构最容易被低估的损失发生在第一步。STT 的职责是把音频转成文字，而文字这个表示形式先天不承载副语言信息——语气、情绪、重音、犹豫、音量、语速全部在这一步被抹掉。同一段音频，用户是平静地说"行啊"还是不情愿地说"行……啊？"，转成文本后可能是同一个字符串，LLM 看到的输入完全一样，于是回应也完全一样。

这个损失在很多场景里无所谓（查账单、订机票、报工单号），但在客服投诉、情绪安抚、销售沟通这类场景里是致命的：用户传递的最重要信息恰恰不在字面上。部分级联方案会用旁路模型单独做情绪识别，再把标签作为额外字段塞进 LLM 的输入里，这是个务实的折中，但拿到的是离散标签而不是连续的韵律信号，粒度损失依然存在。

端到端丢掉的是插桩点

端到端模型解决了副语言信息的问题，也砍掉了两次模态转换的延迟，但它拿走了工程上最有价值的一样东西：那个位于链路中间、人和程序都能读写的文本接口。级联架构里，业务规则、敏感词过滤、工具调用参数校验、审计日志、离线回放，全都挂在这个接口上。端到端模型里没有这个落点，于是每一项都要重新想办法。

这不是说端到端不能接工具——它可以，主流实现都支持在语音会话里发起函数调用。问题在于约束的强度和可审计性下降了：你很难像在级联链路里那样，在文本层面硬性拦下一个不该发出的请求，也很难在事后精确复现"当时模型到底听到了什么、为什么这么答"。

维度级联式（STT → LLM → TTS）端到端（speech-to-speech）
端到端延迟较高，靠重叠压到目标区间较低，天然少两次模态转换
副语言信息在 STT 处丢失，需旁路补全程保留，回应可带语气
可观测性高，每段都有文本落点可埋点回放低，缺少中间可读表示
业务约束注入容易，文本层面硬拦较难，约束强度与可审计性下降
组件替换可以单独换 STT 或 TTS 供应商整体绑定单一模型
合规与审计成熟，文本日志即证据链需要额外设计留痕方案

选型判断

判据其实很干脆：看你的失败代价是"不够自然"还是"做错了事"。如果链路要动账、要改单、要走审批，要在事后向监管或客户解释每一步，那么可审计性不是加分项而是准入条件，走级联；如果是开放域陪聊、语言练习、导览讲解这类以自然度为核心价值、单次出错代价很低的场景，端到端的体验优势明显。

还有一条混合路线值得考虑：用端到端模型承担对话与语音表现，但把所有有副作用的动作抽出来走独立的、有文本契约的工具链路。这样自然度归端到端，可审计性归工具层，两边各拿一半。代价是架构复杂度上升，以及要处理两条链路的状态一致性。

级联式用一个文本接口换走了用户声音里的情绪；端到端用用户声音里的情绪换回了那个接口。先问自己的场景里"说错话"和"做错事"哪个代价更大，答案就出来了。

四、打断是一个契约不是一个功能

打断（barge-in）是语音 Agent 里最容易被当成"一个功能"来实现、然后在生产里制造出最诡异 bug 的地方。表面上它只要求一件事：用户开口时系统立刻停止播放。真正的难点在第二件事——系统必须知道自己被打断前，用户实际听到了哪些内容。

停口只是第一步，难的是记账

设想系统正在播放一句话："您上个月的账单是三千二百元，其中包含了两笔跨境手续费，我已经帮您标记出来了。"用户在"三千二百元"之后就开口问"跨境手续费是什么"。系统停止播放——功能上没问题。

但服务端的对话历史里，这句 assistant 消息是完整存进去的，因为它是模型一次性生成的。于是接下来发生的事是：模型认为自己已经告知了"两笔跨境手续费，我已经帮您标记出来了"，而用户根本没听到这部分。用户问"跨境手续费是什么"，模型可能回答"就是我刚才提到的那两笔"——用户完全不知道它在说什么。更糟的情况是模型认为某个信息已经交付，于是在后续对话里不再重复关键内容，比如已经播报过的金额、确认码或风险提示。

打断契约：把 response_id 与实际播放毫秒数绑定回报 服务端 客户端 / 播放器 用户 │ │ │ │ 生成 response_id=R7 的完整文本 │ │ │ ──── 音频流 ────────────────▶ │ │ │ │ 开始播放 R7 │ │ │ ──────────────────▶ │ 听到 │ │ │ │ │ │ 开口插话 │ │ ◀── VAD 检出语音 ─── │ │ │ │ │ │ ① 立刻停播（本地做， │ │ │ 不等服务端往返） │ │ │ │ │ ◀── ② 上报打断事件 ──────────── │ │ { response_id: R7, │ │ played_ms: 1840 } │ ★ 这个字段是整个契约的核心 ★ │ │ │ ③ 按 played_ms 把 R7 的文本裁剪 │ │ 到用户真正听到的那部分， │ │ 其余丢弃或标注为未送达 │ │ │ │ ④ 用裁剪后的历史继续对话 │ ▼ ▼ 没有第 ②③ 步会怎样： 历史里存着完整的 R7 ── 模型以为全说完了 用户只听到前 1840 毫秒 ── 用户以为没说 ★ 双方对"已经交付了什么信息"的认知从此永久错位 ★

播放位置契约怎么落地

这个契约有三个必须落实的点。第一，停播必须在客户端本地完成，不能等服务端往返。用户开口到声音停止的可感知时延应当控制在一两百毫秒内，任何跨网络的确认都会让它显得迟钝，用户会以为系统没听见而提高音量重复——又回到第一节那条正反馈。

第二，上报的必须是播放位置而不是发送位置。服务端知道自己发出了多少音频，但那不等于用户听到了多少：抖动缓冲、客户端播放队列、网络传输都会让"已发送"远超"已播放"，差值在弱网下可以到几百毫秒甚至更多。只有播放器知道真相，所以这个数字必须由播放器上报。

第三，裁剪要在文本层面按时间对齐。把 played_ms 映射回文本需要 TTS 侧提供时间戳（多数商用 TTS 支持返回词级或句级时间戳）。拿到映射后，把这条 assistant 消息在历史里替换成用户实际听到的那部分，剩余内容要么丢弃，要么标注成"已生成但未送达"——后者更好，因为模型据此可以主动补说关键信息，而不是假装没生成过。

还要防住误打断

打断做得太灵敏会引出反向问题。人类对话里充满了回应词（backchannel）——"嗯"、"对"、"好的"、"是吗"——它们的功能恰恰是表示"我在听，你继续"，而不是要求对方停下。纯能量 VAD 无法区分这两者，于是用户每嗯一声系统就哑一次，对话变得极其别扭。

常见的处理是给打断加一道判据而不是只看有没有声音：结合语音时长（回应词通常很短）、是否构成完整语义单元、以及环境噪音基线做联合判断。同时要区分噪音源——背景电视声、键盘声、他人说话都可能触发误打断，需要说话人识别或方向性拾音来兜底。这里的取舍是明确的：宁可稍微迟一点打断，也不要频繁误打断，因为前者只是一次轻微的体验瑕疵，后者会让用户彻底不敢正常回应。

生产案例一：打断后历史未裁剪导致的认知错位。
示例场景：一个语音账单查询助手，barge-in 功能实现得很干净——用户开口，音频立刻停播，响应时延约 120 毫秒，体验测试全部通过。上线后陆续出现一类难以复现的投诉：用户坚称系统没有告知某项费用，而后台日志显示该内容明确生成过。
问题：客户端只做了停播，没有回报播放位置，服务端把每条 assistant 消息按完整文本写入历史。于是被打断的长回答里，用户没听到的后半段被系统当成已交付。由于打断在长回答里发生的概率远高于短回答，而长回答又恰好是包含费用明细、风险提示的那些，问题集中出现在最要紧的内容上。更隐蔽的是模型的后续行为：它会用"我刚才提到的那笔费用"来指代用户从未听到的内容，让用户以为系统在胡编。
方案：落实播放位置契约。播放器在上报打断事件时携带 response_id 与 played_ms；服务端用 TTS 的词级时间戳把文本裁剪到实际播放点，未播出部分不删除而是标注为未送达；同时给系统提示加一条规则——历史里存在未送达内容时，若该内容含金额、确认码或风险提示，需在合适时机主动重述。
效果：该场景下这类"系统没告诉我"的投诉基本消失，且因为未送达内容会被主动重述，关键信息的实际触达率反而比打断功能上线前更高。
教训：打断不是一个播放器功能，而是一份跨端契约。只做停播等于让服务端和用户对"已经说了什么"产生分歧，而这种分歧不会报错，只会以"模型答得莫名其妙"的形式泄漏出来，极难从日志里定位。

打断的难点从来不是怎么停下来，而是停下来之后谁来记账。服务端只知道自己生成了什么、发送了什么，唯一知道用户真正听到了什么的是播放器——所以播放位置必须由播放器上报，并且必须回写进对话历史，否则模型和用户会从此活在两个不同的对话里。

五、四状态机与工具调用的静默填充

前面几节的约束加起来，逼出了一个结论：语音 Agent 必须有一个显式的状态机。文字 Agent 可以用"请求—响应"这种无状态模型糊过去，因为用户会老老实实等着；语音 Agent 里用户随时可能插话、工具随时可能超时、播放随时可能被截断，没有显式状态就无法判断某个事件在当前时刻是否合法。

这张图里最容易被实现漏掉的是右下角那条：思考态停留过久时必须主动出声。很多实现把 THINKING 当成一个纯等待状态，结果就是用户在静默里数秒——而第一节已经说过，静默在语音链路里被默认解读为"没听见"。

工具调用期间的静默是体验杀手

文字 Agent 调一个三秒的工具毫无问题，界面上转个圈就行。语音 Agent 调同一个工具会得到三秒纯静默，用户在第一秒末就开始怀疑，第二秒重复问题，第三秒挂断。而这三秒里链路一切正常，没有任何错误可报。

解法有三层，应当叠加使用而不是择一：

第一层，填充语。进入工具调用前先说一句"稍等，我查一下"。这句话的作用不是提供信息，而是把静默替换成一个明确的"我收到了、我在办"的信号，把用户的等待预期从"它是不是坏了"切换成"它在查"。填充语要短、要自然、要有多个变体轮换（同一句话反复出现会显得机械），并且本身必须处于可打断状态——用户在填充语期间插话是完全合理的。

第二层，并行与预取。能在端点判定确认前就启动的工具调用就提前启动。很多查询类工具的参数在用户话说到一半时其实已经确定了，可以基于 STT 增量结果乐观发起，若最终文本改写导致参数变化就丢弃结果重来。这与上一节 LLM 预热是同一个思路：把等待挪进别人的时间窗。多个独立工具必须并行发起，串行调三个各一秒的工具会直接毁掉这一轮。

第三层，超时与降级话术。每个工具都要有明确的墙钟超时，超时后不能沉默也不能干等，要有预设的降级话术："这个查询有点慢，我先帮您看另一部分"或"系统响应比较慢，需要我稍后回电给您吗"。降级话术的设计要点是给用户一个选择，而不是通报一个故障，因为在语音场景里用户无法像文字界面那样自己决定继续等还是关掉页面。

生产案例二：工具静默导致的中途挂断。
示例场景：一个语音订单助手，需要在对话中调用库存查询与物流时效两个接口，两者各自的响应时间中位数约 800 毫秒、尾部可到 3 秒。功能测试全部通过，但上线后发现相当比例的会话在同一个位置中断——恰好是查询发起后的两到三秒。
问题：三处叠加。其一，两个接口被串行调用，中位耗时直接翻倍；其二，调用期间完全静默，没有任何填充；其三，接口偶发的尾部延迟没有超时，最坏情况下用户面对超过五秒的纯静默。用户的实际行为符合第一节那条正反馈：先重复问题，此时 VAD 检出语音触发打断，把正在进行的这一轮整个作废，于是下一轮又要重新查一遍，延迟叠加得更长，最后直接挂断。日志里看到的是"用户主动结束会话"，看不出任何错误。
方案：三层解法一起上。两个接口改为并行发起，中位耗时回到单接口水平；发起前插入一句轮换的填充语，把静默窗口压到几百毫秒以内；给每个接口设 1.5 秒墙钟超时，超时走降级话术，先答已拿到的那部分，另一部分改口播预估或询问是否稍后回复；同时在填充语播放期间保持打断通道开放，用户若插话按正常打断流程处理而不是作废整轮。
效果：该场景下这个位置的中途挂断基本消失，且因为并行化，正常路径的这一轮响应时间也从两秒量级回落到一秒以内。
教训：语音链路里"工具很慢"不会表现为超时报错，而会表现为用户挂断，且日志上归因成用户主动离开。任何超过几百毫秒的静默都必须被某种声音占位——填充语的工程成本极低，是语音 Agent 里性价比最高的一处改动。

文字 Agent 里工具慢是一个性能问题，语音 Agent 里工具慢是一个对话问题：它不会报错，它会让用户挂断，然后在报表上算作用户主动离开。所以思考态不允许静默——链路在忙的时候必须有声音说"我在忙"。

六、可观测性与质量回归

前面每一节都在讲某段时间被谁吃掉了。要能持续地回答这个问题，就必须在链路上分段埋点——只记录端到端总时延的系统，在体验退化时根本无法定位原因，因为总时延只告诉你破窗了，不告诉你是谁破的。

五个必须落到毫秒的时间戳

质量维度不止文字正确

文字 Agent 的评测基本围绕内容正确性。语音 Agent 需要额外一组指标，而且这组指标恰好对应前面几节讲的每一个约束：

  • 打断响应时延：用户开口到声音停止的间隔，直接决定打断是否显得灵敏，应看分位数而非均值
  • 误打断率：因回应词或环境噪音导致的非预期停播占比，与上一项构成一对需要平衡的指标
  • 误抢答率：端点判定在用户句中停顿处误判结束的比例，与平均端点等待时长同样构成一对
  • 静默时长分布：一轮对话内所有超过阈值的静默窗口，这是唯一能提前发现工具慢的指标
  • 未送达内容占比：被打断后生成但未播出的内容比例，过高说明回答普遍太长
  • TTS 断句自然度：边收边播的切分点是否造成不自然停顿，通常需要人工抽样打分

注意其中三对指标都是此消彼长的：打断更灵敏必然误打断更多，端点判定更快必然误抢答更多。所以这些指标不能单独设目标值，必须成对看，并且明确当前产品愿意站在取舍曲线的哪个位置。

回归必须用音频，不能只用文本

最后一条工程纪律：语音 Agent 的回归测试集必须是录音，不能是文本用例。用文本喂进链路中段只能验证 LLM 的行为，而前面几节讲的问题——端点判定切在哪、打断时播放到了哪、噪音是否误触发、TTS 切分是否自然——全都发生在文本之外，文本用例对它们完全不可见。

可行的做法是维护一个录音回放集，覆盖几类容易出事的样本：句中长停顿、回应词插话、真打断、背景噪音、口音与语速极值、以及触发慢工具的问法。每次改动端点判定参数、换 STT 或 TTS 供应商、调整填充语策略时，整集回放并比对上面那组指标。这套东西的建设成本不低，但它是唯一能在改参数时不靠猜的办法——语音链路里几乎每个参数都是取舍参数，没有回放集就只能凭感觉在两个方向上来回摆。

  • 把端到端延迟拆成分段预算表，每段有额度和超时兜底
  • 让 STT 最终化、LLM 首句、TTS 首包三段尽量重叠
  • 优先投入语义端点判定，它同时改善延迟与准确率
  • 打断在客户端本地立即停播，不等服务端往返
  • 上报 played_ms 并据此裁剪对话历史
  • 未播出的关键信息标注为未送达并适时重述
  • 思考态超过阈值就出填充语，填充语本身可被打断
  • 独立工具并行发起，每个都设墙钟超时与降级话术
  • 用录音回放集做回归，成对监控取舍类指标
  • 不要照搬文字链路的"等齐再往下传"的串行实现
  • 不要用固定静音阈值当作端点判定的最终方案
  • 不要只实现停播就认为打断做完了
  • 不要用发送位置代替播放位置写回历史
  • 不要让纯能量 VAD 决定是否打断，回应词会误触发
  • 不要在工具调用期间保持静默，用户会挂断而非等待
  • 不要串行调用多个独立工具
  • 不要只监控端到端总时延，破窗时你会无法定位
  • 不要拿文本用例当语音回归，它对链路两端完全盲视

语音链路的可观测性有一条铁律：凡是与用户感知有关的时刻，都只有客户端知道真相。服务端能看到自己发了什么、发得多快，但看不到用户几时听到、听到了多少——所以首次出声时刻和播放位置都必须由播放器回报，否则你的监控面板会在体验已经崩掉的时候依然一片绿。

Q&A

为什么语音 Agent 的延迟目标是 200 到 300 毫秒，这个数字是怎么定的？
它不是产品目标，而是人类对话的行为常数。Stivers 等人 2009 年发表在 PNAS 上的跨语言研究测量了十种互不相关语言的对话轮次交接，发现轮次间隔存在稳定众数，大致落在 200 毫秒量级，且跨文化甚至跨手语存在。超过 700 到 800 毫秒的间隔会被听者解读为犹豫或勉强。更关键的是人类达到这个速度靠的是预测而非检测——听者在对方说完前就根据句法和韵律预判了结束点并提前准备回应。这意味着任何"等静音再开始处理"的串行实现，先天就比人类慢一个准备周期。
延迟超过预算，除了体验变差还有别的后果吗？
有，而且这是语音区别于文字的关键点。文字界面有"已送达""正在输入"这类近乎免费的带外回执，能把"系统在工作"和"系统没收到"区分开，所以用户愿意等。语音链路只有音频一个输出通道，而这个通道在内容没准备好时只能输出静默，于是沉默变成二义信号，用户默认按"没听见"理解。接下来用户会重复、提高音量、换说法或抢话，链路收到的输入就变成重复语句、叠音或半句拼接。所以延迟超支不只是慢，它污染了下一轮的输入，是正确性问题而非体验问题。
各段延迟加起来已经超过 300 毫秒了，怎么可能达标？
靠重叠，不是靠每段更快。串行相加的典型区间是 270 到 580 毫秒，上界必然破窗。三处重叠能把它压回目标：用 STT 增量结果对 LLM 做预填充，把首 token 的一部分成本挪进端点判定的时间窗；LLM 生成出第一个短句就立刻送 TTS，不等整段；TTS 首包一到就开始播，边收边播。所以设计时第一个该问的不是"哪段能再快 20 毫秒"，而是"哪两段本来能并行却被我串起来了"。
端点判定的静音阈值该设多少？
固定阈值无论取多少都是错的，因为它把语义问题当成了能量问题。取小（200-300 毫秒）会把句中停顿误判为说完，用户说"我想查一下……嗯……上个月的账单"时系统会抢答；取大（700-1000 毫秒）会把整条链路的起跑线推后近一秒；取中（500 毫秒）两头的问题各留一半，这也是多数默认配置的位置。正确方向是语义端点判定：用轻量模型看已识别文本判断句法语义是否完整，结合句尾音高走向等韵律特征给出结束概率。它值得优先投入，因为它是少数能同时降低误抢答率和平均等待时长的优化，其余多数优化都是在延迟和质量间做交换。
级联式和端到端语音模型怎么选？
看失败代价是"不够自然"还是"做错了事"。级联式（STT→LLM→TTS）在中间有一个文本接口，业务规则、参数校验、审计日志、离线回放全挂在上面，可控性和可观测性高，但延迟叠加，且语气情绪重音在 STT 那一步就被抹掉了——同一段音频里平静的"行啊"和不情愿的"行……啊？"转成文本后完全等价。端到端模型保留韵律情绪、延迟更低，但没有中间文本落点，业务约束的强度和事后复现能力都下降。要动账、要审批、要向监管解释每一步的场景走级联；开放域陪聊、语言练习这类以自然度为核心且单次出错代价低的场景走端到端。也可以混合：对话与语音表现交给端到端，有副作用的动作抽出来走独立的、有文本契约的工具链路。
打断功能实现了停播就够了吗？
不够，停播只是第一步，难的是记账。假设系统正在播"账单是三千二百元，其中包含两笔跨境手续费，我已帮您标记"，用户在金额后就插话了。如果服务端仍把这条 assistant 消息按完整文本写进历史，模型就会认为后半段已经交付，之后可能用"我刚才提到的那两笔"去指代用户从未听到的内容，或者因为"已经播过"而不再重复金额、确认码、风险提示这类关键信息。这类 bug 不会报错，只会表现为模型答得莫名其妙，极难从日志定位。所以必须把 response_id 与实际播放毫秒数绑定上报，服务端据此裁剪历史。
为什么打断上报的必须是播放位置而不是发送位置？
因为服务端知道自己发出了多少音频，但那不等于用户听到了多少。抖动缓冲、客户端播放队列和网络传输都会让"已发送"远超"已播放"，弱网下差值可达几百毫秒甚至更多。只有播放器知道真相，所以这个数字必须由播放器上报。同样的道理也适用于延迟埋点：链路终点必须是用户实际听到第一声的时刻，而不是服务端 TTS 首包就绪的时刻，否则监控面板会在体验已经崩掉时依然一片绿。凡是与用户感知有关的时刻，都只有客户端知道真相。
打断做得越灵敏越好吗？
不是，会引出误打断问题。人类对话充满回应词——"嗯""对""好的""是吗"——它们的功能恰恰是表示"我在听，你继续"，而不是要求对方停下。纯能量 VAD 区分不了这两者，于是用户每嗯一声系统就哑一次，对话变得极其别扭。此外背景电视声、键盘声、他人说话也会误触发。处理办法是给打断加联合判据而非只看有没有声音：结合语音时长（回应词通常很短）、是否构成完整语义单元、环境噪音基线，必要时加说话人识别或方向性拾音。取舍方向是明确的——宁可稍微迟一点打断，也不要频繁误打断，因为前者只是轻微瑕疵，后者会让用户不敢正常回应。
工具调用要几秒钟，语音场景该怎么处理？
三层解法叠加使用。第一层填充语：进入调用前先说"稍等，我查一下"，把静默替换成明确的"我在办"信号；填充语要短、有多个变体轮换，并且本身必须可被打断。第二层并行与预取：多个独立工具必须并行发起，串行调三个各一秒的工具会直接毁掉这一轮；参数在用户话说到一半就确定的查询可以基于 STT 增量结果乐观发起，最终文本改写导致参数变化就丢弃重来。第三层超时与降级话术：每个工具设墙钟超时，超时后给用户一个选择而不是通报故障，比如"这个查询有点慢，我先帮您看另一部分"。关键认知是语音链路里工具慢不会表现为超时报错，而会表现为用户挂断，且日志上归因成用户主动离开。
为什么语音 Agent 需要显式状态机？
因为语音场景里事件的合法性依赖当前状态。文字 Agent 可以用无状态的请求—响应模型糊过去，用户会老老实实等着；语音 Agent 里用户随时插话、工具随时超时、播放随时被截断，没有显式状态就无法判断某个事件此刻是否该被处理。监听、思考、说话、被打断四个状态之间有几条硬约束：说话到被打断的迁移必须在客户端本地立即完成；被打断状态必须携带播放位置才能退出；思考态停留超过阈值必须进入填充语而不允许静默等待；填充语本身处于可被打断状态，不能占用打断通道。最容易被漏掉的是第三条——很多实现把思考态当成纯等待，结果用户在静默里数秒。
语音 Agent 的回归测试为什么不能用文本用例？
因为文本用例只能验证链路中段的 LLM 行为，而语音特有的问题全部发生在文本之外：端点判定切在哪里、打断时播放到了第几毫秒、回应词和背景噪音是否误触发、TTS 边收边播的切分点是否造成不自然停顿。这些对文本用例完全不可见。可行做法是维护录音回放集，覆盖句中长停顿、回应词插话、真打断、背景噪音、口音与语速极值、以及触发慢工具的问法，每次改端点判定参数、换 STT 或 TTS 供应商、调填充语策略时整集回放并比对指标。建设成本不低，但语音链路里几乎每个参数都是取舍参数，没有回放集就只能凭感觉在两个方向上来回摆。
语音 Agent 该监控哪些指标，怎么设目标值？
除了内容正确性，还要看六项：打断响应时延（看分位数不看均值）、误打断率、误抢答率、静默时长分布、被打断后未送达内容占比、TTS 断句自然度。关键是其中三对指标此消彼长——打断更灵敏必然误打断更多，端点判定更快必然误抢答更多，回答更长则未送达占比更高。所以它们不能单独设目标值，必须成对看，并明确产品愿意站在取舍曲线的哪个位置。另外延迟侧要分段埋点，至少记录语音结束、端点确认、STT 最终化、LLM 首 token、TTS 首包、用户实际听到六个时刻，只记端到端总时延的系统在破窗时无法定位是谁超支了。
