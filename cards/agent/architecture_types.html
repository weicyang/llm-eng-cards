A04 · Agent 架构类型与选型

Architecture Types & Selection — 七种核心架构 / 核心循环与记忆系统 / Blackboard 与 Route+Skill / 三层复合架构 / 选型决策矩阵

Agent 架构选型的核心矛盾是"灵活性与可控性的对抗"——ReAct 最灵活但最难预测，Graph/Workflow 最可控但最不灵活，中间的五种架构（Plan-and-Execute、Reflection、RAG+Memory、Multi-Agent、Tool Calling）各自在这条光谱上占据不同的位置。选错架构的代价远大于选错模型——一个用 Multi-Agent 解决的简单查询任务，通信成本占总计算的 60% 以上，纯属架构浪费。

一、七种核心架构全景总览

2026 年的 Agent 架构生态已经从"ReAct 一统天下"演化为七种核心架构并存的格局。每种架构解决的是不同维度的问题——从简单的工具调用到复杂的多 Agent 协作，从一次性任务到需要从失败中学习的长期任务。理解它们的关键不在于记住每种架构的定义，而在于理解它们之间的"升级关系"——每种架构都是对前一种架构的某种不足的回应。

Anthropic 2024 年发布的"Building Effective Agents"指南中给出了最务实的建议："从简单提示词开始，用全面的评估来优化，只在简单方案不够用时才引入多步骤 Agent 系统。"换言之，正确的架构是"能通过你评估的最简架构"——过度设计是 Agent 工程中最常见的浪费。

二、Agent 核心循环基石：Observe → Think → Act

Agent 的本质：一个能自主感知环境、做出决策、采取行动并根据结果调整策略的智能体。与传统程序的核心区别是"闭环反馈"——Agent 能观察行动结果，动态调整下一步动作。Agent Loop 是所有架构模式的基石：观察 → 思考 → 行动 → 观察结果 → 再思考……直到任务完成或达到终止条件。所有高级模式（ReAct、Plan-and-Execute、Reflection）都是在这个基础循环上叠加不同的策略。

2.2 Agent 的三个核心组件

Agent 的三个核心组件：①LLM（大脑，负责推理决策）②Tools（手脚，执行具体操作）③Memory（记忆，保持上下文连续性）。没有 Tools 的 Agent 只是聊天机器人；没有 Memory 的 Agent 每轮都是"失忆"的。

三、基础认知架构：工具调用型与 ReAct

工具调用型和 ReAct 是 Agent 世界的"Hello World"——所有复杂架构都建立在这两种基础模式之上。工具调用型解决的是"LLM 如何与外部世界交互"的基本问题，ReAct 在此基础上增加了"推理透明度"——让 Agent 不仅做事，还能解释为什么这么做。

3.1 工具调用型（Tool Calling）：边界明确的简单任务

工具调用型（即"单 Agent"形态，ChatGPT 的工具调用就是这种形态）是最简洁的 Agent 架构——LLM 接收用户输入，直接生成一个或多个 function_call，系统执行工具并将结果返回给 LLM 生成最终回答。没有推理链，没有循环，一次调用解决问题。这种架构适用于任务边界清晰、不需要多步推理的场景：查天气、查汇率、简单数据查询。

它的缺陷集中在一处：思考链爆炸。每一轮对话都必须把完整历史重新发给模型，上下文随轮数线性膨胀；当工具清单超过十几个、任务类型开始混杂时，模型在同一个提示里既要选工具又要管状态，注意力被稀释，经常出现选错工具、漏传参数、把上一个任务的上下文带进下一个任务的问题。

单 Agent 就像一个人同时接十个电话——不是他不够聪明，而是他的"工作台"（上下文窗口）只有这么大。

3.2 ReAct：推理与行动的交织循环

ReAct（Reasoning + Acting, Yao et al. 2022, arXiv:2210.03629）是 Agent 架构的基石范式。它在每一步都插入一个显式的 Thought 阶段——LLM 先推理"为什么要做这件事"，再决定"做什么"，然后观察"结果如何"。三者形成 Thought → Action → Observation 的循环，直到任务完成。ReAct 的革命性在于将 LLM 从"文本生成器"提升为"推理-行动体"。这个结构解决了纯思维链"无法中途获取新信息"的致命伤，同时带来了可调试性：每一步的 Thought 都留在 trace 里，失败时能逐行读出逻辑在哪里断裂，这是许多"一次调用黑盒完成多步"的架构给不了的。

3.3 ReAct 的生产效率数据

2026 年 LangChain 基准测试（LangChain Agent Benchmark）对比显示，在一个标准的 10 步任务上，ReAct 需要约 10 次 LLM 调用（每步一次 Thought+Action），而 Plan-and-Execute 仅需 1-2 次（规划一次+执行阶段按需）。ReAct 的 Token 消耗约为 Plan-and-Execute 的 5-8 倍。ReAct 的任务完成率为 85%，但在 5 步以上的长任务中完成率下降明显。但 ReAct 在探索性任务上有不可替代的优势——当"下一步该做什么"无法预先规划时（如调试未知 Bug），只有逐步推理-观察的循环才能应对。

ReAct 原论文的基准验证同样扎实：在 ALFWorld 基准测试中，ReAct 相比模仿学习和强化学习基线取得了 34% 的绝对成功率提升；在 WebShop 任务上提升 10%。

3.4 ReAct 的 Token 膨胀结构与故障设防

ReAct 的代价写在结构里：每一步都要把之前所有的 Thought/Action/Observation 重新塞进提示，实测中每一步会新增 300~600 个 token 的 scratchpad，总消耗随步数加速增长；超过 15-20 步时上下文窗口压力显著，可能触发截断。

ReAct 第 N 步输入 = 系统提示 + 工具 Schema + 前 N-1 轮全部 Thought/Action/Observation 总 Token ≈ 基础开销 × N + 每步增量 × N(N-1)/2 → 随步数平方级膨胀

这正是 ReAct 不适合长流程的根本原因：十步任务的上下文里躺着九步的历史包袱。生产中还有三种高频故障模式必须提前设防——无限循环（模型反复调同一个工具）、工具参数幻觉（编造不存在的字段值）、上下文撑爆（长观察结果挤掉早期指令）。工程上常见的缓解手段包括：只保留最近 K 轮的完整观察、对旧观察做摘要压缩、以及设置硬性步数上限（生产中必须为 ReAct 设置硬性 max_steps 上限，通常 8-15 步）加循环检测（连续两次调用相同工具和参数即判定为死循环），并配备超时熔断机制。

Oracle Integration 的教训：不设上限的 ReAct 循环中约 12% 的任务会陷入重复调用相同工具的无限循环——max_steps 硬上限与超时熔断不是可选项，而是生产准入门槛。

3.6 生产案例：GPT-4o 调试基准（同任务各 30 次试验）

生产案例（同任务基准测试，GPT-4o，各 30 次试验）：在同一个"修复 Python 模块两个失败测试"的调试任务上，ReAct 平均消耗 2,840 token、耗时 11.2 秒、成功率 73%，单次成功成本 $0.039；Reflection（带自我批评重试）消耗 8,610 token、成功率 93%；Plan and Execute 消耗 4,120 token、成功率 80%；而"Plan 为骨架 + 关键节点 Reflection"的混合方案达到 97% 成功率。结论：ReAct 最快最便宜，但在需要验证信号的任务上会触顶，混合结构才是准确率的天花板。

四、规划与反思：Plan-and-Execute 与 Reflection

如果 ReAct 是"走一步看一步"的探险家，那 Plan-and-Execute 就是"先看地图再出发"的旅行者，而 Reflection 是"做完作业自己检查一遍"的好学生。这三种架构分别解决了 Agent 的三个不同痛点：探索效率（ReAct 的随机性）、全局规划（Plan-and-Execute 的前瞻性）、输出质量（Reflection 的自我纠错）。

范式选择的本质是一个承诺度旋钮：你在执行前愿意锁定多少决策？ReAct 每步都重新决策，Plan-and-Execute 一次锁定全局，Reflection 在跨轮次间积累失败经验——三者分别对应"实时适应"、"前置规划"和"事后学习"三种认知策略。

4.1 Plan-and-Execute：完整计划 → 分步执行 → 动态重规划

Plan-and-Execute 架构将 Agent 的工作分为两个显式阶段。Planner（规划器）接收完整任务描述，输出一个有序的步骤列表——它不需要执行细节，只需要宏观规划。Executor（执行器）逐步执行 Planner 给出的步骤，每步可以是 ReAct Agent 或简单的工具调用。关键增强是Replan 机制——当某一步执行失败或结果不符预期时，Planner 根据已完成的结果重新调整后续计划。

在 Oracle Integration 的实现中，Planner 和 Executor 被建模为两个独立的 Agent：Planner Agent 负责将目标分解为有序步骤列表，Executor Agent（本身是一个 ReAct Agent）严格按步骤执行。Planner 从不接触工具，Executor 从不自行决策——它们将战略与执行彻底分离。上下文管理也因此更高效：Planner 只需要任务描述（短 prompt），Executor 只需要当前子任务的上下文，避免 context window 溢出——这比 ReAct 把所有历史消息塞进一个 context 更省。这里的计划是一等公民——它是一个可检查、可审批、可持久化的工件，而不是藏在对话历史里的隐式意图。这种结构在长程任务上的 token 效率非常突出：子任务执行时不再反复携带规划上下文，长任务可比 ReAct 节省 3~5 倍 token；执行步骤之间没有依赖时还可以并行，进一步压缩延迟。

Plan and Execute 像旅行前做完整攻略：攻略做得好，路上又快又省；攻略本身错了，执行力越强偏得越远——所以必须留一个"发现不对就改攻略"的机制。

它的阿喀琉斯之踵是计划错误全盘失败：如果规划器在第 2 步就埋了错误假设，后面所有步骤都会忠实地把错误放大。工程上的补救是给执行循环加一个反思节点——每步执行完评估结果，置信度达标就继续，不达标且重试次数未耗尽就重规划（replan），重试耗尽则升级人工。没有 replan 闸门的 Plan and Execute，只适合步骤可以预先完全枚举的理想任务。

4.2 动态重规划（Re-planning）的触发机制

静态计划的最大风险是计划过时：当外部环境与规划时的假设不符时（如 API 返回异常、数据格式变化），硬编码的计划就会失效。生产级 Plan-and-Execute 必须内置动态重规划机制：

重规划触发条件触发频率处理策略
步骤执行失败每步检测从失败步骤开始重新规划后续步骤
中间结果偏离预期每步验证比较实际输出与预期输出的偏差，超过阈值触发
外部环境变化事件驱动订阅数据变更事件，异步触发重规划
累积步骤超时定时检测单步超时或总耗时超阈值时重新评估计划

Plan-and-Execute 是"项目经理 + 工程师"模式——PM 写好了 Jira ticket 和 Sprint plan，工程师按 ticket 干活，但如果某个 ticket 阻塞了，PM 需要重新调整后续排期。

Oracle Integration 实践洞见：选择范式不是看任务复杂度，而是看路径可预测性。如果你能在 Agent 启动前就列出需要调用的工具序列——用 Plan-and-Execute；如果你必须看到中间结果才能决定下一步——用 ReAct。这是一个简单但极其有效的判断标准。

4.4 Reflection：生成 → 检查 → 修正闭环

Reflection（或 Reflexion, Shinn et al. 2023）在 Agent 的输出之后增加了一个"自我检查"步骤。Agent 生成初始输出后，另一个 LLM 调用（或同一个 LLM 的不同 prompt）检查输出质量，发现问题则生成修改建议，Agent 据此修正输出。这个闭环可以迭代多次，每次迭代都带着上一轮的"反思结论"——不是简单重试，而是"带教训的重试"。与 ReAct 和 Plan-and-Execute 不同，Reflection 并不是一种独立的推理循环模式，而是一种跨轮次的质量增强机制——它包裹在 ReAct 或 Plan-and-Execute 的外层，在每次执行完成后对输出进行自我审查和修正。其核心是 Generator（生成初始输出 Draft）→ Evaluator（评分/反馈，通过则输出，不通过进入修改）→ Reviser（基于反馈修改 Draft）的迭代循环，只要迭代次数未超过 max_iters 就回到 Evaluator，否则输出当前最佳版本；失败经验则沉淀为"自我演进记忆"，在后续尝试中避免重复相同错误。与 fine-tuning 的区别：Reflexion 是 in-context learning（反思存在 prompt 里），不修改模型参数。

4.5 反思的三个层次与 Reflexion 执行流程

层次反思内容示例

Reflexion 的执行流程：①Actor 执行任务（带上历史反思）→ ②Evaluator 评估结果（打分）→ ③如果不够好，Reflector 生成反思（"为什么失败？下次怎么做？"）→ ④存入记忆 → ⑤回到 ①（带上新的反思重新执行）。最多重试 3 次。

实际应用：代码 Agent 运行测试失败后，反思"少了边界检查"，重新生成时加上——效果显著。Reflexion 让 Agent 的"试错"变得有价值，而不是简单的随机重试。

4.7 Reflection 的增效数据与关键基准

Reflexion 论文（Shinn et al., NeurIPS 2023）的关键数据：在 HumanEval 代码生成基准上，GPT-4 的 pass@1 从 80% 提升到 91%——仅通过增加 2-3 轮自我反思，语言反思记忆比数值奖励更有效。这 11 个百分点的提升代价是额外的 30-50% 计算开销（每轮反思需要一次额外的 LLM 调用）。在生产环境中，这意味着用 1.3-1.5 倍的成本换取显著的质量提升——对于代码生成、法律文书、医疗报告等高质量要求的场景，这笔交易是极其划算的。

BenchTrace 基准测试（东京大学、京都大学, 2026）对 Qwen3-32B 和 GPT-4.1 进行了系统评估，发现两个模型在端到端反思评估中的通过率均低于 30%，其中诊断（Diagnosis）是主要瓶颈——模型能检测到失败但无法正确诊断失败原因。更关键的发现：只有完全正确的反思才与更高的失败避免率（FAR）强相关，部分正确的反思几乎无法带来改善。

五、三类记忆系统与管理策略

三类记忆的关系：短期记忆是"工作台上的纸条"（当前对话），工作记忆是"脑中的暂存区"（中间结果），长期记忆是"笔记本"（跨会话持久）。短期记忆的瓶颈是 context window——如何在有限 token 中保留最关键信息是核心挑战。

5.3 长期记忆 = RAG 的变体

长期记忆的检索方式本质上就是 RAG——只不过检索的是 Agent 自己的历史经验而非外部文档。存入向量数据库，按 relevance × recency × importance 综合排序检索。需要定期清理低价值记忆（防止噪声累积降低检索质量）。

六、知识增强与协作架构：RAG+Memory 与 Multi-Agent

RAG+Memory 解决的是"Agent 知道什么"的问题——让 Agent 能够访问和利用外部知识库与历史经验。Multi-Agent 解决的是"谁来做什么"的问题——让多个专业化的 Agent 协作完成单个 Agent 无法胜任的复杂任务。两者分别代表了 Agent 系统在"知识维度"和"协作维度"的扩展。

6.1 RAG+Memory 架构：结构化知识库 + 非结构化经验

RAG+Memory 架构为 Agent 增加两层知识基础。RAG（Retrieval-Augmented Generation）层提供结构化的外部知识库——文档、数据库、API 等，通过向量检索或关键词检索获取相关知识注入 Agent 上下文。Memory 层提供非结构化的历史经验——过去的成功案例、失败教训、用户偏好等，存储在向量数据库或结构化存储中。两层知识协同工作：RAG 提供"世界知识"，Memory 提供"个人经验"。

6.2 Multi-Agent 架构：跨 Agent 通信与协作

Multi-Agent 架构将复杂任务分解给多个专业化 Agent，每个 Agent 有独立的角色定义、工具集和推理能力。关键挑战不是"如何分工"——这通常很直观——而是"如何协作"。2026 年的生产数据显示，Multi-Agent 系统中跨 Agent 通信成本占总计算量的 60% 以上——每次消息传递都需要序列化、传输、反序列化，加上接收方的理解成本。当 Agent 数量超过 5 个时，通信成本开始超过任务执行成本。

Multi-Agent 的第二个价值是上下文污染的隔离——Reviewer 不需要看到 Coder 试错的 40 轮中间过程，只需要看到最终产物和自己的审查标准，每个 Agent 的上下文都保持精简聚焦。如果所有角色挤在一个上下文里，早期信息会被后期信息挤出注意力窗口，审查质量会显著下滑。代价同样存在：角色之间的消息协议、结果交接格式、失败传播路径都需要显式设计；协调者本身可能成为瓶颈和单点故障；而且多 Agent 的调试从"读一条 trace"变成"拼接多条 trace"，可观测性建设必须先行。经验法则是：能用两个角色解决就不要开三个——每加一个 Agent，通信成本是按连接数平方增长的。

6.3 Multi-Agent 的成本真相

Multi-Agent 经常被过度使用。一个常见的错误模式是用 3-5 个 Agent 来解决一个 ReAct Agent 就能搞定的问题。生产实测数据：在一个"研报生成"任务中，3-Agent 系统（研究员+分析师+写手）的总 Token 消耗是单 Agent 的 4.2 倍，其中 62% 是通信开销（Agent 之间传递上下文、协商分工、合并结果）。只有在任务确实需要不同专业知识（如同时需要法律知识+财务知识+技术知识）时，Multi-Agent 才能证明其成本合理性。

Multi-Agent 的正确使用时机：当你发现单个 Agent 的 prompt 已经超过 5000 tokens（因为要同时扮演多个角色），或者单个 Agent 需要同时使用 10 个以上不相关的工具集，或者任务天然包含"审查-被审查"的对立角色——这些信号说明任务复杂度已经超出了单 Agent 的承载能力，是时候拆分了。

七、Blackboard 架构：共享状态驱动

多 Agent 和 Blackboard 代表两种截然不同的协作哲学：前者是组织分工（先定岗位再派活），后者是市场驱动（需求贴出来，谁能干谁来干）。

7.1 起源与三大组件

Blackboard（黑板架构）源自 1980 年的语音理解系统 Hearsay-II，近年被重新发掘用于 LLM 多智能体系统。它的三个组件是：黑板（全局共享的结构化状态空间）、知识源（各自专精的 Agent，只通过黑板读写信息）、控制单元（根据黑板当前内容决定下一个激活哪个知识源）。Agent 之间不直接对话——所有协作都发生在黑板上，循环执行直到黑板上达成共识或达到轮数上限。

7.2 基准验证：bMAS 与 Google 数据湖发现

中科院团队提出的 bMAS 框架在 MMLU、GSM8K 等六个基准上做了验证：黑板式多 Agent 平均得分 81.68%，高于思维链单模型的 77.35% 和静态多 Agent 的 76.65%，且由于共享黑板替代了每个 Agent 各自的记忆模块，整体 token 消耗反而更低。

生产案例（大规模数据发现）：Google Cloud AI Research 将黑板架构用于数据湖信息发现——中央 Agent 把请求贴上黑板，分管不同数据分区的子 Agent 根据自身能力自愿响应，中央协调者无需知道每个子 Agent 的专长。在 KramaBench 等三个基准上，该方案比最强基线的端到端成功率相对提升 13%~57%，数据发现 F1 相对提升最高 9%——在数千个异构文件里找数据这种"协调者不可能全知"的场景，黑板的志愿响应机制显著优于主从式派活。

7.3 缺陷与现代落地

黑板的缺陷同样鲜明：状态管理重——多个 Agent 并发写同一个键需要冲突消解规则；扇出不可控——一个事件可能触发一连串新事件，成本预算需要显式护栏；问题难追踪——虽然事件流可重放，但"为什么当时选了这个 Agent"这类因果链仍然模糊。现代落地通常用 Postgres 加事件流中间件（如 NATS JetStream）承载黑板，事件带类型化 schema（事实/假设/计划/行动）与来源标记，黑板按"原始事实 → 派生假设 → 最终决策"分层，让 Agent 只订阅自己关心的层级。

多 Agent 像项目组——先定组织架构再派活；Blackboard 像急诊室白板——病情写上去，对应的科室自己围过来，没人负责"调度"，白板本身就是调度。

八、Route+Skill 架构：意图路由与封闭技能

8.1 链路即一句话：意图识别 → 路由到 Skill 执行

Route+Skill 的链路只有一句话：意图识别 → 路由到对应 Skill 执行。路由器判断"用户要什么"，然后把请求交给一个行为边界完全封闭的 Skill——每个 Skill 有结构化的输入输出契约、固定的工具集和独立的错误处理，像一个签了合同的服务，而不是一个自由发挥的 Agent。Claude Code 的技能系统、企业智能客服的意图中台都是这种形态。

8.2 级联路由与语义缓存

8.3 生产案例：语义路由替换 LLM 选工具

生产案例（语义路由替换 LLM 选工具）：一个多 Agent 系统原先让 LLM 在每次请求时从全量工具列表里选 API，路由延迟约 5,000ms 且频繁幻觉出不存在的端点。改造为语义路由后——把路由定义为意图而非端点、预计算并缓存意图 Embedding、查询时做向量相似度匹配——路由延迟降到 约 100ms，因全量工具描述塞进上下文造成的 token 膨胀削减最高 95%，端点幻觉归零。级联式路由（先规则、再向量、最后才 LLM）可以把整体路由开销控制在 500~2000ms 响应时间的个位数百分比以内。

8.4 设计成本与语义缓存实现

挑战在于 Skill 设计成本高：意图体系要有人持续维护，新意图出现时路由表和 Skill 库都要跟着扩；Skill 之间的边界划分（"退款问题"和"订单问题"重叠怎么办）需要领域专家拍板。换句话说，Route+Skill 是把复杂度从运行时转移到了设计时。

九、Graph/Workflow 架构：确定性与灵活性

Graph/Workflow 架构（以 LangGraph 为代表）是 2026 年企业 Agent 系统的主流选择，因为它解决了其他所有架构都回避的核心问题：如何在保持 Agent 灵活性的同时实现流程的确定性和可观测性。它用状态图（StateGraph）将 Agent 的执行路径显式建模为节点（处理步骤）和边（状态转换），支持条件分支、循环、断点续传和时间旅行。

9.1 固定节点与动态节点的双层设计

Graph/Workflow 架构的精妙之处在于区分固定节点和动态节点。固定节点执行确定性的操作（数据校验、格式转换、API 调用），不走 LLM，行为可预测。动态节点由 LLM 驱动（推理、决策、生成），行为灵活但不确定。两种节点通过条件边连接——条件边根据当前状态决定下一步走哪个节点，可以是确定性规则（如"如果 API 返回错误 → 走错误处理节点"）或 LLM 判断（如"分析结果质量是否足够 → 走 END 或走 Reflection 节点"）。

9.2 可观测性与可回滚性

Graph/Workflow 架构相比其他架构的最大优势是可观测性和可回滚性。每个节点的输入状态、输出状态、执行耗时、Token 消耗都被完整记录。当 Agent 输出不正确时，开发者可以像查看流水线日志一样，逐个节点检查，精确定位是哪个节点出了问题。更进一步，利用 Checkpoint 机制可以"回退"到任意一个历史节点，用不同的参数重新执行——这就是所谓的"时间旅行"调试。

9.3 Graph Workflow 的三个生产能力

Graph Workflow 把工作流定义为图：节点是执行单元（一次 LLM 调用、一个工具、一段代码），边是控制流，条件边根据状态决定走向。与 ReAct 的"模型决定下一步"相反，图工作流里下一步由确定性代码决定，模型只在被明确授权的节点内发挥。这带来三个生产能力：长流程支持（状态持久化后流程可以跨小时跨天运行，等人工审批睡一觉再继续）、条件分支（置信度、重试次数、业务规则都可以作为路由条件写进代码并接受单元测试）、可回溯（检查点机制把每一步的状态快照落盘，失败后从最近的检查点恢复，而不是从头重跑）。

某保险公司的理赔 Agent 系统采用 LangGraph 构建，包含 12 个节点（4 个固定节点 + 8 个动态节点）。固定节点处理：文件格式校验、保单数据库查询、金额计算、合规检查。动态节点处理：损失评估、欺诈风险判断、理赔方案推荐、客户沟通生成。系统在上线后的前三个月内，通过 Checkpoint 回退机制处理了 347 次"Agent 判断失误"的情况——每次回退都节省了从头开始处理的成本，累计节省约 2.1 万美元的 LLM 调用费用。

9.5 工具链三件套：LangGraph、Temporal、n8n

工具链上三件套各有定位。LangGraph 是开发者的状态机：用 Python 代码定义图，TypedDict 声明状态 schema，条件边是纯函数可写单测，配合 LangSmith 的 trace 开箱即用，适合核心推理逻辑需要精确控制的场景。Temporal 是持久执行（durable execution）引擎：它不关心 Agent 怎么思考，只保证工作流无论基础设施出什么事都能跑完——worker 中途崩溃，流程会从事件日志中精确恢复、已成功的步骤绝不重跑，适合跨天、跨系统、含支付的使命级流程。n8n 是低代码集成层：数百个现成连接器加可视化画布，适合"当 X 发生时从 Y 取数、问一下 LLM、写回 Z"这类以系统集成为主的流程，但分支能力基本限于布尔表达式，复杂 Agent 推理在它是逆水行舟。

11.4 上下文膨胀的工程解法

上下文膨胀是 Agent 系统的头号工程问题。研究表明，当上下文超过模型窗口的 70% 时，模型的注意力质量开始显著下降，错误率上升。三种互补的应对策略：

  • 滑动窗口（Sliding Window）：只保留最近 K 轮对话的完整消息，更早的消息用摘要替代。实现简单，但摘要可能丢失关键细节。
  • 结构化记忆（Structured Memory）：将关键信息提取为结构化存储（如 JSON），而非依赖原始对话文本。查询时按需注入，大幅减少 token 消耗。
  • 子任务隔离（Subtask Isolation）：每个子任务使用独立的上下文，只接收必要的输入（步骤描述 + 前序结果），不继承完整的对话历史。这是 Plan-and-Execute 架构天然具备的优势。

11.6 范式在 LangGraph 中的统一实现

三种范式可以在 LangGraph 框架中统一实现。LangGraph 的核心抽象是状态图：节点是处理函数，边是状态转移，条件是路由逻辑。

  • ReAct 实现：create_react_agent() 是最简形式——LLM 节点和工具节点通过条件边循环连接。
  • Plan-and-Execute 实现：增加 Planner 节点，其输出写入 State 的 plan 字段；Executor 节点从 plan 中读取当前步骤执行。
  • Reflection 实现：在输出节点后增加 Evaluator 节点，条件边根据评估分数决定路由到 Reviser 还是 END。
graph = StateGraph(AgentState)
graph.add_node("planner", plan_task)       # Plan 层
graph.add_node("executor", execute_step)   # ReAct 层
graph.add_node("evaluator", evaluate_output)  # Reflection 层
graph.add_node("reviser", revise_output)

graph.add_edge("planner", "executor")
graph.add_conditional_edges("executor", should_continue,
    {"next_step": "executor", "done": "evaluator", "replan": "planner"})
graph.add_conditional_edges("evaluator", check_quality,
    {"pass": END, "revise": "reviser"})
graph.add_edge("reviser", "evaluator")

Agent 范式本质上是一个有限状态机：ReAct 是单个循环状态机，Plan-and-Execute 是带条件分支的线性链，Reflection 是嵌套循环。理解这个本质，就能在 LangGraph 等框架中自由组合任意拓扑。

十二、架构选型决策矩阵与增效指标

12.8 选型反模式与实践清单

2026 年 LangChain 社区调查：在采用 Agent 架构的团队中，43% 使用了至少两种架构的组合（最常见：ReAct + Reflection），27% 采用纯 Plan-and-Execute，18% 使用 Multi-Agent，12% 采用 Graph/Workflow。值得注意的是，使用 Graph/Workflow 的团队中 89% 同时嵌套了 ReAct 或 Reflection 节点——纯固定流程正在被"固定骨架+动态节点"的混合模式取代。

  • 为每种架构组合设置成本预算和延迟 SLA
  • 从简单到复杂逐步评估：先用最简架构（ReAct 原型）建立 baseline，再评估组合
  • 质量敏感任务固定 Reflection 层，max_iters = 2-3
  • 企业级长流程优先 Graph/Workflow（checkpoint、时间旅行、人工审批）
  • Plan-and-Execute 预留 Replan 钩子（不信任初始计划）
  • 知识密集型场景用 RAG+Memory，减少幻觉依赖检索
  • 为每种架构设置硬上限（max_steps、max_iters、超时）
  • Executor 和 Evaluator 用便宜模型，Planner 才用贵的
  • 意图层与执行层解耦、可观测性先行（trace、checkpoint、事件日志），把 Skill 当契约对待
  • 不要为了"用 Multi-Agent"而用 Multi-Agent（通信开销 > 任务本身）
  • 不要忽略流程可控性需求而盲目选 ReAct
  • 不要为一次性任务使用 Graph/Workflow（设计成本 > 收益）
  • 不要跳过纯架构 baseline 直接上组合
  • 不要无限增加 Reflection 轮次（>3 轮边际收益趋零），也不要在没有验证信号时做 Reflection
  • 不要忽略架构维护成本（Graph/Workflow 维护最贵），也不要为了架构而架构（Blackboard 不设扇出上限、用 Temporal 跑三十秒流程）
  • 不要把 ReAct 的 max_steps 设到 20 以上
  • 不要在低延迟（<5 秒）场景使用 Plan-and-Execute 或 Reflection
  • 不要让 Planner 和 Executor 使用同一个 LLM 实例（Planner 的规划风格会污染 Executor 的执行决策）
  • 不要把长流程交给没有 replan 闸门的 Plan and Execute；不要让 LLM 在几十个工具里现场挑选——先用路由收敛工具集

12.9 ReWOO 与 Tree of Thought：新兴变体

除了上述七种核心架构，2026 年还有两个值得关注的新兴变体。ReWOO（Reasoning Without Observation）将 ReAct 的"观察-推理"循环改为"先规划所有工具调用、再批量执行"——消除了 Observation 的中间等待，但牺牲了动态适应性。Tree of Thought（ToT）将推理过程建模为树搜索，在每个推理节点生成多个分支并评估，选择最优路径——适合数学证明、策略规划等需要"探索多条推理路径"的任务，但计算成本是线性推理的 3-5 倍。

12.11 架构演进的三个阶段与升级信号

Agent 架构的演进遵循"从简单到复杂、从单点到系统"的规律。大多数生产系统的演进路径是：先用 ReAct 跑通基本流程（验证 LLM 能否完成任务），然后加入 Plan-and-Execute + Reflection 提升质量和效率（应对复杂任务），最终用 Graph/Workflow 实现企业级可控性（满足合规和审计要求）。跳过中间阶段直接上复杂架构是常见的过度设计错误。

┌─────────────────────────────────────────────────────────┐ │ Agent 架构演进路径 │ ├─────────────────────────────────────────────────────────┤ │ │ │ 阶段一: 单 Agent + 工具调用 │ │ ├── 适用: 简单任务验证 │ │ ├── 特点: 快速搭建，验证 LLM 能力边界 │ │ └── 瓶颈: 无法处理多步复杂任务 │ │ │ │ │ ▼ 任务复杂度提升 │ │ 阶段二: ReAct + RAG+Memory │ │ ├── 适用: 多步推理 + 知识增强 │ │ ├── 特点: 推理透明，知识驱动 │ │ └── 瓶颈: 缺乏全局规划，质量不稳定 │ │ │ │ │ ▼ 质量和规划需求 │ │ 阶段三: Plan-and-Execute + Reflection │ │ ├── 适用: 复杂报告、代码生成 │ │ ├── 特点: 规划先行，质量保障 │ │ └── 瓶颈: 流程不可控，难以审计 │ │ │ │ │ ▼ 企业级需求 │ │ 阶段四: Graph/Workflow + Multi-Agent │ │ ├── 适用: 企业级生产系统 │ │ ├── 特点: 流程可控，角色分工，完整可观测 │ │ └── 代价: 设计和维护复杂度最高 │ │ │ │ 关键原则: 从简单开始，按需升级，避免过度设计 │ └─────────────────────────────────────────────────────────┘

什么时候必须升级？三类信号最可靠：上下文信号——上下文开始逼近窗口上限，Agent 频繁忘记初始指令，说明单 Agent 的"工作台"不够用了，该拆任务边界或加记忆层；准确率信号——调 prompt、换更强模型都无法突破的准确率和稳定性瓶颈，说明问题出在结构而非模型，该加规划或反思层；可靠性信号——出现需要跨小时运行的流程、需要人工审批的环节、失败后必须从断点恢复的要求，说明必须上状态持久化和检查点，进入图式编排。

生产案例（客服机器人架构演进）：某客服机器人初期用 ReAct，日均处理 20,000 次查询，平均 3.5 步完成。但遇到复杂问题（如"帮我对比三款套餐并推荐最适合的"）时，经常需要 8 步以上，context 膨胀严重，完成率降到 45%。改进方案：Plan-and-Execute 的 Planner 把复杂查询拆解为 3-5 个子任务，每个子任务用 ReAct 执行，子任务之间隔离 context；关键输出加 Reflexion。改进后复杂查询完成率从 45% 提升到 78%，LLM 调用次数下降 30%，其中 Reflexion 让约 25% 的"首次失败"查询最终成功。

架构复杂度是负债，不是资产：每加一个组件，都要回答"它解决了哪个具体问题、值多少成本"。选型的目标不是"最先进"，而是用最小的复杂度覆盖当前需求，并为下一步演进留好接口。

Q&A

ReAct 和 Plan-and-Execute 应该在什么场景下组合使用？

组合使用的黄金场景是"需要全局规划但执行中需要动态适应"的任务。Plan-and-Execute 的 Planner 先生成步骤计划，每个步骤的具体执行则交给 ReAct——ReAct 的 Thought-Action-Observation 循环处理步骤内的不确定性。2026 年的企业研报生成系统几乎都采用这种组合：Planner 决定"先查什么、再分析什么、最后写什么"，ReAct 处理每个步骤中的意外情况（如数据源不可用需要切换）。纯 Plan-and-Execute 在步骤执行遇到意外时需要 Replan，而 ReAct 层的自适应能力大幅减少了 Replan 频率。

Reflection 的轮次多少合适？会不会反思越多越好？

2026 年的实证数据明确回答：不是。Reflection 的边际收益在第二轮之后急剧下降。在代码生成场景中，第一轮反思修正约 60% 的问题，第二轮修正剩余的 25%，第三轮只修正 5-8%——但每轮反思的 Token 成本是固定的。因此大多数生产系统将 Reflection 轮次限制在 2-3 轮。更关键的是，Reflection 需要一个"判断何时停止"的机制：通常由 Evaluator LLM 给出质量评分，当评分超过阈值（如 85 分）时停止反思，避免无谓的迭代。

Multi-Agent 的 60%+ 通信成本是怎么产生的？有办法优化吗？

通信成本的来源有三：①上下文传递——Agent A 需要将完整的推理结果传递给 Agent B，Agent B 需要重新理解这些内容（消耗输入 Token）；②协商开销——多个 Agent 之间需要确认任务分配、结果格式、依赖关系等"元信息"；③冗余传递——Agent C 可能接收了它不需要的信息（因为在广播模式下）。优化方案包括：结构化消息协议（用 JSON schema 替代自由文本，减少 30-40% Token）；按需订阅（Agent 只接收与自身角色相关的消息）；中间结果缓存（共享状态存储替代消息传递）。LangGraph 的 StateGraph 模式通过共享状态而非消息传递，将通信成本从 60% 降到 35% 左右。

Graph/Workflow 的设计复杂度会不会成为瓶颈？什么时候值得投入？

设计复杂度是真实的——一个 10 节点的 StateGraph，其状态转换路径可能有数百条，测试覆盖是巨大的工作量。但投入是值得的，前提是任务满足以下任一条件：①需要人工审批（Human-in-Loop），因为 Graph 的 breakpoint 机制是唯一成熟的实现方式；②需要断点续传（任务可能执行数小时），因为 Checkpoint 可以从中断点恢复；③需要完整审计（监管合规），因为每个节点的 I/O 都被记录。对于简单的多步任务，Graph 的设计成本远超收益——用 Plan-and-Execute 更划算。

如何判断一个任务是否需要 RAG+Memory 增强？

三个信号表明需要 RAG+Memory：①任务依赖特定领域知识（如"根据我们的产品文档回答"），LLM 的训练数据中不包含或已过时；②任务需要"记忆"——用户偏好、历史交互、之前的决策结果，这些信息无法在单次对话中获取；③任务需要引用来源——回答必须指向具体的文档或数据，而非 LLM 的"自由发挥"。判断标准：如果去掉外部知识后 Agent 的回答质量下降超过 20%，说明 RAG 层是必要的。

七种架构中，哪些是 2026 年增长最快的？

Graph/Workflow 是增长最快的——LangGraph 的 GitHub stars 在 2025-2026 年间增长了 3 倍，企业采用率从 8% 跃升到 23%。驱动力来自合规需求：金融、医疗行业要求 Agent 决策可追溯、可审计，Graph 的节点日志天然满足这一要求。Reflection 是第二增长极——代码生成 Agent 的爆发让"自我检查"成为标配。最出乎意料的是 ReAct 的持续生命力——尽管它是最"古老"的架构（2022），但在调试、探索、对话等场景中仍然无可替代，2026 年仍是使用率最高的 Agent 架构（约 65% 的系统包含 ReAct 组件）。

一个生产系统通常会组合几种架构？有上限吗？

2026 年的生产数据显示，典型的 Agent 系统组合 2-3 种架构。最常见的组合是：ReAct + Reflection（45%）、Plan-and-Execute + Reflection（30%）、RAG+Memory + Plan-and-Execute（15%）。超过 3 种架构的组合极为罕见——不是因为技术上不可行，而是因为每增加一种架构，系统的调试难度呈指数增长。一个实用的上限原则：如果你无法在白板上 3 分钟内向同事解释清楚你的架构组合，说明它太复杂了。

什么时候用 ReAct，什么时候用 Plan-and-Execute？

ReAct 适合简单到中等任务（1-5 步），优点是简单、灵活、实现快。Plan-and-Execute 适合复杂任务（5+ 步），优点是效率高、可重规划。判断标准：如果任务步骤可以提前列举，用 Plan-and-Execute；如果需要"走一步看一步"，用 ReAct。另一个考虑是上下文管理：Plan-and-Execute 的 Planner 和 Executor 可以分离上下文，而 ReAct 的所有历史消息都在一个 context 中，容易溢出。

Reflexion 的"反思"和简单重试有什么区别？

关键区别是：Reflexion 会生成一段文字化的"反思"（为什么失败、下次怎么做），存入记忆供下次使用。简单重试只是"再来一次"。在代码生成场景中，Reflexion 能让"3 次内成功"的概率从 60% 提升到 85%，而简单重试只能提升 5-10%。反思的价值在于方向性——每次重试都更聪明。

如何设计 Agent 的记忆系统？三类记忆各扮演什么角色？

短期记忆 = 当前对话的 context window，存放"正在讨论什么"；工作记忆 = 任务状态（State/Scratchpad），存放"执行到哪一步了"；长期记忆 = 向量数据库，存放"用户偏好、历史经验"。设计原则：短期记忆用摘要压缩管理，工作记忆结构化存储（JSON），长期记忆按 relevance × recency × importance 综合排序检索。长期记忆的检索本质上就是 RAG——只不过检索的是 Agent 自己的历史经验。

如何检测和防止 Agent 无限循环？

检测手段：①步数上限（max_iterations）；②重复 Action 检测（最近 3 步出现相同 Action）；③重复 Thought 模式检测（同一个 Thought 出现 3 次以上）；④成本预算（超过 $0.05 强制终止）；⑤超时机制（>60 秒强制返回）。防护策略：循环检测触发时，不是简单终止，而是"换策略"——让 LLM 总结当前进展，换一个完全不同的方法继续。实在无法继续时返回部分结果并说明原因。

LangGraph 的 StateGraph 和 ReAct 是什么关系？

ReAct 是一种推理模式（Thought → Action → Observation 循环），StateGraph 是实现框架（定义节点和边）。LangGraph 的 create_react_agent() 就是用 StateGraph 实现了一个 ReAct Agent：LLM 节点负责推理和决策，工具节点负责执行 Action，条件边决定是继续循环还是终止。StateGraph 的优势在于可以在 ReAct 循环外添加更多节点（如 Reflection 检查节点、Human-in-Loop 审批节点），实现复合架构。此外 StateGraph 支持 Checkpoint（SQLite/Postgres），可以在任意节点暂停和恢复。

如何选择合适的 Agent 架构？有没有通用的选型原则？

选型决策树：①任务简单（1-3 步）→ ReAct；②任务复杂（5+ 步）→ Plan-and-Execute；③需要质量保障 → 叠加 Reflection；④需要知识支撑 → 加 RAG+Memory；⑤需要多角色协作 → Multi-Agent；⑥需要流程可控 → Graph/Workflow。通用原则：从简单开始，按需升级。80% 的任务用 ReAct 就够了。升级信号：ReAct 频繁溢出 context window（→ 升级 Plan-and-Execute）；Agent 反复犯同样的错误（→ 加 Reflexion）。

ReAct 为什么越到后面步骤越容易偏离目标？

这是 ReAct 的结构性缺陷——级联错误：每步的输出成为下步的输入，一旦第 3 步选错了工具，第 4 步就会在错误的观察上继续推理，偏差逐步累积。更根本的原因是上下文膨胀：随着步骤增加，早期指令被挤出注意力窗口，模型逐渐"忘记"原始目标。LangChain 2026 Benchmark 显示，ReAct 在 10 步任务上完成率 85%，但 15 步以上时骤降至 62%。缓解方案：滑动窗口保留最近几轮 + 每步注入目标摘要；或切换到 Plan-and-Execute 用计划锚定方向。

"计划过时"问题如何量化检测？

生产级做法是实现一个"偏差检测器"：比较每步实际输出与计划中预期输出的语义相似度（如用 embedding 余弦相似度），低于阈值（如 0.7）即判定为偏差，触发重规划。Oracle 的实践更精细：维护一个"计划健康度"分数，综合偏差程度、累积偏差次数、剩余步骤风险等级，超过阈值才触发重规划，避免过于敏感导致频繁重规划。关键经验：重规划成本很高（一次完整 LLM 调用），所以阈值设置需要在"及时纠错"和"避免过度重规划"之间平衡——通常偏差阈值设为 30%，但高风险任务降至 10%。

Reflection 在哪些场景下反而是有害的？

三种场景 Reflection 弊大于利：①任务没有明确验证标准时（如创意写作），模型会"过度反思"导致输出趋同、丧失多样性；②延迟敏感场景（如实时客服，P99 要求 <5 秒），Reflection 的额外轮次会直接击穿延迟 SLA；③模型已经很强的简单任务——如果基础准确率已超过 95%，Reflection 的边际收益极小但成本固定，纯浪费。判断原则：Reflection 只在"有验证信号 + 质量敏感 + 延迟可容忍"三者同时满足时才有正 ROI。

三层复合架构中，是否所有子任务都应该做 Reflection？

不应该。生产级系统的做法是按子任务风险分级：高风险步骤（如资金操作、法律文本生成）强制 Reflection，max_iters 设为 3-5；中风险步骤（如数据查询、格式转换）用轻量验证（schema 校验）替代完整 Reflection；低风险步骤直接跳过。全量 Reflection 的问题是成本爆炸——每个子任务 3 轮 Reflection 意味着 LLM 调用次数翻 3 倍，而大部分子任务（如"读取文件"）根本不需要反思。关键指标：Reflection 触发率应控制在 10-30%，过高说明子任务划分粒度有问题。

ReAct 和 Plan-and-Execute 是否互斥？能否运行时动态切换？

不互斥，且 2026 年的前沿实践正是动态切换。dreaming.press 提出的"渐进承诺"框架：先用 ReAct 探索 2-3 步，如果发现任务路径逐渐清晰（工具调用模式趋于稳定），自动升级为 Plan-and-Execute 生成完整计划；反之，如果计划执行中遇到不可预见的分支，降级回 ReAct 逐步探索。实现方式是在两种范式之上加一个轻量"路由 Agent"，根据任务进展的确定性程度决定当前使用哪种范式。这种动态混合在复杂任务上比固定使用任一范式提升 15-20% 的完成率。

Planner 和 Executor 使用不同模型时，如何选择？

标准实践是"强规划、弱执行"：Planner 用最强的推理模型（如 Claude Sonnet 4、GPT-4.1），因为规划质量决定了整个任务的上限；Executor 用更便宜快速的模型（如 Claude Haiku、GPT-4o-mini），因为执行步骤通常是机械的（调 API、读文件、格式化）。成本差异可达 5-10 倍。注意一个陷阱：如果 Executor 模型太弱，它会误解 Planner 的指令，导致执行偏差触发重规划——反而更贵。2026 年的新方向是 CoRefine：用一个 211K 参数的小控制器模型做 Planner-Executor 之间的"翻译层"，token 成本降低 60-70%，任务完成率保持在 90% 以上。

BenchTrace 对工程实践有什么启示？

三个关键启示：①不要假设"模型会自己反思"——GPT-4.1 的端到端反思通过率不到 30%，必须用外部验证信号（测试结果、数据校验）替代模型的自我评估；②反思的质量比数量重要——部分正确的反思几乎无效，只有完全正确的反思才能降低失败率，所以 1 轮高质量反思（有真实验证信号）胜过 5 轮无信号的自我对话；③反思能力不跨任务泛化——在任务 A 上学到的反思策略不能直接用于任务 B，需要按任务类型分别调优。工程落地建议：为每种任务类型建立独立的验证器，而非依赖通用的"反思 prompt"。

如何控制复合架构的 token 成本？有没有经验性的分配比例？

生产级系统的经验分配是 60-25-15：Plan 层占总 token 的 15%（一次强模型调用生成计划），ReAct 执行层占 60%（大量轻量模型调用），Reflection 层占 25%（仅关键输出触发）。控制手段：①Plan 层限制子任务数不超过 8 个；②ReAct 层每步只注入"步骤描述 + 前序结果摘要"，不继承完整历史；③Reflection 层 max_iters = 2-3；④设置总 token 预算，超过后降级为"不做 Reflection 的快速模式"。关键监控指标：上下文利用率超过 75% 时自动触发摘要压缩。

为什么 AI Coding、智能客服偏爱 Route+Skill 架构？

两类场景有共同特征：意图空间有限且可以穷举（查订单/退款/改配置，或写函数/跑测试/修 bug），每个意图对应的执行步骤相对固定，但执行细节需要灵活。Route+Skill 正好匹配——路由器把问题归类到已知意图，Skill 内部用受限的 Agent 完成执行。好处是：行为边界清晰（每个 Skill 只能调特定工具，不会越权）、可独立测试和发布、出问题能精确定位到某个 Skill。相比之下让一个通用大 Agent 自由发挥，在高频、高并发的客服和 coding 场景里稳定性不够。

为什么 ReAct 通常是 Agent 架构的起点？

ReAct 的 Thought → Action → Observation 循环几乎是所有复杂架构的原子单元：Plan and Execute 的每个子任务、Multi-Agent 的每个角色内部，跑的基本都是 ReAct。它上手快、可调试（每一步的思考都可见）、对任务形态不挑剔。更重要的是成本信号清晰——一个中等任务实测约 2,000~3,000 token，一旦超预算或进入循环，就是换架构的明确信号。先用 ReAct 把工具集和提示词打磨好，再决定往哪个方向升级，失败成本最低。

Plan and Execute 和"一步一步想"有什么本质区别？

本质区别在于计划是不是一等公民。一步一步想（思维链）里，推理是隐式的、和当前上下文混在一起，无法单独检查；Plan and Execute 把计划显式输出成结构化的步骤列表，它可以在执行前被人工审批、被程序校验、被持久化。这带来三个工程能力：子任务可以并行（互相独立的步骤同时跑）、token 更省（执行时不用背着全部规划上下文）、失败可以精确定位到某一步并只重做那部分。代价是计划本身可能出错，所以必须配 replan 机制。

Multi-Agent 和 Blackboard 架构怎么选？

看两个问题：角色能否预先定义？流程是否需要动态涌现？如果角色清晰（分析师、评审员、执行者）、协作路径可预定义，用 Multi-Agent——通信协议和交接格式都能提前设计好，行为可预测。如果问题是开放式的（调研、假设验证、大规模数据发现）、不知道需要哪些"专家"、谁该发言取决于黑板上出现了什么，用 Blackboard——它的志愿响应机制让协调者不必全知。生产数据也支持这个分界：Google 用黑板做数据湖信息发现，端到端成功率比主从式派活相对提升 13%~57%；而软件开发这类角色明确的场景，Multi-Agent 分工依然是主流。

LangGraph、Temporal、n8n 是互斥的竞品吗？

不是，三者解决的是不同层的问题，生产系统经常叠加使用。LangGraph 管"Agent 怎么思考"：图结构编排推理步骤、控制工具选择，强项是语义级的条件分支。Temporal 管"流程一定能跑完"：持久执行引擎，worker 崩溃后从事件日志精确恢复，已成功的步骤绝不重跑，适合跨天、含支付的长流程。n8n 管"系统和系统怎么连"：数百个连接器加可视化画布，适合集成密集型流程。典型组合：Temporal 做整体流程骨架，其中一个节点内部用 LangGraph 跑 Agent 推理，n8n 负责连接外部 SaaS。选型时按"最痛的问题"定主框架，其余按需叠加。

什么信号说明该给单 Agent 做架构升级了？

三类信号。上下文信号：上下文逼近窗口上限，Agent 开始忘记初始指令、混淆前后任务——说明单 Agent 的工作台不够用了，该拆任务边界或加记忆层。准确率信号：调提示词、换更强模型都无法突破的准确率和稳定性瓶颈——说明问题出在结构而非模型，该加规划或反思层。可靠性信号：出现需要跨小时运行的流程、需要人工审批的环节、失败后必须从断点恢复的要求——说明必须上状态持久化和检查点，进入图式编排。三个信号分别对应"拆上下文、加结构、建可靠性"三个升级方向。

多种架构混合使用时如何避免混乱？

三条原则。第一，给每种架构划清地盘：Route+Skill 管意图分发，Plan and Execute 管长程骨架，Reflection 只挂在有验证信号的关键节点——用契约（结构化输入输出）固定边界，而不是让 Agent 之间自由对话。第二，统一状态表示：所有架构读写同一份结构化状态，避免每个组件自造格式。第三，可观测性先行：混合架构的调试成本远高于单一架构，trace、checkpoint、事件日志必须在上线前就位。生产数据显示，"Plan 骨架 + 关键节点 Reflection"能把准确率从 80% 提到 97%，单次调用成本从 $0.052 涨到 $0.095——用不到 2.5 倍的成本换 17 个百分点的提升，但前提就是边界清晰、契约明确。
