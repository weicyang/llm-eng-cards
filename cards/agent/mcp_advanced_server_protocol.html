A23 · MCP 进阶：自建 Server 与协议分析

用 Python 创建 MCP Server → 截获输入输出 → 逐行分析协议 → 直接与 Server 通信 → MCP 的本质

MCP 协议拆开看只有两件事：用 JSON-RPC 2.0 自报家门（我有哪些工具），再按 JSON Schema 传参调用工具——看懂 STDIO 上这段文本流，你就从 MCP 用户变成了 MCP 开发者。

一、用 Python 从零构建一个 MCP Server

自建 Server 的第一步是准备环境。这里用 uv——Astral 出品的 Rust 编写的 Python 包管理器，比 pip 快 10~100 倍，其附带的 uvx 命令还能像 npx 一样直接运行未安装的 Python 工具包，是当前 MCP 生态的默认选择。

uv init weather              # 创建项目
cd weather && uv venv        # 创建虚拟环境
uv add "mcp[cli]" httpx      # 安装 MCP SDK 与 HTTP 客户端

1.1 FastMCP：把普通函数变成 Tool

FastMCP 是官方 Python SDK 内置的高级封装，它用装饰器把普通 Python 函数自动转换为符合协议要求的 Tool，开发者完全不需要手写 JSON-RPC 消息。

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather", log_level="error")  # 日志走 stderr，别污染 stdout

@mcp.tool()
def get_forecast(latitude: float, longitude: float) -> str:
    """获取指定地区的天气预报。Args: latitude: 纬度; longitude: 经度"""
    return httpx.get(f"https://api.weather.gov/points/{latitude},{longitude}").text

mcp.run(transport="stdio")

1.2 装饰器"榨"出了哪些元信息

函数上的元素转换成的协议字段作用
函数名 get_forecastname模型调用时引用的工具标识
docstring 第一行description模型判断"该不该用这个工具"的依据
类型注解 floatinputSchema.properties.*.type约束参数类型
docstring 的 Args 段各参数的 description模型提取参数的语义依据

写一个 MCP Tool 就是写一个带类型注解和 docstring 的普通 Python 函数——协议要求的全部元信息，都由装饰器从代码里自动提取。

1.3 为什么必须 log_level="error"

STDIO 模式下，stdout 是唯一的协议通道，任何混入的非 JSON 文本（比如第三方库启动时打印的 banner）都会被 Host 当成协议消息解析并直接报错。把日志级别设为 error 并让日志走 stderr，是 STDIO Server 的第一纪律。

uv venv创建虚拟环境隔离依赖
uv add "mcp[cli]"安装 SDK + 调试工具cli 扩展含 mcp dev / mcp install
uv run python weather.py在虚拟环境中启动 Server进程阻塞等待 stdin 输入

二、协议握手与通信时序

把 Server 的输入输出截获下来，会发现所谓"MCP 协议"就是 JSON-RPC 2.0——一种轻量的远程过程调用协议，每条消息是一行带 jsonrpc、method、id 字段的 JSON，有 id 的是请求（需要响应），没有 id 的是通知（无需响应）。

Client (Host) Server │ │ │ ① initialize │ │ {protocolVersion, clientInfo, ...} │ │ ───────────────────────────────────────► │ │ ② 响应: serverInfo + capabilities │ │ ◄─────────────────────────────────────── │ │ ③ notifications/initialized（通知） │ │ ───────────────────────────────────────► │ │ ④ tools/list（请求，带 id） │ │ ───────────────────────────────────────► │ │ ⑤ 响应: tools[] │ │ (name / description / inputSchema) │ │ ◄─────────────────────────────────────── │ │ ⑥ tools/call {name, arguments} │ │ ───────────────────────────────────────► │ │ ⑦ 响应: content[]（工具执行结果） │ │ ◄─────────────────────────────────────── │
步骤方向内容说明
①Client → Serverinitialize 请求Client 打招呼，报自己的版本和能力
②Server → Clientinitialize 响应Server 自我介绍（名称、版本、能力）
③Client → Serverinitialized 通知Client 确认握手完成，此后才能发业务请求
④Client → Servertools/list 请求询问有哪些工具可用
⑤Server → Clienttools/list 响应返回工具列表（名称、描述、inputSchema）
⑥Client → Servertools/call 请求调用指定工具 + 参数
⑦Server → Clienttools/call 响应返回工具执行结果

2.1 三种消息类型

类型特征典型例子
Request带 id，必须响应initialize、tools/list、tools/call
Notification无 id，单向告知notifications/initialized
Response用 id 与请求配对工具列表、执行结果

2.2 版本协商

initialize 请求里的 protocolVersion 是协议版本字符串（如 2024-11-05），Client 报出自己支持的版本，Server 回复实际将使用的版本。若双方版本完全不兼容，Server 会直接断开连接——这是协议演进留下的安全阀。

MCP 握手就是"先对暗号再谈生意"：initialize 交换版本和能力声明，双方确认协议兼容之后，才允许列工具和发起调用。

三、inputSchema：模型读懂工具的关键

tools/list 响应中，每个工具除了 name 和 description，最重要的就是 inputSchema——一段遵循 JSON Schema 规范的参数结构描述，用 JSON 来定义"另一个 JSON 应该长什么样"，包括参数名、类型、是否必填。它是模型生成合法参数的唯一依据。

{
  "type": "object",
  "properties": {
    "latitude":  {"type": "number", "description": "纬度"},
    "longitude": {"type": "number", "description": "经度"}
  },
  "required": ["latitude", "longitude"]
}
字段作用写不好会怎样
type约束参数整体结构（object）模型可能直接传数组
properties声明每个参数的名称与类型参数类型错乱（如字符串数字）
description告诉模型参数的语义和单位模型漏传、乱传参数
required标记必填参数缺参调用导致执行失败
生产案例：某团队的天气 Server 上线后，模型经常只传 latitude 漏掉 longitude，一次调用成功率只有 71%。抓包发现 docstring 只写了"获取天气"，inputSchema 里两个参数都没有 description，模型只能靠猜。补全 Args 描述并保留 required 约束后，参数完整率升到 99.2%，一次成功率随之翻倍。工具描述不是注释，而是模型唯一能看到的说明书。

inputSchema 是工具的"使用说明书"：description 决定模型会不会选它，required 和 type 决定模型传参传得对不对。

四、中间人抓包：截获 STDIO 通信

想看清真实 Host 与 Server 之间的完整对话，可以写一个中间人脚本 mcp_log.py：让 Host 把自己当成 Server 启动，脚本内部再启动真正的 Server，双向转发每一条消息并逐行写入日志文件。

┌────────┐ spawn ┌────────────┐ spawn ┌────────────┐ │ Host │ ──────► │ mcp_log.py │ ──────► │ MCP Server │ │(Cline) │ ◄────── │ （中间人） │ ◄────── │ (weather) │ └────────┘ stdout └─────┬──────┘ stdout └────────────┘ │ 每条消息追加写入 ▼ mcpio.log（逐行 JSON）
症状日志特征根因修复
Server 加载超时无 initialize 响应uvx 首次下载依赖超过 60 秒先在终端手动跑一次预热缓存
工具列表为空tools/list 响应 tools=[]函数未加 @mcp.tool()检查装饰器与模块导入
Host 报解析错误stdout 混入非 JSON 行print 或库 banner 污染协议通道log_level="error"，日志改走 stderr
调用参数被拒tools/call 返回 error参数不符合 inputSchema完善 docstring 的 Args 描述
生产案例：一个自研查询 Server 接入 Cline 后始终加载失败，团队凭猜测换了三次配置都没解决。挂上中间人日志后 15 分钟即定位：Server 启动时第三方库向 stdout 打印了一行 banner，Host 把它当 JSON 解析失败，重试直到 60 秒超时。把日志改走 stderr 并设置 log_level="error" 后，加载时间从超时失败降到 1.4 秒，工具调用恢复 100% 成功。
STDIO Server 的黄金法则：stdout 只允许出现协议消息。调试信息一律打印到 stderr（print(..., file=sys.stderr)），否则任何一行多余输出都会让 Host 当场翻脸。

STDIO 抓包不需要任何网络工具——通信本来就是两个进程之间的文本流，插一个"传话筒"进程进去就能全量记录。

五、绕过 Host：手动与 Server 对话

既然协议是纯文本 JSON-RPC，完全可以不用任何 MCP Host，直接在终端里给 Server 喂 JSON——启动进程后，向它的 stdin 逐行输入消息即可。

# 启动 Server（进程阻塞等待 stdin）
uv run python weather.py

# ① 握手
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual","version":"0.1"}}}
# ② 列工具
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
# ③ 调用工具
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_forecast","arguments":{"latitude":40.7,"longitude":-74.0}}}
在这种情况下，我们自己就是 MCP Host。这证明了 MCP 协议与模型无关——它只是一套函数的发现与调用规范，整条链路里甚至可以没有大模型参与。

5.1 三种调试手段对比

手段适用场景优点代价
手动 stdin 输入验证协议细节、复现 bug零依赖，看清每个字节手敲 JSON 繁琐
MCP Inspector（mcp dev 启动）日常开发自测官方图形调试器，网页上点点点即可完成握手与调用需要浏览器环境
中间人日志排查真实 Host 环境的问题看到的是生产流量的真实形态要自己写代理脚本

MCP Inspector 是官方 SDK（mcp[cli] 扩展）自带的图形化调试器：一条 mcp dev weather.py 命令即可在网页上完成握手、查看工具列表、手动填参调用，是开发阶段最高频的工具。

能在终端里手动和 Server 完成一次握手，就说明你真正拥有了这个协议——Host 只不过是替你打字的那个角色。

六、MCP 协议的边界：规定了什么、没规定什么

把整条链路摊开，MCP 的管辖范围出人意料地小：它只规定 Server 侧的函数发现（tools/list）与函数调用（tools/call），连同必要的握手与传输方式。至于模型如何拿到工具列表、如何决定调用哪个工具、Host 与模型之间用什么格式通信——协议一概不管。

┌──────────┐ XML / Function Calling ┌──────────┐ │ Host │ ◄─────────────────────────► │ 模型 API │ ← MCP 不规定 └────┬─────┘ （各 Host 自定义格式） └──────────┘ （协议空白区） │ │ JSON-RPC 2.0 │ initialize / tools/list / tools/call │ ┌────▼─────────┐ │ MCP Server │ ← MCP 只管这一段 └──────────────┘ （工具发现 + 调用）
环节协议作用范围
Host ↔ 模型无统一标准（Cline 用 XML、Cherry Studio 用 Function Calling）模型选择工具、解析参数
Host ↔ ServerMCP 协议（JSON-RPC 2.0）工具发现、工具调用
不同 MCP Host 与模型的交互方式差异很大：Cline 用 XML 标签，Cherry Studio 用 Function Calling 的 JSON 结构。MCP 协议本身不规定这些，它只关心 Server 端的函数发现与调用——这正是同一个 Server 能被所有 Host 复用的原因。
  • 开发完 Server 先用 Inspector 或手动握手自测，再接入 Host
  • 日志一律走 stderr，并设置 log_level="error"
  • 把 docstring 和参数描述当成"给模型看的文档"来写
  • 关注 protocolVersion，与 SDK 版本保持同步
  • 不要往 stdout 输出任何非协议内容（print、库 banner）
  • 不要假设所有 Host 的行为一致（确认流程、超时都不同）
  • 不要在 Server 代码里感知或依赖特定模型
  • 不要忽略 initialize 失败——后续所有请求都会被拒绝

MCP 的聪明之处在于"只管一半"：把 Host↔Server 这段做成统一标准，把 Host↔模型 这段留给生态自由竞争——管得少，才推得动。

Q&A

MCP 协议规定了什么？没有规定什么？
MCP 只规定两件事：①Server 有哪些函数可用（tools/list 返回名称、描述、inputSchema）；②如何调用这些函数（tools/call 传名称和参数），外加 initialize 握手与 STDIO/HTTP 传输约定。它没有规定模型与 Host 之间如何交互——不同 Host 可以用 XML（Cline）、Function Calling（Cherry Studio）等任意格式与模型通信。MCP 协议脱离大模型也能运行，本质是一套函数发现与调用规范。
@mcp.tool() 装饰器做了什么？inputSchema 是什么？
装饰器从 Python 函数中自动提取三类元信息：①函数名作为 Tool 的 name；②docstring 首行作为 description，描述工具功能；③参数类型注解和 Args 说明自动生成 inputSchema。inputSchema 遵循 JSON Schema 规范，是一段"描述另一个 JSON 结构"的 JSON，定义了参数名称、类型和是否必填。模型在选择工具和提取参数时严格遵守 inputSchema，描述写得越清楚，模型传参的准确率越高。
为什么说"MCP 与模型无关"？这有什么实际意义？
MCP 协议只作用于 Host↔Server 这一段，消息里没有任何与模型相关的字段。你可以完全不用任何 Host 或模型，直接在终端用 JSON-RPC 格式与 Server 通信（手动发送 initialize、tools/list、tools/call）。实际意义有三：①Server 开发不需要考虑模型差异；②理论上任何语言甚至 shell 脚本都能实现 Server，只要遵循 JSON-RPC；③不同 Host 可以连接同一个 Server，Server 代码零改动。
MCP 通信为什么用 STDIO？还有什么替代方案？
STDIO（标准输入输出）是目前绝大多数 MCP Server 采用的传输方式，优点是实现简单（从 stdin 读请求、向 stdout 写响应）、安全（进程间通信不暴露网络端口）、轻量（无需网络库）。缺点是 Host 和 Server 必须在同一台机器上。替代方案是 HTTP + SSE（Streamable HTTP），适合跨机器或远程部署。使用 STDIO 时务必设置 log_level="error" 并让日志走 stderr，否则日志输出会污染协议通道。
initialize 握手阶段交换了哪些信息？为什么需要版本协商？
Client 在 initialize 请求中携带 protocolVersion（如 2024-11-05）、clientInfo（名称与版本）和 capabilities（支持的能力，如采样、根目录访问）。Server 在响应中返回自己实际使用的 protocolVersion、serverInfo 和能力声明。版本协商是协议演进的安全阀：当 Client 支持的版本与 Server 完全不兼容时，Server 会直接断开连接，而不是用错误的语义勉强通信。握手完成后 Client 还要发一条 initialized 通知，此后才允许发送 tools/list 等业务请求。
STDIO 模式下 Server 加载失败，如何系统排查？
按三层排查：①先看是不是超时——uvx/npx 首次下载依赖可能超过默认 60 秒，先在终端手动执行一次命令预热缓存；②再看协议通道是否被污染——写一个中间人脚本记录 stdout 的每一行，任何非 JSON 输出（print、第三方库 banner）都会让 Host 解析失败，修复方式是日志改走 stderr；③最后看协议语义——用 MCP Inspector 或手动输入 JSON 验证 initialize 和 tools/list 的响应是否正常。这三层覆盖了绝大多数加载失败问题。
FastMCP 和手写 JSON-RPC 有什么区别？该选哪种？
FastMCP 是官方 SDK 的高级封装，用装饰器自动完成函数到 Tool 的转换、inputSchema 生成和协议消息的编解码，几行代码就能跑起一个 Server。手写 JSON-RPC 则需要自己处理 initialize 握手、消息 id 配对、错误码等细节，通常只在需要极端控制或移植到无 SDK 语言时才用。日常开发应优先 FastMCP：它跟随官方协议版本演进，能避免自己实现时踩协议细节的坑。理解手写层的价值在于调试——当你看得懂原始 JSON 消息时，FastMCP 出错才不至于无从下手。
