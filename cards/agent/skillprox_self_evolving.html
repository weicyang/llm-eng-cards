A30 · SkillProX 自进化 Skill 四步法

港科大 × 澳门大学 SkillProx — 前向闭环诊断 · 双指标门禁与回滚 · 冻结留一法效应审计 · 准确率与压缩率的帕累托前沿

Skill 自进化真正难的不是"想出一条新规则"，而是"证明这条规则确实有用"和"把不再有用的旧规则拿掉"——SkillProx 用同批重跑守住前者，用冻结留一法审计守住后者。

一、只增不减的 Skill 会自己变差

Skill 已经开始像模型参数一样被"训练"了：权重一个都不改，Agent 每跑完一批任务，执行结果就被拿来修改 Skill 文本。这条路线的吸引力很明显——轻量、可读、可回滚、不用一张卡。但它有两个会随时间放大的裂缝。

第一个裂缝是诊断和结果之间没有闭环。模型读完失败轨迹，写出一段"错误发生在第三步，因为没有先校验列类型"的分析，这段分析在语义上完全说得通，于是被当成有效的更新方向直接写进 Skill。可"听起来合理"和"实际有用"是两件事，写进去之后任务表现完全可能变差，而且没有任何环节会去测量它、更没有环节把这个测量结果反馈给下一次诊断。这就是开环更新——更新方向的质量由语义合理性判定，而不是由实测后果判定。

第二个裂缝是删除没有被当成一件独立的事。既有框架把删除当成"编辑操作"里的一种普通选项，和新增、替换并列。实际结果是规则只增不减：重复的程序性指令、只适合某一道题的具体解法、以及过度泛化到近乎废话的经验，全部堆在同一份文件里互相干扰。SkillProx 论文（arXiv:2608.07449，香港科技大学联合澳门大学）指出的这两个缺口，正是它要补的两块。

问题类型典型的 Skill 文本诊断为什么看起来合理实际后果
只适合单题的具体解法"处理销售表时先删除第 3 行表头"那道题确实是这么修好的换一份表格直接删错数据
过度泛化的经验"操作前应充分理解数据结构"没有一句是错的不产生任何行为差异，纯占上下文

与旧规则冲突新加"批量一次性写入" vs 旧的"逐格校验"各自的证据都成立模型在两条规则间摇摆，行为不稳定

SkillProx 之前的两条主线都栽在同一处。SkillOpt 给每次编辑加了一个"文本学习率"和一道 held-out 门；SkillGrad 把整个 Skill 包当作结构化参数，用轨迹级的损失证据、文本梯度（把自然语言反馈当成梯度方向反向传播回提示词或文本工件，源自 TextGrad 的思路）和动量来更新它。两者都比手写 Skill 前进了一大步，但都仍然是开环且面向增长的：诊断被当作有效方向接受而不验证其实际效果，删除只是编辑操作之一而非专门的收缩机制。

还有一个更基础的警示。论文引用 SkillsBench 的结论：精选 Skill 在不同领域的帮助很不均衡，而模型自己生成的 Skill 带来的收益微弱甚至为负。也就是说"让模型自己写 Skill"这件事本身并不天然有效——它需要一套验证机制才能变成正收益。

论文实验数据（SkillProx 论文，Qwen3.6-27B，十次独立训练）：开环式 Skill 演化的 OJ 硬准确率平均为 50.30 ± 2.50，而把实测效果反馈给后续诊断的闭环变体为 51.40 ± 1.51。均值提高约 1.1 个点，但更值得注意的是标准差从 2.50 降到 1.51——闭环带来的不只是更高的分数，更是更少的运气成分。论文对代表性训练轨迹的检查也印证了动机：确实存在一些"单看诊断完全合理"的更新，写进 Skill 之后任务表现反而下降。

文本更新的质量无法从它的语义合理性推断出来——一段读起来无懈可击的诊断，写进 Skill 之后照样可能让成绩下降，唯一可信的判据是重跑一遍。

二、目标函数：任务损失 + 复杂度

SkillProx 把 Skill 演化写成一个复合优化问题：既要任务做得好，又要 Skill 不要无限膨胀。Skill 工件指的是一个结构化的文本产物——一份主指令文件 SKILL.md，加一个可选的 references/ 目录（放辅助说明、示例和资源）。复杂度就取这些文件的总字符数。

minX Jλ(X) = LT(X) + λ · G(X), λ ≥ 0

前一项是任务损失，后一项是文本复杂度，λ 控制两者的相对权重。这个形式正是近端梯度（Proximal Gradient，一类处理"可微主项 + 不可微正则项"的优化算法：交替执行一步沿任务损失方向的梯度步，和一次求解带正则约束的近端子问题）的标准形式，SkillProx 的名字就来自这里——ProX 借用的是近端梯度"前后两段分治"的结构：先改善任务表现，再控制 Skill 复杂度。

这里必须如实说明这个类比的边界：SkillProx 并没有在文本上计算数值梯度，也不具备传统近端算法的收敛保证。它借的是算法的结构骨架和职责划分，不是数学性质。论文自己也是以 "proximal-gradient-inspired"（受近端梯度启发）来定位的。把它当成一个好用的工程隐喻是恰当的，把它当成有理论保证的优化器就过头了。

近端梯度算法SkillProx 的对应物类比是否严格
前向梯度步：沿任务损失下降诊断驱动的编辑 + 同批重跑验证结构对应，无数值梯度
后向步：求解近端子问题冻结效用审计 + 语义收缩 + 结构检查 + 验证门控结构对应，无闭式解
局部性：距离惩罚项限制单步跨度单目标局部编辑 + 累计压缩软上限 ρ作用相同，形式不同
收缩强度：由步长与正则权重共同决定候选阈值 τ、硬准确率容差 δh、单元准确率容差 δc、压缩范围 ρ 分别控制拆成四个独立旋钮，非单一标量
收敛性保证没有不对应

两项指标贯穿全流程，需要先分清。硬准确率（hard accuracy）是任务级别的对错——整道题做对才算对，是最终交付口径。单元准确率（mean cell accuracy，论文中的平均单元格准确率）是局部结果的正确比例——在表格类任务里就是逐格比对的平均正确率，它比硬准确率细腻得多，能捕捉到"整题没做对但大部分格子对了"这类中间状态。两个指标必须同时看：只看硬准确率，方差太大、信号太稀疏；只看单元准确率，可能出现"处处接近正确但没有一道题真正做对"的假进展。

ProX 这个名字的全部含义就是"两段分治"：前一段管把任务做对，后一段管别让 Skill 长到把自己绊倒——它借的是近端梯度的分工结构，不是它的数学保证。

三、前向闭环：改完立刻同批重跑

整套方法拆成四步，前两步构成前向闭环（把任务做对），后两步构成后向收缩（把 Skill 变瘦）。

┌──────────────── 前向：闭环诊断演化 X₀ → X_f ────────────────┐ ① 诊断失败 失败轨迹 ⨉ 成功轨迹 对照 ──▶ 错在哪一步？ 当时用了哪条规则？ 该改 SKILL.md 的哪里？ │ 产出候选补丁 ▼ ② 在同一批任务 B_k 上重跑（不换题） │ ┌──────────────────┴──────────────────┐ 硬准确率严格提升 无严格提升 │ │ 立即采纳，早停 最多再试 3 次 │ 按 硬→单元 字典序取最好 │ │ │ 仍需通过双指标门 │ ┌──────────┴────┐ │ 通过 不通过 ▼ ▼ ▼ 提交为新的 X 提交为新的 X 回滚 │ 被拒方向 + 实测效果 ──────────────────────────┘ 写回下一轮 ① 的诊断输入 └───────────────────────────────────────────────────────────────┘ │ K 轮之后 ▼ ┌──────────── 后向：效用感知近端精炼 X_f → X* ────────────────┐ ③ 冻结留一法效用审计（固定验证集 V） ④ 验证门控的合并 / 降权 / 删除 └───────────────────────────────────────────────────────────────┘

3.1 第一步：诊断必须有对照组

诊断不是让模型盯着一条失败轨迹想原因，而是把失败轨迹和成功轨迹配成对照来读。要回答三个具体问题：错误发生在哪一步、当时生效的是哪条规则、SKILL.md 的哪个位置该改。有对照组的意义在于排除"这个做法本来就不行"和"这次运气不好"——如果成功轨迹在同一步用了同一条规则，那问题就不在这条规则上。

关键约束是：这份诊断不能直接进入 Skill。它只是一个候选更新方向。

3.2 第二步：同一批任务，不换题

候选补丁写进一份试用版 Skill 之后，立刻在同一批训练任务上重跑。"同一批"这三个字是这一步的核心：如果换一批题再测，分数变化里就混进了题目难度的差异，无法归因到这次编辑上。同批重跑相当于做了一次配对比较，把题目这个变量固定住。

接受条件是一道双指标门——硬准确率和单元准确率两项都要满足各自的接受条件，门才为真。搜索策略上有个提效设计：第一个取得硬准确率严格提升的候选立刻采纳并早停，不再继续试；如果没有任何候选严格提升硬准确率，那么最多评估三次尝试，按"先硬准确率、再单元准确率"的字典序挑出最好的那个——但这个胜者仍然必须通过双指标门，否则整次编辑回滚，Skill 保持原样。

回滚不等于丢弃。被拒的编辑方向和它的实测效果都会保留下来，作为下一轮诊断的输入。所以诊断过程是随着"前几次改动的真实后果"演进的，而不是每次都从语义分析重新开始——这正是"闭环"二字的含义，也是它相对 SkillGrad 那类开环方法的关键差异。

门禁要素设定作用放松它会怎样
重跑任务集与本轮诊断相同的训练批 Bk固定题目难度，让差异可归因分数变化混入题目差异，判定失真
硬准确率条件严格提升即早停采纳抓住真正有效的改动，省算力无早停则每次都跑满 3 次，成本翻倍
单元准确率条件与硬准确率同时满足才通过防止"整题对了但局部大面积退化"只看硬准确率，方差大、易被噪声骗
尝试次数上限最多 3 次限定单轮成本，避免死磕一个方向在同一个错误方向上无限重试
失败后的处置回滚 + 方向留档下一轮诊断带着实测结果出发下一轮重复提出同一个无效修改

这一步和改代码的类比很贴切：报错帮你找到方向，但测试才决定代码能不能合并。模型说得有道理，不能代替运行结果。

诊断给方向，重跑给判决——而且必须在同一批题上重跑，否则你测到的是题目难度差异，不是这次修改的效果。

四、后向收缩：冻结留一法审计

前向闭环跑完 K 轮，得到一份任务表现更好的 Skill。但新经验通过了检查，旧经验还没有——那些重复的、过时的、过度泛化的内容仍然留在文件里干扰模型判断。后向阶段专门处理它们。

4.1 第三步：把 Skill 拆成知识单元，逐个做留一法

先把 Skill 拆成一个个可审计的知识单元——语义上自成一体的规则片段、段落或示例，是收缩操作的最小粒度。然后对每个单元做留一法（leave-one-out）：暂时把这一个单元拿掉，用固定验证集重跑，看成绩怎么变。

拿掉某个单元后效用值符号结论处置
成绩明显下降正（较大）这条知识在起作用保留，不进候选集
成绩基本不变约等于 0存在但不产生行为差异进候选集，优先考虑合并
成绩反而更好负这条知识在主动干扰进候选集，优先考虑删除

这里有一个关键的工程设计：冻结效用审计——所有单元的效用值在收缩阶段开始之前一次性测完，然后在整个候选遍历过程中保持冻结，不随每次删除而重测。原因是成本：如果每删一条就重新评估全部剩余单元，评测次数会从线性变成平方级。代价是效用值会随 Skill 变化而略微失准，论文用后面的验证门控来兜住这个误差。候选集的筛选规则是取单元准确率效用低于阈值 τ 的那些单元，论文的默认设置是 τ = −0.001——也就是只有"拿掉后基本不变或更好"的单元才会被列为清理候选。

4.2 第四步：合并、降权、删除，每一步都要过验证

收缩不是一刀切地删。论文给了三个梯度递进的动作，先处理贡献低的内容，只有确认有害的才真删：

动作做什么适用的单元为什么不直接删
合并（consolidation）把重复或高度相似的段落归并成一条表述内容重复、措辞不一致信息本身有用，问题只在冗余和歧义
降权（demotion）降低规则的地位，例如从强制指令改为可选参考，或移到引用文件里过度泛化、只在少数场景成立直接删可能丢掉边缘场景的兜底
删除（removal）整条移除效用为负、确认在干扰判断——已确认有害，删是正确处置

每一次收缩编辑都先应用到一份试用副本上，再拿固定验证集跑一遍，必须同时满足三组条件才允许替换正式版本：硬准确率不许下降（δh = 0，这是一条硬红线）；单元准确率的单次下降不超过 δc = 0.02（归一化到 [0,1] 时相当于两个百分点）；累计压缩比例不超过 ρ = 0.10。被拒的试用副本直接丢弃，被接受的才替换活跃 Skill。

两个容易误读的细节。第一，ρ = 0.10 是软上限：压缩条件是在应用本次编辑之前基于当前版本判定的，所以最后一次被接受的编辑可能把总压缩率推过 10%。第二，某个候选没有产生可接受的删除，不会终止整个循环——处理会继续走完候选序列。这两点合起来意味着收缩是"尽力而为但绝不牺牲硬准确率"的。

论文实验数据（SkillProx 论文，代表性案例）：一次效用感知的合并操作只把 Skill 体积缩小了 3.12%，OJ 硬准确率却从 46% 提升到 54%——删掉的那 3% 不是无害的冗余，而是在主动拖累判断。这个案例说明留一法审计找出的"负效用单元"是真实存在的：Skill 里确实有一部分内容，它的存在比不存在更糟。它也解释了为什么删除需要被当成一种专门机制，而不是编辑操作里的普通一项。

留一法回答的是一个此前没人问的问题："如果没有这条规则，成绩会怎样？"——只有能回答这个问题，删除才从赌博变成决策。

五、实验结果：压缩与准确率权衡

论文在 SpreadsheetBench、WikiTQ、HiTab 三个基准上、用 Qwen3.5-4B、Qwen3.5-27B、Qwen3.6-27B 三个骨干模型做了评测，同时报告分布内（IID）和分布外（OOD）表现。总体结论是相对最强的梯度式基线 SkillGrad 平均提升约 3.0 个百分点。

数据来源：SkillProx 论文。三个基准的提升幅度差别很大，最大的是 SpreadsheetBench——相对人工编写 Skill 的 IID 提升最高达 17.8 个百分点。规律和 Skill 演化的一般经验一致：操作序列固定、工具约束明确的任务最适合把经验写成程序性规则；而 WikiTQ 这类以理解为主的任务，程序性知识能帮的忙有限（人工 Skill 的 85.7 已经接近 SkillProx 的 86.2）。

更值得注意的是分布外表现。在 Qwen3.5-4B 上，SkillOpt 演化出的 Skill 在 WikiTQ 和 HiTab 的 OOD 得分分别跌到 26.0 和 16.0，而 SkillProx 是 78.5 和 69.2。这个差距的量级已经不是"更好一点"，而是"一个崩了、一个没崩"——开环增长式的方法把大量只适合训练分布的具体解法写进了 Skill，换到分布外场景这些解法直接变成误导。

消融实验说明两个阶段的贡献是互补的，而且去掉后向收缩的损失（−2.5）比去掉前向闭环（−1.5）更大。这个次序有点反直觉——直觉上"改得对"应该比"删得掉"更重要，但数据说的是：只靠前向编辑会持续累积冗余内容，这些冗余最终反噬任务表现。

5.1 压缩到什么程度合适：一条帕累托前沿

论文把 Prox 阶段离线应用到三份已由 Qwen3.6-27B 前向闭环产出的 Skill 上（不重新训练），扫描候选阈值 τ 观察压缩率与准确率的关系。

这条曲线的形状是这一章最重要的信息：在很宽的区间里，把 Skill 变短和把任务做对是同一个方向。不做 Prox 的锚点是 50.3%；τ = −0.001 时准确率达到最高的 52.3% 且已压缩 25.7%；τ = 0.005 时压缩率升到 41.5%，准确率仍保持 52.0%。只有压缩到接近 75% 时准确率才回落到 51.0%，而这个数字依然高于完全不压缩。

论文还给出一个支持性的相关分析：最终 Skill 长度与 IID 硬准确率呈负相关，相关系数约为 −0.628。以及一个关于模型能力的观察：4B 最终产出的 Skill 平均比 27B 长约 45%，但两者的主文件 SKILL.md 都收敛到大约 15k 字符——差异几乎全部来自引用文件，4B 产出的引用内容大约是 27B 的两倍。这说明模型规模影响的是"需要多少补充指导"，而不是核心 Skill 结构的大小。

论文实验数据（SkillProx 论文 Figure 2 及相关分析）：把一份 Skill 移除掉 74.9% 的内容之后，OJ 硬准确率仍有 51.0%，高于完全不压缩的 50.3%；而最优压缩点（25.7%）反而给出全场最高的 52.3%。同时最终 Skill 长度与 IID 硬准确率的相关系数是 −0.628。三个数字指向同一个判断：一份长期只增不减的 Skill，其中相当大的比例既不是资产也不是中性负担，而是负债。

最后要说清论文自己承认的三条局限，它们直接决定这套方法能不能照搬。第一，评测只覆盖了三个高度结构化的表格类基准，能否推广到更开放的编程或推理场景是未知的。第二，留一法审计需要对每一个知识单元跑一次完整评测，LLM 调用开销很大。第三，Prox 的门控基于一个固定验证集，存在过拟合到该验证集的风险。

在很宽的范围内，让 Skill 变短和让任务做对是同一件事——所以"删规则"不该被当成有风险的清理动作，它本身就是一种优化。

六、简化版四步法与适用边界

完整方法的成本不低：前向每轮最多 3 次同批重跑，后向要为每个知识单元跑一次完整验证集。所以它适合的是高价值、会被反复调用的 Skill——演化是一次性投入，调用是重复收益，只有调用足够频繁才摊得平。

落地顺序上，最务实的路径是先把前向那一半做扎实：准备一组固定任务，以后每次修改 Skill 都完整重跑，结果变差就恢复上一个版本。这一步不需要任何论文里的机制，但已经能挡掉最常见的事故类型。等 Skill 表现稳定、内容也积累到一定体量之后，再逐条把旧内容拿掉，看哪些规则真的影响结果——这就是简化版的留一法审计。

  • 在同一批任务上重跑，把题目难度这个变量固定住
  • 任务级和局部级两个指标同时看，两项都不许变差
  • 回滚时把被拒方向和实测分数留给下一轮诊断
  • 诊断时给失败轨迹配一条成功轨迹做对照
  • 效用值在收缩开始前一次测完并冻结，避免平方级评测开销
  • 每次收缩先改试用副本，过了验证才替换正式版
  • 硬准确率设成不许下降的红线，局部指标才给容差
  • 先合并、再降权，只删确认为负效用的内容
  • 凭诊断的语义合理性就把修改合并进 Skill
  • 换一批新题来验证刚做的修改
  • 一轮里同时改多处，然后看总分决定去留
  • 把删除当成普通编辑操作，指望它自然发生
  • 每删一条就重测全部剩余单元的效用
  • 在只有十几条任务的验证集上跑留一法（信号全是噪声）
  • 为了达到压缩目标而牺牲硬准确率
  • 把"近端梯度"的收敛保证当成这套方法的性质

和同类工作的分工需要说清。《A29 · WikiSkill 三层知识架构》和本文都在做 Skill 自进化，但重心不同：WikiSkill 侧重"经验怎么分层沉淀"——用 Raw / Wiki / Skills 三层不同的写入权限，保证证据不被结论覆盖、失败提案不被回滚丢弃；SkillProx 侧重"修改怎么验证、旧知识怎么收缩"——用同批重跑给每次编辑定罪或定功，用留一法给每条旧规则算效用。两者其实互补：WikiSkill 的 Gating 只判断"新提案能不能进"，不回答"已经进来的那些还该不该留"，而后者正是 SkillProx 的后向阶段。再往上一层的系统视角——经验提取、能力固化、四级受控发布与熔断——见 《A65 · Agent 自主进化工程路径》。

做不了完整四步也没关系，先把"每次改完都在同一批题上重跑、变差就回滚"这一条做到位——它成本最低，却挡掉了绝大多数把 Skill 越改越差的事故。

Q&A

为什么必须在"同一批任务"上重跑，换一批新题不是更能验证泛化性吗？
这里要区分两个不同的问题。前向重跑要回答的是"这次编辑本身有没有效果"，属于归因问题；换一批题会把题目难度差异混进分数变化里，导致你无法分清是编辑起了作用还是新题更容易。同批重跑相当于做配对比较，把题目变量固定住，信号最干净。泛化性是另一个环节的职责——后向阶段的收缩用的是独立的固定验证集，论文还额外报告了分布外（OOD）表现来考察泛化。所以不是不测泛化，而是不在归因这一步测。
硬准确率和单元准确率为什么要同时看？只看最终任务对不对不是更直接吗？
硬准确率是最终交付口径，确实最重要，但它作为优化信号太稀疏也太抖：一批题里对错只有几个整数级的变化，很容易被采样噪声淹没，很多真实的小幅改善根本体现不出来。单元准确率是逐格比对的平均正确率，细腻得多，能反映"这次修改让大部分中间结果更接近正确"这类进展。但只看它也不行，会出现处处接近正确却没有一道题真正做对的假进展。SkillProx 的处理是两项都必须满足接受条件，并且在收缩阶段把硬准确率设成不许下降的红线（δh = 0），只给单元准确率两个百分点的容差——主次分明。
留一法的效用值为什么要冻结？每删一条重测一次不是更准确吗？
更准确，但成本承受不了。假设 Skill 有 n 个知识单元，冻结方案是在收缩前跑 n 次完整验证集，之后遍历候选时不再重测；如果每删一条就重测全部剩余单元，评测次数会从 O(n) 涨到 O(n²)。而每一次评测都是一整个验证集的 LLM 调用，n 稍大就完全不可行——论文自己也把留一法审计的开销列为主要局限之一。冻结带来的误差（效用值会随 Skill 变化而略微失准）由后面的验证门控兜住：每次收缩编辑都要在试用副本上重跑验证集，硬准确率不许下降。也就是说效用值只用于排候选顺序，真正的生死判定还是靠实测。
"过度泛化的规则降权"具体是降什么？和删除的区别在哪？
降权（demotion）是降低这条规则在 Skill 里的地位而不是移除它的信息，典型手法有两种：一是把强制性的指令语气改成可选参考，让模型不再无条件遵守；二是把它从主文件 SKILL.md 移到 references/ 目录里，从"每次都注入"变成"需要时才查"。适用对象是那些只在少数场景成立、但那些场景确实存在的规则。之所以不直接删，是因为留一法测的是在固定验证集上的平均效用——一条只在 5% 场景里救命的规则，平均效用接近零，直接删掉会丢掉这部分兜底。降权是在"占用上下文"和"保留兜底"之间取中间态。真正该删的是效用为负的那些，也就是拿掉之后成绩反而变好、确认在干扰判断的内容。
删掉 74.9% 的内容准确率只掉一点，是不是说明 Skill 大部分内容本来就没用？
大致是这个意思，但要精确一点说。那条曲线的形状是：不压缩时 50.3%，压缩 25.7% 时升到最高的 52.3%，压缩 41.5% 时还有 52.0%，压到 74.9% 才回落到 51.0%——注意即便在最极端的压缩点，成绩仍然高于完全不压缩。所以结论不是"内容没用"，而是"相当大比例的内容是负债"：它们既不提升表现，还要占上下文、还可能和有效规则互相干扰。配合"最终 Skill 长度与 IID 硬准确率相关系数 −0.628"这个数字，方向就很清楚了。不过这些数字来自三个高度结构化的表格类基准，不要直接套到开放式编程或推理场景上。
ProX 借用了近端梯度，这个类比有多严格？可以把它当优化算法来推理吗？
不可以，它是结构类比而非数学对应。相同的部分是职责划分：近端梯度交替执行"沿任务损失下降的梯度步"和"求解带正则约束的近端子问题"，SkillProx 对应地交替执行"诊断驱动的编辑 + 同批重跑"和"效用审计 + 验证门控收缩"；近端算法用距离惩罚项限制单步跨度，SkillProx 用单目标局部编辑加累计压缩软上限 ρ 起同样作用。不同的部分是本质性的：文本上没有计算任何数值梯度，收缩强度也不是由单一的步长乘正则权重决定，而是拆成 τ、δh、δc、ρ 四个独立旋钮；最关键的是它不具备传统近端算法的收敛保证。论文本身用的定位词是 "proximal-gradient-inspired"（受启发），把它当成好用的工程隐喻是恰当的，当成有理论保证的优化器就过头了。
我们只有几十条任务，能做这套东西吗？
前向那一半可以做，后向的留一法审计建议先放着。前向只需要一组固定任务和一个能自动判对错的口径：每次改完 Skill 就完整重跑，两个指标（任务级通过率、局部正确率）任一变差就恢复上一版，被拒的方向记下来给下次诊断参考。这一步在几十条任务上是有意义的，因为它检测的是"明显的回归"，信号足够强。留一法则不同：它要在每次拿掉一个单元后分辨出几个点的差异，任务数太少时这个差异完全在采样噪声范围内，测出来的效用值是随机数，照着它删规则比不删更危险。合理的推进节奏是先靠前向兜底，同时持续扩充固定任务集，等规模上到能稳定分辨小幅差异了，再启动收缩。
这和 WikiSkill 那套三层架构是竞争关系吗？该选哪个？
是互补关系，重心不同。《A29 · WikiSkill 三层知识架构》解决的是"经验怎么分层沉淀"：用 Raw / Wiki / Skills 三层不同的写入权限，保证原始证据不被早期错误结论覆盖、失败提案不因为 Skill 回滚而丢失，让下一轮的提案能站在累积知识上。SkillProx 解决的是"修改怎么验证、旧知识怎么收缩"：同批重跑给每次编辑定功或定罪，留一法给每条旧规则算效用。关键的互补点在于——WikiSkill 的 Gating 只判断"新提案能不能进来"，它不回答"已经进来的那些还该不该留"，而这正是 SkillProx 后向阶段的全部内容。工程上完全可以合起来用：三层架构做知识组织，双指标同批重跑做前向门禁，留一法审计定期做知识收缩。
