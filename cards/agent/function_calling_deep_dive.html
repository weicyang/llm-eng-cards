A02 · Function Calling 工程实践

Function Calling Deep Dive — LLM 边界认知、Tool Description 设计、tool_choice 控制、并行调用、结构化错误、多轮工具使用、跨厂商差异、生产踩坑

Function Calling 的本质是"LLM 输出调用意图 JSON，你的代码执行"——LLM 是决策大脑，不是执行器。这个边界一旦模糊，生产系统必出事故。

一、核心认知：LLM 到底"执行"了函数吗？

一句话核心观点

LLM 只输出"我想调什么工具、传什么参数"的结构化 JSON，真正执行的代码 100% 在你自己的应用里跑。

四步流程

步骤谁来做具体动作
1. 定义工具开发者写 JSON Schema，描述函数名、参数、类型
2. 生成调用意图LLM输出 {"name": "get_weather", "args": {"city": "北京"}}
3. 解析并执行你的代码根据函数名和参数去调真实 API
4. 回传结果开发者把执行结果塞回 messages，交给 LLM 生成最终回答
Function Call 四步流程: 用户提问: "北京天气怎么样" │ ▼ ┌─────────────────────────────────┐ │ Step 1: 定义工具 (开发者) │ │ JSON Schema: get_weather │ └──────────────┬──────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ Step 2: LLM 生成调用意图 │ │ 输出: {"name": "get_weather", │ │ "args": {"city": "北京"}}│ └──────────────┬──────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ Step 3: 你的代码执行 │ │ 调用真实天气 API │ └──────────────┬──────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ Step 4: 回传结果 │ │ role: "tool" │ │ tool_call_id: "call_abc123" │ └──────────────┬──────────────────┘ │ ▼ LLM 生成最终回答

为什么设计成"LLM 不执行代码"？这是 Function Calling 最核心的安全设计。如果 LLM 能执行任意代码，Prompt Injection 就能直接拿到服务器的 shell。

  • LLM 只输出 JSON 意图描述
  • 开发者代码执行具体操作
  • 执行结果回传给 LLM 做下一步决策
  • 让 LLM 直接执行代码或命令
  • 信任 LLM 输出的参数不做校验
  • 把敏感操作（删除/支付）不做二次确认

安全对比：

架构Prompt Injection 后果攻击面
LLM 直接执行代码拿到服务器 shell无限大
Function Calling（当前）最多调用已注册的工具受限于工具列表

可控性体现在：所有副作用都在你自己的代码里，你能加权限校验、限流、审计日志。可测试性体现在：LLM 的输出是纯 JSON，能录制回放做单元测试。

核心价值：Function Calling 的核心价值是将 LLM 的自然语言理解能力转化为结构化的 API 调用能力——它是 Agent 的基础设施，没有它，Agent 无法与外部世界交互。它将 LLM 从"文本生成器"升级为"决策引擎"，让 AI 能调用搜索引擎、查询数据库、发送邮件、操作文件系统等。Function Calling 不是让 LLM "执行函数"，而是让 LLM "描述它想调用什么函数"——真正的执行在应用层，这个分离设计是 Agent 架构的基石。

二、Tool Description：你是写给谁看的？

为什么这题是送命题

Tool Description 是 LLM 选工具的唯一依据。LLM 看不到你的函数实现，也看不到你的注释，它选不选调你这个工具，就看你 description 写得好不好。

黄金结构：四件套

必写字段作用示例
使用场景LLM 判断"该不该选我""用户询问订单状态时使用"
输入约束LLM 判断"参数格式对不对""9-12 位纯数字"
返回格式LLM 知道"回来怎么解读""{status, logistics}"
禁止场景LLM 判断"什么时候别选我""无订单号时先追问"

对比：人话 vs 给 LLM 的话

写给 LLM 看的 description：

"查询订单状态。仅用于用户明确提供订单号的场景。返回 {status, logistics, updated_at}。若用户未提供订单号，先用 ask_user 追问，禁止本工具回填默认值。"

写给人看的 description：

"查询订单信息"

（太模糊，LLM 不知道什么时候该用、参数什么格式、返回什么）

核心原则：Description 是写给 LLM 看的产品文档，不是写给同事看的注释。好的 Description 应该像 API 文档一样：明确输入输出、标注边界条件、给出使用示例。

Trade-off：写得太详细会不会浪费 Token？

会。每个工具的 description 都会塞进 LLM 的上下文。但这是必要成本：description 每省 50 token，工具选错率可能上升 5-10%。

解决方案：工具按意图分组，按需加载，不要一次把 50 个工具全塞进去。

工具定义三要素（JSON Schema）

工具描述的质量直接决定 LLM 的调用准确率——description 不是给人看的，是给 LLM 看的。好的描述让 LLM 准确判断"何时调用"和"如何传参"。

要素作用关键要点
name函数标识符snake_case，动词+名词（get_weather）
description告诉 LLM 何时调用清晰描述功能+触发时机（"当用户询问天气时调用"）
parameters约束调用参数每个参数有 description，用 enum/minimum/maximum 约束

工具描述最佳实践

原则好的示例差的示例
明确用途"查询数据库中的用户信息，按 ID 或邮箱搜索""查用户"
说明触发时机"当用户请求发送邮件时调用""邮件功能"
参数有描述"ISO 8601 日期格式，如 2024-01-15"无 description
用 enum 约束"enum": ["asc", "desc"]"type": "string"（无约束）
enum 字段极其重要：它约束了参数取值范围，大幅减少幻觉参数。例如 "unit": {"enum": ["celsius", "fahrenheit"]} 确保 LLM 不会传入 "kelvin" 或 "华氏度"。required 字段避免 LLM 遗漏关键参数——始终显式声明哪些参数必填。

Few-shot 示例设计：给 LLM 看"标准答案"

工具定义和 description 是静态规则，面对复杂调用场景（多参数组合、缺参追问、异常分支），还可以在 prompt 中追加几个完整的调用示例做 Few-shot（少样本示范）——直接给 LLM 看"标准答案长什么样"。示例的选取不是随手贴几个例子，数量、覆盖度、顺序、格式四条原则共同决定示范效果。

Few-shot 示例是 LLM 模仿的模板——每条示例都是模型眼中的"标准答案"。宁要 3 条覆盖正常+异常的高质量示例，不要 10 条同质化的 happy path。

示例选取四原则

原则要点原因
数量2-5 个性价比最高少于 2 个示范不足；超过 5 个收益递减，还挤占上下文预算、稀释模型对工具定义本身的注意力
覆盖正常情况 + 异常情况（空值、不存在、缺参追问）只给 happy path，模型遇到边界输入就会瞎猜参数；异常示例教会模型"这种情况该怎么处理"
顺序由简到繁排列先给最简单的单参数调用锚定基本格式，再逐步展示多参数、多工具组合，降低模仿门槛
格式与函数定义完全一致示例的字段名、类型、嵌套结构必须与 JSON Schema 逐字对齐，不一致等于给模型一个"错误模板"

示例编排模板

Function Call Few-shot 示例编排 (以 get_weather 为例): 示例 1 正常·最简 "北京天气" → {"city": "北京"} 示例 2 正常·多参数 "上海明天温度,要华氏度" → {"city": "上海", "date": "2025-06-01", "unit": "fahrenheit"} 示例 3 异常·空值 "查下天气" → 不调用工具, 先追问城市 示例 4 异常·不存在 "查火星天气" → 调用后如实告知无数据, 不编造 示例 5 复杂·多工具 "北京和上海天气" → 并行两个 tool_calls 排列顺序: 简单 → 复杂, 正常 → 异常 数量控制: 2-5 条, 按工具复杂度取, 不是越多越好

格式一致性是四条原则里最容易踩的坑。假设工具 schema 里参数名是 city_name，示例却写成 "city": "北京"——模型会在两种写法之间摇摆，下游解析就会偶发失败。同理，示例里的日期格式、枚举取值也要与 schema 约束保持一致：schema 声明了 "unit": {"enum": ["celsius", "fahrenheit"]}，示例就不能出现 "摄氏度" 这种中文写法。

  • 示例数量控制在 2-5 个，按工具复杂度取
  • 正常与异常场景都覆盖（空值、不存在、缺参）
  • 由简到繁排列，先锚定基本格式再展示复杂组合
  • 示例的字段名、类型、枚举值与工具 JSON Schema 完全一致
  • 不要堆十几个示例（收益递减还挤占上下文）
  • 不要只给 happy path（边界输入一来模型就瞎猜）
  • 不要第一个示例就上多工具复杂组合
  • 不要让示例格式与函数定义打架（字段名/单位/日期格式不一致）
三步法框架（也是排查顺序）：讲 Function Call 优化时按三层递进——① 示例与 Schema 优化：Few-shot 示例选取 + enum 约束，体现基本功；② 可靠性设计：指数退避重试、调用去重（详见相关工程卡片），证明考虑过稳定性；③ 成本控制：对相同参数产生相同结果的调用做结果缓存，展现全局观。排查调用准确率问题同样按这个顺序逐层检查：先看示例和工具定义质量，再看重试是否引入重复副作用，最后看缓存是否命中了过期数据。

三、Parallel Function Call：你用了吗？

Parallel Function Call 的本质是"识别任务 DAG——独立分支并行，依赖链路串行"。这是 Agent 工程的基本功。

一句话核心观点

GPT-4o / Claude 3.5+ 从 2024 年起就支持一次返回多个 tool_calls，并行执行，延迟从 T1 + T2 + T3 降到 max(T1, T2, T3)。

对比：串行 vs 并行

维度串行调用并行调用（Parallel FC）
延迟T1 + T2 + T3max(T1, T2, T3)
Token 消耗3 次对话轮次1 次对话轮次
模型支持所有模型GPT-4o、Claude 3.5+、Gemini 1.5+、DeepSeek V3+
适用场景工具间有依赖（A 的输出是 B 的输入）工具间独立（3 个查询没关系）
串行 vs 并行: 串行调用: Tool 1 → 等待 → Tool 2 → 等待 → Tool 3 总延迟: 2s + 3s + 1s = 6s 并行调用 (Parallel FC): Tool 1 ─┐ Tool 2 ─┼→ 并发执行 Tool 3 ─┘ 总延迟: max(2s, 3s, 1s) = 3s

什么时候不能用 Parallel FC？

  • 有依赖关系：比如"先查订单，再根据订单号查物流"——第二个工具的参数依赖第一个的结果，必须串行
  • 有副作用冲突：比如"先扣库存，再下单"——两个写操作并发可能导致数据不一致
  • 不支持的老模型：GPT-3.5、Claude 2 等老模型不支持，硬开会报错
核心原则：识别任务 DAG（有向无环图）——独立分支并行执行，依赖链路串行等待。这是 Agent 工程的基本功。

并行触发的判定与结果匹配

并行调用由 LLM 自主判断——当模型认为多个工具调用之间没有数据依赖时，会在同一个 response 中返回多个 tool_calls，应用层并发执行后一次性回传所有结果。

并行 vs 串行性能对比

场景串行调用并行调用加速比
2 个天气查询（各 200ms）~400ms + 2 轮 LLM~200ms + 1 轮 LLM~3x
5 个数据库查询（各 100ms）~500ms + 5 轮 LLM~100ms + 1 轮 LLM~10x
3 个有依赖关系的调用必须串行无法并行1x

每个 tool_call 有唯一的 id，对应的 tool result 必须通过 tool_call_id 匹配——这是并行调用正确工作的关键。开发者不能直接控制是否并行，但可以通过工具描述暗示依赖关系（如"需要先获取 A 才能查 B"）让 LLM 选择串行。

性能洞察：并行调用大幅减少 LLM 轮次——3 个独立查询从 3 轮变为 1 轮，不仅节省 token 还减少总延迟。典型场景：用户问"对比北京和上海天气"，LLM 自动返回两个并行 tool_calls。

四、tool_choice 控制

tool_choice 是给 Agent Loop 的"方向盘"——控制 LLM 是自主决策、必须调用还是直接回答。在 Agent 的不同阶段使用不同的 tool_choice 是生产环境的标准做法。

四种 tool_choice 模式

模式行为适用场景
autoLLM 自行决定是否调用工具通用 Agent，LLM 自主决策
requiredLLM 必须调用至少一个工具Agent Loop 非最终轮，防止"偷懒"直接回答
none禁止调用工具，只生成文本最终回答阶段，强制 LLM 给出结论
指定函数强制调用指定函数明确知道要调用哪个工具（如分类/路由）

Structured Output via Tool

一个重要的进阶技巧：定义一个"虚拟工具"（不真正执行），其 parameters schema 就是你想要的输出格式，再用 tool_choice 强制调用它——100% 得到符合 schema 的 JSON。这比 response_format 更灵活，支持嵌套对象、数组、enum 等复杂结构，且几乎所有支持工具的模型都兼容。

Agent Loop 最佳实践：前几轮用 auto 或 required（让 LLM 用工具获取信息），最后一轮用 none（强制生成最终答案，防止无限循环）。

五、工具报错怎么回传？

一句话核心观点

工具错误不是抛异常，是给 LLM 一封结构化的"故障说明信"——告诉它错在哪、能不能重试、怎么绕过。

错误信息回传是 Function Calling 最重要的设计——不要静默失败或抛异常，而是把错误信息返回给 LLM，让它自我修正。这比人类程序员的 try-catch 更优雅。

为什么 return "failed" 会死循环？

LLM 拿到 "failed: timeout"，它怎么想？"失败了，可能是参数不对。让我换个参数再试试。"于是它重试，重试，重试……每次重试都烧 token，每次重试都失败，直到触发 max_steps 才停。

结构化错误：三个关键字段

字段作用示例
error_code告诉 LLM 错在哪"TIMEOUT", "BAD_INPUT", "NO_PERMISSION"
retryable告诉 LLM 能不能重试true（超时）/ false（参数错）
hint告诉 LLM 下一步该干嘛"5 秒后重试" / "向用户追问正确订单号"

对比：错误回传的三种写法

结构化错误 + retryable + hint：

LLM 基于信号做决策：重试、追问、或降级。

return "failed" 或抛异常：

LLM 当作参数问题，改参数重试 → 死循环 + Token 爆炸。

核心认知：工具错误回传本质上是"跟 LLM 的一次对话"——LLM 看到错误信息后会自主决定是重试、换工具、还是告知用户失败。这说明 Agent 的控制流不是硬编码的 if-else，而是由 LLM 动态决策的。

常见错误与处理

错误类型原因处理方式
参数格式错误LLM 生成了不合法的 JSONJSON 修复 + 重新调用
幻觉函数名LLM 调用了不存在的工具返回错误信息 + 可用工具列表，让 LLM 重选
参数值越界数值超出 schema 约束校验后返回错误提示
工具执行失败API 超时 / 网络错误重试 + 降级 + 错误信息回传
结果过大工具返回数据超过 token 限制截断 / 摘要后回传

好的错误回传 vs 差的错误回传

维度好的回传差的回传
内容"表 'users' 不存在，可用的表有: customers, orders""Error"
建议"你可能想查询 'customers' 表"无建议

  • 返回有意义的错误信息（让 LLM 能自我修正）
  • 结果超 50K 字符时做截断/摘要
  • 设置合理的超时时间（30s 通用，60s 复杂操作）
  • 非幂等工具（发邮件）必须有去重机制
  • 不要静默失败——LLM 不知道发生了什么
  • 不要把 10MB SQL 结果直接塞进 context
  • 不要忽略超时——超时后返回错误让 LLM 换策略
  • 不要返回 "Error" 这种无意义的错误信息

六、多轮工具使用

多轮 Agent 的核心挑战是 Token 膨胀——每轮包含 assistant(tool_calls) + tool(result) + assistant(response)，10 轮工具调用可能消耗 50K+ tokens，需要对大型结果做摘要压缩。

多轮对话流程

多轮 Tool 使用流程: Round 1: 用户 → LLM → tool_call(查询Q3销售) → tool_result Round 2: LLM → tool_call(查询Q2销售对比) → tool_result Round 3: LLM → tool_call(搜索市场报告) → tool_result Round 4: LLM 综合所有数据 → 生成分析报告（finish_reason: "stop"） 关键约束: - 消息顺序必须严格: assistant(tool_calls) → tool(result) → 下一轮 - tool_call_id 是匹配调用与结果的唯一标识 - assistant 消息有 tool_calls 时 content 可以为 null
上下文管理策略：对超过 2000 字符的工具结果做摘要后再存入历史；超过 10 轮时考虑压缩早期工具调用记录；监控 token 使用量，接近上下文窗口限制时主动终止。

七、OpenAI vs Anthropic vs Google：格式差异

一句话核心观点

OpenAI 和 Anthropic 的 Function Call 格式不是"改个 API URL"的问题——role: tool 和 tool_result block 是两套玩法。

OpenAI vs Anthropic：三层字段差异

维度OpenAIAnthropic Claude

生产解法：中间抽象层（Adapter）

核心思想是"统一工具定义和结果回传，屏蔽不同厂商的格式差异"。业务还在探索期先绑一家别过早抽象；生产系统必抽，否则切模型的那一天代码就是屎山。

适配建议：用 LiteLLM 或 LangChain 的统一接口屏蔽厂商差异，底层自动转换消息格式。OpenAI 和 Anthropic 最大区别在于 tool result 的 role 不同——OpenAI 用专门的 "tool" 角色，Anthropic 把它放在 "user" 消息的 content block 中。
生产经验：切模型最难的不是改代码，是切完之后回归测试——每个 tool_call_id、每个 role、每个 content block 都得跑一遍冒烟测试。建议维护一套自动化的 Function Calling 测试用例集，覆盖所有注册工具的 happy path 和 error path。

八、生产踩坑：三个杀手锏

杀手锏 1：大返回值怎么处理（防 Token 爆炸）

核心设计：摘要进上下文，原始数据挂外部。LLM 按需通过 reference_id 拉取，避免一次性塞爆 128K 窗口。

杀手锏 2：工具幻觉怎么防

LLM 偶尔会调一个不存在的工具名（幻觉）。必须做工具名白名单校验：不在白名单里的工具直接返回结构化错误，告诉 LLM 可用工具列表。

生产案例

案例一：某 SaaS 产品的工具精简与结构化输出

生产验证：某 SaaS 产品将 35 个工具精简至 18 个（按功能域合并），模型工具选择错误率从 12% 降至 3.1%。关键发现：当工具数量 >20 时，模型开始"选择困难"（混淆相似功能工具），通过工具描述添加"使用场景"字段后错误率再降至 1.8%。Parallel Function Calling 上线后，3 个独立工具调用（查天气+查日历+发邮件）的延迟从串行 3.2s 降至并行 1.1s（降幅 66%）。Structured Output（JSON Schema 强制）使下游解析成功率从 87% 提升至 99.7%，每月减少 340 次解析异常告警。

案例二：某电商客服系统的分层路由

背景：日均 3 万次用户咨询，初期用 8 个工具（查订单、查物流、查退款等），LLM 选择准确率 94%。

问题：业务扩展后工具增至 35 个，选择准确率降至 71%，用户投诉"回答了不相关的内容"。

改造：引入分层路由——先让 LLM 选择工具类别（订单/物流/退款/账户），再展开该类别的 5-8 个具体工具。

效果：选择准确率恢复至 92%，平均响应延迟降低 15%（减少无效工具探索）。

Q&A

LLM 到底"执行"了函数吗？
不会。LLM 只输出"我想调什么工具、传什么参数"的结构化 JSON，真正执行的代码 100% 在你自己的应用里跑。这个设计是为了安全（防止 Prompt Injection 拿到 shell）、可控（所有副作用在你代码里）、可测试（LLM 输出是纯 JSON 可录制回放）。关键结论是："LLM 是决策大脑，不是执行器。这个边界一旦模糊，生产系统必出事故。"
Tool Description 是写给谁看的？
写给 LLM 看的产品文档，不是写给同事看的注释。黄金结构四件套：(1) 使用场景——LLM 判断"该不该选我"；(2) 输入约束——LLM 判断"参数格式对不对"；(3) 返回格式——LLM 知道"回来怎么解读"；(4) 禁止场景——LLM 判断"什么时候别选我"。写得太详细会浪费 Token，但这是必要成本：description 每省 50 token，工具选错率可能上升 5-10%。
Parallel Function Call 你用了吗？
GPT-4o / Claude 3.5+ 从 2024 年起就支持一次返回多个 tool_calls，并行执行，延迟从 T1+T2+T3 降到 max(T1,T2,T3)。什么时候不能用：(1) 有依赖关系——第二个工具的参数依赖第一个的结果，必须串行；(2) 有副作用冲突——两个写操作并发可能导致数据不一致；(3) 老模型不支持。识别任务 DAG——独立分支并行，依赖链路串行，这是 Agent 工程的基本功。
工具报错怎么回传？
工具错误不是抛异常，是给 LLM 一封结构化的"故障说明信"。三个关键字段：(1) error_code——告诉 LLM 错在哪（TIMEOUT/BAD_INPUT/NO_PERMISSION）；(2) retryable——告诉 LLM 能不能重试（true/false）；(3) hint——告诉 LLM 下一步该干嘛（"5 秒后重试"/"向用户追问"）。为什么不能 return "failed"？因为 LLM 会当作参数问题改参数重试，陷入死循环烧 Token。
OpenAI 和 Anthropic 的格式差异？
不是"改个 API URL"的问题，是两套玩法。三层差异：(1) 工具定义——OpenAI 用 function，Anthropic 用 input_schema；(2) 调用输出——OpenAI 是 tool_calls（message 级），Anthropic 是 tool_use（content block 级）；(3) 结果回传——OpenAI 是 role: tool，Anthropic 是 role: user + tool_result block。生产解法是用中间抽象层（Adapter）屏蔽差异。切模型最难的不是改代码，是切完之后回归测试。
工具不是越多越好，怎么判断粒度？
每加一个工具都在跟主任务抢 Token，10 个以内按需加载。粒度判断：参数组合 ≤ 5 种 → 1 个大工具；参数组合 > 5 种 → 拆成多个小工具；场景完全不同（读 vs 写）→ 一定拆，避免误触发。1 个大工具 LLM 选工具容易但参数组合爆炸；多个小工具 LLM 选择中等但参数简单。
Function Calling 和直接在 prompt 中要求 LLM 输出 JSON 有什么区别？
核心区别在三个层面：①可靠性：Function Calling 是模型训练时内置的能力，生成的 JSON 格式高度稳定；prompt 方式经常输出格式不规范的 JSON。②Schema 约束：Function Calling 有 JSON Schema 校验，参数类型、枚举值、必填项都有保证。③工具选择：Function Calling 支持 LLM 从多个工具中智能选择，并决定参数。④流程集成：Function Calling 与 Agent Loop 原生集成——finish_reason 告诉你这是工具调用还是最终回答。除非用不支持 Function Calling 的模型，否则都应使用 Function Calling。
并行 Function Calling 在什么情况下会被触发？开发者能控制吗？
并行调用由 LLM 自主判断——当模型认为多个工具调用之间没有数据依赖时，会在同一个 response 中返回多个 tool_calls。典型触发场景：同类查询（"北京和上海天气"→两次 get_weather）、独立操作（"搜索新闻并查汇率"）。开发者不能直接控制是否并行，但可以通过工具描述暗示依赖关系让 LLM 选择串行。OpenAI 提供 parallel_tool_calls 参数可以完全禁用并行。并行调用时，应用层需要并发执行所有工具并一次性回传所有结果。
tool_choice 的 required 和 auto 分别适用什么场景？
auto 是默认值，适合大多数场景——LLM 自主决定是直接回答还是调用工具，适用于通用聊天 Agent。required 强制 LLM 必须调用工具，适用于：①Agent Loop 的非最终轮——确保 Agent 不会提前终止；②结构化抽取——配合虚拟工具强制输出 JSON；③分类/路由——强制调用路由函数。none 用于最终回答轮——强制 LLM 用文本回答而非继续调工具。实际 Agent 通常在 Loop 中动态切换：前几轮用 auto 或 required，最后一轮用 none。
OpenAI、Anthropic、Google 三家的 Function Calling 协议主要差异在哪？
三大差异：①消息格式——OpenAI 用 role: "tool" 回传结果；Anthropic 把 tool_result 放在 role: "user" 的 content block 中；Google 用 role: "function"。②工具定义——OpenAI 用标准 JSON Schema；Anthropic 用 input_schema；Google 用 protobuf FunctionDeclaration。③特色功能——OpenAI 独有 strict mode（100% schema 合规）；Anthropic 的 tool_use 可以夹在 text 之间（更自然的思考+调用交替）；Google 支持 code_execution 作为内置工具。用 LiteLLM 或 LangChain 统一接口屏蔽差异。
如何用 Function Calling 实现 Structured Output？和 response_format 有什么区别？
实现方式：定义一个"虚拟工具"（不真正执行），parameters schema 就是想要的输出格式；用 tool_choice 强制调用它；解析 tool_call.arguments 得到结构化 JSON。与 response_format 的区别：①灵活性——Function Calling 支持更复杂的 schema（嵌套对象、数组、enum）；②兼容性——几乎所有支持工具的模型都支持，response_format 是 OpenAI 特有；③用途——Function Calling 既做结构化输出又做真正的工具调用，response_format 只做格式约束；④控制粒度——可以定义多个虚拟工具实现多种输出 schema。建议：需要真正执行函数→用 Function Calling；只需要 JSON 输出→用 response_format（更简洁）。
