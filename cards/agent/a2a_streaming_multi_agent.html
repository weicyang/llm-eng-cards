A53 · A2A 流式返回与多 Agent 协作

流式返回概念 → 5条消息模式 → 三Agent协作流程 → 调度Agent决策 → 可扩展性

流式返回的本质是把"等全做完再上菜"改成"边做边上"：被调用 Agent 先说"收到了"，再一段段推送结果，最后说"完成了"——5 条消息走完一个完整生命周期。

一、为什么需要流式返回

A52 讲的 message/send 同步调用很美好：调度 Agent 发出请求，被调用 Agent 一次性返回完整 Task。但这只适合短任务——查个天气几百毫秒到一两秒，等一等没感觉。现实中很多任务是长耗时的：汇总多数据源的报告要两三分钟，深度分析甚至更久。如果仍然同步等待，调用方只能干瞪眼，HTTP 连接还容易在长等待中超时断开。

流式返回（Streaming，被调用方把结果拆成多条消息、边执行边推送给调用方的返回方式）就是为解决这个问题：调用方在第一时间收到"任务已提交"的确认，随后结果逐段到达。传输层通常基于 SSE（Server-Sent Events，基于 HTTP 的服务器单向推送通道）实现，一条连接上服务器可以持续发数据，前端可以逐段渲染。

维度非流式（message/send）流式（message/stream）
首响应延迟等全部执行完毫秒级收到第一条消息
用户体验长时间空白等待内容逐段出现，像打字机
超时风险长任务高低，连接持续有数据
实现复杂度低，一问一答中，要处理消息流和状态机
适用任务天气、汇率等秒级查询报告、分析、生成等分钟级任务

非流式是"后厨全做完一起上菜"，流式是"火锅上一盘涮一盘"——总烹饪时间没变，但客人从第一盘就开始动筷子了。

是否支持流式不由调用方决定，而是被调用方在 Agent Card 的 capabilities.streaming 字段里声明。调度 Agent 注册时读到卡片，就会自动选择合适的调用方式——这是 A52"自我介绍"机制的自然延续。

二、流式返回的5条消息模式

当 Agent Card 声明 streaming: true 时，调用方使用 message/stream 方法。以机票 Agent 返回"航班信息"为例，一次完整的流式响应通常由 5 条消息组成：

A2A Client（调度 Agent） A2A Server（机票 Agent） │ │ │ message/stream 请求 │ ├────────────────────────────────────→│ │ │ │ ① status-update state:"submitted" │ 创建 Task │←────────────────────────────────────┤ │ ② artifact-update Part1:"你要查询的机票" │ │←────────────────────────────────────┤ │ ③ artifact-update Part2:"如下" │ │←────────────────────────────────────┤ │ ④ artifact-update Part3:具体航班信息 │ │ lastChunk: true │ Artifact 交付完毕 │←────────────────────────────────────┤ │ ⑤ status-update state:"completed" │ 任务完成，流结束 │←────────────────────────────────────┤
消息序号kind内容说明
①status-updatestate: "submitted"任务已创建并提交
②artifact-updatePart 1: "你要查询的机票"Artifact 第一部分
③artifact-updatePart 2: "如下"Artifact 第二部分
④artifact-updatePart 3: 具体航班信息
lastChunk: true		Artifact 最后部分
⑤status-updatestate: "completed"任务完成，流才真正结束
流式返回的一般模式：先提交任务（submitted）→ 逐步更新 Artifact（多次 artifact-update）→ 最后完成任务（completed）。lastChunk: true 只表示 Artifact 信息全部返回，不代表整个流式结束，还需要最后一条 status-update 标记完成。这是写解析逻辑时最容易踩的坑。

记住"叮 → 叮叮叮 → 叮"的节奏：第一声叮是"收到"，中间几声是"正在写"，最后一声是"搞定"。看到 lastChunk 只代表"写完了"，不代表"下班了"。

三、Task 状态机

流式返回中的 status-update 消息携带 Task 的状态。A2A 为 Task 生命周期（Task 从创建到终结所经历的状态序列）定义了完整的状态机，视频重点讲了主路径上的 6 个状态：

submitted（已提交） │ ↓ working（工作中） ← 可选，长耗时任务上报进度 │ ↓ input-required（需要用户输入） ← 可选，补充输入后可回到 working │ ↓ ┌──────────┼──────────┐ ↓ ↓ ↓ completed failed canceled （已完成） （失败） （取消） 协议还定义了 rejected / auth-failed / unknown， 共 9 个状态，覆盖各类异常分支。
状态含义典型触发场景
submitted任务已创建，尚未开始执行流式返回的第一条消息
working正在执行中长耗时任务上报进度
input-required需要调用方补充信息"你要订哪个舱位？"——用户回答后继续执行
completed成功完成正常结束，Artifact 全部交付
failed执行失败下游 API 报错、参数非法
canceled被取消调用方主动终止任务

状态机是长任务的"进度条"：调用方不用猜被调用方在干什么，看状态就知道它在跑、卡住了还是干完了。input-required 让 Agent 之间可以多轮协商，而不是一锤子买卖。

值得单独说的是 input-required：它让 A2A 不只是"问一次答一次"，而是支持 Agent 之间多轮交互——机票 Agent 可以反问调度 Agent"你更倾向哪天出发"，得到答复后从 input-required 回到 working 继续执行。同步的 message/send 场景很少用到它，流式场景才是它的主场。

四、三Agent协作全流程

把 A52 的同步调用和本集的流式返回合起来，就是一个完整的三 Agent 协作场景："5月1日至3日从西雅图飞纽约，选天气好的那天出发"。

用户提问 → 平台 → 调度 Agent │ │ 任务拆解：需要先查天气，再查机票 ↓ ① 调度 Agent → 天气 Agent（A2A: message/send） "5月1日至3日西雅图天气" ↓ 天气 Agent 返回：5/1晴天, 5/2小雨, 5/3大雨 ↓ ② 调度 Agent 中间决策：选5月1日（晴天） ↓ ③ 调度 Agent → 机票 Agent（A2A: message/stream） "5月1日西雅图飞纽约的航班" ↓ 机票 Agent 流式返回5条消息 （submitted → artifact-update ×3 → completed） ↓ 调度 Agent 汇总天气+机票信息 → 平台 → 用户

整个流程中，调度 Agent 做了 5 个关键决策，每一个都有明确依据：

步骤决策依据
任务拆解需要先查天气再查机票用户问题的逻辑关系（日期取决于天气）
Agent 选择调用天气 Agent + 机票 AgentAgent Card 中的 skills 匹配
子问题生成"5月1-3日天气" / "5月1日机票"原始问题的分解，比原问题更具体
中间决策选5月1日（晴天）天气 Agent 的返回结果
结果汇总整合天气+机票信息两个 Agent 的 Task 与 Artifact

注意"子问题 ≠ 原问题"这个细节：调度 Agent 传给专业 Agent 的不是用户原话，而是分解后、具体化的子任务。调度 Agent 的核心价值是翻译，不是转发。

这条链路里，天气 Agent 用同步 message/send（查询快，没必要流式），机票 Agent 用流式 message/stream（结果长，逐段返回）。同一个 A2A 协议、两种返回方式，在一条协作流里共存——调用方只需读 Agent Card 按需选择。

五、message/send vs message/stream 选择决策

需要调用某个 A2A Agent？ │ ↓ 读它的 Agent Card → capabilities.streaming │ ├── streaming: false ──→ message/send │ （一问一答，简单可靠） │ └── streaming: true ──→ 优先 message/stream │ ├── 任务很快、不关心过程 → 用 send 也行 └── 长耗时 / 需要进度展示 → 必须 stream 注意：即使被调用方流式返回， 调度 Agent 也可能等全部结果到齐再汇总给用户—— 用户侧"看不看得到流"，取决于调度 Agent 的策略。
场景推荐方式原因
天气、汇率等秒级查询message/send结果短，等待成本几乎为零
报告生成、数据分析（分钟级）message/stream避免超时，进度可见
需要中途协商（input-required）message/stream状态机靠消息流驱动
被调用方不支持流式只能 message/send受 Agent Card 声明约束
一个常见误解："机票 Agent 流式返回，用户就一定能看到打字机效果"。不一定——调度 Agent 完全可以选择等 5 条消息全部到齐后再汇总返回。流式是否传递到前端，取决于调度 Agent 的实现策略，A2A 协议本身不强制。

流式是"声明"出来的（被调用方在 Agent Card 里声明）、"选择"出来的（调用方按卡片选 method）、"传递"出去的（调度 Agent 决定是否透传给用户）。三个动作，三个层次，别混为一谈。

六、可扩展性与生产实践

三 Agent 的方案可以直接扩展到更多 Agent：调度 Agent 始终作为总指挥，负责拆解任务和汇总结果；每个专业 Agent 独立部署，通过 Agent Card 自描述；调度 Agent 根据 skills 匹配自动选择合适的 Agent。只要 Agent 数量不是特别夸张，这套方案都成立。

Agent 规模推荐架构主要约束
2-5 个单层调度（本视频方案）几乎无约束
5-20 个单层调度 + 并行调用调度 Agent 的上下文窗口与决策质量
20+ 个分层调度（调度 Agent 也有上级调度）串行延迟累加、卡片匹配复杂度
背景：某企业报表 Agent 需要汇总销售、库存、财务三个数据源生成周报，单次执行耗时 2-3 分钟。
问题：最初用 message/send 同步调用，调用方干等 2-3 分钟，HTTP 连接频繁超时，用户以为系统挂了。
方案：在 Agent Card 声明 streaming: true，改用 message/stream：先返回 submitted 表示任务已接，再按章节逐段 artifact-update 推送内容，最后 completed 收尾。
效果：首屏延迟从 2-3 分钟降到 1 秒内，超时投诉归零，用户能看到报告"一段段长出来"。
背景：某智能客服系统要覆盖订单、退款、物流、售后、FAQ、风控 6 类业务，每类的业务规则和提示词都不同。
问题：6 种能力塞进一个全能 Agent，提示词臃肿、业务间互相干扰，改一条规则要全量回归。
方案：1 个调度 Agent + 6 个专业 Agent，各自独立暴露 Agent Card；调度 Agent 按 skills 匹配分发，跨业务请求（退款+物流）由调度 Agent 串行调用两个 Agent 完成。
效果：单个请求平均 2 跳内完成，单个 Agent 升级不停服，新业务接入只需加一张卡片，回归范围缩小到单个 Agent。
  • 在 Agent Card 中如实声明 streaming 能力
  • 解析流式时把 lastChunk 和 completed 分开处理
  • 需要协商的场景用 input-required 状态
  • Agent 超过 20 个时引入分层调度
  • 不要对不支持流式的 Agent 发 message/stream
  • 不要把 lastChunk: true 当成流结束信号
  • 不要让所有 Agent 共享一个上下文（应各自独立）
  • 不要忽略串行调用多 Agent 时的延迟累加

核心架构始终是"1 个调度 + N 个专业"：调度负责"找谁做、做什么、怎么整合"，专业 Agent 负责"把具体的事做好"，A2A 协议保证它们之间的沟通标准化。分工不变，规模增长方案就不变。

Q&A

A2A 流式返回的消息模式是什么？
流式返回一般遵循 5 条消息模式：① status-update（state: "submitted"）— 任务已创建并提交；②③④ 多条 artifact-update — 逐步返回 Artifact 内容，每条携带一个 Part，最后一条的 lastChunk 设为 true；⑤ status-update（state: "completed"）— 任务完成。整体模式是：先提交 → 逐步更新内容 → 最后标记完成。注意 lastChunk: true 只表示 Artifact 信息返回完毕，不代表流式结束，还需要最后的 status-update 标记完成，解析代码要以 completed 作为收尾信号。
多Agent协作中，调度Agent扮演什么角色？
调度 Agent 是整个系统的总指挥，负责五件事：① 任务拆解 — 将用户的复杂问题分解为多个子任务；② Agent 匹配 — 根据已注册 Agent 的 skills 选择合适的 Agent；③ 子问题生成 — 为每个 Agent 生成针对性的子问题（不一定与原始问题相同）；④ 中间决策 — 根据前一个 Agent 的结果决定下一步（如根据天气选日期）；⑤ 结果汇总 — 整合所有 Agent 的返回，给出最终答案。调度 Agent 通常由平台在启动时创建，通过提示词设定职责，自己不执行具体业务。
message/send 和 message/stream 的选择依据是什么？
选择依据是被调用 Agent 的 Agent Card 中 capabilities.streaming 字段：① streaming: false → 使用 message/send，期望一次性返回完整结果；② streaming: true → 优先使用 message/stream，期望流式返回。调度 Agent 会读取 Agent Card 后自动选择合适的方式。对于用户来说，即使被调用 Agent 是流式返回的，调度 Agent 也可能等全部结果返回后才汇总给用户，所以用户侧可能看不到流式效果——流式是否透传取决于调度 Agent 的策略。
lastChunk: true 和流结束有什么区别？为什么要这样设计？
lastChunk: true 标记的是"这一个 Artifact 的内容交付完了"，但 Task 可能还有未完成的工作——比如 Agent 生成完第一个 Artifact 后还要生成第二个，或者还要做收尾动作。只有最后一条 status-update（state: "completed"）到达，整个流才真正结束。这样设计是因为 Artifact 交付完成和 Task 完成是两件事：前者是内容层面的，后者是任务层面的。写解析逻辑时，收到 lastChunk 只能拼接内容，收到 completed 才能释放资源、关闭连接。
input-required 状态什么时候出现？流程怎么继续？
当被调用 Agent 发现信息不足以继续执行时，会出现 input-required——比如机票 Agent 发现用户没说清楚舱位等级。此时 Agent 暂停执行，返回 state: "input-required" 的 status-update，并在消息里说明需要补充什么。调度 Agent（或用户）补充信息后，Task 从 input-required 回到 working 继续执行。这个机制让 A2A 支持的不只是单次问答，而是 Agent 之间的多轮协商，特别适合需求模糊的长任务。
A2A 方案可以扩展到多少 Agent？有什么限制？
理论上 A2A 方案可以支持任意数量的 Agent，核心架构始终是"1 个调度 Agent + N 个专业 Agent"。实际限制主要有三个：① 调度 Agent 的上下文窗口 — 需要处理所有 Agent Card 和返回结果；② 调度 Agent 的决策质量 — Agent 越多，匹配和拆解任务越复杂；③ 延迟 — 串行调用多个 Agent 时总延迟累加。当 Agent 数量特别多时，可能需要分层调度（调度 Agent 也有上级调度）或并行调用。目前主流实践中，单层调度支撑 10-20 个专业 Agent 没有问题。
为什么专业 Agent 之间不直接通信，而要都经过调度 Agent？
这是刻意的架构取舍。专业 Agent 互相不知道对方的存在，带来三个好处：① 可替换性 — 换掉机票 Agent 只需新 Agent 的卡片技能匹配，其他 Agent 毫无感知；② 可测试性 — 每个专业 Agent 可以单独测试，mock 一个调度 Agent 即可；③ 可控性 — 所有信息流都经过调度 Agent，方便审计、限流和错误定位。代价是调度 Agent 成为中枢，它的上下文和决策能力会成为系统上限，所以规模上去之后需要分层调度来分摊压力。
