A41 · Agent Prompt 优化与有效性验证

Prompt Optimization Evaluation — 三问破局：账本验证、错误分类、链路推进 — 从「单轮输出优化」升级为「端到端链路优化」

Agent Prompt 优化的核心误区：只优化单轮输出质量，忽略端到端链路有效性。三问破局 = 账本是否完整 + 错误是否分类处理 + 链路是否持续推进，从「看起来好」到「真正有效」。

一、Agent 系统构成：四大核心组件

在讨论 Prompt 优化之前，必须先理解 Agent 系统的四个核心组件。优化不是改一段文字，而是调整这四个组件之间的协作关系。

+-----------------------------------------------------------+
|                     Agent 系统架构                          |
+-----------------------------------------------------------+
|                                                           |
|  [Model]  ---- 决策引擎，决定下一步行动                      |
|     |                                                     |
|     v                                                     |
|  [Loop]   ---- 执行循环，维持任务推进                        |
|     |                                                     |
|     v                                                     |
|  [Tools]  ---- 现实接口，连接外部系统                        |
|     |                                                     |
|     v                                                     |
|  [State]  ---- 状态记录，保存执行历史                        |
|                                                           |
+-----------------------------------------------------------+

Agent = Model + Loop + Tools + State，优化必须覆盖全链路

组件职责Prompt 中的体现
Model决策引擎，决定下一步行动System Prompt 中的角色定义、决策规则
Loop执行循环，维持任务推进循环控制指令、退出条件、重试策略
Tools现实接口，连接外部系统工具定义、参数 Schema、使用示例
State状态记录，保存执行历史状态格式约定、更新规则、回滚策略
关键认知：大部分 Prompt 优化失败，不是因为 Model 不够聪明，而是 Loop/Tools/State 三个组件的定义不够清晰。优化 Prompt 的本质是优化这四个组件之间的信息流。

二、验证维度一：账本验证

账本要解决的问题是"复盘时能不能分清事实和猜测"。工具返回值是事实，模型推断是猜测，两者在对话历史里长得一模一样，混在一起你就无法判断错误到底出在取数还是出在判断。来源标注不是审计要求，它是归因的前提条件。

账本验证是最基础的验证维度：Agent 的每一步操作是否都被完整记录？没有账本，就无法定位问题、无法衡量改进。

账本的三个要素

要素含义记录内容
工具调用记录每次 Tool Call 的完整日志工具名、参数、返回值、耗时
执行状态码每步操作的 Exit Code0=成功、1=格式错误、2=权限拒绝、3=执行失败
信息来源标注每条信息的来源追溯用户输入 / 工具返回 / 模型推断 / 知识库检索
Agent 执行账本示例:

Step 1: [ToolCall] grep("error", path="/logs")
        ExitCode: 0
        Source: tool_result
        Output: "3 matches found"

Step 2: [ToolCall] read("/logs/app.log", offset=42, limit=10)
        ExitCode: 0
        Source: tool_result
        Output: "NullPointerException at line 47..."

Step 3: [Model] 推断: 问题出在 UserService.java:47
        Source: model_inference (based on Step 1, 2)
        Confidence: high

账本不仅记录「做了什么」，还记录「为什么这么做」-- 来源标注是调试的关键

常见遗漏：很多 Agent 框架只记录工具调用的输入输出，忽略了「模型推断」这一步。但模型的推断（如「我认为问题在 X 文件」）同样需要记录并标注来源，否则无法区分「事实」和「猜测」。

三、验证维度二：错误分类

分类的目的是让"改一句 Prompt"这个动作有明确的靶子。四类错误对应四种完全不同的修复手段：格式约束、权限声明、重试降级、状态回写。不分类就只能整段重写 Prompt，改完既说不清为什么变好，也防不住下次为什么变坏。

Agent 执行中的错误不是同质的。不同类型的错误需要完全不同的处理策略。错误分类是优化 Prompt 的前提 -- 不知道错在哪，就不知道怎么改。

四类核心错误

错误类型触发原因典型表现处理策略
Parse 失败模型输出格式不符合预期JSON 解析报错、字段缺失强化输出格式约束、添加 Schema 校验
Permission 拒绝工具调用涉及未授权操作403/401 错误、权限不足Prompt 中明确权限边界、添加工具白名单
Exec 失败工具执行超时或内部报错Timeout、500 错误、连接断开增加重试机制、设置超时上限
Context 缺失状态传递中断、上下文丢失Agent 重复已完成的操作强化 State 组件、强制状态回写

错误分类与 Prompt 优化的映射

错误统计:
  Parse 失败: 35% ---> 优化输出格式约束
  Permission: 20% ---> 增加权限边界说明
  Exec 失败:  25% ---> 增加重试指令和降级策略
  Context:    20% ---> 强化状态管理指令

优化优先级: Parse > Exec > Permission > Context
(按出现频率 * 修复难度排序)

先统计错误分布，再针对性优化 Prompt -- 而非盲目调整

实践建议：不要把所有错误混在一起优化。先跑一轮基线测试（100+ 用例），统计四类错误的占比，然后按优先级逐一解决。每解决一类，重新跑测试验证，避免「修了一类、引入另一类」的连锁反应。

四、验证维度三：链路推进

Agent 的输出「看起来正确」不等于「链路在推进」。链路推进验证关注的是：每一步操作是否真正在推动任务向目标前进？

链路推进的三个指标

指标含义衡量方式
循环有效性每轮循环是否在持续推进相邻两轮的状态差异 > 0（有新信息产生）
状态连续性信息是否跨轮次保持连贯后续步骤能正确引用前面步骤的结果
控制可靠性执行路径是否不偏离预期实际步骤与计划步骤的对齐率
链路推进 vs 链路空转:

有效推进:
  Step1: 搜索文件 -> 找到 3 个候选
  Step2: 读取文件A -> 发现关键错误
  Step3: 分析错误 -> 定位根因
  Step4: 提出修复方案
  (每步都有新信息，状态持续前进)

链路空转:
  Step1: 搜索文件 -> 找到 3 个候选
  Step2: 搜索文件 -> 找到 3 个候选 (重复!)
  Step3: 读取文件A -> 内容已遗忘
  Step4: 搜索文件 -> 又找了一遍 (死循环!)
  (状态不前进，信息不累积)

检测空转：如果连续 3 步的状态快照相似度 > 90%，触发空转告警

五、典型优化陷阱

四个陷阱有同一个根源：把"我看着顺眼"当成了验收标准。人对文本质量的直觉在单轮场景下还算可靠，一旦进入多轮链路就彻底失灵——因为链路的失败往往发生在两步之间的衔接处，而那部分是不产生可读输出的。

在实践中，大部分 Agent Prompt 优化都掉入了以下四个陷阱：

陷阱一：单轮输出优化 ≠ 链路优化

最常见的错误：优化后 Agent 的单次输出「看起来更好了」，但端到端的任务完成率没有提升。单轮输出质量只是 Model 组件的局部优化，没有触及 Loop/Tools/State 的协作问题。

陷阱二：成功案例过拟合

在少数成功案例上反复调优 Prompt，导致 Prompt 对这些特定 Case 过度适配，换一批用例就失效。正确做法是在多样化测试集上评估，而非只看几个 Demo。

陷阱三：未分类处理错误类型

把所有错误混在一起「一锅炖」式优化。Parse 失败和 Context 缺失的根因完全不同，需要同步不同的修复策略。不分类 = 盲优化。

陷阱四：缺乏量化对比数据

优化前后没有量化指标对比，凭「感觉」判断效果。必须建立基线（Baseline）并跟踪关键指标的变化。

DO

  • 建立 100+ 用例的多样化测试集
  • 先统计错误分布，再针对性优化
  • 跟踪端到端任务完成率
  • 每次只改一个变量，A/B 对比
  • 优化后跑完整回归测试

DON'T

  • 不要只看单轮输出质量
  • 不要在 3 个 Demo 上反复调优
  • 不要把所有错误混在一起处理
  • 不要凭感觉判断优化效果
  • 不要一次改多处，无法归因

六、生产级解决方案

这三个方案对应三件不同的事：结果回写让信息不因上下文压缩而丢失，退出条件让失败有界，A/B 框架让改动可验证。它们的共同点是都不写在 Prompt 里——真正把 Agent 从"能演示"推到"能上线"的东西，大多是 Prompt 之外的工程约束。

示例场景：一个代码排查 Agent，任务是根据报错日志定位问题文件并给出修复建议，平均需要 8 到 15 轮工具调用。问题：端到端完成率卡在 61%，团队用两周时间改了 9 版 Prompt，完成率在 58% 到 64% 之间上下浮动，看不出任何趋势。后来按四类错误做了一次分布统计才发现方向一直是错的：Parse 类错误只占 8%，而 Context 缺失占了 44%——Agent 在第 6 轮之后频繁重复调用前面已经调过的工具，因为早期的工具返回值随着上下文增长被截断丢失了，它"忘了自己查过"。之前所有 Prompt 改动都在打磨措辞和输出格式，恰好避开了真正的病灶。方案：把工具结果强制回写到一个结构化的 State 对象，下一轮的 Prompt 从 State 拼装而不是从对话历史继承；同时加两条守卫——同一工具加同一参数在一次任务内只允许调用一次，命中则直接返回缓存结果；连续 3 轮状态快照相似度超过 90% 触发空转告警并强制收敛。效果：Context 类错误占比从 44% 降到 9%，端到端完成率从 61% 提升到 84%；平均轮次从 11.2 降到 7.6，单任务 Token 消耗顺带降了 31%。整个改动没有动 Prompt 一个字。

6.1 强制工具结果回写机制

每次工具调用后，强制将结果写入 State 组件，而不是仅保留在对话上下文中。这解决了「Context 缺失」类错误的根源 -- 信息只在对话中存在，一旦上下文被压缩就丢失。

工具结果回写流程:

  [ToolCall] --> [获取结果]
       |
       v
  [写入 State] (强制，不可跳过)
       |
       ├── State.results.append({tool, params, result, timestamp})
       |
       v
  [注入下一轮 Prompt] (从 State 读取，非从对话历史)

结果回写到 State，确保信息不随上下文压缩丢失

6.2 循环退出条件设置

每个 Agent Loop 必须有明确的退出条件，防止空转和死循环。退出条件应该包含三种触发：

退出类型触发条件行为
正常退出任务目标已达成输出最终结果，记录完成状态
超时退出循环轮次超过上限（如 20 轮）输出当前进度，标记为未完成
空转退出连续 N 轮状态无变化触发纠偏或人工介入

6.3 A/B 测试框架

建立标准化的 A/B 测试框架，每次 Prompt 修改都有量化数据支撑。

A/B 测试框架:

  [测试集: 100+ 用例]
       |
       ├──> [Prompt A (基线)] --> [指标采集]
       |
       └──> [Prompt B (修改)] --> [指标采集]
                                      |
                                      v
                              [对比分析]
                              ├── 完成率: A 72% vs B 81%
                              ├── Token 消耗: A 4.2K vs B 3.8K
                              └── 边界 Case: A 3/10 vs B 7/10

三个核心指标：完成率、Token 消耗、边界 Case 覆盖

指标计算方式优化目标
完成率成功完成任务数 / 总任务数提升（核心指标）
Token 消耗平均每个任务的 Token 用量降低（成本优化）
边界 Case 覆盖特殊场景的通过率提升（鲁棒性）

七、终极检验标准

Prompt 优化是否有效，最终用四个量化指标衡量：

指标定义目标值含义
账本记录完整度有完整记录的步骤 / 总步骤数> 95%可观测性基础
四类错误减少量优化后错误总数 vs 优化前基线减少 > 50%优化有效性
任务轮次压缩率优化前平均轮次 vs 优化后压缩 > 20%效率提升
空转检测率被正确检测的空转次数 / 总空转次数> 80%链路健康度
终极原则：不要问「Prompt 看起来好不好」，要问「Agent 的任务完成率提升了多少」。一切优化都必须通过数据验证，否则就是自嗨。
Prompt 优化的核心原则：不要问"Prompt 看起来好不好"，要问"Agent 的任务完成率提升了多少"。一切优化都必须通过数据验证——人工评估主观且昂贵，自动化评估（A/B 测试 + 指标追踪）才是生产级方案。

Q&A

Q1 为什么说「单轮输出优化 ≠ 链路优化」？

单轮输出优化只改善了 Model 组件在一次调用中的表现，但 Agent 的有效性取决于 Model + Loop + Tools + State 四个组件的端到端协作。一个典型的反例：优化后模型的单次回答更流畅了，但因为输出格式变了，导致下游工具解析失败（Parse 错误增加），端到端任务完成率反而下降。链路优化关注的是「任务是否最终完成」，而非「某一步是否看起来好」。

Q2 四类错误（Parse/Permission/Exec/Context）中，哪个最难解决？

Context 缺失最难解决。Parse 失败可以通过强化格式约束解决；Permission 可以通过白名单控制；Exec 失败可以通过重试和降级。但 Context 缺失的根因是 LLM 的上下文管理问题 -- 信息在对话历史中被稀释或丢失，需要系统性的 State 管理方案（强制回写、结构化摘要、检查点机制），涉及整个框架的架构调整，不是改几行 Prompt 就能解决的。

Q3 如何检测 Agent 的「链路空转」？

三种检测方法：(1) 状态差异检测 -- 对比连续 N 轮的 State 快照，如果相似度 > 90% 则判定为空转；(2) 工具调用去重 -- 如果同一工具+同一参数在短期内被重复调用，说明结果未被有效利用；(3) 信息增量检测 -- 每轮循环后检查是否产生了新信息（新数据、新结论、新状态），如果信息增量为 0，则链路在空转。

Q4 A/B 测试框架的三个核心指标为什么是完成率、Token 消耗和边界 Case？

这三个指标分别衡量了 Agent 的三个核心维度：(1) 完成率 = 有效性（能不能完成任务）；(2) Token 消耗 = 效率（完成任务的成本）；(3) 边界 Case = 鲁棒性（极端场景下是否可靠）。只看完成率可能忽略成本暴涨的问题；只看 Token 消耗可能牺牲任务质量；不看边界 Case 则上线后容易出生产事故。三者缺一不可。

Q5 强制工具结果回写和普通的对话上下文有什么区别？

对话上下文是 LLM 的「短期记忆」，会被截断和压缩；State 是 Agent 的「持久化存储」，不随上下文窗口管理而丢失。强制回写意味着每次工具调用的结果都写入 State（如 JSON 结构），后续 Prompt 从 State 读取而非依赖对话历史。这保证了即使对话被压缩，关键数据仍然可用。类似于「写日记」vs 「记在脑子里」-- 日记不会因为记忆力下降而丢失。

Q6 如何避免「成功案例过拟合」？

三个措施：(1) 测试集多样性 -- 确保测试用例覆盖不同任务类型、不同复杂度、不同输入风格，至少 100+ 用例；(2) 留出验证集 -- 把测试数据分为训练集（用于调优）和验证集（只用于最终评估），避免在验证集上反复调优；(3) 交叉验证 -- 每次优化后，不仅在目标任务上测试，还在不相关的任务上跑回归，确保没有引入特定领域的偏见。
