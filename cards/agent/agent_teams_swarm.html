A51 · Agent Teams / Swarm 多 Agent 协同

单Agent局限 → Sub Agent → Agent Teams → 两大缺陷 → Kimi Agent Swarm 解决方案 → PARL 动态并行

多 Agent 协同的全部矛盾可以浓缩成一句话：协作越紧密，Token 越爆炸。Agent Teams 选择了"全员共享上下文"的紧密协作，结果被 Token 成本反噬；Kimi 的 Agent Swarm 用"上下文物理隔离 + PARL 动态裂变"同时解决了省钱和弹性两个问题。

一、从单 Agent 到多 Agent 的演进

2025 年，Agent（智能体，能够自主规划、拆解任务并调用工具完成目标的 AI 系统）已成为 AI 的主流形态。但单体 Agent 有能力上限：一个复杂项目（调研、写作、配图、开发）塞给一个 Agent，上下文会越滚越长，注意力被稀释，错误率随之上升。出路和人类文明一样——分工协作。

以 Claude Code 为代表的工具，走过了一条清晰的四阶段演进路径：

阶段模式特点局限
① 单窗口单 Agent 串行一个窗口一个 Agent上下文过长，只能串行
② 多窗口手动并行自己开多个窗口并行冲突需手动合并
③ Sub Agent主 Agent 控制子 Agent自动拆分并行，自动汇总子 Agent 之间不能直接交流
④ Agent Teams共享任务清单协作子 Agent 可互相通信Token 爆炸、缺乏弹性并行
┌─ ① 单窗口 ────┐ ┌─ ② 多窗口 ────┐ ┌─ ③ Sub Agent ──┐ ┌─ ④ Agent Teams ──┐ │ 1 个 Agent │ │ 人工开 N 个窗口 │ │ 主 Agent │ │ 主 Agent │ │ 串行执行 │ → │ 各自为战 │ → │ ├─ 子A ─┐ │ → │ ├─ 子A ⇄ 子B │ │ 上下文越来越长 │ │ 冲突手动合并 │ │ ├─ 子B ─┼→汇总│ │ ├─ 子B ⇄ 子C │ └───────────────┘ └───────────────┘ │ └─ 子C ─┘ │ │ └─ 共享任务清单 │ └─ 子Agent互不通信 ┘ └─ 上下文全员共享 ───┘ ↓ ⑤ Agent Swarm：隔离 + 动态裂变（见第 4 节）

这条演进史本质上是一部"上下文管理史"：从一个人硬扛全部上下文，到把上下文切碎分发给多人，再到思考"谁该看哪一段"。

二、Sub Agent — 自动拆分与汇总

Sub Agent（子智能体）是由主 Agent 在运行时派生出来、独立持有自己上下文、完成任务后把结果摘要交回的"分身"。主 Agent 负责拆任务和验收，子 Agent 负责执行，彼此之间像"发包方与外包方"的关系。

相比人工开多窗口，Sub Agent 把两件最烦人的事自动化了：任务拆分不再靠人想，结果汇总不再靠人复制粘贴。更重要的是，每个子 Agent 的上下文是隔离的——它只看到自己那部分任务，不会被其他子任务的噪音干扰，主 Agent 也只接收压缩后的摘要，上下文长度始终可控。

维度手动多窗口Sub Agent
任务拆分人工主 Agent 自动
结果汇总人工复制粘贴自动摘要回传
上下文各自独立各自独立（物理隔离）
子任务间通信靠人传话不支持
Sub Agent 的"不能互相交流"是刻意的设计取舍：隔离换来了 Token 可控和注意力聚焦，代价是子任务之间无法实时协调。大多数"改动相互独立"的场景（比如分别修复三个互不依赖的模块）完全不需要通信，这个代价是划算的。

Sub Agent 像外包团队：交代清楚需求、验收最终成果，过程互不打扰——这恰恰是它省钱又稳定的原因。

三、Agent Teams — 共享任务清单的紧密协作

Agent Teams（智能体团队）在 Sub Agent 的基础上补上了"通信"短板：所有成员共享一份共享任务清单（全体可见、可认领、可更新的公共任务列表），子 Agent 之间还能直接互发消息。前后端需要联调、设计与开发需要反复对齐的场景，靠它才能转得动。

┌───────────────┐ │ 主 Agent │ └───────┬───────┘ ↓ 发布任务 ┌───────────────────────┐ │ 共享任务清单 │ ← 所有成员可见、可申领 └───┬───────┬───────┬───┘ ↓ ↓ ↓ ┌────┐ ┌────┐ ┌────┐ │子A │⇄ │子B │⇄ │子C │ ⇄ = 互相通信 └────┘ └────┘ └────┘ └───────┴───────┘ 共享上下文：每轮提示词 = 全员历史消息

3.1 缺陷一：Token 量爆炸

共享是把双刃剑。Sub Agent 方案里，子 Agent 干完活只把摘要（几百 Token）交回主 Agent；而 Agent Teams 让所有成员共享上下文，意味着每个 Agent 的每一轮提示词，都要带上所有 Agent 的全部历史消息。任务越往后，开销越夸张。

轮次Sub Agent（隔离）单次调用输入Agent Teams（5 成员共享）单次调用输入
第 1 轮约 2,000 Token约 10,000 Token（5 × 2,000）
第 5 轮约 2,000 Token约 50,000 Token
第 10 轮约 2,000 Token约 100,000 Token

按每人每轮产出 2,000 Token 估算，5 个成员跑到第 10 轮，任何一次模型调用的输入都逼近 100,000 Token——不仅烧钱，还会逼近上下文窗口上限，触发截断。

3.2 缺陷二：缺乏弹性并行

Agent Teams 的成员在任务开始时按角色固定下来，之后无法根据工作量动态扩容。比如"生成 100 张配图"这种天然可并行的任务，仍然只能由 1 个图片 Agent 串行处理，不会临时裂变出 5 个分身一起干。成员编制是"开会时定的"，不是"按活儿摇的"。

共享上下文就像把全员拉进同一个微信群：信息同步了，但每个人都要爬完所有楼，群越大越爬不动。

四、Kimi Agent Swarm — PARL 驱动的弹性并行

国内 Kimi 推出的 Agent Swarm（智能体集群，可随工作量动态创建和销毁大量子 Agent 的协同架构）方案，正面解决了 Agent Teams 的两个核心缺陷：上下文做物理隔离（Sub Agent 的增强版），并行能力靠 PARL（Parallel Agent Reinforcement Learning，并行代理强化学习——在训练阶段就把"动态编排多个子 Agent"的能力练进模型）获得。

Kimi K2.5 主 Agent（项目经理） ↓ 把复杂任务拆成阶段性子任务 ┌───────┴───────────────────────────────────┐ │ ① 收集事件 → 研究员 ×1（多轮搜索） │ │ ② 筛选事件 → 审核员 ×1（138 个淘汰到 100） │ │ ③ 生成图片 → 发现工作量大 → 现场裂变： │ │ ┌─ 图片Agent① ─┐ │ │ ├─ 图片Agent② ─┤ 5 路并行 │ │ └─ 图片Agent⑤ ─┘ │ │ ④ 审核风格 → 图片审核员 ×1 │ │ ⑤ UI 设计 → 设计师 ×1 │ │ ⑥ 开发网页 → 程序员 ×1 │ └───────────────────────────────────────────┘ 每个子 Agent 只带局部上下文，中间结果总结后返回主 Agent

案例 · 60 篇商品文案的多 Agent 生成： 背景：某内容团队用多 Agent 批量生成 60 篇商品文案，最初采用 Agent Teams 式的共享上下文方案，6 个成员（选题、写手、审校等）同群协作。 问题：跑到第 8 轮，单次模型调用的输入逼近 96,000 Token（6 人 × 8 轮 × 约 2,000 Token），频繁触发截断导致风格漂移，返工率高达 30%，单篇成本约 ¥2.4。 方案：切换为隔离式编排——每个写手 Agent 只携带自己的选题与风格指南，中间结果压缩成约 300 Token 的摘要回传主 Agent。 效果：单次调用输入稳定在 6,000 Token 以内，返工率降到 5%，单篇成本降至 ¥0.4，总耗时缩短约 60%。
  • 改动独立的任务 → 用 Sub Agent
  • 需要紧密协作 → 先评估 Agent Teams 的 Token 成本
  • 大规模并行任务 → 用 Agent Swarm
  • 关注容错性 → 选子 Agent 上下文隔离方案
  • 普通用户 → 选开箱即用的方案
  • 不要为简单任务使用多 Agent（杀鸡用牛刀）
  • 不要忽视共享上下文的 Token 爆炸风险
  • 不要在固定成员架构上跑大批量并行任务
  • 不要忽略局部失败对全局的影响

选方案先问三个问题：子任务独不独立？并行规模大不大？Token 预算够不够？三个答案能把你直接送到正确的那一档。

Q&A

Agent Teams 和 Sub Agent 有什么区别？
Sub Agent 是主 Agent 控制多个子 Agent 独立并行执行的模式：子 Agent 之间不能直接交流，各自执行完后把结果摘要返回主 Agent，上下文长度始终可控。Agent Teams 在此基础上增加了两样东西——共享任务清单和子 Agent 间的互相通信，协作更紧密，适合需要实时对齐的场景。但紧密是有代价的：共享上下文意味着每个 Agent 每轮都要带上全员历史消息，Token 消耗随轮次线性膨胀。选择原则很简单：子任务间改动独立、耦合少就用 Sub Agent；必须频繁互通才用 Agent Teams，同时要盯住 Token 成本。
Agent Teams 的两大缺陷是什么？如何解决？
第一个缺陷是 Token 量爆炸：所有子 Agent 共享上下文，每轮提示词都包含全员历史消息，任务越往后开销越大，5 个成员跑 10 轮就能逼近 100,000 Token 的单次输入。第二个缺陷是缺乏弹性并行：成员在任务开始时按角色固定，无法根据工作量动态扩容，100 张图的任务仍由 1 个 Agent 串行处理。Kimi 的 Agent Swarm 针对性地解决了这两点：一是上下文物理隔离，子 Agent 只携带局部上下文，中间结果总结后才返回主 Agent；二是 PARL（并行代理强化学习）技术，让主 Agent 能在运行时根据工作量动态创建和销毁子 Agent，比如生成 100 张图时自动裂变为 5 个并行。
什么是 PARL？它在 Agent Swarm 中起什么作用？
PARL（Parallel Agent Reinforcement Learning，并行代理强化学习）是 Kimi K2.5 训练时引入的技术，目标是把"编排多个并行子 Agent"的能力直接练进模型。它让主 Agent 具备三种动态调度能力：根据任务复杂度决定需要多少个子 Agent；根据工作量现场裂变，比如生成 100 张图时自动创建 5 个并行 Agent；任务完成后动态回收资源。可以把 PARL 理解为给模型做了"项目经理特训"——不是运行时靠规则硬编码"开几个线程"，而是模型自己会看活儿摇人。官方实测中，这种动态并行比串行执行提速 4 倍以上。
多 Agent 协同中，子 Agent 上下文隔离为什么重要？
上下文隔离有三个核心价值。第一是 Token 可控：每个子 Agent 只加载自己负责的局部任务上下文，不被其他 Agent 的历史消息污染，消耗可以低一个数量级。第二是注意力聚焦：子 Agent 只看自己的子任务，无关信息不进上下文，幻觉和出错概率随之下降。第三是容错性：局部任务失败不会顺着共享上下文扩散到全局，子 Agent 可以内部重试，其他成员完全不受影响。对比 Agent Teams 的共享方案就能看出差距——共享模式下每轮输入随成员数和轮数相乘式膨胀，隔离模式则始终稳定在单任务规模。
从单体 Agent 到多 Agent 协同，架构演进的底层逻辑是什么？
这条演进路径几乎复刻了人类组织的协作史。单体智能是"一个人干所有事"，能力上限低；手动并行是"开多个窗口各干各的"，冲突要人工合并；Sub Agent 实现自动拆分与汇总，但子 Agent 之间不能交流；Agent Teams 加上共享任务清单和互相通信，协作紧密了，Token 却爆炸了；Agent Swarm 用上下文隔离加动态并行，重新找到平衡点。贯穿始终的核心矛盾只有一条：协作紧密度与 Token 成本的对立。每一代架构的本质，都是在"信息该共享到什么程度"这个问题上给出新的答案——Agent Swarm 的回答是"只共享结果摘要，不共享过程"。
什么时候根本不该用多 Agent？
多 Agent 不是越多越好，有三类情况应该坚决用单 Agent。第一，任务本身是线性的小任务，比如改一个函数、写一段摘要——引入多 Agent 只会徒增编排开销和通信成本，属于杀鸡用牛刀。第二，子任务之间高度耦合、无法清晰切分，强行拆分会导致子 Agent 之间需要反复同步，共享上下文的 Token 成本反而超过单 Agent 硬扛。第三，对延迟极其敏感的实时场景，多 Agent 的拆分、并行、汇总都需要额外的模型调用轮次。一个实用的判断标准：如果你无法用一句话说清"这个子任务独立完成、只交回什么结果"，那它就不适合被拆出去。
Agent Swarm 的"只共享结果摘要，不共享过程"具体怎么理解？
这是 Agent Swarm 对"信息该共享到什么程度"给出的核心答案。传统 Agent Teams 把每个成员每一轮的完整对话都塞进共享上下文，过程细节（中间推理、试错、工具原始返回）全员可见，Token 随成员数和轮数相乘式膨胀。Agent Swarm 反其道而行：子 Agent 在物理隔离的上下文里独立完成子任务，过程中产生的海量中间信息不外泄，只在任务收尾时把结论压缩成一段摘要回传主 Agent。主 Agent 拿到的是"做了什么、结果如何"，而不是"每一步怎么想的"。这样既保留了协同所需的信息对齐，又把通信成本从 O(成员数 × 轮数 × 过程长度) 压到 O(成员数 × 摘要长度)，是隔离与协作之间的工程平衡点。
