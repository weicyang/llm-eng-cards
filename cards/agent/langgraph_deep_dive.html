A08 · LangGraph 生产级实践

LangGraph Production Practice — 不止「会用」，更要「懂原理」：State 隔离、Checkpoint 回滚、条件路由防死循环、工具降级策略

LangGraph 的技术分水岭不在于你会不会调用 API，而在于你是否思考过 State 跨会话隔离、Checkpoint 版本回滚、条件路由死循环预防、以及工具调用的优雅降级。

一、从 Chain 到 Graph：为什么线性管道不够用

LangGraph 的核心洞察是：Agent 工作流不是"线性管道"而是"有状态图"。线性管道（A→B→C）无法处理循环、分支、崩溃恢复；而图结构 + 状态机天然支持条件路由、回环重试、并行执行和 Checkpoint 持久化。三要素——节点、边、状态——共同构成了生产级 Agent 编排的基础。

LangChain 的 Chain（LCEL）解决的是"连通性"——把 LLM、工具、解析器用管道串联起来。但当 Agent 需要循环、分支、持久化、人机协作时，线性管道的抽象就迅速崩解。LangGraph 解决的是"编排性"——让 Agent 工作流具备状态机的灵活性。

需求Chain（线性管道）的困境LangGraph（状态图）的解法
循环迭代DAG 不支持回环——Agent 调用工具后无法回到 LLM 节点StateGraph 原生支持循环边
条件分支需要大量 if/else 嵌套 hack条件边（Conditional Edges）显式声明路由
状态持久化进程崩溃后丢失全部上下文Checkpoint 机制，状态落盘到 PostgreSQL/SQLite/Redis
人机协作无法在中途暂停等待人工审批interrupt() 原语冻结状态，恢复时继续
多 Agent 协作多 Agent 之间状态共享困难共享 TypedDict 状态 + Supervisor 模式
故障定位全链路排查，小时级定位精确到节点+分支，分钟级定位

正如 LangChain 团队在 2025 年 v1.0 发布时明确界定的："LangChain 是 Agent 框架（集成与抽象），LangGraph 是编排运行时（durable execution、流式传输、人机协作、持久化）"。截至 2026 年 6 月，LangGraph TypeScript 版的 npm 周下载量超过 42,000 次，Replit、Uber、LinkedIn、GitLab 等公司都在使用它构建生产级 Agent。

二、节点（Nodes）：独立可替换的执行单元

节点的本质是将复杂 Agent 任务拆分为独立、可替换的执行单元。每个节点是一个普通函数，接收当前状态作为输入，返回状态的局部更新（只返回变化的字段）。修改一个节点不影响其他节点。

节点的三大工程价值

价值说明生产示例
独立升级修改单一节点不影响其他组件向量检索节点替换为混合检索节点仅需一下午
快速排障通过节点日志秒级定位问题模块答案不准时直接锁定重排节点，无需全链路排查
可测试性每个节点可独立单元测试Mock 上游节点输出，验证当前节点逻辑

节点函数签名

def planner_node(state: AgentState) -> dict:
    """规划节点：根据用户输入生成执行计划"""
    plan = planner_llm.invoke(state["messages"])
    return {"plan": plan.steps}  # 只返回变化的字段

def executor_node(state: AgentState) -> dict:
    """执行节点：取出计划中的下一步，调用工具执行"""
    current_step = state["plan"][len(state["past_steps"])]
    result = tool_agent.invoke(current_step)
    return {"past_steps": [(current_step, result)]}  # 追加模式

关键设计原则：每个节点函数只返回变化的字段（partial update），而非完整状态。LangGraph 框架自动将 partial update 合并到全局状态中。这确保了节点之间的松耦合——检索节点不需要知道生成节点需要什么字段，它只负责自己的输出。

三、边（Edges）：动态状态机与条件路由

边的本质是构建动态执行的状态机，解决线性流程的僵化问题。边不是编译时写死的执行顺序，而是运行时根据当前状态动态决定下一步走向哪个节点。这让同一个 Agent 图可以根据用户输入走完全不同的执行路径。

三种边类型

条件边动态分支（根据状态决定走向）add_conditional_edges(source, path_fn)意图路由、错误处理
入口边指定图的起始节点add_edge("__start__", first_node)图的入口定义

容灾机制：回环重试与降级兜底

条件边 + 回环 = 自愈能力。当工具调用失败时，条件边检测到错误类型，路由到"参数修正"节点，修正后回到工具调用节点重试。超过重试次数后降级到备用工具或转人工。这种"检测-修正-重试-降级"的循环在 Chain 中无法实现（DAG 不支持回环），但在 LangGraph 中是原生能力。

故障类型处理策略实现方式LangGraph 特性
参数错误自动修正重试错误分类节点 → 参数修正 → 回环重试循环边（Chain 不支持）
网络超时切换备用工具条件边检测 timeout → 路由到备用节点条件路由
多次失败转人工兜底重试计数器 → 超限后降级到人工处理状态 + 条件边
需要审批暂停等待人工interrupt() 冻结状态 → 恢复时继续Human-in-the-Loop
关键设计：边的条件路由是运行时动态决定的，不是编译时写死的。这意味着同一个 Agent 图可以根据用户输入走完全不同的执行路径——闲聊走短路、专业问题走检索增强、订单查询走工具调用。

四、状态（State）：上下文持久化与字段隔离

状态的本质是上下文持久化和执行现场保存。状态是一个 TypedDict（或 dataclass），由所有节点共享。每个节点读写状态中的特定字段，形成全链路可追溯的执行记录。状态通过 Reducer（归约器）控制字段的合并策略——累加还是覆盖。

状态数据结构

State 用 TypedDict 声明（dataclass 亦可），每个字段的类型注解同时承担两件事：声明数据形态，以及通过 Annotated[..., reducer] 指定合并策略。凡是被 Annotated[list, add] 标记的字段（messages、past_steps）采用累加归约器——节点返回的新值追加到列表末尾，历史记录永不丢失；其余字段（plan、intent、retrieved_chunks、rerank_scores、error_count）默认覆盖模式，只保留最新值。这一字之差决定了"对话历史会不会被新消息冲掉"，是 State 设计的第一决策。

字段类型合并策略设计理由
messageslistAnnotated[list, add] 累加对话历史不能丢失
past_stepslistAnnotated[list, add] 累加已执行步骤用于回溯与防重复
planlist[str]覆盖计划只需最新版本
intentstr覆盖意图分类只保留当前结论
retrieved_chunks / rerank_scoreslist覆盖每轮检索结果以最新为准
error_countint覆盖计数器只关心当前值

Reducer 归约器：累加 vs 覆盖

字段类型Reducer行为适用字段
Annotated[list, add]累加新值追加到列表末尾messages、past_steps（历史记录不能丢失）
普通字段覆盖（默认）新值替换旧值intent、plan、error_count（只需最新值）
自定义 Reducer自定义函数按业务逻辑合并去重、TopK、加权合并等特殊需求

Reducer 的选择只有一条经验法则：需要完整历史的字段用累加，只需要最新快照的字段用覆盖。最典型的反面教材是忘记给 messages 加 Annotated[list, add]——每个节点写回的消息会直接替换掉整段历史，Agent 瞬间"失忆"。反过来，给 intent 这类字段配累加 Reducer 则会让 State 无限膨胀，拖慢 Checkpoint 的序列化。

字段隔离原则

每个节点只读写必要字段，避免状态污染：

  • 意图识别节点：只读 messages，只写 intent
  • 检索节点：只读 messages，只写 retrieved_chunks
  • 重排节点：只读 retrieved_chunks，只写 rerank_scores
  • 生成节点：读所有字段，只写 messages

字段隔离的工程价值：(1) 节点间互不干扰——检索节点不会意外覆盖生成节点的输出；(2) 问题定位更精准——如果检索结果异常，只需要检查检索节点的输入和输出字段；(3) 状态瘦身——不需要每个节点都保存完整数据，只存储必要的 chunk ID 和摘要。

五、Pregel 超步执行模型：三要素如何协同运转

LangGraph 的底层执行引擎借鉴了 Google 的 Pregel 图计算框架，采用超步（Superstep）模型。每个超步包含三个阶段：PULL（节点触发检测）→ PUSH（动态任务分发）→ apply_writes（状态归约与屏障同步）。理解超步模型是深入理解 LangGraph 行为的关键。

┌──────────────── Pregel 超步执行流程 ────────────────────┐ │ │ │ Superstep 0: 状态初始化 │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 加载初始状态（从 Checkpoint 或用户输入） │ │ │ │ thread_id + checkpoint_id → 恢复历史状态 │ │ │ └──────────────────────────────────────────────────┘ │ │ ↓ │ │ Superstep 1: PULL（节点触发检测） │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 对比 versions_seen vs channel_versions │ │ │ │ 当触发通道版本更新 → 节点被触发执行 │ │ │ │ 这是一个 O(1) 的高效检查 │ │ │ └──────────────────────────────────────────────────┘ │ │ ↓ │ │ Superstep 2: PUSH（动态任务分发） │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 节点执行后产生 Send() 或 Call() 消息 │ │ │ │ 动态分发到下游节点（可能是并行） │ │ │ │ UUID5/XXH3 确定性任务 ID │ │ │ └──────────────────────────────────────────────────┘ │ │ ↓ │ │ Superstep N: apply_writes（状态归约 + 屏障同步） │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 将所有节点的 partial update 合并到全局状态 │ │ │ │ Reducer 决定累加还是覆盖 │ │ │ │ 屏障同步：所有写入完成后才进入下一个超步 │ │ │ └──────────────────────────────────────────────────┘ │ │ ↓ │ │ Checkpoint: 持久化 │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 序列化当前状态到 Postgres/SQLite/Redis │ │ │ │ ACID + JSONB 存储 │ │ │ │ 每个超步完成后自动触发 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ └──────────────────────────────────────────────────────────┘

版本化状态通道

LangGraph 不直接比较值的变化，而是维护每个通道的版本计数器（channel_versions）和每个节点已见的版本（versions_seen）。当任一触发通道的版本比节点最后见的版本新时，节点触发——这是一个 O(1) 的高效检查。这避免了"比较两个大型状态对象是否相同"的高开销操作。

节点触发条件：∃ channel c, channel_versions[c] > versions_seen[node][c]

六、数据安全基石：State 跨会话隔离

State 如何在多节点间保持跨会话隔离？这是多用户场景下数据安全性与正确性的核心问题。

State 隔离的三个层面

层面含义实现方式
会话级隔离不同用户的 State 互不干扰thread_id 作为 State 的主键
节点级传递同一会话内，State 在节点间正确传递TypedDict 定义 State Schema
并发级安全同一用户并发请求不互相覆盖乐观锁 + 版本号

落地只需三步：① 用 TypedDict 声明 State Schema（例如 messages、current_step、tool_results，再加一个 version 字段支持乐观锁并发控制）；② 以该 Schema 构造 StateGraph；③ 编译时挂上 checkpointer（开发期可用 MemorySaver，生产换 PostgresSaver 等持久化实现）。此后每次调用在 config 里传入不同的 thread_id，Checkpointer 就会为每个会话存取各自独立的 State 实例——隔离不在代码里手写，而是由框架的持久化层自动保证。

class AgentState(TypedDict):
    messages: list           # 对话历史
    current_step: str        # 当前步骤
    tool_results: dict       # 工具调用结果
    version: int             # 版本号（并发安全）

graph = StateGraph(AgentState)
app = graph.compile(checkpointer=MemorySaver())  # 按 thread_id 隔离存取
常见错误：多个用户共享同一个 State 实例，导致 A 用户的对话历史出现在 B 用户的上下文中。解决方案：用 thread_id 作为 State 的隔离键。

七、系统容错：Checkpoint 版本回滚

Checkpoint 的版本冲突该如何设计回滚？这决定了系统在异常状态下的容错能力与可恢复性。

Checkpoint 三态模型

Checkpoint 生命周期: [Node A 执行完成] → Checkpoint v1 (保存) ↓ [Node B 执行完成] → Checkpoint v2 (保存) ↓ [Node C 执行失败!] → 触发回滚 ↓ [回滚到 Checkpoint v2] → 重新执行 Node C ↓ [Node C 成功] → Checkpoint v3 (保存)
策略实现方式适用场景
自动回滚失败时自动恢复到最近的 Checkpoint瞬时性错误（网络超时）
版本分支保存多个版本，允许选择回退到任意版本需要人工审核的场景
状态合并并发分支完成后合并 State并行执行的多分支图
Checkpoint 不仅是"保存进度"，更是"时间旅行"的基础 — 允许 Agent 回到任意历史状态重新执行，这在调试和生产事故恢复中极其重要。

八、条件路由死循环预防

在动态工作流中，条件路由可能形成闭环，导致 Agent 在两个节点之间无限跳转。

死循环的根因

典型的死循环场景: [Node A] → 条件判断 → {结果 == "成功"?} ↓ No ↓ Yes [Node B: 修复] [End] ↓ [Node A] → 条件判断 → {结果 == "成功"?} ↓ No ↓ Yes [Node B: 修复] [End] ... (无限循环!)

三种防护机制

机制实现效果
状态计数每次经过路由时递增计数器，超过阈值强制退出物理级防线
超时机制设置全局超时，超时后强制终止时间级防线
Exit Condition为每个循环定义明确的退出判断函数逻辑级防线

防护要直接写进条件路由函数。条件边在每次路由决策时调用 route_decision(state)，返回下一个节点的名称——只要在函数开头先做两道检查（计数器阈值、全局超时），再走正常的质量判断，死循环就被物理级+时间级双重拦截。注意计数器的递增应通过节点的 partial update 写入 State（由 Reducer 合并），而不是在路由函数里原地修改状态。

防护层判断逻辑触发动作
计数器loop_count 达到阈值（如 5）返回 "force_exit" 强制退出
超时检查当前时间 - start_time 超过 60s返回 "timeout_exit" 终止
正常路由result_quality 是否达到阈值（如 0.8）达标返回 "end"；未达标 loop_count+1 后返回 "retry" 回环

核心骨架只有几行——先查防护、再判质量：

def route_decision(state: AgentState) -> str:
    if state.get("loop_count", 0) >= 5:
        return "force_exit"          # 防护1: 计数器
    if time.time() - state["start_time"] > 60:
        return "timeout_exit"        # 防护2: 超时
    if state["result_quality"] >= 0.8:
        return "end"
    return "retry"                   # 节点内对 loop_count 递增

九、工具调用错误降级策略

外部工具调用失败是常态，不是异常。生产级系统必须为每个工具调用准备降级方案。

三级降级策略

策略触发条件实现方式
重试机制网络超时等瞬时错误有限次数 + 指数退避（1s→2s→4s）
备选方案主工具持续不可用调用备用接口或返回预定义默认数据
缓存结果高频调用且结果稳定持久化缓存成功响应，不可用时返回缓存

在 LangGraph 中，降级逻辑直接内建在工具调用节点里：节点主体是一个 try/except 阶梯，三级策略依次兜底，任何一级失败都不会让异常穿透到用户层。成功或降级后，结果统一写入 State 的 tool_results 字段供下游节点消费；进入降级路径时额外置位 degraded 标记，让下游生成节点感知"当前结果来自备用链路"，必要时在回复中向用户说明。

降级层级触发条件实现要点
第一级 · 重试调用正常路径，容忍瞬时错误max_retries=3 + 指数退避（backoff_factor=2，即 1s→2s→4s），覆盖网络抖动
第二级 · 备选工具捕获 ToolUnavailableError（主工具持续不可用）切换 fallback_tool 完成同类查询，并置 degraded=True 供下游感知
第三级 · 缓存兜底其他一切异常按 query_hash 取历史成功响应；无缓存则返回"服务暂时不可用"的友好话术

底线原则：无论走到哪一级，节点都必须返回合法的 State 更新——绝不把原始异常或空白结果抛给用户。

  • 用 thread_id 实现 State 会话级隔离
  • 每个节点执行后自动保存 Checkpoint
  • 条件路由加计数器 + 超时双重防护
  • 为每个外部工具准备降级方案
  • 缓存高频工具的成功响应
  • 不要让多个用户共享同一个 State 实例
  • 不要省略条件路由的退出机制
  • 不要假设工具调用永远成功
  • 不要无限重试失败的 API 调用
  • 不要在工具降级时向用户展示原始错误

工具降级的核心理念：外部依赖的 SLA（服务等级协议）永远不可信。一个成熟的 Circuit Breaker（熔断器）模式应当嵌入每个工具调用节点 — 当连续失败次数超过阈值时自动熔断，避免雪崩效应拖垮整个 Agent 流水线。

十一、Human-in-the-Loop 与流式输出的生产实践

在生产环境中，Agent 的自主决策必须受到Human-in-the-Loop（人机协作审批）的约束，同时Streaming（流式输出）是降低用户感知延迟的关键手段。

Human-in-the-Loop 审批节点设计

审批类型触发条件实现方式
高风险操作拦截涉及数据库写入、外部 API 调用、资金操作在图节点中插入 interrupt_before 断点
结果审核Agent 输出的内容需要人工校验Checkpoint 暂停 + 人工确认后 resume
权限升级Agent 请求超出权限范围的操作条件路由到审批节点，等待管理员授权
# LangGraph Human-in-the-Loop 审批节点
from langgraph.checkpoint.memory import MemorySaver

# 编译时指定中断点 —— Agent 在执行敏感操作前暂停
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["delete_database", "send_email", "payment"]
)

# 人工审核后恢复执行
app.invoke(None, config)  # 传入 None 表示"批准并继续"

其原理是：执行到 interrupt_before 名单中的节点前，图自动暂停并把完整状态写入 Checkpoint；审批可以在几秒后完成，也可以在几天后完成——恢复时用同一 thread_id 再次 invoke 即可从断点续跑，这正是 durable execution 的体现。审批本身也可以走 interrupt() 原语在节点内部主动触发，把待审材料作为中断载荷传出，再用 Command(resume=审批结果) 恢复。

流式输出降低感知延迟

生产数据表明：流式输出可将首 Token 响应时间从 4s 降至 0.8s，用户感知的等待时间减少 80%。LangGraph 通过 astream_events 接口实现逐 Token 流式推送，配合前端 SSE（Server-Sent Events）即可完成实时展示。

高频问答

State 如何在多节点间保持跨会话隔离？
通过 thread_id 作为 State 的主键实现会话级隔离。每个用户的请求对应一个唯一的 thread_id，LangGraph 的 Checkpointer 基于 thread_id 存储和检索 State。并发场景下，使用乐观锁 + 版本号防止覆盖。关键是：不同用户绝不能共享同一个 State 实例。
Checkpoint 的版本冲突如何设计回滚？
LangGraph 的 Checkpoint 机制会在每个节点执行后自动保存 State 快照。回滚策略：(1) 自动回滚 —— 失败时恢复到最近的 Checkpoint 重新执行；(2) 版本分支 —— 保存完整历史，允许回退到任意版本；(3) 状态合并 —— 并行分支完成后合并。核心思想是把 Checkpoint 当作 Git 的 commit，支持「时间旅行」式的调试和恢复。
如何防止条件路由形成死循环？
三层防护：(1) 状态计数 —— 每次经过路由递增计数器，超过阈值（如 5 次）强制退出；(2) 超时机制 —— 设置全局超时（如 60 秒），超时后强制终止；(3) Exit Condition —— 为循环定义明确的退出判断函数。这三层防线从物理级到逻辑级覆盖，确保任何情况下循环都有终点。
工具调用失败时的降级策略是什么？
三级降级：(1) 重试 —— 对瞬时错误（网络超时）执行有限次重试 + 指数退避；(2) 备选方案 —— 主工具不可用时调用备用接口或返回预定义默认数据；(3) 缓存兜底 —— 返回之前缓存的成功响应。底线：绝不向用户展示原始错误码或空白页面。
多 Agent 协作有哪些通信模式？怎么选？
三种模式：(1) 共享内存 —— 简单直接但耦合度高，适合快速验证；(2) 消息队列 —— 解耦且支持高并发，适合生产环境；(3) 发布订阅 —— 灵活扩展但调试困难，适合复杂事件驱动场景。选择依据：并发需求、耦合度要求、开发成本。大部分场景推荐共享内存 + Checkpoint 隔离。
Human-in-the-Loop 在生产中如何落地？哪些操作需要人工审批？
通过 LangGraph 的 interrupt_before 机制，在编译图时指定需要人工审批的节点。当 Agent 执行到这些节点时自动暂停并保存 Checkpoint，等待人工确认后通过 resume 恢复执行。典型的高风险操作包括：数据库删除/写入、发送外部邮件、资金转账、调用付费 API。生产建议：审批节点不宜过多（影响效率），只对不可逆操作设置拦截。
LangGraph 的流式输出如何降低用户感知延迟？
LangGraph 通过 astream_events 接口实现逐 Token 的流式推送，配合前端 SSE（Server-Sent Events）技术实时展示生成过程。生产实测数据：非流式模式下用户需等待 4s 才能看到完整响应，流式模式下 0.8s 即可看到首个 Token 输出，感知延迟降低 80%。关键实现：在图的终端节点使用 async generator 逐步 yield 结果，而非一次性返回完整响应。
LangGraph 的节点、边、状态分别解决什么问题？
节点解决"任务拆分"——将复杂 Agent 任务拆为独立可替换的执行单元，支持单节点热替换和精准排障。边解决"流程僵化"——构建动态状态机，根据运行时条件路由到不同分支，支持容灾重试和降级兜底。状态解决"现场保存"——持久化每个节点的中间结果，支持全链路追踪和 Checkpoint 恢复。三者协同实现了生产级 Agent 的可观测、可恢复、可热替换。
为什么不直接用 LangChain 的 Chain，而要用 LangGraph？
Chain 是线性管道（A→B→C），无法处理循环（Agent 调用工具后需要回到 LLM 继续推理）、条件分支（不同意图走不同路径）、状态持久化（进程崩溃后恢复）。LangGraph 是图结构 + 状态机，原生支持：(1) 循环边——ReAct Agent 的核心需求；(2) 条件路由——动态决策；(3) Checkpoint——崩溃恢复；(4) Human-in-the-Loop——审批流程。判断标准：流程是否有分支/回环？需要持久化？需要热替换？三条任一是 → LangGraph。
状态中的 Reducer 归约器是什么？为什么重要？
Reducer 控制状态字段的合并策略。用 Annotated[list, add] 标记的字段采用累加模式（新值追加到列表末尾），适合对话历史、已执行步骤等不能丢弃的数据。普通字段采用覆盖模式（新值替换旧值），适合意图分类、当前计划等只需最新值的数据。Reducer 的重要性在于：(1) 避免对话历史被覆盖（没有 add Reducer 的话，每条新消息会替换整个历史）；(2) 避免状态膨胀（计划字段不需要保留历史版本）；(3) 支持自定义合并逻辑（如去重、TopK）。
LangGraph 的 Checkpoint 机制和普通数据库存储有什么区别？
Checkpoint 是"时间点快照"，而普通数据库是"当前状态"。区别：(1) Checkpoint 保留完整历史——每个节点的中间状态都可回溯，普通数据库只存最新值；(2) Checkpoint 支持"时间旅行"——回到任意历史节点重新执行，普通数据库不支持；(3) Checkpoint 天然适配 Agent 的容错需求——服务重启后从最近 Checkpoint 恢复，普通数据库需要额外实现恢复逻辑。LangGraph 在每个超步完成后自动触发 checkpointer.put()，保存当前状态快照。生产数据：Checkpoint 机制在某次 Redis 宕机事件中恢复了 2,800 条进行中的对话。
Pregel 超步模型是什么？它如何影响 LangGraph 的执行行为？
Pregel 是 Google 的图计算框架，LangGraph 借鉴了其超步（Superstep）模型。每个超步包含三个阶段：(1) PULL——检测哪些节点需要触发（通过版本化通道比较，O(1) 效率）；(2) PUSH——执行被触发的节点，分发任务到下游；(3) apply_writes——将所有 partial update 合并到全局状态（屏障同步：所有写入完成后才进入下一步）。理解超步模型有助于：(1) 理解节点并行行为——同一超步中的节点可以并行执行；(2) 理解状态一致性——屏障同步确保所有节点看到一致的状态；(3) 理解 Checkpoint 时机——每个超步完成后自动持久化。
条件边和普通边有什么区别？何时用哪种？
普通边（add_edge）是固定路由——A 节点执行完后总是去 B 节点，适合线性子流程（如检索后总是重排）。条件边（add_conditional_edges）是动态路由——A 节点执行完后根据当前状态决定去哪个节点，适合需要决策的场景（如意图识别后根据意图类型路由到不同处理分支）。实际使用中，约 70% 的边是条件边（Agent 的核心价值就在于动态决策），30% 是普通边（简单的线性子步骤）。条件路由函数接收当前状态作为输入，返回下一个节点的名称。
字段隔离原则是什么？为什么每个节点不应该读写所有字段？
字段隔离指每个节点只读写自己负责的字段：检索节点只写 retrieved_chunks 不碰 messages；重排节点只读 retrieved_chunks 只写 rerank_scores；生成节点读所有字段但只写 messages。好处：(1) 节点间互不干扰——避免意外覆盖；(2) 问题定位精准——检索异常只需检查检索节点的输入输出；(3) 状态瘦身——不需要每个节点保存完整数据。违反字段隔离的典型反模式：所有节点都读写 messages 字段，导致对话历史被意外修改或重复追加。
LangGraph 适合什么规模的 Agent？小项目用会不会过度工程化？
适合有容错/可观测/热替换需求的生产级 Agent（通常 3+ 个节点、需要条件路由）。小项目（单节点、线性流程）用 Chain 就够了，不需要 LangGraph 的状态机和 Checkpoint 开销。判断标准：(1) 流程是否有分支/回环？有 → LangGraph；(2) 是否需要持久化中间状态？需要 → LangGraph；(3) 是否需要单节点热替换？需要 → LangGraph。三条都不满足 → Chain 更简单。迁移路径：先用 Chain 验证业务逻辑 → 确认需要灵活性后迁移到 LangGraph → 逐步添加 Checkpoint 和 Human-in-the-Loop。
