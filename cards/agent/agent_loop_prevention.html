A72 · Agent 防循环机制设计

Loop Prevention Design — 调用指纹 / 全局轨迹表 / 任务状态机 / DAG 无环约束 / 外置状态存储

防循环不是让模型"记得别重复"，而是让重复在机制上根本发生不了：相同指纹的调用直接命中缓存，状态机的每个阶段都有硬退出条件，任务图静态无环。提示词只负责引导，轨迹校验和状态机才是防线。

一、死循环的四类成因

死循环几乎从不是"模型不听话"造成的。它是任务拆解、工具反馈、依赖关系、上下文记忆四条链路上的问题叠加后的必然结果——每一条单独看都不足以致命，凑齐了就出不来了。

把 Agent 反复调用同一个工具归因为"模型不够聪明"，是最常见也最没有出路的诊断，因为它把问题推给了一个你无法直接修改的组件。实际上循环的每一类成因都对应着系统设计上一个可修的缺口。

成因发生机制典型表现对应的机制缺口
子任务拆解冗余分解时产生了语义重叠的子任务，各自独立执行同一份数据被查了三遍，每遍都"成功"分解结果未做去重与依赖检查
工具返回结果模糊返回空、返回不明确的错误、返回与问题弱相关的内容模型判定"这次不算数"，用同样参数再来一次缺少调用指纹去重，缺少结构化错误码
多工具依赖成环A 的输入依赖 B 的输出，B 的输入又依赖 A两个工具交替调用，永远拿不到起始数据依赖关系未显式建模，无环检测缺失
长上下文遗忘轨迹历史执行记录被压缩或挤出窗口跑了 30 步之后重新开始做第 3 步做过的事执行状态寄存在上下文里，未外置

第四类的危害最容易被低估。上下文压缩是长任务的必然操作，一旦执行轨迹和业务内容混在同一份上下文里被一起压缩，Agent 就真的"忘了自己做过什么"。这时候它重新调用同一个工具，从它的视角看完全是合理决策——它掌握的信息里确实没有这条记录。指望通过延长上下文或改进压缩算法来解决这个问题，方向就错了：执行状态本来就不该放在上下文里。

二、为什么提示词和最大次数都不算防线

提示词的生效是概率性的，最大调用次数的生效是滞后的。前者你不知道它有没有起作用，后者起作用时钱已经烧完了。两者都不能作为核心防线。

面对"怎么防死循环"这个问题，最常见的两个答案是"提示词里告诉模型不要重复调用"和"框架里加个最大调用次数"。这两条都有价值，但把它们当成防循环方案就有问题了——它们各自的失效方式都很确定。

提示词为什么只能做引导

提示词约束的失效不是"模型故意违反"，而是三个结构性原因：一是它的生效概率随上下文变长而衰减，恰好长任务才是循环高发区；二是它没有任何可观测性，你无法知道某一次它到底起没起作用，也就无法衡量改动的效果；三是它无法处理"模型认为这次重复是必要的"这种情况——模型自认为上次结果不可信，重试在它的逻辑里完全正当。

正确的定位是：提示词负责降低模型提出重复调用的概率，代码负责保证提出了也执行不了。这两件事不冲突，但不能互相替代。把提示词写好能减少无谓的拦截，但系统的可靠性上界由代码那一层决定。

最大调用次数为什么是粗暴基线

最大调用次数的问题在于它是一个与任务无关的常数，而合理的调用次数与任务复杂度强相关。这就产生了一个无解的取舍：

设置简单任务复杂任务循环发生时结论
次数设小（如 10）够用正常任务被误杀，中途截断能较快止损牺牲了复杂任务的可用性
次数设大（如 50）够用够用照样循环 50 次才停，Token 已烧光形同虚设
按任务动态调整够用够用取决于估算准确度估算本身又依赖模型判断

更根本的问题是它判断的维度不对：同一个工具用四十组不同参数调用四十次，那是在做研究；同一个工具用完全相同的参数调用三次，那就是循环。次数计数器完全区分不了这两种情况，因为它只数次数，不看内容。而防循环真正需要的判据是重复，不是数量。

主流框架的默认兜底值可以说明这类机制的定位：LangChain 的 AgentExecutor 默认 max_iterations=15，LangGraph 在图级别设 recursion_limit（默认 25），CrewAI 每个任务默认 max_iter=25，AutoGen 用 max_consecutive_auto_reply，而 PydanticAI 则不提供内置的循环检测。这些数字的共同点是：它们只保证"不会无限跑"，不保证"不会跑 25 次废的"。以 LangGraph 的典型循环形态为例——agent 节点提议工具调用、tools 节点返回同一个错误、agent 节点再用同样参数提议——recursion_limit 确实会终止它，但要等到二十多轮的输入 Token 全部计费之后。

次数限制回答的是"跑多久算太久"，防循环需要回答的是"这一步是不是白跑"。前者是预算问题，后者是正确性问题，用预算机制解正确性问题必然低效。

机制判据拦截时机误伤风险该承担的角色
提示词引导模型自觉提议阶段（概率性）无降低拦截频率的优化项
最大调用次数累计次数次数耗尽后高，复杂任务被截断最外层兜底
超时熔断墙钟时间超时后中最外层兜底

DAG 无环校验依赖图是否有环执行开始前极低事前根除

三、执行轨迹校验与调用指纹

给每次工具调用算一个指纹，把指纹记在一张与模型上下文无关的表里。指纹重复即命中缓存，调用根本不会发出去——重复这件事就在物理上不成立了。

调用指纹是对一次工具调用做的确定性摘要，通常取工具名加上归一化后的核心入参，做一次哈希。它的作用是把"这次调用和之前那次是不是同一件事"从一个语义判断变成一次字符串比较。

fp = sha256(f"{tool_name}|{canonical_json(core_args)}").hexdigest()[:16]
# canonical_json: 键排序、去除无关字段（如 request_id、时间戳）、
#                 数值与大小写归一化，保证语义相同的入参得到相同指纹

这段代码里真正需要设计的是 core_args 的选取，而不是哈希算法。选窄了会漏判——把分页参数排除在外，那么"查第 1 页"和"查第 2 页"会被误判为重复；选宽了会漏防——把请求 ID、时间戳这类每次都不同的字段算进去，指纹就永远不会重复，去重机制形同虚设。核心入参的定义是每个工具各自的配置项，不能用一套全局规则套所有工具。

全局轨迹表的字段与判定

执行轨迹表是本轮任务内所有调用的结构化流水，独立于模型上下文存储。它既是去重的依据，也是事后回放和排查的唯一可信记录。

图中第三步的环模式检测比单纯的指纹去重更进一步：指纹去重只能拦住完全相同的调用，而实际循环经常是多个节点之间的绕圈。业界的一个可参考做法（RunGuard 的 LangGraph 循环守卫，2026）是维护一个约 32 步的滑动窗口，在窗口尾部扫描长度 1 到 8 的重复片段，任一片段连续重复 3 次即判定为循环。其中长度 1 对应同一工具卡死，长度 2 对应 agent 与 tools 节点之间的乒乓（工具报错、模型用同样参数再提议），更长的片段则对应规划器在几个节点之间来回绕的形态。

缓存返回的措辞很关键

指纹命中后怎么回给模型，直接决定它接下来会不会继续循环。如果只回一句"重复调用已被拦截"，模型收到的是一个失败信号，它很可能换个措辞再试一次；正确的做法是把它当作一次成功的调用来回应——返回上次的完整结果，并明确告知这是第几步执行的、如果需要不同结果应该改什么。这样模型收到的是"这件事已经做完了"，而不是"这件事没做成"。

回应方式模型收到的语义后续行为
"重复调用被拒绝"失败换措辞或换参数继续试，循环可能持续
只返回缓存结果，无说明成功但信息不足可能因为结果和上次一样而再次怀疑
缓存结果 + 执行步序 + 变更指引已完成，且知道如何获得新结果推进到下一步，或带着变更后的参数重来
示例场景：某企业知识问答 Agent 上线初期出现过一类顽固循环：内部检索工具在命中不到结果时返回空数组，模型判定"可能是我没查对"，用完全相同的查询词重试，如此往复直到框架的 25 步上限耗尽，单次会话消耗约 12 万 Token。接入调用指纹去重后，同参重复调用在发出前即被拦截并返回带说明的缓存结果，同类会话的平均步数从 25 步降到 6 步。真正解决问题的不是模型换了，而是"空结果"这个模糊信号第一次不再能触发无限重试。

四、任务状态机与退出条件

状态机把"接下来做什么"从模型的自由发挥变成了在有限合法转移中的选择。模型只能提议下一个状态，能不能转由代码判定——循环需要的自由度就此消失。

调用指纹能拦住重复的调用，但拦不住"每次调用都不同却都在原地打转"的形态。这类循环需要一个更宏观的约束：任务状态机——把执行过程切成有限个阶段，每个阶段有明确的进入条件和退出条件，阶段之间的转移由代码而非模型决定。

这张表里最重要的一列是最后一列：每个阶段超限后都必须有一个确定性的、单向向前的出口。如果超限后的动作是"回到上一阶段重来"，那状态机本身就成了循环的载体。允许回退的设计必须配上回退次数上限，且回退必须携带新信息（比如新的约束条件、被排除的选项），否则重来一遍的结果必然与上次相同。

状态机与 DAG 的关系值得澄清：状态机管的是宏观阶段，DAG 管的是阶段内子任务的依赖顺序。工具调用阶段内部按 DAG 拓扑序推进，整个任务则按状态机推进。两者结合起来，才能同时保证"不会在阶段之间打转"和"不会在子任务之间打转"。

  • 每个阶段的退出条件用可判定的断言写死，如"输出通过 Schema 校验"
  • 回退路径列成白名单，未列出的转移一律拒绝
  • 每次回退必须携带新信息（新约束、已排除的选项），否则拒绝回退
  • 阶段内步数超限时强制向前推进，带着残缺结果也比原地打转好
  • 把当前阶段写进轨迹表，事后能一眼看出任务卡在哪个阶段
  • 不要让模型自己决定当前处于哪个阶段，阶段由代码持有
  • 不要设计无上限的回退路径，可回退的状态机同样能构成循环
  • 不要把退出条件写成"模型认为已完成"，那等于没有退出条件
  • 不要在汇总阶段发现问题时直接跳回分解，那是目标层的问题
  • 不要把阶段划得太细，阶段越多合法转移越复杂，越容易出现意外环路

五、DAG 预拆解：禁止循环依赖

指纹和状态机都是运行期的拦截，DAG 是编译期的根除。把依赖显式画成图，在执行开始前跑一次环检测——有环的计划根本不允许开跑。

前面两层机制都在执行过程中生效，属于"发生了再拦"。有向无环图（DAG）预拆解则把检查前移到执行之前：先让模型产出完整的子任务依赖图，用确定性算法检测是否存在环，有环就拒绝这个计划并要求重新分解。

这样做的价值不只是省下运行期的开销，更在于它提供了一个数学层面的保证：静态无环图加上有界的重试次数，执行必然在有限步内到达终态。这也是 2026 年提出的 Structured Graph Harness（SGH）方案的核心论点——把控制流从隐式的上下文提升为显式的静态 DAG，用一部分表达力换取可控性与可验证性，从而获得"有界终止"这一属性。

环检测与依赖冲突的处理

┌───────────────────────────────────────────────────────────┐ │ 从自然语言到可执行 DAG │ │ │ │ 用户诉求 │ │ │ │ │ ▼ │ │ ┌──────────────┐ 模型产出：节点 + 依赖边 │ │ │ 分解为任务图 │ {id, tool, deps:[...], output_key} │ │ └──────┬───────┘ │ │ ▼ │ │ ┌────────────────────────────────────────┐ │ │ │ 静态校验（纯代码，无模型参与） │ │ │ │ ① 拓扑排序 ──→ 存在环？ │ │ │ │ ② 每个 deps 引用的节点是否存在 │ │ │ │ ③ 每个节点的输入是否被上游产出覆盖 │ │ │ │ ④ 是否存在孤立节点 / 不可达节点 │ │ │ └──────┬─────────────────────────────────┘ │ │ │ │ │ 有环或不合法？ │ │ ├── 是 ──→ 回灌结构化错误 ──→ 重新分解（上限 2 次） │ │ │ "节点 C 依赖 A，A 又依赖 C， │ │ │ 请指定其中一个的初始值来源" │ │ │ │ │ └── 否 ──→ 按拓扑序调度执行 │ │ ├─ 无依赖关系的节点可并行 │ │ └─ 每个节点仍受调用指纹与阶段上限约束 │ │ │ │ 结论：图静态无环 + 节点重试有界 ──→ 有限步内必达终态 │ └───────────────────────────────────────────────────────────┘

环检测本身是标准算法（拓扑排序或深度优先的回边检测），工程上真正需要设计的是发现环之后怎么回灌。直接告诉模型"你的计划有环"帮助有限，有效的回灌要指出环在哪、由哪几条边构成、以及打破它的可行方向——通常是让其中一个节点改用常量、用户输入或默认值作为初始输入，从而切断闭环。

依赖问题静态检测方式回灌内容模型的可行修正
直接成环 A↔B拓扑排序失败指出构成环的边其中一方改用初始值或用户输入
长环 A→B→C→A深度优先回边检测列出完整环路径拆分节点或引入中间常量
依赖不存在的节点引用完整性检查指出无效引用补充缺失节点或修正引用

子任务语义重叠节点指纹相似度比对指出疑似重复的节点对合并节点

最后一行处理的正是第一节提到的"子任务拆解冗余"：两个子任务用的工具相同、参数高度相似，实际上是同一件事被拆了两遍。在图校验阶段用节点指纹做一次相似度比对，可以在执行前就把它们合并掉，比等到运行期靠调用指纹去重要干净——后者虽然也能拦住，但计划里那个冗余节点会一直存在，影响后续的进度判断。

DAG 的约束力来自"无环"这个性质本身，不来自模型的配合。只要图是静态的且校验是代码做的，模型有没有理解"不要循环依赖"这件事就不重要了。

方案循环防护强度灵活性适用任务
纯 ReAct 自由循环无，全靠运行期拦截最高探索型、步数不可预知的任务
状态机 + 阶段内自由中，阶段间不会打转中流程可分段的通用业务
预编译 DAG强，事前根除环低，变化需重新出图高可靠、可并行的确定性任务
DAG + 叶子节点内 ReAct强，环被限制在叶子内中高大多数生产场景的推荐组合

六、状态存储、动态工具与降级兜底

执行状态一旦寄存在模型上下文里，它就会随压缩而消失，防循环机制也就跟着失效。轨迹必须外置存储——这是前面所有机制能成立的地基。

指纹去重、状态机、DAG 三套机制有一个共同前提：系统必须准确知道"到目前为止已经做过什么"。如果这份记录放在模型上下文里，那么每一次上下文压缩都可能把它抹掉，三套机制会同时失效，而且失效得悄无声息。所以执行状态必须放在上下文之外的独立存储里，由编排层持有。

状态放置方式上下文压缩后进程重启后可回放结论
寄存在模型上下文丢失丢失否不可用于防循环
进程内内存保留丢失否仅适合短任务、单实例
外部存储（Redis / 数据库）保留保留是生产标准做法

外置存储还带来两个附加收益：一是任务可以断点续跑，进程被调度到另一个实例上也能接着执行；二是每一次拦截都有据可查，可以事后回放整条决策路径，判断是机制误伤还是确实拦对了。

动态扩展工具怎么办

当工具是运行期动态注册的（比如通过 MCP 接入的第三方工具，或者用户自定义的工具），指纹机制会遇到一个新问题：系统不知道哪些参数属于核心入参。硬编码的核心字段配置对未知工具不适用，而全参数哈希又会因为请求 ID、时间戳这类字段而永不重复。

策略做法准确度适用
Schema 推导从工具声明的参数 Schema 里取必填字段作为核心入参较高工具声明规范的场景，首选
字段黑名单排除已知的易变字段名（request_id、timestamp、nonce、trace 等）中作为 Schema 推导的补充
全参哈希 + 结果摘要参数不同时，再比对返回结果摘要是否相同中，滞后一步参数无法归一化时的兜底
保守放行 + 计数收紧无法可靠计算指纹的工具，改用更严格的单工具调用次数上限低最后手段

第三行的做法值得单独说明：当参数怎么归一化都对不齐时，可以退一步比对结果摘要——如果两次调用参数不同但返回内容的摘要一致，那实质上仍是重复劳动。这个判据滞后了一步（调用已经发生），但能拦住后续的第三次、第四次，也是识别"语义循环"的重要线索。

语义循环：指纹拦不住的那一类

语义循环指的是每次调用的参数都不同、指纹都不重复，但每次调用都同样无用的形态。它常见于上下文变长之后——随着历史不断累积，模型对原始任务的注意力被稀释，开始生成一些与目标越来越弱相关的调用，从"解决问题"退化成"四处探索"。

指纹机制对这类循环无能为力，因为它按定义就不存在重复。识别它需要另一组信号：上下文规模的增长曲线、每步之后关键证据是否增加、以及与原始目标的相关度是否在下降。这类现象的观测手段与目标漂移的治理，正是 《A66 · Agent 死循环与生产防御》 的重点内容——本文的机制负责封住可判定的重复，A66 的观测体系负责捞出这类判定不了的漂移，两者必须配套使用。

降级兜底：机制自身故障时

轨迹校验模块本身也会出故障——外部存储不可用、指纹计算异常、状态机配置加载失败。这时候不能因为防线挂了就让 Agent 裸奔，也不能因为防线挂了就直接拒绝所有任务。合理的做法是降级到最粗的那道兜底：最大调用次数加超时熔断。

┌───────────────────────────────────────────────────────────┐ │ 防循环机制的降级链路 │ │ │ │ 正常态：DAG 校验 + 状态机 + 指纹去重 + 外置轨迹 │ │ │ │ │ │ 外置存储不可用 │ │ ▼ │ │ 降级一级：进程内内存轨迹 + 状态机 + 指纹去重 │ │ │ 影响：任务不可跨实例续跑，重启后轨迹丢失 │ │ │ 同时：收紧最大调用次数（如 25 ──→ 12） │ │ │ │ │ │ 指纹或状态机模块异常 │ │ ▼ │ │ 降级二级：最大调用次数 + 超时熔断 + 单工具调用上限 │ │ │ 影响：只能事后止损，无法事前拦截 │ │ │ 同时：调用次数进一步收紧，并对写操作禁用自动重试 │ │ │ 必须：打出降级告警，让人知道现在跑在裸奔模式 │ │ │ │ │ │ 连兜底也触发 │ │ ▼ │ │ 终止：返回已完成部分 + 明确说明未完成项 ──→ 转人工 │ │ │ │ 原则：降级必须收紧预算，不能降级后还按原预算跑 │ └───────────────────────────────────────────────────────────┘

图中最后那条原则容易被漏掉：降级时必须同步收紧预算。防线削弱了还按原来的调用次数上限跑，等于把风险敞口放大了。合理的做法是每降一级就把次数上限砍掉一半左右，同时对写操作禁用自动重试，并打出明确的降级告警——运维需要知道系统当前跑在哪一档保护级别上。

示例场景：某内部工单处理 Agent 在一次 Redis 故障中暴露了这个问题：轨迹存储不可用后，系统按预案降级到最大次数兜底，但次数上限沿用了正常态的 30 次。故障持续的 40 分钟内，几条本该被指纹拦下的重复调用各自跑满了 30 步，Token 消耗是同期正常会话的 5 倍以上。修复方案不是提高 Redis 可用性，而是在降级预案里加上"每降一级，次数上限减半、写操作禁用自动重试、触发降级告警"这三条，之后同类故障期间的 Token 消耗回落到正常态的 1.3 倍左右。

判断一套防循环方案是否可靠，只要问一个问题：把系统提示词整段删掉，它还拦得住吗？拦得住，说明防线在代码里；拦不住，说明之前所谓的防线只是一段建议。

Q&A

这张卡和《A66 · Agent 死循环与生产防御》讲的不是一回事吗？
是同一个问题的两个面，分工很清楚。A66 站在现象与观测侧：死循环有哪几种类型、目标漂移是怎么发生的、Token 怎么爆炸、线上出了问题怎么及时发现和止血，它的产出是一套监控告警与踩坑闭环。本文站在设计侧：怎么用调用指纹、执行轨迹表、任务状态机和 DAG 无环约束，让重复调用在发出之前就被拦下，它的产出是一套确定性的执行框架。两者互补且都不可缺——只有观测没有机制，你会一直在事后救火；只有机制没有观测，你既不知道机制本身有没有失效，也处理不了那些机制覆盖不到的变种，比如每次参数都不同却每次都无用的语义循环。建议先读 A66 建立对现象的直觉，再用本文的机制去封住它们。
为什么说最大调用次数是粗暴基线而不是防线？
因为它判断的维度不对。同一个工具用四十组不同参数调用四十次是在做研究，用完全相同的参数调用三次就是循环，而次数计数器完全区分不了这两者——它只数次数，不看内容。这就导致一个无解的取舍：次数设小了，复杂任务在正常执行中被误杀；设大了，循环照样能跑满上限，Token 已经烧完才停。主流框架的默认值可以说明这类机制的定位，LangChain 的 AgentExecutor 默认 max_iterations 是 15，LangGraph 的 recursion_limit 默认 25，CrewAI 每任务默认 max_iter 25，它们的共同点是只保证"不会无限跑"，不保证"不会跑二十多次废的"。防循环真正需要的判据是重复，不是数量，所以次数限制只能作为最外层兜底。
调用指纹具体怎么算，哪些参数该算进去？
指纹通常是工具名加上归一化后的核心入参做一次哈希，比如 sha256 后取前 16 位。真正需要设计的不是哈希算法而是核心入参的选取，而且这个选取必须逐工具配置，不能用一套全局规则。选窄了会漏判：把分页参数排除在外，"查第 1 页"和"查第 2 页"就会被误判为重复调用。选宽了会漏防：把 request_id、时间戳、trace_id 这类每次都不同的字段算进去，指纹就永远不会重复，去重机制形同虚设。归一化环节还要处理键排序、数值格式、大小写等问题，保证语义相同的入参一定得到相同指纹。对于运行期动态注册的工具，可以从它声明的参数 Schema 里取必填字段作为核心入参，再配一份易变字段黑名单兜底。
指纹命中后应该怎么回给模型？
应该把它当作一次成功的调用来回应，而不是当作一次拒绝。如果只回"重复调用已被拦截"，模型收到的是失败信号，它很可能换个措辞或微调参数再试一次，循环并没有真正停止。正确的回应包含三部分：上次调用的完整结果、这次调用是在第几步已经执行过的说明、以及如果需要不同结果应该变更哪些参数的指引。这样模型收到的语义是"这件事已经做完了，结果在这里"，它的自然反应是推进到下一步，而不是继续纠缠。这个细节看起来很小，但它决定了拦截之后循环是真的终止了，还是只是换了个形式继续。
任务状态机和 DAG 是不是重复建设，只做一个行不行？
不重复，它们管的是不同粒度。状态机管宏观阶段——任务分解、工具调用、结果汇总、答案生成这四段的推进顺序和退出条件，防的是在阶段之间来回打转，比如汇总时发现证据不足又跳回去重新分解，如此往复。DAG 管的是工具调用阶段内部子任务之间的依赖顺序，防的是子任务互相依赖形成闭环。只做状态机，阶段内的子任务仍可能成环；只做 DAG，宏观上仍可能出现整张图跑完又整体重来的情况。生产上比较推荐的组合是外层用状态机锁住阶段推进、工具调用阶段内按 DAG 拓扑序执行、叶子节点内部允许有限的 ReAct 式自由探索，这样既保住了总步数有上界，又保留了局部灵活性。
为什么执行状态一定要外置存储，放在上下文里不行吗？
不行，而且这是最隐蔽的一类失效。长任务必然要做上下文压缩，一旦执行轨迹和业务内容混在同一份上下文里被一起压缩，Agent 就真的不知道自己做过什么了——这时候它重新调用同一个工具，从它掌握的信息看完全是合理决策。更麻烦的是，指纹去重、状态机、DAG 三套机制都建立在"系统准确知道已经做过什么"这个前提上，轨迹一丢，三套机制会同时失效，而且失效得悄无声息。所以轨迹必须放在上下文之外的独立存储里，由编排层持有。外置还带来两个附加收益：任务可以断点续跑，进程被调度到另一个实例上也能接着执行；每次拦截都有据可查，事后能回放整条决策路径判断是误伤还是拦对了。
每次参数都不一样但每次都没用，这种循环怎么办？
这类叫语义循环，指纹机制对它无能为力，因为按定义它就不存在重复。它常见于上下文变长之后：历史不断累积，模型对原始任务的注意力被稀释，开始生成一些与目标越来越弱相关的调用，从解决问题退化成四处探索。识别它需要另一组信号——上下文规模的增长曲线、每一步之后关键证据是否真的增加、当前动作与原始目标的相关度是否在下降。工程上可行的做法包括：设置证据增量断言，连续若干步没有新增有效证据就强制推进阶段；监控上下文规模，超过阈值先做一次目标重述再继续；以及退一步比对返回结果的摘要，参数不同但结果摘要相同时同样判为重复劳动。这类现象的完整观测手段和目标漂移治理属于《A66》的范围。
轨迹校验模块自己挂了怎么办？
降级到最粗的兜底，也就是最大调用次数加超时熔断，但降级时必须同步收紧预算。这一点最容易被漏掉：防线削弱了还按原来的次数上限跑，等于把风险敞口放大了。建议的降级链路是分级的——外置存储不可用时降到进程内内存轨迹，指纹或状态机模块异常时才降到纯次数兜底，每降一级把次数上限砍掉大约一半，同时对写操作禁用自动重试，并打出明确的降级告警让运维知道系统当前跑在哪一档保护级别上。如果连兜底也触发了，正确的做法是返回已完成的部分并明确说明哪些没做完，转人工处理，而不是静默失败或者继续尝试。
提示词在防循环里还有价值吗？
有，但角色是优化项而不是防线。提示词的价值在于降低模型提出重复调用的概率，这样代码层的拦截就更少触发，交互也更顺畅。但它不能作为可靠性保障，原因有三：生效概率随上下文变长而衰减，而长任务恰恰是循环高发区；没有任何可观测性，你无法知道某一次它到底起没起作用，也就无法衡量改动效果；它处理不了"模型认为这次重复是必要的"这种情况——模型自认为上次结果不可信，重试在它的逻辑里完全正当。判断一套方案是否可靠有个很直接的检验方法：把系统提示词里所有关于"不要重复调用"的内容整段删掉，如果还拦得住，说明防线在代码里；如果拦不住，那之前所谓的防线只是一段建议。
