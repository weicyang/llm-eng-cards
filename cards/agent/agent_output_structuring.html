A73 · Agent 输出逻辑性与结构化

Output Structuring — 入口安检 / 区域划分 / 智能分拣 / 质量抽检 · 显式编排 · 约束手段选型与延迟打包

输出"有条理"和输出"格式不崩"是两件事，而且改善后者有时会伤害前者——把模型死死约束在一个 Schema 里，它可以百分之百吐出合法 JSON，同时把因果关系写反。逻辑性不是靠加一句"请有条理地回答"得到的，而是靠在模型动笔之前就把顺序、边界和检查点安排好。

一、"没条理"到底是什么问题

"输出没条理"是一个被混用的抱怨。它可能指解析失败（格式问题）、可能指字段值瞎编（事实问题），也可能指内容顺序错乱、因果颠倒、前后自相矛盾（组织问题）。只有第三种是本文要解决的，而三者的治法完全不同。

把用户的抱怨拆成可度量的维度，是这件事能不能工程化的前提。一份输出至少要在四个层面被分别评价，混在一起看就会出现"明明格式合规率 100% 了，用户还是说报告没法看"的困境。

维度问的问题怎么度量主要治法
格式有效性能不能解析？字段齐不齐？Schema 校验通过率约束解码、Schema 强约束、重试兜底
事实正确性值是不是真的？有没有编造？可溯源比例、事实抽检准确率检索增强、引用强制、外部核验
语义有效性——格式合规但取值荒谬字段填满了，值合理吗？合规但错（wrong-valid-schema）比例业务规则断言、跨字段不变量校验
逻辑条理性顺序对不对？因果有没有倒置？前后一致吗？结构完整度、因果倒置率、自相矛盾率本文的四层：入口净化 / 任务隔离 / 显式编排 / 输出自检

与《ST01 · 大模型输出稳定性保障》的分工

这里必须把边界划清楚，否则很容易把两件事当成一件事来做。《ST01 · 大模型输出稳定性保障》管的是稳不稳：输出格式会不会崩、能不能被程序解析、解析失败怎么重试、模型不可用时怎么降级兜底。它的成功标准是"下游系统永远拿到一个能用的东西"。本文管的是有没有条理：拿到的这个东西内部的组织顺序对不对、论证链条是否完整、结论和前提是否自洽。它的成功标准是"人读完之后能据此决策"。

格式稳定性（ST01 的战场） 高 │ ┌───────────────────────┼───────────────────────┐ │ ③ 能解析，读不懂 │ ④ 目标状态 │ │ JSON 永远合法 │ 格式稳 + 有条理 │ │ 但因果倒置、前后矛盾 │ │ │ ← 本文要解决的区域 │ │ ├───────────────────────┼───────────────────────┤ 低 ─┤ ① 双输 │ ② 讲得清，程序读不了 ├─ 高 │ 又崩又乱 │ 散文式回答有逻辑 │ 逻辑 │ │ 但无法结构化消费 │ 条理性 └───────────────────────┼───────────────────────┘ │ 低 关键结论：从 ① 到 ③ 是 ST01 的工作（把格式钉死）； 从 ③ 到 ④ 是本文的工作（把逻辑理顺）。 只做 ST01 会稳定地停在 ③——这正是最容易被误判为"已解决"的位置。
arXiv 论文《The Constraint Tax: Measuring Validity-Correctness Tradeoffs in Structured Outputs for Small Language Models》（arXiv:2605.26128，2026-05）在 15,000 次生成的主实验中量化了这个陷阱：对小模型（<3B）施加硬 Schema 解码，Schema 有效率从 61.5% 升到 100.0%，但答案准确率从 19.7% 掉到 11.0%，"格式合规但内容错误"的输出占比从 49.5% 涨到 88.9%。在其日历工具调用的对照实验里，仅用提示词要求输出 JSON 时可执行准确率为 91.5%，换成同样语义的硬工具调用 Schema 后只剩 48.0%——而两种模式的 Schema 有效率都是 100.0%。作者据此建议把"Schema 有效率、答案准确率、可执行准确率、合规但错率"分开上报，并提出"先自由推理、后期再打包"的实践模式。需要说明的是该实验针对小参数模型，大模型上的衰减通常小得多，但方向一致：格式约束买到的是形状，不是条理。

四层的总体形状

把"让输出有条理"拆成四层，本质是在模型生成的前、中、后三个时点各设一道关口：生成之前决定喂什么、怎么分工，生成之中决定按什么顺序产出，生成之后决定检查什么。

原始输入（用户内容 / 检索结果 / 上游数据） │ ▼ ┌ 第 1 层 · 入口安检 ─────────────────────────────┐ │ 剔除噪声、去重、标注来源与可信度 │ │ 失败表现：广告和脏话被当成有效论据进入结论 │ └─────────────────────────────────────────────────┘ │ ▼ ┌ 第 2 层 · 区域划分 ─────────────────────────────┐ │ 一个环节只做一类认知任务，不混装 │ │ 失败表现：写代码的同时做情感分析，风格串味 │ └─────────────────────────────────────────────────┘ │ ▼ ┌ 第 3 层 · 智能分拣 ─────────────────────────────┐ │ 先定骨架再填内容，顺序由程序编排而非模型即兴 │ │ 失败表现：原因写在结果后面，读者被误导 │ └─────────────────────────────────────────────────┘ │ ▼ ┌ 第 4 层 · 质量抽检 ─────────────────────────────┐ │ 规则断言优先，模型自检兜底，按价值决定检不检 │ │ 失败表现：一本正经地输出自相矛盾的段落 │ └─────────────────────────────────────────────────┘ │ ▼ 交付（人可读 / 程序可消费）

四层里只有第四层在"事后补救"，前三层都是在改变模型面对的问题形状。这是投入产出比最高的地方——让模型面对一个已经被拆小、被排好序、输入干净的问题，比让它面对一团乱麻然后反复检查要便宜得多。

二、第一层 · 入口安检

模型没有"这句话是广告，不该作为论据"的默认判断力。塞进上下文的一切都被平等地当作可用信息，所以输入里的噪声不会被忽略，而是会被认真地分析、加权、写进结论。

入口安检要处理的不是"脏数据"这个笼统概念，而是几类性质不同的上下文噪声——它们污染输出的方式各不相同，因此清理手段也不同。

噪声类型对逻辑性的具体破坏处理手段处理时机
无关内容（广告、模板签名、导航文本）被当作有效样本计入统计与结论规则过滤 + 轻量分类器打标入库前，一次性
情绪化表达与脏话污染情感倾向的判断，拉偏整体基调按任务决定：情感分析要保留原文但标注，摘要类可剔除入库前打标，用时按任务选择
重复与近重复同一观点被反复计数，形成虚假共识去重（精确 + 向量近似）检索后、拼接前
相互矛盾的事实模型任选其一或含糊糅合，结论无法追责显式标注冲突并要求模型指出分歧，而不是替它做选择拼接时
缺失来源的片段无法溯源，事实错误无从发现强制携带来源与时间戳，无来源的降权或剔除检索时
超量输入关键信息被稀释，中段内容被忽略先排序再截断，把最相关的放在首尾拼接时

示例场景：一个舆情分析 Agent 直接把抓取到的用户评论原样拼进上下文，没有任何预处理。问题：抓取结果里约三成是营销号的推广文案和纯情绪宣泄，模型把它们与真实用户反馈同等对待，于是"负面情绪占比"被脏话样本推高，"用户关注点"里出现了广告文案中的产品词；更隐蔽的是同一条热评被多个平台转载，去重没做，同一个观点在结论里被表述成"多个独立用户反复提及"，形成了虚假共识。业务方按这份报告调整了投放方向。方案：入口加三道处理——规则+分类器剔除推广文案；对情绪化表达保留原文但打上标签，让下游按任务决定取舍；对评论做精确去重与向量近似去重，并把重复次数作为独立字段传给模型，而不是靠出现次数隐式表达权重。效果：结论中的观点频次从"文本重复次数"改为"独立来源数"，虚假共识消失；报告里的关注点词表不再混入广告词。这里的关键不是过滤器多准，而是把"这条内容值多少权重"从模型的隐式感觉变成了显式字段。

清理不等于删除

入口安检最常见的错误是把它理解成"删掉不好的内容"。删除是不可逆的，而且判断标准依赖任务：情感分析任务里的脏话是核心信号，摘要任务里的同一句脏话是噪声。更稳的做法是打标而非删除——在预处理阶段给每个片段附上类型、来源、时间、可信度、重复次数等元数据，让具体任务在拼接上下文时按需筛选。

  • 预处理阶段只打标，删除决策留给具体任务
  • 把权重信息做成显式字段（重复次数、来源数、时间新鲜度）
  • 矛盾信息保留双方并标注冲突，要求模型指出分歧
  • 先按相关性排序再截断，重要内容放首尾
  • 把全部原始内容一股脑塞进上下文，指望模型自己分辨
  • 用一套过滤规则应付所有任务
  • 靠"同一观点出现多次"隐式表达重要性
  • 丢掉来源与时间戳，让输出无法溯源

三、第二层 · 区域划分

不同任务需要的输出风格、推理方式和评价标准是冲突的。写代码要精确克制，做情感分析要捕捉模糊语气；把两者放进同一次生成，模型会给出一个折中的产物——代码注释开始抒情，情感判断开始讲逻辑。

任务隔离指的是让每一次模型调用只承担一类认知任务，不同类型的任务在时间上或空间上分开。它解决的是"风格串味"和"标准打折"这两个问题：当一次生成里混了多个目标，模型无法同时最优化，只能取折中。

三种隔离方式的取舍

方式做法隔离强度成本适用
分段 Prompt同一次调用内用清晰的分节标记划分任务，要求分块输出弱（共享同一份注意力与风格倾向）最低，单次调用任务同质、彼此依赖强、对风格差异不敏感
多轮串行同一会话内分多次调用，每次只做一件事，上一步结果作为下一步输入中（上下文仍连续，风格有惯性）N 次推理，延迟累加有明确先后依赖的流水线（先抽取再分析再成文）
多 Agent / 独立会话不同任务用独立的系统提示、独立上下文、可用不同模型强（互不污染，可各自调优）最高，需额外编排与结果汇总任务异质（代码 vs 文案）、需分别评测、需不同模型能力

选择的依据不是"哪个更先进"，而是两个任务之间的依赖强度与风格冲突程度。依赖强、风格接近的任务放在一次调用里最划算；风格冲突大的任务必须物理隔离，否则无论提示词怎么写都会互相拉扯。

判断是否需要隔离有个简单的信号：如果你在提示词里不得不写"注意，这部分要严谨，那部分可以活泼"，说明你正试图用文字弥补一个应该用架构解决的问题。这类叮嘱在长上下文里衰减得非常快。

系统提示层面的分工设计，与《E02 · 五层 Prompt 架构设计》讨论的分层是同一件事的两个尺度：E02 讲的是单次调用内部人设、上下文、推理引导、安全与格式约束怎么分层组织；本文这一层讲的是当任务性质冲突时，什么时候不该再往同一次调用里加层，而应该拆成互不污染的两次调用。

四、第三层 · 智能分拣

让模型一步到位写完整篇报告，等于让它一边想清楚顺序一边把句子写出来。它会按"最顺口的下一句"推进，而不是按"论证需要的下一步"推进——于是原因被写在结果后面，因为那样读起来更流畅。

这一层是四层里对逻辑性影响最直接的一层。核心手段是显式编排：把内容的组织顺序从模型的即兴发挥变成由程序或模板固定下来的骨架，模型只负责往指定的格子里填内容。

示例场景：一个周度经营报告生成 Agent 采用单次调用直接产出全文，提示词里写了"请按照原因、影响、建议的顺序组织"。问题：约有六分之一的报告出现因果倒置——把"客单价下降"写成了"促销活动增加"的原因，而实际因果关系相反；模型这样写并不是因为不懂，而是因为它先写了那个更容易展开的段落，后续段落为了衔接顺畅就把因果关系顺过来了。由于格式完全合规、语句通顺，评审时很难发现，一次错误的归因直接影响了下周的促销决策。方案：改成两阶段——第一次调用只产出结构化骨架（一个含 指标变动 → 归因 → 影响 → 建议 四个节点的列表，每个节点只写一句要点，并强制标注归因所依据的数据字段）；程序校验骨架的因果节点是否引用了真实存在的指标、是否存在循环引用；通过后第二次调用按骨架逐节点扩写，扩写时不允许新增节点或调整顺序。效果：因果关系在骨架阶段就以结构形式暴露出来，倒置在几十个字里一眼可见，也可以被程序校验；扩写阶段模型不再有重排顺序的自由度。代价是从一次调用变成两次，但第一次调用的输出很短，总 token 增幅有限。

骨架先行的编排流程

阶段一：产出骨架（短输出，便于校验） │ ├─ 输出形式：节点列表，每节点 ≤ 1 句要点 ├─ 强制字段：本节点依据的数据来源 / 上游节点 ID └─ 不允许：成段文字、结论性表述 │ ▼ 程序校验骨架（不花 token 的确定性检查） │ ├─ 节点是否覆盖必需的逻辑位（前提 / 归因 / 影响 / 建议） ├─ 归因节点引用的指标是否真实存在 ├─ 依赖关系是否成环（A 因为 B，B 因为 A） └─ 顺序是否满足预设的偏序（前提必须早于结论） │ ├─── 校验失败 ──→ 回喂具体问题重出骨架（骨架很短，重试便宜） ▼ 阶段二：按骨架逐节点扩写 │ ├─ 每次只看当前节点 + 其依赖节点的要点 ├─ 不允许新增节点、删除节点或调整顺序 └─ 顺序由程序控制，模型无重排自由度 │ ▼ 组装成文（模板拼接，顺序不再由模型决定）

这个流程的关键不是"分两步"，而是把顺序的决策权从模型手里拿走。骨架阶段之所以有效，是因为几十个字的骨架里，因果倒置和逻辑缺口是肉眼和程序都能发现的；一旦扩写成三千字的通顺文章，同样的错误就被流畅的措辞掩盖了。

三种编排强度

强度做法模型的自由度适用代价
提示词声明顺序在指令里写明"按 A→B→C 组织"高，可自行调整甚至忽略短输出、低风险场景近零，但在长输出上衰减明显
模板填充预设固定小节，模型逐节填内容中，节内自由、节间固定结构可预先穷举的产出（报告、工单、评审意见）模板维护成本；不适合结构多变的任务
骨架先行 + 分步生成先出骨架并校验，再按骨架扩写低，顺序由程序决定长输出、逻辑链要求高、错误代价大多一次调用；骨架校验规则需要维护

凡是"输出很长且顺序错了代价很大"的场景，都值得把生成拆成骨架和扩写两步。判断标准很直接：如果错误只有读完全文才能发现，就必须在更短的中间产物上设检查点。

五、第四层 · 质量抽检

自检的价值高度依赖于"检查项能不能被判定"。"数据加总是否等于明细之和"是程序一行代码就能判的；"逻辑链是否完整"只能交给模型，而模型对自己刚写的东西天然缺乏怀疑。先把能变成断言的都变成断言，剩下的才交给模型。

这一层的常见做法是让模型在输出前自问几个问题——是否符合常识、数据来源是否可靠、逻辑链是否完整。这确实有效，但它是四层里最贵、收益最不确定的一层，所以选对手段和判断该不该做，比做得多重要。

手段做法额外成本能查出什么查不出什么

模型自检同一模型对自己的输出做一次批判性复查约 +1 轮推理明显的自相矛盾、遗漏的必要环节自己的系统性偏见——它倾向于确认而非否定

自一致性采样同一问题采样 k 次，比较结论是否一致，取多数约 k 倍推理成本（常见 k=5–15）不稳定的推理路径、模型自己也没把握的结论模型稳定犯的同一个错（k 次都错则投票无效）

顺序上必须先用尽规则断言。它不花推理成本、判定确定、可回归测试，而且很多所谓"逻辑问题"本质是能被断言捕获的：报告里各分项之和与总数不符、建议引用了不存在的指标、时间线上结果早于原因。把这些交给模型自检，等于用最贵的手段去做最便宜的事。

什么时候自检不值得做

自检的收益不是恒定的，它取决于错误漏出的代价、人工复核是否本来就存在、以及输出的可逆性。下表给出的是决策依据，而不是固定答案。

场景特征是否值得自检理由
输出直接触发不可逆操作（下单、发送、写库）值得，且应叠加规则断言 + 交叉检查错误无法回收，检查成本远低于事故成本
高价值低频产出（尽调报告、事故复盘）值得，可用到自一致性采样单次价值高，k 倍成本仍可接受
高并发低价值（搜索摘要、标签生成）不值得逐条自检，改为抽样离线评测延迟和成本被放大数万倍，单条错误代价很低
下游本来就有人工复核规则断言即可，不必模型自检人会看，模型自检的边际收益低
强实时交互（对话中途）不值得同步自检多一轮推理直接翻倍首字延迟，改为异步事后校验
错误可被用户轻易识别并重试不值得用户自己就是最便宜的检查器

自检本身也会出错，而且它有一种特别麻烦的失败模式：给一段本来正确的输出挑出"问题"，然后改错。所以自检的产出应该是"指出疑点"而不是"直接改写"，修改动作要么交给规则判定，要么保留原文与修改版由下游决定。

# 断言优先：能判定的先判定，判不了的才交给模型
def check(report):
    assert_sum_matches(report.items, report.total)   # 数值不变量
    assert_refs_exist(report.citations, metric_db)   # 引用不悬空
    assert_no_cycle(report.causal_edges)             # 因果不成环
    return llm_critique(report) if report.high_stakes else None

需要提醒的是，自检解决不了输入阶段的问题。如果第一层没做，广告文案已经作为论据进入了推理，自检看到的是一条内部自洽的论证链——它会通过。这也是为什么四层的顺序重要：越靠前的层，单位投入的收益越高。

六、约束手段选型与成本收益

结构化约束加得越早越狠，格式越稳，但留给模型思考的空间越小。合理的做法是延迟打包——先让模型在无约束的空间里把该想的想完，最后一步才把结论装进 Schema。

三类结构化手段的对比

手段保证什么不保证什么成本对逻辑性的影响
JSON Schema 强约束 / 约束解码结构与类型百分之百合规值是否合理、顺序是否符合逻辑Schema 随请求发送，10–15 字段带描述约 300–600 输入 token；首次编译有额外延迟过度约束会挤压推理空间，长枚举与深嵌套时更明显
模板填充小节齐备、顺序固定节内内容质量、跨节一致性低，一次调用即可正向：把顺序决策从模型手里拿走
分步生成（骨架先行）逻辑骨架可被程序校验扩写阶段的措辞与细节准确性多一次调用，但骨架输出很短最强的正向影响，也是最贵的

这三者不是互斥选项。生产上常见的组合是：用分步生成控制逻辑顺序，用模板固定交付形态，只在最后一步把结论装进 Schema 供下游程序消费。这样既拿到了格式保证，又没有在推理阶段束住模型的手。

延迟打包：给推理留一块无约束空间

❌ 一步到位（约束过早） 问题 ──→ [ 严格 Schema 约束下直接生成 ] ──→ 合法 JSON │ └─ 模型必须一边推理一边满足结构 结果：结构 100% 合规，内容质量下降 典型症状：字段填满，因果写反 ✅ 延迟打包（reason free, constrain late） 问题 ──→ [ 无约束 / 弱约束推理 ] ──→ 自由文本的思考与骨架 │ ▼ 程序校验骨架（因果、覆盖、引用） │ ▼ [ 严格 Schema 约束下打包 ] ──→ 合法 JSON │ └─ 此步只做搬运，不做推理 结果：结构合规 + 推理未被压缩 折中写法（单次调用内实现）： 在 Schema 里放一个不受约束的 reasoning 字符串字段， 并把它排在所有结构化字段之前，让模型先想后填。

这个模式的依据在第一节引用的实验里已经给出：约束会带来"合规但错"的比例上升，而把打包动作推迟到推理完成之后，就能同时拿到两者。一个更轻量的实现方式是在 Schema 中保留一个不受约束的推理字段并排在结构化字段之前——因为自回归生成是顺序的，排在前面的自由字段能真正起到"先想清楚"的作用，排在后面就只是事后解释了。

四层的投入产出

层一次性投入每次调用的边际成本对逻辑性的收益优先级
第 1 层 入口安检中（清洗规则、打标管线）近零（预处理可离线）高，且能同时改善事实正确性最先做
第 2 层 区域划分中（拆分任务、编排）低到中（视隔离方式，多轮则线性增加）中高，消除风格串味与标准打折次之
第 3 层 智能分拣中高（骨架 Schema 与校验规则）多一次短调用最高，直接治因果与顺序长输出场景必做
第 4 层 质量抽检低（断言）到高（评测体系）断言近零；模型自检 +1 轮；采样 k 倍可变，取决于检查项能否判定断言先做，模型自检按价值取舍

还有一项容易被忽略的成本：格式约束带来的重试。在结构约束到位的管道里，校验失败导致的重试率通常能压到 2% 以下，对平均成本影响不到百分之几；而如果只靠提示词要求格式，失败率可能在 5%–20% 之间波动，重试成本反而成为主要开销。这正是把格式问题交给 ST01 那套机制处理、而不是在逻辑层顺手解决的原因——两个维度用各自最合适的手段，比用一套手段勉强覆盖两者便宜得多。

  • 先把能变成程序断言的检查项都变成断言
  • 长输出先出短骨架并校验，再扩写
  • Schema 里给推理留一个无约束字段，且排在结构化字段之前
  • 风格冲突的任务物理隔离，不靠提示词叮嘱
  • 把格式有效率、合规但错率、逻辑完整度分开度量
  • 把"加一句请有条理地回答"当作解决方案
  • 用 Schema 合规率证明输出质量已达标
  • 在推理阶段就套上最严格的结构约束
  • 对高并发低价值场景逐条做模型自检
  • 让自检直接改写输出，而不是只指出疑点

Q&A

本文和《ST01 · 大模型输出稳定性保障》到底差在哪？两张卡不是都在讲输出质量吗？
两者管的是不同维度，最好用一句话区分：ST01 管"稳不稳"，本文管"有没有条理"。ST01 的成功标准是下游系统永远拿到一个能解析、字段齐全的东西——所以它讲的是格式约束、解析失败重试、模型不可用时的降级兜底，本质上是可用性工程。本文的成功标准是人读完这份输出能据此决策——所以讲的是输入怎么净化、任务怎么隔离、内容顺序怎么显式编排、输出前检查什么。关键在于这两个维度可以独立取值：一份输出完全可以格式百分之百合规、字段一个不缺，同时把因果关系写反、前后自相矛盾。只做 ST01 的系统会稳定地停在这个状态，而且因为所有格式指标都是绿的，很容易被误判为"已经解决了"。反过来，只做逻辑编排而不管格式稳定性，会得到一份讲得很清楚但程序解析不了的散文。
为什么说加强格式约束有时会让逻辑变差？这听起来反直觉。
因为约束解码是在解码的每一步屏蔽掉不符合 Schema 的 token，模型必须一边推理一边满足结构要求，而它的容量是有限的——用来满足格式的那部分容量就是从推理里挪出来的。第一节引用的 arXiv 论文（2026-05）在小模型上量化了这个代价：硬 Schema 解码把 Schema 有效率从 61.5% 提到 100%，但答案准确率从 19.7% 降到 11.0%，"格式合规但内容错误"的比例从 49.5% 升到 88.9%。要注意这个实验针对的是 3B 以下的小模型，大模型上的衰减通常小得多，所以不能直接照搬数值。但方向是一致的，也符合机制上的解释：约束买到的是形状，不是条理。缓解办法就是延迟打包——先在弱约束下把推理做完，最后一步再把结论装进 Schema，那一步只做搬运不做推理。
为什么"骨架先行"比在提示词里写清顺序有效得多？
因为提示词里的顺序要求只是一个建议，而模型在长文本生成中是按"最顺口的下一句"推进的。当它先写了某个更容易展开的段落，后续内容为了衔接流畅就会顺着调整因果关系——写出来的东西读着通顺，逻辑却是倒的。骨架先行改变的是决策权归属：顺序在一个几十字的短产物里就被确定下来，然后由程序校验（覆盖了必需的逻辑位吗、归因引用的指标真实存在吗、依赖关系成环了吗），校验通过后扩写阶段不允许新增节点或调整顺序。更实际的一点是错误的可发现性：几十个字的骨架里因果倒置一眼可见，也能被程序判定；扩写成三千字之后，同样的错误被流畅的措辞掩盖，评审时极难发现。凡是"错误只有读完全文才能发现"的场景，都必须在更短的中间产物上设检查点。
任务隔离用多轮对话、多 Agent 还是分段 Prompt？
看两个任务之间的依赖强度和风格冲突程度，而不是看哪个方案更先进。风格与评价标准冲突大的任务（写代码 vs 写文案、要求严谨 vs 要求发散）必须物理隔离，用独立系统提示、独立上下文，甚至不同模型，因为这种冲突无论提示词怎么写都会互相拉扯。依赖强、风格接近的任务放在一次调用里用分节标记划分最划算，隔离强度弱但成本最低。有明确先后依赖的流水线（先抽取、再分析、再成文）适合多轮串行，上下文连续、成本是 N 次推理。有一个很好用的判断信号：如果你发现自己在提示词里不得不写"注意这部分要严谨、那部分可以活泼"，说明你在用文字弥补一个该用架构解决的问题，而这类叮嘱在长上下文里衰减得非常快。
让模型自检真的有用吗？它会不会只是自我确认？
有用但有明确的局限，而且它是四层里最贵、收益最不确定的一层。局限在于模型对自己刚写的内容天然倾向于确认而非否定，所以它最擅长发现的是明显的自相矛盾和缺失的必要环节，而对自己的系统性偏见基本无能为力——那需要换一个模型或换一套系统提示做独立评审才能暴露。因此实践上的顺序应该是：先把所有能变成程序断言的检查项都变成断言（加总是否相符、引用是否存在、时间先后是否合理、因果是否成环），这些不花推理成本、判定确定、可回归测试；剩下真正需要判断力的部分才交给模型。还有一个必须注意的失败模式：自检可能给本来正确的输出挑出"问题"然后改错，所以自检的产出应该是"指出疑点"而不是"直接改写"，修改动作交给规则判定或保留两个版本由下游决定。
什么时候不该做输出自检？
判断依据是三个：错误漏出的代价、下游是否本来就有人工复核、以及输出是否可逆。高并发低价值的场景不值得逐条自检——搜索摘要、标签生成这类任务，多一轮推理的延迟和成本会被放大数万倍，而单条错误的代价很低，更合适的做法是抽样做离线评测。强实时交互场景也不该同步自检，因为多一轮推理直接把首字延迟翻倍，应该改成异步事后校验。下游本来就有人工复核时，规则断言就够了，模型自检的边际收益很低。错误能被用户轻易识别并重试的场景同样不必自检，用户本身就是最便宜的检查器。反过来，输出直接触发不可逆操作（下单、发邮件、写库）或者是高价值低频产出（尽调报告、事故复盘）时，自检非常值得，后者甚至可以用到 k 倍成本的自一致性采样。
入口安检是不是就是把脏数据删掉？
不是，把它理解成删除是最常见的错误。删除不可逆，而且什么算噪声完全取决于任务：情感分析任务里的脏话是核心信号，摘要任务里的同一句脏话是干扰项。用一套过滤规则应付所有任务，必然在某些任务上删掉有用信息。更稳的做法是打标而非删除——预处理阶段给每个片段附上类型、来源、时间、可信度、重复次数等元数据，让具体任务在拼接上下文时按需筛选。这里还有一个比过滤准确率更重要的点：把权重信息变成显式字段。如果靠"同一观点在上下文里出现多次"来隐式表达重要性，那么未去重的转载内容就会被模型读成"多个独立用户反复提及"，形成虚假共识；把重复次数和独立来源数作为字段明确传进去，这个问题就消失了。相互矛盾的事实也不该替模型做选择，而应保留双方并标注冲突，要求模型指出分歧。
四层必须全做吗？如果只能做一层，做哪层？
不必全做，而且四层的投入产出差异很大。如果只能做一件事，先做入口安检——它的边际成本近零（预处理可以离线做），一次性投入是清洗和打标管线，而收益同时覆盖逻辑条理性和事实正确性两个维度。原因在于越靠前的层，单位投入的收益越高：输入里的噪声一旦进入推理，后面所有层都在处理一个被污染的问题，连自检都救不了——因为自检看到的是一条内部自洽的论证链，它会通过。接下来的优先级取决于场景：输出很长且顺序错了代价大，就必须做第三层的骨架先行，这是对逻辑性收益最高的一层；任务性质明显冲突（同时要写代码和做文案），第二层的隔离就是刚需。第四层里的规则断言应该无条件做，因为它几乎不花钱，但模型自检要按价值取舍。
