A52 · A2A 协议：Agent 间通信规范

A2A 使用场景 → vs MCP → Agent Card → JSON-RPC 请求 → Task/Artifact/Part → 注册与问答两阶段

A2A 不是又一个工具调用协议，而是 Agent 与 Agent 之间的协作规范——每个 Agent 在固定路径挂一张"名片"（Agent Card），Agent 之间用 JSON-RPC 消息对话，专业 Agent 就能像积木一样被拼装成团队。

一、为什么需要 A2A

早期做 Agent 的常见思路是造一个"全能 Agent"，把所有 MCP 工具都挂在它身上：写代码、查天气、订机票、发邮件全由它一个来。这种做法在 demo 阶段没问题，但很快会撞墙——每多一个工具，提示词里就多一段工具描述，工具越多，每次调用消耗的 Token 越贵，模型选错工具的概率也越高。更根本的问题是，每个 Agent 都有自己的设计目标：Cline 为代码编辑优化，旅行 Agent 为行程规划优化，让一个代码 Agent 顺便订机票，就像让程序员兼职旅行社——能做，但做不好。

更合理的路径是创建专业化 Agent，各司其职，再由一个调度 Agent 统筹。而一旦涉及"Agent 之间的协作"，问题就来了：Agent A 怎么知道 Agent B 能干什么？两者之间怎么传递消息？这就是 A2A（Agent-to-Agent Protocol，Google 于 2025 年 4 月发布的 Agent 间通信协议）要解决的问题——定义 Agent 之间如何互相发现、发送消息、返回结果。

维度全能 Agent + 大量 MCP 工具专业 Agent + A2A 协作
Token 成本所有工具描述每次调用都进提示词，随工具数线性增长调度 Agent 只带 Agent Card 摘要，专业 Agent 只带自己的工具
任务契合度一套提示词兼顾所有领域，设计目标互相干扰每个 Agent 的提示词都为自己领域优化
故障半径一个工具描述写坏，影响所有任务单个 Agent 升级不影响其他 Agent
团队协作一个团队维护一个巨型 Agent各团队维护各自 Agent，靠协议联通

MCP 解决"这个 Agent 手头有什么工具"，A2A 解决"这个 Agent 能找谁来帮忙"。一个对内，一个对外，互为补充。

关键分工：A2A 作用于 Agent 与 Agent 之间的通信，MCP 作用于 Agent 内部（模型与工具的交互）。典型链路中，调度 Agent 通过 A2A 调用天气 Agent，天气 Agent 内部再通过 MCP 调天气 API——两个协议各管一层，互不替代。

记住一句话：MCP 给 Agent 装"手和脚"，A2A 给 Agent 配"同事"。你不会跟自己的手谈判，也不会把同事插到 USB 口上。

两个协议之所以能叠加使用，是因为它们描述的是不同层次的抽象：被调用的天气 Agent，在调度 Agent 眼里是"一个会说 A2A 的同行"，在它自己内部则是"一个模型 + 一组 MCP 工具"。同一个 Agent 在不同关系里扮演不同角色，协议之间自然不冲突。

三、多Agent协作总体架构

以视频中的例子"未来3天西雅图天气好时飞纽约"，整体协作架构如下：

用户："未来3天西雅图天气好时飞纽约" │ ↓ ┌──────────────────────────────────────────────┐ │ 平台 │ │ 负责注册 Agent Card、创建调度 Agent │ └────────────────────┬─────────────────────────┘ ↓ ┌──────────────────────────────────────────────┐ │ 调度 Agent（总指挥） │ │ ① 任务拆解：先查天气，再查机票 │ │ ② 技能匹配：找到对应专业 Agent │ │ ③ 结果汇总：整理后返回给用户 │ └───────┬──────────────────────────┬───────────┘ ↓ A2A ↓ A2A ┌───────────────┐ ┌───────────────┐ │ 天气 Agent │ │ 机票 Agent │ │ 查3天天气 │ → │ 查选定日机票 │ │ 晴/小雨/大雨 │ │ │ └───────────────┘ └───────────────┘ 调度 Agent 选 5/1（晴天）→ 汇总返回用户
角色职责不做什么
用户提出自然语言任务不参与协议细节
平台注册 Agent Card、创建调度 Agent不做业务决策
调度 Agent任务拆解、Agent 匹配、中间决策、结果汇总不执行具体业务
专业 Agent完成自己领域的任务，返回 Task/Artifact不知道其他 Agent 的存在

调度 Agent 像项目经理：自己不写一行代码，但负责想清楚"谁来做、按什么顺序做、结果怎么整合"这三件事。

注意信息流的方向：专业 Agent 之间不直接通信，天气 Agent 不知道机票 Agent 的存在。所有信息都经过调度 Agent 中转，这让系统易于测试、易于替换——换掉机票 Agent，只需要新 Agent 的 Agent Card 技能匹配即可，其他部分毫无感知。

四、Agent Card — Agent 的自我介绍

要让 Agent 协作，先得互相"认识"。A2A 的做法借鉴了 Web 的 well-known URI（RFC 8615 定义的固定路径约定，就像网站根目录下的 robots.txt）——每个 A2A Agent 必须在 /.well-known/agent.json 路径下返回自己的 Agent Card（Agent 名片，描述自身信息与技能清单的 JSON 文档），告诉别人：我是谁、我能干什么、我支持什么格式。

{
  "name": "Weather Agent",
  "description": "处理天气相关任务",
  "url": "http://127.0.0.1:10000",
  "capabilities": { "streaming": false },
  "defaultInputModes": ["text"],
  "defaultOutputModes": ["text"],
  "skills": [{ "id": "weather-forecast", "name": "天气预告",
               "description": "获取未来天气预告" }]
}
字段作用谁来读
name / descriptionAgent 名称与一句话定位调度 Agent 初筛候选
urlAgent 的服务地址平台发起请求时使用
capabilities.streaming是否支持流式返回决定调用方用 send 还是 stream
defaultInputModes / OutputModes支持的输入/输出格式（text、image-png 等）调用方检查格式兼容性
skills技能列表，每个含 id/name/description/tags/examples调度 Agent 匹配任务的核心依据

Agent Card 就是 Agent 的"名片 + 经营范围"：name 和 description 让别人知道你是谁，skills 让别人知道能找你办什么事，capabilities 让别人知道该怎么跟你说话。

skills 字段的写法直接决定调度准确率。视频建议给每个技能写具体的 examples（如"给我纽约未来7天的天气预告"），因为调度 Agent 本质上是靠模型的语义理解把用户问题和技能匹配起来——描述越具体，匹配越稳定。这一点和 MCP 的 tools/list 是同构的：都是"自我介绍"机制，只是介绍的对象不同。

五、JSON-RPC 请求与 Task/Artifact/Part 返回结构

A2A 没有发明新的传输格式，而是选择了 JSON-RPC 2.0（一种无状态、轻量级的远程过程调用协议，消息只有 id/jsonrpc/method/params 四个骨架字段）。A2A 在这副骨架之上定义具体的 method 取值（message/send、message/stream）和 params 结构。注意区分两者的边界：JSON-RPC 只管"消息怎么打包"，A2A 管"包里装什么"。

{
  "id": "req-123", "jsonrpc": "2.0", "method": "message/send",
  "params": {
    "configuration": { "acceptedOutputModes": ["text"] },
    "message": {
      "kind": "message", "contextId": "conv-789", "role": "user",
      "parts": [{ "kind": "text", "text": "西雅图明天天气怎么样？" }]
    }
  }
}
A2A Client（调度 Agent） A2A Server（天气 Agent） │ │ │ message/send（JSON-RPC 请求） │ ├────────────────────────────────────→│ │ │ 创建 Task（工单） │ │ 执行技能 │ │ 生成 Artifact（产物） │ JSON-RPC 响应 │ │←────────────────────────────────────┤ │ 返回结构（三层嵌套）： result (kind: "task") ├── status: { state: "completed" } ├── artifacts: [ { artifactId, name: "天气信息", │ parts: [ {kind:"text", text:"未来三天：晴/小雨/大雨"} ] } ] └── history: [ 该任务中的历史消息 ]
请求字段说明
methodmessage/send = 期望一次性返回完整结果；message/stream = 期望流式返回
parts消息内容片段，kind 可为 text / file / data，一条消息可带多个 part
contextId上下文 ID，A2A 未规定具体含义，由实现方定义（常用于关联同一会话的多个任务）
roleuser 表示消息由调用方发出
概念定义生成方类比
Task被调用 Agent 根据请求创建的任务对象，含 id/contextId/status/artifacts/history被调用方（Server）工单
ArtifactAgent 执行任务产出的成果物（文本/图片/文件）被调用方工单附件（交付物）
PartMessage 或 Artifact 中的一段内容片段双方交付物的一个段落
A2A Client调用方 Agent（如调度 Agent）—发工单的甲方
A2A Server被调用方 Agent（如天气 Agent）—接工单的乙方

Task 是工单，Artifact 是工单里的交付物，Part 是交付物的段落。注意：工单（Task）由接单方创建——只有干活的人才知道这单进行到哪一步了。

本视频的双 Agent 同步场景使用 message/send：调度 Agent 发出请求，天气 Agent 一次性返回完整 Task，协作即完成。如果被调用方在 Agent Card 里声明 streaming: true，调用方就要改用 message/stream，返回会变成一串消息流——那是 A53 的主题。

六、两阶段流程：注册 + 问答

把前面所有零件拼起来，一次完整的 A2A 协作分为两个阶段。注册阶段只在系统启动时发生一次，问答阶段在每次对话时发生：

【注册阶段】（系统启动时，仅一次） 用户输入 Agent URL → 平台请求 /.well-known/agent.json ↓ 获取 Agent Card → 平台创建调度 Agent ↓ 调度 Agent 获得：①自身职责描述 ②可用 Agent 列表 ③send_message 工具 【问答阶段】（每次对话） 用户提问 → 平台 → 调度 Agent ↓ 调度 Agent 查看可用 Agent 列表，匹配技能 ↓ 调用 send_message 工具（A2A 协议）→ 被调用 Agent ↓ 被调用 Agent 返回 Task（含 Artifact） ↓ 调度 Agent 整理结果 → 平台 → 用户
环节是否归 A2A 管说明
平台注册 Agent Card✅ 管抓取 /.well-known/agent.json 是协议规定
平台创建调度 Agent❌ 不管属于平台实现细节
调度 Agent 的模型推理❌ 不管用什么模型随意
Agent 间消息传递✅ 管JSON-RPC + message/send 是协议核心
被调用 Agent 内部执行❌ 不管内部用 MCP 还是别的，完全自由
A2A 协议只作用于两个环节：① Agent Card 注册；② Agent 间的消息传递。其余环节（平台管理、调度 Agent 创建、模型推理、内部执行）全部是"实现自由"。这正是 A2A 能与任何技术栈共存的原因。

A2A 是一个"薄协议"：只规定"自我介绍"和"传话"两个动作，其余全部留给实现方。协议越薄，接入成本越低，生态越容易长出来。

七、生产实践与生态

7.1 生态案例：从 50+ 伙伴到 Linux 基金会

背景：2025 年各家厂商（Salesforce、SAP、ServiceNow 等）都有自己的 Agent 产品，企业内部也有大量自建 Agent，N 个 Agent 互通最多需要 N×(N-1)/2 条点对点对接。
问题：每对 Agent 都要单独做集成，没有统一的发现和通信机制，跨厂商协作几乎不可能。
方案：Google 于 2025 年 4 月发布 A2A 协议，发布时即有 50+ 生态伙伴；各 Agent 只需实现一套协议 + 一张 Agent Card 即可被发现和调用；2025 年 6 月 A2A 捐赠给 Linux 基金会中立治理。
效果：连接复杂度从 N×(N-1)/2 降为 N，新 Agent 入网从"和每个老 Agent 谈一遍接口"变成"发布一份 agent.json"。

7.2 视频实录案例：双Agent同步协作

背景：旅行规划场景既需要查天气，又需要查机票，两种能力属于完全不同的领域。
问题：单个全能 Agent 需要把天气和机票两套工具描述同时塞进提示词，两个领域都做不精，且每次调用都为无关工具付 Token。
方案：拆成 2 个专业 Agent（天气 Agent 声明 streaming: false，机票 Agent 同理），调度 Agent 只带 1 个 send_message 工具 + 2 张 Agent Card，先用 message/send 同步问天气，再根据天气决策日期后问机票。
效果：调度 Agent 的提示词瘦身为"职责描述 + 2 张卡片 + 1 个工具"，天气 Agent 内部照旧用自己的 MCP 天气工具，各 Agent 可独立升级、独立测试，整条协作链可完整复现。

7.3 设计决策清单

  • Agent Card 的 skills 写具体，附上 examples
  • 按业务领域合理拆分专业 Agent
  • 调度 Agent 提示词只保留职责 + 卡片列表 + send_message
  • 在 capabilities 中如实声明 streaming 能力
  • 不要把所有能力都做成 MCP 工具挂在一个 Agent 上
  • 不要让专业 Agent 绕过调度 Agent 互相直连
  • 不要混淆 JSON-RPC 与 A2A 的边界（传输 vs 语义）
  • 不要让被调用方创建 Task 时漏写 status 和 artifacts
需求推荐做法
新增一个确定性函数能力（查库、格式转换）写 MCP Server，挂在现有 Agent 上
新增一个需要自主规划的能力（行程规划、代码审查）做独立 Agent，用 A2A 暴露
现有 Agent 提示词过长、选工具混乱拆成多个专业 Agent + 调度 Agent
跨团队 / 跨厂商的 Agent 协作A2A 是目前共识最广的标准答案

判断标准：新能力是"一个函数"就用 MCP，新能力是"一个角色"就用 A2A。函数是确定性执行，角色才需要自主决策。

Q&A

A2A 和 MCP 有什么区别？各自作用在哪里？
A2A 作用于 Agent 与 Agent 之间的通信，MCP 作用于 Agent 内部（模型与工具的交互）。典型场景中：调度 Agent 通过 A2A 协议调用天气 Agent，天气 Agent 内部通过 MCP 协议调用天气查询工具。两者的作用域不同、解决的问题不同，互不替代：A2A 解决"Agent 之间如何沟通"，MCP 解决"Agent 内部如何调用工具"。生产系统中两者通常是叠加关系——外层 A2A，内层 MCP。
什么是 Agent Card？它包含哪些关键信息？
Agent Card 是每个 A2A Agent 必须在 /.well-known/agent.json 路径下返回的 JSON 文档，描述 Agent 的基本信息，供调度 Agent 做决策。关键字段：① name/description — 名称与定位；② capabilities — 能力声明（如是否支持流式返回）；③ skills — 技能列表（每个技能含 id/name/description/tags/examples），是调度 Agent 判断何时调用的核心依据；④ defaultInputModes/OutputModes — 支持的输入输出格式。它的作用类似于 MCP 的 tools/list，都是"自我介绍"机制，只是介绍给不同的对象看。
A2A 的 Task、Artifact、Part 分别是什么？
① Task — 被调用 Agent 根据请求创建的任务对象，包含 id/contextId/status/artifacts/history，由被调用方（Server）生成；② Artifact — Agent 执行任务产出的成果物，可以是文本、图片、文件等，是 Task 中最重要的部分（代表答案本身）；③ Part — Message 或 Artifact 中的一段内容，类型可以是 text/file/data。三者是三层嵌套关系：Task 包含 Artifact 列表，Artifact 包含 Part 列表。注意 Task 由被调用方创建，不是调用方，因为任务状态只有执行者才能跟踪。
A2A 使用什么传输协议？message/send 和 message/stream 有什么区别？
A2A 使用 JSON-RPC 2.0 作为传输格式。JSON-RPC 定义了基础结构（id/jsonrpc/method/params），A2A 在此之上定义了 method 的两个取值：① message/send — 期望非流式返回，被调用方一次性返回完整结果；② message/stream — 期望流式返回，被调用方多次返回，每次携带部分内容。选哪个取决于被调用方 Agent Card 中 capabilities.streaming 的声明。本视频的双 Agent 同步场景用的是 message/send，天气 Agent 一次性返回完整 Task。
为什么 Task 是被调用方创建的，而不是调用方？
因为任务状态只有执行者才能跟踪。被调用方收到请求后，如何拆解、执行多久、是否失败，这些状态（submitted/working/completed/failed）都只能由被调用方产生。如果让调用方创建 Task，被调用方就得反向汇报每一次状态变化，协议会变得复杂。这样设计还带来一个好处：调用方完全不需要知道被调用方的实现细节——它只管发消息、等 Task 结果，这正是 A2A 想要的封装边界。
JSON-RPC 2.0 和 A2A 协议的边界在哪里？
JSON-RPC 2.0 是通用的远程过程调用格式，只规定消息必须有 id/jsonrpc/method/params、响应必须有 result/error，不关心 method 的具体语义。A2A 建立在它之上：method 的取值（message/send、message/stream）、params 的结构（message/parts/contextId）、响应 result 的结构（Task/Artifact/Part）都是 A2A 规定的。分清边界有助于排错：消息打包错误是 JSON-RPC 层问题，业务字段缺失是 A2A 层问题，两者的修复路径完全不同。
整个多Agent协作流程里，A2A 协议实际只管哪几个环节？
只管两个环节：① Agent Card 注册 — 平台通过 /.well-known/agent.json 获取 Agent 的自我介绍；② Agent 间消息传递 — 调度 Agent 通过 JSON-RPC 的 message/send 或 message/stream 调用被调用 Agent。其余环节——平台创建调度 Agent、给它写职责提示词、调度 Agent 的模型推理、被调用 Agent 的内部执行（用 MCP 还是直接调 API）——全部是 A2A 不管的实现自由。这种"薄协议"设计正是它容易被采用的关键：约束越少，接入越快。
