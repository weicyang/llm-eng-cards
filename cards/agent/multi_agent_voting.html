投票之所以能提高准确率，唯一的理由是各个 Agent 犯的错不一样。一旦它们用同一个基座模型、同一份提示词，投票就只是把同一个错误重复了五遍，而且比单跑一次显得更自信。

一、多数投票的三个隐含前提

"谁得票多听谁的"这句话之所以在生产里立不住，不是因为算法太简单，而是因为它悄悄依赖了三个在生产环境统统不成立的前提。把这三条摊开看，后面所有工程设计的动机就都清楚了。

1.1 独立性是投票的全部本钱

这一点值得单独讲透，因为它是最容易被忽略、后果最严重的一条。统计学上有个经典结论叫孔多塞陪审团定理：如果每个投票者独立作判断且各自正确率 p > 0.5，那么多数投票的正确率会随投票人数增加而单调上升并趋近 1。这个定理正是所有投票机制的理论依据，但它有两个前提缺一不可——独立，以及 p > 0.5。

把数字算出来会更直观。假设单个 Agent 正确率 60% 且错误完全独立：

568.3%31.7%60.0%
771.0%28.8%60.0%

三件事同时暴露出来。第一，即使在理想的独立假设下，收益也远比直觉小——投票人数从 1 加到 7（成本 7 倍）只把正确率从 60% 抬到 71%。第二，当单体正确率低于 50% 时，投票会让结果更差，因为多数投票放大的是趋势而非真相，而错误恰好是趋势。第三，也是最关键的一点：如果错误完全相关，无论投多少人，正确率一动不动，只是账单翻了几倍。

现实中的相关性来源非常隐蔽：同一个基座模型的不同实例、同一份提示词模板、同一个知识截止日期、同一个检索到的错误文档。要让投票真正产生价值，必须主动制造多样性——用不同厂商的模型、给出不同的提示词视角、让不同 Agent 走不同的检索路径。多样性不是副产品，是投票机制必须付费购买的东西。

投票买的不是"更多算力"，是"更多种犯错方式"。五个用同一个模型同一个提示词的 Agent，本质上是同一个投票者投了五次。

2.1 决策层必须无状态、状态必须外置

投票任务天然是长耗时的（要等最慢的投票者），如果一次投票的中间状态——已下发给谁、已收到哪些答案——只存在决策层的进程内存里，那么决策层任意一次重启或崩溃都会让所有在途投票全部作废，而这些答案已经花了钱。正确做法是把投票会话的状态写入外部存储，每收到一票就落一条记录，决策层任意副本都能接手继续聚合。

2.2 不要等所有人

朴素实现是"等 N 个答案全部回来再聚合"，这让整体延迟等于最慢那个投票者的延迟，也就是把长尾延迟直接暴露给用户。更好的做法是早退法定人数：预先算出"已经不可能被翻盘"的条件，一旦满足就立刻返回，不等剩下的。比如 5 个投票者中已有 3 个落进同一个语义簇，剩下 2 票无论投什么都改变不了最大簇，此时继续等待没有任何信息增益。这样延迟就从"第 5 快"降到"第 3 快"。

2.3 留痕不是可选项

投票系统的调试完全依赖留痕，因为它的输出是一个聚合结果，事后必须能回答"当时为什么选了这个答案"。至少要存下每个投票者的原始回答全文、响应耗时、使用的模型与版本、当时生效的权重、以及它被归入了哪个语义簇。缺了"簇归属"这一项，语义归并环节就成了黑盒——你会看到最终答案很奇怪，却完全不知道是某两个答案被错误地合并了，还是本该合并的没有合并。

投票系统的延迟不该由最慢的那一票决定。当胜负已经无法翻转，继续等待就只是在为已经确定的结论付钱。

三、语义等价：从字面到向量聚类

自由文本投票的第一个技术难点是判断两个答案是不是同一个答案。字面比对会在三种情形下失效：同义表述（"苹果手机"与 "iPhone"）、粒度不同（"约 3 亿"与 "2.98 亿"）、结构不同（分点列表与整段叙述表达同一结论）。这三种情况下票会被无谓地打散，五个其实一致的答案被数成五个不同的答案，投票直接失去意义。

3.1 等价判定的方法谱系

方法成本能识别主要失效模式
字面精确匹配近零完全相同的字符串任何措辞差异都判为不同
规范化后匹配近零大小写、空格、单位、数值精度差异同义词、不同句式
Embedding 余弦相似度低同义表述、不同句式对否定极不敏感，正反答案可能高度相似
LLM 裁判判等价高复杂语义、条件与例外成本随候选对数平方增长，自身也会出错
结构化断言比对低关键结论与极性要求答案能被抽成固定字段

3.2 Embedding 的否定陷阱

这是这一节最需要记住的一条。余弦相似度衡量的是两个向量方向的接近程度，用它判断语义等价的隐含假设是"语义相近的文本向量方向相近"。问题在于句向量主要由主题词决定，而"这个方案可行"和"这个方案不可行"共享了几乎所有词，主题完全相同，只差一个否定副词——它们的余弦相似度往往高得惊人，很容易越过 0.8 这样的常用阈值。也就是说，纯粹依赖 Embedding 相似度的聚类会把两个完全相反的答案合并成同一个簇，投票结果变成随机选一个代表元，而且系统还会报告"高度一致"。

解法是不要让 Embedding 单独承担判定责任，而是先抽取结构化断言再比对：让每个投票者按固定格式输出核心结论（结论字段、极性字段、关键实体、以及自由文本理由）。极性和关键实体做精确比对，只有在这些硬字段一致时才用 Embedding 处理剩下的表述差异。这样"可行 / 不可行"在第一步就被硬性分开，Embedding 只负责它擅长的同义归并。

3.3 聚类：连通分量的链式合并陷阱

五个候选答案 ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ │ a │ │ b │ │ c │ │ d │ │ e │ └─┬─┘ └─┬─┘ └─┬─┘ └─┬─┘ └─┬─┘ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ① 结构化抽取：{结论, 极性, 关键实体, 理由} │ ├── 极性/实体不一致 ──────────▶ 硬性分簇（绝不合并） │ ▼ ② 对"理由"向量化，两两算余弦相似度，建相似度图 a ──0.91── b ──0.86── c d ──0.93── e (与 abc 均 < 0.8) │ ▼ ③ 归并：要求簇内两两相似（团），而非仅连通 ┌─────────────┐ ┌─────────┐ │ 簇1: a,b,c │ │ 簇2: d,e │ │ 加权票 3.4 │ │ 加权票 1.8│ └─────────────┘ └─────────┘ │ ▼ ④ 最大簇占比 = 3.4/5.2 = 65% → 超过阈值，选簇1 簇内代表元 = 离质心最近 / 权重最高的那一条

常见做法是在相似度图上求连通分量——只要两个答案相似度超阈值就连边，同一个连通块算一个簇。这个做法简单但有个陷阱：相似度不满足传递性。a 与 b 相似度 0.85、b 与 c 相似度 0.85，但 a 与 c 可能只有 0.6；连通分量会把三者并成一簇，若这条链继续延长，最终可能把语义相差很远的答案一路串在一起，这就是链式合并。更稳妥的判据是要求簇内两两都相似（图论上的团），或者退一步用"离簇代表元的相似度"而非"离任意成员的相似度"作为入簇条件。

密度聚类算法（如 DBSCAN）的优点是不需要预设簇数、还能把离群答案标为噪声，但它的邻域半径参数极难调，且在候选数只有三五个的小样本上，密度概念本身就不太成立。候选数在个位数时，直接用带团约束的贪心归并比套聚类算法更可控。

3.4 最大簇占比是免费的置信度

归并完成后，除了"选最大簇"，还应该输出最大簇的加权票数占总票数的比例。这个数字是一个不用额外花钱的不确定性信号：占比 90% 意味着投票者高度共识，占比 35% 意味着答案严重分散，此时就算最大簇确实最大，也不应该被当成可靠答案直接返回。第四节的"出口设计"完全建立在这个指标上。

向量相似度看的是"在聊同一件事吗"，不是"结论一样吗"。把"可行"和"不可行"交给余弦相似度去分辨，等于让它做一道它从没学过的题。

4.1 Self-Consistency 与多 Agent 投票不是一回事

Self-Consistency（自一致性）指的是让同一个模型对同一个提示词采样多条不同的推理路径，然后对最终答案取多数——它在数学推理这类任务上效果显著，因为同一个模型每次的推理路径确实不同，多数投票能过滤掉中途算错的那些路径。但要看清它的边界：它消除的只是采样随机性，消除不了模型的固有偏见。如果模型系统性地误解了题意或缺失某块知识，一百次采样会一百次犯同一个错，投票结果会以极高的一致性给出错误答案。这正好对应第一节那条"错误完全相关"的列——一致性高不等于正确率高。真正要降低错误相关性，必须换模型、换视角、换检索路径。

4.2 权重从哪来，以及必须截断

权重来源可靠性注意事项
历史准确率（按任务类型分桶）最可靠必须分桶，全局准确率会掩盖能力结构差异
自报置信度低模型普遍过度自信，须先做校准再用
输出概率（logprob）中只有自部署或开放该字段的模型可取
模型能力档位中粗粒度先验，适合冷启动时的初始权重
与最大簇的历史一致率中会奖励"随大流"，不宜作为唯一依据

两条实践约束。一是权重必须设上限截断：如果某个 Agent 的权重可以无限增长，投票机制会逐渐退化成"听它一个人的"，多样性收益归零，而且这个退化过程是缓慢的、不报警的。二是自报置信度不能直接当权重：大模型的自评置信度普遍偏高且区分度差（几乎所有答案都自称"很确定"），必须先用历史数据做校准映射，或者干脆只把它当作一个辅助排序信号。

4.3 出口设计：允许说"不知道"

最大簇加权占比 │ ┌─────────────┼─────────────┐ ≥ 70% 40% ~ 70% < 40% │ │ │ ▼ ▼ ▼ ┌─────────┐ ┌──────────┐ ┌──────────────┐ │ 直接返回 │ │ 升级裁决 │ │ 返回"不确定" │ │ 高置信 │ │ 更强模型 │ │ + 候选清单 │ │ │ │ 或加投票者 │ │ 高风险则转人工 │ └─────────┘ └──────────┘ └──────────────┘ │ │ │ └─────────────┴─────────────┘ ▼ 无论走哪条出口，都把置信度随答案一起返回 让下游能决定"要不要相信"

平票和低置信度绝对不能靠"随便挑一个"或"选第一个"糊过去。投票机制最被低估的价值恰恰是它能识别自己不确定——最大簇占比这个指标是免费的不确定性度量，而单个模型跑一次是拿不到这种信号的。把置信度随答案一起返回给下游，让下游决定是展示给用户、还是走人工复核、还是换个方式重试，这比强行输出一个答案有用得多。

行业数据 · 投票式并行的收益与代价：Anthropic 工程博客《How we built our multi-agent research system》（2025-06）报告，用 Claude Opus 4 作主控、Claude Sonnet 4 作并行子 Agent 的架构，在广度优先的研究类任务上比单 Agent Opus 4 高出 90.2%；同一篇文章也给出代价——多 Agent 系统的 Token 消耗约为普通聊天的 15 倍（单 Agent 约 4 倍），并明确指出这类架构只在"任务价值足够高、能覆盖增加的成本"时才经济可行，且需要共享同一上下文或 Agent 间依赖很多的场景并不适合。这两组数字放在一起就是投票机制的完整定价：并行多路推理确实能显著提升难任务上的效果，但它是一笔按数量级计价的开销，必须靠任务价值来撑。

一个敢说"我不确定"的投票系统比一个总能给出答案的强。分散的票本身就是最有价值的输出——它在告诉你这题不该由机器直接拍板。

五、超时、失效与恶意 Agent

5.1 超时：不是拍一个数，而是一套策略

基础超时不该拍脑袋定，而应该取该 Agent 在该任务类型上的历史 P95 耗时再留一点余量——不同模型、不同任务的耗时分布差异巨大，一个统一的超时值必然对某些组合过于苛刻、对另一些过于宽松。在此之上叠加随机抖动（在基础值上下浮动一定比例），目的是避免一批同时下发的调用在同一时刻集体超时：集体超时会导致重试也集中在同一时刻，把一次抖动放大成周期性洪峰。

对冲请求接近 P50N× + 少量副本长尾严重且单次成本可接受
级联早停第 2 快（多数情况）2×~N×成本敏感且任务多数容易

对冲请求值得解释一下：当某个投票者的耗时超过历史 P95 仍未返回时，不取消它，而是另外再发一个副本给别的 Agent，两者谁先返回就用谁的。这能有效砍掉长尾延迟，代价是少量额外调用。它和早退法定人数是互补的——早退处理"已经够了"的情况，对冲处理"还差一票但那一票卡住了"的情况。

5.2 识别失效与失真的投票者

比宕机更麻烦的是"看起来在工作但票不可信"。这类问题不会抛异常，只会持续污染投票结果，必须靠专门的信号去发现。

失效模式检测信号处置
宕机 / 超时连续超时次数、失败率断路器熔断，暂停派票
格式不合规结构化字段解析失败率一次重试后降权，持续则摘除
答案退化（总答同一个）该 Agent 输出的答案分布熵异常低告警排查提示词或模型版本
响应异常快耗时远低于历史 P5，且答案极短疑似未真正推理，降权并抽查
系统性偏离与最终最大簇的历史偏离率显著偏高动态权重衰减，进入观察名单
投毒 / 越权输出输出违反 schema 约束或含注入痕迹立即隔离，人工介入

处置方式的选择很关键：优先用动态权重衰减，而不是直接踢出。直接摘除有两个问题——一是可能误伤（某个 Agent 在特定任务类型上偏离多，未必是它错了，也可能是它更专业）；二是没有恢复路径，模型升级或提示词修好之后它无法自动回到池子里。权重衰减是连续的、可逆的，而且衰减曲线本身就是一份可观测的能力档案。断路器的状态机细节（最小样本量门槛、半开限量探测、冷却时间指数延长）见 《A54 · 多 Agent 负载均衡与任务调度》第五节。

示例场景 · 早退法定人数的延迟收益：一个风控审核链路用 5 个异构 Agent 投票，各投票者耗时的 P50 大致在 1.2~2.1 秒，但其中一个走了外部检索的 Agent P99 达到 9.4 秒。最初实现等全部 5 票返回，端到端 P99 被这一个投票者钉在 9.8 秒，超出了 8 秒的时延预算，超时率 7%。改为"任一语义簇累计加权票数达到 3 即提前返回"后，端到端 P99 降到 3.6 秒，超时率降到 0.4%；由于约 78% 的请求在收到第 3 票时就已锁定结果，剩余两票的响应被直接丢弃——注意这部分 Token 仍然花掉了，延迟优化了但成本没省。真正要省成本得靠级联早停：先只发 2 票，一致才返回、不一致才补发，这才是"少花钱"而不只是"少等待"。

早退省的是时间，级联省的是钱。两者常被混为一谈，但它们优化的是完全不同的资源——想清楚你缺哪个再选。

六、成本、延迟与何时不该投票

投票机制的成本模型极其简单也极其残酷：N 个投票者就是 N 倍的推理开销，再加上聚合环节的向量化和可能的裁判模型调用。这个倍数不是优化几个百分点能对冲的，必须在架构层面处理。

总成本 ≈ Σ(各投票者 Token 成本) + 聚合成本(向量化 + 裁判) + 重试成本

6.1 预算闸门放在执行前

成本控制的关键是把闸门放在执行之前而不是之后——事后统计只能告诉你钱花超了，事前估算才能阻止它。做法是给每个请求设定 Token 预算，在下发投票任务前用输入长度、预期输出长度、投票者数量和各自的单价估算总开销，超预算时按阶梯降级。

降级档位动作成本变化质量代价
L0按原计划全量异构投票基准无
L1减少投票者数量（5 → 3）约 -40%置信度分辨率下降
L2改用级联早停，先发 2 票约 -50%两票同错时无法察觉
L3换更便宜的模型组合约 -70%单体正确率下降
L4放弃投票，单模型直出约 -80%失去纠错与置信度信号

6.2 级联早停：为什么它是最省钱的模式

级联早停的逻辑是：先只派 2 个投票者，如果它们的答案落进同一个语义簇就直接返回，只有不一致时才补发剩余的投票者。它省钱的原因不在算法巧妙，而在真实流量的分布特性——大多数请求是容易的。假设 80% 的请求两票就能达成一致，那么平均成本是 0.8×2 + 0.2×5 = 2.6 票，而不是 5 票，相当于在只损失少量纠错能力的前提下省下近一半开销。它唯一的盲区是"两票都错且错得一样"，而这个盲区可以通过让这 2 票来自不同厂商的模型来显著收窄。

6.3 最重要的一条：能验证就不要投票

投票的本质是在没有客观判据时用共识近似正确性。所以在动手搭投票系统之前，第一个该问的问题是：这个任务真的没有客观判据吗？

任务特征推荐方案理由
结果可自动验证（跑测试、查库、校验 schema、算式可复算）验证器 + 重试验证给出确定答案，比投票既便宜又正确
有唯一正确答案但无法自动验证（数学推理、抽取）Self-Consistency 或异构投票多路推理能过滤中途出错的路径
开放性判断、需要权衡取舍异构投票 + 裁判 或 Debate没有客观判据，共识是最好的近似
高风险且错误代价极高投票 + 置信度门槛 + 人工兜底低置信必须能转人工，不能强行输出
低价值高频请求单模型 + 缓存投票的成本倍数无法被任务价值覆盖

第一行是最容易被跳过、收益也最大的一条：如果结果能被程序验证，就不要用五个模型投票去猜它。生成的 SQL 能不能跑通、生成的代码能不能过测试、抽取的字段是否符合 schema、引用的数字能不能在原文里核对上——这些都是确定性判据。用一个验证器加一次重试，比五路投票便宜一个数量级，而且给出的是真正的对错而不是多数人的意见。投票应该留给那些确实无法验证的判断。

  • 先问"能不能验证"，能验证就用验证器而非投票
  • 主动购买多样性：不同厂商、不同视角提示词、不同检索路径
  • 先按极性与关键实体硬分簇，再用 Embedding 归并表述差异
  • 簇内要求两两相似，避免连通分量的链式合并
  • 把最大簇占比作为置信度随答案一起返回
  • 低置信时升级裁决或返回"不确定"，不要强行拍板
  • 用早退法定人数砍延迟，用级联早停砍成本
  • 失效投票者用权重衰减而非直接摘除，保留恢复路径
  • 留痕必须含簇归属，否则归并环节是黑盒
  • 用同一个模型同一份提示词跑 5 遍，然后称之为投票
  • 把 Self-Consistency 的高一致性当成高正确率
  • 单独用余弦相似度判等价，把"可行/不可行"合成一簇
  • 在单体正确率低于 50% 的任务上加投票者（只会更差）
  • 拿模型的自报置信度不加校准就当权重
  • 让某个 Agent 的权重无上限增长，静默退化为独裁
  • 平票时"选第一个"糊过去，丢掉不确定信号
  • 等所有票返回，把最慢投票者的长尾暴露给用户
  • 投票会话状态只放决策层内存，一次重启作废全部在途投票
💡 知识要点：本文只解决一个问题——多个 Agent 各说一套，怎么聚合成一个可信的答案，以及怎么知道这个答案有多可信：误差独立性的理论边界、语义归并的具体做法、策略与权重的选型、超时与失效处置、成本与延迟的取舍。多 Agent 协作的完整图景（任务怎么分解成 DAG、角色怎么用 System Prompt 定义、通信拓扑怎么选、Debate 等协作模式的全貌、框架怎么选）见 《A46 · 多 Agent 系统协作机制》：A46 是协作全景（含 Debate 模式的介绍），本文专攻结果聚合这一个环节，把它挖到能落地的深度。任务派给谁见 《A54 · 多 Agent 负载均衡与任务调度》，多个 Agent 抢同一个工具的仲裁见 《A55 · 多 Agent 工具调用冲突仲裁》。

投票是在没有裁判的时候找共识。有裁判（可自动验证）就直接让裁判判——用五个模型投票去猜一件跑一次测试就能确定的事，是花十倍的钱买一个更差的答案。

Q&A

为什么说"错误独立性"是投票机制的全部本钱？
因为投票的理论依据是孔多塞陪审团定理：投票者独立判断且各自正确率高于 50% 时，多数投票的正确率随人数增加趋近 1。这个定理的两个前提缺一不可。如果错误完全相关，无论投多少票，正确率都停在单体水平不动，唯一变化的是账单翻了几倍——五个用同一基座模型、同一份提示词的 Agent，本质上是同一个投票者投了五次。而且相关性的来源很隐蔽：同一模型的不同实例、同一提示词模板、同一知识截止日期、同一份检索到的错误文档。所以多样性不是投票的副产品，是它必须付费购买的核心资产：换厂商、换提示词视角、换检索路径。
加投票者一定能提高准确率吗？
不一定，而且有两种情况会让它变差。第一种是单体正确率低于 50%：多数投票放大的是趋势而不是真相，当错误是主流趋势时，投票会把它放大——单体 40% 正确率的三方投票只有 35.2%，五方降到 31.7%，人越多越错。第二种是错误高度相关：这时增加人数完全无效，正确率原地不动。即使在理想的独立假设下收益也远比直觉小，单体 60% 正确率时，从 1 票加到 7 票（成本 7 倍）只把正确率从 60% 抬到约 71%。所以决定要不要加投票者之前，先要能回答两个问题：单体正确率过 50% 了吗，这些投票者的错误方式真的不同吗。
用 Embedding 余弦相似度判断语义等价，最大的陷阱是什么？
对否定极不敏感。句向量主要由主题词决定，而"这个方案可行"和"这个方案不可行"共享了几乎所有词、主题完全一致，只差一个否定副词，它们的余弦相似度往往高到越过 0.8 这类常用阈值。结果是聚类会把两个完全相反的答案合并成一个簇，最终答案变成从中随机选一个代表元，而系统还会报告"高度一致"——错得彻底且毫无察觉。正确做法是不让 Embedding 单独承担判定：要求每个投票者按固定格式输出结论、极性、关键实体和自由文本理由，先对极性和关键实体做精确比对硬性分簇，只有硬字段一致时才用 Embedding 归并剩下的表述差异。
Self-Consistency 和多 Agent 异构投票有什么本质区别？
Self-Consistency 是同一个模型对同一个提示词采样多条推理路径后取多数，它消除的是采样随机性——每次推理路径不同，中途算错的路径会被多数过滤掉，所以在数学和逻辑推理上效果明显。但它消除不了模型的固有偏见：如果模型系统性地误解题意或缺少某块知识，一百次采样会一百次犯同一个错，并以极高的一致性给出错误答案。多 Agent 异构投票换的是模型、提示词视角和检索路径，攻击的是错误相关性本身，因此能覆盖模型级别的偏见。实践含义很直接：Self-Consistency 的高一致性绝不能被读作高正确率，它只说明"这个模型很稳定地这么认为"。
平票或票数分散时该怎么处理？
绝不能"选第一个"或随便挑一个糊过去，因为票数分散本身就是一条极有价值的信息——它在告诉你这题不该由机器直接拍板。可行的做法是用最大簇的加权占比做分档出口：占比高（比如七成以上）直接返回；处于中间区间则升级裁决，交给更强的模型或补发投票者；占比很低就返回"不确定"加上候选清单，高风险场景直接转人工。关键是无论走哪条出口，都要把置信度随答案一起返回给下游，让下游决定要不要相信。这正是投票机制被低估的价值：单个模型跑一次拿不到不确定性信号，而最大簇占比是一个不用额外花钱就能得到的置信度度量。
怎么砍掉投票带来的延迟放大？
核心手段是不要等所有票。朴素实现的端到端延迟等于最慢投票者的延迟，等于把长尾直接暴露给用户。早退法定人数的做法是预先判断"胜负已不可能翻转"的条件——比如 5 票中已有 3 票落进同一个语义簇，剩下 2 票无论投什么都改变不了最大簇——满足即刻返回，延迟从"第 5 快"降到"第 3 快"。补充手段是对冲请求：某个投票者超过历史 P95 仍未返回时，不取消它而是另发一个副本给别的 Agent，谁先返回用谁的，专门用来处理"还差一票但那票卡住了"的情况。另外超时值本身应取该 Agent 该任务类型的历史 P95 而非拍脑袋，并叠加随机抖动，避免一批调用集体超时导致重试也集中在同一时刻。
怎么发现"在工作但票不可信"的 Agent，发现后该踢掉吗？
这类问题不抛异常，只会持续污染结果，需要专门的信号：结构化字段的解析失败率（格式退化）、该 Agent 输出答案的分布熵异常低（总答同一个，通常是提示词或模型版本出了问题）、耗时远低于历史 P5 且答案极短（疑似没真正推理）、与最终最大簇的历史偏离率显著偏高（系统性偏离）、输出违反 schema 或带注入痕迹（需立即隔离）。处置上应优先动态权重衰减而不是直接摘除，原因有两个：直接摘除可能误伤——某个 Agent 在特定任务类型上偏离多，也可能是它更专业而非它错了；而且摘除没有恢复路径，模型升级或提示词修好后它无法自动回到池子里。权重衰减是连续可逆的，衰减曲线本身就是一份可观测的能力档案。
什么情况下根本不该用投票？
当结果可以被程序验证的时候。投票的本质是在没有客观判据时用共识近似正确性，而只要存在确定性判据——生成的 SQL 能不能跑通、代码能不能过测试、抽取字段是否符合 schema、引用的数字能否在原文中核对上——就应该用验证器加重试，而不是让五个模型投票去猜。验证器比投票便宜一个数量级，而且它给出的是真正的对错，不是多数人的意见。另外两类不该投票的情况：低价值高频请求，投票的成本倍数无法被任务价值覆盖，用单模型加缓存更合适；以及需要所有参与者共享同一份上下文、彼此依赖很深的任务，这类场景并行拆分本身就不成立。投票应该留给那些确实无法自动验证的开放性判断。
投票系统的成本怎么控住，级联早停为什么最省钱？
关键是把预算闸门放在执行之前而不是之后——事后统计只能告诉你钱花超了，事前估算才能阻止它。做法是给每个请求设 Token 预算，下发前用输入长度、预期输出长度、投票者数量和各自单价估算总开销，超预算则按阶梯降级：减少投票者数量、改用级联早停、换更便宜的模型组合、最后才是放弃投票单模型直出。级联早停之所以最省钱，原因不在算法而在真实流量的分布——大多数请求是容易的。先只派 2 票，一致就返回，不一致才补发剩余投票者；若八成请求两票就一致，平均成本是 2.6 票而不是 5 票。它唯一的盲区是"两票同错且错得一样"，让这 2 票来自不同厂商的模型可以显著收窄这个盲区。注意早退法定人数省的是延迟不是成本，因为被丢弃的那些票已经花掉了 Token。
