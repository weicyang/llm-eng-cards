A22 · MCP 入门指南：原理与实战

Model Context Protocol · MCP Host · MCP Server · Tool · 交互流程 · uvx/npx 安装实战

MCP 不是一个远程服务器，而是一个让大模型能够调用本地程序的协议标准——通过统一的 JSON 配置 + STDIO 通信，让模型像使用手机 App 一样使用各种工具。

一、MCP 是什么

1.1 核心定义三连

What：MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月 25 日发布的开放协议，让大模型能够标准化地调用外部工具。

Why：大模型本身只会问答，不会主动使用外部工具。MCP 的出现等于给模型装上了"手和脚"，让它能够操作浏览器、查询实时数据、执行代码等。

What if not：没有 MCP，每个 AI 应用都要为每种工具单独写适配代码，生态碎片化严重，开发者重复造轮子。

MCP 之于大模型，就像 USB 协议之于电脑外设——统一接口标准，让任何工具即插即用。

1.2 MCP 能做什么

  • 让模型使用浏览器上网查询信息
  • 让模型操作 Unity 编写游戏
  • 让模型查询实时路况、天气、股票
  • 让模型读写文件、执行代码、调用 API
关键认知：MCP Server 名字带"Server"但不是传统远程服务器，它本质上就是一个本地程序（Python/Node.js），通过 STDIO（Standard Input/Output，标准输入/输出）与 Host 通信。

2.1 MCP Host（宿主）

MCP Host 是支持 MCP 协议的客户端软件，负责：

  • 连接大模型 API（Claude、GPT、DeepSeek 等）
  • 管理多个 MCP Server 的生命周期
  • 协调模型与 Server 之间的通信
  • 展示结果给用户并获取确认
Host 名称类型特点
Claude Desktop桌面应用Anthropic 官方出品
CursorIDE 插件代码编辑器深度集成
ClineVS Code 插件开源免费，社区活跃
Cherry Studio桌面应用国产，中文友好

2.2 MCP Server（服务端）

MCP Server 名字带"Server"但别被误导——它不是远程服务器，而是一个本地运行的程序，内置了一些函数（Tool）来解决特定问题。

MCP Server 的核心特征：

  • 本地运行：通过 Node.js 或 Python 在本地启动
  • STDIO 通信：使用标准输入/输出与 Host 对话
  • 可联网：内部可能调用外部 API（如天气 API）
  • JSON 配置：通过 JSON 文件注册到 Host

2.3 Tool（工具/函数）

Tool 在 MCP 领域里就是编程语言中的函数：

// 一个天气 MCP Server 包含两个 Tool
{
  "get_forecast": {
    "description": "获取指定地区未来天气预报",
    "parameters": {
      "latitude": "number (纬度)",
      "longitude": "number (经度)"
    }
  },
  "get_alerts": {
    "description": "获取指定州的气象预警",
    "parameters": {
      "state": "string (美国州代码)"
    }
  }
}

三、MCP 完整交互流程

以"查询纽约明天天气"为例，完整流程分 5 步：

用户提问: "明天纽约天气怎样？" │ ▼ ┌─ Host ──────────────────────────────────────┐ │ 1. 启动 Server → 注册 Tool 列表 │ │ Server: "我有 get_forecast 和 get_alerts"│ │ │ │ 2. 转发问题给模型 + 附带可用 Tool 列表 │ │ Model: "我需要调用 get_forecast │ │ 参数: lat=40, lon=-74" │ │ │ │ 3. 调用 Server Tool │ │ Host → Server: get_forecast(40, -74) │ │ Server → Host: {天气数据...} │ │ │ │ 4. 模型生成最终答案 │ │ Model: "纽约明天晴，白天 22°C..." │ └──────────────────────────────────────────────┘ │ ▼ 用户看到答案

3.1 阶段一：Server 注册

Host 启动 MCP Server 后，Server 会主动上报自己拥有的 Tool：

  • Host: "你好，我是 Cline"
  • Server: "你好，我是 Weather，我有 get_forecast 和 get_alerts 两个工具"
  • Host 记住这些信息，后续需要时调用

3.2 阶段二：模型决策

用户提问后，Host 将问题 + 可用 Tool 列表一起发给模型：

  • 模型判断自己无法直接回答（知识截止到去年 12 月）
  • 发现 get_forecast 工具可以解决
  • 返回调用指令："请调用 get_forecast，参数 lat=40, lon=-74"

3.3 阶段三：Tool 执行

Host 收到模型指令后：

  1. 向用户展示调用计划，请求确认（Approve）
  2. 用户同意后，Host 调用 Server 的 Tool
  3. Server 执行函数，返回结果
  4. Host 将结果传回模型

3.4 阶段四：生成回答

模型拿到 Tool 返回的真实数据后，生成最终的自然语言回答。

模型只动嘴、Host 来动手——决策与执行分离，就是整个交互流程的本质。

交互流程中四个角色的职责分工：

角色职责与 Tool 的关系
用户提出问题、确认（Approve）调用计划—
模型推理决策，输出"调用哪个 Tool + 参数"只决策，不执行
Host管理 Server、转发消息、实际调用 Tool发起调用
MCP Server注册 Tool 列表、执行函数逻辑并返回结果执行函数
核心要点：模型本身不执行 Tool，它只是"决定要调用哪个 Tool"，真正的执行由 Host 完成。这种分离保证了安全性和可控性。

四、MCP Server 配置详解

4.1 JSON 配置格式

{
  "mcpServers": {
    "weather": {
      "command": "uvx",
      "args": ["mcp-server-weather"],
      "transport": "stdio"
    },
    "fetch": {
      "command": "uvx",
      "args": ["mcp-server-fetch"],
      "transport": "stdio"
    },
    "hot-news": {
      "command": "npx",
      "args": ["-y", "@anthropic/hot-news-mcp"],
      "transport": "stdio"
    }
  }
}
字段说明示例
command启动 MCP Server 的程序uvx, npx, node
args传给 command 的参数包名、脚本路径等
transport通信方式stdio（主流）, sse（少见）
disabled是否禁用true / false
timeout连接超时（秒）默认 60 秒

4.2 两种启动方式对比

方式适用语言安装前提自动下载
uvxPython安装 UV 包管理器✅ 首次自动下载依赖
npxNode.js安装 Node.js✅ 首次自动下载依赖

uvx（UV 包管理器提供的命令，自动下载并运行 Python 包）与 npx（Node.js 自带的包运行器）都能仅凭一行配置就直接启动对应的 MCP Server，无需提前手动安装 Server 本身。

uvx/npx 首次启动时会下载依赖，默认超时 60 秒。如果网络慢，建议先手动在终端执行一次命令，等下载完再回到 Host 中配置。

JSON 配置只做一件事：告诉 Host"用哪个命令启动哪个 Server"——command 是启动器，args 是目标程序，transport 是通信方式。

4.3 超时问题解决方案

  • 首次配置时，先在终端手动执行命令下载依赖
  • 下载完成后退出（Ctrl+C 或 Ctrl+\），再回 Host 配置
  • 增大 timeout 值（如 120 秒）
  • 确保网络稳定，必要时使用代理
  • 不要在 Host 中直接安装（可能超时失败）
  • 不要忽略红色加载指示（绿色开关只代表未禁用）
  • 不要按 Ctrl+C 退出 MCP Server（它不会响应）
  • 不要用 Ctrl+C 退出，用 Ctrl+\ 或直接关终端

6.2 Hot News MCP Server 实战

使用 hot-news-mcp（npx 启动）拉取实时新闻：

  • npx 自动下载并启动 Node.js 程序
  • 支持多个新闻源（科技、财经、体育等）
  • 模型自动选择合适的 Tool 和参数

MCP 的生产价值：模型负责理解意图、挑选工具，Server 负责把活干扎实——各司其职。

  • 手动配置 JSON，了解每个字段的含义
  • 先用终端测试命令是否可用
  • 关注 MCP Server 市场的文档说明
  • 对首次使用的 Server 先小范围测试
  • 不要完全依赖模型自动安装（可能乱搞环境）
  • 不要忽视安装文档中的特殊要求
  • 不要在生产环境用未经测试的 Server
  • 不要混淆"已启用"和"已加载"的状态

高频问答

MCP Server 和传统的 HTTP API 有什么区别？
MCP Server 是本地运行的程序，通过 STDIO（标准输入输出）与 Host 通信，而传统 HTTP API 是远程服务通过 HTTP 协议通信。MCP Server 内部可能会调用 HTTP API，但它本身不是远程服务。MCP 的优势在于统一了工具调用标准，让任何 Host 都能即插即用地接入任何 Server。
为什么模型不直接执行 Tool，而是通过 Host 中转？
这是安全设计。模型只能"决定要调用哪个 Tool 和什么参数"，实际执行由 Host 完成。Host 可以在执行前向用户展示调用计划并请求确认（Approve），防止模型执行危险操作。这种"决策-执行分离"是 MCP 的核心安全机制。
STDIO 和 SSE 两种 transport 方式有什么区别？分别适用什么场景？
STDIO（标准输入输出）是目前主流方式，Server 作为本地进程运行，通过 stdin/stdout 与 Host 通信，简单高效。SSE（Server-Sent Events）适用于需要远程访问的场景，Server 作为 HTTP 服务运行，Host 通过 HTTP 连接。目前 90%+ 的 MCP Server 使用 STDIO 模式。
uvx 和 npx 首次启动超时怎么解决？
超时原因是首次运行需要下载依赖包，默认超时 60 秒。解决方案：1) 先在终端手动执行一次命令，等依赖下载完毕；2) 下载完成后用 Ctrl+\ 退出（Ctrl+C 可能不响应）；3) 回到 Host 重新配置，此时启动会很快因为依赖已缓存；4) 或者直接增大 timeout 配置值。
MCP Host 在 Tool 注册阶段做了什么？为什么这一步很重要？
Host 启动 Server 后，Server 主动上报自己的 Tool 列表（名称、描述、参数格式）。Host 记住这些信息，在后续对话中将可用 Tool 列表附带给模型。这一步很关键，因为模型需要知道有哪些 Tool 可用才能做出正确的调用决策。如果注册失败，模型就无法使用该 Server 的任何工具。
如何判断一个 MCP Server 是否成功加载？
注意区分两个状态：1) 绿色开关 = 未被禁用（配置层面）；2) 红色圆点 = 尚未加载完成（运行层面）。只有绿色开关亮起且没有红色圆点时，Server 才算成功加载。常见的加载失败原因是超时（依赖未下载完）和命令路径错误。
