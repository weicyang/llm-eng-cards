A09 · Agent 框架选型

四大框架流派解析 / 选型决策矩阵 / MCP 协议互联 / 架构师能力转向

框架选型从来不是"哪个最强"，而是"哪个最合适"：四大流派本质上是对开发速度、控制粒度、生态依赖、合规成本这四件事的不同押注。想清楚你的系统里状态由谁保管、故障由谁兜底、迁移由谁买单，答案就出来了。

一、工程化能力成为选型核心

两年前评估一个 Agent 框架，问题通常是"能不能接上某个模型""有没有现成的 Prompt 模板"。今天这套问法已经失效——Agent（能够自主规划、调用工具并持续迭代直到完成目标的智能体系统）正在从演示走向生产，选型的焦点随之整体迁移：不再验证"功能是否存在"，而是验证"生产级问题如何被工程化地解决"。一个直观的背景数据是：Gartner 预测到 2026 年底将有 40% 的企业应用嵌入任务型 AI Agent（2025 年这个数字还不到 5%），但同期另一份分析预测，超过 40% 的 Agentic AI 项目会在 2027 年底前被砍掉。两个数字之间的鸿沟，大部分由工程化能力不足填满。

工程选型核心关注点可以收敛为四类生产级问题，它们共同决定了框架的"及格线"：

核心关注点生产问题的具体形态选型时要验证的框架能力
逻辑死循环处理模型反复调用同一工具、在两个节点间震荡不收敛，token 持续烧钱迭代上限、节点级超时熔断、重复状态检测与强制终止
长程状态控制任务跨越数小时甚至数天，进程重启、模型故障后必须能接着跑Checkpoint（检查点，将运行状态持久化以便恢复的机制）持久化、断点续跑、状态回放
跨语言技术栈整合企业内 C#/.NET 与 Python 团队并存，Agent 要与两套存量系统对话双语言运行时对等、协议层解耦而非胶水代码硬接
异构系统编排多个 Agent 分工协作、流程中嵌入人工审批闸门、跨框架交接任务图调度、中断恢复、Human-in-the-loop 一等公民支持

以死循环为例：这不是理论风险，而是每个跑过生产 Agent 的团队都见过的事故形态。LangGraph 在 2026 年版本里补齐了节点级超时（per-node timeout），允许给单个节点设置执行时限；微软 Agent Framework 则用 DAG 工作流的检查点机制保证"卡死在第 7 步的任务可以从第 7 步恢复而不是从头重来"。而自研框架如果不在第一天就写进迭代上限和超时逻辑，等于把事故预埋进了地基。

Human-in-the-loop（人在回路，让人类在关键节点审批或修正 Agent 行为的机制）同样从"加分项"变成了"必答题"：金融、医疗、法务场景里，没有人工审批闸门的 Agent 根本过不了合规评审。框架是否原生支持"执行到某节点暂停、挂起状态等待人工确认、确认后精确恢复"，直接决定了这类项目是两周上线还是重写三个月。

行业坐标 · 两个数字的鸿沟：Gartner 预测到 2026 年底 40% 的企业应用将嵌入任务型 AI Agent（一年前不足 5%），但同期警告超过 40% 的 Agentic 项目会在 2027 年底前被砍掉。采用率与砍单率之间这道鸿沟，就是演示级与生产级的分水岭——选型时验证的每一项工程能力，都是在为不被砍掉增加筹码。

判断一个框架是否成熟，别看它的演示有多少炫目功能，看它如何回答"Agent 不收敛、进程崩溃、审批被打回时怎么办"——这三个问题的答案才是生产级成色。

二、四大框架流派深度解析

2026 年的 Agent 框架格局已经沉淀出四个清晰的流派。它们不是同一维度上的竞争关系，而是占据着"封装程度 × 生态完备度"坐标系中不同的象限，各自服务不同形态的工程问题。

生态完备度 / 外部集成依赖 ▲ 高 │ ● 生态万能派 ● 企业专精派 │ LangChain / LangGraph MAF / PydanticAI │ 700+ 集成 · 图调度 · 可观测 合规审计 · 双语言 · 强类型 │ │ ● AI 原生派 │ Claude Code / Claude Agent SDK 低 │ Skills + Subagents · MCP 原生 ● 自研极简派 │ While 循环 · 零依赖 │ 代码全透明 └───────────────────────────────────────────────▶ 封装程度 高封装（模型驱动，少写控制流） 低封装（手写控制流，全透明）

2.1 AI 原生派：Claude Code / Claude Agent SDK

这一派的设计哲学是"把调度权交给模型本身"：不手写状态机，不做复杂的节点编排，而是信任大模型的原生推理能力去驱动整个循环。Claude Code 是这一路线的旗手——它本身就是用这套原语构建的编码 Agent，随后 Anthropic 把同样的机制打包成 Claude Agent SDK 开放给开发者。

它的三大支柱是：Skills（以 Markdown 文件封装的可复用技能包，按需加载指令与脚本）、Subagents（子代理，可派生独立上下文执行子任务，避免主上下文被撑爆）以及 MCP 协议统一接入外部工具。2026 年 6 月的版本进一步支持了层级式 Subagent 派生与后备模型链（主模型失败自动切换备用模型）。在同一家评测机构"同一个研究摘要 Agent 在 13 个框架里各实现一遍"的基准测试中，Claude Agent SDK 以 8 分钟、24 行代码完成首个 MCP Agent，是所有被测框架里最快的一档。

适用场景：快速落地项目、编码与文件操作类任务、工具链已经标准化的团队。反例：SDK 围绕 Claude 模型深度优化，模型锁定评级为"高"——如果业务要求能在 GPT、Gemini 之间自由切换，或者需要精细到每条边的自定义控制流，从这里起步会在中途付出高昂的重构代价。

2.2 生态万能派：LangChain / LangGraph

LangChain 主仓库超过 13 万 GitHub Star、700+ 现成集成，是绝大多数团队接触 Agent 开发的第一站。但真正把这一派推进到生产深水区的是 StateGraph（LangGraph 的核心抽象，把工作流建模为节点是函数、边是状态转移的有向图）：LangGraph 1.0 于 2025 年 10 月 GA，2026 年又陆续补齐了节点级超时、延迟节点（原生 fan-in 屏障）、模型调用前后钩子（上下文裁剪、护栏、PII 脱敏）。行业统计显示，2026 年 Q1 在千人以上规模企业的生产架构文档中，LangGraph 出现在 34% 的方案里，居所有框架之首。

它的杀手锏是控制力与可观测性的组合：状态是带类型的对象、逐字段做检查点，可持久化到 PostgreSQL / SQLite / Redis；配合 LangSmith 全链路追踪，出问题时能精确看到"哪个节点执行了、当时状态长什么样、在哪一步偏离了预期"——这在合规敏感行业是监管方能否审查系统的分水岭。

但这一派有一条必须掌握的"断舍离"原则：只使用核心调度层，不把全家桶组件全部堆进项目。图抽象本身是有代价的——一份硬核基准测试显示，同样的任务 LangGraph 平均延迟 10155ms，而链式方案只需 6046ms，慢 68%；检查点机制带来约 1.5MB 的单步写放大，极端场景下存储膨胀可达 15 倍。这笔"状态税"在需要断点恢复、人工审批、多 Agent 协作时物有所值，在简单一次性问答里就是纯粹的浪费。

生产案例 · Klarna：这家支付巨头将基于 LangGraph 的客服 Agent 推上生产后，平均解决时长从 11 分钟降至 2 分钟（降幅约 80%），系统累计处理 250 万次对话，产出相当于约 700 名全职客服的工作量，公司预计该改进带来 4000 万美元的利润改善。

适用场景：带人工审批闸门的长程工作流、多 Agent 并行后汇总的管线、需要审计追踪的合规场景。反例：一个只做"检索→生成"的线性 RAG 或单轮工具调用，引入图模型就像用 Kubernetes 部署静态网站——能做，但不该。

2.3 自研极简派：While 循环 + JSON 校验 + Function Calling

这一派的立场是反对过度封装：一个可用的 Agent 内核只需要三要素——一个带硬上限的 While 循环、对模型输出的 JSON Schema 校验、以及 Function Calling（函数调用，模型以结构化格式声明要调用哪个工具及参数，由宿主程序执行）。数百行代码就能搭出一个完全透明的轻量框架，每一行都在自己的掌控之中。

while not done and step < MAX_STEPS:          # 硬上限，防死循环
    resp = llm.chat(messages, tools=tools)    # Function Calling
    if resp.tool_calls:
        args = validate(resp.tool_calls, schema)  # JSON 校验白名单
        messages.append(run_tool(args))
    else:
        done = True

透明的另一面是要自己兜底一切：没有内建护栏、没有现成可观测性、状态持久化和失败重试全要手写。行业里把这条路线称为 vanilla（原生代码）档位，它的典型成本画像是：从零到生产需要 6–12 个月、3–6 名工程师、15–50 万美元级别的投入，后续每年还要 10–30 万美元维护费。对比之下，借助成熟框架的档位通常 2–4 个月即可上线。

适用场景：简单审批流、低频工具调用、对代码透明度要求极高且复杂度确实很低的需求；或者 Agent 的推理逻辑本身就是核心竞争壁垒、不允许任何第三方抽象介入的产品。反例：需要在 6 个月内交付、或者做的是客服支持、数据分析这类框架早已解决好的通用场景，自研纯粹是用最贵的成本买最慢的进度。

2.4 企业专精派：微软 MAF 与 PydanticAI

这一派不为"通用"而生，而是为企业级约束（合规、审计、跨语言、强类型）量身打造，2026 年迎来了两个标志性节点。

微软 Agent Framework（MAF）于 2026 年 4 月 3 日发布 1.0，把 Semantic Kernel 与 AutoGen 合并进同一个 MIT 许可的 SDK，同时 AutoGen 进入维护模式——微软系用户一夜之间有了官方迁移目标。它的最独特之处是 C# 与 Python 双语言对等（每语言各 27 个包），并提供 DAG 工作流、检查点、时间旅行调试、5 种编排构建器，原生支持 MCP 与 A2A（Agent-to-Agent，跨框架、跨厂商的 Agent 任务交接协议）。底层与 Azure AI Foundry、Copilot Studio、Cosmos DB、Purview 深度整合，并内建 OpenTelemetry GenAI 语义追踪。合并前的 Semantic Kernel 与 AutoGen 合计带来超过 7.5 万 GitHub Star 的存量用户。

PydanticAI 出自 Pydantic 团队，把 FastAPI 式的开发体验搬进了 Agent 领域：类型化 Agent、依赖注入、以 Pydantic 模型约束结构化输出。V2 于 2026 年 6 月 23 日稳定，转向"harness-first"设计——小核心加可组合的能力原语，由一等公民的 Harness 统一管理记忆、护栏与代码执行。强类型的价值有硬核数据背书：一份对比基准发现，在同等生产负载下，PydanticAI 的类型安全校验层拦截了 23 个会直接漏给用户的 Bug，而对照组框架全部放过——错误在边界处以校验失败的形式显式暴露，而不是在下游变成静默的错误行为。

生产案例 · Rexera：这家每天处理数千条工作流的房地产质检公司记录了清晰的演进轨迹：单提示词 LLM 方案误报率高达 35%，迁到角色式多 Agent 框架后降到 8%，最终落到 LangGraph 的精确路径控制上，误报率压到 2%、漏报率 2%。三次迁移的本质，是业务对"决策路径可解释、可控制"的要求不断收紧。

适用场景：MAF 适合 Azure/.NET 为底座、审计治理是真实需求的企业；PydanticAI 适合已重度使用类型化 Python（FastAPI 技术栈）的团队。反例：MAF 对轻量原型偏重（同一基准里首个 Agent 耗时 26 分钟、84 行代码，是最慢档位），且没有 TypeScript 支持；PydanticAI 只做 Python，不提供对话平台级的运营层。

四大流派没有高下，只有对位：模型能力越强，AI 原生派的天花板越高；状态越复杂，图调度越值钱；合规越硬，企业专精派越划算；复杂度越低，自研越划算——反之亦然。

三、选型决策矩阵

把四个流派放回业务语境，选型可以收敛为一张矩阵：先识别需求的主矛盾（速度、生态、可控性还是稳定性），再让框架的核心考量与之对齐。错配的典型症状不会立刻出现，往往在项目推进六周后才以"框架最不擅长的事恰好是你最需要的事"的形式爆发。

生产案例 · 迁移的代价与收益：AppFolio 的物业助手 Realm-X 从 LangChain 迁移到 LangGraph 后，响应准确率提升 2 倍，特定功能表现从 40% 提升到 80%，每位物业经理每周节省 10 小时以上。迁移不是纯粹的损耗——当原有抽象开始泄漏，果断重写状态层反而是止损。

  • 先写清业务问题的形状（状态复杂度、审批需求、语言栈），再打开框架文档
  • 工具定义尽量走 MCP，让工具资产与框架解耦
  • 给 LangGraph 类图框架预留"状态税"预算：延迟、存储、可观测性成本
  • 用 1.0 / GA 版本作为生产基线，读一遍官方弃用政策
  • 不要因为某个框架 Star 最多就直接采用——熟悉度不等于适配度
  • 不要给单轮工具调用套上状态图和检查点，过度设计与欠设计同样昂贵
  • 不要在原型阶段忽略锁定分析，模型绑定与编排绑定的退出成本完全不同
  • 不要假设"以后随时能换框架"，30+ 工具的迁移是重写而非搬家

锁定发生在抽象层而不是协议层：MCP 已经让工具可以跟着业务走，但状态管理、编排逻辑和可观测性资产，仍然是每次迁移中最难搬走的部分。

四、MCP 协议：框架互联新标准

MCP（Model Context Protocol，模型上下文协议）由 Anthropic 于 2024 年 11 月发起并开源，解决的是一个经典的工程问题：M 个 AI 应用要接 N 个外部系统，如果两两定制集成，总工作量是 M×N；引入一层统一协议后降为 M+N——每个框架实现一次客户端，每个系统实现一次服务端，任意组合即刻打通。这正是"一次接入、多框架复用"的数学基础。

架构上，MCP 是 Host–Client–Server 三层模型：Host 是 AI 应用（如 Claude Code），它为每个 Server 创建一个 Client 连接；Server 则是能力提供方，通过 JSON-RPC 2.0（一种轻量级远程过程调用消息格式）暴露三类原语：

原语角色类比典型例子
Tools（工具）模型可调用的函数，可产生副作用POST 接口执行 SQL、创建 GitHub Issue、发邮件
Resources（资源）供模型读取的上下文数据GET 接口文件内容、数据库记录、设计稿元数据
Prompts（提示模板）预定义的交互模板，引导模型按既定工作流输出参数化模板代码审查模板、SQL 生成模板

传输层提供两种形态，覆盖本地与远程两类部署：

传输方式通信机制优势典型场景
stdio本地进程间标准输入输出延迟极低、无网络暴露面数据库、命令行工具等数据敏感的本地能力
Streamable HTTPHTTP + SSE 服务端推送防火墙穿透好、连接稳定、可水平扩展SaaS 集成、远程云服务、多租户网关

2026 年 7 月 28 日发布的规范版本是一次关键升级：协议核心从"有状态双向会话"转向无状态请求/响应——废弃了 initialize 握手与会话头，每个请求自描述协议版本与客户端能力，可以落在轮询负载均衡后的任意实例上；方法与工具名通过 HTTP 头传递，网关可以直接基于头部做路由和鉴权；工具列表结果可缓存，并承诺至少 12 个月的弃用窗口。这些改动直指生产运维的痛点：扩缩容、网关治理、升级规划从此有了协议级支撑。

框架层（内嵌 MCP Client） 能力层（MCP Server） ┌─────────────────────┐ ┌─────────────────────┐ │ Claude Code │──┐ ┌──│ PostgreSQL 数据库 │ ├─────────────────────┤ │ │ ├─────────────────────┤ │ LangGraph 应用 │──┤ ├──│ GitHub 代码仓库 │ ├─────────────────────┤ │ JSON-RPC │ ├─────────────────────┤ │ MAF（C# / Python） │──┤ stdio / ├──│ 内部 OA / 审批 API │ ├─────────────────────┤ │ HTTP │ ├─────────────────────┤ │ PydanticAI 应用 │──┘ └──│ 监控系统 / 工单系统 │ └─────────────────────┘ └─────────────────────┘ M 个框架 × N 个系统 ＝ 只需 M＋N 个连接 数据库 / GitHub / 内部 API：写一次 Server，处处可用

落到机制细节：假设公司有一个内部审批 API。过去它需要为 Claude Code 写一套插件、为 LangGraph 写一套 Tool 类、为 MAF 再写一套连接器；现在只需把它封装成一个 MCP Server（声明好工具名、输入 Schema、鉴权方式），所有支持 MCP 的框架即刻获得该能力，且工具定义独立于任何 Agent 逻辑单独演进。到 2026 年，七大主流框架已全部原生支持 MCP，MAF 甚至提供了 stdio / Streamable HTTP / WebSocket 三种传输的工具类，并把"工具调用需人工批准"做成了一等消息类型。

生态规模 · 数字会说话：MCP 的一级 SDK 月下载量已接近 5 亿次，TypeScript 与 Python SDK 均突破 10 亿次累计下载；2025 年 12 月，Anthropic 将 MCP 移交 Linux 基金会旗下的 Agentic AI 基金会托管，确立厂商中立地位。一个协议能否成为标准，看的是治理归属与采用曲线——这两项 MCP 都已越线。

MCP 是 Agent 世界的 USB-C 接口：它把"能力提供方"与"能力消费方"彻底解耦，让换框架从一场重写工程降级为一次接入配置变更。

五、趋势与架构师能力

站在 2026 年中期回望，三条趋势正在重塑选型的前提条件：

先看生态时间线——过去 12 个月发生的事情，密度超过此前三年：

时间生态事件对选型的含义
2025 年 10 月LangGraph 1.0 GA，LangChain 弃用 AgentExecutor图调度成为长程 Agent 的标准形态
2025 年 12 月MCP 移交 Linux 基金会 Agentic AI 基金会协议中立化，可放心作为长期资产
2026 年 4 月 3 日微软 MAF 1.0 发布，合并 Semantic Kernel 与 AutoGen巨头整合：评估项目存续意图比评估特性更重要
2026 年 6 月 23 日PydanticAI V2 稳定，转向 harness-first 设计强类型路线进入成熟期
2026 年 7 月 28 日MCP 新规范发布，无状态协议核心协议层扫清生产运维障碍
  • 协议层收敛：工具接入收敛到 MCP，跨框架交接收敛到 A2A。底层线格式的统一意味着"选框架"不再等于"赌上全部资产"，但编排与状态层的锁定依然真实存在。
  • 框架整合加速：微软把 Semantic Kernel 与 AutoGen 合并为 MAF，LangChain 官方弃用 AgentExecutor、把全部 Agent 工作流推向 LangGraph。"框架更替本身就是这个品类的常态"——选型时要像评估产品一样评估项目的存续意图。
  • 从"每轮一个工具调用"到"让模型写代码"：MAF 称之为 CodeAct、PydanticAI 称之为 CodeMode，多家框架不约而同地收敛到同一方向——让模型生成一段代码一次性编排多个工具，而不是逐轮往返。这会改变工具粒度的设计方式。

与此对应，架构师的核心能力正在发生一次明显的转向：从"技术堆砌"——知道多少框架、能罗列多少特性——转向"业务痛点的精准匹配"——能把一个模糊的业务诉求翻译成状态复杂度、审批需求、语言栈约束、总拥有成本这组硬参数，并解释"为什么这个框架的天花板恰好匹配业务的天花板"。

正在贬值的做法正在升值的能力
按 GitHub Star 数和演示视频选框架先给业务问题画像：状态、审批、语言栈、合规
堆砌组件：生态全家桶一次全上断舍离：只引入当前抽象层必需的部分
只算开发成本算总账：状态税、可观测性、迁移与锁定成本
把工具写死在框架私有接口里用 MCP 沉淀可跨框架复用的工具资产
追最新版本与新特性评估弃用政策、长期支持与厂商整合意图

这套能力的落脚点是一份可执行的选型纪律：任何框架决策都要能回答三个问题——这个系统最坏情况下的状态在哪里（能否恢复）？六个月后业务翻倍时哪个组件先撑不住（天花板在哪）？如果明年必须换掉它，哪些资产能带走（退出成本多大）？答得出这三问，选型就从跟风变成了工程判断。

选型判据 ＝ 业务形状（状态复杂度 ＋ 审批需求 ＋ 语言栈） ÷ 退出成本

架构师的价值不在于选中最热门的框架，而在于能说清楚"为什么这个框架的天花板恰好是我们业务的天花板"——精准匹配永远优于技术堆砌。

Q&A

Claude Code 和 LangGraph 经常被放在一起比较，这个对比成立吗？
严格来说不成立，因为两者运行在技术栈的不同层。Claude Code 是开发时工具，帮工程师写代码、调试、跑命令；LangGraph 是运行时框架，生产环境的 Agent 跑在它上面，由它管理状态、控制流和节点路由。真实的生产模式是二者协作：用 Claude Code 来编写和调试 LangGraph 应用的节点逻辑、状态 Schema 与条件边，然后把 LangGraph 应用部署到生产。把它们当作二选一的竞品，混淆了"开发加速器"与"执行底座"两种完全不同的角色。
LangGraph 的"状态税"具体指什么？如何判断这笔钱该不该花？
状态税指图调度与检查点机制带来的额外开销：基准测试显示同样的任务 LangGraph 平均延迟 10155ms，比链式方案慢约 68%，检查点还会造成单步约 1.5MB 的写放大、最高 15 倍的存储膨胀。判断标准是任务形状：当 Agent 步骤数大于等于 5，且需要断点恢复、人工审批或多 Agent 协作时，链式抽象必然泄漏，这笔状态税买到了崩溃恢复与审计能力，物有所值；反之，一次性的检索问答或单轮工具调用引入图抽象就是纯粹的过度设计。
已有成熟框架，为什么还有团队选自研极简路线？边界在哪里？
自研的核心动机是透明与零锁定：While 循环加 JSON 校验加 Function Calling 的三要素内核只有数百行，每一行行为都可审查，模型、编排、状态全部握在自己手里，适合推理逻辑本身就是竞争壁垒的产品。但边界非常明确：vanilla 路线从零到生产通常要 6–12 个月和 15–50 万美元级投入，且护栏、可观测性、持久化全要自建。如果需求能在 6 个月内用框架交付，或做的是客服、数据分析等通用场景，自研就是在用最贵的成本买最慢的进度。
PydanticAI 的强类型是如何降低生产事故的？
PydanticAI 用 Pydantic 模型约束 Agent 的输入输出和工具参数，任何不符合 Schema 的内容都会在边界处立刻抛出校验失败，而不是带着脏数据继续往下游流动。一份对比基准给出了量化证据：在同等生产负载下，PydanticAI 的类型校验层拦截了 23 个会直接漏到用户侧的 Bug，对照框架全部放过。它的工程含义是把"静默的错误行为"转换成"显式的、可定位的校验异常"，让错误在离根因最近的地方暴露，大幅降低生产事故的排查成本。
MCP 是通过什么机制实现"一次接入、多框架复用"的？
MCP 在 M 个 AI 应用与 N 个外部系统之间插入一层标准协议，把 M×N 的两两定制集成降为 M+N：每个框架实现一次 MCP 客户端，每个系统实现一次 MCP 服务器，任意组合自动打通。服务器通过 JSON-RPC 2.0 暴露工具、资源、提示三类原语，传输可选本地 stdio 或远程 Streamable HTTP。因此一个内部 API 只要封装成 MCP Server，Claude Code、LangGraph、MAF、PydanticAI 即刻都能消费，且工具定义独立于 Agent 逻辑单独演进。2026-07-28 规范进一步转向无状态核心，让 MCP Server 可以放在普通负载均衡之后水平扩展。
评估框架锁定风险时，哪些资产最难迁移？
锁定强度在资产类型上差异巨大。工具层如果按 MCP 的 JSON Schema 定义，就是可移植资产；如果写成框架私有子类，迁移时全部报废，且 30 个以上工具的重写工作量常被低估 3 倍。最难迁移的是编排与状态层：状态 Schema、检查点存储格式、图结构定义与厂商运行时深度耦合，跨框架迁移（如 CrewAI 到 PydanticAI）意味着重写每个 Agent 定义和工具装饰器。记忆层则是隐蔽风险点——如果导出的记忆需要原厂 SDK 才能反序列化，它实际上属于厂商而不属于你。
有合规审计需求的企业应该怎么选？
合规场景的第一要求是决策路径可审查、可复现，这直接排除了黑盒程度高的方案。微软生态企业首选 MAF：C#/Python 双语言对等、内建 OpenTelemetry GenAI 追踪、DAG 工作流支持时间旅行回放，并与 Purview 等治理组件原生整合。非微软生态可选 LangGraph 加 LangSmith：每个节点的执行与状态快照全链路可查，Klarna、Rexera 等案例验证了它在受监管流程中的可控性。同时要把人工审批闸门作为硬性验收项：框架必须原生支持"暂停—挂起—人工确认—精确恢复"，而不是靠业务代码硬凑。
如果选型时只能问三个问题，应该问什么？
第一问状态：系统最坏情况下的运行状态在哪里，崩溃后能否从断点恢复——这决定是否需要图调度与检查点。第二问天花板：六个月后业务量翻倍时哪个组件先撑不住——这决定该为哪些维度（吞吐、延迟、状态规模）预留余量，以及是否值得付状态税。第三问退出：如果明年必须换掉这个框架，哪些资产能带走——工具是否 MCP 化、记忆是否可读文本、编排逻辑的耦合深度。三问答完，速度、控制、生态、合规四个维度自然各就各位，选型从跟风变成可追溯的工程决策。
