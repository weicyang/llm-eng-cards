A11 · AI Agent 生态概念全串联

推理服务 → Memory → RAG → MCP → Skills → AI Agent — 一个问题的连锁解决方案

AI 生态里令人眼花缭乱的概念，其实是同一条问题链上的六块补丁：推理服务让大脑开机，Memory 治健忘，RAG 补新知，MCP 装手脚，Skills 教方法，Agent 是拼装完成的最终形态。每解决一个问题就暴露下一个问题，下一个问题的解药就是下一个概念。

一、一条问题链串起所有概念

理解 AI 生态最高效的方式，不是逐个死记概念，而是抓住这条"问题 → 解决 → 新问题"的连锁反应。整条链从最底层的推理服务（把训练好的模型文件加载进内存、对外暴露 HTTP 接口接收请求并返回推理结果的服务，是所有 AI 应用的运行基础）开始。

记忆口诀：大脑（推理服务）+ 记忆（Memory）+ 参考书（RAG）+ 手和工具（MCP）+ 操作手册（Skills）= 智能体（Agent）。六个概念不是并列关系，而是层层叠加的依赖关系。

二、推理服务与 Memory — 大脑开机与记忆

2.1 推理服务：一切的起点

大模型的本质是躺在磁盘上的超大参数文件，它自己不会动。推理服务负责把它加载到内存（通常是 GPU 显存），对外暴露 HTTP 接口：接收请求、做推理、返回结果。再配上一个前端聊天框，就成了我们日常用的聊天 AI。

2.2 Memory：用"重发聊天记录"模拟记忆

推理服务是无状态的 HTTP 服务——每个请求独立处理，处理完就忘。你上一句刚说完"帮我改第三段"，下一个请求里它完全不知道"第三段"是什么。Memory（记忆机制，负责管理哪些历史内容该被带入当前上下文，让无状态的模型表现出"记得"的能力）的解法很朴素：每次请求时，把历史对话拼到上下文里一起发出去。

但上下文窗口有限，不可能把所有历史全发出去，所以要分两层管理：

类型策略示例
短期记忆当前会话最近几轮完整保存"你刚才说要改第三段"
长期记忆历史对话提取关键信息压缩成摘要"用户偏好简洁风格"

短期记忆保证"接得上话"，长期记忆保证"认得这个人"。两者的共同约束是 Token 预算：完整保留贵，压缩摘要会丢细节，工程上就是在二者之间找平衡。

模型根本没有记忆——所谓"它记得我"，只是客户端每次都把聊天记录重新发了一遍。Memory 的全部工作，就是决定这份"重发清单"里放什么、不放什么。

三、RAG — 给大脑配一本参考书

记忆问题解决了，下一个问题随之浮现：模型的知识停在训练截止日期那天。今天的新闻它不知道，公司内部的文档它更不知道。硬等重新训练不现实，RAG（Retrieval-Augmented Generation，检索增强生成——用户提问时先从外部知识库检索相关内容，再把检索结果和问题一起喂给模型生成答案）给出了一个轻巧的答案：不重训模型，给它配一本随时可查的参考书。

RAG 的关键技术难点在检索。传统数据库只能做字面匹配——搜"韩老魔"永远找不到写着"厉飞羽"的段落，尽管两者指向同一个角色。解法是向量数据库（如 Milvus 等，把文本转成高维向量存储、用向量间距离衡量语义相似度的数据库）：先用 Embedding 模型把文本转成语义向量，语义相近的文本在向量空间中距离就近，检索就变成了"按意思找"而不是"按字面找"。

检索方式原理"韩老魔"能否命中"厉飞羽"
关键词匹配字面精确 / 模糊查询不能
向量检索语义向量距离能
混合检索（BM25 + 向量 + 重排）字面与语义互补，再加一层排序能，且更稳
案例 · Anthropic Contextual Retrieval 的检索优化： 背景：企业知识库问答场景中，纯向量检索经常漏掉"意思相近、说法完全不同"的段落，检索失败直接导致模型编造答案。 问题：Anthropic 在公开实验中发现，单纯向量检索的 Top-20 召回存在明显的失败率，专有名词、缩写类查询尤其容易漏检。 方案：Contextual Retrieval——给每个文本切片先补一段"它在全文中位置与语境"的说明再做向量化，同时与 BM25 关键词检索混合，最后叠加一层重排模型。 效果：官方公布的数据中，Top-20 检索失败率下降 49%，叠加重排后累计下降 67%。

RAG 不是让模型把知识背下来，而是让它开卷考试——答案可以现查，但查什么、怎么查，决定了它答得准不准。

四、MCP — 给缸中之脑装上手脚

有了记忆的模型依然只是个"缸中大脑"：能思考、能对话，但不能操作任何外部事物——不能发消息、不能查数据库、不能改代码仓库。MCP（Model Context Protocol，Anthropic 于 2024 年 11 月发布的开放协议，标准化了大模型调用外部工具的消息格式）的解法是：在对话中约定一套 JSON 消息格式，模型输出结构化的调用请求，外部程序解析后真正执行工具，再把结果返回给模型。

整套协议由三个角色构成一条完整的调用链：

角色作用示例
MCP Host宿主程序，解析模型输出的 JSON、调度工具Cursor、Claude Code
MCP Client本地通信组件，接收并转发调用请求Cursor 内置的 Client
MCP Server真正执行操作的一端，封装具体 APIGitHub MCP Server
用户："把这周的周报发到群里" ↓ ┌─ MCP Host（Cursor / Claude Code）────────────┐ │ 模型决策后输出结构化请求： │ │ {"tool":"send_message", "args":{...}} │ └──────────────┬───────────────────────────────┘ ↓ ┌─ MCP Client（本地通信组件）──────────────────┐ │ 解析请求 → 通过 STDIO / HTTP 转发 │ └──────────────┬───────────────────────────────┘ ↓ ┌─ MCP Server（飞书 / GitHub 等）──────────────┐ │ 真正调用 API 执行 → 把结果原路返回 │ └──────────────────────────────────────────────┘

这套分工里有个重要的安全设计：模型只负责"决定调用哪个工具、传什么参数"，从不亲手执行，真正的执行权始终握在 Host 手里——Host 可以在执行前向用户展示计划并请求确认。

MCP 是"AI 界的 USB"：协议统一之前，每个工具都要为每个模型单独适配；协议统一之后，任何工具在任何 Host 上即插即用。

五、Skills 与 AI Agent — 从工具到方法论，再到完整的人

MCP 给了模型工具，但新的问题又出现了：有工具不等于会用。就像给一个大学生一堆钳子扳手，他不一定修得好车——缺的不是工具，是经验和流程。Skills（技能，写明了"什么场景用什么工具、先做什么后做什么"的结构化操作手册，本质是动态加载的系统提示词）就是这份经验：遇到什么场景用什么工具、按什么顺序用、有什么注意事项，全部写成结构化指南。

维度MCPSkills
回答的问题能不能调用工具该怎么组合使用工具
本质通信协议结构化系统提示词
形态Server + Tool 列表文件夹（指令 + 资料 + 脚本）
类比手和扳手维修手册

到这里，五块积木齐了。把它们拼装起来——大模型负责思考规划、Memory 负责记住历史、RAG 负责获取知识、MCP 负责操作工具、Skills 负责操作流程——就得到了最终形态 AI Agent（智能体，能够围绕一个目标自主规划、调用资源、闭环执行直至完成目标的智能系统）。通过提示词设定不同角色，它可以是客服、程序员、律师，Claude 等厂商的"操作电脑"类产品本质上都是 Agent。

遇到一个 AI 需求，先问自己缺哪块积木： 模型跑不起来？ → 推理服务 聊着聊着就忘？ → Memory 答不出新知识/私域知识？ → RAG 需要查系统、改数据？ → MCP 步骤多、模型总是乱序？ → Skills 以上全要、还要自主闭环？ → AI Agent ┌──────────────── AI Agent ────────────────┐ │ Skills（方法论） │ │ MCP（工具） RAG（知识） Memory（记忆） │ │ 推理服务（大脑） │ └──────────────────────────────────────────┘

Agent 不是一项新技术，而是五块积木的拼装成品。缺哪块补哪块，比"从零造一个 Agent"务实得多。

六、落地实践 — 概念组合拳怎么打

案例 · MCP 协议如何终结工具调用的碎片化： 背景：2024 年 11 月 Anthropic 发布 MCP 之前，各家模型的工具调用格式互不兼容，开发者为每个客户端都要重写一遍适配代码。 问题：生态严重碎片化——一个"查数据库"的能力，要在 N 个 AI 应用里重复实现 N 次，维护成本随生态规模相乘式增长。 方案：MCP 统一了 Host-Client-Server 三方协议，模型输出标准 JSON 请求，Server 一次实现、处处可用。 效果：发布后一年多，OpenAI、Google 等主流厂商相继宣布支持，社区 MCP Server 数量增长到数千个，已成为事实上的 AI 工具调用标准。

6.1 落地顺序：按缺口补积木

  • 知识问题优先用 RAG，而不是微调模型

  • 反复出现的多步流程沉淀成 Skills

  • 不要把整个知识库塞进提示词硬扛

  • 不要跳过 Memory 直接做多轮业务

评估一个 AI 需求的正确姿势：它卡在"不知道"（→RAG）、"不记得"（→Memory）、"做不到"（→MCP）还是"做不对"（→Skills）？对症下药，药到病除。

Q&A

Memory 在 AI 系统中是什么？它解决了什么问题？
Memory 是管理上下文的机制，解决的是推理服务"无状态"的问题。推理服务本质是 HTTP 服务，每个请求独立处理、处理完就忘，并不保存任何历史。Memory 的做法是每次请求时把历史对话拼入上下文，用"重发记录"的方式模拟出记忆。它分两类：短期记忆完整保留当前会话最近几轮，保证接得上话；长期记忆把更早的历史提取关键信息压缩成摘要，保证认得用户。核心挑战是上下文窗口有限——不能把所有历史都发出去，必须策略性地取舍和压缩。
RAG 为什么需要向量数据库而不是传统数据库？
传统数据库只能做字面匹配（精确或模糊查询），但语义相近的文本字面可能完全不同。例如"韩老魔"和"厉飞羽"指同一个人，字面却毫无交集，关键词检索永远匹配不上。向量数据库用 Embedding 模型把文本转成高维向量，用余弦相似度等距离度量衡量语义相似性——语义相近的文本在向量空间中距离更近。这让 RAG 能实现"按意思检索"而非"按字面匹配"，大幅提升召回率。实践中更稳的做法是混合检索：BM25 管字面、向量管语义，再叠一层重排，Anthropic 的公开数据显示这能把 Top-20 检索失败率降低近七成。
MCP 协议中 Host、Client、Server 三者的关系是什么？
三者构成 MCP 协议的完整调用链。MCP Host（如 Cursor、Claude Code）是宿主程序，负责把模型输出的 JSON 调用请求解析出来并调度执行；MCP Client 是本地通信组件，接收 Host 的调用请求，通过 STDIO 或 HTTP 转发出去；MCP Server 是真正干活的一端，封装具体系统的 API（如 GitHub、飞书），执行操作后把结果原路返回。一个直观的类比：Host 是大脑做决策，Client 是手臂传导指令，Server 是手在具体环境里操作。值得注意的安全设计是：模型只决定"调什么、传什么参数"，从不亲手执行，执行权始终在 Host 手里。
为什么说 Skills 是 MCP 的"上层建筑"？
因为 MCP 只解决了"能不能调用工具"的问题——给了模型手和工具，但没教它怎么用。就像给了一堆钳子扳手，不一定能修好车，缺的是经验和流程。Skills 在 MCP 之上提供了这一层：规定什么场景用什么工具、先做什么后做什么、有什么注意事项。两者的分工很清晰：MCP 是工具能力层，Skills 是操作经验层；Skills 可以编排 MCP 工具，也可以编排本地脚本。一个项目里 MCP Server 提供"查数据库""发通知"等原子能力，Skills 负责把它们串成"先查库存、再发预警、最后写报告"的完整流程。
AI Agent 的完整组成是什么？每个部分各负责什么？
AI Agent 由五个部分拼装而成。推理服务是运行基础，把模型加载起来对外提供推理能力；Memory 分短期和长期两层，让模型能接上历史对话；RAG 检索外部知识库，补充训练截止后的新知识和私域知识；MCP 提供标准化的工具调用协议，让模型能操作外部世界；Skills 是操作经验和流程指南，指导模型如何组合使用工具。五者缺一不可：没有 Memory 就健忘，没有 RAG 就知识过期，没有 MCP 就只会说不会做，没有 Skills 就做一步乱一步。通过提示词设定角色，同一个 Agent 底座可以变成客服、程序员或律师，各家"操作电脑"类产品的本质都是 Agent。
RAG 和 Memory 都是"给模型喂历史内容"，区别在哪？
两者确实都在往上下文里塞模型原本不知道的内容，但塞的东西性质完全不同。Memory 管的是对话过程——你说过什么、我们聊到哪了，内容随会话产生、随会话消亡，典型形态是聊天记录和摘要。RAG 管的是世界知识——文档、新闻、公司制度，内容独立于任何一次对话存在，典型形态是向量知识库。触发方式也不同：Memory 是每轮自动携带，RAG 是按问题检索召回。一个容易混淆的场景是"用户偏好"：它来自历史对话（Memory 的长期记忆），但如果沉淀成了用户画像文档供检索，就又带上了 RAG 的味道——两者在工程上常常配合使用。
微调和 RAG 都能补充知识，该怎么选？
两者的成本结构和适用场景差别很大。RAG 把知识放在外部库里，更新只需改文档，检索结果还能附来源便于核查，适合更新频繁、需要溯源的知识（新闻、产品手册、公司制度）；微调把知识烤进模型参数，更新要重新训练、成本高、周期长，且难以精确溯源，适合改变模型的"行为方式"而非"知识内容"（语气风格、输出格式、领域推理习惯）。一个实用的判断标准：如果知识会过期、需要审计、或者经常变动，选 RAG；如果要改的是模型说话做事的方式，且相对稳定，才考虑微调。多数生产系统的选择是 RAG 打底、微调做行为层增强，两者并不互斥。
