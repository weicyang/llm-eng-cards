EV06 · Agent 性能量化体系

Performance Quantification — 三层黄金指标 + 自动化评测流水线 + 工程兜底方案

核心直觉：Agent 不是静态脚本，而是会自主规划、选工具、处理反馈的智能体。只看结果无法定位问题根因（模型 / 工具 / 环境），过程量化永远比只看结果更重要。

一、为什么只看结果不行？

Agent 与传统脚本的本质区别：

维度传统脚本AI Agent
执行路径固定流程自主规划、动态决策
工具选择硬编码模型自行选择工具
环境反馈预设处理自主理解和应对
可复现性高低（模型非确定性）

只看结果的问题：当线上出问题时，无法定位是模型的问题、工具的问题还是环境的问题，更谈不上有效优化。

二、三层黄金指标体系

L1 · 业务结果层

L1 回答的是"任务做了没"这个问题。就像餐厅出菜后检查：菜对不对、味道对不对、价格算对了没。Agent 跑完一轮后，用自动化脚本直接验证数据库里的结果。

  • 自动化校验脚本：Agent 跑完后，Python 脚本直接连数据库验证结果（订单状态、乘客信息、价格一致性）。为什么不用人工验证？因为 Agent 评测需要跑数百次，人工验证成本高且容易出错。
  • 焊进 CI/CD 流水线（Jenkins / GitHub Actions），每次改代码自动跑全量测试。CI/CD 就是"代码改了自动测，测了自动上线"的工程流水线。
  • 成功率设为质量门禁——就像考试的及格线，低于阈值（如 95%）直接阻止上线，避免有缺陷的版本流入生产环境

L2 · 执行轨迹层

L2 回答的是"怎么做的"这个问题。就像篮球录像回放：不只看比分，而是看每个回合——传球准不准、跑了几步、失误后能不能补回来。Agent 的执行轨迹（Trace）记录了它每一步决策，是定位问题根因的关键数据。

指标含义告警条件
工具调用准确率是否选对工具、传对参数低于阈值
轨迹效率完成任务所需步数超过步数阈值
自我纠错率遇到报错后能否自主修复低于阈值

L3 · 系统成本层

L3 回答的是"花了多少钱"这个问题。就像打车看账单：等了多久（延迟）、走了多远（Token 消耗）、总共花了多少（任务成本）。Agent 每次调用 LLM 都在烧钱，不设红线的话，一个低效 Agent 可能一个任务花 10 块钱。

  • 端到端延迟：用 Prometheus（时序数据库，专门存储和查询监控指标）+ Grafana（可视化仪表盘，把数字变成图表）埋点监控，超时自动告警
  • Token 消耗：取模型 API 返回的 usage 字段，精确到单次任务平均成本。GPT-4o 的 input token 约 $2.5/1M，output 约 $10/1M，一次复杂任务可能消耗几千 token
  • 每个任务设定成本红线（如订票任务 ≤ ¥0.5），超标系统直接告警且不让上线

三层指标的采集来源与失效表现

三层不只是"看什么"不同，采集位置、采样频率和失效时的表现也完全不同。下表用于排期时判断每层该由谁负责、缺了会漏掉什么。

层级采集位置采样方式缺失时的典型症状负责角色
L1 业务结果业务数据库 / 下游系统状态每次评测跑批全量校验只能靠用户投诉发现问题，且说不清影响了多少单业务 + 测试
L2 执行轨迹Agent 运行时的 Trace 埋点线上全量采集，评测时按用例回放知道失败了但定位不到是哪一步，只能靠人读日志Agent 工程
L3 系统成本模型 API 的 usage 字段 + 网关耗时线上全量，按任务维度聚合账单月底才暴雷，且无法归因到具体任务类型平台 / SRE

三、自动化评测：硬断言 + 软裁判

┌──────────────────────────────────────────────────┐ │ 自动化评测流水线 │ ├──────────────────────────────────────────────────┤ │ │ │ 确定性任务 非确定性任务 │ │ ────────── ────────── │ │ SQL / API / 查数据 写邮件 / 报告 / 客服 │ │ ↓ ↓ │ │ 硬断言（单元测试） 软裁判（LLM-as-Judge） │ │ 输入→Agent→输出→比对 GPT-4o / Claude 3.5 │ │ pass / fail 准确性/逻辑性/合规性 │ │ 零人工干预 ↓ │ │ 人工抽检（每两周50条） │ │ 裁判准确率 ≥ 90% │ │ │ └──────────────────────────────────────────────────┘

确定性任务 → 硬断言

硬断言就是"对答案"——有标准答案的题目，直接比对就行。就像数学考试：答案对不对，一目了然，不需要老师主观判断。

  • 有标准答案的任务（写 SQL、调 API、查数据）
  • 用单元测试方式：输入 → Agent → 输出 → 自动比对
  • 结果绝对客观，零人工干预

非确定性任务 → 软裁判（LLM-as-Judge）

LLM-as-Judge 的本质是"用 AI 评 AI"——当一个更强的模型（如 GPT-4o）阅读 Agent 的输出后，从准确性、逻辑性、合规性三个维度打分。就像让资深编辑审稿：他不需要标准答案，但能凭专业判断给出评分。

  • 没有标准答案的任务（写邮件、报告、客服答疑）
  • 用裁判模型（GPT-4o / Claude 3.5）从三个维度打分：准确性（信息对不对）、逻辑性（推理通不通）、合规性（格式规不规范）
  • 每两周抽 50 条人工抽检，用历史数据对齐 Prompt，裁判准确率稳定在 90%+。为什么不 100%？因为裁判模型也会"幻觉"，需要人工兜底

两种方式的选择对照

实际项目里大多数任务不是纯确定性也不是纯开放，判断该走哪条路要看"能不能写出机器可判定的通过条件"。

对比项硬断言软裁判（LLM-as-Judge）
适用前提存在唯一或可枚举的正确结果结果开放，只能判断"好不好"
单次评测成本近似为零，只有脚本执行开销每条用例额外一次模型调用
结果稳定性完全确定，可重复有波动，需固定裁判 Prompt 与温度
失效方式断言写得太松，错的也能过裁判被冗长漂亮的输出误导，给高分
维护负担业务规则变了要同步改断言要定期人工抽检校准，防止裁判漂移
推荐用法能写断言的一律写，哪怕只覆盖部分字段只用于剩下那部分无法断言的维度

务实的做法是两者叠加而不是二选一：先用硬断言卡住所有可判定的字段（订单号存在、金额匹配、状态正确），剩余的表达质量再交给裁判打分。这样既压低了裁判调用量，也避免了"全靠裁判"带来的评测不稳定。

关键洞察：级联错误是 Agent 评测中最难定位的问题。Mock 隔离测试的本质是控制变量法——固定外部输出，让 Planner 的决策能力成为唯一变量，问题归因一抓一个准。

示例场景：一个内部工单处理 Agent，评测集 200 条用例，成功率长期在 76% 上下波动，同一份代码连跑三次结果能差 5 个百分点。问题：团队一直在调 Prompt，两周内改了 11 版，成功率始终没突破 80%，而且每次都说不清是这版 Prompt 真的更好还是运气好。补上 Trace 分析后才发现问题根本不在 Prompt：失败用例里有 41% 的第一次工具调用返回的是超时或限流错误，Agent 重试策略又不统一，有的重试有的直接放弃；另有 18% 是因为评测环境的测试数据每天被其他任务改动，同一条用例昨天的正确答案今天已经不对了。真正归因到规划能力的只占失败的三成左右。方案：三件事同时做——把外部依赖全部换成用真实响应录制的 Mock，只在专门的集成用例里走真实调用；评测环境用容器每次跑批前重建，测试数据从固定快照恢复；模型温度固定为 0 并固定随机种子。效果：同一份代码三次跑批的成功率波动从 5 个百分点收敛到 0.5 个百分点以内，评测结果第一次可以用来判断改动好坏；在稳定的基线上再调 Prompt，两周内成功率从 76% 提到 89%，而这次每一次提升都能对应到具体的失败类别。

五、Do / Don't

  • 三层指标全覆盖（结果/过程/成本）
  • 自动化校验焊进 CI/CD
  • 成功率设为质量门禁
  • 确定性任务用硬断言
  • Mock 隔离归因
  • 多路裁判防幻觉
  • Docker 保证可复现
  • 只看任务成功率
  • 人工手动算成功率
  • 不设成本红线
  • 所有任务都用裁判模型
  • 单模型评测
  • 忽略裁判幻觉
  • 环境不固定就跑评测

六、核心回答框架

量化 Agent 性能三板斧：
  • 指标体系：结果用自动化脚本校验，过程用全链路追踪，成本用告警红线控制
  • 评测流水线：确定性任务用硬断言，非确定性任务用多模型对齐
  • 工程兜底：Mock 隔离归因，Docker 保证一致，多路裁判防幻觉

Q&A

为什么只看任务成功率不够？

Agent 是自主规划、选工具、处理反馈的智能体，不是静态脚本。只看最终结果就像只看比赛比分不分析过程，无法定位是模型、工具还是环境的问题。必须拆解执行轨迹，关注工具调用准确率、轨迹效率和自我纠错率。

三层黄金指标各解决什么问题？

L1 业务结果层：任务是否完成（老板关心），用自动化脚本校验。
L2 执行轨迹层：Agent 怎么思考和执行的（工程师关心），用 LangSmith/LangFuse 全链路追踪。
L3 系统成本层：花多少钱多少时间（财务关心），用 Prometheus + Grafana 监控延迟和 Token 消耗。

确定性任务和非确定性任务怎么分别评测？

确定性任务（SQL/API/查数据）：硬断言，用单元测试方式自动比对输入输出，零人工干预。
非确定性任务（写邮件/报告/客服）：软裁判，用 GPT-4o/Claude 当裁判模型从准确性、逻辑性、合规性三维度打分，每两周人工抽检 50 条对齐裁判准确率到 90%+。

Agent 评测最大的三个坑是什么？怎么解决？

① 级联错误：第一步错全链路错 → Mock 隔离测试，固定外部返回值，单独测 Planner 决策能力。
② 非确定性：同输入不同输出 → Docker 沙盒 + temperature=0 + 固定随机种子，保证环境完全一致。
③ 裁判幻觉：Agent 骗裁判 / 裁判胡说 → 2~3 个模型交叉打分 + 可疑规则自动推人工审核。

如何把评测融入 CI/CD？

① 写自动化校验脚本，Agent 跑完后自动验证数据库结果。② 将脚本焊进 Jenkins/GitHub Actions，每次改代码自动跑全量测试。③ 设置成功率质量门禁，不达标直接阻止上线。④ Token 消耗设红线，超标系统直接告警且不让上线。

评测集应该多大？用例从哪里来？

先说结论：起步用 30 到 50 条，稳定后维持在 200 到 300 条，超过这个量级维护成本会迅速超过收益。规模的下限由统计意义决定——如果评测集只有 20 条，一条用例的通过与否就是 5 个百分点，你根本分不清改动带来的提升和噪声。上限则由维护成本决定，每条用例都需要一份稳定的输入、一份可判定的期望结果，业务规则变了还要同步更新。

用例来源建议按三份构成。第一份是真实失败样本，也是最重要的一份：把线上出过问题的会话原样固化成用例，这批用例天然覆盖了真实的失败模式，而且修好之后就是防回归的护栏，只进不出。第二份是核心路径的正例，覆盖业务上跑量最大的那几条链路，防止修 bug 时把主流程改坏。第三份是边界与异常，包括空输入、超长输入、工具超时、权限不足这类场景，这部分往往需要人工构造，但它决定了 Agent 在生产里"出问题时体面不体面"。

还有两个容易忽略的点。一是用例要标注类别（哪条链路、哪种失败模式），否则成功率只是一个总数，看不出是哪一类退化了。二是要定期清理，那些无论怎么改都必过的用例其实不再提供信息，可以降频跑；把跑批预算留给区分度高的那部分。
