A44 · Context Engineering 概念与实现

Context 定义 → Context Window 限制 → 四大问题 → 四类技术策略 → 保存/选择/压缩/隔离

Context Engineering 是给模型做"信息供给侧改革"：不改模型结构，只改模型看到什么——用保存、选择、压缩、隔离四板斧，让有限窗口里的每个 Token 都花在刀刃上。

一、Context 与 Context Window

Context（上下文）指模型的输入内容，包括用户问题、背景信息、相关资料、工具列表、工具执行结果和历史对话——模型看不到你的数据库、看不到你的文档库，它只能看到这一次请求里被"端上桌"的所有文字。

Context Window（上下文窗口）指模型单次最多能处理的 Token 数量，是上下文的物理上限。

上下文的六大组成部分

组成来源特点
系统提示词开发者预设稳定、每次重复
历史对话会话累积随轮次线性增长
检索资料（RAG）外部知识库按需动态注入

记忆（Memory）长期记忆库跨会话持久化
用户当前问题用户输入通常最短

上下文窗口是模型的"工作台"，不是"仓库"：摊在台面上的材料模型才看得见，堆在仓库里的再多也与它无关——工程的核心就是决定台面上摆什么。

二、为什么不能把所有资料都塞进去

即使 Context Window 很大，直接塞入所有资料也有问题：

问题说明
① 大部分模型窗口有限许多小模型只有几万 Token，装不下长文档
② 输入太杂乱影响理解模型可能混淆重点，输出含糊其辞
③ 输入越多成本越高API 按 Token 计费，优化输入就是优化成本

问题②在业界有一个著名现象叫迷失中间（Lost in the Middle）——当关键信息位于超长输入的开头或结尾时，模型的召回率明显高于位于中间时。也就是说，塞得越多，中间的信息越容易被"视而不见"，长上下文并不等于好上下文。

输入长度的连锁代价

单次输入规模相对成本首字延迟（典型值）注意力质量
2,000 Token1 倍约 0.3~0.5 秒高
20,000 Token10 倍约 1~2 秒中（中段易被忽略）
100,000 Token50 倍约 5~10 秒低（需配合检索定位）
Context Engineering（上下文工程） 的核心思想：不改变模型结构，只改变模型看到什么。精心设计给模型的输入内容，让模型在有限窗口中理解得更准、答得更好、花得更少。

上下文不是"冰箱"——塞得越满越安心；它是"工作台"——摆得越精越高效。多塞一份无关资料，就多一份干扰、多一笔账单、多一段延迟。

三、四大技术策略

原始信息池（文档 / 历史 / 工具结果 / 用户偏好） │ ┌──────────┬────────┴────────┬──────────┐ ▼ ▼ ▼ ▼ ① 保存 ② 选择 ③ 压缩 ④ 隔离 写入记忆库 静态规则 / RAG 摘要替换 Sub Agent 按需召回 动态检索 原始历史 独立窗口 │ │ │ │ └──────────┴────────┬────────┴──────────┘ ▼ 精炼后的 Context ──→ 送入模型窗口 （更少 Token，更高信噪比）

① 保存 Context

将信息筛选总结后存入记忆库（Memory）——独立于会话之外、可跨对话持久化的信息存储——在模型需要时再发送。例：ChatGPT 的记忆功能，记住用户偏好和历史，下次对话自动带入相关条目。

② 选择 Context

从海量信息中选择与用户问题最相关的内容放入上下文，是最常用的一类策略。

类型说明示例
静态选择每次请求都全部放入（永远重要的信息）.cursorrules、CLAUDE.md 文件
动态选择按需选择与问题最相关的内容RAG（检索增强生成，先从知识库检索相关片段再注入上下文的技术）、工具筛选、记忆库匹配

③ 压缩 Context

对历史消息做总结压缩，释放上下文空间。例：Claude Code 在上下文使用超过 95% 时自动运行 auto compact（自动压缩）——把冗长的历史对话总结成简短摘要、丢弃原始内容的机制，用几千 Token 的摘要替代十几万 Token 的原始历史。

④ 隔离 Context

不同模块之间的上下文互相隔离，互不干扰。常见于多 Agent 系统：每个 Sub Agent（子智能体）——只负责单一子任务、拥有独立上下文的专职 Agent——有独立的上下文、独立的工具、独立的记忆体系，主 Agent 只接收它的最终结论。

策略与问题的对应关系

策略解决的问题典型手段
保存信息需要跨会话持久化Memory、用户画像
选择信息池太大，只需相关部分RAG、规则文件、工具筛选
压缩历史累积占满窗口摘要总结、auto compact
隔离多任务互相污染上下文多 Agent、子任务独立窗口

四板斧各管一摊：保存管"记住"，选择管"挑选"，压缩管"瘦身"，隔离管"分桌"——实际系统往往是四招组合使用。

四、Agent 为什么带火了这个话题

  • 模型足够强大 — 只要给到足够精细的要求和完整的相关资料，模型就能给出准确回答，"喂什么"成了效果的决定因素
  • Agent 兴起 — 工具执行结果会累积占满 Context Window，必须管理上下文

聊天机器人一轮对话只有几百 Token，而 Agent 每调用一次工具，就会把工具的完整返回结果塞回上下文：读一个文件几千 Token，跑一次搜索上万 Token，几十轮下来窗口就被工具结果吃光了。

Agent 运行时的上下文增长估算

运行轮次累计上下文（典型编程 Agent）占 20 万窗口比例
5 轮约 1.5 万 Token约 8%
20 轮约 6 万 Token约 30%
50 轮约 16 万 Token约 80%
60+ 轮逼近 20 万 Token触发压缩或截断
上下文吃紧？先诊断症状，再开药方： 症状：历史对话越来越长，窗口被旧消息占满 └→ ③ 压缩（摘要替换原文，如 auto compact） 症状：每次都携带一大段固定资料 └→ ② 静态选择（确认是否真的每次都需要） 症状：资料库很大，问题只涉及其中一小部分 └→ ② 动态选择（RAG 按需检索 Top-K 片段） 症状：用户偏好、长期事实被反复询问 └→ ① 保存（写入记忆库，按需召回） 症状：多任务互相干扰，工具结果刷屏 └→ ④ 隔离（拆成多个 Sub Agent 独立作战）

Agent 是"上下文粉碎机"：它越能干，产生的工具结果越多，窗口塌得越快——Context Engineering 从"锦上添花"变成了 Agent 能否长时间稳定运行的"生命线"。

五、生产实践案例

案例一 · Claude Code 的 auto compact：背景：编程 Agent 单次任务动辄几十轮工具调用，上下文以每轮数千 Token 的速度累积。问题：20 万窗口在长任务中必然被撑满，若直接截断旧消息，模型会遗忘原始任务目标，后续推理质量断崖式下降。方案：Claude Code 内置 auto compact——上下文使用超过 95%（约 19 万 Token）时自动触发，把历史总结成约 8,000 Token 的摘要并丢弃原始内容，同时保留任务目标和关键决策。效果：压缩后窗口占用从 95% 回落到约 5%，任务可以无缝继续，长任务（50+ 轮）的完成率显著提升。
案例二 · 企业客服 Agent 的上下文瘦身：背景：某客服 Agent 每轮都携带全量产品手册（约 1.8 万 Token）和全部历史对话。问题：单次输入平均 2.4 万 Token，首字延迟 3.8 秒，月成本超 3 万元，且手册无关章节经常干扰回答。方案：三招组合——产品手册改 RAG 动态检索 Top-3 片段（选择）、超过 10 轮的历史自动摘要（压缩）、用户偏好写入记忆库按需召回（保存）。效果：单次输入降到平均 6,800 Token（-72%），首字延迟降到 1.2 秒，人工评测准确率从 78% 升到 89%，月度成本降到约 9,000 元。
  • 把上下文当稀缺资源管理，为每类内容设置 Token 预算
  • 长文档一律先切块检索，再注入最相关片段
  • 为长会话设置压缩阈值，摘要时保留任务目标
  • 多任务场景拆 Sub Agent，让每个子任务轻装上阵
  • 不要以为窗口够大就全量塞入（中段信息会被忽略）
  • 不要无脑截断旧消息，先做摘要保住关键决策
  • 不要把工具返回的原始大 JSON 原封不动塞回上下文
  • 不要等窗口爆了才治理，要在架构设计时就规划

判断 Context Engineering 做得好不好的标准很朴素：模型回答更准了、账单更薄了、Agent 跑得更久了——三者都指向同一件事，窗口里的信噪比变高了。

Q&A

什么是 Context Engineering？它解决了什么问题？
Context Engineering 是精心设计给模型的输入内容，核心思想是"不改变模型结构，只改变模型看到什么"。它解决三个问题：①大部分模型的 Context Window 有限（几万到百万 Token）；②输入太杂乱会影响模型理解（混淆重点、输出含糊，还存在"迷失中间"现象）；③输入越多成本越高（API 按 Token 计费）。通过四类策略（保存/选择/压缩/隔离 Context）让模型在有限窗口中理解得更准、答得更好、花得更少。
Context Engineering 的四大策略是什么？各有什么作用？
①保存 Context——将信息筛选总结后存入记忆库（如 ChatGPT Memory），解决跨会话的信息持久化问题；②选择 Context——从海量信息中选出与问题最相关的内容，分静态选择（每次全量放入，如 .cursorrules、CLAUDE.md）和动态选择（按需匹配，如 RAG 检索）；③压缩 Context——对历史消息做总结压缩释放空间（如 Claude Code 上下文超 95% 时触发 auto compact）；④隔离 Context——不同模块各自独立上下文互不干扰（如多 Agent 架构中每个 Sub Agent 有独立窗口）。实际系统通常组合使用。
为什么 Agent 的兴起带动了 Context Engineering 的话题？
Agent 运行时需要将工具列表、工具执行结果、思考过程等信息都放入模型的上下文中，而工具结果往往体量很大——读一个文件几千 Token，跑一次搜索上万 Token。Agent 运行时间越长，累积的结果越多，会快速占满整个 Context Window，导致：①早期信息被丢弃（上下文截断）；②模型遗忘原始任务目标；③后续推理质量下降。因此必须通过 Context Engineering（尤其是压缩和隔离策略）来管理上下文，确保 Agent 长时间稳定运行。这也是 Claude Code 等编程 Agent 都内置 auto compact 机制的原因。
Context Window 越大越好吗？为什么有了百万窗口还要做压缩？
不是越大越好，原因有三：①成本——输入 Token 按量计费，10 万 Token 的输入成本是 2,000 Token 的 50 倍；②质量——"迷失中间"现象表明，关键信息在超长输入的中段时召回率明显下降，长上下文不等于好上下文；③延迟——Prefill 阶段虽可并行，但输入越长首字延迟越高，10 万 Token 级别的首字延迟可达数秒。所以即使 Gemini 有百万窗口，工程上仍然要用压缩和检索把真正进入窗口的内容控制在"少而精"，窗口大小是兜底能力，不是使用方式。
RAG 和长上下文直接塞文档，应该怎么选？
两者适用场景不同：长上下文直接塞适合"文档不大、每次都要通读全文"的场景，如分析一份 30 页合同，实现简单、不丢细节；RAG 适合"资料库很大、单次问题只涉及局部"的场景，如几千篇产品手册的客服系统。选型看三个指标：资料总量是否远超窗口（是→RAG）、单次问题是否只需要局部信息（是→RAG）、成本是否敏感（敏感→RAG，可省 70%+ 输入 Token）。实践中常见组合是"RAG 粗筛 + 长上下文精读"：先检索出候选文档，再把最相关的 1~2 篇全文塞入窗口。
压缩历史上下文时，哪些信息容易丢？怎么避免？
摘要压缩是有损的，最容易丢三类信息：①原始任务目标和约束（被后续大量对话淹没）；②关键决策及其理由（"为什么选了方案 A"）；③精确数值、文件路径、错误堆栈等细节（摘要倾向于概括而非保留原文）。避免方法：压缩时采用"结构化摘要"——固定保留"任务目标 / 已完成事项 / 关键决策 / 待办"四个板块；对精确细节（如文件路径、报错信息）单独提取成清单附加在摘要后；Claude Code 的 auto compact 就是这样设计的，压缩后仍保留任务目标，让长任务能无缝继续。
静态选择和动态选择有什么区别？分别什么时候用？
静态选择是"每次都全量放入"，适合永远重要、体量又小的信息，如编码规范、项目结构说明（.cursorrules、CLAUDE.md 就是典型代表），优点是实现简单、永不遗漏，缺点是持续占用窗口和费用。动态选择是"按需匹配最相关的片段"，适合体量大、只有部分相关的信息，如知识库文档、历史记忆，典型实现是 RAG 检索和记忆库召回，优点是省 Token、信噪比高，缺点是需要检索系统且可能漏召回。经验法则：单条信息小于几千 Token 且每次必用→静态；资料库庞大或命中率低→动态。
