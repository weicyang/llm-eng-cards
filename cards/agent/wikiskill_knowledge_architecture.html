让 Skill 越用越强的关键不在"这条规则怎么写"，而在"经验进入 Skill 之前要先过三道权限不同的关口"——原始轨迹只能追加不能改写，Wiki 可以反复修正且永不回滚，Skills 只接受在验证集上严格提分的版本。

一、直接追加规则为什么会失效

目前让 Agent 自己进化 Skill 的主流做法是一条很直的路线：跑完一批任务，让模型读一遍成功和失败的轨迹，总结出一条经验，直接追加到 SKILL.md 末尾。工具调用报错了就加一条调用规范，文件路径找错了就加一条路径约定，测试虽然通过但绕了一大圈就再补一条流程规则。跑上几十轮，Skill 的行数确实一路上涨，可它到底变强了多少，没有人说得清。

问题的名字叫开环演化——修改基于"诊断听起来对不对"就被接受，没有任何环节去测量这条修改实际造成了什么后果。开环之下至少混进了三种噪声：一次成功可能只是采样运气，一套规则可能只适合当前那道题，而新经验可能正在和某条旧规则互相拆台。

最麻烦的是第四种：负责提出修改的模型往往也最擅长为自己的修改辩护。它能把一次偶然通过的运行分析得条理分明、因果清晰。如果验收也交给同一个模型，那么出题、答题、改答案、判分就都由一个人包办了——这在工程上叫做归因污染，指的是无法把"成绩变化"和"某次具体改动"对应起来，于是任何结论都不可信。

失效模式具体表现为什么难发现WikiSkill 的对应机制
偶然成功被写成规律一次采样恰好通过，被总结成"有效做法"轨迹本身看起来完全正常Pattern 需要跨轮反复出现才积累证据
规则过拟合单题规则里写死了具体文件名、具体列号训练集上分数确实在涨Gating 用独立验证集判定，训练分不算数
新旧规则冲突后加的流程规则否掉了前面已生效的做法只看新增 diff 看不出冲突Wiki 同时抽样成功轨迹，保护已有效行为
提案者兼裁判模型自评"这次修改改善了推理"解释永远比结果更有说服力模型只能提案，合并权归验证集分数

WikiSkill 之前的几种方案已经各自碰到了这堵墙。按论文的梳理：EvoSkill 维护一份历史提案及其评估结果的累积记录，Trace2Skill 跨轨迹提炼经验再合并进 Skill，SkillOpt 依靠被拒编辑的反馈和 epoch 级别的元指导。它们的共同缺口是同一个——"到目前为止学到了什么"没有被表示成一份独立的、可以持续演化的知识对象，而是散落在优化历史里，下一轮很难系统性地复用。WikiSkill 论文明确提到，这一层的设计受了 Karpathy 关于 "LLM Wiki"（把经验编译成持久、可复利的知识）这一观点的启发。

直接 append 规则的本质问题不是"规则写得不好"，而是没有人负责回答"这条规则值不值得存在"——而这个问题只能用运行结果回答，不能用文字解释回答。

二、三层架构：写入权限即分工

WikiSkill（arXiv:2608.27454，Google Research）的做法是把 Agent 的工作区拆成三个目录，并给三个目录配上完全不同的写入权限。一次运行产生的东西不再只有一个去处，而是被分流到三层：原始过程留下来，反复出现的经验整理起来，只有通过验证的规则才允许进入 Skill。

┌─────────────────────────────────────────────────────────┐ │ ① raw/ Raw Layer 写入后不可修改（append-only） │ └─────────────────────────────────────────────────────────┘ └─ 每次 rollout 的推理步骤 / 工具调用 / 工具返回 / 最终答案 │ Wiki Maintainer 抽样消化（成功 + 失败各若干条） ▼ ┌─────────────────────────────────────────────────────────┐ │ ② wiki/ Wiki Layer 可增可改，跨轮累积，永不回滚 │ └─────────────────────────────────────────────────────────┘ ├─ patterns/ 反复出现的失败模式与已验证有效做法 ├─ logs.md 每轮发现了什么（演化日志） └─ skill-impact.md 提案 diff / 验证分数 / 采纳或拒绝 │ Skill Proposer 每轮提出一次原子修改 ▼ ┌─────────────────────────────────────────────────────────┐ │ ③ skills/ Skills Layer 只留通过验证的版本，可回滚 │ └─────────────────────────────────────────────────────────┘ ├─ SKILL.md 怎么做：适用条件 + 行动规则 └─ PURPOSE.md 为什么存在：指回 wiki 的哪个 Pattern │ 注入下一轮 Inference Agent 的提示词 ▼ 下一轮 rollout ——（读不到 wiki/，只看得到 skills/）

2.1 Raw Layer：不给结论，只保证以后还查得到

不可变轨迹指的是一次运行的完整现场记录：Agent 当时看到了什么、采取了什么动作、工具返回了什么、最终有没有完成任务，全部落盘之后不再修改、不再删除。这一层不做任何总结。

为什么要这么克制？因为早期的分析结论很可能是错的。论文里的 ALFWorld 案例就是现成的例子：第一次复盘时，系统给出的诊断是"Agent 缺乏目标意识"；等到更多轨迹积累起来，才发现问题其实集中在一组非常具体的动作组合上。如果原始记录在第一次总结时就被覆盖成"缺乏目标意识"这句话，后面就再没有现场可以回看，只能带着错误的前提继续往下改。只追加不修改，代价是磁盘，收益是任何时刻都还能重新分析一遍。

2.2 Wiki Layer：把几百份轨迹压成能读完的知识

运行次数一多，原始轨迹会迅速堆积。下一轮修改 Skill 时显然不能从几百份执行记录里从头读起，而且系统还需要知道另外一类信息：哪些错误反复出现过、上次用什么办法修的、那次修改为什么没通过。这些都由 Wiki Layer 承担，它包含三类内容。

Pattern 页是 patterns/ 目录下的一个个 Markdown 文件，每份记录一种反复出现的失败模式或一种已被证实有效的做法，包含根因分析和可执行的应对方式。Wiki Maintainer 对 Pattern 页采用增量式的补丁编辑（追加、替换、插入片段），而不是整篇重写，这样同一个 Pattern 可以随着新证据不断精化。

技能影响追踪是 skill-impact.md，由外层 harness 在每次 Gating 之后程序化写入，记录每一轮提案的 diff、验证分数、以及最终采纳还是拒绝。它和演化日志 logs.md（记录每轮发现了什么）一起，给系统提供了跨轮次的历史意识——下一轮的提案者能看到"这条路已经走过、没走通"。

2.3 Skills Layer：只放现在真正生效的东西

Wiki 会越积越厚，但执行任务的 Agent 不可能每次开工前先把全部 Pattern、原始轨迹和修改历史读一遍——那等于任务还没开始，Agent 先看完了自己的成长纪录片。所以第三层只保留当前生效的内容，且每个 Skill 目录固定含两个文件：SKILL.md 写清怎么做（适用条件和行动规则），PURPOSE.md 写清它为什么存在（指回 Wiki 里促成它创建或修改的那几个 Pattern）。

PURPOSE.md 这一份看似冗余的文件解决的是长期维护问题。一条限制性规则在半年后往往只剩下"限制"这个印象，没人记得它当初拦住过什么。删掉很痛快，旧 bug 回来也很痛快。有了指回证据的链接，任何人想动这条规则，都可以先回到当初的失败轨迹上确认它是否还有必要。

层存什么写入权限Gating 失败时谁能读失去它的后果
Raw Layer raw/完整执行轨迹只追加，不可修改不受影响Wiki Maintainer、Skill Proposer结论一旦出错就无法重新分析
Wiki Layer wiki/Pattern / 演化日志 / 提案影响可增可改（补丁式）保留，不回滚Skill Proposer每轮都从零猜，重复撞同一堵墙

三个目录只是外壳，真正的设计在权限矩阵上。同一份信息，谁能读、谁能写、失败时谁跟着回滚，决定了这套系统是在积累知识还是在积累噪声。

三层的差别不在目录名，而在"能不能改"和"失败时会不会跟着回滚"：轨迹永不改，Wiki 永不回滚，Skill 每一版都可能被撤回。

三、四步进化循环与 Gating 门禁

三层结构就位之后，WikiSkill 让它们进入一个每轮四步的循环。系统状态可以写成一个二元组：当前生效的 Skill 集合，加上持久的知识库。前者会因为验证不通过而被回滚，后者只增不退。整个循环从空的 Skill 集和空的 Wiki 出发。

┌───────────────────────────────────────────────────────────────┐ │ 第 k 轮进化循环 │ └───────────────────────────────────────────────────────────────┘ ① Inference Agent ── 用 S(k-1) 在训练集上跑 rollout 输入：当前生效 Skill 全文 ⛔ 禁止访问 wiki/ 输出：新的不可变轨迹 → raw/ │ ▼ ② Wiki Maintainer ── 抽少量成功 + 失败轨迹（避免撑爆上下文） 失败样本 → 根因分析 → 新建/补充 Pattern 成功样本 → 提炼有效做法 → 保护已经做对的行为 │ ▼ ③ Skill Proposer（ReAct 多轮） 先读：wiki 索引 + skill-impact.md + 本轮任务成败摘要 按需展开：某个 Pattern 页 / 某条原始轨迹 产出：**一次原子修改**（新建一份 Skill 或补丁改一份） │ ▼ ④ Gating & Rollback ── 候选 Skill 在验证集上跑分 │ ┌───────────┴────────────┐ │ │ 分数严格提高 分数持平或下降 │ │ ▼ ▼ 合并进 skills/ skills/ 回滚到上一版本 │ │ └────────┬───────────────┘ ▼ 两种结果都写入 wiki/skill-impact.md（失败提案同样留档）

3.1 第一步：执行时不许翻答案

四步里最反直觉的约束在第一步——训练阶段的 Inference Agent 被明确禁止访问 Wiki Layer。Wiki 里已经整理了大量失败原因和有效做法，如果执行 Agent 一边做题一边从 Wiki 里找答案，产出的轨迹会相当漂亮，但系统就无法判断这次成功来自当前生效的 Skill，还是来自临时翻到的答案。而下一轮要改的恰恰是 Skill，参考的却是被污染的信号。

论文的消融实验给出了直接证据：训练阶段允许执行 Agent 读取 Wiki，最终进化出来的 Skill 反而更差。所以这一步只给它当前生效的 Skill——先老老实实看看现有规则到底教会了它多少。

3.2 第二步与第三步：抽样消化，然后只动一个地方

Wiki Maintainer 不会一口气吞下全部轨迹。论文的设置是每轮按分层抽样规则抽取少量成功与失败样本，主要原因是上下文窗口撑不住，附带的好处是逼着系统去找"反复出现"的模式而不是逐条记账。失败样本负责暴露问题，成功样本负责保护已经有效的行为——少了后者，新规则很容易在修 A 的时候弄坏 B。

Skill Proposer 以 ReAct 的方式多轮工作：它一开始拿到的不是一堆预先抽好的轨迹，而是 Wiki 索引、历史提案影响表、以及本轮全部任务的成败摘要；发现某个问题值得深挖，再按需打开对应的 Pattern 页和原始轨迹。这个"先看目录再按需展开"的设计同样是为了不撑爆上下文。

它每轮只能产出一次原子修改——要么新建一份 Skill，要么对某一份已有 Skill 做增量补丁，且只针对单个目标 Skill。一次只动一个地方，后面的验证才能把分数变化归因到这一处改动上。如果一轮里同时改三处、加一份、删一份，验证集分数涨了 2 个点，没人知道该保留哪部分。

3.3 第四步：Gating 是唯一的合并权

Gating 门禁指的是候选 Skill 必须在独立验证集上跑出严格提高的分数才允许合并；持平或下降，Skills Layer 立刻回到上一个版本。这里的关键设计是回滚只作用于 Skills Layer——这次失败的提案仍然会写进 Wiki，下一轮的 Proposer 能看到"这条路走过、没走通"。

论文里 ALFWorld 的案例把这个机制展示得很完整。有一条轨迹里，Agent 从桌上拿起一个时钟，检查一遍，又把它放回原来的位置；接着再次拿起、再检查、再放回。动作一直在发生，任务却没有向前推进——路线是个圆。这段过程先进 Raw Layer，随后被 Wiki Maintainer 整理成一个 Pattern：Agent 会拿起物品、检查、送回原处，然后重复同一组动作。

第 0 轮，Skill Proposer 针对这个 Pattern 写了一份叫"目标导向行动"的 Skill，希望 Agent 行动时更有目标感。这句话听起来无可指摘，验证集跑完却没有提分，候选被撤回。但这次失败留在了 Wiki 里：不只记了改过什么，还记了"让 Agent 更有目标"这种抽象规则并没有解决循环。下一轮 Proposer 处理同一个问题时，不必换套措辞再撞一次墙，而是给出了一条具体得多的规则——拿起物品之后不要再把它放回原来的位置。验证集重跑，分数提高，这条规则正式进入 Skills Layer。再往后，Agent 出现了另一种循环（围绕同一个物品重复同一种操作），Wiki 继续补录，Skill 又加上一条：同一种操作对同一个物品只执行一次。

步骤输入输出关键约束去掉这条约束会怎样
① 推理 rollout当前生效 Skill 全文不可变轨迹禁止读 Wiki成功来自 Skill 还是来自翻答案，无法区分
② Wiki 维护抽样轨迹 + 现有 WikiPattern / 演化日志成功与失败都抽只看失败，新规则会弄坏原本做对的事
③ Skill 提案Wiki 索引 + 提案历史 + 成败摘要一次原子修改每轮只改一处分数变化无法归因到具体改动

模型负责交方案，验证集决定能不能合并——所谓"自我进化"必须很克制：Agent 可以分析轨迹、可以提出补丁，但它碰不到正确答案、改不了评分标准、也不能跳过验证直接发布。

四、实验结果：Wiki 贡献了多少

论文在五个基准和五个模型上做了交叉测试。基准覆盖数学推理（LiveMathematicianBench）、网页搜索（SealQA）、电子表格操作（SpreadsheetBench）、长上下文文档问答（OfficeQA）和交互式具身任务（ALFWorld）；模型来自 Qwen、Gemma、Gemini 三个家族。所有方法都从空 Skill 集开始，演化出的 Skill 在推理时全文注入提示词；每种方法完整跑三次独立演化，报告的是三份 Skill 的平均测试表现，差异显著性用配对 bootstrap 在 p<0.05 上检验。

SpreadSheet电子表格操作+40.9 点操作序列固定、工具约束明确，最适合写成程序性规则

这张表比总分更有指导意义：越是"有固定操作套路、失败模式可以命名"的任务，Skill 演化的收益越大。同一份 SpreadSheet 上的机制，在 Qwen 三个尺寸上分别带来 +6.5、+9.3、+40.9 点的提升，跨度接近七倍。反过来，如果一个任务的失败原因每次都不一样、说不清是哪一步错的，那么先投入的应该是可观测性建设，而不是 Skill 演化流水线。

论文核心结论（WikiSkill 论文摘要）：带演化 Skill 的较小模型可以超过不带 Skill 的、规模大得多的模型——在这套实验里，就是 9B 级别加上演化后的 Skill，平均表现超过了无 Skill 的 27B 级别。配合前面那条"移除持久 Wiki 平均掉 15.0 个百分点"，两个数字合起来说明了一件事：把经验组织好带来的收益，量级上可以和把模型换大一档相当，而后者的成本要高出一个数量级。但这个结论有明确边界——它成立的前提是任务有可计算指标、有独立验证集、失败模式可以被反复观察到。

Skill 演化和模型规模是两条互补的增益轴，不是替代关系：强模型不是"不需要 Skill"，而是"更用得上 Skill"。

五、迁移效应与来源模型的坏习惯

如果 Skill 只是一份文本，那它理论上可以从一个模型搬到另一个模型上。论文专门做了这组交叉实验：用不同的来源模型演化出 Skill，再交给不同的推理模型执行。结果两个方向都很明显——有些迁移比自己演化的还好，有些迁移直接把成绩打到了地板上。

5.1 小模型的求生偏方，强模型吃了会中毒

论文的错误分析指出了根因，而这个根因值得任何做 Skill 工程的人记住：小模型能力有限，为了避免执行失败，它会在 Skill 里留下大量低层次的规避性补丁——比如强制使用单行 Python 命令、把一个完整流程拆成过分细碎的步骤。这些约束确实能扶住小模型，让它少踩坑；但同样的约束交给强模型，就变成了戴在手上的镣铐。

具体的失效路径是这样的：强模型本来有能力一次性写完并执行一个完整脚本，几步就把表格任务做完；现在被 Skill 教成"一步一动"，每个动作单独发一次工具调用。任务还没做到一半，工具调用预算先花光了，于是被判失败。能力没有下降，是被规则挡住了。

同一份 SpreadSheet Skill，注入两个不同能力的模型： 规则：「强制单行命令」+「把流程拆成大量细步骤」 │ ├──▶ 弱模型（4B） │ 多步长脚本本来就容易写错 → 拆细后每步都能验 │ 工具调用预算：够用 ✅ 表现上升 │ └──▶ 强模型（Gemini-3.5-Flash） 本可一次写完整脚本 → 被迫一步一动 工具调用预算：提前耗尽 ❌ 50.5% → 18.1% ┌─────────────────────────────────────────────────────────┐ │ 判据：这条规则是在补能力短板，还是在传递领域知识？ │ │ 补短板 → 强绑定来源模型，跨模型迁移前必须重测 │ │ 传知识 → 通常可迁移（如解题套路、输出规范、检索策略） │ └─────────────────────────────────────────────────────────┘

另一个侧面证据来自 Skill 的长度统计。同样跑完整套演化流程，Qwen 系列产出的 Skill 长度在 118.9 到 128.6 行之间，而 Gemma-4-31B 只有 45.1 行、Gemini-3.5-Flash 是 81.2 行。强模型自然收敛到更简洁、更有选择性的 Skill——它不需要那么多护栏。

这组结果还带来一个可以直接用的工程推论：负责发现方法的模型和负责执行方法的模型可以分开。既然 27B 演化出的 Skill 能把 9B 从 24.3% 拉到 50.5%（远超 9B 自己演化的 33.6%），那么把 Skill Proposer 这个角色交给最强的可用模型、把执行留给便宜模型，是一种成本效率更好的配置。演化是一次性投入，执行是重复成本。

迁移 Skill 之前先问一句：这条规则是在给来源模型补短板，还是在讲这个领域本来就该怎么做？前者换模型必须重测，后者才是真正可复用的资产。

六、自建三层架构的工程清单

三层架构听起来只是三个目录，但它成立的前提是一整套外部约束。少了这层约束，"自我进化"会很快退化成"自我感觉良好"。所以先判断自己在不在适用范围内。

你的任务有可自动计算的成绩指标吗？ │ ├── 没有 ──▶ 先做可观测性和评测集，别做演化 │ （没有分数，Gating 无从判断） ▼ 能拆出互不重叠的 训练 / 验证 / 测试 三份数据吗？ │ ├── 不能 ──▶ 只做「固定回归集 + 改完重跑 + 变差回滚」 │ （能挡住明显回归，但学不到跨轮知识） ▼ 同类任务每天/每周会重复跑很多次吗？ │ ├── 不会 ──▶ 人工维护 Skill 更划算 ▼ 失败模式说得清吗（能命名成「反复出现的某种循环/某类报错」）？ │ ├── 说不清 ──▶ 先补轨迹记录，让失败可命名 ▼ ✅ 适合上完整三层架构 + 四步循环 必备外围：版本管理 · 自动评测 · 一键回滚 · 提案影响留档

回归集兜底（最简）一组固定任务 + 一个通过率挡住明显回归，改完能判断好坏不积累跨轮知识，同一堵墙会反复撞单个 Skill、人工维护为主

不该用无指标、任务一次性、失败原因说不清——先做评测和轨迹记录

还有一个容易被忽略的成本结构：论文把被采纳的 Skill 更新按迭代阶段分组统计，发现最初的第 0–1 轮就占了各模型采纳更新总量的 39% 到 52%。收益是明显前置的——最容易发现、最有价值的那几条规则，往往在头两轮就被抓到了。这意味着"跑一百轮总会更好"是错的期待，合理的做法是设定固定轮数预算，并在采纳率明显衰减后停下来。而每一轮的成本都是实打实的：一次训练集 rollout，加一次完整验证集评测。

  • 执行 Agent 只注入当前生效的 Skill，把 Wiki 对它完全屏蔽
  • 每轮只允许一处原子修改，让分数变化可归因
  • 验证集严格提高才合并，持平就当失败
  • 被拒的提案连同 diff 和分数一起留档，下一轮能看到
  • 每条 Skill 都写清它对应哪个失败证据（PURPOSE.md 的作用）
  • 换执行模型时把全部 Skill 重跑一遍验证集，别假设可迁移
  • 抽样时成功轨迹和失败轨迹都要抽
  • 让提出修改的模型同时判定修改是否有效
  • 把训练集分数当验证依据（规则会写死具体题目细节）
  • 一轮里同时新建一份、修改两份，然后看总分
  • 回滚 Skill 时顺手把这轮的分析结论也删掉
  • 用抽象规则应付具体循环（"要更有目标感"通常过不了验证）
  • 把小模型演化出的低层补丁直接搬给强模型
  • 指望迭代轮数越多越好，不设停止条件

最后是和现有做法的边界。人工维护 Skill 那条线的工程化——四维成功定义、四类回归样本、黄金注入与多轮防污染、CI/CD 集成与突变测试——见 《A18 · Skills 技能维护方法论》。两张卡的分工是：A18 讲人怎么改 Skill 才不会悄悄引入回归，本文讲怎么让 Agent 自己从失败里积累知识并把修改权交给验证集。前者的回归测试框架其实正是后者 Gating 那一步的工程实现，缺了它，三层架构就只剩三个目录。更上一层的系统视角——经验提取、能力固化、四级受控发布与熔断——见 《A65 · Agent 自主进化工程路径》。

三层架构真正的门票不是那三个目录，而是一套外层设施：训练/验证/测试三分、可计算的指标、版本管理和一键回滚——没有这些，"自我进化"只是让模型给自己发奖状。

Q&A

为什么训练阶段要禁止执行 Agent 读取 Wiki？把知道的都告诉它不是更好吗？
因为训练阶段要测量的不是"这次任务能不能做成"，而是"当前这份 Skill 教会了它多少"。Wiki 里整理了大量失败根因和有效做法，Agent 一边做题一边翻 Wiki，产出的轨迹会很漂亮，但系统再也分不清成功来自 Skill 还是来自临时找到的答案——而下一轮要改的正是 Skill。论文的消融实验直接验证了这一点：训练时开放 Wiki 访问，最终演化出的 Skill 反而更差。注意这个限制只针对训练阶段的执行角色；Wiki Maintainer 和 Skill Proposer 是必须读 Wiki 的。
Skill 被 Gating 拒了、回滚了，那一轮的工作是不是白做了？
不是，这正是三层架构最关键的设计。回滚只作用于 Skills Layer，Wiki Layer 永不回滚。被拒的提案连同它的 diff、验证分数和拒绝原因，都会写进 skill-impact.md，成为下一轮 Proposer 的输入。ALFWorld 那个例子很典型：第 0 轮"目标导向行动"这条抽象规则被拒，但"抽象规则解决不了动作循环"这个信息留下了，下一轮 Proposer 才没有换个措辞重撞一次墙，而是直接给出具体规则并通过验证。换句话说，失败提案的价值在于排除了一条路。
为什么规定每轮只允许一次原子修改？这样迭代不是很慢？
慢是代价，换来的是可归因性。假设一轮里同时新建一份 Skill、修改两份已有 Skill，验证集分数涨了 2 个点——你无法知道该保留哪一处、该撤回哪一处，最坏情况是三处改动里两处有害一处有益，净效果正向于是全部保留，噪声就这样长期驻留下来。一次只动一处，分数变化就唯一对应这处改动，Gating 的判定才有意义。论文的统计也说明这道门确实很紧：编辑类提案的采纳率大约只有四分之一到五分之一。
Raw Layer 只追加不删除，轨迹会不会无限膨胀？
会增长，但这是三层里最便宜的一层。轨迹是纯文本，而且不参与推理时的上下文——Inference Agent 完全读不到它，只有 Wiki Maintainer 和 Skill Proposer 会按需读取，且 Maintainer 每轮只抽少量样本。所以膨胀影响的是存储成本，不是 Token 成本或延迟。真正需要控制上下文的地方是另外两处：Maintainer 用分层抽样限制读入量，Proposer 用"先读索引再按需展开"的方式避免一次性吞下长历史。如果确实要治理存储，合理做法是对久远的轨迹做冷归档，而不是删除——删了就失去了重新分析的能力。
Gating 要求验证集分数"严格提高"，会不会太严，导致很多有价值的改动被挡掉？
会挡掉一部分，这是刻意的偏保守设计。允许"持平也合并"会带来两个后患：一是 Skill 长度只增不减，无效内容持续累积并互相干扰；二是概率性系统里的持平常常只是噪声，长期看等于放任随机漂移。严格门禁的代价由 Wiki 层来对冲——被挡掉的方向不会丢失，下一轮可以基于它提出更精确的版本，这正是从"目标导向行动"精化到"拿起物品后不要放回原位"的路径。如果你的验证集很小、方差很大，更稳妥的做法是提高提升门槛或做多次重复评测，而不是放松到"持平即通过"。
小模型演化出的 Skill 为什么会把强模型拖垮？
因为小模型写下的很多规则是在补自己的能力短板，而不是在传递领域知识。论文的错误分析指出，小模型为了避免执行失败会留下大量低层规避补丁，例如强制使用单行命令、把完整流程拆成过分细碎的步骤。这些护栏对它自己有用，但强模型本来可以一次写完整脚本，被规则逼成一步一动之后，工具调用预算在任务完成前就耗尽了。实测数据很直观：4B 演化的 SpreadSheet Skill 让 Gemini-3.5-Flash 从 50.5% 掉到 18.1%，而 27B 演化的同类 Skill 把它提到 63.4%。判据是问一句"这条规则在补短板还是在讲领域知识"——前者强绑定来源模型，换模型必须重测。
这套架构和人工维护 Skill 的回归测试是什么关系？
两者是同一件事的不同层级，而且互为前提。人工维护那条线（见 《A18 · Skills 技能维护方法论》）解决的是"人改完 Skill 之后怎么确认没有悄悄引入回归"，产出是四维成功定义、精选回归样本集、CI 集成。WikiSkill 解决的是"让 Agent 自己从失败中积累知识，并把修改的合并权交给验证集"。关键在于，A18 那套回归测试框架正是 WikiSkill 第四步 Gating 的工程实现——没有可自动运行、结果稳定的回归评测，Gating 就无法判定，三层架构会退化成三个空目录。所以落地顺序是先有 A18 的评测能力，再上 WikiSkill 的自动化循环。
我们团队只有一份 Skill、也没有 benchmark，这套东西还能用吗？
完整的四步循环用不了，但架构里最有价值的两个约束可以立刻用。第一个是把"证据"和"规则"分开存：给每条 Skill 规则标注它对应哪次真实失败（相当于手工版 PURPOSE.md），半年后想删这条规则时才有依据判断，而不是凭印象。第二个是准备一组固定任务当回归集，每次改完 Skill 都完整重跑，变差就恢复上一版——这就是最小可用的 Gating。这两步不需要训练/验证/测试三分，也不需要自动化 harness，但能挡掉最常见的那类事故：改一处、悄悄弄坏另一处。等固定任务集攒到几十条、结果足够稳定，再考虑把抽样和提案环节也自动化。
