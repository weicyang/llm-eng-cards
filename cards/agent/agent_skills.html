A13 · Agent Skills 系统

Agent Skill System — 技能注册、发现、路由、动态加载、自进化机制与 Skill/MCP 选型

Agent Skills 的本质：把 Agent 的"成功经验"固化为可复用的能力模块。Tool 是 Agent 的"手"（原子操作），Skill 是 Agent 的"经验"（知识 + 流程 + 工具的组合编排）。

一、Skills vs Tools 的本质区别

Skill 和 Tool 的界限在于"粒度 + 知识"：Tool 是无内在知识的原子操作（read_file），Skill 是包含领域知识的多步骤组合流程（"创建 PR"需要 5 步 + 知道 commit 规范）。

维度Tool（工具）Skill（技能）
粒度原子操作（单个函数调用）高级过程（多步骤组合流程）
知识无内在知识（纯执行）包含领域知识和最佳实践
组合性被动等待调用可以调用其他 Skills 和 Tools
触发方式显式参数化调用基于上下文自动路由/触发
示例read_file(), run_shell()"创建 PR"、"调试 CI"、"部署生产"

典型 Skill 示例

Skill包含的步骤依赖 Tools
Create PR分析 diff → 写 commit message → push → 创建 PR → 填 bodygit, shell, gh CLI
Debug CI获取失败日志 → 定位错误 → 分析根因 → 提出修复方案gh API, read_file, grep
Deploy to Prod检查测试状态 → 构建 → 部署 → 验证健康检查 → 通知shell, k8s, slack
Code Review读 diff → 分析变更 → 检查规范 → 写 review commentsgh API, read_file, lint
核心洞察：Tool 是 Agent 的"手"，Skill 是 Agent 的"经验"。拥有 tools 不等于拥有 skills，就像拥有键盘不等于会写代码。Skill 将"成功轨迹"结构化为可复用模块，避免每次从零推理。

二、Skill 注册与发现

Skill 注册的本质：告诉系统"我有哪些经验可用"。三种注册方式各有取舍——文件型最简单、注册表型最安全、插件型最灵活。

三种注册机制

机制实现方式优点缺点
文件型SKILL.md / skill.yaml 放在约定目录简单直观、版本控制友好缺乏动态性
注册表型集中注册（如 registry.py）类型安全、IDE 补全修改需重启
插件型entry_points / 动态导入扩展性强、热加载调试困难

Prompt-as-Skill 是当前最流行的注册模式（Cursor 的 SKILL.md 就是典型）：Skill 的内容就是一个 Markdown 格式的 prompt 模板，激活时直接注入 Agent 的 system prompt，让 LLM 自己理解并执行。门槛极低（写 Markdown 就是写 Skill），且天然灵活。

发现机制三级策略

级别方式延迟适用场景
精确匹配触发关键词直接命中<1ms明确的触发词
全文搜索FTS5 全文索引匹配~5ms关键词模糊匹配
语义搜索Embedding 余弦相似度~10ms同义词/模糊表述
Schema 关键设计：每个 Skill 需要声明 name、description、triggers（触发条件）、required_tools（依赖工具）、permissions（所需权限）。其中 trigger conditions 是最关键的字段——它决定了 Agent 何时"想到"使用某个 Skill。设计不好会导致"该触发的没触发"（假阴性）或"不该触发的误触发"（假阳性）。

三、动态加载与路由

混合路由的核心思想：不要把所有决策都扔给 LLM。先用关键词快速匹配（<1ms），再用语义搜索（~10ms），最后才用 LLM 判断（~500ms）——逐级升级，兼顾速度和精度。

路由策略对比

策略方式速度准确率适用场景
关键词匹配正则/精确匹配 trigger keywords极快（<1ms）中等明确的触发词
语义相似度Embedding 余弦相似 + 阈值快（~10ms）较高模糊表述/同义词
LLM 选择让 LLM 从 skill list 中选慢（~500ms）最高复杂/歧义场景
混合路由关键词 → 语义 → LLM 逐级升级自适应最优生产环境推荐
Skill 混合路由决策流: 用户输入: "帮我提个 PR" │ ▼ Level 1: 关键词匹配 (<1ms) "PR" / "pull request" → 命中 "create-pr" skill 置信度 0.95 > 阈值 0.9 → 直接返回 │ ▼ (未命中) Level 2: 语义搜索 (~10ms) "帮我提交代码变更" → 相似度 0.87 > 0.85 → 返回 "create-pr" skill │ ▼ (未命中) Level 3: LLM 判断 (~500ms) 从候选 skills 中选最合适的 → 返回匹配 skill 或 None 无匹配时: Agent 用通用推理（不依赖 skill）

多 Skill 冲突解决

当多个 Skill 同时匹配时，按四重优先级排序：

  1. 具体性（Specificity）——"Python 单元测试" Skill 应优先于通用"测试" Skill
  2. 上下文加权——当前文件是 .py 则 Python 相关 Skill 加分
  3. 历史偏好——该用户之前选了哪个 Skill
  4. 主动消歧——若分数差距 <0.1，主动询问用户选择
Fallback Chain 确保不死锁：即使没有匹配的 Skill，Agent 也能降级到直接使用底层 Tools 尝试完成。完整 fallback 链：专用 Skill → 同类通用 Skill → 直接使用 Tools → 请求用户澄清。路由的"假阴性"（该触发没触发）比"假阳性"（错误触发）更严重——宁可多提供候选让用户选，也不要遗漏。

四、Skill 四种实现模式

选择实现模式的原则：能用 prompt 解决的不用代码，需要确定性的用代码，需要人审的加审批。80% 的 Skills 用 Prompt Template 模式就够了。

模式实现方式复杂度适用场景
Prompt Template结构化 prompt + 工具序列指令低线性流程、少分支（80% 的 Skills）
Agent Workflow状态机/子图（如 LangGraph）高多分支、条件逻辑、需要重试
Code ExecutionPython/Shell 脚本直接执行中确定性操作、批处理（如代码格式化）
HITL Approval关键步骤暂停等人工确认中高风险操作（部署、数据迁移）

Prompt Template 模式详解

Prompt-as-Skill 是最轻量的实现：Skill 的内容就是一个 SKILL.md 文件，Agent 在执行时将其注入 system prompt。相当于给 Agent "临时注入了一段经验"。LLM 理解指令后自主适配具体场景，无需硬编码每种情况。

Skills 调用 Skills（分层抽象）

高级 Skill 可以编排低级 Skills，实现"分层抽象"。例如 "Deploy to Production" Skill 依次调用 "Run Tests" → "Build Image" → "Deploy" → "Health Check" 四个子 Skills，高级编排 Skill 无需关心底层实现细节。

  • Prompt Template 模式优先——80% 的 Skill 用它就够
  • 复杂分支/重试逻辑用状态机（LangGraph 子图）
  • 确定性操作用脚本（如代码格式化、文件批量处理）
  • 高风险操作加 HITL（部署、数据迁移必须人工确认）
  • 不要所有 Skill 都用代码实现（过度工程）
  • 不要用 Prompt 处理需要 100% 确定性的操作
  • 不要忽略错误处理——每个 tool_call 都可能失败
  • 不要跳过 HITL 直接自动执行高风险操作

五、权限与沙箱

权限系统的核心原则：最小权限——每个 Skill 只声明最少需要的权限，运行时严格检查。类比 Android 权限模型：App 声明需要的权限，用户在安装时授权。

四层权限模型

层级控制内容示例
Tool-level哪些工具可被调用read_file: ✓, delete_file: ✗
Scope-level工具的操作范围write_file: 只限 ./src/ 目录
Action-level具体操作类型git: pull ✓, force-push ✗
Approval-level是否需要人工审批deploy: 需要审批, lint: 自动执行

沙箱执行

第三方/社区 Skill 必须在隔离环境中执行（Docker 容器），关键限制包括：无网络访问、只读文件系统、内存限制（512MB）、CPU 限制、超时限制（60s）。这防止恶意 Skill 造成系统破坏——和 npm/pip 面临的供应链安全问题是同一类威胁。

审计日志是合规要求：企业场景需记录每次 Skill 调用的完整信息——who（谁触发）、when（什么时间）、what（执行了什么操作）、result（结果如何）。审计日志不仅用于事后追溯，也是持续优化 Skill 质量的数据来源。

六、自进化 Skills

自进化的核心洞察：Agent 的每次成功执行都是"训练数据"——可以从中提取成功轨迹，抽象为可复用的 Skill 模板，让 Agent 越用越聪明。

自进化四步流程

步骤操作关键要点
① 轨迹提取记录成功的工具调用序列和决策过程去除噪声步骤（重试、无效探索）
② 抽象化将具体参数替换为变量模板"push feat/login" → "push {branch_name}"
③ 质量评估在相似但不同的任务上测试泛化能力pass_rate > 0.8 才通过
④ 渐进发布candidate → review → canary → active10% 流量先试，稳定后再全量

Skill 生命周期

Skill 生命周期管理: candidate ──→ review ──→ active ──→ deprecated │ │ │ │ │ └── success_rate < 0.7 → 收集失败 case → 优化 │ │ │ └── 自动化测试 + LLM 安全审查 + 去重检测 │ └── 从成功轨迹自动生成 持续优化循环: 执行 → 记录轨迹 → 提取 Skill → 测试 → 发布 → 监控 → 优化 → 执行
质量把关三道关：①多任务测试——不能只在生成它的任务上有效（过拟合）；②与 baseline 对比——必须比没有 Skill 时效率更高；③安全审查——检查是否有越权操作。社区共享还面临信任问题（类比 npm 供应链攻击），需要签名验证 + 沙箱隔离 + 社区审核。
延伸阅读 · 技能记忆：如何把 Agent 的成功轨迹系统化地提取、验证、入库并持续进化为可复用技能，是"程序性记忆"研究的核心命题——SkillPro 用非参数化 PPO 让技能自主进化（经验存储 Token 消耗降 99%），MemSkill 则把记忆操作本身变成可学习的技能（LLM 调用次数降 83%）。详见 A43 · AI 程序性记忆革命。

生产案例：某研发团队 Skill 系统

背景：15 人团队，日均代码审查 50+ 次，CI 失败排查耗时平均 45 分钟。

改造方案：基于 Cursor SKILL.md 模式，创建 8 个核心 Skills（Code Review、Debug CI、Create PR、Deploy Staging 等）。

效果：CI 失败排查时间从 45 分钟降至 8 分钟（降幅 82%）。PR 创建时间从 15 分钟降至 3 分钟。Skill 使用率：Code Review 92%、Create PR 88%、Debug CI 76%。Skill 成功率：Create PR 94%、Code Review 91%、Debug CI 83%（CI 问题根因更复杂）。

八、设计最佳实践

Skill 粒度是最难的设计决策——太细（和 Tool 没区别）没价值，太粗（"万能 Skill"）不可靠。判断标准："2-10 步内可靠完成、有明确结束条件的过程"。

粒度设计

粒度示例问题
太细"git-add-file" Skill和 Tool 没区别，无额外价值
适中 ✓"create-pr" Skill有清晰的输入输出，包含决策逻辑
太粗"complete-feature" Skill太模糊，无法可靠执行

版本管理

借鉴 semver（语义化版本）：patch（修复 bug）→ minor（新增步骤，向后兼容）→ major（修改输入输出 schema，破坏性变更）。必须有 skill-lock.json 锁定版本，避免依赖方因 Skill 升级而突然出问题。

监控告警

指标告警条件意义
成功率<80%外部环境可能变化（API 改版）
平均延迟>10s需要优化流程或拆分
调用量7 天为 0考虑废弃该 Skill
用户满意度<3.0需要收集反馈优化
五大常见错误：①粒度错误——太细没价值、太粗不可靠；②忽视错误处理——每个 tool_call 都可能失败，必须有重试/降级策略；③缺乏可观测性——Skill 执行后不知道哪步成功/失败/慢；④没有版本管理——Skill 升级直接覆盖导致依赖方出问题；⑤信任边界模糊——没区分"自己写的"和"第三方"的权限级别。
  • 从小开始（3-5 个核心 Skill），验证可靠后再扩展
  • 每个 Skill 有测试 + 监控，确保 success_rate > 80%
  • 用 semver + lockfile 管理版本
  • 第三方 Skill 必须沙箱 + 最小权限
  • 不要一次性创建 20+ Skills（维护不过来）
  • 不要把 Skill 做得太粗（宁可拆成多个子 Skills）
  • 不要跳过测试——Skill 是"高频复用"的能力，bug 会被放大
  • 不要给第三方 Skill 过大权限（类似 npm 供应链攻击风险）

九、Skill/FC/MCP 三层关系与核心差异

三者不是"三选一"，而是解决不同层面的问题：Function Calling 是意图生成层（模型表达"我想做什么"），MCP 是执行基础设施层（标准化工具发现和调用），Skill 是行为知识层（教模型"怎么做"）。生产系统通常三者组合使用。Agent Skill 是「针对特定框架的定制工具」，MCP 是「通用的工具总线协议」。从 Skill 到 MCP 的演进，本质是从「农业时代」迈向「工业时代」——实现生态解耦，将适配复杂度从 O(N×M) 降至 O(N+M)。但两者并非替代关系：MCP 解决连接问题（标准化协议打通数据孤岛），Function Calling 解决执行问题（模型表达调用意图），Skills 解决行为问题（过程性知识注入）。

维度Agent SkillFunction CallingMCP
本质行为指令注入（Markdown + 代码片段）模型意图表达（结构化 JSON 请求）标准化执行协议（客户端-服务器架构）
架构高耦合 / 烟囱式架构模型 API 内置 / 厂商私有标准化 / 总线式架构
适配复杂度O(N×M) — N 个模型 × M 个工具O(N×M) — 每个厂商格式不同O(N+M) — 每个模型和工具只适配一次
可复用性低 — 绑定特定框架低 — 绑定特定模型厂商高 — 跨框架通用
生态扩展封闭 — 厂商锁定半封闭 — 厂商生态内开放 — 第三方可自由接入
工具发现静态配置静态注册（每次请求全量注入）动态发现（运行时 tools/list）
传输层N/A（内嵌于应用）N/A（HTTP API 内）stdio / SSE / HTTP

复杂度从 O(N×M) 降到 O(N+M) 的意义：当有 10 个模型和 100 个工具时，Skill/Function Calling 模式需要 1000 次适配，MCP 只需要 110 次。当工具数量增长到 10,000 时，Skill 需要 100,000 次适配，MCP 仅需 10,010 次——这是生态能否规模化扩展的分水岭。截至 2025 年底，MCP 生态已有 2,000+ 社区 Server，月均 SDK 下载量达 9700 万+。

十、MCP 协议深度解析——架构、原语与传输层

MCP 的核心设计哲学是"关注点分离"——将工具定义从应用中完全解耦。工具运行在独立的 MCP Server 进程中，通过标准化协议暴露能力。Host 通过 Client 动态发现可用工具，无需在代码中硬编码任何工具逻辑。

三大角色

角色职责示例
HostAI 应用（用户直接交互的界面）Claude Desktop、VS Code、Cursor
Client维护与 MCP Server 的连接，代理工具调用每个 Host 内嵌一个或多个 Client
Server独立进程，暴露 Tools、Resources、PromptsGitHub Server、Database Server、Stripe Server

三大原语（Primitives）

MCP 定义了三种核心原语，覆盖工具交互的全部场景：

  • Tools（工具）：可执行的操作，如 query_database、create_issue。对应 Function Calling 中的"函数"
  • Resources（资源）：可读取的上下文数据，如数据库 Schema、文件内容。这是 Function Calling 没有的能力
  • Prompts（提示模板）：可复用的交互模板，如"代码审查模板"、"SQL 生成模板"。标准化了 LLM 与工具的交互模式

传输层选择

十一、Skill 的优势场景——什么时候不用 MCP

Skill 并非过时技术——在特定场景下它仍然是最优选择。核心判断标准是：如果操作是纯本地的、无副作用的、不需要权限控制的，Skill 比 MCP 更轻量高效。

Skill 更优的三种场景

场景为什么用 Skill延迟对比
纯本地操作无网络调用、无副作用（如代码格式化、文本处理）Skill ~50ms vs MCP ~120ms
深度模型集成需要访问模型的中间状态、对话历史（Skill 可直接读取上下文）MCP 只能通过标准化接口，无法访问内部状态
快速原型验证开发周期 1-2 小时（写个函数即可），MCP 需要设计 Server 结构原型阶段优先考虑速度

Skills 的独特价值：过程性知识注入

Skills 有一个 MCP 无法替代的能力：过程性知识注入（Procedural Knowledge Injection）。Skills 本质是 Markdown 格式的行为指令，通过 Progressive Disclosure（渐进式披露）注入模型的上下文窗口——先加载元数据（极少 Token），仅在匹配时才加载完整内容。这让 Skills 在 Token 效率上远优于全量加载工具定义。

例如，一个"财务报告生成"Skill 可以包含：SEC 合规要求、标准模板、常见错误清单。这些知识不是"工具"，而是"做事的方法"——MCP 提供工具（查数据库），Skill 提供方法（怎么用数据写报告）。

生产数据：某开发工具平台的 Skill vs MCP 选型实践：(1) 代码格式化（本地、无副作用）→ Skill 实现，延迟 50ms，零网络开销；(2) GitHub 操作（远程 API、需认证）→ MCP Server 实现，支持 OAuth + Token 刷新，月调用 120 万次；(3) 数据库查询（敏感数据、需权限控制）→ MCP Server + RBAC 权限，拦截了 450 次未授权查询。

十二、工程落地四大难点与解决方案

从 Skill 迁移到 MCP 或两者混用，都面临四大工程难题：上下文膨胀、安全风险、存量迁移、参数幻觉。每个难题都有成熟的解决方案，关键在于不要跳过任何一步。

难点一：上下文膨胀

问题方案效果
数百个工具全量注入导致提示词过长动态路由 + RAG 技术实现按需加载Token 消耗降低 60-80%

解决思路：不把所有工具描述塞进 Prompt，而是根据用户意图动态检索相关工具。实现方式类似于 RAG 的召回+精排策略：先用轻量分类器判断意图类别，再从工具库中检索该类别下的 Top-5 工具描述注入 Prompt。

难点二：安全风险

风险类型攻击场景方案
工具注入恶意 MCP Server 返回包含 Prompt Injection 的结果输出过滤 + 沙箱执行
权限提升Agent 组合多个低权限工具实现高权限操作操作链路审计 + 权限叠加检查
数据泄露MCP Server 返回数据中包含其他用户的敏感信息数据隔离 + 结果脱敏

关键原则：高危操作（如数据库写入、文件删除、支付操作）必须经过人工确认（Human-in-the-Loop），同时为不同角色配置最小权限。MCP 的 Session 级访问控制和认证协商机制天然支持这一需求。

难点三：存量代码迁移

问题方案迁移成本
已有 Python Skill 如何低成本转换适配器模式自动转换函数签名降低 80% 迁移工作量

迁移策略：不要求重写，而是用适配器（Adapter）包装现有 Skill，自动将函数签名转换为 MCP 协议格式。适配器负责：(1) 将 Python 函数的参数映射为 JSON Schema；(2) 包装返回值为 MCP 的 TextContent 格式；(3) 注册到 MCP Server 的工具列表中。团队无需改动业务逻辑，只需添加一层薄薄的适配代码。

难点四：参数幻觉

问题方案效果
模型常丢失必填参数或生成错误类型Pydantic 强校验 + 反馈重试机制参数错误率从 12% 降至 < 1%

防御机制：用 Pydantic 定义参数 Schema，模型输出不符合规范时自动反馈错误信息，触发重新生成（最多 3 次）。第一次错误反馈会告知模型"缺少必填字段 date_range"，第二次会提供更具体的示例，第三次仍失败则降级到人工确认。

  • 用 MCP 替代 Skill 实现需要网络调用和权限控制的工具
  • 动态路由按需加载工具描述，控制 Prompt 长度
  • 高危操作必须人机回环确认
  • 用适配器模式迁移存量 Skill，不要求重写
  • Pydantic 强校验 + 重试机制防止参数幻觉
  • 所有 MCP 调用记录审计日志，定期渗透测试
  • 不要全量注入所有工具描述（上下文爆炸）
  • 不要让 Agent 直接操作生产数据库
  • 不要要求团队重写所有存量 Skill
  • 不要信任模型输出的参数格式（永远做校验）
  • 不要在 Skill 和 MCP 之间混用同一功能（选一个）
  • 不要忽略 MCP Server 返回结果中的 Prompt Injection 风险

十三、MCP 安全性深度分析

MCP 的去中心化架构（Client 和 Server 分离部署）引入了传统 Function Calling 不存在的安全挑战。学术界（HKUST + 华为）提出的 MCIP 框架首次系统性地分析了 MCP 的安全风险，并提出了增强方案。

MCP 安全三层模型

MCIP：MCP 的安全增强方案

HKSUT 和华为联合提出的 MCIP（Model Contextual Integrity Protocol）是 MCP 的安全增强版本。它通过两个核心增强弥补 MCP 的安全缺口：(1) Tracking Tools——追踪工具在上下文中的调用链，识别不合理的工具组合；(2) Guard Model——训练专用的安全分类器，在每次工具调用前评估风险等级。实验显示，MCIP 将最先进 LLM 的 MCP 安全评分提升了 20-35%。

生产数据：Cisco 2023 年企业安全报告显示，41% 的 AI 系统缺乏结构化授权层，这在松耦合的 MCP 架构中尤其危险。Forrester 2024 报告指出，64% 的 IT 决策者因缺乏标准化模型-应用接口而导致 LLM 部署延迟。MCP 的 Session 级访问控制和认证协商机制正是针对这些痛点的解决方案。

十四、技术演进趋势与生态格局

从 Skill 到 MCP 不是终点，而是起点。未来的演进方向是 MCP Marketplace（开放工具市场）+ A2A 协议（Agent 间通信标准化）+ AGENTS.md（Agent 能力自描述标准），三者共同构成完整的 Agent 互操作性生态。

阶段特征代表技术复杂度
农业时代烟囱式孤岛，每个模型配专属工具早期 Agent Skill、厂商私有 Function CallingO(N×M)
工业时代标准化总线，工具即插即用MCP 协议（JSON-RPC 2.0）O(N+M)
网络时代Agent 间标准化通信A2A 协议（Google 提出）、AGENTS.mdO(N) 级别

MCP vs A2A：互补而非竞争

MCP 解决的是"模型与工具的连接"（纵向），A2A 解决的是"Agent 与 Agent 的通信"（横向）。一个完整的多 Agent 系统需要两者配合：MCP 让每个 Agent 能调用外部工具，A2A 让不同 Agent 之间能协商和委派任务。Google 的 A2A 协议和 Anthropic 的 MCP 协议正在走向互操作——2025 年已有多个项目同时支持两者。

核心价值：MCP 实现了生态解耦——模型厂商不需要关心工具有多少，工具开发者不需要关心模型是什么。双方只需要适配 MCP 协议一次，就能互相兼容。截至 2025 年底，MCP 生态已有 2,000+ 社区 Server，覆盖 GitHub、Stripe、Slack、PostgreSQL 等主流服务。Skill 生态则依赖各 IDE 插件市场（碎片化更严重），两者的生态规模差距正在拉大。

Q&A

Skill 和 Tool 到底有什么区别？为什么不直接用更多 Tools 替代 Skills？

本质区别在三个维度：①粒度：Tool 是原子操作（read_file, search），Skill 是多步过程（"从零创建 PR"包含 5 步）；②知识：Tool 只有"怎么执行"，Skill 还包含"什么时候用、为什么这样做、常见坑怎么避"的领域知识；③组合性：Skill 可以调用 Tools 和其他 Skills 形成层级结构。不能用 Tools 替代的原因：如果把"创建 PR"做成单个 Tool，它要么太 rigid（无法适应不同项目的 commit 规范），要么太 complex（参数爆炸）。Skill 通过"注入知识+灵活编排"解决这个矛盾。

如何设计 Skill 的路由系统？当多个 Skill 都匹配时怎么办？

推荐混合路由策略（三级升级）：Level 1 关键词精确匹配（<1ms），Level 2 语义相似度检索（~10ms），Level 3 LLM 判断（~500ms）。多 Skill 冲突解决：①按 specificity 排序（"Python 单元测试" > 通用"测试"）；②按 context 加权；③按历史偏好排序；④若分数差距 < 0.1，主动询问用户消歧。设计原则：路由的"假阴性"（该触发没触发）比"假阳性"（错误触发）更严重。

Skill 的自进化机制是如何工作的？如何保证自动生成的 Skill 质量？

自进化四步流程：①轨迹提取：Agent 成功完成任务后，记录完整工具调用序列；②抽象化：将具体参数替换为变量模板，去除噪声步骤；③质量评估：在相似但不同的任务上测试泛化能力（pass_rate > 0.8 才通过）；④渐进发布：candidate → review → canary（10%流量）→ active。质量保证：a) 多任务测试（不能只在生成它的任务上有效）；b) 与 baseline 对比（必须比没有 Skill 时效率更高）；c) 安全审查；d) 去重检测；e) 持续监控（success_rate 下降则自动回退）。

如何保证第三方/社区 Skill 的安全性？

多层防护体系：①发布前审核：签名验证+自动化安全扫描；②安装时隔离：第三方 Skill 默认在沙箱执行（Docker 容器，无网络、只读 FS、有资源限制）；③运行时权限：Skill 只能使用声明的 tools，每次 tool_call 经过 PermissionGuard 实时检查（类似 Android 权限模型）；④审计追溯：所有操作留日志；⑤社区机制：下载量 + 评分 + verified 标识 + 安全报告通道。企业场景应维护私有 Skill 仓库（内部审核后才能使用）。

Cursor SKILL.md 的"Prompt-as-Skill"模式有什么优缺点？

优点：①极低门槛——写 Markdown 就是写 Skill；②天然灵活——LLM 理解自然语言指令后自主适配；③版本控制友好——纯文本，git diff 清晰可读；④即时生效——保存即可，无需编译/部署。缺点：①可靠性依赖 LLM——不同模型执行效果差异大；②无法保证确定性——关键步骤可能被 LLM "自由发挥"跳过；③调试困难——没有明确的"执行日志"；④性能——每次都要理解整个 SKILL.md。适用场景：80% 的日常 Skill 用 Prompt-as-Skill 足够；需要高可靠性/确定性的关键流程应用状态机实现。

设计一个 Skill 系统时，最容易犯的错误是什么？

五大常见错误：①粒度错误（最常见）——要么太细没价值，要么太粗不可靠。判断标准："2-10 步内可靠完成、有明确结束条件"；②忽视错误处理——Skill 内部每个 tool_call 都可能失败，必须有重试/降级/终止策略；③缺乏可观测性——不知道哪步成功/失败/慢，无法优化；④没有版本管理——Skill 升级直接覆盖，导致依赖方突然出问题；⑤信任边界模糊——没区分"自己写的"和"第三方"的权限级别。修正思路：从小开始（3-5 个核心 Skill），每个 Skill 有测试+监控，确认可靠后再扩展。

Agent Skill、Function Calling 和 MCP 的本质区别是什么？
三者解决不同层面的问题：Function Calling 是意图生成层（模型表达"我想做什么"，输出结构化 JSON 请求）；MCP 是执行基础设施层（标准化工具发现、调用和管理，基于 JSON-RPC 2.0 的客户端-服务器架构）；Skill 是行为知识层（通过 Markdown 注入过程性知识，教模型"怎么做"）。本质区别在于耦合方式：Skill/Function Calling 是高耦合的烟囱式架构 O(N×M)，MCP 是标准化的总线式架构 O(N+M)。
MCP 落地最大的工程挑战是什么？
四大难点：(1) 上下文膨胀 — 工具多时全量注入导致 Prompt 过长，需要动态路由+RAG 按需加载，可降低 Token 消耗 60-80%；(2) 安全风险 — 包括工具注入、权限提升、数据泄露、删库风险，需要三层安全模型（传输/认证/运行时）+ 人机回环 + RBAC；(3) 存量迁移 — 已有 Skill 不能全部重写，需要适配器模式自动转换函数签名，降低 80% 迁移工作量；(4) 参数幻觉 — 模型常丢失必填参数，需要 Pydantic 强校验+重试，将错误率从 12% 降至 <1%。
为什么 O(N×M) 到 O(N+M) 的复杂度降低如此重要？
因为这决定了生态能否规模化扩展。假设 10 个模型 × 100 个工具：Skill 模式需要 1000 次适配，MCP 只需 110 次。当工具从 100 增长到 10,000 时，Skill 需要 100,000 次适配，MCP 仅需 10,010 次。O(N×M) 的生态无法规模化——每增加一个工具，所有模型都要适配一次；O(N+M) 可以——每个新工具只需实现一次 MCP Server。截至 2025 年底 MCP 已有 2,000+ 社区 Server，验证了 O(N+M) 的生态扩展能力。
什么场景下 Skill 比 MCP 更合适？
三种场景 Skill 更优：(1) 纯本地操作（无网络调用、无副作用）— Skill 延迟更低（50ms vs MCP 的 120ms 网络往返）；(2) 需要深度集成模型上下文 — Skill 可以直接访问模型的中间状态和对话历史，MCP 只能通过标准化的请求/响应接口；(3) 快速原型验证 — Skill 开发周期 1-2 小时（写个函数就行），MCP 需要设计 Server 结构、实现协议握手。但一旦进入生产环境（需要权限控制、审计日志、多用户隔离），MCP 的优势就显现了。
MCP 协议的安全性如何保障？有什么已知风险？
MCP 安全三层：(1) 传输层 — stdio 天然隔离，SSE/HTTP 需要 TLS 加密；(2) 认证层 — OAuth 2.0 + API Key，Session 级作用域限制工具访问范围；(3) 运行时层 — 工具注入检测、操作链路审计、沙箱执行、人机回环。已知风险包括：恶意 MCP Server 返回 Prompt Injection、Agent 组合多工具实现权限提升、Server 返回数据包含其他用户敏感信息。HKUST+华为提出的 MCIP 框架通过 Tracking Tools + Guard Model 将安全评分提升 20-35%。
MCP 和 A2A 协议是什么关系？会互相取代吗？
不会取代，而是互补。MCP 解决纵向连接（模型 ↔ 工具），A2A 解决横向通信（Agent ↔ Agent）。一个完整的多 Agent 系统需要两者配合：MCP 让每个 Agent 能调用外部工具（如查数据库、发 GitHub Issue），A2A 让不同 Agent 之间能协商和委派任务（如研究 Agent 委派数据分析给分析 Agent）。2025 年已有多个项目同时支持 MCP 和 A2A，趋势是走向互操作而非互相取代。
MCP 的动态工具发现是怎么工作的？
MCP Client 在运行时调用 tools/list 获取 Server 暴露的所有工具及其 JSON Schema 描述。如果 Server 新增或删除了工具，它会发送 notifications/tools/list_changed 通知，Client 自动更新可用工具列表——无需重启应用或修改代码。这与传统 Function Calling 的静态注册（每次请求全量注入工具描述）形成鲜明对比。动态发现的优势：(1) 工具变更无需重新部署；(2) 按需加载，不浪费 Token；(3) 支持工具的版本管理和灰度发布。
如何制定 Skill 到 MCP 的迁移策略？
四步迁移策略：(1) 盘点 — 列出所有现有 Skill，按"操作位置（本地/远程）"、"副作用（有/无）"、"权限需求"三个维度分类；(2) 优先级 — 远程调用、有副作用、需要权限控制的 Skill 优先迁移到 MCP；纯本地、无副作用的 Skill 保留；(3) 适配器迁移 — 用 Adapter 包装现有 Skill 函数，自动转换为 MCP 协议格式（JSON Schema 参数映射 + TextContent 返回值包装），降低 80% 迁移工作量；(4) 灰度切换 — 新旧并行运行 1-2 周，对比结果一致性后全量切换到 MCP。
