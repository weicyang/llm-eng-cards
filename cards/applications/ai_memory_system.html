AI Memory Architecture — 四层记忆架构、跨会话个性化、混合检索与异步更新

AI 记忆体系的本质：让 Agent 在有限上下文窗口中'记住'该记的、'忘掉'该忘的——四层记忆架构（核心/瞬时/短期/长期）模拟人类记忆的工作方式。

一、问题背景：为什么不能存储所有历史对话？

核心问题："长期陪伴 AI 的记忆机制如何分层设计才能实现跨轮对话精准不跑偏？"本质是在有限上下文窗口和可控计算成本下，保持跨会话对话连贯性与精准性的问题。

直接存储所有历史的两大致命瓶颈

瓶颈类型具体问题影响
资源与成本内存爆炸：长对话导致上下文长度指数级增长系统不可用
资源与成本Token 成本飙升：商业场景下长期运行成本不可控商业不可行
模型性能注意力稀释：过长上下文导致关键信息被稀释回答质量下降
模型性能响应跑偏：模型容易遗漏细节或偏离主题用户体验崩塌

核心矛盾：用户期望 AI "记住一切"，但 LLM 的 context window 是有限资源。解决方案不是"存更多"，而是"分层存储 + 智能检索"。

  • 先说清楚"为什么不能全存"，再引出分层方案——展示问题分析能力
  • 资源问题可以用数字量化：128K token ≈ 10 万字，一年的对话可能超过 1000 万字
  • 性能问题是"Lost in the Middle"现象——LLM 对中间位置的信息关注度最低

三、Layer 1: 核心记忆 (Core Memory)

定位与作用

核心记忆是 AI 的"人格锚点"——存储角色定位、核心任务、行为准则等静态配置。它作为 System Prompt 的最高优先级部分，确保 AI 在任何对话场景下都保持一致的身份和行为边界。

核心记忆包含的内容

类别内容示例说明
身份定义名称、角色、性格、语言风格AI "是谁"
核心任务日程管理、技术问答、个性化建议AI "做什么"
行为准则不编造事实、隐私保护、风险提醒AI "怎么做"
用户基础信息姓名、偏好语言、交互风格为谁服务

核心记忆的判据只有一条：这条信息如果丢了，Agent 会不会变成另一个人。会，就放进核心记忆；不会，一律往下沉。按这条筛，绝大多数"用户偏好"其实都不该待在这一层。

它和下面三层的根本区别是写入路径不同：瞬时、短期、长期三层都由系统自动写入，核心记忆只能被显式变更触发。这条边界一旦松掉，核心记忆就会慢慢被自动写入的内容撑大，最后既不精简也不稳定。

设计原则

原则说明反例
精简只保留最核心的不变信息把用户所有偏好都放进核心记忆
稳定内容极少变动，变更需显式触发每次对话都更新核心记忆
高优先级在 System Prompt 中占据最前位置被其他上下文信息覆盖
结构化使用 JSON/YAML 等格式便于管理用自然语言堆砌一大段
  • 核心记忆 ≈ System Prompt 的"不可变部分"——它是 AI 行为的基石
  • Token 预算：核心记忆通常控制在 500-1000 token 以内，避免挤占瞬时记忆空间
  • 变更机制：用户说"以后叫我英文名"时，需要专门的记忆更新逻辑，而非直接修改

四、Layer 2: 瞬时记忆 (Transient Memory)

定位与作用

瞬时记忆对应模型的原生上下文窗口——仅保留最近几轮原始交互内容。它是读写延迟最低的记忆层，直接支撑实时交互的流畅性。

滑动窗口淘汰策略

  • 轮次限制：保留最近 3-5 轮对话，更早的消息被丢弃
  • Token 限制：当总 token 超限时，从最早消息开始移除
  • 重要性保留：关键工具调用结果可标记为不可淘汰

瞬时记忆是唯一"零损耗"的一层 —— 原文进、原文出，模型看到的就是用户说的。代价是它按 token 计费还占着最贵的窗口空间，所以这一层的设计目标从来不是多存，而是尽快把该沉的内容沉下去。

三条淘汰规则里最容易出问题的是重要性保留：一旦允许某些消息标记为不可淘汰，滑动窗口就不再是先进先出，而变成了带钉住项的队列。钉住的条目如果没有过期机制，跑久了会把整个窗口占满，反而让最近几轮被挤出去。

瞬时记忆 vs 短期对话记忆

维度瞬时记忆短期对话记忆
内容形式原始消息（未压缩）摘要（已压缩）
保留轮数最近 3-5 轮整个会话的历史摘要
信息保真度100%（原始数据）有损压缩
Token 消耗较高较低
适用场景实时交互、上下文关联紧密长会话中回顾早期内容

关键洞察：瞬时记忆保留"最新鲜"的原始数据，确保当前对话的精准度；更早的内容交给短期记忆层压缩处理。

  • 瞬时记忆就是 LLM 的 context window——最贵但最快的存储
  • 滑动窗口大小需要根据任务调整：客服场景 3-5 轮，编程助手可能需要 10+ 轮
  • Token 预算分配：瞬时记忆通常占据 context window 的 40-60%

五、Layer 3: 短期对话记忆 (Short-term Dialogue Memory)

定位与作用

短期对话记忆解决单次长会话的容量问题——通过大模型将早期对话摘要压缩，在有限 context 中保留更多历史信息。采用"会话后即焚"策略保护用户隐私。

工作流程

原始对话积累到阈值（如 10 轮） ↓ LLM 摘要压缩（保留关键问题、结论、上下文） ↓ 清空原始消息，保留摘要继续对话 ↓ ... 循环压缩 ... ↓ 会话结束 → 提取有价值信息写入长期记忆 → 销毁短期记忆（即焚）

短期记忆本质是拿算力换窗口：花一次 LLM 调用把十轮对话压成一段摘要，换回来的窗口空间可以继续跑几十轮。判断这笔账划不划算，看的是压缩比和压缩延迟，而不是摘要读起来顺不顺。

循环压缩有个隐藏风险叫摘要漂移：第二次压缩的输入里已经包含第一次的摘要，误差会一层层叠上去，跑到第五、六轮时早期事实可能已经面目全非。工程上的常见做法是保留一份未压缩的原始日志作为回捞源，摘要只负责放进上下文，需要核对细节时再从日志里取。

压缩策略对比

策略原理优点缺点
LLM 摘要用大模型生成对话摘要语义保留好，可控制重点消耗额外 token，有延迟
关键句提取用 NLP 提取关键句子速度快，成本低可能遗漏隐含信息
结构化提取提取实体、意图、结论结构化，便于检索丢失对话流畅性
混合策略先结构化提取，再 LLM 摘要兼顾精度和效率实现复杂

"会话后即焚"设计

会话结束时执行三步操作：

  1. 提取：LLM 从短期摘要中识别值得长期保存的信息（用户偏好、重要事实、影响未来交互的上下文）
  2. 写入：将有价值的信息写入长期记忆
  3. 销毁：清空短期记忆的原始数据和摘要

隐私保护的关键：会话结束后不在内存中残留原始对话，"只存结论，不存过程"。

  • 短期记忆的核心价值：让长会话中 AI 仍能"记得"早期讨论的内容
  • "即焚"是隐私保护的关键——会话结束后不在内存中残留原始对话
  • 压缩时机的选择：太早压缩会丢失细节，太晚压缩会超出 context window
  • 进阶要点：提到"异步压缩"——在用户思考/打字时后台执行压缩，不影响响应速度

六、Layer 4: 长期记忆 (Long-term Memory)

定位与作用

长期记忆是实现跨会话个性化的核心——让 AI 在新会话中仍能"记住"用户的偏好、习惯和历史交互中的重要信息。它包含两个子模块。

双模块架构

┌──────────────────────────────────────────────────────────────┐ │ 长期记忆 (Long-term Memory) │ ├──────────────────────────────┬───────────────────────────────┤ │ 实体画像记忆 (Profile) │ 长期情景记忆 (Episodic) │ ├──────────────────────────────┼───────────────────────────────┤ │ • 结构化存储（KV / 关系型DB） │ • 向量化存储（Vector DB） │ │ • 客观事实：姓名、偏好、习惯 │ • 非结构化语义：对话片段、经验 │ │ • 精确匹配检索 │ • 语义相似度检索 │ │ • 高频更新（用户画像演进） │ • 低频更新（重要事件才存储） │ │ • 示例： │ • 示例： │ │ - 职业: 前端工程师 │ - "上次讨论了 React 性能优化 │ │ - 偏好语言: 中文 │ 后，用户成功解决了问题" │ │ - 技术水平: 高级 │ - "用户对代码示例反馈积极" │ └──────────────────────────────┴───────────────────────────────┘

实体画像记忆

  • 存储介质：Redis / PostgreSQL，以 KV 形式存储用户结构化信息
  • 更新方式：会话结束时由 LLM 从对话中提取结构化字段（职业、偏好、技术栈等），增量合并到画像
  • 检索方式：根据查询意图筛选相关字段，精确匹配返回

长期情景记忆

  • 存储介质：Milvus / ChromaDB 等向量数据库
  • 存储时机：只对重要性评分 > 阈值的情景进行存储
  • 检索排序：综合得分 = 0.6 × 语义相关性 + 0.2 × 时效性 + 0.2 × 重要性
  • 记忆清理：定期删除低重要性 + 长时间未访问的记忆，防止噪声累积

两种记忆的协作

场景实体画像记忆长期情景记忆
用户说"继续上次的话题"—检索上次对话的摘要
用户问"你知道我是做什么的吗？"返回 occupation 字段—
用户问"我之前那个问题解决了吗？"—检索相关问题的情景记忆
AI 调整回答深度读取 expertise_level参考历史交互反馈
  • 长期记忆本质上是"以用户为中心的 RAG"——检索的是用户历史信息而非通用知识
  • 实体画像适合"是什么"类问题（职业、偏好），情景记忆适合"发生了什么"类问题（历史事件）
  • 排序公式是核心亮点：similarity × recency × importance，而非单纯按相似度排序
  • 记忆清理（prune）很重要——不清理会引入噪声，降低检索质量

七、关键技术实现

7.1 异步更新机制

记忆更新不应阻塞主对话流程——采用"主线程优先响应，后台线程静默更新"的异步模式。

步骤线程操作
1主线程生成响应并立即返回给用户
2后台线程LLM 提取实体信息 → 更新用户画像
3后台线程评估情景重要性 → 超过阈值则写入情景记忆
4后台线程更新失败不影响用户体验，log warning 后下次重试

工程实现版（影子 Agent、冲突检测与版本控制）见 M08 · AI 长期记忆架构。

7.2 混合检索策略

检索类型针对记忆方式延迟
结构化精确匹配实体画像根据查询意图筛选相关字段，KV 查询<5ms
语义相似度召回情景记忆Query embedding → 向量 ANN 检索10-100ms
上下文感知调整—后续问题侧重情景记忆，画像类问题侧重结构化数据—

混合检索之所以要分两路，是因为两类问题的失败方式完全不同。"我叫什么"答错是硬错误，只能靠精确匹配；"上次聊了什么"答得不全只是体验差一点，语义召回够用。用一路检索通吃，必然在其中一类上翻车。

7.3 动态资源分配

Context Window 空间的典型分配比例：

这张表定义的是配额上限而不是固定占位：某一层没用满时，多出来的额度可以让给其他层，但任何一层都不能越过自己的上限去抢。这样既避免了长期记忆检索出一大堆内容把瞬时记忆挤没，也保证了响应预留那 20% 永远不会被侵占 —— 那部分一旦被占，模型会直接在生成中途被截断。

组件占比说明
System Prompt5%系统指令
核心记忆8%角色、规则等静态配置
检索到的长期记忆15%画像 + 情景记忆
短期摘要12%早期对话的压缩摘要
瞬时记忆40%最近几轮原始对话
响应预留20%模型生成回复的空间

进阶：可根据对话类型动态调整占比——如技术讨论增大瞬时记忆比例，个性化闲聊增大长期记忆比例。

  • 异步更新是生产级系统的标配——记忆更新延迟不应影响用户体验
  • 混合检索的优势：画像信息精确匹配（"我叫什么"），情景信息语义召回（"上次聊了什么"）
  • 动态资源分配是核心难点——如何在有限 context window 中平衡各层记忆的空间
  • 进阶要点：提到"自适应分配"——根据对话类型动态调整各层占比

生产案例

三大产品级记忆系统（Claude Code / OpenViking / Hermes）的实测数据与选型建议见 M04 · 三大 Agent 记忆系统终极对决。

  • 分层存储：核心记忆（常驻）+ 瞬时（当前对话）+ 短期（近期）+ 长期（历史）
  • 产品选型：编码 → Claude Code / 知识库 → OpenViking / 长期运维 → Hermes，详见 M04 · 三大 Agent 记忆系统终极对决
  • 会话结束后清除原始对话（"只存结论，不存过程"）
  • 动态调整各层占比（技术讨论增大瞬时，闲聊增大长期）
  • 不要全量保留所有对话历史（context 窗口爆炸）
  • 不要忽略记忆质量衰减（长期运行后噪声累积）
  • 不要用单一策略应对所有场景（编码/对话/知识库需求不同）
  • 不要忽视隐私保护（会话结束后不残留原始数据）

Q&A

四层记忆架构中，哪一层最关键？为什么？

长期记忆最关键。原因：①它是实现"跨会话个性化"的唯一手段——没有长期记忆，每次新会话 AI 都是"失忆"状态，用户体验与普通 ChatBot 无异；②它包含两个子模块（实体画像 + 情景记忆），需要同时解决结构化精确检索和非结构化语义召回两个技术难题；③它涉及数据持久化、隐私保护、记忆清理等工程挑战。同时也要强调：四层缺一不可——核心记忆保证一致性，瞬时记忆保证实时性，短期记忆保证长会话质量，长期记忆保证个性化。

长期记忆的"混合检索"具体怎么实现？如何保证检索质量？

混合检索 = 结构化精确匹配 + 语义相似度召回。实现：①实体画像记忆用 KV 存储（Redis），根据查询意图筛选相关字段直接返回，延迟 <5ms；②情景记忆用向量数据库（Milvus/ChromaDB），将查询 embedding 后做 ANN 检索，延迟 10-100ms。保证检索质量的三个手段：①排序公式综合 similarity × recency × importance，避免只按相似度排序导致过时信息排前面；②记忆清理机制定期删除低重要性+长时间未访问的记忆，减少噪声；③查询改写——将用户的模糊问题改写为更适合检索的形式（类似 RAG 中的 query rewriting）。

"会话后即焚"会不会导致信息丢失？如何平衡隐私和记忆？

不会丢失关键信息，因为"即焚"之前有一个"提取-存储"步骤。流程：会话结束 → LLM 从短期记忆中提取有价值的信息 → 写入长期记忆 → 销毁短期记忆原始数据。平衡隐私和记忆的关键是"只存结论，不存过程"——长期记忆存储的是"用户是前端工程师"这样的结论性信息，而非"用户在第 15 轮提到他在做 React 项目"这样的原始对话。这既保护了隐私（不保留完整对话记录），又保留了个性化所需的关键信息。GDPR 合规角度：用户有权要求删除所有记忆，系统需要提供"一键遗忘"功能。

如何解决"注意力稀释"问题？长上下文中关键信息被忽略怎么办？

三个层面的解决方案：①架构层面——四层记忆本身就是解决方案，通过分层存储避免将所有信息塞进一个超长 context；②注入策略层面——将关键信息放在 context 的开头或结尾（利用 Primacy & Recency Effect），避免放在中间（Lost in the Middle 现象）；③检索层面——混合检索只召回最相关的信息，而非全部历史，减少无关信息的干扰。额外技巧：对重要信息添加标记（如"[重要] 用户的偏好是..."），引导模型注意力；使用 Structured Output 强制模型在回答前先列出参考的记忆片段，确保关键信息被"看到"。

异步更新会不会导致记忆不一致？如何处理并发问题？

异步更新确实存在一致性风险，但在记忆系统中这是可接受的权衡。原因：①记忆更新是"最终一致性"而非"强一致性"——晚几秒更新画像不影响当前对话；②主线程读取的是"上一次会话"写入的记忆，当前会话的更新在下次会话才生效，这符合直觉。处理并发：①画像更新使用"读取-合并-写入"的原子操作（Redis 的 WATCH/MULTI 或数据库事务）；②情景记忆使用 append-only 写入，不存在并发冲突；③关键设计：记忆写入失败不应影响用户体验——catch exception 并 log warning，下次再重试。

MemGPT 和这个四层架构有什么关系？有什么异同？

MemGPT（Packer et al., 2023）是四层架构的一个具体实现参考。相同点：①都采用分层存储——MemGPT 分 main context / archival memory / recall memory 三层；②都通过 LLM 自主管理记忆——决定何时存储、何时检索、何时压缩。不同点：①MemGPT 让 LLM 自己决定记忆操作（通过 function calling 调用 store/recall），而四层架构通常用规则+启发式策略驱动；②MemGPT 的 archival memory 是无限的（外存），但检索依赖 LLM 的查询质量；③四层架构更强调异步更新和隐私保护（即焚机制），MemGPT 论文中未重点讨论这些工程问题。可以说"四层架构是设计原则，MemGPT 是实现方案之一"。
