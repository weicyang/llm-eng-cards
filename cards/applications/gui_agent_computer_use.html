26 · GUI Agent

没有 API 的系统怎么自动化 —— 难点不在「让模型点按钮」，而在感知得准、定位得稳、执行得可回滚

GUI 自动化真正的敌人不是「模型不会点」，而是「点了之后什么都没发生，而系统不会告诉你」。API 失败会返回 500，GUI 失败只是画面纹丝不动——所以这类系统的全部工程量，都花在把不可见的失败变成可见的失败上。

一、没有 API 的系统，为什么只能走 GUI

把 Agent 接到业务系统上，第一选择永远是调 API。但真实企业里有一大片系统根本不给你这个选择：十几年前上线的 ERP 和用友金蝶老版本，只有 Windows 客户端；行业主管部门的申报门户，登录之后全靠人点；采购来的 SaaS 后台，公开 API 只覆盖了它想让你自动化的那两成功能，剩下八成藏在管理页面里；还有大量公司内部自研的运营后台，当年写的时候压根没打算给机器调用，接口散落在页面控制器里、跟会话状态绑死、没有文档也没有版本。这些系统的共同点是：界面是唯一的、也是完整的入口。

GUI Agent 指的就是让模型像人一样通过图形界面操作软件的一类系统——看屏幕、移动鼠标、敲键盘、判断结果，Anthropic 的 Computer Use、OpenAI 的 Operator 都属于这条路线。它的价值主张很朴素：不需要对方配合，就能把任何系统接进自动化流程。代价是，你放弃了 API 提供的一整套确定性保障。

GUI 和 API 的四条根本差异

很多团队第一次做 GUI Agent 会栽跟头，原因是把它当成「换了个调用方式的 API 调用」。这两者的差别不是接口形式，而是可靠性模型：

维度API 调用GUI 操作工程后果
契约稳定性接口有版本号，破坏性变更有公告和灰度期界面随时可能改版，供应商不会通知你必须有变更检测，不能假设「昨天能跑今天也能跑」
状态可查询随时 GET 一次就知道当前状态只能看到当前这一屏，屏幕外的状态不可知必须靠导航去「翻」状态，每次翻都可能失败
幂等性可设计成幂等，重试安全点两次提交就是提交两单重试前必须先判断上一次是否已生效
失败信号非 2xx 状态码 + 错误体，机器可判别失败往往表现为「界面没有任何变化」失败必须由自己主动断言出来，而不是等着被告知

第四条是最致命的。API 调用失败时你会拿到一个明确的错误码，可以据此决定重试还是上报；GUI 里一次被浮层吞掉的点击、一次因为按钮处于 disabled 状态而无效的操作、一次因为焦点跑到别的输入框而打飞的键入，在 Agent 的观测里和成功完全一模一样——都是「我发出了一个 click，没有异常抛出」。如果不主动去验证结果，Agent 会带着一个错误的世界模型继续往下走，而且走得越远错得越离谱。

API 的失败会喊出声，GUI 的失败是沉默的。所以 GUI Agent 的可靠性上限，等于你为「沉默失败」写了多少条断言。

一个务实的判断：GUI 是兜底，不是首选

在架构评审上遇到「这个系统要不要上 GUI Agent」，判断顺序应该是：先问有没有官方 API；没有官方 API，就问能不能抓包复用它自己前端在调的内部 HTTP 接口（很多老后台的页面本质上还是 XHR 驱动，抓出来直接调比点界面稳一个量级）；内部接口也走不通——比如全是服务端渲染的表单提交、或者带了前端计算的签名参数——才轮到 GUI。

这个顺序背后是成本账：同一个业务流程，调 API 的实现可能是两百行代码加一套重试，跑起来单步几十毫秒、成功率四个九；换成 GUI，实现量翻几倍，单步要花一到三秒（截图、模型推理、渲染等待），成功率能做到 95% 就算不错，而且每次对方改版你都要再修一轮。GUI Agent 的合理定位是打通那些原本只能靠人力录入的最后一公里，不是用来替换已经跑得好好的接口集成。

二、三条感知路线：结构树、纯视觉与 Set-of-Mark

Agent 要操作界面，先得「看见」界面。怎么把一个屏幕变成模型能理解的输入，是 GUI Agent 最基础也最分化的设计选择。业界收敛出来三条路线，它们不是互斥的技术代差，而是覆盖面、成本、定位精度之间的三角权衡。

路线一：DOM 与无障碍树

无障碍树（accessibility tree）是操作系统或浏览器为读屏软件维护的一棵语义树，每个节点带着 role（这是按钮还是链接）、name（可读名称）、state（是否禁用、是否选中）。它天生就是为「非视觉地理解界面」设计的，拿来喂模型正合适：结构化、语义明确、比原始 HTML 紧凑得多，而且元素引用是稳定的句柄而不是坐标。Playwright 的 getByRole 定位器走的就是这套语义。

它的问题是覆盖不全。Canvas 画出来的表格、WebGL 渲染的图表、自绘控件的桌面应用、封装不规范的 Shadow DOM 组件，在无障碍树里可能就是一个空节点或者干脆没有节点。你能看到画面上有个按钮，树里却什么都没有。跨 iframe、跨窗口的场景还要额外处理上下文切换。所以纯结构树路线在标准 Web 后台上很好用，一碰到富交互界面或者原生桌面就会大面积失明。

路线二：纯视觉截图

截一张图直接扔给多模态模型，让它输出要点的像素坐标。这条路线的优点无可替代：只要人眼能看见，它就能看见，不挑技术栈，不需要注入脚本，远程桌面和虚拟机里的画面同样适用。Anthropic 最早的 Computer Use 就是这个形态。

代价是三重的。一是 token：一张 1080p 截图按主流视觉编码大概要一千五到两千 token，一个二十步的任务光观测就要几万 token，还要乘以每步都重截的次数。二是定位（grounding）——让模型从图像回归出精确坐标，是当前视觉语言模型最薄弱的能力之一，OSWorld 论文（arXiv 2404.07972）在首发时的分析里就把 GUI grounding 列为失败主因。三是小目标：十几像素的图标、密集表格里的单元格、下拉列表中相邻的两项，识别率会明显下滑。

路线三：Set-of-Mark 混合（当前的实用标准）

Set-of-Mark（SoM）的思路是把「定位」这个模型最不擅长的任务，换成「选择」这个它最擅长的任务。做法是：先用 DOM/无障碍树或者视觉检测模型抽出画面上所有可交互元素，在截图上给每个元素叠加一个编号角标，同时给模型一份编号到元素描述的清单，然后要求模型输出编号而不是坐标。运行时拿编号反查真实句柄再执行。

第 1 步 抓取候选元素 ├── 来源 A：DOM / 无障碍树，过滤出「可交互 + 视口内 + 未被遮挡」的节点 └── 来源 B：视觉检测模型，直接框出按钮、输入框、图标（补 Canvas / 桌面控件） │ ▼ 第 2 步 去重与编号 ├── 合并重叠框（IoU 高于阈值视为同一元素，优先保留 DOM 侧的那个） ├── 剔除不可见 / 被遮挡 / 尺寸过小的框，避免编号被垃圾元素占满 └── 按阅读顺序（上→下、左→右）分配编号 1..N，同一页面多轮之间保持稳定 │ ▼ 第 3 步 双通道渲染 ├── 视觉通道：截图上叠加编号角标 + 半透明描边（角标要避开元素本身文字） └── 文本通道：一份元素清单，补上视觉看不出的语义 [12] button "提交订单" 区域=结算卡片 状态=enabled [13] input "优惠码" 区域=结算卡片 当前值="" │ ▼ 第 4 步 模型输出编号，不输出坐标 click([12]) ──→ 运行时按编号反查句柄 ──→ 执行 编号查不到 ──→ 重新截图重新标号，而不是猜一个坐标

为什么这条路线成了实用标准？因为它同时吃到了两边的好处：视觉通道保证覆盖面（Canvas 里的东西检测模型能框出来），编号输出保证定位精度（模型只要说「17」，不用说「x=1043, y=628」）。GUI-Primitives 这项针对 GUI 空间推理的研究（arXiv 2608.21832）做过一个很说明问题的对照实验——在把候选元素显式标出来之后，选择准确率提升了 35 到 57 个百分点，其中 GPT-5 从 30% 升到 87%。虽然那是个给定候选集的上界实验、不能直接当作可部署方法的收益，但它足以说明一件事：模型缺的往往不是「知道该点哪个」，而是「把知道的东西转成准确坐标」的能力。

值得补一句反直觉的证据：并不是观测越精简越好。一项关于 Web Agent 观测缩减的研究（arXiv 2604.01535）发现，能力更强、思考预算更大的模型拿到完整 HTML 反而比拿精简无障碍树表现更好，最大差距到 17.5 个百分点，因为强模型能利用 HTML 里的层叠和布局线索来避免定位错误；而弱模型在长输入下更容易幻觉出不存在的元素引用。所以观测形态的选择要跟模型能力一起定，不能一刀切地追求「越省越好」。

Set-of-Mark 的本质是一次任务替换：把模型不擅长的「从图像回归坐标」，换成它非常擅长的「从列表里挑一项」。定位这件事交给确定性的程序，判断这件事才交给模型。

三、定位与自愈选择器

就算感知这一环解决了，定位仍然是 GUI Agent 最大的脆弱点。原因在于：屏幕上的一切位置信息都是派生的，不是本质的。同一个「提交订单」按钮，在 1920×1080 全屏浏览器里坐标是一个值，用户把窗口拖窄一点是另一个值，系统缩放设成 125% 又是一个值，页面往下滚了三百像素还是另一个值。更麻烦的是动态布局：上方多加载出一条促销横幅，或者某个异步区块从骨架屏切成真实内容，整页元素都会重新流一遍。

这就是为什么坐标不该被持久化。坐标可以作为一次点击的最终产物，但绝不能作为跨会话、跨步骤复用的元素身份。元素的身份应该由更稳定的信号来承载。

自愈选择器：把身份做成多信号指纹

自愈选择器的核心思想来自 UI 测试领域：不要只存一个定位符，而是给每个元素存一组信号构成的指纹——稳定 id、role 加可访问名称、可见文本、在页面结构中的相对位置、周围的锚点元素。当主信号失效时，用剩下的信号重建定位，并且把这次「愈合」记录下来交给人复核。

语义回退与邻居锚定

语义回退指的是当所有结构化定位都失败时，降级到自然语言描述去找：「找那个写着『提交订单』的按钮」。这一步交给多模态模型在截图上做，成功率不如结构定位，但它能救回相当一部分「界面还在、只是我们的选择器过时了」的情况。关键是要给它足够的上下文约束——不是「找提交按钮」，而是「在结算区域内、位于优惠码输入框下方的那个主按钮」，否则页面上如果有多个提交按钮，它会挑错。

邻居锚定是应对动态列表最有效的手段。假设你要在一个订单列表里点击「订单号 A20260315」那一行的「详情」按钮，直接定位「详情」按钮是没有意义的——每行都有一个。正确做法是两段式：先用稳定信号（订单号这个文本本身）定位到那一行的容器，再在这个容器的子树内部找「详情」。这样即使列表顺序变了、分页了、上面插了几条新订单，定位依然成立。更一般地说，就是用页面上语义唯一的东西作参照系，去定位语义不唯一的东西。

示例场景：坐标方案在一次改版后断崖式下跌

背景——某保险公司的理赔录入走的是外采的理赔管理系统，供应商不提供 API，此前全靠三个人手工录入。团队上了一套 GUI Agent，用纯截图加像素坐标的方案，每天自动处理约 1,200 单，稳定运行了两个多月，成功率保持在 91% 上下。

问题——供应商推了一个小版本更新，把左侧导航栏从 220px 加宽到 260px，同时在表单顶部加了一行合规提示条。整页元素横向右移 40px、纵向下移约 34px。当天上午成功率从 91% 跌到 12%。真正糟糕的不是失败率，而是失败形态：偏移后的坐标很多时候仍然落在某个按钮上，只是落在了旁边那个。当天有 300 多单把「暂存」点成了「驳回」，而 Agent 全程没有报出任何异常。

方案——三件事同时做。感知层从纯坐标改成 Set-of-Mark，模型只输出编号；定位层引入六信号指纹与愈合日志；同时推动供应商在下个版本给关键按钮加上稳定的 data-* 标识，作为合同附加条款写进了后续的服务协议。

效果——改版当天切到 SoM 兜底方案后成功率恢复到 78%（主要损失在几个 Canvas 渲染的图表区域），两天后补齐邻居锚定规则升到 94%，误点数归零。更大的收益在运维上：愈合事件日志会直接指出「哪几个元素这一轮是靠降级信号找到的」，等于自动生成了改版影响面清单，把定位人工修复的时间从原来的三天压到 40 分钟。

这个收益量级和 UI 测试领域的公开数据是吻合的。一项对比传统 Selenium 与 Healenium 自愈栈的实证研究（IJAM，2026）报告自愈机制能把定位类失败减少 40% 到 60%、维护工作量减少 30% 到 50%，代价是少量执行开销。GUI Agent 面对的界面波动只会比测试套件更剧烈，所以这套机制的价值更高。

坐标是元素的影子，不是元素本身。任何把坐标当作元素身份存下来的设计，寿命都只到对方下一次改版为止。

四、界面表示的裁剪

把一个真实的企业后台页面的完整 DOM 序列化出来，几万 token 是常态——层层嵌套的容器 div、动辄上百个类名的 class 属性、埋点和 A/B 实验塞进去的 data 属性、内联的样式和事件处理器、还有几百行根本不在视口里的表格数据。直接把这坨东西喂给模型有两个后果，而第二个比第一个严重得多。

第一个后果是贵和慢：一个二十步的任务，每步四万 token 的观测，光输入就八十万 token。第二个后果是准确率下降——关键信息被淹没在噪声里，模型更容易挑错元素，也更容易幻觉出一个页面上不存在的元素引用。所以裁剪不是纯粹的省钱手段，它同时是准确率手段。

原始 DOM ≈ 48,000 token │ ├─ ① 视口过滤 只保留可见且在视口内的节点（含向下预取约一屏） │ display:none / visibility:hidden / 零尺寸 / 被遮挡 → 全丢 │ ├─ ② 可交互过滤 保留 button / a / input / select / textarea │ 以及带 role、tabindex、点击处理器的自定义组件 │ 纯展示容器只保留「有文本内容」的那些 │ ├─ ③ 属性剪枝 丢掉 style / class / 埋点 data-* / 内联脚本 / 长 URL 查询串 │ 保留 id / name / role / aria-* / type / value / disabled │ ├─ ④ 结构折叠 同构列表项保留前若干条 + 一行摘要 │ 「…还有 47 条同类行，字段结构一致」 │ └─ ⑤ 文本截断 超长文本节点只留首尾片段，中间省略 │ ▼ 裁剪后 ≈ 3,400 token（约原始的 7%） + 一张下采样截图（长边限制在 1024~1280，保留可读性即可） + 一份 Set-of-Mark 编号清单（只列本轮真正可点的元素）

五类裁剪策略与取舍

策略做什么典型收益风险
视口过滤只保留当前屏可见元素最大的一块，常占总削减量一半以上目标在屏幕外时会「看不见」，需要配套滚动搜索
可交互过滤只留能点能填的元素显著丢掉纯文本会让模型读不到关键提示（如错误信息）
属性剪枝去样式、去埋点、去内联脚本中等，但几乎无损极少，注意别把 aria-* 和 disabled 一起丢了
结构折叠同构列表只留样本 + 计数列表页上收益极大需要「按需展开」的机制，否则做不了全量遍历任务
文本截断长文本留首尾小截断点可能正好切掉关键数字

关于裁剪能带来多少，有公开的量化参考：Region4Web 提出的 PageDigest 方法（arXiv 2605.07134）在 WebArena 上把平均观测长度从 6,437 token 降到 3,671 token（约减少 43%），同时任务成功率平均还提升了 2.3 个百分点。注意这里两件事同时发生——省了 token，成功率没降反升，这正好印证了前面说的「裁剪也是准确率手段」。

截图侧的裁剪

截图这一侧同样要做取舍，但可调的旋钮不一样。分辨率下采样是最直接的：把 1920×1080 降到 1280×720 大致能省掉一半 token，代价是小图标和密集文字变糊。经验上，只要页面主体文字在下采样后仍然可读，模型的判断质量基本不受影响；一旦文字糊到人眼要凑近看，识别率就开始掉。

关键区域裁切是另一条路：不发整屏，只发当前任务相关的那块区域，比如只发表单区、只发弹窗。省得更多，但风险也更大——如果任务的关键线索（顶部的错误提示条、右上角的账号切换状态）恰好在裁掉的部分里，模型就会做出基于残缺信息的判断。比较稳的折中是两级发送：默认发一张下采样全屏图供模型建立全局理解，模型如果表示某个区域看不清，再针对那块发一张原分辨率的局部放大图。这样把高分辨率的预算只花在真正需要的地方。

上下文预算的通用分配原则不在本卡展开，可以参考《上下文工程：Agent 上下文的组织与管理》（A36）；本卡只讲界面这一类观测特有的压缩手段。

裁剪不是为了省钱才做的妥协，而是提高准确率的手段本身。模型在三千 token 的干净界面表示上，比在四万 token 的原始 DOM 上判断得更准。

五、执行契约：先验证，再动作

前面三节解决的是「看得见、找得着」，这一节解决「做得对」。GUI Agent 里最容易被跳过、也最不该被跳过的设计，是给每一步动作套一个执行契约：动作之前必须验证前提成立，动作之后必须验证结果发生。少了前者，Agent 会往一个不存在或者不可用的元素上发指令；少了后者，Agent 会在一次静默失败之后继续往下跑，而且越跑越错。

前置断言：不做假设，只做检查

前置断言要检查的不只是「元素在不在」。一个完整的前置检查至少包含四项：当前页面是不是我以为的那个页面（会话过期跳登录页是最常见的意外）、目标元素在 DOM 里存在、它处于可见且未被遮挡的状态、它当前是 enabled 而不是 disabled。第三项特别容易漏——全屏浮层、Cookie 同意条、新功能引导气泡都会把点击吞掉，而元素本身在 DOM 里好端端地存在着。

后置断言：把沉默的失败变成响亮的失败

后置断言是这套契约里投入产出比最高的一环。它的作用是回答一个问题：我刚才那一下，到底起作用了吗？ 可用的判据有好几类，实践中通常组合两到三类使用：

断言类型怎么判适用注意
导航断言URL 或窗口标题按预期变化跳转、翻页、进入详情单页应用可能不改 URL，要看路由状态
元素出现 / 消失预期的新元素出现，或弹窗关闭打开对话框、提交后关闭要设超时，别无限等
状态变化输入框有了值、复选框被勾上、按钮转 loading表单填写受控组件可能延迟同步
反馈信号出现「保存成功」提示或错误消息提交类动作toast 会自动消失，要及时抓
画面差分前后截图像素/结构差异超过阈值Canvas 等无结构可查的界面动画和轮播会造成假阳性
业务回读换个入口把刚写的数据读回来核对高价值写操作最可靠但最慢，只用在关键步骤

最后一类值得单独说：业务回读是唯一能证明「数据真的落库了」的断言。界面上出现「保存成功」只能证明前端认为它成功了。对于金额、库存、状态流转这类关键写操作，值得多花几秒钟换个页面把数据读回来核对一遍。

示例场景：缺少后置断言导致整夜的静默失败

背景——某电商团队在多个平台的商家后台上做批量改价，其中一个平台没有开放改价 API，用 GUI Agent 顶上。每晚凌晨跑一批，约 800 个 SKU，运行了一个季度都没出过事。链路设计得很朴素：搜索 SKU → 进编辑页 → 改价格字段 → 点保存 → 下一个。每一步做了前置检查，但没有任何后置断言。

问题——某天平台上线了一个大促活动的全屏公告浮层，凌晨首次打开后台时会弹出来，需要手动关闭。Agent 的搜索和导航都是通过 URL 直达的，不受影响；改价格字段用的是键盘输入，也侥幸成功了一部分；但「保存」按钮被浮层完全盖住，每一次点击都被浮层吞掉。整个流程没有抛出任何异常——元素存在、点击指令发出、没有报错。Agent 认定成功，继续处理下一个。一夜跑完 800 个 SKU，日志全绿，实际生效 0 个。第二天早上运营团队按照「已完成改价」的报告发了大促推送，用户看到的还是原价，客服在两小时内接到 400 多个投诉。

方案——补三层防护。第一层，每次保存后必须命中两个判据之一才算成功：出现「保存成功」提示，或者返回列表页后该 SKU 的价格字段确实等于目标值（业务回读）。第二层，加一个批次级熔断：连续 3 步后置断言判定为「界面零变化」，立即停止整批并告警，因为这几乎一定意味着环境出了系统性变化而不是单个元素的问题。第三层，每次点击保存前存一张证据截图，事后能直接看到当时屏幕上有什么。

效果——后续三个月里同类静默失败又出现了 7 次（浮层、灰度弹窗、会话过期跳转各有几次），全部在第 1 到 2 步就被熔断拦下，平均 12 秒内停机告警，单次事故影响从 800 个 SKU 降到 2 个以内。代价是人工介入率从接近 0 上升到 1.8%，也就是每晚平均有 0.2 次需要人来看一眼，团队认为这个交换非常划算。

不可逆动作与重试判定

GUI 动作绝大多数不幂等——点两次「提交订单」就是两张订单，点两次「发送」就是两封邮件。这让重试变成了一件危险的事：一次超时之后，你并不知道请求是没发出去，还是发出去了但界面没来得及更新。所以重试之前必须先做一次状态查询，判断上一次到底生效没有。如果判断不出来，正确做法是冻结现场转人工，而不是赌一把。重试的通用策略、幂等键的设计方法见《AI Agent 幂等性设计》（A59）与《Agent 系统失败处理策略》（A60），本卡只强调 GUI 场景的额外约束：这里连「上一次生效没有」都需要靠界面去推断，本身就是一次可能失败的观测。

对于提交、支付、删除、群发这类不可逆动作，工程上的答案是加人工确认闸门：Agent 把「我准备点这个按钮，当前表单填的是这些值，这是执行前的截图」打包推给人，人点头才继续。闸门要放在动作之前而不是之后，事后审计救不回已经打出去的钱。至于 Agent 运行环境本身的隔离、权限收敛与凭据管理，属于另一个话题，见安全板块的《Agent Sandbox 架构》（SEC09）与《AI Agent 沙箱与安全执行》（SEC13）。

  • 每一步都写后置断言，哪怕只是「URL 变了」这种最粗的判据，也远好过没有。
  • 关键写操作用业务回读做终判：换个入口把数据读回来核对，而不是相信界面上的成功提示。
  • 点击前显式检查遮挡，把浮层、Cookie 条、引导气泡当成常态而不是意外，进入页面第一件事就是尝试清场。
  • 加批次级熔断：连续几步「界面零变化」就整批停机，这类信号几乎一定是系统性问题。
  • 不可逆动作前存证据截图，出事时能直接看到当时屏幕上是什么。
  • 重试前先查状态，查不清就冻结现场转人工，不要赌。
  • 不要把「点击指令没抛异常」当成成功，这是 GUI 自动化里最贵的一个误解。
  • 不要把坐标持久化成元素身份，它活不过对方下一次改版。
  • 不要对不幂等动作做自动重试，尤其是提交、支付、发送这三类。
  • 不要用固定 sleep 等待页面就绪，改用「等待某个断言成立」的显式等待，前者既慢又不可靠。
  • 不要让自愈静默生效，每次降级定位都要留下愈合日志，否则等于把界面改版这件事从视野里抹掉了。
  • 不要在一个页面上同时跑多个并发 Agent 实例，GUI 是共享可变状态，焦点和滚动位置会互相打架。

把每一步都当成一次小事务来做：进入前检查前提，退出前验证结果，中间那一下动作反而是最不需要操心的部分。

六、评测与界面改版运维

通用的 Agent 评测方法论——任务完成率怎么定义、评分器怎么设计、离线集怎么建——在《Agent 评测指标与体系构建》（EV04）里已经讲透，这里只谈 GUI 场景独有的那几个指标，以及一件在别的 Agent 形态里几乎不存在、在 GUI 里却是头号成本的运维负担：界面改版。

成功率之外，还要看四个数

只看任务成功率会掩盖掉很多问题。两个成功率都是 92% 的系统，可能一个平均 8 步完成、几乎不用人管，另一个平均 31 步、每五次就要人来救一次场——后者在生产上是不可用的。GUI Agent 至少要同时盯这几个维度：

指标含义为什么 GUI 场景特别重要
任务成功率端到端完成且结果正确的比例基础线，但单看会误导
步数分布完成任务实际用了几步，看 P50 和 P95步数暴涨通常意味着 Agent 在原地绕圈找不到入口
单步耗时截图 + 推理 + 渲染等待的总和GUI 单步通常 1~3 秒，长流程会被这个数字主导
人工介入率每百次运行需要人处理的次数决定这套系统到底省不省人力，是真正的经济指标
误操作代价做错时的后果严重度与可挽回性GUI 的错误常常直接落到业务数据上，且难以撤销

最后一项是 GUI 特有的，也最容易被忽略。一个 API Agent 调错接口通常拿到的是 400；一个 GUI Agent 点错按钮，可能就是一张真实的驳回单、一笔真实的转账。所以评测报告里不该只有一个成功率百分比，还要有失败的分型统计：多少是「什么都没做成」（安全的失败），多少是「做了错的事」（危险的失败）。这两类的权重完全不同，前者可以重跑，后者要人去收拾。

公开基准与自建回归的分工

OSWorld 和 WebArena 这类公开基准的价值是给出能力上限的坐标系。它们的数字很能说明这个领域的难度：WebArena 论文（arXiv 2307.13854）里人类完成率 78.24%，而当时最好的 GPT-4 方案只有 14.41%；OSWorld 论文（arXiv 2404.07972）里人类是 72.36%，首发时最强模型仅 12.24%。此后两年模型能力有大幅提升，到 2026 年主流评测榜上顶尖模型已经能在这类环境里逼近甚至达到人类基线水平，但更难的长程版本仍然差距明显——OSWorld 2.0 的 108 个长程工作流里，人类完成一个任务的中位耗时约 1.6 小时、一次任务平均需要三百次以上的工具调用，而其早期评测轮次里最好的模型二元完成率只有两成左右。有意思的是失败原因的转移：OSWorld 2.0 的分析指出，模型现在栽跟头的地方已经不是基础的 GUI 操控，而是跟丢约束条件、错过中途出现的信息、该问的时候不问而是猜、以及跳过验证——这几条恰好对应本卡第五节讲的执行契约。

但公开基准替代不了自建回归。基准测的是通用能力，你需要知道的是「我这条报销录入流程今天还能不能跑」。实践中的做法是维护一套业务流程回归集：把线上跑过的真实任务轨迹挑三五十条固化下来，连同当时的界面快照一起存档，每天定时在预发环境跑一遍。它的作用不是评估模型能力，而是当探针用——回归集突然大面积飘红，几乎一定是对方改版了。

界面改版：GUI Agent 的头号运维负担

这是 GUI Agent 和其它 Agent 形态在运维上最大的区别。你的依赖方随时可能在不通知任何人的情况下改掉你的输入格式，而且没有版本号、没有灰度、没有 deprecation 周期。一个成熟的 GUI Agent 系统必须把「改版」当成一个常态事件来设计流程，而不是当成事故来响应。

环节做法目标
变更检测每天定时对关键页面做结构指纹（元素集合哈希）与视觉基线对比在业务任务失败之前先发现改版
愈合日志记录每次降级定位的元素、命中的信号、置信度愈合率突然上升就是改版的早期信号
影响面评估把改动的元素映射到受影响的业务流程清单知道该先修哪条链路
快速修复通道定位规则从代码里剥离成可热更新的配置修一个选择器不需要走完整发布流程
降级预案改版期间自动切到 Set-of-Mark 兜底，或整链转人工宁可慢，不可错

其中「定位规则可热更新」这一条的收益最被低估。如果元素指纹硬编码在代码里，修一个按钮要走代码评审、构建、发布，半天就没了；如果它是一份配置，运维同学看着愈合日志改两行推上去，几分钟就恢复。考虑到改版是一件每月都会发生几次的事，这个差别会被放大成全年好几周的人力。

  • 把公开基准当能力坐标系，把自建业务回归集当日常探针，两者用途不同不能互相替代。
  • 失败要分型统计：「没做成」和「做错了」要分开报，后者才是需要立刻响应的。
  • 愈合率作为一等监控指标上大盘，它比成功率更早预警改版。
  • 定位规则做成可热更新配置，让修选择器不必走发布流程。
  • 对高价值流程保留人工抽检，按比例采样回看执行截图。
  • 不要只用一个成功率数字汇报，它会同时掩盖步数暴涨和误操作。
  • 不要拿公开基准的分数去承诺自己业务流程的可用性，任务分布完全不同。
  • 不要把改版当偶发事故来处理，它是常态，要有常设流程和值班责任人。
  • 不要在没有回滚方案的情况下扩大自动化范围，覆盖面每扩一块，改版的爆炸半径就大一块。

GUI Agent 上线只是开始。真正决定它能活多久的，不是首发那天的成功率，而是对方改版之后你多快能修好——所以要监控的第一指标不是成功率，是愈合率。

Q&A

什么时候该用 GUI Agent，什么时候不该用？
判断顺序是三步：先看有没有官方 API，有就用 API；没有官方 API 就抓包看前端在调什么内部 HTTP 接口，很多老后台的页面本质上是 XHR 驱动的，直接调内部接口比点界面稳一个量级；内部接口也走不通（服务端渲染的表单提交、带前端签名的参数）才轮到 GUI。原因是成本差距很大：同一个流程，API 方案可能两百行代码、单步几十毫秒、成功率四个九；GUI 方案实现量翻几倍、单步一到三秒、成功率能做到 95% 就不错，而且对方每次改版都要再修一轮。GUI Agent 的合理定位是打通那些原本只能靠人工录入的最后一公里，不是用来替换已经跑得好好的接口集成。
DOM、纯截图、Set-of-Mark 三条感知路线各适合什么场景？
DOM 或无障碍树路线 token 最省、定位最准，适合规范的 Web 后台，但 Canvas 自绘内容、WebGL 图表、封装不规范的 Shadow DOM 和原生桌面应用它都看不到。纯截图路线覆盖面无可替代——只要人眼能看见它就能看见，适合远程桌面、原生客户端和探索性任务，代价是 token 贵、坐标定位容易偏、小控件识别率低。Set-of-Mark 是两者的混合：先抽元素再在截图上打编号，让模型输出编号而不是坐标，同时拿到了视觉的覆盖面和结构化的定位精度，是目前生产环境的实用标准，代价是要多维护一条元素抽取与去重管线，且标号质量直接决定效果上限。
Set-of-Mark 为什么能显著提升定位准确率？
因为它做了一次任务替换：把「从图像回归出精确像素坐标」这个视觉语言模型最薄弱的能力，换成「从一个候选列表里挑一项」这个模型非常擅长的能力。定位这件确定性的活交给程序做——由 DOM 或检测模型抽出元素、分配编号、维护编号到句柄的映射；判断该操作哪个元素这件需要理解的活才交给模型。GUI-Primitives 研究（arXiv 2608.21832）的对照实验显示，把候选元素显式标出来后选择准确率提升 35 到 57 个百分点，GPT-5 从 30% 升到 87%。虽然那是给定候选集的上界实验、不能直接当可部署方法的收益看，但足以说明模型缺的往往不是判断力而是坐标转换能力。
什么是自愈选择器，它的多信号指纹怎么设计？
自愈选择器不存单一定位符，而是给每个元素存一组信号构成的指纹，主信号失效时用其余信号重建定位。按改版存活率从高到低排：data-testid 之类的稳定 id 最可靠；role 加可访问名称次之，前端重构时通常保留；可见文本再次，但改文案或做国际化就会失效；邻居锚定（「收货地址卡片里的第一个按钮」）依赖参照物的稳定性；CSS 路径一重构就断；屏幕坐标最脆，换分辨率或滚动就废。匹配时从最稳的信号往下降级，每次降级都要写一条愈合日志交给人复核。必须是一组信号而不是一个更好的信号，因为不同改版类型打掉的信号不同——改文案会同时废掉 role+name 和可见文本，而这时候 CSS 路径反而还活着。
为什么坐标定位天然脆弱？
因为屏幕上的位置信息是派生的而不是本质的。同一个按钮，浏览器全屏和拖窄之后坐标不同，系统缩放 100% 和 125% 不同，页面滚动前后不同；动态布局的影响更大——上方多加载一条促销横幅，或者某个异步区块从骨架屏切成真实内容，整页元素会重新流一遍。最危险的不是坐标失效导致点空，而是偏移后的坐标仍然落在某个按钮上、只是落在了旁边那个，这时候系统会正常执行一个错误的操作而不报任何错。所以坐标可以作为一次点击的最终产物，但绝不能作为跨步骤、跨会话复用的元素身份被持久化下来。
界面表示的裁剪只是为了省 token 吗？
不是，它同时是准确率手段，而且这一点往往更重要。完整 DOM 动辄几万 token，里面绝大部分是嵌套容器、类名、埋点属性和视口外的数据，关键信息被淹没在噪声里之后，模型更容易挑错元素，也更容易幻觉出页面上不存在的元素引用。Region4Web 的 PageDigest 方法（arXiv 2605.07134）在 WebArena 上把平均观测长度从 6,437 降到 3,671 token，同时任务成功率还平均提升了 2.3 个百分点——省了钱，准确率没降反升。不过也有反向证据：另一项研究（arXiv 2604.01535）发现能力强、思考预算大的模型拿完整 HTML 反而比拿精简无障碍树好，最大差 17.5 个百分点，因为它们能利用布局线索避免定位错误。所以裁剪力度要跟模型能力一起定，不能一味求精简。
后置断言为什么是 GUI Agent 里最关键的一环？
因为 GUI 的失败是沉默的。API 调用失败会返回非 2xx 和错误体，机器可判别；GUI 里被浮层吞掉的点击、点在 disabled 按钮上的操作、焦点跑偏后打飞的键入，在 Agent 的观测里跟成功完全一样——都是「发出了 click，没有异常」。没有后置断言，Agent 会带着错误的世界模型继续往下走，越走错得越离谱，而日志全程是绿的。可用的判据分几类：URL 或标题变化、预期元素出现或消失、元素状态变化、成功提示或错误消息出现、前后截图差分，以及最可靠的业务回读——换个入口把刚写的数据读回来核对。界面显示「保存成功」只能证明前端认为成功了，只有回读能证明数据真的落库。
GUI 动作不幂等，失败之后到底该不该重试？
不能直接重试，必须先做一次状态查询判断上一次是否已经生效。点两次提交就是两张订单，点两次发送就是两封邮件，一次超时之后你并不知道操作是没发出去、还是发出去了但界面没来得及更新。正确的流程是三分支：确认已生效就绝不重试、直接走后续；确认未生效才允许一次重试；判断不出来就冻结现场转人工，不要赌。GUI 场景比 API 场景还多一层困难——连「上一次生效没有」这个判断本身都要靠界面观测来推断，而这次观测本身也可能失败。对于提交、支付、删除、群发这类不可逆动作，更稳妥的做法是干脆在动作之前加人工确认闸门，把待执行的操作、表单当前值和执行前截图打包给人过目。
GUI Agent 该盯哪些指标，为什么不能只看成功率？
只看成功率会掩盖两类严重问题。第一类是效率退化：两个成功率同为 92% 的系统，一个平均 8 步完成、几乎不用人管，另一个平均 31 步、每五次就要人救场，后者在生产上根本不可用。所以要同时看步数分布（P50 和 P95）、单步耗时和人工介入率，其中人工介入率是真正的经济指标，它决定这套系统到底省不省人力。第二类是误操作代价：失败必须分型统计，「什么都没做成」是安全的失败可以重跑，「做了错的事」是危险的失败需要人去收拾。GUI Agent 点错按钮可能直接产生一张真实的驳回单或一笔真实的转账，这跟 API Agent 调错接口拿到 400 完全不是一个量级的后果。
界面改版为什么是 GUI Agent 的头号运维负担，该怎么应对？
因为你的依赖方随时可能在不通知任何人的情况下改掉你的输入格式，没有版本号、没有灰度、没有废弃周期——这跟 API 集成有明确契约和公告完全不同。应对要靠一套常设流程而不是事故响应：每天对关键页面做结构指纹和视觉基线对比，在业务任务失败之前先发现改版；把愈合率当一等监控指标上大盘，它比成功率更早预警；维护一套三五十条真实任务的业务回归集每天在预发环境跑，当探针用；把定位规则从代码里剥离成可热更新的配置，让修一个选择器只要几分钟而不是走完整发布流程；改版期间自动降级到 Set-of-Mark 兜底或整链转人工，宁可慢不可错。
