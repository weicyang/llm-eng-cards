S03 · LLM 可观测性

LLM Observability — 全面覆盖链路追踪、质量监控、成本分析与工具生态

一、LLM 可观测性概述

传统系统出故障会喊，LLM 应用出故障会一本正经地胡说八道——监控接口成功率永远是 100%，问题全藏在返回体的文字里。

什么是 LLM 可观测性

LLM 可观测性是指对大语言模型应用的输入、推理过程、输出质量、延迟与成本进行全链路监控和分析的能力。与传统可观测性三大支柱（Metrics / Logs / Traces）不同，LLM 场景还需关注语义层面的质量。

与传统可观测性的区别

维度传统可观测性LLM 可观测性
输出确定性确定性输出（相同输入 → 相同输出）非确定性输出（同一 Prompt 可能产生不同答案）
错误定义异常 / 状态码 / 崩溃幻觉 / 语义错误 / 有害内容 / 遗漏
核心指标延迟 / 吞吐 / 错误率Token 用量 / 成本 / 质量评分 / 幻觉率
日志内容结构化字段自然语言 Prompt & Response（长文本）
数据隐私脱敏字段即可Prompt 可能包含用户 PII

三支柱之外，多出来的那一支

传统可观测性靠指标、日志、追踪三支柱回答"系统健不健康"。LLM 应用要多加一支质量支柱，才能回答"回答对不对"——前三支全绿而第四支塌方，是这类系统最典型的故障形态。

为什么 LLM 应用更需要可观测性

  • 不确定性：相同 Prompt 可能返回不同结果，需要持续监控输出质量
  • 幻觉 (Hallucination)：模型会"编造"事实，必须通过检测及时发现
  • 成本失控：GPT-4 级别模型每百万 Token 数十美元，缺乏监控易超预算
  • 多模型切换：不同模型的质量/延迟/成本差异大，需 A/B 数据驱动决策
  • 复杂链路：RAG、Agent、Multi-step Reasoning 使调试极其困难
  • 合规需求：审计 Prompt 内容、检测有害输出、追踪数据来源
知识要点
  • LLM 可观测性 ≠ 传统 APM，需要语义层面的质量监控
  • 三大核心关注：质量（幻觉/相关性）、延迟（TTFT/TPS）、成本（Token 消耗）
  • 可观测性是 LLM 应用从 PoC 到 Production 的关键一步

二、LLM Tracing

RAG 和 Agent 的调试之所以难，是因为错误会沉默地往下传：检索错了，生成会一本正经地基于错误材料作答。Trace 的价值就是把"从哪一步开始错"钉死。

Trace/Span 概念在 LLM 中的应用

LLM Tracing 借鉴分布式追踪的 Trace/Span 模型，将一次 LLM 调用链路（从用户输入到最终响应）分解为多个可观测的 Span。

核心概念映射

分布式追踪LLM Tracing说明
TraceTrace / Session一次完整的用户请求链路
SpanSpan / Generation链路中的一个操作步骤
ServiceChain / Agent / Tool执行单元
AttributesPrompt / Completion / Token Count记录的元数据

Prompt → Retrieval → Generation 链路追踪

用户输入→ Prompt 构建→ 向量检索→ Rerank→ LLM 推理→ 后处理→ 响应 
Trace: "RAG Question Answering"
├── Span: prompt_template        (2ms)
│     input: user_query
│     output: formatted_prompt
├── Span: vector_retrieval       (120ms)
│     input: query_embedding
│     output: top_5_chunks
│     metadata: {db: "pinecone", index: "docs"}
├── Span: reranker               (45ms)
│     input: query + chunks
│     output: reranked_chunks (top_3)
├── Span: llm_generation         (1800ms)  ← 最耗时
│     input: system_prompt + context + query
│     output: answer
│     metadata: {model: "gpt-4", tokens_in: 2048, tokens_out: 512}
│     └── Span: streaming_chunks (内部)
└── Span: post_processing        (5ms)
      output: formatted_answer
一条 Trace 上每个 Span 必须记录什么，以及脱敏/采样发生在哪里 ┌─ Trace (trace_id, session_id, user_id, tenant_id, app_version) ────────────┐ │ │ │ Span: prompt_build 必记：模板 id + 版本、变量名（不记变量值） │ │ │ │ │ Span: vector_retrieval 必记：query、top_k、召回 chunk 的 id 与分数 │ │ │ 选记：chunk 正文（量大，通常只存引用） │ │ │ ← 检索为空 / 分数普遍偏低，就是问题的起点 │ │ │ │ │ Span: rerank 必记：重排前后的 id 顺序、模型名 │ │ │ │ │ Span: llm_generation 必记：模型名、温度、input/output token 数、 │ │ │ 完成原因（stop / length / 内容过滤） │ │ │ ← finish_reason=length 常被误判成"模型变笨" │ │ │ │ │ Span: post_process 必记：是否触发敏感词过滤、引用是否成功挂载 │ │ │ └────────────────────────────────────────────────────────────────────────────┘ │ │ │ ▼ ▼ ▼ ┌───────────┐ ┌──────────────┐ ┌──────────────┐ │ 脱敏管道 │ │ 采样决策 │ │ 指标聚合 │ │ 写入前完成 │ │ head 采样： │ │ 全量，不采样 │ │ PII → 掩码 │ │ 正常请求 1% │ │ 只留计数与分位│ │ 保留哈希以 │ │ tail 采样： │ │ │ │ 便去重统计 │ │ 慢/错/低分 │ │ │ │ │ │ 一律 100% │ │ │ └───────────┘ └──────────────┘ └──────────────┘ ★ 采样策略搞反是最常见的坑：均匀采 1% 会让"出问题的那 1%"大概率被丢掉 ★ 正确做法是尾部采样——先跑完再决定留不留，慢的、报错的、评分低的全留

Parent-Child Span

Agent 场景下 Span 嵌套更深：

Trace: "Agent Task Execution"
├── Span: planner_llm
│     → 决定使用哪些工具
├── Span: tool_execution_1 (search)
│     ├── Span: query_generation (LLM)
│     └── Span: web_search (API)
├── Span: tool_execution_2 (calculator)
├── Span: synthesizer_llm
│     → 汇总工具结果生成最终答案
└── Span: guardrail_check
      → 安全性/合规性校验
知识要点
  • LLM Trace 的每个 Span 应记录：输入、输出、耗时、Token 数、模型名称、元数据
  • RAG 场景至少包含：Retrieval Span + Generation Span，追踪检索质量和生成质量
  • Agent Trace 中 Parent-Child 嵌套可达 5-10 层，需要树形可视化

三、LangSmith

定位与核心功能

LangSmith 是 LangChain 官方配套的 LLM 开发平台，覆盖调试、测试、评估、监控全生命周期。

核心模块

模块功能典型用途
Tracing自动采集 LangChain 链路调试复杂 Chain/Agent
Evaluation自动化评估 + 人工标注回归测试、质量基线
Datasets管理测试用例Golden Dataset 维护
HubPrompt 模板共享团队协作、版本管理
Monitoring生产环境实时监控延迟/成本/质量 Dashboard

Trace 可视化

# 自动追踪 LangChain 调用
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "ls_..."
os.environ["LANGCHAIN_PROJECT"] = "my-rag-app"

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个有帮助的助手。"),
    ("human", "{question}")
])
llm = ChatOpenAI(model="gpt-4")
chain = prompt | llm
result = chain.invoke({"question": "什么是 LLM 可观测性？"})

评估 (Evaluator)

from langsmith.evaluation import evaluate, LangChainStringEvaluator

# 内置评估器
correctness = LangChainStringEvaluator("qa")       # 正确性
helpfulness = LangChainStringEvaluator("helpfulness") # 有用性
coherence   = LangChainStringEvaluator("coherence")   # 连贯性

# 自定义评估器
def check_no_hallucination(run, example):
    prediction = run.outputs["output"]
    reference  = example.outputs["answer"]
    # 使用 LLM 判断是否存在幻觉
    score = llm_judge(prediction, reference)
    return {"key": "hallucination", "score": score}

results = evaluate(
    my_chain.invoke,
    data="golden-dataset",
    evaluators=[correctness, helpfulness, check_no_hallucination]
)

Dataset 管理 & Hub

  • Dataset：存储 (input, expected_output) 对，支持版本管理、CSV/JSON 导入
  • Hub：Prompt 模板市场，团队可共享/Fork/版本化 Prompt Template
  • Annotation Queue：人工标注队列，支持多人协作打标
知识要点
  • LangSmith 与 LangChain 深度集成，设置环境变量即可自动采集 Trace
  • 评估支持内置评估器 + 自定义评估器 + LLM-as-Judge
  • 适合已使用 LangChain 的团队；非 LangChain 用户集成成本较高
  • 商业产品，Hosted 方案；对数据隐私敏感的团队需评估

四、Langfuse

定位与优势

Langfuse 是开源的 LLM 可观测性平台，支持自部署（Self-hosted），不绑定任何框架。

核心数据模型

Session (会话级别)
└── Trace (一次请求)
    ├── Span (通用操作)
    │     metadata, input, output, duration
    ├── Generation (LLM 调用)  ← 核心
    │     model, prompt, completion,
    │     tokens_in, tokens_out, cost
    └── Event (事件标记)
          name, metadata

集成方式

# Python SDK — 框架无关
from langfuse import Langfuse

langfuse = Langfuse(
    public_key="pk-...",
    secret_key="sk-...",
    host="https://cloud.langfuse.com"  # 或自部署地址
)

# 创建 Trace
trace = langfuse.trace(name="rag-query", user_id="user-123")

# 记录检索 Span
retrieval = trace.span(
    name="vector-search",
    input={"query": "LLM 监控"},
    metadata={"db": "qdrant", "top_k": 5}
)
retrieval.end(output={"chunks": retrieved_docs})

# 记录 LLM Generation
generation = trace.generation(
    name="answer-gen",
    model="gpt-4-turbo",
    input=[{"role": "user", "content": prompt}],
    model_parameters={"temperature": 0.7}
)
generation.end(
    output="LLM 可观测性是指...",
    usage={"input": 1200, "output": 350}
)

# 用户反馈
trace.score(name="user-feedback", value=1, comment="答案很准确")

Session 追踪

通过 session_id 将多轮对话串联：

trace = langfuse.trace(
    name="multi-turn-chat",
    session_id="session-abc-123",  # 同一会话共享 session_id
    user_id="user-456"

  • Langfuse 的核心优势：开源 + 框架无关 + 可自部署
  • 数据模型：Session → Trace → Span / Generation / Event
  • 成本计算是内置能力，自动按模型单价 × Token 数计算
  • 与 LangSmith 对比：Langfuse 更灵活但生态集成不如 LangSmith 深入

五、Phoenix (Arize)

定位

Phoenix 是 Arize AI 开源的 LLM 可观测性工具，侧重评估、Embedding 可视化、检索质量分析，特别适合 RAG 应用调优。

核心能力

  • LLM Tracing：兼容 OpenTelemetry，支持 OpenAI/LangChain/LlamaIndex 等
  • LLM Evaluation：内置 hallucination / QA / toxicity 等评估模板
  • Embedding 可视化：UMAP 降维，查看 Query-Document 的向量空间分布
  • Retrieval 分析：NDCG / Precision@K / Hit Rate 等检索质量指标

六、Token 用量监控

Token 是 LLM 应用里唯一同时决定延迟、成本和上下文上限的量。盯住它，等于同时盯住了三条曲线。

为什么 Token 监控至关重要

⚠ 成本风险

一次失控的循环调用可能在数小时内消耗数千美元。Token 监控是 LLM 应用的成本生命线。

按维度统计 Token 消耗

统计维度用途典型实现
按用户识别高消耗用户、防滥用user_id → 累计 Token
按模型对比不同模型的性价比model_name → Token + Cost
按功能识别最耗资源的功能feature_tag → Token
按时间趋势分析、容量规划hourly/daily 聚合
Input vs Output优化 Prompt 长度prompt_tokens / completion_tokens

成本归因 (Cost Attribution)

成本归因要求每条计费记录都带上用户、团队、功能三个标签，否则账单只能看到总数、看不出该优化谁。

# 成本归因结构
cost_record = {
    "trace_id": "abc-123",
    "user_id": "user-456",
    "team": "search-team",
    "feature": "rag-qa",
    "model": "gpt-4-turbo",
    "input_tokens": 2048,
    "output_tokens": 512,
    "cost_usd": 0.036,          # 自动计算
    "timestamp": "2025-01-15T10:30:00Z"
}

# 成本公式
# Cost = (input_tokens × input_price) + (output_tokens × output_price)
# gpt-4-turbo: (2048 × $10/1M) + (512 × $30/1M)
#            = $0.02048 + $0.01536 = $0.03584

示例场景：一个带工具调用的客服 Agent 上线两周，日均成本稳定在几十美元，团队只配了"日预算超限发邮件"这一条告警。

问题：周五晚上某类问句触发了工具调用与再规划的循环——Agent 调工具、拿到空结果、重新规划、再调同一个工具，单个会话跑了 40 多轮。八小时内成本冲到日均的 30 倍，日预算邮件在凌晨才发出，而且没人看。

方案：告警按三层重建：① 单请求层——单会话工具调用超过 8 轮直接中断并返回兜底；② 小时层——小时成本超过 7 日均值 3 倍立即触发即时通知并自动降级到更便宜的模型；③ 日层——保留原有邮件作为兜底。同时给每个 Trace 打上 feature 标签，让成本能归因到具体功能。

效果：同类循环在后续两次出现时都被第一层拦下，单次损失从数千美元级降到不足 1 美元；成本归因上线后还顺带发现另一个功能的 Prompt 里塞了整份文档，压缩后该功能日成本下降约 40%。

预算告警

  • 日预算：每日消耗超过 $50 → 邮件通知
  • 小时速率：单小时消耗超过日均 3 倍 → 即时告警
  • 用户级：单用户单日超过 $5 → 限流 + 通知
  • 异常检测：Token 消耗突增（Z-score > 3）→ 自动降级到更便宜的模型

知识要点
  • Token 监控是 LLM 可观测性中最直接与业务成本挂钩的指标
  • 成本归因需要多维度：用户 × 模型 × 功能 × 时间

七、延迟分析

用户感受到的"快慢"是首字延迟，不是总耗时。一个 8 秒才说完但 0.4 秒就开口的回答，体验远好于 5 秒憋出全文。

关键延迟指标

指标全称定义参考值 (gpt-4)
TTFTTime to First Token从请求发送到收到第一个 Token 的时间200ms - 2s
TPSTokens per Second流式输出的 Token 生成速率30-80 tokens/s
E2E LatencyEnd-to-End Latency从用户发送到完整响应的总时间2s - 30s
ITLInter-Token Latency两个 Token 之间的间隔12-33ms

分段延迟分析

检索 120ms→ Rerank 45ms→ Prompt 构建 5ms→ LLM 推理 1800ms→ 后处理 10ms 
# 分段延迟采集示例
import time

class LatencyTracker:
    def __init__(self):
        self.segments = {}
        self._start = None

    def start(self, name):
        self._start = time.perf_counter()
        self._current = name

    def end(self):
        elapsed = (time.perf_counter() - self._start) * 1000
        self.segments[self._current] = elapsed

    def report(self):
        total = sum(self.segments.values())
        for name, ms in self.segments.items():
            pct = ms / total * 100
            print(f"  {name}: {ms:.1f}ms ({pct:.1f}%)")
        print(f"  Total: {total:.1f}ms")

# 输出:
#   retrieval: 120.3ms (6.1%)
#   rerank: 45.1ms (2.3%)
#   prompt_build: 4.8ms (0.2%)
#   llm_inference: 1802.5ms (91.0%)  ← 瓶颈
#   post_process: 8.2ms (0.4%)
#   Total: 1980.9ms
把四个延迟指标画到同一条时间轴上，关系就清楚了 t=0 用户点击发送 │ ├─ 网络 + 网关 + 鉴权 ─────┐ ├─ 检索 + Rerank ──────────┤ 这段用户什么都看不到 ├─ Prompt 组装 ────────────┤ ├─ 排队等 GPU ─────────────┤ ← 高并发时这段常被忽略，却经常是最大变量 ├─ Prefill（处理全部输入）─┘ │ ▼ 第一个 token 吐出 ├──────── TTFT ────────┤ 用户开始看到字，感知延迟到此为止 │ │ tok tok tok tok tok tok tok tok tok … │ └┬┘ 每两个 token 的间隔 = ITL │ ITL ≈ 12~33 ms 1 / ITL = TPS（生成速率） │ ▼ 最后一个 token ├───────────────── E2E Latency ─────────────────┤ 三条优化路径对应三段，不能混着谈 TTFT 偏高 → 查排队时长、输入过长（Prefill 变慢）、检索链路慢 手段：Prompt 缓存、缩短上下文、扩容降低排队 ITL 偏高 → 单卡显存带宽吃紧、batch 过大、KV Cache 换页 手段：调 batch 上限、开更高效的注意力实现、换卡 E2E 偏高但 TTFT/ITL 正常 → 单纯是输出太长 手段：限制 max_tokens、要求模型精简、分段返回 ★ 开了流式之后 E2E 不会变短，变短的只有 TTFT——但用户投诉会明显减少 ★ LLM 延迟长尾很重，P99 常是 P50 的 5~10 倍，SLA 用平均值等于没定

百分位延迟

百分位含义关注场景
P50 (中位数)50% 的请求延迟低于此值典型用户体验
P9595% 的请求延迟低于此值大多数用户体验的上限
P9999% 的请求延迟低于此值极端情况，SLA 定义

💡 LLM 延迟通常呈长尾分布，P99 可能是 P50 的 5-10 倍。SLA 建议关注 P95。

示例场景：一个 RAG 问答服务，P50 延迟 2.1 秒一直很稳，但 P99 长期在 18 秒左右，用户投诉集中在"偶尔要等很久"。

问题：团队一开始认定是模型推理慢，先换了更快的模型，P99 只降到 16 秒。接上分段延迟采集后才看清：慢请求里 LLM 推理耗时其实和平时差不多，多出来的十几秒几乎全在向量检索这一段——某几类长查询触发了向量库的全量扫描回退路径，检索单段就要 12 秒以上。

方案：三处一起改：① 给向量检索加 800 毫秒超时，超时后降级为不带检索直答并在回答里标注；② 修正触发全量扫描的过滤条件写法，让它能命中索引；③ 把分段耗时全部打进 Trace，P99 按分段拆开看而不是只看总数。

效果：P99 从 18 秒降到 3.4 秒，P50 基本不变。真正的收益来自"先分段再优化"这一步——在此之前换模型的两周工作，方向从一开始就是错的。

✅ 延迟优化手段
  • Streaming：降低感知延迟（TTFT），用户更早看到输出
  • Prompt 缓存：OpenAI Prompt Caching / 语义缓存，减少重复计算
  • 并行调用：检索与 Prompt 构建并行执行
  • 模型选择：简单任务用 gpt-4o-mini（速度快 5-10 倍）
  • 输出长度限制：设置 max_tokens 控制生成长度
知识要点
  • TTFT 影响用户感知延迟，E2E Latency 影响实际吞吐
  • LLM 推理通常占总延迟 80-95%，是优化重点
  • SLA 定义应使用 P95/P99 而非平均值
  • Streaming 不能降低 E2E 延迟，但显著改善用户体验

JUDGE_PROMPT = """

# 注意事项
# 1. Judge 模型应 ≥ 被评估模型的能力
# 2. 需要定期用人工标注校准 Judge 的准确性
# 3. 成本：每次评估额外消耗 Token
⚠ LLM-as-Judge 的局限
  • 位置偏见：Judge 可能偏好排在前面的答案
  • 长度偏见：更长的回答可能获得更高评分
  • 自我偏见：GPT-4 评估 GPT-4 的输出时偏高
  • 解决方案：多 Judge 投票、随机位置、与人工评估对齐
知识要点
  • 质量监控需要定量指标 + 定性反馈结合
  • Thumbs Up/Down 是最简单有效的用户反馈方式，要关联到 Trace
  • LLM-as-Judge 可以自动化大规模评估，但有偏见，需定期校准
  • 幻觉检测是 LLM 质量监控的核心难点

九、告警与运维

告警的价值不在于"发现问题"，而在于"每一条都对应一个明确的动作"。没有 Runbook 的告警，第二次响起时就会被静音。

异常检测场景

异常类型检测规则告警级别响应动作
延迟飙升P95 > SLA 阈值 × 2🔴 P1检查模型 API 状态、降级
成本异常小时成本 > 日均 × 3🟡 P2限流 + 排查异常调用
错误率飙升5xx 错误 > 5%🔴 P1切换 Fallback 模型
幻觉率上升日幻觉率 > 10%🟡 P2检查 Prompt / 知识库更新
Rate Limit429 错误持续🟡 P2调整 QPM / 扩容 / 负载均衡
质量下降用户满意度 < 70%🟠 P3分析低分 Case、优化 Prompt

On-call 响应流程

告警触发→ 值班确认→ 查看 Runbook→ 定位根因→ 执行缓解→ 事后复盘
  • 用尾部采样：慢请求、报错请求、用户打差评的请求一律全量留存，正常请求按低比例抽样
  • trace_id 从网关一路透传到日志、指标和用户反馈，让四类数据能对齐到同一次调用
  • Prompt 与 Completion 在写入前脱敏，同时保留内容哈希，这样既不泄露 PII 又能做去重统计
  • 告警分三层——单请求熔断、小时级速率、日级预算，越靠前的层动作越自动
  • 每条 P1/P2 告警都配一份 Runbook，写清症状、排查顺序和缓解动作
  • 记录 finish_reason，被 max_tokens 截断和模型主动停止是两类完全不同的问题
  • 不要只监控接口成功率：LLM 应用最典型的故障是返回 200 但内容是错的
  • 不要把 Prompt 原文直接写进普通日志系统，它几乎必然包含用户隐私数据
  • 不要用均匀采样，1% 的均匀采样会让出问题的那 1% 大概率消失
  • 不要只设日预算告警，失控的循环调用在几小时内就能烧掉一个月的额度
  • 不要把 LLM-as-Judge 的分数当成绝对真值，它存在长度偏好和自我偏好，需要定期用人工标注校准
  • 不要用平均延迟定 SLA，长尾分布下平均值会系统性地掩盖真实体验

Runbook 模板

## Runbook: LLM 延迟飙升

### 症状
- P95 延迟 > 10s 持续 5 分钟
- 用户端出现超时

### 排查步骤
1. 检查 LLM 提供商状态页 (status.openai.com)
2. 查看 Token 用量是否突增 (Prompt 过长?)
3. 检查是否有异常循环调用 (Agent 死循环?)
4. 查看并发量是否超出 Rate Limit

### 缓解措施
1. 【立即】切换到 Fallback 模型 (gpt-4o-mini)
2. 【立即】启用 Prompt 缓存
3. 【短期】限制 max_tokens
4. 【长期】添加超时重试 + 断路器

### 升级条件
- 持续 15 分钟无缓解 → 升级至 P0
- 影响 > 50% 用户 → 通知管理层
知识要点
  • LLM 告警比传统服务多出成本异常 + 质量下降两类
  • Runbook 应包含：症状、排查步骤、缓解措施、升级条件
  • Fallback 策略至关重要：主模型不可用时自动切换到备用模型
  • 事后复盘 (Postmortem) 不要漏掉对 Prompt/模型版本变更的检查

🎓 Q&A（10 题）

Q1: LLM 可观测性与传统微服务可观测性的核心区别是什么？

核心区别在于"语义层面"的不确定性：

  • 输出不确定性：传统服务相同输入 → 相同输出；LLM 同一 Prompt 可能产生不同答案，需要关注输出质量的一致性
  • 错误定义模糊：传统服务有明确的错误码（500/404）；LLM 返回 200 但内容可能是幻觉、不相关或有害内容
  • 新增指标维度：Token 用量/成本、幻觉率、语义相关性评分等传统不需要的指标
  • 数据隐私挑战：Prompt 和 Response 是自然语言，可能包含 PII，日志存储需特殊处理
  • 成本关注：API 调用按 Token 计费，成本波动大，需实时监控
Q2: 如何设计一个 RAG 应用的 Tracing 方案？需要记录哪些关键信息？

RAG Tracing 设计方案：

  • Trace 粒度：一次用户请求 = 一个 Trace，包含多个 Span
  • 关键 Span： ① Query 理解 (query rewrite/expansion) — 输入原始 query，输出改写后的 query
    ② Vector Retrieval — 输入 embedding，输出 top-K chunks，记录检索耗时和数据库
    ③ Reranker — 输入 query + chunks，输出 reranked 结果，记录分数
    ④ Prompt Assembly — 记录最终拼装的完整 prompt（含 system/context/query）
    ⑤ LLM Generation — model、input/output tokens、温度、耗时
    ⑥ Post-processing — 格式化、引用提取等
  • 关键元数据：每个 Span 记录 input、output、duration、status；Generation Span 额外记录 model、token_usage、cost
  • 质量标注：在 Trace 上关联用户反馈 (thumbs up/down) 和自动评估分数
  • Session 关联：多轮对话使用同一 session_id 串联
Q3: LangSmith 和 Langfuse 如何选择？各自的优缺点是什么？

选择依据：

适用框架LangChain 最佳，其他框架需适配框架无关，任何 LLM 应用均可

Q4: 如何实现 LLM 应用的成本归因和预算控制？

成本归因：

  • 每次 LLM 调用记录：user_id、team、feature、model、input_tokens、output_tokens
  • 根据模型价格表自动计算 cost = (input_tokens × input_price) + (output_tokens × output_price)
  • 多维聚合：按用户/团队/功能/模型/时间维度统计

预算控制策略：

  • 前置控制：用户级 Rate Limit（QPM / 日 Token 上限）
  • 实时监控：小时级成本异常检测（> 3 倍均值告警）
  • 自动降级：当成本接近预算时自动切换到更便宜的模型
  • 后置分析：周度/月度成本报告，识别优化机会（如 Prompt 过长、无效重试）
Q5: 什么是 TTFT 和 TPS？它们分别影响什么？如何优化？

TTFT（Time to First Token）：从发送请求到收到第一个 Token 的时间。影响用户的感知延迟——TTFT 越低，用户越快看到响应开始。

TPS（Tokens per Second）：流式输出的 Token 生成速率。影响阅读体验——TPS 过低会导致输出"卡顿"。

优化手段：

  • 降低 TTFT：Streaming 输出、Prompt Caching（减少重复前缀计算）、选择低延迟模型、就近部署
  • 提升 TPS：使用更小/更快的模型（gpt-4o-mini）、限制并发以减少排队、使用 vLLM 等推理框架优化吞吐
  • 注意：Streaming 降低 TTFT 但不降低 E2E Latency；E2E = TTFT + (output_tokens / TPS)
Q6: 如何检测和监控 LLM 的幻觉？

幻觉检测方法：

  • 基于引用验证：检查 LLM 输出是否可以从提供的 context 中找到依据（Faithfulness 检测）
  • LLM-as-Judge：用一个更强的 LLM 评估输出是否包含虚构信息（如 GPT-4 评估 GPT-3.5 的输出）
  • NLI（自然语言推理）：使用 NLI 模型判断输出与 context 之间是 entailment 还是 contradiction
  • 知识库交叉验证：将关键事实与外部知识库比对
  • 用户反馈：收集 thumbs down 并人工审核是否为幻觉

监控体系：

  • 抽样评估：每日随机抽取 N% 的输出做自动幻觉检测
  • 实时检测：高风险场景（医疗/法律）对每条输出做检测
  • 趋势监控：跟踪日/周级幻觉率变化，Prompt 或模型变更后重点关注
Q7: LLM-as-Judge 方案有哪些局限性？如何改进？

核心局限：

  • 位置偏见：Judge 模型倾向于给排在前面的答案更高分
  • 长度偏见：更长、更详细的回答通常得分更高，即使简洁回答更优
  • 自我偏见：用 GPT-4 评估 GPT-4 的输出，可能偏向自己的风格
  • 知识局限：Judge 模型本身的知识可能有错，导致误判
  • 一致性问题：同一对 (question, answer) 多次评估结果可能不同

改进策略：

  • 多 Judge 投票：使用 2-3 个不同模型做 Judge，取多数意见
  • 随机化：随机交换答案位置，消除位置偏见
  • 校准集：维护人工标注的 Golden Set，定期评估 Judge 的准确性
  • 结构化评估：使用明确的评分维度和 rubric，减少主观性
  • 人工兜底：低置信度的评估交给人工复审
Q8: 生产环境中 LLM 应用应该设置哪些告警？

必设告警清单：

  • 延迟告警：P95 延迟超过 SLA 阈值（如 10s），持续 5 分钟 → P1
  • 错误率告警：5xx / API 错误率 > 5%，持续 3 分钟 → P1
  • 成本告警：小时成本超过 7 日均值 3 倍 → P2
  • Rate Limit 告警：429 响应持续出现 → P2
  • 质量告警：日幻觉率 > 10% 或用户满意度 < 70% → P3
  • Token 突增：单请求 Token 超过阈值（如 > 10K）→ 排查 Prompt 注入

关键原则：每条告警必须配 Runbook；区分 actionable 告警和 informational 告警；避免告警疲劳。

Q9: Phoenix 的 Embedding 可视化如何帮助 RAG 调优？

Phoenix 通过 UMAP 降维将 Query 和 Document 的 Embedding 映射到 2D 空间：

  • 发现检索漏洞：如果 Query 聚类远离所有 Document 聚类，说明知识库缺少相关内容
  • 检测文档漂移：新增文档的 Embedding 分布与历史文档不一致，可能是数据质量问题
  • 分析失败案例：低分 Trace 的 Query Embedding 与检索到的 Document Embedding 距离远，说明检索不准
  • 优化 Chunk 策略：如果同一文档的 Chunk Embedding 过于分散，可能需要调整 chunk size 或 overlap
  • 评估 Embedding 模型：切换 Embedding 模型后，对比可视化变化，判断检索质量是否改善

配合 NDCG@K、Precision@K 等指标量化分析，实现"可视化定位 + 定量验证"的调优循环。

Q10: 如何构建一套完整的 LLM 可观测性体系？

分层架构：

  • 数据采集层： - SDK 埋点（Langfuse/LangSmith SDK）采集 Trace/Span/Generation - Proxy 模式（Helicone）零侵入采集 API 调用 - 用户反馈采集（Thumbs Up/Down）
  • 数据存储层： - Trace 数据 → 时序数据库/ClickHouse - Prompt & Response → 对象存储（注意 PII 脱敏） - 评估结果 → 关系型数据库
  • 分析层： - 实时仪表盘（延迟 / Token / 成本 / 错误率） - 质量分析（幻觉检测 / LLM-as-Judge / 检索质量） - 成本归因（多维下钻）
  • 告警层： - 多级告警（P1-P3）+ Runbook - 异常检测（统计异常 + 趋势变化） - 自动化响应（降级 / 限流 / 切换模型）
  • 工具选型： - 开发阶段：Phoenix（本地快速迭代） - 测试阶段：LangSmith/Langfuse（评估 + 数据集管理） - 生产阶段：Langfuse（追踪）+ Helicone（成本）+ Prometheus（告警）
