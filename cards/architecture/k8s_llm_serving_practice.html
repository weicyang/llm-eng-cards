K8s 的默认假设是"副本秒级可换、资源连续可分、就绪即可服务"。LLM 推理把这三条全部破坏：副本启动要几分钟、GPU 是不可切分不可超卖的整数、进程报告就绪时首次编译可能还没做完。这张卡讲的就是这三处错配各自会怎么炸，以及怎么把参数与形态改成适配的样子。K8s 的通用概念不在这里重讲——Pod 与探针机制见 S05，YAML 与运维痛点见 S06。

一、GPU 资源模型与它的三个硬限制

CPU 和内存在 K8s 里是连续可分的：500m 是半核，requests 与 limits 可以不等，因此可以超卖。GPU 完全不是这样。nvidia.com/gpu 是通过 device plugin（设备插件）机制注册的扩展资源，而扩展资源在 K8s 里只支持整数、且不允许超卖——requests 必须等于 limits。这一条约束是后面所有 GPU 调度话题的起点。

1.1 三个硬限制及其后果

硬限制机制原因直接后果能做什么
只能是整数扩展资源不支持小数量纲写不出 nvidia.com/gpu: 0.5要共享必须让插件"多报几个"

第三条是最容易造成浪费的一条。调度器分配的只是一个整数，它不知道你的进程用了 2 GB 还是 80 GB 显存，也不知道算力利用率是 5% 还是 95%。所以十个各用 15% 算力的小服务，在默认配置下要占十张物理卡——真实需求约 1.5 张。

1.2 GPU 共享的三条路径与它们在 K8s 里的样子

既然不能超卖，那"共享"只能通过改变插件对外声称的数量来实现。这就是理解 K8s 上 GPU 共享的关键：kube-scheduler 从来不懂 GPU，它只是照着 device plugin 报上来的整数做账。

device plugin 如何决定调度器看到什么 物理机：1 张 A100 80GB │ ▼ ┌───────────────────────── nvidia device plugin (DaemonSet) ─────────────┐ │ │ │ A) 默认 → 上报 nvidia.com/gpu: 1 │ │ 调度器：这台机器有 1 个可分配单位 │ │ │ │ B) time-slicing → 配置 replicas: 4 │ │ replicas=4 上报 nvidia.com/gpu: 4 │ │ 调度器：有 4 个单位（但物理上还是同一张卡） │ │ ⚠ 无显存隔离：一个 Pod 吃 70GB，其余三个 OOM │ │ ⚠ 无算力保证：replicas 不等于按比例分配算力 │ │ │ │ C) MIG mixed → 硬件切成 7 个实例，按 profile 起独立资源名 │ │ 上报 nvidia.com/mig-1g.10gb: 7 │ │ 调度器：有 7 个"另一种资源" │ │ ✔ 显存与算力硬隔离 │ │ ⚠ 同一容器不能同时请求 gpu 和 mig-* 两种资源 │ │ │ │ D) MIG single → 所有 MIG 设备仍叫 nvidia.com/gpu │ │ 切分规格靠 nodeSelector 表达 │ └────────────────────────────────────────────────────────────────────────┘ 调度器视角：始终只是"某个资源名 + 一个整数"，卡内发生什么它一概不知

三条路径的取舍在 DP04 · 模型部署与 Serving 已有 Serving 视角的介绍，这里补的是它们在调度层暴露成什么。时间片（time-slicing）通过在 ConfigMap 里设置 replicas 让插件把一张卡报成多个副本，调度器于是能放多个 Pod 上去，靠驱动层的上下文切换轮转执行；它的致命短板是零显存隔离，NVIDIA 也建议配 failRequestsGreaterThanOne: true 以免用户误以为"请求 2 个 replica 就有 2 倍算力"。MIG（Multi-Instance GPU）在 Ampere 及更新架构上做硬件级切分，最多 7 个实例，各有独立显存与算力；在 mixed 策略下每种切分规格暴露成独立资源名（形如 nvidia.com/mig-<切片数>g.<显存>gb），官方明确限制同一容器不能同时请求 nvidia.com/gpu 和某个 mig-*，混请求会拿到未定义的设备；single 策略则保持资源名不变，用 nodeSelector 表达规格，代价是一台机器上的切分必须同构。另外要注意 MIG 与 MPS 在 GPU Operator 里不能组合，时间片与 MPS 也是互斥的。

示例场景：某平台把 8 个小模型服务（各自实际用 6~10 GB 显存、算力利用率长期低于 20%）按默认方式部署，每个请求 nvidia.com/gpu: 1，占满了 8 张 A100。改用 MIG mixed 策略把两张 A100 切成 1g.10gb 规格后，8 个服务全部落在这两张卡上，释放出 6 张卡给在线主服务，卡利用率账面上从不足 20% 提升到 60% 以上。踩到的坑有两个：一是切换 MIG 规格要求卡上没有运行中的负载，必须当成一次运维事件排期；二是有一个服务的峰值显存实际会摸到 11 GB，落在 1g.10gb 上直接 OOM，最后单独给它切了 2g.20gb。这说明 MIG 的前提是你得先量准每个服务的真实显存上界，而不是按感觉切。

把 K8s 的 GPU 调度理解成"记账"而不是"分配"：device plugin 是唯一的记账员，它说这台机器有几个单位，调度器就照着排；卡里实际发生什么，账本上一个字都没有。所以所有 GPU 共享方案的本质都是"改账本"——时间片改数量但不改物理隔离，MIG 改数量的同时也真的把硬件切开了。选哪个，取决于你能不能承受"账本和现实不一致"的后果。

二、模型权重怎么交付到 Pod

权重交付路径直接决定了副本的冷启动时间，而冷启动时间又决定了扩缩容策略与滚动更新窗口——所以这是一个看起来像存储问题、实际上影响整条链路的决策。单机侧的四种做法见 S09 · 容器化与镜像工程 第四章，这里讲它们在 Pod 上的形态与代价。其中反复出现的 initContainer（初始化容器）是指在主容器之前运行并必须成功退出的容器，常用来在启动前把权重下载到共享卷里。

2.1 权重之外的第二个挂载

只解决权重还不够：除了权重，还有一份编译产物缓存需要单独持久化，否则每个新容器都会从头编译一遍。这份缓存的默认路径与复用机制属于容器层的问题，见 S09 · 容器化与镜像工程第四章。这里只说它在 K8s 上的后果：你要声明的是两个 volumeMount，而不是一个，而且漏掉第二个既不会报错、也不影响探针转绿。忽略这一条的典型症状是"权重明明挂上了，扩容出来的新副本还是要慢好几分钟才真正能扛流量"——它也是下一章"就绪不等于可用"的主要根因。

        volumeMounts:
        - { name: weights, mountPath: /models, readOnly: true }
        - { name: compile-cache, mountPath: /root/.cache/vllm }
        - { name: shm, mountPath: /dev/shm }   # 张量并行依赖共享内存

第三个挂载同样是 LLM 特有的：vLLM 底层用 PyTorch，进程间通过共享内存传数据，张量并行推理尤其依赖它，官方给的处方是 --ipc=host 或加大 --shm-size；在 Pod 里对应的写法是挂一个 emptyDir 的内存介质卷到 /dev/shm。忘了它的表现是张量并行启动即崩。

权重交付方案的选择，等价于回答一个问题：你愿意把加载成本付在哪个环节。付在镜像分发（内置）、付在网络存储（PVC）、付在每次扩容的下载（initContainer），还是付在维护一套缓存预热机制（本地缓存）。在线服务对扩容速度敏感，通常值得付最后一种；离线批处理反过来，最省事的方案就是最好的方案。

三、探针的重灾区：加载分钟级的服务怎么设参数

探针有哪几种、四种探测方式怎么工作、失败后各自的动作是什么，S05 · Kubernetes Pod 核心机制 第四章已经完整展开了，这里不重复。本节只讲一件事：当启动时间是分钟量级时，这套参数会怎么把服务打进死循环。核心角色是 startupProbe（启动探针）——它在通过之前会把 liveness 与 readiness 全部挂起，是慢启动服务唯一的保护伞。

3.1 无限重启循环是怎么产生的

官方文档给出的判据很明确：如果容器通常需要超过 initialDelaySeconds + failureThreshold × periodSeconds 才能启动，就必须配 startupProbe。反过来读这句话就是失效条件——只配 liveness、不配 startup，而 liveness 的时间预算小于真实加载时间时，会发生这样的事：容器启动、开始加载权重、liveness 连续失败达到阈值、kubelet 杀掉容器、按重启策略重启、再次开始加载……永远走不到加载完成那一刻。这不是偶发故障，而是一个稳定的确定性死循环，且日志里看不到应用错误，只有反复的"Liveness probe failed"。

同一个加载耗时 6 分钟的服务，两种配置的命运 配置 A（错）：只有 livenessProbe，periodSeconds=10, failureThreshold=3 t=0 容器启动，开始加载权重 t=0 liveness 开始探测（无 startupProbe 保护） t=10s 失败 1/3 ← 权重才读了不到 3% t=20s 失败 2/3 t=30s 失败 3/3 ──► kubelet kill 容器 t=30s 按 restartPolicy 重启 ──► 回到 t=0 ⇒ CrashLoopBackOff，永远到不了 t=360s。日志无应用报错。 配置 B（对）：startupProbe 预算 > 最坏加载时间 startupProbe: periodSeconds=15, failureThreshold=40 → 预算 600s t=0 startupProbe 开始；liveness/readiness 全部被挂起 t≈360s startupProbe 首次成功 ──► 交棒 t>360s liveness 接管（快失败，只管进程死没死） readiness 接管（频繁探测，控制流量接入） ⇒ 加载期不会被误杀，加载后仍保留对死锁的快速反应 预算公式：startupProbe 预算 = failureThreshold × periodSeconds 要覆盖【权重下载 + 加载 + 图编译/预热】的最坏情况，再留余量

参考量级：社区的 vLLM 探针方案里，startupProbe 用 30 秒周期配 60 次阈值，也就是给到 30 分钟的启动预算，探测的是 /v1/models（模型列出即视为加载完成），而 liveness 探 /health 且只给 3 次失败。这个组合体现了正确的分工——startupProbe 负责"别急"，liveness 负责"别装死"，readiness 负责"别硬撑"。

3.2 为什么"就绪"不等于"可用"

更隐蔽的一类问题是探针全绿、服务却明显不可用。原因是"进程能应答 HTTP"和"能按 SLA 完成一次推理"之间还隔着好几步：权重已从磁盘读入显存，但 torch.compile 的图编译还没做（上一章提到新容器的编译缓存默认是空的）；CUDA 上下文与算子的首次调用还要现场编译内核；KV Cache 的显存池还没预分配完；前缀缓存是冷的。这些工作往往由第一批真实请求触发，表现就是"刚扩容出来的副本，前几十个请求的首字延迟是稳态的数倍"。

治理这件事的手段有三个层次。最轻的是把 readiness 的判定改成一次真实的小推理（比如生成 1 个 token）而不是端口探活，这样进程会在真正能干活之后才被加入端点。中等的是在容器启动脚本里做主动预热——加载完成后自己先跑几次短请求把编译与显存池走通，再让 readiness 转绿。最重的是把编译缓存持久化（挂卷复用），从根上缩短这段时间。三者可以叠加。

示例场景：某服务上线后每次扩容都会出现一段"新副本拉低整体延迟"的现象：扩容后约 90 秒内，P95 首字延迟从 700 ms 恶化到 3 s 以上，之后自行恢复。排查发现 readiness 探的是 /health（进程活着就返回 200），而副本被加入端点后还要现场做图编译和显存池预分配，负载均衡按轮询给它分了 1/N 的流量，这部分请求全部变慢。修复分两步：readiness 改为探一个执行 1 token 生成的端点，并在启动脚本里加 3 次预热请求。改完后扩容期间 P95 抖动幅度降到 15% 以内。这里真正的错误不是探针参数写错了数字，而是把"进程存活"当成了"能提供服务"的证据。

三个探针对应三个完全不同的问题，混用就一定出事：startupProbe 回答"还在启动吗"，liveness 回答"是不是死锁了"，readiness 回答"现在能不能接客"。LLM 服务的特殊性只在于第一个问题的答案是"分钟级"，以及第三个问题不能只看进程状态。把 startupProbe 的预算按最坏加载时间给足，把 readiness 的判定做成一次真实推理，这两条做到了，探针相关的事故会少掉绝大部分。

四、滚动更新与优雅退出对流式推理的破坏

滚动更新对普通 Web 服务几乎是无感的：请求短、无状态、连接秒级完结。流式推理完全不同——一次生成可能持续几十秒到几分钟，通过 SSE 或长连接持续吐字。Pod 被终止时，这些连接会在半句话中间被切断，用户看到的是回答突然停住。要避免这件事，需要的是连接排空（connection draining）——停止接入新请求、但让已在途的生成跑完再退出。

4.1 终止序列里的两条并行时间线

要理解破坏是怎么发生的，得看清 Pod 终止时两件事是并行发生的：一边是端点摘除（Service 的 EndpointSlice 更新要传播到集群各节点的转发规则），另一边是 kubelet 执行 preStop、然后向容器主进程发 TERM 信号。kubelet 不会等端点传播完成。K8s 官方教程明确把"实现优雅的连接排空"列为需要显式处理的事项，并指出终止中的端点其 ready 状态一定是 false（为了兼容性），如果需要对终止中的 Pod 继续排空流量，要看 serving 这个条件。

Pod 终止时的两条时间线（流式推理为什么会被截断） t=0 收到删除请求 ├──────────────── 时间线 A：端点摘除 ────────────────┐ │ EndpointSlice 更新 → 各节点转发规则同步（需传播时间）│ │ 期间仍可能有新请求被路由到这个 Pod │ └──────────────────────────────────────────────────┘ ├──────────────── 时间线 B：容器终止 ────────────────┐ │ kubelet 执行 preStop（阻塞，必须先跑完） │ │ → 发送 TERM 信号给主进程 │ │ → 到期未退出则 KILL │ └──────────────────────────────────────────────────┘ 两条线不同步 ⇒ 若无 preStop，TERM 可能早于端点传播完成 ⇒ 新请求还在进来，进程已在关闭 → 5xx / 连接被截断 官方口径要点： · 默认 terminationGracePeriodSeconds = 30 · preStop 必须在 TERM 之前跑完；宽限期涵盖 preStop + 进程退出的总时长 · preStop 挂住不返回 → Pod 停在 Terminating，直到宽限期到点被 KILL · 无 sidecar 时，多容器收到 TERM 的顺序是任意的

官方文档在细节上有一处极易读错，值得原样记住：宽限期覆盖的是 preStop 执行与容器正常停止的总时长。文档给的例子是——terminationGracePeriodSeconds 为 60、preStop 花了 55 秒、容器收到信号后还需 10 秒才能停干净，那么容器会在正常停止前被杀掉，因为 55+10 超过了 60。所以设参数时不能只按"生成时长"算，要按 preStop 时长 + 最坏排空时长 之和再留余量。

4.2 "停止接新、跑完旧的"要怎么实现

目标机制LLM 场景的具体设法不做的后果
不再接新请求preStop 中先 sleep，给端点传播留时间sleep 时长覆盖端点传播的观测上界（通常数秒到十几秒）TERM 早于端点摘除，新请求打到正在关闭的进程
旧请求跑完应用收到 TERM 后停止接受新连接、等在途生成结束需要引擎/网关支持"排空模式"；否则靠 preStop 轮询在途计数在途生成被 KILL 截断，用户看到半句话

GPU 那一行是 LLM 特有的死结，值得单独说：普通服务做零中断滚动更新的标准做法是 maxUnavailable: 0 加 maxSurge: 1——先起一个新的，就绪后再下一个旧的。但这要求集群里有一张空闲的卡。GPU 打满的集群做不到这件事，于是只有三个选择：临时扩容节点、接受 maxUnavailable: 1（更新期间容量下降一个副本），或者把发布安排在低峰期。这一条经常在发布当天才被发现，因为在测试环境卡是够的。

示例场景：某对话服务在一次常规发布中收到大量用户反馈"回答说到一半就断了"。复盘发现三处叠加：一是没有 preStop，TERM 早于端点传播完成，更新期间仍有新请求被路由到正在关闭的副本；二是 terminationGracePeriodSeconds 用的是默认 30 秒，而该服务 P99 生成时长约 70 秒，所有超过 30 秒的在途生成都被 KILL 截断；三是引擎进程收到 TERM 后立即退出，完全没有排空逻辑。修复后的组合是 preStop 先 sleep 15 秒（覆盖端点传播）、宽限期设到 180 秒、应用侧收到 TERM 后转入拒新接旧的排空模式。发布期间的截断投诉归零，代价是单次滚动更新的总时长从约 2 分钟拉长到约 8 分钟——这是必须接受的交换。

优雅退出的本质是让两条本来不同步的时间线对齐：K8s 摘端点是异步传播的，kubelet 发信号是不等传播的。preStop 里的那段等待不是"迷信写法"，它是唯一能让 kubelet 停下来等一等的杠杆。而 terminationGracePeriodSeconds 要按"preStop + 最坏在途时长"之和来给——流式推理的在途时长以分钟计，用默认 30 秒等于宣布所有长回答都会被砍。

五、扩缩容为什么对 LLM 特别难

自动扩缩在普通 Web 服务上是成熟能力：CPU 利用率上去了就加副本，秒级起新 Pod，很快追上。这套逻辑在 LLM 上三个环节同时失效——信号错、反馈慢、成本结构不同。平台侧有哪些能力可用（HPA、KEDA、GPU Operator 等）在 S04 · AI 平台设计 第八章已经罗列，本节讲的是这些能力为什么会失效以及失效长什么样。

5.1 信号错：CPU 利用率是彻底的错误指标

推理服务的 CPU 主要花在请求解析、分词、序列化这些边角工作上，真正的瓶颈在 GPU 的算力与显存带宽。一个 GPU 已经打满、请求在队列里排长龙的副本，CPU 利用率可能只有 20%——按 CPU 扩缩的 HPA 会认为它很闲，一个副本都不加。反过来，一波短请求的批量分词能把 CPU 顶起来，触发无谓扩容。

可用的信号按有效性排序：队列深度（引擎里排队等待、尚未开始生成的请求数，最直接反映供不应求）、并发在途序列数（与引擎的最大批容量对比即知饱和度）、KV Cache 占用率（显存侧的真实压力）、以及首字延迟的滑动分位数（最贴近用户体验但滞后）。GPU 利用率看起来合理，实际是个次优信号——连续批处理下它常年在高位，区分不出"忙碌但从容"和"已经过载"。KServe 的 Workload Variant Autoscaler 正是按这个思路做的：明确以 KV Cache 利用率、队列深度、请求饱和度作为扩缩依据，而不是通用的 CPU/内存。

信号反映什么有效性坑
CPU 利用率边角计算量无效与 GPU 饱和度几乎不相关，会同时漏扩和误扩
GPU 利用率算力占用次优连续批处理下常年高位，区分不出从容与过载
队列深度供需差好阈值要按引擎最大批容量定，不能拍数字
在途并发序列数饱和度好需引擎暴露该指标
KV Cache 占用率显存侧压力好受上下文长度分布影响大
首字延迟分位数用户体验可用但滞后指标本身有窗口延迟，作为扩缩输入会加剧震荡

5.2 反馈慢：HPA 的节奏与冷启动完全不匹配

把两组时间尺度并排放，问题就自明了。HPA 控制器的调谐周期默认是 15 秒；扩容方向默认没有稳定窗口（stabilizationWindowSeconds 为 0），也就是一有信号立刻扩；缩容方向默认稳定窗口 300 秒，取窗口内最高的推荐值，避免抖动。这套默认值是为"秒级起 Pod"的服务设计的。而 LLM 副本从被创建到能真正扛流量，要走完调度、拉镜像、加载权重、图编译与预热，通常是分钟量级。

HPA 的反馈延迟为什么会让副本数震荡 流量 ▁▁▁▂▄███████▇▅▃▁▁▁▁▁▁ 时间 0 2min 6min 10min t=2min 队列深度超阈值 → HPA 立刻决定扩容（默认无扩容稳定窗口） t=2min 新 Pod 创建 → 调度 → 拉镜像 → 加载权重 → 编译预热 t=7min 新 Pod 才真正就绪 ← 此时高峰已过大半 t=7min 指标已回落，300s 缩容窗口开始计时 t=12min 副本被缩掉 → 峰期请求大量超时，峰后却在为无用副本付费 副本震荡的成因：控制环的死区时间（分钟级冷启动） 远大于控制器的采样周期（15 秒） ⇒ 控制器在用"五分钟前的世界"做决策，必然过冲与欠冲交替 有效的组合（不是只靠 HPA）： ① 按历史流量定时预扩容：峰前把副本拉到位 ② 常驻热副本吃溢出：把首个峰值的冲击接住 ③ 权重放节点本地缓存 + 复用编译缓存：把死区时间本身压小 ④ 扩容方向设非零稳定窗口、缩容窗口拉长：换稳定性 ⑤ 自动扩缩当兜底，不当主力

控制论的语言能把这件事说得更准：这是一个死区时间远大于采样周期的控制系统，必然过冲。所以对 LLM 服务，正确的心态是把自动扩缩当兜底而非主力，主力交给定时预扩容与常驻热副本。另外 KEDA 相比原生 HPA 在这个场景有两个实用差异：它支持 idleReplicaCount（缩到闲置档而不是被卡在最小 1 副本）以及为模型加载留出的初始冷却期，这两项都直接针对冷启动。

5.3 成本结构：热副本要不要养

预留热副本是唯一能对抗冷启动的手段，问题只是养几个。这笔账的算法是：预留成本 = 热副本数 × 单副本单价 × 全时长，而它买到的是"峰值前 N 分钟的容量"。判断依据是峰值的爬升速度与副本就绪时间的比值——爬升比就绪快得多时，热副本几乎是唯一选项；爬升以小时计时，自动扩缩就够了。经验上把预留容量设在"能独立扛住日常峰值的 60%~70%"是个常见起点，剩余靠扩容补，但这个比例必须用真实流量曲线校准，不能照抄。容量该怎么从压测结果反推，见 DP16 · 推理服务压测方法论。

  • 用队列深度或在途并发做扩缩信号，阈值按引擎最大批容量定
  • 把冷启动时间当成一等指标监控，它决定其他所有策略
  • 峰前定时预扩容，用历史流量曲线驱动
  • 常驻热副本吃溢出流量，把首波冲击接住
  • 缩容窗口设长，一次误缩的代价是几分钟的空档
  • 把权重与编译缓存都做本地复用，从根上压缩死区时间
  • 不要用 CPU 利用率做扩缩信号，它与 GPU 饱和度几乎无关
  • 不要照抄 Web 服务的 HPA 默认节奏，扩容零稳定窗口会加剧过冲
  • 不要指望缩容到零省钱，除非能接受首个请求等几分钟
  • 不要只看均值指标，扩缩决策要看分位数与队列
  • 不要在同一负载上叠两套扩缩控制器，它们会互相打架
  • 不要把 GPU 节点池和普通业务混用，节点扩容速度会被拖慢

一句话概括：自动扩缩解决的是"容量跟得上"，而 LLM 的问题是"容量来不及"。这两件事不是同一个问题。要缩短"来不及"，只有三条路——把冷启动时间压小（缓存与预热）、提前扩（定时预测）、常备余量（热副本）。指标调得再准，也没法让一个需要五分钟才能就绪的副本在一分钟内到岗。

六、打包与平台化：Helm、Operator、KServe 与 Ray Serve

前面五章的所有配置——GPU 资源名、卷挂载、探针预算、宽限期、扩缩参数——最终都要落成可维护的交付物。这一章讲的是选择哪一层抽象来承载它们，以及什么时候不需要抽象。

6.1 Helm：把多环境差异收敛成一组值

Helm 在这个场景里的核心用途只有一个：让"同一套模板 + 不同的值"表达多环境差异。它的取值来源有明确的优先级顺序——chart 自带的 values.yaml 最低，然后是父 chart 的值，然后是命令行用 -f 传入的值文件（可以重复传，后面的覆盖前面的），最高的是 --set 逐项参数。这个顺序就是多环境方案的全部机制：把所有环境共同的部分留在 values.yaml，把每个环境的差异写成独立的值文件，发布时按需叠加。

# base 保持共性，环境文件只写差异，后传的覆盖先传的
helm upgrade --install llm ./chart \
  -f values.yaml \
  -f values-prod.yaml \
  --set image.tag=2026.09.1

对 LLM 服务，值得抽成变量的通常是这几项：副本数与热副本数、GPU 资源名（生产用整卡、测试用 MIG 切片）、模型标识与权重卷来源、startupProbe 预算（测试环境模型小、预算可短）、terminationGracePeriodSeconds、以及扩缩阈值。反过来，探针的探测路径、卷挂载结构这类跨环境一致的东西应该留在模板里，不要开成变量——每开一个变量就多一处漂移可能。多环境配置漂移的危害与其他治理路径（可视化平台、GitOps）见 S06，此处不重复。

6.2 Operator 与 CRD：什么时候值得写

Operator 是把运维知识写成控制器：定义一个自定义资源（CRD）描述"我要一个什么样的模型服务"，然后由控制器把它展开成 Deployment、Service、HPA 等一堆原生对象，并持续调谐。它的收益点很具体——当你有反复执行的多步运维流程时（比如"换模型版本要先起新副本预热、验证通过再切流量、然后回收旧副本"），Operator 能把这套流程变成声明式的一次提交。

但自己写 Operator 的门槛不低，判断标准可以简化成三问：同一套多步流程是否每周都要执行数次？流程中是否有必须按状态机推进的顺序？是否有多个团队需要复用同一套语义？三个都是"是"才值得自研；只有一两个"是"时，一份 Helm chart 加一段 CI 脚本通常更划算。更常见的情形是——你需要的 Operator 已经有人写好了，那就是下一节的两个选项。

每一层抽象都是在用"少写点重复配置"交换"多一层需要理解的语义"。判断该停在哪一层的标准很朴素：当前这一层让你重复劳动的次数，是否已经超过了下一层带来的认知与故障成本。两个模型两套环境时，原生 YAML 加一点复制粘贴完全够用；二十个模型五套环境时，不上模板层就是自找麻烦。

Q&A

为什么 GPU 在 K8s 里不能像 CPU 一样超卖或者按小数请求？

因为 nvidia.com/gpu 不是内建资源，而是通过 device plugin 机制注册的扩展资源，而扩展资源在 K8s 里只支持整数量纲、且不允许超卖（requests 必须等于 limits）。所以你既写不出 nvidia.com/gpu: 0.5，也没法让两个 Pod 各"申请"同一张卡的一部分。更重要的是第三层限制：调度器只维护一个整数账本，它完全看不见卡内情况——一个只用 2 GB 显存、算力利用率 5% 的 Pod 和一个把 80 GB 吃满的 Pod，在账本上都是"占用 1 个单位"。这造成了很直接的浪费：十个各用 15% 算力的小服务在默认配置下要占十张物理卡，真实需求约 1.5 张。要实现共享，唯一的办法是改变 device plugin对外声称的数量——时间片让它把一张卡报成多个副本，MIG 则真的把硬件切开再按规格上报。

时间片和 MIG 在 K8s 里暴露成什么样，选择依据是什么？

时间片通过在 device plugin 的 ConfigMap 里设置 replicas（比如 4）让一张物理卡被上报成 4 个 nvidia.com/gpu 单位，调度器于是能放 4 个 Pod 上去，靠驱动层上下文切换轮转执行。它的致命短板是零显存隔离——一个 Pod 在 80 GB 卡上分配了 70 GB，其余三个直接 OOM，没有任何机制阻止；而且 replicas 数不等于按比例分配算力，NVIDIA 建议配 failRequestsGreaterThanOne: true 避免这个误解。MIG 在 Ampere 及更新架构上做硬件级切分，最多 7 个实例，各有独立显存与算力；mixed 策略下每种规格暴露成独立资源名（形如 nvidia.com/mig-1g.10gb），官方限制同一容器不能同时请求 nvidia.com/gpu 和某个 mig-*，混请求会拿到未定义设备；single 策略保持资源名不变、用 nodeSelector 表达规格，代价是单机切分必须同构。选择依据的第一位是隔离要求：面向用户的生产端点用 MIG，开发测试用时间片。另外 MIG 规格切换要求卡上没有运行负载，得当成运维事件排期。

模型权重交付到 Pod 有哪几种方式，怎么选？

四种，选择的实质是"把加载成本付在哪个环节"。镜像内置最省事、版本语义最干净（镜像摘要同时锁定代码与权重），但几十 GB 的镜像让每个新节点首次拉取变成冷启动瓶颈，Registry 存储与带宽成本也随版本数放大。PVC 共享卷让镜像保持小巧、多副本共用一份权重，代价是加载速度受存储带宽限制，而且多副本同时启动会争抢同一存储。initContainer 启动时拉取的好处是任何节点都能自举、天然适配弹性，代价是每次扩容都要付一次完整下载，扩得越多越慢。节点本地缓存预热最快，命中时几乎只剩加载时间，但要维护一套预热、淘汰与一致性机制。生产上常见组合是本地缓存做主路径、对象存储拉取做兜底，并把"是否命中缓存"做成可观测指标。此外别忘了第二和第三个挂载：编译缓存（vLLM 官方指出 VLLM_CACHE_ROOT 每个新容器默认为空，会重新编译）和 /dev/shm（张量并行依赖共享内存，不够会启动即崩）。

模型加载要好几分钟，探针参数该怎么设才不会陷入重启循环？

核心是必须配 startupProbe，并且它的时间预算要盖住最坏加载时间。官方判据是：如果容器通常需要超过 initialDelaySeconds + failureThreshold × periodSeconds 才能启动完，就必须用 startupProbe。反过来读就是失效条件——只配 liveness 而它的预算小于真实加载时间时，会形成确定性死循环：启动、加载、liveness 连续失败到阈值、被杀、重启、再加载，永远走不到加载完成那一刻，且日志里只有反复的探针失败、没有应用错误。预算公式是 failureThreshold × periodSeconds，要覆盖权重下载、加载、图编译与预热的最坏情况再留余量；社区的 vLLM 方案用 30 秒周期配 60 次阈值，也就是 30 分钟预算，探的是 /v1/models。同时 liveness 要保持小的 failureThreshold（3 左右）专注检测死锁，readiness 要探得频（5 秒左右）以便快速摘掉故障副本。三者的分工是：startupProbe 负责"别急"，liveness 负责"别装死"，readiness 负责"别硬撑"。

为什么探针全绿了服务还是不可用？

因为"进程能应答 HTTP"和"能按 SLA 完成一次推理"之间还隔着好几步工作，而这些工作常常由第一批真实请求触发：权重虽已读入显存，但 torch.compile 的图编译还没做（新容器的编译缓存默认是空的）、CUDA 上下文与算子首次调用要现场编译内核、KV Cache 的显存池还没预分配完、前缀缓存是冷的。表现就是刚扩容出来的副本，前几十个请求的首字延迟是稳态的数倍，而负载均衡按轮询照样给它分了 1/N 的流量，把整体分位数拉坏。治理有三个层次可以叠加：最轻的是把 readiness 判定从端口探活改成一次真实的小推理（比如生成 1 个 token），这样进程只有真正能干活才会被加入端点；中等的是在启动脚本里做主动预热，加载完成后自己先跑几次短请求，把编译与显存池走通再让 readiness 转绿；最重的是把编译缓存挂卷持久化复用，从根上缩短这段时间。

滚动更新时流式回答被截断，怎么彻底解决？

要同时处理三件事，少一件都不够。第一，让 kubelet 等一等端点传播：Pod 终止时端点摘除和发 TERM 信号是两条并行时间线，kubelet 不会等 EndpointSlice 传播到各节点，所以没有 preStop 时新请求还可能被路由到正在关闭的进程。preStop 里 sleep 一段覆盖传播上界的时间是唯一能让 kubelet 停下来的杠杆。第二，给足宽限期：terminationGracePeriodSeconds 默认只有 30 秒，而流式生成 P99 常达一两分钟，超时的在途生成会被 KILL 截断；要按 preStop 时长 + 最坏在途时长 + 余量 来设。注意官方特别说明宽限期覆盖的是 preStop 与容器正常停止的总时长——文档举的例子是宽限期 60 秒、preStop 用了 55 秒、容器还需 10 秒，结果容器仍被提前杀掉。第三，应用侧要有排空逻辑：收到 TERM 后停止接受新连接、等在途生成结束再退出，否则前两步的努力都白费。此外 GPU 打满的集群做不到 maxSurge: 1 加 maxUnavailable: 0（没有空闲卡起新副本），只能临时扩容节点、接受容量下降一个副本，或安排在低峰期发布。

为什么不能用 CPU 利用率给 LLM 推理服务做自动扩缩？

因为 CPU 在推理服务里只承担请求解析、分词、序列化这些边角工作，真正的瓶颈在 GPU 算力与显存带宽，两者几乎不相关。后果是双向的：一个 GPU 已打满、请求在队列里排长龙的副本，CPU 可能只有 20% 利用率，HPA 认为它很闲、一个副本都不加（漏扩）；反过来一波短请求的批量分词能把 CPU 顶起来，触发无谓扩容（误扩）。按有效性排序，可用的信号是队列深度（最直接反映供需差）、在途并发序列数（与引擎最大批容量对比即知饱和度）、KV Cache 占用率（显存侧真实压力），再往后是首字延迟分位数（最贴近体验但有窗口滞后，作为扩缩输入会加剧震荡）。GPU 利用率看起来合理其实是次优信号——连续批处理下它常年在高位，区分不出"忙碌但从容"和"已经过载"。KServe 的 Workload Variant Autoscaler 就是明确按 KV Cache 利用率、队列深度、请求饱和度做决策的。阈值不能拍数字，要按引擎的最大批容量来定。

HPA 为什么追不上 LLM 的流量高峰，副本数还会震荡？

把两组时间尺度并排就清楚了：HPA 控制器默认 15 秒调谐一轮，扩容方向默认没有稳定窗口（一有信号立刻扩），缩容方向默认 300 秒稳定窗口并取窗口内最高推荐值。这套默认值是为秒级起 Pod 的服务设计的。而 LLM 副本从创建到真正能扛流量要走完调度、拉镜像、加载权重、图编译与预热，通常是分钟量级。于是典型剧本是：第 2 分钟指标超阈值、立刻决定扩容，第 7 分钟新副本才就绪、而高峰已过大半，随后指标回落、300 秒窗口一到副本被缩掉——峰期大量超时，峰后却在为无用副本付费。用控制论的说法，这是一个死区时间（分钟级冷启动）远大于采样周期（15 秒）的系统，必然过冲与欠冲交替。有效的做法不是继续调 HPA 参数，而是换策略组合：按历史流量定时预扩容、常驻热副本吃溢出、把权重与编译缓存做本地复用以压小死区时间本身、扩容方向设非零稳定窗口、并把自动扩缩当兜底而非主力。KEDA 在这个场景有两个实用差异：支持 idleReplicaCount 缩到闲置档，以及为模型加载留出初始冷却期。

要不要预留热副本，怎么算这笔账？

预留热副本是唯一能真正对抗冷启动的手段，问题只在养几个。成本侧的算法很直白：预留成本等于热副本数乘单副本单价乘全时长，是按月计费的固定支出；收益侧买到的是"峰值前若干分钟的容量"，属于按事件计的。所以判断依据是峰值爬升速度与副本就绪时间的比值：如果流量能在十分钟内涨到平时数倍，而副本就绪要五六分钟，那么自动扩缩基本救不到场，热副本几乎是唯一选项；如果峰谷是以小时为尺度缓慢变化的（白天忙夜里闲），自动扩缩就够了，预留反而是浪费。一个常见起点是让预留容量能独立扛住日常峰值的六到七成，剩余靠扩容补，但这个比例必须用真实流量曲线校准而不能照抄。同时要把三条降本路径一起考虑：压缩冷启动时间（权重本地缓存加编译缓存复用）能直接减少需要预留的量，定时预扩容能把预留时段从全天缩短到峰前时段，两者都比单纯加热副本便宜。容量数字怎么从压测反推见 DP16。

Helm、Operator、KServe、Ray Serve 这些层，什么时候该上、什么时候不需要？

判断标准很朴素：当前这一层让你重复劳动的次数，是否已经超过下一层带来的认知与故障成本。Helm 的价值点很单一——用"同一套模板加不同的值"表达多环境差异，机制就是它的取值优先级（chart 的 values.yaml 最低，然后是父 chart，然后是可重复传入的 -f 值文件、后传覆盖先传，最高是 --set）。对 LLM 服务值得抽成变量的是副本数、GPU 资源名、模型标识与权重来源、startupProbe 预算、宽限期、扩缩阈值；探针路径、卷结构这类跨环境一致的东西该留在模板里，每开一个变量就多一处漂移可能。自研 Operator 的门槛高，三问都为"是"才值得：同一套多步流程每周执行数次、流程必须按状态机推进、多团队需要复用同一语义。KServe 适合平台团队要给多个业务方提供统一契约的场景，它的长期价值在 Open Inference Protocol 带来的客户端与后端解耦以及 Knative 的请求级扩缩与缩容到零，代价是把整套生态带进来、可能遮住引擎的调优旋钮。Ray Serve 适合推理形态本身就是多模型多阶段流水线、或团队已在用 Ray 的情况，代价是 Ray 集群成为第二个要运维的平台。最重要的一条是不要跳级：先把原生对象的探针、宽限期、GPU 资源、卷挂载调稳，再上 Helm，最后才考虑平台层。
