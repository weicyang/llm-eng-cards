Docker 与 K8s 不是"小工具与大工具"的关系，而是两种不同的世界观：前者你直接管理进程，出了事人来救；后者你只声明期望状态，由控制循环反复把现实拉回声明。K8s 的复杂度不是白付的——它换来的是"人不在场时系统也会自我修正"这一条能力。判断该不该上 K8s，本质上就是判断你是否真的需要这条能力，以及是否付得起它的账单。

一、两种模型的本质差异：进程管理与控制循环

用 Docker 或 Compose 部署时，你下的每一条指令都是命令式的：起容器、停容器、换镜像重启。系统的"当前状态"就是你上一串操作的累积结果，没有人在旁边记录"本来应该是什么样"。容器崩了，Docker 的重启策略能把它拉起来，但宿主机宕了就没人管；镜像换了一半失败，栈就停在半新半旧的中间态。

K8s 换了一套模型：你提交的是期望状态（desired state）——"我要 3 个副本、跑这个镜像、每个要 1 张 GPU"。集群里的每个控制器都在跑一个控制循环（reconcile loop）：读当前状态、和期望状态比对、执行动作消除差异、再读一遍。杀掉一个 Pod，控制器发现"当前 2 个、期望 3 个"，于是补一个。这就是"自愈"的全部机制，它并不神秘，但它带来一个关键性质：系统的正确性不依赖于操作者当时在不在场。

同一件事的两种执行方式 命令式（Docker / Compose） ───────────────────────────────────────────────────── 人 ──► docker compose up -d ──► 容器起来 人 ──► docker compose pull && up -d ──► 换版本 容器崩 ──► restart policy 拉起（同一台机器上） 宿主宕 ──► 没人管，等人上线处理 状态的唯一记录 = 机器的现状 + 你的记忆/文档 声明式（Kubernetes） ───────────────────────────────────────────────────── 人 ──► 提交期望状态（replicas=3, image=v2, gpu=1） │ ▼ 持续、无人值守 ┌──────────────────────────────┐ │ observe：当前 2 个副本 │ │ diff ：期望 3 个，差 1 │ │ act ：创建 1 个 Pod │◄──┐ └──────────┬───────────────────┘ │ └──────────────────────►┘ 循环不止 容器崩 ──► 控制器补 宿主宕 ──► 控制器在别的节点上重建 状态的唯一记录 = 集群里的声明（可入 Git）

1.1 这套复杂度为什么是"换来的"

控制循环要能工作，前提条件一条都不能少：得有一个持久化的期望状态存储（etcd）、一个统一的读写入口（API Server）、一个决定放哪的调度器、每台机器上一个执行代理（kubelet）、以及一堆各管一摊的控制器。这就是 K8s 组件多、概念多的原因——它们不是设计者的偏好，而是"无人值守自我修正"这个目标的必要成本。S06 · K8s 部署痛点与 Porter 解决方案 第一章把这套复杂性的三大根源（声明式模型、分布式本质、多租户）拆得很细，这里不重复。

反过来说，如果你的场景本来就不需要无人值守的自我修正——一台固定的机器、副本数固定、有人白天盯着、夜里挂了第二天修也能接受——那么这套成本就是纯支出，没有对应收益。这是本卡最重要的一句话，第四章的决策表全部由它推导。

维度命令式（Docker / Compose）声明式（Kubernetes）
你提交的东西动作序列（起、停、换）目标状态描述
谁负责收敛人（或人写的脚本）控制器，持续循环
幂等性需自己保证，重复执行可能出错天然幂等，重复提交同一声明无副作用
失败反馈命令立即报错，直观声明合法但可能永远不收敛（Pending / CrashLoop）
节点故障该机器上的服务全丢控制器在其他节点重建
状态真相在哪机器现状集群声明（可与 Git 对齐）
心智负担低：会写 shell 就能上手高：要理解最终一致性与调谐语义

命令式是"我告诉你怎么做"，声明式是"我告诉你做成什么样，你自己想办法一直保持"。前者的失败模式是"命令报错"，后者的失败模式更难受——声明合法但永远不收敛，YAML 提交成功、Pod 却一直 Pending，没有任何一条命令报错。这就是 K8s 排障比 Docker 排障难的根本原因：你不是在看"哪一步失败了"，而是在追问"为什么差异消不掉"。

二、部署流程逐步对照：从代码到线上

把同一个 LLM 应用从代码送到线上，两条路线的步骤数差得并不多，差别在每一步的失败模式复杂度以及"谁来处理失败"。

2.1 两类失败模式的性格差异

Docker 路线的失败大多是即时且局部的：命令报错、容器退出、端口不通，站在机器上看日志基本能定位。K8s 路线的失败分成两类：一类同样即时（YAML 语法错、Schema 错，apply 直接拒绝），另一类是延迟且分布式的——声明被接受了，但差异消不掉。后者的排查要跨对象追（Deployment → ReplicaSet → Pod → Node → 事件），这就是 S06 里讲的"故障排查三级跳"。其中最典型的是 Pending——Pod 对象已创建但调度器找不到满足条件的节点，GPU 资源未注册、污点排斥、亲和性冲突都会落到这一个状态里。

阶段Docker 侧典型故障K8s 侧典型故障难度差异的来源
构建缓存打穿、上下文过大同左，另加 Registry 权限与配额基本相同，见 S09
分发无（本机构建本机跑）ImagePullBackOff、大镜像拉取超时K8s 多了一跳网络

调度不存在（就这一台）Pending：GPU 不足、污点、亲和性冲突K8s 独有的一整类问题
就绪start_period 太短判 unhealthy探针参数错 → 反复重启永不就绪同一病根，K8s 后果更重；探针机制见 S05

示例场景：某团队把已经稳定运行的单机 Compose 栈迁到自建 K8s，迁移当天卡在两个点上，合计耗时约 6 小时。第一个是推理 Pod 一直 Pending，原因是节点池没装 device plugin，nvidia.com/gpu 这个资源在集群里根本不存在，调度器找不到满足条件的节点——而 Compose 时代 GPU 是"本机就有"的隐含前提，没人意识到它需要显式注册。第二个是 Pod 起来后陷入重启循环，因为团队把 Compose 里 start_period: 300s 的语义错记成了 initialDelaySeconds，没有配 startupProbe，liveness 在权重还没加载完时就判定失败。两个问题都不是 K8s 的缺陷，而是"隐含前提变成了显式声明"这个转换本身的成本。

迁移到 K8s 的真实工作量，不在于把 compose 文件翻译成 YAML，而在于把原来靠"机器就长这样"隐含成立的前提，一条条变成显式声明：GPU 要注册成可调度资源、权重路径要变成卷声明、慢启动要变成探针参数、依赖顺序要变成探针与初始化容器。翻译语法是一小时的活，补齐隐含前提是几天的活。

三、优缺点的诚实账单

关于 K8s 的讨论常见两种失真：一种只讲自愈与弹性、不讲代价；另一种只吐槽 YAML 复杂、不承认它解决了真问题。这里说的自愈指控制器在无人干预的情况下把偏离的当前状态拉回声明，包括容器崩溃后重建与节点故障后跨机重调度。把两栏并排写下来，判断会容易得多。

3.1 K8s 换来了什么

收益机制Compose 能否近似做到

水平扩缩HPA/KEDA 按指标改副本数，配合节点自动扩容不能。副本数固定，扩容要人加机器

3.2 K8s 收了什么费

资源开销控制面与每节点系统组件常驻占用 CPU/内存节点规格别太碎，避免系统开销占比过高

示例场景：一个四人小团队为一个内部知识库助手自建了三节点 K8s，跑一个 7B 模型和一套检索服务，副本数常年是 2。半年后回顾工时账：业务代码之外，用在集群本身的时间约占总工时的两成——两次版本升级、一次 CNI 插件导致的跨节点 DNS 间歇失败、一次证书过期导致 kubectl 全面不可用。而这半年里"自愈"真正救过场的次数是 1（一台机器磁盘故障）。事后他们把栈退回到两台机器上的 Compose + systemd，加一个健康检查驱动的主备切换脚本，可用性没有下降，运维工时下降到接近于零。这不是"K8s 不好"，而是这个场景的收益项只有 1 条命中、成本项 6 条全中。

算这笔账的正确方式不是比较功能表长度，而是逐条问"这条收益我今年会用到几次"。自愈一年救两次场、扩缩容一年用不上、多环境只有两套且很少漂移——那么账单的收益侧几乎是空的，成本侧却是逐月计费的。反过来，如果流量有明显峰谷、机器超过一手之数、要同时服务多个业务方，收益侧会迅速把成本压下去。

4.1 三条经验阈值

表格之外，有三条比较可靠的经验判断。第一，"两台机器"是一个真实的门槛：一台机器上 Compose 完全够用；两台可以用 Compose 加一个主备切换脚本撑住；到三台，手工决定"谁跑在哪台"开始变成持续的认知负担，这时集群级调度才开始划算。第二，没有专人养集群就不要自建集群——上面那个示例场景里六条成本项全中，根源就在这里；如果确实需要 K8s 的能力但没有运维编制，正确选项是托管 K8s 而不是自建。第三，先问"痛点是不是部署形态造成的"：很多团队上 K8s 想解决的其实是"发布流程没有自动化"或"配置散落各处"，这两件事在 Compose 上做 CI 与配置版本化同样能解，换编排器只是把问题带到了更复杂的环境里。

  • 先把痛点归因清楚：是缺自愈弹性，还是缺流程自动化
  • 需要 K8s 能力但缺人手时选托管控制面，别自建
  • 迁移前先在 Compose 上补齐健康检查与资源限额，这些声明在 K8s 上会直接复用
  • 先迁无状态的网关与检索，推理服务最后迁
  • 把权重外置作为迁移前置条件，否则镜像拉取会成为扩容瓶颈
  • 业务层的方案选型另算，参考 DP01 · 大模型部署方案选型决策
  • 不要为了"技术栈现代化"上 K8s，账单是逐月付的
  • 不要在没有第二台机器时上 K8s，单节点集群只有成本没有收益
  • 不要把 Compose 文件机械翻译成 YAML，隐含前提要显式补齐
  • 不要指望 HPA 解决冷启动，模型加载分钟级，见 S11 第五章
  • 不要同时迁编排器和换推理框架，两个变量一起动无法归因
  • 不要用"大厂都用 K8s"当理由，大厂的机器数和团队规模才是理由

这张表可以压成一句话：K8s 解决的是"多台机器 + 变化的负载 + 无人值守"这个组合。三个条件同时成立时它几乎无可替代；缺任意一个，就有更便宜的方案能达到同样效果；三个都不成立，上 K8s 只是把复杂度从业务搬到了基础设施。

五、中间态与替代路线

"Docker 还是 K8s"是个假二选一。实际可选的谱系上有好几个中间点，很多团队的最优解就在中间。其中Serverless GPU 指按调用秒数计费、无常驻实例的推理托管形态，闲置期不付费，代价是每次冷启动都要重新加载权重。

选路线的顺序应该是"从右往左砍"：先明确你真正需要哪几条能力，然后挑能提供这些能力的最左边那个方案。绝大多数人的错误方向相反——先选定 K8s，再去论证为什么需要它。

六、分布式部署的几种形态

"分布式部署"在 LLM 场景下至少指三件很不一样的事，它们对编排层的要求差别极大，混在一起谈就会得出错误结论。

6.1 形态一：多副本无状态扩容

每个副本都装得下完整模型，副本之间不通信，请求随便打给谁都能处理。这是 K8s 最擅长的形态——它的整个工作负载模型就是围绕"可替换的无状态副本"设计的，Deployment、Service、HPA 全部直接可用。唯一的 LLM 特色是副本的启动时间是分钟级而非秒级，这会影响扩缩容策略而不影响架构。

6.2 形态二：多机多卡的张量并行与流水线并行

模型装不进单机，必须把它切开跨机器跑：张量并行把每层的权重矩阵按行列切到多张卡上，每层都要做一次集合通信，对网络延迟极其敏感；流水线并行把不同层分到不同设备，通信量小但引入流水线气泡。两者的原理与选择见 DP04 · 模型部署与 Serving，这里只讲它和编排层的冲突。

冲突有三层。第一，这类作业的副本不是可替换的：一个 rank 挂了，整组都得重启，而 K8s 的默认心智是"单个 Pod 可独立重建"。第二，它需要全体同时就位才能开始工作，而默认调度器是逐个 Pod 调度的——资源紧张时会出现"leader 调度上了、worker 一直 Pending"的局面。社区在 LeaderWorkerSet 的 gang scheduling 提案里明确记录了这个问题：调度器可能优先调度 leader 而让 worker 挂起，结果是每个服务都缺零件，没有任何一个能提供服务，而资源已经被占满——这就是资源死锁。第三，它对拓扑有要求：跨机张量并行希望所在节点在同一机架或同一网络域内，否则通信延迟会吃掉并行收益。

为什么多机多卡作业需要 gang scheduling 默认逐个调度（无 gang）：集群剩 5 张卡，两个作业各需 4 张 作业A leader ──► 调度成功（占 1 卡） 作业A worker ──► Pending（等 3 卡） 作业B leader ──► 调度成功（占 1 卡） 作业B worker ──► Pending 结果：占了 2 卡，两个作业都跑不起来，剩余 3 卡谁都不够 → 死锁 gang scheduling（Volcano / Kueue 等）： 把一组 Pod 当作一个准入单位（PodGroup / Workload） minMember = 1 leader + (size-1) worker 资源不够 ──► 整组不调度，一张卡都不占 资源够 ──► 整组一起落地 结果：要么全跑，要么全等，不存在半截占用 配套能力：拓扑感知调度让同一组的 rank 落在同一机架/网络域内 注意：一个作业只用一套 gang 机制，Kueue 与 Volcano 不要同时门控同一负载

解决路径是引入 gang scheduling（成组调度）：把一组 Pod 声明成一个不可分割的准入单位，资源不足时整组不落地，避免部分占用。生态里 Volcano 与 Kueue 是两个常见选择，LeaderWorkerSet 可以为每个副本自动创建对应的 PodGroup，其 startupPolicy 决定 minMember 取整组大小还是取 1。有一条实践约束值得记住：一个作业只走一套 gang 机制，不要让两套准入控制同时门控同一负载。

6.3 形态三：Prefill / Decode 分离部署

把预填充阶段和解码阶段拆成两组独立伸缩的服务，是近年生产系统的重要变化。它对编排层提出的新要求是"两组服务需要各自独立的扩缩边界，但又要按同一套 SLA 协同"——KServe 的 LLMInferenceService 就把"预填充独立扩缩"列为显式能力。这个架构本身的原理、收益与代价见 DP12 · Prefill / Decode 分离架构。

形态副本可替换性调度要求与 K8s 默认模型的契合度需要的额外组件
多副本无状态扩容完全可替换逐个调度即可高，原生支持无（HPA/KEDA 可选）
单机多卡张量并行副本内不可拆，副本间可替换要求整卡组落在同一节点中，需要资源与拓扑约束device plugin，节点亲和

Prefill / Decode 分离各组内可替换两组独立扩缩、协同 SLA中，需要路由与扩缩协同推理网关、分组自动扩缩
批处理与在线混跑批任务可抢占优先级、抢占、队列与配额中，需队列层Kueue/Volcano 等队列组件

K8s 的世界观是"一堆可互换的无状态小盒子"。多副本扩容与这个世界观完全一致，所以顺畅；多机多卡并行作业与它正相反——一组身份固定、必须同时在场、一个挂了全重启的进程。所以在 K8s 上跑这类作业不是配几个字段的事，而是要额外引入成组调度与拓扑感知，把"可互换"的假设显式补成"不可拆分"。判断你是哪种形态，比判断该不该用 K8s 更重要。

Q&A

一句话说清 Docker 部署和 K8s 部署的本质差别是什么？

Docker 部署是命令式的进程管理：你提交动作序列（起、停、换镜像），系统的当前状态就是你历史操作的累积，没有任何地方记录"本来应该是什么样"，所以出了事必须有人来救。K8s 部署是声明式的：你提交期望状态（几个副本、什么镜像、要几张卡），集群里的控制器持续跑调谐循环——读当前状态、和期望比对、执行动作消除差异、再读一遍。自愈没有魔法，就是这个循环。关键性质是系统正确性不依赖操作者是否在场：杀掉一个 Pod 会被自动补上，节点宕机会在别的节点重建。所有 K8s 的复杂度（etcd、API Server、调度器、kubelet、一堆控制器）都是这个循环成立的必要条件，也就是说复杂度是"换来的"而非白付的——前提是你确实需要无人值守的自我修正。

我们只有一台 GPU 服务器，上 K8s 有意义吗？

基本没有。K8s 的核心收益——跨节点重建、集群级调度装箱、水平扩缩——全部需要"多台机器"这个前提，单节点集群把这三条全废掉了，剩下的只有成本：控制面与系统组件常驻占用、YAML 复杂度、集群自身的升级与证书维护、以及新增的一整层故障面。单机上更划算的做法是 Compose 加 systemd 托管，拿到开机自启和崩溃重启；如果有第二台机器，可以再加一个健康检查驱动的主备切换脚本，这样连"机器宕机"这一档也覆盖了。真正该考虑 K8s 的信号是机器数上到三台以上且还会继续加、副本数需要随流量自动变、以及要求无人值守自动恢复。如果单机的痛点其实是"发布流程手工、配置散落"，那该做的是 CI 与配置版本化，换编排器解决不了这个问题。

K8s 的哪些收益是 Compose 加脚本真的无法替代的？

严格来说只有三条无法便宜替代。第一是跨节点自愈：Docker 的重启策略只在本机生效，宿主宕机就是服务不可用，而控制器会在其他节点上重建；用脚本模拟这件事需要自己实现健康判定、领导者选举和状态收敛，本质上是在重写控制器。第二是按指标自动扩缩并配合节点扩容：Compose 的副本数是写死的，扩容要人加机器。第三是混合负载的调度装箱与优先级抢占：在线推理、批处理、微调任务混跑时需要一个集群级资源账本和抢占策略。其余的很多"K8s 优势"在单机上都有廉价替代：服务发现 Compose 内置 DNS 就够、配置版本化靠 Git、滚动更新可以手工蓝绿、回滚靠镜像 tag 管理。所以判断标准很清楚：如果这三条你今年一条都用不上，账单的收益侧基本是空的。

从 Compose 迁到 K8s，真正的工作量在哪里？

不在语法翻译，而在把隐含前提变成显式声明。Compose 时代很多事是"机器就长这样"所以自然成立的：GPU 本机就有、权重就在某个目录、服务启动慢但反正没人管、依赖顺序靠 depends_on 一行搞定。到了 K8s，每一条都要显式化：GPU 必须由 device plugin 注册成可调度资源，否则 Pod 永远 Pending；权重路径要变成 PVC 或初始化容器的拉取逻辑；慢启动要变成 startupProbe 的 failureThreshold × periodSeconds 预算，配错会导致无限重启循环；依赖顺序要拆成探针与初始化容器。此外还要新学一整类以前不存在的故障——Pending 的原因分析（资源不足、污点、亲和性冲突）、ImagePullBackOff、语义正确但不收敛。经验上语法翻译是小时级的活，补齐隐含前提是几天级的活，建议先迁无状态的网关和检索服务，推理服务最后迁，并把权重外置作为迁移的前置条件。

除了 Docker 和 K8s，还有哪些中间选择？

谱系上至少有六个点。Compose + systemd 用 systemd 管住栈的开机自启和崩溃重启，拿到单机自愈，适合长期稳定运行的内部服务。单机多卡直接起多进程，按卡切分让多个推理进程各占若干卡，适合模型装得进单机且副本数固定的场景，代价是端口与显存要自己规划。托管 K8s 保留调度、自愈、弹性，把控制面运维外包，是"需要 K8s 能力但没有运维编制"时的正确答案。Nomad 提供跨机调度与滚动更新而概念少得多，适合要调度但用不上 K8s 生态的团队，代价是 device plugin、Operator 这类 AI 相关组件的生态远不如 K8s。Serverless GPU 按调用付费、零常驻成本，但冷启动明显，适合低频突发与实验负载。托管推理 API 完全绕过部署，适合需求还没验证的阶段。选择的正确顺序是先明确真正需要哪几条能力，再挑能提供这些能力的最左边（最简单）那个方案。

为什么多机多卡的并行推理和 K8s 的假设"天生别扭"？

因为 K8s 的工作负载模型建立在"一堆可互换的无状态副本"之上，而多机张量并行或流水线并行的进程组恰好相反：每个 rank 身份固定、必须全体同时在场才能开始工作、一个挂了整组都要重启、而且对彼此的网络距离敏感。这带来三个具体冲突。一是可替换性假设不成立，默认的"单 Pod 独立重建"心智会导致组内状态不一致。二是逐个调度会造成资源死锁：社区在 LeaderWorkerSet 的 gang scheduling 提案里明确记录，资源紧张时调度器可能把多个作业的 leader 都调度上去而让 worker 全部 Pending，结果每个作业都缺零件、没有一个能服务，而卡已经被占满。三是拓扑无感知：跨机张量并行希望同组 rank 落在同一机架或网络域内，否则集合通信延迟会吃掉并行收益。解决路径是引入 gang scheduling（Volcano、Kueue 等），把一组 Pod 声明成不可分割的准入单位，资源不足时整组不落地、一张卡都不占，再配合拓扑感知调度。注意一个作业只走一套 gang 机制，不要让两套准入控制同时门控同一负载。

K8s 上的"分布式部署"具体指哪几种形态，它们对编排层的要求一样吗？

至少三种，要求差别很大。第一种是多副本无状态扩容：每个副本都装得下完整模型、副本间不通信，这是 K8s 最擅长的形态，Deployment、Service、HPA 全部原生可用，唯一的 LLM 特色是启动是分钟级而非秒级，影响扩缩策略而不影响架构。第二种是多机多卡的张量并行或流水线并行：模型装不进单机，必须切开跨机跑，组内不可替换、需成组调度与拓扑感知，与 K8s 默认假设冲突最大，要额外引入 gang scheduler 与 LeaderWorkerSet 之类的组件。第三种是Prefill / Decode 分离：预填充和解码拆成两组独立伸缩的服务，编排层要支持两组各自独立的扩缩边界又按同一套 SLA 协同（KServe 的 LLMInferenceService 就把"预填充独立扩缩"列为显式能力）。此外还有批处理与在线混跑，需要队列、优先级与抢占。把这几种形态混在一起讨论就会得出错误结论——判断你属于哪一种，比判断该不该上 K8s 更重要。

怎么向管理层解释"K8s 的复杂度不是白付的"？

把它拆成收益清单和成本清单，逐条标注"我们今年会用到几次"。收益侧共七条：跨节点自愈、滚动更新、水平扩缩、声明式回滚、调度装箱、统一服务发现、可沉淀的平台扩展点。成本侧共六条：学习曲线、配置复杂度（语义错不报错）、集群自身的运维人力、故障面扩大、控制面与系统组件的常驻资源开销、发布链路变长。关键在于两侧的计费方式不同——收益是按事件计的（自愈一年救几次），成本是按月计的（每月都要付）。所以论证要落在频次上：如果流量峰谷差三倍以上、机器超过三台、发布每天多次、要求无人值守恢复，收益侧会迅速压过成本侧；如果副本数常年固定、只有两台机器、发布每周一两次，那这笔账就是纯支出。同时给出替代方案的对比（Compose+systemd、托管 K8s、Nomad、Serverless GPU），让讨论从"用不用 K8s"变成"用哪个方案最便宜地拿到我们需要的能力"。

为什么在 K8s 上排障比在 Docker 上难那么多？

因为失败模式的性格完全不同。Docker 的失败大多即时且局部：命令报错、容器退出、端口不通，站在机器上看日志基本能定位。K8s 的失败分两类：一类同样即时（YAML 语法错、字段名拼错，apply 直接拒绝），另一类是延迟且分布式的——声明合法、被接受了，但差异永远消不掉。典型是 Pod 一直 Pending（GPU 资源未注册、污点、亲和性冲突、配额不足）或标签与选择器不匹配导致副本永远是 0，整个过程没有任何一条命令报错。排查这类问题要跨对象追（Deployment → ReplicaSet → Pod → Node → 事件），这就是 S06 里讲的"故障排查三级跳"。此外 K8s 还引入了业务之外的故障层：控制面、网络插件、存储插件、调度器。所以在 K8s 上排障的正确提问方式不是"哪一步失败了"，而是"为什么这个差异消不掉"——前者是线性回溯，后者要同时检查资源账本、调度约束、准入策略和探针状态。

如果流量有明显峰谷，是不是就一定该上 K8s 做弹性？

峰谷明显是必要条件而不是充分条件，还得看冷启动能不能被吸收。LLM 副本的启动时间是分钟量级（拉镜像、加载权重、预热与首次编译），而 HPA 的调谐是十几秒一轮、默认扩容无稳定窗口、缩容有 300 秒稳定窗口。如果你的峰值是在十分钟内涨起来的，那么"检测到指标超阈值"到"新副本真正能服务"之间的几分钟就是纯超时期，弹性并没有救到场。这种情况下更有效的组合是：按历史流量做定时预扩容（在峰前把副本拉上去）、常驻一到两个热副本吃溢出流量、把权重放节点本地缓存缩短加载时间，把自动扩缩当作兜底而不是主力。反过来，如果峰谷是以小时为尺度缓慢变化的（比如白天忙夜里闲），自动扩缩就能真正省钱。所以判断顺序是：先量峰谷的变化速度与副本冷启动时间的比值，再决定弹性该由自动扩缩承担还是由预留容量承担。机制细节见 S11 第五章。
