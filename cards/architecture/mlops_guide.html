从实验到生产 — 机器学习工程化全链路指南

一、MLOps 概述

传统软件坏了会报错，机器学习系统坏了只会"变笨"——代码一行没改、服务全绿，指标却在悄悄下滑。MLOps 的全部工作，就是让这种沉默的退化变得可见。

1.1 DevOps → MLOps → LLMOps 演进

传统软件只需管理代码；而 ML 系统需要同时管理 数据 + 模型 + 代码 三个维度的变更。

阶段关注点核心差异
DevOps代码构建、测试、部署确定性：相同输入 → 相同输出
MLOps数据 + 模型 + 代码非确定性：数据漂移、模型退化
LLMOpsPrompt + 评估 + 成本 + 安全模型通常不自训练；侧重 Prompt 管理与评估

1.1.1 三个维度的变更如何汇进同一条流水线

DevOps 只有代码一条输入，ML 系统有数据、模型、代码三条，任何一条变了都可能改变线上表现。把三条输入画在一起，就能看出 MLOps 的每个组件分别在守哪一条。

1.2 ML 系统的特殊性

  • 数据依赖 — 数据质量直接决定模型质量；需持续监控数据分布
  • 实验性 — 同一任务可能有数百次实验，需要可追溯性
  • 模型退化 — 线上数据分布变化导致 concept drift / data drift
  • 计算成本 — 训练与推理的资源需求远超传统应用
  • 可解释性 — 法规/业务要求可审计、可解释

二、实验追踪

实验追踪的价值不在训练当天，而在三个月后——当有人问"线上这个模型是怎么来的"，你能不能在五分钟内答上来。

2.1 为什么需要实验追踪？

ML 项目的核心是实验驱动：每次修改超参数、数据集或模型结构都构成一次实验。没有追踪 = 无法复现 = 无法迭代。

NeptuneSaaS / 自托管元数据管理灵活、大规模实验企业级、大量实验

三、模型版本管理

Model Registry 的本质是给模型加一层"制品仓库"：训练产出的是候选，只有走完晋级流程的那一个才配叫生产版本。

3.1 MLflow Model Registry

Model Registry 是模型从实验到生产的"中转站"，提供版本控制与生命周期管理。

# 注册模型
result = mlflow.register_model(
    "runs:/<run_id>/model",
    "fraud-detection-model"
)

# 推进到 Staging
client = mlflow.tracking.MlflowClient()
client.transition_model_version_stage(
    name="fraud-detection-model",
    version=3,
    stage="Staging"
)

3.2 模型版本与阶段

None→ Staging→ Production→ Archived
  • None — 刚注册，未经验证
  • Staging — 通过基本测试，等待 A/B 测试或人工审核
  • Production — 当前线上服务版本
  • Archived — 历史版本，保留以备回滚

3.3 模型血缘 (Lineage)

模型血缘 (Lineage) 回答："这个模型是用什么数据、什么代码、什么超参数训练出来的？"

  • 数据血缘 — 训练集版本、预处理步骤
  • 代码血缘 — Git commit hash、训练脚本版本
  • 环境血缘 — Python 版本、依赖包版本 (conda.yaml)
  • 实验血缘 — 关联的 MLflow Run ID

四、CI/CD for ML

ML 的 CI/CD 比软件多了一道关卡：软件的门禁问"能不能跑通"，模型的门禁还要问"比现在线上那个好不好"。

4.1 ML Pipeline 全流程

数据验证→ 特征工程→ 模型训练→ 模型评估→ 模型部署→ 监控

4.2 GitHub Actions 集成示例

# .github/workflows/ml-pipeline.yml
name: ML Pipeline
on:
  push:
    paths: ['data/**', 'src/**', 'configs/**']

jobs:
  data-validation:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Validate data schema
        run: python scripts/validate_data.py
      - name: Check data drift
        run: python scripts/check_drift.py

  train:
    needs: data-validation
    runs-on: [self-hosted, gpu]
    steps:
      - name: Train model
        run: python src/train.py --config configs/prod.yaml
      - name: Log to MLflow
        run: python scripts/register_model.py

  evaluate:
    needs: train
    steps:
      - name: Run model tests
        run: pytest tests/model_tests/
      - name: Performance gate
        run: python scripts/perf_gate.py --min-f1 0.85

  deploy:
    needs: evaluate
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to staging
        run: ./scripts/deploy.sh staging

五、模型注册与发布

发布策略的差别只有一句话：Shadow 不承担风险也拿不到反馈，Canary 用少量真实用户换真实信号，Blue-Green 用双份成本换秒级回滚。

5.1 Model Card

Model Card 是模型的"说明书"，由 Google 提出，包含：

  • 模型详情 — 架构、训练数据、版本、作者
  • 预期用途 — 适用场景与限制
  • 性能指标 — 各评估集上的指标，按子群体分拆
  • 伦理考量 — 偏差分析、风险评估
  • 训练细节 — 数据预处理、超参数、训练时长

5.2 模型签名验证

from mlflow.models.signature import infer_signature

signature = infer_signature(X_train, model.predict(X_train))
mlflow.sklearn.log_model(model, "model", signature=signature)

# 部署时自动验证输入格式
# 输入不符合签名 → 返回 400 错误

签名确保：输入数据类型 / 形状与训练时一致，防止"静默错误"。

5.3 发布策略

策略原理适用场景
Canary小比例流量(5-10%)先切新模型高风险模型、金融/医疗
Blue-Green两套完整环境，一键切换需要快速回滚
Shadow新模型并行推理但不返回结果对比评估、无风险验证
A/B Testing随机分流，统计显著性检验效果对比、产品决策

示例场景：一个风控评分模型每周重训一次，离线 AUC 从 0.871 提升到 0.883，评估门控通过，按流程发布上线。

问题：上线第二天，人工复核队列的量涨了约 40%，但欺诈捕获率没有变化——模型在离线指标上更好，线上却在制造无效工作量。排查发现训练用的是 Feature Store 里的离线特征，而线上服务读的是实时链路，其中一个"近 7 天交易次数"字段线上口径按自然周计算、离线口径按滚动窗口计算，典型的 Training-Serving Skew。

方案：先按版本 pinning 回滚到上一模型止血；随后把该特征的定义收敛到 Feature Store 单一定义，训练与推理都从同一处取数；并在 CI 中加一条新检查——抽样比对线上线下同一批样本的特征值，差异率超过 0.5% 直接卡住发布。

效果：回滚后 20 分钟内复核队列恢复正常；特征统一后重新上线，AUC 0.879，复核量与旧版本持平而捕获率提升约 6%。这类问题在离线评估里永远发现不了，只能靠特征一致性检查拦住。

5.4 回滚策略

  • 自动回滚 — 监控指标触发阈值 → 自动切回上一版本
  • 版本 pinning — 服务端指定精确的模型版本号
  • 流量驱动 — 逐步将新版本流量降为 0

六、特征存储 (Feature Store)

Feature Store 解决的不是存储问题，而是"同一个特征在训练和推理时被算了两遍"的问题——两段代码总有一天会漂移。

6.1 为什么需要 Feature Store？

核心问题：Training-Serving Skew — 训练时和推理时使用不同的特征计算逻辑，导致模型效果下降。

Feature Store 提供统一的特征定义、存储和服务，确保训练与推理使用完全相同的特征。

6.2 主流工具

工具类型核心特征
Feast开源轻量、支持多数据源、Python SDK
Tecton商业企业级、实时特征、流批一体

七、LLMOps 特有挑战

LLMOps 和 MLOps 的分水岭在于：你多半不再训练模型，于是全部工程重心从"怎么训得更好"转到"怎么评得准、控得住成本"。

7.1 Prompt 版本管理

Prompt 是 LLM 应用的"源代码"，需要像管理代码一样管理 Prompt：

  • 版本控制 — Git 或专用工具 (LangSmith, PromptLayer) 追踪 Prompt 变更
  • 模板化 — 将 Prompt 拆分为 System / User / Few-shot 模板
  • A/B Testing — 不同 Prompt 版本的效果对比
  • 环境隔离 — dev / staging / prod 使用不同 Prompt 配置
# prompt_registry.yaml
prompts:
  summarizer:
    v1:
      model: gpt-4o
      system: "你是一个专业的文档摘要助手..."
      temperature: 0.3
    v2:
      model: gpt-4o
      system: "你是一个精准的信息提取专家..."
      temperature: 0.1
      active: true  # 当前生产版本

7.3 成本追踪

  • Token 级别计量 — input tokens vs output tokens 分别计费
  • 按用户/功能归因 — 哪个功能/用户消耗最多
  • 成本优化手段 — 模型降级 (GPT-4 → GPT-4o-mini)、缓存、Prompt 压缩
  • 把 Prompt、模型名、温度这些参数放进配置仓库并打版本，让每次线上回答都能对应到一个确定的配置版本
  • 先建评估集再改 Prompt：没有固定评测集的"优化"只是换一种错法
  • 成本按功能和用户维度归因，而不是只看一个总账单，这样才知道该优化哪条链路
  • LLM-as-Judge 的打分定期用人工标注校准一次，确认裁判本身没有漂
  • 把用户的负反馈自动回流进评估集，让评估集随业务一起长
  • 不要直接在生产配置里手改 Prompt，改完没有 diff、没有记录，出问题无法定位是哪次改动
  • 不要只用几个例子肉眼判断 Prompt 好坏，样本量太小的结论和抛硬币差不多
  • 不要把 LLM-as-Judge 的分数当绝对真值，它对长回答、对自家模型的输出都存在系统性偏好
  • 不要为了省钱无脑把所有请求降级到小模型，先按任务难度分流，简单请求降级、复杂请求保留
  • 不要跳过幻觉监控直接上线 RAG 应用，检索到了不等于答对了，忠实度需要单独度量

7.4 幻觉监控

  • 事实一致性检测 — 将回答与检索文档比对 (RAGAS Faithfulness)
  • 自我一致性 — 同一问题多次采样，检查答案一致性
  • 引用验证 — 检查引用的来源是否真实存在
  • 人类反馈闭环 — 用户标记不准确回答 → 反馈到评估数据集

八、数据版本管理

数据版本管理的目标不是"存下每一份数据"，而是"任何时候都能把某次训练的输入原样重建出来"。

8.1 DVC (Data Version Control)

DVC 是"数据的 Git"，用 Git 管理元数据（.dvc 文件），大文件存储在远程存储（S3 / GCS / Azure Blob）。

# 初始化
dvc init

# 追踪大数据文件
dvc add data/training_set.parquet
git add data/training_set.parquet.dvc .gitignore
git commit -m "Add training dataset v1"

# 推送数据到远程存储
dvc remote add -d myremote s3://my-bucket/dvc-store
dvc push

# 切换数据版本
git checkout v2.0
dvc checkout

8.2 数据血缘追踪

数据血缘回答的问题：

原始数据→ 清洗→ 特征工程→ 训练集→ 模型→ 预测
  • 上游追踪 — 这条训练数据来自哪个原始表？
  • 下游影响 — 修改这个 ETL 步骤会影响哪些模型？
  • DVC Pipeline — 用 dvc.yaml 定义 DAG，自动追踪依赖
# dvc.yaml
stages:
  preprocess:
    cmd: python src/preprocess.py
    deps:
      - data/raw/
      - src/preprocess.py
    outs:
      - data/processed/

  train:
    cmd: python src/train.py
    deps:
      - data/processed/
      - src/train.py
    outs:
      - models/model.pkl
    metrics:
      - metrics.json:
          cache: false

🎯 Q&A

Q1: MLOps 与 DevOps 的核心区别是什么？

核心区别在于 ML 系统的三重管理维度：

  • DevOps 只管理代码的构建、测试、部署
  • MLOps 需要同时管理数据 + 模型 + 代码
  • ML 系统具有非确定性：相同代码 + 不同数据 = 不同结果
  • ML 系统需要持续监控：模型会因数据漂移而退化
  • ML 系统有实验性：需要追踪数百次实验的超参数和指标

额外挑战：数据版本管理、特征工程管道、模型注册中心、A/B 测试、数据隐私合规等。

Q2: 解释 MLOps 成熟度模型 Level 0 到 Level 2 的区别

Level 0（手动过程）：数据科学家在 Jupyter Notebook 中手动实验，手动导出模型文件，手动部署。没有自动化、没有版本控制、没有监控。常见于 POC 阶段。

Level 1（ML Pipeline 自动化）：训练流程自动化（数据预处理 → 训练 → 评估通过 Pipeline 串联），但部署仍需手动操作。有实验追踪，但 CI/CD 未覆盖 ML 组件。

Level 2（CI/CD 自动化）：完整的自动化流程 — 代码提交 → 自动数据验证 → 自动训练 → 自动评估（Performance Gate）→ 自动部署。包含自动化测试（数据测试 + 模型测试），支持持续训练（CT）。

Q3: 什么是 Training-Serving Skew？如何解决？

定义：训练时和推理时使用不同的特征计算逻辑或不同的数据处理方式，导致模型在线上的表现与离线评估不一致。

常见原因：

  • 训练用 Python 预处理，推理用 Java 重写（逻辑不一致）
  • 训练用历史批量数据，推理用实时流数据（时间窗口不同）
  • 特征计算依赖的上游数据在线上不可用

解决方案：

  • Feature Store — 统一特征定义，训练和推理共享同一份特征代码
  • 特征日志 — 在推理时记录实际使用的特征值，与训练数据对比
  • 端到端测试 — 用线上数据回放验证离线/在线结果一致性
Q4: 如何设计 ML 系统的 CI/CD Pipeline？

完整 ML CI/CD Pipeline 设计：

触发条件：代码变更(Git Push) 或 数据变更(新数据到达) 或 定时触发

  1. 数据验证 — Schema 检查、数据质量检查、漂移检测 (Great Expectations)
  2. 特征工程 — 特征计算、Feature Store 更新
  3. 模型训练 — 使用版本化数据和配置训练，记录到实验追踪
  4. 模型评估 — 性能指标 vs 基线、公平性检查、A/B 预评估
  5. Performance Gate — 指标低于阈值自动阻断
  6. 模型注册 — 推入 Model Registry，设为 Staging
  7. 集成测试 — API 延迟、吞吐量、兼容性
  8. Canary 部署 — 5% 流量验证 → 逐步放量 → 全量
  9. 监控 — 数据漂移、模型性能、延迟、成本
Q5: 对比 Canary 部署和 Blue-Green 部署在 ML 场景中的应用

Canary 部署：

  • 将少量流量 (5-10%) 导向新模型，监控关键指标
  • 指标正常则逐步增加流量比例
  • 优点：风险可控，可观察真实效果
  • 缺点：需要流量分割基础设施，验证时间较长
  • 适用：金融风控、医疗诊断等高风险场景

Blue-Green 部署：

  • 维护两套完全相同的环境，一键切换
  • 优点：回滚极快（秒级切换），环境完全隔离
  • 缺点：成本翻倍（两套环境），无法渐进验证
  • 适用：需要快速回滚能力的场景

ML 场景特殊考虑：模型性能需要足够样本量才能评估，因此 Canary 更常用于 ML 模型部署。Blue-Green 适合需要秒级回滚的场景。Shadow 模式（并行推理不返回结果）是最安全的验证方式。

Q6: DVC 和 Git LFS 的区别？什么时候用 DVC？

Git LFS：

  • 将大文件替换为指针文件，实际内容存在 LFS 服务器
  • 与 Git 工作流无缝集成
  • 局限：不支持数据 Pipeline、不能追踪数据血缘、存储受限于 Git 托管平台

DVC：

  • 同样用指针文件（.dvc），但支持任意远程存储 (S3/GCS/Azure/HDFS)
  • 核心优势：支持 dvc.yaml 定义数据 Pipeline (DAG)
  • 支持数据血缘追踪、实验对比 (dvc metrics diff)
  • 与 ML 工作流深度集成

选择建议：如果只需管理几个大文件 → Git LFS 即可。如果需要数据 Pipeline、血缘追踪、实验管理 → 选 DVC。大部分 MLOps 场景推荐 DVC。

Q7: LLMOps 与传统 MLOps 的主要区别？

核心差异：

维度MLOpsLLMOps
训练自行训练模型通常使用预训练模型 (API / Fine-tune)
核心资产数据 + 模型权重Prompt + RAG Pipeline + 评估数据集
版本管理模型版本 + 数据版本Prompt 版本 + 模型 API 版本
评估标准指标 (F1, AUC)主观评估 (LLM-as-Judge, 人工评审)
成本模型计算资源 (GPU 小时)API Token 费用（按量计费）
特有挑战数据漂移、模型退化幻觉、安全对齐、Prompt 注入

LLMOps 特有需求：Prompt Registry、幻觉检测 Pipeline、成本归因系统、安全护栏 (Guardrails)、语义缓存。

Q8: 如何搭建 LLM 应用的评估 (Evals) 体系？

分层评估体系：

  1. 单元级评估
    • 单个 Prompt 的输出质量（准确性、格式、安全性）
    • 使用 LLM-as-Judge 自动打分（GPT-4 作为评判者）
  2. 组件级评估（RAG 场景）
    • 检索质量：Context Precision, Context Recall (RAGAS)
    • 生成质量：Faithfulness（是否忠于检索内容）, Answer Relevancy
  3. 端到端评估
    • 任务完成率、用户满意度、对话轮数
  4. 安全评估
    • Prompt 注入测试、有害内容检测、PII 泄露检测

工具链：OpenAI Evals / RAGAS / DeepEval / LangSmith / Phoenix (Arize)

自动化：每次 Prompt 变更自动触发评估 → 指标对比 → 通过则部署。

Q9: Feature Store 的架构是怎样的？解释 Feast 的核心概念

Feature Store 架构（以 Feast 为例）：

  • Feature View — 特征的定义（名称、类型、数据源、实体关联）
  • Entity — 特征关联的业务实体（用户 ID、商品 ID）
  • Data Source — 特征数据的来源（BigQuery、Parquet、Kafka）
  • Offline Store — 存储历史特征，用于训练（BigQuery / Redshift / 文件）
  • Online Store — 存储最新特征值，用于实时推理（Redis / DynamoDB）
  • Feature Service — 将多个 Feature View 组合，对外提供 API

核心工作流：

  1. feast apply — 部署特征定义到基础设施
  2. feast materialize — 将离线特征物化到在线存储
  3. store.get_historical_features() — 训练时获取历史特征
  4. store.get_online_features() — 推理时获取在线特征
Q10: 如何监控线上模型的性能退化？

监控维度与策略：

  1. 数据漂移 (Data Drift)
    • 监控输入特征分布变化（KS 检验、PSI 指标）
    • 工具：Evidently AI, Alibi Detect, WhyLabs
  2. 概念漂移 (Concept Drift)
    • 监控模型预测分布变化（标签延迟场景用代理指标）
    • 方法：滑动窗口准确率、预测置信度趋势
  3. 性能指标
    • 延迟 P50/P95/P99、吞吐量、错误率
    • 工具：Prometheus + Grafana, Datadog
  4. 业务指标
    • CTR、转化率等业务 KPI 的变化趋势

自动化响应：指标触发阈值 → 告警 → 自动回滚 / 触发重训练。关键是设定合理的告警阈值和响应 SOP。
