一、五段全景：一条请求路径的分工

无论自建 vLLM 集群还是走云厂商 API，一条 LLM 推理请求经过的链路都可以切成五段。这个切法不是随意的——每一段优化的目标函数不同、故障的表现形式不同、能观测的指标也不同，所以它天然就是排障和容量规划的责任边界。

五段里最容易在架构图上被画丢的是 ③。很多人把"Gateway 直连 Worker"当成全部，但真实系统里请求级的调度决策一定存在，只是位置不定：小规模时它就是 Gateway 里的一段负载均衡代码；上了 K8s 推理扩展后它是 InferencePool 感知的智能路由（第二章）；进入引擎进程后它是 continuous batching 的迭代级调度器（第三章）。全景图的价值之一，就是让你在任何具体系统里都能把这几处"隐形调度器"指出来。

把五段想成快递网络：Client 是寄件人，Gateway 是收件网点（验身份、称重、限流），Scheduler 是分拨中心（决定上哪辆车、和哪些包裹拼车），Worker 是干线卡车（真正拉货的运力），GPU 是发动机（马力和油箱决定上限）。包裹慢了，你要能说出是网点压件、分拨排队、还是卡车不够——这三者的解法完全不同。

1.1 两种部署形态下全景怎么变形

上面的五段是自建形态。走云厂商 API 时，②③④⑤ 全部折叠进厂商边界，你只剩 ① 和"厂商给你的限流与计量面板"；混合形态（自建扛基线、API 吃峰值）则是在 ② 之后加一个分流决策，把部分请求转发给外部 API。三种形态的选型判据（合规、SLA、盈亏平衡点）在 DP01 · 大模型部署方案选型决策，单机 Docker 与 K8s 集群的形态差异在 S10，这里不重复。要记住的只有一条：形态变了，五段的职责划分不变，变的只是每段由谁实现、你能观测到哪一层。

二、Gateway 层：路由为什么必须感知推理

Gateway 的机制细节——虚拟钥与项目预算、多厂商熔断 fallback、语义缓存的键怎么设计——在 S08 · LLM 推理网关 已经讲透，这里只讲一个全景视角的问题：为什么传统网关/负载均衡放在 LLM 链路里会失灵，以及"推理感知"到底感知什么。

2.1 默认负载均衡的三个失灵点

K8s Service 或 Nginx 的轮询/最少连接假设"每个请求代价近似、每个后端状态由连接数刻画"。LLM 推理把两条都推翻：

  • 请求代价差两个数量级：一个 8 token 的回答和一个 2000 token 的长文生成，占住 batch 槽位的时间差百倍。轮询把两者等价派发，长请求扎堆的副本队列瞬间堆积。
  • 连接数不等于负载：Worker 的真实压力由 KV Cache 占用率和引擎等待队列深度决定。一个副本可能只有 10 个连接但全是长上下文请求，显存已经顶满；另一个 50 个连接但都是短请求，还很从容。
  • 副本不是等价的：多 LoRA 场景下只有加载了对应 adapter 的副本能服务；前缀缓存场景下，把同一会话路由回原副本能命中缓存、省掉整段 prefill。无状态轮询会把这些局部性全部打散。

推理感知路由（inference-aware routing）就是让路由决策读取 Worker 的实时推理状态而不是连接计数。K8s 社区的 Gateway API Inference Extension 把它标准化成两个资源：InferencePool（一组可服务某模型的副本集合，向上游暴露队列深度、KV 占用等指标）和 InferenceModel（某模型名的流量分发策略，含优先级与目标池）。阿里云 ACK 2026-09 的文档给出的形态很有代表性：同一个 inference-gateway，8080 端口是标准 HTTP 路由，8081 端口是接入 InferencePool 的 LLM 路由，后端 5 副本 vLLM 服务 Qwen-2.5-7B——让团队可以灰度对比两种路由的实际效果。

生产案例（社区来源）：markaicode.com 2026-05 发布的 EKS 实测架构（vLLM v0.6.3 + K8s v1.31 + A100/T4）给出了一个"重网关"的三层数据面：API Gateway（Envoy，TLS 终结 + 每租户 100 req/min 限流）→ Model Router（自研 Go 服务，模型注册表 + 请求去重）→ NATS JetStream 队列（消息数 >1000 时向客户端反压）→ vLLM 推理 Pod。三条经验数字值得记住：GPU 必须独占——跨模型共享 GPU 导致 OOM kill 和约 40% 的吞吐退化；权重预热进共享 PVC——扩容时 Pod 启动从 120 秒降到 10 秒以内；HPA 用 GPU 指标而非 CPU——条件是 GPU util >70% 或队列深度 >50。这套架构把"队列"显式独立成一层，本质是把 ③ 的集群级调度从 Gateway 里拆出来单独扩展。

判断你的网关是不是"LLM 原生"，只需要问一个问题：它做路由决策时，看得见 Worker 的显存和队列吗？看得见，就是推理感知路由；看不见，它就只是在转发。传统网关的所有失灵都源于此——它把 GPU 集群当成了一组无差别的无状态 Web 服务器。

三、调度层：集群级与引擎级的两级调度

全景图里的 ③ 实际上是两级不同的调度器，很多人把它们混为一谈，排障时就会找错责任方。

还有一层容易被忽略：K8s 调度器不参与请求级调度。它只回答"这个 Pod 放到哪个节点"，是整数账本（GPU 不可超卖、调度器看不见卡内状态），这套机制和它的三个硬限制在 S11 第一章。所以完整的调度栈其实是三层：K8s 调度 Pod（分钟级）、集群级调度选副本（每请求）、引擎级调度组 batch（每解码步）。

3.1 引擎级调度为什么值得单独一个进程

引擎级调度的机制深潜（Orca 迭代级调度、三队列与抢占、chunked prefill）在 DP11，这里只讲架构形态的演进。掘金 2026-06 的四大引擎对比文章总结得很清楚：vLLM v1（2025 年起默认）把调度逻辑从 Worker 里拆出来，独立成 EngineCore 进程——Scheduler 在 EngineCore 里做 prefix hash 查找、block 分配、chunked prefill 拆分，Worker 只做前向计算。这样调度策略可以独立演进、独立重启，不被推理进程拖住。SGLang 走的是另一条路：overlap scheduling（重叠调度），CPU 在 GPU 执行 batch N 的同时准备 batch N+1，把调度开销藏进计算时间里，接近零开销。

两级调度的时间尺度（一条请求经历的调度决策） 请求到达 ──► 集群级调度（一次，微秒~毫秒） │ "发给 Worker B" ▼ Worker B 引擎队列（waiting） │ ▼ 引擎级调度（每个解码步都重新决策，~10ms 一步） ┌──── step k ────┬──── step k+1 ────┬──── step k+2 ────┐ │ batch: A C F │ batch: A C F G │ batch: C G │ │ │ (G 新插入) │ (A F 完成退出) │ └────────────────┴──────────────────┴──────────────────┘ 连续批处理：完成的退出、到达的插入，batch 成员步步在变 · 你的请求的 TPOT，取决于每一步和它同批的"邻居"数量 · 集群级调度决定你排哪条队；引擎级调度决定你每轮能不能被带上 · 抢占（preemption）：显存不够时引擎会踢掉低优先级请求重排队
示例场景：某团队发现两个副本负载严重不均——A 副本 P95 TTFT 超过 3 秒，B 副本不到 800ms，而 Gateway 用的是最少连接策略。查队列深度发现 A 的 waiting 队列长期是 B 的 4 倍：原因是长上下文请求（2 万 token 的文档问答）连接存活时间长，"最少连接"反而把短请求持续派给已经在消化长请求的 A。把路由信号换成"队列深度 + KV 占用"后，两副本的 P95 TTFT 收敛到同一水平。这个案例的教训是：集群级调度的失灵，症状却表现在延迟指标上——不懂两级调度的分工，就会去错地方调参（比如加大引擎 max_num_seqs，反而恶化）。

两级调度像医院的"分诊台 + 叫号系统"：分诊台（集群级）决定你去哪个诊室，叫号系统（引擎级）决定这一轮医生看谁。分诊台看的是各诊室候诊人数（队列深度），不是门口的占地面积（连接数）；叫号系统则可能为了效率把复诊的（前缀缓存命中）优先叫进去。投诉"等太久"时，先分清是挂错了诊室，还是诊室内叫号策略的问题。

四、Worker 层：推理进程内部与并行策略

Worker（④）就是推理引擎进程本身。引擎选型（vLLM / SGLang / TensorRT-LLM / TGI 的四框架对比与场景决策）在 DP05，编译式路线在 DP27，这里讲全景视角需要的两块：进程内部的分段结构和一个 Worker 横跨多卡多机时的形态。

4.1 Worker 进程内部的四段结构

主流引擎的进程内部都可以切成四段（以 SGLang 的结构为例，vLLM v1 对应 EngineCore + Worker）：

单个 Worker 进程内部（以 SGLang 形态为例） HTTP/gRPC 入口 │ ▼ ┌─────────────────┐ 文本→token；参数校验 │ TokenizerManager │ （CPU 密集，可成为高 QPS 下的瓶颈） └────────┬────────┘ ▼ ┌─────────────────┐ 每解码步决策：带谁、分配哪些 KV block │ Scheduler │ RadixCache（前缀树组织的 KV 复用） └────────┬────────┘ overlap scheduling：与 GPU 计算并行 ▼ ┌─────────────────┐ 真正的前向计算 │ ModelRunner │ FlashInfer/FlashAttention + CUDA Graph └────────┬────────┘ ▼ ┌─────────────────┐ token 池与权重常驻显存 │ KV Pool + 权重 │ 显存 = 权重 + KV + 激活 + 框架开销 └─────────────────┘ ⑤ GPU 就在这段结构的正下方：ModelRunner 的每个 kernel 都在与显存带宽和算力打交道（第五章）

这个分段解释了为什么分词和流式回传也会成为瓶颈：TokenizerManager 和 detokenize 都在 CPU 上，高 QPS 短请求场景（比如 embedding 化的分类调用）能把 CPU 打满而 GPU 还很闲——这时加 GPU 没用，该加的是 Worker 副本数或者把分词拆成独立服务。

4.2 并行策略：一个逻辑 Worker 横跨几张卡

当模型装不进单卡（或单卡吞吐不够），一个逻辑 Worker 就要横跨多卡甚至多机。四种并行策略的分工（阿里云 ACK 2026-08 多机部署文档的总结）：

策略切什么通信特征适用场景
DP 数据并行不切模型，每卡一份完整副本，分流请求几乎无卡间通信小模型扩吞吐；多副本本质上就是进程级 DP
TP 张量并行把权重矩阵按列/行切到多卡每层两次 AllReduce，要求 NVLink 级带宽单卡装不下的大模型；对延迟友好
PP 流水线并行按层切，前段卡的输出送后段卡点对点传激活值，带宽要求低超深模型、跨机扩展；有流水线气泡
EP 专家并行MoE 的专家分布到不同卡All-to-All 路由 token 到专家MoE 架构（Mixtral、Qwen-MoE 系）

多机 TP 的部署形态以 LeaderWorkerSet（LWS，K8s SIG 项目）为代表：leader Pod 跑推理服务主进程（vLLM 的 Ray head 或 SGLang 主节点），worker Pod 持有其余 GPU 分片，推理时与 leader 通信；LWS spec 里的 size: 2 直接对应 --tensor-parallel-size 2。阿里云文档的例子是 Qwen3-32B（32.8B dense，32K 上下文）用 TP=2 拆到两个节点各一张 32GB+ 的卡上。这条链路的工程细节——/dev/shm 共享内存、NCCL 网卡选择、启动顺序——在 S11 和 S09 有对应章节。

另有一种把 Worker 按阶段拆开的形态：P/D 分离（Prefill 与 Decode 部署在不同卡池，KV 跨节点传输），DistServe 报告最高 7.4× 的 goodput 提升、Mooncake 报告 +59%~498%——它改变了全景图的 ④⑤ 段结构，值得单独一卡，见 DP12。本卡只需记住：P/D 分离后，③ 的调度要多回答一个问题——prefill 完成后 KV 传给哪个 decode 池。

引擎差异的量级感（知识库口径，源自 DP05）：同一台 H100 上跑 Llama-2-70B，SGLang 约 16,200 tok/s、vLLM 约 12,500 tok/s——约 30% 的差距来自 RadixAttention 前缀复用与 overlap scheduling 的组合。而 Orca 式连续批处理相对静态批处理的收益，论文口径是 36.9×，生产环境因流量成分不同一般落在 2~8×。这两个数字放在一起说明：Worker 层的选型收益是"几十个百分点"级，调度机制的收益是"倍数"级——全景图上越往 ③ 走，杠杆越大。

Worker 层的架构决策全是"切与不切"：模型太大切权重（TP）、太深切层（PP）、是 MoE 切专家（EP）、流量大复制整个 Worker（DP）。切法决定通信模式，通信模式决定能不能跨机——TP 每层都要 AllReduce，出了 NVLink 域性能就崩，所以"TP 不出机、PP 才跨机"是默认的部署铁律。

五、GPU 层：显存账本与两阶段瓶颈

⑤ 是全链路的物理底座，也是所有"为什么不能更大 batch / 更长上下文 / 更多并发"问题的最终答案。GPU 硬件结构在 DP14，推理瓶颈的完整推导在 DP10，KV Cache 机制在 DP08。这里只给全景图需要的三笔账。

GPU 层对全景图的意义是"最终否决权"：上游四段的所有优化——路由再聪明、调度再精细、引擎再快——最后都要过显存和带宽这两道闸。看到"吞吐上不去"先别动 ②③ 的参数，先看 ⑤ 的 KV 占用率是不是已经 90%+：是，就要在 Worker 层解决（量化、加卡、P/D 分离）；不是，才轮到调度层背锅。

6.2 全景视角的 Do / Don't

  • 给每段配独立指标：Gateway 看拒绝率与路由耗时，Scheduler 看队列深度，Worker 看 KV 占用与抢占，GPU 看 util 与显存水位
  • trace-id 从 ① 贯穿到 ④，一个请求的全链路时间可以拼出来
  • 路由用推理感知信号（队列深度 / KV 占用），灰度对比默认轮询
  • GPU 独占分配，扩缩容信号用队列或 KV 而不是 CPU
  • 长请求与短请求分池或限 max_tokens，避免同批拖慢
  • 不要用连接数/轮询给 LLM 副本做负载均衡
  • 不要跨模型共享同一张 GPU（OOM 连带 + 约 40% 吞吐退化）
  • 不要让冷副本直接接流量（前几十请求 TTFT 数倍于稳态）
  • 不要在 TTFT 高时盲目调引擎 batch 参数——先分清是 ③ 排队还是 ⑤ 算力
  • 不要把 TP 拉出单机 NVLink 域（跨机 TP 通信量撑不住）

全链路排障的诀窍是"用指标把段切开"：TTFT 把 ①②③ 和 ⑤-prefill 捆在一起，TPOT 把 ⑤-decode 和同批邻居捆在一起，429/503 单独指向 ②，断流单独指向发布与超时。所以监控体系（S03）和这张全景图是一对：全景图告诉你有哪些段，指标体系（DP28）告诉你每段用什么数字看住。

Q&A

已经有 Nginx / K8s Service 了，为什么还要专门的 LLM 网关？

因为 LLM 流量的三个特征让通用网关的假设失效：请求代价差百倍（轮询不再公平）、后端状态由显存和队列决定（连接数不再代表负载）、会话有缓存局部性（无状态转发会打散前缀缓存命中）。专门网关补的就是这三块：推理感知路由、token 级计量计费、面向流式长连接的超时与排空策略。如果规模小（单模型单副本），确实可以先不上一独立网关——但路由信号的读取（哪怕只是轮询换成队列深度探测）迟早要做。机制细节见 S08。

K8s 调度器、集群级调度、引擎级调度，三者到底谁管什么？

三层各管一个时间尺度：K8s 调度器管"Pod 放哪个节点"（分钟级、整数账本、看不见 GPU 卡内状态，见 S11）；集群级调度管"请求发哪个副本"（每请求一次，输入是队列深度/KV 占用/亲和性，实现在 Gateway 或 InferencePool）；引擎级调度管"这个解码步带哪些请求"（每步毫秒级，continuous batching + 抢占，实现在引擎进程内，见 DP11）。排障时先用症状定位是哪一层：副本间不均 → 集群级；吞吐上不去/抢占频发 → 引擎级；Pod 起不来/卡分配失败 → K8s 层。

vLLM v1 为什么要把 Scheduler 拆成独立的 EngineCore 进程？

为了调度与计算解耦演进。v0 时代调度逻辑和 Worker 前向在同一进程里，调度策略升级要动整个引擎、调度卡顿会直接拖慢推理。v1 把 Scheduler、KVCacheManager 收进独立的 EngineCore 进程，Worker 只做前向计算——调度可以独立迭代（prefix hash、chunked prefill 拆分都在 EngineCore 里），进程间用 IPC 通信。SGLang 的思路不同但目标一致：用 overlap scheduling 让 CPU 端调度与 GPU 端计算完全并行，把调度开销藏进计算时间（掘金 2026-06 引擎对比文章的总结）。两条路线都印证一个全景结论：调度是独立的架构层，不是引擎的附属品。

TP / PP / DP / EP 四种并行，部署时怎么组合？

默认铁律是"TP 不出机、PP 才跨机"：TP 每层两次 AllReduce，必须留在 NVLink 域内（单机 8 卡）；PP 只传层间激活值，可以跨机但有流水线气泡；DP 是进程级复制，用于扩吞吐；EP 只对 MoE 模型有意义，All-to-All 通信对网络要求介于 TP 和 PP 之间。常见组合：70B dense 单机 8 卡 TP=8；更大的模型 TP=8（机内）× PP=N（跨机）；MoE 用 EP+TP 混合。多机形态用 LWS 组织（leader Pod + worker Pod，size 对应 TP/PP 度数），阿里云 2026-08 的文档用 Qwen3-32B TP=2 跨两节点做了最小示例。显存怎么算见 DP02，扩展效率怎么量见 DP10。

一个请求很慢，怎么快速定位卡在哪一段？

按归因口诀切：先看错误码——429/503 直接定位 ② Gateway（限流/预算/并发上限）。再看 TTFT 和 TPOT 哪个高：TTFT 高而 GPU util 低 → ③ 排队问题（查队列深度和路由均衡）；TTFT 高且 GPU util 高 → ⑤ prefill 算力或前缀缓存未命中（查输入长度分布）；TPOT 高 → ⑤ decode 带宽或同批有超长请求（查 batch 成分和 KV 占用）。流式中途断 → 发布窗口或超时配置（②④）。刚扩容后变慢 → 冷副本直接接了流量（④，查 readiness 探针形态）。前提是每段有独立指标 + trace-id 贯穿，否则只能猜。

什么时候需要引入消息队列 / P-D 分离这类"重架构"？

都有明确的触发条件，不要预支复杂度。消息队列（如 markaicode 架构里的 NATS JetStream）在两种情况下值得上：需要显式反压保护后端（突发流量下宁可让客户端排队也不打爆 GPU），或调度层需要独立扩展、请求去重、优先级重排。P/D 分离（DP12）的触发条件是 TTFT 和 TPOT 的 SLA 冲突：prefill 抢占 decode 导致吐字卡顿，且流量规模大到两个池的利用率收益能覆盖 KV 跨节点传输的成本——DistServe 报告 7.4× goodput、Mooncake +59%~498%，但都发生在大规模场景。小系统先做好推理感知路由和连续批处理，杠杆更大。

自建与云 API 形态下，这张全景图分别退化/增强成什么样？

云 API 形态：②③④⑤ 折叠进厂商，你只剩 ① 和厂商面板，可控点变成重试策略、超时、多厂商 fallback（S08 的熔断机制）和成本路由（ST24 价格表）。自建形态：五段全在你手里，但每段的运维成本按月计费（S10 的收益-成本口径）。混合形态最常见：Gateway 之后加分流决策，基线流量走自建（单位成本低、数据可控），峰值与长尾走 API（弹性、免运维）。判据见 DP01 的四维过滤和盈亏平衡推导；掘金 2026-06 电商案例的经验线是"QPS>500 且 prompt 长 → 自托管"。

全景图里哪一段的技术演进最快，架构上该怎么预留？

③ 调度层演进最快：从轮询到推理感知路由（Gateway API Inference Extension 2025-2026 才标准化）、从进程内调度到独立 EngineCore、从混合部署到 P/D 分离，每一年都在变。预留方式是把路由决策收敛到单一组件（别让业务代码直连 Worker 地址），并让 Worker 暴露标准指标端点（vLLM/SGLang 都有 /metrics），这样换路由策略不动 Worker。④ 引擎层次之——用 OpenAI 兼容 API 作为契约可以隔离引擎更换（DP05 的选型结论）。⑤ GPU 层最稳定，瓶颈物理规律（算力 vs 带宽）十年未变，变的只是数字。
