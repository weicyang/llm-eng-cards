容器不是"轻量虚拟机"，而是一个被限制了视野（namespace）和额度（cgroup）的普通宿主进程，它看到的文件系统是若干只读层叠出来的幻象（联合文件系统）。这三句话解释了容器的几乎全部工程后果：为什么镜像层缓存怕 COPY 写错顺序、为什么 GPU 驱动必须来自宿主而不能装进镜像、为什么把几十 GB 模型权重塞进镜像会在拉取环节报复你。

一、容器不是虚拟机：namespace、cgroup 与联合文件系统

把容器理解成虚拟机是绝大多数容器化事故的认知起点。虚拟机的隔离边界在硬件层：hypervisor 虚拟出 CPU、内存、磁盘，客户机跑自己的内核。容器完全不是这样——容器里的进程就是宿主内核上的普通进程，用 ps 在宿主上能直接看见它。Docker 官方安全文档把容器的实现直接归结为两组内核设施：启动容器时"Docker 在幕后为它创建一组 namespace 和 cgroup"。

1.1 namespace 负责"看不见"，cgroup 负责"用不了"

namespace（命名空间）是内核对全局资源视图的虚拟化：进入自己 PID namespace 的进程只能看到本 namespace 内的进程树，自己是 1 号进程；mount namespace 让它看到独立的挂载表；network namespace 给它独立的网卡、路由表与端口空间。隔离的是可见性，不是资源量。cgroup（control group，控制组）解决的是另一半问题：资源的计量与限额。Docker 文档对二者分工的表述很直白——cgroup 本身"不阻止一个容器访问或影响另一个容器的数据和进程"，它的价值在于挡住资源耗尽型的拒绝服务，保证一个跑飞的应用不会把整台机器拖死。

容器的三根支柱与它们各自管的事 ┌──────────── 容器进程（宿主上的普通进程） ────────────┐ │ │ 可见性 ───► │ namespace │ │ pid → 只看得见自己这棵进程树，自己是 PID 1 │ │ mount → 独立挂载表，看不到宿主的 / │ │ net → 独立网卡 / 路由 / 端口空间 │ │ ipc / uts / user / cgroup → 消息队列、主机名、UID │ │ │ 额度 ───► │ cgroup │ │ cpu.max → CPU 时间片配额（超了被节流） │ │ memory.max → 内存上限（超了被 OOM Kill） │ │ pids / io → 进程数、块设备带宽 │ │ │ 文件 ───► │ 联合文件系统（overlay2） │ │ 只读镜像层 ×N + 可写容器层 ×1 → merged 视图 │ └──────────────────────────────────────────────────────┘ │ 共享同一个宿主内核（这是所有兼容性约束的源头）

1.2 共享内核带来的三条硬约束

容器与宿主共享内核，这一条推导出后面几章反复出现的限制。第一，容器里装不了内核模块，也装不了 GPU 驱动的内核态部分——所以第五章会看到 nvidia-container-toolkit 的做法是把宿主的驱动挂进容器，而不是让镜像自带驱动。第二，容器不是安全边界，默认的能力集与挂载组合并不构成完整隔离，Docker 官方安全文档明确提示这一点；把不可信代码放进容器执行需要额外加固，这个视角见 SEC13 · AI Agent 沙箱与安全执行。第三，内存限额是硬杀：cgroup 的 memory.max 一旦被突破，内核直接 OOM Kill 进程，没有"降速"这种柔性处理，而 CPU 超限只是被节流。

维度虚拟机容器工程后果
隔离层次硬件虚拟化，独立内核内核 namespace，共享宿主内核容器内无法装驱动 / 内核模块
启动代价秒到分钟级（要引导内核）毫秒到秒级（就是 fork+exec）容器可以做进程级弹性
镜像体积GB 级完整系统盘只含用户态文件，可压到几十 MB分发成本低，但权重打进去会失效
资源限额hypervisor 分配固定规格cgroup 动态限额，可超卖CPU 可超卖，GPU 不行（见 S11）

虚拟机是"另一台机器"，容器是"同一台机器上戴了眼罩、限了口粮的进程"。凡是需要"另一台机器"才能做到的事（换内核、装驱动、绝对隔离），容器都做不到；凡是靠"限制视野和额度"就能做到的事（环境一致、快速启停、密集部署），容器都做得比虚拟机好一个数量级。

二、镜像分层与写时复制：层缓存怎么命中

镜像是一叠只读层，容器运行时在最上面再加一层可写层。Docker 默认的 overlay2 存储驱动用内核的 OverlayFS 实现这件事：只读镜像层是 lowerdir，容器可写层是 upperdir，二者联合挂载后暴露的 merged 目录才是容器里看到的根文件系统，另有一个 workdir 供 OverlayFS 内部使用。官方文档说明 overlay2 原生支持最多 128 层。

2.1 写时复制：第一次写会整文件搬家

写时复制（copy-on-write）是分层能省空间的原因，也是它最容易咬人的地方。读一个文件时，OverlayFS 从上往下找到第一份就直接用，多个容器共享同一份只读层，所以起 20 个同镜像容器几乎不额外占磁盘。但第一次写一个来自镜像层的文件时，驱动要先执行 copy_up，把整个文件从 lowerdir 复制到 upperdir，之后的修改才落在副本上。文件越大，第一次写的代价越大——这就是官方"写密集型负载请用 volume 而不要写容器可写层"这条建议的机制解释。对 AI 应用尤其要留意：如果模型权重躺在镜像层里，而进程启动时要就地改写（例如某些框架会把权重转换成自己的缓存格式写回原目录），一次 copy_up 就能在磁盘上再复制出几十 GB。

2.2 层缓存的失效规则决定构建速度

构建时 builder 逐条比对指令与已缓存层。官方缓存失效文档给出的规则可以浓缩成三句话：基础镜像先比，任何一条指令没能精确命中，它之后的所有层全部重建；COPY、ADD 以及带 bind mount 的 RUN 会额外按文件元数据算校验和，只要参与的文件元数据变了就失效（但仅 mtime 变化不算）；其余 RUN 只比命令字符串本身，不看容器内文件是否会被更新。

示例场景：某 RAG 服务的 CI 每次提交都要 8 分 40 秒才产出镜像，团队一开始以为是 CI 机器慢。逐层看构建日志发现 pip install 每次都在重跑——Dockerfile 里是先 COPY . /app 再装依赖，而依赖里有几个需要现场编译的包。两处改动：把 requirements.txt 单独提前 COPY，再补一份 .dockerignore 排除 .git、__pycache__、本地测试用的 *.parquet。改完后无依赖变更的提交构建时间稳定在 45 秒上下，构建上下文从 1.3 GB 降到 9 MB。这里省下的不是"CI 更快了"，而是把"依赖变更"和"代码变更"两件事在缓存层面解耦开了。

层缓存是一条链，不是一张网：任何一环断了，后面全断。所以 Dockerfile 的排序原则只有一句——越少变的写在越上面，越常变的写在越下面。依赖清单一年变几次，源码一天变几十次，把它们写进同一个 COPY 就等于让源码的变更频率去支配依赖安装的代价。

三、Dockerfile 工程化：多阶段构建与体积治理

能跑的 Dockerfile 和能上生产的 Dockerfile 差距很大，差距集中在四件事：构建产物与构建工具是否分离、构建上下文是否干净、运行身份是否是 root、镜像体积是否被治理过。

3.1 多阶段构建：把编译器留在上一阶段

多阶段构建（multi-stage build）指一个 Dockerfile 里写多个 FROM，每个 FROM 开启一个新阶段，最后一个阶段才是产出的镜像；用 COPY --from=<阶段名> 只把需要的产物搬过去，编译器、头文件、构建缓存全部留在前面的阶段里被丢弃。官方文档还提示两个容易忽略的细节：给阶段起名（FROM ... AS builder）比用序号稳，后续重排不会打断 COPY --from；以及 BuildKit 只构建目标阶段依赖的阶段，而旧版 builder 会把 --target 之前的所有阶段都跑一遍。

FROM python:3.12 AS builder
WORKDIR /w
COPY requirements.txt .
RUN pip wheel --wheel-dir /wheels -r requirements.txt

FROM python:3.12-slim
RUN useradd -r -u 10001 app
COPY --from=builder /wheels /wheels
RUN pip install --no-index --find-links=/wheels /wheels/*.whl && rm -rf /wheels
USER 10001

3.2 构建上下文与 .dockerignore

构建上下文（build context）是执行构建时被打包发给 builder 的那份目录内容。它有两重成本：一是传输与解压本身耗时，二是上下文里的文件会参与 COPY 的校验和计算，无关文件一变就打穿缓存。AI 项目的上下文格外容易膨胀——本地实验的 checkpoint、向量索引文件、notebook 的 .ipynb_checkpoints、几百 MB 的样例数据。.dockerignore 是唯一的治理手段，官方把"写一份精确的 .dockerignore"直接列在缓存优化建议里。

3.4 非 root 用户不是形式主义

镜像默认以 root 运行，一旦容器内进程被攻破，攻击者手里就是一个 root 身份加上默认能力集。加一个专用 UID 并 USER 切过去成本极低。要注意的是身份切换会连带影响挂载卷的写权限：vLLM 官方文档专门提示，非 root 运行时要把可写路径挂到 /home/vllm 而不是 /root，并保证挂载目录对 group 0 可写，否则容器起不来。

  • 依赖清单单独 COPY，装完依赖再 COPY 源码
  • 写 .dockerignore，至少排除 .git、缓存目录、数据与权重文件
  • 给阶段起名，COPY --from=builder 而不是 --from=0
  • 基础镜像钉 digest，构建可复现
  • 建专用 UID 并 USER 切换，同步检查挂载卷权限
  • 包缓存用 --mount=type=cache，重建也只下增量
  • 不要 COPY . /app 打头，等于放弃依赖层缓存
  • 不要用 latest 基础镜像，上游一推缓存全失效且版本不可考
  • 不要在后续层里删前面层的文件，体积不会降，只多一层
  • 不要把密钥写进 ENV 或构建参数，它会留在镜像历史里
  • 不要在镜像里装 GPU 驱动，驱动由宿主挂入（见第五章）
  • 不要用 --no-cache 掩盖缓存问题，要定位就用 --no-cache-filter 只失效某个阶段

Dockerfile 的工程化本质是在做一件事：把"构建时需要"和"运行时需要"分开。编译器、源码树、包缓存、测试数据都属于前者，运行时一个字节都不该带。想不清楚某个文件属于哪一类，就问一句"线上进程会读它吗"，答案是否就该留在 builder 阶段。

四、模型权重要不要打进镜像

这是 AI 应用容器化里最独特、也最容易做错的一个决策。普通 Web 服务的镜像几百 MB，权重一进来直接变成几十 GB，几乎所有和镜像体积相关的成本项都会跟着变形。这个决策没有普适答案，但有一张可以照着算的账。

把这张表读一遍就能看出结论的形状：前四项一致地反对打进镜像，只有第五项支持它。所以真正的问题不是"该不该外置"，而是外置之后怎么把版本语义补回来。所谓权重外置，是指镜像只装代码与运行时，权重通过挂载卷、共享存储或启动时下载的方式在运行阶段才进入容器。可行的做法是把权重的内容摘要（例如各权重文件的哈希或 HuggingFace 仓库的 commit）写进部署清单，与镜像 tag 一起纳入发布记录，回滚时两者同时回退。这样做的额外好处是"换模型不必重建镜像"——同一份代码镜像可以在不同环境挂不同模型。

4.2 权重外置的四种做法

四种权重交付路径（单机视角，K8s 上的对应做法见 S11 第二章） ① 宿主目录直挂（bind mount） /data/models/Qwen ──► 容器内 /models/Qwen (ro) 最简单；缺点是路径与机器绑死，换机器要先同步文件 ② 命名卷（named volume） volume: models ──► 容器内 /root/.cache/huggingface Ollama 官方就是这个形态：-v ollama:/root/.ollama 首次下载后跨容器复用，重建容器不丢模型 ③ 启动时从对象存储拉取 entrypoint → 拉 S3/OSS/内网仓库 → 落盘 → 起服务 优点是任何节点都能自举；缺点是启动时延与出网带宽 ④ 共享网络存储（NFS / 并行文件系统） 多容器挂同一份权重，只存一份 优点是省空间；缺点是首次加载受网络与元数据操作拖累 常见组合：① 或 ② 做节点本地缓存，③ 做缓存未命中时的兜底

两个官方形态值得直接照抄。vLLM 的容器用法是把 HuggingFace 缓存目录挂进去（-v ~/.cache/huggingface:/root/.cache/huggingface），模型参数既可以是仓库 ID 也可以是容器内的本地路径；Ollama 的官方命令是 -v ollama:/root/.ollama，用命名卷持久化已拉取的模型。本地跑模型的完整实践见 DP06 · Ollama 与本地化部署，引擎怎么选见 DP05 · 大模型推理框架选型。

4.3 容易漏掉的第二份缓存：编译产物

只挂权重还不够。vLLM 官方文档明确指出：挂载 HuggingFace 缓存能让权重跨容器复用，但每个新容器的 VLLM_CACHE_ROOT（默认 ~/.cache/vllm）仍是空的，会重新编译 torch.compile 产物；要复用 inductor、Triton 与 AOT 编译结果，得再挂一个命名卷到那个路径。这条细节解释了一类很常见的困惑——"权重明明挂上了，为什么第一次请求还是慢得离谱"。它同时也是 S11 第三章"就绪不等于可用"的根因之一。

示例场景：某团队把 14B 模型权重打进镜像，镜像 31 GB。开发期只有一台机器，感受不到问题；上量后加了 3 台推理机，每次发版三台机器各拉一次 31 GB，内网 Registry 出网被打满，单节点拉取 11~14 分钟，一次发版接近 40 分钟且期间容量不足。改造为"权重放宿主 SSD + 镜像只装代码"后，镜像降到 620 MB，拉取 20 秒内完成，发版全程 3 分钟。代价是新增了一套权重同步与校验的运维流程，以及在部署清单里记录权重哈希——这就是把版本语义手工补回来的那部分工作量。

判断口诀：镜像里装"会随代码一起改"的东西，卷里放"改得比代码慢很多"的东西。代码天天改、权重几周才换一次，硬绑在一起就意味着每次改代码都要为权重付一遍分发成本。反过来，如果你的模型确实小（几百 MB 以内）且与代码强绑定（比如自训的小分类器），打进镜像换来的版本一致性是划算的。

五、GPU 怎么进容器：nvidia-container-toolkit 的工作原理

"容器里为什么看不到 GPU"是 AI 工程里最高频的环境问题之一，而它的答案完全藏在第一章那句"共享内核"里：GPU 驱动分内核态与用户态两部分，内核态必须装在宿主上，容器里能做的只有拿到用户态库和设备节点。nvidia-container-toolkit 干的就是这件搬运工作。

5.1 三个组件与一条调用链

按 NVIDIA 官方架构文档，工具链由三层组成：nvidia-container-runtime 是一个 OCI 运行时的薄壳，它自 2019 年起不再 fork runC，而是接收 runC spec、往里注入一个 prestart hook，再把改过的 spec 交给宿主原生 runC；nvidia-container-runtime-hook 是那个被 runC 在"容器已创建、尚未启动"时刻调用的钩子，它读取 config.json 里的 GPU 选择与能力声明，转译成 nvidia-container-cli configure 的一串参数（--device、能力标志、--ldconfig、--pid 与 rootfs）；最底层的 libnvidia-container／nvidia-container-cli 才真正动手：查询宿主驱动信息，进入容器的 mount namespace，把驱动库、二进制（如 nvidia-smi）、firmware、IPC socket 与 /dev/nvidia* 设备节点挂进去，最后刷新 ldconfig 让动态链接器找得到这些库。

docker run --gpus all 之后到底发生了什么 docker CLI --gpus all │ （把设备请求写进 OCI spec 的 NVIDIA 环境变量/hook） ▼ containerd / dockerd │ ▼ nvidia-container-runtime ← runC 的薄壳 │ 改写 OCI spec：注入 prestart hook ▼ runC（宿主原生）── create ──► 容器已创建，未启动 │ ▼ nvidia-container-runtime-hook ← prestart 时刻被调用 │ 读 config.json，拼参数 ▼ nvidia-container-cli configure（libnvidia-container） │ ns_enter → 进入容器 mount namespace ├── mount 宿主驱动 .so（libcuda.so、libnvidia-ml.so …） ├── mount 宿主二进制（nvidia-smi …）+ firmware ├── mount /dev/nvidia0…N、/dev/nvidiactl、IPC socket └── 刷新 ldconfig ▼ runC start ──► 容器进程启动，能看到 GPU 与 libcuda 关键结论：镜像里只需要 CUDA 运行时/工具，绝不要装驱动——驱动是挂进来的

5.2 驱动与 CUDA 的兼容边界

镜像里的 CUDA 版本与宿主驱动版本必须落在 NVIDIA 的兼容矩阵内，否则容器起得来但一调 CUDA 就报错。三种兼容关系要分清：驱动比 CUDA 新是向后兼容，天然可用；驱动比 CUDA 旧但同一大版本内是小版本兼容，官方给出的门槛是 CUDA 12.x 需要 Linux 驱动 ≥ 525.60.13、CUDA 13.x 需要 ≥ 580，代价是功能受限（依赖 PTX 即时编译或新驱动 API 的路径会失败）；跨大版本要靠前向兼容包 cuda-compat-<major>-<minor>，且只在 NVIDIA 列出的驱动分支与硬件上支持。

六、用 docker-compose 编排一套单机 LLM 应用

单机跑一套完整的 LLM 应用，需要的最小组合是四个角色：入口网关、推理服务、向量库、可观测。docker-compose 的价值不在"能启动多个容器"，而在于把依赖顺序、健康判定、重启策略、日志与资源限额这些运行时约定写成一份可版本化的文件。

6.1 依赖顺序：depends_on 的默认值不够用

depends_on 的默认条件是 service_started——它只等容器进程起来，不等应用就绪，对数据库和推理服务基本等于没有约束。官方给的正确用法是配 condition: service_healthy，并为被依赖服务写 healthcheck。健康检查有五个字段：test（退出码 0 为健康）、interval、timeout、retries、以及最关键的 start_period——它是首次检查前的宽限期，专门给慢启动服务用。推理服务加载权重动辄数分钟，start_period 给小了，容器会在还在加载时就被判为 unhealthy，依赖它的网关永远起不来。这个"慢加载 vs 健康判定"的矛盾在 K8s 上以更严重的形式重现，见 S11 · K8s 上运行 LLM 推理服务 第三章。

  inference:
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://localhost:8000/health || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 300s   # 权重加载留足时间，否则会被判 unhealthy
    restart: unless-stopped

6.2 四类运行时约定

GPU 这一行是迁移期最隐蔽的坑：命令行上 --gpus=all 是有效请求，但它在 compose 文件里不是合法键，把一条能跑的 docker run 手工翻译成 compose 时很容易丢掉 GPU，而服务照样能起来——只是悄悄退化成 CPU 推理，表现为"没报错但慢了几十倍"。官方 compose GPU 文档强调 capabilities 字段必填，缺了会在部署时直接报错，这反而是好事；真正危险的是整段 deploy 都被忘了。

示例场景：一套单机 compose 栈上线后每晚 2 点前后必然有一波 502。排查发现是可观测容器的日志驱动没配轮转，磁盘写满导致向量库写入失败、健康检查转 unhealthy，而网关的 depends_on 只写了 service_started，重启后不等后端恢复就开始接流量。三处修复：日志加 max-size: 50m 与 max-file: 3 轮转、依赖条件全部改为 service_healthy、为向量库与日志采集也补上内存 limits。之后同类故障归零，且单次故障的影响面从"全栈 502"缩小为"单服务重启期间少量请求排队"。

compose 文件的真正内容不是"启动哪些容器"，而是四条运行时契约：谁等谁（依赖）、怎么算活着（健康）、挂了怎么办（重启）、最多能吃多少（限额）。这四条写清楚了，单机栈就有了"自愈"的雏形；写不清楚，加多少监控都只是更快地发现故障。要不要为此升级到 K8s，判据见 S10 · Docker 还是 K8s：AI 应用部署形态选型 第四章。

Q&A

容器和虚拟机的区别，一句话说不清的话，最本质的差别在哪？

最本质的差别是有没有自己的内核。虚拟机由 hypervisor 虚拟出硬件，客户机跑独立内核，隔离边界在硬件层；容器里的进程就是宿主内核上的普通进程，只是被 namespace 限制了可见范围、被 cgroup 限制了资源额度，文件系统由联合文件系统叠出来。从这一个差别可以推出其余全部差异：容器启动是毫秒级的 fork+exec 而非引导内核；容器里装不了内核模块与 GPU 驱动内核态部分，所以 GPU 必须靠宿主驱动挂载进来；容器的隔离强度弱于虚拟机，Docker 官方安全文档也提示默认能力集与挂载并不构成完整隔离，跑不可信代码要额外加固。反过来，凡是"限制视野和额度"就够用的场景，容器的密度和启停速度都比虚拟机高一个数量级。

为什么调整 Dockerfile 里 COPY 的顺序就能让构建快十倍？

因为层缓存是一条链而不是一张网。builder 逐条比对指令，一旦某条没命中缓存，它之后的所有层全部重建。而 COPY／ADD 的命中判据除了指令字符串，还包括所涉文件的元数据校验和（mtime 单独变化不算），所以 COPY . /app 会让任何一行源码改动都失效这一层。如果依赖安装写在它之后，依赖就被源码的变更频率绑架了，每次提交都要重跑一遍完整的依赖安装，有需要现场编译的包时代价尤其大。正确顺序是先只 COPY 依赖清单、装依赖，最后 COPY 源码，这样源码改动只重建最后一层。配合精确的 .dockerignore（排除 .git、缓存目录、数据文件）还能同时减小构建上下文和避免无关文件打穿校验和。

多阶段构建除了减小体积，还有什么值得用的理由？

有三个常被忽略的收益。一是攻击面收敛：编译器、包管理器、构建脚本、源码树都留在 builder 阶段，最终镜像里没有这些工具，攻破容器后能就地利用的东西显著减少。二是构建可并行：Docker 官方文档提到多阶段可以让互不依赖的阶段并行执行，且 BuildKit 在指定 --target 时只构建目标依赖的阶段（旧版 builder 会把前面所有阶段都跑一遍）。三是一份 Dockerfile 多种产物：同一个文件里可以有 test、builder、runtime 等阶段，CI 里用 --target test 跑测试、用默认目标出生产镜像，避免维护多份几乎一样的 Dockerfile。使用上有一个实践细节：给阶段起名而不是用序号引用，这样后续重排阶段不会打断 COPY --from。

模型权重到底该不该打进镜像？有没有可以照着判的标准？

把五个维度摊开算就清楚了：镜像体积、构建时长、拉取时间、Registry 存储与出网成本这四项一致地反对打进镜像（7B 半精度就要加约 14 GB，70B 约 140 GB，且每个版本都要在 Registry 存一份），只有"版本语义"一项支持它——镜像摘要同时锁定代码和权重，回滚天然一致。所以判据是：权重小于几百 MB 且与代码强绑定（比如自训的小分类器、和业务逻辑同生共死的适配器）时打进镜像划算；只要上到 GB 级，就该外置，并用别的方式把版本语义补回来——把权重的内容摘要写进部署清单，与镜像 tag 一起纳入发布记录，回滚时两者同时回退。外置还有个附带好处：同一份代码镜像可以在不同环境挂不同模型，换模型不必重建镜像。

权重外置有哪几种做法，各自适合什么场景？

四种。宿主目录直挂（bind mount）最简单，适合固定机器的单机部署，缺点是路径与机器绑死、换机器要先同步文件。命名卷适合"首次下载后长期复用"，Ollama 官方就是这个形态（-v ollama:/root/.ollama），重建容器不丢模型。启动时从对象存储拉取的优点是任何节点都能自举、天然适合弹性扩容，代价是启动时延和出网带宽，冷启动会因此变成分钟级。共享网络存储让多容器挂同一份权重、只存一份，省空间，但首次加载受网络吞吐与元数据操作拖累，多副本同时启动时容易互相拖慢。生产上常见的组合是节点本地缓存做主路径、对象存储做缓存未命中时的兜底。另外别忘了第二份缓存：vLLM 官方指出即使挂了 HuggingFace 缓存，每个新容器的 VLLM_CACHE_ROOT 仍是空的、会重新编译 torch.compile 产物，要另挂一个卷才能复用。

容器里看不到 GPU，排查该按什么顺序来？

按"从宿主往容器"的顺序，因为工具链的工作方式就是把宿主的东西挂进容器。第一步确认宿主驱动正常，宿主上 nvidia-smi 能出设备表；这一步不过，改镜像毫无意义。第二步确认 nvidia-container-toolkit 已安装并注册——最常被跳过的是 nvidia-ctk runtime configure --runtime=docker 加重启 daemon，装了包不等于在 /etc/docker/daemon.json 里注册了运行时，症状是报"could not select device driver ... capabilities: [[gpu]]"。第三步用一个官方 CUDA 基础镜像跑 nvidia-smi 验证透传本身是否通，通了说明问题在应用侧配置。第四步才怀疑版本：容器内 nvidia-smi 正常但 CUDA 调用失败，通常是宿主驱动低于镜像 CUDA 的下限，CUDA 12.x 要求 Linux 驱动 ≥ 525.60.13、13.x 要求 ≥ 580，处置是升驱动、换低版本镜像或装前向兼容包。

镜像里要不要装 GPU 驱动？CUDA 版本又该怎么选？

绝对不要装驱动。驱动分内核态与用户态两部分，内核态只能在宿主，而用户态库由 nvidia-container-toolkit 在容器启动前挂进来——按 NVIDIA 架构文档，libnvidia-container 会进入容器的 mount namespace，挂载宿主的驱动库、nvidia-smi 等二进制、firmware、IPC socket 和 /dev/nvidia* 设备节点，再刷新 ldconfig。镜像里自带驱动只会和挂进来的版本冲突。镜像里该装的是 CUDA 运行时与工具链，选版本时按兼容矩阵倒推：驱动比 CUDA 新永远安全（向后兼容）；驱动比 CUDA 旧但同大版本内可用小版本兼容，门槛是 CUDA 12.x 需驱动 ≥ 525.60.13、13.x 需 ≥ 580，但功能受限，依赖 PTX 即时编译的路径会失败；跨大版本要装 cuda-compat 前向兼容包，且只在 NVIDIA 列出的驱动分支上支持。集群规模化时把驱动版本作为节点池属性统一治理最省事。

compose 里 depends_on 和 healthcheck 该怎么配才对 LLM 服务有用？

关键是两点：条件必须显式写成 service_healthy，以及 start_period 必须按权重加载的真实耗时来设。depends_on 的默认条件是 service_started，只等容器进程起来、不等应用就绪，对推理服务和数据库基本等于没有约束——网关会在后端还没加载完权重时就开始接流量，表现为发布后一段时间大量 5xx。改成 condition: service_healthy 后，compose 会等被依赖服务的 healthcheck 通过才创建依赖方。而 healthcheck 的五个字段里，start_period 是首次检查前的宽限期，专为慢启动服务设计；按 Web 服务习惯设几十秒，推理服务会在还在加载权重时就被判 unhealthy，依赖它的服务永远起不来。另外 service_completed_successfully 适合一次性的初始化任务（比如启动前拉权重、跑迁移），可以当作单机版的 initContainer 用。

把 docker run 命令翻译成 compose 文件，最容易丢的是什么？

最容易丢也最难发现的是 GPU。命令行上 --gpus=all 是有效的设备请求，但它在 compose 文件里不是合法键，必须改写成 deploy.resources.reservations.devices 并显式声明 driver: nvidia、count（或 device_ids）与 capabilities: [gpu]。危险在于失败是静默的：整段 deploy 忘了写，服务照样能起来，只是退化成 CPU 推理，表现为"没报错但慢了几十倍"，很容易被误判成模型或参数问题。官方文档特别强调 capabilities 必填、缺失会直接报错，这反而是有保护作用的。其次容易丢的是 --ipc=host 或 --shm-size——vLLM 的张量并行依赖共享内存，容器默认的 /dev/shm 太小会导致启动即崩。还有日志轮转配置：docker run 时常靠守护进程的全局默认，翻译成 compose 后如果没显式声明，推理服务的日志量足以在几周内写满磁盘。

overlay2 的写时复制对 AI 应用有什么具体影响？

有两个具体后果。第一个是大文件的首次写代价：overlay2 在容器首次修改来自镜像层的文件时要执行 copy_up，把整个文件从只读层复制到可写层。普通配置文件无感，但如果权重躺在镜像层里而框架启动时要就地改写它（例如把权重转成自己的缓存格式写回原目录），一次 copy_up 就能在磁盘上再复制出几十 GB，表现为"启动时磁盘暴涨、IO 打满"。第二个是可写层不适合承载持续写入：官方文档指出 overlay2 工作在文件级而非块级，写密集负载下容器可写层会膨胀得很快，且写性能低于原生文件系统，建议改用 volume。对 AI 服务来说，需要落盘的东西——权重、编译缓存、向量索引、日志——都应该挂 volume 而不是写进容器层。附带的好处是容器删除重建时这些数据不丢，冷启动因此从"重新下载与重新编译"降级为"直接加载"。
