S07 · AI 应用四层监控体系

流量门禁 / 行为围栏 / 状态雷达 / 价值天平 —— 每层拦什么、采什么指标、阈值怎么定

框架自带的监控是烟雾报警器：它只会喊"着火了"，不告诉你是油温太高还是锅里溅了水，更不会告诉你该盖锅盖还是拿灭火器。

一、原生监控的短板：只报"着火了"

把一个 LLM 应用推上线，多数团队的监控起点是框架自带的那套：请求成功率、平均延迟、错误日志、token 用量曲线。这套东西不是没用，但它有一个结构性的缺陷——它监控的是"接口"，而 AI 应用出问题的地方几乎都不在接口上。

接口层面看，一次胡编乱造的回答和一次完全正确的回答没有任何区别：都是 HTTP 200、都在两秒内返回、都消耗了差不多的 token。原生监控在这里是全盲的。

这张表里，只有第一行是原生监控真正擅长的。下面四行的共同点是：故障信号滞后于故障本身——等到指标动了，损失已经发生了；而且指标只指向"哪里疼"，不指向"为什么疼、该怎么办"。

传统监控问的是"服务还活着吗"，AI 应用要问的是"它还清醒吗、还有用吗"。后两个问题在接口指标里没有答案。

四层体系的划分逻辑

把 AI 应用可能出的事按来源排一遍，会自然分成四类：来自外部的、来自模型输出的、来自模型自身状态的、来自业务价值判断的。四层监控就是对着这四类来源各设一道防线，从外往内层层递进。

顺序不是随意的。越靠外的层，问题越显性、拦截成本越低、见效越快；越靠内的层，问题越隐蔽、越需要业务语境、建设周期越长。这个梯度决定了落地顺序，第六节会展开。

与可观测性工具栈的边界

这里要先把一件事讲清楚，避免和 《S03 · LLM 可观测性》 混淆。S03 讲的是"用什么看"：Tracing 怎么埋、span 怎么串、LangSmith / Langfuse / Phoenix 这类平台怎么选、token 与延迟数据怎么采集和分析，是工具栈与实现层面的事。本文讲的是"该看什么、分几道防线看"：监控应该切成哪几层、每层拦哪一类问题、指标和阈值怎么定。一张偏工具，一张偏分层策略。

两者是配套关系而非替代关系：本文划出的四层里，每一层的指标最终都要落到 S03 描述的那套 trace 与指标基础设施上去采集和展示。没有 S03 的管道，四层就是四句口号；没有本文的分层，S03 采回来的数据就是一堆没有防线归属的散点。

二、第一层 流量门禁：拦住外部的明枪

最外面这一层管的是"谁在敲门、敲得有多急"。它防的是三类东西：恶意请求、爬虫抓取、上游流量突增。这三类的共同点是来源在系统之外，特征在请求层面就能识别，所以拦截成本最低。

案例：某项目上线第一天就被爬虫刷了几十万次请求，直接把 API 额度打爆，整个服务几乎瘫痪。事后复盘，原因不是防御被绕过，而是压根没做请求过滤和限流——所有请求一视同仁地转发给了模型。这类事故的特点是：技术上毫无难度，但代价立刻见血，因为 LLM 的每次调用都是真金白银。

LLM 应用在这一层的风险敞口比传统 Web 服务大得多，原因有三个：单次请求的成本高出两三个数量级；请求是长耗时的，连接占用久，打满并发比打满带宽容易；而且很多 AI 应用为了体验会做无登录试用，等于把付费接口开放给了全网。

阈值怎么定？这一层最实用的方法是基线偏离法——不去拍一个绝对值，而是用过去七天同一时段的分位数（比如 P95）作为基线，超出基线的固定倍数就告警。绝对阈值在业务量变化时会不断失效，基线阈值会自己跟着业务走。

告警条件 = 当前值 > max(基线_P95 × 倍率, 绝对下限)

加一个绝对下限是为了避免凌晨低谷期基线太小、几个正常请求就触发误报。倍率的起手值可以取 3，跑一周看误报率再调。

额度类指标要单独说一句：它必须配硬熔断而不只是告警。告警是给人看的，人可能在睡觉；额度烧穿是不可逆的，所以要有一条"当日费用超过 X 就自动停服"的死线。宁可服务中断一小时，也不要第二天面对一张超出预算十倍的账单。

这一层的性价比高得离谱：它的实现难度最低，但拦掉的是最容易在一夜之间烧穿预算的那类问题。

三、第二层 行为围栏：管住模型的嘴

流量门禁挡住了外面的明枪，但暗箭是从里面射出来的。第二层管的是模型自己说了什么——幻觉（模型生成了看似合理但与事实不符的内容）以及各类异常输出的检测与隔离。

案例：一个金融问答项目，模型在某一天开始推荐根本不存在的理财产品——产品名、收益率、期限说得有鼻子有眼。由于当时已经有一层输出校验能及时发现并隔离这类异常，才没有真正流到用户面前。这个案例的可怕之处在于：从接口指标看，那些回答的延迟、token 数、成功率全部正常，原生监控一个字都不会报。

金融、医疗、法律这类领域尤其危险，因为幻觉内容的"可信度"很高——模型编造的产品名字和真实产品在措辞上难以区分，用户没有能力自己识别。

实现上有一个要点：校验必须放在返回给用户之前，而不是事后统计。事后统计是分析工具，不是围栏。围栏意味着不合格的输出根本走不出去，被替换成兜底话术或转人工。

行为围栏在请求链路中的位置： 用户请求 │ ▼ [模型生成] ──→ 原始输出（尚未返回用户） │ ▼ ┌───────────────────────┐ │ 围栏检查（并行执行） │ │ ├ 结构校验 │ │ ├ 敏感/合规检查 │ │ ├ 关键实体回查 │ │ └ 相关性打分 │ └──────────┬────────────┘ │ ┌────────────┴────────────┐ ▼ ▼ 全部通过 任一不通过 │ │ ▼ ▼ 返回用户 ┌──────────────────┐ │ 隔离原始输出并留痕 │ │ 返回兜底话术 │ │ 触发告警 + 样本入库 │ └──────────────────┘ 关键：不通过的输出要"留下来"，它是下一轮优化最值钱的素材。

被拦下的样本不要直接丢弃。它们是最真实的坏例样本库——用来回归测试、调 prompt、做微调数据，价值远高于任何构造的测试集。很多团队围栏建起来了却没建样本库，等于把最贵的数据当垃圾处理了。

成本上要有心理准备：如果用另一个模型做输出校验，这一层会让单次请求的成本明显上升。常见的折中是分级校验——低风险场景只跑规则和结构校验，高风险场景（金融、医疗、对外承诺）才上模型级校验。风险等级由业务侧定义，不由技术侧拍脑袋。

这层管得住模型的嘴，管不住模型的脑子。它拦的是"说错了"，拦不住"越跑越糊涂"——那是下一层的事。

四、第三层 状态雷达：看模型自己的身体

前两层看的都是"输入"和"输出"，第三层第一次把目光转向系统内部：模型自己现在是什么状态。核心指标只有三组——上下文长度、token 消耗、响应时间趋势。

案例：一个逻辑复杂的 Agent，上线后越跑越慢，排查了很久才定位到根因：上下文一直没有清理，历史越积越大，每一轮都要把之前所有的工具调用结果重新送进模型，最后把自己撑死了。这类问题在原生监控里只表现为"延迟缓慢上升"，看不出成因，而且因为是渐进的，很容易被当成正常波动忽略过去。

这一层的独特之处在于：它监控的不是瞬时值，而是趋势。上下文长到 3 万 token 本身不是问题，"每小时增长 5 千且不回落"才是问题。所以状态雷达的告警规则和前两层不一样，它盯的是斜率和单调性。

最后一行值得单独强调：循环检测指的是识别 Agent 陷入"调用—失败—重试—再失败"的自我循环。它的特征很好认——连续多轮调用同一个工具、参数几乎不变、返回结果也几乎不变。这种模式一旦出现，必须有硬性的轮次上限来强制中断，否则一个死循环的 Agent 能在几分钟内烧掉平时一天的额度。

前两层看瞬时值，这一层看曲线形状。一条永不下降的曲线，就算此刻的绝对值还在安全区，也已经是故障了。

这一层的数据来源几乎完全依赖 trace：要知道单个任务消耗了多少 token、经历了多少轮工具调用、每一轮各花了多久，必须有完整的调用链埋点。这正是与 《S03 · LLM 可观测性》 咬合最紧的地方——S03 讲这些 span 怎么埋、怎么串、用哪个平台看，本文讲埋好之后该盯哪几条曲线、什么形状算异常。

五、第四层 价值天平：技术全绿也可能是失败

前三层都在问"系统有没有出错"。第四层问一个完全不同的问题：它到底有没有用。

案例：某项目的技术指标全线飘绿——响应快、成功率高、无异常输出，但用户投诉率始终居高不下。深挖之后发现，模型回答的都是"正确的废话"：内容没有事实错误、语气礼貌、结构完整，但完全没有解决用户的实际问题。前三层监控对这种情况一个告警都不会发，因为从系统视角看，一切正常。

"正确的废话"是 LLM 应用最典型的失败模式，也是最难量化的。它不违反任何技术约束，只违反一件事：用户的实际诉求。所以这一层的指标必须来自业务侧和用户侧，不可能从系统内部推导出来。

四类价值指标

指标类型具体形式采集方式灵敏度局限
直接反馈点赞/点踩、五星评分界面上的反馈按钮低（参与率通常很低）只有极满意和极不满的人会点，样本有偏
行为信号采纳率、复制率、追问率、重问率前端埋点高（无需用户主动配合）需要能明确定义"采纳"这个动作
任务完成会话是否达成业务目标（下单、工单关闭）业务系统回流最高归因困难，可能有多因素
抽样评测定期抽样人工或模型打分离线评测流水线中有成本、有延迟，只能定期跑

其中最值得投入的是行为信号，因为它不需要用户额外做任何事。几个特别好用的代理指标：

  • 重问率：用户在收到回答后，用不同措辞重新问了同一件事的比例。这是"正确的废话"最灵敏的探针——回答没有事实错误，但用户不满意，只好换个说法再问一遍。
  • 追问轮次分布：健康的对话应该是问题被逐步收敛；如果追问轮次的长尾变厚，说明系统在兜圈子。
  • 采纳率：给出的方案、代码、结论被用户真正采用的比例。在编码类场景可以直接观测代码是否被保留。
  • 提前退出率：用户在回答生成到一半时就关闭会话的比例，说明前几句话就让人失望了。
有效交互率 = 1 − (重问率 + 提前退出率 + 转人工率)

这个组合指标的好处是可以做成单一看板数字，方便向业务方汇报，也方便设趋势告警。它下降的时候未必知道原因，但一定说明有事发生了——然后回到前三层去找线索。

前三层的告警说"系统坏了"，第四层的告警说"系统没坏，但它在浪费所有人的时间"。后者的损失往往更大，因为没人会为它拉紧急群。

六、四层的落地顺序与成本

四层不该同时开工。它们的建设成本、见效速度、维护负担差异巨大，硬要一起上，结果通常是四层都做了半截。

① 流量门禁低（网关层配置为主）极低立即低第一优先，先上
③ 状态雷达中（依赖 trace 埋点）低数天到数周中（阈值需持续校准）第二优先
② 行为围栏中高（需要规则 + 校验模型）高（每次请求都要跑）立即高（规则会持续膨胀）按风险等级选择性上
④ 价值天平高（需业务配合定义与埋点）中数周到数月中最后建，但要最早开始想

注意顺序不是 ①②③④，而是 ① → ③ → ② → ④。原因是第一层几乎零成本却挡住了最烧钱的问题；第三层依托 trace 基础设施，一次埋点长期受益；第二层运行成本高、规则会不断膨胀，应该按业务风险等级挑重点场景上，而不是全量铺开；第四层依赖业务方一起定义"什么算有价值"，这件事的沟通周期比技术实现长得多，所以要早启动、晚交付。

  • 第一周就把限流、配额和费用硬熔断加上，这是投入产出比最高的一步
  • 阈值用七日基线的分位数动态计算，并配一个绝对下限防低谷误报
  • 状态雷达盯曲线形状（有没有下降段、斜率是否为正），不要只盯瞬时值
  • 被围栏拦下的输出全部留痕入库，当作回归测试集和优化素材
  • 行为围栏按业务风险分级：高危场景上模型校验，普通场景只跑规则
  • 第四层的指标定义拉业务方一起做，从第一天就开始谈
  • 每条告警都绑定一个明确的处置动作和责任人
  • 只做"告警"不做"熔断"——额度烧穿是不可逆的，人可能在睡觉
  • 四层同时开工，结果每层都做了一半
  • 把事后统计当成围栏：统计发现不了的问题已经流到用户面前了
  • 用固定绝对阈值，业务量一变就要么全是误报要么全是漏报
  • 把拦下来的坏样本直接丢弃，浪费最真实的优化数据
  • 指标看板铺了几十个图，但没有一条对应明确的处置动作
  • 拿技术指标全绿当作项目成功的证据

告警必须可处置

最后一条原则，也是最容易被忽略的：每一条告警都要能回答"现在该做什么"。原生监控最大的问题不是采得少，而是它给的信号无法转化为动作——"错误率上升了"没法处置，"某个 IP 段在两分钟内消耗了当日额度的三成，已自动限流，请确认是否白名单"才能处置。

把一条告警变成可处置的四要素： ┌──────────┬──────────────────────────────────────────┐ │ 是什么 │ 具体指标 + 当前值 + 基线值 │ │ 在哪里 │ 哪个租户/接口/会话，能一键跳到对应 trace │ │ 已经做了 │ 系统的自动动作（已限流 / 已隔离 / 已降级） │ │ 需要人做 │ 明确的下一步 + 责任人 + 升级路径 │ └──────────┴──────────────────────────────────────────┘ 缺"已经做了"这一行，告警就变成了纯粹的焦虑源； 缺"需要人做"这一行，告警就没有闭环，最终会被静音。

监控体系的成熟度不看采了多少指标，看有多少条告警能在收到的三十秒内变成一个确定的动作。

Q&A

框架自带的监控到底缺什么？把日志打全是不是就够了？
不够，因为缺的不是数据量而是监控对象。框架原生监控盯的是接口状态：成功率、延迟、错误码、token 用量。但 AI 应用的典型故障不体现在接口上——一次胡编乱造的回答和一次完全正确的回答，HTTP 状态码、耗时、token 数几乎一模一样。日志打得再全，只要采的还是这几类字段，幻觉、上下文膨胀、"正确的废话"这三类问题依然全部漏检。要补的是监控对象本身：从"接口活着吗"扩展到"流量正常吗、输出可信吗、状态健康吗、价值成立吗"。
为什么落地顺序是 ① → ③ → ② → ④，而不是按编号来？
因为四层的成本收益曲线差别很大。第一层流量门禁基本是网关层配置，成本极低但拦住的是最容易一夜之间烧穿预算的问题，必须最先上。第三层状态雷达依托 trace 埋点，一次投入长期受益，且能解释大量"莫名其妙变慢"的现象。第二层行为围栏虽然重要，但每次请求都要跑校验，运行成本高，规则集还会持续膨胀，所以应该按业务风险等级挑重点场景上而不是全量铺开。第四层价值天平的瓶颈不在技术而在于和业务方一起定义"什么算有价值"，沟通周期最长，所以要最早开始谈、最晚交付。
告警阈值到底怎么定？定高了漏报，定低了天天误报。
绝对阈值在业务量变化时必然失效，推荐用基线偏离法：取过去七天同一时段的分位数（比如 P95）作为动态基线，超出基线的固定倍数才告警，倍率从 3 起步跑一周再调。同时要配一个绝对下限，否则凌晨低谷期基线很小，几个正常请求就会触发误报。另外不同层的告警口径本来就不该一样：前两层盯瞬时值合适，第三层状态雷达必须盯趋势——上下文长到 3 万 token 本身不是问题，"连续多个采样点只涨不落"才是问题，所以它的规则是关于斜率和单调性的，不是关于绝对值的。
行为围栏的成本很高，是不是所有请求都要跑一遍校验？
不需要，正确做法是分级校验。如果每次输出都用另一个模型做事实核查，单次请求成本会明显上升，很多场景撑不住。实践中把场景按业务风险分级：低风险场景只跑结构校验和敏感词这类零成本的规则；高风险场景——金融、医疗、法律，以及任何会对外做出承诺或报价的输出——才上模型级校验和关键实体回查。风险等级必须由业务侧定义，因为只有他们知道哪一类错误的代价是不可承受的。另外要注意围栏必须放在返回用户之前，事后统计只是分析工具，不构成防线。
"正确的废话"这类业务价值指标怎么量化？
这类问题的特点是不违反任何技术约束，所以只能从用户行为里找信号。最灵敏的代理指标是重问率——用户收到回答后换个措辞重新问同一件事的比例，这几乎是"答了等于没答"的直接证据。配套的还有采纳率（给出的方案、代码、结论是否被真正采用）、追问轮次分布（长尾变厚说明在兜圈子）、提前退出率（回答生成到一半就关闭会话）。这些都是前端埋点就能拿到的行为信号，不需要用户额外配合，比点赞点踩这类主动反馈的覆盖率高得多。可以把它们合成一个"有效交互率"做趋势告警，指标下降时未必知道原因，但足以说明有事发生，再回到前三层找线索。
这四层和 trace、span 那套可观测性工具是什么关系？
是"看什么"和"怎么看"的关系，两者配套而非替代。《S03 · LLM 可观测性》讲的是工具栈与实现：调用链怎么埋点、span 怎么组织、LangSmith / Langfuse / Phoenix 这类平台怎么选、token 与延迟数据怎么采集分析。本文讲的是监控该切成哪几道防线、每层拦哪一类问题、指标和阈值怎么定。四层里每一层的指标最终都要落到 S03 那套基础设施上采集和展示，尤其是第三层状态雷达，几乎完全依赖完整的调用链数据。没有 S03 的管道，四层就是四句口号；没有本文的分层，采回来的数据就是一堆没有防线归属的散点。
状态雷达为什么强调看趋势而不是看瞬时值？
因为这一层要抓的问题基本都是渐进式的。上下文没有回收机制的 Agent，前一百轮可能一切正常，指标全在安全区内，直到某一天撞上窗口上限或者延迟慢到用户投诉。如果只设一个绝对阈值，告警发出来的时候已经很晚了，而且中间那段缓慢恶化会被当成正常波动忽略。正确的做法是盯曲线形状：健康的上下文曲线应该是锯齿状的，涨到阈值就回收；病态的曲线是单调递增、没有任何下降段。同理，端到端时延要看七日趋势的斜率是不是持续为正，token 消耗要看 P99 和中位数的比值有没有突增。
Agent 疯狂调用 API 把额度打光，属于哪一层的职责？
主要是第三层状态雷达，第一层做兜底。这类问题的成因通常是 Agent 陷入了"调用—失败—重试—再失败"的自我循环，特征很好识别：连续多轮调用同一个工具、参数几乎不变、返回结果也几乎不变。状态雷达要做的是循环检测和单任务工具调用轮次上限，一旦超过就强制中断，这是最精准的拦法。同时第一层的额度消耗速率监控要配硬熔断作为最后一道保险——注意是熔断不是告警，因为额度烧穿不可逆，而告警只是给人看的，人可能在睡觉。一条"当日费用超过某个数就自动停服"的死线，比任何告警都可靠。
