06 · Token 机制

Token Mechanism — 为什么 "Hello World" 是 2 个 Token 而 "你好世界" 是 4 个？

核心认知：Token 是大模型处理文本的最小单位，不等于字、不等于词。理解 Token 机制是理解大模型成本、上下文窗口、延迟等一切的基础。

一、什么是 Token？

Token 是模型 tokenizer 将文本切分后的最小处理单元。不同模型的 tokenizer 不同，切分结果也不同。

文本Token 数说明
"Hello World"2英文常见词 = 1 Token
"你好世界"4中文每个字 ≈ 1 Token
"unbelievable"3"un" + "believ" + "able"
"GPT-4"3"G" + "PT" + "-4"

生产案例：中英混合场景的 Token 成本

背景：某企业客服系统需要同时处理中英文对话，日均 10 万次 API 调用。

问题：同样语义的中文文档（500 字）比英文文档（300 词）多消耗 2.5 倍 Token，月度 API 成本差异达 $3,200。

根因：GPT-4 的 tokenizer 训练数据以英文为主，中文每个字独立编码。500 字中文 ≈ 500 Token，300 词英文 ≈ 200 Token。

修复：引入文档摘要压缩（中文文档先摘要再注入），Token 消耗降低 40%，月度成本节省 $1,280。

Subword 切分

现代 tokenizer 使用 Subword（子词）切分——把词拆成更小的有意义的片段，平衡词汇表大小和表达力：

  • BPE（Byte Pair Encoding，字节对编码）：从字符级开始，反复合并最高频的相邻字节对，直到达到目标词汇表大小。GPT 系列使用
  • WordPiece：类似 BPE 但用似然度而非频率来决定合并。BERT 系列使用
  • SentencePiece：直接在原始字节流上训练，不依赖空格分词，特别适合中日韩等无空格语言

生产案例：Prompt Cache 的成本优化

背景：某在线教育平台的 AI 助教系统，System Prompt 长达 2,000 Token（含教学指南、角色设定、输出格式要求），日均 50 万次请求。

问题：每次请求重复发送相同的 System Prompt，月度仅 System Prompt 部分就消耗 1,000 亿输入 Token。

优化：启用 Prompt Cache（Anthropic / OpenAI 均支持），首次缓存 System Prompt 后，后续请求直接复用缓存 Token，缓存命中率达 99.2%，月度节省约 $15,000。

上下文窗口溢出的生产问题

当输入 Token + 预估输出 Token 超出上下文窗口时，API 会返回错误或被截断。生产系统中需要实现 Token Budget Manager（Token 预算管理器）：

分配区域预算策略溢出处理
System Prompt固定预算（不可压缩）启动时校验，超限报警
对话历史弹性预算，优先保留近期滑动窗口 / 摘要压缩
RAG 上下文弹性预算，按相关性排序截断低分文档
预留输出固定预留（如 1024 Token）动态调整 max_tokens
长上下文不等于好效果：即使模型支持 128K 甚至 2M 的上下文窗口，也存在 Lost in the Middle 问题——模型对中间位置的信息关注度显著低于首尾。因此，将关键信息放在 Prompt 的开头和结尾是更有效的策略。

四、Token 优化策略

示例场景：把提示重排一遍，输入 token 少付了七成。背景——某问答服务每轮请求都要拼三段内容：一段较长的固定系统提示（角色设定、输出格式、若干示例）、几段检索回来的文档、以及用户的当轮问题。最初的拼接顺序是"检索文档 ＋ 系统提示 ＋ 问题"，因为写代码时觉得"先给材料更自然"。问题——账单里输入 token 的占比高得反常，而且前缀缓存的命中率长期接近于零。原因就在顺序上：检索文档每次都不同，它被放在最前面，等于把后面那段完全固定的系统提示也一起"污染"了——前缀缓存要求从第一个 token 起逐字相同，第一段一变，整条前缀全部失效，每轮都要为同一份系统提示重新付一遍 Prefill。方案——两步。第一步把顺序改成"系统提示 ＋ 检索文档 ＋ 问题"，让最长且完全不变的那一段占住前缀位置；第二步把系统提示里原本随请求变化的时间戳和会话标识挪到提示末尾，避免它们再次打断前缀。效果——前缀缓存命中率从接近 0 升到八成以上，输入 token 的计费量下降约七成，首字延迟同步明显改善。一般化的规则：按"越稳定的内容越靠前"来组织提示——固定指令、示例，然后才是检索结果和用户输入。这条改动不需要动模型，也不需要压缩任何内容，纯粹是排列顺序的收益。
  • 精简 System Prompt
  • 对话历史定期压缩
  • RAG 检索结果去重摘要
  • 控制输出长度
  • 利用 Prompt Cache
  • 选择合适的模型（性价比）
  • System Prompt 塞入大量冗余信息
  • 不压缩对话历史
  • RAG 注入整篇文档
  • 不限制输出长度
  • 忽视 Token 成本监控
  • 所有场景都用最贵的模型

五、为什么中英文 Token 差异大？

语言Tokenizer 训练数据效果
英文英文数据占多数常见词 = 1 Token，切分效率高
中文中文数据占少数每个字 ≈ 1 Token，切分粒度细
日韩日韩数据更少Token 效率更低
根本原因：Tokenizer 的训练数据分布不均。英文数据占大多数，所以常见英文词被编码为 1 个 Token；中文数据较少，所以每个汉字通常是独立 Token。这导致同样语义的中文文本比英文多消耗 2-3 倍 Token。

生产案例

生产验证：中英混合场景的 Token 成本差异显著。同一段"请帮我分析这段 Python 代码的性能瓶颈"：英文仅 12 tokens，中文需要 28 tokens（每个汉字约 1.5-2 tokens），成本差异 2.3 倍。BPE vs WordPiece vs SentencePiece 对比：GPT-4 使用 cl100k_base（BPE 变体），vocab size 100,256，英文平均 1 token/4 字符；中文平均 1 token/1.5 字符。某 RAG 系统因 Token 预算限制（max 4096），中文文档召回量仅为英文的 43%。解决方案：采用 chunk overlap + 中文专用 Tokenizer（如 ChatGLM 的 tokenizer），中文 Token 效率提升 35%。

Token 是 LLM 的"信息货币"—— 理解 Token 机制是做好 Prompt 工程、成本控制和 RAG 系统优化的基础。中英 Token 效率差异 2-3 倍是多语言场景必须纳入架构设计的核心约束。

高频问答

Token 和字/词有什么区别？

Token 不等于字也不等于词，是 tokenizer 切分后的最小处理单元。英文常见词（如 "Hello"）= 1 Token，但长词会被拆成子词（"unbelievable" = "un"+"believ"+"able" = 3 Token）。中文每个汉字通常 ≈ 1 Token。Token 的数量取决于模型的 tokenizer，不同模型切分结果不同。

为什么中文比英文消耗更多 Token？

因为 tokenizer 的训练数据以英文为主。英文常见词被编码为 1 个 Token（如 "the" "hello"），切分效率高。中文数据在训练集中占比小，所以每个汉字通常是独立 Token，同样语义的中文文本比英文多消耗 2-3 倍 Token。这意味着中文场景的 API 调用成本更高。

如何优化 Token 成本？

六个策略：① 精简 System Prompt（去掉冗余描述），② 对话历史压缩（定期摘要替代完整历史），③ RAG 结果去重摘要（注入摘要而非全文），④ 控制输出长度（设置 max_tokens），⑤ Prompt Cache（复用前缀），⑥ 选择合适模型（简单任务用便宜模型）。

Subword 切分解决了什么问题？

Subword 切分解决了两个核心问题：① OOV（未登录词）：将词拆为子词单元，即使遇到未见过的词也能表示。② 词表大小：不需要为每个词分配独立 ID，子词组合即可表示所有词。BPE、WordPiece、SentencePiece 是三种主流的 Subword 算法。

BPE 和 WordPiece 有什么区别？

BPE（Byte Pair Encoding）和 WordPiece 都是 Subword 算法，核心区别在于合并策略：① BPE：基于频率，反复合并出现频率最高的相邻字节对。GPT 系列使用。② WordPiece：基于似然度，选择合并后语言模型似然度提升最大的字节对。BERT 系列使用。实际效果差异不大，但 WordPiece 对低频词的处理更优。

什么是 Token Budget Manager？为什么生产系统需要它？

Token Budget Manager（Token 预算管理器）是生产级 LLM 系统中负责分配和监控 Token 使用量的组件。它将上下文窗口划分为多个预算区域：System Prompt（固定预算）、对话历史（弹性预算）、RAG 上下文（弹性预算）和预留输出（固定预算）。当总 Token 接近上限时，自动触发压缩策略（如历史摘要、文档截断）。没有它，系统容易出现上下文溢出错误、成本失控、以及关键信息被截断等问题。

为什么输出 Token 比输入 Token 贵？

输出 Token 更贵的根本原因在于计算模式不同。输入阶段（Prefill）可以并行处理所有输入 Token，GPU 利用率高。而输出阶段（Decode）是自回归的——每生成一个 Token 都需要等前一个 Token 完成，导致 GPU 的 batch 并行能力受限，内存带宽成为瓶颈。此外，输出阶段还涉及 KV Cache 的持续增长，显存压力随生成序列长度线性增加。因此，输出单价通常是输入的 2-4 倍。

Prompt Cache 是如何工作的？适用什么场景？

Prompt Cache 允许 API 服务端缓存请求中的前缀 Token（通常是 System Prompt），后续相同前缀的请求直接复用缓存的中间计算结果（主要是 KV Cache）。适用场景：① System Prompt 固定且较长（如 >1000 Token）；② 请求频率高（如日均万次以上）；③ 多个用户共享相同系统指令。不适用场景：① Prompt 频繁变更；② 请求量极低（缓存未命中率高）。注意缓存通常有 TTL（存活时间），长时间无请求后缓存会失效。

什么是 Lost in the Middle 问题？如何缓解？

Lost in the Middle 是指大模型对上下文中间位置的信息关注度明显低于开头和结尾的现象。实验表明，当关键信息被放置在 128K 上下文的中间区域时，模型提取准确率可从 95%+ 降至 50% 以下。缓解策略：① 位置策略：将关键指令和数据放在 Prompt 的首尾；② 重复强调：在开头和结尾重复关键指令；③ 结构化标记：使用 XML 标签或 Markdown 标题突出关键段落；④ 分段注入：对长文档按重要性分层，优先注入首尾。
