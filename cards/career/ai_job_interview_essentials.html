H10 · AI 岗位核心能力图谱

六大评估维度 / 技术栈全景 / Agent 与 GraphRAG 前沿 / 业务理解与沟通

AI 岗位筛选的从来不是"你知道多少个技术名词"，而是"你能不能把一句模糊的业务诉求，变成一个稳定运行、算得过账的产品"。本文的六大能力维度、技术清单与准备方法，全部围绕这一件事展开。

一、六大核心能力维度

当前 AI 岗位市场需求旺盛且薪资优厚，但求职者普遍面临"高投递量、低通过率"的困境。核心矛盾在于：多数候选人仅掌握技术概念（如 Agent（智能体，能自主规划任务、调用工具并循环执行直至达成目标的 LLM 系统）、RAG（检索增强生成，先从外部知识库检索相关内容、再让模型基于检索结果作答的架构）），却缺乏将技术转化为业务解决方案的能力。企业真正评估的，是六项相互支撑的能力。

行业数据快照（2026）：BOSS 直聘披露 AI 相关岗位月均新发职位数同比增长约 74.1%；澎湃美数课工作室对腾讯、字节跳动等 5 家互联网公司的 10221 条招聘信息分析发现，47% 的岗位有 AI 相关要求，其中腾讯 AI 渗透率 56%，字节跳动设计岗的 AI 渗透率高达 63%，甚至超过研发岗。岗位在变多的同时门槛在变高——"纯调 API"的经验已经过剩，具备全链路落地能力的候选人依然稀缺。
能力维度企业实际考察什么典型评估方式成熟信号
技术基础深度学习与 LLM 原理是否扎实，能否解释模型行为原理追问、系统设计中的模型选型能讲清 Transformer、上下文窗口、幻觉成因
工程化能力能否把 Demo 变成扛得住线上的系统部署/性能/稳定性追问、实操测试有监控、灰度、回滚、成本数据
业务理解能否识别真需求、算清 ROI项目深挖："为什么做这个？值多少？"开口先讲业务指标，再讲技术方案
问题解决面对陌生故障的定位与拆解能力开放式场景题、踩坑复盘追问现象→假设→验证→修复→防再犯成闭环
学习能力能否跟上以月为单位迭代的技术栈新技术观点、转域经历有可验证的快速上手证据（代码/文章）
沟通协作能否向非技术方讲清方案与风险价值观轮、跨团队项目追问能把技术语言翻译成业务语言

不同公司的考察权重并不相同

同一个"AI 工程师"头衔，在不同类型的公司里考察侧重差异很大。大厂平台团队把系统设计当作最重要的淘汰轮（在 Meta 它约占招聘信号的 30%，在 OpenAI、Anthropic 是淘汰率最高的一轮）；成长期 AI 公司更看端到端交付能力；前沿实验室则普遍采用五段式流程：初筛 → 实操编码 → AI 系统设计 → 模型观点轮 → 使命价值观轮，其中编码轮越来越务实——不再是纯刷题，而是解析真实数据、构建小型服务，甚至要求候选人现场驱动一个编码智能体，考察的是你审查和纠正它产出的能力。

六个维度归根结底只回答一个问题：交给你一个"智能客服系统"级别的抽象需求，你能不能把它变成稳定、好用、能算清收益的产品。企业需要的是交付者，不是概念收藏家。

二、技术栈全景

AI 岗位的技术栈可以分成三层：底层是经典深度学习与 NLP/CV 基础，它们决定你能不能看懂模型的行为；中层是大模型应用三件套（Prompt 工程、RAG、微调），决定你能不能快速交付；上层是 Agent 编排、GraphRAG 等前沿能力，决定你的薪资天花板。下面按层梳理各方向的核心知识点。

AI 岗位技术栈知识树 基础层 ─── Python 工程能力 │ 线性代数/概率 │ PyTorch │ HuggingFace 生态 │ ├── 深度学习 ── Transformer（注意力机制） │ CNN（卷积） │ RNN/LSTM（序列） │ ├── NLP ─────── 词向量 │ BERT（理解范式） │ GPT（生成范式） │ SFT/DPO 对齐 │ ├── CV ──────── 图像分类 │ 目标检测（YOLO 系） │ 分割（SAM 系） │ 应用层 ─── Prompt 工程 │ RAG（检索增强） │ 微调（LoRA） │ 推理部署（vLLM） │ 前沿层 ─── Agent 编排 │ GraphRAG │ 多模态融合 │ 评测与可观测性

深度学习：三大架构各管一摊

Transformer（基于自注意力机制、可并行处理任意长度依赖的架构，是当前所有大模型的底座）是绝对核心，必须能讲清注意力机制、位置编码与上下文窗口的关系；CNN 与 RNN 在工业界仍大量存活于风控、时序预测等存量系统里，理解它们的边界有助于做迁移决策。

架构核心机制代表应用优势局限
Transformer自注意力 + 位置编码，全序列并行GPT/BERT、多模态大模型长程依赖强、可无限扩展注意力开销随长度平方增长
CNN局部卷积核滑动提取特征图像识别、工业质检参数高效、推理快全局关系需深层堆叠
RNN/LSTM隐状态逐步传递时序预测、存量语音系统天然适配流式序列难并行、长序列梯度问题

NLP：从词向量到生成式范式

词向量（把词语映射为稠密向量、使语义相近的词在空间中距离相近的表示方法）是理解 Embedding 检索的起点；BERT 代表"完形填空式"的双向理解范式，适合分类与抽取；GPT 代表自回归生成范式，适合开放生成与指令跟随。理解两者的预训练目标差异，才能解释为什么检索类任务常用 BERT 系编码器做 Embedding，而对话生成用 GPT 系解码器。

技术定位必须讲清的要点
词向量（Word2Vec 系）语义表示的起点分布式假设、向量空间类比关系
BERT理解范式（编码器）MLM 预训练、[CLS] 表征、下游微调方式
GPT生成范式（解码器）自回归生成、上下文学习、温度与采样策略
SFT / DPO对齐手段指令微调与偏好优化各自解决什么问题

CV：分类、检测、分割三大任务谱系

任务输出形态代表技术典型业务场景
图像分类整图标签ResNet、ViT内容审核、商品类目识别
目标检测框 + 类别YOLO 系工业质检、安防计数
图像分割像素级掩码SAM、U-Net医学影像、抠图编辑

大模型应用层：三条路线的选型逻辑

这是当前岗位需求量最大的一层。Prompt 工程（通过设计输入指令与示例来引导模型输出的技术）上手最快但天花板在降低；微调（在预训练模型上用领域数据继续训练以改变其行为）中的 LoRA（只训练低秩旁路矩阵、冻结主干参数的轻量微调方法）让中小团队也训得起领域模型；RAG 则凭借"不动模型、只换知识"的特性成为企业落地标配。三者不是互斥的，成熟系统往往组合使用。

方案适用场景成本与周期主要局限
Prompt 工程通用任务、快速验证、格式控制小时级，几乎零训练成本受上下文窗口限制，领域深度不足
RAG知识更新频繁、需引用溯源的问答天级，建库 + 检索调优检索质量决定上限，需持续运营
微调（LoRA/SFT）固定风格/格式/领域行为注入周级，需高质量标注数据知识注入不可靠，模型升级需重训

技术栈清单很长，但评估者真正在意的不是你背过几个名字，而是你能否在给定约束（预算、数据、时效）下说出"我选 A 不选 B，因为……"。选型理由比技术名词值钱得多。

三、前沿技术储备

前沿技术是区分"能用"与"能扛线上"的分水岭。2024-2026 年的演进路线非常清晰：从让模型"答得出"，到让系统"干得了"。

前沿技术演进路线 2023 2024 2025 2026 ──────► ┌─────────┐ ┌──────────┐ ┌───────────┐ ┌──────────────┐ │ Prompt │──►│ RAG │──►│ Agent │──►│ 多 Agent │ │ 单轮对话 │ │ 检索 grounding│ │ 工具调用 │ │ + GraphRAG │ └─────────┘ └──────────┘ └───────────┘ │ + 多模态 │ └──────────────┘ 主线变化：模型能回答 → 系统能执行 → 系统可靠地执行并留痕

Agent：架构设计与模式选型

ReAct（推理与行动交替循环的模式：思考一步、调一次工具、看结果、再思考）适合 1-5 步的简单任务，但在复杂多步任务里容易迷路甚至死循环；Plan-and-Execute 先出完整计划再逐步执行、失败时重规划，适合 5-20 步的任务；Multi-Agent（多个专职智能体分工协作的架构，如研究 Agent + 代码 Agent + 写作 Agent）适合跨领域复杂任务，但协调开销与错误传播是代价。生产系统的常见形态是混合式：编排层用 Plan-and-Execute 决定调用谁，每个专家 Agent 内部用 ReAct 跑工具循环。

设计模式工作机制适用任务主要弱点
ReAct思考-行动-观察循环简单顺序任务（1-5 步）复杂任务易迷路、可能死循环
Plan-and-Execute先规划全部步骤，再逐步执行子目标明确的中长任务（5-20 步）规划开销大、计划可能过时
Multi-Agent主控 Agent 路由给专职 Agent跨领域复杂任务协调开销大、错误跨 Agent 传播

框架对比：LangChain、LangGraph 与其他

LangChain（以链式组合构建 LLM 应用的框架，拥有 600+ 集成，适合线性流水线）与 LangGraph（基于节点-边-状态的有环图编排运行时，原生支持循环、分支与断点恢复）不是竞争关系而是分层关系：自 2025 年 10 月 v1.0 起，LangChain 的 create_agent 底层就跑在 LangGraph 引擎上。选型标准只有一个——你的工作流是线性的还是有环的。Klarna、LinkedIn、Uber 等公司已在生产环境使用 LangGraph。

框架架构模型最佳用途局限
LangChainDAG 线性链（LCEL）聊天机器人、RAG、快速原型循环与分支需绕路实现
LangGraph有环图 + 持久状态 + 检查点多 Agent、需人工介入的长流程概念门槛高、简单任务显冗长
CrewAIAgent+Task+Crew 角色分工企业自动化（报告、分析流水线）流程控制弱于 LangGraph
AutoGen群聊式多 Agent 对话代码生成、研究实验配置复杂、业务抽象不足
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
graph.add_node("planner", planner)      # 规划节点
graph.add_node("executor", executor)    # 执行节点
graph.add_edge("planner", "executor")   # 确定性边
graph.set_entry_point("planner")
app = graph.compile(checkpointer=memory)  # 检查点：可中断、可恢复

生产落地的三个关键词：决策边界（哪些动作必须转人工）、Human-in-the-Loop（人工介入机制：高风险操作前设置审批节点，由人确认后再放行）、防失控（步数上限 + 动作指纹去重 + 超时熔断，三件套缺一不可）。工具协议方面，MCP（Model Context Protocol，标准化模型与外部工具交互的开放协议）正在成为工具接入的事实标准。

行业现实：2026 年分析显示，72%-80% 的企业 RAG/Agent 项目未能进入生产环境——卡住它们的不是模型能力，而是确定性、可追溯性与运维成本。一个典型生产团队的经历：12 个 Agent 项目里 8 个从 LangChain 起步，其中 4 个在状态管理成为瓶颈后被重写到 LangGraph。"能跑 Demo"与"能扛线上"之间的距离，正是大多数候选人的能力缺口所在。

GraphRAG：知识图谱融合与多跳推理

GraphRAG（在检索层引入知识图谱结构的 RAG 变体：入库时用 LLM 抽取实体与关系建成图，查询时沿边遍历而非只比向量距离）解决的是向量 RAG 的三个结构性盲区：连不起跨文档的线索、答不了全局性问题、切块时丢掉了关系。知识图谱（以节点表示实体、以边表示关系的结构化知识存储）让多跳推理（答案需要经过多个实体关系链才能拼出的问题类型，如"A 公司的供应商的合规状态"）从碰运气变成可遍历。微软 GraphRAG 还引入社区检测（Leiden 算法）对图做层级聚类并预写摘要，查询时走 map-reduce 合成全局答案。

维度向量 RAGGraphRAG
检索单元相似文本块实体、关系与社区摘要
多跳推理弱：靠嵌入相似度碰运气强：沿图的边显式遍历
全局性问题几乎无法回答社区摘要 + map-reduce 合成
建设成本低，切块入库即可高，需抽取实体关系并运营图质量
适用数据事实集中于单段的问答关系密集型数据（金融/法律/供应链）
带数字的技术证据：微软 GraphRAG 在复杂多实体查询上取得 86% 的全面性得分，而传统向量 RAG 只有 57%；在全局理解类问题上，GraphRAG 赢得 72%-83% 的全面性对比与 62%-82% 的多样性对比，且顶层摘要最多节省 97% 的 token。HippoRAG 在多跳问答上报告最高 20% 的准确率提升，同时成本降低 10-20 倍、速度快 6-13 倍。成本侧，成熟 SDK 用 GPT-4o-mini 构建 1000 篇文档的图约花费 5-6 美元 token，单次查询增量约 0.001 美元。注意：ICLR 2026 的 GraphRAGBench 同时提醒，单事实查询场景下图结构未必优于向量检索——选型的依据永远是问题形态，而不是技术热度。

多模态：跨模态融合与应用

多模态岗位关注异构数据（图片/文字/表格）的统一处理：视觉编码器把图像投影到语言模型的表示空间，实现图文对齐；表格类数据则需要结构化解析后再进入上下文。工程上最难的不是调通模型，而是错误识别与修正流程——OCR 错字、表格错位、图文矛盾时系统如何兜底。

应用方向技术要点工程难点
文档智能（扫描件问答）OCR + 版面分析 + 图文对齐表格结构还原、低质扫描件容错
图文理解（客服图片工单）视觉编码器 + LLM 融合推理图文矛盾时的置信度判定
生成与编辑扩散模型 + 指令控制一致性控制与审核合规

前沿技术的正确学法不是追新名词，而是抓住不变的问题：如何让系统可靠地完成一件真实的事。Agent 解决"执行"，GraphRAG 解决"关联"，多模态解决"感知"——想清楚每个技术在补哪块短板，比记住十个框架名字有用得多。

四、业务理解与价值交付

企业招聘 AI 人才时的本质要求只有一条：核心价值体现在把抽象需求（如"智能客服系统"）转化为可落地的技术方案。这解释了为什么很多技术概念倒背如流的候选人依然在筛选中落败——他们回答的是"这个技术是什么"，而企业想听的是"这个技术在这个场景里值多少钱"。

为什么业务侧愿意为 AI 付钱：麦肯锡测算生成式 AI 每年可为全球经济贡献 2.6-4.4 万亿美元的增量价值；受控实验显示开发者使用 AI 编码工具可将编码任务完成速度提升最高 55%。企业真正需要的不是"会用 AI"的人，而是"能用 AI 把一个部门效率拉高 30%"的人——后者在国内市场的年薪普遍 40 万元起步。

典型案例拆解：智能客服系统的改造逻辑

以一个典型的电商客服改造为例（综合多个公开案例构造的代表性场景），完整展示"业务问题 → 技术方案 → 量化效果"的链条：

背景：某电商月均客服会话 12 万通，人工首响平均 3 分钟，首解率仅 38%，大促期间排队超时投诉激增。
问题定位：62% 的会话是重复性查询（物流、退换货政策），答案其实都沉淀在散落的 FAQ 与政策文档里。
方案：RAG 知识库（政策文档切块入库 + 混合检索 + 重排序）承接重复查询；意图置信度低于阈值时无缝转人工；敏感操作（退款）永远转人工——即先划清决策边界。
效果：上线三个月后首解率从 38% 提升至 71%，人工会话量下降 45%，大促投诉率下降约一半，按人力成本折算年节省约 300 万元；同时因为答案带引用溯源，错误回答的申诉率比初版下降了约 70%。

这个案例值得反复咀嚼：技术上没有任何高深之处（RAG + 阈值分流），真正的功夫在业务判断——先做会话分布分析确认 62% 的重复率，才敢立项；先划清"退款必须转人工"的边界，才敢上线。技术决策能力的含金量，就藏在这些选择里。

评估维度关键问题量化示例

项目阐述的五段式结构

把自己的项目讲清楚，和把项目做出来同样重要。推荐五段式：背景（明确解决的具体业务问题与量化现状）→ 方案（技术选型依据与备选方案对比，说清为什么不用另一个）→ 落地（开发实施的关键节点与分工）→ 坑（真实遇到的典型问题、根因与解法）→ 复盘（效果对比数据与下一步优化空间）。五段之中，"坑"是最能体现工程成熟度的部分——能讲出事故如何变成机制的人，才是交付过真系统的人。

行业趋势洞察如何准备

行业洞察不是背新闻，而是建立自己的判断框架：跟踪 2-3 个目标行业的落地案例（客服、文档智能、代码辅助是三大高频场景），记录每个案例的技术选型与量化效果，再对照目标公司的业务猜测其切入点。当你能说出"贵司的 XX 业务如果引入 RAG，瓶颈大概率在数据清洗而不是模型"时，业务理解这一维度就已经立住了。

业务理解不是软素质，而是一种可训练的硬能力：把每一个技术参数都翻译成钱——节省多少人力、降低多少风险、多快回本。说不出数字的方案，在企业眼里只是实验。

五、工程化与软技能

工程化能力是当前市场最明确的稀缺项。招聘方对"能落地、能扛线上"的定义非常具体：会部署、能优化、可观测、出了问题能定位。以下按推理链路梳理关键知识点。

生产级 LLM 服务的完整链路 请求 → API 网关 → 输入安全过滤 → 推理集群（vLLM · 连续批处理） │ │ 前缀缓存 / KV 缓存 模型路由：简单→小模型 │ 复杂→旗舰模型 ▼ 用户 ◄── SSE 流式输出 ◄── 输出安全校验 ◄── 生成结果 ▲ └──── 监控告警 ◄── 指标看板（p99 延迟 / token 成本 / 错误率）

推理性能优化：每个技术都要带着数字讲

KV 缓存（推理时缓存已计算的 Key/Value 张量，避免重复计算的机制）是推理优化的核心对象；连续批处理（动态地将到达的请求拼入同一批次，而非等凑满固定批次再算）直接决定 GPU 利用率；投机解码（小模型起草候选 token、大模型一次前向并行验证的加速技术）则是延迟优化的利器。

问题解决思路：从救火到建机制

考察问题解决能力时，评估者想听到的是闭环而不是英雄故事。推荐结构：现象（可量化的异常）→ 定位（如何缩小范围）→ 根因（为什么必然发生）→ 修复（改了什么）→ 防再犯（加了什么监控或约束）。例如 Agent 死循环问题：表面是模型"抽风"，根因是没有步数上限与重复动作检测；修复不只是打断循环，而是加最大步数、动作指纹去重、超时熔断三道防线，并把"循环次数"接入监控看板。把事故变成机制，是工程成熟度的分水岭。

带数字的优化案例：某知识库问答系统上线初期，用户口语化提问（如"我这个单咋还没到"对应文档里的"物流进度查询"）导致检索频繁落空，Top-3 召回率仅 61%，p99 延迟高达 4.2 秒。团队分三步优化：① 查询改写——先用小模型把口语化问题改写成 2-3 个检索变体；② 混合检索——稠密向量 + BM25 关键词双路召回，用 RRF 融合；③ 用交叉编码器（Cross-Encoder，把查询与文档拼接后整体打分的重排序模型，精度高但开销大）对候选做重排序。最终 Top-3 召回率（评估集里正确答案被检索进前 K 的比例）升至 89%，p99 延迟降到 1.8 秒，答案无引用的"裸答"比例从 22% 降到 4%。

团队协作与学习路径

AI 项目的协作链条比传统项目更长：产品、算法、工程、合规、业务方都要对齐。两个高频协作场景值得准备——与产品对齐"模型能力边界"（哪些问题该让模型答、哪些必须规则兜底），与运维对齐"可观测性"（每次生成要留痕：输入、检索结果、输出、成本）。学习路径上建议 T 型布局：RAG 全链路做深做透作为竖线（它是当前企业落地标配、岗位需求量最大），Agent 与评测做广作为横线，避免每个方向都浅尝辄止。

  • 每个生产功能先定评估集，再谈优化：没有基线数字的优化都是自我感动
  • 高风险操作设置人工审批节点，决策边界写进设计文档
  • 给 Agent 加步数上限、动作去重、超时熔断三件套
  • 每次生成留痕：输入、检索内容、输出、成本，全链路可追溯
  • 上线先灰度 5%-10% 流量，盯 p99 延迟与错误率再放量
  • 用 Demo 指标冒充生产指标：测试查询与真实查询长度差 3-5 倍
  • 把"模型不稳定"当根因：绝大多数不稳定是系统设计缺陷
  • 只测 happy path：口语化输入、对抗性输入、空检索结果都要覆盖
  • 盲目上多 Agent：单 Agent + 好工具能解决的，别引入协调开销
  • 没有回滚方案就放量：模型升级、Prompt 变更都可能让指标崩盘

工程化的本质是把"偶尔能跑对"变成"持续可预期"：一切优化先看基线数字，一切故障都要沉淀成机制。能说出 p99、召回率、单次成本三个数字的人，天然比只会说"效果不错"的人可信。

作品集的核心原则是"证据思维"：展示你做成了什么，而不是你学过什么。一个好的项目仓库应该包含——问题定义（业务背景与基线数据）、架构决策记录（为什么选这个方案、否决过什么）、评估报告（数字说话）、踩坑记录（事故如何变成机制）、成本账单（每月 token 与服务器开销）。评估者浏览仓库的时间通常不超过十分钟，README 第一屏必须出现数字。

  • 记录选型对比：用过又放弃的方案同样有价值
  • 提供一键启动（docker compose up）与在线 Demo 链接
  • 把失败实验也写进文档：它们证明你做过对照
  • 罗列十几个 Hello-World 级仓库：广度不能弥补深度
  • 只贴代码不写背景：没有业务语境的技术展示没有说服力
  • 用"效果很好"代替数字：形容词在评估中等于零信息
  • 把仓库当网盘：杂乱无 README 的仓库是负分项

Q&A

为什么"能背概念名词"的候选人在 AI 岗位筛选中越来越吃亏？
Agent、RAG、Prompt 等概念已经是入门常识，它们在评估中的边际价值急剧下降。真正的区分度在于：你能否在给定约束下做出选型（什么场景用 RAG、什么场景必须微调）、能否把系统推上生产并保持稳定（死循环怎么防、检索落空怎么兜底、成本怎么控）。市场上"纯调 API"的经验供给过剩，而具备规划、工具、记忆、观测全链路能力的候选人依然稀缺——概念收藏家与交付者之间的差距，就是通过率的差距。
大模型应用工程与传统算法岗的能力要求有何本质不同？
传统算法岗偏"造轮子"：看数学功底、论文复现与模型创新，壁垒最高但岗位最少；大模型应用工程偏"用轮子造车"：核心是把现成模型产品化——需求分析、方案选型、工程部署、成本控制与业务理解。后者岗位需求量大、入门门槛相对友好（Python + FastAPI + RAG 即可切入），但"能落地、能扛线上"的门槛在持续提高，只会跑 Demo 的候选人正在被市场淘汰。
Agent 框架选型时，LangChain 与 LangGraph 到底怎么选？
判断标准只有一个：你的工作流是线性的还是有环的。线性流水线（RAG 链、单轮问答、摘要）用 LangChain 的 LCEL 组合更快、生态更成熟；需要循环、条件分支、人工审批介入、故障后恢复状态的长流程，用 LangGraph 的节点-边-状态模型。两者不是替代关系：自 2025 年 10 月 v1.0 起，LangChain 的 create_agent 底层就跑在 LangGraph 引擎上。一个真实团队的参考数据：12 个 Agent 项目中 8 个从 LangChain 起步，4 个在状态管理成为瓶颈后重写到 LangGraph。
GraphRAG 什么时候真正优于普通向量 RAG？什么时候不该用？
GraphRAG 在三类场景优势明显：多跳推理（答案散落多文档、需经实体关系链拼接）、全局理解（"这两年客诉的主要主题是什么"这类需要纵览语料的问题）、关系密集型数据（金融、法律、供应链）。微软实验显示复杂多实体查询上全面性 86% 对 57%，全局问题赢得 72%-83% 的对比。但单事实查询场景下普通向量 RAG 更便宜更快，GraphRAG 的建图成本（实体关系抽取、图质量运营）需要查询量摊薄——ICLR 2026 的 GraphRAGBench 也证实图结构并非普适增益。选型依据永远是问题形态，不是技术热度。
项目经验薄的人，如何证明自己的业务理解能力？
把现成开源场景（客服问答、文档助手）完整做一遍，并全程量化：会话分布分析、首解率、人工量变化、单查询成本、回本周期。阐述时用"背景 → 方案 → 落地 → 坑 → 复盘"五段式，重点讲清楚两处决策：为什么选这个方案，以及被否决的备选方案代价是什么。数字本身就是业务理解的证据——能算出"这个系统一年省 300 万人力成本"的人，不需要解释自己懂不懂业务。
项目中的"坑"怎么讲，才能体现工程成熟度而不是暴露问题？
用"现象 → 定位 → 根因 → 修复 → 防再犯"的结构讲。以 Agent 死循环为例：现象是任务执行超过 30 步不收敛；定位发现模型在两个工具间反复横跳；根因是没有步数上限也没有重复动作检测；修复是加最大步数、动作指纹去重、超时熔断三道防线；防再犯是把循环次数接入监控告警。关键不是"我遇到过大事故"，而是"我把事故变成了机制"——后者才是交付过生产系统的人才有的叙述方式。
三个月内如何构建有竞争力的作品集？
按"一个深度项目胜过十个 Demo"的原则推进：第 1 个月做 RAG 全链路（清洗、切块、混合检索、重排、评估集基线）；第 2 个月加 Agent 能力（工具调用、人工介入节点、防死循环），并写 LangChain/LangGraph 选型对比；第 3 个月补部署与可观测（容器化、监控面板、成本账单），再按五段式打磨 README。仓库 README 第一屏必须出现数字：基线指标、优化幅度、月度成本。这样一套带完整证据链的项目，胜过十几个 Hello-World 仓库。
为什么沟通协作在 AI 岗位的考察权重持续上升？
AI 项目的价值链条特别长：产品、算法、工程、合规、业务方都要对齐，任何一个环节误解模型能力边界都可能导致项目返工或上线事故。能否向非技术方讲清"这个方案值不值得做、风险在哪、错误了怎么兜底"，直接决定项目能否拿到资源。前沿实验室专门设置使命与价值观轮且拥有一票否决权；国内市场则为"能把技术语言翻译成用户价值"的复合人才开出年薪 40 万起的价码。技术决定下限，沟通决定你的方案能不能真正落地。
