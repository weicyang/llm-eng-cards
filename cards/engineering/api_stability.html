ST03 · 大模型 API 调用稳定性

LLM API Stability — 告别 try-catch 裸奔，三层铁甲防线：智能重试、熔断降级、结果缓存，构建生产级容错体系

核心考察的不是你会不会写 try-catch，而是系统设计思维 —— 故障降级、重试机制、熔断限流。异常捕获 ≠ 稳定性保障，「许愿式编程」在生产环境就是定时炸弹。

一、「许愿式编程」的三大定时炸弹

典型的错误做法：一个 try-catch 了事。

典型的错误链路是：请求失败 → 直接吞异常 → 返回空值给上层。这样做看似“没有报错”，实际上把真实问题转移成了用户失败、线程堆积和监控失真。

三个生产事故场景

场景触发条件后果
API 抖动服务偶尔返回 5xx直接 return None → 用户请求失败 → 用户流失
API 限流并发上来，返回 429不做处理 → 疯狂重试 → IP 被永久拉黑 → 服务瘫痪
服务雪崩上游响应变慢线程全卡在等待 → 连接池打满 → 整个系统崩溃
异常捕获 ≠ 稳定性保障。真正需要关注的是故障降级、重试机制、熔断限流等系统设计思维，而不是基础语法。

生产环境中，LLM API 的 P99 延迟通常在 8-15 秒，任何裸调用（无超时、无重试、无熔断）都相当于把系统的命脉交给了概率——出来混，迟早要还。

📊 生产案例：某电商平台在 2025 年双十一期间，因未对 LLM 客服 API 做限流保护，429 错误在高峰期达到每分钟 12,000 次，导致自动重试风暴，IP 被服务商封禁 47 分钟，直接影响订单咨询转化率下降约 8.3%。

二、第一层防线：智能重试

让偶发故障「自动愈合」，但要避免「雪上加霜」。

智能重试三要素

要素含义实现
可重试错误判断只对特定错误重试5xx 系列 / 429 / 网络超时 → 重试；4xx 其他 → 不重试
指数退避重试间隔成倍增加1s → 2s → 4s → 8s，避免短时间冲击服务
最大重试次数设置截止阈值最多 3 次，超过则进入下一层防线
智能重试决策: 收到响应 / 异常 | +-- 5xx / 429 / 网络超时 ----> 可重试 | | | +--> 按 1s -> 2s -> 4s 退避 | +--> 最多 3 次 | +-- 普通 4xx -----------------> 不重试 | +-- 重试耗尽 -----------------> 进入熔断/降级层

指数退避 + 随机抖动（Jitter）是生产标配。纯指数退避在大规模并发下仍可能产生「重试风暴」，加上 Full Jitter（在 0 到退避上限之间取随机值）可有效打散请求波峰。

📊 生产案例：某 SaaS 平台接入 3 家 LLM 供应商后，通过指数退避（base=1s, max=16s）+ Full Jitter 策略，将 429 限流错误从日均 3,400 次降至 180 次，降幅达 94.7%，API 调用成本因重试命中率提升而降低约 12%。

三、第二层防线：熔断降级

当 API 持续失败时，立刻「切断」请求，避免拖垮整个系统。这就是熔断器模式（Circuit Breaker Pattern）。

熔断器三态

熔断器状态机: ┌──────────┐ 失败率 > 50% ┌──────────┐ │ CLOSED │──────────────→│ OPEN │ │ (正常通行) │ │ (直接断路) │ └──────────┘ └────┬─────┘ ↑ │ │ 超时后(30s) │ 成功 ↓ │ ┌──────────┐ └────────────────────│ HALF-OPEN│ │(试探恢复) │ └──────────┘
状态行为转移条件
Closed（关闭）正常通行，记录失败数失败率 > 阈值 → 转为 Open
Open（打开）直接断路，不发送请求超时后 → 转为 Half-Open
Half-Open（半开）试探性发送少量请求成功 → 转为 Closed；失败 → 回到 Open

重试和熔断的方向是相反的：重试是"再试一次也许就好了"，熔断是"别试了越试越糟"。两者的分界线是失败的性质——单次抖动值得重试，下游整体不可用时重试只会把自己的线程池也拖死，所以熔断必须比重试拥有更高的优先级：熔断器一旦 Open，重试逻辑就不该再被触发。

服务降级兜底

熔断器「打开」时，不直接抛错，而是：

  • 返回默认值（如预设的标准回答）
  • 返回缓存快照（上次成功的结果）
  • 返回友好提示（「服务繁忙，请稍后重试」）

四、第三层防线：结果缓存与本地兜底

4.1 请求结果缓存

对相同或相似的请求，没必要每次都调用昂贵的 API。

方案实现适用场景
Redis 集群基于 Prompt 哈希生成 Key分布式系统，多实例共享缓存
本地缓存Guava Cache / functools.lru_cache单实例，低延迟需求
请求结果缓存流程: 用户请求 | +--> 生成稳定缓存键 | +--> 先查缓存 | +-- 命中 --> 直接返回结果 | +-- 未命中 --> 调用 LLM API | +--> 成功结果写回缓存 +--> 设置 TTL，平衡实时性与成本

4.2 本地兜底

所有防线失效后的「最终防线」—— 当重试、熔断、缓存全部耗尽时：

  • 返回预设的确定性回答
  • 调用轻量级本地模型（如 1B 参数的小模型）
  • 底线：杜绝向用户展示原始错误代码或空白页面
  • 只对 5xx/429/超时做重试，不盲目重试所有错误
  • 用指数退避避免短时间冲击服务
  • 引入熔断器防止服务雪崩
  • 缓存高频请求的结果，减少 API 调用
  • 始终提供本地兜底方案
  • 不要 try-catch 后直接 return None
  • 不要对 4xx 客户端错误做重试
  • 不要无限重试（设最大次数上限）
  • 不要向用户展示原始错误码
  • 不要忽略 429 限流（会被封 IP）

5.1 多提供商故障转移架构

在生产环境中，单一 LLM 供应商的SLA（Service Level Agreement，服务等级协议）通常承诺 99.9% 可用性，即每月允许约 43 分钟宕机。通过多提供商冗余可将整体可用性提升至 99.99%（月宕机 ≤ 4.3 分钟）。

📊 生产案例：某金融科技公司通过部署 Prometheus + Grafana 监控体系，对 LLM API 的 P99 延迟、错误率、熔断器状态进行实时告警。上线后平均故障发现时间（MTTD）从 18 分钟缩短至 2.5 分钟，平均故障恢复时间（MTTR）从 45 分钟缩短至 8 分钟，月度 API 相关工单减少 73%。

Q&A

如何保证大模型 API 调用的稳定性？
三层防线：(1) 智能重试 —— 对 5xx/429/超时做指数退避重试（1s→2s→4s），最多 3 次；(2) 熔断降级 —— 引入熔断器模式，失败率超阈值时直接断路，避免服务雪崩；(3) 结果缓存 + 本地兜底 —— 缓存高频请求结果，所有防线失效时返回预设答案或调用本地小模型。核心思想：假设系统一定会出错，建立完整的事前预防机制。
为什么不能对所有错误都做重试？
因为 4xx 客户端错误（如 400 Bad Request、401 Unauthorized）是请求本身的问题，重试不会改变结果，只会浪费资源和时间。只有 5xx 服务端错误（服务暂时不可用）、429（限流，稍后重试可能成功）、网络超时（瞬时问题）才值得重试。盲目重试所有错误 = 对错误的请求无限浪费资源。
熔断器的三种状态是怎么工作的？
Closed（正常通行，记录失败数）→ 失败率超阈值时转为 Open（直接断路，不发送请求）→ 超时后转为 Half-Open（试探性发送少量请求）→ 成功则回到 Closed，失败则回到 Open。熔断器的核心价值：当上游服务持续故障时，快速失败而非长时间等待，保护下游系统不被拖垮。
指数退避的原理是什么？为什么要用指数而不是固定间隔？
指数退避（Exponential Backoff）让重试间隔成倍增加（1s→2s→4s→8s）。原因是：(1) 如果服务因过载而限流，所有客户端同时以固定间隔重试会形成「惊群效应」，加剧服务压力；(2) 指数增长的间隔给服务恢复留出更多时间；(3) 不同客户端的退避时间自然错开，避免同步重试。固定间隔的问题是所有客户端会在同一时刻同时重试。
什么是服务雪崩（Cascading Failure）？怎么防止？
服务雪崩指上游 API 响应变慢 → 所有线程卡在等待 → 无法处理新请求 → 数据库连接池打满 → 整个系统崩溃。防止方式：(1) 熔断器 —— 快速失败而非长时间等待；(2) 超时控制 —— 每个请求设置合理超时（如 30s）；(3) 线程池隔离 —— API 调用使用独立线程池，不影响其他业务；(4) 限流 —— 控制并发请求数量。核心思想：隔离故障域，防止一个组件的故障扩散到整个系统。
请求合并（Request Batching）什么时候用？有什么限制？
当多个请求在短时间内到达且可以容忍短暂延迟时使用。原理：把 N 个请求打包成一个批量请求发给 API，减少网络开销和连接数。限制：(1) 增加单次请求延迟（需要等待凑够批次或超时）；(2) 不适合实时性要求高的场景；(3) API 必须支持批量接口。适用场景：后台批处理、非实时的数据分析、离线任务。
多提供商冗余架构中，如何处理不同供应商的输出差异？
核心挑战：不同 LLM 供应商即使收到相同 Prompt，输出格式和质量也可能不同。解决方案：(1) 统一适配层 —— 在路由层与供应商之间加入适配器，标准化输入输出格式（如统一 JSON Schema）；(2) Prompt 模板隔离 —— 为每个供应商维护专属 Prompt 模板，针对其模型特性微调；(3) 输出校验 —— 对返回结果做格式校验和语义一致性检查，不合格时自动切换到下一个供应商重试；(4) A/B 测试基线 —— 定期用标准测试集评估各供应商的输出质量，作为流量分配权重依据。生产实践中，头部供应商承载 70-80% 流量，备选供应商承载 20-30%，确保备选线路始终处于「热备」状态。
缓存的 Key 应该怎么设计？语义相似但文本不同的请求能命中缓存吗？
基础方案是对 Prompt 文本做哈希（如 SHA-256）作为缓存 Key，但语义相似而文本不同的请求无法命中。进阶方案：(1) 语义缓存 —— 用 Embedding 模型将 Prompt 转为向量，在向量数据库（如 Milvus、Pinecone）中做相似度检索，余弦相似度 > 0.95 时复用缓存结果；(2) 归一化预处理 —— 对 Prompt 做去停用词、排序、小写化等标准化处理后再哈希，提升命中率；(3) 分层缓存 —— L1 精确匹配（本地 LRU，延迟 < 1ms）、L2 语义匹配（向量库，延迟 ~50ms）、L3 穿透到 API。注意：语义缓存需要评估「复用旧答案」对业务的影响，对准确性要求高的场景（如金融计算）应只用精确匹配。
限流（Rate Limiting）和重试（Retry）是什么关系？如何协同工作？
两者是互补关系：限流是「主动防御」—— 控制自身发出的请求速率，避免触发服务商的 429 限制；重试是「被动恢复」—— 在请求失败后尝试再次执行。协同机制：(1) 令牌桶 / 漏桶算法在客户端侧做请求整形，确保请求速率始终低于服务商配额（如服务商限制 60 RPM，则客户端自限至 50 RPM 留缓冲）；(2) 当 429 发生时，解析响应头 Retry-After 字段获取服务商建议的等待时间，优先使用该值而非指数退避；(3) 全局维护「配额消耗计数器」，当剩余配额 < 20% 时主动降速，为高优先级请求预留额度。核心原则：宁可自己限流丢失部分请求，也不要触发服务商限流导致全局封禁。
