ST09 · AI 系统幂等设计

Idempotency for AI Systems — 用 Redis SETNX + 状态机挡住重试风暴，避免 Workflow、Tool、副作用任务被重复执行

一、幂等不是锁，而是“重复请求的业务记忆”

幂等的本质不是把别人挡在门外，而是让系统记住“这件事已经做过没有、做到哪一步、最终结果是什么”。

幂等（Idempotency）指同一个业务请求执行一次和执行多次，最终对业务世界产生的结果一致。在 AI 系统里，真正危险的不是重复算一遍，而是重复触发副作用，例如重复扣费、重复调用外部 API、重复写入向量库、重复发邮件。

方案解决的问题致命缺口
只加分布式锁避免并发同时执行挡住了第二个请求，却没有保存结果，后来的请求不知道该返回什么
只做缓存复用已完成结果第一次执行期间没有处理中状态，无法解释“现在到底在做什么”
幂等状态机同时处理并发、重试、结果复用需要设计状态、TTL 和失败恢复策略
在 AI 场景里，重试通常来自客户端超时、网关自动补偿、消息队列重复投递、Agent 自恢复机制。没有幂等时，这些"可靠性机制"会反过来制造重复扣费和重复执行。

没有幂等的系统，每一个"为了可靠而生的重试"都会变成一次"不可控的副作用放大器"。

重试风暴放大链路（无幂等时）: 用户点击 "提交" | v 前端超时 (15s) ----> 自动重试 #1 | | v v 网关超时 (20s) ----> 自动重试 #2 | | v v MQ 重投递 --------> 重复消费 #3 | v Agent 自恢复 -----> 重跑整条 Workflow #4 结果: 1 次用户操作 = 5 次业务执行 = 重复扣费 + 重复发邮件 + 重复写库

幂等设计的最高境界，是让调用方完全感知不到重试的存在——无论请求被发送了几次，拿到的结果和第一次成功执行时完全一致。

二、推荐实现：Redis SETNX + 状态机

先抢到“唯一执行权”，再把执行过程写成状态机，系统就既能防重，又能回答后来者“现在是什么状态”。

状态机为什么比锁更适合 AI 工作流

SETNX（Set If Not Exists）是 Redis 的原子写入能力，它保证只有第一个请求能创建记录。关键不在于“抢到锁”本身，而在于它顺手创建了一个可查询的业务状态，后续请求看到的不是空白，而是正在处理、已成功或已失败。

请求到达 | v SETNX idempotent:{key} status=PROCESSING ttl=10m | +---- 创建成功 ----------> 执行业务 ---------> 写回 SUCCESS + result + ttl=24h | +---- 创建失败 ----------> 读取已有记录 | +-- SUCCESS ----> 直接返回结果 +-- PROCESSING -> 返回处理中/轮询 +-- FAILED -----> 按策略允许重试或返回失败
幂等令牌（Idempotency Token）完整流转: 客户端 网关 业务服务 Redis | | | | |-- 生成 idempotency_key ->| | | | |-- 透传 key + payload --->| | | | |-- SETNX key --------->| | | |<-- 创建成功/已存在 ----| | | | | | | |-- [首次] 执行业务 ---->| | | |-- 写回 SUCCESS ------->| | |<-- 返回业务结果 ----------| | |<-- 200 OK ---------------| | | | | | | |-- 超时重试 (同 key) ---->| | | | |-- 透传 key + payload --->| | | | |-- GET key ----------->| | | |<-- SUCCESS + result --| | |<-- 直接返回缓存结果 ------| | |<-- 200 OK (复用结果) ----| | |

上图展示了 幂等令牌（Idempotency Token）从生成到复用的完整生命周期。关键点在于：令牌由客户端在首次请求时生成并持久化，所有后续重试都必须携带同一令牌，服务端据此判断是首次执行还是结果复用。

上面的流转适合 AI 请求，因为很多链路执行时间长，可能跨越 RAG、Tool、LLM、数据库更新多个阶段。只加锁只能防止并发重入；状态机则能把系统从“互斥”升级为“可恢复、可观测、可复用”。

锁只能回答“现在有没有人在做”，状态机还能回答“做到哪了、做完了没、做出来的是什么”。

TTL 策略的三层设计

TTL（Time To Live）是幂等记录的生命线。设得太短，执行还没结束记录就过期，重复请求会被当成新业务再次执行；设得太长，又会浪费存储并在业务变更后返回过时结果。推荐按三层分别配置：

层级TTL 范围目的回收策略
PROCESSING 层5 ~ 10 分钟覆盖单次 Workflow 的最大执行时间到期自动释放，下次请求视为新任务
SUCCESS 层24 小时 ~ 7 天覆盖用户重试、页面刷新、链路补偿按业务重要性分级回收，计费类保留更久
FAILED 层1 ~ 10 分钟短时间防重放，允许退避后安全重试短 TTL 到期后允许新请求重新尝试
生产里最稳妥的做法是让 PROCESSING 的 TTL 略大于工作流 P99 执行时间。如果 P99 是 45 秒，TTL 至少设 3 分钟；如果 P99 是 5 分钟，TTL 至少设 10 分钟。
状态含义建议 TTL设计原因
PROCESSING请求已被接管，业务仍在执行5 到 10 分钟防止实例崩溃后永久卡死，给自动恢复留窗口
SUCCESS请求已完成，可复用最终结果24 小时到 7 天覆盖用户重试、前端刷新、链路补偿等高频重复读
FAILED请求失败，带错误原因1 到 10 分钟避免瞬时错误无限重放，同时允许短时间后安全重试

一个最小可落地的数据结构

record = { status, request_hash, response, error, created_at, finished_at }

request_hash 用来校验“同一个 key 是否真的对应同一份请求”。如果客户端误把两个不同请求塞进同一个 idempotency key，系统必须拒绝，否则幂等层会把错误结果复用给另一条业务。

生产里最常见的坑不是没有幂等，而是“只有 key，没有 payload 校验”。结果就是同一 key 被错误复用，导致看上去稳定，实际上返回了别人的结果。

三、AI 系统里哪些地方必须做，哪些地方别乱做

幂等应该加在“有副作用或成本昂贵的边界”，而不是对所有请求一刀切。

按业务语义划分边界

副作用 指请求除了返回结果，还会改变外部状态，例如扣费、写库、发通知、创建订单。AI 系统最大的误区，是把“模型推理”视为唯一成本点，而忽略了 Tool 调用和异步任务才是重复执行最危险的位置。

场景是否建议幂等原因推荐唯一键
Chat Completion / 整个 AI 请求必须超时重试会重复消耗 Token，还可能重复触发工具链request_id 或业务层 idempotency_key
Agent Workflow强烈建议工作流长、步骤多，重放一次可能造成多次外部写操作session_id + turn_id 或 workflow_id
有副作用的 Tool必须转账、下单、发邮件、发消息不能接受重复执行tool_call_id、订单号、支付单号
RAG 检索通常不需要只读且无副作用，重复执行更多是性能问题而不是一致性问题更适合做 query cache
Embedding / 索引构建建议消息重复消费会让同一 chunk 被写两次，污染召回与统计doc_id + chunk_id

旧方案和新方案的边界差异

思路旧做法工程化做法
Chat API把重试交给客户端 SDK在网关或 Chat Service 入口统一做幂等和结果复用
Agent认为“失败就整条重跑”在 Workflow 入口设幂等，在关键 Tool 层再做一次局部幂等
RAG什么都加锁只做缓存和限流，不把无副作用查询误当成幂等问题
幂等的重点不是“请求会不会重复发来”，而是“重复发来以后会不会对外部世界产生第二次不可逆影响”。

判断要不要做幂等，只需问一个问题：如果这条请求被无声地执行两次，用户能不能接受？不能接受就必须做。

容易误判的三个灰色地带

以下场景经常被团队忽略，但它们在 AI 系统中出现的频率比想象中高得多：

灰色场景常见误判正确做法
LLM 生成后写回数据库以为只是“存个结果”必须按 request_id 幂等，否则同一推理结果被写两份，污染下游统计
异步回调通知以为回调只来一次回调天然不可靠，接收端必须做 幂等消费，按事件 ID 去重
Embedding 增量更新以为消息队列保证 exactly-once大部分 MQ 实际提供 at-least-once，同一 chunk 可能被消费两次，需按 doc_id + chunk_id + version 去重
在 Agent 架构中，Tool 调用是最容易被忽视的副作用边界。一个“查询天气”的 Tool 看似只读，但如果它同时会写审计日志或触发计费，就需要重新评估幂等需求。

四、设计细节：Key、TTL、失败恢复一个都不能少

幂等设计真正难的不是写出 SETNX，而是把 key 生成、超时回收、异常恢复和结果校验全部补齐。

Key 设计要绑定业务语义

Idempotency Key 必须表达“这一件业务事实”，而不是随手生成一个随机值。随机 UUID 只能保证唯一，不能保证语义稳定；如果用户点击重试时产生了新 key，那系统就会把同一业务当成新请求重新执行。

设计项推荐做法不要这样做
Key 生成由客户端或业务层稳定生成，与请求语义绑定每次重试临时生成新 UUID
Payload 校验保存 request_hash，不一致就拒绝只认 key，不看请求体是否一致
返回策略SUCCESS 直接回结果，PROCESSING 回处理中或短轮询PROCESSING 时再次执行业务
失败恢复FAILED 保留短 TTL，并附错误原因和可重试策略失败后立刻删 key，导致抖动时反复打爆下游

一个典型的落地流程

典型幂等落地流程: 请求到达 | +--> 校验 idempotency_key 是否存在 +--> 计算 request_hash，确认同 key 对应同一请求 +--> SETNX 写入 PROCESSING + 短 TTL +--> 执行业务流程 +--> 成功: 写 SUCCESS + 结果 + 长 TTL +--> 失败: 写 FAILED + 错误 + 短 TTL +--> 重复请求: 按已有状态直接返回或等待

这套流程之所以比“查缓存 -> 加锁 -> 执行 -> 写缓存”更稳，是因为每一步都围绕业务状态展开。系统崩溃时，后续请求至少知道上一条记录停在什么阶段，而不是只能猜测“锁是不是忘记释放了”。

幂等方案横向对比

维度数据库唯一索引Redis SETNX消息去重表乐观锁 (version)
适用场景写入型业务，如订单、账单通用 API 幂等，尤其是长耗时 AI 请求MQ 消费端去重更新型操作，如库存扣减
性能受限于数据库写入 TPS内存级，10 万+ QPS取决于数据库取决于数据库
状态表达力只能表达"存在/不存在"可存 PROCESSING/SUCCESS/FAILED 多态只能表达"已消费/未消费"只能表达"版本是否匹配"
故障恢复依赖数据库事务依赖 TTL 自动过期依赖 TTL 或定期清理无自动恢复，需业务重试
AI 系统适配度中（适合落库环节）高（推荐首选）高（适合异步链路）低（不适合长流程）
在 AI 系统中，Redis SETNX 之所以成为首选，是因为它同时满足三个条件：内存级性能足以扛住高并发重试、多态存储能表达完整状态机、TTL 机制天然解决了僵尸记录问题。
  • 让客户端重试时复用同一个业务 key
  • 保存请求哈希，防止错误复用
  • 给 PROCESSING 设置较短 TTL 防僵尸锁
  • 把最终结果和错误原因写回状态记录
  • 对 Tool 层和 Workflow 层分别建幂等边界
  • 不要把随机 UUID 当成稳定业务 key
  • 不要只上分布式锁不保存结果
  • 不要让 PROCESSING 永不过期
  • 不要在重复请求到来时再次执行业务
  • 不要忽略失败态和异常恢复路径
如果一个系统只有 SUCCESS 缓存，没有 PROCESSING 和 FAILED，它解决的是“结果复用”，不是“幂等控制”。

五、生产案例：Agent 工单系统如何从重复执行降到 0

生产事故通常不是因为算法不够先进，而是因为一次超时重试让整个工作流又跑了一遍。

案例背景

某企业内部工单 Agent 日均处理约 8 万次请求，入口链路是“意图识别 -> 检索知识库 -> 调用工单 Tool -> 发送确认邮件”。改造前客户端超时阈值设为 15 秒，而完整工作流 P95 为 22 秒，结果前端和网关都会自动重试。

阶段改造前改造后
重复 Tool 调用率2.8%0.03%
重复发邮件事件日均 430 次日均 4 次以内
平均 Token 浪费每日报废约 11 万 Token下降到 6000 Token 以内
故障定位时长45 分钟8 分钟

根因与修复

根因不是单一超时，而是缺少统一的 Workflow 入口幂等。同一个用户重试请求会重跑整条链路，导致下游 Tool 把“再次请求”误当成“新业务”。修复时团队在入口增加 idempotency_key，对有副作用的 Tool 再加 tool_call_id 级别幂等，同时把 Redis 记录打到可观测平台里，允许排查时直接看到每次请求的状态流转。

Client Retry | v API Gateway ---- idempotency_key ----> Workflow Guard | +--> RAG (query cache) +--> Tool A (tool_call_id) +--> Tool B (tool_call_id) +--> LLM 数据流说明: 1. 整个入口先做一次 Workflow 级防重 2. 有副作用的 Tool 再做局部幂等 3. RAG 不做幂等，只做缓存和限流
最有效的改造不是把所有地方都幂等化，而是把“整条工作流入口”和“有副作用的工具边界”这两个高风险断点守住。

幂等改造的 ROI 极高：一个入口级 SETNX 加两个 Tool 级防重，就能把重复执行率从百分比级压到万分之几。

Q&A（8 题）

为什么说幂等不能只靠分布式锁？

因为分布式锁只能防止并发同时执行，不能告诉后来的请求“前一个请求做到哪了、结果是什么”。AI 工作流通常执行时间长，如果第二个请求只看到“锁没抢到”，它既拿不到结果，也不知道该等待还是失败。状态机方案把 PROCESSING、SUCCESS、FAILED 都记录下来，才能既防重又正确返回。

Chat Completion 为什么也需要幂等？它看起来只是一次推理。

表面上是一次推理，实际上很多 Chat Completion 会串联 RAG、Tool、数据库写入、审计日志和计费。用户超时后重试时，如果入口不幂等，整条链会重新跑一遍，不仅浪费 Token，还可能重复触发外部副作用。所以应在网关或 Chat Service 入口统一拦截。

RAG 检索通常为什么不需要幂等？

RAG Retrieval 大多是只读查询，重复执行不会改变外部状态，风险主要是性能浪费而不是业务错误。对于这类场景，更合适的手段是 query cache、限流和超时控制，而不是引入完整幂等状态机。只有检索链路会顺手写日志、更新统计或触发异步任务时，才需要重新评估边界。

Idempotency Key 应该由谁生成？

最好由最了解业务语义的一层生成，通常是客户端、API 网关或业务服务入口，而不是最底层存储层。关键要求是：同一业务重试时 key 必须稳定，不同业务必须不同。如果只在服务端每次收到请求都随机生成 UUID，那么一旦重试到来，系统根本无法识别这是同一笔业务。

FAILED 状态为什么不建议立刻删除？

因为真实故障常常伴随抖动和短时间重试。失败后立刻删除 key，会让下一次重试重新执行整条链路，把短暂故障放大成流量洪峰。保留一个短 TTL 的 FAILED 状态，可以告诉调用方“刚刚失败过”，并配合退避重试或人工介入，避免把下游持续打挂。

Workflow 已经做幂等了，Tool 层还要不要做？

高风险 Tool 仍然要做。入口幂等负责挡住整条链路的重复提交，但在长工作流中，局部步骤可能因为补偿、恢复、异步队列或人工重放再次被触发。像支付、发券、发邮件、创建工单这类有副作用的 Tool，最好使用独立的 tool_call_id 或业务唯一键再做一层保护，形成"全局一次、局部再验一次"的双保险。

幂等记录存在 Redis 里，Redis 宕机了怎么办？

首先要接受一个现实：幂等层本身也需要高可用。生产环境通常使用 Redis Sentinel 或 Cluster 模式保证故障自动切换。其次，对于计费、支付等零容忍场景，可以在数据库层再加一道唯一索引作为兜底，形成"Redis 挡第一道、数据库挡最后一道"的双层防线。Redis 短暂不可用时，宁可让请求失败并返回 503，也不能跳过幂等检查直接执行业务。

如何验证幂等层在生产中真正生效？

核心是建立可观测指标。建议监控三个关键数据：幂等命中率（重复请求被拦截的比例）、PROCESSING 状态平均停留时间、以及 FAILED 状态的错误分布。如果幂等命中率长期为 0，说明上游根本没有重试，或者 key 生成逻辑有误导致每次重试都用了新 key。可以定期做混沌测试，人为注入超时和重复请求，验证系统是否如预期返回缓存结果而非重复执行。
