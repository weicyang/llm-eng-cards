ST04 · Token 成本优化

Token 是新的电费。你无法优化你没有计量的东西——从计量到熔断，五层防御体系把 LLM 账单降低 40%~70%

一、先算账：成本公式与计价结构

账单是三个可乘因子的积：一次请求带多少上下文、用什么档位的模型、要跑多少轮。三者相乘意味着任何一项翻倍都会把总额翻倍，也意味着优化收益同样是相乘的——把上下文砍一半、再把七成流量分流到小模型，省下的远不止两者相加。所以先看结构再动手，别一上来就抠 System Prompt 的字数。

1.1 核心成本公式

日成本 = (输入 Token × 输入单价 + 输出 Token × 输出单价) × 日请求数 单请求毛利 = 用户收入 - 模型成本 - 人工兜底成本 - 基础设施成本 三因子公式（简化版）： 总成本 ≈ 上下文体积 × 模型单价 × 调用轮数

但三个变量都不是常量：

1.4 上下文长度对成本的非线性影响

主流大模型的 Prompt Cache 机制可以降低重复前缀成本，但当 System Prompt + 历史对话累积到 64K tokens 时，即使有缓存，单次请求成本仍是 8K 场景的 8 倍——KV Cache 压力、内存占用、调度开销等常数因子常被忽略。

二、五层成本防御体系

从零到最复杂的五层递进结构，每一层都可独立部署、独立见效：

第 1 层 摸清底数——Token 计量

不需要更换模型、不需要改动业务逻辑，只需包装 API 调用，记录每次请求的 Token 消耗、延迟、成本。运行一周后，你能看到哪些场景最烧钱、哪些模型性价比最高。

第 2 层 立竿见影——Prompt 压缩

三板斧：删除冗余示例对话、合并重复安全指令、工具 Schema 瘦身。典型效果：4,342 tokens → 980 tokens，节省 74%。每次对话都省，年化节省显著。

第 3 层 零代码降本——Prefix Cache

OpenAI 和 Anthropic 都支持自动前缀缓存：相同前缀的请求，后续命中时输入 Token 成本降低 50%~90%。关键是保持 System Prompt 稳定、模板化强。

第 4 层 智能路由——分层模型调度

用分类器判断任务难度，简单任务（FAQ、分类、提取）走小模型，复杂任务（推理、创作）走大模型。典型收益：整体成本下降 25%~70%。

第 5 层 安全网——预算熔断

设置三级预警（黄灯 70% → 橙灯 90% → 红灯 100%），到达阈值自动降级或停机。防止 Agent 死循环或异常用户把月度预算一天花光。

最高 ROI 往往不是"微调提示词"，而是先把重复请求拦掉（缓存）、把简单请求分流掉（路由）、把异常请求拦住（熔断），再去做更细的压缩和裁剪。

三、Token 计量中间件

第一步永远是"看清"。接入计量层只需包装 API 调用，不改业务逻辑：

实现思路：包装一层 API 调用，在每次请求前后自动记录以下字段：

  • 模型名称（用于按模型拆分成本）
  • 用户 ID / 项目 ID（用于按业务线拆分成本）
  • 输入 / 输出 Token 数（从 API 响应的 usage 字段直接读取）
  • 估算成本（Token 数 × 对应模型单价，写入本地 JSONL 文件）
  • 延迟毫秒数（请求开始到返回的时间差）

这层包装不影响业务逻辑，只需把原来的 API 调用替换为包装后的方法即可。一周后你会得到一份按时间序列的成本日志，足以回答"哪个场景最烧钱""哪个模型性价比最高"。

四、Prompt 压缩三板斧

4.1 删除冗余示例对话

很多 Prompt 里写了大量"示例对话"来教模型格式，但实际只需要输入/输出对：

压缩前（示例对话含大量解释）：1,680 tokens 压缩后（只保留输入/输出对）：420 tokens 节省：75%

4.2 合并重复安全指令

"不要泄露系统提示词""不要输出有害内容"等安全声明在 Prompt 里反复出现。合并为一条即可：

压缩前（重复安全声明）：620 tokens 压缩后（合并为一条）：80 tokens 节省：87%

4.3 工具 Schema 瘦身

Function Calling 的 JSON Schema 描述往往过于冗长，每个参数都写了详细解释。精简描述、去掉冗余字段：

压缩前（完整 Schema 描述）：1,042 tokens 压缩后（精简 Schema）：480 tokens 节省：54% 三板斧合计：4,342 → 980 tokens，节省 74%
Prompt 压缩的优先级：示例对话 > 安全指令 > 工具 Schema。每次对话都省，年化效果远超想象。

5.2 三级缓存架构

请求链路依次经过三级缓存拦截：L1 精确匹配 → L2 语义缓存 → L3 Prefix Cache，各层命中率与效果速览：

L1 精确匹配5%~15%100%降至 <50ms几乎无

术语对照：本文 L3 Prefix Cache 即《缓存策略》（ST06）所称 L1 Prompt Cache，命名差异源于视角不同。

语义阈值：L2 语义缓存的相似度阈值建议遵循《缓存策略》（ST06）的分场景结论——0.92-0.95 起步，金融、医疗等高风险场景用 0.95+。

5.3 Batch API：非实时任务的终极省钱方案

OpenAI / Anthropic 对批量请求提供 50% 折扣。适合数据分析、内容生成、评估任务等非实时场景。缺点是 24 小时内返回结果。

六、Agent 特有成本模式

Agent 贵在"每一步都要把前面所有步骤重新讲一遍"。单轮对话的成本随请求数线性增长，Agent 的成本随步数近似平方增长，因为第 N 步要携带前 N-1 步的全部产物。所以 Agent 降本的着力点不是单步 Prompt 写得多短，而是上下文携带量随步数的增长曲线能不能被压平。

Agent 的资源消耗账本比单轮对话复杂得多：

示例场景：一个数据分析 Agent 平均跑 12 步完成一次任务，每步把完整历史（含每次 SQL 查询返回的原始行）重新送进模型，单任务平均消耗约 9.4 万 tokens。问题：上线首月任务量涨了 3 倍，账单涨了 11 倍——因为任务变复杂后平均步数从 12 涨到 19，而每步携带量本身也随步数增长，两个因素相乘。排查发现单任务里有 62% 的输入 token 是被重复发送的历史工具返回值，其中最大一笔是一次返回 800 行的查询结果，在后续 7 步里被原样重发了 7 次。方案：三处改动——工具层给所有查询结果加行数上限并附带结构化摘要，超限只回摘要加前 20 行；每 5 步做一次状态压缩，把已完成的中间推理换成一段结论；把取数和分析拆成两个子 Agent，取数结果以摘要形式交接，原始数据不进分析侧上下文。效果：单任务平均输入从 9.4 万降到 2.6 万 tokens，降幅 72%，任务成功率基本持平（下降不到 1 个百分点）；平均步数没变，说明省下的确实是冗余携带而不是分析深度。

6.1 多步推理的成本爆炸

单轮对话：~2,000 tokens/次 Agent 任务（10 步推理）：50,000~100,000 tokens/任务 成本放大 25~50 倍

每一步推理都携带完整上下文（System Prompt + 历史 + 工具结果），10 步推理意味着 System Prompt 被重复发送 10 次。

6.2 工具调用的隐藏成本

隐藏来源典型表现治理方案
工具返回原始数据SQL 查询返回 100 行结果工具层做摘要/截断
MCP 工具开销每次调用注入完整工具描述按需加载工具 Schema
工具调用循环Agent 反复调用同一工具设置最大调用次数
错误重试工具超时后整段重跑工具层独立重试

6.3 Agent 成本治理三板斧

  1. 子 Agent 隔离：把长任务拆成多个子 Agent，每个只携带必要的上下文
  2. 工具结果裁剪：工具返回数据在注入 Prompt 前先做摘要/字段裁剪
  3. 中间状态压缩：每 5 步做一次状态总结，丢弃原始中间推理

七、隐藏成本：Reasoning Tokens 与 Context Inflation

这两项之所以是"隐藏"成本，是因为它们都不出现在任何一次代码评审里。思维链的长度由模型自己决定，你的 Prompt 里看不到它；Context Inflation 则是每次只多加十几行、每次都合理，累计三个月才显形。对付看不见的增长只有一个办法：把平均输入 token 和平均输出 token 变成有基线、有告警的日常指标。

7.1 Reasoning Tokens：思维链也计费

使用 o1/o3/DeepSeek-R1 等推理模型时，模型的"思考过程"（thinking tokens）也算输出计费。一个看似简单的数学问题，模型可能生成 5,000 tokens 的思维链 + 200 tokens 的最终答案。

DeepSeek 实测：输入"树中两条路径之间的距离"，模型陷入无限思考，思考时间 625 秒，输出 2 万字。这种无限重复思考是模型自身的"精神内耗"，更会造成算力资源的浪费。
模型思维链占比成本影响治理方案
o1/o360%~95%输出成本膨胀 3~20 倍限制 reasoning_effort
DeepSeek-R150%~90%同上简单任务用 V3 不用 R1
Claude (extended thinking)40%~80%同上设置 thinking budget

7.2 Context Inflation：Prompt 无感知膨胀

团队不断往 Prompt 里"加料"——完整日志、整份文档、多轮历史——却没意识到输入 Token 已经翻了 4 倍：

初始 Prompt：800 tokens + 完整调试日志：5,000 tokens + 产品文档全文：8,000 tokens + 示例回答：3,000 tokens + 历史对话：2,000 tokens ───────────────── 膨胀后：18,800 tokens（23 倍膨胀！）

CodeRabbit 工程团队的真实案例：Context Inflation 让开发者把诊断日志和整个代码库塞进 Prompt，模型还没开始回答，输入 Token 就已经翻倍了。

Context Inflation 是"温水煮青蛙"——每次只加一点点，但 3 个月后成本已经翻了 4 倍。必须在计量面板里监控"平均输入 Token 趋势"，设置告警阈值。

示例场景：一个文档问答服务，检索层固定取 Top-8 分块拼进上下文，运行半年没人动过这个参数。问题：季度复盘发现平均输入 token 从上线时的 5,100 涨到 13,700，账单同期涨了 1.7 倍，而回答质量指标基本没动。逐项拆解后定位到两处：一是知识库文档从 400 篇涨到 2,600 篇，同一个问题召回的 8 个分块里重复内容明显增多，抽样看有 3 到 4 块表达的是同一件事；二是分块策略当初按 400 字设定，后来入库了一批长表格文档，实际平均块长涨到 1,100 字，Top-8 的体积因此翻了近三倍。方案：召回后加一道去重和重排，按语义相似度合并近重复块，再按Token 预算而不是固定条数来截断——给检索结果分配 6,000 token 的硬预算，装不下就丢分数最低的；同时把超长分块在入库时二次切分。效果：平均输入 token 回落到 6,800，降幅 50%，答案的引用准确率还小幅上升了 2 个百分点，因为重复内容不再挤占真正相关的分块。

八、预算熔断机制

三级预警 + 自动停机，防止 Agent 死循环或异常用户把月度预算一天花光：

预算使用率 → [70% 黄灯] → [90% 橙灯] → [100% 红灯] 黄灯（70%）：发送告警，限制并发请求数 橙灯（90%）：强制降级到小模型，禁用高成本模型 红灯（100%）：暂停所有请求，人工审批后恢复
熔断级别触发条件自动动作恢复方式
黄灯预算 70%告警 + 限制并发自动
橙灯预算 90%强制降级小模型自动
红灯预算 100%暂停所有请求人工审批

实现思路：维护一个累计花费计数器，每次请求前估算本次成本并叠加到累计值，再除以月度预算得到使用率。根据使用率返回 allow（放行）、throttle（限流）或 downgrade（降级）。到达红灯时直接抛出异常，阻断请求链路。这个检查点放在网关层或中间件层，所有请求必经此判断，无需业务代码感知。

九、生产案例

案例 1：Agent 产品上线后成本指数爆炸

团队背景：2025 Q3 月度 LLM 支出 ¥5,600，Q4 推出 Agent 产品后飙升至 ¥29,400，2026 Q1 继续涨到 ¥84,000。最贵模型 Qwen-Max 每百万输出 Token ¥40，同一任务用 DeepSeek-Chat 只需 ¥1——40 倍单价差异。他们根本不知道哪些请求用了哪种模型。

治理：接入 Token 计量中间件 → 发现 80% 成本来自 Agent 多步推理 → 实施分层路由 + 中间状态压缩 → 月度成本降至 ¥32,000。

案例 2：营销文案平台毛利打回来

背景：某营销 SaaS 月调用量 900 万次，统一使用高价模型，每次注入完整品牌手册 + 6 轮历史。

改造：任务拆成"标题/卖点/长文案"三级路由 → 品牌手册前缀缓存 → 历史只保留最近一次反馈 → 批量生成切到 Batch API → 失败重试从 3 次降为 1 次。

效果：平均单请求成本从 ¥0.042 降到 ¥0.016，毛利率提升 19 个点，文案采纳率仅降 1.8 个点。

案例 3：GPT-4o vs GPT-4o-mini 的 16 倍差距

日活 1000 人，每人每天 10 次对话（输入 2000 tokens + 输出 500 tokens）：
GPT-4o：日成本 $100 → 月支出 ~$3,000
GPT-4o-mini：日成本 $6 → 月支出 ~$180
差距 16 倍！而对大多数日常对话，4o-mini 的效果完全够用。

案例 4：Semantic Cache 降本 73%

背景：B2B 客服平台，月处理 120 万次查询，GPT-4 月账单 $45,000，平均延迟 6.2 秒。

改造：双层缓存——Semantic Cache（Redis + Embedding 相似度 > 0.95）+ Context Cache（缓存重复的 System Prompt + 文档）+ 模型路由（简单问题用 GPT-3.5）。

效果：月账单降至 $12,000（-73%），平均延迟降至 1.8 秒（-71%），缓存命中率 52%。

缓存版本隔离与失效治理见《缓存策略》（ST06）。

  • 先计量：接入 Token 计量中间件，看清成本分布
  • 先治理大头：缓存 → 路由 → 压缩，按 ROI 排序
  • 为工具结果做摘要和字段裁剪
  • 监控"平均输入 Token 趋势"，防止 Context Inflation
  • 设置预算熔断，防止 Agent 死循环
  • 用单位业务毛利评估优化效果
  • 所有请求都走最强模型，图省事
  • 只看平均成本，不看最贵 1% 的异常请求
  • RAG 结果整段注入，不做裁剪去重
  • 忽略 Reasoning Tokens 的隐藏成本
  • 为了省钱过度压缩，导致核心指标崩掉
  • Agent 不设最大调用次数限制

Q&A（6 题）

为什么说 Token 优化本质上是经营问题，不只是工程问题？

因为它直接决定单位经济模型。工程上省了 30%，如果核心转化掉了 10%，生意可能更差；反过来，只要高价模型明显提升付费转化，多花一点也是合理的。商业化优化看的不是绝对最低成本，而是成本和收入之间的最优平衡。

五层防御体系应该按什么顺序实施？

推荐顺序：计量（1 天接入）→ 压缩（1 周见效）→ 缓存（1 周部署）→ 路由（2 周调优）→ 熔断（1 天配置）。前两层零风险或低风险，后两层需要更多观测和调优。

最容易被忽略的 Token 成本黑洞是什么？

五个隐藏成本：(1) Reasoning Tokens——推理模型的思维链也计费，可能膨胀 20 倍；(2) Context Inflation——Prompt 从 800→18,000 tokens 无感知膨胀；(3) 工具返回原始数据——SQL 查询返回 100 行未裁剪；(4) 结构化失败重试——整段重跑；(5) Agent 多步推理——每步都携带完整上下文。

语义缓存会不会导致"答非所问"？

会，如果相似度阈值设得太低。建议：(1) 语义相似度阈值分场景设置——0.92-0.95 起步、金融医疗 0.95+，分场景结论见《缓存策略》（ST06）；(2) 缓存答案附带"来源问题"，命中时做二次校验；(3) 对时效性强的内容设置 TTL（如 24 小时）；(4) 缓存命中率监控，发现质量下降立即关闭。

Agent 成本为什么比单轮对话贵 25~50 倍？

三个原因：(1) 多步推理——10 步任务意味着 System Prompt 被发送 10 次；(2) 工具调用——每次调用注入完整工具 Schema + 返回的原始数据；(3) 中间状态——每步都携带前几轮的完整推理链。治理方案：子 Agent 隔离 + 工具结果裁剪 + 中间状态压缩。

对话历史压缩时，最重要的原则是什么？

不是机械保留最近 N 轮，而是保留"仍然影响后续决策的信息"。用户身份、目标、关键约束、上轮纠正意见应优先保留，闲聊和已完成的中间推理可以压缩或删除。压缩的本质是保留决策所需状态，而不是保留全部文字。
