E01 · Prompt Engineering

商业化 Prompt 工程不是"写一句咒语"，而是把角色、规则、数据、工具和输出协议固化成可评测、可回滚、可协作的产品资产

一、商业化项目里 Prompt 工程到底解决什么问题

Prompt 在商业系统里承担的是"最上层业务编排协议"角色：它把模型能力翻译成企业可以交付、可审计、可运营的行为。
项目类型核心目标Prompt 重点上线指标
智能客服降人工、提满意度意图识别、拒答边界、引用知识库首问解决率、转人工率、误答率
营销文案提升转化品牌语气、禁用词、渠道适配CTR、转化率、审核通过率
企业 Copilot提升员工效率任务模板、工具调用顺序、权限边界任务完成率、节省时长、错误工单率
审核质检稳定输出标签分类定义、判定阈值、解释字段Precision、Recall、复核通过率

很多团队把 Prompt 当成"模型调参"。但真正影响交付成败的，是 Prompt 是否能把业务规则显式化。比如客服场景里"无法确认时必须拒答并给出人工入口"这类约束，写在 PRD 没用，必须下沉到 Prompt、输出 Schema 和后置校验层中。

二、Prompt 结构化设计：从零搭建一条工业级 Prompt

一条好的生产 Prompt 不是写出来的，而是按层级组装出来的——身份、任务、规则、示例、协议五层缺一不可。
┌─────────────────────────────────────────────────────────┐ │ System Prompt 整体结构 │ ├──────────────┬──────────────────────────────────────────┤ │ ① 身份层 │ role: "你是XX公司售后客服助手" │ │ (Identity) │ tone: 专业、温和、不承诺赔偿 │ ├──────────────┼──────────────────────────────────────────┤ │ ② 任务层 │ task: 根据用户订单信息回答售后问题 │ │ (Task) │ completion: 回答完毕需输出 result_status │ ├──────────────┼──────────────────────────────────────────┤ │ ③ 规则层 │ - 无法确认的信息不得臆测 │ │ (Rules) │ - 涉及退款金额必须引用系统数据 │ │ │ - 超出权限时引导转人工 │ ├──────────────┼──────────────────────────────────────────┤ │ ④ 示例层 │ [Few-shot examples: 3~8 条边界样例] │ │ (Examples) │ 包含: 标准回答 / 拒答 / 格式模板 │ ├──────────────┼──────────────────────────────────────────┤ │ ⑤ 协议层 │ output_schema: { answer, status, refs } │ │ (Protocol) │ tool_constraints: 仅允许查询订单API │ └──────────────┴──────────────────────────────────────────┘

在实际项目中，System Prompt 通常占据 60%~80% 的总 Token 预算。如果身份层和规则层频繁变动，说明业务规则还没有沉淀到位，需要先回去梳理 SOP，而不是急着改 Prompt。

🔑 生产要点：每一层都应有明确的"负责人"和"变更频率"。身份层可能一个季度不动，规则层可能每周迭代，示例层随坏例积累持续更新。分层之后才能做到"谁改动、谁负责、何时回滚"。

各层 Token 预算分配建议

层级Token 占比变更频率负责人
身份层5%~10%低（季度级）产品 / 品牌
任务层10%~15%中（月度级）产品 / 算法
规则层15%~25%高（周级）风控 / 业务
示例层20%~35%持续（随坏例）算法 / 标注
协议层5%~10%低（版本级）工程

💡 注：另有一套五层划分——运行时五层架构（人设 / 上下文 / 指令 / 边界 / 输出），详见 E02 · 五层架构驯服大模型，两套五层视角不同，不要混淆。

三、生产环境要把 Prompt 拆成五层资产

商业化 Prompt 不该是一整段长字符串，而应该分层管理，这样才能做到多人协作、灰度发布和问题定位。
层级内容负责角色为什么重要
身份层角色、人设、语气产品、运营统一品牌表达，防止每个场景各说各话
任务层输入输出目标、完成定义产品、算法保证模型知道"什么算完成"
规则层禁答项、引用要求、合规限制风控、法务、业务把风险从"靠经验"变成"可执行规则"
示例层Few-shot、反例、边界案例算法、标注减少格式漂移和风格不稳定
协议层JSON Schema、字段解释、tool 约束工程让下游系统能消费输出，不靠人工猜格式
五层资产的组装顺序与变更节奏（左侧是发版时的拼装，右侧是各层各自的迭代周期）： 运行时组装 独立迭代 ────────── ────────── ┌────────────────────────┐ │ ① 身份层 │ 角色 / 语气 / 品牌口径 月级，产品与运营改 │ 几乎不随请求变化 │ ← 命中前缀缓存的主体 ├────────────────────────┤ │ ② 任务层 │ 目标 / 完成定义 周级，产品与算法改 │ 按场景选择一个模板 │ ├────────────────────────┤ │ ③ 规则层 │ 禁答 / 引用 / 合规 天级，风控法务改 │ 可叠加多条，按场景启用 │ ← 变更最频繁，必须能热更 ├────────────────────────┤ │ ④ 示例层 │ few-shot 3~8 条 双周评审后替换 │ 按场景动态挑选 │ ← 进一退一，总长度受控 ├────────────────────────┤ │ ⑤ 协议层 │ JSON Schema / tool 约束 跟随下游接口变 │ 放在最后，紧邻输出 │ ← 位置靠后，减少被忽略 └───────────┬────────────┘ │ ▼ 用户输入（包在隔离标签内，不与上述五层混排） │ ▼ 模型输出 ──→ 协议层校验 ──→ 下游系统 三条组装约束： · ①② 必须字节稳定，任何微调都会让前缀缓存整体失效 · ③ 的每一条规则要能单独开关，否则无法按场景灰度 · ⑤ 放末尾利用位置优势；放开头容易在长上下文里被稀释

Few-shot 在商业化场景里最有价值的地方不是"教模型知识"，而是教它学会你们公司的判断口径。例如同样是"退款咨询"，电商平台和 SaaS 平台的处理边界完全不同，few-shot 可以把企业私有 SOP 明确注入。

Few-shot 边界样例怎么选

样例类型为什么必须放典型例子
高客诉样例一旦回答错就直接伤害用户关系超时退款、虚拟商品售后、赔付争议
高金额样例错一次损失就很大大额采购审批、VIP 补偿、金融额度解释
边界拒答样例教模型知道何时不要答证据不足、越权查询、政策未覆盖
格式易漂移样例能稳定输出协议和风格JSON 字段缺失、多标签分类、摘要模板

Few-shot 最怕"只放标准题，不放麻烦题"。商业项目真正消耗人力的，往往不是模型不会的常规题，而是边界模糊、情绪强烈、规则冲突的脏样本。把这些样本提前写进 few-shot，价值远高于再多放几个漂亮示例。

四、Few-shot 流水线：从样例采集到线上生效

Few-shot 不是写一次就完事，而是一条持续运转的数据流水线——线上坏例不断回流、清洗、标注，最终替换掉过时的旧样例。
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ 线上日志 │───▶│ 坏例筛选 │───▶│ 人工标注 │───▶│ 样例评审 │───▶│ 灰度上线 │ │ (每日) │ │ (自动) │ │ (标注队) │ │ (算法+业务)│ │ (A/B) │ └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ 收集误答/ 按场景分类 标注正确回复 替换旧样例 5%流量验证 低满意度会话 去重+优先级 标注拒答边界 补充新场景 指标达标全量

Few-shot Pipeline 的核心原则是"进一退一"：每新增一条样例，就评估是否需要淘汰一条旧样例，保持 Prompt 总长度可控。实测表明，3~8 条精选样例的效果通常优于 20 条堆砌样例，因为过多示例会引入噪声和指令冲突。

Few-shot 样例生命周期管理

阶段动作周期质量标准
采集从线上日志抽取误答和低满意度会话每日自动覆盖所有高频场景
清洗去重、脱敏、按场景归类每周同一场景不超过 2 条
标注标注团队给出标准答案和拒答判定每周标注一致性 > 90%
评审算法 + 业务联合评审，决定是否纳入双周需全票通过方可上线
退役业务规则变更时标记旧样例为过期随时过期样例 48h 内替换
📊 生产数据：某金融客服项目在 3 个月内通过 Few-shot Pipeline 累计迭代 147 条样例，最终保留 32 条活跃样例。拒答准确率从 71% 提升到 94%，Prompt 总 Token 仅增长 12%。

五、Prompt 技术对比：选对方法比堆技巧更重要

不同 Prompt 技术适用于不同场景，盲目叠加反而会增加复杂度和成本。先搞清问题类型，再选技术方案。

主流 Prompt 技术对比

技术核心思路适用场景Token 成本典型收益
Zero-shot直接给出指令，无示例简单分类、格式转换低baseline 快速验证
Few-shot提供 3~8 条精选样例边界判断、格式稳定、企业 SOP中准确率提升 10%~25%
Chain-of-Thought要求模型逐步推理数学推理、逻辑判断、多步分析高复杂任务准确率 +15%~40%
ReAct推理 + 工具调用交替需要查数据库、调 API 的场景高任务完成率 +20%~35%
Self-consistency多次采样取多数投票分类、判断等离散输出任务极高 (N 倍)稳定性 +5%~15%
Prompt Chaining把任务拆成多步串联长流程、多阶段处理中~高端到端质量 +20%~50%

按问题类型选择技术方案

问题类型推荐首选备选方案不推荐
文本分类 / 标签Few-shotZero-shot + 后校验CoT（过度推理浪费 Token）
多步推理 / 计算CoTPrompt ChainingZero-shot（准确率不足）
数据查询 + 回答ReActTool-use Prompt纯 Few-shot（无法动态查询）
长文档摘要Prompt ChainingMap-Reduce单次 Few-shot（上下文溢出）
高稳定性判断Self-consistencyFew-shot + 多数投票Zero-shot（波动过大）
💡 实战经验：在商业项目中，80% 的场景用 Few-shot 就能达到生产标准。只有当 Few-shot 触顶（准确率卡在某个瓶颈不再提升）时，才值得引入 CoT 或 ReAct。过早使用复杂技术会大幅增加 Token 成本和调试难度。
  • 先用 Zero-shot 建立 baseline，再逐步升级
  • 根据问题类型选择最匹配的技术
  • 始终监控 Token 成本与收益的比值
  • 复杂技术只在 Few-shot 触顶后才引入
  • 一上来就用 CoT + ReAct 叠满
  • 不看 Token 成本，只追求准确率
  • 所有场景都用同一种 Prompt 技术
  • 忽略 Self-consistency 的 N 倍成本

六、交付流程：从 Prompt 编写升级为 Prompt 运营

阶段动作产出
需求定义先写任务完成标准和不可接受错误验收指标、拒答规则、坏例列表
离线调试基于 50 到 200 条真实样本调 PromptPrompt v1、baseline 指标
灰度验证5% 到 10% 流量 A/B 测试成本、满意度、人工接管率对比
线上运营持续收集坏例、版本回放、周迭代Prompt changelog、回归报告

在商业落地项目里，Prompt 版本管理至少要记录 4 件事：版本号、修改意图、影响指标、回滚条件。否则几周之后没人说得清"为什么这周转人工率突然升高"，因为你改过 Prompt、知识库、模型版本和工具排序，问题根因会混在一起。

常见变更短期收益长期风险
增加更多规则降低部分错误Prompt 膨胀，成本上升，指令冲突
增加更多示例输出更稳示例过旧，业务规则变化后误导模型
强调拒答幻觉下降拒答过多，产品可用性下降

版本回滚机制要提前设计

  • 版本标识：每次发布绑定 Prompt 版本号、模型版本和知识库版本，避免线上问题无法定位到具体组合
  • 灰度策略：先放 5% 到 10% 流量、按用户桶稳定分配，误答率、转人工率、成本异常波动即止
  • 快速回退：配置中心切换到上一个稳定版本，应对高风险 Bad Case 集中爆发
  • 变更记录：记录修改意图、预期指标、负责人，避免出问题后无法追责和复盘

快照级回滚与灰度分桶详见 ST10 · Prompt/Tool/Memory/Workflow 版本管理。

很多团队把回滚理解成"Git revert 一下"。但商业系统里真正要回滚的是一整套运行时组合：Prompt、知识库版本、Schema、工具开关和路由策略。如果只回 Prompt，不回知识版本，问题经常还在。

七、生产案例集锦：数字说话

Prompt 工程的价值不能只靠"感觉变好了"来衡量——必须有上线前后的硬指标对比，才能证明 ROI。

案例 A：电商客服 Bot 改造

背景：某电商售后 Bot 日均 12 万次会话，早期 Prompt 只有"你是客服助手，请礼貌回答用户问题"。
问题：误导性回复率达 9.4%，客服投诉上升 18%。
改造：拆成角色层、订单规则层、拒答层和输出协议层，加入 32 条高频边界样例。
效果：误导性回复率 9.4% → 2.1%，首问解决率 +11pp，单次 Token 仅增加 8%。

案例 B：营销文案生成平台

背景：某营销 SaaS 为 2000+ 品牌客户提供文案生成，日产出 5 万篇。
问题：品牌语气一致性评分仅 62 分（满分 100），审核退回率 23%。
改造：引入品牌 Tone-of-Voice 身份层 + 禁用词规则层 + 渠道适配模板，每个品牌独立 Few-shot。
效果：语气一致性 62 → 89 分，审核退回率 23% → 7%，客户 NPS 提升 14 分。

案例 C：企业内部 Copilot

背景：某 500 人技术团队的内部 Copilot，覆盖工单处理、文档检索和代码审查。
问题：任务完成率仅 58%，大量请求因工具调用顺序错误而失败。
改造：引入 ReAct 模式，明确工具调用协议和权限边界，加入 16 条任务模板。
效果：任务完成率 58% → 81%，平均处理时长从 12 分钟降到 4.5 分钟，月节省约 320 工时。
  • 先定义业务成功标准，再写 Prompt
  • 把品牌语气、拒答规则、输出协议拆层管理
  • 用真实坏例而不是理想样例做 few-shot
  • 每次变更都做小流量灰度和回归测试
  • 把 Prompt 当可运营资产，而不是代码注释
  • 把所有需求都堆进一个超长 system prompt
  • 只看主观体验，不看误答率和转人工率
  • 没有版本号，线上直接热改 Prompt
  • 用内部造的数据调试，忽略真实脏输入
  • 遇到问题只继续加规则，不做结构重构

Q&A（8 题）

商业项目里，Prompt 工程和产品规则有什么关系？

产品规则定义"系统应该怎么做"，Prompt 工程负责把这些规则翻译成模型可执行的协议。没有 Prompt 的规则只是文档；没有产品规则的 Prompt 只是临场发挥。商业系统里，两者必须一一映射，并接受同一套验收指标约束。

Prompt 应该越详细越好吗？

不是。Prompt 太短会缺规则，太长会增加成本、制造指令冲突、拉低缓存命中率。更好的方法是分层管理，把稳定规则常驻在前缀，把易变策略通过检索、配置或工具动态注入，这样比一味堆长文本更适合商业化运营。

Few-shot 在商业化场景里最该放什么样本？

优先放高价值边界样本，而不是"最好回答"的标准题。比如高客诉、高风险、高金额、高误判的场景最值得进入 few-shot。这样 few-shot 的价值是降低线上损失，而不是单纯展示一个漂亮格式。

Prompt 改动为什么一定要做灰度？

因为 Prompt 改动会同时影响准确率、拒答率、成本、品牌语气和人工接管量。离线看似正确的变更，线上可能因为用户输入更脏、上下文更长、知识库更复杂而失效。灰度可以把损失控制在小范围内，并帮你知道收益是否真的成立。

Chain-of-Thought 和 Few-shot 可以同时使用吗？

可以，但要看场景。CoT 适合需要多步推理的任务（如复杂计算、逻辑判断），Few-shot 适合需要稳定格式和边界判断的任务。在需要"既推理准确、又输出规范"的场景中，可以先用 Few-shot 固定输出格式，再在回答内部嵌入 CoT 推理链。注意 CoT 会显著增加 Token 消耗（通常 2~5 倍），只有在准确率确实触顶时才值得引入。

怎么判断一条 Prompt 是否"过度工程化"？

三个信号：第一，Prompt 超过 2000 Token 但准确率没有明显高于 1000 Token 的版本；第二，规则之间存在矛盾或重叠，模型经常"不知道该听哪条"；第三，每次修改都需要重新理解整个 Prompt 才能下手。好的 Prompt 应该像好的代码一样——模块化、可读、可局部修改。

Prompt 工程的成本应该怎么核算？

至少考虑三层成本：Token 调用成本（System Prompt 每次会话都会发送，按日均会话数 × 平均 Token × 单价计算）；人力维护成本（标注团队、算法工程师的迭代时间）；以及机会成本（因为 Prompt 不够好而导致的转人工、客诉和流失）。多数团队只算第一层，实际后两层往往占 60% 以上。

模型升级后，Prompt 需要重新调整吗？

几乎一定需要。不同模型对同一条指令的理解和遵循程度差异很大。升级后至少要跑一遍回归测试集，重点关注三类退化：格式漂移（输出不再符合 Schema）、规则失效（之前遵守的约束被忽略）、以及过度自信（新模型更少拒答但误答增多）。建议把"模型升级"纳入 Prompt 变更流程，和规则修改走同样的灰度和回滚机制。
