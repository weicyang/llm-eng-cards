ST07 · 意图识别三层漏斗架构

Intent Recognition — 从"关键词匹配"到"语义推理"，让 Agent 理解用户说半句话的真实意图

意图识别不是"分类任务"，而是"语义推理任务"。用户说的从来不是完整句子——省略主语、隐含意图、省略参数是常态。传统 NLU 的 BERT 分类器只能处理"完整句子"，而大模型范式可以处理"不完整输入"，通过上下文推理补全用户真正想做什么。

一、不完整表达：三层挑战

用户在对话系统中的输入很少是完整句子。ChatBox 团队的实战分析揭示了三层递进难度：

层级类型示例难度传统 NLU大模型
L1语法不完整"那个…天气"低✅ 可处理✅
L2隐含语义依赖"帮我看看那个项目"中⚠️ 部分✅
L3多义性消解"取消"（取消订单？取消订阅？取消操作？）高❌ 困难✅

三种典型不完整表达模式

省略型：用户省略了明确动词。"明天" → 查询天气。"订单 123" → 查询订单状态。"红色那个" → 切换主题颜色。传统 NLU 需要关键词触发，省略动词后无法识别。

指代型：用户用"它""那个""上一个"指代前文对象。"它怎么样了" → 查询某个任务的状态。如果缺少对话历史，NLU 完全无法解析指代关系。

隐含型：用户的真实意图需要推理。"好贵" → 可能是想比价、想退款、或者只是吐槽。"这个功能不错" → 可能是想了解怎么用、或者要求添加到收藏夹。

核心矛盾：传统 NLU 的 BERT 分类器是"独立分类"——每句话只看当前输入，不看历史。而真实对话中 60%+ 的输入依赖上下文才能正确理解。这是范式级差异，不是调参能解决的。

二、传统 NLU vs 大模型范式

两条路线的分水岭不是"谁更准"，而是"意图集合会不会变"。意图固定、样本充足时，判别式分类器在延迟和单位成本上有两个数量级的优势；一旦意图需要频繁增删、或者输入依赖上下文才能解析，大模型的零样本泛化就把重训数据的成本直接省掉了。

维度传统 NLU（BERT 分类器）大模型范式（GPT/Claude）
工作方式分类任务：输入 → 固定标签推理任务：输入 + 上下文 → 语义理解
上下文利用无（每句独立分类）有（完整对话历史 + 用户画像）
不完整输入需要完整句子 + 关键词触发可处理省略、指代、隐含
新意图扩展重新标注数据 + 重训模型修改 Prompt 即可
多意图困难（需要级联分类器）自然处理（CoT 推理链）
部署成本低（小模型推理快）高（大模型调用贵）
延迟~10ms~500ms-2s
可控性高（确定性输出）中（需要 Prompt Engineering）

什么时候该用传统 NLU？

不是所有场景都需要大模型。高流量、意图固定的场景（如电商客服 FAQ），BERT 分类器性价比更高：

  • 日均 100 万+ 请求，意图数量 <50 个 → BERT 分类器（成本低 100 倍）
  • 意图复杂多变，需要上下文推理 → 大模型
  • 混合方案：BERT 处理高频确定意图 → 大模型处理长尾模糊意图

三、四组件协同架构

现代意图识别不是单一模块，而是四个组件协同工作：

用户输入: "明天那个航班怎么样了" │ ├──→ ① 意图识别模块 │ 输入: 用户文本 + 对话历史 │ 输出: {intent: "query_flight_status", confidence: 0.92} │ ├──→ ② 语义补全模块 │ 输入: 用户文本 + 对话历史 + 用户画像 │ 输出: 完整化 "查询明天从上海飞往北京的航班状态" │ ├──→ ③ 上下文推理模块 │ 输入: 对话历史 + 用户偏好 + 时间信息 │ 输出: 推断 "那个航班" = 昨天讨论过的 CA1234 │ └──→ ④ 状态跟踪模块 输入: 当前对话状态 + 新意图 输出: 更新对话状态 → 触发后续动作

组件间的依赖关系

组件输入来源输出去向关键技术
意图识别原始文本 + 历史意图标签 + 置信度大模型 Prompt / BERT
语义补全文本 + 历史 + 画像完整化文本大模型 CoT 推理
上下文推理历史 + 偏好 + 时间指代解析 + 隐式推断大模型 + 向量检索
状态跟踪对话状态 + 新意图更新状态 + 触发动作状态机 / 有限自动机
为什么需要语义补全？"明天"这两个字在语义上是空的，但经过补全后变成"查询明天上海的天气"。这一步是传统 NLU 完全做不到的——它需要理解"用户在问天气"的上下文，同时知道"用户在上海"的画像信息。

四、三层漏斗工程实现

三层漏斗的设计哲学：能用规则解决的不用模型，能用小模型解决的不用大模型。每一层过滤掉确定性问题，只把模糊问题交给下一层。

第一层：规则引擎（正则 + 关键词）

规则类型匹配模式示例命中率延迟
精确关键词完全匹配"退款" → refund_intent~30%<1ms
正则模式模式匹配"怎么.*退" → refund_intent~15%<1ms
否定规则排除特定词含"不是退款" → 不走 refund~5%<1ms

第一层覆盖 ~50% 请求，延迟 <1ms，零成本。规则需要持续维护——从错误日志中提取漏匹配的 case，补充正则。

第二层：轻量分类模型（BERT / FastText）

第一层未命中的请求进入第二层。使用轻量模型（BERT-base / FastText）做意图分类：

  • 输入：当前用户文本（不含历史上下文）
  • 输出：意图标签 + 置信度
  • 覆盖：~35% 请求
  • 延迟：~10-50ms
  • 训练数据：从生产日志中挖掘，人工标注 500-1000 条即可启动

第三层：大模型语义推理（GPT/Claude）

前两层未命中或置信度低的请求进入第三层。大模型处理复杂、模糊、多义的输入：

  • 输入：当前文本 + 对话历史 + 用户画像
  • 输出：意图标签 + 推理链 + 置信度
  • 覆盖：~15% 请求（但往往是最高价值的请求）
  • 延迟：~500ms-2s
  • 优势：可处理不完整输入、多意图、隐含意图
请求流转（日均 100 万请求）: 用户输入 → ① 规则引擎 │ 命中 50%（50 万）→ 直接路由 │ 未命中 50% ↓ ② 轻量分类器 │ 高置信度 70%（35 万）→ 路由 │ 低置信度 30% ↓ ③ 大模型推理 │ 处理 15 万请求 ↓ 路由到对应 Agent

五、置信度计算与降级策略

置信度真正的用途不是"打分给人看"，而是决定这次要不要跟用户多说一句话。所以它必须是可校准的——0.7 应该真的对应大约七成正确率，否则所有阈值都是拍脑袋。把模型原始分数、上下文一致性和该用户的历史行为加权，就是在用三个相互独立的证据源，把单一分数的过度自信压下来。

置信度模型

ChatBox 团队提出的多维置信度计算：

confidence = α × semantic_score + β × context_score + γ × consistency_score 其中: α = 0.5 (语义匹配权重) β = 0.3 (上下文一致性权重) γ = 0.2 (历史行为一致性权重) 示例: "明天那个航班" semantic_score = 0.85 (文本匹配 query_flight 意图) context_score = 0.92 (对话历史中昨天讨论过航班) consistency_score = 0.88 (该用户过去 10 次类似表达都是查航班) → confidence = 0.5×0.85 + 0.3×0.92 + 0.2×0.88 = 0.877

降级策略

置信度区间处理策略用户体验
> 0.85直接执行，无需确认无缝体验
0.65 - 0.85执行 + 轻度确认"你是想查航班状态吗？"
0.40 - 0.65提供选项让用户选择"你想做 A 还是 B？"
< 0.40请求用户澄清"能具体说说你想做什么吗？"

Topic Drift 检测

对话过程中，用户话题可能漂移。需要实时检测并决定是否开启新对话上下文：

检测方法原理适用场景
语义相似度当前输入 vs 历史平均 embedding 的余弦距离通用
意图切换频率最近 N 轮中意图标签变化次数多任务场景
共指消解检测"它""那个"指代是否仍指向同一对象长对话

当漂移超过阈值时，系统自动开启新的对话上下文，但保留旧上下文作为参考（而不是丢弃）。

六、Fallback 三级熔断

Fallback 不是"失败了就告诉用户"，而是分级降级——先尝试自主恢复，恢复不了再请求用户，最后才人工接管。

Fallback 三级熔断流程: Level 1: 自主重试（最多 2 次） ├── 换一种 Prompt 策略重新推理 ├── 扩大上下文窗口（加载更多历史） └── 成功 → 继续执行 Level 2: 请求用户澄清 ├── 提供 2-3 个候选意图供选择 ├── "你是想 A 还是 B？" └── 用户选择 → 继续执行 Level 3: 人工接管 ├── 转接人工客服 / 标记待处理 ├── 记录失败日志用于模型改进 └── 通知运维团队排查

生产配置建议

参数推荐值说明
Level 1 重试次数2超过 2 次说明不是 Prompt 问题
Level 2 候选数量2-3太多选项反而让用户困惑
Level 3 触发率告警>5%人工接管率超过 5% 需要排查根因
总体 Fallback 率<15%超过 15% 说明意图识别模型需要重训

七、多意图分层处理

用户一句话可能包含多个意图："帮我查下航班状态，顺便看看明天天气"

多意图处理流程: "帮我查下航班状态，顺便看看明天天气" │ ├──→ 意图分离器（大模型一次输出多个意图） │ → intent_1: query_flight_status │ → intent_2: query_weather │ ├──→ 优先级仲裁器 │ → 判断是否有依赖关系（先查航班再查天气 = 无依赖） │ → 无依赖 → 并行执行 │ → 有依赖 → 串行执行 │ └──→ 分别路由到对应 Agent

意图冲突解决

冲突类型示例解决策略
互斥意图"退款但也别退"请求澄清
依赖意图"查航班然后帮我改签"串行执行（先查后改）
并行意图"查航班 + 查天气"并行执行
优先级冲突"取消订单并下单新的"按用户历史行为推断优先级

九、生产案例与数据

电商客服系统：三层漏斗落地

指标优化前优化后改善
意图识别准确率72%94%+22pp
端到端延迟 P501.2s85ms-93%
Fallback 率28%8%-71%
人工接管率15%3%-80%
大模型调用占比100%12%-88%（成本大幅降低）

关键设计决策

  • 规则引擎持续迭代：每周从 Fallback 日志中提取 50-100 条漏匹配 case，补充正则
  • 轻量模型定期重训：每月用新增标注数据重训 BERT，保持准确率 >85%
  • 大模型 Prompt 版本管理：Prompt 改动走 A/B 测试，灰度发布
  • 不完整表达兜底：对省略型输入，自动触发语义补全模块

落地时的取舍

  • 先上第三层大模型跑通全链路，用真实流量攒够标注样本，再往前补第二层分类器和第一层规则。反过来先写规则，你会照着想象中的用户表达写，命中率通常只有实际的一半。
  • 规则层只放高精确率的模式，宁可少命中也不要误命中——第一层错了后面两层没有机会纠正。
  • 每一层都单独记录"命中了没有"和"命中得对不对"两个指标，混在一起看会掩盖某一层的退化。
  • 把澄清话术做成候选选项而不是开放式追问，用户点选的结果天然就是高质量标注数据。
  • 意图的新增和下线走版本化配置，让路由表和模型、规则的版本能对齐回滚，避免出现配置漂移——规则更新了但路由表没跟上，请求会静默落到兜底分支。
  • 不要为了提高规则层命中率而放宽正则，把 50% 命中做到 70% 的代价往往是误路由翻几倍。
  • 不要在置信度没做校准前就按固定阈值分档，不同意图的分数分布差异很大，一刀切会让冷门意图长期落在澄清区。
  • 不要把 Fallback 当成失败率指标去压——压到很低通常意味着系统在低置信度时也硬猜，错误被藏进了业务侧。
  • 不要让第二层分类器直接吃对话历史，它没有这个能力，塞进去只会让分布偏移、准确率反降。
  • 不要在同一次请求里既做意图识别又做参数抽取还做业务判断，三件事的失败模式不同，混在一个 Prompt 里无法归因。

Q&A

为什么不让大模型处理所有请求？
三个原因：(1) 成本 — 日均 100 万请求全部走大模型，API 费用约 $5,000/天；三层漏斗只让 12% 走大模型，费用降至 $600/天。(2) 延迟 — 大模型响应 500ms-2s，规则引擎 <1ms，用户体感差距巨大。(3) 稳定性 — 大模型有概率输出幻觉，规则引擎是确定性的。原则：能用规则解决的不用模型。
传统 NLU 的 BERT 分类器为什么处理不了"不完整输入"？
BERT 分类器是"独立分类"——每句话只看当前输入，不看历史。"明天"这两个字在 BERT 看来就是两个字，无法判断用户是想查天气、查航班还是查日程。而大模型可以看到对话历史（"昨天聊过天气"）+ 用户画像（"用户在上海"），推理出"明天"大概率是查天气。这是范式级差异，不是加几条规则能解决的。
Fallback 三级熔断为什么不是"直接告诉用户听不懂"？
因为大部分"听不懂"是可以自主恢复的。Level 1（自主重试）：换一种 Prompt 策略，比如扩大上下文窗口、加载更多信息，很多模糊输入就能正确理解。Level 2（请求澄清）：给用户提供 2-3 个选项，比让用户重新描述高效得多。只有真正无法处理的才走 Level 3（人工接管）。生产数据：Level 1 解决了 60% 的 Fallback，Level 2 解决了 30%，只有 10% 需要人工。
多意图处理中，怎么判断两个意图是否有依赖关系？
通过大模型的推理能力判断。Prompt 中明确要求模型输出意图间的依赖关系："查航班然后改签" → 依赖（必须先查才能改）；"查航班 + 查天气" → 无依赖（可并行）。工程实现上，用意图分离器一次输出多个意图 + 依赖图，再用优先级仲裁器决定串行还是并行执行。
Topic Drift 检测误判怎么办？
误判有两种：(1) 没检测到漂移 → 新话题混入旧上下文，导致回答错误；(2) 误检测漂移 → 不必要地开启新上下文，丢失有用历史。解决：(1) 调整阈值，宁可多检测不要漏检测（漂移后的错误答案比丢失历史更严重）；(2) 保留旧上下文作为参考而非丢弃（开新上下文时把旧上下文摘要保留）；(3) 监控误判率，超过 10% 时调整检测算法。
意图识别的"三层漏斗"和"三层缓存"有什么共同设计哲学？
核心哲学相同：分层过滤，逐级升级。三层缓存（Prompt Cache / Semantic Cache / KV Cache）是"能用缓存解决的不调模型"；三层漏斗（规则 / 轻量模型 / 大模型）是"能用规则解决的不调模型"。两者都追求：(1) 最快路径解决大部分问题；(2) 只在必要时使用昂贵资源；(3) 每层都有监控指标。本质是"空间换时间"和"确定性换概率"在不同层面的应用。
什么时候需要重训意图识别模型？
四个信号：(1) Overall F1 < 0.88 — 系统性性能下降；(2) Fallback 率 > 15% — 说明现有模型覆盖不了新出现的意图模式；(3) 新意图类别出现 — 业务新增功能导致用户表达方式变化；(4) 轻量模型准确率 < 85% — 需要补充标注数据重训。生产实践：每月固定重训一次（用新增标注数据），紧急情况（如新业务上线后 Fallback 飙升）随时触发。
