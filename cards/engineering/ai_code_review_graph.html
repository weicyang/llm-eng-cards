ST19 · Graph Engineering 代码审查工程化

Loop 时代终结 / 三层节点架构 / 确定性验证器 / 渐进式引入策略

代码审查的工程化，本质是把"一个模型从头审到尾"的黑盒，拆成"确定性门禁先行、语义审查居中、人工确认兜底"的透明节点图——能用规则免费判定的，绝不花 Token 让模型去猜。

一、从人工到 Graph 智能体

人工审查的效率困境

代码审查是质量防线，也是交付链路上最经典的瓶颈。LinearB 基于 42 个国家、4800 个工程团队、810 万个 Pull Request 的 2026 年基准数据显示：行业中位审查耗时约 15 小时，从开 PR 到合并的中位周期长达 83 小时——一个 PR 生命周期的大部分时间都在"排队"。而头部团队的数字完全是另一个世界：接手（pickup）1 小时以内、审查 3 小时以内、全流程 25 小时以内。差距不在工程师水平，而在队列管理与审查分层。

生产数据：审查瓶颈的真实成本。LinearB 2026 基准（810 万 PR）中位审查耗时 15 小时、中位周期 83 小时；SmartBear 研究指出单次有效审查的认知上限约为 60 分钟 / 200~400 行代码，超过后审查者开始"走马观花"。一家 50 人团队若 PR 平均等待 36 小时，折算的纯等待成本约为每年 19.5 万 ~ 42 万美元。增长型团队的典型现象是：资深工程师 30%~40% 的时间耗在审查上，团队从 5 人扩到 20 人后，PR 中位周期从 4 小时涨到 52 小时——涨的几乎全是等待时间。

人工审查还有一个物理规律：审查耗时与 PR 规模近似二次方关系。一个 600 行的 PR 并不是比 100 行的多花 6 倍时间，而是大约 12~15 倍——审查者在 60 分钟左右进入疲劳期，之后的意见质量急剧下降。这意味着"靠人更努力"无法解决审查瓶颈，只能靠重构审查流程本身。

单 Agent Loop 的三大缺陷

第一代 AI 审查方案普遍是单 Agent Loop——把 diff 丢给一个大模型，让它在"读代码 → 回忆规则 → 提意见 → 自我检查"的循环里一口气干完。这在 demo 里可行，在生产里会集中暴露三个结构性缺陷：

  • 上下文膨胀：为了判断一个函数的改动是否安全，Loop Agent 倾向于把整个仓库的相关文件都读进上下文。Token 消耗随仓库规模线性甚至超线性上涨，注意力却被稀释，改动越大越容易"抄近路"——只挑几个文件看，其余整体漏掉。
  • 规则不可复用：团队规范、安全红线、架构约束全部硬编码在 Prompt 里。同一份规则无法被独立测试、版本化、增量维护；措辞稍微改动，审查结果就剧烈波动，今天能查出的问题明天换个说法就漏了。
  • 结果不可预测：什么时候算"审完了"、意见行号对不对、同一 PR 审两次结论是否一致，全部取决于模型当次采样。典型症状是位置漂移——报告说第 42 行有空指针风险，跳过去却是一行空注释。这种不可复现性让它根本无法进 CI 门禁。

Graph 工程化：把审查变成显式 DAG

Graph Engineering（图工程）指的是把 AI 应用显式设计为节点、依赖、状态转移、验证门禁、恢复路径与控制边界的可执行图，而不是一个自主循环的黑盒。落到代码审查上：diff 拉取、格式检查、lint、类型检查、测试门禁、LLM 语义审查、去重聚合、人工确认，每个环节都是独立节点，节点之间用显式的边连接——验证失败的边走"打回并附精确定位"，全部通过的边才进入下一层。模型只在真正需要语义判断的节点里被调用。

单 Agent Loop（黑盒） Graph 审查 DAG（透明流水线） ────────────────────── ────────────────────────────── ┌──────────────────────┐ ┌──────┐ ┌──────────┐ │ 一个 LLM 包办： │ │ diff │───▶│ lint/类型 │──✗──▶ 打回 │ 读 diff → 回忆规则 │ │ 拉取 │ │ /测试门禁 │ (附精确定位) │ → 审查 → 自我检查 │ └──────┘ └────┬─────┘ │ │ (0 Token) │✓ │ 上下文越滚越大 │ ▼ │ 规则埋在 Prompt 里 │ ┌──────────────────────────┐ │ 结果不可复现 │ │ LLM 语义审查（并行节点） │ └──────────────────────┘ │ 架构风险 ∥ 安全 ∥ 性能 ∥ 规范│ └────────────┬─────────────┘ ▼ ┌──────┐ ┌──────────┐ │ 聚合 │───▶│ 人工确认 │──▶ 合并 │ 去重 │ │ (仅高风险) │ └──────┘ └──────────┘

Loop 是"让一个聪明人凭感觉审完"，Graph 是"把审查拆成流水线工位"：前者上限取决于模型当次发挥，下限不可控；后者把下限用确定性节点焊死，模型的发挥只影响上限。

二、三层节点架构

一个可进生产的审查 Graph，通常收敛为三层节点：确定性验证器挡在最前面消化一切机器可判定的问题，语义审查节点居中处理需要理解力的风险，人工确认节点在最后兜住高风险变更。三层不是并列选项，而是串联漏斗——每一层都只为下一层留下"自己解决不了的东西"。

PR 提交 │ ▼ ┌──────────────────────────────────────────────────────────┐ │ 第一层 · 确定性验证器（零 Token，毫秒~秒级） │ │ 格式检查 ─▶ lint ─▶ 类型检查 ─▶ 测试门禁 ─▶ 结构图增量更新 │ └──────────────────────────────────────────────────────────┘ │ 全部通过 │ 任一失败 ▼ ▼ ┌───────────────────────────────────┐ 直接打回： │ 第二层 · 语义审查（LLM 节点，并行） │ 附文件/行号/规则 ID， │ 架构风险 ∥ 安全漏洞 ∥ 性能隐患 ∥ 规范 │ 开发者本地即可修复 │ └──▶ 聚合去重 + 误报过滤 │ └───────────────────────────────────┘ │ 低风险：意见留档，自动放行 │ 高风险：升级 ▼ ▼ 合并 ┌─────────────────────────┐ │ 第三层 · 人工确认 │ │ 架构变更 / 高危操作 / │ │ 敏感数据访问 / 安全高危项 │ └─────────────────────────┘ │ 批准 / 驳回 ▼ 合并 / 打回重做

第一层：确定性验证器——零成本前置

确定性节点（Deterministic Node）指对同一输入永远产出同一输出的节点：没有采样、没有推理，只有规则执行。格式（Prettier/Black/gofmt）、lint（ESLint/Ruff/Clippy）、类型检查（tsc/mypy/pyright）、测试门禁（pytest/Jest/go test）、静态安全扫描（Semgrep/CodeQL/Bandit）都属于此类。它们共同的特点是：快（毫秒到秒级）、便宜（零模型成本）、可信（结果可复现、可写进 CI 合同）。把这一层放在 LLM 之前，等于在昂贵的语义审查前先过一道免费筛子——格式错误、类型错误、测试回归这类问题根本轮不到模型出手。

第二层：语义审查节点——LLM 只做机器做不了的事

确定性工具看不懂"意图"：这个改动是否破坏了既有架构分层？这段 SQL 拼接是否存在注入路径？这个循环里是否藏着 N+1 查询？这些需要语义理解的判断才交给 LLM 节点。第二层通常按维度拆成多个并行子节点（架构风险、安全漏洞、性能隐患、团队规范），各自只带自己需要的最小上下文，输出再由聚合节点去重、按严重度排序、过滤误报，最后形成一份结构化报告。

第三层：人工确认节点——分级升级的兜底

人工节点不是"所有 PR 都等人"，而是分级升级：只有命中高风险条件的变更才被路由到人——核心模块的架构变更、删除或改写公共 API、涉及密钥/权限/资金的高危操作、敏感数据的读写路径、以及第二层标记为"安全高危"的条目。其余低风险变更在第二层闭环。这样人的注意力被集中在刀刃上，人工审查从"全量瓶颈"变成"抽样门禁"。

节点层处理对象典型组件单次成本失败处理

生产案例：确定性工程 + Agent 混合架构。阿里内部使用两年、服务数万名开发者、累计识别数百万缺陷的行级审查工具 OpenCodeReview 于 2026 年开源。它的设计哲学正是三层分工："该用代码保证的绝不让模型猜"——文件选择、文件打包由工程逻辑精确计算，模型只负责语义判断。在相同底层模型下，其审查精度（Precision）与 F1 综合得分超过直接用通用 Agent 审查，而 Token 消耗仅约 1/9，审查速度更快。这组数字直接验证了三层架构的核心收益：把确定性环节从模型里剥离，质量反而更高。

三层架构是一个成本漏斗：100% 的 PR 进第一层（免费），约三成需要第二层（少量 Token），只有个位数百分比升到第三层（人力）——越贵的资源，处理得越少。

三、确定性验证器设计原则

三条设计原则

规则库复用：规则是资产，不是 Prompt 片段。每条 lint 规则、每个 Semgrep 模式、每项覆盖率阈值都应独立编号、版本化、可回归测试，跨仓库共享同一份基线，各仓库只叠加增量。这样规则演进不再依赖"改 Prompt 试试运气"，而是走正常的代码评审流程。标准化检查：输出格式统一为"文件 + 行号 + 规则 ID + 修复建议"的结构化条目，既是给开发者看的定位信息，也是给下游节点（聚合、统计、看板）消费的合同。快速反馈：第一层的价值在"秒级打回"。如果门禁本身要跑十分钟，开发者就会绕过它。常见做法是增量执行——只对变更文件及其依赖子图跑检查，把分钟级全量压缩到秒级增量。

四类门禁的机制与分工

检查类型代表工具拦截对象成本量级
格式检查Prettier / Black / gofmt风格不一致（可 100% 消灭格式争论）毫秒级
lint 与静态分析ESLint / Ruff / Clippy常见坏味道、未用变量、已弃 API毫秒~秒

其中测试门禁是最强的验证节点——它检查的是行为正确性而不仅是语法合规，但也是最慢、最需要环境准备的。工程上通常把它放在隔离沙箱中运行，并设置超时与资源上限；对变更行设置覆盖率下限（如 80%），可以有效阻止"新代码裸奔合入"。

代码结构图：让验证器和 LLM 都少读代码

确定性层更进一步是AST（抽象语法树，Abstract Syntax Tree，源代码语法结构的树状表示）级别的代码结构图。以社区主流的 Graph Engineering 审查工具为例：用 Tree-sitter 解析代码生成 AST，把函数、类、导入等代码元素及它们之间的调用、继承、测试关系存成图结构，并支持增量更新——每次提交只同步变更部分，不重建全图。审查智能体通过 MCP 协议查询这张图，系统返回最小必要文件集而非全仓库，同时支持测试缺口检测、风险评分与影响范围分析。

代码仓库 ──Tree-sitter──▶ AST 解析 │ ┌────────────────────┼────────────────────┐ ▼ ▼ ▼ 函数 / 类 / 模块 导入依赖 调用 / 继承 / 测试关系 └────────────────────┼────────────────────┘ ▼ 代码结构图（节点 + 边存储） │ ┌───────────────────┼───────────────────┐ ▼ ▼ ▼ 增量更新 MCP 查询接口 衍生分析 （只同步变更部分） （返回最小必要文件集） （测试缺口 / 风险评分 / 影响范围）
生产案例：结构图带来的 Token 坍缩。该类 code-review Graph 工具在 6 个真实代码库上的实测显示：由于审查前先用结构图定位所需上下文，AI 无需全量扫描代码库，Token 消耗较"直接喂仓库"的基线降低数十倍至数百倍。工具生态同样侧面印证了这条路线的成熟度：GitHub star 数 25k+，周下载量约 110 万次，最新版本 v2.3.7 采用 MIT 协议，并提供 VS Code 插件与 GitHub Action 接入——结构图 + MCP 查询已成为审查 Graph 的事实标准组件。 
# CI 中的第一层门禁（示意）：全部确定性、全部秒级
- run: npx prettier --check .        # 格式
- run: npx eslint . --max-warnings 0 # lint
- run: npx tsc --noEmit              # 类型
- run: npx jest --coverage --changedSince=main  # 增量测试

验证器设计的试金石只有一条：开发者被它拦下来时，不需要争论、不需要问模型，看一眼规则 ID 和行号就知道怎么改——凡是还需要"讨论"的检查，都不该放在确定性层。

四、语义审查节点设计

三维审查：架构、安全、性能

语义层最忌讳"一个万能 Prompt 审所有"。生产做法是按风险维度拆成并行子节点，每个子节点有专属的规则提示词、专属的上下文切片和专属的输出 Schema。三个核心维度各有明确的审查焦点：

审查维度核心问题典型检测点所需上下文
架构风险改动是否破坏既有结构？跨层调用、循环依赖、公共 API 语义变化、模块边界侵蚀结构图中的依赖子图 + 变更文件
安全漏洞改动是否引入攻击面？注入路径、权限绕过、密钥硬编码、敏感数据泄露数据流路径 + CWE 专项知识
性能隐患改动是否埋下性能债？N+1 查询、循环内 I/O、无界缓存、全表扫描调用链 + 相关接口签名

Prompt 设计：锚定结构，压制误报

语义审查节点的可信度取决于两件事。其一，位置锚定：要求模型输出的每条意见必须绑定 AST 校验过的文件与行号，聚合节点会丢弃行号无法对上的条目——这是根治"位置漂移"的工程手段，而不是指望模型"小心一点"。其二，专项化提示：研究与工程实践均表明，按 CWE（通用缺陷枚举）等专项知识定制的提示词显著优于泛化提示词；让模型先沿数据流给出证据链再下结论，可以把"看起来像漏洞"的猜测挡在报告之外。HubSpot 在演进其 Sidekick 审查系统时验证了另一个关键结构：在审查 Agent 之后加一个"评审 Agent"（Judge），逐条评估意见的简洁性、准确性与可操作性，再放行给开发者——这被其团队称为最重要的单一架构决策。

上下文精准传递：从"喂仓库"到"喂证据"

语义节点的上下文策略直接决定质量与成本。三个被验证有效的做法：最小文件集——由结构图查询算出"本次 diff 的影响子图"，只传这部分代码；文件打包（file bundling）——把强关联文件捆成一个审查单元，例如 message_en.properties 与 message_zh.properties 这类国际化资源对必须放在一起审，每个包由上下文隔离的子 Agent 独立处理，天然支持并发；历史上下文注入——附上相关 Git 历史与既往 PR 意见，避免对已讨论过的模式反复误报。

生产案例：Anthropic 的多 Agent 并行审查。Claude Code Review 对每个 PR 部署 5 个并行专项 Agent——规范合规检查、缺陷检测、Git 历史上下文、既往 PR 意见复核、代码注释验证——再由独立的聚合 Agent 去重、过滤误报、按严重度排序。结果：在千行以上的大 PR 上，84% 的情况能找到缺陷，平均每个 PR 给出 7.5 条问题；被工程师标记为"错误"的意见不到 1%。部署前 Anthropic 内部仅 16% 的 PR 能收到实质性审查意见，部署后提升到 54%——审查覆盖率与低误报率第一次同时成立。
生产案例：两级流水线压制误报。HubSpot 的 Sidekick 采用"审查 Agent 生成意见 → 评审 Agent 逐条质检"的两级流水线，上线后首次反馈时间（time-to-first-feedback）缩短 90%，峰值降幅达 99.76%，工程师对意见的采纳率（thumbs-up）稳定在 80%。工业界对误报控制的量化结论同样清晰：腾讯在 ICSE-SEIP'26 发表的实证研究显示，静态分析告警经 LLM 复核过滤后，可消除 94%~98% 的误报且保持高召回——误报不是玄学，是可工程化压缩的指标。

语义审查节点的设计顺序永远是：先决定"给它看什么"（上下文），再决定"让它说什么"（Schema），最后才调"怎么问"（Prompt）——上下文错了，Prompt 再好也是在错误的证据上推理。

五、人工确认与实施策略

分级升级：什么必须留给人

人工确认节点的触发条件必须是显式的、可枚举的规则，而不是模型"觉得重要"。典型分级如下：命中即升级，未命中即闭环。升级时不能只丢一句"有风险请确认"，而要附带完整上下文包——风险评分、影响范围分析（结构图算出的下游调用方）、diff 摘要、相关测试缺口，让评审人无需自己重建上下文即可决策。响应侧则要避免人成为新瓶颈：设定分级 SLA、用提醒机器人驱动队列流转。Meta 的内部数据显示，仅靠向评审人发送定向提醒（Nudgebot），整体审查耗时下降 7%，等待超过 3 天的变更占比下降 12%——可见性的价值常常超过审查工具本身。

审查 Graph 不能一夜之间接管合并权限——信任必须用数据挣来。行业共识的路径是影子模式（Shadow Mode，系统只产出意见、不做任何拦截，与旧流程并行运行以积累对比数据）起步的三阶段放权：

阶段一的数据采集尤其关键，因为一个反直觉的事实是：AI 意见的采纳率天然远低于人。对 300 个 GitHub 项目、27 万+ 审查对话的分析显示，人类评审意见的采纳率约 56.5%，而 AI Agent 只有 16.6%——超过一半未被采纳的 AI 建议要么本身有误，要么已被其他方式修复。这决定了阶段一不能只看"AI 提了多少意见"，必须盯采纳率与误报率两条曲线：采纳率长期不达标，说明上下文或 Prompt 设计有问题，贸然进入阶段二只会透支团队信任。

  • 升级触发条件写成显式规则清单，全团队评审后冻结版本
  • 升级包附带风险评分、影响范围与测试缺口，评审人零重建上下文
  • 每阶段设定观察期与量化准入标准，数据达标才放权
  • 保留按仓库/团队粒度的灰度开关与一键回滚
  • 不要跳过影子模式直接让 AI 阻断合并
  • 不要把所有 PR 都路由给人工确认，那只是把旧瓶颈搬了个家
  • 不要用"意见数量"衡量阶段一成效，采纳率与误报率才是真指标
  • 不要在误报未收敛时扩大覆盖范围——信任透支后极难挽回

渐进式引入的本质不是"慢慢上线"，而是把"人信任 AI"这件事拆成可测量的台阶：每一级的台阶都由采纳率、误报率、抽审错误率三块数据铺成，少一块都不许上楼。

规则持续优化：让反馈回流

Graph 的可贵之处在于每条意见都有结构化归宿，因此可以建立反馈闭环：评审人对升级项的批准/驳回、开发者对意见的采纳/标记误报，全部回写到规则库与提示词版本。被连续驳回的规则自动降级复审，被高频触发的模式沉淀为新的确定性规则（从语义层"毕业"到第一层，从此零成本执行）。阿里 OpenCodeReview 的自适应规范学习走的就是这条路——系统从团队的真实反馈中持续校准"什么算问题"，而不是依赖一份静态 Prompt。

人机协同边界：AI 代码越多，审查越重要

一个必须正视的趋势：CodeRabbit 对 470 个 PR 的分析显示，AI 生成代码的 PR 平均问题数 10.83 个，人写代码为 6.45 个（1.68 倍），其中逻辑错误 1.75 倍、安全问题 1.57 倍、XSS 类漏洞高达 2.74 倍。GitClear 对 2.11 亿行变更的统计同样表明复制粘贴代码占比、代码翻工率在持续上升。结论很明确：AI 写码时代审查不是可以放松的环节，而是必须加强的环节——而加强的方式不是堆人，正是本文的三层 Graph 架构。人的注意力应固定在四件事上：架构与设计决策、业务逻辑正确性、可读性与可维护性、知识传递；其余全部交给前两层。

持续监控：上线不是终点

审查 Graph 上线后需要一块长期看板：接手时间 / 审查时间 / 周期时间（对齐 LinearB 四档基准）、语义层误报率与采纳率、升级项占比与 SLA 达成率、第一层拦截率（拦得越多说明左移越成功）、以及 Token 成本曲线。任何一条曲线异常漂移——例如升级项占比突然飙升或采纳率断崖下跌——都应触发规则库复审，而不是等开发者开始抱怨。

  • 确定性检查全部左移到 PR 创建时，秒级反馈、本地可复现
  • 意见输出强制绑定 AST 校验的行号，无法锚定的直接丢弃
  • 按维度拆并行语义子节点，各自喂最小上下文
  • 人工驳回/采纳数据回流规则库，推动语义规则"毕业"为确定性规则
  • 用采纳率、误报率、升级占比三条曲线驱动持续调优
  • 不要让 LLM 判定格式、类型这类有免费确定解的问题
  • 不要用一个万能 Prompt 审所有维度——上下文与目标互相污染
  • 不要全量喂仓库，Token 与注意力会一起爆炸
  • 不要忽略 AI 生成代码占比上升带来的审查压力增量
  • 不要在没有回滚开关的情况下把门禁设为强制阻断

审查 Graph 的终极形态不是"AI 替代评审人"，而是把评审人从格式与语法的泥潭里拔出来，让他们只做人类最擅长的事：判断设计、承担责任、传递知识。

Q&A

为什么确定性验证层必须放在 LLM 审查之前，而不是之后？
因为三层架构本质是成本漏斗，顺序决定了每一层的工作量。格式、类型、测试回归这类问题有免费的确定性解法，放在前面可以在零 Token 成本下拦截大量 PR，只有通过的变更才进入昂贵的语义层；实测中混合架构相比纯 Agent 审查可省下约 8/9 的 Token。若反过来放在 LLM 之后，模型会先把注意力浪费在格式噪音上，意见列表被低价值条目淹没，误报率上升，人工分诊成本也随之增加。此外确定性层前置还保证了"打回理由永远精确可复现"，开发者本地即可修复，无需等待模型二次推理。
Graph 架构是如何逐项解决单 Agent Loop 三大缺陷的？
针对上下文膨胀，Graph 用预构建的代码结构图计算影响子图，每个语义节点只接收最小必要文件集，实测 Token 可降数十至数百倍。针对规则不可复用，Graph 把团队规范从 Prompt 里拆出来，沉淀为可版本化、可回归测试的确定性规则库与专项提示词，规则变更走正常代码评审而非"改措辞碰运气"。针对结果不可预测，Graph 把"何时算审完、意见是否有效"从模型自决改为显式边条件：行号无法锚定 AST 的意见直接丢弃，验证失败的边固定路由到打回节点。三大缺陷分别被上下文工程、规则工程、流程工程化解，而不是靠模型本身变强。
代码结构图（AST 图谱）在审查链路中具体解决什么问题？
它解决的是"审查前的定位问题"。工具用 Tree-sitter 解析代码生成 AST，把函数、类、导入等元素及调用、继承、测试关系存成图结构，并支持增量更新——每次提交只同步变更部分。审查时智能体通过 MCP 协议查询这张图，拿到的不是整个仓库而是最小必要文件集，同时还能获得测试缺口检测、风险评分和影响范围分析等衍生能力。其直接收益是 Token 消耗下降数十倍至数百倍，间接收益是让"影响范围"从模型猜测变成图上的可计算结果，为分级升级提供了确定性依据。
语义审查节点的误报率如何系统性压下来？
误报控制是四个手段的叠加。第一，位置锚定：意见必须绑定 AST 校验过的行号，锚定失败直接丢弃，杜绝位置漂移类误报。第二，专项提示：按 CWE 等专项知识定制的提示词显著优于泛化提示，让模型先给数据流证据链再下结论。第三，评审节点：如 HubSpot 的 Judge Agent 逐条评估意见的准确性、简洁性与可操作性后再放行，首次反馈时间缩短 90% 的同时采纳率稳定在 80%。第四，聚合去重：并行子节点的输出经聚合节点去重、按严重度排序。工业实证给出的上限参考是腾讯的研究：LLM 复核可消除静态告警 94%~98% 的误报且保持高召回。
哪些变更必须保留人工确认？触发条件应该怎么定？
必须留给人的是三类变更：高危操作（删除或绕过权限校验、密钥与资金链路改动）、架构级变更（公共 API 语义变化、跨模块依赖、数据库 Schema 变更）、以及证据链不完整的安全高危项。触发条件必须是显式、可枚举、经团队评审冻结的规则清单，而不是模型输出的风险概率——后者不可审计，也无法向团队解释"为什么这个 PR 要等我"。升级时要附带风险评分、影响范围分析与测试缺口的完整上下文包，并设置分级 SLA（如 P0 一个工作日内双确认），避免人工节点自己变成新瓶颈。
渐进式引入的三个阶段分别以什么标准晋级？
阶段一（影子模式）AI 只评不拦，晋级标准是意见采纳率接近人工水平、误报率降到目标线以下——参考数据是人类意见采纳率约 56.5% 而 AI 仅 16.6%，所以采纳率必须长期跟踪而不是看个位数样本。阶段二把格式、注释、简单修复等白名单类别交给 AI 自动闭环，人工抽审不低于 10%，晋级标准是抽审错误率持续低于阈值且无生产事故。阶段三全量门禁后转为持续运行，按仓库或团队粒度保留灰度降级能力。每个阶段都要预设观察期（如 2~4 周、4~8 周），数据不达标就停在原地修上下文和规则，而不是扩大覆盖范围。
AI 生成代码的比例越来越高，审查压力是变小还是变大？
变大，而且是结构性变大。CodeRabbit 对 470 个 PR 的统计显示 AI 生成代码的问题密度是人工代码的 1.68 倍，逻辑错误 1.75 倍、安全问题 1.57 倍、XSS 类漏洞 2.74 倍；GitClear 对 2.11 亿行变更的分析也显示复制粘贴占比与两周内翻工率在持续上升、重构比例在下降。这意味着"AI 写码所以可以少审查"是危险的错觉——正确的推论是审查必须工程化扩容：用确定性层免费消化增量中的机械问题，用语义层并行处理增量中的逻辑与安全問題，用人工层聚焦真正的高风险变更。三层 Graph 架构恰恰是为这种压力增量设计的。
审查 Graph 上线后应该持续监控哪些指标？
核心是五条曲线。效率侧：接手时间、审查时间、周期时间，对照 LinearB 的分档基准（如审查时间 Elite 档为 3 小时以内）判断团队所处位置。质量侧：语义层误报率与采纳率（采纳率断崖下跌通常是上下文或规则劣化的第一信号）、升级项占比及其 SLA 达成率（占比飙升说明升级条件或语义层校准出了问题）。成本侧：第一层拦截率与 Token 成本曲线，第一层拦截越多说明质量左移越成功。这些指标应汇成统一看板并设告警阈值，异常漂移触发规则库复审，而不是等开发者开始抱怨"审查机器人又在乱报"。
