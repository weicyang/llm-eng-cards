ST05 · 大模型 API 计费与 Token 成本核算

LLM API Billing — token 换算 / 输入输出分价 / 长上下文 O(n²) / 缓存命中 / 隐性成本 / 真实成本公式

大模型账单由三层决定：标价只是第一层，tokenizer 与计费机制是第二层，成功率才是隐藏的第三层——真实成本 = token 数 × 单价 ÷ 成功率，只盯标价的人永远算不准账。

一、Token 与汉字：tokenizer 切分与快速估算

大模型 API 的计费单位不是字、不是行，而是 token（模型词表中的最小处理单元，由 tokenizer 切分产生）。你发一段 500 字的中文到底花多少钱，取决于 tokenizer（把原始文本切成 token 序列的分词器）怎么切——而不同厂商的 tokenizer 切法并不一样，这是后面"隐性成本"的第一个伏笔。

中文不是按"字"机械切分的，而是按词频和组合切分：常见字通常 1 字 = 1 token，生僻字或特殊组合可能 1 字 = 2-3 个 token；高频专有名词反而可能被合并。标点通常 1 个 = 1 token，但连续符号行为不一（如英文省略号可能合并为 1 token，中文句号逐个计算）。代码则更碎：缩进、括号、关键字、引号每个都算。

内容示例字数约 Token 数比例
"你好世界"4 字~4~1 token/字
"今天天气不错，适合出去散步"12 字（含标点）~12~1 token/字
"RAG系统中的混合检索策略"12 字~14~1.2 token/字（中英混合）
"中华人民共和国国务院"9 字~5专有名词合并
两行 Python 函数定义—10-12符号逐个计
快速估算：中文 1 字 ≈ 1~1.5 token（日常文本按 1:1，中英混合/术语多按 1:1.5）

记住这个量级就够日常估算：1000 个汉字大概 1000-1500 个 token。精确核算时用厂商提供的 tokenizer 工具实测，因为同一文本在不同模型上的 token 数可能相差 20% 以上——同样的内容换一个模型，账单直接变。

token 不是字符也不是单词，而是厂商词表里的编号——换算比例由 tokenizer 决定，跨模型比较价格前必须先对齐 token 口径。

二、输入便宜输出贵：自回归生成与 KV Cache

几乎所有厂商的输出单价都是输入单价的 3-5 倍。这不是定价策略上的"坑"，而是算力成本的真实反映：输入是"读"，输出是"写"，两者的计算量根本不是一个量级。

输入阶段，模型把你的 prompt 完整过一遍前向传播，计算出每一层的表示，一次完成。输出阶段则是自回归生成（每生成一个新 token，都要基于之前所有内容计算下一个 token 的概率分布）：生成 1000 个输出 token，相当于在整个上下文上做了 1000 步计算。

输入 vs 输出的计算量差异 输入（读）： prompt 一次前向传播 [1000 tokens] ──过一遍网络──▶ 完成（1 遍） 输出（写）： 逐 token 生成，每步都要看全部前文 t1: 基于 1000 tokens 算 t2: 基于 1001 tokens 算 …… t1000: 基于 1999 tokens 算 （约 1000 步） KV Cache：把每步算过的前文中间结果缓存复用 → 输出不必从头重算，但仍是逐步生成 → 所以输出贵 3~5 倍，而不是 1000 倍

如果没有优化，输出 1000 token 的成本会是输入的约 1000 倍。实际只贵 3-5 倍，靠的是 KV Cache（把每一步计算过的前文键值对缓存起来，后续步骤直接复用，避免从头重算）。但缓存只解决"重复计算"，解决不了"逐步生成"本身——输出仍然是一个 token 一个 token 串行算出来的，算力消耗远大于输入，价格自然更高。

维度输入输出
计算模式一次前向传播（并行）自回归逐 token 生成（串行）
计算遍数1 遍≈ 输出 token 数 步
KV Cache 作用—复用前文中间结果，避免重算
典型单价关系基准输入的 3-5 倍
省钱抓手压缩 prompt、命中缓存控制输出长度、减少无效重试

看到输出单价是输入的 4 倍不必惊讶——那正是"写 1000 步"对"读 1 遍"的算力比价，KV Cache 已经帮你压掉两个数量级了。

三、长上下文为什么贵：O(n²) 计算与跳价

厂商普遍对长上下文单独定一档更高的价格。原因在 Transformer 的注意力机制：每个 token 都要和其他所有 token 计算注意力，计算量随序列长度呈平方增长。输入 1K tokens 的注意力计算量约为 100 万级，32K 约为 10.24 亿级，128K 约为 1.64 万亿级——从 1K 到 32K，长度变 32 倍，计算量变约 1024 倍。

注意力计算量 ∝ n²：1K → 32K 是 1024 倍，不是 32 倍

长上下文档位的高单价，本质是在覆盖这部分超线性增长的算力成本。这不是某一家厂商的做法，而是行业通行定价逻辑。以 GLM-5.1 的定价结构为例（2026-08 快照）：

长上下文涨价不是商业套路，是 O(n²) 注意力计算的账单转嫁——上下文翻倍，成本远不止翻倍。

四、缓存命中：能省多少钱，怎么算

缓存是定价表里最容易让人懵的两行：缓存存储和缓存命中（新请求的输入前缀与已缓存内容一致时，该部分按大幅折扣价计费）。先说结论：这是正规计费项里最大的省钱杠杆，折扣普遍在 75% 以上。

最典型的受益场景是 RAG 系统，每次请求的 prompt 结构高度重复：

[系统提示词 1000 tok（每次相同）]
+ [检索文档 8000 tok（大部分时候相同）]
+ [用户问题 200 tok（每次不同）]

不开缓存，每次都把 9200 个不变的部分从头算一遍、按全价付一遍。开了缓存，模型把前缀的 KV Cache 结果存下来，下次请求前缀一致就直接复用，这部分按缓存命中价计费。以 GLM-5.1 短上下文档为例：正常输入 ¥6/百万 tokens，缓存命中 ¥1.3/百万 tokens，折扣 78%。

RAG 请求的缓存命中流程 第 1 次请求： [系统提示词 + 文档](9000) ──全价计算──▶ KV Cache 存档 [用户问题](200) ──全价──▶ 输出 1000 第 N 次请求（前缀一致）： [系统提示词 + 文档](9000) ──命中！按 ¥1.3 计费，免重算 [用户问题](200) ──全价 ¥6──▶ 输出 1000（全价 ¥24）

生产案例（RAG 知识库问答）：某企业知识库日均 10 万次问答，单请求约 1 万 tokens 固定前缀（系统提示词 + 高频文档）。开启缓存后命中率稳定在 88%-92%，输入侧成本下降约 78%，整单费用从约 ¥9.6/千次降到 ¥5.4/千次（-44%），月账单节省约 ¥12,600，且因省去前缀重算，首 token 延迟同步下降。缓存收益与"固定前缀占比 × 请求量"成正比，是 RAG 场景的第一优先优化项。

缓存的本质是"为算过的结果付一次钱"：prompt 里不变的前缀占比越高、请求量越大，省得越狠——RAG 场景天然吃满这个红利。

五、四种标价里看不到的隐性成本

标价对比只是起点。真实账单里潜伏着四类隐性成本，每一类都能让"看起来便宜"的模型变贵，或让"看起来贵"的模型反而划算。

隐性成本一：长上下文整单跳价

某些模型的上下文分界点不是"超出部分按高价"，而是整条请求全部按高价。以 GPT-5.4 的 272K 分界点为例：一条 271K tokens 的请求按低档价，一条 273K 的请求整单按高档价，成本可能差一倍。做 Agent 系统时上下文很容易滚过分界点，账单会毫无征兆地暴涨。

隐性成本二：tokenizer 膨胀 20%-35%

同一段文本在不同 tokenizer 下产生的 token 数不同。实测中，某些模型对中文和代码的切分更碎，同样内容比切分粗的模型多 20%-35% 的 token：一段 10 万字中文，一边约 10 万 tokens，另一边约 12-13.5 万 tokens。token 数多 20%-35%，实际费用就贵 20%-35%——标价 $5/百万 tokens，等效单价变成 $6-6.75。跨模型比价不对齐 tokenizer，结论必然失真。

隐性成本三：thinking tokens

带推理能力的模型在输出最终答案前会生成大量内部推理 token（thinking tokens），这些内容在回答里看不到，但按输出价计费。一个复杂问题，模型可能内部"想"了 5000 tokens，只输出 500 tokens——你看到 500，账单是 5500。只按可见输出估算成本，会系统性低估。

隐性成本四：失败重试成本

便宜模型一次做对的概率更低。做不对就要重试，重试一次成本翻倍：如果旗舰模型一次成功、便宜模型三次才成功，便宜模型的实际成本就不是标价的 1/7，而是 3/7。这条在 Agent 多步任务里被放大——中间某一步失败，前面所有步骤的 token 可能全部白付。

真实账单的冰山结构 标价（输入/输出单价） ─────────────────────────────────── 水面 tokenizer 膨胀（+20%~35% token） thinking tokens（看不见的输出） 整单跳价（跨分界点成本翻倍） 失败重试（×2、×3 的乘数） ── 水面之下才是账单主体 ──
隐性成本作用机制典型放大倍数高发场景防御手段

六、真实成本公式：token × 单价 ÷ 成功率

把第五节的四个乘数收拢成一个可执行的公式：

真实成本 = token 数 × 单价 ÷ 成功率

结论变了但没完全变：便宜模型与旗舰的真实差距从 4.7 倍收窄到约 3.4 倍，而且这还没算人工排查失败的时间成本。任务越复杂、失败代价越高，成功率项的权重越大——这就是"Agent 场景下成功率比单价重要得多"的数学解释。

生产案例（编码助手成本对照）：某团队用编码 Agent 做一次约 30K tokens 的多文件代码修改：走旗舰模型单次费用约 ¥2.7，一次通过；走便宜模型单次约 ¥0.3，但此类多文件重构约两次才成功一次，真实成本约 ¥0.6，还搭上约 20 分钟人工复核。团队最终的策略是"日常小改用便宜模型、多文件重构直连旗舰"，月度总费用比全量旗舰下降约 65%，返工率没有上升。记住两个粗估数：旗舰模型 1K 总 tokens ≈ ¥0.09，便宜模型 1K ≈ ¥0.01，差约 10 倍——但下单前永远先问成功率。

另一个实用技巧：很多 CLI 工具只显示总 token 数、不拆分输入输出。可用混合单价估算：典型编码交互约 60% 输入 + 40% 输出（含 thinking），混合单价 = 0.6 × 输入价 + 0.4 × 输出价。估个位足够做预算决策，精确核算再去读 API 返回的 usage 明细。

单价是厂商定的，token 数是 tokenizer 定的，只有成功率是你自己的工程质量——它是真实成本公式里唯一能被你的系统直接优化的变量。

七、模型分档与路由建议

把前面的计费知识落到选型上，原则是"按场景分档，混合使用"，而不是押注单一模型：

场景推荐档位理由注意事项
短对话、简单问答、分类低价档模型单价最低，简单任务质量足够用 tokenizer 实测中文占比高的流量
中等复杂度、要求稳定中间档模型性价比平衡盯住上下文分界点，防整单跳价
复杂推理、Agent、代码生成旗舰模型成功率最高，重试成本最低为 thinking tokens 预留预算
RAG 高频重复前缀任意档 + 开缓存输入侧省 75%+保持前缀稳定，别频繁改提示词

这就是"模型路由"的计费视角（路由的工程实现见 A63 混合路由卡片）：先判断任务难度，再分派给合适档位，简单问题用便宜的、复杂问题才上贵的，总成本最低。预算有限时的优先级排序也很明确：先开缓存（收益最确定），再上路由（收益最大），最后才考虑压 prompt 长度（收益最小且容易伤质量）。

  • 用目标模型的 tokenizer 实测 token 数，再比价
  • 读 API usage 明细，单独监控 thinking tokens
  • 给 Agent 上下文设长度监控，分界点前做摘要压缩
  • 按"token × 单价 ÷ 成功率"给每个任务类型建成本档案
  • RAG / 固定前缀场景第一天就开缓存
  • 只拿标价表做跨模型比价
  • 用可见输出长度估算带推理模型的成本
  • 让 Agent 上下文无管控地滚过上下文分界点
  • 在复杂多步任务上为省单价容忍低成功率
  • 频繁修改系统提示词导致缓存集体失效

计费知识的正确用法是建立三层直觉：量级感（一次调用几分到几毛）、结构感（输入输出分价、长档跳价、缓存折扣）、真实感（除以成功率之后的成本）——三层都过一遍，账单才没有意外。

Q&A

一个汉字到底算几个 token？为什么没有固定答案？
常见汉字通常 1 字 ≈ 1 token，但这是统计规律而非固定换算。tokenizer 按词频和组合切分：生僻字可能 1 字拆成 2-3 个 token，高频专有名词反而多个字合并成 1 个；中英混合文本约 1.2 token/字，代码则连括号和缩进都单独计数。日常估算按 1 字 = 1-1.5 token 足够，精确核算必须用目标厂商的 tokenizer 实测，因为同一段文本在不同模型上的 token 数能差 20% 以上。
为什么输出单价是输入的 3-5 倍，而不是反过来？
因为两者的计算模式完全不同。输入是一次前向传播，整个 prompt 并行过一遍网络就算完；输出是自回归生成，每产出一个 token 都要基于全部前文计算一次，生成 1000 个 token 就是约 1000 步。如果没有 KV Cache 缓存前文中间结果，输出成本会是输入的约 1000 倍；正是 KV Cache 的复用把差距压到了 3-5 倍。所以这个价差反映的是真实算力差距，不是定价套路。
长上下文为什么不是线性涨价，而是分档跳价？
根源是注意力机制的 O(n²) 复杂度：每个 token 要与所有其他 token 计算注意力，序列长度变 32 倍，计算量变约 1024 倍。线性涨价无法覆盖这种超线性成本增长，所以厂商用分档定价来对齐成本曲线。更隐蔽的是部分厂商的跳价机制——上下文一旦越过分界点，整条请求全部按高档计费，而不是只有超出部分。Agent 系统的上下文会持续滚动增长，必须在分界点前设置监控和摘要压缩。
缓存命中能省多少？什么场景值得开？
缓存命中价通常是正常输入价的 20%-25%，即折扣 75%-78%。收益公式大致是"固定前缀占比 × 命中率 × 输入费占比"，所以最值得开的场景是 RAG 和带长系统提示词的高频服务：prompt 里 90% 是不变的提示词和文档，命中率稳定在 90% 左右时，整单费用可以省 40%-55%。注意两个前提：前缀必须逐字节稳定，改一个字符缓存就失效；输出部分不享受缓存折扣。日均请求量越大，回收越快。
thinking tokens 是什么，为什么看不见也要付钱？
带推理能力的模型在给出最终答案前，会先生成一段内部推理 token，即 thinking tokens。它们属于模型输出的一部分，占用真实算力，因此按输出单价计费，但通常不展示给最终用户。典型情况是模型内部推理 5000 tokens、只输出 500 tokens，账单却按 5500 计。防御手段有两个：从 API 返回的 usage 明细里单独读出推理 token 数做监控；给不同任务设置推理档位，避免简单任务也触发长篇内部推理。
为什么"真实成本 = token × 单价 ÷ 成功率"比标价更重要？
因为失败重试是成本的乘数。便宜模型单价是旗舰的 1/7，但如果它一次做对的概率只有 60%、平均要 1.7 次才成功，真实成本就变成约 1.7/7 ≈ 24% 的旗舰价，而不是 14%；在 Agent 多步任务里，中途失败还可能让前面所有步骤的 token 白付，乘数更大。更隐蔽的是人工排查失败的时间成本，往往比 token 本身更贵。所以选型时必须按任务类型分别测成功率，再用这个公式算真实单价，任务越复杂、失败代价越高，成功率权重越大。
CLI 工具只显示总 token 数，不拆分输入输出，怎么估钱？
用混合单价估算即可。典型编码交互的 token 构成约为 60% 输入 + 40% 输出（含 thinking tokens），混合单价 = 0.6 × 输入单价 + 0.4 × 输出单价。按此估算，旗舰模型约 ¥0.09/千 tokens，便宜模型约 ¥0.01/千 tokens，相差约 10 倍——一次 30K tokens 的修改分别约 ¥2.7 和 ¥0.3。这种估法精度足够支撑预算决策；需要精确核算时再读 API 响应里的 usage 字段，那里有输入、输出、推理 token 的完整拆分。
