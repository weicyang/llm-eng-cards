P02 · WebSocket 与 SSE 技术对比

双向通信 vs 单向流 / 协议握手与连接管理 / 负载均衡差异 / 六大选型维度

WebSocket 是拨通后不挂断的电话，SSE 是永不关闭的广播电台——前者为"双向"付出复杂度成本，后者为"单向"换来源生可靠性。

一、通信模型本质区别

1.1 从轮询的困境说起

传统 HTTP 是严格的请求-响应模型：客户端问，服务器答，连接随即结束，服务器永远不会主动开口。但大量业务需要"服务器一有数据就告诉客户端"——聊天消息、股票行情、大模型逐字生成的 Token。最原始的办法是短轮询（客户端每隔一秒发一次"有新数据吗"），代价是绝大多数请求返回空结果，实时性还取决于轮询间隔。于是出现了两类"把连接留住"的技术：WebSocket 与 SSE（Server-Sent Events）。

1.2 WebSocket：握手之后彻底离开 HTTP

WebSocket 的起点是一次普通的 HTTP 请求，但它携带了 Upgrade: websocket 与 Sec-WebSocket-Key 头部。服务器若支持，就返回 101 Switching Protocols——这就是协议升级：从这一刻起，这条 TCP 连接不再是 HTTP，而是切换到独立的帧协议（RFC 6455），双方可以随时、独立地向对方发送帧，即全双工通信。帧的开销极小，每条消息仅 2~14 字节头部，且同时支持文本与二进制数据。代价是：升级后的连接对 HTTP 生态完全不可见，缓存、CDN、普通中间件都无法再介入。

1.3 SSE：留在 HTTP 内部的长响应

SSE 走了完全相反的路：它从不离开 HTTP。客户端发起一个 GET 请求，服务器返回 200 OK 并把 Content-Type 设为 text/event-stream，然后这个响应体永远不结束，服务器持续向其中写入 UTF-8 文本事件。它是严格的半双工——服务器单向推送，客户端想说话必须另开一个普通 HTTP 请求。浏览器的 EventSource API（全球浏览器支持率约 97%）把连接管理、事件解析、断线重连全部封装成了内置能力。

1.5 HTTP/1.1 的六连接枷锁与 HTTP/2 的解放

理解两者命运反转的关键在于连接数限制。HTTP/1.1 下浏览器对每个源（origin）最多 6 个并发 TCP 连接，而每条 SSE 流是一个"永不完成"的响应，会永久占用一个槽位——开满 6 条 SSE，该域名下其余所有请求（API、图片、样式）全部排队，多开几个标签页问题更严重（该限制按浏览器+域名计算，Chrome 与 Firefox 官方均标记为"不予修复"）。WebSocket 因为已脱离 HTTP，不受此约束，这是它统治实时通信十余年的结构性优势。

转折点来自多路复用：HTTP/2 把一个源的所有请求收拢到单条 TCP 连接上，每条 SSE 流只是一个逻辑流（stream），浏览器默认允许约 100 个并发流，六连接上限就此消失。再叠加 LLM 流式输出的爆发式需求，行业共识已经从"默认用 WebSocket，除非不行"反转为"默认用 SSE，除非确实需要高频双向"。

还有一个容易被忽略的不对称：SSE 搭上了 HTTP/2 的便车，WebSocket 却没有。WebSocket 本质是 HTTP/1.1 的 Upgrade 机制，RFC 8441 虽然定义了基于 HTTP/2 的 WebSocket，但各服务器实现支持程度参差，实践中绝大多数部署仍走 1.1 升级路径——这意味着 WebSocket 无法享受多路复用带来的连接收敛红利。

协议之争的本质不是性能之争，而是"连接占用规则"之争——HTTP/2 抹掉了 SSE 唯一的硬伤，选型天平才真正开始摆动。

二、工程实现细节对比

2.1 WebSocket：心跳、重连与状态同步全靠自建

WebSocket 协议本身只给了你一条"管道"，管道的可靠性全部是应用层的责任。第一件必须做的事是心跳：协议内置 PING/PONG 控制帧，服务端通常每 15~30 秒向所有客户端发一次 PING，收不到 PONG 的直接 terminate。为什么不能依赖 TCP 自身的存活检测？因为连接中途的 NAT 表项、负载均衡器的空闲超时（如 ALB 默认 60 秒）会悄无声息地回收连接，留下两端都以为对方还活着的半开连接——心跳间隔取 25 秒正是为了压在常见 60 秒超时之下。

第二件事是断线重连与消息补偿：WebSocket 没有原生重试、没有消息编号、没有顺序与去重保证。生产级实现要求每条消息携带唯一 messageId（去重）与自增序列号 seq（乱序重组），客户端记录最后确认的 seq，重连后带上它请求补发，同时用指数退避（1s → 2s → 4s …封顶 30s）避免重试风暴。第三件事是安全与治理：握手阶段的鉴权建议把 JWT 放进 Sec-WebSocket-Protocol 子协议头，而不是 URL query——query 里的 token 会落进网关访问日志；每客户端还要配令牌桶限速，防止单连接刷爆服务端。

2.2 SSE：可靠性写进了协议本身

SSE 的线缆格式只有四种字段：data: 承载内容、event: 定义事件类型、id: 标记事件编号、retry: 指示重连间隔，以冒号开头的行是注释（常用作 keepalive 心跳），事件之间必须以空行（\n\n）分隔。这套格式带来的最大红利是断点续传：连接断开后，浏览器自动等待（默认约 3 秒，或按服务器下发的 retry 值）重新发起请求，并在请求头携带 Last-Event-ID，服务端据此从事件历史中补推漏掉的部分——整套机制零代码。若服务器返回 HTTP 204，浏览器会理解为"永久停止重连"。

但要清醒：断点续传不是免费的。它依赖服务端保留事件历史，而历史缓冲普遍是有界的——Node 的 sse-channel 默认只留 500 条（FIFO 环形），Go 的 r3labs/sse 留 1000 条或 5 分钟（先到先逐），Spring 的 SseEmitter 默认干脆不支持重放。客户端断线时间一旦超过缓冲保留窗口，Last-Event-ID 换回的只有沉默：不报错、不提示，消息直接消失。此外 EventSource 只能发 GET、不能自定义请求头（无法带 Authorization），所以大模型 API 的 POST 流式场景普遍改用 fetch + ReadableStream 手工解析同样的格式。

2.4 代理与防火墙兼容性

SSE 就是普通的 HTTP 长响应，代理、CDN、防火墙、负载均衡器全部天然放行，无需任何特殊配置；唯一要防的是代理缓冲——Nginx 默认会把上游响应攒够再转发，SSE 消息会在缓冲区里积压数秒才成批到达，必须设置 proxy_buffering off 并下发 X-Accel-Buffering: no 头。WebSocket 则相反：Upgrade 握手在部分企业代理与老旧网关上会被直接拦截，升级成功后又绕过了 HTTP 缓存与 CDN 的常规处理路径，任何中间设备要支持它都需要显式配置。

链路环节SSEWebSocket
企业代理 / 防火墙标准 HTTP，全部放行部分代理拦截 Upgrade 握手
CDN / 反向代理天然兼容（需关缓冲）需显式开启 upgrade 支持
HTTP 缓存与普通响应一致完全绕过
调试手段curl -N 直接可读需专用客户端 / 抓帧工具

SSE 把可靠性写进了协议规范，WebSocket 把可靠性留给了你的代码——这句话决定了两个团队完全不同的维护负担。

三、负载均衡与集群差异

3.1 WebSocket 集群：连接是有状态的

单机时代一切简单：用户 A 发消息给用户 B，服务器在本地哈希表里找到 B 的连接直接推。一旦水平扩展，问题立刻出现——A 挂在服务器 37，B 挂在服务器 142，持有 A 连接的进程根本没有 B 的管道。WebSocket 连接天然粘性会话化：一条连接被钉死在某台后端机器上，普通轮询式负载均衡对它毫无意义。

业界三套解法各有取舍：其一是负载均衡层做会话亲和（Cookie 或 IP Hash），实现最简单，但某台机器宕机时其上所有客户端集体掉线，重连后"房间在哪台机器"又要重新解析；其二是引入 Redis Pub/Sub 做消息底板，每台 WebSocket 服务器订阅自己持有连接对应的频道，消息发布后由订阅方投递给本地连接，部署简单、生态成熟，但 Redis 吞吐在约 10 万消息/秒会成为瓶颈，更高压力要分片或换 NATS/Kafka；其三是专用消息代理（NATS JetStream、Kafka），换来高吞吐与持久化，代价是多维护一套中间件。配套的还有两件事：在线状态写 Redis（如 SET user:123:online "server-5" 并加 TTL，进程死了键自动过期）；发布新版本时走优雅下线——先通知客户端"即将断开"，等待约 10 秒让流量自然排空，再强制关闭剩余连接。

WebSocket 集群（有状态） SSE 集群（无状态） ───────────────────────────── ───────────────────────── 客户端群 客户端群 │ │ LB：粘性会话 / ip_hash LB：普通轮询，任意分发 ┌──────┼──────┐ ┌───────┼───────┐ WS-1 WS-2 WS-3 HTTP-1 HTTP-2 HTTP-3 持2万连接 持2万连接 持2万连接 处理完即释放 / 流结束即释放 └──────┼──────┘ 重连请求可落到任意机器 ▼ 无需粘性、无需跨机广播 ┌─────────────────────┐ │ │ Redis Pub/Sub / NATS │ 扩容 = 加机器即可 │ 跨服务器消息扇出 │ └─────────────────────┘

3.2 SSE 集群：重连即无状态

SSE 在集群维度几乎是"免费"的：每条流虽然长，但本质仍是一个 HTTP 请求，客户端每次重连都是一个全新请求，负载均衡器可以把它送到任何一台后端；服务器之间不需要互相知道对方的存在，不需要消息底板，不需要粘性会话。扩容就是加机器，缩容直接摘节点，与普通 Web 服务完全同构。这也是 SSE 能直接架在弹性伸缩与 CDN 体系之上的根本原因。

生产案例一：文件描述符耗尽引发的扩容。某聊天系统单机 WebSocket 服务在 2000 并发时一切正常，冲到 3000 并发开始大面积连接失败——CPU 与内存都很空闲，排查发现是 Linux 默认的 1024 文件描述符上限被打满。处理分三步：ulimit -n 提到 65535、调整 fs.file-max 与 somaxconn 内核参数、同时上第二台机器并引入 Redis Pub/Sub 做跨机扇出。调优后单机稳定承载 5 万+空闲连接，跨机消息投递仅增加 2~5ms 延迟。教训：WebSocket 的第一个扩容信号往往不是 CPU，而是文件描述符。

HTTP 服务扩容是"加机器"，WebSocket 扩容是"改架构"——粘性会话与消息底板这两件事，在写第一行代码前就要想清楚。

四、六大选型维度

把前文的机制差异压缩成六个可以直接打勾的维度，选型时逐条对照业务需求即可。

选型维度WebSocketSSE
① 通信方向全双工，双向同时收发半双工，仅服务器推送
② 实现复杂度高：心跳、重连、seq 去重、状态同步全部自建低：重连与续传内置，服务端只是"写文本"
③ 基础设施要求网关须支持协议升级，LB 须粘性，另需 Pub/Sub 底板标准 HTTP 链路即可，代理/CDN 零配置
④ 连接数与复用每连接独占一条 TCP，受服务端 fd/内存约束HTTP/2 下多流复用单连接（默认 ~100 流）
⑤ 可靠性机制无原生保证，掉线即进入"自建补偿"模式自动重连 + Last-Event-ID 续传（缓冲有界需注意）
⑥ 代理兼容部分企业代理拦截握手，需显式配置中间件天然穿透所有 HTTP 设施

4.1 复杂度维度的展开：你要亲手写多少东西

工程事项WebSocket 团队SSE 团队
断线检测心跳超时判定 + 半开连接清理浏览器 onerror 回调
重连策略自建指数退避 + 抖动内置（可用 retry 字段调节）
消息补偿seq + 补发协议 + 去重Last-Event-ID（服务端留历史）

按"通信方向"这一条硬指标选型，其余维度做验证；

默认 SSE，仅当客户端需要高频（每秒多次）主动上行或传二进制时才上 WebSocket；

WebSocket 项目第一天就实现心跳、退避重连、seq 去重三件套；

SSE 服务端给事件编号并保留有界历史缓冲，让 Last-Event-ID 真正可用；

把并发连接数、消息速率、重连次数写进监控面板。

不要用 WebSocket 做纯单向通知推送——你在为用不到的方向付费；

不要使用固定间隔重连（无抖动），故障恢复瞬间会形成请求洪峰；

不要把 JWT 放在 WebSocket URL 的 query 里，它会出现在访问日志中；

不要在 Nginx 后面跑 SSE 却忘记关 proxy_buffering，消息会延迟数秒成批到达；

不要在 Serverless 函数里托管 WebSocket 长连接。

选型的问题从来不是"哪个更先进"，而是"六个维度里你的业务真正用到几个"——用不到的能力，都是纯成本。

5.2 LLM 流式输出：SSE 的主场

大模型对话是 SSE 最具代表性的场景。交互模式固定为：客户端 POST 一次问题，服务器流式推送几十秒的 Token——方向天然单向，WebSocket 的"双向"能力完全闲置。实测层面，OpenAI、Anthropic、Gemini、DeepSeek、Groq 五大厂商的流式 API 全部采用 SSE（Gemini 额外提供 WebSocket 选项）。流式带来的收益是感知延迟：非流式 GPT-4o 需要 3.2~5.5 秒才吐出第一个字符，流式版本首 Token 只要 300~600ms，感知等待缩短 82%~89%；各厂商首 Token 时间分布大致为 Groq 100~200ms、Gemini 250~500ms、OpenAI 300~600ms、Claude 400~800ms、DeepSeek 500~1200ms。成本方面，SSE 分帧开销只让总生成时间增加 5%~10%，计费按 Token 计算，流式不额外花钱。框架生态也完成了站队：OpenAI SDK、Anthropic SDK、Vercel AI SDK 底层都是 SSE 消费，tRPC v11 明确推荐 SSE 订阅为默认，GraphQL Yoga 的默认订阅传输同样是 SSE。

生产案例二：AI 客服从"整段等待"到"逐字输出"。某客服机器人原本等模型生成完整答案再一次性返回，首字等待 3.2~5.5 秒，用户会话放弃率约 22%。改造为 POST 提问 + SSE 推流后，首 Token 稳定在 300~600ms，感知等待下降约 85%，放弃率降至 9%；Token 费用分文未增，服务端也未引入任何连接管理组件——SSE 端点就是一个普通 HTTP 接口，复用了既有的网关与弹性伸缩。

5.4 混合架构：真实产品常常两者都用

选型不必是非此即彼。一个成熟的 AI 产品完全可以在不同链路上各取所长：文本对话走 SSE 推流，语音对话走 WebSocket 双向音频，任务进度通知再复用同一条 SSE 通道的事件类型（event: 字段天然支持多路复用）。OpenAI 的产品线就是这种形态——Chat Completions API 用 SSE，Realtime API 用 WebSocket。判断每条链路时回到同一个问题：这个交互里客户端上行的频率和时延要求是什么？答案为"几乎没有"就走 SSE，把复杂度预算留给真正需要的地方。

六、性能与成本权衡

6.1 协议开销与服务器资源

单看每条消息，WebSocket 的帧头只有 2~14 字节，SSE 每个事件要付出"data:/id:/空行"等文本围栏，流式总耗时因此多出 5%~10%——但在 LLM 场景里，Token 生成本身动辄数秒，这点围栏开销可以忽略。真正的资源账在服务器侧：每条 WebSocket 连接常驻约 2~8KB 内存（应用状态另计），5 万连接就是 100~400MB 基线，外加每连接的文件描述符与心跳流量；SSE 流同样占连接，但 HTTP/2 复用后一个源只需一条 TCP，且流结束即释放。移动端功耗上，WebSocket 的周期性心跳会持续唤醒无线电模块，而 EventSource 允许浏览器内核统一调度连接（规范明确提及可因此节省电量），长连接功耗模型更友好。

生产案例三：重连风暴与抖动的价值。一次区域性网络故障恢复后，1 万个使用固定 3 秒重连间隔的 SSE 客户端在同一时刻涌回，全部请求挤进约 100ms 的窗口，服务端连接建立队列瞬间打满，引发二次雪崩。整改方案是把重连改为指数退避加 full jitter（延迟 = min(2^n × 基数, 30s) × random(0.5~1.0)），同样的 1 万客户端被摊开到约 15 秒的时间轴上，峰值建连压力降为原来的约 1/150。固定间隔重连只是把洪峰延后，抖动才能真正削峰。

生产案例四：移动端网络切换的静默丢消息。某 App 的 SSE 推送在用户从蜂窝网络走进有 Wi-Fi 的大楼后频繁"断更"。复现发现：切换瞬间 TCP 连接静默死亡（没有 FIN/RST），操作系统要 2~15 秒后才察觉并触发 EventSource 重连，而这段空窗期产生的事件早已被服务端 500 条上限的环形缓冲逐出——Last-Event-ID 换不回任何东西，且没有任何错误提示。最终方案：客户端为每个事件写入本地持久化日志（WAL），重连后从本地最后 ID 续传；服务端把缓冲扩到 2000 条并在缓冲逐出时下发"需要全量快照"信号，客户端收到后回退到一次性拉取。丢消息投诉归零。

6.3 什么时候 WebSocket 的成本是值得的

上述成本并非劝退 WebSocket——当业务是协同编辑、对战游戏或语音时，双向低延迟是核心产品能力，自建心跳、重连、消息底板是必须支付的对价。判断标准只有一条：如果砍掉"客户端高频上行"这个需求产品就不成立，那么 WebSocket 的复杂度是投资；否则它是浪费。

协议选型最大的隐性成本不是 CPU 和内存，而是"为可靠性写的代码"——心跳、重连、补发、监控，这些才是账单的大头。

Q&A

SSE 是单向的，那客户端怎么给服务器发消息？
客户端用普通的 HTTP POST/GET 另发请求即可，两者并行不冲突。大模型对话就是这个标准范式：POST 提交问题，服务器在同一（或新的）SSE 流上逐字推送回答。需要携带会话标识时，POST 与 SSE 通过 URL 参数或 Cookie 关联。这种"控制面走普通 HTTP、数据面走 SSE"的拆分，反而比把所有东西塞进一条 WebSocket 更容易测试和排查。
为什么大模型厂商几乎全部选择 SSE 而不是 WebSocket？
四个原因叠加：第一，对话交互方向天然是"一问一长答"，客户端在生成期间没有上行需求，WebSocket 的双向能力是闲置资产；第二，SSE 是标准 HTTP，能直接穿过厂商现有的 CDN、网关与防火墙体系，无需协议升级配置；第三，自动重连与 Last-Event-ID 内置在浏览器里，客户端 SDK 的实现量大幅减少；第四，SSE 端点就是普通 HTTP 接口，可以复用既有的弹性伸缩与负载均衡。实测上流式让首 Token 时间从数秒降到几百毫秒，而分帧开销只增加 5%~10% 的总时长，性价比极高。
SSE 断线重连后，消息一定不会丢吗？
不一定。Last-Event-ID 续传能否生效取决于服务端是否保留了事件历史，而主流实现的缓冲都是有界的：Node 的 sse-channel 默认 500 条，Go 的 r3labs/sse 默认 1000 条或 5 分钟，Spring SseEmitter 默认不支持重放。客户端断线时间超过缓冲保留窗口时，中间的事件会被静默跳过——没有错误、没有提示。工程上要么扩大缓冲，要么让服务端在检测到 ID 过旧时下发特殊事件，指示客户端回退到全量快照拉取。
WebSocket 为什么必须自己做心跳？TCP 不是有 keepalive 吗？
TCP keepalive 默认间隔太长（通常两小时），且链路上的 NAT 设备与负载均衡器有自己的空闲超时（如 ALB 默认 60 秒），会在双方毫无察觉的情况下回收连接，留下半开连接——客户端以为连着，服务器也以为连着，消息发了没人收。应用层每 15~30 秒发一次 PING、收不到 PONG 就主动断开重连，是发现这类静默死亡的唯一可靠手段。选 25 秒这类间隔就是为了压在常见 60 秒中间件超时之下。
为什么页面多开几个 SSE 连接就卡住了？
这是 HTTP/1.1 的经典限制：浏览器对每个源最多 6 个并发连接，SSE 流是永不结束的响应，会永久占用槽位。开满 6 条后，该域名的所有请求（包括 API 和静态资源）都会排队，表现为网络面板里的 pending/stalled。解法是把服务切到 HTTP/2：所有流复用在单条 TCP 连接上，默认允许约 100 个并发流，槽位竞争消失。注意浏览器实际只支持基于 TLS 的 HTTP/2，明文 h2c 不被接受。
WebSocket 服务怎么做负载均衡？
连接是有状态的，必须分两层处理。第一层是接入：负载均衡器启用粘性会话（Cookie 或 IP Hash），保证同一条连接的握手与后续帧落到同一台后端，否则握手成功后流量被转到别的机器会直接失败。第二层是跨机投递：用户 A 和用户 B 可能挂在不同服务器上，需要 Redis Pub/Sub 或 NATS 作为消息底板做扇出，每台服务器只投递本地连接的消息。同时把"用户 → 所在服务器"的映射写进带 TTL 的 Redis 键，进程崩溃后可自动过期。Redis 的扇出吞吐约 10 万消息/秒，更大规模换 NATS JetStream 或 Kafka。
SSE 需要 POST 请求或自定义 Header 怎么办？EventSource 好像只支持 GET。
放弃 EventSource，改用 fetch + ReadableStream：POST 请求头可以带 Authorization 与任意自定义头，响应体用 getReader() 逐块读取，按 SSE 的文本格式手工切分（以空行分隔事件，解析 data:/event:/id: 字段）。这也是各家大模型 SDK 在浏览器端消费流式 API 的通用做法。代价是自动重连和 Last-Event-ID 也要自己实现，所以通常把这段逻辑封装成与 EventSource 语义一致的客户端类，并配上指数退避加抖动。
长轮询已经过时了吗？还有没有使用价值？
没有完全过时，但定位变成了兜底方案。它的优势是穿透性最强——任何能发 HTTP 的环境都能用，适合 WebSocket 握手被企业代理拦截、客户端环境极端受限的场景，socket.io 等框架至今保留它作为降级传输。劣势也明显：每次推送后要重新建请求，延迟与开销都高于 SSE 和 WebSocket。在 2026 年的技术环境下，新项目应默认在 SSE 与 WebSocket 之间二选一，长轮询只作为兼容性备胎出现在降级链路里。
