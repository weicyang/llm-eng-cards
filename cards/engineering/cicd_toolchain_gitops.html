工具选型看起来是在比功能清单，实际上是在选三样东西的归属：谁持有生产凭据、谁承担运维负担、以及"期望状态"记在哪里。GitOps 的全部价值可以压缩成一句话——把期望状态从流水线的执行日志里搬到版本库里，然后让一个常驻控制器持续负责让现实向它靠拢。前者是一次性动作，后者是一个闭环，这个差别决定了漂移能不能被自动纠正。

一、执行模型：控制平面与执行平面的分离

任何 CI 系统都可以拆成两层。控制平面负责响应事件、解析流水线定义、调度作业、维护状态、聚合日志、管理权限与密钥；执行平面就是真正跑构建命令的那台机器。把这两层分开看，几乎所有的成本、安全与网络问题都能被归位。

托管 runner 与自托管 runner

托管 runner 由平台方提供并维护，每个作业通常拿到一个干净的临时实例，按使用时长计费。自托管 runner 由你自己部署与维护。GitHub 官方对自托管 runner 的描述里有几条特别值得注意：它给你对硬件、操作系统与软件栈的完全控制，但你要负责操作系统和其他所有软件的更新；它本身免费但你承担机器成本；它不需要为每次作业执行都提供干净实例；它可以是物理机、虚拟机、容器、本地或云上，并且能注册在仓库、组织或企业三个层级。

"不需要干净实例"这一条是双刃剑。它带来速度（依赖、镜像层、编译缓存、模型权重都可以留在本地磁盘上复用），也带来两类风险：一是残留污染，上一个作业留下的文件、环境变量、全局安装的包会影响下一个作业，让构建结果不再只由代码决定，直接违反 ST27 · CI/CD 流水线原理与设计 第六章说的幂等要求；二是跨作业攻击面，一个作业若能在机器上留下东西，就可能读到下一个作业的凭据或篡改它的产物。所以公开仓库接受外部 PR 时，用自托管 runner 跑未经审核的代码是高风险配置。

托管 runner 卖的不是算力，是"每次都从干净状态开始"这个保证。自托管 runner 省下的时间，本质上是用放弃这个保证换来的——所以它适合可控的内部代码，不适合来源不可信的代码。

二、主流工具的架构差异与选型

四类工具的差别不在语法糖，而在谁维护控制平面、复用的单位是什么、以及扩容靠什么。

GitHub Actions：SaaS 控制平面 + 事件驱动 + 动作复用

控制平面完全托管，流水线由仓库事件驱动。复用的单位是action——一个可被引用的步骤封装，生态庞大。代价是这个复用单位同时也是供应链入口：引用第三方 action 等于在你的构建里执行别人的代码，所以必须按提交哈希固定版本而不是按可变标签引用（见第五章）。缓存是独立服务，有明确的容量配额与生命周期，超限后按最后访问时间驱逐——具体限额与缓存抖动的成因见 ST27 · CI/CD 流水线原理与设计第六章。

GitLab CI：与仓库一体，DAG 与产物是一等公民

stages 提供默认的串行分层，needs 则把流水线变成有向无环图，让作业只等它真正依赖的上游。官方明确支持三种常见形态（一对多的 fan-out、多对一的 fan-in、两者组合的菱形依赖），还支持完全省略 stages 的"无阶段流水线"，以及用 needs: [] 让 lint 与扫描类作业在流水线创建瞬间就启动。artifacts 与 cache 是两个语义清晰分开的关键字——前者是要传给下游作业或留存的产出，后者只是加速手段，这个区分在很多工具里是混的。

deploy:
  stage: deploy
  needs:
    - job: "test"
    - job: "test_optional"
      optional: true   # 该作业可能因 rules 不存在，避免流水线创建失败
  script: echo "Deploying..."

Jenkins：自运维控制器 + agent，插件即能力也即负担

Jenkins 的控制平面（controller）由你自己运维，作业跑在 agent（node）上。它把流水线定义写进项目仓库的 Jenkinsfile，官方称之为 Pipeline-as-Code，并列出四项收益：所有分支与 PR 自动获得构建流程、流水线改动可像代码一样评审、天然具备审计轨迹、成为流水线的唯一事实来源。语法有声明式与脚本式两种：声明式更易读写，脚本式更灵活。官方强调的能力里有两条是其他工具不太提的——流水线可以跨控制器的计划内与非计划重启存活，以及可以暂停等待人工输入或审批。这两条对长周期、需要合规审批的交付流程很实用。

它的真实成本在插件生态。能力来自插件，但插件的版本兼容性、安全公告、升级顺序、以及控制器本身的单点与备份，全都是你的运维工作量。选 Jenkins 的前提是团队愿意把它当一个需要长期照料的生产系统。

Argo Workflows 与 Tekton：把流水线做成 Kubernetes 资源

Tekton 以扩展形式装进 Kubernetes 集群，流水线的构造块就是一组自定义资源，安装后可以像操作 Pod 一样用 kubectl 或 API 操作。核心四个概念的关系很清晰：Task 定义有序的 Step 序列，Pipeline 定义有序的 Task 序列，TaskRun 与 PipelineRun 分别是它们的一次实例化执行。扩容方式是给集群加节点，不需要重新规划流水线的资源分配。

但官方点明了一个必须提前知道的约束：每个 Task 在自己独立的 Pod 里执行，因此 Pipeline 内的 Task 默认不共享数据，要传数据必须显式配置每个 Task 把输出暴露出来、下游 Task 再把它当输入摄入。这条约束对习惯了"同一个工作目录里一路跑下去"的人是最大的心智落差，也是把已有脚本迁到 Tekton 时返工最多的地方。此外官方建议配好持久卷声明、权限与镜像构建推送所需的存储。Tekton Chains 负责为构建产物生成、存储与签名来源证明，正好衔接第五章。

三、GitOps：声明式期望状态与持续 reconcile

GitOps 有两条主张，缺一条就不是 GitOps。第一条是期望状态以声明式形式存放在版本库中，版本库是唯一事实来源；第二条是有一个常驻控制器持续比对实际状态与期望状态，并主动收敛差异。第二条才是分水岭：把 YAML 放进 Git 然后在流水线里执行一次应用命令，只满足第一条，那仍然是传统的推式部署。

传统部署是一个动词：我"执行"了一次上线，结束了。GitOps 是一个形容词：系统"处于"期望状态，控制器永远在负责这件事。差别体现在有人手改了集群之后——前者要等下次发布才可能被覆盖，后者会主动把它拉回来。

推模型与拉模型的本质区别：凭据在哪一侧

推模型里，CI 流水线持有生产集群的访问凭据，构建完成后主动把变更推进集群。拉模型里，集群内的控制器主动去拉版本库，凭据从不离开集群。Argo CD 官方在讲自动同步时明确说出了这条收益：启用自动同步后，CI/CD 流水线不再需要直接访问 Argo CD 的 API 服务器来执行部署，流水线只需要向被跟踪的版本库提交并推送清单变更。

这个差别的实质是攻击面的大小。推模型下，每一条有权部署的流水线、每一个能改流水线定义的人、每一个被引用的第三方动作，都在生产集群凭据的爆炸半径内。拉模型把这个半径收缩到"谁能合并进版本库"，而这件事本来就有成熟的评审与保护机制。

Argo CD 的同步语义：默认值都偏保守，必须逐项确认

这一节的细节值得逐条记住，因为几乎每条默认值都与直觉相反，而误解的后果是"我以为它会自动纠偏，结果它没有"。官方文档给出的语义包括：

  • 只有 OutOfSync 才同步。处于 Synced 或错误状态的应用不会尝试自动同步。
  • 同一组合只尝试一次。每个唯一的提交哈希与应用参数组合只会尝试一次同步；如果历史上最近一次成功同步已经针对同样的哈希与参数执行过，就不会再同步——除非开了 selfHeal。
  • 失败不自动重试。针对同一提交哈希与参数的同步若曾失败，不会再次尝试，除非显式配置了 retry（支持 limit、指数退避的 duration/factor/maxDuration）。
  • 自动裁剪默认关闭。作为安全机制，自动同步默认不会删除已从版本库移除的资源，需要显式开 prune。
  • 空目标默认被拒。即使开了 prune，当目标资源为空时仍会被保护机制拦住，防止自动化或人为错误把应用清空，要允许则需 allowEmpty。
  • 自动纠偏默认关闭。selfHeal 不开的话，对活动集群做的手改不会触发同步；开了之后，偏离会在 self-heal 超时（默认 5 秒）后被拉回。
  • 开了自动同步就不能回滚。官方明确写出：无法对启用了自动同步的应用执行回滚——因为控制器会立刻把它拉回版本库声明的状态。回滚必须通过改版本库来表达。
  • 周期由配置项决定。自动同步间隔取自 argocd-cm 里的 timeout.reconciliation，默认 120 秒，另加 60 秒抖动，最长约 3 分钟。
spec:
  syncPolicy:
    automated:
      prune: true      # 默认 false：不开则删掉的资源会留在集群里
      selfHeal: true   # 默认 false：不开则手改不会被纠偏
    retry:
      limit: 5
      backoff: { duration: 5s, factor: 2, maxDuration: 3m }

示例场景：某团队把部署迁到 GitOps 后仍然出现环境漂移，排查两周未果。根因是三条默认值的叠加：selfHeal 没开，所以运维为救火直接改的副本数与环境变量从未被拉回；prune 没开，所以三个月前从版本库删掉的旧 Service 与 ConfigMap 一直留在集群里并仍在被引用；而由于同一提交哈希只同步一次，团队"重新点一下同步"也不会有任何动作，进一步坐实了"GitOps 已经在管了"的错觉。修正只是在同步策略里补上 prune 与 selfHeal 并配好 retry，随后一次 reconcile 就清出了 11 个孤儿资源、纠正了 4 处手改。（本例为构造的典型场景，用于说明保守默认值的实际后果，非实测数据。）

应用之上再套应用

当被管理的应用达到几十上百个，逐个手工创建就成了新的手工操作。app of apps 模式的做法是：用一个 GitOps 应用去声明其他一批应用，于是"新增一个服务"也变成一次版本库提交。它把 GitOps 的递归性用到了自身的管理上——连"有哪些应用"这件事本身都变成声明式的。Argo CD 还提供 ApplicationSet 用生成器批量产出应用，并支持渐进式同步。

Kubernetes 上具体用 Helm 还是其他打包方式、以及与平台型产品的取舍，见 S06 · K8s 部署痛点与 Porter 解决方案；平台层的整体分层设计见 S04 · AI 平台设计。本卡只负责 reconcile 与漂移纠偏这套机制本身。

四、基础设施即代码：Terraform 与 Ansible 的两种范式

两个工具经常被并列提及，但它们回答的是不同问题：Terraform 管资源的生命周期（云上的对象该不该存在），Ansible 管已有机器的内部状态（机器里的东西该是什么样）。混用不当的典型症状是用 Ansible 去创建销毁云资源，然后失去了"当前应该有哪些资源"的账本。

Terraform：状态文件是它的账本，也是它的风险点

状态文件是 Terraform 记录"我管过哪些真实资源"的账本，没有它 Terraform 无法知道该更新还是该新建。Terraform 官方对状态的定位说得很清楚：状态的首要目的是存储远端系统中的对象与配置中声明的资源实例之间的绑定关系。它创建一个远端对象时，会把该对象的身份记在对应的资源实例名下，后续的更新与删除都依赖这条绑定。Terraform 在任何操作前会先做一次刷新，用真实基础设施更新状态，再据此决定要做哪些变更。

围绕状态有几条来自官方的硬约束，踩了都很疼：

  • 状态是 JSON 文本文件，但不要直接编辑，要用 terraform state 子命令做修改，因为命令行会屏蔽格式变化。
  • 默认存本地（terraform.tfstate 加一份 .backup），这限制协作且有丢失风险，官方建议放远端后端。
  • 不要把状态放进版本控制系统或任何不支持状态锁与安全访问控制的存储，官方给的理由是可能导致数据丢失或状态文件里的密钥泄露。这一条常被违反，因为"它是个文本文件"看起来很像该进 Git 的东西。
  • Terraform 期望资源实例与远端对象一一对应。用 terraform import 导入外部创建的对象、或用 terraform state rm 让它"忘记"某个对象之后，这个一一对应关系就要由你自己保证。

plan/apply 分离：变更评审的抓手

把"算出要改什么"和"真的去改"拆成两步，是基础设施变更能被评审的前提。plan 阶段产出一份可读的变更集（新增、修改、销毁各多少、具体哪些字段），这份东西才是评审对象——评审 HCL 源码只能看出意图，看不出"这次改动会重建那台数据库"。官方还提供 terraform show -json 与 terraform output -json，典型用法是在自动化里成功 apply 之后立刻执行，把结果作为该次运行的制品留存，供其他软件消费而不必自己去跑 Terraform。

放进流水线时有一条纪律：apply 必须消费 plan 阶段保存下来的那份 plan 文件，而不是重新计算一次。否则评审通过的是 A 变更集，执行的可能是 B——在两次运行之间基础设施发生了变化，这和 ST27 第三章"不可变制品"要解决的是同一类问题。

plan 之于基础设施，等价于制品之于应用：它是那个被评审、被批准、被执行的不可变对象。重新计算一次 plan 就等于重新构建一次制品，评审结论随之失效。

Ansible：收敛式配置，但幂等不是免费的

Ansible 的执行是过程式的（按顺序跑任务），但它的模块是围绕最终状态设计的。官方在"期望状态与幂等性"一节的原话是：大多数 Ansible 模块会检查期望的最终状态是否已经达成，若已达成就不执行任何动作直接退出；重复执行该任务不会改变最终状态，这样的模块被称为幂等的。紧接着有一句同样重要的限定——并非所有 playbook 和所有模块都是这样的行为，不确定时应先在沙箱里反复执行验证。

模块开发指南进一步给出了这个范式的设计原则：实现声明式操作而非增删改查，让用户可以忽略现状只关心最终状态（用 started/stopped、present/absent 这样的取值），并且力求一致的最终状态——如果同一模块连续执行两次会得到两种不同状态，就应该重新设计。

实践中破坏幂等的头号来源是 command 与 shell 任务：它们默认每次都执行，也无法可靠地判断自己是否造成了变化。补救手段是加 creates/removes 守卫（目标文件已存在就跳过）或用 changed_when 基于输出显式判定。验证方法极其简单，也应该写进流水线：连续跑两遍，第二遍必须报告零变更。这一条比任何代码评审都更能抓出伪幂等。

五、凭据与供应链安全

流水线是一个天然的高价值目标：它有生产环境的写权限、能修改即将上线的产物、而且执行的是大量来自外部的代码。这一章讲三件事——怎么不再存长期密钥、攻击面在哪里、以及怎么证明制品来源。

长期密钥的四个固有问题

把云凭据存成 CI 密钥是最常见的做法，也是最难修补的做法。GitHub 官方在讲 OIDC 时点出了症结：使用硬编码的密钥要求你先在云厂商侧创建凭据，然后在 CI 里复制一份。由此产生四个问题：凭据同时存在于两个系统（泄露面翻倍）；它不会自己过期，泄露后在被人工吊销前一直有效；轮换需要跨两个系统协同，于是实际上很少真的轮换；为了少配几次，作用域往往被开得比实际需要大得多。

OIDC：把"长期密钥"换成"每次作业现换的短期令牌"

OIDC 的流程是：你先在云厂商侧建立信任关系，声明哪些工作流可以代表哪个云角色申请访问；作业每次运行时，平台的 OIDC 提供方自动生成一个该次作业独有的 JWT，里面带着多项声明用以构成一个可验证的身份；作业把这个令牌出示给云厂商，云厂商校验声明是否匹配预先配置的信任条件，通过则换出一个只在该次作业期间有效、随后自动过期的短期访问令牌。

关键在于令牌里的声明足够细，使得信任条件可以写得很紧。官方示例中的声明包括 sub（如 repo:octo-org/octo-repo:environment:prod）、repository、repository_owner、ref、environment、runner_environment，以及 job_workflow_ref（指明具体是哪个工作流文件的哪个引用）。这意味着你可以把云角色限定到"只有 main 分支上的 prod 环境作业可以扮演"。有一个演进细节要注意：2026 年 7 月 15 日之后创建的仓库使用包含所有者与仓库数字 ID 的不可变 sub 格式，写信任条件时要按新格式来。此外，组织与企业管理员可以把仓库自定义属性作为 repo_property_* 前缀的声明注入令牌，从而做基于属性的访问控制，而不必维护硬编码的白名单。

最小权限：先收紧流水线自己的令牌

容易被忽略的是 CI 自带的那个仓库令牌。它的默认权限往往比需要的宽，而流水线里执行的任何代码（包括第三方动作）都能拿到它。做法是在工作流里用 permissions 显式声明，默认全部收到只读，按作业按需放开——要用 OIDC 就得给 id-token: write，要评论 PR 就给 pull-requests: write，仅此而已。

permissions:
  contents: read      # 默认收窄到只读
  id-token: write     # 仅为换取 OIDC 令牌
  pull-requests: write

制品签名与来源证明

来源证明记录一个制品是由谁、用什么流程、以什么输入构建出来的。SLSA 把这件事组织成一条构建轨道，级别递进的逻辑非常清晰，值得当成路线图直接用：

级别要求防住的威胁落地动作
Build L0无无——
Build L1存在来源证明，描述构建平台、构建过程与顶层输入，并分发给消费者失误与流程偏差（如从不在上游仓库的提交构建）构建时产出 provenance 并随制品发布；证明此级别可以不签名、可不完整
Build L2构建在专用基础设施（非个人工作站）上运行，来源证明由该平台生成并签名；消费者验证证明的真实性构建之后的篡改迁到托管构建平台，开启签名与验证
Build L3平台实现强隔离：不同运行之间不能互相影响（即使同项目），且签名密钥不可被用户定义的构建步骤访问构建期间的篡改（内部威胁、凭据被盗、同租户攻击）需要对构建平台本身做改造，通常是平台团队的工作

两个容易误解的点。第一，L1 的价值不在防篡改——官方直言 L1 的证明"很容易被绕过或伪造"，它的价值在于让调试、补丁、重建、盘点变得可能，以及防住发布流程中的失误。第二，签名解决的是"构建之后有没有被换掉"，而"构建过程中有没有被下毒"要到 L3 才有保障，这两件事常被混为一谈。

实现上，无密钥签名（keyless signing）与 OIDC 是同一套思路的延伸：用工作流的 OIDC 身份换取一张短期签名证书，签完即弃，避免长期私钥的保管与轮换问题，签名记录进公开的透明日志以便事后验证。Tekton 用户可以直接用 Tekton Chains 生成、存储并签名构建产物的来源证明。

签名回答"这个制品是不是我发出去的那个"，来源证明回答"它当初是怎么被造出来的"。只有签名没有证明，你能确认它没被换过，却说不清它本来该是什么样。

六、可观测与治理：度量、审计与成本

DORA 的度量已从四项演进为五项

DORA 度量是一组用于评估软件交付表现的指标，由长期的研究项目提出并持续修订。很多资料仍在讲"DORA 四项关键度量"。按 DORA 官方当前的表述，这套指标已经从最初的四项演进为五项模型，并且其中一项发生了实质性替换：原来的平均恢复时长（MTTR）被失败部署恢复时长取代。五项按两组归类：

分组指标官方定义数据来源
吞吐变更前置时间一个变更从提交进版本控制到部署进生产所花的时间提交时间戳 + 部署记录
吞吐部署频率给定周期内的部署次数，或两次部署之间的间隔部署事件流
吞吐失败部署恢复时长从一次失败且需立即干预的部署中恢复所需的时间部署事件 + 事件响应记录
不稳定变更失败率部署后需要立即干预（很可能是回滚或热修复）的部署占比部署记录 + 回滚/热修标记
不稳定部署返工率非计划的、因生产事件而发生的部署占比部署记录 + 事件关联

官方还给出了一条反复被研究验证的结论，对说服"要不要为了稳定性牺牲速度"这类争论很有用：速度与稳定性不是取舍关系，多数团队身上这些指标是正相关的，高绩效者五项都好，低绩效者五项都差。文中引用的一句话把这层意思说得更狠：真正的长期取舍是"更好的软件更快"与"更差的软件更慢"之间的取舍。

这五项不是打分表，是一副听诊器。它们的用途是定位你自己的瓶颈并观察它是否在改善，而不是拿去和别的团队比高低——官方把"竞争"和"跨异构应用比较"都明确列进了误用清单。

度量的误用清单

官方的常见陷阱一节几乎每条都对应一种真实的组织病症，照单避坑比自己摸索便宜得多：

  • 把指标设成目标。"年底前所有应用必须日均多次部署"这类宣告会触发古德哈特定律，团队会去优化数字而不是优化交付。
  • 迷信单一指标。复杂系统需要多个指标，而且其中应该存在健康的相互张力（吞吐与不稳定正好构成这种张力）。
  • 拿行业当挡箭牌。以"我们是强监管行业"为理由拒绝改变现状。
  • 做不可比的比较。这些指标适用于单个应用或服务；拿移动应用和主机系统比会得出误导性结论。把多个团队甚至整个组织的指标混合平均同样有问题，因为上下文不同。
  • 指标孤岛化。五项指标应该在开发、运维、发布团队之间共享；只让某个团队背某个指标会产生摩擦和互相指责。
  • 只顾测量不顾改进。为了拿到精确数据去搭建一堆系统集成，初期投入可能不值得——先用对话、快速自查和现成工具起步。

审计追溯：把三段证据链接起来

一次合格的审计要能回答"谁在何时把哪个提交的哪个制品放进了哪个环境，依据是什么"。这需要三段证据能互相对接：流水线即代码提供"当时的流程是什么样"（定义在版本库里，有历史有评审）；来源证明与签名提供"这个制品是怎么造出来的、有没有被换过"；部署记录（GitOps 下就是版本库的提交历史）提供"什么时候生效的、谁批准的"。三段缺任意一段，链条就断在那里。GitOps 在这件事上有个额外好处：回答"生产现在跑的是什么"只需要看版本库的当前提交，不需要去翻流水线运行历史或登录集群查。

审计证据链：三段必须能对接，断一段就查不下去 【流程侧】版本库里的流水线定义 谁在何时改了门禁规则 → 有 PR、有评审、有历史 │ 产出 ▼ 【制品侧】制品 + 签名 + 来源证明 从哪个提交、哪个平台、哪些输入构建 → SLSA Build L1/L2/L3 │ 被部署 ▼ 【运行侧】部署记录（GitOps 下 = 版本库提交历史） 哪个摘要、进了哪个环境、何时生效、谁合并的 问："上周四那次故障，线上跑的是什么？" GitOps：查当时版本库的提交 → 摘要 → 证明 → 构建用的提交 传统推式：翻流水线日志，且日志可能已过保留期

示例场景：某团队的 CI 账单在三个月内翻了 2.4 倍，排查后发现三个独立原因各占一部分：一是给单元测试配了操作系统与语言版本的三乘四矩阵，共 12 个组合全量跑在每次推送上，而其中 9 个组合从未发现过独有缺陷；二是把编译产物（每次约 1.8 GB）写进通用缓存，很快撞上单仓 10 GB 上限，之后缓存进入持续创建又被驱逐的抖动状态，既付了上传时间又几乎零命中；三是 PR 产物没有保留策略，累积了两年。治理后矩阵在推送时缩到 2 个关键组合、其余转为每晚定时执行，编译产物改挂持久卷，PR 产物保留期设为 7 天，月度账单回落到原水平的 1.1 倍。（本例为构造的典型场景，用于说明成本项的分解方式，非实测数据。）

  • 不要把不可信输入（PR 标题、分支名）直接插值进 shell 脚本
  • 不要以为放了 YAML 进 Git 就是 GitOps，没有 reconcile 就只是推式部署

Q&A

什么时候该用自托管 runner，什么时候不该？

该用的情形有三类：需要访问内网资源（内部数据库、私有制品库、受限 API），托管 runner 要打通网络反而更复杂；需要特殊硬件（GPU、大内存、特定 CPU 架构）；以及大体积依赖或产物需要复用本地磁盘缓存，远端缓存的上传下载开销已成瓶颈。不该用的情形最重要的是一条：公开仓库接受外部 PR 时。GitHub 官方明确说明自托管 runner 不需要为每次作业执行提供干净实例，这意味着一个作业能在机器上留下东西，从而读取后续作业的凭据或篡改其产物。执行来源不可信的代码必须走每次全新的托管实例。另外要记住自托管的隐性成本：操作系统与全部软件的更新维护由你负责，这笔长期支出通常比省下的分钟费用更可观。

把 YAML 放进 Git，然后在流水线里执行一次 apply，这算 GitOps 吗？

不算，它只满足了 GitOps 两条主张中的第一条。第一条是期望状态以声明式形式存放在版本库里，版本库是唯一事实来源；第二条是有一个常驻控制器持续比对实际状态与期望状态并主动收敛差异。差别体现在有人手改了集群之后：只有流水线一次性执行的方案，这个手改要等到下一次发布才可能被覆盖，而且如果那次发布的清单没碰到被改的字段，它会一直留着；有控制器持续 reconcile 的方案会在秒级把它拉回来。另一个实质差别是凭据位置——流水线执行 apply 意味着 CI 系统持有生产集群凭据，而拉模型下凭据不出集群，Argo CD 官方把这条列为自动同步的直接收益：流水线不再需要直接访问部署系统的 API，只需要向版本库提交推送。

为什么 Argo CD 开了自动同步，集群里的手改还是没被纠正？

因为自动纠偏是一个独立的开关，默认关闭。官方文档写明：默认情况下，对活动集群所做的改动不会触发自动同步，需要显式设置 selfHeal: true；开启后偏离会在 self-heal 超时（默认 5 秒）之后被拉回。还有一条相关语义加重了这个错觉——自动同步对每个唯一的提交哈希与应用参数组合只会尝试一次，如果最近一次成功同步已经针对同样的哈希执行过，就不会再同步，除非开了 selfHeal。所以团队"手动点一下同步"也可能毫无动作，看起来像是系统认为一切正常。同一类问题还有两个：自动裁剪（prune）默认关闭，所以从版本库删掉的资源会继续留在集群里；空目标保护（allowEmpty）默认关闭，防止误把应用清空。这几个默认值都偏保守，上线 GitOps 时应当逐项确认而不是假设。

Terraform 和 Ansible 是竞品吗，该怎么分工？

不是竞品，它们管的是不同层次。Terraform 管资源的生命周期——云上的对象该不该存在，靠一个显式的状态文件维护"配置里声明的资源实例"与"远端真实对象"之间的一一绑定，所以它天然知道该销毁什么。Ansible 管已有机器的内部状态——机器里装了什么、服务是否在跑、配置文件内容是什么，它每次现场探测目标机器，没有账本。分工的实践判据是：创建和销毁云资源用 Terraform，机器内部状态收敛用 Ansible。用 Ansible 去创建销毁云资源的典型后果是失去"当前应该有哪些资源"的账本，孤儿资源无从发现。两者的核心风险也不同：Terraform 的风险集中在状态文件（丢失、泄露、与现实脱钩），Ansible 的风险集中在 command 与 shell 任务打破幂等。

Ansible 号称幂等，为什么我的 playbook 跑两遍结果不一样？

因为幂等是模块级别的属性，不是框架保证。官方原话是"大多数模块会检查期望的最终状态是否已达成，若已达成就不执行任何动作直接退出"，紧接着就加了限定：并非所有 playbook 和所有模块都是这样的行为，不确定时应先在沙箱反复执行验证。破坏幂等的头号来源是 command 与 shell 任务，它们默认每次都执行，也无法可靠判断自己是否造成了变化。补救办法是加 creates 或 removes 守卫让目标已存在时跳过，或用 changed_when 基于命令输出显式判定变更。另一类来源是模块用法不当，比如用 state: restarted 而本意只是"确保在跑"——官方对 systemd 模块的说明写得很清楚，started 和 stopped 是幂等的，而 restarted 每次都会重启服务。验证方式极简单也该写进流水线：连续跑两遍，第二遍必须报告零变更。

OIDC 到底解决了长期密钥的什么问题？

长期密钥有四个固有问题，OIDC 逐个消除。第一，长期密钥必须在云厂商侧创建后再在 CI 里复制一份，同一份凭据存在于两个系统，泄露面翻倍；OIDC 不存储任何凭据，每次作业现换。第二，长期密钥不会自己过期，泄露后到人工吊销前一直有效；OIDC 换出的令牌只在单次作业期间有效并自动过期。第三，轮换需要跨两个系统协同，于是实践中常年不换；OIDC 每次运行天然轮换。第四，为了少配几次，长期密钥的作用域往往开得过宽；OIDC 令牌携带 sub、repository、ref、environment、job_workflow_ref 等细粒度声明，云侧信任条件可以精确到"只有 main 分支上 prod 环境的这个工作流文件可以扮演该角色"。附带收益是审计——长期密钥只能告诉你"某个密钥被用了"，OIDC 令牌的声明能追溯到具体的工作流与运行。

制品签名了，是不是就不用担心供应链攻击了？

不是，签名只覆盖了其中一段。按 SLSA 构建轨道的划分：Build L1 只要求来源证明存在，官方直言这个级别的证明很容易被绕过或伪造，它的价值在于让调试、重建、盘点变得可能以及防住发布流程中的失误，不是防篡改。Build L2 要求构建跑在专用基础设施上、来源证明由该平台生成并签名、消费者验证其真实性，它防住的是构建之后的篡改。而构建过程之中被下毒（内部威胁、凭据被盗、同租户攻击）要到 Build L3 才有保障，其要求是平台实现强隔离：不同运行之间不能互相影响，即使同一项目内也不行；并且签名所用的密钥材料不能被用户定义的构建步骤访问到。所以签名回答的是"这个制品是不是我发出去的那个"，而"它当初是不是被正确地造出来的"是另一个问题。除此之外还有独立于签名的攻击面需要单独防：流水线表达式注入、第三方动作用可变标签引用、依赖投毒、缓存污染。

DORA 是四项还是五项指标，MTTR 还用吗？

按 DORA 官方当前的表述是五项，并且指标集合确实随技术环境演进过——官方专门写了一篇"DORA 软件交付指标的历史"来解释这些变化，其中包括从 MTTR 转向失败部署恢复时长。五项分两组：吞吐组包含变更前置时间（从提交进版本控制到部署进生产）、部署频率（周期内部署次数或两次部署间隔）、失败部署恢复时长（从一次失败且需立即干预的部署中恢复所需时间）；不稳定组包含变更失败率（部署后需立即干预、很可能导致回滚或热修的部署占比）与部署返工率（非计划的、因生产事件而发生的部署占比）。替换 MTTR 的意义在于口径更明确：它只度量"因部署失败而需要恢复"这一类情况，而不是笼统的所有故障恢复时间，这让它与另外四项处在同一个"围绕部署"的语义框架里，也更容易从部署事件流里客观采集。

CI 账单涨得很快，该从哪里查？

按五个成本项逐项分解，实践中问题几乎总出在前三项。第一是执行时长，常见原因是每次推送都跑全量、以及矩阵构建的组合爆炸——检查方法是统计每个矩阵组合历史上独有地发现过多少缺陷，长期为零的组合应当从推送触发降级为定时执行。第二是缓存存储，典型错误是把大体积产物塞进通用缓存，撞上配额后进入抖动状态，既付了上传时间又拿不到命中收益（限额数字与成因见 ST27 第六章）。第三是制品存储没有保留策略，构建产物永久堆积，应当按环境分级：生产制品长期留存，PR 产物数天即清。剩下两项是专用算力（GPU 预留闲置或按需冷启动）与出网流量（大镜像跨区拉取），在 AI 项目里往往反超前三项成为主项。
