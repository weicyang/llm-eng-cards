ST25 · AI 编程稳定交付工作流

Git 检查点 / AGENTS.md 项目说明书 / MVP 边界 / Demo 决策 / 自测插件 / 人工验收

AI 写得出代码，不代表它交得出你想要的产品。稳定交付靠的不是更长的一句 prompt，而是把「做什么、怎么做、怎么验」外置成可回滚的工程闭环。

一、一句话交付为什么对不齐

视频开场就把常见幻觉拆开：装上 Codex（OpenAI 的编程 Agent，可用 ChatGPT 套餐或第三方模型驱动）或 Claude Code，发一句「给我做个电子书阅读器」，模型确实能吐出可运行的东西。真正的问题在后面——交付物跟脑子里的产品是不是同一件？bug 多不多？方向偏了能不能退回来？

马克用「马克阅读」做演示：从空目录走到能导入 TXT 的阅读器。全程刻意不用 Codex 独有功能，逻辑对 Claude Code、Pi、OpenCode 同样成立。选型上他建议默认 Codex：功能短板少，不跟 GPT 强绑定，DeepSeek / GLM / Kimi 都能接。

做法你得到什么你失去什么
一句话直接实现快，几十分钟有界面边界不清、难回滚、人沦为测试员
先规格再实现方向可对齐、每步可回退前期多花一轮讨论
规格 + 自测 + 人验可验收的 MVP必须给 Agent 验证环境
视频里第一次启动就报错「操作失败请稍后重试」——即便 Agent 自称测过，人工点一次仍然会炸。这不是偶发，而是「模型自测覆盖率 ≠ 产品可用」的硬证据。

对齐预期的成本，必须花在写代码之前：边界没钉死，后面每一轮修改都在放大偏差。

二、环境：Git 与 AGENTS.md

环境只做两件事，而且建议所有项目都做：用 Git（按功能保存版本快照、支持一键回退的版本管理）托管目录；再写一份 AGENTS.md（给编程 Agent 读的项目说明书，新会话优先加载）。视频里两条硬规则写进说明书：每次改动必须 commit；交付前必须更新测试并跑通。

环境一次性搭好（之后每个功能复用） 空目录 "马克阅读" │ ├─ git init → 每个功能一个检查点 └─ AGENTS.md ├─ 规则1: 每次改动必须 git commit └─ 规则2: 交付前测试/验收必须通过 人 ──prompt──► Agent ──改代码──► 自测 ──通过才 commit │ └─ 失败 → 带着错误继续修，不把半成品交给人
环境件解决什么没有它会怎样
Git commit 纪律改坏了能退Agent 把能跑的功能改残，无处可回
远端仓库（可选）本地丢失可拉回机器挂了，劳动成果归零
AGENTS.md新会话不必重讲规范每开一轮都忘记「要测、要提交」
AGENTS.md 不是给人类看的 README。它是跨会话的冷启动上下文：Agent 每次开工先读背景和规范，相当于把「团队约定」从聊天记录里抽出来，变成稳定输入。

Git 管「改坏了怎么办」，AGENTS.md 管「新会话还记不记得规矩」——两者都是把记忆移出聊天窗口。

三、产品设计：先钉死 MVP 边界

MVP（Minimum Viable Product，最小可用产品：第一版只做主流程，其余以后再加）是这期视频的产品方法论。马克先问 AI「第一版做什么合适」，再逐条砍：EPUB 改 TXT、砍目录章节、只留明亮主题、书签后置。AI 补充了编码仅 UTF-8、只做纵向滚动、大文件要提示。共识成型后再让它写一份「不用太详细」的产品设计文档，当作后续开发和实现的底稿。

AI 建议人的裁剪原因
导入 EPUB只支持 TXT格式解析会把 MVP 做肥
目录 / 章节不做纯文本没有稳定可解析结构
明亮 / 护眼 / 深色只做明亮主题不是主流程
书签后置非必要功能
分页阅读先纵向滚动分页会引入排版复杂度

Demo 什么时候值得做

视频用「个人知识库」HTML 演示 Demo（只做可点的前端，后端数据全是假的，用来验交互）：左栏文档、中间推荐问题、右侧引用原文。好处有两件——文字想不出的交互问题，一点就暴露；后面实现时可以把 Demo 当视觉规格交给 Agent。但马克明确说：后端成本低的项目（阅读器导入 TXT）专门做一遍 Demo 是重复劳动，不如直接做真产品再改。

要不要做 Demo？看后端实现成本 后端成本高（检索 / 模型调用 / 知识库） → 先做假数据前端 Demo → 改到顺手 → 再实现后端 后端成本低（读 TXT、本地工具） → 跳过 Demo，直接实现，在真产品上改 判断标准不是"想不想看界面"，而是"做错了重做有多贵"
知识库类产品后端通常包含解析、切片、检索策略和模型调用，做错交互再推倒的成本远高于先画一个假页面。阅读器则相反：导入 TXT 的逻辑很薄，Demo 的时间还不如直接跑起来。

产品设计的产出不是「功能清单越长越好」，而是一份全员（包括 Agent）共用的「做什么 / 先不做什么」边界文件。

四、技术方案：新开会话还是接着聊

规格确认后进入技术设计。马克的经验是：顶级模型加上下文压缩，单会话连续跑几小时往往没问题；但为了让讨论聚焦，技术方案仍建议新开一轮，先读产品文档再聊技术栈。他抛出 Electron，模型认同并对比 Tauri，最终落到 Electron + React + TypeScript + Vite + Electron Forge，再把方案写进 docs/。

决策点继续当前会话新开会话
上下文产品讨论还在，少重复更干净，不容易被闲聊带偏
风险窗口变长，焦点可能漂要重新喂文档
视频选择实现阶段可接着跑技术设计特意新开，求聚焦
「我不是特别懂这块，只要大体方向没问题就行」——这是真人原话。技术方案的人设不是替模型写架构论文，而是挡住明显跑偏（比如为 TXT 阅读器上 Kubernetes）。

技术设计要的是方向锁，不是把每个类名都审一遍。人懂 60 分就够当裁判，剩下交给实现阶段的测试和人工点一点。

五、实现、自测与人工验收

写代码前先给 Agent 验证环境。Codex 至少装两个插件：Computer Use（操作本机应用的插件）和 Chrome（查看页面）。没有验证环境，人就会变成专职点按钮的测试员。指令很短：读产品文档和技术方案，按要求实现并提交。AGENTS.md 的第二条会迫使它测完再交。

单个功能的标准闭环（环境搭好之后） [产品设计] → 边界文档 ↓ [技术设计] → 技术栈 / 架构（可按重要性省略） ↓ [Agent 实现] → 自己跑测试 / 用插件点界面 ↓ 自称通过 [人工验证] → 真启动、真导入、真点一遍 ↓ 报错「操作失败请稍后重试」 [把错误原文丢回 Agent] → 再测 → 再点 ↓ MVP 可交
环节谁负责视频里的证据
写代码Agent按两份文档一次实现
自动化测试Agent（被 AGENTS.md 强制）自称测过再提交
真实启动人第一次 npm start 就报错
修 bug人提供现象，Agent 修把报错原文贴回去即修好
把 Computer Use / 浏览器插件交给 Agent，让它写完自己点；人只做最终验收和体验判断。
只让 Agent 写代码、自己当测试员来回找 bug。没有验证环境的 Agent，交付质量会系统性偏低。

自测降低的是「明显错误」的密度，不是「产品就是你想要的」的概率。最后一公里必须人走。

六、按复杂度取舍的三条硬原则

五个步骤里，环境是一次性的；之后每个新功能（例如给阅读器加全文搜索）仍走：产品设计 → 技术方案 → 实现自测 → 人工验证。但深度可以按「复杂度 × 重要性」缩放：简单且不重要的需求，产品/技术两步可整段交给 AI；复杂且重要的需求，人必须进场当裁判。

视频里「马克阅读」从失败的第一次启动到贴回报错后修好，用的就是这个缩放：MVP 边界已经写进文档，所以返工只修启动路径，不会重新发明 EPUB。下一轮加搜索、主题、书签时，仍然先问「这是不是还在 MVP 里」，而不是直接把愿望清单丢给模型。

需求类型产品设计技术设计人的掌控力
简单、不重要可省略可省略低，换速度
复杂、重要人参与裁剪人锁方向高，换质量
掌控力 ≈ 你愿意参加的设计环节数
速度 ≈ 你交给 Agent 的决策权
视频收束成三条不可省原则：① 必须有版本管理（Git，条件允许再加远端）；② 必须给 AI 自测能力；③ 必须人工验证。产品设计和技术设计做多细，没有固定标准，按这一单需求的风险来。演示里第一次 npm start 失败、贴回原文后修好，就是第 ②③ 条同时生效：自测漏了启动路径，人用真实现象把循环闭合。
这套流程是马克「现阶段」的方法，不是唯一标准。模型变强后，人进场的位置会后移，但回滚、自测、人验这三块短期内不会消失。把「一句话生成」当成默认，只适合可丢弃的草稿；一旦要稳定交付，文档和检查点就要先于代码存在。
落地时可以把三条硬原则写进仓库根目录：Git 钩子或 CI 负责第 ①② 条的一部分，人验收清单负责第 ③ 条。视频里的「马克阅读」只是载体——换任何带真实用户路径的产品，顺序仍然是：边界文档 → 实现 → 自测 → 人用一遍。

能省的是讨论深度，不能省的是回滚点、验证环境和最后亲自用一遍。

七、下一周就能用的检查清单

把视频流程收成仓库里能勾的条目，比再看一遍演示更有用。新项目第一天只做环境；第二天只做 MVP 文档；第三天才允许写实现。顺序反了，后面的自测和人验都会变成救火。

阶段必须留下的产物没有它会发生什么
环境Git 仓库 + AGENTS.md改坏无法回滚，规范随会话蒸发
产品一页 MVP：做什么 / 不做什么Agent 自行加 EPUB、主题、书签
技术独立会话产出的技术说明实现阶段被产品闲聊带着跑
实现可启动的提交 + 自测记录人去当测试员
验收人用真实文件点过一遍自动化绿灯掩盖启动失败
每个新功能重复「文档 → 实现 → 自测 → 人验」，即使功能很小。文档可以短到五条 bullet，但不能为零。
把五个步骤压进同一句 prompt，指望模型自己记住上周定的边界。压缩和开新会话后，没写进文件的东西等于没发生。

流程的最小单位是「带产物的阶段」，不是「又聊了半小时」。

Q&A

为什么不能只发一句「帮我做个阅读器」？
模型会做一个能跑的阅读器，但不保证是你要的那一个。没有 MVP 边界，它会自作主张上 EPUB、多主题、书签；没有 Git，改坏了退不回去；没有自测环境，人只能手工点 bug。视频的核心不是否定一句话生成，而是指出：对齐预期的工作必须发生在写代码之前，并用文档固定下来。
AGENTS.md 和 README 有什么区别？
README 给人看；AGENTS.md 给 Agent 的新会话做冷启动。视频里它只写了两条可执行规则——每次改动必须 commit、交付前测试必须通过。新开一轮时 Agent 会先读它，不必把「要提交、要自测」再说一遍。没有这份文件，规范只活在上一轮聊天里，压缩或新会话后就会丢。
什么时候必须做前端 Demo？
看后端推倒重来的成本。知识库涉及解析、检索和模型调用，交互做错再改后端很贵，值得先用假数据把界面点顺。TXT 阅读器后端很薄，专门做 Demo 是重复劳动，直接实现再在真产品上改更快。判断句是：做错了重做有多贵，而不是想不想先看一眼界面。
技术方案为什么要新开会话？
不是因为上下文一定爆掉。马克承认现在头部模型加压缩，单会话连跑几小时体感仍可。新开是为了让技术讨论更聚焦，避免被产品讨论的细节带着走。实现阶段则可以继续长跑。策略是：需要「换脑子」时新开，需要「接着干」时不换。
Agent 自测过了为什么还要人点？
视频里 Agent 按 AGENTS.md 跑完测试后第一次启动仍报错。自动化测试挡住的是它能想到的断言，挡不住启动路径、真实文件导入、交互体感。人把报错原文丢回去，它很快修好——说明人的价值是提供真实观察，不是替它写补丁。自测是必要非充分条件。
简单需求和复杂需求分别怎么走这套流程？
简单且不重要：环境已在的前提下，直接让 Agent 实现，人只做验证。复杂且重要：人要参加产品裁剪和技术方向锁定，再让 Agent 实现和自测，最后人验收。无论哪一档，Git、自测环境、人工验证三件套都不建议省。省掉的是你对中间决策的参与深度，换来的是速度，也换来更高的预期偏差概率。
Computer Use 和人工验收怎么分工？
视频把浏览器插件和 Computer Use 交给 Agent，让它写完自己点一遍；人只做最终体验判断。这样自测覆盖的是「能不能启动、文件能不能打开」，人覆盖的是「这是不是我想要的阅读器」。两者叠在一起，才是稳定交付；只留其中一层，要么漏启动错误，要么漏产品偏差。
