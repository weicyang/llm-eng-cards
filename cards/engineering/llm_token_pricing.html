ST24 · AI Token 计费机制

分词原理 → 输入/输出 Token → 为什么输出更贵 → 缓存命中机制 → 成本优化技巧

大模型计费像"双轨计价"：输入 Token 是起步价，输出 Token 是里程价——输出必须一个字一个字串行生成、全程占着 GPU，所以单价通常是输入的 3~4 倍；而缓存命中能让重复的输入前缀打到 1~2.5 折。

一、分词与 Token — 计费的起点

大模型只能处理数字，文本进入模型前需经分词器（Tokenizer）——负责把文字切成模型能理解的最小片段——切分成多个 Token，即模型读写文本的最小单位，也是 API 计费的最小单位。

  • Token 可能是一个字、一个词，也可能是标点符号
  • 切分规则基于统计规律——在海量文本中高频共同出现的片段更可能被合成一个 Token
  • 分词器通过查表（词表，即模型认识的全部片段清单）得到每个 Token 的编号，模型真正处理的是这些数字

一次 API 调用的计费维度

计费项含义单价特征
输入 Token你发给模型的文本（含系统提示词）基准价
输出 Token模型生成的回复文本通常为输入的 3~4 倍
缓存命中 Token与历史请求前缀重复的输入部分通常为输入的 0.1~0.5 倍

API 收费不按"字数"而按 Token 数——同样一句中文，在不同模型的分词器下切出的 Token 数可能差两三倍，账单也跟着差两三倍。

项目Token 数单价（DeepSeek）费用
输入（提示词 + 问题）2,0002 元 / 百万0.004 元

注意这个例子里输入是输出的 4 倍长，两者费用却打平——因为输出单价是输入的 4 倍。真实业务里输出往往是成本大头。

输入是"看题"，一次性扫完；输出是"答题"，必须逐字写。看题可以一目十行，答题只能一笔一划——这就是两者价差的根源。

三、为什么输出更贵 — 并行 vs 串行

输出 Token 比输入贵 4 倍的根本原因在于两个阶段的计算方式完全不同。输入阶段叫 Prefill（预填充），指模型一次性并行处理全部输入 Token 的阶段；输出阶段叫 Decode（解码），指模型逐个生成输出 Token 的自回归阶段——前一个没出来，后一个就确定不下来。

Prefill（输入） Decode（输出） ┌──────────────────┐ ┌──────────────────┐ │ T1 T2 T3 ... T2000│ │ t1 → t2 → t3 → ...│ └────────┬─────────┘ └────────┬─────────┘ ▼ 一次前向，全部并行 ▼ 每个 Token 一次前向 ┌──────────────────┐ ┌──────────────────┐ │ GPU 算力吃满 │ │ 每步只算 1 个 Token │ │ 吞吐高、单位成本低 │ │ GPU 大量空转等显存 │ └──────────────────┘ └──────────────────┘ 2000 Token ≈ 1 次计算 500 Token = 500 次计算

两个阶段的资源特征对比

维度Prefill（输入）Decode（输出）
计算方式所有 Token 一次并行处理逐个 Token 串行生成
GPU 利用率高（算力密集型）低（显存带宽瓶颈）
前向次数1 次输出多少个 Token 就多少次
对延迟的贡献首字延迟（TTFT）整体生成时长
单位成本低高（通常为输入 3~4 倍）

Decode 阶段每生成一个 Token 都要把整个模型的权重从显存重新"过"一遍，GPU 的算力大部分时间在等数据搬运，利用率远低于 Prefill。服务商为这部分低效计算收费更贵，是纯粹的成本传导。

Prefill 像"批发"，一次搬一车货，运费摊得薄；Decode 像"零售"，一件一件送货上门，每件都贵。

案例 · 电商智能客服的输出瘦身：背景：某客服机器人日均 10 万轮对话，回复平均 320 个输出 Token，充斥"很高兴为您服务"之类套话。问题：输出成本占总账单的 86%，且长回复让平均响应耗时达 3.4 秒。方案：约束回复为"结论 + 依据"结构化短答，设置 max_tokens=200，套话改由前端模板渲染。效果：平均输出 Token 降至 198（-38%），月度成本从 12,400 元降到 7,900 元（-36%），平均响应耗时降到 1.9 秒，满意度不降反升。

四、缓存命中机制

很多 AI 软件发给大模型的文本前面都有系统提示词，大部分时候是重复的。切分出来的 Token 跟上次一样，模型可以直接复用前面算过的中间结果，不需要重新计算——这就是缓存命中（Cache Hit），即本次请求的输入前缀与历史请求完全相同、可以直接复用已算结果的状态。业界把这项技术叫作 提示词缓存（Prompt Caching），即服务商对相同输入前缀复用 KV 计算结果并给予大幅折扣的计费机制。

状态说明价格（DeepSeek）
缓存命中前缀 Token 与上次相同，直接复用0.5 元 / 百万 Token
缓存未命中前缀变了，需要重新计算2 元 / 百万 Token

案例 · 固定系统提示词的缓存红利：背景：某法律咨询助手带 1,800 Token 的固定系统提示词，日均 10 万请求。问题：优化前提示词每次全价计费，仅输入一项每天就要 360 元（1.8 亿 Token × 2 元/百万）。方案：保持提示词一字不动、只变用户问题，把动态内容全部后置。效果：缓存命中率稳定在 92%，输入日成本降到约 112 元（-69%），每月节省约 7,400 元，首字延迟也因复用计算下降约 40%。

缓存就像餐厅的"预制菜"：前缀不变，厨房直接复用半成品上菜，又快又便宜；前缀一改，就得从洗菜重新做起，价格自然回到原价。

省钱三板斧：输入吃缓存、输出做减法、任务分路由——按"输出占比 → 缓存命中 → 模型路由"的顺序诊断，总能找到最大头的浪费。

Q&A

为什么大模型的输出 Token 比输入 Token 贵？
输入 Token 在 Prefill 阶段可以并行同时处理（一次性计算所有输入），GPU 利用率高、单位成本低。输出 Token 是自回归生成——必须一个一个 Token 往外蹦，前一个没出来，后一个就确定不下来，每生成一个 Token 都要跑一次完整前向。这导致输出阶段 GPU 大量时间在等显存搬运、利用率低，更慢也更吃推理资源，所以输出价格通常是输入的 3~4 倍，本质是服务商的成本传导。
什么是缓存命中？为什么它能大幅降低成本？
缓存命中是指当次请求的输入前缀与上次完全相同，模型可以直接复用之前已经算过的中间结果（KV 缓存），不需要重新计算。这在 AI 应用中非常普遍——系统提示词通常固定，每次请求都重复发送。由于省掉了重复计算，服务商对命中部分大幅打折，例如 DeepSeek 缓存命中价仅为正常输入的 1/4（0.5 vs 2 元/百万 Token），Anthropic 的缓存读取更是低至 0.1 倍。优化技巧：保持系统提示词一字不变，只改用户输入部分，并把易变内容放在请求末尾，让缓存持续生效。
一次 API 调用的账单是怎么算出来的？请举例说明。
账单 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价，缓存命中部分按折扣价单独计。以 DeepSeek 价格（输入 2 元/百万、输出 8 元/百万）为例：一次请求带 2,000 个输入 Token、模型回复 500 个输出 Token，输入费用 0.004 元、输出费用 0.004 元，合计 0.008 元。注意输入长度是输出的 4 倍，费用却打平，因为输出单价是输入的 4 倍——真实业务中输出往往是成本大头，优化要优先盯输出。
为什么系统提示词改一个字，整个缓存就失效了？
提示词缓存按"最长相同前缀"匹配：服务商会逐 Token 对比本次请求与历史请求，从第一个不同的 Token 开始，后面全部视为未命中、重新计算。系统提示词位于请求最前面，它一旦变化，哪怕只改一个字，其后的所有内容（包括本来没变的历史对话）都会失去缓存资格，单价直接从折扣价飙回原价。所以工程上要把最稳定的内容放在请求开头并冻结版本，把时间戳、用户名等易变内容挪到请求末尾。
流式输出（Streaming）能省 Token 费用吗？
不能。流式输出只是把生成结果一边算一边推给前端，改善的是用户感知的"首字延迟"，生成的 Token 总量一个都不会少，计费与非流式完全相同。它的价值在体验侧：长回复时用户不用干等几秒，可以边读边判断要不要提前中断。真想省钱，得从减少输出 Token（结构化短答、长度上限）和提高缓存命中率入手，流式只是"上菜更快"，不是"菜更便宜"。
从计费角度看，DeepSeek、OpenAI、Anthropic 的缓存策略怎么选？
三家的缓存折扣和触发方式差别明显：DeepSeek 自动缓存、命中价 0.25 倍，零配置即享折扣，适合提示词稳定的中文业务；Anthropic 缓存读取低至 0.1 倍输入价，折扣最深，但需要手动标记缓存断点、且首次写入要付 1.25 倍，适合前缀超长且高度重复的场景；OpenAI 自动缓存打 5 折、前缀需满 1024 Token，折扣温和但完全无感。选型时先算自己业务的前缀重复率：重复率越高，越值得为深折扣做手动配置。
为什么有些厂商还要对"缓存写入"额外收费？
因为缓存不是免费的：服务商要把首次计算出的中间结果（KV 缓存）保存在高速显存里一段时间，这部分显存资源有真实成本。以 Anthropic 为例，首次写入缓存按 1.25 倍输入价收费，之后在 TTL（默认 5 分钟）内的每次命中读取只收 0.1 倍。只要前缀在短时间内被复用超过约 2 次，写入成本就能被读取折扣覆盖；反之，如果前缀几乎不重复，开缓存反而更贵。所以缓存适合"高频重复前缀"，不适合一次性请求。
