监控 AI 代码生成，本质不是记录"发生了什么"，而是验证"Agent 声称做的"与"它实际做的"是否一致——声明可以撒谎，但文件事件、产物特征和 Token 账单不会。

一、为什么 Skill 调用不能靠传统日志

普通 API 的监控是成熟的：请求进来，参数校验、业务处理、返回响应，每一步都是确定性的，入口出口打两条日志、记一个延迟，出了问题基本能定位。但 Skill（Agent 按任务意图动态调用的能力单元，如"设计系统组件生成""代码审查"等封装好的技能包）调用完全是另一类负载——它的执行路径由 LLM 在运行时决定，传统"入口/出口"式日志拍下来的只是一张黑盒照片。

普通 API 调用（透明链路） Skill 调用（决策黑盒） ────────────────────────── ───────────────────────────────── 请求 ─► 参数校验 ─► 处理 ─► 响应 请求 ─► ┌───────────────────────┐ ─► 产物 │ │ │ │ LLM 意图判断 │ 每步有日志，延迟可测，路径固定 │ 读文档了吗？调工具了吗？ │ │ 写文件了吗？二次推理了吗？ │ └───────────────────────┘ 日志可见：输入 → 输出 日志可见：输入 → 输出 缺失：无 缺失：中间全部决策与动作

Skill 调用监控有三个特殊难点。第一是决策过程不透明：是否调用某个 Skill 取决于 LLM 的意图判断，可能出现"读了文档但未声明"，也可能出现"声明读了但实际没读"——Agent 的自述本身就是一种需要被验证的数据，而不是可信的事实。第二是执行边界模糊：一次 Skill 调用内部可能折叠了推理、文件读写、多次 LLM 调用、工具执行等十几个步骤，传统日志只能看到一次进出的轮廓。第三是跨系统追踪难：Skill 的执行横跨 LLM API、MCP 工具、文件系统、CI 流水线，缺乏统一的追踪标识，故障定位全靠猜。

维度普通 APISkill / Agent 调用
执行路径编译期固定，可静态分析运行时由 LLM 决定，非确定性
失败形态报错、超时、500，显性失败返回 200 但行为偏离目标，静默失败
日志可信度日志即事实Agent 声明 ≠ 事实，需交叉验证
单次调用粒度一次请求 = 一个操作一次调用 = 一个多步子任务
排查依据错误码 + 堆栈决策链回放 + 证据比对

这不是理论上的担忧。Gartner 预测到 2027 年底将有超过 40% 的 Agentic AI 项目被取消，调试基础设施不足是主要原因之一；业界也有真实案例：一个客服 Agent 一夜之间静默处理错了 2000 个请求，日志全部显示"成功完成"，下游系统却收到了损坏的数据。当"全部日志都是 200"与"行为正确"脱钩时，监控的目标就必须从记录状态升级为验证行为。

静默失败还有一笔隐性账：一次 Skill 调用内部往往折叠着 5~10 次 LLM 调用和若干工具执行，任何一步走偏都不是一次性报错，而是在无意义的重试与自我修正里反复烧 Token。一个失去观测的推理循环，可以在单次任务里消耗掉数倍于预算的 Token，最后交出的还是错误产物——日志盲区同时也是成本漏洞和质量暗坑，三者共用同一个根源。

时间尺度上还存在结构性错配：传统请求日志以"一次请求"为天然边界，生命周期以毫秒计；Skill 任务以"一次任务"为单位，可能横跨数分钟乃至更久，穿越多个进程与系统。如果日志不挂在同一个任务标识上，它们就像散落在十几个群聊里的对话碎片——每一片都真实，却拼不出完整的对话。这正是后文反复强调 trace_id 的原因：它不是可选的优化项，而是撑起整条证据链的骨架。

传统日志回答"系统还活着吗"，Skill 监控要回答"它刚才说的话是真的吗"——这是从体检到审计的差别。

二、结构化日志与四流证据交叉比对

基础方案的第一块基石是 结构化日志：不写自由文本日志，而是让每条日志成为带固定字段的 JSON 事件（trace_id、时间戳、事件类型、主体、载荷），这样才能被程序比对而不是被人眼阅读。但只有结构化还不够——任何单一来源的日志都可以缺失甚至伪造，所以第二块基石是 四流证据交叉比对：采集四条相互独立的证据流，用它们之间的对齐与矛盾来还原真相。

┌───────────────┐ │ Agent 声明 │ "我已阅读设计系统文档并遵循" └───────┬───────┘ │ ① 语义声明流 ┌─────────────────────┼─────────────────────┐ ▼ ▼ ▼ ┌──────────────┐ ┌───────────────┐ ┌──────────────────┐ │ ② 文件探针流 │ │ ③ 事后归因流 │ │ ④ 产物验证流 │ │ 读/写事件 │ │ import/命名 │ │ 硬编码颜色扫描 │ │ mtime 变化 │ │ API 选择特征 │ │ Token 引用率 │ └──────┬───────┘ └───────┬───────┘ └────────┬─────────┘ └─────────────┬─────┴────────────────────┘ ▼ ┌───────────────┐ │ 交叉比对引擎 │──► 四流一致 → ✅ 声明可信 └───────────────┘──► 存在矛盾 → ❌ 虚假声明告警
证据流数据来源采集方式能证明什么弱点
① 语义声明流Agent 输出文本 / 工具调用记录解析输出中的结构化声明Agent 自称做了什么可以撒谎，单独不可信
② 文件探针流文件系统层探针被动记录 read / mtime 事件哪些文档真的被打开过读 ≠ 理解，只能证伪不能证实
③ 事后归因流生成的代码本身分析 import 路径、命名、API 风格产物实际受哪些规范影响归因是概率性的，存在噪声
④ 产物验证流最终产物静态扫描AST / 正则检测硬编码值产物是否符合规范的客观特征只能覆盖可机器判定的规则

四流各有盲区，但盲区互不重叠：文件探针不知道 Agent 是否"理解"了文档，产物验证不知道 Agent 是否"读过"文档，而声明流两者都证明不了——但把四条流放在一起，矛盾就无处藏身。这个思路和财务审计一模一样：账本本身不能证明资金流向，必须拿凭证、银行流水、实物库存交叉对账。

生产案例 · 识破"声明读了但没执行"：某前端团队让 Agent 按设计系统 Skill 生成组件，Agent 每次都声明"已阅读并遵循设计系统文档"，但验收时发现组件颜色全是硬编码的 #1899ff。交叉比对四流证据：语义声明流记录"已阅读"1 次，文件探针流显示 design-system.md 的读取事件为 0，产物验证流统计出 17 处硬编码颜色、0 处 Token 引用。结论：Agent 注入了 Skill 描述但文档内容根本没进上下文。修复 Skill 注入机制后，声明与行动的一致率从 58% 提升到 96%，此类"口头遵循"问题的排查时间也从平均 3 小时缩短到 5 分钟——因为矛盾点直接呈现在比对报告里，不再需要人工翻日志。

实现上还有一个容易踩的坑：四条流必须共享同一个 trace_id。推理层、工具层、文件系统层的事件如果用时间戳对齐，一旦两次任务并发执行就会串线。正确做法是一次任务分配一个 trace_id，每个动作分配 span_id，所有层的所有记录都盖上这两个戳。

生产案例 · trace_id 揪出并发串线：某团队在同一工作区并发跑两个 Agent 任务，某天发现约 13% 的产物出现"文件 A 的风格混着文件 B 的命名"。由于两个任务的时间戳几乎完全重叠，按时间对齐的日志把两边事件搅在一起，排障两小时仍无法确定是哪一侧出了问题。强制为每个任务的全量事件加盖统一 trace_id 后，比对引擎按 trace_id 重放，10 分钟定位根因：一个 Agent 实例的上下文缓存未清理，读到了另一个任务的中间产物。此后"并发任务隔离检查"成为该团队每周演练的固定项目。

比对引擎的输出也要标准化：不输出自由文本结论，而是输出 0~1 的一致分和矛盾点清单。例如"声明读了文档但探针事件为 0"记一条权重 0.6 的重大矛盾，"产物含硬编码值"记一条权重 0.4 的次要矛盾，一致分 = 1 − Σ(矛盾权重)。分数可量化，才能进入指标层做聚合与告警，"一致分 ≥ 0.9 的任务占比"也才能成为管理层和工程师都看得懂的单一数字。

一条证据是口供，四条证据才是案卷——交叉比对的价值不在任何单一流，而在矛盾暴露的那一刻。

三、OpenTelemetry Skill Span 标准化追踪

四流证据解决了"验证"问题，但各团队自定义的日志格式带来了新的麻烦：换个观测后端就要重写解析器，跨框架的数据无法拼接。OpenTelemetry（CNCF 的厂商中立可观测性标准，简称 OTel）的 GenAI 语义约定工作组正在解决这个问题——它定义了一套所有框架都可以写入的统一属性词汇表，让 Agent 的执行树在任何兼容后端里都能被还原。

核心概念是 Span：分布式追踪的基本单元，记录一次操作的名称、起止时间、属性和父子关系。一次完整任务是一个 Trace，Trace 内部嵌套成树。按 GenAI 语义约定，每次 Skill 调用应该包装为一个独立的 Skill Span，记录完整生命周期信息：

属性含义示例
gen_ai.operation.name操作类型chat / execute_tool / invoke_agent
gen_ai.agent.name / id / versionSkill / Agent 身份与版本design-system-ui / v2.3.1
gen_ai.tool.name / call.id工具调用的名称与唯一 IDread_file / call_004
gen_ai.usage.input/output_tokens本次调用的 Token 消耗1820 / 214
gen_ai.response.finish_reasons模型为何停止stop / tool_calls
gen_ai.request.model实际调用的模型gpt-4o-mini
trace_id = run_01J8（一次"生成登录组件"任务） └─ invoke_agent code-agent [agent.version=v2.3.1] ├─ chat gpt-4o-mini [in=1820 tok, out=214 tok] ├─ execute_tool read_file [design-system.md, 42ms] ├─ execute_skill design-system-ui ★ Skill Span │ ├─ chat gpt-4o-mini [推理组件结构] │ └─ execute_tool write_file [Button.tsx, 1.2KB] ├─ execute_tool run_eslint [3 errors → 修复后 0] └─ chat gpt-4o-mini [finish_reason=stop]

有了这棵树，"为什么模型选了这个工具""幻觉是从哪一步开始的""这次任务总共烧了多少 Token"这些原本无法回答的问题，都变成了对 Span 属性的查询。标准的 MCP（Model Context Protocol，模型上下文协议——Agent 调用外部工具的统一协议）工具调用同样各自成 Span，记录参数、异常与延迟，并通过 trace context 向上关联到触发它的那次 LLM 调用，实现"决策 → 动作"的闭环。

标准化的价值有量化证据。AgentTelemetry 基准研究对比了不同观测条件下的故障检测率：仅用原生 OTel + GenAI 约定（只覆盖 LLM 调用与工具执行），对 14 类 Agent 故障只能检测到 6 类，故障检测率（FDR）为 0.429；补齐推理、规划、委派、记忆等 Agent 特有 Span 后，FDR 达到 1.000。同一研究在 112 个 SWE-bench 实例上发现，75% 的 Agent 失败源于推理循环——这种故障在传统追踪视角下完全不可见，而基于遥测数据的干预使修复率提升了 8.3 个百分点。

把这类研究的分类翻译成日常排障词汇，常见 Agent 故障在两种插桩粒度下的可见性大致如下——注意"盲区"故障恰恰是发生频率最高的几类：

故障类型典型表现仅基础 OTel（LLM+工具 Span）补齐 Agent 特有 Span 后
推理循环在相同两三个工具间反复横跳、输出自相矛盾只能看到重复调用，无法定性✅ 推理 Span 序列模式可识别

幻觉 API产物里出现不存在的函数名或 Token 名⚠️ 输出可见但无法即时校验✅ 结合产物验证流可闭环校验

成本上不必担心"全量打爆存储"：Span 本身只是几百字节的结构化元数据，一次含几十个节点的任务执行树不过几 KB 量级；真正昂贵的是把完整 Prompt 和产物文本塞进属性。因此业界惯例是 Span 全量采集、内容类属性按需开启（OTel 约定本身就把内容类属性标为 opt-in），让可观测开销本身也可控，避免"监控系统成为第一个被优化的成本中心"。

插桩方式做法优点代价
框架内嵌框架原生输出 OTel Span（如部分 Agent 框架）接入简单，零胶水代码与框架的 OTel 版本耦合
外部插桩库独立包装库在框架调用外加 Span与框架解耦，可自由升级多库并存时属性可能碎片化
完全自建手写结构化日志，不用标准词汇完全可控锁死单一后端，换工具全部重来
为什么要押注标准：GenAI 语义约定的贡献者来自 Amazon、Google、IBM、Microsoft 及主流观测厂商，Datadog 等商业平台已原生消费这套约定。约定目前仍处于 Development 状态、属性偶有破坏性变更（如 gen_ai.system 更名为 gen_ai.provider.name），所以应锁定插桩库版本；但"插桩一次、后端随便换"的回报是实实在在的——今天写 gen_ai.* 属性，明天从 Jaeger 切到 Grafana Tempo 不需要动一行埋点代码。

Skill Span 就是给每次技能调用办一张"登机牌"：谁（哪个 Skill 哪个版本）、何时、花了多少 Token、带了什么行李（输入输出）、下一站去哪——树状登机牌拼起来就是完整行程单。

四、特有监控维度：合规率与质量指标

链路追踪解决"发生了什么"，但 AI 代码生成还需要回答"生成的东西合不合格"。这是 AI 研发链路特有的监控维度，核心是三个指标族：设计系统合规率、代码质量指标、产物与需求的偏差度。

设计系统合规率的逻辑很直接：如果 Agent 声称遵循了设计系统，那么产物里每一个颜色、间距、圆角都应该引用 Design Token（设计系统的最小变量单元，如 var(--color-primary)，是视觉规范的单一事实来源），而不是硬编码数值。于是合规率变成一个可机器计算的比值：

设计合规率 = 引用 Token 的样式值数量 / 样式值总数 × 100%

检测手段从便宜到昂贵分三档：正则/AST 扫描硬编码颜色（如 #1899ff 这类不在 Token 表里的值）成本几乎为零，适合放进每次 CI；自定义 ESLint / Stylelint 规则强制组件从统一库 import，防止 Agent 从零手写组件；视觉回归测试（截图比对）兜底那些静态规则查不到的布局漂移。

产物-需求偏差度评审模型对产物与 PRD 的语义比对打分偏差分低于阈值自动拦截产物提交前

偏差度的评估值得单独说：用大模型当评审（LLM-as-judge）准确但昂贵且慢，不适合高频生产监控；更经济的做法是训练或选用小型评审模型。业界的对比数据是，专用小模型评审成本可以比 GPT-4 级评审低两个数量级、速度快约 21 倍（152ms 对 3200ms），这让"每个产物都过一遍语义评审"从奢侈品变成了流水线标配。

生产案例 · 质量门禁的数字账：行业统计显示，AI 生成代码的初始正确率约 60%~70%，未经验证的 AI 代码引入的漏洞密度是人工代码的 1.5 倍，约 12% 含可识别安全漏洞；GitClear 的研究还发现 AI 代码的重复率是人工代码的 2~3 倍。一个落地了四层防护网（静态分析 + 单测与变异测试 + 人工审查 + 混沌验证）的团队报告：静态扫描拦下了约 35% 的 AI 提交（多为类型缺失与过度复杂分支），设计合规率从门禁前的 62% 提升到 97%，单个人工审查 PR 的设计合规检查从 15~30 分钟降到 3 分钟以内（机器先筛，人只看边缘情况），最终 AI 代码的线上故障率被压到与人工代码同一水平。关键不是拦截率这个数字本身，而是它证明了：AI 代码应当被当作"草稿"进入流水线，门禁把草稿变成品。

注意打回动作的设计：失败时不只是拒绝，而是把错误清单和 Token 表回注给 Agent 让它重新生成——门禁同时是反馈回路。多数团队的失败教训是关卡之间"只拦不教"，Agent 反复犯同样的错，通过率长期卡在低位。

合规率曲线一旦下滑，归因通常指向三类原因之一：模型版本变更（新模型对风格有不同偏好）、Skill 描述里的约束语句被改动、设计系统文档更新但没有同步进 Skill 的依赖声明。三者的修复动作完全不同，但缺乏监控时它们的表现都是"最近产物变丑了"。正确做法是把合规率与 Skill 版本、模型版本的发布时间线叠加，曲线开始下跌后的第一个变更点往往就是原因。

小模型评审自身也要被"评审"：上线前用 200~500 个人工标注样本做一致性校准，要求人机判定一致率 ≥ 90%；上线后每周抽样约 5% 的产物做人工复核，防止评审模型随生成代码的分布一起漂移。评审模型也是模型，也会有"一次校准、永久有效"的错觉。

测试覆盖率对 AI 代码尤其容易被"刷"出来：Agent 生成测试的速度和生成业务代码一样快，很容易造出覆盖率达标、断言空洞的测试。所以 AI 产物的测试门禁必须把突变得分放在与覆盖率同等甚至更高的优先级——覆盖率回答"有没有测试"，突变得分回答"测试到底拦不拦得住错误"。

  • 把 Token 表（tokens.json）放进项目根目录，让 Agent 生成前就能读到约束
  • 打回时附带机器可读的错误上下文，形成"生成 → 检查 → 反馈 → 重生成"闭环
  • 门禁指标（合规率、通过率）持续上报，按周看趋势而不是只看单次
  • 对 Agent 声明的"已遵循"永远用产物验证流二次确认
  • 不要用"Agent 说它读了文档"作为合规证据——声明是最弱的证据流
  • 不要追求 100% 硬拦截一切风格问题，噪音过多会让团队绕过门禁
  • 不要把语义评审全押在昂贵的大模型上，高频场景用小模型评审
  • 不要只监控失败率——"返回成功但合规率暴跌"的静默退化更危险

合规率是把"风格一致性"这种主观抱怨，翻译成一条能报警的曲线——翻译不了的东西就没法治理。

五、五层可观测架构与 Grafana 落地

前面的部件——声明验证、四流比对、Skill Span、质量门禁——最终要组装成一个整体。完整的 可观测性（从系统的外部输出推断内部状态的能力，对非确定性的 Agent 系统意味着"每次决策都可回放"）体系分为五层，自下而上各管一件事：

五层之间的数据流有两个关键接头。其一是追踪层向指标层投影：Span 上的 gen_ai.usage.input_tokens、skill 版本、错误状态被聚合成"单任务 Token 成本""各版本 Skill 成功率"等时序指标——Trace 是个体病历，指标是群体体检报告，两者靠同一套属性词汇打通。其二是证据比对层向指标层投影：每次任务的"声明-行动一致分"进入时序库，一致分的突降就是最值得报警的信号，因为它意味着 Agent 开始"言行不一"，而这往往先于任何功能性故障出现。

Grafana 上值得建的四个面板：调用链瀑布图（从 invoke_agent 展开到每个工具 Span，排障入口）；合规趋势图（设计合规率按天聚合，跌破 95% 报警）；虚假声明率（声明与探针矛盾的任务占比，正常应接近 0，突增说明 Skill 注入或上下文组装出了问题）；成本曲线（按 Skill 版本分组的 Token 消耗，防止新版本 Prompt 偷偷膨胀）。告警策略上建议参考 SRE 的燃尽率思路：不看单点毛刺，看"合规率相对 SLO 的消耗速度"，避免误报淹没真问题。

告警阈值不是定完就结束：初版阈值应偏宽松，先观察一两周的噪音水平，再按"每次 P1 必须有真实根因"的标准逐步收紧。对反复确认为噪音的告警要当场降级或删除——误报的容忍是会传染的，今天被忽略的一条告警，就是明天被错过的真实故障。

采集策略上，Span 元数据便宜，应全量保留；真正需要取舍的是 Prompt、产物全文这类内容型数据。推荐用 尾部采样：先把全部 trace 暂存在缓冲区，按"是否有错误、一致分是否骤降、Token 是否超阈值"决定哪些 trace 的内容明细落盘。这样常规任务只留几 KB 的骨架，真正需要调查的 trace 保留完整现场——相比头部采样（采集前就随机丢弃），恰好避免了"想查的那条 trace 恰好被丢掉"的尴尬。

面板之间应形成固定的下钻路径：从合规趋势图发现异常日期 → 切到虚假声明率确认是否伴随行为漂移 → 进入调用链瀑布图按 trace_id 查看具体矛盾点 → 最后落到 Skill 版本与 Prompt 差异。这条路径值得在 Grafana 里做成带变量的跳转链接，否则告警响起时人仍要在四个系统之间手动切换，排障速度会退回监控建设之前。

生产案例 · 成本曲线 40 分钟抓出 Prompt 膨胀：某团队上线新版 Skill 后，成本面板显示单任务输入 Token 的 P95 在一小时内从 1.8k 涨到 6.4k，而合规率没有任何变化。回放新版本 trace 发现，新 Prompt 把整份设计系统文档全文塞进了上下文，实际只用到其中两节。由于启用了尾部采样，异常 trace 的完整上下文被保留，从告警到定位只用了 40 分钟：新版本把"按需摘录"改成了"全量注入"。回滚并改为摘录注入后，单任务成本回到 1.9k，产物质量不变——没有这条曲线，该回归只会在月底以三倍账单的形式被发现。
落地阶段建设内容解决的问题投入量级
第 1 周结构化日志 + 产物验证流（硬编码扫描进 CI）抓出最显眼的"言行不一"低：两条流水线规则
第 2~3 周文件探针 + 比对引擎 + trace_id 贯穿四流齐全，矛盾自动暴露中：一个探针服务
第 4~6 周OTel Skill Span + 指标聚合执行树可回放，趋势可监控中：埋点 + Collector
之后Grafana 面板 + SLO 告警 + 偏差度语义评审从"能查"到"能防"持续：面板与阈值调优
分阶段的意义：五层不是大爆炸式工程。第 1 周只做"产物验证流 + 硬编码扫描"的团队，就已经能抓到源文件案例中那种"声称遵循设计系统、产物全是 #1899ff"的问题——因为产物验证是唯一不会撒谎的证据流。其余各层是把这个能力从"事后抽查"升级为"实时报警"的阶梯。

五层架构的终极承诺只有一句话：系统里任何一个"声称"，都能被另一条独立的证据流证实或证伪。

Q&A

为什么"日志全是 200"不能证明 Skill 调用正常？
因为 Skill 调用的典型失败是静默的：HTTP 层成功、任务"完成"，但执行路径已经偏离目标——比如模型在两个工具之间反复重试、跳过该读的文档、生成了不符合规范的产物。传统日志只记录请求边界的输入输出和状态码，无法表达"行为与声明是否一致"。有真实案例是一夜之间 2000 个请求全部记录为成功、下游却收到损坏数据。所以 Agent 系统的监控目标必须从"记录状态"升级为"验证行为"，这正是四流证据交叉比对存在的原因。
四流证据里哪一流最可信？为什么文件探针比语义声明可靠？
文件探针流（被动记录的文件读取/修改事件）最接近事实，因为它产生在 Agent 控制不到的系统层——Agent 无法通过"说"来伪造一条文件读取事件。语义声明流则只是 Agent 的自述，它可能声称读了文档但上下文里根本没有文档内容。产物验证流同样客观（硬编码颜色不会自己消失），但只能覆盖可机器判定的规则。正确用法不是选一流相信，而是四流交叉：声明与探针矛盾即虚假声明，声明与产物矛盾即执行失效。
OTel Skill Span 相比自建结构化日志解决了什么问题？
解决的是"数据可携带"与"跨系统拼接"。自建日志的字段名、层级结构是私有词汇，换一个观测后端就要重写解析器，跨框架、跨团队的追踪数据无法对齐。OTel GenAI 语义约定定义了统一属性（如 gen_ai.operation.name、gen_ai.usage.input_tokens、gen_ai.agent.version），所有插桩方写同一套词汇，后端（Jaeger、Tempo、Datadog 等）可以直接消费，埋点一次、后端随便换。代价是约定仍在演进、需要锁定插桩版本。量化收益上，AgentTelemetry 研究显示：只覆盖基础约定的追踪仅能检测 43% 左右的故障类型，补齐 Agent 特有 Span 后达到 100%——说明"标准化"与"覆盖度"要一起抓。
Agent 声称读了设计系统文档，产物却全是硬编码颜色，完整的定位路径是什么？
第一步，产物验证流扫描确认违规面：统计硬编码颜色数量与 Token 引用率，锁定违规文件。第二步，查文件探针流：design-system.md 在本次任务的读取事件是 0 还是大于 0——为 0 说明文档根本没进上下文，问题在 Skill 注入或上下文组装环节；大于 0 则说明读了但没遵循，问题在 Prompt 约束强度或模型能力。第三步，比对语义声明流与上述证据，确认是"虚假声明"还是"执行失效"。第四步，看 Skill Span 的版本与输入属性，复现该版本的最小用例修复，并把该违规模式加入 CI 门禁，让同类问题在合并前被拦截。
设计合规率门槛定多少合适？追求 100% 有什么风险？
建议硬规则（颜色、组件 import 来源）零容忍，软规则（间距微调、阴影层级）给 95% 左右的目标线并看趋势。100% 全拦截的风险是误报疲劳：一旦门禁把合理的例外（如临时活动页的品牌特例色）也拦掉，团队就会想办法绕过门禁——比如给文件加豁免注释，门禁名存实亡。更健康的做法是区分"阻断级"与"告警级"：硬编码颜色阻断合并，间距偏差记录指标并周报跟进。门禁的权威来自"拦下来的都是真问题"，而不是"拦得够多"。
从零开始建这套监控，最小可用组合是什么？必须一步到位上五层吗？
不需要。最小可用组合只有两样：产物验证流（在 CI 里加硬编码颜色/组件 import 的静态扫描）和带 trace_id 的结构化日志。前者能立刻抓住"言行不一"中最常见的一类——因为产物不会撒谎；后者保证出问题时能按任务 ID 把散落日志串起来。之后再按"文件探针 → 比对引擎 → OTel Span → Prometheus 指标 → Grafana 面板"的顺序逐层加。每加一层都对应一个具体痛点（查不到、对不齐、看不见趋势），避免为了架构完整性而过度建设。
监控数据里包含 Prompt、代码产物和工具参数，如何防止敏感信息泄露？
核心原则是"记录决策，最小化记录内容"。具体做法：Span 属性默认只记录结构性元数据（Skill 名称、版本、Token 数、耗时、错误状态），完整 Prompt 与产物内容做成选择性开启（OTel 约定里内容类属性本身就是 opt-in 的）；必须留存的内容先做脱敏——密钥、个人信息在写入前用规则过滤，或用哈希指纹替代原文；工具参数记录原始入参但限制长度并过滤敏感字段；访问控制上，Trace 存储按团队隔离权限，能看产物明细的人本就应该有代码权限。审计需求与隐私不是对立的——分层采集让两者各得其所。
Token 成本突然上涨，如何区分是 Skill 版本回归还是任务复杂度的自然增长？
看三个信号。第一，按 skill.version 分组：如果旧版本流量的成本没变、只有新版本上涨，基本就是版本回归。第二，看单任务输入 Token 的 P95 变化速度：任务复杂度的自然增长是渐进的，P95 在一天内跳涨 50% 以上几乎必然是变更事件。第三，回放几条高成本 trace，看上下文里装了什么——常见回归模式有整份文档全量注入、重复读取同一文件、重试对话不断累积。三个信号都指向新版本时就先回滚再复盘：成本异常与功能 Bug 不同，多观察一小时就多烧一小时的真实预算。
如果只允许先对一条指标设告警，应该选哪条？为什么？
选一致分（声明与行动的一致程度）。功能失败率、合规率、成本都属于结果指标——它们异动时损失已经发生；一致分下滑则是先行信号：它说明 Agent 开始言行不一，此刻产物可能碰巧还是对的，但执行路径已经不可信。经验上，虚假声明率激增通常领先合规率骤降数天——先是行为漂移，然后才是产物变丑，最后才是用户投诉。所以把最灵敏的告警挂在一致分上，让它充当烟雾报警器，其余面板用于定位根因与评估影响面。
