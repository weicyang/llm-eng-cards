评估不是一次性动作，而是一条从离线到在线、从静态到持续的质量管线。三层评估缺一不可：离线守底线，在线验效果，监控防退化。

二、Golden Dataset 构建

Golden Dataset 是评估的"地基"。数据集质量决定了评测结论的可信度——垃圾数据集上跑出的高分 = 虚假安全感。

评测流水线是"CI/CD 的质量守门员"——每次 Prompt / 模型 / 管线变更，都必须自动触发评测，结果记录在案，形成质量基线。

四、Do / Don't

  • Golden Dataset 版本化管理
  • 每次变更跑评测
  • 多维度评测（准确率/幻觉率/延迟/成本）
  • A/B 测试验证线上效果
  • Bad Case 持续收集分析
  • demo 几条 case 就上线
  • 只看准确率不看幻觉率
  • 评测集不更新
  • 不做 A/B 测试
  • 忽略线上 Bad Case

五、LLM-as-Judge 评估方法论

人工评估成本高、速度慢，LLM-as-Judge 用大模型给大模型打分，是规模化评测的关键杠杆——但需要校准，否则"裁判本身也会犯错"。

为什么需要 LLM-as-Judge

传统 BLEU / ROUGE 等基于 n-gram 重叠的指标，无法捕捉语义等价性。例如"北京是中国首都"和"中国的首都是北京"语义相同，但 n-gram 得分很低。LLM-as-Judge 能理解语义层面的正确性。

六、RAG 管线分层评测

RAG 系统有两大独立环节——检索和生成。只评最终回答会掩盖问题根源，分层评测才能精准定位是"检索没找到"还是"生成答错了"。

分层评测指标体系

评测层指标含义计算方式
检索层Context Recall答案所需信息是否被检索到标准答案中命中的 chunks / 总需 chunks
Context Precision检索结果中有多少是相关的相关 chunks / 总检索 chunks
MRR (Mean Reciprocal Rank)第一个相关结果排第几1/首个相关结果的位置
生成层Faithfulness回答是否忠于检索上下文有证据支撑的声明数 / 总声明数
Answer Relevancy回答与问题的相关性LLM-as-Judge 评分
Hallucination Rate回答中无据可查的内容比例幻觉声明数 / 总声明数
📌 生产案例：某法律文档 RAG 系统上线后发现用户满意度仅 65%。通过分层评测发现：检索层 Context Recall 仅 0.54（大量法条未被召回），而生成层 Faithfulness 高达 0.91。问题定位在 Embedding 模型对法律术语的表征能力不足。更换为领域微调的 Embedding 后，Context Recall 提升至 0.89，用户满意度提升至 82%。

检索 vs 生成：常见问题定位

现象可能原因定位方法修复方向
回答"不知道"但知识库有答案检索失败（Recall 低）检查 Context Recall优化 Chunk 策略 / Embedding / 混合检索
回答与知识库矛盾生成幻觉（Faithfulness 低）检查 Faithfulness 分数强化 System Prompt / 降低 Temperature
回答正确但不完整Top-K 太小或 Chunk 粒度问题对比不同 K 值的 Recall增大 Top-K / 调整 Chunk 重叠

七、Agent 多步任务评测

Agent 与普通 LLM 调用的关键区别：Agent 是多步决策，错误会沿调用链累积放大。单步准确率 95% 的 Agent，10 步下来端到端成功率可能只有 60%。

Agent 评测维度

维度指标说明
任务成功率Task Success Rate端到端完成目标任务的比例
步骤效率Avg Steps to Complete完成任务的平均步骤数（越少越好）
工具选择准确率Tool Selection Accuracy每步选对工具/ API 的比例
错误恢复率Error Recovery Rate遇到错误后能自行修正并继续的比例
成本效率Cost per Task完成单个任务的平均 Token / API 成本
📌 生产案例：某数据分析 Agent（能自主编写 SQL 并生成图表）的评测数据：任务成功率 73%，但分析失败 case 后发现 41% 的失败源于第一步"理解用户意图"出错，而非 SQL 生成能力不足。团队据此在第一步增加了"意图确认"机制，将任务成功率提升至 86%。

评测环境搭建

Agent 评测需要可控的沙箱环境，核心要求：

  • 状态可重置：每次评测前将环境恢复到初始状态
  • 工具 Mock：外部 API 使用 Mock Server，避免真实调用产生的副作用和成本
  • 确定性 Oracle：为每个任务定义明确的"成功条件"验证函数
  • Trace 记录：完整记录每一步的输入、输出、工具调用、耗时

八、A/B 测试工程实践

离线评测再高分，也不能替代线上 A/B 测试——因为离线评测集永远无法完全模拟真实用户分布。A/B 测试是"最后一道防线"。

A/B 测试关键要素

要素实践要点常见陷阱
流量分配50/50 随机分流，按用户 ID 哈希按时间分流导致时段偏差
样本量提前做 Power Analysis，确定最小样本量样本量不足，无法检出真实差异
指标体系主指标 1 个 + 护栏指标 2-3 个只看主指标忽略副作用
运行时间至少跑满 1-2 个完整业务周期提前偷看结果（Peeking Problem）
统计显著性p < 0.05 + 置信区间不跨零p-hacking（反复测不同指标直到显著）
📌 生产案例：某智能客服系统 A/B 测试：新版 LLM 方案 vs 旧版方案，跑 14 天，流量 50/50 分流，共计 12,847 次会话。结果：新版任务完成率从 68.2% 提升至 74.6%（+6.4pp, p=0.003），但护栏指标"平均响应延迟"从 1.8s 上升至 2.7s。最终决策：上线新版但同时启动延迟优化专项。

Q&A

LLM 评测和传统软件测试有什么区别？

传统软件是确定性输出（输入 A → 输出 B），用单元测试即可验证。LLM 是概率性输出（同样输入可能不同结果），需要：① 统计评估（准确率/分布），② 多维度（准确率+幻觉率+延迟+成本），③ 不确定性处理（多次采样取统计量），④ 主观评估（LLM-as-Judge / 人工抽检）。

怎么保证 Golden Dataset 的质量？

① 多标注者一致性检查（Cohen's Kappa > 0.8）。② 定期更新（每月从线上日志补充新样本）。③ 分层抽样保证代表性。④ 版本化管理（Git），每次变更可追溯。⑤ LLM 生成的样本必须人工逐条抽检，剔除假问题。

LLM-as-Judge 的可信度有多高？什么情况下不能用？

经过校准的 LLM Judge（如 GPT-4 级别），在通用事实类任务上与人工评估一致率可达 80-90%。但在以下场景需谨慎：① 高专业领域（医疗/法律/金融），Judge 本身可能缺乏专业知识；② 安全性评估，安全判断不能仅靠 LLM；③ 主观偏好类任务，需要真实用户反馈。最佳实践是"LLM Judge 打分 + 人工抽检 10-15%"的混合模式。

RAG 评测中，检索和生成应该分开评还是一起评？

必须分开评 + 联合评。分开评（检索层看 Recall/Precision，生成层看 Faithfulness/Relevancy）能精确定位问题出在哪一层；联合评（端到端用户满意度）反映最终体验。只看端到端会导致"知道有问题但不知道修哪里"。实践中建议先跑分层评测建立基线，再用端到端指标做线上监控。

A/B 测试跑多久才够？如何确定样本量？

时间上至少跑满 1-2 个完整业务周期（如果业务有周中/周末差异，至少跑 2 周）。样本量需提前做 Power Analysis：给定 MDE（最小可检测效应，如 5% 提升）、显著性水平 α=0.05、统计功效 1-β=0.8，计算出每组所需最小样本。工具推荐 Python 的 statsmodels 库。切忌"边跑边看"——提前偷看结果会导致 Peeking Problem，使 p-value 失效。

Agent 多步任务的评测有什么特殊挑战？

三大挑战：① 错误累积——单步 95% 准确率，10 步后端到端仅 ~60%，需要端到端评测而非单步评测；② 路径多样性——同一任务可能有多条合理路径，不能简单比对输出，需用"最终状态验证函数"判断成功与否；③ 环境依赖——Agent 调用外部工具，评测需要搭建可控沙箱（Mock Server + 状态重置）。推荐记录完整 Trace，失败时逐步回溯定位具体出错步骤。

评测指标之间冲突了怎么办？（如准确率提升但延迟也增加）

这是非常常见的情况。推荐做法：① 明确主指标和护栏指标——主指标（如准确率）是优化目标，护栏指标（如延迟、成本）是底线约束；② 设定护栏阈值——例如"P99 延迟不超过 3s 的前提下，追求最高准确率"；③ 用 Pareto 前沿 分析——绘制指标间的 Trade-off 曲线，找到最优平衡点。最终决策应结合业务场景：用户敏感型场景优先准确率，实时型场景优先延迟。

如何评测 LLM 的幻觉问题？

幻觉评测需要三层策略：① 事实核查——将回答拆解为原子声明（Atomic Claims），逐条验证是否有上下文/知识库支撑，计算 Faithfulness 分数；② 自洽性检查——同一问题多次采样，检查回答是否一致（Self-Consistency）；③ 对抗测试——构造"诱导性问题"（如问一个不存在的事实），测试模型是否"自信地胡说"。工具推荐 RAGAS 的 hallucination_relevancy 指标，配合人工抽检高危场景。

评测数据集应该多大规模？怎么判断够不够？

规模取决于业务复杂度：MVP 阶段 50-100 条足以发现明显问题，预上线阶段建议 200-500 条覆盖主要场景，生产运行阶段需 500-1000+ 条。判断够不够的方法：① 覆盖率分析——检查数据集是否覆盖了所有业务场景类型和问题难度；② 稳定性分析——增加样本后评测结果波动是否收敛（若波动 > 3%，说明样本量不够）；③ 置信区间——计算准确率的 95% CI，区间宽度 < 5% 通常可接受。
