EV09 · 在线评测与发布门禁

离线金标 vs 线上抽样 / 轨迹·工具·任务完成·多轮 / observation 级 LLM-as-judge / shadow 与 canary 晋升 / Judge 漂移治理

评测集回答「这个改动在昨天的题目上过没过」；在线评测回答「今天真实用户的轨迹是不是在静默变坏」。只做前者，等于用旧地图给新城市发驾驶证。

指标怎么定义、硬断言怎么写、Trial/Grader/Suite 底座长什么样，见 EV01、EV04、EV06、EV08。灰度流量怎么粘、怎么放量见 A61。本卡只接「评测结果如何变成不允许发版的门」以及「上线之后如何继续打分」。

一、离线金标只能证明「没立刻变差」

离线评测的优点是可复现：同一份数据集、同一个 grader、同一次 Docker。缺点也正好对称——分布漂移。用户问法、工具失败模式、页面改版、模型供应商静默升级，都不会事先出现在金标集里。Agent 的失败经常长在「路径看起来完成了、但中途用了错误工具参数」这种轨迹问题上，金标若只存最终答案，会放行一条以后再也走不通的路。

离线在线
输入固定数据集抽样生产流量
能抓的回归、已知边界未知问法、工具波动、供应商变更
不能抓的明天才出现的分布没有标签时的绝对对错（需 judge / 人）
失败默认阻断合并阻断放量或自动回滚
两条环，缺一不可 改 Prompt / 换模型 / 改工具 │ ▼ 离线 Suite（EV08）── 不过 → 禁止合并 │过 ▼ shadow 对打生产抽样 │ ▼ canary 5% 在线分 ── 掉点 → 回滚（A61 粘性路由） │稳 ▼ 全量 + 持续抽样 judge

离线是发版前的疫苗；在线是流行病监测。只打疫苗的城市，也会死于新毒株。

二、四维在线上怎么抽样

Langfuse 一类实践把 Agent 质量拆成四维：轨迹（走了哪些步）、工具使用（对不对、参数对不对）、任务完成（用户目标是否达成）、多轮（对话拉长后是否仍稳）。线上不能对每一维全量跑贵模型 judge，要按「能不能用代码判」分层抽样。

维优先判定器抽样建议线上特有噪声
轨迹步数上限、环检测、禁止工具名单全量廉价规则下游超时被记成「多走了一步」
工具schema 校验、幂等键、HTTP 状态全量廉价 + 失败流量 100%对方 429 不是 Agent 变笨
任务完成业务事件（工单关了、PR 绿了）有事件则全量；否则 5–10% judge用户自己取消会被判失败
多轮会话长度分桶后再 judge长会话加权，短会话少抽用户跑题不是模型漂移

2026 年的工程习惯是 judge 打在 observation（单次 span）而不是整条 trace 的遗留「trace 级裁判」。整段对错放在根 observation 的摘要上：先让运行时写出「本轮目标 / 关键工具 / 最终产物」，再让 judge 只读这一段，而不是把十万 token 轨迹塞进评分模型。

能用代码判的，永远不要用 LLM 判。Judge 只买语义判断，不买「参数是不是整数」这种语法税。

三、确定性检查、Judge 与人校准

三条判定器必须同时存在，而且有校准关系：规则是法律，judge 是陪审团，人是最高法院且只抽检。Judge 没有人校准，几周后会开始给「更礼貌但更错」的回复打高分——这叫 reward hacking 在评测侧的镜像。

判定流水线（从便宜到贵） span 进来 │ ├─ 规则：schema / 禁词 / 步数 / 循环指纹 → 全量，失败即记 0 ├─ 业务事件：工单关闭、测试通过、退款成功 → 能接到就当硬标签 ├─ LLM-as-judge：只打「无硬标签」的抽样 → 分数 + 短评 └─ 人抽检：每周校准 judge 与硬标签的一致率
判定器适合不适合
代码断言格式、权限、工具名白名单「回答是否有用」
LLM-as-judge无标准答案的完成度、忠实度高风险写操作的最终放行
人校准、争议样本、安全红线作为日常全量闸门
示例场景：客服 Agent 离线集 400 条全部绿灯后上线。两周内工具参数合法率仍 99%，但「一次解决」从 71% 降到 58%——模型开始用正确的 search_order 反复搜同一个订单号，轨迹更长、用户更烦。离线集没有「同一订单搜三次」的负样本。加上「重复工具指纹」规则全量打分后，该模式在 canary 当天被门禁拦住。

Judge 的 prompt 也要版本化。换评分模型或换评分词而不冻结 judge 版本，等于把尺子和被测物一起换。

四、发布门禁：shadow / canary / 晋升

门禁不是仪表盘上的红点，是 CI 或发布控制器里的硬返回码。推荐三道，和 A61 的流量层对齐：

  1. 合并门：离线 Suite 全过，否则禁止合主干。
  2. Shadow 门：新版本对生产请求只打分不作用户可见输出，对比旧版本的四维差异。
  3. Canary 门：5% 粘性用户，在线分相对基线的跌幅超过阈值则自动回滚。
流量层（A61）和评测层（本卡）同时读 合并 ──► 离线 Suite 全绿 │ Shadow ──► 真实问法、无用户可见副作用 │ 只读链路可以停在这里 Canary ──► 5% 粘性用户 + 写工具真执行 │ 硬失败清单一次命中即回滚 晋升 ──► 窗口内 Δ 不破阈值，才允许下一档流量 任一红灯：停止放量。不要用「再观察一个窗口」盖住付款类事故。
晋升条件示例（需按业务改阈值，不是普适常数）
规则失败率不升 且 任务完成率 Δ ≥ -1.5pt 且 工具错误率 Δ ≤ +0.5pt
窗口：至少 24h 或 N 次会话，取先到者中更严的那个
门阻断什么常见假阳性
合并明显回归、格式崩金标过时
Shadow新模型在真实问法上翻车下游偶发 5xx 被算进新版本
Canary放量后的体验与成本大促流量结构突变

Shadow 比 Canary 便宜的地方是零用户伤害；贵的地方是「没有真实副作用」时评不到写工具。只读链路可以几乎完全靠 shadow；付款链路必须 canary + 人工确认节点。

五、Judge 自身漂移与成本账

Judge 是另一套会变的模型。供应商升级、温度没锁、prompt 被「优化」得更仁慈，都会让分数上涨而产品变差。治理手段：锁定 judge 模型版本；定期用带人标签的校准集测一致率；一致率跌破阈值时冻结晋升，先修尺子。

成本项怎么压压过头的后果
Judge token只评根 observation 摘要；低风险流量少抽漏掉长尾工具误用
存储轨迹抽样落盘，全量只留 span 指标事故无法回放（对 ST13）
人时只看 judge 与规则冲突的样本校准集萎缩，尺子漂
示例场景：把 judge 从「整段 trace」改成「根 span 摘要」后，单次评分输入从约 12k token 降到约 800 token，日均评测账单降一个数量级。副作用是摘要漏写「用过的危险工具」，一度漏判。强制运行时模板必须列出工具名后，漏判在校准集上从 11% 降到 2% 以下。

评测账单可以压，校准集不能省。没有人标签的 judge，几周后会变成昂贵的随机数生成器。

六、最小可运行门禁与关闭条件

规则全量、judge 抽样、人校准三者同时在。晋升看差值不看绝对值。

写操作链路必须 canary；只读链路可以 shadow 为主。

Judge prompt 与模型版本进 ST10 同一套版本管理。

不要用离线总分代替线上任务完成率。

不要让 judge 去检查 JSON 能不能 parse。

不要在大促期间用同一套绝对阈值，改看相对基线。

什么时候不要上完整在线 judge：日请求量小到抽样没有统计意义、还没有稳定的业务事件、评测预算会超过模型调用本身。那时先把规则闸和离线 Suite 做硬，人做周复盘，再长 judge。

和 ST13 回放的衔接：在线 judge 打低分的样本应能一键拉出当时的 trace。评测没有回放，门禁会变成「分数红了但没人能复现」。存储可以抽样，但被门禁挡住的那批必须全量留证据，直到事故关闭。

最小指标看板只要四条：规则失败率、抽样任务完成率、judge 与人校准一致率、门禁触发次数。多了会没人看；少了会只剩延迟当质量。

Q&A

EV07 已经有「生产监控」，和在线评测有何不同？
监控告诉你延迟、错误率、token 是不是爆了，是系统健康。在线评测告诉你「用户的事办成了没有、路径合不合法」，是任务健康。二者都要采样生产流量，但指标语义不同。把 P99 当质量，会放过又快又错的 Agent。
为什么 judge 要打在 observation 而不是整条 trace？
整条 trace 又长又脏，评分模型会把格式噪音当成质量。根 observation 上先写结构化摘要，judge 只看摘要，分数可归因到「这一轮」。需要细查时再下钻子 span。这也是把评测成本从随轨迹线性涨，改成近似常数。
没有业务事件（关单、单测绿）时怎么做任务完成？
用抽样 judge + 明确的成功定义（用户是否得到可执行的下一步、是否引用了检索到的证据）。同时开始接一个最便宜的业务事件，哪怕只是「用户 24h 内没有再问同一件事」。纯语义完成度无法单独做高风险放行。
Shadow 对比时新旧版本下游都 429，会不会误杀新版本？
会。所以对比必须按「可归因切片」：同一工具、同一错误码先从双方扣掉再比。门禁看的是新版本相对旧版本的增量，不是绝对错误率。把基础设施故障算进模型质量，是最常见的假阳性。
门禁阈值怎么定，会不会永远调不准？
先用相对跌幅而不是绝对分数，窗口用时间与样本量的双条件。上线后看一周假阳性，只调那一维。阈值写进配置仓库，和模型版本一起灰度。追求「永远正确的绝对分数」会把门禁调到形同虚设。
小流量产品必须上在线 judge 吗？
不必。日会话太少，5% 抽样没有置信区间。先做离线 Suite + 全量规则 + 每周人工听音。流量起来、出现「离线全绿线上变差」的事故之后，再加 shadow 和 canary 门。
规则失败率和任务完成率同时掉，先看哪一个？
先看规则。规则掉说明格式、禁工具或循环在扩散，修它能立刻缩小爆炸面。任务完成率掉而规则稳定，才轮到 judge 和业务事件，判断是模型、检索还是下游。两个一起红时先停放量，不要在红灯下继续调 judge 阈值。
Canary 窗口还没到样本量，分数已经很难看，要不要等？
安全类和写操作类不要等满窗口。预设「硬失败」清单（付款双花、数据删除、越权工具）一次命中就回滚。窗口是给软指标用的，不是给灾难用的。
和 A61 灰度如何衔接？
A61 管流量怎么粘、怎么从 5% 走到 100%。本卡管「什么分数允许走下一步」。发布控制器应同时读两个信号：路由层的错误与延迟，评测层的任务完成与工具合法性。任一红灯都停止放量。
