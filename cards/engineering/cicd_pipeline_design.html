CI/CD 不是"把脚本搬到服务器上定时跑"。它解决的是一个组织问题：当多人并行改同一份代码时，"当前代码是否可发布"这个判断必须便宜、快速、且自动得出，否则这个判断就会退化成靠人记、靠会议、靠发布前一周的集体加班。流水线的每一个设计决策——阶段怎么切、什么阻断什么告警、制品能不能重建——都是在为"降低这个判断的成本"服务。

一、三个被混用的概念：持续集成、持续交付与持续部署

日常对话里，"我们上了 CI/CD"这句话的信息量接近于零，因为它至少可能指三件性质完全不同的事。把这三件事分清楚是后面所有设计的前提，因为它们的准入条件不同、卡住团队的瓶颈不同、需要的组织授权也不同。

持续集成：一个团队纪律，不是一个工具

持续集成指团队成员把各自的改动高频地合并进主干，并且每一次合并都自动触发构建与测试，一旦主干变红就立即停下来修。它的核心不在"自动构建"这半边，而在"高频合并"这半边。trunk-based development 官方站点把这条准入条件写得很直白：持续集成的核心要求是所有团队成员至少每 24 小时把改动提交进主干一次，而 trunk-based development 正是让这条要求变得容易满足的分支模型。

这就解释了一个常见的误会。一个团队装了 Jenkins，给十几条长生命周期的特性分支各配了一条构建任务，每晚定时跑一遍全量测试——这是自动化构建，不是持续集成。因为集成这个动作（把各人的改动合到一起并验证冲突）仍然被推迟到了分支合并那一天。分支各自都是绿的，合到一起是红的，这种"绿色的谎言"恰恰是持续集成要消灭的东西。判断一个团队有没有真的在做持续集成，问工具是问不出来的，要问两个数字：分支从创建到合入主干的中位寿命是多少天，以及主干变红后恢复绿色的中位时长是多少分钟。

持续集成的反面不是"手工构建"，而是"延迟集成"。工具解决的是自动化，纪律解决的是频率，只有后者才决定你有没有 CI。

持续交付与持续部署：差的那一步是授权，不是技术

持续交付要求每一次通过流水线的提交都产出一个随时可以上线的制品，上线与否是一个业务决策，由人按一个按钮触发。持续部署则把这最后一步也自动化：通过全部门禁的提交直接进入生产环境，没有人工按钮。

很多团队卡在持续交付到持续部署之间，误以为差的是技术。实际上差的是三样配套能力：能把"代码上线"与"功能对用户可见"解耦的特性开关机制（见本卡第五章）、能在指标劣化时自动收敛的回滚路径、以及足够可信的线上可观测性。缺了这三样而强推自动部署，等于把风险从"发布日的集中爆发"改成了"每天随机爆发"，并没有变好。

二、阶段划分与门禁矩阵

流水线为什么要分阶段？如果只是为了界面上好看，那随便分都行。真正的原因是反馈时长与信息量之间存在一个取舍，而阶段划分是对这个取舍的显式编排：越便宜越快的检查放越前面，让大多数错误在几秒到几分钟内被打回；越昂贵越慢的检查放后面，只有前面全绿才值得花这个钱。

反馈时长预算：为什么第一阶段要控制在几分钟内

第一个阶段通常叫提交阶段，它的时长预算一般设在 5 到 10 分钟。这个数字不是拍出来的，它对应一个人的注意力窗口：如果提交后几分钟内拿到结果，开发者还停在同一个心智上下文里，修起来是"接着改"；如果要等半小时，人已经切去做别的事，回来要重新装载上下文，修复成本翻倍，而且这段时间里他很可能已经在这个未验证的基础上继续提交了。更糟的是排队效应——提交阶段慢一倍，等待中的提交就堆积，团队的实际集成频率被迫下降，第一章说的那条 24 小时准入条件就守不住了。

反馈时长不是体验问题，是吞吐问题。提交阶段的时长直接决定团队敢不敢高频合并，而合并频率又决定了每次合并要解决的冲突有多大。慢流水线会把团队推回延迟集成。

快失败：把检查按"成本除以信息量"排序

快失败原则说的是：如果一次流水线注定要失败，让它在最便宜的那一步就失败。实现方式是给每个检查估两个量——执行成本（时长、机器、外部额度）与信息量（能拦住多少比例的真实缺陷），然后按比值排序。格式检查和静态分析几秒就跑完却能拦住相当一部分低级错误，理应最先执行；端到端测试需要拉起整套依赖、跑几十分钟，就不该挡在提交阶段的入口。

现代流水线工具把这件事做成了一等能力。GitLab CI 的 needs 关键字让作业不必等整个上游阶段跑完，只要它自己依赖的那几个作业完成就能启动；官方还专门提供了 needs: []，让 lint 与扫描类作业在流水线创建的瞬间就开始跑，因为它们只依赖源码、不依赖构建产物。

lint_code:
  stage: test
  needs: []          # 不等 build，流水线一创建立即开跑
  script: echo "Linting code..."

门禁矩阵：哪些必须阻断，哪些只告警

门禁的分类标准只有一条：这个信号是否既确定又可操作。确定的意思是它为真时缺陷一定存在（假阳性率低）；可操作的意思是收到信号的人知道该改什么。同时满足才配得上阻断权，否则只能告警。把不确定的信号设成阻断，后果是团队学会了"重跑一次看看"，而这个习惯一旦养成，真正的阻断信号也会被同样对待，门禁整体失效。

阶段该拦什么时长预算阻断 / 告警理由
预检（提交前）格式、密钥泄露、提交信息规范< 10 秒阻断（本地钩子）确定、零歧义、修复成本最低
提交阶段编译失败、单元测试、类型检查、依赖高危漏洞5–10 分钟阻断确定且可操作，是主干可信度的底线
构建与打包制品能否成功产出并带上来源元数据3–10 分钟阻断后续所有阶段都消费这个制品
集成测试跨服务契约、数据库迁移、配置可加载10–25 分钟阻断（合并到主干时）确定性尚可，但不适合挡住每次推送
端到端 / 验收关键业务路径可用20–60 分钟关键路径阻断，其余告警易 flaky，全量阻断会摧毁门禁可信度
性能与容量相对基线的延迟与吞吐回归定时执行大幅回归阻断，小幅波动告警测量噪声大，需设死区
门禁矩阵：一次提交穿过流水线时被过滤的层次 提交 │ ├─[预检 10s]──── 格式/密钥 ──✗ 本地即拒（不消耗 CI 资源） │ │ ├─[提交阶段 6min]─ 编译+单测+类型+依赖审计 ──✗ 阻断，红灯归提交者 │ │ 绿 ├─[构建 5min]──── 产出不可变制品 + 来源证明 │ │ ├─[集成 18min]─── 契约/迁移/配置 ──✗ 阻断合并 │ │ 绿 ├─[E2E 35min]──── 关键路径 ✗ 阻断 · 边缘用例 ✗ 只告警并记账 │ │ └─[性能 定时]──── 对比基线，超出死区才阻断 信息量/成本 递减 ───────────────────────────────→ 昂贵且噪声大

示例场景：某中台团队把全套端到端测试放在提交阶段，每个 PR 必须等 34 分钟才拿到结果，日均合并 6 次，主干平均每周红 3 次且平均 2 小时才恢复。改造做了两件事：把提交阶段裁到编译、单测、类型检查共 4 分钟并保持阻断；端到端拆成"12 条关键业务路径"在合并主干时阻断、其余 200 余条转为每晚定时跑且失败只开工单。结果 PR 中位等待从 34 分钟降到 5 分钟，日均合并升到 21 次，主干红灯次数反而降到每周不到 1 次——因为提交频率上去之后，每次合并的改动量变小了。（本例为构造的典型场景，用于说明反馈时长与集成频率的耦合关系，非实测数据。）

门禁矩阵里有几类检查有专门的卡片展开：自动化评测怎么接进流水线、触发条件与基线对比怎么设计，见 EV01 · 评估与测试 第三章与 SG03 · AI 应用全链路性能评测指南 的 CI/CD 一章；发布阶段的线上门禁阈值怎么定，见 EV09 · 在线评测与发布门禁；AI 生成代码的静态扫描、覆盖率与突变测试门槛，见 ST21 · AI 代码生成与 Skill 调用监控 与 ST19 · Graph Engineering 代码审查工程化。本卡不重复这些阈值细节，只负责把它们放在流水线的正确位置上。

三、制品：不可变与一次构建多处部署

制品是构建阶段的输出：一个容器镜像、一个 jar、一个静态包。围绕制品有一条几乎没有例外的原则——一次构建，多处部署。同一个字节序列依次进入测试、预生产、生产，中间不重新构建。

为什么必须不可变

假设每个环境各自重新构建一次。表面上代码是同一个提交，但构建过程要做依赖解析，而依赖解析在两个时刻可能给出不同答案：某个间接依赖发布了新的补丁版本、某个基础镜像的 latest 标签指向了新内容、某个编译工具链在两次构建之间升级了。于是你在预生产验证过的那一坨二进制，和生产实际运行的那一坨，并不是同一个东西。此时预生产的全部验证价值归零——你验证的是一个再也不会运行的制品。

Docker 的层缓存机制也从反面印证了重建的不可靠。官方文档说明，Dockerfile 的每条指令对应一层，一旦某层发生变化，它之后的所有层都必须重新构建，即使那些层的构建逻辑毫无改动。这意味着"同样的 Dockerfile 在不同时间构建会得到同样的镜像"从来不是一个可依赖的假设。

不可变制品的真正价值是让"测试通过"这句话有指向对象。如果制品会重建，测试通过说的是某个已经消失的东西，等于什么都没说。

可变标签与不可变摘要：部署必须引用后者

引用方式例子指向是否唯一适合用途风险
可变标签myapp:latest否，可被重新推送覆盖本地开发便利两台机器拉到不同内容，问题无法复现
语义化版本标签myapp:2.4.1约定唯一，技术上仍可覆盖对外沟通兼容性依赖发布纪律，被重推后无感知
内容摘要myapp@sha256:9f3c…是，由内容哈希决定部署清单、回滚、审计不可读，需配套元数据映射

语义化版本与构建号：两个受众，两种职责

语义化版本（主版本.次版本.补丁）是一个面向消费者的兼容性契约：主版本变了意味着你需要改代码，次版本变了意味着有新能力但可以不改，补丁变了意味着可以无脑升级。它承载的是意图，由人决定。构建号（单调递增序号或提交哈希）是一个面向流水线的可追溯标识，它承载的是事实，由机器生成。两者不能互相替代：语义化版本回答"我能不能升"，构建号回答"这个二进制是从哪个提交、哪次运行、哪台机器出来的"。生产环境的部署记录必须同时保留两者，否则要么无法判断影响范围，要么无法定位来源。

标识受众生成者回答的问题能否复用

构建号 / 运行 ID流水线、审计、故障定位CI 系统这个制品是怎么来的不能，单调递增
源码提交哈希开发者版本控制系统代码是哪一版可复用（同一提交可多次构建）

制品库的作用不止是存储

把制品扔进对象存储也能"存起来"，但制品库额外提供四件事：不可变性保证（同一坐标不允许覆盖推送）、保留与清理策略（否则存储成本随构建次数线性膨胀）、来源元数据与签名的承载位置（谁构建的、从哪个提交、用了哪些依赖，见 ST28 · CI/CD 工具链与 GitOps 第五章）、以及晋升语义（用仓库或标签表达"这个制品已通过预生产验证"）。缺了这些，制品的可信度就只能靠流水线日志口头保证。

四、多环境晋升与配置代码分离

多环境的存在理由是把"验证什么"分摊到不同置信度与不同成本的位置上。如果三个环境干的是同样的事，那就只需要一个。

环境核心职责数据谁在用失败的后果常见误用
dev让改动能跑起来，快速试错合成或脱敏小样本开发者本人只影响自己当成集成环境，多人抢占
staging验证与生产同构的集成行为脱敏的生产同分布数据流水线、验收拦住发布配置与拓扑和生产不一致，验证失效
prod承接真实流量，是唯一的事实真实数据用户影响收入与信任在这里第一次执行未验证的迁移
staging 的价值完全取决于它与生产的同构程度。一个拓扑、配置、数据分布都和生产不一样的 staging，提供的是虚假的安全感——它会让你以为验证过了，而实际验证的是另一个系统。

晋升是元数据变更，不是重新构建

承接第三章：环境晋升的正确实现是把"某个制品摘要已通过某个阶段"记录下来，部署时按这个记录去拉同一个摘要。晋升动作本身不碰构建。一旦某个环境的部署触发了重新构建，不可变链条就断了，而且断裂位置往往是最关键的那一段（预生产到生产）。

配置与代码分离：十二要素的那条试纸

既然同一个制品要进三个环境，那么环境之间的差异（数据库地址、外部服务凭据、功能开关、副本数）就必须来自制品外部。十二要素应用的配置一章给出了一条非常好用的判定标准：把代码库随时开源出去，会不会泄露任何凭据？如果会，说明配置还没有真正从代码里分离出去。

该文还指出一个容易被忽略的反模式：把配置按"环境"打包成命名组（development / test / production）。它不扩展——项目一大就会出现 staging、qa，然后是某个人的 joes-staging，配置组合爆炸，部署变得脆弱。十二要素主张配置项是彼此正交的细粒度开关，按每次部署独立管理，而不是按环境名分组。这条主张放在今天看更重要了，因为预览环境、按 PR 拉起的临时环境已经是常态，环境的数量本身就是动态的。

环境漂移：成因与治理

环境漂移指环境的实际状态逐渐偏离它应有的、被记录下来的状态。它几乎总是由"绕过流水线的善意操作"累积而成，而且极难察觉，因为每一次单独的操作都看起来合理。

漂移成因典型场景为什么难发现治理手段
紧急手工修复半夜直接改生产配置止血，事后忘记回填到仓库系统恢复了，没人再看手工变更必须留 24 小时内回填任务，并用漂移检测兜底
非声明式变更用命令行直接改副本数、加环境变量仓库里看不到，只在集群里存在声明式期望状态 + 控制器持续纠偏（见 ST28 第三章）
快照式基础设施从一台"配好的机器"做镜像，原始配置步骤已失传能用，没人敢动基础设施即代码，从零可重建
配置副本分叉staging 配置从生产复制后各自演进两边都"正常工作"同一模板 + 差异项显式列出，禁止整份复制
依赖隐式升级基础镜像用可变标签，重建后底座换了构建是绿的基础镜像按摘要固定

示例场景：某支付服务连续两个季度出现"预生产通过、生产报错"的发布事故，共 5 次。复盘发现根因是同一类漂移：预生产的连接池上限是仓库里声明的 50，而生产在一年前的一次容量救火中被手工改成 200 并从未回填。于是所有与连接数相关的行为在两个环境里表现不同。治理动作只有两条——打开控制器的自动纠偏让集群侧的手改在秒级被拉回，以及把所有手工变更强制走"临时授权 + 到期自动回填检查"。之后两个季度该类事故为 0。（本例为构造的典型场景，用于说明漂移的隐蔽性，非实测数据。）

五、分支策略如何决定流水线形态

分支策略常被当成一个团队偏好问题，其实它是一个约束流水线形态的结构性选择：分支模型决定了"集成在什么时候发生"，而流水线只能围绕这个时刻来组织门禁。

两种模型的对比

trunk-based development 主张所有人在一条主干上协作，用短生命周期分支做代码评审与构建校验，坚决不开长期并存的开发分支。官方站点把它的目标写成"避免合并地狱、不弄坏构建"，并明确指出：短生命周期的特性分支用于评审与 CI，但不用于制品的创建与发布；发布分支只在需要时从主干即时切出、硬化后发布、发布后删除。

Git Flow 则设计了 master 与 develop 两条无限生命周期的主分支，外加 feature、release、hotfix 三类支撑分支。值得注意的是原文作者在 2020 年补了一段反思：这个模型是 2010 年为显式版本化、需要同时支持多个在野版本的软件设计的；如果你的团队在做持续交付的 Web 应用，应该采用更简单的工作流（如 GitHub flow），而不是硬把 Git Flow 套进去。这段自述很重要，因为它把选型标准从"哪个更先进"换成了"你的软件是什么形态"。

分支寿命是一个可测量的杠杆：分支活多久，冲突就积累多久，集成风险就攒多大。把分支寿命从两周压到一天，不需要任何新工具，但它会把流水线的门禁效果放大数倍。

合并门禁：为什么"每个 PR 都是绿的"还不够

一个反直觉但常见的失败模式：两个 PR 各自在自己的分支上测试全绿，合并后主干却红了。原因是它们改动了彼此的语义而非同一行文本——A 删了一个函数，B 新增了对它的调用；Git 看不出冲突，编译器才看得出。分支越多、寿命越长，这类语义冲突越多。

解法是合并队列：不再验证"分支自身"，而是串行验证"分支与当前主干合并后的结果"，只有这个结果绿了才真正落地。trunk-based development 官方把合并队列列为超大规模场景下的形态。代价是合并吞吐受串行验证限制，所以它反过来又要求提交阶段足够快——第二章的时长预算在这里再次成为瓶颈。

特性开关：把"发布"与"上线"解耦

trunk-based development 要求未完成的功能也能进主干，这只有在功能可以被关掉时才成立，所以特性开关不是可选配件，而是这个模型的承重结构。它带来的根本转变是：部署变成一个技术动作，发布变成一个业务动作，两者可以在不同时间由不同角色执行。这也正是第一章里持续部署所缺的那块配套能力。

开关类型用途预期寿命由谁操作治理要点
发布开关让未完成功能安全地待在主干里天到周，功能上线后必须删开发者设到期日，过期进技术债清单
运维开关故障时降级、限流、关闭重负载特性长期值班工程师必须能在不发版的情况下改

开关的代价必须一起算：每个开关都在代码里引入一个分支，n 个开关理论上就是 2ⁿ 种运行组合，而你的测试只覆盖其中几条。所以发布开关必须有到期纪律——用完即删。开关长期不清理的团队最终会得到一份没人敢动的配置，这本身就是一种新形态的环境漂移。

六、流水线自身的工程质量

流水线是生产系统。它有可用性、有延迟、有成本、有故障率，也需要被当作代码来维护。团队常犯的错是把流水线当成一堆"能跑就行"的脚本，直到它变成交付的瓶颈。

缓存与增量：省时间的同时别省掉正确性

缓存的核心是缓存键设计，它必须精确表达"什么变了就该失效"。以 GitHub Actions 的缓存为例，其查找顺序是：先精确匹配 key，未命中则按 key 做前缀匹配，仍未命中则按顺序尝试 restore-keys，当前分支都没有才回退到默认分支查找。这个由精确到模糊的阶梯让你能在"完全命中"与"部分复用"之间取舍。

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-

注意缓存不是免费的。官方限制是：超过 7 天未被访问的缓存条目会被删除，单仓库缓存总量默认上限 10 GB，超限后按最后访问时间从旧到新驱逐。文档还特别提醒这会引发缓存抖动——缓存被高频创建又删除，于是既花了上传时间又几乎没有命中收益。所以缓存的粒度要控制：别把巨大的产物塞进通用缓存，那属于制品或持久卷的职责。

并行与依赖图

把流水线从"阶段串行"改成"依赖图"，能砍掉大量无意义的等待。GitLab CI 的 needs 就是把流水线变成有向无环图：作业只等它真正依赖的上游，常见形态有一对多的 fan-out、多对一的 fan-in 以及两者组合的菱形依赖。官方甚至支持完全省略 stages、只用 needs 描述顺序的"无阶段流水线"。

幂等与可重跑

幂等在流水线语境下有两层含义。第一层是重跑同一个提交应当得到同一个结论——做不到就说明流水线依赖了不该依赖的东西（当前时间、外部可变服务、上一次运行残留的工作目录、机器本地状态）。自托管执行机尤其容易犯这个错，因为它们默认不为每个作业提供干净实例。第二层是带副作用的步骤本身幂等：部署同一个制品两次应当收敛到同一状态；制品上传遇到同一坐标应当拒绝覆盖而非静默替换；数据库迁移应当可安全重放。两层都满足，"重跑"才是一个安全操作而不是赌博。

流水线即代码

流水线即代码指把流水线定义写成文件、放进被交付项目的版本库。Jenkins 官方把这称为 Pipeline-as-Code，并列出了四项直接收益：所有分支与 PR 自动获得构建流程、流水线改动可以像代码一样评审与迭代、天然具备审计轨迹、以及成为流水线的唯一事实来源。最后一条最关键——界面里手工点出来的任务配置没有历史、没有评审、没有回滚，而且往往只有一个人知道它为什么是那样。

构建时长与 flaky 测试的治理

flaky 测试指同一份代码多次运行结果不一致的测试。它的破坏性不在于偶尔挡住一次合并，而在于它训练团队忽略红灯。一旦"红了就点重跑"成为肌肉记忆，所有门禁的可信度同时下降，这时流水线仍在运行，但已经不再提供保护。

正确的治理是把它当缺陷管理，而不是靠自动重试掩盖。自动重试有两个隐性代价：它把非确定性的根因（竞态、时序依赖、共享状态未隔离）永久藏起来，而这些根因往往在生产环境同样存在；同时它成倍拉长流水线时长，又回头挤压第二章的反馈预算。

阶梯动作目的判定标准
1 量化记录每个测试的历史失败率与失败模式把"感觉很flaky"变成数字同提交多次运行失败率 > 0
2 隔离移出阻断门禁，进入观察集立刻恢复门禁可信度失败率超过约定阈值即自动隔离
3 定责指派到代码所有者，设修复期限避免进入"无人认领"黑洞有负责人与到期日
4 修复或删除到期未修复则删除该测试不确定的测试不如没有测试隔离集规模不得持续增长
5 防复发补测试隔离能力（时钟注入、独立数据、禁止跨测试共享状态）消除滋生土壤新增 flaky 数量趋零

示例场景：某团队流水线端到端阶段有 180 条用例，其中 14 条长期间歇性失败，平均每 3 次运行有 1 次红灯，团队的标准操作是重跑。一次真实缺陷（并发下订单状态回写丢失）被端到端测试正确捕获，但因为落在"经常红的那一片"，被连续重跑 3 次后放行，最终在生产暴露。此后团队把 14 条用例全部移出阻断集并限期两周修复，其中 9 条的根因是共享测试数据未隔离、3 条是固定 sleep 等待、2 条确实是被测代码的竞态。修复后阻断集失败即真缺陷，重跑习惯随之消失。（本例为构造的典型场景，用于说明 flaky 对门禁可信度的破坏，非实测数据。）

  • 提交阶段死守 5–10 分钟预算，超了就把慢检查往后挪，而不是加机器硬扛
  • 部署清单只引用内容摘要，让"运行的字节"可被审计
  • 基础镜像与第三方动作按摘要或提交哈希固定，不用可变标签
  • 配置按正交的细粒度变量管理，用"仓库能否开源"做泄露试纸
  • 阻断权只给确定且可操作的信号，其余转告警并记账
  • 发布开关设到期日，功能上线即删除
  • flaky 测试先隔离再限期修复，隔离集规模纳入月度复盘
  • 不要在每个环境重新构建，这会让预生产的验证结论失去指向对象
  • 不要把端到端全量测试挡在提交阶段，它会压低团队的合并频率
  • 不要用自动重试掩盖非确定性测试，根因通常在生产同样存在
  • 不要把配置按环境名打包成组，环境一多就是组合爆炸
  • 不要在界面里手工维护流水线配置，它没有历史也没有评审
  • 不要把几十 GB 的产物塞进通用构建缓存，会触发驱逐与缓存抖动
  • 不要让长生命周期分支与"我们在做 CI"这句话共存

Q&A

装了 Jenkins、每次推送都自动构建，为什么还不算持续集成？

因为持续集成的主语是"集成"，不是"构建"。自动构建解决的是"有人帮我跑测试"，持续集成解决的是"所有人的改动尽早合到一起并验证兼容"。如果团队有十几条各活两周的特性分支，每条分支自己的构建都是绿的，那这些绿灯只证明了每个人在自己的世界里没问题，没有任何一次构建验证过"大家合到一起"这个状态。trunk-based development 官方把持续集成的准入条件量化为所有成员至少每 24 小时向主干提交一次，正是因为频率才是这件事的实质。判断方法不看工具看两个数字：分支从创建到合入主干的中位寿命、以及主干变红后恢复绿色的中位时长。前者应当以小时或一两天计，后者应当以分钟计。

持续交付和持续部署之间差的那一步，到底难在哪？

难点通常不在技术管道，而在三样配套能力与一个授权决策。第一样是把"代码上线"与"功能对用户可见"解耦的特性开关机制，否则自动部署就等于自动发布未完成的功能。第二样是可靠的自动回滚路径，即指标劣化时系统能在无人干预下收敛回上一个已知良好状态。第三样是足够可信的线上可观测性，因为取消人工按钮意味着你放弃了"发布前人眼扫一遍"这道防线，必须用线上指标门禁替代它。授权决策则是组织层面的：谁来承担"没有人按按钮就上线了"的责任。缺了配套能力而强推自动部署，只是把风险从发布日的集中爆发改成了每天随机爆发。

提交阶段为什么一定要控制在几分钟内，慢一点有什么实质坏处？

坏处有三层，且会互相放大。第一层是上下文切换：几分钟内拿到结果，开发者还在同一个心智上下文里，修复是"接着改"；等半小时回来就要重新装载上下文，修复成本显著上升。第二层是排队堆积：提交阶段慢一倍，等待验证的提交就积压，团队的实际合并频率被迫下降。第三层是最致命的——合并频率下降会让每次合并的改动量变大，冲突与语义冲突随之增多，主干变红的概率上升，于是团队更不敢频繁合并，形成正反馈。所以提交阶段的时长不是体验指标而是吞吐指标，它直接决定团队能不能守住持续集成那条 24 小时准入条件。超预算时正确做法是把慢检查往后挪到集成或定时阶段，而不是加机器硬扛。

什么检查才配得上"阻断合并"的权力？

判定标准只有一条：这个信号必须既确定又可操作。确定的意思是它为真时缺陷一定存在，假阳性率足够低；可操作的意思是收到信号的人立刻知道该改什么。编译失败、单元测试失败、依赖高危漏洞、密钥泄露都同时满足，理应阻断。容易 flaky 的端到端用例、噪声较大的性能微小回归、刚引入还没清理完历史违规的新 lint 规则都不满足，应当转为告警并记账。把不确定的信号设成阻断有一个连带破坏：团队会学会"红了就点重跑"，而这个习惯一旦形成，真正确定的阻断信号也会被同样对待，整套门禁的可信度一起崩塌。换句话说，门禁的有效性取决于最不可信的那一条规则，而不是最严格的那一条。

为什么不能在每个环境各自重新构建一次，代码明明是同一个提交？

因为同一个提交不保证产出同一个制品。构建过程包含依赖解析，而依赖解析在两个时刻可能给出不同答案：某个间接依赖发布了新补丁版本、某个基础镜像的可变标签指向了新内容、编译工具链在两次构建之间升级了。Docker 官方也说明层缓存是以指令为粒度的，某一层变化会导致其后所有层重建，所以"同样的 Dockerfile 必然得到同样的镜像"从来不是可依赖的假设。后果是你在预生产验证过的那个二进制，和生产实际运行的那个不是同一个东西，于是预生产的全部验证价值归零——你验证的是一个再也不会运行的制品。正确做法是构建一次、产出不可变制品，之后的环境晋升只是元数据变更，部署时按内容摘要而非可变标签拉取。

已经有了语义化版本，为什么还需要构建号？

因为两者服务的受众和回答的问题完全不同。语义化版本是面向消费者的兼容性契约，由人根据变更意图决定：主版本变了意味着你需要改代码，次版本变了意味着有新能力但可以不改，补丁变了意味着可以无脑升级。它回答"我能不能升级"。构建号是面向流水线与审计的可追溯标识，由机器单调生成，它回答"这个二进制是从哪个提交、哪次运行、用了哪些依赖产出的"。一个语义化版本在发布过程中可能对应多次构建尝试，而生产事故定位需要精确到那一次。生产部署记录必须同时保留语义化版本、构建号、源码提交哈希与内容摘要：缺了第一个无法判断升级影响范围，缺了后三个无法定位来源，缺了摘要则无法证明运行的字节没有被换过。

trunk-based 和 Git Flow 到底该怎么选？

选型标准不是"哪个更先进"，而是"你交付的软件是什么形态"。Git Flow 原作者在 2020 年亲自补的反思注记说得最清楚：这个模型是为显式版本化、需要同时支持多个在野版本的软件设计的；如果团队在做持续交付的 Web 应用，应该用更简单的工作流而不是硬套 Git Flow。所以判据是：你是否需要同时维护多个已发布版本并向它们各自打补丁。需要（客户端应用、私有化部署、有长期支持版本承诺的产品）则 Git Flow 那套 release 与 hotfix 分支确有价值；不需要（线上只有一个版本的服务）则它引入的长期并存分支纯属成本，会把集成推迟、把冲突攒大。选了 trunk-based 就必须同时接受它的承重结构：特性开关是必需品，因为未完成的功能也要进主干。

特性开关看起来很好用，它的代价是什么？

最大的代价是组合爆炸与随之而来的认知负担。每个开关都在代码里引入一个运行时分支，n 个开关理论上对应 2ⁿ 种运行组合，而测试只覆盖其中极少数几条，于是线上可能跑在一个从未被验证过的组合上。第二个代价是清理纪律：发布开关本该功能上线后立即删除，但删除没有紧迫性，于是长期堆积，最终形成一份没人敢动的配置——这本身就是一种新形态的环境漂移。治理办法是按类型区别对待：发布开关必须设到期日，过期自动进技术债清单；运维开关长期存在但要求能在不发版的情况下修改；实验开关随实验周期回收；权限开关属于业务逻辑，应该放在业务配置里而不是混进技术开关系统。另外要记住开关本身是生产配置，它的变更同样需要审计与回滚能力。

flaky 测试能不能靠自动重试解决？

不能，自动重试是把问题藏起来而不是解决。它有两个隐性代价。第一个是掩盖根因：测试非确定的原因通常是竞态、时序依赖或共享状态未隔离，而这些缺陷在生产环境同样存在，重试让你失去了发现它们的唯一信号。第二个是成倍拉长流水线时长，回头挤压提交阶段的反馈预算，触发第二章说的那条负反馈链。更深的问题在于它训练团队忽略红灯：一旦"红了就点重跑"成为肌肉记忆，真正的缺陷信号也会被同样处理，这时流水线仍在运行但已不再提供保护。正确做法是把它当缺陷管理走五步阶梯：量化每个测试的历史失败率、超阈值自动移出阻断集、指派代码所有者并设修复期限、到期未修复则删除（不确定的测试不如没有测试）、最后补齐测试隔离能力防止复发。关键约束是隔离集的规模不能持续增长。
