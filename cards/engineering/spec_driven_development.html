ST26 · 规约驱动开发

规格作为跨会话长期上下文 / 与 PRD·TDD·Prompt 的边界 / 提案-设计-任务-验收 / 规格漂移治理 / 分层启用

AI 写代码越快，越要把「做什么」从聊天窗口里搬进仓库。Prompt 只服务这一次上下文；规格是给下一会话、下一个人、下一个 Agent 用的同一份意图。

Vibe Coding 的陷阱、Git 检查点与人工验收，见 ST16 与 ST25。Claude Code 产品侧的模式见前沿实践 HC04。本卡不教某个工具的命令行，只讲 规约驱动开发（Spec-Driven Development）：把需求变成可审查、可版本化、可被 Agent 反复加载的资产。

一、详细 Prompt 服务不了下一会话

一次写得很长的 Prompt 能管住这一轮 Agent。窗口一 compact、会话一关、换一个同事接着改，那堆约束就蒸发了。Agent 下一轮会重新猜意图，于是出现「局部修完、契约裂了」：单测是绿的，调用方的假设已经不是同一份。

聊天里的 Prompt仓库里的规格
寿命当前上下文随 Git 跨周、跨人
审查几乎不可 diffPR 里能评「意图变了没有」
对 Agent临时上下文可重复加载的长期上下文
失败模型忘了规格与代码双双过期（见第五节）
同一需求，两种载体 【Prompt】 人 → 长指令 → Agent → 代码 会话结束，指令消失，下一轮再猜 【规格】 人 → spec 进 Git → 评审 │ ├→ Agent 每轮 Read spec └→ 验收对照 spec 的成功标准

规格的对手不是「写文档慢」，而是「生成速度已经超过人类短期记忆」。没有规格，速度会把错误复制进更多文件。

二、规格与 PRD、TDD、聊天记录的差别

PRD 面向人和排期，常常太宽、太口号。TDD 面向可执行断言，常常太窄、写不出「为什么不能这样改」。聊天记录什么都有，什么都不能当契约。规格夹在中间：足够具体让 Agent 少猜，足够稳定让人能审。

载体好在哪单独用时缺什么
PRD业务目标、范围接口级约束、反例、非目标
规格意图 + 边界 + 验收不能代替测试；不能代替设计权衡记录
TDD / 单测机械裁判测不到没写的用例；测不到「不该做」
CLAUDE.md项目习惯不是这一次需求的成功定义（见 HC06）

一份能干活的规格至少要有：目标一句话、非目标（明确不做）、接口或行为契约、失败与回滚、怎么算做完。缺非目标时，Agent 会把范围长到「顺便重构」。

规格不是把 PRD 贴进 Markdown。它是把「允许的变化」和「禁止的变化」写成 Agent 每次开工都能 Read 到的约束。

三、仓库里的四件套：提案、设计、任务、验收

社区工具（OpenSpec 一类）把流程拆成 proposal / design / tasks 再加验证。名字不重要，四段职责不能混在一个文件里：提案解决「要不要做」，设计解决「约束是什么」，任务解决「顺序」，验收解决「机械上怎么知道做完」。

四段不要合成一团 proposal 动机、范围、非目标、风险 ← 人审「该不该做」 │ design 契约、数据、失败模式 ← 人审「这样改会不会裂」 │ tasks 可并行的小步、依赖 ← Agent 当清单，不当小说 │ verify 测试、类型、手工核对清单 ← 机械裁判优先（ST25）
段谁写谁审Agent 怎么用
提案人为主，Agent 可起草人必须过只读，禁止在提案未过时写业务代码
设计人 + Agent 共写人必须过实现时反复对照
任务Agent 可拆，人可改顺序抽查依赖一次只领一块，做完再领
验收人定标准，Agent 跑红线人签失败则停，不准改标准来迁就实现
示例场景：跨三个服务改鉴权头，无规格时 Agent 在第一个服务「修完」并提交。联调发现另外两个服务仍用旧头，回滚耗了一下午。改为先合设计规格（列出三个服务的契约与兼容窗口）再开工，Agent 按任务清单改全，联调一次过。多出来的规格评审约 25 分钟，换回的是一次未发生的半上线。

任务清单若写成实现小说，Agent 会把它当代码生成。任务应是可勾选的结果，不是伪代码。

四、和执行纪律、交付闭环怎么分层

社区把 OpenSpec、Superpowers、gstack 说成三件套，容易理解成必须全装。工程上它们是三层，可独立启用：

层管什么本库对应
规格做什么、不做什么本卡
执行纪律TDD、一次一块、禁止边写边扩范围ST16 / 技能与 Hook
交付闭环Review、浏览器 QA、Ship 检查ST25、ST19

不要在规格层模仿某个产品的目录名。目录可以是 docs/spec/，只要 Git 能 diff、Agent 知道路径、PR 模板强制链到规格即可。

分层启用（从轻到重） 两行 typo → 不用规格，ST25 检查点足够 单模块行为变更 → 迷你规格：目标 + 非目标 + 验收 跨模块 / 权限 / 钱 → 完整四件套 + 人审设计 持续产品线 → 规格目录成为长期上下文，进 CLAUDE.md 的索引而不是正文

工具可以换，三层不能乱。用执行纪律层去补「没写非目标」，会变成无穷的重写循环。

五、规格漂移：比代码更容易过期的资产

规格一旦进仓库，就会和代码一起腐烂，而且更危险：代码还有测试会红，规格没有测试。漂移的典型形状是实现已经改了兼容策略，规格仍写着旧窗口；下一会话的 Agent 读到旧规格，把新实现「修回去」。

漂移信号治理
PR 改代码不改规格CI 检查：相关目录变更必须动 spec 或显式 spec-unchanged: 理由
规格很长没人读拆短；过期章节直接删，不要「历史附录」堆在主文件
Agent 同时读规格和过时注释代码注释让位给规格；重复的说明只留一处
示例场景：支付回调规格写「允许重复通知，幂等键为 order_id」。后来实现改成「order_id + event_id」。六周后新会话按旧规格「简化」了幂等键，重复事件造成一次重复入账，对账抓出 17 笔。修复是规格与代码同 PR 改，并在验收里加重复事件用例。规格评审的时间远小于一次资金事故。

规格的维护成本和代码同级。不愿维护就不要写长文，写会过期的长规格比没有规格更糟——它会以权威口吻撒谎。

六、何时上、何时不要上

跨模块、权限、钱、兼容窗口：先规格后代码。

规格写非目标和验收；任务保持短、可勾选。

规格与代码同 PR；过期段落删除而不是注释掉。

不要给两行 bug 写四件套。

不要把规格当小说，也不要当未评审的 Prompt 备份。

不要在需求还每周改宗旨时冻结长设计。

需求仍在剧烈摆动时，只写一页「当前假设 + 过期日期」，到期必须重审。假装稳定的规格会把团队锁进错误方向，Agent 会非常勤奋地锁死它。

规格评审清单可以短：非目标是否写了、失败怎么回滚、验收是否机械可跑、有没有把本次需求写进 AGENTS.md。四条全过再让 Agent 写业务代码。评审超过半小时，通常是规格写成了设计论文，该拆任务而不是继续开会。

跨会话加载时只 Read 当前任务链到的那一份 spec，不要把整个 docs/spec/ 倒进上下文。规格目录是索引，不是又一个无限上下文。

规格合入后，把「非目标」抄进 Agent 的短备忘（一行即可）。下一会话最常见的翻车是：人记得别动计费，Agent 只看见任务清单上的「加上优惠」。非目标不进工作记忆，等于没写。

Q&A

这和再写一份详细 PRD 有什么不同？
PRD 服务人和排期，通常不写非目标、失败模式、兼容窗口这些 Agent 最爱猜错的东西。规格服务「下一会话还能加载的契约」，必须能被 Read、能被 diff、能被验收对照。可以把 PRD 链过来，但不能拿 PRD 代替契约。
必须用 OpenSpec 吗？
不必。它只是把四段流程产品化了。Git 里结构清晰、PR 强制关联、Agent 约定路径，就满足本卡。选工具看团队是否需要脚手架，不看品牌。
规格会不会让 AI 编程又变慢？
在两行修改上会。在跨模块改动上，规格把返工从「联调爆炸」前移到「二十五分钟评审」。比的是事故成本不是第一次按键到第一次 commit 的时间。
和 ST25 的 AGENTS.md、检查点如何配合？
AGENTS.md 写习惯和禁区；规格写这一次需求。检查点保证能回滚。三件套：习惯（长期）、规格（本次意图）、检查点（失败恢复）。不要把本次需求写进 AGENTS.md，否则项目记忆会被功能需求污染。
Agent 起草规格，人还要审吗？
要，而且审的是非目标和失败模式，不是文笔。Agent 起草能加速，人签字才能当契约。提案未过就写业务代码，规格会变成对既成事实的说明文。
测试已经很多了，为什么还要规格里的验收段？
测试覆盖已实现行为。规格验收覆盖「我们答应过的行为」，包括故意不实现的分支。没有这一段，Agent 会为了让测试绿而改测试，或者漏掉「重复回调必须幂等」这种跨服务属性。
规格文件放哪，Agent 才找得到？
固定目录 + 在 CLAUDE.md / AGENTS.md 里只放索引路径，不把规格正文贴进项目记忆。每次任务在规格里写自己的链接。找不到的规格等于不存在，Agent 会回到猜。
规格和 issue 系统（Jira）如何同步？
Issue 管流程状态，规格管契约。链接双向即可，不要把验收标准只放在 issue 评论里——Agent 默认不读评论历史。状态变更可以脚本回写，契约变更必须走 Git。
多人同时改同一份规格怎么办？
按任务拆文件，避免万人编辑同一篇。冲突时停 Agent 写代码，先把规格合完。规格冲突却继续生成，是把分歧实现进仓库。
