ST06 · 缓存策略

商业化缓存不是"加个 Redis"，而是把重复请求、热点任务和昂贵上下文变成可复用资产，直接降低延迟和毛利压力

一、商业化项目为什么一定要做多层缓存

缓存的商业价值有三层：省钱、省时、稳态。前两层大家容易理解，第三层更重要，因为缓存能把流量高峰从"打爆模型"变成"命中已有结果"。
层级复用对象直接收益常见场景
L1 · Prompt Cache稳定前缀降低输入成本固定 system prompt、统一工具定义
L2 · Semantic Cache整条问答结果减少完整模型调用客服 FAQ、制度问答、标准解释
L3 · KV Cache推理中间状态提升吞吐、降低时延自建推理服务、长上下文生成
用户请求 | +--> L1 Prompt Cache: 命中固定前缀，减少输入计费 | +--> L2 Semantic Cache: 命中整条答案，直接返回 | +--> L3 KV Cache: 未命中时进入推理层，复用推理状态 商业数据流: 热点问题越多，L2 价值越高 稳定模板越多，L1 价值越高 自建推理越多，L3 价值越高
在 AI/LLM 系统中，缓存命中率 不只是性能指标，它直接等价于"毛利率改善幅度"。每命中一次 L2 缓存，相当于省掉一次完整的模型推理调用，按 GPT-4 级别模型计算，单次调用成本约 ¥0.3-1.5，日均百万请求下，40% 命中率意味着每天节省 ¥12-60 万。
生产数据参考：某头部电商客服平台上线多层缓存后，L1 命中率达到 72%（前缀标准化程度高），L2 语义缓存命中率 47%，综合 Token 成本下降 38%，P95 延迟从 6.9s 降至 2.4s，GPU 峰值负载下降 55%。

二、三层缓存各自适合哪些业务，不适合哪些业务

选缓存层不是选"哪个更快"，而是选"哪个复用风险最低"。L1 复用前缀几乎没有语义风险，L2 复用整条答案有业务风险，L3 复用推理状态有工程风险。风险层级不同，治理手段完全不同。

L1 · Prompt Cache

最适合模板稳定、前缀高度一致的 SaaS 产品，比如客服、文案生成、报表总结。它的优势是几乎不影响回答质量，因为复用的是相同前缀而不是猜测相似语义。真正的难点在于把动态变量挪到后面，否则一点小变化就会导致整段前缀失效。

适合不适合关键设计
固定 system prompt、统一工具说明前缀里夹杂时间戳、随机 ID、用户画像变化把稳定内容前置，动态内容后置

L2 · Semantic Cache

最适合高频重复问答，例如"运费怎么算""发票怎么开""年假怎么申请"。商业价值很高，因为它直接省掉一整次模型调用。但它也最容易把错误答案放大，一旦阈值过低或 TTL 过长，过时政策会被快速复制给大量用户。

适合不适合关键设计
标准 FAQ、静态制度、低个性化问答个性化强、强实时、与订单状态强绑定的问题相似度阈值、TTL、版本隔离、人工抽检
语义相似度阈值选择：生产环境中，cosine similarity 阈值设置在 0.92-0.95 之间通常能取得较好的准确率与覆盖率平衡。低于 0.88 会显著增加错误匹配风险（约 3-5% 的误匹配率），高于 0.97 则命中率过低（通常不到 15%），失去缓存意义。

L3 · KV Cache

对自建推理服务最重要。它不直接减少业务语义成本，而是提升 GPU 利用率和首 Token 速度。在商业化产品里，如果你是走第三方 API，L3 影响相对间接；如果你在自建 vLLM 或 TGI 集群，L3 直接关系到单位 GPU 能承载多少请求。

适合不适合关键设计
长上下文生成、代码场景、Agent 长链路完全依赖第三方托管 API 且无推理控制权PagedAttention、KV 量化、显存监控
PagedAttention 是 KV Cache 领域最重要的工程突破之一。它把显存分配方式从"连续预分配"改为"按需分页"，使 KV Cache 的显存浪费率从平均 60-80% 降低到 4% 以内，相当于同一张 GPU 可以多承载 2-4 倍并发请求。

三、缓存上线时必须先解决三个商业问题

问题如果不解决会怎样推荐做法
一致性缓存命中过期答案，业务口径错误按知识版本、租户、模型版本分桶缓存
收益归因不知道缓存到底省了多少钱记录命中率、节省 Token、节省时延
风险隔离一条错误缓存被大规模复用灰度启用、热点抽检、可快速清空命中池

很多团队把命中率当作唯一指标，这是不够的。更实用的商业指标是：每种缓存层分别省下多少 Token、减少多少 P95 延迟、减少多少峰值 GPU 压力、有没有引入新的错误回答。命中率高但答错更多，这种缓存没有商业价值。

版本隔离和灰度治理要单独设计

治理点推荐做法不这样做的后果
知识版本隔离缓存键带知识库版本号或发布时间新旧口径混用，错误答案持续命中
模型版本隔离不同模型单独命中池不同模型输出风格和质量混在一起
灰度开启先对低风险流量启用缓存，再逐步扩大一旦有错误缓存会瞬间放大到全量用户
热键巡检定期抽查最高命中的前 N 条缓存最危险的热点错误最晚被发现

缓存和模型一样，都应该灰度发布。因为缓存是"放大器"，对的答案会被放大，错的答案也会被放大。商业系统必须先证明它不会放大错误，再追求更高命中率。

缓存键设计规范（生产级示例）: cache_key = hash( tenant_id // 租户隔离 + knowledge_version // 知识库版本 + model_version // 模型版本 + normalized_query // 归一化后的用户查询 + locale // 语言/地区 ) 分桶策略: ┌─────────────────────────────────────────────┐ │ Bucket A: tenant_001 + kb_v3.2 + gpt4o │ │ Bucket B: tenant_001 + kb_v3.2 + gpt4o-mini│ │ Bucket C: tenant_002 + kb_v3.1 + gpt4o │ │ ... │ └─────────────────────────────────────────────┘ 每个 Bucket 独立管理 TTL、命中统计和清空操作

四、案例：客服 FAQ 缓存改造

背景：某客服机器人日均处理 180 万次咨询，其中前 200 个问题占总流量 61%。

问题：全部请求都进大模型，晚高峰延迟经常飙到 8 秒以上，成本也在节节上涨。

改造：前缀模板统一化，启用 Prompt Cache；对 FAQ 类问题增加 Semantic Cache，并按知识库版本号分桶；热点类问题每 2 小时抽检一次，异常可一键清空缓存。

效果：整体请求命中率 47%，输入 Token 成本下降 38%，P95 延迟从 6.9 秒降到 2.4 秒，客服满意度基本持平。

关键指标变化一览：
• L1 Prompt Cache 命中率：72%（稳定前缀复用）
• L2 Semantic Cache 命中率：47%（FAQ 场景）
• 输入 Token 成本下降：38%
• P95 延迟：6.9s → 2.4s（降幅 65%）
• GPU 峰值负载下降：55%
• 客服满意度评分：4.2/5.0 → 4.1/5.0（基本持平）
• 错误答案率：0.3% → 0.5%（可控范围内微升）

说明：成本视角案例（B2B 客服月账单 $45,000→$12,000、命中率 52%、延迟 6.2s→1.8s）见《Token 成本优化》（ST04），与本节为不同案例，请勿混淆。

这个案例最核心的发现不是命中率有多高，而是"错误答案率只上升了 0.2 个百分点"。缓存的商业价值 = 命中率 × 节省成本 - 错误放大代价。如果错误率飙升，再高的命中率也是负收益。
  • 把稳定前缀标准化，先吃到 Prompt Cache 红利
  • 语义缓存先从标准 FAQ 和低风险场景试点
  • 缓存键里加入知识版本、租户、模型版本
  • 同时监控命中率、节省成本和错误率
  • 为错误缓存准备快速失效和回滚机制
  • 只看命中率，不看错误答案是否被放大
  • 所有场景统一用一套语义阈值
  • 缓存永不过期，假设知识永远正确
  • Prompt 前缀夹杂动态字段，导致 L1 无法命中
  • 把缓存当万能优化，忽略模型路由和压缩

五、缓存失效策略与生产监控

缓存失效比缓存建设更重要。在 AI 系统中，知识更新频率快、模型迭代频繁、业务口径随时调整，一个没有失效策略的缓存系统本质上是一个"错误放大器"。

常见缓存失效策略对比

失效策略原理适用场景优点缺点
TTL 过期缓存条目在固定时间后自动失效知识更新周期可预测的场景实现简单，无需外部通知过期窗口内可能命中旧数据
事件驱动失效知识库更新时主动发送失效消息知识更新事件可捕获的场景实时性强，失效精准需要事件管道，架构复杂度增加
版本号失效缓存键包含版本号，版本变更自然失效知识库有明确版本管理的场景无竞态条件，新旧版本并存安全旧版本缓存占用空间直到自然过期
LRU 淘汰缓存满时淘汰最近最少使用的条目缓存空间有限的场景自动管理空间，热点数据保留不关心数据时效性，可能保留过时热点

六、缓存策略综合对比

没有"最好的缓存策略"，只有"最适合当前业务阶段的缓存策略"。早期产品优先做 L1（成本最低、风险最小），流量起来后加 L2（收益最大），自建推理后再做 L3（工程要求最高）。

决策建议：如果你的产品处于早期阶段（日请求量 < 10 万），先做好 L1 即可，投入产出比最高。当日请求量突破 50 万且存在明显热点问题时，加入 L2 语义缓存。当你开始自建推理集群或需要极致延迟优化时，再投入 L3。过早投入 L3 而不做 L1/L2 是常见的优先级错误。

Q&A

为什么说 Semantic Cache 价值高但风险也最高？

因为它省掉的是整次模型调用，收益最大；但它复用的也是整条最终答案，一旦答案过期或不适用于当前用户，就会把错误直接放大。所以 Semantic Cache 非常依赖版本隔离、阈值设置和场景边界管理。

Prompt Cache 为什么常常命中不上？

最常见原因是把动态变量写进了前缀，例如时间戳、用户昵称、临时参数、调试信息。Prompt Cache 要求前缀高度一致，所以工程上要把稳定内容前置，把变化内容后置，才能真正吃到缓存收益。

缓存会不会影响答案正确性？

会，尤其是 L2 语义缓存。如果知识实时性强、个性化强、答案依赖实时订单或权限状态，盲目缓存会直接造成业务错误。因此缓存不是纯性能组件，而是业务策略组件，必须结合 TTL、版本号和风险分级一起设计。

什么时候应该先做缓存，而不是先做模型降级？

当流量里存在大量重复请求、标准模板、固定前缀或热点 FAQ 时，应优先做缓存。因为缓存对质量影响通常比模型降级小，而且收益来得更快。模型降级更适合任务分层明确之后再做，用来进一步扩大利润空间。

如何确定 Semantic Cache 的相似度阈值？

生产环境推荐从 0.93 起步，然后按业务场景微调。具体做法：先收集 1000+ 条真实查询对，人工标注"是否应该命中同一缓存"，然后绘制 Precision-Recall 曲线。一般金融、医疗场景需要更高阈值（0.95+），客服 FAQ 可以适当放宽到 0.90-0.92。关键是要有持续的 A/B 测试机制来验证阈值效果。

缓存冷启动问题怎么解决？

冷启动（如服务重启或缓存清空后）会导致命中率骤降、模型负载突增。常见解决方案包括：（1）预热——从历史查询日志中提取热点查询，提前写入缓存；（2）渐进式启用——冷启动期间只对部分流量启用缓存查询，逐步扩大；（3）双层缓存——本地内存缓存 + 分布式缓存，本地缓存作为热备。生产环境中预热通常能在 15-30 分钟内将命中率恢复到正常水平的 80% 以上。

多租户场景下缓存隔离怎么做？

多租户缓存隔离需要在缓存键中包含租户标识（tenant_id），确保不同租户的数据完全隔离。同时要注意：（1）不同租户可能有不同的知识库版本，需要双重隔离；（2）热点租户的缓存不能挤占其他租户的缓存空间，建议按租户分配缓存配额；（3）租户数据删除（GDPR 合规）时需要能精确清除该租户的所有缓存条目。推荐用 Redis 的 HASH + EXPIRE 或独立的命名空间来实现。

KV Cache 的 PagedAttention 和传统连续分配有什么区别？

传统 KV Cache 为每个请求预分配连续的显存空间（按最大序列长度），导致大量显存浪费（平均 60-80%）。PagedAttention 借鉴了操作系统的虚拟内存分页思想，将 KV Cache 分成固定大小的块（类似 page），按需分配。这带来三个核心优势：（1）显存浪费降到 4% 以内；（2）支持跨请求共享 KV 块（如共享 system prompt 的 KV）；（3）支持更灵活的并行采样和 beam search。在 vLLM 中，PagedAttention 使吞吐量提升了 2-4 倍。
