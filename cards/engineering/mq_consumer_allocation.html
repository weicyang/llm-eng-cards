ST23 · MQ 消费者分配策略：RocketMQ 与 Kafka 的负载均衡设计

队列-消费者绑定规则 / RocketMQ 四策略演进 / 一致性哈希与虚拟节点 / Coordinator + Consumer Leader / KRaft 选举 / Rebalance 治理

MQ 负载均衡的本质是给"队列 ↔ 消费者"画一张绑定账本：RocketMQ 让每个消费者用同一算法各自算出自己那份，Kafka 让一个组长统一算、服务端只负责分发。所有策略演进（切段 → 环形 → 一致性哈希 → 同机房）都在追求同一件事——让"重画账本"的代价越来越小。

一、问题定义：队列-消费者绑定规则

消息中间件为了扛住高并发，会把一个 Topic 物理切分：RocketMQ 叫 MessageQueue（消息队列），Kafka 叫 Partition（分区）。消费端则把多个消费者实例组成一个 Consumer Group（消费者组） 共同消费。负载均衡要回答的问题只有一个：哪个队列归哪个消费者？

Topic: order-topic (6 个队列) Consumer Group: order-service ────────────────────────── ──────────────────────────── Q0 ──────────────────────────────────────► C1 Q1 ──────────────────────────────────────► C1 Q2 ──────────────────────────────────────► C2 Q3 ──────────────────────────────────────► C2 Q4 ──────────────────────────────────────► C3 Q5 ──────────────────────────────────────► C3 绑定规则： ① 同组内，一个队列同一时刻只能绑定给 1 个消费者（不抢活） ② 一个消费者可同时绑定多个队列（能者多劳） ③ 不同消费者组各自拿到全量消息（组间发布-订阅，互不影响） ④ 消费者数 ＞ 队列数 → 多出来的消费者空转，收不到任何消息

"同组一队列单消费者"是铁律：若两个消费者同时读同一队列，offset（消费位点）会互相踩踏，重复消费与乱序随之而来。RocketMQ 该规则只约束集群消费模式，广播模式下人人拿全量、无需分配。

建立/变更这张绑定表的过程就是 Rebalance（重平衡）。它不是免费的：重平衡期间消费暂停、可能重复消费、位点回退。两家框架的触发条件高度相似，但执行节奏不同。

重平衡的代价是量出来的：一个持有数百个分区的大型消费者组，一次传统（Eager）重平衡可以让全组停顿数秒乃至数分钟；期间消费吞吐归零，消费延迟（lag）按锯齿状飙升。重平衡不是"系统抖动"，而是每次成员变更都要支付的一笔账。

绑定表就是消费的账本：账本清晰则不抢活、不漏活；账本频繁重画（重平衡风暴），重复消费和延迟堆积就会接踵而至。

评估一个分配策略，先算两笔账：一次"重画账本"要花多久（停顿与重复消费），成员变更有多频繁——策略的总代价 = 单次代价 × 变更频率，后文所有策略差异都是在这两个乘数上做文章。

二、RocketMQ 四种分配策略

RocketMQ 是去中心化设计：同组每个消费者拿到"排序后的队列全量列表 + 排序后的消费者列表"，独立运行同一个分配算法，算出属于自己的子集。输入相同、算法相同，结果天然一致，不需要中央裁判。内置四种策略正好构成一条演进链：绝对公平 → 物理摊险 → 最小变更 → 拓扑感知。

策略实现类一句话原理解决什么留下什么
AllocateMessageQueueAveragely（默认）队列切段，按消费者顺序分段领取简单、绝对平均物理单点故障
AllocateMessageQueueAveragelyByCircle像发扑克牌一样一人一张轮流发风险跨 Broker 摊平成员变化即全局抖动
AllocateMessageQueueConsistentHash队列和消费者上哈希环，顺时针就近归属增减成员只迁移局部环上拥挤导致倾斜（需虚拟节点）
AllocateMachineRoomNearby同机房队列优先绑定同机房消费者消灭跨城拉取延迟依赖机房元信息配置

切段平均分配 AllocateMessageQueueAveragely —— 默认选择与它的物理单点

8 队列 ÷ 3 消费者 = 2 余 2 → 前 (余数=2) 个消费者各多拿 1 个：C1 拿 3、C2 拿 3、C3 拿 2
队列物理布局： q0 q1 q2 q3 │ q4 q5 q6 q7 ─── broker-a ───│─── broker-b ─── 切段分配结果（按顺序切成连续的段）： C1 ──► q0 q1 q2 ◄── 三个队列全在 broker-a 上！ C2 ──► q3 q4 q5 C3 ──► q6 q7 broker-a 宕机时： C1 ──► [全部不可用] 直接空转 ◄── 物理单点故障 C2 ──► q4 q5 （丢 q3，压力 +50%） C3 ──► q6 q7 （不受影响）

切段法数学上最平均，但队列在物理上按 Broker 聚集。连续的段容易整体落在同一台 Broker 上，一台机器故障就让对应消费者"断粮"，而别的消费者却完好无损——逻辑平均掩盖了物理不均。

优点缺点适用
实现极简、分配绝对平均、结果稳定可复现队列段与 Broker 强绑定，单 Broker 故障打瘫对应消费者单机房、Broker 数量多且队列交错分布的场景

环形分配 AllocateMessageQueueAveragelyByCircle —— 摊平风险与全局抖动

像发扑克牌：q0→C1, q1→C2, q2→C3, q3→C1, q4→C2, q5→C3, q6→C1, q7→C2 C1 ──► q0(broker-a) q3(broker-a) q6(broker-b) C2 ──► q1(broker-a) q4(broker-b) q7(broker-b) C3 ──► q2(broker-a) q5(broker-b) broker-a 宕机 → 每个消费者只失去 3 个队列中的 1 个，风险被均匀摊薄 但：新加一个 C4 → 发牌轮次全变 → 所有绑定关系推倒重来 → 全局抖动

环形法把每个消费者的队列打散到不同 Broker 上，任何一台机器故障，所有消费者等比例受损而非某一家阵亡。代价是它对成员变化零容忍：人数一变，发牌序列整体重排，每个队列的归属几乎全变，全员进入重平衡停顿。

优点缺点适用
队列跨 Broker 交错，物理风险均匀摊平增减消费者导致全量绑定重排，全局抖动成员稳定、看重故障均匀分布的场景

一致性哈希 AllocateMessageQueueConsistentHash —— 局部迁移与虚拟节点

一致性哈希（Consistent Hashing） 把 0 ~ 2³²−1 的哈希值空间首尾相接成一个环：消费者 ID 哈希后作为节点钉在环上，队列哈希后落在环上某点，从该点顺时针走，遇到的第一个消费者就是它的归属。它的目标不是"分得更公平"，而是"变化的时候动得更少"。

0° │ C3 ● │ ● C1 ╲ │ ╱ q5 → ╲ │ ╱ ← q1 ╲ │ ╱ q4 → ● C2 ← q2 │ 180° 规则：队列从落点顺时针走，遇到的第一个消费者即归属 q1 → 顺时针遇 C1 → 归 C1 q4 → 顺时针遇 C2 → 归 C2 新加 C4（落在 C3 与 C1 之间的弧上）： 只有 "C3 → C4" 弧段内的队列改归 C4 其余队列归属纹丝不动 → 迁移范围 ≈ 队列总数 / 消费者数 对比切段/环形：成员一变，近乎 100% 绑定重排

但一致性哈希有个软肋：消费者在环上的位置是哈希决定的，若几个消费者挤在环的一侧，某段巨大的弧只归一个消费者管——队列分布稍微不均，就会出现"一个消费者扛 90% 队列"的倾斜。解药是 虚拟节点（Virtual Node）：每个物理消费者在环上克隆出多个虚拟节点均匀散开，队列先归虚拟节点，再映射回物理消费者。RocketMQ 的该策略默认每个消费者挂 10 个虚拟节点，工程上常见取值是 100~512 个。

负载偏差 ≈ O(1/√T)，T 为虚拟节点数：T=256 时，95% 置信度下每个节点负载落在期望值 ±6% 内
虚拟节点数 T均匀度元数据/查找开销故障时负载去向
1（裸环）差，偏差可达平均值的 2~3 倍最低全部压给顺时针下一个邻居（连环故障风险）
10（RocketMQ 默认）明显改善低分摊给多个邻居
100~512（工程常用）接近理想均匀中等几乎均摊到全环
优点缺点适用
增减成员只迁移约 1/N 的队列，局部变更、抖动最小无虚拟节点时易倾斜；实现复杂度最高频繁扩缩容、弹性伸缩的消费组

同机房分配 AllocateMachineRoomNearby —— 跨城双活的必修课

北京机房 BJ 上海机房 SH ┌──────────────────────────────┐ 26ms ┌──────────────────────────────┐ │ broker-bj-1 broker-bj-2 │ ◄──跨城专线──► │ broker-sh-1 broker-sh-2 │ │ 队列 q4 q5 q6 q7 │ RTT │ 队列 q0 q1 q2 q3 │ │ 消费者 C-bj-1 C-bj-2 │ │ 消费者 C-sh-1 │ └──────────────────────────────┘ └──────────────────────────────┘ 默认切段分配（按队列名排序切段）： C-bj-1 ──► q0 q1 q2 ◄── 全在上海！每次拉消息先付 26ms 跨城往返 C-bj-2 ──► q3 q4 q5 ◄── 1 个本地 + 2 个跨城 C-sh-1 ──► q6 q7 ◄── 全在北京！ AllocateMachineRoomNearby： 第一步：同机房内先配对（内部包一个 Averagely 策略） C-bj-1 ──► q4 q5 C-bj-2 ──► q6 q7 C-sh-1 ──► q0 q1 q2 q3 第二步：某机房消费者死光时，剩余队列兜底分给其他机房（降级保底）

跨城专线往返通常在 20~30ms 量级，是同机房网络延迟（亚毫秒）的几十倍。拉取频率一高，跨城延迟会把消费吞吐和端到端延迟一起拖垮——算法再精妙也救不了物理距离。该策略要求实现一个 MachineRoomResolver，告诉框架"队列属于哪个机房（按 brokerName 前缀解析）"和"消费者部署在哪个机房（按 clientID 前缀解析）"。另有更严格的 AllocateMessageQueueByMachineRoom：直接配置 consumeridcs，消费者只消费指定机房的队列，其余队列不分配（无兜底）。

生产案例 · 跨城拉取消除：某金融系统京沪双活，16 个队列跨两机房、5 个消费者，默认切段分配下跨机房拉取占比约 50%，单次拉取往返 p99 达 28ms，消费端到端延迟 p99 约 1.8s。切换 AllocateMachineRoomNearby 后，正常态跨机房拉取占比降为 0，拉取往返 p99 降至 1.2ms，消费延迟 p99 从 1.8s 回落到约 120ms；且单机房消费者全挂时，队列可自动被另一机房兜底接管。
优点缺点适用
消灭跨城拉取延迟，兼有故障兜底需自行维护机房解析逻辑与命名规范同城双活 / 异地多活部署

四种策略是一条演进链：切段追求"分得平均"，环形追求"坏得均匀"，一致性哈希追求"改得最少"，同机房追求"离得最近"——每一代都在补上一代的致命伤。

三、Kafka：客户端算账，服务端跑腿

Kafka 的分配策略（Range / RoundRobin / Sticky / CooperativeSticky，甚至可以自己写）全部实现在客户端。分区数据明明在服务端，"怎么分"却由客户端说了算——这套机制靠三个角色配合完成：Coordinator（协调者） 是 Broker 侧对接某个消费者组的秘书，Consumer Leader（组长） 是消费者侧被临时点出来的算账人，Controller 则在幕后掌管集群元数据（下一节展开）。

消费者 C1 消费者 C2 消费者 C3 │ │ │ │ ① JoinGroup │ ① JoinGroup │ ① JoinGroup ▼ ▼ ▼ ┌────────────────────────────────────────────────────┐ │ Group Coordinator（某个 Broker 担任） │ │ 定位公式：__consumer_offsets[ hash(groupId) % 50 ] │ │ 该分区的 Leader 即 Coordinator │ └────────────────────────────────────────────────────┘ │ ② 第一个 JoinGroup 的 C1 被点为组长（Consumer Leader） │ ③ 下发全组成员的订阅信息 + 相关 Topic 的分区元数据 ▼ C1 在本地执行分区分配算法（partition.assignment.strategy） │ ④ SyncGroup：把整张分配表带回给 Coordinator ▼ Coordinator 在每个人的 SyncGroup 响应里， 只塞回"属于你自己的那份"分配结果 → 全组达成一致
角色所在位置职责不做什么
CoordinatorBroker 侧（按 groupId 哈希固定到某分区 Leader）收 JoinGroup/Heartbeat，发起重平衡，转发分配结果不计算分配方案，也不懂全集群分区布局
Consumer Leader消费者侧（第一个加入的成员）拉取元数据，本地算出整张分配表不做持久化，挂了下次重平衡换人重算
普通成员消费者侧发心跳、等结果、按分配表拉消息不参与计算
ControllerBroker 侧（全集群唯一）提供分区元数据的权威来源不介入消费组的具体分配
Coordinator 定位：coordinator = Leader( __consumer_offsets[ abs(hash(groupId)) % 50 ] ) —— 问任何 Broker 都会指路到同一个节点

为什么把最核心的"分蛋糕权"放在客户端？这是刻意的解耦设计。对比两种放置方式：

维度分配逻辑放服务端分配逻辑放客户端（Kafka 现状）
换一种分配算法停机升级整个 Kafka 集群改业务代码，重启自己的消费者即可
算法出 bug全公司所有消费组陪葬只影响自家应用，回滚即恢复
服务端复杂度要理解一切业务语义（同机房、粘性、机架感知……）只需当"跑腿的"，协议稳定
策略不一致风险不存在同组成员策略需一致（由 groupId 内的约定保证）
演进成本每次迭代动集群客户端各自演进，服务端无感

"客户端算账，服务端跑腿"是一次权力的开源：服务端只保证"账本分发到位"，把"怎么算账"的权力让渡给业务方，换来的是服务端协议的长期稳定。

补充一个演进方向：Kafka 4.x 时代引入的新消费者协议（KIP-848）开始把分配计算挪回服务端的 Group Coordinator，用服务端 assignor 换取"重平衡不再全组停顿"。注意这并不推翻上面的设计逻辑——它换掉的是经典协议里"每次重平衡都全员重新算账"的低效环节，而不是要把业务定制权收回去。

对照来看：RocketMQ 走"分布式各算各的"，靠排序保证输入一致；Kafka 走"组长统算、服务端分发"，靠 Coordinator 保证结果一致。殊途同归——都避免了让服务端承担业务分配逻辑。

四、选举的反差：董事会级严谨与先到先得

同样是"选一个管事的"，Kafka 服务端选 Controller（控制器） 极尽严谨，客户端选 Consumer Leader 却随意到只有四个字：先到先得——谁第一个向 Coordinator 发出 JoinGroup，谁就是组长。反差背后是资产价值的差异。

服务端 Controller：从抢临时节点到 Raft 董事会

旧时代（依赖 ZooKeeper）： Broker-1 ─┐ Broker-2 ─┼──► 争相创建 ZK 临时节点 /controller Broker-3 ─┘ 谁先建成谁当 Controller（ZK 强一致性保证唯一） 会话约 18s：失联 → 节点消失 → 全员重新抢 新 Controller 必须从 ZK 全量重建元数据（几十万分区要分钟级） 新时代（KRaft，Kafka 4.0 起唯一模式）： ┌─── 元数据仲裁组（3 或 5 个 Controller）───┐ │ C1 ◄──Raft 投票──► C2 ◄──Raft 投票──► C3 │ │ 多数派选出 Active Controller（日志最新者） │ │ 其余为热备，持续追 __cluster_metadata 日志 │ └───────────────────────────────────────────┘ 元数据即日志：写入走 Raft 多数派确认 → 强一致 Leader 故障 → 热备秒级接班（无需重建，<1s）

老架构里所有 Broker 像抢椅子一样扑向 ZooKeeper 的 /controller 临时节点，集群一大，几百节点同时抢就是网络风暴；而且新 Controller 上任要从 ZK 全量拉元数据，分区一多恢复以分钟计。KRaft（Kafka 自研的 Raft 元数据模式）干脆干掉 ZooKeeper：挑 3 或 5 个节点组成"董事会"，用 Raft 投票选出 Active Controller，元数据存进内部 Topic __cluster_metadata，热备节点全程追日志，接班不需要重建任何东西。

客户端 Consumer Leader：先到先得，以及为什么敢这么随意

维度服务端 Controller 选举客户端 Consumer Leader 选举
守护的资产全集群元数据：分区 Leader、ISR、Topic 配置一次分配计算（临时结果）
选错的后果元数据脑裂 → 数据丢失 / 双写无所谓：重平衡重算一遍即可
状态性有状态，必须持久化且可恢复无状态：成员+订阅+分区 → 确定性输出
选举方式ZK 抢节点 → KRaft Raft 投票先到先得（首个 JoinGroup 者）
选举频率极低（只在故障时）每次重平衡都选
能承受的开销昂贵也值得（几年一遇）必须廉价（一天可能发生几十次）
组长挂了怎么办—Coordinator 发起新一轮重平衡，自动换新组长

选举的严谨程度与它守护的资产价值成正比：Controller 管着集群的"房产证"，必须 Raft 公证；Consumer Leader 只是临时会计，账算错了重算就是，先到先得反而是最优解。

同一框架内的刻意反差：服务端为选 Controller 引入了完整共识协议，把故障接班从分钟级压到亚秒级；却对客户端组长选举零投入。因为组长的产出（分配表）可由确定性输入重新推导，任何"严谨选举"带来的收益都会被重平衡的高频率稀释成负收益。

生产案例 · 重平衡风暴：扩容反而让延迟涨得更快

lag（积压） 3.5M ┤ ╭── 锯齿状：每 ~5min 一轮重平衡 2.1M ┤ ╭────────────╯ 800k ┤ ╭───────────╯ 20k ┼─────────────╯ └─────┬───────┬───────┬───────┬───────┬──► 时间 正常运行 发布变更 扩容20→40 风暴持续 止血稳定 (+1次DB调用) (越扩越糟) (T+45min) (T+90min)
背景 → 问题 → 根因 → 止血 → 效果：某订单管道（Kafka → 消费者 → 数据库写入），一次发布让每条消息多了一次数据库调用，单批处理时间从 2s 涨到 380s，超过 max.poll.interval.ms 默认 300s，消费者被逐个踢出组。值班同学按直觉扩容 20 → 40 实例，数据库连接池被进一步打满，组状态在 STABLE 与 REBALANCING 之间反复横跳：每轮 Eager 重平衡全组撤销分区、吞吐归零，2 小时内消费延迟从 2 万条涨到 350 万条，有效吞吐不足正常时的 10%。止血动作按序执行：① 停止继续扩容；② max.poll.records 从 500 调到 50，把重处理挪出 poll 线程；③ 分配器换成 CooperativeStickyAssignor（Kafka 2.4+，只移动真正要换主的分区，其余消费者不停）；④ 配置 group.instance.id 静态成员，滚动重启不再触发重平衡。T+90min 组稳定，积压 4 小时内消化归零。

落地清单

  • 让队列/分区数是消费者数的整数倍，避免"能者过劳"
  • 扩缩容、发布前确认分配策略与重平衡协议（Kafka 优先 Cooperative）
  • 重处理逻辑移出 poll 线程，按业务耗时留足 max.poll.interval.ms
  • 跨城多活为 RocketMQ 配同机房分配并维护好机房命名规范
  • 监控消费延迟曲线：锯齿状上升 = 重平衡风暴的指纹
  • 不要部署多于队列数的消费者（纯空转，浪费资源）
  • 不要在延迟上涨时盲目加消费者——可能把故障扩成风暴
  • 不要在频繁滚动发布的组上沿用 Eager 重平衡且无静态成员
  • 不要在单次 poll 里同步做分钟级耗时操作
  • 不要同组混用不同分配策略，或在发布中途改 group.id

治理重平衡的心法只有一条：先让"变化"变少（静态成员、粘性分配），再让每次变化"动得少"（增量协议、一致性哈希），最后才轮到调超时参数兜底。

选型的终极标准不是"哪个策略更高级"，而是"变更频率 × 单次变更代价"哪个组合对你的业务最便宜：成员常年不动就用最简单的切段，天天扩缩容才值得上一致性哈希与增量协议。

Q&A

为什么同组内一个队列同一时刻只能被一个消费者消费？两个一起消费会怎样？
队列是顺序追加的日志，消费进度由一个 offset 标记。若同组两个消费者同时读同一队列，两者会各自推进自己的位点，要么互相覆盖 offset 导致位点混乱，要么对同一条消息各处理一次造成重复消费；如果业务依赖队列内顺序（如同一订单的状态流转），并发消费还会打乱处理顺序。所以"一队列单消费者"是消费正确性的底线约束，而不是性能优化的选择。需要更高并行度时，正确做法是增加队列数，而不是让多个消费者挤一个队列。
消费者数量超过队列数会发生什么？怎么提升并行度？
多出来的消费者分不到任何队列，处于完全空转状态——不拉消息、不产生吞吐，只是白白占着进程和连接。因为绑定的最小单元是队列，组内有效并行度的上限就是队列数。提升并行度有三条路：给 Topic 扩队列（注意 Kafka 分区只能增不能减，且会破坏按 key 的分区序）；提高单个消费者的消费线程数（RocketMQ 的 consumeThreadMin/Max）；或增大批量消费大小。扩队列前先确认瓶颈确实在消费侧而不是下游依赖。
一致性哈希为什么比取模稳定？为什么还要虚拟节点？
取模是 hash(key) % N，N 一变，几乎所有 key 的归属全变（约 (N-1)/N 的映射失效）；一致性哈希把消费者钉在 0~2³²-1 的哈希环上，队列顺时针找最近的消费者，增减成员只会让环上一小段弧的归属易主，迁移量约 1/N。但裸环有个隐患：消费者位置由哈希随机决定，若挤在环的一侧，某个消费者会管到远超平均的弧段，造成负载倾斜。虚拟节点让每个物理消费者在环上克隆多个分身（RocketMQ 默认 10 个，工程上常用 100~512 个）均匀散开，负载偏差收敛到 O(1/√T)；节点故障时其负载也能分摊到多个邻居而非压垮单个后继。
Kafka 为什么把分配策略写在客户端？同组成员策略不一致会不会乱套？
这是刻意的解耦设计：分配逻辑放服务端意味着每次换算法、修 bug 都要停机升级整个 Kafka 集群，一个业务的坏算法会拖垮共享集群；放客户端后，业务改几行代码重启自己的消费者即可生效，服务端只需维持稳定的 JoinGroup/SyncGroup 协议当"跑腿的"。至于不一致风险：分配表由组长统一计算并经由 Coordinator 分发，只要同组成员配置的 partition.assignment.strategy 不一致，组内就会出现按错误假设计算的分配，因此约定同组统一策略是使用前提，Kafka 也靠这个约定而非服务端强制来维持秩序。
Kafka 的 Consumer Leader 是怎么产生的？它挂了怎么办？
没有任何选举算法——第一个向 Coordinator 发出 JoinGroup 请求的消费者就被指定为组长，纯粹的先到先得。Coordinator 把全组成员的订阅信息和相关分区元数据发给组长，组长在本地用配置的分配策略算出整张分配表，再通过 SyncGroup 交回，Coordinator 把结果拆成每人一份下发。组长挂了不用抢救：Coordinator 感知成员变化后发起新一轮重平衡，在剩余成员里重新点一个组长，基于同样的输入重算一遍——因为分配计算是无状态的确定性函数，重算成本低到不值得为选举投入任何复杂度。
为什么 Controller 选举要用 ZooKeeper/Raft 这么重的机制，而 Consumer Leader 先到先得？
两者守护的资产价值完全不同。Controller 掌管全集群元数据（分区 Leader 归属、ISR、Topic 配置），这是有状态的、唯一的权威来源：一旦选错或脑裂，可能出现双写、数据丢失，所以必须靠 ZK 强一致性或 Raft 多数派来保证唯一与正确，且选举罕见、开销可以昂贵。Consumer Leader 只产出一次分配计算，输入（成员、订阅、分区列表）完全可复得，输出可确定性重算，错了重来即可，且每次重平衡都要选一次，必须廉价快速。严谨程度匹配资产价值，这正是同一框架内两种选举反差巨大的原因。
哪些操作会触发 Kafka 重平衡？如何把停顿降到最低？
四类事件：新消费者加入、消费者退出或崩溃（心跳超过 session.timeout.ms 未达，或两次 poll 间隔超过 max.poll.interval.ms 被踢）、订阅的 Topic 集合变化、Topic 分区数增加。降低停顿的手段按优先级：① 换 CooperativeStickyAssignor，从"全组撤销重来"变成"只移动需要换主的分区"，扰动从秒级降到毫秒级；② 配置 group.instance.id 静态成员，容器滚动重启在超时窗口内回来不触发重平衡；③ 调大 max.poll.interval.ms 并把重处理移出 poll 线程，避免被误踢；④ 优雅关闭（主动 LeaveGroup）代替进程硬杀，免去等待会话超时的十几秒空窗。
跨城双活部署，RocketMQ 和 Kafka 分别该怎么避免跨机房消费？
RocketMQ 用 AllocateMachineRoomNearby：实现 MachineRoomResolver 告诉框架队列属于哪个机房（解析 brokerName 前缀）、消费者在哪个机房（解析 clientID 前缀），策略先在同机房内配对（内部可包一个 Averagely），某机房消费者死光时再把队列兜底给其他机房，避免跨城专线 20~30ms 的往返延迟吃掉吞吐。Kafka 的思路类似但走机架感知：给消费者设置 client.rack，配合 follower fetching（KIP-392），让消费拉取优先命中同机架/同机房的副本，跨城场景下把拉取流量锁在本地机房。两者的共性是：分配算法必须感知物理拓扑，纯逻辑平均在跨城部署里是负优化。
