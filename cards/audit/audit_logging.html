U02 · 审计日志

Audit Logging — LLM 应用的全链路日志记录、存储与合规策略

一、LLM 审计日志概述

审计日志不是"多存一份数据以备万一"，而是把每一次 AI 决策变成半年后仍然举得出来的证据——记不全，事后就只能靠说。

为什么 LLM 应用需要审计日志

驱动因素说明典型场景
合规要求法规要求记录 AI 决策过程EU AI Act 高风险系统、中国生成式 AI 管理办法
安全调查追溯安全事件的输入/输出Prompt 注入攻击、数据泄露回溯
质量优化分析模型表现和用户行为幻觉检测、低质量回答分析
成本归因追踪 token 消耗和费用分配按团队/项目/用户分摊 API 费用
责任追溯AI 决策出错时定位责任自动审批出错、推荐结果投诉

LLM 日志 vs 传统应用日志

维度传统应用日志LLM 审计日志
内容体量结构化短消息大段非结构化文本（prompt/response）
确定性相同输入 → 相同输出相同 prompt → 不同回答（temperature > 0）
敏感性可能含 PII高概率含 PII + 业务敏感信息
关联性请求-响应对多轮对话链 + 工具调用链
存储成本KB 级每条KB~MB 级每条（含完整上下文）

LLM 审计日志的核心挑战：数据量大（每次请求含完整上下文）、敏感信息多（用户输入+模型输出）、关联复杂（多轮对话+工具链）。必须在"记全"和"保护隐私"之间找平衡。

全链路：从采集到查询

一条完整的审计管道要跨过四道关：在业务进程里采集、在管道里脱敏与打标、按温度分层存储、以及最容易被忽视的可查询。前三道做好但没有查询入口，等于把证据埋在了硬盘里。

① 采集（业务进程内，异步不阻塞） ┌──────────────────────────────────────────────┐ │ LLM 网关 / SDK 拦截器 │ │ · 请求前：记 model / params / session │ │ · 响应后：记 content / usage / latency │ └───────────────────┬──────────────────────────┘ │ 本地环形缓冲（丢弃优先于阻塞业务） ▼ ② 脱敏与打标（管道内完成，不落明文） ┌──────────────────────────────────────────────┐ │ PII 扫描 → 打 pii_types / risk_level │ │ 敏感字段就地 REDACT，原文只留 SHA-256 │ │ 补 integrity_hash + prev_hash（哈希链） │ └───────────────────┬──────────────────────────┘ │ Kafka（削峰，保证至少一次投递） ┌─────────────┼──────────────────┐ ▼ ▼ ▼ ③ hot 30 天 warm 1 年 cold 7 年 ClickHouse S3 Standard S3 Glacier 秒级检索 分钟级 小时级恢复 │ │ │ └─────────────┴──────────────────┘ ▼ ④ 查询入口（缺了这层，前面全白做） · 按 session_id 拉完整对话链 · 按 user_id 导出个人数据（响应 GDPR 请求） · 按 trace_id 关联工具调用链 · 校验哈希链，输出完整性报告
  • LLM 审计日志的驱动因素：合规（法规强制）、安全（事件追溯）、优化（质量分析）、成本（费用归因）
  • 与传统日志最大不同：内容非结构化、不确定性高、敏感信息密度大
  • 日志本身也是敏感数据——日志的访问控制和加密同样重要

二、结构化日志 Schema 设计

Schema 设计的本质是提前回答"半年后有人会拿什么条件来查这条日志"——查得到的字段才值得存，查不到的字段只是占空间。

核心日志 Schema — 六个顶层块

核心原则：顶层分块，每块对应一个明确的使用者。运维只读 metadata，财务只读 usage，合规只读 compliance——分块之后就能按块做字段级权限，避免"想查延迟却顺手看到了用户 prompt"。

顶层块关键字段谁在用它缺了会怎样
requestmodel、messages、parameters（temperature/max_tokens/top_p）安全调查、问题复现无法解释模型为何这样回答，参数不同结果就不同
responsecontent、finish_reason、model_version质量分析、责任追溯finish_reason=length 这类截断问题查不出来
usageprompt_tokens、completion_tokens、estimated_cost_usd成本归因、配额管理费用只能看到账单总额，无法分摊到团队
contextsession_id、conversation_id、turn_number、user_id、team_id对话链还原、多维聚合拿到孤立单轮记录，多轮上下文永远拼不回来
metadatalatency_ms、region、trace_id、span_id性能排查、跨服务追踪无法与网关/检索服务的链路对齐
compliancepii_detected、pii_types、content_filtered、risk_level合规审计、风险巡检只能事后全量重扫，成本高且漏检

骨架长这样，[REDACTED] 的位置说明脱敏是在写入时就已完成的，而不是查询时才做：

{"event_id":"uuid-v4", "timestamp":"2024-12-01T10:30:00.123Z",
 "event_type":"llm_completion",
 "request": {"model":"gpt-4-turbo", "parameters":{"temperature":0.7,"max_tokens":2048},
             "messages":[{"role":"system","content":"[REDACTED]"},
                         {"role":"user","content":"帮我分析这份财报..."}]},
 "response": {"content":"根据财报数据分析如下...","finish_reason":"stop",
              "model_version":"gpt-4-turbo-2024-04-09"},
 "usage":      {"total_tokens":2410, "estimated_cost_usd":0.0482},
 "context":    {"session_id":"sess_abc123","turn_number":3,"team_id":"team_engineering"},
 "metadata":   {"latency_ms":2340, "trace_id":"trace_def012"},
 "compliance": {"pii_detected":true,"pii_types":["person_name"],"risk_level":"medium"}}

注意 model_version 与 model 是两个字段：前者是厂商实际服务的快照版本（gpt-4-turbo-2024-04-09），后者只是别名。厂商静默切换快照时，只有前者能解释"同样的 prompt 为什么上周和这周表现不一样"。

事件类型枚举

事件类型描述关键字段

tool_callAgent 工具调用tool_name, arguments, result
retrievalRAG 检索操作query, documents, scores

  • Schema 设计的核心原则：结构化（便于查询）、可扩展（metadata 字段）、可关联（trace_id/session_id）
  • compliance 字段在写入时实时标注 PII 和风险等级，避免事后扫描
  • usage 字段是成本归因的基础——精确到每次请求的 token 和费用

三、Prompt/Response 全量记录

"全量记录"真正的难点不在存不下，而在于脱敏必须发生在落盘之前——明文一旦写进磁盘，就已经是一次数据事件了。

记录策略对比

策略记录内容存储开销合规性适用场景
全量记录完整 prompt + response高最强高风险/合规场景
摘要记录摘要 + token 计数 + 元数据中中等一般业务场景
采样记录按比例采样全量记录低有限低风险/大流量场景
条件记录触发条件时全量记录中低中等异常检测/风险监控

全量记录实现 — 写入管道的四个校验点

写入路径上有四件事必须按顺序做完，顺序错了就有明文落盘或哈希对不上的风险。

校验点为什么重要实现要点
先扫 PII，再构造记录脱敏必须在序列化之前，否则明文可能进入日志缓冲或异常堆栈扫描返回实体列表与位置，就地替换为 <PERSON> 之类占位符
原文只留哈希既要能证明"这就是当时的输入"，又不能长期持有明文脱敏前算 request_hash = sha256(原始请求)，与脱敏后正文一起存
哈希载荷排除易变字段latency、region 等运维字段可能被补写，纳入哈希会造成误报断链json.dumps(..., sort_keys=True) 只覆盖 event_id、timestamp、request_hash、response
写入失败不能吞掉静默丢日志是审计系统最致命的失效模式——出事时才发现没记本地降级落盘 + 丢弃计数上报监控，配"审计管道中断"告警
def log_completion(self, request, response, context):
    pii = self.pii.scan(request, response)          # ① 先扫
    rec = AuditRecord(
        event_id=uuid4().hex, timestamp=time.time(),
        request_hash=sha256(canonical(request)),    # ② 原文只留哈希
        request_body=self.pii.redact(request, pii.entities) if pii.has_pii else request,
        response_body=self.pii.redact(response, pii.entities) if pii.has_pii else response,
        usage=response.get("usage", {}), context=context)
    self.storage.write(rec)   # integrity_hash 在 __post_init__ 中按 ③ 的载荷算好
    return rec

Token 使用归因

Token 归因就是把每条日志的 usage 打散成带标签的时序指标，之后任意维度的费用都能靠聚合算出来，不必为每种报表单独写统计逻辑。关键是标签的基数要可控——按 team、application、model、environment 打标签没问题，但把原始 user_id 当标签会让时序库的序列数爆炸，所以存的是哈希后的用户标识，且只在需要个人级排查时才展开。

metrics.increment("token_usage", value=usage["total_tokens"], tags={
    "team": ctx["team_id"], "application": ctx["application"],
    "model": req["model"], "environment": ctx["environment"]})
cost_tracker.add(team=ctx["team_id"], cost_usd=usage["estimated_cost_usd"],
                 period=get_billing_period())
归因维度回答什么问题典型产出
team_id这个月各团队分别花了多少engineering 12.5M tokens / $250；marketing 45.2M / $67.80
model贵模型是否用在了不需要它的场景gpt-4-turbo 占费用 78% 但只占调用量 12%
application哪个业务是成本大头，值不值support 助手 8.1M tokens / $40.50
user_hash是否存在滥用或脚本刷量单用户日消耗超日均 3 倍触发告警
  • 高风险场景必须全量记录——合规要求能重现完整决策过程
  • 记录时实时脱敏——不能先存明文再脱敏，应在写入管道中完成
  • Token 归因是成本管理的基础——按团队/项目/模型多维度追踪费用

四、防篡改日志设计

防篡改的目标不是让人改不了日志，而是让任何改动都留下无法抹平的痕迹——能证明"没被改过"，日志才算证据。

防篡改技术方案

方案原理优点缺点
哈希链每条日志包含前一条的哈希值简单高效，篡改即断链单点写入瓶颈
Merkle Tree日志组织为 Merkle 树高效验证、支持批量实现复杂
WORM 存储Write Once Read Many硬件级防篡改成本高、不灵活
数字签名可信时间戳 + 签名法律效力强密钥管理复杂
区块链锚定哈希定期写入公链第三方可验证延迟高、费用

哈希链实现

哈希链的构造只有一句话：每条记录把上一条的哈希值当成自己的输入之一。于是改动第 500 条，第 501 条起的所有哈希都算不对——攻击者要么重算整条链（但链尾哈希已被外部锚定，重算无效），要么留下断链。

正常链条 ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ seq 498 │ │ seq 499 │ │ seq 500 │ │ prev=H497 ──┼──▶│ prev=H498 ──┼──▶│ prev=H499 │ │ data … │ │ data … │ │ data … │ │ hash=H498 │ │ hash=H499 │ │ hash=H500 │ └─────────────┘ └─────────────┘ └─────────────┘ H = sha256(seq ‖ timestamp ‖ data ‖ prev_hash) │ 每 N 条 / 每小时取链尾锚定 ▼ ┌────────────────────────────┐ │ 外部时间戳服务 / 公链 │ │ 攻击者无法回溯改写 │ └────────────────────────────┘ 被篡改后（把 seq 499 的 data 改掉） ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ seq 498 │ │ seq 499 ✎ │ │ seq 500 │ │ hash=H498 │ │ hash=H499' │ │ prev=H499 │ └─────────────┘ └──────┬──────┘ └──────┬──────┘ └── H499' ≠ H499 ─┘ ✗ 断链，verify 立即定位到 seq 499
def append(self, record):
    e = {"sequence": len(self.chain), "timestamp": time.time(),
         "data": record, "prev_hash": self.prev_hash}
    e["hash"] = sha256(json.dumps(e, sort_keys=True))   # sort_keys 保证可复算
    self.chain.append(e); self.prev_hash = e["hash"]
    return e
# 校验：逐条比对 chain[i]["prev_hash"] == chain[i-1]["hash"]，
#       并用同样载荷重算 hash，两项都过才算完整。

工程上有两个坑：一是 json.dumps 必须固定 sort_keys 和分隔符，否则同一条记录在不同语言/版本下序列化结果不同，校验会假失败；二是全链校验是 O(n)，亿级日志不可能每次全扫，实际做法是按天分段建链，只校验涉及的时间段，段与段之间用 Merkle Root 串起来。

合规存储策略

核心原则：按"被访问的概率"分层，而不是按"重要程度"分层。审计日志的访问分布极度倾斜——90% 以上的查询打在最近 7 天，但保留义务却按年算，硬把 7 年数据都放在可秒查的引擎里，成本会高一到两个数量级。

层级存储介质保留期访问延迟典型用途
hotElasticsearch / ClickHouse30 天秒级（< 1s）日常运维、实时监控、告警下钻
warmS3 Standard / Azure Blob1 年分钟级安全调查、合规审计取证
coldS3 Glacier / Azure Archive7 年（法定）小时级恢复长期归档、法律诉讼
生命周期动作触发时点处理要点
写入 hot日志产生时建全字段索引，供实时检索
降至 warm30 天后列式压缩 + 服务端加密，索引只留常用维度
降至 cold1 年后正文归档，元数据索引留在线——否则找不到该取回哪个归档包
依法删除7 年后加密粉碎（销毁密钥）并生成删除证书留档
  • 防篡改的关键：哈希链确保任意篡改都能被检测，WORM 存储从物理层面阻止修改
  • 分层存储平衡成本和访问速度：hot（实时查询）→ warm（调查审计）→ cold（合规归档）
  • 日志保留期限取决于法规要求——中国至少 6 个月，金融行业通常 7 年

五、日志级别与 LLM 应用实践

AUDIT 不是"比 INFO 更详细的一档"，而是一条独立通道：普通日志可以按级别关掉，审计事件不能——它的开关不在工程师手里。

LLM 应用日志级别定义

级别语义LLM 场景示例存储
CRITICAL系统不可用模型 API 全面不可达、审计管道中断立即告警 + 全量存储
ERROR请求失败模型返回错误、内容安全过滤拦截全量存储
WARNING异常但可恢复Token 超限截断、延迟异常、重试成功全量存储
INFO正常业务事件请求完成、会话创建/结束全量或采样
DEBUG调试详情完整 prompt、RAG 检索详情、chain 中间状态仅开发环境
AUDIT合规审计事件用户操作、权限变更、数据访问强制全量 + 防篡改

结构化日志实现

用 structlog 这类库的意义是把日志从"拼字符串"变成"传字段"——事件名固定，上下文以键值对附带，渲染成 JSON 后可以直接被 ClickHouse 或 ES 解析。核心配置只有三个 processor：时间戳、级别、JSON 渲染。

structlog.configure(processors=[
    structlog.processors.TimeStamper(fmt="iso"),
    structlog.processors.add_log_level,
    structlog.processors.JSONRenderer()])

logger.info("llm_completion", model=req["model"], latency_ms=ctx["latency_ms"],
            prompt_tokens=u["prompt_tokens"], completion_tokens=u["completion_tokens"],
            session_id=ctx["session_id"], trace_id=ctx["trace_id"])

真正需要设计的是"哪个事件走哪个级别、带哪些字段"。三类事件的差别不只在级别，还在于是否可采样、是否可关闭：

事件级别必带字段可否采样/关闭
llm_completionINFOmodel、token 数、latency_ms、session_id、trace_id低风险业务可按比例采样
content_filter_triggeredWARNING（拦截则 severity=high）filter_type、action、reason、session_id不可采样——这是安全信号，漏一条就是漏一次攻击
audit_eventAUDITuser_id、action、resource、ip_address、user_agent不可关闭，且需进防篡改链

示例场景：某企业内部知识助手把审计日志和应用日志混在同一条 stdout 管道里，靠日志级别过滤。一次促销活动带来 6 倍流量，日志采集 agent 的背压导致进程写日志阻塞，运维按应急预案把日志级别调到 ERROR 以上恢复了服务——代价是当天 9 小时的 AUDIT 事件全部丢失，恰好覆盖了后来被投诉的一次越权文档访问，无法举证。整改做了两件事：AUDIT 走独立的异步通道，本地环形缓冲 256MB，满了丢弃 INFO 但绝不丢 AUDIT；同时把"审计事件写入速率"做成独立监控指标，速率掉零直接触发 CRITICAL 告警。之后一次同等流量的活动中，INFO 采样率被自动降到 20%，AUDIT 事件零丢失。

  • AUDIT 级别是 LLM 应用特有的——独立于 DEBUG/INFO/ERROR 体系，强制全量记录+防篡改
  • 推荐使用 structlog 等结构化日志库——JSON 格式便于后续检索和分析
  • 日志级别决定存储策略：CRITICAL/ERROR/AUDIT 必须全量存储，DEBUG 仅限开发环境

六、用户操作追踪

用户操作日志要记的不是"他和模型聊了什么"，而是"他动了哪些开关、碰了哪些数据"——前者是内容，后者才是责任边界。

用户行为追踪维度

把事件按四类划分，每类的审计价值截然不同。configuration 类最容易被漏记，却往往是事故解释的关键——用户自己把 system prompt 改掉后模型输出变差，若没记这一步，排查会一路怀疑到模型上。

类别事件审计价值
sessionsession_start / session_end / session_timeout划定活动时间窗，异常时段登录的第一线索
interactionmessage_sent / message_edited / message_regenerated / feedback_given / response_copied重新生成与踩的密集出现是质量问题的早期信号；复制行为提示内容外流路径
configurationmodel_switched / system_prompt_changed / parameter_adjusted解释"同样的问题为什么这次答得不一样"，也是越权改配置的证据
data_accessdocument_uploaded / history_exported / data_deletion_requested数据进出边界的记录，泄露调查和 GDPR 响应都从这里查

记录本身要"记行为不记内容"：消息只存长度不存正文，IP 只存哈希，这样这份日志的敏感级别可以低于内容日志，从而放宽查询权限、让安全团队直接使用。

SIEM 集成

七、日志保留策略与合规

保留策略的难点不是"存多久"，而是删除权和保留义务同时压在同一条记录上时怎么办——答案通常是匿名化，把人删掉、把事留下。

各法规保留要求

法规/标准保留要求适用数据
中国《生成式 AI 管理办法》用户输入日志 ≥ 6 个月用户输入、生成结果

保留策略实现

核心原则：策略必须按数据类型分开配，而不是给整个日志库设一个统一保留期。审计事件要留 7 年，但完整 prompt 正文留 7 年既没必要也增加泄露面——把它们混在一起，结果一定是"按最长的存"，成本和风险双输。

数据类型最短保留降级路径删除方式
audit_events（权限变更、数据访问）7 年30 天 → warm，1 年 → cold加密粉碎 + 删除证书
llm_completions（prompt / response 正文）6 个月7 天 → warm，6 个月 → cold 或删除安全删除
user_sessions（会话与操作轨迹）90 天30 天 → warm常规删除

被遗忘权请求进来时，判断逻辑只有一个分叉：这条记录是否处于法务保全（legal hold）或法定保留期内。是则匿名化——把 user_id、IP、正文中的身份信息不可逆替换，事件骨架留下；否则安全删除。两条路都要产出删除证书，因为"已按策略处理"本身也需要举证。

def handle_deletion_request(self, user_id):
    for rec in self.find_user_data(user_id):
        if self.is_under_legal_hold(rec) or self.within_statutory_period(rec):
            self.anonymize(rec)      # 删人不删事：保留事件骨架，抹掉身份
        else:
            self.secure_delete(rec)
    return DeletionCertificate(user_id=user_id)   # 处理动作本身也要留证

匿名化有个容易踩的坑：如果只是把 user_id 替换成该 id 的哈希，那它仍然是可重新识别的——拿同一个用户 id 算一遍哈希就能重新定位到全部记录，这在监管口径下不算匿名化，只算假名化。真正的匿名化需要用一次性随机盐或直接替换为无关联的序号，并且丢弃映射表。

  • 脱敏在落盘前完成：PII 扫描放在序列化之前，原文只保留 SHA-256
  • AUDIT 事件走独立通道，与应用日志的级别开关和采样策略解耦
  • 把审计写入速率本身做成监控指标，速率掉零按 CRITICAL 告警
  • 降到 cold 时元数据索引留在线，否则知道要取证却不知道取回哪个包
  • 哈希链按天分段 + Merkle Root 串联，让校验成本与数据总量脱钩
  • 删除与匿名化都产出证书，把"已合规处理"变成可举证的事实
  • 别先存明文再批量脱敏——明文落盘的那一刻风险已经发生，事后清理无法回溯
  • 别让审计写入阻塞业务线程：背压时该丢 INFO，绝不能靠关掉审计来救服务
  • 别把原始 user_id 当时序标签，序列基数爆炸会把指标系统压垮
  • 别给整个日志库设统一保留期，正文和审计事件的义务与风险完全不同
  • 别用确定性哈希冒充匿名化，它可被重新识别，监管不认
  • 别把日志的访问权限等同于业务权限：业务管理员能改审计日志，等于没有审计
  • 日志保留期限由最严格的适用法规决定——多法规交叉时取最长保留期

Q&A

LLM 审计日志与传统应用日志有什么本质区别？

五个核心区别：①体量——传统日志每条 KB 级，LLM 日志每条 KB~MB 级（包含完整 prompt 和 response）；②确定性——传统应用相同输入产生相同输出，LLM 由于 temperature 等参数相同 prompt 可产生不同回答，必须记录每次实际输出；③敏感性——LLM 日志高概率包含用户发送的 PII 和业务敏感信息，日志本身就是需要保护的数据；④关联性——传统日志是独立的请求-响应对，LLM 日志需要关联多轮对话链和工具调用链，一个会话可能涉及数十条关联记录；⑤不可预测性——LLM 可能产生幻觉或有害内容，日志需要记录内容安全检测结果用于事后审计。

如何设计防篡改的审计日志系统？

多层防篡改方案：①写入层——使用 WORM（Write Once Read Many）存储，从物理层面阻止修改和删除；②数据层——哈希链技术，每条日志包含前一条的 SHA-256 哈希，形成不可篡改的链式结构，任何修改都会导致后续所有哈希失效；③验证层——定期执行完整性验证，遍历哈希链检查一致性，发现断链立即告警；④外部锚定——定期将 Merkle Root 写入外部系统（如公共区块链或第三方时间戳服务），提供独立的第三方验证能力；⑤访问控制——日志系统与业务系统权限隔离，即使业务管理员也无法修改审计日志。在实践中，通常组合使用"哈希链 + WORM 存储 + 独立验证"三重保护。

如何实现 LLM 应用的 Token 使用量归因和成本分摊？

Token 归因需要在日志中记录多维度上下文：①每次 API 请求记录 prompt_tokens、completion_tokens、total_tokens 和 estimated_cost；②关联上下文信息包括 user_id（用户维度）、team_id（团队维度）、application（应用维度）、model（模型维度）、environment（环境维度）；③聚合计算按日/周/月汇总各维度的 token 消耗和费用；④成本分摊模型可选直接归因（按实际使用量）、共享分摊（公共模型按比例）、预算制（按团队配额）。实现关键点：使用时序数据库（如 ClickHouse、InfluxDB）存储 token 指标，用 Grafana 构建可视化仪表盘，设置 per-team 和 per-user 的阈值告警防止滥用。

LLM 审计日志如何与企业 SIEM 系统集成？

集成方案包括：①事件映射——将 LLM 特有事件（content_filter_triggered、abnormal_token_usage、pii_detected）映射为 SIEM 可识别的安全事件格式（如 CEF/LEEF）；②转发通道——使用 Syslog/Kafka/Webhook 将安全相关事件实时转发到 SIEM（Splunk/Sentinel/QRadar）；③告警规则——在 SIEM 中配置 LLM 特有的告警规则，如"单用户 1 小时内触发内容过滤 > 10 次"、"Token 消耗超过日均 3 倍"、"频繁数据导出"；④关联分析——将 LLM 事件与其他安全数据源（网络、终端、身份）关联，发现更复杂的攻击模式（如先窃取凭据再利用 LLM 提取数据）；⑤不是所有日志都转发到 SIEM——只转发安全相关事件，避免 SIEM 被海量 INFO 日志淹没。

日志保留策略如何应对多法规冲突（如 GDPR 删除权 vs 合规保留要求）？

这是审计日志设计中的经典冲突——GDPR 要求尊重用户删除请求，但合规法规（如 SOX 7 年保留）要求保存记录。解决方案：①匿名化而非删除——对处于合规保留期内的日志，将用户身份信息不可逆匿名化（如替换为 hash），保留事件内容但无法关联到具体用户，既满足"被遗忘"又满足"保留"；②分类处理——将日志数据分为"必须保留"（法定审计事件）和"可删除"（非法定要求的详细日志），删除请求只影响可删除部分；③Legal Hold 机制——正在调查或诉讼中的记录暂不处理删除请求，直到 hold 解除；④删除证书——对确实执行删除的数据生成带时间戳的删除证书，证明合规执行了删除操作。核心原则：在所有适用法规中取最严格的要求，当要求冲突时优先满足强制性保留，用匿名化调和隐私删除需求。

审计日志的采集为什么不能阻塞业务线程，工程上怎么保证既不丢又不拖慢？

因为一旦同步写入，日志后端的任何抖动都会直接变成业务接口的延迟甚至超时——审计系统本应降低风险，结果成了新的单点故障。标准做法是三级缓冲：业务线程只把记录放进进程内的有界队列（环形缓冲），由独立的 flush 线程批量投递到 Kafka，再由消费者写入存储。有界队列意味着必须预先决定"满了怎么办"，这里要按事件类别分流：INFO 级的完成记录可以按比例丢弃或降采样，AUDIT 级事件不允许丢，队列压力大时应降级到本地磁盘暂存，等后端恢复后补投。要让这套机制真的有效，还需要两个可观测指标：审计事件的写入速率（掉零说明管道断了，此时所有基于日志的告警都已失效，必须单独报 CRITICAL）和丢弃计数（非零就说明容量规划不足）。最后是投递语义的选择：审计场景应该选至少一次而非最多一次，重复投递可以靠 event_id 在写入端幂等去重，但丢失是不可恢复的。

Prompt 里的敏感信息应该脱敏、加密还是原样保留？如何决定？

三种处理不是互斥选项，而是按字段分别决定的。判断依据是"事后需要用它做什么"：如果只需要证明输入没被改过，那么保留原文的 SHA-256 就够了，正文本身可以脱敏，这是最省心也最安全的一档；如果需要重放请求验证模型行为，就必须保留可还原的内容，此时用字段级加密（信封加密，数据密钥由 KMS 托管），把访问控制转化为密钥授权，谁解密都留痕；只有当法规明确要求留存用户原始输入（例如生成式 AI 管理办法对用户输入日志的要求）时才考虑原样保留，且必须配套加密存储和最小化访问。实践中的组合是：正文默认脱敏，识别出的 PII 实体类型和位置作为元数据单独存（便于统计和巡检但不含具体值），完整原文加密后存一份短保留期的副本（例如 30 天），供近期的安全调查和问题复现使用，过期即销毁。这样长期归档里没有明文，而短期排查能力不受影响。
