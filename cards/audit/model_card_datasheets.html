U06 · Model Card 与数据文档

Model Cards & Datasheets — 模型透明度文档、数据集文档与社区标准

一、Model Card 概述

Model Card 真正的作用是划边界：写清楚"这个模型不该用来做什么"，出事时才能分清是模型缺陷还是使用者越界。

什么是 Model Card

Model Card 是 Google 于 2019 年提出的模型文档标准（Mitchell et al.），旨在为 AI 模型提供标准化的"说明书"，涵盖模型的用途、性能、局限性和伦理考量。

目标受众关注内容Model Card 的价值
模型开发者技术细节、复现记录设计决策和训练配置
模型使用者适用场景、限制判断模型是否适合自己的用例
监管/审计合规、公平性提供合规审计所需的透明度证据
终端用户可信度、风险理解 AI 系统的能力边界
社区/研究方法论、可复现促进开放科学和协作

Model Card 不是可选文档，而是 AI 治理的基础设施。EU AI Act 对高风险 AI 系统要求提供详细技术文档，Model Card 是满足这一要求的标准方式。

文档链：从数据集到部署

单份 Model Card 是孤岛，有价值的是把它接进一条文档链：数据集有 Datasheet、模型有 Model Card、部署有风险声明，三者靠版本号交叉引用。这条链的用途在被追问时才显现——它能把"某批数据有问题"直接映射到"哪些模型版本、哪些线上服务受影响"。

┌─────────────────────────────────────────────────────────┐ │ Datasheet · FinSentiment-CN v1.3.0 │ │ · Motivation / Composition / Collection Process │ │ · 150K 条，标注一致性 Fleiss κ=0.82 │ │ · 许可证、知情同意、伦理审查记录 │ └──────────────────────────┬──────────────────────────────┘ │ 被引用（记录数据集版本号） ▼ ┌─────────────────────────────────────────────────────────┐ │ Model Card · FinBERT-Sentiment v2.0.0 │ │ · Intended Use ←── 决定下游能不能这么用 │ │ · Out of Scope ←── 划责任边界 │ │ · Quantitative Analysis：整体 + 分行业切片 │ │ · Limitations / Ethical Considerations │ └──────────────────────────┬──────────────────────────────┘ │ 被引用（记录模型版本号） ▼ ┌─────────────────────────────────────────────────────────┐ │ 部署风险声明 · 研报舆情服务 v5.2 │ │ · 面向终端用户的能力边界与免责声明 │ │ · 人工复核触发条件、问题上报渠道 │ └─────────────────────────────────────────────────────────┘ 这条链的价值在被追问时才显现： · 数据集某批标注被发现有问题 → 沿引用关系反查：哪些模型版本用了 v1.3.0？ → 再往下：哪些线上服务在跑这些版本？ · 断链的后果：只能全量排查，或者干脆答不出来
  • Model Card 由 Google 2019 年提出——已成为行业事实标准
  • 服务多个受众：开发者（复现）、使用者（适用性）、监管者（合规）
  • EU AI Act 和 ISO 42001 都要求类似的模型文档——Model Card 是最佳实践

二、Google Model Card 标准格式

整体准确率 91% 这个数字几乎没有信息量——真正有用的是按行业、按来源拆开之后最差的那一档是多少。

核心章节结构

Mitchell 等（2019）定义了九个章节。下面用一个金融情感分析模型（FinBERT-Sentiment v2.0.0）作为贯穿示例，说明每节该写什么、以及不写会漏掉什么。

章节示例内容省掉它会怎样
Model Details名称、版本 2.0.0、基础模型 bert-base-chinese、开发团队、发布日期、Apache 2.0 许可、论文链接、联系人无法定位责任方，许可证不清导致下游合规风险
Intended Use主用途：研报/新闻/公告的情感分析；主用户：分析师与量化团队用户凭想象使用，超出设计场景后责任归属不清
Out of Scope非金融文本、实时交易决策（延迟不达标）、法律与合规判断最关键的一节——没有它，任何误用都会被归为模型缺陷
Factors相关因素：文本长度、金融术语密度、语言；评估因素：行业、来源、时间段用户无法判断自己的数据是否落在模型擅长的区间
MetricsAccuracy / F1 / AUC；决策阈值 positive 0.6、negative 0.4；按行业与来源分组评估阈值不公开，下游自行取 0.5 会得到与官方指标不一致的表现
Training DataFinSentiment-CN 自建，150K 条；去重 + PII 脱敏；3 位领域专家独立标注，Fleiss κ=0.82无法评估数据质量与合规性，也无法复现
Evaluation DataFinSentiment-CN-Test + 公开基准，20K 条，含 2024 年数据以测时效性分不清高分是真能力还是测试集与训练集同源
Ethical Considerations风险：训练数据偏向大盘股，小市值公司判断偏弱；不可作为多空决策唯一依据。缓解：标注置信度、附投资风险提示已知风险未披露，等于把风险转移给了不知情的用户
Limitations最大 512 tokens 需截断；讽刺与反语识别弱；知识止于 2024 年前用户对失败模式毫无预期，把偶发错误当系统故障上报

为什么必须报告切片指标

Quantitative Analysis 一节的核心要求是分群体报告。同一个模型，整体看是 0.91，拆开看最差的一档是 0.87：

"Quantitative Analysis": {
  "overall":     {"accuracy": 0.91, "f1": 0.89, "auc": 0.95},
  "by_industry": {"银行": {"accuracy": 0.93, "f1": 0.91},   # 训练样本最多
                  "科技": {"accuracy": 0.90, "f1": 0.88},
                  "能源": {"accuracy": 0.87, "f1": 0.84}}}  # 最弱的一档

差距本身不算大，但对一个只做能源行业研报的用户来说，他实际能拿到的是 0.87 和 F1 0.84，而不是宣传页上的 0.91。只报整体值不算撒谎，但确实让一部分用户形成了错误预期——这就是切片报告要解决的问题。

  • Model Card 的核心是"Intended Use"和"Limitations"——明确能做什么和不能做什么
  • 性能指标必须分群体报告——整体 91% 准确率可能掩盖某些子群体的低性能
  • Ethical Considerations 不是走形式——需要真诚地讨论已知风险和缓解措施

三、Datasheets for Datasets

Datasheet 是用一串问题逼作者把默认知识写出来——数据怎么来的、谁同意过、哪些用途不该碰，这些事只有创建者知道，一旦人走了就永远失传。

数据集文档标准

Datasheets for Datasets（Gebru et al., 2021）为数据集提供类似"产品说明书"的标准化文档，七个模块覆盖从创建动机到长期维护的全过程。它的形式是一组必答问题，而不是自由撰写的介绍——这个设计是有意的，因为自由撰写时作者总会跳过自己觉得"显而易见"的部分。

模块必答问题审计关注点
Motivation为什么创建？谁创建的、是否存在利益冲突？谁资助的？资助方与结论方向是否存在关联
Composition数据是什么形态、多少条、是否为更大总体的抽样及抽样方法、标签如何生成、是否有缺失、是否含机密或冒犯性内容抽样方法直接决定了代表性偏差的大小
Collection Process怎么收集的（爬虫/API/人工/传感器）、数据主体是谁、是否知情同意、时间范围、是否过伦理审查合规审计的重点——来源合法性与同意链条
Preprocessing做了哪些清洗与转换、原始数据是否保留、用了什么工具保留原始数据是复现与纠错的前提
Uses推荐场景、不推荐场景、误用可能造成什么影响与 Model Card 的 Out of Scope 相呼应
Distribution如何获取、许可证、版权归属、是否有出口管制许可证不兼容会让下游模型整体无法商用
Maintenance谁维护、是否更新及频率、如何报告错误、保留多久无人维护的数据集会静默腐坏而使用者不知情

七个模块里最容易敷衍的是 Maintenance。它看起来只是行政信息，实际决定了数据集能不能被长期信任：没有勘误渠道，发现的标注错误就永远留在数据里；没有维护责任人，几年后没人说得清某个字段的含义。

  • Datasheets for Datasets 回答"数据从哪来、怎么处理、该怎么用"三个核心问题
  • Collection Process 是合规审计的重点——知情同意、伦理审查、数据来源合法性
  • "Not Intended Uses"与 Model Card 的"Out of Scope"对应——明确不该怎么用

四、能力边界与风险声明

风险披露的完整形态是四段式，最后一段"残余风险"最不好写也最重要——它承认缓解措施不彻底，才是诚实的文档。

能力边界声明框架

维度需要声明的内容示例
输入限制支持的输入格式、长度、语言最大 128K tokens，仅支持中英文
输出限制输出质量的已知局限长文本可能出现重复，数学推理能力有限
知识边界训练数据的时间截止点知识截止到 2024 年 4 月
场景边界适用和不适用的使用场景适用于问答，不适用于法律建议
性能边界不同条件下的性能变化专业领域准确率显著低于通用场景
安全边界已知的安全风险可能被 prompt 注入攻击绕过安全过滤

六个维度合起来构成一张"可用区域图"，超出任一维度就进入未验证地带：

┌── 知识边界：训练数据止于 2024-04 │ （之后的术语、事件一概不知） │ 输入边界 │ 输出边界 ≤ 128K tokens ─────┼───────── 长文本可能重复 仅中英文 │ 数学推理能力有限 │ │ │ └─────────────┼─────────────────┘ ▼ ┌───────────────────────────────┐ │ 已验证可用区域 │ │ 通用问答 · 文本分类 │ │ 摘要 · 信息抽取 │ │ │ │ 分切片指标已披露： │ │ 银行 0.93 / 科技 0.90 │ │ 能源 0.87 ← 最弱档 │ └───────────────────────────────┘ ▲ ┌─────────────┼─────────────────┐ │ │ │ 场景边界 │ 安全边界 不用于法律建议 ────┼───────── 可能被 prompt 注入 不用于医疗诊断 │ 绕过内容过滤 │ └── 性能边界：专业领域准确率 显著低于通用场景 越界不等于必然出错，而是"我们没测过、不承诺"—— 这个区分是能力边界声明的全部意义。

风险披露文档

核心原则：每条风险写四要素——描述、严重度、缓解措施、残余风险，缺一不可。只写前三项会给人"已经解决"的错觉；写上第四项才把真实状况交代清楚，也才符合监管对"如实披露"的要求。

风险描述严重度缓解措施残余风险
幻觉生成看似合理但事实错误的内容高关键信息强制人工验证；输出附来源引用无法完全消除，使用者需保持批判性判断
偏差对特定群体产生不公平的输出高定期偏差审计；RLHF 对齐训练语料中的社会偏见无法根除
隐私泄露输出中可能复现训练数据里的个人信息中训练数据脱敏；输出侧 PII 过滤记忆化提取攻击仍可能取出部分内容

文档末尾还有两项常被漏掉但都很关键：免责声明（本模型不应作为专业决策的唯一依据）明确了责任边界；报告渠道（如 safety@example.com）给外部研究者和用户一条反馈通路——没有这条通路，问题往往会先出现在社交媒体上，而不是你的工单系统里。

  • 能力边界声明是"设定正确预期"的关键——告诉用户模型能做什么、不能做什么
  • 风险披露应包含：风险描述、严重度评估、缓解措施、残余风险——四要素缺一不可
  • 免责声明不只是法律保护——也是引导用户正确使用 AI 的手段

五、版本跟踪与变更管理

历史版本的 Model Card 一个字都不能改——审计问的不是"现在文档怎么写"，而是"当时你告诉用户的是什么"。

模型版本管理

版本号沿用 semver，但语义要重新定义：模型的"破坏性变更"不只是 API 变了，训练数据大幅变动同样会让下游的评估结论失效。

版本位触发条件下游影响
major（v1 → v2）架构变更或训练数据大幅变动下游必须重新评估，此前的基准结论全部作废
minor（v1.0 → v1.1）微调、超参调整、新增能力行为可能变化，建议回归测试
patch（v1.0.0 → v1.0.1）Bug 修复、安全补丁可直接升级

每次发布必须记录五件事，其中最后一项定义了破坏性变更的处理方式：变更摘要（改了什么）、动机（为什么改）、影响评估（对已有用户和功能的影响）、评估结果（新版指标）、回滚计划（出问题怎么退回）。最后一项在文档评审时最常被跳过，却是唯一在事故当下真正被用到的。

[{"version": "2.0.0", "date": "2024-06-15",
  "changes": ["基础模型 BERT-base → BERT-large",
              "训练数据 100K → 150K", "F1 0.86 → 0.89 (+3.2%)"],
  "breaking": "API 输出格式变更，需同步更新客户端"},   # ← 必须显式标注
 {"version": "1.2.0", "date": "2024-03-01",
  "changes": ["新增能源行业数据", "修复讽刺语句误分类"], "breaking": None}]

数据集版本管理

数据集和模型必须联动追踪——数据变了模型行为就变了，只给模型打版本号会导致"同一个模型版本在不同时间训出来不一样"。

工具适用特点
DVC文件型数据集与 Git 工作流贴合，元数据入库、大文件走外部存储
Delta Lake大规模结构化数据支持时间旅行，可直接查询"某个日期时的表状态"
Hugging Face DatasetsNLP 数据集社区标准，与 Hub 的加载与分享生态打通

版本元数据里除了常规的版本号、创建时间、记录数、内容哈希和变更说明，关键是质量指标要随版本一起冻结——标注一致性 0.85、重复率 0.002、PII 清洁标记，这些数字让版本之间可比。缺了它们，"新版数据更好"就只是一句主张。

{"version": "1.3.0", "created": "2024-05-01", "record_count": 150000,
 "hash": "sha256:abc123...", "changes": "新增 Q1 2024 金融新闻 12K 条",
 "quality_metrics": {"label_agreement": 0.85,     # 随版本冻结，供跨版本对比
                     "duplicate_rate": 0.002, "pii_clean": True}}

示例场景：某团队的推荐模型上线一年后收到监管问询，要求说明去年 3 月某次争议推荐所依据的模型能力边界。团队的 Model Card 存在 Hub 仓库的 README.md 里，一直原地覆盖更新——最新版本写的是"已加入敏感类目过滤"，而争议发生时这项还不存在，历史文档无从查证。更麻烦的是训练数据只有一个 latest 目录，无法确认当时用的是哪一批数据。整改建立了三条规则：Model Card 随每次发布打 tag 归档，历史版本只读；训练数据接入 DVC，模型元数据里必须写清数据集版本号与内容哈希；上线记录中固化"模型版本 + 数据版本 + Model Card 版本"三元组。改造用了约三周，此后同类问询可在半小时内导出当时的完整文档快照。

  • 模型和数据集的版本管理同样重要——数据变了模型就变了，必须联动追踪
  • 每个版本的 Model Card 应独立存储——支持审计追溯"当时的文档是什么"
  • Breaking change 必须明确标注——避免下游用户在不知情的情况下受到影响

六、Hugging Face 社区标准

Hugging Face 把 Model Card 做成了机器可读的：YAML 头让平台能索引、能排行、能门控，Markdown 正文才是给人看的部分。

Hugging Face Model Card 格式

约定很简单——模型仓库的 README.md 就是 Model Card，结构为 YAML 元数据头 + Markdown 正文。YAML 头里的字段不是装饰，每一个都对应平台的一项能力。

language: [zh, en]
license: apache-2.0                 # 缺失则下游无法判断能否商用
tags: [text-classification, sentiment-analysis, finance]
datasets: [finsentiment-cn]         # 建立到 Datasheet 的引用
pipeline_tag: text-classification   # 决定能否直接 pipeline() 调用
model-index:                        # 结构化评估结果 → 自动排行榜
  - name: FinBERT-Sentiment-v2
    results:
      - task:    {type: text-classification}
        dataset: {name: FinSentiment-CN-Test, type: finsentiment-cn}
        metrics: [{type: accuracy, value: 0.91}, {type: f1, value: 0.89}]

正文部分沿用标准章节：Model Description、Intended Uses & Limitations（推荐用于研报情感分析与舆情监控；限制为最大 512 tokens、讽刺识别弱）、Training Data、Evaluation Results（用 Markdown 表格给出分行业指标）、Ethical Considerations。和 Google 版的对应关系是一一对齐的，只是表达形式从字典换成了 Markdown。

pipeline_tag 这个字段容易被当成分类标签随手填，其实它决定了用户能否用一行 pipeline() 直接跑起来。填错或不填，模型的实际使用门槛会明显提高，而这一点在下载量上会直接体现。

社区最佳实践

实践说明好处
YAML 元数据结构化元信息，支持 Hub 搜索/过滤可被自动索引和发现
model-index标准化评估结果格式支持自动排行榜（Leaderboard）
Spaces Demo在 Model Card 中嵌入交互 Demo用户可直接试用
Carbon Footprint记录训练的碳排放环境可持续性透明度

  • Hugging Face 的 Model Card 已成为开源社区事实标准——YAML 头 + Markdown 正文
  • model-index 字段是标准化评估结果的关键——支持自动排行榜对比
  • Gated Access 是管控高风险模型的有效手段——下载前需同意使用条款

七、自动化文档生成

能自动生成的部分必须自动生成，因为手写的指标一定会过时；但不能自动生成的部分绝不要伪装成自动的——Intended Use 需要人来判断。

Model Card 自动生成工具

Google 开源的 model-card-toolkit 提供脚手架 + 结构化对象 + 导出，把"填文档"变成"填对象字段"。它的价值在于结构固定：字段缺失可以被程序检出，而 Markdown 里少写一节没人会发现。

mc = mct.scaffold_assets()
mc.model_details.name, mc.model_details.version.name = "FinBERT-Sentiment-v2", "2.0.0"
mc.quantitative_analysis.performance_metrics = [        # 直接来自评估脚本输出
    mctlib.PerformanceMetric(type="accuracy", value="0.91", slice="overall"),
    mctlib.PerformanceMetric(type="f1",       value="0.89", slice="overall")]
mc.quantitative_analysis.graphics.collection = [        # 公平性图表来自 Fairlearn
    mctlib.Graphic(name="Fairness Metrics by Gender", image=fairness_plot_base64)]
mct.export_format = mctlib.ExportFormat.HTML
mct.export(mc, output_dir="./model_card/")

三档自动化：哪些能自动，哪些不能

核心原则：按"是否需要人的判断"分档。把需要判断的内容自动化，产出的是形式合规但内容空洞的文档，反而增加风险——因为它看起来已经审查过了。

CI/CD 集成

把生成挂到 models/** 与 data/** 的变更上，流水线依次跑评估、公平性审计、渲染模板、校验完整性、提交。校验这一步不能省——它是防止"自动化把文档写空"的唯一闸门。

  • Out of Scope 写具体：列出真实会被误用的场景，而不是"请合理使用"
  • 性能指标必须分切片报告，并显式给出最弱的那一档
  • 历史版本只读归档：按发布 tag 保存快照，永不原地覆盖
  • Model Card 引用数据集版本号与哈希，把文档链接起来
  • 风险披露写全四要素，尤其是残余风险
  • 在 CI 里加完整性校验，必填项缺失即让流水线失败
  • 公开决策阈值，否则下游取默认值会得到与官方指标不符的表现
  • 别只报整体指标——0.91 的均值可能掩盖某个切片的 0.87 甚至更低
  • 别把 Model Card 原地覆盖更新，那等于销毁了历史证据
  • 别自动生成 Intended Use 或伦理章节，形式合规而内容空洞比没有更危险
  • 别把 Ethical Considerations 写成免责套话，审计要看的是具体已知风险
  • 别省略许可证与版权信息，下游整条模型链都会因此无法商用
  • 别让数据集停在 latest 目录——没有版本号，模型就无法复现
  • 别在破坏性变更时只升 minor 版本号，下游会毫无防备地被打断
  • Model Card 应自动化生成——手动维护容易过时，自动化确保文档与模型同步
  • CI/CD 集成：模型或数据变更时自动重新评估并更新 Model Card
  • model-card-toolkit 是 Google 开源的标准工具——支持 HTML/Markdown 导出

Q&A

Model Card 应该包含哪些核心内容？为什么每一部分都重要？

Model Card 的核心内容包括七部分：①Model Details（模型详情）——名称、版本、架构、开发团队、许可证，支持模型识别和归属追溯；②Intended Use（预期用途）——推荐使用场景和明确禁止的场景，设定正确预期，避免误用；③Factors（因素）——影响模型性能的关键维度（如语言、领域、文本长度），帮助用户判断是否适用；④Metrics（指标）——选择的评估指标和原因，不同群体/切片的性能，提供可量化的性能证据；⑤Training/Evaluation Data——数据来源、规模、处理方式，支持可复现和数据合规审计；⑥Ethical Considerations——已知的偏差、风险和缓解措施，体现负责任 AI 实践；⑦Limitations——模型的已知局限性，避免用户过度信任。每部分服务不同受众：开发者关注 ①③⑤，使用者关注 ②④⑦，审计者关注 ⑤⑥。

Datasheets for Datasets 和 Model Card 有什么区别和联系？

区别：Model Card 文档化的是"模型"——记录模型的用途、性能、局限性和伦理考量；Datasheets for Datasets 文档化的是"数据集"——记录数据的创建动机、组成、收集过程、处理方式和使用建议。联系：①互补关系——Model Card 的 Training Data 部分应引用对应数据集的 Datasheet；②共同目标——都是为了提高 AI 系统的透明度和可追溯性；③格式类似——都采用结构化的问答/分节格式；④合规需求——EU AI Act 要求同时提供模型和数据的文档。实践建议：每个模型有一份 Model Card，每个数据集有一份 Datasheet，通过交叉引用建立完整的文档链。当数据集版本更新时，依赖该数据集的所有 Model Card 也应更新。

如何实现 Model Card 的版本管理？

Model Card 版本管理的关键实践：①与模型版本绑定——每个模型版本对应一份 Model Card 快照，使用相同的 semver 版本号（major.minor.patch）；②存储在版本控制系统中——Model Card 作为 README.md 或独立文件存储在 Git 仓库中，每次模型发布时 tag 对应版本；③变更日志——每个版本包含 changelog 记录变更内容、动机和影响评估；④Breaking Change 标注——架构变更、API 格式变更等破坏性变更必须在 major 版本号和 changelog 中明确标注；⑤自动化更新——通过 CI/CD 在模型评估后自动更新性能指标、公平性指标等可自动化的部分，人工审查 Intended Use、Ethical Considerations 等需要判断的部分。注意：历史版本的 Model Card 必须保留不修改——支持审计追溯"当时的文档说了什么"。

Hugging Face 的 Model Card 标准有什么特点？

Hugging Face Model Card 的特点：①YAML 元数据头——结构化的元信息（语言、许可证、标签、数据集、指标），支持 Hub 的搜索、过滤和自动索引；②model-index 标准——统一的评估结果格式，支持自动排行榜（Leaderboard）对比不同模型；③与生态深度集成——pipeline_tag 字段使模型可直接通过 pipeline() 调用，无需手动配置；④社区互动——支持 Discussion、Community 标注、下载统计等社区功能；⑤Gated Access——高风险模型可设置使用条款门控，下载前需同意条款；⑥碳足迹记录——鼓励记录训练的算力消耗和碳排放；⑦Spaces Demo 嵌入——可在 Model Card 中嵌入交互式 Demo。最佳实践：遵循 HF 的格式可以获得最大的社区可见性和工具兼容性。

如何自动化生成和维护 Model Card？

自动化策略分三个层次：①可完全自动化的部分——性能指标（从评估脚本输出）、公平性指标（从 Fairlearn/Aequitas 输出）、训练配置（从训练脚本/config 文件提取）、版本号和时间戳、数据集统计信息；②半自动化的部分——变更日志（从 git commit 生成草稿，人工审核修改）、限制说明（基于评估结果自动标注性能薄弱区域，人工补充原因）；③必须人工撰写的部分——Intended Use 和 Out of Scope（需要业务判断）、Ethical Considerations（需要伦理评估）、风险披露（需要安全评估）。工具链：使用 model-card-toolkit（Google 开源）或自定义模板引擎，集成到 CI/CD 流水线（模型或数据变更触发自动更新），用 lint 工具验证 Model Card 的完整性（检查是否缺少必填字段）。

Out of Scope 这一节应该怎么写才有实际作用？

判断标准是：写下来的每一条都应该对应一个真实可能发生的误用，而不是穷举所有模型做不了的事。"不能用于烹饪指导"这种条目毫无价值，因为没人会那样用；而"不适用于实时交易决策，因为 P99 延迟为 340ms 超出撮合窗口"就是有效的，它阻止了一个看起来很自然的用法。写作上有三个要点。第一是给理由而不只是给禁令：说明是延迟不达标、是训练分布不覆盖、还是错误后果不可承受，使用者才能判断自己的场景是否真的落在禁区内。第二是覆盖"相邻场景"——最容易出问题的不是明显无关的用途，而是看起来只差一点的场景，比如模型用中文金融研报训练，用户拿去分析港股英文公告，形式上都是金融文本情感分析，实际分布差很远。第三是随反馈迭代：每次用户误用事件发生后，都应该回头往这一节加一条，让文档反映真实的踩坑历史而非发布时的想象。最后要清楚它的作用范围：Out of Scope 划分的是责任边界，不是技术拦截，真正要阻止误用还需要在接口层做限制，例如输入长度校验、领域判别器、或者门控访问。

模型发布后 Model Card 里的哪些内容需要定期复审？多久一次？

Model Card 里的内容并非同等稳定，复审节奏应按变化速度分开安排。变化最快的是性能与公平性指标，它们会随线上数据分布漂移而失真——即使模型权重一个字节都没动，三个月前测出的 0.91 也可能已经不成立，因此这部分应该跟着定期评估流水线走，通常是月度或季度重跑并更新。其次是限制说明与已知风险，它们的更新触发点是事件而非时间：每次出现新的失败模式、被红队发现新的绕过手法、或者用户反馈了未预料的错误类型,都应当追加一条，同时把对应的缓解措施和残余风险补齐。第三类是外部依赖信息，包括基础模型的版本、上游数据集的许可证与版本、以及依赖库的安全公告——这些由别人决定的东西会静默变化，建议每季度核对一次，尤其是许可证，上游改成更严格的条款会直接影响你的商用资格。最后是最稳定的部分：Intended Use、Out of Scope 和联系人信息，通常只在产品定位调整或团队变更时更新，但至少应该每年走一次形式复审，确认联系人邮箱还有人看、报告渠道还通着。实操上建议把这四类的复审责任人和周期直接写进 Model Card 的 Maintenance 一节，否则"定期复审"就只是一个没有主人的意愿。
