一、PII 检测技术

PII 检测不存在"一种方法搞定"——规则抓得准但抓不全，模型抓得全但会误伤，所以只能分层叠加，用后一层补前一层的召回缺口。

PII 类型与风险等级

PII 类型示例风险等级检测难度
直接标识符姓名、身份证号、手机号极高低（规则匹配）
间接标识符出生日期、邮编、职业高中（组合识别）
敏感信息医疗记录、财务数据、宗教信仰高高（语义理解）
生物特征指纹、人脸、声纹极高中（格式检测）
上下文 PII特定场景下可识别个人的描述中极高（需要推理）

三层 PII 检测方案

核心原则：三层是互补而非替代。每层的输出都带 type / value / start / end / confidence / method，最后按位置区间去重合并——同一段文本被多层命中时保留置信度最高的判定，并记录是哪几层命中的，这个信息在调阈值时很有用。

检测层能抓什么抓不到什么典型代价
① 正则格式固定的标识符：手机号 1[3-9]\d{9}、身份证 \d{17}[\dXx]、邮箱、银行卡、IP姓名、地址、机构名——它们没有可枚举的模式微秒级；置信度可直接给 0.95
② NER 模型人名、地名、组织名等命名实体需要推理才能定位的隐含身份毫秒级；中文效果弱于英文，跨领域需微调
③ LLM 推理上下文型 PII，如"住在 XX 小区 3 栋 502 的张老师"—（召回最高）秒级 + 按 token 计费；会误检，需人工抽检校准
def detect(self, text, sensitivity="high"):
    r = self.regex_layer.scan(text)          # ① 快、准、召回低
    r += self.ner_layer.scan(text)           # ② 补命名实体
    if sensitivity == "high":                # ③ 只在高敏感场景开，它最贵
        r += self.llm_layer.scan(text)
    return self.deduplicate(r)               # 按 start/end 区间合并

正则层有两个容易被忽略的坑。一是 \d{16,19} 这类宽泛模式会把订单号、流水号一并命中，误报会淹没真实告警，所以银行卡应加 Luhn 校验，身份证应校验末位。二是分层的开关粒度要按数据敏感度而不是按环境定——把第三层挂在"生产环境"上没有意义，应该挂在"这条数据属于哪类业务"上。

  • 三层检测策略：正则（快+精确）→ NER（平衡）→ LLM（高召回），逐层增加召回率
  • 中文 PII 检测的挑战：姓名没有固定模式、地址格式多样、需要上下文理解
  • Presidio（Microsoft 开源）是 PII 检测的标准工具——支持自定义识别器

二、数据匿名化技术

选脱敏方式其实是在回答一个问题："这份数据接下来要被谁、拿去做什么"——给人看的可以直接遮掉，要参与关联分析的就必须保持一致性。

匿名化方法对比

方法原理数据可用性隐私强度适用场景
数据遮蔽用 * 或 [REDACTED] 替换低高日志脱敏、展示脱敏
伪名化用一致的假名替换高中测试数据、数据分析
泛化降低精度（年龄→年龄段）中中统计分析、报表
K-匿名每条记录至少有 K-1 条相同中中高发布结构化数据
差分隐私添加校准噪声中最高统计查询、模型训练
合成数据生成统计上相似的假数据高高开发测试、数据共享

脱敏实现 — 四种算子

四种策略的实现都很短，值得记住的是各自的取舍：遮蔽保留格式便于人工核对但不可用于分析；伪名化保留一致性（同一个"张三"在全库都映射成同一个假名），代价是映射表本身成了新的敏感资产；泛化降低精度换取可统计性；删除最彻底也最不可逆。

算子输入 → 输出保留了什么风险点
mask13812345678 → 138****5678；zhang@a.com → z***@a.com格式与部分明文，便于人工核对尾号+其他字段组合仍可能定位到人
pseudonymize张三 → PSEUDO_person_a3f9c1一致性——可跨表关联、可反向还原盐固定则可被字典枚举反推；映射表必须单独加密托管
generalize年龄 37 → 30-39；地址精确到市统计分布，仍可做分组分析小样本分组里"30-39 + 某罕见职业"可能仍唯一
redact张三 → [PERSON_REDACTED]只保留"这里曾有个 PII"这一事实不可逆，事后无法还原核对
def pseudonymize(self, value, pii_type):
    if value not in self.pseudo_map:                       # 同值同假名 = 一致性
        h = sha256((value + self.salt).encode()).hexdigest()[:12]
        self.pseudo_map[value] = f"PSEUDO_{pii_type}_{h}"
    return self.pseudo_map[value]

def anonymize_text(self, text, findings, strategy="mask"):
    for f in sorted(findings, key=lambda x: -x["start"]):  # 关键：从后往前替换
        rep = self.strategies[strategy](f["value"], f["type"])
        text = text[:f["start"]] + rep + text[f["end"]:]
    return text

sorted(..., key=-start) 这个细节值得留意：替换会改变字符串长度，从前往后替换会让后续 finding 的 start/end 偏移全部失效，导致截错位置——这类 bug 的表现是"脱敏后文本莫名少了几个字"，而且只在一条文本含多个 PII 时才出现。

脱敏管线在 LLM 链路中的位置

把上面这些算子放进真实链路，位置比算法更重要。原则是越靠外的边界越早脱敏：数据要出本地进程、要进日志、要发给第三方模型，这三个出口都必须已经是脱敏态。

用户输入 "我是张三，手机 13812345678，想查我的保单" │ ▼ ① 入口检测（正则 + NER，高敏感业务加 LLM 层） ┌──────────────────────────────────────────────────────┐ │ findings: [person@2-4, phone@8-19] │ └──────────────────┬───────────────────────────────────┘ ▼ ② 伪名化（保留一致性，映射表留在本地 KMS） "我是 PSEUDO_person_a3f9c1，手机 PSEUDO_phone_7d21e8，想查我的保单" │ ┌────────────┴─────────────┐ ▼ ▼ ③ RAG 检索 ④ 审计日志 召回文档同样要过脱敏 写入前 redact （知识库里也有 PII） 原文只留 SHA-256 │ │ ▼ ▼ ┌──────────────────────┐ ┌──────────────────┐ │ ⑤ 外部 LLM API │ │ 冷热分层存储 │ │ ⚠ 跨出组织边界 │ └──────────────────┘ │ 只能收到脱敏文本 │ └──────────┬───────────┘ ▼ 模型返回 "PSEUDO_person_a3f9c1 的保单为…" ⑥ 反脱敏（仅在返回给本人的响应里做，用内存中的映射表） ▼ "张三 的保单为…" ← 明文只在最后一跳、只对数据主体出现
  • 遮蔽最安全但数据不可用，伪名化保持数据可用但可能被逆向，差分隐私提供数学保证
  • GDPR 区分"匿名化"和"伪名化"——匿名化后的数据不再受 GDPR 约束，伪名化仍受约束
  • 脱敏策略应根据使用场景选择——日志用遮蔽/删除，分析用泛化，测试用合成数据

三、差分隐私

差分隐私给的承诺很具体：不管你的数据在不在这个库里，算法输出的概率分布几乎一样——所以攻击者看输出也推不出你在不在。

差分隐私核心概念

差分隐私（Differential Privacy, DP）的定义是：对任意两个相差一条记录的相邻数据集 D 与 D'，以及任意输出集合 S，满足 P[M(D)∈S] ≤ e^ε × P[M(D')∈S] + δ。隐私预算 ε 越小越私密（常用 0.1–10），δ 是允许的失败概率（常取 10⁻⁵）。

实现上最基础的是拉普拉斯机制：按"单条记录能造成的最大影响"（敏感度）除以 ε 来定噪声尺度。

def laplace_mechanism(true_value, sensitivity, epsilon):
    return true_value + np.random.laplace(0, sensitivity / epsilon)

dp_avg = laplace_mechanism(true_value=15000,
                           sensitivity=100000 / len(dataset),  # 单条最大影响
                           epsilon=1.0)   # ≈ 15000 ± 少量噪声

这里 sensitivity 是最容易算错的一项。它不是数据的方差，而是"改动任意一条记录能让结果最多变多少"——求平均值时等于取值上界除以样本数，所以样本量越大、同样的 ε 下噪声相对越小。这也解释了一个常见现象：小数据集上做差分隐私几乎没法用，噪声会盖过信号。

差分隐私在 ML 中的应用

DP-SGD 把这个思路搬到训练里：每个样本的梯度先裁剪到固定范数上界（max_grad_norm），再对批次梯度和加噪。裁剪是关键前提——没有它，单个异常样本可以对参数产生无界影响，敏感度算不出来，隐私保证也就不成立。Opacus 把这些封在 make_private_with_epsilon 里，训练代码几乎不用改。

model, optimizer, dataloader = PrivacyEngine().make_private_with_epsilon(
    module=model, optimizer=optimizer, data_loader=dataloader, epochs=10,
    target_epsilon=8.0, target_delta=1e-5,
    max_grad_norm=1.0)      # 逐样本梯度裁剪：敏感度有界的前提
# 之后 optimizer.step() 内部自动完成裁剪 + 加噪
print(PrivacyEngine().get_epsilon(delta=1e-5))   # 训练结束后核对实际消耗
ε 取值准确率量级（示意）适用场景说明
ε = 1约 85%医疗、金融等高敏感数据噪声大，需要更多数据才能训得动
ε = 8约 92%一般业务场景业界常用区间，Apple 在 iOS 中用 2–8
ε → ∞约 95%无隐私保护基线作为对照，用来量化隐私的代价

需要强调 ε 是累积消耗的：同一份数据训练多次、或对外提供多次统计查询，隐私预算会叠加。因此工程上要有一个预算账本，记录每份数据集已经花掉多少 ε，花完就不能再查——否则"每次都加了噪声"并不等于"始终是私密的"。

示例场景：某数据平台向内部分析师开放"按人群分组的平均收入"查询接口，每次查询走拉普拉斯机制加噪，团队认为这样就安全了。半年后一次内部红队测试发现：只要对同一分组反复查询 400 余次再取平均，噪声会因独立采样而相互抵消，还原出的真实均值误差不到 0.6%；进一步用"含某人"与"不含某人"两个分组各查一轮做差，可以把单个高收入个体的数值反推到约 ±3% 区间。根本原因是没有预算账本——每次查询都"合规"，但累积 ε 早已突破了任何有意义的上限。整改引入两项机制：按（数据集 × 分析师 × 时间窗）记账，单周 ε 上限设为 1.0，超出即拒绝而非降级；同时对重复的同构查询返回缓存的加噪结果而非重新采样，消掉噪声抵消这条路径。改造后同样的攻击在 400 次查询下的还原误差仍高于 18%，接口可用性不受影响——因为真实分析场景几乎没有对同一分组反复查询数百次的需求。

  • 差分隐私是唯一提供数学隐私保证的技术——epsilon 越小隐私越强
  • DP-SGD（Opacus）是 PyTorch 生态的标准差分隐私训练工具
  • 隐私-准确率权衡不可避免——epsilon=1 时准确率通常下降 5-10%

四、联邦学习

联邦学习换的是"数据不出域"，不是"什么都安全了"——梯度本身就携带训练数据的信息，能被反推出原始样本。

联邦学习架构

类型架构适用场景特点
横向联邦样本不同，特征相同多家医院的病历数据各方拥有相同特征的不同样本
纵向联邦样本相同，特征不同银行+电商的同一批用户各方拥有同一用户的不同特征
联邦迁移样本和特征都不同跨领域知识迁移通过迁移学习协同建模

横向联邦学习流程 — FedAvg

FedAvg 每一轮做三件事：服务端把全局模型分发下去、各客户端在本地数据上训几个 epoch、服务端按各方数据量加权平均回收的参数。加权是必要的——若按客户端数等权平均，一个只有 50 条数据的参与方会和拥有 50 万条的参与方拥有同等话语权。

def aggregate(self, updates):                 # updates = [(state_dict, n_i), ...]
    total = sum(n for _, n in updates)
    self.global_model.load_state_dict({
        k: sum(u[k] * (n / total) for u, n in updates)   # 按数据量加权，不是等权
        for k in self.global_model.state_dict()})

联邦学习 + 差分隐私

两者叠加才构成完整防线：联邦保证原始数据不出本地，差分隐私保证传出去的梯度也无法被反推。实现就是把客户端的本地训练换成 DP-SGD——服务端代码不用改，因为它收到的仍是普通的 state_dict。

# 客户端本地训练替换为 DP 版本，服务端聚合逻辑不变
self.model, self.optimizer, self.dataloader = PrivacyEngine().make_private_with_epsilon(
    module=self.model, optimizer=self.optimizer, data_loader=self.dataloader,
    epochs=epochs, target_epsilon=epsilon, target_delta=delta, max_grad_norm=1.0)
攻击做法缓解手段
梯度反推（DLG）从共享梯度优化出一个能产生同样梯度的输入，可部分还原图像或文本客户端 DP-SGD 加噪；增大本地 batch 使梯度混合
模型中毒恶意参与方上传带后门的更新，污染全局模型更新范数裁剪 + 中位数/裁剪均值等稳健聚合，替代朴素平均
成员推断通过多轮更新推断某条数据是否属于某参与方差分隐私；限制单方在单轮中的最大贡献
搭便车提交近乎不变的更新，只享受全局模型收益贡献度评估 + 更新相似度检测
服务端窥探服务端逐个查看单方更新安全聚合：加密后聚合，服务端只能解出总和
  • 联邦学习的核心价值："数据不出域，模型共享"——解决数据孤岛问题
  • 横向联邦最常见（各方有相同特征的不同样本），FedAvg 是最基础的聚合算法
  • 联邦学习 + 差分隐私双重保护：数据不出本地 + 梯度添加噪声

五、GDPR 与中国 PIPL 合规

两部法规的骨架高度重合：先证明"你凭什么处理这些数据"，再证明"你只拿了必需的那部分"，最后证明"用户想查想删时你做得到"。

AI 场景的隐私合规

把法条落到 AI 链路上，义务集中在三个环节。要注意的是这三项的举证难度差异很大：训练数据的合法基础往往是最薄弱的一环，因为数据通常在合规意识建立之前就已经收集完了。

环节对应条款落地做法
训练数据GDPR Art.6（合法基础）、Art.13-14（透明度）；PIPL Art.13（同意或其他合法事由）PII 必须脱敏或取得同意；完整保留数据来源与授权记录；定期复审合规状态
模型推理GDPR Art.22、PIPL Art.24（自动化决策）高风险决策提供人工审核通道；向用户说明决策的主要因素；不得借自动化实施不合理差别待遇
数据主体权利访问权、更正权、删除权建立请求处理流程并在 30 天内响应；向量库要能真正删除；训练数据删除后评估模型影响

其中自动化决策这一项在实现上比看起来重：所谓"提供人工审核"不是加个客服入口就算完，而是人工复核者必须能看到当次决策的依据（哪些特征、命中什么阈值），否则复核只是把同一个结论重复一遍，形式上有流程、实质上没有救济。

示例场景：某 SaaS 团队把客户工单接入外部大模型做自动分类，上线三个月后发现工单正文被原样拼进 prompt 发往境外 API，其中包含约 4.2 万条终端用户的姓名与手机号。问题有两层：一是未取得将数据提供给境外接收方的单独同意，二是完整正文远超分类任务所需，违反最小必要。整改分三步：在 API Gateway 层加入强制脱敏中间件（正则+NER 双层，命中即伪名化），把送给模型的内容从"完整正文"裁剪为"标题+首 200 字"，并对历史 90 天日志做一次全量重扫与清理。改造后单条 prompt 平均 token 从 1180 降到 260，模型调用成本随之下降约 78%，分类准确率从 91.2% 变为 90.6%——几乎没有损失，说明此前多送的那部分数据对任务本身并无贡献。

  • GDPR 和 PIPL 的核心共性：同意、最小化、透明度、数据主体权利
  • AI 训练数据的合法基础是关键合规点——互联网爬取的数据是否有合法基础？
  • 自动化决策（GDPR Art.22 / PIPL Art.24）需特殊关注——需提供人工审核和解释

六、训练数据溯源

溯源记录要回答的是"这条数据凭什么能用"——来源、授权、经过了哪些清洗，缺任何一环，模型就带着一笔说不清的债上线了。

数据溯源框架

数据溯源（Data Provenance）以数据集版本为单位记录四类信息。这份记录的价值在数据集被质疑时才体现：有它可以精确回答"哪一批数据有问题、影响了哪些模型版本"，没有它只能整个数据集连坐重做。

记录块字段与示例用途
sources每个来源记 name / url / license（如 CC-BY-4.0）/ collection_date / consent_type（open_license 或 explicit_consent + consent_record_id）证明合法基础；许可证变更时精确定位受影响批次
processing_chain有序步骤及影响量：去重 MinHash −1200 条、PII 检测 Presidio 发现 356 处、伪名化、质量过滤 fasttext −890 条、毒性过滤 −45 条证明清洗真实执行过；异常的移除比例是数据质量的早期信号
quality_metricstotal 150000 / unique 148800 / pii_clean / toxic_clean / 标注一致性 0.85作为版本间可比的基线；一致性低于 0.8 通常意味着标注规范本身有歧义
compliancegdpr_lawful_basis、pipl_compliance、copyright_review 及复审日期审计时直接出证，不必临时补材料

processing_chain 要记有序步骤而不只是"做过哪些处理"，因为顺序会改变结果：先去重再检测 PII，和先检测再去重，得到的 PII 计数不同；毒性过滤放在脱敏之后，可能因为占位符破坏了语义而误判。

向量数据库中的被遗忘权

删除本身不难，难的是删干净并且能证明删干净了。流程是四步：靠元数据索引定位该用户的全部文档、逐个删除向量、记录审计事件、再反查一次确认为空并出具删除证书。反查这一步不能省——它是把"我调用了删除接口"变成"我验证过已删除"的唯一区别。

doc_ids = self.metadata.find_by_user(user_id)      # ① 靠元数据索引定位
for d in doc_ids: self.db.delete(id=d)             # ② 删向量
self.audit_log.record({"action": "right_to_forget",
                       "user_id": user_id, "documents_deleted": len(doc_ids)})
assert len(self.metadata.find_by_user(user_id)) == 0, "删除不完整"   # ③ 反查验证
return DeletionCertificate(user_id=user_id, docs_deleted=len(doc_ids), verified=True)
挑战问题实质应对
嵌入向量是否算个人数据存在争议；若能由向量反推出个人信息，则应按个人数据对待保守处理——把向量与原文同等看待，一并纳入删除范围
索引未真正移除部分索引结构（如 FAISS 的 IVF）删除只是打标记，数据仍在索引文件中定期重建索引，并把重建纳入删除流程的完成条件
副本与备份多副本、快照、离线备份里仍有该用户的数据删除任务扩展到全部副本；备份用加密粉碎或等其自然过期并记录承诺期限
模型已记住向量若曾用于微调，删向量不等于模型遗忘属于 Machine Unlearning 问题，目前实践是记录影响范围，在下次重训时排除
  • 数据溯源记录"数据从哪来、怎么处理、现在在哪"——合规审计的基础
  • 向量数据库的"被遗忘权"实现有独特挑战——嵌入向量是否构成"个人数据"存在争议
  • 训练数据中的用户数据被删除后，已训练的模型该如何处理？这是开放问题

七、数据最小化原则

最小化不是"尽量少存"这种态度问题，而是一条可检验的规则：每个字段都要说得出它服务于哪个具体目的，说不出就不该在那里。

数据最小化实践

四个阶段各有一个可落地的抓手，其中"处理阶段"是 LLM 应用特有的——传统系统里 prompt 这个概念不存在，也就没人想过它是一处数据出口。

阶段要求技术抓手
收集只收业务必需字段，敏感信息非必要不收，每个用途单独取得同意表单默认不含可选字段；同意项按用途拆分而非打包勾选
存储过期即清、敏感加密、冷热分层TTL 策略 + 自动化生命周期管理，删除由调度器执行而非靠人记得
处理prompt 不含非必要 PII，RAG 结果脱敏后入模，输出再过一次 PII 过滤在 RAG pipeline 中插入 PII filter 中间件
共享调第三方 API 前脱敏，日志脱敏，不把用户原文发给外部模型在 API Gateway 层强制脱敏，做成基础设施而非业务代码的自觉

脱敏放在 Gateway 而不是业务代码里，是个有意的架构选择：业务代码由几十个团队各自编写，任何一处遗漏都会造成明文外发；而 Gateway 是唯一出口，在那里做强制拦截才能保证"不可能绕过"。

def process_request(self, user_input, context_docs):
    inp  = anon.anonymize(user_input, det.detect(user_input), "pseudonymize")
    docs = [anon.anonymize(d.content, det.detect(d.content)) for d in context_docs]
    resp = self.llm.generate(inp, docs)              # 外部模型只见伪名
    return anon.de_anonymize(resp, anon.pseudo_map)  # 仅对数据主体还原

这条管线里有一个反直觉的必要步骤：RAG 检索结果也要脱敏。很多团队只处理用户输入，理由是"知识库是我们自己的内部文档"——但内部文档里同样有客户姓名和联系方式，一旦被召回拼进 prompt，照样会随请求发往外部模型。

  • PII 检测分层叠加：正则打底、NER 补实体、高敏感业务再挂 LLM 层兜底
  • 替换时从后往前遍历 finding，避免偏移量错位截错字符
  • 伪名化的映射表单独加密托管，并按会话生命周期尽早销毁
  • RAG 召回内容同样脱敏——内部文档里的 PII 一样会随 prompt 外发
  • 脱敏做在 API Gateway 这一唯一出口，让绕过在架构上不可能
  • 差分隐私维护 ε 预算账本，累积消耗到上限即停止对外查询
  • 删除后反查验证并出具删除证书，把动作变成可举证的事实
  • 别只用正则就宣称完成 PII 检测——姓名和地址根本不在它的能力范围内
  • 别用固定盐的哈希当匿名化，它可被字典枚举反推，只算假名化
  • 别把用户原文直接拼进发往外部模型的 prompt，那等同于向第三方共享数据
  • 别以为联邦学习就等于安全，裸梯度可被 DLG 攻击反推出训练样本
  • 别在小数据集上硬上差分隐私，噪声会盖过信号，得到一个既不准也没人用的模型
  • 别把删除接口调用成功当作删除完成，索引标记删除和副本残留都很常见
  • 别把脱敏日志与明文备份放在同一套权限下，否则脱敏形同虚设
  • 数据最小化贯穿全生命周期：收集（只要必需的）→ 存储（定期清理）→ 处理（脱敏后使用）→ 共享（不传原始数据）
  • LLM 应用的关键实践：用户输入和 RAG 结果脱敏后再送入模型，输出时反脱敏
  • 向外部 LLM API 发送数据时必须脱敏——发送给第三方等于数据共享

Q&A

PII 检测的三层方案（正则、NER、LLM）各有什么优缺点？

三层 PII 检测方案的对比：①正则匹配——优点：速度极快（微秒级）、精确率高（匹配即确认）、可解释；缺点：只能检测固定模式的 PII（手机号、身份证号），无法检测姓名、地址等无固定模式的 PII，召回率低。②NER 模型——优点：能识别姓名、地址、组织名等无固定模式的实体，速度适中（毫秒级）；缺点：需要领域特定的训练数据，跨领域泛化能力有限，中文 NER 性能不如英文。③LLM 推理——优点：能理解上下文中的隐含 PII（如"住在 XX 小区 3 栋 502 的张老师"），召回率最高；缺点：速度慢（秒级）、成本高、可能产生幻觉（误检）。实践策略：先用正则快速过滤明确的 PII，再用 NER 补充识别实体，高敏感场景最后用 LLM 兜底检测上下文 PII。三层是互补而非替代关系。

差分隐私的核心原理是什么？epsilon 参数如何选择？

差分隐私的核心思想：对于任何两个仅差一条记录的数据集 D 和 D'，算法 M 在这两个数据集上的输出概率分布几乎相同，数学定义为 P[M(D)∈S] ≤ e^epsilon × P[M(D')∈S] + delta。直觉理解：无论你的数据是否在数据集中，算法的输出几乎不变——因此攻击者无法通过观察输出推断你的数据。epsilon 选择指南：epsilon=0.1-1（强隐私，适合医疗/金融敏感数据，准确率损失 5-15%）；epsilon=1-8（中等隐私，适合一般业务场景，准确率损失 2-8%）；epsilon>10（弱隐私，实际保护有限）。Apple 在 iOS 中使用 epsilon=2-8，Google 在 RAPPOR 中使用 epsilon=ln(3)≈1.1。选择原则：根据数据敏感度、数据量（数据越多容忍噪声越大）、和可接受的准确率损失综合决定。

联邦学习如何保护数据隐私？有哪些安全风险？

联邦学习的隐私保护机制：原始数据不离开本地，只共享模型更新（梯度或参数）。三种类型：横向联邦（各方有相同特征的不同样本，如多家医院的病历）、纵向联邦（各方有同一用户的不同特征，如银行+电商）、联邦迁移（样本和特征都不同）。安全风险：①梯度反推攻击——通过分析共享的梯度更新，可以部分重建原始训练数据（DLG 攻击可从梯度恢复图像和文本）；②模型中毒——恶意参与方上传带后门的模型更新，污染全局模型；③搭便车——参与方不贡献真实更新但获取全局模型收益；④推断攻击——通过多轮更新推断某条数据是否存在于特定参与方。缓解措施：联邦学习+差分隐私（梯度添加噪声防止反推）、安全聚合（加密聚合使服务器看不到单个更新）、异常检测（识别恶意更新）。

如何在向量数据库中实现 GDPR 的"被遗忘权"？

向量数据库中实现被遗忘权的技术方案：①元数据索引——为每条向量建立 user_id → vector_id 的映射索引，收到删除请求时通过索引定位所有相关向量；②向量删除——调用向量数据库的 delete API 删除所有关联向量；③验证完整性——删除后查询确认该用户的所有向量已清除；④审计记录——生成删除证书记录操作时间、删除数量、验证结果。独特挑战：①嵌入向量是否构成"个人数据"存在法律争议——如果通过向量可以推断出个人信息，则受 GDPR 约束；②分布式副本——向量数据库通常有多个副本和备份，都需要同步删除；③索引重建——某些数据库（如 FAISS IVF 索引）删除后需要重建索引才能真正移除；④模型记忆——如果向量曾用于模型微调，删除向量不等于从模型中"遗忘"，这是更深层的 Machine Unlearning 问题。

LLM 应用如何实现数据最小化原则？

LLM 应用的数据最小化实践贯穿四个环节：①收集——只收集业务必需的用户输入，不强制要求身份信息，聊天历史设置合理的保留期限（如 30 天自动清理）；②处理——在发送给 LLM 之前脱敏用户输入中的 PII（伪名化），RAG 检索结果也需脱敏后再拼入 prompt，LLM 输出进行 PII 过滤后再返回给用户；③传输——向外部 LLM API（如 OpenAI）发送数据时必须脱敏，因为这等同于数据共享给第三方；④存储——审计日志中的 PII 进行脱敏或加密存储，对话历史定期清理，用户请求删除时能真正删除。关键技术实现：在 LLM pipeline 中添加 PII Filter 中间件（检测→脱敏→调用LLM→反脱敏→输出过滤），使用伪名化保持文本连贯性（"张三"→"PERSON_A"），响应中将伪名映射回真实值。

GDPR 意义上的"匿名化"和"伪名化"差在哪里？为什么这个区别对工程实现很重要？

差别在于能否重新识别到具体个人。匿名化是不可逆的：处理后的数据无论结合什么额外信息都无法定位到自然人，因此这类数据不再属于个人数据，也就不再受 GDPR 约束——保留期限、删除请求、跨境限制都不适用。伪名化只是把直接标识符换成了替代标识，只要还存在映射表、或者替代标识是由原值确定性推导出来的，就仍然可以还原，因此数据依旧是个人数据，全部义务照旧。这个区别在工程上有三个直接后果。第一，用固定盐的 SHA-256 替换手机号不构成匿名化：手机号空间只有约十亿量级，攻击者可以在几分钟内把全部号码算一遍做成彩虹表反查，所以这只是伪名化。第二，只要保留了映射表，映射表本身就是最高敏感级别的资产，需要独立加密、独立授权、并且尽早销毁——很多团队把它随手放在应用内存或普通缓存里，等于把所有脱敏努力集中到一个薄弱点上。第三，真正的匿名化通常需要配合泛化或加噪，并且要评估"组合识别"风险：性别、出生日期、邮编三项组合就能在人群中唯一定位相当比例的个体，单独看每项都不算标识符，合起来却是。

把用户数据发给外部大模型 API 时，除了脱敏还需要注意什么？

脱敏解决的是内容问题，但这条链路上还有四件事同样会构成合规缺口。第一是法律基础与告知：把数据交给外部厂商属于向第三方提供，通常需要在隐私政策中明确披露接收方，涉及跨境时还要满足单独同意和安全评估等额外要求，这一步无法靠技术手段补救。第二是厂商侧的数据使用条款：要确认对方是否会用你的请求做模型训练、日志保留多久、是否支持零保留模式，同一家厂商的不同套餐条款往往不同。第三是最小化本身：脱敏不改变"送了多少"，很多场景下完整正文对任务并无贡献，把输入裁剪到任务真正需要的片段既降风险又降成本，通常比脱敏收益更大。第四是可举证性：需要留下"发出去的是脱敏后内容"的证据，也就是在审计日志里记录实际外发载荷的摘要或哈希，否则事后无法证明没有外泄明文。另外还有一个容易被忽略的方向——模型的输出也要过一遍 PII 过滤，因为模型可能在回答里复述或拼接出敏感信息，尤其是在 RAG 场景下它会照抄召回内容。
