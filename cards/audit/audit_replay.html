U03 · 审计回放

Audit Replay — 对话链回放、决策重建与 Agent 行为轨迹可视化

一、审计回放概述

你没法把 LLM"重新跑一遍"得到当时的答案，所以回放能还原多少，全看当时记了多少——回放是记录质量的兑现，不是补救手段。

什么是审计回放

审计回放是指从存储的日志和追踪数据中，还原 AI 系统在特定时间点的完整行为过程，包括用户输入、模型推理、工具调用、决策路径等全链路信息。注意它和"重新执行"是两件事：回放看的是当时留下的快照，重新执行得到的是今天这个模型的新结果，后者在审计场景里没有证据价值。

维度传统应用调试LLM 审计回放
目标找到代码 bug还原 AI 决策过程、理解"为什么这样回答"
数据源代码 + 日志 + 堆栈对话链 + 工具调用 + 模型参数 + 检索结果
确定性可精确重现不可精确重现（LLM 非确定性），只能"回看"
复杂度线性调用栈多轮对话 + 并行工具调用 + 递归 Agent 调用
用途修复 bug合规审计 + 事件调查 + 质量分析 + 用户投诉

回放场景

场景需要回放的内容关注点
用户投诉用户发了什么 → 模型回了什么回答质量、是否存在幻觉
安全事件攻击者的完整交互序列注入手法、数据泄露范围
合规审查AI 辅助决策的完整依据链决策是否有合理依据
Agent 异常Agent 的完整工具调用链在哪一步出错、为什么走错路
模型退化特定时段的批量输出模型版本切换是否导致质量下降

审计回放的核心原则：你不能"重新运行"LLM 来得到相同结果（非确定性），所以必须在运行时记录足够多的信息以支持事后回看。这就是"记录优先"的设计哲学。

时间轴与快照的关系

把回放想成沿时间轴摆放的一串快照：每次请求都会在多个点位冻结一份现场（上下文窗口、检索结果、工具返回、模型版本），事后能看到什么，取决于当时冻结了哪些点。真实世界的状态会一直往前漂移——文档被更新、模型被升级、工具的下游数据变了——而快照是唯一不漂移的东西。

真实世界（不断漂移，无法回退） ──────────────────────────────────────────────────────────▶ t 知识库 v7 知识库 v8 知识库 v9 知识库 v10 模型快照 模型快照 0409 模型快照 0409 模型快照 0806 0125 ↑ ↑ │ 事件发生在这里 │ 半年后在这里调查 │ T₀ = 2024-04-20 10:30 │ T₁ = 2024-10-15 │ │ ┌─────────────┴──────────────┐ │ │ T₀ 时刻冻结的快照 │ │ │ · context_window 全文 │◀────────────────┘ │ · model + model_version │ ✅ 回放 = 读快照 │ · temperature / top_p │ 与今天的世界无关 │ · retrieval: doc_id+版本+ │ │ score + snippet │ ❌ 重新执行 = 用 0806 模型 │ · tool_call: 入参+出参 │ 查 v10 知识库 │ · finish_reason / usage │ 得到的是新结果，不是证据 └────────────────────────────┘ 没冻结的东西，事后一律拿不回来： 上下文被怎么截断的、检索命中的是文档的哪个版本、 工具当时返回了什么 —— 这些都无法从结果反推。
  • 审计回放 ≠ 重新执行——LLM 的非确定性意味着只能"回看记录"而非"重新运行"
  • 回放的五大场景：用户投诉、安全事件、合规审查、Agent 异常、模型退化
  • 回放质量取决于记录质量——运行时记录不完整，事后无法弥补

二、对话链回放

回放对话链要还原的不是"用户说了什么、模型答了什么"，而是"模型当时到底看到了什么"——上下文窗口才是它做判断的全部依据。

对话链数据模型

核心原则：数据模型分两层——ConversationChain 只管标识与归属（conversation_id / session_id / user_id / created_at），每一轮的证据都挂在 ConversationTurn 上。这样按会话拉取时可以先看骨架再按需展开单轮，避免一次把几十 MB 的上下文全读出来。

单轮必存字段为什么重要实现要点
context_window最关键的一项：模型只依据这份内容作答，只存 user/assistant 两条消息等于丢掉了推理依据存截断后真正发出去的完整消息列表，不是原始历史
model_configtemperature / top_p / max_tokens 直接决定输出的随机性与是否被截断连同 model_version 快照号一起存
retrieval_results幻觉排查的第一现场——是模型编的，还是检索本身给错了存 source、score、片段，以及命中文档的版本号
tool_calls工具返回的外部数据会随时间变化，事后无法重查入参与出参都存，附耗时和成功标志
usage / latency_ms延迟与成本异常的定位依据token 数按 prompt / completion 分开记
content_filter_result解释"为什么这次回答被截断或替换了"记过滤类型、动作、命中原因

对话链可视化回放

渲染器做的事很机械：把每一轮拆成若干带时间戳的事件，按时间排序输出一条统一的时间轴。之所以要拆平，是因为一轮里的检索、工具调用、模型生成在时间上是有先后甚至并行关系的，塞在同一个"turn"里看不出谁在等谁。

for turn in chain.turns:
    tl.append({"type": "user_message", "time": turn.timestamp, ...})
    if turn.retrieval_results:                       # 检索先于生成
        tl.append({"type": "retrieval", "time": turn.timestamp + 50ms, ...})
    for tc in turn.tool_calls:                       # 工具调用各有起止
        tl.append({"type": "tool_call", "time": tc.timestamp,
                   "tool": tc.name, "input": tc.arguments, "output": tc.result})
    tl.append({"type": "assistant_message",          # 生成落在延迟之后
               "time": turn.timestamp + turn.latency_ms, ...})
return ReplayTimeline(events=sorted(tl, key=lambda e: e["time"]))

事件的 time 应该来自各自的实测时间戳，而不是像上面示意那样用固定偏移量推算。用推算值渲染出来的时间轴看着很整齐，但"检索慢了 800ms 拖垮整轮"这类问题会被抹平——而这恰恰是回放最该暴露的信息。

  • 回放必须包含完整的 context_window——不仅是最后一轮，而是模型实际"看到"的所有内容
  • RAG 检索结果也要记录——理解"模型参考了什么"对分析回答质量至关重要
  • 时间轴可视化让非技术人员（合规审计员）也能理解 AI 的行为过程

三、Agent 行为轨迹回放

Agent 出错很少错在最后一步，通常是中间某次观察被误读、然后一路顺着错误前提往下走——所以轨迹要记的是每一步的"想法"和"看到的结果"，而不只是最终答案。

Agent 轨迹数据模型

轨迹以 AgentTrajectory 为根（trace_id、agent_type、原始任务、步骤列表、最终结果、总耗时与总 token），核心是有序的 AgentStep 序列。每步记录 Think-Act-Observe 三元组：thought 是推理文本，action 是选中的工具及入参出参，observation 是它实际读到的结果；委派给子 Agent 时额外记 sub_agent_trace 指向子轨迹。

一个 ReAct 轨迹展开后就是这样一串三元组循环，看的时候要盯 thought 和 observation 之间是否自洽：

step 1  think   "用户要求分析 Q3 财报，需要先获取数据"
        act     search_documents(query="Q3 财报")
        observe "找到 3 个相关文档"
step 2  think   "数据已获取，需要提取关键指标进行对比分析"
        act     extract_data(doc_ids=[...])
        observe "提取到收入、利润率等指标"
step 3  think   "数据充分，可以生成分析报告"
        act     generate_report(format="summary")

三元组齐全之后，几类典型故障可以靠机器扫出来，不必人工逐条读：

故障模式轨迹上的特征自动检测规则
死循环连续多步 observation 完全相同，thought 在换措辞相邻 3 步 observation 哈希一致即告警
错误忽略action 返回 success=false，下一步 thought 却当成功继续失败步之后的 thought 未提及失败即标记
前提漂移thought 引用的数值在任何 observation 里都找不到抽取 thought 中的数字，与上游 observation 做包含性校验
无效委派子 Agent 返回结果但父 Agent 的后续 thought 未使用比对 sub_agent_trace 结果与父级后续步骤的引用

多 Agent 轨迹关联

多 Agent 的关键是别让每个 Agent 各记一本流水账。委派时用 parent_trace_id 把子轨迹挂到父轨迹上，最终得到一棵可折叠的调用树；否则事故调查时你手上是七八条互不相干的 trace，拼不出谁调用了谁。

Orchestrator Agent trace_001 ⏱ 0 ─────────────── 8.4s │ task: "写一份 AI 合规现状报告" │ ├─▶ Research Agent trace_002 ⏱ 0.2s ──── 3.1s │ │ parent_trace_id = trace_001 │ ├─ tool_call web_search("AI regulations 2024") 1.8s ✅ │ └─ tool_call read_document(doc_id=…) 1.1s ✅ │ ├─▶ Analysis Agent trace_003 ⏱ 3.1s ──── 6.0s │ │ parent_trace_id = trace_001 │ ├─ tool_call extract_data(…) 2.2s ✅ │ └─ tool_call calculate_metrics(…) 0.7s ⚠ 重试 1 次 │ └─▶ Writer Agent trace_004 ⏱ 6.0s ──── 8.4s │ parent_trace_id = trace_001 └─ tool_call generate_report(format="summary") 2.3s ✅ 读法：先看树形找责任 Agent，再沿时间轴找卡住的那一段。 没有 parent_trace_id ⇒ 四条独立 trace，无法回答"是谁让它去搜的"。
  • Agent 轨迹记录的核心是 Think-Act-Observe 三元组——完整记录推理、行动和观察
  • 多 Agent 系统需要分布式追踪——用 parent_trace_id 构建调用树
  • 轨迹回放是 Agent 调试的唯一手段——因为你无法"重新运行 Agent 得到相同结果"

四、OpenTelemetry 实现追踪

用 OpenTelemetry 记 LLM，等于把"模型调用"降格为一次普通的外部依赖调用——这样它就能和数据库、向量库、网关的耗时摆在同一条链路上比较。

OpenTelemetry 在 LLM 中的应用

接入只需三步：建 TracerProvider、挂 BatchSpanProcessor（批量导出，避免每个 span 都发一次网络请求）、把 OTLP 端点指向 Jaeger 或 Grafana Tempo。之后在 LLM 调用和 Agent 步骤处开 Span，把关键信息写成属性。

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(   # 批量导出，别用 Simple
    OTLPSpanExporter(endpoint="http://jaeger:4317")))
trace.set_tracer_provider(provider)

with tracer.start_as_current_span("llm.completion", kind=SpanKind.CLIENT) as sp:
    sp.set_attribute("gen_ai.request.model", model)
    resp = client.chat.completions.create(messages=messages, **kwargs)
    sp.set_attribute("gen_ai.usage.output_tokens", resp.usage.completion_tokens)
    sp.set_attribute("gen_ai.response.finish_reasons", [c.finish_reason for c in resp.choices])
埋点位置Span 名 / 属性能回答什么
LLM 调用llm.completion；model、temperature、max_tokens、input/output_tokens、finish_reason延迟花在模型还是别处，是否被 max_tokens 截断
RAG 检索rag.retrieval 及子 span embedding.encode / vector_db.search召回慢在编码还是检索，命中几条、分数多少
Agent 步骤agent.step.N；thought、action、action_args、observation、success哪一步走错、哪一步耗时最久
异常路径span.status=ERROR + record_exception失败是否被上层静默吞掉

有两个属性要小心：agent.thought 和 agent.observation 可能很长且含用户数据，直接写进 span 属性会让 trace 后端膨胀且形成一处未受控的敏感数据副本。通常只在 span 里放摘要或引用 id，全文留在审计存储里，两边用 trace_id 关联。

Trace 关联与上下文传播

LLM 属性名已在向 gen_ai.* 语义约定收敛（gen_ai.system、gen_ai.request.model、gen_ai.request.temperature、gen_ai.response.finish_reasons、gen_ai.usage.input_tokens / output_tokens）。用约定名而非自定义名的好处很实际：换一套可视化工具或换一家厂商 SDK，现成的看板和告警不用重写。

跨服务时靠 上下文传播（W3C traceparent 头）把 trace 串起来，最终在 Jaeger 里得到一棵可下钻的耗时树：

Trace: user_request_abc 总计 ≈ 2.17s │ ├─ Span api.handler ······································· 12ms │ │ │ ├─ Span rag.retrieval ································· 45ms │ │ ├─ Span embedding.encode ·························· 8ms │ │ └─ Span vector_db.search ························· 35ms │ │ │ ├─ Span context.assembly ······························ 3ms │ │ │ ├─ Span llm.completion ····························· 2100ms ◀ 瓶颈 │ │ ├─ Event prompt_tokens = 1520 │ │ ├─ Event stream_first_token @ 380ms ◀ 首字延迟单独记 │ │ └─ Event completion_tokens = 890 │ │ │ └─ Span response.filter ······························· 5ms │ └─ Span audit.log ·········································· 2ms （异步导出，不计入用户可见延迟） 一眼可读：97% 时间在模型侧；若 first_token 早而总耗时长， 说明是逐 token 生成慢，而非排队或网络问题。
  • OpenTelemetry 是可观测性的事实标准——用 Span 表示操作，用 Trace 关联完整链路
  • LLM 语义约定正在标准化（gen_ai.* 命名空间），确保不同工具/供应商的 trace 互操作
  • 在 Jaeger/Zipkin 中可以直观看到每个 Agent 步骤的耗时和调用关系

五、事件根因分析

找根因的诀窍不是盯着异常本身看，而是把异常出现的时刻往前对齐——最近一次部署、配置改动或模型版本切换，往往就在那条线附近。

LLM 事件分类与根因

事件类型表现常见根因回放关注点
幻觉回答含虚假信息检索失败、上下文不足、模型能力检索了什么文档？context_window 完整吗？
安全绕过输出有害内容Prompt 注入、系统 prompt 泄露完整的对话历史、注入点在哪一轮？
Agent 循环Agent 陷入死循环观察结果不变、工具返回错误每步的 thought 和 observation 变化
延迟飙升响应时间异常增长上下文过长、模型过载prompt_tokens 变化趋势、API 延迟
质量退化回答质量突然下降模型版本切换、系统 prompt 变更对比前后的 model_version 和 system_prompt

根因分析工作流

核心原则：四步走——收集证据、比对基线、时间对齐、假设验证。真正产生洞察的是第三步关联分析：把指标异常的起始时刻，与部署事件、配置变更、模型版本切换三条独立时间线叠在一起，看谁最靠前。

步骤做什么为什么不能跳
① 收集按时间范围与受影响实体拉全部相关 trace只看被投诉的那一条会把个例当共性，也可能反过来漏掉面上的问题
② 异常检测与基线对比（如 latency_p99 3000ms、error_rate 1%、token 均值 2000）没有基线就没有"异常"，只有主观感觉"好像慢了"
③ 关联叠加部署、配置、模型版本三条变更时间线LLM 侧的多数退化不是代码 bug，而是外部变更；不叠时间线就查不到
④ 验证在测试环境用 temperature=0 重放可疑输入关联只给出相关性，重放才能把假设变成结论
anomalies = detect_anomalies(traces, baselines={
    "latency_p99": 3000, "error_rate": 0.01, "token_usage_avg": 2000})
correlations = correlate(anomalies, events=[      # ③ 三条变更线同时叠
    get_deployment_events(tr), get_config_changes(tr),
    get_model_version_changes(tr)])
return RootCauseReport(timeline=build_timeline(traces, anomalies),
                       probable_cause=correlations.most_likely,
                       evidence=correlations.supporting_data)

示例场景：某企业客服助手在一周内的用户"踩"率从 3.1% 涨到 11.7%，但延迟、错误率、token 消耗三项指标全部正常，监控没有报警。调查从回放入手：抽取 200 条被踩会话，发现 retrieval_results 的平均相关性分数从 0.81 掉到 0.52，而 context_window 里塞进了大量不相关文档。把三条变更时间线叠上去后对齐到一次向量库的索引重建——重建时 chunk 大小的配置项没有随代码一起同步，从 512 token 变回了默认的 1024，导致召回粒度变粗。修复后重新抽样，相关性分数回到 0.79，两周内踩率回落至 3.4%。这个案例的意义在于：如果当时没有记录 retrieval_results 和完整 context_window，回放只能看到"模型答得不好"，永远查不到检索侧。

  • 根因分析的关键是"关联"——将异常指标与部署事件、配置变更、模型版本切换关联
  • LLM 特有的根因：幻觉（检索失败）、Agent 死循环（observation 不变）、质量退化（模型切换）
  • 根因分析报告应包含：时间线、可能原因、证据数据、修复建议

六、回放 vs 实时调试

生产环境里你只有回放这一种手段——实时调试的前提是能打断点、能改参数、能重试，而这三件事在生产上都不允许做。

两种调试模式对比

维度审计回放（Post-mortem）实时调试（Live Debugging）
时机事后分析实时介入
数据来源存储的日志和 trace实时流数据
精确性取决于记录完整性完整的实时上下文
干预能力只能回看，无法修改可以断点、修改参数、重试
性能影响零影响（离线分析）可能降低服务性能
适用场景合规审计、事件调查开发调试、实时故障排查

混合调试策略

两种模式不是二选一：回放负责在海量记录里定位可疑步骤，实时调试负责在隔离环境里验证假设。串起来就是"先用回放缩小范围，再用重放确认因果"。

suspicious = [s for s in replayer.load_trace(tid).get_timeline()
              if s.anomaly_score > 0.7]                # ① 回放定位
for s in suspicious:
    repro = live_debugger.run_with_breakpoint(
        input=s.input, breakpoint_at=s.step_number,
        model=s.model_config["model"], temperature=0)   # ② 关掉随机性再比
    if compare(s, repro).divergence > 0.5:
        flag_as_non_reproducible(s)                     # ③ 复现不了本身是信息

temperature=0 是这里的关键：不消掉采样随机性，你无法判断差异来自"代码/配置变了"还是"这次骰子不同"。而"复现不出来"也是有价值的结论——它把怀疑对象从确定性逻辑推向了模型侧或外部依赖。

影子模式（Shadow Mode）是另一条路：把生产请求复制一份到测试环境用新配置并行跑，只做 diff 不返回给用户。它的价值在于能在真实流量分布上评估变更，而不是靠人造的测试集。代价是双倍模型开销，所以通常只按 1%～5% 采样。

手段能回答什么代价 / 限制
回放当时发生了什么、哪一步异常受记录完整性限制，看不到没记的东西
测试环境重放（temperature=0）这个差异是确定性原因还是随机性造成的需要能复刻当时的依赖状态，模型版本可能已不可用
影子模式新配置在真实流量上会不会更差双倍推理成本，且必须保证影子链路绝不写生产数据
  • 把 context_window 全文连同 model_version 一起冻结——它是回放唯一不可替代的部分
  • 检索结果记文档版本号，否则知识库更新后无法判断当时召回的是哪一版内容
  • Agent 每步都记 Think-Act-Observe 三元组，并对"连续 observation 相同"做自动告警
  • 多 Agent 一律带 parent_trace_id，让轨迹能拼成调用树
  • span 属性只放摘要或引用 id，长文本与敏感内容留在审计存储
  • 重放验证时固定 temperature=0，先排除随机性再谈因果
  • 别把"重新调一次模型"当回放——今天的模型和当时的模型不是同一个东西，结果没有证据价值
  • 别只存 user / assistant 两条消息，丢掉上下文窗口等于丢掉全部推理依据
  • 别用固定偏移量推算时间轴，会把"检索拖慢一整轮"这类问题抹平
  • 别把 thought / observation 全文写进 trace 后端，那会形成一份没人管的敏感数据副本
  • 别在生产链路上做断点调试或改参重试，生产只允许观测
  • 别让影子链路拥有写权限，一次误写就会污染真实数据
  • 回放适合合规审计和事后分析，实时调试适合开发和故障排查——生产环境通常只有回放
  • 混合策略：先用回放定位可疑步骤，再在测试环境重放验证
  • 影子模式（Shadow Mode）可以在不影响生产的情况下对比新旧模型/配置的行为差异

七、时间线可视化实现

时间线做成"泳道"而不是一条流水，是为了让并行关系一眼可见——单条流水只能告诉你顺序，泳道能告诉你谁在等谁。

时间线可视化架构

数据结构很简单：一个 trace 下挂若干 lane，每条泳道对应一个活动维度，泳道内是带 time 与 duration 的事件。前端用甘特图库（vis-timeline、react-chrono）渲染，支持缩放、点击下钻和按类型过滤。

回放解决单条追查，仪表盘解决"是不是普遍现象"。三组指标各有分工：会话组看整体健康度，模型组看性能与成本，Agent 组看行为质量。

Q&A

为什么 LLM 应用的审计回放不能简单地"重新运行"来重现？

根本原因是 LLM 的非确定性：①即使使用相同的 prompt 和参数（如 temperature=0.7），模型每次生成的内容也可能不同，因为 sampling 过程本质是随机的；②模型版本可能已更新——供应商会持续迭代模型权重，一个月前的 gpt-4 和现在的 gpt-4 可能是不同版本；③上下文依赖——多轮对话中前面轮次的回答影响后续轮次，而前面轮次本身就不可精确重现；④外部状态——Agent 调用的工具（数据库查询、网页搜索）返回的结果会随时间变化。因此审计回放的正确做法是"记录优先"——在运行时完整记录 prompt、response、context_window、工具调用结果、模型版本等全量信息，事后直接回看记录而非重新运行。

如何使用 OpenTelemetry 实现 LLM 应用的分布式追踪？

实现步骤：①初始化 TracerProvider 并配置 Exporter（如 OTLP 输出到 Jaeger/Grafana Tempo）；②在 LLM 调用处创建 Span，记录模型名、temperature、token 使用量等属性（使用 gen_ai.* 语义约定）；③在 RAG 检索处创建子 Span，记录查询、结果数量、相关性分数；④在 Agent 步骤处创建子 Span，记录 thought、action、observation；⑤通过 Context Propagation 确保跨服务的 trace 关联（如 API Gateway → LLM Service → Vector DB）。关键实践：使用 BatchSpanProcessor 避免性能影响；为 LLM 调用设置 span.kind=CLIENT（外部服务调用）；在异常情况下记录 span.status=ERROR 和错误详情；使用 span events 记录时间点信息（如 "stream_first_token"）。

如何设计 Agent 行为轨迹的回放系统？

Agent 轨迹回放系统的设计要点：①数据模型——以 AgentTrajectory 为根，包含有序的 AgentStep 列表，每个 step 记录 Think（推理过程）、Act（工具调用及参数）、Observe（结果及是否成功）三元组；②多 Agent 关联——使用 parent_trace_id 构建 Agent 调用树，支持 Orchestrator → Sub-Agent 的递归追踪；③可视化——使用泳道时间线展示并行活动（推理、工具调用、子 Agent），支持缩放和钻取详情；④异常标注——自动检测异常模式如"连续 3 步 observation 相同"（死循环）、"工具调用失败但继续推理"（错误忽略）；⑤对比分析——支持两个 trace 的 side-by-side 对比，用于分析模型升级或 prompt 变更的影响。

审计回放中如何进行事件根因分析？

LLM 事件根因分析的四步法：①收集证据——获取事件时间范围内的所有相关 traces（对话链、工具调用、系统日志）；②异常检测——将指标（延迟、token 消耗、错误率）与基线对比，标记偏离超过阈值的数据点；③关联分析——将异常指标与系统事件（部署、配置变更、模型版本切换、流量变化）进行时间维度关联，找出"异常出现前最近的变更"；④根因确认——在测试环境重放类似请求验证假设。LLM 特有的根因模式：幻觉通常关联 RAG 检索失败或上下文截断；安全绕过关联特定的输入模式（Prompt 注入）；Agent 循环关联工具持续返回相同错误；质量退化关联模型版本变更。

回放系统的时间线可视化应该包含哪些信息？如何设计？

时间线可视化采用"多泳道"设计，每条泳道代表一个活动维度：①用户交互泳道——用户消息发送和接收时间点；②RAG 检索泳道——检索查询、返回文档数量和相关性分数；③Agent 推理泳道——每步的 thought 内容和持续时间；④工具调用泳道——工具名、参数、结果、耗时，用颜色区分成功/失败；⑤LLM 调用泳道——模型名、token 数量、延迟。设计原则：支持时间轴缩放（从毫秒到分钟级），点击事件可钻取查看详情（完整 prompt、返回内容），支持搜索和过滤（如只看失败的工具调用），异常事件用红色高亮。前端实现可用 vis-timeline、react-chrono 等甘特图库。关键是让非技术人员（合规审计员）也能直观理解 AI 的决策过程。

完整记录 context_window 会带来多大存储压力，怎么在不牺牲回放能力的前提下压下来？

压力主要来自重复：多轮对话里，第 N 轮的上下文包含了前 N−1 轮的绝大部分内容，直接全量存会让存储量随轮数呈平方级增长。一个 10 轮、每轮 4K token 的会话，朴素存法约 200K token，而实际信息量只有 40K。三种压法可以叠加使用。第一种是内容寻址：把每条消息、每个检索片段按内容算哈希单独存一份，turn 只存哈希列表，重复内容天然去重，这一步通常能砍掉 70% 以上。第二种是增量记录：只存本轮相对上一轮的 diff（新增了哪些消息、淘汰了哪些消息、系统 prompt 是否变化），回放时沿链重建，代价是重建有计算开销且依赖链条完整。第三种是分级保留：完整上下文只在热层保留较短时间（例如 30 天，覆盖绝大多数投诉与排查），之后只保留哈希、消息条数、token 数和被截断标记，配合原文的加密归档按需取回。需要提醒的是不要用"只存最后一轮"来省空间，那等于放弃了回放能力；也不要用有损摘要替代原文，摘要无法作为证据。

回放系统本身应该受到什么访问控制？为什么它比普通日志查询更敏感？

因为回放把散落各处的碎片拼成了完整画面：一次回放同时呈现用户的原始输入、模型输出、检索到的内部文档、工具的返回数据。单看任何一条日志可能都不算高敏感，聚合起来却构成对某个具体用户在某段时间内活动的完整重建，这本身就是一种能力放大。因此控制要点有四个。一是按字段分级授权而非按表授权：运维排障只需要时间戳、延迟、token 数和状态码，不需要看正文；只有安全调查和合规取证才开放内容层。二是查询范围限制：禁止无条件全表扫描，要求查询必须带 session_id、trace_id 或明确的时间窗加业务标识，防止"批量拉取"变成一次内部数据导出。三是双人授权与工单绑定：查看内容层需要走审批并关联具体的调查工单，授权是有时效的，到期自动收回。四是对回放行为本身再记一层审计——谁在什么时候回放了哪个会话、看了哪些字段，这条元审计不能由回放系统的使用者自己管理，否则最后一道防线形同虚设。
