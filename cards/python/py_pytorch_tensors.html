张量的 API 和 NumPy 像到你几乎不用学，真正让你加班的是另外三件 NumPy 里不存在的东西：它在哪个设备上、它是不是在偷偷记录计算图、它是什么精度。绝大多数「跑不起来」和「显存莫名其妙涨」都能归到这三个问题之一。

一、张量比数组多了什么：三件事，不是一百件

会 NumPy 的人第一次写 PyTorch，通常半小时就能上手：索引、切片、广播、sum／mean／reshape 的语义几乎一一对应，连很多函数名都一样。这种相似性是 PyTorch 刻意设计的，好处是迁移成本极低，坏处是它会让你误以为「张量就是能跑在 GPU 上的数组」，于是把三个真正的差异当成细节忽略掉。

这三件事是：张量可以放在加速设备上（于是有了「它现在在哪」这个每行代码都要回答的问题）、张量可以记录自己是怎么算出来的（于是有了计算图，以及图带来的内存开销）、张量支持多种低精度格式并能自动混合使用（于是有了溢出、下溢和精度损失）。本卡讲的全部是这三件事在工程上的后果。

至于张量内部是怎么组织的——形状、步长、底层存储三者的关系，reshape 和 transpose 为什么不是一回事，什么叫内存连续、切片为什么会共享存储——那是另一个完整的话题，T01 张量核心 已经讲透了，本卡不重复。你可以把 T01 当成「张量作为数据结构」，把本卡当成「张量作为运行时对象」。

NumPy 的数组只回答一个问题：里面是什么数。PyTorch 的张量要回答四个：里面是什么数、什么精度、在哪台设备上、是不是正被 autograd 盯着。写代码时脑子里要同时挂着这四个。

二、设备是第一类错误来源

设备错误有两个特点，合起来让它成了新手最难受的一类问题。第一，它是硬错误：两个张量不在同一个设备上，运算直接抛异常，不会像广播那样悄悄给你一个错结果。第二，报错的位置离真正的原因很远——你在模型第 17 层的某个矩阵乘上收到报错，而根因是三个文件之外的数据加载函数里漏了一次搬运。

典型的报错长这样：RuntimeError: Expected all tensors to be on the same device，后面跟着实际发现的两个设备名。它告诉你「有东西没对齐」，但不告诉你是谁。

纪律：设备只在入口决定一次

唯一可靠的做法是把设备当成一个从程序入口注入、一路往下传的参数，而不是每个函数各自去猜。下面这种写法是反面教材：在工具函数内部判断有没有可用的加速器，然后自己决定搬到哪——单看没问题，但整个项目里散落十几处这样的判断时，只要有一处条件写得不一样，就会出现一半张量在一个设备、一半在另一个设备。

# 入口处决定一次，之后所有代码都只认这个变量
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = Model().to(device)          # nn.Module.to() 是原地的，返回的还是它自己
x = x.to(device)                    # Tensor.to() 返回新张量，必须接住！

最后两行的不对称是高频坑。nn.Module.to() 会就地把所有参数和缓冲区搬过去，写 model.to(device) 不接返回值也没事；而 Tensor.to() 遵循张量的不可变约定，返回一个新张量，你不接住就等于什么都没做。同理 .cuda()、.float()、.detach() 也都是返回新对象。

异步：你测到的时间可能是假的

往加速设备上发的运算不是同步执行的。Python 这边调用一次矩阵乘，实际发生的只是「把一个 kernel 排进设备的执行队列」，然后立刻返回；真正的计算在设备上排队进行。这种异步执行是性能的关键（主机可以一边排活一边准备下一批数据），但它会让任何朴素的计时代码得出荒谬的结果。

主机（Python 线程） 加速设备的执行队列 ───────────────────── ────────────────────── t0 = perf_counter() y = x @ x ──── 入队 ────► [ matmul kernel ] t1 = perf_counter() ▲ 才刚开始算 print(t1 - t0) → 0.28 ms │ ▲ │ └ 这是「把活派出去」的耗时 │ 不是「算完」的耗时 │ │ torch.cuda.synchronize() ──── 等待 ────┘ t2 = perf_counter() print(t2 - t0) → 41.6 ms ← 这才是真实耗时 规矩：计时区间的前后各同步一次，前面那次用来清掉上一段残留的队列
import time, torch
x = torch.randn(4096, 4096, device="cuda")

torch.cuda.synchronize()                       # 清掉之前排的活
t0 = time.perf_counter()
y = x @ x
torch.cuda.synchronize()                       # 等这次真的算完
print(f"{(time.perf_counter() - t0) * 1e3:.1f} ms")

异步还有第二个后果：设备端的错误也是异步报出来的。一个越界索引可能在你排下去好几个 kernel 之后才被发现，于是栈顶指向的是一行完全无辜的代码。调试这类问题时，把 CUDA_LAUNCH_BLOCKING=1 设进环境变量可以强制每次 kernel 发射都同步，报错位置就回到真正出事的那一行了——代价是全程变慢，所以只在排查时开。

示例场景：某团队把一段特征变换从循环改成批量矩阵乘，自测「从 42 ms 降到 0.3 ms，快了 140 倍」，兴冲冲上线，结果端到端吞吐一点没动。复盘发现计时代码里没有同步，0.3 ms 测的是 kernel 派发时间。补上 torch.cuda.synchronize() 重测，真实值是 41.6 ms → 39.8 ms，提升 4%。这不是「优化没用」，是测量方法错了，导致团队把三天时间花在了一个 4% 的点上。计时与基准的通用方法见 PY42 性能剖析与优化。

矩阵乘、卷积、逐元素运算不会只是把 kernel 排进队列就返回
t.to(device)（默认）会拷贝之后会等一次，确保拷贝完成
t.to(device, non_blocking=True)不会但只有源张量在固定内存里，这个异步才真正有意义

t.cpu() / t.numpy()会同上，跨设备取数据

搬运本身要花钱

主机内存和显存之间的拷贝走 PCIe 总线，带宽比显存内部低一到两个数量级。这意味着一个「在 GPU 上算得飞快」的算子，如果每次调用都要把数据搬上去再搬下来，整体反而可能比留在主机上更慢。判据很简单：数据上去之后要做的计算量，要能摊薄搬运的成本；否则就别搬。

要搬的时候，固定内存（page-locked memory，也叫锁页内存）能让拷贝更快。操作系统默认可以把普通内存页换出到磁盘，所以拷贝前驱动得先做一次额外的中转；固定内存承诺不被换出，驱动可以直接发起 DMA 传输。实践中不要自己在训练循环里调用固定内存转换——那个转换本身是阻塞的，得不偿失；正确做法是让数据加载器在它自己的线程里提前做好（构造时传 pin_memory=True），循环里只写 non_blocking=True 的搬运。

关于设备只要记两条：入口决定一次，之后所有函数都拿着同一个 device 变量；以及凡是要拿数字回来看（打印、.item()、算指标），你就已经在同步了，别放进热循环。

三、dtype 与精度的取舍

PyTorch 里浮点张量的默认类型是 float32。这个选择本身就是一次权衡：深度学习不需要 float64 那么高的精度，而少一半位宽意味着显存占用减半、内存带宽压力减半。既然减半一次有效，那减半两次呢——这就是低精度和混合精度要解决的问题。

先处理最常见的一个报错

NumPy 默认 float64，PyTorch 默认 float32。所以 torch.from_numpy(np.zeros(3)) 给你的是 float64 张量，把它喂进一个 float32 的线性层，会收到 RuntimeError: expected scalar type Float but found Double。这条报错每个写 PyTorch 的人都会遇到一次，处理办法是在数据进入模型之前就统一转成 float32，而不是在报错的那一层临时补一个转换——后者只是把问题推到下一层。

两种低精度格式的区别在指数位

浮点数的位分成三部分：符号位、指数位（决定数值范围）、尾数位（决定有效精度）。两种 16 位格式的分法完全不同，这一个区别决定了它们各自适合干什么。

float32 S EEEEEEEE MMMMMMMMMMMMMMMMMMMMMMM 1 8 23 范围 ~3.4e38 有效位 ~7 位十进制 float16 S EEEEE MMMMMMMMMM 1 5 10 范围 ~6.55e4 有效位 ~3 位十进制 └─ 指数位砍到 5 位：大数溢出成 inf，小数下溢成 0 这是 fp16 训练最容易炸的地方 bfloat16 S EEEEEEEE MMMMMMM 1 8 7 范围 ~3.4e38 有效位 ~2 位十进制 └─ 指数位和 float32 一模一样：范围完全不变，只是数值变「粗」 所以 bf16 几乎不会溢出，训练更稳 一句话：fp16 是「精细但装不下」，bf16 是「装得下但粗糙」。 训练怕的是装不下（一个 inf 会污染整张图），所以训练偏好 bf16。
格式符号/指数/尾数可表示的最大有限值有效十进制位典型用途

TF32 那一行值得单独说一句：它不是你能声明的张量类型，而是某些 NVIDIA 硬件在做 float32 矩阵乘时内部采用的降精度路径。它默认的开关状态在不同 PyTorch 版本之间变过，想显式控制可以用 torch.set_float32_matmul_precision()，传 "highest" 表示老老实实用完整 float32，传 "high" 允许走更快的降精度路径。如果你在排查「同样的代码在两台机器上数值对不上」，这是要查的第一个开关。

自动混合精度：让框架逐算子决定

全模型都换成低精度是行不通的：矩阵乘和卷积用低精度很安全（它们本来就在做大量累加，误差会平均掉），但求和、softmax、损失函数、归一化这类涉及大范围累加或指数运算的算子，低精度下误差会迅速放大。自动混合精度的思路就是不让你手工分类，而是由框架维护一张算子清单，在一个上下文块内自动为每个算子挑合适的精度。

接口是 torch.autocast（也可以写成 torch.amp.autocast），用作上下文管理器，只包住前向和损失计算，不要把反向也包进去——反向会自动沿用前向记录的精度。权重本身仍以 float32 保存，优化器更新也在 float32 上进行，所以「混合」指的是计算过程混合，不是参数存储混合。

scaler = torch.amp.GradScaler("cuda")            # fp16 训练需要；bf16 一般不需要
for x, y in loader:
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast("cuda", dtype=torch.float16):
        loss = loss_fn(model(x), y)              # 只包前向 + 损失
    scaler.scale(loss).backward()                # 放大后再回传
    scaler.step(optimizer)                       # 内部先还原真实梯度再更新
    scaler.update()                              # 根据有没有溢出调整缩放系数

为什么 fp16 需要梯度缩放

回到位宽那张图：float16 能表示的最小正规数量级在 1e-5 附近。训练后期的梯度里，有相当一部分元素比这个还小——它们在 float16 下会直接下溢成 0，对应的参数就再也更新不了了，表现为训练中后期精度停滞，而且不报任何错。

梯度缩放的做法很朴素：反向传播之前把损失乘上一个大系数（量级在几万），链式法则会让所有梯度同比例放大，于是原本要下溢的小梯度被抬进可表示区间；优化器更新之前再把梯度除回去。缩放系数是动态调整的——检测到溢出（出现 inf 或 NaN）就跳过这一步更新并把系数调小，连续若干步没溢出就把系数调大。bfloat16 的指数范围和 float32 一样，不存在这个下溢问题，所以通常不需要缩放器。

示例场景：一个 3.5 亿参数的模型改用 fp16 混合精度训练，显存从 38 GB 降到 22 GB，单步耗时从 480 ms 降到 290 ms，看起来很成功；但第 6 个 epoch 之后验证集指标卡死不动，训练损失也不再下降。排查发现代码里只加了 autocast，漏掉了梯度缩放器，抽样统计显示约 31% 的梯度元素已经下溢成 0。补上缩放器后训练恢复正常；后来干脆换成 bfloat16，把缩放器这一整块逻辑删掉，收敛曲线和 float32 基线几乎重合。

选精度的顺序：默认 float32 跑通基线 → 要提速先上 bfloat16 混合精度（硬件支持的话），因为它不需要额外的缩放逻辑 → 只有硬件不支持 bf16 时才退回 fp16，并且必须配梯度缩放。别一上来就调精度，先确认瓶颈真的在计算上。

四、梯度开关与显存：全卡最实用的一节

每个 requires_grad=True 的张量，以及任何由它参与运算得到的结果，都会被 autograd 记录进计算图。这个「传染性」是关键：你不需要手动声明要不要建图，只要输入里有一个张量开着梯度，输出就自动开着，整条链路全部被记录。模型参数默认就是开着的，所以只要你把数据喂进模型，图就建起来了。

图不是一个轻量的元数据结构。为了能算反向，它必须持有前向过程中产生的中间结果——每一层的激活值、每一个需要在反向里复用的张量。这些中间结果的总量通常和模型参数量同一个量级甚至更大，而且它们要一直活到 .backward() 执行完才会被释放。反向传播本身的原理见 N03 前向传播与反向传播，这里只关心它的内存后果。

结论直接得不能再直接：推理和评估时必须关掉梯度记录。不关掉，你白白多占了一份中间激活的显存，换来一堆永远不会被用到的反向信息。实测上这份开销常常能到总占用的三分之一以上。

五种「关梯度」的机制，别搞混

最后一行是新手最常混淆的点：model.eval() 一个梯度都没关，torch.no_grad() 一个 Dropout 都没关，两者正交，推理时两个都要。

inference_mode 是 no_grad 的加强版，默认优先选它；只有当你发现报错说「inference 张量不能用于 autograd 记录的运算」时，才退回 no_grad。这类报错的意思是：你在推理块里造出来的张量，后面又被送进了需要求导的流程（比如把评估结果当成某个正则项接回训练），这时候 inference_mode 的假设被打破了。上下文管理器本身的机制见 PY19 上下文管理器。

model.eval()                                   # 切 Dropout / BatchNorm 行为
total, n = 0.0, 0
with torch.inference_mode():                   # 不建图，也不做视图追踪
    for x, y in loader:
        x = x.to(device, non_blocking=True)
        loss = loss_fn(model(x), y.to(device))
        total += loss.item() * x.size(0)       # 取标量，别 append 张量
        n += x.size(0)
print(total / n)

显存杀手之一：把带图的张量攒进列表

这是本节的重点，也是生产环境最常见的显存泄漏形态。评估循环里想统计平均损失，很自然会写 losses.append(loss)——但 loss 是一个带着 grad_fn 的张量，它引用着产生它的那个运算节点，那个节点又引用着它的输入……一路回溯到这一批数据的全部中间激活。你以为攒的是一个数，实际攒的是一整条计算历史。

写成 losses.append(loss) 时，列表里到底攒了什么 ────────────────────────────────────────────── 第 1 批 x1 ──► 激活 a1 ──► 激活 b1 ──► loss1 ──┐ 第 2 批 x2 ──► 激活 a2 ──► 激活 b2 ──► loss2 ──┤ losses 列表 第 3 批 x3 ──► 激活 a3 ──► 激活 b3 ──► loss3 ──┤ 持有这三个引用 ▲ │ └── 每个 loss 的 grad_fn 反向引用着整条链上的中间激活， 所以这三整行东西一个字节都释放不掉， 批次越多占用越大，直到 OOM 写成 total += loss.item() 时 ────────────────────────────────────────────── 第 1 批 x1 ──► a1 ──► b1 ──► loss1 ──► 0.4213 （一个 Python float） └──────── 本轮结束即全部释放 ────────┘ 常驻内存：一个 float，8 字节，和批次数无关

正确写法有三种，按推荐程度排：最好是整个循环包在 inference_mode 里（根本就没建图）；其次是取标量 loss.item()；如果确实需要保留张量（比如要拼起来算 AUC），那就 loss.detach() 之后再存，必要时顺手 .cpu() 挪回主机内存。

生产事故复盘：一个模型打分服务上线后，显存从启动时的 6.2 GB 开始缓慢但稳定地增长，每处理约 1000 批（每批 32 条）涨 480 MB；线上流量约 1800 批／小时，折算下来每小时涨 0.86 GB。上线当天夜里约 19 小时后，24 GB 的卡被占满，进程以 CUDA out of memory 崩溃，此后每天固定崩一次，运维只能配一个定时重启凑合。
排查绕了很多弯路：先怀疑显存碎片，加了缓存清理没用；再怀疑批大小不稳定，做了限流也没用。最后用峰值显存统计逐段打点，定位到评估循环里的一行 batch_losses.append(loss)——这是从训练脚本复制过来的代码，在训练里因为每步都 backward() 释放了图所以不显形，搬到只前向的推理服务里就变成了纯泄漏。
修复只改了两处：把 append(loss) 换成 += loss.item()，并把整个循环包进 torch.inference_mode()。修复后稳定占用 6.4 GB，连续运行 7 天峰值 6.6 GB，无增长趋势；顺带因为不再建图，P99 延迟从 182 ms 降到 141 ms。

显存杀手之二：循环里不放手上一轮的引用

Python 的对象生命周期由引用计数决定（见 PY23 内存模型与 GC），显存也一样：只要还有一个 Python 名字指着某个张量，它占的那块显存就不会还给分配器。循环里最隐蔽的一处是循环变量本身——一轮结束时 x、output、loss 这些名字仍然指着上一轮的张量，于是在下一轮的峰值时刻，显存里同时存在两轮的数据。

在显存本来就贴着上限跑的场景里，这多出来的一份足以触发 OOM。处理办法是在循环末尾显式 del 掉大张量的名字。注意这只是把引用放掉，让分配器可以复用那块显存；它不等于把显存还给驱动，所以 nvidia-smi 上的数字不会立刻变小——那是 PyTorch 的缓存分配器故意留着复用的。

显存排查的第一性问题永远是「谁还拿着引用」。看到显存单调增长，先去找两种东西：跨批次存活的容器（列表、字典、日志缓冲），以及没被关掉的计算图。这两类合起来能覆盖绝大多数「推理服务越跑越胖」。

五、与 NumPy 互操作：什么时候共享，什么时候复制

PyTorch 和 NumPy 之间的转换设计得很激进：默认尽量共享同一块内存，而不是复制。这是为了性能——数据管道里动辄几百 MB 的数组，每次转换都复制一遍是不可接受的。但共享意味着改一个会影响另一个，如果你不知道这件事，就会遇到「我明明没动张量，它的值怎么变了」。

共享的是底层那块字节缓冲区，两边各自有一层外壳 ───────────────────────────────────────────────── NumPy ndarray PyTorch Tensor ┌──────────────┐ ┌──────────────┐ │ shape/stride │ │ shape/stride │ │ dtype │ │ dtype/device │ └───────┬──────┘ └──────┬───────┘ │ │ └──────────┬───────────────┘ ▼ ┌──────────────────────┐ │ 同一块主机内存缓冲区 │ ← 谁写都算数 └──────────────────────┘ a = np.zeros(3); t = torch.from_numpy(a) t[0] = 7 → a 变成 [7. 0. 0.] （没有复制过） 想要独立副本：torch.tensor(a) 或 t.clone()

什么情况下一定会复制

共享内存的前提是「两边能用同一块字节看待同一批数字」。只要有一个条件不成立，就必须复制一份：设备不同（数据在显存里，NumPy 根本读不到，必须先搬回主机）、dtype 不同（float64 转 float32 位宽都变了，不可能原地）、内存布局不允许（比如需要连续布局但当前张量是某个转置的视图，得先物化成连续的一份）。连续性与视图的机制在 T01 张量核心 里有完整推导；共享与复制这一对概念在纯 Python 层面的对应物见 PY10 拷贝语义。

取值：三个写法，三个前提

从张量里把数字拿出来有三种常用写法，各自有硬前提，搞错了就报错：

  • t.item()——取单个标量，返回 Python 的 float 或 int。前提是张量里只有一个元素。它会触发一次设备同步，所以别在热循环里每步都调。
  • t.tolist()——转成嵌套的 Python 列表，一定复制，适合小张量。
  • t.numpy()——转成共享内存的 NumPy 数组。两个前提：张量必须在主机内存上，且必须先脱离计算图，否则会收到「不能对 requires grad 的张量调用 numpy」的报错。

最后那条报错的正确处理不是「加个 try」，而是想清楚这个张量为什么还带着梯度——通常说明你忘了包 inference_mode。真的需要时，标准写法是 t.detach().cpu().numpy()，顺序不能反（要先脱图再搬回主机，反过来会先搬一份带图的数据）。如果嫌每次判断条件麻烦，t.numpy(force=True) 会自动把脱图、搬回主机这些步骤都做掉，代价是你放弃了对「有没有复制」的控制权。

我想做什么该怎么写会不会复制
拿 NumPy 数组建张量，并希望共享内存torch.from_numpy(a)不复制（仅限主机内存，dtype 直接映射）
拿 NumPy 数组建张量，要一份独立副本torch.tensor(a)一定复制
主机上的普通张量转数组t.numpy()不复制
带梯度的主机张量转数组t.detach().numpy()不复制（detach 只换外壳）
加速设备上的张量转数组t.detach().cpu().numpy()复制一次（跨设备必然复制）
只要一个数（损失、准确率）t.item()复制，且触发一次设备同步
不想逐条判断上面这些前提t.numpy(force=True)按需复制，由框架决定

示例场景：一个特征预处理流程里，某人为了「省一次拷贝」把 torch.tensor(arr) 改成了 torch.from_numpy(arr)，同时下游有一段做就地操作的归一化代码（t.sub_(mean).div_(std)）。结果是原始的 NumPy 数组被就地改写了，而同一个数组还被另一条分支用来算统计量——于是统计量变成了归一化之后的数据，训练集和验证集的分布对不上。这个 bug 藏了 11 天才被发现，症状是验证指标异常地好。教训：只要下游可能有就地操作，就不要用共享内存的转换，那点拷贝开销远比排查这种 bug 便宜。

判断有没有复制，只要问一句：「转换前后，这批数字在内存里的字节能不能一模一样地复用？」设备变了、dtype 变了、布局要求变了，任何一条成立就一定有复制；三条都不变，PyTorch 默认就不复制。

六、可复现与排查纪律

「我跑了两遍，结果不一样」在深度学习里太常见，以至于很多人默认接受了它。但不可复现会让所有对比实验失去意义——你分不清指标涨了 0.4 个点是因为你的改动，还是因为这次随机种子运气好。真正该做的是搞清楚随机性来自哪里，然后决定固定到什么程度。

随机性有四到五个独立来源

只设 torch.manual_seed() 是不够的，这是最常见的误解。一个典型训练脚本里，随机数至少来自四个互不相干的生成器：PyTorch 自己（参数初始化、Dropout、数据打乱）、NumPy（大量数据增强库在用）、Python 标准库的 random（各种采样逻辑）、以及加速设备上的非确定性算法——后者不是随机数问题，而是浮点加法不满足结合律，并行归约的求和顺序每次不同，结果就有末位差异。

随机性来源固定方式代价
PyTorch：初始化、Dropout、打乱torch.manual_seed(s)（同时覆盖 CPU 与所有 CUDA 设备）无
NumPy：数据增强、采样numpy.random.seed(s)，或改用独立的随机数生成器对象无
Python 标准库 randomrandom.seed(s)无
数据加载的多个工作进程给加载器传入固定的生成器，并用 worker 初始化钩子给每个进程播种无
cuDNN 卷积算法自动选优torch.backends.cudnn.benchmark = False卷积可能变慢，尤其是输入尺寸固定时
非确定性算子（散射写入、部分反向）torch.use_deterministic_algorithms(True)部分算子会变慢；没有确定性实现的算子会直接报错
cuBLAS 的工作区复用进程启动前设环境变量 CUBLAS_WORKSPACE_CONFIG=:4096:8略增显存占用
import random, numpy as np, torch

def seed_all(s: int = 1234) -> None:
    random.seed(s)
    np.random.seed(s)
    torch.manual_seed(s)                       # CPU 和所有 CUDA 设备一起播种
    torch.backends.cudnn.benchmark = False
    torch.use_deterministic_algorithms(True)   # 严格模式，慢但可复现

注意最后一行的环境变量要求：use_deterministic_algorithms(True) 打开后，某些 cuBLAS 操作还要求 CUBLAS_WORKSPACE_CONFIG 在进程启动前就设好，在 Python 里 os.environ 改是来不及的。实践上的建议是：日常开发只做前三行播种，接受末位差异；只有在定位「两次结果不一致到底是不是我改坏了」这类问题时，才临时打开完整的确定性模式。确定性算法的性能代价在卷积密集的模型上可以到两位数百分比。

三步排查：形状、设备、dtype

PyTorch 报错的栈顶经常指向框架内部的某个算子实现，看上去和你的代码没关系。不要从栈顶往下读，按下面这个固定顺序核对三件事，绝大多数报错在第二步之前就解决了。

收到报错先别读栈，按顺序核对这三件事 ────────────────────────────────────────────────────── 1) 形状 shape print(tuple(t.shape)) │ 对不上 ⇒ 批维丢了 / 忘了转置 / 广播成了意料外的形状 │ 典型报错：mat1 and mat2 shapes cannot be multiplied ▼ 2) 设备 device print(t.device) │ 对不上 ⇒ 某个张量漏了 .to(device)，常见于新加的常量 │ 典型报错：Expected all tensors to be on the same device ▼ 3) 类型 dtype print(t.dtype) 对不上 ⇒ NumPy 的 float64 混进来了，或低精度块外泄 典型报错：expected scalar type Float but found Double 万能一行自查，插在报错行前面： print(tuple(t.shape), t.device, t.dtype, t.requires_grad)

这个顺序不是随便排的：形状错最常见也最容易看出来；设备错第二常见，而且报错信息离现场最远；dtype 错相对少，但一旦出现往往牵扯到上游的数据管道。第四项 requires_grad 不在排查链里，但值得顺手打出来——它能立刻告诉你「这段代码到底有没有在建图」，对第四节讲的那类显存问题是最快的判据。

  • 入口处定义一次 device，作为参数一路传下去，不在函数内部各自判断
  • 推理和评估同时用 model.eval() 和 torch.inference_mode()，两个都不能少
  • 统计指标一律 += loss.item()，需要存张量时先 .detach()
  • 计时前后各调一次同步，否则测出来的是派发时间
  • 数据进模型前统一转成 float32，别等报错了再在中间层补转换
  • 低精度优先选 bfloat16；用 float16 训练必须配梯度缩放器
  • 数据加载器开 pin_memory=True，搬运时写 non_blocking=True
  • 报错先按形状 → 设备 → dtype 三步核对，再去读调用栈
  • 写 x.to(device) 不接返回值（张量的 to 不是原地的，模块的才是）
  • 在评估循环里 append 一个带 grad_fn 的张量——整条计算历史都会被留住
  • 把 model.eval() 当成「关梯度」，或把 no_grad() 当成「关 Dropout」
  • 在热循环里 print(tensor) 或频繁 .item()，每次都是一次强制同步
  • 用 torch.from_numpy 共享内存之后，下游还做就地操作
  • 把整个训练步（含反向）都包进 autocast 块里
  • 只设 torch.manual_seed 就宣称「实验可复现」
  • 为了让 nvidia-smi 数字好看，在循环里反复调用清空缓存的接口

这一卡的全部内容压成一句话：张量比数组多了设备、梯度、精度三个状态位，而工程上 90% 的事故就是这三个状态位在某处悄悄变了而你没发现。养成随手打印这三样的习惯，比记住任何 API 都管用。

Q&A

为什么 model.to(device) 不用接返回值，而 x.to(device) 必须接？
因为它们是两个不同的方法，语义有意做得不同。nn.Module.to() 遍历模块的所有参数和缓冲区，就地把它们替换成目标设备上的版本，然后返回模块自身（返回值只是方便链式调用）。Tensor.to() 遵循的是张量「不可变外壳」的约定：它返回一个新的张量对象，原张量一点没变，所以 x.to(device) 单独写一行等于什么都没做。同一组规则适用于 .cpu()、.cuda()、.float()、.detach()、.contiguous() 这些方法——它们全都返回新对象。一个有用的记忆法：PyTorch 里真正就地修改张量的方法都带下划线后缀（add_、copy_、clamp_），没有下划线的一律返回新对象。另外注意优化器：如果你在构造优化器之后才把模型搬到别的设备，优化器里存的还是旧参数的引用，更新会作用不到实际参数上，所以顺序永远是先 to(device) 再建优化器。
model.eval() 和 torch.no_grad() 到底哪个才是「关梯度」？
只有 torch.no_grad()（以及更彻底的 torch.inference_mode()）关梯度，model.eval() 和梯度毫无关系。model.eval() 做的是切换模块的行为模式：让 Dropout 停止随机丢弃、让 BatchNorm 改用训练期积累的滑动均值方差而不是当前批次的统计量。这两件事是正交的，所以推理时两个都要。只调 eval() 不关梯度，后果是白白多占一份中间激活的显存，实测常常是三成以上；只关梯度不调 eval()，后果更严重——Dropout 还在随机丢神经元、BatchNorm 还在用当前批的统计量，输出会随批次组成而变化，小批量推理时结果可能明显偏差，而且这个错误不会报任何异常，只表现为「线上效果比离线评估差一截」。顺带一提，inference_mode 的官方文档专门写了一条提醒：它不会自动帮你设 eval()。
inference_mode 和 no_grad 该选哪个？
默认选 inference_mode，遇到报错再退回 no_grad。inference_mode 在「不记录计算图」这件事上和 no_grad 一样，额外还关掉了视图追踪和版本计数器的维护——这两项是 autograd 用来检测「你是不是就地改了一个反向要用的张量」的机制，推理时纯属浪费，关掉能省一点每算子的固定开销。代价是它更严格：在这个块里创建出来的张量被标记为「推理张量」，退出块之后不能再参与任何会被 autograd 记录的运算，也不能给它设 requires_grad=True，否则会抛运行时错误。什么时候会撞上这个限制？典型是把评估结果接回训练流程，比如用推理块算出一个伪标签或正则项，然后拿去做反向。这种情况下换成 no_grad 就好。实践建议：推理服务、离线打分、数据预处理这类完全自足的场景用 inference_mode；训练脚本内部的评估环节如果结果要回流，用 no_grad 更省心。
循环里每步都调 loss.item() 会不会拖慢训练？
会，但通常可以接受，关键看调用频率和位置。.item() 要把一个数值从设备读回主机，这意味着主机必须等设备把队列里的活全部干完，也就是一次完整的同步。在正常的训练循环里每步调一次，同步点正好落在这一步本来也要等的地方，额外开销很小。真正会出问题的是两种写法：一是在一个批次内部的小循环里（比如逐层、逐样本）调用，那就是把异步流水线彻底打断了；二是在做性能剖析时，每步都 print(loss.item())，得到的耗时分布会因为同步点的存在而完全失真。规避办法是把标量累加也放在设备上做（用一个设备上的张量累加），只在整个 epoch 结束时取一次值；或者退一步，每 N 步才记录一次。顺带说，print(tensor)、float(tensor)、tensor.tolist()、任何 if tensor > 0 形式的条件判断，都会触发同样的同步。
fp16 训练损失变成 NaN，换成 bfloat16 就能解决吗？
大概率能，但先搞清楚是哪种 NaN。fp16 的指数位只有 5 位，能表示的最大有限值是 65504，最小正规数量级在 1e-5 附近，两头都很窄。溢出（数值超过 65504 变成 inf，再参与减法就产生 NaN）通常出现在注意力分数、大范围求和、损失值本身这些地方；下溢（小梯度变成 0）不会报 NaN，但会让训练悄悄停滞。bfloat16 的指数位和 float32 完全一样，表示范围到 3e38，所以溢出型 NaN 基本消失，这也是现在训练普遍偏好 bf16 的核心原因。但要注意两点：第一，bf16 的尾数只有 7 位，有效精度比 fp16 还低，如果你的问题对精度敏感（某些数值求解、极小学习率下的累加），换过去可能出现收敛变慢，通常靠把损失累加和优化器状态保持在 float32 来缓解——混合精度本来就是这么设计的。第二，bf16 需要硬件支持，较老的加速卡上要么不支持要么是软件模拟，性能反而更差。如果只能用 fp16，那就老老实实配上梯度缩放器，它会在检测到溢出时自动跳过那一步更新。
为什么我的推理服务显存一直涨？清空缓存的接口不管用吗？
先明确一点：清空缓存的接口（torch.cuda.empty_cache()）几乎从来不是解决办法。PyTorch 用的是缓存式显存分配器，释放掉的张量占的显存会留在分配器手里等待复用，所以 nvidia-smi 显示的数字本来就高于实际在用的量——这不是泄漏。清空缓存只是把这些空闲块还给驱动，让那个数字变好看，代价是下次分配要重新向驱动申请，更慢；如果显存真的被活着的张量占着，它一个字节也帮不上。真正的泄漏只有一种成因：还有 Python 引用指着那些张量。按这个顺序查：一是有没有把带 grad_fn 的张量攒进列表、字典或日志缓冲（这是本卡第四节那个事故的形态，最常见）；二是有没有在类的属性里缓存了上一次的输出；三是异常处理里捕获的异常对象带着 traceback，而 traceback 会引用栈帧、栈帧又引用局部变量里的张量，导致整批数据活得比预期长。定位工具用峰值显存统计（先重置峰值再跑一段，看增量落在哪一段），比通读代码快得多。引用与生命周期的一般规律见 PY23。
t.numpy() 报「不能对 requires grad 的张量调用」，加 detach 就行了吗？
语法上行，但先想一想为什么它还带着梯度。这条报错的设计意图是拦你一下：NumPy 数组和张量共享同一块内存，如果允许你直接把一个在计算图里的张量转成数组，你就可以绕过 autograd 的监控去就地修改它，导致反向传播算出错误的梯度而不报任何错。所以 PyTorch 强制你显式写 .detach() 表示「我知道我在做什么」。回到实际场景：如果这是在评估或推理代码里，出现这条报错通常说明你整段都没关梯度记录，正确的修法是把循环包进 torch.inference_mode()，而不是在转换那一行补个 detach——后者只治了症状，那份白白建出来的计算图还在占显存。如果确实是在训练流程中间要把某个中间结果导出去看，那 t.detach().cpu().numpy() 就是标准写法，顺序不能颠倒：先脱图再搬回主机，反过来会先把带图的张量整个搬一遍。另外记住 detach() 返回的张量和原张量共享存储，对它做就地操作会污染原数据，需要独立副本时要再 .clone()。
