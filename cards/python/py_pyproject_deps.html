声明文件回答的是「这个项目能接受哪些版本」，不是「这次装了哪些版本」。把这两个问题分开，pyproject.toml 里大部分让人纠结的写法选择就只剩一个判据：你在写库，还是在写应用。

一、一个文件取代一堆文件

翻开一个 2018 年的 Python 仓库，根目录大概长这样：setup.py、setup.cfg、MANIFEST.in、requirements.txt、requirements-dev.txt、.flake8、pytest.ini、mypy.ini、tox.ini。九个文件，九套语法，其中有三四个在重复声明同一件事，而且互相不知道对方的存在。

这种散落不是谁偷懒造成的，而是缺一个约定位置的必然结果。每个工具出现时都得自己决定配置放哪，于是就各选了一个。真正让这件事变成死结的，是 setup.py 自身的一个循环依赖：它是一段要用 setuptools 才能执行的 Python 脚本，而「本项目需要 setuptools」这句话恰恰只能写在这段脚本里——你得先有它，才能读到「你需要它」。构建工具因此只能靠一条不成文的假设活着：setuptools 一定已经装好了，并且版本一定够新。

两个 PEP 各解决一半

PEP 518（2016 年提出，状态 Final）为了打破这个循环，引入了 pyproject.toml 这个文件本身，以及 [build-system] 表区里的 requires 字段——构建开始之前，前端先读这一行，把列出的工具装进一个隔离的构建环境，再去执行构建。顺带地，它还把 [tool] 表区划给了所有工具当公共宿舍，明确写着「不在本 PEP 里指定的表区留给未来的 PEP」。

PEP 621（2020 年提出，状态 Final）解决的是另一半：项目元数据。包名、版本、作者、依赖这些东西每个构建后端都能表达，但拼法各不相同，换一个后端就要把元数据重抄一遍。PEP 621 把它们统一进 [project] 表区，从此这部分是标准，不再属于某个工具。

数据截止 2026-06 · 本卡引用的 PEP 518 / 621 / 660 / 735 在 peps.python.org 上状态均为 Final；字段名以 packaging.python.org 的 pyproject.toml 规范页为准。

以前（每个工具自带一个文件） 现在（一个文件，三个表区） ───────────────────────────── ───────────────────────────── setup.py 构建脚本 + 元数据 pyproject.toml setup.cfg 元数据的声明式写法 │ MANIFEST.in 打包时带哪些附加文件 ├─ [build-system] 用什么构建 requirements.txt 运行时依赖 │ requirements-dev.txt 开发依赖 ├─ [project] 我是谁、要什么 .flake8 / pytest.ini 工具配置 │ └─ [project.scripts] 等子表 mypy.ini / tox.ini 工具配置 │ └─ [tool.ruff] 各工具自留地 九个文件、九套语法 [tool.mypy] 三四处重复声明同一件事 [tool.pytest.ini_options] 彼此不知道对方存在 [tool.uv] ＋ [dependency-groups] 开发依赖（顶层表）

注意最后一行：依赖组 是顶层表区，不在 [project] 里面。这个位置不是随手放的，第四节会讲原因。

最右一列值得多看一眼：只有前八行是标准。最后一行的 [tool.*] 里写什么，标准一个字都没规定，全由各工具自己定。这个区别决定了第二节的全部内容。

pyproject.toml 不是「又一个配置文件」，它是第一个约定了位置的配置文件。价值不在格式好看，在于任何工具都知道该去哪读、该往哪写。

二、三个表区的分工：两个是标准，一个是自留地

一个 pyproject.toml 里只有三个顶层表区是「大家都认」的：[build-system]、[project]、[tool]（PEP 735 之后又多了一个 [dependency-groups]）。把这三者的分工搞清楚，你就能预判任何一次工具迁移要改多少东西。

pyproject.toml │ ├─ [build-system] 定义方：PEP 517 / 518 │ requires = [...] 读它的人：pip、uv 这类安装前端 │ build-backend = "..." 作用时机：构建 wheel / sdist 之前 │ → 决定「用什么把源码变成包」 │ ├─ [project] 定义方：PEP 621 │ name / version 读它的人：构建后端 → 写进包的 METADATA │ dependencies 作用时机：构建时固化，安装时被解析器读 │ [project.scripts] ... → 决定「这个包对外长什么样、要什么」 │ ├─ [tool.ruff] 定义方：各工具自己，标准不管 │ [tool.mypy] 读它的人：只有那一个工具 │ [tool.uv] 作用时机：本地跑那个工具的时候 │ → 决定「我们这个仓库怎么开发」，不会进入发布包 │ └─ [dependency-groups] 定义方：PEP 735（顶层，不在 [project] 下） dev / lint / test 明确规定：不得写进发布包的元数据

前两个表区描述的是「这个项目是什么、怎么把它构建出来」，它们的内容最终会固化进发布产物的元数据文件（sdist 里的 PKG-INFO、wheel 里的 METADATA），被所有下游看到。第三个表区描述的是「我们这个仓库怎么干活」，它只在你本地和 CI 里有意义，永远不会被别人读到。

这个划分的实际后果：换工具只动 [tool.*]

因为 [project] 是标准，从 setuptools 换到 hatchling、再换到 uv 的构建后端，这一整段元数据一个字都不用改——你只需要改 [build-system] 那两行。同理，从 black + flake8 换到 ruff，删掉 [tool.black] 和 [tool.flake8]、加上 [tool.ruff] 就完事，项目元数据和依赖声明毫发无伤。构建后端 与工具链的可替换性，正是标准化换来的东西。

反过来说，这也解释了一个常见的困惑：为什么 [tool.ruff] 里的配置项，在任何 PEP 里都查不到？因为它本来就不归 PEP 管，要查只能去 ruff 自己的文档。类型检查与 lint 工具的配置细节归 PY20（类型注解与静态检查）那张卡，本卡只管「它该放在哪个表区」。

表区由谁定义谁会读它会进入发布包元数据吗换工具时要改吗
[build-system]PEP 517 / 518安装前端（pip、uv）不会（它只指导构建过程）换构建后端时改，两行
[project]PEP 621构建后端 → 下游解析器会，这是它存在的目的基本不用改
[tool.*]各工具自己只有对应那个工具不会换哪个工具改哪一段
[dependency-groups]PEP 735安装器 / 任务运行器不会（规范明确禁止）不用改

一个最小可用的骨架

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "order-sync"
version = "0.3.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27", "pydantic>=2.6,<3"]

八行有效内容，一个能被任何标准工具构建、安装、解析的包就成立了。name 是唯一不能被标记为动态的字段；version 虽然必填，但很常见的做法是写 dynamic = ["version"]，让构建后端从代码里的 __version__ 或 Git 标签取值。这里的「包」指的是可分发的软件包，和 import 语句里那个「包」不是一回事，两者的区别见 PY08（模块与包）。

[build-system] 和 [project] 是你对外签的合同，[tool.*] 是你家里怎么摆家具。改家具不需要通知任何人，改合同要考虑所有下游。

三、版本约束怎么写：先回答「我在写库还是写应用」

依赖声明的语法来自 PEP 508（依赖说明符）和 PEP 440（版本说明符），一条完整的依赖长这样：包名[extra]约束; 环境标记。大部分人真正需要决策的只有中间那段约束，而这段约束写成什么样，取决于一个几乎从不被明说的前提：你的项目在依赖图里是根节点，还是中间节点。

各种写法到底意味着什么

其中最容易被写错的是 兼容性约束 ~=，它的含义随小数点个数变化：~=2.6 等价于「>= 2.6 且 < 3.0」，~=2.6.1 等价于「>= 2.6.1 且 < 2.7.0」。少写一段就从「允许整个 2.x」变成「只允许 2.6.x」，差了一个数量级。规范还规定它不能用在单段版本号上，~=2 是非法的。

写法含义主要风险库应用
httpx任意版本上游任何一次发布都可能把你打挂只在依赖极稳定时可接受可接受（有锁文件兜底）
httpx>=0.27只给下限未来的不兼容大版本会被装进来常见做法常见做法
httpx>=0.27,<1下限加上限上限设得过早会制造无谓的解析冲突有证据时推荐推荐
httpx~=0.27等价于 >=0.27,<1.0同上，且写法不够直白可用可用
httpx~=0.27.2等价于 >=0.27.2,<0.28.0锁得过紧，连小版本修复都进不来不推荐少见
httpx==0.27.2精确到一个版本下游几乎必然与别人冲突不要这样写可以，但该由锁文件承担
httpx===0.27.2任意相等（按字符串比对）绕过全部版本语义避免避免

库和应用的区别是什么

库会被装进别人的环境，和别人的其它几十个依赖共处一个解析空间。你写下的每一条约束都是对所有下游的强制命令：你写 httpx==0.27.2，任何一个已经在用 httpx 0.28 的项目就装不了你的包，而且报错信息里不会写「怪 order-sync」，只会甩出一大段解析失败。约束越窄，你的包越难被采用。

应用是依赖图的根，没有下游，没人需要和你协商。它的核心诉求不是兼容性而是可复现：同一次提交，今天装和三个月后装要得到完全一样的结果。这件事由锁文件负责，声明文件因此可以写得相当宽松——反正每次实际装什么，读的是锁文件。锁文件是下一张卡的主题。

声明文件说的是「可接受的版本集合」，锁文件说的是「这次选中的那一个」 ─────────────────────────────────────────────────────────────────── pyproject.toml 解析器 锁文件 httpx >=0.27 ───────► httpx 0.27.2 pydantic >=2.6,<3 在集合里挑 pydantic 2.9.1 一组自洽的 ├ annotated-types 0.7.0 ← 传递依赖 具体版本 ├ pydantic-core 2.23.3 ← 传递依赖 └ typing-extensions 4.12.2 ← 传递依赖 httpcore 1.0.5 ← 传递依赖 h11 0.14.0 ← 传递依赖 certifi 2024.8.30 ← 传递依赖 常见误解：「我把 pyproject.toml 里全改成 == 精确版本就可复现了」 实际上你只钉住了左边那两行，右边六行传递依赖照样每天都在变。 真正做到可复现的，是把右边整张图连同哈希一起写下来 —— 那是锁文件的活。

上图那句误解值得单独说透。在声明文件里写死全部精确版本，付出的是「下游无法与你共存」的全部代价，换回的却只是直接依赖的确定性；传递依赖 依然完全自由，而线上事故绝大多数出在传递依赖上。这是一笔非常糟糕的交易：代价给满了，收益只拿到一小半。

那么库到底要不要写上限

社区在这件事上长期有分歧，因为两头都有真实代价：不写上限，上游发大版本时你被动挨打；无脑给每个依赖都写 <next-major，你会把整个生态的解析空间切碎，下游很快就撞上「A 要求 X<3，B 要求 X>=3」的死局，而且你每次都得跟着上游发版才能解锁。

可操作的折中是按耦合深度分类：对那些 API 面很大、你深度使用其内部概念的依赖（数据校验库、ORM、数值计算库这类），写上限；对那些你只调了两三个函数的工具型小依赖，只写下限。判据是问自己一句——「如果它明天发 3.0 并改掉一半 API，我的代码需要改吗？」需要，就写上限。

生产事故复盘：某团队维护的内部 SDK order-client（约 40 个下游服务在用）在 dependencies 里写的是 pydantic>=1.8，没有上限，因为「上游一直很稳」。上游发布 2.0 大版本当天（校验 API 与 BaseModel 行为均不兼容），13:51 新版本上架，14:02 收到第一条 CI 告警。最终统计受影响下游服务 17 个：其中 6 个自己钉了 pydantic<2，与 SDK 拉起来的 2.0 冲突，在安装阶段解析失败；另外 11 个顺利装上 2.0，启动时直接 ImportError。14:40 定位到根因，15:10 下发应急步骤（在各服务的锁文件里把 pydantic 回钉到 1.x），17:05 全部恢复，故障时长 3 小时 03 分。事后回看最刺眼的一点是：SDK 自己的代码一行都没改过，被打挂的原因完全来自一个自己不控制的外部发布时刻。最终修复是发 1.4.3 补丁版，把约束改成 pydantic>=1.8,<3 并补上兼容层，pyproject.toml 的 diff 是 1 行。pydantic 与标准库数据类的取舍见 PY21（数据类三选一）。

写库时每加一条约束，先想「这会不会让某个下游装不上我」；写应用时每加一条约束，先想「锁文件不是已经替我做了吗」。两种项目的默认答案正好相反。

四、依赖分组：运行时、可选、开发，三种语义

「pytest 该写在哪」是新项目最常问也最常写错的问题。要答对它，得先看清三类依赖回答的是三个不同的问题，而不是「重要程度」的三个档次。

它们各自回答什么问题

运行时依赖（[project] 的 dependencies）回答的是「装了这个包之后，它要能跑起来还缺什么」。没得选，安装器一定会把它们一起装上。

可选依赖（[project.optional-dependencies]，也就是 extras）回答的是「你要我这个包的哪一部分能力」。它的受众是安装方：别人写 pip install order-client[postgres]，就是在拨一个功能开关。关键性质是——它会随包发布出去，会出现在包的元数据里、显示在索引页面上，任何人都能选。

开发依赖（[dependency-groups]）回答的是「你要在这个仓库里干哪件活」。它的受众是仓库里的人：跑测试、跑 lint、构建文档。它只服务本仓库，不该被任何下游看到。

你的仓库 发布出去的 wheel ┌──────────────────────────────────────┐ ┌────────────────────────┐ │ [project] dependencies │ ───► │ METADATA: │ │ httpx, pydantic │ │ Requires-Dist: httpx │ ├──────────────────────────────────────┤ │ Requires-Dist: ... │ │ [project.optional-dependencies] │ ───► │ Provides-Extra: │ │ postgres = ["asyncpg"] │ │ postgres │ │ → 别人 pip install pkg[postgres] │ │ Requires-Dist: │ ├──────────────────────────────────────┤ │ asyncpg; extra == │ │ [dependency-groups] │ ╳ │ "postgres" │ │ dev = ["pytest", "ruff"] │ 止步 │ │ │ docs = ["sphinx"] │ 于此 │ （这里不会有任何 │ │ → 只给在本仓库干活的人用 │ │ dev / docs 的痕迹） │ └──────────────────────────────────────┘ └────────────────────────┘ PEP 735 规定：构建后端不得把依赖组写进 PKG-INFO / METADATA

为什么 PEP 735 要单开一个顶层表区

在 PEP 735（2023 年提出，2024 年 10 月获批，状态 Final）之前，「不发布的依赖」没有标准位置，社区的通行做法是借用 extras：定义一个 dev extra 把 pytest、ruff 塞进去。这是语义错位，代价有三层——它会出现在你的公开元数据里；任何用户都能装它；最麻烦的是，[project.optional-dependencies] 属于 [project]，而 [project] 强制要求 name 和 version，这等于逼着每一个纯应用仓库把自己伪装成一个可发布的包。

PEP 735 的规范文档里明确讨论过「为什么不叫 [project.dependency-groups]」，给出的正是这个理由。所以 [dependency-groups] 被放在顶层：一个只有 [dependency-groups]、连 [project] 都没有的 pyproject.toml 是完全合法的。对「不打算发布成包、只想管住一组依赖」的仓库来说，这是第一次有了名正言顺的写法。

[dependency-groups]
test = ["pytest>=8", "pytest-asyncio"]
lint = ["ruff>=0.6", "mypy>=1.11"]
dev  = [{include-group = "test"}, {include-group = "lint"}]

[project.optional-dependencies]
postgres = ["asyncpg>=0.29"]
redis    = ["redis>=5.0"]
all      = ["order-client[postgres,redis]"]

两个细节。{include-group = "..."} 是 PEP 735 定义的组嵌套写法，让 dev 成为其它组的并集，不用手抄一遍。而 all 那行用的是「extra 引用自身其它 extra」的写法，同样是为了避免手抄——手抄出来的聚合 extra 几年之后必然和被聚合的内容对不上，这是官方文档专门点名的陷阱。

还有一条容易忽略的规定：依赖组不会隐式安装项目本身。装了 test 组只是把 pytest 装进来，要测你的代码还得另外把项目自己装上（通常是可编辑安装，见下一节）。

uv 里怎么用

uv 直接采用 [dependency-groups] 作为开发依赖的落点。uv add --dev pytest 写进名为 dev 的组，uv add --group lint ruff 写进 lint 组。同步时用 --group / --only-group / --no-group / --all-groups / --no-default-groups 来控制装哪些，其中 dev 组被特殊对待——默认就会装上，另有 --dev / --only-dev / --no-dev 三个等价简写。默认装哪些组可以用 [tool.uv] 里的 default-groups 改。

有一点要提前知道：uv 要求所有依赖组彼此兼容，并且会把它们放在一起解析进同一个锁文件。如果 docs 组和 test 组要求了同一个包的互斥版本，解析会直接失败，而不是各装各的。这通常是好事（它逼你面对真实的冲突），但从 requirements-*.txt 那种「各文件互不知情」的模式迁过来时会显得突然。

示例场景：某开源库把开发工具链放在 [project.optional-dependencies] 的 dev extra 里，其中包含一个内网才能访问的构建插件。发布之后，索引页面上公开列出了这个 extra，外部用户按文档执行 pip install thelib[dev] 时全部失败，两周内收到 9 个内容相同的 issue，维护者累计花了约 3 小时逐个回复解释。根因不是依赖装不上，而是它本就不该出现在对外的元数据里。迁移到 [dependency-groups] 之后，这个组从发布产物中彻底消失，issue 归零。

判断一条依赖该放哪，只问一句：装我这个包的陌生人，有没有可能想要它？一定要：运行时依赖。可能想要：extras。绝无可能：依赖组。

五、本地与私有依赖：越方便的写法越容易带出去

前四节讲的都是「从公共索引装一个有版本号的包」。真实项目还有另外三类来源：本仓库自己的代码、隔壁目录的兄弟项目、公司内网的私有包。它们各有各的坑，而共同的那个坑是——这些写法极其方便，方便到你会不小心把它们发布出去。

可编辑安装：让源码目录表现得像个装好的包

可编辑安装（editable install，即 pip install -e . 那种）要解决的问题是：开发时你希望改完 .py 立刻生效，不想每次都重新构建安装一遍；但你又需要这个包在其它方面表现得像装好了——能被别的代码 import、importlib.metadata 能读到它的元数据、[project.scripts] 声明的命令行入口真的存在。单靠往 PYTHONPATH 里塞路径只能满足第一条。

PEP 660（状态 Final）规定了它在现代构建流程下的实现方式：构建后端产出一个特殊的「可编辑 wheel」，这个 wheel 里装的不是源码副本，而是一段把源码目录接进导入路径的机制——最简单的实现就是放一个写着源码根目录的 .pth 文件，讲究一点的实现会装一组代理模块，好让「哪些模块可见」控制得更精确。这个 wheel 只是构建后端和安装前端之间的临时通信载体，用完即弃，不会被缓存也不会被分发。

由此可以推出一条日常规则：改 Python 源码立刻生效，改 pyproject.toml 不会。新增依赖、新增命令行入口、改 entry point 都属于元数据变更，必须重新安装一次才生效。C 扩展改了同样要重新编译。「明明加了依赖怎么还报 ModuleNotFoundError」十有八九就是这个。

路径依赖与 Git 依赖：别写进会发布的那张表

PEP 508 允许 直接 URL 依赖，写法是 包名 @ URL，URL 可以是 file://、https:// 或者 git+https://。它在本地联调和「临时用一个上游还没发版的修复」时非常好用，但有一条硬约束：带直接 URL 的依赖不能上传到 PyPI。索引拒绝这类元数据，因为它会让下游去一个索引管不到的地方取代码。

uv 对此的做法值得学：[project] 的 dependencies 里始终写普通的版本约束，而「开发期实际从哪拿」挪到 [tool.uv.sources] 这个工具自留地里去表达，可以是本地路径、Git 仓库、工作区成员或指定索引，路径依赖还能加标记要求以可编辑方式安装。这样发布出去的元数据是干净的标准约束，本地开发又能指到隔壁目录。想验证「用发布出去的那份元数据解析会怎样」，加上 --no-sources 跑一次锁定即可。

这里体现的分层很值得记住：「要什么」是标准的、会发布；「从哪拿」是工具的、不发布。一旦你在会发布的那张表里写了路径，这两件事就粘在了一起，而你通常要到发布失败的那一刻才发现。

私有索引与依赖混淆

公司内部包要从私有索引装。最省事的配法是给安装器加一个「额外索引源」，让它在默认的公共索引之外再多找一个地方。这一步就是 依赖混淆 风险的来源。

机制是这样的：当同一个包名在公共索引和私有索引上同时存在时，解析器必须决定听谁的。如果它的策略是「把所有索引的候选版本合到一起，挑版本号最高的那个」，那么攻击者只要去公共索引注册一个和你内部包同名的项目、发一个版本号高得离谱的版本，你的下一次安装就会从公共索引把他的代码拉下来并执行。这不是理论推演，2021 年有安全研究者用这个手法公开演示过对多家大型企业的入侵。

攻击面：同一个包名，两个索引都有 ───────────────────────────────────────────────────────────── 你的内部包 acme-payment 1.4.2 （只在公司私有索引上） 攻击者注册 acme-payment 99.0.0 （在公共索引上，含恶意安装脚本） 解析策略 A：跨索引挑「最好的版本」 ← 危险 候选集 = 私有 1.4.2 ＋ 公共 99.0.0 按版本号排序 → 选中 99.0.0 → 装的是攻击者的代码 注意：这里没有任何报错，安装是「成功」的 解析策略 B：在第一个命中的索引上停下 ← 安全 私有索引先命中 acme-payment → 只在私有索引的候选里解析 公共索引上那个 99.0.0 根本不参与比较 uv 的默认策略是 B（first-index），并且可以把某个包名钉死到某个具名索引。 防守要点：让「这个名字归哪个索引」成为确定的事，而不是让版本号去竞争。

防守分三层，由强到弱。最强的是把包名钉到指定索引：明确声明 acme-payment 只从私有索引取，别处的同名包一律不看。uv 支持用具名索引配合来源声明做到这一点——[[tool.uv.index]] 定义一个具名索引，再在 [tool.uv.sources] 里把某个包指向它；索引还可以标记为「仅服务显式指定它的包」，这样它就不会被顺手用来解析别的包名。其次是在私有索引上把你用到的名字占位注册，让公共索引上的同名包永远排不到前面。最弱但成本最低的是命名约定：所有内部包统一加组织前缀，把撞名概率压低。

反过来，有一个做法要明确避免：把额外索引源写进机器级或用户级的全局配置。那意味着这台机器上每一个项目的每一个包名都可能从那个源解析，风险面从「几个内部包」扩大到「所有依赖」。索引配置应当跟着项目走。

依赖来源声明位置能随包发布吗典型用途主要风险
公共索引 + 版本约束[project] 的 dependencies能绝大多数依赖—
可编辑安装安装命令或工具的来源表不涉及（本地形态）本仓库自身、同仓多包元数据类改动不重装不生效
路径依赖工具的来源表（uv 为 [tool.uv.sources]）不能与隔壁目录的项目联调别人克隆后路径不存在
Git 依赖同上不能用上游还没发版的修复无版本语义，分支会漂移
私有索引索引配置（uv 为 [[tool.uv.index]]）不能（属环境配置）公司内部包依赖混淆

示例场景：某公司 CI 镜像在全局配置里加了内网索引作为额外源，沿用了三年。一次例行依赖审计发现，构建产物里有一个内部工具包的版本号是 99.0.1——而内网上该包的最新版本是 0.8.4。追查下来是公共索引上出现了同名项目，注册时间比这次构建早 11 天，期间共有 34 次构建拉到了它。所幸那个包只是安全研究者的探测样本，没有实际载荷。整改动作是把解析策略改成「第一个命中的索引就停」，并把 6 个内部包显式钉到内网索引，改动集中在一个配置文件里。真正值得记的是发现方式：这个问题不会报错，只能靠比对锁文件里的版本号是否合理发现。

公共索引上的包名是先到先得的全局命名空间，你的内网包名在上面没有任何保护。所以安全不能建立在「版本号谁高听谁的」上，只能建立在「这个名字只许从这个源取」上。

六、工程纪律：让声明文件成为唯一入口

前面五节都是「怎么写」。这一节是「怎么让它别烂掉」。依赖声明腐化的方式高度一致：某次线上救火，有人直接进容器 pip install 了一个包，问题解决了，但那行安装从此只存在于那个容器里。三个月后容器重建，故障重现，而声明文件看上去一切正常。

第一条规矩：依赖只从声明文件进入

环境里装了什么，必须完全由 pyproject.toml 加锁文件决定。手动往环境里装包这个动作本身就是 bug，哪怕装对了也是——因为它制造了一份没人知道的状态。真要临时验证一个包有没有用，用一次性环境去试（uv run --with somepkg ... 这类形式），试完环境就没了，不会污染项目。确认要用，再走 uv add 正式写进去。

第二条规矩：新增依赖要过三问

每一个依赖都是一笔长期负债：它的安全公告你要跟，它的大版本升级你要做，它的传递依赖会挤占你的解析空间，它哪天弃坑你要负责迁移。所以加之前先回答三个问题：

一、它替我解决了什么问题？要能说出具体的那件事，而不是「处理 HTTP 很方便」。如果答案是「少写二十行」，那二十行可能比一笔长期负债便宜。

二、有没有更轻的办法？标准库里是不是已经有了？项目里是不是已经有一个功能重叠的依赖了（两个 HTTP 客户端、两套日期库、两个配置解析器，这种重复在老项目里极其常见）？

三、它的维护活跃度如何？看最近一次发布距今多久、issue 有没有人回、有没有明确的兼容性策略、它自己又背了多少传递依赖。一个自身依赖了十五个包的小工具，你接过来的是十六份负债。

第三条规矩：升级有固定节奏

动作节奏触发条件怎么做
安全公告响应随时扫描器告警或上游公告只动有问题的那一个，走 hotfix 流程
补丁与小版本升级每周或每两周自动化工具提 PR批量升、跑全量测试、一起合
大版本升级按需上游发布不兼容版本单独一个 PR，先读 changelog，不与业务改动混在一起
依赖清理每季度无外部触发找出没人 import 的、功能重叠的、以及只被传递依赖带进来的

节奏比力度重要。攒半年一次性升级，等于把几十个不兼容变更堆在同一个 PR 里，一旦出问题无法二分定位，团队的本能反应就是再攒半年。每两周升一批则始终保持在「出问题能立刻知道是谁」的状态。

第四条规矩：声明文件和锁文件一起提交

这两个文件是一对，分开提交必然产生「声明里有、锁里没有」的中间状态，而 CI 装的是锁文件，于是 CI 绿着、代码却跑不起来。它们也应该一起 review：声明文件的 diff 回答「我们决定接受什么」，锁文件的 diff 回答「这个决定实际带来了什么」——后者经常比前者长几十倍，那几十行就是你刚刚接下的传递依赖。

  • 所有依赖走 uv add 或直接编辑声明文件，改完立即提交
  • 新增依赖前过三问：解决什么、有没有更轻的、维护活跃度如何
  • 库写宽约束，只对深度耦合的依赖加上限；应用靠锁文件钉死
  • 开发依赖放 [dependency-groups]，可选功能才用 extras
  • 声明文件与锁文件同一个提交、同一次 review
  • 内部包显式钉到私有索引，解析策略选「第一个命中就停」
  • 固定节奏升级：安全随时、小版本每两周、大版本单独 PR
  • 进容器 pip install 救急之后不回写声明文件
  • 在库的 dependencies 里写 == 精确版本
  • 用「全部写死精确版本」冒充可复现——传递依赖照样在飘
  • 把 pytest、ruff 塞进 optional-dependencies 的 dev extra
  • 在 [project] 的 dependencies 里写路径或 Git 依赖还指望能发布
  • 把额外索引源写进机器级全局配置，让所有包名都能从它解析
  • 攒半年做一次大升级，然后在一个 PR 里同时改业务代码

检验依赖纪律只要一个动作：删掉 .venv，从声明文件和锁文件重建，跑全量测试。能过，说明环境里没有任何未被声明的东西；过不了，差的那部分就是你团队真正的技术债。

Q&A

我该把依赖写在 pyproject.toml 还是 requirements.txt？
新项目一律写 pyproject.toml。requirements.txt 从来就不是标准，它本质上是一串给 pip 的命令行参数，既不区分「直接依赖」和「传递依赖」，也不携带项目元数据，更没有分组语义——所以才会衍生出 requirements-dev.txt、requirements-test.txt 这一串彼此不知情的文件。[project] 的 dependencies 由 PEP 621 定义，是所有标准工具都认的位置；开发依赖由 PEP 735 的 [dependency-groups] 承接。真正需要保留 requirements.txt 的场景只剩一个：某些部署平台或旧构建系统只认这个格式，这时把它当成锁文件的一种导出产物，由工具生成、不手写、不作为事实来源。
我写的库，到底要不要给依赖加版本上限？
按耦合深度分类，不要一刀切。两头都有真实代价：不加上限，上游发不兼容大版本时你的下游当场受伤，而你的代码一行没改；给每个依赖都加 <next-major，你会把生态的解析空间切碎，下游很快撞上「A 要 X<3、B 要 X>=3」的死局，而且每次上游发版你都得跟着发一个只改一行的版本才能解锁。可操作的判据是问：「如果它明天发 3.0 并改掉一半 API，我的代码需要跟着改吗？」需要——比如数据校验库、ORM、数值计算库这类你深度使用其内部概念的依赖——就加上限；只调了两三个函数的工具型小依赖，只写下限。另外记得配合 CI：定期跑一次「装上游最新版」的任务，让不兼容在下游遇到之前先在你这里暴露。
为什么在 pyproject.toml 里写死精确版本不等于可复现？
因为你只钉住了直接依赖。假设你写了 httpx==0.27.2 和 pydantic==2.9.1，这两行确实固定了，但它们各自拉进来的 httpcore、h11、certifi、pydantic-core、typing-extensions 等等依然按各自的约束自由浮动——而线上事故绝大多数恰恰出在这些传递依赖上。更根本的问题是职责错位：声明文件表达的是「我能接受哪些版本」，锁文件表达的是「这次实际选中了哪些版本，以及它们的哈希是多少」。用声明文件冒充锁文件，你付出了「下游无法与你共存」的全部代价，却只买到直接依赖那一小半确定性。正确做法是声明写宽、锁文件钉死、两者一起提交。锁文件的机制是下一张卡的主题。
extras 和 dependency group 到底怎么选？
只问一句：装你这个包的陌生人，有没有可能想要它？可选的数据库驱动、GUI 后端、性能加速库——用户可能要，放 [project.optional-dependencies]，它会随包发布，用户写 pip install pkg[名字] 来选。pytest、ruff、mypy、sphinx——用户绝无可能要，放 [dependency-groups]，PEP 735 明确规定构建后端不得把它写进发布包的元数据。历史上大量项目用 dev extra 装开发工具，那是在没有标准位置时的将就，代价是把内部工具链暴露在公开元数据里，并且逼着纯应用仓库假装自己是个可发布的包。还有一条实用差别：依赖组不要求项目有 [project] 表区，所以一个只有 [dependency-groups] 的 pyproject.toml 是合法的。
pip install -e . 到底装了什么？改了代码要重装吗？
按 PEP 660，构建后端会产出一个特殊的「可编辑 wheel」，里面装的不是你的源码副本，而是一段把源码目录接进导入路径的机制——常见实现是一个写着源码根目录的 .pth 文件，或者一组在被导入时替换成真实代码的代理模块。这个 wheel 只是构建后端和安装前端之间的临时载体，装完即弃。结论是：改 Python 源码立刻生效，改元数据不生效。新增依赖、改 [project.scripts] 的入口点、改 entry point 都属于元数据变更，必须重新安装一次。C 扩展改了同样要重编。另外提醒一句，可编辑安装的意义不止于「免重装」——它让 importlib.metadata 能读到你的包元数据、让声明的命令行入口真实存在，这些是往 PYTHONPATH 里塞路径做不到的。
[tool.*] 里的配置换工具时会全部作废吗？
会，而这正是它被设计成「自留地」的意义。[tool] 下每个子表的内容完全由对应工具自己定义，没有任何 PEP 规定里面该写什么，所以从 flake8 换到 ruff 就是删掉一段、加上一段，没有迁移工具能替你翻译语义。好消息是作废范围被严格限制住了：[build-system] 和 [project] 是标准，换 lint 工具、换类型检查器、换测试框架统统碰不到它们，项目元数据和依赖声明毫发无伤。反过来，换构建后端时你改的也只是 [build-system] 那两行，[project] 一个字不用动。所以看到一个陌生项目的 pyproject.toml，可以先跳过所有 [tool.*]——那部分只说明他们用什么工具，不说明这个项目是什么。
公司内部包怎么配才安全？额外索引源为什么危险？
危险来自解析策略。加一个「额外索引源」之后，如果安装器的策略是把所有索引的候选版本合在一起挑版本号最高的，那么攻击者只要在公共索引上注册一个与你内部包同名的项目、发一个版本号极高的版本，你的下一次安装就会拉到他的代码并执行安装脚本——整个过程没有任何报错，安装是「成功」的。这就是依赖混淆，2021 年有安全研究者用它公开演示过对多家大型企业的入侵。防守分三层：最强的是把包名钉到指定索引（uv 的默认策略就是「在第一个命中的索引上停下」，并支持用具名索引把某个包锁定到某个源，索引还能标记为只服务显式指定它的包）；其次是在私有索引上把你用到的名字占位注册；最弱但最省事的是给内部包统一加组织前缀。另外别把额外索引源写进机器级全局配置，那会让这台机器上所有项目的所有包名都暴露在同一个风险下。
一个纯应用仓库、不打算发布成包，还需要 [project] 和 [build-system] 吗？
严格来说不需要。PEP 735 特意把 [dependency-groups] 放在顶层而不是 [project] 下面，理由之一就是：[project] 强制要求 name 和 version，硬塞进去等于逼着非包项目把自己伪装成可发布的包。所以一个只有 [dependency-groups] 的 pyproject.toml 是合法的。但实践中通常还是建议写上 [project]，原因有二：一是你多半想把自己的代码 import 进来跑测试，这需要项目本身能被安装（可编辑方式）；二是 requires-python 这类信息写在标准位置上，工具链和同事都能直接读到。折中做法是写 [project] 但告诉工具「这个项目不是要发布的包」，uv 支持这种非包模式，此时它不会尝试构建安装项目自身。
