浮点数不是实数，它是「固定位数的科学计数法」。所有数值稳定性技巧都在做同一件事：把要算的表达式改写成一个数学上完全等价、但中间结果落在浮点能表示的区间里的形式。减最大值不是玄学，是可以推导出来的恒等变形。

一、浮点数不是实数：三个必须记住的后果

大多数数值 bug 的根子在同一个误解上——把 float 当成实数用。实数是稠密、无界、满足结合律的；浮点数三条都不满足。它是一个有限集合：固定位数的符号位、指数位、有效位组合出来的那些值，别的数字一概表示不了，只能四舍五入到最近的一个。Python 的 float 就是 C 的 double，即 IEEE 754 的 binary64；这一点在变量与内置类型那张卡（PY02）里讲过表示层，本节从它推出三个会直接咬到你的后果。

IEEE 754 的一个浮点数 = 符号 × 有效位 × 2^指数 ───────────────────────────────────────────── binary64（Python float / np.float64） ┌─┬───────────┬────────────────────────────────────────────────────┐ │S│ 指数 11 │ 有效位 52 │ └─┴───────────┴────────────────────────────────────────────────────┘ └ 决定「能表示多大多小」 └ 决定「同一量级里能分多细」 binary32（np.float32） binary16（float16） bfloat16（脑浮点） ┌─┬────────┬─────────────┐ ┌─┬─────┬────────┐ ┌─┬────────┬─────┐ │S│ 指数 8 │ 有效位 23 │ │S│指数5│有效位10│ │S│ 指数 8 │有效7│ └─┴────────┴─────────────┘ └─┴─────┴────────┘ └─┴────────┴─────┘ 范围窄、易溢出 范围=f32、精度粗 关键：指数位和有效位是两笔独立的预算。16 位总共只有 15 位可分， 给范围多一点就必须给精度少一点——这正是 bf16 被训练场景选中的原因。

后果一：有限精度，相近的数相减会丢有效位

两个量级相同、数值相近的数相减，结果的量级会骤降，但它继承来的绝对误差不变——于是相对误差被放大了几个数量级。这个现象叫 灾难性抵消（catastrophic cancellation），是精度类 bug 的头号来源。

>>> 0.1 + 0.2
0.30000000000000004          # 0.1/0.2/0.3 三个都不能精确表示
>>> (0.1 + 0.2) == 0.3
False                        # 所以浮点相等比较几乎总是错的
>>> import sys; sys.float_info.epsilon
2.220446049250313e-16        # 1.0 和它的下一个可表示数之间的距离

机器 epsilon 是理解精度的正确单位：它不是「最小能表示的数」，而是相对分辨率。binary64 的 epsilon 约 2.2e-16，意思是在任何量级上，浮点只能分辨出大约 16 位十进制有效数字的差别。在 1e9 附近，相邻可表示数之间就差了约 2e-7；两个 1e18 量级的数相减，误差量级在几百——这正是第五节里朴素方差公式崩掉的原因。

后果二：有限范围，超出就变成无穷或零

指数位的位数决定了可表示区间。超过上界叫 上溢，结果是 inf（NumPy 里）或 OverflowError（Python math 里）；低于下界叫 下溢，结果是 0.0。下溢之前还有一段 次正规数（subnormal）区间，它用牺牲有效位的方式把可表示范围再往下延一截，所以「最小正数」比「最小正规格化数」还要小几十个数量级。

格式指数位 / 有效位最大有限值最小正规格化数机器 epsilon十进制有效位
binary64（双精度）11 / 52（+隐含 1）≈ 1.8e308≈ 2.2e-3082⁻⁵² ≈ 2.2e-16约 15~17 位
binary32（单精度）8 / 23≈ 3.4e38≈ 1.2e-382⁻²³ ≈ 1.2e-7约 6~9 位

这张表最值得记的是最后两行的对比：float16 和 bfloat16 都是 16 位，但范围差了 33 个数量级。float16 的上限只有 65504，一个稍大的中间量就溢出；bfloat16 把指数位加到和 float32 一样的 8 位，代价是有效位只剩 7 位（相对分辨率不到 1%）。深度学习训练更常选 bfloat16，正是因为训练过程对范围的需求远大于对精度的需求——梯度可以糙，但不能变成 inf。

范围和精度是两件独立的事。「换成 16 位会不会不准」和「换成 16 位会不会溢出」要分开问，答案往往相反。

后果三：浮点加法不满足结合律

每一次浮点运算都要把精确结果舍入到最近的可表示值，舍入误差依赖于两个操作数的量级，因此求和的顺序会改变结果。

>>> (1.0 + 1e16) - 1e16
0.0                    # 1.0 相对 1e16 小于半个 ulp，加进去直接被舍掉
>>> 1.0 + (1e16 - 1e16)
1.0                    # 换个括号位置，答案不一样
# 结论：a+(b+c) != (a+b)+c，浮点加法只满足交换律，不满足结合律

这条后果的工程含义比看起来大。多线程或多进程把一个大数组拆开各自求和再合并，划分方式一变，求和顺序就变，结果会在最后几位上抖动。GPU 上的归约、`np.sum` 的分块策略、多卡训练里的梯度 all-reduce 都有这个性质。所以「换了机器 / 换了线程数，结果对不上第 12 位」通常不是 bug，而是浮点的正常行为；真正该做的是把断言从「完全相等」改成「容差内相等」。

二、溢出与下溢的真实场景：指数与连乘是两个引爆点

知道了浮点有范围上限，下一个问题是：什么样的表达式会真的顶到上限？答案高度集中——绝大多数生产环境的数值爆炸都来自指数函数，绝大多数精度归零都来自概率连乘。这两者都不是罕见写法，它们出现在 softmax、注意力、语言模型打分、贝叶斯推断、隐马尔可夫模型里。

指数函数把加法量级变成乘法量级

exp 的输入只要走到三位数，输出就顶破了双精度的上限。这个阈值可以直接算出来：溢出条件是 exp(x) > 最大有限值，也就是 x > ln(最大有限值)。

格式exp(x) 溢出为 infexp(x) 下溢为 0.0可用的安全区间（约）
binary64x ≳ 709.8x ≲ -745[-745, 709]
binary32x ≳ 88.7x ≲ -104[-103, 88]
binary16x ≳ 11.1x ≲ -17[-16, 11]
bfloat16x ≳ 88.7x ≲ -93[-92, 88]

binary16 那一行值得盯一眼：半精度下 exp(12) 就已经是 inf。注意力分数、logit 这些量走到 12 是家常便饭，这就是为什么半精度训练必须把 softmax 之类的归约放到 float32 里算。还有一个容易忽略的差异：Python 的 math.exp 溢出会抛异常，NumPy 的 np.exp 溢出只给一条警告然后返回 inf。前者会立刻停在出错的地方，后者让坏值静悄悄流进下游——这个差异决定了你是在第一现场看到问题，还是在三层调用之后看到一个莫名其妙的 nan。

>>> import math, numpy as np
>>> math.exp(1000)
OverflowError: math range error       # 立刻炸在现场
>>> np.exp(1000.0)
inf                                   # 只有 RuntimeWarning，值继续往下流
>>> np.exp(1000.0) / np.exp(1000.0)
nan                                   # inf/inf，从这里开始不可逆

非数值一旦产生就会污染整张计算图

nan（not a number）的设计目标是「可传播的错误标记」：几乎任何含 nan 的运算结果都是 nan，而且所有涉及 nan 的比较都返回假，包括 nan == nan。这让它极难被常规的边界检查拦住——写 if x > threshold 的分支在 nan 上永远走 else，你的代码会「正常地」得出错误结论。

另一头：概率连乘迅速下溢成零

序列概率是逐项条件概率的乘积。假设每个 token 的概率约 1e-3，300 个 token 的序列概率是 1e-900——远低于双精度的下界 5e-324，直接变成 0.0。麻烦不在于「不精确」，而在于比较彻底失效：两个候选序列的概率都是 0.0，你无法判断哪个更可能；做归一化时又得到 0/0，回到上面那张表的第二行。

判据：只要表达式里出现指数函数或概率连乘，就必须先想稳定性，再想性能。这两个模式是数值爆炸的充分预警信号，没有例外。

生产事故复盘：一个候选排序打分服务上线后偶发返回 nan，触发率约 0.04%，6 小时内影响 1247 个请求（总量约 312 万），定位耗时 9 小时。归一化那一步写的是最朴素的 np.exp(s) / np.exp(s).sum()，没有减最大值。线上 99.96% 的分数落在 [-20, 30]，本来相安无事；但有一路召回通道在特征缺失时把分数兜底填成了 1e3 量级，np.exp(1000) 溢出成 inf，求和后 inf/inf 变 nan，同一批里所有正常候选的分数也被一起抹成 0。定位之所以花了 9 小时，是因为日志只记录了最终的 nan 结果，np.exp 的 RuntimeWarning 默认不入日志，而 0.04% 的触发率在灰度期一次都没复现。修复两处共 3 行：归一化改用减最大值的稳定写法，以及在入口对分数做范围校验并快速失败。

这个事故的教训有两层。表层是「softmax 要减最大值」；深层是坏值的产生点和暴露点被拉开了很远——警告被丢弃、异常样本比例极低、日志只记结果不记中间量。第六节讲的就是怎么把这段距离压回到零。

三、稳定 softmax 的原理：把实现细节还原成恒等变形

「softmax 要减去每行的最大值」这句话在很多代码里以注释形式存在，读的人当作一条要背的规矩。它其实是一个两行就能推完的恒等变形，理解了推导，你就能在遇到新的表达式时自己造出同类的技巧，而不是只会照抄这一个。

为什么减去一个常数不改变结果

softmax 的定义是每一项的指数除以所有项指数之和。把每个输入都减掉同一个常数 m，相当于给分子和分母同时乘上了 exp(-m) 这个非零常数，约掉之后完全回到原式。

softmax(x)ᵢ = exp(xᵢ) / Σⱼ exp(xⱼ)

exp(xᵢ - m) / Σⱼ exp(xⱼ - m)
= [ exp(xᵢ)·exp(-m) ] / [ exp(-m)·Σⱼ exp(xⱼ) ]
= exp(xᵢ) / Σⱼ exp(xⱼ)   = softmax(x)ᵢ

注意这里的等号是数学上的严格相等，对任意实数 m 都成立，不是近似、不是「误差可忽略」。所以我们有完全的自由去挑一个让中间结果最听话的 m。

为什么偏偏选行最大值

取 m = max(x) 之后，所有 xᵢ - m ≤ 0，于是每个 exp(xᵢ - m) 都落在 (0, 1] 区间里。三个好性质同时成立：

  • 杜绝上溢：指数的最大输入变成 0，exp(0) = 1，再大的原始分数也不可能让指数项超过 1。
  • 分母有下界：最大项恰好贡献 1，所以分母 ≥ 1，不可能出现除零。
  • 下溢是安全的：某些 xᵢ - m 非常负，其指数下溢为 0.0——但这恰好是正确舍入的结果。这些项在数学上本来就远小于分母里那个 1，把它们当 0 不改变归一化后的答案在可表示精度内的取值。

第三点是关键，也是最容易被误解的地方：不是所有下溢都危险。危险的下溢是「后面还要拿它做除数或取对数」的那种；这里下溢的项只是被加进一个至少为 1 的和里，贡献为 0，没有任何后续伤害。数值稳定性的功夫，一半在于判断哪些误差无害。

同一组分数，两种写法的中间量 ──────────────────────────── x = [ 1.0, 2.0, 1000.0 ] 朴素：exp(x) 稳定：m = max(x) = 1000 exp(1) = 2.72 x - m = [-999, -998, 0] exp(2) = 7.39 exp(-999) = 0.0 （下溢，无害） exp(1000) = inf ← 炸 exp(-998) = 0.0 （下溢，无害） sum = inf exp(0) = 1.0 ← 上界被钉住 x/sum = [0, 0, nan] sum = 1.0 ← 分母 ≥ 1 恒成立 结果 = [0, 0, 1.0] ✅ 两种写法数学上等价，差别只在中间量有没有跑出可表示区间。 实现要点：m 必须沿 softmax 作用的那一维取，不能取全局最大值——注意力里 是 [batch, head, query, key] 的最后一维。取错维度不会报错， 只会得到静默错误的概率分布。

稳定 softmax 唯一救不了的边界：如果一行全部被掩码成 -inf，此时 m = -inf，-inf - (-inf) = nan，整行直接变非数值。因果掩码的第一行、长度为 0 的序列、padding 全覆盖的样本都可能撞上它。两条防线：归一化之前确保每行至少有一个有效位置；掩码值用一个足够负的有限数（如 float32 下的 -1e9，或 np.finfo(dtype).min 的一半）而不是 -inf，这样减最大值这一步就不会踩到 inf - inf。手写注意力时这一步在缩放点积之后、乘 V 之前，完整实现与掩码写法见 T06 · Attention：从零实现缩放点积注意力——那张卡里减最大值只占一行代码，本节要说明的是它为什么必须是那一行。

减最大值不是「让数字小一点」这种模糊的好意，它是把指数项的上界精确钉在 1、把分母的下界精确钉在 1。凡是能找到这种「等价改写后中间量有硬边界」的变形，就是一个稳定算法。

四、对数域计算：连乘变求和，下溢问题消失

第二节那个下溢场景（300 个 1e-3 相乘等于 0）没法靠平移解决，因为问题不在某一项，而在乘积本身的量级就落在可表示范围之外。这时唯一的出路是换一套坐标：不存概率，存概率的对数，也就是搬到对数域去算。

换了坐标之后，三件事同时变好

对数是严格单调递增的，所以比较大小、求 argmax、排序在对数域完全等价——这就是它能当替身的前提。换过去之后：连乘变成求和（乘法的舍入误差不再累积成灾），量级从 1e-900 变成 -2072 这种舒服的数字（彻底告别下溢），而且加法比乘法更不容易失去精度。

概率域 对数域 ────────────────────────────────────────────────────── p1 · p2 · ... · pn log p1 + log p2 + ... + log pn ↓ 300 项、每项 1e-3 ↓ 1e-900 → 0.0 ✗ -2072.3 ✓ （离 ±709 的指数边界很远） p / Σ p log p - logsumexp(log p) Σ p logsumexp(log p) ← 唯一需要技巧的运算 p_a / p_b（似然比） log p_a - log p_b argmax p argmax log p ← 单调，完全等价 只有「把若干概率加起来」这一步需要回到指数：log( exp(a)+exp(b)+... ) 直接算就又溢出了，所以需要一个稳定的 logsumexp。

logsumexp：对数域的加法，也只需要提最大值

把最大值提到对数外面，同样是一个严格的恒等变形——这次用的是「乘进对数等于加在外面」。

m = max(x)

log Σᵢ exp(xᵢ)
= log [ exp(m) · Σᵢ exp(xᵢ - m) ]
= m + log Σᵢ exp(xᵢ - m)

右边的每个 exp(xᵢ - m) 都在 (0, 1] 里，不会上溢；括号里的和至少是 1，所以对数的输入至少是 1，不会取到 0 或负数。这一个函数是许多算法的基石：隐马尔可夫的前向算法、贝叶斯模型的证据归一化、beam search 的打分、对比学习的损失，本质上都是在反复调用它。标准实现已经有了——NumPy 的 np.logaddexp（两项版本）、SciPy 的 scipy.special.logsumexp、PyTorch 的 torch.logsumexp，优先用现成的，不要自己写。

>>> import numpy as np
>>> np.logaddexp(1000.0, 1001.0)      # log(exp(1000) + exp(1001))
1001.3132616875182                     # 朴素写法这里是 inf
>>> np.log(np.exp(1000.0) + np.exp(1001.0))
inf
# log_softmax 就是 x - logsumexp(x)，同样不要手工拼 log(softmax(x))

log1p 与 expm1：为接近零的那一段保留精度

这两个函数存在的唯一理由是躲开「1 加上一个极小数」这一步的灾难性抵消。1 + 1e-17 在双精度里就等于 1.0（因为 1e-17 小于 1.0 处的半个 ulp），信息在加法那一刻就没了，后面的 log 再怎么算都只能得到 0。math.log1p(x) 直接计算 log(1+x) 这个整体，绕过了中间那个 1+x；math.expm1(x) 对 exp(x)-1 做同样的事。这不是学术洁癖：复利、极小概率的对数似然、学习率衰减、log(1 - p) 形式的二分类损失都会走到这一段，而且这类误差不会报警，只会让结果悄悄偏掉。

>>> import math
>>> math.log(1 + 1e-17), math.log1p(1e-17)
(0.0, 1e-17)                  # 左边全损，右边满精度
>>> math.exp(1e-17) - 1, math.expm1(1e-17)
(0.0, 1e-17)
# 判据：只要参数可能接近 0，log(1+x) 就写 log1p(x)，exp(x)-1 就写 expm1(x)

交叉熵为什么要直接从 logit 算

交叉熵损失是 -log(softmax(x)_y)。分两步算（先 softmax 再取对数）会连撞两个坑：softmax 那一步如果没减最大值会溢出；即使减了，正确答案概率很小时 softmax 的输出会下溢成 0，接着 log(0) = -inf。把两步融合成一个表达式就能同时躲开——代入上面的 logsumexp 恒等式：

-log softmax(x)_y = logsumexp(x) - x_y
= [ m + log Σᵢ exp(xᵢ - m) ] - x_y

右边没有任何一步需要先算出那个可能极小的概率值，指数的输入全都 ≤ 0，对数的输入 ≥ 1。这就是框架里 torch.nn.CrossEntropyLoss 和 torch.nn.functional.cross_entropy 都接受未归一化的 logit 而不是概率的原因；二分类对应的是 binary_cross_entropy_with_logits。名字里带 _with_logits 或文档写「输入是 logit」的那一版，就是融合过的稳定版本，自己先 softmax / sigmoid 再套 log 等于主动放弃这份保护。

要算什么朴素写法（会出问题）稳定写法为什么

五、其他高频不稳定模式

指数和连乘占了大头，但还有四类模式在代码评审里出现的频率很高，而且都有干净的标准解法。

除以一个可能为零的量：小常数要加在分母里

归一化、余弦相似度、注意力缩放都要除以一个由数据算出来的量，而这个量可以是 0。加一个小常数是对的，但加的位置决定它有没有用：

# ✗ 加在结果上：分母仍可能为 0，nan 照样产生
v = x / np.linalg.norm(x) + 1e-8
# ✓ 加在分母里：分母有正下界
v = x / (np.linalg.norm(x) + 1e-8)
# ✓ 或者给分母兜个底（更适合分母量级未知的情况）
v = x / np.maximum(np.linalg.norm(x), 1e-8)

常数取多少也不是随便填的：它必须和分母的量级相称。float32 的机器 epsilon 约 1.2e-7，在这个精度下填 1e-12 起不到作用（加上去等于没加），所以 float32 通道的经验值在 1e-6 到 1e-8 之间。另外注意归一化层的惯例是把常数放在根号里面——(x - mean) / sqrt(var + eps)，而不是 sqrt(var) + eps。PyTorch 的 LayerNorm、BatchNorm 的 eps 参数都是这个位置，自己复现时别放错。

方差的朴素公式会灾难性抵消

「平方的均值减去均值的平方」在数学上正确，在浮点下是个陷阱：当均值远大于标准差时，这两个量几乎相等，相减就把有效位全抵消掉了。下面这组数据的真实方差是 22.5，朴素公式在双精度下返回 0.0：

xs = [1e9 + 4, 1e9 + 7, 1e9 + 13, 1e9 + 16]
m = sum(xs) / 4
naive = sum(x * x for x in xs) / 4 - m * m   # -> 0.0        ✗ 全损
two_pass = sum((x - m) ** 2 for x in xs) / 4 # -> 22.5       ✓ 正确
# 朴素公式还可能返回负方差，接着 sqrt(负数) 就是 nan

正确解法有两个。能过两遍数据就用两遍算法：先求均值，再累加与均值的偏差平方——减法发生在同量级的数之间，没有抵消。只能过一遍（流式、在线统计）就用 Welford 在线算法，它逐点更新均值和偏差平方和，数学上等价于两遍法但只需一次遍历和常数内存。顺带一句：numpy.var 和 statistics.variance 内部用的都是数值稳定的做法，只有自己手写才会踩这个坑——而手写在「不想为了算个方差引入依赖」的场景里非常常见。

n, mean, m2 = 0, 0.0, 0.0
for x in stream:
    n += 1
    delta = x - mean
    mean += delta / n
    m2 += delta * (x - mean)      # 注意：用更新后的 mean
var = m2 / n                       # 总体方差；样本方差用 m2 / (n - 1)

大量数值求和会累积精度损失

朴素的顺序累加里，累加器越大、每一项被舍掉的比例越高，误差随项数线性增长（量级 O(n·ε)）。成对求和（pairwise summation）把序列递归二分求和，误差降到 O(log n·ε)；补偿求和（Kahan 及其改进）额外维护一个误差项把每次舍掉的部分补回来，精度最好、代价最大。实测对比很直观：把 100 万个 np.float32 的 0.1 加起来，这些值的精确和是 100000.0014901161…（不是 100000——因为 0.1 在 float32 里存的是 0.10000000149…，这一点属于表示误差，和求和方式无关，下表比的是各种做法相对这个精确和偏了多少）。

把这张表读成两个可执行的决定：第一行和第二行的相对误差差了五个数量级（100958.34 对 100000.01），差别仅仅是「自己写循环」还是「调 arr.sum()」——这是「能向量化就别手写循环」除性能之外的第二个理由。第三行那个参数值得单独记住：对 float32 数组求和或求均值时显式传 dtype=np.float64，一行代码就把剩下的累加误差抹平，代价只是一个 8 字节的累加器。NumPy 的归约行为与 dtype 提升规则在 NumPy 专卡里另有展开，本卡只取稳定性这一面。

归一化前忘了检查全零输入

这一类的特征是「测试数据里不会出现，线上偶尔出现」。全零向量的模长是 0，除下去就是 0/0；空序列的 softmax、全被掩码的注意力行、分母为 0 的比率指标都属于这一族。它们不会在开发期暴露，因为没人会手工构造一条全零的输入。

最后一行是个容易被忽略的方向：Python 的 int 是任意精度的，永远不会溢出，但 NumPy 的整数是定宽的，溢出会回绕。用 np.int32 累加一个超过 21 亿的计数，结果会变成负数，而且不一定有报错。从纯 Python 迁到 NumPy 时这是一类新增风险。

这五类模式共享一个特征：它们在「正常」输入上完全正确，只在边界输入上崩。所以靠观察平均行为永远发现不了，只能靠主动构造边界输入去撞。

六、怎么发现与防住

前五节是知识，这一节是纪律。数值问题的特殊之处在于它不像普通 bug 那样会在出错处停下——nan 会一路传播，等它出现在你的日志里，产生它的那一帧栈早就返回了。所以防守策略的核心只有一句：把坏值的检测点尽量往产生点推。

把非数值和无穷当成必须报警的信号

默认配置是它们的反面：NumPy 对溢出、除零、无效运算只发 RuntimeWarning，而警告在生产环境里通常既不入日志也不触发告警，等于静默。改掉这个默认是最高性价比的一步。

import numpy as np
# 全局：把溢出/除零/无效运算升级为异常，就地抛出
np.seterr(all="raise")
# 局部：只在某段代码里严格（推荐，避免影响第三方库）
with np.errstate(over="raise", divide="raise", invalid="raise"):
    p = softmax(scores)
# 训练时定位 nan 是哪个算子产生的（有性能开销，仅调试用）
# torch.autograd.set_detect_anomaly(True)

除了让运行时报警，还要在关键边界主动断言并快速失败：模型输出交给下游前、损失回传前、写入缓存或数据库前。检测要用 math.isfinite / np.isfinite 这一族——它同时排除 nan 和 ±inf，比只查 isnan 更完整；不要用比较运算符检测，因为所有与 nan 的比较都返回假。抛什么异常、带什么上下文（哪一批、哪个字段、当时的输入范围）属于异常体系设计的范畴，见 PY24；这里的要点只有一个：在边界上快速失败，代价远低于让坏值流进存储。上一节那个打分服务的 9 小时，几乎全花在「坏值是从哪一步开始的」上。

import numpy as np

def guard(name: str, a: np.ndarray) -> np.ndarray:
    if not np.isfinite(a).all():
        bad = int((~np.isfinite(a)).sum())
        raise ValueError(f"{name}: {bad}/{a.size} 个非有限值, 范围 [{np.nanmin(a)}, {np.nanmax(a)}]")
    return a

logits = guard("logits", model(x))      # 在交给下游之前拦住

用高精度算一遍作为参照

「结果不太对」和「结果错了」之间需要一个量化的判断。做法是把同一段计算用更高精度跑一遍当作参照值，再看你的实现相对它偏了多少：float32 的实现拿 float64 当参照，float64 的实现拿 decimal.Decimal（可设任意精度）或 fractions.Fraction（有理数精确运算）当参照。误差的相对量级如果远大于该精度的机器 epsilon，就说明算法本身不稳定，而不是精度不够。比较时一律用容差、不用相等，而且要注意下表里两个常用函数的默认容差差了四个数量级，混着用会得到自相矛盾的结论。

手段用途要注意的点
np.seterr / np.errstate把溢出、除零、无效运算升级成异常errstate 是上下文管理器，作用域可控，优先用它
np.isfinite / math.isfinite同时检测 nan 与 ±inf比 isnan 更完整；不能用比较运算符替代
math.isclose标量的容差比较默认 rel_tol=1e-9、abs_tol=0.0；比较对象含 0 时必须显式给 abs_tol
np.allclose / np.isclose数组的容差比较默认 rtol=1e-5、atol=1e-8，比 math.isclose 松得多
np.testing.assert_allclose测试里的断言失败时打印最大偏差与位置，比裸 assert 好排查
sys.float_info / np.finfo查当前平台/dtype 的 epsilon、上下界写阈值时用它取值，别硬编码魔数
decimal / fractions高精度或精确参照；金额等不容许误差的场景慢几个数量级，只做参照或低频计算，不进热路径
math.fsum正确舍入的求和参照结果唯一，可当作求和类实现的黄金标准

在测试里加入极端输入

数值 bug 的唯一可靠发现方式是主动构造边界输入。这些用例写起来很便宜，参数化一下就是一组，但能覆盖前五节所有的失效模式。测试的组织方式、参数化与 fixture 见 PY41；这里给出必须覆盖的输入清单：

数值代码的必测输入清单 ──────────────────────── 幅度极端 [1e3, 1e6] / [-1e3, -1e6] → 撞 exp 的上溢与下溢边界 （float32 通道的边界低得多，要单独测） 全相等 [5, 5, 5, 5] → softmax 应返回均匀分布，而非 nan 全零 [0, 0, 0, 0] → 归一化的除零路径 单元素 / 空 [7] 和 [] → 归约的退化分支，最常漏 含特殊值 [nan] [inf] [-inf]→ 是该报错还是该跳过？必须是明确选择 全掩码行 mask 全 False → -inf 减 -inf，第三节那个坑 量级混杂 [1e9+4, 1e9+7] → 方差与求和的抵消 长序列 1e6 个 0.1 → 累加误差，断言用相对容差 断言方式： np.testing.assert_allclose(got, want, rtol=1e-6) ← 不要用 == assert np.isfinite(got).all() ← 每个用例都加这一条

判据：训练中出现 nan 损失时，先查数值稳定性，再查学习率。学习率过大通常表现为损失震荡上升然后才发散，过程是渐进的；数值问题往往是某一步突然从正常值跳到 nan，而且和特定 batch 绑定——换个随机种子或跳过那一批就正常了。这两个特征足以区分，而顺序搞反会浪费掉大量调参时间。

训练出现 nan 损失时的排查顺序 ───────────────────────────── 是「突然」跳到 nan 还是「渐进」发散？ │ ├─ 突然（上一步还正常）───► 数值稳定性问题，先查这条线 │ 1. 固定那个 batch，能否复现？能 → 数据相关，继续往下 │ 2. 查输入：有 nan/inf 吗？极端值？全零或全掩码样本？ │ 3. 逐层查前向，哪一层的输出先出现非有限值 │ （np.errstate，或 forward hook 里加 isfinite 断言） │ 4. 那一层有 exp / log / 除法 / sqrt / 连乘吗？ │ 5. 换成融合的稳定实现（cross_entropy、logsumexp、log1p…） │ └─ 渐进（损失先震荡上升）──► 优化问题 降学习率 / 加 warmup / 梯度裁剪 / 查离群标签 只有在第 1 步「换任何 batch 都立刻 nan」，或第 2~4 步都干净时， 才值得把时间花到学习率上。

还有一类现象容易和溢出混淆：softmax 的输出饱和（某一项趋近 1、其余趋近 0）导致梯度趋近于零。这不是浮点溢出，而是函数本身的形状与温度参数的作用，症状是训练停滞而非 nan，解法也完全不同（调温度、调缩放，而不是改写表达式）。这一侧的讨论见 T19 · Softmax 梯度饱和与温度调节。把「值算不出来」和「梯度传不回来」分开诊断，是不走弯路的前提。

  • 看到 exp 或概率连乘，先问稳定性：能不能改成减最大值或搬到对数域
  • 交叉熵、二分类损失一律用接受 logit 的融合版本（cross_entropy、*_with_logits）
  • 求和取对数用 logsumexp / np.logaddexp，不自己拼 log(sum(exp(...)))
  • 参数可能接近 0 时用 log1p / expm1
  • 小常数加在分母里（归一化层放进根号内），量级与该 dtype 的 epsilon 相称
  • float32 数组求和求均值显式传 dtype=np.float64；方差用 np.var 或 Welford
  • 关键边界用 np.isfinite(...).all() 断言并快速失败，带上范围信息
  • 热点代码段包在 np.errstate(over="raise", invalid="raise") 里
  • 测试覆盖极大、极小、全零、全相等、单元素、空、全掩码七类输入
  • 断言用 assert_allclose 并显式写容差，不用 ==
  • 写 np.exp(x) / np.exp(x).sum()——第二节那个事故的原文
  • 先 softmax 再 log，或先 sigmoid 再 log
  • 用 np.prod(probs) 算长序列的联合概率
  • 把 eps 加在结果上（x / norm + eps）而不是分母里
  • 手写 mean(x²) - mean(x)² 算方差
  • 用 == 比较浮点，或用 x > threshold 试图拦住 nan
  • 让 NumPy 的 RuntimeWarning 保持默认（只打印、不入日志、不告警）
  • 把 nan 无条件 nan_to_num 掉——那是掩盖根因，坏值会换个形式再出现
  • float16 通道里直接算 softmax / 归约（exp(12) 就已经是 inf）
  • 看到 nan 损失第一反应就是降学习率

数值稳定性不是「算得更准」，而是「在坏输入上不给出荒谬答案」。判断一段数值代码合格的标准，是把极端输入扔进去它要么给出正确结果，要么明确报错——绝不能静悄悄返回一个错的数。

Q&A

softmax 减去最大值，会不会让结果产生误差？
不会引入任何理论误差，这是一个严格的恒等变形：给每个输入减去同一个常数 m，等价于给分子和分母同时乘上 exp(-m) 这个非零常数，约掉后完全回到原式，对任意实数 m 都成立。实际上稳定写法的浮点误差比朴素写法更小，因为所有指数项都落在 (0, 1] 里、分母恒 ≥ 1，中间量的量级差距被压缩了。唯一的代价是多一次沿该维的最大值归约，相对指数运算本身可以忽略。要注意的只有一处实现细节：最大值必须沿 softmax 作用的那一维取，取错维度不会报错，只会静默给出错误的概率分布。
float16 和 bfloat16 都是 16 位，为什么训练更常用 bfloat16？
因为它们把 16 位预算分给了不同的地方。float16 是 5 位指数 + 10 位有效位，最大值只有 65504，exp(12) 就已经溢出；bfloat16 是 8 位指数 + 7 位有效位，指数位和 float32 完全一样，所以范围也一样（约 ±3.4e38），代价是相对分辨率只有 2⁻⁷ ≈ 0.8%。训练过程中最怕的是激活值或梯度溢出成 inf，一旦发生整个参数表就报废；而梯度本身是带噪声的估计量，糙一点不影响收敛方向。所以「范围优先于精度」这个取舍在训练场景是划算的。float16 要用起来通常得配一整套损失缩放机制把梯度搬回可表示区间，bfloat16 常常可以省掉这一步。推理场景的取舍不一定相同，因为推理更在意输出的数值精度。
为什么交叉熵的 API 要我传 logit，不让我传概率？
因为把 softmax 和取对数融合成一个表达式，能同时消掉溢出和下溢两个风险。展开后是 -log softmax(x)_y = logsumexp(x) - x_y，其中 logsumexp 内部提出最大值，所以指数的输入全部 ≤ 0（不会上溢），对数的输入 ≥ 1（不会取到 0 或负数）。如果你自己先算 softmax 再取对数，正确答案概率很小时 softmax 的输出会下溢成 0，接着 log(0) 给出 -inf，梯度立刻变 nan——而且这种情况恰好在模型预测很自信但预测错了的时候出现，也就是训练最需要这个梯度的时候。所以 torch.nn.CrossEntropyLoss、torch.nn.functional.cross_entropy、binary_cross_entropy_with_logits 都要求未归一化的分数。反过来说，如果某个 API 明确要求传概率（例如 nll_loss 要求传 log 概率），那是在告诉你稳定化的责任在调用方。
训练损失变成 nan，我该从哪查起？
先判断是「突然」还是「渐进」。数值稳定性问题通常是上一步还完全正常、下一步直接 nan，并且和特定 batch 绑定——固定随机种子后能稳定复现，跳过那一批就正常；学习率过大则表现为损失先震荡、上升，然后才发散，过程是渐进可见的。如果是突然跳变，按这个顺序查：检查那一批输入里有没有 nan/inf、有没有极端值、有没有全零或全掩码样本；然后用 forward hook 加 np.isfinite 断言逐层定位哪一层的输出先变成非有限值；找到那一层后看它有没有 exp、log、除法、sqrt 或连乘，换成融合的稳定实现。只有在「换任何 batch 都立刻 nan」或者前面几步都干净的时候，才值得去调学习率、warmup 和梯度裁剪。顺序搞反的代价很大，因为降学习率有时能把问题压到不那么频繁出现，让你误以为找对了方向。
加一个小常数（eps）到底该加在哪里、取多大？
位置上有一条硬规则：加在分母里，不是加在结果上。x / norm + eps 完全没有防护作用，分母该为 0 还是为 0；要写 x / (norm + eps)，或者在分母量级未知时用 x / np.maximum(norm, eps) 兜底。归一化层还有个惯例：常数放在根号里面，即 (x - mean) / sqrt(var + eps)，PyTorch 的 LayerNorm 和 BatchNorm 的 eps 都是这个位置，自己复现时放到根号外会和框架结果对不上。取值上要和分母的量级以及该 dtype 的机器 epsilon 相称：float32 的 epsilon 约 1.2e-7，填 1e-12 在这个精度下加上去等于没加，经验区间是 1e-6 到 1e-8；float64 可以更小。写阈值时建议直接从 np.finfo(dtype).eps 取值而不是硬编码，这样换精度时不会失效。
我的结果换了机器 / 换了线程数就对不上第十几位，是哪里写错了吗？
大概率没写错。浮点加法不满足结合律——每一步都要舍入，而舍入误差取决于操作数的量级，所以求和顺序一变，末几位就会变。并行归约把数组切成若干块各自求和再合并，切法随线程数、设备、库版本而变，于是结果在最后几位上抖动是正常现象。真正该做的是把断言从「完全相等」改成「容差内相等」（np.testing.assert_allclose 并显式写 rtol），以及不要把浮点结果当作缓存键或做哈希。如果业务确实需要逐位可复现（比如要对齐两次训练的权重），就得付代价：固定线程数与归约顺序、关闭非确定性的算子实现、必要时用 math.fsum 这类正确舍入的求和。顺带说，如果偏差不是在末几位而是在前几位，那就不是结合律的问题了，要按第五节的抵消和累加误差去查。
直接把 nan 用 nan_to_num 替换掉不行吗？
作为兜底可以，作为修复不行。nan_to_num 把 nan 换成 0、inf 换成该 dtype 的最大值，做的是掩盖症状：产生 nan 的那一步仍然在跑，只是它的错误结论被换成了另一个同样没有意义的数字，然后继续往下游流。更糟的是它让问题变得不可观测——原先至少能看到 nan 这个明确信号，现在你得到的是一个看起来正常的数值，错误变成静默的。正确顺序是：先在关键边界用 np.isfinite(...).all() 断言并快速失败，把产生点定位出来，改掉表达式；只在确实需要保证服务不中断、且已经确认该位置的退化返回值有业务含义时，才用 nan_to_num 作为最外层的保险，并且同时打日志计数，让它的触发频率是可监控的。一个被静默 nan_to_num 掉的坑，通常会在几个月后以另一种面貌回来。
