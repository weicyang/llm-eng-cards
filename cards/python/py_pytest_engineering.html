PY41 · pytest 与测试工程化

测试的价值在于支持改动 / 断言重写与收集规则 / fixture 作用域与状态泄漏 / 替身只替进程边界 / 覆盖率看增量与分支

测试不是用来证明代码是对的，是用来让你敢改代码。判断一条测试值不值得留下，只问一句：它变红的时候，是在告诉你「行为坏了」，还是只在告诉你「代码换了写法」。

一、测试的用途不是证明正确，而是让改动变便宜

先问一个不太舒服的问题：如果一段代码写完之后再也不改，它需要测试吗？答案接近「不需要」——你手动跑一遍确认它能用，收益和写一套测试差不多。测试真正的回报发生在第二次以后：你改了一行，需要在几十秒内知道有没有顺手弄坏别的地方。没有这层保护，每次改动都要靠人脑回忆影响面，于是团队自然演化成「能不动就不动」，代码腐化就是从这里开始的。

把这条想清楚，评价测试的标准就变了：不是「覆盖了多少代码」，而是它把一次改动的心理成本和验证成本压低了多少。这个标准能直接推出本卡最重要的一条判据。

锁行为契约，不锁实现细节

测试应该断言行为契约——外部可观察的输入输出、状态变化、抛出的异常、对外发出的副作用；不应该断言实现细节——内部调用了哪个私有方法、调了几次、中间变量长什么样、走了哪条分支。

原因很直接：重构的定义本来就是「改实现、不改行为」。如果测试断言的是实现，那么每一次重构都会让一大片测试变红，而产品行为一点没变。这种红是纯噪声，它不指示缺陷，只指示「代码换了写法」。噪声一旦多到某个程度，团队只会做两件事之一：要么不再重构，要么把测试删掉。两条路通向同一个结果——测试不再提供保护，却还在消耗维护成本。

同一个函数，两种瞄准方式 ───────────────────────────────────────────────────────── ┌──────────────────────────┐ 调用方 ─ 输入 ──► │ │ ── 返回值 ──► 契约面 │ create_order(...) │ ── 抛异常 ──► 契约面 │ │ ── 落库/发消息 ─► 契约面 └───────────┬──────────────┘ │ 内部： │ _validate() 被调了几次 ← 实现面 │ 先查库存还是先查余额 ← 实现面 │ 用 dict 还是 dataclass 存中间态 ← 实现面 └────────────────────────────── 测试瞄准契约面：重构不影响它，行为坏了它必红 ← 值得写 测试瞄准实现面：重构必然误伤，行为坏了未必红 ← 负资产

最后一行值得多说一句：退避的秒数究竟算契约还是实现，取决于它有没有对外承诺。如果只是内部调优参数，断言它就是锁实现；如果它写进了和下游约定的限流协议，那它就是契约。判断标准不是「这个值重不重要」，而是「改掉它算不算改变了对外承诺」。

写完一条测试，先在脑子里做一次演练：假设我把这段代码整个重写一遍、行为完全不变，这条测试还会通过吗？答「不会」，说明它锁的是实现。

反过来也有正当的例外。有些「交互」本身就是契约：支付必须只发起一次、幂等键必须透传给下游、审计日志必须落一条。这类断言看上去像在检查调用次数，实际检查的是对外可观察的副作用，属于契约面。区别在于，它约束的是系统边界上发生了什么，而不是边界内部怎么组织代码。

事故复盘：某订单服务把一个 2000 余行的核心模块按职责拆成四个子模块，纯结构调整，对外接口签名和行为零变化。重构本身 2 名工程师做了 2.5 人日，代码评审一次通过。合并那天 CI 全红：套件共 1847 条测试，一次性失败 412 条，占比 22%。逐条看下来，其中 380 条失败的原因是断言了内部调用序列（形如「某个内部对象的某方法被调用一次、参数为 X」），拆分后调用路径变了但结果没变；31 条是因为断言了日志文案；真正暴露出行为缺陷的只有 1 条——一个边界条件下的空列表处理。修测试花了 9 人日，是重构本身的 3.6 倍。复盘结论有两条：第一，这 411 条测试在此之前从未发现过任何缺陷，却在唯一一次重构中制造了全部成本；第二，团队此后半年内对该模块的改动申请下降了一半——真正的损失不是那 9 人日，而是大家对动这块代码产生了畏惧。

这类事故给出的操作建议不是「不要用替身」，而是把断言的位置往外挪一层：让测试从被测单元的公开入口进去、从它的返回值和可观察副作用出来，中间怎么走不管。第五节会给出替身的具体边界。

二、pytest 的核心机制：裸 assert、收集规则与 conftest

如果只把 pytest 当成「不用继承 TestCase 的 unittest」，会错过它真正省事的地方。它有三件事值得先弄明白：为什么裸 assert 能给出详细失败信息、它按什么规则找到你的测试、conftest.py 凭什么不用 import 就生效。

断言重写：失败信息是编译期塞进去的

Python 的 assert x == y 失败时只会抛一个光秃秃的 AssertionError，什么上下文都没有。unittest 的解法是让你改用 assertEqual 之类的几十个方法名；pytest 的解法是断言重写：它通过导入钩子接管测试模块的加载，在源码编译成字节码之前改写语法树，把 assert 语句替换成一段会把子表达式中间值全部保存下来的等价代码。失败时它就能打印出两边各自的实际值，以及差异在哪。

# 你写的
def test_merge():
    assert merge({"a": 1}, {"b": 2}) == {"a": 1, "b": 2, "c": 3}

# 失败时你看到的
E   AssertionError: assert {'a': 1, 'b': 2} == {'a': 1, 'b': 2, 'c': 3}
E     Common items: {'a': 1, 'b': 2}
E     Right contains 1 more item: {'c': 3}

这个机制有两个必须知道的边界。其一，重写只作用于 pytest 自己负责导入的模块——测试模块、conftest.py，以及通过入口点注册的插件。如果你把断言封装进一个自己写的辅助模块（比如 tests/asserts.py）再 import 进来，那里的 assert 不会被重写，失败信息又回到光秃秃的状态；解决办法是在 conftest.py 里用 pytest.register_assert_rewrite("tests.asserts") 显式登记，且必须在该模块被首次导入之前执行。其二，assert 在 python -O 下会被整体优化掉，所以它只适合出现在测试里，不要用 assert 做生产代码的参数校验；生产侧的校验应当抛显式异常，这部分见 PY24 异常体系设计。

测试发现：默认规则是一组前缀约定

pytest 不需要你注册任何东西，它从指定路径（或配置里的 testpaths）开始递归扫描，按下面这组默认约定判断「什么是测试」。这些规则都可以在配置里改，但在 99% 的项目里改它只会制造理解成本。

层级默认规则常见踩坑
文件文件名匹配 test_*.py 或 *_test.py写成 tests_order.py、order_tests.py 都不会被收集，且不报错
类类名以 Test 开头该类不能定义 __init__，否则整个类被跳过并给出警告
函数 / 方法名字以 test 开头拼成 tset_ 或 check_ 一样是静默跳过
目录递归扫描，跳过隐藏目录与虚拟环境目录不同目录下有同名测试文件且都没有 __init__.py 时会导入冲突
配置根由 pyproject.toml / pytest.ini / tox.ini / setup.cfg 推导出 rootdirrootdir 判错会导致相对路径和节点 ID 与预期不符

「静默跳过」是新手最容易被坑的一点：名字不匹配时 pytest 不会提醒你「这里有个像测试的东西没被收集」，它只会报告收集到 0 条用例然后退出。所以每次新建测试文件，第一件事是确认用例数涨了。收集数量本身就是一条需要盯的信号。

# 只收集不执行，用来确认自己写的东西真的被认出来了
python -m pytest --collect-only -q

# 节点 ID 的形状：文件::类::方法[参数 id]
tests/test_order.py::TestCreate::test_reject_negative[amount=-1]

注意这里用的是 python -m pytest 而不是裸 pytest：前者会把当前工作目录放进模块搜索路径，所以能 import 到项目自己的包。这个差别是「本地全绿、CI 全红」的经典成因，详见 PY01 环境与解释器。

conftest.py：按目录生效的共享配置

conftest.py 是 pytest 的约定文件：它不需要被任何人 import，pytest 在收集阶段自动加载，其中定义的 fixture、钩子、命令行选项对它所在目录及所有子目录下的测试自动可见。同名 fixture 以离测试文件最近的那个为准，这就是「就近覆盖」。

repo/ ├── conftest.py ← ① 全仓生效：环境变量、根级夹具、自定义选项 ├── pyproject.toml ← rootdir 由它确定 └── tests/ ├── conftest.py ← ② 全部测试生效：假时钟、临时目录约定 ├── unit/ │ ├── conftest.py ← ③ 只对 unit/ 生效：内存版仓储 │ └── test_pricing.py 可见 ① ② ③ └── integration/ ├── conftest.py ← ④ 只对 integration/ 生效：真数据库连接 └── test_checkout.py 可见 ① ② ④，看不到 ③ 同名 fixture 的解析顺序：④ 覆盖 ② 覆盖 ①（就近者胜） 测试文件内直接定义的 fixture，优先级高于任何 conftest
conftest 位置影响范围适合放什么不该放什么
仓库根目录所有测试，含子项目自定义命令行选项、全局标记注册、路径设置任何和具体业务模块绑定的夹具
tests/整个测试套件假时钟、随机种子固定、通用构造器真实外部连接（会拖慢所有测试）
tests/unit/仅单元测试内存替身、轻量假实现需要网络或容器的东西
tests/integration/仅集成测试数据库连接、容器启动与回收会被单元测试误用的通用名字
测试文件内部仅本文件只此一处用到的夹具三个以上文件都要用的东西（该上移了）

conftest.py 的作用域规则和 Python 的作用域链很像：从当前目录一路往上找，先找到的先用。放得越靠上影响面越大，出问题时的排查范围也越大——所以能往下放就往下放。

三、fixture 是按需装配的依赖，不是 setUp 的新写法

很多人把 fixture 理解成「换了个写法的 setUp」，这会错过它的全部设计意图。setUp 是推模型：不管这条测试要不要，它每次都跑，于是它会逐渐膨胀成一个什么都准备一点的大杂烩。fixture 是拉模型：测试函数在参数列表里写下 fixture 的名字，pytest 才去创建它；没声明就不会执行。

这个区别带来三个后果。第一，测试的依赖是写在签名上的，读一眼就知道这条测试需要什么环境。第二，fixture 之间可以互相依赖，pytest 会自己算出构建顺序，形成一张按需求解的依赖图。第三，不需要的东西不会被创建，套件不会因为某条测试需要数据库就让所有测试都连数据库。

import pytest

@pytest.fixture
def repo(db_conn):          # 依赖另一个 fixture，pytest 自动先建它
    r = OrderRepo(db_conn)
    yield r                 # yield 之前是准备，之后是清理
    r.truncate()            # 作用域结束时执行，即使测试失败也会执行

def test_create(repo):      # 在签名里"要"它，才会被创建
    assert repo.create(amount=10).status == "CREATED"

yield 形式的 fixture 和 with 语句是同一套思路：把「准备」和「配对的清理」写在同一处，中间交给别人用。理解 PY19 上下文管理器里 contextmanager 的机制，就等于理解了 fixture 的清理模型。一个实用细节：如果 yield 之前抛了异常，yield 之后的代码不会执行，因为 fixture 根本没建成；所以「创建了一半」的资源要在准备段自己用 try 兜住，不能指望清理段。

作用域：越大越快，也越容易泄漏

fixture 的 scope 参数决定它被创建几次、活多久。常用的是函数、类、模块、会话四档（另有一档 package，按包粒度复用，用得较少）。选择本质上是一道速度与隔离的交换题。

作用域创建次数典型用途主要风险
function（默认）每条测试一次绝大多数夹具，尤其是任何可变对象慢——但这是最该先付的成本
class每个测试类一次同一类里多条测试共享的只读准备类内测试之间产生顺序依赖
module每个测试文件一次一整个文件共用的重量级只读数据单跑该文件通过、全跑失败
session整次运行一次启动容器、建连接池、载大模型权重状态泄漏影响面最大，且并行执行时行为复杂

作用域是拿隔离性换时间。默认一律用函数级，等套件真的慢到影响节奏了再挑最贵的几个往上提；而且只提「建起来贵、本身不可变」的东西，比如连接、容器、模型权重。

会话级 fixture 的生命周期（一次 pytest 运行） ──────────────────────────────────────────────────────────── session ┌──────────────── 建库容器 ─────────────────────┐ module │ ┌──── 载入测试数据 ────┐ ┌──── 载入 ────┐ │ function │ │ ┌t1┐ ┌t2┐ ┌t3┐ │ │ ┌t4┐ ┌t5┐ │ │ │ │ └──┘ └──┘ └──┘ │ │ └──┘ └──┘ │ │ │ └──────────────────────┘ └─────────────┘ │ └──────────────────────────────────────────────┘ ▲ ▲ │ └─ t1 往库里写的数据，t3 还能看见 └─ 容器只建一次：快了 40 秒，也把隔离性一起交出去了 症状对照 单跑 t3 通过、全跑失败 ► t3 依赖了前面测试留下的状态 单跑 t3 失败、全跑通过 ► t3 自己没准备好数据，靠别人捎带

上图右下角那两行是本节最值钱的东西。「单跑通过、全跑失败」和「单跑失败、全跑通过」是同一种病的两面：测试之间存在顺序依赖。它几乎总是由共享可变状态引起——大作用域的 fixture、模块级全局变量、没清理的环境变量、真实数据库里的残留数据、被替换后没还原的类属性。

事故复盘：某团队为了把 CI 从 14 分钟压到 6 分钟，把数据库 fixture 从 function 升到 session，只在会话开始时建一次库。当周确实提速到 5 分 40 秒。两周后出现一个诡异现象：一条用户查询的测试在本地单跑必过，在 CI 里每天随机失败一到两次。查了 6 小时才定位到根因——另一条测试为了验证软删除写入了一条 deleted_at 非空的记录且没有清理，而两条测试的相对顺序会随收集顺序变化。修法是保留 session 级的容器，但给每条测试套一层事务并在结束时回滚，隔离性回来了，耗时只涨到 6 分 20 秒。这个案例的通用形态是：可以共享昂贵的连接，不要共享可变的数据。

autouse 与间接参数化

autouse=True 让 fixture 不需要声明就自动生效。它适合那些「所有测试都必须处于这个前提下」的设置，比如固定随机种子、把时区锁成 UTC。代价是隐式依赖：读测试代码看不出它依赖了什么，排查时要一路翻上级 conftest.py。判据是：能写进签名就别用 autouse，只有当它是全局不变量时才值得。

间接参数化解决另一类问题：想让参数先经过 fixture 加工再进测试。给 parametrize 加上 indirect=True，那些值不会直接传给测试函数，而是作为 request.param 传给同名 fixture，由 fixture 决定如何据此装配。

@pytest.fixture
def client(request):
    return build_client(auth=request.param)   # 拿到的是参数化传来的值

@pytest.mark.parametrize("client", ["anonymous", "admin"], indirect=True)
def test_list_orders(client):
    # 同一条测试跑两遍，分别用匿名和管理员身份装配出的 client
    assert client.get("/orders").status_code == 200

四、参数化、命名与分层：让失败信息自己说话

一条测试失败时，你在终端上读到的第一行就是它的节点 ID。这一行信息量的高低，直接决定你是「看一眼就知道哪儿坏了」还是「得点开日志翻半天」。本节讲的三件事——参数化、命名、标记——本质上都是在优化这一行。

用参数化代替循环断言

把多组输入塞进一个 for 循环里断言，是很自然但代价不小的写法：第一组失败就抛出，后面几组根本没跑，你不知道是只坏了一组还是全坏了；失败信息里也看不出是哪一组；想单独重跑某一组更是做不到。参数化把每一组变成独立的用例，全部都会跑，节点 ID 上带着这组的标识。

# 差：一组失败就停，且不知道是哪组
def test_tax_loop():
    for amount, want in [(0, 0), (100, 13), (-1, 0)]:
        assert tax(amount) == want

# 好：三条独立用例，失败行直接写着 amount=-1
@pytest.mark.parametrize("amount,want", [(0, 0), (100, 13), (-1, 0)],
                         ids=["zero", "normal", "negative"])
def test_tax(amount, want):
    assert tax(amount) == want

ids= 用来给每组起一个人类可读的名字，不写的话 pytest 会用参数值自动生成，对数字和短字符串够用，对复杂对象会退化成 param0 这种没信息量的形式。另外 pytest.param(值..., marks=...) 可以给单独某一组挂标记，比如把一个已知失败的组标成 xfail，而不必把整条测试禁掉。

参数化天然适合放边界值。多数缺陷不在正常路径上，而在下面这些地方：空输入、单元素、恰好等于阈值、超出阈值一点、负数与零、超长字符串、非 ASCII 字符、重复元素、None。把它们列成参数表，比写十条形状雷同的测试函数省事得多。

名字应当说清「在什么条件下期望什么」

测试名不是给写的人看的，是给三个月后看到 CI 红灯的人看的。一个合格的名字包含三段：被测的行为、触发的条件、期望的结果。

信息量名字失败时读者的第一反应
无test_1 / test_order不知道坏的是什么，只能点开看代码
低test_create_order_fail知道是创建失败的场景，但不知道为什么该失败
够用test_create_order_with_negative_amount_raises金额为负时应当抛异常，现在没抛（或抛错了）
更好上一行 + 参数化 id [amount=-0.01]连触发它的具体取值都在第一行里

断言异常时同理：断言异常类型和结构化字段，不要断言人类可读的提示文案，后者是给用户看的、随时会改，属于典型的实现细节。

with pytest.raises(InvalidAmount) as exc:
    create_order(amount=-1)

assert exc.value.code == "AMOUNT_NEGATIVE"   # 稳定的契约
# 不要写：assert str(exc.value) == "金额不能为负"   ← 文案一改就红

用标记做分层

套件长到几分钟以上，就必须能分层执行：本地保存时跑快的那批，合并前跑全量。标记是 pytest 的分类机制，用 @pytest.mark.名字 打在测试上，用 -m 按表达式筛选。自定义标记需要在配置的 markers 项里注册一下，否则会产生警告；配合 --strict-markers，任何未注册的标记会直接报错，可以防住拼写错误导致的「标记写了但没生效」。

标记作用使用要点
skip无条件跳过必须写 reason，否则半年后没人知道为什么跳
skipif条件跳过用于平台、版本、依赖是否可用等客观前提
xfail已知失败，通过时报告为意外通过比 skip 好：缺陷修好时它会提醒你
parametrize参数化可叠加，多个装饰器会产生笛卡尔积
usefixtures使用 fixture 但不需要它的返回值适合纯副作用型准备
filterwarnings为单条测试调整告警策略用于定点容忍，不要全局关告警
自定义（如 slow）分层筛选需在配置的 markers 注册，配 --strict-markers

标记本质上就是装饰器语法的一种应用，parametrize 更是典型的「装饰器改写被装饰对象的元数据」，机制层面见 PY14 闭包与装饰器。

# 本地：只跑快的那批，十几秒出结果
python -m pytest -m "not slow"

# 合并前 / CI：全量
python -m pytest

# 只重跑上次失败的，改完立刻验证
python -m pytest --lf

分层的判据不是「这条测试重不重要」，而是「它多久能跑完、要不要外部依赖」。快且自足的进第一层，每次保存都跑；要起容器、连网络的进第二层，合并前跑。

五、替身的边界：只替你不拥有的那一侧

测试替身指的是在测试里顶替真实协作者的那些东西。它们解决的是确定性问题：真实的网络会超时，真实的时间在流逝，真实的随机数每次不同，真实的文件系统上有别人的残留。这些东西让测试变成掷骰子。

但替身是一把很容易用过头的刀。用过头的症状非常好认：你把业务逻辑整个改错了，测试却全绿；或者你只是重命名了一个内部方法，测试却全红。两种症状都指向同一件事——测试测的是你搭出来的那套模拟器，不是真实代码。

核心判据：边界在哪，替身就在哪

判据只有一句：只替掉你不拥有的东西。「不拥有」指的是那些你无法在测试里可靠控制的外部世界——它们通常就在进程边界上。自己写的业务对象属于「拥有」，应该用真实的；把它们换成替身，等于把两个你本该一起验证的东西拆开单独验证，中间那层契约就没人守了。

┌───────── 你拥有的（用真的）─────────┐ │ │ 测试 ──调用──► │ OrderService ──► Pricing ──► Repo │ ──┐ │ 真实 真实 真实 │ │ └─────────────────────────────────────┘ │ ▼ ┌───────── 进程边界 ─────────┐ │ HTTP 外部 API ← 替 │ │ 当前时间 now() ← 替 │ │ random / uuid ← 替 │ │ 文件系统 / 路径 ← 用临时目录│ │ 消息队列 / 邮件 ← 替 │ │ 子进程 / 系统调用 ← 替 │ └────────────────────────────┘ 替在边界上：内部怎么重构都不影响测试，行为坏了必被抓到 替在内部： 重构必红，行为坏了反而抓不到（因为真实协作者没参与）

三类替身的分工

类型它做什么测试断言什么适用风险
打桩（stub）对调用返回预设值，不关心被怎么调被测代码拿到这个返回后的结果外部查询接口、配置读取低
模拟（mock）记录所有调用，供事后断言交互某个对外副作用是否按约定发生发邮件、扣款、发消息这类不可回滚的动作高，最容易滑向锁实现
假实现（fake）一个能真正工作的轻量版本和真实实现一样，断言状态与结果内存版仓储、内存版缓存中，要防假实现与真实现行为漂移

三者之中，假实现是最被低估的一种。写一个内存字典版的仓储通常只要二三十行，却能让一大批测试既快又真实：它有真正的状态，插入之后查得到，删掉之后查不到，被测代码怎么用它都合理。对应的代价是要定期确认假实现和真实实现的行为没有漂移，通常的做法是让两者跑同一组契约测试。

monkeypatch 与 mock 的定位差别

monkeypatch 是 pytest 内置 fixture，干的是临时替换一个值并在测试结束后自动还原：替换对象属性、字典项、环境变量、工作目录。它不记录调用，也不提供断言能力，胜在还原是自动且可靠的——手写 setattr 再在末尾改回来，一旦测试中途失败就还不回去，会污染后续测试。

def test_expires_after_one_hour(monkeypatch):
    monkeypatch.setattr(clock, "now", lambda: FIXED_TIME)
    monkeypatch.setenv("TZ", "UTC")          # 结束后自动还原

    token = issue_token()
    monkeypatch.setattr(clock, "now", lambda: FIXED_TIME + 3601)
    assert token.is_expired()                # 断言行为，不断言 now 被调了几次

unittest.mock 则是标准库里造替身对象的工具，强项在于记录交互并支持事后断言。它有一个默认行为需要特别小心：一个普通 Mock 接受任意属性访问和任意签名的调用，所以你把方法名拼错、或者真实对象改了参数，替身照样笑纳，测试照样通过。autospec（或 create_autospec）会按真实对象的签名生成替身，调用不匹配时直接报错，能挡住这类「测试绿着但早就对不上了」的情况。用 mock 时默认开 autospec，是成本极低、收益极高的一条纪律。

替身用得对不对，有个很直接的检验：把被测模块里某个真实协作者的逻辑故意改错，测试应该变红。如果它还是绿的，说明那个协作者早就被你换成替身了，这块代码其实没人测。

还有一点关于类型：替身是「看起来像」而不是「真的是」，静态类型检查能提前发现替身与真实接口的签名不一致，和 autospec 是互补的两道闸，见 PY20 类型注解与静态检查。异步代码里的替身还要额外注意「协程函数的替身必须仍然可 await」，相关的排查手法见 PY34 异步调试与故障排查。

六、覆盖率、分层与不稳定测试

覆盖率是这个话题里被误用得最彻底的指标。先把定义摆清楚：覆盖率统计的是「测试运行过程中，哪些代码行或分支被执行过」。注意定义里完全没有提到断言——它是执行的指标，不是验证的指标。

# 这条测试能把 calculate_invoice 的行覆盖率拉到 100%
def test_calculate_invoice():
    calculate_invoice(order)      # 跑完就完，什么都没断言

# 它能发现的缺陷只有一类：抛异常。
# 返回值算错、算反、算成负数——它一律报告通过。

所以「覆盖率 90%」这句话唯一可靠的信息是还有 10% 的代码从没被执行过，那 10% 里有什么无人知晓。它不说明剩下 90% 是对的。反过来，覆盖率低确实是个明确信号：没执行过的代码等于没验证过，出问题时你连「测试跑过它」这个前提都没有。把覆盖率当下限指标看是合理的，当质量指标看是错的。

指标回答什么问题看不出什么实用建议
行 / 语句覆盖哪些语句一次都没执行过执行了但没断言；条件分支只走了一边作为最低门槛，别当目标
分支覆盖每个判断的真假两侧是否都走过依然看不出断言强弱优先开它，信息量远高于行覆盖
增量覆盖本次改动新增/修改的代码被覆盖了多少历史欠债真正该卡的门禁，新代码不留新债
总覆盖率绝对值几乎什么都不回答被大量无断言测试、被自动生成代码稀释看趋势不看数值，不要设硬性达标线

为什么要卡增量而不是绝对值？因为一个存量项目把总覆盖率从 45% 提到 80% 是个季度级工程，中间的产出多半是大批为了数字而写的低价值测试；而「本次 PR 新增的代码必须有测试」是每次都做得到的，而且它保护的正是最可能出错的部分——刚写出来的代码。指标要设在改动上，不要设在存量上。

分支覆盖值得单独开。行覆盖会把 if cond: do_a() 在只测了 cond 为真的情况下报告成 100%，而 cond 为假那条路径从没跑过——恰恰是这类被遗漏的分支最容易藏缺陷。覆盖率工具（coverage.py，pytest 侧通常经 pytest-cov 接入）支持分支模式，开启后这类遗漏会显式列出来。

三层测试的成本收益

▲ 单条成本 / 运行耗时 / 不稳定概率 │ ┌─────────┴─────────┐ │ 端到端 E2E │ 5% 真浏览器、真服务链路 │ 分钟级 / 最易抖 │ 只覆盖最关键的几条主干路径 ┌─┴───────────────────┴─┐ │ 集成 Integration │ 20% 真数据库、真消息队列 │ 秒级 / 偶尔抖 │ 验证组件之间的接线对不对 ┌───┴─────────────────────────┴───┐ │ 单元 Unit │ 75% 纯内存、无外部依赖 │ 毫秒级 / 应当永不抖动 │ 验证逻辑分支与边界 └─────────────────────────────────┘ │ ▼ 数量 / 反馈速度 倒过来的形状（大量 E2E、很少单元）叫冰淇淋筒： 跑得慢、抖得多、失败了还定位不到是哪一层坏的
层级典型占比单条耗时量级能发现什么维护成本
单元约 70%–80%毫秒逻辑错误、边界条件、异常路径低，但锁实现的话会暴涨
集成约 15%–25%百毫秒到秒接线错误：SQL 写错、序列化不一致、配置没生效中，需要管理外部依赖
端到端约 5%秒到分钟整条主干路径是否真的能走通高，最易不稳定

比例不是教条，它是从成本结构推出来的：越往上单条越贵、反馈越慢、越容易因为无关原因失败，所以数量必须越少，只留那些「这条路断了业务就停摆」的场景。特别提醒一点：单元测试之所以能占多数，前提是它真的不依赖外部——如果你的「单元测试」需要连数据库，那它是集成测试，只是名字写错了，成本会按集成测试算在你头上。

不稳定测试必须当故障处理

不稳定测试（flaky）指同一份代码、同一个环境下时红时绿的测试。它的危害不在于偶尔浪费一次 CI，而在于它摧毁红灯的意义：一旦团队养成「红了先重跑一次」的习惯，真实缺陷也会被这一次重跑掩盖过去。用重跑掩盖不稳定，等价于关掉告警。

不稳定来源典型表现处理方式
真实时间跨零点、月末、闰秒前后失败注入可控时钟，禁止在断言里用 now()
随机性几百次里失败一次固定随机种子；随机数据只用于探索性测试并打印种子
并发与时序加机器后变频繁，靠 sleep 勉强稳住等条件成立而不是等固定秒数
共享可变状态单跑通过、全跑失败（或相反）缩小 fixture 作用域，或每条测试事务回滚
外部网络失败集中在某个时间段单元层替掉网络，只在集成层保留少量真调用
集合顺序假设换 Python 版本或换机器后失败断言前显式排序，不依赖任何未承诺的顺序

事故复盘：某服务的 CI 里长期有 7 条不稳定测试，团队的共识是「红了点重跑」，单次重跑约 11 分钟。三个月里累计触发重跑 214 次，折合约 39 小时机器时间，还不算每次等待的人力。真正的代价在第四个月显现：一次发布把一个并发写入的缺陷带上了线，事后回看，那条缺陷其实在合并前连续两次让某条测试变红，都被当成老毛病重跑掉了。此后团队改了规则——不稳定测试当缺陷开单，24 小时内要么修好、要么隔离出主流水线并挂上负责人。三周内 7 条减到 1 条，重跑率从 18% 降到 1% 以下。结论是：允许重跑，就等于把红灯的语义从「出问题了」改成了「可能出问题了」，而后者没有任何执行力。

  • 断言公开行为：返回值、状态变化、抛出的异常类型与结构化字段
  • 多组输入用 parametrize，并用 ids 给每组起可读的名字
  • fixture 默认用函数作用域，确有性能需要再逐个往上提
  • 共享昂贵的连接，但每条测试独占可变数据（如事务回滚）
  • 替身只放在进程边界上：时间、随机、网络、文件系统、消息
  • 用 mock 时默认开 autospec，防签名漂移
  • 覆盖率开分支模式，门禁卡在增量而不是总量
  • 不稳定测试当缺陷开单处理，限期修复或隔离出主流水线
  • 断言内部调用序列、私有方法名、日志与错误提示的文案
  • 把多组输入写进 for 循环断言，失败时看不出是哪一组
  • 为了提速把带可变状态的 fixture 提到 session
  • 把自己的业务对象也换成 mock，测出一套模拟器的行为
  • 用 time.sleep 等待异步结果稳定
  • 把覆盖率百分比当作团队 KPI，催生大批无断言的测试
  • 对偶发失败的处理是「再点一次重跑」
  • 测试里直接用 now()、random()、真实网络地址

一套测试是资产还是负债，看它在重构时的表现：帮你发现真问题的是资产，只跟着实现一起红的是负债。负债该删就删，留着它比没有它更糟——它会持续消耗维护成本，还让人误以为有保护。

Q&A

私有方法要不要单独写测试？
默认不要。私有方法属于实现，为它单独写测试等于把实现钉死，重构时这些测试会第一批变红。正确做法是通过调用它的公开入口间接覆盖到它——如果某条私有分支从公开入口怎么都走不到，那说明它要么是死代码可以删掉，要么就是你的公开接口设计漏了一个场景。有一个例外：某个私有方法承载了独立且复杂的算法（比如一个价格计算规则、一段解析逻辑），而且分支多到从外层构造输入很别扭，这时正确的动作通常不是「给私有方法写测试」，而是把它提取成一个独立的、有自己公开接口的单元，然后正常测它。换句话说，「想测私有方法」这个冲动本身，往往是模块该拆的信号。
一个测试里可以写几个断言？「一个测试一个断言」是硬规矩吗？
不是硬规矩，真正的规矩是「一个测试验证一个行为」。一个行为需要三条断言来完整描述（比如下单后要检查返回状态、库存减少、事件已发出），那就写三条，它们共同构成这一个行为的契约。需要警惕的是另一种情况：一条测试里依次验证了创建、修改、删除三件事，这不是断言多，是场景多——它的问题在于第一段失败后面就不跑了，而且失败时从名字看不出坏在哪一步，应该拆成三条。一个实用的自检：如果你得给测试起名叫 test_order_flow 这种笼统的名字，通常就是塞多了。另外，断言之间如果存在「前一条不成立后一条就没意义」的依赖，放在一起反而是对的，因为拆开只会得到一堆连带失败的噪声。
测试该不该连真实数据库？
分层看。单元层不该连：它的价值在于毫秒级反馈，连库之后耗时涨两三个数量级，而且引入了清理、并发、连接池等一堆和被测逻辑无关的失败原因；这一层用内存版假实现替代仓储即可。集成层应该连真库，而且最好是同一款、同一大版本的真库而不是内存数据库——因为这一层要验证的恰恰是「SQL 写对了吗、事务隔离级别对吗、迁移脚本能跑吗」，换成行为不同的替代品，验证的东西就没了。实践上推荐的组合是：容器在会话级启动一次（昂贵，共享），每条测试在自己的事务里跑完就回滚（廉价，隔离）。这样既有真实性又有确定性，代价通常只是几十秒的启动时间。
覆盖率定到多少合适？80% 是不是行业标准？
80% 这个数字没有任何理论依据，它只是流传广。把总覆盖率设成硬性达标线会直接产生反效果：团队为了达标会写大批「调一下就完、不做任何断言」的测试，覆盖率数字上去了，缺陷发现能力一点没涨，还平白多了一堆要维护的代码。更有效的做法有三条。第一，门禁卡增量覆盖——本次改动新增的行必须被覆盖，存量欠债单独排期还。第二，开分支覆盖，它能暴露「只测了 if 没测 else」这类真实遗漏，信息量比行覆盖高得多。第三，把覆盖率报告当地图用而不是当分数用：定期翻一遍未覆盖的区域，人工判断哪些是「确实不需要测」（样板代码、简单委托），哪些是「危险的空白」（错误处理分支、边界判断），后者才是该补的。
conftest.py 越写越大怎么办？该往里放什么、不该放什么？
判断标准是影响半径。适合放进 conftest 的是「这一层目录下多数测试都需要、且改了之后影响是可预期的」东西：fixture 定义、自定义命令行选项、标记注册、钩子。不适合放的有三类：一是业务构造逻辑（造一个复杂订单对象），它应该放进普通的辅助模块由测试显式 import，这样依赖关系看得见；二是只有一两个文件用得上的夹具，它该下沉到那个文件里；三是带全局副作用的 autouse 设置，除非它确实是全套件的不变量。另一条实用经验：conftest 变大通常不是 conftest 的问题，而是测试目录结构没跟上——按「需要什么环境」重新分目录（unit / integration / e2e），每个目录一个小 conftest，比一个大文件好维护得多。最后注意辅助断言函数如果放在普通模块里，需要显式登记才能享受断言重写。
测试代码需要和生产代码一样讲究质量吗？
需要，但讲究的维度不同。生产代码追求抽象和复用，测试代码追求可读和显式——一条测试最好能自上而下读完就懂，不需要跳到三个辅助函数里拼凑上下文。所以测试里适度的重复是可以接受的，甚至是好的：把三条相似测试抽成一个带五个参数的通用函数，读的人得先在脑子里把参数代回去才能知道这条在测什么，反而更难维护。真正要消除的重复是造数据和装环境这类机械重复，用 fixture 和构造器（给对象造一个带合理默认值的工厂函数）处理。另外有两条纪律和生产代码完全一致：测试里不写 if 和 try（有条件分支说明它在测两件事，该拆），以及测试要能被别人读懂失败原因而不用去读被测代码。
已有一个几乎没测试的老项目，从哪儿开始补？
不要从「把覆盖率刷上去」开始，那是最慢也最没回报的路径。推荐的顺序是四步。第一步，先给最近三个月出过线上故障的那几个模块补测试——历史缺陷密度是未来缺陷密度最好的预测指标。第二步，建立增量门禁：从今天起所有新代码必须带测试，先止血再还债。第三步，在动手重构任何一块代码之前，先给它补一层外围的契约测试——只从公开入口进出、只断言可观察行为，作为重构的安全网；这层测试的特点是写起来快、恰恰因为不碰内部所以重构时不会误伤。第四步，只在真正需要时才往里补细粒度的单元测试。这条路径的关键判断是：补测试的目的不是达标，而是为接下来要做的改动买保险，所以哪块要改就先补哪块，不改的地方可以一直欠着。
