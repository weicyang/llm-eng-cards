这张卡的目标不是教你写元类，而是让你在想写元类的那一刻能准确说出「为什么这次不需要」。Python 在过去十年里把元类的活儿拆给了三个更便宜的工具，真正只能用元类解决的问题，在一个普通业务项目里一年遇不到一次。

一、类也是对象，元类是造类的类

PY09 · 对象模型与引用语义反复强调过一句话：Python 里一切都是对象。这句话有个多数人没有认真兑现的推论——类本身也是对象。你可以把一个类赋值给变量、塞进列表、当参数传递、在函数里现造一个出来。既然类是对象，它就必然是某个东西的实例。那个东西就是元类：负责创建类对象的类，默认是内置的 type。

type 的两副面孔

type 是 Python 里少见的、根据参数个数做完全不同两件事的内置对象。这个设计上的巧合让很多人第一次读元类文档时彻底懵掉：明明 type(x) 是查类型的，怎么突然就开始造类了。

调用形式参数返回它在做什么
type(obj)1 个obj 所属的类查询：等价于读 obj.__class__
type(name, bases, ns)3 个一个新建的类对象创建：这才是元类的本职工作
type(name, bases, ns, **kwds)3 个 + 关键字新建的类对象创建，并把关键字透传给 __init_subclass__

三参形式的三个参数正好对应 class 语句里你写下的三样东西：类名字符串、基类元组、以及类体命名空间——一个把类体里所有名字（属性、方法、嵌套类）映射到值的字典。理解到这一步，class 语句就不再神秘了，它只是一段语法糖。

你写的 解释器实际做的 ─────────────────────── ──────────────────────────────────── class Dog(Animal): ns = {} # ① 备好命名空间 kind = 'canine' exec(类体代码, globals(), ns) # ② 执行类体 def bark(self): # 执行完 ns 里有 kind 和 bark return 'woof' Dog = type('Dog', # ③ 调元类造类对象 (Animal,), ns) # ④ 把 'Dog' 这个名字绑定到该对象 关键认知：类体不是声明，是一段真的会被执行的代码。 你在类体里写 print、写 if、写 for 循环，都会在类创建时跑一遍。
# 这两种写法产生的类没有任何区别
Dog = type('Dog', (Animal,), {'kind': 'canine',
                              'bark': lambda self: 'woof'})

class Dog(Animal):
    kind = 'canine'
    def bark(self):
        return 'woof'

实例 → 类 → 元类这条链

把「实例是类的实例」这句话往上再推一层，就得到了完整的对象层级链。链条在 type 这里自己咬住自己的尾巴——type 的元类还是 type，这是 CPython 在 C 层面直接写死的，不需要也无法用 Python 解释。

默认情形（绝大多数类） 自定义元类的情形 ───────────────────── ────────────────────── dog = Dog() cfg = Config() │ type(dog) 是 │ type(cfg) 是 ▼ ▼ Dog ← 类，也是对象 Config class Config(metaclass=Meta) │ type(Dog) 是 │ type(Config) 是 ▼ ▼ type ← 默认元类 Meta ← 你写的元类 │ type(type) 是 │ Meta 必须继承 type ▼ ▼ type ← 闭环，到顶了 type 两条正交的关系，别混： ──继承──► 决定「属性去哪找」，走 MRO ──实例──► 决定「谁创建了我、我的类级行为从哪来」 Dog 继承 Animal，但 Dog 是 type 的实例。 这两句话同时成立，且互不影响。

最后那段提示是本节最容易搞错的地方。Meta 不是 Config 的基类，Config 的 MRO 里根本没有 Meta；Config 的实例 cfg 也看不到 Meta 上定义的方法。元类上的方法只对类本身可见——这正是第四节要展开的、元类唯一不可替代的价值。

类之于实例，正如元类之于类。class 语句做的全部事情，就是把类体执行成一个字典，然后拿着「名字、基类、字典」三样东西去调一次元类。

二、类创建的完整流程与四个介入点

上一节的三步展开是简化版。真实的 class 语句执行流程有六个阶段，其中四个是留给你的钩子。按发生顺序把它们过一遍，你就能判断任何一个「我想在类创建时干点什么」的需求该挂在哪一步。

class C(B, metaclass=Meta, tag='x') 的完整展开顺序 ────────────────────────────────────────────────── ① 确定元类 显式写了 metaclass= 就用它；否则取所有基类的元类 多个候选元类之间必须有派生关系，否则直接 TypeError │ ▼ ② __prepare__ ← 介入点 1（元类的类方法） Meta.__prepare__('C', (B,), tag='x') 返回一个映射对象 默认返回普通 dict；返回别的映射可以改变类体的记录方式 │ ▼ ③ 执行类体 在 ② 返回的那个映射里执行 class 的缩进块 每个赋值、每个 def 都写进这个映射 │ ▼ ④ Meta.__new__(mcls, 'C', (B,), ns, tag='x') ← 介入点 2 类对象在这里才真正诞生；此刻还能改 ns 和 bases │ │ 以下 ⑤⑥ 嵌在 type.__new__ 内部执行 ├──► ⑤ 逐个 __set_name__ ← 介入点 3（在属性值上） │ 对 ns 里每个提供了该方法的值调用 │ value.__set_name__(owner=C, name='它在类体里的名字') │ └──► ⑥ __init_subclass__ ← 介入点 4（在父类上） 调 C 的「父类」的 __init_subclass__(cls=C, tag='x') 注意：不会调 C 自己定义的那个 │ ▼ ⑦ Meta.__init__(cls, 'C', (B,), ns, tag='x') 类已存在，只能做收尾加工，改不了「怎么造」 │ ▼ ⑧ 名字 C 绑定到该类对象，class 语句结束

把 ⑤⑥ 画进 ④ 里面不是细节强迫症。它意味着：描述符（实现了 __get__ 等协议、用来接管属性存取的对象，本系列 PY17 已展开）的 __set_name__ 和父类的 __init_subclass__ 都早于元类的 __init__。如果你在元类 __init__ 里读某个字段的名字，那时它已经被 __set_name__ 填好了；反过来想在 __set_name__ 里依赖元类 __init__ 的结果，则一定拿不到。

钩子触发时机能改什么典型用途
__prepare__类体执行之前类体使用的命名空间映射本身记录定义顺序、禁止重名、收集声明式 DSL
元类 __new__类对象创建的瞬间类名、基类元组、命名空间字典动态注入基类、重写方法、替换成员
元类 __init__类对象已存在只能改类的属性，改不了它的构造注册、加索引、校验；此处能做的类装饰器都能做
__set_name__类体里每个属性值上，早于元类 __init__属性对象自己（让它知道自己的名字和宿主）描述符自动绑定字段名，不再手写两遍
__init_subclass__每个子类创建完成时刚创建好的子类对象子类注册、必填属性校验、默认值填充
类装饰器整个 class 语句结束之后已完成的类，或换成另一个对象注册、包装方法、加字段；不会作用于子类

这张表按介入时机从早到晚排列，而越晚介入的工具越简单、越安全。这不是巧合：介入得越早，你能破坏的东西越多。第六节的选型路径本质上就是「从表的最后一行往上找，找到第一个能满足需求的就停手」。

__prepare__：唯一只有元类能碰的阶段

Python 3.7 起普通 dict 已经保序，所以「用 __prepare__ 换 OrderedDict 来记录字段顺序」这个教科书例子今天基本失效了。它还有意义的场景是换成一个行为不同的映射——比如一个在重复定义时直接报错的 dict，或者一个会把每次赋值记进日志的 dict。

class NoRedefine(dict):
    def __setitem__(self, k, v):
        if k in self:
            raise TypeError(f'类体里重复定义了 {k}')
        super().__setitem__(k, v)

class Strict(type):
    @classmethod
    def __prepare__(mcls, name, bases, **kw):
        return NoRedefine()

四个钩子按时间排成一条线：__prepare__ 决定「拿什么记」，元类 __new__ 决定「怎么造」，__set_name__ 让属性知道自己叫什么，__init_subclass__ 让父类知道又多了个孩子。需求落在哪一格，答案就在哪一格。

三、__init_subclass__ 是多数需求的答案

如果这张卡只能留下一句话，那就是这一节的标题。__init_subclass__ 在 Python 3.6 引入，它把「每当有人继承我，我想做点事」这个占了元类实际用途八成以上的需求，变成了一个普通方法。它是隐式的 classmethod——你不用写 @classmethod 装饰器，解释器会自动帮你包上，写了也不算错。

它相对元类的三个决定性优势：不需要读者理解元类；不参与 MRO，因此不会引入元类冲突；子类想选择性关掉它只需要自己重定义一个空方法。

插件自动注册：定义即登记 ───────────────────────── class Handler: Handler.registry = {} def __init_subclass__(cls, fmt): Handler.registry[fmt] = cls │ │ 每个子类的 class 语句结束前自动触发一次 ┌───────────────┼───────────────┐ ▼ ▼ ▼ class JsonH class CsvH class XmlH (Handler, (Handler, (Handler, fmt='json') fmt='csv') fmt='xml') │ │ │ └───────────────┴───────────────┘ ▼ registry = {'json': JsonH, 'csv': CsvH, 'xml': XmlH} 与手工注册表的差别只有一处，但很要命： 手工版 写 class + 记得回头改 registry → 两处，会漏 自动版 写 class → 一处，漏不了
class Handler:
    registry = {}
    def __init_subclass__(cls, /, fmt, **kw):
        super().__init_subclass__(**kw)      # 协作调用，别省
        if fmt in cls.registry:
            raise ValueError(f'{fmt} 已被 {cls.registry[fmt].__name__} 占用')
        cls.registry[fmt] = cls

class JsonHandler(Handler, fmt='json'):
    ...

注意两处细节。第一，fmt 是通过 class JsonHandler(Handler, fmt='json') 传进来的，这叫类定义关键字参数——写在基类列表后面的具名参数，解释器会原样转交给元类和 __init_subclass__，是它们专属的传参通道。第二，那行 super().__init_subclass__(**kw) 不能省：继承链上可能有多个类都定义了这个钩子，不转发就会把别人的逻辑吃掉，这和 PY16 · 继承、MRO 与组合优先里讲协作式 super() 的道理完全一致。

三种立刻能用的写法

需求在 __init_subclass__ 里做什么失败时的表现
子类自动注册registry[key] = cls重复 key 时在 import 阶段就抛错，而非运行期覆盖
强制子类声明某属性检查 getattr(cls, 'name', None)，缺失就 raise类定义那一行直接 TypeError，不等到实例化
按子类名生成配置键cls.config_key = to_snake(cls.__name__)子类可显式覆盖，只在未定义时填默认值
class Plugin:
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)
        if not cls.__dict__.get('name'):     # 用 __dict__ 才不会误读到继承来的
            raise TypeError(f'{cls.__name__} 必须定义类属性 name')
        cls.config_key = cls.name.lower()

class Bad(Plugin):      # ← 就在这一行抛 TypeError
    pass

第二行代码里用 cls.__dict__.get 而不是 getattr 是个容易漏掉的点：getattr 会沿 MRO 往上找，孙子类会「继承」到父类填的值从而绕过校验。凡是要校验「这个类自己有没有声明」，都必须查 __dict__。

示例场景：某内容平台的消息处理器用手工注册表维护，handlers.py 里有一个 40 多行的 REGISTRY = {...} 字典。一次迭代中同事新增了 ReceiptHandler 类并写完了全部单测（单测直接实例化类，不走注册表），但忘记回头往字典里加一行。灰度上线后 4 小时内约 2 万条回执消息命中默认分支被静默丢弃，直到对账时才发现。改成 __init_subclass__ 自动注册后，「定义类」和「登记类」合并成了一个动作，这类遗漏在结构上不再可能发生，改动量是删掉 40 行字典、加 5 行钩子。

凡是需求能写成「每当有人继承我，就……」，答案就是 __init_subclass__，不用再往下看了。它便宜、可读、不传染，而且新人不需要额外知识就能看懂。

四、真的需要元类的三种情形

劝退了这么久，也得说清楚元类什么时候确实无可替代。判据只有一条：你要做的事，必须发生在类对象存在之前，或者必须作用于类本身而不是它的实例。符合这一条的，现实中只有三类。

情形一：在类被造出来之前改动它的原材料

类装饰器和 __init_subclass__ 都在类对象已经存在之后才拿到控制权，此时基类元组已经定死、MRO 已经算好、命名空间已经冻结成 mappingproxy。如果你要换掉类体执行时用的映射（__prepare__），或者要根据类体内容动态决定基类，就只能在元类 __new__ 里做——那是最后一个还能改 bases 的时刻。

情形二：给类本身添加行为

这是元类最正当的用途。PY15 · 类与特殊方法契约讲过的那些双下方法，写在元类上时作用对象整个上移了一层：它们是类的方法而不是实例的方法。最典型的是 __call__：拦截 MyClass(...) 这个调用动作本身，从而控制实例是怎么产生的。同理，__instancecheck__ / __subclasscheck__ 让你接管 isinstance() 和 issubclass() 的判定，标准库的 abc.ABCMeta 就是靠这两个方法实现「虚拟子类」的。

为什么「每个类一个单例」只能用元类 ────────────────────────────────── Config() 这个调用发生了什么？ │ ▼ 解释器查 type(Config).__call__ ← 注意：查的是「元类」上的 │ 不是 Config 上的 __call__ ▼ type.__call__(Config) 默认实现： obj = Config.__new__(Config) obj.__init__() return obj 换成自定义元类后： Meta.__call__(cls) 先查 cls.__dict__ 里有没有缓存 有 → 直接返回，__init__ 根本不会被调用第二次 没有 → 走默认流程并缓存 为什么 __init_subclass__ 做不到： 它拿到的是「类创建完成」这一时刻，管不到之后每次「调用」类。 为什么类装饰器做不到： 装饰器能返回一个工厂函数替代类，但那样 isinstance 和继承全废。
class PerClassSingleton(type):
    def __call__(cls, *a, **kw):
        if '_inst' not in cls.__dict__:      # 查 __dict__，子类才能有自己的
            cls._inst = super().__call__(*a, **kw)
        return cls._inst

class Config(metaclass=PerClassSingleton):
    ...
assert Config() is Config()

情形三：框架级的声明式语法

ORM 把 name = CharField() 这样的类体声明翻译成表结构，序列化库把字段声明翻译成校验器——这类库历史上普遍用元类，因为在 3.6 之前确实没有别的办法。但今天它们的现代等价物往往不需要：字段绑定交给 __set_name__，子类注册和校验交给 __init_subclass__，最后的装配交给类装饰器（dataclasses.dataclass 就是这么做的，它一行元类都没用）。

工具介入时机能力上限主要代价会作用于子类吗
__init_subclass__子类创建完成时读写已建好的子类几乎为零，是普通方法会，且自动
描述符 + __set_name__属性值上，类创建中接管单个属性的存取需要理解描述符协议会（属性被继承）
类装饰器class 语句之后改已完成的类，或整个替换掉低；静态工具大多能理解不会，每个类都要单独写
元类类创建的全过程换命名空间、改基类、拦截类调用、改 isinstance高：冲突风险、类型推断失效、阅读门槛会，且强制传染

最右一列值得单独看。元类的「会传染给所有子类」既是能力也是负债：一旦某个基类用了元类，整棵继承树上的每个类都被打上这个元类的烙印，包括那些完全不需要它的类，以及那些将来想同时继承别的库的类。这条性质直接通向下一节。

三句话判断要不要上元类：要改类创建的原材料吗？要让类本身（而非实例）多出行为吗？要控制类被调用的那一刻吗？三个都不是，就不需要元类。

五、元类的真实代价

元类不是「高级但危险」，而是「成本高到在多数场景里不划算」。这三类代价里，第一类是硬性的——你没法通过写得更小心来规避，因为它取决于别人的代码。

元类冲突：无解的那一种

元类冲突指的是解释器无法为一个新类挑出唯一合法元类而拒绝创建它。为一个新类确定元类时，解释器会收集所有基类的元类作为候选，然后要求其中存在一个是其余所有候选的子类。两个互不相干的第三方库各自用了自己的元类，你想同时继承它们，这个条件就不成立。

metaclass conflict 是怎么发生的 ──────────────────────────────── 库 A：class ABase(metaclass=AMeta) AMeta ──继承──► type 库 B：class BBase(metaclass=BMeta) BMeta ──继承──► type AMeta 和 BMeta 互不相识 你写：class Mine(ABase, BBase): ... │ ▼ 候选元类 = {AMeta, BMeta} 规则：必须有一个是其余全部的（非严格）子类 AMeta 不是 BMeta 的子类 ✗ BMeta 不是 AMeta 的子类 ✗ │ ▼ TypeError: metaclass conflict: the metaclass of a derived class must be a (non-strict) subclass of the metaclasses of all its bases 唯一出路（也未必走得通）： class Merged(AMeta, BMeta): pass class Mine(ABase, BBase, metaclass=Merged): ... 前提是两个元类的 __new__ 互相兼容——而它们分属两个 互不知情的库，这个前提你无法保证也无法修复。

请注意这个错误发生在 import 阶段，不是运行期。它没有降级方案，也不能用 try/except 绕过，因为类根本没造出来。这就是「传染性」的实际含义：你选用元类的那一刻，就替所有将来继承这棵树的人做了一个不可撤销的决定。

另外两类代价

症状成因缓解手段
import 时 TypeError: metaclass conflict多继承的基类们元类无派生关系手工合并元类；或改用 __init_subclass__ 从根上避免
IDE 补全不出元类生成的方法/字段成员是运行时动态加的，静态分析看不见补 .pyi 存根或 if TYPE_CHECKING 声明——等于把一份信息维护两遍
类型检查器报「属性不存在」但代码能跑同上，检查器只认源码里写出来的加 # type: ignore，噪声会一路扩散到调用方
栈帧里出现没人写过的文件名元类 __new__ 里构造/包装了函数包装时用 functools.wraps 保住名字；仍改不了栈的层数
改了基类，某个八竿子打不着的子类崩了元类逻辑对所有子类强制生效加覆盖全部子类的测试；成本随子类数量线性增长
继承时 __init_subclass__ 被跳过中间某个类重定义了钩子却没调 super()约定所有钩子首行必须转发 super()

示例场景：某数据服务的基础模型类在早期用元类实现了字段声明与自动注册，全项目 60 多个模型类继承自它。两年后团队要引入一个提供数据校验能力的第三方库，该库的基类同样带元类，合并尝试在 import 阶段就抛 metaclass conflict。可选方案有三个：手写合并元类（评估后发现两边的 __new__ 都会重写 __annotations__，逻辑互相踩）、放弃第三方库自研校验（约 3 人周）、或把基础模型的元类改写成 __init_subclass__ + __set_name__（约 5 人日，但要回归全部 60 个模型）。团队选了第三条。复盘结论是：当初那段元类代码总共 30 行，而它锁死的是整棵继承树未来所有的组合自由。

元类的代价不由写它的人承担，而由两年后那个想把这棵继承树和别的库接在一起的人承担。评估元类时，要算的是这笔未来账，不是眼前那 30 行代码。

六、类装饰器：更好的替代品

类装饰器是一个接收类对象、返回类对象的函数，写在 class 语句上方。它和 PY14 · 可变参数、闭包与装饰器讲的函数装饰器是同一套机制，只是被装饰的对象换成了类。关键区别在时机：它在类完全创建好之后才拿到那个类。

def register(fmt):
    def deco(cls):
        Handler.registry[fmt] = cls
        return cls          # 必须返回！忘了就把类名绑成 None
    return deco

@register('json')
class JsonHandler:
    ...

「必须返回 cls」是这里唯一的坑，而且报错离现场很远：漏写会让类名绑定到 None，直到别处 JsonHandler() 时才抛 TypeError: 'NoneType' object is not callable。

类装饰器能做类装饰器做不到
把类登记进注册表改变类体执行时用的命名空间（那是 __prepare__ 的活）
往类上加方法、属性、字段修改基类元组或影响 MRO 的计算
遍历并包装类里的每个方法（计时、日志、重试）拦截 MyClass(...) 这个调用动作
校验类是否满足某个契约，不满足就报错自动作用于子类——子类要用得自己再写一次
整个替换成另一个对象（dataclass 式重建）影响那些你无法修改源码的类

最后一行的「不会自动作用于子类」通常被写成缺点，其实它是类装饰器可控性的来源：作用范围明确写在那一行 @ 上，读代码的人不用回溯整条继承链就知道这个类被动了什么手脚。同样的透明度也让类型检查器受益——主流检查器对 dataclass 这类常见装饰器有专门支持，而对任意元类基本只能放弃推断。

选型决策路径

从下往上找，命中第一个就停手 ──────────────────────────── 我想在类身上做点什么 │ ├─ 只作用于「这一个类」 ──► 类装饰器 │ 注册 / 加方法 / 包装方法 / 校验 最简单，静态工具能懂 │ ├─ 要自动作用于「所有子类」 ──► __init_subclass__ │ 子类注册 / 必填校验 / 填默认值 写在父类上，继承自动生效 │ ├─ 要管「某个属性」的存取 ──► 描述符 + __set_name__ │ 类型校验 / 惰性计算 / 字段绑定 作用域精确到字段 │ └─ 要改「类被创建的过程本身」 ──► 元类（最后手段） 换命名空间映射 / 动态改基类 拦截类调用 / 改写 isinstance 如果停在了最后一格，先回答三个问题再动手： 1. 这个基类将来会不会和别的库的基类一起被继承？ 2. 团队里有几个人能独立维护这段代码？ 3. 用前三种方案组合起来实现，到底贵多少？ 三个问题答不上来，就说明还不到用元类的时候。

示例场景：某后端服务想给全部 12 个 Repository 类的所有公开方法加耗时埋点。最初的方案是写元类在 __new__ 里遍历命名空间包装函数，代码约 45 行，但 IDE 随即失去了对这些方法签名的补全，且有 2 个类因为已经继承了带元类的 ABC 基类而报冲突。改成一个 18 行的类装饰器后，12 个类各加一行 @timed，签名靠 functools.wraps 完整保留，补全恢复正常，冲突消失。多出来的成本只有那 12 行 @timed——而它们恰好让「哪些类被埋点了」这件事一眼可见。

  • 需求能写成「每当有人继承我，就……」时，一律用 __init_subclass__
  • 钩子首行写 super().__init_subclass__(**kw)，保证协作链不断
  • 校验「这个类自己有没有声明某属性」时查 cls.__dict__，别用 getattr
  • 描述符一律用 __set_name__ 自动拿字段名，不要手写两遍名字
  • 只影响单个类的加工用类装饰器，并记得 return cls
  • 确实要写元类时，让它尽量薄，把业务逻辑留在普通函数里便于单测
  • 为了「显得专业」在业务代码里引入元类——代价会转嫁给两年后的维护者
  • 在公共基类上挂元类，除非确认整棵树永远不会和外部基类组合
  • 用元类批量包装方法：类装饰器同样能做，还不破坏签名和补全
  • 在元类 __init__ 里做本可以放进 __init_subclass__ 的事
  • 指望 __prepare__ 返回 OrderedDict 来保序——3.7 起普通 dict 已经保序
  • 在元类里吞掉异常：类创建失败要让它在 import 阶段就大声报出来

类装饰器改的是「已经造好的类」，元类改的是「造类的过程」。绝大多数需求只需要前者；而当你确信需要后者时，再花十分钟确认一次——通常那十分钟会让你回到前者。

Q&A

类和元类的关系，跟类和基类的关系有什么不同？
这是两条完全正交的关系。基类决定「属性去哪里找」，走的是 MRO 那条线性化链路，Dog 找不到的属性会去 Animal 找。元类决定「这个类是谁创建的、类本身有什么行为」，走的是实例关系那条线，Dog 是 type 的实例。关键推论是：定义在元类上的方法，类的实例看不到。比如元类上定义了 describe()，你只能写 Dog.describe()，写 dog.describe() 会报 AttributeError，因为查找实例属性时根本不会走到元类上去。把这两条线分开画一遍，元类相关的绝大多数困惑都会消失。
__init_subclass__ 为什么不用写 @classmethod？
解释器在创建类时会特殊对待这个名字，如果它是个普通函数就自动包成 classmethod，所以写不写装饰器效果一样。加上 @classmethod 不算错，只是冗余；真正的坑是反过来——有人以为它是实例方法而把第一个参数命名为 self，虽然能跑但会严重误导读者，那个参数拿到的是刚创建好的子类，按惯例应当叫 cls。另外要记住它不会在定义它的那个类自己身上触发，只对子类生效；想对基类自己也做同样的事，得在类定义之后单独调一次，或者改用类装饰器。
元类的 __new__ 和 __init__ 分别该放什么？
分界线是「类对象存不存在」。__new__ 在类对象诞生之前运行，参数里的 bases 和 ns 都还是可修改的普通对象，所以凡是要改类名、改基类元组、增删命名空间里的成员，都必须在这里做。__init__ 拿到的是已经造好的类，此刻 __dict__ 已经变成只读的 mappingproxy，MRO 也算完了，你只能通过 setattr 往上加属性。判断方法很简单：如果你的逻辑在 __init__ 里就能完成，那说明它根本不需要元类，改成类装饰器或 __init_subclass__ 即可，两者能做的事和元类 __init__ 完全重合。
遇到 TypeError: metaclass conflict 该怎么办？
先定位是哪两个元类打架：把每个基类的 type(Base) 打出来，找出彼此没有派生关系的那两个。技术上的解法是造一个同时继承两者的元类，class Merged(AMeta, BMeta): pass，然后显式指定 metaclass=Merged。但这只在两边的 __new__ 逻辑互不冲突时才真的能用——如果它们都要改写 __annotations__ 或都要往命名空间塞同名成员，合并后的行为无法预测，而且你没有权限修改任何一方。所以更现实的路往往是绕开：改用组合而不是多继承，或者把自己这边的元类重写成 __init_subclass__。这个错误发生在 import 阶段，没有降级空间，也不能用 try/except 兜住。
__set_name__ 到底解决了描述符的什么问题？
3.6 之前，描述符没办法知道自己在类体里被赋给了哪个名字，所以只能让使用者手写两遍：age = IntField('age')，左边一遍右边一遍。两遍不一致时不会报错，而是表现为「写进去的值读不出来」这种非常难查的 bug。__set_name__(self, owner, name) 在类创建过程中被自动调用，把宿主类和属性名直接送到描述符手上，于是写成 age = IntField() 就够了。这一个钩子消掉了历史上 ORM 用元类的主要理由之一。它的触发时机嵌在 type.__new__ 内部，早于元类的 __init__，所以元类里读字段名时它已经填好了。
ORM 和序列化库现在还用元类吗？如果不用，改用什么？
仍有不少库保留着元类，但多数是历史包袱而非必需。拆开看，这类库需要的能力有三样：把类体里的字段声明和名字绑定起来、在子类定义时做注册和校验、最后把收集到的信息装配成 __init__ 之类的成员。今天这三样分别对应 __set_name__、__init_subclass__ 和类装饰器，都不需要元类。标准库的 dataclasses 就是最好的证据，它做的事情和一个轻量 ORM 的字段装配高度相似，实现上一行元类都没有。对自己写框架的人来说，结论是：先按这三件工具拆需求，拆不掉的残余再考虑元类，通常残余是空的。
用了元类会让程序变慢吗？
运行期基本不会。元类的代码只在类创建时执行一次，也就是模块被 import 的那一刻，之后创建实例、调用方法都不会再经过它。唯一的例外是元类定义了 __call__ 这类会被持续触发的方法——那时每次 MyClass(...) 都要多走一层 Python 函数调用，在热路径上可能需要留意。比性能更值得担心的是启动时间：如果元类在 __new__ 里做了重活（比如扫描注册中心、读配置文件），而项目里有几十个类继承自它，import 阶段就会明显变慢，且这个耗时藏在 import 里很难被常规性能分析工具归因。所以元类应当尽量薄。
abc.ABCMeta 算不算「应该用元类」的正面例子？
算，而且是标准库里最经得起推敲的一个。它需要接管 isinstance() 和 issubclass() 的判定，才能支持虚拟子类——一个没有继承关系的类，也可以被 register() 声明为某抽象基类的子类，并让 isinstance 认账。这个能力只能通过元类上的 __instancecheck__ / __subclasscheck__ 实现，属于第四节说的「作用于类本身而非实例」。但也正因为 ABC 带着元类，它成了元类冲突最常见的来源之一：一旦你的类同时需要继承 ABC 和另一个带元类的第三方基类，就会撞上冲突。如果只是想要「子类必须实现某方法」这一条约束，用 __init_subclass__ 检查更轻，也不会把元类传染出去。
