乱码从来不是「字符坏了」，而是「有人用 A 编码写下的字节，被另一个人用 B 编码读了回来」。把字符串问题都还原成这一句，你要找的就只剩两个答案：写的时候用了什么编码，读的时候用了什么编码。

一、str 与 bytes：两种完全不同的东西

刚开始写 Python 的人常把 str 和 bytes 当成「同一个东西的两种写法」，就像 int 和 float 那样可以随便混着算。它们不是。这两个类型描述的是文本在两个完全不同阶段的形态，把它们分清楚，是理解本卡片后面所有内容的前提。

str 是码点序列——码点（code point）是 Unicode 给世界上每一个字符分配的唯一编号，比如汉字「中」是 U+4E2D，字母 A 是 U+0041。码点是抽象的，它只回答「这是哪个字符」，完全不管这个字符在硬盘上占几个字节。所以 len("中文") 永远是 2，跟你用什么编码存无关。

bytes 是字节序列——一串 0 到 255 的整数，也就是数据在内存之外的真实存在形式。文件里的内容是字节，网络上传的是字节，数据库存的也是字节。len(b"\xe4\xb8\xad") 是 3，因为它就是三个字节。

转换只有两个方向，而且不能搞反

从 str 到 bytes 叫 encode（编码），从 bytes 到 str 叫 decode（解码）。很多人记不住哪个是哪个，一个好用的记法是：「编码」是把人能读的编进机器的形式，所以 str.encode()；反过来解出来给人看，就是 bytes.decode()。方向搞反的后果很直接：bytes 对象上根本没有 .encode() 方法，Python 3 会立刻抛 AttributeError: 'bytes' object has no attribute 'encode'，连跑都跑不起来。

内存里的世界 边界之外的世界 （程序在思考） （数据在流动） ┌──────────────────────────┐ ┌──────────────────────────┐ │ str │ │ bytes │ │ Unicode 码点序列 │ .encode() │ 字节序列 │ │ │ ─────────► │ │ │ "中" → U+4E2D │ (编码) │ b'\xe4\xb8\xad' │ │ len("中") == 1 │ │ len(...) == 3 │ │ │ ◄───────── │ │ │ 关心「是哪个字符」 │ .decode() │ 关心「怎么存怎么传」 │ └──────────────────────────┘ (解码) └──────────────────────────┘ ▲ ▲ │ │ 这一侧该用 str： 这一侧必然是 bytes： 字符串拼接 / 正则 / 切分 / 比较 磁盘文件的原始内容 业务逻辑里的一切文本处理 socket 收发的数据 HTTP 请求体 / 响应体 数据库的 BLOB 字段 加密、哈希的输入 经验法则：让 bytes 只存在于程序的最外层。 数据一进来就 decode 成 str，要出去了才 encode 成 bytes， 中间所有业务代码只见 str。

上图最后三行是本节真正要带走的东西。这个模式有个通用名字叫「Unicode 三明治」：外层是字节，内层是文本，转换只发生在进出口两个薄薄的边界上。一旦你在业务逻辑中间还在跟 bytes 打交道，就说明某个边界没划干净，后面几乎一定会出乱码。

str 是「意思」，bytes 是「形状」。同一个意思可以有很多种形状，但你必须说清楚用的是哪一种，否则接收方只能猜——而猜错的结果就是乱码。

Python 3 的「不便」换来了什么

Python 2 里 str 本质上是字节串，可以直接和 Unicode 字符串相加，解释器会偷偷帮你用一个默认编码转换。这听起来很方便，但这个默认编码通常是 ASCII，一遇到中文就抛异常——而且抛异常的位置往往离真正出错的地方隔着好几层调用，排查起来极其痛苦。更糟的是有时它不抛异常，只是悄悄产出了乱码。

Python 3 的做法是彻底禁止隐式转换。"a" + b"b" 直接报 TypeError: can only concatenate str (not "bytes") to str。这确实带来了写代码时的一点麻烦：每次跨边界都得显式写 encode 或 decode。但这点麻烦的回报是，编码错误从「运行到某个特定数据时才炸」变成了「写的时候就过不去」。

场景该用的类型为什么
业务逻辑里的文本变量str切分、比较、正则、长度语义都基于字符
open(path) 文本模式读出来的内容strPython 已经按 encoding 参数解码过了
open(path, "rb") 二进制模式bytes原样读取，不做任何解码假设

HTTP 响应体（requests）两者都有resp.content 是 bytes，resp.text 是已解码的 str

表格最后一行值得多说一句。requests 的 resp.text 会根据响应头里的 Content-Type 去猜编码，猜不到时退化成 ISO-8859-1，中文站点上这个猜测经常是错的。所以遇到中文网页乱码，标准做法是自己拿 resp.content 手动 decode("utf-8")，而不是指望它猜对。

二、编码方案：UTF-8 为什么成了默认答案

上一节说码点是抽象的编号，那么「U+4E2D 这个编号，要用哪几个字节写到硬盘上」就需要一套规则。这套规则就是编码——一个从码点到字节序列的映射函数。同一个码点，用不同的编码规则写出来，字节完全不同；这正是乱码的全部来源。

历史上出现过很多套规则。ASCII 只管 128 个字符，一个字节搞定，但装不下任何非英文字符。各国于是各搞一套：中文大陆有 GBK，台湾有 Big5，日本有 Shift-JIS，欧洲有一堆 ISO-8859-x。结果是同一份字节在不同地区的机器上打开显示不同的内容，跨国传文件几乎必然出问题。Unicode 的出现统一了「编号」这一层，而 UTF-8 统一了「字节怎么写」这一层。

一个字到底占几个字节，取决于编码

编码「中」占几字节「A」占几字节兼容 ASCII现在还该用吗
ASCII存不下，直接报错1就是它本身只在确定全英文时
GBK / GB1803021是只在对接老系统时
Big521是只在对接繁体老系统时
UTF-831是默认就选它
UTF-162（另加 2 字节 BOM）2否Windows API、Java 内部，自己别选
UTF-3244否几乎不用，太浪费
Latin-1 / ISO-8859-1存不下1是不要用，但要认得它

这张表里有两个容易被忽略的实用结论。第一，UTF-8 下一个中文占 3 字节而 GBK 只占 2，所以同一篇中文文档存成 UTF-8 会比 GBK 大约 50%；这在存几 GB 日志时是真实成本，但绝不值得为此换回 GBK。第二，UTF-16 下连英文字母都要 2 字节，所以纯英文内容用 UTF-16 反而比 UTF-8 大一倍。

UTF-8 是变长编码，这是它赢的关键

变长编码的意思是：不同字符占用的字节数不一样，由第一个字节的高位比特告诉解码器「这个字符总共几个字节」。这个设计让 UTF-8 同时拿到了两个原本矛盾的好处——英文只占 1 字节所以不浪费空间，同时又能表示全部一百多万个 Unicode 码点。

UTF-8 的字节布局：第一个字节的前缀就是「长度说明书」 码点范围 字节数 二进制布局（x 是实际数据位） ───────────────────────────────────────────────────────────────── U+0000 – U+007F 1 0xxxxxxx ▲ 最高位是 0 → 和 ASCII 完全一样 U+0080 – U+07FF 2 110xxxxx 10xxxxxx U+0800 – U+FFFF 3 1110xxxx 10xxxxxx 10xxxxxx ▲ 常用汉字都落在这一档 → 3 字节 U+10000 – U+10FFFF 4 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx ▲ emoji、生僻字在这一档 → 4 字节 拿「中」（U+4E2D）走一遍： 码点 0x4E2D = 0100 1110 0010 1101 （16 位，落在 3 字节档） 套模板 1110xxxx 10xxxxxx 10xxxxxx 填进去 11100100 10111000 10101101 十六进制 E4 B8 AD 所以 "中".encode("utf-8") == b'\xe4\xb8\xad' 这个前缀设计带来两个免费的好处： 1. 后续字节一律以 10 开头，绝不会和首字节混淆 → 从字节流中间任意位置开始，也能往前找到字符边界（自同步） 2. 所有 ASCII 字符编码后仍是原来那一个字节 → 老的 C 程序按字节找 '/' 或 '\n' 依然正确，不用改一行代码

第 2 条是 UTF-8 在工程上真正压倒 UTF-16 的原因。上世纪写的无数程序（文件系统、HTTP 协议解析、各种命令行工具）都假设文本是字节流，并且假设 0x2F 就是斜杠。UTF-8 保证了这个假设永远成立，于是这些程序一行不改就能处理中文。UTF-16 做不到——它把 A 编码成 0x00 0x41，那个 0x00 会被当成 C 字符串的结束符，整个生态要推倒重来。

UTF-8 赢不是因为它最优雅，而是因为它对已经存在的一切最友好：英文不变大，ASCII 不改动，老程序不用重写。技术选型里，兼容性的权重往往高于理论上的完美。

这件事会一路影响到数据库

「一个中文占 3 字节」不是理论知识，它会具体地咬人。MySQL 的 VARCHAR(50) 在字符语义下能存 50 个字符，但底层为它预留的字节数要按最坏情况算；更麻烦的是 MySQL 早年的 utf8 字符集其实是阉割版，每个字符最多 3 字节，装不下 4 字节的 emoji，插入时会直接报 Incorrect string value: '\xF0\x9F\x98\x80'。真正完整的 UTF-8 在 MySQL 里叫 utf8mb4。

示例场景：某内容平台的用户昵称字段建表时用了 VARCHAR(20) CHARACTER SET utf8，上线后约 3.2% 的注册请求失败，日志里全是 Incorrect string value。原因是这批用户在昵称里用了 emoji，而 emoji 是 4 字节字符，旧 utf8 只支持 3 字节。迁移到 utf8mb4 后失败率归零，代价是该字段索引的最大长度从 255 字符降到 191 字符，不得不额外指定前缀索引。这件事的教训是：建表时把字符集写成 utf8mb4 是零成本的，事后迁移则要停机改表。

顺带说一句 BOM。BOM（Byte Order Mark，字节序标记）是文件开头的一个隐形标记，UTF-8 本来不需要它（UTF-8 没有字节序问题），但 Windows 记事本习惯加上 \xef\xbb\xbf 三个字节。后果是你用 encoding="utf-8" 读这种文件时，第一行开头会多出一个看不见的 \ufeff 字符，导致 CSV 的第一个列名匹配不上、JSON 解析直接失败。解法是改用 encoding="utf-8-sig"，它会自动吃掉 BOM；这个编码名对没有 BOM 的普通 UTF-8 文件同样安全。

三、两类 Unicode 报错的读法

Python 里跟编码有关的报错只有两个名字，而它们的区别就藏在名字里：一个是 Decode（解码，bytes → str），一个是 Encode（编码，str → bytes）。看到报错先读这个词，就知道当前卡在哪个方向上，排查范围立刻缩小一半。

UnicodeDecodeError ── 发生在「读进来」的方向 ───────────────────────────────────────────────────────── 文件/网络的字节 用错误的编码去解 结果 b'\xd6\xd0' ──► decode("utf-8") ──► ✗ 报错 ↑ 这是 GBK ↑ 却按 UTF-8 解 0xd6 在 UTF-8 里 的「中」 是非法的起始字节 b'\xd6\xd0' ──► decode("gbk") ──► ✓ "中" 更阴险的情况：字节碰巧「合法」但意思全错 b'\xe4\xb8\xad' ─► decode("gbk") ──► ✓ "涓" + 半个字 ↑ UTF-8 的「中」 不报错，直接产出乱码 UnicodeEncodeError ── 发生在「写出去」的方向 ───────────────────────────────────────────────────────── 内存里的字符 目标编码装不下 结果 "中" ──► encode("ascii") ──► ✗ 报错 ASCII 只有 128 个位置 "😀" ──► encode("gbk") ──► ✗ 报错 GBK 字符集里没有 emoji "中" ──► encode("utf-8") ──► ✓ b'\xe4\xb8\xad' 一句话定位：报错里出现 Decode 就去查「输入是什么编码」， 出现 Encode 就去查「输出通道支持什么编码」。

注意中间那个「不报错但结果全错」的情况。它比报错危险得多——报错至少会让流程停下来，而 GBK 恰好能把 UTF-8 的中文字节解读成另一串合法汉字，程序会一路正常跑到底，直到有人看见页面上的「涓枃」才发现。这也是为什么不应该用「能不能跑通」来判断编码对不对。

errors 参数的三种策略，各有各的代价

encode 和 decode 都接受一个 errors 参数，决定遇到处理不了的字符时怎么办。默认是 strict，也就是抛异常。很多人被异常烦到之后会随手改成 ignore，这个动作看起来「解决」了问题，实际上只是把错误从「响亮的报错」变成了「安静的数据丢失」。

策略行为代价什么时候可以用
strict（默认）抛 UnicodeError流程中断绝大多数场景，数据正确性优先
ignore把处理不了的字符直接丢掉静默丢数据，且无法恢复、无法察觉几乎没有；只在丢几个字符也无所谓的日志清洗里
replace解码时换成 \ufffd（�），编码时换成 ?数据仍然损坏，但损坏痕迹是可见的展示类场景，宁可显示乱码也不要整页 500
backslashreplace换成 \xd6 这样的转义文本内容变长、变丑调试时想看清到底是哪些字节出了问题
surrogateescape把非法字节映射到保留码点，编码回去时能还原这些「字符」不能参与正常文本处理处理文件名等「必须原样还原」的字节

如果一定要在 ignore 和 replace 之间选，永远选 replace。理由很简单：replace 留下了 � 这个肉眼可见的记号，有人会注意到并报告；ignore 什么痕迹都不留，数据就这么少了一块，可能几个月后才在对账时暴露。

示例场景：某团队用一个每日脚本导入外部合作方的商品 CSV，脚本里写的是 content.decode("utf-8", errors="ignore")——这行代码是三个月前为了「让报错的那天能跑完」临时加的。合作方后来把导出格式换成了 GBK，于是每一行里的中文字节都被逐字节丢弃，只剩下逗号和数字。脚本每天照常报告「成功导入 12,480 条」，但商品名字段全部为空。问题在 47 天后由运营发现，期间累计约 58 万条记录需要重跑。如果当初保持 strict，第一天就会因为异常而告警，修复成本是 1 行代码。errors="ignore" 换来的不是稳定，是把故障延后到更贵的时候。

报错是系统在帮你干活。把 strict 改成 ignore，不是修好了问题，只是辞退了那个唯一会告诉你出事了的员工。

最后补一个实践建议：读文件时永远显式写 encoding。Python 3.15 起文本模式的默认编码将统一为 UTF-8（PEP 686），但在那之前，Windows 上 open(path) 的默认编码取决于系统区域设置，简体中文 Windows 上通常是 GBK。这正是「我这跑得好好的，到你机器上就 UnicodeDecodeError」的标准剧本。文件读写的完整讨论在 PY07。

四、f-string：格式化的默认选择

把变量拼进字符串这件事，Python 历史上给过三套方案，而它们至今都还能用，所以初学者经常在教程里看到三种写法而不知道该学哪个。答案很明确：写新代码一律用 f-string，另外两种只需要认得。

最早是 % 运算符，从 C 的 printf 继承来的，写作 "名字是 %s，年龄 %d" % (name, age)。它的问题是参数和占位符靠位置对应，多一个少一个就报错，而且 %s / %d 的类型必须和实参对上。接着是 str.format()，用 {} 占位并支持命名参数，比 % 好但依然啰嗦——变量名要在括号里再写一遍。3.6 引入的 f-string 把表达式直接写进字符串，既短又不会错位，而且因为是编译期就展开成字节码，速度也是三者里最快的。

name, score = "小林", 92.456

"%s 得了 %.1f 分" % (name, score)          # 老写法，靠位置
"{} 得了 {:.1f} 分".format(name, score)     # 中间过渡
f"{name} 得了 {score:.1f} 分"               # 首选：'小林 得了 92.5 分'

f-string 的 f 可以理解成 format。冒号前面写「要显示什么」，冒号后面写「显示成什么样」——所有格式化能力都挤在这个冒号右边。

格式规格迷你语言速查

格式规格迷你语言，指的就是冒号右边那串符号的语法。它的完整形式是 [填充字符][对齐][正负号][#][0][宽度][分组符][.精度][类型]，听起来吓人，但日常用到的就下面这几个。

其中 {:,.2f} 和 {:.1%} 是做报表和监控面板时用得最多的两个，建议直接背下来。注意 .1% 会自动把 0.0837 乘以 100 再加百分号，不要自己先乘一遍。

两个专门为调试准备的写法

冒号左边还可以跟一个转换标记：!r 表示用 repr() 而不是 str() 来渲染这个值。区别在于 repr 会保留引号和转义符，所以 f"{s!r}" 打印空字符串时显示 ''，打印带尾随空格的字符串时显示 'abc '——这两种情况用普通 f"{s}" 是看不出来的。调试「为什么这个值匹配不上」时，加个 !r 经常一眼就能看出是多了空格还是多了换行。

更省事的是 3.8 引入的自文档写法 f"{变量名=}"，它会把表达式原文和值一起打出来，并且默认使用 repr：

user, total = "小林", 1234.5

print(f"{user=}, {total=}")      # user='小林', total=1234.5
print(f"{total * 0.8 = :,.2f}")  # total * 0.8 = 987.60

第二行展示了它能带表达式和格式规格，等号左边原封不动地照抄你写的算式。这个写法专门用来替代那种「print 一堆变量却分不清谁是谁」的调试代码，比手写 print("total:", total) 更短也更不会写错标签。

3.12 放宽了引号限制

在 3.12 之前，f-string 内部不能使用和外层相同的引号，所以 f"{d["key"]}" 是语法错误，必须写成 f"{d['key']}"，嵌套一多就得来回换引号。3.12 起 f-string 由专门的语法解析（PEP 701），内层可以随意使用同类引号，反斜杠也能出现在表达式部分了。不过要注意：这是 3.12+ 独有的，如果你的代码还要在 3.11 上跑，写了会直接语法错误，团队里统一版本之前最好还是保持换引号的老习惯。关于版本选择的权衡，可以回看 PY01 · Python 环境与解释器。

五、常用方法与拼接的性能

字符串方法有几十个，但日常真正高频的就那么六七个。这一节先把它们的正确用法过一遍，然后重点讲一个几乎每个初学者都会写错、而且错得代价很大的地方：循环里拼字符串。

高频方法与它们的坑

方法做什么容易搞错的地方

为什么循环里 += 拼字符串是 O(n²)

Python 的字符串是不可变对象——一旦创建，内容就不能修改。所以 s += "x" 这行代码实际做的不是「在 s 后面追加」，而是「分配一块新内存，把 s 的全部内容复制过去，再把 x 接上，最后让变量 s 指向这块新内存」。原来那块内存等着被回收。

s = ""；循环 5 次，每次 s += "ab" ───────────────────────────────────────────────────────────── 第 1 次 新建长度 2 的对象 复制 0 字符 + 写入 2 [ab] 第 2 次 新建长度 4 的对象 复制 2 字符 + 写入 2 [abab] 第 3 次 新建长度 6 的对象 复制 4 字符 + 写入 2 [ababab] 第 4 次 新建长度 8 的对象 复制 6 字符 + 写入 2 [abababab] 第 5 次 新建长度 10 的对象 复制 8 字符 + 写入 2 [ababababab] ─────────────────── 累计复制 0+2+4+6+8 = 20 字符 n 次循环累计约 n² → O(n²) n = 100,000 时，累计复制量约 100 亿字符级别， 而最终结果只有 20 万字符。99.99% 的工作是在搬运中间产物。 ''.join(parts) 的做法 ───────────────────────────────────────────────────────────── 步骤 1 遍历列表，把每段的长度加起来 → 总长 10 步骤 2 一次性申请长度 10 的内存 步骤 3 依次把每段复制进去，每个字符只被复制一次 parts = ["ab","ab","ab","ab","ab"] │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ [ a b a b a b a b a b ] ← 一块内存，一趟写完 累计复制 = 结果长度 = O(n)。这就是全部区别。

需要说明的是，CPython 对「字符串只有一个引用」的场景做过一个特判优化，某些情况下 s += x 可以原地扩展而不复制。但这个优化很脆弱：只要那个字符串还被别的变量引用着，或者你换了个 Python 实现（比如 PyPy），优化立刻失效，性能悄悄退回 O(n²)。依赖一个「可能生效」的实现细节不是好习惯，何况 join 写法本身也更短。

示例场景：一个导出脚本要把 20 万行记录拼成 CSV 文本，最初写法是在 for 循环里 text += line + "\n"，实测耗时约 46 秒，且内存峰值接近 1.8 GB（大量短命的中间字符串导致 GC 压力）。改成先 lines.append(line)、循环结束后 "\n".join(lines)，耗时降到约 0.09 秒，内存峰值约 120 MB。改动 2 行，性能差约 500 倍。这个差距不是常数级的调优，而是复杂度从 O(n²) 降到 O(n)——数据量越大差距越夸张，所以小数据量的测试根本发现不了这个问题。

循环里别拼字符串，先往列表里塞，出了循环再 join。这是一条不需要判断场景的规则——数据量小的时候它不会更慢，数据量大的时候它救命。

同样的道理适用于往文件里写：不要拼出一个巨大的字符串再一次写入，直接在循环里 f.write(line) 就好，文件对象自带缓冲。还有一个常被忽略的点是 join 的参数可以是生成器，"".join(f"{x}," for x in data) 这种写法能避免先把整个列表物化在内存里。

六、原始字符串、多行字符串与路径

普通字符串里，反斜杠是转义符的开头：\n 是换行，\t 是制表符，\\ 才是一个真正的反斜杠。这个规则在写英文散文时完全没问题，但一遇到两类内容就变成灾难——正则表达式和 Windows 路径，因为它们本身就大量使用反斜杠。

原始字符串：让反斜杠回归字面意思

在引号前加一个 r，字符串就变成原始字符串（raw string），里面的反斜杠不再触发转义，原样保留。这不是「新语法」，只是告诉解析器少做一步处理。

你写的实际得到的内容会发生什么
"C:\\Users\\name"C:\Users\name正确，但双反斜杠读起来费劲
"C:\Users\name"C:\Users + 换行 + ame\n 被当成了换行符，路径直接不存在
r"C:\Users\name"C:\Users\name正确且清晰，推荐
"\d+"Python 3.12+ 会发 SyntaxWarning\d 不是合法转义，靠「碰巧保留」工作
r"\d+"\d+正则的标准写法，永远这么写
r"C:\Users\"语法错误原始字符串不能以单个反斜杠结尾

表格第二行是那类「代码看起来完全正常、报错却毫不相关」的事故。"C:\Users\name" 里的 \U 在 Python 3 中会被当作 Unicode 转义的开头，直接抛 SyntaxError: (unicode error) 'unicodeescape' codec can't decode bytes；而 "D:\data\new\test.txt" 这种则更阴险——它能正常通过语法检查，但 \n 和 \t 变成了真的换行和制表符，运行时报 FileNotFoundError，而报错信息里打印出来的路径看起来还断成了好几行，让人一头雾水。

写正则和写 Windows 路径，第一个字符先敲 r。这个习惯的成本是一个字母，避免的是一整类「代码看着对、运行就是找不到文件」的事故。

三引号多行字符串与缩进

三个引号包起来的字符串可以跨行，换行符会被原样保留，常用于 SQL、帮助文本、提示词模板。它唯一的麻烦是缩进：为了让代码好看，你会把内容跟着函数体一起缩进，而那些缩进空格会真的进到字符串里。

import textwrap

def build_sql():
    sql = """
        SELECT id, name
        FROM users
    """
    return textwrap.dedent(sql).strip()

textwrap.dedent 会找出所有非空行共有的最短前导空白并统一去掉，正好解决这个问题。注意它只处理「公共」缩进，所以内部的层级缩进会被保留下来。另外它对制表符和空格混用的情况判断很严格，文件里缩进风格不统一时可能一个字符都去不掉。

路径不该用字符串拼

手工拼路径的问题不止是分隔符方向（Windows 是 \、Linux 是 /），更常见的是重复或缺失的分隔符：base + "/" + name 在 base 本身以斜杠结尾时会产出 a//b，某些系统能容忍，某些 API 不能。pathlib 用 / 运算符重载来做拼接，这些细节全部由它处理。

from pathlib import Path

p = Path("data") / "2026" / "report.csv"   # 自动用当前系统的分隔符
p.suffix        # '.csv'      ← 不用自己 split('.')
p.stem          # 'report'    ← 不用自己 strip('.csv')（那还会出错）
p.read_text(encoding="utf-8")              # 顺手把编码也显式写上

p.stem 这一行顺便回收了上一节的坑：想拿到不带扩展名的文件名，正确工具是 Path.stem，而不是 strip(".csv")。pathlib 还有个好处是 Path 对象可以直接传给几乎所有接受路径的标准库函数，不需要再 str() 一次。

  • 所有 open() 显式写 encoding="utf-8"，带 BOM 的文件用 utf-8-sig
  • 让 bytes 只出现在程序最外层，进来就 decode、出去才 encode
  • 正则和 Windows 路径一律用 r"..." 原始字符串
  • 循环里往列表 append，出循环后用 "".join() 拼接
  • 去固定前后缀用 removeprefix / removesuffix，取扩展名用 Path.suffix
  • 金额和比例用 {:,.2f} 和 {:.1%}，别手写乘 100 和插逗号
  • 调试打变量用 f"{x=}"，看不见的空格用 f"{x!r}" 照出来
  • 建表字符集写 utf8mb4，从第一天就支持 emoji
  • 用 errors="ignore" 压掉编码报错——那是在静默丢数据
  • 写 "C:\Users\name" 这种不加 r 的 Windows 路径
  • 用 strip(".txt") 去扩展名，它删的是字符集合不是子串
  • 在 for 循环里用 += 拼字符串
  • 调用 s.replace(a, b) 却不接收返回值，以为原字符串会变
  • 用 resp.text 直接读中文网页，它的编码是猜的
  • 依赖 open() 的平台默认编码，在 Windows 上那是 GBK
  • 把 str 和 bytes 混在同一个业务变量里传来传去

这一整张卡片可以压缩成两条纪律：编码永远显式写出来，反斜杠永远用原始字符串。剩下的问题基本都是这两条没做到的衍生品。

Q&A

encode 和 decode，到底哪个是哪个方向？
encode 是 str → bytes，decode 是 bytes → str。记法是把「编码」理解成「把人读的文字编进机器的存储形式」，所以是从 str 出发，方法挂在 str 上；反过来从机器形式解出人能读的内容就是 decode，方法挂在 bytes 上。好消息是这个方向搞反了不会产生隐蔽 bug——bytes 对象上压根没有 encode 方法，写错会立刻抛 AttributeError。真正需要小心的不是方向，而是编码名字：decode() 不传参数时默认按 UTF-8 解，如果数据其实是 GBK，就会报错或者悄悄产出乱码。
为什么同一个中文字符，有人说占 2 字节有人说占 3 字节？
因为他们说的是不同的编码。字符本身没有「大小」，只有在被某种编码写成字节之后才有。「中」这个字在 GBK 下是 2 字节，在 UTF-8 下是 3 字节，在 UTF-32 下是 4 字节，而在 Python 内存里它作为 str 的一个码点，len() 就是 1。说「2 字节」的人通常背景是早年的 GBK 环境或者 Java/Windows 的 UTF-16 世界，说「3 字节」的人在说 UTF-8。实践中的影响是：估算文件大小、设计数据库字段长度、计算网络传输量时，必须先明确编码，否则算出来的数字可能差 50%。
读文件报 UnicodeDecodeError，第一步该做什么？
先确认文件的真实编码，而不是急着改 errors 参数。最快的办法是用二进制模式读前几百字节看一眼：open(path, "rb").read(200)，如果开头是 \xef\xbb\xbf 就是带 BOM 的 UTF-8，改用 utf-8-sig；如果中文部分是 \xd6\xd0 这种两字节一组的模式，基本是 GBK；如果是 \xe4\xb8\xad 这种三字节一组，那就是 UTF-8，报错可能出在文件的其他位置。不确定时可以装 chardet 或 charset-normalizer 做概率探测，但探测结果只能作为参考，最终要和数据提供方确认。绝对不要用 errors="ignore" 绕过去，那只是把报错换成了静默的数据丢失。
errors="ignore" 和 errors="replace" 差别有那么大吗？
差别在于错误是否留下痕迹，这在工程上是决定性的。ignore 把处理不了的字符直接删掉，产出的字符串看起来完全正常，没有任何迹象表明有内容丢失，也无法从结果反推原本是什么。replace 会留下 � 这个显眼的记号，用户会看见、会截图报障，监控也可以对这个字符做告警。同样是数据损坏，一个是可发现的，一个是不可发现的。运维上有句话叫「响亮的失败好过安静的错误」，这两个参数正好是这句话的教科书例子。如果实在必须容错，选 replace；如果需要原样还原原始字节（比如处理文件名），用 surrogateescape。
f-string、.format()、% 三种格式化，现在还要学后两种吗？
写新代码只用 f-string，但要能读懂另外两种，因为老代码和很多库的文档里还在用。% 是最老的写法，靠位置对应参数，容易错位；.format() 支持命名参数但需要把变量名写两遍。f-string 在 3.6 引入，把表达式直接嵌进字符串，最短、最不容易错，而且因为在编译期就展开成字节码，运行时也最快。有两个例外场景仍然需要 .format()：一是模板字符串要先定义、稍后才填值（f-string 在定义那一刻就求值了）；二是日志，logging 推荐写 logger.info("x=%s", x) 这种延迟格式化形式，这样在日志级别不输出时可以省下格式化的开销。
循环里用 += 拼字符串，为什么说是 O(n²)？
因为 Python 字符串是不可变对象，s += x 无法在原地追加，只能新建一个足够长的对象、把 s 的全部内容复制过去、再接上 x。第 k 次循环要复制之前累积的所有内容，于是总复制量是 1+2+3+…+n，也就是 O(n²)。而 "".join(parts) 先遍历一遍算出总长度，一次性申请内存，每个字符只被复制一次，是 O(n)。数据量小时两者都快，看不出区别；到十万行级别就可能是几十秒和零点几秒的差距。需要补充的是 CPython 对「引用计数为 1 的字符串」做过原地扩展的特判优化，所以你有时会测出 += 并不慢——但这个优化随时可能因为多一个引用或换个解释器实现而失效，不能依赖。
strip() 为什么没有去掉我要去的那个后缀？
因为 strip 的参数是「字符集合」而不是「子串」。"test_data.txt".strip(".txt") 的含义是「从两端反复删除字符，只要它属于 {'.', 't', 'x'} 这个集合」，所以开头的 t 被删、结尾的 .txt 连同前面的 a 之后的部分一路被啃，最终得到 'es_da'。这个 bug 特别隐蔽，因为对某些文件名（比如 report.txt）结果碰巧是对的，测试很容易漏掉。正确工具是 3.9 引入的 removesuffix(".txt") 和 removeprefix()，它们严格按子串匹配，不匹配就原样返回。如果处理的是文件路径，更好的选择是 Path(name).stem。不带参数的 strip() 去除两端空白则完全没有这个问题，可以放心用。
Windows 上打印中文或 emoji 报 UnicodeEncodeError，怎么彻底解决？
这个报错的原因不在你的字符串，而在输出通道：Windows 终端的默认编码历史上是 GBK（代码页 936），而 GBK 字符集里没有 emoji，所以编码不出去。最省事的根治办法是设置环境变量 PYTHONUTF8=1，它会开启 Python 的 UTF-8 模式，让标准输入输出和文件默认编码全部走 UTF-8；也可以用更精准的 PYTHONIOENCODING=utf-8，只影响标准流。在 Docker 里则通常需要同时设 LANG=C.UTF-8，因为容器基础镜像常常没有配置任何 locale。临时验证时可以在终端里执行 chcp 65001 切到 UTF-8 代码页。要避免的做法是在代码里给每个 print 加 errors="ignore"，那样中文会被静默吞掉，问题看似消失实则更糟。
什么时候该用原始字符串 r"..."，它有什么限制？
两个场景必用：写正则表达式，以及写 Windows 路径。正则里的 \d、\s、\b 都以反斜杠开头，不加 r 就要写成 "\\d"，而且 \d 在 Python 3.12 起会触发 SyntaxWarning。Windows 路径里的 \n、\t、\U 会被当成转义序列，轻则路径断成多行导致 FileNotFoundError，重则直接抛 SyntaxError。原始字符串有一个明确限制：不能以奇数个反斜杠结尾，r"C:\dir\" 是语法错误，因为解析器仍然认为最后那个反斜杠在转义引号。这种情况可以写成 r"C:\dir" + "\\"，或者更好的做法是根本不手写路径，改用 pathlib.Path 来拼。
为什么大家都建议用 pathlib 而不是字符串拼路径？
手工拼路径要同时处理好几件容易出错的事：分隔符方向在 Windows 和 Linux 上不同；base + "/" + name 在 base 已经以斜杠结尾时会产生 a//b；取扩展名、取父目录、判断绝对路径都得自己写切分逻辑，而这些切分逻辑正是 strip(".txt") 那类 bug 的温床。pathlib.Path 用 / 运算符做拼接，自动使用当前系统的分隔符并归一化多余的斜杠，还提供 .suffix、.stem、.parent、.exists() 这些语义明确的属性和方法。它返回的对象可以直接传给标准库里几乎所有接受路径的函数，不需要转回字符串。唯一要注意的是拼接绝对路径时 Path("/a") / "/b" 会得到 /b，右边的绝对路径会覆盖左边，这个行为和字符串拼接不同。
