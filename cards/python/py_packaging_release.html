发包的难点从来不在那几条命令。你交出去的是一份长期承诺：一个版本号一旦发出就永久占用，一个默认参数一旦改了，下游就会在某个半夜报错。先想清楚承诺的是什么，再去想怎么构建。

一、两种分发格式：源码包与轮子

同样一句 pip install，有时几百毫秒就装完，有时要等几十分钟、最后以一大段编译器报错收场。差别不在网速，而在索引上给你的是哪一类文件。这件事值得先讲清楚，因为它同时解释了「装别人的包为什么慢」和「我发的包为什么让别人装得慢」。

一个发布版本在索引上通常有两类文件。源码分发包（source distribution，习惯简称 sdist）是一个 .tar.gz 归档，内容基本就是原样的源码，外加一个存放项目元数据的 PKG-INFO 文件。轮子（wheel）是一个 .whl 结尾的 ZIP 归档，里面装的正好是安装时需要拷过去的那些文件，外加一个 .dist-info/ 目录存放元数据（METADATA）、归档自身信息（WHEEL）和带哈希的文件清单（RECORD）。

这里有个常被误解的关键点：安装器从不直接「安装」sdist。sdist 的构建过程是自由的——它可以做任何变换，包括编译 C 扩展、生成代码——所以安装器只能先按 sdist 里声明的构建后端把它造成一个 wheel，再安装这个 wheel。「装 sdist 很慢」不是因为解压慢，是因为中间多了一次完整的构建。

pip install mypkg —— 索引上同一个版本，两类文件 ──────────────────────────────────────────────── 找到匹配的 wheel 只有 sdist（或 wheel 都不匹配本平台） mypkg-1.2.0-py3-none-any.whl mypkg-1.2.0.tar.gz │ │ ▼ ▼ 解压 ZIP，按 RECORD 清单 读 sdist 里声明的构建后端 摊到 site-packages 建隔离环境装上后端 │ 调后端的 build_wheel 钩子 │ （可能要编译 C / Rust 扩展） │ │ ▼ ▼ 几百毫秒，不需要编译器 几十秒到几十分钟，需要完整工具链 在没装工具链的机器上直接失败 │ ▼ 得到 wheel，再走左边那条路

结论是两类都要发，这也是官方打包指南的明确建议。只发 sdist，每个下游的每次容器构建都要现场造一遍轮子；只发 wheel，下游打包者和不在你覆盖范围内的平台就没有退路。

轮子文件名里编码了什么

轮子的文件名不是给人看的标签，而是一份机器可读的兼容性声明——安装器靠解析它来判断「这个文件能不能装在我这台机器的这个解释器上」。文件名末尾三段合称兼容性标签（compatibility tags）。

轮子文件名的形状（中间的 build tag 可选，日常基本不用） {distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl └──────── 合称 compatibility tags ────────┘ 例一：纯 Python 包 mypkg-1.2.0-py3-none-any.whl │ │ └─ platform tag: any → 不依赖操作系统与 CPU 架构 │ └────── abi tag: none → 不依赖 C 层 ABI └─────────── python tag: py3 → 任何 Python 3 实现，CPython / PyPy 都行 一个文件就覆盖了所有平台、所有 Python 3 版本 例二：带 C 扩展的包 fastthing-2.1.0-cp312-cp312-manylinux_2_17_x86_64.whl │ │ └─ glibc 2.17 及以上的 Linux，x86_64 架构 │ └─────── CPython 3.12 的 ABI └───────────── CPython 3.12 专用 「Python 版本 × 操作系统 × CPU 架构」每一个组合都得单独构建一个文件

纯 Python 项目因此有个很实在的便利：py3-none-any 这一个轮子就够了，不需要构建矩阵。习惯上把这种覆盖面最广的轮子叫「通用轮子」——严格说历史上 universal 特指同时兼容 Python 2 和 3 的 py2.py3-none-any，现在已经没有意义了，但说法留了下来。

还有一个细节解释了为什么纯 Python 轮子能这么通用：轮子里不包含 .pyc 字节码。字节码生成代价很低，而且它带解释器版本标记，一旦打进轮子就得按 Python 版本各发一个。所以规范把这件事留给安装器在安装时做。

示例场景：某团队的内部库一直只往私有索引传 sdist——本地 python -m build 两个都产出了，但上传脚本里写的是只传 .tar.gz。这个包纯 Python，本身没有编译需求，所以没人觉得有问题。直到下游 11 个服务的容器镜像构建时长被拉平均了 40 秒：每次构建都要为这个包建一次隔离环境、装一次构建后端、造一次轮子。补上 wheel 之后单次构建省下 35 秒左右，按每天约 120 次构建算，一天回收约 70 分钟的流水线时间。改动是上传脚本里的一行。

sdist 是配方，wheel 是成品。让用户装 sdist，等于让他在自己厨房里现做一遍——成不成要看他有没有炉子。

二、构建后端与构建前端：一次职责拆分

早年的打包只有一条路：写一个 setup.py，执行 python setup.py sdist。这条路的问题是构建脚本本身就是任意 Python 代码，安装器要构建一个包就得执行它，既不安全也没法提前知道构建需要什么。现在的做法把这件事拆成了两半，理解这个拆分能解释绝大多数构建相关的怪现象。

构建后端是真正干活的库：决定收哪些文件、元数据怎么填、轮子长什么样。构建前端是你在命令行敲的那个工具：它读配置、准备环境、按顺序调用后端。pyproject.toml 里的 [build-system] 表就是两者之间的合同，它声明两件事——requires（构建这个项目需要先装哪些包）和 build-backend（调用哪个后端的哪个入口）。

# pyproject.toml —— 这段不是注释，是给构建前端的指令
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
你敲 python -m build（或 uv build）之后 ──────────────────────────────────────── │ │ 读 pyproject.toml 的 [build-system] │ requires = 列出构建期依赖 │ build-backend = 指定后端入口 ▼ ┌──────────────────────────────────────┐ │ 临时的隔离构建环境（前端的默认行为） │ ← 和你项目的 .venv 无关 │ 只装 requires 里列的那几个包 │ 本机装了什么都影响不到结果 └──────────────────┬───────────────────┘ │ 在这个环境里 import 并调用后端的钩子 ▼ ┌──────────────────────────────────────┐ │ 构建后端（hatchling / setuptools …） │ 决定「收哪些文件、元数据怎么填」 └──────────────────┬───────────────────┘ ▼ dist/ ├── mypkg-1.2.0.tar.gz （sdist） └── mypkg-1.2.0-py3-none-any.whl （wheel） 前端管「在哪构建、按什么顺序」；后端管「构建出什么」。

隔离构建为什么重要

隔离构建是指前端不在你当前的虚拟环境里调用后端，而是新建一个干净环境、只装 requires 里声明的包，在那里面构建。这一步看起来只是慢了几秒，实际上是「构建结果可复现」的全部基础。

不隔离会怎样？你本机恰好装了某个版本的构建后端、某个插件、某个能改变元数据生成方式的包，产出的轮子就带上它们的行为。你机器上构建出来的包是对的，同事和 CI 上构建出来的却不一样——而且这种不一致往往不表现为构建失败，而表现为「产出的轮子里少了一个数据文件」这类安静的差异。隔离构建把等式钉死成：同一份源码 + 同一份 requires = 同一种产出。

常用前端有两个：PyPA 的 build（用 python -m build 调用）和 uv build，两者都默认隔离构建。python -m build 不带参数时的行为还有个附带好处：它先从源码树造 sdist，再从那个 sdist 造 wheel。这个顺序顺手验证了一件事——sdist 里的内容是否足够重建出轮子。如果你的包有文件漏进 sdist，这一步就会失败，而不是等到用户装的时候才失败。

后端怎么选

后端build-backend 的值适合什么项目要注意
setuptoolssetuptools.build_meta需要在构建期跑 Python 逻辑（如编译扩展）的项目、以及大量既有项目历史包袱最重：setup.py、setup.cfg、[project] 三套配置并存，行为要靠版本区分；但兼容性与资料量无人能敌

对纯 Python 项目，现在的默认选项比 setuptools 轻得多。选 setuptools 的理由应该是「我确实需要在构建期执行逻辑」或者「这是个既有项目，换后端的收益不抵风险」，而不是「教程里都这么写」。反过来说，一旦要编译扩展，就别在通用后端上硬凑，直接上专门的那几个。

[build-system] 少写了不会立刻报错，前端会回退到老的 setuptools 路径继续构建——这正是它危险的地方。它不是可选装饰，是让构建结果确定下来的那一行。

三、包里该有什么、不该有什么

打包工具的默认行为是「把配置告诉它的目录收进去」，它分不清哪个文件是你想发的、哪个是你忘了删的。所以「包里有什么」是一件需要主动确认的事，而不是构建成功就代表对了。

判据可以简化成两句话：轮子里只放装完要用到的东西，sdist 里放从零重建轮子要用到的东西。把每个文件按这两句话归位，绝大多数取舍都有答案了。

文件进 sdist进 wheel说明
包目录下的 .py要要漏了它就是「装完 import 不到」
包内数据文件（模板、schema、词表）要要要在后端配置里显式声明，不要指望非 .py 文件被默认收进去
许可证文件要要用 license-files 声明；元数据 2.4 起落在 .dist-info/licenses/
README要内容进元数据readme 字段指向它，正文写进 METADATA 的长描述，显示在索引页面上
测试代码常放不该放下游打包者要靠 sdist 跑测试；最终用户装包用不到
文档源文件可放不该放同上，而且会白白增大每一次下载
CI 配置、开发脚本、格式化配置不必不该放对使用者没有任何意义
.env、令牌、私钥、内部地址绝不绝不发布不可撤销，见第五节
__pycache__ / .pyc不放规范不含安装器会在安装时自己生成

密钥那一行不是假想题。开发时随手放在包目录里的 config_local.py、跑通接口时留下的 .env，只要位置落在被收集的目录下，就会安静地跟着轮子一起发出去。而一旦发出去，你能做的只有吊销那个密钥——文件删不掉，历史版本可能已经被镜像站和各种缓存抓走了。

「本地能 import、装完 import 不到」

这是打包环节最高频的一类故障，而它的根因几乎总是同一个：产出的轮子里根本没有你的包目录，后端没把它认出来（包发现规则没配、目录名与声明不一致、或者用了命名空间包却没按规则声明）。真正让它难排查的，是你在本地压根测不出来。

原因在于解释器把当前工作目录放在导入路径的最前面。你在仓库根目录跑测试时，import mypkg 命中的是仓库里的源码目录，而不是装进 site-packages 的那份。于是「打包漏了」和「打包没漏」在本地表现完全一致，测试全绿，问题留给第一个真正装它的人。

flat 布局 src 布局 ───────── ──────── myproj/ myproj/ ├── pyproject.toml ├── pyproject.toml ├── tests/ ├── tests/ └── mypkg/ ← 就在仓库根 └── src/ ├── __init__.py └── mypkg/ └── client.py ├── __init__.py └── client.py 在仓库根目录执行测试时，导入路径第一项 = 当前目录 ┌───────────────────────────────────────────────────────────────┐ │ flat： 当前目录下就有 mypkg/ → import mypkg 直接命中仓库源码 │ │ 打包配置漏没漏，本地完全测不出来 │ │ src： 当前目录下没有 mypkg/ → 必须先安装才能 import │ │ （开发期用可编辑安装） │ │ 打包漏了包目录，第一次跑测试就 ModuleNotFoundError │ └───────────────────────────────────────────────────────────────┘ src 布局的价值不是「目录更整齐」，是把「靠当前目录蒙对」这条退路堵掉， 让打包遗漏在开发期就暴露，而不是在用户机器上暴露。

代价是多一个步骤：src 布局下代码必须装过才能跑，开发时用可编辑安装解决。这个代价换来的是打包配置从第一天起就一直在被验证。至于包目录本身怎么组织、__init__.py 里该导出什么才算「公开 API」，属于模块与包的范畴，见 PY08。

构建完成后花一分钟做两件事，比事后排查便宜得多：

# 1. 直接看轮子里有什么（轮子就是个 ZIP）
python -m zipfile -l dist/mypkg-1.2.0-py3-none-any.whl

# 2. 到一个干净环境里只装这个轮子，并且离开仓库目录再 import
#    留在仓库目录里测等于没测——当前目录会替你把包「找」到

验证打包成功的标准动作，是在一个不是你仓库的目录里 import 它，然后打印 模块.__file__。如果这个路径指向你的仓库而不是 site-packages，你测的一直是源码。

四、版本号是一份兼容承诺

版本号最容易被当成「这次改了多少」的度量，于是出现「重构了三千行，怎么能只升修订位」这类争论。但语义化版本（SemVer）承诺的对象从一开始就不是代码量或工作量，而是公开 API 的兼容性——它回答的唯一问题是：使用者升级之后，要不要改自己的代码。

三段的含义是：主版本在做出不兼容的 API 变更时递增；次版本在以向后兼容的方式增加功能时递增；修订号在做出向后兼容的缺陷修复时递增。按这个定义，重写三千行但外部行为一字未变，就该是修订号；删掉一个参数，哪怕只改了一行，也该是主版本。

这里必须诚实地补一句，否则会给出错误的安全感。官方讨论页明确提醒：版本号反映的是维护者的判断，可能和使用者的预期不一致。多数大项目并不严格遵循语义化版本——NumPy 就公开声明走「宽松」语义化版本，次版本也可能带不兼容变更；安全修复也常常以修订版形式发出，却不可避免地带破坏性变更。所以作为发布者，要把自己的判据写下来并公开；作为使用者，不要把「修订版不会坏」当成保证。

什么算破坏性变更

改动破坏性？该升哪一位
新增函数、类、或带默认值的可选参数否次版本
把某个用法标记为弃用，但仍然可用否次版本
修缺陷，让行为回到文档已经描述的样子否修订号
只改内部实现，公开行为完全不变否修订号
删除或重命名参数、函数、类是主版本
改一个参数的默认值是主版本
增加必填参数，或改变位置参数的顺序是主版本
改返回值结构（改类型、改键名，甚至多一个键——如果下游会遍历它）是主版本
改抛出的异常类型，或改异常的继承关系是主版本
收紧输入校验：原来能过的输入现在报错是主版本
提高 requires-python 的下限是主版本

表里最容易被漏掉的就是加粗那一行。改默认值的人心智模型往往是「我在修 bug」，因为旧的默认值在他看来是错的。但对下游而言，判据只有一条：不改一行代码，行为变了没有。变了就是破坏性变更，跟谁对谁错无关。异常类型那一行也常被忽略——抛什么异常属于公开契约的一部分，这方面的设计取舍见 PY24。

事故复盘：某内部库 xx-common 发布 2.3.4，唯一的改动是把 retry(times=3) 的默认值从 3 改成 0。作者的理由是「默认就重试」本身是个缺陷，会让幂等性未知的写接口被重复调用——这个判断本身没错。但版本号只升了修订位。下游 17 个服务的依赖声明写的是 xx-common~=2.3，当晚发版的 6 个服务自动装到了新版；其中 4 个一直靠这个默认重试兜住上游偶发的 502，上线后接口错误率从 0.3% 涨到 11%，P95 从 180ms 涨到 2.4s。故障持续 92 分钟。恢复分两步：先在索引上撤下 2.3.4、发出把默认值改回 3 的 2.3.5，再逐个重新构建部署那 4 个服务（撤下只影响之后的依赖解析，已经装上的不会自己退回去）。真正的行为变更两周后以 3.0.0 发出，附迁移说明。复盘留下两条：改默认值是破坏性变更，不管改动者觉得自己在修什么；以及下游对内部库不能只锁到次版本。

预发布、开发版与后置版

正式版之外还有几种带标记的形态，用来表达「这个版本不是给所有人的」。安装器默认只挑正式版，预发布和开发版要显式要求（--pre，或用精确的版本号点名）才会被选中——这个默认行为正是它们能安全存在于同一个索引上的前提。

正式版1.2.0正常发布会
开发版1.2.0.dev1开发周期早期的构建，比如每日构建不会
alpha1.2.0a1早期试用，接口还会变不会
beta1.2.0b1功能冻结，找缺陷不会
候选版1.2.0rc1准备转正式，没问题就原样发布不会
后置版1.2.0.post1修正发布本身的错误，比如发布说明写错。不用来修代码缺陷会
本地版1.2.0+internal.4本地构建或下游打补丁的变体，不用于公开发布不适用

顺序是 alpha → beta → 候选版 → 正式版。后置版那一行的限定要记住：代码有缺陷就发新的修订版，别用 .post 蒙过去，因为使用者没法从版本号上看出代码变了。

版本号的单一来源

版本号写在几个地方，就一定会有一天不一致——pyproject.toml 里是 1.2.0，__init__.py 里还是 1.1.9，而报错日志里打出来的是后者。规则是只有一处是事实，其余从它读。

常见做法有三种：从版本控制系统的 tag 推导（发布流程天然和打 tag 绑定）；硬编码在 pyproject.toml 里，由后端在构建时拷到需要的地方；硬编码在源码的某个模块或专用文件里，由后端在构建时读出来。后两种要把 version 标成动态字段，也就是 dynamic = ["version"]，意思是「这个字段由后端负责填」。具体怎么配，各后端文档不一样，照抄它自己的说明。

运行时要读版本，优先用标准库：

from importlib.metadata import version, PackageNotFoundError

try:
    __version__ = version("mypkg")   # 读的是装进环境那份的元数据
except PackageNotFoundError:         # 直接在源码树里跑、没装过
    __version__ = "0.0.0+unknown"

区别很实在：importlib.metadata.version() 读的是实际安装的那份的元数据，而源码里手写的 __version__ 只是个字面量，两者不一致时后者会骗你。如果你同时对外提供 __version__，官方建议加一个自动化测试断言两者相等。另外注意它要的是分发包名而不是导入包名——这两者可以完全不同（装的是 pillow，导入的是 PIL）。

升哪一位，只问一个问题：使用者不改代码，会不会出问题。会 → 主版本。不会且有新东西可用 → 次版本。不会且只是修了缺陷 → 修订号。跟你改了多少行没有关系。

五、发布流程与安全：一条单向的路

这一节的所有做法都从同一个事实推导出来：发布是不可撤销的。索引是只能往后追加的存储，你能做的只有「再发一个」，不能「把刚才那个改掉」。理解了这一条，流程该怎么设计几乎是自明的。

先发测试索引

公共索引一般会提供一个独立的测试索引（PyPI 对应 TestPyPI），账号体系也是分开的。它的用处不是测代码——测代码是 CI 的事——而是验证流程和元数据：项目名有没有被占、README 在页面上渲染成不成样子、分类器和链接有没有写错、产物能不能被真的装上并 import 成功。这些问题在正式索引上发现一次，就得白烧掉一个版本号。

需要注意它不适合当成持续部署目标：每次提交都往上传会撞上项目体积上限，要在 CI 里做这种高频验证，更合适的做法是起一个本地的索引服务。

# 在 pyproject.toml 里登记测试索引（uv 的写法）
[[tool.uv.index]]
name = "testpypi"
url = "https://test.pypi.org/simple/"
publish-url = "https://test.pypi.org/legacy/"
explicit = true
uv build                      # dist/ 下产出 sdist 与 wheel
uv publish --index testpypi   # 先发测试索引
uv publish                    # 验过了再发正式索引

产物必须由 CI 生成

本地构建的问题不是「不方便」，而是不可复现：你装了哪些版本的构建依赖、有没有未提交的本地改动、目录里有没有上次调试留下的文件，除了你自己没人知道，连你自己过两周也不知道。CI 从 tag 检出干净代码构建，产出才有一份可追溯的来源。

PyPA 指南里还有一条很具体的建议，值得照做：把构建作业和发布作业分开。构建作业产出 dist/ 并存成构建产物，发布作业只负责下载产物并上传，不在发布作业里现场构建。这样「发到测试索引的」和「发到正式索引的」是同一批字节，而不是两次独立构建碰巧一样的结果。

一条可复现的发布流水线 ────────────────────── 给提交打 tag v1.2.0 并推送 │ ▼ ┌─────────────────────────────────┐ │ 构建作业 │ 从 tag 检出干净代码，不带任何本地改动 │ python -m build / uv build │ 产出 dist/，作为构建产物存起来 └────────────────┬────────────────┘ │ ← 产物在这里被固定下来；之后的作业只搬运，不重建 ┌─────────┴──────────┐ ▼ ▼ ┌───────────────┐ ┌──────────────────────────────┐ │ 发布作业：测试 │ │ 发布作业：正式 │ │ 验流程与元数据 │ │ 仅 tag 触发 │ │ 不需要审批 │ │ 环境上配置人工审批 │ │ │ │ 授予申请身份令牌的权限 │ └───────────────┘ └──────────────┬───────────────┘ ▼ 版本号与文件名从此永久占用 发错了只能往后发新版，回不了头 发布作业只做两件事：下载产物、上传。构建一次，发布多处。

受信任发布：不要在 CI 里存长期令牌

传统做法是在索引上生成一个 API 令牌，存进 CI 的密钥配置。问题在于这是一份长期有效的凭据：它躺在那里，泄露一次就是持续风险，而且轮换要靠人记得。

受信任发布（Trusted Publishing）换了条思路：CI 平台为这一次运行签发一个短期的身份令牌，索引侧事先登记好「哪个仓库的哪个工作流有资格发这个项目」，核对通过后换发一个只够这次上传用的临时凭据。CI 里不再需要保存任何长期密钥。

在 PyPI 上登记一个受信任发布者要填的是：项目名、代码仓库的所有者、仓库名、发布工作流的文件名，以及 CI 侧的环境名。工作流那边要给发布作业显式授予申请身份令牌的权限——GitHub Actions 里就是 id-token: write 这一项，漏了它拿不到令牌，报错会指向认证失败而不是权限缺失。项目还没发布过也能先登记「待用」的发布者，第一次使用时自动建项目。已经在用 API 令牌的项目切过来之后，记得把旧令牌从 CI 里删掉并在索引侧吊销，否则等于白切。

正式索引对应的环境上应该加人工审批：这样「谁手滑推了个 tag，东西就在无人看管时发出去了」不会发生。测试索引通常不需要审批。第三方索引和自建索引对受信任发布的支持程度不一，具体配置项以各自文档为准。

发错了怎么办：撤下，而不是删除

文件名在索引上是永久占用的。文件名由项目名、版本号、分发类型三部分组成，索引不允许重用；即使把文件、整个发布、甚至整个项目删掉，那个文件名也回不来。这个设计是有意的——它保证「某个项目某个版本的某类文件」永远解析到同一份字节，谁都没法事后偷偷替换。顺带一个反直觉的后果：删掉整个项目会把项目名释放给别人注册。

所以想让安装器别再选中某个坏版本，正确动作是撤下（yank）而不是删除。被撤下的版本依然可以下载（已经精确锁定它的构建不会断），但安装器在解析版本范围时会跳过它——除非它是唯一满足精确匹配的版本。PyPI 目前只支持按整个发布撤下，不能只撤其中一个文件；撤下时填的原因会显示在页面和索引接口上，下游据此判断怎么应对，值得认真写。

情况该做什么不该做什么
发出去的版本装不上或有严重缺陷先发修订版，再撤下坏版本删掉再用同一个版本号重传——文件名已永久占用
版本号本身写错了直接发下一个版本号指望改名或者「重发一次」
只有发布说明写错，代码没问题发 .post1顺手改了代码还继续用 .post
误发了含密钥的产物先吊销那个密钥，再撤下或删除只删文件就当没事——镜像和缓存可能已经抓走了
项目不再维护在元数据和文档里标明状态，留下继任说明删除项目——项目名会被释放给陌生人

示例场景：某团队的发布流程是「本地 build 完手工上传」。一次发版时本地工作区有个未提交的调试改动，把日志级别写死成了 DEBUG，产物就这么带着它进了私有索引。下游 8 个服务在随后两天里陆续升级，日志量涨了约 30 倍，其中 2 个服务打满了日志盘触发告警，磁盘清理和回滚一共花掉约 3 小时。后续整改是把构建搬进 CI（从 tag 检出）、构建与发布作业分离、并在构建前加一步「工作区必须干净」的校验。根因不是那一行 DEBUG，而是产物来自一台没人能复现的机器——同样的事换成别的改动还会再发生一次。

索引是只能追加的。所有发布流程的设计都从这一条推出来：宁可多发一个版本号，也不要指望改掉已经发出去的那个。

六、发布之后的责任与判据

这一节先讲一条前置判据，因为它能省掉前面五节的全部工作。

先问：要不要发包

把代码发成公共包意味着一份长期维护承诺：会有人依赖它、提问题、被你的破坏性变更影响；你占用的项目名和版本号永久有效；而「不再维护」这件事本身也需要一个交代。所以在决定发之前，先看看有没有更轻的方案能满足真实需求。

真实需求更轻的做法什么时候才升级成发公共包
只在公司内部复用私有索引（自建或托管），或让下游直接依赖代码仓库的某个 tag外部用户也需要它，且你愿意承担公开支持
几个运维脚本想共享放在一个仓库的目录里，给明确的入口，别做成包被三个以上独立项目依赖，且有版本兼容压力
想「装完就有命令可用」，但只给自己用工具安装器直接装本地路径别人也要装
要发内部包，但怕误传到公共索引元数据里加 Private :: Do Not Upload 这个特殊分类器，PyPI 会拒收任何以 Private :: 开头的分类器—

最后那一行是个很便宜的保险：它把「手滑发到公共索引」从一次不可逆事故降级成一次上传失败。内部包值得默认加上。

变更日志写给使用者看

没用的变更日志长这样：Merge pull request #412 from feat/refactor-client。它对使用者的信息量是零——不知道要不要升，也不知道升了要改什么。有用的变更日志回答的是对使用者的影响，每一条都能让人判断「我要不要动代码、动哪里」。

实操上按影响分组，而不是按时间或按提交：破坏性变更（每条都带迁移写法）、新增功能、缺陷修复、弃用通知。破坏性变更那一组永远排最前面，因为它是唯一会让人加班的那组。对照上一节的事故，那次真正该出现在变更日志顶部的是这么一条：「retry() 的 times 默认值由 3 改为 0；依赖旧行为的调用方请显式传 times=3」——而不是「修复了默认重试的缺陷」。

弃用要走流程，不能直接删

删掉一个公开用法之前，至少要走完三步：

一是标记。旧用法保持可用，同时发出 DeprecationWarning，警告文本里必须写替代写法，而不是只说一句「已弃用」——看到警告的人下一个动作是找替代品，你不写他就得去翻源码。同时在文档和变更日志里同步写上。

二是等待。至少保留一个大版本周期，给下游留出真实的升级窗口。这里有个陷阱：DeprecationWarning 在 Python 的默认警告过滤规则下，只有由 __main__ 中的代码触发时才显示，库内部发出的默认是被过滤掉的。也就是说「我发了警告」不等于「下游看到了」。测试运行器（如 pytest）默认会把它打开，这是下游最可能真正看到警告的地方——但你不能假设每个下游都跑测试。所以变更日志、文档、发布说明这三处必须冗余地写。

三是删除。在下一个主版本里删掉，并在变更日志的破坏性变更一节里明确列出。

能少走这套流程的办法是一开始就把公开面收窄：明确哪些是公开 API、哪些是内部实现。用 Protocol 和枚举把对外契约显式写下来（见 PY22），再配上类型注解与静态检查（见 PY20），很多破坏性变更能在下游的检查阶段就暴露，而不是等到运行时。公开面越小，你能自由改动的空间越大。

  • sdist 和 wheel 都发；纯 Python 项目一个 py3-none-any 轮子就够
  • pyproject.toml 里显式写 [build-system]，让构建结果确定下来
  • 用 src 布局，让打包遗漏在开发期而不是用户机器上暴露
  • 构建完先 python -m zipfile -l 看一眼轮子里有什么
  • 版本号只有一处事实来源，运行时用 importlib.metadata.version() 读
  • 产物由 CI 从 tag 检出构建，构建作业与发布作业分离
  • 用受信任发布替代长期令牌；正式索引的发布加人工审批
  • 先发测试索引验元数据与可安装性，再发正式
  • 坏版本用撤下（yank）处理，附上原因
  • 内部包加 Private :: Do Not Upload 分类器兜底
  • 把测试、文档源文件、CI 配置打进 wheel
  • 把 .env、令牌、内部地址留在被收集的目录里
  • 改默认参数值、改异常类型、改返回结构，却只升修订位
  • 把版本号同时手写在 pyproject.toml 和 __init__.py 里
  • 在本地机器上构建产物并手工上传到正式索引
  • 把长期 API 令牌存在 CI 密钥里，切到受信任发布后还不吊销旧的
  • 删掉发错的版本想用同一个版本号重传
  • 删除整个项目（项目名会被释放给别人注册）
  • 用 .post 版本号来修代码缺陷
  • 把「罗列提交记录」当成变更日志
  • 不走弃用流程，直接在次版本里删掉公开用法

一次发布真正交付的不是那个 .whl 文件，而是一句话：「按这个版本号升级，你的代码不用改。」变更日志、弃用流程、版本号规则，全部都是为了让这句话可信。

Q&A

我的包是纯 Python 的，只发 wheel 不发 sdist 行不行？
技术上能装，但官方建议是两个都发，原因有三。一是下游打包者（Linux 发行版、conda、Homebrew 这类）通常以 sdist 为源，里面常带测试，他们要靠它验证打包结果；只有 wheel 会把你的包挡在这些渠道之外。二是 sdist 是兜底路径：将来你要是加了编译扩展、或者出现了你没覆盖的平台，没有 sdist 就完全没有退路。三是 python -m build 默认「先造 sdist、再从 sdist 造 wheel」的顺序本身是一道检查，能提前发现「有文件没进 sdist」。反过来说，只发 sdist 才是真的有代价的——每个下游的每次构建都要现场造一遍轮子。
版本号从 0.x 开始有什么讲究？什么时候该发 1.0？
惯例上 0.x 表示「接口还在变，不承诺兼容」，这给了你在早期自由改动的空间，语义化版本规范本身也允许这种用法。问题是很多项目把 0.x 拖成了永久状态，一边说「不承诺兼容」一边已经有几十个真实下游在用——这时候 0.x 的实际作用只是免除你写迁移说明的义务，对使用者纯是损失。判据很简单：一旦有你不认识的人在依赖它，就该发 1.0 并开始遵守承诺。另外注意 0.x 阶段下游没法用依赖范围保护自己，因为「哪一位算兼容」根本没定义，所以这个阶段拖得越久，下游锁版本就越只能靠精确锁定。
下游该怎么锁版本，用 ~= 还是 ==？
分两种角色。应用（最终要部署的东西）应该用锁文件把整棵依赖树精确锁定，包括间接依赖，这样部署才可复现；直接依赖声明里写个宽松范围、由锁文件负责精确版本，是现在的主流做法。库则相反，应该给尽量宽的范围，尤其避免加版本上限——库的上限会传染，最终导致下游根本解不出一组可行的版本。至于 ~=，它只在依赖方严格遵守语义化版本时才有保护作用；本节的事故恰好说明了它保护不了你，因为它信的是对方的自我判断。对内部库，更稳的是精确锁定加上定期主动升级，而不是让自动升级替你决定什么时候上新版本。
发布后发现漏了一个数据文件，能补传一个文件吗？
不能。文件名由项目名、版本号、分发类型组成，索引不允许重用，即使你把原文件删掉也一样——这是有意的设计，它保证某个版本的某类文件永远解析到同一份字节，不会被事后替换。所以唯一的路是：修好打包配置，升一位版本号（漏文件通常算缺陷修复，升修订号），重新构建，重新上传；然后把坏版本撤下（yank）并写清原因，让还没锁定它的下游不再选中它。顺便说，删除在 PyPI 上是永久且不可逆的，管理员也恢复不了，而删掉整个项目还会把项目名释放给别人，所以「删了重来」几乎永远不是正确动作。
为什么我的包本地 import 得好好的，装到别的机器上就 ModuleNotFoundError？
十有八九是轮子里根本没有你的包目录，而你本地测不出来——因为解释器把当前工作目录放在导入路径最前面，你在仓库根目录里 import 到的一直是仓库源码，不是安装后的那份。验证只要两步：python -m zipfile -l 直接看轮子里的文件清单；然后到一个干净环境里只装这个轮子、并且离开仓库目录再 import，打印 模块.__file__ 确认路径落在 site-packages 下。根治办法是改用 src 布局，它让「靠当前目录蒙对」这条退路不存在，打包漏了在开发期第一次跑测试就会暴露。至于后端为什么没认出包目录，通常是包发现规则没配、目录名和声明不一致，或者非 .py 的数据文件没有显式声明。
内部库就几个人用，也要搭 CI 发布流程吗？
先反问一句：这东西真的需要打包吗。如果只有一两个项目用，让它们直接依赖代码仓库的某个 tag，或者干脆把代码放到同一个仓库里，比维护一条发布链路便宜得多。如果确实要发，那 CI 构建的价值和用户数无关——它防的是「产物来自一台没人能复现的机器」，而这个风险跟有几个下游没关系，本节的 DEBUG 日志事故就是三个人的内部库。最低配版本也很省：一个由 tag 触发的作业，从干净检出构建，把产物传到私有索引，再加上受信任发布或者短期凭据。另外内部包一定要加 Private :: Do Not Upload 分类器，防止某次手滑把它发到公共索引上——那一步是不可逆的。
我只改了函数内部实现，但性能明显退化了，这算破坏性变更吗？
按语义化版本的字面定义不算——公开 API 没变，使用者不需要改代码，所以它落在修订号。但字面定义在这里给出的是个不够用的答案：如果退化的量级足以让下游超时（比如某个函数从毫秒级变成秒级），使用者要做的事和面对破坏性变更没什么区别。务实的处理是三条：在变更日志里显著写明性能变化和量级，哪怕版本号只升了修订位；如果退化幅度大，考虑放到次版本里发，让「保守只升修订号」的下游不会被自动带上；如果曾经在文档里承诺过复杂度或延迟量级，那它就是公开契约的一部分，破坏它按破坏性变更处理。归根到底，版本号是给下游的信号，信号不够时就用变更日志补。
受信任发布和 API 令牌能同时留着吗？
能同时存在，但这么做等于没切。受信任发布的全部价值在于「CI 里不存在长期有效的凭据」，只要旧令牌还躺在 CI 的密钥配置里，攻击面就一点没减少——攻击者不会挑难的那条路走。所以切换要走完：先配好受信任发布（登记项目名、仓库所有者、仓库名、工作流文件名、环境名），确认发布作业有申请身份令牌的权限，跑通一次发布，然后把旧令牌从 CI 里删掉、并在索引侧吊销它。最后一步最容易被省掉，因为它不影响任何功能。顺带提醒，第三方索引和自建索引对受信任发布的支持程度不一样，切之前先确认对方支持。
