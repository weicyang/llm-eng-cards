PY56 · 批量任务的吞吐与续跑

批量与交互的目标函数之别 / 瓶颈闸口定位 / 有界并发流水线 / 断点续跑与幂等 / 成本与质量的权衡

交互式请求是一场百米赛，批量任务是一场马拉松。用跑百米的姿势去跑马拉松——超时设得短、重试催得急、跑完才落盘——问题不是跑不快，是跑不完。

一、批量任务的目标函数不一样

把几万条数据丢给模型跑一遍，代码看起来和写一个线上接口没什么区别：发请求、拿结果、处理异常。但两者优化的根本不是同一个量，把线上接口那套参数原样搬过来，批量任务往往在半路就散架。

交互式请求优化的是单次延迟：用户在屏幕前等着，P95 超过两秒体验就崩了，所以超时要短、重试要快、宁可快速失败也不要让人干等。批量任务优化的是总完成时间（从启动到最后一条落盘的墙钟时间）和单位成本：没有人在等某一条，只要整批在时间窗口内跑完、花的钱在预算内，就算成功。

这两个目标函数经常给出相反的最优策略。单条请求慢到三十秒，在交互式场景是事故，在批量场景可能恰恰是最优解——因为继续等它比超时后重发一遍更省配额也更省钱。退避退到一分钟，在交互式场景不可接受，在批量场景是撞上限流后最该做的事。

批量任务里，慢不是问题，停才是问题。任何会让整批停下来的设计——短超时引发的重试风暴、一条失败就整体退出、结果攒在内存里把机器撑爆——都比单条慢十倍严重得多。

和服务端的批处理不是一回事

推理服务自己也在为吞吐做优化，但那是另一层的事。DP11 Continuous Batching 与推理调度策略 讲的是推理服务内部如何把多个请求拼进同一个批次、如何做迭代级调度与抢占——那是被调用方的调度器在做的决策，你作为客户端既看不见也控制不了。

本卡站在调用方这一侧：你手上有几万条任务和一份别人给你的配额，怎么把它们全部跑完。两者不冲突，也不能互相替代——服务端把单位时间能处理的请求数做上去了，调用方仍然要自己解决并发编排、断点续跑和成本控制，否则照样跑不完。

二、吞吐由最紧的那道闸决定

优化批量任务最常见的浪费，是把力气花在一道本来就不紧的闸上。把并发从 32 提到 128，吞吐纹丝不动——因为真正卡住的是下游每分钟的 token 配额，它在你把并发提上去之前就已经满了。提高非瓶颈环节的能力，收益严格等于零。

所以第一步永远是找出当前的瓶颈闸口。一条批量链路上串着好几道闸，每道都有自己的额定速率，整条链路的实际吞吐等于其中最小的那个。

两个问题就能定位瓶颈

第一个问题：把实际速率分别除以每道闸的额定值，比值最接近 1 的那道就是瓶颈。下游配额尤其要按两个维度各算一次——请求数没满不代表 token 没满，输入长的任务几乎总是先撞 token 配额。

第二个问题：看在飞请求数。如果它长期贴着你设的并发上限，说明瓶颈在下游或在你自己设的这个上限上；如果它常年只有上限的三成，说明任务根本喂不进来，瓶颈在上游的读取或预处理，这时候调并发毫无意义。

下游 token 速率配额每分钟消耗 token ÷ 配额请求数明明没满也被限流压缩输入、限制输出长度

示例场景：某批量任务把并发从 32 一路提到 256，吞吐从每分钟约 500 条只涨到约 560 条就再也不动，限流错误率却从 1% 涨到 18%。按上面两个问题算一遍：请求数配额用掉约 55%，token 配额用掉约 97%——瓶颈在 token 速率而不是请求数。把提示词里一段两千多字符、对本任务毫无作用的固定说明删掉之后，并发退回 64，吞吐反而升到每分钟约 900 条，限流错误率回到 1% 以下。之前那半天都花在往一道已经关死的闸上推。

找瓶颈最快的办法不是读代码，是把「实际速率 ÷ 额定速率」这个比值对每道闸各算一遍。哪个最接近 1，哪个就是今天唯一值得动的地方，其余的改了都是白改。

三、有界并发流水线：几万条任务的正确形状

拿到几万条任务，最自然的写法是把它们全部转成任务对象，一次性交给编排原语等结果。这在几十条时完全没问题，到几万条就同时踩三个坑：内存里一次性躺着几万个任务对象和几万份输入数据；下游在一瞬间收到远超配额的请求；以及任何一条出错时，你手上只有一个几万元素的结果列表，既不好定位也不好重跑。

正确的形状是有界并发流水线：一个生产者按需逐条读取任务放进队列，固定数量的工作协程从队列取任务处理，处理完立刻把结果交给写入端。队列长度有上限，于是反压能一路传回源头——下游慢了，工作协程取不走，队列满了，生产者自然停下来等，内存不会跟着任务总数涨。

编排原语（任务组、结果聚合、异常传播）见 PY30，队列本身的用法与收尾顺序见 PY32，限流器与超时的写法见 PY31。本节只讲批量场景特有的三个取舍。

有界并发流水线 ────────────────────────────────────────────── 数据源 ──逐条读取──▶ ┌────────────┐ （不要一次读进内存） │ 任务队列 │ maxsize ≈ 并发度 × 2 └─────┬──────┘ ┌────────────────┼────────────────┐ ▼ ▼ ▼ worker-1 worker-2 ... worker-N N 由配额反推 │ │ │ └────────────────┼────────────────┘ ▼ ┌─────────────┐ │ 结果写入端 │ 边完成边追加落盘 └─────────────┘ 队列满 ⇒ 生产者阻塞 ⇒ 反压传回源头 ⇒ 内存有上界 对照：一次性建 40000 个任务 ⇒ 没有反压 ⇒ 内存与下游同时爆

取舍一：并发度从下游配额反推

并发度不该拍脑袋设一个大数。稳态下，在飞请求数约等于目标吞吐乘以单条平均耗时——目标每秒 10 条、单条平均 6 秒，就需要大约 60 个在飞请求，再留点余量，并发度设 64 左右。反过来先设并发再看结果，就只能靠反复试，而且每试一次都要烧真金白银。

并发度 N ≈ 目标吞吐（条/秒） × 单条平均耗时（秒） × 安全系数（0.8 ~ 1.0）

目标吞吐本身也不是随便定的，它由配额倒推：请求数配额除以 60 得到每秒能发多少次，token 配额除以单条平均 token 量再除以 60 得到另一个值，取两者里小的那个。算出来的并发度通常比大家凭感觉设的要小得多，这是正常的。

取舍二：任务粒度不要太细

如果单条任务只要几十毫秒，调度、队列出入、日志、落盘这些固定开销就会占掉相当大的比例；把若干条打包成一个工作单元能把这部分摊薄。但粒度也不能太粗——单个工作单元越大，中断时丢掉的进度越多，第四节讲的续跑代价就越高。经验区间是让单个工作单元的处理耗时落在秒级到十秒级。

取舍三：结果边完成边落盘

常见写法是把所有结果收集到一个列表里，等全部跑完再统一写文件。几万条带长文本的结果足以吃掉几个 GB；更糟的是进程一旦中断，几小时的成果一起消失，这正是第四节那个事故的直接原因。正确做法是每条（或每小批）完成就追加写出去，写入端和工作协程解耦。

async def worker(q, sink):
    while True:
        task = await q.get()
        try:
            await sink.write(await handle(task))   # 完成一条写一条
        except Exception as exc:
            await sink.fail(task.id, exc)          # 失败单独记录，不抛出
        finally:
            q.task_done()

注意 except 这一支：批量场景里单条失败不应该让异常冒泡出去终止整批，它应该被就地记录。这和交互式场景的习惯正好相反，也是照搬接口代码最容易漏掉的一处。

编排形状内存占用有反压吗中断后损失适用规模
一次性创建全部任务与任务总数成正比没有全部几十条以内
分批循环，每批等全部完成与批大小成正比很弱当前整批写起来简单，但有木桶效应
有界并发流水线与并发度成正比有只丢在飞的那几条几千条以上的标准选择
多进程，每进程一条流水线进程数 × 上一行有同上本地预处理是瓶颈时

「分批循环」那一行的木桶效应值得展开：每批都必须等最慢的那条返回才能开下一批。大模型调用的耗时分布长尾很明显（同一批里从 1 秒到 30 秒都有），于是每批的时间都被最慢的那条拖住，实测的并发利用率常常只有六七成。流水线没有这个问题——一条完成就立刻补进下一条，槽位从不空着。

判断编排写对了没有，只看一个现象：任务总数从一万涨到十万，进程的内存占用应该几乎不变。如果内存跟着任务数一起涨，说明你名义上写了队列，实际上还是先把整个列表展开了。

四、断点续跑是刚需

几万条任务要跑几个小时，这段时间里发生中断几乎是必然事件：撞上限流、网络抖动、机器重启、被别人误杀、或者你自己发现提示词写错了要改代码。问题从来不是能不能避免中断（不能），而是中断之后是从断点继续还是从头再来。在几小时量级的任务上，这两者的差别就是几百块钱和一整个下午。

做到续跑需要四件事，每一件都不复杂，但缺一不可。

一、为每条任务设计稳定的标识

任务标识稳定的含义是：同一条输入，今天跑和明天跑算出来的标识必须一模一样。有业务主键就直接用（文档 ID、订单号），没有就对「决定输出的全部输入」做哈希。不能用的是循环下标——数据源的顺序或过滤条件一变，所有标识整体平移，续跑会跳错任务而且你不会收到任何报错。

标识来源稳定吗要注意什么
业务主键（文档 ID、订单号）稳定首选；跨数据源合并时加前缀，避免不同来源撞号
输入内容的哈希稳定先做规范化：去掉时间戳、统一空白与换行，否则同一条会算出不同标识
文件名 + 行号半稳定源文件重新生成或重新排序就全部错位
循环下标不稳定过滤条件一改就整体平移，续跑静默跳错
随机 ID / 每次新生成的 UUID不稳定每次运行都不同，等于没有续跑

二、结果以可追加的形式落盘

每行一条 JSON 的行式文件是最省事的选择：追加写不需要读取或重写已有内容，进程被强杀最多损坏最后一行，解析时跳过即可。相比之下，一个大的 JSON 数组文件必须在最后才闭合，中断即整份不可解析。写完要让内容真正落到文件里（按小批刷新），而不是停在缓冲区里等着和进程一起消失。追加写、编码与异常处理的细节见 PY07。

三、启动时先加载已完成集合

启动时先扫一遍已有的结果文件，把里面的任务标识读进一个集合，生产者产出任务时直接跳过集合里已有的。几万个标识放在内存里是几 MB 量级，代价完全可以忽略；哪怕到百万量级，也只是几百 MB，仍然比重跑一遍便宜得多。

四、失败单独记录，并带上类别

失败的任务写进另一个文件，除了标识还要记错误类别：限流、超时、下游报错、输出解析失败、输入本身有问题。整批跑完后只重跑可重试的那几类；输入有问题的那些应该去修数据，反复重试只是在烧钱。

幂等是续跑的前提

续跑必然会重跑一小部分任务——中断那一刻正在飞的那几条，状态是不确定的：可能下游已经处理完了，只是结果还没写回来。如果这条任务除了返回结果还会产生副作用（写库、发消息、生成计费记录），重跑就会留下两份。

解决办法是把任务标识一路带到产生副作用的那一端，用它当幂等键，让下游能识别出「这条我已经处理过了」。只读的抽取、分类、打标任务天然幂等，不用额外处理；一旦链路里有写入动作，这一步不能省——而它恰恰是最容易被忽略的，因为在没有中断的理想路径上永远不会暴露。

生产事故复盘：一个约 4 万条的文档字段抽取任务，第一次启动跑了约 3 小时 10 分、完成约 2.7 万条时，撞上下游按分钟计的配额收紧，重试次数耗尽后进程退出。因为结果全攒在内存里、也没有已完成标识，这 2.7 万条的成果全部作废，只能从头再来。第二次只改了退避参数就继续跑，在约 4 小时 15 分、完成约 3.6 万条时又撞上同一个问题，再次归零——离终点只差不到 4 千条。两次白跑合计浪费约 7.5 小时的墙钟时间和约 6.3 万次调用，重复烧掉的钱超过完整跑一遍成本的 1.5 倍。

第三次上线前只加了三样东西：行式结果文件追加落盘、启动时加载已完成标识集合、失败任务单独记录类别。同一批数据依然中断了两次（还是同样的配额问题），但每次重启后需要重跑的不到 200 条，全量跑完用时约 5 小时，额外的重复调用不到 400 次。改动量是几十行代码，省下的是两个下午和一大半预算。

判断续跑做没做对，只需要一个动作：跑到一半直接把进程杀掉，再原样启动一次。如果它接着往下跑、并且结果文件里没有出现重复标识，才算做对了。这个测试要在小样本阶段就做，不要等真出事的时候才第一次验证。

五、成本与质量的权衡

批量任务是整条链路上最容易省钱、也最容易烧钱的地方，原因只有一个：同一个数字被乘了几万次。提示词里多出 500 个 token，在单次调用里根本看不出来；乘以 4 万条就是 2000 万 token。反过来，把一个能用小模型处理的子集分流出去，省下的也是同一个量级。

总成本 ≈ 条数 × (1 − 缓存命中率) × (1 + 重试率) × 单条 token 量 × 单价

这四个可控因子是相乘关系，意味着任何一个失控都会吃掉其他三个的全部优化成果。你把单条 token 量砍掉一半，却让重试率从 5% 涨到 120%，净结果是成本上升。

省钱的四个手段

对重复输入做缓存。关键全在缓存键上：它必须包含所有影响输出的因素——输入内容、提示词版本、模型标识、温度等采样参数、以及输出格式约定。漏掉提示词版本是最常见也最隐蔽的错误：你改完提示词重跑，命中的却是旧提示词产出的结果，于是得出「改动没有效果」的错误结论。

把简单件分流给小模型。几万条任务里往往有很大一部分是格式规整、字段明确的简单件，小模型甚至规则就能处理，只把难例送给大模型。做法是先用便宜的方式处理，对结果做置信度判断，不达标的再升级。代价是要维护一套判据，而判据本身也会出错，所以必须配抽检。

压缩不必要的上下文。批量任务的提示词往往是从交互式场景整段复制过来的，里面带着大量对批量场景无用的内容：寒暄式的角色设定、与当前字段无关的示例、重复三遍的格式说明。逐段审视一遍，每删一段都要乘以几万。

合并可以一次处理多条的任务。一次请求处理多条输入能显著降低请求数，也能摊薄固定的提示词开销。但它有三个代价必须认：多条之间会互相干扰（前一条的内容影响后一条的判断）、单条出错会牵连整批、输出对齐变难（模型少输出一条，整个批次就对不上号）。合并数量要保守，并且必须要求输出里带上每条的标识。

另外，有些服务商提供延迟以小时计的离线批量提交方式，单价明显低于实时调用。它适合完全没有时效要求的整批任务，代价是提交之后不可交互、出错反馈很慢。各家的形态、限制和支持的任务类型差别很大，用之前要按各自的文档确认，不要假设它和实时调用完全等价。

手段节省量级质量代价什么时候别用
输入级缓存取决于重复率，常见 10%–40%键设计错会返回过期结果，且不报错输入几乎没有重复时

三种烧钱形态

三种烧钱形态，共同点都是「一个小数乘以几万次」 ────────────────────────────────────────────────────── ① 失控重试 单条失败 ──▶ 立刻重试 ──▶ 还是限流 ──▶ 再重试 …… 重试本身占满配额，成功率继续下降，于是重试更多 ← 正反馈 成本 ×1.5 ~ ×3，而吞吐比不重试还低 解法：指数退避 + 次数上限 + 全局降速，而不是单条狂试 ② 重复跑已完成的任务 没有续跑 ──▶ 中断一次 ──▶ 前面跑过的全部重新付一遍 成本 ≈ 完整一遍 × （中断次数 + 1） 解法：第四节的已完成标识集合 ③ 提示词冗余乘以条数 多余 500 token × 40000 条 = 2000 万 token 在单次调用里完全看不出来，在账单上是最大的一项 解法：批量任务的提示词单独维护，逐段问「这段值 2000 万吗」

示例场景：同一批 4 万条分类任务，第一版每条都走大模型、提示词里带 6 个示例，跑完消耗约 4600 万 token。第二版做了三件事——示例从 6 个减到 2 个、对重复输入做缓存（命中率约 18%）、把置信度高的简单件分流到小模型（占比约 55%）——消耗降到约 1200 万 token。抽检 500 条的准确率从 94.2% 变成 93.6%。质量掉了 0.6 个百分点，成本降到约四分之一，在批量场景这个交换通常划算；但这个判断必须建立在有抽检数据的基础上，凭感觉做分流是另一回事。

批量任务里改任何一个参数之前，先把它乘以总条数再看一眼。500 个 token、0.1 秒、1% 的重试率，单看每一个都可以忽略；乘以四万之后，没有一个可以忽略。

六、进度、验收与预演纪律

一个要跑几小时的任务，如果启动之后只能盯着终端发呆，它就是不可运维的——你既不知道它是不是已经卡死，也不知道该不该现在去吃饭。可观测的进度和可判断的收尾，是批量任务和「一段能跑的脚本」之间的分界线。

进度要有四个数

已完成、失败、剩余、预计完成时间。前三个是计数器，第四个要算——而且要用最近一段窗口的速率去除剩余条数，不要用全程平均速率。全程平均会被启动阶段的预热和中途的限流拖慢，给出的预计时间常常偏差一倍以上；滑动窗口（比如最近 5 分钟）才能反映当下的真实速度。

进度输出建议走结构化日志，而不是刷屏的进度条。几小时的任务通常在后台或容器里跑，日志要能事后回看、能被采集聚合。每隔固定时间（比如 30 秒）输出一条心跳记录，带上这四个数以及按错误类别分桶的计数，就足够了。日志字段设计与指标暴露见 PY43。

收尾要有判据

「跑完了」不等于「跑对了」。交付之前至少要过下面这张表，其中前两条是纯机械的等式检查，最容易被跳过，也最容易抓出静默丢任务的 bug。

检查项怎么算不通过意味着什么
覆盖完整已完成数 + 失败数 = 总数有任务被静默吞掉了，编排里有漏洞
没有重复结果文件里唯一标识数 = 总行数续跑逻辑或标识设计有问题
失败率达标失败数 ÷ 总数 ≤ 事先定好的阈值不能直接交付，先看失败分布
失败可解释「未知」类别的计数 = 0存在没被识别的失败模式，你不知道自己漏了什么
输出可解析抽样解析成功率落盘格式或输出约束有问题

这里的验收判据必须事先定好数字。事后看着结果说「5% 的失败率应该还行吧」，本质上是在用结果给自己找理由。

预演纪律：最贵的错误发生在第三个小时

跑了三小时才发现结果文件格式不对、或者发现续跑其实根本没生效——这类错误的共同点是，只要先用一百条数据跑一遍全链路就能提前发现。很多人跳过这一步，理由是「先小跑一遍很麻烦」，而代价是整整一个下午加上一笔白花的调用费。

从预演到全量的四级阶梯，每一级只看特定的东西 ────────────────────────────────────────────────────── ① 1 条 走通一次调用，看清输出到底长什么样 检查：能否解析、字段是否齐全、格式约束有没有生效 ② 100 条 走通全链路，重点是落盘与续跑 检查：结果文件格式对不对 跑到一半杀掉进程，重启后能否接上且不重复 失败的那几条有没有真的落进失败文件 ③ 1000 条 跑出真实的速率与成本 检查：每分钟多少条、单条平均多少 token 按比例外推全量的耗时与花费，超预算就现在改 ④ 全量 只看进度与失败分布，原则上不再改代码 检查：心跳是否持续、失败率是否在阈值内 跳过 ② 的典型代价：跑三小时后发现结果文件解析不了 跳过 ③ 的典型代价：跑到一半才发现预算根本不够

第 ③ 级的外推有个前提要说清楚：小样本的单条成本可以线性外推，但吞吐不能。1000 条时你可能还没碰到任何配额上限，全量跑起来才会撞上，所以外推出来的总耗时应该当成乐观下界看待，留出余量。

  • 结果边完成边追加落盘，每条都带稳定的任务标识
  • 启动时先加载已完成标识集合，跳过已经跑过的
  • 并发度由下游配额反推，而不是设一个感觉上很大的数
  • 撞限流时全局降速并拉长退避，不对单条快速重试
  • 缓存键包含提示词版本、模型标识与采样参数
  • 每 30 秒输出一条含「完成 / 失败 / 剩余 / 预计完成」的心跳
  • 全量之前用百条量级跑通全链路，并真的杀一次进程验证续跑
  • 失败按错误类别分桶记录，只重跑可重试的那几类
  • 一次性把几万个任务全部创建出来再等结果
  • 把所有结果收集在内存里，等全部跑完再统一写文件
  • 用循环下标或每次新生成的随机 ID 当任务标识
  • 沿用交互式接口的短超时和快速重试参数
  • 没确认瓶颈在哪一道闸就先去调高并发
  • 把交互式场景的提示词整段复制过来不做裁剪
  • 用全程平均速率估算剩余时间
  • 「未知错误」还剩一大桶就把结果交付出去

批量任务的交付标准不是「跑完了」，而是能回答三个问题：哪些条跑成了、哪些没跑成分别是什么原因、现在要再跑一次得花多久多少钱。这三个问题答不上来，就还没跑完。

Q&A

并发度到底该设多少？有没有一个通用的默认值？
没有通用值，因为它完全由你的配额和单条耗时决定，而这两个数每个项目都不同。算法是固定的：先由配额算出目标吞吐——请求数配额除以 60 得到每秒能发几次，token 配额除以单条平均 token 量再除以 60 得到另一个数，取小的那个；再乘以单条平均耗时，得到需要的在飞请求数；最后乘以 0.8 到 1.0 的安全系数。目标每秒 10 条、单条平均 6 秒，算出来约 60，设 64 就很合适。这个数通常比凭感觉设的要小，如果你算出来是 30 而手上代码写着 500，那 500 那个值从第一天起就没起作用——多出来的请求只是在下游排队或者被限流打回。另外记得连接池上限要跟着并发度一起调，否则并发提上去了，请求都堵在拿连接那一步。
一次请求合并处理多条输入，到底值不值？
看瓶颈在哪。如果瓶颈是请求数配额，合并的收益很直接——10 条合一次，请求数降一个量级。如果瓶颈是 token 速率配额，收益就小得多，因为合并只摊薄了固定的提示词开销，内容本身的 token 一个都没少。代价有三个：多条之间会互相干扰，前面几条的内容会影响后面几条的判断，准确率通常会掉一点；单条触发的错误会牵连整批，一批 10 条里有 1 条让模型跑偏，你可能要把 10 条全部重跑；输出对齐很脆弱，模型少输出一条或者顺序变了，你就得整批作废。实践上的折中是合并数量保守（个位数到十几条）、在输出格式里强制要求带上每条的标识、并且在解析时校验条数和标识是否与输入对得上，对不上就整批打回重试。
任务标识用输入内容的哈希，有什么坑？
最大的坑是没有规范化就直接哈希。输入里只要带了时间戳、请求 ID、或者仅仅是行尾换行符从 LF 变成了 CRLF，同一条逻辑上的数据就会算出两个不同的标识，续跑时它会被当成新任务重新跑一遍，你的结果文件里会出现语义重复但标识不同的两行。所以哈希之前要先做规范化：去掉与内容无关的字段、统一空白与换行、必要时统一大小写和全半角。第二个坑是哈希的范围取错了。如果只哈希输入文本，那么改了提示词或换了模型之后重跑，所有标识都没变，续跑会认为「全都跑过了」直接跳过，你会得到一个什么都没做的运行。判断方法和缓存键一样：所有影响输出的因素都要进哈希；如果某个因素是全局统一的（比如提示词版本），也可以不进哈希，而是换一个输出文件目录，用目录来隔离。
结果落盘应该用行式文件还是直接写数据库？
两条路都能做到续跑，选哪个取决于结果之后要怎么用。行式文件（每行一条 JSON）的优点是零依赖、追加写极快、进程被强杀最多坏最后一行、出问题时能直接用文本工具查看；缺点是去重和查询要靠自己扫一遍，并且多进程同时往一个文件追加需要小心（通常的做法是每个进程写自己的分片文件，最后合并）。数据库的优点是天然能用唯一约束来保证幂等——同一个任务标识插第二次直接冲突，续跑的去重逻辑几乎不用写；缺点是多了一个依赖，写入吞吐可能反过来变成新的瓶颈，而且批量写要自己攒批。经验上，一次性的离线任务用行式文件，结果要长期被别的系统查询的用数据库；无论哪种，任务标识都必须作为一等字段存下来，不能只存结果。
撞上限流之后，是整批停下来等，还是只让失败的那条退避？
要全局降速，不能只处理失败的那一条。原因是限流反映的是整条链路的容量已经到顶，此时其他还在飞的请求同样会陆续失败；如果只让失败的那条退避、其余照常全速发，你会在接下来几十秒里持续制造失败，每一次失败都白占一次配额，成功率越来越低——这就是第五节说的失控重试正反馈。正确做法是让限流信号作用在整个工作池上：收到限流后统一降低发送速率（比如并发度减半），等一段时间没有再出现限流信号，再逐步恢复。这个「快降慢升」的形状和网络拥塞控制是同一个思路。具体的限流器与退避写法见 PY31。另外提醒一句，退避一定要带抖动，否则所有 worker 会在同一时刻同时恢复，立刻再撞一次。
这套客户端的做法，和服务端的连续批处理是什么关系？
是两层完全不同的问题，不能互相替代。服务端的连续批处理（本卡第一节链接的 DP11）解决的是推理服务内部的调度：怎么把来自不同客户端的请求拼进同一个批次、怎么在每一步迭代后动态换入换出、怎么避免短请求被长请求堵住。它决定的是这台服务「每秒能处理多少请求」这个额定值。客户端这一侧解决的是：给定那个额定值，我手上这几万条任务怎么编排、怎么在中断后接着跑、怎么控制总花费。就算服务端的调度做到了极致，客户端如果一次性把几万个请求砸过去、中断后又从头再来，任务照样跑不完、钱照样白花。反过来也一样，客户端做得再好也突破不了服务端给的配额上限。顺带一提，客户端的三种调用模式（同步、异步、流式）以及重试、熔断、降级这类韧性机制各自有专门的一张卡，本卡只在需要时引用它们的结论。
预演阶段用小样本测出来的成本和耗时，外推到全量准不准？
成本比较准，耗时往往偏乐观。成本之所以准，是因为它基本是线性的——单条平均消耗多少 token 乘以条数即可，唯一要留意的是小样本可能不能代表输入长度的分布，如果你的数据里有少量超长文档，随机抽 1000 条可能一条都没抽到，全量跑起来这部分会额外多出一块，所以抽样时最好按长度分层。耗时偏乐观的原因是配额：1000 条时你的速率可能还没顶到任何一道闸，全量跑起来在飞请求数上去了才会撞上限流，实际吞吐会低于小样本的外推值。此外还要算上中断恢复的时间。实践上把外推出来的耗时乘以 1.3 到 1.5 当作预期，并且在预演阶段就把限流错误率记下来——如果 1000 条时已经出现限流，全量必然更严重，这时应该先调并发度而不是直接放全量。
