PY49 · Pandas 核心模型与陷阱

Pandas 的怪异行为，九成能归到同一个根因上：它不是二维数组，而是「带标签的列的集合」。你以为在按位置操作，它其实在按标签对齐；你以为在改原表，它其实在改一个临时结果。把「当下这个对象的索引是什么、它是不是原表本身」这两个问题随时能答出来，怪异感就消失了。

一、索引是 Pandas 的灵魂，也是麻烦之源

很多人把 DataFrame 当成「带列名的二维数组」，这个心智模型能支撑前两周的日常使用，然后就会在一个具体现象上崩掉：两列相加，结果里冒出一大片缺失值，而两列本身都是满的。这不是 bug，是你用错了模型。

DataFrame 真实的结构是三部分：若干列数据，加上一个行索引（df.index）和一个列索引（df.columns）。索引不是装饰，它参与运算——几乎所有二元运算都会先按索引对齐（align），再逐位置计算。两个操作数的索引取并集，只在一边出现的标签，结果里就是缺失值。

a = Series([1, 2, 3], index=[0, 1, 2]) b = Series([10, 20, 30], index=[1, 2, 3]) a + b 做的不是「逐位相加」，而是先对齐： a b 对齐后 a + b idx val idx val idx a b idx val 0 1 1 10 0 1 NaN 0 NaN ← b 没有 0 1 2 2 20 1 2 10 1 12 2 3 3 30 2 3 20 2 23 3 NaN 30 3 NaN ← a 没有 3 索引取并集 → 只在一边出现的标签，结果必定是缺失值 长度一样、看着能对上，也不代表标签能对上

这个机制在两种场合下会咬人。第一种是筛选之后：df[df["amt"] > 0] 保留了原来的行索引，于是它的索引变成了 0、3、7、11 这样带洞的序列；把它的某列和另一张表的列相加，标签自然对不上。第二种是不同来源拼装：两份分别读进来的数据各自从 0 开始编号，行数相同、顺序也相同，但它们的第 5 行在业务上并不是同一条记录，对齐只是让错误变得更隐蔽。

按位置还是按标签：两套语义的适用场合

维度NumPy 数组（按位置）Pandas（按标签对齐）
二元运算的配对依据元素的下标位置索引标签；标签取并集
两边长度不同报错，或按广播规则扩展不报错，结果变长，缺的位置补缺失值
长度相同但语义错位静默算错静默算错（标签恰好都是 0..n-1 时）
行被筛掉之后下标重新从 0 开始标签保留原值，出现「空洞」
擅长的事规整的数值矩阵、线性代数异构列、键关联、时间序列重采样
典型故障表现形状不匹配报错（早暴露）结果里多出缺失值或多出行（晚暴露）

对齐不是缺陷，它是 Pandas 处理真实业务数据的核心能力：两份时间序列采样点不完全一致时，按时间戳对齐远比按位置硬拼正确。代价是它把「错位」从一个立刻报错的问题变成了一个安静产出脏数据的问题。所以纪律很明确：拼装数据之前先看一眼索引。如果索引本身没有业务含义（只是自增编号），reset_index(drop=True) 让两边归一；如果索引有业务含义（订单号、时间戳），那就该走第五节的合并，而不是并排相加。

left = df_a.reset_index(drop=True)
right = df_b.reset_index(drop=True)
assert left.index.equals(right.index)          # 拼装前先确认
df = left.assign(total=left["qty"] * right["price"])

s = df_a["qty"].add(df_b["qty"], fill_value=0)  # 想要「缺就当 0」必须显式说
total = df_a["qty"].to_numpy() + df_b["qty"].to_numpy()  # 想按位置就退到数组

最后一行值得记住：.to_numpy() 是「我确认要按位置算」的显式声明，它把对齐语义主动关掉。这比让对齐在背后悄悄发生要安全得多。容器语义的基础在 PY03，Pandas 的列与 Python 的 list 是两种完全不同的东西——前者是同质的连续内存块，后者是指针数组。

看到「明明两列都是满的，相加却出现一堆缺失值」，不要去找数据里的空值，去打印两边的 .index。九成是标签对不上。

二、选择与赋值：loc、iloc，以及为什么链式赋值不可靠

Pandas 的选择语法多到让人无从选择：df["a"]、df[["a","b"]]、df[3:5]、df.loc[...]、df.iloc[...]、df.at[...]。看着是「风格问题」，实际不是——其中一部分只能读，另一部分才能写，混用会让赋值静默失效。

先把两个主力分清：.loc 是按标签选，参数是索引里的标签值和列名，切片两端都包含；.iloc 是按位置选，参数是从 0 开始的整数下标，切片和 Python 一样左闭右开。两者都接受「行, 列」两个参数，这是它们能用来赋值的关键。

写法依据切片端点能用来赋值吗说明
df["col"]列名—整列替换可以取单列为 Series，最常用的读法
df[["a","b"]]列名列表—不要结果是新对象，改它不影响原表
df[3:5]行位置左闭右开不要方括号里放切片时含义突然变成行，容易误读
df.loc[行标签, 列名]标签两端都含是，首选布尔数组也走这里：df.loc[mask, "col"]
df.iloc[行位置, 列位置]位置左闭右开是索引是乱序或非整数时用它定位「第几行」
df.at[] / df.iat[]标签 / 位置—是，单个值只取单元格，比 loc 快，循环里偶尔有用

注意第三行那个坑：df["a"] 选的是列，而 df[3:5] 选的是行。同一个方括号，参数类型一变含义就变。这也是为什么写生产代码时应当只用 .loc 和 .iloc——它们的行、列两个位置永远在固定的地方，不靠猜。

链式赋值：赋值可能落在一个临时对象上

链式赋值指的是用两步方括号完成一次修改，比如 df["amt"][df["ok"]] = 0 或 df[df["ok"]]["amt"] = 0。它不可靠的原因很直接：这是两次独立的操作。第一步先取出一个中间结果，第二步再往这个中间结果上写。中间结果究竟是原表数据的视图（共享内存，写进去会反映到原表）还是拷贝（独立内存，写进去就丢了），取决于列的 dtype 是否一致、块的内部布局、选的是行还是列等一堆实现细节。

df.loc[mask, "amt"] = 0 一次操作，目标明确 ┌──────────────────────────┐ │ df 自己收到 setitem │ ──► 直接改 df 的那块内存 ✔ └──────────────────────────┘ df["amt"][mask] = 0 两次操作，第二次目标不确定 ┌─────────────┐ ┌──────────────────────────────┐ │ 取 df["amt"]│ ──► │ 临时 Series（视图？拷贝？） │ └─────────────┘ └──────────────┬───────────────┘ │ setitem 写在这里 ▼ 是视图 → 原表变了（旧版本的偶然成功） 是拷贝 → 写进临时对象，语句结束就被丢掉 pandas 3.0 起：恒定是后者，且会警告

这就是 SettingWithCopyWarning 的真实含义。它经常被理解成「你的写法不规范」，其实它在说的是一句更弱的话：「我不确定你刚才改的是谁。」它是一个启发式警告——既会在真的丢了修改时报，也会在修改其实生效了的时候报，还会漏报一部分真正出问题的情况。这种「不准的警告」比没有警告更折磨人，因为团队很快就学会了用 .copy() 到处消音，而消音并不等于修好。

正确写法只有一条：一次性用 .loc 同时定位行和列，让 df 本身收到这次赋值，中间不产生任何临时对象。

df.loc[df["status"] == "void", "amount"] = 0          # ✔ 一步到位
df.loc[:, "rate"] = df["amount"] / df["total"]        # ✔ 整列写入

df["amount"][df["status"] == "void"] = 0              # ✘ 链式，可能丢
df[df["status"] == "void"]["amount"] = 0              # ✘ 链式，几乎必丢
sub = df[df["amt"] > 0]
sub["flag"] = 1                                        # ✘ 改的是筛选结果
sub = df.loc[df["amt"] > 0].copy()                     # ✔ 想要独立副本就说清

写时复制让这套语义变确定了

Pandas 长期以来「有时是视图有时是拷贝」的不确定性，在 写时复制（Copy-on-Write，CoW）机制下被彻底消掉了。它的规则只有一句：任何索引操作或返回新对象的方法，其结果在语义上一律视为拷贝——改它永远不会影响原对象；而底层的实际复制被推迟到真正发生写入时才做，所以「语义上都是拷贝」并不意味着到处都在复制内存。

行为pandas 2.x 默认pandas 3.0（CoW，默认且唯一）
切片/取列的结果可能是视图，可能是拷贝语义上一律当拷贝
链式赋值 df["a"][m]=v可能生效、可能静默丢失恒定不生效，并抛 ChainedAssignmentError 警告
SettingWithCopyWarning存在，启发式，误报漏报都有已移除（不再有歧义，无需此警告）
防御性 .copy()常被用来消音不再需要；只在确实想要独立副本时写
mode.copy_on_write 选项可开启（1.5 起可选）已无作用，标记弃用，计划 4.0 移除
方法上的 copy= 参数有效无作用，已弃用，可直接删掉

数据截止 2026-06 · pandas 3.0.0 发布于 2026-01-21，CoW 在该版本成为默认且唯一模式，SettingWithCopyWarning 同版本移除；pandas 3.0 要求 Python 3.11 及以上。以官方 whatsnew/v3.0.0 与 Copy-on-Write 用户指南为准。

迁移提醒：CoW 带来的是破坏性变更，不是纯收益。旧代码里那些「靠视图生效」的链式赋值升到 3.0 后会静默失去效果——注意是数据不再被修改，而不是报错中断。官方给出的路径是先升到 2.3 并把警告清干净，再升 3.0。如果你的仓库里 .copy() 撒得很多，升级前正好可以把它们清掉：它们当初多半只是为了消掉那条不准的警告。

视图与拷贝这组语义在纯 Python 层的对应物是浅拷贝与深拷贝，PY10 讲了同一件事在对象层面的表现。两处的教训一致：「这个变量和那个变量是不是同一份数据」必须是确定的，靠不确定的默认行为写代码，早晚会赔。

只要你的修改语句里出现了两对方括号，就当它不会生效。把两步合成一个 .loc[行, 列]，这一类问题就永久消失。

三、dtype 与缺失值：内存和速度都由这一行决定

同一份数据读进来，占 200 MB 还是占 2 GB、聚合跑 0.3 秒还是 30 秒，主要不由行数决定，而由每列的 dtype 决定。这一节要解释三个最常撞上的现象。

为什么整数列一有缺失值就变成浮点

Pandas 的默认数值列直接建在 NumPy 数组上，而 NumPy 的整数类型没有任何位组合可以用来表示「缺失」——64 位整数的每一个取值都是一个合法整数。浮点类型不一样，IEEE 754 专门留了一类非数值编码（NaN），Pandas 历史上就借它当缺失值标记。于是逻辑链条很硬：一个 int64 列出现缺失值，就只能整列转成 float64 才装得下这个标记。

后果是真实的：float64 只能精确表示到 2 的 53 次方以内的整数，更大的整数 ID 会被悄悄改值；打印出来的 ID 会带上小数点；拿它去和别的表的整数键做合并会匹配不上。所以见到「用户 ID 列变成了 1000000123.0」，不要去改格式化，要去看这一列是怎么变成浮点的——通常是某一步左连接没匹配上。

解法是可空整数类型（Int64，注意首字母大写）。它在 int64 数组之外额外维护一个布尔掩码标记哪些位置缺失，因此能同时保住整数语义和缺失值。它是可选的（自 pandas 0.24 起提供），默认推断不会用它，得显式写 dtype="Int64" 或用 convert_dtypes()；它的缺失值标记是 pd.NA 而不是 NaN。

为什么 object 列慢，以及字符串列的现状

object dtype 的列不存值，存的是指向 Python 对象的指针。这意味着任何运算都要逐个解引用、进入 Python 对象层做方法调用，向量化带来的好处全部失效——性能退回到跟写 Python 循环差不多的量级，内存上除了每格一个指针，还要为每个对象本身付出 CPython 的对象头开销。PY23 解释了这份开销从哪来。

历史上字符串列只能落在 object 上，这是 Pandas 最大的性能包袱之一。现状是：pandas 1.0 起提供可选的 dtype="string"（缺失值用 pd.NA）；pandas 1.5 起可以用 Arrow 承载的字符串类型（IO 函数上统一的 dtype_backend="pyarrow" 参数自 2.0 起提供）；而 pandas 3.0 起专用字符串类型成为默认——推断字符串列时用 str 这个别名，装了 PyArrow 就由 Arrow 数组承载，没装则退回 NumPy 的 object，缺失值标记是 NaN，与其它默认类型保持一致。需要注意官方文档至今仍把 StringDtype 标为实验性，细节可能调整，所以关键链路上值得显式写死 dtype 而不是依赖推断。

另一条省内存的路是分类类型（category）。它把列拆成「一份去重后的取值字典」加「一列指向字典的小整数码」。对低基数列（唯一值远少于行数，比如省份、渠道、状态）收益很大：几百万行的省份列，原本每行都存一个字符串对象，转成分类后每行只剩一个一两字节的码。反过来，对高基数列（订单号、用户 ID）它是负优化——字典几乎和原列一样长，还多出一份码。

dtype能存缺失吗缺失表示单值内存量级什么时候选它

三种「空」不是一回事

业务数据里的「没有值」至少有三种互不相同的语义，而它们在代码里长得很像，混用会直接产出错误的业务结论。

语义典型表示参与求和参与计数混淆后的后果
缺失 / 未知NaN、pd.NA、NaT默认被跳过count() 不计它被当 0 会把均值拉低
真实的零0、0.0计入计入被当缺失会让「零消费用户」凭空消失
空字符串""不适用计入（非缺失！）isna() 查不到它，清洗时整批漏过

第三行最阴。空字符串在 Pandas 眼里是一个完全正常的值，isna() 返回假，dropna() 不会删它，fillna() 不会填它。数据从 CSV 或某些数据库驱动进来时，「这个字段没填」经常就表现为空字符串而不是缺失值。纪律是：读入后立刻把三种语义显式归一，把这件事写成一个函数并测试它，而不是每次分析时临时判断。缺失值的填充策略必须写在代码里而不是留在脑子里——fillna(0) 是一个业务决策，需要有人签字。

示例场景：一份 480 万行的订单明细，19 列，直接 read_csv 读进来占 3.1 GB，服务容器上限 4 GB，跑到聚合那步被内核杀掉。逐列看 memory_usage(deep=True) 后只改了三处：4 个低基数文本列（渠道、省份、状态、支付方式，唯一值都在 40 以内）转 category；2 个金额列从 float64 降到 float32；usecols 去掉 6 个本次分析根本没用到的列。内存降到 620 MB，聚合恢复正常。没有改一行业务逻辑——这类收益全部来自「读进来的那一刻用什么类型」。

拿到一份陌生数据，第一件事不是 head()，是 info(memory_usage="deep")。哪一列是 object、哪一列的整数莫名变成了浮点，这一眼就能看到，而这两件事决定了后面所有步骤的成本。

四、分组与聚合的心智模型：拆分、应用、合并

groupby 是 Pandas 里表达力最强也最容易写慢的一块。它的模型只有三步：拆分（按键把行分到各组）、应用（对每组做一件事）、合并（把各组结果拼回一个对象）。难点不在三步本身，而在第二步里「做一件事」有三种形状完全不同的做法，选错了后面就得靠 merge 或 reset_index 硬掰回来。

原表（按 shop 分组） 拆分 应用 合并 shop amt A 10 ┐ B 7 │ A: [10, 30] agg → A:40 缩成一行一组 A 30 │ ──► B: [7, 5] → B:12 结果行数 = 组数 B 5 │ A ?? ┘ transform → 每组算出的值广播回该组每一行 结果行数 = 原表行数，可直接赋回 filter → 整组保留或整组丢弃 结果行数 = 被保留组的行数之和 选错形状的代价：本来一句 transform 能解决的事， 变成 agg 之后再 merge 回去，多一次连接 = 多一次行数放大的风险

三类操作的区别值得掰开说清，因为这是 groupby 用得对不对的分水岭。

过滤 filterg.filter(lambda x: len(x) >= 10)≤ 原表行数不适用（是子集）只看订单数够 10 的店
通用 applyg.apply(fn)看 fn 返回什么看情况前三类都表达不了时的兜底

transform 是被低估得最厉害的一个。「每行减去本组均值」「每行占本组总额的比例」「组内排名」这类需求，用它是一句话，而且结果索引与原表完全一致，直接 df["dev"] = g["amt"].transform("mean") 就赋回去了。换成「先 agg 出一张小表再 merge 回来」不只是多写几行，而是多引入了一次连接——第五节会讲，连接是行数意外膨胀的主要来源。

g = df.groupby("shop_id")

df["shop_avg"] = g["amt"].transform("mean")        # ✔ 形状不变，直接赋回
df["share"] = df["amt"] / g["amt"].transform("sum")

summary = g.agg(total=("amt", "sum"), cnt=("amt", "size"))   # 命名聚合，列名明确
big = g.filter(lambda x: len(x) >= 10)             # 按组筛，返回原表的子集

为什么逐组调用 Python 函数会慢一个数量级

g.sum() 和 g.apply(lambda x: x.sum()) 在结果上可能一样，在执行路径上完全不同。前者走的是 Pandas 内部用 C 实现的聚合：一次遍历，在原生类型上累加，Python 解释器全程不介入循环。后者要为每一个组构造一个 Pandas 对象、回到 Python 层调用你的函数、再把返回值收集拼装——组数有几万，这套开销就付几万遍。慢多少取决于组数和函数复杂度，但这是一个量级上的差别，不是常数上的差别，而且组越碎差距越大。

这跟 PY42 的结论一致：真正的加速来自换掉执行层，而不是在同一层里抠常数。判据很简单——如果你要做的事内置聚合能表达（sum、mean、size、nunique、quantile、first…），或者能用 agg 字符串名、transform 字符串名表达，就不要写 apply。apply 是兜底手段，不是默认手段；写下它之前先确认前三类真的表达不了。

另外两个容易被忽略的点。一是分组键里有缺失值时，默认整组被丢掉（dropna=True），聚合结果的总和于是对不上原表——需要保留就显式写 dropna=False。二是分组键是分类类型时，observed 参数决定是否把没出现过的类别也列出来；这个参数的默认值在 pandas 3.0 从 False 改成了 True，跨版本跑同一段代码结果行数可能不同，值得显式写出来。

先问「我要的结果是几行」：跟组数一样多就用 agg，跟原表一样多就用 transform，是原表的一个子集就用 filter。答对这一题，代码基本就写对了。

五、合并与重塑：行数膨胀是最常见的静默错误

merge 的语法很像 SQL 的 join，所以大家学得很快，也因此容易忽略一个 SQL 里同样存在、但在数据管道里破坏力更大的问题：连接不保证行数。你以为在给左表「贴上几列」，实际上如果右表的连接键不唯一，左表的每一行会按右表匹配到的条数被复制出多份。这就是笛卡尔放大。

左表 orders（3 行） 右表 profile（键不唯一！） oid uid uid city snapshot 1 u1 u1 北京 2026-05-01 2 u1 u1 北京 2026-05-02 ← 同一个 uid 三行 3 u2 u1 上海 2026-05-03 u2 广州 2026-05-01 merge(左, 右, on="uid", how="left") 之后： oid=1 → 3 行 uid=u1 在右表匹配到 3 条 oid=2 → 3 行 oid=3 → 1 行 ──────────────── 合计 7 行，不是 3 行。金额一求和就是 3 倍多的假数字。 校验只看「非空」是查不出来的：每一行都非空，只是行变多了

为什么这个错误特别难发现？因为它不报错、不产生缺失值、每一行看起来都合法，只是行数变了。所有基于「字段不为空」「取值在枚举范围内」的数据质量检查都会全绿放行。它唯一的外部表现是下游的求和、计数类指标整体偏大——而如果偏大的幅度不夸张，可能几天都没人注意到。

事故复盘：某日 09:12，运营反馈昨日日报的 GMV 从往常的 710 万跳到 4120 万。管道本身没报任何错，调度全绿。排查发现问题出在一次左连接：订单明细 182,431 行，连上用户画像维表之后变成 1,058,204 行（放大约 5.8 倍）。根因在上游——画像表两天前改成了按天写快照，从「一个用户一行」变成了「一个用户每天一行」，而下游这次 merge 只按 user_id 连。管道的质量校验只检查了关键字段非空和枚举合法，完全没有校验行数，所以一路放行。
影响面：日报邮件（已发出，含管理层）、2 个看板的日活与 GMV 卡片、1 个下游的渠道归因任务（用了错误的 GMV 做分母）。从收到反馈到定位根因耗时 3 小时 28 分，其中 2 小时多花在逐个怀疑业务逻辑上；真正的修复只用了 约 40 分钟：连接键补上 snapshot_date，并给这次 merge 加上 validate="m:1" 和一行行数断言。
教训不是「要小心 merge」，而是行数是一个必须被断言的契约。如果第一天就写了那行断言，这个故障会在上游改动的当晚直接让任务失败，成本从 3 小时变成 3 分钟。

纪律因此有两条，都很便宜：合并前检查键的唯一性，合并后检查行数。Pandas 自带了做这件事的参数，不需要自己写检查逻辑——validate= 会在关系不符合声明时直接抛异常，这正是 PY24 讲的快速失败：让错误在发生的地方炸掉，而不是让它变成一份看起来很正常的报表。

assert right["uid"].is_unique, "右表键不唯一，先去重或补齐连接键"

before = len(left)
df = left.merge(right, on="uid", how="left", validate="m:1", indicator=True)
assert len(df) == before, f"行数从 {before} 变成 {len(df)}"

miss = (df["_merge"] == "left_only").sum()      # 没匹配上的左表行数

validate 接受 "1:1"、"1:m"、"m:1"、"m:m" 四种声明，它把你脑子里的假设写成了机器能检查的东西。indicator=True 则会加一列 _merge 标出每行来自哪边，用来量化「没匹配上多少」——左连接后不声不响多出一堆缺失值时，先看这一列。

四种连接方式，各自会怎么改变行数

how保留哪些键行数相对左表右键唯一时右键不唯一时
left左表全部≥ 左表行数恰好等于左表行数按匹配条数放大
inner两边都有的键≤ 或 ≥ 都可能≤ 左表行数（丢掉没匹配的）既可能丢行又可能放大
outer两边的并集≥ 左表行数左表行数 + 右表独有键数放大后再加独有键
right右表全部由右表决定= 右表行数= 放大后的右表行数
cross不用键，全组合左 × 右行数必然爆炸，只在确实需要全组合时用

inner 那一行是另一个常见陷阱：它既可能放大也可能丢行，而丢行同样不报错。用 inner 做「贴字段」的操作时，没匹配上的左表行会静默消失，指标于是偏小。想贴字段就用 left，让没匹配上的变成缺失值——缺失值是看得见的，消失的行是看不见的。

长宽转换：用途与坑

宽表每个指标一列（日期, 北京, 上海, 广州），适合人看和直接出表；长表把指标名也变成数据（日期, 城市, 值），适合机器处理——新增一个城市不需要改表结构，分组、筛选、绘图全都自然。melt 做宽转长，pivot / pivot_table 做长转宽，stack / unstack 则是在多层索引的层级之间搬动。

最常踩的坑是 pivot 和 pivot_table 的区别：pivot 只做形状重排，要求「行键 + 列键」组合唯一，有重复会直接抛 ValueError；pivot_table 会对重复组合做聚合（默认求均值）。这里有个隐蔽风险——用 pivot_table 当作 pivot 的「更宽容版本」，遇到重复数据时它不报错，而是默默把几条记录平均掉了。想重排就用 pivot，让重复暴露出来；想聚合就用 pivot_table，并且显式写 aggfunc，不要依赖默认值。另外 unstack 会把长表铺成宽表，如果被铺开的那一维基数很高（比如商品 ID），列数会瞬间膨胀到内存放不下。

连接和重塑是管道里唯一会改变行数的两类操作，也是唯一会静默产出假数字的两类操作。在它们前后各加一行行数断言，成本是两行代码，省下的是一个下午。

六、性能与内存纪律：按收益排序，不按顺手排序

Pandas 的优化手段网上有几十条，但收益差距极大，而且顺序几乎是固定的。按下面的次序做，绝大多数场景在前两条就够了；跳过前两条去抠后面的，属于在错误的层面上花时间。

① 不要逐行遍历

这是收益最大的一条，没有竞争对手。for idx, row in df.iterrows(): 看起来很自然，实际上把 Pandas 最核心的优势关掉了：它为每一行构造一个 Series 对象，让你在 Python 解释器里逐行处理，等于把 C 层的批量计算换成了解释执行的循环。更糟的是 iterrows 会丢 dtype——一行里混着整数和字符串时，返回的 Series 会被统一提升成 object，你拿到的整数可能已经不是整数了。

itertuples() 比 iterrows() 快不少（它用命名元组，不构造 Series，也保留 dtype），但那只是把一个很慢的做法变成一个没那么慢的做法，量级没变。真正的替代是：算术用列运算，条件赋值用 np.where 或 df.loc[mask, col] = v，多分支用 np.select，按键汇总用 groupby 的内置聚合，查表用 map 或 merge。

# ✘ 逐行：解释执行，还会丢 dtype
for i, row in df.iterrows():
    df.loc[i, "fee"] = row["amt"] * 0.03 if row["vip"] else row["amt"] * 0.05

# ✔ 向量化：一次算完整列
df["fee"] = df["amt"] * np.where(df["vip"], 0.03, 0.05)

# ✔ 多分支用 np.select，按顺序取第一个成立的条件
df["tier"] = np.select([df["amt"] > 1000, df["amt"] > 100], ["A", "B"], default="C")

② 读取时就把类型和列定下来

第二条收益同样很大，而且实现成本最低：read_csv 时用 usecols 只读要用的列，用 dtype 指定每列类型。好处有两层——少读的列不占内存也不花解析时间；而显式给 dtype 还能省掉 Pandas 的类型推断，顺带消掉「同一列在不同数据块里被推断成不同类型」这类警告，以及第三节说的整数列被动变浮点的问题。日期列用 parse_dates 一次转好，别留在字符串里等后面 to_datetime 再扫一遍。

③ 不要在循环里反复拼接

df = pd.concat([df, new_rows]) 写在循环里，是一个隐蔽的平方级复杂度陷阱：每次拼接都重新分配内存并复制已有的全部数据，循环 n 次就复制了 n 次逐渐变大的数据。正确做法是先把各块收集到一个列表里，循环结束后 pd.concat(chunks) 一次拼完。顺带一提，老代码里的 df.append(...) 已经在 pandas 2.0 被移除（1.4 起弃用），遇到它直接改成收集加一次 concat。

④ 内存真的不够时，换策略而不是硬扛

前三条做完还装不下，说明这份数据的规模已经超出「整体读进内存」这个模式。此时有三个方向：read_csv(chunksize=...) 分块读、逐块聚合再汇总，适合可分解的统计；把中间结果落成列式存储（Parquet）而不是 CSV，读的时候只取需要的列；或者换用支持惰性执行与流式处理的工具——Polars、DuckDB、PyArrow 这一类，它们能在不把全量数据装进内存的前提下完成查询。Polars 的模型与取舍是下一张卡的主题，这里只说判据：当你开始为了内存而牺牲代码清晰度时，就该考虑换工具了。

手段收益量级代价什么时候值得做
去掉逐行遍历，改向量化 / 内置聚合最高，量级上的差别要重写逻辑；分支多时可读性下降只要代码里有 iterrows，无条件先做
读取时指定 dtype + usecols高，内存与解析时间同降几乎没有；要事先知道 schema数据源固定的管道，第一天就写上
低基数列转 category中到高，主要省内存后续赋新值要先加类别；部分操作行为不同唯一值远少于行数的文本列
数值列降位宽（float32/int32）中，内存对半精度与取值范围变小，要先确认边界已知量程、且内存是瓶颈
循环里的 concat 改成收集后一次拼中到高，看循环次数几乎没有见到循环里有 concat 就改
用 transform 替掉 agg 再 merge中，还顺带去掉一次连接需要理解三类操作的区别需求是「组内统计量贴回每一行」
分块读取 / 换列式存储取决于数据量代码结构要改；逻辑必须可分解单机内存装不下全量
换惰性 / 流式引擎取决于查询与数据量新依赖、新 API、团队学习成本前面都做完仍然不够用

这张表的顺序不是绝对的，但有一件事是绝对的：动手之前先测量。哪一列吃内存看 df.memory_usage(deep=True) 和 df.info(memory_usage="deep")，哪一步吃时间按 PY42 的方法剖析。Pandas 的性能直觉特别不可靠——同一个操作在不同 dtype 上可以差出一个量级，凭感觉改很容易改到不相干的地方。

  • 拼装数据前确认索引；没有业务含义就 reset_index(drop=True)
  • 读写一律用 .loc[行, 列] / .iloc[行, 列]，一步到位
  • 读入时显式给 dtype 和 usecols，日期用 parse_dates
  • ID 类列保住整数语义：Int64 或字符串，别让它变浮点
  • 合并前 is_unique 校验键，合并时写 validate=，合并后断言行数
  • 「组内统计量贴回每一行」用 transform，不要 agg 之后再 merge
  • 缺失值 / 零 / 空字符串读入后立刻归一，并为这段清洗写测试
  • 改动前先 info(memory_usage="deep") 和剖析，别凭直觉优化
  • 用 iterrows 逐行算列——慢一个量级，还会丢 dtype
  • 写两对方括号做赋值（df["a"][mask] = v），pandas 3.0 起恒定无效
  • 用 .copy() 消掉警告了事，而不去查「到底改的是谁」
  • 在循环里 pd.concat；或继续用已被移除的 df.append
  • 用 inner 做「贴字段」——没匹配上的行会静默消失
  • 把 pivot_table 当 pivot 用，让重复数据被默默平均掉
  • 只校验「字段非空」就认为数据没问题，不看行数
  • 高基数列转 category，或对全表无脑 astype 降位宽

Pandas 的正确用法可以概括成一句话：让每一步都作用在整列上，让每一步的行数都是你预期的。前半句管性能，后半句管正确性，两句都做到，剩下的都是细节。

Q&A

两列相加为什么会冒出一堆缺失值？数据里明明没有空值
因为 Pandas 的二元运算先按索引对齐再计算，而不是按位置逐个相加。两个操作数的索引取并集，只在一边出现的标签在结果里就是缺失值。最常见的触发方式是其中一个 Series 来自筛选：df[df["amt"] > 0]["qty"] 保留了原来的行索引（比如 0、3、7、11），把它和一个从 0 连续编号的 Series 相加，能对上的标签寥寥无几，结果自然满是缺失。排查方式是打印两边的 .index 而不是去找空值。修法看意图：如果索引只是自增编号、两边行序确实一致，就都 reset_index(drop=True)；如果索引有业务含义，那这件事本质上是一次连接，应该用 merge；如果你确实想按位置算，就显式 .to_numpy() 把对齐关掉。
SettingWithCopyWarning 到底在说什么？看到它怎么处理
它在说的不是「你写错了」，而是一句更弱的话：「我不确定你刚才修改的是原表还是一个临时对象。」触发它的典型写法是链式赋值——先用一次索引取出中间结果，再往中间结果上写。这个中间结果可能是共享内存的视图（写进去会反映到原表），也可能是独立的拷贝（写进去就丢了），取决于 dtype、内存块布局等实现细节。它是启发式的，既会误报也会漏报，所以拿 .copy() 消音是最差的处理方式：警告没了，但「改的是谁」这个问题依然没有答案。正确处理是把两步索引合成一步 df.loc[行, 列] = 值，让 df 自己收到这次赋值。在 pandas 3.0 中这条警告已经被移除，因为 CoW 让链式赋值恒定无效、不再有歧义。
pandas 3.0 的写时复制会不会把我的老代码改坏？
会，而且它是破坏性变更而不是纯优化，需要专门安排迁移。pandas 3.0.0（2026-01-21 发布）把 CoW 设为默认且唯一模式：任何索引操作或返回新对象的方法，结果在语义上一律视为拷贝，改它不会影响原对象。受影响最大的是那些「靠视图偶然生效」的链式赋值——升级后它们不再修改数据，但也不会报错中断，只会抛一条 ChainedAssignmentError 警告，程序继续跑，结果静默变了。这类故障比崩溃难查得多。官方建议的路径是先升到 2.3、把警告清干净，再升 3.0。同时 mode.copy_on_write 选项已无作用并标记弃用（计划 4.0 移除），各方法上的 copy= 参数也不再有效，可以直接从代码里删掉。此外 3.0 还有别的破坏性变更（默认字符串类型、datetime 精度推断、groupby 的 observed 默认值等），建议整体读一遍 whatsnew 而不是只看 CoW。
为什么整数列一有缺失值就变成浮点？怎么避免
因为默认的数值列建在 NumPy 数组上，而 NumPy 的整数类型没有任何位组合可以表示「缺失」——每个取值都是合法整数。浮点类型有 IEEE 754 的非数值编码（NaN）可以借用，所以一个 int64 列出现缺失时只能整列升成 float64。这不只是显示问题：float64 只能精确表示 2 的 53 次方以内的整数，更大的 ID 会被悄悄改值，还会导致和别的整数键合并时匹配不上。避免方式有三条。一是用可空整数 Int64（首字母大写，pandas 0.24 起提供），它额外维护一个布尔掩码来标记缺失，缺失值是 pd.NA；注意它是可选的，默认推断不会用它，得显式写 dtype="Int64"。二是如果这一列只是标识符、不参与算术，干脆存成字符串更安全。三是从源头看：整数列变浮点往往是某次左连接没匹配上造成的，先去查那次连接。
groupby 之后该用 agg、transform 还是 apply？
先问自己「我要的结果是几行」，答案直接决定选哪个。要一组一行（每个店的总额）用 agg；要和原表一样多行（每一单相对本店均值的偏差、占本店总额的比例、组内排名）用 transform，它形状不变、索引与原表一致，可以直接赋回 df 的新列；要按组整体保留或丢弃（只看订单数够 10 的店）用 filter。apply 是前三类都表达不了时的兜底，不是默认选项——它要为每个组构造 Pandas 对象、回到 Python 层调你的函数、再收集拼装，组数一多就是量级上的性能损失。特别提醒一个常见的绕路：需求是「组内统计量贴回每一行」时，用 agg 算出小表再 merge 回去不只是多写几行，而是多引入了一次连接，也就多了一次行数放大的风险；transform 一句话就解决，且不碰行数。
merge 之后行数变多了，怎么定位和防止
行数变多只有一个根因：连接键在右表不唯一，于是左表每一行按右表匹配到的条数被复制成了多份。定位分两步——先 right["key"].is_unique 确认唯一性，再 right["key"].value_counts() 看哪些键重复、重复几次，通常能直接指向上游的某次改动（比如维表从「一个实体一行」改成了「一个实体每天一行」，那就该把日期也加进连接键）。防止的手段是把假设写成机器能检查的东西：merge(..., validate="m:1") 声明「多对一」，关系不符时直接抛异常；再在调用前后各记一次 len(df) 并断言相等。另外加上 indicator=True 能得到一列 _merge，用来量化有多少左表行没匹配上。这三样都很便宜，而它们防的是「不报错、不产生空值、每行都合法，只是指标整体偏大」这种最难发现的错误。
Pandas 慢的时候，该按什么顺序优化？
按收益从大到小，顺序基本固定。第一位是去掉逐行遍历：iterrows 为每行构造一个 Series、把计算拉回 Python 解释器执行，还会把混合类型的行提升成 object 丢掉 dtype；改成列运算、np.where、np.select、groupby 内置聚合是量级上的差别。itertuples 只是没那么慢，不算解法。第二位是读取时就定好类型和列：usecols 少读列、dtype 省掉类型推断，成本几乎为零。第三位是 dtype 层面的收敛：低基数文本列转 category、确认过量程的数值列降位宽。第四位是去掉循环里的 concat（每次都重新分配并复制全量数据，是平方级复杂度），改成收集后一次拼。这些都做完还是不行，才考虑分块读取、换 Parquet 这类列式存储，或换用支持惰性与流式的引擎。全程的前提是先测量：内存看 memory_usage(deep=True)，耗时按 PY42 的方法剖析。Pandas 的性能直觉很不可靠，同一操作在不同 dtype 上能差一个量级。
