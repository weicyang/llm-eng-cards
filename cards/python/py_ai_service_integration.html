把模型接进业务系统，难点从来不在「怎么发出那次调用」，而在于你的系统里第一次出现了一个输出不可预测、延迟不可控、成本按量计费的组件。整卡讲的就是怎么在它周围搭出一圈可控的结构，让它的不确定性不外溢。

一、接入的四种形状：先选形状，再谈实现

「我们要接大模型」这句话在工程上至少对应四种完全不同的系统形状。选错形状之后，再怎么优化代码都救不回来——因为形状决定了延迟下限、成本量级和故障传播路径，而这三者恰恰是这类系统唯一真正难办的部分。

四种形状按「用户要不要在场等」由浅入深排列：同步直调把调用直接写在请求处理函数里；异步任务把耗时挪出请求链路，用任务号加轮询或推送回传结果；流式响应不缩短总时长，但把首字延迟压下去；离线预计算干脆在没人等的时候把结果算好存起来，在线只做一次查询。

同一个「给内容生成摘要」的需求，四种形状下用户到底在等什么 ────────────────────────────────────────────────────────── ① 同步直调 用户点击 ──▶ 业务进程 ──▶ 模型服务 ──▶ 组装 ──▶ 返回 └─────────────── 用户全程干等 ────────────────┘ 用户可见延迟 = 下游完整生成时间；下游抖动原样变成用户可见抖动 ② 异步任务 + 轮询/推送 用户点击 ──▶ 入队 ──▶ 立刻返回任务号（毫秒级） │ ▼ 后台工作进程消费，和请求链路彻底解耦 模型服务 ──▶ 结果落库 ──▶ 推送 / 被轮询到 用户可见延迟 = 拿到任务号的时间；真正的耗时被挪出了请求链路 ③ 流式响应 用户点击 ──▶ 建立长连接 ──▶ 首块 ──▶ 续块 ──▶ … ──▶ 结束 ↑ 首字延迟比 ① 的总延迟小一个量级 总时长与 ① 相当，但「第一眼看到东西」的时间大幅提前 ④ 离线批量预计算 定时任务 ──▶ 批量调用 ──▶ 结果写入存储/缓存 在线请求 ──▶ 查一次存储 ──▶ 返回 在线链路里根本没有模型调用，延迟回到普通接口的量级
形状用户可见延迟单位成本实现复杂度适合什么
① 同步直调最高，等于下游全程按调用量，无摊薄最低，一个函数调用低频、必须即时给结论、且下游够快的场景
② 异步任务毫秒级（只返回任务号）与 ① 同量级中，要队列、结果存储、状态机耗时以十秒计的长任务，如长文处理、批量改写
③ 流式响应首字低，总时长同 ①与 ① 同量级中，要长连接、分块协议、中断处理人在屏幕前逐字阅读的交互式场景
④ 离线预计算最低，等于一次查询最低，可跨请求摊薄中高，要调度、失效策略、回填输入集合可枚举、结果可复用、时效要求不苛刻

表里最容易被低估的是第四行。很多团队默认「AI 功能必须实时算」，但大量场景的输入其实是可枚举的：商品有限、文章有限、标签体系有限。这类需求根本不需要在用户的请求链路里放一次模型调用——提前算好、存起来、在线查一次，延迟从秒级回到毫秒级，成本随复用次数摊薄。

能提前算的就不要在线算。在线算的每一次都要付延迟、付成本、承担一次失败风险；提前算只付一次，之后的每次读取都是白赚的。

四种形状不是互斥的。成熟系统通常是组合：热门输入走④的缓存，未命中回落到③的流式，超长输入转②的异步任务，而①只留给那些确实需要立刻拿到结构化结论的内部调用。选型的问题因此变成「这条请求该落到哪一档」，而不是「全站用哪一种」。

落档的判断顺序

按下面的顺序问四个问题，绝大多数需求在前两问就定下来了：

  • 输入集合可枚举吗？可以就先做④，把能提前算的部分算掉，剩下的才进在线链路。
  • 结果给人看还是给程序用？给程序用的结构化结果不适合流式，因为要等完整输出才能校验。
  • 下游耗时的高分位超过业务容忍上限吗？超过就转②，不要让用户替下游的长尾买单。
  • 这次调用会阻塞住一条更长的链路吗？会就不能用①，否则一处抖动会沿着链路向上放大。

注意第三问看的是高分位而不是均值。这类下游的耗时分布通常很偏——均值一秒、P99 十几秒是常态，而决定用户体验和上游超时是否被击穿的，永远是尾部那一段。

二、把不确定性围起来：三道墙

传统系统里，你调用的每个组件都有确定的契约：给定输入，要么返回符合约定的结构，要么抛出可枚举的错误。接入模型之后，这个前提第一次不成立了——同样的输入可能得到措辞不同、结构不同、偶尔根本不合法的输出，而且没有任何一次调用能保证「这次一定对」。

这个差别不能靠「把提示词写好一点」来抵消。提示词是概率性的引导，它能把不合规输出的比例从两成压到千分之几，但压不到零；而工程上要的是「不合规输出一定不会流到下游」这种确定性保证。把千分之几乘上日均几十万次调用，仍然是每天几百次事故。所以提示词和校验不是二选一，前者降低发生率，后者负责兜底，缺一不可。

三道墙：让不确定性停在边界内 ─────────────────────────────────────────────────────────────── 第一道墙 第二道墙 请求 ──▶ ┃ 输入校验 / 规范化 ┃ ──▶ ┃ 不确定的核心 ┃ ──▶ ┃ 输出契约校验 ┃ ──▶ 下游 · 长度上限 · 模型调用 · 结构是否合法 · 字段白名单 · 超时 / 重试 · 取值是否在域内 · 敏感内容前置拦截 · 并发上限 · 业务不变量是否成立 │ │ │ └──────── 任一环节失败 ────────┴──────────┘ ▼ ┃ 第三道墙：降级路径 ┃ · 返回缓存里的旧结果 · 退到规则/模板结果 · 明确告知「本次不可用」并保留重试入口 ← 关键：降级是被测试过的正常分支，不是异常兜底
墙挡住什么典型做法缺了它会怎样
输入侧校验与规范化超长输入、异常字符、来源不可信的拼接内容长度截断、字段白名单、把用户内容与指令分区放置单次成本失控；外部内容影响到指令区的语义
输出侧契约校验结构不合法、字段缺失、取值越界、自相矛盾先解析成结构化对象，再逐条校验业务不变量，不合格直接拒绝脏数据写进数据库，事后清洗的代价远大于当场拒绝
全链路降级下游超时、限流、配额耗尽、校验连续失败缓存旧结果 / 规则结果 / 明确的不可用响应一个外部依赖的抖动直接变成整条业务线不可用

第二道墙有个常见误区：把校验写成「解析失败就重试一次」。重试对偶发的格式抖动有效，但对系统性偏差无效——如果提示词或模型版本导致输出稳定地少一个字段，重试只是把一次失败变成三次失败，成本翻三倍、延迟翻三倍，结果一样。所以重试必须带上限，并且失败计数要按「解析失败 / 校验失败 / 下游报错 / 超时」分类统计，这几类的处置方式完全不同。异常体系的设计方法见 PY24 异常体系设计，重试与超时的并发写法见 PY31 取消、超时与限流。

def call_with_contract(payload, *, max_attempts=2):
    for attempt in range(max_attempts):
        raw = invoke_model(payload)          # 可能超时，由调用方设上限
        try:
            result = parse_and_validate(raw)  # 结构 + 取值域 + 业务不变量
        except ContractError as exc:
            record_failure("contract", exc, attempt=attempt)
            continue
        return result
    return fallback_result(payload)          # 降级是正常分支，不是兜底

这段代码的形状比细节重要：调用被包在一层契约里，失败被分类记录，最终一定有一个确定的返回值。注意 fallback_result 必须和主路径一样被测试覆盖——降级路径最典型的故障模式是「上线一年没走过，真需要它的那天发现它自己也会抛异常」。测试工程化的做法见 PY41 pytest 与测试工程化。

示例场景：某内容审核功能要求模型返回一个枚举标签，开发时抽查两百条都正常，于是直接把返回字符串写进了数据库的枚举列。上线第六天，某批输入触发模型在标签外多写了一句解释，写库时触发约束异常，接口 5 分钟内错误率从 0.2% 升到 31%。修复只用了一行——把「直接写库」改成「先映射到枚举，映射不到就走降级」。教训是：不确定的输出与确定的存储之间，必须隔一层显式映射，不能让模型的输出直接成为数据库里的值。

不确定性无法消除，只能围住。围墙的判断标准很具体：假设模型这一次返回的是一段完全无关的文本，你的系统会发生什么？如果答案不是「被拒绝并走降级」，墙就还没砌好。

三、状态与上下文放在哪

多轮对话、分步骤的长任务、需要「记得上一步」的流程，都会引入状态。这里最常见的起步写法是把会话状态放在进程内的一个字典里——本地测试完全正常，因为只有一个进程。一旦部署成多实例，它立刻暴露两个硬伤：同一个用户的下一次请求很可能被负载均衡分到另一个实例，那里没有他的历史；以及任何一次发布、重启、扩缩容都会让所有进行中的会话凭空消失。

进程内状态在多实例下为什么必然出错 ──────────────────────────────────────────────────────── 第 1 轮 第 2 轮 用户 ──▶ 负载均衡 ──▶ 实例 A 用户 ──▶ 负载均衡 ──▶ 实例 B │ │ 内存里存了历史 内存里空空如也 │ │ ▼ ▼ 回答正常 「我们刚才聊到哪了？」 再叠加一次发布：A 和 B 一起重启，所有进行中的会话全部蒸发 ──────────────────────────────────────────────────────── 外置之后 实例 A ─┐ 实例 B ─┼──▶ 外部状态存储（会话 ID 为键，带 TTL） 实例 C ─┘ │ └──▶ 任意实例都能接住任意一轮；重启不丢 代价：每轮多一次网络往返 + 需要处理并发写同一会话的竞争
放哪多实例下正确吗重启后还在吗适合
进程内字典否，请求可能落到别的实例否单进程的本地调试与原型，不要带上生产
带 TTL 的外部缓存是是（受 TTL 与淘汰策略约束）会话状态的默认选择，读写频繁、容忍过期
关系型数据库是是需要审计、回溯、与业务数据一起做事务的场景
客户端持有并回传是（服务端无状态）取决于客户端状态很小、且不介意被客户端篡改的场景

状态外置之后，第二个问题才浮出来：上下文不是免费的。每轮把完整历史重新发一遍，单次请求的输入长度会随轮次线性增长，而一次会话的累计消耗随轮次呈平方级增长。这不是优化项，是必须在设计阶段就定下策略的结构性约束——下一节的事故复盘正是踩在这一点上。

def build_context(system_prompt, history, *, keep_recent=6):
    # 固定头 + 摘要（更早的轮次压成一段） + 最近若干轮原文
    older, recent = history[:-keep_recent], history[-keep_recent:]
    parts = [system_prompt]
    if older:
        parts.append(summarize(older))   # 摘要本身也要缓存，别每轮重算
    parts.extend(recent)
    return parts

需要强调的是：裁剪策略是产品决策，不是技术细节。「只保留最近 6 轮」意味着用户在第 10 轮提到「你刚开始说的那个方案」时，系统已经不记得了；「把更早的压成摘要」意味着细节会丢，而丢掉的恰恰可能是用户认为最关键的那句。这些后果会直接被用户感知成「它变笨了」，所以策略必须由懂业务的人拍板，并且要有对应的观测指标——比如摘要触发率、以及触发摘要后用户追问同一问题的比例。

判断状态该不该外置，只需要问一句：如果现在把这个进程 kill 掉再拉起来，用户会不会发现？会，就说明状态不该待在进程里。

外置状态带来的三件新工作

把状态挪出进程不是免费的，它换来了正确性，同时带来三件必须处理的事。一是过期与清理：会话数据如果不设过期时间，存储会随时间单调增长，几个月后变成一笔无人认领的成本；过期时间应当由业务定义「一个会话多久没动就算结束」，而不是随手填一个数。二是并发写：同一会话的两个请求可能同时读到旧状态再各自写回，后写的覆盖先写的，需要用会话粒度的锁、版本号比对或只追加的记录结构来处理。三是序列化开销：状态每轮都要序列化、传输、反序列化，状态越大这笔固定开销越可观，所以外置的应当是「必须跨请求存活的最小集合」，而不是把整个上下文对象整个丢进去。

至于「怎么从海量历史里挑出该带上的那几条」，那是检索与记忆的方法论，属于另一个系列的范围，本卡只负责把工程放置问题讲清楚：状态外置、上下文有预算、裁剪策略要显式且可观测。

四、成本、配额与容量规划

传统服务做容量规划，看的是自己这几台机器的 CPU、内存和连接数。接了模型服务之后，这套方法会给出严重乐观的结论——因为容量上限通常不在你的机器上，而在下游：每分钟能发多少次请求、每分钟能消耗多少 token、账户上还有多少额度。你的进程可以轻松并发一千，但下游只放行一百，多出来的九百只会变成排队、超时和重试风暴。

容量要从下游配额往回推，而不是从本机资源往前算 ──────────────────────────────────────────────────────────── 下游给你的硬上限（每分钟请求数 / 每分钟 token 数 / 总额度） │ ▼ 除以「单次请求的平均 token」 本服务每分钟能安全发出的调用次数 │ ▼ 乘以「缓存命中后不需要调用的比例」 本服务每分钟能承接的业务请求量 │ ▼ 对照峰值并发 需要的排队深度与限流阈值 ──▶ 超出就拒绝，不要让它变成超时 │ └──▶ 本机 CPU / 内存通常远不是瓶颈， 这类服务绝大多数时间在等 I/O

反推的前提是四个数必须算清楚，缺一个都会让规划失真。它们不需要很精确，量级对了就有用。

要算清的数怎么拿到它决定什么
单次调用的平均 token 与相对成本抽样统计真实请求的输入 + 输出长度，而不是拿示例估成本模型的基数；也是「一次调用贵不贵」的唯一依据
峰值并发按业务高峰的每秒请求数乘以平均处理时长并发上限、排队深度、要不要转异步形状
日均调用量业务量乘以「每次业务触发几次调用」——这个倍数常被漏算日成本与配额是否够用
缓存命中率灰度期间实测，不要用拍脑袋的估计值成本的放大或缩小系数，影响往往比换模型还大
日成本 ≈ 日均调用量 × 单次平均 token × 单位价格 × (1 − 缓存命中率)

这个式子的价值在于它指出了四个可调的乘数。很多团队一提降本就只想着「换便宜的模型」，那只动了第三项；而前两项和第四项往往有更大的下降空间——把每次业务触发的调用次数从三次降到一次是直接除以三，把缓存命中率从 0 做到 0.6 是直接乘以 0.4。

还有一个反直觉的点：限流阈值必须设在配额之下，而且要留出重试的余量。如果你按配额的 100% 放行，那么任何一次重试都会把你推过线；越过线之后下游开始拒绝，你的重试逻辑又会把拒绝变成更多请求，几十秒内就能演化成一次自我放大的雪崩。实践中把放行阈值定在配额的 70%–80%，把剩下的留给重试和突发，是更稳的做法。超出阈值时正确的动作是立即拒绝并告知，而不是排队——排队只会把限流问题转化成超时问题，而超时更难排查、对用户也更糟。

多档模型分流与灰度换版本

成本优化的下一步是分档：不是所有请求都值得用最强的档位。分流依据应当是可判定的客观条件，而不是「感觉这个难」。

分流依据怎么判定走哪档
输入长度与结构复杂度token 数、字段数、是否含多步要求短而结构化的走轻档
任务类型分类/抽取/改写 vs 多步推理/生成长文前者轻档，后者重档
置信度与校验结果轻档输出未通过契约校验时升档重试一次先轻后重，只为失败的那部分付费
业务重要度付费用户、关键流程、对外展示内容重档，并放宽超时

灰度切换模型版本时要格外小心一件事：换版本会改变输出分布。同一套提示词在新版本下可能变得更啰嗦、更爱加解释性前缀、或者数值型输出的分布整体偏移。这会让两类下游悄悄失效——一是基于字符串形态的解析（多一个前缀就解析不到），二是基于经验值定下的阈值（原本 0.7 是合理分界，新版本下打分整体抬高，0.7 就形同虚设）。所以切换必须按流量比例灰度，并且在灰度期间同时观测契约校验失败率、输出长度分布和各档位的成本，而不只是看业务指标有没有掉。性能与成本的量化方法见 PY42 性能剖析与优化。

生产事故复盘：某产品的多轮助手功能上线三周后，月度调用成本达到预算的 7.4 倍。排查过程：调用量本身符合预期（日均约 12 万次，预估 10 万次），异常的是单次请求的平均输入长度——从灰度期的约 1.2k token 涨到了约 9.1k token。根因有两条且相互放大：一是每轮都把完整历史原样重发，而真实用户的会话轮次远超预期（灰度期平均 3 轮，放量后平均 18 轮，长尾会话超过 60 轮），于是单会话的累计 token 随轮次呈平方级增长；二是完全没有缓存，同一份固定的系统指令和知识片段在每一轮里被重复计费。
优化做了三件事：固定头 + 最近 6 轮原文 + 更早轮次压缩成摘要（摘要结果缓存复用）、对完全相同的输入直接返回缓存结果（实测命中率 0.31）、把可枚举的高频问题改成离线预计算。两周后单次平均输入降到约 2.1k token，月成本降到原来的 23%（降幅约 77%），用户侧的会话质量评分没有可观测的下降。
这次事故真正的教训不是「要加缓存」，而是上线前没有人算过「平均轮次翻六倍时成本会怎样」这道题——平方级增长的东西，靠灰度期的观测是看不出来的。

这类系统的成本曲线不跟着用户数走，跟着「每个用户平均带多长的上下文」走。前者你会盯着，后者没人盯，于是账单总是从后者上爆掉。

示例场景：某团队在切换模型档位后发现输出质量下降，但由于档位是硬编码在代码里的，回滚需要重新构建镜像并走完发布流程，从发现到恢复用了 47 分钟，期间约 2.3 万次请求拿到了劣化的结果。事后改造只做了一件事：把档位选择挪进配置中心，并加了一个「一键回到上一档」的开关。下一次同类问题的恢复时间是 90 秒。回滚速度是设计出来的，不是临场发挥出来的。

  • 每一次外部调用都写显式超时，并在超时后走降级而不是重试到死
  • 输出先解析成结构化对象，校验通过才允许进入业务逻辑或落库

  • 关联标识贯穿全链路，日志里带 token 用量与失败分类
  • 提示词、模型档位、功能开关做成可独立回滚的配置
  • 上线前把「用量翻五倍」代入成本公式算一遍
  • 把模型返回的字符串直接写进数据库或直接展示给用户
  • 用「把提示词写得更严格一点」代替输出侧的契约校验
  • 无上限重试：既放大成本，又把下游的抖动变成雪崩
  • 把会话状态放在进程内存里，然后部署多实例
  • 只监控业务指标，不监控 token 用量与输出长度分布
  • 灰度换模型版本时只看效果，不看下游解析与阈值是否还成立

Q&A

同步直调什么时候是可以接受的？是不是应该一律改成异步？
不是。同步直调的问题在于把下游的延迟和故障原样暴露给用户，但它的实现复杂度最低，在两类场景下仍然是正确选择：一是调用耗时稳定在一两秒以内、且用户确实需要立刻拿到结论的交互；二是服务端内部的短链路调用，比如一次结构化抽取，其调用方本身就是后台任务。判断标准是把三个数放在一起看——下游的耗时分位（尤其是 P99 而不是均值）、业务能容忍的等待上限、以及这条链路上是否还有别的下游在等它。只要 P99 超过业务容忍上限，或者这次调用会阻塞住一条更长的链路，就应该换成异步或流式。另外要注意，同步直调下的超时设置必须比上游的超时更短，否则上游先断开，你这边还在为一个没人要的结果付费。
流式响应看起来体验最好，为什么不全站都用流式？
流式优化的是首字延迟，不是总时长，也不省成本，而它带来的复杂度是实打实的。第一，长连接占用连接资源，且和常见的网关、负载均衡、缓冲层都可能打架，中间任何一层做了缓冲，流式就退化成了一次性返回。第二，输出契约校验变难了：结构化输出必须等完整才能解析校验，边流边显示意味着用户可能先看到一段最终会被判定为不合格的内容。第三，中断处理变复杂：用户中途关闭页面时，你需要主动取消下游调用，否则会继续产生费用。所以流式适合「人在屏幕前逐字阅读自然语言」的场景；如果输出是要被程序消费的结构化结果，流式几乎没有收益，反而把校验位置弄乱了。
既然提示词能把不合规输出压到很低，为什么还要写校验？
因为两者提供的保证类型不同。提示词是概率性手段，它能把不合规率从两成降到千分之几，但没有任何机制能让它降到零；校验是确定性手段，它保证「不合规的输出一定不会进入下游」。把千分之几乘上日均几十万次调用，每天仍然有几百次不合规输出，如果下游是数据库写入或对外展示，这几百次就是几百个事故。还有一个更现实的理由：提示词的效果会随模型版本变化而漂移，你今天调好的那套，在下次版本切换后可能不再成立，而校验代码不会漂移。正确的关系是分工——提示词负责降低发生率（减少重试和降级带来的成本与延迟），校验负责给出边界保证，两者都要有。
会话状态外置之后，同一个会话的并发请求会不会互相覆盖？
会，而且这是外置之后最容易被忽略的新问题。典型场景是用户快速连点两次，或者客户端重试时上一次请求其实还在处理，两个请求都读到了同一份历史，各自追加一轮后写回，后写的覆盖先写的。处理方式有三档：最简单的是在会话粒度上加一把带过期时间的分布式锁，同一会话同时只允许一个请求在处理，冲突时直接拒绝并提示用户稍候；中等做法是给状态加版本号，写回时比对版本，不一致就拒绝或重新读取合并；最彻底的是把历史设计成只追加的结构，每轮写一条独立记录而不是覆盖整份，读的时候按序号组装。选哪种取决于业务对「丢一轮」的容忍度，但无论选哪种，都不能假设同一会话的请求是严格串行的。
怎么在项目早期就估算出成本量级，而不是等账单来了才发现？
用一个能在纸上算完的模型，输入是四个数：日均调用量、单次平均 token、单位价格、缓存命中率。关键不在于精确，而在于把三个容易被漏掉的放大因子显式算进去。第一个是「每次业务触发几次调用」——一个功能看起来是一次调用，实际可能包含一次改写加一次校验加一次兜底重试，倍数是三。第二个是上下文增长：多轮场景里单次输入长度会随轮次增长，累计消耗是平方级的，必须按「平均轮次的悲观估计」而不是灰度期的观测值来算。第三个是失败重试带来的额外调用。算完之后做一次敏感性分析：把调用量和平均轮次各乘五倍，看月成本是否仍在可接受范围内，不在就说明当前设计撑不住放量，要在上线前而不是上线后解决。
灰度切换模型版本时，除了看业务指标还该盯什么？
至少三类技术指标，它们会比业务指标更早暴露问题。第一是契约校验失败率按类型拆分——结构解析失败、字段缺失、取值越界各自的比例，任何一项突然上升都说明输出形态变了。第二是输出长度分布，不是均值而是分位数，新版本变啰嗦会同时抬高成本和延迟，均值可能看不出来但 P95 会很明显。第三是各档位的实际成本与调用分布，尤其是「轻档失败后升档重试」的比例，这个比例上升意味着轻档在新版本下不再够用，总成本会悄悄翻倍。此外还要检查所有基于经验值定下的阈值是否仍然成立：如果下游用了打分阈值做分流或过滤，新版本的分数分布偏移会让阈值失效，而这类失效通常不报错，只是结果慢慢变差。
降级路径具体怎么设计？返回一句「服务繁忙」算不算降级？
算，但那是最后一档，不应该是唯一一档。降级应该是有层次的，按「对用户的价值」从高到低排：第一档返回缓存里的历史结果，附上生成时间，多数场景下旧结果远好于没有结果；第二档退到不依赖模型的规则或模板结果，比如用关键词匹配给出一个粗粒度的答案；第三档降级到只提供部分功能，比如生成失败但仍然把检索到的原始材料展示出来；最后一档才是明确告知不可用，并且必须保留一个明确的重试入口，而不是让用户对着一个通用错误页面猜。设计时还有两个要点：降级要在响应里带上可识别的标记，这样前端能做差异化展示、监控也能统计降级率；以及降级路径必须有自动化测试覆盖，最常见的故障是降级代码自己在真正被调用的那天抛了异常。
