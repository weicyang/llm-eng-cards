PY33 · 同步与异步的互通

四种互通方向 / to_thread 与默认线程池 / CPU 密集只能进程池 / 跨线程提交协程 / 异步边界划在哪

没有哪个真实项目是纯异步的。生态里一半的库还是同步写法，所以你写的每个异步服务本质上都是一座桥：桥搭对了，阻塞被挪到别的线程，事件循环继续转；桥搭错了，整个循环停在那一行上，而且平时一点都不报错。

一、问题的形状：真实项目永远是混合的

「学会 async/await」和「能在生产里用好 asyncio」之间隔着的不是语法，而是这件事：你几乎不可能让整条调用链都是异步的。异步的 Web 框架里要调一个只有同步版本的数据库驱动；一个同步的批处理脚本里要复用团队已经写好的异步客户端；一个要被两种调用方同时使用的内部库，得同时给出两套入口。这些都不是设计失误，而是生态的现状。

把这类问题笼统叫做「异步兼容」没有用，因为互通其实有四个方向，每个方向的正确解法完全不同，混用错了就是事故。先把方向认出来，后面五节才有落点。

四个方向，四套解法 ──────────────────────────────────────────────────────────── ① 异步 ─► 同步阻塞 I/O ② 异步 ─► 同步纯计算 async def handler(): async def handler(): rows = db.query(...) score = heavy_math(x) ↑ 阻塞在 socket 上 ↑ 阻塞在 CPU 上 解法：挪到线程池 解法：挪到进程池 asyncio.to_thread(...) run_in_executor(ProcessPool, ...) 线程等 I/O 时不占解释器锁 纯 Python 计算不放解释器锁， 换线程没用 ③ 同步 ─► 异步 ④ 一个库要同时服务两种调用方 def main(): lib.fetch() ← 同步入口 data = fetch_async() await lib.afetch() ← 异步入口 ↑ 拿到的是协程对象 解法：分两种情况 解法：以异步为唯一实现， 当前线程没有运行中的循环 同步入口只是薄薄一层包装； → asyncio.run(...) 千万别把 asyncio.run 埋进 循环在别的线程上 被复用的库函数里 → run_coroutine_threadsafe 认错方向的后果： ①用了进程池 → 多付一次序列化，白花钱 ②用了线程池 → 事件循环照样被拖慢，压测才发现 ③在已有循环里调 asyncio.run → 直接 RuntimeError ④把 asyncio.run 写进库 → 调用方永远无法复用自己的循环

怎么认出一个调用是不是阻塞的

这一步比想象中重要，因为方向①的典型症状就是「代码看起来完全正常，测试全绿，上线后慢得莫名其妙」。没有任何语法特征能告诉你 db.query() 会把线程挂住 30 毫秒——你得从别的地方判断。

线索判断说明
函数前面能不能加 await不能 → 极可能是同步的最快的一眼判据，但对返回 Future 的老式 API 会误判
库的文档里有没有 async def 示例没有 → 同步库requests / psycopg2 / redis-py 的同步类都属此列
内部有没有 socket / open() / subprocess有 → 阻塞 I/O包括看不见的那些：DNS 解析、TLS 握手、文件 fsync
开 asyncio 调试模式跑一遍有告警 → 循环被卡住过asyncio.run(main(), debug=True)，单次回调超过 slow_callback_duration（默认 0.1 秒）就打印告警
压测时延迟是否随并发同步抬升是 → 循环里有阻塞纯异步链路的延迟在饱和前应当基本平坦

最后一条调试模式的办法值得固定进开发流程。它不需要你预先知道哪一行有问题，直接把「循环被某个回调独占超过 100 毫秒」这件事报出来，是排查方向①最省力的入口。注意它只在调试模式下生效，不要开到生产上。

异步不是「更快」，是「等待的时候让出去」。任何一行没有让出去的等待，代价都不是它自己慢，而是它把同一个循环上所有别人的等待一起延后了。

二、异步里调同步阻塞代码：to_thread 与它的隐形队列

方向①是四个方向里最高频的，也是解法最成熟的。从 Python 3.9 起，标准答案是 asyncio.to_thread()：

import asyncio

# 同步阻塞的老驱动，改不动，也不打算改
def query_user(uid: int) -> dict:
    return legacy_db.execute("select * from users where id=%s", uid)

async def handler(uid: int) -> dict:
    return await asyncio.to_thread(query_user, uid)

它做的事非常薄：拿到当前运行中的循环，复制一份 contextvars 上下文，然后把函数交给 loop.run_in_executor(None, ...)——也就是循环的默认线程池。所以下面这两行在效果上几乎等价，只差一个上下文传递和参数写法：

# 3.9 起的写法：支持关键字参数，自动传递 contextvars
await asyncio.to_thread(query_user, uid=42)

# 底层等价物：run_in_executor 的签名是 (executor, func, *args)
# 没有 **kwargs，要传关键字参数得自己包一层 partial
loop = asyncio.get_running_loop()
await loop.run_in_executor(None, functools.partial(query_user, uid=42))

run_in_executor 不接受关键字参数这一点每个人都会踩一次。to_thread 存在的主要价值就是替你把 functools.partial 和上下文复制这两件杂事做掉，此外没有任何魔法。

它究竟解决了什么，又没解决什么

关键在于「阻塞」发生的位置变了，但阻塞本身一秒也没减少。原来是事件循环所在的那个线程停在 socket 上，现在是线程池里的某个工作线程停在 socket 上——差别在于前者会连累所有在途请求，后者只连累自己。循环得以继续转，这就是全部收益。

await asyncio.to_thread(query_user, 42) 发生了什么 ───────────────────────────────────────────────────────── 事件循环线程 默认线程池（容量有上限） ┌────────────────────┐ ┌──────────────────────────┐ │ handler 协程 │ │ worker-1 忙：等 DB 25ms │ │ ↓ to_thread │ 提交任务 │ worker-2 忙：等 DB 25ms │ │ ├───────────────────────────►│ worker-3 忙 │ │ │ │ │ ... │ │ │ 挂起，循环继续 │ │ worker-N 忙 │ │ │ 跑别的协程 ✔ │ │──────────────────────────│ │ │ │ │ 等待队列 ← 排在这里的时间 │ │ ▼ 结果回来，恢复 │◄──────────│ 不计入 query_user 的耗时 │ └────────────────────┘ 唤醒 └──────────────────────────┘ ▲ └── 事故就藏在这一格： 你在应用里给 query_user 打的耗时日志永远是 25ms， 而调用方实测是 1.6 秒

上图右下角那一格是本节的核心。线程池的容量是有限的，当同时发起的阻塞调用数量超过工作线程数时，多余的任务进入 Executor 的等待队列。队列里的等待时间不体现在任何一次函数调用的耗时上——你在 query_user 里打的埋点从进入函数体才开始计时，排队那段完全是空白。这使得它成为一类极难从应用日志里看出来的故障。

生产事故复盘：某异步服务（4 核容器）把全部同步数据库调用一律用 to_thread 包起来就上线了，功能测试全绿。压测时出现典型的非线性恶化：并发 50 时 P95 是 120 毫秒，并发 200 时涨到 780 毫秒，并发 400 时 1.6 秒，而吞吐无论怎么加压都封顶在每秒 310 次左右。诡异之处在于，应用侧给数据库调用打的耗时埋点始终稳定在 26～30 毫秒，数据库自己的慢查询日志一条都没有。根因是默认线程池容量远小于并发请求数：4 核机器上默认只有 8 个工作线程，单次查询 25 毫秒，理论吞吐上限正好是 8 ÷ 0.025 ≈ 320 次每秒，400 个在途请求要排大约 50 轮才轮得到最后一个。修复分两步：先给数据库调用换成 32 线程的专用线程池并加上信号量限流，P95 降到 240 毫秒；随后把驱动换成原生异步版本，P95 落到 48 毫秒，线程池整个撤掉。

默认线程池到底有多大

循环的默认执行器是在第一次用到时惰性创建的一个 ThreadPoolExecutor()，不传 max_workers，因此它的容量就是 concurrent.futures 的默认值。这个默认值随版本改过两次，写代码时不要凭记忆假设：

版本默认 max_workers4 核机器上的实际值
3.5 – 3.7os.cpu_count() * 520
3.8 – 3.12min(32, os.cpu_count() + 4)8
3.13 起min(32, (os.process_cpu_count() or 1) + 4)8（但会遵守容器的 CPU 亲和性限制）

注意 3.8 那一次改动是大幅调小：8 核机器上从 40 个线程降到 12 个。如果你读到的经验帖写于 2019 年之前，它对默认容量的估计会偏大好几倍。3.13 的改动方向不同，是让容量识别 cgroup 之类的限制——在只分到 2 核的容器里，os.cpu_count() 可能报告宿主机的 64 核，而 os.process_cpu_count() 报告 2，两者差出一个数量级。

关于容量，真正该记住的不是公式而是量级：它是个位数到几十的数量级，和你的并发请求数完全不在一个尺度上。公式随时可能再变，这个结论不会变。

三条路怎么选

做法适合代价要补的配套
默认线程池（to_thread）低频调用：启动期加载配置、偶发的一次外部调用容量个位数且全进程共享，任何一类调用都能把它占满无，但要确认调用频率真的低
自建专用线程池高频但确实换不掉的同步驱动要自己管生命周期与关闭；线程本身有栈内存开销按依赖分池隔离、容量与连接池对齐、加信号量上限与排队指标
换原生异步驱动有成熟异步实现的依赖（数据库、HTTP、对象存储）一次性的迁移与回归测试成本连接池参数要重调；长期看这是唯一真正的解

自建池那一行的「按依赖分池隔离」值得展开一句。共用一个线程池的后果是故障会串门：调用某个外部 HTTP 接口时对方超时到 10 秒，这些线程会把池占满，于是数据库查询也跟着排队，监控上看起来像数据库出了问题。给每类依赖一个独立的池，故障就被关在自己的格子里。线程池的创建与关闭建议交给上下文管理器或应用的生命周期钩子来管（见 PY19），不要让它随进程泄漏。

DB_POOL = ThreadPoolExecutor(max_workers=32, thread_name_prefix="db")
SEM = asyncio.Semaphore(32)          # 上限和池容量对齐，让排队发生在这里

async def query(uid: int) -> dict:
    async with SEM:                  # 超限时在这里等，可观测、可超时
        loop = asyncio.get_running_loop()
        return await loop.run_in_executor(DB_POOL, query_user, uid)

加信号量的目的不是限制并发——线程池自己就限制了——而是把排队从不可见的地方搬到可见的地方。信号量的等待发生在你的代码里，可以埋点、可以设超时、可以在超限时快速失败并返回明确的错误类型（异常分层见 PY24）；而 Executor 内部队列的等待你什么都拿不到。前面那起事故如果一开始就有这个信号量，压测第一轮就能定位。

to_thread 不会让阻塞消失，只是给它换了个地方等。真正的问题从来不是「这次调用多久」，而是「同时有多少次调用在等，它们在哪排队，你看不看得见那个队列」。

三、异步里调 CPU 密集计算：线程池救不了它

方向②看起来和方向①很像——同样是一个同步函数卡住了循环，同样想把它挪走——但把它扔进 to_thread 基本没有用。原因在于两种「卡住」的性质完全不同。

阻塞 I/O 的线程在等操作系统，它在 read 上睡着，此时会释放解释器全局锁，别的线程可以照常执行 Python 字节码。而纯 Python 的计算需要持续持有这把锁才能往下执行字节码，把它挪到另一个线程，两个线程只会轮流抢同一把锁，总的计算吞吐一点没涨，还多付了线程切换的开销。

同样是「挪到线程池」，两种负载的结果完全不同 ───────────────────────────────────────────────────────── 阻塞 I/O（可以挪） 纯 Python 计算（挪了没用） ┌─────────────────────┐ ┌─────────────────────┐ │ 循环线程 ████████ │ 一直在跑 │ 循环线程 ██··██··█ │ 被切碎 │ worker-1 ~~~~~~~~ │ 等 socket│ worker-1 ··██··██· │ 抢锁 │ worker-2 ~~~~~~~~ │ 等 socket│ worker-2 ··········│ 排队等锁 └─────────────────────┘ └─────────────────────┘ ~~~ 段不持有解释器锁 ██ 段必须持有解释器锁 循环照常处理别的请求 ✔ 循环被抢走时间片 ✘ 正解：换成进程池，每个进程有各自独立的解释器与锁 ┌────────────────────────────────────────────────────┐ │ 主进程：事件循环 ──提交──► 进程 1（独立锁）│ │ 参数 pickle ─► 管道 ─► 子进程反序列化 ─► 真正计算 │ │ 结果 pickle ◄─ 管道 ◄─ 子进程序列化 ◄───────────│ └────────────────────────────────────────────────────┘ 多出来的成本：两次序列化 + 两次进程间拷贝 + 进程启动

写法上和线程池只差一个执行器对象：

from concurrent.futures import ProcessPoolExecutor

CPU_POOL = ProcessPoolExecutor(max_workers=4)   # 应用启动时建一次

async def score(payload: dict) -> float:
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(CPU_POOL, heavy_math, payload)

注意 asyncio.to_thread() 没有对应的「to_process」版本，方向②必须走 run_in_executor。还要注意进程池要在应用启动时创建一次并复用，不要在每个请求里现建——建池要 fork 或 spawn 出若干个进程，成本比一次计算高得多。

代价：所有东西都得能 pickle

参数和返回值要跨进程传输，就必须被序列化。ProcessPoolExecutor 默认用 pickle，于是一批东西直接出局：lambda 与局部函数、打开着的文件句柄与数据库连接、线程锁、闭包捕获的不可序列化对象。传入的参数在子进程里是一份独立的副本，你在子进程里改它，主进程完全看不到——这一点和深浅拷贝的直觉是一致的（见 PY10）。

子进程里抛出的异常会被序列化后在主进程重新抛出，但栈信息会被压扁，自定义异常如果构造函数签名特殊还可能在反序列化时二次失败。跨进程的错误传播要提前测一遍，不要等线上才发现异常本身也传不回来。

判据：多大的计算才值得付这笔钱

进程间通信的固定成本对小对象大约在亚毫秒到几毫秒的量级（两次序列化加两次管道往返），随载荷大小线性增长。把这个成本和单次计算的耗时放在一起比，判据就出来了：

单次计算耗时建议理由
小于 1 毫秒就在循环里直接算挪出去的成本远大于计算本身，纯亏
1 – 10 毫秒留在循环里，但要批量合并进程池的固定成本占比过高；真的卡就先优化算法
10 – 50 毫秒看频率：高频才进进程池灰色地带，用实测决定，不要凭感觉
大于 50 毫秒明确走进程池通信成本被摊薄到百分之几，收益清晰
任意耗时但载荷是 MB 级改传引用而非传值序列化本身成为瓶颈，应传文件路径、对象存储键或共享内存名

还有一类计算不需要进程池：如果热点其实落在 NumPy、加解密库、压缩库这类 C 扩展里，它们在计算期间通常会主动释放解释器锁，那么线程池对它们是有效的。判断方法只有实测——把负载放进线程池，看多线程下总吞吐涨不涨。涨了说明锁被释放了，没涨说明是纯 Python 计算，老老实实上进程池。

示例场景：一个文档处理服务在请求路径上做纯 Python 的文本分词与打分，单次约 180 毫秒。最初用 to_thread 包起来，压测时发现连不带计算的健康检查接口 P95 都从 3 毫秒涨到了 260 毫秒——循环被抢走了时间片，整个服务一起变慢。改成 4 进程的 ProcessPoolExecutor 后，健康检查回到 4 毫秒，处理接口的 P95 从 1.4 秒降到 320 毫秒。单次多付的序列化成本实测约 2 毫秒，相对 180 毫秒的计算可以忽略。

线程池搬运的是「等待」，进程池搬运的是「计算」。搬错了不会报错，只会在压测时让你看见一条不该变慢的曲线跟着变慢。

四、同步里调异步代码：先回答「有没有运行中的循环」

方向③的入口函数是 asyncio.run()，它做三件事：新建一个事件循环、把传入的协程跑到完成、然后关闭这个循环并清理异步生成器。关键限制在第一步——它只能在当前线程没有运行中的循环时调用。在一个已经跑着循环的线程里调它，得到的是：

RuntimeError: asyncio.run() cannot be called from a running event loop

所以方向③不存在一个万能写法，你必须先回答一个问题：当前这个线程上，有没有正在运行的事件循环？标准答案用 asyncio.get_running_loop() 探测，它在没有循环时抛 RuntimeError：

import asyncio

def running_loop_or_none():
    """当前线程有运行中的循环就返回它，否则返回 None。"""
    try:
        return asyncio.get_running_loop()
    except RuntimeError:      # "no running event loop"
        return None

不要用 asyncio.get_event_loop() 来做这个探测。它的语义跨版本一直在变，在没有循环的非主线程里直接抛 RuntimeError: There is no current event loop in thread ...（3.12 实测），在主线程上则经历了「自动创建 → 弃用告警 → 报错」的演进过程。get_running_loop() 的语义从 3.7 引入起就是明确且稳定的：只返回正在运行的循环，没有就抛错。

你在哪本线程有运行中的循环吗正确做法
脚本 main、CLI 入口、定时任务没有asyncio.run(main())，一个进程只在最外层调一次
协程直接调用的同步函数（同一线程）有不能调 asyncio.run。把这个函数改成 async def，让 await 链路连起来
线程池 worker 里想用异步客户端本线程没有，主线程有asyncio.run_coroutine_threadsafe(coro, loop).result(timeout=...)
自己起的独立后台线程没有该线程内自己 asyncio.run()；注意它与主循环互不相通，连接池不共享
Jupyter、pytest-asyncio、框架的生命周期钩子有（框架已经起好了）直接 await。在 Jupyter 里就是顶层 await，不要包 asyncio.run

跨线程把协程交给已有的循环

表里第三行是方向③里最需要讲清的一种。场景是：主线程跑着事件循环，某个同步函数被扔进了线程池，而它内部需要调用一个只有异步版本的客户端。这时既不能 await（当前不是协程），也不能 asyncio.run（会起第二个循环，连接池和上下文全都不共享）。正确的桥是 asyncio.run_coroutine_threadsafe(coro, loop)。

跨线程提交协程的完整路径 ───────────────────────────────────────────────────────── 事件循环线程 线程池 worker 线程 ┌────────────────────────┐ ┌────────────────────────┐ │ loop 正在运行 │ │ 同步函数 sync_work() │ │ │ │ 需要 await 一个客户端│ │ ◄───── 线程安全地提交 ───────────│ run_coroutine_threadsafe│ │ 把协程排进本循环 │ │ (coro, loop) │ │ ↓ 正常调度执行 │ │ ↓ 拿到的是 │ │ ↓ 完成后填充结果 │ │ concurrent.futures │ │ ─────── 结果回传 ───────────────►│ .Future │ │ │ │ fut.result(timeout=5)│ └────────────────────────┘ │ ↑ 阻塞等待 │ └────────────────────────┘ 两个必须记住的点 ① 返回的是 concurrent.futures.Future，不是 asyncio.Future ⇒ 不能 await，要用阻塞的 .result(timeout=...) 取值 ② 绝对不要在事件循环所在的那个线程里调 .result() ⇒ 循环被阻塞在这一行，提交进去的协程永远没机会执行 = 死锁
# 主线程：起循环前把 loop 传给需要它的同步代码
loop = asyncio.get_running_loop()

def sync_work(url: str) -> bytes:        # 跑在线程池 worker 里
    fut = asyncio.run_coroutine_threadsafe(client.fetch(url), loop)
    return fut.result(timeout=10)        # 必须给 timeout，否则可能永久挂起

await asyncio.to_thread(sync_work, "https://example.com")

返回类型这一点值得单独强调，因为它是这个 API 最容易记错的地方：run_coroutine_threadsafe 返回的是 concurrent.futures.Future，不是 asyncio.Future。两者名字像、用途像，但前者的 result() 是阻塞的普通方法，后者要 await。这个设计是合理的：调用方本来就在一个同步的、没有循环的线程里，给它一个只能 await 的对象毫无意义。

同族还有一个更轻量的 loop.call_soon_threadsafe(callback, *args)，用于从别的线程往循环里塞一个普通回调（不是协程），它不返回任何可等待的东西，适合「通知一下、不要结果」的场景，比如从线程里 set() 一个 asyncio.Event。

踩坑提醒：上面代码里的 timeout=10 不是可选项。concurrent.futures.Future.result() 不传超时就是无限期阻塞，一旦事件循环因为别的原因卡住或已经关闭，这个 worker 线程会永久挂在那里。线程池里的线程从 Python 3.9 起不再是守护线程，若干个线程这样挂住之后，进程连正常退出都做不到——表现为「服务收到停止信号后一直不退出，最后被强杀」。

「同步里怎么调异步」这个问题没有统一答案，因为它其实是两个问题。先问清楚「当前线程上有没有循环在跑」，答案分岔之后，每一支的写法都只有一种。

五、陷阱清单：五种平时不报错的写法

这一节的五条有一个共同特征：它们在开发和单元测试里几乎都不报错。低并发下阻塞一下没人看得出来，测试里跑一次也正常返回。它们要等到压测或者线上流量才显形，而那时的症状又指向别的地方。

其一：在协程里直接调同步 I/O

最常见的一条，也是第二节整节在讲的那个问题。症状很有辨识度：不相干的接口也一起变慢。因为被卡住的是共享的事件循环，健康检查、静态资源、别的业务接口全在同一个循环上排队。如果你看到「只是某个下游变慢了，但整个服务的 P95 都抬起来了」，先怀疑这条。

其二：在协程里用 time.sleep

本质上是其一的特例，但因为太常见值得单列。time.sleep(1) 把整个线程挂起一秒，循环上所有协程一起停一秒；await asyncio.sleep(1) 只挂起当前这一个协程。重试退避、轮询间隔、限流等待这几处是重灾区，写法要检查到位。

其三：把 asyncio.run 写进库函数

库函数内部调 asyncio.run，意味着这个函数永远不能被异步调用方使用——对方已经有循环在跑，调进来直接 RuntimeError。即使调用方恰好是同步的，每次调用也会新建再销毁一个循环，连接池、contextvars、取消信号全都无法跨调用复用。正确做法是异步实现为本体，同步入口用一个名字上就能看出来的薄包装单独提供。

  • 异步实现是唯一本体：async def fetch(...)
  • 同步入口显式命名：def fetch_sync(...)，内部才调 asyncio.run
  • 同步入口在文档里写明「不可在已有循环中调用」
  • 在协程里等待用 await asyncio.sleep(...)
  • 跨线程提交协程一律带 timeout
  • 线程池按依赖分池，容量与下游连接池对齐
  • 在库函数体内直接调 asyncio.run，让调用方失去循环控制权
  • 协程里 time.sleep / requests.get / 裸 open() 读大文件
  • 用 asyncio.get_event_loop() 跨线程去「拿」循环
  • 把 asyncio.Queue / Event 直接交给线程池里的函数操作
  • 对协程对象做 if 判断或直接当结果用
  • fut.result() 不带超时，或在循环线程里调它

其四：对协程对象做条件判断

调用一个 async def 函数不会执行任何函数体，只是返回一个协程对象。而协程对象没有定义 __bool__，按 Python 的默认规则它永远为真。于是这样的代码会静默走错分支：

async def get_user(uid):  ...

# ✘ 函数体一行没跑，coro 恒为真，永远进 if 分支
if get_user(42):
    print("找到了")

# ✔ 同步上下文里要么 asyncio.run，要么在协程里 await
if await get_user(42):
    print("找到了")

Python 会为此发一条 RuntimeWarning: coroutine 'get_user' was never awaited，但默认配置下 RuntimeWarning 只打印到 stderr 且不中断程序，在有日志框架的服务里很容易被淹没。把测试环境的 -W error::RuntimeWarning 打开，这类漏掉的 await 会在 CI 里直接变成失败。

其五：线程池里的函数碰了事件循环相关对象

asyncio 的绝大多数对象不是线程安全的。在 worker 线程里往 asyncio.Queue 里 put_nowait、set() 一个 asyncio.Event、或者取消一个 Task，都可能造成循环内部状态错乱，而且错乱的表现是随机的——偶发卡死、偶发丢消息、偶发的 Future attached to a different loop。跨线程只有两个官方入口：loop.call_soon_threadsafe() 和 asyncio.run_coroutine_threadsafe()，其余一律不要碰。如果只是想从线程往协程侧传数据，用 queue.Queue（线程安全的那个）加上 call_soon_threadsafe 通知，比直接操作 asyncio.Queue 稳妥得多。

症状可能的陷阱确认办法
下游变慢时，连健康检查都变慢其一：循环里有同步 I/O开 debug=True 看慢回调告警
延迟正好是某个整秒的倍数其二：协程里 time.sleep全局搜 time.sleep，看是否在 async def 内
asyncio.run() cannot be called from a running event loop其三：库函数内部起了循环看报错栈里哪个第三方库调了 asyncio.run
分支永远走同一边，且日志里有 never awaited其四：对协程对象做判断-W error::RuntimeWarning 跑一遍测试
偶发卡死 / attached to a different loop其五：跨线程碰了 asyncio 对象审查所有传进 run_in_executor 的闭包捕获了什么

这五条没有一条会在你写的时候报错。它们的成本不在修复，在发现——所以值得把调试模式、-W error::RuntimeWarning 和一轮真实并发的压测固定进流程，让它们在 CI 里显形，而不是在凌晨的告警里。

六、架构判据：桥要搭，但边界要划在外面

前面五节都在讲「怎么搭桥」。这一节讲一件更重要的事：桥的数量和位置，决定了这个服务能不能维护。每一座桥都是一处线程边界、一处需要单独配容量和加指标的地方、一处可能出错的取消与超时传播路径。桥多到一定程度，异步带来的收益会被桥本身的复杂度吃光。

一条决策路径 ───────────────────────────────────────────────────────── 这个依赖有成熟的原生异步实现吗？ │ ├── 有 ──────► 换掉它。别搭桥。 │ 迁移是一次性成本，桥是永久成本。 │ └── 没有 ───► 要桥接的调用占整条链路的比例有多高？ │ ├── 低（少数几处）──► 搭桥，并且补齐三件套： │ 专用线程池 + 并发上限 + 排队指标 │ ├── 中 ─────────────► 搭桥，但把这些依赖 │ 收拢到一个模块里统一管 │ └── 高（大半都要桥）► 停下来重新想： 这个服务本就不该做成异步的。 同步框架 + 多进程 + 线程池 又简单又好调，别硬上 asyncio。 最后一行不是玩笑。全是桥的「异步服务」拿不到异步的任何好处， 却背上了异步的全部调试难度。

最下面那一支值得说透。异步的收益来自「等待时把线程让出去」，如果你的每一次等待最终都发生在某个线程池的工作线程上，那你实际的并发上限就是线程池容量——和直接用一个同步框架配同样大小的线程池完全一样，甚至更差，因为多了一层调度。这种情况下 asyncio 只贡献了调试难度。能不能受益于异步，取决于你有多少等待真的是非阻塞的，而不是你写了多少个 async def。

异步边界应该划在哪

假设桥是必须搭的，下一个问题是搭在哪一层。答案是：异步边界越靠外越好，整条调用链上只穿越一次。最糟的形态是在调用链中段来回切换——异步的处理器调同步的服务层，服务层里又通过 run_coroutine_threadsafe 调回异步的客户端。

边界位置形态评价
最外层（推荐）入口是异步的，整个内部实现同步，只在入口处一次 to_thread桥只有一座，容量集中可控，栈干净好调
最内层整条链路异步，只在真正碰到同步驱动的那一个函数上桥接次优。桥多但都很薄，前提是必须集中在一个适配层里
中段来回切异步 → 同步 → 异步 → 同步要避免。栈深且乱、取消信号传不下去、超时无法端到端计算
无边界（全异步）所有依赖都有原生异步实现理想态。值得为之做驱动迁移

「中段来回切」那一行的真正危害不在性能，在取消与超时。asyncio 的取消是通过向协程抛 CancelledError 实现的，而它穿不过线程边界：客户端断开连接、上游超时触发取消，事件循环侧的协程确实被取消了，但已经进了线程池的那个函数会一直跑到自己结束为止，没有任何办法打断它。链路上每多一次切换，就多一段无法取消的区间，端到端的超时预算也就无从计算。

还有一个常被忽略的后果是可观测性断裂。基于 contextvars 的请求追踪 ID 在 to_thread 时会被自动复制过去（这是 to_thread 相对裸 run_in_executor 的一个实质优势），但在 run_coroutine_threadsafe 反向提交时不会自动传播，得自己带。来回切几次之后，链路追踪就断成了几截。

判断一个异步服务健不健康，数一下它有几处线程切换就够了。零处是理想，一处是正常，每类依赖一处还能接受；如果一个请求要穿越五六次线程边界，问题已经不是某座桥搭得对不对，而是这个服务当初就不该选异步。

Q&A

asyncio.to_thread 和 loop.run_in_executor 到底该用哪个？
默认用 to_thread（Python 3.9 起可用）。它是 run_in_executor(None, ...) 的封装，额外替你做了两件事：支持关键字参数（run_in_executor 的签名是 (executor, func, *args)，没有 **kwargs，要传关键字得自己包 functools.partial），以及自动把当前的 contextvars 上下文复制到工作线程——这对基于上下文变量的请求追踪很关键。唯一必须用 run_in_executor 的场合是你要指定执行器：自建的专用线程池，或者 CPU 密集任务要用的 ProcessPoolExecutor。to_thread 不接受执行器参数，永远走默认线程池。实践上的分界很清楚：低频的一次性调用用 to_thread，高频的依赖调用用自建池加 run_in_executor。
默认线程池到底有多大？会不会自动扩容？
不会自动扩容，容量在池创建时就定死了。事件循环的默认执行器是第一次用到时惰性创建的一个不带参数的 ThreadPoolExecutor()，所以容量就是标准库的默认值，而这个默认值改过两次：3.5–3.7 是 os.cpu_count() * 5；3.8–3.12 改成 min(32, os.cpu_count() + 4)，这是一次大幅调小；3.13 起改成 min(32, (os.process_cpu_count() or 1) + 4)，区别在于 process_cpu_count() 会遵守容器的 CPU 亲和性限制，在只分到 2 核的容器里不会误报宿主机的核数。真正该记住的不是公式而是量级：它是个位数到几十，和动辄几百的并发请求数根本不在一个尺度上。超出容量的任务在 Executor 内部队列里排队，这段等待不体现在被调用函数的耗时埋点上。
为什么 CPU 密集任务放线程池没用，放进程池就有用？
因为两者「卡住」的性质不同。阻塞 I/O 的线程是在等操作系统，等待期间会释放解释器全局锁，别的线程可以继续执行 Python 字节码，所以挪到线程里是真的把等待挪走了。纯 Python 计算则必须持续持有这把锁才能往下走，两个线程只会轮流抢同一把锁，总吞吐一点不涨还多付切换开销。进程池则让每个子进程拥有各自独立的解释器和锁，真正并行。代价是参数和返回值要 pickle、要跨管道拷贝，固定成本对小对象在亚毫秒到几毫秒量级。一个重要的例外：NumPy、加解密、压缩这类 C 扩展在计算期间通常会主动释放锁，对它们线程池是有效的。判断方法只有实测——放进线程池看多线程下总吞吐涨不涨。
run_coroutine_threadsafe 返回的 Future 为什么不能 await？
因为它返回的是 concurrent.futures.Future，不是 asyncio.Future。两者名字相近、职责相似，但不是同一套东西：前者面向线程，取值方法 result(timeout=...) 是阻塞的普通方法；后者面向协程，必须 await。这个设计是合理的——调用 run_coroutine_threadsafe 的代码本来就跑在一个同步的、没有事件循环的线程里，给它一个只能 await 的对象毫无意义。两条铁律：第一，result() 一定要带 timeout，否则循环一旦卡住或关闭，这个线程会永久挂起，进程连正常退出都做不到；第二，绝对不要在事件循环所在的那个线程里调 result()，那会把循环阻塞在这一行，刚提交进去的协程永远没机会被调度，直接死锁。
我的库既要给同步代码用，又要给异步代码用，该怎么设计？
以异步为唯一实现本体，同步入口做成一层显式命名的薄包装。具体说：核心逻辑全部写成 async def fetch(...)，然后额外提供 def fetch_sync(...)，内部才调 asyncio.run(fetch(...))，并在文档里写明它不可在已有循环中调用。关键是绝不要把 asyncio.run 藏进普通函数里——那样异步调用方一调进来就是 RuntimeError: asyncio.run() cannot be called from a running event loop，等于把整类用户挡在门外；即使调用方恰好是同步的，每次调用新建再销毁循环也让连接池、上下文变量、取消信号全都无法复用。反过来的做法（同步为本体、异步入口用 to_thread 包）在低频场景下也可以，但并发上限会被线程池容量卡死，不适合做高频客户端库。
怎么快速排查「哪一行阻塞了事件循环」？
最省力的入口是 asyncio 的调试模式：asyncio.run(main(), debug=True)，或者设环境变量 PYTHONASYNCIODEBUG=1。开启后，任何单次执行超过 loop.slow_callback_duration（默认 0.1 秒）的回调都会打印告警，并带上是哪个 Handle。它的好处是不需要你预先猜测哪里有问题。注意调试模式本身有性能开销，只在开发和压测环境开，不要带到生产。第二个办法是看症状特征：如果某个下游变慢时连健康检查接口的 P95 都跟着抬起来，那基本可以确定循环被独占过——真正的异步链路上，一个依赖变慢不应该影响不相干的接口。第三，把 -W error::RuntimeWarning 加进 CI 的测试命令，漏掉的 await 会直接变成测试失败。
在 Jupyter 里跑 asyncio.run 报错，怎么办？
Jupyter 的内核本身就跑在一个事件循环上，所以当前线程已经有运行中的循环，调 asyncio.run 必然得到 RuntimeError: asyncio.run() cannot be called from a running event loop。正确做法是直接用顶层 await：在 cell 里写 result = await fetch(url) 就行，IPython 支持这种写法。不要去装那些「给循环打补丁允许嵌套」的第三方库来绕过这个限制——嵌套循环会让重入语义变得难以预测，调试成本远高于改一行写法。这个场景也是判断规则的好例子：遇到「同步里调异步」，第一步永远是问「当前线程有没有运行中的循环」，Jupyter、pytest-asyncio 的用例、Web 框架的生命周期钩子都属于「有」，一律直接 await。
请求被取消时，已经提交到线程池的那个函数会停下来吗？
不会。asyncio 的取消机制是向协程抛 CancelledError，而它穿不过线程边界。客户端断连或上游超时触发取消后，事件循环侧的协程确实被取消了、await 立即返回，但已经在工作线程里跑着的那个同步函数会一直执行到自己结束，占着线程和下游连接。这带来两个实际后果：一是取消不能释放资源，被取消的请求仍在消耗线程池容量，高取消率场景下会加剧排队；二是端到端超时预算无法保证，因为链路上存在不可打断的区间。缓解手段只有间接的：给下游调用本身设置库级别的超时（比如数据库驱动的 statement_timeout）、把线程池容量与信号量上限对齐避免堆积、以及最根本的——减少线程边界的穿越次数。这也是「异步边界越靠外越好」的一个重要理由。
