PY15 · 类与特殊方法契约

写类的难点从来不是 class 这个关键字，而是你写下的每个双下划线方法都不是「给自己用的函数」，而是在向解释器承诺一份契约。契约签对了，你的对象能进 set、能被打印、能参与运算；签错了，报错往往出现在离案发地很远的地方。

一、类、实例与属性查找顺序：读写是不对称的

先把一件事说清楚：class 语句不是声明，而是一段会立即执行的代码，执行结果是创建一个对象。类体里的赋值、函数定义、甚至 print，都在 class 语句被执行到的那一刻跑完，产物被收进一个命名空间，然后交给类型构造器做成类对象绑定到那个名字上。这就是为什么类可以被赋给变量、放进列表、当参数传递——它和整数、函数一样只是个对象。

类对象和实例对象各自都有自己的命名空间。实例属性存放在实例的 __dict__ 里，类属性存放在类对象上。两者名字可以重复，重复时谁生效，取决于属性查找链——即解释器读取属性时依次搜索的容器序列，顺序是「实例自身 → 它的类 → 类的基类链」。

不对称在哪里

读取会走完整条链，写入却只作用在链的第一环。obj.x = 1 从不修改类属性，它总是在实例的 __dict__ 里创建或覆盖一个同名条目。于是同一个名字出现了两种截然不同的行为：读到的可能是类属性，一旦写过就永远变成实例属性，而且此后类属性的变化对这个实例再无影响。

读 obj.x 写 obj.x = 1 ──────────────────────────── ──────────────────────────── ① 类及其基类链上的数据描述符 直接写入 │ 未命中 obj.__dict__["x"] ▼ （类属性完全不受影响， ② obj.__dict__["x"] ── 命中 → 返回 也不检查类上有没有同名） │ 未命中 ▼ ③ 沿 MRO 逐个类查找 Sub → Base → object ── 命中 → 返回 │ 未命中 ▼ ④ 类上的 __getattr__（若有） │ 没有 ▼ AttributeError: 'Sub' object has no attribute 'x' 结论：读是「三层向上找」，写是「一层原地放」。 名字相同 ≠ 同一个存储位置。

这条不对称本身不是缺陷，它让「类属性作为默认值、实例属性作为个性化覆盖」这种常见写法成立。真正的坑在于当类属性是可变对象时，读取拿到的是那个共享对象本身，而对它的原地修改（append、update、+= 作用在列表上）根本不算「写属性」，不会触发实例属性的创建——所有实例改的是同一份数据。

class Task:
    tags = []                 # 类属性，所有实例共享同一个列表

    def add(self, t):
        self.tags.append(t)   # 原地修改共享对象，不是赋值

a, b = Task(), Task()
a.add("urgent")
print(b.tags)                 # ['urgent'] —— b 从没调用过 add

把 self.tags.append(t) 换成 self.tags = self.tags + [t] 会「看起来修好了」，因为赋值触发了实例属性创建；但这掩盖了根因，也放弃了原地修改的性能。正确做法是在 __init__ 里给每个实例创建自己的容器。这与引用语义和浅拷贝那一卡（PY10）讲的是同一件事：共享的是对象，不是值。

特征类属性实例属性
存放位置类对象的命名空间实例的 __dict__
共享范围该类及其子类的所有实例仅该实例
典型用途常量、默认值、计数器、注册表每个实例各不相同的状态
被 obj.x = v 影响不会，永远不会会，创建或覆盖
写成可变对象危险：所有实例共享一份，原地修改互相污染安全：在 __init__ 里各建一份
删除方式del Cls.xdel obj.x（删掉后又能读到类属性）

最后一行值得留意：del obj.x 之后再读 obj.x，查找链会继续往上走，于是类属性「复活」了。这个行为在实现「可重置为默认值」的配置对象时非常好用，也是理解「读写不对称」是否真的想通了的一个小检验。

把类属性想成一张贴在墙上的公告，实例属性是每个人手里的便签。你读的时候先看便签再看公告，写的时候永远只写自己的便签——除非公告本身是个可以被涂改的白板，那所有人就都改到同一块板子上了。

二、__init__ 不是构造函数，__new__ 才是

几乎所有从 Java 或 C++ 过来的人第一天就会把 __init__ 当构造函数，绝大多数时候这个误解不会造成任何问题，直到你尝试子类化 tuple 或者实现一个单例。此时会发现 __init__ 拿到的 self 已经是一个完整存在的对象了——它不负责创造，只负责往里填东西。

真正分配对象的是 __new__。它是一个静态方法（哪怕你不写 @staticmethod，解释器也会特殊对待它），第一个参数是类本身而不是实例，职责是返回一个对象。只有当它返回的对象是该类（或其子类）的实例时，解释器才会紧接着调用 __init__ 去初始化它。

Point(3, 4) 展开成什么 ──────────────────────────────────────────────────────────── ① type(Point).__call__(Point, 3, 4) ← 由元类接管整个流程 │ ▼ ② obj = Point.__new__(Point, 3, 4) ← 分配内存，得到一个空对象 │ 此时实例还没有任何属性 │ ├── 若 obj 不是 Point 的实例 ──► 直接返回 obj， │ __init__ 被完整跳过 ▼ ③ Point.__init__(obj, 3, 4) ← 往已存在的对象里填字段 │ 必须返回 None ▼ ④ 返回 obj 多数类只重写 ②③ 中的 ③；重写 ② 的场景不到 5%。

把这张图记住能解释两个高频困惑。第一，为什么 __init__ 里 return self 会报 TypeError: __init__() should return None——因为返回值不是给你用的，解释器只允许 None，实例由第 ④ 步统一返回。第二，为什么某些库里的 __init__ 明明写了却没被执行——因为该类的 __new__ 返回了一个别的类型的对象，第 ② 步的分支直接短路掉了初始化。

维度__new____init__
调用时机实例化的第一步，对象尚不存在对象已创建之后
第一个参数cls（类本身）self（已创建的实例）
职责分配并返回对象给已有对象设置初始状态
返回值要求返回实例；返回非本类实例会跳过 __init__必须是 None，否则 TypeError
方法类型隐式静态方法普通实例方法
可以被跳过吗不能，一定会执行能，取决于 __new__ 的返回值
什么时候重写子类化不可变类型、实例缓存、单例、控制分配几乎所有类

什么时候真的需要 __new__

第一类是子类化不可变类型。tuple、str、int、frozenset 这些类型的值在创建时就定死了（PY02 · 变量与内置类型 里讲过它们的不可变性），等到 __init__ 拿到 self 时已经无从修改，所以要在 __new__ 里把值交给父类。

class Version(tuple):
    def __new__(cls, text: str):
        parts = tuple(int(p) for p in text.split("."))
        return super().__new__(cls, parts)   # 值必须在这里定下来

    def __str__(self):
        return ".".join(map(str, self))

print(Version("3.12.1") > Version("3.9.20"))   # True，元组比较天然可用

第二类是控制实例数量或复用实例：单例、按参数缓存实例（享元）、连接池句柄。这类需求有一个必须警惕的细节：只要 __new__ 返回的是本类实例，__init__ 就照样会被调用一遍。也就是说缓存命中时，你返回的老对象会被新一轮 __init__ 重新初始化，缓存的意义被抹掉。这类 bug 表现为「明明用了缓存，状态却总被重置」。

因此实例缓存的正确落点通常不是 __new__，而是类方法工厂：写一个 @classmethod def get(cls, key)，命中缓存直接返回，未命中才调用 cls(key)。这样初始化只在真正创建时发生一次，代码意图也直白得多。用 __new__ 做单例是能写出来的经典练习，但在真实项目里，模块级变量或工厂函数几乎总是更好的选择。

__new__ 是产房，__init__ 是命名和登记。你想改的十有八九是登记流程，不是产房；一旦真要动产房，记得登记环节可能会对同一个孩子重复执行。

三、__repr__ 与 __str__：给谁看的区别

这两个方法的差别不在实现难度，而在受众。__repr__ 是写给开发者的：目标是无歧义地说清「这是什么对象、里面装了什么」，理想状态是输出一段合法的构造表达式，让 eval(repr(x)) 能还原出一个等价对象。__str__ 是写给最终用户的：目标是可读、友好，可以省略细节、可以做本地化，不需要精确。

大多数类的这两个受众其实是同一批人，所以只写一个就够。关键是写哪一个：只定义 __repr__ 时，str(x) 会自动回退到它；只定义 __str__ 时，repr(x) 不会回退，仍然输出默认的 <module.Cls object at 0x...>。这个回退是单向的，所以规则很干脆：只实现一个，就实现 __repr__。

维度__repr____str__
面向谁开发者、日志读者、调试者最终用户、界面文案
目标无歧义、可复原、信息完整可读、简洁、可本地化
被谁触发repr()、REPL 回显、容器打印、%r、f"{x!r}"str()、print()、f"{x}"、format()
缺失时的回退无回退，退化成默认的内存地址形式回退到 __repr__
典型输出Order(id=1042, total=99.5)订单 1042（¥99.50）
只写一个时写这个不要只写这个

容器打印用的是 repr，不是 str

这条规则容易被忽略，但影响面极大：打印一个列表、字典、集合时，容器自己的 __str__ 会对每个元素调用 repr。原因也很实在——容器需要区分 "1" 和 1、区分 None 和字符串 "None"，只有 repr 能提供这种区分度。于是一个只写了 __str__ 的类，单独 print(obj) 时漂漂亮亮，一放进列表就整排变成内存地址。

只写 __str__ 的后果（同一个对象，三种上下文） ────────────────────────────────────────────────────────────── print(order) → 订单 1042 print([order, order]) → [<shop.Order object at 0x7f9c1a0d3e50>, <shop.Order object at 0x7f9c1a0d3e50>] logger.info("%r", o) → <shop.Order object at 0x7f9c1a0d3e50> raise ValueError(...) → 异常上下文里同样是地址 只写 __repr__ 的后果 ────────────────────────────────────────────────────────────── print(order) → Order(id=1042, total=99.5) ← str 回退到 repr print([order, order]) → [Order(id=1042, total=99.5), Order(id=1042, total=99.5)] logger.info("%r", o) → Order(id=1042, total=99.5) 回退只有一个方向：str 缺 → 找 repr；repr 缺 → 无处可去。

把 __repr__ 写好的实际收益出现在事后排查——即只能依靠已经落盘的日志、异常栈和监控数据来还原问题现场的场景。这种时候你没法回到现场加断点，日志里每个对象打出的信息量，直接决定了能不能定位问题。

示例场景：某订单服务的一条告警链路上，异常日志里 12 条上下文记录全部是 <shop.Order object at 0x...> 形式。值班同学为了知道出问题的是哪几笔订单，先按时间戳去数据库反查，再比对 3 张表，耗时约 45 分钟才锁定 2 笔异常订单。事后给 Order 补了一个 6 行的 __repr__，输出订单号、状态和金额；下一次同类告警从看到日志到定位订单用了不到 2 分钟。修改量 6 行，节省的是每次故障 40 分钟以上的排查时间。

实现上有两个惯例值得遵守。一是让输出长得像构造调用：Cls(field=value, ...)，即使做不到真的能 eval，这个形状也最容易读，也方便直接复制到 REPL 里改一改重现问题。二是在 __repr__ 里引用其他对象时用 {x!r} 而不是 {x}，保证嵌套层级也保持无歧义。

class Order:
    def __init__(self, oid, total, status):
        self.oid, self.total, self.status = oid, total, status

    def __repr__(self):
        return f"Order(oid={self.oid!r}, total={self.total!r}, status={self.status!r})"

    def __str__(self):
        return f"订单 {self.oid}（¥{self.total:.2f}）"

顺便一提，用 @dataclass 装饰的类会自动获得一个符合上述惯例的 __repr__，这也是它在实践中最被低估的好处之一。数据类那一卡（PY16）会展开讲它还顺手替你生成了什么。

__repr__ 不是给对象「美化外观」，而是给未来的自己留一份可读的现场记录。判断标准很简单：三个月后只看日志这一行，你能不能说清出问题的是哪个对象。

四、__eq__ 与 __hash__ 的联合契约

默认情况下，一个对象的相等就是身份相等（是不是同一个对象），哈希由内存地址派生。这套默认行为是自洽的。一旦你重写 __eq__ 表达「字段相同就算相等」，自洽就被打破了：两个字段相同的对象现在相等，但它们的地址不同，哈希也不同。Python 的选择是宁可让你立刻报错，也不给你一个悄悄坏掉的哈希——只要类里定义了 __eq__ 而没定义 __hash__，解释器就把 __hash__ 置为 None。

后果是这个类的实例马上不能进 set、不能当字典键，报错是 TypeError: unhashable type: 'Point'。这个报错常被误读成「Python 不让我用自定义类当键」，实际含义是「你只签了契约的一半」。

契约的三条内容

所谓哈希契约，指的是 __hash__ 与 __eq__ 必须共同满足的一组约束，缺一条就会让基于哈希的容器出现静默错误。三条内容分别是：相等的对象哈希值必须相同；不相等的对象哈希值最好不同（只影响性能，不影响正确性）；哈希值在对象的整个生命周期内必须稳定。

第三条直接推出一个设计约束：参与哈希的字段不能是会变的字段。所以「可哈希」和「可变」在实践中是一对矛盾——真正需要进集合、作键的对象，应该把参与相等判断的那部分字段设计成只读。

d[key] 与 s.add(x) 内部的两段式查找 ────────────────────────────────────────────────────────────── 第一段：算哈希，定桶（O(1)，只做整数运算） h = hash(key) ──► idx = h & (table_size - 1) │ ▼ ┌──────────────────────┐ │ 槽位空 → 未命中，插入 │ └──────────────────────┘ │ 槽位有东西 ▼ 第二段：逐个比相等（可能调用你的 __eq__） 先试 key is stored ── 是同一个对象 → 命中（快路径） 再试 key == stored ── 调用 __eq__ → 命中 都不成立 ── 哈希冲突，探测下一个槽位 违反契约会发生什么 ────────────────────────────────────────────────────────────── 相等但哈希不同 → 两个「相等」的对象落进不同的桶， 第二段永远碰不上 → 去重失效、查不到已存的键 哈希会变 → 对象被改过之后算出新桶号， 去新桶里找不到 → 键还在字典里但取不出来

上图的关键是：哈希决定「去哪找」，相等决定「是不是它」。第一段错了，第二段再正确也没用——这就是为什么违反契约的错误不会抛异常，只会让结果悄悄不对。

示例场景：一个数据清洗脚本要对 50000 条记录按「姓名 + 手机号」去重，做法是给记录类写了 __eq__ 比较这两个字段，同时为了让实例能进 set，随手写了 __hash__ = object.__hash__。脚本不报错，跑完输出 50000 条，一条都没去掉。原因是哈希仍按身份计算，两条字段相同的记录落在不同的桶里，__eq__ 从头到尾没被调用过一次。把 __hash__ 改成 hash((self.name, self.phone)) 后，同一份数据去重到 47318 条，即 2682 条重复被识别出来。全部改动 1 行，而这 1 行的缺失让下游统计口径错了整整一周。

正确的写法是让两个方法用同一组字段，并且把这组字段写在一个地方避免以后改漏。NotImplemented 那一句同样重要：当右操作数不是同类型时，返回它而不是 False，Python 就会去尝试反射比较（问对方的 __eq__），双方都放弃时才退回身份比较。直接返回 False 会让「你的类和别人的兼容类型比较」这条路永久关闭。

class Point:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x, self.y = x, y

    def _key(self):
        return (self.x, self.y)      # 相等与哈希唯一的字段来源

有了这个 _key，两个方法都只引用它，以后增删字段改一处即可：

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented    # 交给对方尝试，而不是断言 False
        return self._key() == other._key()

    def __hash__(self):
        return hash(self._key())
你写了什么实例可哈希吗后果
都不写可以按身份相等、按地址哈希，自洽但无法按值去重
只写 __eq__不可以__hash__ 被置为 None，进 set 立刻 TypeError
只写 __hash__可以相等仍按身份判断，去重几乎必然失效
__eq__ + __hash__ = object.__hash__可以最危险：不报错，但去重静默失效
两者共用同一组不可变字段可以正确，推荐
__eq__ + __hash__ = None（显式）不可以正确的表态：这是可变对象，本就不该作键

比较运算符不会自动补全

还有一个独立的坑：定义了 __eq__ 不会让你自动获得 != 之外的任何运算符。!= 确实由 __eq__ 取反得到，但 <、<=、>、>= 对应四个独立方法 __lt__、__le__、__gt__、__ge__，一个都不会被推导出来。只定义了 __lt__ 就去 sorted() 是可行的（排序只用 <），但拿去和别的对象比大小就会报 TypeError: '>' not supported between instances of 'Point' and 'Point'。

要补全就用 functools.total_ordering：它要求你提供 __eq__ 和四个比较之一，自动派生剩下三个。代价是派生出来的方法要多绕一层调用，热路径上有微小开销；对性能敏感的类型手写四个方法更合适。

哈希是门牌号，相等是核对身份证。门牌号算错了，身份证再准也敲不开那扇门——而且不会有人报错，只会告诉你「这户人家不存在」。

五、运算符重载与协议方法地图

把前面几节的内容抽象一层：Python 的运算符和内置函数几乎都不是「针对特定类型的硬编码逻辑」，而是翻译层。len(x) 翻译成 type(x).__len__(x)，a + b 翻译成 type(a).__add__(a, b)，for i in x 翻译成取 __iter__。这些以双下划线开头结尾的方法叫特殊方法，它们是解释器与你的类之间约定的接口名，只要实现了对应的方法，你的类就能接入相应的语法。PY03 · 容器四件套 里那些「列表可以切片、字典可以 in」的能力，本质上都是内置类型实现了这些方法而已，而你的类同样可以。

有两个细节容易踩：其一，特殊方法的查找是在类上进行的，不走实例 __dict__。给实例挂一个 obj.__len__ = ... 不会让 len(obj) 生效。其二，只实现一部分协议是完全合法的，Python 不强制你「全都实现」——但缺失的部分不会自动补齐，比如实现了 __getitem__ 却没有 __len__，那 len() 就是不能用。

反射版和原地版：两个最容易漏的分支

算术那三行值得再说两句。a + b 时解释器先问 type(a).__add__，返回 NotImplemented 才转而问 type(b).__radd__。所以 vec * 3 只需要 __mul__，而 3 * vec 必须有 __rmul__，因为 int.__mul__ 完全不认识你的类型。反射运算指的就是这套「左边不认识时把机会让给右边」的回退机制，它让自定义类型能和内置类型混算。

__iadd__ 是另一个易漏点。不实现它时 a += b 会退化成 a = a + b，也就是创建新对象再重新绑定。对不可变类型这正是想要的；对可变的容器类型则意味着白白复制一份数据，而且如果这个名字有别的引用，那些引用不会看到变化。实现 __iadd__ 时务必原地修改并 return self，忘了返回会让 a 变成 None——这个 bug 特别难认，因为报错发生在后续用到 a 的地方。

__getattr__ 与 __getattribute__ 的分工

这两个名字只差几个字母，行为差别却是天壤之别。__getattr__ 是兜底钩子：只有第一节那条查找链全部走空、正要抛 AttributeError 时才被调用。它是实现动态代理、懒加载、配置对象「点号访问」的标准手段，而且因为不参与正常路径，对性能几乎没有影响。

__getattribute__ 相反，它拦截该类实例的每一次属性访问，包括 self.x 这种内部访问。一旦在它内部写了 self.something，就会再次触发它自己，直接无限递归到 RecursionError；正确写法是 super().__getattribute__(name)。日常开发几乎没有必须动它的场景，需要拦截时优先考虑属性描述符或 property。

class LazyConfig:
    def __init__(self, path):
        self._path, self._data = path, None

    def __getattr__(self, name):        # 仅在常规查找失败后触发
        if self._data is None:
            self._data = _load(self._path)
        if name not in self._data:
            raise AttributeError(name)  # 保持契约，别漏出 KeyError
        return self._data[name]

最后一行的 raise AttributeError 不是可选的装饰。hasattr、getattr(obj, k, default)、序列化库、调试器全都依赖「取不到就抛 AttributeError」这个约定；在 __getattr__ 里漏出 KeyError，会让这些工具在你的对象上行为异常，而且异常来源看起来毫无关联。

特殊方法不是 API，是插头。你实现哪个方法，就等于把类插进 Python 的哪条语法插座；插座是标准的，形状不对就插不上，插错了也没人拦你。

六、实例状态的组织与 __slots__

默认情况下每个实例都带一个 __dict__，这是它灵活性的来源——你可以随时给实例加任何属性。代价是每个实例都多了一个字典对象：字典本身有哈希表结构、有为扩容预留的空槽，还要为每个键存一份引用。对单个对象来说这点开销无所谓，对几十万个同类小对象来说，字典的开销可能超过你真正想存的数据。

__slots__ 就是针对这个场景的机制。在类体里写一个字符串序列声明「这个类的实例只会有这几个属性」，解释器就不再给实例创建 __dict__，改用固定偏移的槽位——即在实例对象内部按顺序排布的引用位置，通过描述符按下标直接存取，不再经过哈希查找。

两种实例状态布局（示意，字段为 x / y 两个） ────────────────────────────────────────────────────────────── 普通类 实例对象 ──► [ 类型指针 | 引用计数 | __dict__ 指针 ] ─┐ ▼ ┌────────────────────────────────────┐ │ dict: 哈希表 + 预留空槽 + 键的引用 │ │ "x" → 3 "y" → 4 │ └────────────────────────────────────┘ 读写要算哈希、定桶、比较键 带 __slots__ = ("x", "y") 的类 实例对象 ──► [ 类型指针 | 引用计数 | slot0 | slot1 ] ↑ x ↑ y 没有字典，按固定偏移直接取 代价：只能有 x / y 这两个属性 取舍：省的是「每个实例一个字典」的固定开销， 丢的是「随时加属性」的灵活性。

收益只在数量级上才有意义。造几百个对象时省下的内存无人在意；造几十万到上百万个同结构小对象时，内存占用往下掉一半以上是常见结果，而且因为省掉了哈希查找，属性读写也会略快。典型适用场景是解析出来的记录行、几何点、时间序列采样点、图的节点这类「字段固定、数量巨大、逻辑简单」的对象。

示例场景：一个日志分析脚本把每行解析成一个只有 5 个字段的 Event 对象，一次批处理约 120 万个实例，常驻内存约 610 MB，在 1 GB 内存限额的容器里频繁被杀。给 Event 加上 6 个字符的 __slots__ 声明后，同样的输入常驻内存降到约 230 MB，降幅约 62%，处理耗时也从 41 秒降到 36 秒。改动 1 行，问题从「要加机器」变成「不用管了」。反过来说，如果这个脚本一次只处理 2000 行，同样的改动省下的是几百 KB——那就纯属给后来人添麻烦。

约束也要说清楚。声明了 __slots__ 之后给实例赋一个未声明的属性会直接报 AttributeError: 'Event' object has no attribute 'extra'，这个特性有时反而是优点（能挡住拼错属性名这类 bug），但它和很多依赖动态属性的库不兼容。继承上的规则是：任何一个基类没有声明 __slots__，子类实例就照样会有 __dict__，优化归零；多个基类各自声明了非空 __slots__ 时，多继承会直接报布局冲突。弱引用也需要显式在 __slots__ 里加 "__weakref__" 才可用。

判断维度值得用 __slots__属于过度优化
同时存活的实例数几十万以上几百、几千
字段是否固定固定且已定型还在频繁增删字段
是否被实测确认内存已是瓶颈，profile 指向这类对象凭感觉「先优化一下」
继承结构单继承，链上各层都声明了复杂多继承、混入大量第三方基类
是否需要动态属性不需要，固定即是约束依赖运行时挂属性的框架
替代方案是否更好无换成 NamedTuple、数组、列式结构更彻底

最后一行值得展开一句：当你真的在处理上百万条结构化记录时，比 __slots__ 更彻底的方案往往是干脆不要每行一个对象——用列式存储（每个字段一个数组）能把内存再降一个量级，而且对向量化计算友好。__slots__ 适合的是「必须保留对象语义、但要削掉字典开销」这个中间地带。

属性命名约定：一个是礼貌，一个是机制

单下划线前缀 _name 纯粹是约定：解释器不做任何事，它只是在告诉读代码的人「这是内部实现，不属于对外接口，我可能随时改」。唯一有实际效果的地方是 from module import * 会跳过它们（PY08 · 模块、包与项目结构 讲过这个规则）。也就是说，别人硬要访问 obj._name 完全可以，Python 从设计上就不提供强制私有。

双下划线前缀 __name（末尾不带双下划线）则触发真正的机制：名字改写——编译期把类体内出现的 __name 改写成 _ClassName__name。它的目的不是防止外部访问（改写规则是公开的，外面照样能用 obj._Event__name 拿到），而是避免子类无意间覆盖基类的内部属性。

写法解释器做了什么含义什么时候用
name无公开接口默认选择
_name仅 import * 时跳过内部实现，外部请勿依赖绝大多数「私有」需求
__name改写为 _Cls__name不希望被子类撞名的内部状态设计供人继承的基类时
__name__无改写协议名，留给 Python 用不要自己发明这种名字
name_无规避与关键字或内置名冲突，如 class_参数名撞了保留字时

名字改写还有一个附带效果值得知道：它在 __slots__ 里同样生效，写 __slots__ = ("__x",) 得到的槽位名是 _Cls__x。这也是调试时看到 _Cls__x 这种奇怪属性名不必惊讶的原因。

  • 可变的默认值在 __init__ 里为每个实例新建，类属性只放不可变的常量
  • 只写一个字符串化方法时写 __repr__，格式对齐 Cls(field=value)
  • __eq__ 和 __hash__ 成对出现，共用同一组不可变字段
  • 类型不匹配时 __eq__ 返回 NotImplemented，把机会留给反射比较
  • 需要动态属性兜底时用 __getattr__，并在取不到时抛 AttributeError
  • __slots__ 等 profile 确认内存瓶颈后再加，并检查继承链上每一层
  • 内部属性统一用单下划线；只在设计可继承基类时才用双下划线
  • 把 [] 或 {} 写成类属性，然后在方法里 append / update
  • 只写 __str__ 不写 __repr__，导致日志和列表打印全是内存地址
  • 为了让实例能进 set 而写 __hash__ = object.__hash__——去重会静默失效
  • 把会变的字段放进 __hash__，对象改一次键就再也取不出来
  • 在 __init__ 里 return self，或指望它的返回值被谁用到
  • 用 __new__ 做实例缓存却忘了 __init__ 仍会重跑一遍
  • 重写 __getattribute__ 并在里面直接写 self.xxx，等着 RecursionError

实例状态的组织顺序应该是：先用最普通的类写对，再看数据量决定要不要削开销。__slots__ 是在几十万个对象上生效的工具，不是写每个类都该加的模板代码。

Q&A

为什么给类属性写了一个空列表，改一个实例会影响所有实例？
因为类属性只有一份，所有实例读到的是同一个列表对象。self.tags.append(x) 这行代码里没有任何赋值动作，它先按查找链读到类上的那个列表，再对它原地修改，所以修改结果对所有实例可见。如果写成 self.tags = self.tags + [x]，赋值会在实例 __dict__ 里新建一个属性，看起来问题消失了，但类属性依然是共享的可变对象，隐患还在。正确做法是在 __init__ 里写 self.tags = []，让每个实例拥有自己的容器。类属性适合放常量、默认的不可变值、计数器和注册表，一旦要放可变容器就应该先问自己是不是真的想让所有实例共享它。
我什么时候需要重写 __new__？
日常业务代码基本不需要。真正必须用它的场景是子类化不可变类型：tuple、str、int、frozenset 的值在创建时就固定了，等 __init__ 拿到 self 时已经无法修改，只能在 __new__ 里把值传给父类。另一类是需要控制对象分配本身，比如实例缓存、享元、单例，或者根据参数返回不同子类的实例。用它做缓存有个必须注意的陷阱：只要返回的是本类实例，__init__ 就会照常再执行一遍，把你缓存的对象重新初始化。因此实例复用更推荐用类方法工厂，把「查缓存」和「真正创建」分开，逻辑更直白也不会踩这个坑。
__repr__ 和 __str__ 只写一个的话，写哪个？
写 __repr__。回退是单向的：没有 __str__ 时 str() 和 print() 会自动使用 __repr__，反过来没有 __repr__ 时 repr() 不会去用 __str__，只会输出默认的 类名 object at 0x...。而 repr 的使用场景恰恰是你最需要信息的那些地方：日志的 %r、异常上下文、REPL 回显，以及打印容器时对每个元素的展示。只写 __str__ 的类会出现一种典型症状——单独打印很好看，一放进列表就整排变成内存地址。只有当面向用户的展示格式和调试格式确实需要分开时，才补上 __str__。
重写了 __eq__ 之后为什么实例不能放进 set 了？
因为解释器在类里定义了 __eq__ 而没有定义 __hash__ 时，会把 __hash__ 设为 None，于是实例变成不可哈希，报 TypeError: unhashable type。这是刻意的保护而不是限制：你重新定义了「什么叫相等」，但默认哈希还是按内存地址算的，两者已经不一致了。如果放任不管，两个相等的对象会因为哈希不同落进不同的桶，去重和字典查找会静默出错，比直接报错难查得多。解决办法是同时定义 __hash__，用和 __eq__ 完全相同的那组字段计算，通常写成 hash((self.a, self.b))。如果这个对象本来就是可变的、不该作为键，那就显式写 __hash__ = None 表明态度。
可变对象能不能实现 __hash__？
语法上能，但基本上不该这么做。哈希契约要求哈希值在对象的整个生命周期内保持稳定，因为字典和集合是用哈希值决定「把它放在哪个桶」的。如果对象在被放进容器之后参与哈希的字段变了，再去查它时会算出一个新的桶号，在那个桶里当然找不到——键还在字典里，你却取不出来，而且不会有任何报错。折中方案有两种：只让不会变的那部分字段参与哈希和相等判断，把可变字段排除在外；或者干脆把这个类设计成不可变的，需要修改时返回一个新对象。frozenset 和 tuple 可哈希、set 和 list 不可哈希，正是同一条规则的体现。
__getattr__ 和 __getattribute__ 到底差在哪？
差在触发时机和触发频率。__getattr__ 是兜底钩子，只有当常规查找链（实例字典、类、基类链）全部走空、解释器正准备抛 AttributeError 时才被调用，所以正常属性访问完全不经过它，性能开销可以忽略。__getattribute__ 拦截的是这个类实例的每一次属性访问，包括你在方法里写的 self.x。这带来两个后果：一是每次访问都多一层 Python 调用，热路径上很贵；二是如果在它内部写了 self.something，会再次触发它自己造成无限递归，必须改用 super().__getattribute__(name)。实践中动态代理、懒加载、配置对象点号访问这些需求都用 __getattr__ 就够了，需要更精细的控制时优先考虑 property 或描述符，而不是动 __getattribute__。
a += b 和 a = a + b 对自定义类有区别吗？
有，取决于你是否实现了 __iadd__。实现了的话 a += b 会调用它，通常的写法是原地修改自身状态然后 return self，对象身份不变，所有指向它的引用都能看到变化。没实现的话 a += b 会退化为 a = a.__add__(b)，即创建一个新对象再把名字重新绑定过去，原对象没变，别处的引用看不到任何更新。对不可变类型这正是期望行为，对可变容器则意味着白白复制一份数据。实现 __iadd__ 时最常见的 bug 是忘了 return self，那么 a 会被绑定成 None，而报错会推迟到后面某个用到 a 的地方，看起来毫无关联。
是不是所有类都该加 __slots__？
不是，它是针对特定场景的优化而不是通用最佳实践。收益来自省掉「每个实例一个字典」的固定开销，因此只有在同时存活几十万甚至上百万个同类小对象时才有意义；几百几千个实例的场景，省下的内存完全不值得付出代价。代价是实实在在的：不能给实例动态添加未声明的属性，弱引用要显式声明 "__weakref__"，继承链上任何一层漏了声明就会重新长出 __dict__ 让优化归零，多个基类都有非空槽位时多继承还会直接报布局冲突。合理的顺序是先用普通类把功能写对，等 profile 明确指出内存瓶颈在这类对象上再加。另外，如果数据量真的大到那个程度，改成列式存储或数组通常比 __slots__ 更彻底。
