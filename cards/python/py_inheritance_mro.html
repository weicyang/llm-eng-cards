继承不是「把父类的代码搬过来」，而是「把自己挂到一条属性查找链上」。你省下的是重复代码，付出的是这条链上任何一环变动都会波及自己。搞清楚链是怎么排的、谁在链上走、走到哪一步停，继承的绝大部分玄学就消失了。

一、继承做了什么，以及它真正的代价

写下 class Dog(Animal) 的那一刻，Python 做的事情比大多数人想象的少：它没有把 Animal 里的任何代码复制到 Dog 里，只是在 Dog 这个类对象上记了一笔「我的上游是 Animal」，并据此算出一条有序的类列表。之后每次访问 dog.speak，解释器都沿着这条链现场查找。

这个「现场查找」是理解继承一切行为的起点。它意味着基类后来新增的方法，子类立刻就有；也意味着基类改掉一个内部方法的语义，所有子类在下一次调用时立刻跟着变——没有编译期检查，没有提示。

一次属性访问走过的路

d = Dog("旺财"); d.speak() ───────────────────────────────────────────────────────── 第 1 站 实例自己的 __dict__ {'name': '旺财'} 没有 speak → 继续 │ ▼ 第 2 站 沿 type(d).__mro__ 逐个翻类的 __dict__ Dog.__dict__ {'__init__', 'fetch'} 没有 → 继续 Animal.__dict__ {'speak', 'describe'} 命中 ✔ object.__dict__ {...} 轮不到 │ ▼ 第 3 站 命中的是函数对象 → 触发描述符协议 → 绑定成方法 → 调用 │ ▼ 全链未命中 → 最后才调 __getattr__（若定义了） → 仍然没有 → AttributeError: 'Dog' object has no attribute 'speak' 关键：查的是「类的 __dict__」，不是「父类的源码」。 基类今天加一个方法，昨天写的子类今天就拥有它。

这条链解释了一个常被误解的现象：子类「覆盖」父类方法，本质上不是替换，而是抢先命中。父类的那份实现还在原地，只是查找时先撞上了子类的版本，所以你随时可以用 Animal.speak(self) 把它请回来。

继承没有复制任何代码，它只是给你排了一条查找队列。子类覆盖父类方法，不是把父类的删掉，而是站到了队伍前面。

脆弱基类：耦合强度被严重低估

脆弱基类问题指的是：基类的一处内部改动，在不修改任何子类代码的前提下，导致子类行为出错。它之所以危险，是因为破坏发生在「基类作者认为自己只改了私事」的时候。

典型形态是这样的：基类的 add() 原本独立实现，add_many() 循环调用 add()；某个子类为了统计条数，覆盖了 add() 加了一行计数。某天基类作者出于性能考虑，把 add_many() 改成直接批量写入、不再走 add()——基类的对外行为完全没变，测试全绿，但那个子类的计数从此少算了一大半，而且不会报任何错。

问题的根源在于：子类依赖的不是基类的接口，而是基类的内部调用顺序。而这个顺序从来没有被写进任何契约里。这正是继承比函数调用、比组合都更强的耦合——它把实现细节也一并暴露给了下游。

示例场景：某内部 SDK 的基类 BaseClient 把 request() 的重试逻辑从「send() 内部循环 3 次」改成「外层 request() 循环 3 次」，基类自身的 12 个单测全部通过。但下游有 7 个子类覆盖了 send() 来打点，改动后这些打点从每次请求上报 3 条变成 1 条，监控面板上的失败率曲线整体下移到原来的三分之一，两周后才因为一次真实故障没告警而被发现。基类的公开行为一个字没改，坏掉的是没人写下来的内部调用约定。

接口继承与实现继承：把两种动机分开

接口继承是为了多态——让一族类对外呈现同一组方法，调用方可以互换使用而不必知道具体是哪一个。实现继承是为了复用——我想白拿基类那几个写好的方法，至于要不要对外可替换，无所谓。

这两种动机在语法上长得一模一样，代价却完全不同。接口继承的耦合停在方法签名上，基类通常很薄甚至是抽象的；实现继承的耦合深入到基类的内部流程，脆弱基类问题几乎全部出自这一侧。

维度接口继承（为了多态）实现继承（为了复用）
目的让一族类可互换，调用方写一套代码白拿基类已经写好的方法体
基类形态薄，常是抽象基类或只有签名厚，装着大量具体逻辑
耦合面方法名与签名方法名、签名、加上内部调用顺序
基类改动的影响只有改签名才会波及子类改任何内部实现都可能波及子类
更合适的替代抽象基类 / 协议（通常无需替代）组合 + 委托，见第六节
层级深度经验值2 层足够，很少需要第 3 层超过 2 层基本就是信号灯

实用的自查是一句话：我需要「把子类对象传给一个接受基类的函数」吗？需要，那是接口继承，继承合理；不需要，只是想少写几行，那就该考虑把基类当成一个成员对象持有起来。

二、MRO：方法解析顺序为什么需要一个算法

单继承时，查找顺序是显而易见的：自己、父亲、祖父、一路到 object，一条直线，没有任何歧义。需要算法，是因为多继承把这条直线变成了图。

一旦两个父类共享同一个祖先，就形成了菱形继承——从子类出发有两条不同的路径能走到同一个基类。这时「先深度还是先广度」两种朴素规则都会翻车：纯深度优先会让共同基类排在另一个直接父类前面，导致本该生效的覆盖被祖先抢走；纯广度优先又会让父子顺序错位。

C3 线性化给出唯一确定的顺序

Python 从 2.3 起使用 C3 线性化——一种把继承图压平成一条有序列表的算法，它保证结果同时满足两条约束：子类一定排在它的所有父类之前；父类之间的相对顺序，和 class 语句里书写的顺序一致。满足这两条的顺序如果存在，C3 给出的就是唯一的那一个。

object class Base: pass ▲ class A(Base): pass │ class B(Base): pass Base class D(A, B): pass ▲ ▲ │ │ 两条路径都能从 D 走到 Base： A B D → A → Base 和 D → B → Base ▲ ▲ 「深度优先」会排成 D, A, Base, B —— B 被 Base 挡在后面， └─┬──┘ B 里对 Base 方法的覆盖会失效，这显然不对。 D C3 线性化结果 D.__mro__ = (D, A, B, Base, object) ↑ └─┬─┘ └──┬───┘ 自己 声明顺序 共同基类只出现一次， 且排在所有派生类之后 两条不可违背的约束（单调性） ① 子类一定排在它的每一个父类之前 ② 父类之间的相对顺序 = class D(A, B) 里书写的顺序

可以直接查看这条链，不需要任何推理：

>>> class Base: pass
>>> class A(Base): pass
>>> class B(Base): pass
>>> class D(A, B): pass
>>> [c.__name__ for c in D.__mro__]
['D', 'A', 'B', 'Base', 'object']

遇到任何「为什么调到的是这个方法」的疑惑，别猜，把 Klass.__mro__ 打出来。答案永远是这条列表里从左往右第一个拥有该属性的类，没有例外。

声明顺序直接决定行为

继承声明MRO（省略 object）说明
class C(A)C, A, Base单继承，一条直线，无需算法
class D(A, B)D, A, B, Base菱形；A 先于 B，与书写顺序一致
class D(B, A)D, B, A, Base只换了书写顺序，同名方法的胜者就换人
class S(LogMixin, Service)S, LogMixin, Service混入写在左边才能拦在主类前面，这是惯例的由来
class S(Service, LogMixin)S, Service, LogMixin混入排在主类后面，多半拦不到任何调用，等于白写
class D(Base, A)TypeError要求 Base 先于 A，又要求子类 A 先于父类 Base，矛盾

最后一行值得留意：不满足单调性的继承声明，错误发生在类定义时，也就是模块被 import 的那一刻，而不是等到你去实例化。报错原文是 TypeError: Cannot create a consistent method resolution order (MRO) for bases Base, A。它看起来吓人，但其实是最友好的一类失败——在任何业务代码跑起来之前就把矛盾摆了出来。

第四行和第五行的对比则是混入类惯例的全部理由：混入必须写在左侧。这一点在第五节还会再展开。

三、super() 不是「调用父类」，而是「沿 MRO 走下一个」

这是整张卡片里最值得改掉的一个认知。大量教程把 super() 解释成「调用父类的方法」，在单继承下这个说法恰好总是对的，于是没人发现它错了——直到写出第一个多继承。

super() 的真实语义是：在实例的 MRO 里，找到「当前这个类」所在的位置，然后取它右边第一个拥有目标属性的类。注意两个限定词：用的是实例的 MRO（不是当前类自己的），起点是当前类（不是实例的类）。因此 super() 完全可能跳到一个和当前类毫无父子关系的兄弟类上。

class Base / class A(Base) / class B(Base) / class D(A, B) d = D(); d.setup() ───────────────────────────────────────────────────────────── 实例 d 的 MRO（super() 就在这条链上向右走一格） D ──► A ──► B ──► Base ──► object │ │ │ │ │ │ │ └─ Base.setup 里的 super() → object │ │ └─ B.setup 里的 super() → Base │ └─ A.setup 里的 super() → B ←★ A 和 B 没有父子关系！ └─ D.setup 里的 super() → A 写 A 的时候，你根本不知道 B 存在； 运行时 A 里的 super().setup() 却跳进了 B。 这不是意外，这就是 super() 的定义：取「实例 MRO 中当前类的下一个」。 反过来，如果 A 直接写死 Base.setup(self) 而不是 super()： D ──► A ──╳──► Base B 被整条跳过，静默失效

上图最后两行是协作式多继承的核心——多个类各自只调 super()、不指名道姓调具体父类，于是它们能被任意组合、按 MRO 串成一条完整的责任链。任何一个环节改成硬编码的 Base.setup(self)，链条就在那里断开，后面的类被静默跳过。

class A(Base):
    def setup(self, **kw):
        print("A 先做点事")
        super().setup(**kw)   # 不是「调父类」，是「交给 MRO 里的下一个」

把 super() 读成「下一个」，不要读成「父类」。它是一根接力棒，交给谁由实例的 MRO 决定，而 MRO 由最终那个子类的继承声明决定——写基类的人无权也无需知道。

无参 super() 的隐形依赖

Python 3 允许直接写 super()，省掉 Python 2 时代的 super(A, self)。这不是语法糖那么简单：编译器在检测到函数体里出现 super 或 __class__ 时，会给这个函数悄悄加一个名为 __class__ 的闭包单元，指向它所在的类。super() 正是靠读这个单元 + 读第一个位置参数（也就是 self）来还原出那两个隐含参数的。

这个机制带来三条实际约束：函数必须定义在类体内部，事后用赋值挂上去的函数里 super() 会抛 RuntimeError: super(): __class__ cell not found；函数必须有第一个位置参数可取；在 staticmethod 里没有 self 可用，只能退回带参形式。

写法能否使用场景与注意
super().m()（类体内）可以默认写法，编译期注入 __class__
super(A, self).m()可以需要显式指定起点时用；写错类名会跳错位置
super(type(self), self)不要用子类调用时起点是子类自己，直接无限递归
类外函数里 super()不可以RuntimeError: super(): __class__ cell not found
staticmethod 里 super()不可以没有 self，只能用带参形式或改成 classmethod
Base.m(self) 硬编码能跑但危险绕过 MRO，协作链在此断开，后续类被跳过

第三行那个陷阱很值得记一下。super(type(self), self) 看起来聪明，实际是死循环制造器：当 C 继承 A、你在 A 里这样写，实例是 C 时 type(self) 得到 C，于是 super() 的起点永远从 C 之后算起，又落回 A，直到 RecursionError。

四、多继承的真实故障模式

多继承本身不是错误，出事的几乎总是同一批具体问题。把它们逐个拆开，比记住「不要用多继承」这条口号有用得多——因为混入类、collections.abc、大量框架的基类体系全都建立在多继承之上，你躲不开。

所有故障归结起来只有一个共同点：协作链的某一环没有履行契约。契约有两条，一是把参数原样往后传，二是一定要调 super()。

理想状态：每个类都 super() 转发，链条走到底 D.__init__ ──► A.__init__ ──► B.__init__ ──► Base.__init__ ✔ ✔ ✔ ✔ 全部执行 故障一：A 忘了调 super() D.__init__ ──► A.__init__ ──╳ B.__init__ 从未执行（无任何提示） Base.__init__ 从未执行（无任何提示） 症状：B 本该设置的 self.conn 不存在 AttributeError 出现在几十行之外的某个方法里 故障二：A 的签名不接受 **kwargs D(name='x', level=3) ──► A.__init__(self, name) level 无处安放 ✗ 症状：TypeError: __init__() got an unexpected keyword argument 'level' 或更糟 —— 参数被 A 悄悄吞掉，B 拿到的是默认值 故障三：同名方法按 MRO 静默取胜 D(A, B) 里 A.save 和 B.save 都存在 → 永远只有 A.save 被调用 症状：没有报错、没有警告，只是 B 的那份逻辑从来没跑过

第四行的「执行两次」尤其隐蔽。菱形结构下，如果 A 和 B 都老老实实用 super()，Base.__init__ 恰好执行一次——这正是 C3 让共同基类只出现一次的价值。但只要有一个类改成 Base.__init__(self) 硬调，Base 就会被执行两次：一次来自硬调，一次来自另一条 super() 路径。

示例场景：某数据同步服务的 Worker 同时继承 RetryMixin 和 MetricsMixin，两者最终都指向 BaseWorker。上线后监控显示每处理 1 万条记录，连接池被创建 2 次、活跃连接数稳定在配置上限的 2 倍（40 而非 20），数据库侧连接数告警连续触发 6 天。排查发现 MetricsMixin.__init__ 里写的是 BaseWorker.__init__(self) 而不是 super().__init__()，导致 BaseWorker 被初始化两遍。改成 super() 后连接数回到 20，改动量 1 行。整个过程没有任何异常抛出，靠的是连接数曲线才发现。

多继承的 bug 有个共同特征：不报错。少执行一个类、多执行一遍基类、调错同名方法，Python 都会安静地继续跑下去。所以这里的排查工具不是 try/except，而是 __mro__ 和打印。

把协作契约写进签名

要让一条链可靠，参与其中的每个类的 __init__ 都应该满足：只用关键字参数取走自己关心的那几个，其余原封不动通过 **kwargs 往后传，并且无条件调用 super().__init__(**kwargs)。位置参数是协作式多继承的天敌——它们的含义取决于顺序，一旦经过多层传递就无法保证对齐。

这条规矩的收益是：类的组合顺序可以随便换，链条都不会断。代价是签名略啰嗦，以及必须约定「链条的终点」是 object——它的 __init__ 不接受任何多余参数，所以没被消费完的关键字参数会在这里暴露成 TypeError，这反而是好事，等于一个自动的拼写检查。

五、混入类与抽象基类：让多继承变得可控

既然多继承的风险集中在「实现继承 + 状态 + 断链」上，那么让它安全的思路就很直接：约束参与者。混入（Mixin）是一类专门为多继承设计的小类——它只提供行为、不提供身份，不打算被单独实例化。

混入类的五条纪律

这些不是语法规定，Python 不会强制检查，但它们几乎是经验的最大公约数：

  • 不自己实例化：LoggingMixin() 是没有意义的，它缺少主类提供的那部分。
  • 不持有状态：不定义 __init__，不设自己的属性。一旦持有状态，就要参与初始化链，风险立刻回来了。
  • 名字带 Mixin 后缀：读代码的人一眼就知道 class S(LogMixin, Service) 里谁是主体、谁是配料。
  • 只加行为，不改语义：混入应该是可加可减的，去掉它类还能正常工作，只是少了那项能力。
  • 必须 super() 转发：混入天生站在 MRO 中间，不转发就等于把后面的人全挡住。

第五条配合第二节那张表的第四、五行看：混入必须写在主类左边才能拦在主类前面，写在右边就轮不到它先执行，等于白加。

混入是调料不是主菜。判断一个类该不该做成混入，问一句：单独实例化它有意义吗？有意义的话它是个正经的类，该用组合；没意义的话它才适合当混入。

抽象基类：把「没实现完」提前到实例化时报错

抽象基类是一种不能被直接实例化、并且可以要求子类必须实现某些方法的类，标准库入口是 abc.ABC 加 @abstractmethod。它解决的是这样一个问题：基类里写了 raise NotImplementedError 的占位方法，子类忘了实现，程序照样能启动、照样能跑很久，直到某条分支第一次碰到它才炸——可能是深夜的定时任务。

from abc import ABC, abstractmethod

class Exporter(ABC):
    @abstractmethod
    def write(self, rows): ...

class CsvExporter(Exporter):      # 忘了实现 write
    pass

CsvExporter()   # TypeError: Can't instantiate abstract class CsvExporter

差别在于失败的时机和信息量：NotImplementedError 发生在第一次调用那个方法时，可能是上线三天后；抽象基类的 TypeError 发生在构造对象时，而且报错里直接列出了缺哪几个方法。对于在进程启动阶段就会创建对象的服务，这等于把故障从生产环境挪到了启动阶段。

collections.abc 把这套机制用到了极致：继承 Sequence 只需要自己实现 __getitem__ 和 __len__，就能白得 __contains__、__iter__、__reversed__、index、count 这一批派生方法；继承 MutableMapping 实现 5 个必需方法，能补齐 get、pop、setdefault、update、items 等十来个。这是接口继承最理想的形态——基类很薄，给的是能力而不是纠缠。

六、组合优先：什么时候不该用继承

「优先使用组合而非继承」这条建议流传很广，但「是一个（is-a）还是有一个（has-a）」的判据在真实代码里经常失灵——因为几乎任何东西都能被论证成「是一个」。CachedUserService 是一个 UserService 吗？听起来是。但它真正需要的只是转发调用加一层缓存，继承在这里只带来了耦合。

更可操作的判据是另一句：我是否需要把这个对象传给一个只认基类的地方。需要，说明多态替换是刚需，继承有理由；不需要，那你要的只是复用，组合能以更低的代价做到。

委托：把「继承」换成「持有」

委托是组合的落地方式——把被复用的对象存成实例属性，需要它的能力时转发过去。多写的那一行转发，换来的是耦合面从「基类的全部内部实现」缩小到「你实际调用的那两三个方法」。

继承版（紧耦合） 组合 + 委托版（松耦合） ┌──────────────────────┐ ┌──────────────────────────┐ │ ReportService │ │ ReportService │ │ (HttpClient) │ │ _client: HttpClient │ ← 存为属性 │ │ │ │ │ 继承来的公开方法： │ │ 对外暴露的方法： │ │ get post put │ │ fetch(day) │ │ delete session │ │ │ │ retry close ... │ │ 内部只用到 1 个： │ │ 共 12 个全部外泄 │ │ self._client.get(...) │ └──────────────────────┘ └──────────────────────────┘ ▲ ▲ │ 基类改 retry 的行为 │ 基类改 retry 的行为 │ → 可能波及本类 │ → 只要 get 签名不变就无感 │ 测试要造一个真的 HttpClient │ 测试传入一个假的 client 即可 │ │ 耦合面 = 基类全部实现 耦合面 = get() 一个方法

右侧还顺带解决了一个实际痛点：可测试性。继承版里 HttpClient 的行为焊死在对象内部，要测 fetch 就得想办法拦住真实网络请求；委托版只需要在构造时传一个有 get 方法的假对象进去，测试用例可以是三行。

一次具体的重构

重构前，继承的唯一理由是「想用 self.get()」——典型的实现继承：

class ReportService(HttpClient):          # 继承只为了白拿 get()
    def fetch(self, day):
        return self.get(f"/report/{day}")

重构后，依赖从继承关系变成了构造参数：

class ReportService:
    def __init__(self, client):           # 依赖显式传入
        self._client = client
    def fetch(self, day):
        return self._client.get(f"/report/{day}")

多出来的是两行样板，换回来的是三件事：ReportService 不再暴露 post/close 等 11 个与报表无关的方法；HttpClient 改任何内部实现都不会波及它；测试时传一个三行的假 client 就能跑。

什么时候该停下来换成组合

信号为什么是问题换成什么
继承层级超过 3 层改一个方法要翻 4 个文件才知道最终跑的是哪份把中间层拆成可注入的组件
「为了复用一个方法而继承」顺带继承了基类的全部实现与内部约定持有对象并委托，或干脆抽成普通函数
子类覆盖后抛 NotImplementedError说明子类不满足基类契约，is-a 关系本来就不成立拆开继承，各自实现
子类需要「删掉」基类的某个能力继承只能加不能减，只能靠覆盖成报错来假装删除组合，只暴露需要的那部分

继承是把两个类的命运绑在一起，组合只是让它们互相认识。默认选认识，只有在确实需要「可以互相替换」的时候，才升级为绑定。

这一组八张卡连起来看

「语言核心与数据模型」这一组到这里收尾。把八张卡按依赖顺序串起来，会看到一条相当清晰的主线：对象模型（PY09）说清楚了变量是名字、对象有身份，这是一切的地基；拷贝语义（PY10）在这个地基上回答「复制到底复制了什么」；协议与接口（PY11）把关注点从「它是什么类型」转向「它能做什么」；迭代器与生成器（PY12）是协议思想最成功的一次落地；推导式（PY13）把这套迭代能力变成日常写法；闭包与装饰器（PY14）展示了函数作为一等对象能被怎样包装；特殊方法（PY15）让自定义类接入所有内置语法；而继承与 MRO（本卡）回答的是这些类之间如何组织。

如果要从这一组里只带走一件事，那就是：Python 的设计重心一直在「对象能响应什么」而不是「对象属于哪个类」。协议、鸭子类型、特殊方法都在往这个方向推，继承只是组织代码的诸多手段之一，而且是耦合最强的那一个。往前回看，PY05 · 函数入门与参数传递 里的参数传递语义、PY08 · 模块、包与项目结构 里的模块边界，其实一直在讲同一件事——先把边界划清楚，再决定要不要把它们绑在一起。往后走，异常体系（PY18）和类型注解（PY22）会分别从错误契约和静态契约两个角度，继续补上「怎么把约定写下来」这个话题。

  • 继承前先问「我需要多态替换吗」，只为复用就改用组合
  • 行为搞不清顺序时，先打印 Klass.__mro__，不要靠猜
  • 协作链上的类一律 def __init__(self, **kwargs) 并转发 super().__init__(**kwargs)
  • 混入写在主类左边，带 Mixin 后缀，不持有状态
  • 一族可替换的实现用 abc.ABC + @abstractmethod，把失败提前到实例化时
  • 把依赖作为构造参数传入，测试时就能替换成假对象
  • 继承层级控制在 2 层以内，第 3 层出现时先停下来评估
  • 在协作链里硬编码 Base.__init__(self)——会跳过兄弟类或让基类跑两遍
  • 把 super() 理解成「父类」，多继承下它常常跳到兄弟类
  • 用 super(type(self), self)，子类调用时会无限递归
  • 让混入类持有自己的状态或被单独实例化
  • 在基类里写 if isinstance(self, 子类)，依赖方向反了
  • 为了共享几个常量或工具函数而建继承体系
  • 靠 raise NotImplementedError 当契约，它要等调用到才报

Q&A

为什么 super() 调用的不是我写在 class 括号里的第一个父类？
因为 super() 查的是实例的 MRO，不是当前类自己的父类列表。它先在 type(self).__mro__ 里定位「当前这个类」的位置，然后取右边第一个拥有目标属性的类。单继承时这两者恰好总是同一个，所以大家习惯把它读成「父类」。多继承时就不同了：假设 D(A, B) 且 A、B 都继承自 Base，实例是 D 时，A 里的 super() 会跳到 B——而 A 和 B 之间没有任何父子关系。这正是协作式多继承的机制，它让写 A 的人不需要知道 B 的存在。想确认具体跳到哪，打印 type(self).__mro__ 即可，答案完全由这条列表决定。
类定义时报 TypeError: Cannot create a consistent method resolution order 怎么办？
这说明你的继承声明违反了 C3 线性化的单调性约束，最常见的形式是 class D(Base, A) 而 A 本身又继承自 Base。这里有两条矛盾的要求：写在前面的 Base 要排在 A 之前，而子类必须排在父类之前又要求 A 排在 Base 之前，无解。修复方法通常只是调换书写顺序，把更派生的类写在前面，即 class D(A, Base)——而且这时 Base 往往是多余的，因为 A 已经带着它了。这个错误发生在类定义时，也就是模块被 import 的那一刻，属于最容易修的一类问题。如果继承关系复杂到难以推断，把每个父类的 __mro__ 都打出来对照看，矛盾点一般一眼可见。
多继承里基类的 __init__ 被执行了两次，问题出在哪？
几乎可以肯定是菱形结构里混用了 super() 和硬编码的父类调用。C3 线性化保证共同基类在 MRO 里只出现一次，所以只要链上每个类都用 super().__init__()，基类恰好执行一次。但如果其中一个类写成 Base.__init__(self)，这次硬调之外，另一条 super() 路径仍然会再走到 Base，于是执行了两遍。后果通常不报错但很难受：连接建两份、计数器被重置、缓存被清空。定位方式是在 Base.__init__ 里临时加一行打印，实例化一次数一下条数，然后逐个检查链上的类有没有硬编码调用。修复就是全部改成 super()，通常只要改一行。
混入类为什么一定要写在主类左边？
因为 MRO 里父类的相对顺序和你在 class 语句里书写的顺序一致，而方法查找是从左往右取第一个命中的。class S(LogMixin, Service) 的 MRO 是 S、LogMixin、Service，混入的方法排在主类前面，所以调用 s.save() 时先进 LogMixin，它打完日志再 super().save() 转给 Service，拦截生效。反过来写 class S(Service, LogMixin)，MRO 变成 S、Service、LogMixin，Service 的 save 先命中；除非 Service 自己也调 super()，否则 LogMixin 永远轮不到，等于白加了一个混入。这也是为什么混入必须转发 super()——它天生站在链条中间，不转发就把后面的人全挡住了。
抽象基类和直接 raise NotImplementedError 有什么实质区别？
区别在失败的时机和信息量。raise NotImplementedError 只是一个普通方法体，子类忘了实现时对象照样能创建、程序照样能启动，直到某条代码路径第一次调到它才抛异常——这个「第一次」可能是上线三天后的一个低频分支，也可能是凌晨的定时任务。用 abc.ABC 加 @abstractmethod 则是在实例化那一刻就抛 TypeError，并且报错信息里直接列出缺少哪几个抽象方法。对于在进程启动阶段构造对象的服务来说，这等于把一个生产事故变成了一次启动失败。额外的好处是抽象基类可以顺带提供派生方法的默认实现，collections.abc 就是靠这个让你实现两个方法白得五六个。
什么情况下多继承是合理的，不该一刀切禁止？
当参与方都是无状态、只加行为、并且规范转发 super() 的混入时，多继承是安全且好用的。标准库和主流框架大量依赖它：collections.abc 的各种基类、Web 框架里的权限校验与序列化混入、测试框架里的 fixture 混入，都是这个形态。判断标准是看有没有「状态参与」：一旦某个参与类定义了自己的 __init__ 并持有属性，它就进入了协作初始化链，签名兼容和调用顺序的风险立刻回来。所以实践中的分界线不是「能不能用多继承」，而是「多继承的参与者里最多只能有一个持有状态的主类，其余都必须是纯行为混入」。守住这条线，第四节那四类故障基本都不会发生。
组合到处写转发方法很啰嗦，有没有折中办法？
先确认啰嗦是不是真的。委托版通常只需要转发你实际用到的那两三个方法，而不是基类的全部；如果你发现要转发十几个，那往往说明这里确实需要的是接口继承而不是组合。真的需要大面积转发时，可以用 __getattr__ 做兜底转发——属性在自己身上找不到时自动转给内部对象，代价是丢掉了显式性，IDE 补全和静态检查都看不到这些方法，拼写错误也不会被发现。另一种更克制的做法是用 functools.wraps 或一小段循环批量生成转发方法，把范围限制在明确列出的方法名上。折中的原则是：宁可多写几行显式转发，也不要用动态转发把接口变成黑盒——组合的核心价值就是把耦合面收窄到看得见的那几个方法。
怎么快速判断一个方法调用最终会落到哪个类上？
两行代码解决，不需要推理。先 [c.__name__ for c in Klass.__mro__] 看完整的解析顺序，再 Klass.方法名.__qualname__ 直接看这个名字实际绑定到了哪个类的函数上——__qualname__ 会给出类似 'B.save' 的限定名，胜者是谁一目了然。如果想看整条链上有几个类定义了同名方法，可以遍历 MRO 检查每个类的 __dict__ 里有没有这个键。这套方法对排查「我明明改了 B 的代码却毫无效果」特别有效，那种情况通常就是 A 在 MRO 里排在 B 前面，B 的实现从来没被执行过。养成先查再改的习惯，多继承里的大部分玄学都能在一分钟内定性。
