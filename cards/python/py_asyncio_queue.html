队列的价值不是让程序跑得更快，而是让快的那一端愿意等一等慢的那一端。这个「等」就是反压，也是一条流水线不被自己压垮的唯一机制——没有它，你只是把下游的排队搬到了自己的内存里。

一、为什么需要队列：速率不匹配的代价

设想一个很常见的活：把 50 万条文档读出来，逐条调用 embedding 接口，再写进向量库。你手上有 async def handle(doc)，现在要把它跑 50 万次。最自然的写法是一个循环把所有任务建出来，然后 await asyncio.gather(*tasks)。这段代码能跑通，在 1000 条的样本上甚至跑得很漂亮，然后在 50 万条上把进程弄死。

原因不在 asyncio，而在你把并发度交给了数据量。50 万个 Task 对象同时活着，每个都持有自己的协程帧、局部变量和那条文档的内容；同一瞬间还有 50 万个请求打向 embedding 服务。真正需要决定的那个数字——「同时处理多少条」——在这种写法里根本没有出现过，它被默认设成了「全部」。

同样 50 万条文档，三种写法的形状 ───────────────────────────────────────────── A 全量并发 for x in items: create_task(work(x)) 内存 ┃████████████████████████████ 50 万个 Task 同时活着 下游 ┃████████████████████████████ 瞬时 50 万并发打过去 结局 ┃内存打满，或者下游先被打挂 B 分批处理 每 500 条 gather 一次，一批做完再下一批 内存 ┃██ 峰值 = 批大小 下游 ┃██ 峰值 = 批大小 代价 ┃每批都要等最慢的那一条，批与批之间有空转 C 队列流水线 生产者 put，固定 N 个消费者 get 内存 ┃█ 峰值 ≈ maxsize + N 下游 ┃█ 恒定 = N，不随总量变化 收益 ┃生产与消费各跑各的，没有空转，也没有峰值

B 和 C 的差别容易被低估。分批处理看着已经解决了内存问题，但它引入了一个新的浪费：批内木桶效应。一批 500 条里有 1 条慢了 8 秒，另外 499 条做完之后就只能空等这 8 秒，谁也不能开始下一批。批越大，浪费越明显；批越小，调度开销和首尾空转的占比越高。队列流水线没有「批」这个概念，任何一个消费者一旦空出手就立刻去拿下一条，慢的那条只占住一个消费者。

做法内存占用峰值下游并发压力首个结果可用时间主要代价
全量并发（一次性 create_task）随总量线性增长瞬时等于总量，不可控快（最快的一条立刻出）并发度由数据量决定，规模一大就崩
分批处理（chunk + gather）恒定 ≈ 批大小峰值等于批大小慢（要等整批走完）批内木桶效应，批间空转
队列流水线（put / get）恒定 ≈ maxsize + 消费者数恒定等于消费者数快且稳定（流式产出）要自己处理关闭与异常，代码量最大

所以队列干的是两件事。第一是速率解耦：生产者按自己的节奏往里放，消费者按自己的节奏往外取，两边不必互相等待，中间那点缓冲把抖动吸收掉。第二是用容量上限提供反压：队列满了，put 就停在那里，生产者被迫慢下来，这个「慢下来」会一路传导回它的上游。

不加上限的队列不是队列，是一个正在长大的列表。它把「下游处理不过来」这个事实从一个会报错的问题，变成了一条只升不降的内存曲线。

二、Queue 的核心语义：等待就是反压

asyncio.Queue 的 API 面很小，一页文档就看完了，但里面有两处语义值得反复确认，因为大多数线上问题都出在这两处。

put 和 get 都是协程

第一处是：put 和 get 都必须 await。队列满时 await put(item) 会挂起当前协程，直到有消费者取走一个；队列空时 await get() 会挂起，直到有生产者放进一个。这个「挂起」不是实现上的妥协，它就是反压本身——把压力以「你先等着」的形式还给上游，而不是以内存增长的形式吃下来。

maxsize 决定缓冲区有多大，也决定反压从哪里开始 ──────────────────────────────────────────────── 队列容量 maxsize = 4 生产者 ──put──▶ ┌───┬───┬───┬───┐ ──get──▶ 消费者 │ ● │ ● │ ● │ ● │ └───┴───┴───┴───┘ 已满 ↑ 此刻再 await queue.put(x)，协程就挂在这一行， 直到某个消费者 get 走一个，腾出位置 │ └─ 生产者被迫慢下来 = 反压（backpressure） 它会继续传导回生产者的上游： 读文件的游标停住、拉接口的循环停住、扫库的分页停住 maxsize = 0（默认）表示无上限：put 永不等待 └─ 没有反压。队列只管长，内存曲线只升不降， 进程被 OOM kill 之前不会有任何异常抛出

所以 maxsize 是一个设计参数，不是随手填的数。它回答的问题是：「允许多少工作量停在半空中？」这个数字越大，对抖动的容忍越好，但内存占用和「故障时丢多少」都跟着涨；越小则反压越灵敏，队列空转的概率也越高。第三节会给一个可以直接用的起点值。

未完成计数与 task_done / join

第二处是 task_done() 和 join() 这一对。队列内部维护一个未完成计数：每次 put 加一，每次 task_done() 减一。注意减一的时机是 task_done()，不是 get()——取出来只说明它离开了队列，不说明它被处理完了。await join() 就是「阻塞直到这个计数归零」。

这个设计把「队列空了」和「活干完了」区分开来。队列可以是空的，但 8 个消费者手上还各自握着一条正在处理的数据，此时计数是 8，join() 不会返回。这正是我们想要的语义：等的是全部处理完毕，而不是全部取完。反过来，task_done() 调多了会直接抛 ValueError，这是一个有用的保护——它会在你把 task_done() 写重了的时候立刻报错，而不是让 join() 提前返回。

成员是协程吗满 / 空时的行为用在哪
await put(item)是队列满则等待生产端默认写法，要反压就用它
put_nowait(item)否队列满则抛 QueueFull不能 await 的场合（同步回调、线程桥接）
await get()是队列空则等待消费者主循环
get_nowait()否队列空则抛 QueueEmpty只想「顺手看看有没有」，不想挂住
task_done()否调用次数超过入队数则抛 ValueError每次 get() 之后必须配一次
await join()是等未完成计数归零主协程等「活干完了」
qsize() / empty() / full()否返回瞬时快照上报积压指标；不要拿来做控制判断
shutdown(immediate=False)否后续 put / get 抛 QueueShutDownPython 3.13 起可用的主动关闭

版本说明 · Queue.shutdown() 与 QueueShutDown 异常是 Python 3.13 新增的，3.12 及更早没有这两个名字。如果你的项目要兼容 3.12，关闭只能用第四节的哨兵值或 join + cancel。另外 asyncio.Queue 的 loop 参数在 3.10 已被移除。

它不是跨线程通信工具

官方文档对 asyncio.Queue 的表述是明确的：这个类不是线程安全的。它的等待机制建立在事件循环的 future 之上，只在自己所属的那个事件循环内部成立。3.10 移除 loop 参数之后它不再在构造时绑定循环，但这只是让构造更灵活，不意味着可以跨线程使用。

跨线程的保守结论：线程与线程之间通信，用标准库的 queue.Queue；协程与协程之间通信，用 asyncio.Queue；两者之间要打通，不要直接在别的线程里调 asyncio.Queue 的方法，而是经由事件循环调度过去。最常用的两个入口是 loop.call_soon_threadsafe(...)（把一个同步调用排到循环里执行）和 asyncio.run_coroutine_threadsafe(coro, loop)（从别的线程提交一个协程，返回 concurrent.futures.Future）。反方向——协程要用一个会阻塞的同步函数——用 asyncio.to_thread(...)（Python 3.9 起）。这三条之外的写法，先当成不安全。

# 工作线程里产出的数据要送进 asyncio.Queue，必须借事件循环回去
loop = asyncio.get_running_loop()

def in_worker_thread(item):        # 注意：这里是普通线程，不是协程
    loop.call_soon_threadsafe(queue.put_nowait, item)
    # put_nowait 在队列满时抛 QueueFull —— 这条路径上没有反压，
    # 要么把 maxsize 放宽，要么在线程侧自己做限速

另外两种队列

asyncio 还提供 LifoQueue 和 PriorityQueue，它们和 Queue 的 API 完全一致，只是取出顺序不同。绝大多数流水线用 FIFO 的 Queue 就够了，另外两个是针对特定形状的问题。

类取出顺序典型用途要注意
Queue先进先出默认选择，几乎所有流水线公平，等待时间可预期
LifoQueue后进先出深度优先爬取、栈式回溯不公平：早入队的任务可能长期饿死
PriorityQueue优先级数值最小的先出任务有 SLA 分级，高优先级要插队元素通常是 (priority, data) 元组；优先级相同时会去比较 data，若 data 不可比较就抛 TypeError，习惯写法是插一个自增序号变成 (priority, seq, data)

get() 减的是队列长度，task_done() 减的是未完成计数。join() 等的是后者。把这三句话记牢，本卡后面所有的挂死问题都能自己推出来。

三、工作流水线骨架：固定消费者 + 优雅关闭

这一节是全卡的核心。下面这个骨架可以直接抄进项目：一个生产者、固定数量的消费者、一个明确的收尾。它的形状值得先看一眼，再看代码。

数据源（文件 / 接口 / 数据库游标） │ 一条一条产出，不一次性展开成列表 ▼ ┌──────────────┐ │ producer │ await queue.put(item) └──────┬───────┘ │ │ └─ 队列满时挂在这里 = 反压 ▼ ┌───────────────────────────────────┐ │ asyncio.Queue(maxsize=64) │ ← 唯一的共享状态 └──┬─────────┬─────────┬────────┬───┘ ▼ ▼ ▼ ▼ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ │ w0 │ │ w1 │ │ w2 │ …│ w7 │ 固定 8 个消费者协程 └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘ 每个都是： │ │ │ │ while True: │ │ │ │ item = await get() │ │ │ │ handle(item) └─────────┴────┬────┴────────┘ task_done() ▼ 结果汇聚（写库 / 落文件 / 计数器） 主协程的收尾顺序，三步不能换： 1. 生产者跑完（此时队列里可能还有积压） 2. await queue.join() → 未完成计数归零，活真的干完了 3. w.cancel() × 8 → 收掉还挂在 await get() 上的消费者

消费者是这个骨架里最需要写对的部分。它是一个不会自己结束的循环，靠外部取消或哨兵值退出；处理逻辑必须整段包在异常保护里；task_done() 必须放在 finally 里。

async def consumer(name, queue, sink):
    while True:
        item = await queue.get()          # 队列空就在这里等
        try:
            sink.append(await handle(item))
        except Exception:                 # 不兜住，这个协程就地死亡
            log.exception("处理失败 name=%s item=%r", name, item)
        finally:
            queue.task_done()             # 成败都要调，漏一次 join() 永挂

这里有个容易忽略的细节：await queue.get() 写在 try 外面。如果把它挪进 try，那么 get() 自己抛异常时也会走到 finally 里的 task_done()——而这一项根本没被取出来，计数就被多减了一次，最终换来一个莫名其妙的 ValueError。get() 成功之后才进入受保护区间，这个边界是刻意的。

生产者相对简单，关键是不要先把数据源展开成列表。用异步迭代器或生成器逐条产出，反压才能真正传到源头；PY12 讲的惰性产出在这里是前置条件。

async def producer(queue, source):
    async for item in source:       # 逐条产出，不要 list(source)
        await queue.put(item)       # 队列满时在此等待，反压回到 source

主协程负责组装、等待和收尾。注意消费者任务的引用要保存在一个变量里：asyncio.create_task 返回的任务只被事件循环弱引用，不持有强引用的话有被提前回收的风险。

async def run(source):
    queue = asyncio.Queue(maxsize=64)      # 缓冲上限 = 设计参数
    sink = []
    workers = [
        asyncio.create_task(consumer(f"w{i}", queue, sink))
        for i in range(8)                  # 消费者数 = 真正的并发度
    ]
    await producer(queue, source)   # 生产者结束，但队列里可能还有积压
    await queue.join()              # 等到每一项都被 task_done()
    for w in workers:               # 此时消费者都空闲地挂在 get() 上
        w.cancel()
    await asyncio.gather(*workers, return_exceptions=True)
    return sink                     # 到这里所有资源都收干净了

最后那行 gather(..., return_exceptions=True) 不是可选的装饰。cancel() 只是打个标记，协程要等下一次被调度才真正响应；不 await 一下就返回，事件循环关闭时会打一串 Task was destroyed but it is pending 的警告。return_exceptions=True 则是为了让取消产生的 CancelledError 不要反过来打断收尾流程。

部件职责写错的典型后果
生产者逐条产出并 await put先展开成列表 → 反压失效，内存峰值回到全量
队列 maxsize决定缓冲量与反压灵敏度设 0 → 无反压；设过大 → 等于无反压
消费者数量这就是真正的并发度随数据量变化 → 下游压力不可控
task_done()递减未完成计数不在 finally 里 → 异常路径漏调 → join() 永挂
queue.join()等「活干完」而不是「队列空」换成 while not queue.empty() → 提前收尾，丢掉在途任务
收尾的 gather确认取消真的完成了省掉 → 一串 pending task 警告，资源可能没释放

maxsize 怎么选

没有普适的最优值，但有一个好用的起点：消费者数量的 2 到 4 倍。这个量级保证每个消费者手上有活、队列里还有几个候补，调度不空转；同时缓冲总量仍然是个小常数，内存可控。定下来之后把 qsize() 上报成指标，看它长期贴着 0 还是贴着上限，再决定往哪边调。

maxsize实际行为什么时候合适
0（默认）无上限，put 永不等待数据源本身就很小且有限，或上游已有别的限流；否则不要用
1近似握手，生产者产一个等一个要求严格同步、不允许任何缓冲的场合
消费者数的 2–4 倍小常数缓冲，能吸收抖动默认起点，多数流水线从这里开始调
很大（如 100000）实际接近无上限基本没有正当理由；等于用一个大内存池换掉了反压

消费者的数量才是你的并发度，队列的 maxsize 只是缓冲垫。想让下游轻一点，改消费者数量；想让抖动更平滑一点，改 maxsize。这两个旋钮不要混着拧。

四、优雅关闭的两种做法

消费者是 while True，它不会自己停。所以任何队列流水线都必须显式设计一个收尾路径，否则主协程跑完了，进程却因为还有 8 个永远挂在 await get() 上的任务而不肯退出。业界稳定的做法只有两种。

两种收尾方式的时序 ────────────────────────────────────────────────────── 做法一：哨兵值（sentinel） producer │ put x1 … put xN │ put ⊙ ⊙ ⊙ ⊙（N 个，一人一个） w0 │ 干活 …… │ 取到 ⊙ → return，协程自然结束 w1 │ 干活 …… │ 取到 ⊙ → return main │ │ await gather(w0…w7) → 全部结束 易错点 │ 哨兵数 ≠ 消费者数 → 少的那几个永远挂在 get() 上 做法二：join + cancel producer │ put x1 … put xN │ 结束（队列里可能还有积压） main │ │ await queue.join() → 计数归零 main │ │ w.cancel() 逐个发出 w0/w1 │ 干活 …… │ 在 await get() 处收到取消 main │ │ await gather(..., True) → 确认收干 易错点 │ 漏调 task_done() → join() 永远不返回，卡在第二行

哨兵值的做法是给队列里塞一个特殊对象作为「到此为止」的信号。它必须是一个不可能和真实数据相等的东西，object() 实例是最省事的选择——用 None 或 -1 这类值都有和真实数据撞车的风险。

SENTINEL = object()   # 唯一对象，不可能和任何真实数据相等
async def consumer(queue):
    while True:
        item = await queue.get()
        try:
            if item is SENTINEL:
                return                  # 吃掉一个哨兵，自己退出
            await handle(item)
        finally:
            queue.task_done()           # 哨兵也算一项，也要 task_done
# 生产结束后，投 N 个哨兵，N 必须等于消费者数量
for _ in range(len(workers)):
    await queue.put(SENTINEL)
await asyncio.gather(*workers)   # 消费者自己 return，不需要 cancel

「一人一个」这条约束是哨兵法的全部风险所在。每个消费者取到哨兵就退出，所以它只会消费掉一个；投 7 个而有 8 个消费者，第 8 个就永远挂在 get() 上。更麻烦的是这个数量在代码里往往分散在两处——创建消费者的循环和投哨兵的循环，一旦有人改了其中一个就出问题。所以要么像上面那样写成 len(workers)，要么干脆选第二种做法。

两个必须刻进肌肉记忆的易错点。第一，task_done() 漏调一次，join() 就永久挂住——它等的是计数归零，不是超时。而漏调最常见的原因不是忘了写，是异常路径上没走到那一行：处理逻辑抛异常，控制流直接跳出，task_done() 被跳过。这就是为什么它必须放在 finally 里，这也是 PY19 讲的那套「获取与释放必须成对、且释放要在 finally 或 with 里」的纪律在队列上的具体形态。第二，收尾前先 join() 再 cancel()，顺序不能反。先 cancel() 会把正在处理的那几条活生生打断，这些数据既没处理完也不在队列里了，直接丢失。

维度哨兵值join + cancel
消费者退出方式自己 return，路径显式被取消，退出点在 get() 处
需要知道消费者数量吗需要，且必须精确相等不需要
消费者数量动态伸缩难支持天然支持
在途任务会被丢掉吗不会（哨兵排在数据后面）不会（join 先保证计数归零）
要不要 await 收尾要 gather(*workers)要 gather(..., return_exceptions=True)
最常见的错哨兵数少于消费者数 → 有协程永挂漏调 task_done() → join() 永不返回
适合消费者固定、希望退出路径出现在代码里默认选择，代码更短，伸缩更自由

Python 3.13 起还有第三条路：queue.shutdown()。调用后 put 直接抛 QueueShutDown，挂在 put 上的协程被唤醒并抛出同样的异常；get 仍能把队列里剩下的取完，取空之后也开始抛 QueueShutDown，消费者的 while True 就自然结束了。它把「关闭」变成了队列自己的状态，比哨兵值干净。shutdown(immediate=True) 会立刻清空队列并把未完成计数按清掉的条数减掉——这会让 join() 在活没干完的情况下返回，官方文档也提醒了这一点，所以它只适合「不要了，赶紧停」的场景。如果你的运行环境还有 3.12，暂时用不上这条路。

关闭是设计的一部分，不是收尾的杂活。一条流水线写完之后先问自己：谁来让消费者停？它们停之前手上那条数据怎么办？答不出来，这段代码就还没写完。

五、错误处理与不丢任务

这一节讲的是队列流水线最阴险的一类故障，它不报错、不崩溃，只是「变慢了」。

根源在于：消费者是一个独立的 Task。它的主循环里抛出未捕获异常，结果不是程序崩溃，而是这一个协程静默终止。队列还在、其他消费者还在、进程还活着，只是并发度悄悄从 8 掉到了 7。异常对象被存进那个 Task 里等人来取，而没有人会去取它。

更隐蔽的是日志：asyncio 确实有一个兜底机制，会对未被取出异常的任务打印 Task exception was never retrieved——但这个打印发生在 Task 对象被垃圾回收的时候。而我们恰恰按最佳实践把所有消费者任务存在 workers 列表里，强引用一直在，对象永远不被回收，于是那行日志永远不会出现。「按最佳实践持有引用」和「异常兜底靠 GC 触发」这两件事叠在一起，造出了一个完全静默的故障。

消费者静默死亡：吞吐逐级下降，全程没有任何报错 ────────────────────────────────────────────────────── t0 12 个消费者 吞吐 4200 条/分 队列 11/64 一切正常 t1 一条脏数据进来 → w3 抛 AttributeError → 协程终止 ├─ 异常去哪了？留在 Task 对象里，没人 await 它 └─ asyncio 只在 Task 被回收时才打印 "Task exception was never retrieved" 而 workers 列表还强引用着它 → 这行日志永远不出现 t2 9 个消费者 吞吐 3100 条/分 队列 64/64（满） t3 4 个消费者 吞吐 1400 条/分 积压开始堆在上游 t4 1 个消费者 吞吐 380 条/分 积压 46 万条 t5 0 个消费者 吞吐 0 条/分 主协程永远停在 await join() 从外面看：日志干净、进程活着、CPU 还降了，只是「有点慢」

生产事故复盘：一个文档入库流水线（解析 → 切片 → embedding → 写向量库），12 个消费者协程，稳定态吞吐 4200 条/分。某次上线新增了一批来源不同的 PDF，跑了约 3 小时后吞吐掉到 380 条/分，上游积压 46 万条，而错误日志一条都没有，告警只在「吞吐低于阈值」这条规则上响了一次，值班同学当成下游 embedding 服务抖动，扩了容，没有效果。

真正的原因是新来的这批 PDF 里有约 0.3% 抽不出 title 字段，值是 None，而切片函数里直接调了 doc["title"].strip()，抛 AttributeError。消费者主循环没有异常保护，撞上一条就死一个；12 个消费者在 3 小时里被逐个消耗掉，只剩 1 个还活着——380 条/分正好是单个消费者的吞吐，这个比例后来成了定位的关键线索。定位耗时 3 小时 40 分，最后是有人打了一次 py-spy dump，看到只剩一个消费者栈才明白过来。

修复分三层，缺一不可：消费者主循环包 try/except Exception，失败的条目连同 traceback 写进死信表；新增 consumer_alive 指标并配「存活数 < 配置数」告警；切片函数里的字段访问改成带默认值。修复后吞吐回到 4300 条/分，积压在 2 小时 10 分内追平，死信表里落了 1400 余条，事后单独重跑。

这个事故给出的纪律很清楚：消费者的主循环必须是不死的。它可以失败、可以记错误、可以把任务丢进死信，但它自己不能退出。

async def consumer(queue, dlq):
    while True:
        item = await queue.get()
        try:
            await handle(item)
        except Exception:          # 只兜 Exception，不碰 CancelledError
            dlq.append((item, traceback.format_exc()))
        finally:
            queue.task_done()      # 放在 finally，异常路径也要算完成

为什么写 except Exception 而不是 except BaseException：asyncio.CancelledError 从 Python 3.8 起继承自 BaseException 而不是 Exception，所以 except Exception 天然放行取消信号，第四节的 cancel() 才能正常收掉消费者。反过来，写成 except BaseException 或裸 except: 会把取消信号也吞掉，结果是 cancel() 叫不停这个协程，进程退不出去。异常粒度的设计原则在 PY24 里有系统的讨论，队列这里只需要守住一条：兜住业务异常，放行取消。

需要重试时有个坑：不要在消费者里对同一个队列 await queue.put(...) 重排队。队列满、且所有消费者都卡在这个 put 上时，没有任何人能去 get，整条流水线自锁死。重试要么用 put_nowait 并处理 QueueFull，要么走一个独立的重试队列。

        except Exception:
            if tried + 1 < MAX_RETRY:
                retry_q.put_nowait((item, tried + 1))   # 独立队列，不回灌
            else:
                dlq.append(item)                        # 到顶了，进死信
        finally:
            queue.task_done()

光有异常保护还不够，因为它只保证「消费者不会因为业务异常死掉」，不保证「消费者一定活着」——协程还是可能被取消、被某个 BaseException 带走，或者卡在一个没有超时的下游调用上。所以要有一个能看见的指标。

async def monitor(queue, workers, interval=10):
    while True:
        alive = sum(not w.done() for w in workers)
        log.info("queue=%d alive=%d/%d", queue.qsize(), alive, len(workers))
        await asyncio.sleep(interval)   # alive 掉了就告警，别等吞吐指标

这两个数放在一起看才有意义。alive 下降说明消费者在死；qsize 长期贴着上限说明消费能力不足；qsize 长期贴着 0 说明瓶颈在生产端，加消费者没用。只看吞吐这一个数，就只能等它掉下来再猜原因——上面那个事故正是这么发生的。

失败类型该怎么处理不这么做的后果
瞬时失败（超时、429、连接重置）有限次重试 + 指数退避，重试次数随任务走要么一次就丢，要么无限重试把下游打死
脏数据（字段缺失、编码异常）不重试，直接进死信记录，带上 traceback重试永远不会成功，白占吞吐和日志
下游整体不可用熔断：暂停 get，让队列积压并反压回生产端每条都重试，日志刷爆，下游恢复瞬间雪崩
消费者协程自身异常退出主循环兜 Exception；存活数上报指标并告警吞吐静默下降，最终 join() 永挂
CancelledError不要吞，让它往上抛关闭流程挂住，进程无法正常退出
  • task_done() 一律写在 finally 里，和 get() 严格一对一
  • await queue.get() 放在 try 外面，成功取出后才进受保护区间
  • 消费者主循环兜 except Exception，失败进死信，协程不退出
  • 同时上报 qsize 和消费者存活数，两个都配告警
  • 收尾顺序固定为「生产完 → join() → cancel() → gather」
  • maxsize 从消费者数的 2–4 倍起步，再按指标调
  • 用裸 except: 或 except BaseException，把取消信号一起吞掉
  • 在消费者里 await 同一个队列的 put 做重试（会自锁死）
  • 用 while not queue.empty() 代替 await queue.join()
  • 先 cancel() 再 join()，把在途的那几条数据打断丢掉
  • maxsize=0 上生产，用内存无声地吸收下游的慢
  • 不保存 create_task 的返回值，让任务被弱引用着

一个消费者死掉不会有人喊。它表现为「系统有点慢」，而「有点慢」几乎总会被先归因到下游。所以消费者存活数必须是一个指标，不能靠日志、更不能靠吞吐反推。

六、判据与扩展：什么时候该换外部消息队列

asyncio.Queue 是一个内存里的对象，它的生命周期和进程完全绑定。这句话就是所有判据的来源：进程一死，队列里的东西全没了，没有持久化、没有消费确认、没有重投、也没有第二个进程能看见它。

进程内队列 ───────────── 分界线 ───────────── 外部消息队列 asyncio.Queue Redis Stream / RabbitMQ / Kafka 它够用的信号 必须换掉的信号 · 生产和消费在同一个进程内 · 要跨进程、跨机器消费 · 任务丢了可以重跑（源头还在） · 重启不能丢，必须持久化 · 单机吞吐够，不需要水平扩 · 要按积压量自动扩缩消费者 · 只需要速率解耦和反压 · 要消费确认、重投、延迟队列 · 队列里放的是内存对象 · 任务要序列化、可能跨语言 · 挂了重跑一遍成本可接受 · 任务有副作用，不能重复执行 中间形态：进程内队列 + 外部 checkpoint ──────────────────────────────────── 队列只负责速率解耦，进度单独落库； 重启后从 checkpoint 续跑，不引入消息中间件的运维成本。 一次性的批量回填任务，绝大多数停在这一档就够了。

这里最容易犯的错是两个方向的。一个方向是明明只在一个进程里做一次性的批量处理，却先搭一套 Kafka，把两周的时间花在运维上；另一个方向是把一个需要重启不丢、需要多机消费的长期任务硬塞进 asyncio.Queue，然后用一层层的重试和补偿脚本去弥补它天生没有的能力。

需求进程内 asyncio.Queue外部消息队列
跨进程 / 跨机器消费做不到原生支持
进程重启后任务还在全部丢失持久化后不丢
消费确认与失败重投要自己实现内建 ack / nack / 重投
水平扩消费者只能加协程，受单进程与单机限制加实例即可
端到端延迟微秒级，没有网络跳和序列化毫秒级起，多一次序列化和网络往返
可观测性自己埋 qsize 和存活数指标自带积压、消费延迟、消费者组看板
运维成本零部署、监控、容量规划、故障演练
适合的任务形态单进程流水线、批量回填、抓取-处理-落库长期在线的异步作业、多服务解耦、事件驱动

顺手厘清几个相邻工具

队列常被拿来和另外两个东西比较，值得说清楚边界。asyncio.Semaphore 能限制同时进行的操作数，看起来也能控并发——但它控的只是并发，任务对象还是要先全部建出来，内存仍然随数据量线性增长，也没有任何缓冲和反压。asyncio.TaskGroup（Python 3.11 起）解决的是「一组任务的生命周期和异常传播」，它让子任务的异常不再静默丢失，这恰好补上了第五节那个坑；但它不提供速率解耦，任务数还是等于数据量。

三者的关系不是替代，而是分工：队列决定什么时候放多少进来，消费者数量决定并发度，TaskGroup 决定这组协程的异常和取消怎么传播。一条成熟的流水线里三个都会出现。

选型只看一个问题：任务丢了会怎样。答案是「重跑一遍就行」，进程内队列足够；答案是「不能丢，也不能重复执行」，那你需要的其实不是队列，是带持久化和幂等语义的消息系统——这一步的复杂度是真实的，别在不需要时提前支付。

Q&A

maxsize 到底该设多少？有没有一个能直接用的数？
起点用「消费者数量的 2 到 4 倍」，比如 8 个消费者就设 16 到 32。这个量级的含义是：每个消费者手上有一条活，队列里还躺着一两条候补，消费者几乎不会空等调度；同时缓冲总量是个小常数，内存可控。定下来之后把 qsize() 上报成时序指标再观察：长期贴着上限说明消费能力不够，该加消费者或优化 handle；长期贴着 0 说明瓶颈在生产端，加消费者一点用都没有。唯一要避开的是 maxsize=0——它不是「性能最好」，是「放弃反压」，队列会一直长到进程被 OOM kill，而且整个过程不抛任何异常。
task_done() 到底在计什么？漏调一次会怎样？
队列内部有一个未完成计数：每次 put 加一，每次 task_done() 减一。get() 不减——取出来只说明它离开了队列，不说明处理完了。await join() 就是等这个计数归零。所以漏调一次的后果是计数永远停在 1 以上，join() 永久挂住，没有超时、没有报错，你只会看到程序停在那一行不动。漏调最常见的原因不是忘了写，而是异常路径跳过了它：handle(item) 抛异常，控制流直接跳出，后面那行 task_done() 根本没执行。所以它必须放在 finally 里。反过来调多了会抛 ValueError，这是好事——它让「配错了」当场暴露，而不是变成一次提前返回的 join()。
queue.join() 和 asyncio.gather(*workers) 有什么区别？两个都要吗？
等的是完全不同的东西，而且通常两个都要。queue.join() 等的是「所有入队的数据都被 task_done() 了」，也就是活干完了；此时消费者协程还活着，正空闲地挂在 await get() 上。gather(*workers) 等的是「这些消费者协程都结束了」。用 join + cancel 方案时，标准顺序是先 await queue.join() 确认活干完，再逐个 cancel()，最后 await asyncio.gather(*workers, return_exceptions=True) 确认取消真的生效——cancel() 只是打标记，不 await 一下就返回，事件循环关闭时会打一串 Task was destroyed but it is pending 警告。用哨兵值方案时消费者自己 return，就只需要 gather。
消费者里能不能往同一个队列再 put 东西（比如重试或递归展开）？
能，但 await queue.put(...) 这种写法有明确的死锁风险：队列满的时候 put 会等待，而如果所有消费者都正卡在这个 put 上，就没有任何人去 get 腾位置，整条流水线自锁，且不会抛任何异常。爬虫里「从页面里发现新链接再入队」是这个模式的典型场景。两条安全写法：一是用 put_nowait 并显式处理 QueueFull（丢弃、落盘、或者交给别的路径），二是让重试和新发现的任务走一个独立的队列，避免回灌。另外要留意，往同一个队列 put 会让未完成计数重新上升，join() 的结束时点也随之推后——这通常正是你想要的，但如果重试没有上限，join() 就可能永远等不到归零。
asyncio.Queue 能跨线程用吗？我想让线程池把结果送进来。
不能直接用。官方文档明确写着这个类不是线程安全的，它的等待机制建立在事件循环的 future 上，只在所属的那个事件循环内成立。3.10 移除 loop 参数让构造更灵活，但并没有改变这一点。保守可靠的做法是把跨线程这一跳交给事件循环：在别的线程里调 loop.call_soon_threadsafe(queue.put_nowait, item)，或者 asyncio.run_coroutine_threadsafe(queue.put(item), loop)（后者返回 concurrent.futures.Future，还能在线程侧等结果，也保留了反压）。反方向——协程需要执行一个会阻塞的同步函数——用 asyncio.to_thread(...)（Python 3.9 起）。纯线程之间的通信仍然用标准库 queue.Queue。这三条之外的写法都先当成不安全。
为什么消费者死掉了，日志里一条报错都没有？
因为消费者是独立的 Task，它抛出的异常不会传播到主协程，而是被存进 Task 对象等人来 await 它取走。asyncio 有一层兜底：如果一个带异常的 Task 最终没人取，会打印 Task exception was never retrieved。但这个打印是在 Task 对象被垃圾回收时触发的，而我们按最佳实践把所有消费者任务存在 workers 列表里，强引用一直在，对象永远不被回收，那行日志就永远不会出现。两件各自正确的事叠起来造出了一个完全静默的故障。解法是不要依赖这层兜底：消费者主循环自己兜住 except Exception 并打日志，同时把存活消费者数上报成指标；如果运行在 Python 3.11 及以上，用 TaskGroup 管理这些消费者也能让异常不再静默。
用 Semaphore 或 TaskGroup 限制并发，是不是就不需要队列了？
解决的层次不一样。Semaphore 限制的是「同时进行中的操作数」，但你仍然要先把所有任务对象创建出来——50 万条数据就是 50 万个 Task 挂在那里排队拿信号量，内存照样随数据量线性增长，也没有任何缓冲可以吸收抖动。TaskGroup（Python 3.11 起）解决的是一组任务的生命周期和异常传播，让子任务的异常不再静默丢失，但它同样不限制任务总数。队列的独特之处是它让「同时存在的任务数」和「数据总量」彻底脱钩：内存峰值是 maxsize 加消费者数这个常数，跟你要处理 1 万条还是 1 亿条无关。判断很简单：数据量有上限且不大，Semaphore 就够；数据量大、或者根本不知道有多少（流式、游标、无界输入），必须用队列。
Python 3.13 的 Queue.shutdown() 值得用吗？
如果你的运行环境能保证 3.13 及以上，值得——它比哨兵值干净得多。调用 shutdown() 之后队列进入关闭态：后续 put 抛 QueueShutDown，挂在 put 上的协程被唤醒并抛同样的异常；get 仍然能把队列里剩下的数据取完，取空之后才开始抛 QueueShutDown，消费者的 while True 自然结束。这就把「关闭」从一个要靠约定传递的信号（哨兵数必须等于消费者数）变成了队列自身的状态，少了一类配错的可能。但有两点要注意：shutdown(immediate=True) 会立刻清空队列并把未完成计数按清掉的条数减掉，于是 join() 会在活没干完的情况下返回，官方文档专门提醒了这一点，它只适合「不要了，赶紧停」；另外 3.12 及更早完全没有这个名字，要兼容就还得保留 join + cancel 这条路。
