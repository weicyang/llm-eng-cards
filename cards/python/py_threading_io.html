PY26 · 多线程与 I/O 密集任务

等待时间才是优化对象 / 线程池与 as_completed / 竞态与加锁纪律 / Queue 与停止信号 / 并发度怎么反推出来

多线程在 Python 里几乎永远不是用来「算得更快」的，而是用来「等得更省」。一次远程调用的九成时间是这条线程躺在 socket 上什么都不做，多开几条线程只是让这些空等重叠起来——搞清楚这一点，你就能预判它什么时候有效、什么时候一点用都没有。

一、线程省掉的是等待，不是计算

「加线程能不能变快」这个问题没有统一答案，但有一个统一的判断方法：先看时间花在哪。把一次典型的外部调用拆开，你会发现它的耗时构成极度不均衡，真正占用 CPU 的部分小得可以忽略。

一次内网 HTTP 调用的 200ms，都花在什么上 ────────────────────────────────────────────────────────── 建连 + TLS 握手 ████ ~55ms 纯等待 发出请求 ▏ ~1ms 本地 CPU 服务端处理 + 网络回程 ████████████ ~130ms 纯等待 读取响应体 █ ~8ms 以等待为主 本地 JSON 解析 ▏ ~6ms 真的在算 ───────── CPU 真正在干活 ≈ 7ms / 200ms ≈ 3.5% 其余 96.5%，这条线程只是挂在内核的等待队列上，一点 CPU 都不占 串行跑 4 个请求 4 条线程并发跑同样 4 个 ├─req1─┤ ├─req1─┤ ├─req2─┤ ├─req2──┤ ├─req3─┤ ├─req3─┤ ├─req4─┤ ├─req4──┤ └───────── 800ms ──────────┘ └─ 约 215ms ─┘ 总耗时 = 四次逐个累加 总耗时 ≈ 最慢的那一次

这张图解释了两件事。第一，I/O 密集任务的墙钟时间（wall clock，从按下回车到拿到结果的真实时间）主要由等待构成，而等待是可以重叠的——一条线程在等内核返回时，解释器会把执行权交给别的线程。第二，重叠之后总耗时不会变成零，它收敛到「最慢的那一个」加上一点调度开销，所以并发的收益有天花板。

并发墙钟 ≈ ⌈N / C⌉ × 单次耗时　　（N 个任务，并发度 C）

这个近似式只在下游扛得住的前提下成立，第五节会讲它是怎么失效的。先用它估一下不同规模下的差距，因为量级感比公式本身更有用。

什么情况下线程一点忙都帮不上

反过来说，如果一个任务的时间是花在计算上——图像缩放、大矩阵运算、纯 Python 的循环统计——多开线程不但不会变快，还可能变慢。原因是 CPython 默认构建里有全局解释器锁（GIL，Global Interpreter Lock），同一时刻只允许一条线程执行 Python 字节码。多条 CPU 密集的线程会互相抢这把锁，把本来连续的计算切成碎片，额外付出切换成本。

判断要不要上线程，只需要问一句：这段代码的时间是花在「等别人」还是「自己算」。等别人就上线程，自己算就换进程或者换库。

需要补一句的是，「自己算」这个判断要落到实现层。NumPy 的矩阵运算、大多数压缩与加解密库、数据库驱动的网络部分，都在 C 层执行并且在执行期间主动释放了 GIL，从 Python 的视角看它们的行为更接近 I/O 而不是计算。所以「用了 NumPy 的代码是 CPU 密集，所以线程没用」这个推论是错的，得实测。

二、别裸起线程：线程池才是生产写法

threading.Thread 是最直白的入口，值得先看懂它，因为线程池的行为是建立在这套语义之上的。它的模型很简单：给一个可调用对象，start() 让它在新线程里跑起来，join() 阻塞等它结束。

import threading

def fetch(url):
    ...

t = threading.Thread(target=fetch, args=("/a",), name="w-1")
t.start()                 # 不 start 就只是个普通对象，什么都不会发生
t.join(timeout=5)         # 不 join，主线程不会等它
print(t.is_alive())       # join 超时不抛异常，要靠这个判断是否真结束

这里有两个容易踩的点。join(timeout=5) 超时后不抛异常也不终止线程，它只是放弃等待返回，线程还在后台跑；想知道结果必须再查 is_alive()。另一个是 target 的返回值没有任何地方能接住——裸线程没有返回值通道，你得自己用队列或共享变量把结果传出来，而这恰恰是最容易写出 bug 的地方。

守护线程：主线程一退，它就地消失

守护线程（daemon thread）指的是 daemon=True 的线程。它和普通线程唯一的区别在进程退出时：解释器只等所有非守护线程结束，然后就开始收尾，守护线程会被直接掐断——不抛异常、不执行 finally、不运行上下文管理器的 __exit__（见 PY19 · 上下文管理器）。

后果是具体的：守护线程里如果正在写文件，会留下半截内容；正在提交事务，连接直接断开；缓冲区里攒着的日志，一条都不会落盘。所以判据很清楚——守护线程只能用来跑「随时可以丢弃」的活，比如心跳上报、指标采集；凡是有收尾动作的任务都不能设成守护线程，而要用停止信号让它自己退出（第四节）。

线程池解决的四件事

生产代码里默认用 concurrent.futures.ThreadPoolExecutor，不是因为它写起来短，而是因为裸线程有四个坑它都替你填了：线程复用（不用为每个任务付创建开销）、并发上限（max_workers 是一道硬闸门）、结果回传（Future）、以及异常捕获（不会像裸线程那样悄悄消失）。

ThreadPoolExecutor 的内部结构 ───────────────────────────────────────────────────────────── 你的代码 内部任务队列 工作线程（会复用） ex.submit(f, x1) ─┐ ┌──────────────┐ ┌──────────┐ ex.submit(f, x2) ─┼─▶│ x3 x4 x5 ... │──┬───▶│ worker-0 │─┐ ex.submit(f, x3) ─┘ │ 无界排队 │ ├───▶│ worker-1 │─┤ │ └──────────────┘ └───▶│ worker-2 │─┤ │ └──────────┘ │ ▼ 最多 max_workers 条 │ 3 个 Future ◀──── 结果和异常都回填进 Future ◀───────────┘ 闸门只拦「同时在跑几个」，不拦「排了多少个」： submit 一百万次也不会阻塞，它们全在内存里的队列排着。 要控制排队规模，只能在提交侧自己分批。

图里那一行注释值得单独记住：submit 永远不阻塞。很多人以为设了 max_workers=8 就万事大吉，然后在一个循环里 submit 了几十万个任务，内存被参数对象撑爆。闸门管的是执行并发度，不是提交速率。

示例场景：一个导出作业用 max_workers=8 的线程池处理 240 万行记录，写法是先把全表查出来、在一个 for 里逐行 submit。线程数确实只有 8，但那 240 万个待执行任务连同各自的行数据全都堆在线程池的内部队列里，进程 RSS 在 4 分钟内从 300MB 涨到 6.2GB 被 OOM 杀掉。改成「每次只提交 2000 个，等这批的 Future 全部取完结果再提交下一批」之后，峰值稳定在 420MB，总耗时反而因为不再换页少了两成。

submit + as_completed 与 map 的差别

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=16) as ex:
    futs = {ex.submit(fetch, u): u for u in urls}   # Future 映射回输入
    for f in as_completed(futs):                    # 谁先完成谁先出来
        url = futs[f]
        try:
            data = f.result()      # 任务里的异常，在这一行才抛出来
        except Exception:
            log.exception("失败: %s", url)          # 单个失败不影响其余

as_completed 是一个生成器，按完成顺序吐出 Future。因为顺序被打乱了，你需要一个 dict 把 Future 映射回原始输入，否则拿到结果也不知道它属于谁。这个写法的价值在于「边出边处理」：一万个请求里先回来的那些可以立刻写库，不用等最慢的那个。

with ThreadPoolExecutor(max_workers=16) as ex:
    # map 按 urls 的顺序返回结果，与谁先完成无关
    for url, data in zip(urls, ex.map(fetch, urls)):
        handle(url, data)

map 短得多，代价是行为更粗粒度：结果严格按输入顺序返回，所以如果第一个任务最慢，后面全部完成了你也一个都拿不到——它们只能在内存里等着。异常同样是延迟的：任务内部抛出的异常不会在 map() 调用时出现，而是在迭代到那个位置、内部取 result() 时才抛出来，并且会中断整个 for 循环。

维度submit + as_completedmap
结果顺序完成顺序，先好先出严格按输入顺序
拿到第一个结果最快的那个一回来就能处理必须等第一个输入完成
异常时机f.result() 时抛，可逐个接住迭代到那一项时抛，默认中断整个循环
关联原始输入要自己用 dict 映射回去天然一一对应

适合结果独立、要边出边处理、要精细处理单个失败一一对应的转换、顺序重要、失败就整批放弃

选择判据可以压缩成一句：失败是否允许单个处理。能容忍「一万条里坏了三条，记下来继续」就用 as_completed；要求「一条坏了整批重来」就用 map，它的中断语义正好是你要的。异常本身该怎么分类和转译，PY24 · 异常体系设计那一卡讲得更细。

把线程池当成「一个有闸门的队列」，而不是「一堆线程」。你要关心的永远是闸门开多大（max_workers）和队列排多长（提交侧分批），线程本身是实现细节。

还有一个容易漏的细节：with 块退出时会调用 shutdown(wait=True)，它会等所有已提交的任务跑完，包括还在队列里排队、一行都没开始执行的。想在出错时尽快收场，需要 shutdown(wait=False, cancel_futures=True)（Python 3.9 起），它会把尚未开始的任务从队列里丢掉——但已经在跑的那些依然无法中断，原因见第五节。

三、竞态、锁，以及怎么不写出死锁

只要两条线程会碰同一个可变对象，就存在竞态条件（race condition）：结果取决于线程调度的先后，而调度是你控制不了的。最小的例子就是一行 counter += 1——它看起来是一步，实际上是三步。

counter += 1 在字节码层是「读 - 改 - 写」三条指令 ────────────────────────────────────────────────────────── （指令名取自 3.11 及以后；3.10 及更早那条「改」叫 INPLACE_ADD） LOAD_GLOBAL counter ← 读：把当前值取到栈上 BINARY_OP (+=) 1 ← 改：算出新值 STORE_GLOBAL counter ← 写：放回去 解释器可以在任意两条指令之间切走（默认约每 5ms 检查一次， 见 sys.getswitchinterval()），于是： 时刻 线程 A 线程 B counter 实际值 t1 读到 41 41 t2 读到 41 41 t3 算出 42 41 t4 算出 42 41 t5 写回 42 42 t6 写回 42 42 ← 丢了一次 两条线程各加 100 万次，期望 200 万，实测常常是 100 多万。 加得越频繁越容易丢，而低频调用时可能几个月都不出错一次。

最后那句是这类 bug 最难缠的地方：它的出现概率和调度时机相关，压测时稳定复现，上线后一周崩一次，本地永远重现不了。所以对待共享可变状态的态度不能是「测一测看会不会出问题」，而必须是「从结构上让它不可能出问题」。

顺带澄清一个常见误解：GIL 不能替你保证这三步的原子性。GIL 保证的是同一时刻只有一条线程在执行字节码，而切换发生在指令边界上——你的三条指令中间恰恰全是合法的切换点。（CPython 3.13 起的自由线程构建连这层保护都没有，竞态窗口更宽。）

Lock 与 RLock

临界区是指「同一时刻只允许一条线程进入」的那段代码。用 Lock 把它围起来，写法只有一种值得推荐：

lock = threading.Lock()

def incr():
    global counter
    with lock:            # 等价于 acquire + try/finally + release
        counter += 1      # 临界区里只放「改共享状态」的那几行

坚持用 with 而不是手写 acquire() / release()，理由是临界区里一旦抛出异常，手写版本会跳过 release()，这把锁就永远不会被释放，之后所有想进来的线程全部卡死。这是一个「一次疏忽换来整个服务挂起」的典型场景。

只有一种情况需要手写：你不想无限期地等这把锁。acquire(timeout=2) 返回布尔值而不是阻塞到死，拿不到就走降级分支——这在「缓存刷新拿不到锁就用旧值」之类的场景里很有用。

if lock.acquire(timeout=2):
    try:
        refresh()
    finally:
        lock.release()   # 手写形式必须自己保证 finally
else:
    use_stale_cache()    # 拿不到就降级，而不是把调用方拖住

RLock（可重入锁）的区别只有一条但很关键：同一条线程可以重复 acquire，内部用计数器记录层数，释放同样次数后才真正放开。它存在的理由是加了锁的方法内部又调用了另一个加锁的方法——用普通 Lock 时这会立刻自己把自己锁死，而且死得毫无提示。

原语同线程重复 acquire谁可以 release什么时候用
Lock立刻自锁死任何线程都能释放默认选它：一小段明确的临界区
RLock可以，计数 +1只有持有者加锁方法之间会互相调用时
Semaphore(n)可以，配额减 1任何线程限制同时访问某个下游的数量
Condition取决于底层锁持有者等待某个状态成立，配合 notify 唤醒
Event不适用不适用广播型的一次性 / 可重置信号

表里第一行第二列那个「任何线程都能释放」经常被忽略：Lock 没有所有者概念，B 线程可以释放 A 线程持有的锁，解释器不会报错。这让「锁被误释放」成为一类很难查的 bug，也是 RLock 在需要归属语义时更安全的原因之一。

需要 RLock 往往是个信号：说明你的加锁边界和函数边界重叠了。更干净的做法通常是把「加锁的公开方法」和「不加锁的内部实现」拆开，让锁只在最外层加一次。

死锁：成因只有一个，纪律有三条

死锁的成因可以概括成一句话：两条线程以相反的顺序去拿同两把锁。一旦形成，双方都在等对方手里的那把，谁也不会退让，进程停在那里不报错、不超时、CPU 占用为零——最糟糕的故障形态，因为它看起来像「卡住了」而不是「出错了」。

死锁的最小形态 ───────────────────────────────────────────────────────── 线程 A 线程 B acquire(lock_account) ✔ acquire(lock_ledger) ✔ ... ... acquire(lock_ledger) ✖ 等 ──▶ 持有中，不放 持有中，不放 ◀── 等 ✖ acquire(lock_account) 两边都在等对方，进程永远停在这里。 现象：CPU 0%、没有报错、请求全部超时——最难定位的一种。 三条纪律，任何一条守住都能破环 1. 固定加锁顺序：给所有锁定一个全局次序，永远按次序加 2. 缩小临界区：锁里只放改状态的那几行，别放整个函数体 3. 持锁期间绝不做 I/O：一次 30 秒的网络超时 就是把所有等这把锁的线程一起卡 30 秒

第三条最值得展开，因为它是性能问题和死锁的共同来源。在锁里发起一次 HTTP 请求或数据库查询，等于把这个外部依赖的延迟乘以并发度加到你的系统上：正常时下游 50ms，你只是慢一点；下游抖到 30 秒，你所有线程排在这把锁后面，整个服务表现为完全无响应。正确做法是先在锁外把数据准备好，进锁只做赋值。

示例场景：一个内存缓存的刷新逻辑写成了「持锁 → 调上游拉全量配置 → 写进 dict → 放锁」。平时上游 80ms，看不出任何问题。某次上游发布导致响应退化到 9 秒，该服务的 40 条工作线程在 12 秒内全部堆在这把锁上，健康检查超时被摘除，实际上进程本身是活的、CPU 接近 0%。改成「锁外拉数据，锁内只做一次字典替换」后，同样的上游抖动只表现为缓存刷新慢一拍。改动 4 行。

四、线程间怎么传东西：少共享，多交接

上一节讲了怎么把共享状态保护好，这一节讲一个更根本的思路：尽量不共享。锁的数量和共享可变状态的数量成正比，而每一把锁都是一个潜在的死锁点和性能瓶颈。把「共享一块内存」换成「传递一个消息」，大部分锁就自然消失了。

queue.Queue：线程安全的交接点

queue.Queue 内部已经用锁和条件变量实现好了，你不需要再加任何锁。它比「共享一个 list 再自己加锁」更不容易出错的原因在于：list 的读、判空、弹出是三次独立操作，你必须把它们一起锁起来才正确，而 Queue.get() 本身就是原子的，还顺带提供了阻塞等待和超时。

生产者 - 消费者：唯一的共享点是那个队列 ───────────────────────────────────────────────────────── 生产者线程 有界队列 消费者线程池 ┌───────────┐ ┌──────────────┐ ┌───────────┐ │ 扫描文件 │─put─▶│ │─get─▶│ worker-0 │ │ 拉取分页 │─put─▶│ maxsize=100 │─get─▶│ worker-1 │ └───────────┘ │ │─get─▶│ worker-2 │ └──────────────┘ └───────────┘ 队列满时 put 会阻塞，生产者自动被拖慢到消费者的速度， 这就是免费拿到的背压——不用自己写限速逻辑。 停止有两种语义，别混用： stop_event.set() 立刻别干了，各线程在下一个检查点退出 往队列放 N 个 None 把队列里排着的干完再退，适合批任务
q = queue.Queue(maxsize=100)   # 有界：满了 put 就阻塞，天然背压

def worker():
    while True:
        item = q.get()
        try:
            if item is None: break     # 哨兵值：一个 None 停一条线程
            handle(item)
        finally:
            q.task_done()              # 漏掉它，q.join() 永远不返回

maxsize 不是可选优化，而是必须设的参数。无界队列意味着生产者可以无限快地往里塞，当消费速度跟不上时，积压全部堆在内存里——这是「批处理任务跑着跑着内存被打满」的头号原因。设了上限之后，put 会在队列满时阻塞，生产者自动被拖慢到消费者的速度，这就是背压（backpressure）。

task_done() 和 q.join() 是一对：前者每消费一项调一次，后者阻塞到「放进去的都被标记完成」。忘记调用 task_done() 的后果不是报错，而是 join() 永远挂着，表现为程序跑完了却不退出。Python 3.13 起 Queue 增加了 shutdown() 方法，可以让所有阻塞中的 get / put 抛 queue.ShutDown，不再需要哨兵值这套约定。

Event：一个能被所有线程看见的开关

stop = threading.Event()

def poller():
    while not stop.is_set():
        pull_once()
        stop.wait(5)     # 比 time.sleep(5) 好：信号一到立刻醒，不用等满 5 秒

stop.set()               # 主线程发信号，各线程在下一个检查点自己退出

stop.wait(5) 替代 time.sleep(5) 这个细节，实际效果差别很大。用 sleep 时，发出停止信号后最坏要等一个完整周期线程才会醒来检查；轮询间隔如果是 60 秒，你的服务关闭就要拖 60 秒，超过容器编排的宽限期就会被强杀，收尾逻辑照样丢失。

threading.local：让「每线程一份」代替共享

_local = threading.local()

def session():
    s = getattr(_local, "s", None)
    if s is None:
        s = _local.s = requests.Session()   # 每条线程独享一个连接会话
    return s

这是「不共享」思路最直接的体现：与其给一个全局 Session 加锁，不如让每条线程拿自己的那份。数据库连接、HTTP 会话、日志上下文都适合这么处理。但有一个必须知道的副作用——线程池会复用线程，所以存进 threading.local 的东西会一直留到下一个任务。当作连接缓存正好；当作「本次任务的上下文」就会串味，上一个请求的 trace id 被下一个请求带上，排查时看到的调用链完全是错的。

手段传递什么要不要自己加锁主要风险
queue.Queue任务与结果对象不用，内部已保证不设 maxsize 会把内存吃光
threading.Event一个布尔广播不用只有两态，多状态别硬套
threading.local每线程私有对象不用，本来就不共享线程池复用线程，值会留到下一个任务
Future.result()单个任务的返回值不用不取结果，异常就被静默吞掉
共享 list / dict + Lock任意结构要，且必须全覆盖漏锁 = 偶发丢数据；持锁做 I/O = 全局卡住

共享可变状态越少，需要的锁就越少，能写出的死锁也越少。看到「加个锁就好了」这种念头时，先想想能不能改成「把东西放进队列交出去」。

五、线程的代价、边界与静默失败

线程不是免费的。每条线程都要分配自己的调用栈，栈大小按平台和构建配置在 512KB 到 8MB 之间（Linux 上通常跟随 ulimit -s，可用 threading.stack_size() 调整）。这是虚拟地址空间，实际驻留内存按页分配、远小于这个数，但线程开到几千条时，光是栈的地址空间就足以让 32 位进程直接失败，64 位进程也会明显感到调度压力。

并发度不是越大越好，上限由四个来源共同决定

约束来源上限怎么反推超了之后的症状
下游连接池客户端配置的 pool_maxsize（requests 默认每主机 10）日志刷 connection pool is full，连接被丢弃重建，每次请求多付一次握手
上游限流配额允许 QPS × 单次耗时 = 可用并发（Little 定律）429 比例上升，成功率下跌，重试又加重限流
本机内存线程数 × 栈大小 + 每任务的中间对象RSS 持续上涨，极端情况 can't start new thread
响应处理的 CPU单次解析耗时 × 目标 QPS 不能超过一核GIL 争抢加剧，P95 不降反升
目标时延并发越高排队越深，P95 = 排队 + 处理吞吐还在涨，但单请求的体感越来越慢

生产事故复盘：一个每日跑的数据同步作业，要从上游 HTTP 接口拉 12 000 条记录，线程池 max_workers=8，单次调用 P50 约 420ms，实测吞吐约 19 QPS，全量耗时 10.5 分钟，成功率 99.9%，P95 0.42 秒。有人想「再快一点」，把 max_workers 直接从 8 调到 200 上线。

结果是三件事同时发生：一是那个共享的 requests.Session 连接池上限是默认的 10，200 条线程把它打穿，日志里每秒上百条 connection pool is full，连接被丢弃后重建，每个请求额外付一次 TLS 握手；二是请求速率冲到接近 470 QPS，远超上游 50 QPS 的配额，429 占比涨到 8.8%；三是重试逻辑把这些 429 又原样打回去，进一步加重限流。最终成功率从 99.9% 掉到 91.2%，P95 从 0.42 秒涨到 6.8 秒，全量耗时不降反升到 23 分钟。

处置是把并发回调到 16（按 50 QPS × 0.42 秒 ≈ 21 的可用并发再打八折），同时把连接池 pool_maxsize 设为 16 与之对齐、给重试加上指数退避。恢复后吞吐约 36 QPS，成功率 99.93%，P95 0.51 秒，全量 5.5 分钟——比原来的 8 并发快了近一倍，比 200 并发快了四倍。教训不是「并发不能调大」，而是并发度是从下游的连接池和限流反推出来的，不是从「我希望多快」推出来的。

Python 没有办法安全地终止一条线程

这一条经常让从别的语言过来的人意外：标准库里没有 thread.kill()，而且这是有意为之。强行终止一条线程意味着它可能停在任意一条指令上——锁还持有着、文件只写了一半、事务没提交也没回滚。这种状态下的进程已经不可信了，所以 Python 的选择是干脆不提供这个能力。

唯一正确的做法是协作式取消：被取消方自己在合适的位置检查停止标志并退出。这也意味着取消的响应速度取决于检查点的密度，一个卡在没有超时的 recv() 上的线程，你设多少次标志它都不会醒——所以超时和取消其实是同一件事的两面。

网上流传的 ctypes.pythonapi.PyThreadState_SetAsyncExc 注入异常的技巧不要用于生产：它只在线程执行 Python 字节码时才生效，线程阻塞在系统调用里时完全无效，而它「有时能用」的特性恰恰最危险。

异常默认只在那条线程里打印一下

def job():
    raise RuntimeError("boom")

t = threading.Thread(target=job)
t.start(); t.join()
print("主线程认为一切正常")   # 回溯打在 stderr，主线程完全不知情

裸线程里未捕获的异常会交给 threading.excepthook（Python 3.8 起）处理，默认行为是把回溯打到 stderr，然后那条线程结束——主线程不会收到任何信号，退出码依然是 0。在容器里，这意味着日志采集如果只收结构化日志、不收 stderr，这次失败就彻底消失了。生产上应当替换 threading.excepthook，把它接进统一的异常上报。

线程池的情况稍好但坑同样存在：异常被存进 Future，只在你调用 result() 或 exception() 时才抛出来。写成 for u in urls: ex.submit(fetch, u) 而从不取结果，所有失败就都留在无人查看的 Future 里。这也是「任务显示全部完成，数据却少了一半」这类问题的典型来源。

症状真实原因处理
作业报成功，数据少了一部分submit 后从不取 result()，异常留在 Future 里逐个 result()，或用 as_completed 显式处理
进程跑完不退出非守护线程还活着，或 q.join() 等不到 task_done()用停止信号让线程自己退，检查 task_done 配对
退出时文件只写了一半收尾任务跑在守护线程里，被直接掐断改成非守护线程 + Event 停止信号
CPU 0%、请求全超时死锁，或持锁时卡在无超时的 I/O 上faulthandler.dump_traceback 看所有线程栈
并发调大后反而变慢下游连接池打穿 / 触发限流 / 重试放大按上表四个来源重新反推并发度

线程的三个代价里，内存和切换都能算出来，最贵的其实是第三个：它把「顺序执行」这个你赖以调试的前提拿走了。凡是能用不共享的结构解决的问题，就别用锁去解决。

六、落地判据：并发度、超时、重试

把前面几节收成可执行的规则。第一件事是并发度必须算出来而不是拍出来，算法就是拿三个上限取最小值再留余量。

C ≈ min( 连接池上限, 允许 QPS × 单次耗时, 内存允许的线程数 ) × 0.8

中间那一项是 Little 定律的直接应用：系统里同时在途的请求数等于吞吐乘以时延。上游给你 50 QPS、单次 0.42 秒，那么同时在途的请求超过 21 个就一定会触发限流，跟你本地开了多少线程无关。乘 0.8 是给抖动留的余量——下游变慢时单次耗时会涨，可用并发会自动缩小，卡在上限上运行等于把自己放在悬崖边。

第二件事是超时必须显式设置，而且要分开设。大多数网络库的默认值是「永不超时」，配上线程就是一个隐蔽的资源泄漏：一条线程挂在一个永远不会返回的连接上，池子里少一个工位，而监控上完全看不出来——它不算失败，只是永远没结束。

# 连接超时和读取超时分开：建连慢通常是网络问题，读取慢是服务端慢
resp = session.get(url, timeout=(3.05, 10))

# 线程池侧再设一道整体超时，防止个别任务拖垮整批
for f in as_completed(futs, timeout=120):
    ...

要注意这两道超时的性质不同。timeout=(3.05, 10) 是真的会让底层 socket 放弃并抛异常；而 as_completed(timeout=120) 只是让等待方抛 TimeoutError，后台任务依然在跑——因为线程无法被强制终止。整体超时能保护调用方的时延，不能回收资源，资源只能靠第一道超时回收。

第三件事是重试必须幂等。并发环境下重试的破坏力被放大：一次超时可能是请求根本没到达，也可能是对方已经处理完只是响应丢了，客户端分不清这两种情况。对读操作无所谓，对「扣款」「发消息」「创建订单」这类写操作，不带幂等键的重试就是在制造重复数据。除此之外还要加指数退避与随机抖动，否则大量客户端会在同一时刻一起重试，把刚缓过来的下游再打趴一次。

线程、进程、异步怎么选

维度多线程多进程asyncio
适用场景I/O 密集，并发在几十到几百CPU 密集，需要吃满多核纯 I/O，并发上千甚至上万
单位开销每线程 MB 级栈 + 内核调度每进程独立解释器，几十 MB 起每协程 KB 级，同进程内
切换成本内核上下文切换，微秒量级最贵，还要跨进程传数据用户态跳转，最便宜
能否真并行算默认构建受 GIL 限制能，各进程各一把 GIL不能，单线程事件循环

并发上千是线程和异步的分水岭，原因是成本结构不同。一万条线程意味着一万份栈和一万个内核调度实体，而一万个协程只是一万个对象，切换不进内核。反过来，如果你的依赖里有任何一个只提供同步接口的库（不少数据库驱动、SDK 都是这样），异步方案就得给它包一层线程池（asyncio.to_thread，Python 3.9 起），此时线程并没有消失，只是退到了幕后。

还有一个常被忽略的判据是团队能读懂哪一种。线程的调试工具链（faulthandler、线程栈转储）成熟且直观，异步的报错栈对新手更难读。在并发量只有几十的场景里，为了理论上更省的资源把整条链路改成异步，通常不划算。

  • 默认用 ThreadPoolExecutor，显式传 max_workers，值从下游上限反推
  • 每个网络调用都设超时，连接超时和读取超时分开设
  • 用 with 管理锁，临界区里只放改状态的那几行
  • 用 queue.Queue(maxsize=N) 交接数据，靠有界队列拿到背压
  • 停止靠 Event + 协作式检查，用 stop.wait(n) 代替 sleep(n)
  • 每个 Future 都取一次 result()，让异常有地方可去
  • 客户端连接池大小和线程池大小对齐，两边一起调
  • 为了「再快一点」把并发翻十倍，却不看下游连接池和限流配额
  • 在持有锁的时候发起 HTTP 请求或数据库查询
  • 用守护线程跑有收尾动作的任务（写文件、提交事务、flush 日志）
  • 用无界 Queue，或在循环里无限 submit 却不分批
  • 共享一个 requests.Session 却不调整 pool_maxsize
  • 用 ctypes 注入异常来「杀死」线程
  • 对非幂等的写操作做重试，还不加退避和抖动

并发度是一个从外部约束反推出来的数，不是一个可以调大的旋钮。你能调的其实只有一件事：让每次调用更快返回——超时、退避、缓存，都是在做这件事。

Q&A

CPython 有 GIL，那多线程到底还有没有用？
有用，而且对绝大多数后端场景是首选。GIL 约束的是「同时执行 Python 字节码」，而线程在等待网络、磁盘、子进程返回时会主动释放 GIL——这段时间正好让别的线程去跑。由于 I/O 密集任务里等待占了九成以上，重叠这部分等待的收益和有没有 GIL 无关。GIL 真正封死的是「多条线程同时跑纯 Python 计算」，那种场景该用多进程。另外要注意大量 C 扩展（NumPy、压缩、加解密、数据库驱动）在耗时操作期间也会释放 GIL，所以「调用了 C 库就等于 CPU 密集、线程没用」这个推论是错的，得实测。
max_workers 到底该设多少？有没有公式？
有一个可用的起点：取「下游连接池上限」「允许 QPS × 单次耗时」「内存允许的线程数」三者的最小值，再乘 0.8 留余量。中间那一项是 Little 定律，比如上游限 50 QPS、单次 0.42 秒，同时在途请求超过 21 个就必然触发限流。关键在于这三项都来自你之外的约束，所以正确顺序是先去查下游的配额和连接池配置，而不是先猜一个数再压测。不传 max_workers 时，Python 3.8 起 ThreadPoolExecutor 的默认值是 min(32, os.cpu_count() + 4)——这个默认值是为通用场景取的，对有严格限流的下游通常偏大。
submit + as_completed 和 map 该选哪个？
看失败的处理粒度。如果一万条任务里坏了三条，你希望记录下来继续跑完，用 submit + as_completed：结果按完成顺序回来，每个 result() 单独 try，一个失败不影响其他；代价是要自己用 dict 把 Future 映射回原始输入。如果语义是「一条失败整批作废」，map 更合适，它在迭代到失败项时抛出异常并中断循环，正好是你要的行为。还有一个次要差别：map 严格按输入顺序返回结果，第一个任务最慢时后面的结果只能在内存里等着，处理不能提前开始。要边出边处理就只能用 as_completed。
能强行杀掉一条线程吗？任务卡住了怎么办？
不能，标准库没有提供这个能力，而且是有意的：强杀会让线程停在任意指令上，锁可能还持有着、文件写了一半、事务不明不白，之后整个进程都不可信。唯一的办法是协作式取消——用 threading.Event 发停止信号，被取消方在循环里检查并主动退出。这意味着取消的响应速度取决于检查点密度，一条卡在没有超时的 socket 读取上的线程，设多少次标志都不会醒，所以给每个阻塞调用设超时本身就是取消能力的一部分。网上用 ctypes 注入异常的技巧不要用于生产，它在线程阻塞于系统调用时完全无效，「有时能用」比「完全不能用」更危险。如果确实需要硬性终止，把那部分任务放进子进程，进程是可以被杀的。
线程里抛了异常，为什么程序还显示成功？
这是线程最常见的静默失败。裸线程里未捕获的异常交给 threading.excepthook（Python 3.8 起）处理，默认只把回溯打到 stderr，线程就此结束，主线程收不到任何通知，进程退出码依然是 0。线程池的情况类似但更隐蔽：异常被存进 Future，只有你调用 result() 或 exception() 时才会抛出来，所以 for u in urls: ex.submit(fetch, u) 这种从不取结果的写法会让所有失败石沉大海。两条对策：每个 Future 都取一次结果（或用 as_completed 遍历），以及在服务启动时替换 threading.excepthook，把线程内异常接进统一上报。
多个线程共用一个 requests.Session 可以吗？
官方文档明确说 Session 不保证线程安全，所以稳妥做法是用 threading.local 给每条线程一个独立 Session。如果确实要共享，至少必须把连接池调大：HTTPAdapter 的默认 pool_maxsize 是每个主机 10 条连接，线程数超过它之后，多出来的连接用完即弃，日志会刷 connection pool is full 的警告，每个请求都要重新握手，性能不升反降。规则是连接池大小和线程池大小对齐，两边一起调。注意共享 Session 还有一个副作用：cookie jar 是共享的，多线程互相污染会话状态，这类 bug 很难查。
把线程池换成进程池会不会更快？
对 I/O 密集任务通常更慢。进程池的每个任务都要把参数序列化（pickle）传过去、再把结果序列化传回来，对于「发个 HTTP 请求拿一段 JSON」这种任务，序列化开销可能和任务本身一个量级，而它要解决的 GIL 问题在这里根本不存在——线程等待时本来就不占 GIL。进程池的适用场景是响应回来之后的处理很重：大量正则解析、图像处理、纯 Python 的数值计算。这时可以分工，用线程池负责拉数据、进程池负责算，两级串起来。另外还有两个额外成本：不可 pickle 的对象（打开的连接、lambda、闭包）传不过去，以及子进程崩溃后需要自己处理回收，见 PY23 · 内存模型与垃圾回收里关于进程内存不共享的讨论。
什么时候该从线程切到 asyncio？
三个信号同时出现时：并发目标上千、任务是纯 I/O、依赖链上的库都有异步版本。前两条是收益，第三条是可行性，而第三条通常才是决定性的——只要链路里有一个只提供同步接口的库，一次调用就会阻塞整个事件循环，让所有协程一起卡住，这种问题比线程的竞态更难定位。折中方案是保持异步主干、用 asyncio.to_thread()（Python 3.9 起）把那几个同步调用扔进线程池，此时线程并没有消失，只是退到了幕后。如果并发只有几十上百，线程池完全够用，为了理论上更省的资源把整条链路改成异步通常不划算，还要额外承担团队读不懂异步报错栈的成本。
