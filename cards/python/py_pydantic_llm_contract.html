PY53 · 用 Pydantic 约束大模型输出

把大模型返回的那段文本，当成一个陌生人通过公网 POST 过来的请求体。你不会拿那种请求体直接去写数据库，也就不该拿模型输出直接去写数据库。差别只在于：请求体坏了会立刻报错，模型输出坏了往往能一路滑到很远的地方才暴露。

一、模型输出为什么必须当成不可信输入

大模型生成的是概率上最可能的下一段文本，不是一个数据结构。即使你在提示词里把格式写得再清楚，即使九成九的调用都乖乖返回了合法 JSON，剩下那一小部分仍然会以各种方式坏掉——而且坏的方式每次都不太一样。

这件事和「模型够不够强」关系没有想象中大。换更强的模型能把坏输出的比例从 2% 压到 0.3%，但压不到 0。只要你的流程每天跑几万次，0.3% 就是几百条。所以问题从来不是「怎么让它别出错」，而是出错的那几百条应该在哪里被拦下来。

典型的坏法有哪几种

坏输出形态一个具体例子不校验会怎样
外包一层解释文字JSON 前面多一句「好的，以下是抽取结果：」，或裹了一层代码块围栏解析阶段直接抛异常——这反而是最容易发现的一类
字段名漂移约定 amount，返回 Amount 或 amount_value按键取值拿到 None，下游当成「没抽到」，静默丢数据
枚举取值超纲约定三选一，模型自己发明了第四个取值分支逻辑落进 else，统计口径悄悄变形
数字变字符串约定 12.5，返回 "12.5 万元"入库到文本列不报错，做聚合时被当成 0
嵌套层级缺失约定 {"items": [...]}，返回顶层直接是数组遍历时类型错误，或者把一条误当成多条
凭空多出字段模型自作主张补了一个你没要的字段多数代码会忽略，但写进宽表会污染表结构

注意这张表的第二列和第三列的错位：越是显眼的坏法，危害越小。解析就失败的那一类当场就炸了，你马上知道；而字段名漂移和数字变字符串这两类，是能顺利通过 json.loads 的合法 JSON，它们会安静地往下走。

危险的不是「模型返回了垃圾」，而是「模型返回了看起来像好数据的垃圾」。前者会自己暴露，后者需要你主动去拦。

不拦在门口，就等于把不确定性扩散到整个系统

一段没校验过的数据每往下游走一层，它可能出错的假设就多一层，而排查时要回溯的路径也长一层。这就是校验边界这个概念的全部理由：在数据进入系统的那一刻做一次判定，通过就是可信的，不通过就当场拒绝。

模型返回的那段文本 │ ├─── 路径 A：直接用 ── 把不确定性扩散出去 │ │ │ ▼ │ json.loads 侥幸成功 → 入库 → 日报 → 对外接口 → 财务对账 │ │ │ │ │ │ │ └── 坏值可能在这五层里的任意一层才暴露 │ 离产生点越远，定位成本越高，且可能根本不暴露 │ └─── 路径 B：进门就校验 ── 把不确定性关在门口 │ ▼ 契约模型校验一次 ├─ 通过 → 下游所有代码都拿到已知形状的数据，不再重复判空 └─ 失败 → 明确知道：哪个字段、期望什么、实际收到什么 可重试 / 可降级 / 可告警，但绝不静默往下走

路径 B 的附带好处常被低估：一旦入口处做了校验，下游那些 if x is not None and isinstance(x, float) 的防御式代码就全都可以删掉。校验集中在一处，代码总量反而变少。这个论点在 PY21 里已经作为选型结论讲过——本卡要展开的是具体怎么做。

事故复盘：一条合同信息抽取流水线，日均处理约 6.5 万条记录，模型输出经 json.loads 后直接写入数据库。某次对提示词做了一处措辞微调（把「返回金额」改成了「返回合同金额」），模型开始在 amount 这个数值字段上偶发返回带单位的字符串，如 "12.5 万元"，比例约 0.7%。入库列是宽松的文本类型，写入不报错；下游统计任务把无法转数字的值当 0 处理，同样不报错。问题静默运行了 9 天，累计影响约 4100 条记录。最终不是被任何监控发现的，而是财务做月度对账时发现合同总额对不上，差了 3.2%，反查才定位到抽取环节。补上契约校验后的第一周，45.5 万条里拦截了约 2900 条（0.64%），其中 96% 经一轮修复重试后通过，剩下约 120 条进了人工队列；回溯重跑那 4100 条历史记录另外花了 2 天。真正的教训不是「模型不靠谱」，而是整条链路上没有任何一个环节有资格说「这个字段是数字」。

二、把契约写成模型

数据契约指的是「这份数据必须长什么样」的一份可执行声明。用 Pydantic 写契约，本质就是写一个类：字段名是类属性，字段类型是类型注解，业务规则用字段约束表达。

from pydantic import BaseModel, Field

class Extracted(BaseModel):
    amount: float = Field(ge=0, description="合同金额，单位元，不带单位")
    currency: str = Field(pattern=r"^[A-Z]{3}$")
    note: str = Field(default="", max_length=200)

这段代码里没有一行是「校验逻辑」，但它已经完整表达了四条规则：金额必须能解析成非负浮点数、币种必须是三位大写字母、备注最长 200 字、备注可以不给。

为什么它比手写校验强：一份定义，三个用处

这才是选 Pydantic 而不是手写 if 的根本原因。同一个类定义，同时扮演三个角色，而且三者永远不会互相跑偏，因为它们来自同一份源。

class Extracted(BaseModel) amount: float = Field(ge=0) │ ┌────────────────────────┼────────────────────────┐ ▼ ▼ ▼ ① 运行时校验器 ② 给模型看的格式说明 ③ 静态类型信息 收到数据时逐字段 从模型导出 JSON Schema 编辑器补全字段名， 检查并做必要的转换， 塞进提示词，或直接传给 类型检查器能在改 不合规就抛出带路径 供应商的结构化输出参数 契约时把所有受影 的结构化错误 （两种用法都常见） 响的代码标出来 │ │ │ └────────────────────────┴────────────────────────┘ 改一次字段，三处同时生效 手写校验做不到这一点，因为那时是三份东西： 校验代码 + 提示词里手打的格式描述 + 下游取字段的代码 改任意一处，另外两处都会悄悄过期，而且没有任何机制会提醒你

第②点值得展开。模型能把自己导出成一份标准的 JSON Schema——描述数据结构的通用格式。这份 Schema 有两种用法：拼进提示词当作格式说明，或者作为参数交给供应商的结构化输出接口去做解码期约束。后者效果强得多，但不是所有供应商和所有模型都支持，两种方案的取舍与更完整的谱系见 L13 结构化输出的四道防线。

import json

schema = Extracted.model_json_schema()      # 标准 JSON Schema 字典
prompt = SYSTEM + "\n严格按以下结构输出：\n" + json.dumps(
    schema, ensure_ascii=False)

顺带一提，Field 里那个 description 会原样进入导出的 Schema。也就是说，写给同事看的字段注释和写给模型看的字段说明是同一句话——这是个很小但很实在的收益。

手写校验是在「描述数据」之外额外写一套检查；契约模型是让「描述数据」这件事本身就产生检查。少写的不只是代码，还有三份东西不同步的风险。

各类规则该用什么表达

想表达的规则用什么表达要注意
字段是什么类型类型注解，如 float / list[Item]嵌套模型会递归校验，错误路径自带层级
数值范围字段约束 ge / le / gt / lt会一并写进导出的 Schema，模型也看得到

类型注解在这里不只是给人看的提示，而是真正被执行的约束——这一点和标准库的 dataclass 截然不同，注解与校验的区别在 PY20 和 PY21 里都讲过。

三、校验失败要能定位到字段

「校验失败了」这句话本身没有任何价值。有价值的是「第 3 个条目的 amount 字段期望一个数字，实际收到字符串 '12.5 万元'」。两者的差距，决定了你是花 5 分钟还是花 5 小时。

结构化的校验错误长什么样

校验失败时抛出的 ValidationError 不是一句文本，而是一个可遍历的错误列表，而且是一次性收集全部错误后才抛——不是遇到第一个就返回。列表里每一项都是一个结构化的条目：

errors() 返回的每一项大致长这样（Pydantic v2） ┌────────────────────────────────────────────────────────────────┐ │ loc ('items', 2, 'amount') │ │ 出错位置：第 3 个条目里的 amount 字段（索引从 0 起） │ │ type 'float_parsing' │ │ 机器可读的错误类别，字符串常量，适合拿来分支 │ │ msg 'Input should be a valid number, ...' │ │ 人读的说明，适合放进给模型的修复提示 │ │ input '12.5 万元' │ │ 实际收到的值，原样保留 │ └────────────────────────────────────────────────────────────────┘ │ │ │ ▼ ▼ ▼ 打点用的维度 分流用的依据 喂回模型的证据 items.*.amount 格式类还是内容类 「你给的是这个， 能看出是哪个 决定要不要重试 但要求是那样」 字段长期不稳定

注意 loc 的形态：它是一个序列而不是字符串，嵌套模型和列表索引会一层层拼进去。把它连成 items.2.amount 这样的点分路径只是一行代码，但这一步做与不做，决定了你的日志能不能被聚合。

维度手写 if 校验结构化校验错误
哪个字段出错混在错误文本里，只能靠人读独立字段，可直接当监控维度用
嵌套与列表定位几乎写不出来，写出来也难维护路径自带层级和索引
一次报几个错通常第一个就 return 了一次收集全部，一轮就能全修
能否机器分类不能，只有一句自由文本能，有稳定的错误类别标识
实际收到了什么要自己记得拼进消息里自带，不会忘
够不够喂回模型信息通常不足位置、期望、实际三要素齐全

只记「校验失败」，你得到的是一条曲线；记下字段路径，你得到的是一张可以下钻的表。前者只能告诉你「最近变差了」，后者能告诉你「是 amount 这一个字段变差了」。

把字段路径记进日志和指标

这是本节最容易被跳过、但回报最高的一步。只打一个「校验失败总数」的计数器，你永远分不清两种完全不同的状况：某一个字段长期小比例不稳定（说明该字段的提示词描述有歧义，改提示词就能解决），还是整体格式突然崩掉（说明模型版本变了或提示词被改坏了，得回滚）。这两件事的应对方式完全相反，而总数曲线对它们的反应长得一模一样。

try:
    data = Extracted.model_validate_json(raw_text)
except ValidationError as e:
    for err in e.errors():
        path = ".".join(str(p) for p in err["loc"])
        log.warning("contract_reject", field=path,
                    kind=err["type"], got=repr(err["input"])[:80])

把 field 和 kind 作为结构化日志的字段而不是拼进消息文本，才能在日志系统里按字段聚合——这套写法的完整理由在 PY43 里。got 记得截断：模型偶尔会返回几千字的东西，原样打进日志会把采集链路撑爆。另外，校验失败属于预期内的失败，不该用崩溃级别的日志，异常分层的取舍见 PY24。

四、把错误喂回模型

拦住坏输出只是止损，真正能把可用率拉上去的是下一步：把校验错误翻译成给模型的修正指令，让它自己改。上一节那三个信息——出错在哪、期望什么、实际给了什么——正好就是修复提示需要的全部内容。

修复循环的形状

┌── 第 n 轮 ────────────────────────────────────────────────────┐ │ 输入 = 任务提示词 + 契约的结构描述 │ │ n ≥ 2 时再追加三样： │ │ · 上一轮的原始输出（原样贴回去，别自己改写） │ │ · 哪些字段不合规（错误路径 + 说明） │ │ · 那些字段期望什么 │ └────────────────────────────┬──────────────────────────────────┘ ▼ 模型返回文本 ▼ 预处理：去代码块围栏、大小写归一、同义词映射 ▼ 契约校验 ┌────────────┴────────────┐ 通过 失败 │ │ ▼ 是格式错误吗 交给下游 ┌────────┴────────┐ 是 否 │ │ n 未到上限就再来一轮 内容错误：重试只会 （上限通常 2，最多 3） 得到同样的结果 │ │ 到上限 ▼ └────────► 人工队列 / 降级 + 告警

实践里这个循环的收敛速度往往出人意料：绝大多数格式问题一轮就修好了。原因不难理解——模型本来就知道正确格式该怎么写，它只是这一次没写对；你把具体错在哪指出来之后，这就变成了一个比原任务简单得多的改写任务。

修复提示的关键不是措辞，而是具体。「格式不对，请重新输出」基本等于重掷一次骰子；「字段 items.2.amount 需要数字，你给的是 '12.5 万元'」几乎一次就能修好。你手里已经有了这份具体信息，别浪费。

def repair_prompt(raw: str, e: ValidationError) -> str:
    problems = "\n".join(
        f'- 字段 {".".join(str(p) for p in x["loc"])}：{x["msg"]}，'
        f'你给的是 {x["input"]!r}'
        for x in e.errors()
    )
    return f"上次输出不合规：\n{raw}\n\n问题：\n{problems}\n只返回修正后的 JSON。"

三条纪律

第一，修复次数必须有硬上限。没有上限的重试循环，在一个模型死活修不好的样本上会一直转下去。这不是理论风险：单条请求的成本乘以无限次，加上批量任务里并发的几十条一起转，能在很短时间里烧掉大量配额。上限设 2（即最多一次修复）通常就够了，因为第二次还修不好的，第三次大概率也修不好。

第二，必须区分格式错误与内容错误。这是决定「该不该重试」的唯一依据，也是最容易被忽略的一条。

对比项格式错误内容错误
典型表现数字写成带单位的字符串、多包了一层、字段名大小写不对金额抽成了另一个数、枚举语义选错、把推测当事实填上
契约能发现吗能，这正是它擅长的只能发现「不合法」，发现不了「合法但不正确」
重试有用吗有，指出问题后通常一轮修好没用，同样的输入会得到同样的错
该怎么处理走自动修复循环人工队列、降级为空结果、或换更强的模型重跑
该监控什么修复率、平均修复轮数抽样人工核对的准确率

这张表最右列有个必须承认的事实：契约管不了内容对不对。一个格式完美、数值却抽错的输出，会毫无阻碍地通过所有校验。所以契约是防线之一而不是全部，它和采样复核、交叉验证之类的手段是互补关系，整体防线的组合策略见 L13 结构化输出的四道防线。

第三，把修复率当成提示词质量的指标。修复率指的是「需要走修复循环才通过的调用占比」。它平时应该是一个很小的、稳定的数——一旦某次提示词调整后它跳了一个台阶，说明这次改动引入了歧义，即使最终结果还是对的，你也在为每一次调用多付一轮 token。把它和上一节的字段维度放在同一张看板上，提示词改坏了当天就能看见，而不是等九天后财务来对账。

事故复盘：一个批量摘要任务在夜间跑，修复循环写成了 while not valid:，没有上限。当晚有 37 条输入里含有大段代码片段，模型持续把代码里的花括号带进输出，格式永远校验不过。这 37 条各自转了平均 1900 多轮，四个多小时里消耗掉当月配额的 六成，直到早上配额触顶、整条链路 429 才被发现。修复只有两行：加上 for attempt in range(2) 的上限，以及超限后写入人工队列并告警。之后同类输入的表现是——每条多花 1 轮，然后干净利落地进队列。

五、宽严的边界在哪

契约收得太紧和放得太松，是两个方向上等价的错误。过严会把本来完全可用的输出拒掉：要求精确枚举 positive，模型给了 正面，语义一模一样，却被判失败，然后白白触发一轮重试。过松则是另一回事——所有字段都写成 str，所有字段都有默认值，校验永远通过，那这层契约除了制造一种「我们有校验」的错觉之外什么也没做。

契约的松紧不是一个全局旋钮，是逐字段的决定。同一个模型里，主键字段应该严到错一个字符就整条拒绝，摘要字段应该松到只管长度别的不问。

先预处理，再校验，最后才兜底

关键的认识是：能自动修正的偏差，根本不该走到校验失败那一步。代码块围栏、首尾空白、枚举取值的大小写、几个已知的同义词——这些都是确定性的、可以用几行代码抹平的，让模型重试一轮去修它们，既慢又贵还不稳定。

import re

FENCE = re.compile(r"^\s*```(?:json)?|```\s*$")
ALIAS = {"pos": "positive", "正面": "positive", "neg": "negative"}

label = ALIAS.get(raw_label.strip().lower(), raw_label)

第三层的兜底取值尤其重要，而且违反直觉。很多人觉得枚举里加一个 unknown 是在给模型偷懒的机会，实际恰恰相反：不给它表达「我不确定」的出口，它就只能在剩下的选项里挑一个，于是你得到的是一个格式完美、看起来很确定、实际上是瞎猜的值——这比一个诚实的 unknown 危险得多，因为它不会触发任何后续复核。同样的道理适用于置信度字段：允许低分，并在低分时自动转人工。

事故复盘：一个工单分类流程把优先级枚举定成了 high / medium / low 三选一，严格匹配，不合规就整条丢弃并计入失败。上线后失败率稳定在 8.4%，团队一度以为是模型能力不足，准备换更贵的模型。导出失败样本一看才发现，被拒的值里超过九成是 High、HIGH、紧急 这三种——语义完全正确，只是大小写和语言不同。加了一层七条映射的归一表之后，失败率降到 0.5%，换模型的计划直接取消。这个坑的教训是：在判断「模型不行」之前，先把被拒样本导出来看一眼，成本几乎为零。

六、性能、版本与工程纪律

校验有开销，而且不小。虽然 v2 把校验核心用 Rust 重写后比 v1 快了很多，但和「直接赋值」相比仍是数量级的差距。结论和 PY21 完全一致：把校验放在系统边界，不要放进内层热路径。

不过在大模型场景里，这个权衡比普通场景轻松得多——一次模型调用的耗时是百毫秒到数秒量级，校验那点微秒级的开销完全淹没在里面。真正需要留意的只有一种情况：批量处理几十万条历史数据时逐条构造模型。那时正确的做法不是放弃校验，而是整批校验一次（用一个包着列表的模型），再把结果转成内层的轻量对象参与计算。

在大模型链路里纠结校验开销，相当于在一趟跨国航班上纠结值机柜台多走的那十步路。校验的成本永远小于一条坏数据流进下游的成本。

v1 与 v2 的差别要写进项目约定

Pydantic 的 v1 到 v2 是一次大改，方法名几乎全换了一遍。混淆版本是这个库最常见的时间浪费来源：网上很多教程还停留在 v1 写法，抄进 v2 项目会报一堆看不懂的错。凡是涉及这个库的文档、示例、代码评审，先说清楚是哪个大版本。

v1 的那些名字在 v2 里多数还在，只是被标记为废弃——所以抄错了不一定立刻报错，可能只是打一条警告。更隐蔽的是配置项改名（比如 orm_mode 变成 from_attributes）：写错的键会安静地待在配置字典里从不被读取，行为不生效也没有任何提示。新项目直接用 v2；老项目迁移时把配置项逐个对着迁移文档核一遍，别只信运行不报错。

契约要集中管理并纳入版本

契约模型不该散落在各个调用点，而应当集中在一个模块里。理由是契约的变更是破坏性变更：加一个必填字段，所有历史数据都不再合法；改一个枚举取值，所有存量记录的语义都变了。它和数据库表结构是同一类东西，理应享受同样的待遇——改动走评审，变更留记录，必要时给契约本身编个契约版本号，让日志里能看出某条记录是按哪一版契约校验通过的。

契约模型是接口定义，不是工具函数。判断标准很简单：如果改它会让别人的代码或者历史数据出问题，那它就该放在能被看见的地方，而不是藏在某个 handler 文件的中段。

用真实坏输出做回归样本

最后一条纪律，也是最有杠杆的一条：为契约写测试，测试样本必须来自线上真实拦截到的坏输出。这正是第三节要求「把被拒的原始文本存下来」的兑现时刻。

自己构造的坏样本和真实坏样本完全不是一回事。你能想到的无非是「少个字段」「类型不对」；而模型真实的坏法千奇百怪——中文全角引号、末尾多一个逗号、把整个 JSON 又包进一个 result 键里、数字里夹了千分位逗号。这些你坐在工位上想不出来，但线上一周就能攒出几十个。把它们存成 fixture 目录，每次改契约或改提示词都跑一遍，这套回归样本的组织方式见 PY41。

@pytest.mark.parametrize("sample", load_bad_samples("fixtures/llm_bad/"))
def test_known_bad_is_rejected(sample):
    with pytest.raises(ValidationError):
        Extracted.model_validate_json(sample.raw)

def test_golden_sample_parses():
    assert Extracted.model_validate_json(GOLDEN).amount == 12.5

这套测试的真正价值在放宽契约的时候才显现：当你为了降低失败率想把某个字段改松，它会立刻告诉你这一改会让哪几个历史坏样本变成「合法」。没有它，放宽契约就是闭着眼睛拆防线。

  • 模型输出在进入系统的第一行代码就过契约，通过之后下游不再重复判空
  • 校验失败时把字段路径和错误类别作为结构化日志字段打点，不是拼进消息文本
  • 修复重试设硬上限（通常 2 轮），超限走人工队列并告警
  • 修复提示里带上原始输出、具体字段路径、期望是什么这三样
  • 确定性的偏差（围栏、大小写、已知同义词）在预处理层抹平，不占重试次数
  • 枚举留一个 unknown 出口，让模型能表达「不确定」而不是硬猜
  • 契约模型集中在一个模块，变更按破坏性变更对待
  • 把线上拦截到的坏输出存成 fixture，当作契约的回归样本
  • 把 json.loads 的结果直接写库或直接喂给下游
  • 只记录「校验失败 +1」，不记是哪个字段——分不清单字段漂移和整体崩盘
  • 写 while not valid: 这种没有上限的修复循环
  • 对内容错误反复重试——同样的输入只会得到同样的错
  • 用「格式不对，请重新输出」这种没有具体信息的修复提示
  • 所有字段都写成 str 且都给默认值，校验永远通过
  • 不看被拒样本就断定「模型不行」，直接上更贵的模型
  • 照抄网上的 v1 写法进 v2 项目，或反过来
  • 只用手工构造的坏样本做测试，不收集线上真实坏输出

Q&A

就几个字段，用 json.loads 加几行 if 判断不行吗？非要引一个库？
字段少的时候确实能写，问题在于三件事会随时间变差。第一是嵌套：一旦结构里有列表套对象，手写的定位逻辑会迅速变得难以维护，而你几乎肯定写不出「第 3 个条目的 amount 字段」这种精度的错误信息。第二是三处不同步：校验代码、提示词里手打的格式说明、下游取字段的代码是三份独立的东西，改一处漏两处是必然而不是偶然。第三是错误信息的形态——手写校验给出的是一句自由文本，既不能按字段聚合做监控，也不足以喂回给模型做修复。真正的分水岭不是字段多少，而是你需不需要「按字段打点」和「自动修复循环」这两件事。只要需要其中任何一件，手写方案就撑不住了。
把 JSON Schema 塞进提示词，模型就一定会照着输出吗？
不会，这只是提高概率，不是保证。塞进提示词的 Schema 本质上还是文本，模型读了它之后仍然是在做概率生成，没有任何机制强制它遵守。真正能提供强约束的是供应商提供的结构化输出接口——那类接口在解码阶段就限制了可生成的 token，从机制上排除了不合法的输出，但它有代价（不是所有模型都支持、复杂 Schema 可能被降级或拒绝、有时会影响生成质量）。所以现实的做法是两层都要：能用解码期约束就用，同时运行期的契约校验一层都不能省。把提示词里的格式说明当成「引导」而不是「约束」，这个心态摆正了，后面的设计就不会出错。更完整的方案谱系与选型见 L13 结构化输出的四道防线。
修复重试的上限到底该设几次？
默认设 2，也就是最多修一次。依据是修复成功率的分布形状：格式错误在第一次修复时的成功率通常很高（本卡第一个复盘里是 96%），而第一次没修好的样本，第二次修好的概率会掉得很厉害——因为它们往往不是格式问题，而是被误判成格式问题的内容问题，或者输入本身有结构性障碍（比如内容里含大段代码、含大量引号）。继续重试只是在为同一个失败反复付费。如果你的业务确实对单条成功率极度敏感，可以放到 3，但同时必须做两件事：给整批任务设一个总的重试预算上限，以及把「用满次数仍失败」的样本单独存下来定期人工看——那批样本通常能直接告诉你提示词该怎么改。
校验失败的样本要不要保存？保存什么？
要，而且这是投入产出比最高的一件事。至少保存四样：模型返回的原始文本（原样，不要做任何清洗）、错误列表里的字段路径与错误类别、当次用的提示词版本或哈希、以及模型名与版本。原始文本是回归样本的来源；字段路径与类别用来做聚合分析，看出是哪个字段长期不稳定；提示词版本用来把失败率的跳变对上是哪次改动引入的；模型版本则是为了应对供应商静默更新模型这种情况。存储上注意两点：原始文本要截断（模型偶尔会返回几千字），以及如果内容涉及敏感信息，样本库要和正式数据享受同等的权限与脱敏待遇。
v1 和 v2 差别大到什么程度？老项目值得迁吗？
差别很大，方法名基本全换了一遍（见第六节的对照表），配置方式从内嵌类改成了配置字典，校验器装饰器也换了名字和签名。新项目没有任何理由不用 v2。老项目要不要迁，看两点：一是性能——v2 的校验核心是 Rust 实现的，如果你的校验量大，收益是实打实的；二是依赖——生态里的主流库现在基本都以 v2 为准，继续留在 v1 会越来越难升级其他依赖。迁移时最需要小心的不是那些会报错的改动（报错的反而好办，跑一遍就知道），而是静默失效的那一类：配置项改名之后，写错的旧键会安静地留在配置字典里永不被读取，行为悄悄地不生效。所以迁移后一定要补一组针对配置行为的测试，别只看「能跑起来」。
契约里该不该允许模型多给字段？
分两种情况。如果下游是把整个对象原样落库或者转发出去，应该禁止多余字段，因为模型自己发明的字段会污染表结构或对外接口。如果下游只按名字取用固定的几个字段，那么默认的「忽略多余字段」是合理的，还顺带带来一点容错。但无论选哪种，都建议把「出现了多余字段」这件事记一条日志——它通常是一个信号，说明提示词里的格式说明有歧义，或者模型版本变了。需要注意的是默认行为是忽略而不是报错，想要严格模式得在模型配置里显式打开。另外别忘了反向的情况：字段缺失和字段显式给了 null在语义上是两回事，如果你的业务需要区分，就不能简单地给个默认值了事。
批量处理几十万条时，校验会成为瓶颈吗？
在大模型链路里几乎不会。一次模型调用是百毫秒到数秒量级，一次校验是微秒到几十微秒量级，两者差了四五个数量级，校验完全淹没在调用耗时里。会成为瓶颈的是另一种场景：你已经有了几十万条存量的模型输出（比如回溯重跑历史数据），在一个循环里逐条构造模型。这时的正确做法不是放弃校验，而是改成整批校验一次——定义一个包着列表的模型，一次校验整批，错误路径自带条目索引，照样能定位到具体是第几条的哪个字段。如果校验之后还要参与大量计算，再把结果转成内层的轻量对象（dataclass 或具名元组），这套分层的理由和边界在 PY21 里讲得更细。
