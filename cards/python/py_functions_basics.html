初学者写函数时踩的坑，几乎都不是「语法不会」，而是没意识到 Python 里的变量名只是一张贴在对象上的标签。参数传的是标签指向的那个对象，默认值只在定义时贴一次标签，赋值会悄悄把名字变成局部的——这三件事想明白了，函数这一章的坑就基本没了。

一、函数是什么：一个可调用的对象

大多数教程会说「def 用来定义函数」，这句话没错，但它掩盖了一件更重要的事：def 是一条在运行时执行的语句，它做了两个动作——先创建一个函数对象，再把一个名字绑定到这个对象上。它和 x = 3 在结构上是同一类事情，只是右边那个对象比整数复杂一些。

这里的 函数对象 指的是一个真实存在于内存里的值，它内部装着字节码、参数签名、默认值、所属模块等信息，和整数、字符串一样可以被赋值、被传递、被放进容器。把这一点接受下来，很多看起来「很高级」的 Python 写法就变成了理所当然。

执行 def greet(name): ... 时发生了什么 ─────────────────────────────────────── ① 创建函数对象 ② 把名字绑上去 ┌──────────────────────────┐ │ function object │ ◄──────── greet （名字，模块全局空间里的一个条目） │ 地址 0x7f3a... │ ◄──────── say_hi （再绑一个名字，指的还是同一个对象） ├──────────────────────────┤ ◄──────── handlers[0]（放进列表，容器里存的也是这个指向） │ __code__ 字节码 │ │ __name__ 'greet' │ ← 只记录「出生时」的名字， │ __defaults__ 默认值元组 │ 后来绑的 say_hi 不会改它 │ __doc__ 文档字符串 │ │ __annotations__ 类型注解 │ └──────────────────────────┘ 名字 ──引用──► 函数对象 ──包含──► 代码体 （可以有很多个） （只有一份） （调用时才执行）

图里最右边那句「调用时才执行」是理解一切的起点。def 执行完之后，函数体一行都没有跑，它只是被编译成字节码存进了 __code__。真正让代码体跑起来的是那对圆括号。

f 和 f()：一个字符的天壤之别

没有括号的 f 是在引用那个函数对象本身——你拿到的是函数，不是结果；加上括号的 f() 是在调用它——你拿到的是函数体 return 出来的值。忘记括号是新手最高频的错误之一，而它的可怕之处在于：多数时候不报错，只是行为静悄悄地变得离谱。

def is_ready():
    return False

if is_ready:        # 忘了括号：判断的是「函数对象存不存在」
    print("走到这里了")   # 永远会打印，因为函数对象恒为真

print(is_ready)     # <function is_ready at 0x7f3a1c2d4e00>
print(is_ready())   # False

上面这段的第一个 if 是一个真实会上线的 bug：函数对象作为布尔值永远是 True，所以这个分支从来不会走错——它永远走进去。发现它的唯一线索通常是打印出来的那串 <function ... at 0x...>，看到这种输出就该立刻想到「我少了一对括号」。

写法实际含义得到什么典型用途
f引用函数对象函数本身当参数传给别的函数、存进字典做分发表
f()调用函数return 的值，没写就是 None要它的执行结果
f()()调用后再调用一次需要 f() 本身返回一个函数装饰器、工厂函数（后续卡片展开）
callable(f)检查能不能被调用True / False写通用工具时校验入参

不写 return 等于 return None

函数体执行到末尾没有遇到 return，Python 会替你返回 None。写了光秃秃一个 return 也是同样的结果。这个规则本身很简单，麻烦的是它和「原地修改」的方法撞在一起时的表现：标准库里大量方法是原地改、返回 None 的，一旦你按直觉去接它的返回值，就会得到一个 None。

nums = [3, 1, 2]
nums2 = nums.sort()      # sort 原地排序，返回 None
print(nums2)             # None ← 不是 [1, 2, 3]

nums3 = sorted([3, 1, 2])  # sorted 返回新列表
print(nums3)               # [1, 2, 3]

后续如果对 None 继续操作，报错会是 TypeError: 'NoneType' object is not subscriptable 或者 AttributeError: 'NoneType' object has no attribute 'append'。看到报错里出现 NoneType，第一反应应该是「上游某个函数没有返回值，而我把它的返回值接了下来」。

def 不是声明，是一条会执行的赋值语句：右边造一个函数对象，左边挂一个名字。名字可以有很多个，对象只有一份，代码体要等括号来了才跑。

二、参数传递到底传的是什么

「Python 是传值还是传引用」是个经典问题，而正确答案是：都不是。C 语言意义上的传值会复制一份实参，Python 不复制；C++ 意义上的传引用允许函数内重新赋值影响到调用方，Python 做不到。Python 的机制叫 传对象引用（call by object reference，也叫 call by sharing）——传进去的是「指向那个对象的引用」这件事本身被复制了一份，而对象没有被复制。

换成一句可操作的话：调用方和函数内部，一开始指向的是同一个对象；但它们各自持有一个独立的名字。后果就分成了泾渭分明的两类。

情况 A：函数内「重新赋值」→ 只换了自己的名字指向，调用方看不见 ────────────────────────────────────────────────────────────── def bump(x): 调用前 执行 x = x + 1 后 x = x + 1 n ──► [ 10 ] n ──► [ 10 ] ← 原对象没变 return x x ──► ↑ x ──► [ 11 ] ← x 改指新对象 n = 10; bump(n) n 仍然是 10。int 不可变，x+1 只能造新对象。 情况 B：调用对象自己的方法「原地修改」→ 同一个对象变了，双方都看得见 ────────────────────────────────────────────────────────────── def add_one(lst): 调用前 执行 lst.append(1) 后 lst.append(1) items ─┐ items ─┐ ├─► [ ] ├─► [ 1 ] ← 同一个对象被改 items = [] lst ─┘ lst ─┘ add_one(items) items 变成 [1]。列表可变，append 改的就是那个对象。 一句话分界线： 名字 = 新东西 → 改的是「名字的指向」，出不了函数 对象.方法(...) → 改的是「对象本身」，调用方同样看得见 对象[i] = 新东西 → 也是改对象本身，出得去

这条分界线里隐含着另一个概念：可变对象 指内容可以在原地被修改的对象（list、dict、set、以及大多数自定义类的实例），不可变对象 则一旦创建内容就固定（int、float、str、tuple、bool、None）。情况 A 之所以「改不到外面」，本质原因不是参数传递机制，而是 int 根本没有「原地加一」这种操作，x + 1 只能造出一个新对象。

所以传不可变对象时，你永远不用担心函数偷偷改了你的值——不是因为它被保护了，而是因为它压根改不动。传可变对象时就必须留神了。

函数内的操作改的是什么调用方是否可见说明
x = 5名字 x 的指向❌ 不可见只在函数的局部空间里换了个绑定
x = x + 1名字的指向（造了新对象）❌ 不可见对 int / str / tuple 一律如此
lst.append(v)列表对象本身✅ 可见原地修改，双方指向同一对象
lst[0] = v列表对象本身✅ 可见下标赋值是改对象，不是改名字
lst += [v]列表对象本身✅ 可见list 的 += 等价于 extend，原地改
lst = lst + [v]名字的指向❌ 不可见和上一行只差一点写法，结果完全相反
d["k"] = v字典对象本身✅ 可见同下标赋值
lst = []名字的指向❌ 不可见想清空得写 lst.clear()

表里第 5、6 两行值得盯一会儿。lst += [v] 和 lst = lst + [v] 在数学上读起来一模一样，在 Python 里却一个改到了外面、一个没改到——因为列表实现了原地版本的 +=，而 lst + [v] 必然产出新列表。这种「看起来等价、实际不等价」的地方，是代码审查时最值得停下来的位置。

示例场景：某数据清洗脚本里有个 normalize(records) 函数，内部用 records.sort(key=...) 做了排序以便去重。调用方随后又用原列表按原始顺序写了一份审计日志，结果 12 万条记录的审计日志顺序全错，与上游系统对账时出现 3 处「记录丢失」的误报，团队花了半天才定位到是这一行原地排序。修复只有一行：把 records.sort(...) 换成 rows = sorted(records, ...)。规则很简单——函数收到的可变参数，默认当成只读；确实要改就在函数名和文档里写明白。

想避免被改，就在函数里先复制

如果你写的函数需要修改传进来的列表或字典，但又不想影响调用方，做法是在函数开头复制一份。注意 list(x) 和 x.copy() 都是浅复制——外层列表是新的，但里面装的元素还是原来那些对象。嵌套结构要真正隔离需要 copy.deepcopy，代价明显更高，用之前先确认是否真的需要。

def tidy(rows):
    rows = list(rows)        # 浅复制：换了外层容器
    rows.sort()              # 现在怎么改都不影响调用方
    return rows

参数传的不是值也不是变量，而是「指向同一个对象」这件事。换名字的指向出不了函数门，动对象本身则内外都看得见。

三、四类参数与调用方式

Python 的参数系统比多数语言灵活，代价是规则稍多。但这些规则都服务于同一个目标：让调用处能读懂。一个 send(user, msg, True, False, 3) 这样的调用，读代码的人必须跳到函数定义才知道那三个字面量是什么意思；而 send(user, msg, urgent=True, silent=False, retries=3) 一眼就懂。

四类参数各自解决什么问题

类型定义处写法调用处写法解决的问题
位置参数def f(a, b)f(1, 2)最简形式，参数少且顺序天然时用
关键字参数同上，无需特殊声明f(a=1, b=2)调用处自带说明，顺序可任意
默认值参数def f(a, b=10)f(1) 或 f(1, 5)让常用情况少写参数，同时保留扩展点
可变位置参数def f(*args)f(1, 2, 3)个数不定，函数内 args 是元组
可变关键字参数def f(**kwargs)f(x=1, y=2)透传未知选项，函数内 kwargs 是字典

*args 和 **kwargs 现在只需要建立直觉：星号在定义处表示「把剩下的都收集起来」，收位置参数得到元组，收关键字参数得到字典；同一对星号写在调用处时作用相反，表示「把这个容器摊开传进去」。它们真正常用的场合是写通用装饰器和转发层，那些细节留给后面的卡片，这里先不展开。

def log_all(*args, **kwargs):
    print(args)      # ('a', 'b')      元组
    print(kwargs)    # {'level': 'INFO'} 字典

log_all("a", "b", level="INFO")

顺序规则与两个分隔符

参数在定义处必须按固定顺序排列，否则是语法错误。顺序背后的逻辑是「确定性由强到弱」：能靠位置确定的排前面，能兜底的排后面。中间还可以插入两个特殊符号 / 和 *，它们本身不是参数，而是分界标记。

完整的参数排列顺序（定义处） ────────────────────────────── def f( a, b, /, c, d, *, e, f=0, **kw ): └──┬─┘ ▲ └─┬─┘ ▲ └──┬──┘ │ │ │ │ │ │ │ │ │ └── 强制关键字：只能 f(e=1)，写 f(1) 报错 │ │ │ └──────── 星号分隔符：它右边全部强制关键字 │ │ └────────────── 普通参数：位置、关键字两种方式都行 │ └─────────────────── 斜杠分隔符：它左边全部强制位置 └──────────────────────── 强制位置：只能 f(1)，写 f(a=1) 报错 调用处的实参顺序只有一条规则： 所有位置实参必须排在所有关键字实参前面 f(1, c=2) ✔ f(a=1, 2) ✘ SyntaxError: positional argument follows keyword argument

为什么要有强制位置参数？因为一旦某个参数可以用关键字传，它的名字就成了公开接口的一部分——以后想改名就是破坏性变更。标准库大量使用 / 正是为了保留改名自由，比如 len(obj, /) 就不允许你写 len(obj=x)。强制关键字参数则是反过来：那些布尔开关、罕用选项，逼调用方写出名字，避免出现连着四个 True, False, True, False 的调用。

分隔符作用范围违规时的报错什么时候该用
/左边的参数只能按位置传TypeError: f() got some positional-only arguments passed as keyword arguments参数名不想承诺稳定；语义上就是「那个东西」，名字无意义
*右边的参数只能按关键字传TypeError: f() takes 1 positional argument but 3 were given布尔开关、可选配置项、以后可能加参数的地方
都不写两种方式都允许—参数少（两三个以内）且含义明确

三个以上参数就该用关键字调用

这不是硬性规定，而是一条经验阈值。人类短期记忆大致能稳定保持三到四个项目，超过之后「第四个位置是什么」就需要回去查定义。更现实的风险是相邻同类型参数写反了不报错：resize(img, 800, 600) 把宽高传反，程序照常跑完，只是输出全变形，这类 bug 往往要到肉眼看到结果才被发现。写成 resize(img, width=800, height=600)，传反的概率几乎归零。

参数的设计目标不是让定义处好看，而是让调用处不需要跳转就能读懂。布尔开关一律做成强制关键字，超过三个参数一律带上名字调用。

四、可变默认参数：Python 最经典的陷阱

先看现象。下面这个函数看起来人畜无害：不传 acc 就用一个空列表，把 x 放进去返回。但连续调用三次，结果一次比一次长。

def collect(x, acc=[]):
    acc.append(x)
    return acc

print(collect(1))   # [1]
print(collect(2))   # [1, 2]   ← 上次的还在
print(collect(3))   # [1, 2, 3]

原因只有一句话：默认值在函数定义时求值一次，之后就存在函数对象里，每次调用复用同一个对象。def 那一行执行的时候，[] 就被创建出来并塞进了 collect.__defaults__ 这个元组。后面无论调用多少次，只要没传 acc，绑定到 acc 上的都是那同一个列表。而列表是可变对象，append 改的正是它本身。

默认值的生命周期 ───────────────── 【定义时·执行一次】 def collect(x, acc=[]): ──► 创建列表对象 L（地址 0x7f...） collect.__defaults__ = (L,) ▲ └── 这里从此不再变 【调用时·每次都复用那个 L】 ┌──────────┬──────────────────┬───────────────┬──────────────┐ │ 第几次调用│ acc 绑定到 │ append 之后 L │ 返回值 │ ├──────────┼──────────────────┼───────────────┼──────────────┤ │ 第 1 次 │ L（同一个对象） │ [1] │ [1] │ │ 第 2 次 │ L（同一个对象） │ [1, 2] │ [1, 2] │ │ 第 3 次 │ L（同一个对象） │ [1, 2, 3] │ [1, 2, 3] │ │ ... │ L（永远是它） │ 只增不减 │ 越来越长 │ └──────────┴──────────────────┴───────────────┴──────────────┘ 【正确写法·每次调用新建】 def collect(x, acc=None): if acc is None: ──► 每次进函数才创建 acc = [] 新列表，互不干扰 acc.append(x) return acc

把默认值改成 None 之所以有效，是因为 None 是不可变的单例对象，存在 __defaults__ 里没有任何风险；真正的列表创建被挪进了函数体，而函数体每次调用都会执行。这就是标准库里到处都是 def f(x, opts=None) 的原因，它不是风格偏好，是绕开语言机制的固定手法。

默认值写法存进 __defaults__ 的是多次调用之间安全吗
n=0 / s="" / t=()不可变对象无法被改动，天然独立✅ 安全
flag=NoneNone 单例无法被改动✅ 安全，推荐做哨兵值
acc=[] / d={} / s=set()可变对象，只造一次状态会一路累积❌ 几乎总是 bug
ts=time.time()定义那一刻的时间戳永远是进程启动时间❌ 静默错误，更难发现
obj=SomeClass()定义时构造的那一个实例所有调用共享一个实例❌ 共享状态污染

表里第 4 行比列表那一行更阴险：def log(msg, ts=time.time()) 不会累积、不会变长、不会报错，它只是让所有日志的时间戳都等于程序启动的那一刻。这种 bug 可以在生产环境安静地活很久，直到有人对着时间序列图问「为什么这些日志全是同一秒」。

示例场景：一个商品推荐接口的内部函数写成 def recommend(uid, picked=[])，本意是「允许调用方传入已选商品做去重」。上线后单实例累计处理 1 万次请求，picked 里堆进了 4.2 万个商品 ID；接口返回体从最初的 2 KB 涨到 3.1 MB，P99 延迟从 45 ms 涨到 2.3 s，并且不同用户开始看到彼此的商品——越晚请求的用户被污染得越严重。重启实例会短暂恢复正常，于是最初被误判成「内存泄漏」查了两天。真正的修复是一行：把默认值改成 None，在函数体内 picked = picked or []。这个陷阱的危险之处在于本地单次调用永远测不出来，它只在同一进程内反复调用时才显形。

默认值是贴在函数对象身上的一件行李，不是每次调用发的一次性用品。所以默认值只能放不可变的东西，要用列表或字典就默认 None，进了函数体再造。

五、作用域：LEGB 查找顺序

函数里写下一个名字，Python 需要决定去哪里找它。规则叫 LEGB——按 Local、Enclosing、Global、Builtin 四层依次向外查找，找到第一个就停，四层都没有才抛 NameError。

名字查找：从里往外，找到就停 ──────────────────────────────── ┌─ B Builtin ─────────────────────────────────────────┐ │ print / len / list / sum ... 解释器启动时就在 │ │ │ │ ┌─ G Global ─────────────────────────────────────┐ │ │ │ 当前 .py 模块顶层定义的名字（不是「全局程序」）│ │ │ │ CONFIG = {...} │ │ │ │ │ │ │ │ ┌─ E Enclosing ──────────────────────────────┐ │ │ │ │ │ def outer(): │ │ │ │ │ │ total = 0 ◄── 对 inner 来说是 E │ │ │ │ │ │ │ │ │ │ │ │ ┌─ L Local ─────────────────────────┐ │ │ │ │ │ │ │ def inner(): │ │ │ │ │ │ │ │ n = 1 ◄── 本层局部 │ │ │ │ │ │ │ │ print(n) ── 查找路径： │ │ │ │ │ │ │ └──────────────── L→E→G→B ─────────┘ │ │ │ │ │ └──────────────────────────────────────────────┘ │ │ │ └──────────────────────────────────────────────────┘ │ └───────────────────────────────────────────────────────┘ 查 n ：L 命中 → 停 查 total ：L 没有 → E 命中 → 停 查 CONFIG：L 没有 → E 没有 → G 命中 → 停 查 len ：一路到 B 命中 → 停 查 xyz ：四层都没有 → NameError: name 'xyz' is not defined

图里的 Enclosing 层只有在「函数里定义函数」时才存在，这就是 闭包 的基础——内层函数能访问外层函数的局部变量，而且外层函数返回之后这些变量依然活着。闭包的完整讨论留给后续卡片，这里只需要知道它在 LEGB 里占了 E 这一层。

为什么「读全局能读到、写全局报错」

这是 LEGB 最容易让人困惑的地方。同一个全局变量，函数里只读它没问题，一旦加上赋值，连之前的读取都开始报错——而且报的还是个看起来自相矛盾的 UnboundLocalError。

count = 0

def bad():
    print(count)   # UnboundLocalError
    count = count + 1

bad()

根因在于 Python 在编译函数时就决定了每个名字属于哪一层，不是运行到那一行才判断。编译器扫描函数体，发现有 count = ... 这条赋值语句，就把 count 整个函数范围内都标记为局部变量。于是第一行的 print(count) 读的是局部的 count，而它此刻还没有被赋值——报错信息 UnboundLocalError: cannot access local variable 'count' where it is not associated with a value 说的正是这件事。

注意这个判定是整个函数体一次性完成的，赋值语句写在第几行都不影响结论，哪怕它在一个永远不会执行的 if False: 分支里也一样生效。

函数内的写法名字被判定为结果
只有 print(count)沿 LEGB 向外找，命中 Global✅ 正常读到全局值
有 count = count + 1整个函数内都算 Local❌ UnboundLocalError
global count 后再赋值强制指向 Global 层✅ 能改全局，但引入隐式耦合
nonlocal total 后再赋值强制指向最近的 Enclosing 层✅ 能改外层函数的局部变量
lst.append(1)（不赋值）不是赋值，不触发局部判定✅ 能原地改到全局的列表

最后一行是第二节那条分界线在作用域上的回声：lst.append(1) 没有对 lst 这个名字赋值，所以编译器不会把它标成局部，名字照常沿 LEGB 找到全局那个列表，然后原地改掉它。这也意味着「不写 global 就改不到全局」是个错误的安全感——可变对象随时能被改。

global 与 nonlocal：能用，但通常不该用

global x 声明「本函数里的 x 指模块层那个」，nonlocal x 声明「指最近一层外层函数里那个」（找不到会直接报语法错误，它不会新建变量）。两者都能解决前面的报错，但都带来同一个代价：函数的行为不再由参数和返回值完全决定，读代码的人必须去搜索所有修改这个变量的地方才敢下结论。

更现实的问题是测试。依赖全局状态的函数，测试用例之间会互相影响——上一个用例把计数器加到 3，下一个用例的断言就莫名其妙地失败了，而单独跑它又是通过的。这类「单独跑通过、一起跑失败」的测试是最耗时的一类排查。绝大多数情况下，把要改的值作为参数传进来、作为返回值传出去，代码会更短也更好测。

# 不推荐：靠副作用改全局
total = 0
def add(n):
    global total
    total += n

# 推荐：进出都走明面
def add(total, n):
    return total + n

函数里只要对一个名字赋过值，它在整个函数里就是局部的，与赋值写在第几行无关。想读全局就别在函数里给它赋值；真想改全局，先考虑能不能改成参数进、返回值出。

六、返回值、文档字符串与类型注解入门

函数写完，还有三件事决定它好不好用：返回什么、别人怎么知道怎么用、以及工具能不能帮你检查。

「返回多个值」其实是返回一个元组

Python 里 return a, b 看起来像返回两个值，实际上逗号构造了一个元组，函数返回的仍然是单个对象。调用方写 x, y = f() 则是 解包——按位置把元组里的元素依次绑定到左边的名字上。理解这一层能解释两个常见报错：元素个数对不上时报 ValueError: too many values to unpack (expected 2)，而不小心少写了逗号时得到的是完全不同的东西。

def stat(nums):
    return min(nums), max(nums)   # 返回的是一个元组

lo, hi = stat([3, 1, 4])   # 解包
pair  = stat([3, 1, 4])    # 不解包，pair == (1, 4)
lo, hi, extra = stat([3, 1, 4])   # ValueError: not enough values

返回值超过三个时，元组开始变得难读——调用方得数位置。这时更好的选择是返回 dict，或者用 dataclass / NamedTuple 给每个字段起名字，让调用方写 result.max 而不是 result[1]。那些类型的细节属于后面的卡片，此处只需记住「元组适合两三个值，再多就该起名字」这个阈值。

早返回让嵌套变平

把校验失败、边界情况放在函数最前面直接 return，主逻辑就能待在最外层缩进上。对比之下，层层 if 包裹会让真正干活的代码缩进到第四、第五层，读的人得在心里维护一个「现在满足了哪些条件」的栈。

深层嵌套 早返回 ─────────── ───────── def pay(u, amt): def pay(u, amt): if u is not None: if u is None: if u.active: return "no user" if amt > 0: if not u.active: if u.bal >= amt: return "inactive" do_pay() if amt <= 0: else: ... return "bad amount" else: ... if u.bal < amt: else: ... return "insufficient" else: ... do_pay() ◄── 主逻辑在第一层缩进 ▲ 主逻辑在第 5 层缩进 ▲ 每个 else 对应哪个 if 要数 每个失败原因一眼可见， 括号，改一处容易错位 加一个校验就是加三行

docstring：写给使用者，也写给 help()

文档字符串 是紧跟在 def 那一行之后的第一个字符串字面量。位置很关键——写在别的地方就只是一个被丢弃的表达式。放对了位置，它会被存进函数对象的 __doc__，于是 help(f)、IDE 的悬浮提示、自动生成的 API 文档都能读到同一份内容。

def clamp(x, lo, hi):
    """把 x 限制在 [lo, hi] 区间内。

    lo 必须不大于 hi，否则行为未定义。
    """
    return max(lo, min(x, hi))

help(clamp)   # 会打印上面那段

写 docstring 的重点不是复述函数名。get_user 上面写「获取用户」是纯噪音。真正值得写的是调用方无法从签名看出来的东西：单位是什么（毫秒还是秒）、边界怎么处理（空列表返回什么）、会不会抛异常、有没有副作用（会不会改传入的参数）。

类型注解：给人和工具看，运行时不检查

类型注解 是写在参数和返回值上的类型说明，语法是 def f(x: int) -> str。它最需要澄清的一点是：Python 运行时对注解不做任何检查。你标了 x: int，传进去一个字符串，解释器照跑不误，直到某行代码真的对它做了整数运算才会报错——而那个报错的位置往往离传错值的地方很远。

def repeat(s: str, n: int) -> str:
    return s * n

repeat(3, "ab")    # 注解写反了也照样运行，返回 'ababab'
                   # 运行时零检查，报错要等到真正类型不兼容的那一行

那注解的价值在哪？在于把「这个参数该传什么」这条信息从人脑和注释里搬进代码，让 IDE 能做补全和跳转，让 mypy、pyright 这类静态检查工具在提交前就把错误挑出来。上面那个 repeat(3, "ab")，运行时安静通过，静态检查会直接标红。想要运行时真正校验，得靠 pydantic 这类库主动读取注解去做验证，那是另一套机制。

两者不是二选一，它们覆盖的是不同信息：注解说「是什么类型」，docstring 说「是什么意思」。def wait(t: float) 只告诉你传浮点数，秒还是毫秒必须由 docstring 补上。

  • 可变默认值一律写成 None，进函数体再 if x is None: x = []
  • 收到的列表、字典默认当只读；确实要改先 list(x) 复制一份
  • 布尔开关放在 * 右边做成强制关键字，超过三个参数就带名字调用
  • 校验和边界用早返回处理，让主逻辑留在第一层缩进
  • docstring 写单位、边界、异常和副作用，而不是复述函数名
  • 公开函数加类型注解，并在 CI 里跑一遍 mypy 或 pyright
  • 需要的值用参数进、返回值出，替代 global
  • 写 def f(x, acc=[]) 或 def f(x, opts={})
  • 把 time.time()、datetime.now() 当默认值——会永远停在定义那一刻
  • 在函数里原地 sort() 调用方传来的列表却不声明
  • 用 if f: 判断函数结果——少了括号永远为真
  • 把 nums.sort() 的返回值接下来用，那是 None
  • 用 global 在多个函数间传状态，导致测试互相污染
  • 以为写了 x: int 运行时就会拦住字符串

一个函数好不好用，看三件事：返回值能不能直接接着用、不看实现能不能知道怎么调、传错了能不能在上线前被工具拦住。注解和 docstring 就是为后两件事准备的。

Q&A

Python 到底是传值还是传引用？
都不是，准确的说法是「传对象引用」（call by object reference 或 call by sharing）。调用发生时，实参指向的对象没有被复制，函数内的参数名和调用方的变量名指向同一个对象；但这两个名字是彼此独立的，函数内给参数重新赋值只是改了自己那个名字的指向，调用方完全看不见。所以判断「改动能不能传出去」不要去想传值传引用，而要问「我是在给名字重新赋值，还是在修改对象本身」。给名字赋值（x = ...）出不了函数，修改对象（lst.append(...)、d[k] = ...）内外都可见。传不可变对象时之所以感觉像传值，是因为 int、str、tuple 根本没有原地修改的手段。
为什么 def f(x, acc=[]) 会在多次调用之间累积数据？
因为默认值是在 def 语句执行的那一刻求值的，只求一次，结果被存进函数对象的 __defaults__ 元组里。之后每次调用只要没有显式传 acc，绑定上去的就是当初那同一个列表对象。列表是可变的，append 修改的正是它本身，所以状态会一路累积下去。正确写法是把默认值设为 None，在函数体里判断 if acc is None: acc = []——函数体每次调用都会执行，于是每次都拿到新列表。这个坑最危险的地方在于本地单次调用测不出来，它只在同一个进程里反复调用时才暴露，因此常常是上线后才发现。
函数里明明能读到全局变量，为什么加了一行赋值就报 UnboundLocalError？
因为 Python 在编译函数时就静态决定了每个名字属于哪一层作用域，而不是运行到那一行才判断。编译器扫描整个函数体，只要发现对某个名字有赋值语句，就把这个名字在整个函数范围内都标记为局部变量。于是函数里更早的那次读取读的也是局部变量，而它此时还没被赋值，就抛出 UnboundLocalError: cannot access local variable 'count' where it is not associated with a value。注意这个判定与赋值写在第几行无关，哪怕赋值在一个永远不会执行的 if False: 分支里也照样生效。要改全局得写 global count，但更推荐的做法是把值作为参数传进来、结果作为返回值传出去。
lst += [1] 和 lst = lst + [1] 在函数里有什么区别？
区别很大，而且方向相反。lst += [1] 对列表来说等价于 lst.extend([1])，是原地修改那个对象，所以调用方能看到变化。lst = lst + [1] 则先用 + 造出一个全新的列表，再把函数内的名字 lst 指过去，原对象纹丝不动，调用方什么都看不见。这个差异只存在于可变对象上：对元组和字符串，+= 同样只能造新对象，因为它们没有原地修改的能力。写代码时如果这行改动的可见性很关键，建议不要依赖 += 的隐式行为，直接写 extend 或者显式返回新列表，让意图一眼可见。
/ 和 * 这两个参数分隔符分别是干什么的？
/ 左边的参数变成强制位置参数，只能按位置传，写成关键字会报 TypeError: got some positional-only arguments passed as keyword arguments。它的价值是让参数名不成为公开接口的一部分，以后改名不算破坏性变更，标准库大量使用它，比如 len(obj, /)。* 右边的参数变成强制关键字参数，只能写 f(flag=True)，按位置传会报参数个数不匹配。它适合布尔开关和可选配置项，能杜绝 f(x, True, False, True) 这种看不懂的调用，同时以后往中间加参数也不会破坏已有调用。两者都不写时，参数既可以按位置也可以按关键字传，这对两三个参数的小函数完全够用。
为什么 nums.sort() 的返回值是 None？
因为 sort() 是原地排序，它直接修改列表本身，没有 return 语句，而函数不写 return 时 Python 会自动返回 None。这是标准库的一个一致约定：原地修改的方法返回 None，正是为了让你不要把它当成返回新对象的函数来链式调用。需要新列表就用内置的 sorted(nums)，它不动原对象，返回排好序的新列表。同样的模式还有 list.reverse() 对 reversed()、list.append() 也返回 None。如果你写了 nums = nums.sort()，原列表虽然排好了序，但 nums 这个名字已经被改绑到 None，后续操作会抛出带 NoneType 字样的报错——看到这个字样就该往上游找没返回值的函数。
类型注解在运行时会做检查吗？不检查为什么还要写？
不会做任何检查。def f(x: int) 传进去一个字符串，解释器完全不会拦，函数照常执行，直到某行代码对它做了整数才特有的操作才报错，而那个报错位置往往离传错值的地方很远。注解只是被存进 __annotations__ 属性里的元数据。写它的理由有三个：IDE 靠它做补全、跳转和重构；mypy、pyright 这类静态检查工具能在提交或 CI 阶段把类型错误挑出来，成本远低于线上排查；以及它让函数签名自带文档，读代码的人不用去猜参数该传什么。如果确实需要运行时校验，要用 pydantic 这类会主动读取注解并执行验证的库，那是独立于语言本身的一层机制。
函数返回多个值时，用元组还是字典？
return a, b 实际返回的是一个元组，调用方写 x, y = f() 是在做解包。两三个值时元组最合适：写起来短，解包语义清晰，位置对应关系一眼能看明白。超过三个之后元组开始变成负担，调用方必须记住第四个位置是什么，而且以后在中间插入一个返回值会悄无声息地破坏所有调用处。这时应该换成有名字的结构——返回 dict 是最轻的做法，更规范的是用 dataclass 或 NamedTuple，让调用方写 result.max 而不是 result[1]，同时还能享受 IDE 补全和类型检查。另一个信号是：如果你发现自己在解包时写了 _, _, x = f() 忽略掉大半返回值，说明这个函数大概率该拆成两个。
为什么 if is_ready: 这种忘记括号的写法特别难发现？
因为它不报错，只是行为静悄悄地变错。is_ready 不加括号拿到的是函数对象本身，而任何函数对象作为布尔值都恒为 True，所以这个分支永远会进去，看起来程序还在正常运行，只是那个本该拦住流程的判断彻底失效了。类似的还有把函数对象当值打印或写进日志，输出会是 <function is_ready at 0x7f3a1c2d4e00> 这种形式——看到日志或 JSON 里出现这串东西，基本可以确定就是漏了一对括号。防范手段一是给判断类函数起 is_、has_ 开头的名字，看到 if is_xxx: 后面没括号会觉得别扭；二是开启静态检查，ruff 和 pyright 都能识别出「布尔上下文里出现了函数对象」这类可疑写法。
什么时候该用 global 或 nonlocal？
日常业务代码里基本不该用。global x 声明函数内的 x 指模块顶层那个变量，nonlocal x 声明它指最近一层外层函数的局部变量（外层没有这个名字会直接抛语法错误，它不会新建变量）。它们确实能解决「函数内写不了外层变量」的问题，但代价是函数的行为不再由参数和返回值完全决定——读代码的人必须搜遍全文件才能确定这个值会被谁改。更实际的痛点在测试：依赖全局状态的函数会让测试用例互相污染，出现「单独跑通过、一起跑失败」这种最难排查的现象。绝大多数场景改成参数进、返回值出就解决了。真正合理的使用场合很少，主要是模块级的单例初始化、缓存开关这类确实需要跨调用共享的全局配置，而这些通常也有更好的替代方案。想深入理解 Python 的环境与执行模型，可以回看 PY01 · Python 环境与解释器。
