PY13 · 推导式与惰性求值

推导式不是「写得短的 for 循环」，它是一句「我要一个什么样的集合」的声明。写循环时你在描述过程，写推导式时你在描述结果——这个视角差别决定了它什么时候好用、什么时候是滥用。

一、四种推导式与它们的统一结构

推导式指的是用一行表达式直接构造出一个容器的语法，Python 里一共有四种：列表推导式、字典推导式、集合推导式，以及生成器表达式——它长得像推导式，但产出的是一个逐个吐值的迭代器而不是容器。它们四个共享同一套骨架，学会一个就等于学会四个：

输出表达式   for 目标 in 可迭代对象   [ if 条件 ]

外面套什么括号决定了结果是什么类型。方括号给列表，花括号里带冒号给字典、不带冒号给集合，圆括号给生成器。就这一条规则，没有例外。

一张表看清四种写法

写法语法形状结果类型是否惰性典型场合
列表推导式[f(x) for x in it]list否，当场建完整列表结果要多次用、要取长度或索引
字典推导式{k(x): v(x) for x in it}dict否建映射、反转键值、按键过滤
集合推导式{f(x) for x in it}set否去重、做成员判断的候选集
生成器表达式(f(x) for x in it)generator是，被 next() 驱动才算喂给聚合函数、数据量大或未知

表里没有「元组推导式」这一行，这不是遗漏——Python 没有元组推导式。用圆括号写出来的是生成器表达式，这是新手最常见的误解之一，而且它的表现足够诡异：(x*x for x in range(3)) 打印出来是 <generator object ...>，用 len() 会报 TypeError: object of type 'generator' has no len()，第二次遍历则直接是空的。真想要元组，得显式转换：tuple(x*x for x in range(3))。

圆括号被生成器表达式占用，是因为它更值得占用。方括号、花括号本来就是列表和字典/集合的字面量记号，而圆括号在 Python 里从来不是元组的专属记号（元组靠逗号，不靠括号），把它让给一个更有价值的语法是合理的取舍。

括号决定结果类型，逗号决定元组。圆括号里写推导式，得到的是一个还没开始干活的生成器，不是元组。

推导式怎么等价展开成 for 循环

每一个推导式都能机械地翻译成一段 for 循环，翻译规则固定：从左往右读 for 和 if 子句，逐层写成缩进；最后把开头那个输出表达式塞进最内层。看懂这套翻译，后面三节的坑就都变成了「循环本来就是这样」。

[ f(x) for x in it if cond(x) ] │ │ │ │ │ └── 可选筛选：条件为假就跳过这一轮 │ └── 迭代来源：任何可迭代对象 └── 输出表达式：每轮产出一个元素，写在最前面 ─── 列表推导式的等价展开 ─────────────────────── _out = [] for x in it: if cond(x): _out.append(f(x)) result = _out ← 循环跑完才拿到结果，元素全在内存里 ─── 换成圆括号：不是元组，是生成器 ───────────── ( f(x) for x in it if cond(x) ) def _gen(): for x in it: if cond(x): yield f(x) ← 每次 next() 才走到这一步 result = _gen() ← 这一行执行完，循环体一次都还没跑

最后一行的注释是惰性求值的全部含义：把「计算的描述」和「计算的发生」分开，先返回一个描述，等到有人来取值才真正算。列表推导式没有这个分离，等号右边写完，活就全干完了。这个区别在第五节会变成一条明确的选择依据。

字典和集合推导式的展开同理，只是最内层从 append 换成 _out[k] = v 和 _out.add(v)。顺带一个容器细节：字典推导式遇到重复键时后者覆盖前者，不报错也不警告，所以 {len(w): w for w in words} 这种写法多半会静默丢数据。容器四件套那一节（PY03 · 容器四件套）讲过字典的键唯一性，这里只是它在推导式里的一次现身。

二、推导式为什么比等价的 for 循环快

「推导式快因为它是 C 实现的」这句话流传很广，但它经不起追问：for 循环的求值循环也在 C 里，两边跑的都是同一个虚拟机。真正的差别在每一轮要执行多少条字节码，而这件事是可以数出来的。

手写 for 循环往列表里塞元素时，每一轮至少要做三件与业务无关的事：查到 out 这个名字、在它上面查 append 这个属性、发起一次真正的方法调用（建栈帧、传参、返回、丢弃返回值）。列表推导式一条都不做——编译器知道结果列表是自己造的、只有自己能碰，于是把它藏在求值栈上，用一条专用指令 LIST_APPEND 直接完成追加。

for + out.append(x) 的每一轮 列表推导式 [x for x in it] 的每一轮 ────────────────────────────── ────────────────────────────────── FOR_ITER 取下一个 x FOR_ITER 取下一个 x LOAD_FAST out ← 名字查找 STORE_FAST x LOAD_METHOD append ← 属性查找 LOAD_FAST x LOAD_FAST x LIST_APPEND 2 ← 一条指令搞定 CALL 1 ← 方法调用 JUMP_BACKWARD POP_TOP ← 丢弃 None JUMP_BACKWARD 结果列表始终留在求值栈上， 名字查找、属性查找、方法调用全省了 想自己确认：import dis; dis.dis(那个函数)，数一数循环体里的指令条数

省掉的这几条指令单看非常便宜，但它们乘上了循环次数。这也立刻说明了优势的边界：如果循环体本身就在做一次函数调用、一次正则匹配、一次字典查找，那这点固定开销的占比会被稀释到看不见。推导式的速度优势只在循环体足够简单时才成立。

关于上面这些数字 · 它们是同一台机器、同一个 CPython 版本、同一数据量级下互相对比的相对倍数，不是可以跨机器引用的绝对基准。换 CPU、换 Python 版本、换数据规模，倍数都会变，但排序关系相当稳定。要看自己环境里的真实数字，用 timeit 现场测，别抄别人的表。

示例场景：某个日志清洗脚本每批处理 100 万条记录，热点是一行「取字段并转大写」。原写法是 for 循环里 out.append(r["level"].upper())，单批耗时约 620 毫秒；改成列表推导式后降到约 380 毫秒，省下 39%。同一个作者顺手把另一处循环也改成推导式——那处每轮要调用一个自己写的 normalize(r) 函数，耗时从 2.9 秒变成 2.8 秒，只快了 3%，因为每轮 2.7 微秒的函数调用把那 0.2 微秒的固定开销彻底淹没了。两次改动都对，但只有第一次值得改。

推导式省下的是「每轮几条固定指令」，不是「计算本身」。循环体里只要有一次 Python 函数调用，这点便宜就基本归零了——这时候改写法的收益不如改算法。

所以性能不该是选推导式的主要理由。真正的理由是它把「我要构造一个集合」这件事写成了一个表达式：能直接当参数传、能直接赋值、读者一眼看到结果形状而不用在脑子里模拟循环。速度只是顺带的赠品，而且赠品的大小取决于循环体。

三、嵌套与多重 for：顺序和直觉相反吗

一个推导式里可以写多个 for 子句，它们的嵌套顺序是从左到右：最左边的 for 是最外层循环，最右边的是最内层。这和等价 for 循环的书写顺序完全一致，没有任何反转。

那为什么这么多人记成「反的」？因为输出表达式被放在了最前面。读一个多重推导式，视线要先跳过开头的输出表达式，从中间开始读 for 链，读完再回到开头看产出什么——「先看中间，再看两头」。习惯了顺序阅读的人第一次读会觉得别扭，误以为顺序被打乱了。

pairs = [(x, y) for x in "ab" for y in (1, 2)]
# [('a', 1), ('a', 2), ('b', 1), ('b', 2)]

# 等价展开：从左到右，就是外到内
for x in "ab":          # 左边的 for → 外层
    for y in (1, 2):    # 右边的 for → 内层
        out.append((x, y))

由这个顺序还能推出一条常被忽略的规则：右边的子句可以用到左边的变量，反过来不行。[y for row in m for y in row] 是对的，因为 row 在被用到之前已经在左边绑定了；把两个 for 调个位置写成 [y for y in row for row in m]，就会在运行时抛 NameError: name 'row' is not defined——此时 row 还没有值。

多重 for 和嵌套推导式是两件事

这两个说法经常被混着用，但它们产出的东西形状完全不同。多重 for 是一个推导式里串了几个 for 子句，结果是扁平的；嵌套推导式是一个推导式的输出表达式本身又是一个推导式，结果是嵌套的。

m = [[1, 2], [3, 4], [5, 6]] ① 多重 for（展平） ② 嵌套推导式（保形） [ y for row in m for y in row ] [ [ y*2 for y in row ] for row in m ] │ 外层 内层 └─ 内层推导式 ─┘ └ 外层 ┘ │ ▼ ▼ 展开成 展开成 out = [] out = [] for row in m: for row in m: for y in row: inner = [] out.append(y) for y in row: inner.append(y*2) out.append(inner) 结果 [1, 2, 3, 4, 5, 6] 结果 [[2, 4], [6, 8], [10, 12]] len = 6，一层 len = 3，两层 形状被拍平，行的边界丢了 形状保持，每行仍是一个子列表

把两者搞混的后果通常不是报错，而是拿到一个形状不对的结果，然后在下游几十行之外炸开——比如后面写了 result[0][1]，而 result[0] 已经是个整数了，报 TypeError: 'int' object is not subscriptable。这类问题的定位成本远高于写的时候多想两秒。

需求写法结果形状常见误用
把二维展成一维[y for row in m for y in row]扁平，长度 = 元素总数写成嵌套推导式，拿到套了一层的结果
逐行变换但保持行结构[[f(y) for y in row] for row in m]嵌套，长度 = 行数写成多重 for，行边界丢失
求笛卡尔积[(x, y) for x in A for y in B]扁平，长度 = len(A)×len(B)忘了长度是乘法，数据一大就爆内存
只要满足条件的组合[(x, y) for x in A for y in B if p(x, y)]扁平，长度不确定把 if 写在错误的位置，筛错了层
三层以上展平改用 itertools.chain.from_iterable 或写循环—硬塞进一行，可读性崩掉

if 子句的位置也跟着这个顺序走：它筛的是它左边所有 for 已经绑定好的那一轮。[(x, y) for x in A if x > 0 for y in B] 里那个 if 在外层就把 x 过滤掉了，内层循环压根不会为负数的 x 跑；挪到最后写成 for y in B if x > 0 则是在内层逐个判断——结果一样，但内层白跑了很多轮。数据量大时这是个真实的性能差别。

多个 for 从左到右就是从外到内，唯一别扭的是输出表达式被提到了最前面。读的时候从中间的 for 链读起，读完再回头看产出什么。

四、作用域：推导式有自己的领地

推导式在 Python 3 里有自己的作用域，循环变量不会泄漏到外层。这条规则今天看起来理所当然，但它是 Python 3 的一个破坏性修复：Python 2 里列表推导式的变量会留在外层，[x for x in range(3)] 执行完，外面的 x 就被悄悄改成了 2。无数「循环跑完变量被覆盖」的诡异 bug 出自这里，Python 3 把它改掉了，代价是这段行为不向后兼容。

有自己的作用域不等于与外界隔绝。推导式能读到外层的变量——这就是闭包捕获，即内层函数记住外层作用域里那个变量的能力。能读不能写，是这一节所有现象的总纲。

n = 10 data = [1, 2, 3] result = [ x * n for x in data if x != 2 ] ───────────────────────────────────────────── │ │ │ └── 最外层的可迭代对象 data │ 在【外层作用域】就地求值， │ 然后作为参数交给推导式 │ └── x 和 n 的解析发生在【推导式自己的作用域】里： x 是它的局部变量 n 找不到，就顺着闭包链往外找 → 拿到 10 推导式结束后 ┌──────────────────────────────────────────┐ │ print(result) → [10, 30] ✓ │ │ print(n) → 10 ✓ 没被动过 │ │ print(x) → NameError ✓ 不泄漏 │ └──────────────────────────────────────────┘ Python 2 里最后一行会打印 3，这是当年的坑 例外：class 体的作用域不参与闭包链 class C: vals = [1, 2, 3] doubled = [v * 2 for v in vals] ✓ vals 是最外层可迭代对象 scaled = [v * len(vals) for v in vals] ✗ NameError: 'vals'

最隐蔽的那个坑：捕获的是变量，不是值

表格最后两行指向同一个陷阱。闭包捕获的是变量本身而不是它当时的值，所以在推导式里造一批 lambda 或者一个生成器，等到之后再调用时，它们读到的是那个变量最终的值。这叫延迟绑定——名字的解析被推迟到了调用时刻，而不是定义时刻。

fs = [lambda: i for i in range(5)]
print([f() for f in fs])          # [4, 4, 4, 4, 4]  ← 全是最后一个

fs = [lambda i=i: i for i in range(5)]
print([f() for f in fs])          # [0, 1, 2, 3, 4]  ← 默认参数当场绑定

修法就是第二段那一行：把 i 写成默认参数。默认参数在函数定义时求值一次并存下来，于是每个 lambda 都拿到了属于自己那一轮的值。这个技巧的代价是给函数多了一个不该被外部传的参数，所以更正式的场合会用 functools.partial(f, i) 表达同一件事。闭包直觉在函数那一节（PY05 · 函数入门与参数传递）已经建立过，这里只是它在推导式里最容易被忽略的一次现身。

示例场景：一个批处理任务要给 8 个分片各注册一个回调，作者写了 handlers = [lambda: process(shard) for shard in range(8)]，随后把 8 个回调丢进线程池。上线后监控显示分片 7 被处理了 8 次、分片 0 到 6 一次都没跑，7 个分片的数据整天缺失，而日志里没有任何异常——因为代码本身完全合法。定位花了约 4 小时，修复只改了一处：把 lambda: 改成 lambda shard=shard:，1 行。这类 bug 的特征是「不报错、结果错、错得整齐」，一旦看到「N 个任务全部作用在最后一个对象上」，先怀疑延迟绑定。

推导式的变量不会漏出去，但它能被别人记住。凡是在推导式里创建「以后才调用」的东西（lambda、生成器、偏函数），就要问一句：它记住的是值还是变量？要值就用默认参数当场钉死。

五、什么时候该用生成器表达式而不是列表推导

这个选择不该凭手感，它有三个可以逐条回答的判据：结果会不会被完整消费、会不会被多次遍历、数据量有多大。三个问题答完，答案基本唯一。

只把结果喂给 sum、any、all、max、min、str.join、sorted 这类一次性吃完就走的聚合函数时，用生成器表达式。中间那个列表根本没人要，建它纯属浪费——峰值内存跟着数据量线性涨，而收益是零。反过来，需要多次遍历、需要 len()、需要索引或切片、需要把结果返回给别人长期持有，就必须用列表：生成器只能走一遍，走完就空了，第二次遍历静默地什么都不给，这是比报错更难查的失败方式。

sum([x*x for x in range(10_000_000)]) ← 列表推导：先攒，再算 ┌──────────────────────────────────────────────────────────┐ │ range ──► 算 1000 万个平方 ──► 全部塞进一个 list ──► sum │ │ ▲ │ │ └── 峰值内存跟数据量成正比│ └──────────────────────────────────────────────────────────┘ sum(x*x for x in range(10_000_000)) ← 生成器：边算边吃 ┌──────────────────────────────────────────────────────────┐ │ range ──► 算一个 ──► 交给 sum ──► 丢掉 ──► 算下一个 ... │ │ │ │ 同一时刻内存里只有一个元素，峰值内存与数据量【脱钩】 │ └──────────────────────────────────────────────────────────┘ any(is_bad(r) for r in records) ← 惰性还带来短路 记录 1 ─► False ─► 继续 记录 2 ─► False ─► 继续 记录 3 ─► True ─► any 立刻返回 True，后面 999 万条【一条都不读】 换成 any([is_bad(r) for r in records]) 呢？ 1000 万条全部算完、全部装进列表，然后 any 才开始看第一个 —— 短路失效

数据量大、未知，或来自文件/网络流生成器表达式峰值内存与数据量脱钩
结果要遍历两次以上列表推导式生成器走完即空，第二次静默返回空
要 len()、索引、切片、排序后复用列表推导式生成器不支持这些操作，会抛 TypeError
结果要 return 给调用方长期持有列表推导式把惰性对象交出去，异常和资源生命周期都不可控
元素少（几十、几百个）列表推导式内存差别可以忽略，可读性和可调试性更值钱
需要立刻知道构造过程有没有出错列表推导式生成器的异常延后到消费时才抛，栈回溯离现场很远

示例场景：一个统计任务要算 1000 万条记录的字段总和。原写法 sum([r.size for r in load()])，进程峰值常驻内存约 780 MB，在 1 GB 内存限额的容器里跑到第 6 分钟被 OOM Killer 杀掉，退出码 137，日志里没有任何 Python traceback（因为进程是被信号杀的，不是抛异常）。把方括号删掉改成 sum(r.size for r in load())，峰值降到约 60 MB，任务在 5 分 40 秒内正常完成。修改量是两个字符，收益是这个任务能不能跑完的区别。

顺带一个语法细节：生成器表达式作为函数的唯一参数时，可以省掉自己那层圆括号，写 sum(x*x for x in it) 而不必写 sum((x*x for x in it))。但只要还有第二个参数，括号就必须补回来——max(x*x for x in it, default=0) 是 SyntaxError，得写成 max((x*x for x in it), default=0)。这条规则解释了为什么有些地方看起来「少了一层括号也能跑」。

还有一个容易被忽略的惰性副作用：生成器里的循环体在 next() 时才执行，所以它读到的外层变量是消费时刻的值，而不是定义时刻的。定义完生成器再改一下被引用的变量，结果会跟着变——这是第四节延迟绑定的同一个机制换了个马甲。迭代器与生成器那一节（PY12）讲过生成器的暂停恢复语义，这里只把它当成选型依据来用。

只吃一遍、量大、可能提前有答案，用圆括号；要反复用、要长度、要索引，用方括号。删掉或加上一对方括号是几乎零成本的修改，但在大数据量上是能不能跑完的区别。

六、可读性红线：推导式什么时候该拆回循环

推导式的价值来自「一眼看清结果形状」。一旦读者必须在脑子里模拟执行才能弄明白它产出什么，这个价值就已经付掉了，剩下的只有紧凑本身——而紧凑不是目的。下面这几条是相当可靠的越线信号，命中任何一条就该考虑拆开。

越线信号为什么算过线怎么改
三层及以上 for 子句读者要同时记住三个变量的绑定关系拆成外层 for + 内层推导式
两个以上 if 子句筛选逻辑分散在不同层，难判断谁筛谁抽成一个具名谓词函数 if keep(x)
输出表达式是嵌套三元式a if p else b if q else c 挤在开头，最难读的部分在最不显眼处抽成一个具名函数，推导式里只写调用
整行超过一屏宽（约 90 字符）要横向滚动或折行才能读完先试着分行缩进，仍然不清楚就拆成循环
循环体有副作用（改外部状态、写文件、发请求）推导式的语义是「产出一个集合」，用它跑副作用是滥用写成普通 for 循环
需要中途 break推导式没有提前终止的语法for + break，或 itertools.takewhile
需要 try/except 处理单个元素推导式里放不进语句，异常会终止整个构造抽成带 try 的函数，推导式里调用它

副作用那一条值得多说两句

把推导式当循环用是最常见的滥用形式：[print(x) for x in items] 或者 [save(x) for x in items]。它能跑，但代价有三层。语义上你在骗读者——写成推导式意味着「我要一个集合」，而这个集合被立刻丢掉了。内存上你为了丢掉它先把它建了出来，一百万条记录就是一百万个 None。工具上静态检查器会警告「表达式结果未使用」，于是你要么忍受警告，要么加注释屏蔽它。想要循环就写 for，多两个字符，少三个问题。

# 想提前停下来，但推导式没有这个语法
first_bad = [r for r in stream if r.bad][0]   # 整个流读完才取第一个
                                              # 空结果还会抛 IndexError

终止条件简单就交给 itertools.takewhile，它在第一个不满足条件的元素处就停；条件复杂、或者停下来时还要做别的事，就老实写循环。

from itertools import takewhile
head = list(takewhile(lambda r: r.ok, stream))   # 遇到第一个不 ok 即停

for r in stream:              # 复杂终止条件：写循环，清楚且可调试
    if r.bad:
        first_bad = r
        break

调试代价也是真实成本

推导式挤在一行里，带来三个具体的不便。你没法在中间插一句 print 看某一轮的中间值——想看就得先拆开。异常的栈回溯指向整行，报 TypeError: unsupported operand type(s) 时你知道这一行有问题，但不知道是哪个元素、第几轮出的问题。断点也只能打在整行上，单步进去每一轮都要停一次。控制流那一节（PY04 · 控制流与真值判断）里那些正常的调试手段，在推导式里大半用不上。

一个实用的折中：写的时候先写成普通 for 循环，跑通、调好，最后再判断要不要压成推导式。压不下去（因为有 break、有 try、有副作用），那本来就不该压。压下去之后自己读一遍还得停顿超过三秒，也别压。

  • 只喂给 sum/any/join 等聚合函数时，用生成器表达式，删掉那对方括号
  • 多重 for 按从左到右 = 从外到内理解，读的时候先看中间的 for 链
  • 推导式里造 lambda 或生成器，用 lambda x=x: 把当轮的值当场钉死
  • 筛选条件复杂就抽成具名谓词，推导式里只留 if keep(x)
  • 要元组就显式写 tuple(...)，别指望圆括号
  • 先写循环调通，最后再决定要不要压成推导式
  • 用 [print(x) for x in items] 这类写法跑副作用，白建一个要丢掉的列表
  • 以为圆括号里的推导式是元组，然后对它调 len()
  • 把生成器表达式当列表反复遍历——第二次会静默返回空
  • 为了「快一点」把带函数调用的循环改成推导式，实测往往只差个位数百分比
  • 三层 for 加两个 if 硬塞进一行，还配上嵌套三元输出表达式
  • 在 class 体内的推导式里引用类属性（除最外层可迭代对象），会 NameError

推导式是用来「声明一个集合长什么样」的。当你发现自己在用它「跑一段流程」，或者读者必须模拟执行才能看懂结果形状时，它就已经不该是推导式了。

Q&A

为什么没有「元组推导式」？圆括号里写推导式得到的是什么？
得到的是生成器表达式，一个惰性的迭代器，不是元组。可以从两个角度理解这个设计。语法上，圆括号在 Python 里从来不是元组的专属记号——元组是靠逗号构成的，1, 2 就已经是元组了，括号只是用来消除歧义，所以把圆括号让给生成器表达式并没有抢走谁的地盘。设计上，生成器表达式的价值远大于一个「元组推导式」：后者能被 tuple(...) 一行替代，前者提供的是惰性和短路，没有替代品。实际影响是三个容易撞上的现象：print 出来是 <generator object>、len() 报 TypeError、第二次遍历为空。想要元组就显式写 tuple(x*x for x in it)。
推导式真的比 for 循环快吗？快多少值得改代码？
在循环体足够简单时确实快，来源不是「C 实现」这种含糊说法，而是可以数出来的字节码差异：手写循环每轮要查 out 这个名字、查 append 这个属性、发起一次方法调用，列表推导式用一条 LIST_APPEND 指令全省了。同机同量级的相对比较里，简单循环体上推导式大约是 for+append 的 1.6 到 1.9 倍快，这个倍数会随机器和版本变，但排序稳定。关键是边界：一旦循环体里有一次 Python 函数调用，每轮几百纳秒的固定开销就被几微秒的调用开销淹没，差距会收窄到个位数百分比。所以别把性能当成选推导式的主要理由，可读性和「结果是一个表达式」才是。真要优化就先测，看看时间到底花在哪一层。
多重 for 的嵌套顺序到底是怎样的？为什么很多人记成反的？
从左到右就是从外到内，和等价 for 循环的书写顺序完全一致，没有反转。[(x, y) for x in A for y in B] 里 A 是外层、B 是内层，每个 x 会配上全部的 y。之所以有「反的」这种印象，是因为输出表达式被提到了最前面，读者习惯从头顺读，一开头就撞上产出物，于是对后面的顺序也产生怀疑。正确的读法是先跳过开头，从中间的 for 链读起，读完再回头看产出什么。这个顺序还带出一条规则：右边的子句能引用左边已绑定的变量，反过来会在运行时报 NameError，因为那个名字此刻还没有值。
为什么 [lambda: i for i in range(5)] 里的函数全部返回 4？
因为闭包捕获的是变量而不是它当时的值。五个 lambda 都记住了同一个 i，推导式跑完 i 的最终值是 4，所以之后无论调用哪一个都读到 4。注意这不是推导式独有的行为，普通 for 循环里造 lambda 一样如此，只是推导式让这种写法变得太顺手。修法是用默认参数当场绑定：[lambda i=i: i for i in range(5)]，默认参数在函数定义时求值一次并存下来，于是每个函数拿到属于自己那一轮的值。更正式的写法是 functools.partial，表达的是同一件事但不会给函数留下一个不该被外部传的参数。这类 bug 的特征是不报错、结果错、而且错得很整齐——N 个任务全部作用在最后一个对象上。
为什么 class 体里的推导式引用类属性会报 NameError？
因为类作用域不参与闭包链。推导式有自己的作用域，它查找外部名字时会沿着闭包链往外找函数作用域、模块作用域、内置作用域，但会跳过中间的类作用域——这是 Python 作用域规则里一个刻意的设计，避免类属性意外遮蔽同名的全局变量。所以 class C: vals = [1,2,3]; scaled = [v * len(vals) for v in vals] 会报 NameError: name 'vals' is not defined。有趣的是同一行里第一个 vals 是好的：最外层的可迭代对象在外层作用域就地求值，然后作为参数传进推导式，所以它看得见类属性。绕过办法是把需要的值先存进一个局部名字，或者干脆写成普通 for 循环、或挪到 __init__ 里去。
生成器表达式什么时候反而不如列表推导式？
至少四种情况。一是结果要遍历两次以上：生成器走完即空，第二次遍历会静默返回空，这是比报错难查得多的失败方式。二是需要 len()、索引、切片：生成器不支持，会抛 TypeError。三是数据量本来就小：几十几百个元素的内存差别可以忽略，而列表在调试时能直接打印查看，生成器打印出来只有一个对象地址。四是要把结果返回给调用方长期持有：惰性对象把「计算什么时候发生」交给了别人，异常会延后到消费时才抛，栈回溯离出错现场很远，如果生成器还持有着文件句柄，资源的生命周期也变得难以推理。另外纯性能上，要完整列表时绕生成器再 list() 一遍反而慢一到五成，因为多了每轮的挂起恢复。
推导式里能写 try/except 或者 break 吗？不能的话怎么办？
都不能，因为推导式是表达式，而 try 和 break 是语句，语法上没有它们的位置。异常处理的办法是把逻辑抽成一个自己带 try 的函数，推导式里只写调用，比如让 safe_parse(s) 失败时返回 None，然后 [r for s in items if (r := safe_parse(s)) is not None]。提前终止有两条路：条件简单就用 itertools.takewhile，它在第一个不满足条件的元素处停下；条件复杂或者要在停下时做别的事，就老实写 for 循环加 break。要特别避免 [r for r in stream if r.bad][0] 这种写法——它把整个流读完才取第一个，既慢又可能在空结果时抛 IndexError。
推导式里用 := 绑定的变量会不会泄漏到外层？
会，而且这是 PEP 572 特意设计的，不是漏洞。推导式的普通循环变量不泄漏，但赋值表达式 := 绑定的名字会留在包含这个推导式的那个作用域里，正是为了让你能把中间结果捞出来复用。典型用法是避免重复计算：[y for x in data if (y := f(x)) > 0] 里 f(x) 只算了一次，既用于判断又用于输出，而不用写成 [f(x) for x in data if f(x) > 0] 那样算两遍。代价是这个名字确实污染了外层，循环跑完它保留着最后一次的值，所以别取 x、tmp 这种容易撞车的名字。另外在 class 体里和作为参数默认值的推导式里用 := 是被明确禁止的，会直接报 SyntaxError。
