锁文件回答的是「装哪些包的哪些版本」，镜像回答的是「这些包装在哪个操作系统、哪个 C 库、哪个解释器上」。前者是清单，后者是地基。只交付清单不交付地基，同一份锁文件在两台机器上仍然可能装出两个行为不同的东西。

一、镜像是可复现的最后一环

把锁文件提交进仓库之后，很多人会觉得可复现这件事已经做完了：版本都钉死了，还能出什么岔子。实际上锁文件只钉住了要装什么，没有钉住在什么上面装。而后者足以让两次「完全一样」的安装产出不一样的结果。

锁文件管不到的三件事

第一件是源码分发包。锁文件里写着某个包的 2.9.1 版，但如果当前平台没有匹配的预编译轮子，安装器会退回去下载源码包，在本机现场编译。编译用的是本机的编译器版本、本机的头文件、本机的系统库——这些东西锁文件一个字都没提。同一行锁记录，在一台装了 OpenSSL 3 的机器和一台装了 OpenSSL 1.1 的机器上，可以链接出两个不同的扩展模块。

第二件是轮子的平台标签。就算拿到了预编译轮子，Linux 上的轮子文件名里带着 manylinux_2_17 这类标记，含义是「要求 C 库版本不低于某个基线」。它保证的是能装上、能加载，不保证底下那份 C 库和你同事机器上的是同一个版本。涉及到时区数据、字符集、加密算法后端这些由系统库提供的东西时，差异会直接冒到业务行为上。

第三件是解释器本身。锁文件通常只声明一个版本区间，比如「3.12 以上」。3.12.3 和 3.12.11 之间隔着十几个补丁版本，其中包含过安全修复和行为修正。环境与解释器那一卡（PY01）讲过「先搞清楚谁在执行」，到了生产环境，这个「谁」必须精确到补丁号。

锁文件是配料表，镜像是那家厨房。配料表一样、厨房不一样，端出来的东西就可能不一样。容器化不是为了赶时髦，它是把厨房也一并交付出去的唯一实用手段。

哪一层固定了什么

把整条链路摊开看，就能看清每一层各自的职责，以及缺了哪一层会漏出什么不确定性。

层固定了什么靠什么钉住不钉住会漏出什么
宿主内核系统调用接口不由镜像固定，靠兼容性保证极少出问题，但太老的内核会让新镜像跑不起来
基础镜像发行版、C 库、系统库（加密、压缩、时区）镜像标签，最好到摘要加密后端、时区数据、字符集行为随宿主漂移
解释器CPython 的精确补丁版本与构建选项基础镜像标签里的版本号补丁级行为差异，自由线程与默认构建混淆
依赖每个包的版本与哈希锁文件 + 严格锁定安装次版本悄悄升级，传递依赖飘动
应用源码业务逻辑本身提交哈希「线上跑的到底是哪次提交」说不清
一个镜像自底向上固定了什么 ──────────────────────────────────────────────── ┌──────────────────────────────────────────┐ │ 应用源码 ← git commit 钉住 │ 每天变几十次 ├──────────────────────────────────────────┤ │ 第三方依赖 ← 锁文件钉住 │ 每周变几次 ├──────────────────────────────────────────┤ │ 解释器 3.12.11 ← 基础镜像标签钉住 │ 每月变一次 ├──────────────────────────────────────────┤ │ 系统库 / C 库 ← 基础镜像标签钉住 │ 很少变 ├──────────────────────────────────────────┤ │ 发行版根文件系统 ← 基础镜像摘要钉住 │ 很少变 └──────────────────────────────────────────┘ ▲ └── 只有锁文件时，虚线以下全是「跟着宿主走」 换台机器构建，下面四层可能全都不一样

基础镜像标签必须写死到版本

上一节说的地基，在 Dockerfile 里就是第一行 FROM。这一行的精度直接决定了整个镜像的可复现程度，而默认写法几乎都不够精确。

写法精度会在什么时候变适合
python / python:3几乎没有大版本一发布就跟着跳本地随手试，绝不能进生产
python:3.12只锁到次版本每次补丁发布仍不够，补丁版本会静默变化
python:3.12.11-slim-bookworm版本 + 变体 + 发行版都写死同名标签被重新构建以打系统安全补丁日常推荐的下限
python:3.12.11-slim-bookworm@sha256:…内容寻址，完全不可变永不变，除非你自己改合规、审计、需要逐字节可复现的场景

第三行那个「同名标签会被重新构建」值得展开一句：官方镜像会定期重新打包同一个标签，把底层发行版的安全补丁带进去。这通常是好事——你不用改一个字就拿到了安全修复——但它意味着完全一样的 Dockerfile 在两个月后构建出的镜像不是同一个。要的是安全更新就用全限定标签，要的是逐字节一致就用摘要固定，并配一个定期更新摘要的流程。两者的差别是取舍，不是对错。

二、层缓存与构建顺序：顺序错了，构建时间翻十倍

镜像不是一个大文件，而是一叠只读层，Dockerfile 里的每条构建指令生成一层。这个结构带来一条铁律：层缓存按顺序命中，一旦某一层失效，它之后的所有层全部重建，无论那些层的内容有没有变。

缓存是否命中，判断依据是「父层是否相同」加上「这条指令是否相同」。对 COPY 和 ADD 来说还要额外比对被拷贝文件的内容校验和——文件内容变了，这一层就重来。

两种顺序，天壤之别

项目里两类东西的变化频率差了两个数量级：源码每天改几十次，依赖声明可能几周才动一次。把它们的拷贝顺序放反，等于让最慢的那一步跟着最快的变化走。

改一行业务代码之后，重新构建会发生什么 ═══════════════════════════════════════════════════════════ 顺序 A（正确）：先拷依赖声明 → 装依赖 → 再拷源码 ┌────────────────────────────────┬──────────┬─────────┐ │ 指令 │ 缓存 │ 耗时 │ ├────────────────────────────────┼──────────┼─────────┤ │ FROM python:3.12.11-slim │ 命中 ✔ │ 0s │ │ COPY pyproject.toml uv.lock . │ 命中 ✔ │ 0s │ ← 没改，命中 │ RUN uv sync --locked │ 命中 ✔ │ 0s │ ← 整段跳过 │ COPY . . │ 失效 ✘ │ 3s │ ← 只有这里重来 │ CMD ... │ 失效 ✘ │ 0s │ └────────────────────────────────┴──────────┴─────────┘ 总计 约 3 秒 顺序 B（错误）：先拷全部源码 → 再装依赖 ┌────────────────────────────────┬──────────┬─────────┐ │ FROM python:3.12.11-slim │ 命中 ✔ │ 0s │ │ COPY . . │ 失效 ✘ │ 3s │ ← 源码变了 │ RUN uv sync --locked │ 失效 ✘ │ 数分钟 │ ← 被迫全量重装 │ CMD ... │ 失效 ✘ │ 0s │ └────────────────────────────────┴──────────┴─────────┘ 改一行注释也要把所有依赖重装一遍

顺序 A 的写法只有一个要求：装依赖那一步只能看见依赖声明与锁文件，看不见源码。所以拷贝要分两次。

# 第一次拷贝：只有依赖声明，变化极少
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-install-project

# 第二次拷贝：源码，每天都变
COPY . .
RUN uv sync --locked

事故复盘：某内部服务的镜像构建耗时中位数长期稳定在 2 分 40 秒，某次重构后涨到 14 分 10 秒，CI 队列开始积压，发布窗口从半小时拖到两小时。查 Dockerfile 的 diff 只有一处改动：有人为了「让文件操作看起来集中一点」，把 COPY . . 从装依赖之后挪到了之前。于是每次改一行代码，那一层的校验和都变，后面装依赖的层全部失效，六十多个依赖每次重装。按当时每天 22 次构建算，每次多花 11.5 分钟，每天白烧掉约 4.2 小时的构建机时；从改动合入到被发现隔了 9 个工作日，累计浪费约 38 小时，接近 5 个人日。修复就是把那一行挪回去，缓存命中率从 12% 回到 91%，耗时回到 2 分 50 秒。教训不是「有人粗心」，而是构建耗时本身没有被当成一个要盯的指标，否则第一天就该报警。

构建上下文：被忽略的那一大坨

执行构建时，客户端会先把构建上下文——通常就是当前目录的全部内容——打包送给构建器，然后才开始执行指令。这一步发生在任何缓存判断之前，所以目录里有什么，都会实打实地被传一遍。

一个开发了几个月的项目，目录里往往躺着本地虚拟环境、测试产出、数据样本、模型权重、缓存目录。它们加起来经常比源码大两三个数量级。不排除的后果有三层：构建每次都要多传一大堆无关文件；COPY . . 会把它们原样烙进镜像层；更糟的是本地的 .env 里那些密钥也会一起进去。

该排除的东西不排除的代价
.venv/、venv/体积巨大，且里面写死了本机绝对路径，进了镜像反而会干扰运行时环境
.git/历史全在里面，体积可观，还会把历史上删过的敏感文件一并带走
__pycache__/、*.pyc宿主编译的字节码，和镜像里的解释器未必匹配
.env、*.pem、credentials*密钥直接进镜像层，删都删不干净（见第五节）
data/、*.ckpt、*.parquet数据与权重应当运行时挂载，打进镜像会让拉取时间失控
tests/、docs/、notebooks/不影响正确性，但白白增大体积与攻击面

.dockerignore 不是「顺手优化」，它是安全边界的一部分。判断标准很简单：这个文件你愿不愿意让任何能拉到这个镜像的人看到？不愿意，就必须排除。

一个实用的写法是先全部排除，再显式放行——这样新增的临时目录默认进不去，不用每次记得补一条。

# .dockerignore：默认全排除，只放行需要的
*
!pyproject.toml
!uv.lock
!src/
!README.md

三、基础镜像选型：小不等于好

选基础镜像时，绝大多数人第一反应是挑最小的那个，于是选了 Alpine。这个选择在 Python 项目里经常是错的，原因和体积无关，和 C 库有关。

Alpine 的问题不是小，是换了 C 库

常见的 Linux 发行版用 glibc，Alpine 用的是 musl——一个更小、更严格的 C 库实现。这两者的二进制接口不兼容，因此为 glibc 编译的轮子在 Alpine 上不能用。

Python 打包生态对这件事的处理方式是给轮子打不同的平台标签：面向 glibc 的叫 manylinux，面向 musl 的叫 musllinux。问题在于，绝大多数带 C 扩展的包都会发布 manylinux 轮子，但发布 musllinux 轮子的要少得多。装不到轮子，安装器就退回源码编译——这正是第一节说的那条最坏路径。

pip / uv 在 Linux 上装一个带 C 扩展的包 ═══════════════════════════════════════════════════════════ 需要安装 somepkg 2.9.1 │ ▼ 当前平台标签是什么？ │ ┌─────────────────┴──────────────────┐ ▼ ▼ manylinux（glibc） musllinux（musl / Alpine） │ │ ▼ ▼ 仓库里几乎都有轮子 仓库里常常没有轮子 │ │ ▼ ▼ 解压即用，几秒钟 下载源码包，现场编译 ✔ 快 ✔ 稳 需要 gcc、make、头文件 科学计算类还要 BLAS / Fortran │ ▼ 构建慢几倍到几十倍 缺一个头文件就整段失败 ✘ 镜像小了，构建可靠性没了

这个代价对不同项目差别极大。如果依赖只有几个纯 Python 的 Web 框架，Alpine 基本无感；一旦依赖里出现数值计算、图像处理、数据库驱动这类包，构建时间可能从一分钟涨到十几分钟，而且随时会因为某个系统头文件缺失而失败。更讽刺的是，为了编译而装进去的工具链本身就有几百兆，最后镜像未必真的更小。

基础镜像体积量级（参考）轮子可用性什么时候真的该选它
完整版（如 python:3.12.11）接近 1 GB 量级最好，还自带完整工具链需要现场编译、或做构建阶段的基底
精简版（-slim）百兆量级和完整版一样好（同为 glibc）默认答案，兼顾体积与可靠性
Alpine（-alpine）数十兆量级差，很多包只能现场编译依赖全是纯 Python，且体积是硬指标
Distroless 类百兆量级不适用（只放运行产物）安全要求高，且已经在用多阶段构建

数据截止 2026-06 · 上表体积仅为量级参考，官方镜像的实际大小随发行版与解释器版本持续变化，请以 docker images 的实测结果为准，不要把这里的数字当作依据写进文档。

选基础镜像先问一句：我的依赖里有没有 C 扩展？有，就用 slim；只有纯 Python 且体积真的卡脖子，才考虑 Alpine。为省几十兆换来一个随机失败的构建，是笔亏本买卖。

顺带说一句 slim 的含义：它是同一个发行版的精简变体，去掉了文档、部分开发头文件和不常用的工具，C 库还是 glibc，所以轮子照常可用。代价是装某些需要系统库的包时要自己补一两个运行时包，这属于一次性成本，加一行安装指令就解决，和 Alpine 那种「整条编译路径都要自己扛」完全不是一个量级。

四、多阶段构建：把编译期的东西留在门外

就算选了 slim，构建过程里仍然可能需要编译器、头文件、下载缓存这些东西。它们只在装依赖时有用，运行时一点用都没有，却会永久留在镜像层里——因为删除文件的那一层并不会让文件消失，只是在上层把它标记为不可见，底下那一层的数据还在。

多阶段构建解决的正是这个问题：在一个 Dockerfile 里声明多个 FROM 阶段，前面的阶段随便装什么都行，最后一个阶段只从前面的阶段里挑选需要的产物拷过来。没被拷的东西完全不进入最终镜像，连历史都不留。

单阶段 vs 多阶段 ═══════════════════════════════════════════════════════════ 单阶段：装了就甩不掉 FROM slim RUN apt install gcc ... ← 几百兆，进了层 RUN uv sync ← 缓存目录，进了层 RUN apt remove gcc ← 只是标记不可见，数据还在底层 最终镜像 = 全部历史之和 多阶段：只搬走产物 ┌── builder 阶段 ─────────────────┐ │ FROM slim AS builder │ │ apt install gcc 头文件 ... │ ← 随便装，不心疼 │ uv sync --locked │ │ 产出：/app/.venv │ └─────────────┬───────────────────┘ │ COPY --from=builder /app/.venv /app/.venv ▼ 只搬这一个目录 ┌── 运行阶段 ─────────────────────┐ │ FROM slim │ 干净的底 │ 只有 .venv + 源码 + 运行时依赖 │ └─────────────────────────────────┘ 编译器、缓存、中间产物：一个字节都没进来

把虚拟环境整体搬过去：做法与两个坑

Python 项目里最常用的搬运方式，就是让构建阶段生成一个虚拟环境目录，然后整个拷到运行阶段。它简单可靠，但有两个前提必须满足，否则拷过去是坏的。

第一个坑是路径必须完全一致。虚拟环境里的 pyvenv.cfg 和那些命令行入口脚本里写的都是绝对路径（PY01 讲过虚拟环境本质上就是一组路径约定）。构建阶段建在 /app/.venv，运行阶段就必须还放在 /app/.venv；挪个位置，入口脚本里的解释器路径就指空了。

第二个坑是解释器版本必须匹配。虚拟环境里的 site-packages 路径带着版本号，编译出的扩展模块文件名也带着版本标记。构建阶段用 3.12、运行阶段用 3.13，拷过去的包根本不在搜索路径上，报错是干脆利落的「模块找不到」，和真正的原因看着毫无关系。可靠的做法是两个阶段的 FROM 写同一个基础镜像标签，让它们没有机会不一致。

搬运方式怎么做优点要注意
整体拷虚拟环境构建阶段建 /app/.venv，运行阶段 COPY --from最直观，工具链支持最好路径与解释器版本必须两阶段一致
装进系统环境容器本身已是隔离单元，直接装到系统 Python少一层目录，路径问题消失与基础镜像自带的包可能打架
先打成轮子再装构建阶段产出 .whl，运行阶段安装产物干净，可复用于多个镜像步骤多，运行阶段仍需安装器

uv 在容器里的几个要点

uv 官方给了容器集成的推荐写法，下面几条是和本节主题直接相关的。命令与参数以 uv 官方文档的容器集成页为准。

用严格锁定模式安装。uv sync --locked 会断言锁文件与 pyproject.toml 一致，不一致直接失败而不是就地更新锁文件。容器构建里这一点很关键：你要的是「照着锁文件装」，不是「顺手把锁文件改了」——后者的改动还留在容器里，根本传不回仓库。工作区项目由于校验需要全部成员的声明文件，首次同步要用 --frozen，等成员都拷进来之后再用 --locked 校验。

依赖与项目分两层装。--no-install-project 让这一步只装依赖、不装项目自身，配合上一节的拷贝顺序，就能把「依赖层」和「源码层」彻底分开。

WORKDIR /app
# 只装依赖：挂载锁文件与声明，不落进镜像层
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv uv sync --locked

缓存要么挂载，要么不留。上面那个 --mount=type=cache 是构建器提供的缓存挂载：目录在构建时可读写、跨构建保留，但不会成为镜像层的一部分，既加速又不增肥。用了缓存挂载时通常要配 UV_LINK_MODE=copy，因为缓存和目标环境不在同一个文件系统上，硬链接不可用，设成拷贝模式可以消掉那条警告。如果不用缓存挂载，就必须走另一条路：加 --no-cache（或设 UV_NO_CACHE），让它压根不写缓存目录。最糟的是两条都不做——缓存目录被原样烙进镜像层，白白多出几百兆。

还有三个常用开关。UV_COMPILE_BYTECODE=1 在安装时就把字节码编出来，用构建时间换运行时的启动速度，对需要快速扩容的服务值得开；UV_NO_DEV=1 或同步时排除开发依赖组，把测试与格式化工具挡在生产镜像之外；UV_PYTHON_DOWNLOADS=0 禁止 uv 自行下载解释器，强制使用基础镜像里那个——这正好呼应第一节：解释器应当由基础镜像标签钉死，不该在构建过程中另外引入一个。

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_NO_DEV=1 \
    UV_PYTHON_DOWNLOADS=0

数据截止 2026-06 · 上述参数依据 uv 官方文档的 Docker 集成章节（uv 0.12 系列）。uv 迭代较快，落地前请对照当前版本文档确认参数是否仍然有效。

多阶段构建的判断标准只有一句：这个东西运行时用得上吗？用不上就别让它跨过最后那道 FROM。编译器、头文件、下载缓存、测试依赖，全都属于用不上的那一类。

五、运行时配置与安全：容器跑起来之后的事

镜像构建完只完成了一半。剩下一半是它跑起来之后的行为：用什么身份跑、密钥怎么给、日志出不出得来、被要求停止时能不能干净地退出。这几件事单拎出来都不难，但都属于「不做也能跑，出事才发现」的类型。

不要用 root 跑

容器默认以 root 身份运行进程。这个 root 虽然被各种机制限制过，但它仍然是纵深防御里最不该白送的一层：一旦应用被攻破，攻击者在容器里就是管理员，写任何路径、装任何工具都没有阻碍。做法很简单，建一个普通用户，在最后切过去。

RUN useradd --create-home --uid 10001 appuser
# 把运行时需要写的目录交给它
RUN chown -R appuser:appuser /app
USER appuser
CMD ["/app/.venv/bin/python", "-m", "myapp"]

切换之后有个常见的连锁问题：应用启动时报权限错误，因为它要往某个目录写临时文件或日志，而那个目录属主还是 root。正确的处理是显式把需要写的路径交给这个用户，而不是把 USER 那行删掉了事。文件与异常那一卡（PY07）讲过权限类错误的识别方式，在容器里它们会集中在启动的头几秒出现。

密钥进了镜像层就再也删不掉

这是容器里最容易犯、后果最重的一个错误。镜像历史保存了每一层的内容，某一层写进去的文件，即便后面的层把它删了，数据仍然完整地躺在那一层里，任何拿到镜像的人都能翻出来。

密钥为什么删不掉 ═══════════════════════════════════════════════════════════ 层 1 FROM slim 基础层 层 2 COPY .env /app/.env ← 密钥写进这一层 层 3 RUN pip install -r requirements.txt 层 4 RUN rm /app/.env ← 只是加了一条「已删除」标记 最终镜像 = 层1 + 层2 + 层3 + 层4 ▲ └── 层 2 的数据原封不动还在 导出镜像、逐层解包，密钥完整可读 正确姿势 构建期需要密钥 → 用构建器的秘密挂载，不进任何层 运行期需要密钥 → 环境变量 / 挂载文件 / 秘密管理服务注入 任何时候 → .dockerignore 排除 .env、*.pem、credentials*

示例场景：某团队把私有包仓库的访问令牌写进了 Dockerfile 的一条 ARG，构建完再 unset。半年后镜像仓库做只读授权审计时才发现，那段时间产出的 400 多个镜像标签的历史里都能直接读出这个令牌，而镜像仓库对全公司只读开放。处置花了 3 天：轮换令牌、清理镜像、逐个仓库重新构建。根因不是谁不小心，而是团队默认「后面删掉就等于没写过」。判断方法很直接——凡是能被 docker history 或逐层解包看到的东西，就要当成公开信息。

日志被缓冲住，等于没有日志

Python 的标准输出在不连接终端时是块缓冲的。容器里的标准输出连的是管道，于是缓冲区攒够几 KB 才会真正吐出来。表现就是：服务明明在跑，日志里什么都没有；或者进程崩溃时，最后那几行最关键的日志因为还在缓冲区里而永远丢失。

解决办法是设 PYTHONUNBUFFERED=1，让输出不经缓冲直接写出。这一条几乎没有代价，属于容器镜像里应当无条件加上的环境变量。

优雅退出：谁收到了终止信号

停止容器时，运行时先给主进程发终止信号，等一段宽限期（命令行工具默认 10 秒，编排系统里通常是 30 秒），到点还没退出就强杀。想干净地收尾——把在途请求处理完、把缓冲写盘、把连接关掉——就必须真的收到那个信号。这里有两个坑串在一起。

停止容器时的信号链路 ═══════════════════════════════════════════════════════════ 写法 A：CMD python app.py （shell 形式） 停止请求 │ 发送 SIGTERM ▼ PID 1 = /bin/sh -c "python app.py" │ ╳ sh 不转发信号给子进程 │ python（PID 7）什么都没收到 → 宽限期满被强杀 写法 B：CMD ["python", "app.py"] （exec 形式） 停止请求 │ 发送 SIGTERM ▼ PID 1 = python ← 信号直达 │ ├─ 没装 SIGTERM 处理函数：PID 1 的默认动作被内核忽略 │ → 进程不退，宽限期满被强杀 │ └─ 装了处理函数：置停止标志 → 收尾 → 主动退出 ✔

第一个坑是 CMD 的写法。带方括号的 exec 形式让你的进程直接成为 1 号进程，信号能直达；不带方括号的 shell 形式会先起一个 shell，信号发给 shell，而 shell 通常不会转发给子进程。容器里的 CMD 和 ENTRYPOINT 一律用 exec 形式，这条没有例外。

第二个坑更隐蔽：1 号进程的信号处理有特殊规则——对于没有安装处理函数的信号，内核直接忽略，不执行默认的「终止进程」动作。所以即使用了 exec 形式，一个没写 SIGTERM 处理的 Python 进程照样杀不掉，只能等强杀。写法是显式注册一个处理函数。

import signal

stopping = False

def _on_term(signum, frame):
    global stopping
    stopping = True          # 只置标志，收尾放到主循环里做

signal.signal(signal.SIGTERM, _on_term)

信号处理函数里只置标志、不做实际工作，这是通用原则：处理函数在主线程的字节码间隙执行，在里面做 I/O 或抢锁很容易出问题。真正的收尾放到主循环或框架的关闭钩子里。如果你的进程需要管理子进程，还要考虑僵尸进程回收——容器运行时一般提供一个轻量的初始化进程选项，开启它由这个进程来转发信号和回收子进程，比自己实现可靠。

配置项推荐做法不做会怎样
运行身份建普通用户并 USER 切过去应用被攻破即等同容器内管理员
密钥构建期用秘密挂载，运行期用环境变量或挂载注入写进层就永久留在历史里，删不掉
配置环境变量注入，同一个镜像跑所有环境每套环境一个镜像，测过的那个不等于上线的那个
日志PYTHONUNBUFFERED=1，写标准输出不写文件日志延迟甚至丢失，崩溃现场看不到
启动命令CMD 用 exec 形式（方括号写法）信号发给 shell，应用收不到
优雅退出注册 SIGTERM 处理函数，在宽限期内收尾退出每次发布都被强杀，在途请求直接断
资源限制显式设内存上限，并让应用知道这个上限超限被直接杀掉，没有任何 Python 层的报错

最后一行值得补一句：容器内存超限时进程是被内核直接杀掉的，拿不到异常、来不及打日志，现象就是「服务无声无息地没了」。内存与 GC 那一卡（PY23）讲过 Python 把内存还给操作系统的时机并不由你控制，所以容器的内存上限要留出足够余量，并且要监控实际占用而不是只看有没有报错。

六、镜像瘦身与部署纪律

「把镜像做小」是个很容易上瘾的目标，但值得先想清楚小了到底赚在哪，免得为了几十兆把构建的可靠性搭进去。

瘦身的真实收益

收益主要有两块。一是拉取时间：节点第一次运行某个镜像要把它整个拉下来，这段时间直接计入扩容延迟和故障恢复时间。流量突增时要新起十几个实例，镜像大一倍，这十几个实例就慢一倍到位。二是攻击面：镜像里每多一个系统包，就多一份将来被披露漏洞的可能，而扫描器报出来的问题不管你用不用得上那个包都得处理，纯属白白增加的运维负担。

不在收益里的是磁盘成本——存储早就便宜到不值得为它优化了。也不在收益里的是运行速度：镜像大小和跑起来之后的性能没有关系。

反过来说，有几个代价是不该为瘦身付出的：换成 Alpine 导致构建随机失败、删掉调试工具导致线上出问题时连个 shell 都进不去、把依赖精简到只在正常路径上能跑。层缓存命中率对日常效率的影响，比镜像小几十兆大得多。

瘦身的优先级排序：先用多阶段把编译期产物挡在门外，再用 .dockerignore 挡住无关文件，再合并那些会留下垃圾的安装步骤。做完这三步还想再挤，性价比就很低了。

部署纪律：镜像标签怎么打

比瘦身重要得多的是标签纪律。这件事的核心诉求只有一个：任何时刻，都能从一个正在运行的实例反查出它对应哪次代码提交。出故障时这个能力决定了你是五分钟定位还是两小时排查。

标签策略能反查到提交吗不可变吗适合
只用 latest不能不，随时被覆盖本地试验，生产禁用
递增构建号要查 CI 记录才行是聊胜于无，别单独用
提交哈希（如 app:9f3c1ab）能，直接对应是默认方案
语义版本（如 app:2.7.0）能，对应发布 tag是对外发布的制品，和提交哈希并存
内容摘要（@sha256:…）需配合元数据绝对不可变部署清单里最终引用的形式

推荐的组合是：构建时同时打上提交哈希和（如果是发布）语义版本，部署清单里引用摘要。latest 可以留着给本地方便，但生产环境的部署清单里出现 latest 应当被当成配置错误——它不可复现，回滚时你甚至说不清要回到哪里。

另外两条纪律。一次构建，多环境复用：测试环境和生产环境跑的应当是同一个镜像，差异全部通过环境变量注入。如果每套环境各构建一次，那么你测过的那个镜像和上线的那个就不是同一个东西，测试的意义打了折扣。扫描要卡在流水线里：镜像扫描只有在能阻断发布时才有用，扫出报告没人看等于没扫；同时要设一条定期重建基线，否则底层发行版的安全补丁永远进不来——这也是第一节说的「全限定标签 vs 摘要固定」那个取舍的另一面。

  • FROM 写到具体补丁版本与变体，合规场景再加摘要固定
  • 先拷依赖声明与锁文件、装依赖，最后才 COPY 源码
  • .dockerignore 用「先全排除再放行」的写法
  • 默认选 slim；确认依赖里有 C 扩展时更要坚持
  • 多阶段构建，两个阶段用同一个基础镜像标签
  • 严格锁定模式安装依赖，缓存走挂载或干脆不留
  • 建普通用户并 USER 切过去，运行目录显式授权
  • 设 PYTHONUNBUFFERED=1，CMD 用 exec 形式
  • 注册 SIGTERM 处理函数，在宽限期内完成收尾
  • 用提交哈希打标签，部署清单里引用摘要
  • 把构建耗时和缓存命中率当作要盯的指标
  • 用 python:3 这类浮动标签做生产基础镜像
  • 把 COPY . . 放在装依赖之前（本卡第二节那起事故）
  • 让 .venv、.git、数据文件进入构建上下文
  • 为了几十兆换 Alpine，然后花一周修编译失败
  • 构建阶段与运行阶段用不同版本的解释器
  • 把密钥写进任何一层，指望后面 rm 掉
  • 在镜像里写死某套环境的配置，每个环境各构建一份
  • 用 CMD python app.py 这种 shell 形式启动
  • 生产部署清单里引用 latest
  • 扫描报告只生成不阻断，基础镜像一年不更新

这一组卡从锁文件讲到镜像，主线只有一条：把「在我机器上能跑」逐步替换成「在任何机器上都能构建出同一个东西」。镜像是这条链路的最后一环——它把操作系统、系统库、解释器这三样过去只存在于口头约定里的东西，变成了可以提交、可以审计、可以回滚的制品。

Q&A

有了锁文件，为什么还需要容器镜像？
锁文件固定的是「装哪些包的哪些版本」，覆盖不到三件事。第一，没有匹配预编译轮子时安装器会退回源码编译，编译结果取决于本机的编译器和系统库，同一行锁记录能装出不同的二进制。第二，就算拿到轮子，它只声明了对 C 库版本的最低要求，底下那份系统库具体是哪个版本、带哪些补丁，锁文件管不着，而加密后端、时区数据、字符集这些行为就来自那里。第三，锁文件通常只约束解释器的版本区间，管不到补丁号。镜像把这三层一起固定下来，才算把「环境」真正交付出去。反过来说，镜像也不能代替锁文件——镜像里装了什么版本，仍然要靠锁文件来说清楚，两者是配合关系。
为什么先拷源码再装依赖会把构建时间拖垮？
因为层缓存是顺序失效的。缓存判断依据是「父层相同 + 指令相同」，拷贝类指令还要比对文件内容校验和。如果 COPY . . 排在装依赖之前，那么任何一次源码改动都会让这一层的校验和变化，这一层失效之后，它后面的所有层——包括最慢的装依赖——统统要重建，哪怕依赖一个字都没动。反过来把依赖声明和锁文件单独先拷、装完依赖再拷源码，源码改动只会让最后那一两层失效，装依赖那层继续命中，重建成本从几分钟降到几秒。判断方法很简单：按变化频率从低到高排列指令，改得最勤的东西放在最后面。
构建上下文太大有什么具体危害？只是慢一点吗？
不止是慢。构建开始前，客户端会把整个上下文目录打包传给构建器，这一步在任何缓存判断之前发生，所以目录里有多少东西就要传多少，本地虚拟环境和数据文件常常比源码大两三个数量级。更严重的是两个后果：一是 COPY . . 会把这些东西原样写进镜像层，拉取时间和攻击面一起涨；二是安全问题，本地的 .env、私钥、云凭证只要在目录里就会被带进去，进了层就再也删不干净。所以 .dockerignore 应当被当成安全边界而不是性能优化，推荐写法是先用 * 全部排除，再显式放行需要的几项，这样以后新增的临时目录默认进不去。
Alpine 镜像那么小，为什么不推荐给 Python 项目？
因为 Alpine 用的是 musl 而不是 glibc，两者的二进制接口不兼容。Python 打包生态为此区分了两套平台标签：面向 glibc 的 manylinux 和面向 musl 的 musllinux。现实是绝大多数带 C 扩展的包都提供 manylinux 轮子，提供 musllinux 轮子的要少得多，于是在 Alpine 上装这些包往往只能下载源码现场编译。后果是构建慢几倍到几十倍，而且会因为缺某个头文件而整段失败，对依赖科学计算包的项目尤其明显。更讽刺的是，为编译而装进去的工具链本身就有几百兆，最终镜像未必更小。所以默认答案是 slim：它还是 glibc，轮子照常可用，体积也已经砍掉了大头。只有依赖全是纯 Python、且体积确实是硬指标时，Alpine 才划算。
多阶段构建里把虚拟环境整个拷过去，要注意什么？
两个硬性前提。第一，路径必须完全一致。虚拟环境的配置文件和命令行入口脚本里写的都是绝对路径，构建阶段建在哪里，运行阶段就得放在同一个位置，挪了地方入口脚本里的解释器路径就是空的。第二，解释器版本必须匹配。site-packages 的目录名带版本号，编译出的扩展模块文件名也带版本标记，构建阶段用 3.12、运行阶段用 3.13，拷过去的包压根不在搜索路径上，报错却只是「模块找不到」，很难联想到真实原因。最稳妥的做法是两个阶段的 FROM 写同一个基础镜像标签，从源头上消除不一致的可能。另外记得禁止安装器在构建过程中自行下载解释器，否则你以为在用基础镜像那个，实际用的是另一个。
密钥不小心打进镜像了，后面加一层删掉行不行？
不行。镜像由一叠只读层组成，删除操作只是在上层记一条「这个文件已删除」的标记，底下那一层的数据原封不动还在。把镜像导出来逐层解包，或者直接查镜像历史，密钥完整可读。正确做法分两种情况：构建期需要凭证（比如访问私有包仓库）时，用构建器提供的秘密挂载机制，它在构建时可见、但不写进任何层；运行期需要凭证时，通过环境变量、挂载文件或秘密管理服务在启动时注入，镜像里一个字都不存。另外一定要用 .dockerignore 把 .env、*.pem、credentials* 排除掉，这类泄漏最常见的来源不是刻意写进去，而是 COPY . . 顺手带的。已经泄漏的只有一条路：轮换凭证，然后清理镜像。
为什么容器停不下来，总要等十几秒才被强杀？
通常是两个原因之一，也可能两个同时中招。第一，CMD 用了不带方括号的 shell 形式，运行时实际启动的是一个 shell，它才是 1 号进程；终止信号发给 shell，而 shell 一般不会转发给子进程，你的 Python 进程什么都没收到。改成 exec 形式即可。第二，就算信号直达了，1 号进程有个特殊规则：对于没有安装处理函数的信号，内核直接忽略，不执行默认的终止动作。所以一个没注册 SIGTERM 处理函数的 Python 进程作为 1 号进程时，收到信号也不会退出，只能等宽限期结束被强杀。解决办法是显式注册处理函数，在里面只置一个停止标志，真正的收尾放到主循环里做。宽限期命令行默认 10 秒、编排系统里通常 30 秒，收尾逻辑要设计得能在这个时间内完成。
生产环境用 latest 标签到底有什么问题？
三个问题。一是不可复现：latest 随时会被下一次构建覆盖，你在部署清单里写的 latest 和昨天那个 latest 不是同一个镜像，但清单里看不出任何差别。二是回滚无从下手：故障时想退回上一个能用的版本，你说不出它叫什么。三是排查断链：从一个正在运行的实例反查不到它对应哪次代码提交，而这个能力往往决定了定位故障要五分钟还是两小时。推荐做法是用提交哈希打标签，发布版本再额外打一个语义版本，部署清单里最终引用内容摘要——摘要是内容寻址的，绝对不会被覆盖。latest 可以保留给本地方便使用，但它出现在生产部署清单里就应当被当成配置错误拦下来。
