同步的 with 和 for 藏着一个假设：进入、退出、取下一个，这三件事都是瞬间完成的本地计算。一旦它们本身要走网络，这个假设就塌了。异步协议加的不是新能力，只是把「获取」和「释放」这两个动作也变成了可以挂起的点。

一、为什么同步协议不够用

写异步代码的人最先注意到的是「计算过程」要 await：查数据库要等、调接口要等。但资源的获取与释放本身也是 I/O，这件事往往到出事故才被想起来。建一条数据库连接要完成 TCP 握手加认证往返；关一条 WebSocket 要按协议发出关闭帧并等对端回应；提交一个事务要等存储引擎确认落盘。这些动作没有一个是「瞬间完成的本地计算」。

问题在于，同步的 上下文管理协议把释放动作放在 __exit__ 里，而 __exit__ 是一个普通方法，不是协程——它的函数体里根本不允许出现 await，这是语法层面的限制。于是在协程里用同步上下文管理器包住一个网络资源，退出时只剩两条路，而两条都是坑。

需求：退出时要 await conn.close()（发关闭帧、等对端确认） ───────────────────────────────────────────────────────── 同步协议： def __exit__(self, et, ev, tb) ← 普通函数，体内不能 await 走法 A：调阻塞版本 走法 B：发出去就不管 ────────────────── ───────────────────── conn.close_blocking() create_task(conn.close()) │ │ ▼ ▼ 整个事件循环停住 with 块立刻结束，没人 await 它 同进程里几百个其它任务 任务只是被排进队列 一起陪这一次 socket 往返 异常没人接、进程退出可能没跑完 │ │ ▼ ▼ 一次关闭拖垮全局 P95 「关了」只是你以为关了 异步协议： async def __aexit__(self, et, ev, tb) ← 协程，体内可以 await await conn.close() → 只挂起当前这一个任务，其它任务照跑 → 而且真的等到它完成才离开 async with

走法 B 尤其值得警惕，因为它看起来是对的：代码里确实写了 close，日志里也不会报错。但 即发即忘（fire-and-forget）的任务如果没人持有引用、没人 await，它的异常会被静默丢弃，进程退出时也可能压根没被调度到。你以为的「释放」变成了一次概率性事件。第四节的事故就是这条路的一个变体。

判断一个资源该不该用异步上下文管理器，只看一个问题：它的关闭动作里有没有网络或磁盘往返。有，就必须能 await；没有，同步的 with 在协程里用着完全没问题。

两套协议是严格对称的

Python 没有为异步发明新概念，只是把已有的四个特殊方法各加了一个 a 前缀，并规定它们返回 可等待对象（awaitable，实践中就是写成 async def）。同步侧的知识可以整体平移过来——包括 PY19 讲过的 __exit__ 返回值语义，和 PY12 讲过的迭代器状态机。

还有一条纯语法的约束：async with 和 async for 只能出现在 async def 的函数体里，写在普通函数里是 SyntaxError，在导入阶段就会失败。这条限制本身不难受，难受的是它会传染——某个深处的工具函数改用异步资源，调用链上所有函数都得跟着变成协程。所以引入异步资源之前，先想清楚它的调用边界画在哪。

二、async with 与异步上下文协议

把 async with 展开成等价的普通代码，是理解它最快的方式。下面这个展开来自语言参考对 async with 语义的定义，和同步 with 的展开逐行对照，你会发现差别只有三个 await。

async with EXPR as TARGET: SUITE 语义上等价于（隐式特殊方法查找的细节已略） ──────────────────────────────────────────────── manager = (EXPR) aenter = type(manager).__aenter__ ← 从类上查，不看实例属性 aexit = type(manager).__aexit__ ← 进入前就把两个都取好 value = await aenter(manager) ① 可挂起 hit_except = False try: TARGET = value SUITE except: hit_except = True if not await aexit(manager, *sys.exc_info()): ② 返回假值才继续抛 raise finally: if not hit_except: await aexit(manager, None, None, None) ③ 正常路径 读这段能一次性回答三个常见疑问： · 两个方法在进入前就从类上取好了 → 运行中改实例属性没用 · 异常路径和正常路径分别调用 aexit，参数不同 → 所以要判 exc_type · aexit 的返回值被 not 了一下 → 真值 = 别再抛了

第 ② 步是最容易写错的地方。__aexit__ 的返回值不是「成功与否」，而是「要不要把这个异常吞掉」。协程函数如果不写 return，返回的是 None，那是假值，异常照常向外传播——这正是绝大多数实现想要的行为。但如果你在 __aexit__ 里写了日志然后顺手 return True，异常就被静默压制了，调用方拿到的是一个「一切正常」的假象。

__aexit__ 的返回值块内有异常时的行为什么时候该这么写
不写 return（即 None）异常继续向外抛默认选择，绝大多数实现
False 或其它假值异常继续向外抛等价于上一行，只是把意图写显式
True 或其它真值异常被吞掉，async with 之后的代码照常执行仅当「压制这一类异常」就是这个管理器的职责时
自己抛出新异常新异常取代旧的，旧的挂在 __context__ 上包装成领域异常时用，注意别丢掉原始故障点

要吞异常也必须按类型吞：先看 exc_type 是不是自己认识的那一类，是才返回真值，不认识的一律放行。无差别返回 True 会连 asyncio.CancelledError 一起吞掉，那意味着这个任务再也取消不掉了。异常分类的原则在 PY24 里有系统讨论。

类写法与生成器写法

类写法就是把两个特殊方法实现出来，适合状态多、需要被 isinstance 检查、或者要复用继承体系的场景。

class Transaction:
    def __init__(self, pool):
        self._pool = pool

    async def __aenter__(self):
        self._conn = await self._pool.acquire()
        await self._conn.execute("BEGIN")
        return self._conn

退出侧要处理三件事，而且顺序不能乱：按有没有异常决定提交还是回滚，无论如何都要还连接，最后什么都别返回。

    async def __aexit__(self, exc_type, exc, tb):
        try:
            sql = "COMMIT" if exc_type is None else "ROLLBACK"
            await self._conn.execute(sql)
        finally:
            await self._pool.release(self._conn)
        # 不写 return，返回 None（假值），异常照常向外抛

注意那个 try/finally：提交和回滚本身也可能抛异常（连接断了、超时了），如果不包住，连接就还不回池子。这是本卡反复出现的主题——清理代码自己也会失败，它需要自己的清理保护。

更多时候用 @contextlib.asynccontextmanager（3.7 引入）更省事：写一个异步生成器，yield 之前是进入逻辑，之后是退出逻辑。3.10 起这样定义出来的管理器还可以直接当装饰器用。

from contextlib import asynccontextmanager

@asynccontextmanager
async def acquired(pool):
    conn = await pool.acquire()        # yield 之前 = __aenter__
    try:
        yield conn                     # ← 让出点必须被 try 包住
    finally:
        await pool.release(conn)       # yield 之后 = __aexit__

生成器写法唯一的硬纪律：yield 必须被 try 包住。原理是这样的——async with 块里抛出的异常，会被 asynccontextmanager 通过 athrow 扔回生成器的让出点。如果 yield 裸在外面，这个异常会直接从生成器里穿出去，yield 之后那几行清理代码一行都不会执行。而正常路径下它们执行得好好的，所以这个 bug 只在出错时才发作——恰恰是最需要清理生效的时刻。用 finally 承载「无论如何都要做」的动作，用 except 承载「只在失败时做」的动作，两者别混。

把 @asynccontextmanager 的函数体读成一个 try/finally 骨架：yield 那一行是「用户代码插进来的位置」，它随时可能就地爆炸。这么读，该包 try 的地方一眼就能看出来。

数量不定的资源：AsyncExitStack

嵌套 async with 只能处理数量固定的资源。一旦资源个数由配置或运行时数据决定（每个分片一条连接、每个租户一个客户端），嵌套写法就没法表达了。contextlib.AsyncExitStack（3.7 引入）把「退出动作」变成一个可以运行时压栈的数据结构，离开时按登记的逆序退栈。

async with AsyncExitStack() as stack: cfg = await stack.enter_async_context(load_config()) ① 压栈 pool = await stack.enter_async_context(make_pool(cfg)) ② 压栈 for shard in cfg.shards: ③ 数量不定 await stack.enter_async_context(pool.connect(shard)) stack.push_async_callback(flush_metrics) ④ 登记回调 离开块时按登记的逆序退出： ④ flush_metrics ③ shard 连接 N … shard 连接 2 → shard 连接 1 ② pool ① cfg 关键性质：③ 进行到一半抛异常时，已经压进去的那些 仍然会被逆序退干净 —— 手写嵌套做不到这一点，因为 异常发生时你根本不知道自己嵌到了第几层

常用的三个方法要分清：enter_async_context(cm) 接一个异步上下文管理器并 await 它的 __aenter__；push_async_callback(fn, *args) 只登记一个收尾协程，不做任何进入动作；aclose() 手工把整个栈退干净，用于「资源的生命周期比某个语法块长」的场景，比如把 stack 挂在服务对象上、在 shutdown 钩子里统一退栈。

逆序释放不是审美偏好，是正确性要求。连接依赖连接池、连接池依赖配置，反过来释放就会出现「池子已经没了，连接还想往里还」。同步侧的 ExitStack 也是同样的语义，PY19 有更细的展开。

三、async for 与异步迭代协议

async for 解决的是另一类问题：取下一个元素这件事本身要等 I/O。分页 API 的下一页要发一次 HTTP 请求；数据库游标的下一批要走一次网络往返；大模型的流式响应，下一个 token 要等服务端算出来。这些都不是「集合里已经有了，取出来就行」。

异步迭代协议由两个方法构成。__aiter__ 必须返回一个异步迭代器对象——注意它自己不是协程，Python 3.7 起返回 awaitable 会直接报 TypeError。真正干活的是 __anext__，它返回一个可等待对象，await 之后给出下一个元素；没有下一个了就抛 StopAsyncIteration，这个异常由 async for 语句捕获，不会外泄给你。

class Cursor:
    def __aiter__(self):            # 不是 async def！
        return self

    async def __anext__(self):
        row = await self._fetch_one()
        if row is None:
            raise StopAsyncIteration
        return row

手写这个类的机会其实不多，因为异步生成器（3.6 引入，PEP 525）把同样的逻辑压缩成了几行：在 async def 的函数体里写 yield，调用它得到的就是一个现成的异步迭代器。和同步生成器一样，函数体在第一次迭代前不执行任何代码，每次 yield 交出一个值并原地冻结，下次迭代从冻结点继续。

async def fetch_pages(client, url):
    while url:
        page = await client.get(url)        # 这里等 I/O
        for row in page["items"]:
            yield row                       # 一条一条交出去
        url = page.get("next")

# 消费端：
# async for row in fetch_pages(client, first_url):
#     await handle(row)

有两个细节容易踩：异步生成器里不允许 return 带值（会得到 SyntaxError: 'return' with value in async generator），只能写光秃秃的 return 来提前结束；另外同一个异步生成器对象不能被并发迭代，两个任务同时对它 __anext__ 会抛 RuntimeError: anext(): asynchronous generator is already running。想让多个消费者共享一个数据流，得自己在中间加一层队列做分发。

流式消费到底省下了什么

异步生成器最大的价值不在写法简洁，而在于它把「取数据」和「用数据」这两件事交错了起来。先全量收集再统一处理的写法，要等最后一页返回才能动第一条；流式写法第一页一到就能开工。

凡是「每取一条都要等一次 I/O」，且结果集大小不可控，就该用异步生成器。判据不是数据量有多大，而是你能不能承诺它一定不大——承诺不了，全量收集就是一颗定时炸弹。

流式也有它的代价。下游处理慢的时候，背压会一路传导回上游连接：连接被占着不放，服务端可能因为长时间没读而超时断开，某些分页 API 的游标也有有效期。所以流式管道里每一段都要有超时，而不是只在最外层包一个总超时——总超时到期时你只知道「整体慢了」，不知道慢在拉取还是处理。

最后一行「清理责任」是本卡的核心，下一节整节都在讲它。异步生成器和同步生成器在这一点上有本质区别，而这个区别在日常写法里完全看不出来——直到线上出事。PY12 讲过的同步生成器关闭机制，到了异步这边不再够用。

四、异步生成器的清理难题

先回顾同步侧的机制：一个同步生成器如果没被消费完就失去了所有引用，CPython 在回收它时会把 GeneratorExit 抛进它挂起的那个 yield 点，于是 finally 块得以执行，文件被关上、锁被释放。这一整套是同步完成的，在垃圾回收的那一刻就地做完，你几乎感觉不到它的存在。

异步生成器的 finally 里可以有 await。这一个差别摧毁了上面那套机制：清理不再是一个能就地做完的动作，而是一个协程，需要一个还在运行的事件循环来驱动它。而对象什么时候被回收，取决于 PY23 里讲的引用计数与 GC 时机——那是你控制不了的，完全可能落在事件循环已经关闭之后。

同步生成器的清理是「回收时顺手做掉」，异步生成器的清理是「回收时预约一件将来要做的事」。预约能不能兑现，取决于那时候还有没有事件循环——这就是全部难点。

CPython 是怎么兜这个底的

解释器通过 sys.set_asyncgen_hooks 提供了两个钩子，asyncio 的事件循环启动时会装上它们：firstiter 在某个异步生成器第一次被迭代时触发，循环借此把它登记进自己的一张表；finalizer 在它被回收时触发，循环借此把 aclose() 排成一个任务。有了这张表，循环在收尾阶段就能主动把所有还挂着的异步生成器关掉——这就是 loop.shutdown_asyncgens()（3.6 引入）。

好消息是asyncio.run 已经替你调了它。它的收尾顺序是固定的：先取消所有剩余任务，再 await loop.shutdown_asyncgens()，再关闭默认执行器，最后才 loop.close()。这是「不要手工 new_event_loop 再 close」这条建议的又一个理由——手工管理循环时，这三步收尾极少有人写全。

下面这段行为是实测出来的，不是推测。同一个「取三条就 break」的异步生成器，用手工建的循环跑完直接 close，finally 一次都没有执行，stderr 上只留下一行 Task was destroyed but it is pending!，任务名是 async_generator_athrow；换成 asyncio.run 跑同一段代码，finally 正常执行。

async for v in gen(): gen 的 finally 里有 await conn.release() if v == 42: break ← 只取了几条就跳出，gen 还挂在 yield 上 ① 什么都不做，指望 GC gen 失去引用 → 等 GC → 触发 asyncio 装的 finalizer 钩子 → 把 gen.aclose() 排成一个任务 → 但此刻循环可能已经 close 了，任务永远跑不起来 现象：finally 一行没跑，stderr 上只有 Task was destroyed but it is pending! ... async_generator_athrow 最坏情况：连这行都被日志采集吃掉，故障完全静默 ② 靠 asyncio.run 的收尾兜底 run 退出前 await loop.shutdown_asyncgens() → finally 跑了 但时刻是「整个 run() 结束时」。常驻服务的 run 一跑就是几个月， 等于把资源泄漏拖满整个进程寿命 —— 兜底不等于及时 ③ async with aclosing(gen()) as it: 离开 async with 的那一刻立即 await gen.aclose() break、异常、正常结束三条路径全覆盖， 且清理与迭代跑在同一个上下文里（上下文变量、任务归属都对得上）

路径 ③ 用的是 contextlib.aclosing（3.10 引入）。它做的事很朴素——离开块时调用对象的 aclose()，等价于一个包着 try/finally 的两行上下文管理器。官方文档对它的定位说得很准：它保证生成器的退出代码与它的迭代运行在同一上下文中，因此异常和上下文变量的行为符合预期，退出代码也不会在它所依赖的某个任务已经结束之后才跑。

from contextlib import aclosing

async with aclosing(fetch_pages(client, url)) as rows:
    async for row in rows:
        if row["id"] == target:
            break            # ← 离开 async with 时立刻 aclose()
# 等价的显式写法（3.10 之前）：
#   agen = fetch_pages(client, url)
#   try:  ...  finally:  await agen.aclose()
做法清理发生在覆盖 break / 异常前提评价
什么都不做GC 说了算，可能在循环关闭之后不可靠—静默失败的来源
asyncio.run 收尾的 shutdown_asyncgens整个 run() 结束时覆盖用 asyncio.run，不手工建循环兜底，但对常驻服务远远不够及时
显式 await agen.aclose()你调用它的那一刻要自己写进 finally 才覆盖拿得到生成器对象及时，但容易漏写
async with aclosing(agen)离开块的那一刻三条路径全覆盖3.10+消费端的标准写法
资源根本不放进生成器由外层 async with 决定覆盖需要调整接口设计最稳，见第五节

事故复盘：连接数每六天涨满一次。一个流式转发接口把上游模型服务的响应逐块转给客户端，实现方式是一个异步生成器：finally 里写着 await resp.release()，把连接还给连接池。上线后一切正常，直到第 6 天凌晨接口开始整片 5xx，重启后立刻恢复，被当成偶发问题放过；第 12 天、第 18 天又各来了一次，才有人注意到这个间隔太规整了。
数字：上游连接池上限 200，稳态占用约 55，可消耗余量 145。日均流式请求约 1600 次，其中约 1.6%（25 次左右）客户端会提前断开——用户关掉页面或切走。每断开一次，转发协程被取消，异步生成器没被消费完就丢弃，finally 里的 release() 排成任务后随循环状态一起消散，那条上游连接既没关闭也没归还。25 条/天的泄漏速率，145 ÷ 25 ≈ 5.8 天，正好对上「每六天一次」。
为什么难查：连接池占用是单调上涨的，任何一天的曲线看上去都很平缓；而重启会把计数清零，于是每次事后去看指标都是「一切正常」。真正定位靠的是把 pool.size 和 pool.freesize 打成指标后拉出跨重启的长周期曲线，一条不回头的斜线立刻就露馅了。
修复：把连接的获取与释放从生成器的 finally 里搬出来，交给外层的 async with；生成器本身只负责产出数据块，不再持有任何需要及时释放的东西。同时在消费端用 aclosing 包住生成器兜底。改动约 30 行，之后连续观察两周，连接占用稳定在 55 ± 8，不再有单调上涨。

这个事故的教训不是「记得写 aclose」，而是更结构性的一条：不要把「必须及时发生」的清理动作，托付给一个「什么时候结束由别人决定」的对象。异步生成器的生命终点掌握在消费方手里，你在它的 finally 里写什么，都只是一个愿望。

五、实战范式

把前面几节落到三个常见形状上。三段骨架都刻意写得很短，重点不在 API 细节，而在资源归谁管这一个问题上。

范式一：分页拉取封装成异步生成器

生成器只负责翻页和产出，HTTP 客户端由调用方从外面传进来——它的生命周期不属于这个生成器。这样即使调用方中途 break，被丢弃的生成器里也没有任何需要抢救的东西。

async def iter_orders(client, since):
    """client 由外层 async with 管理，本生成器不持有需要释放的资源。"""
    cursor = since
    while cursor:
        page = await client.get("/orders", params={"cursor": cursor})
        for item in page["items"]:
            yield item
        cursor = page.get("next_cursor")

范式二：异步事务封装成异步上下文管理器

事务是天生的上下文管理器：进入时开启，退出时按有没有异常决定提交还是回滚。注意这里把「归还连接」这一层单独交给了第二节那个 acquired——嵌套组合比把三件事挤在一个 try 里更不容易写错。

@asynccontextmanager
async def tx(pool):
    async with acquired(pool) as conn:   # 归还连接的事交给它
        await conn.execute("BEGIN")
        try:
            yield conn
        except BaseException:
            await conn.execute("ROLLBACK")
            raise
        await conn.execute("COMMIT")     # 没抛异常才走得到这里

范式三：流式转发，且保证连接一定被关闭

这是第四节那个事故的正确写法。关键是让 async with（而不是生成器的 finally）持有上游响应：无论客户端是正常读完还是中途断开，退出 async with 都是确定发生的。

async def relay(client, payload):
    async with client.stream("POST", "/v1/chat", json=payload) as resp:
        resp.raise_for_status()
        async for chunk in resp.aiter_bytes():
            yield chunk
# 上游响应由 async with 持有：客户端提前断开时，
# 取消会从 yield 点抛进来，async with 照样执行退出逻辑。
# 消费端再用 aclosing(relay(...)) 包一层，双保险。

一个反复出现的误用

把这三段放在一起看，一条设计原则就浮出来了：在异步生成器里持有需要及时释放的资源，同时又让调用方决定什么时候停止迭代，等于把释放时机交给了别人。调用方可以 break、可以被取消、可以在中间抛异常，甚至可以把生成器对象存起来放着不管——你在 finally 里写的任何东西，执行时机都不由你决定。

识别这个误用有一个简单信号：如果一个异步生成器的文档里需要写「请务必迭代完，或者用 aclosing 包起来」，那它的设计就已经出问题了。文档约束不是约束，它只在有人读的时候生效。

范式内部持有什么释放由谁负责调用方需要额外做什么
分页拉取（异步生成器）只有游标位置和一个外部传入的客户端引用客户端由外层 async with 管什么都不用做，正常 async for
事务（asynccontextmanager）连接 + 未完成的事务__aexit__，提交/回滚二选一后必还连接用 async with 包住，别手工调
流式转发（生成器 + 内层 CM）由内层 async with 持有上游响应内层 async with 的退出逻辑建议再用 aclosing 兜一层
反例：生成器直接 acquire 连接连接，且只在 finally 里还名义上是生成器，实际是调用方必须迭代完或 aclosing，漏一次泄漏一条

设计异步接口时问自己：如果调用方在任意一个 await 点被取消，我这里会漏掉什么？答不上来，就说明资源的归属还没理清楚。

六、并发与异步小组收束

这一组卡从「为什么需要并发」讲到了「资源怎么释放」。回头看，所有内容其实都在回答同一串问题，而且顺序是固定的：先定并发模型，再定编排原语，再画边界，再处理混合代码，最后才是可观测性。跳过任何一步，后面的选择都会变成拍脑袋。

一个异步能力要落地，按顺序回答六个问题 ──────────────────────────────────────────────────── ① 时间花在「等」还是花在「算」？ 等为主 → asyncio 单线程高并发 算为主 → 多进程；纯 Python 且已实测瓶颈 → 才谈自由线程构建 ② 这批任务的成败是绑定的吗？ 绑定（要么全成要么全撤） → TaskGroup（3.11+） 不绑定，只是批量收集 → gather 只要最快的那一个 → wait(FIRST_COMPLETED) ③ 每个出网调用都有超时和并发上限吗？ 没有 = 没有边界。一次下游变慢就能把在飞任务数顶到天上 ④ 有没有同步阻塞代码混进来？ 有 → 走执行器桥接，别让它站在事件循环上 ⑤ 每个资源的释放挂在谁身上？ ← 本卡 挂在 async with / AsyncExitStack / aclosing 上 不要挂在异步生成器的 finally 上 ⑥ 出事时能不能分辨「慢」和「漏」？ 事件循环滞后 + 在飞任务数 + 连接池占用，缺一个就分辨不了
判据维度要回答的问题落到具体选择
负载类型时间花在等 I/O 还是花在算等为主选 asyncio；算为主用多进程；纯 Python 计算且已实测瓶颈，才评估自由线程构建
任务组织一组任务的成败是否绑定绑定用 asyncio.TaskGroup（3.11+，异常自动取消同组）；松散收集用 gather；竞速用 wait(FIRST_COMPLETED)
边界控制失控时谁来踩刹车每个出网调用套 asyncio.timeout（3.11+）；并发用 Semaphore 封顶；队列必须设 maxsize
同步桥接有没有阻塞库混进事件循环asyncio.to_thread（3.9+）或 run_in_executor；线程池大小要显式设，别用默认值
资源生命周期释放动作挂在谁身上async with / AsyncExitStack / aclosing；不要挂在异步生成器的 finally 上
取消语义被取消时清理跑得完吗CancelledError 要放行不能吞；清理段里不要再做没有超时的 await
可观测性出事时能分辨慢和漏吗事件循环滞后、在飞任务数、连接池占用与等待时长；三个指标要在上线前就位

这张表的使用方式是自上而下、不能跳行。常见的返工路径都是从跳行开始的：先挑了 gather（第二行）才发现负载其实是 CPU 密集（第一行），整套异步化白做；或者边界（第三行）留到压测才补，而这时超时值该设多少已经没有依据了——因为没有第七行的指标。第一行错了，后面六行全都要重来。

异步不是「让程序变快」的开关，是「让等待的时间可以被复用」的机制。凡是没在等的场景，异步只带来复杂度；凡是在等的场景，边界和清理没做好，异步带来的是更难查的故障。

异步服务上线检查清单

  • 入口统一用 asyncio.run，让 shutdown_asyncgens 这道兜底始终生效
  • 凡是关闭动作里有 I/O 的资源，一律用 async with；数量不定的用 AsyncExitStack
  • 消费别人的异步生成器时，只要可能提前退出，就用 aclosing 包住
  • @asynccontextmanager 里的 yield 必须被 try 包住，清理放 finally
  • __aexit__ 默认不写 return；确实要吞异常时先判 exc_type
  • 每个出网调用都有超时，每个并发点都有上限，每个队列都有 maxsize
  • 上线前接好三个指标：事件循环滞后、在飞任务数、连接池占用与等待时长
  • 拿连接池占用画一条跨重启的长周期曲线，泄漏只在这条线上看得见
  • 在异步生成器的 finally 里释放连接、锁这类必须及时归还的资源
  • 手工 new_event_loop / close，把三步收尾漏掉两步
  • 在同步的 __exit__ 里调阻塞的 close，或者 create_task 完就不管
  • __aexit__ 里无条件 return True——会连 CancelledError 一起吞掉
  • 把「请务必迭代完」写进文档当约束用，文档只在有人读的时候生效
  • 让多个任务并发迭代同一个异步生成器对象（直接 RuntimeError）
  • 只在最外层包一个总超时，中间每一跳都没有
  • 结果集大小不可控时还先全量收集，再考虑要不要改流式

整组内容压成一句话：异步的难点从来不是怎么把任务发出去，而是怎么保证每一条发出去的路径，无论成功、失败还是被取消，都有人负责收尾。

Q&A

__aexit__ 到底该返回什么？我看有的库返回 False，有的什么都不返回。
两者行为完全一样。协程不写 return 时返回 None，None 是假值，而 async with 的展开里对返回值做的是 if not await aexit(...): raise——假值意味着「我没处理这个异常，继续往外抛」。写 return False 只是把这个意图显式化，风格问题。真正需要注意的是反面：返回任何真值都会吞掉块内的异常，调用方会以为一切正常。只有当「压制某一类异常」正是这个管理器存在的理由时（比如一个专门用来忽略清理期错误的包装器）才这么写，而且必须先判断 exc_type 是不是自己认识的那一类，不认识的一律放行。无差别返回 True 会连 asyncio.CancelledError 一起吞，那意味着这个任务再也取消不掉了。
类写法和 @asynccontextmanager，实际项目里怎么选？
默认用 @asynccontextmanager：它把进入、退出、异常处理写在同一个函数里，顺序即时序，读起来是线性的，短小的资源管理用它代码量能少一半。转用类写法的信号有三个：一是需要在管理器上暴露额外的方法或属性（生成器写法只能通过 yield 交出一个值）；二是需要参与继承体系或被 isinstance(x, AbstractAsyncContextManager) 检查；三是同一个对象要被重复进入或嵌套进入——@asynccontextmanager 产出的是一次性对象，进入第二次会失败（3.10 起可以当装饰器用，因为每次调用会新建一个生成器实例，这是另一回事）。顺带一提，生成器写法有个硬纪律：yield 必须被 try 包住，否则块内抛异常时 yield 之后的清理代码一行都不会执行。
async for 里 break 会有什么后果？和同步 for 一样吗？
语句层面一样：跳出循环，不再请求下一个元素。但后果差别很大。同步生成器被丢弃时，解释器把 GeneratorExit 抛进挂起点，finally 就地同步执行完毕，你基本不用操心。异步生成器的 finally 里可能有 await，清理本身是个协程，需要一个还在运行的事件循环，而回收时机由 GC 决定，完全可能落在循环关闭之后。结果就是清理静默失败，最多在 stderr 留一行 Task was destroyed but it is pending!。所以只要你的 async for 可能提前退出，而生成器里有清理逻辑，就该用 async with aclosing(gen()) as it: 包住——离开块的那一刻立即 aclose()，break、异常、正常结束三条路径都覆盖。
我的异步生成器里 finally 明明写了，为什么没执行？
按三个可能性排查。第一，生成器没被消费完就丢弃了，而清理任务的排期赶不上事件循环关闭——这是最常见的，现象是 stderr 上一行 Task was destroyed but it is pending!，任务名里带 async_generator_athrow。第二，你手工建了事件循环并直接 close()，没有调 loop.shutdown_asyncgens()；换成 asyncio.run 就好了，它的收尾里包含这一步。第三，用 @asynccontextmanager 时 yield 没被 try 包住，异常被 athrow 扔回让出点后直接穿出去了。定位方法是在 finally 第一行打一条日志，先确认到底是「没进 finally」还是「进了但里面的 await 挂住了」——这两种的修法完全不同。
aclosing 和 AsyncExitStack 有什么区别？什么时候用哪个？
解决的是两个不同问题。aclosing(thing)（3.10 引入）针对的是「这个对象有 aclose() 方法，但它本身不是上下文管理器」，最典型的就是异步生成器——你想在离开块时确定性地关掉它。AsyncExitStack（3.7 引入）针对的是「资源数量在运行时才知道」，它把退出动作做成一个可以随时压栈的结构，离开时逆序退栈。两者可以叠着用：在一个 AsyncExitStack 里 await stack.enter_async_context(aclosing(agen))，就把一个异步生成器的关闭也纳入了统一的逆序释放。选择判据很简单：资源个数固定且已知，用嵌套 async with；个数不定，用 AsyncExitStack；对象只有 aclose() 没有 __aenter__，用 aclosing 转接一下。
同一个异步生成器能不能给多个消费者同时用？
不能。两个任务同时对同一个异步生成器对象调 __anext__，会直接抛 RuntimeError: anext(): asynchronous generator is already running。这不是限制，是保护——生成器本质是个单线程状态机，并发推进它的状态没有合理语义。要让多个消费者共享一个数据流，标准做法是加一层分发：起一个任务专门迭代生成器，把每个元素扔进 N 个 asyncio.Queue（每个消费者一个），消费者各自从自己的队列取。这样做还有个附带好处——队列的 maxsize 天然成了背压开关，某个消费者慢下来时不会拖垮别人，只会让自己的队列先满。代价是要自己处理生产者提前结束和某个消费者提前退出的收尾。
__aiter__ 可以写成 async def 吗？
不可以。Python 3.7 起 __aiter__ 必须直接返回一个异步迭代器对象，不能返回可等待对象（3.7 之前那种写法已经被移除）。写成 async def __aiter__ 的话，调用它得到的是一个协程对象，而协程对象没有 __anext__，async for 会报 TypeError: 'async for' received an object from __aiter__ that does not implement __anext__: coroutine，同时还会附带一个「协程从未被 await」的 RuntimeWarning。记法很简单：只有 __anext__ 是协程，__aiter__ 是普通方法，通常就一行 return self。反过来说，如果你在写异步生成器（async def + yield），这两个方法解释器都替你生成好了，不用管。
协程里还能用普通的 with 和 for 吗？
能，而且大部分时候就该用普通的。判据只有一条：这个 with 的进入/退出、这个 for 的取下一个元素，会不会阻塞。遍历一个内存里的列表、用 with 包一个计时器或一次 Decimal 精度设置，这些都是纯本地计算，在协程里用同步写法完全正确，换成异步版本反而是无谓的开销。真正要警惕的是看起来同步、实际会阻塞的东西：同步的数据库驱动、requests、大文件的 open/read、time.sleep。它们在事件循环上一站就是几百毫秒，整个进程的所有任务陪着一起卡。这类代码要么换异步库，要么用 asyncio.to_thread（3.9+）桥接到线程池里去。
