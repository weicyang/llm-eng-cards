PY54 · 大模型客户端的三种调用模式

调用特性与超时预算 / 同步的线程代价 / 异步的并发上限反推 / 流式的首字延迟 / 流式带来的四个新问题

同步、异步、流式不是三种「性能档位」，而是三种不同的代价分配：同步拿线程换简单，异步拿复杂度换并发，流式拿工程复杂度换首个结果的等待时间。选错的代价不是慢一点，是线上把线程池或连接池打满。

一、这类调用的四个特性，决定了后面所有的选择

把一次大模型调用当成「一个稍微慢一点的 HTTP 接口」，是这类代码出事故最集中的根源。它确实是一次 HTTP 调用，但它的四个特性和你平时调的任何接口都不一样，而这四个特性几乎决定了本卡后面每一条结论。

第一，单次耗时以秒计，不是毫秒。一次完整生成从几秒到几十秒都很正常。这意味着所有为毫秒级接口准备的默认值——连接超时、读超时、线程池大小、熔断窗口——搬过来全部失效。

第二，耗时与输出长度强相关，因而难以预估。服务端是一个 token 一个 token 地生成的，输出越长耗时越长，两者基本呈线性关系。同一个接口，回答「是」和回答一篇八百字的分析，耗时可能差二十倍。所以你没法像对数据库那样给出一个稳定的 P99，超时只能按「允许的最长输出」来预算。

第三，按 token 计费，所以重试有真实成本。普通接口重试一次只花掉一点 CPU 和带宽；这里重试一次要把输入重新付一遍钱，如果失败发生在生成中途，已经产出的部分通常也照样计费。「失败就重试三次」这种在内部服务里无害的默认策略，在这里会把账单和配额一起放大。

第四，失败率明显高于内部服务。它是外部依赖，要跨公网，还普遍带有按分钟计的请求数与 token 数配额。被限流、瞬时超载、网关抖动都是日常，不是异常。你的代码必须把失败当成常态路径来写，而不是当成兜底分支。

判断一段调用代码写得对不对，先问一句：如果这次调用要花 30 秒才返回，我这段代码会发生什么？答不上来，就说明还在按毫秒级接口的直觉写。

二、同步模式：最简单，代价是一整条线程

同步模式就是最朴素的那种写法：发起调用，阻塞等待，拿到完整结果，继续往下走。它的优点不该被低估——代码是线性的，异常沿调用栈往上抛，调试器能一步步跟，日志顺序和代码顺序一致。在脚本、离线任务、定时作业这类场景里，它不但够用，而且是最佳选择：你根本没有并发压力需要解决，引入异步只是在给自己增加一层排查难度。

# 示意写法：client 是自己封装的客户端，不对应任何 SDK 的真实接口
def summarize(text: str) -> str:
    return client.call(prompt=text, timeout=60)   # 这 60 秒里本线程什么都干不了

# 离线脚本里这样写完全没问题：没有别人在等这条线程
for doc in docs:
    print(summarize(doc))

问题出在把同样的写法搬进 Web 服务。同步调用期间，当前线程被完全占住：它不在计算，CPU 占用几乎为零，但它也不能去服务任何别的请求。对毫秒级的下游，这点占用无所谓；对一次要等 8 秒的上游，这条线程就等于被扣押了 8 秒。

Web 服务里的同步大模型调用（假设线程池 32 条线程） ──────────────────────────────────────────────────── 线程 1 │████ 等待上游生成 8s ████│ 返回 │ 线程 2 │████ 等待上游生成 6s ███│ 返回 │ 线程 3 │████ 等待上游生成 11s ██████│ 返回 │ ...... 线程 32 │████ 等待上游生成 9s █████│ ────────┴─────────────────────────────────────────── 第 33 个请求 │ 排队 …… 排队 …… 排队 …… │ 网关 504 这 32 条线程在等待期间 CPU 几乎为 0，却没有一条能去干别的事。 能承载的吞吐 ≈ 线程数 ÷ 平均耗时 = 32 ÷ 8s ≈ 每秒 4 个请求。 想扛 40 QPS 就要 320 条线程 —— 线程不是这么用的。

上图最后那行是关键。同步模式下，服务的吞吐上限被死死锁在「线程数 ÷ 单次耗时」这个公式上。而单次耗时是秒级的，于是线程数必须往上堆才能换吞吐，堆到几百条时线程本身的内存与切换开销又会反噬。这条路在毫秒级下游时走得通（因为除数很小），在秒级下游时走不通。

示例场景：某内部知识问答接口沿用了团队既有的同步 Web 框架模板，线程池 64，压测时 30 QPS 全绿——因为压测用的提示词很短，平均耗时 1.2 秒。上线后真实用户的提问长得多，平均耗时涨到 7 秒，实际承载能力降到每秒 9 个请求左右。当天下午并发到 20 QPS 时线程池全部占满，队列堆积，网关侧 504 比例冲到 38%，而机器 CPU 只有 11%。CPU 闲着、服务却挂了，是同步模式配秒级下游的典型画像。

场景同步模式合适吗原因
一次性脚本、数据生成合适没有并发压力，线性代码最好调试
定时离线任务（量小）合适总量可控，串行跑完即可
命令行工具、内部小工具合适单用户，占住线程无人受影响
低并发内部服务（个位数 QPS）勉强可以需按「线程数 ÷ 单次耗时」算清上限并留余量
面向用户的 Web 接口不合适一个请求占住一条线程数秒，并发稍高即耗尽线程池
需要一次发起多个调用不合适串行等待，总耗时等于各次之和

同步模式的判据只有一句：只用在没有并发压力的地方。只要还有别人在排队等这条线程，它就不该被一次秒级调用占住。

还有一种常见的中间态：服务本身是异步的，但你手上只有一个同步的客户端库。这时不要在协程里直接调它——那会阻塞整个事件循环，后果比同步框架还严重。正确做法是把同步调用挪到线程池里执行，让事件循环继续转，具体写法见 PY33。

三、异步模式：把等待期间的线程还回去

异步模式解决的正是上一节那条公式。调用发出后，协程主动让出控制权，事件循环立刻去处理别的请求；上游返回时再把这个协程唤醒接着往下走。等待那 8 秒里，这条线程服务了别人。于是单机能承载的并发量级和同步模式完全不在一个数量级上——受限的不再是线程数，而是内存和下游配额。

它适合两类场景：需要同时发起多个调用（批量处理、多路召回、并行调用多个模型再比较），以及本身就跑在异步服务里（异步 Web 框架的请求处理函数里）。事件循环本身的机制不在本卡展开，见 PY28。

异步不会让单次调用变快一毫秒。它改变的是「这台机器在等待期间还能不能干别的」。总耗时没变，被解放的是线程。

两条不能省的纪律

纪律一：必须设超时。这类调用不设超时不是「偶尔慢一点」，而是可能挂住很久——网络半开、上游排队、连接被中间设备静默丢弃，都会让一个 await 永远等不到结果。异步模式下这件事尤其隐蔽：挂住的协程不占线程，不会像同步模式那样表现为线程池告警，它只是安静地堆积，直到内存或连接数出问题。超时与取消的完整机制见 PY31。

纪律二：并发必须有上限。异步模式下开出几千个并发协程在语法上毫无阻力，一行推导式就够了。但上游有配额，打爆配额的结果是整片请求被限流退回——你不但没跑快，还把本来能成功的那部分也拖下水。批量并发的编排原语（任务组、结果收集、部分失败处理）见 PY30，限流手段见 PY31。本卡只讲一件事：这个上限的数值该怎么定。

并发上限从哪里来：从下游配额反推，不是从本机资源反推 ──────────────────────────────────────────────────────── ✗ 常见错法 本机 8 核 / 16G 内存 → 协程很轻 → 开 2000 个 结果：瞬间打爆每分钟请求配额，整片请求被限流退回， 成功率不升反降，还白白消耗了重试预算 ✓ 正确算法 稳态并发 = 允许的每分钟请求数 × 平均单次耗时(秒) ÷ 60 例：配额 600 次/分钟，实测平均单次耗时 6 秒 稳态并发 = 600 × 6 ÷ 60 = 60 再用 token 配额复核一遍： 每分钟 token 配额 ÷ 单次平均 token 数 = 另一个每分钟请求数 代回上式，两个结果取小值，再留 20% 余量 ──────────────────────────────────────────────────────── 本机资源只决定「不能再高」，下游配额决定「实际该是多少」
sem = asyncio.Semaphore(60)                # 上限按上图从配额反推得出

async def one(text: str) -> str:
    async with sem:                        # 并发闸门
        async with asyncio.timeout(60):    # 3.11+；不设超时会挂很久
            return await client.acall(prompt=text)

async with asyncio.TaskGroup() as tg:      # 3.11+，结构化并发
    tasks = [tg.create_task(one(d)) for d in docs]

注意信号量放在超时外面：先排队拿到名额，再开始计时。反过来写的话，排队等待的时间会被算进超时预算里，队列一长就会出现大批「还没真正发出请求就超时」的假失败。并发上限和超时是两件事，不要让它们互相干扰。

这几个数里最容易被忽略的是第三行。它不是性能调优，而是正确性问题：把信号量写在超时里面，超时统计出来的会是「排队时长」而不是「上游响应时长」，你的监控从此测量的就不是它以为的东西了。

示例场景：一个离线打标任务要处理 12 万条文本，作者按「协程很轻」的直觉一次性建了 3000 个任务。前 20 秒跑得飞快，随后限流响应占比升到 91%，重试逻辑又把请求量放大了三倍，最终 40 分钟只成功了 4100 条。改成按配额反推的 60 路并发、失败退避重排队之后，同一批数据 2 小时 10 分钟全部跑完，限流占比降到 0.4%。并发度从 3000 降到 60，吞吐反而涨了近 6 倍。

四、流式模式：它改变的是首字延迟，不是总耗时

这是最容易被误解的一点：流式不会让生成变快。一段 600 token 的回答，无论流不流式，服务端生成完它需要的时间是一样的。流式改变的是你什么时候拿到第一个结果——从「等十几秒拿到全部」变成「一两秒内看到第一个字，然后持续吐字」。

这个差别在交互式产品里几乎是决定性的。用户面对一个转圈十几秒的输入框，会认为它坏了；面对一个一秒内开始逐字输出的界面，即使总时长一样，感受是「它在认真回答」。所以对话、写作、代码补全这类产品，首字延迟才是真正要优化的指标，总耗时反而是次要的。

同一个请求（输出约 600 token，服务端总生成耗时 12 秒） ──────────────────────────────────────────────────────────── 时间 → 0s 2s 4s 6s 8s 10s 12s │ │ │ │ │ │ │ 同步 │░░░░░░ 线程被占住，用户什么都看不到 ░░░░░░░░░░░░│●全文 │ ↑ 首字 12.0s │ 异步 │░░░░░░ 线程已让出，可服务别的请求 ░░░░░░░░░░░░░│●全文 │ ↑ 首字 12.0s │ 总耗时与同步完全一样，省下来的是线程 │ 流式 │░░│▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓│◎结束标志 │ ↑ 首字 1.4s，此后持续吐字直到结束 ──────────────────────────────────────────────────────────── 三种模式的总耗时都是 12 秒。流式唯一改变的是首个结果的延迟： 12.0s → 1.4s。交互式产品的体感差别，几乎全部来自这一格。

传输层怎么把这些分块推给浏览器、用什么协议、断线了怎么续，是另一个完整的话题，见 ST17 大模型流式传输五层方案与生产实战。本卡只讲客户端这一侧：拿到一个流式接口之后，代码要做什么。

客户端要处理的三件事

一是逐块消费与增量拼接。流给你的是一串片段，不是一串完整答案。片段可能切在词中间甚至字符中间，所以要维护一个累积缓冲：一边把新片段追加进去，一边把增量推给下游（前端或调用方）。不要每次都把「当前完整文本」重新发一遍，那会让传输量随长度平方增长。

二是区分结束标志与中断。流停下来有两种完全不同的原因：服务端正常生成完毕并发出结束信号，或者连接在中途断了。前者是成功，后者是失败，但在代码里它们都表现为「迭代结束了」。必须显式记录「我有没有收到过结束标志」，没收到就当失败处理——否则用户会看到一段被截断的话，而你的监控里这次调用是成功的。

三是必须保证连接被关闭。这是流式最容易出事的地方，值得单独强调：流式调用持有一条长时间打开的上游连接，而交互式场景里客户端提前离开是常态——用户关页面、切走、点了「停止生成」。如果你的代码只在「正常读完」的路径上关闭连接，这些提前退出的路径就会留下一条永远不会被回收的上游连接，也就是连接泄漏。

async def answer(text: str):
    async with client.astream(prompt=text) as stream:   # 进出都走上下文管理
        async for chunk in stream:                      # 逐块消费
            yield chunk                                 # 立刻推给下游
    # 正常读完、调用方提前不取了、中途抛异常 —— 三条路径都会释放连接

异步上下文管理器与异步生成器的清理时机（包括「调用方提前不取了」这条路径上 finally 到底什么时候跑）是有讲究的，见 PY35。这里只记一条规则：流式资源一律用上下文管理包裹，不要手工配对打开与关闭。异常路径和提前退出路径永远比你想的多。

客户端要做的事不做会怎样判据
增量拼接每块都重发一次全文，传输量随长度平方增长只推增量，完整文本留在服务端累积
区分结束标志与中断被截断的回答在监控里记成成功显式记录「是否收到过结束标志」，没收到即失败
保证连接关闭提前退出路径留下不回收的上游连接一律用上下文管理包裹，不手工配对
首字延迟埋点无法证明流式改造到底有没有收益首块到达时单独打点，与总耗时分开看

流式不是「更快的异步」。它是把一次调用从「一个结果」变成「一串结果加一个结束标志」，代价是你要自己管好这串结果的拼接、终止判断和连接回收。

五、流式带来的四个新问题

上一节讲的是流式要做什么，这一节讲它会打破什么。下面四件事在非流式模式下根本不存在，是流式独有的代价，而且每一件都有过真实的线上事故。

流式调用的四个新危险点 ────────────────────────────────────────────────────────── 发起 ──► 首块 ──► 块 ──► 块 ──► …… ──► 结束标志 ──► 用量统计 │ │ │ │ │ │ │ └─② 错误可能在这里发生 │ │ │ 此时用户已看到半截回答 │ │ │ │ │ └─④ 超时要盯「相邻两块的间隔」 │ │ 而不是「从发起到现在的总时长」 │ │ ③ 提前中断 └─① 结构化校验在这里做不了 就拿不到统计 收到的 JSON 只有一半，解析必然失败 贯穿全程：无论从哪一步退出，上游连接都必须被关闭

① 结构化输出与流式天然冲突

如果你要求模型返回一个 JSON 对象并在代码里解析它，流式就成了麻烦：在收到最后一块之前，你手上永远是一段不完整的 JSON，解析必然失败，校验也无从谈起。所谓「流式解析 JSON」的做法能勉强边收边猜，但它无法判断一个字段是「还没传完」还是「模型漏了」，用来做校验并不可靠。

现实里只有两条路。第一条是结构化输出就别用流式——机器消费的结果本来也没人盯着看，首字延迟毫无价值，用非流式换取「拿到即可校验」的确定性。第二条是流式只用于展示，校验放在结束时做：把分块直接推给界面让用户看到进度，同时在服务端累积完整文本，收到结束标志后再统一解析和校验，校验失败就走兜底。判据很简单：这个结果是给人看的，还是给程序用的。

② 错误可能发生在流的中途

非流式调用只有两种结局：成功拿到全部，或者失败什么都没有。流式多出来一种：已经输出了一部分，然后失败了。这打破了重试的前提——你不能像平常那样「失败就重发一次」，因为用户界面上已经躺着半截回答，重发会让内容重复一遍。

处理办法是让展示层具备幂等展示能力：给每次生成一个标识，重试时不是追加而是替换该标识下的全部内容。界面上表现为「刚才那半截被清掉，从头重写」，用户能接受；而「半截 + 完整版」拼在一起，用户会认为系统坏了。如果产品上不允许清空重来，那就干脆不重试，把这次失败如实告诉用户，让他自己决定要不要重问。

③ 统计与计费信息通常在流的末尾

token 用量、结束原因（是自然说完还是撞到长度上限）这类信息，一般只在流的最后一块里给出。于是只要提前中断——用户点了停止、你的超时触发、连接断了——这些信息就永远拿不到了。后果是账单对不上：你的埋点统计出来的 token 消耗，会明显低于服务商账单上的数字，因为中断掉的那些请求，服务端照样算钱，你这边却记了个零。

务实的做法是：中断时按「已收到的分块数」做一个本地估算并打上「估算」标记，同时单独统计中断次数与中断占比。别追求精确，追求的是账单出现偏差时你能解释得清偏差来自哪里。日志与指标的落地方式见 PY43。

④ 超时语义必须换成「块间空闲超时」

这是最反直觉的一条。非流式调用的超时是「从发起到拿到结果的总时长」，天经地义。但流式沿用这个语义就是个陷阱：一个正常工作、每 40 毫秒稳定吐一块的流，只要回答够长，就会撞上总耗时超时被自己掐断。用户看到的现象是「长回答总是写到一半就断」，而监控里这是一次超时，看不出任何上游问题——因为上游确实没问题，是你掐的。

正确的语义是块间空闲超时：只约束「距离上一块过去了多久」，每收到一块就把计时器清零。流在健康工作时这个间隔始终很小，一旦上游真的卡住，间隔立刻超限，能快速识别。通常还会给首块单独一个更宽的预算，因为首块要等模型加载与预填充，天然比后续的块慢一个量级。

# 错误：总耗时超时 —— 回答一长就被自己掐断
async with asyncio.timeout(30):
    async for chunk in stream:
        consume(chunk)

# 正确：每收一块就重置计时，只约束相邻两块的间隔
async for chunk in with_idle_timeout(stream, first=20, idle=15):
    consume(chunk)

生产事故复盘：某交互式问答接口从非流式改为流式，上线当天首字延迟从 P50 9.8s 降到 1.3s，用户满意度打分明显上升，回归和压测全绿。但一周后开始出问题：上游连接池上限 256，从改造上线起活跃连接数每天净增约 35 条且从不回落，第 8 天午高峰打满，新请求全部在连接池排队，接口 P99 从 1.5s 飙到 60s 超时，失败率 73%。根因是：用户中途关闭页面时，服务端只终止了给前端的响应，没有关闭对上游的那条流式连接——代码里的关闭动作写在「读完全部分块」之后的正常路径上，提前退出根本走不到。埋点显示中断率约 22%，与每天 160 次左右的问答量相乘，正好是每天 35 条泄漏。修复做了三件事：把流式调用整体包进异步上下文管理器，保证异常与提前退出路径都释放；在客户端断开时向上游传播取消；新增「当前活跃上游流数」指标并设置阈值告警。修复后活跃连接稳定在 18 条上下并随并发起落，观察三周未再增长。

维度流式带来的收益流式带来的代价
首字延迟从秒级降到百毫秒到一两秒—
总耗时不变因分块开销可能略增
用户体验可见进度，可中途叫停—
结构化输出—收完前无法校验，需二选一
错误处理—中途失败，重试需幂等展示
用量统计—中断则丢失，只能估算
超时设计能更早发现上游卡死要改成块间空闲超时，多一套参数
连接管理—长连接，漏关就泄漏

流式的收益集中在一个指标上（首字延迟），代价却分散在五六个地方（校验、重试、统计、超时、连接）。所以它值得用在用户盯着屏幕等的地方，不值得用在程序读结果的地方。

六、选型与封装：把三套写法关进一层

前面五节的结论可以压缩成一张表。选型的第一个问题不是「哪种性能好」，而是「结果给谁看、有没有并发压力」。

场景推荐模式理由要注意
离线批处理、数据生成异步（量小则同步）要并发跑完大批量，无人等待首字并发度按配额反推，失败重排队而非立即重试
命令行工具、内部脚本同步单用户、无并发压力，线性代码最好调仍要设超时，别让脚本挂死在半夜
交互式产品（对话、写作）流式首字延迟是核心体验指标连接必须保证关闭，超时改块间空闲
高并发后端服务（打标、审核、抽取）异步，不流式结果给程序用，首字延迟无价值并发上限、超时、背压三件套齐备
需要结构化结果并校验非流式（同步或异步）收完才能校验，流式徒增复杂度确需展示进度时，流式展示 + 结束时校验
异步服务里只有同步客户端异步 + 线程池桥接协程里直接阻塞会卡住整个事件循环桥接写法见 PY33

封装纪律：业务代码不该同时面对三套写法

这三种模式的差异如果直接暴露给业务代码，会发生一件很难挽回的事：超时常量、重试次数、并发信号量、埋点字段会被复制到每一个调用点。等到要换模型、调超时、加一个指标时，你得改二十几处，而且一定会漏掉几处——漏掉的那几处就是下次事故的起点。

做法是收口成一层薄封装：对业务只暴露两个入口，一次性结果和逐块结果。模式差异、超时策略、并发闸门、连接生命周期、埋点，全部关在封装层里。背压也在这一层处理——下游消费得慢时要让流慢下来，而不是在内存里无限缓冲。

┌────────────────────────────────────────────────┐ │ 业务代码：只认识两个入口 │ │ 一次性结果 = call(请求) │ │ 逐块结果 = stream(请求) （异步迭代） │ └──────────────────────┬─────────────────────────┘ │ 业务侧不应出现：超时常量、重试次数、 │ 并发信号量、埋点字段、三套模式分支 ┌──────────────────────▼─────────────────────────┐ │ 客户端封装层（本卡的落点） │ │ · 超时：整体超时 与 块间空闲超时 分开设 │ │ · 并发：按下游配额反推的统一上限 │ │ · 关闭：进出都走上下文管理，异常路径也释放 │ │ · 埋点：首字延迟 / 总耗时 / token 数 / 中断原因│ │ · 重试与降级（韧性策略，由下一张卡展开） │ └──────────────────────┬─────────────────────────┘ ▼ 上游大模型服务（流式接口 / 非流式接口）

封装层的埋点字段值得单独列一下，因为这四个字段决定了出事时你能不能查：首字延迟（流式体验的唯一指标）、总耗时（配合输出长度才有意义）、输入与输出 token 数（对账用，中断时标记为估算）、结束原因（正常结束／长度截断／用户中断／超时／上游错误）。尤其是最后一个：上一节那个连接泄漏事故，如果一开始就按结束原因分类统计，「用户中断」占 22% 这个数字会在第一天就摆在面板上。

至于重试怎么退避、限流了怎么排队、上游挂了怎么降级——这些属于韧性策略，是下一张卡的主题，这里只强调它们的位置：全部属于封装层，不属于业务代码。

  • 调用前先算一遍「线程数 ÷ 单次耗时」，确认吞吐上限撑得住目标 QPS
  • 并发上限从下游配额反推，再留 20% 余量
  • 信号量放在超时外面：先拿名额，再开始计时
  • 流式一律用上下文管理包裹，保证异常与提前退出都释放连接
  • 流式超时用块间空闲超时，首块单独给更宽的预算
  • 显式判断有没有收到结束标志，没收到就算失败
  • 埋点至少含首字延迟、总耗时、token 数、结束原因四项
  • 三种模式的差异收口在一层客户端封装里
  • 在面向用户的 Web 接口里用同步调用等待秒级上游
  • 在协程里直接调用同步客户端库（会卡住整个事件循环）
  • 不设超时，或沿用毫秒级接口的超时常量
  • 按本机资源决定并发度，一次性开出上千个任务
  • 给流式调用设总耗时超时，让长回答被自己掐断
  • 对流式失败直接重发，导致界面上出现重复内容
  • 要求结构化结果却坚持全程流式，边收边猜着解析
  • 把超时、重试、并发参数复制到每一个业务调用点

这张卡真正要记住的只有三句：同步只用在没人排队的地方；异步的并发上限由下游配额决定；流式买到的是首字延迟，付出的是连接、校验、重试和统计这四笔账。

Q&A

既然异步在各方面都更好，为什么还要保留同步写法？
因为异步的收益只在「有人在排队」时才兑现。离线脚本、命令行工具、定时任务里没有并发压力，把线程让出来也没人接手，异步带来的只有额外的心智负担：调用栈变得难读、异常传播路径变复杂、调试器单步跟踪的体验下降、还要额外考虑事件循环的启动与关闭。判断标准很直接：这条线程被占住几秒，有没有第三方因此受损？没有，就用同步。另外还有一类现实情况是你依赖的库只有同步版本，这时在异步服务里要通过线程池桥接（见 PY33），而在脚本里直接同步调用就好。
流式能让总耗时变短吗？
不能，甚至会因为分块传输的额外开销略微变长。服务端生成 600 个 token 需要的时间，和你用不用流式接收没有关系。流式唯一改变的是首个结果到达的时间：从「等全部生成完」变成「生成出第一块就给你」。所以它优化的指标是首字延迟，不是吞吐也不是总延迟。这个区分很重要——如果有人提出「用流式提升系统吞吐」，那是选型理由搞错了：提升吞吐靠的是异步并发，不是流式。反过来，如果产品的痛点是用户盯着空白界面等太久，那流式是唯一有效的手段。
并发上限到底该设多少？有没有一个通用的默认值？
没有通用默认值，但有通用算法：稳态并发 = 允许的每分钟请求数 × 平均单次耗时（秒）÷ 60。比如配额 600 次/分钟、平均单次 6 秒，算出来是 60。然后用 token 配额复核一遍（每分钟 token 配额 ÷ 单次平均 token 数 = 另一个每分钟请求数），两个结果取小值，再留 20% 余量给重试和抖动。关键点在于这个数字的来源是下游配额而不是本机 CPU 或内存——协程很轻，本机资源算出来的数字往往大一两个数量级，直接用会把配额打爆，成功率不升反降。另外平均单次耗时要用自己埋点里的真实值，不要用压测值，因为压测的提示词通常比真实用户的短得多。
流式调用的超时应该怎么设？
分成两个参数，都不要用「从发起到结束的总时长」。第一个是首块超时，覆盖连接建立、排队和预填充，通常给到十几到几十秒的量级；第二个是块间空闲超时，只约束「距离上一块过去了多久」，每收到一块就重置，通常给到十几秒。用总耗时超时的后果是长回答会被自己掐断，而且现象极具迷惑性——监控里是一次超时，上游其实完全正常。另外建议再加一个「最大总输出长度」的上限作为兜底，防止异常情况下流无限输出；这个上限应该按 token 数或字符数来限制，而不是按时间，因为时间和输出长度本来就是强相关的，用时间限制等于间接限制了长度，还限得不准。
要求模型返回 JSON，还能用流式吗？
能，但要想清楚流式在这里换到了什么。如果结果是给程序用的（比如抽取字段后写库），没人盯着看，首字延迟没有价值，直接用非流式，收完立即校验，逻辑简单得多。如果结果既要给人看又要结构化（比如一边展示分析过程一边最后给出评分），可以流式展示、结束时校验：分块照常推给界面，同时在服务端累积完整文本，收到结束标志后再一次性解析校验，失败就走兜底路径。要避免的是「边收边解析并据此做业务判断」——不完整的 JSON 无法区分「字段还没传完」和「模型漏了这个字段」，基于它做判断迟早出错。
流到一半失败了，能重试吗？
技术上可以，但要先解决展示重复的问题。用户界面上已经有了半截回答，直接重发会得到「半截 + 完整版」的拼接结果，用户会认为系统坏了。可行的做法是给每次生成一个标识，重试时替换该标识下的全部内容而不是追加，界面表现为「清空重写」，这是用户能接受的。如果产品形态不允许清空（比如内容已经被用户复制走了，或者已经落库），那就别重试，如实告诉用户这次失败了。还要记得成本问题：中途失败的那部分输出通常也是计费的，重试等于为同一个问题付两次钱，所以重试次数要比内部服务保守得多，一般一次就够，并且要配合退避。
怎么才能确信自己没有泄漏上游连接？
靠指标，不靠代码走读。加一个「当前活跃上游流数」的实时指标，正常情况下它应该随并发量起落，闲时回到接近零。如果它只涨不落，就是在泄漏，而且这个信号比连接池打满早很多天出现。代码层面的保证是把流式调用整体包进异步上下文管理器，让正常读完、调用方提前不取、中途抛异常三条路径都走同一段释放逻辑，不要手工配对打开与关闭；异步生成器的清理时机有其微妙之处，见 PY35。另外要在客户端断开时主动向上游传播取消，而不只是停止往前端写数据——只停写前端，上游那条连接还好好开着，这正是最常见的泄漏根因。
中断的请求拿不到 token 统计，账单对不上怎么办？
先接受它对不齐，然后让偏差可解释。用量信息通常在流的最后一块给出，提前中断就永远拿不到，而服务端对已生成的部分照常计费，于是你的埋点会系统性地低于账单。务实做法有三步：一是中断时按已收到的分块数做本地估算并打上「估算」标记，区别于精确值；二是单独统计中断次数和中断占比，这个比例本身也是产品指标（占比高说明回答太长或答非所问）；三是每月对账时用「精确值 + 估算值」和账单比对，偏差控制在一个可接受的范围内即可。不要为了拿到精确统计而禁止用户中断——那是拿体验换对账精度，方向反了。
