PY22 · 枚举与 Protocol

把「合法取值」和「必须会做什么」从注释里搬进代码：Enum 家族选型 / 别名与 _missing_ 陷阱 / 名义与结构子类型 / Protocol 的依赖倒置用法

一个类型系统真正要回答两个问题：这个值只能是哪几个之一，以及这个对象至少得会做什么。前一个问题交给枚举，后一个问题交给 Protocol。剩下的写法——裸字符串、鸭子类型加注释——都是把答案留在了人的脑子里。

一、魔法字符串与魔法数字的代价

几乎每个业务系统里都有一段这样的代码：if order.status == "pending":。它能跑，读起来也不难看，很多人因此觉得引入枚举只是「风格问题」。但这里的代价不在观感上，而在四个具体的地方，每一个都会在项目变大之后变成真实的排查时间。

魔法字符串指的是直接写在业务逻辑里、没有任何定义来源的字面量字符串，比如上面那个 "pending"。它的第一个问题是：拼错不会报错。"pendng" == "pending" 只是求值为 False，程序继续往下走 else 分支，既不抛异常也不打日志。你得等到业务数据对不上，才会顺着结果反推回这一行。

同一段业务：判断订单是否待支付 ───────────────────────────────────────────────────────── 写法 A：裸字符串 写法 B：枚举成员 if order.status == "pendng": if order.status is Status.PENDNG: ↑ 少了一个 i ↑ 少了一个 I ┌──────────────────────────────┐ ┌──────────────────────────────┐ │ 运行时：表达式恒为 False │ │ 导入 / 求值时立刻抛 │ │ 静默走 else 分支 │ │ AttributeError: PENDNG │ │ 无异常 · 无日志 · 无告警 │ │ 栈顶就是出错那一行 │ │ 类型检查器：str == str，合法 │ │ 类型检查器：成员不存在，报错 │ └──────────────────────────────┘ └──────────────────────────────┘ │ │ ▼ ▼ 错误在「数据对账时」暴露 错误在「敲完这行时」暴露 定位成本：小时～天 定位成本：秒

第二个问题是取值范围无法枚举。系统里到底有多少种订单状态？裸字符串写法下，唯一可靠的答案是全局搜索所有和 status 比较过的字面量，然后祈祷没有漏掉动态拼出来的那几个。这直接导致第三个问题：改名就是全局替换，而字符串 "pending" 可能同时出现在状态判断、日志文本、前端字段名里，替换时无法机械区分。

第四个问题是类型检查器帮不上任何忙。在 status: str 这个签名下，"pending"、"peding"、"用户昵称" 是完全等价的合法值。检查器没有任何依据判断哪个对哪个错。而 status: Status 一写出来，检查器就获得了一个封闭的取值集合，可以做穷尽性检查——match 语句漏掉一个分支时它会告诉你。

示例场景：某订单系统的对账任务里写了 if o.status in ("paid", "shiped")，把 shipped 拼成了一个 p。任务每天凌晨跑，连续 11 天正常退出、日志全绿，直到财务发现累计 3,482 笔已发货订单没有进入结算流水，涉及金额对不上。排查用了 6 小时，修复只改了 1 个字符。改用 Status.SHIPPED 后，同类拼写错误会在这个模块被导入的瞬间抛 AttributeError，根本进不了生产。

所以枚举的价值可以概括成一句话：它把「这个字段的合法取值集合」从散落各处的约定变成了一个可以被检查、被遍历、被 IDE 跳转的对象。你可以对它按 F12 跳到定义，可以 list(Status) 拿到全部成员，可以让检查器替你盯住每一个分支。

裸字符串把「合法取值有哪些」这个知识存在人的记忆里，枚举把它存进代码里。区别在错误发生时才显现：前者静默走错分支，后者当场炸。

二、Enum 家族：四种基类怎么选

标准库 enum 模块提供的不是一个类，而是一族基类。它们的语法几乎相同，差别集中在成员与原始值之间的关系上，而这个差别决定了它能不能直接进数据库、会不会和无关的值意外相等。

先看最基础的 Enum。它的成员是唯一的单例对象，不是它的值。Color.RED 的类型是 Color，不是 int，因此 Color.RED == 1 为 False。这种「类型隔离」正是它的核心价值：一个颜色永远不会和一个无关的整数相等。

Color.RED 到底是个什么东西 ──────────────────────────────────────────────────── class Color(Enum): RED = 1 │ ▼ ┌────────────────────────────────────┐ │ Color.RED —— 一个单例成员对象 │ │ .name ──> "RED"（成员名） │ │ .value ──> 1（原始值） │ │ type() ──> <enum 'Color'> │ └────────────────────────────────────┘ Color.RED == 1 ──> False 值不等于成员 Color.RED is Color(1) ──> True 按值查回的是同一个对象 Color.RED is Color["RED"] ──> True 按名查回的也是同一个 class Level(IntEnum): LOW = 1 Level.LOW == 1 ──> True IntEnum 成员本身就是 int Level.LOW == Color.RED.value ──> True ← 意外相等的来源

IntEnum 让成员同时是真正的 int，因此可以直接参与算术、比较大小、被 json.dumps 序列化、被数据库驱动当整数写入。方便的代价是丧失类型隔离：任何值恰好相同的 IntEnum 成员之间会互相相等，哪怕它们语义上毫无关系（HttpStatus.OK == Priority.LOW 只要值都是 1 就成立）。

StrEnum（Python 3.11+）是字符串版的同一套权衡。在此之前常见写法是 class Status(str, Enum)，效果接近但 str() 和 f-string 的行为有微妙差异——旧写法下 f"{Status.PAID}" 得到的是 "Status.PAID"，而 StrEnum 得到的是 "paid"。和外部字符串协议打交道（HTTP header 名、消息队列的 topic、配置文件里的字段）时，StrEnum 是最省心的选择。

from enum import Enum, IntEnum, StrEnum, Flag, auto

class Status(StrEnum):          # 3.11+
    PENDING = "pending"
    PAID = "paid"

class Perm(Flag):
    READ = auto()               # 1
    WRITE = auto()              # 2
    ADMIN = READ | WRITE        # 3，组合成员

Flag / IntFlag 用于位标志——一组可以自由组合、用按位运算拼装的开关，典型场景是权限位和特性开关。它支持 |（并集）、&（交集）、in（包含判断），Perm.READ in user_perms 读起来就是自然语言。IntFlag 相对 Flag 多了「同时是 int」这一层，代价与 IntEnum 完全一致。

基类比较行为序列化 / 落库适用场景主要风险
Enum只与自身成员相等，推荐用 is需手动取 .value，json.dumps 会报 TypeError纯内部状态机、不出进程边界的分类忘了 .value 导致落库写进 "Color.RED"
IntEnum与相同数值的任意 int 相等可直接落库、可直接 JSON与既有整数编码兼容（状态码、错误码）类型隔离失效，不同枚举间意外相等
StrEnum（3.11+）与相同内容的任意 str 相等可直接落库、可直接 JSON、f-string 输出原值外部字符串协议：API 字段、topic、配置项同上；且 3.10 及以下不可用
Flag / IntFlag支持 | & ~ 与 in 组合判断Flag 需转 .value；IntFlag 可直接落库权限位、特性开关等可叠加的集合值必须是 2 的幂，手写数字易冲突，用 auto()

选型可以压成一条决策链：默认用 Enum；只有当这个值要跨出进程（落库、发消息、进 JSON、对接旧接口）时，才降级到 StrEnum 或 IntEnum 换取便利；需要组合叠加时用 Flag。注意「降级」这个词——放弃类型隔离是有代价的，不要因为写起来顺手就默认选 IntEnum。

Enum 换来类型安全，IntEnum / StrEnum 换来互操作性，两者不可兼得。判断标准很简单：这个值需不需要离开 Python 进程？不需要就用 Enum。

三、枚举的实用细节

枚举的语法只有一行，但真正会在项目里咬人的是几个细节。它们的共同点是：出问题时不报错，只是行为和你以为的不一样。

auto() 与 @unique：一个安静的坑

auto() 让你不必手写值，从 1 开始自动递增（Flag 里则按 2 的幂递增）。它适合「值本身没有业务含义、只是需要互相区分」的场合；反过来，如果这个值要落库或对接外部接口，务必显式写死——auto() 的结果依赖成员定义顺序，有人在中间插了一个成员，所有后续成员的数值就全变了，而已经落库的旧数据不会跟着变。

@unique 装饰器禁止两个成员共用同一个值。不加它并不会报错，而是把第二个成员变成第一个的别名——一个指向同一成员对象的另一个名字。别名不出现在 list(Status) 的遍历结果里，不出现在 Status.__members__.values() 的去重视图里，Status.CANCELLED is Status.VOID 会返回 True。这套行为本身是有意设计的（用于给枚举做平滑改名），但如果你只是手滑复制粘贴写重了值，它就成了一个完全静默的 bug。

示例场景：某风控系统的 RiskLevel 枚举里，新同事复制上一行加了 SUSPICIOUS = 2，而 MEDIUM 已经是 2。没有 @unique，于是 SUSPICIOUS 静默变成 MEDIUM 的别名。风控面板按 list(RiskLevel) 渲染筛选项，只出现 4 个档位而不是 5 个；更严重的是「可疑」命中的 1,207 条记录被统计进了「中风险」，两周后才被人工抽检发现。加一个 @unique 装饰器（1 行）就能让这次提交在导入时直接抛 ValueError: duplicate values found。

_missing_：接住上游新增的取值

当上游系统给你一个 Status("archived") 而你的枚举里没有这个成员时，默认行为是抛 ValueError。这在多数时候是对的，但如果你消费的是一个持续演进的外部接口，对方新增一个状态值就会让你的服务整批解析失败。_missing_ 类方法是官方给的兜底钩子：按值查找失败时会调用它，返回什么就用什么，返回 None 则继续抛错。

class Status(StrEnum):
    PENDING = "pending"
    PAID = "paid"
    UNKNOWN = "unknown"

    @classmethod
    def _missing_(cls, value):
        return cls.UNKNOWN          # 上游新增值时降级，不炸整批

用它的前提是你确实有一个合理的降级语义。如果未知状态本来就该报警，那就别写 _missing_，让它抛出来。把它当作「忽略错误」的开关是误用。

枚举是类，可以放业务逻辑

这是很多人没意识到的一点：Enum 的成员定义之外，你可以像普通类一样加方法、加 property、加 classmethod。于是「哪些状态算终态」这种知识可以直接挂在枚举上，而不是散落在各个调用点的 in (...) 判断里。这和 PY15 讲过的「让对象自己回答关于自己的问题」是同一个思路。

class Status(StrEnum):
    PENDING = "pending"
    PAID = "paid"
    CANCELLED = "cancelled"

    def is_terminal(self) -> bool:
        return self in (Status.PAID, Status.CANCELLED)

# 调用点从 status in ("paid", "cancelled") 变成 status.is_terminal()

最后一个约束：不要用可变对象作枚举值。list、dict、set 作为成员值时，按值查找 Color([1,2]) 会因为不可哈希而失败，而且成员值被就地修改后枚举的语义会彻底混乱。需要挂多个属性时用 tuple，或者自定义 __new__ 把附加信息存成 property。PY10 讲过的共享可变状态陷阱在这里同样成立。

操作写法说明
遍历全部成员list(Status)按定义顺序，不含别名
含别名的全量视图Status.__members__有序映射，名字 → 成员，别名也在里面
按值查找Status("paid")失败抛 ValueError，可被 _missing_ 接管
按名查找Status["PAID"]失败抛 KeyError，注意和上一行的异常类型不同
安全查找getattr(Status, name, None)不想处理异常时的写法
取名字 / 取值s.name / s.value落库、打日志时几乎总要用 .value
判断成员归属x in Status3.12+ 支持直接传原始值判断，旧版本只接受成员
禁止重复值@unique不加时重复值静默变别名

枚举出问题时几乎从不抛异常，只是「少了一个成员」或者「两个名字变成了同一个东西」。所以除非你明确想要别名，否则把 @unique 当成写枚举的标配。

四、名义子类型与结构子类型的分野

话题从「值」切到「行为」。枚举回答的是「这个值只能是哪几个」，接下来要回答的是「这个对象至少得会做什么」——也就是接口问题。而 Python 在这件事上长期存在一个割裂：运行时的规则和类型检查器的规则不是同一套。

名义子类型（nominal subtyping）靠声明判定：B 是不是 A 的子类型，取决于 B 的定义里有没有写继承 A。Java 的 implements、Python 的 class B(A) 和 ABC 都属于这一套。结构子类型（structural subtyping）靠形状判定：只要 B 具备 A 要求的那些方法且签名兼容，B 就是 A 的子类型，两者之间不需要任何声明关系。

问题：MyFile 算不算「一个能写的东西」？ ══════════════════════════════════════════════════════════════ 名义子类型 · 靠声明 结构子类型 · 靠形状 ────────────────────── ────────────────────── class Writable(ABC): class Writable(Protocol): @abstractmethod def write(self, s: str) def write(self, s: str): ... -> int: ... class MyFile(Writable): class MyFile: ← 不继承任何东西 def write(self, s): ... def write(self, s): ... │ │ ▼ ▼ 判定：查 MyFile.__mro__ 判定：逐个比对方法名与签名 里有没有 Writable write 在不在？签名兼容吗？ │ │ 在 → 是子类型 兼容 → 是子类型 不在 → 不是（哪怕方法全有） 不看继承关系一眼 │ │ 代价：要改实现方的继承链 代价：无。实现方一个字都不用改 第三方库的类你改不了 第三方库的类照样能满足

Python 的运行时从第一天起就是结构化的——这就是鸭子类型：解释器执行 obj.write(s) 时只做一件事，去 obj 上找名为 write 的属性，找到就调，找不到就 AttributeError。它从不关心 obj 继承自谁。

问题出在类型检查器上。mypy、pyright 这类工具早期只认名义关系，于是出现了一个很别扭的局面：代码明明能正常运行，检查器却报错。你写了一个接受「任何有 write 方法的对象」的函数，参数标注成 IO[str]，传进去一个自己写的、行为完全正确的假 sink，检查器立刻告诉你类型不匹配。为了让它闭嘴，你只能选：要么标注成 Any 放弃检查，要么强行让自己的类去继承一个本不需要的基类。

typing.Protocol（Python 3.8+，PEP 544）补上的正是这个缺口：它让鸭子类型第一次能被静态检查。你用一个只含方法签名的类描述「我需要的形状」，检查器就按结构去比对，而运行时什么都不变——协议类不产生任何继承关系，不影响 MRO，不改变方法解析（PY16 讲的那套 MRO 规则在这里完全用不上，因为压根没有新的继承边）。

维度ABC（抽象基类）Protocol（协议）
子类型判定名义：必须显式继承结构：方法对得上就算
实现方要改代码吗要，得加到继承列表里不用，实现方完全无感
能约束第三方库的类吗不能（除非用 register() 手工登记）能，第三方类天然可满足
能提供默认实现 / 共享代码吗能，这是 ABC 的主要价值之一不建议，协议应当只描述形状
忘记实现某方法会怎样实例化时直接 TypeError运行时不管；类型检查阶段报错
isinstance 支持原生支持，且会查方法是否齐全需 @runtime_checkable，且只查方法存在与否
协议 / 基类定义在哪一侧通常在实现方（库作者）推荐在消费方（使用者）
典型用途同一体系内的多个子类共享骨架跨库、跨体系的接口约定与测试替身

ABC 问的是「你爸是谁」，Protocol 问的是「你会干什么」。Python 运行时从来只问后一个问题，Protocol 只是让类型检查器终于也开始问同一个问题。

五、Protocol 怎么用

定义一个协议就是写一个继承 Protocol 的类，里面只放方法签名，方法体写 ...。任何实现了这些方法的类自动满足它，不需要继承、不需要注册、不需要修改被约束的那个类——这最后一点是相对 ABC 的决定性优势：你无法让别人的库去继承你的基类，但你可以让你的协议去描述别人的库。

from typing import Protocol

class SupportsWrite(Protocol):
    def write(self, s: str) -> int: ...

def dump_report(rows: list[str], sink: SupportsWrite) -> None:
    for r in rows:
        sink.write(r + "\n")

# open() 的文件对象、io.StringIO、sys.stdout、你的测试替身，全都能传

协议应当定义在使用方

这是最容易被写反的一点。习惯了 Java 风格接口的人会把协议放在实现方旁边，当成「实现者要遵守的规范」。但 Protocol 的正确用法是依赖倒置：由消费者声明「我需要一个能做 X 的东西」，然后所有能做 X 的东西自动符合。协议文件里不 import 任何实现，实现文件里也不 import 协议——两边完全解耦。

依赖倒置：协议长在消费者这一侧 ══════════════════════════════════════════════════════════════ report.py ← 消费者，也是协议定义方 ┌──────────────────────────────────┐ │ class SupportsWrite(Protocol): │ │ def write(self, s) -> int: ...│ │ │ │ def dump(rows, sink: │ │ SupportsWrite): ... │ └──────────────────────────────────┘ ▲ │ 「谁满足这个形状？」 ┌────────────┬───────────┼───────────┬────────────┐ │ │ │ │ │ io.StringIO open() 文件 sys.stdout socket 包装 FakeSink 标准库 标准库 标准库 第三方库 测试替身 │ │ │ │ │ └────────────┴───────────┴───────────┴────────────┘ 五者互不相识，都没有 import 过 report.py，也没继承任何基类 却全部自动满足 SupportsWrite —— 依赖箭头只从右指向左 换成 ABC 的话：上面这五个里，你只能改动最后一个。

@runtime_checkable 只检查方法名

协议默认不支持 isinstance，加上 @runtime_checkable 装饰器之后可以。但必须清楚它做了什么：它只检查那几个方法名存不存在，完全不看签名。一个 write() 不接受任何参数的类，照样能通过 isinstance(obj, SupportsWrite)；真正调用时才抛 TypeError。它也不检查属性（非方法成员）——对只声明了数据属性的协议，isinstance 会直接抛 TypeError 拒绝执行。

所以 @runtime_checkable 的定位是「粗筛」，不是校验。用它做分派前的快速判断可以，把它当成「我验证过这个对象符合契约了」就是误用。真正的把关在类型检查阶段——那里才会逐个比对签名。

协议要小

一个协议只放一两个方法时最好用。原因很直接：协议越大，能满足它的类越少，你就越接近「必须专门写个适配器」的状态，而那正是 Protocol 想要消除的东西。标准库 typing 里那批 SupportsInt、SupportsFloat、SupportsIndex 全都只有一个方法，这个尺度是有意的。需要多个能力时，把几个小协议组合起来（一个协议可以继承多个协议），比写一个大协议灵活得多。

示例场景：某服务的推送模块依赖一个第三方 SDK 的 PushClient，测试时无法真发请求。原方案是定义抽象基类 BasePushClient，再写一个适配器把 SDK 的客户端包起来去继承它——适配层共 3 个文件、214 行，且 SDK 每次升级加方法都要同步改一遍。改成在调用方定义一个只含 send(self, msg: str) -> bool 的 Protocol 后，SDK 客户端零改动自动满足，适配层 214 行全部删除，测试替身缩到 4 行。SDK 后续两次升级都没有再触碰这个模块。

ABC 是「我规定你要长什么样」，Protocol 是「我描述我需要什么样」。前者要求全世界配合你，后者只要求你把需求写清楚——所以协议应该长在需要它的那一侧。

六、组合使用与选型

枚举和 Protocol 在实践里常常同时出现，因为它们回答的是同一个建模问题的两半：用枚举表达「有哪些种类」，用 Protocol 表达「每种要能做什么」。前者给你一个封闭的、可遍历的集合，后者给你一个开放的、可扩展的能力约定。

但真到写代码时，「按种类做不同的事」有三条路，它们的适用规模差得很远。选错的典型症状是：为 2 个分支引入了 5 个类，或者一个函数里堆了 12 个 elif。

「按种类做不同的事」的三条路 ══════════════════════════════════════════════════════════════ A. 枚举 + if/elif 分派 if kind is Kind.PDF: return to_pdf(data) elif kind is Kind.CSV: return to_csv(data) ├ 适用：分支 ≤ 3、逻辑短、不常变 ├ 优点：最直白，读代码不用跳文件 └ 代价：每加一种就要改这个函数；漏分支只能靠检查器兜 B. 枚举 + 字典分派表 ← 多数场景的甜点 HANDLERS = {Kind.PDF: to_pdf, Kind.CSV: to_csv} HANDLERS[kind](data) ├ 适用：3～8 种、每种就是一个函数、无额外状态 ├ 优点：加一种只加一行；可断言 set(HANDLERS) == set(Kind) └ 代价：分派表和枚举要同步维护 C. Protocol + 多实现 class Renderer(Protocol): def render(self, data) -> bytes: ... ├ 适用：每种自带状态 / 多个方法 / 要被外部扩展 ├ 优点：新增实现完全不碰既有代码，测试替身随手写 └ 代价：类多了，读一条链路要跳好几个文件 分界线：行为只有「一个函数」时选 B；行为是「一组方法 + 状态」时选 C。

B 方案有个值得写进代码的小技巧：在模块导入时加一句 assert set(HANDLERS) == set(Kind)。这一行把「分派表漏了一种」从运行时的 KeyError 提前到了导入时的 AssertionError，成本一行，收益是这类遗漏永远进不了生产。这也是把枚举「可遍历」这个性质用起来的典型方式——裸字符串写法下你根本无法写出这句断言。

至于 Enum、Protocol、ABC 三者之间怎么选，可以按「你到底想约束什么」来分：

你的需求选它为什么
某字段只能取固定的几个值Enum取值集合可遍历、可跳转、拼错立刻报错
取值要落库 / 进 JSON / 对接外部协议StrEnum（3.11+）或 IntEnum成员本身就是 str/int，无需处处 .value
一组可自由叠加的开关Flag / IntFlag按位组合与 in 判断是现成的
约定「能做什么」，且实现方不受你控制Protocol第三方类零改动即可满足，依赖只往一个方向走
测试里要替换掉某个重依赖Protocol替身只需实现用到的那一两个方法
多个子类要强制实现某些方法并共享代码ABC能给默认实现，漏实现时实例化即报错
需要一个类型体系的显式标识（isinstance 做真分派）ABC名义关系明确，运行时判定可靠

最后提醒一个组合上的细节：如果你想让某个枚举本身满足一个协议（比如所有状态枚举都要能 describe()），直接在枚举类里定义那个方法即可，不需要也不应该让枚举去继承 Protocol——协议是给检查器看的形状描述，不是给运行时用的继承边。

  • 业务上「只能是这几个之一」的字段一律用枚举，别用裸字符串
  • 枚举默认加 @unique，除非你明确要造别名
  • 值要落库或出网时用 StrEnum（3.11+）；纯内部状态用 Enum 加 is 比较
  • 把「哪些是终态」这类判断写成枚举方法，别散在调用点
  • 协议定义在消费方，一个协议只放一两个方法
  • 分派表旁边加 assert set(HANDLERS) == set(Kind)
  • 要共享代码和默认实现时用 ABC，只要约定形状时用 Protocol
  • 为了写起来顺手默认选 IntEnum——它会和无关整数意外相等
  • 给要落库的枚举用 auto()——插入一个成员就会改掉后面所有数值
  • 用 list / dict 这类可变对象作枚举值
  • 把 @runtime_checkable 的 isinstance 当成契约校验（它不看签名）
  • 写一个带十几个方法的大协议，然后被迫为每个实现写适配器
  • 为了迁就类型检查器，强行让业务类去继承一个用不上的基类
  • 用 _missing_ 吞掉本该报警的未知取值

枚举收敛「有哪些」，Protocol 收敛「会什么」。判断自己有没有用对：新增一个种类时要改几处？新增一个实现时要动既有代码吗？答案分别是「一处」和「不用」，模型就立住了。

Q&A

枚举成员比较到底该用 == 还是 is？
对普通 Enum，两者都能得到正确结果，但推荐用 is。因为枚举成员是单例对象，is 表达的正是「就是这个成员」这层语义，而且它不会被 __eq__ 的任何自定义行为影响。到了 IntEnum 和 StrEnum 上这个选择就变得有实际差别了：Level.LOW == 1 为真，而 Level.LOW is 1 为假，如果你想要的是「严格是这个枚举成员」，只有 is 能表达。反过来，当你在和外部传进来的原始 str/int 比对时，就该用 == 并显式选用 StrEnum/IntEnum。一个简单的习惯是：内部逻辑判断一律 is，跨边界的值比对才用 ==。
已有一堆用字符串表示状态的老代码，怎么平滑迁移到枚举？
用 StrEnum（3.11 以下用 class Status(str, Enum)）做过渡，因为它的成员本身就是字符串，和既有的 == "pending" 比较、JSON 序列化、数据库读写全都保持兼容，可以先把枚举定义加进去而不改任何调用点。第二步是把所有产生状态值的地方（构造、反序列化、ORM 字段）换成枚举成员，让新数据从源头就是枚举。第三步再逐个把消费端的字面量比较换成枚举成员比较，这一步可以靠全局搜索字面量来定位。全部换完之后，如果状态不再需要出网，可以考虑从 StrEnum 收紧到 Enum 拿回类型隔离。整个过程每一步都可独立上线，不需要大爆炸式替换。
@unique 到底防的是什么？不加会怎样？
它防的是「两个成员写了同一个值」这件事静默通过。不加 @unique 时，第二个同值成员不会报错，而是成为第一个的别名——两个名字指向同一个成员对象。别名的行为很有迷惑性：Status.A is Status.B 为 True，list(Status) 里只出现一个，但 Status.__members__ 里两个都在。这套机制本身是为枚举改名设计的，让旧名字继续可用而不产生新成员。问题在于手滑写重值时的表现和它一模一样，没有任何提示。所以除非你在刻意造别名，否则把 @unique 当作写枚举的默认装饰器，它会把重复值变成导入时的 ValueError。
Protocol 和 ABC 到底怎么选？能不能一直用 Protocol？
决定性的判断点有两个。第一，实现方在不在你的控制范围内：要约束第三方库的类，只能用 Protocol，因为你没法改别人的继承列表。第二，你要不要提供共享代码：ABC 可以写默认实现、模板方法、公共的辅助逻辑，多个子类共用一套骨架；Protocol 只描述形状，写默认实现是反模式。所以不能一直用 Protocol——当你有一族同源的子类需要共享代码，并且希望「漏实现某个方法时实例化就报错」这种硬约束，ABC 更合适。实践中最常见的组合是：对外的接口约定用 Protocol，对内的类族骨架用 ABC。
加了 @runtime_checkable 之后，isinstance 检查可靠吗？
只能算粗筛，不可靠。它做的事仅仅是遍历协议里声明的方法名，逐个检查目标对象上有没有同名属性，完全不看参数个数、参数类型和返回类型。一个 write() 不接受任何参数的类可以毫无阻碍地通过 isinstance(obj, SupportsWrite)，等到真正调用时才抛 TypeError。另外它不支持只声明数据属性的协议，那种情况下 isinstance 会直接拒绝执行并抛错。真正逐条比对签名的是静态检查阶段的 mypy 或 pyright。所以正确的分工是：靠静态检查保证契约正确，isinstance 只用来做运行时的快速分类判断。
为什么说协议应该定义在使用方，而不是实现方？
这是依赖倒置原则在类型层面的体现。协议放在实现方时，它退化成了「实现者要遵守的规范」，消费者必须 import 实现方的模块才能标注类型，依赖箭头就从消费者指向了实现——和普通继承没有本质区别。放在消费方时，协议表达的是「我需要一个能做 X 的东西」，实现方对协议的存在完全无感，两个模块之间没有任何 import 关系，依赖箭头只从实现指向抽象。实际收益很具体：同一个实现可以同时满足好几个消费者各自定义的小协议；替换实现时消费方一行不用改；测试替身只需实现消费方真正用到的那一两个方法，而不是整个接口。标准库 typing 里那批 SupportsInt 之类的协议就是这个思路。
枚举值该用 auto() 还是手写死？
取决于这个值会不会离开你的代码。如果它只在进程内部用来区分成员，值本身没有业务含义，auto() 更好，省得手工维护还写重。但只要这个值要落库、进 JSON、发消息、或者和外部接口的编码对齐，就必须显式写死。原因是 auto() 的结果依赖成员的定义顺序：有人在中间插入一个新成员，后面所有成员的数值会整体后移，而数据库里已经存下的旧数字不会跟着变，于是历史数据的语义被静默改写。这类事故的排查难度很高，因为代码看起来完全正常。一个折中办法是即使用了 auto()，也只往末尾追加成员，但显式写死显然更稳。
枚举可以放业务方法吗？会不会把模型搞重？
可以放，而且往往应该放。Enum 本质上是一个类，成员定义之外可以正常写方法、property 和 classmethod。把「哪些状态算终态」「这个状态对应的中文名是什么」这类只依赖枚举自身的判断写成方法，比让每个调用点各写一遍 in ("paid", "cancelled") 要可靠得多——后者是典型的知识散落。边界在于：只放仅依赖枚举自身的逻辑。一旦某个方法需要查数据库、调服务、或者依赖别的业务对象，它就不该待在枚举里，那说明你在把领域服务塞进值对象。判断标准是这个方法会不会 import 业务模块，会的话就搬出去。
状态很多、每种行为都不一样，该用枚举加分派表还是 Protocol 加多实现？
看「行为」的形态而不是种类的数量。如果每种类型对应的行为就是一个函数、没有额外状态，用枚举加字典分派表最划算：新增一种只加一行，还能在导入时断言分派表和枚举完全对齐。如果每种类型自带配置或状态、要暴露好几个方法、或者需要被外部扩展（比如插件），那就值得上 Protocol 加多实现，代价是类变多、读一条链路要跳文件。经验上的分界大约在 3 到 8 种之间：低于这个区间连字典都不用，直接 if/elif；高于它且行为复杂时多态才回本。最糟的两种情况是为 2 个分支建 5 个类，以及在一个函数里堆 12 个 elif。
