PY45 · 调试工具箱与排查方法

收敛式排查流程 / 回溯与异常链的读法 / breakpoint() 与事后调试 / 不能打断点时的手段 / 工程化小组收束

排查的本质是把「可能出错的地方」这个集合一次次砍半，直到只剩一个。所有工具——回溯、断点、剖析器、日志——都只是砍半的手段；先有收敛的流程，工具才有用，否则只是换着花样猜。

一、排查是个收敛过程，不是猜谜

「改一行，重启看看」这种做法在几百行的脚本上是有效的，因为可能出错的地方本来就只有几处，穷举很快。但一旦系统里有了依赖、并发、外部服务和环境差异，可疑点的数量会从个位数跳到几十上百，穷举立刻失效——你会发现自己改了两个小时，问题时好时坏，而且已经说不清是哪一次改动起的作用。

专业排查和猜谜的区别只有一条：每一步都必须让可疑范围变小。达不到这个效果的操作（重启、清缓存、随便加点日志、把 try 范围扩大）不是排查，是拖延。

一条可复用的五步流程

收到一个「它坏了」 │ ▼ ① 稳定复现 ────────── 复现不了？ ──→ 先补可观测性，不要硬猜 目标：一条命令 / 一个请求， （见第四节） 跑十次坏十次 攒够样本再回到 ① │ 能复现了 ▼ ② 缩小范围（二分，一次只动一个维度） ┌───────────┬───────────┬───────────┬───────────┐ │ 输入数据 │ 代码版本 │ 依赖版本 │ 运行环境 │ │ 砍掉一半 │ 好坏之间 │ 锁文件回退 │ 本机／容器 │ │ 还坏吗？ │ 二分提交 │ 逐个还原 │ ／CI 对比 │ └───────────┴───────────┴───────────┴───────────┘ │ 范围小到「就这一段」 ▼ ③ 形成一个可证伪的假设 ✗「大概是缓存的问题」 ← 无法证伪，等于没说 ✓「第二次调用命中了缓存， ← 可以用一次实验判真假 返回了上一次的过期对象」 │ ▼ ④ 改一处 → 验一次 → 记录结论（真／假） │ 假设为假就回退，回到 ② ▼ ⑤ 修复 + 补一条能复现原问题的测试 + 写进事故记录

第 ①、④ 两步最容易被跳过。跳过 ① 的代价是你永远无法确认「修好了」，只能说「这两天没再出现」；跳过 ④ 的代价更隐蔽——复合改动会让你失去因果判断能力：同时改了三处之后问题消失，你不知道是哪一处生效，也不知道另外两处是不是引入了新问题。

为什么「一次改多处」这么致命：它把一次实验变成了一次赌博。假设三处改动中只有第二处有用，你会把三处全部保留并当作「修复方案」提交，于是第一、三处成了没人理解、也没人敢删的代码。半年后有人清理它们，问题重现，而事故记录里写的是三条一起的方案，没有任何信息能帮到他。判据：一次实验只允许存在一个变量。忍不住想一起改的时候，说明你其实没有假设，只有直觉。

先分诊，再选工具

不同症状对应完全不同的第一手段。把工具用错顺序是常见的浪费——比如对「结果不对」这类问题一上来就打开剖析器，或者对「慢」的问题去逐行单步。下面这张分诊表给出每类症状的起手式。

症状类型第一手段第二手段不要一上来就做
崩溃 / 进程直接退出读完整回溯与退出码faulthandler、核心转储套一层 try/except 把它吞掉
错误结果（稳定复现）做最小复现，断点查中间值对拍：同一输入跑新旧两版比对全量加日志（噪声淹没信号）

复现不了不是「先猜着改」的理由，而是「可观测性不够」的信号。这时唯一正确的动作是加埋点然后等，而不是上线一个自己也不确定的改动——后者会同时污染现场和结论。

二、读懂回溯信息：它说了什么，没说什么

回溯（traceback）是成本最低的排查材料，但很多人只看最后一行的异常消息，把上面那几十行当作噪声划过去。这会丢掉最有价值的信息：异常是在哪个调用路径下被抛出来的。同一个 KeyError，出现在配置加载路径上和出现在请求处理路径上，是两个完全不同的问题。

阅读顺序：从下往上，再从上往下

Traceback (most recent call last): ← 标题就写明了顺序：最近的调用在最后 File "app.py", line 42, in handle return render(build_ctx(req)) ~~~~~~~~~~~~~~~~~~~~~~ ← 3.11 起的细粒度定位（PEP 657） File "render.py", line 17, in render 指出是这一段表达式出的事 return tpl.format(**ctx) File "ctx.py", line 9, in __getitem__ return self._data[key] ~~~~~~~~~~^^^^^ KeyError: 'user_name' ← ① 先看这里：什么错、错在什么值上 读法： ① 最后一行 ── 异常类型 + 消息（是什么） ② 倒数第二块 ── 抛出点，文件／行号／函数（在哪） ③ 从上往下扫 ── 调用路径，谁把它带到这里的（怎么来的） ④ 找边界 ── 路径里哪一帧是「我的代码」和「库的代码」的交界 绝大多数根因就落在这一帧上 注意：faulthandler 打印的栈顺序是相反的 （most recent call first），别按同一个习惯读

第 ④ 步是熟手和新手差别最大的地方。当回溯里有二十帧、其中十八帧属于框架或标准库时，真正值得看的是那个「你的函数调用了库的函数」的交界点——因为你能改的、也最可能传错东西的，就是那一帧。

异常链的三种形态

Python 3 会把「一个异常引发了另一个异常」这层关系也打印出来，三种形态在回溯里长得不一样，分别对应三种不同的代码意图。把它们认出来能省下大量时间——尤其是第二种，它往往说明你的错误处理分支本身也是错的。

形态写法回溯中间那句提示含义
显式引发raise New() from oldThe above exception was the direct cause of the following exception有意转译：底层错误被包装成业务语义的错误（__cause__）
隐式带上在 except 块里又抛出During handling of the above exception, another exception occurred处理错误时自己也出错了，两个都要看（__context__）
显式断开raise New() from None没有提示，只显示新异常有意隐藏内部细节，只对外暴露干净的错误（__suppress_context__）
try:
    cfg = json.loads(raw)
except json.JSONDecodeError as e:
    # 显式引发：保留原因，回溯里两段都在
    raise ConfigError(f"配置文件不是合法 JSON: {path}") from e

看到第二种（During handling…）时要格外警觉：它意味着 except 分支里的代码自己炸了。最常见的是在错误处理里访问了一个只在成功路径上才被赋值的变量，于是真正的原始错误被一个 UnboundLocalError 或 NameError 盖住，看起来像是「报错信息完全对不上」。异常层次怎么设计、什么时候该用 from，在 PY24 异常体系设计里有完整讨论，这里只讲怎么读。

回溯能给你什么，给不了什么

你能从回溯里拿到你拿不到
异常类型、消息，以及 3.11 起的表达式级定位标记出事那一刻各个变量的值
抛出点的文件、行号、函数名循环执行到第几轮才出的事
完整调用路径：谁调用了谁抛出前那几行做了什么、走了哪个分支
异常链：谁引发了谁、是否被刻意断开别的线程或任务当时在干什么
发生在哪个线程（多线程崩溃时的线程名）外部依赖当时返回了什么

右边那一列就是断点和日志存在的全部理由。回溯给的是控制流快照，缺的是数据快照；接下来两节讲的两类手段，本质上都是在补右边这一列——能让程序停下来时用断点，不能停下来时用日志。

回溯告诉你「代码是怎么走到这里的」，从来不告诉你「当时数据长什么样」。凡是你盯着回溯看了五分钟还没头绪的，缺的几乎一定是数据，这时该做的是加一个断点或一条带值的日志，而不是把回溯再读一遍。

三、交互式调试：让程序停在你想看的那一刻

很多人不用调试器，理由是「插 print 更快」。在只想看一个值时确实如此，但一旦你需要看的是「这个对象在第 173 次循环时的完整状态」或者「这个值是从哪一层传进来的」，print 的成本就开始指数上升：你得猜要打印什么、改代码、重跑、发现打错了、再改再跑。调试器把这个循环压缩成一次——程序停在现场，整个作用域都能查。

breakpoint()：断点不必写死在代码里

Python 3.7 起有一个内置函数 breakpoint()（PEP 553）。它比老写法 import pdb; pdb.set_trace() 强的地方不在于少打字，而在于它是可被外部切换的：breakpoint() 实际调用的是 sys.breakpointhook()，而这个钩子由环境变量 PYTHONBREAKPOINT 决定。

PYTHONBREAKPOINT 的值breakpoint() 的行为用途
未设置（或为空）进入标准库调试器 pdb默认，本地开发
0直接返回，什么都不做生产／CI 兜底：即使代码里漏了一个断点也不会挂住进程
一个可导入的可调用对象名改为调用它换成别的调试器，或换成「把栈打到日志里」这类自定义动作

这条机制的实际价值是：临时断点不再需要「改代码加、改代码删」的往返。你可以在排查期间把 breakpoint() 留在几个关键位置，靠环境变量控制它是否生效。不过要说清楚——这不等于鼓励把 breakpoint() 提交进仓库，它只是给你一层兜底，防止漏删的那一个把线上进程挂死。真正的纪律仍然是提交前清干净，并在 CI 里加一条禁止 breakpoint() 的检查。

事后调试：在异常现场直接开查

事后调试（post-mortem）解决的是这样一个尴尬：异常已经抛了，栈也已经退了，你想看的那些局部变量本该随之消失——但 Python 把它们留在了 traceback 对象引用的帧里，所以还能进去翻。

# 交互式解释器里刚炸完，直接进现场
import pdb; pdb.pm()          # 用 sys.last_exc 里那个异常

# 让脚本异常退出时自动进调试器
python -m pdb app.py          # 异常退出后自动进入事后调试

# 测试里最常用的一种
pytest -x --pdb               # 第一个失败的用例当场停在现场

pdb.post_mortem(t) 接受一个 traceback 或（3.13 起）异常对象，pdb.pm() 是它读取 sys.last_exc 的便捷形式。3.13 还加了 exceptions 命令，可以在异常链的各段之间来回跳——配合第二节讲的三种链形态，能直接跳到最底层那个真正的原因帧上去看变量。

四、打不了断点的场合怎么查

断点有一个隐含前提：你能让这个程序停下来。生产进程停不得（一停就是故障），容器里通常没有可交互的终端，偶发故障你不知道该在什么时候停，而卡死的进程压根没有异常可以触发事后调试。这四种场合覆盖了线上排查的绝大部分，所以必须有一套不依赖「停下来」的手段。

我能让它停下来吗？ │ ├── 能（本地、测试环境、可复现） │ └─→ 断点 / 条件断点 / 事后调试 ← 第三节 │ └── 不能 │ ├── 它还活着，但行为不对或很慢 │ └─→ 采样剖析器按 PID 抓栈（不改代码、不重启） │ 3.14 起也可以 python -m pdb -p PID 直接挂上去 │ 代价：只有栈，没有变量值；挂调试器会暂停业务 │ ├── 它卡死了，不返回也不报错 │ └─→ 看门狗：faulthandler.dump_traceback_later(超时) │ 到点自动把所有线程的栈打到 stderr │ ├── 它直接崩了（段错误之类，没有 Python 回溯） │ └─→ faulthandler.enable() 或 PYTHONFAULTHANDLER=1 │ 崩溃时打印 Python 层的栈；再不够就核心转储 │ └── 它偶发，你根本不知道什么时候发生 └─→ 没有捷径：提前把关键中间状态打成结构化日志 这是唯一能「事后回放」的手段

四类手段各自的边界

采样剖析器（py-spy、austin 这一类）的关键能力是挂到运行中的进程：给它一个 PID，它就能周期性地读出目标进程里每个线程的 Python 调用栈，目标进程不需要改一行代码、不需要重启、也基本不受影响。它既能回答「慢在哪」（累积采样出火焰图），也能回答「卡在哪」（一次性 dump 当前栈）。代价是它只看得到栈，看不到变量值；另外读别的进程的内存需要相应权限，在容器里往往要额外授予 ptrace 能力，这件事要在部署清单里提前写好，不要等出事时才发现拿不到。具体工具的命令行参数各版本会变，用之前查一下它自己的文档。

faulthandler 是标准库模块，专门解决「解释器层面崩了，没有 Python 回溯」的问题。faulthandler.enable() 会为 SIGSEGV、SIGFPE、SIGABRT、SIGBUS、SIGILL 装上处理器，崩溃时把 Python 栈打到 stderr；也可以不改代码，用 PYTHONFAULTHANDLER=1 或 -X faulthandler 在启动时开启（开发模式 -X dev 会自动开）。dump_traceback_later(timeout, repeat=False, exit=False) 是一个看门狗定时器，到点打印所有线程的栈，抓卡死特别顺手。

关于 Windows 需要说清楚两件事，别踩空：enable() 和 dump_traceback_later() 在 Windows 上可用（3.6 起 enable() 还会一并安装 Windows 异常处理器）；但基于用户信号按需打印栈的 faulthandler.register() / unregister() 在 Windows 上不提供，官方文档明确标注为不可用。所以 Linux 上那套「给进程发个 SIGUSR1 让它吐一份栈」的常用招数，在 Windows 上没有对应物，只能改用定时看门狗或外部采样器。还要注意 faulthandler 的输出是简化版：只有文件名、函数名、行号，没有源码行也没有变量；只支持 ASCII，每个字符串截断到 500 字符，最多 100 帧 100 线程；而且顺序和普通回溯相反，最近的调用在最前面。

核心转储与事后分析是最后的手段：让操作系统把崩溃瞬间的整个进程内存写成文件，事后用系统级调试器配合 CPython 的调试辅助脚本还原出 Python 层的栈。它能看到 C 扩展内部的状态，这是别的手段做不到的；代价也最高——转储文件动辄几 GB，需要与线上完全一致的二进制和调试符号，流程还与操作系统强绑定。只有在怀疑 C 扩展或解释器本身出问题时才值得走这条路。

结构化日志听起来最土，覆盖面却最广，而且是唯一能处理「偶发」的手段。要点不是「多打日志」，而是打对东西：每条日志带上请求或任务的唯一 id（串起一次完整处理）、带上关键中间状态的值而不只是「进入了某函数」、用字段而不是拼接好的句子（这样才能按值过滤和聚合）。判断标准很直接：出事后你能不能只靠日志把那一次的处理过程复述出来。能，可观测性就够了；不能，下次还是只能等它再发生一次。

场景可用手段代价与前提
生产进程在跑，不能停采样剖析器按 PID 抓栈；3.14 起 pdb -p PID只有栈无变量；需要 ptrace 类权限；挂调试器会真的暂停业务
容器里，没有可交互终端结构化日志 + 外部采样；把栈 dump 写到挂载卷采样能力要在镜像与安全策略里提前放行
卡死，不返回也不报错faulthandler.dump_traceback_later() 看门狗；采样器一次性 dump看门狗要预先装上；输出只有栈
进程直接崩，没有 Python 回溯faulthandler.enable()；核心转储 + 系统调试器输出简化（无源码无变量）；转储体积大、要符号、按平台走
偶发，几百次一次提前埋好的结构化日志 + 留存输入样本存储成本；必须在事故之前就埋好，事后补来不及
需要按需拿栈（Unix）faulthandler.register(signo) + 发信号Windows 不提供此接口，改用看门狗或外部采样器

断点是「我能让它停」时才有的特权。不能停的时候，你能用的只有「它自己说过的话」和「外面看得见的栈」。所以可观测性不是出事之后补的东西——它决定了出事那一刻你手上到底有没有牌。

五、五类疑难症状与定位路径

下面五类问题的共同点是：报错信息指向的位置和真正的根因离得很远，所以「照着报错查」会反复扑空。每一类给一条固定的起手路径，照着走能在十分钟内把范围收敛到一两个候选。

本地能跑，线上报缺模块

先看三件事，顺序不要换：第一，跑代码的解释器和装包的解释器是不是同一个（打印 sys.executable，再用 python -m pip list 而不是裸 pip list 看包）；第二，这个依赖有没有真的进入声明文件和锁文件，还是只活在你本机的环境里；第三，启动方式变了没有——python app.py 与 python -m app 的 sys.path[0] 不同，前者是脚本所在目录，后者是当前工作目录，很多「换了个启动方式就 import 不到」都出在这里。都排除了再看打包：非 .py 的数据文件、命名空间包、隐式依赖在打包时被漏掉，是容器里最常见的一类。这条链路的原理在 PY08 模块与包里有完整说明。

结果偶发不对

偶发的错误结果几乎总是三种来源之一：共享可变状态（可变默认参数、模块级全局、类属性被当成实例属性用，参考 PY09 对象模型与 PY10 拷贝语义）、隐含的顺序假设、隐含的环境默认值（本地时区、区域设置、随机种子）。

「同样的输入，有时候结果不一样」的二分路径 这份输入，在同一个进程里连跑两次结果一样吗？ ├── 不一样 ──→ 有状态被带过去了 │ 查：模块级可变全局、可变默认参数、 │ 类属性、缓存、单例里的累积值 └── 一样 │ 换一个新进程再跑，结果和刚才一样吗？ ├── 不一样 ──→ 进程级的不确定性 │ 查：集合迭代顺序（依赖哈希， │ 而 str／bytes 哈希每进程随机化） │ 随机数种子、字典以外的无序结构 └── 一样 │ 换一台机器／换个时间点跑呢？ ├── 不一样 ──→ 环境差异 │ 查：时区（本地 vs UTC）、区域设置、 │ 文件系统大小写、依赖版本 └── 一样 ──→ 不是偶发，是输入没复现全 回到「稳定复现」这一步

顺序假设这一条要说清楚一个常见误解：字典自 Python 3.7 起保证按插入顺序迭代，这是语言层面的承诺，可以依赖。真正没有顺序承诺的是 set 和 frozenset——它们的迭代顺序由元素哈希决定，而 CPython 默认对 str 和 bytes 的哈希做每进程随机化（由 PYTHONHASHSEED 控制）。所以同一份数据，在不同的 worker 进程里遍历同一个集合，顺序可以完全不同。容器各自的顺序承诺见 PY03 容器总览。

事故复盘：一个只在生产出现的偶发计算错误。某报表服务的「Top N 归因」结果偶发和用户手算对不上，用户报障每天 2～3 次。本地拿同一批数据连跑 2000 次全部正确，生产侧统计下来约每 1800 次请求出现 1 次（≈0.055%），故障持续 11 天，累计 4217 条记录的归因字段与事后重算结果不一致。前 3 天全耗在「本地复现不出来」上——反复加大数据量、反复重跑，一无所获。转折点是放弃复现，改为在生产把「候选集合的全部元素」和「最终选中的那个」一起打成结构化日志；两天后攒到 3 个异常样本，一眼看出同一个候选集在不同请求里选出了不同的代表。根因是去重时用了 set，然后直接取迭代出的第一个元素当代表；打分并列时哪个排在前面取决于字符串哈希，而它每进程随机。本地数据规模小、并列几乎不出现，所以「总是对的」。修复是去重后显式 sorted() 再取首个，共改 6 行；同时补了一条测试，用不同的 PYTHONHASHSEED 各跑一遍并断言结果一致。总定位耗时 4 天，其中 3 天可以省掉——只要一开始就承认「复现不了就先补可观测性」。

内存只涨不落

先分清是泄漏还是没还给操作系统：前者是对象还被引用着回收不了，后者是对象已经回收但内存留在分配器里，后者通常不需要处理。确认是泄漏后，按可能性排查三处：无上限的缓存（模块级字典当缓存用，只写不淘汰）、长生命周期容器留存了引用（注册表、监听器列表、任务列表只增不删）、循环引用叠加自定义析构逻辑。手段上用 tracemalloc 在两个时间点各取一次快照做差，直接看哪一行分配的内存在涨。完整机制见 PY23 内存模型与 GC。

卡死，没有任何报错

卡死只有两种可能：在等一个永远不会来的东西，或者死锁。第一步永远是抓栈（看门狗或外部采样器），看它停在哪一行——这一步就能区分开两者。等待型的根因通常是某个外部调用没设超时（网络请求、数据库查询、队列 get、子进程 wait），判据很简单：任何会阻塞的调用都必须有超时，没有超时的等待迟早会变成一次生产故障。死锁型则要看多个线程的栈：两个线程各自持有一把锁、又在等对方那把，就是典型的获取顺序不一致，解法是全局约定一个固定的加锁顺序。异步场景下的卡死有自己的一套排查方式（任务被静默取消、忘记 await、事件循环被同步调用阻塞），见 PY34 异步调试与故障排查。

只在 CI 上失败

本地全绿、CI 全红，差异一定来自环境或执行方式，按下面这张表逐条对。

可疑点怎么验证典型表现
用例之间互相影响本地用随机顺序跑一遍；单独跑那个失败用例单独跑过，一起跑挂；换个顺序换一批失败
并行执行争抢资源把并行度降到 1 再跑临时目录、端口、测试库被多个用例同时写

「只在 X 上失败」是一份礼物，不是坏消息——它已经帮你把范围缩小到「本地和 X 的差异集合」里了。把这个集合列出来（版本、时区、文件系统、并行度、启动方式），逐条对齐，通常五条之内就能命中。

六、工程化小组收束：把这一组串成一条线

这一组讲的看起来是八件不相干的事：依赖、CI、镜像、测试、性能、可观测性、发布、排查。但它们回答的是同一个问题——怎么让「它在我这儿是好的」变成一句可以被别人验证的话。每一项都是在消除一种「只有你知道」的隐含状态。

主题一句话结论失守时的典型代价
依赖管理声明文件说清要什么，锁文件钉死用哪个版本，两个都进仓库「昨天还能构建」——上游发了个新版本，你的构建换了内容
CI用严格锁定模式安装，装出锁文件之外的版本就直接失败锁文件形同虚设，锁了个寂寞
容器镜像基础镜像和解释器版本都固定，用摘要引用而不是 latest同一份 Dockerfile 重建出来的不是同一个东西
测试锁契约不锁实现：断言行为与输出，不断言内部调用次数改一行实现红一百个用例，最后大家一起改测试迁就实现
性能优化先测量再动手，优化前后用同一基准对比花两周优化了不是瓶颈的那一段，P95 纹丝不动
可观测性上线前就建好：结构化日志、关键指标、请求 id 串联全链路出事那天只能靠猜，或者只能等它再发生一次
发布版本号是对使用方的承诺，发出去的版本撤不回，只能发新的覆盖一个破坏性改动混进小版本，下游批量崩
排查有流程：稳定复现 → 二分收敛 → 可证伪假设 → 单点验证改了一堆东西问题消失，没人知道是哪一处起了作用

把这张表倒过来读会更清楚：每一行的「代价」都是同一种病的不同症状——某个关键事实只存在于某个人的脑子里或某台机器上，没有被写进仓库、没有被机器验证过。工程化不是流程洁癖，它是在系统性地把这些事实外化。

为什么发布这一项和别的不一样：依赖装错了可以重装，镜像构建坏了可以重建，测试写错了可以改——这些都是可逆的。只有发布不可逆：版本一旦发出去、被别人装上，你就再也收不回来了，即使撤下制品，已经装上的那些机器也不会自动回退。所以发布前的检查清单和别的环节不是一个量级的事，它是唯一一处「错了只能往前修，不能往回退」的地方。

一个新 Python 服务上线前的工程化清单

  • 解释器版本与基础镜像都固定，镜像按摘要引用，不用 latest
  • 依赖有声明文件 + 锁文件，CI 用严格锁定模式安装，装不出锁文件里的版本就失败
  • 入口统一写成 python -m 形式，用退出码表达成败
  • 结构化日志：每条带请求 id，关键中间状态带上具体的值
  • 启动时开 faulthandler（或设 PYTHONFAULTHANDLER=1），长任务配一个看门狗
  • 生产环境统一设 PYTHONBREAKPOINT=0，兜住漏删的断点
  • 有一条冒烟用例：干净机器上照声明装完依赖就能跑通
  • 排查流程和历史事故记录写进仓库，新人第一天就能看到
  • 用 latest 基础镜像，或者只有声明没有锁文件
  • 把可观测性留到第一次事故之后再补——那次事故你注定查不明白
  • 在生产代码里留裸 breakpoint()，且没有环境变量兜底
  • 一次改三处然后重启看看，事后把三处一起当作修复方案提交
  • 用 print 调试完忘记删，日志里全是没有上下文的裸字符串
  • 假设 set 的迭代顺序、假设服务器时区是本地时区
  • 发现慢了先加缓存，不先测量到底慢在哪一层
  • 把「记得先装 xxx」写进 README 当作依赖声明

整个工程化小组只有一条主线：把「只有我知道」变成「机器能验证」。依赖、镜像、测试、日志、版本号、排查流程，全都是这句话在不同环节上的具体写法。判断一项工程实践值不值得做，问一句就够了——它消除了哪一个「只有我知道」？

Q&A

为什么「改一行试一下」在小项目里管用，到了线上系统就不行了？
因为它的有效性完全取决于可疑点的数量。几百行的脚本里可疑点只有个位数，随便试几次就能撞上；而线上系统的可疑点包括你的代码、依赖的几十个库、运行环境、并发时序、外部服务的返回、数据本身的分布，规模是几十到上百。在这个规模上随机试探的期望次数高到不可接受，而且每一次试探都在污染现场——你改过的地方越多，越说不清当前的行为是原问题还是你引入的。真正的替代方案不是「试得更聪明」，而是换成二分：每一步都必须让可疑集合减半，无论用的是砍一半输入、回退一半提交，还是把环境从容器换回本地。能做到这一点，几十个可疑点也只要五六步。
breakpoint() 可以提交进仓库吗？PYTHONBREAKPOINT 到底怎么用才安全？
原则上不要提交，但要在提交之外再加一层兜底，因为「漏删一个」这件事一定会发生。机制上，breakpoint() 调用的是 sys.breakpointhook()，它读环境变量 PYTHONBREAKPOINT：不设置就进 pdb；设成 0 则直接返回、什么都不做；设成一个可导入的可调用对象名就改为调用它。所以正确的做法是三层：第一层，CI 里加一条静态检查，代码里出现 breakpoint() 就拒绝合并；第二层，生产和 CI 的环境变量里统一写死 PYTHONBREAKPOINT=0，万一漏了也只是空操作，不会把进程挂在一个没人看的 pdb 提示符上；第三层，本地想换调试器时用这个变量指过去，而不是去改代码里的 import。这套组合下来，「断点挂死线上进程」这类事故就消失了。
回溯里为什么看不到变量的值？有没有办法补上？
因为回溯记录的是控制流：哪个文件、哪一行、哪个函数，一层层调过来。变量值属于运行时数据，量可能极大（一个列表里几十万个元素），把它们全部序列化进异常信息既不现实也不安全（很容易把密钥和用户隐私打进日志）。补齐的办法有三条，按场合选：能让程序停下来时用断点或事后调试，pdb.pm() 进去之后整个作用域都能查；不能停但能预判时，在抛出点附近把关键值打成结构化日志；不能停也无法预判时，在自定义异常里把必要的上下文作为字段带上——注意是挑选过的少量字段，不是把整个对象塞进去。第三种做法和异常层次的设计强相关，PY24 里有更完整的讨论。
faulthandler 在 Windows 上到底能用到什么程度？
能用大部分，但缺一块关键能力。faulthandler.enable() 在 Windows 上可用，从 3.6 起它除了装 SIGSEGV 这类信号处理器外还会安装 Windows 异常处理器，所以进程崩溃时能拿到 Python 层的栈；dump_traceback() 和看门狗式的 dump_traceback_later() 也都可用，抓卡死没问题。缺的是 faulthandler.register() / unregister()，官方文档明确标注在 Windows 上不提供——也就是 Linux 上那个「给进程发一个 SIGUSR1，让它当场吐一份所有线程的栈」的常用手法，在 Windows 上没有等价物。替代方案是提前用 dump_traceback_later(timeout, repeat=True) 装一个周期性看门狗，或者用外部的采样剖析器按 PID 抓。另外不论哪个平台都要记住输出是简化版：没有源码行、没有变量值、只支持 ASCII、限 100 帧 100 线程，而且顺序和普通回溯相反，最近的调用排在最前面。
用 print 调试是不是不专业？什么时候该换成别的？
不是。看一个值、验证一下分支有没有走到，print 是最快的，没必要上调试器。它的问题出在三种场合。第一，你需要看的不是一个值而是一整个现场（这个对象的所有字段、调用方传进来的是什么），这时插 print 要来回改好几轮，断点一次就够。第二，问题出在循环的第 173 次或者只在某条特定数据上，条件断点能精确命中，而 print 会给你几千行需要人眼筛的输出。第三，也是最要命的——生产环境。print 写的是无结构的裸字符串，没有时间戳、没有级别、没有请求 id，既无法按值过滤也无法关联，而且一旦忘删就永久留在日志里成为噪声。所以判据是：本地临时看一眼随便用 print，但只要这行输出有可能活过今天，就该用结构化日志；只要你要看的超过一个值，就该用断点。
字典不是从 3.7 起就保证有序了吗，为什么还说不能依赖迭代顺序？
字典确实可以依赖。dict 按插入顺序迭代从 Python 3.7 起是语言层面的正式承诺，不是实现细节，放心用。真正没有顺序承诺的是 set 和 frozenset：它们的迭代顺序由元素哈希值和内部表的布局共同决定，而 CPython 默认对 str 和 bytes 的哈希做每进程随机化（由 PYTHONHASHSEED 控制，目的是防哈希碰撞攻击）。后果是同一份字符串数据放进集合，在不同进程里遍历出的顺序可以完全不同——单机单进程测试时你可能一辈子撞不上，一上多 worker 部署就开始偶发。典型踩法是「去重之后取第一个」和「集合运算的结果直接拿去拼字符串或算哈希」。规则很简单：任何要进入结果的顺序都必须由你显式指定，去重后加一次 sorted() 的成本远低于查这种 bug 的成本。各容器的顺序承诺见 PY03。
进程卡死了但没有任何报错，从哪一步开始查？
第一步固定是抓栈，不是看日志也不是重启——重启会毁掉唯一的现场。抓栈有两条路：如果启动时就装了 faulthandler.dump_traceback_later(timeout, repeat=True)，到点它会自动把所有线程的栈打到 stderr；没装的话用外部采样剖析器按 PID dump 一次，不需要改代码也不需要重启。拿到栈之后，卡死只会落进两类。一类是在等一个永远不来的东西：栈会停在某个网络请求、数据库查询、队列 get 或者子进程 wait 上，根因几乎总是这个调用没设超时。另一类是死锁：你会看到两个或多个线程各自停在获取锁的那一行，互相等对方手里的那把，根因是加锁顺序不一致。前者的根治办法是给所有阻塞调用加超时，后者是全局约定一个固定的加锁顺序。抓不到栈的情况下别硬猜，先把看门狗装上，等下一次。
事后调试的几个入口有什么区别，分别什么时候用？
四个入口，对应四种场合。pdb.pm() 用于交互式解释器里刚刚炸完，它读 sys.last_exc 直接把你送回异常现场，适合在 REPL 里探索时用。pdb.post_mortem(t) 是显式版本，接受一个 traceback，3.13 起也接受异常对象，适合写在自己的错误处理代码里。python -m pdb app.py 让脚本异常退出时自动进入事后调试，而且退出调试器后会重启程序并保留断点，适合反复调一个命令行脚本。pytest --pdb 让第一个失败的用例当场停在现场，是日常用得最多的一个。另外 3.13 给 pdb 加了 exceptions 命令，遇到异常链时可以在各段之间跳，直接落到最底层那个真正的原因帧上——配合第二节讲的三种链形态，能省掉「报错信息和根因对不上」的那段困惑。
