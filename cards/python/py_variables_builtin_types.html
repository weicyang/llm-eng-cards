一、动态类型到底意味着什么

几乎所有教程都会说 Python 是动态类型语言——意思是变量不需要事先声明类型，同一个名字前后可以指向不同类型的值。这句话本身没错，但它省略了最关键的一半：类型并没有消失，它只是不属于名字，而属于对象。

在 C 或 Java 里，int x = 5; 做的事是向栈上划出一块 4 字节的内存，给它起名 x，往里写 5。「盒子」这个比喻在那里是准确的：盒子有固定大小、固定类型，赋值就是换里面的内容。Python 的执行模型完全不同。x = 5 做的是：在堆上找到（或创建）一个值为 5 的整数对象，然后在当前名字空间——一张从名字到对象的映射表——里记下「x 指向它」。这个动作叫名字绑定，而不是「写入」。

这个差别不是术语游戏，它直接决定了三件事的答案：赋值会不会拷贝数据、两个名字能不能互相影响、以及类型检查在什么时候发生。

a = 256 b = a ← 没有拷贝任何数据，只是多贴了一张标签 名字空间（一张字典：名字 -> 对象） 堆上的对象 ┌────────────────┐ │ "a" ●────────┼──┐ │ "b" ●────────┼──┤ ┌──────────────────────┐ └────────────────┘ └────────►│ int │ │ 值 = 256 │ │ 类型 = int │ ← 类型写在这里 │ 引用计数 = 2 │ └──────────────────────┘ a = "hi" ← 这一行没有「修改 a 里的内容」 ┌────────────────┐ ┌──────────────────────┐ │ "a" ●────────┼───────────►│ str 值 = "hi" │ ← 新建的对象 │ "b" ●────────┼──┐ └──────────────────────┘ └────────────────┘ │ ┌──────────────────────┐ └────────►│ int 值 = 256 │ │ 引用计数 = 1 │ ← 降了 1 └──────────────────────┘ 所以 type(a) 问的从来不是「a 是什么类型」， 而是「a 现在指着的那个对象是什么类型」。

赋值不是把值放进盒子，是把标签贴到对象上。一个对象可以被贴很多张标签，一张标签任何时候只能贴在一个对象上。

用三个内置函数把这件事看清楚

光读概念容易滑过去，动手观察一次就再也忘不掉。Python 提供了三个函数让你直接看到名字与对象的关系，它们是调试这一类问题的基本工具。

函数它回答的问题返回什么典型用法
type(x)x 指着的对象是什么类型类型对象本身，如 <class 'int'>调试时确认「这到底是 str 还是 bytes」
id(x)x 指着的是哪一个对象该对象的唯一整数标识（CPython 里就是内存地址）验证两个名字是否指向同一对象
x is y两个名字指的是同一个对象吗布尔值，等价于 id(x) == id(y)只用于 None / True / False 和身份判断
>>> a = [1, 2]
>>> b = a            # 贴第二张标签，不是拷贝
>>> id(a) == id(b)
True
>>> b.append(3)      # 通过 b 修改了那个唯一的对象
>>> a

最后那一步是新手最容易被咬到的地方：b = a 之后往 b 里 append，a 也变了。它并不神秘——因为从头到尾只有一个列表对象，a 和 b 只是它的两个名字。这种「多个名字共享一个可变对象」的行为叫引用语义，它在函数传参、默认参数、类属性里会反复出现，本系列后面（PY09）会专门展开可变对象的复制与共享问题，这里只需要牢记：赋值从不复制对象。

动态类型不等于没有类型

动态的只是「检查时机」。静态类型语言在编译期就拒绝 "abc" - 1，Python 要等到真的执行那一行才发现问题，然后抛出 TypeError: unsupported operand type(s) for -: 'str' and 'int'。代价是错误暴露得更晚——一段没被测试覆盖的分支可能上线三个月才炸；好处是灵活性，同一个函数可以接受任何「行为像文件」的对象，这就是鸭子类型，即只要对象支持所需的操作就能用，不要求它属于某个特定类型。

动态类型不是「省掉了类型」，而是「把类型检查推迟到运行时」。所以类型注解和测试在 Python 里不是可选的装饰，它们补的正是编译器没帮你做的那一步。

二、整数与浮点：任意精度和 IEEE 754

int 和 float 看起来是一对孪生的数值类型，实际上它们的底层设计哲学截然相反。int 追求绝对正确，为此不惜牺牲空间和速度；float 追求固定开销和硬件速度，为此接受可控的误差。不知道这个分工，就会在该用 int 的地方担心溢出，在该警惕 float 的地方盲目相信结果。

int 没有上限，这不是夸张

大多数语言的整数是定长的：32 位 int 超过约 21 亿就会溢出，结果悄悄变成负数。Python 的 int 是任意精度整数——内部用一串「数字块」表示，需要多大就分配多大，位数只受可用内存限制。所以 2 ** 1000 会老老实实给你一个 302 位的精确整数，不会溢出、不会截断、不会变成科学计数法。

>>> 2 ** 64                      # 换成 C 的 uint64 已经溢出了
18446744073709551616
>>> len(str(2 ** 1000))          # 302 位，依然精确
302
>>> (10 ** 30 + 1) - 10 ** 30    # 大数运算不丢最低位
1

代价在两处。一是内存：一个小整数对象在 64 位 CPython 上大约占 28 字节，而 C 的 int 只占 4 字节；一亿个 Python 整数放进列表会吃掉好几个 GB。二是速度：超过机器字长后，加法要逐块进位，乘法要走专门算法，运算时间随位数增长。这就是数值计算普遍用 NumPy 的原因——它用定长的 C 类型换回空间和速度，代价是溢出风险重新回来了。

float 的误差来自进制，不来自 Python

先看那个所有人都会撞到的例子：

>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
>>> format(0.1, '.20f')          # 看看 0.1 真实的样子
'0.10000000000000000555'

很多人第一反应是「Python 的浮点数有 bug」。它不是 bug，而且和 Python 没关系——C、Java、JavaScript、Go 全都是这个结果，因为它们都用同一套硬件标准：IEEE 754 双精度，即用 64 位（1 位符号 + 11 位指数 + 52 位尾数）表示一个二进制小数。

根因是进制。二进制小数只能表示形如「若干个 1/2 的幂之和」的数。十进制的 0.5 是 1/2，能精确表示；0.25 是 1/4，也能。但 0.1 等于 1/10，而 10 含有质因数 5，5 不是 2 的幂，所以 1/10 在二进制里是无限循环小数 0.0001100110011...，就像 1/3 在十进制里写成 0.333… 永远写不完一样。64 位只能存下前 52 位有效尾数，后面必须截断，于是存进去的从来不是 0.1，而是一个离 0.1 最近的可表示数。两个近似值相加，误差叠加后就跨过了显示阈值，露了出来。

0.1 + 0.2 != 0.3 不是 Python 的缺陷，是「用二进制存十进制小数」这件事本身做不到。就像你没法用有限位十进制精确写出 1/3。

那该怎么比较浮点数

结论很直接：不要用 == 比较两个计算出来的浮点数，改成判断「差距是否小到可以忽略」。标准库 math.isclose 就是为这件事准备的，它同时考虑相对误差和绝对误差，比手写 abs(a - b) < 1e-9 更稳。

>>> import math
>>> math.isclose(0.1 + 0.2, 0.3)
True
>>> math.isclose(1e-20, 0.0)                    # 默认只看相对误差，和 0 比会失败
False
>>> math.isclose(1e-20, 0.0, abs_tol=1e-12)     # 和 0 比较必须给绝对容差
True

中间那一行是 isclose 最容易用错的地方。它默认的 rel_tol=1e-09 是相对容差，也就是按两数量级的比例判断；而任何非零数相对于 0 的偏差比例都是 100%，所以「和 0 比较」必须显式传 abs_tol。凡是要判断某个结果是否为零，记住这一条。

三种精确数值类型的分工

float 的误差在科学计算里通常无害，但在两类场景下不可接受：金额和精确分数。标准库为它们各准备了一种类型。

类型怎么存值适用场景代价关键陷阱
float64 位二进制小数（IEEE 754），约 15–17 位十进制有效数字科学计算、统计、图形、机器学习特征几乎为零，由 CPU 直接运算十进制小数存不准，不能用 == 比较
decimal.Decimal十进制定点/浮点，精度与舍入方式可配置金额、税率、计费、财务报表软件实现，比 float 慢约 10–100 倍必须用字符串构造：Decimal(0.1) 会把 float 的误差原样吃进去
fractions.Fraction一对任意精度整数（分子/分母），自动约分精确有理数运算、单位换算、符号推导、教学演示最慢，且连续运算会让分母不断膨胀无法表示无理数；开方、三角函数一律退回 float
>>> from decimal import Decimal
>>> Decimal("0.1") + Decimal("0.2") == Decimal("0.3")
True
>>> Decimal(0.1)                      # 用 float 构造 = 把误差带了进来
Decimal('0.1000000000000000055511151231257827021181583404541015625')
>>> from fractions import Fraction
>>> Fraction(1, 3) * 3 == 1            # 分数是精确的
True

示例场景：某订单系统用 float 累加金额，单笔 19.99 元的商品下单 1000 次后，累加结果是 19989.999999997673 元，而财务系统按 Decimal 算出的应收是 19990.00 元，差了约 0.0000000023 元。金额本身微不足道，但对账脚本用 == 判断两侧是否相等，于是当天 1 笔对账任务失败、触发人工介入。把订单金额字段从 float 改为 Decimal（数据库侧用 DECIMAL(18,2)）后不再出现差额。教训是：钱不是数值计算，是精确算术，从存储层就不该用浮点。

三、字符串、布尔与 None 的特殊性

str、bool、None 是使用频率最高的三种类型，也各自藏着一个不读文档就想不到的设计决定：str 完全不可变、bool 其实是 int、None 全程只有一个实例。这三件事分别对应三类真实的 bug。

str 不可变：修改就是新建

Python 的字符串是不可变对象，意思是对象一旦创建，它的内容永远不会改变。所有看起来在「修改字符串」的操作——拼接、替换、大小写转换、切片——实际都是造了一个新对象并把名字指过去。s[0] = "x" 这种写法会直接抛 TypeError: 'str' object does not support item assignment。

s = "abc" s = s + "d" ← 看起来是「追加」，实际是「新建 + 换标签」 执行第 1 行后 "s" ●───────► ┌────────────────┐ │ str "abc" │ id = 0x7fa1...a10 └────────────────┘ 执行第 2 行后：先造一个全新对象，再把 s 指过去 "s" ●───────► ┌────────────────┐ │ str "abcd" │ id = 0x7fa1...b80 ← 换了对象 └────────────────┘ ┌────────────────┐ 已无人引用 ───► │ str "abc" │ 引用计数归零，被回收 └────────────────┘ 后果：循环里用 s += x 拼 10000 次，就创建了 10000 个中间字符串， 每次都要复制一遍已有内容，总复制量与长度的平方成正比。 正确写法：先收进 list，最后一次性合并 parts = [] for x in items: parts.append(x) ← list 是可变对象，append 是原地操作 s = "".join(parts) ← 只分配一次最终大小

不可变听起来是限制，但它换来了三样好处：字符串可以安全地做字典的键（哈希值不会中途变化）、可以在多个地方共享同一个对象而不担心被别人改掉、解释器可以放心地缓存和驻留它们。第四节讲的字符串驻留正是建立在不可变之上——如果字符串能被改，共享同一个对象就是灾难。

「不可变」不代表名字不能重新指向新值，只代表那个对象本身改不了。s += "x" 永远合法，因为它换的是标签指向，不是对象内容。

bool 是 int 的子类，这会带来真实的坑

Python 早期没有布尔类型，用 1 和 0 代替；2.3 版本引入 bool 时为了不破坏已有代码，把它做成了 int 的子类。这个历史决定至今生效：True 就是 1，False 就是 0，它们能参与任何整数运算。

>>> True + True
2
>>> isinstance(True, int)
True
>>> sum([True, False, True, True])    # 惯用法：统计满足条件的个数
3
>>> {1: "a", True: "b"}               # 1 和 True 哈希相同、相等，是同一个键
{1: 'b'}

前三行是有用的：sum(x > 0 for x in data) 这种写法简洁而地道。最后一行就是坑了——字典里 1 和 True 会互相覆盖，因为它们相等且哈希值相同。同类问题还有：函数参数收到 True 时，用 isinstance(n, int) 校验会通过；用 if flag == 1 判断时，传 True 和传 1 无法区分。要真正区分布尔和整数，得先判断 isinstance(x, bool)，再判断 int。

None 是单例，所以必须用 is 判断

None 表示「没有值」，它是 NoneType 类型的单例——整个进程从启动到结束只存在一个 None 对象，你没法再造一个。正因为如此，判断一个值是不是 None 的唯一正确写法是 x is None，比较身份而不是比较值。

为什么 == None 不行？因为 == 会调用对象的 __eq__ 方法，而这个方法可以被任意重写。NumPy 数组的 __eq__ 返回的是逐元素比较的布尔数组，把它放进 if 会抛 ValueError: The truth value of an array with more than one element is ambiguous；ORM 的查询对象重写 __eq__ 后返回的是 SQL 条件表达式，恒为真。而 is 比较的是对象身份，谁也改不了它的行为，也不用调用任何方法，因此更快也更安全。

特殊之处正确写法错误写法及后果
None 是单例if x is None:if x == None: — 遇到重写了 __eq__ 的对象会给出错误答案或直接抛异常
None 与「假值」不同if x is None: 判断「没传」；if not x: 判断「空或假」if not x: 当成「没传」用 — 0、""、[]、False 全部会被误判成没传
bool 是 int 子类if isinstance(x, bool): ... elif isinstance(x, int): ...先判 int — True 会被归到整数分支

is 只在四种情况下该出现：is None、is True、is False，以及你确实想问「这俩是同一个对象吗」。其余一切比较都用 ==。

四、小整数缓存与字符串驻留：is 和 == 为什么会给出矛盾答案

这一节解释初学者最困惑的一个现象。同样的代码形状，换个数字结论就反了：

>>> a = 100; b = 100
>>> a is b
True
>>> a = 1000; b = 1000
>>> a is b
False                    # 同样的写法，答案反了
>>> a == b
True                     # 但值当然还是相等的

这里没有魔法，也没有语言规则在起作用。原因是 CPython 做了一项性能优化：小整数缓存——解释器启动时就把 -5 到 256 这 262 个整数对象预先创建好放在一个数组里，之后任何地方用到这个范围的整数，都直接复用池里那个现成对象，不再新建。超出范围的数字就老老实实每次新建，于是两个 1000 是两个独立对象。

CPython 启动时就把一批整数对象造好，放进一个固定数组 ┌──────────────────────────────────────────────────────────────────┐ │ 小整数缓存池（范围 -5 .. 256，共 262 个对象，编译期写死） │ │ [-5][-4][-3][-2][-1][ 0][ 1][ 2] ...... [254][255][256] │ └──────────────────────────────────────────────────────────────────┘ ▲ ▲ │ │ x = 100 ───┘ y = 100 ───────┘ 两个名字都指向池里同一个对象 ==> x is y 为 True x == y 为 True x = 1000 ──► ┌────────────┐ y = 1000 ──► ┌────────────┐ │ int 1000 │ │ int 1000 │ │ id=0x..a10 │ │ id=0x..c40 │ └────────────┘ └────────────┘ 两个独立对象 ==> x is y 为 False ← 变了 x == y 为 True ← 没变 要记住的只有一条： is 问的是「有没有复用同一个对象」——由实现的优化策略决定 == 问的是「值是否相等」 ——由语言语义保证 业务代码需要的永远是后者。

字符串驻留是同一套把戏

字符串也有类似机制，叫字符串驻留：CPython 会把「看起来像标识符」的字符串字面量（只含字母、数字、下划线）放进一张全局表复用，因为模块名、属性名、函数名这类字符串会被反复比较，共享同一对象能让比较退化成一次地址比对。所以 "hello" is "hello" 为真，而 "hello world" is "hello world"（含空格，不像标识符）在很多情形下为假。

>>> a = "hello"; b = "hello"
>>> a is b
True                          # 像标识符，被驻留了
>>> a = "hello world"; b = "hello world"
>>> a is b
False                         # 含空格，未驻留（取决于版本与上下文）
>>> import sys; a = sys.intern("hello world"); b = sys.intern("hello world")
>>> a is b
True                          # 手动驻留才有保证

为什么必须把这当成实现细节

缓存区间是 -5..256、驻留规则是「像标识符」，这些数字和规则不写在语言规范里。它们是 CPython 当前版本的选择，可以在任何小版本里改动，PyPy、MicroPython 等其他实现的行为也不同。更麻烦的是，同一份 CPython 里结果还会随上下文变化：在同一行或同一个函数体内写的两个相同字面量，会被编译器合并成一个常量，于是 is 为真；分开在交互式解释器里逐行输入，就可能是两个对象。

这意味着任何依赖 is 比较值的代码都是偶然正确的。它在你的测试数据上能过，因为测试里用的都是小数字；上线遇到真实数据就开始漏判，而且没有报错、没有栈帧，只有静默的错误结果——这是最难排查的一类 bug。

这张表的正确读法不是背下来，而是从中得出一条规则：只要 == 那一列全是 True，你的代码就应该只用 ==。is 列的花样全部来自优化，与你的业务逻辑无关。

示例场景：某接口用 if status_code is 200: 判断上游返回，在开发和预发环境跑了 3 周一直正常——因为这两个环境的 mock 数据里状态码是从同一常量读出来的，是同一个对象。上线后真实响应里的状态码由 JSON 解析得到，是新建的整数对象（200 虽在缓存区间内，但解析路径下走的是另一条构造逻辑），判断恒为假，约 12 万次成功请求被记成失败并触发了重试，放大了 2 倍上游流量。修复是把 is 改成 ==，改动 1 个字符。is 在小整数上「看起来能用」，正是这类事故能潜伏这么久的原因。

is 在小数字和短字符串上偶尔为真，这不是你可以依赖的特性，而是一个会让 bug 推迟到生产环境才暴露的陷阱。看到用 is 比较数字或字符串的代码，一律当成缺陷处理。

五、类型转换：显式转换与数值提升

Python 在类型转换上的态度有点分裂：算术运算里它会悄悄帮你提升类型，但跨大类的转换必须你亲自写出来。1 + 2.5 能算，1 + "2" 直接报 TypeError——因为前者是数值内部的拓宽，不会丢信息；后者的意图有歧义（是 3 还是 "12"？），语言选择让你自己说清。

四个转换函数的边界行为

这四个函数日常用得最多，而它们的边界行为恰好是新手最容易猜错的部分。尤其是 int()：它对字符串要求严格到只接受整数形式，对 float 却是直接截断小数部分而不是四舍五入。

提升阶梯与两个除法

混合算术遵循数值提升规则：参与运算的两个数会被统一到「更宽」的那个类型上，方向单一，只升不降。阶梯是 bool → int → float → complex。关键推论是：一旦表达式里出现一个 float，结果就被拉进了浮点世界，第二节讲的所有误差也随之生效。

-7 // 2 == -4 是这一节最反直觉的结果。C、Java 的整除是向零截断，所以 -7 / 2 在那里是 -3；Python 选的是向下取整，即朝负无穷方向靠，所以 -3.5 变成 -4。这不是任性，而是为了让上面那个恒等式成立，从而保证取模结果的符号始终和除数一致。好处很实际：用 i % 7 算星期几、用 i % n 做环形索引时，即使 i 是负数，结果也永远落在 0..n-1 内，不需要额外加一次 + n 再取模。

/ 永远给 float，// 向下取整。需要索引、页数、分组数这类必须是整数的量，就用 //；需要比例、均值这类连续量，就用 /。混着用会得到 list[3.0] 这种 TypeError。

六、命名规范与常见报错对照

命名是唯一一件你每写三行代码就要做一次决定的事，也是最容易被当成「风格问题」而忽略的事。它其实有两层：一层是语言强制的标识符规则，违反了直接语法错误；另一层是 PEP 8 约定，违反了代码照样能跑，但会让读代码的人（包括三个月后的你）多花时间，甚至埋下真实的 bug。

语言强制的规则

合法标识符必须以字母或下划线开头，后面可以跟字母、数字、下划线，区分大小写，且不能是 35 个关键字之一。Python 3 的「字母」包含 Unicode，所以 总金额 = 100 语法上完全合法——但别这么写，中文变量名在跨平台编辑器、日志、grep 和团队协作里都会带来麻烦。

PEP 8 的命名约定：每种形式都在传递信息

PEP 8 是官方风格指南，它规定的不只是「好看」，而是一套让读者看一眼名字就知道该怎么用它的编码。看到全大写就知道别改它，看到前导下划线就知道那是内部实现、升级时可能消失。

遮蔽内置名：能跑，但会在很远的地方炸

Python 有 70 多个内置名（list、dict、str、id、type、sum、max、input、filter、bytes…），它们不是关键字，所以可以被赋值覆盖，解释器不会有任何提示。问题是覆盖之后，同一作用域里所有依赖那个内置名的代码都会失效，而报错通常出现在离赋值很远的地方。

>>> list = [1, 2, 3]          # 合法，没有任何警告
>>> list(range(5))            # 50 行之后，你想用内置的 list()
TypeError: 'list' object is not callable
>>> id = 42                   # 同理
>>> id(some_obj)
TypeError: 'int' object is not callable

'X' object is not callable 这句报错的含义就是「你在一个不是函数的东西后面加了括号」，而在这类场景里，它几乎总意味着某个内置名被变量覆盖了。所以看到它先别看出错那一行，去搜一下这个名字有没有在别处被赋过值。用 items、values、rows、names 这类具体名词替代 list、dict，这个问题就不存在了。

  • 用 x is None 判断空值，用 == 比较数值和字符串
  • 金额、税率、计费一律用 Decimal，并用字符串构造：Decimal("19.99")
  • 比较浮点结果用 math.isclose；和 0 比较时补上 abs_tol
  • 循环拼字符串先 append 进 list，最后 "".join(parts)
  • 名字用 snake_case，常量 UPPER_CASE，类 PascalCase
  • 撞上关键字或内置名时加后缀下划线：class_、id_
  • 需要整数结果（索引、页数、分组）时明确用 //
  • 区分 bool 和 int 时先判 isinstance(x, bool)，再判 int
  • 用 is 比较数字或字符串——小值上偶然为真，大值上静默失败
  • 用 == None 判空——对重写了 __eq__ 的对象会给出错误答案
  • 用 if not x: 表达「参数没传」——0、""、[] 会被误判
  • 用 float 存钱，或用 == 比较两个算出来的浮点数
  • 写 Decimal(0.1)——float 的误差会被原样带进来
  • 把 list、dict、id、type、sum 当变量名
  • 用 bool(env_str) 解析配置开关——"false" 也是 True
  • 以为 int(3.9) 是 4，或以为 -7 // 2 是 -3

命名不是审美问题，是成本问题。一个好名字省下的是每个读者每次读到它时的理解时间；一个遮蔽了内置名的坏名字，代价是某人某天花两小时排查一句毫不相关的 not callable。

把这一章的内容装进脑子之后，再回头看PY01 · Python 环境与解释器里那张字节码执行图会更有感觉：LOAD_NAME 这条指令做的正是「从名字空间这张字典里查出对象」，而不是「从内存里读一个盒子」。变量模型和执行模型是同一件事的两面。

Q&A

为什么 0.1 + 0.2 不等于 0.3？换个语言会好吗？
不会，C、Java、JavaScript、Go 给出的是同一个结果，因为它们都遵循 IEEE 754 双精度标准。根因是进制而不是语言：二进制小数只能精确表示分母为 2 的幂的分数，而 0.1 等于 1/10，10 含有质因数 5，所以 1/10 在二进制里是无限循环小数，就像 1/3 在十进制里写成 0.333… 永远写不完。64 位浮点只有 52 位尾数，必须在某处截断，所以存进去的从来不是 0.1 而是最接近它的可表示数。两个近似值相加后误差叠加，跨过了显示精度阈值就露了出来。实践上的应对只有两条：比较时用 math.isclose 而不是 ==；涉及金额时改用 Decimal，从存储层就别让浮点参与。
a is b 和 a == b 到底该怎么选？
is 比较的是对象身份，等价于 id(a) == id(b)，问的是「这两个名字指的是不是同一个对象」；== 比较的是值，会调用对象的 __eq__ 方法。选择标准很简单：判断值是否相等永远用 ==，is 只用于 None、True、False 这三个单例，以及你确实想知道两个变量是否指向同一对象的场合（比如检查缓存是否命中、判断某个可变对象有没有被替换过）。之所以要立这条规矩，是因为 CPython 的小整数缓存和字符串驻留会让 is 在小数字和短字符串上「看起来能用」，这种偶然正确的代码会一直潜伏到遇上真实数据才失效。
小整数缓存的范围是 -5 到 256，这个数字要背吗？
不需要背，需要记住的是「它是 CPython 的实现细节，不是语言保证」。这个区间写在 CPython 源码里，可以在任何版本中调整；PyPy、MicroPython 等其他实现的策略完全不同。更重要的是，即使在同一份 CPython 里，结果也随上下文变化：同一行或同一个函数体内的两个相同字面量会被编译器的常量折叠合并成一个对象，于是 is 为真；分行写在交互式解释器里就可能是两个对象。所以这个知识的唯一正确用途是理解「为什么 is 有时骗人」，而不是拿来写判断逻辑。业务代码里只要看到用 is 比较数字，就当成缺陷处理。
为什么 True + True 等于 2？这个设计有什么用，又有什么坑？
因为 bool 是 int 的子类。Python 早期没有布尔类型，用 1 和 0 代替，2.3 版本引入 bool 时为了不破坏已有代码，把它做成 int 的子类，True 就是 1，False 就是 0。有用的一面是可以直接统计：sum(x > 100 for x in data) 就能数出满足条件的元素个数，非常地道。坑主要有三个。一是字典里 1 和 True 是同一个键，会互相覆盖，{1: "a", True: "b"} 的结果是 {1: 'b'}。二是 isinstance(True, int) 为真，用 int 做参数校验时布尔值会溜进来。三是 == 1 无法区分 True 和 1。要严格区分，得先判 isinstance(x, bool) 再判 int，顺序不能反。
str 不可变，那 s += "x" 为什么能执行？在循环里拼字符串为什么慢？
不可变说的是对象内容改不了，不是名字不能重新绑定。s += "x" 实际做的是：新建一个内容为原串加 "x" 的字符串对象，然后把名字 s 指向这个新对象，原对象引用计数归零后被回收。单次执行没问题，放进循环就有问题了：每一轮都要把已有内容整体复制一遍，拼 n 次的总复制量与 n 的平方成正比，字符串一长就明显变慢，同时产生大量短命的中间对象加重内存分配压力。正确写法是先把片段 append 进 list（list 是可变对象，append 是原地操作，摊销成本是常数），循环结束后用 "".join(parts) 一次性分配最终大小。需要说明的是 CPython 对某些简单的 s += x 有原地优化，但它依赖引用计数恰好为 1 等条件，不能作为依据。
什么时候该用 Decimal，什么时候用 Fraction，什么时候 float 就够了？
按「误差可不可接受」来分。float 用于科学计算、统计、图形、机器学习特征这类场景——数据本身就有测量误差，浮点的十几位有效数字远超需求，而且由 CPU 直接运算，速度无可替代。Decimal 用于金额、税率、计费、财务报表：这些场景要求十进制小数精确存储、舍入方式可控、结果能和人工核算逐分对齐，代价是软件实现比 float 慢一两个数量级，另外必须用字符串构造，Decimal(0.1) 会把 float 的误差原样吃进来。Fraction 用于需要精确有理数的场合，比如单位换算、符号推导、教学演示，它用一对任意精度整数存分子分母，连续运算会让分母不断膨胀所以最慢，且无法表示无理数。一个实用的判断：结果要给财务或用户看具体到分的数字，就用 Decimal；其余默认 float。
为什么 -7 // 2 是 -4 而不是 -3？int(-3.9) 又为什么是 -3？
因为这两个操作的取整方向不同。// 是向下取整（floor），朝负无穷方向靠，所以 -3.5 落到 -4；int() 是向零截断，直接丢掉小数部分，所以 -3.9 变成 -3。// 之所以选向下取整，是为了让恒等式 (a // b) * b + (a % b) == a 对负数也成立，从而保证取模结果的符号始终与除数一致。这个选择有实际好处：用 i % n 做环形索引或算星期几时，即使 i 是负数，结果也永远落在 0 到 n-1 之间，不需要再补一次 + n 取模。注意 C 和 Java 的整除是向零截断的，所以从那些语言迁移过来的取模逻辑在负数上会算出不同答案，这是移植代码时的一个隐蔽差异点。另外还要记住 round(2.5) 是 2 而不是 3，它用的是银行家舍入，.5 向最近的偶数靠。
不小心写了 list = [1, 2] 会发生什么？怎么发现和避免？
赋值本身完全合法，解释器不会有任何提示，因为内置名不是关键字，只是放在一个优先级最低的内置作用域里，同名的局部或全局变量会把它遮住。后果是从这一行之后，同一作用域里所有对内置 list() 的调用都会失败，报 TypeError: 'list' object is not callable——意思是「你在一个不是函数的东西后面加了括号」。麻烦在于报错位置往往离赋值很远，看起来毫无关联，排查时容易在错误的地方打转。发现方法有两个：看到 'X' object is not callable 就去全局搜一下 X 这个名字有没有被赋值；更省事的是让 linter 帮你看，ruff 的 A001/A002 规则和 pylint 的 redefined-builtin 专门检查这件事。避免方法是用具体名词命名，items、rows、names、values 都比 list 更能说明内容；确实想不出别的名字时按 PEP 8 加后缀下划线，写成 list_。常被误用的内置名还有 id、type、sum、max、input、str、bytes、filter。
