一、四种容器的定位与选择依据

初学者常把这四个东西当成「四种装数据的盒子」，按顺手程度随便挑一个。这个理解会让人在很长一段时间里只用 list，因为 list 语法最短、什么都能塞。但它们各自解决的是完全不同的问题，选择依据不是「好不好写」，而是「我的数据本质上是什么形状」。

先把四个问题摆出来。第一，我有一串东西，顺序有意义，而且之后还要往里加、往外删——这是 list。第二，我有一条固定字段的记录，比如一个坐标 (经度, 纬度)，它一旦生成就不该再改——这是 tuple。第三，我要用某个标识去查对应的值，比如用用户 ID 查用户信息——这是 dict。第四，我只关心「这个元素在不在集合里」以及「去重」，顺序无所谓——这是 set。

这四句话里藏着两个正交的维度：有序性指的是元素之间是否存在一个稳定的、由位置定义的先后关系，有序容器才能用整数下标访问；可变性指的是对象创建之后其内容能否原地修改，不可变对象的任何「修改」实际上都是造了一个新对象。把这两个维度交叉一下，四种容器的位置就清楚了。

容器有序可变能作字典键字面量典型用途
list是是不能[1, 2, 3]顺序有意义的元素序列，需要增删改
tuple是否能（元素全可哈希时）(1, 2, 3)固定结构的记录、函数多返回值、字典的复合键
dict是（插入序）是不能{"a": 1}键到值的映射、配置、按 ID 查对象
set否是不能{1, 2, 3}去重、成员判断、交并差运算
frozenset否否能frozenset({1,2})需要当字典键或放进另一个 set 的集合

表里有两处容易被跳过。一是 dict 的「有序」带了括号，它指的是迭代时按插入顺序，不是按键排序，这一点第三节会展开。二是空 set 写不出字面量：{} 是空字典不是空集合，只能写 set()。这个小坑每年都会绊倒一批人，因为 {} 看起来就该是空集合。

该用哪个：一张决策图

拿到一堆数据，先问自己三个问题 ────────────────────────────────────────────── ① 我是靠「位置」找元素，还是靠「名字/ID」找元素？ 靠名字/ID ──────────────────────────► dict {"u1001": {...}, "u1002": {...}} 查询是 O(1)，别用 list 存了再遍历找 靠位置 ──┐ │ ② 我根本不在乎位置，只想知道「在不在」/「去个重」？ │ 在不在 ──────────────────────────────► set 已处理ID = {1, 5, 9} if uid in 已处理ID: ← O(1) 在乎顺序 ─┐ │ ③ 建好之后还会变吗？ │ 会增删改 ────────────────────────────► list 日志行、批次结果、待办队列 建好就定死 ──────────────────────────► tuple (lat, lng) / 数据库一行 / 函数返回多值 额外收益：能当 dict 的键、能放进 set ────────────────────────────────────────────── 补充判据：同一份数据可以有两种视图 records = [...] ← 保留顺序，用于遍历输出 index = {r.id: r ...} ← 建索引，用于 O(1) 查找 空间换时间，这是最常见也最划算的一次交易

选容器不是选语法，是在回答「我将来最频繁的那个操作是什么」。最频繁的是按位置遍历就用 list，是按键查找就用 dict，是判断存在性就用 set，是当成一条不会变的记录传来传去就用 tuple。

还有一个常被忽略的收益：容器类型本身就是一种文档。别人看到函数返回 tuple，不用看实现就知道这东西不打算让你改；看到参数类型是 set，就知道传进去的顺序无所谓、重复元素会被吃掉。用 list 装一切，等于把这些信息全都抹掉了。

二、list 的内部结构与扩容代价

几乎所有性能问题都来自同一个误解：把 list 当成链表。名字确实是这么叫的，中文也常译作「列表」，但 CPython 里的 list 是一个动态数组——一块连续的内存，里面按顺序放着指向各个元素对象的指针，容量不够时整体搬到一块更大的内存里。

「连续内存 + 指针数组」这七个字能推导出这一节剩下的全部结论。既然是连续内存，那么第 i 个元素的地址就是「起始地址 + i × 指针宽度」，一次算术运算直接算出来，所以 lst[10000] 和 lst[0] 一样快，都是 O(1)。既然要维持连续，那么在中间或头部插入一个元素，后面所有元素都必须整体往后挪一格，所以 lst.insert(0, x) 是 O(n)。

lst = ["ab", 42, [7, 8]] list 对象本体（一个定长的头 + 一块指针数组） ┌──────────────────────────────────┐ │ ob_size = 3 ← 当前元素个数 │ │ allocated = 4 ← 已申请的槽位数 │ │ ob_item ─────────┐ │ └───────────────────┼───────────────┘ ▼ 连续内存（每格存一个指针，64 位机上 8 字节） ┌────────┬────────┬────────┬────────┐ │ ptr0 │ ptr1 │ ptr2 │ (空槽) │ └───┬────┴───┬────┴───┬────┴────────┘ │ │ │ ▼ ▼ ▼ ┌──────┐ ┌──────┐ ┌──────────┐ │ str │ │ int │ │ list │ ← 真正的对象散落在堆上 │ "ab" │ │ 42 │ │ [7, 8] │ list 本身只存地址 └──────┘ └──────┘ └──────────┘ ────────────────────────────────────────────── 由此直接推出四条： lst[i] 地址 = 起点 + i*8，一次乘加 → O(1) lst.append(x) 写进空槽，满了才扩容 → 摊还 O(1) lst.insert(0,x) 后面 n 个指针整体右移一格 → O(n) lst.pop(0) 后面 n 个指针整体左移一格 → O(n)

扩容为什么不是每次加一

如果每次 append 都只多申请一个槽位，那么每次都要重新分配内存并把旧内容整体拷过去，追加 n 个元素的总代价就是 1+2+3+…+n，也就是 O(n²)。CPython 的做法是按比例预留：容量不够时一次多申请一批，新容量大致是当前元素数的 1.125 倍再加一个小常数，序列大致是 0、4、8、16、25、35、46、58、72、88……

关键在于「按比例」这三个字。预留量随规模增长，于是扩容发生的频率随规模下降，n 次 append 触发的搬移总量是 O(n)，平均到每次就是常数——这就是摊还复杂度的含义：单次操作可能很慢（正好赶上扩容那一次要搬 n 个指针），但把足够多次操作的总代价平均下来，每次是 O(1)。

操作发生了什么单次最坏摊还
append(x)写入预留槽；槽满则整体搬家O(n)O(1)
pop()（尾部）元素数减一，不搬移O(1)O(1)
insert(0, x)全部指针右移一格O(n)O(n)
pop(0)全部指针左移一格O(n)O(n)
lst + other造一个全新 list，拷两边O(n+m)O(n+m)
lst.extend(other)原地追加，可能扩容一次O(m)O(m)

最后两行的对比值得记住。在循环里写 result = result + [x] 会每轮造一个新列表，n 轮就是 O(n²)；改成 result.append(x) 是 O(n)。这两种写法读起来差别不大，跑起来差一个数量级。

存的是引用，不是值

指针数组还有一个直接后果：list 里放的从来不是对象本身，而是对象的地址。两个 list 可以指向同一个对象，改动透过任何一条路径都会被另一条看到。最经典的翻车现场是用乘法造二维列表。

grid = [[0] * 3] * 3      # 看起来是 3x3 的零矩阵
grid[0][0] = 1
print(grid)               # [[1,0,0], [1,0,0], [1,0,0]]  ← 三行一起变了

grid = [[0] * 3 for _ in range(3)]   # 正确写法：循环里各造各的
grid[0][0] = 1
print(grid)               # [[1,0,0], [0,0,0], [0,0,0]]
为什么 [[0]*3] * 3 会三行联动 ────────────────────────────────────────────── 第一步：[0] * 3 对 int 做重复 ┌───┬───┬───┐ │ • │ • │ • │ 三个指针都指向同一个 int 0 └─┬─┴─┬─┴─┬─┘ 但 int 不可变，改不了，所以没问题 └───┴───┘ ▼ (0) 第二步：[ 那个列表 ] * 3 对 list 做重复 外层 list ┌───┬───┬───┐ │ • │ • │ • │ ← 复制的是「地址」，不是内容 └─┬─┴─┬─┴─┬─┘ └───┼───┘ ▼ ┌──────────────┐ │ [0, 0, 0] │ ← 只有一个内层列表！ └──────────────┘ 三个槽位指向它 grid[0][0] = 1 → 改的是这唯一一个内层列表 grid[1][0] / grid[2][0] 看到的是同一份 ────────────────────────────────────────────── 规律：* 重复对不可变元素安全，对可变元素危险 [0]*3 安全（int 不可变） ["x"]*3 安全（str 不可变） [[]]*3 危险（list 可变） [{}]*3 危险（dict 可变）

* 重复复制的永远是引用，不是对象。元素不可变时你察觉不到区别，元素可变时它就变成一个共享状态的陷阱。判据很简单：只要方括号里装的是能改的东西，就别用 *，改用列表推导式。

引用语义不止影响乘法，赋值、切片、作为函数参数传递时都有类似的表现。这部分展开起来是独立的一大块（浅拷贝与深拷贝详见 PY09），这里只需要先建立一个警觉：当你发现「我明明只改了一个地方，怎么别处也变了」，先怀疑两个变量指向了同一个对象。

三、dict 与 set：哈希表原理

dict 和 set 是同一套机制的两种包装：set 就是只存键、不存值的 dict。这套机制叫哈希表——通过一个函数把键直接算成存储位置，从而绕过「逐个比对」这个过程。理解它，就同时理解了这两个容器的全部性能特征和全部限制。

核心的一步叫哈希：对任意一个键调用 hash(key)，得到一个整数，再把这个整数对表的容量取余，得到一个槽位下标。同一个键永远算出同一个下标，所以查找不需要遍历——算一次、跳过去、比一下，结束。这就是 O(1) 的来源，它不依赖表里有多少元素。

d = {"alice": 30, "bob": 25} 查 d["bob"] 发生了什么 ────────────────────────────────────────────── "bob" ──► hash("bob") ──► 一个大整数 ──► % 表容量 ──► 槽位 5 （字符串内容决定） （取低位） │ ▼ 哈希表（一块定长的槽位数组） ┌────┬────────────────────────────┐ │ 0 │ (空) │ │ 1 │ hash=…41 key="alice" v=30 │ │ 2 │ (空) │ │ 3 │ (空) │ │ 4 │ (空) │ │ 5 │ hash=…77 key="bob" v=25 │ ◄── 一步到位 │ 6 │ (空) │ │ 7 │ (空) │ └────┴────────────────────────────┘ 落位后还要做一次校验： 先比 hash 是否相同（比整数，极快） 再比 key == key （防止两个不同的键撞到同一个哈希） 两个都过，才算命中 ────────────────────────────────────────────── 冲突了怎么办：开放寻址（CPython 的做法） 插入 "carol"，算出来也是槽位 5，但 5 已被占 槽5 被占 ──► 按扰动序列探测下一个候选槽 ──► 槽 2 空 ──► 放这 查询 "carol" 时重走同一条探测路径，直到命中或遇到空槽 所以：表越满，探测链越长，O(1) 越不像 O(1) CPython 在装载率约 2/3 时扩容并 rehash，把链压回去

为什么 list 不能作键，tuple 可以

整条链路的前提是「同一个键永远算出同一个哈希值」。如果一个对象的内容可以变，那它今天算出槽位 5、明天改了内容算出槽位 9，昨天放进去的那条记录就再也找不回来了——表会静默地损坏。所以 Python 直接从源头堵死：只有可哈希对象才能作键，判据是它实现了 __hash__ 且在生命周期内哈希值稳定。

不可变类型天然满足这个条件，所以 int、str、bool、float、tuple、frozenset 都能作键。list、dict、set 是可变的，CPython 把它们的 __hash__ 显式设成 None，一旦拿去作键就会抛 TypeError: unhashable type: 'list'。这个报错信息里的 unhashable 就是在说这件事。

d = {}
d[(2026, 9, 14)] = "会议"      # OK：tuple 全是不可变元素
d[["a", "b"]] = 1              # TypeError: unhashable type: 'list'
d[(1, [2])] = 1                # TypeError: unhashable type: 'list'
                               # tuple 可哈希的前提是元素全部可哈希

第三行是最容易被忽略的一条：tuple 本身不可变，但它是否可哈希取决于里面装的东西。装了 list 的 tuple 照样作不了键，因为算它的哈希值要把所有元素的哈希值揉在一起，而 list 这一步就算不出来。

成员判断：O(1) 与 O(n) 的分水岭

插入顺序：3.6 是实现细节，3.7 才是承诺

很长一段时间里，「dict 是无序的」是 Python 的常识，教程都会提醒你不要依赖迭代顺序。CPython 3.6 重写了 dict 的内部布局，用一个紧凑的条目数组加一个稀疏的索引数组来省内存，副产品是迭代恰好呈现插入顺序——但官方当时明确说这是实现细节，不保证、也不许依赖。

到 Python 3.7，这个行为被正式写进语言规范，成为所有实现都必须遵守的承诺。这个区别在实践中是有意义的：3.6 上的代码依赖顺序，换成同版本的另一个实现就可能出问题；3.7 起则可以放心依赖。set 没有这项保证，它的迭代顺序取决于哈希值和插入历史，看起来「随机」但其实是确定的，只是不要去依赖。

哈希表用空间换了时间：它必须留出大约三分之一的空槽让探测不至于变长。所以 set 的内存开销明显大于同样元素数的 list——这笔交易在「需要频繁判断存在性」时非常划算，在「只是存一串数据从头遍历」时纯属浪费。

四、复杂度对照：这张表决定了大部分性能问题

新手写出的慢代码，八成不是因为算法写错了，而是因为在错误的容器上做了它不擅长的操作。下面这张表把三个容器的常见操作放在一起，它足以解释绝大多数「数据量一大就卡住」的现象。

看这张表有个省力的读法：找出所有标着 O(n) 的格子，它们就是潜在的性能地雷。list 占了其中绝大多数——in、insert(0)、pop(0)、remove。如果这些操作出现在一个循环里面，整体复杂度就变成了 O(n²)。

示例场景：一个去重脚本要从 20 万条日志里过滤掉已处理过的记录，已处理 ID 存在一个 list 里。代码是 if log.id not in processed_ids:，循环 20 万次、每次平均扫描 10 万个元素，总比较次数达到 200 亿量级，脚本跑了 47 分钟还没结束。把 processed_ids = [] 改成 processed_ids = set()，一个字符的改动（append 改 add 算第二处），运行时间降到 2.1 秒。复杂度从 O(n²) 变成 O(n)，加速约 1300 倍。这不是微优化，是把一个算法错误改对了。

值得强调的是这类问题的隐蔽性。开发时用 200 条测试数据，list 方案跑 0.01 秒，set 方案跑 0.008 秒，看不出任何区别，代码顺利上线。问题只在数据量涨到某个规模之后才暴露，而那时候现象是「服务变慢」，很难一眼定位到这行看起来人畜无害的 in。

示例场景：另一个常见形态是把 list 当队列用。某个任务分发脚本用 tasks.pop(0) 取下一个任务，队列长度稳定在 5 万左右，每次弹出都要搬移 5 万个指针。改用 collections.deque 的 popleft() 之后，单次出队从 O(n) 变成 O(1)，整批 5 万个任务的分发耗时从 18 秒降到 0.04 秒。改动是两行：导入 deque、把 pop(0) 换成 popleft()。

判断一段代码会不会出性能问题，只需要问一句：有没有 O(n) 的操作被放进了 O(n) 的循环里。for x in a: if x in b 这个形状就是典型——只要把 b 换成 set，整体立刻从平方降到线性。

一个反直觉的补充：小数据量下 list 可能更快

哈希表有固定开销：算哈希、取余、探测、比对。当元素只有十几个时，这些开销可能超过 list 那十几次简单比较。经验阈值大约在几十个元素，低于这个规模两者差别可以忽略，用哪个都行。但真实系统里数据规模往往会增长，而代码不会跟着改——所以当语义上就是「判断存在性」时，从一开始就写 set，不要等它变慢了再回来改。

五、tuple 与不可变性的真实含义

「tuple 是不可变的 list」这句话流传很广，它对一半、错一半。错的那一半会在某天让你写出一个诡异的 bug：一个声称不可变的对象，内容却变了。

准确的说法是：tuple 的不可变性作用在它自己那一层——它内部那个指针数组一旦建好，长度和每个槽位存的地址就永远不会改。但地址指向的对象是什么状态，tuple 管不着。如果某个槽位指向一个 list，你完全可以通过它去修改那个 list 的内容，而 tuple 的每个槽位仍然指向原来那个地址，从 tuple 的角度看什么都没变。

t = (1, "ab", [7, 8]) ────────────────────────────────────────────── tuple 的三个槽位（建好之后彻底冻结） ╔════════╦════════╦════════╗ ║ ptr0 ║ ptr1 ║ ptr2 ║ ← 这三个地址不可改 ╚═══╤════╩═══╤════╩═══╤════╝ 长度也不可改 │ │ │ ▼ ▼ ▼ ┌─────┐ ┌──────┐ ┌──────────────┐ │ int │ │ str │ │ list │ │ 1 │ │ "ab" │ │ [7, 8] │ ← 这个对象本身 └─────┘ └──────┘ └──────────────┘ 是可变的！ 冻结 冻结 ▲ │ t[2].append(9) │ 合法！改的是内层 list → t 现在是 (1, "ab", [7, 8, 9]) 但 t 的三个指针一个都没动 t[2] = [] ✗ TypeError: 'tuple' object does not support item assignment （这是在改 ptr2 本身，被禁止） ────────────────────────────────────────────── 连带后果：可哈希性也被内层对象拖累 hash((1, "ab")) ✓ 元素全可哈希 → tuple 可哈希 hash((1, "ab", [7])) ✗ TypeError: unhashable type: 'list' 算 tuple 的哈希要先算每个元素的哈希

这个特性带来的实际风险是：一个装了可变元素的 tuple，既不能作字典键（会抛 TypeError），也不能当作「安全传递的快照」——你把它传给别人，别人照样能改里面的 list。真正需要「传出去不会被改」的保证时，tuple 里必须全是不可变元素。

两个语法细节

第一个是单元素 tuple。让一个值成为 tuple 的是逗号，不是括号——括号在这里只起分组作用。所以 (5) 就是整数 5，(5,) 才是长度为 1 的 tuple。这条规则在函数返回值和字符串格式化里最容易出事，症状通常是后续代码抛出一个类型完全对不上的错误。

a = (5)       # int，括号只是分组
b = (5,)      # tuple，长度 1 ← 逗号才是关键
c = 5,        # 也是 tuple，括号可以省
d = ()        # 空 tuple，唯一不需要逗号的情况
print(type(a), len(b))    # <class 'int'> 1

第二个是解包。x, y = point 这种写法之所以自然，是因为 tuple 天然就是「一条固定字段的记录」，函数返回多个值实际上返回的就是一个 tuple。这也解释了为什么约定俗成地用 tuple 而不是 list 来返回多值：字段数量是固定的，语义上根本不该让调用方去 append。

什么时候该升级成 namedtuple

tuple 的短板是位置即含义。p[0] 是经度还是纬度？三个月后回来看这行代码，你得翻到定义处才知道。字段超过两三个时，这种下标访问会迅速变成维护负担，而且交换两个字段的顺序不会报错，只会静默算错。

具名元组解决的正是这个问题：它生成一个 tuple 的子类，给每个位置起个名字，既能 p.lat 这样访问，又保留 tuple 的全部特性——不可变、可哈希、能解包、能当字典键、内存开销和普通 tuple 几乎一样。

Point = namedtuple("Point", "lat lng")

print(p.lat)          # 31.23   ← 有名字，不用记下标
print(p[0])           # 31.23   ← 仍然是 tuple，下标照用

{p: "上海"}           # 可哈希，能当字典键

不可变是一层「壳」的属性，不是整棵对象树的属性。tuple 保证的是「我这几个格子里装的地址不会变」，它从不保证「那些地址指向的东西不会变」。想要真正的只读快照，里面必须全是不可变元素。

六、collections 里那几个真正常用的

标准库的 collections 模块提供了一批容器的变体。它们并不提供内置类型做不到的功能——每一个都能用 list/dict 手写出来——但它们能把一段重复出现的样板代码收成一行，或者把一个 O(n) 的操作变成 O(1)。真正高频的只有四个。

defaultdict：省掉「键不存在怎么办」的判断

往字典里累积数据时，每次都要先确认键存不存在，不存在就初始化一个空容器。这段判断在任何分组、计数、建倒排索引的代码里都会出现。defaultdict 接受一个「工厂函数」，访问不存在的键时自动调用它生成默认值，样板就消失了。

有一个行为要留意：defaultdict 在读取不存在的键时也会创建它。d["不存在的键"] 不会抛 KeyError，而是静默插入一个空值。想检查存在性时要用 in 或者 .get()，不要直接下标访问。

Counter：计数这件事被做完了

Counter 是 defaultdict(int) 的特化版本，额外提供了 most_common(n) 直接拿出出现次数最多的 n 项（内部用堆，比全排序快），还支持计数器之间做加减和交并运算。统计词频、统计错误码分布、统计标签分布这类需求，它基本一行解决。

deque：两端都是 O(1)

双端队列的内部结构是分块的双向链表，而不是连续数组。代价是不能按下标随机访问（dq[5000] 要沿着链走，是 O(n)），收益是两端的插入和删除都是 O(1)。凡是「先进先出」的场景——任务队列、广度优先搜索、滑动窗口——都应该用它而不是 list。它还支持 maxlen，超出长度自动从另一端丢弃，做「最近 N 条」的缓冲区非常顺手。

collections 不是「高级用法」，而是把最常写错的那几段代码做成了现成件。看到自己在写 if k not in d: d[k] = []，就该想到 defaultdict；看到 pop(0)，就该想到 deque。

  • 语义是「判断存在性」或「去重」时，从第一天就用 set，别等慢了再改
  • 需要按 ID 查找就建 dict 索引，别在 list 上做线性查找
  • 队列、滑动窗口、BFS 用 collections.deque，两端都是 O(1)
  • 二维列表用推导式 [[0]*n for _ in range(m)] 构造
  • 函数返回多个值用 tuple；字段 ≥ 3 个时升级成 namedtuple
  • 累积数据用 defaultdict，计数用 Counter，别手写样板
  • 循环里拼接列表用 append / extend，不要 result = result + [x]
  • 在循环里对 list 做 in 判断——这是 O(n²) 的标准形状
  • 用 lst.pop(0) / lst.insert(0, x) 模拟队列
  • 用 [[0]*3]*3 造二维列表——三行共享同一个内层列表
  • 用 {} 表示空集合——那是空字典，空集合只能写 set()
  • 把可变对象（list/dict/set）拿去作字典键——直接 TypeError
  • 在遍历一个 list/dict 的同时增删它的元素——行为不可预期
  • 依赖 set 的迭代顺序——它没有任何顺序保证

最后补一句关于选型时机的话。这些取舍看起来都很小，改一个词的事，但它们的成本极不对称：写代码时选对容器是零成本的，上线之后再改则要重新验证、重新回归。与其事后优化，不如在写下变量名的那一刻就想清楚——这份数据将来最频繁的操作是什么。关于解释器本身和运行环境的部分，可以回看 PY01 · Python 环境与解释器。

Q&A

list 和 tuple 除了「能不能改」还有别的区别吗？
有三个实际差别。第一是可哈希性：元素全部可哈希的 tuple 可以作字典键、放进 set，list 永远不行，这往往是选 tuple 的真正原因而不只是「防止误改」。第二是语义信号：tuple 表达「一条结构固定的记录」，list 表达「一串同类元素的序列」，所以坐标、数据库行、函数多返回值用 tuple，日志行集合、批处理结果用 list。第三是开销：tuple 长度固定不需要预留扩容空间，内存略小，创建也略快，但这个差距在绝大多数场景下可以忽略，不该作为选型依据。反过来说，如果你的数据之后要增删元素，tuple 就完全不适用，每次「修改」都得造一个新对象。
为什么 list 不能作字典的键，而 tuple 可以？
因为字典靠键的哈希值决定存储位置，这要求哈希值在对象整个生命周期里保持稳定。list 的内容可以随时改，改完哈希值就变了，之前按旧哈希值存进去的那条记录会永远找不回来——表会静默损坏而不是报错，这比报错更糟。所以 CPython 直接把 list、dict、set 的 __hash__ 设成 None，拿去作键时立刻抛 TypeError: unhashable type: 'list'。tuple 不可变，哈希值算出来就固定了，因此可以作键。但要注意一个前提：tuple 的哈希值由所有元素的哈希值共同算出，所以装了 list 的 tuple 同样不可哈希，(1, [2]) 作键一样会报错。需要用序列作键时，把 list 转成 tuple 即可。
[[0]*3]*3 为什么改一个格子会三行一起变？
因为 * 重复运算复制的是引用，不是对象。[[0]*3]*3 分两步：内层 [0]*3 先造出一个列表；外层的 *3 再把这个列表的地址复制三份放进外层列表。结果是外层三个槽位指向的是同一个内层列表，改任何一行都是在改那唯一的一份。为什么内层的 [0]*3 没问题？因为 int 是不可变的，三个槽位虽然也指向同一个 0，但你永远改不了 0 本身，只能让槽位指向别的数，所以观察不到共享。正确写法是列表推导式 [[0]*3 for _ in range(3)]，循环每轮都会真正执行一次 [0]*3，造出三个独立的列表。判断规律很简单：* 重复对不可变元素安全，对可变元素危险。
为什么 set 的 in 是 O(1)，list 的 in 是 O(n)？
因为两者的查找机制完全不同。list 是一块连续存放元素指针的内存，没有任何索引结构，判断某个值在不在里面只能从头逐个用 == 比较过去，平均要比 n/2 次，元素越多越慢。set 是哈希表：先对目标值算一次哈希，把哈希值映射成槽位下标，直接跳到那个位置看有没有东西，有就再比一次值确认，整个过程与集合里有多少元素无关。代价是内存：哈希表必须留出大约三分之一的空槽来降低冲突，所以同样元素数的 set 占用内存大约是 list 的三到四倍。另外 O(1) 是平均复杂度，极端情况下大量键哈希冲突会退化，但对正常数据分布来说不用担心。实践结论是：只要语义上是「判断存在性」，就用 set。
append 明明有时候要搬移整个数组，为什么还说它是 O(1)？
这里说的是摊还复杂度，不是单次最坏复杂度。单看一次 append，如果正好赶上预留槽位用完，确实要申请一块更大的内存并把已有的 n 个指针全部拷过去，这一次是 O(n)。但关键在于 CPython 按比例预留空间而不是每次只多要一格：新容量大约是当前元素数的 1.125 倍再加一个常数，容量序列大致是 0、4、8、16、25、35、46、58、72、88。预留量随规模增长，扩容频率就随规模下降，连续做 n 次 append 的搬移总量加起来仍然是 O(n)，平均到每次就是常数。这就是摊还分析的意义：衡量一连串操作的平均代价，而不是盯着最坏的那一次。如果换成每次只多申请一格，总代价会变成 1+2+…+n，也就是 O(n²)。
dict 到底有没有顺序？听说 3.7 之后就有序了。
要区分「排序」和「插入顺序」这两件事。dict 从来不会按键的大小自动排序，想要排序得自己 sorted(d.items())。所谓「3.7 之后有序」指的是迭代时按插入顺序：先放进去的键先被迭代到。这个行为的历史是这样的：CPython 3.6 为了省内存重写了 dict 的内部布局，副作用是恰好呈现插入顺序，但官方明确说这是实现细节、不许依赖；到 3.7 才正式写进语言规范，成为所有 Python 实现都必须遵守的承诺。所以在 3.7 及以上版本可以放心依赖插入顺序，3.6 上不行。另外注意 set 没有这项保证，它的迭代顺序由哈希值和插入历史共同决定，看起来杂乱且会随数据变化，任何时候都不要依赖。
tuple 不是不可变吗，为什么我能改它里面的 list？
因为不可变性只作用在 tuple 自己那一层。tuple 内部是一个定长的指针数组，它保证的是「长度不变、每个槽位存的地址不变」。而地址指向的对象是什么状态，tuple 完全管不着。所以 t = (1, [7, 8]) 里，t[1].append(9) 是合法的——改的是那个 list 对象本身，t 的两个指针一个都没动；但 t[1] = [] 会抛 TypeError: 'tuple' object does not support item assignment，因为这是在改指针本身。这个特性有个连带后果：装了可变元素的 tuple 不可哈希，作不了字典键，因为算 tuple 的哈希值要先算每个元素的哈希值。所以「传出去保证不被改」的只读快照，前提是 tuple 里全部是不可变元素。
什么时候该从 tuple 换成 namedtuple 或 dict？
判据是字段数量和结构稳定性。两个字段、含义靠上下文一看就懂（比如 (key, value)、(width, height)），普通 tuple 完全够用，上 namedtuple 是过度设计。字段到了三个以上，而且这个对象要传给别的函数或者存进容器，就该换 namedtuple：p.lat 比 p[0] 可读得多，更重要的是它能防止字段顺序搞反——搞反了普通 tuple 不会报错，只会静默算出错误结果。namedtuple 保留了 tuple 的全部特性：不可变、可哈希、能解包、能当字典键，内存开销几乎一样。如果还需要类型注解、默认值或字段校验，就上 typing.NamedTuple 或 dataclass。而如果字段本身会增删、结构不固定，那它压根就不是一条「记录」，应该用 dict。
什么时候真的需要 collections 里的东西，什么时候内置类型就够？
两个触发条件。第一个是性能：发现自己在用 lst.pop(0) 或 lst.insert(0, x) 模拟队列，这两个操作是 O(n)，队列一长就会拖垮整体，换成 deque 立刻变 O(1)。这是唯一一类「不换不行」的情况，其余都属于可读性优化。第二个是重复样板：发现自己反复写 if k not in d: d[k] = [] 或 d[k] = d.get(k, 0) + 1，就该换成 defaultdict(list) 和 Counter，它们把意图直接写在了类型上。反过来说，简单的小字典、短列表没必要为了用而用。还有一个使用 defaultdict 时的注意点：读取一个不存在的键也会把它创建出来，所以检查存在性要用 in 或 .get()，别直接下标访问，否则字典会被你的检查动作悄悄撑大。
