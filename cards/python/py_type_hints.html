PY20 · 类型注解与静态检查

注解的运行时地位 / 语法速查 / 泛型与型变 / mypy 与 pyright 落地 / 收益与成本 / Protocol 与入口校验

注解不是给 Python 看的，Python 根本不看。它是写给下一个读这段代码的人、以及替那个人提前把话说清楚的工具链看的——所以判断一处注解该不该写，标准从来不是「语法允许吗」，而是「它能替谁省下一次翻源码」。

一、注解在运行时的真实地位

先把最容易误解的一件事摆平：CPython 不检查类型注解。下面这段代码能正常运行，返回 "xy"，解释器连一句警告都不会给。

def add(a: int, b: int) -> int:
    return a + b

print(add("x", "y"))   # 输出 xy，没有任何报错

类型注解是附着在函数、变量、类属性上的一段元数据，解释器把它求值后存进 __annotations__ 字典，然后就不管了。add.__annotations__ 的值是 {'a': int, 'b': int, 'return': int}——仅此而已，它和函数体的执行没有任何关系。这一点决定了后面所有讨论的基调：注解的价值全部来自「谁在读它」，而不是来自 Python 本身。

注解在运行时是一段死数据，在工程上是一份活契约。它没有强制力，只有传播力——所以写错的注解比不写更危险，因为它传播的是错误信息。

注解从源码流向了哪里

既然解释器不用，那注解写给谁？下面这张图画的是它离开源码之后的四条去向。

延迟求值：注解什么时候变成字符串

默认情况下注解是立即求值的表达式，这带来两个麻烦：一是类还没定义完就不能在自己的方法里引用自己，二是每个函数定义都要真的去执行一遍注解表达式，导入变慢。from __future__ import annotations（3.7 起可用，曾计划在 3.10 成为默认但被推迟）把整个模块的注解改成「原样保存成字符串、不求值」。

这让前向引用——在类型还没定义出来的位置提前引用它——变得自然：过去要写成 "Node" 这种手工字符串，现在直接写 Node 就行。代价是拿到的不再是类型对象而是字符串，谁想要真正的对象就得调 typing.get_type_hints() 自己解析一次。

from __future__ import annotations

class Node:
    def sibling(self) -> Node:      # 不加 future 就得写成 "Node"
        ...

print(Node.sibling.__annotations__)  # {'return': 'Node'}  ← 是字符串

于是上一节说的「少数派」会受影响：某些版本较老的、直接读 __annotations__ 又不做字符串解析的库，一旦遇到这个 future 导入就会拿到 'Node' 而不是 Node，表现为「加了一行 import 之后模型突然构造失败」。主流库（pydantic v2、FastAPI 新版）都已经改用 get_type_hints()，但遇到小众库仍要留意。Python 3.14 起按 PEP 649/749 把注解改成了真正的惰性求值，兼顾了两边，长期看这个历史包袱会淡出。

二、类型语法速查：从简单到组合

类型语法在 3.9 到 3.12 这几个版本里变化很大，网上大量教程停留在旧写法。判断一段注解是不是「现在该这么写」，看两点：还在不在从 typing 里 import 容器类型，以及还在不在写 Optional。这两样都属于被内置语法取代的历史写法。

类型语法的演进方向只有一个：把 typing 模块里的东西搬回语言本身。所以看到 List、Dict、Optional 这种大写开头的写法，基本可以判定这段代码或这篇教程是 3.9 之前的产物。

Any 和 object：一字之差，方向相反

这是最容易混淆、后果也最大的一对。Any 是逃生舱：标成 Any 的值可以赋给任何类型，也可以对它做任何操作，检查器一律放行。object 是最宽的具体类型：任何值都能赋给它，但你几乎不能对它做任何事——取属性、调用、下标全都会被报错，因为检查器无法确认所有对象都支持这些操作。

Any object │ │ ┌──────────────┴──────────────┐ ┌──────────────┴──────────────┐ │ 检查器：我不看了，你随便 │ │ 检查器：我只让你做所有对象 │ │ │ │ 都能做的事（str()、is 比较）│ └──────────────┬──────────────┘ └──────────────┬──────────────┘ │ │ x: Any = get() │ x: object = get()│ x.whatever() │ ✓ 放行 x.whatever() │ ✗ 报错 x + 1 │ ✓ 放行 x + 1 │ ✗ 报错 y: int = x │ ✓ 放行 y: int = x │ ✗ 报错 │ │ ── 传染性：Any 会 │ ── 收敛性：object │ 顺着赋值链一路 │ 逼你先 isinstance 扩散，把下游的 │ 收窄，再往下用 检查一起关掉 │ │ 经验：想表达「什么都可能」用 object；想表达「我暂时不想管」才用 Any， 并且用一次就该配一条注释说明为什么管不了。

Any 的真正问题是传染性。一个函数返回 Any，调用方接住它的变量也就成了 Any，再往下传就把整条链路的检查都关掉了——这也是 mypy 的 --warn-return-any 和 pyright 的 reportUnknownMemberType 这类选项存在的理由：它们专门用来揪出这种静悄悄的失守。

用 Literal 把「魔法字符串」变成可检查的约束

大量真实 bug 出在字符串参数拼错上：mode="wirte" 这种问题在运行到那一行之前没人发现。Literal 把取值集合写进签名，拼错在编辑器里就是红波浪线。

from typing import Literal

def open_file(path: str, mode: Literal["r", "w", "a"] = "r") -> str:
    ...

open_file("a.txt", "wirte")   # 检查器：不在 "r" | "w" | "a" 之中

配合 Final 还能表达「这个常量不许再改」，配合 ClassVar 能区分「类级共享配置」和「实例字段」——后者在 dataclass 里尤其重要，因为标了 ClassVar 的属性不会被当成构造参数。

三、泛型与类型变量

有了前两节的语法，还有一类签名写不出来：「返回值的类型取决于参数的类型」。比如取列表第一个元素的函数，传 list[int] 该返回 int，传 list[str] 该返回 str。写成 object 太宽，写成 Any 等于放弃，这里需要的是类型变量——一个在签名内部代表「某个待定类型」的占位符，同一个名字出现多次就表示它们必须是同一个类型。

# 3.12 起的新语法：方括号里直接声明 T
def first[T](xs: list[T]) -> T:
    return xs[0]

# 3.12 之前：先造一个 TypeVar 对象
from typing import TypeVar
T = TypeVar("T")
def first_old(xs: list[T]) -> T:
    return xs[0]

类型变量表达的不是「什么类型都行」，而是「进来和出去必须是同一个类型」。它锁住的是关联关系，不是具体类型——这正是 Any 做不到的事。

约束与上界的区别

两种收窄类型变量的方式长得像，含义完全不同。约束（constraints）是枚举：T 只能是列出的那几个类型之一，不能是它们的子类混搭。上界（bound）是继承封顶：T 可以是这个类型或它的任意子类。

写法3.12 新语法含义典型用途
TypeVar("T", int, str)[T: (int, str)]约束：只能是 int 或 str 之一函数对少数几个类型分别有实现
TypeVar("T", bound=Number)[T: Number]上界：Number 或其任意子类要求参数「至少具备某种能力」
TypeVar("T")[T]完全自由，只保证前后一致容器工具函数，如 first

型变：为什么 list[Cat] 不是 list[Animal]

型变说的是「容器的子类型关系要不要跟着元素的子类型关系走」。直觉上 Cat 是 Animal 的子类，那 list[Cat] 好像也该是 list[Animal]——但这个直觉是错的，而且理由非常具体。

假设允许 list[Cat] 当成 list[Animal] 用： cats: list[Cat] = [Cat()] animals: list[Animal] = cats ← 假设这一行放行 animals.append(Dog()) ← 完全合法：Dog 是 Animal cats[1].meow() ← 💥 运行时炸：这是条狗 根因：list 可写。往「宽」的视角里塞东西， 会污染「窄」的那个引用看到的内容。 ──────────────────────────────────────────────────────────── 只读视角就没有这个问题： cats: list[Cat] = [Cat()] animals: Sequence[Animal] = cats ← 放行，且安全 animals.append(...) ← Sequence 压根没有 append ──────────────────────────────────────────────────────────── 不变（invariant） 协变（covariant） ┌──────────────────────┐ ┌──────────────────────────┐ │ list / dict / set │ │ Sequence / Iterable │ │ 可变容器 │ │ Mapping（值位置）/ tuple │ │ list[Cat] ≠ list[Animal] │ Sequence[Cat] ⊂ Sequence[Animal] │ └──────────────────────┘ └──────────────────────────┘ 逆变（contravariant） ┌────────────────────────────────────────────────┐ │ Callable 的参数位置 │ │ 能处理 Animal 的函数，一定能处理 Cat │ │ Callable[[Animal], None] ⊂ Callable[[Cat], None] │ └────────────────────────────────────────────────┘

把这三条合起来，会自然导出一个非常实用的签名原则：参数类型尽量声明得宽，返回类型尽量声明得窄。参数写成 Iterable/Sequence/Mapping 这类只读抽象，调用方传 list、tuple、生成器都行；返回写成具体的 list/dict，调用方拿到手就能直接索引、直接改，不用再包一层。

这些抽象类型都在 collections.abc 里，3.9 起可以直接当泛型下标用，不必再从 typing 导入。把参数从 list[str] 放宽成 Iterable[str] 通常是零成本的改动，却能让调用方省掉一次 list(...) 的物化——尤其是上游本来就是生成器的时候，这一步可能意味着几百 MB 内存。PY12 · 迭代器与生成器协议里讲过的惰性优势，只有在签名放宽到 Iterable 之后才真正传得下去。

四、mypy 与 pyright：两个检查器的差异与落地

静态类型检查器是一个独立于解释器的程序，它读源码和注解，在不执行代码的前提下推断每个表达式的类型并找出矛盾。Python 生态里有两个主流选择，它们不是竞品关系那么简单，很多团队实际上两个都在跑。

mypy 是你在 CI 里设的那道闸，pyright 是你敲代码时身边那位随时插话的同事。前者要求稳定可复现，后者要求快和贴身——这两件事本来就不该由同一个工具承担。

维度mypypyright
身份事实上的参考实现，PEP 落地的风向标微软出品，VS Code 里 Pylance 的引擎

两者对同一段代码给出不同结论是常态，因为它们对「未注解的函数要不要查」「推断到什么程度算确定」的默认立场不同。实际做法是：CI 只认一个（多数团队选 mypy，因为它的行为更贴近 PEP 字面），编辑器里用另一个当辅助，并且接受编辑器偶尔比 CI 更啰嗦。

严格度是渐进的，不是开关

Python 的类型系统被设计成渐进式类型——同一个项目里可以一部分有注解、一部分没有，两边混跑，未注解的部分默认按 Any 处理。这个设计的全部意义就在于让存量项目能分批迁移。可惜第一次接入的人几乎都会直接开 --strict，然后被几千条报错劝退。

存量项目接入静态检查的推荐顺序（每一档都先把报错清零再进下一档） 第 0 档 装上、跑通、把基线记下来 mypy . → 先只看有多少条、集中在哪几个包 第 1 档 只开语法级检查，关掉所有「没写注解」类的提醒 ignore_missing_imports = true ← 第三方库先放过 目标：清掉真正的类型矛盾（往往是真 bug） 第 2 档 按模块打开 disallow_untyped_defs [[tool.mypy.overrides]] module = "myapp.core.*" ← 从最核心、改动最少的包开始 disallow_untyped_defs = true 第 3 档 补存根：给第三方库装 types-xxx，去掉 ignore_missing_imports pip install types-requests types-PyYAML 第 4 档 全仓 strict，遗留点用 # type: ignore[具体错误码] 挂起 并在 CI 里加 warn_unused_ignores，防止 ignore 越积越多 ── 每一档都是可发布状态；任何一档卡住都可以停在那里，不影响前面的收益 ──

第 4 档那条关于 ignore 的写法值得单独说：# type: ignore 会关掉这一行的所有检查，包括以后新引入的真 bug；# type: ignore[arg-type] 只关掉指定的那一类。再配上 warn_unused_ignores = true，当某个 ignore 因为代码修好而不再需要时，检查器会主动提醒你删掉它——否则这些注释会在仓库里沉淀成永久的盲区。

第三方库没有注解怎么办

一个库能不能被检查器理解，取决于它有没有提供类型信息：要么内联注解并带上 py.typed 标记文件，要么由社区在 typeshed 维护独立的存根包——一批只含签名不含实现的 .pyi 文件，安装后检查器就能读到它。命名规律是 types- 加库名，比如 types-requests、types-PyYAML。装不上存根的小众库，就用 ignore_missing_imports 单独对那个模块放行，而不是全局关掉。

示例场景：一个 12 万行的 Django 服务第一次接入 mypy，直接开 --strict 跑出 4300 多条报错，团队看了一眼就把这件事搁置了半年。第二次换渐进路线：第 1 档关掉缺失导入相关的检查后剩 217 条，其中 9 条是真 bug（两处把 None 当 dict 用、一处参数顺序传反），当周修完；第 2 档按包打开 disallow_untyped_defs，6 个核心包用了 3 周补完签名；第 3 档装了 5 个 types- 存根包；第 4 档全仓 strict 剩 38 处遗留，全部用带错误码的 ignore 挂起并建了跟踪清单。全程 11 周，期间每一次提交都是可发布的，CI 从未因为类型检查红过超过一天。

五、注解真正付费的地方，以及它的成本

注解不是越多越好，它的收益分布极不均匀。判断标准可以概括成一句话：信息在人脑里越容易失效的地方，注解的回报越高。函数签名、模块公共 API、数据结构定义——这些地方的信息要跨越文件、跨越团队、跨越几个月的时间去传递，人是记不住的；而三行之内就能读完的局部变量，注解只是把检查器已经知道的事情又说了一遍。

注解收益 vs 距离（信息要跨越多远才被使用） 高 ▲ │ ┌──────────────────┐ │ │ 对外发布的库 API │ 跨团队、跨版本、有人照着写代码 │ └──────────────────┘ │ ┌──────────────────────┐ 收 │ │ 跨模块的函数签名 │ 调用方不会点进来看实现 益 │ └──────────────────────┘ │ ┌────────────────────────┐ │ │ 数据结构 / dataclass │ 字段含义最容易被忘掉 │ └────────────────────────┘ │ ┌──────────────┐ │ │ 模块内私有函数│ 还值得写，成本也低 │ └──────────────┘ │ ┌──────────────────────┐ 低 │ │ 局部变量 x = len(ys) │ 检查器早就知道了 └──────────────────────────┴──────────────────────┴────────► 距离近 跨团队 ───────────── 跨模块 ───────────── 函数内几行之间 ── 例外：局部变量在两种情况下该注解 ── 1) 空容器初始化： results: list[str] = [] ← 否则推断成 list[Unknown] 2) 推断结果明显过宽： conf: Config = load() ← load 返回 Any 时收住它

该不该写这处注解，问一句就够了：如果读代码的人看不到函数体，他还能正确调用吗？答案是「不能」的地方，注解就是刚需；答案是「能」的地方，注解多半是噪声。

成本是真实的，别假装它不存在

第一项成本是签名膨胀。一个五行的工具函数，配上多层嵌套泛型之后签名可能比函数体还长，读者的注意力被语法吃掉。遇到这种情况，用类型别名把复杂类型收成一个有名字的概念，往往比硬写更好——type Handler = Callable[[Request], Awaitable[Response]]（3.12 语法）一行就让下游所有签名短一半。

第二项成本是和动态特性冲突。猴子补丁、**kwargs 透传、会改变签名的装饰器，这些写法在 Python 里合法且常用，但类型系统很难完整表达。ParamSpec（3.10+）能救回一部分装饰器场景，但复杂的元编程仍然只能靠 Any 或 ignore 让路。

第三项成本最隐蔽：写错的注解比不写更糟。没有注解时读者知道自己不知道，会去看实现；有错误注解时读者以为自己知道了，直接照着写——而错误会一直传播到运行时才暴露。函数被改过但签名没跟着改，是这类问题最常见的来源。

示例场景：某数据管道里一个函数早期签名是 -> dict[str, int]，半年后为支持小数改成返回浮点，函数体改了、注解忘了改。因为该模块被排除在 mypy 检查范围之外（当初为了让 CI 快点通过），错误签名存活了 4 个月。期间 3 个下游模块照着注解写了整数运算，其中一处对金额做了 int() 截断，导致 约 1.2 万条记录的金额被抹掉小数部分，对账差异累计 3700 多元，排查用了 2 天。把这个模块纳入检查范围后，同一处矛盾在 CI 里 30 秒内就能被指出来。结论不是「别写注解」，而是写了就必须让检查器守着它——无人校验的注解会退化成过期文档。

六、Protocol 与运行时校验的边界

Python 的日常写法建立在鸭子类型上：我不管你是什么类，只要你有 .read() 我就当你是个可读对象。用名义类型（必须显式继承某个基类）去描述这种代码会非常别扭，而 typing.Protocol（3.8+）提供的结构化子类型——只看有没有对应的方法和属性，不看继承关系——正是为它准备的。

from typing import Protocol

class Reader(Protocol):
    def read(self, n: int = -1) -> str: ...

def load(src: Reader) -> str:     # 文件对象、StringIO、自定义类都能传
    return src.read()

关键在于：任何拥有匹配 read 方法的类都自动满足 Reader，不需要也不应该显式继承它。这让你可以给第三方类型、给标准库对象、给同事写的类补上类型约束，而完全不碰它们的定义。枚举与 Protocol 那一张卡（PY22）会更完整地展开这套用法，包括运行时可检查的 runtime_checkable 变体及其局限。

普通基类问的是「你的祖先是谁」，Protocol 问的是「你会做什么」。鸭子类型本来就只关心后者，所以给鸭子类型加类型标注，用 Protocol 才不拧巴。

这也正好接上PY16 · 继承、MRO 与组合优先的结论：为了满足类型检查而硬造一层继承，是典型的「用继承解决非继承问题」。Protocol 让你既保留组合式的松耦合，又拿到了静态检查。

静态检查管不了外部输入

最后一条边界必须讲清楚，它是整张卡里最容易出事故的地方：静态检查只覆盖你写的代码，覆盖不了运行时流进来的数据。把一个 HTTP 请求体标成 dict[str, int]，检查器会信你，但对面发来的 JSON 里那个字段完全可能是字符串 "12"、可能是 null、也可能压根不存在——注解对此毫无办法，程序会在几十行之后以一个毫无线索的 TypeError 崩掉。

两者是互补而不是替代关系。合起来的目标是：把「数据不合法」这件事的发现时间，从业务逻辑深处提前到入口那一行。pydantic 的价值恰恰在于它复用了同一套注解语法——你写的类型注解既被 mypy 静态检查，又被 pydantic 在运行时真的拿去校验，一份声明两处生效。

  • 公共函数、模块边界、数据结构定义一律补全注解
  • 参数用 Iterable/Sequence/Mapping 放宽，返回用具体 list/dict 收窄
  • 存量项目分档接入检查器，每档清零再进下一档
  • 用 # type: ignore[错误码] 并开 warn_unused_ignores
  • 鸭子类型用 Protocol 描述，不为了类型去硬造继承
  • 外部数据一进来就在入口做运行时校验，转成可信的内部类型
  • 空容器初始化写出元素类型：results: list[str] = []
  • 第一次接入就开 --strict，然后被几千条报错埋掉
  • 用 Any 消报错——它会顺着赋值链把下游检查一起关掉
  • 给每个局部变量都加注解，把签名淹没在噪声里
  • 写裸 # type: ignore，连以后的真 bug 一起屏蔽
  • 改了函数体不改签名，让注解退化成过期文档
  • 以为注解能挡住外部脏数据，省掉入口校验
  • 还在写 typing.List / Optional[X]（3.9 / 3.10 起已有内置写法）

Q&A

既然 Python 运行时不检查注解，写它到底图什么？
图的是把「这个函数怎么用」这件事，从人的记忆里搬到机器能校验的地方。注解本身确实只是存进 __annotations__ 的元数据，解释器求值一次就不管了；但 mypy、pyright 会在代码执行之前把类型矛盾找出来，IDE 会据此给出准确补全和跳转，文档工具会把它渲染成 API 说明。收益的量级取决于你是否真的跑了检查器：只写注解不跑检查，收益基本只剩「读起来清楚一点」，而且随着代码演进会慢慢退化成过期文档。另外有一类库确实在运行时读注解——pydantic、FastAPI、dataclasses——对它们来说注解是真正的输入，写错了程序行为就会变。
Any 和 object 到底该用哪个？
先问自己想表达什么。想说「这里什么对象都可能出现，我会先判断再用」，用 object：它是最宽的具体类型，任何值都能赋给它，但检查器只允许你做所有对象都支持的操作，想往下用就必须先 isinstance 收窄——这是一种良性的强制。想说「这块我暂时管不了，别查了」，才用 Any：它和任何类型双向兼容，检查器完全放行。Any 最大的问题是传染性，一个返回 Any 的函数会让接住它的变量也变成 Any，顺着调用链把下游的检查一起关掉，所以 mypy 才提供 --warn-return-any 专门揪这种情况。实践上的规矩是：Any 每出现一次就配一条注释说明为什么必须放弃检查。
为什么 list[Cat] 不能当 list[Animal] 用？
因为 list 是可写的。假设允许这么用，那么把一个 list[Cat] 赋给 list[Animal] 类型的变量之后，通过后者 append(Dog()) 是完全合法的——Dog 确实是 Animal。但原来那个 list[Cat] 引用还在，它现在指向一个混进了狗的列表，随后对元素调用 meow() 就会在运行时炸掉。所以可变容器必须是不变的，元素类型必须严格一致。只读的抽象就没有这个隐患：Sequence 没有 append，因此 Sequence[Cat] 可以安全地当作 Sequence[Animal] 使用，这叫协变。由此得到的实用结论是参数尽量声明成只读抽象，返回值声明成具体容器。
团队该选 mypy 还是 pyright？能不能两个都用？
常见做法正是两个都用，但分工明确：CI 门禁只认一个，多数团队选 mypy，因为它是事实上的参考实现、行为最贴近 PEP 字面、配置项细粒度且稳定；编辑器里则用 pyright（VS Code 装 Pylance 就自带），它快得多、支持 watch 模式、推断更激进，写代码时能更早发现问题。要接受的代价是两者对同一段代码可能给出不同结论，主要分歧在「未注解的函数要不要查」和「推断到什么程度算确定」上。关键是别让两个工具都有否决权，否则开发者会陷入互相矛盾的报错里；把其中一个定为唯一的准绳，另一个当作参考提示。
存量项目第一次接入类型检查，报错几千条怎么办？
别硬啃，也别放弃——Python 的类型系统本来就被设计成渐进式的，允许一部分模块有注解、一部分没有。推荐分四档走：先只开语法级检查并对第三方库放行，把真正的类型矛盾清掉，这一档里往往能捞出若干真 bug；再按模块逐个打开 disallow_untyped_defs，从最核心、改动最少的包开始补签名；然后给第三方库装 types-xxx 存根包，去掉之前的全局放行；最后才全仓开 strict，剩下的遗留点用带具体错误码的 # type: ignore[...] 挂起并建跟踪清单。每一档结束时仓库都是可发布状态，任何一档卡住都可以停在那里，前面的收益不会丢。
# type: ignore 怎么用才不会变成技术债？
三条规矩。第一，永远写具体错误码，比如 # type: ignore[arg-type]，而不是裸的 # type: ignore——后者会关掉这一行的全部检查，包括以后新引入的真 bug，等于在代码里开了个永久盲区。第二，开启 warn_unused_ignores，这样当某处代码被修好、ignore 不再必要时，检查器会主动提醒你删掉它，避免这些注释越积越多。第三，给每个 ignore 配一句注释说明原因，是第三方库缺注解、还是用了检查器表达不了的动态特性，这决定了它将来能不能被清理。做到这三条，ignore 就是一份有记录、会过期的临时豁免，而不是无声的技术债。
from __future__ import annotations 加了会有什么副作用？
它把当前模块里所有注解从「立即求值的表达式」改成「原样保存的字符串」。好处很实在：可以自由写前向引用，类在自己的方法签名里直接写类名而不用加引号；同时省掉了导入时求值注解的开销，模块加载更快。代价是运行时拿到的 __annotations__ 里全是字符串，需要真实类型对象的代码必须调 typing.get_type_hints() 解析一次。因此少数直接读 __annotations__ 又不做解析的库会因为这一行 import 而失灵，表现为「加了个 import 之后模型突然构造失败」。主流库早已改用 get_type_hints()，遇到小众库才需要留意。Python 3.14 起把注解改成真正的惰性求值，两边的好处兼得，这个历史包袱会逐渐淡出。
有了类型注解，还需要在入口做数据校验吗？
必须要，这是两件不重叠的事。静态检查只看你仓库里的源码，它能保证内部调用方式一致、字段名没拼错、分支没漏掉 None；但它完全看不到运行时流进来的数据。你把请求体标成 dict[str, int]，检查器会信你，可对面发来的 JSON 里那个字段完全可能是字符串、是 null、或者根本不存在，程序会在几十行之后以一个毫无线索的 TypeError 崩掉。正确做法是在数据进入应用的第一道门就做运行时校验（pydantic 之类），把外部数据转成可信的内部类型，之后全程不再写 isinstance 兜底。好消息是两者共用同一套注解语法，一份声明既被 mypy 静态检查，又被校验库在运行时真正执行。
Protocol 和普通基类比，什么时候该用哪个？
看你要表达的是「身份」还是「能力」。需要共享实现、需要表达一条明确的继承谱系、需要 isinstance 判断家族归属时，用普通基类或 ABC。只关心「这个对象会不会做某件事」——有没有 read、能不能迭代、支不支持 close——就用 Protocol，因为它是结构化子类型，只比对方法和属性，不看继承关系。Protocol 的独门优势是能给你改不了的类型加约束：第三方库的类、标准库对象、别人写的类，都可以在不碰其定义的前提下被纳入检查。这也更贴合 Python 本来的鸭子类型风格，硬造一层继承只为了满足类型检查通常是本末倒置。
