先量出瓶颈在数据侧还是计算侧 / 映射式与迭代式两种抽象 / 批次拼接、填充与掩码 / 多进程加载的机制与四类坑 / 供给优化的收益顺序与正确性纪律

训练速度从来不由最快的那一环决定。加速设备每秒能吃多少样本是一个数，数据管道每秒能产出多少样本是另一个数，实际速度等于这两个数里小的那个——而绝大多数人只优化前者，因为后者不写在任何一条曲线上。

一、数据管道决定训练速度的上限

加速设备很贵，也很快。它一秒能做完的矩阵运算量，用纯 Python 做要几个小时。但正因为它快，它对「喂料速度」极度敏感：如果下一批数据还没准备好，它就只能停下来等——不是降速运行，是真的空转。

这件事最麻烦的地方不是它会发生，而是它不留痕迹。损失曲线只记录「第几步、损失多少」，不记录每一步之间等了多久。一个数据喂不上来的训练，曲线形状和一个健康的训练完全一样：该降的时候降，该收敛的时候收敛，只是每一步之间多等了几百毫秒，一轮从 12 分钟变成 42 分钟。你会觉得「这个模型就是训得慢」，然后去调批大小、换优化器、加机器——全都打在空处。

怎么判断瓶颈在哪一侧

判断方法的核心思路只有一句：把两侧分别单独跑一遍，各自量出一个「每秒多少样本」的数。加载器空跑（只遍历、不做前向反向）量出的是数据侧的产能；用一批常驻内存的假数据反复喂计算图，量出的是计算侧的产能。两者取小，就是这次训练的理论上限；两者的比值，就是你能拿到的设备利用率。

这张表的次序就是推荐的排查次序：利用率告诉你「有没有问题」，两个吞吐数告诉你「问题在哪侧」，批次间隔告诉你「被卡住的具体是哪一步」，资源读数告诉你「卡在 CPU 还是磁盘」。PY42 讲过一条通用纪律——没有可复现的测量方法就不要开始优化，它在数据管道上同样成立，而且更重要：管道的每一次改动都同时影响吞吐和内存，没有基线你分不清是改好了还是换了个瓶颈。

动手之前先量两个数：加载器空跑能出多少样本每秒，计算侧用内存里的假数据能吃多少样本每秒。小的那个是你的上限，另一边的优化一分钱收益都没有。

事故复盘：一个多模态分类任务，18 万条样本一轮，预期一轮 12 分钟左右，实际跑了 42 分钟，六十轮要两天。第一反应是模型太大、机器不行。按上表量了两个数：加载器空跑 74 样本/秒，换成常驻内存的假批次后计算侧能吃 280 样本/秒——比值 26%，和监控里看到的 23% 平均利用率吻合。瓶颈在数据侧，且差着近四倍。

根因在数据集的取样方法里：它每次都 open() 一个 120 MB 的清单文件，从头切分出 18 万行的偏移表，再按索引定位那一条。也就是说这份清单被完整解析了 18 万次，单次约 110 毫秒，8 个加载进程摊下来正好凑出一轮 42 分钟。修复是把清单解析挪出取样路径：进程启动后首次访问时构建一次内存索引（每条只留一个偏移量，总共几 MB），之后取样只做一次定位读取，单次降到约 3 毫秒。

结果：设备利用率 23% → 88%，一轮耗时 42 分钟 → 12 分钟，六十轮总时长 42 小时 → 12 小时，单次训练省下约 30 小时。模型、超参、批大小一个字没改。

二、两种数据集抽象：按索引取样与顺序产出

「数据集」这个词在框架里对应两种完全不同的契约，选错会在多进程或多机阶段才暴露，改起来往往要重写取数逻辑。区别只有一个问题：你能不能按编号随机拿到第 i 条。

映射式数据集回答「总共多少条」和「第 i 条是什么」两个问题。有了这两个能力，框架就能先生成一个 0 到 N-1 的索引序列，再按这个序列去取数据——于是打乱变成了「打乱这个索引序列」，多进程分片变成了「把这个序列切成几段」，都不需要碰你的数据。迭代式数据集只回答一个问题：「从头顺序产出」。它适合根本没有「第 i 条」概念的数据：网络流、消息队列、按行追加的日志、以及大到无法建立全量索引的分片文件。

映射式：索引在框架手里，数据集只负责「按号取货」 ────────────────────────────────────────────────────────── 总长度 N ──▶ 采样器生成索引序列 [7, 3, 91, 25, ...] │ 打乱 = 打乱这个序列 │ 分片 = 把序列切成 W 段，一段给一个加载进程 ▼ 取样方法(i) ──▶ 一条样本 ──▶ 拼接函数 ──▶ 一个批 迭代式：框架不知道有多少条，也不能跳着取 ────────────────────────────────────────────────────────── 数据流 ──▶ 迭代方法 ──▶ 样本 样本 样本 ... ──▶ 拼接 ──▶ 批 │ ├─ 打乱：只能用固定大小的缓冲区近似 │ （先蓄满 K 条，从中随机弹一条，再补一条） └─ 分片：必须自己按加载进程序号跳过不属于自己的条目 忘了写 = 每个进程把整份数据各产一遍， 一轮的数据量悄悄变成 W 倍重复

上图迭代式那条分支的最后一句是这类数据集的头号坑。映射式的分片由框架代劳，迭代式的分片是你的责任：框架只是把同一个数据集对象复制给了每个加载进程，如果对象自己不区分「我是第几个进程」，每个进程都会老老实实从头产出全部数据。训练不会报错，损失也照降，只是每一轮实际上把同一份数据重复喂了 W 遍。

映射式的两个方法各自承担什么

长度方法不只是给进度条用的。它定义了「一轮有多少条」，而这个数会一路传导到学习率调度的总步数、验证触发的时机、以及采样器生成索引的范围。写错它的后果不是报错，是每一轮少喂或多喂一部分数据。

取样方法承担「给一个索引，返回一条完整样本」。这里有两条容易被忽视的约束。第一，它会被随机顺序、并发调用——采样器给的索引是乱序的，而调用它的是多个互不相识的子进程，所以它必须是无副作用的纯读取，不能依赖上一次调用留下的状态。第二，它在整个训练里被调用的次数等于「样本数 × 轮数」，所以任何放在它内部的重活都会被放大几十万倍，这正是上一节那起事故的成因。

class ManifestDataset:
    def __init__(self, path):
        self.rows = read_manifest(path)   # 只存轻量索引，不在这里开句柄
        self.handle = None                # 句柄留到子进程里首次用时再建
    def __len__(self):                    # 一轮有多少条
        return len(self.rows)
    def __getitem__(self, i):             # 给一个索引，返回一条完整样本
        return decode(self._file().read_at(self.rows[i]))

这个骨架里有两处刻意的设计：构造函数只留下轻量索引（每条一个偏移量，18 万条也就几 MB），以及句柄字段先置空。第四节会解释为什么句柄必须延后到子进程里创建。迭代式那一侧的契约本质上就是迭代器协议，PY12 讲过它的惰性语义——数据管道是这套协议在工程上最重的一个应用场景：整条链路（读取、解码、增强、拼批）都是惰性的，只有被消费时才真正干活。

映射式把「取哪条」的权力交给框架，所以打乱和分片免费；迭代式把这个权力留在自己手里，所以打乱和分片都得自己写对。能建索引就用映射式，这不是风格偏好，是省掉两类安静的错误。

三、批次是怎么拼出来的

取样方法返回的是单条样本，但计算需要的是批。中间那一步由拼接函数完成：它收到一个「若干条样本」的列表，要返回一个「批」。默认实现做的事很简单——按字段递归下去，把同名字段沿一个新增的批维度堆叠起来。

堆叠意味着一个硬要求：同一批里的样本形状必须完全一致。图像都是 224×224 没问题，但文本长度不等、音频时长不等、检测框数量不等，堆叠会直接因形状不匹配而失败。好消息是这个错误是响亮的——它当场抛异常，不会悄悄算错。

变长数据：填充与掩码是一对，不能只做一半

解决变长的标准做法是填充：在批内把所有样本补齐到本批最长，短的那些用一个约定的填充值垫上。但填充值是凭空造出来的数据，如果不额外告诉下游「哪些位置是真的」，它就会被当作真实内容参与计算。

这就是掩码必须同时产出的原因，也是本节最重要的一句话：只填充不给掩码，是一个不报错的错误。它的后果分散在下游各处——平均池化会把填充位算进分母，于是句子越短、表示被稀释得越厉害；损失会把填充位算进分子，于是模型花力气去预测那些不存在的位置；注意力会允许真实位置去关注填充位。训练照样收敛，指标照样像个样子，只是永远差那么几个点，而你从任何一处报错都看不到它。

def collate_pad(samples):                  # samples: [(ids, y), ...]
    lens = [len(ids) for ids, _ in samples]
    n = max(lens)                          # 对齐到「本批最长」，不是全局最长
    ids  = [s + [PAD_ID] * (n - len(s)) for s, _ in samples]
    mask = [[1] * L + [0] * (n - L) for L in lens]   # 掩码与填充同时产出
    ys   = [y for _, y in samples]
    return to_tensor(ids), to_tensor(mask), to_tensor(ys)

注意第三行对齐到的是本批最长而不是全局最长。这个差别很大：全局最长意味着每一批都被最极端的那条样本拖着走，而按批动态对齐让大多数批都紧凑。代价是每批形状不同，某些需要固定形状的编译优化会因此反复重编译——这是个真实的取舍，不是免费的。

按长度分桶：省掉的是白算的算力

动态填充之后仍有浪费，因为随机打乱会把一条 500 长度的样本和一堆 60 长度的样本凑进同一批。分桶的思路是让长度接近的样本尽量落在同一批：在一个几千条的窗口内按长度排序再切批，批之间再打乱顺序——这样既大幅压掉填充，又保留了足够的随机性。

还有一个位置问题值得记住：拼接函数运行在加载子进程里，不在主进程。这带来两个后果——它能吃到多进程的并行（所以把能向量化的活放进来是划算的），以及在需要序列化的启动方式下它自己必须可被序列化（所以不能写成 lambda 或局部函数）。下一节展开这件事。

填充和掩码是一对，永远一起出现。填充决定形状对不对，掩码决定算得对不对；只做前者，程序能跑、指标会骗人。

四、多进程加载的机制与坑

数据准备几乎全是 CPU 上的活：读文件、解码、分词、重采样、增强。这些活在 Python 字节码层执行，受全局解释器锁约束，放在主进程里做就只能和计算串行——回到第一节那张时间轴的上半部分。用子进程加载的唯一目的就是让数据准备和计算重叠，把「相加」变成「取最大」。

机制本身不复杂：主进程只管计算，若干加载进程各自领一段索引，各自取样、预处理、拼批，把成品批通过队列送回主进程。张量这类大块数据通常放进共享内存，队列里传的只是一个句柄而不是数据本体——PY27 讲过为什么跨进程传大对象时序列化本身才是瓶颈，数据加载器正是靠共享内存绕开了这笔开销。

图最下面那两行是调参的判据：队列的水位直接告诉你该往哪个方向使劲。下面逐条讲这套机制带来的坑，它们的共同特征是——没有一条会在你写代码时报错。

坑一：启动方式带来的开销与序列化要求

子进程怎么创建出来，决定了它出生时知道多少事。CPython 3.14 起，POSIX 平台的默认启动方式由 fork 改为 forkserver，fork 不再是任何平台的默认值；macOS 自 3.8 起默认 spawn，Windows 一直是 spawn。这个变化对数据加载的直接影响是：数据集对象、拼接函数、增强流水线都必须能被序列化，过去在 fork 下靠继承内存侥幸能用的 lambda、闭包、已打开的文件对象，现在会在启动加载进程时就报序列化失败。

开销也跟着变。fork 是毫秒级，spawn 要重新启动解释器并重新导入主模块，单个进程几十到几百毫秒；forkserver 在两者之间——服务进程预热后创建本身很快，但子进程同样不继承父进程已导入的模块和已建好的对象，数据集要序列化过去重建。如果加载进程每一轮都销毁重建，这笔钱每轮都要付一遍——小数据集上「每轮开头卡几秒」多半就是这个原因，对应的解法是让加载进程常驻。

坑二：每个子进程拿到的是数据集对象的副本

这是最值得记住的一条。fork 下子进程按写时复制继承父进程的地址空间，spawn 和 forkserver 下是把对象序列化过去重新构造——两种路径的结果都是每个加载进程手里都是一份独立的副本，它们之间的修改互不可见。PY10 讲的拷贝语义在这里从语言细节升级成了正确性问题。

于是在数据集的构造函数里持有数据库连接或已打开的文件句柄会出事，而且出的是两种不同的事。文件句柄带着一个共享的读偏移量，多个进程交替 seek 和 read 会互相踩踏，读到的是拼接错位的字节——这个错误完全安静，你拿到的是能解码、但内容错乱的样本。数据库连接更糟：连接上的请求响应是有状态的协议，多个进程同时往同一条连接上写，服务端会看到乱序的报文，表现为随机的连接重置或莫名其妙的结果集。

正确做法是构造函数里只存路径和轻量索引（第二节那个骨架就是这么写的），句柄延迟到子进程里首次访问时再创建，并且按进程各建一份。PY07 讲过文件对象的生命周期与关闭时机，多进程加载给它加了一条约束：句柄的创建位置必须和使用它的进程是同一个。

一条硬纪律：数据集对象必须能被序列化，并且不在构造函数里持有任何连接或句柄。这两条一起满足，你的数据集在任何启动方式、任何进程数下行为一致；违反其中任一条，故障形态都是「换个平台或换个进程数就变」——而这类问题的排查成本，通常是把句柄改成惰性创建的几十倍。顺手加一个自检：在取样方法里断言当前进程序号与句柄的归属一致，让错误在第一次发生时就响。

坑三：子进程里的随机种子

增强要用随机数，而随机状态也是被复制的那部分状态之一。fork 下每个加载进程继承的是父进程那一刻的随机状态副本，于是它们产出完全相同的随机序列——8 个加载进程意味着每 8 批里藏着同一组增强参数，数据多样性被悄悄砍掉了一大截，而训练和指标看不出任何异常。

框架通常会替你为它自己那套随机源按进程派生种子，但第三方数值库和标准库的全局随机状态不在其中。所以规则是：增强里用到的每一个随机源，都要在加载进程的初始化钩子里用「基础种子 + 进程序号 + 轮次」派生后重新播种；缺了轮次这一项，则每一轮的增强序列会完整重复。验证方法很直接——关掉打乱，连跑两轮，打印每个进程头几条样本的哈希，看有没有重复值。

坑四：进程数不是越多越好

加载进程有三笔成本。内存：每个进程一份数据集副本加一份预取缓冲，总占用随进程数线性增长，把索引做重了（比如把全量元数据读进内存）会让这条线很陡——PY23 解释过为什么进程里的内存释放了也未必还给操作系统，长期运行的加载进程会一点点累积。CPU：超过物理核数后进程开始互相抢，纯数据吞吐反而下降。还有一笔最容易被忽略的：线程超订——很多数值库默认按整机核数开线程，8 个加载进程各开 16 个线程，就是 128 个线程去抢 16 个核，切换开销吃掉了并行收益。

现象真实根因处理
启动加载进程时报序列化失败数据集或拼接函数里有 lambda、闭包、已打开的句柄改成模块级函数与可序列化对象；句柄改惰性创建
样本内容错乱但不报错多个进程共享同一个文件句柄的读偏移句柄在子进程内按进程各建一份
随机的连接重置、结果集串味数据库连接被复制后多进程共用连接池建在子进程里，绝不跨进程传递
增强看起来「重复度很高」随机状态被复制，各进程产出同一序列初始化钩子里按进程序号与轮次派生种子
每轮开头固定卡几秒加载进程每轮销毁重建，重复付启动成本让加载进程常驻
进程数加到一定程度后吞吐反降超过物理核数的争抢，或线程超订限制每进程的数值库线程数；进程数回退到峰值点
训练跑一阵后被内存杀掉副本数 × 单副本体积 + 预取缓冲超出物理内存瘦身数据集对象，减小预取批数或进程数

进程数怎么定？别猜，按第一节的纯数据吞吐翻倍试：4 起步，测 8，再测 16，涨幅低于一成就退回上一个值。这个数和机器核数、单样本成本、存储介质都相关，换一台机器就得重测。

每个加载进程都是一份副本，不是一个共享视图。凡是「同一份资源被多个进程同时用」的东西——文件句柄、数据库连接、随机状态——都必须在子进程里各建一份，否则错误会安静地进入你的数据。

五、让数据供给跟上

确认了瓶颈在数据侧，手段是有收益顺序的。下面这个顺序按「改动量小、收益大」排，前两条通常就能解决大部分问题，后面几条属于榨最后那几成。

手段一 · 预取与流水线重叠

预取是让加载侧始终领先计算侧若干批，这样主进程取批时数据已经在队列里。它几乎是唯一一个「配置一下就生效」的手段，也是第一节那张时间轴从串行变重叠的直接实现。预取深度不必大——能盖住计算一步的时长就够了，再深只是多占内存。

手段二 · 把重复的预处理提前做掉

这是收益最被低估的一条。同一份数据要训六十轮，意味着每条样本的解码、分词、重采样被做了六十遍，每一遍结果完全相同。把这些确定性的步骤离线做一次，转成可以直接读的中间格式（定长记录、数组文件、列式格式），取样路径就只剩下读取和反序列化。注意只有确定性的步骤能这么搬——随机增强必须留在线上，否则六十轮看到的是同一套增强结果。

手段三 · 存储格式与文件数量

大量小文件的随机读是最常见的隐形瓶颈，而且它不表现为带宽不足，表现为元数据操作和寻址次数过多：每条样本一次打开、一次定位、一次读取、一次关闭，磁盘带宽还剩九成，IOPS 已经打满。在网络文件系统或对象存储上，这个差距会再放大一个量级，因为每次打开都要付一次往返。

手段四 · 固定内存与异步搬运

主机内存到设备内存的拷贝可以和计算重叠，但前提是源缓冲区不会被操作系统换页——这就是固定内存的作用。它让拷贝引擎能在计算进行的同时搬数据，收益在批次较大、搬运量可观时才明显。代价也实在：固定内存是不可换页的物理内存，开太多会挤压系统可用内存，在容器里尤其容易触发限额。

手段五 · 把逐样本的活挪到批级

同一个归一化，写在取样方法里就是每条样本一次 Python 调用，写在拼接函数里就是整批一次数组运算。批大小 32 时，前者是 32 次跨语言调用加 32 次小数组分配，后者是 1 次。能向量化的预处理都该往批级挪，这一条对纯 Python 开销占比高的管道效果最明显。

手段适用的瓶颈代价
预取 + 加载进程重叠数据侧稍慢于计算侧，等待呈周期性内存（进程数 × 预取批数 × 批体积）
离线预处理 / 缓存中间结果每轮重复做同样的确定性变换额外磁盘空间；数据版本要跟着管，改了预处理要重跑
合并小文件为大分片IOPS 打满而带宽空闲；网络存储上的每次打开开销一次性转换成本；分片内随机性要靠打乱缓冲补回
更高效的存储格式（定长 / 列式）解析与反序列化占了取样路径的大头格式转换与工具链复杂度；调试时不能直接看原文
固定内存 + 异步搬运主机到设备的拷贝无法与计算重叠占用不可换页的物理内存，容器内易触发限额
预处理向量化到批级逐样本的 Python 开销占比高拼接函数变复杂；样本级逻辑差异不好表达
少做无用功（先裁剪再解码、只读需要的列）解码或读取了远多于所需的数据需要支持部分读取的格式配合
加加载进程单样本 CPU 成本高且核数有余量内存线性增长；超过峰值点后反而变慢

最后一行放在最后是有意的：加进程是最容易想到、也最容易掩盖真实问题的手段。当单条样本的成本本身不合理时（比如每次都重新解析一个大文件），加进程只是让八个进程一起做同样的蠢事。先把单样本成本压下来，再谈并行度。

优化数据管道的第一问永远是「这件事有没有必要每次都做」。能离线做一次的别每轮做，能批级做一次的别逐样本做——这两句话的收益，通常比任何并行度调整都大。

六、正确性纪律

数据管道的错误比性能问题贵得多，原因就一个字：安静。性能问题会让你等，等久了总会去查；正确性问题什么都不做，它只是让指标偏一点点，让线上表现配不上离线数字，而你会先去怀疑模型、怀疑分布漂移、怀疑一切——最后才回头看数据是怎么喂进去的。

打乱：训练集必须打乱，评估集不能打乱

训练集不打乱的后果来自数据本身的排列。真实数据集常按类别、时间或来源排序，不打乱就意味着连续很多个批里全是同一类样本，一个批内的梯度方向高度相关，批量大小带来的方差抑制基本失效——在按类别排序的数据上，不打乱几乎训不出可用的模型。

评估集则相反。打乱验证集不会改变全量遍历后的聚合指标（平均就是平均，顺序无关），但它会破坏两件事：逐样本输出与原始顺序对不上，误差分析和多次实验之间的样本级对比全部失效；如果评估里含分组或排序逻辑（检索、排序类指标），打乱会直接改变结果。更要注意的是它和「丢弃不完整批次」的组合——两个单独看都无害的选项凑在一起，指标就真的变了，因为被丢掉的那几十条每次都不同。

统计量只能从训练集算

归一化的均值方差、分位数裁剪的边界、类别编码的取值表、缺失值的填充值、分词器的词表、特征选择的结果——所有从数据里「学」出来的东西，都只能在训练集上拟合，然后原样套到验证与测试集上。在全量数据上算一遍再切分，就是信息泄漏：验证集的信息通过这些统计量进了训练。

它的危险之处在于偏差幅度恰好在「看起来正常」的区间：通常是虚高一两个百分点，你既不会因为它太离谱而怀疑，又会因为它比上一版好而采纳。等上线了掉回去，你已经在这条错路上迭代了十几个版本。

丢弃不完整批次：训练侧可开，评估侧必关

一轮的样本数很少能被批大小整除，最后那个批不满。训练侧丢掉它可以让形状恒定（对编译优化和显存复用有好处），代价是每轮最多丢掉「批大小减一」条样本——因为有打乱，每轮丢掉的是不同的样本，影响被平摊掉；但如果同时关掉了打乱，那就是每轮永久丢掉同一批尾部样本。

评估侧必须关掉，否则你算的指标不是在完整集合上算的。举个具体的数：验证集 10,043 条、批大小 64，开启丢弃后实际只评估 9,984 条，少了 59 条。59 条只占 0.6%，落到准确率上通常是零点几个百分点的浮动——而两个版本之间的差距往往也就这么大，于是你分不清是改进生效了还是尾批换了。

可复现要固定的不只是种子

可复现在数据管道上是个比看起来更宽的要求。要固定的随机源至少有四处：打乱的顺序、增强的参数、参数初始化、以及每个加载进程派生出的种子。但除了种子，还有一批结构性配置也是复现条件：加载进程数（它决定索引怎么分片、种子怎么派生）、批大小、是否丢弃尾批。改了进程数而种子不变，增强序列就变了，两次「相同配置」的实验结果对不上——这类不可复现最耗人，因为配置文件里看不出差别。

环节训练集验证 / 测试集违反的后果
打乱必须开关训练侧梯度相关、难收敛；评估侧样本无法对齐、可复现失效
预处理统计量在这里拟合只能复用训练集的值信息泄漏：离线虚高一两个点，上线掉回去
丢弃不完整批次可开（形状恒定）必须关评估集被悄悄截短，指标不可比
随机增强开，且每轮不同关（或只保留确定性变换）评估带随机性，同一模型两次跑出不同分数
数据划分方式时序数据按时间切；有近重复时先去重再切未来信息泄漏；同一内容分别落在两侧
种子与结构配置种子、加载进程数、批大小、尾批策略一并记录实验无法复现，且从配置上看不出差别

把数据管道当代码测。最低成本的三个测试就能挡住本节大部分事故：第一，取一个批出来断言形状、取值范围和掩码与长度一致（掩码求和应当等于真实长度）；第二，固定种子跑两次，断言前若干批的哈希完全相同，这一条同时守住了可复现和「进程数影响增强序列」；第三，断言验证集的遍历条数等于验证集大小，这一条专门抓丢弃尾批和忘记分片。三个测试加起来几十行，但它们检查的是唯一那类不会报错的错误。

  • 动手前先量两个数：加载器空跑吞吐、假数据下的计算吞吐
  • 能建索引就用映射式数据集，把打乱与分片交给框架
  • 数据集构造函数只存路径与轻量索引，句柄在子进程里惰性创建
  • 填充与掩码永远一起产出，并断言掩码求和等于真实长度
  • 每个随机源都按「基础种子 + 进程序号 + 轮次」派生
  • 确定性预处理离线做一次，小文件合并成大分片顺序读
  • 评估侧关闭打乱、关闭丢弃尾批，并断言遍历条数等于集合大小
  • 种子、加载进程数、批大小、尾批策略一起写进实验记录
  • 在取样方法里打开并解析大文件——它会被调用「样本数 × 轮数」次
  • 在数据集构造函数里持有数据库连接或已打开的文件句柄
  • 只做填充不给掩码，让填充值参与池化、注意力和损失
  • 在全量数据上算归一化统计量再切分数据集
  • 迭代式数据集不做分片，让每个加载进程各产一遍全量
  • 靠加加载进程去掩盖单样本成本本身不合理的问题
  • 把随机增强放进离线缓存，导致每轮看到同一套增强结果
  • 时序数据随机划分，或让近重复样本分别落进训练与验证

性能问题会让你等，正确性问题只会让你困惑。所以数据管道的验收顺序是反的：先用几个断言把「不会报错的错误」钉死，再去优化那些你能用秒表量出来的部分。

怎么最快判断到底是数据慢还是模型慢？
量两个吞吐数，十分钟能做完。第一个：只遍历加载器、不做前向反向，记下每秒多少样本，这是数据侧的产能。第二个：造一批常驻内存的假数据反复喂计算图，绕开整个管道，记下每秒多少样本，这是计算侧的产能。两者取小就是这次训练的上限，比值就是你能拿到的设备利用率——如果第一个数明显小于第二个，瓶颈在数据侧，任何模型侧优化都不会带来提速。补充一个更细的读数：在「取下一批」前后打时间戳并累计，如果等待时长占一步耗时的大头，基本可以直接定案。注意别只看平均利用率，要看按秒采样的时间序列：数据瓶颈的典型形态是锯齿状的忙一下、空一段，而平均值会把它抹平。
加载进程开几个合适？有没有经验公式？
没有可靠的公式，因为它同时取决于物理核数、单条样本的 CPU 成本、存储介质的并发能力和可用内存。可靠的是测法：用纯数据吞吐做指标，4 起步，测 8，再测 16，涨幅低于一成就退回上一个值。三件事会让曲线提前见顶。一是内存——每个进程一份数据集副本加一份预取缓冲，总占用随进程数线性增长；二是超过物理核数后的 CPU 争抢；三是线程超订，很多数值库默认按整机核数开线程，8 个进程各开 16 个线程就是 128 个线程抢 16 个核，这一条往往是「加到 16 反而更慢」的真正原因，处理办法是限制每个加载进程里数值库的线程数。还要注意换机器就得重测，这个数不能跨环境照搬。
为什么多个加载进程产出了一模一样的增强结果？
因为随机状态也在被复制的那部分状态里。以 fork 方式创建子进程时，每个进程继承的是父进程那一刻的随机状态副本，于是它们从同一个点出发产出完全相同的随机序列；8 个加载进程就意味着每 8 批里藏着同一组增强参数。框架一般会替它自己那套随机源按进程派生种子，但第三方数值库和标准库的全局随机状态不在这个范围内，这就是漏点所在。做法是在加载进程的初始化钩子里，用「基础种子 + 进程序号 + 轮次」派生后给每一个随机源重新播种——少了进程序号，各进程重复；少了轮次，每一轮重复。验证很简单：关掉打乱，连跑两轮，打印每个进程头几条样本的哈希，看有没有重复值。这个错误不会报任何异常，只会让数据多样性悄悄打折。
数据集里能直接持有数据库连接或打开的文件吗？
不能，至少不能在构造函数里持有。每个加载进程拿到的是数据集对象的副本，于是同一个资源会被多个进程同时使用，而这两类资源都受不了。文件句柄带着共享的读偏移量，多个进程交替定位和读取会互相踩踏，读到拼接错位的字节——它能解码成功，只是内容是错的，全程没有任何报错。数据库连接上的请求响应是有状态协议，多进程同时往一条连接上写会让服务端看到乱序报文，表现为随机的连接重置或串味的结果集。正确写法是构造函数只存路径和轻量索引，句柄延迟到子进程里首次访问时创建，并按进程各建一份。顺手加个断言：取样时检查句柄的归属进程与当前进程一致，让这类错误在第一次发生时就响，而不是在指标上慢慢渗出来。
迭代式数据集怎么打乱和分片？
两件事都得自己做，这是它和映射式最大的实操差别。打乱只能近似：维护一个固定大小的缓冲区，先蓄满 K 条，之后每次从缓冲区里随机弹一条、再从流里补一条。缓冲越大越接近全局打乱，代价是内存和启动延迟；如果源数据本身是按类别或时间聚集的，小缓冲的打乱效果会非常有限，更好的办法是在离线打包分片时就先打散一遍，训练时再叠加缓冲打乱。分片更关键：框架会把同一个数据集对象复制给每个加载进程，如果迭代逻辑不按进程序号过滤，每个进程都会从头产出全部数据，一轮的实际数据量变成进程数的倍数重复。常见做法是按分片文件分配——让每个加载进程只读属于自己的那些分片，这样既避免重复又保持顺序读。这个错误不报异常，检验方式是数一轮实际产出了多少条，和数据集大小对比。
变长文本一定要填充吗？不给掩码会怎样？
只要你想按批并行计算，就必须对齐形状，填充是最常用的对齐方式（替代方案是按 token 总数成批或做长度分桶，但它们也仍然要填充，只是填得少）。不给掩码的后果是一个不报错的错误：填充值是凭空造的数据，下游无法区分它和真实内容，于是平均池化把填充位算进分母（句子越短，表示被稀释得越厉害）、损失把填充位算进分子（模型花力气去预测不存在的位置）、注意力允许真实位置去关注填充位。训练照样收敛，指标照样像个样子，只是永远差几个点。所以填充与掩码要当成一对来写，并且加一条断言：掩码求和应当等于每条样本的真实长度。顺带一提，把对齐长度设成「本批最长」而不是全局最长，通常就能省下大半的填充量。
丢弃不完整批次这个开关到底该不该开？
分两侧看。训练侧可以开：它让每个批的形状恒定，对编译优化和显存复用有好处，代价是每轮最多丢掉「批大小减一」条样本。因为有打乱，每轮丢掉的是不同的样本，影响被平摊；但如果你同时关掉了打乱，那就变成每轮永久丢掉同一批尾部样本，这是个真实的偏差。评估侧必须关掉，否则指标不是在完整集合上算的：验证集 10,043 条、批大小 64，开启后实际只评估 9,984 条，少了 59 条。这 0.6% 足以让准确率在实验之间的差距量级上浮动，你会分不清是改进生效了还是尾批换了。还有个组合要特别留意：打乱验证集单独看无害（全量平均与顺序无关），丢弃尾批单独看影响也很小，两个凑在一起就让每次评估的实际样本集都不同，指标从此不可复现。
每一轮开头都固定卡住几秒，这是什么问题？
最常见的原因是加载进程在每一轮结束时销毁、下一轮开头重建，于是每轮都重新付一次启动成本。这个成本和启动方式强相关：fork 是毫秒级，感觉不到；而 spawn 要重新启动解释器并重新导入主模块，单个进程几十到几百毫秒，乘上进程数就是好几秒。CPython 3.14 起 POSIX 平台的默认启动方式由 fork 改成了 forkserver：它创建进程本身仍然很快（服务进程预热后只是一次 fork），但子进程不再继承父进程已导入的模块和已建好的对象，数据集得序列化过去重建——所以从旧版本升级上来的项目，这个卡顿可能是突然出现的。macOS 自 3.8 起、Windows 一直是 spawn，这个成本从来都在。解法是让加载进程常驻，别每轮重建。另一类原因是每轮开头的一次性重活，比如重新构建索引、重新打开分片、或者惰性初始化的句柄在每个进程里同时建立并触发一批元数据请求；这类要看的是第一批的耗时而不是平均耗时，把第一批单独计时就能区分出来。
