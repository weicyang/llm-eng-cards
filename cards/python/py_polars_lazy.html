PY50 · Polars 惰性执行与流式处理

列式布局与多线程 / 表达式与上下文 / 查询计划与两种下推 / 流式引擎与静默回退 / 生态互通与选型判据

上一套工具让你一步一步算，Polars 让你先把「要算什么」完整说完，再由引擎决定「怎么算」。这一句差别带来的不是语法上的小改动，而是性能排查的入口整个换了位置——从「哪一行代码慢」变成「引擎给我生成了什么计划」。

一、换工具的真实动机：三个结构性差异，而不是「新的更快」

「Polars 比 Pandas 快」这句话对决策没有任何帮助。快多少完全取决于你在做什么：一万行的表上两者的差别小于你敲回车的手速差异，而在一亿行上做多列聚合，差的可能是一个量级。真正值得换的理由不是速度这个结果，而是产生速度差的那三个结构性设计——因为这三点同时决定了「什么场景下它根本不会更快」。

差异一：列式内存布局 + 默认多线程

列式内存布局指同一列的所有值在内存里连续排放。这个安排对分析型负载天然有利：你算某列的均值时读到的每一个缓存行都是有用数据，而按行存放时每读一次缓存行都要顺带拖进来同一行里你并不关心的其它字段。Polars 的内存格式遵循 Apache Arrow 这一列式标准，这一点在第五节讲互通时还会再用到。

更重要的是执行侧：Polars 的引擎用 Rust 写成，默认就会把工作切给多个线程，不受 CPython 全局解释器锁的约束——因为真正在跑的循环根本不在 Python 字节码层。这和 PY27 里为了绕开锁而开多进程的思路正好相反：这里不需要你做任何并行化动作，把任务描述交出去就行。

差异二：表达式先构建，再整体优化

逐步执行的模型里，每一行代码都立刻产生一个中间结果，引擎没有机会知道你下一步要干什么。Polars 的写法是先把整段变换描述成一棵表达式树，执行时机由你显式触发——中间这段空隙就是优化器的工作窗口。第三节会讲它具体能做什么。

差异三：能处理超过内存的数据（有前提）

流式引擎按批处理数据，内存占用不随数据量线性增长，于是「数据比内存大」不再是一个硬墙。这是三点里收益最大、但也最容易踩坑的一点——第四节整节都在讲它的前提条件，请不要看到这句就直接上生产。

「没有行索引」值得单独讲

Pandas 的 Index 是一个强大但昂贵的抽象。它带来的收益是按标签取数和自动对齐；带来的成本是一整类只有踩过才知道的困惑：两个 Series 相加时按索引对齐而不是按位置、reset_index 忘了加 drop=True 于是多出一列、分组后索引变成多层、切片有时按标签有时按位置。这些问题的共同点是——它们都不是你的业务逻辑，是索引这个机制的副作用。

Polars 干脆不要行索引。表就是一组等长的列，行没有名字，只有位置。想要行号就显式造一列（with_row_index），想按某列对齐就显式写 join。代价很直接：习惯了 df.loc[...]、set_index、reindex 这套写法的人，等于要重新学一套。收益也很直接：没有隐式对齐，就没有隐式对齐带来的错。这类「去掉一个机制来消掉一类错误」的取舍，在工程上通常比「加一个机制来解决问题」更划算。

换工具的决策依据不是「谁的跑分高」，而是「我的瓶颈是不是正好落在它改掉的那三件事上」。数据装得进内存、单次几秒钟跑完、团队全在旧生态上，那三个优势一个都用不上。

二、表达式是核心抽象：它描述动作，不返回数据

学 Polars 最大的认知门槛不在语法，而在一个反直觉的事实：pl.col("amount") * 0.93 这个东西不是一列数据，它是一段「拿 amount 这一列乘 0.93」的描述。你可以把它存进变量、塞进列表、在四个不同地方复用，而它一次都还没有算过。

这就是 表达式：一个「对某些列做什么」的可组合描述。它之所以重要，是因为三件事都依赖这个性质——描述可以被优化器改写（第三节）、可以被并行调度（互不依赖的表达式同时跑）、可以被复用而不产生任何中间数据。

上下文决定表达式在哪里生效

表达式本身不知道自己要被用来干什么，这件事由 上下文 决定。上下文就是那几个接收表达式的方法：select（选出这些结果作为新表）、with_columns（在原表上追加或覆盖列）、filter（把表达式当作布尔条件筛行）、group_by(...).agg(...)（分组后逐组求值）。

关键在于同一个表达式在不同上下文里含义完全一致，变的只是它作用的范围。pl.col("amount").mean() 放在 select 里是全表均值，放在 agg 里是每组均值——你不需要为分组场景换一套写法，也不需要记「分组之后该用哪个方法」。这种一致性是这套 API 真正省脑子的地方。

表达式：一段描述，不是数据 ───────────────────────────────────────────────────────── e = pl.col("amount") * 0.93 ← 此刻什么都没算 └ 意思是「取 amount 列，逐元素乘 0.93」 把同一个 e 放进不同上下文，含义不变，作用范围变 ┌──────────────────┬──────────────────────────────────────┐ │ select(e) │ 求值，结果作为新表的一列 │ │ with_columns(e) │ 求值，追加/覆盖到原表上 │ │ filter(e.gt(100))│ 求值成布尔列，用来选行 │ │ agg(e.mean()) │ 在每个分组内部求值 │ └──────────────────┴──────────────────────────────────────┘ 互不依赖的表达式天然可并行 with_columns( pl.col("a").sum() , ← 线程 1 ┐ pl.col("b").mean(), ← 线程 2 ├─ 同时跑，因为 pl.col("c").max() , ← 线程 3 ┘ 它们读的是不同列 ) 并且没有「先算 a 再基于 a 算 b」这种隐式顺序： 同一个 with_columns 里的表达式都看到调用前的那张表

上图最后两行藏着一个必须记住的规则：同一个 with_columns 里的多个表达式，看到的都是调用之前的那张表。想用刚造出来的列，就再起一个 with_columns。这不是限制，正是它能并行的前提。

为什么这套写法天然没有链式赋值那类歧义

Pandas 里 df[df.a > 0]["b"] = 1 这类写法之所以危险，根源在于「取出来的东西到底是原表的视图还是副本」这个问题取决于运行时的内存布局，你从代码上看不出来，只能收到一句警告或者干脆静默失败。这个话题在 PY10 里有更一般的讨论：任何「不确定手上是别名还是副本」的 API 都会长出这类坑。

表达式模型从根上绕开了它：表达式不返回数据，所以你拿不到任何可以就地赋值的对象，也就写不出链式赋值。要改一列只有一条路——在 with_columns 里描述新值，得到一张新表。「改哪张表」和「改成什么」在语法上就被分开了，歧义没有生存空间。

从旧思维到表达式思维的对照

想做的事旧生态的典型写法表达式写法思维上的变化

这张表里最值得体会的是最后一列。四行的共同方向是同一个：手上握着的从「一块数据」变成「一段还没执行的描述」。这个转变和 PY12 讲生成器时的那个转变是同一回事——生成器也是先描述「怎么产生」，直到被消费才真的产生。语言层面早就有这套思路，Polars 只是把它搬到了表结构上。

import polars as pl

net = pl.col("amount") * 0.93          # 存起来，一次都没算
q = (
    df.filter(pl.col("status") == "paid")
      .with_columns(net.alias("net"), pl.col("city").str.to_uppercase())
      .group_by("city")
      .agg(net.sum().alias("net_sum"), pl.len().alias("n"))
)

注意 net 这个变量在 with_columns 和 agg 里各用了一次，含义一致、写法一致。这就是表达式可复用性的实际收益：业务口径（比如「净额 = 金额乘费率」）只定义一次，后面所有用到它的地方自动跟着变。

把 pl.col(...) 读成「那一列」而不是「那一列的数据」。它是一个名词性的指代，等到被放进某个上下文里才有值。一旦这个语感建立起来，这套 API 剩下的部分基本可以靠猜。

三、惰性与查询优化：性能问题先看计划，再看代码

Polars 有两套入口。read_parquet 这类函数立刻把数据读进来，返回一张真实的表；scan_parquet 这类函数什么都不读，只返回一个 惰性帧——一个记录着「将来要做什么」的对象。你在它上面链式调用得到的还是惰性帧，直到调用 collect() 才真正执行。

这个延迟不是为了省事，而是为了攒信息。当整段流水线都描述完之后，优化器能看到全貌，于是可以做一些在逐步执行模型里原理上不可能的事情。

两个最该知道的优化：谓词下推与投影下推

谓词下推是把过滤条件尽量推到靠近数据源的位置，最理想的情况是推进读取本身：读 Parquet 时，读取器先看每个行组的列统计信息（最小值、最大值），如果条件不可能成立就整组跳过，连解压都不做。投影下推是只读真正被用到的列——表有 120 列而你的查询只碰 5 列，那就只解码这 5 列。

这两条合起来解释了大文件上那种「不太合理」的速度：它并不是把同样的活干得更快，而是根本没干大部分活。也正因如此，收益高度依赖你的查询和文件结构：过滤性很强又落在有序列上，可能跳掉九成数据；全表全列聚合则一点都省不下来。这也是为什么本卡不给具体倍数——倍数是你的数据和查询决定的，不是工具属性。

怎么查看计划

explain() 打印将要执行的计划文本，默认给的是优化后的版本；传 optimized=False 得到你原样写下的那一版。把两者对着看，就能确认下推到底有没有生效。计划要从下往上读：最底下是扫描节点，上面逐层是变换。

q = (pl.scan_parquet("events/*.parquet")
       .filter(pl.col("city") == "SH")
       .select("city", "amount"))

print(q.explain(optimized=False))   # 你写下的样子
print(q.explain())                  # 优化器改写后的样子
# 在 scan 节点上确认两件事：
#   PROJECT 只列出 city / amount（投影下推生效）
#   SELECTION 里出现 city == "SH"（谓词下推生效）

如果 scan 节点上写的是「全部列」，或者过滤条件还留在上层节点上，说明下推没发生。最常见的原因是你在中间插了一个优化器看不穿的操作——比如一个自定义 Python 函数。优化器无法知道那个函数会读哪些列、会不会依赖被过滤掉的行，只能保守地放弃下推。这就是为什么在惰性管道里插 Python 回调的代价远不止那个函数本身的耗时。

一条纪律：惰性管道的性能问题，先看计划，再看代码。理由是这类问题的根因分布和普通 Python 代码完全不同。普通代码慢，慢在你写的那些行里，PY42 那套剖析方法直接可用；惰性管道慢，绝大多数时候慢在「优化器没能按你预期改写计划」——某个下推被一个不透明的操作挡住了，或者某个算子选了昂贵的实现。这类原因在剖析器里表现为「时间都花在引擎内部」，看不出任何线索，而在计划文本里一眼就能看到。顺序搞反的代价很实在：你会花半天优化一段本来只占 3% 耗时的代码。

惰性模式下你写的不是「执行步骤」，而是「需求说明」。既然交出去的是需求，验收的对象自然就是引擎返回的那份方案——看计划不是高级技巧，是这套模型里的基本操作。

四、流式处理与超过内存的数据：以及那个不会报错的回退

流式引擎把查询拆成按批推进的流水线：读一批、算一批、把结果攒到聚合状态里、丢掉这一批，再读下一批。因为任何时刻内存里只有若干批数据加上聚合状态，内存占用就不随输入规模线性增长——这才是「能处理比内存大的数据」的机制来源。

先把版本差异说清楚

行序那一行是 2.0 升级时最容易被忽略的坑：它不会报错，只会让依赖「偶然有序」的下游逻辑安静地出错。官方升级指南把这一条单独标成了危险提示。需要顺序就显式 sort，或者在支持的算子上传 maintain_order。另外 2.0 移除了 LazyFrame.profile()，理由是它为 in-memory 引擎设计，在并发的流式引擎下逐节点计时会给出误导性结果——这是个信号：流式下的性能观测手段和 in-memory 下不是一套。

最关键的一条：不支持流式的算子会静默回退

Polars 的很多算子有流式实现，但不是全部。有些操作本质上需要看到全量数据，有些只是还没实现流式版本。遇到这种算子时，引擎的处理方式是回退到 in-memory 引擎——官方文档的原话是「用户不需要知道这件事，但它对排查内存或性能问题可能有用」。

请把这句话读两遍。「用户不需要知道」意味着：没有异常、没有警告、没有返回值上的任何区别。你的代码照样跑出正确结果。在测试数据上它甚至跑得更快——因为小数据本来就不该走流式。等上了全量数据，那个回退点会把整段数据拉进内存，然后你的进程被内核杀掉。

怎么确认流式真的生效了

这一节是全卡最该落到手上的部分。按可靠性从低到高排，有这么几条手段。

一是读流式物理计划。注意一个陷阱：explain() 和 show_graph() 只有在显式传 engine="streaming" 时才渲染流式计划，否则给的是优化后的逻辑计划——你从里面看不出哪里回退。图形化的 show_graph(plan_stage="physical", engine="streaming") 会画出物理图，图例标注各节点的内存强度，比读文本更容易发现问题（它需要本机装有 graphviz）。

# 关键：不传 engine 的 explain 看不出流式，别拿它当依据
print(q.explain(engine="streaming"))

# 有 graphviz 的话画物理图，图例会标出各节点的内存强度
q.show_graph(plan_stage="physical", engine="streaming")

# 运行期日志（环境变量名以当前版本文档为准）
with pl.Config(verbose=True):
    q.collect(engine="streaming")

二是开详细日志。pl.Config.set_verbose(True)（或上面的上下文写法）会打开引擎的额外日志。Polars 还有一批 POLARS_* 环境变量可以控制详细程度、临时目录等，但这批变量长期处于「存在但未正式文档化」的状态，名称和语义在版本间变过。要用就先在你的版本上试一次确认，不要照抄博客。

三是做内存标定，这条最可靠。前两条都依赖你猜对了当前版本的 API 名，而这一条不依赖任何 API：用 1 倍、2 倍、4 倍规模的样本各跑一遍，记录进程峰值内存。流式真的生效时，峰值内存三次应该基本持平；如果峰值跟着样本规模一起翻倍，就是没流式，无论计划里写了什么。这个方法的好处是它验的是你真正关心的性质——内存不随数据量增长——而不是某个 API 的输出文本。

四是把内存上限变成测试失败。给批处理任务的测试环境设一个明确低于生产的内存上限（容器 --memory、cgroup、或进程内 resource.setrlimit），并用足够大的样本跑一遍。回退一旦发生，在 CI 里就会炸，而不是在生产的凌晨三点。PY23 讲过 RSS 不降不代表泄漏；这里关心的是另一个方向——峰值 RSS 的增长斜率，而不是它的绝对值。

五是能用 sink_* 就不要用 collect()。collect() 的语义是「把结果全部装进内存」，哪怕中间是流式的，最终结果也得装下。sink_parquet 这类接口边算边往外写，结果不需要驻留内存，因此才是真正意义上的「超内存输入 + 超内存输出」。批处理任务的默认写法应该是 sink，不是 collect。

# 批处理任务的默认形状：scan 进来，sink 出去，中间不落地
(pl.scan_parquet("s3://bucket/events/dt=*/*.parquet")
   .filter(pl.col("event") == "order_paid")
   .group_by("city", "dt")
   .agg(pl.col("amount").sum().alias("gmv"), pl.len().alias("n"))
   .sink_parquet("out/gmv.parquet"))
# 结果不需要装进内存；collect() 则必须装下整个结果

生产事故复盘：测试环境 40 秒跑完，全量上被内核杀掉。一个日级 GMV 聚合任务，测试用单天分区：约 820 万行、12 列、Parquet 压缩后 1.1 GB，跑 40 秒，容器峰值内存 2.3 GB，一切正常。上到全量 90 天：约 7.2 亿行、Parquet 约 96 GB，容器内存上限 16 GB。任务跑到第 6 分钟被 OOM 杀掉，退出码 137，日志里除了被截断的进度什么都没有——没有 Polars 的异常，没有警告。

排查走了两天弯路：先怀疑数据倾斜，按城市拆分批跑，某几个分片照样挂；又怀疑读取层，把 96 GB 换成本地盘，无效。转折点是拿 explain(engine="streaming") 打了一次流式计划，和之前一直在看的 explain() 对照——后者看起来完全正常，前者里有一段落在了 in-memory 节点上：管道中一个算子在该版本没有流式实现，引擎把它上游的结果整体物化了。这个回退从第一天就存在，只是 1.1 GB 的数据物化进内存毫无压力，测试永远不会暴露它。

修复是两件事：把那个算子改写成流式支持的等价形式（分组聚合 + 一次 join 替代原先的整表变换），以及把输出从 collect() 后再写盘改成 sink_parquet 直接落盘。修复后全量 90 天跑 28 分钟，容器峰值内存 3.4 GB，和单天的 2.3 GB 处在同一量级——这个「峰值不随规模增长」才是流式生效的验收标志。同时补了两条防线：CI 里用 8 天样本跑并把容器内存限到 4 GB，以及在管道的单元测试里断言流式计划中不出现 in-memory 节点。

流式这件事上，正确的心态是「默认它没生效，直到我验证过」。因为这套机制的失败方式是静默的：结果对、测试绿、小数据更快，唯一的症状出现在生产数据量上，而那时你已经没有排查的从容了。

五、与现有生态的衔接：共存，而不是替换

「要不要换成 Polars」这个问题本身问错了。真实的工程现实是两者长期共存：用 Polars 做重活（读大文件、过滤、聚合），把体量已经缩小的结果交给旧生态去做画图、统计建模、以及那些只有旧生态才有的专门功能。决定用哪个的不是喜好，是这一步的数据规模和下游要什么。

列式内存标准让传数据不必序列化

这种混用之所以代价低，靠的是 Apache Arrow 这个列式内存标准。当两个库都把数据按同一套列式布局放在内存里，「传数据」就退化成交换指向同一块内存的元信息——不需要序列化成字节流、不需要反序列化、不需要多占一份内存。这就是 零拷贝。

但零拷贝有条件，不满足条件就退化成一次完整复制。这是实践中最容易出问题的地方，所以值得一条条列清楚。

转换方向写法拷贝行为要注意
Polars → pandas（默认）df.to_pandas()会复制：Arrow 转 NumPy峰值内存至少翻倍；数值列的 null 变成 NaN，整型列被迫提升为浮点
Polars → pandas（Arrow 背后）df.to_pandas(use_pyarrow_extension_array=True)可零拷贝需装 pyarrow；保留 null 语义；之后在 pandas 侧做 Arrow 不支持的运算仍可能触发转回 NumPy
pandas → Polarspl.from_pandas(df)源列是 Arrow 背后时可零拷贝，NumPy 背后则复制想零拷贝要让 pandas 侧先用 Arrow 类型（读取时指定 Arrow 后端）
Polars ↔ Arrow 表df.to_arrow() / pl.from_arrow(...)通常零拷贝和别的 Arrow 生态组件对接时的通用中转
Polars → NumPydf.to_numpy()一般会复制NumPy 要的是单一 dtype 的稠密数组，多类型表必然重排

表里第一行是最常被忽略的一条：to_pandas() 这个看起来很轻的调用会把内存占用推到至少两倍。一个刚用流式把 96 GB 压成 200 MB 结果的管道，在最后一行 to_pandas() 上把内存翻倍通常没事；但如果中间结果还有几个 GB，这一行就是新的内存峰值。

# 重活交给 Polars，结果小下来之后再过桥
small = (pl.scan_parquet("events/*.parquet")
           .filter(pl.col("dt") >= "2026-09-01")
           .group_by("city").agg(pl.col("amount").sum())
           .collect(engine="streaming"))

pdf = small.to_pandas(use_pyarrow_extension_array=True)  # 走 Arrow，不复制
# 只有在下游明确要 NumPy 语义时，才用默认的 to_pandas()

什么情况下不该换

三种情况下换工具是净亏损。第一，数据量小。几十万行以内、单次几秒钟跑完的活，两者的耗时差异被你读代码、查文档、改写逻辑的时间彻底盖住。这时切换成本是确定的支出，收益是零点几秒——这笔账怎么算都是亏。第二，团队与下游全在旧生态上。如果协作者读不懂表达式写法、下游脚本假定拿到的是带索引的对象、notebook 模板全按旧 API 写成，那么你引入的不是性能提升而是一道翻译层，每次交接都要付一次转换的代价和一次沟通的代价。第三，依赖只有旧生态才有的专门能力。围绕旧生态积累了十几年的专用库（统计建模、特定领域的时间序列工具、各种可视化封装）往往只接受旧生态的对象，硬换等于自己去补这些轮子。

这三条的共同点是：它们都不是技术能力问题，是总成本问题。换工具的收益只有在瓶颈真的落在第一节那三个差异上时才存在，而上面三种情况的瓶颈都在别处。

不要问「该用哪个」，问「这一步的数据有多大、下一步要拿它干什么」。前一个问题没有答案，后一个问题每次都有明确答案——而且答案会随着管道推进而变化，所以同一个项目里两个工具同时在用是正常状态，不是设计缺陷。

六、迁移与选型判据：从新写的管道开始

把前面五节收敛成可以直接用的判断。先是选型：按数据规模和场景查表，而不是按个人偏好。

场景建议理由
小数据交互式分析（十万行级，notebook 里探索）用手上顺的那个，通常是旧生态瓶颈是你的思考速度，不是执行速度；生态和肌肉记忆的价值更高
单机大数据批处理（千万到十亿行，装得进内存或接近）Polars 惰性模式，scan_* 进 collect() 出多线程 + 两种下推的收益最集中，且不必引入分布式框架
超过内存的数据（单机放不下）Polars 流式，scan_* 进 sink_* 出，并按第四节验证唯一能在单机上做完的路；前提是全链路真的流式
需要 SQL 接口（口径由分析师维护）Polars 的 SQL 入口，或直接用嵌入式分析数据库SQL 写的口径仍能吃到同一套优化器；纯 SQL 团队用嵌入式数据库可能更顺
规模已超单机（TB 级、需要多机）分布式方案，Polars 只做单机那一段单机引擎的上限终究是单机的内存带宽和磁盘
下游是统计建模 / 特定领域专用库Polars 做预处理，过桥后交给旧生态专用库只认旧生态的对象，硬换等于重写轮子

SQL 入口值得单独提一句

Polars 提供 SQL 接口（pl.SQLContext，以及惰性帧上的 sql 方法），SQL 写出来的查询同样会进优化器。这在团队里很实用：业务口径由熟 SQL 的人维护，管道的读取、流式配置、输出由工程侧维护，两边在同一个引擎里汇合。如果你的团队几乎只写 SQL，那也该老实评估一下嵌入式分析数据库——那条路上 SQL 是一等公民，可能比在 Python 里包一层更顺手。

ctx = pl.SQLContext(events=pl.scan_parquet("events/*.parquet"))
q = ctx.execute("""
    SELECT city, SUM(amount) AS gmv
    FROM events WHERE dt >= '2026-09-01' GROUP BY city
""")                       # 返回惰性帧，仍然可以 explain / sink
print(q.explain(engine="streaming"))

迁移策略：从新写的管道开始

迁移最常见的失败模式是「为了统一而重写」。某人换了工具觉得好，于是提议把仓库里所有数据处理代码都迁过来，包括那些跑了两年、每晚三分钟跑完、从没出过问题的脚本。这类重写的收益是零（它们本来就没有性能问题），风险却是实打实的：口径在重写中被改掉、边界情况被漏掉，而这些错误往往要到下个月的报表对不上时才暴露。

务实的顺序是三步。第一，新写的管道直接用新工具——没有历史包袱，学习成本落在本来就要花的开发时间里。第二，只迁真的有痛点的老管道：跑得太慢挡住了交付节奏，或者已经因为内存问题挂过。这时迁移有明确的验收标准（耗时、峰值内存），做完能说清收益。第三，迁移时保留一条对账通道：新旧两套并行跑一段时间，逐字段比对输出。前面提到的行序不保证问题，就是靠这种比对才能发现的——两套结果的集合一样但顺序不同，只看前几行完全看不出来。

  • 批处理默认写成 scan_* 进、sink_* 出，不要中途 collect() 落地
  • 性能问题先 explain()，确认两种下推都生效，再动代码
  • 要判断流式，用显式传 engine="streaming" 的计划，不要拿默认 explain() 当依据
  • 用 1／2／4 倍样本标定峰值内存，持平才算流式真的生效
  • 测试环境设一个明确低于生产的内存上限，让回退在 CI 里就炸
  • 把业务口径存成表达式变量复用，别在多处重复同一段计算
  • 依赖行序就显式 sort，或在支持的算子上传 maintain_order
  • 在 pyproject.toml 里锁定次版本，升级前读一遍升级指南
  • 因为「新工具更快」就把跑得好的老管道全部重写
  • 在小数据上换工具——切换成本远大于那零点几秒
  • 在惰性管道中间插自定义 Python 函数，那会挡住下推
  • 只在小样本上验证流式，就直接上全量数据
  • 默认 to_pandas() 处理还有几个 GB 的中间结果（内存翻倍）
  • 把「测试跑得快」当成流式生效的证据——小数据本来就不该走流式
  • 照抄博客里的 POLARS_* 环境变量名，不在自己版本上验证
  • 升级到 2.0 后不检查行序假设，就相信下游逻辑没受影响

最后回到第一节那个判断。这套东西真正给你的不是「更快」，而是一个把「要算什么」和「怎么算」分开的模型：你负责说清需求，引擎负责生成方案，而你要学的新技能只有一个——看方案。PY13 讲推导式与惰性时说过，惰性的价值在于把「描述」和「求值」解耦；Polars 是这条思路在表结构上的完整版本，代价也和那里一样：你得知道求值到底发生在哪一刻。

迁移的正确单位是「一条管道」，不是「一个仓库」。每条管道单独判断：它有痛点吗？痛点落在那三个结构性差异上吗？验收标准是什么？三个问题都有答案再动手，剩下的老代码就让它继续安静地跑。

Q&A

惰性模式和流式模式是一回事吗？
不是，是两层不同的东西。惰性说的是「什么时候执行」：你链式写下的变换不立刻跑，先攒成一棵查询计划，等 collect() 或 sink_* 触发才执行。它的收益是给优化器一个改写计划的窗口（谓词下推、投影下推等），和内存无关——一个惰性查询完全可以把全部数据拉进内存再算。流式说的是「怎么执行」：把计划编译成按批推进的流水线，一次只在内存里拿几批数据。所以关系是单向的：流式必须建立在惰性之上（引擎需要看到完整计划才能编排流水线），但惰性不一定流式。实际后果是，你可能写了一个完美的惰性查询、也看到优化器漂亮地下推了条件，结果它还是把所有数据都装进了内存——因为你没选流式引擎，或者选了但被某个算子挡了回去。
为什么我的流式查询还是把内存吃满了？
按概率从高到低查四件事。第一，管道里有算子没有流式实现，引擎静默回退到了 in-memory——这是最常见的原因，用显式传 engine="streaming" 的执行计划确认，别用默认的 explain()，它渲染的不是流式计划。第二，你用 collect() 收尾：即使中间环节都是流式的，collect() 的语义就是把最终结果全部装进内存，结果本身很大时照样 OOM，改成 sink_* 边算边写。第三，聚合状态本身很大：流式的内存优势建立在「聚合状态远小于输入」上，如果你按一个基数上亿的键分组，那个哈希表就是新的内存墙，这时要么先降基数，要么改成分区跑。第四，管道里插了自定义 Python 函数，它既挡住下推也可能要求物化。顺序上先查第一条，它的性价比远高于其它三条。
没有行索引，那原来用索引做的事怎么办？
拆成三类分别处理。按标签取行（loc 那类）改成显式过滤：把原来的索引留作一个普通列，然后 filter(pl.col("key") == ...)，写出来更长但意图更明确。自动对齐（两个对象相加时按索引配对）改成显式 join：这是收益最大的一项，因为原来的隐式对齐在索引有重复值或部分缺失时行为相当反直觉，显式 join 则强迫你回答「用什么键、哪种连接方式、对不上怎么办」这三个本来就该回答的问题。需要行号的场合用 with_row_index 造一列出来，但先想清楚是不是真的需要——很多时候「需要行号」只是旧写法的残留，业务上并不依赖它。习惯之后你会发现代码变长了一点，但「这一步到底在按什么对齐」永远能从代码上看出来。
为什么不该在惰性管道里插自定义 Python 函数？
三重代价叠在一起。第一重是优化器失明：它不知道你的函数会读哪些列、会不会依赖被过滤掉的行，只能保守地不把下推穿过这个节点——于是投影和谓词下推同时失效，扫描退回成读全表全列，而这往往是整个查询最大的那笔开销。第二重是并行退化：Python 回调要回到解释器执行，受全局解释器锁约束，引擎那套多线程执行在这一段变成串行。第三重是流式受阻：这类节点常常需要把上游结果物化才能逐行喂进去，于是触发第四节那个静默回退。实际的处理顺序是：先花时间找内置表达式的等价写法（覆盖面比大多数人以为的宽，字符串、时间、列表、结构体都有成套的方法），确实找不到再考虑写扩展；万不得已要用 Python 函数时，尽量把它挪到管道的最后一段——那时数据已经小了，三重代价的绝对值也小了。
行序不保证这件事，实际会怎么咬到我？
它的危险在于症状极晚出现。流式引擎对不需要顺序的算子（连接、分组、逆透视等）不保证输出行序，而你的测试很可能一直在无意中依赖「偶然有序」：比对输出时只看了前几行、断言用的是「第 0 行等于某值」、或者下游拿结果直接往有序的文件里追加。这些在 in-memory 引擎下能稳定通过，换到流式后集合仍然正确、顺序变了，于是断言时好时坏——甚至同一份数据两次运行结果的顺序都不同，因为顺序取决于线程调度。处理办法有两条：真的需要顺序就显式 sort（成本诚实地写在代码里），或者在支持的算子上传 maintain_order。更重要的是排查手段：比对两套实现的输出时，永远先按业务键排序再逐字段比，不要比文件的字节。
官方说流式引擎快好几倍，我能按这个数字做容量规划吗？
不能，两个理由。第一，那个数字是厂商在自己的基准集上、拿新引擎和自家旧引擎比出来的聚合结果，它回答的是「同一个库换引擎能好多少」，不是「换掉另一个库能好多少」，两件事被舆论经常混为一谈。第二，这类收益的方差极大，因为它主要来自「少读数据」而不是「算得更快」：过滤性强、列很多而你只取几列、文件按过滤键有序，这些条件凑齐时可能跳掉九成数据；反过来全表全列做一次聚合，该读的一个字节都省不掉，差距就退回到列式布局和多线程带来的那部分。所以容量规划只能用你自己的数据和查询实测：拿一份有代表性的样本，记录耗时和峰值内存，按规模做两三个点的标定再外推。任何从博客上抄来的倍数，在你的场景里都只是一个先验，不是预算依据。
什么时候该放弃单机、上分布式？
判据不是数据量的绝对值，是三个信号。第一，流式已经确认生效、也用了 sink_* 不落地，单次任务耗时仍然长到挡住交付节奏（比如日级任务跑不完一天）。第二，瓶颈已经从内存转到了 I/O 带宽或单机磁盘容量——数据连落盘都放不下，再优化计算也没用。第三，任务本身有天然的分片维度（按日期、按地区），拆开后各片之间无需交换数据。前两个信号说明单机到顶了，第三个信号说明拆开的代价低。要强调的是先做前两条确认：分布式引入的运维复杂度、调试难度、以及数据在节点间移动的成本都是长期负担，而很多「必须上分布式」的场景，实际上是单机管道里有一个没被发现的静默回退，或者一个本来可以下推却被 Python 回调挡住的过滤。先把单机这条路走到真正的尽头，再谈多机。
现在该装 1.x 还是 2.0？
写到本卡时（2026-09）稳定版是 1.44.1，2.0 还处在候选版阶段，没有发布日期。默认装到的是 1.x，要拿 2.0 得显式指定版本号。建议是生产继续锁在 1.x 的具体版本上，同时开一个分支装 2.0 候选版跑一遍测试——目的不是追新，是提前发现那批默认值变化会不会咬到你，其中最值得查的就是行序假设，因为它不会报错。另外提醒两点。一是依赖里写宽松的版本范围有风险：正式版发布的那天，你的构建会在你没选的时间点上换掉默认执行引擎。二是 Rust 侧的版本号是另一条线，「2.0」说的是 Python 包；如果你的系统里嵌的是 Rust 库，这次变更暂时和你无关。所有这些结论都会随时间失效，升级前请读当前版本的升级指南，而不是照抄本卡。
