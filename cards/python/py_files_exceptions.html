文件和异常是同一件事的两面：文件是操作系统借给你的资源，异常是「借出去的东西中途出了岔子」的通知机制。把「谁负责还」和「出错时还能不能还上」这两个问题答清楚，这一整块知识就立住了。

一、打开文件：模式与编码这两个参数决定一切

open() 看起来只是「拿到一个文件」，实际上它在一次调用里同时决定了四件事：文件不存在时新建还是报错、已有内容保留还是抹掉、你拿到的是文本还是字节、以及字节按哪张码表翻译成字符。这四件事全靠 mode 和 encoding 两个参数表达，而它们的默认值恰好都不是你想要的那个。

open() 返回的是一个文件对象——它不是文件内容，而是一个带「当前读写位置」的游标式句柄，你每次 read 或 write 都会让这个位置往后移动。这解释了一个常见困惑：连续两次 f.read()，第二次返回空字符串，因为第一次已经把游标推到了文件末尾。

模式矩阵：四个主模式 × 文本/二进制 × 可选的 +

模式字符串由三部分拼成。主模式只有 r（读）、w（写）、a（追加）、x（独占创建）四个，必选其一；t / b 决定文本还是二进制，不写默认是 t；+ 表示「在原有能力上再补一项」，把只读变成可读写、只写变成可读写。

模式文件不存在文件已存在能读能写起始位置
r（默认）抛 FileNotFoundError原样打开✓✗开头
w新建打开瞬间清空为 0 字节✗✓开头
a新建保留，写入一律追加到末尾✗✓末尾
x新建抛 FileExistsError✗✓开头
r+抛 FileNotFoundError原样打开✓✓（从头覆盖）开头
w+新建同样立即清空✓✓开头
a+新建保留✓✓（只能追加）末尾

整张表里最该记住的是 w 那一格：清空发生在 open() 返回之前，不是在你第一次 write 时。也就是说，只要这行代码执行了，哪怕下一行就抛异常、哪怕你一个字节都没写，原文件也已经变成 0 字节。这不是边缘情况，而是真实世界里最常见的一类数据丢失原因。

示例场景：一个配置同步脚本需要「读出旧配置、合并新字段、写回」，作者顺手把模式写成了 open("config.json", "w")，然后在下一行调用 f.read()。open() 执行的那一瞬间，2.3 MB 的配置被截断为 0 字节；f.read() 在只写句柄上抛出 io.UnsupportedOperation: not readable，脚本退出。因为这份配置不在版本控制里，4 套环境的配置只能靠人工比对重建，耗时约 3 小时。修复本身只需要把模式改成 r 读完关闭、再用 w 单独打开写回——两个阶段用两次 open，永远不要用一个句柄同时干读和写。

w 是「我不在乎里面原来有什么」的意思。当你其实在乎的时候，正确的模式是 a（追加）、x（不许覆盖）或者先 r 再 w。

文本模式和二进制模式：磁盘上其实只有字节

磁盘上不存在「字符」，只有字节。文本模式做的事情是在你和磁盘之间插了一层翻译：读的时候按 encoding 把字节解码成 str，写的时候反向编码；顺带还会按 newline 规则统一行尾。二进制模式不翻译，给你原始的 bytes。

encoding 不写会怎样：同一份代码在不同机器上行为不同

文本模式下不写 encoding，Python 不会默默用 UTF-8，而是去问操作系统的 locale 要一个「首选编码」。在绝大多数 Linux 和 macOS 上这个值是 UTF-8，所以作者本机一切正常；而在中文 Windows 上，它长期以来是 cp936（GBK）。于是同一行 open("data.json") 在两台机器上读到的是两份不同的字符串——甚至在一台上直接崩掉。

崩掉时的报错长这样：UnicodeDecodeError: 'gbk' codec can't decode byte 0xa5 in position 1023: illegal multibyte sequence。注意这条信息里有两个关键线索：codec 名字告诉你它没在用 UTF-8，position 告诉你出错的偏移量。初学者容易把它当成「文件坏了」，实际上文件完全正常，是解码用的码表选错了。

# ❌ 行为取决于运行它的那台机器的 locale
with open("data.json") as f: ...

# ✅ 行为在任何机器上都一样
with open("data.json", encoding="utf-8") as f: ...

# 明知数据源可能有脏字节时，显式声明容错策略
with open("legacy.log", encoding="utf-8", errors="replace") as f: ...

errors 参数是这里的第二个决策点，默认值 "strict"（遇到无法解码的字节就抛异常）在大多数场景是对的——你确实希望数据有问题时立刻知道。只有在处理来源不可控的历史日志时才改成 "replace"（把坏字节换成 � 继续）或 "ignore"（丢掉）。把 errors="ignore" 当成万能解药的代价是数据静默损坏，而且事后无法区分「原本就没有」和「被吞掉了」。

顺带说一句：输出侧的编码问题（打印中文时的 UnicodeEncodeError）和这里的输入侧问题成因不同，那属于终端编码不匹配，在 PY01 · Python 环境与解释器 里有一张对照表。

二、with 语句：为什么不能靠手工 close

「打开了就要关上」听起来是纪律问题，其实是机制问题。open() 拿到的不只是一个 Python 对象，背后还有一个文件描述符——操作系统分配给进程的一个小整数，用来索引内核里那张「这个进程打开了哪些文件」的表。这张表是有大小上限的，而且不会因为你的 Python 变量被垃圾回收就自动缩短。

不关文件带来的问题底层机制你会看到的现象
描述符耗尽每个进程可打开的描述符数有上限（Linux 上 ulimit -n 的常见默认值是 1024）OSError: [Errno 24] Too many open files
写入数据丢失write() 只写进用户态缓冲区，攒够一块才交给内核文件末尾被截断，内容比预期少
Windows 上文件被占用句柄未释放时系统保持文件锁PermissionError: [WinError 32] 另一个程序正在使用此文件
「反正会自动关」不可靠CPython 靠引用计数可能及时回收，但这是实现细节；异常回溯帧会持有引用，PyPy 更是延迟回收ResourceWarning: unclosed file（默认不显示）

最后一行值得展开。很多人的经验是「我从来不关文件也没出事」，这是因为 CPython 的引用计数常常恰好在函数返回时把文件对象回收掉、顺带触发关闭。但这是实现层的巧合，不是语言保证：一旦这个变量被异常的 traceback 引用、被闭包捕获、或者你换到 PyPy 上运行，回收时机就完全不同了。依赖巧合写出来的代码，会在换环境时突然开始泄漏。

三种写法在抛异常时的执行路径

知道要关之后，问题变成「怎么保证一定关得上」。直觉写法是在末尾补一行 f.close()，但这行代码只在前面的代码没有抛异常时才会被执行到——而文件处理恰恰是最容易抛异常的场景之一。

前提：do_work(f) 在处理到一半时抛出 ValueError ══════════════════════════════════════════════════════════ 写法 A —— 末尾补一行 close f = open(p) ① 拿到句柄，描述符已分配 do_work(f) ② 抛异常 ──┐ f.close() ③ 永不执行 │ 句柄泄漏 + 缓冲未落盘 └─► 异常继续向上抛 写法 B —— try / finally f = open(p) ① 拿到句柄（必须在 try 之外） try: do_work(f) ② 抛异常 ──┐ finally: │ f.close() ③ 一定执行 ◄┘ 句柄已释放 └─► 异常继续向上抛 正确，但每个资源要重复 4 行样板，且容易把 open 误写进 try 写法 C —— with with open(p) as f: ① 进入时获取 do_work(f) ② 抛异常 ──┐ ③ 退出钩子 ◄┘ 自动 close └─► 异常继续向上抛 语义与 B 完全等价，样板由语言承担 三者对「异常是否被吞掉」的处理是一致的： 都不吞。finally 和 with 只负责释放资源，不负责处理异常。 资源释放和错误处理是两件独立的事，别混在一起想。

with 背后的机制叫上下文管理器协议——一个对象只要实现了「进入时做什么」和「退出时做什么」这两个钩子，就能被 with 使用。协议的完整细节（包括怎么自己写一个、退出钩子如何选择是否压制异常）留到上下文管理器那一节（PY19）展开，这里只需要建立直觉：进入时获取，退出时无论正常结束、抛异常、还是 return，都保证释放。

这个抽象的价值在于它不只适用于文件。数据库连接、线程锁、临时目录、网络会话、性能计时器都遵循同一个「获取—使用—必须释放」的形状，所以它们在 Python 里全都长成 with 的样子。学会这一个语法，等于同时学会了半个标准库的资源管理方式。

# 一个 with 管多个资源，按从左到右获取、从右到左释放
with open("src.csv", encoding="utf-8") as src, \
     open("dst.csv", "w", encoding="utf-8") as dst:
    for line in src:
        dst.write(line.upper())
# 走到这里，两个文件都已关闭、缓冲都已落盘

注意上面这个写法和「嵌套两层 with」在语义上完全一样，只是少了一层缩进。另外别写成 with (open(a), open(b)): 这种带括号但没有 as 的形式——那是构造了一个元组，元组本身不是上下文管理器，文件也就不会被管理。

示例场景：一个报表服务在每次请求里打开 3 个文件（模板、数据、输出），代码用的是写法 A，末尾补 close()。平时正常，但模板缺失时会在中途抛 FileNotFoundError，那 3 个句柄就泄漏一次。该进程的 ulimit -n 是 1024，起始已占用约 30 个，于是在累计约 330 次失败请求之后，服务开始对所有请求抛 OSError: [Errno 24] Too many open files，包括原本正常的请求。现象极具误导性：报错指向的是随机的正常请求，真正的元凶是几小时前那批失败请求。改成 with 后，一行样板都不用加，泄漏彻底消失。

close() 写在末尾，等于把「一定要做的事」放在了「可能走不到的地方」。with 不是语法糖，它是把释放时机从「代码流程走到哪」改成了「作用域退出」这个必然事件。

三、读写的正确姿势：不要一次读进内存

文件对象提供了好几种读法，它们的语法差别很小，内存行为差别极大。read() 把整个文件变成一个字符串，readlines() 把整个文件变成一个字符串列表——这两个都是「先全部装进内存，再开始处理」。在你本机用 200 KB 的样例文件测试时毫无问题，在生产环境遇到 2 GB 的日志时会直接把进程打死。

正确的默认写法是直接对文件对象做迭代：for line in f。这利用了惰性迭代——只在你索取下一项时才去读，每次只在内存里保留当前这一行加一个固定大小的读缓冲区。文件有多大都不影响内存峰值。

写法返回什么内存峰值什么时候用
f.read()整个文件的一个 str/bytes≈ 文件大小确定是小文件（几 MB 以内），且需要整体处理，比如喂给 json.loads
f.read(n)最多 n 个字符/字节固定，约 n二进制分块拷贝、流式上传、计算大文件哈希
f.readline()一行（含行尾）一行需要手工控制推进节奏，比如先单独读掉 CSV 表头
f.readlines()list[str]≈ 文件大小 + 每行约 50 字节的对象开销文件很小且需要随机访问行号，否则基本没有理由用它
for line in f逐行惰性产出一行 + 一个读缓冲块（8 KB 量级）默认就用这个，除非有明确理由换

readlines() 那一行的「每行约 50 字节开销」不是笔误。Python 里每个 str 都是一个完整对象，带着类型指针、引用计数、长度、哈希缓存等头部信息；一个只有 12 个字符的短行，实际占用远超 12 字节。行数越多、每行越短，这个放大倍数越夸张。

示例场景：一个 1.8 GB、约 2000 万行的访问日志，平均每行 90 字节。用 lines = f.readlines() 处理时，内存不只是 1.8 GB：2000 万个 str 对象的头部开销约 1.0 GB，加上列表本身 2000 万个指针约 0.16 GB，实测常驻内存接近 3 GB，在一台 2 GB 内存限制的容器里直接被 OOM Killer 杀掉，日志里只留下一个 Killed，连 traceback 都没有。改成 for line in f 后，同一份文件的常驻内存稳定在 30 MB 以下，处理时间反而略有下降——因为不再需要为几千万个对象分配内存。这个改动是一行代码，收益是两个数量级。

判断标准很简单：如果文件大小可能随着业务增长而变大，就不要用 read() 或 readlines()。能流式处理的地方一律流式处理，这是唯一不会随数据量翻倍而崩掉的写法。

行尾那个换行符：rstrip 该怎么写

逐行迭代拿到的 line 自带行尾换行符，因为它是按分隔符切出来的，分隔符属于前一行。这会造成一类安静的 bug：if line == "END" 永远为假，因为实际值是 "END\n"；把行拼进路径会得到一个带换行的文件名，报错信息里看起来一切正常，因为换行符不可见。

for line in f:
    line = line.rstrip("\n")     # 只去行尾换行，最保守
    # line.rstrip()              # 会顺带吃掉行尾空格和 \t
    # line.strip()               # 连行首缩进一起吃掉
    if not line:                 # 跳过空行
        continue

三种写法都常见，但含义不同，选哪个取决于数据。处理 CSV 或缩进敏感的格式时用 rstrip("\n")；处理人手写的配置清单时用 strip() 反而更宽容。注意文本模式已经帮你把 Windows 的 \r\n 统一成了 \n，所以只写 rstrip("\n") 通常够用；但如果是二进制模式读的，就得自己处理 \r。

写入：两个方法都不帮你加换行

方法自动加换行接受什么要注意
f.write(s)不加单个 str（二进制模式下必须是 bytes）返回写入的字符数；不接受数字，f.write(1) 抛 TypeError
f.writelines(seq)也不加任何产出 str 的可迭代对象名字里有 lines 但完全不管行尾，每项必须自己带 \n
print(x, file=f)加（end 默认 "\n"）任意对象，自动调 str()写人类可读的文本时最省心，不用操心类型转换
f.flush()——把用户态缓冲交给内核；长跑进程写日志时需要，否则被 kill -9 时缓冲内容全丢

writelines 的命名是历史遗留，它和 readlines 并不对称：后者会把换行符保留在每一项里，所以 f2.writelines(f1.readlines()) 恰好能还原原文——这个巧合让很多人误以为 writelines 会加换行。真正的规则是：它只是循环调用 write，一个字符都不会替你补。想逐行写列表，用生成器表达式自己补上分隔符。

rows = ["alice,30", "bob,25", "carol,41"]

# ✅ 显式补换行，一次 I/O 调用
with open("out.csv", "w", encoding="utf-8") as f:
    f.writelines(row + "\n" for row in rows)

# ✅ 或者用 join，语义最清楚
#   f.write("\n".join(rows) + "\n")

四、路径处理：用 pathlib，别拼字符串

路径本质上是有结构的数据：它有分隔符、有层级、有扩展名、有「父目录」这种关系。把它当成普通字符串来拼接，等于扔掉了所有结构信息，然后靠手工维护那些规则。手工维护的第一个失手点就是分隔符：Windows 用 \，POSIX 用 /，而 \ 在 Python 字符串里还是转义字符的引导符，于是 "C:\data\new\test.txt" 里的 \n 和 \t 会被当成换行和制表符，路径直接变成一串乱码。

第二个失手点是重复和缺失的分隔符。base + "/" + name，当 base 本身以 / 结尾时得到 dir//name；当你为了避免这个而去掉，遇到不以 / 结尾的 base 就粘成了 dirname。这类代码最终总会演化成一堆 if path.endswith("/") 的判断——而这些判断 pathlib 早就替你写好了。

from pathlib import Path

# ❌ 分隔符、重复斜杠、转义全都要自己操心
p = base_dir + "/" + name + ".json"

# ✅ / 运算符被重载为「路径拼接」，跨平台自动正确
p = Path(base_dir) / f"{name}.json"

Path 对象把 / 运算符重载成了路径拼接，读起来像路径、写起来不用想分隔符。更重要的是它把路径的各个部分变成了可以直接取用的属性，而不是需要你用 split 和切片去猜的位置。

表达式对 Path("/data/2026/report.csv") 的结果说明
p.name'report.csv'最后一段，含扩展名
p.stem'report'去掉扩展名的文件名，改名时最常用
p.suffix'.csv'带点，判断时写 p.suffix == ".csv"
p.parentPath('/data/2026')父目录；p.parents[1] 是 /data
p.exists()True / False只表示「此刻存在」，不保证下一行还在（第六节会讲这个竞态）
p.with_suffix(".json")Path('/data/2026/report.json')换扩展名，不用切字符串
p.read_text(encoding="utf-8")整个文件的 str小文件一行读完，内部自带 with；大文件仍要用逐行迭代
p.parent.mkdir(parents=True, exist_ok=True)—写文件前建目录的标准写法，目录已存在也不报错

read_text() / write_text() 这对方法很适合小文件：它们内部已经用了 with，所以不会泄漏句柄。但注意 encoding 参数照样要显式写，否则和裸 open() 一样会跟着系统 locale 走。它们不适合大文件，因为语义上就是「全部读进内存」。

pathlib 不是「更好看的字符串拼接」，而是把路径从字符串升级成了有类型、有结构的对象。判断该不该用它的标准很简单：只要你打算对路径做 split、replace 或 endswith，就说明该换 Path 了。

相对路径的锚点是工作目录，不是脚本目录

这是文件操作里最反直觉的一条，也是「在 IDE 里点运行一切正常，同事在终端里跑就报 FileNotFoundError」的唯一根因。相对路径由操作系统在调用时解析，锚点是当前工作目录——进程启动时继承下来的那个目录，也就是 os.getcwd() 的返回值。它和脚本文件放在哪里毫无关系，只是在很多常见情形下碰巧相同。

项目结构 myproj/ ├── scripts/ │ └── report.py ← 脚本在这里 └── data/ └── input.csv ← 数据在这里 代码里写的是： open("data/input.csv") ← 相对路径 ┌──────────────────────────────────────────────────────────┐ │ 场景 1：在 IDE 里点「运行」 │ │ IDE 默认把工作目录设成项目根 → cwd = myproj/ │ │ 系统解析为 myproj/data/input.csv ✓ 跑通 │ ├──────────────────────────────────────────────────────────┤ │ 场景 2：终端里 cd scripts 然后 python report.py │ │ cwd = myproj/scripts/ │ │ 系统解析为 myproj/scripts/data/input.csv ✗ 不存在 │ │ FileNotFoundError: [Errno 2] No such file or │ │ directory: 'data/input.csv' │ ├──────────────────────────────────────────────────────────┤ │ 场景 3：cron / systemd / Docker 启动 │ │ cwd 往往是 / 或 用户家目录，几乎必错 │ └──────────────────────────────────────────────────────────┘ 两个目录的区别（在 report.py 里打印出来看） os.getcwd() ← 进程的工作目录，谁启动谁决定 Path(__file__).resolve() ← 脚本文件自己的绝对路径，固定不变 解法：把锚点钉死在脚本上，而不是留给调用者 BASE = Path(__file__).resolve().parent.parent # → myproj/ CSV = BASE / "data" / "input.csv" # 与 cwd 无关

Path(__file__).resolve().parent 这个惯用法值得逐段理解。__file__ 是模块级变量，值是当前文件的路径（可能是相对的）；.resolve() 把它变成绝对路径并解开符号链接；.parent 取到所在目录。三步下来得到一个不受调用方式影响的锚点，数据文件、模板、配置都从它出发定位。__file__ 这个变量的来历属于模块机制的一部分（在模块与包那一节，PY08），这里先当成固定写法用。

反过来说，命令行工具应该尊重工作目录：用户在哪个目录下敲 mytool data.csv，就该处理那个目录下的文件。所以规则不是「永远别用相对路径」，而是：程序自带的资源（模板、内置配置）用脚本锚点，用户传进来的路径按工作目录解析。分清这两类，路径问题就不会再来找你。

五、异常机制：层次结构与 try 的四个分支

异常在 Python 里不是一个特殊的语言构造，而是普通对象：FileNotFoundError 是一个类，抛出时创建它的实例，实例上带着消息、errno、filename 等属性。既然是类，它们就有继承关系，而 except 的匹配规则正是基于继承的 isinstance 判断——这一条把异常处理的大部分行为都解释清楚了。

这个继承关系构成了异常层次：所有异常的共同祖先是 BaseException，其下最重要的一支是 Exception，代表「程序运行出错」。刻意放在 Exception 之外的那几个，表示的不是错误而是控制流信号——用户按了 Ctrl+C、代码调了 sys.exit()。这个设计决定了 except Exception 的边界：它能接住几乎所有真正的错误，但接不住这些信号，而这正是你想要的。

BaseException ← except Exception 抓不到下面这三兄弟 ├── SystemExit sys.exit() 抛的；抓了会让退出失效 ├── KeyboardInterrupt Ctrl+C 抛的；抓了会让程序按不停 ├── GeneratorExit 生成器被关闭时抛的 │ └── Exception ← 「程序出错了」的根，日常都在这一支 ├── OSError 操作系统层面的失败（旧名 IOError） │ ├── FileNotFoundError Errno 2 文件/目录不存在 │ ├── PermissionError Errno 13 权限不足 │ ├── FileExistsError Errno 17 "x" 模式撞上已有文件 │ ├── IsADirectoryError Errno 21 把目录当文件打开 │ └── TimeoutError Errno 110 系统级超时 ├── ValueError 类型对但值不合法 │ └── UnicodeDecodeError ← 编码错误属于 ValueError 一支 ├── LookupError │ ├── KeyError 字典里没这个键 │ └── IndexError 序列越界 ├── TypeError 类型不对 ├── AttributeError 对象没这个属性 └── ArithmeticError └── ZeroDivisionError ───────────────────────────────────────────────────────────── except 的匹配 = 自上而下逐个做 isinstance，第一个命中就停 所以父类写在子类前面时，子类分支永远走不到（父类遮蔽子类） 正确顺序：具体的在前，宽泛的在后

这张图有三处值得单独记住。第一，文件相关的异常几乎都在 OSError 这一支下，所以想「统一处理所有文件问题」时写 except OSError 就够了，不必逐个列。第二，UnicodeDecodeError 挂在 ValueError 而不是 OSError 下面——它不是系统调用失败，是拿到字节之后解码失败的，所以 except OSError 抓不到编码错误。第三，父类遮蔽子类是个静默错误：代码能跑，只是某个分支永远不执行，没有任何警告。

# ❌ 第二个分支是死代码：FileNotFoundError 是 OSError 的子类
try:
    load()
except OSError: ...
except FileNotFoundError: ...     # 永远走不到

# ✅ 具体的写前面，宽泛的兜底
except FileNotFoundError: ...
except OSError: ...

except 就是一串 isinstance 检查，自上而下第一个命中就停。理解这一句，「为什么分支不生效」「为什么 except Exception 抓不住 Ctrl+C」这两个问题同时有了答案。

try 的四个分支：各自何时执行

try 语句有四个可选部分，但大多数人只用两个。剩下的 else 和 finally 不是装饰，它们解决的是一个真实的表达问题：怎么区分「可能出错的那一步」和「成功之后要做的事」。

分支什么时候执行应该放什么
try总是进入只放可能抛异常的那一两行。范围越窄，异常来源越明确
excepttry 内抛出且类型匹配时（未匹配则继续向上传播）你确实知道怎么应对的处理：降级、重试、给默认值、换路径
elsetry 正常执行完、一次异常都没抛时「成功后」的后续逻辑。放这里的代码抛的异常不会被本层 except 捕获
finally无条件执行：正常结束、抛异常、return、break 都会走释放资源、清理临时文件、埋点计时。不要在这里 return

else 的价值最容易被低估。没有它的时候，你只能把成功后的逻辑也塞进 try 里，于是 try 的范围膨胀，except FileNotFoundError 可能意外接住了后续代码抛出的同类异常，错误被归因到了完全错误的地方。有了 else，try 可以只包住那一行真正危险的操作。

try:
    f = open(path, encoding="utf-8")     # try 里只有这一行
except FileNotFoundError:
    cfg = DEFAULT_CONFIG                 # 没配置文件就用默认值
else:
    with f:                              # 只有打开成功才会走到这里
        cfg = json.load(f)
finally:
    log_duration()                       # 成功失败都要记耗时

finally 的「无条件执行」很彻底：连 return 都拦得住。正因如此，在 finally 里写 return 是个陷阱——它会丢弃正在传播的异常，把一个失败悄悄变成成功返回，这是最难排查的一类 bug 之一。finally 里只做清理，不改变控制流。

还有一点：finally 主要解决的正是第二节那个「保证释放」的问题，而 with 是它的高层封装。所以二者的关系是——with 能表达的场景优先用 with，剩下那些没有上下文管理器可用的清理动作（比如删临时文件、恢复全局状态）才手写 finally。

六、该抓什么、不该抓什么

学会 try/except 之后最容易走向的歧路，是把它当成「让报错消失的工具」。但异常的价值恰恰在于它会中断程序并留下现场：一个响亮的崩溃比一个静默的错误结果好得多，因为前者能在五分钟内定位，后者可能几个月后才在对账时被发现。

所以判断标准不是「这里会不会出错」，而是「出错时我知道该怎么办吗」。知道就抓——配置文件不存在就用默认值、网络超时就重试三次、缓存读失败就回源。不知道就别抓，让它往上传播，交给真正有决策能力的那一层（通常是程序入口或者框架的错误处理器）。

两个明确的反模式

第一个是裸 except:。它等价于 except BaseException:，也就是连 KeyboardInterrupt 和 SystemExit 一起接住。后果是很具体的：你的程序按 Ctrl+C 停不下来（信号被循环里的 except 吃掉了），或者 sys.exit(1) 失效、进程以退出码 0 结束，让 CI 误判成功。需要兜底时，写 except Exception:，差一个单词，边界完全不同。

第二个是 except Exception: pass。它在语法上合法、在语义上是「我知道这里可能出错，并且我决定不留任何痕迹」。故障发生时你会看到的是：结果少了几条数据、某个字段永远是空的、定时任务「成功」了但什么也没干——没有日志，没有 traceback，没有任何线索指向这几行代码。真正需要「忽略某个具体异常」时，至少要把范围收窄并留一行日志。

# ❌ 吞掉一切，包括 Ctrl+C；故障零痕迹
try:
    tmp.unlink()
except:
    pass
# ✅ 范围收窄到「确实可以忽略」的那一个，并留痕
try:
    tmp.unlink()
except FileNotFoundError:
    logger.debug("临时文件已不存在，跳过")

抓到之后：别把线索弄丢

抓住异常只是开始，怎么记录决定了事后能不能排查。这里最常见的损失是 traceback——print(e) 只会打印异常的消息文本，而消息往往是最没信息量的部分。真正告诉你「错在哪一行、经过了哪些调用」的是 traceback，而它只有特定的记录方式才会保留。

写法保留了什么丢掉了什么
print(e)仅消息文本，如 [Errno 2] No such file...异常类型名、traceback、原始 cause
print(repr(e))类型 + 消息traceback、cause 链
logger.error("失败: %s", e)消息 + 日志的时间/模块/级别上下文traceback
logger.exception("失败")消息 + 完整 traceback + __cause__ 链—
raise（裸重抛）全部，原样交给上层决策—

logging.exception() 必须在 except 块内部调用，因为它是从当前异常上下文里取 traceback 的。它等价于 logger.error(msg, exc_info=True)，级别固定为 ERROR。如果你想用别的级别记 traceback，就写 logger.warning(msg, exc_info=True)。

raise ... from e：保留因果链

包装异常是个好习惯——底层抛出的 KeyError: 'db_host' 对调用方毫无意义，换成 ConfigError("配置缺少 db_host") 才有用。但如果直接在 except 里 raise ConfigError(...)，原始异常的位置信息就会被埋在一段令人困惑的 "During handling of the above exception, another exception occurred" 里。from e 把关系明确成「因果」，输出变成 "The above exception was the direct cause of the following exception"，两层信息都清晰保留。

try:
    host = cfg["db_host"]
except KeyError as e:
    raise ConfigError("配置缺少 db_host") from e   # 保留因果链
    # raise ConfigError(...)          ← 因果关系变成「处理中又出错」
    # raise ConfigError(...) from None ← 刻意隐藏内部细节时才这么写

这里的异常链就是 Python 自动维护的 __cause__ / __context__ 属性，traceback 打印时会顺着链条把每一层都展开。一个习惯：跨层抛出时永远带上 from e，只有在异常信息涉及敏感内容、需要刻意对外遮蔽时才用 from None。

EAFP 比 LBYL 更地道，而且不只是风格问题

LBYL（Look Before You Leap，先检查再做）是先用 if 确认条件再操作；EAFP（Easier to Ask Forgiveness than Permission，先做再道歉）是直接操作、用 try 接住失败。Python 偏好后者，原因不只是代码更短。

关键在于 LBYL 在检查和操作之间留下了一个时间窗口。if path.exists(): 返回 True 的那一刻文件确实存在，但在下一行 open() 执行之前，文件可能已经被另一个进程删除、被日志轮转改名、被清理任务移走。这个窗口通常只有微秒级，所以本地测试永远测不出来，上线后在高并发下以极低概率出现——恰恰是最难复现的那类故障。EAFP 没有这个窗口，因为「检查」和「操作」在系统调用层面是同一个原子动作。

# ❌ LBYL：exists() 和 open() 之间存在竞态窗口
if path.exists():
    data = path.read_text(encoding="utf-8")

# ✅ EAFP：打开与检查是同一个原子操作，无窗口
try:
    data = path.read_text(encoding="utf-8")
except FileNotFoundError:
    data = ""

LBYL 仍有它的位置：当检查本身廉价、失败是常态而非例外，或者你需要在操作前做批量校验并给出汇总报告时，if 更直接。但涉及文件系统、网络、数据库这类外部状态可能随时变化的资源时，一律用 EAFP。

抓异常的门槛是「我有一个明确的应对动作」。如果 except 块里只能写 pass 或者一句日志然后继续，那大概率不该抓——让它崩，崩得越早越清楚。

  • 文本模式一律显式写 encoding="utf-8"，包括 read_text / write_text
  • 所有文件操作放进 with，一个 with 可管多个资源
  • 逐行处理默认用 for line in f，配 line.rstrip("\n")
  • 路径用 Path 和 / 运算符；程序自带资源以 Path(__file__).resolve().parent 为锚点
  • 兜底写 except Exception:，具体的 except 分支排在宽泛的前面
  • try 只包住真正危险的那一两行，成功后的逻辑放 else
  • 记录用 logger.exception()，跨层包装用 raise ... from e
  • 外部资源用 EAFP（直接做 + try），别用 exists() 预检
  • 用 "w" 打开只是想读——open() 那一刻文件就已经被清空了
  • 省略 encoding，让行为跟着机器的 locale 变
  • 末尾补 f.close() 当作已经关好了（中途抛异常就走不到）
  • 对可能变大的文件用 read() / readlines()
  • 以为 writelines 会帮你加换行符
  • 拼字符串造路径，或对路径做 split / endswith
  • 写裸 except:（连 Ctrl+C 一起吞）或 except Exception: pass
  • 用 print(e) 记录错误（丢掉 traceback），或在 finally 里 return

Q&A

open(path, "w") 到底什么时候清空文件？我还没写就已经没了？
清空发生在 open() 调用内部，在它返回文件对象之前。这是操作系统 O_TRUNC 标志的行为，Python 只是把它透传出来。所以只要这一行执行了，原文件就已经是 0 字节，哪怕你随后立刻抛异常、或者一个字节都没写。这也意味着 w 模式没有「反悔」的机会，没有回滚。如果你的意图是「读出来改一改再写回」，正确做法是分两个阶段：先用 r 模式读完并关闭，处理完数据后再用 w 模式打开写入。对重要文件还可以再稳一层：先写到同目录的临时文件，写成功后用 Path.replace() 原子替换，这样即使写入过程中崩溃，原文件也还是完整的。
为什么大家都说必须写 encoding="utf-8"？不写会有什么具体后果？
不写的话，文本模式会去问操作系统的 locale 要一个默认编码，这个值在不同系统上不一样：多数 Linux 和 macOS 是 UTF-8，而中文 Windows 长期以来是 cp936（GBK）。后果分两种。运气差的时候直接崩，报 UnicodeDecodeError: 'gbk' codec can't decode byte ...，看起来像文件坏了，其实是码表选错了。运气「好」的时候更麻烦：某些字节序列在 GBK 下恰好能解出合法但完全错误的汉字，程序不报错，只是数据变成乱码流进了下游，可能到很久之后才被发现。写上 encoding="utf-8" 就把这个变量固定下来了，同一份代码在任何机器上行为一致。Path.read_text() 和 write_text() 同样要写，它们的默认值规则和 open() 一样。
with 是不是只是 try/finally 的语法糖？两者有区别吗？
在文件这个场景下，二者的效果确实等价：都保证无论正常结束还是抛异常，资源都会被释放；也都不会吞掉异常，异常照样往上传播。但 with 不只是省了几行。首先它把「怎么释放」的知识从调用处移到了对象自己身上——你不需要知道这个资源该调 close() 还是 release() 还是 shutdown()，with 会调对的那个。其次它消掉了一类容易写错的样板：手写 try/finally 时如果把 open() 误放进 try 里面，open 自己失败时 finally 里的 f.close() 会抛 NameError，把真正的错误盖住。最后，这个协议是通用的，锁、连接、临时目录、事务都用同一个语法，学一次到处适用。
处理一个 10 GB 的日志文件，具体该怎么写？
用 for line in f 逐行迭代，这是唯一不随文件增大而涨内存的写法。它的内存占用是「当前这一行 + 一个 8 KB 量级的读缓冲」，10 GB 和 10 MB 的文件表现完全一样。绝对不要用 read()（整个文件变成一个字符串）或 readlines()（整个文件变成一个列表，还要额外付每行约 50 字节的对象开销）。如果需要做聚合统计，在循环里累加计数器而不是先攒成列表；如果需要筛选出子集，用生成器把「读取、过滤、处理」串成流水线，任何一环都不要落地成完整列表。二进制文件（比如算哈希、做拷贝）用 f.read(65536) 分块读，配合 while 循环或 iter(functools.partial(f.read, 65536), b"")。判断依据只有一条：只要文件大小可能随业务增长，就必须流式处理。
为什么代码在 IDE 里能跑，在终端里就报 FileNotFoundError？
因为代码里用了相对路径，而相对路径的锚点是进程的当前工作目录，不是脚本文件所在的目录。IDE 点「运行」时通常把工作目录设成项目根目录，所以 open("data/input.csv") 解析到项目根下的 data/，正好命中；你在终端里 cd 到别的目录再执行同一个脚本，工作目录变了，同一个相对路径就解析到别处去了。cron、systemd、Docker 启动时工作目录常常是 / 或用户家目录，几乎必错。确诊方法是在脚本里打印 os.getcwd() 和 Path(__file__).resolve()，一眼就能看出两者不同。解法是给程序自带的资源钉一个固定锚点：BASE = Path(__file__).resolve().parent，然后所有内部路径都从 BASE 出发拼。注意用户从命令行传进来的路径应该反过来，按工作目录解析才符合直觉。
except Exception 和裸 except: 差在哪？为什么后者是反模式？
裸 except: 等价于 except BaseException:，会连 KeyboardInterrupt、SystemExit、GeneratorExit 一起接住，而这三个在设计上根本不是「错误」，是控制流信号。具体后果很好观察：程序进了一个带裸 except 的循环之后，按 Ctrl+C 停不下来，因为 KeyboardInterrupt 每次都被吃掉；或者你在某处调 sys.exit(1) 表示失败，异常被吞，进程最终以退出码 0 结束，CI 把一次失败当成了成功。except Exception: 只接 Exception 那一支，也就是所有真正的程序错误，同时让信号顺利穿过去。所以需要兜底时写 except Exception:，两者只差一个单词，语义边界完全不同。顺带一提，兜底块里至少要有一行 logger.exception()，否则就退化成了另一个反模式。
try/except/else/finally 里的 else 有什么用？不是多余的吗？
不多余，它解决的是「try 范围膨胀」这个具体问题。没有 else 时，成功之后的逻辑只能一起塞进 try，于是 try 包住了一大段代码；一旦后续代码抛出了和你捕获的类型相同的异常（比如你在接 KeyError，而后面的业务逻辑也会抛 KeyError），它会被同一个 except 接住，错误被归因到完全错误的地方，而且不留痕迹。else 让你把 try 收窄到真正危险的那一两行，成功后的逻辑放进 else——放在这里的代码抛的异常不会被本层的 except 捕获，这正是我们想要的隔离。判断标准：try 超过三行就该考虑是不是有东西该挪进 else。
为什么 Python 提倡 EAFP（先做再道歉）而不是 LBYL（先检查再做）？
主要不是风格问题，是正确性问题。LBYL 在「检查」和「操作」之间留下了一个时间窗口，而外部资源的状态随时可能在这个窗口里改变：path.exists() 返回 True 之后、open() 执行之前，文件可能被另一个进程删掉、被日志轮转改名、被清理任务移走。这个窗口通常只有微秒级，所以本地测试永远测不出来，上线后在高并发下以极低概率触发，是最难复现的一类故障（这类问题有个专门名字叫 TOCTOU，检查与使用之间的竞态）。EAFP 直接执行操作、用 try 接住失败，检查和操作在系统调用层面是同一个原子动作，没有窗口。次要的好处是它对「鸭子类型」更友好：与其检查对象有没有某个属性，不如直接调用、接住 AttributeError。LBYL 也不是一律不用——检查廉价、失败是常态、或者需要批量预校验给出汇总报告时它更直接；但只要涉及文件系统、网络、数据库，一律用 EAFP。
