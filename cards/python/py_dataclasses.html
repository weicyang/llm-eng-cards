PY21 · 数据类三选一

dataclass / pydantic / attrs 的分工 · 自动生成了什么方法 · 为什么注解不等于校验 · 边界校验与内层不可变的分层写法

这三个库不是「同一件事的三种写法」，而是三个不同的问题：dataclass 省样板，pydantic 守边界，attrs 给你更细的控制。选错的代价不是难看，是把校验放到了错误的层，错误在离现场很远的地方才炸出来。

一、数据载体类的样板问题

先看一个再普通不过的需求：表示一笔订单。它只有数据，没有行为——四个字段，需要能打印出来看、能相互比较、能放进集合去重。用最朴素的写法，你得亲手写三个方法。

class Order:
    def __init__(self, oid, items, total, paid=False):
        self.oid, self.items = oid, items
        self.total, self.paid = total, paid

    def __repr__(self):
        return (f"Order(oid={self.oid!r}, items={self.items!r}, "
                f"total={self.total!r}, paid={self.paid!r})")

这还没写 __eq__。真写完，四个字段要换来大约三十行代码，其中没有一行表达业务，全是样板代码——即由字段定义可以机械推导出来、写与不写没有信息量差别的代码。PY15 · 类与特殊方法契约 讲过这些方法各自的约定，这里的问题不是「不会写」，而是「写了四遍同样的字段名」。

真正的代价不是长度，是四处同步

长只是难看，可维护性才是要命的。给 Order 加一个 coupon 字段，你要改四个地方：__init__ 的参数列表、__init__ 的赋值、__repr__ 的格式串、__eq__ 的比较元组。前三处漏了会立刻暴露（少个属性、打印不全），第四处漏了不会——代码照跑，只是两个优惠券不同的订单从此被判为相等。

这个 bug 的表现是什么？去重时少了一条记录；缓存里命中了不该命中的条目；测试断言 assert a == b 通过了但两个对象其实不一样。等你发现时，现场早已不在改字段的那次提交里。

手写 __eq__ 的危险不在于写错，在于忘记改。漏掉一个字段不会报错，只会让两个不同的对象从此相等——这是最难查的一类 bug。

一次声明，生成一组方法

所有数据类方案——这里指「由字段声明自动生成特殊方法的类」——做的都是同一件事：把字段当作唯一真相来源，其余方法由它推导。加一个字段，四个方法自动跟着变，同步问题从根上消失。

一次字段声明 自动生成的方法 ──────────── ──────────── @dataclass class Order: ┌───► __init__(self, oid, items, total, paid=False) oid: str ──────────► ┤ 参数顺序 = 字段声明顺序 items: list[str] ──────────► ┼───► __repr__(self) total: float ──────────► ┤ Order(oid='A1', items=['x'], total=9.9, paid=False) paid: bool = False ──────────► └───► __eq__(self, other) 比较 (oid, items, total, paid) 这个元组 开关决定「还生成哪几组」 order=True ──────────────────► __lt__ __le__ __gt__ __ge__ frozen=True ──────────────────► __setattr__ 拦截 + __hash__ slots=True ──────────────────► __slots__ = ('oid','items','total','paid') 加一个 coupon 字段 ⇒ 上面这些方法全部自动跟着变，没有第二处要改

三个库都建立在这个模型上，区别在于「声明」里还能塞进多少信息，以及实例化那一刻还额外做了什么。

方案来源解决的核心问题实例化时做什么典型位置
dataclass标准库 dataclasses消除样板只赋值，不检查内部数据结构、值对象
pydantic第三方外部数据的校验与转换强制校验并转换类型系统边界：请求体、配置、外部 JSON
attrs第三方更强的字段控制与校验器按你声明的校验器/转换器执行需要复杂校验但不需要序列化

这张表里最该记住的是第四列。「实例化时做什么」才是三者的真正分界线，其余差异都是从这里派生出来的：不检查所以最快，强制校验所以最慢，可配置所以最灵活。

二、dataclass：标准库的答案

@dataclass 是一个类装饰器（机制见 PY14 · 可变参数、闭包与装饰器），它在类创建时读取 __annotations__，把每个带注解的类属性当作一个字段，然后按字段列表生成方法并挂回类上。整个过程发生在类定义时，运行期不再有额外开销——这一点是它性能表现的根源。

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Order:
    oid: str
    items: list[str] = field(default_factory=list)
    total: float = 0.0
    paid: bool = False

六行代码换来了 __init__、__repr__、__eq__、__hash__，外加不可变保证和更省内存的 __slots__。

@dataclass 是一台代码生成器，不是一个基类。它在类定义那一刻把方法写好挂上去，之后你的类就是个普通的类，运行期没有任何魔法在跑。

参数速查

参数默认生成 / 改变什么什么时候开
initTrue__init__几乎总是开着；自己要写构造逻辑时才关
reprTrue__repr__总是开着，日志和调试全靠它
eqTrue__eq__（按字段元组比较）总是开着；关掉会退回按身份比较
orderFalse__lt__ __le__ __gt__ __ge__需要排序或取 min/max 时
frozenFalse赋值时抛 FrozenInstanceError，并生成 __hash__值对象、配置对象：默认就该开
slotsFalse__slots__，去掉实例 __dict__3.10+；要创建几十万个实例时
kw_onlyFalse所有字段强制关键字传参3.10+；字段多、或被默认值顺序卡住时

frozen=True 值得单独说。它做两件事：拦截 __setattr__ 让实例不可变，同时自动提供 __hash__。PY09 · 对象模型与引用语义 讲过可变对象作为字典键的危险——一个可变的 Order 放进 set 后改了字段，哈希桶就对不上了，这条记录会变成「存在但查不到」。frozen=True 从源头堵死这条路，所以配置对象和值对象（只靠字段值确定身份、没有独立生命周期的对象）应该默认开着它。

kw_only 解决的那个真实别扭

没有 kw_only 时，Python 的规则是「有默认值的字段必须排在没默认值的字段后面」——这是函数默认参数规则的直接继承。于是基类定义了一个带默认值的字段，子类再想加一个必填字段就会直接报 TypeError: non-default argument follows default argument。这个限制经常逼得人把字段顺序排成不符合语义的样子。

@dataclass(kw_only=True)
class Job:
    retries: int = 3      # 有默认值的可以排前面
    name: str             # 必填的排后面也没问题
    timeout: float = 30.0

Job(name="sync", timeout=5.0)   # 只能关键字传参

代价是调用点必须写全参数名。对字段超过四五个的类，这反而是好事：Job("sync", 3, 5.0) 这种调用读起来全是谜题，位置一错还不报错。

可变默认值：标准库帮你挡了经典坑

PY05 · 函数入门与参数传递 讲过函数默认参数只求值一次导致的共享陷阱。数据类里同样的写法更危险——所有实例会共享同一个列表，一个实例 append 之后另一个实例也跟着变。dataclasses 的处理很硬气：直接在类定义时就报错。

@dataclass
class Bad:
    items: list = []      # ValueError: mutable default
                          # <class 'list'> for field items
                          # 类定义时就抛，不等到运行

@dataclass
class Good:
    items: list = field(default_factory=list)   # 每个实例各自新建

默认工厂（default_factory）是一个零参可调用对象，在每次构造实例时被调用一次，返回该实例专属的默认值。注意报错时机：它发生在模块导入阶段，而不是运行到某一行时。这是标准库难得的一次主动拦截——把一个经典的隐性 bug 变成了一个显性的启动失败。

__post_init__：派生字段与轻量校验

生成的 __init__ 会在赋值完所有字段后调用 __post_init__（如果你定义了的话）。它的正当用途是算派生字段，以及做一点点断言式的合法性检查。

@dataclass
class Range:
    lo: float
    hi: float
    span: float = field(init=False)   # 不进 __init__ 参数

    def __post_init__(self):
        if self.lo > self.hi:
            raise ValueError(f"lo={self.lo} 不能大于 hi={self.hi}")
        self.span = self.hi - self.lo

注意 field(init=False)：这个字段不出现在构造参数里，但仍然参与 __repr__ 和 __eq__。还有一个容易忘的细节——frozen=True 的类里不能直接在 __post_init__ 中赋值，得用 object.__setattr__ 绕过拦截，这是不可变性的必然代价。

三、关键澄清：dataclass 不做类型校验

这是整张卡片最重要的一节，也是新手对数据类最普遍的误解：以为写了 x: int 就有人替你检查 x 是不是 int。

@dataclass
class Point:
    x: int
    y: int

p = Point(x="abc", y=[1, 2])
print(p)        # Point(x='abc', y=[1, 2])   完全合法，零警告

没有异常，没有警告，p.x 就是字符串 "abc"。原因在 PY17 那张类型注解的卡片里已经铺垫过：注解是元数据，不是断言。CPython 把它收进 __annotations__ 字典就完事了，运行期谁都不会去读它做检查。mypy 这类静态检查器会读，但那是写代码时的事，跟运行期没有半点关系——而外部数据恰恰只在运行期才出现。

x: int 是写给人和静态检查器看的一句话，不是运行期的一道门。数据从外面进来时，这句话拦不住任何东西。

误解的真正代价：错误延迟暴露

如果坏数据在进门时就炸，问题其实不大——栈顶就是现场，改完走人。麻烦在于它不炸，而是继续往下走，在离入口很远的地方以一个看不懂的形式出现。

① 外部输入 ② 构造实例 ③ 一路向下流 ────────── ────────── ────────────── API 返回的 JSON {"sku":"A1","qty":"3"} ──► Item(sku="A1", qty="3") ──► 存进列表 ↑ ↑ ──► 写入数据库 qty 是字符串 注解写着 qty: int ──► 进入日均统计 （对面改了个字段类型） 但没有任何检查发生 ──► 汇总进周报 ──► 推给 BI 看板 错误在 ① 产生 ─────────────────────────────────────► 在 ⑤ 之后才被人看见 沿途可能发生的三种情况，没有一种会立刻告诉你根因： sum(qty) → TypeError，栈顶在统计函数里，看不出是 API 变了 qty * 2 → 得到 "33"，静默算错，永远不报错 ← 最坏的一种 写库 → 驱动隐式转换或存成字符串，坏数据落盘持久化

第二种情况最该警惕。字符串支持 * 和 +，所以「数量乘以单价」「数量累加」这类操作可能一路不报错地算出一个假数字。你得到的是一份看起来完全正常、只是数值不对的报表。

示例场景：某内部结算服务用 dataclass 直接承接上游 API 的 JSON。上游把 qty 字段从数字改成了字符串形式的数字（3 → "3"），双方都没察觉。累加逻辑写的是 total = total + item.qty，初值恰好也是从第一条记录取的，于是 "3" + "5" + "2" 拼成了 "352"，全程零异常。问题在 5 天后财务对账时才浮出水面：报表里某个品类的销量比实际高出近百倍。定位耗时约 6 小时，其中 5 个多小时花在「统计逻辑没问题啊」上，真正的修改只有一行——在入口处把 dataclass 换成带校验的模型。如果入口就校验，这个问题在上游改动后的第一个请求里就会以「qty 字段应为整数，实际收到 str」的形式报出来。

把误解摆到一起看

常见误解实际行为后果
写了 x: int 就不会传进字符串注解只进 __annotations__，运行期无人读取坏数据静默进入领域模型
mypy 过了就等于运行期安全静态检查只覆盖代码内部；外部 JSON 一律是 Any边界处的类型完全不受保护
__post_init__ 可以当校验层用能做轻量断言，但要逐字段手写字段一多就退化成一堆 if，仍会漏
出错了总会抛异常字符串支持 + *，算术可能静默得出错误结果不报错、但数值错，最难发现

要强调的是：这不是 dataclass 的缺陷。它的定位就是「省样板」，不校验才换来了接近手写类的速度。问题出在把它放错了位置——放到了系统边界上。

四、pydantic：把校验放在边界上

pydantic 补上的正是上一节缺的那道门。它的模型在实例化那一刻按注解逐字段校验，不匹配就转换，转换不了就抛出结构化的错误。同样一份声明，行为完全不同。

from pydantic import BaseModel

class Point(BaseModel):
    x: int
    y: int

Point(x="3", y=4)      # x 被转成整数 3，通过
Point(x="abc", y=4)    # ValidationError：明确指出是 x 字段，
                       # 以及「不是合法整数」这个原因

抛出的 ValidationError 不是一句模糊的文本，而是一个可遍历的错误列表：每一项都带着字段路径（嵌套模型下形如 user.address.zipcode）、错误类型、以及收到的实际值。这意味着你可以直接把它转成 HTTP 400 的响应体，告诉调用方到底哪个字段错了。

pydantic 的价值不是「更严格」，是把错误的暴露点从下游拉回到入口。同一个 bug，在入口炸是一条清晰的错误信息，在下游炸是一场排查。

它该待在哪儿

把它放在系统边界——即你的代码与外部世界之间那条线。边界之外的数据你无法控制，任何假设都可能被打破。

┌──────────────── 外部世界（不可控） ────────────────┐ │ HTTP 请求体 配置文件 大模型返回的 JSON 第三方 API 响应 │ └───────┬────────────┬────────────┬────────────────┬────────┘ ▼ ▼ ▼ ▼ ╔══════════════════════════════════════════════════════════╗ ║ pydantic 模型 ── 唯一的校验点 ║ ║ 类型转换 + 范围/长度/正则约束 + 自定义校验器 ║ ║ 失败 ⇒ ValidationError（字段路径 + 原因 + 实际值） ║ ╚══════════════════════════════════╤═══════════════════════╝ ▼ 校验通过后转成内部类型 ┌──────────────────────────────────────────────────────────┐ │ 内层：frozen dataclass ── 一律假定数据已合法 │ │ 不再重复校验，也不把外部库的类型带进领域模型 │ └──────────────────────────────────────────────────────────┘ 规则：数据穿过边界时校验一次；进来之后就是可信的

大模型返回的 JSON 是这条规则近年最典型的应用场景。模型被要求输出固定结构，但它不保证每次都照做——可能少字段、多字段、把数字写成字符串、或者在 JSON 外面裹一层解释文字。这类输出必须当成彻头彻尾的外部数据处理，用模型校验一次再往下走。

约束、嵌套与序列化

from pydantic import BaseModel, Field, field_validator

class Item(BaseModel):
    sku: str = Field(pattern=r"^[A-Z]{2}\d{4}$")
    qty: int = Field(ge=1, le=999)      # 1 到 999

    @field_validator("sku")
    @classmethod
    def upper(cls, v: str) -> str:
        return v.upper()

Field 负责声明式约束：数值范围、字符串长度、正则。field_validator 负责声明不了的规则，比如「订单结束时间必须晚于开始时间」这种跨字段逻辑。模型可以嵌套——一个 Order 里放一个 list[Item]，校验会递归下去，错误路径也会带上索引，形如 items.2.qty。

另外两个能力常被低估：model_dump() / model_dump_json() 把模型转回字典或 JSON（可以指定排除某些字段），以及自动导出 JSON Schema——一份描述数据结构的标准格式文档。后者的实际价值在于，它能直接喂给前端做表单生成、喂给 API 文档工具、或者作为约束条件传给大模型的结构化输出接口。这是 dataclass 和 attrs 都不提供的一整块能力。

代价：实例化开销

校验不是免费的。dataclass 的 __init__ 只是一串赋值语句，pydantic 的每次实例化都要走一遍校验管线。当前主流版本把核心逻辑下沉到了 Rust 实现，比早期版本快了很多，但和「纯赋值」之间仍然是数量级的差距。

维度dataclasspydantic
实例化时做的事逐字段赋值校验 + 类型转换 + 构造
相对开销基准，接近手写类明显更高，量级差距
类型保证无运行期强制
错误信息要自己写结构化，带字段路径与实际值
序列化 / JSON Schema只有 asdict()完整支持
依赖标准库第三方
合适的位置内层、热路径、值对象边界、配置、外部数据入口

「量级差距」在什么时候才要紧？取决于你创建多少个实例。一个 HTTP 请求校验一次请求体，这点开销淹没在网络耗时里，完全不必在意。但在一个循环里为百万行 CSV 每行造一个模型，它就会变成主要瓶颈——这时正确的做法不是放弃校验，而是整批校验一次（用一个包含 list[Item] 的模型），再把结果转成内层的 dataclass 参与计算。

示例场景：某配置加载模块原先用 dataclass 接住 YAML，合法性检查散落在七八个调用点的 if 里，还有几项根本没检查。线上事故的典型形态是：超时参数被写成字符串 "30s"，服务正常启动，直到两小时后第一次触发超时逻辑才抛出 TypeError，定位平均要 40 分钟以上——因为报错位置在超时处理代码里，跟配置文件毫无表面关联。改成 pydantic 模型后，同类问题在进程启动的头几毫秒就以「timeout_sec 字段应为数字，实际收到 '30s'」的形式失败，定位时间降到接近于零，服务也不会带着坏配置跑起来。同时删掉了散落各处的 20 多行校验 if。

五、attrs：能力最全的第三方选项

顺序上得先说清楚：attrs 比 dataclasses 早。标准库的数据类很大程度上是 attrs 的一个精简子集被官方吸收的结果——PEP 557 的设计讨论里就明确提到了这层渊源。所以两者的形状高度相似，差别在 attrs 保留了那些没被收进标准库的部分。

from attrs import define, field

@define(frozen=True)
class Port:
    number: int = field(converter=int)      # 先转换

    @number.validator
    def _check(self, attr, value):          # 再校验
        if not 1 <= value <= 65535:
            raise ValueError(f"端口越界: {value}")

两个关键词。转换器（converter）在赋值前把值转成目标形式，"8080" 进来变成 8080；校验器（validator）在转换后检查合法性。顺序固定是先转换后校验，这让「宽进严出」的处理变得自然。

attrs 站在 dataclass 和 pydantic 中间：比标准库能干，比 pydantic 轻——它给你校验，但不强塞一整套序列化和 Schema 体系。

它比 dataclass 多出来的部分

除了校验器与转换器，还有几处值得知道。字段控制更细：可以单独指定某个字段不参与 __eq__ 或 __repr__（比如密码、超长的二进制内容）、指定比较时先做变换（大小写不敏感的字段名比较）。slots 支持更成熟：@define 默认就开着 slots=True，而且处理好了继承、cached_property 等一系列边角情况——标准库的 slots=True 是 3.10 才加的，早期版本里遇到这些场景会有意外。此外它还有 __attrs_pre_init__ 这类更细的钩子，以及 attrs.evolve() 这种「基于旧实例改几个字段生成新实例」的不可变友好操作。

代价与三者能力矩阵

attrs 的代价很直白：多一个依赖，团队要多学一套 API（而且它有 @define 的现代接口和 @attr.s 的老接口两套写法，容易在老代码里撞见后者而困惑）。当标准库已经够用时，引入它换来的边际收益不足以抵消这份认知成本。

六、选型决策与混用策略

把前面五节压缩成一条可执行的判断路径，只需要问两个问题：数据从哪来，以及要不要出去。

我要定义一个数据载体类 │ 数据是从系统外部来的吗？ （HTTP / 配置 / 大模型 / 三方 API） ┌────────────┴────────────┐ 是 否 │ │ ▼ ▼ ┌─────────────┐ 需要复杂校验或类型转换吗？ │ pydantic │ ┌────────┴────────┐ │ 在边界校验 │ 是 否 └─────────────┘ │ │ │ ▼ ▼ 还要导出 Schema ┌──────────┐ ┌─────────────┐ 或做序列化？ │ attrs │ │ dataclass │ 是 ⇒ 留在 pydantic │ 校验器 │ │ frozen=True │ 否 ⇒ 转成内层 dataclass │ 转换器 │ │ 默认选它 │ └──────────┘ └─────────────┘ 一句话版本：外部数据 ⇒ pydantic；内部数据 ⇒ dataclass； 夹在中间、要校验但不要序列化 ⇒ attrs

注意默认值是 dataclass。绝大多数类根本不接触外部数据，用标准库就够了，不需要为它引入依赖。

选型的问题从来不是「哪个更强」，而是「这个类站在边界的哪一侧」。边界之外的数据不可信，边界之内的数据已经被验过一次——两侧的需求本来就不一样。

真实项目的答案往往是「都用」

三选一是个简化的说法。稍有规模的项目里，典型形态是分层混用：边界一层用 pydantic 校验，紧接着转成内层的 frozen dataclass，业务逻辑只跟后者打交道。

请求进来 │ ▼ ┌──────────────────────────────────────────────┐ │ 边界层 class CreateOrderReq(BaseModel) │ ← pydantic │ 校验失败 ⇒ 直接 400，带字段路径 │ └────────────────────┬─────────────────────────┘ │ to_domain()：一次显式转换 ▼ ┌──────────────────────────────────────────────┐ │ 领域层 @dataclass(frozen=True, slots=True)│ ← 标准库 │ class Order │ │ 已校验、不可变、零依赖、创建成本极低 │ └────────────────────┬─────────────────────────┘ │ 内层随便传、随便建实例 ┌────────────┼────────────┐ ▼ ▼ ▼ 定价计算 库存扣减 审计日志 （不再校验，也不 import pydantic） 出站时再走一次反向转换：领域对象 ⇒ 响应模型 ⇒ JSON

为什么值得多写这一层转换？三个理由。一是性能，内层可能创建成千上万个实例，不该每次都付校验成本。二是依赖方向，领域模型不 import 任何第三方库，将来换掉边界框架时业务代码一行不动。三是语义清晰：看到一个 pydantic 模型就知道「这是外部数据」，看到 frozen dataclass 就知道「这是已验证的内部事实」，类型本身在传递信息。

两条容易越过的界线

第一条，不可变应该是默认而不是例外。配置对象、值对象、任何要进 set 或当字典键的对象，一律 frozen=True。PY10 · 拷贝语义与共享状态陷阱 讲过共享可变状态的传播问题：一个可变对象被传进三个函数，其中一个悄悄改了它，另外两个的行为就变了，而调用点看不出任何线索。冻结把这类问题变成立即抛出的 FrozenInstanceError。需要改的时候用 dataclasses.replace() 生成新实例，语义比原地修改清楚得多。

第二条，数据类不该长出复杂业务方法。数据类的职责是「持有一组值并保证它们的相等性、可打印性、不可变性」。往里塞「从数据库加载」「发送通知」「调用支付网关」这类方法，等于把 IO 和外部依赖焊进了本该最容易构造、最容易测试的对象上——之后每写一个单元测试都要先 mock 一堆东西。判断标准很简单：这个方法只用到自己的字段吗？是就可以留下（比如 Range.contains(x)），不是就该搬到服务层或独立函数里。

  • 默认用标准库 dataclass，只在有明确理由时才引入第三方
  • 所有外部数据（HTTP 体、配置、大模型 JSON、三方响应）在入口用 pydantic 校验
  • 值对象和配置对象一律 frozen=True，要改用 dataclasses.replace()
  • 可变默认值一律写 field(default_factory=...)
  • 字段超过四五个时开 kw_only=True，让调用点自解释
  • 边界模型与领域模型分开，中间放一次显式转换
  • 要创建海量实例时开 slots=True 省内存
  • 以为 x: int 在 dataclass 里有运行期约束力
  • 把外部 JSON 直接灌进 dataclass，让坏数据静默流向下游
  • 在内层热路径上大批量创建 pydantic 模型
  • 写 items: list = []（这行会在类定义时直接报错）
  • 让 pydantic 的类型渗透到领域模型和核心业务函数签名里
  • 往数据类里塞数据库访问、网络调用这类带 IO 的业务方法
  • 为了「统一」把三个库混在同一层，看不出哪个类站在边界上

把这张卡片压成一句话：边界校验一次，内层不可变。边界用 pydantic 把不可信数据挡在外面，内层用 frozen dataclass 承载已经可信的事实，中间那次显式转换就是两个世界的分界线。

Q&A

dataclass 里写了 x: int，为什么传字符串一点反应都没有？
因为注解在 CPython 里只是元数据，被收进类的 __annotations__ 字典就结束了，运行期没有任何代码去读它做检查。@dataclass 读取这些注解的目的只是「知道有哪些字段、按什么顺序排」，用来生成 __init__、__repr__、__eq__，它不关心你实际传了什么类型。mypy 这类静态检查器确实会读注解并报错，但那发生在你写代码或跑 CI 的时候，而外部数据只在运行期才出现，静态检查对它无能为力。所以正确的心智模型是：注解是写给人和工具看的说明，不是运行期的一道门。需要运行期保证时，要么用 pydantic，要么在 __post_init__ 里自己写检查。
field(default_factory=list) 和直接写 = [] 到底差在哪？
差别和函数默认参数那个经典坑是同一个：= [] 写法下，列表只在类定义时创建一次，所有实例会共享同一个对象，一个实例 append 之后其他实例也跟着变。default_factory 接收的是一个零参可调用对象，每次构造实例时调用一次，因此每个实例拿到的是各自新建的列表。特别值得注意的是报错时机——dataclasses 检测到可变默认值会在类定义时就抛 ValueError，也就是模块导入阶段直接失败，而不是等到运行出问题。这算标准库难得的一次主动拦截，把一个隐性 bug 变成了显性的启动错误。判断规则很简单：默认值是 list、dict、set 或任何自定义可变对象，就一律用 default_factory。
frozen=True 之后到底还能不能改字段？__hash__ 是怎么冒出来的？
不能直接改。frozen=True 会生成一个拦截版的 __setattr__，任何赋值都抛 FrozenInstanceError。需要「改」的时候用 dataclasses.replace(obj, field=new_value)，它基于旧实例生成一个新实例，语义上是「派生」而不是「修改」。至于 __hash__：默认情况下只要 eq=True，Python 就会把 __hash__ 设为 None 让实例不可哈希，因为一个可变又按值相等的对象放进 set 会破坏哈希不变量；而 frozen=True 保证了字段不会变，所以 dataclasses 就放心地按字段元组生成一个 __hash__。这就是为什么想把数据类放进 set 或当字典键，必须开 frozen=True。还有个小陷阱：冻结类的 __post_init__ 里不能直接赋值派生字段，得用 object.__setattr__ 绕过拦截。
既然 pydantic 更安全，能不能整个项目都用它，省得来回转换？
能跑，但在两方面会付出代价。第一是性能：每次实例化都走一遍校验管线，内层如果在循环里创建成千上万个对象，这部分开销会变成主要瓶颈，而这些对象的数据其实早在边界就验过一次了，是纯粹的重复劳动。第二是依赖方向：领域模型一旦继承 BaseModel，第三方库的类型就渗透进了整个业务代码，将来升级大版本或更换框架时改动面会铺得很大。还有个更隐蔽的问题是语义模糊——当所有类长得一样时，你没法从类型上看出哪个对象是「待验证的外部输入」、哪个是「已确认的内部事实」。所以推荐做法是分层：边界用 pydantic，内层用 frozen dataclass，中间放一次显式转换。小脚本和一次性工具不必这么讲究，直接全用 pydantic 完全可以。
标准库都有 dataclass 了，attrs 还有存在的必要吗？
有，但适用面明显变窄了。attrs 比标准库早，标准库的数据类本来就是它的一个精简子集被官方吸收的产物，所以形状高度相似。它保留的优势集中在三处：内置的校验器与转换器体系（validator / converter，转换先于校验执行）、更细的字段控制（比如某字段不参与 __eq__ 或 __repr__）、以及更成熟的 slots 支持——标准库的 slots=True 是 3.10 才加的，在继承和缓存属性等边角场景上不如 attrs 稳妥。它的定位是「需要比 dataclass 更强的校验，但不需要 pydantic 那套序列化和 JSON Schema」。如果标准库已经够用，就没必要为边际收益引入一个依赖，何况它还有新旧两套 API 会增加团队的认知成本。
边界 pydantic、内层 dataclass，中间那层转换写起来会不会太啰嗦？
转换代码通常就是一个 to_domain() 方法，把校验后的字段传给内层类的构造函数，字段名大多能对上，实际量很小。而且它换来的东西相当实在：内层不必重复校验、领域模型零第三方依赖、类型本身就在表达「这份数据处在哪个阶段」。真正让人觉得啰嗦的情况，往往是把边界模型和领域模型设计成了一比一镜像——这通常说明边界模型定义得太贴近内部结构了。好的边界模型应该贴着外部协议的形状（字段名可能是下划线或驼峰、可能有冗余字段、可能嵌套很深），领域模型贴着业务概念的形状，两者本来就不该长得一样，转换那一层正是把外部形状翻译成业务语言的地方。小项目里当然可以先不分层，等到边界模型开始为了迁就内部结构而变形时，再拆也来得及。
slots=True 和 kw_only=True 什么时候值得开？有没有副作用？
slots=True 的收益是去掉每个实例的 __dict__，内存占用明显下降、属性访问也略快，代价是实例不能再动态添加未声明的属性，并且和某些依赖 __dict__ 的模式（比如 functools.cached_property、部分弱引用用法）配合时需要额外注意。判断标准是量级：要同时存在几十万个实例时开它收益明显，只有几百个就没必要。kw_only=True 强制所有字段用关键字传参，副作用只有一个——调用点变长。但对字段多的类这反而是收益，因为 Job("sync", 3, 5.0) 这种调用读起来全是谜题，位置错了还不一定报错。它另外顺手解决了一个真实的别扭：普通数据类里「有默认值的字段必须排在后面」，继承时经常导致字段顺序不符合语义甚至直接 TypeError，开了 kw_only 这条限制就不存在了。两个参数都需要 Python 3.10 及以上。
