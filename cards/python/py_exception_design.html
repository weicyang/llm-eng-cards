写 try/except 是为了「别崩」，设计异常体系是为了回答另一个问题：这个错误该由谁来处理。答不上来，就会长出一种既不崩也查不出问题的系统——每一层都顺手吞一点，最外层什么都不知道。

一、异常是控制流的一部分，不是「出错兜底」

很多人对异常的心理模型停留在「正常逻辑写在 try 里，出事了在 except 里补救」。这个模型不算错，但它把异常当成了程序的边角料。实际上在 Python 里，异常是一等的控制流机制：迭代结束靠 StopIteration，属性查找失败靠 AttributeError 触发 __getattr__ 兜底，dict 的 setdefault 语义在 C 层同样建立在「先试后补」之上。这些都不是「出错了」，而是正常流程的一部分。

先检查再做，还是先做再处理

LBYL（Look Before You Leap，先检查再跳）是先用条件判断确认操作能成功，再执行；EAFP（Easier to Ask Forgiveness than Permission，先做再道歉）是直接执行，失败了用 except 接住。Python 惯用后者，理由有两条，而且都不是风格偏好。

第一条是竞态窗口。os.path.exists(p) 返回 True 到 open(p) 真正执行之间，文件可能已经被别的进程删掉、权限可能已经被改掉。检查得出的结论在下一行就可能过期，而 open 本身的检查和打开是原子的。第二条是检查逻辑会扩散：每个调用点都要重复写一遍前置判断，一旦条件变了，你得找遍所有调用点。

主流程与异常路径在代码结构上的分离 ───────────────────────────────────────────────────────────── 风格 A：用返回值 / 错误码层层传递 caller ──> f1() ──> f2() ──> f3() │ │ │ │ if err? if err? if err? return -1 │ │ │ └── 每一层都要写一遍判断，主流程被 if 切得七零八落 漏掉任何一层的判断 = 错误被当成正常值继续往下走 风格 B：异常沿调用栈自动上抛 caller ──> f1() ──> f2() ──> f3() │ │ │ raise UpstreamUnavailable └──── except AppError <──────┘ 中间两层一行都不用写，主流程是一条直线 「不知道怎么处理」的层，什么都不做才是正确做法

风格 B 的好处不在少写几行，而在阅读时主流程是连续的。你顺着读下来看到的是「取配置 → 调上游 → 解析 → 落库」，而不是「取配置 → 判断 → 调上游 → 判断 → 解析 → 判断」。异常路径被集中到一处，它和主流程在视觉上就是分开的两块。

异常的价值不是「让程序别崩」，而是把正常路径和异常路径在代码结构上拆开，让主流程保持一条直线。中间层什么都不写，恰恰是它在正确地履行职责。

但可预期的业务分支不该用异常表达

这是另一侧的边界，比上面那条更常被搞错。「用户没有优惠券」「搜索结果为空」「这条记录还没有备注」——这些都是完全正常的业务状态，不是错误。用 raise CouponNotFound() 表达它们，会带来三个具体代价：调用方被迫为正常情况写 try；日志里堆满不代表问题的异常，把真正的异常淹掉；监控上的「异常率」指标失去意义。

判据可以收敛成一句话：当前这一层还能不能给出一个有意义的结果。「没有优惠券」时返回 None 或空列表就是有意义的结果；「数据库连不上」时返回 None 是在撒谎——调用方无法区分「查了，确实没有」和「根本没查成」。

情形用返回值（None / 空列表 / 布尔）用异常
查询命中为空✅ 空是合法答案❌ 会逼调用方写 try
可选配置项缺失，有默认值✅ 返回默认值❌ 正常情况不该中断
用户输入格式不合法（表单校验）✅ 返回错误清单，一次性告诉用户全部问题⚠️ 抛第一个就停，用户要改很多轮
启动期必需的配置项缺失❌ 用默认值兜底 = 服务行为诡异✅ 立刻崩，见第五节
数据库 / 上游连接失败❌ 无法与「确实没有」区分✅ 当前层无法继续
不变量被破坏（余额算出负数）❌ 继续跑会写坏数据✅ 必须中断
调用方传了自相矛盾的参数❌ 静默纠正会掩盖调用方的 bug✅ 这是编程错误，越早暴露越好

表里第三行值得展开。表单校验抛异常在语法上没问题，但产品体验上很糟：抛出第一个错误就中断，用户填 8 个字段错了 3 个，得来回提交 3 次。这类场景更适合「收集所有错误后一次性返回」的结构。这说明一件事——该不该用异常，取决于调用方想要什么，而不只是取决于「有没有出错」。

二、设计自定义异常层次：按处理方式分组，不按发生位置分组

基础语法那一卡（PY07 · 文件读写与异常处理）讲过怎么捕获内置异常。到了模块或库的规模，你会开始定义自己的异常类——这时第一个决定就决定了后面所有调用方的体验。

每个库、每个应用模块都该有一个根异常

先定义一个 AppError（或 MyLibError），让所有自定义异常从它派生。收益很直接：调用方想「兜住你抛出的一切、但不误伤别人的异常」时，只需要写一行 except AppError。如果没有这个根，调用方要么把你的异常一个个列出来（你加一个新异常他就漏一个），要么写 except Exception——那会连同 KeyError、TypeError 这些真正的代码 bug 一起吞掉。

一棵按「调用方怎么处理」组织的异常树 ───────────────────────────────────────────────────────────── Exception └── AppError ← 根：一行 except 兜住本应用全部 ├── ConfigError ← 处理方式：启动期直接崩，不重试 │ ├── InputError ← 处理方式：回 4xx，告诉调用方改请求 │ ├── ValidationError 重试多少次结果都一样 │ └── UnsupportedFormat │ ├── UpstreamError ← 处理方式：回 5xx / 降级，可退避重试 │ ├── UpstreamTimeout retriable = True │ └── UpstreamUnavailable │ └── DataIntegrityError ← 处理方式：立刻停，人工介入 绝不能自动重试（可能重复扣款） 判据：如果两个异常的 except 块里写的代码一模一样， 它们就不该是两个类——合并，或者用字段区分。

注意这棵树的分组维度。它不是按「错误发生在哪个文件/哪个模块」分的，而是按调用方拿到它之后会做什么分的。这是异常层次设计里最容易走偏的一步，值得单独对比。

维度按发生位置分组按处理方式分组
典型类名DBError / RedisError / HttpClientErrorRetriable / InputError / ConfigError
调用方要写什么把所有「可能超时的组件」列一遍：except (DBError, RedisError, HttpClientError)一行 except UpstreamError
新增一个组件时所有调用点都要补一个类名，漏一个就漏一类错误新异常挂到已有分支下，调用方零改动
重构（Redis 换成 Memcached）异常类名跟着漏出去，调用方被迫改内部换实现，对外契约不变
什么时候仍然合理库内部调试用的细分类型，可以作为叶子节点保留作为对外暴露的中间层节点

两种维度并不互斥：合理的做法是中间层节点按处理方式划分，叶子节点保留位置信息。上面那棵树里 UpstreamTimeout 和 UpstreamUnavailable 就是叶子，它们携带了更细的信息供日志使用，但调用方只需要认识父类 UpstreamError。

异常应当携带字段，而不是拼字符串

新手写自定义异常最常见的形态是 raise AppError(f"订单 {oid} 的上游 {svc} 超时了")。信息是全的，但它只能被人读，不能被程序用。上层想知道「这个错该不该重试」，只能去正则匹配消息里有没有「超时」两个字——消息一改，判断逻辑就悄悄失效。

正确做法是把可判断的信息做成结构化异常字段：异常对象上的属性，供上层做决策和写结构化日志，而消息字符串只负责给人看。

class AppError(Exception):
    """本应用抛出的一切异常的共同根。"""

class UpstreamError(AppError):
    retriable = True          # 类级默认值，子类可覆盖

    def __init__(self, service, *, order_id=None, user_hint="服务繁忙，请稍后重试"):
        super().__init__(f"上游 {service} 调用失败 (order={order_id})")
        self.service, self.order_id = service, order_id
        self.user_hint = user_hint

有了 retriable，最外层的重试装饰器就能写成 if getattr(e, "retriable", False)，而不是猜消息内容。有了 user_hint，就能把「给用户看的话」和「给工程师看的话」彻底分开——后者可以包含内部服务名和订单号，前者绝不该包含。这两条信息混在同一个字符串里，几乎必然导致内部细节泄漏到用户界面。

异常类的数量不该由「有多少种出错原因」决定，而该由「调用方有多少种不同的应对动作」决定。两个异常的 except 块写的是同一段代码，那它们就是同一个异常。

还有一个实现细节：自定义异常继承自 Exception 而不是 BaseException。BaseException 是留给 KeyboardInterrupt、SystemExit 这类「不该被业务代码拦截」的信号用的，第五节会说明为什么这条界线必须守住。继承体系相关的 MRO 规则见 PY16 · 继承、MRO 与组合优先，异常类同样受它约束。

三、在哪一层处理：让异常穿过不知道怎么办的层

「在哪捕获」比「捕获什么」更难决定，也更容易错。一个可操作的原则是：只在你真的能做点什么的那一层捕获。做不了任何有意义的事（只是打条日志然后重新抛、或者更糟，返回 None），那就不要捕获——让它穿过去。

异常在分层架构里的传播与转译 ───────────────────────────────────────────────────────────── ┌─ 入口层（HTTP handler / 任务入口 / CLI main）───────────────┐ │ except AppError as e: 记日志(含 traceback) + 映射状态码 │ ← 唯一 │ except Exception as e: 记日志 + 500 + 告警 │ 兜底点 └────────────────────────────▲────────────────────────────────┘ │ UpstreamTimeout 一路上抛 ┌─ 服务层（业务编排）─────────┴────────────────────────────────┐ │ 不 catch。它不知道超时该怎么办，也不该替入口层决定 │ └────────────────────────────▲────────────────────────────────┘ │ ┌─ 适配层（第三方 SDK 的包装）┴────────────────────────────────┐ │ except requests.Timeout as e: │ ← 转译 │ raise UpstreamTimeout("pay-api") from e │ 发生地 │ 职责：把外部类型翻译成自己的契约，保留因果链 │ └────────────────────────────▲────────────────────────────────┘ │ requests.exceptions.Timeout ┌─ 第三方库 / 系统调用 ───────┴────────────────────────────────┐ │ 只抛，不吞 │ └──────────────────────────────────────────────────────────────┘
层该做什么不该做什么
底层（IO、系统调用、第三方库）让原始异常自然抛出捕获后返回 None 或 -1
适配层 / 防腐层异常转译：捕获外部异常，包装成自己的类型并 from e把 requests.Timeout 原样漏给上层
服务层 / 业务编排原则上什么都不做，让异常穿过「打个日志再 raise」——会导致同一个错误被记 4 遍
入口层（handler / task / CLI）统一兜底：记 traceback、映射状态码或退出码、决定用户看到什么把内部异常消息直接返回给用户

为什么必须转译：避免第三方类型变成你的公开契约

假设你的用户服务内部用 requests 调支付网关，并且让 requests.exceptions.ConnectionError 原样抛给了调用方。这一刻起，requests 就成了你对外契约的一部分——调用方为了处理错误必须 import requests，即使他根本不用 HTTP。半年后你把客户端换成 httpx，异常类型全变，所有调用方一起报错，而你改的只是一个内部实现细节。

转译就是在自己的边界上立一道墙：外面的类型进不来，出去的只有 UpstreamTimeout 这类你自己定义的、你能保证稳定的类型。这和上下文管理器那一卡里「把资源生命周期收进边界」是同一种思路——边界的意义在于内部可以随便改。

转译时必须 from e

try:
    resp = client.post(url, json=payload, timeout=3)
except requests.Timeout as e:
    raise UpstreamTimeout("pay-api", order_id=oid) from e   # ✅ 因果链保留
except requests.RequestException as e:
    raise UpstreamError("pay-api", order_id=oid) from e

# ❌ 反例：raise UpstreamTimeout("pay-api")
#    原始 traceback 里「卡在连接 10.2.3.4:443 三秒」这层信息全没了

漏掉 from e 的代价不是少一行日志，而是原始现场彻底消失。你在日志里只能看到「上游 pay-api 调用失败」和自己这一层的调用栈，看不到究竟是 DNS 解析失败、TCP 连接超时、还是读响应超时——而这三者的处理动作完全不同。

示例场景：某支付回调服务的适配层写了 12 处 except ... : raise PaymentError("支付失败")，全部漏了 from e。一次线上故障中，告警只有「支付失败」和一串指向同一行包装代码的 traceback，无法区分是证书过期、DNS 抖动还是对方限流。团队靠抓包和逐个手工复现定位，耗时约 3 小时 40 分钟。补上 from e 后，同类告警的日志里直接出现 SSLCertVerificationError: certificate has expired，下一次同类问题的定位时间压到 5 分钟以内。改动量是 12 处各加两个单词。

判断「这一层该不该 catch」只问一句：接住之后我能做出一个和不接住不同的决定吗？答案是否，就别接。「打条日志再抛出去」不算一个决定，它只会让同一个错误在日志里出现四遍。

四、异常链与上下文：from 的三种形态

当一个异常在处理另一个异常的过程中被抛出时，Python 会把两者关联起来，这就是异常链。链子怎么连，由你写的形式决定，一共三种，打印出来的 traceback 形态也完全不同。读不出这三种形态的区别，就会把包装层当成根因。

写法设置的属性traceback 里的连接语什么时候用
raise X from e__cause__ = e（同时 __suppress_context__ 为真）The above exception was the direct cause of the following exception显式转译：我知道 e，我是因为它才抛 X 的
在 except 块里裸 raise X__context__ = e（自动设置，你不用写）During handling of the above exception, another exception occurred多数是意外：处理 e 的代码自己又炸了
raise X from None__suppress_context__ = True，链条不打印（无，只显示 X）原始异常是纯实现细节，露出去只会误导

第二行最需要留意。它多数时候不是你主动设计的，而是事故的信号：你在 except KeyError 里写了清理逻辑，清理逻辑自己抛了 AttributeError。Python 忠实地把两个异常都保留下来，于是 traceback 变成两段。此时真正需要修的往往是第二段（你的清理代码有 bug），而根因是第一段。

怎么读一段两层的 traceback

Traceback (most recent call last): ┐ File "adapter.py", line 31, in call_pay │ ← 段 1：根因 resp = client.post(url, timeout=3) │ 真正发生的第一件坏事 requests.exceptions.ConnectTimeout: │ HTTPSConnectionPool(host='pay-api')... ┘ The above exception was the direct cause of the following exception: ↑↑↑ 看到这句 = 下面那段是「包装」，上面那段才是根因（from e） Traceback (most recent call last): ┐ File "adapter.py", line 33, in call_pay │ ← 段 2：你的包装 raise UpstreamTimeout("pay-api") from e │ 只告诉你「谁包的」 File "service.py", line 88, in place_order │ File "handler.py", line 14, in post │ app.errors.UpstreamTimeout: 上游 pay-api 调用失败 ┘ 阅读规则 ─────────────────────────────────────────────────────────── 1. 从最下面一段开始看「异常类型 + 消息」→ 知道最终抛的是什么 2. 往上找连接语： direct cause → 上一段是你主动声明的根因，重点看它 During handling → 上一段是原始错误，下一段多半是处理逻辑的 bug 3. 最上面那段的最后一行，通常就是你要查的那个根因 4. 每段内部仍是「从下往上 = 从最内层调用往外」

多层包装时这套结构会继续嵌套，可能出现三段四段。规则不变：最上面那一段永远是最原始的。这也是为什么 from e 不能省——省掉之后，最上面那段就没了，你拿到的是一段没有根的 traceback。

from None 不是偷懒，是有用途的

raise X from None 主动切断链条，唯一正当的理由是：原始异常属于实现细节，暴露给调用方只会误导。典型场景是你的配置加载器内部从 json 换成了 tomllib，用户传了一个坏配置，如果原样透出 tomllib.TOMLDecodeError，用户会以为是自己的 TOML 有问题——但他给的明明是 YAML 路径写错了。

def load_config(path):
    try:
        return _parse(path.read_text(encoding="utf-8"))
    except (ValueError, OSError):
        raise ConfigError(
            f"配置文件无法解析: {path}（期望 UTF-8 编码的 TOML）"
        ) from None

但要清醒地认识到代价：from None 之后，原始异常在日志里彻底看不到了。所以用它的前提是——你已经在异常消息里把用户需要知道的全部信息说清楚了。如果只是嫌 traceback 太长就切断，那是在给未来的自己埋雷。折中做法是切断对外的链条，同时在切断前用 logger.debug(..., exc_info=True) 把原始异常留在日志里。

from e 是「因为它，所以我」，from None 是「它是我的内脏，不该给你看」，而裸 raise 出来的 During handling 往往是「我的处理代码自己也炸了」——第三种通常不是设计，是 bug 的提示音。

五、什么时候该让它崩

吞异常之所以有诱惑力，是因为它的收益立刻可见（服务不挂了、告警不响了），代价却推迟到未来某次故障排查时才结算。而那时候，错误已经静默扩散了几小时，根因早就被覆盖。所以需要一组事前就能用的判据。

快速失败的三条判据

快速失败指在错误刚出现、影响面还最小的时刻立刻中断，而不是带病继续运行。满足以下任意一条，就应该让它崩：

  • 不变量被破坏。不变量是程序在任何时刻都应当成立的约束，比如「库存数量非负」「订单总额等于各项之和」。它一旦不成立，说明前面某处逻辑已经错了，后面每一行代码都在错误的前提上运行。
  • 继续运行会造成更大损害。写坏数据、扣错钱、发错通知——这类副作用一旦落地，回滚的成本远高于当场崩溃。崩溃只损失一个请求，写坏数据可能污染整张表。
  • 在当前层无法有意义地恢复。「有意义」是关键词：返回 None、返回空列表、用默认值顶上，如果调用方无法区分这个结果和真实结果，那就不是恢复，是伪造。

注意第一行。启动期的配置错误是最值得崩的一类：此时还没有任何用户流量，崩溃的代价是零；而用默认值兜底跑起来的服务，可能连着三天把数据写进了默认的测试库。越早的错误越该崩得越响。

示例场景：某数据同步任务在单条记录处理外面套了 except Exception: continue，意图是「别让一条脏数据中断整批」。上游某次调整字段名后，解析全部失败，任务每轮照常「成功」结束，监控上的成功率是 100%。11 天后业务方发现报表数据停在半个月前，此时已累计漏同步约 240 万条记录，补数据 + 对账耗时 2 天。修复只加了两样东西：continue 前记录 logger.exception，以及「单批失败率超过 5% 就整批失败」的阈值。改动不到 10 行，但它把「静默 11 天」变成了「10 分钟内告警」。

有些异常永远不该被吞

裸 except Exception 之所以比 except BaseException 安全，是因为 Python 特意把几个「不属于程序错误」的信号放在 BaseException 下面，让 Exception 抓不到它们：

异常含义吞掉的后果
KeyboardInterrupt用户按了 Ctrl+C进程杀不掉，只能 kill -9，跳过所有清理逻辑
SystemExitsys.exit() 发出的退出请求退出码丢失，CI 与编排系统以为你成功了
GeneratorExit生成器被提前关闭资源不释放，还会触发 RuntimeError
MemoryError内存分配失败任何后续操作都可能再次失败，包括你的错误处理代码本身
asyncio.CancelledError任务被取消（3.8+ 起继承 BaseException）取消信号被无视，超时和优雅关闭全部失效

所以规则很简单：业务代码里永远不写 except BaseException，也不写 except:（裸 except 等价于前者）。需要「兜住一切并记录」时用 except Exception，它刚好放过上面这几个。

finally 里 return 会吞掉正在传播的异常

def load(path):
    try:
        return parse(path.read_text())    # 这里抛了 ValueError
    finally:
        return {}        # ❌ 异常被无声丢弃，函数返回 {}

# 同样的陷阱：finally 里写 break / continue，
# 以及在 finally 里 raise 新异常（会覆盖原异常，只剩 __context__）

这是 Python 语言层面规定的行为：finally 块里的 return / break / continue 会终止正在进行的异常传播，函数正常返回。它不会有任何警告，静态检查工具默认也未必开这条规则。finally 里只应该放清理动作，收尾工作更推荐交给上下文管理器，理由和这一条完全一样——把清理和控制流分开。

吞掉异常买到的是「看起来还在跑」，付出的是根因。这笔交易的账单不会当场到，而是在几天后以「数据错了但没人知道从哪天开始」的形式送达。

六、异常与可观测性：异常只有被看见才有价值

前面五节都在讲怎么抛、抛到哪、什么时候不接。但异常最终要落到人的眼睛里，而这一段是最常被草率对待的：一个设计精良的异常层次，配上 print(e) 的日志，效果和没设计一样。

日志里必须留 traceback

print(e) 或 logger.error(str(e)) 只会输出异常的消息字符串——一行文本，没有调用栈，没有异常链，没有类型。你知道「上游 pay-api 调用失败」，但不知道是哪个请求、从哪里调的、根因是什么。

except UpstreamError as e:
    logger.exception("下单失败", extra={"order_id": e.order_id})   # ✅
    # 等价写法：logger.error("下单失败", exc_info=True)

    # ❌ logger.error(f"下单失败: {e}")   —— 只有一行消息，根因没了
    # ❌ print(e)                        —— 连日志级别和时间都没有

logger.exception 只能在 except 块里调用（它从当前异常上下文取 traceback），级别固定为 ERROR。需要别的级别时用 exc_info=True。第四节说的异常链会被完整打印出来，包括所有 direct cause 段落——这正是 from e 的收益兑现的地方。

示例场景：某内部服务的错误日志长期写成 logger.error(f"处理失败: {e}")，一次线上事故中值班同学面对 4700 条内容一模一样的「处理失败: list index out of range」，完全无法定位是哪个字段、哪条数据、哪段代码。团队最终靠在本地按线上参数重放请求才复现，从告警到定位耗时约 2 小时 15 分钟。事后把这一处改成 logger.exception 并加上 extra={"order_id": ...}，下一次同类问题从告警到看见出错行号只用了约 3 分钟。改动是一个方法名加一个参数。

异常消息该写什么、不该写什么

要素反例正例
当时的输入操作失败解析配置失败: config/prod.toml 第 14 行
期望与实际参数错误timeout 需为正数，收到 -3
可定位的标识数据库错误写入 orders 失败 (order_id=A10293)

最后一行单独强调：异常消息会进日志，日志会进日志平台，日志平台的权限范围通常远大于代码仓库。密钥、令牌、身份证号、完整请求体（可能含密码字段）都不该出现在异常消息里。需要定位时用「前缀 + 长度」「哈希后八位」这类不可逆的指纹。这条在代码评审里很容易漏，因为它不影响功能，只在泄漏发生后才显形。

重试的边界

重试只对瞬时性错误有意义——那些「同样的请求，过一会儿再发就可能成功」的错误：连接超时、上游 503、数据库连接池暂时耗尽。反过来，4xx 这一类表示「请求本身有问题」，请求不变，重试一万次结果完全相同，只是在给已经不健康的上游继续加压。第二节里那个 retriable 字段的价值就在这里：让重试逻辑读属性，而不是猜消息。

情况重试要点
连接超时 / 读超时 / 503 / 429✅指数退避 + 抖动，避免所有客户端同时重试形成尖峰
400 / 401 / 403 / 422❌请求本身的问题，重试只会放大上游压力
非幂等写操作（下单、扣款）⚠️必须先有幂等键，否则重试 = 重复扣款
批量任务中的单条失败⚠️要有失败率阈值，整批静默跳过就是第五节那个案例

另外提一点：Python 3.11 引入的 ExceptionGroup 和 except* 语法，用于并发场景下「多个任务同时失败、需要一次性抛出多个异常」的情况——传统的单异常模型在这里表达不了「三个任务里两个失败了，而且失败原因不同」。这属于并发那一组的内容，本卡不展开。

  • 每个应用 / 库定义一个根异常，让调用方一行 except AppError 兜住
  • 异常层次按调用方的处理动作分组，处理方式相同就合并成一类
  • 把可判断的信息做成字段（retriable、资源 id、user_hint），别拼进消息字符串
  • 在适配层把第三方异常转译成自己的类型，并且始终写 from e
  • 中间层不 catch，让异常穿过；只在入口层统一兜底一次
  • 日志用 logger.exception 或 exc_info=True，保住完整 traceback 与异常链
  • 启动期的配置错误立刻崩，用非 0 退出码表达
  • 只对瞬时性错误重试，非幂等写操作先有幂等键
  • 用异常表达正常业务分支（「没有优惠券」返回空就好）
  • 写 except Exception: pass 或 except:，把 KeyboardInterrupt 一起吞掉
  • 转译时漏掉 from e，把原始 traceback 丢在包装层里
  • 在每一层都「记条日志再 raise」，同一个错误刷四遍日志
  • 靠正则匹配异常消息判断该不该重试
  • 在 finally 里写 return / break，无声吞掉正在传播的异常
  • 把令牌、密钥、完整请求体写进异常消息
  • 批处理里 except Exception: continue 却不记日志、不设失败率阈值

异常设计的最终检验标准只有一个：线上出事时，你能不能只看日志就说出「哪一行、因为什么、下一步该改哪里」。说不出来，前面所有层次划分都只是好看的类图。

Q&A

什么时候该定义自定义异常，什么时候直接用内置的就行？
判据是「调用方会不会需要专门针对它写一个 except 分支」。如果只是参数类型不对、索引越界这类通用编程错误，直接用 TypeError、ValueError、KeyError 就好——它们有公认的语义，额外定义一个 MyValueError 只会增加调用方的认知负担。反过来，如果这个错误代表你这个模块特有的失败模式，并且调用方会因此做出不同的动作（重试、降级、提示用户），那就值得定义。判断标准始终是调用方的处理方式，而不是「这个错误听起来特不特别」。经验上，一个中等规模的服务有 5 到 15 个自定义异常类是合理的，几十个通常意味着分得太细了。
为什么不推荐在每一层都记一次日志？
因为同一个错误会在日志里出现四五遍，而且每一遍的 traceback 都指向不同的包装位置，排查时你得先判断哪几条其实是同一件事。更糟的是它会让日志量和告警数量虚高，真正的新问题被淹没在重复条目里。正确做法是让中间层完全不 catch，由入口层记录一次完整的 traceback——因为异常链已经把中间经过的所有层都记录在调用栈里了，中间层补的那条日志并没有提供新信息。如果某一层确实有独有的上下文需要留（比如重试了几次），更好的方式是把它作为字段挂到异常对象上，而不是单独打一条日志。
raise X from e 和在 except 块里直接 raise X，打印出来到底差在哪？
两者都会保留原始异常，区别在于语义声明和打印的连接语。from e 设置 __cause__，traceback 里显示「The above exception was the direct cause of the following exception」，意思是「我是有意基于它抛出新异常的」。而在 except 块里裸写 raise X，Python 会自动设置 __context__，显示「During handling of the above exception, another exception occurred」，意思是「处理上一个异常的过程中又出了一个」。前者通常是设计，后者通常是意外——你的错误处理代码自己出了 bug。读日志时看到 During handling，第一反应应该是去检查 except 块里的代码，而不是只看最终抛出的那个异常类型。
吞异常（except Exception: pass）有没有合理的场景？
有，但比大多数人以为的少得多，而且必须同时满足两个条件：这个失败对主流程确实无关紧要，并且你已经把它记进日志了。典型的合理场景是清理动作的收尾——比如关闭一个已经出错的连接、删除一个临时文件，失败了也不影响主结果。即便如此，也应该写成 except Exception: logger.warning("清理临时文件失败", exc_info=True) 而不是 pass，因为「无关紧要」是你当下的判断，未来它可能变成排查线索。真正的 pass 只在极少数情况下成立，比如探测某个可选依赖是否存在。凡是写 pass 的地方，都应该有一行注释说明为什么可以忽略。
启动时配置错了，为什么不能用默认值兜底跑起来？
因为用默认值跑起来的服务处在一个「看起来健康、实际行为错误」的状态，而这是所有状态里最难发现的一种。典型后果是数据库地址落到了默认的本地或测试实例，服务正常接收流量、正常返回 200，数据却全写去了错地方，等发现时已经过了几天。相比之下，启动期崩溃的代价几乎是零——此时还没有任何用户流量，编排系统会立刻发现容器起不来并告警，你在部署阶段就能改掉。一个实用的做法是在进程启动的最开始集中做一次配置校验，把所有缺失和格式错误一次性收集完再抛出，而不是等到第一次用到某个配置项时才在业务代码深处报错。
为什么不该让第三方库的异常类型直接漏给我的调用方？
因为异常类型是你对外契约的一部分。一旦 requests.exceptions.ConnectionError 从你的函数里抛出去，调用方为了处理它就必须 import requests，哪怕他根本不关心你内部用什么发 HTTP。后果是你被锁死了：换成 httpx 或加一层缓存，异常类型全变，所有调用方一起报错，而你改的明明只是实现细节。正确做法是在适配层把外部异常转译成自己定义的类型，比如 UpstreamUnavailable，并且用 from e 保留因果链，这样原始信息仍在日志里，但对外的类型是稳定的。这层转译的成本是几行代码，省下的是未来一次跨团队的破坏性变更。
finally 里写 return 为什么会吞掉异常？该怎么避免？
这是 Python 语言规定的行为：finally 块中的 return、break、continue 会终止正在进行的异常传播，函数转为正常返回。语言这样设计是因为这三个语句都表示「离开当前控制结构」，而异常传播也是一种离开，后发生的那个赢。问题在于它完全无声——没有警告，没有日志，异常就这样消失了，函数返回了一个看起来正常的值。避免方式很简单：finally 里只放清理动作，不放任何改变控制流的语句；同理也不要在 finally 里 raise 新异常，那会让原异常降级成 __context__。更好的选择是把清理逻辑交给上下文管理器，让资源的获取与释放成对出现，这样根本不需要手写 finally。
批处理任务里怎么做到「单条失败不中断整批」又不静默吞错？
关键是把「跳过」和「记录」拆成两件必须同时做的事。第一，每次跳过都必须写一条带 traceback 的日志（logger.exception），并且带上能定位到那条记录的标识，否则你事后无法知道漏了哪些。第二，要统计失败数并设阈值——单批失败率超过某个比例（比如 5%）就让整批失败，因为那已经不是脏数据问题，而是上游变更或代码 bug。第三，把失败条数暴露成监控指标，而不只是埋在日志里，这样它才能触发告警。只做第一步仍然危险：日志里有一万条 ERROR，但没人看日志，成功率指标依旧是 100%。三步齐备，才算是真正的「容错」而不是「静默」。
