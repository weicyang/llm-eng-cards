PY14 · 可变参数、闭包与装饰器

打包与解包的对称性 / 单元对象与自由变量 / 延迟绑定事故 / 装饰器三层结构 / wraps 与元信息 / lru_cache 与叠放顺序

这三个话题看起来是三件事，其实是一条链：*args/**kwargs 让一个函数能原样转发任意调用，闭包让这个转发函数记住被它包住的对象，装饰器只是把这两件事合起来换掉一个名字的指向。谁都能背出「装饰器是语法糖」，真正决定你会不会踩坑的是中间那一环——闭包捕获的是变量，不是值。

一、星号的两个方向：打包与解包是一对反向操作

* 和 ** 之所以让人反复记不住，不是因为规则复杂，而是因为同一个符号在两个不同位置的语义正好相反。写在函数定义处的参数列表里，它做的是收集：把调用方给多的实参拢进一个容器。写在函数调用处的实参列表里，它做的是摊开：把一个容器拆成一个个独立实参。方向完全反过来。

具体来说，定义处的 *args 声明一个可变位置参数——它把所有没被前面形参接住的位置实参打包成一个元组；**kwargs 声明一个可变关键字参数，把所有没有对应形参名的关键字实参打包成一个字典。这里有个常被忽略的细节：打出来的一定是元组和字典，类型固定，不受你传进去的是列表还是生成器影响。而调用处的 * 和 ** 执行的是解包，即把可迭代对象按位置铺开、把映射按键名铺开。

定义处的 * / ** —— 打包（多个实参 → 一个容器） ───────────────────────────────────────────────── log(1, 2, mode="fast") │ │ │ └──┴──┐ └────────────┐ ▼ ▼ def log(*args, **kwargs): │ │ ▼ ▼ args = (1, 2) kwargs = {'mode': 'fast'} 固定是 tuple 固定是 dict 调用处的 * / ** —— 解包（一个容器 → 多个实参） ───────────────────────────────────────────────── nums = [1, 2] opt = {'mode': 'fast'} │ │ │ *nums │ **opt ▼ ▼ log( 1, 2 , mode="fast" ) │ │ │ ▼ ▼ ▼ def log(a, b, mode="slow"): ... 两边写法一模一样，方向恰好相反： 定义处把散的收起来，调用处把收起来的散开

看代码比看文字快。下面这段的最后两行和第四行是完全等价的调用，区别只在于实参是现场写死的还是从容器里摊出来的。

def log(*args, **kwargs):        # 定义处：打包
    print(args, kwargs)

log(1, 2, mode="fast")           # args=(1, 2)  kwargs={'mode': 'fast'}

nums = [1, 2]
opt = {"mode": "fast"}
log(*nums, **opt)                # 调用处：解包，与上面那行等价

同一个星号，在形参表里是漏斗（把多的收进来），在实参表里是喷头（把一个撒出去）。判断它此刻是哪个意思，只看它写在 def 那一行还是写在调用那一行。

定义处与调用处的语义对照

写法出现位置做的事结果类型 / 约束
*args定义处收集多余的位置实参元组；一个函数最多一个
**kwargs定义处收集多余的关键字实参字典；必须放在参数表最后
*（裸星号）定义处它后面的形参强制按关键字传不接收任何值，只是分隔符
*seq调用处把可迭代对象铺成位置实参任意可迭代对象都行，含生成器
**mapping调用处把映射铺成关键字实参键必须是合法标识符字符串
a, *rest = seq赋值语句收集剩余元素列表（不是元组），最多一个星号

表里那个裸 * 值得一提：写成 def connect(host, *, timeout=5) 之后，connect("db", 10) 会直接报 TypeError: connect() takes 1 positional argument but 2 were given。这是有意的，它让调用点必须写出 timeout=10，日后你调整参数顺序也不会悄悄改变已有调用的含义。参数传递的基础规则在 PY05 · 函数入门与参数传递 里已经讲过，这一节只补星号的两个方向。

转发：装饰器的地基就这一行

把打包和解包接在一起，就得到了原样转发：外层函数用 *args, **kwargs 把任何调用都收下来，再用 *args, **kwargs 原封不动交给内层。它的价值是外层不需要知道内层的签名——不管内层是 f() 还是 f(a, b, *, c=1)，这一行都成立。第四节的装饰器之所以能装饰任意函数，靠的就是这个性质。

def forward(*args, **kwargs):
    return log(*args, **kwargs)   # 先打包再解包，等于什么都没改

a, *rest = [10, 20, 30]           # a=10   rest=[20, 30]  ← rest 是 list
first, *mid, last = range(5)      # mid=[1, 2, 3]
merged = {**opt, "mode": "safe"}  # 解包也能用在字面量里，后写的覆盖先写的

解包赋值里那个星号也是同一套语义的延伸：等号左边的 *rest 是打包（收集剩余元素），只不过它打出来的是列表而不是元组。这个差异偶尔会咬人——如果你打算把结果拿去当字典的键，得自己 tuple(rest) 一下。

二、闭包：函数带着它出生的环境一起走

函数调用结束时栈帧被销毁，局部变量随之消失，这是通常的理解。但如果外层函数返回了一个引用了外层局部变量的内层函数，这些变量就不能跟着栈帧一起死掉——否则内层函数被调用时就没东西可读了。Python 的解决办法是：编译阶段就识别出这类变量，把它们放进一种叫单元对象的中转盒子里，函数对象持有对盒子的引用，于是栈帧销毁与变量存活彼此独立。

内层函数里那些「既不是本地定义、也不是全局」的变量，正式名称是自由变量。一个函数对象加上它引用的自由变量的集合，就是闭包。注意这个定义里没有「值」这个词，全是「变量」，这不是措辞随意，而是第三节全部事故的源头。

f = make_counter(10) 执行完之后的内存结构 ────────────────────────────────────────── ┌─ make_counter 的栈帧 ──────────┐ │ start = 10 │ 函数一返回，栈帧就销毁 │ tick = <function> │ 但 start 没有跟着消失 └────────────────┬───────────────┘ │ 编译期就决定：start 是 tick 的自由变量 │ 所以它不放在栈帧里，放进 cell ▼ ┌───────────────┐ │ cell 对象 │ ← 单元对象：变量的一个中转盒子 │ contents: 10 │ 盒子本身可以被改写 └───────▲───────┘ │ 被函数对象引用（引用计数 ≥ 1，不会回收） ┌─────────────────┴─────────────────────────┐ │ 函数对象 f │ │ __code__.co_freevars = ('start',) │ ← 我需要哪些自由变量 │ __closure__ = (cell,) │ ← 这些变量现在住在哪 └───────────────────────────────────────────┘ 关键：f 持有的是「盒子」，不是「盒子里那个 10」

这两个属性不是内部黑箱，随手就能看：__code__.co_freevars 是编译期确定的名字列表，__closure__ 是运行期真正绑上去的单元对象元组，两者按下标一一对应。没有自由变量的普通函数，__closure__ 是 None——这也是判断「一个函数到底是不是闭包」最直接的办法。

def make_counter(start):
    def tick():
        return start            # start 不是本地也不是全局 → 自由变量
    return tick

f = make_counter(10)
f.__code__.co_freevars          # ('start',)
f.__closure__[0].cell_contents  # 10
(lambda: 1).__closure__         # None ← 没有自由变量，不是闭包

闭包不是「函数记住了当时的值」，而是「函数和外层那几个变量共用同一个盒子」。盒子里的内容随时可能变，函数每次调用都是现场去盒子里取。

三类变量，三种改写方式

读一个外层变量不需要任何声明，Python 会顺着作用域链往外找。但赋值就不一样了：函数体里只要出现对某个名字的赋值，该名字在整个函数里就被当成本地变量，于是赋值前读它会得到 UnboundLocalError: cannot access local variable 'total' where it is not associated with a value。想改写外层的变量而不是新建本地变量，就得显式声明。

变量类别定义在哪只读要声明吗改写用什么不声明就改写的后果
本地变量当前函数体内不需要直接赋值—
自由变量外层函数体内不需要nonlocal x变成本地变量，读时 UnboundLocalError
全局变量模块顶层不需要global x同上，且外层的值不受影响
内置名builtins 模块不需要不该改遮蔽内置，如定义 list = [] 后 list(...) 报 TypeError
def make_acc():
    total = 0
    def add(x):
        nonlocal total          # 去掉这行 → UnboundLocalError
        total += x              # 改的是同一个 cell 里的内容
        return total
    return add

acc = make_acc()
acc(3), acc(4)                  # (3, 7) ← 状态留在闭包里

nonlocal 和 global 的区别不只是找的层数不同：nonlocal 要求外层必须已经存在这个名字，否则是语法错误（SyntaxError: no binding for nonlocal 'total' found），在导入阶段就报，跑不到运行时；global 则可以凭空创建一个模块级变量。这个差异让 nonlocal 相对安全一些——拼错名字会当场被拦住。

上面的 make_acc 顺带展示了闭包最常见的正当用途：把状态封在函数里，对外只暴露一个可调用对象。它比模块级全局变量安全（外面改不到），也比为此专门写一个类轻。这类「只有一个方法的小类」用闭包实现往往更贴切。

三、延迟绑定：在循环里造闭包的经典事故

现在把上一节那句「闭包捕获变量、不捕获值」放进循环，就得到了 Python 里被踩得最多的坑之一。下面三个 lambda 看起来应该分别返回 0、1、2，实际上全都返回 2。

fs = [lambda: i for i in range(3)]
[f() for f in fs]               # [2, 2, 2]  ← 不是 [0, 1, 2]

原因不是「lambda 有问题」，也不是「推导式有问题」。三个 lambda 引用的是同一个变量 i，也就是同一个单元对象；循环每一轮只是把新值写进这个盒子，并没有造出三个盒子。等到 f() 真正执行时，循环早已结束，盒子里剩下的是最后一次写入的 2。这种「取值发生在调用时而非定义时」的行为叫延迟绑定。

fs = [lambda: i for i in range(3)] 循环结束后的结构 ──────────────────────────────────────────────────── lambda #0 ──┐ lambda #1 ──┼──► 同一个 cell ──► i = 2 ← 最后一轮写进去的 lambda #2 ──┘ ▲ │ 三个函数共享一个盒子，不是各持一份值 调用 f() 时才去读盒子，此刻读到的只能是 2 ⇒ [f() for f in fs] == [2, 2, 2] 修法 A：默认参数——把「读」的时机提前到定义时 ──────────────────────────────────────────────────── fs = [lambda i=i: i for i in range(3)] ▲ └── 等号右边的 i 在「def 那一刻」求值， 结果拷进函数对象的 __defaults__ lambda #0.__defaults__ == (0,) ← 各自一份，已与外面脱钩 lambda #1.__defaults__ == (1,) lambda #2.__defaults__ == (2,) 不再有 cell，也不再有共享 ⇒ [0, 1, 2] 修法 B：partial——把值冻进一个新的可调用对象 ──────────────────────────────────────────────────── partial(handle, i) ──► 对象内部 .args == (0,) / (1,) / (2,) 调用时 partial 先把自己存的实参摊开，再调 handle 签名干净（不会多出一个可被外部覆盖的形参）

这个坑真正危险的地方在于它几乎只出现在「批量造函数」的场景，而那些场景恰好都是循环：给一批按钮注册点击回调、按配置表批量生成字段校验器、给路由表里每个路径挂一个处理函数、给一组任务各自绑一个重试策略。它们的共同特征是函数被创建的时刻和被调用的时刻相隔很远，中间隔着一次事件、一次请求、一次调度——延迟绑定的窗口就在这段间隔里。

示例场景：一个数据同步服务从配置读出 12 张表，用 for t in tables: handlers.append(lambda: sync(t)) 批量注册定时任务。上线后监控显示 12 个任务全部指向配置里的最后一张表 orders：该表被重复同步 12 次、写入放大约 11 倍，其余 11 张表整整 6 小时零更新。排查时最迷惑的一点是日志完全正常——每个任务都「成功」了，只是都在同步同一张表。修复是把 lambda: sync(t) 改成 lambda t=t: sync(t)，改动 1 处、4 个字符，之后 12 张表各自更新正常。事故成本几乎全在定位上，而不在修复上。

两种修法的取舍

做法写法原理代价适合
默认参数当场绑定lambda t=t: sync(t)默认值在定义时求值并存入 __defaults__签名多一个形参，调用方能误传把它覆盖掉lambda、临时回调，改动最小
functools.partialpartial(sync, t)把实参冻进一个新可调用对象多一层对象，__name__ 需要另找已有具名函数，且这个对象会被传得比较远
工厂函数再包一层make(t) 返回内层函数每次调用生成独立栈帧与独立 cell要多写一个函数绑定逻辑本身有几行，值得命名
（不可行）循环内 del—删名字不改变已建立的引用无效，仍然共享不要尝试

两种主流修法里，默认参数最省事但把一个内部细节暴露成了公开形参——别人真的可以 f(t="别的表") 把它覆盖掉；partial 干净但会让 obj.__name__ 这类访问失败（partial 对象没有这个属性），日志里打函数名的地方要改成 obj.func.__name__。两者都对，选哪个取决于这个可调用对象会不会离开你的模块。

只要「造函数」和「调函数」之间隔着一次循环迭代，就必须问一句：我是想让它记住当时那个值，还是想让它跟着变量一起变？想要前者，就得在定义时把值取出来。

四、装饰器的本质：一个接受函数、返回函数的函数

装饰器常被当成一种独立的语言特性来记，其实它只是一条改写规则。写在 def 上面的 @deco，效果完全等同于在函数定义之后补一句 f = deco(f)——解释器做的就是这个替换，没有别的魔法。所以任何「接受一个函数、返回一个可调用对象」的东西都能当装饰器用，它不需要实现什么协议，也不需要继承什么基类。

@timed
def fetch(url, retry=3): ...

# 上面两行与下面两行完全等价：
def fetch(url, retry=3): ...
fetch = timed(fetch)

把这个等式念清楚，能立刻回答两个常见困惑。第一，被装饰的原函数有没有被修改？没有，它一个字节都没变，变的只是 fetch 这个名字现在指向 timed 的返回值。第二，装饰发生在什么时候？在 def 语句执行时，也就是模块导入阶段，而不是函数被调用时——这就是为什么装饰器里写的 print 会在 import 时就打出来。

装饰前 装饰后（@timed） ───────────────────────────── ────────────────────────────────── 名字 fetch ──► 函数对象 A 名字 fetch ──► 函数对象 wrapper （真正干活的） │ 闭包持有 fn └──► 函数对象 A （还在，没被改） 调用 fetch(url) 调用 fetch(url) └─► 直接进 A └─► 进 wrapper ├─ 前置：记下开始时间 ├─ fn(*args, **kwargs) ──► A └─ 后置：算差值、打日志 @deco 不改 A，它只改「fetch 这个名字指向谁」 所以原函数依然可达：fetch.__wrapped__ ──► A（加了 wraps 之后）

手写一个最小可用的装饰器，三层结构就完整暴露出来了。外层 timed 只在装饰那一刻执行一次，它的任务是接收被装饰函数并返回替身；中层 wrapper 是真正顶替原名字的那个函数，每次调用都走它；内层是对 fn 的调用，也就是原来那份逻辑。

import time

def timed(fn):                        # 外层：装饰时执行一次
    def wrapper(*args, **kwargs):     # 中层：每次调用都走这里
        t0 = time.perf_counter()
        result = fn(*args, **kwargs)  # 内层：调用原函数，fn 是自由变量
        cost = (time.perf_counter() - t0) * 1000
        print(f"{fn.__name__} 耗时 {cost:.1f}ms")
        return result
    return wrapper

注意 wrapper 里的 fn：它既不是 wrapper 的参数也不是全局变量，而是第二节说的自由变量，被单元对象持住。这意味着装饰器必然是闭包——它能在外层早已返回之后还找到原函数，靠的就是闭包机制。这也解释了为什么讲装饰器前一定要先讲闭包。

层次执行时机执行次数职责常见错误
外层 timed(fn)模块导入时每个被装饰函数 1 次接收原函数、返回替身忘了 return wrapper → 函数变成 None
中层 wrapper每次调用N 次前置逻辑、转发、后置逻辑忘了 return result → 返回值全变 None
内层 fn(...)每次调用N 次执行原逻辑写成 fn() 丢掉参数 → TypeError

表里两个「忘了 return」是新手最高频的两个错误，而且症状都很隐蔽：前者要等到调用时才报 TypeError: 'NoneType' object is not callable，后者根本不报错，只是所有返回值静默变成 None，可能到很远的地方才暴露成一个莫名其妙的 AttributeError。*args, **kwargs 的原样透传是第三个必须做对的点——只有它能保证同一个装饰器既能装 fetch(url) 也能装 save(a, b, *, dry_run=True)。

装饰器不是「给函数加功能」，是「用一个新函数顶替旧名字，并在新函数里选一个时机调用旧函数」。理解成名字的重新指向，三层嵌套就不神秘了。

五、functools.wraps：不加会坏掉什么

上一节那个 timed 能跑，但它有个副作用：fetch 这个名字现在指向的是 wrapper，而 wrapper 身上带的是它自己的元信息。于是 fetch.__name__ 变成 'wrapper'、fetch.__doc__ 变成 None、__module__ 和 __qualname__ 也指向定义装饰器的那个模块而不是被装饰函数所在的模块。原函数还在，只是所有自省手段都问不到它了。

fetch.__name__              # 'wrapper'  ← 没加 wraps
fetch.__doc__               # None       ← 原来的文档字符串没了
fetch.__qualname__          # 'timed.<locals>.wrapper'
inspect.signature(fetch)    # (*args, **kwargs)  ← 真实签名丢失
help(fetch)                 # 只能看到 wrapper(*args, **kwargs)

functools.wraps 就是来补这个洞的。它本身也是一个装饰器（准确说是 functools.update_wrapper 的装饰器形式），做的事很朴素：把原函数的 __name__、__doc__、__module__、__qualname__、__annotations__ 复制到 wrapper 上，把原函数的 __dict__ 合并进来，并额外设置一个 __wrapped__ 指回原函数。最后这一项是关键：inspect.signature 默认会顺着 __wrapped__ 往下找，所以加了 wraps 之后签名自省能穿透包装层拿到真实签名。

from functools import wraps

def timed(fn):
    @wraps(fn)                        # 就加这一行
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

fetch.__name__              # 'fetch'  ← 回来了
fetch.__wrapped__           # <function fetch>  ← 原函数的入口

表格最后三行是真正会造成生产故障的部分。靠 inspect.signature 读签名来决定行为的框架相当多：FastAPI 根据形参名和注解决定从路径、查询串还是请求体里取值；pydantic 的 validate_call 按注解校验实参；各种 CLI 生成库把形参映射成命令行选项。一旦签名被压成 (*args, **kwargs)，这些框架看到的是「一个不接受任何具名参数的函数」，行为直接崩坏，而报错位置往往在框架内部，离你那个漏写 wraps 的装饰器隔了十几层调用。

示例场景：某服务给 40 多个接口统一加了一个鉴权装饰器，作者漏写了 @wraps。上线后三件事同时坏掉：接口文档里 40 多个端点的参数列表全部塌缩成同一个 args / kwargs；带路径参数的 9 个接口一律返回 422，报错是 field required: args；日志里所有函数名字段都变成 wrapper，按函数名做的 6 条告警规则同时失效。加上 @wraps(fn) 这 1 行后三个问题一起消失。这也是个通用信号：写装饰器时 wraps 不是可选的礼貌，是正确性的一部分。

wraps 搬的不是「好看的名字」，是别人赖以工作的身份证。日志、测试、文档、框架的参数注入全都通过自省读这些属性，少这一行等于让被装饰的函数集体改名叫 wrapper。

还有一点要说清楚：wraps 只复制元信息，并不能让包装层在类型检查器眼里「透明」。静态检查工具看到的仍然是 wrapper 的签名，除非你用 ParamSpec 把参数规格显式标出来。运行时自省和静态类型检查是两套独立的通道，wraps 只修好了前一条，这也是第六节末尾「装饰器不适合的场合」里的一条。模块与包的组织方式见 PY08 · 模块、包与项目结构，装饰器改写 __module__ 造成的归因偏差和那一节讲的导入机制是同一套上下文。

六、带参数的装饰器与常用范式

要让装饰器接受自己的参数，比如 @repeat(3)，就得再多一层。原因很机械：@ 后面跟的必须是「一个接受函数的可调用对象」，而 repeat(3) 是一次函数调用——所以 repeat 不是装饰器，它是装饰器工厂，调用它得到的返回值才是装饰器。三层嵌套看起来复杂，但它就只是这一个原因导致的，没有别的门道。

def repeat(times):                # 第一层：收装饰器自己的参数
    def deco(fn):                 # 第二层：这才是真正的装饰器
        @wraps(fn)
        def wrapper(*a, **kw):    # 第三层：每次调用都走这里
            for _ in range(times):
                r = fn(*a, **kw)
            return r
        return wrapper
    return deco                   # @repeat(3) == deco，再 == deco(fn)

顺着这个等式念一遍就不会记错：@repeat(3) 先执行 repeat(3) 得到 deco，然后 @deco 再执行 deco(fn) 得到 wrapper。所以带参装饰器比不带参的多一次函数调用，也多一层闭包（times 被 deco 和 wrapper 共同持有）。一个实用建议：不要试图写「既能 @deco 又能 @deco(x)」的两用装饰器，那需要在第一层判断实参是不是可调用对象，代码会变得难读，收益只是省一对括号。

记忆化：lru_cache 的便利和它的账单

标准库里最常用的装饰器大概是 functools.lru_cache，它做的是记忆化——把入参组合当键，缓存函数的返回值，同样的入参第二次直接返回缓存。对纯函数（相同输入必然相同输出、无副作用）来说这是几乎免费的加速。但它有两个必须知道的约束。

from functools import lru_cache

@lru_cache(maxsize=512)           # maxsize=None 表示不限容量
def resolve(host: str) -> str: ...

resolve.cache_info()              # 命中率自查：hits / misses / currsize
resolve.cache_clear()             # 配置变更后要手动失效

第一个约束是参数必须可哈希：传 list、dict、set 会直接抛 TypeError: unhashable type: 'list'。这也顺带说明它为什么不能用来缓存「接受配置字典」的函数——要么改成接受 tuple，要么别用它。第二个约束更容易造成事故：缓存对参数和返回值都持强引用，只要缓存项还在，这些对象就不会被回收。maxsize=None 加上一个取值范围很大的参数（用户 ID、URL、时间戳），等于写了一个只增不减的字典。

示例场景：一个查询服务给 lookup(user_id) 加了 @lru_cache(maxsize=None)，本意是缓存热点用户。实际流量里 user_id 有约 80 万个不同取值，每个返回值约 2KB，运行 4 天后这个缓存独占约 1.6GB，容器在第 5 天触发 OOMKilled 重启，而重启后又要几天才复现，一度被当成偶发问题。改成 maxsize=4096 后内存稳定在约 8MB，命中率仍有 71%——cache_info() 读出来的。这里的教训不是别用 lru_cache，而是给缓存设上限，并且用 cache_info() 而不是直觉来判断容量够不够。

类装饰器与叠放顺序

装饰器返回的不必是函数，只要是可调用对象就行。所以可以用一个实现了 __call__ 的类实例来顶替原函数，好处是状态存在实例属性里、可以额外挂方法、调试时打印出来比闭包直观。代价是它不是函数，绑定到类上会少掉描述符协议那一层，装饰实例方法时容易出问题。

class Counted:                    # 类装饰器：用实例顶替函数
    def __init__(self, fn):
        wraps(fn)(self)           # 元信息照样要搬
        self.fn, self.n = fn, 0
    def __call__(self, *a, **kw):
        self.n += 1               # 状态放实例属性，不用 nonlocal
        return self.fn(*a, **kw)

多个装饰器叠在一起时，顺序问题几乎每次都要现推一遍。记住两句话就够：应用是由下往上（离 def 最近的先被应用），执行是由上往下（最外层的 wrapper 先拿到调用）。这两个方向相反，正是混淆的来源。

@timed ← 写在上面 = 最外层 @retried ← 写在下面 = 离 def 最近 def fetch(): ... ───────────────────────────────────────────────────────── 应用顺序（导入时，由下往上包） fetch = timed( retried( fetch ) ) ② ① 原函数 执行顺序（调用时，由上往下剥） fetch(url) └─► timed.wrapper 开始计时 └─► retried.wrapper 进入重试循环 └─► 原函数 真正干活 ◄─┘ 重试若干次都在 timed 的计时范围内 ◄─────┘ 打印总耗时（含所有重试） 顺序反过来写会改变语义： @retried / @timed ⇒ 每次重试各自计时，打印 N 条日志 @timed / @retried ⇒ 只打 1 条，数字是所有重试的总和 哪个对取决于你想量什么，但一定要是有意选的

顺序不是风格问题，它改变行为。鉴权和限流的相对顺序决定了未授权请求是否消耗限流配额；缓存和日志的相对顺序决定了命中缓存时还会不会打日志；事务和重试的相对顺序决定了重试是在事务内还是各起一个新事务——最后这个搞反了会造成数据一致性问题。

什么时候不该用装饰器

装饰器的适用前提是「附加逻辑与原函数签名无关」。一旦要改变签名（增删形参、改变参数含义），装饰器就成了负担：调用方看到的签名和实际接受的参数不一致，自省失真，类型检查器无法理解，IDE 补全也会给错。这种情况下显式的包装函数或者调整原函数本身都更好。另外，需要被静态类型检查完整理解的公共 API，装饰前最好用 ParamSpec 把参数规格标出来，否则包装层会把类型信息吞掉。

范式典型写法合适的场景要留神的地方
无参装饰器@timed日志、计时、异常兜底必须 wraps + 原样透传
带参装饰器@repeat(3)重试次数、缓存 TTL、权限等级三层，别忘最外层要 return deco
记忆化@lru_cache(512)纯函数、入参收敛、计算或 IO 较贵参数需可哈希；设 maxsize 防内存增长
类装饰器@Counted需要维护较多状态或对外暴露方法不是函数，装饰实例方法要额外处理
叠放多个@a + @b正交关注点组合由下往上应用、由上往下执行
（不建议）改签名包装后增删形参—自省与类型检查都会失真，改用显式包装
  • 写装饰器第一行就把 @wraps(fn) 敲上，当成模板的一部分
  • 中层一律用 *args, **kwargs 透传，并且记得 return 结果
  • 循环里造函数时用 lambda x=x: 或 partial 把值当场绑定
  • lru_cache 显式给 maxsize，上线后用 cache_info() 校准
  • 需要在闭包里改写外层变量时用 nonlocal，别改成全局变量
  • 叠放多个装饰器时，在注释里写清为什么是这个顺序
  • 漏写 wraps——日志函数名、文档、签名注入会一起坏掉
  • 在循环里写 lambda: f(i) 然后指望三个闭包记住三个值
  • 给非纯函数（读数据库、依赖当前时间）加 lru_cache
  • @lru_cache(maxsize=None) 配上取值无界的参数
  • 用装饰器增删形参，让调用方看到的签名和实际不一致
  • 写「既能带参又能不带参」的两用装饰器，省一对括号换一堆歧义

装饰器是给正交关注点用的：计时、日志、重试、鉴权、缓存这些与业务逻辑无关、又到处都要的横切能力。一旦你发现装饰器开始关心业务参数的含义，它就该退回成一个普通函数调用了。

Q&A

为什么定义处和调用处的 * 含义正好相反，这是设计失误吗？
不是失误，而是刻意的对称。语言设计上希望「怎么收」和「怎么发」看起来一致，这样 f(*args, **kwargs) 这种转发写法读起来就像把形参表原样搬到实参表，视觉上不用转译。代价是初学者必须多记一条判断规则：看星号写在 def 那一行还是写在调用那一行。一个实用的记法是把定义处当漏斗、调用处当喷头，方向和字面顺序一致——定义在前面所以先收集，调用在后面所以再撒开。真正需要小心的只有一种情况：同一行里两种用法都出现，比如 def f(*args): g(*args)，这时要分清哪个是形参表哪个是实参表。
闭包捕获的到底是变量还是值？这个区别在什么时候会咬到我？
捕获的是变量，更准确说是持有一个装着变量的单元对象。函数被调用时才去盒子里读当前内容，而不是在定义时把值拷一份。这个区别在「创建函数」和「调用函数」两个时刻之间存在变化时才会显形：如果外层变量在这段时间里被改了，闭包读到的是新值。最典型的场景就是循环——循环变量每轮都被改写，所以循环里创建的所有闭包最后都读到同一个末值。如果你确实想要「记住当时那个值」的语义，必须在定义时就把值取出来，常见手段是默认参数或 functools.partial。
用默认参数修延迟绑定有什么隐患？
最大的隐患是它把一个纯内部细节升格成了公开形参。写成 lambda t=t: sync(t) 之后，这个可调用对象的签名里就真的多了一个名为 t 的参数，任何拿到它的人都可以 f(t="别的值") 覆盖掉，而你本来只是想固化一个值。如果这个对象只在本地循环里用完就丢，问题不大；如果它会被注册到某个框架、放进回调表、或者暴露给外部代码，就要考虑用 functools.partial 或工厂函数来实现，它们不会污染签名。另外还有个次要的坑：默认参数只在定义时求值一次，如果默认值是可变对象（列表、字典），所有调用会共享同一份，这是另一个独立的经典陷阱。
我的装饰器跑起来函数就变成 None 了，怎么回事？
几乎一定是漏了 return，而且要分两种情况看。第一种是外层忘了 return wrapper：这时 deco(fn) 返回 None，被装饰的名字就绑到了 None 上，调用时报 TypeError: 'NoneType' object is not callable，报错还算直白。第二种更阴险，是中层 wrapper 里忘了 return fn(...) 的结果：原函数照样正常执行，副作用都发生了，但返回值被吞掉，所有调用点拿到 None，不报任何错。第二种通常要到很远的地方才暴露成 AttributeError: 'NoneType' object has no attribute ...，和装饰器看不出关系。所以写装饰器时把两个 return 当成模板的固定部分，先敲上再填逻辑。
不加 functools.wraps 除了名字难看，还会有实际影响吗？
会，而且影响可以严重到线上故障级别。名字和文档只是表面：__name__ 变成 wrapper 会让所有按函数名聚合的日志、埋点和告警规则失效；__qualname__ 错位会让 pytest 报告里的用例名全都一样，也会让 pickle 找不到对象。真正致命的是签名——inspect.signature 只能看到 (*args, **kwargs)，而 FastAPI、pydantic 这类靠读签名做参数解析和校验的框架会因此完全误判，表现为请求参数校验失败或者依赖注入拿不到值，报错位置还在框架内部。wraps 做的事就是把元信息搬过来并设置 __wrapped__，后者让签名自省能穿透包装层找到原函数。所以它不是可选的润色，是装饰器正确性的一部分。
多个装饰器叠在一起，执行顺序到底是怎样的？
应用和执行是两个相反的方向，这是混淆的根源。应用发生在导入时，由下往上：离 def 最近的那个先被应用，所以 @a 加 @b 等价于 f = a(b(f))。执行发生在调用时，由上往下：最外层也就是写在最上面那个的 wrapper 先拿到调用，然后一层层往里传，最后才到原函数。这个顺序会改变语义而不只是改变日志长相，比如计时和重试叠放时，计时在外量到的是所有重试的总耗时并只打一条日志，计时在内则是每次重试各自计时打多条日志。更严重的例子是事务和重试：顺序反了会决定重试是在同一个事务里还是各起一个新事务。所以叠放顺序应该是有意选择的，并且值得写一句注释说明理由。
lru_cache 什么时候不能用？
三类情况要避开。一是函数不纯——依赖数据库当前状态、当前时间、随机数或者有副作用，缓存会让它返回过期结果，而且这种 bug 极难复现。二是参数不可哈希，传 list 或 dict 会直接抛 TypeError: unhashable type，如果一定要用就得把参数改成 tuple 或 frozenset。三是参数取值范围无界，比如以用户 ID、完整 URL 或时间戳为键，这时 maxsize=None 等于写了一个只增不减的字典，缓存对键和值都持强引用，内存会一路涨到容器被杀。判断方法很直接：上线后读 cache_info()，看 currsize 是不是在持续增长、hits/misses 的比值是否值得这份内存。需要按时间失效或跨进程共享的缓存，应该用专门的缓存库或外部缓存服务，lru_cache 只解决「同一进程内、纯函数、入参收敛」这一种情况。
什么时候该用闭包，什么时候该用类？
看状态的规模和对外暴露的接口数量。如果只需要记住一两个值、对外只暴露一个调用入口，闭包更贴切——代码更短，状态天然私有，外面根本拿不到，也不需要为此定义一个只有 __init__ 和一个方法的类。一旦出现这几个信号就该换成类：需要多个方法共享同一份状态、需要在外部读取或重置状态、状态字段超过两三个、或者调试时需要能打印出可读的对象。还有一个现实考虑是可测性，类的属性可以在测试里直接断言，闭包里的状态只能通过 __closure__[0].cell_contents 这种方式间接读，写在测试里很难看。装饰器这个场景两者都行，标准库里 lru_cache 用的是闭包加函数属性的混合方案。
