PY09 · 对象模型与引用语义

身份/类型/值三件套 · 名字绑定与引用计数 · 可变性分界线 · is 与 == · __eq__ 与 __hash__ 契约 · 值对象设计

Python 里不存在「变量里装着值」这回事。变量只是一张贴纸，对象才是箱子；赋值是把贴纸撕下来贴到另一个箱子上，从头到尾没有人搬动过箱子里的东西。前八张卡讲的所有奇怪现象——传参改了外面的列表、默认参数记住了上次调用、两个相等的对象在 set 里没被去重——根都在这一句话里。

一、一切皆对象：身份、类型、值三件套

「一切皆对象」这句话被说得太多，以至于失去了信息量。它真正的含义不是一句口号，而是一条可以被验证的结构性规定：Python 运行时里凡是能被名字指向的东西，都是同一种数据结构的实例，都带着完全相同的三样元数据。搞清楚是哪三样，后面五节的所有结论都能自己推出来。

身份是对象在其生命周期内唯一且不变的标识，用 id() 读取；在 CPython 里它恰好就是对象的内存地址，但这只是实现细节，语言只保证「同时存活的两个对象身份必然不同」。类型决定这个对象能做什么——支持哪些运算、有哪些方法、占多大空间，用 type() 读取，而且对象创建后类型基本不可更改。值是它承载的内容，也是三者中唯一可能变、也可能不能变的一项，第三节整节都在讲这件事。

「都是对象」到底覆盖到哪

把范围划清楚很重要，因为它直接决定了你能写出什么样的代码。函数是对象，所以能赋值给变量、当参数传、装进字典当分派表；类也是对象，所以能放进列表、能当返回值；模块同样是对象，import 之后你拿到的就是一个类型为 module 的实例。PY05 · 函数入门与参数传递 里那些「把函数当值传」的写法，合法性的根据就在这里。

类型的类型还是类型

表格最后两行藏着一个有意思的事实：type(42) 是 int，而 type(int) 是 type，再往上 type(type) 还是 type。这个自指不是脑筋急转弯，而是把「类型也是对象」这条规则贯彻到底之后的必然结果——如果类型必须是对象，对象又必须有类型，那么这条链必须在某处闭合，否则就会无限向上。

type(42)        # <class 'int'>      42 的类型是 int
type(int)       # <class 'type'>     int 的类型是 type
type(type)      # <class 'type'>     到此闭合，不再往上

isinstance(int, type)     # True，类确实是 type 的实例
isinstance(42, object)    # True，一切都是 object 的后代

你现在还不需要用到这个结构，但它解释了一件日常可见的事：为什么 int、list 这些内置类型可以直接当函数调用（int("42")）。因为它们是 type 的实例，而调用一个类就是在请求 type 帮你造一个实例——这和调用普通函数走的是同一套机制。

身份回答「你是谁」，类型回答「你能干什么」，值回答「你装了什么」。后面所有的坑，都是因为把「你是谁」和「你装了什么」这两个问题搞混了。

二、引用语义：名字、绑定与引用计数

写 a = [1, 2, 3] 时，实际发生的事情分成两步且顺序固定：先在堆上创建一个列表对象，然后把名字 a 绑定到它上面——绑定就是在某个命名空间（本质是字典）里记下「a 这个键指向那个对象」。再写 b = a 不会复制任何东西，它只是让 b 这个键指向同一个对象。两个名字，一个对象，从此改哪边另一边都看得见。

这一点和 C 系语言差别很大，值得用最直白的方式说清楚：Python 的赋值号右边永远求值出一个对象，左边永远只是给它挂个名字。没有「拷贝构造」，没有「值语义」，也没有办法让赋值变成复制——想要副本必须显式地要（list(a)、a.copy()、copy.deepcopy(a)）。

引用计数：对象什么时候真的消失

每个对象头部都有一个计数器，记录当前有多少条引用指着它。引用计数归零的那一刻，CPython 立即回收这块内存——注意是「立即」，不是「等下次 GC」。这个即时性是 CPython 的重要特征，也是文件句柄不显式关闭往往也能被释放的原因（虽然你仍然不该依赖它，PY07 · 文件读写与异常处理 讲过要用 with）。

引用计数的一生 ───────────────────────────────────────────────────── obj = [1, 2, 3] 创建对象，obj 指向它 ┌──────────────┐ │ list [1,2,3] │ refcnt = 1 └──────────────┘ alias = obj +1 多一个名字指着 refcnt = 2 bucket = [obj] +1 容器槽位也算一条引用 refcnt = 3 def use(x): ... use(obj) +1 调用期间形参也是一条引用 (返回后自动 -1) refcnt = 4 → 3 del alias -1 删掉的是名字，不是对象 refcnt = 2 bucket.clear() -1 容器放手 refcnt = 1 obj = None -1 最后一条引用改指别处 refcnt = 0 ┌──────────────┐ │ 立即回收 │ ← 不用等 GC └──────────────┘

图里 del alias 那一步是最容易误解的地方。del 是一个作用在名字上的语句，它做的事是把这个键从命名空间里摘掉，并把对应对象的计数减一。对象被不被销毁，取决于减完之后是不是零。所以「我 del 了它为什么还在」和「我只是 del 了一个别名，怎么整个数据都没了」这两类困惑，答案是同一条规则的两面。

用 sys.getrefcount 观察，但要减掉那个 1

sys.getrefcount(x) 能读出当前计数，但它的返回值总是比你预期的大 1——因为把 x 传进这个函数本身就创建了一条临时引用（形参）。这个 +1 不是 bug，是引用语义的必然结果，恰好也是对「传参会增加引用计数」这件事最好的现场证明。

import sys

data = [1, 2, 3]
print(sys.getrefcount(data))   # 2 ← 1 条来自 data，1 条来自形参

alias = data
print(sys.getrefcount(data))   # 3

del alias
print(sys.getrefcount(data))   # 2  回到原状
操作对引用计数的影响常被误解成
b = a+1「复制了一份」——没有，只是多了个名字
lst.append(a) / d["k"] = a+1「容器存了内容」——存的是引用
f(a) 调用期间+1（返回后 -1）「参数是副本」——形参是又一个名字
del a-1「删除了对象」——只删了名字
a = None / a = 其他值原对象 -1「清空了变量」——是改了指向
函数返回，局部名字消失该帧内所有绑定各 -1「局部变量自动销毁」——销毁的是绑定
sys.getrefcount(a)读数比真实值多 1「结果不准」——多的正是形参那条

容器装的是引用，这条几乎解释了一半的 bug

列表、字典、集合里放的从来不是对象本身，而是指向对象的引用。所以一个列表出现在三个地方，不等于有三份数据；对其中任何一处做原地修改，另外两处立刻反映出来。这也是 [[0] * 3] * 3 造出来的「二维列表」改一行全变的根本原因——* 3 复制的是引用，三行本来就是同一个列表。PY03 · 容器四件套 里提过这个现象，现在你能从机制上解释它了。

示例场景：某配置加载模块把解析好的默认配置缓存成一个模块级字典 DEFAULTS，各处调用 get_config() 时直接返回它。上线后出现的现象是：第 1 个请求正常，从第 2 个请求起返回的配置里多了上一个请求写入的 3 个租户私有字段。原因是所有调用方拿到的是同一个字典的引用，任何一处 cfg["tenant"] = ... 都在改全局状态。修复只有一行——返回 copy.deepcopy(DEFAULTS)，代价是每次约 40 微秒，换掉了一类会随并发量放大的串号故障。

赋值不复制，传参不复制，放进容器也不复制。Python 里只有一种复制——你自己动手写出来的那一种。

三、可变与不可变：这是最重要的一条分界线

上一节说「改动会被所有引用看见」，但这句话有个前提：这个对象得能被改。可变性指的正是对象在创建之后，其值能否在保持身份不变的前提下被修改。这条线把所有 Python 类型劈成两半，而几乎每一个「结果和我想的不一样」的场景，都发生在你误判了手里那个对象在哪一半。

不可变类型不是「不让你改」，而是根本没有提供原地修改的手段——str 上找不到任何一个会改变自身的方法，tuple 也没有 append。所以当你写 s = s + "x" 或者 n += 1 时，实际发生的是：算出一个全新的对象，然后把名字重新绑定过去。旧对象要么被别的名字继续持有，要么计数归零被回收。这就是为什么在循环里拼接字符串会有性能问题，PY06 · 字符串与编码 讲过该用 "".join()。

不可变换来了三样东西

不可变看起来是限制，其实是在用「不能改」换三项具体能力，而这三项能力恰好是 Python 数据结构设计的支柱。

第一是可以作字典键。字典靠哈希值定位桶位，如果键在放进去之后还能变，它的哈希值就会飘，下次查找会去错误的桶里找，表现为「明明放进去了却 KeyError」。语言干脆从源头堵死：可变类型不实现稳定的 __hash__，直接拒绝入场。

第二是可以安全共享。既然谁也改不了，那么把同一个字符串对象同时给一百个线程、一百个缓存槽都没有风险，不需要加锁，也不需要防御性拷贝。第二节那个配置字典的故障，换成不可变结构就根本不会发生。

第三是可以被缓存与驻留。正因为不可变对象之间无法互相影响，解释器才敢把它们合并：小整数在启动时就预创建好了一批共享实例，符合标识符规则的短字符串会被驻留成同一个对象。这是纯粹的内存与速度优化，对语义完全透明——直到你用 is 去比较它们，这就是下一节的主题。

判断一个对象能不能当字典键，不用背表：问自己「它能不能被原地改」。能改的一律不能当键，因为键的哈希值必须一辈子不变。

四、is 与 == 的分界

回到第一节的三件套：is 问的是身份，== 问的是值。a is b 等价于 id(a) == id(b)，它只看两个名字是不是指着同一个对象，永远不会去读对象的内容，因此速度是恒定的一次指针比较。a == b 则会调用 a.__eq__(b)（必要时反过来问 b），走的是类型自己定义的逻辑，可能遍历整个列表，也可能发起一次数据库查询——只要有人这么写。

这带来一个不对称：相等性运算符 == 是可重载的，任何类都能决定它返回什么，甚至可以返回一个数组（NumPy 就是这么干的，arr1 == arr2 给你一个布尔数组，直接放进 if 会抛 ValueError: The truth value of an array with more than one element is ambiguous）。而 is 由解释器实现，任何代码都改不了它的行为。这个「改不了」有时是优点，有时是陷阱，区别只在于你用它比的是身份还是值。

把这张表压缩成一句可执行的规则：is 只用在和 None、True、False 这三个单例比较，以及你确实要问「是不是同一个对象」的时候；其余一律用 ==。之所以这三个可以用 is，是因为它们在整个解释器进程里各自只有一个实例，身份相等和值相等在它们身上必然同时成立。

小整数与字符串驻留：让 is 「碰巧对了」的实现细节

CPython 会预先创建 -5 到 256 的整数对象共享使用，也会把源码里出现的、形如标识符的短字符串驻留成同一个对象。结果就是 a = 100; b = 100; a is b 返回 True，而同样的写法换成 1000 就可能返回 False。这类驻留行为在 PY02 · 变量与内置类型 里已经展开过，这里只需要记住它的定性：这是 CPython 的内存优化，不是语言规范的承诺。它随版本变、随构建变、随你是在 REPL 里还是在模块里执行而变。

a, b = 256, 256
a is b          # True  —— 落在小整数缓存区间内

c, d = 257, 257
c is d          # 在同一行/同一代码块里编译可能为 True
                # 跨语句、跨函数、从外部输入解析出来则多为 False

x = 257
y = int("257")  # 运行时计算出来的，不走缓存
x is y          # False —— 但 x == y 永远是 True

最后两行说明了为什么这个坑特别难发现：只要数据是写死在代码里的字面量，is 往往「碰巧」正确；一旦数据来自 JSON、数据库、命令行参数——也就是真实生产环境里的所有数据来源——它就开始失败。测试用例通常写字面量，于是全绿；线上数据走解析路径，于是偶发。

示例场景：某订单服务用 if status_code is 200: 判断上游返回码，本地与预发环境全部通过，上线后约 0.7% 的请求被误判为失败并触发重试。原因是预发的 mock 直接返回字面量 200（落在 −5~256 小整数缓存里，is 恰好成立），而线上返回码来自响应头解析，走 int() 构造出新对象；更关键的是灰度期间上游改用了 201，超出缓存区间后 is 稳定为 False。把 is 改成 == 后误判归零，改动 1 个字符，定位却花了 6 小时。顺带一提，现代 Python 对这种写法会给出 SyntaxWarning: "is" with a literal. Did you mean "=="?，把警告当错误处理就能在编译期拦下它。

is 问的是「你俩是不是同一个人」，== 问的是「你俩长得一样吗」。除了跟 None 打招呼，日常你想问的几乎总是后者。

五、等价性契约：__eq__ 与 __hash__ 必须一起改

自定义类如果什么都不写，会继承 object 的默认行为：__eq__ 退化成身份比较（a == b 等价于 a is b），__hash__ 则基于 id() 计算。这套默认值内部是自洽的——同一个对象必然相等、必然同哈希，不同对象几乎必然不等、几乎必然不同哈希，所以实例可以随便放进 set 和字典。问题出在你想让「内容相同的两个实例算相等」的那一刻。

一旦你只重写 __eq__，Python 3 会自动把这个类的 __hash__ 设为 None。这不是 bug，是语言刻意做的保护：你改变了相等的定义，却没有同步更新哈希，两者已经矛盾，与其让它在半年后表现为诡异的数据丢失，不如现在就让实例根本无法被哈希。表现就是一行清晰的报错：

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

契约本身：一个单向要求

哈希容器依赖的哈希契约只有一条核心规则：相等的对象必须有相同的哈希值。反过来不要求——两个哈希相同的对象完全可以不相等，这叫哈希冲突，是正常现象，容器自己会处理。理解这个方向性很关键：哈希值的作用是快速缩小候选范围，最终判定相等还是要靠 __eq__。

set / dict 查一个元素时，两个方法怎么配合 ═══════════════════════════════════════════════════════ x in my_set │ ▼ ┌──────────────────┐ │ hash(x) │ ① 算哈希 → 定位到某个桶 └────────┬─────────┘ O(1)，只看哈希值 ▼ ┌──────────────────────────────────────┐ │ 桶 #37: [ obj_a, obj_b ] │ ② 桶里可能有多个 └────────┬─────────────────────────────┘ （哈希冲突） ▼ ┌──────────────────┐ │ x == obj_a ? │ ③ 逐个用 __eq__ 精确比对 │ x == obj_b ? │ 只在同桶内比，所以仍然很快 └────────┬─────────┘ ▼ True / False 契约被破坏时会怎样 ───────────────────────────────────────────────────── 两个「相等」但哈希不同的对象： a hash=17 ──► 桶 #17 ──┐ 彼此永远不会被放进同一个桶 b hash=93 ──► 桶 #93 ──┘ → ③ 这一步压根不会发生 → set 认为它们是两个不同元素 → 去重失效，且不报任何错

图的下半部分是整节最重要的一张图：契约被破坏不会抛异常，只会静默地给出错误结果。a == b 明明是 True，但 {a, b} 的长度是 2；用 a 存进字典，用 b 去取会 KeyError。没有报错、没有警告，只有数据慢慢变得不对。这类问题的排查成本极高，因为症状出现的地方离根因很远。

你怎么定义__hash__ 状态能进 set / 当键吗后果
两个都不写（默认）基于 id()能按身份去重，内容相同的两个实例算两个
只写 __eq__被自动置为 None不能立刻抛 TypeError: unhashable type
只写 __hash__你的实现能相等仍按身份判，去重几乎不生效
两个都写且一致你的实现能✅ 正确：按值去重、按值查找
两个都写但不一致你的实现能❌ 静默错误：去重失效、KeyError，不报警
@dataclass(eq=True)被置为 None不能和「只写 __eq__」等价
@dataclass(frozen=True)自动按字段生成能✅ 推荐写法，两者天然一致

哈希必须在对象一生中保持不变

契约还有条隐含要求：只要对象还在某个哈希容器里，它的哈希值就不能变。这直接推出一条实践铁律——不要让可变字段参与哈希计算。如果你用 self.tags（一个会被 append 的列表）去算哈希，那么对象放进 set 之后任何一次 append 都会让它的哈希漂移，从此它就「躺在错误的桶里」，谁也找不到它，连它自己都找不到。

示例场景：某爬虫用自定义 Article 类做 URL 去重，重写了 __eq__（比较归一化后的 URL）和 __hash__，但哈希里混入了 self.fetched_at 这个抓取后才回填的时间戳字段。对象入 set 时该字段为 None，抓取完成后被赋值，哈希随之改变。结果是一轮 12 万条 URL 的任务里有约 1.8 万条被重复抓取，日志里没有任何异常，只有出口带宽比预期高了 15%。把哈希改成只依赖不可变的归一化 URL 后，重复数降到 0。教训是：哈希只能建立在对象创建后不再改变的那部分状态上。

最省事的实现方式是把参与相等判断的字段打包成一个元组，直接复用元组的哈希——元组会把成员的哈希混合成一个值，既正确又快，还天然保证了 __eq__ 和 __hash__ 用的是同一组字段。

class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y
    def _key(self):
        return (self.x, self.y)          # 同一组字段，两处共用
    def __eq__(self, other):
        return isinstance(other, Point) and self._key() == other._key()
    def __hash__(self):
        return hash(self._key())         # 复用 tuple 的哈希

__hash__ 负责「大概在哪一格」，__eq__ 负责「是不是这一个」。你只改了后者，容器就会拿着旧地图去找新位置——找不到，而且不会告诉你。

六、对象的生命周期与相等性设计实践

第二节说引用计数归零就立即回收，但这套机制有个补不上的缺口：循环引用。a.peer = b; b.peer = a 之后，就算外部所有名字都消失了，这两个对象互相把对方的计数撑在 1，谁也降不到 0，内存就这么漏着。CPython 为此配了第二套机制——分代垃圾回收器，它定期扫描容器类对象，专门找出这种「彼此引用但外界已经够不着」的孤岛并回收掉。

CPython 的两套回收机制分工 ══════════════════════════════════════════════════════ ① 引用计数（主力，实时） 每次绑定/解绑都改计数 → 归零立即回收 优点：及时，内存曲线平稳，资源释放可预测 盲区：循环引用永远降不到 0 a ──► b ▲ │ └─────┘ 外界已无引用，但两边都 refcnt=1 ② 分代 GC（兜底，周期性） 把容器对象按存活时间分成 3 代 ┌─────────┐ 熬过一轮 ┌─────────┐ 熬过一轮 ┌─────────┐ │ 第 0 代 │ ───────► │ 第 1 代 │ ───────► │ 第 2 代 │ │ 扫得最勤 │ │ 扫得较少 │ │ 扫得最少 │ └─────────┘ └─────────┘ └─────────┘ 假设：活得久的对象更可能继续活着，不值得反复扫 分工：计数管 99% 的日常回收，GC 只负责打扫循环引用 （分代阈值调优、gc 模块的用法留给 PY23 内存与性能那张卡）

不要依赖 __del__

类可以定义 __del__，它在对象被回收时调用，看起来很像 C++ 的析构函数，但它的保证弱得多，弱到不该用它做任何要紧的事。调用时机不确定（循环引用中的对象要等 GC 跑到才回收）；解释器退出时可能根本不被调用；里面抛出的异常会被吞掉，只在 stderr 打一行 Exception ignored in: ... 然后继续；更糟的是它自己可能复活对象，把回收流程搅乱。

释放资源的正确工具是上下文管理器，也就是 PY07 · 文件读写与异常处理 里那个 with。它的释放时机由代码结构决定，异常路径也覆盖得到，和垃圾回收器什么时候心血来潮没有关系。__del__ 最多只适合当一道「忘了关」的兜底日志。

weakref：引用它，但不养着它

弱引用是一种不增加引用计数的引用方式：它能访问目标对象，但不会阻止对象被回收；一旦目标消失，弱引用调用后返回 None。它解决的是「我需要指向你，但不该由我决定你的存活」这类关系。

场景用普通引用的问题弱引用怎么解
缓存已加载的大对象缓存持有引用，对象永不释放，内存只涨不跌WeakValueDictionary，无人使用时自动出缓存
父子节点互指形成循环引用，只能等分代 GC 兜底子指父用弱引用，环被打破，计数即可回收
观察者 / 回调注册表注册表把已退场的观察者一直吊着WeakSet 存观察者，对象消失自动摘除
给对象挂额外元数据外部字典以对象为键，对象永远回收不掉WeakKeyDictionary，键消失条目自动清理
需要在对象消亡时做清理__del__ 时机不可控、异常被吞weakref.finalize，时机明确且可提前触发

要注意并非所有对象都支持弱引用：int、str、tuple 这些内置不可变类型不行，定义了 __slots__ 又没加 "__weakref__" 的自定义类也不行，会抛 TypeError: cannot create weak reference to 'str' object。

值对象该怎么设计

把这六节的结论收拢，就得到一条明确的设计建议：值对象——那些「内容相同就该视为同一个」的东西，比如坐标、金额、日期区间、配置项——应该做成不可变的，并且同时实现相等、哈希和可读的字符串表示这三件事。不可变让它可以安全共享、能当字典键；相等与哈希成对出现让它在 set 和 dict 里行为正确；__repr__ 让它在日志和调试器里说得出自己是谁，而不是打出一串 <Point object at 0x7f3a...>。

在现代 Python 里，这三件事有一个一行的答案：给类加上 @dataclass(frozen=True)。它会自动生成按字段比较的 __eq__、按字段计算的 __hash__、可读的 __repr__，并且拦截所有属性赋值（改一下会抛 FrozenInstanceError）。两者由同一组字段生成，契约天然不会被违反。

from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Money:
    amount: int              # 以「分」为单位，避免浮点误差
    currency: str = "CNY"

a, b = Money(1999), Money(1999)
a == b, len({a, b})          # True, 1 —— 按值判等、按值去重
new = replace(a, amount=2999)  # 「修改」= 造一个新的
  • 和 None / True / False 比较时用 is，其余一律用 ==
  • 重写 __eq__ 时同步重写 __hash__，两者基于同一组字段
  • 哈希只依赖创建后不再变化的字段，最省事的写法是 hash(self._key())
  • 值对象用 @dataclass(frozen=True)，相等、哈希、repr 一次给齐
  • 要副本就显式写出来：list(x) / x.copy() / copy.deepcopy(x)
  • 需要「引用但不延寿」的关系时用 weakref，缓存优先考虑 WeakValueDictionary
  • 释放资源一律走 with，让时机由代码结构决定
  • 用 is 比较数字或字符串——小整数缓存会让它在测试里碰巧通过
  • 只重写 __eq__ 就往 set 里塞，会直接吃到 unhashable type
  • 让列表、字典这类可变字段参与哈希计算，对象会在容器里「走失」
  • 把可变对象当函数默认参数，它在函数定义时只创建一次并被长期持有
  • 用 __del__ 关文件、断连接、写日志——时机不可控且异常被吞
  • 返回模块级可变对象（配置字典、缓存列表）却不拷贝，调用方一改就是全局事故
  • 用 [[0] * 3] * 3 造二维结构，三行是同一个列表的三条引用

设计一个类之前先问一句：它是「一个东西」还是「一个值」。东西按身份走，默认行为就够；值按内容走，那就必须冻起来，并且把相等和哈希一起交出去。

Q&A

Python 的参数传递到底是「传值」还是「传引用」？
两个词都不准确，准确的说法是「传对象引用」，有时也叫按共享传递。调用时形参会被绑定到实参所指的同一个对象上，没有发生任何复制，所以函数内部对可变对象的原地修改（lst.append(x)）在函数外面看得见。但如果函数内部执行的是重新绑定（lst = []），改的只是形参这个局部名字的指向，调用方的名字纹丝不动。这两种行为的差别不在于「传值还是传引用」，而在于你写的是原地修改还是重新绑定。想让函数不影响外部数据，要么在函数内部先拷贝一份，要么传不可变对象进去。
为什么 a = b = [] 之后改 a，b 也变了？
因为整个语句只创建了一个列表对象，然后把 a 和 b 两个名字都绑定到它上面。链式赋值不会为每个名字各造一份，它是「求值一次、绑定多次」。此后 a.append(1) 是原地修改那个唯一的列表，通过 b 自然也看得到。验证方法是 a is b，结果为 True。如果你想要两个独立的列表，必须分开写成 a, b = [], []，或者显式拷贝 b = list(a)。同样的道理也适用于 [[]] * 3 和类属性里写可变默认值这两类写法。
为什么 0.1 + 0.2 == 0.3 是 False？这和对象模型有关吗？
这个和身份、引用都无关，纯粹是浮点数的值本身不精确。二进制浮点无法精确表示 0.1 和 0.2，相加后的结果比 0.3 大了约 5.6e-17，所以按值比较自然不相等。它之所以常被和 is/== 的话题放在一起，是因为两者都属于「相等看起来理所当然、实际不成立」的场景。解决办法是用 math.isclose(a, b) 做容差比较，或者在金额这类场景里改用整数（以分为单位）或 decimal.Decimal。顺便说，Decimal 是不可变类型，可以安全地当字典键。
什么时候需要 copy.deepcopy，什么时候浅拷贝就够？
浅拷贝（list(x)、x.copy()、copy.copy(x)）新建一个外层容器，但内部元素仍然是原来那些对象的引用。如果元素全是不可变的（数字、字符串、元组），浅拷贝就完全够用，因为那些元素谁也改不了。一旦容器里装着列表、字典或可变的自定义对象，浅拷贝出来的新容器和原容器仍然共享这些内层对象，改一处两边都变，这时才需要 deepcopy 递归复制整棵结构。代价是深拷贝明显更慢，还会因为对象图大而占用额外内存，所以不要无脑用。更好的策略往往是让数据结构本身不可变，从根上取消拷贝的必要。
字典的键必须不可变，那自定义类的实例为什么默认能当键？
严格说，字典对键的要求不是「不可变」而是「可哈希且哈希值稳定」。自定义类默认继承 object.__hash__，它基于 id() 计算，而身份在对象整个生命周期里恒定不变，所以哪怕对象的属性改来改去，哈希值也不会动，契约没有被破坏。代价是这时的相等判断也是按身份来的：两个字段完全相同的实例会被当成两个不同的键。这个默认行为对「唯一的实体对象」是合适的，对「值对象」则不是——后者需要你重写 __eq__ 和 __hash__，而一旦重写，就必须只用不可变字段参与哈希。
重写了 __eq__ 之后怎么恢复可哈希？直接写 __hash__ = object.__hash__ 行吗？
技术上可行，但通常是错的。这样写等于说「相等按内容判、哈希按身份算」，两者不一致，直接违反契约：两个 == 为 True 的实例会落进不同的桶，set 去重失效、跨实例取值抛 KeyError，而且全程不报错。只有一种情况适合这么写——你明确知道这些实例永远不会进入 set 或 dict，只是想保留可哈希性以通过某个库的检查，而这通常说明设计需要重新想想。正确做法是基于参与相等判断的那组不可变字段实现 __hash__，最简写法是 hash((self.x, self.y))，或者干脆改用 @dataclass(frozen=True)。
循环引用会导致内存泄漏吗？既然有 GC，我还需要关心吗？
在 CPython 里，纯 Python 对象之间的循环引用最终会被分代垃圾回收器清理掉，不算永久泄漏，但回收时机不可预测，可能显著滞后。需要关心的有三种情况。一是循环里的对象持有非内存资源（文件句柄、socket、数据库连接），延迟回收意味着这些资源被长时间占着，甚至撑爆连接池。二是对象量大时，延迟回收会让内存峰值明显高于稳态。三是涉及 C 扩展分配的内存时，GC 未必能完整追踪。实践建议是：树形结构里子指父用弱引用打破环，资源一律用 with 管理，不要把回收时机交给 GC 去猜。
如何判断两个变量指向同一个对象，以及怎么调试引用相关的问题？
最直接的是 a is b，等价于 id(a) == id(b)，返回 True 就说明是同一个对象。要看还有多少人持有它，用 sys.getrefcount(x)，记得减掉形参贡献的那个 1。想知道具体是谁在引用它，用 gc.get_referrers(x) 能列出引用方对象，配合 gc.get_referents(x) 反向查看它引用了谁。排查「改了一处别处也变」这类问题时，标准动作是在可疑的两处各打印一次 id()，相同就证明是共享同一个对象，此时的修复方向只有两个：在合适的位置做拷贝，或者把这个数据结构换成不可变的。
