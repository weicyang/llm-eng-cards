PY04 · 控制流与真值判断

缩进即语法 / falsy 完整清单与判定机制 / for 的取值过程 / for-else 的真实语义 / 短路求值的兜底陷阱 / match-case 的解构本质

控制流看着是全书最简单的一章，但它同时是最容易写出「能跑、结果却悄悄错了」的一章。原因是 Python 在这里做了三个与其他语言不同的选择：块结构靠缩进、条件不要求布尔、逻辑运算符返回操作数本身。这三点都很方便，也都各自对应一类静默 bug。

一、分支：if / elif / else 与缩进即语法

C、Java、JavaScript 用大括号划定代码块，缩进只是给人看的排版习惯，删掉所有缩进程序照样编译。Python 反过来：它没有块的起止符号，缩进本身就是语法。同一层级的语句必须对齐到同一列，多一个空格少一个空格都是语法结构的改变，而不是风格问题。

这里说的缩进块指的是在 if、for、def 这类以冒号结尾的行之后、缩进更深的那一组连续语句，它们共同构成一个被条件或循环控制的单元。解析器在 tokenize 阶段就会把缩进的增加和减少转成 INDENT/DEDENT 这两种 token 交给语法分析器，所以缩进错误是在真正执行任何一行之前就被发现的——和 PY01 里讲的「语法错误发生在编译期」是同一回事。

在 Python 里，缩进不是「排得好看」，而是你在告诉解析器「这几行属于上面那个条件」。把它当成不可见的大括号，混用空格和 Tab 就等于写了一个大括号忘了配对。

为什么 Tab 和空格不能混

一个 Tab 在你的编辑器里显示成 4 格，在同事的编辑器里可能是 8 格。如果一行用 4 个空格、下一行用 1 个 Tab，两行在屏幕上看起来完全对齐，但 Python 无法确定它们是否属于同一层级——因为它不知道你的 Tab 该算几格。Python 3 的处理很干脆：直接拒绝，抛 TabError。这类 bug 最烦人的地方在于肉眼看不出来，你盯着那行代码找半小时也找不到问题，因为问题是不可见字符。

报错触发条件你在屏幕上看到的处理
IndentationError: expected an indented block冒号结尾的行之后没有缩进更深的语句if x: 下面一行顶格写了补缩进，或用 pass 占位
IndentationError: unexpected indent某行缩进比上下文更深，但上一行不以冒号结尾多敲了一个空格对齐到同一列
IndentationError: unindent does not match any outer indentation level退出块时退到了一个不存在的层级退了 3 格而外层是 4 格统一用 4 空格为一级

唯一可靠的预防手段是让工具代劳：编辑器设置里勾上「插入空格代替 Tab」、缩进宽度 4，再让 ruff format 或 black 之类的格式化工具在保存时统一处理。PEP 8 规定的 4 空格已经是整个生态的事实标准，不需要参与讨论。

elif 存在的意义：把嵌套压平

只有 if/else 的语言里，多路分支只能写成 else { if ... } 的嵌套形式。Python 提供 elif 这个专门的关键字，让 N 路分支的缩进深度永远保持为 1。这不只是少敲几个字：缩进深度直接决定了读代码时你需要在脑子里同时记住多少个「当前所处的条件」。

同样的四路分支，两种写法的控制流形状 ────────────────────────────────────────────────────────── 【嵌套 if】缩进逐层加深，读到最内层要记住 3 个前提条件 if score >= 90: grade = "A" else: if score >= 80: ← 深度 2 grade = "B" else: if score >= 60: ← 深度 3 grade = "C" else: grade = "D" ← 深度 4：读者要同时记住 「不>=90 且 不>=80 且 不>=60」 控制流： ┌─>[>=90]─是─> A └否─>┌─>[>=80]─是─> B └否─>┌─>[>=60]─是─> C └否────────> D ← 右侧不断漂移 【elif 扁平链】所有分支同一深度，从上到下读一遍即可 if score >= 90: grade = "A" elif score >= 80: grade = "B" ← 深度始终为 1 elif score >= 60: grade = "C" else: grade = "D" 控制流： [>=90]─是─> A ─┐ │否 │ [>=80]─是─> B ─┤ │否 ├─> 汇合，继续往下 [>=60]─是─> C ─┤ │否 │ else ────> D ─┘ ← 一条竖线，形状不漂移

两段代码语义完全等价，但右侧的「漂移」是有认知成本的。经验法则是：缩进超过 3 层就该重构，手段通常是提前 return（卫语句）、把内层逻辑抽成函数，或者改用 elif 链。分支之间互斥时用 elif 还有一个实质好处——它保证只有一个分支会执行，而连写多个独立的 if 则可能同时命中好几个。

另外注意 Python 在 3.10 之前没有 switch 语句。这不是遗漏，而是长期的有意选择：社区认为 elif 链已经能表达同样的东西，而字典查表（把「值 → 处理函数」写成 dict）比 switch 更灵活也更快。3.10 引入的 match/case 看起来像 switch，但它解决的其实是另一个问题，第六节会说清楚。

二、真值判断：哪些东西是「假」

在 Java 里 if (list) 根本不能编译，条件必须是 boolean。Python 允许你把任何对象放进 if 后面，解释器会先问这个对象「你算真还是算假」，再决定走哪个分支。这个过程叫真值测试，是 Python 数据模型的一部分，而不是 if 语句的特殊照顾——while、and、or、not、filter() 用的都是同一套规则。

Python 不问「这个条件是不是 True」，它问「这个对象是不是空的/零的」。容器空、数字为零、值不存在，这三种情况一律算假，剩下的一律算真。

falsy 的完整清单

被判为假的对象叫 falsy，反之叫 truthy。内置类型里 falsy 的成员是有限且可以背下来的，一共就这么几类：

表格右侧那一列比左侧更值得看。'0'、' '、[None]、float('nan') 全都是 truthy，因为真值测试看的是「容器空不空、数值是不是零」，不看里面装的是什么。从表单或 CSV 读出来的数据尤其危险：用户什么都没填，你拿到的可能是 ' ' 而不是 ''，于是 if value: 判定为真，一个只有空格的名字就进了数据库。这种情况该写的是 if value.strip():。

机制：先 __bool__，再 __len__

上面那张清单不是硬编码在解释器里的特例表，它是两个特殊方法——名字前后带双下划线、由解释器在特定语法出现时自动调用的方法——共同作用的结果。判定顺序固定为三步：

bool(obj) / if obj: / while obj: 都走同一条路 ──────────────────────────────────────────────────────────── ┌─────────────────────────┐ │ 对象定义了 __bool__ 吗？│ └───────────┬─────────────┘ 是 │ │ 否 ▼ ▼ ┌──────────────┐ ┌──────────────────────────┐ │ 调用它 │ │ 对象定义了 __len__ 吗？ │ │ 必须返回 bool│ └──────────┬───────────────┘ │ 否则 TypeError│ 是 │ │ 否 └──────┬───────┘ ▼ ▼ │ ┌──────────────┐ ┌────────────────┐ │ │ 调用它 │ │ 一律判为 True │ │ │ len==0 → 假 │ │ ← 默认行为 │ │ │ len>0 → 真 │ │ 自定义类、函数│ │ └──────┬───────┘ │ 模块、类型对象│ │ │ └───────┬────────┘ ▼ ▼ ▼ ┌───────────────────────────────────────────┐ │ 最终的 True / False │ └───────────────────────────────────────────┘ 推论： • 自己写的 class 若两个方法都没定义 → 实例永远 truthy （所以 if my_obj: 检查不出「这个对象是空的」） • list / dict / str / set 靠 __len__，不是靠 __bool__ • numpy 数组两个都有但会抛 ValueError，必须用 .any()/.all()

最后一条推论是实践中最常撞到的：NumPy 的多元素数组无法回答「你是真还是假」，因为答案可能是「一部分真一部分假」，所以它主动抛 ValueError: The truth value of an array with more than one element is ambiguous。这条报错信息是好设计的范例——它不猜你的意思，而是逼你用 .any() 或 .all() 说清楚。

为什么 if lst: 比 if len(lst) > 0: 地道

两种写法结果一样，但前者更好，理由有三层。可读性上，if lst: 直接表达「如果有东西」这个意图，而 len(lst) > 0 是把意图翻译成了一次计数加一次比较，读者要反向还原。通用性上，if lst: 对任何支持真值测试的对象都成立，而 len() 只对有长度的对象可用，换成生成器就直接 TypeError。正确性上，len(lst) > 0 在 lst 意外是 None 时会抛异常，而 if lst: 会安静地走 else 分支——这一点是双刃剑，取决于你想不想让 None 暴露出来。

示例场景：某数据清洗脚本用 if not record.get('qty'): 过滤缺失字段，跑完 12 万条记录后发现有 3400 条本该保留的行被丢掉了——它们的 qty 合法地等于 0（库存售罄），而 0 是 falsy，被当成「缺失」处理了。把判断改成 if record.get('qty') is None: 之后，3400 条记录全部回来，改动 1 行。这就是 falsy 清单必须背熟的现实理由：0 和「没填」在业务上是两件完全不同的事，但在 if 里长得一模一样。

由此得到一条可以无脑执行的规则：判断「有没有内容」用真值测试，判断「是不是 None」用 is None。前者关心容器空不空，后者关心值存不存在，两者不可互换。顺带一提，判断 None 必须用 is 而不是 ==，因为 None 是单例，is 比较身份，快且无法被自定义类的 __eq__ 骗过去；ruff 和 flake8 都会把 == None 报成 E711。

三、循环：for 遍历的是可迭代对象，不是下标

写过 C 或 Java 的人第一次看 Python 的 for，往往会把它理解成 for-each 的语法糖，以为底层还是「取长度、下标自增、越界退出」。这个误解会直接导致 for i in range(len(seq)) 这种写法满天飞。Python 的 for 完全不知道什么叫下标，它的工作对象是可迭代对象——任何能被要求「交出一个迭代器」的对象。

for 做的事只有两步：先跟对象要一个「取值器」，然后反复跟这个取值器要下一个值，直到它说没有了。中间没有任何计数器，也不关心对象里有多少元素。

for name in users: 这一行背后发生的事 ────────────────────────────────────────────────────────── 【准备】只做一次 iter(users) ──> 拿到一个迭代器对象 it （users 本身不变，它只是「能产出迭代器」） 【循环】反复执行 ┌──────────────────────────────┐ │ next(it) │ └──────┬──────────────┬────────┘ │ 拿到值 │ 抛 StopIteration ▼ ▼ name = 那个值 循环正常结束 执行循环体 ├─> 有 else 分支 → 执行它 │ └─> 没有 → 往下走 └────> 回到 next(it) 循环体里遇到 break └────> 立即跳出，StopIteration 永远不会发生 → else 分支被跳过（第四节的关键） ────────────────────────────────────────────────────────── 所以： • 对象只要能给出迭代器就能被 for 遍历，不需要有长度 • 文件对象、生成器、数据库游标都能直接 for，因为它们都能 • 「还有多少个」这个问题 for 从来不问，所以它能处理无限序列 （iter / next / StopIteration 这套迭代器协议在 PY12 详讲）

这个模型解释了几件事。文件对象可以直接 for line in f: 逐行读，哪怕文件有 100 GB——因为它按需产出，不需要先知道总行数。生成器、zip、map 的返回值同理。反过来，这也解释了为什么这些对象不能用 len()、不能用下标、而且只能遍历一次：值被取走就没了，第二次 for 会立刻得到 StopIteration，表现为循环体一次都没执行，连报错都没有。

range 是惰性的，不是列表

range(1000000) 不会创建一百万个整数。它是一个只存了 start/stop/step 三个数的轻量对象，需要第 N 个值时现算出来。所以 range(10**12) 占的内存和 range(10) 一样多，都是几十字节。这是 Python 3 相对 Python 2 的改进之一（Python 2 的 range 真的返回列表，xrange 才是惰性的）。

import sys
sys.getsizeof(range(10**12))        # 48 字节，与规模无关
sys.getsizeof(list(range(10**6)))   # 约 8 MB，且会真的分配

# range 和列表的区别：能索引、能取长度，但不存储元素
r = range(0, 100, 7)
r[5], len(r), 91 in r               # (35, 15, True) —— in 是 O(1) 算的

注意最后一行：91 in range(0, 100, 7) 是常数时间完成的，因为 range 用算术判断而不是逐个比较。这种「看起来像容器、其实是规则」的设计在 Python 里很常见，也是判断性能时容易误判的地方。

要下标用 enumerate，要并行用 zip

你想做的事不地道的写法地道的写法为什么后者更好
遍历元素for i in range(len(xs)): x = xs[i]for x in xs:少一次索引，且对无长度对象也成立
同时要下标和元素for i in range(len(xs)): ... xs[i]for i, x in enumerate(xs):下标与元素同步，不可能错位
下标从 1 开始for i in range(1, len(xs)+1)for i, x in enumerate(xs, start=1):不用手算偏移，报错信息里的行号直接可用

zip 默认按最短的那个截断这一点要留意：它意味着两个本该等长的列表如果因为 bug 差了一个元素，zip 会安静地少处理一条，不报任何错。strict=True 就是为这个场景加的，处理成对数据时建议默认打开。

遍历中修改容器：会漏元素

这是初学者最容易写出、也最难自己发现的一类 bug。列表的迭代器内部维护一个位置计数器，你在循环体里 remove 掉当前元素，后面的元素会整体前移一格，但计数器照样 +1，于是紧跟其后的那个元素被跳过了。它不报错，只是结果不对。

nums = [1, 2, 2, 3]，循环体里删掉所有偶数 ────────────────────────────────────────────────────── for n in nums: if n % 2 == 0: nums.remove(n) ← 边遍历边删 位置 i=0: [1, 2, 2, 3] n=1 奇数，跳过 ↑ 位置 i=1: [1, 2, 2, 3] n=2 删除 → [1, 2, 3] ↑ 原本第 2 个 2 前移到了 i=1 位置 i=2: [1, 2, 3] n=3 ← 直接读到了 3！ ↑ 第二个 2 被整个跳过 位置 i=3: 越界 → StopIteration，循环结束 结果 [1, 2, 3] ← 还剩一个偶数，且不报错 ─────────── 三种正确做法 ─────────── 推导式（首选）: nums = [n for n in nums if n % 2] 遍历副本 : for n in nums[:]: / for n in list(nums): 倒序删除 : for i in range(len(nums)-1, -1, -1): ... dict / set 更严格：遍历中增删键会直接抛 RuntimeError: dictionary changed size during iteration

列表和字典在这里的表现不一样值得注意：字典和集合会主动检测长度变化并抛 RuntimeError，而列表不会报错，只会给出错的结果。所以列表是更危险的那个。规则很简单：需要按条件筛选就重建一个新容器，不要原地边遍历边改。推导式在这里既最快也最清晰，是绝大多数场景的答案。如果必须原地修改（比如这个列表被别的地方引用着），用切片赋值 nums[:] = [n for n in nums if n % 2]，它保留原对象身份。

四、for-else 与 while-else：被误解最多的语法

Python 的循环可以带一个 else 分支，这是很多写了几年 Python 的人也说不清的语法。误解的根源是 else 这个词：在 if 里它表示「条件不成立」，于是人们自然猜测循环的 else 表示「循环条件不成立时执行」或者「循环体一次都没执行时执行」。两个猜测都是错的。

循环后面的 else 真正配对的是 break，不是循环条件。把它读成「没被 break 打断就执行」——或者干脆在心里改名叫 nobreak——这个语法立刻就通顺了。

准确的规则是：循环正常结束时执行 else，被 break 中断时跳过 else。「正常结束」包括两种情况——迭代器耗尽（第三节图里那个 StopIteration）、或者 while 的条件变为假。注意空序列也算正常结束：for x in []: ... else: ... 里的 else 会执行。另外 continue 不影响 else，只有 break 会。return 和抛异常当然也会跳过它，但那是因为整个函数都退出了。

它解决的是什么问题：省掉标志变量

「在一堆数据里找符合条件的第一个，找不到就报错」是极常见的需求。没有 for-else 时标准做法是引入一个布尔变量记录「找到了没有」，循环结束后再检查它。这个变量不承载业务含义，纯粹是为了把「循环内部的状态」传递到「循环外部」，属于脚手架代码。

# 用标志变量：found 只为了把「循环里发生过什么」带到循环外
found = False
for u in users:
    if u.id == target:
        found = True
        break
if not found:
    raise LookupError(f"用户 {target} 不存在")

换成 for-else，「没有 break 发生」这个事实本身就代表「一个都没匹配上」，标志变量随之消失：

for u in users:
    if u.id == target:
        break
else:
    raise LookupError(f"用户 {target} 不存在")
对比维度标志变量写法for-else 写法
额外状态多一个 found 变量，作用域延伸到循环外零额外变量
失败分支的位置在循环之后，与循环之间可能隔着别的代码紧贴循环，位置上无法分离
典型 bug忘记置 True、或在多层循环里复用同一个标志把 else 缩进错，变成 if 的 else
加一个分支时要改两处（赋值处 + 检查处）只改一处
可读性对所有人都直白对不熟悉此语法的人是负担
适用场景逻辑复杂、循环后还要用到「找到的是哪个」纯粹的「搜索成功/失败」二分

最后两行是诚实的部分。for-else 确实更紧凑，但它的可读性依赖于读者认识这个语法；在团队水平不齐的代码库里，一个带注释的标志变量可能是更好的工程选择。真正推荐使用 for-else 的判断标准是：这段循环是否只有「找到了」和「没找到」这两种出路。一旦循环后还需要知道「找到的是哪一个」，你反正要引入变量，那时候 next() 配默认值往往比两者都更简洁。

一个具体的查找场景

假设要在一组候选配置目录里找到第一个真实存在的配置文件，全都不存在时使用内置默认值并打一条警告。这个场景里「失败」不是异常而是一条正常路径，for-else 表达得非常贴切：

CANDIDATES = ["./app.toml", "~/.config/app.toml", "/etc/app.toml"]
for path in CANDIDATES:
    p = Path(path).expanduser()
    if p.is_file():
        config = load(p)
        break
else:
    config = DEFAULT_CONFIG
    logger.warning("三个候选路径均未找到配置，已回退到内置默认值")

while-else 的规则完全一致，只是「正常结束」意味着循环条件变为假。它的典型用途是重试循环：重试成功就 break，把「重试次数耗尽仍未成功」的处理放进 else。不过实践中 while-else 比 for-else 更罕见，因为重试逻辑通常已经被 tenacity 这类库封装掉了。

示例场景：一段权限校验代码用标志变量写成 3 层嵌套循环，共 4 个布尔标志（has_role、has_scope、matched、ok）。某次重构中有人在中间加了一个 continue，导致最内层的 matched = True 在特定路径上被跳过，未授权请求被放行；问题上线 11 天后才由一次审计发现。改写为 for-else 后标志变量归零、嵌套降到 2 层，同类路径的单测从 3 个补到 9 个全绿。教训不是「标志变量有罪」，而是每一个不承载业务含义的状态变量都是一个可以被改错的地方。

五、短路求值与条件表达式

大多数语言的 && 和 || 返回布尔值。Python 的 and/or 不是——它们返回参与运算的那个操作数本身，原封不动。这是个很容易忽略的差别，因为在条件判断里它看不出来（反正都要做真值测试），但一旦你把结果赋给变量，类型就会暴露。

and 和 or 不是在算真假，而是在挑一个操作数还给你。or 挑第一个为真的，and 挑第一个为假的，挑不到就还最后一个。所以 1 or 2 得到 1，不是 True。

短路求值：右边可能根本不执行

短路求值指的是：当左操作数已经能决定整个表达式的结果时，右操作数完全不会被求值。这不只是性能优化，它有语义后果——如果右边是个函数调用，那个函数就是没被调用；如果右边会抛异常，那个异常就不会发生。这一点被大量用作安全守卫，比如 if node is not None and node.value > 0:，靠的就是左边为假时右边不执行，从而避免 AttributeError。

表达式结果右操作数求值了吗说明
0 or 'fallback''fallback'是左边 falsy，or 必须继续看右边
'a' or crash()'a'否左边已 truthy，crash() 根本不执行

all() 对空序列返回 True 这一条会咬人：all(x.is_valid for x in items) 在 items 为空时返回 True，于是「零条数据」被判定为「全部校验通过」。这在数学上是对的（空集上的全称命题恒真），在业务上往往是错的，需要额外补一句 if items and all(...)。

x or default：最常见的兜底写法，也是最常见的坑

因为 or 返回操作数本身，name = user_input or "匿名" 就成了一个非常顺手的兜底表达式：输入为空就用默认值。问题在于它的触发条件是「x 是 falsy」，而你真正想表达的几乎总是「x 没有提供」。当 0、0.0、''、[]、False 是合法的业务取值时，这两者就分道扬镳了。

# 陷阱：0 是合法的超时时间（表示不超时），却被兜底覆盖成了 30
timeout = user_timeout or 30        # user_timeout=0 → 得到 30 ✗

# 正确：只在「没提供」时兜底
timeout = 30 if user_timeout is None else user_timeout
# 或者
timeout = user_timeout if user_timeout is not None else 30

判断标准很明确：默认值的触发条件是「值缺失」还是「值为空」？ 如果是前者，必须用 is None；只有确认 falsy 的所有取值都该走兜底时，or 才是安全的。对字符串这种场景 or 通常没问题（空字符串确实该兜底），对数字和布尔值几乎总有问题。字典取值同理：d.get('k') or default 有这个坑，而 d.get('k', default) 只在键不存在时兜底，语义更准。

条件表达式（三元）

Python 的三元写法是 a if cond else b，条件放在中间。这个词序和 C 系的 cond ? a : b 不同，但读起来更像英语自然语序（「用 a，如果 cond，否则用 b」）。它是表达式而不是语句，所以能出现在任何需要值的地方：函数参数里、推导式里、f-string 里、返回值里。

label = "成年" if age >= 18 else "未成年"
# 可以嵌进推导式，但只嵌一层
tags = ["高" if s > 80 else "低" for s in scores]

# 不要写成这样 —— 三层嵌套的三元没人读得懂，改用 if/elif
# g = "A" if s >= 90 else "B" if s >= 80 else "C" if s >= 60 else "D"

它和 and/or 的分工是：三元表达式的分支由条件决定，两个分支的值互不相干；or 兜底则是把「被测的值」直接当作结果之一。想清楚这个区别就不会再用 cond and a or b 这种老写法去模拟三元了——当 a 本身是 falsy 时它会静默地返回 b，那是 Python 2 时代的遗物。

六、match / case：3.10 起的结构化模式匹配

match/case 是 Python 3.10 引入的，语法上很像其他语言的 switch，但把它当 switch 用会完全错过重点。它的正式名字叫 结构化模式匹配——关键词是「结构化」：它比对的不是「值相不相等」，而是「这个数据的形状是不是长这样」，匹配成功的同时把你关心的部分绑定到变量上。

switch 问的是「这个值等于哪一个」，match 问的是「这个数据长得像哪一种结构，里面的零件分别是什么」。它更接近解包赋值，而不是等号比较。

这个差别用一行代码就能看清：case [x, y] 匹配的是「一个恰好有两个元素的序列」，并且顺手把两个元素命名为 x 和 y。用 if/elif 表达同一件事，你需要先判断类型、再判断长度、再手工解包，三步都可能写错。

match msg: —— 一次匹配同时完成「判形状」和「拆零件」 ────────────────────────────────────────────────────────────── msg = {"type": "move", "from": [1, 2], "to": [3, 4]} match msg: case {"type": "move", "from": [x1, y1], "to": [x2, y2]}: │ │ │ │ │ └─ 嵌套序列模式： │ │ 要求是长度 2 的序列 │ │ 并绑定 x2, y2 │ └─ 字面量模式：要求这个键的值 == "move" └─ 映射模式：要求是 Mapping 且**至少**含这些键 （多出来的键不影响匹配） ...使用 x1, y1, x2, y2 ← 已经是可用的局部变量 case {"type": "quit"}: ← 按顺序往下试，第一个匹配上就停 ... case _: ← 通配模式，兜底；放在最后 raise ValueError(f"未知消息: {msg}") ──────────── 换成 if/elif 要手写的等价逻辑 ──────────── if isinstance(msg, dict) and msg.get("type") == "move" \ and isinstance(msg.get("from"), (list, tuple)) and len(msg["from"]) == 2 \ and isinstance(msg.get("to"), (list, tuple)) and len(msg["to"]) == 2: x1, y1 = msg["from"] x2, y2 = msg["to"] ... ← 6 行守卫 + 2 行解包，且每一处 len / isinstance 都是潜在的漏判

上图右下角那段对比就是 match 的价值所在：它把「类型检查 + 长度检查 + 解包」这三件必须同时做对的事压缩成一个声明式的形状描述。

几种模式各自匹配什么

表里加粗的三处都是真实陷阱。第一，case CONST: 这样写不是在和常量 CONST 比较，而是一个捕获模式：它无条件匹配成功，并把被匹配的值重新赋给 CONST，后面所有 case 全成死代码。要比常量必须写成带点号的形式（Color.RED、status.OK）或者用字面量。第二，字符串不被当作序列，case [a, b] 不会匹配 "ab"——这是刻意设计，避免字符串被意外逐字符解构。第三，映射模式是「至少包含」而不是「完全等于」，所以 case {}: 会匹配任何字典，包括非空的。

什么时候用它，什么时候是过度设计

判断标准是：你要区分的是「值」还是「形状」？ 如果只是把几个字符串或整数映射到不同处理，if/elif 或者字典派发表更简单，用 match 属于杀鸡用牛刀。match 真正发挥作用的场合是输入为形状固定但种类多样的嵌套数据——解析 JSON 消息、处理 AST 节点、实现状态机、分派 WebSocket 事件，这些场景下你本来就要写一堆 isinstance 加 len 加下标访问，match 能把它们全部收进模式里。

还有一个现实约束：版本门槛是 3.10。如果你的库要支持 3.9（在 2026 年仍有少量长期支持环境停留在那里），match 连语法检查都过不了——它是语法层面的新增，不是运行时特性，没法用 try/except ImportError 之类的手段降级。所以在应用代码里可以放心用，在需要宽版本兼容的库代码里要先确认 pyproject.toml 里的 requires-python。关于版本支持窗口的判断方法，PY01 · Python 环境与解释器那一节已经讲过。

示例场景：某消息网关用 if/elif 处理 7 种事件类型，守卫条件加起来 34 行，其中 3 处漏了 len() 检查，导致畸形载荷触发 IndexError 并让整个消费者进程退出，两周内重启 9 次。改写为 match 后分派逻辑压缩到 19 行，形状不符的载荷全部落到 case _: 分支被记录并丢弃，重启次数归零。关键收益不是代码变短，而是「形状不对」从一个会抛异常的意外变成了一条被显式处理的正常分支。

本章的取舍清单

  • 判断「有没有内容」用 if lst:、if s:，让真值测试替你工作
  • 判断「值是否缺失」一律用 if x is None: / is not None
  • 兜底默认值写 x if x is not None else default，除非确认所有 falsy 都该兜底
  • 要下标用 enumerate，并行遍历用 zip(..., strict=True)
  • 按条件筛选就重建容器：xs = [x for x in xs if ...]；需要保留原对象身份时用 xs[:] = [...]
  • 纯「搜索成功/失败」的循环用 for-else，替掉标志变量
  • match 里比常量要带点号（Color.RED），并始终留一个 case _: 兜底
  • 编辑器统一 4 空格、不插入 Tab，保存时自动格式化
  • if x == None: —— 用 is None；== 会被自定义 __eq__ 骗过去（ruff E711）
  • if len(lst) > 0: —— 冗余，且对生成器直接 TypeError
  • if flag == True: —— 写 if flag:；1 == True 也成立，比较反而引入歧义
  • 遍历中 lst.remove(x) / del d[k] —— 列表静默漏元素，字典抛 RuntimeError
  • timeout = user_timeout or 30 —— 0 这类合法 falsy 值会被兜底吃掉
  • for i in range(len(xs)): 只为了取元素 —— 多一次索引，也丢了通用性
  • cond and a or b 模拟三元 —— a 为 falsy 时静默返回 b
  • 用 match 做纯值分派、或用三层嵌套三元 —— 都是把简单事写复杂
  • Tab 与空格混用 —— 报 TabError，且屏幕上看不出任何异常

这一章所有的坑都能归到同一句话：Python 在控制流上给了你很多便利，代价是「空」「零」「不存在」这三件事在 if 里长得一模一样。每次写条件判断时多问一句「我关心的到底是哪一个」，这一章的 bug 就写不出来了。

Q&A

为什么 Python 用缩进而不是大括号？这不是更容易出错吗？
出发点是消灭「排版和语义不一致」这类问题。在用大括号的语言里，代码的实际结构由括号决定、而人阅读时依赖缩进，两者可以不一致——历史上有过因为缩进误导而漏掉一层 if 导致的严重安全漏洞。Python 让两者强制统一，你看到的层级就是解释器理解的层级。代价是缩进变成了不可见字符组成的语法，Tab 与空格混用会产生「看起来对、实际错」的情况，所以 Python 3 干脆把混用定为 TabError 直接拒绝执行。实践中这个代价几乎为零：编辑器设成 4 空格、配上自动格式化工具之后，你不会再手工管理缩进。
if lst: 和 if len(lst) > 0: 到底该用哪个？
默认用 if lst:。它更短、意图更直接（「如果有东西」），而且对任何支持真值测试的对象都成立，包括那些没有长度的对象。len() 的写法多了一次计数和一次比较，而且只能用在有 __len__ 的对象上，换成生成器会直接抛 TypeError。唯一需要注意的差别是当变量意外为 None 时：if lst: 会安静地走 else 分支，而 len(None) 会抛异常把问题暴露出来。如果你希望 None 被当成错误而不是「空」，那就不要靠真值测试，明确写 if lst is None: raise ... 把两种情况分开处理。
哪些值是 falsy？有没有办法不用背？
内置类型里的 falsy 值是：False、None、数字零（0、0.0、0j、Decimal(0)）、空容器（''、[]、{}、()、set()、range(0)）以及 timedelta(0)。不用死记的办法是记住机制：解释器先找对象的 __bool__，没有就退而调 __len__ 并看长度是否为 0，两个都没有就一律判为真。容器靠 __len__，所以「空即假」；数字类型自己定义了 __bool__，所以「零即假」；你自己写的类如果两个方法都不定义，实例就永远是真的。真正需要记住的反而是几个反直觉的 truthy 值：' '（一个空格）、'0'、'False'、[0]、[[]]、float('nan') 全都是真。
for-else 的 else 到底什么时候执行？
循环正常结束时执行，被 break 中断时跳过。「正常结束」对 for 来说是迭代器耗尽，对 while 来说是条件变为假。所以这个 else 配对的是 break，而不是循环条件——很多人把它误读成「循环体没执行时执行」，那是错的：遍历空列表时循环体一次都没跑，else 照样执行。continue 不影响它，只有 break 会跳过它（return 和抛异常也会，但那是整个函数都退出了）。记忆方法是在心里把这个关键字念成 nobreak，语义立刻就顺了。它的用途就是表达「遍历完了也没找到」，从而省掉一个 found = False 标志变量。
x or default 这种兜底写法有什么问题？
问题在于触发条件错位。or 在左边是 falsy 时返回右边，而你想表达的通常是「左边没有提供时用右边」。当 0、0.0、''、[]、False 是合法的业务取值时，这两者就不是一回事了。典型事故是 timeout = user_timeout or 30：用户明确传了 0 表示不超时，却被悄悄改成 30 秒。正确写法是 timeout = user_timeout if user_timeout is not None else 30，把判断条件从「是否为空」换成「是否缺失」。字典取值同理，d.get('k') or default 有这个坑，d.get('k', default) 没有，因为后者只在键不存在时才兜底。只有当你确认 falsy 的每一种取值都确实该走默认值时（比如空字符串确实该替换成占位名），or 才是安全的。
为什么遍历列表时删除元素会漏掉东西？dict 为什么反而报错？
列表的迭代器内部维护一个整数位置计数器。你在循环体里删掉当前元素后，后面的元素整体前移一格，但计数器下一轮照样 +1，于是紧跟其后的那个元素被跳过了——它不报错，只是结果少处理了一些元素，所以极难自查。字典和集合的实现不同，它们在迭代过程中会检测容器大小是否变化，一旦发现就抛 RuntimeError: dictionary changed size during iteration。这反而是好事：显式失败比静默出错容易发现得多。正确做法有三种：用推导式重建一个新容器（首选，也最快最清晰）、遍历一份副本 for x in lst[:]、或者倒序遍历下标删除。如果必须保留原对象的身份（有别的代码持有这个列表的引用），用切片赋值 lst[:] = [x for x in lst if ...]。
match/case 和 if/elif 相比，什么时候真的值得用？
看你区分的是「值」还是「形状」。如果只是把几个字符串或状态码映射到不同的处理函数，if/elif 或者一张 dict 派发表更简单，用 match 是过度设计。它真正的优势在处理形状固定但种类多样的嵌套数据：JSON 消息分派、AST 节点遍历、状态机转移、协议帧解析。这些场景下用 if/elif 你必须手写一长串 isinstance 加 len 加下标访问，每一处都是潜在的漏判，而 match 把类型检查、长度检查和解包压成一行声明式的模式，同时把需要的字段绑定成局部变量。还要注意版本门槛是 3.10，而且它是语法层面的新增，在更低版本上连解析都通不过，没法运行时降级。
match 里写 case MY_CONST: 为什么后面的分支全都不执行了？
因为一个不带点号的裸名字在模式里是捕获模式，不是值比较。case MY_CONST: 的含义是「无条件匹配，并把被匹配的值绑定到名字 MY_CONST 上」，所以它永远成功，后面所有的 case 都变成了不可达的死代码，同时你的常量还被悄悄覆盖了。解决办法是把常量写成带点号的形式，比如放进枚举后写 case Color.RED:，或者放进一个类/模块里写 case status.OK:——带点号的叫值模式，会做 == 比较。直接写字面量 case 404: 也可以。这是模式匹配语法里最容易踩的一个坑，好在静态检查工具通常能提示「后续 case 不可达」。顺带提一句，case _: 里的 _ 是语法上特殊对待的通配符，它不绑定任何东西，只用来兜底，而且必须放在最后。
all() 对空列表返回 True，这算不算设计缺陷？
不算，它在逻辑上是正确的：全称命题「集合中所有元素都满足 P」在空集上恒为真，因为找不到反例。对称地，any([]) 返回 False，因为找不到正例。但这个数学上的正确经常和业务预期相反——if all(r.is_valid for r in records): 在 records 为空时会判定「全部校验通过」，于是零条数据被当成完美数据放行。防御办法是把「非空」这个前提显式写出来：if records and all(...)。另外这两个函数都是短路的，any 遇到第一个真值就停，all 遇到第一个假值就停，所以传生成器进去比先构造列表更省，尤其是判断条件里带 IO 或重计算的时候。
