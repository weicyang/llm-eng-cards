PY11 · 序列协议与切片

协议方法与语言特性的映射 / 负索引与越界责任 / slice 对象与静默裁剪 / 切片赋值 / memoryview 零拷贝 / 自定义序列的契约清单

Python 里「是不是序列」从来不是一个身份问题，而是一个能力问题：你实现了 __len__ 和 __getitem__，方括号和 for 就开始对你生效。整套序列语法都只是这几个方法的调用语法，认清这层映射，切片那些反直觉的行为就都有了解释。

一、协议即约定：Python 的鸭子类型怎么工作

换一个语言背景来看这件事会更清楚。在 Java 里想让自己的类支持 size() 和下标语义，你必须显式写上 implements List，编译器会检查你有没有把接口里的方法都填齐；缺一个方法，代码根本编译不过去。Python 走的是另一条路：它不问你继承了谁，只问你身上有没有它要调的那个方法。

这套做法有个通行的名字叫鸭子类型——判断一个对象是什么，只看它能做什么，不看它的血统。落到类型系统的术语上，Java 那种「必须显式声明才算」的方式叫名义类型，Python 这种「长得像就算」的方式叫结构类型。而所谓序列协议，就是一组被语言认可的方法名约定：你实现了哪几个，语言就为你打开对应的哪几个语法入口。

你写下的语法 / 内置函数 解释器实际去找的方法 ────────────────────────── ──────────────────────────── len(x) ──► x.__len__() x[3] ──► x.__getitem__(3) x[1:5:2] ──► x.__getitem__(slice(1, 5, 2)) x[2] = v ──► x.__setitem__(2, v) del x[2] ──► x.__delitem__(2) v in x ──► x.__contains__(v) ← 缺失则退化为线性遍历 for v in x ──► x.__iter__() ← 缺失则退化为旧式协议 reversed(x) ──► x.__reversed__() ← 缺失则用 len + getitem 倒着取 x + y ──► x.__add__(y) x * 3 ──► x.__mul__(3) 「能当序列用」的最小集合 = 上面的前两行 其余每一行，决定的是「像得有多真」——能跑，但语义和内置类型差多少

上图最后两行的说明是本张卡片反复要用到的判断标准。序列协议不是一个全有或全无的开关，而是一条渐进的光谱：只写 __getitem__ 就已经能索引，再补 __len__ 就能被 len() 和负索引相关的工具函数正确处理，继续补 __contains__、__iter__、__reversed__，行为才逐步逼近内置的 list。

为什么只实现两个方法就能被 for 遍历

这是最容易让人困惑的一点：明明没写 __iter__，for 循环却跑起来了。原因是 Python 保留了一条历史遗留的回退路径，通常称为旧式迭代协议——当 iter() 发现对象没有 __iter__ 但有 __getitem__ 时，它会构造一个内部迭代器，用 0、1、2、3…… 递增的整数不断调用 __getitem__，直到某次调用抛出 IndexError 就认为序列结束。

class Ruler:
    def __len__(self): return 3
    def __getitem__(self, i):
        if i >= 3: raise IndexError(i)   # 这一行决定循环何时停
        return i * 10

print(list(Ruler()))   # [0, 10, 20]  —— 没写 __iter__ 也能遍历

注意那句 raise IndexError 不是为了防御性编程而写的，它在这里承担着终止信号的职责。如果越界时你返回 None 而不抛异常，这个 for 循环会变成死循环；如果你抛的是 ValueError，异常会直接穿透到调用方。这种「靠异常传递控制信息」的设计在现代代码里已经不推荐依赖，但它仍然活在语言里，所以你会遇到。

协议方法是语言留给你的插座：len() 插 __len__，方括号插 __getitem__。你插上哪几个，就获得哪几种语法能力，不需要向任何基类报备。

二、索引：负数、越界与 __getitem__ 的责任

负索引是 Python 最讨人喜欢的小设计之一：s[-1] 取末尾元素，不需要先算 len(s) - 1。它的规则只有一条——传进来的整数小于 0 时，先加上长度再当正索引用。换算完之后如果还落在合法区间外，就抛 IndexError。

s = "PYTHON" len(s) = 6 正索引 0 1 2 3 4 5 ┌─────┬─────┬─────┬─────┬─────┬─────┐ │ P │ Y │ T │ H │ O │ N │ └─────┴─────┴─────┴─────┴─────┴─────┘ 负索引 -6 -5 -4 -3 -2 -1 换算规则：i < 0 ⇒ 真实位置 = i + len(s) s[-2] ⇒ -2 + 6 = 4 ⇒ 'O' 合法区间：-6 ≤ i ≤ 5 s[6] ⇒ IndexError s[-7] ⇒ IndexError 两端都没有「多一格」的容错，这一点和切片完全相反

s[5]不换算'N'最后一个合法正索引，等于 len - 1

IndexError 与 KeyError 的血缘关系

序列越界抛 IndexError，字典缺键抛 KeyError，这两个名字看着毫无关系，实际都继承自同一个父类 LookupError。这个设计让「查找失败」成为一类可以统一处理的事件：当你写一个既可能接到列表也可能接到字典的通用取值函数时，捕获 LookupError 一次就够，不需要写成 except (IndexError, KeyError)。

def pick(container, key, default=None):
    try:
        return container[key]
    except LookupError:        # 同时覆盖 IndexError 与 KeyError
        return default

print(pick([1, 2, 3], 9), pick({"a": 1}, "b"))   # None None

反过来说，这个继承关系也是一个提醒：except LookupError 的覆盖面比你想的大。如果函数内部还做了别的字典查询，一个本该暴露的配置项缺失也会被这段代码默默吞成默认值。异常捕获的粒度问题在 PY07 · 文件读写与异常处理 里讨论过，这里只补一条具体结论：捕获父类异常时，try 块里应该只留那一行真正会失败的表达式。

自定义类要自己补齐哪些行为

内置序列替你做掉的事情，在自定义类里全部变成你的责任。__getitem__ 收到的参数是原封不动传进来的：写 obj[-1]，方法里拿到的就是 -1 这个整数，语言不会替你加上长度。如果你内部只是简单转发给一个 list，负索引恰好能工作；但只要你自己算下标、或者把数据存在别的结构里，负索引就会算出一个荒谬的位置，而且往往不报错——它只是安静地返回错的数据。

行为内置 list / str自定义类需要你做什么

索引是「精确寻址」，找不到就必须报错；这条铁律只被内置类型执行。你自己写的 __getitem__ 如果不主动抛 IndexError，就等于对所有依赖它的语法说了谎。

三、切片：一个独立的对象，不只是语法糖

很多人把 x[a:b:c] 当成一种特殊的下标写法，好像解释器在内部展开成了一个循环。事实要有趣得多：冒号语法会先构造一个真实存在的对象——slice 对象，一个只携带 start、stop、step 三个属性的轻量容器——然后把它作为唯一参数传给 __getitem__。也就是说，x[1:5:2] 和 x[slice(1, 5, 2)] 是完全等价的两种写法。

s = slice(1, 5, 2)
print(s.start, s.stop, s.step)        # 1 5 2
print("PYTHON"[s])                    # 'YH'

print(slice(None, 3).indices(6))      # (0, 3, 1)  ← 已按长度 6 裁剪好
print(slice(2, 99).indices(6))        # (2, 6, 1)  ← 99 被裁到 6

这个设计带来一个直接后果：__getitem__ 的参数类型是不确定的，可能是整数，也可能是 slice。自定义序列类里几乎必然要写一次类型分派，这是第六节契约清单里的固定条目。而上面那个 indices() 方法是标准库送给你的礼物——把长度交给它，它会返回一组已经裁剪、已经规范化的 (start, stop, step)，你不必自己重写裁剪逻辑。

取值过程与裁剪行为

这张图最下面两行是整节的重点，也是本卡片最值得记住的一条差异。索引的契约是「精确寻址」，寻不到必须失败；切片的契约是「取一段，有多少给多少」，所以它把越界当成正常输入静默处理。两种截然相反的哲学共用一个方括号，于是产生了一类特别难发现的 bug：代码不抛异常、日志干干净净，只是返回的元素比预期少。

示例场景：一个分页接口按 items[page * 20 : page * 20 + 20] 取数据，前端传来的 page 因为一处前后端不一致而多了 1。总数 1000 条、每页 20 条的情况下，用户翻到第 50 页看到的是空白页而不是错误提示，第 49 页则只返回了 0 条——因为 items[1000:1020] 静默返回了空列表。监控上没有任何异常，接口成功率 100%，问题靠用户反馈才发现，累计影响 3 天。修复只是在取值前加一句 if start >= len(items): raise ValueError。切片的宽容是特性，但它把「参数算错了」这个事实一并吞掉了。

切片返回的是什么

切片对不同类型返回不同东西，但有一条共性：它总是返回新对象，不会返回原对象的引用。list 切片返回新 list，其中的元素是原对象的引用——也就是浅拷贝，只复制最外层容器，内层对象仍然共享。所以 y = x[:] 这个惯用法能让你安全地增删 y 的元素而不影响 x，但如果 x 里装的是可变对象，改动内层依然会互相可见。

str 和 tuple 的切片同样返回新对象，只是因为它们不可变，「共享还是复制」在语义上观察不到，CPython 也保留了一些优化空间（例如 s[:] 对字符串可能直接返回原对象）。这类优化不属于语言保证，不要写依赖它的代码。字符串切片还有一个 PY06 · 字符串与编码 里强调过的前提：它按码点切，不按字节切，所以对含 emoji 或组合字符的文本，切片位置未必落在你肉眼看到的字符边界上。

把方括号里有没有冒号当成两套不同的 API：没冒号是「精确寻址，错就报错」，有冒号是「尽量取一段，取不满就算了」。同一个越界数字在两套 API 下的命运完全不同。

四、切片赋值与原地修改

切片出现在赋值号左边时，走的是另一个方法 __setitem__，能力也完全不同：它允许你用任意长度的新内容替换掉一段区间。这一点让切片赋值成为唯一一个能同时表达「替换、插入、删除」三种操作的语法——长度相等就是替换，右侧更长就是插入，右侧更短或为空就是删除。

x = [1, 2, 3, 4, 5]
x[1:3] = [9]              # 用 1 个换 2 个 → [1, 9, 4, 5]
x[1:1] = [7, 8]           # 空区间赋值 = 插入 → [1, 7, 8, 9, 4, 5]
x[1:3] = []               # 赋空 = 删除 → [1, 9, 4, 5]

y = [1, 2, 3, 4, 5]
y[1:3] = "ab"             # 字符串被逐字符展开！
print(y)                  # [1, 'a', 'b', 4, 5] —— 通常不是你要的

第 6 行那个陷阱值得停一下。切片赋值的右侧要求是一个可迭代对象，而不是「一个元素」，所以解释器会去遍历它。字符串恰好可迭代，于是 "ab" 变成了两个字符元素；如果右侧写的是一个整数 5，你会得到 TypeError: can only assign an iterable——反而是好事，因为它立刻报错了。真正危险的是字符串和生成器这类「能迭代但你没打算让它迭代」的东西，它们不报错，只是悄悄把结构改成别的样子。

带步长的切片赋值是另一套规则

不带步长时长度可以自由变化，一旦写上步长（x[::2] = ...），要求立刻变严：右侧的元素个数必须和左侧选中的位置数严格相等，差一个就抛 ValueError。原因不难理解——带步长的切片选中的是一组不连续的坑位，个数是固定的，解释器无法为「多出来的元素」在中间腾地方。

x[1:1] = [a, b]无在位置 1 前插入 2 个元素—

还有一个容易混淆的对比：x[:] = y 和 x = y 看着差不多，语义完全不同。前者是原地替换 x 的全部内容，所有持有 x 这个列表的引用都会看到新数据；后者只是把名字 x 重新绑定到 y，原列表对象毫发无损，别处的引用还指着旧数据。这正是 PY02 · 变量与内置类型 里那套「名字与对象」模型在切片场景下的具体体现。函数内想清空调用方传进来的列表，就必须写 lst[:] = [] 或 lst.clear()，写 lst = [] 什么也不会发生——这个细节在 PY05 · 函数入门与参数传递 里也出现过。

示例场景：某数据清洗脚本用 rows[:] = [r for r in rows if r.valid] 就地过滤一个 12 万行的列表，因为下游还有 4 处代码持有同一个列表引用，改成 rows = [...] 后那 4 处全部继续看到未过滤的数据，最终导出的文件里混进了 8300 行脏数据。这类问题的排查难点在于代码逻辑「看起来是对的」——过滤表达式本身没错，错的是它没有作用在别人看到的那个对象上。凡是要让改动对调用方可见，就用切片赋值或原地方法，不要重新绑定名字。

切片赋值不是「赋一个值」，而是「用一个可迭代对象替换一段区间」。带步长时坑位数固定，必须等长；不带步长时长度自由，于是插入和删除也顺带被它包了。

五、内存视图与零拷贝切片

切片返回新对象这件事，在日常写法里几乎感觉不到代价——从 100 个元素里切 10 个，复制成本可以忽略。但当对象变大，这个代价就会直接变成延迟和内存峰值。读一个 200 MB 的文件到 bytes，然后切出前半段做校验，那一刻进程里同时存在 200 MB 原数据和 100 MB 副本；如果这样的切片在循环里做 10 次，内存曲线会非常难看。

标准库为此提供了 内存视图——memoryview 对象，它不复制任何数据，只记录「从哪个对象的哪个偏移开始、取多长」。对它做切片依然得到 memoryview，依然不复制。代价是它不是 bytes，不能直接当字符串用，要拿到真实数据仍需 bytes(mv) 转换一次；但在只需要读取、比较、传给底层接口的场景里，这一次转换可以彻底省掉。

示例场景：一段协议解析代码从 bytes 里按 4 KB 逐块切分并校验，输入是 120 MB 的数据包，约 30000 次切片。改用 bytearray + memoryview 之后，进程内存峰值从约 240 MB 降到约 125 MB，解析耗时从 1.8 秒降到 0.4 秒——省掉的时间几乎全部来自那 30000 次 memcpy。这个收益只在数据够大时才成立：同样的改写用在 4 KB 的小包上，因为多了视图对象的创建开销，反而慢了一点。

bytearray 加 memoryview 是处理大块二进制数据的标准组合：前者提供一块可原地修改的缓冲区，后者提供零拷贝的分片视图。文件读取接口里的 readinto()、socket 的 recv_into() 都接受这种视图，让数据从内核直接落进你预分配的缓冲区，中途不产生临时对象。

buf = bytearray(1024)
mv = memoryview(buf)

with open("data.bin", "rb") as f:
    n = f.readinto(mv[:512])      # 直接写进 buf 的前半段，无临时对象
    print(n, buf[:4])

mv.release()                      # 用完释放，否则 buf 无法 resize

值得单独提醒的一点：NumPy 的数组切片在这件事上和 Python 内置序列行为相反——它默认返回视图而不是副本，所以 arr[1:3] += 1 会改到原数组。从 Python 列表迁到 NumPy 的人常在这里栽跟头，因为同样的写法在两边的含义正好颠倒。这部分属于后续 AI 组的内容，这里只需先记住这个反差的存在。

切片默认给你一份独立的副本，这是安全但不便宜的选择。当数据大到复制开始疼的时候，换成 memoryview 把「复制一段」变成「记住一段」，代价是从此要自己关心共享带来的可见性。

六、自己实现一个序列类：契约清单

前五节都在讲内置类型的行为。现在把方向反过来：如果要写一个自己的序列类，需要实现哪些方法，才能让别人用起来「感觉不出和 list 有区别」？答案不是一个方法列表，而是一份带优先级的契约清单——每一条对应一类会被破坏的语法能力。

方法必要性不实现的后果
__len__必须len() 报 TypeError；真值判断退化为「永远为真」，空对象也算真
__getitem__（支持 int）必须完全不能下标访问，object is not subscriptable
__getitem__（支持 slice）必须切片时拿 slice 当整数用，典型报错是列表索引处的 TypeError
__contains__强烈建议能跑但退化为线性遍历；自定义类型若能 O(1) 判断则白白浪费
__iter__强烈建议走旧式协议，靠 IndexError 终止，语义模糊且无法表达惰性序列
__reversed__建议reversed() 回退到 len + 逆序取值，对链式结构会很慢
__setitem__ / __delitem__可变序列才需要不支持赋值与删除，只读序列不需要
__eq__ / __repr__建议比较退化为比身份，调试时只看到内存地址

这份清单里有一半可以让标准库替你写。collections.abc.Sequence 是一个混入基类——它自己不存储数据，只基于你提供的少量方法推导出其余方法。你只要实现 __len__ 和 __getitem__，它就自动补齐 __contains__、__iter__、__reversed__、index()、count()，并且让 isinstance(obj, Sequence) 返回真。

注意上图倒数第三行的限定。混入基类给的是「能用」的实现，不是「最优」的实现——__contains__ 的默认版本就是从头扫到尾。如果你的序列内部是有序的，自己写一个二分查找的 __contains__ 能把 O(n) 降到 O(log n)；基类不会知道你的数据有什么性质，这类优化只能你自己来。

切片应该返回什么类型

这是自定义序列里最容易做错的一个决定。很多人的 __getitem__ 在收到 slice 时直接 return self._items[key]，于是切出来的东西是个 list，不再是你的类。后果是链式操作立刻断裂：obj[1:5] 得到 list，它身上没有你精心实现的那些方法，再切一次或者调用自定义方法就报 AttributeError。内置类型全都遵守「切片返回同类型」这条约定——str 切出 str，tuple 切出 tuple，你也应该遵守。

class Track:
    def __init__(self, pts): self._pts = list(pts)
    def __len__(self): return len(self._pts)

    def __getitem__(self, key):
        if isinstance(key, slice):
            return Track(self._pts[key])       # 同类型，可继续链式切
        if isinstance(key, int):
            return self._pts[key]              # 转发给 list，负索引自动生效
        raise TypeError(f"索引必须是 int 或 slice，收到 {type(key).__name__}")

这段代码只有 10 行，却把契约清单里最关键的三条都落实了：类型分派、切片返回同类型、非法类型明确报错。内部用 list 转发的写法顺带解决了负索引和越界——这两件事由 list 保证，不需要重写。如果你的数据不在 list 里，就必须回到第二节那张表，手工补齐负索引换算和 IndexError。

写自定义序列的验收标准很简单：把你的对象和一个等价的 list 放在同一段代码里互换，行为应该看不出差别。凡是看出差别的地方，都是某个协议方法没实现或实现得不够像。

  • 继承 collections.abc.Sequence，让它替你补齐 __contains__ / __iter__ / index
  • __getitem__ 里先 isinstance(key, slice) 分派，再处理整数
  • 切片返回同类型对象，保证 obj[1:5][0:2] 这类链式操作连贯
  • 自己算下标时补上 if i < 0: i += len(self)，并在越界时抛 IndexError
  • 需要按长度裁剪时用 key.indices(len(self))，不要手写裁剪逻辑
  • 要让改动对调用方可见时用 lst[:] = new，而不是重新绑定名字
  • 处理大块二进制数据用 bytearray + memoryview，用完 release()
  • 把切片当成不会出错的操作——它越界只会静默裁剪，不会提醒你参数算错了
  • __getitem__ 越界时返回 None，这会让 for 循环永不终止
  • 切片赋值右侧写字符串（x[1:3] = "ab"），它会被逐字符展开
  • 用带步长的切片赋值时给不等长的右侧，直接 ValueError
  • 自定义类的切片返回 list，导致下一步操作 AttributeError
  • 在热路径上对大 bytes 反复切片，每次都是一次完整复制
  • 把 NumPy 的切片语义套到内置列表上（或反过来），两者一个给视图一个给副本

Q&A

只实现 __getitem__ 和 __len__，为什么 for 循环就能跑？
因为 Python 保留了一条旧式迭代协议的回退路径。iter() 拿到对象时会先找 __iter__，找不到就退一步看有没有 __getitem__；如果有，它会构造一个内部迭代器，用 0、1、2 这样递增的整数不断调用 __getitem__，直到某次调用抛出 IndexError 才判定序列结束。所以这条路径能不能正常工作，完全取决于你有没有在越界时抛 IndexError：抛别的异常会穿透到调用方，返回 None 会导致死循环。这套机制是 Python 2 时代的遗产，能用但语义模糊，也无法表达惰性序列，所以新代码应该显式实现 __iter__。
为什么 x[7] 会报错，而 x[2:7] 不报错？
因为两者的契约不同。单个下标表达的是「精确寻址」，你指名要第 7 个元素，那个位置不存在就必须失败，否则调用方会拿到一个错的值继续算下去。切片表达的是「取这一段」，语义上更接近一个范围查询，所以语言选择把越界的边界裁剪到合法范围内，有多少给多少。这个设计让 x[:10] 这类「取前十个，不够就全给我」的写法非常方便，但代价是它会把「参数算错了」这个事实一起吞掉。实践上的结论是：凡是切片的边界来自外部输入或计算结果，就别指望切片替你校验，要自己判断 start 是否已经超出长度。
x[::-1] 是怎么工作的，它比 reversed(x) 好吗？
x[::-1] 构造的是 slice(None, None, -1)，step 为负时解释器从尾部向头部遍历，产出一个全新的反转对象。reversed(x) 完全不同，它返回一个迭代器，不复制任何数据，只在你逐个取值时反向索引。所以选择取决于你要什么：需要一个能反复使用、能再次索引的反转结果就用切片；只是想倒着遍历一遍就用 reversed()，它对大列表能省下整份副本的内存。另外 reversed() 要求对象实现 __reversed__ 或者同时有 __len__ 和 __getitem__，而 [::-1] 只要求 __getitem__ 能处理 slice。
x[:] = y 和 x = y 到底差在哪？
前者是原地操作，后者是重新绑定名字。x[:] = y 调用 x.__setitem__，把 x 这个列表对象的内容整体换成 y 的元素，对象身份不变，因此所有持有这个列表的引用都会看到新内容。x = y 只是让名字 x 指向另一个对象，原来那个列表毫发无损，别处的引用还指着旧数据。这个差别在函数内部尤其重要：想清空调用方传进来的列表必须写 lst[:] = [] 或 lst.clear()，写 lst = [] 对调用方毫无影响。判断方法很简单——问一句「我是想改这个对象，还是想改这个名字」。
带步长的切片赋值为什么要求长度严格相等？
因为带步长的切片选中的是一组不连续的坑位，个数在赋值前就已经确定了。x[::2] 在长度 5 的列表上选中位置 0、2、4 共 3 个坑，解释器能做的只是把 3 个新值填进这 3 个坑，它没有办法为多出来的元素在中间腾地方——那会破坏其余元素的相对位置。不带步长的切片选中的是一段连续区间，整段可以被任意长度的新内容替换，剩余部分顺势前移或后移，所以长度自由。不满足等长要求时的报错信息写得很直白：attempt to assign sequence of size 4 to extended slice of size 3。
什么时候该用 memoryview，什么时候是过度设计？
判断标准是数据规模和切片频率。memoryview 的收益来自省掉复制，所以数据越大、切片次数越多，收益越明显；对几 KB 的小数据，视图对象本身的创建开销反而可能让代码变慢。典型值得用的场景有三类：解析大二进制文件或网络协议、把大缓冲区分片交给底层接口（readinto、recv_into）、以及需要在不复制的前提下原地修改某一段。代价也要算进去：视图和底层缓冲区共享数据，改一边另一边立刻可见；视图存活期间 bytearray 不允许扩容，否则抛 BufferError，所以用完要记得 release()。如果你的数据是小的、不可变的、用完就扔的，普通切片更简单也更安全。
自定义序列类的切片，返回 list 还是返回自己这个类型？
应该返回自己这个类型。内置类型全都遵守这条约定：str 切出 str，tuple 切出 tuple，list 切出 list。遵守它的实际好处是链式操作不会断裂——如果 obj[1:5] 返回的是 list，那么这个结果身上就没有你自定义的任何方法，再切一次或者调用自定义方法会直接抛 AttributeError，而且这个错误往往出现在离根因很远的地方。实现上并不麻烦，在 __getitem__ 里判断参数是 slice 之后，把切出来的底层数据重新包成自己的类型即可。唯一要注意的是构造成本：如果你的类初始化时做了很重的工作，可能需要一个轻量的内部构造路径。
collections.abc.Sequence 值得继承吗，还是自己写全套方法？
绝大多数情况值得继承。它是一个混入基类，只要你提供 __len__ 和 __getitem__，就自动获得 __contains__、__iter__、__reversed__、index()、count() 的可用实现，同时让 isinstance(obj, Sequence) 返回真，便于别人对你的类型做检查。它的默认实现都是基于逐个取值的 O(n) 通用版本，这是它唯一的局限：如果你的结构有特殊性质（例如内部有序可以二分查找，或者元素存在哈希集合里可以 O(1) 判断包含），就应该覆盖掉对应方法。需要可变语义时换成 MutableSequence，它额外要求 __setitem__、__delitem__ 和 insert，换来 append、extend、pop、remove 一整套。
