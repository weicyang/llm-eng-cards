性能工作里真正稀缺的不是技巧，而是「知道时间花在哪」。技巧网上到处都是，而一个能复现的测量方法只能自己搭；没有它，你写下的每一行优化都只是在赌。

一、优化的前置条件：先有指标，再有基线，最后才是目标

「这个接口有点慢，你优化一下」是一个无法执行的需求。慢是多少毫秒？在什么负载下？是所有请求都慢还是一小部分慢？接受到多少算优化完成？这四个问题任何一个答不上来，后面的工作就没有验收标准——你只能凭感觉改，改完凭感觉说「快了」。

所以优化的第一步不是打开剖析器，而是依次确定三样东西：指标（用什么数衡量快慢）、基线（当前这个数是多少）、目标（改到多少就停）。这三样缺一不可，而且顺序不能倒。

为什么凭直觉猜热点几乎总是猜错

人看代码时对「重」的判断来自结构复杂度：三重嵌套循环看起来很重，一行属性访问看起来无害。但实际耗时等于单次成本 × 调用次数，再加上等待外部系统的时间，这三个因子里只有第一个能从代码结构上看出来。

于是典型的误判长这样：那个吓人的三重循环在真实数据上只跑了 12 次，总耗时 0.4 毫秒；而某个看起来人畜无害的 obj.config.timeout，因为在一个百万级的循环里，贡献了 30% 的 CPU 时间。更常见的是第三种——整个函数 95% 的时间在等一个数据库连接，而你盯着剩下 5% 的纯计算改了一下午。

代码的「看起来重」和「实际耗时」之间几乎没有相关性。前者由嵌套深度决定，后者由调用次数和等待决定，而这两个量都不写在代码里。

平均值会掩盖问题，必须看分位数

假设一个接口 1000 次调用里有 950 次是 20 毫秒，50 次是 2000 毫秒。平均延迟是 119 毫秒，看起来不算灾难；但每 20 个用户里就有 1 个等了 2 秒。平均值把这批人的体验平摊掉了，而他们才是会来投诉的人。

所以延迟要看分布，标准做法是报 P50（中位数，典型体验）、P95 与 P99（尾部，最差体验）。长尾通常有独立于主路径的成因：缓存未命中、垃圾回收停顿、连接池排队、下游重试、冷启动——这些都不会在平均值上留下明显痕迹，却会在 P99 上非常显眼。

同一批请求的两种看法 ───────────────────────────────────────────────────────── 请求数 ▲ │ ████████████ │ ████████████ │ ████████████ │ ████████████ │ ████████████ ██ └─┴──────────┴──────────────────────────────────┴┴──▶ 延迟 20ms │ 2000ms │ 平均值 119ms ─┘ 落在没有任何请求的空白区， 它既不代表典型体验，也不代表最差体验 P50 = 20ms ← 大多数人的真实感受 P95 = 20ms ← 还没触到尾巴 P99 = 2000ms ← 投诉来自这里 推论：只报平均值的监控面板，等于把 5% 的最差体验隐藏了

常用指标各自能回答什么

指标它回答什么问题什么时候会骗你
吞吐（QPS / 条每秒）系统单位时间能做完多少活限流或客户端并发不足时，测到的是压测端的上限，不是服务端的
平均延迟几乎什么都回答不了只要分布有长尾就失真；两个体验天差地别的系统可以有同一个均值
P50 延迟典型用户的感受尾部恶化时它可以完全不动，掩盖正在扩大的故障面
P95 / P99 延迟最差那批用户的感受样本量太小时噪声极大；一天只有 300 次调用时 P99 由 3 个点决定

这张表可以合成一条经验：延迟看分位数，容量看饱和度，CPU 利用率只在 CPU 密集场景里有意义。三者一起看才能区分「算得慢」和「排队久」，而这两种慢的处理方式完全不同。

一条硬纪律：没有可复现的测量方法，就不要开始优化。可复现意味着四件事都固定下来——固定的输入数据（同一份样本，不是随机生成）、固定的环境（同一台机器、同样的并发、预热之后再测）、足够的重复次数（至少几十次，取分布而不是单次）、以及每次都输出同一组数字。做不到这四点，你后面每一次「快了 15%」都无法和机器抖动区分开，改对改错全靠运气。

def bench(fn, arg, rounds=200, warmup=20):   # import statistics, time
    for _ in range(warmup):
        fn(arg)                              # 预热：排除冷缓存与首次导入
    xs = []
    for _ in range(rounds):
        t0 = time.perf_counter()
        fn(arg)
        xs.append((time.perf_counter() - t0) * 1000)
    q = statistics.quantiles(xs, n=100)      # 3.8 起提供
    return {"p50": q[49], "p95": q[94], "p99": q[98]}

这段骨架很短，但它把上面四件事都固定住了：预热排除首次导入与缓存冷启动的干扰，重复采样得到分布，time.perf_counter 提供单调的高精度计时，返回的是分位数而不是一个平均值。把它存进仓库，它就是这次优化的基线脚本——之后每一次改动都用它重跑一遍。

二、工具分层：从打点计时到采样剖析

剖析工具不是越精细越好。精细意味着开销大，开销大意味着两个后果：跑不进生产环境，以及扭曲你要测的东西本身。所以实际做法是分层——用粗的工具定位到大致区域，再用细的工具确认到具体行。

由粗到细的四层，箭头方向 = 排查推进方向 ───────────────────────────────────────────────────────────── 第 0 层 端到端埋点 粒度：一次请求 / 一个阶段 perf_counter 开销：可忽略 可上生产 │ 回答：慢在哪个阶段 ▼ 第 1 层 采样剖析 粒度：函数调用栈（按频率抽样） 栈采样类工具 开销：小（个位数百分比） 可挂到已运行的进程 │ 回答：CPU 时间集中在哪条调用链 ▼ 第 2 层 确定性剖析 粒度：每次函数调用，逐个计数 cProfile+pstats 开销：大（常见 1.3 倍以上，调用密集时更高） │ 回答：哪个函数被调了多少次、累计多久 ▼ 第 3 层 行级 / 内存剖析 粒度：单行代码 / 单次内存分配 tracemalloc 等 开销：很大，只对已锁定的单个函数开 回答：这个函数内部是哪一行在烧时间或占内存 常见错误：跳过第 0 层直接上 cProfile， 结果剖出来一堆函数，却不知道它们属不属于慢的那条路径

四类工具的取舍

工具 / 类别粒度开销适用场景
time.perf_counter 手工打点你自己划定的代码区间可忽略（一次调用的量级）开发机与生产都可以，是阶段耗时埋点的默认做法
timeit（含 python -m timeit）一小段表达式或语句不适用，它本身就是测量仅限开发机做微基准，对比两种写法哪个快
确定性剖析：cProfile + pstats每个函数的调用次数与耗时大，且对「调用次数多、单次很短」的代码惩罚更重开发机 / 预发环境跑离线任务或单条请求
采样剖析（py-spy 属于这一类）按固定频率抓取调用栈小，通常个位数百分比生产首选：可以挂到一个已经在跑的进程上，不需要改代码重启
行级剖析（需第三方库）函数内逐行耗时很大只在已经锁定某个函数之后，对那一个函数临时开启
tracemalloc（标准库）内存分配按代码行或调用栈归因大，时间和内存都显著增加查内存增长与疑似泄漏，开发机或可控的灰度实例

表里第三行和第四行的差别值得展开。确定性剖析在每次函数进出时都记一笔，所以调用计数绝对准确，但也因此给「被调用一百万次的小函数」额外加上了一百万次记账成本——剖出来的相对耗时会向这类函数倾斜。采样剖析则是每隔固定时间（比如 100 赫兹）抓一次当前栈，谁在栈上出现得多谁就占得多，开销与程序的调用密度无关，代价是它给不出精确的调用次数，短时间运行的函数也可能一次都没被采到。

确定性剖析回答「调了多少次」，采样剖析回答「时间在哪」。生产环境上你几乎只能用后者，而它恰好也是更该先看的那个。

计时函数别选错

函数测的是什么单调什么时候用它
time.perf_counter()最高可用分辨率的经过时间（含休眠与等待）是测代码块耗时的默认选择
time.perf_counter_ns()同上，返回整数纳秒是极短区间，避免浮点误差累积
time.monotonic()单调时钟，分辨率通常低于前者是超时判断、限流窗口这类长区间
time.process_time()本进程的 CPU 时间，不含休眠与 I/O 等待是区分「在算」还是「在等」的关键工具
time.time()挂钟时间（Unix 时间戳）否记录事件发生时刻；不要用来测耗时，会被校时跳变影响

第四行藏着一个很实用的技巧：同一段代码分别用 perf_counter 和 process_time 各测一次，两者相减就是等待时间。如果一段代码耗时 900 毫秒而 CPU 时间只有 8 毫秒，那它在等外部系统，本地任何算法优化都不会有效果——这个判断只要两行代码，却能省掉整场误入歧途的优化。

# 微基准：只在开发机上、只用来对比两种写法
import timeit

setup = "xs = list(range(10_000)); s = set(xs)"
a = timeit.repeat("9999 in xs", setup=setup, number=1000, repeat=5)
b = timeit.repeat("9999 in s",  setup=setup, number=1000, repeat=5)
print(min(a), min(b))   # 取最小值：它受其他进程干扰最小

timeit 有两个默认行为要知道。一是它在计时期间关闭垃圾回收，这让结果更稳定，但也意味着它测不出分配压力带来的 GC 成本——这部分见 PY23。二是官方建议看 repeat 结果里的最小值而不是平均值：噪声只会让某次变慢，不会让它变快，所以最小值最接近真实下限。

# 确定性剖析：把结果落盘，再用 pstats 慢慢看
# 命令行： python -m cProfile -o out.prof your_script.py
import cProfile, pstats

with cProfile.Profile() as pr:
    run_one_request(sample)

st = pstats.Stats(pr).strip_dirs()
st.sort_stats(pstats.SortKey.TIME).print_stats(15)   # 按自身耗时
st.sort_stats(pstats.SortKey.CUMULATIVE).print_stats(15)

cProfile.Profile 从 Python 3.8 起支持上下文管理器写法，比 enable() / disable() 更不容易漏关。pstats.SortKey 是排序键的枚举（3.7 引入），比传字符串安全。另外补一条版本信息：Python 3.12 引入了 sys.monitoring（PEP 669），提供低开销的事件监控接口，它主要是给剖析器和调试器作者用的底层设施，日常排查仍然直接用上面这些成品工具。

三、怎么读剖析结果：三个数比一堆数有用

第一次看 pstats 输出的人通常会被几百行函数名淹没，然后随便挑一个眼熟的开始改。实际上有用的信息只有三列，而且它们回答的是不同的问题。

字段含义用来回答
ncalls调用次数（递归时显示为「总次数/原始次数」）是不是在重复做同一件事
tottime自身耗时：函数体内的时间，不含它调用的子函数真正在烧 CPU 的是谁
cumtime累计耗时：含全部子调用的时间这条慢路径从哪个入口进来的
percall上述耗时除以调用次数单次是不是异常贵

两个耗时的分工很明确：按 cumtime 排序是自顶向下找入口，最顶上永远是 main 之类的东西，你要找的是那个第一次出现的、属于你业务的函数；按 tottime 排序是自底向上找干活的地方，排在前面的就是真正消耗 CPU 的叶子。两个榜单都要看：只看 cumtime 会停在无意义的外层，只看 tottime 会看到一堆底层库函数却不知道谁在调它们。

调用次数异常，往往比单次耗时更值得看

一个函数单次 0.3 毫秒不算慢，但如果 ncalls 是 48000 而你处理的只有 800 条数据，那真正的问题不是它慢，是它不该被调这么多次。这类信号几乎总指向同一批成因：循环内部重复做本可以提到循环外的工作、每条记录单独发一次查询的 N+1 模式、以及在遍历中反复构造同一个对象或重复编译同一个正则。

这也是确定性剖析唯一不可替代的价值——采样剖析给不出准确的调用次数。所以实际节奏常常是：先用采样剖析在生产上确认「时间在这条链路上」，再在开发机用 cProfile 对同一条链路跑一遍，看调用计数有没有离谱。

典型的调用树（宽度 = 累计耗时，缩进 = 调用层级） ═══════════════════════════════════════════════════════════ handle_request cum 1010ms ████████████████████████████████████████████████████████ ├─ load_orders cum 905ms │ ████████████████████████████████████████████████ │ └─ cursor.execute ★ 平顶 tot 900ms │ ███████████████████████████████████████████ │ ↑ 宽且没有子调用 = 时间真的耗在这里 │ 但这是在「等数据库」，不是在「算」 │ ├─ render_rows cum 80ms │ ████ │ ├─ fmt_amount ncalls 48000 ★ 次数可疑 tot 46ms │ │ ██ │ └─ to_dict ncalls 800 tot 28ms │ █ └─ json.dumps tot 20ms █ 该先看哪里： 1. 找最宽的「平顶」——自身耗时大、没有子调用，那是真正的热点 2. 再扫一遍 ncalls 明显超出数据量的行，那是重复工作的信号 3. 平顶如果是 I/O 调用（execute / recv / read）， 说明瓶颈在外部系统，本地优化到此为止

火焰图是同一份数据的另一种画法：横轴宽度仍然是耗时占比，但横轴不代表时间先后，同名函数会被聚合到一起，纵轴是调用深度。读法和上面一致——找宽的平顶，忽略窄的尖刺。一个常见误读是看到某个函数在图上出现了很多细条就觉得它有问题，实际上碎片多只说明它出现在多条不同的调用链上，把它们加起来才有意义。

累计耗时告诉你「从哪扇门进去的」，自身耗时告诉你「屋里谁在干活」。只看门会一直在走廊里打转，只看人会不知道该关哪扇门。

四、优化的优先顺序：这一节比任何技巧都重要

拿到剖析结果之后，多数人的下一个动作是搜「Python 怎么让这个函数更快」，然后得到一堆微优化建议。这是顺序错了。同一个热点，不同层次的改法收益能差三个数量级，而该先试哪一层是有固定次序的——从「能不能不做」开始，一直到「做得更快一点」结束。

优化的六级阶梯：从上往下试，不要跳级 ═══════════════════════════════════════════════════════════ ① 减少工作量 去重复、加缓存、批量化、过滤下推到数据源 收益 ██████████ 「这件事根本不用做」——唯一能做到 10 倍以上的一层 ↓ 上一层榨干了再往下 ② 数据结构与复杂度 list 查找换 set、循环嵌套换索引表、换算法 收益 ████████ 数据量越大收益越大，小数据上可能看不出差别 ↓ ③ 减少跨边界开销 数据库往返、网络调用、跨进程序列化 收益 ██████ 一次往返的固定成本远大于其中的计算 ↓ ④ 用更快的实现 向量化、成熟的原生扩展库 收益 ████ 换库通常划算，自己写 C 扩展通常不划算 ↓ ⑤ 换并发模型 I/O 密集用异步或线程，CPU 密集用多进程 收益 ███ 不减少总工作量，只是让它们重叠或并行 ↓ ⑥ 微优化语言细节 局部变量、避免属性查找、换写法 收益 █ 通常几个百分点，且让代码更难读 代价方向恰好相反：越往下改动越局部、越安全， 越往上越需要动设计，但收益也越大

① 减少工作量：唯一能带来数量级收益的一层

这一层的核心问题不是「怎么算得更快」，而是「这件事能不能不做、少做、或者晚点做」。四种常见形态：把循环内不变的计算提到循环外；给纯函数加缓存（functools.cache 与 functools.lru_cache，用法见 PY14）；把 N 次单条操作合并成 1 次批量操作；把过滤条件下推到数据源，让数据库或文件层只返回需要的行，而不是取回全部再在 Python 里筛。

最后一条的收益常被低估。取回 50 万行再用列表推导筛出 300 行，和让数据库用索引直接返回这 300 行，Python 侧的代码看起来只差一行，但前者要为 50 万行付出网络传输、反序列化和对象创建的成本。惰性求值与生成器可以减少内存峰值（见 PY13），但它减不掉「数据已经被传过来了」这件事——真正的解法是一开始就别传。

# N+1：800 条记录发了 801 次查询
orders = db.query("select id, user_id from orders limit 800")
for o in orders:
    o.user = db.query("select * from users where id = ?", o.user_id)

# 批量化：2 次查询，外加一次内存中的哈希关联
ids = {o.user_id for o in orders}
users = {u.id: u for u in db.query_in("select * from users where id in", ids)}
for o in orders:
    o.user = users[o.user_id]

② 数据结构与算法复杂度

这一层的典型案例是「在一个 list 里反复做成员判断」。x in list 是 O(n) 的线性扫描，x in set 是平均 O(1) 的哈希查找；放在一个同样 n 量级的循环里，前者是 O(n²)，后者是 O(n)。n 等于 100 时你察觉不到，n 等于 10 万时差距就是「秒」和「毫秒」的区别。各容器操作的复杂度见 PY03。

需要提醒的是反方向也存在：为了「复杂度更好」而引入的字典、索引、堆，在数据量很小的时候可能比朴素的线性扫描更慢，因为常数项和内存分配成本占了主导。所以这一层同样要测，不能只看大 O。

③ 减少跨边界开销

每一次跨进程、跨机器的调用都有一笔固定成本：连接获取、协议编解码、序列化反序列化、网络往返。这笔成本和你要传的数据量关系不大，和往返次数关系极大。所以这一层的手段几乎都是「合并往返」：批量查询、管道化、连接复用、一次多进程任务里传大块数据而不是频繁传小块（跨进程传对象要经过序列化，还可能触发意外的深拷贝，语义细节见 PY10）。

④⑤⑥ 剩下三层

换更快的实现，指的通常是把手写的数值循环换成向量化库，或者把手写的解析换成成熟的原生扩展实现。判断标准很简单：换现成的库通常划算，自己写 C 扩展通常不划算，因为后者带来的构建复杂度、跨平台编译和调试难度是长期成本。

换并发模型要先想清楚它不减少总工作量，只是让工作重叠（I/O 等待期间去做别的）或并行（多核同时算）。它对「在等」的场景有效，对「在算」的场景需要绕开全局解释器锁才有效。这一整套判断属于并发那一组卡片的内容（负载类型与模型选型见 PY25，剖析发现热点在等待时的异步改造见 PY28），这里只强调它的位置：排在减少工作量之后。给一个跑着 O(n²) 算法的函数套上并发，只是让几个核同时跑慢算法。

手段、收益量级与代价

手段典型收益量级代价
去掉重复计算 / 加缓存数倍到数十倍，取决于命中率与重复度缓存一致性、内存占用、失效逻辑的复杂度

前两层在回答「能不能不做这件事」，后两层在回答「这件事能不能做快一点」。经验上，绝大多数真正的胜利来自第一个问题，而绝大多数投入浪费在第二个问题上。

五、Python 特有的性能常识：全是微优化，别当第一步用

下面这些都属于上一节的第 ⑥ 层。它们是真实存在的效应，在确认为热点的循环里有可测量的收益；但在非热点处使用，唯一的效果是让代码更难读。本节所有内容的前提都是：剖析已经指向了这段代码。

属性查找和函数调用不是免费的

写 self.cache.get(k) 时，解释器要先取 self、再查 cache 属性、再查 get 方法，最后才发起调用。每一步都是一次字典查找，还可能触发描述符协议。单次成本极小，但乘以百万次循环就能被测出来。对应的手法是在进入热循环之前把方法绑定到局部变量。

# 只在确认这是热点循环之后才这么写
def collect(self, items):
    out = []
    append = out.append          # 把方法取到局部变量
    fmt = self.formatter.format  # 把多级属性查找提到循环外
    for it in items:
        append(fmt(it))
    return out

要强调这是最后一步而不是第一步：如果 fmt 本身花 200 微秒，省下的那几纳秒查找成本完全不可见。这类改写只在循环体极短、次数极多时才有意义。

字符串拼接的复杂度陷阱

字符串是不可变对象，s = s + x 语义上要新建一个字符串并复制全部已有内容，在循环里就是 O(n²)。正确做法是把片段收集进列表，最后用 "".join(parts) 一次性拼成，整体 O(n)。

这里有个容易被误传的细节：CPython 对 s += x 存在一个原地扩展的优化，条件是该字符串只有一个引用。它能让很多循环拼接在实测中表现得接近线性，但这是实现细节而非语言保证——一旦字符串被别处引用，或换到别的实现上，就退化回 O(n²)。所以规则仍然是用 join，编码与字符串的更多细节见 PY06。

局部变量、内置函数与推导式

局部变量的读取编译成 LOAD_FAST，走的是数组下标；全局与内置名字要走模块字典乃至内置字典的查找。这就是「把全局常量在函数开头赋给局部变量」这类写法的来源。补一句版本信息：Python 3.11 起对全局查找做了内联缓存优化，这个差距比过去小了，但方向没变。

内置函数（sum、min、any、sorted）与列表推导式通常快于等价的手写循环，原因是循环体在 C 层执行，省掉了每轮迭代的字节码调度。但注意不适用于带复杂条件或副作用的情形，那时推导式只是把同样的 Python 代码换了个写法，快不了多少，可读性反而更差（见 PY13）。

换版本本身就是一次免费优化

CPython 近几个版本持续有性能改进：3.11 是其中最显著的一次（官方公布的基准套件整体提升在 10%–60% 区间，具体幅度高度依赖负载类型），3.12 与 3.13 继续在解释器与内存布局上推进，3.13 还引入了一个默认关闭的实验性 JIT（PEP 744）。对纯 Python 计算密集型代码，升级解释器有时比你改一周代码收益更大；而对以 I/O 等待为主的服务，升级几乎看不出差别——同样要先测。

微优化项为什么有效量级什么时候别用
方法绑定到局部变量省掉每轮的属性查找与描述符触发百分之几，循环极短时更明显循环体本身就重，或循环次数很少
"".join() 代替循环 +=避免反复复制已有内容大 n 时可达数量级片段只有两三个，直接拼更清楚
全局名提为局部名LOAD_FAST 走数组，不查字典百分之几；3.11 起差距缩小非热点代码，会牺牲可读性

升级解释器版本解释器自身的持续优化依负载而定，I/O 密集接近无感依赖还没有对应版本的预编译包
减少临时对象分配降低分配与垃圾回收压力分配密集型场景明显为省对象而把代码写成一团（见 PY23）

微优化的正确用法是收尾，不是开场。它能把已经对的方案再挤出几个百分点；它救不了一个错的方案，只会让这个错的方案更难被看懂和替换。

六、优化的纪律与收尾：知道什么时候停

优化最容易失控的地方不是技术，是流程。一次性改五处、改完不重测、觉得「应该更快了」就合并——这样做的结果是：性能可能确实变好了，但没人知道是哪一处起了作用，也没人知道有没有某一处其实拖慢了。

四条可执行的纪律

每次只改一处，改完立刻用基线脚本重测。这条看起来啰嗦，实际能省下大量时间：一旦某次改动没有收益，立刻回退，你就永远不会积累一堆「不知道有没有用但不敢删」的复杂代码。

基线脚本进仓库，和测试放在一起。它不是一次性的草稿。三个月后有人报告同一个接口又慢了，有这个脚本就能在十分钟内拿到对比数据，没有它就要从头搭一遍测量环境。

把性能断言写进测试，防止回退。但这里有个陷阱：直接断言墙钟时间（例如「必须小于 50 毫秒」）在 CI 上极易抖动成 flaky 测试，因为构建机负载不可控。更稳的做法是断言操作计数——这次请求最多发几条 SQL、最多调几次外部接口、最多读几次文件。计数是确定的，不受机器快慢影响，而且它恰好能拦住最常见的性能回退：有人无意中在循环里加了一次查询。

def test_no_n_plus_one(db_spy, client):
    client.get("/orders?limit=800")
    # 断言操作次数而不是耗时：结果确定，不受 CI 机器负载影响
    assert db_spy.query_count <= 3
    assert db_spy.max_rows_fetched <= 2000

达到目标就停。目标是在第一节里定下的那个数。到了就收工，把剩下的时间还给功能开发。继续优化的边际收益递减，而代码复杂度的增长是线性甚至更快的——这是很多性能工作最后变成技术债的路径。

一条反向判据：如果热点在等待外部系统，本地优化毫无意义。用第二节那个办法可以在两分钟内确认——同时测 perf_counter 和 process_time，如果 CPU 时间只占经过时间的很小一部分，说明进程绝大多数时候在阻塞等待。这时候有效的动作只有三类：让外部系统本身变快（加索引、调查询、扩容），减少对它的调用次数（缓存、批量、合并往返），或者让等待重叠起来（并发发起）。把本地那段计算从 80 毫秒优化到 12 毫秒，在 900 毫秒的等待面前是看不见的。

一次真实的三天弯路

事故复盘：订单列表接口 P95 端到端 1010 毫秒，用户持续投诉。负责人打开 cProfile，看到 render_rows 这条链路上函数最多、名字最眼熟，判断瓶颈在「内部数据加工」，随后花了三天（约 22 人时）做优化：把逐行格式化改成批量、消掉一处重复的字典构造、给两个纯函数加了缓存，内部计算从 80 毫秒压到 12 毫秒——这部分优化本身是成功的，收益 85%。

但端到端 P95 只从 1010 毫秒降到 942 毫秒，降幅 6.7%，用户完全无感。第四天有人补了阶段埋点，才发现真正的耗时是一条 where status = ? and created_at > ? 的查询走了全表扫描，单独占 900 毫秒。加一个复合索引，耗时 900 毫秒降到 35 毫秒，改动一行 DDL，耗时 20 分钟，端到端 P95 落到 77 毫秒。

事后算账：真正生效的那一处改动占总投入时间的 1.5%，贡献了 92% 的收益。而如果第一天就先做阶段耗时分解，那三天中的大部分本可以不发生——它们不是白做（12 毫秒确实比 80 毫秒好），只是顺序错了。

Q&A

cProfile 报出来的总耗时比程序实际运行时间还长／对不上，是不是坏了？
没坏，这是确定性剖析的固有特性。它在每一次函数进入和退出时都要记账，这笔开销被算进了统计里，所以剖析状态下的绝对数字一定大于真实运行时间，常见放大在 1.3 倍以上，函数调用越密集放大越明显。更需要警惕的是它对相对比例也有扭曲：一个被调用一百万次的小函数，记账成本占比很高，在报告里会显得比实际更重；而一个只调用一次的大函数几乎不受影响。所以正确用法是把 cProfile 的输出当成「相对排序和调用次数」的来源，而不是耗时的真值；要拿准确的绝对耗时，用 perf_counter 在不开剖析的情况下单独测那一段。
为什么不建议直接用 timeit 测一整个业务函数？
三个原因。第一，timeit 默认在计时期间关闭垃圾回收，业务函数往往会产生大量临时对象，关掉 GC 等于把一部分真实成本从账单里抹掉了。第二，它会把同一段代码重复执行很多次，缓存、连接池、数据库查询缓存都会在第二次之后命中，测出来的是热态性能，而线上大量请求处于冷态。第三，业务函数通常有副作用——写库、发消息、改全局状态，重复执行成百上千次要么报错要么污染数据。timeit 的定位是微基准：对比两种纯计算写法哪个快。测业务函数请用第一节那种带预热、报分位数的基准骨架。
能在生产环境上开剖析吗？
分工具看。采样剖析可以，这正是它存在的意义——开销通常在个位数百分比，而且可以挂到一个已经在跑的进程上，不需要改代码、不需要重启，py-spy 就属于这一类。确定性剖析（cProfile）原则上不要在生产全量开，开销大且会扭曲结果；如果确实需要，限定在单个灰度实例、按采样比例只剖一小部分请求、并设置自动关闭的兜底。tracemalloc 同理，它对时间和内存的影响都很显著，只在排查内存增长时短时开启。另外永远要给这类开关准备一个「不重启就能关掉」的路径，否则忘记关就变成了新的事故。
监控上平均延迟明明降了，为什么用户还在说慢？
因为平均值对尾部不敏感。假设你把 95% 的快请求从 25 毫秒优化到 15 毫秒，平均值会明显下降，但那 5% 卡在两秒的请求一点没变——而抱怨恰恰全部来自这 5%。更糟的情况是尾部其实在恶化：慢请求从 2 秒涨到 3 秒，因为快请求变多而被稀释，平均值反而继续下降，监控面板一片绿色。所以延迟指标要看分位数，并且至少看到 P99；同时看请求量，样本太少时 P99 本身噪声很大。如果尾部和主路径的成因不同（缓存未命中、GC 停顿、连接池排队），还需要把这些请求单独打标采样，否则在聚合数据里永远找不到它们。
加了缓存为什么没变快，有时候反而更慢？
先看命中率，这是唯一要紧的数字。命中率低的缓存等于给每次调用增加了一次查找加一次写入的成本，本来就慢的路径会更慢。命中率低通常有三个来源：缓存键里混进了每次都不同的成分（时间戳、请求 ID、未排序的集合），缓存容量太小导致频繁淘汰，以及被缓存的函数本来就很少被重复调用。第二种可能是缓存位置太靠内层——在最底层的小函数上缓存，外层的重复工作一点没省；往上挪一层，一次命中能跳过整条链路。第三种是缓存的东西本身不贵，省下的计算还不够付哈希键的成本。无论哪种，判断方法都一样：把命中率打出来，再用基线脚本对比开关缓存的两组数字。
火焰图里最宽的那块是 socket 读取，接下来该干什么？
这说明进程在等，不在算，本地代码优化的空间已经基本为零。有效的动作只有三类。一是让被等的那一方变快：定位到具体是哪个下游，是数据库就去看执行计划和索引，是外部接口就去看它的服务端指标。二是减少等待次数：合并往返、批量请求、加缓存，把 N 次调用降成 1 次。三是让等待重叠：多个互不依赖的外部调用并发发起，总耗时从「求和」变成「取最大值」——这条属于并发模型的选择，需要评估下游的承载能力，别把自己的延迟问题转嫁成下游的过载。要特别避免的动作是继续在 Python 侧抠计算，那部分在总账里可能只占百分之几。
热点函数要不要重写成 C 扩展？
绝大多数情况下不要，至少不要作为早期选项。先确认前三层都榨干了：这段计算是不是重复做了、数据结构对不对、能不能批量。然后优先考虑换用成熟的原生实现——如果你的热点是数值循环，向量化库已经把 C 层的工作做完了，收益和自己写扩展接近，成本却低一个数量级。自己写扩展的真实代价不在写的那几天，而在之后：需要维护构建链路、为每个平台和 Python 版本出预编译包、调试时栈跟踪跨语言、内存错误会直接让解释器崩溃而不是抛异常。只有当热点非常集中（少数几个函数占了绝大部分时间）、算法已经确定不会再变、并且现成的库确实覆盖不了时，它才是划算的。
性能测试在 CI 上老是随机失败，要不要干脆删掉？
不要删，换一种断言方式。墙钟时间在共享的 CI 机器上本来就不可靠：邻居任务、缓存状态、CPU 降频都会让同一段代码的耗时浮动几十个百分点，硬卡阈值必然 flaky，而 flaky 测试最后的命运是被所有人忽略。替代方案是断言确定性的量：一次请求最多发几条 SQL、最多调几次外部接口、最多加载多少行数据、某个函数最多被调用几次。这些数字不受机器快慢影响，而且它们拦住的正是最常见的性能回退——有人在循环里加了一次查询、有人不小心关掉了缓存。如果确实需要盯住绝对耗时，把它挪到专用的、独占的基准机器上定时跑，用趋势告警而不是单次红绿。
