初学者卡在环境上，几乎从不是因为「不会装 Python」，而是因为不知道自己刚才那行命令用的是哪个解释器、它会去哪些目录找包。把「谁在执行」和「去哪找包」这两个问题永远能答出来，环境问题就消失了九成。

一、语言、实现与解释器：先把三层分开

「Python 慢」「Python 有 GIL」这类说法几乎每天都能看到，但它们严格来说都是错的——至少不精确。因为 Python 这个词同时指三个不同层次的东西，而这些论断只对其中一层成立。

语言规范指的是语法和语义的定义，也就是「`for x in y` 该怎么理解」这套规则，由 CPython 官方文档和 PEP（Python Enhancement Proposal，Python 改进提案）共同确定。语言实现是把这套规则真正跑起来的程序，可以有很多个。解释器则是你机器上那个具体的可执行文件，比如 /usr/bin/python3.12 或者 .venv\Scripts\python.exe。

GIL 是实现层的产物，只存在于 CPython（以及默认构建）里；PyPy 有自己的方案，而 CPython 3.14 的自由线程构建干脆把它关掉了。所以「Python 有 GIL」准确的说法是「CPython 的默认构建有 GIL」。这个区分不是咬文嚼字：等你以后排查并发性能问题时，第一步就是确认自己跑在哪个实现的哪个构建上。

语言是规则，实现是引擎，解释器是你手上这台具体的车。谈性能和并发只能谈到实现和构建，谈不到语言。

CPython 执行一段代码经过了什么

很多人以为解释型语言就是「一行一行读着执行」，CPython 并不是。它先把整个源文件编译成字节码——一种介于源码和机器码之间的紧凑指令序列——然后才由虚拟机的求值循环逐条执行这些指令。理解这一步能解释两个日常现象：为什么语法错误会在运行任何一行之前就报出来，以及 __pycache__ 目录是干什么的。

你的 hello.py │ ▼ ┌───────────────┐ 词法 + 语法分析 │ Tokenizer │ 把字符流切成 token │ ↓ │ │ Parser │ → 语法错误在这里就报了 └───────┬───────┘ （一行都还没执行） ▼ ┌───────────────┐ │ AST │ 抽象语法树，代码的结构化表示 └───────┬───────┘ ▼ ┌───────────────┐ 编译 │ Bytecode │ 一串虚拟机指令，如 LOAD_NAME / CALL └───────┬───────┘ │ ← 缓存到 __pycache__/hello.cpython-312.pyc ▼ ┌───────────────────────────────┐ │ CPython VM（求值循环） │ 逐条取指令、执行 │ ceval.c 里的那个大 switch │ ← GIL 在这一层 └───────────────┬───────────────┘ ▼ 实际的计算与 IO

字节码缓存只对 import 进来的模块生效，直接 python hello.py 跑的主脚本不会生成 .pyc。这就是为什么你会看到「被别人导入的模块有 __pycache__，入口脚本没有」。缓存文件名里带着 cpython-312 这样的标记，换版本自动失效，所以它不需要你操心；但它不应该提交到 git，标准 .gitignore 都会排除它。

注意 PyPy 那一行的限定条件。它对纯 Python 循环提速明显，但一旦你的热点在 NumPy 或者别的 C 扩展里，收益会大幅缩水甚至变成负数——因为那些代码本来就不在 Python 字节码层执行。这也是一个贯穿本系列的判断习惯：先搞清楚时间花在哪一层，再决定换什么。

二、版本怎么选：跟着支持窗口走，不跟着新特性走

CPython 从 3.9 起固定为每年 10 月发一个大版本，每个版本有大约 5 年的支持期：前 2 年左右接受常规 bug 修复，后 3 年只接受安全修复。这个节奏意味着任何时刻都有 4 到 5 个版本同时「活着」，选哪个是个真实问题。

这张表里对本系列后续内容影响最大的是 3.11 那一行的 TaskGroup。并发那一组会讲到，它正在取代 asyncio.gather 成为并发编排的默认选择——如果你的项目还锁在 3.10，那一整套写法用不上。这就是版本选择的现实意义：它决定了你能用哪套写法，而不只是快几个百分点。

选版本的第一决策依据不是「有什么新特性」，而是「我要用的那几个包在这个版本上有没有现成的预编译包」。新特性可以等，装不上依赖会直接卡住整个项目。

为什么依赖的可用性排在新特性前面

Python 包分两类：纯 Python 的包在任何版本上都能装；而带 C 扩展的包（NumPy、PyTorch、数据库驱动等）需要针对「Python 版本 × 操作系统 × CPU 架构」分别编译出wheel——一种预编译的二进制分发格式。新版本刚发布的头几个月，这些 wheel 往往还没跟上。

没有匹配的 wheel 会怎样？pip 会退而求其次去下载源码包并尝试在你机器上现场编译，这需要完整的 C/C++ 工具链，在 Windows 上失败率极高，报错信息也和真正的问题相距甚远（通常是一大段编译器输出，最后一行才是 error: Microsoft Visual C++ 14.0 or greater is required）。初学者在这里能卡上一整天，而根因只是版本选早了一步。

示例场景：某团队在新版本发布后第 3 周把 CI 的基础镜像升到最新 Python，构建时长从 4 分钟涨到 27 分钟，且 Windows 上的构建作业全部失败。排查发现 6 个依赖里有 2 个没有对应版本的 wheel，pip 转为源码编译。回退一个小版本后构建时长恢复到 4 分钟，失败归零。结论不是「不要升级」，而是升级前先跑一遍依赖的 wheel 可用性检查，不要把它留给 CI 去发现。

三、装在哪里：四条路，以及为什么 2026 年首选 uv

「装 Python」这件事之所以混乱，是因为一台机器上同时存在好几个 Python 是常态而非异常：系统自带一个、你自己装了一个、某个 IDE 顺手带了一个、每个项目的虚拟环境里还各有一个。混乱的根源不是数量多，而是你不知道 python 这个命令当下指向哪一个。

你敲下 python 之后发生了什么 ──────────────────────────── shell 按 PATH 里的顺序，从左到右找第一个叫 python 的可执行文件 PATH = /项目/.venv/bin : /opt/homebrew/bin : /usr/bin : ... ↑ 命中！ ↑ 轮不到 ↑ 轮不到 这就是「激活虚拟环境」做的唯一一件重要的事： 把 .venv 的目录塞到 PATH 最前面 所以「我装的包怎么 import 不到」几乎总是同一个问题： 装包的那个 python 和跑代码的那个 python 不是同一个 自查命令（三条，任何环境问题先跑这三条） python -c "import sys; print(sys.executable)" ← 我是谁 python -c "import sys; print(sys.prefix)" ← 我的环境根在哪 python -m pip --version ← 跟我配套的 pip 在哪

那三条自查命令值得背下来。注意第三条用的是 python -m pip 而不是 pip——这两者可能是不同的东西，第五节会解释为什么。

四条安装路径的取舍

方式能管多版本吗主要优点主要代价
系统自带（Linux/macOS）不能开箱就有不要用它装包，系统工具依赖它，装崩了会连带包管理器一起坏
官方安装包 / 包管理器勉强（手工并存）简单直接，官方签名切版本靠改 PATH，多版本并存容易搞乱
pyenv能版本切换成熟，社区方案久经考验需要本地编译，首次安装慢；Windows 支持是另一个分支项目
conda / mamba能能一并管理非 Python 的系统库（CUDA、MKL 等）自带一套独立的包体系，和 pip 混用容易冲突
uv能装解释器、管虚拟环境、锁依赖一把抓，速度快 10–100 倍工具较新，极端场景（复杂 CUDA 栈）仍可能要靠 conda 兜底

本系列默认用 uv——一个用 Rust 写的 Python 包与项目管理器。它不只是更快的 pip，而是把过去要用六七个工具（pip、pip-tools、virtualenv、pyenv、pipx、以及 poetry 的大部分职责）才能覆盖的事情收到一个命令里。对初学者的实际好处是：需要记的命令少了一个数量级。

# 装 uv 之后，从零到能跑代码只要三步
uv python install 3.12      # 装解释器（不碰系统 Python）
uv init myproject           # 建项目：pyproject.toml + .python-version
uv add requests             # 加依赖（自动建 .venv 并写入 uv.lock）
uv run main.py              # 跑代码（不需要「激活」任何东西）

系统自带的那个 Python 是操作系统的一部分，不是给你用的。把它当成只读的，所有项目都用自己的解释器和虚拟环境，一类最难排查的故障就永久消失了。

示例场景：一位新同事在 Ubuntu 上直接用 sudo pip install 升级了系统 Python 的 requests，当晚 apt 和 ufw 全部报 ImportError，机器无法安装任何软件包，最终靠手工回滚 3 个包的版本恢复，耗时约 90 分钟。触发这件事只需要一条命令，而避免它也只需要一条规则：永远不对系统 Python 执行安装或升级。看到教程里写 sudo pip install，直接换成虚拟环境里的 uv add。

四、虚拟环境不是沙箱，只是一组路径约定

虚拟环境常被描述成「隔离的沙箱」，这个比喻会带来错误预期——它不提供任何安全隔离，虚拟环境里的代码能读写你的整个磁盘。它解决的是另一个问题：依赖冲突。项目 A 需要某个库的 1.x，项目 B 需要 2.x，全局只有一份安装目录时这两个需求无法共存。

它的实现比你想的简单得多

一个虚拟环境就是一个普通目录，里面装着三样东西：一个指向真实解释器的链接或副本、一个 pyvenv.cfg 配置文件、一个空的 site-packages。启动时解释器读到 pyvenv.cfg，就把找包的根目录改到这个虚拟环境里——没有内核魔法，没有容器，只是改了搜索路径。

.venv/ ├── pyvenv.cfg ← 关键：写着真实解释器在哪 │ home = /usr/local/bin │ include-system-site-packages = false ├── bin/ (Windows: Scripts/) │ python ─────────────► 指向真实解释器的链接/副本 │ pip, pytest, ... ← 装进来的命令行工具 └── lib/python3.12/site-packages/ requests/ numpy/ ... ← 你 install 的包都落在这里 import requests 时，解释器按 sys.path 顺序找： ┌────────────────────────────────────────────────┐ │ 1. 脚本所在目录（或 -m 时的当前目录） │ ← 同名文件会遮蔽标准库！ │ 2. PYTHONPATH 环境变量里列出的目录 │ │ 3. 标准库目录 │ │ 4. .venv/lib/.../site-packages │ ← 第三方包在这 └────────────────────────────────────────────────┘ 第一条是新手踩最多的坑：目录里放个 random.py 会让 import random 拿到你的文件，而不是标准库

上图第 1 条那个坑值得单独强调。把自己的脚本命名为 json.py、random.py、types.py 这类标准库同名文件，会让同目录下所有代码的 import 拿到你的文件。报错通常表现为某个第三方库内部抛出莫名其妙的 AttributeError，和你刚创建的文件看不出任何关系。

「激活」到底做了什么

激活脚本只做两件事：把虚拟环境的 bin（Windows 上是 Scripts）插到 PATH 最前面，以及改一下命令行提示符让你看得见。它不是必须的——直接用完整路径 .venv/bin/python script.py 效果完全一样。uv 的 uv run 正是利用这一点，替你拼好路径，于是「忘记激活」这类问题不再存在。

做法命令适合
显式激活source .venv/bin/activate要在一个终端里连续敲很多命令
全路径调用.venv/bin/python app.py脚本、cron、Dockerfile 里，不依赖 shell 状态
uv 托管uv run app.py日常开发首选，顺带保证依赖与锁文件同步

虚拟环境不是牢笼，是一张「去哪找包」的地图。激活只是把这张地图摆到最上面，你也完全可以每次直接指名要用哪张。

五、四种运行方式，以及 python -m 的真实差别

同一段代码有四种启动方式，它们的差别不在「能不能跑」，而在 sys.path[0] 被设成了什么——也就是 Python 会优先从哪个目录找包。这个细节解释了大量「在 A 环境能跑在 B 环境报 ModuleNotFoundError」的情况。

项目结构 myproj/ ├── mypkg/ │ ├── __init__.py │ └── tool.py └── tests/ └── test_tool.py 四种启动方式下 sys.path[0] 的值（在 myproj/ 目录里执行） ┌────────────────────────────┬──────────────────────┬─────────────────────┐ │ 命令 │ sys.path[0] │ import mypkg 能成吗 │ ├────────────────────────────┼──────────────────────┼─────────────────────┤ │ python │ ''（当前目录） │ 能 │ │ python -c "import mypkg" │ ''（当前目录） │ 能 │ │ python -m mypkg.tool │ ''（当前目录） │ 能 │ │ python mypkg/tool.py │ 'myproj/mypkg' │ ✗ 不能 │ │ │ ↑ 脚本所在目录 │ 当前目录不在路径上 │ └────────────────────────────┴──────────────────────┴─────────────────────┘ 记住这一条就够了： python 文件路径.py → 路径是「脚本所在的那个目录」 python -m 模块名 → 路径是「你当下所在的那个目录」

最后两行是全节的重点。python -m 把模块当作脚本执行，并且把当前工作目录加进搜索路径；而 python 某个文件.py 加的是那个文件所在的目录。前者让你在项目根目录下总能 import 到项目自己的包，后者不能。

这就是 python -m pip 优于 pip 的原因

pip 是一个独立的可执行文件，它属于某一个特定的 Python 安装；python -m pip 则明确表示「用这个 python 配套的 pip」。当机器上有多个解释器时，你敲的 pip 很可能属于另一个——包装上去了，代码里却 import 不到，就是这么来的。同理，python -m pytest 会把当前目录加入路径，所以能 import 到本地包，而裸 pytest 不会。

示例场景：一个项目的测试在开发机上全绿，进 CI 后 23 个用例全部报 ModuleNotFoundError: No module named 'mypkg'。差别只有一处：本地跑 python -m pytest，CI 里写的是 pytest。前者把仓库根目录放进了 sys.path，后者没有。把 CI 命令统一改成 python -m pytest 后全部通过，修改量 1 行。这类问题的排查成本远高于修复成本，所以值得从第一天就固定用 -m 形式。

启动方式典型用途要注意
python（REPL）试语法、查对象、临时算东西3.13 起的新 REPL 支持多行编辑和彩色报错，体验和旧版差别很大
python app.py跑一个独立脚本sys.path[0] 是脚本目录，不是你所在的目录
python -c "..."一行命令做完的活，写在 shell 脚本里引号嵌套在 Windows 上容易出错，长了就换成文件
python -m pkg调用工具（pip/pytest/venv）、跑包内入口首选形式：解释器明确、当前目录在路径上

凡是「装上了却 import 不到」，先把 pip install 换成 python -m pip install。这一个改动能消掉这类问题的绝大多数。

六、第一个可交付的脚本：比 hello world 多四件事

能打印 hello world 和能交给别人运行，中间差着四件小事。它们都不难，但缺了任何一件，脚本在别人机器上就有相当概率跑不起来。

入口守卫

把可执行的逻辑放进 if __name__ == "__main__": 里面。这个条件在「直接运行本文件」时为真，在「被别人 import」时为假。不写它的后果是：别人一旦 import 你的文件想复用某个函数，你的主流程会立刻整段执行一遍。模块与包那一节（PY08）会讲清这个变量的来历，现在先当成必须写的一行。

import sys

def main() -> int:
    print("hello")
    return 0

if __name__ == "__main__":
    sys.exit(main())

退出码

脚本的返回值是给调用方看的：0 代表成功，非 0 代表失败。CI、cron、shell 的 && 串联全都依赖它。只 print("失败了") 而不返回非 0，在自动化流程里等于什么都没说——上游会当你成功了继续往下走。

编码

Python 3 里源码默认 UTF-8，字符串是 Unicode，这部分不用操心。真正会出问题的是输出：Windows 的旧终端默认编码不是 UTF-8，打印中文或 emoji 可能抛 UnicodeEncodeError。这不是你的代码错了，是输出通道的编码不匹配。

报错真实原因怎么处理
UnicodeEncodeError（打印时）终端编码装不下这个字符设 PYTHONUTF8=1，或用支持 UTF-8 的终端
UnicodeDecodeError（读文件时）文件不是你以为的编码open(..., encoding="utf-8") 显式指定，别依赖默认值

依赖声明

脚本用到第三方库时，把它写进 pyproject.toml（uv add 会自动做），而不是在 README 里写一句「记得先装 requests」。前者是机器能执行的，后者只是希望。

  • 每个项目一个虚拟环境，用 uv run 跑，不依赖「记得激活」
  • 装包统一写 python -m pip install 或 uv add
  • 环境有问题先跑 sys.executable / sys.prefix / python -m pip --version 三连
  • 新项目选一个已经发布满一年的版本，先确认依赖有对应 wheel
  • 可执行逻辑放进 if __name__ == "__main__":，用退出码表达成败
  • __pycache__ 和 .venv 写进 .gitignore
  • 对系统 Python 执行 sudo pip install——会连带搞坏系统工具
  • 把脚本命名为 json.py / random.py / types.py 这类标准库同名文件
  • 大版本刚发布就升级生产环境，把 wheel 缺失留给 CI 去发现
  • 在项目里混用 conda 和 pip 装同一个包
  • 把 .venv 目录提交进仓库或拷到别的机器（里面有绝对路径）
  • 用「请先 pip install xxx」的 README 代替依赖声明

一个脚本算不算交付完成，标准是把它扔到一台干净机器上，照着 pyproject.toml 装完依赖就能跑。做不到，说明环境信息还留在你脑子里，没写进项目。

Q&A

为什么同一段代码在我机器上能跑，在同事机器上报 ModuleNotFoundError？
绝大多数情况是依赖没有被声明，只存在于你的环境里。你当初用 pip install 装了某个库，但没写进 pyproject.toml，同事克隆仓库后自然装不到。少数情况是解释器错位：他装包用的是系统 pip，跑代码用的是虚拟环境里的 python，包装到了另一个环境。排查顺序是先在他机器上跑 python -c "import sys; print(sys.executable)" 和 python -m pip list，确认「跑代码的解释器」里到底有没有这个包。根治办法是所有依赖都通过 uv add 进入 pyproject.toml 和 uv.lock，让环境可以从声明重建。
python、python3、py 这三个命令有什么区别？
python3 是 Linux/macOS 上的历史产物：Python 2 和 3 长期共存时，python 指向 2、python3 指向 3，这个约定保留至今，所以在系统层面 python 可能不存在或指向别的东西。py 是 Windows 专属的版本启动器，它读取 .python-version 之类的信息帮你挑版本，也支持 py -3.12 显式指定。在虚拟环境里这三者的差异基本消失——激活后 python 就是本环境的解释器。结论是：虚拟环境内部用 python，环境外部要区分时用完整路径或 uv run，不要靠猜命令名。
激活虚拟环境到底改了什么？不激活能用吗？
激活脚本只做两件事：把虚拟环境的 bin/Scripts 目录插到 PATH 的最前面，以及修改命令行提示符做视觉提示。它不修改系统状态，不启动任何进程，退出终端就失效。所以完全可以不激活：直接执行 .venv/bin/python app.py 效果一模一样，这也是 Dockerfile、cron、systemd 里推荐的写法，因为它们没有交互式 shell 可以「激活」。uv run 做的就是自动替你拼这个路径。理解这一点之后，「忘记激活导致装错地方」这类问题就不会再发生了。
python -m pytest 和直接敲 pytest 有什么区别？
两个区别。第一，python -m pytest 明确指定了用哪个解释器配套的 pytest，而裸 pytest 是由 PATH 决定的，机器上有多个环境时可能命中别的那个。第二个区别更常踩：-m 形式会把当前工作目录加入 sys.path，所以在项目根目录下执行时，测试代码能直接 import 到项目自己的包；裸 pytest 不会加，于是报 ModuleNotFoundError。这个差异是「本地全绿、CI 全红」的常见根因。建议把所有工具调用统一写成 python -m xxx 形式，包括 pip。
__pycache__ 是什么？能删吗？要提交到 git 吗？
它存放 CPython 编译出的字节码缓存 .pyc，作用是让模块下次被 import 时跳过编译步骤，加快启动。可以随时删除，删掉只会让下一次 import 稍慢一点，之后自动重建。不要提交到 git：文件名里带着解释器版本标记（如 cpython-312），换版本就失效，提交进去只会污染 diff 并可能引起困惑。标准 Python 的 .gitignore 模板默认排除它。另外注意只有被 import 的模块会生成缓存，直接 python app.py 运行的入口文件不会。
2026 年起一个新项目，该选哪个 Python 版本？
默认选一个已经发布满一年的版本——当下即 3.12 或 3.13。理由是这个时间点上主流库的 wheel 已经齐备，踩不到「装不上、要现场编译 C 扩展」的坑，同时还有三四年的安全支持窗口。如果项目重度使用 asyncio，至少要 3.11 起步，因为 TaskGroup 这套结构化并发写法从那一版才有。只有在明确需要自由线程能力、并且已经逐个确认过依赖兼容性时，才考虑 3.14 的自由线程构建。反过来说，3.10 及更早的版本不适合作为新项目的起点，它们的支持窗口已经在倒计时。
自由线程构建（3.14t）要不要现在就用？
除非你有明确的、被实测确认过的纯 Python 多核瓶颈，否则先不用。三个理由。一是它不是默认构建，要单独安装（如 uv python install 3.14t），部署链路上每个环节都得跟着换。二是兼容性有个隐蔽陷阱：任何没有声明支持自由线程的 C 扩展一旦被 import，解释器会发出一条警告并把 GIL 重新启用，你的线程照样跑但不再并行。那条警告混在启动日志里极容易被忽略，所以别指望它提醒你，要用 sys._is_gil_enabled() 主动确认当前到底有没有在无锁模式下跑。三是代价真实存在：单线程性能下降约 5–10%，内存占用增加约 15–20%。对 AI 场景还要补一句：PyTorch 的前向计算和 CUDA 调用本来就不受 GIL 约束，真正能受益的是 tokenize、特征抽取这类纯 Python 预处理。并发那一组的第一张卡（PY25）会专门展开这个话题。
