PY29 · 协程、任务与 Future

协程对象不会自己跑 / Task 才是被调度的单位 / Task 是 Future 的子类 / 事件循环只持弱引用 / 异常停在 Task 上等人来取

上一张卡讲清了事件循环怎么转、await 怎么让出。这张卡回答紧接着的那个问题：循环手里被调度的到底是什么东西。答案不是协程——协程只是一段配好参数、等人来推的代码；真正被排队、被轮询、能被取消、能承载结果和异常的，是 Task。

一、三个东西各是什么：协程对象、Future、Task

写 async def 的人几乎都会在某个时刻问一句：我明明都用 asyncio 了，为什么代码还是串行的？追下去往往发现，问题出在把「协程」和「并发单位」当成了同一个东西。这三个名词在日常交流里被混着用，但它们在运行期是三种不同的对象，职责不重叠。

协程函数与协程对象不是一回事

协程函数是你用 async def 定义的那个函数本身，它和普通函数一样只是个可调用对象。调用它不会执行函数体里的任何一行，而是返回一个协程对象——一段已经装好参数、随时可以从头开始推进、并且能在中途暂停的调用。这个「能暂停」的能力来自生成器的同一套底层机制，如果对暂停与恢复还没感觉，可以先回头看 PY12 迭代器与生成器。

协程对象本身没有任何主动性。它躺在那里，需要有人反复调用它的 send() 把它往前推。await 就是「我来推它，推不动的时候我陪它一起等」；asyncio.create_task() 则是「交给事件循环去推，我先干别的」。

协程对象是一张点好的菜单，不是一盘菜。你把菜单放在桌上放一晚上，厨房什么都不会做。

Future 是占位符，Task 是「带执行器的占位符」

Future 表示「将来某个时刻会有一个结果」的占位符。它不知道结果从哪来，也不负责去算——它只有三种状态（待定、有结果、有异常，外加被取消），以及一个「结果到了就通知我」的回调机制。典型用途是把回调式的底层 API 桥接到 await 语法上。

Task 是 Future 的子类，多出来的那部分职责恰好就是 Future 缺的那块：它包着一个协程对象，并且已经在事件循环里登记，循环会一轮一轮地去推它，推到底之后把返回值填进自己（Future 的那一半），或者把异常存进自己。

可等待对象（能写在 await 后面的东西） ├── 协程对象 async def 函数调用后的返回值 ├── Future 「将来会有结果」的占位符 │ └── Task 包着一个协程、已被事件循环接管的 Future └── 自己实现了 __await__ 的对象 CPython 3.12 实测： issubclass(asyncio.Task, asyncio.Future) 结果为 True asyncio.Task.__mro__ 依次是 Task → Future → object 一句话分工： Future 只回答「结果什么时候到」 Task 在这之上还回答「谁负责一步步把那个协程推到有结果」

这个继承关系不是冷知识。它解释了为什么 task.result()、task.done()、task.add_done_callback() 这些方法存在——它们全是 Future 的接口，Task 只是继承下来。理解了这点，第五节那套取结果的规则就不用背了。

从协程对象到结果，中间发生了什么

async def fetch(uid): ... ← 协程函数（定义） │ │ fetch(7) ← 调用它 ▼ ┌──────────────────────────┐ │ 协程对象 │ 参数已绑定，函数体一行都没执行 └────────────┬─────────────┘ │ ┌────────┴─────────────────────────────┐ │ │ await coro asyncio.create_task(coro) │ │ ▼ ▼ 在当前任务里「就地展开」 ┌────────────────────────┐ 没有新的调度单位诞生 │ Task（Future 子类） │ 调用方挂起，直到它返回 │ 状态：PENDING │ │ └───────────┬────────────┘ │ │ 循环反复推进 │ ▼ │ ┌────────────────────────┐ └─────────────────────────▶│ 结果 / 异常 / 已取消 │ └────────────────────────┘ 取结果的方式见第五节

图里最值得停一下的是左边那条路。await coro 并没有创造新的调度单位：协程在当前这个 Task 的上下文里就地展开，就像函数调用一样。所以一串顺序的 await 从头到尾只有一个 Task 在跑，自然是串行的。这是第三节的全部前提。

「同一个协程对象只能 await 一次」这条值得记住。重复 await 会抛 RuntimeError: cannot reuse already awaited coroutine。想重试就得重新调用一次协程函数造一个新对象——这也是为什么重试装饰器要接收「函数和参数」而不是「一个协程对象」。

判断手上这个东西是协程还是 Task，有个很实在的办法：如果我不去 await 它，会不会有事情发生？协程对象——不会，什么都不会发生；Task——会，它已经在跑了。

二、调用了协程函数却没 await：最常见的第一个坑

几乎每个人都会踩一次这个坑，而且踩的时候往往毫无察觉。代码长这样：

async def handle(order):
    validate(order)
    save_audit(order)          # 少了 await
    return {"ok": True}

这段代码不报错、不崩溃、返回值完全正常，只是 save_audit 的函数体一行都没执行过。save_audit(order) 这个表达式做的唯一一件事是造出一个协程对象，然后因为没人接收它，引用计数归零，对象被回收。

为什么这不是报错，只是一条警告

因为「造出协程对象但不立刻 await」是完全合法且常用的写法。asyncio.gather(f(1), f(2)) 传进去的就是一串没被 await 的协程对象；把协程对象存进列表稍后统一调度也是标准做法。Python 在调用发生的那一刻，没有任何办法区分你是「忘了」还是「打算稍后用」。

所以这个检查只能推迟。协程对象的析构逻辑会检查它是否从未被推进过，是的话就发一条 RuntimeWarning: coroutine 'save_audit' was never awaited。这条信息有两个先天缺陷：时机晚（取决于垃圾回收，不取决于你的代码执行到哪），以及通道弱（它走 warnings 模块打到 stderr，默认每个代码位置只打一次，且完全不经过 logging）。很多服务的日志采集只收 logging 的输出，于是这条警告在生产环境里基本等于不存在。

t0 执行到 save_audit(order) 这一行 ┌────────────────────────────────┐ │ 协程对象已创建 │ 返回值没人接，引用计数 = 0 │ 函数体：一行都没跑 │ └────────────────────────────────┘ t0+ε 对象被回收，析构逻辑发现「从未被推进过」 warnings.warn(...) → stderr: RuntimeWarning: coroutine 'save_audit' was never awaited 注意两个错位： 报告的位置 = 创建它的那一行（对） 报告的时机 = 它被回收的那一刻（可能晚得多，甚至跨测试用例） 报告的通道 = stderr，不是你的 logging 管道

开了 asyncio 调试模式（asyncio.run(main(), debug=True) 或环境变量 PYTHONASYNCIODEBUG=1）之后，这条警告会附带一段 Coroutine created at 的创建堆栈，定位会容易很多。但调试模式不适合常开，它会额外做很多检查。

为什么测试里容易漏过

这类 bug 在测试中生还率极高，原因不止一个。协程对象是真值——它没有定义 __bool__ 也没有 __len__，所以 if fetch_user(uid): 恒为真，条件分支照样走对的那一支。断言「没有抛异常」的用例照样通过。返回值被丢弃的调用（写日志、发消息、落库）本来就没有可观察的返回值，断言不到。

更麻烦的是那条 RuntimeWarning 的时机：它在对象被回收时才发，完全可能在下一个测试用例执行期间才打印出来，看起来像是别的用例的问题。而 pytest 默认会把警告收集到末尾汇总，很容易被当成噪音略过。

写法实际发生了什么你会收到什么提示
save_audit(order) 单独一行造出协程对象后立刻丢弃回收时一条 RuntimeWarning，仅此而已
if fetch(uid):条件恒为真，分支判断失效没有任何提示，逻辑静默走错
rows = [fetch(u) for u in users]得到一串协程对象，len(rows) 正确但内容没跑每个对象回收时各一条警告

示例场景：一个消息消费者的单元测试套件有 140 个用例，全绿运行了三个月。上线后发现某类事件的下游通知一条都没发出去。回查代码，是 notify(event) 漏了 await。测试为什么没发现：断言只检查了 handle() 的返回码和数据库落库结果，通知本身用的是 mock，而 mock 对象「被调用过」这件事恰好是成立的——协程函数确实被调用了，只是产物被丢掉了。把 pytest 配置里的 filterwarnings 设成 error 之后，同一批用例立刻暴露出 3 处同类问题，其中 2 处还没上线。

把 RuntimeWarning 升级成错误，是这套东西里性价比最高的一条配置。它让「忘了 await」从一个静默的逻辑 bug 变成一个必定在 CI 里红掉的失败。

三、并发的真正起点：create_task 而不是 await

第一节说过，await 不产生新的调度单位。所以下面这段代码虽然每一行都写着 await，但它是彻头彻尾的串行：三个各耗时 200 毫秒的请求，墙钟时间 600 毫秒。

并发的起点是 asyncio.create_task()。它把协程对象包成 Task 并登记到事件循环，从这一刻起这个 Task 就是一个独立的调度单位，循环会在任何一次让出机会里去推进它。

# 串行：总耗时 = 三次之和
a = await fetch(1)
b = await fetch(2)

# 并发：先全部交给循环，再统一等
t1 = asyncio.create_task(fetch(1))
t2 = asyncio.create_task(fetch(2))
a = await t1
b = await t2

create_task 之后，任务并没有立刻开始跑

这是最容易产生错觉的一点。因为是单线程，create_task() 返回之后，CPU 仍然在你这段代码里。新任务只是被放进了循环的待运行队列，它一行都还没执行。要等到你这段代码碰到下一个 await（或者协程返回）主动让出控制权，循环才有机会去推进它。

单线程时间轴（横向表示 CPU 实际在执行谁） t1 = create_task(A) ← A 进入待运行队列，一行都没跑 t2 = create_task(B) ← 同上 log.info("已提交") ← 仍然是 main 在跑 do_some_sync_work() ← A、B 依旧原地不动，哪怕这里耗时 2 秒 await t1 ← main 在这里让出，循环才终于开始推 A、B ┌── main ────────────────────────────────┐ ┌─ main ─┐ │ create A │ create B │ 同步代码 │ 让出 │ 收结果 │ └────────────────────────────────────────┘ ↓ └────────┘ ┌── A ──────┐ └───────────┘ ┌── B ──────┐ └───────────┘ 结论：create_task 保证的是「已排队」，不是「已开始」。 中间夹一段阻塞的同步代码，并发收益会被整段吃掉。

这个细节有一个直接的工程后果：create_task() 和第一个 await 之间，不要放耗时的同步代码。它不只是延迟了任务开始，而是在这段时间里整个事件循环都是停摆的——所有其他任务也一起被卡住。

Python 3.12 起有一个例外设施可以改变这个语义：急切任务工厂（asyncio.eager_task_factory），启用后协程会在 Task 构造期间就同步执行，一直跑到第一次真正阻塞为止。第四节会说明它解决什么、不解决什么。

await 是「我要结果，现在就等」，create_task 是「这件事交给循环，我稍后来收」。一段代码有没有并发，看的不是写了几个 await，而是同一时刻有几个 Task 在飞。

墙钟时间对照

假设 fetch() 是一个耗时约 200 毫秒的网络请求，三次调用互不依赖。

最后两行是实际项目里最常见的两种「用了 asyncio 但没变快」。第四行还额外埋着第四节要讲的引用问题，第五行则说明 asyncio 的并发收益完全建立在「让出得够勤」这个前提上——一段不让出的 CPU 密集代码会让整个循环退化成单线程同步程序。

四、任务引用必须自己留住

这条规则反直觉到官方文档专门用加粗的「Important」标出来：事件循环只对任务持有弱引用。一个没有被别处引用的 Task，可能在任何时刻被垃圾回收掉，哪怕它还没执行完。这个行为到 Python 3.14 的文档里依然是这么写的。

所以 asyncio.create_task(coro) 这种「发出去就不管」的写法，不只是缺少错误处理的问题——它本身就不保证任务会跑完。

你写： asyncio.create_task(write_audit(row)) ← 返回值没接住 │ ▼ ┌────────────────────┐ │ Task │ └────────────────────┘ ▲ ▲ 弱引用 │ │ 强引用（只在它「就绪待运行」时存在） │ │ 循环的任务登记表 循环的待运行回调队列 任务挂起在一个 await 上时，它是否还有强引用， 取决于它当时在等什么：若所等对象也无人引用， 这一小团对象就成了孤岛，可以被 GC 整体收走。 症状 A：stderr 出现 Task was destroyed but it is pending! 症状 B：什么都没有，只是那件事再也没有发生过

标准写法：存进集合，完成回调里移除

官方文档给出的写法很简单：用一个集合持住强引用，再用 add_done_callback() 在任务完成时把自己从集合里摘掉，避免集合无限增长。discard 比 remove 合适，因为它在元素已不存在时不抛异常。

_background = set()

def spawn(coro):
    task = asyncio.create_task(coro)
    _background.add(task)                        # 强引用，挡住 GC
    task.add_done_callback(_background.discard)  # 完成即移除，避免堆积
    return task

但要看清这个写法解决了什么、没解决什么。它解决的是「任务中途消失」，没有解决「任务失败了没人知道」——它从头到尾没有 await 过任何任务，所以下一节那条 Task exception was never retrieved 照样会出现。这两个问题必须分别处理，这也是 Python 3.11 引入任务组的直接动机（任务组的细节是下一张卡的主题，这里只作纯文本提及）。

「后台任务」这个说法本身就有误导性。asyncio 没有后台，只有你这一个线程。所谓后台任务只是另一个排在同一条队伍里的 Task，它没有任何特权，也没有任何人替你照看它。

急切任务工厂常被误解成「顺手解决了引用问题」，并不是。它改的是什么时候开始执行：启用后协程在 Task 构造期间同步执行，如果它不阻塞就直接跑完、根本不进循环调度。文档明确提醒这是一处语义变更，会改变应用的任务执行顺序，不要为了省一点调度开销随手打开。

另外提一句版本内情：Python 3.14 重写了任务登记的内部结构，把全局的 WeakSet 换成了每线程的链表，主要目的是自由线程构建下的性能和线程安全。这是实现细节的变化，对外承诺没变——3.14 的文档里那句「事件循环只持有弱引用，请自己保存引用」原样保留。不要指望升版本能免掉这件事。

示例场景：一个 WebSocket 网关在每条连接建立时用 asyncio.create_task() 起一个心跳协程，返回值没保存。灰度期间一切正常，全量后开始出现零星的「连接还在、但对端认为已断开」。排查了两天才在 stderr 里翻到几条 Task was destroyed but it is pending!——心跳任务在两次 sleep 之间被回收了。发生概率和内存压力正相关，所以低流量时永远复现不出来。修复就是把任务存进连接对象的一个属性上，改动 2 行。

五、异常去哪了：存在 Task 上，等人来取

同步代码里，异常沿调用栈往上抛，不处理就一路抛到顶层，你一定会看到它。异步代码里这条规律失效：Task 内部抛出的异常不会冒到创建它的那段代码，因为那段代码早就往下走了，栈上根本没有它的位置。异常被存在 Task 对象里，任务标记为完成，然后——就在那里等着。

同步世界 asyncio 世界 ────────── ───────────── 函数里 raise Task 的协程里 raise │ │ ▼ ▼ 沿调用栈逐层上抛 停在 Task 边界，不再往外走 │ │ ▼ ▼ 调用方接住，或者进程崩溃 异常存进 Task，状态标记为已完成 │ ┌─────────────────┴──────────────────┐ │ │ 有人 await / result() 没有人来取 │ │ ▼ ▼ 在取的那一行原样抛出 Task 被回收时，asyncio 的 堆栈完整、时间点明确 日志器打一条 ERROR： Task exception was never retrieved 最后这条的两个要命之处： 时间点由垃圾回收决定，可能离故障发生已经过去很久 内容里只有异常本身，没有订单号、没有 trace_id，和业务日志对不上

四个取结果的接口，时机各不相同

done() 回答的是「跑完了没有」，它对成功、失败、被取消三种情况一律返回 True。用 done() 判断成功是很常见的错误。

result() 是「把结果拿出来」：正常完成返回返回值，内部抛过异常就在这一行原样重新抛出，被取消则抛 CancelledError，还没完成则抛 InvalidStateError。exception() 是同一件事的非抛出版本：完成且失败时返回那个异常对象，完成且成功时返回 None；但被取消时它同样抛 CancelledError，未完成时同样抛 InvalidStateError。

add_done_callback(cb) 注册一个完成回调，回调收到的唯一参数就是这个 Task。注意它不是同步调用：回调通过 loop.call_soon() 排队，在任务完成之后的下一轮事件循环迭代里才执行。还要注意，回调被调用这件事本身不算取过异常，你必须在回调里真的调用 exception() 或 result()，才能消掉那条 never retrieved 日志。

def on_done(task):
    if task.cancelled():          # 先判取消，否则 exception() 会抛
        return
    exc = task.exception()        # 取过了，不会再有 never retrieved
    if exc is not None:
        log.error("审计写入失败 order=%s", task.get_name(), exc_info=exc)

task.add_done_callback(on_done)

异常会在什么时候、以什么形式出现

你对 Task 做了什么异常出现的时机出现的形式能拿到原始堆栈吗
await task立刻，就在 await 那一行原异常被重新抛出能，完整
task.result()调用的那一刻原异常被重新抛出；未完成则 InvalidStateError能，完整
task.exception()调用的那一刻返回异常对象，不抛；被取消时抛 CancelledError能，挂在对象上
完成回调里调 exception()任务完成后的下一轮循环迭代由你自己决定记日志还是上报能，完整
只调 done()，不取结果不出现done() 对成功和失败都返回 True拿不到
什么都不做Task 被垃圾回收时asyncio 日志器一条 ERROR：Task exception was never retrieved有堆栈，但没有业务上下文
任务还没完成就被回收对象析构时Task was destroyed but it is pending!没有

还有一个容易踩的边界：CancelledError 从 Python 3.8 起直接继承 BaseException 而不是 Exception。这是刻意的设计——取消是控制信号，不是业务错误。它带来的实际影响是，你那个「兜底不让它崩」的 except Exception 不会误吞取消信号；反过来说，写了裸 except: 或 except BaseException 的地方会把取消也接住，导致任务拒绝退出、关停流程挂起。异常分层该怎么设计，可以参考 PY24 异常体系设计。

事故复盘：某订单服务在下单主链路返回前，用 asyncio.create_task(write_audit(row)) 把审计流水异步写到对象存储，写完就不管。对象存储偶发 503，write_audit 抛出异常，但没有任何人 await 这批 Task，异常就停在 Task 上；进程常驻、内存充裕，这些对象很久以后才被回收，Task exception was never retrieved 才被打出来。更糟的是它走的是 asyncio 自己的日志器，内容里没有订单号也没有 trace_id，而告警规则是按业务关键字过滤的，一条都没触发。这个状态持续了 11 天，直到月末对账才发现审计流水比订单表少了 4217 条（同期约 100 万单，缺失率 0.42%），且缺失分布零散、看不出任何时间规律。修复分两步：把后台任务统一收进一个集合、在完成回调里检查 exception() 并按业务字段记日志；给写入加上有次数上限的重试和失败落盘。真正的教训不是「该加重试」——而是这段代码从第一天起，就没有任何人对这批任务的成败负责。

异步系统里最难查的故障，共同特征是「报错时间点和故障时间点脱钩」。Task exception was never retrieved 就是典型：它告诉你确实出过事，但不告诉你是什么时候、哪一笔业务。想避免，只能保证每个异常都有人在确定的时刻取走。

六、三种写法的取舍，以及唯一那条纪律

前面五节的内容可以压成一句可执行的纪律：每一个被创建出来的任务，都必须有一个明确的归属者，负责 await 它或者取消它。「发出去就不管」不是一种写法，它是一个待爆的故障。

在这条纪律之下，日常写代码只需要在三种形态里选一个。

场景用什么理由
下一步马上就要用它的结果裸 await本来就没有并发可言，包成 Task 只是多一个要管的对象和一点调度开销
同一时刻要发出多个互不依赖的 IOcreate_task 后统一等，或交给任务组并发收益来自「一起在飞」，前提是创建之后尽快让出
一个请求作用域内的一批子任务，要求一损俱损任务组（3.11 起，下一张卡展开）内部持强引用、退出时统一 await、异常聚合、一个失败其余自动取消
生命周期超出当前函数的常驻任务（心跳、消费循环）create_task + 自己存引用 + 明确的停止与收尾路径没有天然的作用域能兜住它，归属者只能是你自己维护的那个对象
只想「发出去不等结果」没有这种选项必须指定归属者，否则就是第五节那个事故

第三行和第四行的分界就是「有没有一个天然的作用域」。请求处理、批量抓取、扇出查询这类有明确起止的场景，交给任务组最省心；而心跳、后台消费者这类活得比任何一次函数调用都久的任务，作用域只能由你自己建立——通常是挂在连接对象、服务对象上，并在关停流程里显式取消。

问自己一个问题就能定位绝大多数异步 bug：这个任务出错了，谁会知道？如果答不出一个具体的代码位置，那它现在就已经是隐患，只是还没轮到它爆。

关停路径同样要写

常驻任务的另一半是收尾。服务退出时如果直接关掉循环，还在跑的任务会被当成「pending 时被销毁」处理，正在写的数据可能只写了一半。标准做法是先逐个 cancel()，再用一次带 return_exceptions=True 的收集等它们全部退出，最后再关闭资源。协程内部则用 try/finally 保证清理一定执行。

  • 每个 create_task 产生的任务都指定一个归属者，负责 await 或 cancel 它
  • 长驻的后台任务存进集合，并在 add_done_callback 里移除
  • 完成回调里显式调 exception()，翻译成带业务字段的日志
  • 关停时先 cancel() 再统一收集，协程内用 try/finally 做清理
  • 测试配置里把 RuntimeWarning 升成错误，让漏 await 在 CI 红掉
  • 有明确作用域的一批任务，优先交给任务组而不是手工管理
  • 把 create_task 当成「扔出去就不用管」的语法糖
  • 用 done() 判断任务是否成功——它对失败和取消也返回 True
  • 在 create_task 和第一个 await 之间夹耗时的同步代码
  • 用裸 except: 兜底，把 CancelledError 一起吞掉
  • 只把任务存在局部变量里，函数一返回引用就没了
  • 指望 stderr 上那条 RuntimeWarning 在生产环境提醒你

协程负责「怎么写」，Task 负责「怎么被调度」，Future 负责「结果怎么送达」。三者搞混的代价不是写不出来，而是写出来的东西在低负载下一切正常，在你最不希望的时候静默地少做一件事。

Q&A

协程对象和 Task 到底差在哪，能不能用一句话说清？
协程对象是「配好参数、等人来推的一段代码」，它自己不会动；Task 是「已经交给事件循环、循环会反复来推」的那个包装。最实用的判别方法是问一句：如果我不去 await 它，会不会有事情发生？协程对象——不会，一行都不会执行，最后只留下一条回收时的警告；Task——会，它已经排进队列了，你 await 只是去收结果。另外 Task 是 asyncio.Future 的子类，所以它天然带着 done()、result()、cancel()、add_done_callback() 这一整套接口，而协程对象一个都没有。
为什么忘了 await 只是一条警告，不是报错？
因为「造出协程对象但暂时不 await」是合法且常用的：asyncio.gather(f(1), f(2)) 收到的就是没被 await 的协程对象，把协程存进列表稍后统一调度也很常见。Python 在调用那一刻无法区分你是忘了还是打算稍后用，所以检查只能推迟到对象被回收、确认它从未被推进过时才发出 RuntimeWarning: coroutine '...' was never awaited。代价是时机晚（取决于垃圾回收）、通道弱（走 warnings 打到 stderr，不经过 logging）。要把它变硬，在 pytest 配置里把 filterwarnings 设为 error，或用 python -W error::RuntimeWarning 跑。
create_task 之后要不要加一句 await asyncio.sleep(0) 来「启动」它？
技术上确实有效：await asyncio.sleep(0) 会让出一次控制权，让刚创建的任务跑到它自己的第一个阻塞点。但不建议把它当成固定手法，因为这是对调度顺序的隐式依赖，读代码的人看不出这一行为什么存在，以后有人删掉它也不会有任何测试失败。正常的做法是在真正需要结果的地方 await，让出自然会发生。如果确实需要「创建时就跑一段」的语义，Python 3.12 起有 asyncio.eager_task_factory，通过 loop.set_task_factory() 启用，这是有文档支持的正式设施——但要先读清楚它会改变任务执行顺序这件事。
asyncio.gather 和自己 create_task 再一起等，有什么区别？
gather 会把传进来的协程对象自动包装成 Task，所以在「创建 + 等待」这件事上它更紧凑，归属者也明确。区别主要在异常语义上，这里要小心：默认 return_exceptions=False 时，第一个抛出的异常会立刻传播给 await gather 的那一方，但其余任务不会被取消，它们继续在后台跑，而且它们的异常同样可能变成「没人取」的状态。return_exceptions=True 则把异常当成普通结果收集进返回列表，需要你自己逐个检查类型。如果你要的是「一个失败、其余全部取消」，那是任务组的语义，从 3.11 起可用。
我需要自己创建 Future 吗？
业务代码里基本不需要。官方文档的建议是不要在面向用户的 API 里暴露 Future 对象，并且推荐用 loop.create_future() 而不是直接构造，这样替换事件循环实现时能用上对方优化过的版本。真正需要它的场景只有一类：把回调式的底层接口桥接到 await 语法上。做法是建一个 Future 交给上层去 await，然后在回调触发时调用 set_result() 或 set_exception()。协议实现、驱动层、包装只提供回调的第三方 SDK 时会用到。日常写业务，用 Task 就够了。
为什么 except Exception 接不住任务取消？
因为 CancelledError 从 Python 3.8 起直接继承 BaseException，不再是 Exception 的子类。这是刻意为之：取消是一个控制信号而不是业务错误，不应该被「兜底不让它崩」的代码顺手吞掉。实际影响有两面。好的一面是你那些 except Exception 的保护层不会干扰取消。要警惕的一面是，裸 except: 和 except BaseException 会把取消也接住，任务因此拒绝退出，关停流程会一直挂着等它。需要在取消时做清理，正确写法是 try/finally，或者在 except asyncio.CancelledError 里清理完之后重新 raise。
「保存任务引用」用一个全局 list 行不行？
能保命，但有两个问题。一是必须在任务完成时把它移出去，否则这个容器只增不减，就是一处内存泄漏——长驻服务跑上几天就能看出来。二是 list.remove() 是 O(n)，任务多了会变成热点，官方文档给的示例用的是 set 加 add_done_callback(背景集合.discard)，discard 还有个好处是元素已不存在时不抛异常。更重要的是要认清这个集合的边界：它只解决「任务被中途回收」，完全不解决「任务失败了没人知道」。异常仍然停在 Task 上，你得在完成回调里主动去取。
Task exception was never retrieved 到底什么时候打出来？
在这个 Task 对象被垃圾回收的时候，由 asyncio 通过自己的日志器记录，级别是 ERROR。关键在于「被回收的时候」——这个时间点由引用计数和垃圾回收决定，和异常实际发生的时刻可能隔着很久，长驻进程里隔上几小时甚至几天都不奇怪。这就是它难查的根本原因：日志时间戳无法用来定位故障窗口。另外它的内容只有异常和堆栈，没有任何业务字段，和你的请求日志对不上。所以不要把它当成告警来源，它只是一个「你这里漏了一个归属者」的事后提示。真正的解法是在完成回调或 await 处主动取走异常，并且带上业务上下文记日志。
