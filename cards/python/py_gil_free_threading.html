GIL 不是「Python 慢」的原因，它是「Python 的多线程吃不满多核」的原因。这两句话差一个字，结论差一整套架构：分清它们，九成的并发选型你自己就能做对；剩下的一成，才轮到自由线程出场。

一、GIL 是什么，当年为什么必须有它

先把定义收紧。CPython 解释器里有一把全局互斥锁，任何线程想执行 Python 字节码，必须先拿到它。于是同一个进程里，无论你开 4 个线程还是 400 个，同一时刻只有一个线程在执行字节码。这把锁就是 全局解释器锁（Global Interpreter Lock，GIL）。

注意它是实现层的东西，不是语言规范的一部分——语言规范里根本没有「锁」这个概念。PY01 讲过语言、实现、解释器的三层区分，GIL 只存在于 CPython 的默认构建里，换个实现或换个构建它就不在了。所以「Python 有 GIL」这句话严格来说是错的，准确说法是「CPython 的默认构建有 GIL」。

它保护的不是你的数据，是解释器自己

很多人把 GIL 理解成「Python 帮我把多线程代码变安全了」。这是个代价高昂的误解：GIL 保护的是解释器内部状态，完全不保护你的业务逻辑。两个线程同时对一个列表做「检查是否存在，不存在就插入」，该错还是会错。

它真正必须保护的是 引用计数。CPython 用引用计数做主要的内存回收手段（细节见 PY23）：每个对象头上有一个计数器，多一个名字指向它就 +1，少一个就 -1，归零立刻释放。问题在于这个 +1/-1 在机器层面是「读出来、加一、写回去」三步，不是一条原子指令。

没有 GIL 时，两个线程同时给同一个对象加引用会发生什么 ────────────────────────────────────────────────── 时刻 线程 A 线程 B refcount ───── ──────────────────── ──────────────────── ──────── t1 读出 refcount = 5 5 t2 读出 refcount = 5 5 t3 算出 5 + 1 = 6 5 t4 算出 5 + 1 = 6 5 t5 写回 6 6 t6 写回 6 6 ← 丢了一次！ 两个线程各持有一份引用，计数却只涨了 1。 丢一次 +1 → 对象被提前释放，之后访问就是野指针（进程直接崩） 丢一次 -1 → 对象永远不归零，内存泄漏（进程慢慢胀死） GIL 的做法简单粗暴：谁都别想同时跑字节码，那三步自然不会交错。

上图那种崩溃是最难排查的一类问题：没有 Python 层的异常栈，只有一行 Segmentation fault，而且概率极低、换台机器就复现不出来。1990 年代想在不牺牲单线程性能的前提下解决它，没有好办法——于是就有了 GIL。

这笔交易当年换回了什么

历史收益具体表现不要 GIL 的话，当年得付什么
单线程性能好引用计数的加减是普通整数运算，不需要原子指令，也不需要内存屏障全部改成原子操作，单线程会明显变慢，而当年绝大多数程序都是单线程
C 扩展作者不用考虑线程安全扩展代码只在持有 GIL 时运行，天然串行，内部用全局变量和静态缓存都没问题每个扩展都要自己设计锁策略，生态会立刻分裂成「线程安全的」和「不安全的」两半
内存管理实现简单对象分配器、分代 GC、各种 freelist 都可以按单线程假设来写需要每线程堆、无锁数据结构、分代 GC 的暂停协议，实现复杂度上一个数量级

第二行是三条里最重要的。CPython 之所以能长出今天这个规模的科学计算与 AI 生态，很大程度上是因为写 C 扩展的门槛足够低——你只要会写 C，不需要同时是并发专家。这个红利吃了三十年，而移除 GIL 首先要还的也正是这笔账（第五节会讲）。

GIL 是一笔很早就签好的合同：拿「多线程不能并行跑字节码」，换「单线程快、C 扩展好写、内存管理简单」。在单核机器上这笔交易近乎白赚，代价要到多核普及之后才开始显现。

它不是一直锁着的

GIL 会被主动交出去，否则一个死循环线程就能饿死其他所有线程。交出的时机有两类：一是线程执行到阻塞型系统调用（读文件、发网络请求）之前，二是解释器按固定的 切换间隔强制让出，让别的线程有机会抢。这个间隔默认 5 毫秒，可以用 sys.setswitchinterval() 读写。

「会被释放」这件事是下一节全部结论的基础：GIL 卡住的只是执行字节码这一段，凡是不在执行字节码的时间，它都不占着。

二、它卡住了什么，没卡住什么

把上一节的结论展开成时间轴，多线程什么时候有用、什么时候没用就一目了然了。关键变量只有一个：这段时间里，线程到底在不在跑字节码。

三种负载，各开 2 个线程，横轴是时间（▓ = 真在干活，░ = 在等 GIL） ───────────────────────────────────────────────────────────── ① 纯 Python 计算（正则清洗、分词、手写循环） 线程1 ▓▓▓▓░░░░▓▓▓▓░░░░▓▓▓▓░░░░ 线程2 ░░░░▓▓▓▓░░░░▓▓▓▓░░░░▓▓▓▓ └── 任一时刻只有一个 ▓，总时长 = 单线程时长 + 切换开销 结论：不会变快，通常还更慢 ② 文件与网络 I/O（HTTP 请求、数据库查询、读盘） 线程1 ▓▓ ·········等待响应········· ▓▓ 线程2 ▓▓ ·········等待响应········· ▓▓ └── 等待期间 GIL 已交出，两个等待完全重叠 结论：并发数可以几十上百倍地放大 ③ C 扩展内的计算（NumPy 大矩阵、zlib 压缩、hashlib） 线程1 ▓ ━━━━━ 在 C 里算，GIL 已释放 ━━━━━ ▓ 线程2 ▓ ━━━━━ 在 C 里算，GIL 已释放 ━━━━━ ▓ └── 两段 ━━ 真的跑在两个核上 结论：真并行，加速比接近核数

这张图里 ① 和 ③ 的差别值得反复咀嚼：同样是「CPU 密集」，一个完全不能并行，一个几乎线性加速，区别只在于计算发生在 Python 字节码里还是 C 代码里。这也是为什么「我的任务是 CPU 密集的，所以要用多进程」这句话并不总成立。

四类负载的对照

负载类型典型例子多线程能吃满多核吗根本原因该用什么
纯 Python 计算正则清洗、分词、JSON 结构改写、手写数值循环、大量小对象创建不能，常常更慢全程持有 GIL，多开的线程只贡献切换开销多进程 / 子解释器 / 下沉到 C / 自由线程构建
文件与网络 I/OHTTP 调用、数据库查询、读写磁盘、消息队列收发能（重叠的是等待，不是 CPU）进入阻塞系统调用前 GIL 已交出线程池；连接数上千时换 asyncio
C 扩展内的计算NumPy 大数组运算、zlib/lz4 压缩、hashlib、图像编解码能，真并行扩展在计算段主动释放 GIL，算完再取回线程池就够，不必上多进程
子进程subprocess 调 ffmpeg、调外部 CLI 工具能计算根本不在本解释器里，主线程只在等待线程池 + subprocess

第三行有个常被忽略的限定：不是所有 C 扩展调用都会释放 GIL。释放和重新获取本身有开销，对小数组来说这笔开销可能比计算还大，所以库作者通常设了尺寸阈值——小数组直接算完返回，根本不释放。把「NumPy 会释放 GIL」当成无条件成立，会让你在一堆小数组的场景里白忙一场。真要确认，只能实测：看 16 线程跑起来进程的 CPU 占用是接近 100% 还是接近 1600%。

事故复盘：批量文本清洗改多线程，反而慢了 56%。一条离线链路每批处理 48 万条工单文本（平均 2 KB），做正则去噪、分词、算去重键，全是纯 Python。单线程基线：吞吐 3200 条/秒，整批 150 秒，单条处理 P95 = 1.9 毫秒。机器是 16 核，于是改成 ThreadPoolExecutor(max_workers=16)，预期提速十倍。上线后整批耗时涨到 234 秒（吞吐掉到 2050 条/秒），单条 P95 从 1.9 毫秒涨到 27 毫秒，而进程 CPU 占用始终在 105% 上下徘徊——16 核只用满了一个。慢下来的那 84 秒全是 GIL 争抢和线程切换的开销，P95 变差则是因为每条任务都要排队等锁。改成 ProcessPoolExecutor(max_workers=12) 后整批 26 秒（吞吐 18600 条/秒）。代码改动只有一个类名，真正的错误发生在动手之前：把「CPU 密集」的任务当成了「并发能救」的任务。这个事故里，CPU 占用曲线是最早、也最便宜的诊断信号——它在第一次压测时就摆在那里了。

判断多线程能不能提速，只问一句话：这段代码的绝大部分时间，是在等外面，还是在跑字节码？等外面的能提速，跑字节码的不能。不确定就压测一次看进程 CPU 占用——它不会骗人。

三、绕开它的三条路线怎么选

确认了自己确实撞上 GIL 之后，摆在面前的是三条成熟路线加一条新路。它们不是「哪个更好」的关系，判据其实只有三条：等待为主还是算为主、任务之间要不要共享大状态、单机核数够不够。

方案能并行跑字节码共享状态的成本单位开销最适合的场景
threading / 线程池不能（默认构建）直接共享内存，但正确性要自己用锁保证每线程一个栈，切换走系统调度I/O 等待为主，且要共享一份大对象
multiprocessing / 进程池能要序列化来回传，大对象非常贵每进程一份完整解释器，启动以百毫秒计CPU 密集，且任务之间基本独立
asyncio不能（本来就单线程）同一线程内共享，不需要锁协程对象只占几 KB，切换不进内核高并发 I/O，连接数上千
concurrent.interpreters（3.14 起，PEP 734）能（每个子解释器有自己的 GIL）默认不共享，靠队列传值比线程重、比进程轻，同进程内想要进程级隔离，又不想付进程的内存代价

最后一行是 Python 3.14 才进标准库的新选项。子解释器从 3.12 起（PEP 684）就不再共享 GIL，3.14 用 PEP 734 给它配了 concurrent.interpreters 这个公开模块。它介于线程和进程之间，但目前限制不少：能在解释器之间真正共享的对象类型还很有限，很多第三方扩展也还不兼容多解释器。把它当成一个值得关注的方向，而不是今天的默认答案。

选型决策树（从上往下，第一个命中的就是答案） ──────────────────────────────────────── 这段代码的时间主要花在哪？ │ ├─ 等 I/O（网络、磁盘、数据库） │ │ │ ├─ 并发量几十到几百，代码是同步写法 ──→ 线程池，最省事 │ └─ 并发量上千，或已经是 async 生态 ──→ asyncio │ └─ 算（CPU 忙） │ ├─ 热点已经在 C 扩展里（NumPy / 压缩 / 编解码） │ └─→ 线程池就够了，它本来就在并行 │ └─ 热点是纯 Python 字节码 │ ├─ 先问：这段能不能向量化 / 换成 C 扩展 / 用更好的算法？ │ └─→ 能，就先做这个（收益通常最大，改动最小） │ ├─ 任务之间基本独立，传的数据不大 ──→ 多进程 ├─ 要共享一份很大的只读状态 ──────→ 自由线程构建（第四节） └─ 单机核数不够用了 ──────────→ 别在并发模型上纠结，先横向扩机器

在线程池和进程池之间切换，代码上往往只是换一个类名，因为 concurrent.futures 给了它们同一套接口。这也意味着你可以低成本地两个都测一遍，而不是靠推理下结论。

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# 接口完全一致，换类名即可对比；进程池要求任务函数和参数可被 pickle
Pool = ProcessPoolExecutor          # 换成 ThreadPoolExecutor 再跑一遍

with Pool(max_workers=12) as ex:
    for out in ex.map(clean_one, records, chunksize=256):
        sink.write(out)

进程池有两个参数值得单独记住。max_workers 别超过物理核数，超了只会加剧调度竞争；chunksize 决定一次派发多少条任务，任务很短时不设它会让序列化开销吃掉全部收益——上一节那个事故里，进程池版本如果 chunksize 用默认的 1，吞吐会掉掉一大截。

换并发模型是改架构，把热点下沉到 C 扩展或向量化往往只是改十几行代码。先量一遍热点再动手：能用 re 预编译、能用批量接口、能用 NumPy 一次算完的地方，收益经常比换模型更大，而风险小一个数量级。

还有一类容易被忽视的收益来源：减少要做的工作。批量文本处理里预编译正则、把逐条数据库写入改成批量写入、把 JSON 解析换成更快的实现，这些都不涉及任何并发模型的改动。并发是最后一招，不是第一招。

四、自由线程构建：PEP 703 定方向，PEP 779 定门槛

移除 GIL 的尝试有过很多次，都倒在同一个地方：能让多线程变快，但把单线程拖慢太多，社区不接受。2023 年 Sam Gross 提出的 PEP 703《Making the Global Interpreter Lock Optional in CPython》是第一个真正过关的方案——关键不在于它做到了零开销（并没有），而在于它把单线程的退步压到了可以谈判的范围，同时给出了一条渐进的迁移路径。指导委员会当年接受了它。

接受之后的问题变成了「什么时候能算数」。PEP 779《Criteria for supported status for free-threaded Python》回答的就是这个：它不引入新功能，只定义一组判据——性能退步幅度、内存增长幅度、API 稳定性、文档完备度——达标就把「实验性」标签摘掉。这个 PEP 在 Python 3.14 的开发周期里被接受，于是 3.14 的自由线程构建正式进入「受支持但仍然可选」的阶段。

自由线程的三个阶段 ────────────────── 阶段 I · 实验性 Python 3.13（2024-10） ├─ configure 加 --disable-gil 可以编出无 GIL 的解释器 ├─ 官方安装包里作为可选组件提供 └─ 明确标注 experimental，不保证长期存在 阶段 II · 正式支持但可选 Python 3.14（2025-10） ← 当下在这里 ├─ PEP 779 判据达标，"实验性" 标签摘除 ├─ PEP 659 的自适应特化解释器在无 GIL 模式下也启用了，性能大幅改善 ├─ 承诺：不会在不走正常废弃流程的情况下被移除 └─ 但它仍然是【另一套构建】，不是默认解释器 阶段 III · 成为默认 没有时间表 └─ 需要生态（尤其是 C 扩展）准备到什么程度，社区还在讨论 一台机器上两套构建是并存的，互不影响： python3.14 ← 带 GIL 的常规构建（默认） python3.14t ← 自由线程构建，t 是 ABI 标记，不是笔误

数据截止 2026-09 · 上述阶段划分与版本对应关系取自 CPython 3.14 的官方发行说明与 PEP 703 / PEP 779 正文。阶段 III 至今没有公布时间表，任何声称「某某版本会默认关掉 GIL」的说法都还没有官方依据。

它是另一套构建，不是一个开关

这一点最容易被误解，也最容易在部署时翻车。自由线程不是运行时的 flag，而是编译期决定的另一个解释器：它有自己的可执行文件（python3.14t）、自己的 ABI、自己的一套 C 扩展二进制包。你的 Dockerfile、CI 镜像、部署脚本、以及每一个依赖的 wheel，全都要跟着换。

因此「我要不要用自由线程」在工程上不是一个代码问题，而是一个供应链问题。真正的成本在于确认你那几十个依赖里，有多少已经提供了对应的二进制包。

你想确认什么怎么查说明
我装的是不是自由线程构建python -VV自由线程构建的版本串里会标出 free-threading
编译期到底关没关 GILsysconfig.get_config_var("Py_GIL_DISABLED")自由线程构建返回 1，常规构建返回 0 或 None

装一个来试uv python install 3.14t和常规构建并存，不会覆盖它

表里第三行是本节最该记住的一行。_is_gil_enabled 开头那个下划线说明它是 CPython 的内部接口，名字前缀就是在告诉你「不保证稳定」——但在没有正式公开接口之前，它是判断「我的进程现在到底有没有并行能力」的唯一办法。把它写进服务的启动自检里，比事后看性能曲线猜要可靠得多。

# 放进服务启动自检：三行输出就能定位「我以为关了其实没关」
import sys, sysconfig

print(sys.version)                                  # 版本串里会标 free-threading
print(sysconfig.get_config_var("Py_GIL_DISABLED"))  # 编译期：自由线程构建为 1
print(sys._is_gil_enabled())                        # 运行时：False 才是真的关着
# 编译期为 1 但运行时为 True = 某个 C 扩展把 GIL 又打开了，见第五节

自由线程不是 3.14 的一个开关，是 3.14 的另一个可执行文件。装它、确认依赖都为它编译过、再用 sys._is_gil_enabled() 确认它真的关着——三步缺一不可，少一步你就只是背了代价没拿到收益。

五、自由线程要付的四笔账

移除 GIL 不是纯收益。第一节那张表列的三个历史收益，现在要一笔一笔还回去。

第一笔：单线程慢一点

引用计数不能再用普通加减了。PEP 703 的方案是组合拳——不朽对象（常量、小整数这类永不释放的对象干脆不计数）、偏向引用计数、延迟引用计数——尽量让常见路径不走原子指令，但总归比原来多做事。

CPython 3.14 的官方说明给出的量级是单线程代码慢 5% 到 10% 左右，具体取决于平台和编译器；PEP 779 给阶段 II 定的是 15% 的硬上限。这两个都是用标准基准套件测出来的量级参考，不是对你应用的预测——你的实际数字取决于热点在哪，可能更小，也可能因为某个特定模式而更大。3.14 相比 3.13 有明显改善，一个重要原因是自适应特化解释器（PEP 659）在无 GIL 模式下也启用了。

第二笔：内存涨一点

对象头要装下更多并发相关的字段，每个线程要维护自己的引用计数结构，一些原本共享的内部缓存要改成每线程一份。PEP 779 给阶段 II 定的内存上限是不超过常规构建的 20%（按标准基准套件的几何平均算）。同样，这是准入门槛，不是你的应用会涨多少。对象数量特别多的工作负载受影响更明显。

第三笔：C 扩展要重新编译，还要显式表态

这是四笔里工程量最大的一笔。自由线程构建有独立的 ABI，扩展必须为它单独编译——发行版上体现为轮子文件名里的 cp314t 标记，和常规构建的 cp314 不通用。更关键的是，编译通过还不够，扩展还得显式声明自己支持无 GIL 运行。

在自由线程构建上 import 一个 C 扩展时，解释器做的判断 ────────────────────────────────────────────────── import some_c_ext │ ▼ 有没有为这个 ABI 编译过？（文件名带 cp314t） │ ├─ 没有 ──→ ImportError / 根本找不到轮子 │ 这一步在装依赖时就会暴露，算好事 │ └─ 有 │ ▼ 模块有没有声明「我不需要 GIL」？ （多阶段初始化加 Py_mod_gil 槽） │ ├─ 声明了 ──→ 正常加载，GIL 保持关闭 ✅ │ └─ 没声明 ──→ 打印 RuntimeWarning 并【在运行时把 GIL 重新启用】 │ └─ 你的线程照样跑，但不再并行 性能回到起点，代价却照付 只有 sys._is_gil_enabled() 看得见 PYTHON_GIL=0 可以跳过最后这道检查，强行不启用 GIL。 但那道检查存在是有原因的：跳过它意味着你替扩展作者 担保了它的线程安全，出问题通常是进程级崩溃，不是异常。

注意那条 RuntimeWarning 的实际处境：它在进程启动的一瞬间打印，往往被淹没在几百行启动日志里，没人会看见。等到几周后有人问「为什么换了 3.14t 性能没变化」，才发现 GIL 从第一天起就是开着的。这就是为什么上一节强调要把 sys._is_gil_enabled() 写进启动自检——让它以断言的形式失败，而不是以警告的形式被忽略。

第四笔：你的纯 Python 代码要自己面对数据竞争

这一笔最隐蔽，因为它不报错，只是算错。

先把话说准：数据竞争在带 GIL 的构建上也一直存在，GIL 从来没有保证过复合操作的原子性。counter[k] += 1 是「读、加、写」三步字节码，中间完全可能被切换打断。只不过 GIL 构建下切换间隔默认 5 毫秒，而这三步只要几十纳秒，撞上的概率低到你可能写了十年都没遇到过。自由线程构建把线程变成真正并行，那个窗口就从「几乎撞不上」变成了「常态命中」。

另一个要分清的层次：CPython 在自由线程构建上给 list、dict 这些内置容器加了每对象的保护，单个内置方法（比如一次 append）不会把容器内部结构搞坏。但那只保证容器自己不崩，不保证你那个由多步组成的逻辑是对的。

# 这段在 GIL 构建上几乎总是对的，在自由线程构建上会稳定丢更新
from collections import Counter
hits = Counter()

def worker(keys):
    for k in keys:
        hits[k] += 1        # 读 / 加 / 写三步，中间可以被真正地并行打断

事故复盘：迁到 3.14t 之后，统计结果每跑一次都不一样。把上一节那条清洗链路的去重统计搬到自由线程构建上试水，8 个线程、每轮约 200 万次计数累加。GIL 构建下连跑 20 轮，结果一字不差；自由线程构建下同样跑 20 轮，每轮的总计数都比正确值少，缺口在 3 万到 12 万之间（相对误差 1.5%–6%），而且每轮都不一样。没有异常，没有告警，下游报表就这么小幅偏低了两天才被对数的同事发现。根因就是上面那行 hits[k] += 1。修法有两个：加锁最直观，但 8 个线程抢同一把锁会把并行收益抹掉大半；更好的做法是每个线程各累各的局部 Counter，全部结束后再合并——既没有锁竞争，也没有竞态，最终吞吐反而比加锁版本高。这个事故真正的教训是：迁移到自由线程时，最该复查的不是性能，是共享可变状态；先把「哪些对象会被多个线程写」列出来，再谈提速。

这笔账量级参考怎么判断它对你有多疼
单线程性能官方说明给的是 5%–10% 左右；PEP 779 阶段 II 硬上限 15%如果你的服务本来就是单线程吞吐敏感型，这笔直接从利润里扣
内存占用PEP 779 阶段 II 的准入上限是 20% 以内对象数量越多越明显；容器实例多的服务先拿测试环境实测
C 扩展供应链不是百分比，是「有没有」的二元问题数一遍依赖里有多少个带 C 扩展，逐个查有没有 cp314t 轮子
并发正确性无法用百分比衡量，是一次性的代码审查成本看有多少全局可变状态被多线程写；共享越多，这笔越贵

GIL 消失后，「多线程能不能并行」这个问题解决了，「多线程写得对不对」这个问题才刚开始。以前是解释器替你把窗口缩得极小，现在窗口敞开着，得靠你自己的锁策略和数据设计。

六、现在该怎么做

最要紧的一条结论放在最前面：不要为了等自由线程而推迟架构决策。阶段 III 没有时间表，而你的性能问题今天就在扣钱。更重要的是，这不是浪费——把 CPU 密集部分拆成独立、无共享状态的任务单元，这件事无论最终跑在多进程、子解释器还是自由线程上都是必需的前置工作。今天为多进程做的拆分，将来换成自由线程时几乎可以原样复用。

你的情况现在该做什么
瓶颈在数据库、HTTP、磁盘等待上完全不必关心。线程池或 asyncio 已经把并发做满了，GIL 消失不会让网络变快一毫秒
热点在 NumPy / PyTorch / 压缩 / 编解码里完全不必关心。这些计算本来就在 C 层并行，它们从不受 GIL 约束
已经用多进程跑得好好的，任务之间不共享状态不必急着动。进程模型在容错和部署上的好处还在，换过去未必划算
纯 Python 的 CPU 热点，且要共享一份很大的只读状态（大索引、大字典、模型元数据），多进程的内存复制扛不住这是最对口的场景，值得现在就开个分支实测。共享内存正是线程相对进程的核心优势
任务粒度很细、数量巨大，进程间序列化开销占比过高同上，值得试。线程之间传对象不需要序列化
你在做库或框架，下游可能在 3.14t 上跑该现在就把 3.14t 加进 CI 矩阵，带 C 扩展的话要出 cp314t 轮子并声明支持

真正决定是否值得的，是第四、五行描述的那个特征：需要共享大状态的纯 Python 并行计算。这是多进程唯一真正解不好的场景——每个进程一份副本，内存翻 N 倍；换共享内存又得自己做序列化和生命周期管理，复杂度陡增。除此之外的大多数情况，现有方案都够用。

进程隔离的价值不会随 GIL 一起消失

有种说法是「无 GIL 之后就不需要多进程了」。这话只在性能维度成立，而生产环境从来不只有性能这一个维度。

同样是 12 路并行，两种模型在故障面前的差别 ────────────────────────────────────────── 多进程 自由线程（单进程 12 线程） ┌────┐┌────┐┌────┐ ... ┌──────────────────────────┐ │ P1 ││ P2 ││ P3 │ │ T1 T2 T3 ... T12 │ └────┘└────┘└────┘ └──────────────────────────┘ 某个 C 扩展段错误 → 死 1/12 → 整个进程没了，12 路全停 某个任务内存失控 → 该进程被 OOM → 整进程被 OOM，12 路全停 杀掉，其余照跑 想按资源限流 → cgroup 直接 → 要在应用层自己实现配额 按进程限 想灰度 / 滚动重启 → 逐个进程换 → 只能整进程一起换 想用满多台机器 → 同一套代码横向 → 跨机还是得起多进程 铺开即可 结论：性能只是选型的一个维度。多进程换来的隔离性、 可观测性和运维手段，无 GIL 一条都不提供。

相当常见的生产形态其实是两层叠加：每台机器起 N 个进程（隔离与容错），每个进程内部用线程或协程压榨 I/O 与并行计算。自由线程改变的是第二层能做到什么，不是第一层该不该存在。

  • 动手前先压测，用进程 CPU 占用确认瓶颈到底是不是 GIL
  • 纯 Python 的 CPU 热点，优先考虑向量化或下沉到 C 扩展
  • I/O 密集老老实实用线程池或 asyncio，不必等自由线程
  • 试 3.14t 前先数依赖：有多少带 C 扩展，有多少出了 cp314t 轮子
  • 把 sys._is_gil_enabled() 写进启动自检，不符合预期就直接失败
  • 迁移前先列清单：哪些可变对象会被多个线程写
  • 累加统计优先用「每线程局部结果 + 最后合并」，而不是加锁共享
  • 版本相关的结论都标清版本号，3.13 和 3.14 的自由线程差别很大
  • 因为「等自由线程」而推迟今天就该做的架构拆分
  • 把 CPU 密集的纯 Python 任务丢进线程池，指望线程数越多越快
  • 以为 GIL 保证了你的业务逻辑线程安全——它从来没有
  • 看到官方说「慢 5%–10%」就当成自己应用的预测值
  • 为了让某个扩展跑起来随手设 PYTHON_GIL=0，把兼容性检查绕过去
  • 把「NumPy 会释放 GIL」当成无条件成立，小数组场景下未必
  • 无 GIL 之后就把多进程整个拆掉，连带丢掉进程隔离的容错能力
  • 只看整批耗时不看 P95——争抢导致的尾延迟劣化比均值更致命

自由线程是一个给特定人群准备的工具，不是一次所有人都要跟进的升级。判据只有一条：你的瓶颈是不是「纯 Python 的并行计算 + 必须共享大状态」。是，现在就值得试；不是，继续用你手上那套，等它成为默认的那天再说。

Q&A

我把线程数从 4 调到 16，程序反而更慢了，这正常吗？
如果任务是纯 Python 计算，这完全正常，而且是必然的。GIL 保证同一时刻只有一个线程执行字节码，所以总的计算量一点没少，多出来的 16 个线程只贡献了三样东西：GIL 的争抢与交接开销、操作系统的线程上下文切换、以及 CPU 缓存局部性被打散。尾延迟劣化通常比平均耗时更明显，因为每个任务都要排队等锁。诊断方法很便宜：跑起来看进程的 CPU 占用，如果始终在 100% 上下（而不是接近「核数 × 100%」），说明你撞上的就是 GIL。确认之后，按第三节的决策树走：先看能不能向量化或下沉到 C，不能再换多进程。
GIL 多久释放一次？调 sys.setswitchinterval() 能救性能吗？
默认的切换间隔是 5 毫秒，可以用 sys.setswitchinterval() 读写。但要清楚它能调的是什么：它只影响「一个线程最多连续持有 GIL 多久」，也就是公平性和尾延迟，完全不影响总吞吐——因为任一时刻仍然只有一个线程在跑字节码。调小它可以让延迟敏感的线程更快拿到执行机会，代价是切换次数变多、总开销上升；调大则相反。所以它是一个延迟与吞吐之间的微调旋钮，不是性能问题的解药。如果你在考虑动这个参数，八成说明真正该做的是换并发模型。
NumPy 真的能绕开 GIL 吗？为什么我这边没看到加速？
能，但有条件。NumPy 这类库在进入耗时的 C 计算段之前会主动释放 GIL，算完再取回，所以那一段确实是多核并行的。没看到加速通常是三个原因之一。一是数组太小：释放和重新获取 GIL 本身有开销，库作者一般设了尺寸阈值，小数组直接算完返回、根本不释放。二是瓶颈不在 NumPy 里：如果每次循环里只有一行 NumPy、外面裹着大量纯 Python 的取值和拼装，时间其实花在了字节码上。三是底层库已经在多线程了：很多 BLAS 实现自己就会开线程池吃满核，你在外面再套一层线程只会互相抢核。判断方法还是看 CPU 占用，接近 100% 说明没并行，接近核数倍才是真并行。
自由线程构建、子解释器、PyPy，这三个是什么关系？
三个不同层面的东西，可以同时了解但不要混为一谈。自由线程构建是 CPython 的另一套编译产物，把 GIL 整个去掉，一个进程内的多个线程能真正并行执行字节码，代价是单线程稍慢、C 扩展要重新适配。子解释器是同一个进程里跑多个相互隔离的解释器实例，从 3.12（PEP 684）起它们各有各的 GIL，3.14 用 PEP 734 给了 concurrent.interpreters 这个标准库入口；它的定位是「进程级的隔离 + 线程级的开销」，默认不共享对象。PyPy 则是另一个完全独立的 Python 实现，靠 JIT 让长时间运行的纯 Python 代码快数倍，它有自己的 GIL 方案，且对 C 扩展的支持不如 CPython。简单记：自由线程解决「并行」，子解释器解决「隔离」，PyPy 解决「单线程慢」。
我想试 3.14t，但某个依赖没有对应的轮子，怎么办？
先确认这个依赖到底带不带 C 扩展。纯 Python 的包在任何构建上都能装，不存在轮子问题。带 C 扩展的包需要专门为自由线程 ABI 编译的版本，轮子文件名里会带 cp314t 这样的标记。没有的话，你有几个选择，按推荐程度排序：一是去上游仓库看有没有相关 issue，很多项目已经在推进；二是找功能等价的替代库；三是自己从源码编译（需要完整的 C 工具链，Windows 上尤其麻烦）；四是评估这个依赖能不能从热点路径上移走。有一个选项不推荐——用 PYTHON_GIL=0 强行绕过兼容性检查跑一个没声明支持的扩展。它确实能让进程起来，但你等于替扩展作者担保了它的线程安全，出问题的形式通常是随机的进程崩溃或数据损坏，不是能被 try 住的异常。
自由线程普及之后，multiprocessing 是不是就没用了？
不是。GIL 消失后，多进程在性能维度上的独有优势确实被削弱了，但进程隔离从来不只是为了性能。一个线程触发 C 扩展的段错误会带走整个进程，而多进程模型下只损失一个工作单元，其余照跑；内存失控时进程可以被单独 OOM-kill 并重启，线程不行；用 cgroup 按进程限 CPU 和内存是现成的运维手段，换成线程就得在应用层自己实现配额；灰度发布和滚动重启也都以进程为最小单位。而且一旦要横跨多台机器，多进程是绕不开的。比较现实的形态是两层叠加：每台机器起若干进程负责隔离与容错，进程内部用线程或协程压榨并行度。自由线程改变的是第二层的上限，不是第一层的必要性。
以前那些「靠 GIL 保证原子」的写法，在自由线程下还成立吗？
要分两层看。第一层是内置容器自身的完整性：CPython 在自由线程构建上为 list、dict 这类容器加了每对象的内部保护，所以并发调用单个内置方法不会把容器的内部结构搞坏、不会崩溃。第二层是你的逻辑：凡是由多步组成的操作——「读出来、改一下、写回去」，或者「先判断在不在、再决定插不插」——从来都不是原子的，GIL 时代也不是，只是那时切换间隔是 5 毫秒而这几步只要几十纳秒，撞上的概率低到近乎不存在。自由线程让线程真正并行，这个窗口就成了常态。所以答案是：容器不会坏，但你的复合逻辑会错，而且是静默地错。迁移时最该做的一件事是把「会被多个线程写的可变状态」列成清单逐个过一遍，优先改成每线程局部结果最后合并的形态，实在要共享再上锁——上锁的粒度和位置，可以用 PY19 讲的上下文管理器写法固定下来。
