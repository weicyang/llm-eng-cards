PY08 · 模块、包与项目结构

import 的三步机制与 sys.modules 缓存 / 命名空间与遮蔽 / 包与相对导入 / 入口守卫 / 循环导入与 src layout

import 不是「把文件内容贴过来」，而是「把另一个文件完整执行一遍，然后把执行结果的那个对象借你一个名字」。前面七张卡讲的都是怎么写好一个文件里的代码，这张卡讲的是怎么让几十个文件互相认识——而所有的坑，都来自那句「完整执行一遍」。

一、模块就是一个 .py 文件，import 做了三件事

模块是 Python 里最小的代码复用单位，它的定义朴素得让人意外：一个 .py 文件就是一个模块，文件名去掉后缀就是模块名。你写的 utils.py 和标准库里的 json.py、第三方的 requests/api.py，在解释器眼里是完全同一类东西，没有任何特权差别。

真正需要理解的是 import utils 这一行执行时发生了什么。很多人从别的语言带来的直觉是「引入一个声明」，像 C 的 #include 那样做文本插入，或者像 Java 的 import 那样只是给类起个短名字。Python 都不是。它做了三件事，而中间那件是所有意外的来源。

第一次 import mycfg ═══════════════════════════════════════════════════════ ① 查缓存 sys.modules["mycfg"] ? ──► 未命中，继续 （sys.modules 是一个普通的 dict，键是模块名） ② 找文件 按 sys.path 里的目录顺序，逐个找 mycfg.py 找不到 ──► ModuleNotFoundError: No module named 'mycfg' ③ 执 行 新建一个空的模块对象，把 mycfg.py 从第一行 跑到最后一行，产生的名字都挂到这个对象上 ┌──────────────────────────────────────┐ │ 顶层的每一行都是"真的执行"： │ │ print("loading") → 真的打印了 │ │ conn = connect() → 真的连了库 │ │ CFG = load_yaml() → 真的读了磁盘 │ └──────────────────────────────────────┘ ④ 存 缓存 sys.modules["mycfg"] = 那个模块对象 ⑤ 绑 名字 当前文件的命名空间里，mycfg ──► 该对象 第二次 / 第三次 / 第 100 次 import mycfg ═══════════════════════════════════════════════════════ ① 查缓存 sys.modules["mycfg"] ? ──► 命中！ ⑤ 绑 名字 直接指过去。文件不再读，代码一行都不再跑。

把这张图记牢，「模块顶层代码只执行一次」这个结论就不再需要背。它不是一条特殊规定，而是缓存命中的自然结果：第二次 import 压根没走到执行那一步。sys.modules 是解释器维护的一个全局字典，进程活着它就在，所以「一次」的范围是整个进程，不是「每个文件一次」。

import 一个模块 = 执行一个文件 + 把结果存进全局字典。谁第一个 import 它，谁就承担了执行那个文件的全部代价和副作用。

为什么「顶层副作用」是个真问题

既然模块顶层的代码会在首次 import 时执行，那么把连接数据库、读配置文件、发起网络请求这类动作写在顶层，等于把它们的执行时机交给了import 顺序——而 import 顺序是由调用方决定的，你在这个文件里看不到。

后果是一类特别难查的问题：代码在 python app.py 下正常，在 pytest 收集测试用例时却卡住三十秒，因为 pytest 为了发现测试函数需要 import 你的每一个模块，于是顶层那行 conn = connect_db() 在收集阶段就被触发了。你甚至没运行任何一个用例。

写在模块顶层的东西首次 import 时会发生什么建议
def / class 定义创建函数/类对象，代价极小正常写，这就是模块该做的事
常量、字面量字典创建对象，代价极小正常写
print() / logging.basicConfig()真的输出、真的改全局日志配置挪进函数，或只在入口文件做
CFG = json.load(open(...))真的读磁盘；文件不存在直接 import 失败改成惰性函数 get_cfg() 加缓存
conn = connect_db()真的建连接；网络不通时 import 就抛异常绝不要放顶层
耗时计算 / 加载大模型整段阻塞，被谁 import 谁买单惰性初始化，首次调用时才做

判断标准很简单：这一行如果在别人只想 from mymod import helper 借一个小函数时被执行，合理吗？不合理就不该放顶层。

二、import 的四种写法与命名空间

上一节说 import 的最后一步是「绑名字」。四种写法的差别，全部集中在这一步：它们绑的是哪个名字、绑到了什么对象上。执行文件那一步是完全一样的——无论你写哪种，目标模块都会被完整执行一遍并进入 sys.modules。

命名空间指的是「名字到对象的映射表」。每个模块有自己独立的一张表，这就是为什么 a.py 里的 count 和 b.py 里的 count 互不干扰。import 做的事，本质是往你当前这张表里塞条目。

写法你的命名空间里多了什么使用时怎么写适合的场景
import mypkg.utils只多了顶层名 mypkgmypkg.utils.f()默认选择；来源一眼可见
import numpy as np多了 np，不再有 numpynp.array()长名字、社区有约定俗成的别名
from mypkg.utils import f多了 f，没有 mypkgf()高频调用的少数几个名字
from mypkg.utils import *多了对方所有公开名字，数量不确定f()基本不要用（见下）

注意第三行的一个反直觉之处：from mypkg.utils import f 虽然只给了你一个名字 f，但 mypkg 和 mypkg.utils 两个模块都被完整执行并缓存了。「我只导了一个函数，应该很轻量」是错觉；代价由被 import 的文件决定，和你取几个名字无关。

为什么 import * 应该被禁用

星号导入把对方模块里所有不以下划线开头的名字一次性搬进你的命名空间，问题有三层。第一层是污染：你不知道多了哪些名字，读代码的人看到一个 process() 无从判断它从哪来。第二层更危险，是静默遮蔽：两个模块都有 load，后 import 的那个会无声无息地覆盖前一个，不报错、不警告，直到某天行为不对才被发现。第三层是工具失效：编辑器跳转、类型检查、静态检查都无法确定名字来源，跳转失灵、误报一片。

唯一相对可接受的例外，是模块作者显式定义了 __all__——一个字符串列表，声明「星号导入时只暴露这几个名字」。它把不确定的集合变成了确定的契约。即便如此，在应用代码里仍建议改成显式导入；__all__ 更主要的价值是给包的 __init__.py 声明公共 API。

# mypkg/utils.py
__all__ = ["parse", "dump"]      # 星号导入只给这两个

def parse(s): ...
def dump(o): ...
def _internal_helper(): ...      # 下划线开头，本来就不会被导出
def debug_probe(): ...           # 不在 __all__ 里，星号导入拿不到

import x 是「借书时记下书架编号」，from x import y 是「把那一页撕下来拿走」。撕下来的那页，原书后来改了你也不知道。

绑的是对象引用，不是「实时视图」

这一点是上面那句直觉的技术版本，也是新手会真实踩到的坑。from m import CONFIG 做的是赋值：把执行 import 那一刻 m.CONFIG 指向的对象，绑到你这边的名字 CONFIG 上。之后如果 m 内部重新给 CONFIG 赋了新对象，m.CONFIG 指向新的，而你手里的 CONFIG 还指着旧的——两个名字从此分道扬镳。

m.py your.py ──────────── ───────────────────────── CONFIG = {"mode": "dev"} from m import CONFIG import m ┌─────────────────┐ m.CONFIG ───►│ {"mode": "dev"} │◄─── CONFIG（你这边的名字） └─────────────────┘ 两个名字指向同一个对象 ── 之后 m 内部执行了 CONFIG = {"mode": "prod"} ── ┌──────────────────┐ m.CONFIG ───►│ {"mode": "prod"} │ ← m 里的名字改指了新对象 └──────────────────┘ ┌──────────────────┐ CONFIG ───►│ {"mode": "dev"} │ ← 你的名字纹丝不动（还是旧值） └──────────────────┘ 结论：要读会被重新赋值的模块级变量，用 import m 然后写 m.CONFIG （注意区别：如果 m 只是原地改字典 CONFIG["mode"]="prod"， 两边指的还是同一个对象，你能看到变化）

图末尾那个括号里的区别很重要：重新赋值会断开联系，原地修改不会。这也是为什么很多配置库把配置包在一个对象或函数里返回，而不是暴露一个裸的模块级变量——避免调用方用哪种 import 写法都能拿对。

三、模块去哪里找：sys.path 与 ModuleNotFoundError

第一节图里的第 ② 步「找文件」，依据的是 sys.path——一个普通的字符串列表，里面是一串目录路径。解释器拿着模块名，按列表从前往后逐个目录去找，找到第一个匹配的就停止。这个「从前往后、找到就停」的规则，既解释了 ModuleNotFoundError，也解释了本节后半段那个更阴险的坑。

import json → 解释器按 sys.path 顺序查找 ═══════════════════════════════════════════════════════════ sys.path[0] ┌──────────────────────────────────────────┐ │ 脚本所在目录（python app.py） │ ◄── 陷阱在这 │ 或当前工作目录（python -m / REPL） │ └──────────────────────────────────────────┘ │ 没找到，继续 ▼ ┌──────────────────────────────────────────┐ │ PYTHONPATH 环境变量里列出的目录 │ └──────────────────────────────────────────┘ │ 没找到，继续 ▼ ┌──────────────────────────────────────────┐ │ 标准库目录 .../lib/python3.12/ │ ◄── 真正的 json └──────────────────────────────────────────┘ │ 没找到，继续 ▼ ┌──────────────────────────────────────────┐ │ site-packages（第三方包，pip 装的都在这） │ └──────────────────────────────────────────┘ │ 还没找到 ▼ ModuleNotFoundError: No module named 'json' ★ 遮蔽发生的位置：如果你在脚本目录放了一个 json.py， 第一格就命中了，后面三格永远轮不到。 整个进程里所有代码（包括第三方库内部）的 import json 拿到的都是你那个文件。

sys.path 第一项的具体取值取决于你怎么启动程序，这和 PY01 · Python 环境与解释器 里讲 python -m 的那一节是同一件事的两面：那里关心「哪个解释器在跑」，这里关心「它从哪开始找」。python mypkg/tool.py 放进去的是 mypkg/ 目录，python -m mypkg.tool 放进去的是你当前所在的目录——这一个差别就能决定同一份代码是能跑还是报错。

sys.path 是一份有序的「找包地图」，第一站永远是你自己的目录。所以你在项目里新建的任何一个文件，都在和整个标准库抢名字。

标准库同名文件遮蔽：为什么它这么难查

假设你在项目目录里新建了 random.py 想练习随机数，或者建了 types.py 放自己的数据类型定义。从这一刻起，同目录下运行的所有代码，凡是 import random / import types，拿到的都是你的文件。

难查的原因在于报错位置和根因完全脱节。你的文件里没有 choice 这个函数，于是标准库使用者会拿到 AttributeError: module 'random' has no attribute 'choice'；而真正调用 random.choice 的往往不是你，是你装的某个第三方库。于是你看到的是一段深入第三方包内部的 traceback，最后一行指着别人的源码，和你五分钟前新建的那个文件看不出任何关系。更迷惑的变体是：你的 random.py 顶层恰好又 import random，这时它 import 到了自己，症状变成各种莫名其妙的属性缺失。

示例场景：某个新人在项目根目录建了一个 email.py 练习字符串处理，当天下午整个服务启动失败，traceback 有 47 行，最后停在第三方 HTTP 库内部的 AttributeError: module 'email' has no attribute 'message_from_string'，团队 3 个人排查了近 2 小时。定位方法其实只要一条命令：python -c "import email; print(email.__file__)"，输出是项目目录下的 email.py 而不是标准库路径，问题立刻明确。把文件改名为 email_demo.py、删掉同目录的 __pycache__ 后恢复。这条自查命令值得记住：任何行为诡异的 import，先打印它的 __file__ 看看到底导到了哪个文件。

症状多半的真实原因先做什么
ModuleNotFoundError: No module named 'mypkg'项目根目录不在 sys.path 里改用 python -m 启动，或把包装成可安装项目
ModuleNotFoundError，但 pip list 明明有装包的解释器和跑代码的不是同一个见 PY01 · Python 环境与解释器 的三条自查命令
标准库对象「少了属性」被同目录同名文件遮蔽print(模块.__file__) 确认来源
改了文件但行为没变残留的 __pycache__，或进程里已缓存旧模块删缓存目录，重启进程
只有某个子目录里跑会报错sys.path[0] 随启动目录变了固定从项目根目录用 -m 启动

四、包：带 __init__.py 的目录，以及绝对导入与相对导入

模块解决了「一个文件内的复用」，但项目长到二三十个文件时，全平铺在一个目录里就会出现名字打架：数据层想要一个 models.py，接口层也想要一个。包的作用就是给模块加一层命名空间——它是一个目录，目录名成为模块名的前缀，于是 db.models 和 api.models 可以共存。

myapp/ ← 包 myapp ├── __init__.py ← 标记它是包；import myapp 时执行的就是这个文件 ├── config.py ← 模块 myapp.config ├── db/ ← 子包 myapp.db │ ├── __init__.py │ └── models.py ← 模块 myapp.db.models └── api/ ← 子包 myapp.api ├── __init__.py ├── models.py ← 模块 myapp.api.models（和上面同名不冲突） └── routes.py ← 模块 myapp.api.routes 在 routes.py 里引用 myapp.db.models 的两种写法 ─────────────────────────────────────────────── 绝对导入 from myapp.db.models import User ← 从"根"写全路径 相对导入 from ..db.models import User ← 从"我自己"往上数 ↑↑ 一个点 = 当前包（myapp.api） 两个点 = 上一层包（myapp）

__init__.py 是包的标志文件，它可以完全为空——很多项目里就是空的，存在本身就是全部作用。它的第二个用途是充当包的门面：在里面 from .db.models import User，外部就能直接写 from myapp import User，不必知道 User 藏在哪个子模块里。这是一种有价值的封装，但要克制：__init__.py 里的 import 会在任何人 import 这个包时全部执行，把整个包的子模块都拉起来，第一节说的顶层副作用问题在这里会被放大成「import 一个包等于加载全部代码」。

Python 3.3 之后引入了命名空间包：没有 __init__.py 的目录也能被当成包导入。它的设计目的是让同一个包名的内容分散在多个目录里（大型插件体系会用到）。代价是它让「少写了一个 __init__.py」从一个立刻报错的显式错误，变成一个不报错但行为微妙不同的隐式状态——比如工具扫描包时可能把无关目录当成包，或者两个同名目录被意外合并。对普通项目的建议很直接：该建包就老老实实放一个空的 __init__.py，把这份便利留给真正需要它的场景。

包就是给模块加姓氏的目录。__init__.py 是这个家族的门牌和门面：有它才算一户人家，里面写什么决定了外人一进门能直接看到谁。

绝对导入与相对导入怎么选

维度绝对导入 from myapp.db.models import User相对导入 from ..db.models import User
写法从项目顶层包名开始写全. 表示当前包，.. 表示上一层，可继续叠加
可读性一眼知道来源，跨文件搜索友好短，但要先知道自己在哪一层才能读懂
重命名包包改名要全局替换包内移动/改名不受影响
移动单个文件不受影响文件换层级后点数要跟着改
能直接 python 文件.py 跑吗能（只要根目录在 sys.path 上）不能，必然报 ImportError
官方倾向PEP 8 推荐，作为默认包内部引用可用，跨包不要用

表格最后两行值得展开。相对导入的点号是相对于当前模块所属的包解析的，而这个信息存在模块的 __package__ 属性里。当你用 python myapp/api/routes.py 直接运行时，这个文件被当作顶层脚本，__package__ 是空的——解释器不认为它属于任何包，自然无从解析那两个点。于是你会看到这条经典报错：

$ python myapp/api/routes.py
ImportError: attempted relative import with no known parent package

$ python -m myapp.api.routes     # 正确做法：让解释器知道它属于哪个包
（正常运行）

这条报错的真正含义不是「相对导入坏了」，而是「你用错了启动方式」。python -m 把参数当作模块路径而不是文件路径来解析，解释器会先确定 myapp.api 这个包，再在包的语境里运行 routes，__package__ 就有了正确的值。这也再次呼应了 PY01 · Python 环境与解释器 的结论：-m 不只是换个写法，它改变了程序被加载的语境。

五、__name__ == "__main__"：它到底是什么

几乎每份 Python 教程都会让你写这一行，但很少解释它。其实没有任何魔法：__name__ 就是一个普通的模块级变量，由解释器在加载模块时自动写入，值是这个模块的名字。myapp/config.py 被 import 时，它的 __name__ 是字符串 "myapp.config"。

唯一的特例是：被当作入口直接运行的那个模块，解释器不会用它的文件名，而是固定写入 "__main__"。因为此时它不是被谁 import 的，没有「在包里的名字」这回事，解释器需要一个统一的标记。

启动方式__name__ 的值if 块说明
python tool.py"__main__"✅ 执行它是入口
python -m myapp.tool"__main__"✅ 执行同样是入口，只是加载语境不同
别的文件里 import myapp.tool"myapp.tool"❌ 跳过它是被复用的库
别的文件里 from myapp.tool import f"myapp.tool"❌ 跳过整个文件仍被执行，只是 if 块跳过
pytest 收集到这个文件"myapp.tool"❌ 跳过收集本质上就是 import
在 REPL 里敲代码"__main__"—交互式会话本身就是 __main__

所以这一行判断的语义可以翻译成大白话：「如果我是被直接运行的那个人，就干活；如果我只是被别人借去用的一个零件，就安静地只提供定义。」

__name__ 回答的是「我这次是主角还是配角」。写这个判断，就是让同一个文件既能当命令行工具跑，又能当库被别人 import，两种身份互不打扰。

不写它的实际后果

假设你写了一个数据清洗脚本 clean.py，里面定义了一个好用的 normalize() 函数，文件末尾直接是主流程：读取一个 800 MB 的 CSV、清洗、写回磁盘。同事看中了 normalize()，在自己的文件里写 from clean import normalize——按第一节的机制，clean.py 会被完整执行一遍，那 800 MB 的读写在他毫不知情的情况下跑了起来，还可能覆盖掉输出文件。他的代码里连一次 normalize() 都还没调用。

示例场景：一个日报生成脚本没有写入口守卫，主流程末尾会给 12 个人发一封邮件。后来有人把它 import 进测试文件复用其中的日期解析函数，CI 每次跑测试就发一轮邮件，一周内多发了 340 多封才被发现。修复只用了 2 行——把主流程包进 def main(): 再加一句 if __name__ == "__main__": main()。这个例子的价值在于：入口守卫防的不是「跑错」，而是「被别人 import 时悄悄跑了」，而后者你在自己的文件里永远测不出来。

包也可以有入口：__main__.py

模块靠 if __name__ == "__main__" 表明入口，包则靠一个名叫 __main__.py 的文件。在包目录里放上它，python -m myapp 就会执行这个文件——你平时敲的 python -m pip、python -m http.server、python -m venv，走的都是这条路。

# myapp/__main__.py
import sys
from .cli import run          # 包内相对导入，因为 -m 加载语境正确

if __name__ == "__main__":
    sys.exit(run(sys.argv[1:]))

注意这个文件里仍然要写那行判断。虽然 python -m myapp 时它必然成立，但 __main__.py 也可能被别的工具 import 到（例如打包工具扫描模块、测试框架收集文件），加上它没有成本，漏掉它就退回到上面那个发邮件的故事。

六、循环导入与最小项目结构

循环导入是模块机制里最后一个、也是最容易让人怀疑人生的坑：a.py 顶层 import b，而 b.py 顶层又 import a。它之所以令人困惑，是因为报错信息往往是 ImportError: cannot import name 'X' from partially initialized module，而你盯着两个文件，每一行单独看都没毛病。

用第一节那张图就能推演出原因。关键在于：模块对象是在开始执行之前就被放进 sys.modules 的（否则无法处理自引用），所以在它执行到一半时，缓存里已经有一个「半成品」了。

入口执行 import a ═══════════════════════════════════════════════════════════ t1 sys.modules["a"] = 空模块对象 ← 先占位，再执行 t2 开始执行 a.py t3 a.py 第 1 行：import b t4 sys.modules["b"] = 空模块对象 t5 开始执行 b.py t6 b.py 第 1 行：from a import helper t7 查 sys.modules["a"] ──► 命中！（但它是 t1 的半成品） t8 到这个半成品里找 helper ┌────────────────────────────────────────┐ │ a.py 才执行到第 1 行，helper 定义在 │ │ 第 20 行，此刻这个名字还不存在 │ └────────────────────────────────────────┘ t9 ✗ ImportError: cannot import name 'helper' from partially initialized module 'a' (most likely due to a circular import) ★ 注意 t7：缓存"命中"了，所以不会重新执行 a.py， 也就永远等不到 helper 被定义。 ★ 同样是循环，如果 b 写的是 import a（而不是 from a import helper）， t8 只是绑定模块对象、不取属性，往往能侥幸通过—— 直到某个函数在运行期真的访问 a.helper 才出问题。

图里最后那条备注解释了一个常见现象：同样的循环依赖，改一下 import 写法有时就「好了」。这不是修好，是把报错从 import 期推迟到了运行期，风险更大。真正的修法有三种。

解法怎么做适用情形代价
抽出共享部分（首选）把 a、b 都依赖的类型/常量挪到第三个模块 common.py，两边都只依赖它循环的根因是职责划分不清要动结构，但换来的是真正无环的依赖图
函数内延迟导入把 import b 从文件顶层挪到用到它的那个函数体里依赖只在少数几个函数里用到把问题推迟到调用时；藏起了真实依赖关系
类型检查期导入if TYPE_CHECKING: 里导入，注解写成字符串依赖纯粹只为了写类型注解只解决注解场景，运行期真要用还是会炸
# 解法三：注解需要 User，但运行期并不需要真的导入它
from typing import TYPE_CHECKING

if TYPE_CHECKING:            # 只有类型检查器会走进来，运行时恒为 False
    from .models import User

def save(u: "User") -> None: # 注解写成字符串，运行期不求值
    ...

循环导入几乎总是设计信号而不是语法问题：它说明两个模块在互相知道对方的细节。所以第一解法排在首位——多数情况下，抽出 common.py 之后你会发现代码本来就该这么分。

循环导入不是 Python 的缺陷，是依赖图上有环的报警器。遇到它先别想怎么绕过，先问「这两个模块为什么必须互相认识」。

收尾：一个能交付的最小项目结构

把前面所有内容收束起来——虚拟环境、依赖声明、包与入口、可被 import 的结构——落地成一套目录，就是下面这个样子。它不是唯一正确答案，但对 95% 的项目够用，而且每一项都能说出理由。

myproject/ ├── pyproject.toml ← 依赖 + 项目元信息（唯一的真相来源） ├── uv.lock ← 锁定的精确版本，提交进 git ├── README.md ├── .gitignore ← 至少排除 .venv/ 和 __pycache__/ ├── .venv/ ← 虚拟环境，不提交 ├── src/ │ └── myapp/ ← 真正的包，全部源码在这 │ ├── __init__.py ← 暴露公共 API │ ├── __main__.py ← python -m myapp 的入口 │ ├── config.py │ ├── common.py ← 共享类型/常量，斩断循环依赖 │ └── db/ │ ├── __init__.py │ └── models.py └── tests/ ├── test_config.py └── test_models.py ← 里面写 from myapp.db.models import ... 注意：不写 from src.myapp... 运行方式 ──────────────────────────────────────────── uv sync 装依赖，顺便把 myapp 以可编辑方式装进 .venv uv run python -m myapp 跑程序 uv run python -m pytest 跑测试

最需要解释的是那个 src/ 目录，也就是社区说的 src layout。它看起来只是多套了一层，实际解决的是一个很具体的问题：测试到底在测哪份代码。

如果包直接放在项目根目录（myproject/myapp/），那么你在根目录下跑测试时，sys.path[0] 就是根目录，import myapp 会直接命中源码目录——即使这个包压根没被正确安装、即使 pyproject.toml 里的打包配置漏了文件，测试照样全绿。等到别人 pip install 你的包，才发现装出来的东西缺东西、根本 import 不起来。这类问题在发布环节暴露，修复成本最高。

src layout 把源码挪进 src/ 之后，根目录下就不存在一个叫 myapp 的目录了，sys.path[0] 里找不到它。测试想 import 成功，唯一的途径是包已经被正确安装进虚拟环境（uv sync 或 pip install -e . 会做这件事）。于是「能不能装出来」这个问题被前移到了每一次本地测试，而不是留到发布那天。用第三节的话说：src layout 就是刻意把源码目录从 sys.path 第一站上拿掉，逼你走安装这条正路。

  • 模块顶层只放 def、class、常量；有代价的初始化改成函数惰性执行
  • 默认用绝对导入 from myapp.db.models import User，包内部才考虑相对导入
  • 包内模块当脚本跑时用 python -m myapp.tool，不用 python myapp/tool.py
  • 每个可执行文件都写 if __name__ == "__main__": main()，主逻辑收进 main()
  • import 行为诡异时先 print(模块.__file__) 确认导到了哪个文件
  • 新项目起手就用 src layout + pyproject.toml + tests/，源码只放 src/ 下
  • 遇到循环导入优先抽出 common.py，把依赖图改成无环
  • 在模块顶层连数据库、读配置文件、发网络请求、加载大模型
  • 使用 from x import *（即使对方定义了 __all__，应用代码里也显式导入）
  • 把文件命名为 json.py / random.py / types.py / email.py 等标准库同名
  • 对会被重新赋值的模块级变量用 from m import CONFIG——你拿到的会是旧值
  • 为了绕开循环导入，把 from a import f 随手改成 import a 就当修好了
  • 在 __init__.py 里 import 整个包的所有子模块，让「用一个函数」变成「加载全部」
  • 在 tests/ 里写 from src.myapp import ...——这等于绕过了安装校验

关于把项目真正打包发布到 PyPI、配置构建后端与版本号策略，属于工程化那一组的内容（详见 PY37），本卡到「本地能装、能跑、能测」为止。走到这一步，你已经具备把一堆 .py 文件交付成一个项目的全部基础。

Q&A

同一个模块被 import 了五次，里面的 print 为什么只打印一次？
因为 import 的第一步是查 sys.modules 这个全局字典。首次 import 时模块文件被从头到尾执行一遍，执行结果的模块对象被存进字典；之后每一次 import 都会在第一步就命中缓存，直接把名字绑到那个已有对象上，文件根本不会被再次读取和执行。所以「模块级代码只执行一次」不是一条特殊规则，而是缓存命中的自然结果。需要注意这个「一次」的范围是整个进程：进程重启后缓存清空，会重新执行。这也是为什么在模块顶层写有副作用的代码很危险——它的执行时机取决于谁第一个 import 它，而这个信息在你的文件里完全看不出来。
import m 和 from m import f 哪个更快、更省资源？
两者的代价几乎完全一样，因为它们都会把 m.py 完整执行一遍并缓存。差别只在最后一步绑定了什么名字：前者绑模块对象，后者绑模块里的某个属性。「我只导了一个函数所以更轻量」是很常见的误解，实际上你导一个名字和导整个模块，触发的文件执行是同一份。如果 m 是一个包，from mypkg.sub import f 还会连带执行 mypkg/__init__.py 和 mypkg/sub.py 两个文件。真正影响启动耗时的，是被导入模块顶层做了多少事，以及 __init__.py 里拉起了多少子模块，而不是 import 的写法。
为什么不能用 from module import *？
有三个层次的问题。首先是命名空间污染：它一次性搬进来的名字数量不确定，读代码的人看到一个函数调用无法判断它来自哪里。其次是静默遮蔽，这一条最危险——如果两个模块都有叫 load 的函数，后 import 的会无声覆盖前一个，没有任何报错或警告，直到行为出错才会被发现。第三是工具失效：编辑器的跳转定义、静态类型检查、未定义变量检查都无法确定名字的来源，跳转失灵、误报一片。唯一相对可控的情况是对方模块定义了 __all__ 显式声明导出清单，但即便如此，在应用代码里仍建议改成显式导入，把 __all__ 留给包的 __init__.py 声明公共 API。
我在项目里建了个 random.py，结果一个完全无关的第三方库报错了，这是怎么回事？
这是标准库被同名文件遮蔽。解释器按 sys.path 从前往后找模块，第一站通常是脚本所在目录或当前工作目录，标准库排在它后面。所以当同目录下存在 random.py 时，整个进程里所有代码的 import random——包括第三方库内部那些——拿到的都是你的文件。难查的原因在于报错位置和根因脱节：你的文件没有 choice，于是报错出现在真正调用 random.choice 的第三方库源码里，traceback 最后一行指着别人的代码。定位方法只有一条命令：python -c "import random; print(random.__file__)"，如果输出是你的项目目录而不是标准库路径，问题就确定了。修复是改名并删掉同目录的 __pycache__。
__init__.py 能不能不写？Python 3.3 之后不是可以省略了吗？
技术上可以省略，那样得到的是命名空间包，它的设计目的是让同一个包名的内容分散在多个目录里，主要服务于大型插件体系。但对普通项目不建议依赖这个特性，原因是它把一个显式错误变成了隐式状态：以前少写 __init__.py 会立刻 import 失败，现在不报错，但行为有微妙差异——打包工具在自动发现包时可能漏掉它，测试框架扫描目录时可能把无关目录当成包，两个同名目录还可能被意外合并成一个包。这些问题的共同点是不会当场报错，而是在打包或部署阶段以奇怪的形式出现。建议是：该建包就放一个空的 __init__.py，成本为零，换来的是行为确定。
为什么 python mypkg/tool.py 会报 attempted relative import with no known parent package？
相对导入里的点号是相对于「当前模块所属的包」解析的，这个信息存在模块的 __package__ 属性里，由解释器在加载时根据加载语境填入。当你用 python 某个文件.py 直接运行时，这个文件被当作顶层入口脚本，解释器不认为它属于任何包，__package__ 是空的，于是那个点没有参照物可解析，只能报错。正确做法是用 python -m mypkg.tool：-m 接收的是模块路径而不是文件路径，解释器会先定位 mypkg 这个包，再在包的语境里执行 tool，__package__ 就有了正确的值。顺带一提，-m 还会把当前工作目录放进 sys.path，所以在项目根目录下执行时也更容易 import 到自己的包。
不写 if __name__ == "__main__": 到底会怎样？
你的文件一旦被别人 import，整个文件会从第一行执行到最后一行，包括你写在末尾的主流程。也就是说，同事只想借用你文件里的一个工具函数，写了 from clean import normalize，你那段读 800 MB CSV、写回磁盘的主流程就会在他毫不知情的情况下跑起来，甚至可能覆盖输出文件——而他连一次 normalize() 都还没调用。更隐蔽的触发场景是测试：pytest 收集用例的本质就是 import 每一个文件，所以主流程会在「收集阶段」被触发，你还没跑任何一个用例。__name__ 在直接运行时是 "__main__"、被 import 时是模块名，这个判断表达的就是「我这次是入口还是零件」。修复通常只要两行：把主流程包进 def main():，末尾加 if __name__ == "__main__": main()。
循环导入报 partially initialized module，为什么把 from a import f 改成 import a 就不报了？
因为两种写法在 import 的最后一步做的事不同。模块对象会在开始执行之前就被放进 sys.modules 占位，所以循环回来时缓存是命中的，只不过拿到的是个执行到一半的半成品。from a import f 需要立刻到这个半成品上取属性 f，而 f 可能还没被定义，于是当场报错；import a 只是把模块对象绑到名字上，不访问任何属性，所以能通过。但这不是修好了，只是把失败从 import 期推迟到了运行期——等某个函数真的访问 a.f 时如果那时已经定义好了就侥幸没事，时序稍变就会以更难定位的形式爆出来。真正的修法是消除环：优先把两边共用的类型和常量抽到第三个模块，其次是函数内延迟导入，纯注解场景可以用 if TYPE_CHECKING:。
src layout 只是多套一层目录，真的有必要吗？
它解决的是一个具体且代价很高的问题：测试到底在测哪份代码。如果包直接放在项目根目录，你在根目录下跑测试时 sys.path[0] 就是根目录，import myapp 会直接命中源码目录，哪怕这个包根本没被正确安装、哪怕打包配置漏掉了某些文件，测试照样全绿。等到别人真的去安装你的包，才发现装出来的东西是残缺的。这类问题在发布环节才暴露，排查和修复成本都最高。把源码挪进 src/ 之后，根目录下不再存在名为 myapp 的目录，测试想 import 成功就必须先把包正确安装进虚拟环境，于是「能不能装出来」这个检验被前移到了每一次本地测试。代价只是多一层目录和一次 uv sync，收益是打包配置错误当天就会被发现。
包已经装进虚拟环境了，为什么改了源码却不生效？
大概率是以普通方式安装的，也就是把源码复制了一份到 site-packages 里，你改的是项目目录里的原件，运行时 import 到的是副本。解决办法是改用可编辑安装（pip install -e .，uv sync 对当前项目默认就是这个行为），它在 site-packages 里放的是一个指向你源码目录的链接，改完立刻生效。另外还有两种情况会造成类似症状：一是残留的 __pycache__ 在极少数时间戳异常的场景下没有失效，删掉重跑即可；二是长期运行的进程（比如开着的 Jupyter 内核或未重启的服务）里模块早已缓存在 sys.modules 中，import 命中缓存不会重新读文件，必须重启进程。判断到底是哪一种，还是那条命令：打印模块的 __file__，看看它实际加载的是哪个路径下的文件。
