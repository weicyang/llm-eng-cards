PY10 · 拷贝语义与共享状态陷阱

赋值不是拷贝 / 浅拷贝只拷一层 / 共享状态的四类经典事故 / deepcopy 的真实代价 / 不可变优先的设计取舍

Python 里没有「把这个值复制一份」这种默认动作。你写的每一个赋值、每一次传参、每一处返回，都只是让一个新名字指向同一个对象。所有共享状态的 bug 都源自同一个误解：以为自己拿到了副本，其实拿到的是钥匙。

一、三个层次：赋值、浅拷贝、深拷贝

把拷贝这件事想清楚，只需要接受一个事实：Python 的变量不是盒子，是标签。b = a 这行代码做的全部工作是给 a 当前指向的那个对象再贴一张写着 b 的标签，对象本身一个字节都没有动。这种「多个名字指向同一对象」的状态叫 别名，也就是 aliasing——它本身完全合法，甚至是 Python 高效的原因之一，出问题的只是当你误以为自己拿到了独立副本的时候。

真正需要区分的是三个层次。赋值压根没拷，连外层容器都是同一个。浅拷贝新建了外层容器，逐个把原容器里的元素引用抄进去——注意抄的是引用，所以内层对象仍然是共享的。深拷贝递归地走遍整个 对象图（对象与对象之间通过引用连成的有向图），把路上遇到的每个可变对象都新建一份。三者不是「拷贝程度不同」，而是「在对象图的第几层停手」。

原始结构：data = [inner, tags]，其中 inner = [1, 2]，tags = ["a"] ① 赋值 b = data ② 浅拷贝 b = data[:] ③ 深拷贝 b = deepcopy(data) ───────────────────── ───────────────────── ───────────────────────── data ─┐ data ─> [ · · ] data ─> [ · · ] ├─> [ · · ] │ │ │ │ b ──┘ │ │ b ─> [ · · ] ▼ ▼ ▼ ▼ │ │ [1,2] ["a"] [1,2] ["a"] ▼ ▼ [1,2] ["a"] b ─> [ · · ] 外层同一个 外层是新的 │ │ 内层同一个 内层还是同一个 ▼ ▼ [1,2]' ["a"]' 整棵图都是新的 验证方式（三行就能分辨自己处在哪一层） b is data → ①True ②False ③False ← 外层是不是同一个 b[0] is data[0] → ①True ②True ③False ← 内层是不是同一个 b == data → ①True ②True ③True ← 值相等，分辨不出任何东西

最后一行值得单独说。== 在这三种情况下全都返回 True，所以它对判断「有没有拷贝」毫无帮助。要确认共享关系，只能用 is 或 id()。这也是后面第六节排查手法的全部基础。

改外层和改内层，分别谁能看见

下面这张表是本卡最该记住的东西。它把「你做了什么操作」和「原对象是否被牵连」拆开对照，三列分别对应上面三个层次。

你对 b 做的操作赋值 b = data浅拷贝 b = data[:]深拷贝 b = deepcopy(data)
b.append(x)（改外层结构）data 也变长 ⚠️data 不变 ✅data 不变 ✅
b[0] = 新对象（重绑外层槽位）data[0] 被换掉 ⚠️data[0] 不变 ✅data[0] 不变 ✅
b[0].append(9)（改内层对象）data[0] 也变长 ⚠️data[0] 也变长 ⚠️data[0] 不变 ✅
b[0] += [9]（列表原地扩展）data[0] 也变长 ⚠️data[0] 也变长 ⚠️data[0] 不变 ✅
b[1] = b[1] + "x"（不可变元素）data[1] 被换掉 ⚠️data[1] 不变 ✅data[1] 不变 ✅

表格里只有第三、四行是浅拷贝与深拷贝的分界线，而它们恰好是实际项目里最容易出现的两种写法。换句话说，绝大多数「明明拷过一份为什么还是串了」的问题，都落在这两行上：你拷的是外层，改的是内层。

最后一行则解释了另一个常见困惑：如果容器里装的全是不可变对象（数字、字符串、元组），浅拷贝的效果和深拷贝看起来完全一样。因为不可变对象无法被原地修改，共享它毫无风险——这正是下一节里「对 tuple 拷贝没有意义」的同一个道理。关于可变与不可变的划分，PY02 · 变量与内置类型 和 PY03 · 容器四件套 已经铺过底，这里直接拿来用。

赋值是「再贴一张标签」，浅拷贝是「换个新篮子、原封不动把东西挪过去」，深拷贝是「连篮子里的东西也照着做一个」。判断自己在哪一层，只看 is，别看 ==。

二、浅拷贝的四种写法与它们的等价性

浅拷贝在 Python 里有好几种写法，新手常以为它们之间有深浅差别，于是在代码里混着用、或者反复叠加，指望多写一层能多拷一层。实际上对列表来说，list(x)、x[:]、x.copy()、copy.copy(x) 是完全等价的四种拼法：都新建一个列表对象，都把原列表里的元素引用逐个抄过去，都只拷一层。它们的差别仅在可读性和适用范围，不在语义。

写法适用类型本质什么时候选它
x.copy()list / dict / set容器自己的浅拷贝方法首选：意图写在方法名上，读代码的人不会误会
list(x) / dict(x) / set(x)任何可迭代对象用构造函数新建同类容器需要顺便换类型时，例如把元组、生成器收成列表
x[:]list（及支持切片的序列）整段切片，切片本身返回新对象老代码里很常见，但对不熟悉的人不直观，新写别用
copy.copy(x)几乎任何对象走 __copy__ 协议的通用浅拷贝对象类型不确定，或要拷自定义类的实例
copy.deepcopy(x)几乎任何对象递归拷整个对象图确实需要完全独立的副本，且清楚代价（见第四节）

字典和集合没有切片语法，所以只剩 dict(x) / x.copy() 和 set(x) / x.copy() 两条路，同样都是浅的。dict 的浅拷贝容易给人错觉，因为很多字典的值本来就是数字或字符串，拷完怎么改都不串；但只要某个值是列表或嵌套字典，问题就立刻回来了——这是配置对象最常见的翻车方式。

import copy
cfg = {"retry": 3, "hosts": ["a", "b"]}

c1 = cfg.copy()             # 浅：hosts 是同一个列表
c1["retry"] = 5             # 改标量，互不影响
c1["hosts"].append("c")     # 改嵌套，cfg["hosts"] 也变成三个了

c2 = copy.deepcopy(cfg)     # 深：hosts 是新列表
c2["hosts"].append("d")     # cfg 完全不受影响

对不可变容器拷贝没有意义

元组是不可变的，谁都无法原地修改它，因此「独立副本」这个需求对它不存在。Python 干脆做了优化：tuple(t) 和 copy.copy(t) 直接把原对象还给你，tuple(t) is t 为真。同样的道理适用于 frozenset、字符串、数字。这不是特例，而是可变性推出的必然结论——不能被改的东西，共享和复制没有任何可观测差别。

但这里有个必须警惕的错位：元组不可变，指的是它的槽位不可变，不是它装的东西不可变。t = ([1, 2], "x") 里那个列表照样能被 append，而且因为 tuple(t) is t，你连「拷一份元组来隔离」这条路都走不了，只能 deepcopy。所以「用元组做常量就安全了」这个说法只在元组里装的全是不可变对象时才成立。

四种浅拷贝写法是同一件事的四种拼法，不存在「更深一点」的那个。想确认是不是真的隔离了，别数拷了几次，去看内层的 id() 变不变。

三、共享状态的四类经典事故

知道了浅拷贝只拷一层，接下来的问题是：现实代码里哪些地方会在你没意识到的时候产生共享？下面四类占了绝大多数。它们表面上毫不相干，成因却是同一个——某个可变对象只被创建了一次，却被多处引用。

事故典型写法成因修法
(a) 乘法造多维结构[[0] * 3] * 3、[[]] * n* 只复制引用，n 行是同一个列表用推导式 [[0] * 3 for _ in range(3)]
(b) 类属性写成可变对象class C: items = []类属性属于类，所有实例共用一份在 __init__ 里建实例属性
(c) 返回内部可变对象return self._items调用方拿到的是内部状态本体返回 self._items.copy() 或只读视图
(d) fromkeys 配可变默认值dict.fromkeys(ks, [])那个 [] 只求值一次，所有键共享用推导式 {k: [] for k in ks}

还有第五类——可变对象作为函数默认参数，def f(items=[])。它的成因和 (d) 完全一样（默认值在函数定义时求值一次，之后每次调用复用同一个对象），PY05 · 函数入门与参数传递 已经完整讲过，这里不再重复。

(a) 乘法造出来的「多维数组」只有一行

这是最容易复现、也最容易被误诊的一类。[[0] * 3] * 3 看起来像个 3×3 的矩阵，改一个格子却会让整列一起变。原因在于两个 * 的含义并不对称：内层 [0] * 3 复制的是不可变的整数 0，没问题；外层的 * 3 复制的是「那个列表的引用」，于是三行指向同一个对象。

grid = [[0] * 3] * 3 ← 外层乘法只复制引用 grid ──> [ · · · ] ← 外层列表确实有 3 个槽位 │ │ │ └────┼────┘ ▼ [ 0, 0, 0 ] ← 但三个槽位指向同一个内层列表！ grid[0][1] = 9 之后 [ 0, 9, 0 ] ← 只有一个对象被改 grid 打印出来：[[0,9,0], [0,9,0], [0,9,0]] ← 三行全变 正确写法：推导式让循环体每轮都执行一次 [0] * 3 grid = [[0] * 3 for _ in range(3)] grid ──> [ · · · ] │ │ └──> [0, 0, 0] ← 三个独立对象 │ └───────> [0, 0, 0] └────────────> [0, 0, 0] 自查一行：len({id(row) for row in grid}) 应该等于 len(grid)

最后那行自查很实用：把每一行的 id() 收进集合，如果去重后只剩 1 个，说明所有行其实是同一个对象。这条思路可以推广到任何「一堆容器怀疑在共享」的场景。

(b) 类属性与实例属性：一份还是每个一份

写在 class 语句体里的赋值创建的是类属性，它在类被定义时执行一次，归类所有；写在 __init__ 里的 self.x = ... 创建的是实例属性，每次实例化各建一份。类属性放常量（如 MAX_RETRY = 3）完全没问题，放可变对象就变成了全局共享池。

class Cart:
    items = []              # ⚠️ 类属性：所有购物车共用一个列表

class CartOK:
    def __init__(self):
        self.items = []     # ✅ 实例属性：每个实例一份

a, b = Cart(), Cart()
a.items.append("book")
print(b.items)              # ['book'] —— b 凭空多了一件商品

这类 bug 的隐蔽性来自一个细节：读取时 a.items 和 b.items 都能正常工作，看不出异常；a.items = [] 这样的重新赋值还会悄悄创建一个实例属性遮蔽掉类属性，于是现象变得时有时无——改用 append 就串，改用 = 就不串。同一段代码两种表现，排查时极易误判为「偶发」。

(c) 返回内部可变对象的引用

一个类精心用 _items 这样的下划线前缀表示「内部状态」，却在 getter 里直接 return self._items，等于把内部状态的钥匙交了出去。调用方完全可以 obj.get_items().clear()，绕过你所有的校验逻辑把状态清空，而且这行代码看起来相当无辜。封装在这里是失效的——私有约定只挡住了名字，没挡住引用。

(d) dict.fromkeys 的陷阱

dict.fromkeys(keys, []) 的问题在于第二个参数是一个已经求值完毕的对象，不是「每个键各造一个空列表」的指令。fromkeys 只是把这同一个列表塞进每个键，于是给任意一个键 append，所有键都跟着变。表现和 (a) 完全同构，改法也一样：换成字典推导式，让 [] 在循环里反复执行。

示例场景：某订单服务用 dict.fromkeys(warehouse_ids, []) 初始化「仓库 → 待发货订单」的映射，共 8 个仓库。上线后第一天，运营发现 8 个仓库的待发货列表内容完全一致，都是全量 1,240 条订单；按仓库拆单的下游任务因此重复推送了 8 次，产生 9,920 条发货指令，人工回滚耗时约 3 小时。根因是那个 [] 只被创建了一次，8 个键共享它。修复只有一行：改成 {wid: [] for wid in warehouse_ids}。事后补的回归测试也很简单——断言 len({id(v) for v in mapping.values()}) == 8。

这四类事故只有一个共同成因：某个可变对象只被创建了一次，却被当成了多份用。看到 *、fromkeys、类属性、裸 return self._x，就该条件反射地问一句「这里到底造了几个对象」。

四、深拷贝的代价与边界

知道了共享的危险，很容易走向另一个极端：凡是要传出去的对象一律 deepcopy 一下，图个安心。这个习惯在小对象上无害，在真实系统里则是性能事故的常见来源，而且它还会把一些你根本不想复制的东西一起复制走。

copy.deepcopy 的工作方式是递归遍历整个对象图：每遇到一个对象就检查它在 备忘表（memo，一个 id(对象) → 新对象 的字典）里有没有出现过，没有就新建一份并登记，然后继续往它的每个属性、每个元素里钻。备忘表的存在让循环引用不会导致无限递归，也保证了原图里共享的两处引用在副本里仍然指向同一个新对象——拓扑结构是被忠实保留的。代价是：耗时和内存都随对象图的节点总数增长，而不是随你关心的那几个字段增长。

deepcopy 在做什么：带备忘表的图遍历 原图（注意 C 被 A、B 共同引用，且 D 指回 A 形成环） A ──> B ──> C │ ▲ └───────────┘ A ──> D ──> A (环) 遍历过程 memo: {id(原) : 新} ───────────────────────── ────────────────────── 访问 A → 不在 memo → 新建 A' {A: A'} 访问 B → 不在 memo → 新建 B' {A:A', B:B'} 访问 C → 不在 memo → 新建 C' {A:A', B:B', C:C'} 访问 D → 不在 memo → 新建 D' {A:A', B:B', C:C', D:D'} A 的第二条边指向 C → 命中 memo → 直接复用 C' ← 共享关系被保留 D 指回 A → 命中 memo → 直接复用 A' ← 环不会死循环 代价 ≈ O(图中对象总数)，而不是 O(你关心的字段数) 一个挂着 50 万个小对象的实例，deepcopy 就要走 50 万次这个流程

它会连带复制你不想复制的东西

deepcopy 不知道你的业务语义，它只知道「这个属性引用了一个对象，那就把它也拷一份」。于是一个持有数据库连接池的服务对象被深拷贝时，连接池、底层 socket 包装、线程锁会一起进入递归。结果通常是两种：要么直接抛 TypeError: cannot pickle '_thread.lock' object 这类错误（很多不可复制的资源会在这一步拒绝），要么更糟——拷出一个看起来正常、实则持有失效句柄的对象，等到真正用它读写时才在完全无关的地方炸开。

需要控制这个行为时，可以在类上定义 __deepcopy__ 或 __copy__，显式声明哪些字段拷、哪些字段共享、哪些字段置空重建；__reduce__ 则同时影响 pickle 和 copy，适合想统一序列化与复制语义的场景。实现 __deepcopy__ 时记得把 memo 传递下去，否则会丢掉循环引用保护。

class Service:
    def __init__(self, conn, cache):
        self.conn, self.cache = conn, cache   # conn 共享，cache 独立

    def __deepcopy__(self, memo):
        new = object.__new__(Service)
        memo[id(self)] = new                  # 先登记，防循环引用
        new.conn = self.conn                  # 直接共享，不递归
        new.cache = copy.deepcopy(self.cache, memo)
        return new

四种方案的代价对比

把「不拷 / 拷一层 / 拷整棵图 / 从源头重建」并排放在一起看，选择就清楚多了。重建这一列常被忽略，但它往往是最优解：与其深拷贝一个庞大对象，不如重新走一遍构造流程，只带上真正需要的字段。

方案时间代价内存代价隔离程度适用场景
赋值（不拷）常数级无新增零隔离只读传递，或明确就是要共享同一状态
浅拷贝与元素个数成正比只多一个外层容器只隔离外层元素全是不可变对象；或只需防止外层被增删
深拷贝与对象图节点总数成正比接近翻倍完全隔离小而复杂的嵌套结构，如配置树、测试夹具
显式重建取决于构造逻辑，通常远低于深拷贝只占新对象完全隔离且可裁剪大对象、持有外部资源的对象、只需要部分字段时
改成不可变零（无需拷贝）无新增天然安全常量、配置、值对象——见第五节

示例场景：某风控服务在每次请求处理前对一个「规则上下文」对象做 copy.deepcopy，图的是各请求互不干扰。上线初期上下文里只有十几条规则，单次深拷贝约 0.4 毫秒，毫无感知。三个月后规则库涨到 3,200 条、且每条挂着历史命中样本，同一个对象的图规模膨胀到约 47 万个节点，单次深拷贝升到 310 毫秒，P99 延迟从 45 毫秒涨到 620 毫秒，进程常驻内存也因为峰值期的副本翻倍而从 1.2 GB 冲到 2.9 GB，触发了两次 OOM 重启。修法不是优化深拷贝，而是把规则库改成加载后不再修改的不可变结构、只对每请求真正会写的那个小字典做浅拷贝；改完单次开销降到 0.02 毫秒以下。

deepcopy 的代价是「整张对象图的规模」，不是「你关心的那几个字段」。当你想深拷贝一个大对象时，先问问能不能改成不可变，或者干脆按需重建一个小的。

五、可变性作为设计选择：如何从根上避免这类 bug

前面几节都在讲「怎么发现和怎么补救」，但共享状态的 bug 有个特点：补救永远是逐点的，漏一处就还会出。真正一劳永逸的做法是在设计层面减少「可以被别人改的可变对象」的数量，让这类 bug 没有生长的土壤。

不可变优先

需要一组常量时用元组而不是列表，需要一组不重复的常量时用 frozenset 而不是 set，需要一个只承载数据的值对象时给 dataclass 加上 frozen=True（它会让实例的属性赋值直接抛 FrozenInstanceError，同时自动生成 __hash__，于是这个对象能当字典键用）。这类选择的代价几乎为零，收益是整整一类 bug 的消失：不可变对象可以被放心地共享、缓存、当默认值、跨线程传递，因为没有任何人能改它。dataclass 的完整用法在后续讲类与数据建模的卡片里展开，这里只需要先形成「默认加 frozen，确实需要改再去掉」的直觉。

边界处的防御性拷贝

防御性拷贝指的是在模块或类的入口、出口处主动拷一份，不让外部对象和内部状态产生引用关系。它有两个方向，而且必须成对考虑：进来时拷——构造函数收到一个列表就 self._items = list(items)，这样调用方后续改他手上那个列表不会影响你；出去时拷——getter 返回 self._items.copy()，这样调用方改不到你的内部状态。只做一个方向等于没做，因为漏掉的那一侧仍然能建立引用通路。

出去的方向还有个更轻的选择：返回只读视图，也就是一个不复制底层数据、但禁止写操作的包装对象。标准库的 types.MappingProxyType 就是字典的只读视图，它的读取是零拷贝的，任何写操作抛 TypeError。列表没有等价的标准包装，常见做法是转成元组。

from types import MappingProxyType

class Config:
    def __init__(self, data: dict):
        self._data = dict(data)              # 进来时拷一份
    @property
    def data(self):
        return MappingProxyType(self._data)  # 出去给只读视图

Config({"retry": 3}).data["retry"] = 9       # TypeError: 不支持赋值

要注意 MappingProxyType 只锁住最外层这一层：如果字典的值是列表，调用方照样能 cfg.data["hosts"].append(...)。它和浅拷贝是同一个层级的保护，想彻底封住嵌套结构，还是得让内层也是不可变的。

明确所有权约定

第三条路不写任何代码，只定规矩：每个可变对象都有一个明确的所有者，只有所有者能改它，其他模块拿到的一律视为只读。约定通常表达为命名规范（下划线前缀）、类型注解（用 Sequence 而非 List 声明只读入参、用 Mapping 而非 Dict）、以及文档里一句明确的「本方法返回的对象请勿修改」。它的优点是零运行时开销，缺点是靠人守——所以它适合团队内部约束，不适合对外暴露的公共 API。

取舍维度防御性拷贝不可变设计所有权约定
运行时开销每次穿越边界都有拷贝成本零，反而省掉拷贝零
安全强度强，但漏一处边界就破最强，语言层面拦住弱，完全靠自觉
改造成本低，局部加几行即可高，要改数据结构和写法最低，只改文档与命名
出错时的表现静默——串状态但不报错立即抛 TypeError 等静默，且难追责
最适合已有可变代码的边界加固配置、常量、值对象、跨线程共享同团队内部的模块间协作
不适合大对象（拷贝太贵）本身就要频繁原地增删的结构对外公开的 API、跨团队协作

三条路的优先级是：能改成不可变就改成不可变，改不动就在边界处拷一份，两者都做不到才退到「靠约定」。约定是最后一道防线，不是第一选择。

六、排查手册：怀疑共享状态时怎么定位

共享状态的 bug 有一套相当独特的指纹，认出它能省掉大量无方向的排查。核心特征是：它不是随机的，是累积的。同一个输入第一次调用完全正常，第十次开始不对，第一百次错得更厉害——因为那个被共享的对象在每次调用里都被追加了一点脏数据。

症状为什么指向共享状态下一步验证
bug 随调用次数递增、错误量越来越大某个对象跨调用累积，没被重置连续调用 5 次，打印可疑容器的长度看是否单调增长
只在长跑进程（服务、worker）里出现短命进程每次重新初始化，掩盖了共享在同一进程里循环调用，而不是反复重启脚本
重启就好，好几个小时又复发进程内状态被污染，重启清空了它别急着重启，先 dump 出可疑对象的 id() 和内容
单元测试全绿，生产必炸测试每个用例新建对象，生产是同一对象反复用写一个「同一对象连续调用 N 次」的测试
两个本该无关的对象内容同步变化典型的别名或类属性共享a.x is b.x 直接判一下
改成 = 赋值就好、改回 append 就坏赋值创建了新对象/实例属性，原地修改动的是共享的那个对比两种写法前后的 id()

定位手法：让共享关系显形

所有手法都围绕同一件事——把「是不是同一个对象」从猜测变成观测。id() 返回对象在当前进程里的唯一标识（CPython 上就是内存地址），is 比较的正是它。注意 id() 只在对象存活期间唯一，对象被回收后数值可能被复用，所以要在同一时刻对比，不要跨时间点存下来比。

怀疑共享状态时的三步定位法 第一步：确认「是不是同一个对象」 ───────────────────────────── print(a is b, a[0] is b[0]) ← 外层、内层分别判 print(len({id(x) for x in rows})) ← 一批容器里到底有几个不同对象 若去重后个数 < 实际元素个数 → 存在共享 第二步：找出「谁在改它」 ───────────────────────────── 在可疑对象的生命周期各关键点打同一格式的日志： print(f"[after_load] id={id(ctx.items)} len={len(ctx.items)}") print(f"[after_calc] id={id(ctx.items)} len={len(ctx.items)}") id 不变而 len 一直涨 → 同一对象在被反复原地追加 id 每次都变 → 每轮新建，问题不在这里 第三步：用隔离验证因果 ───────────────────────────── 在怀疑点插入一次 copy / deepcopy，现象消失 → 确诊共享 注意：这只是「诊断手段」，不是最终修法 确诊后回到第三节四类成因，去掉那个「只创建一次」的对象

第三步里那句提醒很重要。插一个 deepcopy 让现象消失，很容易被当成修复完成，但这只是把症状盖住了：真正的问题是某处存在不该有的共享，而深拷贝在热路径上还会带来第四节说的性能代价。确诊之后应该回到成因本身——把 * 换成推导式、把类属性挪进 __init__、把裸返回改成拷贝或只读视图。

为什么测试抓不住这类 bug

这是本节最值得记住的一条。典型的单元测试长这样：每个用例在 setUp 里新建一个对象，调用一次，断言结果，然后对象被丢弃。这个流程恰好绕过了共享状态的触发条件——共享要靠「同一个对象被反复使用」才显形，而测试每次都给你一个全新的。生产环境则相反：一个服务实例可能在进程里存活数天，同一个类属性、同一个模块级字典被调用几百万次。

补救办法是针对性地写「有状态测试」：在一个用例里对同一个对象连续调用同一个方法 3 到 5 次，断言第 N 次的结果和第 1 次一致；或者直接断言对象图里不存在意外共享，例如前面用过的 len({id(v) for v in mapping.values()}) == len(mapping)。这类断言写起来只有一两行，却能在改动引入共享的当天就报警。异常与边界情况的测试思路可以参考 PY07 · 文件读写与异常处理 里的做法。

  • 造多维结构一律用推导式：[[0] * 3 for _ in range(3)]
  • 可变的实例状态只在 __init__ 里建，类属性只放常量
  • getter 返回 self._items.copy() 或 MappingProxyType 只读视图
  • 构造函数收到外部容器时 self._x = list(x) 拷一份再存
  • 常量用 tuple / frozenset，值对象用 frozen=True 的 dataclass
  • 写「同一对象连续调用 N 次」的有状态测试，断言结果不漂移
  • 怀疑共享时先用 is / id() 观测，再动手改
  • 用 [[]] * n 或 dict.fromkeys(ks, []) 初始化可变结构
  • 用 == 判断有没有拷贝——三种层次下它都返回 True
  • 在热路径上无条件 deepcopy 大对象「图个安心」
  • 对持有连接、句柄、锁的对象做 deepcopy
  • 只在入口或只在出口做防御性拷贝，漏掉另一侧
  • 插一个 deepcopy 让现象消失就结案，不追成因
  • 指望「记得别改这个对象」这种口头约定挡住跨团队调用

看到「越跑越错、重启就好、单测全绿」这三件事同时出现，几乎可以直接按共享状态立案。第一个动作不是改代码，是打一串 id() 看看到底有几个对象。

Q&A

b = a 和 b = a.copy() 到底差在哪？什么时候必须用 deepcopy？
b = a 没有创建任何新对象，只是让 b 这个名字也指向 a 指向的那个对象，之后对 b 的任何原地修改都会在 a 上看到，b is a 为真。b = a.copy() 创建了一个新的外层容器，把原容器里的元素引用逐个抄进去，所以增删 b 的元素不影响 a，但 b[0] is a[0] 仍然为真——内层对象是共享的。判断要不要 deepcopy 的标准很简单：容器里是否存在可变元素，以及你是否会去原地修改它们。如果容器里全是数字、字符串、元组这类不可变对象，浅拷贝就已经完全够用；只有当嵌套层里有列表、字典、自定义可变对象，并且你会去改它们时，才需要深拷贝。
为什么 [[0] * 3] * 3 改一个格子会整列一起变？
因为这里的两个 * 复制的东西不同。内层 [0] * 3 复制的是整数 0，整数不可变，共享它没有任何可观测后果。外层的 * 3 复制的是「内层那个列表对象的引用」，它不会帮你把列表内容再造两份，所以外层列表的三个槽位指向的是同一个对象。你写 grid[0][1] = 9 时，改的是那唯一一个内层列表，通过另外两个槽位看过去自然也变了。正确做法是用列表推导式 [[0] * 3 for _ in range(3)]，循环体每一轮都会重新执行 [0] * 3，于是得到三个独立对象。想验证只需一行：len({id(row) for row in grid}) 应该等于行数。
类属性写成可变对象为什么危险？为什么有时候又看不出问题？
写在 class 语句体里的 items = [] 在类定义时执行一次，这个列表归类所有，所有实例通过 self.items 访问到的都是它，于是任何一个实例的 append 都会被其他实例看到。之所以有时看不出问题，是因为读取操作完全正常，只有原地修改才会串；更迷惑的是 self.items = [] 这种重新赋值会在实例上创建一个同名的实例属性，把类属性遮蔽掉，此后这个实例就不再共享了。结果同一段代码里用 append 会串、用 = 不会串，现象时有时无，很容易被误判为偶发问题。规则很清晰：类属性只放不可变的常量，一切可变的实例状态都在 __init__ 里创建。
deepcopy 为什么有时特别慢，有时还直接报错？
慢的原因是它的代价取决于对象图的节点总数，而不是你关心的字段数。deepcopy 会递归访问对象的每个属性、容器的每个元素，每个节点都要查一次备忘表、新建一份副本并登记，所以一个挂着几十万个小对象的实例，深拷贝就要走几十万次这个流程，耗时和内存都会按规模线性上涨，内存峰值接近翻倍。报错则是因为它不区分业务语义，会把数据库连接、文件句柄、线程锁这类不该复制的资源也拖进递归，其中很多对象明确拒绝被复制，于是抛出类似 TypeError: cannot pickle '_thread.lock' object 的错误。更危险的情况是不报错——你得到一个持有失效句柄的副本，问题延迟到真正使用时才暴露。需要精细控制时可以实现 __deepcopy__，声明哪些字段共享、哪些递归拷贝。
copy.copy、list(x)、x[:]、x.copy() 有区别吗？
对列表来说这四种写法在语义上完全等价，都是浅拷贝：新建一个列表对象，把原列表的元素引用逐个抄进去，只拷一层。区别只在可读性和适用范围。x.copy() 最推荐，意图直接写在方法名上，dict 和 set 也有同名方法。list(x) 的特点是接受任意可迭代对象，所以适合需要顺便转换类型的场景，比如把生成器或元组收成列表。x[:] 在老代码里很常见，但对不熟悉切片的人不够直观，新代码没必要用。copy.copy(x) 是通用入口，会走对象的 __copy__ 协议，适合类型不确定或者要拷自定义类实例的情况。需要强调的是，它们之中没有哪一个「拷得更深一点」，叠加使用也不会变深。
元组不可变，是不是就完全安全了？tuple(t) is t 为什么是真？
元组的不可变指的是它的槽位不可变——你不能给已有位置重新赋值，也不能增删元素。既然内容无法改变，「独立副本」这个需求就不存在了，所以 Python 直接优化成返回原对象，tuple(t) is t 和 copy.copy(t) is t 都为真，frozenset、字符串、数字同理。但安全性只到这一层：t = ([1, 2], "x") 里那个列表照样可以被 append，而且因为拷贝元组拿回的是原对象，你连「拷一份来隔离」这条路都被堵住了，只能用 deepcopy 或者一开始就不要往元组里放可变对象。所以「用元组做常量就安全」这个说法有个前提：元组里装的必须全是不可变对象。这也是为什么不可变设计要一路贯彻到底，只做最外层等于没做。
防御性拷贝和不可变设计该选哪个？
优先选不可变设计，因为它是语言层面的保障：常量用元组或 frozenset、值对象用 frozen=True 的 dataclass，一旦有人试图修改会立刻抛异常，而不是静默地污染状态。它还顺带省掉了所有拷贝开销，可以放心共享、缓存、跨线程传递。防御性拷贝适合两类情况：改造已有的可变代码，在类或模块的边界上局部加几行；以及对象本身确实需要频繁原地增删，无法改成不可变。用防御性拷贝时务必两个方向都做——进来时 self._x = list(x)，出去时返回 copy() 或只读视图，只做一侧等于没做。至于所有权约定，它零开销但完全靠自觉，适合团队内部模块协作，不适合对外公开的 API。
共享状态的 bug 为什么单元测试测不出来？该怎么补测试？
因为典型的单元测试恰好绕过了触发条件。测试通常每个用例都新建一个对象、调用一次、断言、丢弃，而共享状态要靠「同一个对象被反复使用」才会显形。生产环境正好相反：一个服务实例可能在进程里活好几天，同一个类属性、同一个模块级字典被调用几百万次，脏数据就在这几百万次里一点点累积。补测试的办法有两种，都很便宜。一是写有状态测试：在一个用例里对同一个对象连续调用同一方法三到五次，断言第 N 次的结果与第一次一致。二是直接断言不存在意外共享，比如 len({id(v) for v in mapping.values()}) == len(mapping)，或者 a.items is not b.items。这类断言只有一两行，却能在有人不小心引入共享的当天就报警。
