PY17 · 描述符协议与 property

属性访问的完整解析路径 / property 的演化友好性 / 数据与非数据描述符的优先级 / __set_name__ 与存储位置 / __getattr__ 的代价

读一个属性看起来是全语言最廉价的操作，但 Python 在这条路径上留了好几个可以插手的口子。把「谁有权拦截、谁的优先级更高」这一条链搞清楚，方法为什么自动带 self、property 为什么不能被实例属性覆盖、ORM 字段为什么能校验，就全是同一件事的三个侧面。

一、属性访问是可以被拦截的

到目前为止我们一直把属性当成一个存取动作：obj.x 去 obj.__dict__ 里取，obj.x = 1 往里面塞。对普通数据来说这个模型够用，但它解释不了一件每天都在发生的事——你写 def greet(self)，调用时却写成 obj.greet()，那个 self 是谁塞进去的？

答案是：属性查找不是一次字典命中，而是一段有分支的流程。Python 在沿着类的 MRO 找到某个类属性之后，会先检查这个对象有没有实现特定的几个方法；实现了，就不返回它本身，而是转去调用那几个方法。这套约定就是 描述符协议——一个对象只要定义了 __get__、__set__、__delete__ 中的任意一个，它作为类属性被访问时就会接管访问过程。

这条机制的覆盖面比大多数人预期的广。绑定方法（调用 obj.f 得到的那个自动携带实例的可调用对象）就是函数这个非数据描述符 __get__ 的返回值；classmethod、staticmethod、property、__slots__ 的槽位、functools.cached_property，全部建立在同一套协议上。换句话说，你从 PY15 起用过的每一个「类上的东西」几乎都走过这条路。

描述符不是一个高级技巧，而是 Python 属性系统的底座。你不是在「学一个新特性」，而是在给已经用了十几节课的东西补上原理。

第 2 步和第 3 步的先后顺序是全篇最重要的一条信息，第三节会专门展开。这里先记住结论：类上的某些东西可以压过实例自己的 __dict__，这在「实例属性优先于类属性」的朴素模型里是不存在的。

为什么方法能自动拿到 self

函数对象实现了 __get__，所以它是描述符。通过实例访问时，__get__ 收到实例并返回一个把实例预先塞进第一个参数的包装对象，这就是绑定方法。这件事可以直接验证：

class Foo:
    def bar(self): ...

f = Foo()
Foo.bar                     # <function Foo.bar at 0x...>
f.bar                       # <bound method Foo.bar of <Foo object>>
Foo.bar.__get__(f, Foo)     # 同样得到 bound method
# 也就是说：f.bar 等价于 Foo.__dict__['bar'].__get__(f, Foo)

最后那行注释值得停一下。方法调用的「魔法」被完全拆解成了一次普通的描述符调用，没有任何专门为函数开的后门。这也是为什么 classmethod 和 staticmethod 能用纯 Python 实现——它们只是换了一种 __get__ 的返回策略。

二、property：最常用的描述符

绝大多数人第一次用到描述符协议，是通过 property。它做的事一句话能说清：把一个托管属性（外部看起来是属性、内部实际执行方法的接口）挂到类上，读的时候调 getter，写的时候调 setter，删的时候调 deleter。

它真正的价值不在「能加校验」，而在加校验的时机可以推迟。你可以第一版就写最朴素的 self.age = age，等到真的需要限制取值范围、需要记录变更、需要从别处惰性拉取时，再把它换成 property——所有调用方的代码一行都不用改。这在很多语言里要靠「一开始就全部写成 getter/setter」来换取，Python 把这个成本推迟到了真正需要的那一刻。

同一段调用方代码：user.age = 30 / print(user.age) v1 裸属性 class User: def __init__(self, age): self.age = age 读写直接落在 user.__dict__['age'] v2 需求变了：年龄不能为负 —— 改成 property class User: @property def age(self): return self._age @age.setter def age(self, v): if v < 0: raise ValueError('age must be >= 0') self._age = v ─────────────────────────────────────────────────────── 调用方视角 user.age = 30 print(user.age) v1 写进 __dict__ 读出 __dict__ v2 走 setter 校验 走 getter 返回 ─────────────────────────────────────────────────────── 调用方需要改动的代码行数：0

property 的意义是「保留反悔的权利」。先按最简单的属性发布出去，等需求真的来了再换实现，而不是为了可能不会发生的需求提前把每个字段都包成方法。

三个装饰器与只读属性

写法上只有三件事：@property 定义读取，@x.setter 定义写入，@x.deleter 定义删除。注意后两个装饰器的名字必须是前面那个 property 的名字，因为 setter 是在已有的 property 对象上调用的，它返回一个补齐了 setter 的新 property。

class Temperature:
    @property
    def celsius(self):
        return self._c
    @celsius.setter
    def celsius(self, v):
        if v < -273.15:
            raise ValueError(f"低于绝对零度: {v}")
        self._c = v

只定义 getter 就得到只读属性。此时对它赋值不会静默落进 __dict__，而是抛 AttributeError: property 'celsius' of 'Temperature' object has no setter（3.11 起的报错文案，之前版本是 can't set attribute）。这个行为正是数据描述符优先级的直接后果：property 同时实现了 __set__，即便没有 setter 函数，它也会接管赋值并主动报错——所以「类上的 property 被实例属性偷偷覆盖」这件事不会发生。

最常见的误用：让读属性变得很贵

property 的语法糖同时是它最大的风险：调用方看到的是 order.customer_name，从字面上完全看不出这次读取要走网络、要查库、要解压一个大文件。人在读代码时会本能地认为属性访问是 O(1) 且无副作用的，于是会毫无顾虑地把它放进循环、放进日志、放进模板。

示例场景：某订单列表页把 order.customer_name 做成 property，getter 里执行一次按 id 查客户表的查询。一页 50 条订单，模板中该属性被引用了 3 次（标题、悬浮提示、导出按钮的 title），单次页面渲染因此产生 50 × 3 = 150 次数据库往返，P95 渲染耗时从 80 ms 涨到 2.4 s。修复没有改调用方：在 getter 外层加了一次批量预取，并把 property 内部换成读预取结果，150 次查询降为 1 次，P95 回到 95 ms。

这个案例的教训不是「不要用 property」，而是给它划一条线：getter 应该廉价、幂等、无副作用。一旦某次读取可能失败、可能很慢、可能改变对象状态，就应该写成显式的方法名（fetch_customer()、reload()），让调用方在字面上看见代价。

表格倒数第二行指出了 property 的天花板：它是按字段写死的。三个字段都要做「非负整数校验」，就得把同样的 if 写三遍；换成十个类、每个类五个字段，这份重复会变得无法维护。这正是下一节要引入完整描述符协议的原因。

三、三个协议方法与两种描述符

协议本身只有三个方法，签名固定：

方法签名何时被调用返回/作用
__get__(self, obj, objtype=None)读取 obj.x 或 Cls.x 时返回真正要给出去的值；通过类访问时 obj 是 None
__set__(self, obj, value)执行 obj.x = value 时负责把值存到某处，没有返回值
__delete__(self, obj)执行 del obj.x 时负责清理存储，没有返回值

注意 self 是描述符实例自己，obj 才是被访问的那个对象。这两个名字在描述符代码里极易搞混，而搞混的直接后果就是第四节要讲的那个经典事故。

数据描述符与非数据描述符

按实现了哪几个方法，描述符分成两类，这个分类不是学术划分，它直接决定优先级：

  • 数据描述符：实现了 __get__，并且实现了 __set__ 或 __delete__ 中至少一个。它优先于实例 __dict__。
  • 非数据描述符：只实现了 __get__。它低于实例 __dict__，会被同名的实例属性遮蔽。
查找 obj.x 时的优先级（从高到低） ────────────────────────────────── ① 数据描述符 类上的 x 有 __get__ 且有 __set__ / __delete__ │ 代表：property、__slots__ 槽位、ORM 字段 │ ★ 压过实例 __dict__，实例属性挡不住它 ▼ ② 实例 __dict__ obj.__dict__['x'] │ 所有普通的 self.x = ... 都落在这一层 ▼ ③ 非数据描述符 类上的 x 只有 __get__ │ 代表：函数、classmethod、staticmethod、cached_property │ ★ 被实例 __dict__ 压过，可以被同名实例属性遮蔽 ▼ ④ 普通类属性 类上的 x 不是描述符，如 LIMIT = 100 ▼ ⑤ __getattr__ 以上全部失败后的兜底钩子（定义了才有这一层） ▼ raise AttributeError 两条可以马上验证的后果 o.some_property = 1 → 走 property.__set__，没有 setter 就抛 AttributeError o.some_method = 1 → 落进实例 __dict__，此后 o.some_method() 调的是你塞进去的东西 类本身毫发无伤，其他实例不受影响
class NonData:                       # 只有 __get__ → 非数据描述符
    def __get__(self, obj, owner): return "来自描述符"

class Data(NonData):                 # 补上 __set__ → 升级为数据描述符
    def __set__(self, obj, value): raise AttributeError("只读字段")

class C:
    a = NonData()                    # c.__dict__['a'] 能遮蔽它
    b = Data()                       # c.__dict__['b'] 压不过它

上面这段里 Data 只比 NonData 多了一个方法，行为却发生了质变：c.a = 1 之后再读 c.a 得到 1，描述符被彻底旁路；而 c.b = 1 直接抛出 AttributeError: 只读字段，连写入的机会都没有。

类上的 x有 __get__有 __set__/__delete__类型与实例 __dict__ 的关系典型例子
property 对象是是数据描述符压过 __dict__，赋值必被拦截@property
自定义校验字段是是数据描述符同上ORM 的 IntegerField
普通函数是否非数据描述符被 __dict__ 压过，可遮蔽类里的 def f(self)
cached_property是否非数据描述符主动写 __dict__ 让自己被绕开functools.cached_property
普通类变量否否不是描述符被 __dict__ 压过MAX_RETRY = 3

「谁能压过实例字典」这一问的答案，只取决于类属性有没有实现 __set__ 或 __delete__。一个方法的加与不加，决定了这个字段是「可以被实例随手覆盖的建议」还是「实例绕不过去的规则」。

顺带解释一个从 PY15、PY16 遗留下来的现象：给实例打补丁（monkey patch）时，直接写 obj.method = new_func 能成功但不会自动传 self——因为你塞进 __dict__ 的是一个裸函数，第 3 步命中就返回了，根本没走第 4 步的 __get__，自然没人给它绑定实例。

四、__set_name__ 与数据该存在哪

写一个自定义描述符时，马上会撞上两个实际问题：描述符实例被赋给了哪个属性名，它自己并不知道；以及，__set__ 收到的值到底该存到什么地方。这两个问题的答案是连在一起的。

描述符怎么知道自己叫什么

写 balance = Money() 时，Money() 这个实例被创建的那一刻，赋值还没发生，它拿不到 'balance' 这个名字。Python 3.6 以前只能手动传（Money('balance')，名字写错就是一个静默 bug）或者上元类。3.6 起类创建过程会在类体执行完之后，自动对类命名空间里每个实现了 __set_name__ 的对象调用一次 __set_name__(owner, name)，把宿主类和属性名送过来。

这个改动看着不起眼，它才是描述符从「需要元类配合的小众技巧」变成「日常可写」的分水岭。

class Field:
    def __set_name__(self, owner, name):
        self.name = name                     # 类创建时自动调用，name = 'balance'
    def __get__(self, obj, owner=None):
        if obj is None: return self          # 通过类访问时返回描述符本身
        return obj.__dict__[self.name]
    def __set__(self, obj, value):
        obj.__dict__[self.name] = value      # 存进「实例」，不是存进 self

这里有个容易疑惑的点：值存进了 obj.__dict__['balance']，而类上也有个 balance，读取时不会被实例字典先命中吗？不会——Field 实现了 __set__，是数据描述符，它排在实例 __dict__ 前面，所以 __get__ 始终有机会执行，再由它主动去实例字典里把值捞出来。这正是把优先级规则用对了的写法。

存错地方是这一节最经典的 bug

类空间（全类只有一份） 实例空间（每个实例各一份） ───────────────────── ──────────────────────────── class Account: a1 = Account() balance = Money() a1.__dict__ = {'balance': 100} │ ▲ │ 一个 Money 实例 │ ✓ 正确：值存在这里 │ 被所有 Account 实例共用 │ │ a2 = Account() │ a2.__dict__ = {'balance': 250} ▼ ▲ Money 实例自己的 __dict__ │ {'name': 'balance'} ← __set_name__ 写进来的名字 │ （只放「这个字段叫什么」这类 ┌────────┘ 与具体实例无关的元信息） │ │ ✗ 错误写法：在 __set__ 里写 self.value = value 值落进了上面那个共用的 Money 实例 → a1.balance = 100 之后 a2.balance = 250 再读 a1.balance 得到 250，而不是 100

这个 bug 的可怕之处在于它在单实例场景下完全正常。你写完描述符，建一个对象，测一遍读写，全对；单元测试里往往也只造一个对象。问题只在同时存在两个以上实例时才浮现，而那通常是上线之后。

示例场景：某服务用自定义描述符给用户对象的 6 个金额字段做统一校验，值被误存进了描述符实例自身。开发期的 12 个单元测试每个只构造 1 个用户对象，全部通过；灰度 1 天也没问题，因为压测脚本复用同一个对象。全量上线后 18 分钟出现首个投诉：并发请求下同一进程内的多个用户对象共用同一个描述符实例，A 用户页面显示出了 B 用户的余额。回滚耗时 40 分钟，修复代码只有一行——把 self.value = value 改成 obj.__dict__[self.name] = value。

存储位置写法结论说明
描述符实例自身self.value = value✗ 几乎总是错的描述符是类属性，全类一份，所有实例共享同一个值
实例 __dict__，同名键obj.__dict__[self.name] = value✓ 默认选这个数据描述符压过 __dict__，不会被短路；名字由 __set_name__ 提供
实例 __dict__，加前缀obj.__dict__['_' + self.name]✓ 也可以调试时 vars(obj) 里能一眼看出哪些是描述符管的
描述符内部字典，以 id(obj) 为键self._store[id(obj)] = value✗ 不要用对象销毁后条目不会清理，且 id 会被复用，导致串值
WeakKeyDictionaryself._store[obj] = value△ 有条件可用能自动回收，但要求实例可哈希且可被弱引用，__slots__ 类要额外声明

描述符实例住在类上，用户数据必须住在实例上。判断标准很简单：这份数据换一个实例还成不成立？成立（字段名、校验范围）就放描述符里，不成立（余额、年龄）就必须放实例 __dict__。

另外记住 __set_name__ 有它的边界：它只在类体执行时被自动触发。类创建完之后再补一句 Account.extra = Money()，这个描述符的 __set_name__ 不会被调用，self.name 也就不存在，第一次读写时会抛 AttributeError: 'Money' object has no attribute 'name'。遇到这种情况需要手动调用一次 Money().__set_name__(Account, 'extra')。

五、另一条拦截路径：__getattr__ 与 __getattribute__

描述符是在类属性层面拦截，粒度是单个字段。还有一条完全不同的路径是在对象层面拦截，一次覆盖所有属性。这条路径上有三个钩子，它们的触发时机和代价差距非常大，混用是新手最容易写出无限递归的地方。

读 obj.x 时，两个读钩子的位置完全不同 ──────────────────────────────────── obj.x │ ▼ __getattribute__ ← 每一次属性读取都会进来，无论成败 │ 重写它 = 给全对象所有属性访问加一层开销 │ 方法体里写 self.foo 会再次触发它 → 无限递归 │ 必须改写成 super().__getattribute__('foo') │ ├─ 默认流程：数据描述符 → 实例 __dict__ → 非数据描述符 → 类属性 │ └─ 命中 ──► 返回值，__getattr__ 这辈子都不会被调用 │ └─ 抛出 AttributeError │ ▼ __getattr__ ← 只有这条失败分支才会进来 代理转发、惰性加载、友好报错都写在这 正常存在的属性一次都不会经过它 规模感（某对象一次请求内被读 100 万次属性，其中 3 次是不存在的名字） __getattribute__ 被调用 1 000 000 次 __getattr__ 被调用 3 次

__getattribute__：能力最大，代价也最大

它是所有属性读取的总入口，连 self.__dict__ 这种访问本身也要经过它。所以下面这段是必踩的坑：

class Bad:
    def __getattribute__(self, name):
        return self.__dict__[name]   # self.__dict__ 又触发 __getattribute__
# 结果：RecursionError: maximum recursion depth exceeded

class Good:
    def __getattribute__(self, name):
        return super().__getattribute__(name)   # 转发给默认实现，不再递归

规则很硬：在 __getattribute__ 内部，任何对 self 属性的普通访问都会再次进入自己。唯一安全的做法是走 super().__getattribute__(name) 或 object.__getattribute__(self, name)。同理，在 __setattr__ 内部要用 object.__setattr__(self, name, value)，直接写 self.x = ... 同样会自我递归。

示例场景：某配置对象重写了 __getattribute__，在里面做键名归一化（把 - 换成 _、统一小写）。功能完全正确，但这个对象在请求处理的热路径上，压测时每秒发生约 1200 万次属性读取，CPU profile 显示 31% 的时间消耗在这个方法里，QPS 从 4800 掉到 3100。改法是把归一化逻辑从 __getattribute__ 挪到 __getattr__：正常拼写的键走默认路径零开销，只有归一化前匹配不上的名字才进钩子。改完后该方法在 profile 中占比 0.4%，QPS 回到 4700。

__getattr__：便宜的兜底钩子

因为只在查找失败后才触发，它几乎不产生常规开销，是实现代理对象（把属性访问原样转发给被包装对象的壳）和惰性加载的首选。

class Proxy:
    def __init__(self, target):
        object.__setattr__(self, "_target", target)   # 绕开自定义 __setattr__
    def __getattr__(self, name):                      # 常规查找失败才进来
        return getattr(self._target, name)
    def __setattr__(self, name, value):               # 所有赋值都会进来
        setattr(self._target, name, value)

还有一个常被忽略的用途：给库写友好报错。默认的 AttributeError: 'Config' object has no attribute 'tiemout' 什么线索都没给，而在 __getattr__ 里做一次近似匹配，就能抛出 AttributeError: 'Config' 没有 'tiemout'，你是不是想写 'timeout'？。代价是零——这个分支只在真的写错时才执行。

钩子触发时机被调用频率典型用途主要风险
__getattribute__每一次属性读取，成功失败都进极高全局审计、访问日志、强制只读对象递归 + 全局性能损耗，非必要不要重写
__getattr__常规查找失败后极低代理转发、惰性加载、拼写纠错、动态字段会吞掉内部真实的 AttributeError，掩盖 bug
__setattr__每一次属性赋值与写入次数相同不可变对象、变更追踪、字段白名单内部必须用 object.__setattr__，否则递归
__delattr__每一次 del obj.x很低禁止删除关键字段同上，内部要转发给默认实现
描述符 __get__/__set__只在被托管的那个字段上按字段计字段级校验、类型转换、单位换算存储位置写错会导致实例间串值

表格第二行那个「吞掉真实异常」的风险值得展开。如果 __getattr__ 里访问了一个真的不存在的内部属性，Python 会再次调用 __getattr__，很容易变成递归或者把一个本该报出来的拼写错误伪装成「找不到属性」。稳妥的写法是在 __getattr__ 开头拦掉下划线开头的名字，直接 raise AttributeError(name)，不让内部属性掉进转发逻辑。

需要「兜底」就写 __getattr__，需要「全拦」才动 __getattribute__。两者名字只差几个字母，代价差了六个数量级——绝大多数场景你要的都是前者。

六、该用，还是过度设计

描述符的能力很强，但它同时是这门语言里对读者最不友好的机制之一：代码跳转会停在一个看不出用途的类上，报错栈里多出几层，类型检查器经常推断不出 obj.x 到底是什么类型。所以真正的问题不是「会不会写」，而是「值不值得写」。

判断标准只有一条：复用的规模

描述符的收益来自复用。同一套属性逻辑要落在多个类的多个字段上时，它把重复的 if 收敛成一个可测试的小类；只有一两个字段时，这份收敛毫无意义，property 更直白。

方案什么时候选它什么时候别选主要代价
裸属性纯数据、没有任何约束有校验、有计算、需要只读约束只能写在文档里，靠自觉

这张表里最容易被跳过的是后两行。很多人写描述符，本质需求是「声明式地定义一批带约束的字段」——那是 dataclass 和 pydantic 已经解决过的问题，它们内部同样用描述符实现，但把复杂度封在库里，还顺带提供了序列化、默认值、错误聚合。数据类与类型注解那一组（PY21）会专门展开这条路线。自己手写描述符的合理场景，是需求刚好落在这些库的能力之外，比如带单位换算的物理量字段、或者要接一套自有的权限模型。

在写下第一个 __get__ 之前先数一遍：这套逻辑到底会被多少个字段复用？答案小于 3 就写 property，答案是「一批字段的声明」就去用 dataclass 或 pydantic，剩下的情况才轮到自己写描述符。

写之前和写之后的检查清单

  • 先用 property，等重复出现三次以上再抽成描述符
  • 描述符的值一律存进 obj.__dict__，键名由 __set_name__ 提供
  • __get__ 里判断 obj is None 并返回 self，保证通过类访问时不炸
  • getter 保持廉价、幂等、无副作用；昂贵操作写成有括号的方法名
  • 需要兜底转发时优先用 __getattr__，把热路径留给默认实现
  • 在 __getattribute__ / __setattr__ 内部一律走 super() 或 object. 转发
  • 给描述符写单测时至少构造两个实例，交叉读写验证互不干扰
  • 在 __set__ 里写 self.value = value——所有实例会共享同一个值
  • 在 property 的 getter 里查数据库、发网络请求或修改对象状态
  • 为了「以后可能要加校验」把每个字段都提前包成 property
  • 重写 __getattribute__ 去做本可以在 __getattr__ 里做的兜底
  • 在 __getattribute__ 内部直接写 self.xxx 或 self.__dict__
  • 用 id(obj) 当键把值存进描述符内部的普通 dict
  • 需求其实是「一批带约束的字段」时还坚持手写描述符，而不用 dataclass / pydantic

最后回到起点。这一节讲的所有东西——property、描述符、__getattr__——都是同一个问题的不同粒度的答案：属性访问这条路径上，你想在哪一层插手。单个字段用描述符，整个对象用 __getattr__，不需要插手就什么都别写。能把这三者的适用边界说清楚，比能默写协议方法签名有用得多。

Q&A

什么时候应该一开始就把字段写成 property，而不是先用裸属性？
判断依据是这个字段有没有必须在写入那一刻就成立的约束。如果赋一个非法值会让对象进入不可用状态、并且错误会在很久以后的另一处代码里才暴露出来，那就值得从第一版开始用 property 拦住，让报错发生在赋值现场。典型例子是取值范围（年龄、百分比）、互相关联的字段（结束时间必须晚于开始时间）、以及需要归一化的输入（路径、URL）。反过来，如果字段只是纯数据搬运，没有任何约束，提前包成 property 只会增加噪音——Python 的价值恰恰在于你可以之后再改而不影响调用方。还有一个信号：如果这个类会被外部依赖、发布出去后接口不好改，那么提前用 property 的性价比会更高一些。
为什么给实例赋一个和 property 同名的属性会报错，而给方法同名赋值却能成功？
因为两者在属性优先级链上的位置不同。property 同时实现了 __get__ 和 __set__，属于数据描述符，排在实例 __dict__ 前面，所以 obj.x = 1 会被它的 __set__ 接管；如果这个 property 没有定义 setter，__set__ 就直接抛 AttributeError。普通函数只实现了 __get__，属于非数据描述符，排在实例 __dict__ 后面，赋值不会被拦截，值老老实实落进 obj.__dict__，此后读取在第 3 步就命中了，根本走不到函数那一层。这也解释了为什么给实例打补丁得到的是裸函数而不是绑定方法——没有经过 __get__，就没人给它绑 self。要注意这种遮蔽只影响那一个实例，类本身和其他实例都不受影响。
描述符的 __get__ 里，参数 obj 为什么可能是 None？该怎么处理？
当你通过类而不是实例访问时，比如 Account.balance，没有任何实例参与，Python 会用 None 作为 obj 传进来。如果代码里直接写 obj.__dict__[self.name]，这时会抛 AttributeError: 'NoneType' object has no attribute '__dict__'，而且触发场景往往很意外——IDE 的自动补全、help()、文档生成工具、序列化库都会通过类去探查属性。惯例做法是在 __get__ 开头写 if obj is None: return self，把描述符实例本身返回出去。这样调用方既能拿到元信息（比如字段的校验规则、字段名），也不会崩。property 的实现也是这么做的，所以 SomeClass.some_property 返回的是那个 property 对象而不是报错。
__set_name__ 在什么情况下不会被自动调用？
它只在类对象被创建的那一刻触发，由类的构造过程遍历类命名空间逐个调用。所以类定义完成之后再动态挂上去的描述符不会被通知，比如 Account.extra = Money()，或者用 setattr(Account, 'extra', Money())。这时描述符内部记名字的那个属性根本不存在，第一次读写会抛 AttributeError: 'Money' object has no attribute 'name'，报错信息指向描述符内部，和你刚才那行赋值看不出关系。补救办法是手动补一次调用：desc.__set_name__(Account, 'extra')。另一个不会触发的场景是描述符实例被放进容器里（比如 fields = [Money(), Money()]），因为类命名空间里的那个名字绑定的是列表而不是描述符，Python 不会递归进去找。
在 __getattr__ 里访问 self 的其他属性，会不会像 __getattribute__ 那样无限递归？
通常不会，但存在一类会。__getattr__ 只在常规查找失败后才被调用，所以在它内部访问一个确实存在的属性时，常规查找会成功返回，不会再次进入 __getattr__。危险的是访问一个不存在的属性：那次访问同样失败，于是再次触发 __getattr__，如果逻辑每次都走到同一行，就变成了无限递归，报出 RecursionError。最常见的触发方式是在 __init__ 里还没来得及设置某个内部属性时就有别的代码读它。稳妥做法有两条：在 __getattr__ 开头对下划线开头的名字直接 raise AttributeError(name)，不让内部属性进入转发逻辑；以及用 object.__setattr__ 在 __init__ 最开始就把关键内部属性设好。
functools.cached_property 和普通 property 的关键区别在哪？
最本质的区别是描述符类型不同：property 是数据描述符，cached_property 是非数据描述符。cached_property 首次被读取时执行你的函数，然后把结果直接写进实例的 __dict__，键名就是属性名；由于它是非数据描述符，优先级低于实例 __dict__，之后所有读取都在优先级链的第 2 步就命中缓存，压根不会再进它的 __get__。这也带来两个实际约束：宿主类必须有 __dict__，用了 __slots__ 的类不能用它；而且缓存失效的方式是 del obj.attr，也就是把实例字典里那个键删掉。另外它不支持 setter，需要写入语义就得换回 property。对那个 N+1 查询案例来说，cached_property 能把单对象内的重复读取压成一次，但跨 50 个对象的 50 次查询它解决不了，那仍然需要批量预取。
什么时候应该放弃手写描述符，改用 dataclass 或 pydantic？
当你发现自己真正想要的是「声明式地定义一批字段」而不是「给某类字段定制访问行为」时，就该换了。一个明确信号是描述符类越写越像字段规格说明：带默认值、带类型、带必填标记、还要拼装 __init__ 和 __repr__——这些 dataclass 全部自动生成，不用你写一行。另一个信号是数据来自进程外部（HTTP 请求体、YAML 配置、消息队列），需要的是解析加校验加可读的错误汇总，这正是 pydantic 的主场，它能一次报出所有不合规字段而不是遇到第一个就抛。这两个库内部同样是用描述符和元编程实现的，所以你不是放弃了能力，只是把复杂度交给了经过大量生产验证的代码。手写描述符仍然合理的场景，是需求落在这些库覆盖范围之外，比如带单位换算的物理量字段、接入自有权限模型的受控字段。数据类与类型注解那一组（PY21）会专门讲这条路线怎么选。
描述符和继承、MRO 是怎么配合的？子类能覆盖父类的描述符吗？
能，而且规则和普通类属性完全一致：查找类属性时沿着 MRO 从左到右找第一个命中的名字，找到什么就用什么。所以子类里写一个同名的 property 或描述符，就会把父类的那个完全替换掉，父类版本不会被自动调用。这里有个常见的绊脚石：想在子类里只改 setter、保留父类的 getter，不能写 @x.setter，因为子类作用域里没有那个 x；正确写法是 x = ParentClass.x.setter(new_setter)，在父类的 property 对象上派生一个新的。另一个要注意的点是描述符实例是在定义它的那个类上，__set_name__ 收到的 owner 也是那个类，不是子类；如果描述符逻辑依赖宿主类信息，用 __get__ 里的 type(obj) 才能拿到真实的运行时类型。继承那一节（PY16 · 继承、MRO 与组合优先）讲的查找顺序在这里原样适用。
