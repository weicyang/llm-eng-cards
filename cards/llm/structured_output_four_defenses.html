L13 · 大模型结构化输出：方案谱系与四道防线

五大方案谱系 / 选型决策树 / JSON Schema 约束 / 重试机制 / 输出清洗 / 日志审计 / Schema 设计 / 生产案例

大模型结构化输出的核心矛盾：LLM 本质是概率文本生成器，不是 API 服务器——你不能假设它每次都输出合法的 JSON。解决思路不是"让模型更听话"，而是在模型外面套一层确定性约束与工程化防线：从提示词引导 → API 强制 → 解码层控制逐层递进，可靠性从 85% 提升到 99.9%+。

一、核心困境：五大翻车现场

概率生成模型的本质决定了每一个 token 都是从概率分布中采样。即使同一个输入，不同时刻的输出也可能不同。当业务系统期望 LLM 返回严格的 JSON 结构时，这种概率性与确定性需求产生了根本矛盾。

生产环境的五大翻车现场

翻车类型具体表现下游后果发生概率（无约束）

TokenMix.ai 对 200 万次 API 调用的监控数据显示：无 Schema 约束时，LLM 的 JSON 输出解析失败率在 8-15% 之间。每次失败触发重试，成本翻倍，延迟增加 500-2000ms。1 万次调用中就有 800-1500 次需要额外处理。

问题的本质不在于"模型偶尔不听话"，而在于概率模型的输出不可能 100% 可预测。商业系统需要的不是"大概率正确"，而是"失败可检测、可重试、可降级"——这正是后文四道防线的出发点。

二、五大解决方案：从软引导到硬约束

五大方案可靠性阶梯: ┌─────────────────────────────────────────────────────────┐ │ 第5层：约束解码 (Outlines / LMQL / XGrammar) │ │ → GPU 显存级别控制，精度 100%，仅限开源模型 │ ├─────────────────────────────────────────────────────────┤ │ 第4层：结构化输出模式 (OpenAI JSON Schema strict) │ │ → API 层面 Schema 强制校验，失败率 < 0.1% │ ├─────────────────────────────────────────────────────────┤ │ 第3层：Function Calling │ │ → 工具定义约束，自动适配，支持复杂嵌套 │ ├─────────────────────────────────────────────────────────┤ │ 第2层：JSON Mode │ │ → 保证有效 JSON，但不校验具体 Schema │ ├─────────────────────────────────────────────────────────┤ │ 第1层：Prompt 工程 │ │ → 角色 + 结构化指令 + 示例引导，成本最低但最不可靠 │ └─────────────────────────────────────────────────────────┘

约束方式总览

方式实现可靠性适用模型
Structured Output调用 API 时传入 Schema 参数最高（模型内部约束）OpenAI / Claude / Gemini
Prompt 约束在 system prompt 中描述格式要求中（依赖模型遵守指令）所有模型
Logit Bias在解码时限制 token 概率分布高（但灵活性低）开源模型自部署

Structured Output 是最可靠的方式——模型在解码阶段就被约束为只生成符合 Schema 的 token 序列。Prompt 约束是最灵活但最不可靠的方式——即使 GPT-4 也有约 2-5% 的概率输出不合规格式。

Structured Output 的本质是"把 JSON 语法编码到模型的 token 采样规则中"——每一步生成时，不合法的 token 被直接屏蔽。这不是模型"学会了"输出 JSON，而是系统在物理层面不允许它输出别的东西。

方案 ①：Prompt 工程——从"许愿"到"引导"

Prompt 工程是成本最低的入门方案，核心技巧包括三个维度：

技巧维度具体做法效果提升
角色明确化"你是一个严格的数据提取引擎，只输出 JSON，不输出任何其他文字"减少 30% 格式错误
结构化指令用 XML/Markdown 标记格式要求，明确每个字段的类型和含义减少 50% 字段漂移
Few-shot 示例给出 2-3 个完整的输入-输出示例对减少 60% 类型不匹配

Prompt 工程的可靠性上限约 85-92%。对于原型验证和人工审阅场景够用，但对于程序消费的自动化管线来说远远不够。它是"引导"而非"强制"。

方案 ②：JSON Mode——成本最低的 API 级约束

通过设置 response_format: {"type": "json_object"}，API 层面保证输出是合法的 JSON 语法。OpenAI 从 2023 年 11 月开始支持，几乎所有主流提供商都已跟进。JSON Mode 只保证"JSON 语法合法"，不保证字段名、类型和值符合你的业务 Schema。

方案 ③：Function Calling——工具定义约束

Function Calling 把期望的输出结构定义为工具的参数 Schema。模型为了正确"调用工具"，必须严格按照 Schema 生成参数。这种方式天然支持嵌套对象、数组和枚举类型。

关键优势：模型不是在"输出 JSON"，而是在"决定调用哪个工具并传入参数"——后者是模型经过专门训练的任务，可靠性远高于自由文本格式化。

Function Calling 的可靠性约 99.5-99.8%（Anthropic 测试数据）。失败主要来自安全拒绝（refusal）而非格式错误。它是 Agent 系统的默认首选方案。

方案 ④：结构化输出模式——API 级 Schema 强制校验

Structured Outputs 通过设置 response_format: {"type": "json_schema", "strict": true} 启用。模型在解码时被强制遵守用户提供的 JSON Schema，保证所有 required 字段存在、所有类型匹配、所有 enum 值合法。TokenMix.ai 的 50 万次调用测试显示：Schema 合规失败率低于 0.1%，几乎可以忽略不计；额外 Token 开销约 80-120 tokens/次。

JSON Mode 管"格式对不对"，Structured Outputs 管"内容对不对"——前者保证合法 JSON 语法，后者在解码层强制符合指定 Schema。

方案 ⑤：约束解码——GPU 显存级别的 100% 精度

约束解码 (Constrained Decoding)是在模型生成 token 的每一步都进行约束：根据预定义的 Schema，计算出当前步骤允许输出的 token 集合，将不允许的 token 概率设为 0。最终输出 100% 符合 Schema。该方式主要适用于自部署开源模型（如 LLaMA、Qwen），灵活性较低、不适合过度复杂的嵌套 Schema，但在无 Structured Output API 的场景下是有效的替代方案。

主流框架对比：

框架核心技术适用场景局限

约束解码的两个核心思想：(1) 每一步只允许输出符合当前 Schema 位置的 token；(2) Schema 中已确定的部分（如括号、字段名）直接跳过生成，模型只需关注内容部分。这使得约束解码在某些场景下反而比无约束更快。

四、第一道防线：JSON Schema 约束

JSON Schema 是结构化输出的"模具"——通过 Schema 定义期望的输出格式（字段名、类型、必填项、枚举值），让 LLM 在生成时受到格式约束。这也是四道防线中最靠前的一道：约束越强，后面需要兜底的失败越少。

三种约束方式的取舍

上文五大方案对应三种约束机制：Structured Output（API 硬约束）、Prompt 约束（软引导）、解码层约束（Logit Bias / 约束解码）。生产环境的默认选择是 Structured Output API——模型在解码阶段就被约束为只生成符合 Schema 的 token 序列；Prompt 约束仅作为补充（在 system prompt 中再强调一次格式要求），解码层约束用于自部署开源模型场景。

关键设计原则：Schema 设计应遵循"最小必要"原则——只约束必须的结构（如 name: string, age: integer），不要过度约束内容（如不要用 enum 限制所有可能的值）。过度约束会降低模型的表达能力，导致"格式正确但内容空洞"。完整的 Schema 设计原则与反模式见第八章。

五、第二道防线：智能重试机制

即使有 Schema 约束，LLM 仍有小概率输出不合规格式。重试机制是"不合格就返工"的工程化实现。

重试策略设计

策略触发条件重试方式上限
格式重试JSON 解析失败追加"请严格按格式输出"提示后重试最多 3 次
内容重试格式正确但字段值不合法追加字段约束说明后重试最多 2 次
降级重试多次重试仍失败切换到更简单的 Schema 或备选模型1 次

重试的核心原则是递增约束 + 有限次数：第一次重试只追加格式提示，第二次重试追加格式 + 内容约束，第三次切换为降级方案。避免无脑重试同一个请求——如果模型连续失败 3 次，大概率是 Schema 设计有问题，而不是模型"运气不好"。

重试不是"再给模型一次机会"，而是"给模型更多信息"。每次重试都应携带失败原因和更明确的约束，让模型在下一次尝试时有更大的概率生成合规输出。

补充两条按失败类型区分的重试规则：安全拒绝（refusal）类失败重试无意义，应直接进入降级流程；网络 / API 临时故障与格式错误无关，适合用指数退避（如 100ms → 200ms → 400ms）处理，不计入格式重试次数。

重试消息模板

# 降级提示（第3次 → 切换备选模型或简化 Schema）

超时保护：重试机制必须配合超时控制。建议单次 LLM 调用（含重试）的总超时设为 30 秒。如果第一次调用已耗时 20 秒，后续重试应缩短超时时间或跳过重试直接降级，避免阻塞整个请求链路。流量高峰时，无限重试可能拖垮整个系统——重试必须有明确上限，超限即降级。

六、第三道防线：输出清洗与容错

输出清洗是在 JSON 解析前后做"预处理"和"后处理"，修复 LLM 常见的格式偏差。

常见清洗规则

问题LLM 输出示例清洗方式
Markdown 包裹```json\n{...}\n```正则去除代码块标记
多余文本这是结果：{"name": "Alice"}提取第一个 { 到最后一个 }
尾随逗号{"a": 1, "b": 2,}正则去除逗号后无值的情况
单引号{'name': 'Alice'}替换为双引号（注意处理内容中的撇号）
注释{"a": 1 // 说明}正则去除 // 和 /* */ 注释

清洗层应使用宽松的 JSON 解析器（如 Python 的 json5 库），它原生支持尾随逗号、单引号、注释等非标准 JSON 语法，减少手动清洗的工作量。

清洗管线实现示例

import json5, re

def clean_llm_output(raw: str) -> dict:
    # Step 1: 去除 Markdown 代码块包裹
    text = re.sub(r'^```(?:json)?\s*\n?', '', raw.strip())
    text = re.sub(r'\n?```\s*$', '', text)

    # Step 2: 提取首个 { 到末尾 } 的区间
    start = text.find('{')
    end = text.rfind('}')
    if start == -1 or end == -1:
        raise ValueError("未找到 JSON 对象边界")
    text = text[start:end + 1]

    # Step 3: json5 宽松解析（自动处理尾随逗号、单引号、注释）
    return json5.loads(text)

清洗顺序很重要——先做"大范围"的提取（去 Markdown、截取 JSON 区间），再做"细粒度"的修复（逗号、引号）。如果顺序反了，正则表达式可能被 Markdown 标记干扰，导致修复失败。

Pydantic 语义校验：防 Silent Failure

清洗与 JSON 语法解析只解决"格式"问题。更隐蔽的是 Silent Failure（静默失败）：JSON 通过了语法校验，Schema 也完全匹配，但内容是错的。例如评分字段应该是 85，模型输出了 185——类型是 int，范围没限制就通过了。

因此在清洗管线之后、交给业务逻辑之前，应叠加 Pydantic 的 field_validator 做业务语义校验：分数必须在 0-100 之间、日期必须在合理范围内、状态必须是预定义枚举之一。这是 Schema 结构校验之上的语义防线——不仅校验类型，还校验值域和业务逻辑。

七、第四道防线：日志审计与监控

日志不是为了"有就行"，而是为了"出问题能追溯"。每次 LLM 调用的输入、输出、重试次数、耗时都应记录。

日志关键字段

字段用途示例
request_id唯一追踪 IDreq-20240101-abc123
raw_outputLLM 原始输出（清洗前）完整字符串
parsed_output清洗后的结构化结果JSON 对象
retry_count重试次数0 / 1 / 2 / 3
schema_validSchema 校验是否通过true / false
latency_ms总耗时（含重试）1200

基于日志可以建立监控告警：重试率 > 10% 触发 P2 告警（可能是 Schema 设计问题或模型降级），格式失败率 > 5% 触发 P1 告警（可能是 API 变更或模型更新）。

超限之后：三级降级阶梯

当重试上限用尽仍然失败时，系统必须有明确的兜底路径，目标是系统永远不崩溃：

  1. 默认值回退：关键字段使用预设默认值，非关键字段置为 null
  2. 原始文本保存：保存模型原始输出文本，后续人工解析
  3. 人工接管：将任务放入人工审核队列，保证最终正确性

日志存储与查询建议

生产环境推荐将结构化输出日志写入 Elasticsearch 或 ClickHouse，支持按 request_id 精确检索单次调用的完整链路。常用查询场景：

  • 按 model_version 聚合失败率，定位是否某次模型升级引入了回归
  • 按 schema_id 聚合重试次数，找出"最容易失败"的 Schema 进行优化
  • 按 input_length 分桶统计延迟，发现长文本场景下的性能瓶颈
  • 按时间窗口对比 raw_output 与 parsed_output，追踪清洗层的修复命中率

日志的价值不在于"写了多少"，而在于"能不能在 5 分钟内定位到根因"。一条好的结构化输出日志应该能让 oncall 工程师直接看到：哪个模型、哪个 Schema、什么输入、输出长什么样、在哪一步失败——无需再翻其他系统。

  • 优先使用 Structured Output API（模型内部约束）
  • 重试策略递增约束，设上限避免死循环与成本爆炸
  • 用 json5 等宽松解析器减少清洗工作
  • 每次调用记录完整日志，建立监控告警
  • 只靠 Prompt 约束不做重试
  • 无脑重试同一个请求 10 次
  • 忽略 LLM 输出中的 Markdown 包裹
  • 不记录原始输出，出问题无法追溯

八、Schema 设计：原则、反模式与兼容

JSON Schema 在商业项目里的最大价值不是让模型"输出 JSON"，而是让多团队协作有共同契约。产品知道会输出什么，后端知道怎么接，数据团队知道哪些字段可分析，风控知道哪些字段必须校验。真正难的不是解析，而是定义契约。

五大设计原则

原则推荐做法常见坏味道
字段原子化每个字段对应一个业务决策点把多个含义塞进一个 description 字段
枚举约束高频分类字段使用 enum自由文本导致下游无法聚合统计
nullable 语义明确区分 null（有值但为空）和 missing（字段缺失）两者混淆，下游无法判断
版本管理Schema 带版本号，向后兼容直接改名，线上消费者全挂
失败处理验证失败有重试、回退、人工接管路径校验失败后静默吞掉

在此之上还有一个总纲性的"最小必要"原则：只约束必须的结构，不要过度约束内容——过度约束会降低模型的表达能力，导致"格式正确但内容空洞"。

Schema 设计反模式

反模式问题改进方案
枚举所有可能值模型无法生成 Schema 中未列出的值，导致截断或空值用 string + 描述性说明替代 enum，仅对有限集合（如性别、状态）使用 enum
嵌套超过 3 层生成 token 数增加，格式失败率显著上升拆分为多个扁平 Schema，通过多次调用组合结果
必填字段过多模型在信息不足时被迫填充"占位值"，降低内容质量区分 required 和 optional，仅将业务关键字段设为必填
字段名使用缩写模型对缩写的理解不一致，可能生成错误字段使用完整的、有语义的英文字段名（如 sentiment_score 而非 ss）

兼容设计的三个要点

  1. 新增字段先灰度：先作为 optional 字段上线，验证模型能稳定输出后再改为 required
  2. 改名用双写：新旧字段同时存在一段时间，明确废弃时间表
  3. 消费方宽容解析："有则读、无则忽略"——永远不要因为多了一个未知字段就报错

Schema 变更是生产事故的高发区。一次不小心改了字段名，下游十几个服务同时挂掉。兼容设计的核心是让新旧版本能共存，把迁移从"硬切换"变成"平滑过渡"。

九、多模型输出统一化处理

多模型架构下，不同提供商的 LLM 对同一 Schema 的输出"癖好"截然不同。统一化处理是在清洗层和校验层之间增加一个"模型适配器"，抹平各家差异。

适配器层设计

适配器（Model Adapter）是一个按模型类型分发的中间层，负责将各家模型的原始输出转换为统一的中间格式，再交给下游的 Schema 校验和业务逻辑。

多模型适配器架构 ┌──────────┐ ┌──────────┐ ┌──────────┐ │ OpenAI │ │ Claude │ │ Gemini │ └─────┬────┘ └─────┬────┘ └─────┬────┘ │ │ │ ▼ ▼ ▼ ┌──────────────────────────────────────────┐ │ Model Adapter Layer │ │ │ │ OpenAIAdapter: │ │ · strip_surrounding_text(output) │ │ · normalize_scientific_notation() │ │ │ │ ClaudeAdapter: │ │ · strip_xml_tags(output) │ │ · fill_missing_nulls(schema, output) │ │ │ │ GeminiAdapter: │ │ · fix_trailing_commas(output) │ │ · normalize_quote_style(output) │ │ · fix_unicode_encoding(output) │ └──────────────────┬───────────────────────┘ ▼ 统一中间格式（Canonical JSON） │ ▼ Schema 校验 → 业务逻辑

适配器应该保持"薄层"——只做格式归一化，不做业务逻辑。每个 Adapter 的代码量通常在 50-100 行，核心是正则表达式和字段映射。新增模型时只需实现一个新 Adapter，不影响已有管线。

统一化最佳实践

  • 为每个模型维护独立的 Adapter 类，通过工厂模式按 model_name 分发
  • 在 Adapter 输出上运行同一套 Schema 校验，确保"多入口、单标准"
  • 定期对比各模型的 raw_output 样本，发现新的格式偏差及时补充清洗规则
  • 对空值统一为 null，对数字统一为 Python Decimal 避免精度丢失
  • 在业务代码里写 if model == "gpt-4" 的条件分支
  • 对不同模型使用不同的 Schema——这会导致下游逻辑复杂化
  • 忽略模型更新带来的格式变化，应建立"模型版本变更 → 触发 Adapter 回归测试"的流程
  • 把 Adapter 和业务逻辑耦合，导致换模型时需要改业务代码

多模型回归测试策略

每次模型版本升级或 Adapter 修改后，需要运行回归测试套件来验证输出质量没有退化。推荐建立以下测试体系：

测试类型内容通过标准触发时机
格式合规测试使用 100 条典型输入，验证输出能被 json5 解析且通过 Schema 校验通过率 ≥ 98%每次模型版本变更
字段完整性测试检查必填字段是否全部存在且非空缺失率 < 1%每次 Schema 修改
一致性对比测试同一输入分别调用两个模型，比较输出结构的相似度Jaccard 相似度 ≥ 0.85新增或切换模型时
边界值测试使用极长文本、空输入、特殊字符等边界场景不抛出未捕获异常每次 Adapter 修改
工程建议：将回归测试集成到 CI/CD 管线中。每次模型提供商发布新版本公告后，自动触发回归测试。如果测试失败，阻断部署并通知 oncall。建议保留至少 3 个月的历史测试数据，用于趋势分析和基线对比。

在实际落地中，建议为每个 Adapter 维护一份"格式偏差清单"（Quirk Manifest），记录该模型已知的输出特性和对应的清洗规则。当模型版本更新时，逐条验证清单中的每一项是否仍然有效。

十、生产案例与 Do/Don't

案例 1：电商评论情感抽取——四道防线落地

某电商评论分析系统接入 GPT-4 进行结构化情感抽取，初期仅依赖 Prompt 约束，格式失败率高达 12.3%（主要为 Markdown 包裹和尾随逗号）。部署四道防线后：Structured Output API 将格式失败率降至 1.8%；输出清洗层进一步修复 90% 的残余格式问题，最终到达 Schema 校验阶段的不合规率仅 0.3%；重试机制兜底后，业务侧实际感知到的失败率低于 0.05%（日均调用 50,000 次，失败约 25 次）。端到端 P99 延迟从 4.2s 降至 2.8s（因重试次数大幅减少）。

案例 2：B2B 销售线索自动抽取（86% → 98.9%）

背景：某 B2B 销售助手从通话摘要中抽取客户信息，自动写入 CRM 系统。

问题：初版通过 Prompt 要求输出 JSON，线上经常出现 budget 写成文字描述、timeline 缺失、extra_note 混入 JSON 外文本，导致 CRM 写入失败率达 14%。

改造：改用 Structured Outputs + Pydantic 校验，所有关键字段使用 enum 或显式类型；失败时只重试 1 次，仍失败降级为"保存原文 + 进入人工补录队列"。

效果：自动入库成功率从 86% 提升到 98.9%，人工补录工作量下降 63%。

案例 3：多语言客服意图分类

背景：某跨境电商客服系统需要将用户消息分类为 15 个意图类别。

问题：纯 Prompt 方案在中文场景下格式错误率 12%，西班牙语场景更达 18%。

改造：使用 Function Calling 定义分类工具，intent 字段用 15 个 enum 值约束。叠加 Instructor 自动重试。

效果：分类格式错误率降至 0.15%，全语言一致性达标。

案例 4：金融合同条款抽取

背景：某金融机构需要从 PDF 合同中抽取 30+ 个关键条款字段。

问题：嵌套 JSON Schema 过于复杂，Structured Outputs 偶发 Schema 不完全匹配。

改造：本地部署 Llama-3-70B + Outlines 约束解码，Token 级别强制输出合规。叠加 Pydantic 语义校验。

效果：Schema 合规率 100%，语义准确率 97.2%，完全满足合规审计要求。

Do / Don't

  • 优先使用 Structured Output API / Function Calling，只要结果要给程序消费就上 Schema
  • 关键字段用 enum、number、boolean 等强类型，并用 Pydantic 做语义校验（防 Silent Failure）
  • 重试策略递增约束且设上限，配合明确的降级路径
  • 每次调用记录完整日志，监控解析成功率、重试率、降级率
  • Schema 变更走版本管理 + 灰度发布
  • 只靠 Prompt 写"请输出 JSON"就上线，且不配重试
  • 把自由文本字段作为业务核心字段
  • 无限重试同一个请求，放大成本和延迟
  • 忽略 LLM 输出中的 Markdown 包裹、不记录原始输出
  • 不做 Schema 兼容设计直接改字段名

Q&A

1. Structured Output 和 Prompt 约束的本质区别是什么？
Structured Output 在模型解码阶段约束 token 生成——如果某个 token 会导致输出不合规，它的概率被强制设为 0。这是"硬约束"，100% 保证格式合规。Prompt 约束只是"告诉模型要输出 JSON"，模型可能不遵守（尤其是输出较长时容易"忘记"格式要求）。前者可靠性远高于后者。
2. Structured Outputs 和 JSON Mode 的本质区别是什么？
JSON Mode 只保证输出是合法 JSON 语法（约 95-98% 可靠），但不保证字段名、类型和值符合你的 Schema。Structured Outputs 设置 strict: true 后，模型在解码时就被约束只能生成符合指定 JSON Schema 的内容，失败率降至 0.1% 以下。简单说：JSON Mode 管"格式对不对"，Structured Outputs 管"内容对不对"。
3. Function Calling 一定比 Structured Outputs 更好吗？
不一定。Function Calling 更适合"模型决定调用哪个工具并传参"的场景（Agent 系统），Token 开销也更高（150-300 tokens）。如果只是想稳定产出结构化数据给数据库或 BI 系统，Structured Outputs 更直接、开销更低（80-120 tokens）。关键看你的业务链路：需要调用工具选 FC，只需要结构化数据选 SO。
4. 约束解码为什么能做到 100% 精度？它的代价是什么？
约束解码在模型生成每个 token 时实时干预：根据当前 Schema 位置计算允许输出的 token 集合，将不允许的 token 概率强制设为 0。这相当于在 GPU 显存级别做约束，所以精度是 100%。代价是：(1) 需要本地部署开源模型，无法用闭源 API；(2) 初始化有时间和空间开销（同一 Schema 只需计算一次）；(3) 可能影响模型生成质量（被约束掉的 token 中可能有更好的选择）。
5. 重试时为什么不能直接用同一个请求重试？
因为 LLM 的输出有随机性（temperature > 0），同一个请求重试可能输出相同的结果（如果 temperature 很低）或完全不同的结果（如果 temperature 很高）。更有效的方式是在重试时追加更明确的约束提示（如"你的上次输出格式不正确，请严格按以下 Schema 输出"），给模型更多上下文来纠正错误。同时必须设置重试上限，超限转入降级。
6. json5 和标准 json 库有什么区别？
json5 是 JSON 的超集，支持标准 JSON 不允许的语法：尾随逗号（{"a":1,}）、单引号（{'a':1}）、注释（{"a":1 //注释}）、无引号键名（{a:1}）。LLM 输出的"不标准 JSON"大多能被 json5 直接解析，减少手动清洗的工作量。
7. 什么是 Silent Failure？为什么它比格式错误更危险？
Silent Failure（静默失败）指输出通过了 JSON 语法校验和 Schema 校验，但内容是错的。例如评分应该是 85 但输出了 185，类型是 int、格式完美，但值不合理。它比格式错误更危险，因为格式错误会被 json.loads() 立即捕获并触发重试，而 Silent Failure 会悄无声息地写入数据库，污染下游分析和决策。防法：用 Pydantic field_validator 做业务语义校验——不仅校验类型，还校验值域和业务逻辑。
8. 如何区分"格式失败"和"内容不合法"？
格式失败是 JSON 解析异常（如缺少大括号、引号不匹配），发生在 json.loads() 阶段。内容不合法是 JSON 解析成功但字段值不符合 Schema（如 age 字段应该是 integer 但模型返回了 string "twenty"），发生在 Schema 校验阶段。两者的重试策略不同：格式失败追加格式提示，内容不合法追加字段约束说明。
9. Schema 设计中最常见的错误是什么？
两类最常见：一是设计层面——字段语义不清和自由文本过多，比如把"客户预算、采购阶段、紧迫程度"全塞进一个备注字段，模型虽然能写出话，但下游无法统计、筛选和自动流转；二是不做 nullable 语义区分——字段值为 null 和字段缺失是完全不同的含义，混为一谈会让下游无法判断"是没有数据"还是"没有收集这个字段"。此外，Schema 过于复杂（嵌套超过 3 层、必填字段超过 10 个）会同时拖慢生成速度并推高格式失败率，必要时应拆分为多次 LLM 调用。Schema 设计应该围绕业务决策拆字段，而不是围绕人类阅读习惯堆描述。
10. Anthropic Claude 的结构化输出为什么需要额外校验？
Anthropic 的 Tool Use 虽然支持 Schema 定义，但 Claude 没有 OpenAI 那样的 strict mode——它不保证 100% 遵守 Schema。TokenMix 测试显示 Claude Tool Use 的合规率约 99.8%，比 OpenAI 的 99.9%+ 略低。对于高风险场景，需要在 Claude 输出后叠加 Pydantic 校验层，自行捕获不合规的输出并触发重试。
11. 多模型架构下，如何处理不同提供商的 API 参数差异？
通过 Model Adapter 模式实现解耦。定义一个统一的 StructuredOutputClient 接口，内部按 model_name 分发到对应的 Adapter。OpenAI 使用 response_format={"type": "json_schema", ...}，Claude 使用 Tool Use 的 input_schema，Gemini 使用 response_mime_type="application/json"。Adapter 负责将不同的 API 参数翻译为各家的原生格式，并在返回时将输出统一为 Canonical JSON。新增模型只需实现一个新 Adapter 类，业务代码零修改。
12. 监控告警频繁误报怎么办？
误报通常源于告警阈值设置不合理。三个优化方向：（1）用"持续时间窗口"替代"瞬时阈值"——例如格式失败率 > 5% 需持续 5 分钟才触发，避免偶发请求导致的抖动告警；（2）引入"基线对比"——将当前指标与过去 7 天同时段均值比较，只有偏离基线 2 个标准差才告警；（3）区分"工作日 vs 周末"和"高峰 vs 低谷"时段，为不同时段设置不同阈值。目标是将告警的"有效率"提升到 70% 以上，避免 oncall 产生告警疲劳。
13. 流式传输场景下怎么处理半截 JSON？
三种策略：(1) 缓冲区等待——收到完整 JSON 后再解析，不在半截 JSON 上做业务逻辑；(2) 流式 JSON 解析器——使用支持不完整输入的解析库（如 ijson），在 JSON 完整时触发回调；(3) 超时兜底——设置最大等待时间（如 10 秒），超时后用已收到的部分做降级处理。核心原则：不要在半截 JSON 上做业务逻辑判断。
14. Instructor 框架和 Marvin 框架有什么区别？怎么选？
Instructor 是一个轻量级框架，核心功能是 Pydantic + 自动重试：定义 Pydantic 模型，Instructor 自动将校验错误反馈给模型重新生成，代码量极少。Marvin 是一个更完整的 AI 工程框架，除了结构化输出还包括分类、提取、生成等高级功能，适合构建完整的 AI 应用。选择建议：只需要结构化输出 → Instructor；需要完整的 AI 工程能力 → Marvin。
