L14 · 大模型选型与成本控制

选型黄金三角 / 四维评估框架 / 全链路成本核算 / 降本优化策略 / 决策树

大模型选型的本质不是"哪个模型最好"，而是"在给定约束下哪个模型最合适"。效果、速度、成本三者构成不可能三角——你几乎不可能同时拿到最优解，但可以在约束空间内找到帕累托最优。

一、选型黄金三角：效果、速度、成本

三个目标互相牵制，任何方案都只能同时占住两个角 效果 （准确率、可用性） ▲ ╱ ╲ ╱ ╲ ╱ ╲ 用大模型 ╱ ╲ 用大模型 ＋ 长提示 ╱ ╲ ＋ 深度推理 ＋ 多次采样 ╲ ▶ 效果高 ╱ ╲ ▶ 效果高 成本高 速度慢 ╱ ╲ ╱ ╲ ╱ ─────────────────────────────────╲ ▼ ▼ 成本 速度 （单次调用开销） ◀── 用小模型/量化/缓存 ──▶ （首字延迟、吞吐） ▶ 成本低、速度快，但效果打折 ───────────────────────────────────────────────────────── 三条边各自代表一种现实的取舍： 效果 ↔ 成本 ：换更强的模型、加长提示、多次采样投票 ── 每一项都直接提高单次调用开销 效果 ↔ 速度 ：让模型多想几步、串更多工具调用 ── 准确率上去了，首字延迟和总耗时也上去了 成本 ↔ 速度 ：量化、批处理、更小的模型 ── 通常能同时改善这两项，代价记在"效果"那一角 ───────────────────────────────────────────────────────── 所以选型的正确起点不是"哪个模型最好"，而是先把约束钉死： ① 业务能接受的延迟上限是多少？ （砍掉一批候选） ② 单次调用的成本上限是多少？ （再砍掉一批） ③ 在剩下的候选里，用自己的数据比效果 （才轮到比"好不好"） 顺序颠倒的典型后果：选出了效果最好但延迟或成本无法上线的方案， 然后花几周去优化一个从一开始就不该入选的候选。

大模型选型不是简单的"跑分排名"，而是在效果（输出质量是否达标）、速度（延迟是否满足业务要求）、成本（每千次调用的花费是否可持续）三个维度之间做工程权衡。很多团队的选型失败，不是选了"错误"的模型，而是根本没有定义清楚这三个维度的优先级。

黄金三角的约束关系

效果-速度-成本构成不可能三角：追求极致效果必然牺牲速度或成本，追求极致速度必然牺牲效果或增加成本，追求极致成本必然牺牲效果或速度。工程决策就是在这三者之间找到业务可接受的平衡点。

维度核心指标典型约束评估方法
效果准确性、相关性、连贯性、安全性准确率 ≥ 90%（金融场景）领域数据集 + 人工评估
速度TTFT（首 Token 延迟）、TPS（每秒 Token 数）TTFT ≤ 800ms（实时对话）压力测试 + P99 延迟监控
成本单次调用成本、月度总费用月预算 ≤ ¥5万全链路成本建模

关键洞察：选型的第一步不是对比模型，而是定义约束。例如"实时对话要求 TTFT ≤ 800ms"这一条硬约束，就能直接排除 70B 以上的稠密模型，将候选范围缩小 80%。先定约束、再选模型，是成熟工程师与初级工程师的分水岭。

常见选型误区

初级错误：只看 API 单价或公开 Benchmark 分数。公开评测分数与业务效果之间的相关性往往很弱——MMLU 得分 85% 的模型在你的客服场景中可能只有 65% 的准确率，因为 Benchmark 测的是通用知识，而你的场景需要的是领域专业能力。

深层误区：未定义需求就直接开始模型对比，忽略指令稳定性（同一 prompt 多次调用结果波动大不大）和推理效率（吞吐和延迟直接影响实际成本）。一个平均得分高但方差大的模型，在生产环境中远比一个平均分略低但稳定的模型更难用。

二、效果评估：从公开 Benchmark 到业务实测

模型效果评估的核心挑战在于：公开 Benchmark 衡量的是通用能力，而你的业务场景需要的是特定领域的专业能力。MMLU 87 分的模型在法律文书审查中可能只有 62% 的可用率，而 MMLU 82 分但经过法律数据微调的模型可用率可能达到 89%。

领域评测数据集构建

公开 Benchmark 是"高考"，业务评测集是"岗位考试"——高考状元不一定能胜任你的岗位，但岗位考试第一名一定是最合适的人选。

构建领域评测集的三步法：采样（从历史业务数据中抽取 200-500 条代表性样本）、标注（至少两位领域专家独立标注标准答案并交叉校验）、分级（按难度分为 L1 基础 / L2 进阶 / L3 专家级，确保评测覆盖不同复杂度）。一个高质量的领域评测集，其价值远超任何公开排行榜。

多维度评估指标

评估维度定义权重建议自动化可行性
准确性事实是否正确、有无幻觉30-40%中（需参考答案比对）
相关性回答是否切题、有无跑偏20-25%高（可用 Embedding 相似度）
连贯性逻辑是否通顺、结构是否清晰15-20%高（可用 LLM-as-Judge）
安全性是否存在有害内容或信息泄露20-30%高（规则 + 分类器）

人工评估 vs 自动化评估

人工评估是"金标准"但成本高、速度慢——100 条数据的人工评估可能需要 2-3 人天。自动化评估（如 LLM-as-Judge，用一个高端模型去评价另一个模型的输出）速度快、成本低，但存在评判偏差。最佳实践是"自动化做日常监控，人工做关键抽检"：日常用 GPT-4 做 Judge 评估所有请求，每周人工抽检 100 条进行校准。

生产级评估策略：建立"评估 → 反馈 → 优化"闭环。每轮 Prompt 迭代或模型切换后，自动跑领域评测集，将分数变化趋势可视化。当自动化评估分数下降超过 5% 时自动告警，触发人工复核。某电商客服团队通过这套机制，将回答准确率从 72% 持续优化到 94%。

三、速度评估：TTFT 与 TPS 的双维度博弈

大模型的推理速度不是单一指标，而是由两个独立维度决定的：TTFT（Time To First Token，首 Token 延迟）和TPS（Tokens Per Second，每秒生成 Token 数）。TTFT 决定用户"等多久开始看到回答"，TPS 决定"回答生成的流畅感"。两者对用户体验的影响截然不同，不能混为一谈。

TTFT vs TPS：为什么需要分开看

指标技术含义影响因素业务敏感场景
TTFT从请求发出到收到第一个 Token 的时间模型大小、Prompt 长度、Prefill 计算量实时对话、语音助手（≤ 800ms）
TPS每秒生成的 Token 数量模型大小、Batch Size、KV Cache 效率长文本生成、批量处理（≥ 30 TPS）

量化对速度的影响

模型量化（如 FP16 → INT8 → INT4）通过降低参数精度来换取推理速度。INT4 量化可以将推理速度提升约 300%，但代价是精度下降约 3-5%。这个 trade-off 是否值得，完全取决于业务场景：对于摘要生成等容错较高的任务，INT4 几乎无损；对于代码生成或数学推理等精度敏感的任务，INT8 是更安全的折中。

速度提升 ≈ 量化压缩比 × GPU 带宽利用率提升
INT4 量化：速度 ×3~4 | 精度损失 3~5%
INT8 量化：速度 ×1.5~2 | 精度损失 1~2%

量化的本质是"用精度换速度"——INT4 就像把 4K 视频压缩成 720P，加载快了 4 倍，但细节糊了。要不要压缩取决于你是在手机上看短视频（够用）还是在影院放映（不够用）。

四、成本核算：从 API 单价到全链路成本

大模型的成本远不止 API 调用费。一个完整的成本模型包含四层：直接推理成本（API 调用或 GPU 租用）、硬件运维成本（自建集群的电费、运维人力）、延迟成本（用户等待导致的流失率折算）和切换成本（模型更换带来的适配和测试开销）。只算 API 单价就像只算食材成本不算房租水电一样——最终利润和预期会差很远。

Token 基础与成本公式

大模型 API 按 Token 计费。一个关键常识：1 Token ≈ 0.75 个英文单词 ≈ 0.4 个汉字。这意味着同一段文本，中文消耗的 Token 数量是英文的 1.5-2 倍——中文业务场景的 API 成本天然高于英文场景。

总成本 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价

注意：输出单价通常是输入单价的 2~4 倍
例如 GPT-4o：输入 $2.5/M tokens，输出 $10/M tokens（输出是输入的 4 倍）

实际成本计算案例

场景：智能客服系统，日均处理 5000 次用户咨询，平均每次对话 800 输入 Token + 400 输出 Token。

日消耗 = 5000 × (800 + 400) = 6,000,000 tokens/日
其中输入 = 5000 × 800 = 4,000,000 tokens
其中输出 = 5000 × 400 = 2,000,000 tokens

GPT-4o 日成本 = 4M × $2.5/1M + 2M × $10/1M = $10 + $20 = $30/日 ≈ ¥210/日
GPT-4o-mini 日成本 = 4M × $0.15/1M + 2M × $0.6/1M = $0.6 + $1.2 = $1.8/日 ≈ ¥13/日
Gemini Flash 日成本 = 4M × $0.075/1M + 2M × $0.3/1M = $0.3 + $0.6 = $0.9/日 ≈ ¥6.3/日

月成本：GPT-4o ≈ ¥6,300 | GPT-4o-mini ≈ ¥390 | Gemini Flash ≈ ¥189

成本差异惊人：同一业务场景下，GPT-4o 月费 ¥6,300，而 GPT-4o-mini 仅 ¥390——差距 16 倍。如果 mini 版本的效果能满足业务要求（通常简单问答场景差距不大），选 mini 每月节省近 ¥6,000。这就是为什么"先评估够不够用，再看哪个更便宜"是正确的选型顺序。

五、降本优化策略：从 30% 到 85% 的分级节省

降本不是一个动作，而是一套分层策略。从低到高排列：提示词优化（~30% 节省）→ 批处理（~50%）→ 缓存（~80%）→ 开源模型（~70% 长期）→ 混合策略（~85%）。每一层都可以独立实施，也可以叠加使用达到最大节省效果。

提示词优化（节省 ~30%）

提示词优化是最简单的降本手段——同样的问题，精炼的 Prompt 比冗长的 Prompt 少消耗 20-40% 的输入 Token，而且效果往往更好（模型更聚焦）。

核心方法：去除冗余指令（"你是一个专业的AI助手"这类废话占 Token 但不提供信息）、结构化输出格式（JSON Schema 约束比自然语言描述更省 Token）、Few-shot 精简（从 5 个示例减到 2 个，效果下降不到 3% 但 Token 节省 40%）。

批处理优化（节省 ~50%）

将多个请求打包成 Batch 发送，大幅提升 GPU 利用率。API 服务商（如 OpenAI Batch API）对批量请求通常提供 50% 的价格折扣。适合不要求实时响应的场景：数据标注、报告生成、邮件草稿等。

缓存机制（节省 ~80%）

三级缓存架构：L1 精确匹配（完全相同的 Query 直接返回缓存结果，命中率约 10-15%）、L2 语义相似（Embedding 相似度 > 0.95 的 Query 复用结果，命中率约 20-30%）、L3 Prompt Cache（复用 KV Cache 前缀，节省 Prefill 计算，命中场景下 TTFT 降低 80%）。三级叠加可拦截 40-60% 的重复计算。

开源模型自部署（长期节省 ~70%）

当调用量达到百万级/日时，自建推理集群的成本优势开始显现。以 Llama 3.1 70B 为例，4 张 A100 GPU 的月租用成本约 ¥3-4 万，但可以处理日均 200 万次调用——折合单次调用成本不到 ¥0.02，远低于 GPT-4o 的 ¥0.05-0.10/次。但自建意味着要承担运维、升级、故障处理的额外人力成本。

混合路由策略（综合节省 ~85%）

这是降本的终极形态：用一个路由模型（通常是小模型或规则引擎）对每个请求做分类——简单问题发给轻量模型（如 GPT-4o-mini），复杂问题发给高端模型（如 GPT-4o），专业问题发给领域微调模型。实测可将整体成本降低 60-85%，同时保持 95%+ 的回答质量。

  • 先评估"够不够用"再比价格
  • 建立领域评测集做业务实测
  • 分级缓存：精确匹配 → 语义相似 → KV Cache
  • 混合路由：简单问题走轻量模型
  • 定期重新评估（模型降价很快）
  • 监控 P99 延迟，而非平均延迟
  • 只看公开 Benchmark 排名
  • 拿 API 单价当总成本
  • 所有请求都走最贵的模型
  • 忽略指令稳定性（同一 prompt 多次结果差异大）
  • 不做 A/B 测试就全量切换
  • 忽略中文 Token 消耗更高的事实

四维评估的核心洞察：任务相关性占 40% 权重——因为通用 Benchmark 只能告诉你模型"聪不聪明"，而领域评测才能告诉你模型"适不适合你的活"。一个 MMLU 78 分的领域微调模型，在你的业务场景中很可能打败 MMLU 90 分的通用大模型。

案例：某电商平台智能客服系统选型

背景：日均处理 10 万次用户咨询，初期全部使用 GPT-4o，月成本约 ¥12 万。

问题：成本不可持续，且 70% 的咨询是简单 FAQ（退款政策、物流查询），用 GPT-4o 处理这些简单问题属于"杀鸡用牛刀"。

改造：引入混合路由策略——规则引擎识别 FAQ 直接返回缓存答案（拦截 25%），轻量模型（GPT-4o-mini）处理简单问题（覆盖 50%），GPT-4o 只处理复杂投诉和纠纷（保留 25%）。

效果：月成本从 ¥12 万降至 ¥3.2 万（降低 73%），客户满意度从 4.1 分提升到 4.3 分（因为简单问题响应更快），回答准确率保持 94% 以上。

Q&A（8 题）

为什么不能直接用公开 Benchmark 排名来选模型？
公开 Benchmark（如 MMLU、HumanEval）衡量的是模型的通用能力，但业务场景需要的是领域专业能力。一个 MMLU 87 分的模型在法律文本审查中可能只有 62% 的可用率，而 MMLU 82 分但经过法律数据微调的模型可用率可达 89%。此外，Benchmark 不测试指令稳定性、输出格式遵循度、中文理解能力等生产环境关键指标。正确做法是构建领域评测集，用真实业务数据做实测对比。
TTFT 和 TPS 哪个对用户体验影响更大？
取决于场景类型。实时对话（如聊天机器人、语音助手）中 TTFT 更重要——用户期望在 800ms 内看到第一个字，超过 2 秒会明显感到"卡顿"。长文本生成（如报告、翻译）中 TPS 更重要——TTFT 稍长用户能接受，但生成速度慢（如每秒只有 5 个 Token）会让用户觉得"卡住了"。实际工程中建议分别监控：对话场景关注 P95 TTFT ≤ 800ms，生成场景关注 TPS ≥ 30。
中文业务场景为什么成本天然更高？怎么缓解？
因为 Token 化机制的原因，1 Token ≈ 0.75 英文单词 ≈ 0.4 汉字。同样一段 100 字的内容，英文大约 133 Token，中文大约 250 Token——中文消耗近 2 倍的 Token。缓解方法：(1) 选择对中文优化过的模型（如 DeepSeek、Qwen），它们的 Tokenizer 对中文编码效率更高；(2) 精简 Prompt 中的中文描述，用结构化模板替代冗长指令；(3) 利用缓存减少重复中文查询的推理次数。
三级缓存的具体架构是怎样的？各层命中率大约多少？
L1 精确匹配缓存：对 Query 做归一化（去空格、统一大小写）后查哈希表，完全相同直接返回，命中率约 10-15%，几乎零延迟。L2 语义相似缓存：将 Query 转成 Embedding 向量，在向量库中查找相似度 > 0.95 的历史记录，命中率约 20-30%，延迟增加 20-50ms（向量检索开销）。L3 Prompt Cache：复用相同 System Prompt 前缀的 KV Cache，省去 Prefill 重复计算，命中时 TTFT 降低约 80%。三级叠加可拦截 40-60% 的重复推理。
什么时候应该从 API 调用切换到自建推理集群？
关键指标是日调用量。经验法则：日均调用量 < 10 万次，API 更划算（无运维负担）；10-50 万次，需要做详细的成本对比（考虑 GPU 租用 vs API 单价）；> 50 万次，自建几乎一定更优。以 Llama 3.1 70B 为例，4 张 A100 月租 ¥3-4 万，可处理日均 200 万次调用，单次成本 < ¥0.02。但自建还要考虑：运维人力（至少 1 名 ML Engineer）、模型升级成本、故障处理 SLA。建议先用 API 跑通业务验证 PMF，再考虑迁移。
模型量化（INT4/INT8）什么时候值得用？精度损失可以接受吗？
取决于任务类型。对于摘要生成、FAQ 回答、文本分类等容错较高的任务，INT4 量化精度损失约 3-5%，但速度提升 3-4 倍，非常值得。对于代码生成、数学推理、结构化数据提取等精度敏感任务，INT8 是更安全的折中（精度损失 1-2%，速度提升 1.5-2 倍）。关键决策方法：用领域评测集分别跑 FP16 和量化版本，对比分数差异。如果量化后分数下降 < 3%，就大胆用；下降 > 5%，考虑保持高精度或换更大的量化后模型。
混合路由策略的路由模型怎么实现？会不会路由本身也有成本？
路由模型有三种实现方式，复杂度递增：(1) 规则引擎——基于关键词、意图分类等硬规则分流，零额外成本但覆盖率有限（约 30-40%）；(2) 小模型分类——用 GPT-4o-mini 或微调的 BERT 对请求做复杂度评分，成本约 ¥0.001/次（可忽略），覆盖率 70-80%；(3) Embedding 相似度——将请求与历史已分类请求做相似度匹配，中等成本。推荐"规则引擎 + 小模型"组合：先用规则引擎拦截明确的简单请求，再用小模型分类剩余请求。路由本身的成本通常不到总成本的 1%，但能节省 60-85% 的推理费用。
如何评估模型切换的"切换成本"？容易被忽略的隐性成本有哪些？
切换成本包含四个层面：(1) 工程适配——新模型的 Prompt 格式、输出格式可能不同，需要重写 Prompt 模板和解析逻辑（通常 1-3 人天）；(2) 评测验证——需要在领域评测集上重新跑全量测试，确认效果不退化（1-2 人天）；(3) 灰度发布——不能一次性全量切换，需要 10% → 50% → 100% 逐步放量（1-2 周）；(4) 回滚准备——万一切换后出问题，需要有快速回滚机制。容易被忽略的隐性成本还包括：延迟成本（新模型 TTFT 变长导致用户体验下降）、数据合规成本（切换供应商可能需要重新审核数据安全协议）、团队学习成本（新模型的特性和限制需要时间熟悉）。
