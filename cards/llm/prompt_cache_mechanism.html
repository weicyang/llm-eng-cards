L11 · Prompt Cache 核心机制

KV Cache 单次加速 → Prompt Cache 跨请求复用 → 推理成本指数级降低

一、Transformer 推理两阶段

Prefill 与 Decode 的性质对比

维度Prefill（处理输入）Decode（生成输出）
处理方式全部输入 token 一次并行前向每次只前进一个 token，必须串行
主要瓶颈算力（矩阵乘密集）显存带宽（每步都要把权重读一遍）
耗时随什么增长输入长度（注意力部分按平方）输出长度（线性）
对应的延迟指标首字延迟 TTFT每秒输出 token 数 TPS
增大批量的效果算力已接近饱和，收益有限权重读取被多请求摊薄，总吞吐显著提升
能否被缓存跳过可以，相同前缀的 KV 可直接复用不可以，每个 token 都必须真算
典型优化手段前缀缓存、分块预填充、更高效的注意力实现连续批处理、投机解码、量化、压缩 KV cache

LLM 推理本质上是"一次性读懂题目（Prefill）+ 一个字一个字写答案（Decode）"，两个阶段的计算瓶颈完全不同。

Prefill（预填充）和Decode（解码）是 Transformer 自回归推理的两个核心步骤，它们的计算模式决定了所有缓存优化的切入点。

Prefill：并行处理全部输入

将整段提示词的所有 token 并行送入模型，一次性计算每层的 Q / K / V 矩阵。输入 token 之间没有依赖关系，GPU 可以充分利用并行计算能力，N 个 token 同时处理。如果逐个计算，首 token 延迟（TTFT）将增加 N 倍。

Prefill 计算复杂度：O(N² × d)   （N = 输入长度，d = 隐藏维度）
┌──────────────────────────────────────────────┐ │ Prefill 阶段 │ │ │ │ 输入 Tokens: [t₁, t₂, t₃, ..., tₙ] │ │ ↓ ↓ ↓ ↓ │ │ ┌───────────────────────────────────────┐ │ │ │ 并行计算所有层的 Q / K / V 矩阵 │ │ │ │ Attention: softmax(QKᵀ/√d)V │ │ │ └───────────────────────────────────────┘ │ │ ↓ │ │ 输出: 所有 token 的 K/V 矩阵 + 首个输出token │ │ 复杂度: O(N²) │ └──────────────────────────────────────────────┘

Decode：自回归逐 token 生成

每次生成 1 个新 token，新 token 的 Q 需要与之前所有 token 的 K 做注意力计算。因为自回归特性，每个新 token 都依赖前面所有 token，无法并行。没有 KV Cache 的话，生成 N 个 token 的总计算量将从 O(N²) 膨胀到 O(N³)。

┌──────────────────────────────────────────────┐ │ Decode 阶段 │ │ │ │ Step 1: 新 token tₙ₊₁ │ │ Q_new × [K₁...Kₙ]ᵀ → attention scores │ │ scores × [V₁...Vₙ] → output │ │ │ │ Step 2: 新 token tₙ₊₂ │ │ Q_new × [K₁...Kₙ₊₁]ᵀ → 需要前面所有 K！ │ │ │ │ 关键：每个新 token 都要"回看"所有历史 K/V │ │ → 这就是 KV Cache 存在的意义 │ └──────────────────────────────────────────────┘

二、KV Cache：单次对话内的加速引擎

KV Cache 的本质是"空间换时间"——把已经算过的 K/V 矩阵存起来，让 Decode 阶段每步复杂度从 O(N²) 降到 O(N)。

只存 K 和 V，不存 Q

KV Cache 存储每一层 Transformer 中已处理 token 的 Key 和 Value 矩阵。Query 不需要缓存，因为 Decode 阶段每次只有 1 个新 token 的 Q。K/V 是"被查询的索引"和"被查到的值"，是静态的；Q 是"查询请求"，用完即弃。

核心加速公式：无 KV Cache 时，生成第 N 个 token 需要计算 N 次完整注意力 → O(N²)。有 KV Cache 时，只需 1 次 Q × KcachedT → O(N)。对于 8K token 上下文，加速约 8000 倍。

显存开销

KV Cache 虽快，但代价是显存占用。算式的关键是用 KV head 数而不是隐藏维度：现代 70B 模型普遍上了 GQA，KV 的宽度是 num_kv_heads × head_dim，远小于 hidden_dim。以 LLaMA-3-70B（80 层，64 个 Q head、8 个 KV head、head_dim 128）为例：

每 token KV = 2（K+V）× num_layers × num_kv_heads × head_dim × dtype_bytes               = 2 × 80 × 8 × 128 × 2 B = 320 KB
参数值说明
每 token 每层 KV 大小2 × (8 × 128) × 2 bytes (FP16)K + V，各 1024 维（GQA 后的 KV 宽度）
80 层总计80 × 4KB = 320 KB / token所有层的 KV Cache
4K 上下文~1.3 GB单个请求的 KV Cache
32K 上下文~10 GB约占 A100 80GB 的八分之一
128K 上下文~42 GB长上下文下单请求就吃掉半张卡
为什么别用 hidden_dim 估算：若按 MHA 口径 2 × 80 × 8192 × 2 B 算，会得到 2.5 MB/token，比真实值高 8 倍——那正是 GQA 省下来的倍数（64 个 Q head 共享 8 组 KV）。拿这个数去做容量规划，会把可承载并发数低估一个数量级。全站 KV 显存口径统一按 GQA 计算，与 DP08 · KV Cache 与推理优化 一致。

长上下文场景的优化手段：GQA/MQA 减少 KV head 数量（LLaMA-2-70B 的 GQA 将 KV head 从 64 减到 8，省 87.5%）；MLA 低秩压缩再进一步（DeepSeek-V3 每 token 约 50 KB）；KV Cache 量化（FP16→FP8/INT8 再省 50%）；PagedAttention 减少显存碎片；分层卸载——热页留 GPU，冷页卸载到 CPU 内存。

常见疑问："KV Cache 为什么不缓存 Q？"
答：Decode 阶段每次只生成 1 个 token，只有 1 个 Q 向量，不需要缓存。Q 是"查询请求"，用完即弃；K/V 是"知识库"，后续所有 token 都要查询，必须缓存。

三、Prompt Cache：跨请求的 Prefill 优化

什么样的请求能命中前缀缓存

请求构造方式能否命中原因改法
系统提示完全固定，放在最前面能，且命中长度最大前缀逐 token 一致，KV 可整段复用已是最佳实践
系统提示里插入了当前时间戳几乎不能时间戳一变，其后全部 token 的 KV 全部失效把易变字段移到提示末尾
把用户 ID、会话 ID 拼在提示开头不能每个用户的前缀都不同，缓存无法共享改放到提示尾部或作为独立字段
多轮对话按"系统提示 ＋ 历史 ＋ 新问题"顺序拼能，命中到历史结尾历史是只追加的，已有前缀始终不变保持只追加，不要重排或摘要化改写历史
每轮把历史压缩重写一遍不能重写改变了前缀内容，缓存整体失效压缩后作为新的稳定前缀，接受一次性重算
检索到的文档放在系统提示之前不能文档每次都不同，把固定前缀挡在了后面调整顺序：固定提示在前，检索结果在后
相同前缀但间隔很久才再次请求不确定缓存有存活时间，过期即被回收对高频前缀考虑常驻或定期预热

Prompt Cache 的核心思想：多个请求共享相同的系统提示词前缀，每次都重新做 Prefill 计算是巨大的浪费，把前缀的 K/V 缓存下来直接复用。

重复 Prefill 的浪费

在生产环境中，大量请求共享相同的系统提示词（System Prompt）、角色设定、Few-shot 示例等前缀。典型场景：一个 AI 客服系统，系统提示词 2000 tokens，日均 10 万次请求 → 每天对同样的 2000 tokens 做 10 万次 Prefill 计算。

Prompt Cache 核心思路：将高频复用的前缀文本（如系统提示词）的 K/V 矩阵持久化到显存中。后续请求命中缓存时，直接复用已计算的 K/V，跳过 Prefill。命中部分的计算量从 O(N²) 降至 O(1)。

工作流程

请求 1（冷启动）: ┌──────────────────────────────────────────────────┐ │ System Prompt (2K tokens) + User Query (500) │ │ ↓ │ │ 全量 Prefill: 计算所有 2500 tokens 的 K/V │ │ ↓ │ │ 缓存 System Prompt 部分的 K/V (2K tokens) │ │ ↓ │ │ Decode: 正常自回归生成 │ └──────────────────────────────────────────────────┘ 请求 2（命中缓存）: ┌──────────────────────────────────────────────────┐ │ System Prompt (2K tokens) + New Query (300) │ │ ↓ │ │ ✅ 命中缓存！直接加载 System Prompt 的 K/V │ │ ↓ │ │ 仅 Prefill 新增的 User Query (300 tokens) │ │ ↓ │ │ Decode: 拼接缓存 K/V + 新 K/V → 生成 │ │ 节省: 2000 tokens 的 O(N²) 计算 │ └──────────────────────────────────────────────────┘

缓存匹配策略

最长前缀匹配：从请求开头开始，逐 token 与缓存中的前缀比对，找到最长的匹配子序列。不能做模糊匹配，因为 K/V 矩阵是位置敏感的——第 5 个 token 的 K 向量编码了"我在第 5 个位置"的信息，位置不同则 K/V 不同。

LRU 淘汰：显存有限时，使用最近最少使用（Least Recently Used）策略淘汰长时间未命中的缓存条目。

生产案例：某 AI 编程助手

日均 50 万次 API 调用，系统提示词（角色设定 + 代码规范 + Few-shot 示例）共 3000 tokens。改造前每次请求全量 Prefill，首 token 延迟（TTFT）约 800ms。

启用 Prompt Cache 后：

  • 缓存命中率：92%（46 万次/天命中缓存）
  • 命中请求 TTFT：从 800ms 降至 120ms（仅 Prefill 用户输入部分）
  • 日均 GPU 算力节省：~65%（Prefill 阶段）
  • 年化成本降低：约 $180K（按 A100 $2/hr 计算）

四、KV Cache vs Prompt Cache 深度对比

KV Cache 和 Prompt Cache 不是竞争关系，而是互补——一个优化 Decode，一个优化 Prefill，联合使用实现推理全链路加速。

维度KV CachePrompt Cache
存储目标单次对话内的动态 K/V跨请求共享的静态 K/V
优化阶段Decode 阶段Prefill 阶段
复杂度降级O(N²) → O(N)O(N²) → O(1)（命中部分）
生命周期对话结束销毁长期驻留显存（LRU 淘汰）
匹配方式无需匹配（顺序追加）精确前缀匹配
显存占用与并发数 × 上下文长度成正比与缓存条目数 × 前缀长度成正比
实现复杂度低（框架内置）中（需缓存管理 + 匹配逻辑）

联合效果：半线性缓存特性

当 KV Cache + Prompt Cache 同时工作时，推理性能呈现"半线性"特征：

  • 冷启动（首次请求）：全量 Prefill + 全量 Decode，无加速
  • 热路径（缓存命中）：跳过前缀 Prefill → 仅 Prefill 增量 → KV Cache 加速 Decode
  • 效果叠加：Prefill 节省 O(N²)，Decode 每步节省 O(N)，总加速可达 数十到数千倍
总推理时间 ≈ Prefill(增量部分) + Decode(N步) ≈ O(M²) + N × O(K)
其中 M = 未缓存的增量 token 数，N = 生成长度，K = 上下文总长度
常见疑问："为什么 Prompt Cache 不能替代 KV Cache？"
答：两者优化不同阶段。Prompt Cache 只加速 Prefill（一次性计算），不影响 Decode（逐 token 生成）。即使 Prefill 被完全跳过，Decode 阶段仍需要 KV Cache 来避免重复计算历史 K/V。它们是推理流水线上两个独立的优化点。

五、进阶：CrossPoint Cache 与 PromptCash

各种进阶缓存方案都在放宽同一个限制：基础的前缀缓存要求"从第一个 token 起逐字相同"，一旦中间插入了变动内容，后面全部作废。进阶方案的思路是让缓存能在非前缀位置复用，代价是要额外记账、还要接受一点近似——所以它们的收益高度依赖你的提示到底有多"可分段"。

CrossPoint Cache：中间结果复用

CrossPoint Cache 是一种更激进的缓存策略，不仅缓存 K/V 矩阵，还缓存模型推理过程中的中间激活值（如 FFN 输出、LayerNorm 结果），进一步减少重复计算。代价是显存占用倍增，适用于前缀高度一致且显存充裕的场景（如单一 System Prompt 的客服系统）。

PromptCash 优化方案

问题根因PromptCash 方案

  • 监控缓存命中率，低于 70% 时排查前缀一致性
  • 对高频前缀设置"常驻缓存"，避免被 LRU 淘汰

Q&A

KV Cache 和 Prompt Cache 的区别是什么？分别优化推理的哪个阶段？
KV Cache 优化 Decode 阶段——存储单次对话中已生成 token 的 K/V 矩阵，避免每生成一个 token 都重新计算所有历史 token 的 K/V，将单步复杂度从 O(N²) 降到 O(N)。Prompt Cache 优化 Prefill 阶段——存储跨请求共享的前缀（如系统提示词）的 K/V 矩阵，后续请求命中缓存时跳过 Prefill 计算，命中部分复杂度从 O(N²) 降到 O(1)。两者互补：KV Cache 是"单次对话内的加速"，Prompt Cache 是"跨请求的加速"。
Prompt Cache 为什么只能做前缀匹配，不能做任意子串匹配？
因为 Transformer 的 K/V 矩阵是位置编码敏感的。第 i 个 token 的 K 向量不仅编码了 token 本身的信息，还编码了"我在第 i 个位置"的信息。即使两段文本完全相同，如果它们在不同位置出现，对应的 K/V 矩阵是不同的。因此只有从位置 0 开始的连续前缀才能直接复用 K/V。如果要支持任意子串匹配，需要引入相对位置编码（如 RoPE）并设计位置无关的缓存索引，这在工程上复杂度很高。
KV Cache 的显存占用如何计算？长上下文场景下如何优化？
KV Cache 显存 = 2(K+V) × 层数 × num_kv_heads × head_dim × 数据类型字节数 × 上下文长度 × 并发请求数。注意宽度取的是 GQA 之后的 KV 宽度，不是隐藏维度——用 hidden_dim 会高估 8 倍。以 LLaMA-3-70B（80 层，8 个 KV head × 128 head_dim，FP16）为例，每 token 约 320 KB，32K 上下文单请求约 10 GB，128K 约 42 GB。优化方案：(1) GQA/MQA 减少 KV head 数量（LLaMA-2-70B 的 GQA 把 KV head 从 64 减到 8，省 87.5%）；(2) MLA 低秩压缩（DeepSeek-V3 每 token 约 50 KB）；(3) KV Cache 量化（FP16→FP8/INT8 再省 50%）；(4) PagedAttention 减少碎片；(5) 分层卸载——热页留 GPU，冷页卸载到 CPU 内存。
什么场景下 Prompt Cache 收益最大？什么场景下不适合？
收益最大的场景：(1) 高并发 + 长固定前缀（如 AI 客服系统，系统提示词 2K+ tokens，日均 10 万+ 请求）；(2) 前缀稳定不频繁修改；(3) 首 token 延迟（TTFT）敏感的应用。不适合的场景：(1) 低并发（缓存管理开销 > 节省的计算）；(2) 每个请求的前缀差异大（如 RAG 场景下每次检索结果不同导致前缀不一致）；(3) 显存紧张，KV Cache 已经占满 GPU 内存。
如何设计一个生产级的 Prompt Cache 系统？需要考虑哪些工程问题？
核心设计：(1) 缓存索引——用前缀 token 序列的哈希做快速查找，支持最长前缀匹配；(2) 淘汰策略——LRU 或 LFU，根据命中率动态调整缓存容量；(3) 显存管理——与 KV Cache 共享显存池，设置 Prompt Cache 的显存上限（如不超过总显存的 30%）；(4) 一致性——系统提示词更新时主动失效相关缓存条目；(5) 监控——追踪缓存命中率、命中延迟、未命中时的回源延迟。关键工程挑战：缓存条目大小不一（不同长度前缀）导致显存碎片，可借鉴 vLLM 的 PagedAttention 做分页管理。
为什么 Decode 阶段的计算瓶颈是 memory-bound 而不是 compute-bound？
Decode 阶段每次只处理 1 个新 token，计算量是 O(K)（K 为上下文长度），但需要从显存中读取所有缓存的 K/V 矩阵（大小也是 O(K)）。这意味着每次计算的"数据搬运量"与"实际计算量"处于同一量级，GPU 大量时间在等待数据从显存搬到计算单元，而不是在做矩阵乘法。这就是 memory-bound。工程启示：Decode 阶段的优化重点不是增加算力，而是减少显存带宽瓶颈——GQA 减少 KV 大小、KV Cache 量化减少搬运数据量、Speculative Decoding 每次生成多个 token 来分摊读取开销。
