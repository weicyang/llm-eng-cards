L19 · Token 切分与文本压缩

BPE 基础 → 字节合并规则 → 英文中文差异 → GPT-4o vs Qwen 分词器对比 → Token 统计

Token 是文本在大模型世界里的"最小积木"兼"计价单位"：分词器把文字切成片段、编上号，模型只认这些数字；同一句话在不同模型里切出的 Token 数可以差出两三倍，直接决定你要付多少钱。

一、Token 是什么

大模型本质上是一台巨大的数字计算机，它只能理解数字，无法直接处理文字。分词器（Tokenizer）就是横在文字和数字之间的翻译官，负责把一段文本切分成一个个片段，每个片段就是一个 Token——模型读写文本的最小单位，它可以是一个完整的词、一个汉字、一个词缀，甚至只是一个标点或换行符。

切分完成后，分词器会拿每个片段去查一本"字典"——词汇表（Vocabulary），即模型认识的全部片段的清单——得到对应的编号 Token ID。模型真正吃进去、吐出来的都是这些整数编号，文字只是进出模型时的一层"包装"。

"今天天气不错" ← 人类看到的文字 │ ▼ ① 分词器切分 [今天] [天气] [不错] ← 一个个 Token │ ▼ ② 查词汇表 [8374, 12901, 5523] ← Token ID（数字序列） │ ▼ ③ 转为向量送入模型 模型计算（只和数字打交道） │ ▼ ④ 输出数字 → 反查词汇表 "适合出门散步" ← 人类看到的回答

二、BPE 算法 — 分词器的核心

主流大模型的分词器几乎都使用 BPE（Byte-Pair Encoding，字节对编码）——一种基于统计的贪心合并算法：在海量训练文本上反复找出出现频率最高的相邻片段对，把它们合并成一个新符号，直到词汇表达到预定大小。规则非常简单，却极其有效。

核心思想

找到文本中出现频率最高的一对相邻字节/字符，将它们合并为一个新符号，然后重复此过程。越常用的组合越早被合并成单独的符号，占用的 Token 也就越少。

逐步合并示例

原始文本: A B A B A B A A B

第 1 轮: 合并 A,B → 符号 C
  C C C C A C

第 2 轮: 合并 C,C → 符号 D
  D C A D A C (注意从左往右优先)

第 3 轮: 合并 A,C → 符号 E
  D C E D E

整个过程只需记录：最终文本 + 每步合并规则 + 规则顺序 → 即可还原原始文本，完全可逆。

┌────────────────────────────────────────────┐ │ BPE 训练循环（离线完成） │ │ │ │ 海量训练文本 │ │ │ │ │ ▼ │ │ 统计所有相邻片段对的出现频率 │ │ │ │ │ ▼ │ │ 选出频率最高的一对 → 合并为新符号 │ │ │ │ │ ▼ │ │ 新符号登记进词汇表 │ │ │ │ │ └──→ 回到"统计频率"，直到词汇表满 │ └────────────────────────────────────────────┘ │ ▼ 推理时：按学到的合并规则依次切分新文本

BPE 就像输入法的联想词库：你越常打"今天"，它越倾向于把"今天"当成一个整体来记——常用组合永远值得一个"短编码"。

BPE 的本质

用更少的基础符号（词汇表更小）来描述更长的文本（Token 数更少）。这是一种典型的"以空间换效率"：词汇表里多存一个高频组合，线上每句话就少算一个 Token。

三、英文与中文的分词差异

英文分词器

英文由 26 个字母组成，BPE 算法效果非常好：高频字母对会被逐步合并成常见单词，一个常用英文单词往往只占 1 个 Token。

A, T 合并 → AT
A, T, T 合并 → ATT
最终: "I am attending a meeting" → 7 tokens

中文分词器

中文已经是"终极形态"——一个汉字本身就是一个完整的语义单位，不存在更小的可合并单元（再拆就是笔画和字节，合并收益极低）。所以中文分词器必须把大量汉字和词组直接收进词汇表，词汇表天然就更大。

维度英文分词器中文分词器
基础单位字母 → 合并成词汉字（已是完整单位）
词汇表大小较小较大（需覆盖大量汉字和词语）
压缩效果好（高频字母对可大量合并）有限（汉字本身不可再拆）
典型效率1 token ≈ 0.75 个英文单词1 token ≈ 1.5 个汉字

同等信息量的 Token 消耗对比

文本规模约消耗 Token
英文100 个单词≈ 133
中文100 个汉字≈ 67
代码100 个字符≈ 25~33

英文字母是"原材料"，要靠 BPE 现场组装成词；汉字是"成品"，出厂即成品——所以中文分词器拼的是词汇表的收录量，而不是合并轮数。

词汇表越大，Token 压缩效率越高，但模型需要记忆的映射关系（Embedding 矩阵）也越大。这是精度和效率的权衡，并非"越大越好"。

词汇表就像模型自带的"词典"，词典是按它读过的语料编纂的——读英文多的模型英文词条密，读中文多的模型中文词条密。

Token 为什么重要

大模型 API 按 Token 数量计费，上下文窗口也以 Token 为上限，所以了解 Token 对控制成本和设计系统都至关重要。

案例一 · 跨境电商商品文案系统：背景：某团队每天生成 5 万条中文商品文案，单条平均 400 个输出 Token，使用 GPT-4o。问题：中文在英文主导训练的分词器下消耗偏高，月度输出成本约 1.5 万美元。方案：换用中文词汇表覆盖更好的模型，并把提示词模板从 600 Token 精简到 220 Token。效果：单条平均 Token 从 400 降到 260（-35%），月度成本降到约 6,800 美元，输出更短也让单条生成耗时下降约 30%。
案例二 · RAG 知识库问答：背景：某客服系统把整篇产品手册（约 8,000 Token）全量塞进上下文。问题：输入 Token 高企，关键段落被无关内容淹没，回答经常抓不住重点。方案：按 512 Token 切块、64 Token 重叠做语义检索，每次只注入 Top-3 相关块。效果：单次输入从 8,000 降到约 1,700 Token（-79%），人工抽检准确率从 74% 提升到 88%。
  • 上线前用目标模型的官方分词器实测 Token 数
  • 中文场景给预算留 1.5~2 倍余量
  • 把固定模板做成精简、可复用的短提示词
  • 长文档先切块检索，再注入最相关片段
  • 不要用"字数"直接当 Token 数报预算
  • 不要假设 A 模型的 Token 数适用于 B 模型
  • 不要图省事把整篇文档塞进上下文
  • 不要忽略输出 Token（它通常比输入贵 3~4 倍）

Token ≠ 字数 ≠ 单词数：1 token ≈ 0.75 个英文单词 ≈ 1.5 个汉字，同一句话在不同模型中的 Token 数可能差 2~3 倍——先量，再花。

Q&A

什么是 Token？大模型为什么需要 Token？
Token 是文本被分词器切分后的最小单位，每个 Token 对应词汇表中的一个编号（数字）。大模型需要 Token 的原因在于它本质上是数字计算机，只能处理数字而不能直接处理文字。分词器将文本转换为数字序列后，模型才能理解和生成内容。Token 可以是一个字、一个词、一段字节或一个符号，具体取决于分词规则和训练数据。
BPE 算法的核心思想是什么？为什么它能压缩文本？
BPE（Byte-Pair Encoding）的核心思想是：找到文本中出现频率最高的相邻字符对，将它们合并为一个新符号，重复此过程直到达到词汇表大小限制。它能压缩文本的原因有三：①高频字符对被合并为单个符号，减少总 Token 数；②只需记录合并规则和顺序即可还原原始文本，完全可逆；③用更少的基础符号描述更长的文本，词汇表更小但表达能力更强。整个过程类似"常用组合的编码越短越好"的优化思路。
为什么不同模型对同一句话的 Token 数不同？
原因有三：①训练数据不同——词汇表的构建依赖训练文本的频率统计，不同数据集的高频字符对不同；②语言偏好不同——GPT-4o 英文训练数据多，英文合并效率高，Qwen 中文训练数据多，中文词条覆盖更好；③合并规则不同——同样的片段在一个分词器中可能合并为 1 个 Token，在另一个分词器中可能拆成 3 个。因此同一句话在不同模型中的 Token 数可能差 2~3 倍，直接影响 API 调用成本，跨模型估算时必须重新实测。
词汇表是不是越大越好？
不是。词汇表越大，Token 压缩效率越高，同样文本消耗的 Token 越少，但代价也很明显：①Embedding 矩阵随词汇表线性增大，模型参数和显存占用上升；②低频词条训练不充分，反而可能拖累效果；③词表过大还会增加输出层 Softmax 的计算量。所以各家模型都在"压缩效率"和"参数开销"之间找平衡，GPT-4o 约 20 万、Qwen 约 15 万都是权衡后的工程选择。
如何快速估算一段文本的 Token 数？
粗略估算用经验口诀：英文 1 token ≈ 0.75 个单词（约 4 个字符），中文 1 token ≈ 1.5 个汉字，代码 1 token ≈ 3~4 个字符。精确统计则要用目标模型的官方分词器：OpenAI 系列可用 tiktoken 库或 platform.openai.com/tokenizer 页面，多模型对比可用 Tiktokenizer。注意估算结果只适用于同一个分词器，换模型必须重新统计，中文和代码场景建议在估算值上再留 1.5~2 倍余量。
工程上有哪些常见的"浪费 Token"坏习惯？怎么优化？
常见坏习惯包括：①把整篇文档塞进上下文，而不是检索最相关片段；②提示词模板冗长重复，每次请求都发送几千 Token 的固定文本；③用字数代替 Token 数做预算，中文场景严重低估；④只盯着输入 Token，忽略更贵的输出 Token。对应优化：长文档先切块做 RAG 检索（实测可省 70%+ 输入）；精简并复用提示词模板；用官方分词器实测后再报预算；对输出设置长度上限和结构化格式，压缩输出 Token。
