L03 · 开源 LLM 全景

从 LLaMA 到 DeepSeek —— 主流开源大模型架构、技术选型与选型指南

一、 LLaMA 系列

这一系列真正的贡献不是某个架构创新，而是把"权重可下载"变成了行业默认选项。今天的微调工具链、量化方案、推理框架、社区评测，几乎都是围着它先长出来的——生态的先发优势比单项跑分重要得多。

LLaMA-1（2023.02）

Meta 发布的首个开源基座模型，参数规模覆盖 7B / 13B / 33B / 65B。核心设计理念：

  • Pre-Norm + RMSNorm：在每个 Transformer 子层之前做归一化（而非 Post-Norm），使用 RMSNorm 替代 LayerNorm，去掉 mean-centering，计算效率更高
  • SwiGLU 激活：在 FFN 中使用 SwiGLU 替代 ReLU/GELU，引入门控机制提升表达能力，FFN 隐层维度为 8/3 × d_model
  • RoPE 位置编码：旋转位置编码，将位置信息编码为旋转矩阵，天然支持相对位置关系，且具备良好的外推能力
  • 训练数据：约 1.4T tokens，覆盖 CommonCrawl、C4、Wikipedia、Books、ArXiv、StackExchange、GitHub

LLaMA-2（2023.07）

  • 训练数据扩充至 2T tokens，上下文长度从 2048 扩展到 4096
  • 引入 GQA（Grouped-Query Attention）：在 34B/70B 模型中使用，KV head 数量减少（70B 仅 8 个 KV head），降低推理时 KV Cache 显存
  • 发布 LLaMA-2-Chat：经过 SFT + RLHF 对齐，是早期最强开源对话模型之一

LLaMA-3 / 3.1（2024）

  • 训练数据 15T+ tokens（LLaMA-3.1），多语言覆盖，数据质量大幅提升
  • 上下文长度扩展到 128K（LLaMA-3.1）
  • 分词器从 SentencePiece 切换到 tiktoken（BPE，128K 词表），编码效率提升约 15%
  • 全系列统一使用 GQA，8B 模型也配备 GQA
  • LLaMA-3.1 405B 成为当时最强开源模型，性能逼近 GPT-4
  • RoPE vs ALiBi vs 绝对位置编码：RoPE 通过旋转矩阵编码相对位置，支持外推；ALiBi 在 attention score 上加线性偏置；绝对位置编码直接加可学习 embedding
  • GQA 的本质：介于 MHA（每个 head 独立 KV）和 MQA（所有 head 共享 KV）之间的折衷方案，将 query head 分组共享 KV head，平衡性能与效率
  • RMSNorm vs LayerNorm：RMSNorm 省去均值计算，只做方差归一化，训练速度更快，效果相当
  • SwiGLU：SwiGLU(x) = Swish(xW₁) ⊙ (xW₂)，引入门控的同时使用 Swish 平滑激活

二、 Mistral / Mixtral

混合专家模型的账很直白：总参数决定它知道多少，激活参数决定它算得多快。显存按总参数付费，算力按激活参数付费——所以它换来的是"同等推理开销下更强"，而不是"同等显存下更强"。

稠密 FFN 与 MoE FFN：同一个位置，两种走法 ── 稠密（Dense）────────────────────────────────────── token ──▶ ┌────────────────────────────┐ ──▶ 输出 │ FFN（全部参数都参与计算） │ └────────────────────────────┘ 每个 token 都过同一套完整参数 总参数 = 激活参数 ⇒ 显存和算力同步增长 ── MoE ───────────────────────────────────────────── token │ ▼ ┌──────────────────────────────────┐ │ Router（一个很小的线性层） │ │ 给每个专家打分，取分数最高的 top-k │ └───────────────┬──────────────────┘ │ 假设 8 个专家、top-2 ┌──────┬──────┼──────┬──────┬──────┬──────┬──────┐ ▼ ▼ ▼ ▼ ▼ ▼ ▼ ▼ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │E1 │ │E2 │ │E3 │ │E4 │ │E5 │ │E6 │ │E7 │ │E8 │ │ ❄ │ │███ │ │ ❄ │ │ ❄ │ │███ │ │ ❄ │ │ ❄ │ │ ❄ │ └────┘ └─┬──┘ └────┘ └────┘ └─┬──┘ └────┘ └────┘ └────┘ │ │ │ ███ = 本次被激活 │ ❄ = 本次不参与计算 │ │ 但权重仍要驻留显存 └──────┬──────────────┘ ▼ 按 router 给的权重加权求和 ┌─────────┐ │ 输出 │ └─────────┘ ───────────────────────────────────────────────────────── 两笔账要分开算： 显存 ── 按"总参数"付：8 个专家的权重全都要在显存里 算力 ── 按"激活参数"付：每个 token 只过 2 个专家 于是同一个模型可以做到"参数量像大模型、推理速度像小模型"， 代价是显存需求并没有跟着速度一起降下来。 两个绕不开的工程问题： · 负载不均 ── router 可能把大量 token 挤给少数专家 ⇒ 需要负载均衡辅助损失 ＋ 每专家容量上限 · 专家并行 ── 专家分散在多卡时，每层要做两次 All-to-All ⇒ 通信模式比稠密模型的 All-Reduce 更难优化

稠密模型与 MoE 模型的取舍

维度稠密模型MoE 模型
每 token 参与计算的参数全部参数只有被路由到的少数专家
显存需求与参数量成正比按总参数算，不因稀疏激活而降低
同等推理算力下的能力较弱较强（这是它的主要卖点）
同等显存下的能力较强较弱（专家权重占了大量显存）
训练难度低，无额外机制高，需负载均衡损失与容量控制
分布式通信模式All-Reduce，可与计算重叠额外的 All-to-All，量随路由结果波动
微调友好度好，工具链成熟较差，路由行为容易被少量数据带偏
适合场景显存受限的单卡/边缘部署吞吐优先、显存充足的服务端批量推理

Mistral 7B（2023.09）

来自 Mistral AI，以 7B 参数量取得了超越 LLaMA-2 13B 的性能，核心创新：

  • Sliding Window Attention（SWA）：每个 token 只关注窗口内 W=4096 个 token，通过多层堆叠实现理论感受野 W × n_layers，KV Cache 内存从 O(seq_len) 降为 O(W)
  • Rolling Buffer KV Cache：循环复用 KV Cache 位置，配合 SWA 进一步降低显存
  • 架构细节：GQA（8 KV heads）+ RoPE + SwiGLU + Pre-Norm RMSNorm

Mixtral 8x7B（2023.12）

Mistral 推出的首个开源 Mixture-of-Experts（MoE） 模型：

  • 每层 8 个 expert FFN，每次 token 选择 top-2 expert
  • 总参数 46.7B，激活参数仅 ~12.9B（≈ 2 × 单 expert 参数）
  • Router 机制：使用线性层 + softmax 计算每个 expert 的权重，选 top-k 后重新归一化
  • 训练稳定性：使用 load balancing loss 避免 expert 坍缩（所有 token 路由到同一 expert）
  • 推理效率：激活参数少，推理速度接近 12B dense 模型，但性能媲美 70B 级别

Mistral Large / Codestral

  • Mistral Large：闭源旗舰模型，竞争 GPT-4 级别
  • Codestral：针对代码优化的专用模型，支持 256K 上下文
  • SWA 为什么有效：自然语言具有局部性，多数依赖集中在近邻 token；通过多层叠加，高层 token 可间接感知远处信息（类似 CNN 感受野扩张）
  • MoE 核心问题：负载不均衡（expert collapse）、通信开销（分布式训练需 All-to-All）、expert 冗余
  • MoE vs Dense 取舍：MoE 在相同计算量下可扩展更多参数→更强表达；但显存仍需存储所有 expert，推理部署需要更多 GPU 内存

三、 Qwen 系列

中文能力的差别多数不在模型结构，而在词表和数据配比。词表覆盖不好的模型，同样一句中文要多花几成 token——这同时意味着更贵的调用、更快耗尽的上下文，以及更差的长文档表现。

Qwen-1.5 / Qwen-2 / Qwen-2.5（阿里巴巴通义千问）

  • 参数规模：0.5B / 1.5B / 7B / 14B / 32B / 72B，覆盖全场景
  • 中文优化：训练数据中中文比例显著提高，中文 benchmark 领先同级开源模型
  • 长上下文：Qwen-2 支持 32K 上下文，Qwen-2.5 部分版本支持 128K
  • 分词器：基于 BPE，词表 ~152K，对中文字符、代码、数学公式有针对性优化
  • 架构：标准 Transformer Decoder + RoPE + SwiGLU + GQA + RMSNorm

Qwen-VL / Qwen-Audio

  • Qwen-VL：多模态模型，支持图文理解、OCR、视觉问答，使用 ViT 作为视觉编码器，通过 cross-attention 或 projection 融合视觉与语言特征
  • Qwen-Audio：支持语音识别、音频理解
  • Qwen-2-VL：升级动态分辨率、视频理解，多模态 benchmark 大幅领先

Qwen 代码 & 数学

  • Qwen-Coder：代码专用版本，HumanEval 表现优异
  • Qwen-Math：数学推理专用版本，GSM8K/MATH 成绩突出
  • Qwen 中文优势来源：大规模高质量中文语料 + 中文友好分词 + 中文 SFT/RLHF 数据
  • 多模态融合方式：早融合（Early Fusion）vs 晚融合（Late Fusion）→ Qwen-VL 采用 cross-attention 实现深层交互
  • 长上下文扩展技术：RoPE 频率缩放（NTK-aware、YaRN）+ 长文本持续训练

四、 DeepSeek 系列

这一系列的路线可以概括为"用架构换成本"：把注意力的 KV 缓存压下去、把 FFN 稀疏化，目标不是刷榜，而是让同等效果的训练与推理都更便宜。在算力受限的条件下，架构效率本身就是竞争力。

KV cache 是长上下文推理的主要显存开销， 分组查询注意力族的三种方案就是在压它 设：注意力头数 = 8 ── MHA（多头注意力）：每个 Q 头配一套独立的 K/V ────────── Q: q1 q2 q3 q4 q5 q6 q7 q8 │ │ │ │ │ │ │ │ K/V k1 k2 k3 k4 k5 k6 k7 k8 ← 8 套 KV KV cache 大小：8 份 表示能力：最强 ── GQA（分组查询注意力）：每组 Q 头共享一套 K/V ─────────── Q: q1 q2 q3 q4 q5 q6 q7 q8 └───┬───┘└──┬─┘ └──┬──┘└──┬─┘ │ │ │ │ K/V k1 k2 k3 k4 ← 4 套 KV（2 头一组） KV cache 大小：4 份 表示能力：接近 MHA ⇒ 现代开源模型的默认选择，是效果与显存的折中点 ── MQA（多查询注意力）：全部 Q 头共享同一套 K/V ─────────── Q: q1 q2 q3 q4 q5 q6 q7 q8 └───┴───┴───┴─┬─┴───┴───┴───┘ │ K/V k1 ← 1 套 KV KV cache 大小：1 份 表示能力：明显下降 ───────────────────────────────────────────────────────── 为什么这件事这么重要： KV cache 显存 ∝ 批量大小 × 序列长度 × 层数 × KV 头数 × 头维度 只有"KV 头数"这一项是架构可以改的，而且它是乘法因子。 把 8 套压到 4 套，长上下文场景下的显存直接对半 —— 省下来的显存能换成更大的批量，吞吐随之上去。 再往下一层的思路是把 K/V 先压缩成低维潜向量再缓存， 推理时临时还原：cache 里存的不再是 K/V 本身，而是它们的压缩表示。

DeepSeek-V2（2024.05）

DeepSeek（深度求索）的突破性架构创新：

  • MLA（Multi-head Latent Attention）：
    • 将 KV 压缩为低秩潜在向量（latent vector），c_kv = W_DKV · h，维度远小于原始 KV
    • 推理时只需缓存压缩后的 c_kv，KV Cache 大小降低 93.3%
    • 通过上投影恢复 K 和 V：K = W_UK · c_kv，V = W_UV · c_kv
    • 将 RoPE 信息解耦为额外的小维度 key，避免与压缩矩阵冲突
  • DeepSeekMoE：细粒度 expert 设计
    • Expert 数量更多但更小（如 160 个小 expert），增加组合灵活性
    • 引入 shared expert：部分 expert 始终激活，学习通用知识
    • 总参数 236B，激活参数仅 21B

DeepSeek-V3（2024.12）

  • 总参数 671B，激活参数 37B
  • 训练仅使用 2048 块 H800，训练成本约 557 万美元（极低）
  • FP8 混合精度训练：大规模使用 FP8 降低计算和通信开销
  • Multi-Token Prediction（MTP）：每步预测多个 token，提升训练效率
  • 无辅助损失的负载均衡：使用自适应偏置项替代传统 auxiliary loss
  • 性能接近 Claude-3.5-Sonnet 和 GPT-4o

DeepSeek-R1（2025.01）

  • 推理模型：专注于复杂推理任务（数学、代码、逻辑）
  • GRPO（Group Relative Policy Optimization）：
    • 去掉 PPO 中的 Critic 模型，直接用组内相对奖励作为 baseline
    • 对同一 prompt 采样一组回答，计算组内奖励的 z-score 作为优势函数
    • 大幅降低 RL 训练的计算成本和内存消耗
  • "思考"过程：模型生成详细的 chain-of-thought 推理步骤，在数学竞赛题上达到 SOTA
  • 发布蒸馏版本：R1-Distill-Qwen（1.5B/7B/14B/32B）、R1-Distill-LLaMA（8B/70B）
  • MLA vs MHA/GQA/MQA：MLA 通过低秩压缩 KV，比 GQA 更省显存，且不牺牲表达能力（可数学等价于完整 MHA）
  • 细粒度 MoE 的优势：更多更小的 expert → 更灵活的专家组合 → 更精细的知识分工
  • GRPO vs PPO：GRPO 去掉 Critic → 训练更稳定更省资源；用组内归一化代替 value function 作为 baseline
  • DeepSeek-V3 为何训练成本低：FP8 训练 + 高效 MoE + 工程优化（DualPipe 流水线并行、自研通信库）

五、 Gemma / Phi

小模型的翻身仗打的是数据质量而不是参数量：用高度筛选、甚至专门合成的"教科书级"语料，能在同一参数量级上明显超过拿海量网页数据硬训出来的模型。这条结论也反过来说明，网页语料的信噪比还有很大的压榨空间。

Google Gemma

  • Gemma-1（2024.02）：2B / 7B，基于 Gemini 技术栈，使用 SentencePiece 分词器（256K 词表）
  • 架构：Multi-Query Attention（2B）/ Multi-Head Attention（7B）+ RoPE + GeGLU 激活 + RMSNorm
  • Gemma-2（2024.06）：2B / 9B / 27B，引入交替使用局部（sliding window 4096）和全局注意力的混合策略
  • 训练数据：Gemma-1 使用 6T tokens（主要英文）；Gemma-2 数据扩展至 8-13T tokens
  • 知识蒸馏：Gemma-2 小模型使用大模型输出做蒸馏，提升小模型质量

Microsoft Phi 系列

  • 核心理念："Textbooks Are All You Need" —— 高质量数据 + 小模型可以击败大模型
  • Phi-1（2023.06）：1.3B 参数，专注代码生成，使用合成教科书数据训练，HumanEval 超过很多更大模型
  • Phi-2（2023.12）：2.7B 参数，通用能力提升，性能接近 LLaMA-2 7B
  • Phi-3（2024.04）：3.8B（mini）/ 7B / 14B，使用精心筛选和合成的 3.3T tokens 训练，Phi-3-mini 性能接近 Mixtral 8x7B
  • Phi-4（2024.12）：14B 参数，在推理、STEM、编码等任务上超越同级模型，大量使用合成数据
  • 数据策略：大量使用 GPT-4 生成的合成数据，强调数据质量而非数据量
  • 小模型路线的核心观点：模型性能不仅取决于参数量，数据质量和组成同样关键（甚至更关键）
  • 合成数据的利弊：优点是质量可控、可大规模生成；风险是 model collapse（模型在自己的输出上训练导致退化）和分布偏移
  • Gemma 的混合注意力策略：交替使用局部/全局注意力层，兼顾效率和长距离依赖建模
  • 知识蒸馏在预训练中的应用：使用大模型的 logits 作为 soft target 训练小模型，比纯预训练收敛更快、效果更好

六、 其他重要模型

开源生态的另一半价值在"可改"：能换词表、能续预训练、能塞进自己的对齐流程、能按业务裁剪层数。这些都是调用接口拿不到的自由度，也是很多团队即使效果略逊也选择开源模型的真正原因。

Yi（零一万物）

  • Yi-34B 性能优异，架构类似 LLaMA，训练 3T tokens
  • Yi-1.5 改进数据质量和长上下文支持
  • 提供 Vision-Language 多模态版本

InternLM（书生·浦语，上海 AI Lab）

  • InternLM-2 / 2.5：7B / 20B，中英双语强模型
  • 支持 200K 长上下文（InternLM-2）
  • 配套工具体系完善：InternLM-XComposer（多模态）、InternLM-Math

Baichuan（百川智能）

  • Baichuan-1/2：7B / 13B，中文优化
  • Baichuan-1 使用 RoPE，Baichuan-2 13B 使用 ALiBi
  • 中文理解和生成能力突出

ChatGLM（智谱 AI）

  • 基于 GLM（General Language Model）架构，使用 prefix decoder + bidirectional attention for prefix
  • GLM-4 系列全面升级，支持 128K 上下文
  • 中文对话能力优秀，广泛用于国内应用

Falcon（TII, 阿布扎比）

  • Falcon-40B / 180B，早期最强开源模型之一
  • 使用 Multi-Query Attention 加速推理
  • 训练数据 RefinedWeb 强调网页数据清洗质量
  • GLM 架构特点：不同于纯 causal decoder，GLM 使用自回归空白填充（autoregressive blank infilling），前缀部分双向注意力，生成部分单向
  • 国产模型趋势：中文语料质量竞争、长上下文支持、多模态能力成为标配
  • MQA 的代价：所有 head 共享一组 KV → 推理速度最快但可能损失表达能力，Falcon 在大规模时表现良好

七、 架构差异对比表

现代开源模型的架构已经高度收敛：Pre-Norm、RMSNorm、旋转位置编码、SwiGLU、分组查询注意力，基本人人都有。真正的差异化早就搬到了数据配比与后训练上——看架构表已经很难预测谁强。

八、 Benchmark 对比

榜单分数只适合用来筛掉明显不行的，不适合用来选出最合适的。原因很简单：榜单题目大概率以某种形式出现在训练数据里，而你的业务数据一定没有——这两件事的方向刚好相反。

示例场景：照榜单挑了第一名，上线后不如第三名。背景——某团队要做中文长文档摘要，从公开榜单上挑了同尺寸里综合分最高的模型直接接入。问题——实测效果反而不如榜单排名靠后几位的另一个候选。拆解出三个原因：一是榜单以英文推理与知识题为主，与"中文长文摘要"这个任务几乎不相关；二是所选模型的中文词表覆盖较差，同一份文档要多花约 40% 的 token，在固定上下文里能塞进的正文明显更少，长文档直接被截断；三是它的后训练风格偏向长篇详尽输出，与业务要求的简洁摘要天然冲突，靠提示词压不住。方案——改成用自己的数据做决策：抽 200 篇真实文档建一个小盲评集，三个候选各跑一遍，人工做两两盲评；同时把"中文字符 ÷ token 比"和"平均输出长度"两个量化指标一并纳入对比。效果——最终选中的是榜单上排第三的模型，它在盲评里的胜率明显更高，token 效率也更好。可复用的做法：榜单用来定候选集（三到五个），选型用自己的数据定胜负，两百条真实样本的信息量远大于任何公开分数。

九、 如何选择开源模型

选型的顺序是固定的三步：先按可用显存框定参数量级（这一步是硬约束，不由效果决定），再按语种和任务类型筛出三到五个候选，最后用自己的真实数据做小规模盲评定胜负。顺序颠倒，就会出现"选了个跑分最高但放不进显存"的典型浪费。

示例场景：把一个 70B 级模型塞进单张 80GB 卡。背景——某团队只有一张 80 GB 显存的卡，需要用一个 70B 级开源模型做离线批量文档处理，任务对延迟不敏感但对质量有要求。问题——按 FP16 算，光权重就约 140 GB，根本放不下；退到 8-bit 约 70 GB，权重勉强进得去，但一旦上长上下文，KV cache 和激活立刻把剩下的十来 GB 吃光，批量只能开到 1 且长文档必 OOM。方案——三步：权重用 4-bit 量化，占用压到约 35 GB，把腾出来的四十多 GB 全部留给 KV cache 和激活；利用该模型的分组查询注意力结构，KV cache 本身的单位开销已经比多头注意力小得多；对少数经实测对量化最敏感的层保留更高位宽，做混合精度量化以回收一部分质量。效果——单卡跑通，长上下文批处理稳定运行，批量可以开到有意义的大小；业务盲评上的质量损失约一到两个百分点，在这个场景可以接受。代价必须说清——4-bit 的解量化开销让单请求吞吐低于 FP16 多卡方案，所以这套配置只适合离线批处理，不适合低延迟在线服务。一般化的判据：显存不够时先量化权重再考虑加卡，但要先确认任务对量化损失的敏感度。

十、 Q&A

Q1：RoPE 旋转位置编码的原理是什么？为什么现在大多数模型都用它？

原理：RoPE 将位置信息编码为旋转矩阵，对 query 和 key 向量施加与位置相关的旋转。具体来说，将 d 维向量分为 d/2 组二维子空间，每组施加不同频率的旋转：

R(θ_i, m) = [[cos(mθ_i), -sin(mθ_i)],
              [sin(mθ_i),  cos(mθ_i)]]

其中 m 是位置，θ_i = 1/10000^(2i/d) 是频率。

优势：(1) 内积自然包含相对位置信息：q_m · k_n 仅依赖于 m-n；(2) 无需额外参数；(3) 兼容线性注意力；(4) 通过调整频率基数（NTK-aware scaling）或插值可扩展上下文长度。这些特性使其成为事实标准。

Q2：GQA、MQA、MHA 三者有什么区别？各自的适用场景？

MHA（Multi-Head Attention）：每个 attention head 有独立的 Q、K、V 投影。KV Cache 大小 = n_heads × d_head × seq_len × 2。表达能力最强，但推理时 KV Cache 显存最大。

MQA（Multi-Query Attention）：所有 head 共享一组 K、V，仅 Q 各自独立。KV Cache 缩减为 1/n_heads。推理最快，但可能损失质量。代表：Falcon、PaLM。

GQA（Grouped-Query Attention）：将 query head 分为 G 组，每组共享一组 KV。KV Cache = G × d_head × seq_len × 2。是 MHA 和 MQA 的折衷，G=1 时退化为 MQA，G=n_heads 时等价于 MHA。代表：LLaMA-2/3、Mistral。

选择建议：大模型推理密集场景用 GQA；极端推理速度需求用 MQA；训练为主或小模型可用 MHA。

Q3：MoE（Mixture of Experts）的核心原理是什么？有哪些关键挑战？

原理：在 FFN 层替换为多个并行的 expert 网络 + 一个 router（门控网络）。Router 为每个 token 计算各 expert 的权重，选择 top-k expert 激活，其余不参与计算。

y = Σ_{i ∈ TopK} g_i · Expert_i(x)
g = Softmax(W_router · x) → select TopK

优势：总参数量大（强表达）但每次前向仅激活少量参数（低计算成本）。

关键挑战：(1) 负载不均衡：少数 expert 被过度选择，其余闲置 → 用 auxiliary loss 或自适应偏置惩罚不均衡；(2) 通信开销：分布式训练需 All-to-All 通信在 GPU 间路由 token；(3) expert 冗余：部分 expert 学到相似知识；(4) 推理显存：虽然只激活部分 expert，但所有 expert 权重都需加载到显存。

Q4：DeepSeek MLA（Multi-head Latent Attention）是如何压缩 KV Cache 的？

核心思想：将高维的 KV 向量通过低秩投影压缩为低维的潜在向量（latent vector），推理时只需缓存压缩后的向量。

具体步骤：

  1. 压缩：c_kv = W_DKV · h，其中 c_kv 维度 d_c 远小于 n_h × d_h（如 d_c = 512 vs 原始 8192）
  2. 恢复：K = W_UK · c_kv，V = W_UV · c_kv，上投影回完整维度做 attention
  3. RoPE 解耦：RoPE 需要作用在 K 上，但压缩矩阵与位置无关 → 额外分配少量维度的 decoupled key 专门携带 RoPE 信息

效果：KV Cache 从 2 × n_h × d_h 降至 d_c（+少量 RoPE key），压缩比超过 93%，且可数学等价于完整 MHA（不损失理论表达能力）。

Q5：GRPO 和 PPO 的区别是什么？为什么 DeepSeek 选择 GRPO？

PPO（Proximal Policy Optimization）：标准 RLHF 算法，需要训练 4 个模型：Policy（策略模型）、Reference（参考模型）、Reward（奖励模型）、Critic/Value（价值模型）。Critic 模型用于估计状态价值函数作为 baseline。

GRPO（Group Relative Policy Optimization）：DeepSeek 提出的简化方案：

  1. 去掉 Critic 模型 → 省下接近一个完整 LLM 的显存和计算
  2. 对同一 prompt 采样 G 个回答，计算各自的 reward
  3. 用组内 reward 的 z-score（均值为 0，标准差为 1）作为优势函数：A_i = (r_i - mean(r)) / std(r)
  4. 仍使用 clipping 约束策略更新幅度，保持训练稳定

GRPO 的优势：(1) 训练资源减少约 25-30%；(2) 实现更简单，超参更少；(3) 组内相对比较天然消除奖励模型的偏差；(4) 实验证明效果不逊于 PPO。

Q6：SwiGLU 激活函数为什么比 ReLU/GELU 更好？

SwiGLU 结合了 Swish 激活和 GLU（Gated Linear Unit）门控机制：

SwiGLU(x) = Swish(xW₁) ⊙ (xW₂)
Swish(x) = x · σ(βx)  （σ 是 sigmoid，β 通常为 1）

为什么更好：

  1. 门控机制：GLU 引入信息选择能力，模型可以学习"让哪些信息通过"，比无门控的 ReLU/GELU 更灵活
  2. 平滑性：Swish 在 0 附近平滑（不像 ReLU 不可导），梯度流更稳定
  3. 非单调性：Swish 在负值区域有轻微负输出，可以保留部分负值信号
  4. 实验验证：PaLM、LLaMA 等论文均验证 SwiGLU 在 Transformer FFN 中优于 ReLU/GELU

代价：SwiGLU FFN 有 3 个权重矩阵（W₁, W₂, W₃）而非 2 个，为保持参数量一致通常将隐层维度设为 2/3 × 4d ≈ 8/3 × d。

Q7：如何将开源模型的上下文长度从 4K 扩展到 128K？

上下文扩展是当前热门研究方向，主要方法包括：

  1. RoPE 频率缩放：
    • 线性插值（Position Interpolation）：将位置 m 缩放为 m/s（s 为扩展倍数），压缩到训练范围内
    • NTK-aware Scaling：调整 RoPE 的频率基数 base，低频分量插值、高频分量保持
    • YaRN：结合 NTK 和注意力缩放因子，效果优于纯插值
  2. 长文本持续训练：用扩展后的上下文长度继续预训练少量步数，让模型适应新的位置分布
  3. 注意力优化：Flash Attention、Ring Attention 解决长序列计算效率问题
  4. KV Cache 优化：GQA/MQA 降低 KV Cache 显存、PagedAttention（vLLM）管理动态显存

实际做法（如 LLaMA-3.1）：base = 500000 的高基数 RoPE + 长文本数据持续训练 → 原生支持 128K。

Q8：开源模型的训练数据策略有哪些关键经验？

数据质量 > 数据数量 已成为共识，关键经验：

  1. 数据清洗：去重（MinHash / SimHash）、质量过滤（perplexity filter）、安全过滤（有毒内容）、隐私脱敏
  2. 数据配比：Web / 书籍 / 代码 / 学术论文 / 对话数据的混合比例影响模型能力倾向。代码数据比例高 → 推理能力强（代码训练的溢出效应）
  3. 合成数据：Phi 系列证明 GPT-4 生成的教科书式合成数据可大幅提升小模型质量。但需注意模型坍缩风险
  4. 课程学习：先用大量低质量数据预热，后期用少量高质量数据精炼（如 LLaMA-3 的 annealing 阶段）
  5. 多语言策略：中英比例、代码占比直接影响各任务表现。Qwen 高中文比例 → 中文强；LLaMA 以英文为主
  6. 数据 epoch：大部分数据只过 1 epoch，高质量数据可重复使用（up-sampling）
Q9：Dense 模型和 MoE 模型在部署上有什么区别？如何选择？

Dense 模型部署：

  • 显存需求 ≈ 参数量 × 精度字节数（如 70B FP16 ≈ 140GB）
  • 计算负载与参数量成正比
  • 推理延迟可预测，batch 处理简单

MoE 模型部署：

  • 显存需求 ≈ 总参数量（非激活参数），如 Mixtral 8x7B 需 ~93GB FP16
  • 计算量仅与激活参数相关（12.9B），推理速度接近同等激活参数的 dense 模型
  • 需要更多 GPU 内存但计算效率高 → 性价比优势在高吞吐场景显著
  • Expert 并行：不同 expert 可分布在不同 GPU，需要 All-to-All 通信

选择建议：显存充裕 + 追求高吞吐 → MoE（花更少计算获得更多参数）；显存紧张 + 追求低延迟 → Dense 小模型；端侧部署 → Dense（避免通信开销）。

Q10：Benchmark 评测的局限性有哪些？如何更全面地评估模型？

主要局限性：

  1. 数据污染（Contamination）：评测数据可能出现在训练集中，导致分数虚高。部分模型被发现 GSM8K 泄漏
  2. 格式敏感：prompt 模板、few-shot 示例数量、解码参数（temperature、top-p）都显著影响成绩
  3. 任务覆盖不全：MMLU 偏知识记忆、HumanEval 仅 164 题且限 Python、GSM8K 仅小学数学 → 无法代表全面能力
  4. 静态评测：Benchmark 固定后容易被"刷分"，难以反映真实用户交互体验
  5. 多语言不足：主流 Benchmark 以英文为主，中文/小语种评测体系不成熟

更全面的评估方式：

  • 人类偏好评测：Chatbot Arena（LMSYS）通过真人 A/B 投票计算 Elo，最接近真实体验
  • 任务专项评测：针对具体应用场景构建评测集（如客服对话、文档摘要）
  • 对抗评测：使用对抗样本测试鲁棒性
  • 动态评测：LiveBench 等持续更新评测数据避免污染
  • 综合套件：Open LLM Leaderboard 聚合多个 benchmark 给出综合排名
