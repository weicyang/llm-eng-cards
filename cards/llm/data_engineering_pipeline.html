大模型数据工程的本质：把"脏乱差的原始数据"变成"高质量的结构化知识"，让模型吃得进去、消化得好、吐出来的准。数据质量决定了系统上限，模型再好也架不住数据拉胯。

一、数据清洗与标准化治理

原始数据的质量问题多种多样：OCR 扫描的 PDF 存在乱码和水印，网页爬虫数据掺杂 HTML 标签和脚本噪声，办公文档有表格嵌套和合并单元格等复杂排版。如果不清洗就直接入库，检索结果会充满噪声。

标准化处理三步走

第一步：图像预处理。对扫描件做纠偏去噪和版面解析，统一文档格式。这一步解决 OCR 引入的噪声——实测不纠偏的文档检索精度下降 15-20%。

第二步：标签体系构建。为每份文档建立三层标签——元数据标签（发布日期、来源）、业务标签（部门、分类）、权限标签（保密等级）。标签通过唯一 ID 关联关系数据库，支持检索时的精准过滤（如"只检索 2024 年之后、财务部、机密级别"的文档）。

第三步：ID 关联设计。每个文档块分配唯一 ID，通过 ID 与元数据库关联。这样检索时不仅能返回文档内容，还能返回其标签信息，用于权限控制和来源追溯。

生产数据：某企业 RAG 系统在数据清洗阶段投入 2 周，将检索精度从 62% 提升到 85%。清洗前后的对比：乱码率从 8% 降至 0.1%，无效标签从 23% 降至 2%。

通用图抽取：把原图渲染为答案配图

技术文档里充斥着流程图、架构图等插图，常规的文本抽取只能拿到图中零散的文字，丢失了图形本身的连接关系与布局信息。通用图抽取换了个思路：用连通分量算法对文档的渲染页面做区域分析——相互连通的像素构成一个连通分量，一幅完整的图形通常对应一个面积较大的连通分量。据此即可把流程图、架构图从版面中识别并裁剪出来，重新渲染成原图存储入库。

这一做法的价值在问答环节兑现：当查询命中与图相关的内容时，将渲染好的原图作为答案配图随文字一起返回。用户看到的是作者绘制的那张图，信息完整度远胜于任何对图的文字转述。

表格图抽取：表格渲染成图片随答案返回

表格面临同样的问题：合并单元格、多级表头、对齐的数字，转成纯文本后极易变形，字段一字不落往往做不到。表格图抽取把表格单独处理——解析阶段将表格直接渲染成图片，与表格的文本内容一起入库；检索命中时，表格图片随答案一并返回。这样既保住了全部字段，也让用户看到表格的原始排版。

检索排除副块：副块只存储不参与检索

上述抽取出的图表内容，通常以主文本块派生的副块形式存储，但它们不参与检索。原因很直接：副块的文本信息（图注、表格 OCR 文字）往往碎片化、语义不完整，若与主文本块一起进入检索候选池，很容易在相近的 query 下抢占前排位置，造成"命中但不精准"的错配，浪费宝贵的 top-k 名额。正确的姿势是：副块只存储、通过 ID 挂在主文本块上；检索只在主文本块上进行，命中主文本块后，再把它携带的副块（原图、表格图片）附带返回拼成完整答案。

副块是"答案的附件"而非"检索的选手"——存储它们保证答案的完整性，排除它们保证检索的纯净度，一举两得。

分块的核心矛盾：小块精准定位但丢失上下文，大块保留上下文但定位模糊。双架构同时维护两种粒度的分块，用 ID 映射关联。

分块类型大小功能定位技术方案
检索小块200-300 字精准定位单一知识点智能递归切割 + 动态滑窗重叠
生成大块1500-2000 字保留完整上下文按段落/章节边界切割，ID 映射关联

重叠比例是关键参数：通用文本建议 10%-20%（防止句子被截断），医疗/法律等专业领域建议 5%-10%（术语密集，过多重叠反而引入噪声）。分块时应主动识别段落、换行等语义边界，避免机械切割。

双架构的工作方式：检索时用小块精准定位（返回 Top-K 个 200 字的小块），生成时通过 ID 映射找到对应的大块（1500 字的完整上下文），将大块喂给 LLM。这样既有精准定位，又有充足上下文。

三阶段选型路线

冷启动阶段：直接采用行业开源专用模型（如医疗领域用 medical-embeddings，法律领域用 legal-bert）。避免使用通用模型（如 text-embedding-ada-002）处理专业术语——"心肌梗死"和"心脏停搏"在通用模型中的向量距离可能很远，但在医疗专用模型中距离很近。

数据积累后：用收集到的 query-document 对做对比学习微调。实测微调后检索精准度提升 20%-50%。微调数据量不需要很大，500-1000 对高质量标注即可见效。

入库前：强制对所有向量做归一化处理（L2 normalize）。不归一化会导致距离计算偏差——模长大的向量天然"距离远"，模长小的向量"距离近"，这会干扰相似度排序。

  • 冷启动用行业专用模型，不贪"最新最大"
  • 积累 500+ 对后做对比学习微调
  • 入库前强制 L2 归一化
  • 定期评估 Embedding 质量（抽样检查 Top-K 语义相关性）
  • 用通用模型处理专业术语（如医学/法律）
  • 跳过归一化直接入库
  • 只有一两百条数据就急着微调
  • Embedding 模型更新后不做全量重建

四、向量库性能优化

索引算法选型

算法原理性能适用场景
FLAT 暴力检索逐一计算距离千万级数据耗时数秒小规模测试（淘汰方案）
HNSW 分层导航多层图跳转毫秒级响应线上标配（千万~亿级）
IVF-PQ 倒排量化聚类 + 量化压缩毫秒级，精度略低超大规模（十亿级+）

HNSW（Hierarchical Navigable Small World）是当前最主流的 ANN 索引算法，通过构建多层"高速公路"图结构，在每层跳跃式搜索，快速定位最近邻向量。典型配置：ef_construction=200（构建精度），ef_search=100（查询精度），M=16（每层连接数）。

HNSW 深度调参指南

HNSW 的三个核心参数相互影响，需要系统调优：

  • M（每层最大连接数）：控制图的连通性。M=16 是默认值，适合大多数场景；数据维度 > 768 时建议提升至 M=24-32，因为高维空间需要更多连接来维持图的导航性。但 M 过大会导致内存占用线性增长（每个节点存储 M×2 个邻居指针）。
  • ef_construction（构建时搜索宽度）：决定索引质量。值越大，构建的图越精确，但构建时间呈超线性增长。推荐范围：小规模数据（< 100 万）用 100-200，中大规模（100 万-1 亿）用 200-400。超过 400 后 Recall 提升边际递减（< 0.5%），但构建时间可能翻倍。
  • ef_search（查询时搜索宽度）：控制召回率与延迟的平衡。ef_search 必须 ≥ Top-K，否则结果不完整。生产环境中建议从 ef_search=2×K 开始，逐步增加直到 Recall 满足要求。

HNSW 调参的核心思路：先用高参数建索引（ef_construction=400, M=24），保证索引质量不成为瓶颈；然后只调 ef_search 找到召回率和延迟的甜点。ef_search 是唯一可以在运行时动态调整的参数，不同请求可以设置不同的值。

批量入库优化

百万级数据入库时，批量大小直接影响速度：低维向量（128-256 维）建议 500-1000 条/批，高维向量（768-1536 维）建议 200-500 条/批。优化后入库速度提升 5-10 倍——百万数据从小时级降至分钟级。

入库字节截断：中文长文本的长度校验

入库环节还有一个容易踩的坑：文本长度校验按字符数做。很多实现习惯用字符数判断是否超限，但下游的接口与数据库字段往往按字节限制——一个中文字符在 UTF-8 下占 3 个字节，字符数"刚好达标"的中文长文本，字节长度可能早已超限。此时若直接按字节强行截断，切口可能落在多字节字符的中间，产生乱码甚至直接导致入库报错。正确的做法是改按字节做长度校验：需要截断时，从截断位置回退到完整字符边界再切。切换为字节级校验后，才能从根本上避免中文长文本截断出乱码的问题。

五、多层检索防幻觉机制

单次向量检索不够可靠。多层检索通过"混合检索 + 重排序"两道关卡，将检索质量提升一个台阶。

第一层：混合检索。将向量语义检索和 BM25 关键词检索的结果加权融合。语义检索擅长理解意图（"用户认证"→ login/auth），BM25 擅长精确匹配（"OAuth2.0" 只能靠关键词命中）。两者互补，融合后的召回率比单一检索高 10-15%。

第二层：重排序防线。从混合检索的 Top-50 候选中，用 Rerank 模型（如 Cohere Rerank、bge-reranker）做二次打分。Rerank 模型是 cross-encoder，精度远高于 bi-encoder 的向量检索，但速度慢——所以只对 Top-50 做重排序，而非全库。HyDE 技术可作为补充：让 LLM 先生成一个假设性回答，用这个回答的向量去检索，增强召回。

场景适配：混合检索 + Rerank 在短问答场景（如 FAQ）效果显著，可提升准确率 15-25%。但在复杂长问题场景（如"对比 A 和 B 的优缺点"）中效果有限，因为单个文档块很难覆盖完整答案，需要多跳检索或 Agentic RAG。

六、数据质量监控与持续迭代

数据工程不是一次性工程，而是持续运转的闭环。数据会老化、分布会漂移、用户反馈会暴露盲区——没有监控的数据管道等于在裸奔。

MRR（平均倒数排名）正确答案排名的倒数均值< 0.6 告警正确答案是否排在前面
空检索率无结果返回的请求占比> 5% 告警是否存在覆盖盲区
用户负反馈率点击"无用"按钮的请求占比> 15% 告警终端用户的直观满意度

数据漂移检测

随着时间推移，入库数据的分布可能发生显著变化（即数据漂移），导致检索质量下降。常见的漂移类型及应对策略：

  • 语义漂移：新增文档的主题分布与存量数据差异过大。检测方法：对新增文档的 Embedding 向量做聚类，与存量聚类中心对比，偏移超过阈值时触发告警。应对：重新评估分块策略和 Embedding 模型是否需要更新。
  • Query 漂移：用户的提问模式发生变化（例如新产品上线后出现大量新术语 query）。检测方法：对 query 日志做关键词频次分析，识别突增的新术语。应对：将新术语补充到 BM25 词典中，或用新 query 对微调 Embedding 模型。
  • 标签退化：元数据标签随时间失效（如组织架构调整导致部门标签过时）。应对：定期（建议每季度）做标签审计，自动检测失效标签并标记待人工复核。
  • 格式漂移：新入库文档的格式与存量文档不一致（如新版模板、新字段）。应对：在数据入库管道中增加格式校验环节，不符合规范的数据自动进入人工审核队列。

用户反馈闭环

用户反馈是最真实的评估信号。建议在 RAG 系统的前端加入显式反馈入口（如"有用 / 无用"按钮），并建立自动化反馈处理管道：

  • 对负反馈 query 自动保存检索日志，定期人工分析根因
  • 高频率负反馈 query 加入硬编码规则或 FAQ 白名单
  • 正反馈样本作为高质量训练数据用于 Embedding 微调
  • 每周生成检索质量周报，追踪关键指标趋势
  • 忽视用户负反馈，认为"模型没问题就是数据问题"
  • 只在上线初期做评估，之后不再关注检索质量
  • 反馈数据量太少就急着做自动化优化
  • 模型更新后不做回归测试就直接上线

索引重建与增量更新策略

索引重建的代价很高（百万级数据约 10-30 分钟），但不重建的代价更高——过期的索引会让检索质量悄悄退化，而且这种退化很难被用户直接感知，只会表现为"回答不太准"。

当检测到以下信号时，应考虑触发索引重建：

  • Embedding 模型更新（必须全量重建，因为不同模型的向量空间不兼容）
  • 数据漂移超过阈值（建议增量更新 + 局部重建受影响的聚类分区）
  • 索引碎片化严重——HNSW 图在大量增删后性能退化，Recall 下降 > 3% 时触发紧凑化
生产经验：某企业 RAG 系统接入监控后发现，每月约有 8% 的 query 属于"新增知识盲区"（系统无法回答）。通过建立反馈闭环，将这些 query 对应的缺失文档定向补充入库，3 个月后盲区率降至 2%，用户满意度从 68% 提升至 89%。

Q&A

双架构分块中，小块和大块的 ID 映射怎么实现？
每个小块存储时附带一个 parent_id 字段，指向其所属的大块。检索时先用小块做向量搜索（精准定位），返回的 Top-K 小块通过 parent_id 找到对应的大块，将大块内容喂给 LLM（保留完整上下文）。这样兼顾了定位精度和上下文完整性。
为什么 Embedding 向量必须做 L2 归一化？
不归一化时，向量的模长会影响距离计算。例如两个语义相同的向量，如果模长不同（一个 [1,0]，一个 [100,0]），它们的欧氏距离会很大，被误判为"不相似"。归一化后所有向量模长为 1，距离计算只反映方向差异（即语义差异），不受模长干扰。
HNSW 的 ef_construction 和 ef_search 参数怎么调？
ef_construction 控制索引构建质量（越大越精确但构建越慢），线上推荐 200-400。ef_search 控制查询精度（越大召回率越高但查询越慢），线上推荐 50-200。调参策略：先固定 ef_construction=200，调整 ef_search 使 Recall@10 > 95%，然后适当降低 ef_search 以满足延迟要求。
混合检索中 BM25 和向量检索的权重怎么分配？
常用融合算法是 RRF（Reciprocal Rank Fusion），不依赖权重参数，而是根据排名位置融合。如果手动加权，推荐向量权重 0.6-0.7、BM25 权重 0.3-0.4（语义检索为主、关键词为辅）。具体权重取决于 query 类型：短 query（如"登录失败"）BM25 权重可高些，长 query（如"如何处理用户登录失败的异常"）向量权重应高些。
HyDE 技术适用于所有场景吗？
HyDE（Hypothetical Document Embeddings）在短 query 场景效果最好——query 越短，生成的假设性回答提供的语义信息越多。但在 query 已经很长很具体的场景（如完整的技术问题描述），HyDE 的增益有限甚至可能引入噪声（因为 LLM 生成的假设性回答可能偏离真实意图）。建议对 query 长度 < 20 字的请求启用 HyDE。
如何检测线上 RAG 系统的数据漂移，多久检测一次？
数据漂移检测建议分两层做：（1）轻量级检测——每日对 query 日志做关键词频次统计，识别突增的新术语和异常分布，成本低且可自动化；（2）深度检测——每周对新增入库文档的 Embedding 向量做聚类分析，与存量聚类中心比较余弦距离偏移量。偏移超过 15-20% 时触发告警。实践中，大多数企业级 RAG 系统每月会经历一次明显的数据分布变化（如新产品发布、政策更新），因此月度全量评估 + 每日轻量监控是比较合理的节奏。
Embedding 模型更新后，为什么必须全量重建索引而不能增量更新？
不同 Embedding 模型（甚至同一模型的不同版本）产生的向量位于不同的向量空间中。例如模型 A 将"心肌梗死"映射到向量 v1，模型 B 映射到向量 v2，v1 和 v2 之间的余弦距离没有语义意义。如果只将新文档用新模型编码、旧文档仍用旧模型的向量，混合后的索引中距离计算会完全失效——相同语义的文档可能被判为"不相似"。因此模型更新后必须对所有存量文档重新编码并重建索引，这是不可省略的步骤。
