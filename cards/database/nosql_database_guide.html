NoSQL Database — 四大模型与 CAP 定理实战

一、NoSQL 四大数据模型

四种 NoSQL 模型不是四种"更快的数据库"，而是四种放弃：文档型放弃跨表 JOIN，列族型放弃临时改查询方式的自由，键值型放弃一切查询条件，图数据库放弃大规模聚合。选型就是挑一个你付得起的放弃。

模型代表产品数据结构典型场景
文档型MongoDB、DynamoDB、CouchDBJSON/BSON 文档内容管理、用户画像、产品目录
列族型Cassandra、HBase、ScyllaDB列族（Column Family）时序数据、日志、IoT 大规模写入
键值型Redis、etcd、DynamoDBKey-Value 对缓存、会话、分布式配置
图数据库Neo4j、NebulaGraph、Amazon Neptune节点 + 边 + 属性社交网络、知识图谱、推荐

NoSQL 不是"不用 SQL"

NoSQL = "Not Only SQL"，强调的是数据模型多样性和水平扩展能力，而非放弃 SQL。很多 NoSQL 数据库已支持类 SQL 查询（如 Cassandra CQL、MongoDB Aggregation Pipeline）。

  • NoSQL 四大模型要能分别举出代表产品和典型使用场景
  • 文档型 ≠ 键值型：文档型支持嵌套结构和字段级查询
  • DynamoDB 同时具备键值和文档的特性，是 AWS 最重要的 NoSQL 服务

二、文档型数据库：MongoDB 与 DynamoDB

文档型建模只有一个问题需要回答：这份数据是永远跟着父对象一起读的，还是会被单独查、被别人共享？前者 嵌入，后者 引用，其余规则都是这一条的推论。

数据建模原则

  • 嵌入优先：1:1 / 1:少量 关系嵌入子文档（减少查询次数）
  • 引用关联：1:大量 / 多:多 关系使用 ObjectId 引用（避免文档过大）
  • 文档大小上限 16MB，超过用 GridFS

    { city: "上海", street: "浦东新区2号" }
  ]
}

分区键决定的物理布局

DynamoDB 单表设计的物理分布: PK = USER#123 ─── hash ──► Partition A PK = USER#456 ─── hash ──► Partition B PK = PROD#A1 ─── hash ──► Partition A ┌───────────── Partition A ─────────────┐ ┌──── Partition B ────┐ │ PK=USER#123 SK=PROFILE │ │ PK=USER#456 SK=... │ │ PK=USER#123 SK=ORDER#2026-001 │ │ │ │ PK=USER#123 SK=ORDER#2026-002 │ │ │ │ PK=USER#123 SK=ORDER#2026-003 │ │ │ │ PK=PROD#A1 SK=INFO │ │ │ └───────────────────────────────────────┘ └─────────────────────┘ 同一 PK 的所有条目物理相邻，且按 SK 有序 一次 Query(PK="USER#123", SK begins_with "ORDER#") → 单分区内的一段连续顺序读，拿到该用户全部订单，无需 JOIN 这也是它的边界: 分区键选错 (比如用 status，只有 3 个取值) → 数据全压在 3 个分区上，形成热分区，吞吐被单分区上限卡死 需要按订单金额查 → PK/SK 帮不上忙，必须再建 GSI，等于再存一份数据

DynamoDB 核心设计

  • Partition Key（分区键）：决定数据分布，必须选高基数字段
  • Sort Key（排序键）：同一分区内的排序与范围查询
  • GSI / LSI：全局/本地二级索引，支持多维查询
  • 单表设计（Single Table Design）：将多个实体放入同一张表，通过 PK/SK 组合区分
  • 按需计费 vs 预置容量（RCU/WCU）
# DynamoDB 单表设计示例
PK              | SK                | 数据
USER#123        | PROFILE           | {name, email, ...}
USER#123        | ORDER#2024-001    | {amount, status, ...}
USER#123        | ORDER#2024-002    | {amount, status, ...}
PRODUCT#A1      | INFO              | {title, price, ...}
示例场景：某协作工具用 MongoDB 存文档，把每篇文档的全部评论以数组形式嵌入文档本身，理由是"一次查询就能拿全"。问题：热门文档累积到 4 万余条评论后，单个文档体积逼近 16MB 上限，超过后写入直接报错；即使没超限，每追加一条评论都要重写整个文档，写放大让该集合的写入延迟 P99 从 8ms 涨到 1.4s，同时任何只需要标题的列表查询也被迫把十几 MB 的评论一起读出来。方案：评论拆到独立集合，以 doc_id 建索引并按分页查询；文档内只保留最近 3 条评论和一个 comment_count 计数，用于列表页直接渲染；计数用 $inc 原子更新，避免回读。效果：文档平均体积从 6.8MB 降到 12KB，写入 P99 回到 9ms，列表接口的网络传输量下降约 99%，同时保住了列表页"一次查询直接渲染"的体验。
  • MongoDB 嵌入 vs 引用的选择标准：访问频率、数据大小、一致性要求
  • DynamoDB 单表设计是 AWS 高频考点，需理解 PK/SK 建模思路
  • MongoDB 4.0+ 支持多文档 ACID 事务，但性能代价大，不应作为常态

三、列族型数据库：Cassandra 与 HBase

LSM-Tree 把随机写变成了顺序写：先在内存里排好序，攒够一批再整块落盘。写得快的代价是同一行可能散落在多个文件里，读的时候要挨个找，所以后台必须不停地做 Compaction——写放大换来了写吞吐。

Cassandra 架构

  • 去中心化：无主节点，所有节点对等（Peer-to-Peer），使用 Gossip 协议
  • 一致性哈希：数据按 Partition Key 哈希分布到环上的虚拟节点
  • 可调一致性：每次读写可指定一致性级别（ONE / QUORUM / ALL）
  • 写入路径：Commit Log → Memtable → SSTable（LSM-Tree 结构）
  • CQL：类 SQL 查询语言，但不支持 JOIN 和子查询
-- Cassandra CQL 示例
CREATE TABLE user_events (
    user_id UUID,
    event_time TIMESTAMP,
    event_type TEXT,
    payload TEXT,
    PRIMARY KEY (user_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);

LSM-Tree 的写入路径与合并

写入 (顺序，不做原地更新): INSERT / UPDATE / DELETE │ ├──► Commit Log (顺序追加，仅用于崩溃恢复) │ ▼ ┌──────────────┐ │ Memtable │ 内存中的有序结构，写满阈值后冻结 └──────┬───────┘ │ flush (整块顺序写盘，不改动已有文件) ▼ SSTable-1 SSTable-2 SSTable-3 ... 都是不可变文件 └───────────┴───────────┘ Compaction 合并同 key 的多个版本， 丢弃被覆盖的旧值与已过期的 tombstone 读取 (要在多个地方找同一个 key): 查询 key │ ├─► Memtable 最新数据在这里 ├─► Bloom Filter 先判断"这个 SSTable 里肯定没有"，跳过大部分文件 ├─► SSTable-3 索引 可能命中 └─► SSTable-1 索引 可能命中 │ ▼ 取时间戳最大的那个版本返回 DELETE 不是真删，而是写一个 tombstone 墓碑标记， 等 Compaction 时才真正清掉。所以删得多的表，读会越来越慢。

HBase 架构

  • 基于 HDFS 的列族存储，依赖 ZooKeeper 协调
  • Region：数据按 RowKey 范围分片到不同 RegionServer
  • 列族（Column Family）：物理存储单元，同族列存于同一文件
  • 强一致性（CP 系统），适合需要强一致的大数据场景
  • 与 Hadoop/Spark 生态深度集成

Cassandra vs HBase

维度CassandraHBase
架构无中心（P2P）主从（Master + RegionServer）
CAP 倾向AP（可调）CP
写入性能极高（所有节点可写）高（需经 RegionServer）
读取性能高（单分区查询）随机读较好（Bloom Filter）
运维复杂度较低（无中心节点）较高（依赖 ZK + HDFS）
生态独立运行深度绑定 Hadoop 生态
  • Cassandra 的可调一致性（Tunable Consistency）是其最大特色
  • LSM-Tree 写入路径（Memtable → SSTable → Compaction）是底层核心
  • HBase 适合已有 Hadoop 生态的团队；Cassandra 适合需要高可用写入的独立部署

四、CAP 定理与一致性模型

CAP 里的 P 从来不是让你选的，网络分区一定会发生。真正要回答的是：分区持续的那几十秒里，你的系统宁可返回错误，还是宁可返回一份可能过时的数据。

CAP 定理

分布式系统在网络分区（P）发生时，只能在一致性（C）和可用性（A）之间二选一：

  • C（Consistency）：所有节点看到的数据一致（线性一致性）
  • A（Availability）：每个请求都能收到非错误响应
  • P（Partition Tolerance）：网络分区时系统仍能运行

网络分区在分布式系统中不可避免，因此实际选择是 CP 或 AP。

各数据库的 CAP 定位

定位代表数据库特点
CPHBase、etcd、ZooKeeper、MongoDB（默认）网络分区时牺牲可用性保数据一致
APCassandra、DynamoDB、CouchDB网络分区时牺牲一致性保服务可用

一致性模型谱系

  • 强一致性（Linearizability）：写入立即对所有节点可见 → etcd、ZooKeeper
  • 顺序一致性：操作顺序一致但不要求实时 → ZAB 协议
  • 因果一致性：有因果关系的操作保序 → MongoDB（causal consistency sessions）
  • 最终一致性：无时间保证，最终所有副本一致 → Cassandra（ONE）、DynamoDB
强一致 ← 顺序一致 ← 因果一致 ← 最终一致 （从左到右，一致性递减，可用性递增）

一致性哈希环与 QUORUM 读写

Cassandra 的 Ring (RF=3，每条数据存 3 份): Node A ╱ ╲ Node E Node B │ │ Node D ──────── Node C key="user:42" ── hash ──► token 落在 A 与 B 之间 │ ▼ 归属节点 = 顺时针第一个 = B 副本 = B, C, D (顺时针再取 RF-1 个) 写入 (CL=QUORUM，需要 2/3 确认): 客户端 ──► 任意节点当 Coordinator │ 并行发给 B、C、D ├──► B ✓ 已确认 ├──► C ✓ 已确认 ── 2 票达成 QUORUM，立即返回成功 └──► D ✗ 超时/宕机 ── 写进 hinted handoff，等它回来补 读取 (CL=QUORUM，需要 2/3 应答): 读 B (完整数据) + 读 C (仅摘要 digest) │ ├── 摘要一致 → 直接返回 └── 摘要不一致 → Read Repair: 取时间戳最新的版本返回， 并把落后的副本就地修好 W + R ＞ RF ⇒ 读一定能撞上最新写入的那份 2 + 2 ＞ 3 所以 RF=3 时 QUORUM 读写组合是强一致的 1 + 1 ＜ 3 CL=ONE 则快但可能读到旧值

最终一致性的冲突解决

  • Last Write Wins（LWW）：时间戳最大的写入胜出（Cassandra 默认）
  • 向量时钟（Vector Clock）：检测并发冲突，交给应用层决策（Riak）
  • CRDT（Conflict-free Replicated Data Types）：数据结构自动合并（Redis CRDT、Riak）
  • 读修复（Read Repair）：读取时发现不一致则自动修复
  • CAP 定理的本质：网络分区是"必然"而非"选择"，核心是 C vs A 的取舍
  • PACELC 是 CAP 的扩展：无分区时 Latency vs Consistency 的额外权衡
  • 最终一致性 ≠ 不一致，是"给定足够时间后一定一致"

五、键值型数据库：Redis 与 etcd

Redis 和 etcd 都叫键值存储，但一个的设计目标是每秒十万次读写、丢一点无所谓，另一个是每秒几千次、一个字节都不能丢。把它们放在同一个类目里比较，本身就容易选错。

Redis 概览

  • 内存数据结构存储，支持多种数据类型（String/Hash/List/Set/ZSet/Stream）
  • 单线程命令处理（6.0+ 多线程 I/O），避免锁竞争
  • 持久化：RDB 快照 + AOF 追加日志
  • 集群模式：16384 个 Slot 哈希分片
  • 典型用途：缓存、会话、排行榜、消息队列、分布式锁

etcd 概览

  • 基于 Raft 共识的分布式键值存储
  • 强一致性：所有读写经过 Leader，线性一致
  • Watch 机制：监听 Key 变化事件
  • Lease（租约）：TTL 机制实现服务注册与心跳
  • Kubernetes 的核心存储组件

Redis vs etcd

维度Redisetcd
一致性最终一致（异步复制）强一致（Raft 协议）
性能极高（10万+ QPS/节点）中等（数千~万 QPS）
数据模型丰富数据结构纯 Key-Value
典型场景缓存、高速数据处理配置管理、服务发现、分布式协调
数据量GB~TB 级建议 <8GB（存元数据）
  • Redis 单线程不代表慢 — 瓶颈在网络 I/O 而非 CPU
  • etcd 不适合存大量数据，设计目标是少量关键元数据的强一致存储
  • Kubernetes 所有集群状态（Pod/Service/ConfigMap）都存在 etcd 中

六、NoSQL 数据建模模式

关系型建模先问"有哪些实体"，NoSQL 建模先问"有哪些查询"。反范式化 不是偷懒，而是把 JOIN 的代价从每一次读，挪到了每一次写——读多写少时这笔账划算，反过来就不划算。

反范式化设计

NoSQL 的核心建模原则是"按查询建模"而非"按实体建模"：

  • 冗余存储：为不同查询模式存储同一数据的不同视图
  • 宽行模式：将相关数据合并为单行/文档，一次读取所有所需数据
  • 预计算：写入时计算聚合值，避免读时聚合

范式化（RDBMS 思维）→ 反范式化（NoSQL 思维）的核心转变：读优化 > 写优化 > 存储优化

常见建模模式

模式描述适用场景
Embedding（嵌入）将子实体嵌入父文档1:1 / 1:少量关系
Bucketing（分桶）将多条记录聚合为一个文档时序数据、事件日志
Computed Pattern写入时预计算结果实时统计、排行榜
Polymorphic Pattern同一 Collection 存不同类型文档多态实体（产品变体）
Outlier Pattern异常大的文档单独处理热门用户的关注列表
  • NoSQL 建模核心问题：先确定查询模式，再设计数据模型
  • 冗余不是"坏的" — NoSQL 用空间换时间、用写入冗余换读取效率
  • 需要展示从 RDBMS 思维到 NoSQL 思维的转变能力

七、SQL vs NoSQL 选型决策

选 SQL 还是 NoSQL，别从"数据量大不大"开始问，从"我的查询模式在写代码之前是不是已经定死了"开始问。定死了，NoSQL 给你可预测的性能；没定死，SQL 的即席查询能力值回票价。

决策矩阵

决策因素选 SQL (RDBMS)选 NoSQL
数据结构结构化、Schema 稳定半结构化/非结构化、Schema 灵活
查询模式复杂 JOIN / 聚合 / Ad-hoc 查询主键查询、预定义查询模式
一致性强 ACID 事务最终一致性可接受
扩展方式垂直扩展为主水平扩展（分布式优先）
写入量中等写入量极高写入量（日志、IoT、事件）
团队经验SQL 生态成熟特定 NoSQL 产品经验

混合使用（Polyglot Persistence）

现代架构中很少只用一种数据库，而是根据场景选择最合适的：

用户数据 → PostgreSQL   |   会话/缓存 → Redis   |   日志/事件 → Cassandra

搜索 → Elasticsearch   |   文件元数据 → MongoDB   |   关系图谱 → Neo4j

挑战：数据一致性（跨库事务）、运维复杂度、团队学习成本。

先写查询清单，再定分区键

把所有会上线的访问模式列出来，逐条验证能否只用 PK/SK 或分区键命中单个分区。列不出来，说明还不该上 NoSQL。

分区键必须高基数且分布均匀

用 user_id、order_id 这类天然分散的值。用 status、region、date 做分区键，几乎必然出现热分区。

跨库同步走 CDC，不走双写

应用里同时写 MySQL 和 Elasticsearch，只要有一边失败就永久不一致。从 binlog 捕获变更再投递，失败可重放。

别把 NoSQL 当"不用设计的数据库"

Schema-less 只是没有强制校验，不代表没有结构。字段命名和类型不统一的集合，半年后没有人敢写查询。

别用最终一致性存钱和库存

余额、扣减这类不允许出现中间态的数据，放在有事务的关系库里，NoSQL 只承接读多写少的派生视图。

别为了"技术先进"引入第五种数据库

多存储确实是主流，但每多一种就多一套备份、监控、扩容和故障预案。能用现有组件解决的，先别开新的。

示例场景：某内容平台把互动流水写进 Cassandra，分区键选了 content_id，RF=3、CL=QUORUM。问题：一条爆款内容三天内累计约 260 万条互动，全部落在同一个分区上，该分区所在的三个节点磁盘写入被打满，读取时单分区扫描耗时超过 8s，并触发多次 tombstone 超限异常；同时这三台机器的负载是集群其他节点的 6 倍以上。方案：分区键改成 content_id + 日期桶（(content_id, yyyymmdd)），把单个热点内容摊到按天的多个分区；查询侧改为按天并行取近 N 天再合并；清理逻辑由逐条 DELETE 改为按 TTL 让整个 SSTable 自然过期，避免堆积墓碑。效果：单分区最大行数从 260 万降到 9 万量级，热点查询耗时从 8s 降到 120ms，集群节点负载差异收敛到 1.3 倍以内。
  • 不要一刀切 — 展示"按需选型"的思维，解释选择的理由
  • Polyglot Persistence 是微服务架构的标准实践
  • "为什么不用 MongoDB 替代 MySQL？"的标准回答：事务、JOIN、生态

🎯 Q&A

Q1：CAP 定理的核心含义是什么？为什么不能同时满足三者？

CAP 定理指出：分布式系统在网络分区（P）发生时，无法同时保证一致性（C）和可用性（A）。因为网络分区时，节点间通信中断，如果要保证一致性就必须拒绝响应（牺牲可用性），如果要保证可用性就必须允许各节点独立响应（可能数据不一致）。在没有分区的正常情况下可以同时满足 CA，但网络分区不可避免，所以实际系统需要在 CP 和 AP 之间权衡。PACELC 扩展了 CAP：即使无分区（E=Else），也需要在 Latency 和 Consistency 之间权衡。

Q2：MongoDB 和 MySQL 各自在什么场景下更有优势？

MySQL 优势场景：① 需要复杂 JOIN 和事务的 OLTP 系统（电商/金融）；② Schema 稳定、数据高度结构化；③ 需要强一致性 ACID 保证；④ 团队 SQL 经验丰富。MongoDB 优势场景：① Schema 频繁变化（敏捷开发/原型）；② 数据天然是文档结构（CMS/用户画像/产品目录）；③ 需要水平扩展处理大量写入；④ 嵌套数据结构无需拆表 JOIN。核心区别：MySQL 是"Schema-first"，MongoDB 是"Query-first"。

Q3：Cassandra 如何实现高可用写入？一致性如何保证？

Cassandra 采用无中心 P2P 架构，所有节点都可接受写入（无单点瓶颈）。数据通过一致性哈希分布到 Ring 上，每条数据有 N 个副本（Replication Factor）。写入时通过 Coordinator 节点并行写入所有副本节点，根据一致性级别（CL）决定需要几个节点确认：ONE=1个、QUORUM=N/2+1、ALL=N个。例如 RF=3, CL=QUORUM 时，写入需 2 个节点确认，即使 1 个节点故障仍可写入。这就是"可调一致性"——同一集群中不同查询可选择不同的一致性级别。

Q4：什么是 DynamoDB 的单表设计？为什么推荐？

单表设计是将多种实体类型（用户、订单、产品等）放在同一张 DynamoDB 表中，通过精心设计 Partition Key 和 Sort Key 的组合来区分实体。例如 PK=USER#123, SK=PROFILE 存用户信息；PK=USER#123, SK=ORDER#001 存该用户的订单。推荐原因：① DynamoDB 不支持 JOIN，单表可用 Query 操作一次获取一个用户的所有相关数据；② 减少表数量降低成本（DynamoDB 按表计费容量）；③ 利用 Sort Key 实现范围查询和排序。缺点是建模复杂，需要预先明确所有访问模式。

Q5：最终一致性系统中如何处理数据冲突？

主要策略：① Last Write Wins（LWW）— 用时间戳判断，最新写入覆盖旧值，简单但可能丢失并发更新（Cassandra 默认）；② Vector Clock — 每个节点维护逻辑时钟向量，可检测并发冲突但无法自动解决，需应用层策略（Riak 经典方案）；③ CRDT — 设计特殊数据结构使并发操作可交换/幂等，自动合并无冲突（如计数器、集合、LWW-Register）；④ 读修复 + 反熵 — 读取时比较副本版本并修复不一致，后台定期扫描同步。实际系统通常组合使用这些策略。

Q6：NoSQL 里的"二级索引"为什么经常不好用？该怎么绕过去？

根因是分布式分片架构和二级索引的目标天然打架。数据是按分区键切开分布在各节点上的，而二级索引查的是非分区键的字段，系统无从知道满足条件的数据落在哪些分片上。于是只有两种实现方式，各有各的毛病。本地索引（Cassandra 的 SASI、MongoDB 分片集合上的普通索引）在每个分片内部各建一份，查询时必须扇出到所有分片、各自扫一遍再归并，分片越多单次查询越慢，而且延迟由最慢的那个分片决定。全局索引（DynamoDB 的 GSI）实质是再存一份以索引字段为分区键的数据副本，查询确实快，但它是异步更新的，写完主表后读 GSI 有可能读不到，而且要额外付一份存储和写入容量的钱。实践上的绕法有三条：第一，把最重要的查询做进主键设计，比如 DynamoDB 用组合 SK、Cassandra 为同一份数据按不同主键建多张表，靠写入时冗余换读取时确定性；第二，确实需要多维、任意组合的过滤时，把这类查询整体外移到 Elasticsearch 或 ClickHouse，用 CDC 保持同步，让 NoSQL 只负责它擅长的按键读写；第三，如果发现自己在不停加二级索引，通常是选型信号——说明查询模式其实并不固定，这类业务本来更适合关系型数据库。
