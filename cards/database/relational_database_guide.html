Relational Database — MySQL / PostgreSQL 核心原理与实战

一、MySQL 与 PostgreSQL 对比

MySQL 与 PostgreSQL 的分歧从一个决定开始：行的旧版本放在哪。InnoDB 把它挪进 Undo Log，PostgreSQL 就把它留在表里——之后所有差异（回滚快慢、要不要 VACUUM、会不会表膨胀）都是这一个选择的连锁反应。

架构差异

对比维度MySQL (InnoDB)PostgreSQL
存储引擎可插拔引擎（InnoDB 为默认）统一存储引擎（Heap + TOAST）
MVCC 实现Undo Log（回滚段）Heap Tuple 多版本（在表内存多个版本）
索引结构聚簇索引（数据存于主键 B+ Tree 叶子）堆表 + 独立 B-Tree 索引
并发控制行级锁 + Gap Lock行级锁 + SSI（可串行化快照隔离）
复制方式基于 Binlog（行/语句/混合）基于 WAL（物理复制）+ 逻辑复制
JSON 支持JSON 类型（5.7+）JSONB（二进制存储，支持索引）
扩展性有限（UDF/Plugin）极强（自定义类型/操作符/索引/FDW）
全文检索基础 FULLTEXT内置 tsvector + GIN 索引

选型建议

选 MySQL

  • Web 应用高并发读写（互联网典型 OLTP）
  • 团队 MySQL 经验丰富、生态工具链完善
  • 云托管成本敏感（RDS MySQL 最成熟）

选 PostgreSQL

  • 复杂查询/分析（窗口函数/CTE/递归查询）
  • 需要 JSONB、GIS（PostGIS）、向量（pgvector）
  • 强一致性与高级事务隔离要求
  • MySQL InnoDB 的聚簇索引 vs PostgreSQL 的堆表是最核心的架构差异
  • PostgreSQL 的 MVCC 不用 Undo Log 但需要 VACUUM 清理旧版本
  • MySQL 的 Binlog 可实现 CDC，PostgreSQL 用 WAL + 逻辑解码

二、B+ Tree 索引原理

B+ 树 之所以能当默认索引，是因为它用同一个结构解决了两件事：内部节点只放键，一个 16KB 页能塞下上千个，三四层就够索引上亿行；叶子之间又串成双向链表，范围扫描不用回头爬树。

B+ Tree 结构

B+ Tree 是关系数据库最核心的索引结构，特点：

  • 所有数据存于叶子节点，内部节点只存键值和子节点指针
  • 叶子节点通过双向链表连接，支持范围扫描
  • 每个节点大小 = 一个磁盘页（通常 16KB），最小化 I/O
  • 树高度通常 3~4 层，可索引数十亿行（单次查询 3~4 次 I/O）

B+ 树的层级与叶子链

InnoDB 主键索引 (聚簇索引)，一页 16KB: ┌──────────────────────┐ Root │ [ 100 | 500 | 900 ] │ 1 页，常驻内存 └───┬──────┬───────┬───┘ ┌─────────┘ │ └─────────┐ ▼ ▼ ▼ ┌───────────┐ ┌───────────┐ ┌───────────┐ Internal │ [110|180] │ │ [520|660] │ ... │ [910|970] │ 约 1200 项/页 └──┬─────┬──┘ └─────┬─────┘ └─────┬─────┘ │ │ │ │ ▼ ▼ ▼ ▼ ┌──────┐┌──────┐ ┌──────┐ ┌──────┐ Leaf │ 行数据│││行数据│ │ 行数据│ ... │ 行数据│ 叶子直接存整行 └──┬───┘└──┬───┘ └──┬───┘ └──┬───┘ └──►────┴──►──────┴────► ... ────►┘ 叶子之间双向链表，范围扫描顺序走 高度 3 层 ≈ 1200 × 1200 × 每页若干行 ≈ 上亿行， 单点查询只需 3 次页访问，其中前两层通常已在 Buffer Pool 里。 二级索引的回表: SELECT * FROM orders WHERE user_id = 100 idx_user_id 叶子: [user_id=100 → pk=8821] │ ▼ 拿主键再查一次 主键索引叶子: [pk=8821 → 完整行数据] 两棵 B+ 树，两次查找。覆盖索引 (查询列全在索引里) 可以省掉第二次。

聚簇索引 vs 非聚簇索引

类型MySQL InnoDBPostgreSQL
聚簇索引主键 B+ Tree 叶子存完整行数据无聚簇索引（堆表无序存储）
二级索引叶子存主键值（需回表）叶子存 CTID（堆表物理位置）
回表代价二级索引 → 主键索引 → 数据（两次 B+ Tree）索引 → 堆表（一次跳转但可能随机 I/O）

覆盖索引与索引优化

  • 覆盖索引（Covering Index）：查询所需的所有列都在索引中，无需回表
  • 联合索引：遵循最左前缀原则 — INDEX(a,b,c) 支持 (a)、(a,b)、(a,b,c) 查询
  • 索引下推（ICP）：MySQL 5.6+ 在索引扫描阶段直接评估 WHERE 条件
  • 前缀索引：对长字符串只索引前 N 个字符，节省空间
-- 覆盖索引示例
CREATE INDEX idx_cover ON orders(user_id, status, amount);
SELECT status, amount FROM orders WHERE user_id = 100;
-- 只需扫描索引，不回表
  • B+ Tree 高度 3~4 层即可覆盖亿级数据是高频考点
  • MySQL 回表：二级索引 → 拿主键 → 主键索引 → 数据，理解这个链路
  • 联合索引最左前缀、覆盖索引是 SQL 优化第一步

三、查询优化与 EXPLAIN

读执行计划的第一件事不是看耗时，是看 扫描行数 和最终返回行数的比值——扫一百万行只返回十行，说明过滤条件没落到索引上，换再快的机器也只是在更快地浪费 I/O。

EXPLAIN 输出关键字段

字段含义关注点
type访问类型system > const > eq_ref > ref > range > index > ALL（越左越好）
key实际使用的索引NULL 表示全表扫描
rows预估扫描行数越少越好
Extra额外信息Using index（覆盖）、Using filesort（需优化）、Using temporary（需优化）
filtered过滤百分比值越大说明索引选择性越好

慢查询常见原因与优化

索引失效场景

  • 对索引列使用函数：WHERE YEAR(create_time) = 2024 → 改为范围查询
  • 隐式类型转换：WHERE varchar_col = 123 → 加引号
  • LIKE 左模糊：WHERE name LIKE '%abc' → 考虑全文索引
  • OR 条件未全部有索引 → 拆为 UNION
  • NOT IN / NOT EXISTS 可能导致全表扫描

JOIN 优化

  • 小表驱动大表（MySQL 优化器通常自动处理）
  • 确保 JOIN 列都有索引
  • 避免在 JOIN 中使用 !=、函数
联合索引按"等值列在前、范围列在后"排

WHERE a=? AND b>? ORDER BY c 应建 (a,b) 或 (a,c,b)。范围列后面的列无法再用于索引定位，把它放最后才不浪费。

先看 rows，再看 type

预估扫描行数与返回行数的比值最能说明问题。小表全表扫描本来就比走索引快，type=ALL 未必要优化。

深分页改成游标翻页

LIMIT 100000,20 要先丢弃十万行。改成 WHERE id > :last_id ORDER BY id LIMIT 20，代价与页码无关。

别在索引列上套函数

WHERE DATE(created_at)='2026-01-01' 会让索引失效。改成 created_at >= '2026-01-01' AND created_at < '2026-01-02'，或建函数索引。

别让字符串列和数字比较

WHERE phone = 13800000000 会触发隐式类型转换，整列被迫转成数字后逐行比对，索引直接不用了。加引号即可。

别为每个 WHERE 列各建一个索引

单列索引越多，写入时要维护的 B+ 树越多，优化器还可能选错。多数场景一两个精心设计的联合索引就够了。

示例场景：某订单列表页的 SQL 是 SELECT * FROM orders WHERE merchant_id=? AND status='paid' ORDER BY created_at DESC LIMIT 20，表约 4200 万行，只有 merchant_id 的单列索引。问题：大商户单个 merchant_id 命中约 90 万行，索引定位后仍要回表 90 万次再排序，EXPLAIN 里 Extra 是 Using filesort，单次查询约 6.4s，高峰期把从库拖到负载 20 以上。方案：建联合索引 (merchant_id, status, created_at DESC)，让过滤和排序都走索引；把 SELECT * 收窄到页面真正用到的 7 个列，使索引接近覆盖。效果：扫描行数从 90 万降到 20，Extra 变为 Using index condition，单次查询降到 8ms，从库负载回落到 2 以内。

PostgreSQL 特有优化

  • EXPLAIN (ANALYZE, BUFFERS) — 显示实际执行时间和缓冲区命中
  • Partial Index：CREATE INDEX ON orders(status) WHERE status = 'pending'
  • BRIN 索引：适合有序数据（时间戳/自增 ID），极小存储
  • 并行查询：PostgreSQL 自动为大表扫描启用多工作进程
  • EXPLAIN type 字段从 ALL → const 的优化路径是经典考点
  • 索引失效的 5 个常见场景必须能举例说明
  • PostgreSQL 的 Partial Index 和 BRIN 是其独有的优化利器

四、事务 ACID 与 MVCC

MVCC 的本质是用空间换并发：读之所以不用加锁，是因为它读的是属于自己那一刻的旧版本，而不是当前值。所以"读到的数据不是最新的"不是 bug，是设计。

ACID 特性

特性含义实现机制
Atomicity（原子性）事务要么全部成功，要么全部回滚Undo Log（MySQL）/ WAL（PG）
Consistency（一致性）事务前后数据满足所有约束约束检查 + 应用逻辑
Isolation（隔离性）并发事务互不干扰MVCC + 锁
Durability（持久性）提交后数据不丢失Redo Log / WAL + fsync

隔离级别

隔离级别脏读不可重复读幻读说明
Read Uncommitted✅✅✅几乎不用
Read Committed❌✅✅PostgreSQL 默认
Repeatable Read❌❌⚠️ *MySQL InnoDB 默认
Serializable❌❌❌最安全但性能最低

* MySQL RR 通过 Gap Lock 部分解决幻读（范围锁），但非标准方式。

版本链与快照读

InnoDB: 一行的版本链挂在 Undo Log 上 聚簇索引里的当前行 ┌────────────────────────────────────────┐ │ id=1 balance=300 trx_id=88 roll_ptr │ └───────────────────────────┬────────────┘ ▼ ┌──────────────────────┐ Undo Log │ balance=200 trx_id=75│ └──────────┬───────────┘ ▼ ┌──────────────────────┐ │ balance=100 trx_id=62│ └──────────────────────┘ 事务开始时拍下 Read View: m_ids = [88, 91] 当前活跃(未提交)事务 min_trx_id = 88 max_trx_id = 92 creator = 91 沿版本链自上而下判断可见性: trx_id = 88 → 在 m_ids 里，未提交，不可见，继续往下 trx_id = 75 → 小于 min_trx_id，已提交，可见 → 返回 balance=200 RC : 每条 SQL 都重新拍一次 Read View → 能读到别人刚提交的，故不可重复读 RR : 事务内只拍一次并复用 → 整个事务看到同一份快照 PostgreSQL: 旧版本直接留在堆表里 Heap Page ┌──────────────────────────────────────────┐ │ tuple A xmin=62 xmax=75 balance=100 │ 已被 75 删除 │ tuple B xmin=75 xmax=88 balance=200 │ 已被 88 删除 │ tuple C xmin=88 xmax=0 balance=300 │ 当前有效版本 └──────────────────────────────────────────┘ │ ▼ 死元组越堆越多 VACUUM 回收空间，否则表膨胀、索引变胖、顺序扫描变慢 代价对调: InnoDB 回滚要走 Undo 反向补偿，PG 回滚只需把事务标记为 abort； 但 PG 必须长期供养 autovacuum，InnoDB 不用。

MVCC 实现对比

MySQL InnoDB MVCC

  • 每行记录隐藏列：trx_id（最后修改事务 ID）、roll_pointer（指向 Undo Log）
  • Undo Log 形成版本链
  • Read View：活跃事务列表快照
  • RC：每条 SQL 创建新 Read View
  • RR：事务首次读创建 Read View 并复用

PostgreSQL MVCC

  • 每行 Tuple 携带 xmin（创建事务 ID）和 xmax（删除事务 ID）
  • 旧版本直接存在堆表中（不使用 Undo Log）
  • 需要 VACUUM 回收死亡 Tuple
  • 优点：无需 Undo 管理，回滚即时
  • 缺点：表膨胀（bloat），需定期 VACUUM
  • MySQL RR 级别通过 MVCC + Gap Lock 实现"近似"解决幻读
  • MySQL 的 Undo Log vs PostgreSQL 的多版本堆存储是经典对比题
  • PostgreSQL 的 VACUUM 机制（autovacuum 参数调优）是运维重点

五、连接池与读写分离

连接池不是为了"多接一点请求"，恰恰相反，它是为了不让数据库同时干太多事——并发连接数超过 CPU 能真正并行处理的量之后，吞吐不升反降，这条曲线在压测里几乎每次都能复现。

连接池原理

数据库连接的创建代价高昂（TCP 三次握手 + 认证 + 分配内存），连接池通过复用已有连接降低开销。

常见连接池

连接池语言/平台特点
HikariCPJava高性能、Spring Boot 默认、字节码优化
PgBouncerPostgreSQL轻量级代理、支持 Transaction Pooling
ProxySQLMySQL查询路由/缓存/读写分离/故障转移
DruidJava阿里开源、监控完善、SQL 防火墙

关键参数

  • maxPoolSize：最大连接数 ≈ CPU 核心数 × 2 + 有效磁盘数
  • minIdle：最小空闲连接数
  • connectionTimeout：获取连接超时时间
  • maxLifetime：连接最大存活时间（避免数据库端超时断开）
示例场景：某订单服务部署 16 个 Pod，每个 Pod 的 HikariCP 都按"越多越保险"配了 maximumPoolSize=100，后端是一台 8 核的 MySQL。问题：大促流量上来后，数据库端并发连接达到 1600，线程上下文切换和行锁等待急剧放大，CPU 有 60% 以上耗在系统态，吞吐从平峰的 4200 QPS 掉到 1100 QPS，接口平均耗时从 25ms 涨到 900ms——典型的"连接越多越慢"的过载下降曲线。方案：按 核心数 × 2 + 有效磁盘数 把单 Pod 池大小降到 12（全局约 192 个连接），同时把 connectionTimeout 设为 3 秒让排队请求快速失败而不是无限堆积；在数据库前加一层 PgBouncer 式的连接复用（MySQL 侧用 ProxySQL）承接突发。效果：数据库端并发连接从 1600 降到 190，吞吐回升到 4600 QPS，平均耗时降到 21ms，且高峰期不再出现雪崩式的连接等待。

读写分离架构

应用 → Proxy (ProxySQL/PgBouncer) → 写请求 → Master
应用 → Proxy → 读请求 → Replica 1 / Replica 2

主从复制延迟问题

  • 问题：写入主库后立即读从库可能读不到最新数据
  • 方案一：关键读走主库（强制路由 /*master*/）
  • 方案二：半同步复制（semi-sync）— 至少一个从库确认收到才返回
  • 方案三：监控复制延迟（Seconds_Behind_Master），超过阈值切回主库
  • HikariCP 最大连接数的经验公式：connections = CPU cores × 2 + disk spindles
  • 主从延迟是分布式系统经典问题，需给出至少两种解决方案
  • PgBouncer 的 Transaction Pooling vs Session Pooling 模式区别

六、分区与分库分表

分区 是同一个库里换个放法，分库分表 是把数据搬到别的机器上。前者改一条 DDL 就完事，后者要重写跨库 JOIN、分布式事务和全局 ID，代价差着一个数量级——所以先把分区、归档、索引都试过，再考虑分片。

分区（Partitioning）

单表数据量过大时，将表按规则拆分为多个物理分区：

分区类型适用场景示例
Range时间序列数据按月份分区 orders_2024_01
Hash均匀分布数据按 user_id 哈希取模
List枚举值分类按 region 分区
Composite多维分区先按日期 Range，再按 user_id Hash
-- PostgreSQL 原生分区示例
CREATE TABLE orders (
    id BIGINT, user_id INT, created_at DATE, amount DECIMAL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

分区表与分片集群的数据分布

分库分表（Sharding）

水平拆分策略

  • Hash 取模：shard = hash(user_id) % N，均匀分布但扩容困难
  • 范围分片：按 ID 范围分片，扩容方便但易热点
  • 一致性哈希：扩容时只迁移部分数据，减少重分布

中间件方案

方案类型特点
ShardingSphereJava 生态功能全面（分库分表 + 读写分离 + 分布式事务）
VitessMySQL ProxyYouTube 开源，云原生，支持 K8s
CitusPG 扩展PostgreSQL 原生分布式扩展

分库分表的挑战

  • 跨分片 JOIN → 应用层聚合或冗余数据
  • 分布式事务 → 2PC / TCC / SAGA
  • 全局唯一 ID → Snowflake / UUID / 数据库序列
  • 数据迁移与扩容 → 双写方案 / 影子表
  • 分区是单库内优化，分库分表是跨多个数据库实例的水平扩展
  • 分片键（Sharding Key）选择直接决定数据分布均匀性和查询效率
  • 分库分表后的跨分片查询、分布式事务、全局 ID 是三大经典难题

七、高可用与灾备

高可用方案的差别，最后都落到同一个问题上：主库已经回包、但还没同步出去的那几个事务，切换时你打算认还是不认——RPO 就是这句话的量化版本。

RPO 与 RTO

  • RPO（Recovery Point Objective）：能容忍丢失多少数据 → 决定备份频率与复制策略
  • RTO（Recovery Time Objective）：能容忍多长恢复时间 → 决定 HA 方案选择
  • 同步复制：RPO=0 但性能降低；异步复制：高性能但可能丢数据
  • MySQL MGR 使用 Paxos 实现多主强一致，与传统主从的本质区别
  • PostgreSQL 高可用首选 Patroni + etcd
  • RPO/RTO 是灾备方案设计的核心指标，需量化讨论

🎯 Q&A

Q1：MySQL InnoDB 中，为什么推荐用自增主键而非 UUID？

InnoDB 使用聚簇索引，数据按主键顺序物理存储。自增主键保证新数据顺序追加到 B+ Tree 尾部，页分裂少、写入性能高。UUID 是随机值，插入位置随机导致频繁页分裂、碎片增多、写放大严重。在高并发写入场景下，自增主键的写入吞吐量可高出 UUID 方案 3~5 倍。如果需要分布式唯一 ID，推荐 Snowflake 等趋势递增算法。

Q2：EXPLAIN 中 type=ALL 说明什么？如何优化？

type=ALL 表示全表扫描，是最差的访问类型。优化思路：① 检查 WHERE 条件列是否有索引 → 创建合适的索引；② 检查是否有索引失效情况（函数包装、隐式转换、左模糊 LIKE）→ 改写 SQL；③ 检查 rows 预估值 → 如果表本身很小，ALL 可能是优化器正确的选择（全表扫描比走索引更快）；④ 使用 FORCE INDEX 提示优化器。目标是将 type 优化到 ref/range/const 级别。

Q3：MySQL 的 MVCC 在 RR 隔离级别下如何解决幻读？

MySQL RR 通过两种机制协同：① MVCC 的 Read View — 快照读（普通 SELECT）使用事务首次读时创建的一致性视图，后续读不会看到新插入的行；② Gap Lock — 当前读（SELECT ... FOR UPDATE / INSERT）会锁定索引范围间隙，阻止其他事务在该范围内插入新记录。注意：仅快照读时通过 MVCC 避免幻读，当前读需要 Gap Lock 配合。这与 SQL 标准定义不同，标准 RR 不要求解决幻读。

Q4：分库分表后如何解决跨分片查询问题？

方案有多种：① 合理选择分片键 — 让高频查询集中在单分片内完成；② 冗余数据 — 将需要 JOIN 的维度表冗余到每个分片；③ 全局表 — 小型字典表在所有分片保持完整副本；④ 应用层聚合 — 多分片查询后在应用层合并排序；⑤ CQRS 模式 — 写入走分片，查询走独立的汇总库（如 Elasticsearch/ClickHouse）。核心原则是"尽量单分片查询，不可避免时优先选择异步汇总而非实时跨片"。

Q5：如何设计数据库连接池大小？连接数过多会有什么问题？

经验公式：maxPoolSize ≈ CPU核心数 × 2 + 有效磁盘数。例如 4 核 SSD 服务器约 9~10 个连接即可达到最大吞吐。连接过多的问题：① 上下文切换开销急剧增加（线程/进程调度）；② 内存消耗（每连接约占 5~10MB）；③ 锁竞争加剧，吞吐量反而下降（经典的"过载下降"曲线）。PostgreSQL 还需注意进程模型下连接更昂贵，建议用 PgBouncer 做连接复用（Transaction Pooling 模式可支持数千应用连接映射到少量数据库连接）。

Q6：给一张几千万行的在线表加字段或加索引，为什么可能拖垮服务？怎么做才安全？

风险来自两处。其一是元数据锁：MySQL 执行 DDL 时要先拿到表级 MDL 写锁，而这把锁必须等表上所有已开始的事务结束。只要有一个忘了提交的长事务，DDL 就会一直等待，而它后面所有新到的查询又会排在这把锁后面，几秒之内连接池就被占满，表现出来是整张表"突然全部超时"。其二是数据重建：早期版本或某些操作（改列类型、加全文索引等）需要重建整张表，几千万行会产生长时间的磁盘和 I/O 压力，还会让主从复制延迟拉长到分钟级。安全做法有三层：第一，先在 information_schema.innodb_trx 里确认没有跑了很久的事务，并给 DDL 设 lock_wait_timeout，宁可失败重试也不要无限等待；第二，优先使用 MySQL 8.0 的 ALGORITHM=INPLACE, LOCK=NONE 或 Instant DDL（加列到末尾只改元数据，毫秒完成），PostgreSQL 则用 CREATE INDEX CONCURRENTLY 和"加列不带默认值再分批回填"的两步法；第三，无法在线完成时改用 gh-ost 或 pt-online-schema-change 这类影子表工具，它们建一张新表、按 binlog 追平增量、最后原子改名，全程只有改名那一刻的锁。最后一条通用纪律：所有 DDL 放在低峰期执行，并全程盯住复制延迟。
