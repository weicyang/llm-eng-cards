B05 · 时序数据库

Time Series Database — 时间序列数据的存储、查询与可视化

一、时序数据模型

时序数据库的所有优化都来自同一个观察：相邻两个点的时间戳几乎等距、数值几乎不变。把这两个"几乎"编码掉，一个原本 16 字节的样本就能压到一两个字节——它不是存得更聪明，是干脆不存那些可以推出来的东西。

核心概念

时序数据是以时间戳为主键的有序数据点序列：

概念含义示例
Measurement数据表/指标名称cpu_usage、http_requests
Tag索引维度（低基数字符串）host=server01、region=us-east
Field实际数值（不索引）value=85.5、latency=120
Timestamp数据点时间2024-01-15T10:30:00Z
Series唯一时间序列 = Measurement + Tag 组合cpu_usage{host=s01,cpu=0}

时序数据特点

  • 追加写入：绝大多数操作是 INSERT，极少 UPDATE/DELETE
  • 时间有序：数据天然按时间排列，最新数据最有价值
  • 高写入量：IoT / 监控场景可达百万数据点/秒
  • 时间范围查询：查询通常带有时间窗口（最近 1 小时/7 天）
  • 降采样：旧数据可聚合为粗粒度（5 分钟平均值 → 1 小时平均值）
  • 自动过期：数据有生命周期，过期后自动删除（Retention Policy）
  • Tag vs Field 的区别：Tag 被索引可高效过滤，Field 不索引但存实际值
  • 时序数据库的写入优化核心：批量写入 + LSM-Tree / 列式压缩
  • "高基数（High Cardinality）"问题：Tag 值种类过多导致 Series 爆炸

二、InfluxDB

TSM 引擎本质是给 LSM-Tree 换了一套按列组织的编码：时间戳归一列、数值归一列。同一列里的数据长得像，压缩算法才有发挥空间，这也是行存数据库存时序天生吃亏的原因。

架构与存储引擎

  • TSM（Time-Structured Merge Tree）：专为时序数据设计的列式存储引擎
  • 写入路径：WAL → 内存缓存（Cache）→ 刷盘为 TSM 文件 → 后台 Compaction
  • 高压缩率：时间戳差分编码 + 数值 Gorilla 编码 + Snappy 压缩
  • InfluxDB 3.x（IOx）基于 Apache Arrow + DataFusion + Parquet 全面重写

TSM 的写入路径与压缩编码

写入路径: 批量写入点 (measurement + tags + fields + ts) │ ├──► WAL 顺序追加 崩溃后可重放 │ ▼ ┌────────────────────┐ │ Cache (内存) │ 按 series key 分组，各自保持时间有序 └─────────┬──────────┘ │ 达到 cache-snapshot 阈值 ▼ ┌──────────────────────────────────────────┐ │ TSM 文件 (不可变，列式布局) │ │ │ │ Index Block series key → block 偏移量 │ │ ──────────────────────────────────── │ │ Data Block [时间戳列][数值列] 分开压缩 │ └──────────────────────────────────────────┘ │ Level 1 → 2 → 3 逐级 Compaction ▼ 更大、更少、压得更狠的 TSM 文件 两列各用各的编码: 时间戳列 10:00:00 10:00:10 10:00:20 10:00:30 └─ Delta-of-Delta: 存 一个起点 + 全 0 的二阶差分 完全等距的采样几乎不占空间 数值列 71.2 71.3 71.2 71.5 └─ Gorilla XOR: 相邻浮点数异或后高位全是 0， 只存有效位，变化小的指标压得最狠 这也解释了一个反直觉现象: 抖动剧烈的指标比平稳指标占的磁盘多好几倍。

Flux 查询语言

// 基本查询：过去1小时 CPU 使用率
from(bucket: "monitoring")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu" and r.host == "server01")
  |> filter(fn: (r) => r._field == "usage_idle")

// 聚合：每5分钟平均值
from(bucket: "monitoring")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "cpu")
  |> aggregateWindow(every: 5m, fn: mean)
  |> yield(name: "5m_avg")

// 降采样任务
option task = {name: "downsample_cpu", every: 1h}
from(bucket: "monitoring")
  |> range(start: -task.every)
  |> filter(fn: (r) => r._measurement == "cpu")
  |> aggregateWindow(every: 5m, fn: mean)
  |> to(bucket: "monitoring_downsampled")
示例场景：某 IoT 平台把 3 万台设备、每台 40 个指标、10 秒一次的采样直接写进 MySQL 的一张宽表，靠 (device_id, ts) 联合索引支撑查询。问题：日增约 10.4 亿行，两周后单表 145 亿行、磁盘占用 3.2TB，B+ 树高度增加导致每次插入都要做随机页写入，写入吞吐从 12 万点/秒跌到 1.8 万点/秒并开始堆积；"查某台设备最近 24 小时曲线"要扫 34 万行、耗时 6s 以上。方案：迁移到 InfluxDB，device_id 与指标名作 Tag、数值作 Field，让时间戳走 Delta-of-Delta、数值走 Gorilla XOR 编码；配上分层保留策略——原始数据留 7 天，1 分钟聚合留 30 天，1 小时聚合留 2 年。效果：磁盘占用从 3.2TB 降到 210GB（约 15 倍压缩），写入吞吐稳定在 42 万点/秒，24 小时曲线查询从 6s 降到 90ms，且存储量不再随时间线性膨胀。

Retention Policy（保留策略）

  • 自动删除超过保留期限的数据
  • 常见策略：原始数据 7 天 → 5 分钟聚合 30 天 → 1 小时聚合 1 年
  • InfluxDB 2.x 通过 Bucket 的 retention 参数配置
  • TSM 引擎是 InfluxDB 高压缩率和高写入性能的核心
  • Flux 的管道式语法（|>）类似函数式编程，表达力强
  • InfluxDB 3.x 的 Apache Arrow 底层是未来方向

三、TimescaleDB

TimescaleDB 没有发明新数据库，它把"按时间自动分区"塞进了 PostgreSQL 的表继承机制里——你写的还是标准 SQL，只是每次查询自动跳过了不相关的时间块，而且能直接和业务表 JOIN。

PostgreSQL 扩展方案

TimescaleDB 是 PostgreSQL 的时序数据扩展，核心理念：SQL 全功能 + 时序优化

  • Hypertable：自动按时间（和可选的空间维度）分区的虚拟表
  • 对应用透明 — 标准 SQL 操作，无需学新语言
  • 完整 ACID 事务、JOIN、子查询、窗口函数
  • 支持连续聚合（Continuous Aggregates）— 增量物化视图
-- 创建 Hypertable
CREATE TABLE metrics (
    time TIMESTAMPTZ NOT NULL,
    host TEXT NOT NULL,
    cpu_usage DOUBLE PRECISION,
    memory_usage DOUBLE PRECISION
);
SELECT create_hypertable('metrics', 'time');

-- 查询最近1小时每主机 CPU 平均值
SELECT host, time_bucket('5 minutes', time) AS bucket,
       avg(cpu_usage) AS avg_cpu
FROM metrics
WHERE time > now() - INTERVAL '1 hour'
GROUP BY host, bucket
ORDER BY bucket DESC;

-- 连续聚合
CREATE MATERIALIZED VIEW metrics_hourly
WITH (timescaledb.continuous) AS
SELECT host, time_bucket('1 hour', time) AS bucket,
       avg(cpu_usage), max(cpu_usage), min(cpu_usage)
FROM metrics
GROUP BY host, bucket;

维度TimescaleDBInfluxDB

  • TimescaleDB 最大优势：完整 SQL 生态 — 关系数据和时序数据在同一数据库
  • Hypertable 自动分区对应用透明是其核心设计理念
  • 连续聚合（增量物化视图）自动更新，替代手动 cron 降采样

四、Prometheus TSDB

Prometheus 用 拉取模型 换来的最大好处不是省事，是"拉不到就是故障"这条免费的健康检查——推送模型下，一个静默死掉的实例和一个正常但没数据上报的实例，长得一模一样。

Prometheus 数据模型

Prometheus 是云原生监控的事实标准，内置高效的 TSDB：

metric_name{label1="value1", label2="value2"} → (timestamp, value) 序列

指标类型

类型描述示例
Counter单调递增计数器http_requests_total
Gauge可增可减的当前值temperature、memory_usage
Histogram值的分布（桶）request_duration_seconds
Summary值的分位数request_duration_quantile

TSDB 存储引擎

  • Block：每 2 小时一个数据块，内含 chunks（压缩数据）+ index + meta
  • WAL：最新 2 小时数据先写 WAL，定期压实为 Block
  • Compaction：后台合并小 Block 为大 Block
  • 压缩：Gorilla 压缩算法（时间戳 Delta-of-Delta + XOR 编码），16 字节/样本 → ~1.37 字节
  • 默认保留 15 天，长期存储需外部方案（Thanos / Cortex / Mimir）

Block 分层与长期存储的衔接

本地磁盘上的时间分层: 现在 ◄──────────────────────────────────────── 过去 ┌──────────┐ ┌────────┐ ┌────────┐ ┌──────────────┐ │ Head Block│ │ Block │ │ Block │ │ 合并后 Block │ │ (内存) │ │ 2h │ │ 2h │ │ 2 天 │ │ + WAL │ │ │ │ │ │ │ └─────┬─────┘ └────────┘ └────────┘ └──────────────┘ │ 满 2 小时后落盘 └────┬────┘ ▼ ▼ 持久化为 Block Compaction 合并小块为大块 (同时删除超出 retention 的块) 每个 Block 目录里: chunks/ 压缩后的样本数据 (Gorilla 编码) index 倒排索引: label → series → chunk 位置 meta.json 时间范围与合并层级 默认只留 15 天，因为本地盘装不下更多。 长期存储怎么接上去: ┌──────────────┐ │ Prometheus │ │ 本地 15 天 │ └──────┬───────┘ │ Sidecar 把已落盘的 Block 上传 ▼ ┌──────────────┐ │ 对象存储 S3 │ 按 Block 原样存放，成本低一个数量级 └──────┬───────┘ │ ┌────────────┴────────────┐ ▼ ▼ Store Gateway Compactor (对历史 Block 提供查询) (在对象存储上继续合并 + 降采样) │ │ └────────────┬────────────┘ ▼ Querier 把"本地最近 15 天"和"对象存储里的历史" 拼成一个全局视图，对使用者透明

PromQL 查询

# 过去5分钟的 HTTP 请求速率
rate(http_requests_total{job="api-server"}[5m])

# CPU 使用率（百分比）
100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# P99 延迟（Histogram）
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# 告警规则
groups:
- name: api_alerts
  rules:
  - alert: HighLatency
    expr: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 0.5
    for: 5m
    labels: {severity: warning}
    annotations: {summary: "P99 延迟超过 500ms"}
  • Prometheus 的 Pull 模型（主动拉取指标）vs Push 模型是高频对比考点
  • Gorilla 编码将 16B/样本压缩到 ~1.37B 是其高效存储的关键
  • rate() 和 irate() 的区别：rate 看整个窗口平均，irate 看最后两点（更灵敏但更嘈杂）

五、降采样与数据保留

降采样 是在承认一件事：三个月前那一秒的 CPU 到底是 71% 还是 73%，没有人会关心；但那天的峰值是多少，可能一年后还要查。所以降采样时保留 max 和 min，往往比只留 mean 有用得多。

降采样策略

随时间推移，原始高精度数据降为低精度聚合以节省存储：

时间段数据精度存储占比
最近 24 小时原始数据（10s 间隔）100%
最近 7 天1 分钟聚合~17%
最近 30 天5 分钟聚合~3%
最近 1 年1 小时聚合~0.3%

聚合函数选择

  • mean：平均值（通用选择）
  • max/min：峰值监控（如 CPU 最大使用率）
  • sum：累计值（如请求总数）
  • last：最新值（如当前温度）
  • 最佳实践：同时保留 mean、max、min 以支持不同查询需求

分片写入与按时间降采样的存储曲线

写入分片 (按 series 哈希打散，避免单节点热点): 采集端 ──► 写入网关 ──┬──► Shard 0 series hash % 3 == 0 ├──► Shard 1 series hash % 3 == 1 └──► Shard 2 series hash % 3 == 2 每个 Shard 内部再按时间切块，查询时: 带时间范围 → 只读命中的时间块 (时间裁剪) 带标签匹配 → 先查倒排索引定位 series，再取对应块 降采样在时间轴上的形状: 数据量 ▲ 100%│████ │████ │████ 17%│████ ████████ │████ ████████ 3%│████ ████████ ████████████ 0.3%│████ ████████ ████████████ ████████████████████ └────┴────────┴────────────┴────────────────────► 时间 24h 7 天 30 天 1 年 原始 1 分钟 5 分钟 1 小时 10s 聚合 聚合 聚合 一条 10 秒采样的指标，一年原始数据约 315 万点； 按上面的分层保留后，总点数降到约 4.6 万， 两个数量级的差距，全部来自"旧数据不需要那么细"。 聚合函数别只留 mean: mean 丢掉峰值，容量复盘时会得出错误结论 推荐同时保留 mean / max / min / count 四条派生序列

六、AI 训练日志分析与 Grafana 可视化

训练监控和服务监控其实是同一套东西：loss 曲线就是业务指标，GPU 利用率就是资源指标，唯一的差别是把"实例"这个维度换成了"实验"——想清楚这一点，就不会再为训练单独造一套监控轮子。

AI 训练监控指标

时序数据库在 AI/ML 训练中记录关键指标：

指标类别具体指标用途
训练进度loss、accuracy、learning_rate、epoch模型收敛监控
GPU 资源GPU 利用率、显存占用、温度、功耗硬件资源优化
吞吐量samples/sec、tokens/sec、step_time训练效率分析
梯度状态gradient_norm、gradient_variance检测梯度爆炸/消失
数据管道data_loading_time、queue_sizeI/O 瓶颈识别
标签只放低基数维度

host、region、job、experiment_id 这类取值有限的字段才做标签。想按 request_id 查明细，那是日志系统的活，不是指标系统的。

Counter 只增不减，查询时再算速率

上报累计值、用 rate() 求速率，重启后计数归零也能被自动识别。上报"每分钟增量"则一旦漏采就永久丢失。

写入前先给基数设上限

在采集端或网关加 series 数量配额与告警。等到内存被打满才发现基数失控，通常已经需要停机清数据了。

别用时序库存事件明细

每条记录都带唯一 ID 的数据是日志不是指标。塞进 TSDB 会让 series 数量随数据量线性增长，压缩优势荡然无存。

别对 Histogram 的分位数做平均

把多个实例的 P99 再求平均没有任何统计意义。正确做法是先 rate() 各个 bucket、sum by 汇总，最后一次性 histogram_quantile()。

别指望默认 15 天保留期能满足复盘

容量规划、同比分析都需要至少一年数据。要么一开始就接上远端长期存储，要么明确接受"三周前的事查不到"。

示例场景：某平台给 HTTP 指标加了一个 path 标签用于排查慢接口，而路径里带着用户 ID（形如 /api/user/88213/orders）。问题：上线约 6 小时，活跃 series 从 42 万涨到 1900 万，Prometheus 常驻内存从 6GB 涨到 48GB 后被 OOM Kill，重启时重放 WAL 又花了 22 分钟，这段时间内全部告警规则失效。方案：在 relabel 阶段把路径里的数字段统一替换成占位符（/api/user/:id/orders），把标签取值收敛到约 120 个；给采集配置加 sample_limit 硬上限，单个目标超限直接丢弃并告警；接口级明细改由日志链路承担。效果：活跃 series 回落到约 51 万，常驻内存稳定在 7GB 左右，查询 P99 从 9s 降到 400ms，重启恢复时间缩短到 90 秒内。

Grafana 可视化

Grafana 是时序数据可视化的事实标准：

  • 支持多数据源：Prometheus、InfluxDB、TimescaleDB、Elasticsearch 等
  • Dashboard：多面板组合，一个仪表盘展示完整监控视图
  • Alert：基于查询条件触发告警（邮件/Slack/PagerDuty）
  • Annotation：在时间轴上标记事件（如部署、故障）

  • Grafana 的 Dashboard as Code（JSON 定义）支持版本化和自动化部署

🎯 Q&A

Q1：时序数据库与关系型数据库有什么区别？为什么需要专用的 TSDB？

核心区别：① 写入模式 — TSDB 以追加写入为主（99%+ INSERT），RDBMS 需要支持复杂的 UPDATE/DELETE；② 查询模式 — TSDB 几乎所有查询都带时间范围，RDBMS 查询模式多样；③ 数据特点 — 时序数据有天然的时间有序性，TSDB 利用这一特性做压缩（Delta 编码、Gorilla 算法），压缩率可达 10~20x；④ 生命周期管理 — TSDB 内置 Retention Policy 和降采样，RDBMS 需手动实现。用 MySQL 存时序数据的问题：写入性能不足（需频繁更新 B-Tree）、压缩率低、缺乏时序特化功能。

Q2：InfluxDB 和 TimescaleDB 如何选择？

选 InfluxDB：① 纯监控/IoT 场景，不需要复杂 SQL；② 需要极高写入吞吐（百万点/秒）；③ 团队愿意学习 Flux 查询语言；④ 不需要与关系数据 JOIN。选 TimescaleDB：① 已有 PostgreSQL 基础设施；② 需要 SQL 全功能（JOIN、子查询、窗口函数）；③ 时序数据需要与业务数据关联查询；④ 需要 ACID 事务保证。核心决策：如果你的团队熟悉 SQL 且需要关系+时序混合查询 → TimescaleDB；如果是纯指标监控场景且追求最大写入性能 → InfluxDB。

Q3：Prometheus 的 Pull 模型和 Push 模型有什么优缺点？

Pull（Prometheus 默认）：Server 主动拉取目标的 /metrics 端点。优点：① 中心控制 — 可立即知道目标是否健康（拉不到 = 故障）；② 无需在目标配置 Server 地址；③ 防止目标过载 Server。缺点：① 短生命周期任务可能错过数据（需 Pushgateway 中转）；② 需要服务发现机制。Push：目标主动推送到 Server（如 InfluxDB、Graphite）。优点：① 适合短生命周期任务和批处理；② 穿越防火墙更容易。缺点：① Server 可能被写入洪峰压垮；② 无法感知目标是否存活。Prometheus 选择 Pull 的核心原因是"Server 掌握控制权"。

Q4：什么是 "高基数（High Cardinality）" 问题？如何解决？

高基数指 Tag/Label 的唯一值组合过多。例如 user_id 作为标签，100 万用户 = 100 万个 Series。TSDB 为每个 Series 维护索引和内存结构，高基数导致：① 内存暴涨（每个 Series 消耗固定内存）；② 索引膨胀、查询变慢；③ Compaction 压力大。解决方案：① 设计层面 — 高基数维度放 Field 而非 Tag（不索引但可查询）；② 限制标签 — 禁止 user_id、trace_id 等高基数字段作为标签；③ 预聚合 — 在采集端先聚合（如按 region 汇总而非按 instance）；④ 选合适引擎 — InfluxDB IOx / ClickHouse 对高基数有更好的处理。

Q5：如何设计 AI 训练的监控方案？

技术栈：Prometheus/InfluxDB（存储）+ Grafana（可视化）+ 训练框架集成。关键设计：① 指标体系 — 训练指标（loss/accuracy/lr/epoch）、资源指标（GPU 利用率/显存/温度）、吞吐指标（tokens/sec/step_time）、数据管道指标（loading_time/queue_size）；② 采集方式 — 训练代码中通过 Prometheus Client 或 InfluxDB Client 每 N 步上报，GPU 指标通过 DCGM Exporter 采集；③ 降采样策略 — 原始数据保留 7 天，5 分钟聚合保留 30 天；④ 告警 — GPU 温度过高、Loss 突变（NaN 或异常跳变）、GPU 利用率持续低于 50%；⑤ Dashboard — 多实验对比视图，变量切换 experiment_id。相比 TensorBoard 的优势：长期存储、多实验对比、基础设施统一监控、告警能力。

Q6：Counter、Gauge、Histogram、Summary 该怎么选？用错了会有什么后果？

四种类型对应四种不同的语义，选错了不是风格问题，是数据直接不可用。Counter 用于只增不减的累计量，比如请求总数、错误总数、处理的字节数。它必须上报累计值而不是增量，因为查询时用 rate() 或 increase() 求速率，这两个函数能自动识别进程重启导致的计数归零并做补偿；如果直接上报"这一分钟发生了多少次"，一旦某次采集失败，那段增量就永久消失了。Gauge 用于可增可减的瞬时值，比如队列长度、内存占用、当前温度、正在处理的请求数。对 Gauge 用 rate() 是典型错误，得到的数字没有任何含义。Histogram 用于观测值的分布，客户端把观测值累加进预设的桶里上报，服务端用 histogram_quantile() 算分位数。它的关键优势是可聚合——多个实例的桶可以先 sum 再算分位数，得到的是全局真实分位数；代价是桶边界必须提前定好，如果你的延迟集中在 200ms 而桶边界设在 1s、2.5s、5s，那算出来的 P99 会非常不准。Summary 由客户端直接计算分位数后上报，好处是不用猜桶边界、单实例数值精确，致命缺点是分位数无法跨实例聚合——十台机器各自的 P99 求和或求平均都得不出集群的 P99。所以经验规则很简单：单实例、且确实需要精确分位数时才用 Summary；只要是分布式服务，一律用 Histogram，并且花时间把桶边界设在你真正关心的延迟区间上。
