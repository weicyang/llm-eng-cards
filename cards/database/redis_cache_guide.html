Redis & Caching — 数据结构、持久化、集群与缓存策略

一、Redis 核心数据结构

Redis 快的根本不是"数据在内存里"这一条，而是它把 数据结构 搬到了服务端——排行榜不必把十万行拉回应用层再排序，一条 ZADD 加一条 ZRANGE 就在 Redis 里算完了，省掉的是十万次网络往返，不只是磁盘。

数据类型底层编码典型命令应用场景
StringSDS（Simple Dynamic String）GET/SET/INCR/MGET缓存、计数器、分布式锁、Session
Hashziplist / hashtableHGET/HSET/HGETALL用户信息、对象属性、购物车
Listquicklist（ziplist + linkedlist）LPUSH/RPOP/LRANGE消息队列、时间线、最新列表
Setintset / hashtableSADD/SMEMBERS/SINTER标签、去重、共同好友
ZSetziplist / skiplist + hashtableZADD/ZRANGE/ZRANGEBYSCORE排行榜、延迟队列、优先级队列
StreamRadix Tree + ListpackXADD/XREAD/XREADGROUP消息队列（支持消费组和 ACK）

高级数据结构

  • Bitmap：位操作，适合签到、在线状态（SETBIT/BITCOUNT）
  • HyperLogLog：基数估算，内存仅 12KB 可统计 2^64 个元素的去重数（PFADD/PFCOUNT）
  • GEO：地理位置查询，底层 ZSet（GEOADD/GEORADIUS）
  • BloomFilter（RedisBloom 模块）：概率性判断元素是否存在，防缓存穿透
  • ZSet 底层用 skiplist + hashtable：skiplist 支持范围查询 O(logN)，hashtable 支持 O(1) 单元素查找
  • String 最大 512MB，但实际建议 <10KB 避免大 Key
  • Stream 是 Redis 5.0 新增的日志型数据结构，可替代 Pub/Sub 实现可靠消息队列

二、持久化机制：RDB 与 AOF

RDB 赌的是"崩溃不常发生"，AOF 赌的是"最多只丢一秒"。生产上两个都开不是保守，而是它们分别负责恢复速度和数据安全，谁也替不了谁。

RDB（Redis Database）

  • 按时间间隔生成内存数据的二进制快照
  • 使用 fork() 创建子进程，利用 Copy-On-Write 写时复制
  • 恢复速度快（直接加载二进制）
  • 可能丢失最后一次快照后的数据
# redis.conf RDB 配置
save 900 1      # 900秒内至少1次修改则快照
save 300 10     # 300秒内至少10次修改则快照
save 60 10000   # 60秒内至少10000次修改则快照

AOF（Append Only File）

  • 记录每个写命令的文本日志
  • 三种刷盘策略：always（每条刷盘）/ everysec（每秒，推荐）/ no（OS 决定）
  • AOF 重写（BGREWRITEAOF）压缩文件大小
  • Redis 7.0+ 引入 Multi-Part AOF（基础 AOF + 增量 AOF）

两种持久化的写入与恢复路径

写入期: 客户端 SET k v │ ▼ ┌──────────────┐ │ 内存数据集 │ └──┬────────┬──┘ │ │ │ └──────────► AOF 缓冲区 │ │ everysec 刷盘 │ ▼ │ appendonly.aof (追加文本命令) │ │ 文件涨到阈值 │ ▼ │ BGREWRITEAOF (fork 子进程重写为最小命令集) │ │ save 60 10000 命中 ▼ fork() 子进程 ──► Copy-On-Write ──► dump.rdb (二进制快照) fork 期间父进程每改一页就复制一页， 写入越密集，内存峰值越接近数据集的 2 倍。 重启恢复期: AOF 与 RDB 都在 ──► 优先加载 AOF (数据更新，但要逐条重放) 只有 RDB ──► 直接加载二进制，最快 只有 AOF ──► 逐条重放命令，最慢

RDB vs AOF 对比

维度RDBAOF
数据安全性可能丢失分钟级数据最多丢失 1 秒数据（everysec）
恢复速度快（二进制加载）慢（重放命令）

  • AOF everysec 是性能与安全的最佳平衡点
  • Redis 7.0 的 Multi-Part AOF 解决了重写期间的可靠性问题

三、集群模式与哨兵高可用

哨兵 回答的是"主挂了谁顶上"，Cluster 回答的是"一台机器装不下"。这是两个不同的问题，不要指望用一个方案去解决另一个。

Redis Sentinel（哨兵）

  • 监控主节点状态，自动故障转移（Failover）
  • 多个 Sentinel 节点通过投票决定主节点是否宕机
  • 客户端通过 Sentinel 获取当前主节点地址
  • 不支持数据分片 — 所有数据在单个主节点上
Sentinel 1/2/3 → 监控 → Master ← 复制 → Replica 1 / Replica 2
Master 宕机 → Sentinel 投票 → 选举新 Master → 通知客户端

Redis Cluster

  • 数据分片到 16384 个 Slot，每个主节点负责一部分 Slot
  • 使用 CRC16(key) % 16384 计算 Key 所属 Slot
  • 节点间通过 Gossip 协议通信
  • 每个主节点可配从节点实现 HA
  • 不支持跨 Slot 的多 Key 操作（除非使用 Hash Tag {tag}）
# Hash Tag 示例：保证相关 Key 在同一 Slot
SET {user:100}.name "张三"
SET {user:100}.age 25
# 两个 Key 的 CRC16 只计算 {user:100} 部分

主从复制与哨兵切换的完整过程

正常状态: ┌────────────┐ ┌────────────┐ ┌────────────┐ │ Sentinel 1 │ │ Sentinel 2 │ │ Sentinel 3 │ └──────┬─────┘ └──────┬─────┘ └──────┬─────┘ │ 每秒 PING │ │ └───────┬───────┴───────┬───────┘ ▼ ▼ ┌─────────┐ ┌───────────┐ 写请求 ──────► │ Master │ ──► │ Replica 1 │ │ │ 异步 ├───────────┤ │ │ 复制 │ Replica 2 │ └─────────┘ └───────────┘ ▲ 读请求 ─────────────────────────────┘ 复制的三个阶段: 1) 全量同步 Replica 发 PSYNC ? -1 → Master fork 出 RDB → 传输 → 加载 2) 命令传播 Master 把写命令实时推给 Replica (异步，因此有延迟) 3) 断线重连 Replica 带 offset 发 PSYNC，对得上 repl-backlog 就走增量 故障转移: Master 无响应 │ ▼ 单个 Sentinel 标记主观下线 (SDOWN) │ 向其他 Sentinel 求证 ▼ 票数达到 quorum ──► 客观下线 (ODOWN) │ ▼ Sentinel 之间选出 Leader (Raft 式投票) │ ▼ 按 复制偏移量最大 / slave-priority 挑一个 Replica │ ▼ SLAVEOF NO ONE 提升为新 Master ──► 其余 Replica 改指向 ──► 通知客户端 代价: 异步复制下，旧 Master 已回包但尚未传出去的写会永久丢失。

  • Hash Tag 是 Cluster 模式下 multi-key 操作的解决方案
  • Sentinel 和 Cluster 可以同时使用，但通常二选一

四、缓存穿透、击穿与雪崩

穿透、击穿、雪崩听起来是三种事故，其实是同一个问题的三种形态：缓存没兜住的请求最后都由数据库来还，区别只在于漏下去的是"根本不存在的 Key"、"刚好过期的那一个热 Key"，还是"同一秒集体到期的一大片 Key"。

三大经典问题

问题定义触发条件解决方案
缓存穿透 查询不存在的数据，缓存和 DB 都没有 恶意攻击 / 非法参数 ① 布隆过滤器拦截
② 缓存空值（短 TTL）
③ 参数校验
缓存击穿 热点 Key 过期瞬间，大量请求直接打到 DB 热点数据到期 ① 互斥锁（SETNX）
② 逻辑过期（不设 TTL，后台异步刷新）
③ 永不过期 + 主动更新
缓存雪崩 大量 Key 同时过期，DB 压力暴增 批量导入相同 TTL / Redis 宕机 ① TTL 加随机偏移
② 多级缓存（L1 本地 + L2 Redis）
③ 限流降级
④ Redis 高可用

读路径与击穿时的互斥回源

Cache-Aside 读路径: 请求 ──► GET cache:k │ 命中 ──┴── 未命中 │ │ ▼ ▼ 返回 SETNX lock:k (互斥，只放一个请求回源) │ 抢到锁 ───┴─── 没抢到 │ │ ▼ ▼ 查 DB sleep 50ms 后重试 GET │ │ ▼ │ SET cache:k v EX 300 │ + 随机偏移 0~60s │ │ │ ▼ ▼ DEL lock:k 命中缓存，返回 Cache-Aside 写路径 (先改库，再删缓存): UPDATE db ──► DEL cache:k ──► 延迟 500ms ──► 再 DEL cache:k └── 延迟双删，清掉这期间 被并发读回填的脏缓存 为什么是删而不是更新? 两个并发写更新缓存的先后顺序， 和它们更新数据库的先后顺序并不保证一致；删除则天然幂等。
示例场景：某商品详情接口在凌晨把 20 万条数据批量预热进 Redis，TTL 统一写死 3600 秒。问题：一小时后这批 Key 在同一秒集体过期，约 8000 QPS 的请求全量落到 MySQL，100 个连接的连接池瞬间打满，接口 P99 从 30ms 涨到 12s，持续约 4 分钟。方案：TTL 改为 3600 + rand(0,600) 摊到 10 分钟窗口；热点 Key 额外做逻辑过期（value 内嵌 expire_at，到期后由后台线程刷新、前台仍返回旧值）；回源路径统一加 SETNX 互斥。效果：同一时刻真正回源的请求从 8000 降到个位数，DB 峰值 QPS 从 8000 降到不足 50，接口 P99 回到 35ms 以内。

缓存更新策略

Cache-Aside（旁路缓存，最常用）

  • 读：先读缓存 → 命中则返回；未命中 → 读 DB → 写入缓存
  • 写：先更新 DB → 再删除缓存（而非更新缓存）
  • 为什么删除而非更新？避免并发写导致的缓存与 DB 不一致

Read/Write-Through

  • 缓存层封装 DB 读写，应用只与缓存交互
  • 写入时缓存同步写入 DB（Write-Through）或异步写入 DB（Write-Behind）
  • 穿透/击穿/雪崩的区别必须清晰 — 从触发原因和解决方案两个维度区分
  • Cache-Aside 的"先更新 DB 再删除缓存"是标准答案
  • 延迟双删：更新 DB → 删缓存 → 延迟 N 毫秒 → 再删缓存（解决极端并发）

五、分布式锁（Redlock）

Redis 分布式锁真正难的不是加锁，而是"我以为我还持有锁，其实它 30 秒前就过期了"——所以 看门狗续期 和释放时的 value 校验，比 SETNX 本身重要得多。

基础分布式锁

# 加锁：原子操作 SET + NX + PX
SET lock_key unique_value NX PX 30000

# 释放锁：Lua 脚本保证原子性（先检查再删除）
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

关键要素

  • 互斥：NX 保证只有一个客户端获取锁
  • 防死锁：PX 设置自动过期时间
  • 安全释放：unique_value 确保只释放自己的锁
  • 续期：看门狗机制（Redisson 的 WatchDog）自动延长锁时间

Redlock 算法

Martin Kleppmann 指出单节点 Redis 锁在主从切换时可能失效。Redlock 使用 N 个独立 Redis 实例（建议 5 个）：

  1. 记录开始时间 T1
  2. 依次向 N 个 Redis 实例请求加锁（相同 key 和随机 value，短超时）
  3. 如果在 多数（N/2+1）实例上加锁成功，且总耗时 < 锁过期时间，则加锁成功
  4. 锁的有效时间 = 原始过期时间 - 加锁耗时
  5. 释放时向所有实例发送释放命令

Redlock 争议：Martin Kleppmann 撰文指出 Redlock 在 GC 暂停、时钟跳变等场景下仍不安全。如果需要绝对安全的分布式锁，应使用 ZooKeeper 或 etcd（基于共识协议）。Redis 分布式锁适合大多数"尽力而为"的场景。

  • Redis 分布式锁三要素：NX（互斥）+ PX（防死锁）+ Lua（安全释放）
  • Redlock 的争议必须了解 — 提到 Martin Kleppmann 的批评是加分项
  • Redisson 的 WatchDog 续期机制是 Java 生态的标准实现

六、Redis 在 AI 场景中的应用

语义缓存 把命中条件从"字符串完全相等"换成了"向量距离够近"，省下的是 LLM 调用费，代价是你必须为"多近才算同一个问题"这个阈值负责——阈值调松一点，用户就会拿到别人问题的答案。

Semantic Cache（语义缓存）

传统缓存基于精确 Key 匹配，语义缓存基于语义相似度命中：

用户提问 → Embedding → Redis 向量搜索（RediSearch）→ 相似度 > 阈值 → 返回缓存答案
未命中 → 调用 LLM → 存入 Redis（向量 + 答案）
  • Redis Stack 内置 RediSearch 模块，支持向量索引（HNSW/FLAT）
  • 显著降低 LLM API 调用成本（相似问题复用答案）
  • 适合 FAQ、客服、重复性高的场景

七、性能优化与运维实践

大 Key 和 热 Key 是同一枚硬币的两面：前者让单次操作变慢，后者让单个节点被打满，而 Redis 的单线程模型意味着这两件事都会连累实例上所有其他请求。

大 Key 问题

  • 定义：String > 10KB，集合类型元素 > 5000 个
  • 危害：阻塞主线程、网络带宽占满、主从复制延迟、内存碎片
  • 排查：redis-cli --bigkeys、MEMORY USAGE key
  • 解决：拆分大 Key（Hash 分片）、异步删除（UNLINK）、压缩 Value

热 Key 问题

  • 定义：单个 Key 被极高频访问（如热门商品详情）
  • 危害：单节点 CPU 打满、Cluster 单 Slot 热点
  • 解决：① 本地缓存（L1 + L2）；② 读副本（READONLY 从节点读）；③ Key 拆分加后缀（随机路由到多个 Key）

内存优化

  • 使用合适的数据结构（Hash 替代多个 String 存储对象字段）
  • 设置 maxmemory + 淘汰策略（allkeys-lru 最常用）
  • 压缩 Value（Snappy/LZ4）
  • 短 Key 名节省内存（u:100:n vs user:100:name）
删大 Key 一律用 UNLINK

UNLINK 只在主线程里摘链，真正的内存释放交给后台线程。DEL 一个上百万元素的 Hash 会把主线程卡住几百毫秒，期间所有命令排队。

TTL 一律带随机偏移

批量写入时用 base + rand(0, base/10) 把过期时间摊开。就这一行改动，能挡掉绝大多数雪崩。

线上巡检用 SCAN，不用 KEYS

KEYS * 会遍历整个键空间并阻塞主线程；SCAN 带游标分批返回，虽不保证快照一致性，但不会让线上停顿。

别把 Redis 当唯一数据源

AOF everysec 仍可能丢最后一秒，主从异步复制在切换时会丢更多。订单、余额这类数据必须有数据库兜底。

别在 Cluster 里做跨槽多 Key 操作

跨 Slot 的 MGET、MULTI 会直接报错。需要一起操作的 Key 用 Hash Tag {user:100} 绑到同一个 Slot。

别让单个 Key 无限增长

评论、日志一路追加进同一个 List 或 ZSet，几个月后就是几百 MB 的大 Key。写入时就按时间或 ID 分片，例如 msg:{uid}:202601。

示例场景：某社区应用把每个话题的全部评论存进单个 Hash，最活跃话题积累到约 120 万个 field、序列化后约 340MB。问题：一次 HGETALL 耗时约 900ms，期间主线程完全阻塞，同实例其他命令的 P99 从 2ms 飙到 900ms；主从全量同步时这个 Key 一次性传输，还撑爆了复制缓冲区，Replica 反复重连。方案：按评论 ID 取模拆成 256 个子 Hash（topic:{id}:c:{n}），读取只取需要的分片；清理旧 Key 全部换成 UNLINK；把 redis-cli --bigkeys 加进每日巡检。效果：单次读取耗时降到 3ms 以内，实例 P99 稳定在 2ms 左右，主从全量同步不再中断。
  • 大 Key 和热 Key 是 Redis 运维最常见的两大问题
  • UNLINK 是 DEL 的异步版本 — 避免删除大 Key 时阻塞主线程
  • maxmemory 淘汰策略：allkeys-lru（推荐缓存场景）、volatile-lru（有过期的 Key 先淘汰）、noeviction（写满报错）

🎯 Q&A

Q1：Redis 为什么这么快？单线程如何实现高性能？

Redis 快的核心原因：① 纯内存操作，数据存储在 RAM 中，读写延迟纳秒级；② 单线程避免了上下文切换和锁竞争开销；③ I/O 多路复用（epoll/kqueue）一个线程处理数万连接；④ 高效的数据结构（SDS、ziplist、skiplist 等针对性优化）。Redis 的瓶颈是网络 I/O 而非 CPU，单线程模型已足够。6.0+ 引入多线程 I/O（多线程处理网络读写，命令执行仍单线程），进一步提升网络吞吐。

Q2：缓存穿透、击穿、雪崩有什么区别？如何解决？

穿透：查询的数据在缓存和 DB 中都不存在（恶意攻击/非法 ID）→ 布隆过滤器拦截 + 缓存空值。击穿：热点 Key 恰好过期，瞬间大量请求打到 DB → 互斥锁（SETNX）让一个请求回源、其他等待；或使用逻辑过期（不设 TTL，后台异步刷新）。雪崩：大量 Key 同一时间过期或 Redis 宕机 → TTL 加随机偏移分散过期时间；多级缓存（本地 + Redis）；限流降级兜底。核心区分：穿透是"数据不存在"，击穿是"单个热点过期"，雪崩是"大面积过期/宕机"。

Q3：Redis 分布式锁如何实现？有哪些注意事项？

基础实现：SET key value NX PX timeout 原子加锁，Lua 脚本原子释放（先验证 value 再删除）。注意事项：① 必须设过期时间防死锁；② value 使用 UUID 防止误删他人的锁；③ 锁续期（Redisson WatchDog 机制）防止业务未完成锁已过期；④ 主从切换可能导致锁丢失 — 可使用 Redlock（多节点加锁取多数派）；⑤ Redlock 存在争议（时钟偏移、GC 暂停问题），强一致场景建议 ZooKeeper/etcd。

Q4：RDB 和 AOF 各自的优缺点？生产环境如何选择？

RDB 优点：恢复速度快（二进制加载）、文件紧凑适合备份、fork 后对主线程影响小。RDB 缺点：可能丢失最后一次快照后的数据（分钟级），fork 大内存实例时短暂卡顿。AOF 优点：数据安全性高（everysec 最多丢 1 秒）、可读性好（文本格式）。AOF 缺点：文件较大、恢复慢（需重放命令）。生产建议：同时开启 RDB + AOF，AOF 保证数据安全，RDB 用于快速恢复和定期备份。Redis 7.0+ 的 Multi-Part AOF 进一步提升了可靠性。

Q5：Redis Cluster 如何进行数据分片？扩容时如何迁移数据？

Redis Cluster 将键空间划分为 16384 个 Slot，每个主节点负责一部分 Slot。Key 所属 Slot = CRC16(key) % 16384。扩容流程：① 新节点加入集群（CLUSTER MEET）；② 将目标 Slot 从旧节点迁移到新节点（CLUSTER SETSLOT ... MIGRATING/IMPORTING）；③ 逐个 Key 迁移（MIGRATE 命令，原子操作）；④ 迁移完成后更新 Slot 映射。迁移期间，如果客户端访问正在迁移的 Slot，旧节点返回 ASK 重定向到新节点。整个过程对客户端近乎透明。缩容类似但反向操作。

Q6：Redis 的过期 Key 是怎么被删掉的？和内存淘汰策略是什么关系？

这是两套机制，解决的是不同问题。过期删除处理"这个 Key 到点了"：惰性删除在每次访问 Key 时检查 TTL，过期就地删掉并返回空；定期删除由 serverCron 每秒执行 10 次，每次从设了 TTL 的 Key 里随机抽 20 个删掉已过期的，若过期比例超过 25% 就立刻再抽一轮。两者结合意味着"逻辑过期"和"物理删除"之间存在时间差，一个既不被访问、又一直没被随机抽中的 Key 可以在内存里躺很久，所以 DBSIZE 通常大于逻辑上的有效 Key 数。内存淘汰处理的是另一件事："内存不够了，得腾地方"：写命令执行前先检查是否触及 maxmemory，触及则按策略挑 Key 淘汰——noeviction 直接让写命令报错，allkeys-lru 在全部 Key 里按近似 LRU 淘汰，volatile-lru 只在设了 TTL 的 Key 里淘汰。选择要点是：纯缓存实例用 allkeys-lru；缓存和持久数据混在一个实例时用 volatile-lru，并严格保证持久数据不设 TTL，否则它们会被当成缓存淘汰掉。还有一个容易踩的坑：主从环境下 Replica 不会自行删除过期 Key，而是等 Master 传来 DEL，所以直接读 Replica 有极小概率读到已过期的值。
