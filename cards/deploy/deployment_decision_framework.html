部署选型看起来是一道成本题，其实是一道约束题：合规红线决定了你有没有选择权，延迟 SLA 决定了架构形状，运维能力决定了方案能不能活过半年，而成本只在前三项都放行之后才有资格上桌。把顺序搞反的团队，通常在自建三个月后又灰溜溜地迁回 API。

一、四种部署形态与四维决策框架

"要不要自己部署大模型"这个问题被问烂了，但绝大多数争论没有结论，是因为参与者脑子里想的根本不是同一件事。实际可选的形态有四种，它们在谁持有权重、谁持有算力、数据流经哪里三件事上完全不同。

四种形态的本质差异

云 API指的是直接调用厂商的公共推理端点（OpenAI、Anthropic、以及国内各家大模型开放平台）。你既不持有权重也不持有算力，付出的是每一百万 token 的单价，换回来的是零运维和随时可用的最强模型。它的隐含代价是：请求内容离开了你的网络边界，模型版本由厂商控制，且成本随调用量严格线性上涨——永远不会有规模效应。

托管推理是一个常被忽略的中间态：AWS Bedrock、Amazon SageMaker、Azure AI Foundry、阿里云百炼、火山方舟这类形态，让你在云厂商的 VPC 内以专属实例或专属吞吐的方式跑模型（有的还允许你上传自己微调的权重）。算力是租的、运维大部分是厂商的，但数据留在你自己的云账户与私有网络内，还能挂上云厂商已有的合规资质。它填补的正是"云 API 数据出域不可接受，但自建又养不起团队"的那段空白。

自部署（私有化 / on-premise）是你自己买卡或租裸金属 GPU，用 vLLM、SGLang 之类的推理引擎把开源权重跑起来。权重、算力、数据三样全在自己手上，控制力最强，代价是你要为 CUDA 驱动、引擎版本、显存调优、监控告警、值班响应负全责。

混合方案不是骑墙，而是承认"不同请求的约束不同"：敏感请求走私有集群，通用长尾走云 API，二者由一层统一网关分流。这是 2026 年绝大多数中大型企业的实际落点。

四个决策维度的判定顺序

关键不在于罗列维度，而在于顺序。四个维度不是并列打分，而是层层过滤：合规是一票否决项，延迟 SLA 是硬约束项，运维能力是可行性项，成本才是最后的优化项。很多团队从 Excel 里的成本对比表开始做决策，做到一半发现法务不批，前面全白算。

顺序维度性质核心问题不通过的后果
第一层合规与数据边界一票否决请求内容允许离开本网络/本地域吗？方案直接出局，无论多便宜

第三层运维能力可行性有没有人能 7×24 处理 GPU 故障与版本升级？上线三个月后无人维护，静默腐化
第四层成本优化项在前三层允许的方案里，哪个 TCO 最低？钱多花了，但系统还能跑

把四维框架想成机场安检：合规是护照（没有就登不了机），SLA 是登机时间（赶不上就没意义），运维能力是行李限重（超了带不走），成本只是选经济舱还是商务舱。绝大多数人却在还没拿到护照时就开始比较票价。

二、成本维度：盈亏平衡点怎么算

"自建更省钱"是这个领域流传最广也最经不起推敲的说法。它之所以能流传，是因为大家算的都是 GPU 租金除以吞吐这一项，而这一项恰恰只占真实成本的三分之一左右。要得到能拿去和 API 账单对比的数字，必须走完三步推导。

第一步：单位 token 的裸算力成本

自建的原始成本只取决于两个量——GPU 每小时单价和该卡上模型的实际吞吐：

每百万 token 成本 = GPU 时价 ÷ (吞吐 tok/s × 3600 × 利用率) × 106

2026 年的 GPU 云市场报价大致落在这个区间：A100 80GB 约 1.6 美元/小时，H100 80GB 约 2.0-3.5 美元/小时（不同供应商差异显著），H200 141GB 约 3.7-5.0 美元/小时，B200 约 5.5-6.5 美元/小时；预留/长约通常比按需便宜 30-40%。以单卡 H100 跑 70B FP8、生产并发下约 400 tok/s 为例，在理想的 100% 利用率下，每百万 token 约 1.9-2.0 美元。这个数字看起来很美，直到你把利用率放进去。

第二步：利用率税——最容易被无视的乘数

利用率税指的是 GPU 空转时段仍要付费所带来的成本放大。API 在你不调用时收费为零，而一块闲置的 GPU 和一块满载的 GPU 账单一模一样。业务流量天然有峰谷：早九点是峰值，凌晨两点接近为零，加上为吸收 P95 尖峰而做的过量配置，多家 2026 年的 TCO 分析给出的真实持续利用率区间是 23%-65%，中位数在 40% 上下。

第三步：把 GPU 账单还原成全成本

行业内一个反复被验证的经验比例是：GPU 硬件/租金只占自建真实成本的 30%-40%，其余是运维人力、可观测栈、冗余备份和升级折腾。一个包含 0.25 FTE 运维的两卡 H100 部署，月度全成本常见落在 7,000-11,000 美元区间，而其中 GPU 账单只有 3,600-5,000 美元。更极端的估算把资深 MLOps 的全负荷人力成本（美国 25-36 万美元/年、欧洲 14-22 万美元/年）摊进去后，八卡集群的名义 15,700 美元/月会膨胀到 45,000-90,000 美元/月。

自建月度全成本 ≈ (730 × GPU 时价 × 卡数) ÷ 0.35   |   盈亏平衡量 V* = 全成本 ÷ API 单价

这张表暴露了两个关键结论。其一，自建大模型对旗舰 API 的套利空间极窄：单卡 H100 跑 70B 的平衡点（26M/天）几乎就等于它的物理产能上限（35M/天），意味着必须常年跑在 75% 以上利用率才能真赢，而前面已经说过真实利用率的中位数只有 40%。其二，自建真正赚钱的地方是小模型跑大批量：同一块 H100 跑 7B-14B，产能可达 250-500M/天，平衡点却不变，这条路的裕度是 10 倍级的。这也解释了为什么 2026 年主流实践是"自建小模型接海量长尾、旗舰能力留给 API"。

另一个必须写进模型的变量是低价 API 的存在。DeepSeek 系列、各家 Flash/Mini 档位把单价压到 0.15-0.7 美元/百万 token 之后，对这一档 API 的自建平衡点普遍要求 5,000 万到 1 亿 token/月起步，很多分析给出的门槛是每天上亿 token。纯粹以省钱为目的的自建，在低价 API 面前基本已经算不过账了——这不是观点，是算术。

生产案例：内部知识助手在低利用率下自建反而更贵。某企业内部知识问答上线后日均 800 万 token，团队按"$2.79/hr × 730 = $2,036/月，比 API 账单 $1,800 便宜"的口径拍板自建单卡 H100。上线后实测：工作日 9:00-18:00 承载了 87% 的流量，夜间与周末近乎归零，月度持续利用率只有 21%。折算后的裸算力成本从预估的 $1.94/百万 token 涨到 $9.2/百万 token；再叠加 0.2 FTE 的运维投入（约 $3,500/月）与一次 CUDA 版本升级引发的 6 小时故障，第一个季度实际支出 $17,400，而同期若继续用 API 只需 $5,400，反向多花了 3.2 倍。第二季度改为"白天跑在线服务、夜间跑文档批量向量化与摘要"的错峰复用后，利用率拉到 63%，单位成本降到 $3.1/百万 token，才回到与 API 大致持平的水平。教训很直白：自建的成本优势不是买来的，是靠把 GPU 填满挣来的。

API 是打车，自建是买车。买车的每公里成本确实更低，但前提是你天天开。一年只开两千公里的人买车，账单里 80% 付给了停在车位上的那段时间——GPU 的空转，就是最贵的那个车位。

三、合规维度：什么时候根本没得选

成本是连续的、可优化的；合规是离散的、二值的。当合规红线落下来时，前一节所有的算术都不再重要——你只能自部署或托管推理，剩下的问题只是"用什么形态把它做得别太贵"。

需要澄清一个常见误解："用了云就等于数据出域"是不成立的。托管推理形态（Bedrock、SageMaker、百炼、方舟等）通常把推理放在你自己的云账户和 VPC 内，请求不进入模型厂商的公共端点，也不用于训练；很多机构的合规部门在完成云厂商资质审查后是认这条路的。真正过不去的，是"内容必须留在本机构自有机房/本地网络"这一档要求——那时候只剩自建。

脱敏网关：把"不能出域"变成"部分可出域"

金融风控类实践里有一个很有价值的中间做法：在数据流转最前端部署脱敏网关，用规则加轻量命名实体识别的混合引擎实时拦截请求，把姓名、身份证号、银行卡号等标识符替换为无意义的哈希令牌（Tokenization），只把脱敏后的上下文或特征向量送出。这样一来，原本整类必须私有化的请求中，有相当一部分可以合法地走云 API，既守住红线又释放了成本空间。代价是网关本身成为关键路径上的组件，它的延迟、可用性和脱敏准确率都要按核心服务的标准来做。

合规不是"能不能用 AI"的开关，而是"数据能走多远"的量尺。工程上的价值不在于争论红线合不合理，而在于设计一条把红线内外区分开的通路——脱敏网关就是这条通路的收费站。

四、延迟、SLA 与运维能力

延迟：网络 RTT 是 API 无法优化掉的地板

延迟维度上真正决定性的不是模型快慢，而是网络 RTT——请求跨公网往返所需的时间。这一项在自建方案里通常是 1-5 毫秒（同机房内网），在跨境调用海外 API 时可以达到 150-300 毫秒，而且它是加在首 token 之前的固定开销，无论你怎么优化 prompt 都消不掉。当业务对首 token 延迟有 100 毫秒级要求（语音实时交互、输入法联想、交易链路内联推理），跨境 API 在物理上就不可能满足。

另一个容易低估的是限流（rate limit）与配额。公共 API 的 TPM/RPM 上限是按账户给的，大促、开学季、财报季这类行业性峰值会让所有客户同时打满，厂商侧排队时间不受你控制。自建的峰值上限虽然更低，但至少是确定的、可提前扩容的。对可用性承诺严格的业务，"确定的 3000 QPS"往往比"名义无限但会被限流的能力"更有价值。

运维能力：那条最容易被跳过的可行性检查

自建的运维负担不是一次性的部署工作，而是持续的版本地狱：NVIDIA 驱动、CUDA Toolkit、cuDNN、推理引擎（vLLM/SGLang）、模型权重，五层组件各有自己的发布节奏和相互依赖。升级 vLLM 以支持一个新模型架构，就要验证新版本不会破坏现有 CUDA 环境；FlashAttention 与 xformers 必须针对特定 CUDA 版本编译，否则得到的不是报错而是静默的性能退化。业内的量化经验是：每次重要模型版本升级消耗 1-3 个工程日，稳态下每月还要投入 8-20 小时。

生产案例：混合路由把总支出压掉一半以上。某 SaaS 团队每月旗舰 API 支出约 4.2 万美元，其中 78% 的调用是分类、抽取、摘要这类"批量但不难"的任务，剩下 22% 是复杂推理与代码生成。团队没有整体自建，而是只把批量任务迁到自建：单台 H100 跑 13B 模型，在约 50% GPU 利用率下覆盖每天约 8,000 场会话，含人力摊销的月成本落在 1,500-5,000 美元区间；旗舰能力继续走 API，月支出降到约 9,200 美元。合计从 4.2 万降到约 1.3 万，总 AI 支出下降 69%，落在这类"选择性自建"实践普遍报告的 40%-70% 区间内。关键在于团队没有去挑战"用开源模型替代旗舰模型"这道难题，只是把它不擅长的那 78% 拿走了。

运维能力不是"我们能不能搞定"的自信题，而是"半年后还有没有人管"的排班题。一套没有值班表、没有告警面板、没有升级预案的自建推理服务，本质上是一笔延期支付的技术债，利息在第一次线上故障时一次性还清。

五、混合方案：分流规则与网关设计

混合方案之所以在 2026 年成为主流，是因为它同时解开了两个死结：合规上"敏感请求不出域"，成本上"长尾请求不值得自建"。但混合的正确实现方式只有一种——统一网关；让业务代码自己判断走公有还是私有，是最常见也最危险的错误做法。

为什么不能让业务代码自己判断

直连模式看起来更简单：在业务代码里写个 if，敏感就调内网、不敏感就调云端。问题在于敏感判定逻辑会在几十个服务里各写一份，任何一处判断失误就是一次数据外泄，而且事后没有统一的拦截点可以兜底。更现实的是，随着业务迭代，这些散落的判定逻辑会迅速失去一致性——上线三个月后没人说得清到底哪些请求出了域。统一网关的核心价值不是路由本身，而是把"合规底线"从几十处约定收敛成一处强制执行。

分流规则怎么定

分流规则应当是一张可审计的策略表，而不是散落的代码分支。实践中通常按两个正交维度切：敏感度决定"能不能出域"，任务复杂度决定"需不需要旗舰模型"。两个维度交叉出四个象限，每个象限有明确的默认目标与兜底策略。

最后一行是混合架构里最容易写错的一条：故障转移不得越过合规边界。私有集群挂了就应该让高敏感请求失败并告警，而不是"聪明地"自动切到公有 API——那是把一次可用性事故升级成一次数据合规事故。

削峰填谷是混合方案的额外红利。金融风控领域的实践报告显示，把无需私有化处理的通用知识查询分流到云端后，本地 GPU 集群的算力峰值需求可以下降 40% 以上——这意味着自建部分的采购规模可以按"稳态负载"而非"峰值负载"来定，直接改善了前面第二节里那个致命的利用率数字。

混合架构的真正产物不是"省了多少钱"，而是把"敏感度"这个业务属性变成了一个可以被系统强制执行的路由参数。一旦它成为参数，合规就从每次评审的争论题，变成一次配置变更。

迁移路径：几乎所有团队的正确顺序

值得强调的是，这四种形态不是四选一的单选题，而是一条随规模演进的路径。绝大多数成功的落地都遵循同一个顺序：先用云 API 把业务跑通（此阶段任何自建都是在为一个还没被验证的需求付固定成本）；流量与合规压力上来后引入网关做混合（先有分流能力，再谈自建）；把最大宗、最简单的那类任务迁到自建小模型（这是投入产出比最高的一步）；只有当私有部分的负载稳定到能填满 GPU 时，才考虑扩大自建规模。反过来先建集群再找负载的团队，几乎都在为空转付费。

  • 决策按合规 → SLA → 运维 → 成本的顺序过滤，成本放最后
  • 用真实峰谷曲线算加权利用率，再折算单位 token 成本
  • 把 GPU 账单除以 0.35 当作全成本下界，明确写进预算
  • 先建统一网关再谈自建，让分流成为一处强制执行的配置
  • 先迁"大宗且简单"的任务到自建小模型，这是回报最高的一步
  • 用 30 天真实流量验证单位经济性，再决定扩不扩集群
  • 夜间用离线批任务填谷，把利用率从 30% 拉到 60% 以上
  • 统一走 OpenAI 兼容协议，为换后端留一条改 base URL 的后路
  • 不要用满载吞吐算成本，那是永远达不到的理想值
  • 不要拿旗舰 API 单价当唯一基准，先试试能不能降档
  • 不要让业务代码自己判断走公有还是私有，一定要过网关
  • 不要让故障转移越过合规边界，宁可失败也不要越界出域
  • 不要在没有值班表和告警面板的情况下上自建生产服务
  • 不要按峰值配置硬件，那等于长期为空转的算力付费
  • 不要把"用了云"和"数据出域"划等号，托管推理是有效中间态
  • 不要在业务还没验证时就自建，那是为不确定的需求付固定成本

部署选型没有标准答案，但有标准顺序。合规圈定候选集，SLA 淘汰不可行项，运维能力决定能不能长期活着，成本只负责在剩下的选项里挑一个。这个顺序在任何行业、任何规模都不会变——变的只是每一层过滤掉多少选项。

Q&A

自建大模型到底在什么调用量下才比 API 便宜？

没有单一阈值，它同时取决于对比的是哪一档 API、用的什么硬件、以及最关键的 GPU 利用率。一个可操作的推导是：把 GPU 月租金除以 0.35 得到含人力的全成本，再除以 API 单价得到平衡点 token 量。按 2026 年的价格，单卡 H100 全成本约 5,800 美元/月，对旗舰 API（约 7.5 美元/百万 token）的平衡点在 7.7 亿 token/月，也就是每天约 2,600 万 token；对低价 API（0.5 美元/百万 token）则要每天约 3.9 亿 token，单卡根本达不到。多方 2026 年的分析给出的经验区间是：对旗舰 API 约 2-5 百万 token/天起步，对低价 API 需要 1,500-2,500 万 token/天以上。还要做一次可行性校验——如果算出的平衡点超过该配置的物理日产能，说明这条路在数学上就不成立。

为什么 GPU 租金只占自建成本的三分之一？剩下的钱花在哪了？

剩下的主要是四块。第一是运维人力，这是最大的一块，一个自建推理服务通常需要 0.25 到 1.5 个 FTE 的 MLOps 投入，按人力成本折算往往超过 GPU 账单本身。第二是版本维护，NVIDIA 驱动、CUDA、cuDNN、推理引擎、模型权重五层组件各有发布节奏，每次重要升级消耗 1-3 个工程日，稳态每月还要 8-20 小时。第三是可观测与评测栈，Prometheus、指标面板、回归评测集这些要么买 SaaS 每月几百到几千美元，要么自建再占 0.1 FTE。第四是冗余与故障成本，包括为可用性做的备用容量，以及第一次线上事故的代价——业内的说法是首次 Sev-1 的损失往往超过半年的 API 溢价。多份 2026 年的 TCO 研究一致给出的比例是 GPU 硬件只占真实成本的 30%-40%。

托管推理（Bedrock、SageMaker、百炼这类）和云 API 到底差在哪？

差别在数据边界和控制力，不在"是不是云"。公共云 API 是把请求发到厂商的共享推理端点，内容离开你的网络边界，模型版本由厂商控制，你还会和其他租户共享限流池。托管推理则是在你自己的云账户和 VPC 内起专属实例或专属吞吐，请求不进入模型厂商的公共端点，很多平台还允许你上传自己微调的权重、锁定模型版本、挂上云厂商已有的合规资质与审计能力。代价是你要为实例常驻付费（有闲置浪费），并且会对特定云厂商产生绑定。它的定位很明确：当合规要求是"不能进第三方模型服务"但不是"必须在自有机房"时，托管推理是成本和风险都更低的正确答案。

混合方案的分流规则应该按什么维度切？

核心是两个正交维度：敏感度决定"能不能出域"，任务复杂度决定"需不需要旗舰模型"。高敏感的简单任务走私有集群的小模型，成本最低；高敏感的复杂任务走私有集群的大模型，或者先脱敏再考虑出域；低敏感的简单任务优先走私有小模型或低价 API；低敏感的复杂任务走公有旗舰 API，这类需求不值得为它自建。除此之外还应把私有集群负载、成本预算水位、后端健康度作为动态路由信号，让网关在集群拥堵时把低敏感流量溢出到 API、在预算逼近上限时把可降级任务切回私有。有一条铁律：故障转移不得越过合规边界，私有后端挂了就让高敏感请求失败告警，绝不能自动切到出域后端。

合规要求私有化，但预算只够买两张消费级卡，怎么办？

先把问题拆开：合规约束的是数据流向，不是模型规模。可行的路径有几条并且通常要组合使用。其一是模型降档加量化，用 7B-14B 的量化模型覆盖分类、抽取、改写、检索问答这类占比最大的简单任务，这类任务对模型能力的要求远低于直觉；其二是引入脱敏网关，把请求中的敏感标识符替换为哈希令牌后，其中一部分就可以合法地走云 API，红线守住了但成本释放了；其三是任务路由，只有真正复杂的推理才唤醒本地大模型，实践中这能把本地算力峰值需求压掉 40% 以上；其四是引入检索增强，用私有知识库补足小模型的知识短板，比堆参数便宜得多。如果做完这四步能力还不够，那才是真正需要申请预算加卡的时刻，而且此时你有实测数据支撑。

为什么说"自建真正赚钱的地方是小模型跑大批量"？

因为盈亏平衡点由固定成本决定，而日产能由模型规模决定，两者是解耦的。同一块 H100，跑 70B FP8 的生产吞吐约 400 tok/s，日产能上限约 3,500 万 token，而它对旗舰 API 的平衡点就在 2,600 万 token/天附近——几乎贴着天花板，意味着必须常年跑在 75% 以上利用率才真的划算，而真实利用率的中位数只有 40%。换成同一块卡跑 7B-14B，吞吐能到几千 tok/s，日产能 2.5-5 亿 token，平衡点却一分没变，裕度是十倍级的。这就是为什么 2026 年的主流实践是"自建小模型接海量长尾任务、旗舰能力留给 API"，实测这种选择性自建通常能把总 AI 支出压掉 40%-70%。

低价 API 越来越便宜，自建是不是彻底没意义了？

纯粹以省钱为目的的自建，在低价 API 面前确实基本算不过账了，这是 2026 年一个必须承认的现实——对这一档 API 的自建平衡点普遍要求每天上亿 token 起步。但自建的理由从来不只有成本，还有三条依然成立：一是合规，数据不能离开自有网络时 API 无论多便宜都不是选项；二是延迟，跨公网 RTT 一百多毫秒是物理事实，需要百毫秒级硬实时的链路只能自建；三是模型资产，深度微调的权重是核心资产，需要冻结版本、需要定制量化裁剪时也只有自建能做到。判断方法很简单：如果你自建的唯一理由是"想省钱"，那大概率不该建；如果理由里包含上面三条中的任何一条，成本就只是在既定路径上做优化。

已经建了集群但利用率上不去，有什么补救办法？

核心思路是给谷段找负载，让同一块卡在闲的时候也在产出。最直接的是错峰复用：把文档批量向量化、历史数据摘要、离线评测、数据清洗这类不要求实时性的任务排到夜间和周末跑，这一招通常能把利用率从 20%-30% 拉到 60% 上下，单位成本随之下降一半以上。其次是多模型共部署，一块 80GB 的卡跑一个 INT4 的 7B 模型只占 4GB 左右，剩下的空间完全可以再放一个大模型或多个微调变体，用 LoRA 复用同一份底座权重。第三是把原本走 API 的低敏感流量收回来一部分，用网关按集群水位动态调节分流比例，让私有集群优先吃满再溢出。第四是承认沉没成本，如果做完这些利用率仍然长期低于 40%，把峰值容量退租、改成稳态配置加 API 溢出的混合模式，通常比继续硬撑更划算。

怎么在两周内做出一个有依据的部署决策，而不是靠拍脑袋？

按四个维度的顺序各做一件事，两周足够。第一步用两天时间找法务或合规团队把数据边界问到明确结论，输出是一张"哪类请求允许走到哪一层"的表，这一步直接圈定候选方案集合。第二步用两天梳理业务的延迟要求和峰值 QPS，特别是确认是否存在百毫秒级的硬实时链路。第三步用一天做运维能力的诚实评估，问题只有一个：半年后谁在值班、故障时谁被叫醒，答不上来就把自建方案降级为托管推理。第四步用剩下一周做真实数据的成本测算，关键是导出至少 30 天的调用日志，统计任务类型分布、token 量分布和小时级峰谷曲线，然后按本文的三步法算加权利用率下的单位成本。做完这四步，结论通常是自明的，而且它有据可查，经得起复盘。
