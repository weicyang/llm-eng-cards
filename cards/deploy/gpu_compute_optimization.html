DP19 · GPU 算力瓶颈与优化

GPU 利用率低 → 全功能GPU → MUSA 架构 → 计算核心共享电路 → 动态调度 → 万卡协同

榨干 GPU 算力的全部故事围绕两个字——"别等"：别让核心等数据（访存优化），别让数据等核心（算子融合与流水线），别让卡等卡（集合通信与超节点）。硬件、架构、系统三层协同，才能把标称算力变成真实吞吐。

一、GPU 为什么在"摸鱼"：利用率低的三大原因

GPU 内部有成千上万个计算核心，纸面算力动辄几百上千 TFLOPS，但实际跑大模型时，这些核心大部分时间都在"摸鱼"。统计下来，真正用于有效计算的时间往往不足六成。核心们的时间主要浪费在三种等待上：

等待类型等什么根因对应优化手段
等数据等内存把权重/激活搬进计算单元算力增速远快于显存带宽增速（访存墙）算子融合、量化、增大 batch
等指令等任务分发和调度小算子太多、调度开销占比高算子融合、CUDA Graph、编译优化
等同步等其他核心/其他卡完成负载不均、梯度同步、流水气泡动态调度、通信重叠、负载均衡

业界用 MFU（Model FLOPs Utilization，模型算力利用率）来量化这件事：实际有效算力 ÷ 硬件理论峰值算力。大规模训练场景下，MFU 普遍只有 30%~50%——也就是说，花几千万买的卡，一半时间在空转。提升 MFU 的每一个百分点，都是真金白银。

GPU 像一座有上万名工人的超级工厂：原料（数据）运不进来、工单（指令）发不下去、完工还要等全员集合点名（同步），真正开工的时间不到六成——优化的本质就是消灭这三种等待。

二、算力与带宽：屋顶线下的 GPU

三种等待里最致命的是"等数据"，因为它由物理规律决定：过去十年 GPU 算力增长了近百倍，而HBM（高带宽显存）的带宽只增长了十几倍，两者之间的剪刀差就是访存墙（Memory Wall）。判断一个算子是否被访存墙卡住，工程上常用屋顶线模型（Roofline Model）：横轴是算术强度（Arithmetic Intensity）——每从内存搬运 1 字节数据能做多少次浮点运算（FLOPs/Byte），纵轴是实际可达算力。

以 NVIDIA H100 SXM 为例：FP16/BF16 算力 989 TFLOPS，HBM3 带宽 3.35 TB/s，拐点约在 295 FLOPs/Byte——算术强度低于 295 的算子，带宽就是天花板，堆算力毫无意义。

屋顶线模型是一把尺子：算术强度低于拐点，再猛的算力也是摆设，瓶颈在"运数据"；高于拐点，才轮到算力说话。优化前先量一量，方向错了努力全白费。

三、全功能 GPU：一张卡吃下全精度

不同任务对数值精度的需求天差地别：科学计算要 FP64 的双精度，AI 训练用 TF32/BF16 就够，推理甚至可以压到 INT8/INT4，而图形渲染又离不开 FP32。传统做法是不同场景买不同的卡，数据中心里塞满异构硬件，利用率可想而知。全功能 GPU（以摩尔线程为代表）的思路是：用共享电路设计让同一套计算核心支持全精度场景——同一块硅片，既能跑 FP64 科学计算，也能跑 BF16 训练和 INT8 推理，还能做 FP32 渲染。

精度典型场景为什么用这个精度
FP64科学计算（物理仿真、气象）误差累积敏感，必须双精度
TF32 / BF16AI 训练梯度对数值范围敏感，BF16 指数位与 FP32 相同，训练稳定且省一半带宽
INT8 / INT4AI 推理权重已收敛，低精度量化几乎不掉点，吞吐翻倍
FP32图形渲染光照、几何计算的标准精度
数据格式位宽指数/尾数位特点
FP3232 bit8 / 23通用基准，显存占用大
TF3219 bit8 / 10NVIDIA 训练加速格式，范围同 FP32
BF1616 bit8 / 7范围大、精度低，训练首选
FP1616 bit5 / 10精度高、范围小，易溢出需 loss scaling
INT88 bit—推理量化主力，带宽占用降为 1/4

共享电路的工程价值在于"一卡多用"：白天跑训练，晚上跑推理，周末还能接渲染农场——硬件利用率从"专用卡只能干一件事"变成"全场景通吃"。对预算有限的数据中心，这比峰值算力数字更实际。

全功能 GPU 像一口"万能灶"：同一套灶具，大火（FP64）炖科学计算，中火（BF16）炒 AI 训练，小火（INT8）煎推理——不用为每道菜单独买灶，厨房利用率自然上去了。

四、MUSA 架构：动态调度避免忙闲不均

有了全精度的计算核心，还差一个聪明的"调度员"。传统 GPU 调度比较僵硬：任务按提交顺序排队，资源按固定规则分配，经常出现"一边核心在排队等任务，一边核心在空转"的忙闲不均。MUSA（Moore Threads Unified System Architecture）是摩尔线程的统一系统架构，核心能力是动态调度：根据任务的实时需求，把计算核心、内存控制器、通信单元灵活分配给最需要的任务，让硬件资源始终流向最忙的地方。

静态调度 (传统方式): 任务A ████████░░░░░░░░ ← 占着资源但后期空闲 任务B ░░░░░░░░████████ ← 前期只能干等 核心1 [A][A][空][空] ← 忙闲不均, 利用率低 MUSA 动态调度: 任务A ████████ 任务B ░░████████████ 核心1 [A][A][B][B] ← 实时重分配, 无缝衔接 核心2 [B][A][B][B] ← 谁忙给谁, 全程无空转
对比项静态调度动态调度（MUSA）
资源分配提交时固定，运行中不变按实时负载动态调整
忙闲不均常见，空闲核心无法被借用空闲资源实时补给繁忙任务
多任务混跑互相干扰，性能抖动隔离 + 弹性分配，干扰可控
生态兼容—提供 musify 等工具转换 CUDA 代码，降低迁移成本

动态调度像智能红绿灯：哪条车道车多就把绿灯时间给谁，而不是每个方向固定 30 秒——路口通行效率（硬件利用率）靠的是"看见流量"，而不是"遵守规则"。

五、万卡协同：超节点与集合通信

单卡算力再强也有上限，训练千亿级大模型必须上万张卡。卡一多，问题就从"算得快"变成"配合得好"：跨卡通信延迟、梯度数据一致性、故障恢复，任何一环掉链子，几千张卡就得停下来陪跑。万卡协同的核心技术栈包括：

技术作用关键手段
超节点架构把多张卡组成一个内部高速互联的节点节点内 NVLink/光模块直连，节点间组带宽网络
HCCL 集合通信高效完成卡间数据交换NPU Direct 绕开 CPU 直接传输，降低通信延迟
数据并行扩大吞吐各节点处理不同数据批次，AllReduce 同步梯度
张量并行切开单层大矩阵节点内切分权重，高频通信走节点内链路
流水线并行按层切分模型微批次流水接力，压缩气泡空转
┌─ 超节点 A (节点内高速互联) ────────────┐ │ GPU₀ ── GPU₁ ── GPU₂ ── … ── GPUₙ │ │ └─────── NVLink / 光模块直连 ────────┘│ └──────────────────┬────────────────────┘ │ 节点间网络 (RDMA / RoCE) ┌──────────────────┼────────────────────┐ │ 超节点A ⇄ 超节点B ⇄ 超节点C ⇄ … │ │ │ │ 数据并行: 各节点算不同数据批次 │ │ 张量并行: 节点内切矩阵 (通信不出节点) │ │ 流水线并行: 节点间按层接力 │ │ 每步结束: AllReduce 全员对表同步梯度 │ └──────────────────────────────────────────┘

这里的关键设计原则是通信分级：通信频率最高的张量并行被严格限制在节点内部（走 NVLink 这类每秒数百 GB 的链路），通信量大的数据并行梯度同步走节点间网络，并用计算-通信重叠把同步时间藏在计算背后。万卡训练的本质，就是把每一种通信都安排到它该去的链路上。

万卡训练是一场万人接力赛：超节点是同一间更衣室的队友（内部传接快），节点间靠光模块"高速公路"递棒，AllReduce 是每轮结束后的全员对表——棒掉一次，全场都得等。

六、榨干算力的工程清单

把前五节的认知落到工程上，优化决策可以浓缩成三个问题：

性能不达标？先问三个问题: ① 算术强度够吗？ 不够 → 访存受限 → 算子融合 / FlashAttention / 量化 INT8 ② 精度可以降吗？ 可以 → 训练换 BF16 混合精度 / 推理上 INT8-INT4 → 带宽占用减半起步, 吞吐近翻倍 ③ 卡在等卡吗？ 是 → 通信与计算重叠 / 超节点内高频通信 → 梯度累积减少同步次数 / 负载均衡
层面技术收益量级
算子层算子融合 / FlashAttention注意力 2~4 倍加速
精度层BF16 混合精度训练 / INT8 推理带宽占用减半~四分之一
显存层KV Cache + PagedAttention推理吞吐 2~4 倍
通信层计算-通信重叠、梯度累积同步开销大幅隐藏
系统层超节点 + 动态调度MFU 从 30% 级提升到 50% 级
生产案例 · FlashAttention 把注意力从"访存大户"变成"算力标兵"：背景是标准注意力实现要把 n×n 的注意力矩阵反复写回 HBM——序列长度 4096 时，单头单层就是 1600 万个元素来回搬运。问题是注意力因此成为典型的访存受限算子，GPU 算力利用率长期不到 30%，训练时间被"搬数据"吃掉大半。方案是 FlashAttention：把 Q·Kᵀ、softmax、加权 V 三步融合为一个算子，用分块 + 在线 softmax 技巧让所有中间结果留在片上 SRAM，永不写回 HBM。效果：FlashAttention-2 在 A100 上达到理论算力峰值的约 70%，相比标准实现端到端训练提速 15% 以上，如今已是 PyTorch 和所有主流大模型框架的默认实现——一个算子层面的改动，撬动了整个行业的训练成本。
生产案例 · vLLM 用"虚拟内存"思路救活推理吞吐：背景是在线推理服务中，KV Cache 必须为每个请求按最大上下文长度预分配显存——一个 70B 模型 2048 长度的 KV Cache 约 5GB，32 并发就是 160GB 起步。问题是请求实际用不满预分配的空间，实测浪费高达 60%~80%，显存被"占座"导致并发上不去，吞吐被死死卡住。方案是 vLLM 的 PagedAttention：借鉴操作系统虚拟内存，把 KV Cache 切成固定大小的"页"按需分配，请求结束立即回收。效果：显存浪费降到 4% 以内，同等硬件下吞吐提升 2~4 倍，vLLM 由此成为开源推理引擎的事实标准——又是"别等、别浪费"这条主线的胜利。
  • 优化前先用屋顶线模型判断瓶颈在算力还是带宽，再选手段
  • 训练默认开 BF16 混合精度，推理能上 INT8 就上 INT8
  • 推理服务用 PagedAttention 类方案管理 KV Cache，别让显存被占座
  • 万卡训练把高频通信（张量并行）锁在节点内，梯度同步与计算重叠
  • 不要看到"算力 989 TFLOPS"就以为能跑满——decode 阶段可能连 5% 都用不上
  • 不要对访存受限算子堆算力，那是给堵车的路修停车场
  • 不要忽略 MFU：30% 和 50% 的差距，就是几千万硬件投资打水漂的比例
  • 不要在节点间跑张量并行——层内通信频率极高，跨节点延迟会拖垮全局

GPU 优化有严格的顺序：先判断瓶颈（屋顶线），再降精度（BF16/INT8），然后融合算子（FlashAttention），最后治通信（超节点/重叠）——顺序反了，就是用战术上的勤奋掩盖战略上的懒惰。

Q&A

GPU 利用率为什么低？如何提升？
GPU 利用率低的核心原因是计算核心大量时间在等待而非计算，主要有三类：等数据（内存带宽跟不上算力，即访存墙）、等指令（小算子太多、调度开销大）、等同步（负载不均、梯度同步、流水气泡）。实际训练中 MFU 普遍只有 30%~50%。提升手段要对症下药：访存瓶颈用算子融合、量化和增大 batch 来提高算术强度；调度瓶颈用算子融合和 CUDA Graph 减少小算子；同步瓶颈用动态调度、通信-计算重叠和负载均衡。关键是先定位瓶颈类型再选手段，对访存受限的算子堆算力是无效的。
什么是全功能 GPU？它的核心创新是什么？
全功能 GPU 是指同一块芯片支持全精度计算场景的 GPU：FP64 用于科学计算，TF32/BF16 用于 AI 训练，INT8/INT4 用于 AI 推理，FP32 用于图形渲染。它的核心创新是共享电路设计——传统方案中不同精度往往需要不同的专用硬件，导致数据中心堆满异构卡、各自利用率低下；共享电路让同一套计算核心通过配置切换精度，一块硅片覆盖所有场景。工程价值在于"一卡多用"：同一批卡白天跑训练、晚上跑推理、周末接渲染任务，硬件利用率从专用卡的单场景变成全场景通吃，对预算有限的数据中心比峰值算力数字更实际。
什么是屋顶线模型？怎么用它判断算子是计算受限还是访存受限？
屋顶线模型是判断算子性能上限的工具：纵轴是实际可达算力，横轴是算术强度（每搬运 1 字节数据做多少次浮点运算）。图中有两条线——水平的算力天花板（如 H100 的 989 TFLOPS）和斜向上的带宽线（带宽 × 算术强度），两线交点就是拐点（H100 约 295 FLOPs/Byte）。算术强度低于拐点的算子落在带宽斜坡上，属于访存受限，瓶颈在搬数据，堆算力无效，该做算子融合、量化或增大 batch；高于拐点的算子顶到算力天花板，属于计算受限，该优化 Tensor Core 利用率和混合精度。例如 decode 阶段 batch=1 时算术强度只有 1~2，是典型的访存受限；大 batch 训练的矩阵乘算术强度上千，是典型的计算受限。
为什么大模型 decode 阶段是访存瓶颈而不是计算瓶颈？
因为 decode 阶段是逐 token 生成的自回归过程：每生成一个 token，都要把模型全部权重从显存读进计算单元一次，但每个权重只参与极少量的计算。以 batch=1 为例，读入 1 个 FP16 权重（2 字节）只做约 2 次乘加运算，算术强度约 1~2 FLOPs/Byte，远低于 H100 约 295 的拐点——算力 989 TFLOPS 几乎完全闲置，时间全花在 3.35 TB/s 的带宽搬权重上。这就是为什么 decode 速度主要取决于显存带宽而非算力，也是为什么增大 batch（多个请求共享一次权重读取）、INT8 量化（权重减半）和 KV Cache 优化能直接提升吞吐——它们都在提高算术强度或减少搬运量。
数据并行、张量并行、流水线并行该怎么选？
选择取决于模型形状和集群拓扑。数据并行：每卡一份完整模型、处理不同数据批次，只需周期性 AllReduce 同步梯度，实现最简单、扩展性最好，模型装得下就优先用它。张量并行：把单层权重矩阵切开分给多卡，通信发生在每一层内部、频率极高，必须限制在节点内走 NVLink 这类高速链路，跨节点用会被延迟拖垮。流水线并行：按层把模型切到不同节点，层间只传激活值、通信量小，适合跨节点，但要注意微批次划分以压缩流水气泡。实践中大规模训练是三者叠加：节点内张量并行、节点间流水线并行、全局再套数据并行，MoE 模型还会在专家维度加一层专家并行。
万卡训练中 AllReduce 梯度同步为什么成为瓶颈？怎么优化？
数据并行下，每完成一步训练，所有卡都要通过 AllReduce 交换并平均梯度，保证各卡模型参数一致。万卡规模下这个操作的数据量等于整个模型的参数量（千亿模型就是数百 GB），而且它是同步屏障——最慢的一张卡决定全场等待时间，任何一条链路抖动都会放大成全局延迟。优化手段有几类：一是通信-计算重叠，把梯度同步拆到反向传播过程中，边算边传，把通信时间藏在计算背后；二是梯度累积，多个 micro-step 攒一批再同步，减少同步次数；三是拓扑优化，用超节点把高频通信限制在节点内、节点间走 RDMA 高速网络；四是算法层面用梯度压缩或异步更新降低通信量。字节、Meta 等公司的万卡实践都表明，同步效率直接决定 MFU 能到 30% 还是 50%。
混合精度训练为什么能提速又不损失精度？
混合精度训练用 BF16/FP16 做前向和反向计算，用 FP32 保存主权重。提速来自两方面：低精度数据只有一半的位宽，显存占用和搬运量直接减半，算术强度翻倍；同时 Tensor Core 对低精度有数倍于 FP32 的吞吐。不损失精度的关键在于三个设计：一是保留 FP32 主权重，参数更新的累积误差不会因低精度被截断；二是 loss scaling（FP16 场景）把小梯度放大到可表示范围，反向后再缩回来，避免梯度下溢；三是 BF16 本身指数位与 FP32 相同（8 位），数值范围一致，几乎不需要 loss scaling 就能稳定训练。这也是为什么 BF16 成为大模型训练的事实标准——它用一半的带宽换来了几乎无损的稳定性。
