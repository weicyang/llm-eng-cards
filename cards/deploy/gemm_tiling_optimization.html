DP26 · GEMM 与 Tiling 分块优化

Transformer 的矩阵形状与 FLOPs 账 / naive GEMM 为什么必然访存受限 / shared memory tile 与 register tile 的定量推导 / MMA 与 wgmma 形状约束 / double buffering 与 split-K / TMA / cuBLAS 与 CUTLASS 与 OpenAI Triton 的分工

GEMM 的 FLOPs 是 O(MNK)，而数据量只有 O(MK + KN + MN)。这个差值就是全部优化空间——分块做的唯一一件事，就是把"每搬一个字节能算几次"从 0.5 提到几十上百，让计算单元而不是显存带宽成为瓶颈。分块不是技巧，它是这个差值的必然产物。

一、GEMM 在 Transformer 里占多少

优化之前先算账：如果 GEMM 只占 20% 的时间，把它加速一倍也只换来 10% 的端到端收益。所以先把 Transformer 的矩阵乘拆开，看清每一个的形状和 FLOPs 权重。GEMM（General Matrix Multiply，通用矩阵乘，形式为 C = αAB + βC）在 Transformer 里出现在三个地方：注意力的 QKV 与输出投影、FFN 的三个线性层、以及最后的词表投影 lm_head。

以 Llama-3-8B 为例，逐个算 FLOPs

取公开配置：hidden 4096、FFN 中间层 14336、32 层、32 个查询头配 8 个 KV 头（GQA，head_dim 128）、词表 128256。单 token 一次前向的乘加按 2 FLOPs 计，M 是 token 数（prefill 时是 batch × 序列长度，decode 时就是 batch）：

这张表有两处值得停下来看。第一，FFN 吃掉了约四分之三的 GEMM FLOPs（50.1% + 25.0% = 75.1%），注意力的四个投影合起来只有 18%。这解释了为什么 MoE 把专家放在 FFN 位置——那里才是算力真正花掉的地方。第二，把 15.01 GFLOPs 和"每 token 约 2N FLOPs"的经验公式对一下：模型 8.03 B 参数减去 0.525 B 的 embedding（embedding 是查表，不产生 FLOPs），剩 7.5 B，乘 2 正好 15.0 GFLOPs，两条路算出同一个数，说明账没算错。

注意力分数本身（QKᵗ 和 PV）没有列进上表，因为它的 FLOPs 依赖序列长度：每层每 token 是 4 × S × 4096 FLOPs。S = 2048 时全模型约 1.07 GFLOPs，相当于总量的 6.7%；但它随 S 线性增长，S = 32768 时会涨到约 17 GFLOPs，反超所有线性层之和。这也是长上下文优化的全部动机所在（见 T21 · Transformer 长文本优化技术）。

M 维度决定这个 GEMM 是什么性质的问题

同一组权重矩阵，在训练、prefill、decode 三个场景下是完全不同的计算问题，区别只在 M：

场景M 的量级矩阵形态瓶颈性质分块还有用吗
训练 / prefill数千到数万（batch × 序列长度）三个维度都大，标准 GEMM算力受限，Tensor Core 是主角这是分块的主战场
decode，batch 大数十到数百瘦长矩阵（M ≪ K, N）介于两者之间，M 越大越靠算力侧有用，但 M 方向的 tile 用不满
decode，batch = 11退化为 GEMV（矩阵乘向量）纯访存受限，权重读一次只算一次基本无用，要靠 batching 和量化

最后一行是整个大模型推理经济学的根源：batch = 1 的 decode 每读一个权重只做两次浮点运算，算术强度约 0.5，而 H100 的屋顶线拐点在 295 附近（拐点的推导和各代卡的数值见 DP19 · GPU 算力瓶颈与优化），差了近三个数量级。所以 decode 阶段再怎么优化 GEMM kernel 都是徒劳，唯一的出路是提高 M（连续批处理）或减少搬运量（量化），前者见 DP10 · 大模型推理性能瓶颈分析，后者见 DP13 · 模型量化。本文后面讨论的所有分块技术，默认针对的是训练与 prefill 这类 M 足够大的场景。

先算账再优化：Transformer 的 GEMM FLOPs 里 FFN 占约四分之三，注意力投影不到两成。但 FLOPs 占比大不等于时间占比大——M = 1 的 decode 里，FLOPs 最多的 FFN 反而跑得离峰值最远，因为它的瓶颈根本不是算力。

二、naive GEMM 的访存账

现在写一个最直白的 GEMM：每个线程负责输出矩阵 C 的一个元素，沿 K 方向循环累加。这份代码功能完全正确，性能却只有 cuBLAS 的百分之几。原因不在指令效率，而在一笔可以精确算出来的访存账。

// naive GEMM：每线程算一个 C 元素（这是反面教材）
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
float acc = 0.f;
for (int k = 0; k < K; ++k)
    acc += A[row * K + k] * B[k * N + col];   // 两次全局访存，两次浮点运算
C[row * N + col] = acc;

算术强度只有 O(1)

算术强度（Arithmetic Intensity，每从内存搬运 1 字节数据所能完成的浮点运算次数）是判断瓶颈归属的核心量，定义与屋顶线模型的关系见 DP19，这里直接用。对上面这段代码，单个输出元素的账是：

算术强度 = 2K FLOPs ÷ (2K × 元素字节数) = 1 / 元素字节数

FP16 是 2 字节，代入得 0.5 FLOP/Byte；FP32 是 0.25 FLOP/Byte。注意这个结果里没有 K——循环再长也没用，因为每多一次迭代，既多两次运算也多两次访存，比值恒定。这就是"算术强度只有 O(1)"的准确含义：它是常数，不随问题规模改善。而 H100 的屋顶线拐点约在 295 FLOP/Byte，0.5 距离它差了约 590 倍。结论不是"这份代码写得不够好"，而是"任何不做数据复用的 GEMM 实现都必然访存受限"——这是算法结构决定的，不是编码水平决定的。

换成总搬运量看，浪费更直观

275 GB 是个什么概念？H100 的 HBM 带宽 3.35 TB/s，光搬这些数据就要 82 ms，而这个 GEMM 的计算量 2 × 4096³ = 137 GFLOPs，在 989 TFLOPS 的 BF16 Tensor Core 上只需要 0.14 ms。算 0.14 毫秒的活，搬了 82 毫秒的数据，差了约 590 倍——这个比值和"拐点 295 除以算术强度 0.5"算出来的完全一致，两条路互相验证。

naive GEMM 的问题不是"慢"，是"重复搬"。A 的每个元素被从显存读了 N 次，B 的每个元素被读了 M 次。把它想成从仓库取零件：每装一个成品就跑一趟仓库拿一颗螺丝，而不是先搬一整箱螺丝到工位旁边。分块就是"搬一箱到工位旁"。

三、两级分块：把算术强度提上去

分块的思路一句话就能说完：把输出矩阵切成小块，每块的计算所需的输入数据一次性搬到更快的存储里，在那里被复用多次。关键在于 GPU 的存储层次有两级需要分别对付（层次的容量与延迟阶梯见 DP25 · GPU 执行模型与存储层次），所以分块也是两级的：shared memory tile 治 HBM 流量，register tile 治 shared memory 流量。CUTLASS 把这套结构写成了一个五层嵌套的循环，从外到内依次是 threadblock tile、warp tile、instruction tile，每一层对应硬件的一个并发层级。

第一级：block tile 把 HBM 流量降到 1/BM + 1/BN

设 threadblock 负责输出的一块 BM × BN，沿 K 方向按 BK 分步推进。因为 A 的一个 tile 被这一行上的 N/BN 个 block 各读一次、B 的一个 tile 被这一列上的 M/BM 个 block 各读一次，总元素搬运量是 MNK × (1/BM + 1/BN)，于是：

HBM 侧算术强度 = 2 ÷ [(1/BM + 1/BN) × 元素字节数]

代入几组常用配置（FP16，2 字节）就能看出 tile 尺寸的杠杆有多大：

block tile（BM × BN）HBM 侧算术强度相对 naivetile 的 shared memory 用量（BK=32，双缓冲）H100 上能驻留几个 block

256 × 256128256×64 KB3

三条结论从这张表里直接读出来。第一，tile 越大算术强度越高，但增长是次线性的——从 32 到 128 提升 4 倍，从 128 到 256 只提升 2 倍。第二，tile 越大能驻留的 block 越少，H100 的 228 KB shared memory 在 128×128 双缓冲配置下只够 7 个 block；再加上寄存器压力（累加器 128×128 个 FP32 要分摊到 block 的所有线程上），实际 occupancy 会相当低。这正是 CUTLASS 文档指出的现象：GEMM 的累加器占掉线程寄存器预算的一半以上，导致 GEMM 的 occupancy 天生比别的负载低——但这不是问题，因为 Tensor Core 不需要很多 warp 就能喂饱（见 DP25 第四节）。第三，也是最容易被忽略的一点：128×128 给出的 64 FLOP/Byte 仍然低于 H100 的 295 拐点。那为什么实测的 cuBLAS 大 GEMM 能跑到峰值的八九成？答案是这个公式假定了"所有 tile 都从 HBM 读"，而现实里 L2（50 MB）会捕获大量跨 block 的复用——这就把话题引到了 block 的排布顺序上。

threadblock 的排布顺序：让 L2 帮上忙

block 的执行顺序决定了同时在跑的那批 block 是否共享输入 tile。默认的行主序排布会让一波 block 横扫输出矩阵的一整行，它们共享 A 的 tile 但 B 的 tile 全不相同；改成把若干行"打包成组"再换列（CUTLASS 叫 threadblock rasterization，OpenAI Triton 教程里叫 grouped ordering），同时在跑的 block 就会聚成一个方块，A 和 B 的 tile 都能复用。Triton 官方矩阵乘教程给了一个非常清晰的算例：一个 9×9 块的矩阵乘，按行主序算出前 9 个输出块需要加载 90 个输入块，按分组顺序只需要 54 个——降低 40%，代码改动只有几行下标算术。

第二级：register tile 把 shared memory 流量再降一个量级

数据搬进 shared memory 之后，还有第二笔账：每个线程从 shared memory 取操作数的次数。如果一个线程只负责一个输出元素，那它每走一步 K 就要读 A、B 各一个元素做一次乘加，shared memory 侧的算术强度又回到了 0.5。解法同构：让每个线程负责一小块 TM × TN 的输出，把这块的累加器全部放在寄存器里。此时一步 K 里读 TM + TN 个元素，却能做 TM × TN 次乘加：

Shared memory 侧算术强度 = 2 × TM × TN ÷ [(TM + TN) × 元素字节数]
register tile（TM × TN）每步 K 的 smem 读取每步 K 的乘加次数smem 侧算术强度（FP16）每线程累加器寄存器数
1 × 1210.51
4 × 48162.016

8 × 16241285.3128
16 × 16322568.0256（超出单线程 255 上限）

最后一行是个硬边界：单线程最多 255 个寄存器，16×16 的累加器就已经把预算吃光，一定 spill。这就是两级分块的调优本质——block tile 的上限由 shared memory 容量决定，register tile 的上限由寄存器预算决定，两个都是硬墙，调 tile 尺寸就是在两面墙之间找那个既有足够复用度、又不撞墙的点。

把极简的分块骨架写出来，就三行关键逻辑（省略边界处理与同步细节）：

// 两级分块的骨架：外层搬 tile，内层在寄存器里算
for (kt = 0; kt < K; kt += BK) {
    load_tile(sA, A + kt);  load_tile(sB, B + kt);  __syncthreads();
    for (k = 0; k < BK; ++k)                        // smem → 寄存器
        for (i = 0; i < TM; ++i) for (j = 0; j < TN; ++j)
            acc[i][j] += sA[i][k] * sB[k][j];       // 累加器全程不落地
    __syncthreads();
}
示例场景：一次 tile 尺寸调优的完整账本。某团队为一个 W8A8 量化 GEMM 写 Triton kernel，初版沿用了教程默认的 64×64×32 tile 配置，实测在 [M=4096, K=4096, N=14336] 这个 FFN 形状上只跑到 BF16 cuBLAS 的 54%。Nsight Compute 显示 DRAM Throughput 72%、SM Throughput 48%——偏访存侧，说明复用度不够。按第三节的公式算：64×64 的 HBM 侧算术强度是 32，而 128×128 能到 64。于是把 tile 提到 128×128×32，shared memory 用量从 16 KB 涨到 32 KB（双缓冲），每 SM 驻留 block 从 14 降到 7，实测 occupancy 从 43% 掉到 22%——但 kernel 快了 1.6 倍，因为 DRAM Throughput 降到 41%、SM Throughput 升到 79%，瓶颈成功从访存侧转到算力侧。第二轮再把 GROUP_SIZE_M 从 1 改成 8 启用分组排布，L2 命中率上升，又快了 9%。第三轮尝试 256×128（算术强度 85），驻留 block 降到 4，这次反而慢了 4%——说明已经越过了那个平衡点。最终配置停在 128×128×32 + GROUP_SIZE_M=8，达到 cuBLAS 的 91%。这组数字是构造的示例，但这个调优路径（先用公式估算术强度、再用两个 Speed of Light 确认瓶颈是否转移、最后靠实测找平衡点）可以直接照用，关键是别把中途 occupancy 的下降当成退步。
两级分块是同一个动作做了两遍：第一遍把数据从仓库（HBM）搬到工位旁的料架（shared memory），第二遍把料架上的零件抓到手里（寄存器）再拼装。每一级都在问同一个问题——"搬一次能用几回"。答案从 0.5 变成 64，性能就从百分之几变成八九成。

四、Tensor Core 的形状约束

分块讲完了复用，还剩最内层那个问题：tile 里的乘加到底用什么指令做。走 CUDA Core 的标量 FFMA，一条指令一个 warp 只有 64 FLOPs；走 Tensor Core 的矩阵指令，一条就是几千 FLOPs（对比数据见 DP25 第二节）。代价是 Tensor Core 只吃固定形状的输入，而这个形状约束会一路向上传导，最终变成"你的 hidden_size 必须是某个数的倍数"这种模型设计层面的要求。

Hopper 这一代的变化很值得说清楚：MMA 从"warp 同步"变成了"warpgroup 异步"。wgmma 由 128 个线程协作发射，发射后不阻塞，需要用 fence → commit_group → wait_group 三段式原语来排序，而且操作数可以直接从 shared memory 取、不必先经 ldmatrix 搬进寄存器。这两点合起来，才让第五节要讲的"搬运和计算真正并行"成为可能。M 被固定在 64 的原因也不神秘：固定的 M 让操作数到 Tensor Core 输入端的映射变成静态布线，省掉了昂贵的动态路由。

为什么矩阵维度要对齐到 8 或 16 的倍数

这里有三个不同层次的约束，经常被混成一句"要对齐到 8"，其实后果完全不同：

约束层次具体要求不满足的后果权威出处
① 内存对齐矩阵维度与 leading dimension 乘以元素字节数后能被 16 整除；A/B/C 指针也 16 字节对齐。FP16 即维度为 8 的倍数cuBLAS 11.0 之后仍可用 Tensor Core，但走不了最宽的向量化访存路径，效率下降；FP8 是硬性要求cuBLAS 文档「Tensor Core Usage」列出的 9 条对齐条件
② Tile 量化输出维度能被 threadblock tile 尺寸整除，实践上取 64 的倍数、理想 128~256 的倍数边缘那一排 tile 做了全量计算却只产出部分有用数据，算力按比例白扔NVIDIA《Matrix Multiplication Background User's Guide》
③ Wave 量化tile 总数是 SM 数的整数倍（A100 为 108，H100 SXM5 为 132）最后一"波"只有部分 SM 在干活，其余空转同上，及 GTC「Tensor Core Performance Guide」

NVIDIA 的官方口径在这里有过一次演进，值得说明以免读到旧资料时困惑：cuBLAS 11.0 / cuDNN 7.6.3 之前，维度对齐是使用 Tensor Core 的硬性前提，不满足就直接退回 CUDA Core，实测有 2~4 倍的落差；之后放宽成"不对齐也能用 Tensor Core，但对齐了效率更好"。所以今天的正确表述是：对齐不再是开关，而是效率系数。官方建议是按 16 字节对齐（FP16 即 8 个元素），做不到时退而对齐到更小的 2 的幂仍有帮助；A100 上甚至可以进一步对齐到 128 字节（FP16 即 64 个元素）以获得更高效率。

padding 的代价，其实小得出乎意料

面对不对齐的维度，工程上的标准做法是 padding 到对齐边界。很多人担心"补零不是白算吗"，算一下就知道这笔账极其划算：

场景原始维度padding 后多算的 FLOPs换来的收益
GPT-2 系词表50257（质数）50304 = 128 × 393+0.09%lm_head 从"最差 tile 量化"变成完美整除
hidden 非对齐40904096 = 128 × 32+0.15%所有投影层同时受益

第一行是最经典的例子：50257 是质数，任何 tile 尺寸都除不尽，最后一排 tile 几乎全是浪费；补到 50304 只多算 0.09% 的 FLOPs，却把词表投影这个占总 GEMM 量 7% 的大矩阵从最差情况变成了完美对齐。反过来看现代大模型的配置表——Llama-3 的 4096、14336、1024，Qwen 系的 hidden 与 intermediate，全都是 128 甚至 256 的倍数。这不是审美，是被 Tensor Core 的形状约束反向倒逼出来的设计规范。

示例场景：一个 +7 就废掉三成算力的维度。某团队做领域自适应时给词表新增了 7 个特殊 token，词表从 32000 变成 32007，模型其余配置不动。训练吞吐下降了约 18%，而 FLOPs 只增加了 0.02%。用 Nsight Compute 单独看 lm_head 这个 GEMM：SM Throughput 从 82% 掉到 61%，而且 kernel 选择从 128×256 的大 tile 退到了 64×64 的小 tile（cuBLAS 为了减少量化损失主动选了更小的 tile，代价是算术强度从 85 掉到 32）。根因是 32007 = 3 × 47 × 227，既不满足 16 字节对齐（FP16 需要 8 的倍数），也无法被任何常见 tile 尺寸整除。修法是把词表补到 32128（= 128 × 251），多出的 121 个位置在词表里置为永不采样的占位符，同时给 logits 对应位置加 -inf 掩码保证分布不变。吞吐恢复到基线的 99%，多算的 FLOPs 是 0.4%。这组数字是构造的示例，但"维度加几个就掉一大截吞吐"是真实且高频的故障模式，排查入口就是单独 profile 那个维度异常的 GEMM 看它选了多大的 tile。
Tensor Core 是一台只接受固定尺寸模具的液压机。维度对齐不是为了"让它能用"（现在的库不对齐也能用），而是为了"让它别在边角上空压"。补几个零的代价通常在千分之一以下，而不补的代价可能是两成吞吐——这是性价比最高的一类优化，改一行配置就完事。

五、流水线：双缓冲、split-K 与 TMA

分块解决了"搬得少"，形状对齐解决了"算得快"，还剩最后一个问题：搬的时候能不能同时在算。如果每轮循环都是"搬 tile → 等搬完 → 算 → 等算完 → 搬下一块"，那搬运时间和计算时间是相加的；理想情况应该是两者重叠，总时间等于两者的最大值。这就是流水线要做的事。

双缓冲：用两份缓冲区换来重叠

双缓冲（double buffering，也叫软件流水，在 shared memory 里开两份 tile 缓冲区轮换使用）是最基础的手段。CUTLASS 在两个尺度上同时做这件事：

  • block 尺度：shared memory 里分配两块 tile，一块正在被计算消费，另一块同时在接收下一轮从 HBM 来的数据。
  • warp 尺度：寄存器里分配两份 matrix fragment，一份正在被 Tensor Core 消费，另一份同时在接收从 shared memory 来的数据。

CUTLASS 文档给出的动机说得很直接：GEMM 的累加器占掉线程寄存器预算的一半以上，导致 occupancy 天生偏低，因此 GPU 靠"切换到别的 warp"来掩盖延迟的能力也就弱，只能靠单线程内部的软件流水来自救。这句话解释了一个重要的因果关系——GEMM 之所以必须精心做流水线，恰恰是因为它没法靠高 occupancy 蒙混过去。Ampere 引入 cp.async 之后，缓冲级数可以从 2 提到 3~5 级（CUTLASS 的 Stages 参数），代价是 shared memory 用量按级数线性增长。

Hopper 的 TMA 带来了什么

TMA（Tensor Memory Accelerator，张量内存加速器，Hopper 新增的专用搬运引擎）解决的是一个之前被忽视的开销：在 Ampere 上，即使用了 cp.async 异步拷贝，地址计算本身仍然要由计算 warp 的指令发射带宽来承担——每个线程都得算自己那份地址、做边界判断。多维张量的地址算术相当啰嗦，这部分指令挤占的正是本该发给 Tensor Core 的发射槽。

TMA 把这件事整个搬到硬件里：软件只需要构造一个描述符（说明张量的形状、步长、目标 tile 的坐标与 swizzle 模式），然后由单个线程发一条指令，硬件就会自动完成整块多维 tile 的 global ↔ shared memory 搬运，包括所有地址生成和越界处理。配合 CUTLASS 3.0 引入的 warp 专精化（warp specialization，把 block 内的 warp 分成专职搬运的生产者组和专职计算的消费者组，用异步屏障传递"缓冲区满/空"信号），搬运和计算才真正跑在两套互不抢占的资源上。

split-K：当 K 很大而 M、N 很小

前面所有讨论都假定 M 和 N 足够大，能切出足够多的 block 填满 GPU。但有一类形状会破坏这个假设：M 和 N 都小、K 却很大。此时 block 总数 = (M/BM) × (N/BN) 可能只有个位数，132 个 SM 里绝大多数在空转——不是算力不够，是活没铺开。

split-K（把归约维度 K 切成若干段，交给不同的 block 并行计算部分和，最后再归约相加）就是为此设计的。CUTLASS 的实现需要两个 kernel：先跑一个 partitionedK GEMM 算出各段的部分和写进 workspace，再跑一个 batched reduction kernel 沿 K 方向求和。文档给的例子是 m=128, n=128, k=4096 切成 20 份，前 19 份各取 k=204、最后一份取 k=220。还有一个变体叫 sliced-K，把切分放在 block 内部的 warp 之间，归约成本更低但并行度增益也更小。Hopper 之后 CUTLASS 又提供了 Stream-K 调度器，把工作量按 SM 数均匀摊平，能同时缓解 tile 量化和 wave 量化。

场景特征推荐策略额外成本典型出现位置
M、N、K 都大标准分块 + 多级流水，不用 split-K无训练、长 prefill
M、N 小，K 大（block 数 < SM 数）split-K（跨 block 归约）需 workspace 显存 + 第二个归约 kernel小 batch decode 的投影层、LoRA 的低秩矩阵
M、N 中等，K 大，想省一次 kernel 启动sliced-K（跨 warp 归约）block 内一次小归约中等 batch 的注意力投影
tile 数不是 SM 数整数倍，尾波浪费明显Stream-K 调度器实现复杂度，部分 tile 需跨 SM 归约形状不规则的生产负载
示例场景：LoRA 推理里被 split-K 救回来的两个瘦矩阵。某团队把 LoRA 适配器合进在线推理路径，rank 取 16。合并前的两个 GEMM 形状是 [M=8, K=4096, N=16] 和 [M=8, K=16, N=4096]，profile 显示这两个 kernel 合起来占了单步延迟的 31%，而它们的 FLOPs 只占全模型的不到 0.5%。原因一眼可见：第一个 GEMM 按 128×128 tile 只能切出 1 个 block，H100 的 132 个 SM 里 131 个在空转，SM Throughput 2%、DRAM Throughput 也只有 19%——两个 Speed of Light 都低，典型的"活没铺开"（这个判据见 DP25 第六节）。处理方式有两条并行：一是对 K=4096 那个 GEMM 启用 split-K 切 32 份，把 block 数提到 32；二是把同一 batch 内多个请求的 LoRA 调用合成一次 grouped GEMM 把 M 撑起来。两项合计后这两个 kernel 的占比从 31% 降到 6%，单步延迟降低约 21%。数字是构造的，但"低秩矩阵在大卡上因为 block 数太少而严重低效"是 LoRA 与 MoE 路由场景里非常真实的问题，split-K 和 grouped GEMM 是标准解法。
流水线优化的三个阶段刚好对应三个问题：双缓冲问"搬的时候能不能同时算"；TMA 问"搬运能不能别占用算的人手"；split-K 问"活是不是根本没铺开"。前两个是让忙的人更高效，第三个是让闲的人有活干——诊断时要先分清是哪一类，否则方向就反了。

六、cuBLAS / CUTLASS / OpenAI Triton 的分工

前五节讲的全部机制，在生产中绝大多数时候你不需要亲手实现——它们已经被封装在三层工具里。这一节讲清每层的边界，以及那个真正值钱的判断：什么时候才轮到自己写 kernel。

先辨析一个高频混淆：两个「Triton」完全无关

形状极端（M=1 的 GEMV、低秩矩阵、MoE 的 grouped GEMM）库的启发式对这些形状选不出好 kernel，见第五节的 split-K 案例Triton 做 grouped GEMM，CUTLASS 做 split-K / Stream-K
新硬件特性刚出、库还没覆盖时间差窗口CUTLASS / CuTe，必要时内联 PTX

反过来，有三类情况不该自己写：形状规整的标准 GEMM（cuBLAS 已经接近峰值，你赢不了）、占端到端时间不到 5% 的算子（优化上限就是 5%）、以及团队没有 Nsight 调优能力时（写得出来但调不动，维护成本会失控）。至于融合本身该怎么设计、哪些算子值得融，见 DP27 · 算子融合与 Kernel 优化实战；如果目标是让编译器自动完成这些，则属于推理编译栈的范畴，见 DP28 · TensorRT 与推理编译栈。

  • 先算这个 GEMM 占端到端多少时间，再决定要不要优化它
  • 模型配置里的 hidden、intermediate、词表一律取 128（至少 64）的倍数
  • 维度不对齐时直接 padding，代价通常在千分之一以下
  • block tile 的选择同时看 shared memory 容量和累加器寄存器数两面墙
  • M、N 小而 K 大时启用 split-K，或把多次调用合成 grouped GEMM
  • 标准 GEMM 直接用 cuBLAS；有融合需求先试 OpenAI Triton
  • 说「Triton」时明确是 OpenAI 的 DSL 还是 NVIDIA 的推理服务器
  • 不要指望分块能救 batch=1 的 decode，它的瓶颈是带宽不是算力
  • 不要为了提 occupancy 而缩小 tile，那会直接降低算术强度
  • 不要把 register tile 开到 16×16，累加器会超过单线程 255 个寄存器上限
  • 不要随手给词表或 hidden 加几个奇数，一次维度失配可能吃掉两成吞吐
  • 不要在没 profile 的情况下手写 GEMM 去和 cuBLAS 比，标准形状上你赢不了
  • 不要为占端到端不到 5% 的算子投入手写 kernel 的工程量
  • 不要把 tile 数刚好卡在 SM 数的非整数倍上，尾波会白扔算力
工具选择的逻辑和分块本身一样是算账：每往下一层，性能上限提高一点，开发与维护成本提高一个量级。所以顺序永远是"先量占比，再选层级"——一个占 3% 时间的 kernel，就算你手写到极致也只能换来 3% 的收益，而代价是一个永久的维护负担。

Q&A

为什么 naive GEMM 的算术强度是 O(1)，一定访存受限？

naive 实现里每个线程负责一个输出元素，沿 K 方向循环：每次迭代读 A 的一个元素和 B 的一个元素（共 2 个元素），做一次乘加（2 FLOPs）。所以算术强度 = 2 FLOPs ÷ (2 × 元素字节数) = 1 / 元素字节数，FP16 是 0.5 FLOP/Byte，FP32 是 0.25。注意这个结果里不含 K——循环再长也不改善，因为每多一次迭代既多两次运算也多两次访存，比值恒定。这就是"O(1)"的含义：它是常数，不随问题规模变好。而 H100 的屋顶线拐点约在 295 FLOP/Byte（推导见 DP19），差约 590 倍，所以任何不做数据复用的 GEMM 实现都必然落在带宽斜坡上。换成总搬运量看更直观：4096³ 的 FP16 GEMM，naive 要从 HBM 搬约 275 GB（A 的每个元素被读 N 次、B 的每个元素被读 M 次），理论下限只要 100 MB，差 2750 倍。以 H100 的 3.35 TB/s 算，搬这 275 GB 要 82 ms，而计算本身在 989 TFLOPS 的 Tensor Core 上只要 0.14 ms。

shared memory tile 和 register tile 分别解决什么问题？

它们治的是存储层次上两段不同的流量，所以必须都做。shared memory tile（block tile）治 HBM 流量：让一个 threadblock 负责 BM×BN 的输出块，把所需输入一次搬进 shared memory 供 block 内所有 warp 共享，HBM 侧算术强度变成 2 ÷ [(1/BM + 1/BN) × 元素字节数]，128×128 的 tile 在 FP16 下是 64 FLOP/Byte，比 naive 的 0.5 提升 128 倍。register tile 治 shared memory 流量：如果一个线程只算一个输出元素，它每步 K 要从 shared memory 读两个元素做一次乘加，smem 侧算术强度又回到 0.5；让每个线程负责 TM×TN 的小块、累加器全放寄存器，每步 K 读 TM+TN 个元素却做 TM×TN 次乘加，算术强度变成 2×TM×TN ÷ [(TM+TN) × 字节数]，8×8 是 4.0，提升 8 倍。两级的上限来自不同的硬墙：block tile 受 shared memory 容量限制（H100 每 SM 228 KB），register tile 受寄存器预算限制（单线程最多 255 个，16×16 的累加器就已超标）。调 tile 尺寸本质上就是在这两面墙之间找平衡点。

128×128 的 tile 算出来算术强度只有 64，低于 H100 的 295 拐点，为什么 cuBLAS 还能跑到接近峰值？

因为那个公式假定了"所有 tile 都必须从 HBM 读"，而现实中 L2 缓存会捕获大量跨 block 的复用。H100 有 50 MB L2，同时在跑的那批 block 如果访问的输入 tile 有重叠，第二个及之后的 block 就能从 L2 命中，不必回 HBM。所以真实的 HBM 流量介于"tile 公式给出的值"和"三个矩阵各读一次的理论下限"之间。这也解释了为什么 threadblock 的排布顺序会影响性能：默认的行主序排布让一波 block 横扫输出矩阵的一整行，它们共享 A 的 tile 但 B 的 tile 全不相同；改成把若干行打包成组再换列（CUTLASS 叫 threadblock rasterization，Triton 叫 grouped ordering），同时在跑的 block 聚成方块，A 和 B 都能复用。Triton 官方矩阵乘教程给的算例是：一个 9×9 块的矩阵乘，行主序算出前 9 个输出块要加载 90 个输入块，分组顺序只需 54 个，降低 40%，代码改动只有几行下标算术。所以"提高算术强度"实际上是三件事叠加：block tile、register tile、以及让 L2 帮上忙的排布顺序。

Tensor Core 的形状约束具体是什么，为什么矩阵维度要对齐？

指令层面：Ampere 起的 mma.sync.aligned.m16n8k16 由一个 warp（32 线程）同步执行，M=16、N=8 固定，K 由数据类型决定（FP16/BF16 为 16，FP8 为 32）；Hopper 的 wgmma.mma_async.m64nNk16 由一个 warpgroup（128 线程）异步执行，M 固定为 64，N 是 8 的倍数且取值 8 到 256，K 固定为 32 字节。维度对齐的要求分三个层次，后果完全不同。第一层是内存对齐：cuBLAS 文档要求矩阵维度与 leading dimension 乘元素字节数后能被 16 整除、指针也 16 字节对齐，FP16 即维度为 8 的倍数；cuBLAS 11.0 之前这是使用 Tensor Core 的硬性前提（不满足有 2~4 倍落差），之后放宽成"不对齐也能用但效率更低"，FP8 仍是硬性要求。第二层是 tile 量化：输出维度要能被 threadblock tile 尺寸整除，官方建议取 64 的倍数、理想 128~256 的倍数，否则边缘那排 tile 做了全量计算却只产出部分有用数据。第三层是 wave 量化：tile 总数最好是 SM 数的整数倍（A100 是 108，H100 SXM5 是 132），否则最后一波只有部分 SM 在干活。padding 的代价通常极小——GPT-2 的词表 50257 是质数，补到 50304（128 × 393）只多算 0.09% 的 FLOPs。

double buffering 为什么对 GEMM 特别重要？

因为 GEMM 恰恰是最没法靠高 occupancy 掩盖延迟的那类 kernel。CUTLASS 文档把因果说得很清楚：分块结构要求每个线程持有大量累加器，累加器通常占掉线程寄存器预算的一半以上，因此 GEMM 能驻留的 warp、block 数相对其他负载明显偏低，GPU"切换到别的 warp"来掩盖访存延迟的能力也就弱——只能靠单个线程内部的软件流水来自救。double buffering 就是这个自救手段：在 shared memory 里开两块 tile 缓冲区，一块正被计算消费、另一块同时在接收下一轮从 HBM 来的数据；在寄存器层面同样开两份 matrix fragment 轮换。这样总时间从"搬运时间加计算时间"变成"两者取最大值"。Ampere 引入 cp.async 后缓冲级数可以提到 3~5 级（CUTLASS 的 Stages 参数），代价是 shared memory 用量按级数线性增长。Hopper 进一步用 TMA 加 warp 专精化把生产者和消费者彻底解耦，搬运不再占用计算 warp 的指令发射带宽。

什么时候需要 split-K？

当 M 和 N 都小、K 却很大的时候。标准分块按输出矩阵切 block，block 总数是 (M/BM) × (N/BN)；M、N 小时这个数可能只有个位数，而 H100 有 132 个 SM，绝大多数在空转——问题不是算力不够，是活没铺开。这种情况的识别特征很明确：Nsight Compute 里 SM Throughput 和 DRAM Throughput 两个都很低。split-K 把归约维度 K 切成若干段，交给不同 block 并行算部分和，最后再归约相加，从而把 block 数提上去。CUTLASS 的实现需要两个 kernel：partitionedK GEMM 把各段部分和写进 workspace，再跑一个 batched reduction 沿 K 求和，所以额外成本是 workspace 显存加一次 kernel 启动。文档给的例子是 m=128、n=128、k=4096 切 20 份，前 19 份各取 k=204、最后一份 k=220。还有个变体 sliced-K 把切分放在 block 内部的 warp 之间，归约更便宜但并行度增益更小。典型触发场景是 LoRA 的低秩矩阵、小 batch decode 的投影层、MoE 路由后的小专家矩阵。另一条并行的解法是把多次小调用合成 grouped GEMM 把 M 撑起来，两者常常一起用。

OpenAI Triton 和 NVIDIA Triton Inference Server 是什么关系？

没有任何关系，只是重名。OpenAI Triton（现为独立开源项目 triton-lang）是一门写 GPU kernel 的 Python 嵌入式 DSL 加配套编译器，抽象层级在 block 级：你写 tile 的逻辑，编译器负责线程映射、访存合并、寄存器分配和软件流水。PyTorch 2.x 的 torch.compile 默认就是用它来生成融合算子的，FlashAttention 也有 Triton 实现版本。NVIDIA Triton Inference Server 是一个模型服务框架，管的是 HTTP/gRPC 接口、请求队列、动态批处理、多模型与多框架后端编排，你和它打交道的方式是起一个容器、配一份 config.pbtxt。一个解决"算子怎么写得快"，一个解决"模型怎么对外提供服务"，处在技术栈完全不同的两层。实际读资料时判断语境很简单：讨论 tile、autotune、@triton.jit、tl.dot 的是 OpenAI Triton；讨论 instance group、dynamic batching、model repository 的是 NVIDIA 的推理服务器。

什么情况下才该自己写 GEMM kernel，而不是用 cuBLAS？

判断标准只有一条：现成库解决不了你的需求，并且这个 kernel 在端到端时间里占比足够大。具体有四类该写的场景。一是需要把 GEMM 和相邻算子融成一个 kernel（比如 GEMM 接 SwiGLU 再接量化），cuBLAS 的 epilogue 能力有限，拆成多个 kernel 会多几轮 HBM 往返，这时先试 OpenAI Triton，不够再用 CUTLASS 的自定义 epilogue。二是非标准量化格式，比如分组量化、W4A16、per-channel scale 与 GEMM 交织，反量化必须写在内循环里，库不支持，CUTLASS 有成熟的混合精度 GEMM 范式可以借。三是形状极端，比如 M=1 的 GEMV、LoRA 的低秩矩阵、MoE 的 grouped GEMM，库的启发式对这些形状选不出好 kernel。四是新硬件特性刚出、库还没覆盖的时间差窗口。反过来有三类不该写：形状规整的标准 GEMM（cuBLAS 已接近峰值，你赢不了）、占端到端时间不到 5% 的算子（优化上限就是 5%）、以及团队没有 Nsight 调优能力时（写得出来但调不动，会变成永久的维护负担）。

这张卡和 T20 讲的 FlashAttention 分块是什么关系？

本卡讲的是通用矩阵乘的分块机制，它是 FlashAttention 得以成立的前置知识，而不是它的重复。两者共享同一个核心思想——把工作集搬进 shared memory（SRAM）复用、减少 HBM 往返——但处理的问题不同。通用 GEMM 的分块要解决的是 C = AB 这个纯粹的三重循环怎么映射到 threadblock / warp / instruction 三级硬件并发，难点在算术强度的定量推导、Tensor Core 的形状约束、以及流水线与 split-K 这些调度问题。FlashAttention 面对的是一个额外的困难：softmax 需要整行的最大值和求和，天然不可分块，所以它必须引入 online softmax（维护 running max 和 running sum，每处理一个新 tile 就用修正因子回溯修正之前的部分结果）才能在分块的前提下拿到和标准注意力逐位一致的结果。那套推导以及 FlashAttention-2/3 的改进在 T20 · 高效注意力 里已有完整展开，本卡不重复。阅读顺序上，先看本卡理解"分块为什么必须做、怎么算收益"，再看 T20 理解"注意力这个特殊算子怎么克服 softmax 的不可分块性"。
