DP15 · 国产芯片推理部署

国产化动因 / 昇腾 CANN 与 MindIE / vLLM 硬件插件生态 / 寒武纪与海光与摩尔线程 / 迁移四类障碍 / 公平对标方法 / 混合集群分流

国产芯片推理部署的难点从来不在芯片，而在软件栈：算力可以买，算子库、融合策略、通信库和调试工具链的成熟度买不来。所以这件事的正确打开方式不是"国产卡能不能跑大模型"，而是"我的这个模型、这个上下文、这个并发，在现有软件栈的支持清单里排第几位"。

一、为什么要做推理国产化

先把动机说清楚，因为动机直接决定了后面所有技术选择的容错空间。绝大多数团队启动国产芯片推理迁移，不是因为国产卡在某个基准上更快——客观地说，2026 年的公开与内部实测数据都不支持这个结论——而是因为三类外部约束把"用什么卡"从一个性能问题变成了一个可得性与合规问题。

驱动力具体表现对推理部署的直接影响
供应链可得性高端加速卡出口管制、交货周期不确定、现货溢价与配额分配扩容节奏不由自己决定；被迫在"能买到的卡"上做容量规划
合规与信创要求政务、金融、能源、军工与央国企的自主可控目录、等级保护与数据不出境要求采购清单先于技术选型；某些项目里非国产方案直接不进入评标
成本与议价整机方案报价、本地化服务响应、多供应商制衡把国产卡纳入池子本身就能改善议价，但要算上迁移人力成本
业务连续性单一供应商依赖带来的断供风险需要保留一条"能跑起来"的备用链路，即使性能打折

这里的关键词是 信创——即信息技术应用创新，指在关键行业逐步替换为自主可控的软硬件体系，实践中体现为一份从芯片、操作系统、数据库到中间件的入围目录。当项目落在信创范围内，芯片选择被前置为一条硬约束，工程团队要做的不是选型而是适配。理解这一点很重要：如果把国产化当成性能优化项目，几乎一定会失望；把它当成"在受限软件栈上重建一条达标服务链路"的工程项目，预期就正常了。

推理软件栈分层对照（同一模型，两条链路） NVIDIA 链路 国产链路（以昇腾为例） ┌──────────────────────┐ ┌──────────────────────────────┐ │ 应用 / RAG / Agent │ 接口不变 │ 应用 / RAG / Agent │ ├──────────────────────┤ ←── 兼容层 ──→ ├──────────────────────────────┤ │ vLLM / SGLang / TGI │ │ MindIE Service │ vllm-ascend │ ├──────────────────────┤ ├────────────────┴─────────────┤ │ PyTorch (CUDA) │ │ PyTorch + torch_npu │ ├──────────────────────┤ ├──────────────────────────────┤ │ cuBLAS/cuDNN/Flash │ ←── 断裂带 ──→ │ CANN aclnn 算子库 / ATB │ ├──────────────────────┤ ├──────────────────────────────┤ │ CUDA Runtime + NCCL │ │ CANN Runtime + HCCL │ ├──────────────────────┤ ├──────────────────────────────┤ │ 驱动 / GPU │ │ 驱动固件 / NPU │ └──────────────────────┘ └──────────────────────────────┘ 上两层几乎无痛：OpenAI 兼容 API、PyTorch 模型代码基本不用改 中间两层是全部工作量所在：算子覆盖、融合策略、通信库语义 下两层是黑盒：版本配套表说什么就是什么，没有第二条路

这张分层图解释了为什么"迁移体感"两极分化。上层接口高度一致——国产推理引擎普遍提供 OpenAI 兼容接口，模型仍然是 PyTorch 代码，甚至部分设备操作还沿用 torch.cuda 命名空间——所以第一天往往能很快看到模型返回第一个 token，团队信心大增。但返回第一个 token 只证明基本执行链接通了，不证明算子覆盖完整、不证明融合路径存在、更不证明在真实并发下延迟达标。真正的工作量集中在中间两层，而这两层的进展只能靠一个个模型、一个个算子推进。

把国产化迁移想成给一辆车换发动机舱：方向盘（API）和座椅（应用代码）都还在原位，看着像没变；但油路、点火时序、传动比全部要重新标定。第一次点火成功很容易，标定到能上高速跑长途才是真正的工程量。

二、主流路线全景与生态成熟度

2026 年国产推理芯片可用于大模型部署的路线，大体收敛为四家：华为昇腾、寒武纪、海光、摩尔线程。它们的差异不只在硬件，更在"用什么编程模型接住 PyTorch 生态"这个根本选择上，而这个选择决定了迁移难度、性能天花板和排障方式。

厂商代表推理硬件编程模型 / 底座主推推理路径生态获取方式
华为昇腾Atlas 800I A2 / A3、Atlas 300I DuoCANN（异构计算架构）+ torch_npuMindIE 原生引擎；vllm-ascend 社区插件昇腾社区公开文档 + AscendHub 镜像，MindIE 已于 2025 年 12 月开源
寒武纪MLU370 及以上Cambricon NeuWare SDKvllm-mlu（基于 vLLM 插件系统）仓库公开，但 SDK 与镜像需通过官方商务渠道申请
海光DCU K100 系列（如 gfx936）DTK + ROCm/HIP 兼容接口定制镜像内的 vLLM（HIP 后端）光源开发者社区定制镜像（image.sourcefind.cn），按驱动版本对应
摩尔线程MUSA 架构 GPU（如 M1000 整机）MUSA + torch_musa + torchada 兼容层vllm-musa 硬件插件（仅 V1 引擎）GitHub 公开仓库 + 官方文档站 + AIOS 整机镜像

三种接生态的姿势，决定了三种迁移体验

把上表抽象一层，四家其实只用了三种策略，理解这三种策略比记住产品名更有用。

策略代表工作原理优点代价
自建原生引擎昇腾 MindIE厂商自己写一套推理服务与模型库，深度贴合自家算子与调度性能上限最高，特性由厂商保证，官方支持路径清晰与开源社区异步演进；模型支持范围受官方清单限制
vLLM 硬件插件vllm-ascend、vllm-mlu、vllm-musa按 vLLM 的 Hardware pluggable 机制注册后端平台，复用调度器与模型代码沿用社区模型实现与参数习惯，升级跟随上游上游节奏快，插件常滞后；特性支持是"逐个打勾"而非全有
CUDA 生态兼容层海光 HIP、摩尔线程 torchada在源码或运行时层面把 CUDA 接口翻译到自家运行时大量既有代码零改动跑起来，起点极高接口相同不等于实现等价，未针对本架构优化的内核容易慢或不可用

第三种策略最容易被误读。海光 DCU 能承接 vLLM，不是因为它"模拟成了另一种 GPU"，而是它在通用 GPGPU 硬件之上提供了与 ROCm/HIP 兼容的编程接口，因此上层 Python、PyTorch、Triton 代码能被承接；但一条来自既有 ROCm 路径的原生内核能否为当前芯片架构成功构建、能否处理模型真实传入的张量形状、又能否被推理框架正确追踪或回退，是三个彼此独立的问题。实践中就体现为部署时要显式设置 HSA_OVERRIDE_GFX_VERSION 去匹配目标架构，以及必须使用厂商定制镜像——因为公开镜像缺少针对该芯片优化的内核。

兼容层给你的是"起点"，不是"终点"。它把迁移的第一步从三个月压缩到三天，但从"能跑"到"达标"的那段路，兼容层帮不上忙，只能靠一条条算子的能力分派：精确选择走哪条实现、验证数值与性能、不合格就关闭并回退。

成熟度要看三个可验证的指标，不看宣传

评估一个国产栈是否可用于自己的场景，最有效的做法是查三份材料，它们都是公开或可索取的硬事实，比任何评测稿都可靠。

要查的材料回答什么问题常见的坏消息
模型支持清单我的模型在不在清单里、支持到什么程度（全量支持 / 仅功能支持 / 实验性）清单里只有主流开源模型；自研或魔改结构基本不在
版本配套表引擎、驱动固件、加速库、PyTorch 插件的版本必须如何对齐强绑定关系，装错版本直接起不来，且升级要整栈联动
特性支持矩阵前缀缓存、图模式、投机解码、量化格式、PD 分离是否可用"支持"常带脚注：某些硬件型号、某些模型、某些并发下才成立

一个能说明问题的细节：寒武纪 vllm-mlu 官方给出的示例启动命令里同时出现了 --block-size 1、--no-enable-prefix-caching 和 --enforce-eager。这三个参数在 NVIDIA 上的含义分别是把分页粒度降到最小、关掉前缀缓存、关掉图模式——每一个都会牺牲性能。它们出现在示例里，说明这条路径优先保证"跑通与稳定"，把性能特性留给逐步开启。这不是贬义，恰恰是成熟工程的做法，但看不懂这个信号的团队会把示例配置直接搬到生产，然后困惑于吞吐为什么这么低。

读国产栈文档要有"看脚注"的习惯：示例命令里关掉了什么，往往比开启了什么信息量更大。所有 --enforce-eager、--no-enable-* 都是一句话——这条路还没铺完，先绕行。

三、昇腾栈剖析与迁移工作量

昇腾是当前生态最完整、公开资料最多的国产推理路线，值得单独剖开看。它的软件栈自下而上分成四层，每层有独立的名字和职责，把名字对上号，排障时才知道该去哪一层看日志。

昇腾推理软件栈分层（两条并行路径） ┌───────────────────────────────────────────────────────────────────────┐ │ 业务层：HTTP / gRPC 请求，OpenAI / TGI / vLLM 兼容格式 │ └────────────────────────────┬──────────────────────────────────────────┘ │ ┌───────────────────┴────────────────────┐ │ │ ┌────────▼──────────────┐ ┌──────────▼──────────────────┐ │ MindIE Service │ │ vllm-ascend（社区插件） │ │ · 服务化 / 调度 │ │ · 复用 vLLM V1 调度器 │ │ · conf/config.json │ │ · 按硬件可插拔 RFC 注册 │ ├───────────────────────┤ ├─────────────────────────────┤ │ MindIE-LLM / ATB-Models│ │ vLLM 模型实现 + torch_npu │ │ · PagedAttention │ │ · Chunked Prefill / 前缀缓存│ │ · Continuous Batching │ │ · W8A8 / W4A8 量化 │ │ · FlashDecoding │ │ · Mooncake PD 分离 │ └───────────┬───────────┘ └──────────┬──────────────────┘ │ │ ┌───────────▼─────────────────────────────────────▼──────────────────┐ │ ATB（Ascend Transformer Boost，libatb.so 由 NNAL 提供） │ │ CANN：aclnn 算子库 / 图编译 / 内存与流管理 / HCCL 集合通信 │ └───────────────────────────────┬────────────────────────────────────┘ │ ┌───────────────────────────────▼────────────────────────────────────┐ │ NPU 驱动与固件 → Atlas 800I A2 / A3 / Atlas 300I Duo │ └────────────────────────────────────────────────────────────────────┘

其中 MindIE 是昇腾原生的大模型推理引擎，它不是 vllm-ascend 的备选，而是昇腾推理栈的默认选项：MindIE-LLM 提供深度优化的模型库与推理优化器，内置 Continuous Batching、PagedAttention、FlashDecoding 等加速特性；MindIE Service 则是面向服务化的那一层，负责 HTTP/gRPC 接口、并发调度与配置管理，启动后兼容 OpenAI、TGI、vLLM 等多种接口格式，这也是应用层几乎无需改造的原因。往下 ATB（Ascend Transformer Boost）提供 Transformer 结构的高性能加速原语，其动态库由 NNAL 加速库包提供；最底层的 CANN 则相当于 CUDA 的位置，包含算子库、图编译、运行时以及对标 NCCL 的集合通信库 HCCL。

版本强绑定：这是昇腾迁移的第一课

昇腾栈的版本关系是 1:1 强绑定，不是"建议搭配"。装错版本的表现不是性能差，而是直接起不来，且报错信息经常指不到根因。下表是 2026 年两条路径各自的配套要求，注意两条路径要求的 CANN 版本并不相同——这意味着同一台机器上同时跑两条路径需要谨慎的环境隔离。

路径引擎版本CANNPyTorch / 插件其他约束
MindIE 原生MindIE 2.3.0（2025/12 开源）8.5.0（唯一支持）torch_npu 2.7.1+Python 3.10.x 推荐
vllm-ascend 稳定版v0.18.0（2026/05 发布）9.0.0torch 2.10.0 / torch-npu 2.10.0.post2NNAL 9.0.0 提供 libatb.so；Python ≥3.10 且 <3.13
vllm-ascend RC 通道v0.21.0rc1 / v0.22.1rc1随文档更新随上游 vLLM 演进提供 A2 / A3 / 310P 的 Ubuntu 与 openEuler 双镜像

硬件支持也有明确边界，必须提前核对而不能想当然。vllm-ascend 目前覆盖 Atlas A2 系列（对应 Ascend-cann-kernels-910b）、Atlas A3 系列以及 Atlas 300I 系列（310p 内核包），而较早的 Ascend 910、Ascend 910 Pro B 等型号并不在支持范围内。这类"手里有卡但栈不支持"的情况在盘点存量硬件时相当常见，也是国产化项目最容易踩的第一个坑。

MindIE 还是 vllm-ascend？

对比维度MindIE 原生vllm-ascend 插件

实践中的常见组合是"双栈并行"：用 vllm-ascend 快速验证业务能不能跑通、把应用层和压测脚本先跑顺，同时用 MindIE 做性能攻坚与正式上线。这样做的隐含成本是要维护两套环境与两套版本配套，团队小的话不建议。若已经确定长期使用昇腾且对性能敏感，直接从 MindIE 起步更划算；若国产化只是多供应商策略中的一条腿，vllm-ascend 的一致性收益更大。参考同目录《DP05 · 大模型推理框架选型》里对 vLLM 架构的拆解，插件路径继承的正是那套调度与显存管理逻辑。

场景典型工作量主要动作风险点

生产案例：某省级政务问答系统从 8×A800 迁到 2 台 Atlas 800I A2。背景是项目验收要求核心推理链路进入信创目录，原系统在 8 卡 A800 上用 vLLM 跑 32B 量级中文模型，日请求约 42 万次，P95 端到端 1.9 秒。迁移分四个阶段：第一周走 AscendHub 镜像用 vllm-ascend 跑通，首次请求成功当天完成，但只能开 --enforce-eager，吞吐仅为原系统的 34%，P95 冲到 5.2 秒；第二到三周切 MindIE 原生引擎并严格对齐 CANN 版本，开启 Continuous Batching 与 PagedAttention 后吞吐回到 61%；第四到六周做两件事——把权重从 AWQ 4-bit 重做为该栈支持的 W8A8 量化，并针对约 1100 token 的固定 System Prompt 打开前缀缓存（命中率实测 68%），吞吐达到原系统的 83%，P95 降到 2.4 秒；最后两周做精度回归，中文问答人工评测通过率从迁移中期的 91.2% 修回 97.6%（原系统 98.1%）。结论是：达标可行，但性能仍有约 17% 的差距需要靠多买一台机器补齐，全过程投入 2 名工程师约 8 周。
昇腾迁移的时间分布很反直觉：跑通只占 5% 的工期，剩下 95% 花在"把关掉的开关一个个打开、每打开一个就回归一次精度"。所以排期时不要按"多久能跑通"报，要按"多久能把加速特性全开且精度不掉"报。

四、迁移的四类典型障碍

跨硬件迁移的问题看起来千奇百怪，但归类之后就是四类，且四类的排查顺序有讲究——从下往上排，因为下层问题会伪装成上层现象。

障碍一：算子缺失与精度对齐

这是最根本的一类。国产算子库覆盖的是"主流模型用到的主流算子"，一旦模型里出现自定义注意力变体、非常规激活函数或特殊归一化，就可能落到没有实现的路径上。表现分两种：报错说算子不支持（这算好消息，问题明确），或者悄悄走了某个数值行为不完全一致的替代实现（这才是噩梦，服务正常返回但答案质量下滑）。

精度对齐必须靠工具，不能靠肉眼看输出。昇腾侧的做法是用 msprobe（MindStudio Probe 精度调试工具）在"问题侧"和"标杆侧"分别 dump 数据再比对：L0 级别按模块 dump 并生成结构信息供可视化重建网络，L1 级别只采集算子级统计量适合轻量排查，mix 级别同时拿到结构与数值。两份 dump 不需要完全同源——可以来自不同分支、不同框架版本甚至不同算子实现，只要输入、拓扑与采样点相近就能比对出首个发散节点。几个实操要点：怀疑异步执行掩盖了问题时设 ASCEND_LAUNCH_BLOCKING=1 让算子同步执行；fp16 数据在 CPU 侧会被提升到 fp32 计算，所以 CPU 标杆更接近真值；Dropout 这类带随机性的算子不能按逐元素相等来判定，工具会按零元素比例是否接近设定的 p 值来判断。

精度问题的定位原则是"找第一个偏差算子"，不是"看最后输出差多少"。误差会沿着网络逐层放大，等到 logits 层再看，所有算子看起来都不对；从头逐层比对，往往只有一个算子是真凶。

障碍二：算子融合缺失与性能回退

算子存在不等于快。NVIDIA 侧的性能很大程度来自融合内核——把归一化、投影、注意力、激活等一串操作合成一个内核，省掉中间结果反复读写显存的开销。国产栈的融合覆盖率是逐个模型、逐个结构补上来的，缺一个融合算子往往就是几十个百分点的吞吐差距。

与之绑定的是图模式：把计算图整体编译下发，减少 host 侧调度开销。图模式是性能的主要来源，但对形状变化与算子支持更敏感，出问题时的逃生门是 --enforce-eager 退回逐算子执行。这个开关很容易变成一个陷阱——它让服务立刻能跑，团队于是就把它留在生产配置里，然后带着一个性能腰斩的系统去做对标，得出"国产卡不行"的结论。另一个易错点是加速特性的生效阈值：昇腾侧的 FlashDecoding 默认要序列长度达到 4K 以上才启用，用 512 token 的短请求压测根本测不出它的价值；前缀缓存也一样，请求前缀不固定时命中率就是 0%，只有 RAG 这类 System Prompt 固定的场景才有意义。

--enforce-eager 是止血带，不是治疗方案。它出现在生产配置里超过两周，就该被当成一个待还的技术债记进看板，而不是被当成"我们的标准配置"。

障碍三：显存管理与分布式通信差异

显存侧的差异体现在分页粒度与内存池行为上。KV Cache 的 block-size 在不同后端的最优值差别很大，前面提到寒武纪示例用 --block-size 1 就是一个信号；显存利用率上限参数（如 --gpu-memory-utilization）在国产栈上留的安全余量也常常需要更保守，因为内存池的碎片行为与 CUDA 不同，压到 0.95 以上更容易触发运行时分配失败。关于 KV Cache 的原理与调参逻辑，可对照《DP08 · KV Cache 与推理优化》理解差异来源。

通信侧的差异更隐蔽。昇腾用 HCCL 承担 NCCL 的角色，接口语义相近但错误码体系、超时行为与初始化时序完全不同：多卡启动阶段常见的现象是通信域建立超时，处理方式是显式放宽 HCCL_CONNECT_TIMEOUT；报错码如 EI0006 在很多场景下的真实根因只是 CANN 版本过低导致不兼容，升级即可，但从报错文本完全看不出来。若要用 PD 分离（Prefill 与 Decode 拆到不同实例），vllm-ascend 支持基于 Mooncake 后端的实现，部署时要注意端口冲突——建议把 kv_port 设在 20000 以上以避开传输组件的默认端口范围。

通信类故障有个可靠特征：单卡永远复现不出来。所以排障时先确认"单卡 eager 能不能跑对"，能跑对就说明算子与数值没问题，把注意力全部转到通信与并行配置上，能省掉大量无效尝试。

障碍四：生态与调试工具链薄弱

这一类没有技术含量但最消耗士气。同一个报错在 NVIDIA 生态里搜索能命中十几条 issue 和博客，在国产栈里可能只有一条厂商文档的 FAQ，甚至什么都没有。周边组件也需要手工适配——例如在寒武纪上用 Ray 做分布式，需要把插件仓库里准备好的加速器识别、设备管理等文件手动覆盖到 Ray 安装目录下，这类操作既不优雅也难以纳入 CI。profiling 工具虽然有（昇腾侧的 msprof 与 MindStudio Insight 系列），但生态积累与使用习惯远不如成熟平台，团队要额外花时间学。

生产案例：一次"服务正常但答案变差"的精度对齐排查。某金融客服知识助手迁到国产卡后，服务、延迟、吞吐三项指标全部达标，上线灰度 5% 流量两天后才被业务发现问题：涉及金额与日期比较的问题答错率明显上升，人工抽检 300 条，正确率从 96.3% 掉到 88.7%，而通用寒暄类问题毫无异常。团队最初怀疑是检索召回退化，排查两天无果；随后改用精度比对思路，在同一批 20 条固定输入上分别在原 GPU 环境与国产环境做逐层 dump，比对发现问题出在归一化算子的一个数值实现上——该实现为提速在低精度下做了累加，长上下文时误差累积到影响注意力分布，越往后的 token 偏差越大。修复方案是把该算子的累加改回高精度路径，代价是单卡吞吐下降约 6%。修复后抽检正确率回到 95.8%。这个案例的价值在于：吞吐和延迟指标全绿，不代表迁移完成；没有精度回归门禁的迁移项目，等于把质量问题推给了线上用户。

五、性能对标怎么做才算公平

国产卡对标最常见的错误是拿纸面算力说话。芯片规格表上的 TFLOPS 或 TOPS 是理论峰值，它假定算子完美打满计算单元、数据完美驻留在片上、没有任何调度与通信开销——现实中的大模型推理，Decode 阶段是显存带宽密集而非算力密集，能不能把峰值算力用出来，取决于算子实现与融合水平，而这恰恰是国产栈当前的短板。所以纸面算力持平的两张卡，实测有效吞吐差两三倍完全正常，反过来也说明"算力追平"不等于"可用性追平"。

调度策略也要纳入对标设计，因为它在国产栈上未必单调更优。昇腾侧提供多种调度器可选，实践反馈是：单卡场景用先来先服务更稳，高并发下某些调度策略反而会让延迟升高，八卡以上才值得尝试更复杂的调度。这类"参数在小规模上是负优化"的现象在新栈里很常见，所以对标要按规模分档，不能用一档配置的结论覆盖所有规模。关于集群与硬件层面的成本核算方法，可参考《DP14 · GPU 基础设施》；量化格式的选择与精度影响见《DP13 · 量化部署指南》。

生产案例：一次自我推翻的对标。某互联网公司算力团队第一轮对标结论是"国产卡吞吐只有 H 卡的 21%，不具备生产可用性"，报告差点定案。复盘时发现三处口径问题：国产侧仍带着 --enforce-eager（图模式未开）、压测用 512 token 短请求（长序列优化特性未触发生效阈值）、且两侧量化格式不同（一侧 BF16、一侧 W8A8）。重做对标：统一为 W8A8、输入输出按线上真实分布（均值约 3200 token 输入 / 480 token 输出）、并发分 8/32/64 三档、国产侧开启图模式与前缀缓存。第二轮结果是每卡有效吞吐达到对照组的 58%，并发 32 档位 TTFT P95 为对照组的 1.7 倍，折算单位成本后国产方案高出约 22%——不算便宜，但在合规必须满足的场景里完全可接受。团队最终的结论从"不可用"改为"核心链路保留 H 卡、内部与离线链路迁国产"。第一轮那个 21% 的数字并非造假，只是测了一个不该测的配置。
对标报告的可信度，几乎完全取决于"变量冻结清单"写得多细。看到任何国产卡与 N 卡的对比数字，先问三句：什么量化格式、什么上下文长度、图模式开没开。这三个问题里只要有一个答不上来，这个数字就只能当传闻。

六、混合集群调度与落地节奏

现实中极少有团队一夜之间全量切换，绝大多数处在"国产卡与 NVIDIA 卡共存"的中间态。混合集群的第一原则是：异构算力不能混在同一个并行组里。张量并行要求组内设备算力与通信带宽同质，把不同厂商的卡放进同一个 TP 组，最好的情况是起不来，最坏的情况是被最慢的卡拖成木桶效应。所以实践中的最小调度单位是"同型号整节点"，混合发生在节点之上的调度层，而不是节点之内。

在 Kubernetes 上，各厂商都提供自家的设备插件把加速卡作为可调度资源上报，节点需要按厂商、型号、驱动版本打标签，再用亲和性规则把工作负载钉到匹配的节点组。容器侧还有个容易漏的细节：不同厂商的设备挂载参数完全不同——昇腾需要挂 /dev/davinci_manager、/dev/hisi_hdc、/dev/devmm_svm 并只读挂载驱动目录，海光则需要 /dev/kfd、/dev/dri 以及 /opt/hyhal，还要加上相应的用户组与安全选项。把这些差异沉淀成各池独立的 Pod 模板，比试图写一份通用模板要现实得多。

分流策略怎么做适用条件风险
按业务分流核心对外业务留 NVIDIA 池，内部工具、批处理、长尾业务走国产池业务 SLA 分层清晰，国产池性能足够覆盖次要场景业务边界模糊时容易互相甩锅；两池质量口径需一致
按模型分流大模型主链路留 NVIDIA，Embedding、Rerank、小模型分类器放国产池小模型对算子的依赖简单，适配成功率高需要额外的服务发现与容量规划
按阶段分流离线灌库、批量生成、数据清洗等吞吐型任务放国产池任务可容忍更长时延，只关心单位成本吞吐型任务对长稳要求高，需先跑通 24 小时压测
按流量比例灰度同一业务按百分比切流到国产池，逐步放大两池输出质量已验证一致必须有跨池熔断与自动回切，否则故障面翻倍
纯冗余备份国产池平时低流量待机，作为断供或故障时的接管能力合规要求"具备自主可控能力"而非全量替换长期空转成本；不跑真实流量的备份往往接管失败

把 Embedding 与 Rerank 这类小模型优先放到国产池，是被验证过的性价比最高的切入点：模型小、算子简单、结构主流，适配成功率显著高于大模型；同时它们通常是纯吞吐型或短延迟型负载，对图模式与长序列融合的依赖也低。这条路径的部署细节可参考《DP17 · Embedding 与 Rerank 模型部署》。

  • 不要向业务方承诺"迁移后性能与体验完全不变"
  • 不要让国产池只做零流量待机备份，不跑真实流量的备份会在接管时失败
混合集群的真正价值不是"两种卡一起用"，而是"把不同 SLA 的业务放到匹配的算力上"。当你能清楚说出哪些业务放国产池、为什么放、性能差多少、出问题怎么回切时，国产化才算真正落地；说不出来的时候，混合集群只是两套故障面的叠加。

Q&A

国产卡推理部署最大的难点到底是硬件性能还是软件栈？

是软件栈，而且差距主要在中间两层。上层的服务接口与模型代码高度兼容——国产引擎普遍提供 OpenAI 兼容接口，模型仍是 PyTorch 代码，所以第一天就能看到模型返回 token；底层的驱动与芯片是黑盒，按版本配套表配置即可。真正的工作量在算子库覆盖度、融合内核完整性、图编译成熟度和集合通信库语义这几层。这也解释了为什么迁移体感两极分化：跑通很快，但把加速特性一个个打开并保证精度不掉，往往要花几周到几个月。硬件峰值算力当然也有差距，但它不是当前的主要瓶颈，因为纸面算力在算子实现不到位时根本用不出来。

昇腾上应该用 MindIE 还是 vllm-ascend？

看团队的技术栈惯性和对性能的要求。MindIE 是昇腾原生引擎，包含 MindIE-LLM 模型库与 MindIE Service 服务层，内置 PagedAttention、Continuous Batching、FlashDecoding 等特性，是厂商深度调优的默认选项，官方性能基准也以它为准，代价是配置方式与 CUDA 侧经验不通用、版本与 CANN 严格 1:1 绑定。vllm-ascend 是社区维护的 vLLM 硬件插件，按 vLLM 的硬件可插拔机制注册昇腾后端，参数与上游完全一致，既有 vLLM 技术栈的团队几乎不用改运维脚本，但特性支持是逐项对齐的，某些能力会滞后于上游。常见做法是用 vllm-ascend 快速跑通验证、用 MindIE 做性能攻坚上线；若长期押注昇腾且对性能敏感，直接从 MindIE 起步更省事。

海光 DCU 能直接跑现成的 vLLM 吗，为什么还要用定制镜像？

能跑起来，但不能用公开镜像。海光 DCU 在通用 GPGPU 硬件之上提供了 DTK 以及与 ROCm/HIP 兼容的编程接口，所以由 Python、PyTorch、Triton 和 C 扩展组成的推理框架能被承接，模型结构不用改，服务仍然暴露 OpenAI 兼容接口，部分设备操作甚至沿用 torch.cuda 命名空间。但公开镜像缺少针对该芯片架构优化的计算内核，所以要用厂商定制镜像并按驱动版本严格对应，同时通过 HSA_OVERRIDE_GFX_VERSION 声明目标架构、挂载 /dev/kfd 与 /dev/dri 等设备。更重要的是理解"接口相同不等于实现等价"：一条既有内核能否为当前架构构建、能否处理真实张量形状、能否被框架正确追踪或回退，是三个独立问题，适配就发生在这些边界上。

迁移后服务正常、延迟达标，怎么判断精度有没有掉？

必须做逐层数值比对，不能靠抽看几条输出。标准做法是在原环境（GPU 或 CPU 作为标杆侧）和国产环境（问题侧）用同一批固定输入分别 dump 中间数据，然后比对找出第一个出现明显偏差的算子或模块。昇腾侧有对应的精度调试工具，支持模块级（含结构信息，可视化重建网络）、算子级统计量（轻量排查）以及两者混合的采集级别，两份 dump 不要求完全同源，只要输入与采样点相近即可比对。实操上有几个注意点：怀疑异步执行掩盖问题时把算子改为同步执行；fp16 数据在 CPU 侧会提升到 fp32 计算，所以 CPU 标杆更接近真值；带随机性的算子不能按逐元素相等判定。工程上更关键的是把精度回归做成上线门禁，与吞吐指标同等权重，否则质量问题只能靠线上用户帮你发现。

为什么不能拿芯片规格表上的算力数字做对标？

因为规格表上的 TFLOPS/TOPS 是理论峰值，它假定算子完美打满计算单元、数据完美驻留片上、没有调度与通信开销。真实的大模型推理里，Decode 阶段是显存带宽密集而非算力密集，而能否把峰值算力兑现出来完全取决于算子实现与融合水平——这正是国产栈当前的短板。所以纸面算力接近的两张卡，实测每卡有效吞吐差两三倍是常态。正确的对标要先冻结六个变量（模型与权重、量化格式、上下文长度分布、并发档位、前缀重复率、加速开关状态），再分并发档位测 TTFT、TPOT 和每卡有效吞吐，最后归一化到每百万 token 成本，并补一轮 24 小时长稳测试。任何缺少这些前置条件的对比数字，只能当传闻看。

国产卡和 NVIDIA 卡能放在同一个推理集群里混用吗？

可以共存，但混合必须发生在调度层而不是并行组内。张量并行要求组内设备算力与通信带宽同质，把不同厂商的卡编进同一个 TP 组，好一点是起不来，差一点是被最慢的卡拖成木桶效应。可行的做法是以"同型号整节点"为最小调度单位，各厂商设备插件把加速卡上报为可调度资源，节点按厂商、型号、驱动版本打标签，再用亲和性规则把负载钉到匹配节点组，前面用统一网关按业务标签与 SLA 分流。容器模板要按池分开写，因为设备挂载参数各厂商完全不同。监控也要按池分开看，混在一张 P95 曲线里的数据没有诊断价值。

国产化迁移应该从哪个模型开始？

从小模型开始，尤其是 Embedding、Rerank 和分类器这类 Encoder 结构的模型。原因有三：结构主流、用到的算子简单，落在支持清单内的概率高；没有自回归解码，不依赖图模式与长序列融合这些成熟度最低的能力；本身是吞吐型或短延迟型负载，对尾延迟的要求比对话式主链路宽松。用它们打通镜像、驱动、设备挂载、监控、压测和精度回归这一整套流程，团队会在几周内积累到真正需要的工具链经验，之后再迁大模型时踩的坑会少一大半。反过来，把自研或魔改结构的大模型作为第一个迁移目标是最容易失败的选择——它同时暴露算子缺失、融合缺失和精度对齐三类难题，而团队此时还没有任何排障经验。

版本配套表为什么被反复强调，不能只升一个组件吗？

不能，国产栈的版本关系是强绑定而非建议搭配。以昇腾为例，MindIE 2.3.0 只支持 CANN 8.5.0；vllm-ascend 稳定版则要求 CANN 9.0.0、torch 2.10.0 与配套的 torch-npu，以及提供加速库动态库的 NNAL 同版本。装错的表现通常不是性能下降，而是服务直接起不来，且报错信息经常指不到根因——一个典型例子是某些通信库报错码的真实原因只是加速库版本过低导致不兼容，从报错文本完全看不出来。工程上的两条纪律是：基线环境一律用厂商官方镜像（它把整套配套关系固化好了），以及绝不在一次变更里同时动引擎、加速库和驱动固件的版本，否则出问题时无法二分定位。

国产化项目应该向业务方承诺什么？

承诺合规达标与服务可用，不要承诺性能与体验完全不变。客观地说，2026 年在同精度、同上下文分布、同并发档位、加速特性全开的条件下，主流国产栈的每卡有效吞吐通常仍落后于同代高端 NVIDIA 方案，TTFT 尾延迟也更高，折算单位成本后不一定更便宜。正确的沟通方式是把三件事讲清楚：一是性能差距的量级以及准备用多少额外机器来补齐容量；二是精度回归的验收口径和门禁标准；三是出现故障时的回切方案与恢复时间。同时把排期按"加速特性全开且精度不掉"来报，而不是按"多久能跑通"来报——跑通往往只占整个工期的很小一部分，按跑通排期几乎必然延期。
