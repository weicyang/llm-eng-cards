Edge AI Deployment — 让大模型跑在终端设备上

一、端侧 AI 的意义

端侧推理换的不是算力，是"数据不出设备"和"没网也能用"——为此愿意接受一个能力更弱的模型。

将 AI 模型部署到手机、PC、IoT 等终端设备（Edge），而非完全依赖云端推理，正在成为大模型落地的关键方向。

核心优势

维度云端推理端侧推理
隐私保护数据需上传至服务器数据本地处理，不出设备
延迟受网络延迟影响（50–500ms）本地推理，延迟可 <10ms
离线可用必须联网无网络环境也可使用
成本GPU 算力费用高利用终端算力，边际成本低
带宽大量数据传输仅传输必要结果
同一句话，走云端和走端侧的两条路径 ┌── 云端推理 ─────────────────────────────────────────────────┐ │ 用户输入 → 网络上行 → 网关鉴权 → 排队 → GPU 推理 → 网络下行 │ │ ▲ ▲ │ │ │ │ │ │ 数据离开设备 算力费用按 Token 计 │ │ 隐私边界在这里破掉 延迟受网络波动支配 │ └─────────────────────────────────────────────────────────────┘ ┌── 端侧推理 ─────────────────────────────────────────────────┐ │ 用户输入 → 本地内存 → NPU / GPU / CPU 推理 → 直接返回 │ │ ▲ │ │ │ │ │ 受限于：内存上限、算力上限、功耗与发热 │ │ 换来的：数据不出设备、无网可用、边际成本近零 │ └─────────────────────────────────────────────────────────────┘ ★ 所以端侧不是"云端的廉价版"，而是约束条件完全不同的另一套工程

典型场景

  • 智能助手 — Siri、小爱同学等设备端语音/文字助手
  • 实时翻译 — 离线翻译 App、会议同传
  • 隐私敏感 — 医疗影像分析、金融数据处理
  • 工业 IoT — 工厂质检、边缘网关异常检测
  • 车载 AI — 自动驾驶感知、车内语音交互
  • 端侧部署的四大优势：隐私、低延迟、离线、低成本
  • 端侧 ≠ 完全替代云端，更多是"端云协同"架构
  • 端侧模型的核心挑战：内存限制、算力有限、功耗约束

二、llama.cpp

llama.cpp 把"跑大模型"从"要有显卡"变成了"有台电脑就行"——代价是精度，靠量化级别自己权衡。

llama.cpp 是纯 C/C++ 实现的 LLM 推理引擎，由 Georgi Gerganov 开发，是端侧部署最流行的开源方案。

GGUF 格式

GGUF（GPT-Generated Unified Format）是 llama.cpp 使用的模型格式，取代了早期的 GGML 格式：

  • 单文件包含模型权重 + 元数据 + 词表
  • 支持内存映射（mmap），按需加载
  • 向后兼容，支持扩展元数据
# 从 HuggingFace 格式转换为 GGUF
python convert_hf_to_gguf.py ./model_dir --outtype f16 --outfile model.gguf

# 量化
./llama-quantize model.gguf model-Q4_K_M.gguf Q4_K_M
GGUF 单文件的结构，以及 mmap 为什么能让内存占用看起来"变小" model-Q4_K_M.gguf ┌────────────────────────────────────────────┐ │ Header 魔数 / 版本 / 张量数 │ ├────────────────────────────────────────────┤ │ Metadata 架构、层数、head 数、RoPE 参数 │ │ 词表 + 分词器配置（都在文件里） │ ├────────────────────────────────────────────┤ │ Tensor Info 每个张量的名字 / 形状 / 量化类型 │ ├────────────────────────────────────────────┤ │ Tensor Data ┌── block 0 ─┐ │ │ │ scale(fp16)│ 32~256 个权重 │ │ │ min (fp16)│ 共享一组 scale │ │ │ 4-bit 权重 │ │ │ └────────────┘ ... 重复 N 次 │ └────────────────────────────────────────────┘ │ │ mmap ▼ ┌─ 进程地址空间 ───────────────────────────────┐ │ 权重页并不预先读入，访问到哪一页才缺页加载 │ │ 多个进程加载同一模型时共享同一份物理页 │ │ 内存吃紧时 OS 可回收干净页，不会 OOM 直接死 │ └─────────────────────────────────────────────┘ ★ 这也是为什么 llama.cpp 启动很快：它没有真的"加载"整个模型 ★ 但首轮推理会明显偏慢——缺页中断都发生在这一轮

  • Q4_K_M 是最常用的量化级别，"K" 表示 k-quant 分组量化

三、MLC-LLM

llama.cpp 是手写一份高度优化的实现去适配所有硬件，MLC-LLM 是让编译器针对每块硬件各生成一份。

MLC-LLM（Machine Learning Compilation for LLM）是基于 Apache TVM 的多平台 LLM 部署框架，由陈天奇团队主导开发。

核心架构

HuggingFace 模型 → TVM Relax IR → 编译优化 → 平台特定代码

支持平台

平台后端特点
iOSMetal GPU原生 Swift App 集成
AndroidVulkan / OpenCL原生 Java/Kotlin 集成
WebWebGPU浏览器内运行 LLM
Windows/LinuxCUDA / Vulkan桌面端 GPU 加速
macOSMetalApple Silicon 原生支持

TVM 编译优化

  • 算子融合 — 将多个小算子合并为一个 kernel，减少内存访问
  • 内存规划 — 静态分析推理图，最大化内存复用
  • 量化感知编译 — 在编译期完成量化，生成高效量化 kernel
  • Auto-tuning — 针对具体硬件自动搜索最优实现
# MLC-LLM 编译示例
mlc_llm compile ./model_config.json \
  --device "cuda" \
  --opt "O2" \
  --output ./compiled_model

WebGPU 支持

MLC-LLM 通过 WebGPU 实现浏览器内 LLM 推理，这也是 WebLLM 项目的基础：

  • 利用浏览器 GPU 加速，性能远超 WASM
  • Chrome 113+ 默认启用 WebGPU
  • 模型权重缓存在 IndexedDB / Cache Storage
  • MLC-LLM vs llama.cpp：MLC 侧重多平台 GPU 编译优化，llama.cpp 侧重 CPU 推理
  • TVM 编译的核心优势：针对目标硬件生成最优代码，而非通用实现
  • MLC-LLM 是目前 WebGPU 端 LLM 推理的主要方案

四、ONNX Runtime

ONNX 负责让模型能被搬走，ONNX Runtime 负责让它在搬到的那台机器上跑得动——两件事常被混为一谈。

ONNX Runtime（ORT）是微软开源的跨平台推理引擎，支持 ONNX 格式的模型推理优化。其可移植性来自 Execution Provider 机制。

ONNX 格式转换

# PyTorch → ONNX
import torch

model = load_my_model()
dummy_input = torch.randn(1, 512)
torch.onnx.export(
    model, dummy_input, "model.onnx",
    opset_version=17,
    dynamic_axes={"input": {0: "batch", 1: "seq_len"}}
)

# HuggingFace Optimum 转换
optimum-cli export onnx --model meta-llama/Llama-3-8B ./onnx_output/

执行提供者（Execution Provider）

一个 ONNX 模型在不同设备上的落地路径：图不变，执行的人换了 model.onnx（一份计算图） │ ┌────────┴────────┐ │ 图优化 / 常量折叠 │ │ 算子融合 / 布局转换│ └────────┬────────┘ │ ┌──────────┬──────────┼──────────┬──────────┐ ▼ ▼ ▼ ▼ ▼ CUDA EP QNN EP CoreML EP DirectML EP CPU EP N卡 GPU 高通 NPU Apple 设备 Win 全系 GPU 任意 CPU │ │ │ │ │ └──────────┴──────────┴──────────┴──────────┘ │ ▼ ★ EP 只接手它支持的算子子图，剩下的自动回落到 CPU EP 副作用：一张图可能被切成多段，在 NPU 和 CPU 之间来回搬 搬运开销有时会吃掉加速收益 —— 这是端侧调优的常见坑

DirectML 集成

DirectML 是 Windows 上的跨厂商 GPU 推理方案：

  • 支持 AMD、Intel、NVIDIA 全系列 GPU
  • Windows 10/11 原生支持，无需额外驱动
  • Windows Copilot Runtime 底层基于 DirectML + ONNX Runtime
  • ONNX 是模型交换的"通用语言"，几乎所有框架都可导出 ONNX
  • ONNX Runtime 的优势在于 Execution Provider 机制——同一模型自动适配不同硬件
  • DirectML 让 Windows 端 AI 推理不再绑定 NVIDIA
  • 注意区分：ONNX（格式标准）vs ONNX Runtime（推理引擎）

五、CoreML / Apple Silicon

Apple 端侧能跑大模型，靠的不是算力多强，而是统一内存让"显存"这个瓶颈消失了。

Apple 通过 CoreML + Apple Neural Engine + MLX 构建了完整的端侧 AI 部署生态。

CoreML 模型转换

import coremltools as ct

# PyTorch → CoreML
mlmodel = ct.convert(
    traced_model,
    inputs=[ct.TensorType(shape=(1, 512))],
    compute_precision=ct.precision.FLOAT16,
    compute_units=ct.ComputeUnit.ALL  # CPU + GPU + ANE

mlmodel.save("model.mlpackage")

MLX 框架

MLX 是 Apple 专为 Apple Silicon 设计的机器学习框架：

  • 统一内存 — CPU 和 GPU 共享内存，零拷贝切换
  • 惰性计算 — 按需执行，减少不必要计算
  • NumPy 风格 API — 学习成本极低
# MLX 加载 & 推理
import mlx.core as mx
from mlx_lm import load, generate

model, tokenizer = load("mlx-community/Llama-3-8B-4bit")
response = generate(model, tokenizer, prompt="Hello", max_tokens=100)

六、Android 端部署

Android 的难处不在框架，在碎片化：同一份模型要在几十种芯片上都能跑，NNAPI 就是那层挡住差异的墙。

TensorFlow Lite / NNAPI

TensorFlow Lite (TFLite) 是 Google 的移动端推理框架：

  • 模型转换：TF/PyTorch → TFLite FlatBuffer 格式
  • NNAPI 委托：自动利用芯片厂商的 NPU/DSP 加速
  • GPU 委托：通过 OpenGL ES / OpenCL 调用 GPU
// Android: TFLite 推理
val interpreter = Interpreter(loadModelFile("model.tflite"))
interpreter.run(inputBuffer, outputBuffer)

NNAPI（Android Neural Networks API）是 Android 8.1+ 提供的硬件抽象层，让推理框架透明调用底层加速器。

MediaPipe

Google 的端侧 AI 解决方案，提供即开即用的任务 API：

任务模型说明

Text ClassificationBERT-based文本分类
Object DetectionEfficientDet实时目标检测
Image SegmentationDeepLab图像分割

Qualcomm AI Engine

  • Hexagon NPU — 高通旗舰 SoC 的专用 AI 加速器，Snapdragon 8 Gen 3 可达 73 TOPS
  • QNN SDK — 直接编程 Hexagon NPU，性能最优
  • AI Hub — 提供预优化模型库，覆盖常见任务
  • SNPE — 支持 Caffe/ONNX/TF 模型导入，自动硬件调度
  • Android 端侧推理路径：App → TFLite/MediaPipe → NNAPI → 芯片厂商驱动 → NPU/GPU
  • MediaPipe 适合快速集成标准任务，QNN SDK 适合追求极致性能
  • 高频考点：NNAPI 的作用？— 硬件抽象层，屏蔽芯片差异

七、小模型策略

端侧不缺"把大模型压小"的办法，缺的是判断：这个任务到底需不需要大模型的知识广度。

端侧设备资源有限，需要"小而精"的模型。以下是主要的小模型构建策略。

知识蒸馏（Knowledge Distillation）

大模型（Teacher） → 软标签 / 特征 → 小模型（Student）
  • 输出蒸馏 — Student 学习 Teacher 的 logits 分布（软标签）
  • 特征蒸馏 — Student 模仿 Teacher 中间层的特征表示
  • 数据蒸馏 — 用 Teacher 生成高质量训练数据，再训练 Student
# 蒸馏损失 = α * hard_loss + (1-α) * soft_loss
loss = alpha * F.cross_entropy(student_logits, labels) + \
       (1 - alpha) * F.kl_div(
           F.log_softmax(student_logits / T, dim=-1),
           F.softmax(teacher_logits / T, dim=-1),
           reduction="batchmean"
       ) * (T * T)

模型剪枝（Pruning）

方法粒度说明
非结构化剪枝单个权重将小权重置零，需要稀疏计算支持
结构化剪枝整个神经元/层/头直接减小模型尺寸，不需特殊硬件
SparseGPT半结构化2:4 稀疏模式，NVIDIA A100+ 硬件加速

小模型 vs 量化大模型

方案示例内存质量推理速度
小模型原生Phi-3 Mini FP16~7.6 GB★★★★快
大模型量化Llama3-8B Q4_K_M~4.1 GB★★★☆中等
小模型量化Phi-3 Mini Q4~2.3 GB★★★最快

经验法则：相同内存下，高质量小模型（如 Phi-3）通常优于量化大模型；但大模型在知识广度和复杂推理上仍有优势。

示例场景：一款离线笔记 App 要在中端 Android 机上做"选中文字改写"，设备可用内存约 3 GB。

问题：团队第一版直接上 8B 模型的 Q2_K 量化（约 2.7 GB），内存刚好装下，但改写结果频繁出现语义漂移和中英混杂，人工抽检合格率只有约 六成；同时首 Token 要等 4 秒以上，用户几乎不会用第二次。

方案：换成 3B 级小模型的 Q4_K_M（约 1.9 GB），省出的内存拿去做两件事：把上下文窗口从 512 提到 2048，让改写能看到完整段落；再对高频的四类改写意图各写一版固定 Prompt 模板，减少模型自由发挥的空间。

效果：抽检合格率回到约 九成，首 Token 降到 1 秒出头，内存峰值反而低了约 0.8 GB。结论不是"小模型更好"，而是在这个内存档位上，把参数量花在极端量化上不如花在上下文和确定性上。

  • 蒸馏的核心：让小模型学习大模型的"暗知识"（soft label 中的类间关系）
  • 结构化剪枝可直接提速，非结构化剪枝需要稀疏计算硬件/库支持
  • 高频考点：蒸馏温度 T 的作用？— T 越大，软标签越平滑，学到更多类间关系
  • 小模型选择关注：参数量、目标语言、许可证、社区活跃度

八、WebLLM / 浏览器端

浏览器端 LLM 真正的门槛不是算得慢，是用户要先下载几个 GB 才能看到第一个字。

WebLLM 让 LLM 完全运行在浏览器中，无需服务器，是端侧部署的前沿方向。

WebGPU API

WebGPU 是下一代浏览器 GPU API，取代 WebGL：

  • Compute Shader 支持 — 通用 GPU 计算，不限于图形渲染
  • 更低开销 — 比 WebGL 更接近原生 GPU 性能
  • Chrome 113+、Edge 113+、Firefox Nightly 已支持
// WebGPU 计算着色器示例
const device = await navigator.gpu.requestAdapter()
  .then(adapter => adapter.requestDevice());

const shaderModule = device.createShaderModule({
  code: `@compute @workgroup_size(64)
         fn main(@builtin(global_invocation_id) id: vec3u) {
           // matrix multiplication kernel
         }`
});

浏览器内推理架构

模型下载 → Cache Storage 缓存 → WebGPU Compute → Token 流式输出

WebAssembly 方案

对于不支持 WebGPU 的浏览器，WASM 是备选方案：

前景：随着 WebGPU 普及和模型小型化，浏览器端 AI 将成为隐私优先应用的标配。Chrome 已内置 Gemini Nano 支持（window.ai API）。

示例场景：一个面向法务的文档脱敏工具，要求原文绝不上传，于是选了浏览器内推理，模型权重约 1.6 GB。

问题：上线后发现首次打开的跳出率超过 七成。埋点显示中位下载耗时接近 3 分钟，期间页面只有一个进度条；更糟的是部分用户在下载完成前关掉标签页，下次进来又要从头下——缓存写入发生在下载全部完成之后。

方案：三处调整：① 权重按分片下载并逐片写入 Cache Storage，中断后可续传；② 首屏先加载一个几十 MB 的极小模型，让用户马上能用基础的正则+小模型脱敏，大模型在后台继续下载，好了再无感切换；③ 在下载页明确写出"约 1.6 GB，仅首次，之后完全离线"。

效果：首次跳出率降到约 三成，二次访问因为命中缓存基本是秒开。这里的关键不是让下载变快，而是把"等待"从阻塞变成了后台。

  • WebLLM 基于 MLC-LLM 的 WebGPU 编译产物
  • WebGPU vs WebGL：WebGPU 支持 Compute Shader，WebGL 只能用 Fragment Shader 模拟计算
  • 浏览器端 LLM 的核心限制是 GPU 内存，通常只能跑 ≤3B 的量化模型
  • 亮点：提到 Chrome window.ai API（Gemini Nano 内置推理）

端云协同的全部工程量都在路由那一步：判错一次的代价，往往比多花的那点云端费用大得多。

离线缓存

端云协同的关键组件——确保离线时也能提供服务：

  • 响应缓存 — 缓存高频问答结果，相似查询直接命中
  • 嵌入缓存 — 本地向量库缓存常用文档的 embedding
  • 模型版本管理 — 端侧模型按需更新，增量下载
  • Prompt 缓存 — KV Cache 持久化，加速重复 prefix 推理
  • 先量化再评估，用真实业务样本跑一遍抽检，而不是只看困惑度
  • 把模型下载做成可断点续传、分片写缓存，首次体验决定留存
  • 端侧结果和云端结果分别打点，事后能算清路由判对判错的比例
  • 为低端机准备降级路径：更小的模型、更短的上下文、纯 CPU 后端
  • 发布前在最差的目标机型上跑长时压测，观察发热降频后的速度
  • 不要为了塞进内存无脑上 2-bit 量化，质量崩塌往往先出现在长回答上
  • 不要假设 NPU 一定更快，算子不被支持时会来回搬运，反而比 CPU 慢
  • 不要在主线程做模型加载和推理，界面卡死比慢更劝退
  • 不要让端侧模型静默返回低置信度结果，至少要有可见的来源标记
  • 不要把端侧当成云端的完整替代，复杂推理和长上下文仍应上云

🎯 Q&A

Q1：llama.cpp 的 Q4_K_M 量化是如何工作的？为什么叫 K-quant？

A：Q4_K_M 采用 k-quant（k-means quantization）分组量化策略：

  • 将权重按 block（通常 32 或 256 个权重一组）进行量化
  • 每个 block 有独立的 scale 和 min 值，用更高精度（FP16）存储
  • "K" 代表 k-quants 方法，"4" 代表主体 4-bit，"M" 代表 Medium 质量档（介于 S/Small 和 L/Large 之间）
  • 关键创新：对模型中更重要的层（如 attention 的 Q/K 矩阵）使用更高精度量化

与朴素的 round-to-nearest 量化相比，k-quant 通过分组和自适应精度显著降低量化损失。

Q2：知识蒸馏中，温度参数 T 的作用是什么？

A：温度 T 控制 Teacher 输出的 softmax 分布平滑度：

  • T = 1：标准 softmax，输出集中在 top-1 类别
  • T > 1：分布更平滑，暴露更多类间关系（"暗知识"）
  • 例如：手写数字识别中，"7" 与 "1" 的相似度 > "7" 与 "0" 的相似度，这种关系在高温度下才能被 Student 学到
  • 常用 T = 2~20，通过验证集调优

蒸馏损失中 ×T² 的原因：高温度下 softmax 梯度缩小为 1/T²，乘以 T² 补偿梯度幅度。

Q3：ONNX Runtime 的 Execution Provider 机制是什么？

A：Execution Provider（EP）是 ONNX Runtime 的硬件抽象机制：

  • 每个 EP 负责在特定硬件上执行算子（如 CUDAExecutionProvider 在 GPU 上执行）
  • 支持 EP 链：按优先级尝试多个 EP，某个算子在高优先级 EP 不支持时，自动回退到下一个
  • 同一模型的不同算子可以运行在不同设备上（如部分在 GPU，部分在 CPU）
  • 开发者只需改一行代码切换硬件：providers=["CUDAExecutionProvider", "CPUExecutionProvider"]

这种设计让同一个 ONNX 模型可以无缝适配从云端 GPU 到端侧 NPU 的全场景。

Q4：Apple 的统一内存架构（UMA）对 LLM 推理有何优势？

A：Apple Silicon 的统一内存架构对 LLM 有独特优势：

  • 无显存墙：传统 PC 的 GPU 显存通常 8–24GB，限制可运行模型大小；Mac 统一内存最大可达 512GB（M4 Ultra），CPU/GPU 共享
  • 零拷贝：数据在 CPU/GPU/ANE 间切换无需复制，大幅减少延迟
  • 带宽优势：M4 Max 统一内存带宽 546 GB/s，LLM 推理是内存带宽密集型任务
  • 能效比：同等性能下功耗远低于独立 GPU 方案

这使得 Mac 成为本地运行大模型的优秀平台——M2 Ultra 128GB 可流畅运行 70B 模型。

Q6：端云协同架构中，路由策略如何设计？

A：常见的端云路由策略：

  1. Confidence-based：端侧模型先推理，输出 confidence < 阈值时转云端（最常用）
  2. Classifier-based：训练一个轻量分类器判断任务难度，决定端/云
  3. Rule-based：根据任务类型（如代码生成 → 云端）、输入长度等规则路由
  4. Cascade：小模型 → 中模型 → 大模型逐级升级
  5. Speculative Decoding 变体：端侧模型生成 draft tokens，云端验证

实际系统通常组合多种策略，并根据网络状态、预算、延迟要求动态调整。关键指标是"路由准确率"——减少不必要的云端调用同时保证质量。

Q7：WebGPU 和 WebGL 用于 AI 推理有什么区别？

A：

  • WebGL：图形渲染 API，AI 推理需要"hack"——将矩阵运算编码为纹理操作，通过 Fragment Shader 执行，效率低且编程复杂
  • WebGPU：原生支持 Compute Shader，可直接编写通用 GPU 计算 kernel，更接近 CUDA/Metal 的编程模型

关键差异：

AI 推理性能基准3–10× 提升

WebGPU 让浏览器端 LLM 推理从"勉强可用"变成"实际可用"。

Q8：结构化剪枝和非结构化剪枝的区别和各自优势？

A：

  • 非结构化剪枝：移除单个权重（置零），可实现高稀疏率（90%+），但需要稀疏计算库（如 cuSPARSE）或专用硬件才能加速
    • 代表方法：Magnitude Pruning, SparseGPT
  • 结构化剪枝：移除整个神经元、注意力头或整层，直接减小模型维度，无需特殊硬件即可加速
    • 代表方法：LLM-Pruner, SliceGPT
  • 半结构化（2:4 稀疏）：每 4 个权重保留 2 个，NVIDIA A100+ 硬件原生支持，2× 理论加速

选择建议：追求部署便利性选结构化剪枝；有硬件支持时选半结构化；追求最大压缩率选非结构化。

Q10：Speculative Decoding 如何提升推理效率？与端云协同有何联系？

A：Speculative Decoding（投机解码）的核心思路：

  1. Draft 阶段：用小模型（draft model）快速自回归生成 K 个 token
  2. Verify 阶段：用大模型一次前向传播并行验证这 K 个 token
  3. Accept/Reject：验证通过的 token 保留，不通过的从大模型重新采样

数学保证：通过修正采样策略，输出分布与纯大模型完全一致（无质量损失）。

与端云协同的联系：

  • 可以将 draft model 放在端侧，verify model 放在云端
  • 端侧持续生成 draft tokens，批量发送云端验证
  • 减少云端请求次数（K 个 token 只需 1 次验证），降低延迟和成本
  • 离线时降级为纯端侧小模型推理

典型加速比：2–3×，取决于 draft model 的 acceptance rate。
