DP12 · Prefill / Decode 分离架构

阶段干扰 / DistServe 与 Mooncake / KV 跨节点传输 / xPyD 配比 / SLO 拆分 / Goodput 导向

Prefill 想要算力，Decode 想要带宽，把两个胃口完全相反的阶段塞进同一张卡，等于让它们互相抢饭吃；PD 分离就是给它们各开一桌。

推理系统的优化走到某个阶段会遇到一堵墙：TTFT 和 TPOT 这两个延迟指标像跷跷板，压下去一个另一个就翘起来，加卡也只是把整条曲线平移一点。这堵墙的成因不在内核也不在调度算法，而在两个阶段被物理地绑在同一批 GPU 上。PD 分离（Prefill/Decode Disaggregation）是拆掉这堵墙的架构级手段。阅读本文前建议先理解 DP08 · KV Cache 与推理优化 里的阶段划分，以及 DP11 · Continuous Batching 与推理调度策略 里的单卡内调度权衡——PD 分离正是在单卡调度手段用尽之后的下一步。

一、为什么要拆开：两个阶段的资源画像完全冲突

自回归推理被 KV Cache 天然切成两段，这两段对硬件的诉求几乎是对立的。

算力密集 vs 访存密集

Prefill 一次性处理整段 prompt，n 个 token 的 QKV 投影和 FFN 都是大矩阵乘，算力需求约为 2 × 参数量 × n FLOPs，而权重只需从显存读一遍。算术强度（Arithmetic Intensity，每读取一字节数据能做多少次浮点运算）很高，GPU 的 Tensor Core 能吃满，属于典型的 compute-bound（算力受限）。

Decode 每步只处理 1 个 token，算力需求约 2 × 参数量 FLOPs，但仍然要把整个模型权重和该请求的全部 KV Cache 从 HBM 读一遍。算术强度低到个位数，GPU 绝大部分时间在等数据，SM 利用率常年不到 10%，属于 memory-bandwidth-bound（访存带宽受限）。

Prefill 是把一整车货一次卸完的重体力活，Decode 是每隔几十毫秒来回跑一趟取一件小东西的跑腿活；派同一个人干，两件事都干不好。

干扰是怎么发生的

把两者混在一张卡上，会产生双向的伤害。长 prompt 的 prefill 占满计算单元时，同批的 decode 请求虽然只需要读点数据，也得排队等这个前向步结束——用户看到的是输出流突然卡顿。反过来，为了让 decode 的批足够大以摊薄权重读取成本，系统要留大量显存给 KV Cache，留给 prefill 激活值的空间就被压缩，长 prompt 的 prefill 只能切得更碎、跑得更慢。

更深一层的代价是资源分配与并行策略被强行耦合。共置架构下，张量并行度、batch 上限、显存切分比例这些配置对两个阶段是同一套，而两个阶段的最优解并不相同。想让 prefill 快就要小 TP（减少通信开销、靠 token 维度并行），想让 decode 快就要大 TP（每卡分到更多带宽、更多 KV 空间）。共置意味着必须选一个折中值，两边都不最优。

共置架构的根本困境不是"资源不够"，而是"同一份资源被两种相反的需求同时定义"，加卡只能平移曲线，改不了形状。

二、PD 分离的架构拓扑与代表性设计

PD 分离的核心动作只有一句话：把 prefill 和 decode 放到不同的 GPU 上，中间通过网络传 KV Cache。但把这句话做成能上生产的系统，需要补齐路由、传输、调度、容错四块拼图。

三种代表性设计

DistServe（OSDI 2024，UCSD & 北大）是把这件事讲透的学术起点。它的核心论点是评价指标应该从吞吐换成 Goodput（有效吞吐，即在满足 SLO 前提下每秒能完成的请求数）：一个系统吞吐再高，如果大部分请求都违反了 TTFT 或 TPOT 承诺，这些吞吐对业务毫无价值。基于这个指标，DistServe 把两个阶段拆到不同 GPU，并用模拟器驱动的搜索算法为每个阶段单独选择 GPU 数量和并行策略，同时按集群带宽拓扑做放置以压低传输成本。论文报告在满足延迟约束（>90% 请求达标）的前提下，可服务请求数最高提升 7.4 倍，或在同等资源下支撑 12.6 倍更严格的 SLO。

Mooncake（月之暗面 Kimi 的服务平台，FAST 2025）把架构重心从"分离"推进到"KVCache 为中心"。它不仅分离 P/D 集群，还把 GPU 集群里长期闲置的 CPU、DRAM、SSD、网卡组织成一个全局分布式 KVCache 池，让 KV 既能在节点间传递，也能跨请求、跨会话复用——本质是"用更多存储换更少计算"。配套的 Transfer Engine 做拓扑感知的路径选择：每台服务器启动时生成一份拓扑矩阵并广播全集群，为每类内存区域标注首选网卡和备选网卡，传输时优先走同 NUMA 域内的 RDMA 或经本地 PCIe Switch 的 GPUDirect RDMA，避开跨 UPI 的带宽瓶颈。调度层还引入基于预测的早期拒绝：在过载时提前判断某请求无论如何都无法满足 SLO，直接拒绝，避免把算力浪费在注定违约的请求上。Mooncake 已运行在数千节点上，日处理超过 1000 亿 token；真实 trace 下有效请求容量提升 59%~498%，在 A800 和 H800 集群上分别让 Kimi 多承接 115% 和 107% 的请求。

NVIDIA Dynamo 代表了工程化封装的方向：它把 PD 分离做成一个跨推理后端（vLLM、SGLang、TensorRT-LLM）的编排层，用 NIXL 做 GPU 显存到 GPU 显存的直接传输，支持运行时可重配的 xPyD（x 个 prefill worker + y 个 decode worker），worker 可以在线增减；配套的 Planner 会根据 TTFT/ITL 的 SLA 目标和 KV 传输成本，自动调整 P/D 的数量配比。

第③步有个容易被忽略的坑：传输失败时的策略。如果配成"失败就在 decode 侧重算"，看似优雅降级，实际是让一台按 decode 优化（大 TP、大 batch、小激活空间）的机器去干 prefill 的活，效率极低，还会把同机器上其他请求的尾延迟一起拖垮。生产环境更稳妥的做法是让传输失败显式报错并由上层重试，而不是静默降级。

PD 分离不是把一个系统劈成两半就完事，它把"阶段间的资源竞争"换成了"节点间的数据搬运"，成败取决于这笔交换划不划算。

三、KV Cache 跨节点传输：核心成本与带宽账

分离带来的唯一新增成本就是 KV 传输。这笔账必须算清楚，因为它直接决定了 PD 分离在你的场景下是赚是赔。

先算传输量

每 token KV 字节数 = 2 × 层数 × KV头数 × 头维度 × 精度字节
单请求传输量 = 每 token KV 字节数 × prompt 长度

以 Llama-3.1-70B 为例（80 层、8 个 KV 头、头维 128、GQA），FP16 精度下每 token 的 KV 为 2 × 80 × 8 × 128 × 2 = 327,680 字节，约 320 KB。据此可以列出不同 prompt 长度的传输量：

把这张表和 prefill 本身的耗时对比，结论就出来了。8K prompt 在 H100 上做 prefill 大约需要 300~600 毫秒，此时走 NVLink 的 6.4 毫秒或 InfiniBand 的 51 毫秒都只是零头；但 512 token 的 prompt prefill 只要 15~30 毫秒，再叠加固定的握手开销，传输反而成了主要成本。PD 分离的经济性随 prompt 长度单调上升，业界经验阈值大致在 2K token 附近。

三个把传输成本压下去的工程手段

  • 与 decode 重叠：KV 按 block 分批传输，第一批到达 D 就可以启动前几个 decode 步，后续 block 在计算的同时继续传。传输因此被计算掩盖，在 NVLink 上几乎完全隐藏。
  • 拓扑感知选路：同一台服务器上有多张网卡，但只有部分网卡与目标显存处在同一 NUMA 域或同一 PCIe Switch 下。盲目选卡会让数据穿越 UPI 总线，带宽腰斩。Mooncake 的做法是预先生成拓扑矩阵，为每段内存标注首选和备选网卡列表。
  • 传输前压缩：把 KV 量化到 FP8 再传，字节数直接减半，且 decode 侧本来就可以用 FP8 KV 计算，无需反量化。这是性价比最高的一招，具体方法见 DP09 · KV Cache 优化。

KV 传输不怕慢，怕的是"挡在关键路径上"；只要它能和 decode 计算重叠、能被前几步掩盖，几十毫秒的传输在用户侧就是不存在的。

生产案例（长文档摘要服务）：某法律科技公司提供合同审阅服务，平均 prompt 27K token、输出 600 token，用 8×H100 共置部署 Llama-3.1-70B（TP=4，两副本）。共置方案下 TTFT p95 为 11.3 秒、TPOT p95 为 118 ms，两个指标同时违反了产品定的 8 秒 / 60 ms SLO；把并发压低能救 TPOT 但 TTFT 更差，加到 12 卡也只是把两条曲线各平移 15% 左右。改为 PD 分离后（4 卡 prefill 池 TP=2 两副本 + 8 卡 decode 池 TP=4 两副本，共 12 卡，InfiniBand NDR 400G 互联，KV 走 FP8），单请求 KV 传输量约 4.2 GB、实测传输 78 ms 且与前几个 decode 步重叠掉约六成。最终 TTFT p95 降到 6.1 秒（−46%），TPOT p95 降到 41 ms（−65%），SLO 达标率从 34% 升到 96%。注意达标率的提升幅度远大于任何单项延迟的降幅——这正是 goodput 视角的价值所在。

四、P 与 D 的独立扩缩容与配比计算

分离之后最大的运维红利是：两个池子可以按各自的瓶颈独立扩缩，不再被迫等比例加卡。

配比的基本算法

把 P 池和 D 池当成流水线上的两道工序，配比的目标是让两道工序的处理速率匹配，谁也不成为长期堵点。

单个 P worker 速率 Rp = 1 / (平均 prompt 长度 × 单 token prefill 耗时)
单个 D worker 速率 Rd = 并发批大小 / (平均输出长度 × TPOT)
配比 x : y ≈ Rd : Rp　（速率慢的一方要配更多实例）

直觉上，输入越长、输出越短，prefill 的活越重，P 池要配得越多；反之输出越长，decode 的活越重，D 池要配得越多。这解释了为什么不同业务的最优配比差异巨大。

并行策略也应该分开选

分离最被低估的收益是：P 和 D 可以用不同的张量并行度。Prefill 本身有充足的 token 维并行度，不需要靠大 TP 来榨算力，反而 TP 越大跨卡通信开销占比越高，所以 P 池倾向用小 TP。Decode 相反，大 TP 意味着每卡只需读 1/TP 的权重、聚合带宽更高，同时每卡分到的 KV 空间更大，能支撑更大的批和更高的前缀缓存命中率，所以 D 池倾向用大 TP。共置架构被迫用一个折中值，分离后这个约束消失了。

扩缩容的独立性（同一集群，两种流量变化） 场景 1：早高峰，用户涌入，prompt 长度不变 P 池：QPS↑ → 需要更多 prefill 算力 → 扩 P D 池：并发↑ → KV 压力↑ → 同步扩 D ⇒ 两池等比例扩，与共置无本质差异 场景 2：产品上线"上传文档提问"功能，prompt 从 1K 涨到 20K P 池：单请求 prefill 算力 ×20 → P 需扩 3~4 倍 D 池：输出长度不变，KV 变大 → D 只需小幅扩容 ⇒ 共置架构下你必须整体扩 3 倍（浪费） 分离架构下只扩 P 池（省下的是真金白银） 场景 3：模型换成推理型，输出从 300 涨到 4000 token P 池：几乎无变化 → 不动 D 池：每请求占用 D 的时间 ×13 → D 需扩数倍 ⇒ 分离让扩容动作精准落在真正的瓶颈上 ┌──────────────────────────────────────────────────┐ │ 共置：任何一端成为瓶颈，都要整体扩容 → 另一端浪费 │ │ 分离：哪端瓶颈扩哪端 → 资源利用率显著提升 │ └──────────────────────────────────────────────────┘

固定配比还是动态调度

业界有两派做法。动态派（如 Dynamo 的 SLA/负载 Planner）在运行时根据实时 SLO 达标情况和队列长度调整 P/D 数量，理论上最优，但要和自动扩缩容联动，编排复杂度和抖动风险都不低。固定派则预先压测出一个配比，配合常规的整体自动扩缩。近期的对比基准显示，在多种负载画像和并发水平下，精心选定的固定配比已经能提供相当稳健的表现，动态调整的额外收益未必能覆盖它带来的复杂度。务实的建议是：先用固定配比上线并把监控做扎实，只有当流量画像本身随时段剧烈漂移（例如白天短问答、夜间长文档批处理）时，才引入动态 Planner。

配比不是一个需要求解的最优化问题，而是一个需要按流量画像选档位的工程决策；先固定，再观察，别一上来就上动态。

五、SLA 拆分与 Goodput 导向的容量规划

PD 分离带来的一个思维方式转变是：SLO 不再是一个整体，而是可以拆开归属的。

把 SLO 分配给对应的池子

这种归属关系让排障变得干净：TTFT 报警只需要看 P 池，TPOT 报警只需要看 D 池，两者不会互相甩锅。共置架构下这是不可能的——任何一个指标劣化都可能是另一个阶段挤压的结果。

为什么要用 Goodput 而不是 Throughput

吞吐量统计的是"每秒完成了多少 token"，不区分这些 token 属于按时交付的请求还是已经超时的请求。而对业务来说，一个 TTFT 超过 10 秒的请求，用户早就关掉页面了，它产生的 token 是纯粹的浪费。Goodput 只统计同时满足 TTFT 和 TPOT 约束的那部分请求，是真正对应用户体验和商业价值的指标。

Throughput 与 Goodput 的分歧 随并发上升的两条曲线 指标 ↑ │ Throughput ────────────●──────────── 继续爬升 │ ╱ │ ╱ │ ╱ ╲ │ ╱ ╲ Goodput 在此见顶后回落 │ ╱ ╲ │ ╱ ╲────────────── └────────────────────────────────────────────→ 并发 ↑ 最优工作点 ↑ 吞吐仍在涨， （Goodput 峰值） 但违约请求越来越多 超过 Goodput 峰值后，系统在做"生产废品"： 算力被消耗，token 被生成，但请求已违约，业务价值为零 容量规划应该锚定 Goodput 峰值，而不是 Throughput 峰值

Goodput 视角还改变了过载时的策略。传统做法是"尽力而为，都排着"，结果是所有请求一起变慢、一起违约。更优的做法是预测式早期拒绝：在请求入队时就根据当前队列深度估算它的预期 TTFT，如果注定违约就直接返回错误或降级，把算力留给还能达标的请求。Mooncake 在重载场景下正是用这个机制守住 SLO 的。这在直觉上有点反常识——主动拒绝一部分请求反而提升了整体交付量——但只要指标是 goodput，这个结论就是自洽的。

吞吐量是"机器有多忙"，Goodput 是"用户拿到了多少有用的东西"；过载时主动丢掉注定违约的请求，是在提升后者。

生产案例（编程助手的 SLO 拆分）：某代码补全服务平均 prompt 9K token（整个文件加上下文）、输出仅 90 token，TTFT SLO 定为 900 ms、TPOT SLO 为 50 ms。共置部署 16×H100（Qwen2.5-Coder-32B，TP=4，四副本）时 goodput 只有 8.7 req/s，瓶颈全在 TTFT——长 prompt 的 prefill 反复被 decode 请求切碎，p95 TTFT 达 2.4 秒。团队按 SLO 归属做了拆分改造：TTFT 归 P 池，于是把 10 卡划给 prefill（TP=2，五副本，小批快进快出）；TPOT 归 D 池，剩 6 卡给 decode（TP=3，两副本，大批高并发）。由于输出只有 90 token，D 池负担很轻，这个偏 prefill 的配比（约 5:2）与常规的 1:3 完全相反，但正好匹配业务画像。改造后 p95 TTFT 降到 680 ms，p95 TPOT 为 33 ms，goodput 升至 26.5 req/s（提升 3.05 倍），GPU 总数未变。同样 16 张卡，只是换了切分方式和配比，有效产出翻了三倍。

六、什么场景不该上 PD 分离，以及与 Chunked Prefill 的取舍

PD 分离是有明确适用边界的架构手段，用错场景会既增加复杂度又降低性能。

四类不该上的场景

场景为什么不该上正确做法
短 prompt（< 1~2K token）KV 传输的固定开销（握手 + 首字节，通常 5~20 ms）与 prefill 本身耗时同量级，纯亏共置 + Chunked Prefill
小规模部署（单机或几张卡）拆池后每池只剩一两张卡，批规模和 KV 容量双双腰斩，收益为负共置，把卡集中给一个池子用
SLO 宽松的离线批处理没有延迟约束，goodput 等于 throughput，分离带来的传输开销和调度损失是净成本共置 + 大 token 预算，吞吐优先

还有一类值得单独提醒：流量规模不足以喂饱两个池子时不该拆。分离的前提是两个池子都能跑在各自的高效工作点上——P 池需要持续的 prompt 流来打满算力，D 池需要足够并发来摊薄权重读取。如果 QPS 很低，拆开后两边都在低负载空转，总体效率反而不如共置。业界经验是集群规模到几十张卡、并发上量之后，分离的收益才稳定为正。

与 Chunked Prefill 的关系：递进而非互斥

两者解决同一个问题的不同层次。Chunked Prefill 是时间维度的隔离：在一张卡上把长 prefill 切片，与 decode 交替执行，把"一个人卡所有人"变成"每步都卡一点点"。PD 分离是空间维度的隔离：干脆让它们在不同的卡上跑，干扰从根上消失。

正确的演进顺序是：先把共置架构下的调度参数调到位（这是零成本的，方法见 DP11 · Continuous Batching 与推理调度策略），把前缀缓存和 KV 量化都开起来，如果此时 TTFT 和 TPOT 仍然无法同时达标，再考虑 PD 分离。跳过前面的步骤直接上分离，常见结果是复杂度上去了、指标却没什么改善——因为真正的瓶颈可能只是一个没调过的 token 预算。

Chunked Prefill 是止痛药，PD 分离是手术；先吃药看效果，药不管用再考虑动刀，别一上来就进手术室。

  • 先穷尽共置调优（token 预算、前缀缓存、KV 量化）再考虑分离
  • 用 goodput 而非 throughput 做容量规划和上线判据
  • KV 传输前量化到 FP8，字节数直接减半且 decode 侧可直接使用
  • P 用小 TP、D 用大 TP，这是分离最容易被忽略的红利
  • 按 SLO 归属分池监控：TTFT 报警只查 P 池，TPOT 只查 D 池
  • 过载时启用预测式早拒，保护还能达标的请求
  • KV 传输失败应显式报错重试，而非静默回退到 D 侧重算
  • 不要在 p90 prompt 短于 2K token 的场景上分离，传输开销纯亏
  • 不要在单机或不足 8 卡的部署上拆池，两边都会退化
  • 不要用普通以太网跑跨节点 KV 传输，先把网络升级好
  • 不要照抄别人的 1:3 配比，配比由输入输出长度比决定
  • 不要一上来就上动态 Planner，先用固定配比把监控做扎实
  • 不要为离线批处理任务上分离，那里 goodput 等于 throughput
  • 不要忘了 D 池要承接全量 KV，容量规划时别只算 decode 的增量

Q&A

Prefill 和 Decode 放在同一张卡上到底是怎么互相干扰的？
干扰是双向的。方向一：prefill 是大矩阵乘，会把 GPU 的计算单元占满，同批的 decode 请求即使只需要读点数据也得排队等这个前向步结束，用户端表现为输出流突然卡顿；prompt 越长这个停顿越明显。方向二：为了让 decode 的批足够大以摊薄权重读取成本，系统必须留大量显存给 KV Cache，留给 prefill 激活值的空间被压缩，长 prompt 只能切得更碎、跑得更久。更深一层的干扰是配置耦合：张量并行度、batch 上限、显存切分对两个阶段是同一套，而两者的最优解相反（prefill 想要小 TP，decode 想要大 TP），共置只能取折中值，两边都不最优。结果就是 TTFT 和 TPOT 形成跷跷板，压下一个另一个必然翘起来。
为什么 DistServe 强调 goodput 而不是 throughput？两者差在哪？
Throughput 统计的是每秒完成多少 token，不区分这些 token 属于按时交付的请求还是已经超时的请求。Goodput 只统计同时满足 TTFT 和 TPOT 两个约束的那部分请求。差别在过载时会变得极其显著：随着并发上升，throughput 曲线会一直爬升，因为 GPU 确实在生成 token；但 goodput 会在某个点见顶然后回落，因为越来越多的请求虽然完成了却已经违约——用户早就关掉页面了，这些 token 的业务价值为零。用 throughput 做容量规划会把系统推到"生产废品"的工作点上。Goodput 视角还导出了一个反直觉但正确的策略：过载时主动拒绝那些注定违约的请求，把算力留给还能达标的，整体有效交付量反而上升。
KV Cache 跨节点传输会不会成为新瓶颈？怎么判断值不值？
判断方法是把传输耗时和 prefill 耗时放在一起比。先算传输量：每 token 的 KV 字节数等于 2 × 层数 × KV头数 × 头维度 × 精度字节，Llama-3.1-70B 在 FP16 下约 320 KB/token，8K prompt 就是 2.5 GB。再除以互联带宽：NVLink（约 400 GB/s）需 6.4 ms，InfiniBand NDR（约 50 GB/s）需 51 ms，普通万兆以太网则要几百毫秒。而 8K prompt 的 prefill 在 H100 上本来就要 300~600 ms，前两者都只是零头。但若 prompt 只有 512 token，prefill 仅 15~30 ms，此时哪怕是 RDMA 的握手开销也和 prefill 同量级，分离就成了净亏损。所以经验阈值大致是 prompt 超过 2K token 才划算，并且要配合三个手段把成本进一步压低：传输与前几个 decode 步重叠、拓扑感知选网卡、传输前把 KV 量化到 FP8。
P 和 D 的数量配比怎么定？1:3 是通用答案吗？
1:3 只是通用对话场景（约 1K 输入 / 1K 输出）下的一个稳健默认值，绝不是通用答案。配比由输入输出长度比决定：输入越长、输出越短，prefill 的活越重，P 池要配得越多。长文档摘要（16K 输入 / 300 输出）往往需要 1:1 甚至 2:1；代码补全（8K 输入 / 128 输出）可能要 2:1 以上；而推理型模型（500 输入 / 4K+ 输出）则要反过来到 1:4 甚至 1:6。计算方式是把两个池子当流水线的两道工序，分别估算单个 worker 的处理速率，让两者匹配。实践建议是先按业务画像选一个固定配比压测验证，把监控做扎实，只有当流量画像本身随时段剧烈漂移时才引入动态 Planner——近期的对比基准显示，精心选定的固定配比在多种负载下已经足够稳健，动态调整的额外收益未必覆盖它带来的编排复杂度。
Chunked Prefill 和 PD 分离能同时用吗？该怎么选？
两者不互斥，但解决问题的层次不同。Chunked Prefill 是时间维度的隔离——在同一张卡上把长 prefill 切片，与 decode 交替执行，成本为零且现代引擎默认开启，所以它应该是所有部署的起点。PD 分离是空间维度的隔离——让两个阶段跑在不同的卡上，干扰从根上消失，代价是 KV 传输开销和编排复杂度。正确的演进顺序是：先把共置下的调度参数调到位（token 预算、并发上限）、把前缀缓存和 KV 量化开起来，如果这时 TTFT 和 TPOT 仍无法同时达标，再上 PD 分离。分离之后，prefill 池内部通常仍然保留分块能力来平滑自身负载，两者是叠加关系而非替代关系。跳过调优直接上分离的常见结果是复杂度上去了指标却没改善，因为真正的瓶颈可能只是一个从没动过的默认参数。
什么场景明确不该上 PD 分离？
四类场景要避开。第一是短 prompt 场景，p90 低于 1~2K token 时，KV 传输的固定开销（握手加首字节通常 5~20 ms）与 prefill 本身耗时同量级，分离纯亏。第二是小规模部署，单机或不足 8 卡时拆成两池，每池只剩一两张卡，批规模和 KV 容量双双腰斩，收益为负。第三是 SLO 宽松的离线批处理，没有延迟约束时 goodput 等于 throughput，分离带来的传输开销和跨池调度损失都是净成本。第四是缺乏高速互联的环境，只有普通以太网时跨节点传几个 GB 的 KV 需要数百毫秒，足以抵消全部收益。此外还有一个隐性条件：流量规模要能同时喂饱两个池子——P 池需要持续的 prompt 流打满算力，D 池需要足够并发摊薄权重读取，QPS 太低时拆开会导致两边都在低负载空转。
KV 传输失败时，让 decode 侧重算 prefill 是个好的降级策略吗？
不是，这是个看起来优雅实则危险的配置。decode 实例是按 decode 特性优化的：大张量并行度、大 batch、把绝大部分显存留给了 KV Cache 而只给激活值留了很少空间。让它去跑 prefill，等于让一台专为跑腿优化的机器去干重体力活，执行效率很低。更严重的是连锁反应：这个意外的 prefill 会占满该实例的计算单元，把同机器上所有正在 decode 的其他请求一起拖慢，尾延迟集体恶化——本来只是一个请求的传输失败，最后变成一批用户的体验受损。生产环境更稳妥的做法是让传输失败显式报错，由上层做重试或路由到另一对 P/D，把故障限制在单个请求范围内，同时故障也能被监控清晰捕捉到，而不是被静默的性能退化掩盖。
Mooncake 的"KVCache 为中心"和普通的 PD 分离有什么不同？
普通 PD 分离把 KV 当成 P 传给 D 的一次性中间产物，用完即弃。Mooncake 把 KV 提升为系统的一等公民：除了分离 P/D 集群，它还把 GPU 集群里长期闲置的 CPU、DRAM、SSD 和网卡组织成一个全局分布式的 KVCache 池，让 KV 既能在节点间传递，也能跨请求、跨会话被复用——本质是"用更多存储换更少计算"。这个设计对多轮对话和 Agent 场景收益极大，因为这类流量的前缀高度重复，命中缓存就意味着整段 prefill 被省掉。配套的两个机制也很关键：Transfer Engine 做拓扑感知的路径选择，预先生成拓扑矩阵、为每段内存标注首选网卡，避免数据穿越 UPI 或跨 PCIe Switch 导致带宽腰斩；调度层做基于预测的早期拒绝，重载时提前判断哪些请求注定违约并直接拒绝，把算力留给能达标的。公开数据是真实 trace 下有效请求容量提升 59%~498%，在 A800 和 H800 集群上分别多承接 115% 和 107% 的请求。
为什么分离后 P 用小 TP、D 用大 TP？
因为两个阶段从并行度中获得的收益来源不同。Prefill 一次处理整段 prompt，token 维度本身就提供了充足的并行度，GPU 的计算单元很容易被打满，不需要靠加大张量并行来榨算力；而 TP 越大，每层都要做的跨卡 all-reduce 通信占比越高，反而拖慢 prefill。所以 P 池倾向小 TP（比如 2）。Decode 每步只算一个 token，算力需求极小但必须把整个模型权重从 HBM 读一遍，是带宽受限的；加大 TP 后每张卡只需读 1/TP 的权重，聚合带宽随卡数线性增长，单步耗时直接下降。同时大 TP 意味着每卡分到的 KV 空间更多，能支撑更大的 decode 批和更高的前缀缓存命中率。所以 D 池倾向大 TP（比如 8）。共置架构下两个阶段被迫共用一个 TP 值，只能取折中，这个红利拿不到；分离后这个约束消失，这是分离最容易被忽略但收益很实在的一环。
上了 PD 分离之后，监控上应该重点看哪些指标？
按 SLO 归属分池看，这是分离架构在可观测性上的最大红利。P 池看三样：p95/p99 TTFT（是否守住承诺）、prefill 队列深度（是否在堆积）、前缀缓存命中率（骤降通常意味着系统提示被改或路由亲和性失效）。D 池看三样：p95/p99 TPOT 或 ITL、KV Cache 使用率（超过 90% 即将触发抢占重算）、decode 批的平均大小（太小说明 D 池配多了或 P 池供不上）。传输层看两样：单请求 KV 传输耗时的分布，以及传输失败率（失败会直接转化为尾延迟尖刺）。全局看两样：goodput（同时满足两个 SLO 的请求速率，这是最终判据）和 P/D 两池各自的负载比值——如果长期一边打满一边空闲，说明配比错了，该调的是配比而不是总卡数。排障时的好处是不会互相甩锅：TTFT 报警只查 P 池，TPOT 报警只查 D 池。
