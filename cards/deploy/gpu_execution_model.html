你写下的 kernel<<<grid, block>>> 只有两个参数，硬件却要把它翻译成"哪些 block 落到哪个 SM、每个 SM 同时驻留几个 block、每条指令的操作数从存储层次的哪一级取"。这三件事决定了同一份算法为什么能差一个数量级——而它们全都不出现在你的源码里。

一、从一次 Kernel 启动看全链路

一个能把 GPU 用好的工程师和一个只会调库的工程师，差别往往就在这一节：前者看到 <<<1024, 256>>> 时脑子里浮现的是 132 个 SM 上的驻留情况，后者看到的只是两个数字。DP14 · GPU 基础设施 已经把 grid / block / warp 这套词汇表建立起来了，这里要做的是把它们和硬件的调度行为一一对应，讲清"谁是调度单位、谁是执行单位、谁只是个编号"。

五个层级，各自的身份完全不同

kernel（在 GPU 上并行执行的一个函数）被启动时，运行时把它包装成一次 grid launch 提交给 GPU 的工作分发器。grid（一次 kernel 启动产生的全部线程块的集合）本身只是一个逻辑集合，不对应任何硬件实体。真正被调度的是 block（也叫 CTA，Cooperative Thread Array，一组能通过 shared memory 互相通信并做栅栏同步的线程）——工作分发器把 block 整体分配给某一个 SM（Streaming Multiprocessor，GPU 的基本计算单元），而且一旦分配就不再迁移，直到这个 block 的所有线程都退出。这条"不迁移"的性质是很多性能现象的根源：它意味着 block 所需的寄存器和 shared memory 必须在 SM 上被完整预留，也意味着一个执行特别慢的 block 会一直占着 SM 的资源槽位。

block 进入 SM 后被切成 warp（32 个连续编号的线程，GPU 的指令发射与执行单位）。warp 才是硬件真正"执行"的对象：一条指令被发射给一个 warp，32 个线程同步走同一条指令。thread 本身既不是调度单位也不是执行单位，它只是 warp 里的一条 lane 加上一份私有寄存器。Hopper 之后还多了一层可选的 thread block cluster（线程块簇，一组被保证同时调度到同一个 GPC 内的 block，可以互相访问对方的 shared memory），把"能协作的范围"从单个 SM 扩大到了一小群 SM。

把 SM 当成一间车间：block 是"一整个订单连人带料一起进车间，进了就不许换车间"，warp 是"车间里 32 人一组、同步做同一道工序的班组"，thread 只是班组里的工位号。你调 block size，本质上是在决定"每个订单要占多少料架和多少工位"——占太多，车间里就放不下第二个订单。

二、SM 内部：SIMT 与 warp 调度器

SM 不是一个大而无当的核心池，它内部被切成 4 个对称的处理分区（processing block / SM sub-partition）。每个分区有自己的 warp 调度器、指令分发单元、一份寄存器堆分片和 L0 指令缓存。理解这个切分是理解"为什么 block size 最好是 128 的倍数"的关键：block 里的 warp 会被轮流派到 4 个分区上，如果 warp 数不是 4 的倍数，就一定有分区空转。

warp 调度器做的唯一一件事：挑一个不在等待的 warp

每个 warp 调度器每个时钟周期做一次选择：在它管辖的驻留 warp 里，找出eligible warp（所有操作数就绪、没有在等内存或等同步的 warp），发射它的下一条指令。这就是 GPU 掩盖延迟的全部机制——CPU 靠乱序执行和分支预测，GPU 靠"手上有几十个 warp 可以随时换"。所以当一个 warp 因为访存卡住几百个周期时，只要还有别的 warp 可发，SM 的执行单元就不会闲着；反过来，如果驻留 warp 太少，调度器就会陷入"每个周期都无人可发"的状态，这时 SM 的利用率会崩，但纸面算力一点没变。

发射节拍也值得算一下。A100 每个分区有 16 个 FP32 CUDA Core，而一个 warp 是 32 个线程，所以一条 warp 级 FP32 乘加要占用该分区 2 个周期才发射完；H100 把每分区的 FP32 单元加到 32 个，同一条指令只要 1 个周期。这解释了为什么 H100 的非 Tensor FP32 峰值大约是 A100 的两倍多，而 SM 数只多了 22%。

SIMT 与分支发散

SIMT（Single Instruction, Multiple Thread，单指令多线程）是 GPU 的执行模型：一条指令发给整个 warp，32 条 lane 各自处理自己的数据。它和 CPU 的 SIMD 的区别在于每条 lane 有独立的寄存器和程序计数器视图，可以走不同分支——但代价是同一个周期里，一个 warp 只能执行一条路径。当 warp 里的线程走进 if/else 的两侧时，硬件会先执行一侧（另一侧的 lane 被掩码屏蔽），再执行另一侧，两段时间相加。Volta 之后引入的独立线程调度让发散后的重新收敛更灵活，也让 warp 内线程可以互相等待，但"发散会让有效算力打折"这条结论没有变。

warp 调度器不是在"优化"什么，它只是在每个周期问一句"谁现在能干活"。GPU 的延迟掩盖能力，等于你留给它多少个可以随时换手的 warp。驻留 warp 不足时，一个几百周期的访存延迟就会直接变成执行单元的几百周期空转。

CUDA Core 与 Tensor Core：不是快慢之分，是接口之分

这两类单元最常见的误解是"Tensor Core 就是更快的 CUDA Core"。它们真正的区别在指令的粒度：CUDA Core 执行的是标量指令（一条 FFMA 让每条 lane 做一次 a×b+c），Tensor Core 执行的是矩阵指令（一条 mma 让整个 warp 协作完成一次小矩阵乘加）。把两者的单指令产出算出来，差距一目了然：

Tensor Core · mma.sync.m16n8k16（SM80+）1 个 warp寄存器（经 ldmatrix 装载）2 × 16 × 8 × 16 = 4,09664×
Tensor Core · wgmma.mma_async.m64n256k16（SM90）1 个 warpgroup（4 warp / 128 线程）可直接从 shared memory 取2 × 64 × 256 × 16 = 524,288约 2048×（按每 warp 折算）

指令粒度的差别直接反映在峰值算力上：H100 SXM5 的 FP32（走 CUDA Core）约 67 TFLOPS，而 BF16 Tensor Core 稠密算力约 989 TFLOPS，差约 15 倍。所以工程上的分工非常清晰——能写成矩阵乘的都要想办法喂给 Tensor Core，剩下的逐元素运算、归约、索引、类型转换、softmax 的指数与除法留给 CUDA Core。这也是为什么大模型里 LayerNorm、GELU、RoPE 这类算子即使 FLOPs 极少也可能占掉可观的时间：它们根本用不上那 989 TFLOPS，只能在 CUDA Core 和显存带宽的双重限制下慢慢走，而这正是算子融合要解决的问题（见 DP27 · 算子融合与 Kernel 优化实战）。

CUDA Core 是"一次拧一颗螺丝的电动螺丝刀"，Tensor Core 是"一次压一整块面板的液压机"。液压机不是更快的螺丝刀——你没法用它拧螺丝。所以判断一个算子快不快，先问它的形状能不能被塞进液压机的模具里。

寄存器不是免费的：spill 的代价

初学者最容易忽略的是寄存器是有硬预算的共享资源。每个 SM 只有 65,536 个 32 位寄存器，单线程上限 255 个。编译器会尽力把变量放在寄存器里，但当 kernel 需要的寄存器超出预算时，多出来的变量会被放进 local memory（逻辑上线程私有、物理上位于 HBM 的存储空间）——这就是寄存器溢出（register spill）。名字里的"local"只描述作用域，不描述位置，所以一次 spill 访问的延迟和访问全局显存是同一个量级。

示例场景：一次被 spill 吃掉的"优化"。某团队手写了一个融合 kernel，把 RMSNorm、RoPE 和 QKV 切分合进一个 kernel，逻辑上少了两轮 HBM 往返，预期能快三成。上线后实测只快了不到 5%。用 nvcc --resource-usage 一看，每线程用了 168 个寄存器，编译器报告有 40 字节的 spill store 和 spill load；同时 Nsight Compute 显示 achieved occupancy 只有 12.5%，limiter 是寄存器。根因是把整段中间结果都留在了寄存器里，寄存器预算 65,536 ÷ (256 线程 × 168) 只够驻留 1 个 block，延迟完全无法掩盖，而 spill 又把省下的那两轮 HBM 往返以另一种形式还了回去。处理方式是把中间结果显式挪到 shared memory（用掉 24 KB，仍能驻留多个 block）并对 kernel 加 __launch_bounds__ 约束寄存器上限，寄存器降到 72 个/线程、spill 归零、occupancy 回到 50%，融合的收益才真正兑现。这个案例的数字是构造的，但"融合导致寄存器压力上升、反而变慢"是极常见的真实故障模式，排查顺序（先看 resource-usage 的 spill，再看 occupancy limiter）可以直接照用。
存储层次不是"缓存自动帮你搞定"的东西。硬件只自动管 L1 和 L2；寄存器由编译器管，shared memory 完全由你管，HBM 的搬运时机也由你管。写 kernel 的手艺，八成就是在决定"哪块数据什么时候搬到哪一级、在那里被用几次"。

四、Occupancy 到底是什么

Occupancy 是被误用最多的 GPU 指标，误用方式有两种：一种是把它当成"GPU 利用率"，另一种是把"提到 100%"当成优化目标。两个都错，而且错得方向相反。先把定义钉死——CUDA 官方文档的原话是：occupancy 是活跃 warp 数与 SM 支持的最大活跃 warp 数之比。它衡量的是"你给 warp 调度器留了多少可换手的余量"，不衡量算力有没有被用上。

Occupancy = 每 SM 活跃 warp 数 ÷ 每 SM 最大可驻留 warp 数（A100/H100 均为 64）

四个限制项，取最小值

每个 SM 能同时驻留几个 block，由四个约束同时决定，实际驻留数是四者的最小值。下面用 H100（CC 9.0）做一次完整推演，block size 取 256 线程（8 个 warp）：

限制项SM 侧预算本 kernel 的用量推出的驻留 block 数
每 SM 驻留线程上限2048 线程256 线程 / block2048 ÷ 256 = 8
每 SM 驻留 block 上限32 个—32
寄存器堆65,536 个 32 位寄存器64 个 / 线程 → 16,384 / block65,536 ÷ 16,384 = 4
Shared Memory228 KB / SM48 KB / block⌊228 ÷ 48⌋ = 4

取最小值得到 4 个 block，即 4 × 8 = 32 个活跃 warp，理论 occupancy = 32 / 64 = 50%。同一个 kernel，如果把每线程寄存器压到 32 个、shared memory 用量压到 24 KB，寄存器限制和 shared memory 限制都放宽到 8 个以上，此时线程数限制（2048 ÷ 256 = 8）成为新的短板，occupancy 升到 8 × 8 / 64 = 100%。这就是 --maxrregcount 和 __launch_bounds__ 起作用的原理：它们不是在加速指令，而是在换取驻留深度。代价是可能引入 spill，所以这是一笔需要实测的交易，不是稳赚的优化。

理论 occupancy 与实测 occupancy

理论 occupancy（theoretical occupancy）由启动配置和资源用量算出来，是上限；实测 occupancy（achieved occupancy）是运行时统计的平均值，Nsight Compute 里对应的指标是 sm__warps_active.avg.pct_of_peak_sustained_active。两者差距大通常意味着三类问题：grid 太小填不满所有 SM、block 之间执行时间不均导致尾部只剩少数 warp、或者 __syncthreads() 让大量 warp 长期处于等待态（等待中的 warp 仍是活跃 warp，但它不 eligible，所以 occupancy 高而算力照样闲着）。

为什么 occupancy 不等于 GPU 利用率

这是本节最重要的一段。工程上有三个名字很像、含义完全不同的量，混用它们会导致完全错误的优化决策：

指标准确含义取值 100% 时说明什么取值 100% 时不说明什么
nvidia-smi 的 utilization.gpu采样周期内"有至少一个 kernel 在执行"的时间占比GPU 没有空窗，一直有活在跑不说明用了几个 SM、算力用了几成——一个只占 1 个 SM 的 kernel 也能报 100%
Achieved Occupancy活跃 warp 数 / 最大可驻留 warp 数调度器手上随时有 64 个 warp 可换不说明这些 warp 在干有用的事，也不说明执行单元被用满
SM Throughput（Speed of Light）sm__throughput.avg.pct_of_peak_sustained_elapsed，最忙的 SM 执行资源相对峰值的占用某条流水线确实接近打满不说明打满的是你想打满的那条流水线

把这三者的区别落到一句可操作的话：nvidia-smi 的利用率只能用来判断"卡有没有闲着"，任何关于"算力用了几成"的结论都不能从它得出。它的官方定义就是时间占比——一个占着 SM 却在等 HBM 的访存 kernel，和一个把 Tensor Core 打到 95% 的 GEMM，在 nvidia-smi 里都是 100%。训练场景下换用 MFU 来量的做法在 DP14 · GPU 基础设施 里有完整算例，这里补的是 kernel 级别的对应关系。

高 occupancy 不是目标：GEMM 的反例

更反直觉的是：写得最好的 kernel 往往 occupancy 很低。CUTLASS 官方文档直接指出，GEMM 的累加器通常要占掉一个线程寄存器预算的一半以上，所以 GEMM kernel 的 occupancy 相对其他类型负载天生就低；Hopper 与 Blackwell 上的高性能 GEMM 甚至常常运行在个位数百分比的 occupancy。原因很清楚：Tensor Core 的算力密度太高，少数几个 warp 就足以把它喂饱，多留 warp 不但没收益，还会挤掉寄存器和 shared memory 这些真正稀缺的资源。NVIDIA 的 Nsight Compute 三级排查指南也把这条写成了明确的例外——"实测 occupancy 低于 60% 才值得关注，除非负载以 Tensor Core 为主，或者 compute / memory 的 Speed of Light 已经很高"。

示例场景：把 occupancy 提到 100% 之后变慢了。某团队为一个自研的分组量化 GEMV kernel 做优化，Nsight Compute 报告实测 occupancy 只有 18.75%，limiter 是 shared memory。团队按"提 occupancy"的思路把 tile 从 128×64 缩到 64×32，shared memory 用量从 40 KB 降到 12 KB，occupancy 顺利涨到 75%。结果 kernel 耗时反而增加了约 22%。复盘发现：tile 缩小后每个 block 的数据复用次数减半，DRAM Throughput 从 61% 涨到 89%，kernel 从"接近算力受限"退回了明确的访存受限——occupancy 涨了，但每个 warp 干的有用功变少了，总搬运量翻倍。正确的读法是：occupancy 是"是否暴露了足够并行度"的证据，不是分数。只有在 compute 和 memory 两个 Speed of Light 都偏低（说明确实是延迟暴露不足）时，提 occupancy 才是对症的。这里的数字是构造的示例，但"缩 tile 提 occupancy 反而变慢"是分块类 kernel 上非常典型的翻车路径。
Occupancy 像餐厅的"候补客人数量"：候补太少，一有客人上厨房就闲着；但候补排到爆棚，也不代表厨房出菜快——它只说明前厅不缺人。真正要看的是灶台在不在动（compute SOL）和后厨进货跟不跟得上（memory SOL）。

五、访存合并与 shared memory bank conflict

这一节讲的是本文里最能立刻换来性能的两件事，而且它们的共同特点是：算法一个字没改、FLOPs 一个都没多，仅仅因为访问顺序不同，性能就差一个数量级。理解它们需要的全部前提，就是第二节末尾提到的那三个 32。

全局访存合并：把 warp 的 32 个请求压成几个 sector

访存合并（coalescing）是硬件把一个 warp 内 32 个线程的访存请求合并成尽量少的内存事务的过程。CUDA C++ Best Practices Guide 对计算能力 6.0 及以上的表述非常干脆：一个 warp 的并发访问会被合并成"服务这 32 个线程所需的 32 字节事务个数"。这句话是可以直接拿来算账的：

  • 理想情况：32 个线程访问连续的 4 字节元素，覆盖 128 字节连续区间 = 4 个 32 字节 sector。每次请求 4 个 sector，取回来的每一个字节都被用到，带宽效率 100%。
  • 最坏情况：32 个线程访问的地址两两跨越 32 字节以上（典型是按列访问行主序矩阵），每个线程各自触发一个 sector。每次请求 32 个 sector，每个 32 字节 sector 里只有 4 字节被用到，87.5% 的带宽被浪费。

NVIDIA 技术博客给出过一组同一 kernel 的实测对照，两个版本发出的请求数完全相同（8,388,608 次），合并版消耗 33,554,432 个 sector，非合并版消耗 268,435,456 个 sector——sector/request 分别是 4 和 32，正好 8 倍。这也给了一个非常好用的判据：在 Nsight Compute 里看 sectors per request，理想值是 4（4 字节元素），越接近 32 越糟。

Shared memory 的 bank 结构与冲突

Shared memory 为了支持并发访问被切成 32 个 bank，每个 bank 宽 4 字节，连续的 32 位字依次落在连续的 bank 上。于是相隔 32 × 4 = 128 字节的地址映射到同一个 bank。Best Practices Guide 的规则是：一次访问如果落在 n 个不同 bank 上，就能并行完成，有效带宽是单 bank 的 n 倍；但如果一次请求里多个地址映射到同一个 bank，访问会被串行化，硬件把它拆成若干个无冲突的请求，有效带宽按拆分数成比例下降。唯一的例外是多个线程访问同一个地址——那会走广播/多播通路，不算冲突。

这就是矩阵转置类 kernel 的经典陷阱：把 tile 读进 shared memory 时按行（合并、无冲突），写出去时按列（为了让全局写也合并），而按列读 shared memory 恰好构成 32 路冲突。修法有三条，代价和适用面各不相同：

示例场景：一次纯访存顺序的重写。某团队为自研的 KV Cache 布局转换写了一个 kernel，把 [层, 头, 位置, 维度] 重排成推理引擎需要的分页布局。初版按目标布局的下标顺序循环，Nsight Compute 报告 sectors per request 为 28.4（理想 4）、DRAM Throughput 88%、SM Throughput 9%——典型的纯访存受限且访存效率极差。改法只做了两件事：让读侧沿最内维连续（把 threadIdx.x 绑到 head_dim 而不是 position），并把中间转置放进 shared memory、行长 padding 一个元素。结果 sectors per request 降到 4.3、bank conflict 归零，kernel 耗时从 3.1 ms 降到 0.42 ms，约 7.4 倍。算法一个字没改，FLOPs 一个都没多。这组数字是构造的，但"7~8 倍"这个量级和第一性原理算出来的 32/4 = 8 倍带宽浪费上限是吻合的，实际收益通常落在 4~8 倍之间。
把一次 warp 访存想成 32 个人同时去 32 个取件柜取快递。合并访存 = 32 个人的包裹刚好塞在相邻的 4 个格子里，一趟搬完；非合并 = 32 个包裹散在 32 个格子里，每趟只能拿一个格子还得整格搬走。bank conflict 则是 32 个人挤在同一个柜门前排队——柜子里东西不多，但门只有一个。

六、四类典型瓶颈的定位路径

前五节的量现在可以连起来了。一个 kernel 跑得慢，原因一定落在四类里，而区分它们靠的是两个 Speed of Light 指标的组合，不是靠猜。这里有一个必须先说清的分工：算术强度与屋顶线模型（判断"这个算子的理论天花板在哪"）在 DP19 · GPU 算力瓶颈与优化 里已有完整推导和拐点数据，本文直接把它当已知结论用。本节讲的是另一半——拿到一个具体 kernel 之后，怎么用硬件指标把它归类到四个抽屉里，以及每个抽屉对应本文哪一节的机制。

一个容易忽略的第五类：算力和带宽都没打满，因为活儿没铺开

严格说这不算瓶颈，而是启动配置的问题，但它在生产中出现频率很高，值得单列。第一节算过 1024 个 block 落在 132 个 SM 上的"零点七五波"——当 block 总数不是 SM 数的整数倍时，最后一波只有部分 SM 在干活，其余空转。block 数远小于 SM 数时更极端：一个只启动了 8 个 block 的 kernel，在 H100 上最多用到 8/132 ≈ 6% 的 SM，而 nvidia-smi 依然报告 100% 利用率。这类问题在小 batch 推理、逐层调用的小算子上尤其常见，修法通常不在 kernel 内部，而在把多个小 kernel 合成一个（DP27 · 算子融合与 Kernel 优化实战）或用 CUDA Graph 消掉 launch 开销。GEMM 场景下这个现象有专门的名字叫 wave quantization，处理办法见 DP26 · GEMM 与 Tiling 分块优化。

  • block size 取 128 的倍数，让 4 个处理分区都分到整数个 warp
  • 先用两个 Speed of Light 指标定性，再决定往哪个方向优化
  • 用 nvcc --resource-usage 检查寄存器用量与 spill，这是最便宜的一次体检
  • 看 sectors per request 判断访存效率，4 是理想值
  • shared memory 的二维数组习惯性 padding 一个元素，或直接用成熟库的 swizzle 布局
  • 判断"算力用了几成"一律用 Speed of Light 或 MFU，不用 nvidia-smi
  • 确认 block 总数至少是 SM 数的若干倍，避免尾波浪费
  • 不要把 nvidia-smi 的 100% 利用率当成算力被用满
  • 不要把 occupancy 提到 100% 当作优化目标——高性能 GEMM 常跑在个位数
  • 不要为了提 occupancy 而缩小 tile，那通常是用复用度换驻留深度的亏本交易
  • 不要在没看 limiter 的情况下加 --maxrregcount，可能换来 spill
  • 不要让 warp 按列访问行主序数据，那是 8 倍带宽浪费的标准写法
  • 不要假设 shared memory 一定快——32 路 bank conflict 会让它慢过 L2
  • 不要用一堆小 kernel 表达逻辑，SM 铺不满时纸面算力完全无意义
四类瓶颈其实对应四个不同的问句：访存受限问"数据够不够快地送来"，算力受限问"计算单元还有没有余量"，延迟受限问"有没有足够多的活可以随时切换"，占用率受限问"是不是资源预算把并行度掐死了"。搞错问句，后面所有努力都在答错题。

Q&A

block、warp、thread 三者到底谁是调度单位？

三者身份完全不同。block（CTA）是资源分配与驻留单位：工作分发器把一个 block 整体分配给某一个 SM，分配之后不会迁移到别的 SM，它需要的寄存器和 shared memory 会在这个 SM 上被整块预留，直到 block 内所有线程退出才释放。warp 是指令发射与执行单位：block 进入 SM 后被切成 32 线程一组的 warp，一条指令发给一个 warp，32 条 lane 同步执行同一条指令；SM 内的 4 个 warp 调度器每周期各自挑一个操作数就绪的 warp 发射指令。thread 既不是调度单位也不是执行单位，它只是 warp 里的一条 lane 加一份私有寄存器。这个区分有实际后果：因为 block 不迁移，所以一个 block 的资源需求过大会直接压低 SM 的驻留数；因为 warp 是执行单位，所以 block size 应该是 32 的倍数（最好是 128 的倍数，让 4 个处理分区都分到整数个 warp）。

为什么 warp 宽度是 32 而不是 8 或 128？

32 是三个方向压力的折中点。往窄了走，取指、译码和调度的固定开销摊不薄，控制逻辑会占掉更多芯片面积，而且需要更多调度器才能喂饱同样多的执行单元，访存请求也会碎片化。往宽了走，一次分支发散需要串行执行的路径更多、惩罚成倍放大，寄存器堆的读写端口压力剧增，而且一个 warp 的访存地址跨度太大，很难落进少量缓存行。选 32 还额外得到一个很整齐的对齐关系：32 个线程各访问 4 字节正好是 128 字节，等于 4 个 32 字节 sector（一次完美合并访存）；shared memory 也正好是 32 个 bank。warp 宽度、bank 数、理想 sector 数这三者咬合在同一个数上，不是巧合，而是硬件设计自洽的结果。

Shared memory、L1 和 L2 有什么本质区别？

区别在"谁来管"和"作用域多大"，不只是快慢。shared memory 和 L1 数据缓存在物理上是同一块 SRAM（A100 每 SM 共 192 KB，H100 共 256 KB），由 carveout 配置切分比例——H100 支持把 shared 部分配成 0/8/16/32/64/100/132/164/196/228 KB 中的一档。但两者的语义完全不同：shared memory 由程序员显式分配和读写，作用域是一个 block（Hopper 的 cluster 可以跨 SM 访问），数据什么时候进来什么时候出去完全由你决定，所以它是 tiling 的工作台；L1 由硬件自动管理，你只能影响它而不能指挥它。L2 是全卡共享的最后一级片上缓存（A100 40 MB，H100 50 MB），也由硬件管理，但 Ampere 之后开放了驻留策略控制。延迟上大致是 shared 约 23 周期、L1 命中约 33 周期、L2 约 200 周期（均为 A100 微基准值），差距接近一个数量级。实践含义是：跨 block 的数据复用只能靠 L2 兜底，而 block 内的复用必须靠你自己搬进 shared memory。

occupancy 是什么？为什么把它提到 100% 不一定更快？

occupancy 的官方定义是每个 SM 的活跃 warp 数除以该 SM 支持的最大活跃 warp 数（A100 和 H100 都是 64）。它衡量的是你给 warp 调度器留了多少可以随时换手的余量，也就是掩盖访存延迟的能力，而不是算力有没有被用上。实际驻留数由四个约束取最小值决定：每 SM 线程上限（2048）、block 上限（32）、寄存器堆（65,536 个 32 位寄存器）、shared memory 容量。提高 occupancy 通常要付代价：压寄存器可能引入 spill（溢出到物理在 HBM 上的 local memory），缩小 tile 会降低数据复用度、把 kernel 从算力受限推回访存受限。更关键的是，高性能 kernel 常常本就不需要高 occupancy——CUTLASS 文档指出 GEMM 的累加器要占掉线程寄存器预算的一半以上，所以 GEMM occupancy 天生偏低，Hopper 和 Blackwell 上的高性能 GEMM 甚至运行在个位数百分比，因为少数几个 warp 就足以喂饱 Tensor Core。正确的用法是把 occupancy 当作"是否暴露了足够并行度"的证据：只有当 compute 和 memory 两个 Speed of Light 都偏低时，提 occupancy 才是对症的。

nvidia-smi 显示 GPU 利用率 100%，是不是说明算力已经跑满了？

不是，这是最常见也最昂贵的误读。nvidia-smi 的 utilization.gpu 定义是"采样周期内有至少一个 kernel 在 GPU 上执行的时间占比"，它只回答"卡有没有闲着"这一个问题。它不区分用了几个 SM——一个只启动 8 个 block 的 kernel 在 132 个 SM 的 H100 上最多用到约 6% 的 SM，依然会报 100%；它也不区分执行单元在干什么——一个占着 SM 却在等 HBM 返回数据的访存 kernel，和一个把 Tensor Core 打到 95% 的 GEMM，读数完全一样。要判断算力用了几成，kernel 级别应该看 Nsight Compute 的 Speed of Light 指标（sm__throughput 与 gpu__compute_memory_throughput 的 pct_of_peak），训练全局应该看 MFU（实际模型 FLOPs 除以峰值 FLOPs 乘时间）。用 nvidia-smi 的利用率做容量规划或判断优化是否见效，方向从一开始就是错的。

什么是访存合并？不合并到底损失多少？

访存合并是硬件把一个 warp 内 32 个线程的访存请求合并成尽量少的内存事务的过程。CUDA C++ Best Practices Guide 对计算能力 6.0 以上的规则是：一个 warp 的并发访问会被合并成"服务全部 32 个线程所需的 32 字节事务个数"。理想情况下 32 个线程访问连续的 4 字节元素，覆盖 128 字节连续区间，正好是 4 个 32 字节 sector，取回的每个字节都被用到；最坏情况是 32 个线程的地址两两跨越超过 32 字节（典型写法就是按列访问行主序矩阵），每个线程各触发一个 sector，一次请求消耗 32 个 sector，而每个 sector 里只有 4 字节有用，87.5% 的带宽被白白搬运掉，效率相差 8 倍。NVIDIA 技术博客给过一组实测对照：同一 kernel 两个版本发出的请求数都是 8,388,608 次，合并版消耗 33,554,432 个 sector，非合并版消耗 268,435,456 个，sector/request 分别是 4 和 32。所以 Nsight Compute 里的 sectors per request 是判断访存效率最直接的指标，4 是理想值，越接近 32 越糟。

shared memory bank conflict 是怎么产生的，怎么修？

shared memory 被切成 32 个 bank，每个 bank 宽 4 字节，连续的 32 位字依次映射到连续的 bank，因此相隔 128 字节（32 × 4）的地址会落在同一个 bank 上。一次访问如果落在 n 个不同 bank 上就能并行完成；但如果多个地址映射到同一个 bank，硬件会把请求拆成若干个无冲突的请求串行执行，有效带宽按拆分数成比例下降（多个线程访问完全相同的地址是例外，会走广播通路）。最经典的触发方式是对行长为 32 个 float 的二维数组按列访问：每行正好 128 字节，于是 32 个线程全部落在 bank 0 上，构成 32 路冲突，有效带宽掉到 1/32。修法有三条：一是 padding，把行长从 32 改成 33 个元素，让每个线程的偏移变成 132k、bank 索引变成 (33k mod 32) = k，重新散开，代价是多用约 3% 的 shared memory；二是 swizzle，用异或之类的位运算打散列到 bank 的映射，不额外占内存但索引推导容易写错，这是 CUTLASS/CuTe 的标准做法；三是换指令绕过，用 ldmatrix 直接装载 Tensor Core 需要的 fragment，或在 Hopper 上用 TMA 配 wgmma 从 shared memory 直取，代价是必须遵守硬件规定的布局与 swizzle 模式。

拿到一个跑得慢的 kernel，应该按什么顺序排查？

先定性，再动手，顺序不能倒。第一步用 Nsight Compute 同时取两个 Speed of Light 指标：sm__throughput.avg.pct_of_peak_sustained_elapsed（计算侧）和 gpu__compute_memory_throughput.avg.pct_of_peak_sustained_elapsed（内存侧）。NVIDIA 的排查指南给的阈值是低于约 60% 算低、高于约 80% 算高。内存侧高而计算侧低是访存受限，接着查 sectors per request 和 bank conflict，修访问模式或做算子融合；计算侧高而内存侧低是算力受限，接着确认饱和的是哪条流水线（Tensor Core 还是 FP32），方向是降精度和对齐形状让 Tensor Core 吃满；两者都低说明延迟暴露不足或者被资源掐住了并行度，这时再去看实测 occupancy 和它的 limiter——occupancy 低且 limiter 明确（寄存器或 shared memory）属于占用率受限，occupancy 不低但依然慢就是延迟受限，要查依赖链和同步；两者都高则说明已经贴着这个算法在这块硬件上的极限，只能换算法或换精度。另外要单独确认一件事：block 总数是否远小于 SM 数或不是 SM 数的整数倍，这种"活儿没铺开"的情况两个 SOL 也会都低，但修法在启动配置和 kernel 合并上，不在 kernel 内部。

这张卡和 DP19、DP14 的分工是什么？

三张卡处在不同的抽象层，配合使用而不是互相替代。DP14 · GPU 基础设施 建立词汇表并给出选卡与集群视角：主流卡型参数对比、NVLink 与 InfiniBand 互联、集群拓扑与存储、云 GPU 计费，以及 grid/block/warp 的层次图和 CUDA 编程入门。DP19 · GPU 算力瓶颈与优化 回答"这个算子的理论天花板在哪"：算术强度的定义、屋顶线模型与各代卡的拐点数值、访存墙的由来，以及从精度、算子、通信三层榨算力的清单。本卡回答的是中间那一层——硬件到底怎么调度你写的 kernel、数据在存储层次里怎么流动、以及某些写法为什么天然就慢：调度单位与执行单位的区别、SM 内部的处理分区与 warp 调度器、存储层次的定量阶梯、occupancy 的准确定义与它和利用率的差别、访存合并与 bank conflict 的机制。实践上的用法是：用 DP19 判断这个算子值不值得优化、上限在哪，用本卡判断这次为什么没跑到上限，用 DP26 和 DP27 落到具体手段上。
