DP03 · 显存 OOM 与高并发故障处置

症状判别 / 六步应急流程 / 三把止损闸刀 / 四类场景对照表 / 参数速查 / 水位线与告警阈值 / 应急预案 Checklist

推理服务半夜炸了，你缺的往往不是"显存怎么算"这类知识——那个你早就会了。你缺的是一套在告警响起后的十分钟里，不需要思考也能照着做的动作序列：先拉闸止血，再看监控验伤，最后才谈根治。这张卡讲的就是那套动作序列，以及每个动作会付出什么代价。

这张卡刻意不重讲机制。显存怎么分账看 DP02 显存估算与硬件配置，KV Cache 与分页管理看 DP08 与 DP09，调度器与批处理旋钮看 DP11，压测怎么找拐点看 DP16。这里只讲一件事：**线上已经出事了，接下来的每一分钟该做什么。**

一、故障现场：五类症状分别指向什么

推理服务出问题时，用户侧的反馈几乎总是同一句"变慢了"或"报错了"，但底下的根因可能完全不同。把症状拆细，是整个处置流程里唯一能大幅缩短时间的环节——因为一旦症状认错，后面五步全都做在错误的方向上。

先看清请求在哪一段被卡住

一个请求从进网关到吐完最后一个 token，中间有四个可能积压的位置。观测点没铺到位，你就只能盯着 nvidia-smi 猜。

最反直觉的一条：显存被占满 90% 以上，在 vLLM 里是正常状态，不是故障。引擎启动时就按 gpu_memory_utilization 把 KV 池一次性预分配好了，nvidia-smi 从第一秒起就是满的。所以判断 KV 是否吃紧，要看 vllm:gpu_cache_usage_perc（池内用了多少），而不是看显卡占用率。盯错指标是这类故障里最常见的第一步错误。

TTFT 变长不等于 Prefill 变慢

TTFT（Time To First Token，首字延迟）是个复合指标，它同时包含了排队等待和 Prefill 计算两段。服务过载时，真正膨胀的几乎总是前者：请求在 waiting 队列里躺了两秒，Prefill 本身只花了 80 毫秒，但用户测到的 TTFT 是 2.08 秒。这个区分之所以关键，是因为两者的处置方向完全相反——排队问题要在准入侧解决（限流、缩短上下文、扩容），Prefill 变慢才需要动 chunked prefill 之类的计算侧参数。压测口径下 TTFT 与 TPOT 各自意味着什么，DP16 里拆得更细。

二、六步处置流程：先止血，再验伤

线上事故处置最容易犯的错误，是一上来就想弄明白"到底为什么炸"。这个冲动在工程上是对的，在事故现场是错的——因为诊断需要时间，而故障期间每一秒都在产生用户损失。成熟的处置流程把止损和定位严格分成两个阶段，并且规定止损优先。

为什么必须先止损

把 MTTR（平均恢复时间）拆开看就清楚了：MTTR = 发现耗时 + 定位耗时 + 修复耗时。定位耗时是三者里方差最大的一项——运气好五分钟，运气差两小时。如果坚持"先搞清楚再动手"，用户受损时长就等于这个高方差的量。而止损动作是低方差的：降 QPS 这个操作永远在一分钟内生效，无论根因是什么。把止损提到定位前面，等于把用户受损时长从"取决于诊断难度"变成"取决于操作速度"。

示例场景：某内部代码助手服务跑在单张 A100 80G 上，某天上午十点推广邮件群发后并发从 8 涨到 40，服务开始大面积超时。值班同学第一反应是登机器排查，花了 25 分钟才发现是长上下文请求把 KV 池挤爆。复盘后团队把流程改成"告警响起两分钟内先把网关并发上限压到 12"，下一次同类事件的用户受损时长从 25 分钟降到 3 分钟——根因排查还是花了 20 多分钟，但那 20 分钟里服务是可用的。
止损和修复是两件事，混在一起做会两件都做不好。止损的标准是"用户不再报错"，可以很粗暴，可以牺牲吞吐，可以临时拒掉一部分流量；修复的标准是"同样的输入不再触发问题"，必须讲道理、可验证。事故现场只谈第一个标准。

Step 3 该看什么日志

引擎日志里最有价值的不是那行 CUDA out of memory，而是它前面几十行的调度记录。vLLM 在 KV 吃紧时会打印抢占相关的告警，明确告诉你是因为空间不够而把某些序列踢回队列重算。看到这类记录，说明问题在 KV 容量而非模型加载；反之，如果崩溃发生在启动阶段或第一批请求上，那就是权重加上激活根本装不下，跟并发无关。

三、三把止损闸刀与它们的代价

止损阶段可用的手段只有三类，按对用户的伤害从小到大排列。选哪一把不取决于根因（那时候还不知道根因），而取决于你能在多少秒内把它执行完。

闸刀怎么执行生效速度代价什么时候别用
降并发网关侧把最大并发或 QPS 上限调低，多余请求排队或快速失败秒级，无需重启部分用户排队变长或收到 429几乎总是先用这个
压生成长度网关强制覆盖 max_tokens，比如压到 512秒级，只影响新请求长回答被截断，体验受损但服务可用业务本身就是长文生成时慎用
隔离重启把异常实例摘出负载均衡，重启后再放回分钟级冷启动期间容量下降，且丢掉全部前缀缓存只剩一个实例时（会造成全站中断）
三把闸刀的共同点是都不需要改引擎启动参数。这不是巧合——改启动参数意味着重启，重启意味着几十秒到几分钟的容量真空，在事故现场这个代价常常比故障本身还大。所以止损阶段的原则是：能在网关解决的，绝不动推理服务。

为什么重启是最后一招

重启一个推理实例的成本远高于重启一个普通 Web 服务。权重要重新从磁盘或对象存储加载到显存，几十 GB 的模型这一步就要几十秒；接着引擎要做显存探测和 KV 池预分配；如果没关 CUDA Graph，还要走一遍图捕获（capture）预热。这几步加起来，一个中等规模模型的冷启动通常在一到三分钟量级。更隐蔽的代价是前缀缓存（prefix cache）——那些被多个请求共享的系统提示词 KV 块全部清零，重启后的头几分钟里，本来能命中缓存的请求都要重新 Prefill，实际吞吐比稳态还低。所以重启只在两种情况下值得：怀疑进程内状态已经损坏，或者必须改启动参数才能恢复。

示例场景：某问答服务在事故中连续重启了四次实例，每次重启后两分钟内又被流量打挂，形成"重启—打挂—重启"的循环，累计中断 18 分钟。事后发现如果第一次就把网关并发从 64 压到 16，服务在 30 秒内就能稳住。教训是：重启解决的是进程状态问题，解决不了流量与容量不匹配的问题——后者不先按住，重启多少次都会再炸一次。

拉闸之后立刻要做的一件事

闸拉下去、错误率回落之后，不要马上开始排查，先把当前的现场快照存下来：监控面板截图（覆盖故障前 30 分钟到恢复后 5 分钟）、引擎日志片段、当时的启动参数、当时的流量结构（请求速率、上下文长度分布）。原因很实际——止损动作本身会改变现场，降了并发之后所有指标都会回到正常区间，等你半小时后回头排查时，最有诊断价值的那段曲线可能已经被监控系统按低精度归档了。

四、四类场景对照：从现象查到根因

把线上遇到的显存与并发问题归拢，基本跑不出四类。这一节按"判别特征 → 常见根因 → 止损 → 根治"的顺序给出对照，事故中可以直接当查询表用。

场景一：启动就 OOM，还没接流量就崩

这一类跟并发完全无关，纯粹是账算错了。判别特征很干脆：服务起不来，或者刚接第一批请求就崩，日志里的 OOM 发生在模型加载或引擎初始化阶段。

常见根因怎么确认处置
权重精度选错，FP16 加载了本该量化的模型算一遍参数量 × 精度字节，和卡的显存比换 AWQ/GPTQ 量化权重，或加卡做张量并行
max_model_len 设得比实际需要大得多看引擎启动日志里报的 KV 池可容纳 token 数按业务真实的上下文分布调小
gpu_memory_utilization 设太高，没给运行时留余量值是否 > 0.95回调到 0.85~0.90
卡上还有别的进程（上一次没退干净、其他容器共卡）nvidia-smi 看进程列表清理残留进程，或用 MIG / 独占调度隔离

显存到底该怎么分账、每一项占多少，DP02 有完整的公式和卡型对照表，这里不重复。

场景二：并发升高后 OOM 或大面积超时

这是最典型的一类。服务平时好好的，流量一涨就出问题。判别特征是故障与流量曲线高度相关，且 vllm:gpu_cache_usage_perc 在故障前贴近 1.0，num_requests_waiting 和 num_preemptions_total 同步飙升。

常见根因指标特征止损根治
并发数超过 KV 池能承载的序列数KV 使用率贴顶 + 等待队列非空网关降并发调 max_num_seqs，或扩容实例
少数超长上下文请求吃掉大半个池子KV 使用率跳变而非缓涨网关按 token 数拒绝超长请求设 max_model_len 上限 + 长请求走独立实例
生成长度失控（模型不停不下来）单请求占用时间远超均值强制覆盖 max_tokens补停止条件与超时中断
抢占风暴：请求被踢回队列重算，加剧拥塞num_preemptions_total 快速增长降并发打破循环见 DP11 的调度调参
场景二里最容易被忽略的是"少数超长请求"这一条。假设 KV 池能装 40 个 2K 上下文的请求，那么只需要 5 个 16K 的请求进来，池子就满了——从池子的角度看，占用量是按 token 数算的，不是按请求数算的。这解释了一个常见现象：QPS 明明没怎么涨，服务却突然扛不住了，因为涨的是单请求的上下文长度，不是请求数。

场景三：不 OOM，但就是慢

服务稳定运行，没有报错，但 P95 延迟明显劣化。这类问题的处置反而最需要耐心，因为它不紧急，容易被拖着不解决，最后演变成场景二。

现象区分方法指向
TTFT 涨、TPOT 正常看等待队列长度准入侧排队，需要限流或扩容
TPOT 涨、TTFT 正常看批次内请求数批次过大，单请求分到的算力变少
两者都涨且抖动大看抢占计数抢占重算在浪费算力
两者都涨但很平稳看 GPU 利用率与显存带宽可能真的到了硬件上限，需要扩容或换卡

场景四：显存或内存逐渐上涨

这一类最容易被误诊，因为"缓慢上涨"这个形态天然让人联想到内存泄漏。但在 vLLM 这类采用分页 KV 管理的引擎里，KV Cache 本身几乎不可能"泄漏"——它是池化的，请求结束时块就归还池子，池子的总大小在启动时就固定了。所以看到显存缓涨，要分两种情况处理。

涨的是什么怎么看常见原因处置
GPU 显存（池外部分）DCGM_FI_DEV_FB_USED 涨但 KV 使用率平稳某些自定义算子或多模态预处理没释放中间张量定位算子，或定期滚动重启兜底
CPU 内存 RSS容器内存曲线涨，显存不涨请求对象堆积、日志缓冲、tokenizer 缓存、Prometheus 标签基数爆炸查标签基数与对象引用，见 ST12
看起来涨其实没涨KV 使用率随流量波动，显存总量不变把 KV 池水位当成了泄漏不处置，改告警口径
判断是不是真泄漏有个便宜的办法：把流量停掉五分钟再看。真泄漏不会因为没有请求就回落，而池水位一定会掉回基线。这个动作花的时间比读代码找引用短得多，值得在排查早期就做一次。

五、参数速查：七个旋钮怎么调

参数口径以 vLLM 为准，数据截止 2026-09 · 不同引擎（SGLang / TGI）的参数名不同但作用类似；具体默认值随版本变动，落地前核对当前版本文档。

下面这张表按"出事时最先该动"的顺序排列。每个参数都给了作用、调整方向和代价——代价那一栏是重点，因为大多数调参失误不是调错方向，而是没意识到副作用。

参数作用OOM 时怎么调代价 / 常见误用
gpu_memory_utilization引擎可预分配的显存比例，直接决定 KV 池大小每次下调 5~10 个百分点，常见安全起点 0.85~0.90调低即缩小 KV 池，并发能力同步下降；设到 0.98 会挤掉运行时余量，反而更易崩
max_model_len单请求最大上下文长度，决定单序列 KV 上限按业务真实分布调小，而不是照抄模型标称长度调小会直接拒掉长请求；照抄模型的 128K 标称值是启动期 OOM 的头号原因
max_num_seqs同时在批次里运行的最大序列数调小以降低并发内存压力调太小会浪费 GPU 算力，吞吐塌方；它是并发上限不是队列上限，超出的请求会排队而非报错
max_num_batched_tokens单次迭代最多处理的 token 数，主要约束 Prefill调小可缓解长 prompt 造成的显存尖峰调太小会让长 prompt 被切成很多块，TTFT 变长；与 chunked prefill 配合使用
swap_space预留多少 CPU 内存用于把 KV 块换出显存适当调大（GB 为单位），给抢占时的换出留空间是 CPU 内存不是磁盘 swap；换入换出走 PCIe，命中时延迟明显抖动；设太大会挤爆容器内存限额
kv_cache_dtypeKV Cache 的存储精度，可设为 FP8转 FP8 可近似把 KV 显存占用减半需要硬件支持（Hopper 及以后较稳妥），老卡上开可能反而变慢或精度受损
tensor_parallel_size把模型权重切到几张卡上加卡切分，让单卡权重占用下降、KV 池变大引入卡间通信开销，没有 NVLink 时收益会被通信吃掉；一般设为单机 GPU 数

三个二线旋钮

参数什么时候才用为什么不该常用
cpu_offload_gb显存实在装不下权重，且能接受大幅降速权重走 PCIe 反复搬运，吞吐损失通常是数量级的，只适合离线或调试
block_size极端碎片场景下想提高块粒度利用率调小省内存但增加调度开销，默认值在绝大多数场景已经够好
enforce_eager排查阶段想拿到干净的错误栈，或显存紧到连图捕获都做不了关掉 CUDA Graph 会牺牲吞吐，排查完必须改回去
这些旋钮里只有一个是"免费"的：kv_cache_dtype 转 FP8 在支持的硬件上几乎是纯赚（显存减半、精度损失通常可接受）。其余每一个都在同一条守恒线上——你省下来的显存，一定是从并发能力、上下文长度或吞吐里扣的。所以调参前先想清楚要牺牲哪一项，而不是挨个试到不报错为止。

调参顺序

事故后要改启动参数时，按下面的顺序试，代价从低到高：

调参决策顺序（每一步先问"能不能不改"） ① 业务侧能不能收窄需求？ └─ 上下文真的需要 32K 吗 → 调小 max_model_len（代价最低） │ 不能 ▼ ② 精度侧还有空间吗？ └─ KV 能不能走 FP8 → kv_cache_dtype=fp8（硬件支持时几乎白赚） └─ 权重能不能量化 → AWQ / GPTQ │ 不能 ▼ ③ 并发侧退一步？ └─ 降 max_num_seqs / gpu_memory_utilization（牺牲吞吐换稳定） │ 还不够 ▼ ④ 加硬件 └─ 张量并行加卡 → 加实例 → 换更大显存的卡（代价最高但最彻底）

关于 PagedAttention 的一条版本提醒

vLLM v0.25.0（2026 年 7 月 11 日发布）的 release notes 里明确写了两件事：Model Runner V2 成为所有 dense 模型的默认执行路径，以及 PagedAttention 被移除（PR #47361）。这条容易引起误解，需要说清楚：被删掉的是那段独立的旧实现代码，不是分页管理 KV 这个技术本身。块式 KV 分页现在已经融进 FlashAttention、FlashInfer 这些现代 attention 后端和 V1 引擎里，是所有部署都在走的标准路径。所以排查显存问题时，"KV 按块分页管理"这个心智模型依然成立；但如果你在读较老的资料或按老版本参数配置，遇到与 attention 后端相关的报错，先确认自己的版本落在哪一侧。原理层面的分页机制拆解见 DP09。

六、预防：水位线、告警与预案

做完前五节，你已经能把事故处理干净。这一节讲的是怎么让下一次的告警在故障发生之前响起——核心是把"KV 池水位"当成容量管理的第一指标，像看数据库连接池一样看它。

水位线分档

KV 使用率状态含义该做什么
< 0.70健康有充足余量应对流量尖峰无需动作；长期低于 0.4 说明资源浪费，可考虑缩容或提高并发上限
0.70 ~ 0.85观察正常繁忙区间确认扩容预案就绪
0.85 ~ 0.95预警已接近调度器开始排队的边界触发扩容或收紧准入
> 0.95危险抢占与超时随时可能出现立即限流；持续 5 分钟以上应告警到人

四条最低限度的告警

告警触发条件为什么需要它
KV 水位持续高vllm:gpu_cache_usage_perc > 0.95 持续 5 分钟这是所有并发类故障的共同前兆，比错误率早几分钟
等待队列非空vllm:num_requests_waiting > 0 持续 2 分钟说明容量已经不够，用户正在排队但还没报错
抢占在增长vllm:num_preemptions_total 增速非零抢占意味着算力在做重复计算，是拥塞的明确信号
尾延迟劣化TTFT P95 超过 SLA 阈值直接对齐用户体验，兜住前三条漏掉的情况
示例场景：某团队在补上"KV 水位 > 0.95 持续 5 分钟"这条告警之前，全年四次推理服务事故都是由用户投诉先发现的，平均从故障开始到值班介入间隔 11 分钟。补上告警后的两次容量不足事件，都在水位预警阶段就完成了扩容，没有升级成用户可见故障。这条告警的价值不在于它多精确，而在于它比错误率提前——错误率涨起来的时候，用户已经受损了。

Do / Don't

  • 在网关层就限制上下文长度和 max_tokens，别把治理责任交给推理引擎
  • 把 gpu_memory_utilization 留 10~15 个百分点余量，给运行时和碎片留空间
  • 长上下文请求路由到独立实例，避免它们和短请求抢同一个 KV 池
  • 按 DP16 的阶梯压测定期跑，把拐点位置写进容量文档
  • 告警配在 KV 水位和等待队列上，它们比错误率早
  • 每次改启动参数都记录变更时间，事故排查时这是最有用的线索
  • 别把 gpu_memory_utilization 拉到 0.98 去榨最后一点显存
  • 别照抄模型标称的最大上下文长度当 max_model_len
  • 别用重启当常规手段，它掩盖问题还清空前缀缓存
  • 别把 nvidia-smi 的显存占用率当成 KV 水位来看
  • 别在没有独立压测环境的情况下直接在生产调参
  • 别只配错误率告警——它响的时候用户已经在受损了
  • 网关限流开关在哪里、谁有权限改，值班同学是否演练过
  • 强制覆盖 max_tokens 的配置项是否存在且可热更新
  • 实例摘流与恢复的操作步骤是否成文，冷启动耗时是否实测过
  • 备用容量在哪里，扩容需要多久，是否有预热好的实例
  • 降级路径是什么：切小模型、返回缓存答案，还是直接返回友好提示
  • 监控面板是否覆盖四个积压点，故障期间的高精度数据保留多久
  • 事故现场快照的采集清单是否明确（监控截图、日志、启动参数、流量结构）
  • 复盘模板是否包含"这次的告警为什么没有提前响"这一栏
容量规划的本质是承认一件事：你不可能让服务扛住任意流量，只能让它在超载时以可预期的方式退化。可预期的退化是有人排队、有人收到 429、长请求被拒；不可预期的退化是进程崩溃、全量请求超时。这两者之间的差别，几乎全部来自准入侧有没有闸门。

Q&A

nvidia-smi 显示显存占用 95%，是不是快 OOM 了？
大概率不是。vLLM 这类引擎在启动时就按 gpu_memory_utilization 把 KV Cache 池一次性预分配好，所以从服务起来的第一秒起，显卡占用率就会稳定在设定值附近，这是设计如此而不是压力信号。判断 KV 是否真的吃紧，要看池内水位指标 vllm:gpu_cache_usage_perc——它表示预分配的池子里实际用掉了多少。举个例子：gpu_memory_utilization=0.9 时 nvidia-smi 恒显示 90%，但如果池水位只有 0.3，说明并发还有很大余量。把这两个数字搞混，是显存类故障排查中最常见的第一步错误。
为什么要先止损再定位？直接找到根因不是更彻底吗？
因为定位耗时的方差极大而止损耗时的方差极小。把 MTTR 拆成"发现 + 定位 + 修复"，其中定位这一项可能是五分钟也可能是两小时，取决于问题的隐蔽程度；而降并发这个动作无论根因是什么都能在一分钟内生效。先止损，等于把用户受损时长从"取决于诊断难度"变成"取决于操作速度"。止损之后服务已经可用，事故等级从 P0 降到 P2，你可以从容地花两小时把根因搞透，这时候的排查质量反而比在压力下更高。需要注意的是止损前要留好现场快照，否则降载后指标回归正常，最有价值的曲线就丢了。
显存缓慢上涨，是不是 KV Cache 泄漏了？
在采用分页 KV 管理的引擎里几乎不可能。KV 池是启动时一次性预分配的固定大小空间，请求结束时占用的块归还池子，池子总量不会增长，所以"KV 泄漏"这个说法本身就和它的内存模型矛盾。真正在涨的通常是三者之一：池外的 GPU 显存（某些自定义算子或多模态预处理没释放中间张量）、CPU 侧 RSS（请求对象堆积、日志缓冲、Prometheus 指标标签基数爆炸），或者根本没在涨——你看的是池水位随流量的正常波动。区分方法很便宜：把流量停掉五分钟，真泄漏不会回落，池水位一定掉回基线。
swap_space 调大能不能彻底解决 OOM？
不能，它是个缓冲垫不是扩容手段，而且这个参数最容易被误解。首先它指的是预留多少 CPU 内存（GB 为单位）用于把 KV 块换出显存，跟操作系统的磁盘 swap 完全无关，设太大会挤爆容器的内存限额。其次它的作用发生在抢占时刻：调度器决定把某个序列踢出显存，与其丢弃后重算，不如先换到 CPU 内存里，之后再换回来。但换入换出走 PCIe，一旦频繁触发，延迟抖动会非常明显，TPOT 曲线会出现毛刺。所以它适合用来削平偶发的容量尖峰，如果稳态就要靠它撑着，说明容量本身不够，该做的是降并发或扩容。
并发升高后 OOM，为什么降 max_num_seqs 有时候没用？
因为 KV 池的占用是按 token 数算的，不是按请求数算的。max_num_seqs 限制的是同时在批次里的序列条数，但如果进来的是超长上下文请求，少数几条就能吃掉大半个池子。假设池子能装 40 个 2K 上下文的请求，那么 5 个 16K 的请求进来池子就满了——这时候把 max_num_seqs 从 64 降到 32 完全不解决问题，因为瓶颈根本不在条数上。正确做法是同时约束长度维度：在网关按 token 数拒绝超长请求，或调小 max_model_len，或者把长上下文流量路由到独立实例，让它不和短请求抢同一个池子。这也解释了为什么 QPS 没涨服务却挂了——涨的是单请求的上下文长度。
TTFT 变长，是不是 Prefill 计算慢了？
多数情况下不是。TTFT 是个复合指标，包含排队等待和 Prefill 计算两段，服务过载时膨胀的几乎总是前者。典型形态是：Prefill 本身只花 80 毫秒，但请求在 waiting 队列里躺了 2 秒，用户测到的 TTFT 就是 2.08 秒。区分方法是看 vllm:num_requests_waiting——如果 TTFT 抬升的同时等待队列也在涨，那就是准入侧排队。这个区分之所以重要，是因为两者的处置方向相反：排队问题要在准入侧解决（限流、缩短上下文、扩容），而真正的 Prefill 变慢才需要动 chunked prefill、max_num_batched_tokens 这类计算侧参数。方向搞反了会越调越糟。
重启实例为什么不算好的止损手段？
推理实例的重启成本远高于普通 Web 服务。权重要从磁盘或对象存储重新加载进显存，几十 GB 的模型这一步就要几十秒；接着引擎做显存探测和 KV 池预分配；没关 CUDA Graph 的话还要走一遍图捕获预热。合计通常在一到三分钟量级，这段时间容量是真空的。更隐蔽的代价是前缀缓存被清空——那些被大量请求共享的系统提示词 KV 块全没了，重启后头几分钟本该命中缓存的请求都要重新 Prefill，实际吞吐比稳态还低，很容易一放回流量就再次被打挂，形成重启循环。重启只在两种情况下值得：怀疑进程内状态已损坏，或者必须改启动参数才能恢复。
应该配哪些告警才能在故障前就发现问题？
最低限度四条，按提前量排序。第一条是 KV 水位：vllm:gpu_cache_usage_perc 超过 0.95 持续 5 分钟，这是所有并发类故障的共同前兆。第二条是等待队列：vllm:num_requests_waiting 大于 0 持续 2 分钟，说明容量已经不够、用户在排队但还没报错。第三条是抢占计数 vllm:num_preemptions_total 的增速非零，抢占意味着算力在做重复计算，是拥塞的明确信号。第四条是 TTFT P95 超 SLA，直接对齐用户体验，兜住前三条漏掉的情况。关键在于前三条都是前兆指标——等错误率涨起来再告警，用户已经受损了，那时候能做的只有止损而不是预防。
