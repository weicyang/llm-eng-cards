Ollama 和 llama.cpp 的关系，很像 Docker 和 Linux 容器原语的关系：真正干活的内核早就有了，Ollama 做的是把"拉取、版本、配置、加载、卸载、暴露 API"这一整套生命周期管理包装成三个命令。它让本地跑模型这件事从"编译半小时、调二十个参数"变成 ollama run，代价是把高并发调度这块能力留在了门外。

一、Ollama 的定位：内核之上的分发层

要用好 Ollama，第一件事是搞清楚它在整个技术栈里站在哪一层。它不是一个新的推理引擎——真正执行矩阵乘法、管理 KV Cache、做量化反量化的是 llama.cpp（纯 C++ 重写的推理栈，零外部依赖，针对 AVX2/AVX512/ARM NEON 手工优化，并提供 CUDA、Metal、Vulkan 后端）。Ollama 在这个内核之上补齐了 llama.cpp 有意不做的那部分：模型怎么获取、怎么版本化、怎么配置、什么时候加载进内存、什么时候踢出去、怎么暴露成 HTTP 服务。

Ollama 在本地推理栈中的位置 ┌──────────────────────────────────────────────────────────────┐ │ 应用层 IDE 插件 / 桌面客户端 / LangChain / 自研脚本 │ └───────────────────────────┬──────────────────────────────────┘ │ OpenAI 兼容 HTTP (/v1/chat/completions) │ 原生 API (/api/generate, /api/chat) ┌───────────────────────────▼──────────────────────────────────┐ │ Ollama 守护进程 ← 这一层是 Ollama 的全部价值 │ │ ├─ 模型分发：registry 拉取、内容寻址 blob、层复用 │ │ ├─ 配置封装：Modelfile（FROM / PARAMETER / TEMPLATE / SYSTEM）│ │ ├─ 生命周期：按需加载、keep_alive 空闲卸载、多模型换入换出 │ │ ├─ 资源编排：显存评估、多 GPU 放置、CPU/GPU 层切分 │ │ └─ 服务化：HTTP 监听、请求队列、CORS、并发槽位 │ └───────────────────────────┬──────────────────────────────────┘ │ ┌───────────────────────────▼──────────────────────────────────┐ │ llama.cpp 内核 GGUF 解析 · 量化算子 · KV Cache · 采样 │ └───────────────────────────┬──────────────────────────────────┘ │ ┌───────────────────────────▼──────────────────────────────────┐ │ 硬件后端 CUDA · Metal · Vulkan · ROCm · CPU SIMD │ └──────────────────────────────────────────────────────────────┘

这个分层解释了 Ollama 的全部优点和全部局限。它把 llama.cpp 里那些劝退新手的事情（编译选项、GGUF 文件到处找、prompt 模板要手写、采样参数要背）全部收进了一个守护进程和一份声明式配置里；但它没有、也不打算去补 llama.cpp 在服务端调度上的短板——没有 PagedAttention 式的分页显存管理，没有 vLLM 那样的迭代级连续批处理，跨请求的前缀复用能力也很弱。这不是缺陷，是定位。

顺带厘清一个常见误解：Ollama 慢并不等于 llama.cpp 慢。同一硬件上，Ollama 的默认配置（并发数 1、上下文 4096、不开 Flash Attention）会让它看起来明显不如调优过的 llama.cpp server，而这些几乎都可以通过环境变量调回来。真正拉不回来的是架构层面的差距——那部分见第五节。关于四大推理框架的横向定位，可参考 DP05 · 大模型推理框架选型。

二、Modelfile、模型层与本地存储

Ollama 对"模型"的抽象比大多数人以为的要重。在它眼里，一个模型不是一个权重文件，而是权重 + 提示模板 + 系统消息 + 采样参数 + 停止词 + 可选 LoRA 适配器打成的一个整体。这个整体由 Modelfile 定义——一份声明式的纯文本配置，语法刻意模仿 Dockerfile。

Modelfile 的指令集

指令作用典型用法与要点
FROM（必需）指定基础模型可以是已有模型名、Safetensors 目录，或本地 .gguf 文件路径
PARAMETER设定运行参数上下文长度、温度、采样、停止词等，写进模型即成为默认值
TEMPLATE完整提示模板Go 模板语法，变量为 .System / .Prompt / .Response，模板错了模型会"发疯"
SYSTEM内置系统消息把角色设定固化进模型，调用方不传也生效
ADAPTER挂载 LoRA 适配器支持 Safetensors 与 GGUF 两种格式；基座不匹配会导致输出错乱
MESSAGE预置对话历史用 user/assistant 轮次做少样本引导，固化进模型
LICENSE声明许可协议分发自定义模型时的合规字段
REQUIRES声明最低 Ollama 版本避免旧版本加载新特性模型时行为异常

PARAMETER 里有几个默认值值得记住，因为它们直接影响显存占用和输出质量。num_ctx 在 Modelfile 层面默认 2048，而服务端默认上下文窗口是 4096（可用 OLLAMA_CONTEXT_LENGTH 覆盖）；temperature 默认 0.8 偏发散，做结构化输出时通常要调到 0.1~0.3；top_k 默认 40、top_p 默认 0.9；repeat_penalty 默认 1.0 也就是默认不惩罚重复，小模型上容易复读，常调到 1.1 左右；num_predict 默认 -1 表示无限生成，服务化时应当设上限防止单请求长期占住槽位。

# 把角色、模板、采样参数固化成一个可分发的"内部模型"
FROM qwen3:8b
PARAMETER num_ctx 8192
PARAMETER temperature 0.2
PARAMETER repeat_penalty 1.1
PARAMETER num_predict 1024
SYSTEM """你是内部知识库助手，只依据给定资料回答，无资料时明确说明。"""

保存后用 ollama create kb-assistant -f Modelfile 构建，之后团队里任何人 ollama run kb-assistant 拿到的都是同一套配置。反过来，ollama show --modelfile <模型> 可以把官方模型的 Modelfile 反解出来，这是排查"为什么输出格式不对"的第一手段——绝大多数格式问题都出在 TEMPLATE 的特殊 token 上。

Modelfile 的真正价值不是"能改参数"，而是把配置从调用方挪进了模型里。传统做法下，system prompt 和采样参数散落在每个调用方的代码里，改一次要发五个版本；有了 Modelfile，改一次重建模型即可，所有调用方立刻生效。这就是把"提示词工程"变成"可版本化的构件"。

模型层与内容寻址存储

Ollama 借鉴 Docker 的地方不止语法。它把模型拆成若干层（layer）：权重是一层，模板是一层，参数是一层，系统消息是一层，每层按内容哈希（sha256）存成一个 blob，再用一份 manifest 记录"这个模型由哪些 blob 组成"。这带来两个直接好处：基于同一底模的多个自定义模型只存一份权重（几 GB 的大头被复用，各自只多出几 KB 的配置层）；以及拉取时可以跳过本地已有的层。

路径这件事在服务器上经常出问题：Linux 下 Ollama 以 ollama 系统用户运行，如果把 OLLAMA_MODELS 指到一块新挂载的大盘却忘了改属主，守护进程会因为无权限写入而拉取失败，日志里只报一个含糊的错误。另一个高频坑是模型盘容量——量化后的 8B 模型约 4~5 GB，但 70B 级别的 Q4_K_M 会到 40 GB 以上，几个模型就能把系统盘撑爆。

典型场景推演：一次靠层复用省下的磁盘账。某团队为不同业务线基于同一个 8B 底模做了 6 个定制模型（客服话术、代码注释、日报摘要、SQL 生成、合规检查、翻译），每个只是 SYSTEM 和采样参数不同。如果按"一个模型一个权重文件"管理，Q4_K_M 档位下每份约 4.6 GB，6 份就是约 27.6 GB；借助内容寻址的层复用，权重层只存一份，6 个模型合计仍是约 4.6 GB 加上几十 KB 的配置层，磁盘占用降到原来的六分之一左右。更重要的收益在加载行为上：这 6 个模型共享同一个权重 blob，切换时不需要重新从磁盘读取整份权重，冷启动明显快于加载 6 份独立权重。这里的数字直接来自模型体积与份数的算术，可自行按你的底模大小复算。

三、并发行为与关键环境变量

这一节是 Ollama 从"玩具"走向"内网小服务"的关键，也是踩坑最密集的地方。默认配置是为单人本地使用优化的，直接拿来给一个团队用，几乎必然遇到"两个人同时问就开始排队"的问题。

Ollama 的两级并发

Ollama 的并发分两个层次，理解这一点才能把参数调对。第一级是多模型并存：内存/显存足够时可以同时加载多个不同模型，由 OLLAMA_MAX_LOADED_MODELS 控制上限，默认是 GPU 数量的 3 倍（纯 CPU 推理时为 3）。第二级是单模型内的并行请求：一个已加载的模型能同时处理几个请求，由 OLLAMA_NUM_PARALLEL 控制，默认值是 1——也就是说，开箱即用的 Ollama 对同一个模型是串行处理请求的。

官方文档里有一句必须记住的话：并行请求会让上下文按并行数成倍放大。原文的例子是"2K 上下文配 4 个并行请求，实际会变成 8K 上下文并分配额外内存"。换句话说：

KV Cache 内存需求 ∝ OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH

这个乘法关系是 Ollama 显存规划的核心公式。很多人把 OLLAMA_NUM_PARALLEL 调到 8、又把 OLLAMA_CONTEXT_LENGTH 拉到 32768，然后困惑于模型为什么突然从 100% GPU 掉到部分跑在 CPU 上——因为 KV Cache 的需求被放大了几十倍，显存装不下，Ollama 只好把部分层卸载到内存。

模型换入换出：延迟毛刺的主要来源

keep_alive 机制决定了模型在内存里待多久。默认 5 分钟空闲后卸载，这对笔记本很友好（不用时把显存还给系统），但对一个内网服务是灾难：每天早上第一个提问的人、每次午休后的第一次调用，都要等模型从磁盘重新加载——大模型的加载动辄十几秒到几十秒，用户看到的是"这个 AI 时好时坏"。

keep_alive 取值含义适用场景

还有两个实用细节。其一，/api/generate 和 /api/chat 的 keep_alive 请求参数会覆盖环境变量，这意味着可以按调用方区分策略：常驻的主力模型走 -1，偶尔用一次的大模型走 0。其二，可以通过发一个只带 model 字段的空请求来预热模型，服务启动脚本里加一行就能把冷启动从用户请求路径上挪走。

# 服务启动后主动预热并常驻，把冷启动挪出用户请求路径
curl http://localhost:11434/api/generate -d '{"model":"qwen3:8b","keep_alive":-1}'
# 需要腾显存时立即卸载
ollama stop qwen3:8b

诊断当前状态用 ollama ps，它会列出已加载模型、占用大小、剩余驻留时间，以及最关键的 PROCESSOR 列：100% GPU 表示全在显存里，100% CPU 表示完全跑在内存里，而像 48%/52% CPU/GPU 这样的混合值意味着发生了部分卸载——这一列是排查"为什么突然变慢"的第一入口。

典型场景推演：内网小服务的默认配置翻车。某 15 人小组把一台带 24GB 显存显卡的工作站装上 Ollama，跑 Q4_K_M 量化的 8B 模型（权重约 4.6 GB）当内部助手，直接用默认配置对内提供服务。问题很快出现：两个人同时提问时，第二个人的首字延迟从 1 秒级涨到十几秒——因为 OLLAMA_NUM_PARALLEL 默认是 1，请求实际在排队而不是并行；同时因为默认 5 分钟空闲卸载，午休后第一次调用要多等一次完整的模型加载。调整方案是三件事：OLLAMA_NUM_PARALLEL=4 打开并行槽位、OLLAMA_KEEP_ALIVE=-1 让模型常驻、OLLAMA_CONTEXT_LENGTH=8192 匹配业务实际需要的上下文。这里必须同时算显存账：并行 4 × 上下文 8192 意味着 KV Cache 要按 32768 token 的规模预留，加上 4.6 GB 权重，要确认仍能落在 24GB 内、ollama ps 稳定显示 100% GPU；若超了就得降并行数或开 OLLAMA_KV_CACHE_TYPE=q8_0（约省一半 KV 显存）。这个案例的可迁移部分是那条乘法关系和 ollama ps 的校验动作，绝对数值随卡型与模型而变。
Ollama 的默认配置是为"一个人、一台笔记本、偶尔用一下"设计的：串行处理省资源，5 分钟卸载省电。这套默认值放到多人共享的服务器上，每一条都恰好是错的。所以把 Ollama 用作服务的第一步不是写代码，是把这三个环境变量改对。

四、GGUF 量化档位与混合卸载

GGUF（GPT-Generated Unified Format）是 llama.cpp 生态的模型格式，把权重、量化方案、分词器和元数据打包进单个文件，支持 mmap 按需加载。量化则是本地部署的核心杠杆：把 FP16 权重压到 2~8 bit，用可控的质量损失换取"这台机器到底跑不跑得动"。

把 F16 和 Q4_K_M 两行对比着看：体积从 14.96 GiB 降到 4.58 GiB（约三分之一），解码速度反而从 29.17 t/s 涨到 71.93 t/s，快了约 2.5 倍；而预填充速度从 923 t/s 降到 822 t/s，不升反降。这不是测试误差，而是两个阶段瓶颈不同的直接体现：Decode 每生成一个 token 都要把全部权重从内存读一遍，是带宽瓶颈，权重变小等于要搬的数据变少，所以量化越狠解码越快；Prefill 是把整段输入并行做矩阵乘法，是算力瓶颈，量化格式还要额外做反量化，所以速度不升反降。这条规律解释了本地部署最重要的一个体感——量化对"吐字速度"的提升远大于对"首字延迟"的提升。这两个阶段的完整机理见 DP10 · 大模型推理性能瓶颈分析，量化算法本身见 DP13 · 大模型量化实战指南。

量化不只是"用质量换体积"，在本地场景它常常是"用质量换体积顺便换来速度"。因为个人设备的内存带宽远比算力稀缺，把权重压小直接缓解了最紧的那个约束。这也是为什么服务端 GPU 上量化的收益模式和笔记本上完全不同——服务端的瓶颈往往在别处。

档位命名也有规律：K 表示 K-quant 分组混合精度（对不同张量用不同精度，关键权重保留更高位宽），后缀 _S/_M/_L 是同一位宽下的小/中/大变体，体积和质量依次递增。此外还有 IQ 系列（i-quant），在极低位宽下质量优于同体积的 K-quant，代价是对 CPU 指令集更挑剔。官方文档同时指出，量化质量损失可以用重要性矩阵（imatrix）显著缓解——用一批校准数据统计各权重的重要性，量化时对重要权重更保守。这也是为什么社区里同名的 Q4_K_M 文件质量可能有差别：看它是不是用 imatrix 量化的。

CPU+GPU 混合卸载：装不下时会发生什么

当模型装不进显存，llama.cpp 系的引擎不会直接报错，而是做层卸载（offload layers）：把 Transformer 的前 N 层放进显存，剩余层留在系统内存用 CPU 计算。Ollama 会自动评估并决定这个切分点，ollama ps 的 PROCESSOR 列显示的 48%/52% CPU/GPU 就是这种状态。

全量 GPU vs 混合卸载：每个 token 的代价差异 【100% GPU】权重全在显存，解码只读显存（带宽 ~TB/s 量级） token ─► [L1..L32 全在 VRAM] ─► 输出 速度：快且稳定 【混合卸载 50/50】一半层在内存，每个 token 都要跨 PCIe token ─► [L1..L16 VRAM] ═PCIe═► [L17..L32 RAM/CPU] ─► 输出 ▲ └ 系统内存带宽比显存低一个量级， 且每层都要等 CPU 算完 —— 木桶效应 速度：由留在 CPU 上的那部分主导，可能只有全 GPU 的几分之一 经验判断：宁可降一档量化让模型完整进显存， 也不要为了"用更好的量化"而触发混合卸载。

混合卸载的性能特征是典型的木桶效应：只要有一部分层跑在 CPU 上，整体速度就由那部分主导，而不是按比例折中。所以本地部署有一条相当硬的经验法则——能整份塞进显存的低一档量化，通常远优于触发卸载的高一档量化。比如 12GB 显存跑 14B 模型，Q4_K_M 刚好塞得下就选它，别为了质量去挑 Q5_K_M 然后卸载三分之一层到 CPU。

Apple Silicon 是个特例：统一内存架构下 CPU 和 GPU 共享同一块高带宽内存，不存在跨 PCIe 搬运的问题，所以大内存的 Mac 能相对流畅地跑很大的模型，这也是 Ollama 在 Mac 用户里格外流行的原因。

五、Ollama / vLLM / LM Studio 选型边界

这三个工具经常被拿来比较，但它们其实处在不同的坐标上：Ollama 是命令行优先的本地模型运行时，LM Studio 是图形界面优先的本地实验环境（同时也提供无界面的守护进程形态），vLLM 是为 GPU 服务端高并发设计的推理引擎。搞混它们的定位，就会得出"Ollama 性能不行"这种既对又没抓住重点的结论。

为什么 Ollama 不适合高并发生产服务

这不是"调优不够"的问题，而是架构层面的三点差距，值得逐条说清：

  • 没有连续批处理。vLLM 在每个解码步都重新组批，完成的请求立刻退出、新请求立刻插入，GPU 几乎不空转。Ollama 走的是固定并行槽位模型，槽位被占住就得等，请求之间的调度粒度粗得多，GPU 利用率上不去。
  • 显存按最坏情况预留。KV Cache 需求等于并行数乘以上下文长度，无论请求实际用多长都按这个规模分配。vLLM 的分页管理是"用多少占多少、用完立刻归还"，同样显存能塞下的并发数完全不是一个量级。
  • 缺少生产必备的周边。默认没有 API Key 鉴权机制，没有内建的 Prometheus 指标体系，没有多副本编排与灰度发布能力。这些在对外服务里不是加分项而是及格线。

反过来说，这三条在本地开发场景下全都不是问题：单人使用并发就是 1，显存预留策略无所谓，鉴权和指标更是多余负担。所以正确的说法不是"Ollama 性能差"，而是"Ollama 优化的是另一个目标函数"。

LM Studio 值得单独说一句，因为它常被低估成"给不会命令行的人用的"。它的差异化优势在模型探索环节：可以在图形界面里直接搜索 Hugging Face、并排看到同一模型的各个量化档位与体积、根据本机硬件给出"能否跑得动"的提示，然后一键下载试用。这个流程在 Ollama 里要靠查文档和试错完成。同时它也提供无界面的守护进程形态（lms daemon up）和开机自启，并支持按需加载（JIT loading）——开启后调用推理端点时会自动把模型载入内存，配合空闲自动卸载，行为与 Ollama 的 keep_alive 机制类似。它同时提供 OpenAI 兼容和 Anthropic 兼容两套端点，接入面比 Ollama 更宽。

一个实用的分工心法：LM Studio 用来选模型，Ollama 用来跑模型，vLLM 用来卖模型。在 LM Studio 里横向对比几个候选和量化档位，选定之后用 Ollama 固化成带 Modelfile 的内部构件供团队日常使用，等到要对外提供服务、并发上百时，再把同一个模型的非量化版本搬到 vLLM 上。

六、三类落地场景与接入方式

把前面的机制落到具体场景上，Ollama 的合理用法基本可以归成三类。它们对配置的要求差别很大，用错配置比用错工具更常见。

OpenAI 兼容接入：一行 base_url 的事

Ollama 同时提供两套 HTTP 接口：原生的 /api/generate 与 /api/chat（支持 keep_alive、options 等 Ollama 特有字段），以及 OpenAI 兼容端点 /v1/chat/completions。后者的意义在于迁移成本几乎为零：任何用 OpenAI SDK 写的代码，只要把 base URL 指向本地、API Key 随便填一个占位串，就能跑在本地模型上。LangChain、LlamaIndex 等框架也都能直接对接。

from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
resp = client.chat.completions.create(
    model="qwen3:8b",
    messages=[{"role": "user", "content": "总结这段日志的异常原因"}])

这条兼容路径同时也是一条退路：本地验证完逻辑后，把 base URL 换成 vLLM 服务或云 API，业务代码一行不用改。所以即使明知未来要上 vLLM，前期用 Ollama 做原型也不会产生返工。

内网服务场景有一个必须强调的安全问题。Ollama 默认只监听 127.0.0.1:11434，一旦为了让同事访问而改成 0.0.0.0，就等于把一个完全没有鉴权的推理接口暴露给了整个网络——任何能连到这个端口的人都可以调用模型、拉取甚至删除模型。正确做法是在前面挂一层反向代理（Nginx 是官方文档给出的方案）来做鉴权、限流和访问日志，并用防火墙把 11434 端口限制在代理机可达的范围内。官方 Nginx 示例里有个容易漏掉的细节：需要设置 proxy_set_header Host localhost:11434，否则会因为来源校验失败而被拒绝；用 ngrok 或 Cloudflare Tunnel 做临时穿透时同样要带上对应的 host header 参数。

另外两个部署期的实用点：拉取模型走代理时要用 HTTPS_PROXY 而不是 HTTP_PROXY，因为 Ollama 的模型拉取只走 HTTPS，设置 HTTP_PROXY 反而可能干扰客户端到服务端的正常连接；如果需要完全离线运行，可以通过 OLLAMA_NO_CLOUD=1 或在 ~/.ollama/server.json 里设置 disable_ollama_cloud 关闭全部云端能力，这在合规审计场景下是一个可以拿出来说的配置项。边缘侧的更多约束与优化手段见 DP07 · 边缘设备部署。

典型场景推演：从 Ollama 迁移到 vLLM 的判断时点。某公司内部助手最初用 Ollama 服务 15 人，配置为并行 4、常驻、8K 上下文，运行稳定。半年后接入范围扩到 200 人并嵌入了工单系统自动摘要（机器发起的批量调用），日间高峰的并发请求数经常超过 20。此时症状很典型：OLLAMA_MAX_QUEUE 尚未打满所以不返回 503，但请求在队列里等待，首字延迟从 1 秒级恶化到十几秒；把 OLLAMA_NUM_PARALLEL 从 4 提到 16 后，KV Cache 需求按 16 × 8192 放大到原来的 4 倍，模型被迫部分卸载到 CPU，ollama ps 从 100% GPU 变成混合状态，解码速度反而更差——这就是架构上限，不是参数没调好。判断规则可以简化成一条：当稳定并发超过约 10、或者出现"加并行数反而变慢"时，说明已经越过 Ollama 的适用边界，该把同一模型的非量化版本搬到 vLLM 上，靠连续批处理和分页显存拿回吞吐。具体阈值随卡型、模型规模与上下文长度变化，但"加并行反而更慢"这个信号本身是通用的。
  • 服务化前先算显存账：权重 + 并行数 × 上下文对应的 KV Cache
  • 用 ollama ps 确认 100% GPU，这是性能是否正常的第一判据
  • 内网服务设 OLLAMA_KEEP_ALIVE=-1 并在启动脚本里主动预热
  • 用 Modelfile 把系统提示与采样参数固化成可版本化的内部模型
  • 暴露到网络时必须挂反向代理做鉴权限流，并用防火墙收敛端口
  • 量化默认从 Q4_K_M 起步，显存有余量再往 Q5_K_M / Q6_K 升
  • 业务代码统一走 OpenAI 兼容端点，为将来换后端留好退路
  • 不要拿默认配置对多人提供服务（并行数默认是 1，请求会排队）
  • 不要为了用更高档量化而让模型触发 CPU 混合卸载，那是木桶效应
  • 不要把 OLLAMA_HOST 改成 0.0.0.0 却不加任何鉴权
  • 不要靠调大 OLLAMA_MAX_QUEUE 解决过载，那只是延后拒绝
  • 不要在并发持续超过十几路的场景硬扛，该换 vLLM 就换
  • 不要盲目拉大 OLLAMA_CONTEXT_LENGTH，它会和并行数相乘放大显存
  • 不要假设同名的 Q4_K_M 文件质量一致，留意是否用 imatrix 量化
Ollama 的甜蜜区是"少数几个人、数据不能出门、想马上跑起来"。在这个区间里它几乎没有对手；一旦并发上到两位数、或者需要鉴权指标灰度这些生产设施，继续硬扛的成本会迅速超过换引擎的成本。知道边界在哪，比知道怎么调参更重要。

Q&A

Ollama 和 llama.cpp 到底是什么关系？

llama.cpp 是推理内核，Ollama 是构建在它之上的分发与生命周期管理层，两者不是竞争关系。真正执行矩阵乘法、解析 GGUF、管理 KV Cache、做量化算子的是 llama.cpp；Ollama 补齐的是它有意不做的部分：从 registry 拉取模型、用内容寻址的层做存储与复用、用 Modelfile 把提示模板和采样参数打包进模型、按需加载与空闲卸载、自动决定 CPU/GPU 层切分、暴露 HTTP 服务。类比的话，llama.cpp 像 Linux 的容器原语，Ollama 像 Docker。所以"Ollama 比 llama.cpp 慢"这个说法要拆开看：默认配置确实保守（并行数 1、上下文 4096），但这些大多能通过环境变量调回来；真正拉不平的是服务端调度架构，那部分两者本来就都不擅长。

为什么两个人同时用 Ollama 就开始排队？

因为 OLLAMA_NUM_PARALLEL 默认值是 1，即单个模型同一时刻只处理一个请求，其余请求进队列等待。这个默认值是为单人本地使用优化的——一个人用的时候并发本来就是 1，串行处理最省内存。要支持多人，需要显式把这个变量调大。但调之前必须算显存账：官方文档明确说明并行请求会让上下文按并行数成倍放大，文档给的例子是"2K 上下文配 4 个并行请求会变成 8K 上下文并分配额外内存"，也就是 KV Cache 需求正比于并行数乘以上下文长度。盲目调大会让模型装不进显存而触发 CPU 混合卸载，结果是并发上去了但每个请求都更慢。调完后用 ollama ps 确认 PROCESSOR 列仍是 100% GPU。

OLLAMA_KEEP_ALIVE 该怎么设？

取决于场景。默认是 5 分钟空闲后卸载模型，这对个人笔记本很合适——不用时把显存还给系统。但对内网服务是灾难：每天早上第一个人提问、每次午休后第一次调用，都要等模型重新从磁盘加载，大模型动辄十几秒到几十秒，用户感受到的是"这个 AI 时好时坏"，而且毫无规律，是最难排查的那类问题。服务化场景应当设为 -1（任意负数都表示永久常驻），并在启动脚本里发一个只带 model 字段的空请求做预热，把冷启动彻底移出用户请求路径。取值形式支持时长字符串（如 "10m"、"24h"）、秒数、负数（常驻）和 0（生成完立即卸载）。此外 API 请求里的 keep_alive 参数会覆盖环境变量，可以按调用方区分策略：主力模型常驻，偶尔用一次的大模型设 0。

GGUF 量化档位这么多，实际怎么选？

默认从 Q4_K_M 起步，这是质量、体积、速度三者的公认平衡点，Llama-3.1-8B 上它的体积是 4.58 GiB（F16 为 14.96 GiB）。选择的核心约束是"能不能整份装进显存"——如果 Q4_K_M 装得下且还有余量，可以往上升到 Q5_K_M 或 Q6_K 换取质量；如果装不下，宁可降到 Q4_K_S 甚至 Q3_K_M，也不要用更高档位然后触发 CPU 混合卸载。命名规律是：K 表示 K-quant 分组混合精度（关键权重保留更高位宽），后缀 S/M/L 是同位宽下的小中大变体；IQ 系列在极低位宽下质量更好但对 CPU 指令集更挑剔。还有一点容易忽略：同名的 Q4_K_M 文件质量可能不同，取决于量化时是否使用了重要性矩阵（imatrix）校准，用了的质量明显更好。

为什么量化后解码变快了，但首字延迟没怎么改善？

因为推理的两个阶段瓶颈完全不同。解码阶段每生成一个 token 都要把全部权重从内存读一遍，是带宽瓶颈，权重体积变小直接等于要搬运的数据变少，所以量化越狠解码越快——llama.cpp 官方实测的 Llama-3.1-8B 上，F16 的解码速度是 29.17 t/s，Q4_K_M 是 71.93 t/s，快了约 2.5 倍。预填充阶段是把整段输入并行做矩阵乘法，是算力瓶颈，量化格式还要额外做反量化计算，所以速度不升反降：同一组数据里 F16 的预填充是 923.49 t/s，Q4_K_M 反而是 821.81 t/s。首字延迟主要由预填充决定，这就是为什么量化对"吐字速度"的提升远大于对"首字延迟"的提升。想改善首字延迟要从别处入手，比如缩短输入、开启前缀缓存或提升算力。

什么时候必须从 Ollama 换到 vLLM？

核心信号是"加并行数反而变慢"。当稳定并发超过十几路时，把 OLLAMA_NUM_PARALLEL 继续调大会让 KV Cache 需求线性放大（正比于并行数乘上下文长度），模型被迫部分卸载到 CPU，触发木桶效应导致整体更慢——这是架构上限，不是参数没调好。背后是三点架构差距：Ollama 没有连续批处理（固定并行槽位，调度粒度粗，GPU 利用率上不去）；显存按最坏情况整块预留而非分页按需分配；缺少 API 鉴权、Prometheus 指标、多副本编排这些生产必备设施。另外两个明确的换引擎信号是：需要对外提供服务因而必须有鉴权和可观测性，以及需要多副本灰度发布。反过来，如果只是几个人内网用、并发个位数，Ollama 完全够用，换 vLLM 反而是给自己加运维负担。

Modelfile 有什么实际价值，不用它行不行？

不用也能跑，但会失去配置的可版本化管理。Modelfile 的作用是把提示模板、系统消息、采样参数、停止词、可选的 LoRA 适配器和基础模型打包成一个整体构件，用 ollama create 构建后，团队里任何人拉到的都是同一套配置。没有它的话，system prompt 和采样参数会散落在每个调用方的代码里，改一次要发多个版本。指令集包括 FROM（必需，可指向已有模型、Safetensors 目录或本地 GGUF 文件）、PARAMETER、TEMPLATE（Go 模板语法，变量为 .System/.Prompt/.Response）、SYSTEM、ADAPTER、MESSAGE、LICENSE、REQUIRES。还有个排查技巧：ollama show --modelfile 能把官方模型的配置反解出来，绝大多数"输出格式不对"的问题都能在 TEMPLATE 的特殊 token 里找到原因。

把 Ollama 暴露到内网有什么安全注意事项？

这是最容易出事的一步。Ollama 默认只监听 127.0.0.1:11434，很多人为了让同事访问就把 OLLAMA_HOST 改成 0.0.0.0，但 Ollama 本身没有任何内建鉴权机制——这等于把一个开放的推理接口暴露给整个网络，任何能连到该端口的人都能调用模型、拉取甚至删除模型，还可能被拿去跑与业务无关的负载。正确做法是在前面挂一层反向代理（官方文档给的是 Nginx 方案）承担鉴权、限流和访问日志，同时用防火墙把 11434 端口限制在只有代理机可达。官方 Nginx 示例里有个易漏细节：必须设置 proxy_set_header Host localhost:11434，否则会因来源校验失败被拒绝；用 ngrok 或 Cloudflare Tunnel 做临时穿透时同样要带上对应的 host header 参数。此外还应通过 OLLAMA_ORIGINS 收敛允许的跨域来源，而不是图省事全开。

ollama ps 显示 48%/52% CPU/GPU 意味着什么，要不要处理？

意味着模型没能完整装进显存，发生了层卸载：一部分 Transformer 层留在显存由 GPU 计算，剩余层留在系统内存由 CPU 计算。这个状态一定要处理，因为它的性能特征是木桶效应而非按比例折中——每生成一个 token 都要跨 PCIe 搬运数据，且要等 CPU 那部分算完，整体速度由留在 CPU 上的部分主导，可能只有全 GPU 的几分之一。处理方向有四个：降一档量化让模型完整进显存（这几乎总是比"用更好的量化但卸载"更划算）、调小 OLLAMA_NUM_PARALLEL 或 OLLAMA_CONTEXT_LENGTH 减少 KV Cache 占用、开启 Flash Attention 并把 OLLAMA_KV_CACHE_TYPE 设为 q8_0（约省一半 KV 显存，质量影响通常无感）、或者调小 OLLAMA_MAX_LOADED_MODELS 避免多个模型争抢显存。唯一的例外是 Apple Silicon，统一内存架构下 CPU 和 GPU 共享同一块高带宽内存，不存在跨 PCIe 的问题。
