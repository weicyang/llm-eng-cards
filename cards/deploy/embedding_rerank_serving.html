DP17 · Embedding 与 Rerank 模型部署

双峰负载 / Encoder 推理特性 / TEI 与 Infinity 与 vLLM 对比 / token 级动态批处理 / padding 税 / Cross-Encoder 延迟预算 / GPU 与 CPU 分界 / 共卡与容量核算

RAG 的部署注意力几乎全给了生成模型，但真正卡住延迟预算的常常是 Rerank，真正拖慢知识库上线的常常是 Embedding。这两个模型的负载形状是"双峰"的——离线灌库要吞吐，在线检索要延迟——一套配置同时伺候两种峰，必然两头都不达标。

一、被忽略的瓶颈：两种截然不同的负载

先看一份真实的延迟账本。一个企业级 RAG 应用把首字延迟目标定在 1 秒以内，把这 1 秒拆开：混合检索（BM25 加向量召回）P50 约 15ms、P95 约 35ms；内部网络传输与反序列化 3~8ms；Cross-Encoder 对 100 个候选打分 P50 约 35ms、P95 约 65ms；上下文拼装与分词 2~5ms；大模型 Prefill 到首 token P50 约 350ms、P95 约 650ms。检索加重排这一段合计 P50 约 55ms、P95 约 113ms，看起来只占预算的一成。

但这份账本成立有个前提：Rerank 用了合适的模型尺寸、合适的候选数、并且做了整批打分。前提一破，账本立刻反转。另一份面向 700ms 检索 P95 目标的拆解显示：首轮召回在候选数 100 时 30~50ms，而一个大号 Cross-Encoder 在候选数 100、批大小 8 的配置下要花 300~400ms，结果拼装与网络 40~80ms，摘要类大模型调用 150~300ms——重排一项就吃掉了半个延迟预算。同一个组件，配置对与不对之间差了将近十倍。

RAG 链路两种负载：吞吐敏感 vs 延迟敏感 ┌──────────────── 离线：灌库 / 重建索引（吞吐敏感）─────────────────┐ │ │ │ 文档 → 解析 → 切片 → ★Embedding 批量编码★ → 写入向量库 → 建索引 │ │ └─ 百万级文本，一次跑几小时 │ │ 关心：docs/sec、总耗时、单位成本 不关心：单条延迟 │ │ 手段：大 batch、长度分桶、FP16/INT8、多进程灌、可抢占可重跑 │ └───────────────────────────────────────────────────────────────────┘ ┌──────────────── 在线：检索 / 问答（延迟敏感）─────────────────────┐ │ │ │ Query → ★Embedding 单条编码★ → ANN 检索 TopK │ │ 5~15ms 5~15ms │ │ → ★Rerank 对 K 个 pair 打分★ → TopN → LLM Prefill │ │ 25~90ms（K=100） → 350~650ms │ │ 关心：P95/P99 尾延迟 不关心：峰值吞吐 │ │ 手段：小 batch 或整批一次调用、短截断、常驻显存、队列深度告警 │ └───────────────────────────────────────────────────────────────────┘ 同一个 Embedding 模型，两种负载的最优配置几乎完全相反

这就是 双峰负载的含义：Embedding 流量天然由两部分组成——重建语料索引时的批量任务，喂给加速器几百万篇文档、只关心纯吞吐；以及查询时一次一条用户问题的涓涓细流，批次几乎是空的、只关心低延迟。一个好的 Embedding 服务必须同时擅长这两件事，而实现这一点的杠杆是批处理：把并发请求聚成一次前向，让加速器不会在批大小为 1 的状态下空转。

被忽略的原因也不难理解：Embedding 与 Rerank 模型都很小。以常用的 bge-reranker-v2-m3 为例，5.68 亿参数、FP16 下约 1.1GB 显存，随便一张卡都装得下。"装得下"给人一种"随便部就行"的错觉，于是它们经常以一个 FastAPI 加 Transformers 的脚本形式上线，串行处理请求，把加速器大部分算力闲置。而真正的成本不在显存，在于批处理有没有做对——单文档循环推理与配置正确的批处理服务之间，同硬件同模型可以差一个数量级。关于模型本身的选型标准，可对照《Embedding 模型选型》；重排在检索链路中的作用则见《检索与重排序》。

"模型小所以不重要"是 RAG 部署里最贵的一个误判。Embedding 决定了知识库多久能上线，Rerank 决定了用户等多久才看到第一个字。这两个数字都不写在模型参数量里。

二、Embedding 的推理特性与优化差异

把生成模型那套优化直接套到 Embedding 上，是第二个常见错误。原因在于两者的推理结构根本不同。Embedding 模型是 Encoder-only 架构：把整段文本一次性送进编码器，所有 token 双向互相注意，最后用一个池化操作把 token 级隐状态压成一个定长向量。整个过程只有一次前向传播加一次池化，没有自回归、没有逐 token 循环，因此也就没有 KV Cache——缓存历史 Key/Value 是为了避免自回归解码重复计算，而 Encoder 根本不做自回归。

生成模型 vs Embedding 模型：推理结构对照 生成模型（Decoder-only，自回归） ┌──────────┐ ┌────────────────────────────────────────┐ │ Prefill │──▶│ Decode: t1 → t2 → t3 → ... → tN │ │ 一次并行 │ │ 每步读全部权重 + 读写 KV Cache │ └──────────┘ └────────────────────────────────────────┘ 算力密集 带宽密集，步数不定，显存随并发×长度增长 ⇒ 需要：KV 分页管理、迭代级连续批处理、前缀复用、投机解码 Embedding 模型（Encoder-only，单次前向） ┌────────────────────────────────────────────────────────┐ │ 输入全部 token → L 层双向自注意力 → 池化 → 定长向量 │ │ 一次前向结束，无状态，无 KV Cache，耗时可由长度预估 │ └────────────────────────────────────────────────────────┘ ⇒ 需要：token 级动态组批、长度分桶减 padding、算子/图优化 ⇒ 不需要：KV 分页、前缀缓存、投机解码 Rerank 模型（Cross-Encoder，单次前向但要跑 K 次） ┌────────────────────────────────────────────────────────┐ │ [CLS] query [SEP] doc_i [SEP] → 全交叉注意力 → 分数 │ │ 每个 (query, doc) 对都要独立前向；doc 表示依赖 query， │ │ 因此无法离线预计算、无法跨查询复用 │ └────────────────────────────────────────────────────────┘ ⇒ 成本 ≈ K × 单次前向，K 就是延迟旋钮

这张表解释了一个反复出现的疑问：既然 vLLM 这么强，为什么还需要专门的 Embedding 服务？答案是 vLLM 的招牌能力里有一半在 Embedding 上用不上——分页注意力管的是 KV Cache，而 Encoder 没有 KV Cache。它仍然值得考虑，但理由变成了另一个：连续批处理让请求自由加入和离开批次，这恰好是双峰流量最需要的性质；以及如果你本来就在跑 vLLM，那就少部署一个服务。想理解那套生成侧优化的完整逻辑，可参考《DP05 · 大模型推理框架选型》与《DP08 · KV Cache 与推理优化》。

生成模型的成本是"长度乘以步数"，Embedding 的成本是"一次前向"，Rerank 的成本是"一次前向乘以候选数"。三个公式不同，所以三套调优手段不能互换。搞清楚自己在优化哪个公式里的哪个因子，比记住任何参数都重要。

池化方式不是玄学，它决定了服务端能不能换模型

把 token 级隐状态压成单个向量的方式称为 池化，常见有取 [CLS] 位置、对所有 token 取均值、取最后一个 token，以及产出稀疏词权重的 SPLADE 式池化。它的部署意义在于：池化方式必须与模型训练时一致，否则向量语义会错乱，而检索结果只是"变差"不是"报错"，极难发现。所以服务端支持哪些池化方式，直接决定了你能部哪些模型——比如要做学习式稀疏检索就必须要求服务端支持 SPLADE 池化，只支持稠密池化的方案会把这条路堵死。

池化方式配错的故障特征是"一切正常但召回率悄悄掉了几个点"。这类问题不会报警，只会让业务觉得"这个 RAG 好像不太聪明"，所以换模型时把池化配置纳入回归检查清单，比事后排查便宜得多。

三、服务化方案对比与选型

自建 Embedding / Rerank 服务，通常在四种压力之一出现后才被提上日程：调用量大到 API 账单不可接受、尾延迟不可控、数据不能出域、或者想用的开源模型托管方没有提供。到了这一步，候选方案基本收敛为五个。

关于性能，必须先说一句反直觉的结论：两个配置正确的专用服务之间的差距，远小于任一个与"transformers 循环"之间的差距。朴素循环每次前向只处理一个请求，加速器大部分单元是暗的；这三个服务存在的意义都是修好这件事。批处理开对了之后，再去比谁快 20%，多半是在小数点后面较劲。

有参考价值的公开对比（以 bge-m3 为被测模型）大致给出这样的画像：vLLM 在高吞吐档位领先，例如批大小 32、切片长度 512、并发 100 时约 150 请求/秒；TEI 在极低延迟档位领先，批大小 1、极短文本、并发 1 时约 5ms；Infinity 表现均衡但在任何单一指标上都不突出。同一组实验还有个普适规律：吞吐随批大小上升，但延迟的改善在批大小超过 16 以后基本停滞——这为在线服务的批大小上限提供了一个经验起点。

Embedding / Rerank 服务选型决策树 已经在跑 vLLM 且有显存余量？ │ ┌──────────────────┴──────────────────┐ 是 否 │ │ 模型在池化任务清单里且 这条链路只做 Embedding 小型 Encoder 支持良好？ （± Rerank）吗？ │ │ ┌───────┴───────┐ ┌─────────┴─────────┐ 是 否 是 否 │ │ │ │ 用同一引擎服务 退回专用服务 TEI 需要 ColBERT / 少一个组件 （见右侧分支） 体积最小、专用 ColPali / CLIP / ⇒ 停在这里 路径最快、支持 多模态 / 多模型？ SPLADE 稀疏 │ Infinity 一个 API 管全家 纯 CPU 环境 / 边缘 / Serverless / 量小 → ONNX Runtime 路线 只有半小时且是内部原型 → FastAPI + Transformers，但别上生产

决策顺序比基准数字更重要，按下面三条走基本不会错：其一，已经在运维 vLLM 且有显存余量，就用同一个引擎顺带服务 Embedding，直接删掉一个组件——除非你的模型在它的池化支持清单里不是一等公民；其二，Embedding（可能加上 Rerank）就是全部工作，选 TEI，它足迹最小、启动最快、专用路径最快，还支持稀疏检索所需的池化；其三，链路里模型种类繁多——Rerank、ColBERT 后交互、文档图像检索、图文多模态——选 Infinity，一个 API 管住动物园胜过维护三套部署。只有在两个方案都过线时，才需要打开基准数据来破平局。

这三者看起来在竞争，其实在回答不同问题：TEI 回答"怎么把专用活儿干到最省最快"，Infinity 回答"怎么用一个服务养一整个模型动物园"，vLLM 回答"能不能干脆不部署第二个服务"。选型是架构题，不是跑分题。

两个容易被忽视的运维约束

TEI 的单容器单模型架构，在需要同时提供 Embedding 与 Rerank（甚至再加几个语言的变体）时会变成多个部署单元，运维与显存成本随模型数线性上升；而 Infinity 虽然能单实例托管多模型，却没有精细的显存换入换出管理，一旦所有模型无法同时驻留显存，就要自己解决。这两个约束往往比吞吐差异更影响长期成本，值得在选型阶段就写进评估表。服务化的通用工程问题——健康检查、灰度、指标暴露、扩缩容——可参考《DP04 · 模型服务化部署》。

选型时把"要同时在线几个模型"这个数字先算清楚。1 个模型时 TEI 的极简是优势，5 个模型时它就变成 5 套部署、5 份显存和 5 条告警规则，此时单实例多模型的方案会突然显得聪明起来。

四、批处理、序列长度与 padding 浪费

这一节是全文性价比最高的部分：Embedding 服务的性能，八成由批处理与长度处理决定，剩下两成才归框架选择。

按 token 组批，而不是按条数组批

直觉上"一批 32 条"是个自然的配置，但它把两条 8 token 的短句和三十条 500 token 的长段落一视同仁，于是批的实际计算量完全由长样本决定，而批数量却是固定的。TEI 采用的是另一种思路：按批内总 token 数组批。设定每批 token 上限后，这个"token 额度"可以由一百条短查询填满，也可以由两篇长文档填满，或者任意组合。结果是加速器利用率稳定得多，在输入长度方差大的真实语料上吞吐显著更好。TEI 侧对应的两个参数是每批最大 token 数（吞吐主旋钮）和单请求最大字符串条数；批越大吞吐越高但显存占用也越高。vLLM 走的是另一条路——自动动态组批，不需要手工调 token 上限，由调度器自行逼近显存与算力的甜点区。

这就是 padding 税：一批混合长度的文本会把每一行补齐到最长那一行，模型随后做的功正比于批大小乘以批内最大长度乘以隐藏维度，与批里有多少真实内容无关。真实文本长度方差极大——八句随机文本里可能有一个 60 token 的离群值和七个 8 token 的短句，模型于是把大部分周期用在把 padding 和注意力权重相乘。有个反直觉的推论：当长度方差足够大时，"不组批"逐条推理反而比"盲目组批"更省算力，因为逐条推理的计算量严格正比于该条的真实 token 数。当然，正解不是放弃组批，而是组批前先按长度排序分桶，再配动态 padding 只补到批内最长。

padding 消除图优化ONNX Runtime 侧把 padding 位置从计算图中剔除去掉 embedding 之后的无效计算需模型结构与算子在支持列表内
时间窗聚批累积 10~20ms 或达到条数上限即触发一次前向在线场景吞吐提升明显窗口就是延迟下限，必须计入 P95 预算
关闭线程自旋CPU 部署时关掉推理库内部线程池的忙等自旋吞吐上升同时 CPU 占用下降仅在"多并发小请求"模式下必要

时间窗聚批值得单独说明，因为它是在线服务里最实用的一招：服务端不立刻处理请求，而是累积一小段时间（例如 15ms）或达到条数上限（例如 8 条）后合成一批送去推理，每个请求持有自己的回调通道等结果。这个窗口是纯粹的延迟成本换吞吐收益，所以窗口长度必须写进延迟预算——15ms 的窗口在 1 秒预算里可以忽略，在 50ms 的内部服务预算里就是灾难。

生产案例：把灌库从 11 天压到 19 小时。某制造企业要为约 340 万条工艺文档切片建向量索引，初版灌库脚本用 FastAPI 加 Transformers、逐条调用、GPU 上跑 bge 系列模型，实测约 3.6 条/秒，按此速度需要约 11 天，且中途 OOM 重启过两次、无断点续跑。优化分四步：第一步换成按 token 组批的专用服务，批 token 上限按最长切片压测确定，吞吐升到 26 条/秒；第二步在灌库侧按切片长度排序后再分批投递，把 padding 浪费从抽样统计的 71% 压到 9%，吞吐升到 41 条/秒；第三步权重切 FP16 并把最大长度从模型上限 8192 收到语料 P99 的 640，吞吐升到 58 条/秒；第四步用 4 个并发进程灌库并加上按批次的断点记录，整体稳定在约 49 条/秒（单进程略降但总量提升），最终 19 小时跑完，全程无人工干预。同一张卡、同一个模型，端到端提速约 13 倍，唯一的改动是"怎么组批"和"补到多长"。
Embedding 服务的性能问题，九成能用一句话诊断：你在为多少 padding 付钱？抽样统计一下"批内真实 token 数 ÷（批大小 × 批内最大长度）"，这个比值低于 0.5 就说明一半的钱在乘零。

五、Rerank 的成本结构与延迟预算

Rerank 用的是 Cross-Encoder（交叉编码器）：把 query 和候选文档拼成一条序列送进同一个编码器，让 query 的每个 token 与 doc 的每个 token 在所有层里全交叉注意，最后从分类位置投影出一个相关性分数。这与 Embedding 用的 Bi-Encoder（双塔）形成鲜明对比——双塔把 query 与 doc 各自独立编码成向量，因此文档向量可以离线预计算、检索时只做向量点积，代价是把一整段文本压进单个向量造成信息瓶颈，无法建模跨 token 的交互、否定与数值比较。

交叉注意力带来了质量跃升：把 Cross-Encoder 放在召回与上下文注入之间，公开报告的收益大致是 precision@5 提升 10%~30%，或 NDCG@10 提升 10~25 个点。但它的成本结构也因此完全不同：文档表示依赖于 query，所以没有任何东西可以离线预计算、也没有任何东西可以跨查询复用。K 个候选就是 K 次前向，一次都省不掉。

两阶段检索漏斗与延迟归属 Query │ ▼ ┌───────────────────────────────────────────────────────────┐ │ 阶段一 · 广召回：BM25 + HNSW 稠密向量 │ │ 百万级文档库 → 取 TopK 候选（K = 50~100） │ │ 延迟 10~25ms，成本近似与 K 无关（ANN 检索） │ └───────────────────────┬───────────────────────────────────┘ │ K 个 (query, doc) 对 ▼ ┌───────────────────────────────────────────────────────────┐ │ 阶段二 · 精排：Cross-Encoder 全交叉注意力 │ │ 逐对前向，成本 ≈ K × f(Lq + Ld)，且对长度是二次关系 │ │ → 取 TopN（N = 3~10） │ │ 延迟 25~90ms（K=100，合理模型与截断） │ │ 但配置错误时可达 300~400ms（大模型 + 小 batch 串行） │ └───────────────────────┬───────────────────────────────────┘ │ ▼ LLM 上下文注入 → Prefill → 首 token 两个旋钮：K 决定要跑几次前向，截断长度决定每次前向多贵 K 与截断长度共同决定 Rerank 在延迟预算里占多大一块

计算量对序列长度是二次关系（全交叉注意力的复杂度正比于 query 与 doc 长度之和的平方），所以放开候选块长度是最贵的错误——让 2048 token 的长块直接进 Rerank 会造成延迟尖峰。生产架构普遍强制截断，只把每个候选块的前 256~384 token 送进模型；依据是在绝大多数常规 RAG 语料里，相关性信号集中在前 300 token 左右。若候选块确实很长，做法是切成子段分别打分再取最大值聚合，而不是整段硬塞。

候选数 K 与批处理方式：延迟预算的两个主旋钮

K 的经验区间是 50~100。把 K 提到 150 以上，尾延迟明显上升而召回收益已经边际趋零；生产里常见的浪费是"K 当年拍了个数就再没复核过"，实际在为评测集根本不需要的两倍算力付钱。另一个更隐蔽的浪费是批处理方式：如果对 K=100 用批大小 8 串行调用，就是 13 个往返，而每次调用的固定开销（分词、数据传输、内核启动）会被重复支付 13 次。有分析给出的量化模型是"(K/8) × 15ms 固定开销 + K × 单文档成本"，在 K=100 时约 265ms，而同样的工作合成一次整批调用只需付一次固定开销。实践反馈是：把串行小批合并为单次全量批调用，可以把 Rerank 总耗时削掉 50%~65%，不换模型、不损精度。

生产案例：Rerank 吃掉半个延迟预算的修复过程。某企业内部搜索的检索段 P95 目标是 700ms，上线后实测 P95 约 940ms，其中 Rerank 一项占 380ms。排查发现三个问题叠加：K 被设成 200（当年拍的数，从未复核）、候选块未截断（平均约 1100 token 直接送进模型）、客户端按批大小 8 串行调用 Rerank 服务（25 个往返）。修复按代价从低到高做：先把串行小批合并为单次整批调用，Rerank 降到 210ms；再把候选块截断到 384 token，降到 132ms；最后把 K 从 200 降到 80，降到 71ms。三步做完检索段 P95 落到 590ms，同时用离线评测集验证 NDCG@10 仅下降 0.4 个点（K 从 200 到 80 的影响），完全在可接受范围。整个过程没有更换模型、没有加卡、没有改动检索算法。

分数不能配固定阈值

Cross-Encoder 输出的是一个标量分数，训练目标不同的模型输出可能是无界 logit 也可能是经过 sigmoid 的概率。工程上最常见的错误是配一个全局固定阈值（例如丢弃所有分数低于 0.7 的候选）。这会失效，原因有三：长而具体的多约束 query 得到的原始分数系统性偏低，即使文档是精确匹配；域外词汇会整体平移分类位置的激活分布，造成 logit 压缩；不同模型的损失函数不同，有的原始 logit 中心在负值区间。可用的替代策略是相对口径：按与首位分数的差值做边界过滤、在每个查询的候选池内做最小最大归一化后再切、或按相邻排名的分差找"断崖"动态定 N。TopK 与候选数的整体权衡逻辑可参考《TopK 策略》。

Rerank 的延迟不是模型的属性，是配置的属性。同一个 bge-reranker 在 K=200、不截断、批大小 8 串行下要 380ms，在 K=80、截断 384、整批一次调用下只要 71ms。先把这三个旋钮拧对，再考虑换模型或加卡。

六、部署形态、共卡取舍与容量核算

GPU 还是 CPU：分界线在哪

Embedding 与 Rerank 模型小到可以在 CPU 上跑，这让"要不要买卡"成为一个真问题。参考数据能给出量级感：在最大输入长度 256 token 的条件下，某 GPU 部署在批大小 128 时达到约 57 文档/秒，而同期 4 核 CPU 只有约 2.45 样本/秒，差距约 23 倍；把 CPU 侧从 PyTorch 换成 ONNX Runtime 并做图优化，可提升到约 3.125 文档/秒（约 27% 增益），但量级不变。另一组在 16 核/32 线程普通服务器上的实测显示，把推理路径从 SentenceTransformers 改成精心调优的 ONNX 路径，平均提速约 14 倍——从 5~11 文档/秒提升到 70~230 文档/秒区间，说明 CPU 上的优化空间远比多数人以为的大，关键在于避开 padding 税与线程自旋这两个反模式。

与主 LLM 共卡还是独立部署

共卡的诱惑是显而易见的：Embedding 与 Rerank 模型加起来可能只占两三 GB 显存，专门为它们留一张卡看着很浪费。但共卡引入两个真实风险。第一是显存争用：生成引擎通常按一个显存利用率上限预占大块显存做 KV Cache 池，剩余空间是否够放 Encoder 模型的权重与激活，必须按峰值批量算，而不是按空载算。第二是优先级倒挂：Rerank 在请求路径上、对尾延迟极敏感，而生成侧一个大 batch 的 Prefill 会瞬间抢满算力，导致 Rerank 的 P99 出现无法解释的尖峰——这类抖动排查起来非常痛苦，因为两个服务的监控通常是分开看的。

容量规划与成本核算

容量规划的常见错误是只按 QPS 算。Embedding 与 Rerank 的容量要按"token 吞吐"和"pair 吞吐"两个口径分别算，因为这两个才是真正的成本单位。

核算项怎么估易错点
灌库总量切片数 × 平均切片 token 数 ÷ 实测 token 吞吐用模型最大长度而不是语料 P99 长度估算，结果虚高数倍
在线编码容量峰值 QPS × 每查询 token 数，按 P99 留 2~3 倍余量忘记多语言或长查询会拉高平均长度
Rerank 容量峰值 QPS × K，与实测 pair/s 对比按"请求数"而非"pair 数"估算，低估 K 倍
显存权重（FP16 下约参数量 × 2 字节）+ 峰值批激活只算权重不算激活，大批量时 OOM
单位成本卡时成本 ÷（实测吞吐 × 3600）用理论吞吐算成本，实际账单翻倍
队列健康度监控服务端排队深度与等待时长只看 GPU 利用率，看不到请求在队列里堆积

成本感上有个有用的参照：不同排序范式的每百万查询成本相差极大——稠密双塔约在最低档，后交互（ColBERT 类）与 Cross-Encoder 高一个档位但仍在可控范围，而用大模型直接做排序会再高一到两个数量级，同时延迟进入秒级。这解释了为什么"两阶段"结构如此稳定：用最便宜的方式广召回，只对少量候选付昂贵的精排费用，把最贵的生成能力留给最后一步。

  • 离线灌库与在线服务各用一套配置，不要共用一份参数
  • 按 token 组批而非条数组批，入批前按长度排序分桶
  • Rerank 候选块强制截断到 256~384 token，超长块切子段取最大值
  • K 控制在 50~100，并定期用离线评测集复核这个值
  • 对 K 个候选做单次整批调用，不要按小批串行请求
  • Rerank 分数用相对边界或池内归一化，不配固定阈值
  • 监控排队深度与等待时长，而不只看加速器利用率
  • 换模型时把池化方式纳入回归检查清单
  • 不要用 FastAPI 加 Transformers 的串行脚本上生产
  • 不要把 max_length 直接设成模型上限（如 8192）去跑短文本
  • 不要指望 KV Cache、前缀缓存、投机解码对 Embedding 有收益
  • 不要把 90 亿参数级别的 Rerank 模型放在同步请求路径上
  • 不要为了省延迟就一路换更小的 Rerank 模型，精度掉得更快
  • 不要让在线 Rerank 与生成模型共卡后不做优先级与超时保护
  • 不要按请求数估算 Rerank 容量，它的成本单位是 pair 数
  • 不要在时间窗聚批时忽略窗口本身就是延迟下限
Embedding 与 Rerank 的部署优化，几乎全是"别为空气付钱"：别为 padding 付钱，别为重复的固定开销付钱，别为用不上的候选付钱，别为模型上限那段永远填不满的长度付钱。把这四笔浪费掐掉，大多数团队根本不需要加卡。

Q&A

为什么 Embedding 服务不能直接沿用生成模型的那套优化？

因为推理结构不同。Embedding 模型是 Encoder-only 架构，输入整段文本、所有 token 双向互注意、一次前向加一次池化就输出定长向量，全程没有自回归。生成模型的核心优化基本围绕自回归展开：KV Cache 分页管理是为了省下逐步重算历史注意力的开销，跨请求前缀缓存是为了复用共享的 System Prompt，投机解码是为了减少解码步数——这三项在 Encoder 上都无从发挥。真正对 Embedding 有效的是另一组：按 token 总量动态组批、入批前长度排序分桶、动态 padding 只补到批内最长、以及权重低精度量化。连续批处理仍然有用，但理由变成了"请求可以自由加入和离开批次"，这恰好匹配离线批量与在线单条并存的双峰流量。

TEI、Infinity 和 vLLM 的 embedding 模式该怎么选？

按三步顺序判断，基本不会错。第一步：如果已经在运维 vLLM 且显存有余量，就用同一个引擎顺带服务 Embedding，直接少部署一个组件、少一套监控和扩缩容——除非你的模型在它的池化任务支持里不是一等公民，小型 Encoder 模型的支持程度确实不如解码器类模型。第二步：如果 Embedding（可能加上 Rerank）就是全部工作，选 TEI，它是 Rust 实现的专用服务，足迹最小、启动最快，池化方式支持最全，包括学习式稀疏检索需要的 SPLADE。第三步：如果链路里模型种类多——Rerank、ColBERT 后交互、文档图像检索、图文音多模态——选 Infinity，一个 API 管住整个模型动物园胜过维护三套部署。只有当两个方案都过线时，才需要打开基准数据破平局，因为配置正确的两个专用服务之间的差距，远小于任一个与朴素串行循环之间的差距。

什么是 padding 税，为什么有时"不组批"反而更快？

一批混合长度的文本会把每一行都补齐到批内最长那一行，模型随后做的计算量正比于批大小乘以批内最大长度乘以隐藏维度，与批里有多少真实内容无关，这部分为补位符做的无效计算就是 padding 税。真实文本长度方差很大，八条随机文本里可能有一条 60 token 的离群值和七条 8 token 的短句，此时批的算力有七成以上花在把 padding 和注意力权重相乘上。逐条推理的计算量严格正比于该条的真实 token 数，所以在长度方差足够大时它反而比盲目组批更省算力。但正解不是放弃组批，而是组批前先按长度排序分桶、再用动态 padding 只补到批内最长；在重排场景里，这一步可以削减最多约 40% 的冗余计算。判断自己有没有交这笔税，可以抽样统计"批内真实 token 数 ÷（批大小 × 批内最大长度）"，比值低于 0.5 就说明一半的算力在乘零。

Rerank 为什么比 Embedding 贵得多？

因为它没有任何东西可以预计算或复用。Embedding 是双塔结构，query 和文档各自独立编码，所以文档向量可以离线算好存进向量库，在线只做向量点积，成本几乎与库大小无关。Cross-Encoder 把 query 和候选文档拼成一条序列送进同一个编码器做全交叉注意，文档的表示依赖于当前 query，因此既不能离线预计算也不能跨查询缓存——K 个候选就是 K 次完整前向，一次都省不掉。更进一步，全交叉注意力的计算量对 query 与文档长度之和是二次关系，所以候选块越长成本上升越快。代价换来的是质量：把 Cross-Encoder 放在召回与上下文注入之间，precision@5 通常有 10% 到 30% 的提升。工程上的应对就是两阶段结构：用便宜的方式广召回，只对 50 到 100 个候选付昂贵的精排费用。

候选数 K 和 TopN 怎么定，它们如何共同决定延迟？

K 决定要跑几次 Cross-Encoder 前向，是延迟的主旋钮；截断长度决定每次前向多贵，是第二个旋钮；TopN 只影响送进大模型的上下文长度，对 Rerank 本身的延迟没有影响。经验区间是 K 取 50 到 100、N 取 3 到 10。K 超过 150 之后尾延迟明显上升而召回收益已边际趋零，所以生产里常见的浪费就是"K 当年拍了个数从未复核"，实际在为评测集不需要的算力付双倍钱。定 K 的正确方法是用离线评测集扫一遍：从 K=200 往下降，观察 NDCG@10 或 recall 的下降幅度，找到那个"再降就明显掉点"的位置。实践中从 200 降到 80 常常只损失不到半个点，却能把 Rerank 延迟砍掉一半以上。TopN 则要与上下文预算和"中间信息丢失"效应一起权衡，塞太多反而降低生成质量。

Rerank 服务的延迟超预算了，第一步该改什么？

先改批处理方式，这是代价最低、收益最大的一步。如果客户端在用小批（比如 8 个一批）串行调用 Rerank 服务，那么 K=100 意味着 13 个往返，而分词、数据传输、内核启动这些固定开销会被重复支付 13 次。把它们合并成一次全量批调用，只付一次固定开销，实践反馈可以把 Rerank 总耗时削掉 50% 到 65%，不换模型也不损失任何精度。第二步是把候选块截断到 256 到 384 token，因为绝大多数常规语料的相关性信号集中在前 300 token 左右，而计算量对长度是二次关系。第三步才是复核 K 值，用离线评测集确认能降到多少。最后才考虑量化服务、换更快的同级模型或加卡。特别不建议一开始就换更小的 Rerank 模型——交叉注意力的信号在模型容量低于某个门槛后会非线性退化，精度掉得比延迟降得更快，最终得到一个又快又差、不值得留在请求路径上的组件。

Embedding 和 Rerank 能不能和主 LLM 共用一张卡？

分场景。离线灌库很适合共卡，它是可抢占、可重跑的吞吐型任务，正好能吃掉生成侧的空闲算力，只要加上限流或只在业务低峰窗口跑，并做好断点续跑。在线 Rerank 则尽量不要与生成共卡，原因是两个风险：一是显存争用，生成引擎通常按显存利用率上限预占大块空间做 KV Cache 池，剩余空间够不够放 Encoder 的权重与峰值激活必须按峰值批量算而不是空载算；二是优先级倒挂，生成侧一个大 batch 的 Prefill 会瞬间抢满算力，导致处在请求路径上的 Rerank 出现无法解释的 P99 尖峰，而两个服务的监控通常分开看，这类抖动排查极其痛苦。折中方案是同机分卡：同一节点不同卡，既有算力隔离又没有网络往返，Encoder 卡的空闲再用离线灌库任务填满。

Embedding 部署到底该用 GPU 还是 CPU？

看负载类型而不是看模型大小。百万级以上语料的灌库应该上 GPU：这是纯吞吐型任务，公开测算里同一模型在 GPU 上大批量推理与几核 CPU 的差距在一个数量级以上（某组对照是约 57 文档/秒对约 2.45 样本/秒）。在线查询编码则完全可以放 CPU，因为单条编码本身就在 5 到 15ms 量级，QPS 不高时没必要占一张卡；关键是要用 ONNX Runtime 这类做过图优化的路径，并避开两个反模式——盲目组批带来的 padding 税，以及推理库内部线程池的忙等自旋在"多并发小请求"模式下把 CPU 占满却不干活。有实测显示，把 CPU 推理路径从 SentenceTransformers 换成精心调优的 ONNX 路径可以平均提速十几倍。在线 Rerank 建议上 GPU，即使模型很小，因为 K 次前向在同步请求路径上，CPU 的尾延迟不好控；只有 2000 万参数级别的超轻量 Rerank 模型才适合 CPU 或 Serverless。

为什么不能给 Rerank 分数配一个固定阈值？

因为 Cross-Encoder 的分数不是校准过的概率。训练目标不同的模型输出可能是无界 logit，也可能是过了 sigmoid 的 0 到 1 值，两者不可比。即使在同一个模型内，分数也会系统性漂移：长而具体的多约束查询得到的原始分数明显偏低，即使文档是精确匹配；域外词汇会整体平移分类位置的激活分布造成 logit 压缩；不同模型的损失函数差异会让原始 logit 的中心落在完全不同的区间。所以配一个"低于 0.7 就丢弃"的全局阈值，实际效果是在某些查询上把好文档全丢掉、在另一些查询上一条都不过滤。可用的替代是相对口径：按与首位分数的差值做边界过滤、在每个查询的候选池内做最小最大归一化后再切、或者按相邻排名的分差找断崖来动态决定保留几条。这些方法的共同点是只比较同一次查询内部的分数，从而绕开跨查询的校准漂移。

灌库跑得太慢，优化的优先顺序是什么？

按收益从大到小依次是：换成会组批的专用服务、长度排序分桶、收紧最大长度、低精度权重、多进程并发。第一步最关键——用 FastAPI 加 Transformers 逐条调用的脚本会让加速器大部分算力空转，换成按 token 总量组批的专用服务通常能带来数倍提升。第二步是在灌库侧按切片长度排序后再分批投递，让相近长度的文本进同一批，把 padding 浪费从常见的七成压到一成以内。第三步是把 max_length 从模型上限（可能是 8192）收到语料实际长度的 P99（可能只有几百），这一步经常被忽略却收益巨大，因为计算量与长度直接相关。第四步是权重切 FP16 或 INT8。第五步才是多进程并发灌，同时一定要加按批次的断点记录——灌库跑几小时到几天，中途 OOM 或网络抖动不可避免，没有断点续跑就要从头再来。这五步做完，同一张卡同一个模型端到端提速十倍以上是常见结果。
