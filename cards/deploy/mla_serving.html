DP22 · MLA 推理服务

packed latent 的缓存形态 / FlashMLA 与 FlashInfer 后端 / prefix cache 不兼容点 / 与 PD 分离和 FP8 KV 的叠加 / 何时不要开

MLA 在训练时把多头 KV 压进一条低维潜向量；服务时你缓存的是这条 packed 流，不是 GQA 那套「按头分页」。把 GQA 的前缀复用假设原封搬过来，轻则前缀缓存被框架关掉，重则静默算错位置。

MHA / MQA / GQA / MLA 的数学对比见 T20 与 T21；KV 显存公式与量化见 DP08、DP09；PD 分离见 DP12。本卡从「模型已经是 MLA，要在 vLLM / SGLang 上跑」接着往下。

一、服务侧要记住：缓存的是 packed latent 不是每头 KV

MLA（Multi-Head Latent Attention）推理时缓存低维潜向量，需要时再吸收权重展开。GQA 的分页假设是「物理上按 KV 头切开」；MLA 是「一条 packed 流对应很多逻辑 query 头」。前缀复用、跨请求共享、PD 之间传 KV，都要按 packed 流来设计，不能按头 scatter/gather。

GQA 服务假设MLA 服务假设
缓存对象每组 KV 头的向量packed latent（+ 少量 RoPE 相关分量）
前缀复用头对齐即可拼接不能拆 packed 流；位置要用 query 侧 RoPE 修补
显存账跟 kv_heads 成正比跟 latent 维成正比，与逻辑头数基本解耦
不要按头切开再拼回来 GQA: [h0 KV][h1 KV]... → 按头 page → 前缀命中按头复用 MLA: [c_latent | rope_extra] → 整条流进 page 逻辑头在计算时展开，物理缓存始终 packed 拆开会引入额外 TP 同步，把 MLA 的省显存吃掉

MLA 省的是缓存宽度。服务代码若把 latent 展开成满头 KV 再存，等于把论文里的收益在第一公里还回去。

二、后端选型：FlashMLA / FlashInfer / Triton

vLLM / SGLang 在 MLA 上有多套 kernel 后端。默认策略随 GPU 代数变：Hopper / Blackwell 走 FlashMLA 或 FlashInfer，带 FP8 KV；需要 batch invariant 或某些 Triton 路径时，框架可能主动关掉 prefix caching。这不是配置笔误，是内核还不支持「不变性 + 前缀」同时成立。

后端更适合服务时注意
FlashMLAHopper/Blackwell 上的 DeepSeek 系与 FP8 KV、CUDA Graph 组合前要看发行说明
FlashInfer MLA要 FP8 / NVFP4 KV 的路径与 batch invariant 同时开可能禁 prefix
Triton MLA兼容与调试同样可能禁 prefix；不要当生产默认
引用：vLLM 文档在 TRITON_MLA / FLASHINFER 遇上 batch invariant 时会 warning 并关闭 prefix caching。把它当故障而不是提示，会浪费一晚上查「为什么命中率是 0」。

先看启动日志里 prefix cache 有没有被禁用，再谈命中率。被禁用时调 block size 没有用。

三、Prefix Cache 何时必须关

GQA 上「系统提示很长就开前缀缓存」几乎总是对的。MLA 上多三条关闭条件：

  1. 当前 backend + 不变性标志组合不支持（上一节）。
  2. 请求之间「相同 token 前缀」其实带着不同的 RoPE 绝对位置（文档插入位置不同），packed 流不能当普通前缀拼。
  3. 多 LoRA / 多适配器（DP23）：键必须含 adapter 身份，否则会把别人的 latent 当自己的前缀。
位置修补（概念，不是让你手写 kernel） 离线：不可变文档在规范位置 0 编成 MLA 工件 在线：query 侧 RoPE 把文档「搬」到请求中的位置 少量 global 头 / 保护行当场重算 packed latent 始终不拆 做不到上述修补时：关掉跨请求前缀，只保留本请求内的常规 KV
场景前缀缓存理由
固定系统提示、短对话开位置稳定，命中干净
RAG 把不同文档插到不同偏移默认关或走专用工件方案绝对位置变了
batch invariant 打开做复现跟框架走，常为关内核限制

MLA 的前缀复用是「带位置修补的工件复用」，不是「token 相等就能 memcpy」。

四、与 PD 分离、量化的组合

PD 分离要在节点间传 KV。传满头 KV 和传 packed latent，带宽账差一个数量级，这正是 MLA 在长上下文集群里值钱的地方。但接收端必须是同一套 MLA 布局：prefill 实例展开成 GQA 页再发给 decode，是常见的自残。

组合通常可叠加先验证的回归
MLA + FP8 KV是，Hopper 默认方向长上下文质量；不是所有 backend 都齐
MLA + 权重量化 AWQ看发行版吸收权重与量化核是否同一套
MLA + PD 分离是，且更划算传输形态必须是 latent 不是展开 KV
MLA + 投机解码谨慎草稿模型是否同架构；接受率可能掉
PD 之间传什么 正确： Prefill ── packed latent 页 ──► Decode 错误： Prefill ── 展开成 GQA 头 ──► Decode （带宽和布局一起毁） 接收端必须是同一套 MLA page 语义 不要在传输边界「为了兼容旧 decode」做一次 scatter
示例场景：把 DeepSeek 系从单机 GQA 思维迁到 MLA 集群时，KV 传输仍按「每 token 数百 KB」规划链路。换成 packed latent 后，跨节点 KV 流量下降一个数量级，decode 池才能按 DP12 的 xPyD 配比扩。此前的瓶颈其实是传输格式，不是 GPU。
示例场景：评测环境打开 batch invariant 做复现，生产却按「系统提示很长，prefix 命中率该有 40%」做容量。上线后命中率一直是 0，TTFT 比压测差一截。查启动日志才发现 FlashInfer MLA 路径已经 warning 并关闭前缀。关掉 invariant、换回支持前缀的后端后命中恢复。那一晚调 block size 完全没有用。

PD 分离的带宽预算要用 MLA 的每 token 字节，不要用同参数量 GQA 模型的经验数。

五、接受率以外的两个服务指标

投机解码看接受率（DP21）。MLA 服务另外两个数更常翻车：prefix 命中率（被框架静默关掉时是 0）和 prefill 小算子时间（RoPE、拼接、吸收，未融合时会把 TTFT 吃掉）。DP18 提过把 MLA 前处理 13 个小算子融成一个后，该段从 109ms 到 45ms 量级的国产栈案例——含义是：MLA 的服务收益经常不在注意力核本身，而在别把展开/融合做砸。

指标异常长什么样先查
prefix hit一直是 0日志是否 disable prefix；键是否含 LoRA
TTFT短请求也很慢前处理是否融合；chunked prefill 是否误伤
显存并不比 GQA 省是否展开后存储；kv dtype 是否仍 FP16

六、默认策略与关闭条件

选框架官方的 MLA 后端，读启动 warning。

PD 传 packed latent；显存账用 latent 维。

系统提示稳定时开前缀；文档偏移变化时关或走专用工件。

不要为了「看着像 GQA」把 latent 展开入库。

不要在 Triton 调试后端上对 prefix 命中率做容量规划。

不要假设投机解码与 MLA 默认正交，要单独测接受率。

什么时候不要为 MLA 做专项：模型本身是 GQA/MQA。硬上 MLA 服务路径没有收益。非 DeepSeek 系却「想省 KV」时，先量化与 GQA，而不是假装 MLA。

容量规划用「每 token latent 字节 × 层数 × 并发 × 精度」而不是隐藏维度。DP02 的 GQA 表不能直接套。测 TTFT 时把前处理融合前后分开记，否则会把 kernel 问题和搬运问题混成一笔。

升级框架版本后第一件事是读 changelog 里 MLA backend 与 prefix 的互斥项，而不是先开更大的 max_num_seqs。MLA 路径的静默关闭比 OOM 更难发现。

七、延伸阅读

原理对照 T20、DP08、DP12。投机解码叠加见 DP21。多适配器键空间见 DP23。

具体 --speculative-* / MLA backend 开关以 vLLM、SGLang 当期发行说明为准，本卡只固定「packed 不拆、前缀可能被静默关掉」这两条不变量。

Q&A

T20 已经讲了 MLA，为什么还要服务卡？
T20 讲为什么省显存、和 GQA 差在压缩而不是少头。服务卡讲缓存布局、前缀键、后端互斥、PD 传输形态。把原理卡里的压缩比直接当集群带宽规划，会在展开存储或错误前缀上把比还回去。
为什么 batch invariant 会关掉 prefix cache？
复现性要求同一 batch 的数值路径稳定。某些 MLA 后端的前缀路径与这条约束还没同时被证明。框架选择关掉前缀而不是输出不可复现的 logits。要复现评测就接受无前缀；要吞吐就把 invariant 关掉，不要两者都要又假装命中率还在。
MLA 能不能当普通 PagedAttention 用？
页还可以是页，页里装的东西变了。调度器仍按 block 管显存，但 block 的语义是 latent 条而不是头切片。用错 layout 的自定义 kernel 是第一事故源。
长上下文 RAG 为什么前缀命中很差？
每次检索插入的文档内容和位置都变，token 前缀并不相等，RoPE 位置也不等。这时该优化检索与缓存文档工件，而不是调 prefix 参数。硬开会命中错误前缀或命中率为 0。
FP8 KV 和 MLA 谁先开？
先保证 MLA 后端在该卡型上稳定出正确 logits，再开 FP8 KV，再谈前缀。量化会掩盖布局错误，变成「又快又错」。质量回归集要含长上下文，不只是短指令。
和 DP21 投机解码如何叠加？
草稿模型最好与目标同为 MLA 或明确支持的混合。接受率掉就按 DP21 缩短草稿，而不是关 MLA。两者都吃显存时，先保目标模型的 latent 缓存，草稿用更轻的方案。
国产栈上 MLA 要注意什么？
前处理小算子未融合时 TTFT 会很难看，这和 GPU 代数无关。优先查融合和内存往返次数，再怪「MLA 不适合这张卡」。口径对齐仍用 latent 每 token 字节，不要用 CUDA 博客里的 GQA 表。
chunked prefill 和 MLA 前缀一起开会怎样？
短请求通常没问题。超长 prefill 被切块时，要确认每块写回的仍是 packed latent 布局。若切块实现按头 scatter，命中率与正确性会一起坏。先用框架默认，不要自己改切块对齐。
MLA 模型能量化后再开前缀吗？
可以，但键必须含 kv dtype 与量化方案。FP16 前缀不能当 FP8 用。换量化档等于换缓存世界，旧前缀作废。
