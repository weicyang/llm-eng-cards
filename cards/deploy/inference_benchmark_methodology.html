传统 Web 压测里，一次请求的工作量基本是常数，所以 QPS 就够用了。LLM 打破了这个前提：同一个接口，一个请求吐 20 个 token，另一个吐 2000 个，工作量差 100 倍。压测 LLM 的本质，是把"每秒多少请求"换成"每秒多少 token，并且第一个字多久出来、后面吐字有多稳"。

一、为什么 LLM 压测不能照搬 QPS 压测

做过 Web 服务压测的工程师第一次压 LLM 服务，几乎都会掉进同一个坑：拿 JMeter 或 k6 打一轮，看到 QPS 数字很好看就下结论"这台机器能扛 200 并发"，上线当天尾延迟就炸了。原因不是工具不好，而是QPS 这个指标在 LLM 场景下不再是充分统计量。传统压测建立在三个隐含假设上：单请求工作量近似恒定、响应是一次性返回的、请求之间互不干扰。LLM 推理把这三条全部推翻了。

差异一：单请求工作量可变，且变化幅度是量级级别

一个电商搜索接口，无论查什么关键词，返回的都是 20 条结果，服务端做的功基本一样，所以"每秒处理 200 个请求"是一句有意义的话。LLM 不是：用户问"今天几号"可能只生成 8 个 token，问"帮我写一份季度复盘"可能生成 1500 个 token。生成阶段是逐 token 串行的，工作量与输出长度近似成正比，两个请求之间可以差近 200 倍。这意味着相同的 QPS 可以对应完全不同的实际负载，QPS 达标不代表系统不过载。所以 LLM 压测的第一指标是 token 吞吐（每秒生成多少个 token），QPS 只能作为业务侧的辅助口径。

差异二：流式输出让"单一延迟"失去意义

绝大多数 LLM 应用都开着流式返回，用户体验被拆成了两段完全不同的感受：等待感（点了发送之后要盯着光标闪多久）和阅读感（开始出字之后，吐字速度跟不跟得上眼睛）。这两段由不同的系统机制决定——前者取决于排队和 Prefill（预填充，一次性并行处理全部输入 token），后者取决于 Decode（逐 token 生成，受显存带宽约束）。用一个"平均响应时间"把两者揉在一起，等于把两个独立的故障域压成一个数字，出问题时根本定位不到是排队慢还是解码慢。

差异三：请求在 GPU 上互相"抢座位"

现代推理引擎用连续批处理（Continuous Batching，每个解码步都允许完成的请求退出、新请求插入）把多个请求塞进同一个 batch 一起前向。好处是吞吐大涨，代价是请求之间不再隔离：你这条请求的 TPOT，取决于同一 batch 里还有多少个"邻居"以及它们要吐多久。一个 4000 token 的长文生成请求会占住 batch slot 和 KV Cache 好几十秒，期间所有和它同批的短请求都被拖慢。传统压测里"单请求延迟"是个体属性，LLM 压测里它是群体属性——这就是为什么 LLM 服务的 P99 对流量成分极度敏感。

二、核心指标体系：TTFT、TPOT 与 ITL

指标定义是整个压测方法论的地基，也是最容易被含糊带过的部分。NVIDIA 在其 LLM 压测指南里给出了一句非常关键的提醒：各家工具对同名指标的实现口径并不一致，只有当定义对齐时结果才可比。所以下面每个指标都给出测量点和公式，而不只是中文名字。

TTFT：首 token 延迟

TTFT（Time To First Token）指从客户端发出请求，到收到第一个非空 token 的时间。它不是纯粹的模型指标——它包含了排队等待、Prefill 计算、网络往返三部分。输入越长，注意力机制要为整段输入构建 KV Cache，TTFT 就越大；系统越拥挤，排队分量就越大。这也是 TTFT 作为告警指标特别灵敏的原因：它同时反映模型效率和调度压力。工程上有个细节容易踩坑——有些服务会先返回一个空 chunk 或角色标记，NVIDIA AIPerf 会显式丢弃无内容的首个响应，否则 TTFT 会被记成一个毫无意义的极小值。

ITL 与 TPOT：看起来一样，其实不是同一个东西

ITL（Inter-Token Latency）是相邻两次流式响应之间的时间间隔，一个请求会产生很多个 ITL 采样点，最后跨请求聚合。TPOT（Time Per Output Token）则是每个请求算一个值，公式是把首 token 之后的全部时间摊到剩余 token 上：

TPOT = (端到端延迟 − TTFT) / (输出 token 数 − 1)

分母减一，是为了让这个指标只刻画解码阶段，不把 Prefill 混进来。在标准逐 token 解码下，一次流式响应通常只含一个 token，此时 ITL 和 TPOT 数值非常接近——这就是很多人误以为它们是同义词的原因。一旦引入投机解码（Speculative Decoding），两者立刻分道扬镳：投机解码一个引擎步可以一次性吐出多个被接受的草稿 token，打包在同一个流式响应里。ITL 只记录响应与响应之间的间隔，不会为同一响应内的多个 token 补上"零间隔"采样；TPOT 则把解码总时间平摊到每一个 token 上。

vLLM 官方文档给了一个极清晰的例子：某请求观测到两个 40ms 的 ITL 采样，其中第二次响应一口气带回了 3 个 token。此时平均 ITL 是 40ms，而 TPOT = (180ms − 100ms) / (5 − 1) = 20ms/token。两个指标差了整整一倍。如果只看 ITL，你会得出"开了投机解码反而变慢"的错误结论；只有 TPOT 才如实反映用户实际感受到的吐字速度。

三种吞吐口径不要混用

"吞吐"这个词在 LLM 压测里至少指三样东西，报告里不写清楚就没法比较。输出 token 吞吐只统计生成的 token，是衡量 Decode 阶段产能的核心指标；总 token 吞吐把输入 token 也算进去，能反映 Prefill 侧的压力，在长输入短输出的 RAG/摘要场景下这个数会显著高于前者；请求吞吐（RPS）则是业务侧最关心的口径。还有一个常被忽略的第四类：单用户 TPS，等于该请求的输出长度除以端到端延迟，随着输出变长会渐近于 1/ITL。

吞吐口径定义随并发上升的走向主要用途

总 token 吞吐(输入 + 输出) token / 窗口时长同上，长输入场景数值更高评估 Prefill 压力

💡 知识要点：系统总吞吐和单用户体验是反向的。并发从 1 加到 64，总 token/s 一路涨，但每个用户感受到的吐字速度一路降。压测报告只报总吞吐等于只讲了一半故事——必须同时给出该并发档位下的 P95 TTFT 与 P95 TPOT，读者才知道这个吞吐是在什么体验代价下取得的。

成功率与错误分类同样是压测指标

高并发下推理服务会以几种不同方式"失败"，而它们的含义完全不同，报一个笼统的成功率会掩盖问题。请求被引擎队列拒绝（如返回 503）说明并发超过了配置上限，属于容量问题；请求超时说明系统已经过饱和，排队时间超过了客户端耐心；输出被截断（达到 max_tokens 而非自然 EOS）会让 token 统计失真；而 OOM 类错误则直接指向 KV Cache 配置不当。压测报告里应当分类统计这四类，而不是合并成一个百分比。

把三个核心指标对应到用户的三种抱怨就记住了：TTFT 对应"点了半天没反应"，TPOT/ITL 对应"字一个一个往外蹦"，吞吐对应"这套系统每个月要烧多少钱"。前两个是体验，第三个是成本，压测就是在这两者之间找那条能同时接受的线。

三、压测数据集设计：长度分布决定结论

在 LLM 压测里，数据集不是配角，它和被测系统同等重要。同一个服务，换一套输入输出长度分布，测出来的吞吐可以差好几倍，饱和点也完全不同。原因在第一节已经埋下：工作量与序列长度直接挂钩。所以压测的第一步不是敲命令，而是先把生产流量的长度分布统计出来。

ISL 与 OSL：两个决定一切的变量

ISL（Input Sequence Length，输入序列长度）包括系统指令、对话历史、思维链内容和 RAG 检索到的上下文；OSL（Output Sequence Length，输出序列长度）是模型实际生成的 token 数。ISL 主导 Prefill 的显存与算力开销，进而主导 TTFT；OSL 主导 Decode 期间 KV Cache 的增长和总解码时间，进而主导 ITL 与 e2e。NVIDIA 的压测指南按典型业务给出了这两个量的经验区间，可以作为设计压测集时的起点参照：

注意这四行的"压力偏向"列——它解释了为什么不能用一套压测集给所有业务下结论。摘要类流量把 Prefill 打满时，Decode 单元其实很闲；生成类流量正好相反。一个在生成类负载上表现优异的配置，换到 RAG 负载上可能因为 Prefill 排队而 TTFT 翻倍。

为什么固定长度压测会给出误导性结论

最常见的错误做法是把 ISL 和 OSL 都钉死成一个数（比如统一 512/512）。这样做确实让结果"干净可复现"，但它制造了一个真实世界不存在的理想工况：batch 里所有请求同时开始、同时结束、工作量完全一致。连续批处理调度器在这种负载下几乎不需要做任何困难的决策，KV Cache 占用平稳可预测，没有任何请求会长期霸占 slot。测出来的数字是调度器的"最好一天"。

真实流量的 OSL 是长尾分布：大量 50~200 token 的短回答，加上少量数千 token 的长文。长尾请求会连续几十秒占住一个 batch 槽位并让 KV Cache 持续增长，把同批短请求的 TPOT 一起拖慢，P99 由此被抬起来。固定长度压测完全看不到这个效应，于是产生了经典的"压测很好、上线就崩"。

固定长度 vs 长尾分布：同样的并发，调度压力完全不同 【固定 OSL=512】所有请求整齐进出，KV 占用平稳 slot1 ████████████ ████████████ ████████████ slot2 ████████████ ████████████ ████████████ slot3 ████████████ ████████████ ████████████ └─ 每轮同时退出，新请求整批灌入，调度无压力 【真实长尾】短请求快速轮转，长请求长期霸占槽位 slot1 ██ ██ █ ███ ██ █ ██ ███ █ ██ ██ █ ███ ██ slot2 ███ █ ██ ███ █ ██ █ ███ ██ █ ███ █ ██ █ slot3 ██████████████████████████████████████ ← 4000 tok 长文 └─ 有效并发被长请求吃掉，KV 持续膨胀，短请求 P99 被拖高 结论：固定长度测出的是吞吐上限，长尾分布测出的才是可交付产能

前缀重复率是数据集的第三个属性

除了 ISL/OSL，还有一个经常被漏掉的维度：请求之间的前缀重复率。生产流量里几乎所有请求都共享同一段 System Prompt，多轮对话还共享逐轮累积的历史。开启前缀缓存的引擎在这类流量上 TTFT 会大幅下降。如果压测数据集用了完全随机、互不重复的 prompt，就等于人为关掉了这项优化，结论会低估真实性能；反过来，如果压测集的重复率远高于生产（比如反复发同一条 prompt），结论又会严重高估。压测集的前缀重复率必须与生产对齐，这一点和长度分布同等重要。

数据集来源真实性可复现性获取成本适用阶段

工具层面有两个默认值特别值得警惕。genai-perf 的 --synthetic-input-tokens-mean 默认 550，而 --synthetic-input-tokens-stddev 默认是 0——也就是说不显式设置标准差，你拿到的就是一份固定长度数据集。vLLM 的 random 数据集在固定 --seed（默认 0）下完全可复现，这对回归测试是优点，对容量规划是陷阱。另一个必调项是 ignore_eos：压测时应设为 true，让模型一直生成到 max_tokens 而不是提前遇到 EOS 停止，否则实际 OSL 会远小于设定值，吞吐被高估、TPOT 采样也不足。

典型场景推演：固定长度压测导致的容量误判。某团队为内部文档助手做容量规划，用统一 ISL=512 / OSL=512 的合成集压测，得到"单副本 64 并发下输出吞吐约 2200 token/s、P95 TTFT 约 420ms"，据此按峰值 QPS 折算出 4 个副本即可。上线后实际流量的 OSL 中位数只有 90，但 P95 达到 1400、P99 超过 3500（用户经常让它"完整写一份周报"）。结果是：请求吞吐远高于预期（短答居多），但少量长文请求长期占住槽位，有效并发从 64 掉到约 40，P95 TTFT 涨到 1.3 秒以上，触发前端超时重试，进一步放大负载。改用生产日志回放重测后，同一副本在 SLA 内的可用并发只有 38，需要 7 个副本——比原计划多 75%。这里的教训不是某个数字，而是容量规划必须建立在真实长度分布上，压测集选错，后面所有推导都是错的。具体数值随模型、卡型与引擎版本变化很大，方法论才是可迁移的部分。
压测集就是你对生产流量的一个假设。固定长度等于假设"所有用户问的问题一样长、要的答案一样长"——这个假设一旦写进压测脚本，后面所有漂亮的曲线都只是在验证这个假设，而不是在验证你的系统。

四、吞吐-延迟曲线与饱和点判定

单次压测只能给出一个点，而选型和容量规划需要的是一条曲线：随着负载增加，吞吐怎么涨、延迟怎么恶化、在哪里开始崩。这条曲线怎么跑出来，取决于你用哪种方式加压。

并发数加压 vs 请求速率加压

两种加压模型的行为差别很大。并发数（Concurrency）模型下有 N 个虚拟客户端，每个客户端手上永远有且只有一个在途请求，收到完整响应后立刻发下一个——系统里始终维持 N 个活跃请求，这是一个闭环负载。请求速率（Request Rate）模型下按固定间隔或泊松过程发请求，不管前一个有没有回来，这是开环负载。

NVIDIA 明确建议大多数基准测试优先用并发数模型，理由很实在：在请求速率模型下，一旦到达率超过系统吞吐能力，在途请求数会无界增长，队列越堆越长，你测到的"延迟"主要是排队时间，曲线会直接垂直起飞，得不到任何关于系统能力的信息。并发模型天然自带背压，永远不会把系统压进这种发散状态。

vLLM 的压测脚本把这两种模型组合成了几种实用模式，其中最贴近生产架构的是 --request-rate=inf 配合 --max-concurrency=N：用户侧无限速发送（模拟真实用户不会互相谦让），由网关/负载均衡侧限制最大并发连接——这正是绝大多数线上部署的形态。另外 --burstiness 参数用 Gamma 分布控制到达的抖动程度：1.0 是自然泊松流量，0.1~0.5 制造突发尖峰用于韧性测试，2.0~5.0 制造均匀间隔用于稳定的延迟画像。

压测模式参数组合模拟的现实场景主要用途
最大吞吐--request-rate=inf + 限并发用户全速发送、网关限连接数产能上限、饱和点扫描
真实流量有限速率 + --burstiness=1.0自然泊松到达基线性能画像
突发压力高并发 + --burstiness=0.1~0.5秒杀、推送、热点事件韧性与排队行为

SLA 验证目标速率 + 并发上限设为 SLA 限值生产约束下的合规检查上线前验收

阶梯加压：怎么把曲线跑出来

标准做法是并发数阶梯扫描：从 1 开始，按 1 → 2 → 4 → 8 → 16 → 32 → 64 → 128 的方式倍增（接近拐点时改用更细的步长），每一档跑满足统计量的请求数并记录全套指标。扫描上界应略大于引擎的最大 batch size——超过这个点后多出来的请求只能排队，吞吐不再增长而延迟线性上升，正好把饱和之后的形态也画出来。

上界怎么定不用猜。vLLM 在启动时会打印 KV Cache 的容量信息，形如 GPU KV cache size: 15,728,640 tokens 和 Maximum concurrency for 8,192 tokens per request: 1920。这两行直接告诉你显存能容纳多少并发：容量规划时把 --max-concurrency 设到这个上限的 80~90% 做压测，就是在测"贴近资源约束但不撞墙"的真实状态。

饱和点与 SLA 拐点是两个不同的点

这是压测报告里最容易混淆的一处。饱和点是纯粹的系统属性：GPU 算力或显存带宽被打满，再加并发吞吐也不涨了。SLA 拐点则是业务属性：在满足"P95 TTFT ≤ 800ms 且 P95 TPOT ≤ 50ms"这类约束的前提下，能承受的最大并发。SLA 拐点几乎总是出现在饱和点之前，往往早很多——因为吞吐曲线快压平的时候，延迟早就翻了几倍。

容量规划必须用 SLA 拐点处的吞吐，而不是饱和点的峰值吞吐。用峰值吞吐推副本数，等于默认允许系统长期运行在体验已经崩坏的状态。下面是一次阶梯扫描应当记录的表格骨架（数值为示意，实际结果强烈依赖模型规模、卡型、量化方式与引擎版本）：

五、压测工具选型与实操参数

工具选型的关键分野不是"哪个更强"，而是性能基准测试和负载测试是两件不同的事。NVIDIA 在指南里把这个区分讲得很清楚：负载测试（如 k6）模拟并发流量，用来检验扩缩容、网关、网络与资源上限；性能基准测试（如 AIPerf/genai-perf）在受控条件下测量模型级的吞吐、延迟与 token 级行为。要理解端到端的部署行为，两者必须结合，而不是二选一。

  --dataset-name sharegpt --dataset-path <PATH>/ShareGPT_V3.json \
  --num-prompts 1000 --max-concurrency 64 --seed 42 --save-result

这条命令跑完会输出一份结构化报告，把成功请求数、压测时长、输入/输出 token 总量、请求吞吐、输出 token 吞吐、总 token 吞吐，以及 TTFT / TPOT / ITL 各自的 mean / median / P99 全部分栏列出。三个延迟指标分开报告这件事本身就是方法论的体现——它逼着你去区分"等待"和"吐字"，而不是把它们平均成一个没有物理意义的数。

# 基准线：genai-perf 显式补上预热与长度分布，避免默认值陷阱
genai-perf profile -m <MODEL> --endpoint-type chat --streaming \
  --concurrency 32 --request-count 500 --warmup-request-count 50 \
  --synthetic-input-tokens-mean 1000 --synthetic-input-tokens-stddev 300

六、容量规划与压测陷阱自检

压测的最终交付物不是一堆曲线，而是一句能写进预算表的话："为了在大促峰值下守住 P95 TTFT ≤ 800ms，我们需要 N 个副本、共 M 张卡。"这一节讲怎么从压测数据推到这句话，以及推的过程中最容易翻车的地方。

从 SLA 反推副本数与卡数

推导链路是逐层展开的，每一层都对应一个必须先测出来或先定下来的数：

从 SLA 到 GPU 数量的推导链路 ① 定 SLA P95 TTFT ≤ 800ms，P95 TPOT ≤ 50ms，成功率 ≥ 99.9% │ ② 阶梯压测 ▼ 在真实长度分布数据集上扫并发 找到 SLA 拐点并发 N_sla 与该档位平均 e2e 延迟 L │ ③ 单副本产能 ▼ 闭环负载下的小定律（Little's Law） 单副本可用 QPS = N_sla / L │ ④ 峰值需求 ▼ 取分钟级 P95 峰值，不是日均 所需副本数 = 峰值 QPS / 单副本 QPS × 冗余系数 R │ ⑤ 卡数换算 ▼ 总卡数 = 副本数 × 单副本张量并行度 TP │ ⑥ 校验 ▼ 显存是否装得下：权重 + KV Cache(N_sla × 平均上下文) 若装不下 → 降并发重算，或提高 TP / 量化 / 开 KV 量化 冗余系数 R 的构成：滚动发布期少 1 副本 + 单点故障容忍 + 扩容爬坡时间 常见取值 1.2 ~ 1.5；跨可用区高可用场景按 N+1 另算

第 ③ 步用的是排队论里的小定律（Little's Law）：稳态系统中，平均在途请求数 = 到达率 × 平均驻留时间。在闭环并发压测里在途请求数恒为 N_sla，所以吞吐就是 N_sla / L。这也解释了为什么延迟和吞吐不是两个独立指标——固定并发下，延迟涨一倍，吞吐就掉一半。

规划参数怎么取值取错的后果
峰值 QPS取分钟级 P95 峰值，不用日均用日均会在高峰期直接过载
峰谷比内部工具常见 3~5 倍，to C 应用可达 10 倍按峰值固定配置会在低谷浪费 70%+ 资源
冗余系数 R1.2 ~ 1.5（发布 + 故障 + 爬坡）不留冗余时滚动发布本身就会打穿 SLA
稳态 GPU 利用率目标60% ~ 70%长期超过 85% 尾延迟迅速恶化
弹性扩容时间含模型加载与预热，通常分钟级低估会让尖峰期扩容"赶不上趟"
KV Cache 预算N_sla × 平均上下文 × 每 token KV 字节数低估会在长上下文流量下触发抢占或 OOM

峰谷比这一行值得多说一句。按峰值配固定副本，低谷期利用率可能只有 15~20%，账单极不划算；按均值配则峰期必崩。实践中的折中是基线副本按 P95 分钟峰值的 60~70% 配置，尖峰交给弹性扩容兜底，同时把扩容的冷启动时间（拉镜像 + 加载权重 + 预热）算进 SLA 预算——这个时间在大模型上通常是分钟级，意味着弹性扩容能兜住持续几十分钟的高峰，但兜不住秒级尖刺，秒级尖刺只能靠基线冗余和排队。GPU 资源形态与成本模型的更多细节见 DP14 · GPU 基础设施。

典型场景推演：一次可复现的容量推导。某企业内部助手要求 P95 TTFT ≤ 800ms、P95 TPOT ≤ 50ms。用脱敏后的生产日志回放做阶梯扫描，SLA 拐点落在单副本并发 40，该档位平均端到端延迟约 4 秒，于是单副本可用产能 = 40 / 4 = 10 QPS。业务侧统计分钟级 P95 峰值为 55 QPS（日均只有 12 QPS，峰谷比约 4.6 倍），取冗余系数 1.3，得到所需副本数 = 55 / 10 × 1.3 ≈ 7.2 → 8 个副本；单副本用 TP=2，合计 16 张卡。再回头校验显存：40 并发 × 平均上下文长度对应的 KV Cache 必须能与权重共存于单副本显存内，若装不下就得下调并发重跑推导，或者通过 KV Cache 量化把这部分压下来（见 DP09 · KV Cache 优化）。最后按 60~70% 稳态利用率目标复核：8 副本在日均 12 QPS 下利用率过低，于是把基线定为 5 副本、峰段自动扩到 8——这套推导里唯一"测"出来的是 N_sla 和 L 两个数，其余全是算术，可以完整复现。请注意具体数值强依赖于模型规模、卡型、量化与引擎版本，方法链路才是可迁移的。

八个最常见的压测陷阱

下面这些坑几乎每个团队都会踩一遍，它们的共同点是都会让压测结果偏乐观——也就是说，你不会在压测阶段发现问题，只会在上线后发现。

陷阱为什么会让结果虚高怎么规避
预热不足首批请求包含 CUDA Graph 捕获、权重换页、内核 JIT 编译、tokenizer 初始化，TTFT 可能是稳态的数倍，混进统计会污染均值和分位数显式设 --warmup-request-count（默认是 0），或跑一轮丢弃后再正式测
前缀缓存命中虚高vLLM 官方明确警告：对同一 server 重复跑压测会复用留在前缀缓存里的 prompt，吞吐被抬高；随机数据集在固定 seed 下完全可复现，反而更容易全中每轮换 --seed、重启服务、或用 vllm bench sweep serve（自动在轮次间重置缓存）；同时留意 run 内部的共享前缀
客户端成为瓶颈单进程客户端在数百并发下 SSE 解析与 tokenize 吃满 CPU，测出的"延迟"其实是客户端排队，服务端明明还有余量监控压测机 CPU 与网卡；用多进程/多机分布式加压；压测机与服务端分离部署
只看均值LLM 延迟分布长尾极重，均值可能只有 P99 的几分之一，均值达标而大量用户体验崩坏报告必须给出 P50 / P90 / P95 / P99，SLA 也按分位数定义
忽略 ignore_eos模型提前遇到 EOS 停止，实际 OSL 远小于设定，单请求变短使吞吐被高估、TPOT 采样点不足压测时开 ignore_eos，让输出稳定到达 max_tokens
跨工具直接比数字各工具对 ITL 是否含 TTFT、吞吐是否含输入 token、是否排除 warmup 的定义都不同比公式和测量点，不比指标名；横向对比时统一用同一个工具重测
单副本结论直接乘副本数忽略负载均衡不均、共享存储与网络争用、网关连接数上限，实际线性度达不到至少做一次多副本联合压测验证扩展效率
采样参数没固定贪心解码省去了概率归一化与排序，与带温度的采样速度不同；不同轮次参数不一致会让对比失去意义同一组对比里锁死 temperature / top_p / top_k 与解码方式
  • 先统计生产流量的 ISL/OSL 分布和前缀重复率，再设计压测集
  • TTFT、TPOT、ITL 三个延迟指标分开报告，全部给到 P95/P99
  • 用并发数阶梯扫描画出完整曲线，上界取到略大于 max batch size
  • 按 SLA 拐点的吞吐做容量规划，而不是饱和点峰值吞吐
  • 每轮压测显式预热，并换 seed 或重置服务端缓存
  • 记录完整环境快照：引擎版本、模型与量化、卡型、驱动、并发与数据集参数
  • 引擎基准与业务链路压测两条线都跑，各自回答不同的问题
  • 不要只用 QPS 衡量 LLM 服务的产能
  • 不要用固定 ISL/OSL 的合成集做容量规划
  • 不要在开环速率模式下把系统压到排队发散，那测的是队列不是系统
  • 不要把厂商基准里的峰值吞吐直接当作自己的可用产能
  • 不要在没确认客户端和网关都不是瓶颈之前就调引擎参数
  • 不要跨工具直接对比同名指标，先核对公式
  • 不要在报告里只写均值，也不要省略成功率与错误分类
压测报告的价值不在于那个最大的数字，而在于它能不能被别人在另一台机器上复现出来。把环境、数据集、并发策略、预热方式、指标公式全部写进报告，这份报告才是资产；只有一个"我们跑到了 5000 tok/s"的结论，下个版本就作废了。

Q&A

TPOT 和 ITL 到底差在哪，为什么两个都要报？

ITL 是相邻两次流式响应之间的时间间隔，一个请求会产生很多个采样点；TPOT 是每个请求算一个值，公式为 (端到端延迟 − TTFT) / (输出 token 数 − 1)，分母减一是为了只刻画解码阶段。标准逐 token 解码下一次响应通常只带一个 token，两者数值基本一致，所以容易被当成同义词。差别在投机解码下暴露：一次响应可能带回多个被接受的草稿 token，ITL 只记录响应之间的间隔、不为同一响应内的 token 补零间隔，因此偏大；TPOT 则把解码时间摊到每个 token 上。vLLM 官方给的例子里，同一请求平均 ITL 是 40ms，而 TPOT 是 (180 − 100) / (5 − 1) = 20ms/token，相差一倍。两个都报的意义在于：TPOT 反映真实的吐字效率与 SLA 达成情况，ITL 反映吐字是否卡顿抖动，一个是平均速度，一个是节奏平滑度。

为什么不能只用 QPS 衡量 LLM 服务？

因为 QPS 隐含"每个请求工作量相近"的假设，而 LLM 请求的工作量与输出长度近似成正比，同一接口上不同请求可以相差上百倍。一个用户问"今天几号"生成 8 个 token，另一个让它写季度复盘生成 1500 个 token，两者都记作 1 个请求，但对 GPU 的占用天差地别。因此相同的 QPS 可能对应完全不同的实际负载，QPS 达标不代表系统没过载。正确做法是把输出 token 吞吐作为主吞吐指标，QPS 作为对接业务目标的辅助口径，并且必须同时给出该负载下的 TTFT 与 TPOT 分位数，否则无法判断这个吞吐是在什么体验代价下取得的。

压测应该固定并发数还是固定请求速率？

大多数基准测试应优先用固定并发数。并发模型是闭环负载：N 个客户端各持一个在途请求，收到响应立刻补发，系统里始终维持 N 个活跃请求，天然自带背压，永远不会发散。固定请求速率是开环负载，一旦到达率超过系统吞吐能力，在途请求会无界增长，队列越堆越长，你测到的延迟主要是排队时间而非系统能力，曲线会直接垂直起飞。请求速率模式的价值在于模拟真实到达模式（泊松分布、突发流量）用于韧性测试。生产压测最常用的其实是组合模式：请求速率设为无限、同时限制最大并发，这正好对应"用户全速发送 + 网关限连接数"的真实线上架构。

用固定输入输出长度做压测有什么问题？

固定长度制造了一个真实世界不存在的理想工况：batch 里所有请求同时开始、同时结束、工作量一致，连续批处理调度器几乎不需要做困难决策，KV Cache 占用平稳，没有请求会长期霸占槽位。测出来的是调度器的最好状态。真实流量的输出长度是长尾分布，大量短回答加上少量数千 token 的长文，长尾请求会连续几十秒占住 batch 槽位并让 KV Cache 持续膨胀，把同批短请求的 TPOT 一起拖慢，P99 被显著抬高。固定长度压测完全看不到这个效应，于是出现"压测很好、上线就崩"。需要特别注意工具默认值：genai-perf 的输入长度标准差默认是 0，不显式设置拿到的就是固定长度数据集。

怎么判断推理服务的饱和点？

做并发数阶梯扫描，从 1 开始倍增到略大于引擎的最大 batch size，每档记录输出吞吐与延迟分位数。曲线会呈现三段：线性区（吞吐随并发近似线性增长，延迟几乎不变）、收益递减区（吞吐增速放缓，TTFT 明显爬升）、饱和平台（吞吐不再增长甚至回落，延迟线性发散）。实用的量化判据是：并发翻倍后吞吐增益不足 10% 而 P95 TTFT 涨幅超过 30%，说明已经越过收益递减区。但要区分两个不同的点——饱和点是系统属性（算力或带宽被打满），SLA 拐点是业务属性（仍满足 P95 延迟约束的最大并发），后者几乎总是出现在前者之前且往往早很多。容量规划要用 SLA 拐点处的吞吐。

为什么压测结果总是比线上表现好很多？

最常见的原因有四个，且都会让结果偏乐观。一是预热不足反过来说的情况——多数团队会重复跑压测，前缀缓存里留着上一轮的 prompt，vLLM 官方明确警告过这会抬高吞吐，尤其随机数据集在固定 seed（默认 0）下完全可复现，更容易全部命中。二是压测集用了固定长度或前缀重复率与生产不符，掩盖了长尾请求对有效并发的侵蚀。三是只看均值不看 P95/P99，而 LLM 延迟分布长尾极重。四是单副本压测结论直接乘以副本数，忽略了负载均衡不均、共享存储争用和网关连接数上限。规避方法分别是：每轮换 seed 或重启服务重置缓存、用生产日志回放构造压测集、报告全分位数、以及至少做一次多副本联合压测验证扩展效率。

从压测结果怎么反推需要几个副本、几张卡？

推导分五步。先定 SLA（例如 P95 TTFT ≤ 800ms、P95 TPOT ≤ 50ms）；再在贴近真实分布的数据集上做阶梯压测，找到 SLA 拐点并发 N_sla 及该档位的平均端到端延迟 L；然后用小定律算单副本可用产能，即 QPS = N_sla / L（闭环并发下在途请求数恒定，所以吞吐就是并发除以驻留时间）；接着用分钟级 P95 峰值 QPS 除以单副本 QPS，再乘冗余系数（通常 1.2~1.5，覆盖滚动发布少一副本、单点故障与扩容爬坡）得到副本数；最后乘以单副本的张量并行度得到总卡数。算完还要回头校验显存：N_sla 并发对应的 KV Cache 加上模型权重必须装得进单副本显存，装不下就下调并发重算或用量化压缩。此外要按 60~70% 的稳态利用率目标复核，避免长期运行在 85% 以上导致尾延迟恶化。

genai-perf、vLLM bench serve 和 k6 该怎么分工？

它们回答的是不同问题，不是竞品关系。genai-perf（及其后继 AIPerf）指标定义最规范、文档化程度最高，适合做跨引擎的标准化横向对比与基准报告。vLLM 的 bench serve 与引擎指标口径完全一致，数据集生态最全（ShareGPT、BurstGPT、HuggingFace 系列、随机、前缀重复、自定义 jsonl 都支持），适合引擎特性评估、参数扫描和版本回归测试；vLLM 官方还推荐 GuideLLM 用于生产服务器的性能基准。k6 和 Locust 不理解 token，需要自己解析 SSE 才能算出 TTFT，但它们能编排完整业务链路（鉴权、向量检索、多轮会话状态）并做分布式加压和 CI 集成，适合验证自动扩缩容、网关限流和端到端 SLA。成熟团队通常两条线并行：引擎线定位"哪一层慢"，业务线验证"整体扛不扛得住"。

压测时为什么要开 ignore_eos，这会不会让结果失真？

开 ignore_eos 是为了让输出长度真正达到设定的 max_tokens，而不是模型提前生成 EOS 就停下。如果不开，实际输出长度会明显小于设计值，带来三个问题：单请求变短使系统吞吐被高估、TPOT 的采样点不足导致统计不稳定、以及不同轮次之间输出长度随机波动使结果不可比。所以在受控的性能基准测试里它是标准做法，NVIDIA 的压测指南也明确建议这样设。它确实让负载偏离了真实生成行为，但这正是"性能基准测试"与"业务链路负载测试"分工的意义所在：基准测试要的是可控可比，真实的 EOS 行为由业务链路压测（用生产日志回放、不改采样行为）来覆盖。两者结合才能既定位引擎效率，又验证真实体验。
