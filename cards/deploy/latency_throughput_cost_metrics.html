DP16 · 推理服务压测方法论 回答了"每个指标怎么测"；这张卡回答的是另一半问题：指标之间怎么换算、互相怎么制约、最后怎么折成钱。TTFT、TPOT、吞吐、利用率、$/1M token 不是五个孤立的数字，而是一张关系网——动任何一个，网上的其他节点都会跟着动。会算这张网，你就能不压测先估算、看到账单能归因、定 SLA 时知道自己在买什么卖什么。

一、指标全景：一张关系网

先把全网的节点和边画出来。指标的精确定义与测量方法（TTFT 含排队 + Prefill + 网络的服务视角口径、TPOT=(e2e−TTFT)/(OSL−1)、ITL 与 TPOT 在投机解码下分道扬镳）在 DP16 第二章，这里不重述，只用这些定义。

这张网的用法是"从任何一个节点出发都能走到其他节点"。老板问"我们比 API 便宜多少"，你从 $/1M token 出发，经过有效吞吐（Goodput 口径），落到 SLA 达标率；产品问"并发翻倍用户会不会变慢"，你从 TPOT 出发，经过 batch 邻居效应，落到吞吐-延迟曲线。走不通的时候，缺的那条边就是要补的测量。

二、延迟与吞吐的换算锚点

估算不需要压测数据时，靠三条锚点公式就能把"物理参数 → 单请求延迟 → 系统吞吐 → 卡数"整条链走下来。这三条与 DP08 第九章的口径完全一致。

2.1 锚点一：单请求延迟分解

e2e ≈ TTFT + output_tokens ÷ TPS单请求

它把体验指标拆成两段独立可优化的部分：TTFT 归 prefill（算力 + 排队 + 缓存命中），逐 token 速度归 decode（显存带宽）。注意口径：DP08 从引擎内部视角讨论时 TTFT 有时不含网关排队；本卡与 DP16 一致，采用服务视角——用户感知的 TTFT 包含排队与网络。

2.2 锚点二：decode 速度的物理上限

TPS单请求 ≈ 显存带宽 ÷ (2 × 参数量 × 精度字节)
系统吞吐 ≈ batch_size × TPS单请求（带宽未饱和前近似成立）

decode 每步要把模型权重完整读一遍显存，所以单请求速度被带宽锁死：H100 的 3.35 TB/s 带宽跑 70B FP16（权重约 140 GB），理论单请求上限约 20+ tok/s。这条公式解释了为什么 量化（分母变小）和 大 batch（一次读取摊给多个请求）是 decode 提速的两大杠杆——机制推导见 DP10。

2.3 锚点三：Little's Law 连接体验与产能

在途请求数 N = 到达率 RPS × 平均驻留时间 e2e

这是排队论里最耐用的一条：闭环并发下在途请求数恒定，所以 单副本产能 QPS = Nsla ÷ L（N_sla 是 SLA 拐点并发，L 是该档位平均 e2e）。利用率的口径也在这里统一：单请求视角下 decode 的 GPU 算力利用率不足 10%（带宽密集所致），大 batch 下才逐步升高——所以"GPU util 低"不等于"还有大把算力可挖"，要先看 batch 是不是已经受 KV 显存限制（见 S12 第五章）。

从物理参数到卡数的估算链（示例量级：70B FP16，H100） 硬件: 带宽 3.35TB/s ──► 单请求 TPS ≈ 3350 ÷ 140 ≈ 24 tok/s │ SLA: TPOT ≤ 50ms ────► 允许的最小人均带宽份额 → batch 上限估算 KV: 320KB/token ─────► 8K 上下文×40 并发 ≈ 10GB×4 = 105GB KV │ （TP=8 分摊到 8 卡，每卡 13GB） ▼ 单副本(8×H100): batch 40, e2e ≈ 0.8s + 180×0.04s ≈ 8s QPS_副本 = 40 ÷ 8 = 5 req/s ← Little's Law │ 业务: 峰值 55 QPS × 冗余 1.3 = 71.5 → 15 副本？ ✗ 太贵 —— 说明该场景应量化/换引擎/分流，估算链的价值 正是让你在买卡之前看见这条路的分叉

三条锚点各管一段路：锚点一把"体验"拆成可归因的两段；锚点二把 decode 段钉在物理带宽上；锚点三把单请求体验放大成系统产能。估算时从物理参数往上走（能扛多少），定 SLA 时从上往下走（要多少卡）——同一条链，两个方向。

三、Goodput：把 SLA 焊进吞吐里

系统吞吐有个致命盲区：它不关心请求是不是在用户能忍的时间内完成的。把并发压到饱和点之后，吞吐曲线走平甚至回落，但延迟分位数已经飞了——这时报出来的"峰值吞吐"是一个没有任何用户价值数字。Goodput（有效吞吐）的定义就是把 SLA 焊进吞吐：只统计满足延迟 SLO 的请求折算出的吞吐。这个概念由 DistServe 论文带入业界（vLLM 官方压测代码也采用此口径），详细推导在 DP12 第五节，这里讲它作为 KPI 的用法。

Goodput = 达标请求数（TTFT ≤ SLO₁ 且 TPOT ≤ SLO₂）÷ 窗口时长 × 平均输出长度
口径回答的问题适用场景陷阱
峰值吞吐（无 SLA）硬件理论产能引擎选型横评、论文对比不能直接用于容量规划
SLA 拐点吞吐体验不崩的最大产能容量规划（DP16 第六章的推导起点）依赖 SLA 定得是否合理
Goodput实际产出了多少"有价值的 token"架构优化 KPI、成本核算分母跨团队比较必须先对齐 SLO 数值
Goodput 为什么是架构优化的正确 KPI（数据口径源自 DP12）：DistServe 用 P/D 分离把 goodput 提升到混合部署的 7.4×；Mooncake 报告 +59%~498% 的 goodput 增益。更直观的是长上下文案例：27K token 的 prompt 负载下，优化前 TTFT p95 达 11.3s、SLA 达标率只有 34%——意味着三分之二的算力在产出"用户已经关掉的页面"的 token；优化后 TTFT p95 降到 6.1s、达标率 96%。同样的硬件、同样的名义吞吐，Goodput 差了 3 倍。用名义吞吐做分母算单位成本，会把这类系统的真实成本低估到危险的程度。

名义吞吐像餐厅"每小时出多少盘菜"，Goodput 是"每小时出多少盘没被客人退掉的菜"。后厨再快，端上去超时了客人走了，那些菜就是纯成本。所以第四章的单位成本公式里，分母写的都是 Goodput 而不是峰值吞吐。

四、成本指标：三本账与单位 token 成本

成本侧的指标体系可以整理成三本账：买 API 的账、自建算力的账、以及两本账都容易漏的隐藏账。三本账共同的最小核算单位是 $/1M token（或 ¥/百万 token），因为它是唯一能和市面 API 报价直接对比的口径。

4.1 账本 A：API 侧的价格结构

价格表本身（各家单价、档期、免费额度）在 ST24 · LLM API 价格与计费 维护，这里只提三条对指标体系有结构性影响的规律：输出单价约为输入的 3~4 倍（decode 比 prefill 贵，与第二章的物理原因一致）；缓存命中价约为标准输入价的 0.1~0.5 倍（前缀缓存命中率因此直接进成本公式）；以 DeepSeek 为参照系（输入 ¥2/百万、输出 ¥8/百万，ST24 表口径），行业同等能力的价格线在过去两年被持续拉低——社区研究（IntuitionLabs 2026-09 报告引 a16z 观点）甚至给出"同等模型质量的推理成本每年下降约 10×"的估计。这意味着 API 侧的成本指标必须带时间戳，任何"自建更便宜"的结论都有保质期。

4.2 账本 B：自建的单位成本核算

$/1M token = GPU 时价 × 10⁶ ÷ (Goodput tok/s × 3600)
生产案例一（知识库口径，源自 DP05）：2×RTX 4090 自托管 Qwen-32B AWQ，稳态聚合吞吐约 1,800 tok/s，月成本约 ¥2,400（含折旧与电费）。代入公式：¥2,400 ÷ (1,800 × 3600 × 86400 ÷ 10⁶ × 30 天折算) —— 按满月满载算约 ¥0.007/百万 token；但真实流量有峰谷，按 40% 平均利用率折算就是 ¥0.018/百万 token，再叠加输出:输入 ≈ 1:5 的真实比例（输出更贵），有效口径回到 ¥0.05~0.1/百万 token 量级。对比当时的 API 报价仍省约 55%——但注意这个结论对利用率极度敏感，利用率跌破 20% 就该重新算账。
生产案例二（知识库口径，源自 DP11）：某服务在不加任何硬件的前提下，仅通过调度参数调优（max_num_seqs、chunked prefill 配置、抢占策略）把单位 token 成本降低 64%。拆开看全部来自 Goodput 分子分母的变化：同样的卡时，达标吞吐上去了，分母变大，单位成本自然下降。这是"成本指标必须用 Goodput 做分母"的最好证明——用名义吞吐算，这次调优的成本收益会显示为 0。

三本账的关系像"打车 vs 买车 vs 忘了算的停车费"：账本 A 是打车价目表（透明但每程都付）；账本 B 是买车（单价随里程摊薄，但闲置也在折旧）；账本 C 是停车费、保险和油——两边都有，且最容易被漏进决策。盈亏平衡点的完整推导在 DP01，本卡提供的是核算用的指标口径。

五、延迟-吞吐-成本三角与破局手段

前四章的换算边汇总起来，就是一个不可能三角：同一套硬件与流量下，低延迟、高吞吐、低成本三者不可兼得。所有的架构决策本质上都是在三角里选位置，或者花钱（新硬件/新架构）把三角往外推。

读表的方法：先明确你的业务在三角里必须守住哪条边（交互式产品守 TTFT/TPOT，离线批处理守 $/1M），然后在"改善守边、恶化弃边"的手段里挑杠杆最大的。两个常见的错误姿势：给离线批处理配交互式 SLA（白白多付几倍卡）；给交互式产品追极限利用率（尾延迟把口碑打穿）。

三角的三条边其实由同一个物理量牵动——每个 token 摊到多少显存带宽和算力。batch 大就是摊得薄：钱省了、吞吐高了，但每个 token 分到的资源少了、慢了。所有"往外推"的手段，本质都是让同样的硬件在每个 token 上干更少的活（量化）、或者把活重新分配给更合适的硬件（P/D 分离）、或者干脆少干活（缓存、投机解码一次出多个 token）。

六、指标体系落地：SLA、告警与容量推导

关系网最终要落成三样东西：对业务承诺的 SLA、对着 SLA 的告警面板、以及从 SLA 反推硬件的容量推导链。

6.2 容量推导链：从 SLA 到卡数

完整的五步推导（定 SLA → 阶梯压测找 N_sla 与 L → Little's Law 算单副本 QPS → 峰值 ÷ 单副本 × 冗余系数 → 乘 TP 度得卡数，外加显存校验与 60~70% 稳态利用率复核）在 DP16 第六章有逐步骤展开，这里给一个走完链条的数字示例：

成本行的 $/1M token 要按 Goodput 口径自动计算并进面板，而不是月底对账单——单位成本是滞后指标里最需要前置的那个，它恶化的前兆（利用率下滑、达标率下滑）都在产能行里。

  • SLA 按业务形态分级承诺，阈值写 P95/P99 而不是均值
  • 容量规划用 SLA 拐点吞吐，成本核算用 Goodput 做分母
  • $/1M token 进实时面板，带 7 天滚动窗口和环比告警
  • 每次架构变更前用第二章锚点先口算方向，再压测验证（DP16）
  • API 比价数据带档期时间戳，季度复核自建/API 盈亏平衡（ST24）
  • 不要用峰值吞吐（无 SLA）对外承诺容量或算成本
  • 不要把稳态利用率推到 85% 以上换取账面成本下降
  • 不要跨团队比较 Goodput 而不对齐 SLO 数值
  • 不要用 "GPU util" 单一指标判断还有多少产能可挖
  • 不要拿两年前的 API 价格论证自建合理性

指标体系落地的成熟度可以自查：初级团队报均值和总吞吐；中级团队报 P95/P99 分位数和 SLA 达标率；成熟团队报 Goodput 和实时的 $/1M token——因为最后这两个数字才同时回答"用户满意吗"和"这生意划算吗"。从初级到成熟，加的其实不是监控项，而是第二章那张换算网。

Q&A

为什么不能只报"平均延迟"或"总吞吐"一个数字？

因为它们各自掩盖了一半事实。平均延迟掩盖长尾——LLM 延迟分布长尾极重，均值 1s 的系统 P99 可能在 8s，而 5% 的用户体验由 P99 决定（Google SRE 指南的原话口径："简单平均会掩盖尾延迟"）。总吞吐掩盖体验代价——并发压到饱和点后吞吐曲线走平，但延迟分位数已经发散，这时的"峰值吞吐"没有用户价值。正确的报法是三件套：P95/P99 的 TTFT 与 TPOT（体验）、SLA 拐点吞吐或 Goodput（有效产能）、$/1M token（成本）。三个数字互相制约，单独哪一个都可以被"优化"到失真。

不压测，怎么快速估一张卡能跑多少吞吐？

用第二章三条锚点走估算链：先算单请求 decode 上限 ≈ 显存带宽 ÷ 权重字节（H100 3.35TB/s ÷ 70B FP16 的 140GB ≈ 24 tok/s）；再看 KV 显存能塞多少并发（KV 池 ÷ 单请求 KV，70B FP16 是 320KB/token）；系统吞吐 ≈ batch × 单请求 TPS，在带宽饱和前近似成立；最后用 Little's Law 把吞吐换算成 QPS（÷ 平均 e2e）。注意三处会让估算偏乐观：batch 变大后单请求 TPS 会衰减（带宽被分薄）、prefill 会抢 decode 的时间片、TPOT SLA 会限制 batch 上限。估算的价值不是精确，是在买卡/租卡之前看清数量级和分叉点，精确数字永远以 DP16 的压测为准。

Goodput 和普通吞吐到底差在哪？KPI 该用哪个？

Goodput 只统计满足延迟 SLO（如 TTFT ≤ 800ms 且 TPOT ≤ 50ms）的请求折算的吞吐，概念由 DistServe 论文带入业界。差距在低达标率时会非常大：DP12 记录的 27K prompt 案例里，优化前 TTFT p95 达 11.3s、达标率仅 34%——三分之二的算力在产出用户已经放弃的 token，名义吞吐看着正常，Goodput 只有三分之一。对内 KPI 和成本核算分母都应该用 Goodput（DP11 的调参案例：名义吞吐口径下收益为 0，Goodput 口径下单位成本 −64%）；对外横评引擎可以用峰值吞吐，但必须注明无 SLA 约束。跨团队比较 Goodput 前必须先对齐 SLO 数值，否则数字没有可比性。

自建服务的 $/1M token 怎么算？什么规模下比 API 便宜？

公式：GPU 时价（租金或折旧+电费）× 10⁶ ÷（Goodput tok/s × 3600），再加上运维人力与冗余闲置的摊销。三个最容易算错的点：分母用了峰值吞吐而不是 Goodput（低估成本）、按满载 24×7 算利用率（真实流量有峰谷，利用率 40% 意味着单位成本 ×2.5）、漏掉输出 token 更贵的事实（API 报价输出是输入的 3~4 倍，自建时 decode 也是带宽大头）。规模判据参考 DP01 的盈亏平衡推导和掘金 2026-06 电商案例的经验线：QPS > 500 且 prompt 长的稳定负载适合自建；DP05 的案例（2×RTX4090 跑 Qwen-32B AWQ、月 ¥2,400、省 55%）是小规模自建的参照——但注意该结论对利用率极度敏感，且 API 价格每年下探约一个数量级（a16z 口径），自建优势的时间窗要定期复核。

为什么稳态利用率建议 60~70%，不能冲到 90%+？

排队论的非线性：等待时间对利用率的响应是发散的——利用率从 70% 到 85%，队列长度和尾延迟的增幅远大于从 50% 到 70%；逼近 100% 时任何流量抖动都会让队列无界增长。LLM 场景雪上加霜：单请求时长方差极大（8 token 和 2000 token 混排），长请求会周期性把瞬时利用率顶满，触发抢占和重算，反而让名义吞吐下降。所以 60~70% 的稳态目标（DP16 口径）不是浪费，是给方差留的缓冲垫。真想把利用率做上去，方向不是调阈值，而是把方差变小：长短请求分池、离线任务填谷、按队列深度做预测性扩缩。

SLA 阈值怎么定？直接抄别人的 800ms/50ms 行不行？

不能直接抄，但可以当起点。定阈值走三步：先从产品体验反推——TTFT 对应"点了没反应"的忍耐极限（对话产品普遍 500ms~1s），TPOT 对应阅读速度（中文阅读约 5~10 token/s，TPOT 50ms ≈ 20 tok/s 已快于人眼）；再看流量成分修正——RAG 长输入场景 TTFT 天然更高（prefill 时间与输入长度成正比），阈值要放宽或倒逼上前缀缓存；最后用压测验证可达性——SLA 定在压测曲线上"达标率 ≥95% 且成本可接受"的档位，定得太紧会用指数级成本换边际体验。800ms/50ms 是 DP16 的示例口径，适合中等长度输入的交互式对话；Agent 循环、批处理各有自己的守边（第六章分级表）。

从 SLA 到"要买几张卡"的完整推导链是什么？

五步（DP16 第六章的口径）：① 定 SLA（P95 TTFT/TPOT）；② 在贴近生产分布的数据集上阶梯压测，找到 SLA 拐点并发 N_sla 和该档平均 e2e L；③ Little's Law 算单副本产能 QPS = N_sla ÷ L；④ 峰值 QPS ÷ 单副本 QPS × 冗余系数（1.2~1.5，覆盖发布、故障、爬坡）= 副本数；⑤ 副本数 × 单副本 TP 度 = 总卡数。算完必须回头做两个校验：N_sla 并发的 KV Cache + 权重装得进单副本显存吗？稳态利用率落在 60~70% 吗？任一不过就下调并发或上量化重算。第六章给了走完链条的数字示例（N_sla=40、L=4s → 10 QPS → 8 副本 × TP2 = 16 卡）和三个敏感度口算。

月度账单突然涨了 30%，按什么顺序查指标？

按"量 → 价 → 效"三步。第一步查量：token 消耗总量涨了吗？拆输入/输出（输出贵 3~4 倍，输出占比上升本身就是账单放大器）、拆业务线，常见元凶是上下文膨胀（多轮历史没截断、RAG 召回段数变多、思维链模型切换）。第二步查价：流量结构变了吗？缓存命中率掉了（缓存价只有 0.1~0.5×）、贵模型分流比例升了、免费额度用完、供应商调价（对照 ST24 的档期表）。第三步查效（自建）：Goodput 和利用率掉了吗？达标率下滑意味着同样的卡时产出更少有效 token——按 S12 第六章归因表定位是排队、抢占还是冷副本问题。三步都对应第六章面板的四行指标，这也是为什么 $/1M token 要实时进面板而不是月底看账单。
