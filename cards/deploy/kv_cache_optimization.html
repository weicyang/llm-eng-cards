DP09 · KV Cache 显存优化

KV Cache Memory Optimization — PagedAttention、GQA/MQA、KV 量化与窗口丢弃策略

KV Cache 的本质：用空间换时间——缓存已计算的 Key/Value 向量，避免自回归生成时对相同 token 重复做矩阵乘法。

一、KV Cache 原理回顾

为什么需要 KV Cache？

Transformer 的自回归生成每产生一个新 token，都需要对之前所有 token 做 Attention 计算。如果不缓存，每步都要重新计算所有 Key 和 Value——计算量随序列长度二次方增长。

无 KV Cache（每步重算）： Step 1: 计算 token_1 的 K, V → 生成 token_2 Step 2: 重新计算 token_1, token_2 的 K, V → 生成 token_3 Step 3: 重新计算 token_1, token_2, token_3 的 K, V → 生成 token_4 ... → 大量重复计算 有 KV Cache（增量追加）： Step 1: 计算 token_1 的 K, V → 缓存 → 生成 token_2 Step 2: 复用缓存 + 只算 token_2 的 K, V → 追加缓存 → 生成 token_3 Step 3: 复用缓存 + 只算 token_3 的 K, V → 追加缓存 → 生成 token_4 ... → 每步只计算新增部分

KV Cache 的本质是"空间换时间"——用显存存储已计算的 Key/Value 矩阵，避免重复计算，将生成复杂度从 O(n²) 降到 O(n)。

二、核心痛点：显存碎片化

传统 KV Cache 分配方式的问题

传统方案为每个请求预分配连续显存块，按最大上下文长度预留空间。这导致严重的显存碎片化：

传统连续分配（按最大长度预分配）： GPU 显存 ┌──────┬──────────┬──────┬──────────┬──────┐ │ Req A│ 预分配 │ Req B│ 预分配 │ ... │ │ 实际用│ 浪费(空闲)│ 实际用│ 浪费(空闲)│ │ │ ██ │ ░░░░░░░░ │ ███ │ ░░░░░░░░ │ │ └──────┴──────────┴──────┴──────────┴──────┘ 问题： • 预分配空间按最大长度（如 2048），实际可能只用了 200 token • 内部碎片：已分配但未使用的空间无法给其他请求用 • 外部碎片：请求结束后留下不连续的空洞 • 多轮对话场景下显存浪费高达 60-80%

碎片化的具体表现

碎片类型成因影响
内部碎片预分配空间 > 实际使用长度单个请求浪费大量预留显存
外部碎片请求结束释放后留下不连续空洞新请求无法利用分散的小块显存

核心矛盾：GPU 显存是稀缺资源，但传统 KV Cache 管理方式导致 60-80% 的显存被浪费。这直接限制了并发请求数和系统吞吐量。

  • 重点指出"碎片化"是核心痛点——不只是显存不够，而是分配方式不合理
  • 类比：就像停车场按最长车辆预留车位，小车也占大车位——空间利用率极低
  • 这个痛点直接引出 PagedAttention 的解决方案

三、核心方案：PagedAttention (vLLM)

设计思想：借鉴操作系统虚拟内存

PagedAttention（Kwon et al., 2023, vLLM）的核心灵感来自操作系统的虚拟内存分页机制——不再要求 KV Cache 在物理显存中连续存储，而是切分为固定大小的 Block，通过映射表实现逻辑上的连续访问。

PagedAttention 原理（类比 OS 虚拟内存）： 操作系统虚拟内存 PagedAttention ─────────────────── ─────────────────── 虚拟页 (Virtual Page) → 逻辑 Block（token 的逻辑顺序） 物理页帧 (Physical Frame) → 物理 Block（GPU 显存中的实际位置） 页表 (Page Table) → Block Table（逻辑→物理映射表） 按需调页 (Demand Paging) → 按需分配 Block（生成新 token 时才分配） 逻辑视图（连续）： 物理视图（分散）： ┌───┬───┬───┬───┐ GPU 显存 │ B0│ B1│ B2│ B3│ ┌───┬───┬───┬───┬───┬───┐ └───┴───┴───┴───┘ │B2 │ X │B0 │ X │B1 │B3 │ ↓ Block Table └───┴───┴───┴───┴───┴───┘ B0 → 物理 Block #2 (X = 其他请求的 Block) B1 → 物理 Block #4 B2 → 物理 Block #0 B3 → 物理 Block #5

PagedAttention 的工作流程

步骤操作说明
1请求到达不预分配整块显存，仅初始化 Block Table
2生成新 token检查当前 Block 是否已满

Block 共享机制

PagedAttention 天然支持跨请求共享 KV Cache——多个请求可以指向同一个物理 Block：

  • Beam Search：多个候选序列共享前缀部分的 KV Cache，只需不同的最后一个 Block
  • Parallel Sampling：同一 prompt 的多个输出共享 prompt 部分的 KV Cache
  • Prefix Caching：相同 System Prompt 的请求共享前缀 Block
  • PagedAttention 是 vLLM 的核心创新——必知"vLLM 为什么快？"
  • 关键类比：OS 虚拟内存分页 → 显存分页，这个类比能帮助快速理解
  • 显存利用率从 20-40% 提升到接近 100%——相当于 3-5 倍的吞吐量提升
  • Block 共享是额外收益——Beam Search 场景下显存节省可达 N 倍（N = beam width）

四、优化策略一：GQA / MQA

Multi-Head Attention 的 KV 冗余

五、优化策略二：KV 量化

原理

KV Cache 通常以 FP16/BF16（16-bit）存储。量化将其压缩到 8-bit 甚至 4-bit，直接减少 50-75% 的显存占用。核心挑战是量化精度损失的控制。

KV 量化省的是"存"，不是"算"。写进 Cache 之前压成 8 bit，读出来参与 Attention 时再还原回 FP16 —— 计算图一行不用改，显存直接对半砍，这是所有 KV 优化里改动面最小、见效最快的一招。

量化能不能用得住，几乎全押在离群值上：KV 张量里少数几个 channel 的数值范围能比其他 channel 大一两个量级。如果整个张量共用一个 scale，这几个 channel 会把量化步长撑得极大，剩下的 channel 全被压进同一个格子里，等于白量化。所以生产实现普遍走per-channel 量化或分组量化，让每组各自持有 scale 与 zero-point。

量化方案对比

精度显存节省质量影响适用场景
FP16 / BF16基准基准高质量推理
INT850%极小（<1%）通用生产场景
INT475%可接受（1-3%）资源受限 / 长上下文
NF4 (NormalFloat)75%优于普通 INT4分布不均匀的 KV 值

关键技术要点

  • K 和 V 分开量化：Key 和 Value 的数值分布不同，独立量化效果更好
  • 分组量化（Group Quantization）：将 KV 按 channel 或 token 分组，每组独立计算 scale/zero-point
  • 离群值处理：KV 中存在少量极端值（outlier），需要特殊处理（如保留 FP16 或用更细粒度量化）
  • 量化时机：可以在写入 KV Cache 时量化（存储 INT8，计算时反量化回 FP16），对计算流程改动最小

量化精度 vs 显存节省的权衡

场景推荐精度理由
短文本生成（<2K）FP16KV Cache 本身不大，无需量化
中等长度（2K-8K）INT8显存节省 50%，质量几乎无损
长上下文（8K-128K）INT4 / NF4显存压力极大，需要 75% 压缩
超大批量INT8 + GQA两者叠加，显存节省可达 10 倍+
  • KV 量化是最"立竿见影"的优化——INT8 几乎无损，显存直接减半
  • 与模型量化的区别：模型量化影响所有计算，KV 量化只影响 Attention 的缓存部分
  • 加分点：提到"离群值"问题——KV 中少量 channel 的值范围远大于其他 channel

六、优化策略三：窗口丢弃与选择性保留

核心思想

并非所有历史 token 的 KV 都对当前生成有贡献。通过丢弃低重要性的 KV 条目，在保持生成质量的同时减少显存占用。

窗口丢弃赌的是"注意力天然稀疏"：绝大多数历史 token 拿到的权重接近零，扔掉对输出几乎无感。难点从来不是怎么扔，而是判断哪些不能扔 —— 开头那几个 Sink Token 就属于看着没用、一扔就崩的。

这类策略和前两节有本质区别：它是有损的。GQA 和量化改的是同一份信息的表示方式，窗口丢弃是真把信息删掉了。换来的好处是显存收益从"固定比例"变成了恒定上界 —— 不管请求跑到 10K 还是 1M token，占用都停在 (Sink 数 + 窗口宽度) 这个常数上，这也是流式场景唯一能长期跑下去的形态。

丢弃策略对比

策略原理显存优化质量影响
滑动窗口只保留最近 W 个 token 的 KV30-50%丢失长距离依赖

Attention Sink 的发现

研究发现一个有趣现象：LLM 在生成时，对序列最开始的几个 token（"Sink Token"）分配了异常高的 Attention 权重，即使这些 token 本身语义不重要。丢弃它们会导致生成质量急剧下降。

StreamingLLM 策略：保留 Sink Token + 滑动窗口 序列: [t0] [t1] [t2] ... [t95] [t96] [t97] [t98] [t99] [t100] ... ████ ░░░ ░░░ ░░░ ████ ████ ████ ████ ████ 保留 丢弃 丢弃 丢弃 保留 保留 保留 保留 Sink 滑动窗口（最近 W 个） 显存占用固定 = (Sink 数量 + 窗口大小) × KV 大小 无论序列多长，显存都不增长
  • Attention Sink 是亮点——"为什么最开始的 token 这么重要？"目前认为是模型将其作为"无信息默认关注点"
  • 滑动窗口 + Attention Sink = StreamingLLM，支持无限长度推理且显存恒定
  • H2O 等自适应策略更智能，但实现复杂度更高——需要在 Attention 计算时追踪权重
  • 窗口丢弃与 PagedAttention 可以叠加使用——PagedAttention 管理物理分配，窗口策略管理逻辑淘汰

七、系统级优势与策略组合

各策略的收益叠加

优化策略显存节省适用层是否可叠加
PagedAttention消除碎片化（利用率 →100%）显存管理层可叠加
GQA / MQA2-8 倍 KV 减少模型架构层可叠加
KV 量化 (INT8)50%存储层可叠加

推荐组合方案

生产级 KV Cache 优化 = 四层策略叠加 Layer 1: 模型层 → GQA (8 groups) → KV Cache 减少 8 倍 Layer 2: 存储层 → INT8 量化 → 再减少 2 倍 Layer 3: 管理层 → PagedAttention → 消除碎片化 Layer 4: 逻辑层 → Attention Sink + 窗口 → 控制长序列增长 综合效果（70B 模型，32K 上下文，并发 100 请求）： 未优化: ~51 GB/请求 × 100 = 5.1 TB（不可能） 优化后: ~0.8 GB/请求 × 100 = 80 GB（8×A100 可行）

四层策略能相乘而不是相加，是因为它们各管一段互不重叠：GQA 决定每个 token 存几份 KV，量化决定每份存几个 bit，PagedAttention 决定这些块怎么摆进显存，窗口策略决定留多少个 token。四个乘数彼此独立，才有 51 GB 压到 0.8 GB 这种量级的落差。

落地顺序与常见坑

  • 按"改动成本从低到高"推进：先开 PagedAttention（换推理引擎即可，零质量损失），再上 INT8 量化，最后才碰窗口丢弃这类有损策略。
  • GQA 是模型架构层的决定，只能在选型或继续训练阶段定下来，别指望部署时临时加。
  • 把 KV Cache 算进容量规划：显存先扣掉权重和激活，剩下的除以单请求 KV 大小，才是真实并发上限。
  • 回归测试专挑长依赖任务（多轮引用、长文档定位），这类任务对丢弃策略最敏感，普通对话样本测不出问题。
  • 不要在没量过碎片率之前先上量化：碎片率还有 60% 的时候，把碎片消掉的收益远大于把每个数压掉一半。
  • 不要让 K 和 V 共用一套量化参数，两者数值分布不同，混用会白白吃掉一截精度。
  • 不要为了省显存把滑动窗口砍到 Sink Token 以内，那等于把模型的注意力锚点一起丢掉，输出会迅速退化。
  • 不要只看显存和吞吐就宣布收工，有损策略的代价不会体现在吞吐曲线上，质量回归必须同批跑。

生产案例

生产验证：某 LLM 推理服务（Llama 3 70B，A100 80GB × 8）的 KV Cache 优化全记录：(1) 基线 — 预分配连续 KV Cache，单请求占用 512MB，最大并发 8 个，显存碎片率 65%；(2) +PagedAttention — 碎片率降至 4%，并发提升至 32 个（4x），吞吐从 120 tokens/s 提升至 480 tokens/s；(3) +GQA — KV Cache 大小降至 64MB/请求（-87.5%），并发进一步提升至 64 个；(4) +FP8 量化 — KV Cache 再降至 32MB/请求，总并发达 128 个。最终：单卡 A100 支撑 16 个并发请求（原 1 个），单位请求推理成本从 $0.08 降至 $0.005（降幅 94%）。

Q&A

请解释 KV Cache 的原理和它解决的问题。

KV Cache 是 Transformer 自回归生成中的"空间换时间"优化。生成每个新 token 时，需要对所有历史 token 做 Attention 计算。如果不缓存，每步都要重新计算所有 Key 和 Value，计算量随序列长度二次方增长。KV Cache 将已计算的 K/V 矩阵存入显存，每步只需追加计算新 token 的 K/V，将生成复杂度从 O(n²) 降到 O(n)。代价是显存占用随序列长度线性增长——这就是优化的出发点。

多轮对话场景下 KV Cache 有什么痛点？如何解决？

核心痛点是显存碎片化。传统方案为每个请求预分配连续显存块（按最大上下文长度），但实际使用长度远小于预分配长度，导致：①内部碎片——已分配但未使用的空间无法给其他请求；②外部碎片——请求结束后留下不连续空洞。多轮对话场景下显存浪费高达 60-80%。解决方案是 PagedAttention：借鉴 OS 虚拟内存分页，将显存切分为固定大小的 Block，按需分配非连续 Block，通过 Block Table 映射逻辑顺序。显存利用率从 20-40% 提升到接近 100%。

GQA 和 MQA 有什么区别？为什么主流模型选择 GQA？

MQA（Multi-Query Attention）让所有 Query Head 共享一组 KV，KV Cache 减少 N 倍（N = Head 数），但模型质量有明显下降。GQA（Grouped-Query Attention）是折中方案：将 Query Head 分为 G 组，每组共享一组 KV，KV Cache 减少 N/G 倍，质量接近 MHA。主流模型（LLaMA 2 70B、Mistral、Qwen 2.5）选择 GQA 因为它在质量和效率之间取得最佳平衡——8 组 GQA 可节省 8 倍 KV Cache，质量损失 <1%。MQA 虽然节省更多但质量下降明显，只在资源极度受限时使用（如 Falcon 40B）。

KV 量化会影响生成质量吗？如何控制精度损失？

INT8 量化对生成质量影响极小（<1%），是生产环境首选。INT4 影响稍大（1-3%）但显存节省 75%，适合长上下文场景。控制精度损失的关键技术：①K 和 V 独立量化——两者数值分布不同，分开处理效果更好；②分组量化——按 channel/token 分组，每组独立的 scale 和 zero-point；③离群值处理——KV 中少量 channel 的值范围远大于其他，需要保留高精度或更细粒度量化；④NF4（NormalFloat 4-bit）——针对正态分布数据优化的量化格式，比普通 INT4 更精准。实际建议：短文本（<2K）用 FP16，中等长度用 INT8，长上下文用 INT4。

PagedAttention 和 KV 量化/窗口丢弃能同时使用吗？

可以，而且应该叠加使用——它们解决不同层面的问题。PagedAttention 在显存管理层消除碎片化；KV 量化在存储层压缩每个 Block 的大小；窗口丢弃在逻辑层控制 KV Cache 的增长上限。三者互不冲突：PagedAttention 管理物理 Block 的分配和回收，KV 量化决定每个 Block 内部的存储精度，窗口丢弃决定哪些逻辑 Block 可以被淘汰。组合效果：GQA (8x) + INT8 (2x) + PagedAttention (3x 利用率) → 综合 40+ 倍的显存效率提升，使 70B 模型在消费级 GPU 上长上下文推理成为可能。

vLLM 为什么比 HuggingFace 默认推理快这么多？

核心原因是 PagedAttention 带来的显存效率革命。HuggingFace 默认方案为每个请求预分配连续显存，碎片化导致显存利用率仅 20-40%，大量显存被浪费。vLLM 的 PagedAttention 将显存切分为 Block 按需分配，利用率接近 100%——同等 GPU 下可容纳 3-5 倍的并发请求。此外 vLLM 还有：①Continuous Batching——新请求可以随时插入正在运行的 batch，不必等整个 batch 完成；②高效的 CUDA Kernel——Attention 计算针对 Block 结构做了底层优化；③前缀共享——相同 System Prompt 的请求共享 KV Cache Block。综合效果：在相同硬件上，vLLM 的吞吐量比 HuggingFace 高 2-4 倍。
