DP08 · KV Cache 与推理优化

从自回归生成到高效推理系统 — 理解大模型推理的核心瓶颈与优化手段

一、自回归推理过程

自回归生成天然是串行的：想快，就只能在"每一步少算点"和"一步多产出几个 Token"上做文章。

逐 Token 生成

Transformer 语言模型采用 自回归（autoregressive）方式生成文本：每一步根据前面所有 Token 的信息，预测下一个 Token，将其追加到序列末尾，再进行下一步预测。

输入:  [x₁, x₂, ..., xₜ]
模型:  P(xₜ₊₁ | x₁, x₂, ..., xₜ)
输出:  xₜ₊₁
循环:  [x₁, ..., xₜ, xₜ₊₁] → P(xₜ₊₂ | ...) → ...

每步都需要所有前文的 K/V

在 Self-Attention 中，当前 Token 的 Query 需要与所有前文 Token 的 Key 做点积得到注意力分数，再对所有前文 Token 的 Value 加权求和。这意味着：

  • 生成第 t 个 Token 时，需要前面 t-1 个 Token 的 K 和 V
  • 朴素实现下，每步都要重新计算所有 Token 的 K/V → 重复计算量巨大

朴素推理的 O(n²) 问题

生成长度为 n 的序列时：

  • 第 1 步计算 1 个 K/V，第 2 步计算 2 个，…，第 n 步计算 n 个
  • 总计算量 = 1 + 2 + ... + n = O(n²)
  • 这使得长序列生成的延迟随序列长度平方级增长，完全不可接受
  • 自回归生成是串行的，无法对输出 Token 进行并行化（与训练形成鲜明对比）
  • 朴素推理的瓶颈在于重复计算 K/V，这正是 KV Cache 要解决的问题
  • 计算复杂度从 O(n²) 降到 O(n) 是 KV Cache 最核心的价值

二、KV Cache 原理

KV Cache 就是把已经算过的历史 K/V 存下来不再重算——省下的是计算，付出的是显存。

核心思路：缓存已计算的 K/V

已经生成的 Token 对应的 Key 和 Value 不会随后续 Token 的生成而改变（因果注意力掩码保证了这一点）。因此可以将它们缓存到 GPU 显存中，后续步骤直接复用，无需重新计算。

# 朴素推理（无 Cache）
step t: 计算 K₁,V₁, K₂,V₂, ..., Kₜ,Vₜ → Attention → 输出 xₜ₊₁

# 使用 KV Cache
step t: 从缓存取 K₁..Kₜ₋₁, V₁..Vₜ₋₁
         仅计算新 Token 的 Kₜ, Vₜ
         追加到缓存
         Attention([K₁..Kₜ], [V₁..Vₜ]) → 输出 xₜ₊₁

缓存逐步节省的计算量

步骤无 KV Cache（朴素）有 KV Cache（缓存）节省比例
第 1 步计算 1 个 K/V → Attention计算 1 个 K/V → Attention0%（首步无差异）
第 2 步重新计算 2 个 K/V → Attention复用缓存 + 新增 1 个 K/V50%
第 10 步重新计算 10 个 K/V → Attention复用缓存 + 新增 1 个 K/V90%
第 100 步重新计算 100 个 K/V → Attention复用缓存 + 新增 1 个 K/V99%
第 1000 步重新计算 1000 个 K/V → Attention复用缓存 + 新增 1 个 K/V99.9%

KV Cache 在 Attention 中的数据流

第 t 步生成 Token_t：
  ┌─────────────────────────────────────────────────────┐
  │ Query_t (新计算)                                    │
  │   ↓                                                  │
  │ Q_t × [K_1, K_2, ..., K_{t-1}, K_t]ᵀ / √d_k       │
  │         ↑ 从 KV Cache 读取          ↑ 新计算并缓存   │
  │   ↓                                                  │
  │ softmax(scores) × [V_1, V_2, ..., V_{t-1}, V_t]     │
  │                     ↑ 从 KV Cache 读取    ↑ 新缓存   │
  │   ↓                                                  │
  │ Output_t → 送入 FFN → Token_t                        │

第 t+1 步：
  KV Cache 新增一行：[K_t, V_t]
  Query_{t+1} 与缓存中全部 t+1 个 K 做点积
  → 只需计算 1 个新 K/V，其余全部复用

内存换速度

KV Cache 是典型的 空间换时间策略：

  • 优势 每步只需计算 1 个 Token 的 K/V，计算量从 O(n²) → O(n)
  • 代价 需要额外显存存储所有历史 K/V，且随序列长度线性增长

KV Cache 大小计算公式

KV Cache Size = 2 × L × n_heads × d_head × seq_len × dtype_bytes

各项含义：

符号含义示例 (LLaMA-2 7B)
2K 和 V 各一份—
LTransformer 层数32
n_heads注意力头数（KV 头数，GQA 下更少）32
d_head每头维度128
seq_len序列长度4096
dtype_bytes数据类型字节数（FP16=2, FP8=1）2 (FP16)

LLaMA-2 7B 示例：

2 × 32 × 32 × 128 × 4096 × 2 bytes
= 2 × 32 × 32 × 128 × 4096 × 2
= 2,147,483,648 bytes ≈ 2 GB（单条序列！）

可见 KV Cache 的显存占用非常惊人，尤其在大 batch 或长序列场景下会成为主要显存瓶颈。

  • KV Cache 将推理计算量从 O(n²) 降到 O(n)，是所有现代推理引擎的基础
  • 必须能手算 KV Cache 大小 — 高频考点
  • KV Cache 只在推理阶段使用；训练使用 Teacher Forcing，可以并行处理所有 Token
  • GQA/MQA 通过减少 KV 头数来压缩 Cache 大小（见第 7 节）

三、Prefill vs Decode

Prefill 缺算力，Decode 缺带宽——两个阶段的瓶颈不同，所以优化手段基本不通用。

使用 KV Cache 后，LLM 推理自然分成两个截然不同的阶段：

Prefill 阶段（首 Token 延迟）

  • 处理完整 Prompt（一次性输入所有 Token）
  • 并行计算所有 Prompt Token 的 K/V
  • 填充 KV Cache
  • 计算密集（Compute-bound）
  • GPU 算力利用率高，类似训练
  • 决定 TTFT（Time To First Token）

Decode 阶段（逐 Token 生成）

  • 每步只处理 1 个新 Token
  • 从 KV Cache 读取历史 K/V
  • 计算量小但需要大量内存读取
  • 内存带宽瓶颈（Memory-bound）
  • GPU 算力利用率极低（<10%）
  • 决定 TPS（Tokens Per Second）

  • 部分系统（如 Sarathi、Splitwise）将 Prefill 和 Decode 分离到不同 GPU以优化资源利用

四、Continuous Batching

静态批处理的浪费不在于算得慢，而在于短请求算完后还要陪着最长的那个请求空等。

静态 Batching 的浪费

传统静态 Batching 将多个请求组成一个 batch 一起推理，但每个请求的生成长度不同。短请求结束后必须等待最长请求完成，GPU 在等待期间被浪费（padding idle）。

静态 Batching:
Req A: |████████████████████|............| ← 已完成，空等
Req B: |████████████████████████████████| ← 最长请求
Req C: |█████████████|...................| ← 已完成，空等
       └─────── 所有请求必须等 B 完成 ────────┘

Iteration-level Scheduling

Continuous Batching（也叫 Inflight Batching）的核心思想是在每个 decode 迭代级别进行调度：

  • 一旦某个请求生成了 EOS Token，立即释放其资源并插入新请求
  • 不再等待整个 batch 完成
  • GPU 始终在做有效计算
Continuous Batching:
Req A: |████████████████████|
Req D:                      |██████████████████| ← A 完成后立即插入
Req B: |████████████████████████████████|
Req C: |█████████████|
Req E:               |███████████████████████| ← C 完成后立即插入
       └─────── GPU 始终满载 ────────────────┘

Orca 论文

Continuous Batching 的概念由 Orca (OSDI 2022) 论文正式提出。核心贡献：

  • 提出 Iteration-level Scheduling：每个 decode step 都可以调度
  • 实现 Selective Batching：允许 batch 内不同请求处于不同阶段（有的在 prefill，有的在 decode）
  • 相比静态 Batching，吞吐量提升 2-8x
  • Continuous Batching 解决的是静态 Batching 中 GPU 空闲浪费的问题
  • 核心调度粒度从 request-level → iteration-level
  • 几乎所有现代推理引擎（vLLM、TGI、TensorRT-LLM）都已实现 Continuous Batching
  • 提升的是吞吐量（throughput），对单请求延迟帮助有限

五、PagedAttention (vLLM)

把操作系统那套分页搬到显存上：不再按最长可能长度预留，而是用多少给多少，碎片就没了。

KV Cache 碎片化问题

传统推理框架为每个请求预分配最大长度的 KV Cache，但实际生成长度往往远小于最大长度。这造成：

  • 内部碎片：预分配空间未被完全使用
  • 外部碎片：请求结束释放后留下不连续的空闲块
  • 实际 KV Cache 显存利用率仅 20-40%

分页管理（类似 OS 虚拟内存）

PagedAttention 借鉴操作系统的虚拟内存分页机制：

  • 将 KV Cache 切分为固定大小的 Block（类似内存页，通常 16 个 Token 一块）
  • Block 不要求物理连续，通过 Block Table 映射逻辑位置 → 物理位置
  • 按需分配，用多少分配多少，消除内部碎片
  • 空闲 Block 可以分配给任意请求，消除外部碎片

Block Table

逻辑 Token 序列:  [T₀ T₁ T₂ T₃ | T₄ T₅ T₆ T₇ | T₈ T₉ ...]
                   Block 0        Block 1        Block 2

Block Table (请求 A):
┌─────────┬──────────────┐
│ 逻辑块号 │ 物理块地址    │
├─────────┼──────────────┤
│    0    │  GPU Block 7  │
│    1    │  GPU Block 2  │
│    2    │  GPU Block 15 │  ← 物理不连续，但逻辑连续
└─────────┴──────────────┘

Copy-on-Write

当多个请求共享相同的 Prompt（如 Beam Search 或 Parallel Sampling），它们的 Prompt 部分 KV Cache 完全相同。PagedAttention 支持：

  • 多个请求的 Block Table 指向同一物理 Block（共享）
  • 当某个请求需要修改共享 Block 时，才复制一份（Copy-on-Write）
  • Parallel Sampling 场景可节省 55% 显存

Prefix Caching：跨请求共享 KV Cache

很多 LLM 请求共享相同的系统提示（System Prompt）或前缀，PagedAttention 的 Block 机制天然支持前缀缓存：

  • 相同的 System Prompt 只计算一次 K/V，缓存为共享 Block
  • 后续请求直接引用这些 Block，无需重新 Prefill
  • 在 System Prompt 很长（如 2000+ Token）的场景下，TTFT 可降低 50-80%
  • vLLM 通过 --enable-prefix-caching 启用此功能

示例场景：一个客服问答服务开了 Prefix Caching，System Prompt 约 1800 Token，预期绝大多数请求都能命中共享前缀。

问题：上线后命中率长期只有个位数百分比，TTFT 和没开时几乎一样。排查发现 System Prompt 模板里带了两样东西：一个精确到秒的当前时间，和一个每次请求随机生成的会话 ID，两者都拼在最前面。前缀匹配是从第一个 Token 开始逐块比对的，第一个 Block 就不同，后面 1800 个 Token 再一样也没用。

方案：把 System Prompt 拆成两段：不变的角色设定、规则、示例放最前面；时间、会话 ID、用户画像这些每次都变的内容挪到用户消息里。时间精度也从秒降到天，因为业务上并不需要更细。

效果：前缀命中率升到约 九成，TTFT 中位数降了约 六成。这里没有换任何组件，只是把"会变的内容"从前缀里挪走了——前缀缓存的收益完全取决于 Prompt 的拼装顺序。

指标传统方式PagedAttention
显存利用率20-40%>95%

  • 提升的是显存利用率和并发能力，从而提升系统吞吐

六、Speculative Decoding

让小模型先猜几个 Token，大模型一次性验证——猜对了白赚，猜错了也不亏，输出分布还完全不变。

核心思路：小模型草稿 + 大模型验证

标准自回归解码每步只能生成 1 个 Token（因为下一个 Token 依赖上一个）。Speculative Decoding（投机解码）打破了这一限制：

  1. Draft 阶段：用一个小而快的 Draft Model 快速生成 γ 个候选 Token
  2. Verify 阶段：将这 γ 个 Token 一次性送入大模型并行验证
  3. Accept/Reject：大模型从左到右逐个检查，接受概率匹配的 Token，在第一个被拒绝的位置用大模型自己的分布重新采样
Draft Model (68M):  快速生成 γ=5 个候选
  → [the, cat, sat, on, the]

Target Model (7B):  并行验证 5 个 Token
  → [the ✓, cat ✓, sat ✓, on ✓, a ✗] → 接受前 4 个 + 重采样第 5 个

结果: 一次大模型 forward pass 生成了 5 个 Token！

加速比分析

设 Draft Model 接受率为 α，每次生成 γ 个候选：

期望接受 Token 数 = (1 - αᵞ⁺¹) / (1 - α)
加速比 ≈ 期望接受数 / (c + 1)，其中 c = Draft 开销 / Target 开销
  • α 越高（Draft 越准），加速越明显
  • Draft Model 越小越快，c 越小，加速越好
  • 实际加速通常为 2-3x，最优可达 3-4x

Draft Model 选择

策略说明优缺点
独立小模型同系列小模型（如 LLaMA-68M 做 LLaMA-7B 的 draft）简单灵活；需要额外显存
自草稿 (Self-Draft)跳过部分层 / 早退（如 Medusa、EAGLE）无需额外模型；需要微调
N-gram / 检索从 Prompt 或历史中检索匹配片段零额外计算；仅适合重复性内容
Medusa在大模型上加多个预测头，并行预测多个位置高质量；需要训练额外头
  • Speculative Decoding 不改变输出分布（数学等价于直接用大模型采样）— 这是最关键的性质
  • 加速来源于：用一次大模型 forward pass 验证多个 Token，而大模型 forward pass 在 decode 阶段是 memory-bound 的，处理 1 个 Token 和 γ 个 Token 耗时接近
  • 接受率 α 是核心指标 — Draft 与 Target 分布越接近，α 越高

七、KV Cache 压缩

压 KV Cache 有四条正交的路：少存几个头、每个数存得更省、别浪费空位、干脆扔掉不重要的——它们可以叠着用。

GQA / MQA 减少 KV 头数

标准 Multi-Head Attention (MHA) 中 Q、K、V 头数相同。通过减少 K/V 头数可以直接压缩 KV Cache：

方法Q 头数KV 头数Cache 压缩比代表模型
MHA32321x (基准)LLaMA-1, GPT-3
GQA3284xLLaMA-2 70B, Mistral
MQA32132xPaLM, Falcon
MLA—低秩压缩为 Latent Vector5-10xDeepSeek-V2/V3
CLA—跨层共享 K/V（相邻层复用）2-3xHunyuan-Large

质量损失对比：GQA <0.5%，MLA <0.5%，MQA 1-2%。MLA 不存储完整的 K/V 矩阵，而是用低秩投影将 K/V 压缩到低维 Latent Vector，推理时再展开——DeepSeek-V3 借此将每 Token KV 压到约 50 KB（见第二章模型表）。注意 MLA 和 CLA 都需要在模型训练时采用，无法对已训练模型追加。

KV Cache 量化

将 KV Cache 从 FP16 量化到更低精度：

  • FP8 (E4M3)：2x 压缩，精度损失极小，已被 TensorRT-LLM 支持（需 H100/B200 等 Hopper+ 硬件加速）
  • INT8：2x 压缩，需要校准（Calibration），硬件支持广泛
  • INT4：4x 压缩，需要搭配 group-wise 量化或校准
  • KIVI：Key 用 INT2，Value 用 INT4，结合 residual 补偿，可达 5-6x 压缩

vLLM FP8 KV Cache 实测数据（2026 年 4 月）：在 H100 上对 LLaMA-3.1-8B 启用 --kv-cache-dtype fp8，Decode 阶段的每 Token 延迟降至 BF16 的 54%（最佳情况），128K 上下文下 Needle-in-a-Haystack 准确率从修复前的 13% 恢复到 91%（BF16 基线）。关键修复：Flash Attention 3 内核中的 FP8 累积精度问题通过两级累积策略解决。注意：滑动窗口注意力层（如 gpt-oss-20b 的 128 Token 窗口层）不适合 FP8，应使用 --kv-cache-dtype-skip-layers sliding_window 跳过。

滑动窗口丢弃

只保留最近 W 个 Token 的 KV Cache，丢弃更早的。Mistral 采用了这种方式（W=4096）。

  • 优势：KV Cache 大小固定为 O(W)，不随序列增长
  • 劣势：丢失远距离依赖，不适合需要全局信息的任务

H2O (Heavy Hitter Oracle)

观察到注意力分数呈幂律分布：少数 "Heavy Hitter" Token 获得大部分注意力权重。H2O 策略：

  • 始终保留注意力得分最高的 Top-k Token 的 KV（Heavy Hitters）
  • 加上最近的窗口 Token
  • 动态淘汰中间不重要的 Token
  • 可将 KV Cache 压缩到 20% 而不显著损失质量

StreamingLLM

发现 LLM 在推理时，开头几个 Token（attention sink）始终获得高注意力，即使它们语义上不重要。StreamingLLM 的策略：

  • 保留前 k 个 Sink Token + 最近 W 个窗口 Token
  • 支持无限长度的流式推理
  • 相比纯滑动窗口，PPL 显著降低
KV Cache = [Sink Tokens (前4个)] + [滑动窗口 (最近 W 个)]

Token 合并

将语义相近的相邻 Token 合并为一个，可压缩 KV Cache 2-4x，适合冗余内容较多的场景；缺点是合并过程本身有一定计算开销。

优化叠加效果

量化、内存管理、前缀共享、稀疏化四个方向相互正交，可以叠加使用：

九、推理性能指标

吞吐和延迟是同一份显存的两种花法，任何调参之前先想清楚这次要买哪一个。

指标全称定义优化方向
TTFT Time To First Token 从请求发送到接收到第一个 Token 的时间 优化 Prefill：FlashAttention、Tensor 并行、Prompt 缓存
TPS Tokens Per Second 单个请求每秒生成的 Token 数（又叫 decode speed） 优化 Decode：量化、投机解码、更快的内存带宽
Throughput 系统吞吐量 系统每秒处理的总 Token 数（所有请求合计） Continuous Batching、PagedAttention、大 batch
Latency 端到端延迟 从请求到完整响应的总时间 = TTFT + 输出长度 / TPS 综合优化各阶段

指标之间的关系

Latency = TTFT + (output_tokens / TPS)

Throughput = Σ(所有并发请求的 TPS)
           ≈ batch_size × single_TPS（理想情况下，decode 阶段近似线性扩展）

TTFT 主要受 Prefill 影响:
  TTFT ≈ prompt_tokens × compute_per_token / GPU_FLOPS

TPS 主要受 Decode 影响:
  TPS ≈ model_bandwidth / (2 × model_params × dtype_bytes)  (roofline 近似)

  • Roofline Model 可用于分析当前系统是 compute-bound 还是 memory-bound

生产上限不是模型算得多快决定的，是"一张卡能同时装下几份 KV Cache"决定的。

# 容量规划公式
可用 KV Cache 空间 = GPU 总显存 - 模型权重 - 激活值预留

最大并发请求数 = 可用 KV Cache 空间 / (每请求 KV Cache 大小)

  模型权重: 70 GB (FP8)
  激活值预留: ~10 GB
  可用 KV Cache: 320 - 70 - 10 = 240 GB
  每请求 32K context: 10.7 GB
  最大并发: 240 / 10.7 ≈ 22 个请求

生产案例：某 AI 编码助手服务（日均 300 万次推理请求，平均上下文 8K Token），使用 vLLM + LLaMA-3 70B FP8 部署在 8×H100 80GB 集群上。初始配置（BF16 KV Cache）最大并发 40 请求，高峰期排队严重，P99 延迟 12 秒。启用 FP8 KV Cache + Prefix Caching（共享 1.5K Token 的系统提示）后，最大并发提升到 85 请求，P99 延迟降至 4.2 秒，月 GPU 成本从 $28,000 降至 $16,000（减少 4 张 GPU）。

示例场景：一个内部推理服务为了把吞吐做上去，把最大并发序列数从 64 一路调到 256，压测时总吞吐确实涨了约 七成。

问题：上线后投诉反而变多。日志显示 P50 延迟只涨了一点，但 P99 从 3 秒涨到 20 秒以上，还偶发请求被直接拒绝。原因有两层：并发一高，KV Cache 池被占满，新请求要么排长队要么被拒；同时 batch 里只要混进几个超长上下文请求，每轮迭代都要把这几份巨大的 Cache 读一遍，整个 batch 的其他请求全被拖慢。吞吐是总量指标，它涨了不代表每个用户变快了。

方案：三处调整：① 最大并发回调到压测中 P99 仍达标的档位，而不是吞吐最高的档位；② 按上下文长度分两个队列，长请求单独限流，不和短请求混在一个 batch 里；③ 把 KV Cache 池占用率和队列长度做成报警项，占用率超过阈值就提前拒绝而不是无限排队。

效果：P99 回到 5 秒以内，总吞吐相比峰值配置只降了约 一成五。教训是压测目标不能只写吞吐，必须带上 P99 约束，否则调出来的参数一定是牺牲尾延迟换来的。

  • 在生产环境中，KV Cache 管理是 LLM 推理系统的第一瓶颈——不是计算不够快，而是显存不够大
  • 每减少 1 GB 的 KV Cache 浪费，就意味着可以多处理一个并发请求
  • PagedAttention 和 FP8 KV Cache 已成为生产推理系统的标配——它们直接决定了同样的硬件能服务多少用户

最佳实践 Do / Don't

✅ Do

  • 优先选择 GQA 模型：KV Cache 压缩 4-8x，质量损失可忽略
  • 使用 vLLM/SGLang 作为推理框架：自动启用 PagedAttention
  • 启用 Prefix Caching：相同 System Prompt 的请求共享 KV Cache
  • H100+ GPU 启用 FP8 KV：显存减半，Decode 加速，精度几乎无损
  • 基于监控数据调参：用 Prometheus 采集 KV Cache 利用率，动态调整 max-num-seqs
  • 容量规划用公式：显存 - 权重 - 激活 = 可用 KV Cache 空间

❌ Don't

  • 不要在 A100 上启用 FP8 KV：A100 不支持 FP8 硬件加速，会回退到软件模拟
  • 不要设置过大的 max-model-len：KV Cache 按最大长度预分配会浪费显存
  • 不要忽略 KV Cache 监控：显存溢出是最常见的生产故障
  • 不要在滑动窗口层启用 FP8：小窗口下 FP8 开销无法被摊薄
  • 不要假设 FP8 完全无损：长上下文（128K+）需要验证精度
  • 不要混用不同精度的 KV Cache：同一请求的 K 和 V 必须使用相同精度
  • KV Cache 优化的终极目标是用更少的显存服务更多的请求
  • 标准推理栈：GQA 模型 + vLLM + FP8 KV Cache + Prefix Caching + Continuous Batching
  • 这套组合在 H100 上可将每请求成本降低到 2023 年的约 1/10

Q&A

Q1: 什么是 KV Cache？为什么需要它？

KV Cache 是在自回归推理时，将已计算过的每层 Attention 的 Key 和 Value 向量缓存在 GPU 显存中的机制。

为什么需要：自回归生成每步都需要当前 Token 的 Query 与所有前文 Token 的 Key 做点积。如果不缓存，每步都要重新计算所有前文的 K/V，总计算量为 O(n²)。有了 KV Cache，每步只计算一个新 Token 的 K/V 并追加到缓存中，总计算量降为 O(n)。这是用显存空间换计算时间的经典策略。

Q2: KV Cache 的大小如何计算？以 LLaMA-2 7B 为例。

公式：2 × layers × kv_heads × d_head × seq_len × dtype_bytes

LLaMA-2 7B：32 层，32 个 KV 头，每头 128 维，FP16 (2 bytes)。

对于 seq_len=4096：2 × 32 × 32 × 128 × 4096 × 2 = 2 GB（单条序列）。

如果 batch_size=32，总 KV Cache = 64 GB，已超出单张 A100 80GB 的显存。这说明 KV Cache 是大模型推理的核心显存瓶颈。

Q3: Prefill 和 Decode 阶段有何区别？各自的瓶颈是什么？

Prefill 阶段：一次性处理完整 Prompt，并行计算所有 Token 的 K/V 填充 Cache。这一阶段涉及大矩阵乘法，是 compute-bound（受 GPU FLOPS 限制），GPU 利用率高。它决定了 TTFT（首 Token 延迟）。

Decode 阶段：逐 Token 生成，每步只计算一个新 Token，但需要读取整个 KV Cache。计算量小但内存访问量大，是 memory-bound（受 GPU 内存带宽限制），GPU 算力利用率极低（通常 <10%）。它决定了 TPS（每秒 Token 数）。

Q4: 什么是 Continuous Batching？相比静态 Batching 有什么优势？

静态 Batching：将多个请求打包成 batch，必须等所有请求都完成才释放资源。短请求完成后 GPU 空等，浪费算力。

Continuous Batching（Orca 论文提出）：在每个 decode iteration 级别进行调度。请求一旦完成（生成 EOS），立即释放其 KV Cache 并插入新请求。GPU 始终保持高利用率。

吞吐量提升 2-8x，几乎所有现代推理引擎都已采用。

Q5: PagedAttention 是什么？解决了什么问题？

PagedAttention 借鉴了 OS 虚拟内存的分页机制来管理 KV Cache。传统方式为每个请求预分配最大长度的连续 KV Cache，导致严重的内部和外部碎片（利用率仅 20-40%）。

PagedAttention 将 KV Cache 切分为固定大小的 Block（通常 16 Token），通过 Block Table 映射逻辑块到物理块。按需分配、不要求连续，利用率提升到 95% 以上。还支持 Copy-on-Write，在 Beam Search 等共享 Prompt 场景下避免重复存储。

Q6: Speculative Decoding 的原理是什么？为什么它不改变输出分布？

原理：用小而快的 Draft Model 连续生成 γ 个候选 Token，然后将这 γ 个 Token 一次性送入大模型并行验证。大模型从左到右检查每个 Token 的概率，接受与大模型分布一致的 Token，在第一个拒绝位置用大模型分布重新采样。

不改变分布的原因：验证使用了修正的拒绝采样（modified rejection sampling）。接受条件为 min(1, P_target(x)/P_draft(x))，拒绝后从 norm(max(0, P_target - P_draft)) 重新采样。数学上可以证明，最终每个 Token 的分布与直接从大模型采样完全一致。

Q7: GQA、MQA、MHA 有什么区别？各自的 trade-off 是什么？

MHA (Multi-Head Attention)：Q、K、V 各有 n 个头。质量最好但 KV Cache 最大。

GQA (Grouped-Query Attention)：Q 有 n 个头，K/V 只有 g 个头（g < n），每组 Q 头共享同一组 K/V 头。Cache 压缩 n/g 倍，质量损失很小。代表：LLaMA-2 70B (g=8)。

MQA (Multi-Query Attention)：K/V 只有 1 个头，所有 Q 头共享。Cache 压缩 n 倍，但质量可能有明显下降。代表：PaLM、Falcon。

目前 GQA 是最佳平衡点，大多数新模型都采用 GQA。

Q8: StreamingLLM 中的 Attention Sink 是什么？为什么需要保留开头 Token？

Attention Sink 现象：研究发现 LLM 在推理时，无论输入内容如何，最前面的几个 Token（通常前 4 个）始终获得极高的注意力分数。这并非因为它们语义重要，而是 Softmax 需要一个"汇聚点"来分配剩余的注意力权重。

如果使用纯滑动窗口丢弃了这些 Sink Token，模型的 PPL 会急剧上升甚至崩溃。StreamingLLM 的做法是始终保留前 k 个 Sink Token + 最近 W 个 Token，从而实现稳定的无限长度流式推理。

Q9: vLLM、TGI、TensorRT-LLM、llama.cpp 分别适合什么场景？
  • vLLM：最适合高并发在线服务。PagedAttention 提供最优显存效率，Continuous Batching 提供高吞吐。提供 OpenAI 兼容 API。
  • TGI：适合 HuggingFace 生态用户快速部署。开箱即用，与 HF Hub 深度集成。
  • TensorRT-LLM：适合 NVIDIA GPU 上追求极致单卡性能。通过图编译和深度量化（FP8）实现最高推理速度，但配置较复杂。
  • llama.cpp：适合本地 / 边缘 / CPU 部署。纯 C++ 实现，支持 GGUF 量化在消费级硬件运行大模型。
Q10: 如何分析推理性能瓶颈？TTFT 高和 TPS 低分别怎么优化？

TTFT 高（首 Token 慢）→ Prefill 阶段瓶颈（compute-bound）：

  • 使用 FlashAttention 减少 Attention 计算开销
  • Tensor Parallel 多卡分担 Prefill 计算
  • Prompt Caching：缓存相同前缀的 KV Cache，避免重复 Prefill
  • 减少 Prompt 长度（Prompt 压缩）

TPS 低（生成慢）→ Decode 阶段瓶颈（memory-bound）：

  • 量化（INT4/FP8）减少模型权重和 KV Cache 的内存访问量
  • Speculative Decoding：一次 forward pass 生成多个 Token
  • GQA/MQA 减少 KV Cache 读取量
  • 使用更高带宽的 GPU（如 H100 vs A100）

使用 Roofline Model 可以量化分析当前系统处于 compute-bound 还是 memory-bound，从而选择正确的优化方向。

Q11: 为什么 KV Cache 只缓存 Key 和 Value，不缓存 Query？

在自回归生成中，Query 只代表当前正在生成的 Token 的查询向量——每一步的 Query 都是新的，不会在后续步骤中被复用。而 Key 和 Value 代表所有已生成 Token 的信息，在后续每一步的 Attention 计算中都需要被读取。

具体来说：生成第 t+1 个 Token 时，Q_{t+1} 需要与 K_1 到 K_{t+1} 做点积，但 K_1 到 K_t 的值与上一步完全相同（因为它们对应的是已经固定的历史 Token），所以可以缓存。Q_t 在生成完第 t 个 Token 后就不再需要了——下一步会用新的 Q_{t+1}。缓存 Query 不仅没有收益，还会浪费显存。

Q12: PagedAttention 的 Block Size 应该选多大？为什么 vLLM 默认是 16？

Block Size 是一个空间和时间的 trade-off。Block 越小，内部碎片越少（最后一个 Block 的浪费更少），但 Block Table 更大，管理开销更高，GPU Kernel 的并行效率也更低。Block 越大，GPU Kernel 可以更高效地并行处理一个 Block 内的 Token（利用 Shared Memory），但内部碎片更严重。

vLLM 选择 16 是基于实验数据的平衡点：(1) 16 个 Token × 128 head_dim = 2048 个浮点数，刚好填满一个 GPU Shared Memory Bank，Kernel 效率最高；(2) 平均内部碎片仅 8 个 Token（半个 Block），浪费可忽略；(3) Block Table 大小可控（128K 上下文 = 8192 个 Block，页表约 64 KB）。对于超长上下文（1M+），可以尝试增大到 32 以减少页表开销。

Q13: FP8 KV Cache 在长上下文（128K+）下真的能保持精度吗？需要注意什么？

可以，但需要注意两个关键点。第一，必须使用修复了 FP8 累积精度问题的 vLLM 版本（2026 年 4 月之后）。早期版本在 Flash Attention 3 内核中使用 FP16 累积，导致 128K Needle-in-a-Haystack 准确率从 91% 暴跌到 13%。修复方案是两级累积策略：Block 内使用 FP32 累积，Block 间使用 FP32 归约。

第二，对于混合注意力模型（包含滑动窗口层的模型如 gpt-oss-20b），滑动窗口层不适合 FP8——因为窗口很小（如 128 Token），FP8 的量化/反量化开销无法被足够的计算量摊薄。使用 --kv-cache-dtype-skip-layers sliding_window 跳过这些层，对大窗口层使用 FP8。在 head_dim=128 的标准模型上（如 LLaMA-3.1），FP8 KV Cache 的精度损失可以忽略。

Q14: KV Cache 占满了 GPU 显存怎么办？有哪些应急措施？

按优先级执行以下应急措施：(1) 立即措施：降低 --max-num-seqs（减少并发请求数），这会直接减少同时存在的 KV Cache 数量；(2) 降低 --max-model-len（缩短最大上下文长度），减少每个请求的 KV Cache 大小；(3) 降低 --gpu-memory-utilization 从 0.95 到 0.90，为系统预留更多缓冲空间避免 OOM。长期措施：启用 FP8 KV Cache（2x 压缩）、启用 Prefix Caching（共享前缀）、增加 GPU 数量、或切换到 GQA/MLA 架构的模型。预防措施：配置 Prometheus 监控 KV Cache 使用率，当超过 85% 时自动告警，避免等到 OOM 才发现。

Q15: Disaggregated Prefill（分离 Prefill 和 Decode）是什么？什么时候需要用它？

传统推理系统将 Prefill（处理 Prompt）和 Decode（生成 Token）两个阶段放在同一组 GPU 上执行。问题是：Prefill 是计算密集型（大矩阵并行运算），Decode 是显存带宽密集型（读取 KV Cache），两者的硬件需求完全不同。混合执行时，Prefill 会"霸占"GPU 计算资源，导致正在 Decode 的请求延迟飙升。Disaggregated Prefill 将两个阶段分离到不同的 GPU 集群：Prefill 集群专门处理 Prompt（高 GPU 计算利用率），计算完的 KV Cache 传输到 Decode 集群（高显存带宽利用率）。

适用场景：(1) Prompt 很长（>4K Token），Prefill 耗时超过 200ms；(2) 对 TPOT 延迟要求严格（<30ms/Token）；(3) 有足够的 GPU 资源部署两套集群。对于大多数短 Prompt 场景（<1K Token），Continuous Batching 已经足够，不需要 Disaggregated Prefill。

Q16: MLA 相比 GQA 有什么优势？为什么 DeepSeek-V3 能在 128K 上下文下只用 6.4 GB KV Cache？

GQA 通过减少 KV 头数来压缩 KV Cache（如 64 个 Q 头共享 8 组 KV，压缩 8x）。MLA 更进一步——它不存储完整的 K/V 矩阵，而是用一个低秩投影将 K/V 压缩到一个低维向量（Latent Vector），推理时再展开。具体来说：标准 MHA 的 KV 维度是 num_heads × head_dim（如 64 × 128 = 8192），MLA 将 KV 压缩到一个 512 维的 Latent Vector，压缩比约 16x。

DeepSeek-V3（671B MoE，61 层）使用 MLA 后，每 Token 的 KV 仅约 50 KB（对比同规模 MHA 模型约 1 MB/Token），128K 上下文下仅 6.4 GB/请求——这使得在 8×H100 80GB 上可以同时处理大量并发请求。MLA 的代价是需要额外的上投影计算（Latent → Full K/V），但这个计算量远小于重新计算 K/V 的开销。
