DP04 · 模型部署与 Serving

从训练好的模型到生产级推理服务——框架选型、性能优化与高频考点

一、模型部署挑战

模型训练完只是有了权重文件，把它变成能扛住流量的服务，中间还隔着显存、延迟、吞吐和成本四道账。

从一个权重目录到一个能对外的服务，中间要经过的几层 训练产出 ┌──────────────┐ │ 权重 + 配置 │ .safetensors / .bin + config + tokenizer └──────┬───────┘ │ 格式转换（可选）：ONNX / TensorRT engine / GGUF ▼ ┌──────────────┐ │ 推理引擎 │ KV Cache 管理、批处理调度、算子实现 │ │ 决定：单卡能装多少并发、decode 有多快 └──────┬───────┘ ▼ ┌──────────────┐ │ 服务框架 │ 多模型加载、版本管理、健康检查、指标暴露 │ │ 决定：能不能灰度、能不能一键回滚 └──────┬───────┘ ▼ ┌──────────────┐ │ 接入层 │ 鉴权、限流、超时、流式返回、重试 └──────┬───────┘ ▼ 客户端 ★ 每一层都可能成为瓶颈，但排查顺序应该反过来：先看接入层的超时与重试， 再看服务层的排队，最后才怀疑引擎——顺序搞反会浪费大量时间 ★ 换引擎的收益通常最大，换框架的收益通常最小，但后者的迁移成本反而更高

大模型推理部署面临四大核心挑战：

显存需求

  • 7B 模型 FP16 ≈ 14GB 显存（仅参数权重）
  • 70B 模型 FP16 ≈ 140GB，需要多卡甚至多机
  • 推理时还需要 KV Cache + 激活值内存

延迟要求

  • 首 Token 延迟（TTFT）：用户感知关键指标
  • Token 间延迟（ITL）：决定流式输出流畅度
  • 端到端延迟 = Prefill时间 + Decode时间

吞吐量

  • Tokens/second：单请求生成速度
  • Requests/second：系统整体并发能力
  • 吞吐量与延迟通常是 trade-off 关系

成本

  • GPU 硬件成本：A100 80GB ≈ $10k+，H100 ≈ $30k+
  • 云端 GPU 计算时长费用
  • $/1M tokens 成为衡量标准
  • 提高 GPU 利用率是降本核心
  • 能说出"延迟与吞吐量 trade-off"，知道 Batch Size↑ → 吞吐↑ 但单请求延迟↑
  • 知道 7B FP16 ≈ 14GB，能快速估算不同规模模型的显存需求
  • 理解 Prefill（计算密集）vs Decode（内存密集）的不同瓶颈

二、vLLM

vLLM 的全部竞争力可以压成一句话：把 KV Cache 当虚拟内存管，于是同样一张卡能接更多人。

开源高性能UC Berkeley

PagedAttention

  • PagedAttention 借鉴操作系统虚拟内存分页思想管理 KV Cache
  • 将 KV Cache 分为固定大小的 Block（如 16 tokens/block）
  • 按需分配物理 Block，消除内存碎片化
  • 支持 Copy-on-Write 实现 Beam Search 零拷贝
  • KV Cache 利用率从 ~20-40% 提升至 >95%

Continuous Batching

  • Continuous Batching：请求完成后立即释放 slot，新请求动态加入
  • 不同于 Static Batching 需等整个 batch 完成
  • 吞吐量提升 2-5x

Tensor Parallel

  • 支持多 GPU 张量并行推理
  • 自动将模型权重切分到多张 GPU
  • 使用 NCCL 进行 AllReduce 通信

其他特性

  • OpenAI 兼容 API：一行代码替换 OpenAI 后端
  • LoRA 支持：单次部署多个 LoRA adapter，共享 base 模型
  • Speculative Decoding：小模型草稿 + 大模型验证加速
  • Prefix Caching：相同 system prompt 复用 KV Cache

性能数据（参考）

# 吞吐量提升: ~14-24x

  • 核心：PagedAttention 解决了什么问题？→ KV Cache 内存碎片化与浪费
  • 类比操作系统分页，物理块按需分配，逻辑到物理映射表
  • Continuous Batching 与 Static Batching 的关键区别和性能差距
  • vLLM 的 OpenAI 兼容 API 如何简化迁移

三、TGI (Text Generation Inference)

TGI 卖的不是极限吞吐，是"从模型仓库到能对外的接口只差一条命令"这件事。

HuggingFaceRust实现生产级

核心特性

  • HuggingFace 出品：与 HuggingFace 生态深度集成，模型仓库直接部署
  • Rust + Python 架构：Router(Rust) + Model Server(Python)，高并发低延迟
  • Flash Attention 集成：自动使用 Flash Attention 2 加速注意力计算
  • Token Streaming：SSE（Server-Sent Events）流式返回 token
  • Watermark：内置文本水印算法，可检测 AI 生成内容

架构设计

Client Request
    ↓
[Router (Rust)] → 请求调度、Batching、队列管理
    ↓
[Model Server (Python)] → 模型推理、Flash Attention
    ↓
Token Streaming Response (SSE)

部署方式

# Docker 一键部署
docker run --gpus all -p 8080:80 \
  -v /data/models:/models \
  ghcr.io/huggingface/text-generation-inference:latest \
  --model-id meta-llama/Llama-2-13b-chat-hf \
  --quantize bitsandbytes-nf4 \
  --max-batch-prefill-tokens 4096

与 vLLM 的差异

  • TGI 更偏向"开箱即用"的企业级 Serving
  • vLLM 在纯吞吐量上通常略胜
  • TGI 的水印功能是独有亮点
  • HuggingFace Hub 集成更加无缝
  • TGI 的 Rust Router 层负责什么？→ 请求调度、动态 Batching、队列管理
  • Watermark 原理：通过影响 token 采样概率分布嵌入可检测信号
  • Flash Attention 的核心优化：减少 HBM 读写次数（IO-aware）

四、TensorRT-LLM

用编译期的复杂度换运行期的性能：引擎要针对具体 GPU 型号提前编译，换卡就得重编。

NVIDIA极致性能FP8/INT4

NVIDIA 优化

  • NVIDIA 官方推出的 LLM 推理优化库
  • 底层使用 TensorRT 引擎，针对 NVIDIA GPU 深度优化
  • 自定义 CUDA Kernel：针对 Transformer 每一层手写优化
  • 支持 Hopper（H100）特有指令集：FP8、TMA

量化支持

  • FP8（H100+）：几乎无损精度，2x 吞吐提升
  • INT8：SmoothQuant、GPTQ、AWQ
  • INT4：GPTQ、AWQ，4x 显存节省
  • Weight-Only vs Weight+Activation 量化

Inflight Batching

  • 类似 Continuous Batching，请求级别动态调度
  • 支持不同请求处于不同 decode 阶段
  • 与 Triton Inference Server 协同工作

与 Triton 集成

# TensorRT-LLM 作为 Triton Backend
model_repository/
├── preprocessing/    # Tokenizer
├── tensorrt_llm/     # TRT-LLM Engine  
├── postprocessing/   # Detokenizer
└── ensemble/         # Pipeline 编排

编译流程

# 1. 转换权重
python convert_checkpoint.py --model_dir ./llama-2-7b \
  --output_dir ./checkpoint --dtype float16

# 2. 构建 TRT Engine
trtllm-build --checkpoint_dir ./checkpoint \
  --output_dir ./engine \
  --gemm_plugin float16 \
  --max_batch_size 64 \
  --max_input_len 2048 \
  --max_output_len 512
  • TensorRT-LLM vs vLLM 核心区别？→ TRT-LLM 需要预编译 engine，针对特定 GPU 架构极致优化；vLLM 更灵活开箱即用
  • FP8 量化为什么能几乎无损？→ H100 硬件原生支持，动态范围足够覆盖 LLM 权重分布
  • Inflight Batching 和 Continuous Batching 本质相同，只是 NVIDIA 的命名

五、Triton Inference Server

Triton 不负责算得快，它负责让一堆模型在同一台机器上有序地被调用、被换版本、被观测。

NVIDIA多模型管理生产级

核心功能

  • 多模型管理：单实例同时服务多个模型（LLM、Embedding、Reranker）
  • 多 Backend 支持：TensorRT、PyTorch、ONNX、TensorFlow、Python、vLLM
  • 动态 Batching：自动聚合请求，提高 GPU 利用率
  • Model Ensemble：串联多模型形成 Pipeline（如预处理→推理→后处理）
  • 模型版本管理：支持 A/B Testing 和灰度发布

通信协议

  • gRPC：低延迟，适合内部微服务通信
  • HTTP/REST：易于调试，适合外部 API
  • Shared Memory：GPU Direct 减少数据拷贝
"引擎"和"服务框架"的分工：一次请求怎么在 Triton 里流动 ┌──── 客户端 ────┐ │ gRPC / HTTP │ └───────┬────────┘ ▼ ┌────────────────────────────────────────────────┐ │ Triton Inference Server │ │ │ │ 请求队列 ─► 动态 Batching ─► 调度 │ │ （preferred_batch_size / 最大排队延迟） │ │ │ │ │ ┌─────────────────┴──────────────────┐ │ │ │ Model Repository（多模型 + 多版本） │ │ │ │ llm/1 llm/2 ← 版本共存，可灰度可回滚│ │ │ │ embedding/1 │ │ │ │ reranker/1 │ │ │ └─────────────────┬──────────────────┘ │ │ ▼ │ │ ┌─── Backend 层（真正算的地方）────────┐ │ │ │ TensorRT-LLM │ vLLM │ ONNX │ Python │ │ │ └──────────────┴──────┴──────┴───────┘ │ └────────────────────────────────────────────────┘ Ensemble 把多步串成一次调用： 文本 ─► tokenizer ─► llm_engine ─► detokenizer ─► 文本 (Python) (TRT-LLM) (Python) 中间张量留在服务端，客户端只发一次、收一次 ★ 引擎决定"算多快"，Triton 决定"能不能安全地换版本、同时服务几个模型" ★ 动态 Batching 的排队延迟是把双刃剑：调大提吞吐，调大也直接抬高 TTFT

  • Triton 的定位：不是推理引擎本身，而是模型 Serving 的"管理平台"
  • Model Ensemble 的典型场景：Tokenize → LLM Inference → Detokenize
  • gRPC vs HTTP 选择：内部调用用 gRPC（低延迟），外部暴露用 HTTP
  • 与 TensorRT-LLM 的关系：TRT-LLM 是"引擎"，Triton 是"服务框架"

六、GPU 资源管理

显存账里最容易漏的是 KV Cache：权重是固定支出，它才是随并发和上下文一起膨胀的那部分。

GPU 显存估算公式

显存需求 ≈ 模型参数 × 精度字节 + KV Cache + 激活值内存

详细拆解：

  • 模型参数：参数量 × bytes_per_param（FP16=2B, INT8=1B, INT4=0.5B）
  • KV Cache：2 × num_layers × hidden_size × seq_len × batch_size × bytes_per_param
  • 激活值：推理时通常较小，约占参数量的 5-10%
# 示例：LLaMA-2 7B FP16, batch=1, seq_len=2048
参数显存 = 7B × 2 bytes = 14 GB
KV Cache = 2 × 32 × 4096 × 2048 × 1 × 2 bytes ≈ 1 GB
激活值 ≈ 0.5-1 GB
总计 ≈ 15.5-16 GB → 需要 1× A100 40GB 或 1× RTX 4090 24GB

# LLaMA-2 70B FP16, batch=1, seq_len=2048
参数显存 = 70B × 2 bytes = 140 GB
→ 需要 2× A100 80GB (TP=2) 或 4× A100 40GB (TP=4)

多卡推理

策略原理适用场景通信开销
Tensor Parallel (TP)将权重矩阵按列/行切分到多 GPU单节点多卡，降低延迟高（AllReduce 每层）
Pipeline Parallel (PP)将不同 Transformer 层分配到不同 GPU多节点，超大模型低（层间传递激活）
TP + PP节点内 TP，节点间 PP多节点大规模部署混合

示例场景：一个 7B 模型的推理服务，按"权重 14 GB + 一点激活值"估算，团队认为 24 GB 的卡绰绰有余，就按单卡部署上线了。

问题：白天低峰一切正常，晚高峰开始间歇性 CUDA Out of Memory，重启后又能撑一阵。复盘发现估算里只算了 batch=1、seq_len=2048 的 KV Cache（约 1 GB），而线上高峰并发有二十几路，长文档场景的上下文接近 8K，KV Cache 实际要吃掉十几 GB。更糟的是服务没有对并发做上限，请求全都接下来，直到显存耗尽整个进程崩掉，正在处理的请求一起丢失。

方案：三处改动：① 容量按"权重 + 激活 + 最大并发 × 最长上下文的 KV Cache"重算，而不是按 batch=1 估；② 在引擎层设置最大并发序列数和最大上下文长度，超出的请求排队或返回明确的限流错误；③ 加上显存占用与队列长度的监控，并在接近阈值时提前拒绝。

效果：高峰期不再 OOM，最坏情况从"整个服务崩溃"变成"少量请求排队或被限流"。这里真正的错误不是估小了一个数，而是把一个随负载变化的量当成了常数。

GPU 共享技术

  • NVIDIA MPS (Multi-Process Service)：多进程共享 GPU，适合小模型多实例
  • NVIDIA MIG (Multi-Instance GPU)：A100/H100 硬件级分区，最多 7 个独立实例
  • Time-Slicing：时间片轮转共享，最简单但延迟不稳定。Kubernetes 上开启 GPU 时间分片（如 50ms 时间片）让多个推理任务共享一张卡，实测可把 GPU 利用率从不足 50% 提升到约 90%
# MIG 分区示例 (A100 80GB)
sudo nvidia-smi mig -cgi 9,9,9  # 创建 3 个 GPU Instance (各约 20GB)
sudo nvidia-smi mig -cci         # 创建 Compute Instance

# 效果：一张 A100 变成 3 个独立的 "小 GPU"
# 适合同时部署 3 个 7B 模型
  • 能手算：给定模型参数量和精度，估算所需 GPU 数量
  • TP vs PP 的选择原则：TP 降延迟（但通信多），PP 扩规模（通信少）
  • MIG vs MPS 区别：MIG 硬件隔离（更安全稳定），MPS 软件共享（更灵活）
  • KV Cache 为什么随 batch_size 和 seq_len 线性增长？→ 每个请求每层独立缓存

七、动态 Batching

Decode 阶段 GPU 大半时间在等内存，Batching 等于把这些空档填上——吞吐几乎白捡，延迟要另算。

为什么需要动态 Batching？

  • GPU 计算能力远大于单请求需求 → 单请求 GPU 利用率极低（<10%）
  • Batching 通过并行处理多请求，提高 GPU 计算单元利用率
  • LLM 推理的 Decode 阶段是 Memory-Bound → Batch 可以"免费"增加计算

Static Batching vs Continuous Batching

特性Static BatchingContinuous Batching
请求管理等所有请求完成才释放完成一个立即释放 slot
GPU 利用率低（短请求等长请求）高（动态填充空位）
吞吐量较低2-5x 提升
实现复杂度简单需要迭代级调度
适用场景离线批处理在线 Serving
# Static Batching 的问题示意
Request A: [████████████████]  (生成 200 tokens)
Request B: [████]              (生成 50 tokens)
Request C: [██████████]        (生成 100 tokens)
                              ↑ B和C完成后空等A

# Continuous Batching
Request A: [████████████████]
Request B: [████] → 释放 → Request D: [██████]
Request C: [██████████] → 释放 → Request E: [████]
                              ↑ GPU 始终满载

最优 Batch 参数调优

  • max_batch_size：受限于 GPU 显存（主要是 KV Cache）
  • max_waiting_tokens：新请求最多等多久才被调度
  • max_concurrent_requests：同时处理的请求上限
  • 调优方向：在"延迟 SLA"约束下最大化吞吐量

关键调优参数速查

参数控制什么调大的后果调小的后果调优起点
max_batch_size同时进入一个 batch 的请求数上限吞吐上升，KV Cache 吃紧，P99 变差延迟稳定，GPU 空转，吞吐下降先按显存算出理论上限，再往下退一档
最大排队延迟为了凑批愿意让请求等多久批更满、吞吐更高，TTFT 直接被抬高TTFT 好看，批凑不满，吞吐下降取 TTFT 预算的一到两成，不要更多
max_model_len单请求允许的最大上下文KV Cache 预算被最长请求绑架长文档请求被拒，需要业务侧截断按真实分位数（如 P99 上下文）设，别按极值
max_concurrent_requests服务同时受理的请求总数队列变长，超时和重试放大压力限流更早触发，但失败可预期压测中 P99 仍达标的最大值
显存利用率上限留给 KV Cache 池的显存比例并发更高，突发流量下容易 OOM更安全，可服务并发变少先留出余量，观察峰值后再逐步上调
最大 Batch ≈ (GPU显存 - 模型参数) / (单请求 KV Cache 大小)
  • Decode 阶段为什么是 Memory-Bound？→ 每步只生成 1 token，计算量小但需读取全部权重
  • Continuous Batching 的"迭代级调度"含义：每个 decode step 都可以增删请求
  • Batch Size 增大后延迟为什么不一定线性增长？→ GPU 并行计算，Memory-Bound 阶段 Batch 几乎"免费"

八、模型格式

格式不是文件后缀的差别，而是在"能不能跨框架""加载快不快""会不会执行任意代码"之间做取舍。

格式转换流水线

PyTorch (.bin/.pt)
   ↓ torch.onnx.export()
ONNX (.onnx)          → 跨框架通用格式
   ↓ trtexec / polygraphy
TensorRT (.engine)     → NVIDIA GPU 极致优化
   
PyTorch (.bin/.pt)
   ↓ convert_to_safetensors
SafeTensors (.safetensors) → 安全 + 快速加载

PyTorch (.bin/.pt)
   ↓ llama.cpp convert
GGUF (.gguf)           → CPU/Apple Silicon 推理

各格式详解

格式用途优势劣势
PyTorch训练、研究灵活、生态完善推理慢、pickle 不安全
ONNX跨框架部署框架无关、优化工具多大模型支持有限
TensorRTNVIDIA GPU 生产推理极致性能仅 NVIDIA、编译耗时
SafeTensors安全存储与加载无代码执行风险、mmap 快速加载仅存储格式，非推理格式
GGUFCPU / 端侧推理多种量化、无需 GPU性能低于 GPU 方案

SafeTensors 为什么重要

  • PyTorch 使用 pickle 序列化 → 可注入任意代码（安全隐患）
  • SafeTensors 仅存储纯张量数据，无代码执行能力
  • 支持 mmap：加载 70B 模型只需几秒（零拷贝映射到内存）
  • 已成为 HuggingFace 默认推荐格式

示例场景：一个分类服务把模型从 PyTorch 转成引擎格式上线，离线评测准确率 九成二，符合预期。

问题：上线后线上抽检只有约 八成，且错的样本毫无规律。对齐排查时把同一条输入分别喂给离线脚本和线上服务，发现两边的 input_ids 就不一样——转换模型时只导出了权重，tokenizer 仍沿用服务镜像里旧版本的那份，两者的特殊 Token 处理方式有差异。模型没错，输入在进模型之前就已经不同了。

方案：把 tokenizer 和权重当作同一个不可分割的制品一起打包、一起版本化；发布流程加一道对齐检查：用固定的一组样本比对离线与线上的 input_ids 和输出 logits，不一致就拦住发布。

效果：线上准确率回到与离线一致的水平。这类问题的共同点是模型本身完全正常，所有指标也都是绿的，只有端到端逐字节比对才能暴露出来。

GGUF (GPT-Generated Unified Format)

  • llama.cpp 项目推出，替代旧的 GGML 格式
  • 支持 Q2_K 到 Q8_0 多种量化级别
  • 元数据自包含：Tokenizer、模型配置全在文件内
  • 适用：MacBook（Metal）、纯 CPU 服务器、边缘设备
  • SafeTensors vs pickle 的安全区别？→ pickle 可执行任意 Python 代码，SafeTensors 只有纯数据
  • TensorRT engine 为什么不可跨 GPU 架构？→ 编译时针对特定 SM 版本优化 kernel
  • GGUF 适用场景？→ 资源受限环境、没有 NVIDIA GPU、开发测试
  • ONNX 在 LLM 时代的局限？→ 动态 shape 支持、超大模型的图优化效率

📝 Q&A（Top 10）

Q1: 解释 PagedAttention 的原理和为什么能提升性能？

答：PagedAttention 借鉴了操作系统虚拟内存的分页机制来管理 KV Cache。传统方法为每个请求预分配最大序列长度的连续显存，导致大量碎片和浪费（利用率仅 20-40%）。PagedAttention 将 KV Cache 切分为固定大小的 Block（如 16 tokens），使用 Block Table 维护逻辑到物理的映射，按需分配物理块，不要求连续显存。这样 KV Cache 利用率提升至 95%+，同等显存可服务更多并发请求，吞吐量提升 2-4x。此外还支持 Copy-on-Write 语义，让 Beam Search 等场景实现 KV Cache 零拷贝共享。

Q2: Continuous Batching 和 Static Batching 的区别？为什么重要？

答：Static Batching 将一批请求组成 batch 后统一处理，必须等 batch 内所有请求都完成才能释放资源处理下一批。如果 batch 内请求生成长度差异大，短请求完成后 GPU 空转等待长请求，利用率极低。

Continuous Batching（也叫 Iteration-level Scheduling）在每个 decode step 都可以调度——某请求完成立刻释放 slot 并将排队中的新请求加入。GPU 始终满载工作，吞吐量提升 2-5x。这是现代 LLM Serving 框架（vLLM、TGI、TensorRT-LLM）的标配能力。

Q3: 如何估算一个 LLM 推理所需的 GPU 显存？

答：公式：显存 ≈ 参数显存 + KV Cache + 激活值。

①参数显存 = 参数量 × 精度字节数（FP16=2B, INT8=1B, INT4=0.5B）。例如 70B FP16 = 140GB。

②KV Cache = 2 × num_layers × hidden_dim × seq_len × batch_size × bytes_per_element。这是随 batch 和 seq_len 动态增长的部分。

③激活值在推理时较小，约参数量的 5-10%。

例如 LLaMA-2 7B FP16：14GB + ~1GB(KV) + ~1GB(激活) ≈ 16GB，一张 A100 40GB 可运行。70B FP16 约需 2×A100 80GB。

Q4: Tensor Parallel 和 Pipeline Parallel 如何选择？

答：Tensor Parallel(TP) 将每层权重矩阵切分到多 GPU，每层计算后需要 AllReduce 通信。优点是降低单请求延迟（多卡并行计算同一层），缺点是通信频繁，要求高带宽互联（NVLink）。适合单节点内多卡。

Pipeline Parallel(PP) 将不同 Transformer 层分配到不同 GPU，仅在层之间传递激活值。通信量小，适合跨节点部署。缺点是引入 Pipeline Bubble，单请求延迟不降反增。

实际生产中常用 TP + PP：节点内 TP（利用 NVLink），节点间 PP（仅需以太网/InfiniBand 传小张量）。

Q5: vLLM 和 TensorRT-LLM 分别适合什么场景？

答：vLLM 适合：需要快速部署、频繁切换模型、多 LoRA 场景、研发迭代快的团队。优势是 Python 生态友好、OpenAI API 兼容、PagedAttention 内存效率高、不需要预编译。

TensorRT-LLM 适合：已确定模型和硬件、追求极致性能和最低成本的生产环境。NVIDIA 官方手写 CUDA kernel，支持 FP8 等硬件级量化，吞吐通常比 vLLM 高 20-50%。但需要预编译 engine、模型切换成本高、部署复杂。

实际中可能组合使用：开发测试用 vLLM，线上高并发用 TensorRT-LLM + Triton。

Q6: 什么是 Flash Attention？它优化了什么？

答：Flash Attention 是一种 IO-aware 的注意力计算算法。标准 Attention 需要 O(N²) 的中间矩阵（Q×K^T），必须写入 HBM（GPU 高带宽内存），内存读写成为瓶颈。

Flash Attention 通过分块计算（Tiling）+ 在线 Softmax 算法，始终在 SRAM（片上高速缓存）中完成计算，避免 O(N²) 大矩阵的 HBM 读写。结果：计算量不变，但内存 IO 从 O(N²) 降至 O(N)，实际加速 2-4x，且支持更长序列。TGI、vLLM 等框架均内置集成。

Q7: SafeTensors 解决了什么安全问题？

答：PyTorch 的模型保存使用 Python pickle 序列化，pickle 反序列化时可执行任意 Python 代码。攻击者可以在模型文件中注入恶意代码（如 `os.system("rm -rf /")`），用户加载模型时就会执行。

SafeTensors 格式仅包含纯张量数据（Header + 原始字节），无任何可执行代码。还支持 mmap（内存映射文件），加载速度极快（零拷贝，70B 模型几秒内完成）。现已成为 HuggingFace 默认推荐格式，也被 vLLM、TGI 等框架原生支持。

Q8: MIG 和 MPS 的区别是什么？分别适合什么场景？

答：MIG（Multi-Instance GPU）是 A100/H100 硬件级别的 GPU 分区技术，将一张 GPU 物理划分为最多 7 个独立实例，每个实例有独立的显存、计算单元和缓存，完全隔离互不影响。适合多租户、需要 QoS 保证的场景。

MPS（Multi-Process Service）是 CUDA 层面的 GPU 共享技术，允许多进程共享 GPU 计算资源（时间和空间复用），但无硬件隔离。适合同一用户的多个小模型推理进程共享 GPU，对隔离性要求不高的场景。

核心区别：MIG 是硬件隔离（安全、稳定、有保证），MPS 是软件共享（灵活、利用率高、无隔离）。

Q9: 部署 LLM 时如何选择量化方案？

答：选择量化方案需考虑：精度损失容忍度、目标硬件、推理框架。

① FP8（H100+ 硬件支持）：几乎无损，推荐首选，吞吐提升 ~2x。

② INT8（SmoothQuant/W8A8）：轻微精度损失，广泛硬件支持（A100+）。

③ INT4（GPTQ/AWQ）：显存节省 4x，有一定精度损失，适合显存紧张场景。AWQ 通常优于 GPTQ。

④ GGUF 量化（Q4_K_M 等）：llama.cpp 生态，CPU/Metal 推理首选。

建议优先级：FP8 > INT8 > AWQ INT4 > GPTQ INT4 > 更低比特量化。

Q10: 生产环境部署 LLM 的完整架构是怎样的？

答：典型架构分为四层：

① 接入层：API Gateway（Kong/Nginx）→ 认证鉴权、限流、负载均衡

② 调度层：请求路由（按模型/LoRA/优先级）→ 队列管理 → 动态扩缩容信号

③ Serving 层：Triton/vLLM 实例集群 → Continuous Batching → 多模型/多LoRA

④ 基础设施层：Kubernetes + GPU Operator → 自动扩缩容（基于队列深度/GPU利用率）→ 监控（Prometheus + Grafana 看 TTFT/吞吐/GPU利用率）

关键指标监控：TTFT P99 < 500ms、吞吐量、GPU 显存/计算利用率、队列等待时间。灰度发布用 Triton 模型版本管理或 K8s Canary Deployment。
