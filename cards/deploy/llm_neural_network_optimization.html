DP18 · 神经网络与大模型性能优化

神经网络本质 → 计算架构中间层 → 算子融合 → MoE 混合专家 → 大规模专家并行 → 集合通信

大模型性能优化的全部秘密就一句话——让计算单元少搬数据、少等待、少做无用功：算子融合解决"搬运多"，MoE 解决"算得多"，专家并行与集合通信解决"等得久"。

一、神经网络的本质：算子与计算图

生物神经元接收输入信号、处理后输出信号，这个过程可以抽象为一个函数 Y = F(X)。AI 领域把这样一次基本运算称为算子（Operator）——它是神经网络里最小的可执行单元，比如一次矩阵乘法、一次激活函数、一次归一化。把成百上千个算子按一定顺序和逻辑连接起来，就构成了计算图（Computational Graph），也就是我们说的 AI 神经网络。当计算图变得特别庞大、算子多到数不清时，它就成了大模型（如 DeepSeek）：一次前向推理要穿过几十层、触发上万个算子调用。

算子是乐高积木块，计算图是拼装说明书，大模型就是一座用几百万块积木拼成的城市——城市越大，交通调度（性能优化）就越重要。

二、计算架构：模型与硬件之间的翻译官

计算架构是 AI 算法模型和底层硬件之间的中间层：它把神经网络的计算图翻译成 GPU/NPU 能识别执行的指令流，并驱动硬件真正跑起来。没有它，PyTorch 里优雅的计算图对芯片来说就是一堆看不懂的符号。

翻译过程不是逐字直译——计算架构会在翻译时顺手做大量调度优化：合并啰嗦的指令、复用内存空间、重排执行顺序。同一张计算图，翻译水平高低可以带来数倍的性能差距，这正是各家厂商在计算架构上持续投入的原因。

计算架构是同声传译：算法说"我要做一次注意力计算"，它翻译成硬件听得懂的几千条指令，还能顺手把几句啰嗦的话合并成一句——翻译信达雅的程度，直接决定硬件出力的程度。

三、算子融合：把 13 个小算子捏成 1 个

上一节说过，激活、归一化这类小算子的计算本身很快，真正的开销在数据搬运：每个算子都要从内存读入数据、算完再写回内存，下一个算子再读一遍。芯片内部计算单元的速度远快于内存读写速度，于是大量时间浪费在"等数据路上"。算子融合（Operator Fusion）的解法很直接——把多个小算子合并成一个超级大算子，中间结果全部留在芯片内部的高速缓存里，只在最开始读一次、最后写一次。

生产案例 · DeepSeek MLA 前处理优化：背景是 DeepSeek 的 MLA（多头潜在注意力）在推理时，前处理阶段包含 13 个小算子，涉及张量变形、旋转位置编码、拼接等操作。问题在于这些小算子单个计算量都极小，却要在 NPU 和内存之间来回搬运 20 多次数据，整个阶段耗时 109ms，大部分时间芯片在"等搬运"。方案是通过计算架构层的算子融合，把 13 个小算子编译成一个超级大算子，中间结果全部留在片上。效果：该阶段耗时从 109ms 降到 45ms，端到端推理性能提升超 20%——没有改一行模型代码，纯粹靠"少搬数据"赢来的。

同样的思路在注意力计算上诞生了 FlashAttention：标准实现要把 n×n 的注意力矩阵反复写回显存，而融合版本把 Q·Kᵀ、softmax、加权 V 三步捏在一个算子里分块完成，注意力部分获得 2~4 倍加速，如今已是所有大模型框架的默认实现。

与其让厨师每切一刀就跑一趟仓库取料，不如把这道菜的全部食材一次备齐放在案板上——算子融合就是"备菜上桌一次完成"。

四、MoE 混合专家：参数多，但每次只用一小撮

稠密模型有一条残酷的规律：参数规模超过临界点后，继续堆参数带来的收益越来越小，而计算资源消耗成倍增加——每个 token 都要穿过全部参数，推理成本随模型线性上涨。MoE（Mixture of Experts，混合专家模型）换了一个思路：把模型的前馈层拆成多个专家子网络，用户输入先经过门控网络（Router/Gate）打分，只分发给得分最高的少数几个专家参与计算。总参数量可以做得很大（知识容量大），但单次推理只激活一小部分（计算量小）。

生产案例 · DeepSeek-V3 的 MoE 账本：背景是稠密模型路线上，70B 级别模型的训练和推理成本已经让大多数团队望而却步。问题是：想要更强的能力就要更大的参数，但更大的参数意味着更贵的推理，形成死结。方案是 MoE 架构——DeepSeek-V3 设置 256 个路由专家 + 1 个共享专家，每个 token 只激活 Top-8 个专家，总参数 671B 而激活参数仅 37B（约 5.5%）。效果：以约 278.8 万 H800 GPU 时（官方论文披露约 557.6 万美元）完成预训练，成本仅为同级别稠密模型的零头；推理时只算 37B 参数的算力，却拥有 671B 的知识容量，"满血版 DeepSeek"正是靠这套架构实现了能力与成本的同时破局。

MoE 像一家综合医院：你感冒不需要挂遍所有科室，导诊台（门控网络）把你分给最对口的 8 位医生。全院 256 位医生的知识都在，但每次问诊只消耗 8 位的精力。

五、大规模专家并行与集合通信

MoE 用激活参数换来了推理效率，但总参数是实打实的：671B 参数即使用 FP16 存储也要约 1.3TB 显存，单张 80GB 的 AI 卡连零头都装不下。解决方案是专家并行（Expert Parallelism）——把专家拆分到多张 NPU 卡上做分布式部署，每张卡专注负责一个或少数几个专家，门控网络把 token 路由到目标专家所在的卡上计算。

专家分散之后，token 就必须在卡之间流动，这就需要高效的集合通信（Collective Communication）。HCCL（Huawei Collective Communication Library，华为集合通信库）专门优化 NPU 集群通信，核心手段包括：

  • NPU Direct 通信：卡间数据绕开 CPU 直接传输，降低小包通信耗时；
  • 超节点架构：多张卡组成一个节点，节点内部高速互联，节点之间用光模块组成带宽网络；
  • 一卡一专家：每张卡专注负责一个或少数专家，避免卡内排队。

并行策略就是"分活儿的艺术"：数据并行是每人做一份不同的卷子，张量并行是多人合做一道大题，流水线并行是接力赛，专家并行是专科门诊——选哪种，取决于活儿（模型）长什么样。

六、负载均衡：动态冗余与亲和部署

专家并行的理想很丰满，现实却有个坑：token 的路由分布并不均匀。写代码的 token 可能都涌向"代码专家"，聊天气的 token 都去找"闲聊专家"——热门专家的卡前排起长队，冷门专家的卡却在空转。整个系统的吞吐被最忙的那张卡锁死，这就是负载不均问题。

技术解决的问题方法
动态专家冗余热点专家负载不均，排队严重在线分析各专家实时负载，给热门专家动态增加备份副本，token 分流到多个副本上
专家亲和部署协同专家被分散到不同节点，跨节点通信慢离线分析路由共现关系，将经常同时被激活的专家编排到同一节点，减少约 30% 跨节点通信量
生产案例 · 亲和部署砍掉三成跨节点流量：背景是 MoE 模型做大规模专家并行后，每个 token 都要通过 All-to-All 通信被送到目标专家所在的卡。问题在于，如果随机分配专家的部署位置，经常协同工作的专家对（比如"代码语法专家"和"代码补全专家"）很可能被拆到不同节点，每次路由都要走节点间的慢速链路，通信延迟成为推理耗时的主要部分。方案是先离线分析历史路由数据，找出高共现的专家组合，再把它们编排进同一个超节点，让高频通信发生在节点内部的高速互联上。效果：跨节点通信量减少约 30%，端到端推理延迟显著下降，而且这是纯调度层面的优化，不改动任何模型参数。

负载均衡的本质是让每张卡都"忙得均匀"：热门专家多开几个分身（动态冗余），老搭档尽量安排在同一间办公室（亲和部署）——排队消失了，整体吞吐自然上去了。

  • 优化前先 profiling：确认瓶颈在计算、搬运还是通信，再对症下药
  • 优先做算子融合——它不改模型、不加参数，收益立竿见影
  • MoE 部署时监控各专家的负载分布，及时发现热点专家
  • 跨节点通信能省则省：把高频协同的专家/层放进同一节点
  • 不要盲目堆卡：负载不均时，加卡只会放大通信开销
  • 不要忽略小算子：单个不起眼，13 个串起来就是 109ms
  • 不要静态分配专家副本：流量模式会随业务时段变化，冗余必须动态调整
  • 不要把张量并行跨节点部署：层内通信频率极高，跨节点延迟会拖垮整条流水线

Q&A

什么是 MoE？它解决了什么问题？
MoE（Mixture of Experts，混合专家模型）是一种模型架构：模型内部包含多个专家子网络，用户输入由门控网络打分后，只分发给得分最高的少数几个专家参与计算。它解决的问题是稠密模型的规模困境——当稠密模型参数超过临界点后，增加参数带来的收益越来越小，而每个 token 都要穿过全部参数，计算资源消耗成倍增加。MoE 单次推理只激活部分专家（如 DeepSeek-V3 总参 671B、激活仅 37B），在大幅减少计算量的同时保持与更大稠密模型相近的效果。代价是总参数量巨大，单卡装不下，必须配合多卡专家并行部署。
算子融合是什么？为什么能提升性能？
算子融合是将多个小算子合并成一个超级大算子的编译期优化技术。它能提升性能的原因在于数据搬运：原本多个小算子依次执行，每个算子都要在 NPU（计算单元）和内存之间读写一次数据，而芯片计算速度远快于内存读写速度，大部分时间浪费在等数据上。融合后变成一个大算子，只需一次读入和一次写回，中间计算全在芯片内部的高速缓存中完成。以 DeepSeek MLA 前处理为例，13 个小算子原本搬运 20 多次、耗时 109ms，融合后降到 45ms，端到端推理性能提升超 20%。
为什么说计算架构是模型与硬件之间的"中间层"？
因为算法和硬件说的是两种"语言"：算法层（如 PyTorch）描述的是计算图——哪些张量做什么运算、按什么顺序连接；而 GPU/NPU 硬件只能执行底层的线程调度和内存指令。计算架构（如 NVIDIA 的 CUDA、华为的 CANN）负责中间的翻译工作：把计算图编译成硬件可执行的指令流，分配计算核心，驱动硬件运行。更关键的是，翻译过程不是直译——计算架构会顺手做算子融合、内存复用、流水编排等调度优化，同一张计算图在不同计算架构下的性能可以差出数倍。所以它不只是传话筒，而是直接决定硬件出力程度的"调度中枢"。
为什么不把稠密模型做得更大，而要转向 MoE？
因为稠密模型的 scaling 收益在递减，而成本在递增。稠密模型每增加一倍参数，推理时每个 token 的计算量也增加一倍——能力和成本被绑死在同一条曲线上。研究和实践都表明，当参数规模超过某个临界点后，继续堆参数带来的能力提升越来越小，但训练和推理的账单却线性上涨。MoE 把"知识容量"和"计算成本"解耦：总参数可以做得很大（256 个专家容纳海量知识），但每个 token 只激活 Top-k 个专家（DeepSeek-V3 只算 5.5% 的参数）。代价是显存占用依然很大、需要复杂的专家并行和负载均衡，但对于追求"低成本高能力"的推理场景，这笔账是划算的。
专家分散到多张卡之后，token 是怎么找到目标专家并通信的？
这个过程分两步：路由和通信。首先门控网络在每个 token 上计算出 Top-k 个目标专家的编号，这一步与专家部署在哪无关。然后由集合通信库（如华为的 HCCL）执行 All-to-All 通信：每张卡把本地 token 按目标专家的位置打包，发送到对应专家所在的卡，各卡收到后本地计算，再把结果通过 All-to-All 送回。为了降低通信开销，HCCL 采用 NPU Direct 让卡间数据绕开 CPU 直接传输，并用超节点架构把多张卡组成内部高速互联的节点、节点间用光模块连接。通信效率直接决定 MoE 的扩展性——这也是亲和部署（把协同专家放同一节点）能省下约 30% 跨节点通信量的原因。
热点专家负载不均怎么解决？
负载不均的根源是 token 路由分布不均匀：某些专家（如代码类）被频繁选中，对应的卡排起长队，而冷门专家的卡在空转，系统吞吐被最忙的卡锁死。解决手段有两类。第一类是动态专家冗余：在线监控各专家的实时负载，给热门专家动态增加备份副本，把流量分流到多个副本上，负载下降后再回收副本。第二类是专家亲和部署：离线分析路由共现关系，把经常同时被激活的专家编排到同一节点，让高频通信走节点内高速链路而非跨节点慢速链路，可减少约 30% 的跨节点通信量。两者配合，一个解决"忙闲不均"，一个解决"通信太慢"。
数据并行、张量并行、流水线并行、专家并行该如何选择？
选择取决于模型形状和硬件拓扑。如果模型能装进单卡，优先数据并行——每卡一份完整模型、算不同的数据批次，只需周期性 AllReduce 同步梯度，实现最简单、扩展性最好。如果单层权重太大，用张量并行在层内切矩阵，但它通信频率极高，必须限制在节点内部使用。如果模型层数多、总参数大，用流水线并行按层切分到不同节点，注意控制流水气泡带来的空转。如果是 MoE 模型，专家天然适合专家并行——每卡负责少数专家，用 All-to-All 路由 token。实践中大规模训练往往四种混用：节点内张量并行、节点间流水线并行、全局数据并行，MoE 层再叠加专家并行。
