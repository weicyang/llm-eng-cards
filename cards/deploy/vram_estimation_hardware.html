显存里只装四样东西：权重、KV Cache、激活值、框架开销。其中三样是常数，只有 KV Cache 会随着用户数和上下文长度往上长——所以"这张卡能跑什么模型"是一道加法题，而"这张卡能扛多少并发"才是那道真正会把你半夜叫醒的题。

一、显存总账：四大占用项

部署前最常见的错误估算是"70B 模型 FP16 是 140GB，两张 80GB 的卡够了"。这个算法漏掉了三项，而漏掉的部分恰恰决定了服务在真实流量下能不能活。把显存当成一本账来记，只有四个科目：

Mtotal = Mweights + Mkv + Mact + Mframework
占用项是什么大小特征受什么影响估算难度
权重 Mweights模型参数本身静态，加载后不变参数量 × 量化精度极易，一乘就出
KV Cache Mkv历史 token 的 Key/Value 缓存动态，随上下文与并发线性增长层数、KV 头数、序列长度、并发数、KV 精度中等，需查模型配置
激活值 Mact前向传播的中间张量瞬时峰值，随批内 token 数增长batch 内 token 总数、隐藏维度难，通常靠经验比例
框架开销 MframeworkCUDA context、通信缓冲、分配器碎片、CUDA Graph近似固定的"税"驱动版本、并行方式、引擎配置难，只能实测

四项里权重是唯一可以精确预知的，KV Cache 可以按公式算准，后两项通常合并处理——业界的通行做法是给总量加 10%-20% 的余量，或者等价地把可用显存按标称值的 85%-90% 来算。Hugging Face 官方的模型显存估算器也明确提醒过：它给出的数字"只够把模型加载进来，不足以完成推理"，做推理需要在此基础上再加最多 20%。

这张图揭示了一个反直觉但极其重要的事实：决定服务能力的不是"模型装不装得下"，而是"装完之后还剩多少"。同样是 70B 装进一张 H100，用 4-bit 量化能留下 36.5 GiB 给 KV，用 FP8 量化就只剩不到 5 GiB——前者能服务十几路并发，后者连一路 32K 长上下文都放不下。

把显存想成一间办公室：权重是搬不走的办公桌，占多大取决于你买的是什么型号；KV Cache 是每来一个客人就要摆一把椅子的空地；激活值是过道，人多的时候必须留出来；框架开销是墙壁和柱子的厚度。桌子选小一号，能摆的椅子就多好几倍——这就是量化的全部意义。

二、权重显存与量化精度

权重显存是四项里唯一能一步算出来的，它就是参数量乘以每个参数占用的字节数：

Mweights = 参数量 P × 每参数字节 bw

每参数字节由存储精度决定：FP32 是 4 字节，FP16/BF16 是 2 字节，FP8 与 INT8 是 1 字节，INT4/NF4 是 0.5 字节。推理场景下 FP32 已基本不用（相对 FP16 没有质量收益却翻倍占用），所以实际选择只在 2 / 1 / 0.5 这三档之间。

精度每参数字节7B14B32B70B质量与适用性
FP32428 GB56 GB128 GB280 GB推理无必要，纯浪费
FP16 / BF16214 GB28 GB64 GB140 GB基线精度，无损参照系
FP8 / INT817 GB14 GB32 GB70 GB质量损失通常可忽略，H100 及以后有原生 FP8 算力
INT4（AWQ/GPTQ）0.53.5 GB7 GB16 GB35 GB常见退化在 1%-2% 以内，量化流程质量差异较大

三个容易踩的细节。第一，实际权重文件通常比理论值大 5%-15%：量化只作用于线性层权重，embedding 层、归一化参数、量化用的 scale 与 zero-point 往往仍以更高精度保存，所以 70B INT4 的实测占用常在 32-38 GB 而非教科书上的 35 GB。能拿到真实 checkpoint 时，永远以文件大小为准，不要用参数量反推。

第二，MoE 模型要按总参数算，不能按激活参数算。一个 109B 总参数、17B 激活参数的 MoE 模型，推理时虽然每 token 只激活 17B 的计算量，但所有专家的权重都必须常驻显存，FP16 下依然要 218 GB。用激活参数估显存是 MoE 部署中最经典的翻车方式。

第三，量化压得了权重，压不了 KV Cache。这是本文最需要记住的一句话。把 70B 从 FP16 压到 INT4，权重从 140 GB 降到 35 GB，收益巨大；但每个 token 的 KV 占用一分未变，仍然是 320 KiB。这就导致大量团队在"模型终于装进单卡了"的喜悦中上线，然后被长上下文请求瞬间打爆——他们省下的空间，被 KV Cache 一口吃回去了。要压 KV 得用另一个开关：--kv-cache-dtype fp8。

量化不是"让模型变小"，而是"把省下来的空间换成并发"。一次 FP16 到 INT4 的量化，在 80GB 卡上把 70B 的 KV 空间从不到 5 GiB 撑到 36 GiB，可服务的并发从 1 路涨到 14 路——真正的收益从来不在权重那一行，而在被腾出来的那一大格。

三、KV Cache：并发上限的真正阀门

为什么会有 KV Cache

自回归生成时，模型每产出一个新 token 都要对之前所有 token 做注意力计算。如果每步都重新计算全部历史 token 的 Key 和 Value 投影，复杂度是平方级的，完全不可用。KV Cache 就是把每一层每个 token 的 K、V 向量算一次存下来，后续步骤直接读取。它把计算问题转成了存储问题——代价是这份存储会随对话变长、用户变多而无止境地涨。

逐项拆解的公式

Mkv = 2 × layers × kv_heads × head_dim × seq_len × batch × dtype_bytes
因子含义去哪里找典型值
2一份 Key 加一份 Value常数2
layersTransformer 层数，每层各存一份num_hidden_layers7B 约 28-32；70B 为 80
kv_headsKV 头数，GQA 下远小于查询头数num_key_value_heads常见 4 或 8
head_dim每个头的维度head_dim 或 hidden_size ÷ num_attention_heads绝大多数为 128
seq_len输入加输出的总 token 数你的真实流量分布，不是模型声明的最大值按 P99 取
batch同时在跑的序列数你的并发目标由 max_num_seqs 约束
dtype_bytesKV 的存储精度默认与权重一致，可单独降为 FP82 或 1

把 seq_len 和 batch 抽出来，剩下的部分是模型的固有属性，值得单独记住——每 token 的 KV 字节数。有了它，任何容量问题都变成一次除法。

GQA 与 MQA：把 kv_heads 压下去

公式里唯一可以由架构设计压缩的因子是 kv_heads。原始的多头注意力（MHA）让每个查询头配一套独立的 K/V，分组查询注意力（GQA）则让若干个查询头共享同一套 K/V，多查询注意力（MQA）走到极端，全部查询头共用一套。压缩比就是查询头数除以 KV 头数。

这也解释了为什么查模型配置时必须看 num_key_value_heads 而不是 num_attention_heads——两者在现代模型上相差 4 到 8 倍，用错了显存估算就会离谱地偏大。

反过来用：算出 token 预算

实际部署中更常问的问题不是"要多少显存"，而是"这张卡能扛多少"。把公式反解即可：

总 token 预算 N = (利用率 u × 卡显存 − 权重 − 框架开销) ÷ 每 token KV 字节

这个 N 是所有并发序列的 token 总数上限，怎么切分由你决定：可以是少数几路长上下文，也可以是很多路短上下文。三个真实配置的算例：

生产案例：长上下文请求打爆一个"容量充足"的服务。某文档问答服务用单卡 A100 80GB 部署 Qwen2.5-32B AWQ，上线时按"权重 18 GiB，卡有 80 GiB，绰绰有余"的判断把 max_model_len 设成了模型声明的 131072。压测阶段用 2K 左右的短问答跑，60 路并发稳定无异常，团队据此定了 50 QPS 的容量承诺。上线第三周开始出现规律性的 P99 尖刺和大量请求超时，日志里 vllm:num_preemptions_total 持续攀升。排查发现真实流量中有约 6% 的请求是整份合同全文分析，单条 40K-60K token。按公式核算：KV 池 51.1 GiB ÷ 256 KiB = 约 209,000 token 总预算，一条 60K 的请求就吃掉 29%，四条同时进来 KV 池就见底，引擎开始驱逐并重算其他请求，形成雪崩式抖动。修复只改了三个参数：max_model_len 从 131072 降到实测 P99 的 24576，max_num_seqs 从 256 降到 32，并对超长文档在应用层改走分段摘要。改完后抢占计数归零，P99 从 11.4 秒回到 1.8 秒，稳定并发反而从 38 路升到 52 路。容量不是被平均值决定的，是被尾部决定的。

权重决定"门票价格"，KV Cache 决定"场馆座位数"。买票只花一次钱，座位却是每来一个人、每多待一分钟都要占的。所以真正需要盯住的运行指标不是显存总占用，而是 KV 池的占用率——它接近 100% 的那一刻，服务的延迟曲线就开始失控。

四、激活值与框架开销

激活值：被 Prefill 尖峰放大的那一项

激活值是前向传播过程中产生的中间张量——注意力分数矩阵、FFN 的中间层输出、各种临时缓冲。它和 KV Cache 的关键区别是用完即弃：一层算完就可以释放，所以它占用的是"峰值"而不是"累积量"。

正因为是峰值，它的大小不取决于历史长度，而取决于单次前向传播里一起处理的 token 总数。这就带来了推理服务里一个非常典型的故障形态：一台已经平稳流式输出了几小时的服务器，会在某人粘贴进一份长文档的瞬间崩掉。Decode 阶段每步只处理 batch 内每序列一个新 token，激活值很小；而 Prefill 阶段要一次性并行处理整段输入，激活值瞬间放大几十上百倍。压垮服务的是 Prefill 尖峰，不是稳态。推理引擎用分块预填充（chunked prefill）把长输入切成小块分多步处理，正是为了削掉这个尖峰。

阶段一次处理的 token 数激活值量级显存风险缓解手段
Prefill（预填充）整段输入，可达数千至数万大，随批内 token 数近线性高，OOM 多发生在此分块预填充、降低 max_num_batched_tokens
Decode（解码）每序列 1 个小，基本可忽略低无需特别处理
混合批（连续批处理）新请求的 prefill 与在跑请求的 decode 混合由 prefill 部分主导中高，取决于调度策略限制每步 prefill 配额

框架开销：那些不写在任何公式里的显存

剩下的一类是"税"，它们不属于模型，但确实占着显存。这部分几乎无法精确预测，只能靠实测和留余量。

最后一行值得单独提醒：厂商标称的 80 GB 是十进制 GB，操作系统和框架报告的是二进制 GiB，两者差约 7%。一个恰好算到 79.8 GB 的部署方案，在真实的 74.5 GiB 面前根本起不来。所有估算都应该统一在 GiB 单位下做，并且把"卡满"的定义设在标称容量的 85% 左右，而不是 100%。

激活值是过道，框架开销是墙。它们都不产出任何服务能力，但少留一寸就会在最忙的那一刻把人卡死。工程上处理这两项的正确态度不是精算，而是留白——把可用显存按 85%-90% 计，剩下的交给运气以外的东西。

选卡时容易只盯显存容量而忽略显存带宽。Decode 阶段是彻底的带宽密集型任务——每生成一个 token 都要把全部权重从显存读一遍，所以生成速度基本正比于带宽。同样是 80GB，H100 的 3.35 TB/s 相对 A100 的 2 TB/s 意味着 decode 速度快约 1.7 倍。在长上下文高并发场景下，算力与带宽的差距还会被进一步放大，导致"看起来更贵"的新卡反而单请求成本更低。

生产案例：把 KV Cache 降到 FP8，并发翻倍且质量无感。某代码助手服务用 2×H100 跑 32B FP8 权重，平均上下文 12K，原本稳定支撑 22 路并发，再多就出现抢占。团队本想加卡，先做了一次 KV 精度实验：加上 --kv-cache-dtype fp8 后，每 token KV 从 256 KiB 降到 128 KiB，KV 池能容纳的 token 总数直接翻倍，稳定并发从 22 路升到 47 路（未到理论 2 倍是因为激活与调度开销并未同步下降）；在 500 条内部代码补全评测集上，通过率从 71.2% 变为 70.8%，差异落在评测噪声范围内。这一步等价于凭空多出一张 H100，改动只有一个启动参数。需要说明的边界：KV 量化在超长上下文与数学推理类任务上偶有可感知退化，务必用自己的评测集验证过再上线，不能照搬他人结论。

"这张卡能跑什么模型"是一个不完整的问题，完整版本是"这张卡能以多长上下文、多少并发跑什么模型"。前者是加载得下，后者才是服务得动，两者之间常常隔着一整个数量级。

六、vLLM 三参数与 OOM 排查

三个参数如何共同决定显存

理解 vLLM 显存行为的前提是知道它不是按需分配的：启动时先加载权重，再跑一次前向传播profile 出激活峰值，然后把剩余的显存一次性全部圈走作为分页 KV 缓存池。所以 vLLM 的 OOM 绝大多数是预算配置错误，而不是内存泄漏。

KV 池 = gpu_memory_utilization × 总显存 − 权重 − 激活峰值 − 非 torch 分配 − CUDA Graph

一个高频误解需要澄清：gpu_memory_utilization 是占总显存的比例，不是占剩余空闲显存的比例。如果卡上已经有别的进程占了 20 GB，把这个值设成 0.9 会让 vLLM 试图使用 72 GB 而不是剩余的 60 GB，启动瞬间就撞墙。共享 GPU 场景必须手动扣掉他人占用后再折算。

三个参数与显存的因果链（顺着箭头读，就是调参的思路） gpu_memory_utilization ──► 引擎总预算 │ ├── 减去 权重（由量化精度决定，静态） ├── 减去 激活峰值（受 max_num_batched_tokens 影响） ├── 减去 CUDA Graph（受 max_num_seqs 影响） ▼ ★ KV 缓存池 ★ │ ┌──────────────┴──────────────┐ ▼ ▼ max_model_len max_num_seqs （单序列最长多少） × （同时几路） └──────────────┬──────────────┘ ▼ 两者乘积 ≤ KV 池 token 预算 超出 → 请求排队 → 抢占重算 → P99 雪崩 调参口诀：先砍 max_model_len（改真实 P99），再砍 max_num_seqs， 最后才动 gpu_memory_utilization——它的可调空间只有几个百分点。

排查顺序：从最省事到最伤筋动骨

OOM 排查最忌讳的是一上来就调 gpu_memory_utilization——它的可调空间只有几个百分点，且逼近 1.0 时反而更容易因碎片崩溃。正确的顺序是先做诊断，再削减需求，最后才改变部署形状。

# 排查顺序（自上而下，多数问题在第三步解决）
1. nvidia-smi          确认 GPU 独占，无残留进程占用
2. 读启动日志          找 "Available KV cache memory" 与引擎给出的建议值
3. --max-model-len     降到真实 P99（输入+输出），最高频有效的一步
4. --kv-cache-dtype fp8  上下文常超 7K 时，每 token KV 直接减半
5. --max-num-seqs      压低并发，同时削掉激活峰值与图捕获规模
6. --enforce-eager     放弃 CUDA Graph 换显存（代价是 decode 变慢）
7. 量化权重 / 提高 --tensor-parallel-size / 换更大显存的卡

第二步值得强调：动手改参数之前一定要先读启动日志。vLLM 会明确打印出它实际拿到了多少 KV 缓存显存，这个数字加上前面的公式，能让你在一分钟内判断问题出在权重、开销还是配置上，而不是靠盲目试参数。运行期则要盯两个指标：vllm:kv_cache_usage_perc 长期贴近 100% 说明容量不足，新请求会被迫排队；vllm:num_preemptions_total 持续上涨说明已经在抢占重算，这是延迟雪崩的前兆，必须立刻降并发或扩容。

  • 先查 num_key_value_heads 再算 KV，别用注意力头数
  • 用真实流量的 P99 长度设 max_model_len，不用模型声明值
  • 统一在 GiB 下估算，把"卡满"定义在标称容量的 85%
  • 能拿到 checkpoint 就以文件大小为准，不用参数量反推
  • MoE 按总参数算权重，所有专家都要常驻显存
  • 上线前用尾部长请求压测，而不是只用平均长度
  • 监控 KV 池占用率与抢占计数，而不只是显存总量
  • KV 量化到 FP8 前，先在自己的评测集上验证质量
  • 不要以为量化压小了权重就等于解决了显存问题，KV 一分没少
  • 不要把 gpu_memory_utilization 当成占剩余显存的比例
  • 不要为了救 OOM 把利用率推到 0.98，碎片会让它更容易崩
  • 不要用 MoE 的激活参数量估权重显存，那会少算好几倍
  • 不要在 128K 声明上下文上直接开服务，那是给尾部请求留的炸弹
  • 不要只按平均上下文长度做容量规划，容量由尾部决定
  • 不要忽略 GB 与 GiB 约 7% 的换算差，算到贴边的方案起不来
  • 不要在没读启动日志的情况下盲目试参数

vLLM 的显存模型可以用一句话概括：它先把权重放好，再留出干活的过道，然后把剩下的全部空间铺成 KV 停车场。你能停多少车，等于停车场面积除以每辆车的占地——max_model_len 决定车有多长，max_num_seqs 决定放几辆，两者的乘积一旦超过面积，引擎就只能开始拖车（抢占重算），而拖车的那一刻，用户看到的就是延迟雪崩。

Q&A

估算模型显存最快的心算方法是什么？

分两步。第一步算权重：参数量乘以每参数字节，FP16 是 2、FP8/INT8 是 1、INT4 是 0.5，所以 7B 的 FP16 就是 14 GB，70B 的 INT4 就是 35 GB，非常好记。第二步算 KV Cache：查模型配置里的层数、num_key_value_heads 和 head_dim，用"2 × 层数 × KV头数 × head_dim × 精度字节"得到每 token 的字节数，再乘以你的上下文长度和并发数。最后把两者相加，除以 0.85 到 0.9 得到含激活与框架开销的总需求。一个更快的粗算是：把每 token KV 记住（7B 约 56 KiB、8B 约 128 KiB、32B 约 256 KiB、70B 约 320 KiB），任何容量问题就变成一次除法。

为什么模型量化到 INT4 之后，长上下文还是会爆显存？

因为量化只压缩了权重，完全没有触碰 KV Cache。以 70B 为例，从 FP16 量化到 INT4，权重从 140 GB 降到 35 GB，看起来单卡装得下了；但每个 token 的 KV 占用仍然是 320 KiB，一条 128K 的长上下文请求需要 40 GiB 的 KV，比量化后的权重本身还大。这就是"模型终于装进去了，一来长请求就崩"的根本原因。要压 KV 得用独立的开关，也就是把 KV 的存储精度单独降到 FP8，这能让每 token 占用减半。另外两个有效手段是把上下文上限设到真实需求而非模型声明的最大值，以及降低同时在跑的序列数。

GQA 和 MQA 到底怎么把显存压下来的？为什么现在的模型都用 GQA？

KV Cache 公式里有一项是 KV 头数。原始的多头注意力让每个查询头配一套独立的 Key/Value，Llama-3-70B 有 64 个查询头，如果用这种方式每 token 要占 2.5 MiB。分组查询注意力让若干查询头共享一套 KV，70B 实际用的是 8 个 KV 头，也就是每 8 个查询头共享一组，KV 直接压缩 8 倍到 320 KiB。多查询注意力更极端，全部查询头共用一套，压缩 64 倍到 40 KiB，但表达能力损失明显。业界收敛到 GQA，是因为它在实测中把 KV 压掉数倍的同时，质量损失通常在 0.2% 以内，属于几乎白拿的优化。实践上的提醒是：估算显存时一定要看配置文件里的 num_key_value_heads，用注意力头数会把结果算大好几倍。

vLLM 里 gpu_memory_utilization 应该设多少？调到 0.98 行不行？

常规建议是 0.90 到 0.95。这个参数是引擎可以使用的显存占总显存的比例，不是占空闲显存的比例——如果卡上还有别的进程占了 20 GB，设 0.9 会让引擎试图使用总量的 90% 而直接撞墙，共享卡场景必须手动扣掉他人占用后折算。调到 0.98 通常不是好主意：留白不只是"浪费"，它还要吸收 CUDA context、通信缓冲和分配器碎片，而碎片会随运行时间累积，逼近满载时反而更容易在几小时后突然崩溃。更重要的是，这个参数的可调空间只有几个百分点，而降低上下文上限动辄能让 KV 池容量翻倍——遇到 OOM 应该优先动后者，而不是把利用率往 1.0 推。

服务平稳跑了几小时，突然被一个请求打崩，为什么？

典型的 Prefill 尖峰问题。生成阶段每一步只处理每个序列一个新 token，激活值很小，所以稳态运行看起来非常健康。但当有人粘贴进一份长文档时，引擎需要一次性并行处理整段输入来构建它的 KV Cache，这一步的激活值会瞬间放大几十到上百倍，同时还要为这条长序列申请大量 KV 块。两个压力叠加，就在那一瞬间超出了预算。另一种表现形式是不直接 OOM 而是触发抢占：引擎为了给新请求腾地方，把正在生成的其他请求驱逐并稍后重算，导致所有用户的延迟同时飙升。缓解手段是开启分块预填充把长输入切成小块分步处理，降低每个调度步的 token 上限，同时把上下文上限设到真实 P99 而不是模型声明的最大值。

为什么 MoE 模型不能按激活参数量估显存？

因为激活参数量描述的是计算量，不是存储量。混合专家模型每处理一个 token 只会路由到少数几个专家，所以每 token 的浮点运算量对应的是激活参数规模；但路由是逐 token 动态决定的，你无法预知下一个 token 会用到哪几个专家，因此所有专家的权重都必须常驻显存。一个 109B 总参数、17B 激活参数的模型，FP16 下权重占用是按 109B 算的 218 GB，而不是按 17B 算的 34 GB，差了六倍多。这是 MoE 部署里最经典的翻车方式：按激活参数订了硬件，模型根本加载不进来。正确做法是权重按总参数算，吞吐和延迟才按激活参数的计算量来预估。

选卡时该优先看显存容量还是显存带宽？

两者管的是不同的事，得分开看。显存容量决定"能不能跑"以及"能扛多少并发"，因为它同时约束权重和 KV 池；显存带宽决定"跑多快"，因为解码阶段每生成一个 token 都要把全部权重从显存完整读一遍，是彻底的带宽密集型操作，生成速度基本正比于带宽。实践中的判断顺序是：先用容量公式圈定候选卡型，确保目标模型加上目标并发的 KV 能装下；再在满足容量的候选里按带宽和算力挑。容易被忽视的是，同样 80GB 的 A100 和 H100，后者带宽高出约 1.7 倍，在长上下文高并发场景下单请求成本反而可能更低——评价指标应该是"每 GB 显存能承载多少有效并发"和"每请求成本"，而不是"每 GB 显存多少钱"。

把 KV Cache 量化到 FP8 有什么代价？值不值得开？

收益非常直接：每 token 的 KV 占用减半，KV 池能容纳的 token 总数翻倍，等价于并发能力接近翻倍或者上下文上限翻倍，而这只是一个启动参数。实测中并发提升往往达不到理论的两倍，因为激活值和调度开销没有同步下降。代价方面，KV 量化引入的是数值精度损失，在常规对话、摘要、分类这类任务上通常察觉不到，但在超长上下文和数学推理这类对数值稳定性敏感的任务上偶有可感知退化。所以结论是：上下文经常超过七八千 token 的服务几乎都应该试一试，但必须先在自己的评测集上跑一遍回归，确认关键指标的变化落在噪声范围内再上线，不能照搬别人的结论。

做容量规划时，用平均上下文长度算够不够？

不够，而且这是生产事故的常见来源。KV Cache 的占用由当前在跑的请求决定，而不是由历史平均值决定。一个平均 2K 上下文的服务，如果有 5% 的请求是 50K 的长文档分析，那么在这些长请求同时到达的时刻，几条请求就能吃掉大半个 KV 池，引发排队和抢占重算，进而让所有用户的延迟一起崩。正确做法是按 P99 甚至 P99.9 的长度做容量规划，并且在压测时刻意混入真实比例的长尾请求，而不是拿平均长度跑一遍就定容量承诺。如果尾部请求确实超出硬件能力，工程上的解法通常是在应用层拦截：对超长输入改走分段摘要或检索增强，而不是硬扛。
