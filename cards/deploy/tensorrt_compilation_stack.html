编译式推理的交易条款只有一句：把"每次跑都要做的决策"提前到构建期做一次，做得比运行时更好；代价是产物变成一块绑死了硬件、驱动和版本的二进制。所以评估 TensorRT 从来不是"它快不快"，而是"这块二进制在你的机型矩阵、发布节奏和运维体系里，养不养得起"。

一、编译式与解释式：先 build 再跑换来了什么

TensorRT 官方文档把它的工作模型拆得非常干净，两句话就能概括：构建期由 builder 编译你的网络，为目标 GPU 上的每一层挑出最快的可用 kernel，产出一个序列化的二进制，叫 engine（也叫 plan file）；运行期由 runtime 把 engine 载入进程并在 GPU 上执行。理解这两段的分工，就理解了编译式推理的全部得失。

三种执行模型，差别在"决策发生在什么时候"

解释式执行（PyTorch eager 是典型）在每次调用时才决定这一步要做什么：dispatch 到哪个 kernel、用什么精度、内存从哪来。好处是灵活性免费——shape 随便变、加个 print 也能跑、想改哪层就改哪层。代价是每一步都要付一次调度开销，而且系统在任何时刻都只知道当前这一个算子，看不到相邻算子，因此天然无法做跨算子的优化。

编译式执行把这些决策全部前移。因为构建期能看到整张图，它可以做只有全局视野才能做的事：把相邻层融掉、把可静态求值的子图折叠成常量、为每层实测挑选 kernel、统一规划显存复用、给每个张量分配精度。运行期剩下的只是"按计划执行"，dispatch 开销被彻底消掉。

JIT 编译（torch.compile）是中间档：首次调用时编译、装上守卫（guard），shape 或结构变化就重编译。它保留了大部分 Python 灵活性，但优化深度不如 AOT——它没有"为这台具体的卡实测每层所有候选实现"的预算。

付出的代价里有一项容易被忽略：engine 是可执行的原生代码

TensorRT 文档对此有一段措辞相当强硬的说明：序列化的 engine 里包含已编译的 CUDA tactic 和 plugin 调用指针，反序列化一个来源不可信的 engine，等价于在 GPU 和主机上执行不可信的原生代码，而这个文件格式没有任何沙箱。因此官方的要求是：只加载自己构建的 engine，或者通过可信且经过认证的通道收到的 engine；绝不加载来自第三方、公网、用户上传等不受端到端控制的 plan 文件。多租户部署应在可信主机上构建，再通过带签名和完整性校验的通道把 engine 送到推理主机。文档还特别补了一句：跨版本兼容路径（如 8.x 到 10.x、10.x 到 11.x）不放宽这条要求——那条路径是给你自己用旧工具链构建的 engine 用的，不是用来接受外部 engine 的。

解释式执行像现场点菜：每道菜都要问一次厨房、等一次回复，灵活但每次都有沟通成本。编译式执行像宴席定制：提前把全部菜单、火候、上菜顺序敲定并排练一遍，当天只管出菜，快得多——但菜单一旦印好，换厨房、换灶台、换季节食材都得重新排一遍。这就是 engine 不可移植的根源，不是实现缺陷，是这套交易的必然条款。

把 TensorRT 放进整个部署栈的位置（引擎层 vs 服务框架层）见 DP04 · 模型部署与 Serving，本卡不重复那一层的定位介绍，只讲编译流程内部与由此带来的工程代价。

二、TensorRT 构建流水线的五个阶段

构建期做的事可以拆成五段：解析、图优化、精度标定、tactic 选优、序列化。这五段各有各的失败方式，而且失败点越靠后越难排查，所以值得逐段看清它在做什么。

TensorRT 构建流水线：每一段的输入、动作与常见翻车点 ① parse ───────────────────────────────────────────────── ONNX 文件 / INetworkDefinition API 动作：把外部表示翻译成内部网络定义 翻车：算子不在支持列表 → 需要 plugin 或改写模型 ↓ ② 图优化 ──────────────────────────────────────────────── 动作：常量折叠 → 层融合（按模式目录）→ 消除死层 "融合检测受支持的操作模式，把多层合并成一层， 并启用该层内部那些创建网络时无法直接访问的选项" 翻车：期望的融合没出现（精度/架构约束没满足）， 日志里能看到，不看日志就只会觉得"怎么没变快" ↓ ③ 精度标定 ────────────────────────────────────────────── 动作：INT8 隐式量化走 calibrator 求每个激活张量的 scale （或走显式 Q/DQ 路径，scale 已在模型里） 翻车：标定集不代表真实分布 → 精度掉点； 两条路径混用（显式 Q/DQ 又给 calibration table）→ 报错 ↓ ④ tactic 选优 ─────────────────────────────────────────── 动作：为每层枚举候选实现，逐个实测计时，取最快 翻车：构建极慢（层多/拓扑复杂）； 计时噪声导致同一份输入两次构建选出不同 tactic ↓ ⑤ 序列化 ──────────────────────────────────────────────── 产出 engine（plan file）：图结构 + 已编译 tactic + plugin 调用指针 + 其他状态 翻车：把 engine 当成"跨环境可搬运的模型文件"（见第三节）

阶段二：图优化的两件事

常量折叠（constant folding）把构建期就能算出结果的子图预先算掉，运行时不再重复计算。层融合（layer fusion）是 TensorRT 的招牌能力，官方描述值得原样理解：融合把网络变成更简单的形式但保持整体行为不变；许多层实现内部带有创建网络时无法直接访问的额外参数和选项，融合优化步骤检测受支持的操作模式，把多层合并成一层并配上内部选项集。换句话说，融合不只是"少启动几次 kernel"，它是在把你的图映射到 TensorRT 内部那些更强、但外部 API 触达不到的层实现上。

关键在于这份模式目录是带条件的。以官方 Layer Fusion Catalog 里几条为例：Conv → ReLU 要求激活正好是 ReLU；Conv → GELU 要求输入输出精度相同且同为 FP16 或 INT8，并且需要 Turing 及更新架构；深度可分离卷积融合要求两个卷积精度都是 INT8 且计算能力不低于 7.2。所以同一张图在不同卡、不同精度设置下会融出不同结果——"换了张卡性能对不上"这类现象，很多时候根源就在这里。核对方式只有一个：把日志级别开到 kINFO，或者用 engine inspector 看构建后的层结构，确认预期的融合真的发生了。融合本身为什么能省时间、省的是什么，见 DP27 · 算子融合与 Kernel 优化实战。

阶段三：INT8 标定在解一个什么问题

INT8 只有 256 个可表示的值，把一个浮点激活张量映射进去必须选一个 scale（缩放因子）。TensorRT 文档把这件事的难点讲得很清楚：选 scale 不是精确科学，它要在两类误差之间取平衡——离散化误差（representable 范围越大，每个量化格子代表的区间越宽，误差越大）与截断误差（范围外的值被夹到边界上）。范围放宽，离散化误差涨；范围收紧，截断误差涨。正因为没有唯一最优解，TensorRT 提供了多个用不同方式计算 scale 的 calibrator。

量化路径scale 从哪来关键约束适用
隐式量化（calibration）喂一批代表性数据，由 calibrator 统计激活分布后算出默认在层融合之前标定；不能同时提供显式 Q/DQ手上只有 FP32 模型、没有量化训练流程
IInt8EntropyCalibrator2熵标定：选择使量化后张量的信息论内容最优的 scale官方推荐的熵标定器；DLA 场景必须用它；标定 batch size 会影响结果通用首选，对 CNN 类网络官方明确推荐
IInt8MinMaxCalibrator直接取观测到的最小/最大值对离群值敏感——一个极端值就能把范围撑大、把有效精度摊薄激活分布本身较紧、或已知无离群值
显式量化（Q/DQ）模型里已经带 QuantizeLinear/DequantizeLinear 节点，scale 是模型的一部分不能再提供 calibration table，否则报错做过量化感知训练、或用外部量化工具产出的模型

标定缓存的可移植性有一条容易踩的规则：只要标定发生在层融合之前，标定缓存就可以跨设备复用（使用 IInt8EntropyCalibrator2、IInt8MinMaxCalibrator，或显式设置 QuantizationFlag::kCALIBRATE_BEFORE_FUSION 时成立）。这个特性很实用——可以在装了独立显卡的机器上生成标定表，再拿到嵌入式平台上复用。原因也很直白：融合在不同平台、不同设备上不保证一致，所以在融合之后标定得到的缓存必然不可移植。但要注意另一条：标定缓存一般不能跨 TensorRT 版本复用。量化方案本身的精度权衡与选型见 DP13 · 模型量化。

还有一个常被误解的点：精度标志 FP16、INT8、TF32 是独立开关，而且开了不等于一定用。官方说明是 TensorRT 仍然会选择更高精度的 kernel，只要它跑得更快，或者压根不存在低精度实现。所以"我开了 INT8 但看日志某些层还是 FP16"通常不是配置错了，而是 builder 判断这样更快或别无选择。

阶段四：tactic 选优——性能的来源，也是不确定性的来源

tactic 指的是某一层的一个具体 kernel 实现。builder 会为每层枚举可用 tactic 并逐个实测计时，选出最快的组合成最终 plan。这是 TensorRT 性能优势的主要来源——它不是靠启发式猜，而是在你的这块卡上真的跑过。代价有两个。

第一个代价是构建时间。官方直言：层数多或拓扑复杂时构建时间可能很长。控制手段有三层：ITimingCache 缓存逐层计时信息，重复的层可以跳过实测直接复用（缓存内容与目标设备、CUDA 版本、TensorRT 版本以及会改变层实现的 BuilderConfig 参数如 kTF32、kREFIT 绑定；JIT 编译产物构成的 compilation cache 默认也序列化在里面）；builder 优化级别默认为 3，调低可以显著加快构建但引擎可能更差，调高则构建更慢、有机会找到更好的 tactic。

第二个代价更隐蔽：构建不是确定性的。官方原文是——builder 用计时来找最快 kernel，而计时会受噪声影响，例如 GPU 上有其他工作、GPU 时钟频率波动；计时噪声意味着连续几次构建可能选出不同的实现。对需要可复现构建的场景，TensorRT 提供了 Editable Timing Cache：首次构建时打开 BuilderFlag::kEDITABLE_TIMING_CACHE 并保留日志与缓存文件，日志会给出每层的名字、key、可用 tactic 与最终选中的 tactic；下次构建时用 ITimingCache::update 为指定层钉死 tactic，builder 就会用你指定的那一个（每层只能钉一个）。

示例场景：构建不可复现把一次发布拖成了两天。某团队的 CV 排序模型走 TensorRT 部署，CI 里每次合并都重新构建 engine 并跑一遍延迟门禁（P99 ≤ 12ms）。上线前一周出现"同一个 commit 有时过门禁、有时不过"的怪现象：连续构建 5 次，四次 P99 落在 10.4–10.7ms，第五次却是 11.9ms，几乎顶到阈值。开 kINFO 日志逐层比对后发现，某个卷积层在那次构建里选到了另一个 tactic，单层耗时高出约 1.2ms——构建机上当时有另一个任务在抢 GPU，计时被污染。修法分三步：构建时独占 GPU 并锁定时钟；引入 ITimingCache 后构建时间从约 22 分钟降到约 4 分钟；对少数敏感层用 Editable Timing Cache 钉死 tactic，之后 20 次构建的 P99 波动收敛到 0.3ms 以内。可迁移的结论是：只要门禁比对的是延迟数字，构建环境就必须和测试环境一样被当作受控变量。这里的具体毫秒数是构造的示例场景，用于说明排查链路，不可直接搬用。
构建期配置项作用取值取错的后果

tactic 选优本质上是构建期替你跑了一轮小规模压测：把每层的所有候选实现在你这块卡上都试一遍，留最快的。理解这一点，两件怪事就都通了——为什么构建这么慢（它真的在跑），以及为什么两次构建结果会不同（跑的时候被别人干扰了）。想要可复现，就得像对待压测环境一样对待构建环境。

三、engine 为什么不可移植

这是编译式方案在工程上最贵的一条约束，而且它常常在上线前一周才被发现。TensorRT 文档写得毫不含糊：默认情况下，序列化的 engine 只保证在与序列化时相同的 OS、CPU 架构、GPU 型号和 TensorRT 版本下正确工作。

四个绑定维度，各自的失效方式不同

绑定维度为什么会绑变了会怎样官方给的缓解手段
GPU 型号 / 架构tactic 是为具体架构实测选出并编译进 engine 的；可用融合模式本身也随计算能力变化反序列化失败，或能跑但性能与预期严重不符Hardware Compatibility（硬件兼容模式），以放弃架构专属优化为代价
TensorRT 版本engine 内含已编译 tactic 与 plugin 调用指针，其格式与实现随版本演进反序列化失败Version Compatibility + lean / dispatch runtime
OS 与 CPU 架构engine 里含主机侧状态，且构建依赖工具链反序列化失败无——只能在目标平台上重建
驱动 / CUDA 版本tactic 依赖特定 CUDA 运行时与驱动能力；timing cache 显式包含 CUDA 版本维度加载或执行异常；缓存复用失效把驱动与 CUDA 版本纳入基础镜像并锁定

值得单独说的是 TensorRT 提供的三档运行时，它们正是"版本兼容"这条缓解手段的实现方式：默认运行时是主库 libnvinfer；lean runtime（libnvinfer_lean）体积更小，只包含运行版本兼容 engine 所需的代码；dispatch runtime（libnvinfer_dispatch）是一层很小的 shim，能加载 lean runtime 并转发调用，还能加载更旧版本的 lean runtime，从而在新版 TensorRT 与旧 plan 文件之间提供兼容性。

但这条路要付一笔明确的性能费用，官方讲得很直接：lean runtime 包含的算子实现比默认运行时少，而 TensorRT 是在构建期选定算子实现的，所以你必须在构建时就声明"这个 engine 是给 lean runtime 用的"（启用版本兼容），而这样构建出的 engine 可能比为默认运行时构建的更慢。也就是说，版本兼容不是免费的向后兼容，它是用性能换运维弹性的一档权衡。

示例场景：一次"只换了机型"的扩容事故。某在线服务原本全量跑在 A100 上，engine 由 CI 统一构建。为应对流量增长，运维加了一批 L40S 节点进同一个部署，镜像和 engine 文件都没动。结果新节点全部启动失败——engine 反序列化直接报错，因为 GPU 型号不匹配。临时方案是把 L40S 节点从负载均衡里摘掉，代价是那天的扩容窗口白等。补齐方案分三步：一是把机型加进 engine 的产物 key，构建矩阵从 3 格（1 机型 × 3 精度组合）扩到 6 格，CI 单次全量构建时间从约 35 分钟涨到约 70 分钟（引入 timing cache 后回落到约 25 分钟）；二是给 Deployment 按 nodeSelector 分机型分组，各组挂各自的 engine；三是在启动探针里加一道"engine 与本机 GPU 型号是否匹配"的前置校验，让不匹配在启动时就明确报错，而不是等到第一个请求。这里的教训不是某个数字，而是：机型必须是 engine 的一部分身份，不是部署时的实现细节。具体构建时长强依赖模型规模与构建机配置。
把 engine 当成"编译好的可执行文件"而不是"模型权重文件"，所有约束就都顺理成章了：你不会指望一个为 x86 编译的二进制在 ARM 上跑，也不会把它从一个陌生人那里下载下来直接执行。engine 就是这种东西——它不是数据，它是代码。

四、TensorRT 与 TensorRT-LLM 的关系

一句话概括：TensorRT 是通用推理编译器与运行时，它的世界观里一次前向就是一次完整的推理；而自回归大模型把这个世界观的三条前提全部打破了，TensorRT-LLM 就是为补上这三条而存在的。

LLM 打破了哪三条前提

TensorRT 的原始假设LLM 推理的真实情况不补会怎样
输入 shape 在一次执行内固定解码每一步序列长度都在增长要么为每个长度准备档位，要么按最大长度 padding，两条路都极浪费
请求之间无状态，一次前向算完一个请求每个请求带自己的 KV 状态，要跨几十上百步持续存在无处安放 KV，只能每步重算全部历史，成本爆炸
一个 batch 里所有样本同进同出请求在不同步到达和结束，batch 成分每一步都在变整批必须等最慢的那条走完，GPU 大量空转

TensorRT-LLM 补上的四件事

其一，in-flight batching（在官方文档里也称 continuous batching 或 iteration-level batching）：让处于 context 阶段（预填充）的序列与处于 generation 阶段（解码）的序列在同一次前向里一起处理，目的是更好地交错请求，既降延迟又提高 GPU 利用率。有一条实现约束值得记住——出于效率原因，in-flight batching 要求输入张量是 packed 的（无 padding），这也解释了为什么它不能简单地套在一个普通 TensorRT engine 上。

其二，chunked context：原本 context 阶段是一次性处理全部输入 token，这个特性把 context 切成若干 chunk，使 chunk 能与 generation 阶段的 token 一起组批，从而提高整体吞吐，同时解除了对输入长度的限制。启用它需要同时开启 FMHA 的 paged KV cache，且除最后一个 chunk 外，每个 chunk 的大小必须是 KV cache 块大小的整数倍。

其三，paged KV cache：把 KV cache 拆成固定大小的块，由 cache manager 在处理过程中分配给不同请求——它跟踪各序列、从池里分配新块、并在需要时回收。TensorRT-LLM 里每个 Transformer 层各有一份 KV cache，层数就是 cache 数。配置上关键是 kv_cache_type=paged、tokens_per_block（取 2 的幂）与 enable_block_reuse（开启块复用即前缀复用）。分页与前缀复用的原理和显存账见 DP09 · KV Cache 显存优化，迭代级调度的机制见 DP11 · Continuous Batching 与推理调度策略，本节只说 TensorRT-LLM 侧的形态。

其四，两级调度器 + 多卡并行。调度分两步走：CapacityScheduler 先判断资源（主要是 KV cache 容量）够不够，输出 fitting_requests 与 paused_requests；MicroBatchScheduler 再从中挑出这一步真正要跑的 context_requests 和 generation_requests。多卡侧提供张量并行、流水线并行、专家并行等切分方式，配合针对 Transformer 手写的注意力 kernel 与 FP8/INT4 支持。

TensorRT-LLM 的执行循环（PyExecutor，每个 rank 一个后台循环） ┌───────────────────────── 每一步迭代 ─────────────────────────┐ │ │ │ ① 取请求 从内部请求队列拉新请求（如果有） │ │ ↓ │ │ ② 调度 CapacityScheduler：KV cache 等资源装得下吗？ │ │ → fitting_requests / paused_requests │ │ MicroBatchScheduler：这一步跑哪些？ │ │ → context_requests + generation_requests │ │ ↓ （两类混在同一次前向里 = in-flight batching）│ │ ③ 备资源 KVCacheManager.prepare_resources │ │ 从块池分配 KV 块；已完成的请求归还块 │ │ ↓ │ │ ④ 前向 ModelEngine.forward 一次单步前向 │ │ ↓ │ │ ⑤ 采样 Decoder / Sampler 产出下一个 token │ │ ↓ │ │ ⑥ 出结果 更新各请求的部分输出；完成的请求返回用户 │ │ │ └──────────────────────────────────────────────────────────────┘ 两项额外优化（官方文档提到）： · overlap scheduling：不等第 n 步的结果在 CPU 侧处理完， 就先把第 n+1 步发出去 → CPU 做停止条件判断/组装响应的同时 GPU 已在算 · CUDA Graph padding：batch 尺寸向上取到最近的已捕获图尺寸， 提高图命中率（代价是有少量 padding 浪费） ★ 注意这已经不是"一个 TensorRT engine 被调用"的形态了—— 调度、KV 管理、采样都在这个 executor 循环里， TensorRT-LLM 是一个完整的 LLM 运行时，不只是 TensorRT 的封装层。
对比项TensorRTTensorRT-LLM
面对的模型通用网络：CV、排序、编码器、判别式模型自回归 Transformer 解码器

TensorRT 像一台把整条产线预先排布好的自动化设备：料进去、成品出来，节拍固定。LLM 的解码却是"每个客人点了不定量的菜、还要一口一口上"，节拍不固定、每桌都有自己的进度。TensorRT-LLM 补的正是这套"排队叫号 + 每桌记账 + 拼桌上菜"的机制——它保留了设备本身的加工能力，在外面加了一个调度大厅。

五、与运行时调度式方案的定位与共存

vLLM、SGLang 这类方案常被摆在 TensorRT-LLM 对面做二选一，但这个问法本身在过时。各框架的功能矩阵与横向对比已经在 DP05 · 大模型推理框架选型 里完整给过，本节不重复，只讲一件它不覆盖的事：编译式与运行时调度式在优化目标上的根本差异，以及它们在同一套系统里怎么共处。

两条路线优化的不是同一个量

这是最容易被"谁更快"的口水战掩盖的一点。编译式方案（把整张图交给构建期）主攻的是单次前向的执行时间：融合、tactic 实测选优、显存规划、精度分配，全都在压这一个数。运行时调度式方案主攻的是GPU 上有效工作的占比：每个解码步该让谁进 batch、KV 显存怎么分页复用、抢占和排队怎么排——它压的是"有多少时间在做有用的事"。

端到端产能 ≈ 单次前向效率（编译期能改善） × 有效工作占比（运行时调度能改善）

两个因子相乘，所以哪一侧是短板就该补哪一侧。一个连 continuous batching 都没有的系统，单次前向再快也填不满 GPU；反过来，调度已经把 GPU 排得很满时，单步前向的每一点效率都直接折成吞吐。

现实是两条路线在互相靠近

这一点让"选路线"这个决策变得没那么重要了。编译式一侧补了大量本属运行时调度的能力——上一节列的 in-flight batching、paged KV cache、两级调度器，本来都是运行时调度的活。运行时调度式一侧则补了本属编译期的能力：接入 torch.compile 做图捕获与融合、做 CUDA Graph 捕获消灭启动开销、内置手写融合 kernel。结果是两边的能力集大幅重叠，真正的差异退回到工程属性上：构建期投入是否划算、产物管理成本你付不付得起、迭代速度要多快。

判断维度倾向编译式（构建期投入）倾向运行时调度式
模型结构稳定度已冻结，几个月不动还在改结构、换基座、试新变体
硬件同构度单一机型或少数几种异构车队、机型经常变动
shape 分布集中、可用少数几个优化档位覆盖长尾分散，档位难以收敛
发布节奏周级/月级发版，能容纳构建与验证窗口天级甚至小时级迭代
团队能力有构建流水线、产物仓库、精度验证体系希望"拉起来就能服务"，不想维护构建矩阵
延迟敏感度P99 卡得极紧，愿意为最后 10~20% 付工程代价吞吐优先，延迟有余量

四种共存形态，选一个或几个

  • 分层共存：编译式引擎当后端，服务框架管调度、多模型、版本灰度与观测——这是生产里最常见的形态，引擎负责"算多快"，服务框架负责"能不能安全换版本、同时服务几个模型"。这一层的分工在 DP04 · 模型部署与 Serving 里有完整展开。
  • 分流量共存：结构冻结、流量大、延迟卡得紧的主力模型走编译式，吃它单次前向的优势；迭代频繁的实验模型和长尾小模型走运行时调度式，吃它零构建成本与灵活性。两类模型共用同一套网关、鉴权与观测。
  • 分阶段共存：预填充与解码分离部署时，两侧的瓶颈完全不同（一侧算力密集、一侧带宽密集），因此可以各选各的实现，只要中间的 KV 传递协议对齐。
  • 影子共存：同一模型两条实现并行部署，用同一套压测口径与同一份数据集比对延迟分位数与精度。这是唯一靠得住的选型证据，做法见 DP16 · 推理服务压测方法论——跨方案比数字之前必须先对齐指标公式和测量点，否则比的是工具差异不是方案差异。
别问"该选编译式还是调度式"，问"我现在的短板是单步算得不够快，还是 GPU 有一半时间在空转"。前者补编译，后者补调度。而且两边这几年一直在抄对方的作业，能力集越来越像——最后决定选型的往往不是性能，是你养不养得起一个构建矩阵。

六、ONNX 作为中间表示的坑

ONNX（Open Neural Network Exchange）是训练框架与推理编译器之间的通用语：一张计算图，加上一套按 opset 版本演进的算子集合。它让"PyTorch 训练、TensorRT 部署"这条链路成立。但它同时是整条链路上最容易出问题的一段，因为它是翻译——而翻译有两头，两头都可能不认。

PyTorch → ONNX → TensorRT：三道独立的关卡，别只过第一道 PyTorch 模型 │ │ ① 导出关：exporter 能不能发出这个算子？ │ 失败长相：UnsupportedOperatorError: Exporting the operator │ 'aten::xxx' to ONNX opset version N is not supported ▼ ONNX 图（带 opset 版本 + 输入是否声明为动态） │ │ ② 消费关：下游（TensorRT / ONNX Runtime）认不认这个算子和这个 opset？ │ 失败长相：构建 engine 时报不支持的算子 / 需要 plugin； │ 或运行时 [ShapeInferenceError] 之类的类型/形状推断失败 ▼ TensorRT engine │ │ ③ 精度关：数值和任务指标还对不对？ │ 失败长相：能跑、不报错、logits 余弦相似度看着也高， │ 但下游任务指标掉点 —— 最难发现的一类 ▼ 上线 ★ 最危险的误解："导出没报错" ≈ "转换成功"。 第 ① 关过了只说明 exporter 写出了一个文件， 第 ② ③ 关完全独立，必须各自设验证。

坑一：算子不支持，而且有两层含义

第一层是 exporter 发不出来。典型报错就是 UnsupportedOperatorError: Exporting the operator 'aten::erfc' to ONNX opset version 18 is not supported。处理方式有三条：用 custom_translation_table（新 dynamo 路径）或 register_custom_op_symbolic（旧路径）配合 onnxscript 给这个算子写一个 ONNX 实现；把它拆解成受支持的原语组合；或者在下游写 plugin 顶上。

第二层是下游认不出来。exporter 成功写出的图，TensorRT 或 ONNX Runtime 未必能构建——这是两套独立的支持列表。更阴的是注册了自定义符号函数、导出也没报错，但产出的图在运行时挂在形状/类型推断上，报出类似 [ShapeInferenceError] ... Input 0 expected to have type but instead is null 的错。PyTorch 文档对此有一条明确建议：为自定义算子注册符号函数时，强烈建议同时用 setType 补上形状推断，否则导出图在某些极端情况下会有错误的形状推断。所以"导出没报错"绝不能当作验证通过。

坑二：动态 shape 要声明两次，而且两套 API 别混

PyTorch 文档说得很直接：tracer 记录的是示例输入的 shape，默认导出的模型里所有输入输出 shape 会与 args 完全一致。要让某些轴在运行时才确定，必须显式声明。这里有个高频错误：新的 dynamo 路径（dynamo=True）用 dynamic_shapes，旧的 trace 路径（dynamo=False）用 dynamic_axes——两者不能混用，配错的表现是"我明明声明了动态，导出的还是固定 shape"。

声明完 ONNX 侧只是第一步，TensorRT 侧还要配优化档位（optimization profile，给出 min / opt / max 三组 shape）。关键机制是：tactic 是针对 opt 那组 shape 实测选出来的，离 opt 越远的 shape 跑在并非为它挑选的 tactic 上。于是形成一个真实的权衡——档位开得太宽，各处都平庸；开得太窄，真实流量里超出范围的请求在运行时被直接拒。实践上的做法是先统计生产流量的 shape 分布，用几个档位分段覆盖，把 opt 放在各段的密集区。

坑三：opset 版本是一个三方交集

opset_version 该怎么定，官方给的原则是：按你打算用来运行这个模型的运行时后端或编译器所支持的 opset 版本来设。这意味着可选范围是三个集合的交集——exporter 支持的范围、下游（TensorRT / ONNX Runtime）支持的范围、以及你的模型实际需要的算子在哪个版本才有。三者取交集之后往往只剩一两个可选值。

还有一个容易忽略的风险：升级 opset 可能改变某个算子的语义或属性。同名算子在新版本里的行为、默认属性、支持的类型都可能变化，所以 opset 升级要按"改了模型"来验证，不能按"改了个参数"来对待。

坑四：精度漂移，最难发现的一类

转换链路上有好几处会合法地改变数值，累积起来就是漂移。它们全都不报错：

漂移来源机制什么时候暴露
导出期常量折叠do_constant_folding 在 exporter 的精度下预先求值子图，结果被写死成常量与原模型逐层比对时才看得出
层融合改变累加顺序融合后的层内部累加顺序与逐层执行不同，浮点不满足结合律逐层输出比对；单看端到端 logits 容易被掩盖
FP16 下的溢出/下溢Softmax 前的 reduce、方差计算、指数运算在 FP16 动态范围内可能溢出特定输入（长序列、极端取值）才触发，抽样测不到
INT8 标定集不代表真实分布scale 是从标定集统计出来的；标定集偏窄则截断误差在真实流量上放大上线后在长尾流量上掉点
不同后端的累加类型不同同一个 ONNX 算子在 ONNX Runtime 与 TensorRT 里可能用不同的中间累加精度换后端对比时才发现
Python 控制流被 trace 固化forward 里依赖输入值的分支（如 if seq_len > 512）在 trace 时只保留走过的那条换一类输入后行为静默变错，不报错
示例场景：余弦相似度 0.999，任务指标掉了 2.3 个点。某意图分类模型从 FP32 ONNX 转 FP16 engine 上线，转换后团队按惯例比对了 logits 的余弦相似度，200 条样本平均 0.9992，判定"数值无差异"就发了版。灰度一天后离线评估显示准确率从 94.1% 掉到 91.8%。定位过程是逐层导出中间输出比对：前面几十层的相对误差都在 1e-3 量级，到某个 Softmax 之前的 reduce 层突然出现若干 inf——该层在 FP16 下对长文本样本溢出了。把这一层用精度约束回 FP32（其余仍走 FP16）后准确率恢复到 94.0%，延迟只上升约 3%。教训有两条：一是余弦相似度对"少数样本严重错、多数样本正确"极不敏感，验收指标必须是任务级指标而不是张量相似度；二是精度验证的样本必须覆盖长尾（最长输入、极端取值、特殊字符），因为溢出恰恰只在长尾上发生。这里的百分比是构造的示例场景，用于说明排查方法。
验证阶段该验什么怎么验
导出后（ONNX 在手）图结构完整、输入输出名与动态轴符合预期、能通过 ONNX 检查用 ONNX 的检查工具跑一遍；打印输入输出签名核对动态轴
ONNX 推理ONNX Runtime 上的输出与 PyTorch 在同一批固定输入上是否对齐固定一组黄金输入（含长尾样本），逐输出设容差比对
engine 构建后预期的融合是否发生、每层实际用了什么精度kINFO 日志 + engine inspector 看层结构与精度分配
engine 推理逐层中间输出与 ONNX 侧的相对误差；出现 inf/nan 的层逐层输出比对工具；对可疑层做精度约束再复测
上线前任务级指标（准确率、召回、生成质量），不是张量相似度用完整评估集跑离线评估，与 FP32 基线对齐；容差按输出分别定义
  • 固定一组黄金输入（含最长、最短、极端取值样本）贯穿全链路比对
  • 动态轴按新旧路径分别用 dynamic_shapes 或 dynamic_axes，不混用
  • 先统计生产 shape 分布，再定优化档位，把 opt 放在密集区
  • opset 版本取"exporter × 下游 × 模型需求"的交集，并锁进构建配置
  • 构建后用 kINFO 日志核对预期融合与每层精度是否落地
  • 验收用任务级指标，容差按输出分别定义
  • engine 按 (机型, TRT 版本, 精度, 档位) 入产物仓库，灰度期新旧都留着
  • 构建时独占 GPU、锁时钟，并用 timing cache 稳定结果
  • 不要把"导出没报错"当成转换成功——后面还有两道独立关卡
  • 不要用 logits 余弦相似度当精度验收指标，它掩盖少数样本的严重错误
  • 不要在 forward 里留依赖输入值的 Python 分支后直接 trace 导出
  • 不要把优化档位开成一个覆盖全部可能长度的超宽范围
  • 不要把 engine 当模型权重文件跨机型、跨版本分发
  • 不要加载来源不可信的 engine——那等于执行不可信原生代码
  • 不要指望版本兼容运行时是免费的，它用性能换弹性
  • 不要在标定集里只放"干净好看"的样本
ONNX 的坑几乎全部来自一个错觉：以为它是一种"保存格式"。它不是，它是一次翻译——有源语言的表达能力、目标语言的接受能力、还有译者对上下文（shape、精度、控制流）的假设。翻译能顺利产出一份文件，完全不代表读者能读懂，更不代表意思没变。所以导出、消费、精度三道关必须各自设验收。

Q&A

为什么 TensorRT 要先 build 再跑，这样换来了什么？

因为很多优化只有在能看到整张图、并且知道目标硬件是哪块卡的时候才做得出来。TensorRT 的工作分两段：构建期由 builder 编译网络、为目标 GPU 上每一层挑出最快的可用 kernel，产出序列化的 engine；运行期由 runtime 载入 engine 执行。构建期换来的是四类能力：跨层融合（把多层合并成一层，并启用那些创建网络时外部 API 触达不到的内部选项）、常量折叠、按实测计时选 kernel（不是靠启发式猜，而是在你这块卡上真跑一遍）、以及统一的显存规划与精度分配。同时运行期的 dispatch 决策被彻底消掉。付出的代价是构建时间（分钟到小时级）、shape 灵活性（必须预先声明优化档位）、可调试性（engine 内部是黑盒）、以及产物与环境强绑定。所以这是一笔明确的交易，不是单方面的性能提升。

engine 为什么不能拷到另一台机器上用？

TensorRT 文档的原话是：默认情况下，序列化的 engine 只保证在与序列化时相同的 OS、CPU 架构、GPU 型号和 TensorRT 版本下正确工作。原因在于 engine 里装的不是权重数据，而是已经为特定架构编译好的 CUDA tactic、plugin 调用指针和主机侧状态——它更像一个编译好的可执行文件而不是一个模型文件。你不会指望为 x86 编译的二进制在 ARM 上跑，engine 也是同理。官方提供了两条放宽路径：Hardware Compatibility 用放弃架构专属优化换取跨 GPU 型号可用；Version Compatibility 配合 lean runtime（只含运行版本兼容 engine 所需代码）或 dispatch runtime（能加载更旧版本的 lean runtime）换取跨 TensorRT 版本可用。但这两条都要付性能费用——官方明确说 lean runtime 包含的算子实现比默认运行时少，而 TensorRT 是构建期选实现的，所以为 lean runtime 构建的 engine 可能更慢。OS 和 CPU 架构变化则没有缓解手段，只能在目标平台重建。

同一份模型两次构建 engine，性能不一样正常吗？

正常，而且官方明确解释过原因。builder 是通过实测计时来找每层最快的 kernel 的，而计时会受噪声影响——GPU 上有其他任务在跑、GPU 时钟频率波动都会干扰。文档原话是：计时噪声意味着同一个实现在连续几次构建里可能被不同地选中。所以两次构建可能给某些层选出不同的 tactic，进而导致端到端延迟有差异。要让构建可复现，有三层手段：一是把构建当受控实验对待，独占 GPU 并锁定时钟频率；二是用 ITimingCache 复用逐层计时结果（注意缓存内容与目标设备、CUDA 版本、TensorRT 版本以及会改变层实现的 BuilderConfig 参数绑定）；三是用 Editable Timing Cache——首次构建时打开 kEDITABLE_TIMING_CACHE 并保留日志与缓存，日志会给出每层的可用 tactic 与选中项，之后用 ITimingCache::update 为指定层钉死一个 tactic。如果 CI 里有延迟门禁，第一条几乎是必须做的，否则门禁会变成抽奖。

INT8 calibration 到底在算什么，为什么标定集这么重要？

它在为每个激活张量求一个缩放因子（scale），把浮点范围映射到 INT8 仅有的 256 个可表示值上。TensorRT 文档把难点讲得很清楚：选 scale 不是精确科学，它要在两类误差间平衡——离散化误差（可表示范围越大，每个量化格子代表的区间越宽）和截断误差（范围外的值被夹到边界）。范围放宽则前者涨，收紧则后者涨，没有唯一最优解，所以 TensorRT 提供了多个用不同方式算 scale 的 calibrator。IInt8EntropyCalibrator2 是官方推荐的熵标定器，它优化量化后张量的信息论内容、通常会抑制离群值，DLA 场景必须用它，对 CNN 类网络官方也明确推荐；IInt8MinMaxCalibrator 直接取观测最小最大值，对离群值敏感。标定集重要，是因为 scale 完全由标定集的统计量决定：标定集偏窄，真实流量里超出范围的值就被截断；标定集里全是"干净好看"的样本，长尾流量上就会掉点。还有一条工程细节：只要标定发生在层融合之前（用上述两个 calibrator 或设 kCALIBRATE_BEFORE_FUSION），标定缓存可以跨设备复用，因为融合在不同平台上不保证一致；但标定缓存一般不能跨 TensorRT 版本复用。

TensorRT 和 TensorRT-LLM 是什么关系，后者补了什么？

TensorRT 是通用推理编译器与运行时，它的假设是"一次前向 = 一次完整推理、请求无状态、batch 同进同出"。自回归 LLM 把这三条全部打破：序列长度每步都在增长、每个请求持有跨步的 KV 状态、请求在不同步到达和结束使 batch 成分每步都变。TensorRT-LLM 就是为补这三条而生的，主要补了四件事。第一是 in-flight batching（官方也称 continuous batching 或 iteration-level batching），让处于 context 阶段的序列与处于 generation 阶段的序列在同一次前向里一起处理；出于效率原因它要求输入张量是 packed 的、无 padding。第二是 chunked context，把预填充切成块与解码 token 一起组批，从而解除输入长度限制；启用它需要同时开 FMHA paged KV cache，且除最后一块外每块大小必须是 KV cache 块大小的整数倍。第三是 paged KV cache，由 cache manager 从块池分配、跟踪序列并回收，支持块复用即前缀复用；TensorRT-LLM 里每个 Transformer 层各有一份 KV cache。第四是两级调度器（CapacityScheduler 判断资源装不装得下，MicroBatchScheduler 挑这一步跑哪些）加上张量/流水线/专家并行。值得注意的是，加了这一整套之后它已经是一个完整的 LLM 运行时，而不只是 TensorRT 的一层封装。

编译式方案和 vLLM 这类运行时调度式方案该怎么共存？

先认清两者优化的不是同一个量：编译式主攻单次前向的执行时间（融合、tactic 选优、显存规划、精度分配），运行时调度式主攻 GPU 上有效工作的占比（每步谁进 batch、KV 怎么分页复用、抢占排队怎么排）。端到端产能大致是这两个因子的乘积，所以补短板才有意义——调度都没做好时单步再快也填不满 GPU，调度已经排满时单步效率就直接折成吞吐。而且这几年两条路线在互相靠近：编译式一侧补了 in-flight batching、paged KV、两级调度器（本属运行时的活），运行时调度式一侧补了图捕获融合、CUDA Graph、手写融合 kernel（本属编译期的活），能力集大幅重叠。共存有四种形态：分层共存（编译式引擎当后端，服务框架管调度与多模型灰度）、分流量共存（结构冻结的主力模型走编译式，迭代频繁的实验模型走运行时调度式，共用网关与观测）、分阶段共存（预填充与解码分离部署时两侧各选各的实现，对齐 KV 传递协议）、以及影子共存（同一模型两条实现并行，用统一压测口径比延迟分位数与精度）。具体框架的功能矩阵对比见 DP05，本卡不重复。

ONNX 导出没报错，为什么 engine 还是构建不出来？

因为"能导出"和"能被消费"是两套独立的支持列表，中间还隔着形状与类型推断。第一道关是 exporter 能不能发出这个算子，失败长相是 UnsupportedOperatorError: Exporting the operator 'aten::xxx' to ONNX opset version N is not supported。第二道关是下游能不能构建：TensorRT 和 ONNX Runtime 各有自己的算子支持范围与 opset 支持范围，exporter 成功写出的图，下游未必认——这一关的失败在构建 engine 时才暴露，可能提示不支持某算子或需要 plugin。还有一种更阴的情况：你给不支持的算子注册了自定义符号函数，导出确实不报错了，但产出的图在运行时挂在形状/类型推断上，报出类似 [ShapeInferenceError] Input 0 expected to have type but instead is null 的错。PyTorch 文档对此的建议是注册自定义符号函数时用 setType 补上形状推断，否则导出图在某些情况下会有错误的形状推断。所以正确心态是：导出成功只说明生成了一个文件，消费关和精度关必须各自设独立验证。

动态 shape 该怎么正确处理？

要在两个地方分别声明，而且 ONNX 侧有两套不能混用的 API。PyTorch 的 tracer 记录的是示例输入的 shape，默认导出的模型所有输入输出 shape 与 args 完全一致，所以必须显式声明动态轴：新的 dynamo 路径（dynamo=True）用 dynamic_shapes，旧的 trace 路径（dynamo=False）用 dynamic_axes，配错的典型症状是"明明声明了动态，导出的还是固定 shape"。ONNX 侧声明完之后，TensorRT 侧还要配优化档位，给出 min / opt / max 三组 shape。这里有个关键机制：tactic 是针对 opt 那组 shape 实测选出来的，离 opt 越远的 shape 就跑在并非为它挑选的 tactic 上。于是形成一个真实权衡——档位开得太宽，所有 shape 都平庸；开得太窄，超出范围的真实请求在运行时被直接拒。实践做法是先统计生产流量的 shape 分布，用几个档位分段覆盖，每段的 opt 放在该段的密集区。另外要检查 forward 里有没有依赖输入值的 Python 分支（比如按序列长度走不同路径），trace 会把走过的那一条固化下来，换一类输入后行为静默变错且不报任何错。

精度漂移怎么排查，验收该看什么指标？

转换链路上有六处会合法地改变数值，且都不报错：导出期常量折叠在 exporter 精度下预先求值子图；层融合改变了累加顺序而浮点不满足结合律；FP16 下 Softmax 前的 reduce、方差、指数运算可能溢出；INT8 标定集不代表真实分布导致截断误差在长尾放大；同一个 ONNX 算子在不同后端可能用不同的中间累加精度；以及 Python 控制流被 trace 固化。排查方法是逐层比对：固定一组黄金输入，把 PyTorch、ONNX Runtime、TensorRT engine 的逐层中间输出拉出来算相对误差，找第一个误差跳变或出现 inf/nan 的层，对该层做精度约束（其余层保持低精度）再复测。验收指标这里有个关键陷阱：不要用 logits 的余弦相似度——它对"少数样本严重错、多数样本正确"极不敏感，可能出现平均相似度 0.999 而下游任务准确率掉两三个点的情况。验收必须用任务级指标（准确率、召回、生成质量），在完整评估集上与 FP32 基线对齐，容差按输出分别定义。同时精度验证的样本必须覆盖长尾（最长输入、极端取值、特殊字符），因为 FP16 溢出这类问题恰恰只在长尾上触发。
