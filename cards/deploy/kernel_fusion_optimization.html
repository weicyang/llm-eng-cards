融合几乎从不让 GPU 少算一次乘加。它让同一批数据少在显存和芯片之间跑几趟。这句话是全卡的地基：一旦某段计算已经把算力打满，融合就没什么可省的；反过来，只要一段计算的时间主要花在搬数据，融合就是最便宜的加速手段——而且它不改数值结果。

一、算子边界在哪：省下的是 HBM 往返，不是 FLOPs

"融合了 13 个算子，快了一倍"这句话经常被理解成"少算了一半"。事实完全不是。融合前后的浮点运算次数逐位相同，某些情况下融合版本甚至多算（FlashAttention 的反向就靠重算换访存）。要看懂融合，得先看清"算子边界"在物理上到底是什么东西。

算子边界就是一次强制的显存往返

GPU 上一次 kernel 调用的生命周期是固定的三段：从 HBM（High Bandwidth Memory，显卡上那块几十 GB、nvidia-smi 里显示的显存）把输入读进来，在流处理器里算，再把输出写回 HBM。在 PyTorch 这类 eager 框架里，每个算子都要返回一个真实存在的 Tensor，这个"返回值必须落在 HBM 里"的契约，就是算子边界的全部物理含义。

问题在于 HBM 比片上的 SRAM（Static RAM，指寄存器与共享内存所在的片上高速存储，容量只有几十到几百 KB，但带宽比 HBM 高一个数量级）慢得多。Dao 等人在 FlashAttention 论文里给的 A100 数字是：片上 SRAM 约 19 TB/s，而 HBM 约 1.5–2.0 TB/s。更要紧的是算力和带宽的比值——现代 GPU 每从 HBM 读进 1 个字节，能配套做上百次浮点运算。于是一个判据自然浮现出来：算术强度（arithmetic intensity，一段计算的 FLOP 数除以它必须搬运的字节数）如果远低于这个比值，这段计算就不可能吃满算力，它一定在等内存。

算术强度 = FLOPs ÷ 必须搬运的字节数   vs   硬件比值 = 峰值 FLOPS ÷ HBM 带宽

把这个尺子往逐元素算子上一量，结论相当刺眼。Horace He 在《Making Deep Learning Go Brrrr From First Principles》里算过：一个一元逐元素算子（比如 torch.cos()）对每个元素只做 1 次浮点运算，却要为它读 4 字节、写 4 字节（FP32），算术强度是 0.125 FLOP/byte——比硬件比值低两三个数量级。这类算子的耗时几乎全部是搬运时间，计算单元在旁边闲着。

三个瓶颈区间，决定了优化该往哪走

同一篇文章提出的三分法是所有 kernel 级优化的分诊入口：一段计算要么受算力限制，要么受带宽限制，要么受"框架和启动的固定开销"限制。三种情况的解法完全不同，而融合只对后两种有效。

这个账也直接给出了融合的收益上限公式：融合最多只能拿走"中间结果的 HBM 流量"这部分时间。如果一段子图里中间结果的搬运只占该段耗时的 30%，那么无论融合做得多漂亮，这段最多快 30%；如果这段子图本身只占整个前向的 5%，端到端最多快 1.5%。先量这两个比例，再决定要不要动手，是本卡后面几节反复回到的纪律。

把每个算子想成一个只会"从仓库取料、加工、送回仓库"的工位。工位之间的搬运车才是瓶颈，加工本身很快。融合不是让工人手更快，而是把相邻几道工序挪到同一张案板上，让半成品别再来回坐车。仓库（HBM）和案板（片上 SRAM）之间的车程差一个数量级，这就是全部收益的来源。

二、三类融合：链式、epilogue、算法重写

"算子融合"是一个被过度压缩的词，底下至少有三种难度和收益完全不同的做法。分不清它们，就会出现两类典型误判：明明编译器能自动搞定的事去手写，或者明明必须重写算法的事指望编译器。

第一类：element-wise 链式融合——编译器的主场

把一串逐元素算子接成一个 kernel，中间值只在寄存器里传递。TorchInductor 官方文档把这条称作"inductor 做的最重要的一项优化"。它有三个常见变体，方向不一样：

  • 纵向融合（vertical / pointwise fusion）：生产者-消费者关系的逐元素链，就是上一节 cos().cos() 的形态，省的是中间结果的往返。
  • 规约融合（reduction fusion）：把逐元素的生产者吃进一个规约算子里。(x * scale).sum() 融合后不需要先物化 x * scale。规约只能当"汇点"——它可以吸收前面的逐元素算子，但不能反过来把自己融进后面的算子。
  • 横向融合（horizontal / combo kernel）：把彼此独立、没有数据依赖的若干小 kernel 合成一次启动。这里省的不是访存而是启动开销，所以它专治 overhead-bound，在小 batch 解码这类场景才明显。TorchInductor 里由 config.combo_kernels 控制。

第二类：GEMM + epilogue 融合——"顺手做掉"

epilogue 融合指的是把矩阵乘之后紧跟的逐元素操作，塞进矩阵乘 kernel 的收尾阶段完成。这类融合的逻辑和第一类不同，值得单独理解：矩阵乘本身是 compute-bound 的，它的输出分块本来就在寄存器或共享内存里，而且本来就要写一次 HBM。既然如此，在写出去之前顺手给这个分块加上 bias、过一遍 GELU、再乘一个量化 scale，额外成本接近于零——省下的是"再读一遍输出、再写一遍输出"这一整趟往返。

反方向叫 prologue 融合：在把权重加载进片上时顺手做反量化。INT4/INT8 权重量化推理之所以能真的变快而不是先解压成 FP16 再算，靠的就是这个——这部分与 DP13 · 模型量化 的精度侧讨论互补。

第三类：整体算法重写——FlashAttention 是极致案例

当"不落地中间结果"这件事被算法本身阻挡时，机械融合就走到尽头，必须换算法。注意力就是最典型的一例：标准实现要算出 N×N 的分数矩阵、对它按行做 softmax、再乘 V。softmax 把一整行耦合在了一起——不看完全行就不知道归一化因子，所以你没法简单地把三个 kernel 串起来让中间值留在片上。

FlashAttention（Dao 等，NeurIPS 2022）的做法是把算法结构改掉：分块遍历 K/V，配合在线 softmax——维护逐行的运行最大值与运行和，边走边重新缩放已累积的输出，从而在任何时刻都不需要完整的一行。反向传播不再读回巨大的中间矩阵，而是存下 softmax 的归一化因子、在片上重算。整套操作被写进一个 CUDA kernel，N×N 矩阵从头到尾没有在 HBM 里出现过。

来源引用 · FlashAttention 论文（Dao et al., NeurIPS 2022）：论文报告注意力计算本身获得最高 7.6× 加速（GPT-2 上，对比 PyTorch 实现）；端到端 GPT-2（序列长 1K）训练加速 3×；BERT-large（序列长 512）比 MLPerf 1.1 训练速度记录快 15%；显存占用从序列长度的二次变为线性。最值得记住的一点是：这套算法输出的是精确注意力而非近似，FLOPs 与标准实现同阶（O(N²d)），反向因为重算甚至更多——它快，纯粹是因为 HBM 访问次数被大幅削减。论文同时指出，此前五年大量"降 FLOPs 的近似注意力"在真实硬件上并没有换来 wall-clock 加速，因为它们优化的不是绑定项。注意力机制本身的原理与各类高效变体见 T20 · 高效注意力，本卡只把它当作融合思路的上限案例引用。

三类融合的难度差别，用"做菜"打个比方：第一类是把切、拌、调味挪到同一块案板上，谁都会；第二类是炒菜起锅前顺手撒盐——因为锅本来就在手上，几乎不花时间；第三类是重新设计一道菜的做法，让某个必须冷藏的半成品干脆不存在。前两类可以交给工具，第三类只能靠人重新想。

三、编译栈的融合能力边界

三条主流编译路径都会做融合，但它们"能融什么"由各自的中间表示和融合规则严格限定。搞清边界的价值很实在：知道边界在哪，才能判断某段代码没变快是"编译器该融但被挡住了"，还是"编译器结构上就融不了"——这两种情况的处理方式完全相反。

torch.compile / TorchInductor：规则清楚，但怕被打断

它的流水线是四段：TorchDynamo 在字节码层面抓取计算图 → AOTAutograd 顺带把反向图也 trace 出来 → TorchInductor 降级到自己的 IR 并在调度阶段决定融合 → 生成代码（GPU 上生成 OpenAI Triton kernel，CPU 上生成 C++）。融合的核心判据是调度器里的 can_fuse(node1, node2)：一次融合必须合法（不在依赖图里引入环）且有益（真的减少了开销）。它支持的融合种类与上一节对应：逐元素融合（要求迭代域 numel 相同）、规约融合（共享输入与规约维）、混序规约（对同一张量不同维度的规约，仅 Triton 后端支持）、以及横向的 combo kernel。融合完成后 Inductor 还会自动尝试 CUDA Graph 捕获，把启动开销一并干掉。

这条路径最常见的失效模式不是"融得不好"，而是 graph break（图断裂：Dynamo 遇到无法 trace 的东西时，把已抓到的部分先编译，剩下的退回 eager 执行）。官方 FAQ 直说：用了 dynamo 却没看到期望加速，主要原因就是过多的 graph break。它的杀伤力有两层，第二层经常被忽略：

  1. 断点处的代码退回 eager——这部分只是回到原来的速度，损失有限。
  2. 断点把编译区域切成了碎片——横跨断点的那些融合机会全部消失，而且整段不再满足 CUDA Graph 捕获条件。真正的损失发生在"接缝"上：本该留在寄存器里的中间张量，现在要多走两趟 HBM。

示例场景：一个断点吃掉了大半收益。某团队给自研的 RMSNorm + SiLU 段写了 CUDA 扩展，按官方推荐用 torch.library.custom_op 注册，随后在整个 decoder 层上开 torch.compile。压测发现单步耗时几乎没变。用 torch._dynamo.explain 一看，自定义算子在每层中间形成一个不透明边界，把原本一整张的 decoder 图切成了前后两段；前后两段各自要把边界张量物化回 HBM，而这些张量原本会被 Inductor 融进相邻的逐元素链里，同时整层丧失 CUDA Graph 捕获资格、退回逐 kernel 启动。把自定义算子撤掉、让 Inductor 自己生成融合 kernel 后，单步耗时明显下降。结论不是"别写自定义算子"，而是：自定义算子必须自己赚回它摧毁的那部分融合，否则净收益为负。具体幅度强依赖模型结构、序列长度与 PyTorch 版本，此处只给可复现的排查链路，不给可搬用的数字。

TensorRT：按模式表融合，融不融还取决于精度和卡型

TensorRT 在构建期做融合，官方文档描述得很直接：构建阶段的第一件事就是"尽可能把层融掉"，方式是检测受支持的操作模式，把多层合并成一个带内部选项集的层。它维护一份公开的层融合目录（Layer Fusion Catalog），里面每一条都带约束——这几条约束特别能说明问题：

  • Conv → ReLU：激活必须正好是 ReLU；
  • Conv → GELU：输入输出精度必须相同且同为 FP16 或 INT8，且需要 Turing 及更新架构；
  • 深度可分离卷积融合：两个卷积精度必须都是 INT8，且计算能力 ≥ 7.2。

也就是说，同一张图在不同卡、不同精度下会融出不同的结果——这直接解释了"换了张卡性能对不上"这类现象。TensorRT 的融合决策可以通过 kINFO 级日志和 engine inspector 查看，这是 TensorRT 侧唯一靠得住的核对方式。它的能力边界也很清晰：目录里没有的模式就不融，需要新模式只能写 plugin（而 plugin 本身又成了一个优化屏障）。构建流程的完整拆解、tactic 自动选优与 engine 不可移植性，见 DP28 · TensorRT 与推理编译栈。

TVM：把算子按"可融合类型"分类，规则可以完整背下来

TVM 的做法最形式化，也最适合用来理解"融合规则"这件事本身。它给每个算子标一个 OpPatternKind，然后按类型跑三阶段融合：

OpPatternKind含义代表算子融合角色
kElemWise(0)逐元素，输入输出一一对应add、relu、exp最灵活，每一阶段都参与，可融进任何 injective 或 reduction 的汇点
kBroadcast(1)广播，输出轴按序映射到输入轴bias_add与 elemwise 同等待遇（注意 transpose 不算广播，因为它换了轴序）
kInjective(2)每个输出元素只依赖一个输入元素，但映射可以不平凡reshape、concatenate、transpose只在全路径都是 injective 或更简单时才融
kCommReduce(3)可交换规约sum、max、mean只能当汇点：能吸收前面的算子，永不向后融
kOutEWiseFusable(4)复杂算子，输出端可以接逐元素后继conv2d、matmul、dense第 0 阶段优先处理；两个此类算子永远不能互相融合
kOpaque(8)不可融合外部函数调用、有副作用的操作融合屏障（作用等价于 PyTorch 侧的 graph break）

三阶段的顺序本身就是一条设计经验：先给复杂算子（conv/matmul）配好它们的逐元素后继，再处理纯 injective 的融合，否则 reshape 之类的算子会抢先把链条切开，让 conv2d + bias_add + relu 这种最值钱的组合融不上。TVM 论文报告图级融合带来 1.2× 到 2× 的加速，量级与"取消中间结果往返"的理论预期一致。

四、手写 kernel 的性能账

决定自己写一个 kernel，就等于接下四笔账：占用率与寄存器的权衡、分支发散、共享内存复用、以及全局访存合并。这四笔账互相拉扯，几乎没有"全都最优"的配置——手写 kernel 的技艺，主要就体现在为具体 shape 找到那个折中点。

occupancy 与寄存器压力：不是越高越好，但太低一定出事

occupancy（占用率，SM 上活跃 warp 数与硬件支持的最大活跃 warp 数之比）的硬件定义见 DP25 · GPU 执行模型与存储层次，这里只谈它在调 kernel 时怎么用。Nsight Compute 文档给了一句非常精准的表述：更高的占用率并不总带来更高性能，但低占用率一定削弱隐藏延迟的能力。理论占用率由每线程寄存器数、每 block 共享内存、block 槽位、warp 槽位、barrier 等资源共同封顶；实测占用率则是运行时收集的 sm__warps_active.avg.pct_of_peak_sustained_active。

寄存器是这里最常见的封顶项。每个 SM 有一块固定大小的寄存器文件，每线程用得越多，能同时驻留的 warp 就越少。更糟的情况是寄存器溢出：编译器把放不下的变量挪到 local memory，而 local memory 物理上在 DRAM 里——本来想少访存，结果凭空多出一堆访存。调节手段是 --maxrregcount、__launch_bounds__，以及缩短变量的活跃区间。

但真正要理解的是反向权衡：一个分块良好的 GEMM kernel 会故意把大块累加器常驻寄存器，因此寄存器用量高、占用率低——而这往往是对的，因为累加器常驻正是数据复用的来源。Nsight Compute 的 triage 指南把这种情况明确列为一个象限：低占用率 + 高流水线利用率时，再加 warp 是反效果，因为已经饱和的流水线吸收不了更多工作，此时该优化的是那条热流水线本身，不是占用率。

warp divergence：32 个线程必须走同一条路

一个 warp 里的 32 个线程共享取指与发射。当它们因为条件分支走向不同路径时，硬件只能串行执行各条路径，代价与分歧路径数成正比。CUDA C++ Best Practices Guide 把控制流放在"指令优化"一章单独讨论，实践上的关键是让分支的粒度对齐 warp 边界：如果分支条件是 threadIdx.x / 32 这种整 warp 一致的量，就没有发散；如果是 threadIdx.x % 2，每个 warp 内部都要走两遍。对很短的分支体，编译器会用分支预测化（branch predication）把分支变成带条件的指令，代价从"串行两条路径"降为"多执行几条被丢弃结果的指令"。

Nsight Compute 侧对应的信号是 branch_resolving 停顿——注意官方对它的定义很克制：这是"等待程序计数器为分支更新"的簿记时间，不是"决定走哪条分支"的时间。减少不必要的跳转和控制流发散能压低它。

共享内存复用与 bank conflict

共享内存是手写 kernel 的主要武器：把一块数据从 HBM 载入一次，让 block 内多个线程反复取用。但它有一个硬性陷阱——共享内存被切成 32 个 bank，当一个 warp 里多个线程访问同一 bank 的不同地址时就发生 bank conflict，硬件把请求拆成若干次无冲突访问串行完成，有效带宽按拆分份数成比例下降。bank 的地址映射规则、32 路冲突的逐线程推演、以及 padding 到 33 为什么能修好它，在 DP25 · GPU 执行模型与存储层次 第五节有完整图解，这里只讲它在融合场景下的特殊表现。

融合 kernel 比普通 kernel 更容易踩到这件事，因为融合经常顺手改变了共享内存的访问方向：上游算子按行把 tile 写进共享内存，被融进来的下游算子却要按列把它读出来。这类改动既不增加 FLOPs 也不增加 HBM 流量，端到端的访存账算下来还是省的，所以从计算图层面看不出任何异常；但只要 tile 的行宽正好是 32 个 float，列方向访问就会整齐地全部落进同一个 bank。这正是"融合做对了、流量也确实降了、kernel 却没变快"的一类典型成因。常规解法是把行宽 padding 错开映射或做地址 swizzle，分块矩阵乘里这类布局设计的完整讨论见 DP26 · GEMM 与 Tiling 分块优化。

访存合并：官方标注的"高优先级"事项

全局内存的读写会被硬件合并（coalescing，把一个 warp 的访存尽可能凑成最少的事务）。CUDA C++ Best Practices Guide 把"确保访存合并"标为 High Priority。破坏合并的三种典型写法是未对齐起点、跨步访问、以及完全随机访问。指南还补了一条容易忽略的运维细节：在 GDDR 显存上开启 ECC 时，分散写入的开销会被进一步放大。

Nsight Compute 官方分诊顺序（"改了但没变快"照这个走） ① 指标可信吗？ kernel 时长与 Nsight Systems 的 wall-time 偏差超过约 2× → 先查 时钟锁定 / 缓存控制 / replay 模式，别急着看别的 （利用率略超 100% 通常是多趟采集的伪影，不是错误） │ 可信 ▼ ② 工作量够大吗？ waves per SM < 1 ⇒ 网格连一轮都填不满所有 SM → 此时任何 kernel 内部优化都可能被"填充不足"掩盖， 先加并行度（增大 grid / 合并调用 / 横向融合） │ 够大 ▼ ③ 受延迟限制还是受吞吐限制？ 比较 SM 计算吞吐 与 内存吞吐 ├─ 两者都低 (<60%) → 延迟受限，进 ④ ├─ 计算 ≫ 内存 → 查哪条计算流水线是限制项 ├─ 内存 ≫ 计算 → 查哪一级访存机制主导（DRAM / L2 / 共享内存） └─ 两者都高 (>80%) → 已接近该算法的硬件上限，只能换算法 │ ▼ ④ 为什么发不出指令？ 发射活跃度 < 约 20% = 严重饥饿 看 warp stall 分解，任一原因占比 > 约 30% 才追： long_scoreboard → 等 L1TEX（全局/局部）访存 ⇒ 访存"延迟"受限 （注意：这与"带宽受限"不是一回事， 解法是改合并 / 加 ILP / 预取进共享内存） short_scoreboard → 等 MIO，多数是共享内存 ⇒ 查 bank conflict math_pipe_throttle → 计算流水线被过订阅 ⇒ 其实是计算受限 lg_throttle / mio_throttle → 指令队列满 ⇒ 少量宽访存代替大量窄访存 barrier / drain → 同步等待 / 收尾大量写回，看尾部效应 branch_resolving → 控制流发散过多 │ ▼ ⑤ 占用率被什么封顶？ launch__occupancy_limit_* → register / shared-mem / CTA-slot / warp-slot 四种之一，对症减压 ★ 两条官方护栏，值得抄在便签上： · 优化目标是"提高发射槽利用率"，不是"把停顿数降到零" · 只有 kernel 时长同时改善，才算这次停顿优化成功

第 ④ 步里那条区分特别值钱：long_scoreboard 主导意味着 kernel 是访存延迟受限，这和"访存带宽吃紧"是两种不同的病。前者的解法是隐藏延迟（改善合并、增加指令级并行、预取到共享内存、提高缓存命中），后者的解法才是减少总字节数。把延迟问题当带宽问题治，改一堆布局却毫无收益，是这一层最常见的误诊。

示例场景："融合成功了，但端到端没变快"的三种真实死法。某推理服务把一段 RMSNorm + 残差 + SiLU 手工融成一个 kernel，微基准里该 kernel 单独测确实比原来三个 kernel 之和快了一截，但整层耗时几乎没动。按上面的顺序逐条走，暴露出三层各自独立的原因：其一，Nsight Compute 显示 waves per SM 小于 1——这个 kernel 在实际 batch 下网格太小，连一轮都填不满 SM，快慢基本被启动与填充掩盖；其二，融合后的 kernel 为了把三步的中间量都留在寄存器里，寄存器用量上升，实测占用率被 register 封顶压低，而这个 kernel 又是延迟受限的（发射活跃度低、long_scoreboard 占主导），占用率下降正好削掉了延迟隐藏能力；其三，该 kernel 以自定义算子形式注册，在 torch.compile 区域里形成不透明边界，把整层切成两段并使其丧失 CUDA Graph 捕获资格——微基准量不到这项损失，因为微基准里根本没有编译区域。可迁移的教训有两条：微基准与端到端必须都测，且当两者结论矛盾时，答案通常在"这个 kernel 之外"。服务级别的指标口径与压测方法见 DP16 · 推理服务压测方法论，推理侧瓶颈的整体归因见 DP10 · 大模型推理性能瓶颈分析。

六、什么时候不该手写

手写 kernel 的技术门槛是显性的，它的持有成本是隐性的——而后者才是多数团队真正付不起的部分。这一节讲怎么在动手之前把账算完。

先算收益上限，这一步不能省

能拿到的加速被两个比例锁死：目标区段占端到端时长的比例，以及这段里"中间结果搬运"占该段的比例。

端到端收益上限 ≈ 该区段耗时占比 × 该区段可省的访存时间占比

举个再简单不过的算术：某段逐元素链占单步耗时 8%，其中中间结果往返大约占这段的一半，那么把它融到理论最优，端到端上限约 4%。如果这段已经被 torch.compile 融过一轮、只剩两成余量，上限就掉到 1.6% 以下。先把这个数算出来，再决定它值不值一个人两周。这条纪律能筛掉大部分手写冲动，因为多数"看起来很多小算子"的地方，占比其实很小。

版本与硬件绑定：手写 kernel 真正的长期成本

一个手写 kernel 实际上是把一批假设焊死在代码里，其中任何一条变化都可能让它从"最快"变成"最慢"：

  • 硬件绑定：每 SM 的寄存器文件大小、共享内存容量、SM 数量、Tensor Core 支持的形状与精度，跨代都在变。为某代卡精心调过的分块，在新一代上可能不再是好配置，需要重新扫参。
  • 框架绑定：自定义算子按官方推荐用 torch.library.custom_op 注册后，Dynamo 会把它当不透明边界处理——这是正确设计，但意味着每一个手写 kernel 都自带一个 graph break。它必须先赚回自己摧毁的那部分融合，才谈得上净收益。
  • 反向自己兜：训练路径上手写前向就要配套手写反向，还要保证数值与自动微分一致，测试面翻倍。
  • 数值口径：融合改变累加顺序，输出与未融合版本会有合法的微小差异。没有事先约定的容差基准，之后每次精度波动都会变成一场"是不是 kernel 写错了"的拉锯。

阶梯式路线：手写永远是最后一档

优化阶梯：从上往下，成本递增、可维护性递减 ① 清掉 graph break 成本最低、收益常常最大 torch._dynamo.explain 定位 → 消除数据相关控制流与不必要边界 CI 里用 fullgraph=True 当门禁，防止断点被无声提交 │ 还不够 ▼ ② 让编译器多做一点 开更激进的编译模式与 autotune；确认 CUDA Graph 真的捕获成功； 对齐/分桶输入 shape，避免反复重编译 │ 还不够 ▼ ③ 换用现成的融合实现 FlashAttention 系列、框架自带的 fused RMSNorm / fused 优化器、 带 epilogue 的 GEMM 库（CUTLASS 模板） —— 别人已经付过维护成本，且通常已适配多代硬件 │ 仍有明确且够大的缺口 ▼ ④ 用 OpenAI Triton 手写 Python 里几十行，编译器接管块内调度与共享内存分配； 配 autotune 后跨硬件重调成本可控 │ Triton 表达不了（warp 级原语 / 异步拷贝 / │ Tensor Core 精细排布 / 极致流水） ▼ ⑤ CUDA C++ / CUTLASS 从底层写 能力天花板最高，持有成本也最高：绑硬件、绑版本、绑人 ★ 每下一档之前先回答两个问题： 上一档真的做尽了吗？这一档的收益上限算过吗？
  • 动手前先量两个比例：区段占端到端多少、其中访存占该区段多少
  • 先用官方 triage 顺序确认瓶颈类型，再决定改什么
  • 把"清掉 graph break"当第一优化项，它通常最便宜
  • 能用现成融合库就用，别人已经替你付了跨代适配成本
  • 手写优先选 OpenAI Triton，只有表达不了才下到 CUDA C++
  • 为每个手写 kernel 配 shape 覆盖测试与明确的数值容差基准
  • 微基准与端到端两条线都测，结论矛盾时去 kernel 外面找原因
  • 不要说"融合减少了计算量"——FLOPs 通常一字不变
  • 不要在 waves per SM 小于 1 的情况下调 kernel 内部参数
  • 不要把占用率当成越高越好的指标去优化
  • 不要把访存延迟受限（long_scoreboard 主导）当带宽问题去治
  • 不要以停顿计数下降为验收标准，要看 kernel 时长是否真的缩短
  • 不要在 compute-bound 的大矩阵乘上手写 kernel 去挑战厂商库
  • 不要在模型结构与 shape 还在变的阶段特化 kernel
  • 不要让一个 kernel 只有一个人能维护
判断该不该手写，只需要一个问题问三遍：这段代码的时间到底花在哪？如果花在等数据、而编译器又结构性地融不了（需要跨规约的算法重写），那手写是对的。如果花在算力上，或者编译器本来能融、只是被一个断点挡住了，那手写就是在用最贵的方式解决一个便宜的问题。

如果你的结论是"不该手写，但需要把整张图交给一个更强的编译器"，那么下一站是编译式推理方案：构建期做完全部图优化与 kernel 选优，用编译时间换运行时性能，代价是产物与硬件、驱动、版本强绑定——完整讨论见 DP28 · TensorRT 与推理编译栈。如果结论是"kernel 没问题，是调度和批处理没做好"，那该看 DP11 · Continuous Batching 与推理调度策略 与 DP09 · KV Cache 显存优化；框架层面的整体选型见 DP05 · 大模型推理框架选型。

Q&A

算子融合到底省下了什么，为什么说不是省计算？

省的是中间结果在显存（HBM）和片上存储之间的往返次数，计算量基本一字不变。GPU 上每次 kernel 调用都要把输入从 HBM 读进来、算完写回 HBM，因为框架契约要求每个算子返回一个真实存在的 Tensor。融合的本质是识别出"没有第二个消费者"的中间结果，让它只留在寄存器或共享内存里，不再落地。以 x.cos().cos() 为例：未融合需要 4 次 HBM 访问（读 x、写中间、读中间、写结果），融合后只需 2 次，浮点运算次数完全相同 2N，但在带宽受限时耗时约减半。FlashAttention 更极端——它的反向传播为了不读回中间矩阵而选择在片上重算，FLOPs 反而增加了，却仍然快得多。所以"融合减少计算量"这个说法是错的，正确的说法是"融合提高了算术强度"。

为什么有的地方融合了几乎没提速？

有四种常见原因，对应四种不同的处置。第一种是这段计算本来就是 compute-bound（比如大矩阵乘），时间花在真实的乘加上，中间结果的搬运本来占比就低，没什么可省。第二种是工作量太小：Nsight Compute 的 waves per SM 小于 1，说明网格连一轮都填不满所有 SM，此时快慢主要由填充不足和启动开销决定，kernel 内部怎么改都被掩盖。第三种是融合把寄存器用量推高，压低了占用率，而这个 kernel 恰好是延迟受限的——省下的访存收益被削弱的延迟隐藏能力抵消掉了。第四种最隐蔽：融合以自定义算子形式注册进 PyTorch，形成了 graph break，把编译区域切碎、丧失 CUDA Graph 捕获资格，微基准量不到这项损失，因为微基准里没有编译区域。判断方法是按官方 triage 顺序走一遍，并且微基准和端到端两条线都测。

OpenAI Triton 和 NVIDIA Triton Inference Server 是什么关系？

没有任何关系，只是名字撞了。OpenAI Triton（triton-lang）是一个写 GPU kernel 的 Python DSL 加 JIT 编译器：你用 @triton.jit 写块级程序，编译器负责块内调度、共享内存分配和访存合并，它也是 TorchInductor 在 GPU 上生成代码的后端。NVIDIA Triton Inference Server 是一个模型服务框架，负责多模型加载、版本管理、动态批处理、gRPC/HTTP 接口，运行形态是拉容器镜像加配置 model repository。一个解决"怎么算得快"，一个解决"怎么把模型稳定服务出去"，处在技术栈的完全不同层次。撞名的原因是：Tillet 在 2019 年 MAPL 论文里给这个 DSL 定名 Triton 时，NVIDIA 那款产品还叫 TensorRT Inference Server，约一年后 NVIDIA 才改名为 Triton Inference Server，而 DSL 一方因为论文已被引用、PyPI 名字已占用等原因选择不改名（见 triton-lang/triton issue #156）。实践上的辨认方法：看到 import triton 就是 DSL，看到 tritonserver 容器就是服务框架。

graph break 为什么会伤害性能，怎么定位？

graph break 是 TorchDynamo 遇到无法 trace 的代码时的行为：把已抓到的图先编译，剩下的退回 eager 执行。伤害有两层，第二层更重。第一层是断点处的代码回到原速度，损失有限。第二层是断点把编译区域切成碎片，横跨断点的融合机会全部作废，断点两侧必须各自把边界张量物化到 HBM，同时整段丧失 CUDA Graph 捕获资格、退回逐 kernel 启动——真正的损失发生在"接缝"上。PyTorch 官方 FAQ 明确指出，用了 dynamo 却看不到期望加速，主因就是过多的 graph break。定位工具是 torch._dynamo.explain(fn)(*inputs)，它会聚合列出所有断点及其原因；torch.compile(fn, fullgraph=True) 会在遇到第一个断点时直接报错，适合放进 CI 当门禁。常见触发包括数据相关的控制流（.item()、按张量值分支）、用 torch.library.custom_op 注册的自定义算子（这是设计如此的不透明边界）、对 view 的原地操作与复杂 aliasing、以及不支持的 Python 结构。

占用率（occupancy）应该调到多少？

没有目标值，只有配合流水线利用率一起看才有意义。Nsight Compute 官方文档的表述是：更高的占用率并不总带来更高性能，但低占用率一定削弱隐藏延迟的能力。实践上用一个二维判断：占用率低而流水线利用率高，说明少量 warp 已经把某条流水线打满，再加 warp 是反效果，该优化的是那条热流水线或换算法——分块良好的 GEMM kernel 常常就落在这个象限，它故意把大块累加器常驻寄存器，寄存器用量高、占用率低，但这正是数据复用的来源。占用率高而流水线利用率低，说明 warp 在但发不出指令，属于延迟受限，该去看 warp stall 原因。两者都低是填充不足或启动资源受限。两者都高则说明已接近该算法的硬件上限。另外还有一条独立信号：实测占用率明显低于理论占用率时，问题不在资源封顶，而是负载不均、尾部效应或调度开销——官方原话是"理论与实测的巨大差距通常指向高度不均衡的工作负载"。

融合把中间结果留在了共享内存里，为什么反而更慢了？

先排除两个常见误判：一是融合后的 kernel 寄存器用量涨上去触发了 spill，中间结果名义上在共享内存、实际有一部分被挤到了 local memory（走 HBM），这时 DRAM 流量不降反升；二是共享内存用量涨了导致每个 SM 的驻留 block 数下降，延迟暴露不足。这两类在 Nsight Compute 里分别体现为 local memory 流量出现和占用率的 limiter 变成 shared memory。如果两者都排除了，最可能的就是 bank conflict——融合往往改变了共享内存的访问方向，上游按行写、下游按列读，端到端流量确实降了，但列访问会把一个 warp 的 32 个线程整齐地送进同一个 bank，请求被拆成多次串行。它的信号是 short_scoreboard 停顿占比偏高（等 MIO 操作，主要来自共享内存），访存分析 section 也会直接给出冲突计数。bank 映射规则与修复手法见 DP25 · GPU 执行模型与存储层次 第五节。这三类原因的共同点是：它们都不在计算图这一层，所以只看融合前后的算子数量和理论访存量永远发现不了，必须落到 profiler。

为什么 FlashAttention 不能靠编译器自动做出来？

因为它不是机械融合，而是换了算法。编译器做的融合必须保证逐步等价：它能把生产者-消费者关系的逐元素算子串起来让中间值留在寄存器，也能把逐元素算子吸收进一个规约里，但它不会重新设计计算顺序。注意力的障碍在于 softmax 把一整行耦合在一起——不看完整行就不知道归一化因子，所以你没法简单地把"算分数、做 softmax、乘 V"三个 kernel 拼成一个而不物化 N×N 矩阵。FlashAttention 的解法是引入在线 softmax：维护逐行的运行最大值与运行和，分块遍历 K/V 时边走边重新缩放已累积的输出，从而任何时刻都不需要完整一行；反向不再读回中间矩阵，而是存下归一化因子在片上重算。这套改造涉及数值稳定性设计和反向的重新推导，属于人类算法设计范畴，没有编译器能自动完成。这也给出一条实用判据：某个融合如果需要跨规约，就别等编译器；如果不需要，那它没被融合就一定是被某个屏障挡住了，去找屏障。

怎么判断一段代码值不值得手写 kernel？

先算收益上限，再算持有成本。收益上限约等于"该区段占端到端耗时的比例"乘以"该区段里可省的访存时间比例"。比如某段逐元素链占单步 8%，其中中间结果往返约占该段一半，理论上限就是 4%；如果这段已经被 torch.compile 融过一轮只剩两成余量，上限掉到 1.6% 以下。持有成本包括：手写 kernel 是对具体 shape 与精度的特化，模型一改就要重调；跨硬件代际的寄存器文件、共享内存、Tensor Core 形状都在变，需要重新扫参；用 torch.library.custom_op 注册后它自带一个 graph break，必须先赚回被摧毁的融合；训练路径还要配套手写反向并保证数值一致。四类明确不该手写的情形是：目标区段已是 compute-bound（挑战不过厂商 GEMM 库）、收益上限只有个位数百分比、shape 与 dtype 仍在频繁变化、以及团队里只有一个人能维护它。正确顺序是阶梯式的：先清 graph break，再让编译器多做一点，再换用现成融合库，然后才是用 OpenAI Triton 手写，最后才下到 CUDA C++。

Inductor、TensorRT、TVM 的融合能力差在哪？

差在决策时机和决策依据。TorchInductor 在运行时首次触发编译，靠调度器的启发式 can_fuse 判断——一次融合必须合法（不引入依赖环）且有益（真的减少开销），支持逐元素融合（要求迭代域相同）、规约融合（共享输入与规约维）、混序规约（仅 Triton 后端）和横向 combo kernel，融合后还会自动尝试 CUDA Graph 捕获；它最大的敌人是 graph break。TensorRT 在离线构建期融合，依据是一份固定的层融合模式目录，每条都带约束——比如 Conv → GELU 要求输入输出同为 FP16 或 INT8 且需要 Turing 及更新架构，深度可分离卷积融合要求 INT8 且计算能力不低于 7.2——这意味着同一张图在不同卡、不同精度下会融出不同结果，目录外的模式只能写 plugin，而 plugin 本身又是优化屏障。TVM 最形式化：给每个算子标 OpPatternKind（elemwise / broadcast / injective / commReduce / outEWiseFusable / opaque），按三阶段跑，规约只能当汇点、两个 outEWiseFusable 永不互融、opaque 是屏障；先处理 conv/matmul 的逐元素后继再处理纯 injective，就是为了不让 reshape 抢先切断 conv2d + bias_add + relu 这种最值钱的组合。三者的共同上限是：都只做保证等价的机械合并，没有一个能替你重新设计算法。
