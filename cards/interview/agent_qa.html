一、基础概念

这一章回答三个最基础也最容易被追问到哑火的问题：Agent 到底是什么、由什么构成、和 Workflow/Tools 的边界在哪。答题主线只有一条：谁在做「下一步干什么」的决策。

Q1 · 什么是 Agent？与大模型的本质不同

Agent 是围绕目标「自主闭环」的智能系统：给定目标后自己拆步骤、调工具行动、把结果感知回来、动态调整下一步，直到任务完成。普通大模型是被动的文本生成器——一问一答、知识冻结在训练截止点、不能执行动作、没有持续状态；Agent 在模型之上加了一层「感知 → 规划 → 行动 → 再感知」的闭环，从生成文字变成真正做事。

追问链：

追问问题回答要点
为什么 Agent 到 2024-2025 才爆发？三个条件同时成熟：模型推理与指令遵循跨过「能用」门槛（GPT-4/Claude 3 一代）；Function Calling 让工具调用标准化为结构化 JSON；框架、向量库、API 生态配套完善。
「能调工具」就等于 Agent 吗？不等于。工具调用只是一种能力，Agent 的关键是自主决策：自己决定用不用、用哪个、何时停，并带多步反馈闭环。
工具到底是谁在执行？模型只输出「调哪个工具、传什么参数」的决策，真正执行是外部代码，结果再回填给模型——决策与执行分离。
MCP 和 A2A 是什么？MCP（Anthropic，2024）标准化 Agent 与工具的连接，被称为工具界的 USB-C，2025 年底捐给 Linux 基金会旗下 AAIF；A2A（Google，2025）标准化 Agent 之间通信，靠 Agent Card 声明能力。一个管拿工具，一个管互相说话，互补分层。
举个直观例子说明差别？「查天气，下雨就取消跑步计划」：LLM 只会说「您可以打开天气 App 查询…」；Agent 会调天气 API → 发现中雨 → 调日历 API 删掉跑步计划 → 告诉你结果。总结句：LLM 有四个天花板——只会说不会做、没有记忆、知识截止、不会规划，Agent 的工具 / 记忆 / 规划模块正好逐一补上这四个洞。
❌ 答「Agent 就是给大模型加了插件/工具」→ ✅ 先点出「自主闭环」：自主规划、多步执行、反馈调整，工具调用只是其中一环。

Q2 · Agent 的核心组件构成

四大组件缺一不可：LLM 是大脑，负责理解输入并决策下一步；工具系统是手脚，是与外部世界交互的唯一入口；记忆系统是档案室，短期保住当前任务状态、长期跨任务积累；规划模块是项目经理，把复杂目标拆成可执行步骤。四者共同支撑「规划 → 决策 → 执行 → 存入记忆 → 再决策」的运行节奏。

追问链：

追问问题回答要点
记忆就是上下文吗？不完整。短期记忆是 context window 里的 messages，任务结束即清空；长期记忆用向量数据库持久化、支持跨任务语义召回，两者机制与用途都不同。
System Prompt 有多重要？它是 Agent 的「岗位说明书」，定义角色、行为边界与输出格式，是最直接的行为控制手段，工程调优中占很大比重。
模型选型看什么？三点：推理能力决定拆解质量、工具调用稳定性决定 JSON 出错率、上下文窗口决定多步结果装不装得下。常见做法是强模型做核心决策、便宜小模型做意图分类等轻任务。
规划模块怎么工作？底层依赖 CoT/ToT 等推理技术；运作上分「先规划后执行」（Plan-and-Execute）和「边执行边规划」（ReAct）两种模式，实践中常粗计划定方向 + 执行中动态微调。
❌ 只说 LLM 和工具，漏掉记忆与规划 → ✅ 一次说全四件套，并用「老板 / 外包团队 / 档案室 / 项目经理」的类比加深印象。

Q3 · Workflow / Agent / Tools 三者区别

三者是粒度从小到大的嵌套结构，不是三选一：Tools 是最小能力单元，一个带 schema 暴露给 LLM 的函数，只执行、不决策；Agent 是决策主体，由 LLM 自主判断何时调哪个 Tool、何时停止；Workflow 是上层编排，开发者把流程骨架写死在代码里，LLM/Agent/Tools 都只是节点。一句话区分：谁决定「下一步」——Tools 不决定，Agent 自己决定，Workflow 由开发者提前写好。

追问链：

追问问题回答要点
Workflow 的节点必须是 Agent 吗？不是。LLM 可以直接当节点（如意图分类、回答生成），关键不在节点是什么，而在流程走向由代码控制。
生产里三者怎么组合？主流是 Agentic Workflow：主链路用 Workflow 保证可控，只在需要灵活判断的节点嵌入 Agent 能力，整体可控 + 局部灵活。
为什么说「能用 Workflow 就不用 Agent」？生产环境可控性优先于灵活性：Workflow 行为可预测、好测试、好定位；Agent 行为概率性，测试覆盖天然低。从简单到复杂、按需升级才稳健。
两者的成本差距能量化吗？同一任务下 Agent 的 Token 消耗通常是 Workflow 的 4-8 倍，可预测性也显著更低。大多数生产系统是混合架构——简单问题走 Workflow，复杂问题启动 Agent，搞不定升级人工；Anthropic 的官方建议也是「能用 Workflow 就别上 Agent」。
❌ 「Workflow 就是多个 Agent 串联」→ ✅ Workflow 节点可以是 LLM/Agent/Tools，本质区别在「下一步去哪」由代码决定还是由 LLM 决定。

二、设计范式与任务拆分

这一章是问答的主战场：三大范式要能说出「各自解决哪个层次的问题」，选型要给维度，任务拆分要给机制和收益。记住一句总纲：ReAct 管单步灵活，Plan-and-Execute 管全局不跑偏，Reflection 管输出质量。

Q4 · Agent 设计范式有哪些

主流设计范式三种：ReAct 边想边干，Plan-and-Execute 先规划再执行，Reflection 在前两者之上叠加自我评估做质量把关。Agent 与 Workflow 的分界线是「谁决定下一步」。生产环境纯 Agent 很少见，主流是 Agentic Workflow——用 Workflow 框住主流程保可控，在需要灵活决策的节点嵌入 Agent 能力。

追问链：

追问问题回答要点
Reflection 的定位是什么？不是独立流程，而是叠加在 ReAct / Plan-and-Execute 之上的「质量 buff」，在执行流里内嵌自我评估环节，代价是额外的 token 消耗与延迟。
为什么纯 Agent 在生产里少见？行为概率性、同一输入可能走不同路径、问题难复现，成本还容易失控；线上可控性远比灵活性重要。
范式之间怎么选？看任务复杂度与质量要求两个维度：步骤少且独立用 ReAct；长链路有依赖用 Plan-and-Execute；高质量要求再叠 Reflection，三种可以混用。
❌ 把「多 Agent 协作」列为设计范式 → ✅ Multi-Agent 是架构模式；设计范式指 ReAct、Plan-and-Execute、Reflection 三件套。

Q5 · ReAct 是什么、怎么实现

ReAct = Reasoning + Acting：LLM 交替输出 Thought（分析当前局势）与 Action（决定调什么工具），工具执行后把 Observation 写回历史，再进入下一轮思考，直到输出 Final Answer 终止。实现的关键认知：循环不是模型自己在转——模型每次只输出下一步决策，外层代码负责解析 Action、执行工具、回填历史并再次调用。现代实现用 Function Calling 的结构化 JSON 替代文本格式解析，更稳。

追问链：

追问问题回答要点
为什么要显式写出 Thought？防止模型「冲动决策」，先把问题理清再行动，决策质量更稳；且思考过程可见，出问题能直接定位是哪一步想歪了。
ReAct 有哪些常见坑？两个：循环漂移（无全局计划，被中间结果吸引而偏离原始目标）、错误传播（没有回头检查，早期一步错则整条链被污染）。根源都是纯前向推理。
ReAct 和 CoT 什么关系？CoT 只把推理写出来、无法与外部世界交互；ReAct 在推理链中插入真实行动。多跳问答基准上，只行动不推理的 Act-only 明显更差，说明推理为行动提供方向、行动为推理提供事实。
怎么防止 ReAct 死循环？三板斧：① 最大步数——通常设 15 步，超过强制终止；② 重复检测——连续 3 次出现相同工具 + 参数就直接退出（或基于已有信息直接总结）；③ 超时控制——给整个任务设最大执行时间。绝不能依赖模型自己停下来。
循环到底是谁在转：外层代码 vs 模型的职责边界 ┌──────────────── 外层代码（你写的 while 循环）────────────────┐ │ │ │ while step < MAX_STEPS: │ │ ① 拼上下文 = System + 工具 schema + 目标 + 历史(T/A/O) │ │ ② 调用 LLM ─────────────────────┐ │ │ │ 模型只做这一件事： │ │ ▼ 输出下一步决策 │ │ ┌──────────────────────────┐ │ │ │ Thought: 需要先查订单 │ │ │ │ Action : query_order(...)│ │ │ └────────────┬─────────────┘ │ │ ③ 解析 Action（Function Calling 的 JSON 比文本更稳） │ │ ④ 校验工具名白名单 + 参数 schema ← 模型不做校验 │ │ ⑤ 执行工具，拿到 Observation ← 模型不执行任何东西 │ │ ⑥ 截断/摘要 Observation 后回填历史 │ │ ⑦ 判定终止：Final Answer？超步？重复动作 3 次？超时？ │ │ 否 → step += 1，回到 ① │ │ 是 → 交付结果或走降级兜底 │ └─────────────────────────────────────────────────────────────┘ 记住这个边界：模型是「每轮被调用一次的决策函数」， 循环、执行、校验、终止判定全在你的代码里——它一步也管不了。
❌ 「模型自己在循环」→ ✅ 模型每轮只做一件事：输出下一步 Thought + Action；循环驱动、工具执行、历史维护全在外层代码。

Q6 · ReAct / Plan-and-Execute / Reflection 选型

三者解决的是不同层次的问题：ReAct 解决单步灵活性，边想边干、最灵活但长任务易跑偏；Plan-and-Execute 解决长任务跑偏，规划与执行解耦、有全局计划兜底并可动态 Replan；Reflection 解决输出质量，是叠加在前两者之上的检查修正环。选型看任务复杂度、流程确定性、质量要求三个维度，同时别忘成本账。
范式核心机制优势代价适用场景
ReActThought→Action→Observation 单步迭代灵活度最高、实现简单、过程透明每轮携带完整历史，token 随步数线性增长复杂度适中、需实时调整的任务
Plan-and-Execute规划-执行解耦 + 动态 Replan全局结构清晰、不易跑偏、可并行额外规划与重规划调用；初始计划错则难挽回长流程、步骤有依赖的复杂任务
Reflection生成→评估→改进闭环显著降低幻觉与逻辑漏洞每轮反思 token 增加 30%~100%，延迟上升代码、报告等高质量要求场景
📌 成本案例：一个 5 步工具调用任务、每步约 2000 token。ReAct 每轮携带完整历史，输入累计 2000+4000+6000+8000+10000 ≈ 30000 token；Plan-and-Execute 只在规划（≈3000）与汇总（≈4000）两个大头用足上下文，执行每步只带本步指令 + 前序结果摘要（每步 ≈1500），总计约 14500 token，省一半以上。再叠加「强模型规划、弱模型执行」的模型分层策略，实际花费还能再降 70% 以上。

追问链：

追问问题回答要点
动态 Replan 怎么做？每步执行完把结果和剩余计划交回规划器，判断是否需要调整；可设触发条件（输出偏离预期或步骤失败才重规划），避免每步都多花一次调用。
Reflexion 比普通 Reflection 多了什么？不止重做，还把失败原因写成「错题本」存入经验记忆，下次尝试作为上下文带入，避免重蹈覆辙，本质是语言强化学习。
有没有混合用法？有且常见：Plan-and-Execute 定全局计划，每步内部用 ReAct 执行，关键步骤再叠 Reflection 做质量把关。工程原则是「够用就好」，别为炫技堆范式。
被问「四种工作模式怎么选」怎么答？先给三个范式的速配表：ReAct 边想边做、灵活但 Token 高，适合通用任务；Plan-and-Execute 先规划再执行、最省 Token，适合复杂多步可预见任务；Reflection 生成→审查→迭代，适合代码/文书等高质量场景。再点明 Multi-Agent 不属于设计范式而是架构级第四选项——多专家协作、Token 消耗最高，只在复杂跨领域时使用。关键是讲清 trade-off：提升多少、成本多少、为什么这么选。
❌ 把三者当成并列且互斥的独立流程 → ✅ 先点明 Reflection 的「buff」属性，再按「解决的问题层次」对比，最后给选型口诀。

Q7 · 复杂任务怎么做任务拆分

拆分的根源是 LLM 的「工作台」有限：任务越大、中间状态越多，搜索原文、半成品段落、分析意见全堆在上下文里，模型追踪不住当前子目标，输出质量骤降。拆成原子步骤后每步只聚焦一件事，且每步产出可独立验证，失败只重试该步、不必从头再来。拆法两种：静态拆分写死流程，稳定可预测但僵化；动态拆分交给 LLM 规划（Plan-and-Execute），灵活但规划质量不稳定。

缺口补强一：自适应拆分。拆分不必一次定死——先让执行器直接尝试，做不好（超步数、质量不达标）就交回规划器继续拆细，递归进行。这样任务树只在真正困难的节点加深，计算开销与任务实际难度成正比，而不是一刀切。拆分结果还要过三条验收标准：完备性（所有步骤合起来覆盖原始任务全部要求）、独立性（职责边界清晰、不重复劳动）、可验证性（每步预先写好验收断言，不达标自动重试）。

缺口补强二：并行优化。拆完后把步骤依赖画成 DAG，无依赖节点并发执行，总耗时由关键路径决定而非步骤之和。前提是任务依赖稀疏、工具 I/O 占主要耗时；若每步都强依赖上一步，并行空间为零。

📌 并行案例：四个步骤各需 3 秒，其中步骤 3 依赖步骤 1、步骤 4 依赖步骤 2 和 3。串行执行共 12 秒；识别依赖后让步骤 1、2 并行，关键路径变为「1/2 并行 → 3 → 4」，总耗时 9 秒。在生产中依赖稀疏的任务上，端到端延迟降低 40%~60% 是常见水平。

追问链：

追问问题回答要点
拆分粒度的标准是什么？原子操作：只做一件事、边界清晰、有明确输出。判别技巧：能否给这一步写出清晰的函数签名，写不出说明还要再拆。
为什么不是拆得越细越好？过细导致调用次数和 token 上升、每步视野过窄、各部分衔接生硬；过粗又回到「桌面太乱」。粒度以原子性为准。
动态拆分的风险点在哪？规划质量是命门——规划一旦错了，后续所有步骤都建立在错误基础上；可要求规划步骤同时输出依赖关系与验收标准来兜底。
❌ 只说「拆了准确率更高」却讲不出原因 → ✅ 落到上下文工作台限制 + 独立验证重试，再补两种拆法、粒度标准与并行优化。

三、记忆机制

记忆题的答题框架固定：先分层（四层记忆），再回答三个工程问题（存什么、怎么存、何时取），最后落到粒度与衰减等细节。把「记忆 = 上下文」这种浅答法直接避雷。

Q8 · 记忆机制与设计

记忆分四层：感知记忆（当次调用的原始输入）、短期记忆（context window 里的 messages）、长期记忆（外部存储 + 语义检索，可细分语义 / 情景 / 程序三类）、实体记忆（结构化提取的关键事实）。设计记忆模块就是回答三问：存什么——偏好、关键结论、外部知识值得存，中间推理与闲聊不值得；怎么存——语义内容进向量库、结构化字段进关系库/KV，混合存储是主流；何时取——会话开始主动检索注入 system prompt，执行中把「查记忆」封装成工具按需调用。

追问链：

追问问题回答要点
为什么不能什么都存？存不是免费的：记忆库噪音会直接拉低检索精度。入库前先问一句「这条信息下次任务知道后会做得更好吗」。
什么是记忆衰减？检索分 = 语义相似度 × 时间衰减因子，越久远的记忆权重越低，防止过时信息淹没新事实；衰减速度按业务调——客服快、合规慢。
有哪些现成记忆框架？Mem0（记忆服务层，自动去重与冲突消解、按用户隔离）；Letta（前 MemGPT，仿操作系统分层：Core/Recall/Archival，由 Agent 自己通过工具管理）；Zep（时间感知，给记忆标有效期窗口）。
知识图谱补什么短板？向量检索只能找语义相近的单条记忆；图谱以「实体-关系-实体」三元组存储，支持多跳推理（从「用户 A 是 B 公司 CTO」+「B 主营云计算」推出答案），与向量检索互补使用。
外部存储类型怎么分工？按数据形态分：向量数据库存用户偏好与历史经验，靠语义检索；关系数据库存结构化事实与用户档案，精确查询；KV 存储（Redis）存任务状态与中间结果，读写极快；上下文窗口承载当前对话与工具调用历史，但容量有限（128K token 量级）。生产记忆的主流落地就是「Redis 短期 + 向量 DB 长期」的组合。
❌ 「长期记忆就是向量库，全塞进去全检回来」→ ✅ 先给四层分类，再答「存什么 / 怎么存 / 何时取」三问，最后才谈具体实现。

Q9 · 长短期记忆落地与粒度

短期记忆就是 messages 列表：每轮产出追加进去，每次调用携带完整历史，任务结束清空；进阶做法是结构化工作记忆——在工作台划出「目标 / 已确认结论 / 待验证假设」固定区域，每步主动更新区域而非无限追加。长期记忆 = Embedding + 向量数据库：写入时向量、原文、metadata 一起存；读取时把查询转向量，靠 HNSW/IVF 等近似最近邻索引找语义最相近的 top-k。粒度既不是逐句也不是整段会话，而是以「一次完整交互」或「一个独立知识点」为单位。

追问链：

追问问题回答要点
为什么不用关键词搜索？语义不重叠就漏检：问「代码习惯」、库里存的是「Python 风格偏好」，字符串匹配命中为零；向量检索靠意思相近命中。
粒度太细的具体危害？把一套完整用户偏好拆成四五条，一次检索只命中其中几条，LLM 拿到碎片化信息，行为就会不一致。
两层记忆何时起作用？短期保任务内连贯（工作台）；长期作用于两端——任务开始前检索注入背景，任务结束后把重要结论沉淀入库。
metadata 有什么用？记忆的标签：写入时间、任务类型、重要程度、记忆类型，检索时可精确过滤，比如只取最近 7 天 coding 类记忆。
❌ 以为粒度越细覆盖越全 → ✅ 粒度要保证「信息完整性」，一条偏好/知识点完整存一条，拆太碎必然检索出碎片。

四、Multi-Agent

Multi-Agent 题切忌说「多个 AI 一起效率更高」这种空话，必须落到两个结构性驱动因素：context 硬上限与单点泛才问题。

Q10 · 什么是 Multi-Agent

Multi-Agent 是把任务按职能拆给多个专职 Agent 协作完成。背后有两个结构性驱动：一是单 Agent 的 context window 有硬上限，复杂任务的信息量一旦溢出就开始遗忘早期内容；二是单个 Agent 身兼数职只能做泛才，上下文互相干扰、每件事都不专注。分工之后每个 Agent 的工作台只装与自己职责相关的信息，专业度高、子任务还能并行。三种典型协作形态：顺序流水线、并行扇出（调度者分发 + 汇总）、辩论/评审（多方案由裁判选优）。

追问链：

追问问题回答要点
中心化还是去中心化？工程上压倒性选中心化：调度逻辑清晰、责任可追踪、问题可排查；去中心化多停留在学术探索。
有哪些可用框架？CrewAI（上层易用）、LangGraph（底层灵活）；微软 2025 年把 Semantic Kernel 与 AutoGen 合并为 Microsoft Agent Framework 作为生产级统一 SDK。
A2A 协议解决什么？跨框架、跨厂商的 Agent 互联互通，用 Agent Card 声明能力；2025 年 6 月捐给 Linux 基金会，生态仍较早期。
❌ 答「任务太复杂单个 Agent 处理不过来」就停 → ✅ 落到两个结构性原因：context 窗口硬上限 + 单点泛才问题，再谈分工与并行收益。

Q11 · Single-Agent vs Multi-Agent 设计方案

Single-Agent = 一个 LLM + 工具集跑决策循环，整条链路在掌控之中、好调试。出现三类信号才升级 Multi-Agent：context 频繁撑爆、不同环节需要差异化的专业能力、存在可并行的子任务。Multi-Agent 拓扑分两种：中心化 Orchestrator（由简到繁有静态路由、动态规划、自适应编排三档，大多数场景动态规划够用）和去中心化 P2P。推荐渐进式演进：先用单 Agent 跑通，确认哪个环节是瓶颈，再把该环节拆给专职 Worker，而不是一上来设计五六个 Agent。

架构复杂度低中高
Context 压力全部压在一个实例各 Agent 隔离，Orchestrator 只持高层状态隔离但需额外共享协调状态
专业能力泛才，什么都做专才分工，各有专责专才分工，各有专责
并行能力不支持支持子任务并行支持并行
可控性 / 调试高 / 最易高，按调度链路追踪低，行为难预测、难排查
工程实用性高高低，主要用于学术研究

追问链：

追问问题回答要点
去中心化具体坑在哪？四条：任务分配无人协调（重复劳动）、执行顺序无保证、失败无人感知、没人确认整体完成——本质是缺少统筹者。
Orchestrator 和 Worker 怎么分工？Orchestrator 不做具体活，只读目标、拆任务、派发、汇总；Worker 只拿到自己那份指令，做完返回即退出，上下文始终干净。
步骤多就要 Multi-Agent 吗？不一定，单 Agent 循环调工具也能跑多步；看三类升级信号，不看步骤数量。

Q12 · Agent 记忆压缩方法

四种方法解决的是不同维度的问题：滑动窗口（按时间硬截断，零成本但会把三周前的关键决策和昨天的闲聊一并丢掉）、摘要压缩（丢弃前先提炼，可做层级式——近期留原文、中期留要点、远期只留决策）、重要性过滤（按价值而非时间，规则打分或 LLM 打分；进阶做法是观察遮蔽，不删除、只在构造 prompt 时按当前阶段动态隐藏）、结构化抽取（把事实抽成结构化字段，信息密度最高，类似病历卡）。工程最常见的是「滑动窗口 + 截断前摘要」的组合拳。

缺口补强：分清信息层与计算层。上面四种都在信息层工作——决定哪些内容留在历史里；Prompt Caching 则是计算层优化：多次请求之间如果 prompt 前缀相同，就复用 prefill 计算结果，不必重复计算。以 Claude 为例，缓存命中的 token 费用约为正常输入的 1/10，写入缓存有一次性溢价（5 分钟有效期约 1.25 倍、1 小时约 2 倍），前缀被复用两次以上即回本——Agent 的 system prompt + 长期记忆注入段多轮几乎不变，天然适合。选型口诀：短对话滑动窗口；长对话摘要 + 窗口组合；业务有明确关键字段用结构化抽取；高频长 prompt 叠加 Prompt Caching。

追问链：

追问问题回答要点
滑动窗口的本质缺陷？把时间当成唯一维度：关键决策和闲聊在截断面前一视同仁，属于「金鱼记忆」。
摘要一定够用吗？不一定。摘要按 LLM 的重要性判断取舍，当时看似不重要的细节事后需要时找不回，所以关键信息要另用结构化抽取兜底。
什么是主动压缩？不等 context 将满才动手：工具返回 2000 token 原始结果，读完立刻压缩成 200 token 要点替换原文，从源头控制增长速度。
❌ 只答滑动窗口，被追问就补「窗口调大一点」→ ✅ 四种方法是三个维度（截断 / 提炼 / 换载体），说清组合策略，并区分 Prompt Caching 的计算层属性。

Q13 · 为什么有时手搓 Agent 而不用成熟框架

手搓不是重复造轮子的姿态问题，而是拿回核心链路的掌控权。框架在探索期确实提速，但进入生产后会逐步暴露四类问题：抽象税、调试黑盒、破坏性升级、通用性隐性开销。手搓换回三样东西：链路透明（任意位置插日志与监控）、精确裁剪（只写需要的逻辑）、升级稳定（接口自己说了算）。务实答案是分阶段折中：POC 用框架，生产核心链路手写，周边工具继续借框架。

展开一：框架抽象税。框架的价值是把工具注册、循环驱动、历史维护这些样板代码封装掉，POC 从两周缩到两天是真实的。但抽象是贷款——省下的时间会在排障时以认知成本偿还：你自己只写了 50 行，报错 stack trace 却有 40 层，分不清问题在你的代码、框架某个版本的逻辑变化，还是 callback 触发时机。LangChain 早期的 AgentExecutor 后来被官方废弃、推荐迁移 LangGraph，本身就印证了框架升级之痛。

展开二：调试黑盒与可观测性。生产排障最快的路径是「靠日志复现故障」。手搓的每一行都在明处，可断点、可监控；框架则要穿透你没写、也不完全懂的层。Anthropic 在官方 Agent 构建指南里给过类似建议：不要一上来就用框架，先用最少的抽象把核心逻辑跑通——抽象层让你离底层更远，出问题后的调试成本可能高于当初省下的开发时间。

展开三：上下文与流程控制力。Agent 的心脏是那个循环：消息列表怎么拼、工具怎么选、循环何时退出、失败怎么重试。手搓可以精确控制何时压缩历史、何时强制终止、哪些错误值得重试；框架为通用性设计的逻辑（序列化中间结果、触发一堆 callback、记录详细日志）每次调用都跟着跑，高流量下累积成真实的延迟与费用，而且定制需求与通用设计偏差大时，改框架反而比自己写更费劲。

展开四：团队能力边界与折中策略。判断标准不是「框架好不好」，而是「你有没有掌控感」：能说清「框架替我做了什么、方法内部发生了什么」就可以用；说不清就是在依赖黑盒。因此分阶段演进最务实——探索期、团队刚接触 Agent、深度依赖框架生态时用框架；上生产、流量上来、高度定制、要求高可观测时，把工具循环、历史管理、错误重试、状态维护这些心脏手写，周边（tracing、文档解析、向量库客户端）继续借框架。

维度成熟框架手搓核心逻辑
上手速度快，样板代码全封装慢，样板自己写
调试stack trace 穿透抽象层，归因难链路透明，日志可复现
稳定性受 breaking change 影响接口自持，不受上游升级牵制
性能通用逻辑的隐性开销精确裁剪，优化空间在自己手里
适用阶段POC、团队入门、生态依赖生产、性能敏感、高度定制

追问链：

追问问题回答要点
框架的痛点分几个阶段暴露？三个：第一个诡异 bug（抽象深、归因难）、依赖升级打挂线上（breaking change）、规模化后 profile 出隐性开销。
手搓成本会不会太高？Agent loop 本体通常只有几十行，样板没想象多；真正贵的是建在黑盒上之后出线上事故。
一句话总结取舍？框架不是问题，「不理解就依赖」才是问题。

Q14 · 如何赋予 LLM 规划能力

本质是把隐式推理显式化。三种机制层层递进：CoT 让它把推理链写出来（加一句话、零成本，但是单链——开头走错全链皆错）；ToT 从链变树，生成→评估→剪枝循环探索多条路径（典型配置每层 3 条路径 × 2~3 层，成本约为 CoT 的 3~5 倍）；GoT 从树变图，允许不同分支的中间结论合并复用（学术前沿，生产几乎无落地）。工程上真正常用的是 Plan-and-Execute：Planner 出步骤清单、Executor 逐步执行、Re-planner 每步后评估是否调整计划。

缺口补强：为什么需要规划 + 工程怎么搭配。LLM 的 next-token 预测是一口气生成，多步推导的中间步骤全在暗处，误差悄悄累积、最后暴露在答案里——规划机制等于给每步推理一个可检查的落点。另外 CoT/ToT/GoT 与 Plan-and-Execute 不是替代关系：前者解决「每一步怎么想清楚」（推理模式），后者解决「多个步骤怎么全局编排」（设计范式），实际系统经常叠加使用。规划-执行解耦还带来模型分层的隐藏收益：规划只调一次用强模型，执行调用次数多但任务具体，用便宜小模型即可，总成本可降 70%~90%。

追问链：

追问问题回答要点
ToT 和「多生成几个选最好」的区别？ToT 不是最后才选，而是每层生成→评估→剪枝的循环，及早放弃差分支，把算力集中在有希望的分支上。
GoT 为什么难落地？图结构要管理推理节点的合并、依赖与评估，编排复杂度远超树形，目前主要是学术场景。
Plan-and-Execute 与 ReAct 的关系？不是替代：P&E 负责步骤的整体编排与动态调整，每个步骤内部仍可用 ReAct 循环来执行。
❌ 「加一句 CoT 就是规划能力」→ ✅ 规划是系统工程：显式推理（CoT/ToT/GoT）+ 全局编排（Plan-and-Execute + Replan），说出每层的演进逻辑与成本。

Q15 · 反思机制的原理与实现

反思是「生成 → 评估 → 改进」的结构化闭环（源自 Self-Refine），不是随机重试。它靠两个 prompt 驱动：评估 prompt 必须给出明确检查维度（事实 / 逻辑 / 完整性 / 表达）并提供 PASS 出口，否则模型要么敷衍说「看起来不错」，要么无限挑毛病把对的改错；改进 prompt 必须同时传入原始任务、原始输出、评估意见三样，缺一个改进就会盲目。触发粒度分步骤级（错误早发现，但调用翻倍）和任务级（开销小、能看整体连贯性问题）。工程上必须设 2~3 轮硬性上限防死循环，绝不能依赖 LLM 自己停。

缺口补强：多 Agent 互评与进阶变体。自我反思有个天然缺陷：评估者和生成者是同一个模型，对自己的输出逻辑存在「自洽」偏见，容易放过问题——所以高要求场景改用独立 Critic Agent 互评，道理和代码 review 一样。进阶变体有两个：Reflexion 额外把失败教训写入经验记忆，下次遇到类似任务先翻「错题本」再动手；LATS 把蒙特卡洛树搜索和反思结合，多路径探索 + 经验反馈，目前仍以学术研究为主。

📌 量化证据：在 HumanEval 代码生成基准上，GPT-4 直接生成的 pass@1 约 80%，加上 Reflexion「反思 + 记住教训」机制后提升到 91%。代码任务特别适合反思，因为可运行、可测试，执行结果就是最直接的反馈信号。

追问链：

追问问题回答要点
反思和重试的区别？重试是无信息增量的再来一次；反思把评估意见带入下一轮，改进是有针对性的定向修改。
两种粒度怎么选？看步骤间依赖：前一步错后面全错的用步骤级；步骤相对独立、更看重整输出质量的用任务级。
什么场景不值得开反思？简单任务（格式转换、简单问答）纯属浪费；实时性要求高的场景承受不了每轮多出的一次完整 LLM 调用。
❌ 「反思就是不满意就重新生成一次」→ ✅ 说出「生成→评估→改进」三步闭环、评估 prompt 的两个设计要点（维度 + PASS 出口）与硬性轮次上限。

Q16 · 多 Agent 协作与动态切换

协作解决「信息怎么传」，两种方案：消息传递（发送方不需要知道接收方，解耦好，但需要消息中间件）与共享状态（所有 Agent 读写同一个状态对象，直接，LangGraph 即此思路；状态设计要点：全局 / 局部分层、只追加不覆盖、错误也要写入状态）。切换解决「下一步叫谁」：静态路由把规则写死，稳定可预测但接不住边缘情况；动态路由让 LLM 做分类决策，灵活但每次多一次调用且偶有误路由。最稳的组合是主流程静态路由保底，只在规则匹配不上时交给 LLM 动态兜底。

追问链：

追问问题回答要点
通信方式怎么选？依赖强（前一步产出直接喂给后一步）用共享状态；需要 Agent 独立并行、互不感知，用消息传递。
Handoff 交接模式是什么？由当前执行的 Agent 自己决定下一棒交给谁（OpenAI Swarm 演示的模式，Swarm 本身是教育性、非生产级框架）；优点是无中央瓶颈、决策者最懂任务边界，缺点是无全局视角，必须记录流转路径、检测重复经过以防死循环。
动态路由怎么落地？把当前状态 + 可用 Agent 列表交给 LLM，只返回名称；配三道保护：名称合法性校验、fallback Agent、路由决策日志。
❌ 「协作就是流水线传结果，切换就是 LLM 每次决策」→ ✅ 说出两种通信模式的解耦 vs 直接取舍、两种路由的优缺点，以及「静态保底 + 动态兜底」的混合策略。

答题策略 Do / Don't

  • 先给 30 秒结论，再按追问逐层展开，让问答跟着你的节奏走
  • 永远带着取舍讲：灵活 vs 可控、质量 vs 成本、信息层 vs 计算层
  • 主动暴露工程坑：循环漂移、反思死循环、记忆粒度碎片化、框架黑盒
  • 引用具体数字：token 消耗对比、延迟降幅 40%~60%、准确率 80%→91%
  • 被问到没做过的点，先给概念框架，再明说「这块我了解到……落地细节还没实践」
  • 把「能调工具」等同于 Agent，漏掉自主规划与反馈闭环
  • 堆 ReAct、Reflexion、LATS 等名词却不讲适用场景和代价
  • 无脑吹 Multi-Agent / 纯 Agent，不谈协调成本与可控性
  • 用「更灵活」「更智能」代替具体机制与数字
  • 一上来就给最复杂方案，违背「够用就好、按需升级」的工程原则

Q&A

以下 7 个元问题针对「跨题追问」场景：问答不会一题一题按顺序进行，而是顺着一个答案往下钻。这里给的是应对策略，不是知识点本身。

被追问到没实操过的概念，怎么把话题拉回来？

三步法：先给概念的正确定位（一两句话证明你知道它是什么），再给相邻的实操经验（「Reflexion 我没直接落地，但反思闭环我在项目里用过，轮次上限设的 2」），最后主动把话题引向你熟悉的区域（「这块和记忆衰减的思路其实相通，我可以展开讲讲」）。切忌硬编细节——一个追问就能戳穿，而坦诚 + 迁移能力反而是加分项。

被反复追问「还有更好的方案吗」，用什么心态应对？

这不是在否定你，而是在测你的方案空间有多大。应对框架是「演进视角 + 代价标注」：承认当前方案是特定约束下的选择，然后给出升级路径（滑动窗口 → 摘要 → 结构化抽取；ReAct → Plan-and-Execute → 叠加 Reflection；单 Agent → 中心化 Multi-Agent），每一步都说清楚「换来什么、付出什么」。最后补一句「工程上够用就好」，展示你不是方案收藏家。

怎么把 16 题串成一个完整叙事？

用一条主线：「感知 → 规划 → 行动 → 再感知」的自主闭环。Q1-Q3 定义闭环的参与者（LLM / 工具 / 工作流），Q4-Q7 讲闭环里的规划怎么组织（范式与拆分），Q8-Q9 讲闭环的状态如何延续（记忆），Q10-Q11 讲闭环复制成团队（Multi-Agent），Q12-Q16 讲闭环在生产里的五大工程难题（压缩 / 框架 / 规划 / 反思 / 协作）。任何一题被深挖，都能顺着这条主线把相邻知识带出来。

被问「长上下文模型越来越强，记忆系统是不是要消失了」？

给三个不会消失的理由：一是成本，128K~1M 窗口每轮全量携带的费用随轮数线性增长，长会话扛不住；二是注意力稀释，窗口越长，每条信息分到的注意力越少，「装得下」不等于「用得好」；三是跨会话持久化，窗口再大任务结束也清空，用户偏好与历史经验必须外存。正确的表述是：长上下文缓解了短期记忆压力，但把记忆设计的重心推向了「存什么、何时取」的信息管理问题。

被问 MCP / A2A 这类生态协议，从哪个层次回答？

从「解决什么问题」切入而不是背协议细节：MCP 解决 Agent 与工具的 M×N 适配爆炸——标准化工具暴露后任何支持 MCP 的 Agent 即插即用，类比 USB-C；A2A 解决不同框架 Agent 之间的互发现与协作，靠 Agent Card 声明能力。再补一句两者的分层关系：MCP 管「伸手拿工具」，A2A 管「互相说话合作」。能说出 MCP 已捐给 Linux 基金会旗下 AAIF、A2A 2025 年 6 月捐给 Linux 基金会这类时间线，会显得信息很新。

同一道题，初级和高级的答法差在哪？

差在三层：初级答「是什么」（ReAct 是边想边做的循环）；中级答「怎么做」（循环由外层代码驱动，Function Calling 解析，max_steps 兜底）；高级答「什么时候不做以及代价」（这个任务 Workflow 就够了，上 ReAct 会引入不确定性和 token 线性增长，我们的判断信号是……）。每道题都尽量答到第三层——带取舍、带数字、带止损机制。

被问具体数字（成本 / 延迟 / 准确率）但记不准了怎么办？

给「量级 + 推导」而不是硬背数字：比如忘了 ReAct 的精确 token 账，可以现场推「每轮携带完整历史，输入是 1+2+…+n 的等差和，随步数平方级增长；Plan-and-Execute 每步只带摘要，是线性增长」——推导过程比数字本身更能证明理解。引用基准数据时加限定词（「我印象里 HumanEval 上是 80 到 91 个点」），既展示知识面又不把话说死。
