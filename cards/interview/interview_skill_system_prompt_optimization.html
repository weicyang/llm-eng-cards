IA-05 · 上百 Skill 塞爆 System Prompt 优化方案

提问：当上百个 Skill 塞爆 System Prompt 时，你该如何进行架构重构与优化？

核心观点

核心哲学：最好的 prompt 不是写出来的，而是根据上下文实时组装出来的。五层架构解决：广度（路由+检索）、深度（多代理）、速度（缓存+微调）。

两大技术陷阱

陷阱原理后果
Lost in the Middle注意力分配不均匀，开头结尾记得牢，中间断片第50个核心技能被视而不见
Attention Dilution总注意力带宽有限，指令越多每条权重越稀疏知道有工具但不按要求格式输出

五层优化架构

Layer 1: 极速意图路由

部署轻量小模型/分类器做"前台"，把用户大白话翻译成意图标签，过滤不相关技能。

效果：一分钟处理成千上万请求，只留一条清爽路径

Layer 2: Skill RAG（技能向量库检索）

将100+技能的描述、参数、成功范例打碎存入向量库。用户需求触发相似度匹配，只召回 Top-K（3-5个最相关技能）。

效果：System Prompt 从1万行减到几十行

Layer 3: 动态组装引擎

用 Markdown/JSON Schema 结构化描述（而非自然语言）+ Dynamic Few-shot（动态只取最像的一个示例）。

效果：模型一眼看出指令/参数位置，上下文压榨到极致

Layer 4: 分身代理架构（多智能体协作）

Manager Agent 负责拆解和分发任务，专家 Agent 各背负精简专属 prompt（数据专家、文案专家等）。

效果：每个专家住在精简纯净的小屋子里工作

Layer 5: 性能杀招

  • Context Caching：静态规则放开头，KV Cache 锁死，首字延迟降一个数量级
  • SFT 模型内化：核心高频技能直接微调进模型"肌肉记忆"

高频问答

Q1: 为什么 prompt 太长模型会变笨？

不只是 token 贵的问题，还有两个核心陷阱：(1) Lost in the Middle：模型对中间信息召回率断崖式下降；(2) Attention Dilution：总注意力带宽有限，指令越多每条分配到的权重越稀疏。结果就是模型"知道"有工具但不按格式输出。

Q2: Skill RAG 和传统文档 RAG 有什么区别？

传统 RAG 检索的是文档内容，Skill RAG 检索的是技能的描述、调用参数和成功案例。用户说"分析上季度财报"，系统召回"SQL生成"和"图表绘制"两个技能。System Prompt 从全量变成"精准缩印本"，模型只需处理 Top-3~5 个技能。

Q3: Dynamic Few-shot 是什么？和传统 Few-shot 有什么不同？

传统 Few-shot 把几十个示例写死在 prompt 里。Dynamic Few-shot 根据当前上下文，从库里只抓取最像的一个示例塞进去。既保证模型知道怎么模仿，又把上下文空间压榨到极致。

Q4: 什么时候不需要这么复杂的架构？

如果技能一共就十几个，核心模型完全能 hold 住，直接全量塞进去才是最稳最快的。只有当技能规模突破临界点、模型开始间歇性失忆或胡言乱语时，动态组装带来的精度提升才值得承受那一点延迟成本。要在响应速度、理解精度和实现成本之间找平衡。
