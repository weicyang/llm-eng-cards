IA-08 · Agent 上下文取舍方案

提问：如何设计一套 Agent 的上下文取舍方案？

核心观点

核心命题：上下文窗口已经越来越长（128K 甚至 1M），为什么还要做取舍？三个硬伤：(1) 首字延迟（KV Cache 计算量爆炸）；(2) 成本（Agent 循环跑，每次带几万 token 计费）；(3) Lost in the Middle（中间信息召回断崖式下降）。做取舍不是为了偷懒，而是保持极高的信息密度和决策质量——少即是多。

四大取舍维度

维度说明
时效性用户刚才的指令比半小时前的废话更重要
相关性语义向量计算，找与当前任务目标最贴近的历史记忆
重要性系统级指令、用户核心偏好（如"不吃辣"）必须焊死在上下文里
多样性避免全是重复报错信息，保留不同阶段的思考逻辑

四套实战组合拳

1. 动态滑动窗口

保留最近 N 轮原始对话，但窗口大小动态调整——当工具描述占空间大时自动缩小，给工具说明腾地方。

2. 层级化总结

旧对话不直接删，而是启动后台任务压缩成精炼摘要（脱水）。像人的记忆：忘掉具体吃了什么，但记住见了重要的人。

3. 向量检索回旋（RAG）

冷热数据分离：暂时用不到的背景知识移出 prompt，塞进向量库。Agent 推理时觉得"以前处理过"再通过语义检索精准捞回。

4. 逻辑脱水 / 推理减脂

工具返回的原始 JSON 又臭又长，80% 都是括号和冗余字段。存入长效记忆时只保留核心结果，剔除繁琐思考链路，省 50%+ 无效空间。

量化评价体系

用测试集对比：裁剪上下文后任务成功率是否下降。如果成功率不变但 token 节省 60%、首字延迟降低 40%，就是教科书级优化。追求帕累托最优解：用最少的钱、最快的速度办最漂亮的事。

高频问答

Q1: 上下文窗口已经很长了，为什么还要做取舍？

三个硬伤：(1) 首字延迟：KV Cache 计算量随长度爆炸，用户等 3 秒就关掉；(2) 成本：Agent 循环跑，每次带几万重复 token 计费，项目可能被砍；(3) Lost in the Middle：无关信息一多，中间信息召回断崖式下降，Agent 跑着跑着忘了最初目标。

Q2: 动态滑动窗口和普通滑动窗口有什么区别？

普通滑动窗口死板按时间删最早的对话。动态滑动窗口会检测当前任务需要调用的工具数量——如果工具描述占了很大空间，自动缩小对话窗口给工具说明腾地方，避免对话把指令给顶掉。

Q3: 什么是"逻辑脱水"？能省多少空间？

Agent 推理时工具返回的原始 JSON 数据又臭又长，80% 是括号和冗余字段。存入长效记忆时只保留核心结果（如计算器的答案、搜索的关键结论），剔除繁琐思考链路。至少省 50% 以上无效空间，模型读起来也更顺畅。

Q4: 怎么证明取舍方案是科学的？

建立测试集量化评估：对比裁剪前后的任务成功率。如果成功率不变但 token 节省 60%、首字延迟降低 40%，就是帕累托最优解。用任务成功率和成本曲线持续优化，不拍脑袋定策略。
