IA-04 · Agent 上下文维护机制

提问：项目里怎么设计 Agent 上下文维护机制？

核心观点

核心矛盾：不能把历史对话全塞给模型——(1) token 成本高；(2) Lost in the Middle（U型注意力衰减，中间信息召回率断崖式下跌）。解决方案是三层架构：短期记忆 → 工作记忆 → 长期记忆。

三大技术流派

流派核心思想优势
动态窗口派极致过滤，剔除废话省钱，模型不被干扰
压缩抽象派长文本 → 逻辑摘要逻辑完整，保留精髓
外挂检索派记忆存在外部，按需精准捞取精准，不污染上下文

三层架构方案

第一层：短期记忆（当下连贯性）

  • 语义剪裁：按相关性删除（剔除"Hello"、"谢谢"等冗余），而非死板按时间删
  • 保留决策点：system prompt 核心规则 + 关键工具调用结果始终在场

第二层：工作记忆（几十到上百轮对话）

  • 递归摘要：设触发阈值，超长对话压缩成 current_state
  • 流转替代堆叠：用结构化状态变量代替纯文本拼接（如"任务A已办，任务B正在办"）

第三层：长期记忆（跨天/跨月）

  • 结构化抽取：异步抽取用户偏好、习惯、关键信息
  • 存入图数据库/向量库：按需 RAG 召回，动态注入上下文

工程落地要点

要点说明
图状态机制上下文定义为 state，在图节点间传递和覆盖
记忆更新异步化响应归响应，提炼记忆丢进后台队列
上下文蒸馏离线压缩系统规则，千字 → 核心词汇
监控指标token命中率，检查召回的记忆是否被模型使用

高频问答

Q1: 为什么不能直接把所有历史对话塞给模型？

两个致命问题：(1) 成本：几百轮对话单次回复可能花好几块钱；(2) Lost in the Middle：斯坦福研究证明模型对长文本中间部分召回率断崖式下跌，简单堆叠会导致 Agent 在中段开始胡言乱语，忘记关键约束。

Q2: 短期记忆和滑动窗口有什么区别？

滑动窗口是死板按时间删除最早的对话；短期记忆采用语义剪裁——按相关性删除（剔除闲聊废话），保留决策点（system prompt 规则 + 工具调用结果）。这样即使对话很长，重要信息也不会被误删。

Q3: 工作记忆的"递归摘要"怎么实现？

设触发阈值（如每N轮或达到一定token数），让模型把之前的细节压缩成 current_state。用结构化状态变量代替纯文本拼接，如记录"任务A已完成、任务B进行中"。这样 token 消耗恒定化，Agent 无论聊多久都有强任务目标感。

Q4: 长期记忆更新为什么要异步化？

如果 Agent 每次回答前都先跑总结、写向量库，用户等待时间太长。正确做法：响应归响应（同步返回结果），提炼记忆的操作丢进后台队列异步跑。这样用户体验不受影响，记忆系统也能持续更新。

Q5: 怎么拔高回答？

核心心法：优秀的 Agent 架构师追求的不是"让模型记住更多"，而是"让模型学会主动遗忘"——主动丢弃噪音，把逻辑抽象成状态机，把海量知识做异步分离存取。在 token 成本、推理延迟和信息完备性三者之间找到平衡点。
