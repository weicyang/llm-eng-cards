一、Agent 与 Workflow 的边界

Agent 基本架构跟 LLMChain 到底差在哪？
LLMChain 是静态流水线 —— 预定义的线性工作流，各执行逻辑与调用顺序均被硬编码固化，缺乏动态规划与自适应调整能力。Agent 是带大脑的项目经理 —— 由规划、记忆、工具使用和推理循环组成，能根据核心目标自主决定执行路径。核心差异在于自主性：LLMChain 的每一步都是写死的，Agent 的每一步都是动态决策的。判断一个系统是不是 Agent，只需问一句：执行路径是代码决定的，还是模型每轮现场决定的？
什么场景根本不需要 Agent？
当任务路径可以被穷举时就不该上 Agent。判据有三条：一是步骤固定，比如「读工单 → 分类 → 写库 → 发通知」，路径不随输入变化；二是错误代价高，需要每一步都可审计可回放；三是延迟与成本敏感，Workflow 一次 LLM 调用能完成的事，Agent 往往要跑 4~6 轮。不这么做的代价很实在：把固定流程交给 Agent，等于用 4 倍 Token 和 4 倍延迟换来一个随机性更高的结果，还额外引入死循环和目标漂移两类新故障。
工作流和自主智能体，到底该怎么选？
两种范式的选择取决于业务特性：静态工作流（求稳） —— 基于 DAG 或状态机路线写死，高度可靠可预期，适合核心业务线如报销单审计、规范化客服；自主智能体（求变） —— 放权让模型做黑盒调度、自我判断调用路径，适用于无边界探索性研究、开放式代码生成。核心心法：越靠近公司核心利润 / 风控业务，越要限制其自主行动空间；越偏向创意与研发环节，越要放权。实践中最常见的落地形态是「Workflow 骨架 + 局部 Agent」——主流程用状态机保证可控，只在真正需要探索的那一个节点里放一个受限 Agent。
Agent 的自主度可以分几档？
业界常按五档描述，面试里能报出档位说明你思考过边界：L1 纯 Prompt 链，路径全写死；L2 单 Agent 带工具，模型选工具但流程受限；L3 单 Agent 带反思（Producer-Critic 自审自改）；L4 多 Agent 分工协作；L5 完全自主、可自行创建子任务与工具。真实生产的重心压在 L2~L3——约八成场景根本用不到多 Agent。选档位的原则是「够用就停」：每升一档，可观测性变差一档、Token 成本翻一倍、故障模式多一类。

示例场景：某企业把「发票识别 → 校验 → 入账」的固定三步流程从 Workflow 改造成 Agent，希望「更智能」。结果单次处理 Token 从 1.8K 涨到 7.2K（4 倍），P95 延迟从 2.1s 涨到 9.4s，准确率反而从 96% 掉到 91%——因为 Agent 偶尔会自主决定「跳过校验直接入账」。回退成 Workflow 后指标全部恢复。这个案例的价值在于：能力上限不是自主度决定的，任务确定性才是。

二、ReAct 与推理循环

ReAct 的循环具体是怎么跑起来的？
ReAct（Reasoning + Acting）把「想」和「做」交替进行：每轮模型先输出 Thought（分析当前状态、决定下一步），再输出 Action（选定工具与参数），系统执行后把结果作为 Observation 追加回上下文，进入下一轮。这样设计的关键理由是「让推理可以被现实纠偏」——纯 CoT 只在脑内推理，一旦中间假设错了会一路错到底；ReAct 每一步都能拿到真实反馈，错了下一轮就有机会修正。代价是上下文线性膨胀：第 N 轮要重传前 N-1 轮的全部 Thought 和 Observation，所以必须配步数上限和上下文压缩。
ReAct 和 Plan-and-Execute 有什么区别？
ReAct 是走一步看一步，每轮都重新决策下一步；Plan-and-Execute 是先一次性产出完整计划，再逐条执行，执行中不再回头改计划（或只在失败时重新规划）。ReAct 适应性强但容易在长任务里绕路、丢目标；Plan-and-Execute 目标稳定、Token 更省（规划只做一次），但计划一旦有误，后续执行全在错误路径上做无用功。折中方案是 ReWOO 式的「计划 + 变量占位」：先规划出带依赖关系的步骤骨架，执行时把上一步结果填进占位符，既保留计划的稳定性又不必每轮重传全量上下文。
Agent 的终止条件应该怎么设计？
必须同时有「成功退出」和「强制退出」两类，缺一不可。成功退出是显式的完成判据：模型调用特定的 finish 工具、输出满足 Schema 校验、或状态机达到终态。强制退出是物理护栏：最大步数（常取 10~25）、最大 Token 预算、墙钟超时、连续失败次数上限。只有成功退出没有强制退出，一旦模型判断不出「已完成」就会无限打转；只有强制退出没有成功退出，任务会跑满步数才停，白烧 Token。生产上还建议加一条「无进展退出」——连续 3 轮的动作和参数完全重复即判定卡死。
反思（Reflection）机制有用吗？代价是什么？
有用但要限量。反思的做法是让 Agent 在产出结果后再跑一轮自审：对照目标检查输出、找出缺陷、给出修改意见，然后重做一次。它对「有明确评判标准」的任务收益明显——代码能跑通编译、报告有结构要求、数据有校验规则；对开放式创作收益很小，甚至会把答案改得更平庸。代价是每轮反思让成本和延迟翻倍，而且反思轮数超过 2~3 轮后收益迅速衰减，还可能出现「自我说服」——模型反复确认一个错误结论。实践规则：反思最多 2 轮，且尽量用外部可验证信号（编译器、测试、Schema 校验）代替模型自评。

三、工具调用与工具设计

工具描述该怎么写，模型才选得准？
工具描述是给模型看的 API 文档，写法直接决定选择准确率。四条硬要求：一是名字动宾明确，query_order_by_id 好过 getData；二是描述里写清「什么时候用」和「什么时候不要用」，边界比功能更重要；三是参数给出类型、枚举值、单位和示例，避免模型自由发挥；四是把易混淆的工具在描述里互相点名区隔（「本工具只查未发货订单，已发货请用 query_shipment」）。不这么写的后果是模型在两个相似工具间反复摇摆，或者传入超出枚举范围的参数导致下游报错。
工具数量多了会怎样？怎么治？
工具数量是 Agent 最容易被忽视的成本项和准确率杀手。全部工具的 Schema 每轮都要塞进上下文，20 个工具轻松占掉 3~5K Token，且每轮重复计费；同时选项越多，模型选错的概率越高，超过约 15 个工具后选择准确率明显下滑。治法有三：按需加载——先用一个轻量分类器或路由把任务归到某个工具域，只注入该域的工具；分层工具——把细粒度工具包成粗粒度复合工具，对模型只暴露少量高层动作；命名空间隔离——按业务域给工具加前缀，配合描述里的互斥说明降低混淆。
Function Calling 和 MCP 是什么关系？
两者不在同一层。Function Calling 是模型侧能力——模型按给定 Schema 输出结构化的工具调用请求，本质是「让模型会填表」；MCP（Model Context Protocol）是工具侧协议——规定工具服务如何声明自己的能力、如何被发现、如何被安全调用，本质是「让工具可插拔」。没有 MCP 时每接一个新工具都要写一份适配代码，工具和 Agent 强耦合；有了 MCP，工具方按协议起一个 Server，任何支持 MCP 的 Agent 都能直接接入。生产上的典型组合是：MCP 负责工具的注册与发现，Function Calling 负责单次调用的参数生成。
工具调用失败了怎么处理？
按错误类型分流，不能一律重试。参数校验失败（类型错、枚举越界）应把校验错误信息回灌给模型让它改参数重试，这类错误模型自己能修；网络超时、限流这类瞬时故障走指数退避重试，重试 2~3 次，且必须保证工具幂等，否则「重复下单」就出现了；业务语义失败（订单不存在、余额不足）不该重试，要把结果作为正常 Observation 告诉模型，让它改变策略；权限或参数根本性错误则直接终止并上报。关键原则：把「可修复错误」变成模型的输入，把「不可修复错误」变成控制环的终止信号。
工具返回的数据太大怎么办？
这是 Token 爆炸最常见的来源——一个数据库查询返回上千行 JSON，直接回灌就把上下文撑爆了。四层处理：一是工具侧限流，在工具实现里强制分页与字段裁剪，只返回模型真正需要的字段；二是结果摘要，超过阈值的返回先用小模型或规则压成结构化摘要；三是外部引用，把大结果落到临时存储，只把句柄和统计信息给模型，需要细节时再按需取；四是硬截断兜底，超长直接截断并明确告知模型「结果已截断，共 N 条」，避免模型误以为看到了全量数据而给出错误结论。

四、记忆与上下文

ReAct 模式里，记忆机制到底怎么落地？
三层记忆：短期记忆 —— 驻留在当前上下文窗口，实时保存对话历史与工具调用结果，保障本轮多步推理连贯；长期记忆 —— 以向量数据库形式存在，跨会话前先去向量库根据 Embedding 检索历史经验和用户偏好；务实落地方案 —— 业界主流是增加「摘要层级」，通过递归压缩旧对话，避免海量 Token 推高成本和稀释注意力。关键挑战是「防稀释」—— 对话越长，每条信息的注意力权重越低，所以不是塞得越多越好，而要主动裁剪。
上下文压缩有哪些做法，各自会丢什么？
四种主流做法，代价各不相同。滑动窗口只保留最近 N 轮，实现最简单，但会丢掉任务开头的目标声明，是目标漂移的常见诱因，所以必须把系统目标固定钉在窗口外。递归摘要把旧对话压成摘要再拼接，能保留主线，但摘要过程会丢失精确数字和 ID，涉及金额、订单号的场景要单独做结构化留痕。结构化状态不存对话原文，只维护一份 JSON 任务状态（已完成步骤、已知事实、待办），Token 最省且可审计，代价是要为每类任务设计 Schema。外部记忆检索把历史全量落库、按需检索回来，容量无上限，但引入了检索准确率这个新失败点。
长期记忆该存什么、不该存什么？
该存的是「跨会话仍然成立且能改变后续决策」的信息：用户稳定偏好（语言、口味、常用地址）、已确认的事实型结论、成功解法的经验条目、历史失败的教训。不该存的是易变状态（当前购物车、临时会话变量）、可随时查到的权威数据（订单状态应实时查库而不是记在记忆里）、以及敏感个人信息（除非有明确合规依据与加密方案）。不做这个区分的典型事故是：Agent 把三个月前记下的「用户地址」当成当前地址下单，而真实地址早已变更——权威数据必须实时查，记忆只存偏好和经验。
怎么判断上下文出问题了？有哪些可观测信号？
四个信号非常有指示性：一是每请求 Token 的 p99 异常，突增通常意味着某个工具返回体失控；二是轮次分布右偏，正常任务 3~5 轮完成，如果大量任务跑到步数上限，说明模型判断不出完成或在绕路；三是重复动作率，同一 Action+参数在一次任务里出现两次以上，是卡死的前兆；四是目标一致性抽检，用一个小模型定期比对「最终输出」与「原始目标」，不一致率上升就说明上下文被污染或目标被截断丢弃。这四个指标应该和延迟、成功率一起进监控面板。

五、多 Agent 协作

单 Agent 也能干活，为什么还要上多 Agent？
单 Agent 的核心痛点是注意力漂移 —— 处理跨领域极度复杂的长任务时，如果背负过多工具与指令，极易发生推理链断裂。多 Agent 的核心价值是专注与分工 —— 让每个 Agent 只盯自己那一亩三分地（如编码 Agent、审查 Agent、测试 Agent），提高容错率与领域专业度。但注意：约 80% 的场景只需要单 Agent（含 Producer-Critic 自审），不需要上多 Agent。只有当工具数量超过 15 个、或任务明显跨多个独立领域时，才值得付出协作成本。
多 Agent 常见的协作模式有哪些？
三种主流模式：中心化策略（高可控） —— 主控 Agent 如同大脑，负责任务拆解，分别派发给底层各个 Worker 子 Agent，执行后由中心汇总，适合需要强一致性的场景；流水线串联（强依赖） —— 上一个 Agent 的输出严丝合缝作为下一个的输入，常用于「构建 → 审查 → 修复」工程流；民主协作探讨（重策略） —— 多个 Agent 根据各自系统身份进行圆桌讨论后得出共识，仅在线上策略分析场景偶有使用。选择依据：一致性需求选中心化、流程依赖选流水线、决策质量选民主协作。
多 Agent 的成本和延迟是怎么涨上去的？
涨的不只是「Agent 个数倍数」，而是叠加了通信开销。三个来源：一是每个子 Agent 都要一份自己的 System Prompt 和工具清单，固定开销按 Agent 数量线性叠加；二是主控与子 Agent 之间的任务描述、结果回传都是 Token，且回传内容往往还要被主控重新阅读一遍；三是子 Agent 内部各自跑 ReAct 循环，轮次乘以 Agent 数。实测量级上，一个三 Agent 流水线相对等价单 Agent 常见是 2.5~4 倍 Token、1.5~3 倍墙钟延迟（可并行的部分能压回来一些）。这也是「先用单 Agent 打到能力上限再考虑拆分」的原因。
子 Agent 之间怎么传递信息才不失真？
最容易踩的坑是拿自然语言当接口——上游 Agent 写一段散文，下游 Agent 各自理解，误差逐级放大。正确做法是给 Agent 间通信定义结构化契约：用 JSON Schema 规定字段、必填项、枚举值，附带 status 与 errors 字段区分成功失败，并让接收方在消费前做 Schema 校验，校验失败直接打回而不是猜测。此外要传「结论 + 依据句柄」而不是传原始长文：把大块中间产物落到共享存储，消息里只带引用和摘要，既省 Token 又避免层层转述丢细节。

六、失败模式与防护

多智能体系怎么防无限循环和通信爆炸？
三道防线：熔断阈值（物理级） —— 硬编码配置 Max Iterations 重试次数阈值，触发后强制抛出中止异常；状态机制（逻辑级） —— 为每次流转定义极其清晰的工作完成判断函数（Exit Condition），不达标不换阶段；摘要瘦身（内容级） —— Agent 网络互发消息强制经过 Token 级别语义总结，屏蔽闲聊，传输纯净 Payload。核心思想：从物理限制到逻辑判断到内容压缩，三层防线确保循环有终点、通信有边界。
目标漂移是怎么发生的？怎么防？
目标漂移是长任务里最隐蔽的故障：跑到第 8 轮时，模型交付的东西已经不是用户最初要的了。三个诱因叠加造成——滑动窗口把开头的目标声明裁掉了；中间某个 Observation 里出现了新的诱人线索，模型顺着追下去；反思环节把目标改写成了模型自己更容易完成的版本。防护也对应三条：把原始目标固定在上下文的不可压缩区，每轮都在场；每 K 轮做一次显式的目标对齐检查（把原目标和当前计划一起问模型「还在做同一件事吗」）；反思只允许改方法不允许改目标，目标字段设为只读。
Agent 上线前必须补齐哪些护栏？
六项一个都不能少，缺任何一项都会在生产上变成事故：步数与预算上限（防成本失控）、工具名白名单校验（防幻觉工具调用）、幂等键 + 分级重试（防重复副作用）、高危操作人工审批（删数据、转账、发外部通知必须停下等人）、全链路 Trace（每轮的 Thought / Action / Observation 都要可回放，否则线上问题无法定位）、降级兜底链（模型失败 → 规则兜底 → 转人工，任何一层都要有用户可感知的合理反馈）。这六项是工程护栏而不是模型能力，靠换更强的模型解决不了。
示例场景：一个内部运维 Agent 上线首周烧掉了预期三个月的 Token 预算。复盘发现两个叠加原因：日志查询工具单次返回约 40 万字符未做截断，单轮就吃掉 100K Token；同时没有重复动作检测，模型对同一台机器连续查了 9 次同样的日志。加上「工具返回硬截断到 4K + 连续 3 次重复动作即终止」两条护栏后，单任务平均 Token 从 118K 降到 9.6K，降幅约 92%，任务成功率反而从 74% 升到 88%——因为上下文不再被垃圾数据淹没。

答题策略 Do / Don't

  • 先给判据再给方案：「路径能不能穷举」比罗列框架名更能体现判断力
  • 主动报代价：Agent 比 Workflow 贵几倍、多 Agent 再贵几倍，带数字说
  • 把护栏说成工程问题：步数上限、幂等、白名单、Trace，都不靠换模型解决
  • 承认八成场景不需要多 Agent，这是加分项而不是减分项
  • 每个失败模式都配一个可观测信号（重复动作率、轮次分布、Token p99）
  • 只背框架名词：说完 LangGraph / AutoGen 就答不出它们解决了什么问题
  • 把「更自主」当成「更好」，忽略可预测性和审计需求
  • 一上来就上多 Agent，暴露没算过 Token 和延迟账
  • 用自然语言当 Agent 间接口，还说「模型自己能理解」
  • 把权威数据（订单、余额）存进长期记忆当缓存用
