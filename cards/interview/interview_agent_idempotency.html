IA-17 · Agent 幂等性设计

提问：AI Agent 为什么更需要幂等性？

核心观点

核心结论：Agent 幂等性的本质是“允许重复执行，但只允许一次有效副作用”。它不是接口层的小技巧，而是工作流级可靠性能力。

为什么 Agent 比普通接口更需要幂等

字幕强调，Agent 天生运行在会重试、会恢复、会超时、会重复投递的环境里。一次调用失败，并不代表外部副作用没发生；如果没有幂等保护，系统就会出现重复扣费、重复发消息、重复写库等问题。

  • 模型输出不稳定，容易多次触发相同操作
  • 外部系统可能执行成功，但回包失败，导致上层再次重试
  • 长链路任务中局部成功、局部失败很常见，没有幂等就无法安全恢复

三层幂等设计

层级目标典型手段
请求层阻止入口重复执行Idempotency Key、Request ID、去重表、唯一约束
工具层限制外部副作用只生效一次幂等接口、唯一业务键、外部系统幂等令牌
流程层支持长链路恢复与补偿状态机、Checkpoint、补偿机制、重试策略

真正高分的回答，不能只停在“入口加唯一键”。入口层只解决“不要重复开始”，流程层才决定“已经跑了一半怎么接着跑”。

常见的落地例子

视频里用“订票超时重试”来说明这个问题：如果票已经锁住，但回包超时，上层再次重试时必须能够识别“这是同一次业务请求”，否则就会出现重复锁票甚至重复扣费。

高频问答

Q1: 幂等性的标准定义应该怎么说？

可以直接说三点：重复执行、结果一致、副作用只生效一次。对 Agent 来说，重点在第三点，因为它经常会和支付、通知、工单、数据库写入等外部系统交互。

Q2: 为什么 Agent 场景下幂等比普通接口更重要？

因为 Agent 天生有重试、恢复和长链路特性。一次任务可能跨多个工具、多个服务，任何一步网络抖动都可能让系统误以为没成功，于是再次执行同一副作用。

Q3: 只靠 Request ID 就够了吗？

不够。Request ID 只能防入口重复，真正安全的方案还要让工具层和流程层也能识别重复执行。否则入口幂等了，链路中间的副作用仍可能重复发生。

Q4: 幂等和 Exactly Once 是一回事吗？

不是。Exactly Once 是系统语义目标，现实里很多系统更接近 At Least Once。幂等设计的价值，就是让 At Least Once 的重试语义尽量在业务效果上接近 Exactly Once。
