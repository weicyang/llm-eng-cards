一、AI 系统设计框架

AI 系统设计通常要求在 30-45 分钟内设计一个完整的 AI 应用系统。推荐用以下框架组织回答：

AI 系统设计回答框架 (45 分钟): Phase 1: 需求澄清 (5 min) ├── 用户规模 / QPS / 延迟要求 ├── 输入输出格式 ├── 质量要求 (准确率 / 召回率) └── 非功能需求 (成本、安全、可扩展) Phase 2: 高层架构 (10 min) ├── 核心组件划分 ├── 数据流向 ├── 技术选型 (模型、向量库、缓存) └── 部署架构 Phase 3: 深入关键模块 (20 min) ├── 检索/推理核心链路 ├── 质量控制 (防幻觉、Guardrails) ├── 性能优化 (缓存、模型路由) └── 安全设计 (输入过滤、权限控制) Phase 4: 扩展讨论 (10 min) ├── 监控与可观测性 ├── A/B 测试与迭代策略 ├── 成本控制 └── 扩展性 (如何从 1K → 1M 用户)

二、设计题：智能客服系统

请设计一个企业级智能客服系统，支持多轮对话、工单分类和知识库问答。

需求分析：①多轮对话——保持上下文连贯性；②意图识别——自动分类用户问题（咨询/投诉/退款等）；③知识库问答——RAG 检索企业知识库；④工单自动创建——结构化提取信息创建工单；⑤人机协作——复杂问题自动转人工。 架构设计：

  • 接入层——WebSocket 长连接，支持多端（Web/App/微信）
  • 对话管理层——会话状态机 + 短期记忆（Redis 存储最近 N 轮对话）
  • 意图路由——轻量级分类器先判断意图类型，路由到不同处理链路：简单FAQ→RAG、复杂问题→Agent、投诉→工单系统
  • RAG 链路——Query Rewrite → 混合检索（BM25 + Dense）→ Reranking → LLM 生成
  • 工单系统——LLM 提取结构化信息（类别/优先级/摘要）→ JSON Schema 校验 → 写入工单系统
  • 安全层——输入过滤（Prompt 注入检测）→ 输出过滤（PII 脱敏）→ Guardrails
  • 降级策略——LLM 超时/失败 → 规则引擎兜底 → 转人工
关键设计决策：
  • 模型路由：简单 FAQ 用小模型，复杂推理用大模型，降低成本 50-80%
  • 输出稳定性：工单分类必须 JSON Schema + 枚举值约束，校验失败重试 2 次后转人工
  • 延迟控制：RAG 链路 P95 < 3s，缓存高频问答结果（命中率 ~30%）

三、设计题：企业文档问答系统

请设计一个支持 100 万文档的企业知识库问答系统。

核心挑战：①文档量大（100 万文档 × 平均 10 chunks = 1000 万向量）；②权限隔离（不同部门/角色看到不同文档）；③实时更新（文档变更需及时反映到检索结果中）。 架构设计：

  • 文档处理 Pipeline——文档上传 → 格式解析（PDF/Word/HTML）→ 智能分块（语义分块 + 结构化分块）→ Embedding → 向量入库
  • 向量存储——Milvus/Qdrant 集群，支持 1000 万级向量的 ANN 检索，每个向量附带权限元数据
  • 检索层——混合检索（BM25 + Dense）→ Reranking（Cross-Encoder）→ 权限过滤（Pre-filtering 按用户角色过滤）
  • Query 处理——Query Rewrite（多路扩展）→ 意图分类 → 选择检索策略
  • 生成层——检索结果 + 用户问题 → LLM 生成回答 + Citation（标注来源）
  • 实时更新——文档变更事件 → 增量更新向量索引（不重建全量）
权限设计：
  • 文档安全分级（L0 公开 → L3 绝密）
  • Pre-filtering：向量检索时 metadata filter 按权限过滤，必须前置——否则 Top-K 名额被无权限文档占满，答案质量断崖下跌
  • Post-filtering：检索结果二次权限校验，只作兜底不作主防线
  • L3 文档使用独立索引（物理隔离）
性能指标：
  • 检索延迟 P95 < 200ms（1000 万向量）
  • 端到端回答延迟 P95 < 5s
  • 文档更新延迟 < 5min（增量更新）

四、设计题：AI 代码助手

请设计一个企业级 AI 代码助手，支持代码补全、代码审查和代码生成。

核心功能：①代码补全（实时，延迟 < 500ms）；②代码审查（PR 级别，分析代码质量和安全问题）；③代码生成（根据自然语言描述生成代码）。 架构设计：

  • 补全引擎——本地部署的代码模型（如 StarCoder/CodeLlama）→ KV Cache 优化 → Speculative Decoding 加速。关键：补全必须低延迟（< 500ms），使用 Speculative Decoding（小模型草稿 + 大模型验证）可加速 2-3x
  • 上下文构建——当前文件 + 相关文件 + 最近编辑历史 → FIM (Fill-in-the-Middle) 格式。上下文窗口有限，需要智能选择最相关的上下文（基于文件依赖图 + 最近修改）
  • 代码审查——PR diff → 分块分析 → LLM 审查（安全漏洞、性能问题、代码风格）→ 结构化输出（JSON 格式的审查意见）→ 发布到 PR 评论
  • 代码生成——自然语言描述 → 代码生成 → 自动测试生成 → 沙箱执行验证 → 输出代码 + 测试结果
  • 安全——代码不能发送到外部 API（本地部署）→ 生成代码需通过安全扫描（SAST）→ 不生成包含硬编码密钥的代码
关键设计决策：
  • 补全用本地小模型（低延迟），复杂生成用云端大模型（高质量）
  • KV Cache 管理：按文件/项目缓存，LRU 淘汰策略
  • 代码审查的输出必须结构化（JSON Schema），方便集成到 CI/CD 流水线

五、设计题：企业级 Agent 系统

请设计一个企业级 Agent 系统（如智能客服 Agent、业务办理 Agent）。

五层架构必须覆盖（画出来就是加分项）：

┌─────────────┐ │ 接入层 │ ← 多渠道（网页/APP/公众号/企微） ├─────────────┤ │ 对话管理层 │ ← 上下文管理、多轮状态跟踪 ├─────────────┤ │ Agent 核心层 │ ← 规划、工具调用、反思、记忆 ├─────────────┤ │ 工具层 │ ← 知识库 RAG / 工单 API / 用户查询 / 物流 ├─────────────┤ │ 输出管控层 │ ← 敏感词过滤、内容审核、话术规范 └─────────────┘

追问必答五点：

  1. 工具管理——MCP 标准化接入 + 权限分级（只读 / 写入 / 高危操作分层授权）
  2. 记忆设计——Redis 存短期会话状态，向量 DB 存长期用户偏好与历史经验
  3. 可靠性——工具调用与整体任务双层超时 + 熔断 + 高危操作人工审批
  4. 可观测性——全链路 Trace + Token 成本监控（详见本卡第七节）
  5. 安全——Prompt Injection 纵深防御 + 最小权限原则 + 输出数据脱敏

六、通用设计要点总结

核心评估维度

维度考察点加分项
架构完整性端到端链路是否完整考虑异常路径和降级策略
技术选型为什么选这个技术而不是另一个展示权衡分析能力
质量控制如何保证输出质量防幻觉 + Guardrails + A/B 测试
性能优化延迟/成本/吞吐量缓存 + 模型路由 + 异步处理
安全设计输入/输出安全Prompt 注入防御 + PII 脱敏 + 权限控制
可扩展性从 1K → 1M 用户的扩展方案水平扩展 + 分层缓存 + 异步处理
可观测性如何监控系统健康指标/日志/追踪三件套 + 告警

常见的追问方向

  • 成本控制："如果 QPS 从 100 增加到 10000，成本如何变化？"
  • 故障处理："如果 LLM 服务挂了，系统如何降级？"
  • 数据一致性："知识库更新后，多久能反映到检索结果中？"
  • 冷启动："新产品线没有历史数据，如何冷启动？"
  • A/B 测试："如何验证新模型/新策略的效果？"
系统设计的核心不是给出"正确答案"，而是展示结构化思维和权衡分析能力。关键是要能清晰地拆解问题、分析约束、提出方案、讨论权衡。

七、Agent 生产工程：可靠性 / 成本 / 可观测性 / 踩坑

生产环境 Agent 的可靠性怎么保证？

六大机制各司其职，答全了就是"做过生产系统"的信号：

机制说明
幂等性同一操作多次执行结果相同，重试无副作用
回滚重要操作前备份，失败可恢复原状态
超时每个工具调用 + 整体任务分别设最大时间
降级大模型挂了 → 规则匹配兜底 → 转人工，逐级降级
熔断器检测重复失败后自动切到备用模型，防止雪崩
Human-in-the-Loop删数据 / 发邮件 / 改权限 / 超额资金 → 暂停等人工审批

级联回退是最后一道防线：主模型（GPT-4o）→ 备用模型（Claude）→ 缓存响应 → 优雅错误消息，任何一层失败用户侧都有兜底体验。

Agent 的 Token 成本怎么优化？

五个策略按投入产出排序：

策略效果
模式选择：简单任务走 Workflow 不上 Agent省 4 倍 Token
模型路由：简单子任务用小模型节省 20-40%
语义缓存：相似查询复用历史答案节省 20-40%
上下文压缩：摘要历史对话减少输入 Token
工具按需加载：别把全量工具描述一次塞进上下文减少上下文占用

组合使用可降低 60-80% 成本。作答时先说模式选择（收益最大），再逐层往下讲，最后给组合收益数字收尾。

Agent 的可观测性怎么做？

三大支柱：追踪（Traces）、日志（Logs）、指标（Metrics）。告警阈值要有具体数字：

指标告警阈值
请求延迟 p95> 30s
每请求 Tokenp99 > 10,000
每请求成本p99 > $0.50
工具成功率< 95%
LLM 错误率> 2%

采样策略：错误请求和昂贵请求 100% 追踪，正常请求 10% 采样，兼顾排查能力与存储成本。工具选型：LangChain 生态用 LangSmith，开源选 Langfuse，企业级选 Datadog LLM Observability。

生产踩过什么坑？（六大坑与解法，常被连环追问）

这题考的是真实经验，六个坑配六个解法一次说全：

坑解法
死循环最大步数 + 重复动作检测
幻觉工具调用（调不存在的工具）严格校验工具名白名单
上下文污染合理截断 + 任务重置
Token 爆炸（工具返回超大数据）输出截断 + 分页
Prompt Injection数据/指令分离等纵深防御
目标漂移（越跑越偏）每步目标对齐 + 定期反思 + 重新规划
示例场景：某客服系统从 100 QPS 扩到 3000 QPS，成本没有按 30 倍增长，而是只涨了约 6 倍。三处结构性优化贡献了差额——意图分类把 34% 的请求分流到语义缓存直接返回；模型路由把 58% 的请求交给小模型，单价约为大模型的十五分之一；稳定前缀走 Prompt Caching 后输入部分按缓存价计费。同时 P95 从 4.1 秒降到 1.6 秒，因为缓存和小模型这两条路本身就比主链路快。这类题的加分点正是能说清「成本不随 QPS 线性增长」的机制。

答题策略 Do / Don't

  • 先澄清需求再画架构：QPS、延迟预算、质量门槛、合规约束，四问缺一不可
  • 按「接入 → 编排 → 模型与数据 → 管控 → 观测」五层报菜名，再深入一层
  • 主动给异常路径：LLM 挂了怎么降级、检索为空怎么拒答、超时怎么兜底
  • 每个选型都给替代方案与切换条件（「数据量到千万级我会从 pgvector 迁到 Milvus」）
  • 报可验证的数字：检索 P95、端到端 P95、缓存命中率、单请求成本
  • 不问约束直接开画，做出一个没人需要的系统
  • 只画正常路径，对故障、降级、回滚一字不提
  • 把技术栈罗列当架构设计，说不出组件之间为什么这样连
  • 忽略权限与合规，企业级题目里这是硬性扣分项
  • 假设成本随 QPS 线性增长，答不出缓存与路由带来的结构性节省
