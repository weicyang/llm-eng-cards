IR-09 · 结构化数据 (SQL/表格) 查询难题

核心问题

在RAG系统中，结构化数据（SQL或表格）查询的难题怎么解决？

关键认知：向量检索无法做数学运算（聚合、排序、精确匹配），这种需求必须走结构化查询。

大模型直接写SQL的三大坑

  1. 表太多：公司可能有几百上千张表，全塞进prompt模型CPU过载、幻觉满天飞
  2. 业务逻辑猜不透：什么叫"活跃用户"？登录过就算还是下单才算？
  3. SQL语法写不对：字段名错误、函数不对

EAG-RAG 混合架构

1. 智能路由（第一站）

让大模型先判断问题类型：

  • 查手册文档（非结构化）→ 向量库搜文档
  • 查报表数据库（结构化）→ 结构化流算销量
  • 混合意图 → 拆开处理，最后合并

双轨制：专业玩家的标配

2. Schema RAG（精简上下文）

把所有表的表名、字段名和中文注释做成向量存起来：

  • 模型写SQL前，先搜一下跟问题相关的表是哪几张
  • 只把那3~5张最相关的表结构传进去

效果：精简上下文，避免模型被几百张表搞晕

3. Few-Shot 示例检索

把之前写的对的高手写过的SQL例子存成库：

  • 模型写SQL前先参考一下类似的例子
  • 准确率从60%拉到90%以上

4. Agent闭环（自我进化）

大模型第一次生成的SQL万一报错了：

  • SQL先在沙盒环境里跑一下
  • 如果报错，把报错信息+写错的SQL一起丢回给大模型
  • 告诉它"兄弟字段名写错了或者函数不对，你再改改"
  • 模型自己纠错，直到跑通为止

自我进化能力：解决SQL语法幻觉的终极武器

5. 安全防护

万一模型写了DROP TABLE把数据库删了怎么办？

  • 只读权限：给大模型的账号必须是严格的READ ONLY
  • 拦截层：SQL真正执行前，用AST解析或正则校验，发现修改/删除操作直接毙掉

高频考点

解决结构化数据查询不是靠一个超级prompt，而是靠一套意图路由 + 工具调用 + 容错重试的流程式智能体架构。
