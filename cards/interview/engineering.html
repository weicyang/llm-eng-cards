一、Prompt Engineering

Chain-of-Thought (CoT) 和 Tree-of-Thought (ToT) 有什么区别？

CoT：让模型在回答前展示推理过程（"Let's think step by step"），单条线性推理链。适用于数学题、逻辑推理等需要逐步推导的场景。ToT：将推理过程展开为树状结构，探索多条推理路径并评估每条路径的可行性，选择最优路径。适用于需要创造性探索的问题（如写作、策略规划）。核心区别：CoT 是一条路走到黑，ToT 是同时探索多条路并回溯。实际生产中 CoT 更常用（成本低、效果好），ToT 适合对质量要求极高的场景——它的代价是 Token 消耗随分支数与深度指数级增长。

Self-Consistency 是什么？它解决了 CoT 的什么问题？

Self-Consistency（自一致性）解决 CoT 单次推理可能出错的问题。方法：让模型对同一问题用 temperature>0 生成多个不同的 CoT 推理路径，然后对最终答案投票，选出现次数最多的答案。例如 5 次推理得出 3 次答案 A、2 次答案 B，则选 A。效果：在数学和推理任务上比单次 CoT 提升 5~15% 准确率。代价：推理成本 ×N（N 为采样次数）。实践中通常 N=5~10，在成本和准确率之间权衡；它只适用于「答案可归一化比较」的任务，开放式生成没法投票。

System Prompt 设计有哪些最佳实践？

核心原则：①角色定义——明确模型的角色和能力边界（"你是一个专业的客服助手，只回答产品相关问题"）；②结构化输出要求——用 JSON Schema 或明确的格式模板；③安全边界——明确拒绝策略（"如果用户要求做 X，请礼貌拒绝"）；④Few-shot 示例——给出 2~3 个输入输出示例；⑤分隔符——用 XML 标签或 Markdown 分隔不同指令区块，减少指令混淆。常见错误：System Prompt 过长导致关键指令被忽略（Lost in the Middle 问题）；缺少安全边界导致模型被越狱。

Few-shot 示例该给几个、怎么挑？

数量上 2~5 个通常就到收益拐点，再加只是烧 Token；示例的多样性比数量重要得多。挑选三原则：一是覆盖决策边界，正例反例都要有，尤其要包含「应该拒答」和「参数缺失需追问」这类容易被漏掉的分支；二是格式必须与期望输出逐字一致，模型对格式的模仿远强于对指令的服从，示例里出现的任何不一致都会被复制；三是动态 Few-shot 优先——按当前输入检索最相似的历史标注样例注入，效果通常明显好于固定示例，代价是要维护一个样例库并多一次检索。要避免的坑是示例分布偏斜：如果 3 个示例都是「同意」，模型在边界情况下也会倾向同意。

Prompt 改动怎么管理，才不会改一处坏一处？

把 Prompt 当代码管，而不是当配置里的字符串。四条工程纪律：版本化——Prompt 进 Git，改动走 Code Review，线上运行的版本号要能从日志里查到；模板化——用变量槽位而不是字符串拼接，用户输入永远只能进入预定义槽位，既防注入也防格式错乱；回归化——每个 Prompt 绑定一组固定测试样例，改完必跑，通过率下降即阻断；可回滚——Prompt 版本切换不依赖重新发版，出问题一分钟内能切回。缺了回归这一环最常见的事故是：为修一个 Bad Case 加了一句约束，结果把另外三类正常请求带崩，而没人发现。

二、上下文管理

什么是 Lost in the Middle？怎么应对？

指模型对长上下文中开头和结尾的信息利用得好，对中间位置的信息明显更容易忽略，呈 U 形性能曲线。它的直接后果是：把 20 段检索结果一起塞进去，真正的答案如果排在第 10 段，模型可能视而不见。四个应对手段：一是少而精，用 Rerank 把候选压到 3~5 条，从根上避免中间区；二是关键信息放两端，把任务指令和最相关片段分别置于开头与结尾；三是结构化标注，给每段加编号与来源标签并要求引用，逼模型逐段过一遍；四是分而治之，长文档先分段抽取再汇总，而不是一次性硬读。

上下文窗口越大，是不是就不用管上下文了？

恰恰相反，窗口越大越需要治理。三个理由：成本线性增长——输入 Token 按量计费，把 200K 窗口填满意味着每次请求都付满额，而其中多数内容与本次问题无关；延迟随输入增长——首字延迟与输入长度正相关，长输入直接伤体验；注意力被稀释——有效信息占比越低，模型越容易抓错重点，实测很多任务在上下文从 8K 加到 64K 后准确率反而下降。所以正确的心态是「上下文是稀缺资源」：每一段进入上下文的内容都要能回答「它凭什么占这个位置」，宁可少放而放对。

多轮对话的历史该怎么裁剪？

分区治理，不要一刀切。把上下文划成三块：不可压缩区放 System Prompt、任务目标、输出格式要求，任何情况下都保留；滚动区放最近 N 轮原文，超阈值后最老的几轮进入摘要；状态区放一份结构化 JSON，记录已确认的事实（用户身份、已选商品、已给出的承诺），这部分不随轮次丢失。这样设计的原因是：纯滑动窗口会把开头的任务目标裁掉，导致跑偏；纯摘要会丢失精确的数字和 ID。涉及金额、单号、日期的字段一律走状态区结构化留痕，绝不依赖摘要复述。

三、防幻觉策略

LLM 幻觉的主要类型和成因是什么？

三大类型：①事实性幻觉——编造不存在的事实（如虚构的论文、错误的数据）；②忠实性幻觉——生成的内容与输入 / 上下文不一致（如摘要中添加原文没有的信息）；③逻辑幻觉——推理过程看似合理但结论错误。成因：①训练数据中的噪声和偏差；②模型的取悦倾向（sycophancy）——倾向生成用户期望的回答而非事实；③知识截止——模型不知道最新信息但仍会自信地回答；④概率采样的固有不确定性。理解成因的价值在于：前两类靠外挂知识和约束能大幅压制，第三类必须靠外部校验，不存在靠 Prompt 消除幻觉的方案。

如何在生产系统中有效防止幻觉？

多层防御：①RAG 增强——检索外部知识库作为参考依据，让模型基于事实回答而非纯记忆；②Citation 机制——要求模型标注信息来源，无法找到来源时明确说「我不知道」；③Self-Check——让模型在回答后自我检查「以上信息是否有依据」；④Guardrails 框架——用 NeMo Guardrails 或 Guardrails AI 对输出做事实校验；⑤多模型交叉验证——用不同模型回答同一问题，结果一致则可信度高。最有效的是 RAG + Citation 组合——模型基于检索到的真实文档回答，并标注来源让用户可验证。

怎么让模型「体面地说不知道」？

默认情况下模型倾向于给答案而不是拒答，所以拒答必须被显式设计出来。四件事：一是Prompt 里给拒答话术模板并声明拒答是合格输出，不写模板模型就会硬编；二是加检索质量门控，Rerank 最高分低于阈值直接走拒答分支，不让模型在低质上下文上硬撑，阈值靠「答案在库 / 不在库」两组测试集的分数分布找切点；三是Few-shot 里必须包含拒答样例，否则示例全是正面回答，模型学到的就是「总要答」；四是把拒答率纳入监控，过低说明门控没生效，过高说明知识库有缺口，这个指标是知识库运营的重要输入。

防线手段拦住哪类幻觉代价

示例场景：某政策问答系统上线初期投诉集中在「答得很像但条款是编的」。加了两道最便宜的防线后问题基本消失——Prompt 强制逐条标注条款编号，检索最高分低于 0.42 直接返回拒答话术。有据回答率从 78% 升到 97%，拒答率从 0.4% 升到 6.1%，用户满意度反而提升，因为「明确说查不到」比「编一条像样的」可信得多。

四、Token 成本优化

LLM 应用中如何优化 Token 成本？

五个层面：①Prompt 压缩——去除冗余指令、用缩写替代长描述、用 Few-shot 代替冗长的规则描述；②模型路由——简单问题用小模型，复杂问题才用大模型，降低平均成本 50~80%；③缓存——语义缓存对相似 query 返回缓存结果，命中率可达 20~40%；④工具返回结果过滤——工具返回的原始数据（如大段 JSON）可能很长，用摘要或关键字段提取后再注入上下文；⑤Batch API——非实时场景使用批处理接口，成本通常降低约 50%。关键指标是两个：cost per request（每次请求成本）和 cost per useful answer（每次有效回答的成本），后者才是真正该优化的目标。

什么是 Semantic Cache？和传统缓存有什么区别？

传统缓存（Exact Match Cache）精确匹配 key，「如何报销」和「怎么报销」是不同的 key，无法命中。Semantic Cache 用 Embedding 相似度匹配——两句话的向量相似度高，可以命中同一条缓存。实现路径：query 向量化 → 在缓存向量库中搜索 → 相似度超阈值 → 返回缓存结果。关键参数是相似度阈值：太高则命中率低，太低则可能返回不相关的缓存结果。命中率通常 20~40%，可将 LLM 调用成本同比例降低。必须加的两条约束：只对无副作用的只读请求启用；把用户身份与权限组纳入缓存 key，避免跨用户串答。

Prompt Caching 和 Semantic Cache 是一回事吗？

完全不同的两种机制，面试里混为一谈是常见失分点。Prompt Caching 缓存的是模型侧的前缀计算结果：把 System Prompt、工具 Schema、Few-shot 这些逐轮不变的长前缀标记为可缓存，命中后这部分按远低于原价的缓存读取价计费，输出仍然是每次真实生成的，所以答案质量不受影响。Semantic Cache 缓存的是完整的问答对：命中后直接跳过模型调用返回历史答案，省掉全部推理成本和延迟，但存在返回过时或不匹配答案的风险。两者可以叠加：先查语义缓存，未命中再走模型调用并吃 Prompt Cache 的折扣。

五、结构化输出与稳定性

如何保证大模型输出的稳定性和可靠性？

三层防御体系：①输入预处理——关键字段前置提取（正则 / 规则），减轻模型注意力漂移；②模型推理层——JSON Schema 约束 + 严格枚举值 + 低温度（T=0~0.3）+ RAG 知识增强；③输出后处理——多层校验（JSON 解析 → Schema → 值域 → 逻辑一致性）+ 重试（最多 2 次）+ 降级兜底（转人工 / 规则兜底 / 默认安全值）。核心思维转变：从「驯服模型」到「管理模型」——把模型当成需要严格管理的同事，而不是可以完全信任的函数。实战教训：未限定枚举值导致模型输出「十万火急」作为 priority 值，下游枚举转换直接抛异常。

结构化输出有哪些实现方式？

三种主流方式：①JSON Mode——模型内置的 JSON 输出模式（如 response_format），保证输出是合法 JSON 但不保证符合特定 Schema；②Function Calling / Tool Use——通过定义工具的参数 Schema 来约束输出，模型按 Schema 生成结构化参数；③Constrained Decoding（约束解码）——在 token 采样阶段就屏蔽掉会破坏 Schema 的候选（如 Outlines、llama.cpp 的 grammar），100% 保证格式正确但可能影响生成质量，且需要能干预解码过程即通常要自部署。推荐方案：生产环境优先用 Function Calling（灵活且可靠），对格式要求极严格的场景用 Constrained Decoding。

降级兜底策略如何设计？

完整链路：JSON 解析失败 → 重试（最多 2 次，退避延迟）→ Schema 校验失败 → 带修正提示重试 → 重试耗尽 → 判断优先级：高优先级转人工，低优先级走规则引擎兜底 → 仍失败则返回默认安全值。关键原则：永远不要假设模型输出 100% 正确。监控指标：Schema 校验通过率（低于 95% 告警）、重试率（高于 10% 告警）、降级率（高于 5% 告警）。实战教训有两条——无兜底时模型的异常 JSON 会直接把下游服务打崩；无监控时错误率会悄悄上升好几周没人发现。

重试为什么必须「带错误信息」重试？

因为同样的输入重试一遍，模型很可能给出同样的错误——温度低时几乎必然如此，重试就纯粹是浪费成本和延迟。正确做法是把校验器的具体报错回灌给模型：「字段 priority 的值 '十万火急' 不在允许枚举 [P0,P1,P2,P3] 中，请修正后重新输出完整 JSON」。这类带反馈的重试一次成功率通常远高于盲目重试。三条细节：错误信息要具体到字段和原因，不要只说「格式错误」；要求重新输出完整对象而不是补丁，避免拼接出错；重试上限设 2 次并且每次都记录，重试率本身就是一个质量指标——它上升说明 Prompt 或 Schema 该改了。

六、可观测性与评测

LLM 应用的可观测性和传统服务有什么不一样？

传统服务的可观测性关心「是否可用」，LLM 应用还必须关心「是否有用」，多出三类数据。第一类是成本维度：每请求输入 / 输出 Token、单价、成本，要看 P99 而不只是均值，因为长尾请求能贵出两个数量级。第二类是质量维度：Schema 校验通过率、拒答率、引用命中率、用户点踩率，这些指标在传统监控里根本不存在。第三类是可回放的 Trace：完整记录最终拼装出的 Prompt、模型版本、参数、原始返回，否则线上出现一个坏答案时你连复现都做不到——这是 LLM 排障与传统排障最大的差别。

Prompt 和模型版本怎么和线上问题对得上？

靠三个 ID 贯穿全链路。请求 ID 关联一次用户交互的所有调用；Prompt 版本号 记录本次使用的模板版本（含变量填充后的哈希），这样能区分「模板变了」和「输入变了」；模型标识 记录具体模型名与快照版本，因为厂商会静默更新同名模型，不记快照版本就会出现「什么都没改但效果变了」这种无从下手的问题。三个 ID 都要落到日志和 Trace 里，并在质量指标上支持按维度下钻——能一眼看出「点踩集中在 Prompt v7 + 小模型路由」这样的组合，归因效率完全不同。

离线评测集该怎么建、怎么维护？

分两类建。回归集 100~300 条，覆盖主流程与所有已修复的 Bad Case，每次 Prompt 或模型变更必跑，目标是「不许变差」，通过率下降即阻断发布。能力集 按维度分层（抽取 / 分类 / 改写 / 拒答 / 边界），每类 30~50 条，用于横向对比模型与策略。维护上有三条纪律：评测集与代码同仓同版本管理；每个 Bad Case 修复后立刻回填成新样例，这是评测集保值的唯一途径；每条样例必须带明确的期望结果和判分方式，否则自动化跑不起来，最终又退化成人工看结果。

用 LLM 当裁判打分，怎么防止分数不可信？

防三个偏差、加一道校准。位置偏差：对比两个答案时模型偏好靠前的，做法是交换顺序各评一次取平均。长度偏差：偏好更长的答案，做法是在评分标准里显式声明不因长度加分。自偏好：偏好同家族模型的输出，做法是裁判与被评模型跨厂商。校准是指用 50~100 条人工标注样例定期核对裁判与人工的一致率，低于约 80% 说明评分标准写得不够明确，要把标准细化成可勾选的检查项。另外裁判必须输出「每维度分数 + 依据」而不是一个总分，否则分数掉了你也不知道掉在哪。

答题策略 Do / Don't

  • 按「输入治理 → 上下文装配 → 模型调用 → 输出校验 → 观测留痕」五关口组织答案
  • 每个方案都配代价：Self-Consistency 贵 N 倍、生成后核查翻倍延迟，说清才可信
  • 区分容易混淆的概念对：Prompt Caching vs 语义缓存、JSON Mode vs 约束解码
  • 给出可执行阈值：温度 0~0.3、重试 2 次、校验通过率 95%、TTFT 2 秒
  • 把 Prompt 当代码讲：版本化、模板化、回归、可回滚
  • 把「加一句请根据资料回答」当成防幻觉方案
  • 认为窗口够大就不用管上下文，忽略成本、延迟与注意力稀释
  • 盲目重试：不回灌校验错误，低温度下重试基本是原样再错一遍
  • 只报平均延迟和平均成本，长尾才是真正出事的地方
  • 没有评测集就宣称「优化后效果更好」，这在生产语境里等于没有结论
