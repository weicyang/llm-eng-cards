一、分层归因与 Bad Case 运营

准确率 60% 上不去，你会怎么排查？
先做分层归因，从成本最低的层开始修复。将 Agent 分为三层：质量层（知识库 / 数据）、工程层（Prompt / 检索策略 / 工具描述）、模型层（底层 LLM）。质量层最靠近数据源，修复成本最低，往往收益最大。具体做法：人工抽取约 100 条 Bad Case，按问题场景分层采样（查询 / 操作 / 故障 / 边界），保证各类 Case 都能看到；分析完为每个 Bad Case 打标签，按「修复成本 ÷ 影响面」排优先级。不这么做的后果是直接跳到模型层，花三倍成本换来两个百分点的提升，而八成问题其实在数据和 Prompt 里。
100 条怎么抽的？这个量够吗？
不是纯随机抽取，会按问题场景分层采样，保证各类 Case 都能看到（如查询类 30 条、操作类 30 条、故障类 20 条、边界 Case 20 条）。100 条在快速诊断场景下性价比很高——与 500 条相比，归因分布的比例差不了太多，但人工分析成本只有五分之一。关键是覆盖面而不是绝对数量：如果只做随机抽样，高频场景会占掉九成样本，低频但严重的失败模式一条都抽不到，归因结论就是失真的。当某类占比接近阈值需要做决策时，再对该类单独加抽 50~100 条确认。
实际效果如何？发现了什么问题？
示例场景：某内部服务台 Agent 用这个方法处理，准确率从 63% 提升到 82%。发现的错误分布是：35% 知识库过期（修复成本最低，清理 / 更新知识库即可）、25% Prompt 缺关键约束（修复成本低，补约束与枚举值）、20% 检索模块问题（修复成本中，调整切片与召回策略）、20% 真正的模型能力问题（修复成本高，需换模型或微调）。核心洞察：约 80% 的问题不需要改模型——这也是这道题真正的考点，考的是成本意识和归因能力，不是模型知识。
那 20% 模型能力问题怎么处理？
会单独拎出这些 Case 作为评测集，对比测试不同模型，计算 ROI（准确率提升 vs 成本增加）。可以先用 CoT 模板和 Few-shot 示例榨一轮提升，通常还能拿到几个百分点；剩下约 5% 用人工兜底（模型置信度低时转人工）。决策框架很直接：如果换模型成本增加 3 倍但准确率只提升 2 个百分点，不如用人工兜底加持续优化知识库。只有当某类 Case 的业务价值高且模型层是唯一瓶颈时，换模型或微调才划算。
如何保证优化后效果不回退？
建立闭环迭代机制：优化后再抽 100 条新 Bad Case，检查归因分布的变化。如果某类错误比例上升，说明引入了新问题，需要回退排查。同时持续补充新出现的 Case 类型，动态更新 Prompt 和检索策略。要监控三件事：归因分布变化（知识库类错误是否反弹）、新增 Case 类型（是否出现新的失败模式）、端到端准确率趋势（周级别跟踪）。核心思想：Agent 调优不是一次性工程，而是持续迭代的闭环系统。

二、Token 成本优化

Agent 的 Token 到底花在哪了？
拆开看四块，比例常常和直觉相反。第一块是固定开销 × 轮次：System Prompt 加全量工具 Schema 每轮都要重传，10 个工具约 2~3K Token，跑 6 轮就是 18K，这往往是最大的一块。第二块是历史累积：前面每轮的 Thought / Action / Observation 都在上下文里，呈三角形累积。第三块是工具返回体，未截断的数据库查询或日志能单条吃掉几万 Token。第四块才是模型输出，通常占比最小但单价最高（输出价常是输入价的 3~5 倍）。搞清这个分布才知道该优化哪里——多数团队一上来压 Prompt 措辞，其实收益远小于砍工具 Schema 和截断工具返回。
Agent 的 Token 成本怎么优化？
五个策略按投入产出排序：模式选择——简单任务走 Workflow 不上 Agent，直接省约 4 倍 Token，收益最大；模型路由——简单子任务用小模型，节省 20%~40%；语义缓存——相似查询复用历史答案，节省 20%~40%；上下文压缩——摘要历史对话、只保留结构化状态，减少输入 Token；工具按需加载——别把全量工具描述一次塞进上下文，按任务域路由后只注入相关工具。组合使用可降低 60%~80% 成本。作答时先说模式选择（收益最大），再逐层往下讲，最后给组合收益数字收尾。
Prompt Caching 对 Agent 特别有用，为什么？
因为 Agent 的上下文天然是「长而稳定的前缀 + 短而变化的尾部」，这正是 Prompt Caching 的最佳形态。System Prompt、工具 Schema、Few-shot 示例在整个任务里一字不变，把它们放在上下文最前面并标记为可缓存，后续每轮命中缓存的部分只按缓存读取价计费（常见是原价的 10%~25%），而缓存写入只发生一次。要吃到这个收益有两个硬要求：一是稳定前缀必须逐字节相同，所以不能在 System Prompt 里插入时间戳、随机 ID 这类每轮变化的内容；二是变化内容必须全部放在后面，一旦在前缀中间插入一个变量，后面的缓存全部失效。
语义缓存的阈值怎么定？会不会答错？
会，所以阈值和适用范围都要收着来。阈值太低会把「查订单 A」的答案返给「查订单 B」，这是真实事故；太高则命中率归零。实践做法：通用问答类取 0.85~0.90，高精度场景取 0.90~0.95，并且只对无副作用的只读查询启用缓存，任何涉及写操作、金额、个人数据的请求一律绕过。另外要把用户身份、权限组、时间窗口作为缓存 key 的一部分，否则会出现跨用户串答和过期数据被复用。建立缓存后必须监控「缓存命中且被用户点踩」的比例，这个指标是阈值是否过低的直接证据。

三、延迟优化

Agent 的延迟该怎么拆解？
先做分段 Profiling 再谈优化，否则全是猜。一次 Agent 任务的墙钟时间 = Σ(每轮 LLM 首字延迟 + 生成时间 + 工具执行时间 + 编排开销)。分段 Profiling 会得到很反直觉的结论：多数团队以为瓶颈是 LLM，实测常常是工具——一次没走索引的数据库查询能占掉总时长的一半。定位后按段处理：LLM 段压输入长度（输入越长首字延迟越高）、并行化独立工具调用、给工具加超时和缓存、减少总轮次。把「平均耗时」换成「P50 / P95 / P99 分段耗时」是这题的加分点，因为长尾才是用户投诉的来源。
轮次是延迟的乘数，怎么把轮次降下来？
四个手段。一是并行工具调用：一轮里如果需要查订单、查物流、查库存三件互不依赖的事，让模型一次输出三个 tool_call 并行执行，三轮压成一轮。二是复合工具：把常一起出现的细粒度调用在服务端封装成一个高层工具，模型少决策一次就少一轮。三是预取：任务开头就把几乎必用的上下文（用户档案、当前工单）直接注入，不让模型花一轮去查。四是明确的完成判据：很多任务其实第 3 轮就做完了，却因为没有清晰的 finish 信号又空跑两轮。
流式输出能解决延迟问题吗？
能解决感知延迟，不能解决总耗时，这个区分要说清楚。TTFT（首字延迟，Time To First Token）是用户感受到「系统卡住了」的主要来源，流式把它从「等 9 秒看到全部」变成「等 0.8 秒开始看到」，体验改善巨大。但 Agent 的中间轮次通常不能直接流给用户——Thought 和工具调用暴露给终端用户既不安全也不友好。实践做法是分层：中间轮次流式输出「进度事件」（正在查询订单…），只有最终答复走内容流式；同时把总耗时的优化交给并行化和轮次压缩，两者是互补而不是替代关系。
延迟预算应该怎么定？
按交互形态倒推，而不是按技术能力顺推。同步对话场景用户容忍上限约 TTFT 2 秒、总时长 10 秒，超了就要么流式化要么异步化；后台批处理可以放到分钟级，重点转为吞吐和成本；带进度反馈的长任务（如报告生成）能撑到几分钟，前提是每 3~5 秒必须有可见进展。定好总预算后逐段分配，例如总 8 秒 = 检索 0.6s + 模型 4 轮 × 1.4s + 工具 1.2s + 编排 0.6s，任何一段超预算就触发告警。没有预算就没有优化目标，这是延迟治理最容易被跳过的一步。
延迟段典型占比主要成因优化手段
LLM 首字延迟（TTFT）20%~35%输入过长、排队、无缓存压缩上下文、Prompt Cache、就近部署

示例场景：一个订单查询 Agent 的 P95 从 14.2 秒压到 3.9 秒，四步贡献分别是——把三次独立查询改成一轮并行 tool_call（-5.1s，收益最大）、给订单表的 user_id 加索引让慢查询从 2.4s 降到 0.11s（-2.3s）、把 12 个工具按域路由到 4 个使输入 Token 从 4.8K 降到 1.3K（-1.8s）、补一个显式 finish 工具消掉平均 1.2 轮空跑（-1.1s）。四步里只有一步和模型有关，这就是「先 Profiling 再优化」的价值。

四、稳定性与可靠性

生产环境 Agent 的可靠性靠哪些机制保证？
六大机制各司其职，缺一项都会在生产上变成事故：幂等性——同一操作多次执行结果相同，重试无副作用；回滚——重要操作前留快照，失败可恢复原状态；超时——每个工具调用与整体任务分别设最大时间；降级——大模型不可用时走规则匹配兜底再转人工，逐级下降而不是直接报错；熔断器——检测到重复失败后自动切到备用模型，防止把下游打崩；Human-in-the-Loop——删数据 / 发外部通知 / 改权限 / 超额资金操作必须暂停等人工审批。这六项都是工程护栏，换更强的模型解决不了。
Agent 输出不稳定，同样的输入结果不一样，怎么治？
先接受「概率模型天然有波动」，再用三层把波动收进可接受范围。输入层：把能用规则确定的字段先用正则或代码抽出来，别让模型做它不擅长的抄写工作。推理层：温度压到 0~0.3、输出走 JSON Schema 约束、所有分类字段给死枚举值、关键任务加 Few-shot 锚定格式。输出层：多层校验（JSON 可解析 → Schema 合规 → 值域合法 → 与输入逻辑一致），校验失败带错误信息重试最多两次，仍失败则降级。真实教训：没限定枚举值时模型会自创「十万火急」作为优先级值，下游枚举转换直接抛异常。
降级链应该怎么设计？
降级的目标不是「不报错」，而是「每一层失败用户都能拿到一个合理结果」。典型四级：主模型 → 备用模型（换厂商，防单点）→ 规则 / 检索兜底（返回最相关的知识条目或标准话术）→ 明确的人工接管入口。三条设计原则：一是降级要显式，返回结构里带 degraded: true 和降级原因，便于统计和排查；二是降级路径必须常态演练，只在故障时第一次跑的降级代码几乎一定是坏的；三是不要静默降质，如果降级后答案可靠性明显下降，要在 UI 上告知用户这是兜底回复。
Agent 的可观测性要采哪些数据？
三大支柱缺一不可：Trace 记录每一轮的 Thought / Action / 参数 / Observation，保证任何线上问题都能完整回放，这是 Agent 排障的唯一可靠手段；Metrics 覆盖成功率、轮次分布、分段延迟、每请求 Token 与成本、工具成功率、降级率；Logs 记录结构化的错误与校验失败明细。告警要带具体阈值，例如 P95 延迟超 30 秒、每请求 Token 的 P99 超 1 万、单请求成本 P99 超 0.5 美元、工具成功率低于 95%、模型错误率高于 2%。采样策略上，错误请求和昂贵请求 100% 全采，正常请求 10% 抽样，兼顾排查能力与存储成本。

五、评测体系

Agent 该怎么评测？和评测一次问答有什么不同？
单次问答只需评「答得对不对」，Agent 必须同时评结果和过程。结果层看任务完成率（端到端是否达成用户目标）、答案正确性、输出合规性。过程层看工具选择准确率、参数正确率、轮次效率（用了几轮，有没有绕路）、成本与延迟是否在预算内。只评结果的问题是：一个任务可能靠 12 轮乱试碰对了答案，指标看着漂亮但成本和稳定性都不可接受；只评过程则可能每步都规范却没解决用户问题。所以评测报告必须是「完成率 + 平均轮次 + 单任务成本 + P95 延迟」四项一起看。
评测集怎么建？多少条合适？
分三类建，用途不同。回归集：100~300 条覆盖主流程和已修复 Bad Case，每次改动必跑，目标是「不许变差」。能力集：按能力维度分层（简单查询 / 多步操作 / 需澄清 / 应拒答），用于对比模型和策略，每类 30~50 条即可看出差异。压力集：专门收集边界与对抗样例（超长输入、缺参数、诱导越权、工具故障），用于验证护栏。每条样例要带上「期望结果 + 期望路径 + 是否允许拒答」，否则自动化判分无从下手。评测集要和代码一起进版本库，Bad Case 修复后立即回填，这是它保值的关键。
用 LLM 当裁判可靠吗？怎么用才靠得住？
在有明确评分标准时相当可靠，但要防三个偏差。位置偏差——比较两个答案时模型偏好靠前的那个，做法是交换顺序各评一次取平均。长度偏差——偏好更长的答案，做法是在评分标准里显式要求「不因长度加分」。自偏好——模型偏好自己家族生成的文本，做法是裁判模型与被评模型跨厂商。此外必须让裁判输出结构化打分（每个维度分数 + 依据），而不是一个笼统的总分，这样才能定位问题；并且用 50~100 条人工标注样例定期校准裁判与人工的一致率，一致率低于 80% 就说明评分标准写得不够明确。

六、上线与持续迭代

Agent 的改动怎么安全上线？
四步不能省。第一步离线回归：在回归集上跑新旧两版，完成率、轮次、成本、延迟四项都不许退化，任一项退化超过阈值就阻断发布。第二步影子运行：新版本对线上真实流量只跑不返回结果，比对新旧差异，专门看新版本是否引入新的失败模式。第三步灰度放量：按 1% → 5% → 20% → 100% 递进，每档观察足够长的时间覆盖业务波峰，重点盯降级率和成本 P99 而不只是平均值。第四步一键回滚：Prompt、工具配置、模型版本都要可独立回滚，且回滚不依赖重新发版。
怎么让 Bad Case 自动回流形成闭环？
靠三个自动化环节把人工从「收集」中解放出来，只保留「判断」。采集：把用户点踩、会话中途放弃、转人工、Schema 校验失败、降级触发这五类信号自动打标并落库，附带完整 Trace 便于复现。聚类：对失败 Case 做语义聚类，按「影响用户数 × 严重度」排序，让最痛的一类自动浮到前面，而不是按时间倒序人工翻。回填：修复后的 Case 自动加入回归集并标注修复方式，形成「发现 → 归因 → 修复 → 回归 → 监控」的完整闭环。没有这套机制，Bad Case 运营会在第三周因为人力耗尽而停摆，这是最常见的失败结局。

示例场景：某工单 Agent 建立自动回流后的第一个月，Bad Case 池累积 1,842 条，语义聚类收敛成 27 类，其中前 4 类覆盖 61% 的失败量。团队只修了这 4 类（三类属知识库过期、一类属工具描述含糊），任务完成率从 71% 升到 86%，人工分析投入从每周约 12 小时降到 2 小时。结论很朴素：Bad Case 运营能不能持续，取决于聚类和排序有没有自动化，而不取决于团队多勤奋。

答题策略 Do / Don't

  • 先归因再优化：报出三层占比（约 35% / 45% / 20%）比罗列技巧有说服力
  • 成本和延迟都先做分段 Profiling，再给优化动作，每步带收益数字
  • 把稳定性讲成工程护栏：幂等、超时、白名单、降级、Trace，与模型强弱无关
  • 评测同时报结果和过程：完成率 + 轮次 + 成本 + P95 四项一起给
  • 提灰度与回滚：说明哪一项退化会阻断发布，体现有生产纪律
  • 一上来就说「换更好的模型」，这是这道题最典型的减分答法
  • 用「感觉快了 / 效果好了」代替指标，被追问 P99 就答不出
  • 只报平均值不报长尾，长尾才是投诉和成本失控的来源
  • 把语义缓存无差别用在写操作和涉敏请求上
  • Bad Case 全靠人工翻，没有采集与聚类自动化，两周后必然停摆
