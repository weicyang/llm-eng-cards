一、Agent 架构与选型

这一节回答架构层的三个问题：整条链路长什么样、编排为什么选 LangGraph、为什么不直接站在现成产品上。答题主线：先给全景，再给取舍，最后给边界。

Q1 · Agent 项目的核心架构

按「接入层 → 编排层 → 能力层 → 数据层」四层组织。接入层承接 API/SSE 请求与会话管理；编排层用 LangGraph 状态图驱动 ReAct 循环，条件分支、人工介入点显式化；能力层挂工具（Function Calling + MCP）、Skill 库、RAG 检索与 Memory 服务；数据层放向量库、关系库（结构化记忆与业务数据）、Redis（会话状态）与对象存储。一次请求的完整路径：意图识别 → Query 改写 → 检索与记忆并行注入 → LLM 决策 → 工具执行 → 结果回填 → 答案生成，全程每个节点打 Trace。

追问链：

追问问题回答要点
为什么不直接写一个大 while 循环？裸循环撑不住分支、回滚、人工介入与断点恢复；状态图把每次流转变成可测试、可重放的边，是生产排障与灰度的前提。
状态在各节点间怎么传？定义 Typed State（messages、plan、retrieved_docs、tool_results、预算计数器），节点只读写自己关心的字段，Checkpointer 统一持久化。
能力层为什么要独立成服务？工具 / RAG / Memory 独立部署后，编排层只认接口：换模型、换向量库、加工具都不动主循环代码，迭代互不阻塞。
可观测性怎么接？每个节点一个 span，模型调用、工具调用、检索结果都带统一 trace_id，直接供评测平台与成本看板消费。
❌ 只答「LLM + 工具 + 循环」就停 → ✅ 给出四层架构与一次请求的完整链路，证明你做过的是生产版而不是 Demo 版。

Q2 · 为什么选 LangGraph？缺点？是否过度设计？

选 LangGraph 三点：一是显式状态图，把 Agent 循环画成节点与边，条件分支、人工介入点、循环边都显式可查，比框架封装的黑盒 while 循环好排障；二是 Checkpointer 支持持久化与断点恢复，长任务中断后可从断点继续；三是子图机制天然支撑 Multi-Agent 编排。缺点也明确：学习曲线陡（state reducer、channel 概念）、抽象层增加调试成本、相比裸循环多一层调度开销。是否过度设计看场景：单链路简单工具调用用它就是过度设计；一旦有分支、断点恢复、人工审批、多 Agent 需求，它就是刚好够用。

追问链：

追问问题回答要点
备选方案对比过什么？两条路：裸写 ReAct 循环（轻，但要自建检查点、并发、中断恢复）；LangChain AgentExecutor（黑盒、难排障，官方已弃用转向 LangGraph）。结论：POC 期裸循环验证价值，生产期切 LangGraph 换可控性。
调试难具体难在哪？条件边让执行路径动态生成，stack trace 不直观、异常可能被节点回调吞掉；对策是节点进出全量日志 + 图结构可视化回放。
上线后踩过什么坑？两个：异步节点没等状态更新完成就读，造成脏读——要理解 reducer 合并语义；Checkpointer 用关系库高并发写成为瓶颈，换 Redis 后端 + 异步落盘。
❌ 只夸 LangGraph 灵活 → ✅ 主动说缺点，并给出「过度设计判定标准」：没有分支 / 恢复 / 人工介入需求，单循环就够，别上状态图。

Q3 · 为什么不直接用 Claude Code 或公司内部 Agent

三个理由。数据边界：业务数据、用户画像、工具凭证不能出域，通用产品接不进内网私有工具与权限体系；业务耦合：要做的是公司 Skill 库、行业术语 RAG、业务级评测这些深度定制，通用 Agent 的编排策略只是泛化模板；成本与合规：大调用量下自建编排 + 小模型路由成本优势明显，审计与留痕要求外部产品无法满足。所以正确姿势是「平台能力复用、业务链路自建」：模型网关、沙箱、Trace 基建用公司平台，编排、Skill、RAG、Memory、评测集自建。

追问链：

追问问题回答要点
公司内部平台复用了哪些？模型网关（统一鉴权、限流、降级）、沙箱执行环境、Trace 基建；编排层与提示词管理不复用——那是业务差异化的核心。
自建成本怎么控制？核心循环只有几千行，真正成本在评测与运维；对齐平台 Trace 协议、复用其存储与看板，避免重造可观测性。
边界一句话怎么划？通用能力（模型调用、沙箱、可观测）用平台，业务知识（Skill、RAG、Memory、评测集）必须自建。

二、Skill、MCP 与工具链

Skill 与 MCP 是当前 Agent 工程的两个热点，出题视角高度一致：不问定义背诵，问「你具体做了什么、边界在哪里」。答题必须落到开发细节与边界判断。

Q4 · Skill 机制是做什么的

Skill 是「打包好的、可按需装载的能力单元」：把特定场景的知识、步骤说明、工具绑定与 few-shot 示例封装成标准结构（名称 + description + 触发条件 + 正文），Agent 处理该场景任务时装载进上下文，让模型「照着手册做事」。它解决两个问题：一是领域知识全塞 System Prompt 会爆炸且互相干扰；二是同类任务全靠模型临场发挥导致输出不稳定。本质是把知识和流程按需加载，从「通才即兴」变成「专家照章」。

追问链：

追问问题回答要点
Skill、提示词模板、工具有什么区别？提示词模板是一次性静态文本；工具是执行即返回的原子能力；Skill 是「说明 + 工具绑定 + 知识」的套装，指导一整类行为。工具回答「能做什么」，Skill 回答「该怎么做好」。
Skill 怎么被触发？显式（用户指定 / 前端传场景标签）与隐式（用 Skill description 与当前任务做语义匹配，类似对 Skill 库做 RAG，命中 top1 再装载）两种。
Skill 数量多了怎么办？不能全量进上下文：两级选择——先向量检索 description 召回 top-k，再由模型决定装载哪个；同一时刻上下文里只驻留 1-2 个 Skill。
❌ 把 Skill 说成工具的另一种叫法 → ✅ Skill 是「按需装载的说明书 + 工具绑定 + 场景知识」，解决的是 System Prompt 塞不下、行为不稳定的问题。

Q5 · 支持 Skill 机制做了哪些开发工作

四块工作：① Skill 定义与注册中心——标准 schema（name / description / version / 依赖工具 / 正文），注册中心支持版本管理与灰度发布；② 装载编排——编排层实现 Skill selector：先向量检索 description 召回，再模型仲裁，命中的 Skill 正文注入上下文的 system 段；③ 工具绑定——Skill 声明依赖的工具集，装载时动态组装 tools，避免模型一次看到几十个工具互相干扰；④ 评测与迭代——每个 Skill 配独立评测用例，新版本过回归才发布，线上监控调用成功率与 token 消耗。

追问链：

追问问题回答要点
Skill 版本冲突怎么处理？注册中心多版本共存，按流量比例灰度；回滚就是切路由权重，正文热更新不需要重启服务。
评测粒度怎么定？每个 Skill 一组小评测集（10-30 条典型请求），重点验证流程合规与输出格式，每次发布前全量跑，成本可控。

Q6 · Skill 里放不放代码

原则是「放说明，不放逻辑」：Skill 正文放声明式的流程描述、约束与示例，业务逻辑放工具里。两种情况可以放代码：一是可执行脚本型 Skill——Skill 附带脚本文件目录（如 Claude Skills 的 scripts 模式），Agent 在沙箱里执行它，脚本是确定性执行体而不是提示词；二是教学用的 few-shot 代码示例。边界判断一句话：逻辑会频繁变化、需要测试的，归工具；稳定的程序性知识，归 Skill。

追问链：

追问问题回答要点
为什么正文里不该有复杂逻辑？提示词「执行」逻辑不可测试、不可调试、行为概率性漂移；同一段逻辑放代码里是确定的、可单测的。
脚本型 Skill 和 MCP 什么关系？互补：脚本在本地沙箱执行，适合文件处理、格式转换类；MCP 管远程服务连接。一个 Skill 可以同时声明脚本与 MCP 工具。
❌ 把分支计算、数据库查询写进 Skill 正文让模型「照着算」→ ✅ 确定性逻辑进工具/脚本（可测试），Skill 只管编排说明，否则行为不可验证。

Q7 · MCP 与 Skill 的区别，及与 CU 的边界

两者解决不同层的问题：MCP 是「连接协议」，标准化 Agent 如何发现与调用外部工具/资源（JSON-RPC 传输、schema 注册、能力协商），解决 M×N 适配爆炸；Skill 是「知识单元」，打包场景化的流程与说明，解决模型「拿到工具后怎么用好」。一句话：MCP 管「伸手拿工具」，Skill 管「拿到之后照着做」。实践中组合使用：Skill 里声明依赖若干 MCP Server 的工具，装载 Skill 时一并接通。至于 CU（客户端/计算单元类的上下文载体，可理解为运行时承载会话上下文与能力挂载的容器单元）：它是「载体」概念，管一个会话能挂载哪些上下文与能力；MCP 与 Skill 都是被 CU 装载的内容——CU 决定「装在哪」，MCP/Skill 决定「装什么、怎么连」。

追问链：

追问问题回答要点
MCP 的 resources/prompts 和 Skill 重叠吗？边界清晰：MCP resources 是暴露给 Agent 读取的数据（文件、视图），prompts 是参数化模板建议，都是细粒度原语；Skill 是粗粒度的场景化打包方案。
Skill 体系能暴露成 MCP 吗？可以：把 Skill 注册中心封装成 MCP Server，暴露 list_skills / load_skill 为工具，任何支持 MCP 的客户端即插即用。
为什么不能只用 MCP 不要 Skill？MCP 不解决「流程知识」：同样 10 个工具，编排顺序、参数规范不同，结果质量天差地别，这些编排知识正是 Skill 的载体。

Q8 · 工具链能否 Skill 化

可以，而且值得做，但要分层。以运维/研发日常工具链（构建、发布、查询、审批）为例：把高频场景（「线上问题排查」「灰度发布」）封装成 Skill，正文写清流程规范——检查顺序、审批要求、红线操作，绑定对应的 MCP 工具。收益：流程知识从口口相传变成可复用资产，高危操作有 Skill 正文约束，比裸暴露工具安全。三个注意点：审批与审计必须由工具/平台侧强制执行，不能指望模型自觉；写权限最小化；Skill 更新要走评测回归。

追问链：

追问问题回答要点
哪些工具链不适合 Skill 化？纯原子查询接口直接作为 MCP 工具即可，不必再包一层；Skill 封装的是「场景流程」，不是「单个动作」。
安全边界怎么划？读操作允许自主执行；写操作走人工审批节点（LangGraph interrupt）；红线操作（删除、回滚）只允许生成建议、禁止自动执行。

三、Multi-Agent 与 Subagent

Multi-Agent 题最忌空谈「分工协作效率高」，必须落到「消息怎么传、上下文怎么隔离、循环怎么停」三个工程细节。

Q9 · Multi-Agent 通信方式与上下文管理

通信用中心化星型结构：Orchestrator 以结构化消息（任务描述 + 输入约束 + 期望输出 schema）下发给子 Agent，子 Agent 返回结构化结果，不横向互相调用——通信路径可审计、可排查。上下文管理的核心纪律是「最小必要信息传递」：不传全量对话历史，只传任务相关输入；子 Agent 上下文独立，做完只回传结论摘要；Orchestrator 维护全局状态表（目标、已完成步骤、关键结论），子 Agent 结果以摘要形式追加而非原文。这样每个 Agent 的上下文都控制在几千 token，避免互相污染与爆炸。

追问链：

追问问题回答要点
两个子 Agent 有依赖怎么办？Orchestrator 中转：从上游结果中只抽取「下游需要的字段」转发，不做全量转发。
共享内存用不用？慎用。共享写冲突与读污染很常见；多数场景用「Orchestrator 状态表 + 结构化消息」覆盖，真正全局的事实（用户画像）才放共享 KV。
消息格式长什么样？JSON schema 约束：task_id / goal / inputs / constraints / expected_output；返回含 status / summary / artifacts / error。结构化才能被汇总与评测。
❌ 把全量对话历史广播给所有 Agent → ✅ 只传最小必要信息、只回传结论摘要；全量传递会导致上下文爆炸、注意力稀释，排障时完全无法追踪。

Q10 · 无限循环与通信冗余治理

三道防线。结构性防线：消息路径设跳数上限（单任务 ≤5 跳），每个 Agent 设执行次数上限，超限强制终止并升级人工；内容性防线：冗余检测——连续相同的（发送方, 接收方, 消息类型）或内容相似度 >0.95 判定为冗余直接掐断，Orchestrator 维护进度台账，一轮结束没有新进展（无新结论、无状态变化）就触发终止；目标性防线：每次下发任务明确验收条件，子 Agent 返回「完成/未完成 + 原因」，Orchestrator 按验收结果决定下一步，杜绝模糊的「来回传话再看看」。

追问链：

追问问题回答要点
「没有进展」怎么检测？对比每轮前后的状态表快照：没有新完成步骤、没有新产物、没有缩小不确定性 → 判定空转，强制重规划或终止。
两个 Agent 互相踢皮球怎么办？禁止横向互调，强制经 Orchestrator 仲裁；子 Agent 对结果不满只能上报，不能直接要求对方返工。
终止之后呢？不能静默失败：把当前进度、卡点、建议打包成事故报告转人工，同时该案例进入回归评测集。

Q11 · Subagent 设计

Subagent 设计回答四个问题。怎么拆：按「专业域 + 上下文隔离需求」拆，如 RAG 问答、代码执行、结果摘要各一个；给什么上下文：每个 Subagent 独立 System Prompt（角色 + 边界 + 输出格式）、独立工具集（最小权限）、只拿任务卡不看主会话历史；怎么回传：结构化「结论 + 证据 + 置信度」，主 Agent 只要结论不要原始过程；谁来派：Orchestrator 统一 spawn，且 Subagent 不允许再 spawn Subagent（禁止递归），避免深度失控。

追问链：

追问问题回答要点
Subagent 和工具的区别？工具是单次确定性操作；Subagent 是带自己循环的小 Agent，能多步推理、调用多个工具，适合「需要探索的子任务」。
Subagent 失败谁兜底？三级：Subagent 内重试（工具级错误）→ Orchestrator 换策略重派 → 人工兜底。失败原因必须结构化，Orchestrator 才能做决策。
拆多少个 Subagent 合适？看信号：某类子任务是否有独立知识域、独立工具集、与主上下文互相干扰。三者不全满足就不拆，拆多了协调成本反超收益。

四、RAG 检索链路

RAG 是本卡问题最多、也最深的一节。答题主线是一条链：意图 → 改写 → 召回 → 精排 → 生成，每一环都要说清「为什么这么做」而不只是「怎么做」。

Q12 · RAG 整体架构与构建流程

离线 + 在线两条流水线。离线构建：文档接入（多格式解析）→ 清洗归一化 → 语义切片 → Embedding 向量化 → 双写向量库与倒排索引（BM25），同时挂 metadata（来源、生效时间、文档类型、权限标签）。在线服务：请求进入 → 意图识别 → Query 改写/扩展 → 混合检索（稠密 + 稀疏，RRF 融合）→ Rerank 精排 → 相似度阈值过滤 → Prompt 组装（带引用）→ LLM 生成 → 幻觉校验与引用回填。横向支撑三件套：评测集回归、Trace 监控、知识库增量更新流水线。

追问链：

追问问题回答要点
为什么向量 + 倒排双写？向量管语义、漏精确词（型号、编号、代码标识符）；倒管精确词、漏语义。混合 + RRF 取两者之长。
知识库变更怎么走？增量流水线：源变更触发重切片 + 重向量化，带版本号与软删除；检索端按版本切索引，不做全库重建。
线上 bad case 主要分布在哪？按占比：切片粒度不当（上下文被切断）、召回阈值过松（带进噪音）、改写缺失（口语查询对书面文档）、生成不遵循检索（幻觉）。定位到哪一环就用哪一环的手段。
❌ 把 RAG 说成「检索 + 拼 prompt + 生成」三步 → ✅ 给出离线/在线双流水线与横向支撑（评测、监控、增量更新），这才是生产级 RAG 的完整形态。

Q13 · Agentic RAG 与主动式 RAG

传统 RAG 是「检索一次 → 生成」的单程流水线；Agentic RAG 把检索闭环交给 Agent 控制：要不要检索、检索够不够、要不要换方向再检索。三种典型形态：Self-RAG——生成时模型自判断是否需要支持、检索内容是否有用，不够就重检重生成；多跳迭代检索——复杂问题拆子问题，逐子问题检索，用中间结论引导下一跳查询；检索工具化——把检索封装为工具，由 Agent 自主决定调用时机与参数。我们落地第三种：检索是工具之一，配合意图分级，简单直答不检索，复杂问题多轮检索。代价是 LLM 调用次数与延迟上升，所以只在复杂意图路径开启。

追问链：

追问问题回答要点
怎么判断「检索够了」？两个信号：rerank 分数达阈值 + 模型判断检索内容覆盖问题的实体与条件；任一不满足触发改写重检，设上限 3 次。
Agentic RAG 的成本怎么算？检索轮次多 1-2 轮、延迟增加秒级；所以必须做意图分级：简单问题走单程流水线，复杂多跳才走 Agent 闭环。
Self-RAG 和它的关系？Self-RAG 是 Agentic RAG 的一种具体实现，特点是训练了特殊反思 token（Retrieve/Relevant/Supported），微调场景下可以免额外调用做反思；工程落地更常见的是外挂校验。

Q14 · 意图识别与 Rewrite 实现及提示词写法

两级流水线：先意图分类（轻量模型或分类器），判定走哪条链路——直接问答 / 任务执行 / 是否需要检索 / 是否多跳；再做 Rewrite：LLM 输入「历史对话 + 当前问题」，输出改写后的 query。提示词固定四模块：任务定义（指代消解、省略补全、口语转书面）、输入格式（历史与问题分区标注）、few-shot 示例（覆盖指代、省略、错别字、多意图）、输出约束（只输出 JSON：rewritten_query / need_retrieval / intent，不输出多余文本）。规则兜底：模型失败或超时就用原句；改写结果与原句都保留，检索结果做并集融合，评测时可对照。

追问链：

追问问题回答要点
多意图 query 怎么处理？改写输出为数组，每个意图一个子 query，分别检索再合并结果；而不是硬合成一句话丢信息。
Rewrite 改错了怎么办？两道保险：原句保留参与融合检索（RRF 并集），不只用改写结果；评测集跟踪改写前后的召回变化，改坏可回滚。
Rewrite 质量怎么评？看下游指标：改写后检索命中率与最终答案准确率；离线建「原句 → 标准 query」改写对评测集做回归。

Q15 · 召回策略：稠密 / 稀疏 / 混合检索

混合检索：BM25 稀疏 + 向量稠密双路并行，各召回 top-50，用 RRF（Reciprocal Rank Fusion）融合出 top-20 再进 Rerank。理由：稠密检索擅长语义泛化（「怎么退钱」能命中「退货流程」），但对专有名词、编号、代码标识符不敏感；稀疏正好相反，精确词命中强但不懂同义。RRF 融合只用排名不用分数，免去两路异构分数的归一化调参，k=60 是经验稳定值。混合后召回命中率显著优于任何单路，是生产知识库的默认配置。

追问链：

追问问题回答要点
为什么用 RRF 而不是加权分数融合？稠密余弦分与 BM25 分量纲、分布都不同，加权要先归一化且每个数据集都要调参；RRF 只用排名信息，免调参、跨数据集稳定。
什么场景可以只用稠密？语料纯口语、无专有名词查询、embedding 模型足够强时勉强可行；但生产知识库几乎都有编号/术语查询需求，混合更稳。
召回量怎么定？两路各 top-50，共约百条进 rerank；rerank 批量推理延迟可控制在百毫秒级，是召回充分性与延迟的平衡点。
❌ 只做向量检索就上线 → ✅ 专有名词、编号、代码标识符是向量检索盲区，BM25 一路成本极低却补上大坑；混合是生产标配。

Q16 · 为什么要单独 Rerank 与向量模型选型

两阶段架构解决「召回 vs 精度」的矛盾：检索阶段追求召回，用轻量模型 + ANN 近似索引从百万级文档快速捞候选；rerank 阶段追求精度，用 Cross-Encoder 对小候选集精排——query 与 doc 拼接整体输入、逐层注意力交互，精度远高于双塔 Bi-Encoder，但单对推理就要几十毫秒，扫不起全库，只能做第二阶段。向量模型我们主力用 bge-m3（多语言、支持稠密 + 稀疏 + 多向量三模态），调研过 bge-large-zh-v1.5、m3e、text-embedding-3-large、Conan-embedding 等。选型方法只信一条：拿自建业务评测集跑召回命中率，公开 benchmark 排名与业务表现并不完全一致。

追问链：

追问问题回答要点
Cross-Encoder 为什么更准？Bi-Encoder 两侧独立编码，只在最后做点积，交互太浅；Cross-Encoder 让两段文本在 attention 里逐层交互，能捕捉否定、数字、限定词等细粒度语义。
rerank 候选集取多大？20~100 是性价比区间：太少漏召回，太多延迟线性涨；我们取 50，批量推理 + 量化后延迟可控。
rerank 分数只用来排序吗？还做门控：分数低于阈值的候选直接丢弃，全部低于阈值就走「未找到相关资料」兜底话术，宁可不答也不硬编。
❌ 拿向量检索 top-k 直接拼进 prompt 生成 → ✅ 检索为召回服务，top-k 里必有噪音；Cross-Encoder 精排 + 分数门控是精度底线，省掉这步答案质量直接打折。

Q17 · 文档切片策略与召回不到数据的处理

切片三层原则：结构优先——按文档自然结构（标题、章节、段落）切，保持语义块完整；长度约束——每块 256~512 token，10%~15% overlap 防边界信息被切断；metadata 增强——每个 chunk 携带完整标题路径（文档名 + 各级标题）再进 embedding，解决「chunk 缺主语」问题，表格单独展平处理。召回不到的处理是降级链：降阈值/扩 top-k → 改写重检（同义扩展、拆子问题）→ BM25 精确词兜底 → 确实没有就诚实回答「未找到相关资料」并把该 query 记入 bad case 做知识库缺口分析。绝不允许用幻觉静默兜底。

追问链：

追问问题回答要点
为什么 chunk 要带标题路径？切片后常缺主语（「支持」——谁支持？）；标题路径给 chunk 定位坐标，检索命中与生成接地都明显改善。
chunk 大小怎么选？太大主题混杂精度降，太小语义破碎召回碎；FAQ 类 128~256，长文档 512 左右，最终以评测集调参为准。
召回阈值怎么定？看 rerank 分数分布上正负样本的分离拐点；阈值高了「说不知道」变多，低了带噪音生成跑偏，两个方向都要线上监控。

Q18 · 文档隔离：关联关系文档与行业术语文档

隔离做两层：存储隔离——不同文档类型分 collection/namespace，metadata 打类型标签；检索隔离——意图识别后按类型过滤召回，或给不同类型不同的召回权重。关联关系文档（产品、组织、功能之间的实体关系）：不把关系信息拆散进普通 chunk，而是建轻量关系索引（实体 → 关联文档 id 列表），查询命中实体时把关联文档拉进候选集做一跳扩展；关系密集场景可上 GraphRAG 三元组支持多跳。行业术语文档：单独建术语表（术语 → 标准释义 + 别名），Rewrite 阶段先做术语归一化（把黑话映射到标准词），检索时术语表提权，必要时把高频术语释义直接注入 System Prompt。

追问链：

追问问题回答要点
为什么不能全混一个库？文档类型的切片策略、更新频率、检索权重完全不同；混库导致没法分别调参，bad case 归因也说不清是哪类文档的问题。
关联关系从哪来？业务系统现成关系（组织架构、产品目录）直接导出；文档共现与人工标注做补充。关系维护成本高，只对高频实体建。
术语表什么形态？KV + 倒排：术语、别名集合、释义、关联实体；Rewrite 时精确 + 模糊匹配，命中做归一化替换，未命中原样放行。

Q19 · Code-RAG 设计

Code-RAG 与文本 RAG 三个本质差异。索引对象：对函数/类/文件建多粒度索引，符号表（标识符 → 定义位置）做精确通道，代码专用 embedding 做语义通道；检索方式：代码查询常是精确意图（找定义、找调用方），优先符号/AST 精确查找（tree-sitter 解析 + LSP），查不到再落语义检索，并沿调用图、依赖图做图扩展；上下文组装：代码 chunk 必须带签名、docstring、import 信息，否则模型写不出正确调用。切片按 AST 节点（函数/类）切，绝不按行数硬切。更新走 git webhook 增量索引。

追问链：

追问问题回答要点
多仓库怎么检索？先做仓库级路由（按问题判断目标仓库）再库内检索；避免跨全仓库召回，噪音过大且延迟失控。
代码检索靠 BM25 还是向量？代码标识符规律性强，精确查找/BM25 往往比向量准；主流是混合——符号精确通道为主，向量语义通道补「用自然语言找代码」的场景。
怎么评测？建「问题 → 期望文件/函数」评测集看 recall@k；端到端看生成代码能否通过编译与单测。

五、Memory 记忆系统

记忆题答题框架固定：先分层（短期/长期、结构化/向量），再答三个工程问题（存什么、怎么存、何时取），最后落到冲突与去重。

Q20 · Memory 实现、上下文注入与长度预算

Memory 分两条线：短期记忆就是当前会话 messages（滑窗 + 滚动摘要），长期记忆存用户画像与历史偏好（结构化字段 + 向量记忆两种形态）。注入时机两处：会话开始时按用户 id + 当前意图检索 top-k 相关长期记忆，注入 system 段作为「用户背景」；执行中把「查记忆」封装成工具供模型按需调用。上下文长度用预算制：总上下文按块划分——System Prompt 约 2k、记忆注入 ≤1k、检索文档 ≤4k、对话历史 ≤6k、工具结果 ≤2k（超了先压缩）、预留输出空间；每块独立上限、独立压缩策略，不等总量爆才处理。

追问链：

追问问题回答要点
为什么注入 system 段而不是 user 段？记忆是「背景设定」不是「用户发言」；放 system 模型态度一致，放 user 会被当成新问题，还会被后续对话冲淡。
记忆检索不准怎么办？检索 query 用「当前意图 + 用户标签」构造，不用全量对话；检索结果带分数门控，宁可不注入也不注入低相关噪音。
记忆注入挤占其他块怎么办？预算制就是防这个：记忆超限先压记忆（只保 top-3），不动检索与对话空间；各块互不侵占。
❌ 觉得「多存多注入总没错」，把对话全量沉淀进记忆 → ✅ 存储噪音直接拉低检索精度，注入噪音稀释注意力；写入标准是「下次任务知道它会做得更好吗」，记忆膨胀是不可逆的上下文污染。

Q21 · Mem0 实现细节

Mem0 的核心是在 LLM 之上加了一层「记忆管理循环」：新对话进来先抽取——LLM 从对话中提取值得记的候选事实（偏好、关键决定）；再比对——用候选事实到已有记忆库做向量检索找相关旧记忆，由 LLM 决策四种操作之一：ADD（新信息）、UPDATE（补充修正旧记忆）、DELETE（旧信息失效）、NOOP（冗余跳过）。存储侧向量库 + metadata（user_id、时间戳、来源），检索按用户隔离 + 时间衰减。优势是自动去重与冲突消解；生产注意：每次写入要两次 LLM 调用，写入延迟与成本不可忽略，高频场景要异步或批量；抽取 prompt 要针对业务调优，否则记一堆无用琐事。

追问链：

追问问题回答要点
UPDATE 和 DELETE 怎么区分？LLM 判断语义关系：新事实是补充修正 → UPDATE；新事实直接否定旧记忆（搬家 vs 旧地址）→ 旧记忆标记失效 + 写入新记忆。
检索侧怎么做？query 向量检索 top-k，叠加 user_id 过滤与时间衰减重排，近期记忆加权，防止过时记忆压过新事实。
直接用 Mem0 还是自研？借鉴其 ADD/UPDATE/DELETE/NOOP 决策机制，抽取模板与存储 schema 按业务重写；开源版 prompt 通用，直接用会记很多低价值内容。

Q22 · 长短期记忆区分保存与结构化 / 文本去重

两条分界线。按生命周期：短期 = 当前会话 messages，任务结束即清空或压缩归档；长期 = 跨会话持久化，按用户维度存。按形态：结构化信息（用户等级、地址、显式偏好）进关系库/KV，精确查询、强一致；文本信息（对话结论、经验描述）做 Embedding 进向量库，语义检索。重复确实会发生——同一偏好既在结构化字段、又在对话文本里出现。去重策略：结构化优先，写入前先查结构化字段是否已覆盖，已覆盖则不再写向量；检索注入前按实体合并去重。每条记忆带「置信度 + 来源」，冲突时结构化 > 文本、新 > 旧。

追问链：

追问问题回答要点
什么信息值得进长期记忆？标准一句话：「下次任务知道它会做得更好」——偏好、约束、关键结论保留；过程闲聊、一次性查询不留。
结构化信息怎么提取？会话结束后 LLM 做 schema 约束的结构化抽取，规则兜底（手机/地址先走正则）；高风险字段写入前校验。
重复不处理会怎样？注入时同一事实出现多次既浪费 token，又会在两条记忆版本不一致时制造冲突；写时去重比读时去重便宜得多。

Q23 · 记忆冲突怎么解决

冲突即两条记忆互相矛盾（旧「用户住北京」vs 新「用户搬到上海」）。处理四步：发现——检索命中多条相关记忆时做一致性检查（规则查同一实体属性值不同，LLM 判断语义矛盾）；裁决——优先级链：时间戳新 > 旧、来源可靠度高 > 低（用户亲口说 > 模型推断）、结构化 > 文本；处置——失败方不物理删除，标记失效 + 保留审计记录；防御——写入端前置比对（Mem0 的 ADD/UPDATE/DELETE 机制），冲突在写入时解决而不是留给读取时。无法裁决的冲突（用户自己前后矛盾）保留两条并标注不确定性，生成时按上下文判断或直接向用户澄清。

追问链：

追问问题回答要点
为什么不直接删掉失败方？审计与回滚需要：新记忆可能是错误抽取，标记失效可以恢复，物理删除就死无对证。
多用户共享记忆冲突呢？先隔离：按用户/租户 namespace；真正共享的知识（团队规范）单独库、写入走审批，不和个人记忆混。
冲突检测性能扛得住吗？不做全量两两比对，只对同一实体的「相关记忆」（向量 top-k）做局部比对，复杂度可控。

Q24 · 用 RAG 检索 Memory 与分层检索设计

可以，Memory 检索就是复用 RAG 的检索栈——记忆本质是「个人化的外部知识」。用向量方式的原因：检索 query 是当前话题的语义表达，记忆存储是自然语言描述，两者词汇重叠低（「推荐个餐馆」要命中「用户偏好川菜」），只有语义检索能覆盖；结构化字段（用户等级）走精确通道不进向量。分层检索三层：L1 结构化快取（KV/关系库直查画像字段，毫秒级，必命中高频字段）；L2 短期近况（本次会话摘要与最近结论，走缓存）；L3 长期向量（语义检索 + 时间衰减 + 重要性过滤，top-k 注入）。执行按 L1 → L2 → L3，前层够用就不动后层，控制延迟与噪音。

追问链：

追问问题回答要点
向量层为什么加时间衰减？记忆有保鲜期，三个月前的偏好可能失效；检索分 = 语义相似度 × 时间衰减 × 重要性权重，防旧记忆淹没新事实。
检索什么时候触发？主动 + 被动：会话开始自动注入 L1 高频画像；对话中模型按需调用「查记忆」工具触发 L3，意图涉及偏好/历史决策时才查。
Memory 和知识库 RAG 共用一个库吗？不共用：namespace 隔离，知识库是公共事实、记忆是私人数据，权限与生命周期都不同；检索栈可复用，索引必须分开。

六、Agent 循环与任务范式

循环与范式是基本功，但「谁驱动循环、谁防失控」是区分新手与老手的分水岭。绝不能说「模型自己在循环」。

Q25 · ReAct 循环流程

ReAct 循环 = Thought → Action → Observation 的迭代直至任务完成。工程实现的关键认知：驱动循环的不是模型，是外层代码——① 组装上下文（system + 历史 + 工具定义）调 LLM；② 解析返回：有 tool_calls 走 ③，有最终答案则退出；③ 执行工具（可并行），结果以 tool 角色写回 messages；④ 回到 ①。现代实现用 Function Calling 的结构化输出替代文本格式解析，更稳。必备三个保险丝：max_steps 步数上限（我们设 15）、工具 + 参数重复检测（连续 3 次相同调用强制终止）、整体超时。被终止时携带当前进度说明退出，不静默失败。

追问链：

追问问题回答要点
并行工具调用怎么处理？一轮返回多个 tool_calls 时，无依赖的并发执行（async gather），有依赖的按依赖顺序串行，结果同一轮写回。
为什么要显式 Thought？两个作用：决策质量（先想后动不冲动）、可排障（Trace 里能看到哪一步想歪了）。
循环退出条件怎么设计？三个出口：模型输出最终答案（正常终止）、步数用尽（强制终止）、超时（强制终止）；后两者必须给用户明确反馈。

Q26 · Plan&Execute 与 ReAct 的区别与适用场景

核心区别是「先规划再执行」vs「边执行边规划」。ReAct 每步根据当前状态决定下一步，灵活、适合不确定性高的任务，但没有全局视野、长任务易漂移，且每轮携带完整历史、token 随步数平方级增长。Plan&Execute 先由 Planner 产出完整步骤清单，Executor 逐步执行、每步后可评估是否 Replan；全局结构清晰、步骤可并行、执行时每步只带本步指令与前序摘要、token 省一半以上，但初始计划错了难回头，且多一次规划调用。选型：步骤少且不确定（要看到结果才能定下一步）用 ReAct；步骤多、依赖明确、结构可预见（报告生成、批量处理）用 Plan&Execute；生产常混合——P&E 定骨架，步骤内部用 ReAct，规划用强模型、执行用便宜模型降本。

追问链：

追问问题回答要点
Replan 什么时候触发？不是每步都重规划（太贵），设触发条件：步骤执行失败、输出偏离预期、发现新信息；否则按原计划执行。
P&E 怎么处理动态任务？纯 P&E 不行，所以有动态 Replan：执行结果与剩余计划一起回传 Planner 决定调整，相当于「粗粒度 ReAct」。
成本账怎么算？5 步任务：ReAct 每轮带全量历史，输入按 1+2+…+n 增长；P&E 只有规划与汇总两次用足上下文，执行带摘要，总量约省一半，再叠模型分层还能降。

Q27 · Agent 死循环怎么解决

死循环是工程问题不是模型问题，绝不依赖模型自己停。五层防线：① 步数上限——max_steps 强制终止（15 步经验值）；② 重复检测——连续 N 次（3 次）相同工具 + 相同参数判定空转，直接退出或换策略（换 query、换工具）；③ 进度检测——一轮结束没有新结论、没有状态变化判定无进展，强制终止；④ 超时预算——整个任务级时间上限；⑤ 根因处理——多数循环源于模型在同一步反复失败（工具报错、格式错误），必须把错误信息写回上下文并明确告知「你已失败 N 次，换方法或总结退出」，给模型台阶下。循环触发后 Trace 记入 bad case 归因。

追问链：

追问问题回答要点
模型为什么会反复调同一工具？两个原因：错误反馈不足（只说「失败了」没说哪里错，模型不知道怎么改）、任务无解但没有退出指令。对策是细粒度错误回填 + prompt 里写兜底出口。
重复检测能被「微调参数」绕过吗？先做工具 + 参数精确匹配（零成本）；若模型每次微调参数绕过，加参数相似度判断（语义相似度 >0.95 视为重复）兜底。
终止后给用户什么？不是「系统错误」，而是结构化说明：已完成什么、卡在哪、为什么卡、建议怎么办；该请求同时进人工复核队列。
❌ 只设一个 max_steps 就算治理 → ✅ 步数上限只是止血；重复检测 + 错误回填 + 明确退出指令才能降低循环发生率，否则上限频繁触发、任务成功率照样难看。

示例场景：一个内部研发助手 Agent 上线两周后收到成本告警——日均 token 消耗从 800 万涨到 3400 万，但请求量只涨了 15%。拉 Trace 归因发现 6.2% 的会话触发了 max_steps，其中 83% 是同一个日志查询工具连续调用超过 8 次：工具在查不到数据时只回一句「query failed」，模型既不知道是语法错还是时间范围错，就不断微调参数重试。改法只有两条——工具错误改成结构化回填（错误码 + 失败字段 + 一个可用示例），并在 prompt 里写死「同一工具失败 3 次后必须输出已知结论并退出」。一周后 max_steps 触发率从 6.2% 降到 0.7%，日均 token 回到 1100 万，任务成功率反而从 71% 升到 84%——因为绝大多数循环并不是「任务太难」，而是「模型不知道自己哪里错了」。

七、上下文工程

上下文工程是 Agent 工程的核心。这一节五问连成一条线：怎么组装、怎么辨析结构、怎么防重复调用、怎么压缩、压缩时怎么保全工具历史。

Q28 · 上下文分层组装方式

按五层组装，从外到内、稳定在前变化在后：① System Prompt 层——角色定义、行为规范、输出格式、few-shot，基本不变；② 能力定义层——工具 JSON Schema 与选中的 Skill 正文，按任务动态选择；③ 知识注入层——RAG 检索文档 + Memory 画像，每次请求动态生成；④ 对话历史层——messages，带窗口与摘要策略；⑤ 当前输入层——用户本轮发言与本轮工具结果回填。组装三原则：预算制（每块独立上限）、稳定前缀尽量前置（吃 Prompt Cache）、工具结果先加工（截断/摘要/外存）再进上下文。

追问链：

追问问题回答要点
为什么稳定在前变化在后？Prompt Cache 按前缀匹配，前部任何变化都会使后续缓存全部失效；System Prompt + 工具定义前置，缓存命中时输入成本可降一个量级。
工具结果放在哪一层？属于对话历史层——assistant 的 tool_calls 与 tool 角色结果成对穿插在 messages 中；大结果先外存、上下文只留摘要与引用 id。
Memory 注入放哪？与检索文档同属知识注入层，顺序在检索之后；都带来源标注，方便生成端引用与校验。

Q29 · System Prompt + Memory + Tools Result + Conversation 结构辨析

方向对，但要补四块、校准顺序。完整结构：System Prompt（角色 + 规范 + few-shot）→ 工具定义（JSON Schema，独立一块）→ Memory 注入 → 检索文档 → Conversation 历史 → 当前输入，而 Tools Result 不是独立一层，是穿插在 Conversation 历史里的 tool 角色消息（每次工具调用后结果紧跟成对出现）。四个辨析点：工具定义（静态 Schema）与工具结果（动态返回）是两回事，前者是能力声明、参与前缀缓存，后者是运行时数据；检索文档是独立层，不与 Memory 混放；顺序影响缓存与注意力（稳定在前、重要信息在两端）；每块要有预算上限，没有一块可以无限膨胀。

追问链：

追问问题回答要点
工具定义能省吗？不能，Function Calling 每次调用都要求完整 Schema 在场；它稳定，恰是前缀缓存的高价值目标。工具多时做动态选择——只暴露当前任务相关工具，平衡 token 与选择准确率。
为什么重要信息放两端？长上下文存在「lost in the middle」现象，中段内容分到的注意力弱；关键约束放 system 头部、当前输入放尾部，历史与材料放中间。
few-shot 放哪里？放 System Prompt 块内，与工具定义一起构成稳定前缀；示例选取要覆盖高频意图与易错格式。

Q30 · 长期运行导致模型重复调用工具

根因是上下文变长后模型「忘了」已经调过：历史太长，工具结果摘要被淹没，模型找不到结论就重新执行。四层治理：① 去重拦截——工具执行前对近期（工具, 参数）签名做匹配，完全重复直接返回「已调用过，结果是 X」，不真实执行；② 结论黑板——在上下文靠前位置维护「已确认结论 / 工具结果摘要」结构化清单，不随对话流被淹没；③ 滚动摘要——把早期工具调用细节压缩成「调过 X 工具，得到 Y 结论」，保留原始引用 id 供溯源；④ prompt 纪律——System Prompt 明确「调用工具前先查结论清单，避免重复调用」。

追问链：

追问问题回答要点
去重拦截对写操作安全吗？查询类拦截安全；写类操作要靠幂等键（请求携带业务唯一 id），不能只比参数，否则误判会造成重复写入。
结论黑板会不会自己也膨胀？会，所以结论也要治理：只保留「活跃结论」（与当前任务仍相关），过期结论下沉到记忆，上下文只留一行索引。
拦截的收益在哪？真实工具执行往往比 LLM 调用更贵（外部 API、数据库、副作用风险），拦截是成本与安全的双赢，Trace 里拦截次数本身就是监控指标。

Q31 · 上下文超长与压缩策略

不等超——80% 水位线就主动触发压缩。按信息价值分层处理：① 工具结果——最大头，优先压：大结果回填时就先摘要（原文外存），早期轮次的工具细节直接换成一行结论；② 对话历史——滑动窗口保留近 N 轮原文 + 更早内容的滚动摘要（层级式：近期留原文、中期留要点、远期只留决策）；③ 检索文档——只保留实际用到的 top-3，未命中的材料移除；④ 绝不压缩——System Prompt、当前用户输入、活跃的工具调用对。压缩用一次 LLM 调用批量处理累积的旧历史，压缩结果带「这是摘要」声明。压完仍超限走兜底：Subagent 拆分或转人工。

追问链：

追问问题回答要点
压缩保什么丢什么？丢：礼貌性对话、失败尝试细节、冗余原文；保：已确认结论、用户约束、活跃任务状态、关键实体值。判据一句话：「丢了它下一步决策会不会错」。
怎么验证压缩没压坏？回放测试：同一任务分别用完整上下文与压缩后上下文跑，比对关键决策一致性；评测集定期抽检压缩前后答案质量。
压缩本身不也花 token 吗？花一次 LLM 调用，所以批量触发而非每轮压；压缩输入是被淘汰的旧历史，换来后续每轮的 token 下降，长任务里稳赚。
❌ 超长后直接硬截断，或对所有内容一视同仁地压缩 → ✅ 按信息价值分层：工具结果先压、历史次之、检索再次；System Prompt、当前输入、活跃工具对绝不动。

Q32 · 压缩丢失工具调用历史导致膨胀的处理

这是个悖论：工具结果是最大 token 消耗源（需要压），但 Function Calling 有格式硬约束——API 要求 assistant 的 tool_calls 与对应的 tool 角色结果成对存在，压缩掉任何一方，请求直接被拒绝。我们的做法是「留骨架、去血肉」：① 保住配对结构——tool_calls 与 tool 结果的成对关系不破坏；② 只压结果内容——大结果正文换成「摘要 + 外存引用」，配对仍在；③ 过期调用整组下沉——把一整组「调用 + 结果」写进「历史档案摘要」段（自然语言描述），再从 messages 里删除原始消息，相当于从正式消息降级为背景叙述；④ 写类调用的参数永久保留，供审计与重放。一句话：压缩的对象是内容，不是消息结构。

追问链：

追问问题回答要点
为什么有的实现没这个问题？文本式工具协议（ReAct 式文本解析）的 messages 是纯文本，随便压；结构化协议用格式约束换稳定性，这是选择它的代价，必须配套压缩策略。
真过不了校验怎么兜底？整组删除过期调用对，同时在 system 末尾补一行「早期工具调用已摘要说明」，保持模型认知连续，并用回放评估行为是否退化。
和 Checkpointer 什么关系？全量未压缩历史进 Checkpointer 持久层，供重放与审计；上下文只放压缩后的工作副本。两者分离是长运行 Agent 的关键设计。
❌ 直接摘要 messages，破坏 tool_calls / tool 结果的配对 → ✅ 格式约束是硬墙：配对结构不能断，只能压内容或整组下沉，否则 API 直接报错、任务中途崩。

Q33 · Trace 结构与日志结构化

一次请求一棵 Trace 树：根 span 是请求入口，一级子 span 是编排节点（意图 / 改写 / 检索 / rerank / LLM 调用 / 工具执行 / 压缩），LLM 与工具 span 再挂属性（模型名、token 数、耗时、输入输出摘要、错误码）。结构化日志三要素：统一 schema（JSON：trace_id / span_id / parent_id / stage / status / latency_ms / token_in / token_out / cost / error）；统一关联 id（trace_id 贯穿 Agent 循环每一轮、session_id 贯穿多轮、user_id 贯穿账号）；全量 + 采样双通道（错误请求全量记录，正常请求采样）。这么做的原因：Agent 排障是「找哪一轮、哪个节点」，没有树状结构无法表达嵌套；评测与成本分析依赖结构化字段做聚合，文本日志没法统计；跨请求追查依赖 id 体系串联。

Q34 · 跨 Session 是否需要日志系统

需要，但分级记录。跨 Session 数据有三类：① 记忆写入审计——何时写了哪条记忆、被哪次对话触发、写入前内容快照，记忆出错排查全靠它；② 任务级关联——有的任务跨多个 session（「昨天的分析继续」），task_id 必须独立于 session_id 做关联，否则上下文断裂无法追查；③ 长期行为聚合——高频意图分布、失败模式，进数仓供产品与评测消费。合规注意：原始对话日志要有保留期限、脱敏与用户删除权。工程上分级存储：会话日志热存 7 天供快速排查，冷存归档供审计，聚合指标长期保留。

追问问题回答要点

Q35 · 评测方法：数据集自建 / 沙箱 / 监控 / 准确率优化

三层评测体系。离线评测集（自建）：来源是线上真实请求采样 + bad case 回收 + 人工构造对抗用例，标注「期望行为 + 检查点」，规模数百到数千条；指标拆到子链路——改写准确率、检索 recall@k、工具选择准确率、最终答案准确率，定位问题到哪一环。沙箱执行：代码执行与工具调用类评测在沙箱里跑，以编译通过 / 单测通过自动判定；开放式答案用 LLM-as-Judge 打分，配人工抽检校准。线上监控：实时看板（任务成功率、循环触发率、工具报错率、token 成本、P95 延迟）+ 用户反馈 + 定期抽检评测。准确率优化方法论：先拆解归因（找最差环节），再对症下药（检索差调切片/召回、生成差调 prompt/精排），每次优化必须过评测集回归才上线。

追问链：

追问问题回答要点

❌ 只看整体准确率 → ✅ 整体准确率下降定位不了原因：检索 recall@k、工具选择准确率、答案忠实度要各自独立指标，优化才有抓手。

示例场景：早期我们只有一个「最终答案准确率」的总指标，某次把检索 top-k 从 5 调到 8，总指标从 76% 掉到 73%，团队争了两天也说不清是检索变差还是生成被噪声带偏。补上子链路评测集后答案立刻清楚：改写准确率 91%（未变）、检索 recall@k 从 82% 升到 89%（变好了）、但生成忠实度从 88% 掉到 79%——多召回的 3 条里有 2 条是相关但过期的旧政策，模型分不清版本。真正的修法不是回退 top-k，而是给 chunk 加生效时间 metadata 并在 prompt 里写明「同一政策以最新生效日为准」，改完 recall 保持 89%、忠实度回到 90%、总指标升到 84%。这件事之后我们定了一条规矩：任何单一总指标的波动，必须能拆到至少三个子链路指标上才允许下结论，否则一律按「归因未完成」处理。

Q36 · 幻觉产生原因与减少方法

根因四个：训练目标是「生成流畅的高概率文本」而非「真实文本」，模型没有内置事实校验机制；参数化记忆模糊，低频事实易编造；检索材料缺失或不相关时模型只能「自备干粮」补全；采样解码引入随机性。减少靠全链路而不是单点：检索侧提高召回与精度，让模型有料可用；生成侧 prompt 约束「只依据检索内容回答、不足时明说不知道」+ 低温度；输出侧忠实度校验——答案中的实体、数字与检索材料交叉核对，引用强制校验存在性；架构侧 Self-RAG 反思，高风险字段（数字、日期、引文）走规则校验。关键认知：幻觉无法根除，工程目标是「高风险输出必校验、可校验点必有溯源」。

追问链：

追问问题回答要点
哪类幻觉最危险？具体数字、日期、引用来源、API 参数——模型倾向编造「看起来真实」的细节；这些点是规则校验与重点抽检对象。
线上怎么检测？抽检 + 自动校验：引用 id 必须真实存在于检索集、数字与原文交叉核对、LLM-Judge 打忠实度分；低置信请求触发二次生成或人工。
有了 RAG 就够了吗？不够。RAG 解决「有没有料」，不解决「跟不跟料走」（忠实度问题），生成约束 + 输出校验双保险缺一不可。

Q37 · 部署问题、性能优化与并发控制

典型问题三类。长连接与超时：Agent 任务动辄分钟级，同步 HTTP 扛不住，用 SSE/WebSocket 流式 + 任务异步化（提交任务、查询进度），网关超时按任务级别调整。资源与并发：LLM 调用是 IO 密集，并发数由下游限流决定而不是 CPU；三级限流——用户级（防单用户独占）、任务级（限制并发 Agent 循环数）、模型网关级（令牌桶 + 队列削峰）；触发限流自动降级（排队延迟 / 小模型兜底 / 提示稍后重试），不静默丢请求。状态恢复：长任务进程重启丢状态，Checkpointer 持久化 + 断点续跑。性能优化优先级：Prompt Cache（输入成本与首 token 延迟双赢）> 并行工具调用 > 流式输出 > 模型路由分层。

追问链：

追问问题回答要点
流式输出落地细节？LLM SSE 透传 + 编排层事件流（工具执行进度事件）一起下发，前端渐进渲染；注意关闭网关 proxy buffer，否则流式退化成批量输出。
怎么做水平扩容？服务层无状态化，状态外置到 Checkpointer / Redis；真正的瓶颈是模型网关限流与向量库 QPS，扩容前先算这两个上限。
监控盯哪些指标？队列长度、P95 延迟、任务成功率、限流触发率、token 成本，五个指标构成健康度看板，任何一个异动都要能归因到链路环节。

Q38 · 项目最难的困难与解法

最难的困难是「线上稳定性与效果迭代的矛盾」：每次改 prompt / Skill / RAG 策略都牵动多个环节，bad case 归因困难，早期经常出现「修好一个问题、带出三个新问题」。解法是建「评测驱动的迭代闭环」：① 建子链路评测集 + bad case 库，每个线上问题强制归因到环节（检索 / 生成 / 工具 / 循环）；② 任何变更先过离线回归再灰度上线，核心指标下降自动回滚；③ Trace + 监控让线上问题分钟级可见。效果：迭代周期从「改完 prompt 观察三天」缩到「当天回归、当天灰度」，bad case 从发现到修复有闭环。这个困难的本质：Agent 系统是概率性的，工程要求确定性，评测与可观测就是连接两者的桥。

追问链：

追问问题回答要点
有没有纯技术上的难点？两个：上下文压缩时的工具调用历史保全（Q32 方案）与记忆冲突消解（Q23 方案），都是从线上 bad case 反推出的设计。
效果怎么度量？三个指标：任务成功率（评测集 + 线上抽检）、bad case MTTR（发现到修复时长）、变更回归通过率。
评测结果和人工体感不一致怎么办？通常是评测集分布偏了——按线上真实分布抽样修正；「LLM-Judge 与人工一致率」本身作为评估指标持续跟踪。

Q&A

以下 5 个元问题针对「跨题追问」场景：出题人不会一题一题按顺序问，而是顺着一个链路往下钻。这里给的是应对策略，不是知识点本身。

如何把 38 题串成一条「项目链路深挖」的叙事主线？

用一条完整请求路径做主线：请求进入 → 意图/改写 → 检索 + 记忆注入 → LLM 决策循环 → 工具执行 → Trace 进评测。架构选型（Q1-Q3）是这条链路的骨架，Skill/MCP（Q4-Q8）与 Multi-Agent（Q9-Q11）是能力扩展，RAG（Q12-Q19）与 Memory（Q20-Q24）是两大输入，循环与范式（Q25-Q27）是引擎，上下文工程（Q28-Q32）是供油系统，Trace 评测与治理（Q33-Q38）是仪表盘。任何一题被深挖，都能顺着这条主线把相邻环节带出来——讲的是一套运行中的系统，而不是 38 个孤立知识点。

被追问「这样是不是过度设计」时，怎么给取舍框架？

不要辩解「没有过度设计」，给判定标准：任何设计问三件事——场景里有没有对应的痛点信号（分支 / 断点恢复 / 人工介入 / 上下文爆炸）、复杂度付出了什么成本（开发、调试、延迟、token）、能不能渐进拆除。再给真实例子：LangGraph 是因为有断点恢复与人工审批需求才上的（Q2）；但简单意图路径用单循环 ReAct 而不是 Plan&Execute，这就是「不过度设计」的一面。结论永远是：设计层级与问题复杂度匹配，复杂度要能加也要能减。

Memory 与 RAG 结合类问题，怎么分层回答？

固定三层。第一层分库：知识库是公共事实、记忆是私人数据，索引隔离、检索栈复用（Q24）；第二层检索策略：结构化快取 → 短期缓存 → 长期向量，三层按需触发，长期层加时间衰减与重要性权重（Q24）；第三层注入纪律：预算上限（记忆注入 ≤1k token）、注入 system 段、分数门控、宁缺毋滥（Q20）。最后一句话收拢：RAG 给模型「世界知识」，Memory 给「熟人关系」，两者是同一个工程问题——外部知识注入——的两个平行实例。

被问具体数字（延迟 / 成本 / 准确率）但记不准时怎么办？

给「量级 + 推导」，不背数字。例：rerank 延迟可现场推——「Cross-Encoder 单对几十毫秒，50 个候选串行是秒级，批量 + 量化压到百毫秒级」；ReAct 的 token 账——「每轮携带全量历史，输入随步数近似平方级增长，1+2+…+n」。同时加限定词：「我们线上观测到的量级大概是……」。数字可以模糊，推导链必须正确——考查的是理解而不是背诵。

如何展示线上治理经验，而不是背概念？

三个技巧。从 bad case 切入：「线上发现 X 现象 → Trace 定位到 Y 环节 → 所以做了 Z 设计」，用现象而不是概念开场；带阈值与量级：15 步上限、相似度 >0.95 判重复、80% 水位触发压缩——阈值证明你真的调过参；讲闭环：发现 → 归因 → 修复 → 回归 → 灰度，展示治理是体系而不是救火。Q38「最难的困难」就是检验这套答法的综合题。

38 问怎么串成一条主线，避免答成知识点清单？

主线就是 Q1 的四层架构：接入 → 编排 → 能力 → 数据。任何一题答完都用一句话挂回主线——Skill 与 MCP 是能力层的两种装载方式（Q4–Q8）、RAG 与 Memory 是数据层的两个平行实例（Q12–Q24）、ReAct 与上下文组装是编排层的内循环（Q25–Q32）、Trace 与评测是横切这四层的观测面（Q33–Q37）。这样做有两个好处：面试官换顺序提问你也不会乱，因为每题都有固定坐标；被追问时你能顺着相邻层延展，把一道题的答案变成一段链路的讲解。反过来，如果 38 题在你脑子里是 38 条并列条目，任何一次跳跃提问都会让你从头检索——那正是「背过」和「做过」在临场时最明显的区别。
