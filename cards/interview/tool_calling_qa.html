一、Function Calling 基础（Q1-Q3）

Q1 · 什么是 Function Calling？原理是什么？

Function Calling 是让模型以结构化方式发起工具调用的机制：开发者先用 JSON Schema 把工具的名字、用途、参数描述清楚传给模型，模型判断需要外部帮助时，不再生成自然语言，而是直接输出携带函数名和参数的 tool_calls JSON。真正的执行由宿主程序完成，结果以 tool 消息塞回对话，模型再据此给出最终答案。整个过程是「两轮对话 + 中间执行」的闭环，模型全程只负责决策。
追问问题回答要点
为什么必须输出 JSON 而不是自然语言？自然语言要靠 if/else 猜意图，换个说法就失配；JSON 格式固定、可直接被程序解析，2023 年 OpenAI 把它标准化后，Claude、Gemini、Qwen 等主流模型相继支持，工具调用才有了统一对接标准。
并行调用是怎么做到的？tool_calls 本身是列表，多个互不依赖的调用（如同时查两个城市天气）可以在一次响应里全部给出，宿主并发执行后一次性回填，把多轮往返压缩成一轮；有依赖关系的调用（先查订单号再查物流）只能串行分轮。加分数据：GPT-4o 与 Claude 3.5+ 支持 Parallel Function Call，一次返回多个调用并行执行，总延迟从 T1+T2+T3 降到 max(T1,T2,T3)。
schema 里哪个字段最关键？description。它是模型判断「要不要调、参数怎么填」的唯一依据，写得含糊模型就会瞎猜误调；参数的格式要求、取值限制、示例也应写进描述里。
一次 Function Calling 的两轮对话 + 中间执行 第 1 轮请求 宿主程序 模型 ┌──────────────────────────┐ │ messages: [user: 北京和 │ ─────────────────────────────→ ① │ 上海今天天气怎么样] │ │ tools: [get_weather 的 │ 模型判断需要外部数据， │ name/description/schema]│ 不生成自然语言，改输出： └──────────────────────────┘ ┌────────────────────────┐ ←────── │ tool_calls: [ │ │ {get_weather,"北京"}, │ │ {get_weather,"上海"} │ ← 列表 ⇒ 可并行 │ ] │ └────────────────────────┘ │ 第 2 轮请求 ▼ 宿主侧执行（模型碰不到） ┌──────────────────────────┐ ┌────────────────────────────────┐ │ messages: [ │ │ ② 工具名白名单校验 │ │ user: …, │ │ ③ 参数 schema / 枚举 / 归属校验 │ │ assistant: tool_calls, │ │ ④ 并发调用真实 API │ │ tool: 北京 12℃ 晴, │ ← │ ⑤ 结果截断，以 tool 消息回填 │ │ tool: 上海 16℃ 多云 │ └────────────────────────────────┘ │ ] │ └────────────┬─────────────┘ └────────────────────────────→ ⑥ 模型据此组织最终自然语言答复 两个边界要说清：模型只在 ① 和 ⑥ 出现，中间 ②~⑤ 全是宿主代码； 并行只对「互不依赖」的调用成立，先查订单号再查物流只能串行分轮。
❌ 模型自己去访问网络、执行 API → ✅ 模型只输出结构化调用请求，一切执行都在宿主代码里完成，「模型决策、代码执行」是整个机制的核心分工

Q2 · LLM 是如何学会调用外部工具的？

工具调用能力不是预训练涌现出来的，而是后天专项训练的结果：SFT 用完整的工具调用对话样本教模型「怎么调」，让它学会识别工具定义并输出规范 JSON；RLHF 再用人类偏好反馈教模型「该不该调」，建立能直接回答就不调用的边界感。训练完成后，这套能力在运行时以 Function Calling 的形式落地——模型输出决策 JSON，代码负责执行。
追问问题回答要点
预训练为什么学不会？预训练的目标只是预测下一个 token，语料里不存在「给定工具 schema、输出标准 tool_calls」的成对模式，模型最多用文字描述「我需要查天气」，生成不出可被程序解析的调用请求。
只有 SFT 会出什么问题？SFT 样本绝大多数是「该调」的正例，模型会过拟合出调用冲动：1+1 也要调计算器、总结文本也要找工具。边界感必须靠 RLHF 的偏好信号来塑造。
RLAIF 是什么？用更强的 AI 模型代替人类标注员给回答打分，成本低一到两个数量级、速度快，但打分模型自身的偏见也会被继承，业界常把人工与 AI 打分混用。
❌ 参数量够大、涌现能力一到自然就会调工具 → ✅ 结构化 JSON 调用不在预训练分布里，必须经过 SFT + RLHF 专项训练才能获得

缺口补充｜格式对齐：训练样本的「标准答案」必须和上线时的消息格式严格一致——system 放工具定义、assistant 的调用轮输出 JSON、tool 消息回填结果。不同厂商的格式并不互通：OpenAI 用 tools/tool_calls 字段，Anthropic 用 tool_use 块，不少开源模型用的是自定义 XML 标签。一个只在 A 格式上训练过的模型，换到 B 格式的推理接口上就会输出错乱文本。这也解释了为什么在 prompt 里「手写」工具说明让通用模型调用，稳定性远不如经过专项训练的模型——前者靠临场理解，后者靠训练时烙进去的格式反射。

缺口补充｜训练与运行的衔接：训练阶段塑造的是倾向，运行时还可以用 tool_choice（auto/required/指定工具）这类推理参数再做一层约束，但推理期约束只是治标；「何时该调」的判断力本身来自 RLHF。把训练视角和运行时视角接起来回答，才能体现对这条链路的完整理解。

Q3 · FC 能力是怎么训练出来的？

FC 能力分两个阶段训练，各解决一个问题。SFT 解决「怎么调」：构造覆盖完整调用链路的对话样本让模型模仿，样本形态是「system 工具定义 → user 提问 → assistant 输出 tool_calls JSON → tool 回填结果 → assistant 最终回答」，损失函数只惩罚模型角色的输出，反复训练后模型把这套格式变成肌肉记忆。RLHF 解决「该不该调」：人类对多种回答排序训练出奖励模型，再用 PPO 把「该调才调、能答就答」的偏好压进模型参数。

训练数据形态：一条 SFT 样本就是一出完整的五幕剧。第一幕 system 消息注入工具清单（名字、描述、参数 schema），相当于发给新员工的工具手册；第二幕是用户提问；第三幕是「标准答案」——注意这里不是自然语言，而是结构化的调用 JSON，这正是模型要学会输出的东西；第四幕模拟工具返回的数据；第五幕模型基于结果给出最终回答。反向传播只对模型扮演的角色生效：当输出偏离正确 JSON，损失产生惩罚，梯度逐步把权重调到能复现正确格式。所谓「格式对齐」，就是训练样本的这套消息结构必须和推理时框架暴露的格式一致，否则模型认不出这套「暗号」。

场景覆盖与数据来源：好的训练集不能只有「正常调一个工具」。至少要覆盖五类场景：单工具调用、多工具并行（一次输出多个 tool_calls）、调用失败后的处理（识别错误并重试或换路，而不是崩溃或无限重复）、不需要工具直接回答（防止调用冲动）、多轮对话中引用历史工具结果。数据构造主要两条路：人工标注质量高但昂贵，通常只用于核心种子数据；业界主流是用已具备 FC 能力的强模型批量蒸馏（Self-Instruct / Distillation）再人工抽查，成本低量大，但上游模型的错误样本会被下游原样学走，即「蒸馏的幻觉传递」，质量抽查环节省不得。

RL 优化工具选择：RLHF 分四步。先让模型对同一问题采样多种处理方式（直接答、调工具、参数填错），覆盖各种情况；再让标注员对它们排序，比如实时天气题里调工具排第一、简单算术题里直接回答排第一；然后用这批偏好数据训练一个只打分不回答的奖励模型，人类的判断标准被蒸馏进这个裁判；最后用 PPO 拿奖励信号持续调主模型。选 PPO 有两个务实原因：训练稳定不易崩，且内置 KL 散度约束，防止模型为了讨好奖励模型把输出分布拉成只会重复套话的怪胎。奖励信号真正塑造的是「调用时机策略」：把工具用在该用的地方，而不是用得越多越好。

两阶段缺一不可：只做 SFT，模型有调用冲动没有边界感；只做 RLHF，模型连 JSON 格式都输不出来，奖励信号无处发力。把两种训练数据粗暴混在一起还会看到三类失败模式：思考中途跳出格式错误的 JSON、能力整体倒向某一边、工具结果回来后推理断裂答非所问。所以工程上是先 SFT 立格式、再 RLHF 修边界的串联流程。

追问问题回答要点
为什么预训练语料里的代码帮不上忙？代码教给模型的是「API 长什么样」，而 FC 要求的是「在给定 schema 的条件下按固定格式输出调用意图」，这种成对模式在自然语料中几乎不存在，必须专项构造。
训练数据为什么要包含「失败重试」样本？真实环境里工具会超时、参数会非法、权限会不足；没见过失败样本的模型遇到报错要么崩掉要么原样重调，有了这类样本才学会识别错误信息并换策略。
蒸馏数据怎么防幻觉传递？抽查 + 规则过滤 + 可执行校验：把生成的调用真正跑一遍，看参数是否合法、结果是否可用，坏样本剔除后再入库。
PPO 的 KL 约束为什么重要？没有它，模型可能极端优化奖励而语言能力退化（reward hacking）；KL 约束把新策略拉住，不让它偏离原模型分布太远。
❌ 预训练语料里有 API 代码，模型自然就会 Function Call → ✅ 工具调用 JSON 不是人类文本的自然模式，必须靠专项 SFT 立格式、RLHF 立边界

二、MCP 协议（Q4-Q8）

Q4 · 什么是 MCP？

MCP（Model Context Protocol）是 Anthropic 2024 年底推出的开放协议，目标是把「AI 接工具」标准化：工具方按规范实现一个 Server，任何支持 MCP 的客户端即插即用，一次实现到处复用，终结了每个工具对每个应用都要单独写对接代码的碎片化局面。协议定义了三类能力——Tools（有副作用的操作）、Resources（只读数据）、Prompts（提示词模板），消息层统一用 JSON-RPC 2.0，传输层分本地 stdio 与远程 Streamable HTTP。可以把它理解成 AI 工具界的 USB 接口。
追问问题回答要点
MCP 到底解决了什么问题？工具接入碎片化：过去每个工具 × 每个客户端都是一个独立集成点，格式、认证、错误处理各不相同，换模型换客户端就得重写。MCP 把 N×M 的对接矩阵压缩成 N+M。
Tools、Resources、Prompts 怎么区分？Tools 有副作用、会改变外部状态，通常需要用户授权；Resources 只读无副作用，可以更宽松地暴露；Prompts 是带参数占位符的可复用提示模板。一句话：Tools 改变世界，Resources 观察世界，Prompts 结构化表达。
传输方案最近有什么演进？早期（2024-11-05 规范）远程用 HTTP+SSE 双端点，2025 年 3 月被标记 deprecated，改为单端点的 Streamable HTTP；流式推送底层仍是 SSE，只是合并了端点，对负载均衡和 serverless 更友好。
❌ MCP 是 Anthropic 给 Claude 做的专属框架 → ✅ MCP 是厂商中立的开放协议，属于标准层，与「某个工具调用框架的实现」不是一个层面的东西

📎 深入：A12 · MCP 核心架构

Q5 · MCP 由哪几部分组成？

MCP 可以拆成三层来看。角色层：Host 是宿主应用（Claude Desktop、Cursor 这类），Client 是 Host 内部专职与某个 Server 通信的模块，一个 Client 对应一条 Server 连接，一个 Host 可以同时挂多个 Client；Server 是工具方维护的独立进程。能力层：Server 可暴露 Tools、Resources、Prompts 三类东西。协议层：消息格式统一 JSON-RPC 2.0，传输方式可选 stdio 或 Streamable HTTP，且消息格式与传输方式互相解耦。
追问问题回答要点
Host 和 Client 为什么要分开？Host 管「连谁、何时断」的调度决策，Client 负责某一条连接的初始化、能力发现与调用转发；职责分离后一个 Host 才能干净地并行管理多个 Server。
Client 怎么知道 Server 有什么工具？连接建立后做能力发现：Client 调 tools/list 拉取全部工具定义，再把它们转换成模型原生的 Function Calling 格式注入对话，模型据此决定调用。
消息格式与传输解耦有什么好处？同一套 JSON-RPC 消息既能跑在本地管道也能跑在 HTTP 上，切换传输方式不影响上层调用逻辑，Server 可以从原型期的本地进程平滑升级为正式微服务。
MCP 生产落地有哪些踩坑题？三个，说到就是加分：① 安全隐患——恶意 MCP Server 的供应链攻击，用白名单 + 沙箱执行防御；② 上下文爆炸——工具描述太长挤占 token，按需加载、用到才注入；③ 版本地狱——SDK 迭代快、破坏性变更多，锁定版本号跟公告。
❌ MCP 就是 Client + Server 两端，Server 只提供工具 → ✅ 漏掉 Host 角色、漏掉 Resources 和 Prompts 两类能力、漏掉协议层的解耦设计，都说明没把 MCP 拆开看过

📎 深入：A12 · MCP 核心架构

Q6 · MCP 和 Function Calling 有什么区别？

两者不是新旧替代关系，而是不同层次的两件事。Function Calling 是「调用语言」，规定单次调用请求长什么样：工具怎么描述、模型怎么表达调用意图、结果怎么回填。MCP 是「工具生态协议」，规定工具怎么被标准化打包、注册、发现和跨项目复用。最关键的联系是：MCP 底层仍然靠 Function Calling 驱动——Client 把 Server 的工具定义转成模型原生 FC 格式，模型输出 tool_calls 后由 Client 路由到对应 Server，模型全程感知不到 MCP 的存在。
追问问题回答要点
MCP 依赖 FC 具体体现在哪？整条链路是：Client 拉取工具定义 → 转换成 FC schema 喂给模型 → 模型输出 tool_calls → Client 路由到 Server 执行 → 结果以 tool 消息回填。所以模型若不支持 FC，MCP 的翻译层直接失效。
一个恰当的类比？FC 像 HTTP 请求格式，管「一次调用怎么表达」；MCP 像 REST 规范加服务注册发现，管「一堆服务怎么组织和复用」。层次不同，谁也替代不了谁。
❌ MCP 是 Function Calling 的升级版，FC 会被淘汰 → ✅ FC 是 MCP 的地基，两者是底层语言与上层生态的配合关系

📎 深入：A20 · CLI 与 MCP 架构对比

算一笔集成成本的账：假设团队有 5 个应用、每个要接 8 个工具，纯 FC 方案就是 40 份对接代码，某工具接口改一个字段要同步改 5 处，漏一处就是线上事故；换成 MCP，工具只封装一次，接口变更只改 Server 一侧，所有客户端自动受益。工具越多、应用越多，MCP 的复用红利越明显。

缺口补充｜内嵌与独立的本质差异：FC 的工具是「内嵌」在应用代码里的——schema 和执行逻辑都写死在项目里，与应用生命周期绑定；MCP 的工具是「独立」的——作为独立进程存在，有自己的版本和维护方，任何客户端按需接入。这和「CLI 脚本直连 vs 标准化服务」的架构对比同构：前者点对点、强耦合、每个消费方各自维护一套；后者把能力变成带声明、可发现、可插拔的服务。判断一个工具方案处在哪一层次，就看工具的生命周期是否与应用解耦。

Q7 · FC 与 MCP 的场景选型

选型只需要回答一个核心问题：这个工具会不会在本应用之外被用到？只用一次、只服务这一个应用、做原型验证，直接写 Function Calling，简单直接不引入额外进程；需要跨项目跨团队复用、社区已有现成 Server、工具规模起来了、或者在做正式 Agent 系统，就上 MCP。另外别漏掉部署环境约束：不允许启动子进程的平台，stdio 模式的 MCP Server 根本跑不起来，只能退回 FC。
追问问题回答要点
Function Calling 反而更合适的场景？四类：快速原型与 Demo；工具只为单一应用服务（如内部私有库查询）；需要对执行逻辑精细控制（权限校验、链路追踪直接嵌在调用代码里）；部署环境受限无法起子进程。
社区已有现成 Server 还要自己写 FC 吗？不必。GitHub、Slack、PostgreSQL、Puppeteer、Google Maps 等高频工具都有官方或社区维护的 MCP Server，配置文件加几行即可使用，手写对接等于重复造轮子。
工具多到多少算「规模起来」？不建议给绝对数字，要综合工具复杂度、维护人数、接口变更频率判断——当 schema 和调用逻辑开始散落在代码各处、改动要跨多处同步时，就是该上 MCP 统一管理的拐点。
❌ 小项目用 FC、大项目用 MCP，只看项目规模一刀切 → ✅ 要综合复用需求、现成生态、工具规模、系统性质、部署约束多个维度做判断

📎 深入：A20 · CLI 与 MCP 架构对比

缺口补充｜一个可复用的判断流程：回答时可以按五步走：第一步查社区有没有现成 MCP Server，有就直接用；第二步问是否需要跨项目、跨团队复用，需要就选 MCP；第三步综合评估规模（数量 × 复杂度 × 维护人数 × 变更频率），散乱感出现就迁 MCP；第四步看系统性质，正式 Agent 系统优先 MCP、Demo 优先 FC；第五步检查部署环境是否允许子进程或长连接。这个流程展示了多维判断力，比「看规模拍脑袋」成熟得多。

Q8 · 为什么有些推理模型不支持 MCP？

根源是生成范式的结构性冲突。推理模型的价值在于那段一次性连续生成的长思考链，中途不能打断；而工具调用天然要求「生成到一半暂停、等外部执行、拿结果再继续」。两种模式无法兼容，所以早期推理模型干脆不支持 Function Calling。而 MCP 底层完全靠 FC 驱动——工具定义要转成 FC 格式喂给模型、调用请求要由模型以 tool_calls 输出——FC 缺位，MCP 的翻译层整体失效。这是能力缺失的连锁反应，不是生态适配进度问题。

冲突一：连续思考 vs 中途暂停。推理模型每一步推演都建立在前面所有思考内容之上，整条链是一个依赖完整上下文的有机整体，就像写推理论证写到一半被电话打断，回来只能重新梳理。工程上更现实的障碍是 KV Cache：暂停意味着把积累的全部注意力缓存原样占在 GPU 显存里，等工具执行的几秒到几十秒内这块显存无法服务其他请求，在线系统的吞吐量会大幅下滑；恢复之后，新注入的工具结果还要与旧思路融合，之前的推理是基于「不知道结果」展开的，一致性很难保证。

冲突二：训练目标相反。推理模型靠强化学习重奖「把思考链跑完整且结论正确」的输出，越训越倾向于一直想下去；FC 训练恰恰要求模型学会在合适时机打断自己、切换到结构化 JSON 输出。两种目标混在一起训，常见的失败模式有三种：思考到一半突然跳出格式错误的 JSON、能力整体倒向一边（思考变浅或不会调工具）、工具结果回来后推理与先前思考链脱节。与其两头都做不好，早期产品选择先保推理能力。

冲突三：注入与格式限制。不少推理模型对系统消息注入有严格限制——例如 OpenAI 早期 o1-preview 对 system 消息的支持非常有限，指令只能塞进用户消息，而 FC/MCP 的工具定义恰恰依赖系统层注入。同时一些推理模型只允许在最终答案处使用结构化输出，思考过程是自由文本；开源推理模型的自定义格式（如特定思考标签）与工具调用格式还容易互相污染，解析层分不清哪段是思考、哪段是调用。这些约束叠加，进一步堵死了早期推理模型接入 MCP 的路。

后来的折中方案：主流解法是把工具调用挪到思考阶段结束之后——先让思考链完整跑完，进入答案生成阶段才触发 FC，o1 正式版、o3、Claude Extended Thinking 都走这条路，推理质量得以保住。Claude 进一步提供 interleaved thinking，允许在多次工具调用之间穿插思考，部分缓解「思考阶段看不到工具结果」的局限。但本质权衡仍在：对「必须先查数据才能深入推理」的任务，思考阶段只能基于已有知识盲推。

追问问题回答要点
暂停时保存状态、执行完恢复不行吗？代价过大：KV Cache 长期独占显存拖垮吞吐；且工具结果与既有思考链的融合存在一致性问题，没有简单解法。
为什么不支持 FC 就等于不支持 MCP？MCP 的工具定义必须转成模型原生 FC 格式才能被理解，调用请求也必须由模型以 tool_calls 生成；模型的 FC 能力缺失，MCP 链路从中间断掉。
现在的推理模型怎么兼容的？调用后置：思考完整跑完再进入工具调用阶段；进阶做法是 interleaved thinking，在多次调用间穿插思考，但「带着工具结果深度推理」仍受限。
上下文窗口不够才是原因吗？不是。窗口装得下工具定义，真正的矛盾是生成的连续性被打断，以及训练目标、注入限制、格式约束的结构性冲突。
❌ 只是还没适配，等厂商更新 SDK 就能支持 → ✅ 这是连续思考与中断调用两种生成范式的结构性冲突，属于工程取舍而非进度问题

三、Skill 与三者关系（Q9-Q11）

Q9 · 什么是 Skill？

Skill（Agent Skills，Anthropic 2025 年 10 月推出、同年 12 月开放为标准）是把指令、脚本、模板一体化打包的可复用能力模块：一个文件夹加一份 SKILL.md 指令文件，可选携带脚本、参考文档与输出模板。它与普通 prompt 的本质区别有两点：Agent 能自动发现并按需加载，无需人工粘贴；加载采用三层渐进式披露——启动时只读每个 Skill 的 name 和 description（约 30-50 token），任务相关时才加载 SKILL.md 全文，执行中需要时才读取脚本和模板资源。
追问问题回答要点
和保存下来的 prompt 有什么本质区别？prompt 是一次性口头指令，Skill 是持久化、可版本管理、可被 Agent 自动发现的能力模块，且不只是文字——还能带可执行脚本和资源文件。
渐进式加载解决了什么？上下文经济学：全量加载所有 Skill 会吃掉大量窗口且大多用不上；分层加载让 Agent 只在需要时获取需要的知识，和人类翻手册先看目录是一个逻辑。
和 Slash Command 的区别？斜杠命令必须人工输入触发；Skill 由 Agent 根据任务语义自主匹配加载，自动发现是关键差异。
❌ Skill 就是保存好的 prompt，复制粘贴即可 → ✅ Skill 是可自动发现、渐进加载的指令 + 脚本 + 模板模块，是工程化能力而非文本收藏

📎 深入：A13 · Agent Skills 系统 · A17 · Skill 设计与架构：从设计到运行

上下文经济学实例：假设团队有 20 个 Skill，每个指令加参考文档约 2000 token，全量加载就是 4 万 token，占掉 20 万上下文窗口的五分之一，且大部分在当前任务里根本用不上。换成渐进式加载，启动成本只有 20 ×（30~50）≈ 600~1000 token，相差约两个数量级——这就是「先看简历、再翻详情、用到才取」三层设计的价值。

Q10 · MCP 和 Skill 的区别

两者层次不同、互补而非竞争。MCP 解决「Agent 能做什么」——把数据库、API、文件系统标准化封装成服务，给 Agent 装上做事的手；Skill 解决「Agent 该怎么做」——把完成某类任务的步骤、标准、模板打包成操作手册。粒度上，MCP 是原子操作（一次 read_file、一次 query_database），Skill 是完整工作流（如「代码审查」，内部串联多个步骤与多个工具）。运行时 Skill 编排流程、MCP 提供执行，流程里每一步的动手仍然落到 MCP 工具上。
追问问题回答要点
举一个两者配合的例子？代码审查场景：Agent 匹配到 code-review Skill 并加载流程——第一步读文件（调文件系统 MCP Server 的 read_file）、第二步跑 Skill 自带的 check_security.py 脚本、第三步按 Skill 内模板输出报告。Skill 像项目经理定流程，MCP 工具像专业工人干活。
能不能只用其中一个？缺了 Skill，Agent 拿着一堆工具不知何时用、按什么标准用；缺了 MCP，Skill 流程再详细也无工具可调，只能纸上谈兵。复杂系统两者都要。
❌ MCP 和 Skill 都是描述 Agent 能力的，只是格式不同 → ✅ 一个提供能力（工具与数据访问），一个提供知识（流程与标准），层次完全不同

📎 深入：A13 · Agent Skills 系统

Q11 · FC、Skill、MCP 三者区别

三个概念是自底向上的三层架构，不是三个竞争方案。Function Calling 是底层调用语言，解决模型如何表达「我要调什么、参数是什么」；MCP 在中间做工具生态，解决工具如何标准化暴露、被发现、被复用；Skill 在顶层做知识与流程封装，解决拿到工具后按什么步骤和标准完成任务。记忆锚点：FC 是语言，MCP 是工具箱，Skill 是操作手册。依赖链是 Skill → MCP → FC，每层都建立在下一层之上。
追问问题回答要点
为什么三个概念先后出现？FC 先解决「能不能调」；普及后暴露出每个应用重复对接的痛点，MCP 解决「接入是否标准化」；工具多了又出现「有工具不会用」的痛点，Skill 解决「知识与流程复用」。每个概念都在补上一阶段的洞。
从通信双方怎么区分？FC 发生在模型与宿主函数之间（单次调用格式）；MCP 发生在 Client 与工具 Server 之间（标准化封装与发现）；Skill 发生在 Agent 与知识模块之间（流程加载与执行）。
一个场景串联三者？「分析销售数据找下滑产品线」：Agent 匹配「数据分析报告」Skill 获得流程 → 按流程通过 MCP 发现数据库与 Python 执行器工具 → 模型用 FC 输出 query_database 等调用请求，逐层协作产出报告。
❌ 三者是不同厂商的竞争方案，选一个用就行 → ✅ 分层依赖、各司其职，真实系统往往三层同时在运转

四、A2A 与通信协议（Q12-Q15）

Q12 · 什么是 A2A 协议？

A2A（Agent-to-Agent）是 Google 发布的开放协议，解决多个 Agent 之间如何互相发现、通信与协作。每个 Agent 发布一张 Agent Card 声明自己的身份与能力清单，调度方据此路由任务；协作以 Task 为一等公民，带完整状态机（submitted → working → completed/failed），天然支持异步长任务、流式推送与完成回调。它和 MCP 的关系是一纵一横：MCP 向下连工具，A2A 向外连 Agent，复杂多 Agent 系统里两者同时使用。
追问问题回答要点
为什么需要多 Agent 协作？单 Agent 有三个天花板：工具数量（装太多模型会混乱）、上下文窗口（中间产物很快撑满）、专业深度（全能不如专精）。委派后子 Agent 在自己上下文里完成调研，只把结论摘要返回调度方，上下文压力被有效隔离。
Agent Card 起什么作用？相当于 Agent 的名片，发布在约定位置（如 /.well-known/agent-card.json），声明名称、能力清单（Skill 列表）、是否支持流式与推送通知，是自动发现与任务路由的依据，新 Agent 上线无需改调度方代码。
为什么说 A2A 是 Agent 的微服务化？Agent Card 对应 API 文档、Task 状态机对应异步消息队列、.well-known 发现对应服务注册中心；每个 Agent 都是独立部署、语言无关的标准服务。
MCP、A2A、AG-UI 三大协议怎么一次说清？按「核心关系」分层：MCP 管 AI ↔ 工具（Anthropic 主导，成熟度最高，生态 3000+ 工具）；A2A 管 AI ↔ AI（Google 主导，100+ Agent）；AG-UI 管 AI ↔ 界面（微软 + 社区主导，50+ App），专治「没有 API 可调」的前端交互场景。一句话记忆：MCP 管纵向（Agent↔工具），A2A 管横向（Agent↔Agent），AG-UI 管界面层。新动态：2026 年 4 月 Google 发布 A2A 1.1，新增 Streaming Task Updates，任务进度可实时推送。
❌ A2A 是 MCP 的竞品，Google 想替代 MCP → ✅ 一个纵向连工具、一个横向连 Agent，面向对象完全不同，是互补关系

Q13 · MCP 常用通信方式

MCP 的通信分两层看。消息格式统一用 JSON-RPC 2.0：请求里带方法名、参数和请求 ID，响应凭 ID 配对，JSON 载体易读易调试、语言无关。传输方式按部署形态二选一：本地用 stdio，Client 把 Server 作为子进程启动，通过标准输入输出的管道通信，不经过网络协议栈、延迟极低、无需开端口；远程用 Streamable HTTP，单一端点接收 POST 请求，短任务直接返回 JSON，长任务把响应升级成 SSE 流持续推送。消息格式与传输方式解耦是 MCP 灵活性的关键。
追问问题回答要点
为什么不用 WebSocket？本地场景 stdio 根本不经过网络，无需长连接；远程场景 HTTP 对代理、负载均衡友好且便于无状态扩展，WebSocket 有状态、扩容麻烦还容易被企业代理拦截。
早期 HTTP+SSE 为什么被弃用？双端点把同一会话拆成两条通道（POST 发请求、SSE 收推送），断网时消息处理状态难以判定，排查链路长；2025 年 3 月规范合并为单端点 Streamable HTTP，流式部分底层仍是 SSE。
stdio 有什么限制？只能本机、随宿主进程生命周期存亡；不允许子进程的部署环境（部分 serverless 平台）用不了，只能改走远程 HTTP。
❌ MCP 本地工具也是通过 localhost HTTP 访问 → ✅ 本地走 stdio 管道通信，数据在操作系统内存里流转，不经过网络协议栈也不占端口

📎 深入：ST17 · 大模型流式传输五层方案与生产实战

缺口补充｜解耦设计的基建意义：MCP「消息格式 ⊥ 传输方式」的分层，与 LLM 流式基础设施的思路一脉相承：上层是稳定的事件语义（JSON-RPC 方法调用 / SSE 事件流），下层是可替换的字节管道。Streamable HTTP 的单端点设计让 Server 可以无状态化部署，能直接放进 serverless 环境和任意七层负载均衡之后——这正是「HTTP + SSE 路线」在 AI 基建里比 WebSocket 更流行的根本原因：运维简单、扩展自由、穿透性好。理解了这一点，Q13 与 Q14 其实是一道题的两个侧面。

Q14 · SSE 和 WebSocket 的区别与局限

SSE 不是新协议而是对 HTTP 的巧用：客户端发起请求后服务端不关闭响应，以 text/event-stream 持续追加数据，天然适合「模型推 token、用户只管看」的单向场景，OpenAI、Anthropic 的流式 API 都选它。WebSocket 是独立协议，经 Upgrade 握手（101 Switching Protocols）后连接变成全双工信道，双方随时可说，适合打断、协同这类真双向场景。选型铁律：单向推用 SSE，真双向才上 WebSocket——不是谁功能强选谁。
追问问题回答要点
SSE 有哪些坑？三个：HTTP/1.1 下同域名连接数上限 6 条，多标签页会排队卡死（HTTP/2 多路复用可解）；只能传文本，二进制要 Base64 编码膨胀约 33%；断线重连要配合 Last-Event-ID 重放才能不丢消息，很多实现省略了这一步。
WebSocket 为什么难横向扩展？连接状态绑死在某台后端机器上，新机器接不到老连接，扩容需要把状态外移到 Redis 等共享存储再做消息中转；另外 Upgrade 握手常被企业代理和防火墙当异常请求拒掉，且没有内置的请求-响应配对机制，要自己维护请求 ID 映射。
为什么文字流适合 TCP？token 序列要求不丢不乱序，等 TCP 重传换来正确内容是值得的；语音场景完全相反（容忍丢包、不容忍延迟），所以语音要换 WebRTC 走 UDP。
❌ SSE 是 WebSocket 的简化版、功能是它的子集 → ✅ 两者底层机制完全不同，各有明确局限，选型看通信方向与运维代价而非「强弱」

📎 深入：ST17 · 大模型流式传输五层方案

缺口补充｜SSE 为何赢得 LLM 基建：把视角拉到基础设施层，SSE 的优势全是运维侧的：每次交互都是普通 HTTP 请求，负载均衡器可以随意路由、横向扩容零成本；代理、CDN、防火墙全链路友好；浏览器内置 EventSource 自动重连。LLM 对话天然是「用户 POST 输入 + SSE 推回输出」的双通道模型，用一个 conversation ID 关联即可，复杂度远低于维护 WS 长连接。MCP 远程传输从 HTTP+SSE 演进到 Streamable HTTP 而不是转向 WebSocket，也是同一逻辑的延续。

Q15 · WebRTC 与 WebSocket 在 AI 对话流中的差异

分水岭在传输层：WebSocket 跑在 TCP 上，丢包必须重传，后续数据全部排队等待，延迟会滚雪球；WebRTC 跑在 UDP 上，丢包不等重传，用丢包隐藏（前后帧插值）填补，用一点音质换稳定低延迟（通常 50-150ms）。语音的铁律是「容忍丢包、绝不容忍延迟」——对话延迟超过 200ms 就明显卡顿，超过 400ms 就会出现抢话串线。再加上 WebRTC 内置回声消除、噪声抑制、自动增益、自适应码率一整套音频工程能力，OpenAI Realtime API 这类实时语音产品选它几乎是必然。

文字与语音的需求分叉：同样是流式，文字与语音对网络的诉求正好相反。文字要求每个 token 准确、有序到达，丢一个字符语义可能全变，所以愿意等 TCP 重传——这也是 LLM 文字流式走 SSE/TCP 的原因。语音则是另一套账：人耳对时序极其敏感，但对偶发的 20ms 小缺口几乎无感；TCP 的队头阻塞会让一次小丢包拖住整条流，延迟累积到几百毫秒，通话体验直接崩塌。所以实时语音必须跳出 TCP，这是 WebRTC 存在的根本理由。

P2P 与协议全家桶：WebRTC 不是单一协议而是一套协议组合：UDP 打底保证低延迟；DTLS 完成加密握手（UDP 版的 TLS）；SRTP/RTCP 负责带时间戳和序列号的媒体传输与质量反馈；ICE 框架负责连接建立。建连前双方还要通过信令通道交换 SDP「协商书」（编解码能力、网络地址、加密参数），这个信令通道通常就是 WebSocket——所以 AI 语音架构里常见 WS 跑信令、WebRTC 跑媒体流的分工，两者是配合不是替代。NAT 穿透走三级降级：局域网直连 → STUN 辅助打洞 → 打洞失败（如对称 NAT）退化为 TURN 服务器中转。也就是说 P2P 不是 WebRTC 的全部，最坏情况下它也会退化成类似 WebSocket 的中转模式，只是多数时候能拿到直连的低延迟。

内置音频能力与 LLM 场景适配：WebRTC 真正难被替代的是多年积累的音频处理全家桶：回声消除（AEC）防止扬声器外放的 AI 声音被麦克风再次采回形成循环；噪声抑制（NS）过滤咖啡厅背景音；自动增益（AGC）稳定音量；自适应码率（ABR）依据 RTCP 的网络反馈动态降码率保流畅。这些用 WebSocket 方案都得自己造轮子。对照实时 AI 语音的硬指标——端到端低于 300ms、双向同时流动、用户可随时打断、无回声循环——TCP 系的 WebSocket 在网络抖动下必然不达标。而对 LLM 文字流式场景，WebRTC 的信令与 STUN/TURN 运维成本完全不值得，文字继续走 SSE 或 WebSocket 即可。

追问问题回答要点
为什么语音丢了包不重传？20ms 音频帧丢了人耳无感，重传却会阻塞后续所有音频；丢包隐藏用插值生成替代帧，以轻微音质损失换延迟稳定，这是语音场景的正确取舍。
WebRTC 一定是 P2P 吗？不一定。ICE 按「直连 → STUN 打洞 → TURN 中转」逐级降级，对称 NAT 等环境打洞失败就走中转，仍比「建不起连接」强。
WebRTC 这么强，文字对话为什么不用？文字要的是可靠不是低延迟，TCP 反而是朋友；WebRTC 的信令服务器、STUN/TURN 部署运维成本对纯文字场景纯属浪费。
WebRTC 和 WebSocket 会同时出现吗？会。WebRTC 建连需要信令通道交换 SDP，实践中常用 WebSocket 承担；连接建立后媒体流走 UDP，两者各司其职。

五、LLM 网关（Q16）

Q16 · LLM 网关解决什么问题？

LLM 网关是架在应用与各家模型 API 之间的中间层，把散落在每个服务里的横切关注点集中处理：统一接口（业务只调网关，换模型改路由配置即可，代码无感）；API Key 集中托管（业务方只拿虚拟 Key，真实密钥不扩散）；按团队设 token 配额（防止一个失控脚本烧光全公司额度）；成本追踪与可观测性（知道钱花在哪个服务哪个模型）；负载均衡与故障转移（主路由失败自动切备用）；统一的 Prompt 安全与内容过滤；以及 LLM 特有的语义缓存——用向量相似度匹配语义相近的问题，命中即返回历史答案，直接跳过模型调用。
追问问题回答要点
语义缓存和普通缓存的区别？普通缓存要求请求逐字匹配；语义缓存先把问题 embedding 成「数字指纹」，在向量库里做相似度搜索，超过阈值（通常 0.85~0.95 之间调）就复用历史答案。阈值太低会答非所问（北京的问题命中上海的答案），太高则形同虚设；缓存时效也要按内容区分——天气股价几分钟过期，FAQ 可以缓存几天。
故障转移怎么做？同一个「模型名」配置主备路由（如 OpenAI 主、Azure/Anthropic 备），主路由连续失败达到阈值后自动切换，业务层与用户无感，是生产可用性的重要手段。
和普通 API 网关的本质区别？token 配额管理、语义缓存、Prompt 注入防护、按模型维度的成本核算，都是 LLM 场景特有需求，Nginx 这类通用反向代理提供不了。
常见框架怎么选？LiteLLM 开源社区最活跃、支持 100+ 模型（注意 2026 年 3 月供应链安全事件，生产使用要锁版本跟公告）；One API 对国产模型友好部署简单；Bifrost 用 Rust 主打高性能；PortKey、Kong AI Gateway 适合要托管或已有 Kong 的团队。
❌ 网关就是负载均衡，用 Nginx 反向代理就够了 → ✅ token 配额、语义缓存、Prompt 安全过滤是 LLM 特有命题，普通网关给不了

📎 深入：S01 · LLM 后端设计

没有配额管理的真实代价：某个工程师周五晚上跑了个失控的批量脚本，一夜间吃掉整周的 token 预算，周一全产品线的调用全是 429；API Key 散落在各服务配置里时，一次泄漏就能让黑客在一晚上烧出数千美元账单。网关把密钥收口到一处、给每个团队发虚拟 Key 配独立日预算，超额的请求被挡在单个 Key 上，其他业务完全不受影响——这类「集中控制点」的价值只有在事故视角下才看得清。

Q&A

FC、MCP、Skill、A2A 四个概念怎么用一句话快速区分？
看「谁和谁通信」就一目了然：Function Calling 是模型对宿主程序说话，属于调用语言；MCP 是 AI 客户端对工具服务说话，属于工具箱生态；Skill 是 Agent 翻阅自己的知识模块，属于操作手册；A2A 是 Agent 对另一个 Agent 说话，属于横向协作。四者自底向上分层，依赖链是 Skill → MCP → FC，A2A 与 MCP 一横一纵互补。先抛出这个骨架，再往任意一层深挖都不会乱。
协议对比类问题有没有通用答题框架？
有，四步走：第一步讲定位差异——两者各自解决什么问题、面向什么对象（这是大多数误判的根源）；第二步讲层次或粒度差异——谁在谁之上、原子操作还是完整流程；第三步讲协作方式——它们如何在同一个系统里配合，最好举一个贯穿全流程的例子；第四步讲选型条件——什么场景选谁、边界在哪里。用这个框架回答 MCP vs FC、MCP vs Skill、SSE vs WebSocket、A2A vs MCP，逻辑都成立。
被追问「你实际跑过吗」，没有实操经验怎么接？
诚实但有策略：先说清楚你理解的实操细节，证明你离动手只差一步——比如 MCP 接入就是在 claude_desktop_config.json 里配 command 和 args、重启后自动发现工具；Streamable HTTP 单端点怎么用、哪个方案被 deprecated。再主动谈设计权衡而非操作步骤，例如「stdio 不能跨机器、HTTP 要处理认证和重连」。切忌编造经历，被两个细节追问就会穿帮；展示「我知道动手时会遇到什么」同样能拿分。
「模型决策、代码执行」这句话为什么值得反复强调？
它是整章内容的承重墙。Q1 的职责分工直接由它定义；MCP 的调用路由（Client 把 tool_calls 转发给 Server）是它在宿主层的延伸；安全设计（参数校验、权限控制、沙箱执行）全部挂在「代码执行」这一侧；LLM 网关的集中管控也是在执行链路上做文章。任何把模型说成「自己去访问网络」的答法都会被当场抓住。把这句话当成全章的第一性原理，其余 15 题都是它的推论。
这一章值得背哪些数字和案例？
六个就够撑起大部分追问：① 5 应用 × 8 工具 = 40 份对接代码，说明 FC 的复用痛点；② 20 个 Skill 全量加载约 4 万 token、渐进式加载启动只要约一千 token，说明渐进披露价值；③ HTTP/1.1 同域名 6 条连接上限，SSE 的经典坑；④ Base64 编码使二进制膨胀约 33%，SSE 传不了音视频的原因；⑤ 语音延迟超过 200ms 卡顿、超过 400ms 串线，WebRTC 选 UDP 的生理依据；⑥ 语义缓存相似度阈值 0.85~0.95，网关调参的工程感。数字不在多，在于每个都能挂到一个论点上。
怎么解释「推理模型不支持 MCP」这种反直觉现象？
用类比开场最省力：推理模型的思考链像一篇写到一半的推理论证，工具调用要求中途放下笔去接二十分钟电话，回来只能重写。再补三个技术支点：暂停要长期占用 KV Cache 显存、训练目标（持续深想 vs 学会打断）相反、系统提示注入与结构化输出的限制。最后给传导关系：MCP 依赖 FC 做翻译层，FC 缺位则 MCP 整体失效，并补充现状——o3、Claude Extended Thinking 用「调用后置 + interleaved thinking」做了折中。这个答案有类比、有机制、有演进，层次完整。
追问链一般往哪个方向走，怎么准备？
本卡 16 题的追问链高度模式化，基本沿五个方向下钻：原理 → 实现细节（格式、字段、状态机）→ 局限与坑（连接数上限、有状态扩容、KV Cache 占用）→ 演进史（deprecated 与替代方案）→ 选型权衡（什么场景用什么）。准备时按这五层给每个知识点做自检：能不能说出它怎么工作、哪里会坏、后来怎么改、什么时候不该用。四层都能答上，追问基本到顶了。
