一、Agent 项目与意图路由

这一节检验「真做过」：链路要能一步步说清组件，复盘要有根因有动作，复合意图要给拆分与并行机制，准确率要给评测口径，指标下滑要给三分法排查路径。每一问都可能被往下追三层。

Q1 · Agent 项目从用户输入到结果返回的完整链路

全链路七步：① 接入层接收语音/文本（车载场景先过 ASR），做安全过滤；② 意图识别/路由决定走哪条管线（端侧小模型分类 + 云端 LLM 兜底）；③ 上下文组装：Redis 取会话状态、注入长期记忆与用户权限；④ 编排层（LangGraph 状态图）按意图拆解并驱动执行；⑤ 执行层 Function Calling 调车控/搜索等工具，或走 RAG 检索拼 prompt；⑥ LLM 生成结果，过格式校验与安全审查；⑦ 返回用户，同时落 trace、回写会话状态与记忆。要点：编排与执行分离、工具结果全部可校验、全程有 trace 可回放。

追问链：

追问问题回答要点
哪一步最容易出问题？执行层工具调用：超时、脏数据、参数幻觉都在这。所以工具层必须有重试 + 校验 + 降级，trace 必须记录入参与出参。
链路延迟怎么保？分层：高频简单意图端侧小模型毫秒级处理；可并行的工具调用并发执行；高频重复查询走语义缓存；输出流式返回降低首字等待。
流式输出怎么做？SSE/WebSocket 推 LLM 流式 token；但工具调用段必须等执行完成，通常先给承接话术、结果回来后再续流。
安全审查卡在哪？生成后、返回前：敏感内容过滤、JSON schema 校验；车控等危险操作执行前必须二次确认或走硬规则白名单。

Q2 · Agent 项目线上踩坑复盘

复盘按「现象 → 根因 → 对策 → 沉淀」讲三个真实坑：① 参数幻觉——LLM 调空调接口编造了不存在的档位值，对策是执行前按 schema + 枚举白名单校验，非法参数结构化回错让模型重试；② 无限循环——搜索返回空结果后 Agent 反复调同一工具，token 消耗暴涨，对策是步数上限 + 重复调用指纹检测 + token 预算三重防线；③ prompt 回归——一次 prompt 微调让意图准确率悄悄下滑，两天后才被用户反馈发现，对策是建固定回归评测集，prompt 变更必须过评测门禁再上线。核心体会：Agent 事故很少出在模型智商，大多出在校验、边界和变更管理。

追问链：

追问问题回答要点
哪个坑损失最大？无限循环——发现晚，直接后果是成本飙升。事后补了 token 消耗实时看板与阈值告警，把「发现时间」从天级压到分钟级。
参数校验上了之后幻觉消失了吗？没消失，但从「用户可见的错误操作」变成「工具层拦截的结构化错误」，模型拿到错误说明后大多能自行修正参数重试。
prompt 回归怎么更早发现？固定评测集 + CI 门禁：每次 prompt/模型变更跑同一基线集，准确率降幅超阈值直接阻断发布；线上再叠加抽样评估做持续监控。
❌ 复盘只泛泛说「遇到过幻觉问题」，给不出根因和动作 → ✅ 用「现象 → 根因 → 对策 → 沉淀」结构，每个坑绑定一次具体的监控改进或流程变更，坑才变成工程资产。

Q3 · 车载复合意图拆分：「我有点冷，顺便找家附近川菜馆」

拆分四步：① 意图抽取——一次 LLM 调用输出结构化意图列表：[{intent: 车控.调温, params:{delta:+2}, priority:高}, {intent: POI.搜索, params:{品类:川菜, 范围:附近}, priority:普通}]；② 定优先级——车控/安全类高优、信息查询普通，规则（领域优先级表）与模型输出互校验；③ 编排执行——两个意图相互独立就并行：车控指令走端侧小模型直达车控通道（毫秒级），POI 搜索走云端工具，互不阻塞；④ 聚合回复——按「先车控后查询」的执行顺序合并成一句自然语言反馈。核心原则：按「动作独立性」拆分并行，不是按句子切分。

追问链：

追问问题回答要点
两个意图有依赖怎么办？抽取时同时产出依赖关系（如「顺路如果下雨就关窗」），有依赖的节点串行、独立的并行，本质是生成一张小型 DAG。
抽取漏了意图怎么办？三层兜底：模型抽取 → 规则模板补充（「顺便」「还有」「对了」等连接词是多意图信号）→ 向用户确认「是否还要搜索餐厅」。
一次调用抽多意图稳定吗？用结构化输出（JSON Schema / Function Calling 格式）约束字段与枚举，比自由文本解析稳定得多；高频复合句式再加模板缓存。
❌ 复合意图串行执行——用户说完「冷」要先等餐厅搜完才调空调，体验直接崩 → ✅ 独立意图必须并行，车控类指令走最短路径（端侧直达），绝不排进云端 LLM 的慢车道。

Q4 · 意图识别实现选型与准确率评估口径

选型是三层漏斗：高频头部意图用轻量分类模型（BERT 级或蒸馏小模型，毫秒级、成本低）；长尾与复合意图交给 LLM 路由；规则兜底接住明确关键词模式（安全类必须命中且不可漏）。评估口径三要素：① 评测集从线上真实日志分层抽样构建，覆盖头部 + 长尾 + 历史 badcase，标注有明确 guidelines；② 指标算分类别 precision/recall 与 macro-F1，不能只看 accuracy——头部意图占九成流量时全猜头部也有九成 accuracy；③ 重点盯易混淆意图对的混淆矩阵。「准确率 90%」必须绑定评测集版本与指标口径，否则没有意义。

追问链：

追问问题回答要点
为什么不全部用 LLM？成本与延迟：头部意图占大头流量，全走 LLM 扛不住 QPS 也扛不住时延；小模型接头、LLM 接尾是最经济的分工。
评测集数据从哪来？线上日志分层抽样（头部/长尾按固定配比）+ badcase 主动回流 + 人工构造的边界样本，双人标注、不一致时第三人仲裁。
评测集怎么演进？固定基线集保证版本间可比，滚动追加新 badcase 保证覆盖；每次 prompt/模型变更跑同一基线，数字才有可比性。
❌ 没有评测集就报准确率，被追问「怎么算的」直接哑火 → ✅ 主动交代三件事：评测集来源（线上抽样）、标注方式（guidelines + 双人）、指标口径（macro-F1 而非 accuracy）。

Q5 · 意图准确率从 90% 掉到 82% 的排查路径

先确认口径再定位：第一步核对「尺子」——评测集版本、标注口径、计算脚本是否与上次一致，排除度量本身变化。确认真跌后用三分法定位：① 数据漂移——对比线上 query 分布与评测集分布，看新说法、新黑话、新功能词的命中率，常见于版本更新或季节变化；② prompt/模型变更——查发布记录，system prompt、few-shot 示例、模型版本是否动过，用旧评测集回放新 prompt 验证；③ 工具侧回归——意图识别依赖的外部特征（上轮对话、用户画像、ASR 结果）如果上游接口字段缺失或质量下降，也会表现为准确率下滑。定位到哪层修哪层，并把线上抽样评估做成持续监控，下次自动告警。

追问链：

追问问题回答要点
怎么区分数据漂移还是 prompt 变更？回放实验：prompt 回滚到旧版本，用新线上数据回放——仍低说明数据漂移；恢复说明是 prompt/模型变更导致。
数据漂移确认后怎么办？短期把新分布样本补进评测集并更新 few-shot/微调；长期建漂移监控（线上 query 与评测集的分布距离），超阈值自动告警。
查不出任何变更但就是跌了？查输入侧依赖：上游字段缺失、ASR 错误率上升、新方言新黑话——「输入本身变了」和「模型变了」表现一样但修法不同。

示例场景：座舱助手的意图准确率（macro-F1）从 90% 掉到 82%，用三分法两天定位完毕。先核尺子：评测集版本、标注口径、计算脚本都没变，排除度量本身的问题。再看分布：把线上一周 query 与评测集做词分布对比，发现「小憩模式」「哨兵模式」这两个新说法占了当周流量的 6.3%，而它们在评测集里一条都没有——这部分几乎全落到兜底意图上。第三看链路：车机端 ASR 的一次固件升级把「打开座椅通风」高频误转成「打开座椅童风」，端侧规则匹配直接失效，这一类占掉约 2.8% 的流量。两个根因加起来正好解释 8 个点的缺口。修法也分两条：新功能词在发版时同步进评测集与规则词表（流程性修复），ASR 错字用一层轻量拼音归一化兜底（工程性修复）。三天后 macro-F1 回到 89.4%。这件事之后我们把「新功能上线必须同步评测集」写进了发版清单——指标掉了不可怕，可怕的是没有能立刻区分「数据漂移 / 链路故障 / 度量变化」的排查顺序。

二、Function Calling 与工具链

这一节问的是「模型输出到工具执行」的最后一公里：协议要能讲清 tool_call 的产生与解析，出错要分层处理，MCP / Function Calling / Skills 要说清「各自解决哪一层的问题」。

Q6 · Function Calling 底层协议与 tool_call 到执行的坑

协议流程：请求时把工具定义（name / description / parameters JSON Schema）随消息传给模型；模型决定调用时输出结构化 tool_call（函数名 + JSON 参数，可能一次返回多个）；执行端解析 JSON、校验参数、真正执行，再把结果以 role=tool 的消息回填，供下一轮模型推理。四大坑：① JSON 解析失败——模型输出的参数 JSON 可能截断或转义错误，必须容错解析并把错误回喂模型重新生成；② 参数幻觉——编造枚举外的值、不存在的 ID，执行前必须白名单校验；③ 并行调用——多个 tool_call 的执行顺序与结果配对（靠 tool_call_id）不能乱；④ 超时与幂等——工具调用必须设超时，写操作要幂等设计，重试不能重复产生副作用。

追问链：

追问问题回答要点
为什么模型会输出非法 JSON？流式输出被截断、生成时转义出错两类原因。对策：优先用 SDK 的严格结构化输出模式；解析失败不硬执行，把报错回喂模型重试。
并行 tool_call 怎么处理？无依赖的并发执行，有依赖的强制串行；每个结果用 tool_call_id 对应回原请求，回填顺序必须与请求一致。
写操作幂等怎么保证？请求带幂等键（会话 + 步骤 + 工具名组合），工具端按键去重；或执行前先查询当前状态再决定是否执行。
❌ FC 参数幻觉不做校验直接执行——空调 API 被幻觉调用就是真实事故 → ✅ 任何 tool_call 先过 schema 校验 + 枚举白名单 + 范围检查，校验失败作为结构化错误返回给模型自纠，而不是抛异常终止。

Q7 · 工具调用出错的三层处理：tool / Agent / system

三层防线各管一段：① tool 层重试——网络抖动、超时这类瞬时错误在本层指数退避重试 2~3 次搞定，不暴露给模型；② Agent 层换路——把错误打包成结构化 observation 回喂模型，由模型决定换参数重试、换备选工具还是直接告知用户；脏数据与 schema 不匹配属于这层，不要盲目重试；③ system 层熔断——单位时间内某工具错误率超阈值直接熔断，快速失败并降级到兜底话术或人工入口，防重试风暴拖垮下游。关键：按错误类型（瞬时/脏数据/schema 不匹配）分流，不是一律重试。

追问链：

追问问题回答要点
怎么区分瞬时错误和永久错误？按错误码分类：超时、限流、503 属瞬时可重试；参数校验失败、业务拒绝属永久错误，重试无意义，直接进 Agent 层换路。
Agent 层换路不会让模型乱试吗？回喂结构化错误（错误类型 + 原因 + 是否可重试提示）而非原始堆栈；同时限制同一工具的最大换路次数，防止来回震荡。
熔断和降级具体指什么？熔断：错误率超阈值后一段时间内不再调用该工具，快速失败；降级：返回预设兜底（缓存结果或「功能暂不可用」），关键路径保留人工入口。

Q8 · MCP、Function Calling、Skills 三者关系

三者分层不冲突：Function Calling 是「模型层能力」，解决 LLM 如何表达结构化调用意图；MCP 是「连接层协议」，标准化工具的暴露、发现与鉴权（类似 USB-C），任何支持 MCP 的客户端可即插任何 MCP 工具，把 M 个 Agent × N 个工具的适配量降为 M+N；Skills 是「能力封装层」，把提示词、脚本、资源打包成可按需加载的可复用技能单元。企业内部工具倾向接 MCP 的原因：统一接入标准、跨框架复用、权限与审计集中管控、新 Agent 接入零改造成本；而裸 FC 定义散落在各 Agent 内部，工具与 Agent 强耦合、治理困难。
概念解决层面类比典型场景
Function Calling模型输出格式「我要用工具」的手势任何需要工具调用的场景
MCP工具连接协议USB-C 接口企业内部工具统一接入、跨框架共享
Skills能力封装与分发App / 插件包可复用的提示词 + 脚本 + 资源组合

追问链：

追问问题回答要点
已有 FC 为什么还要 MCP？FC 只规定「模型怎么表达调用」，不管工具怎么注册、发现、鉴权；多 Agent 共享工具集时，每家写一遍 FC 定义是 M×N 成本，MCP 把它降成 M+N。
MCP 会不会引入额外延迟与依赖？本地 stdio / HTTP 传输的延迟增量通常可忽略；换来的是集中审计、版本管理、权限隔离这些治理能力，企业场景得大于失。
Skills 和工具有什么区别？工具是单个原子能力；Skill 是「做一类事的方法」，可包含多个工具 + 提示词模板 + 执行脚本，作为整体按需挂载，减少常驻上下文。

Q9 · LangChain 的 Chain / Agent / Tool 抽象与弃用框架时机

三个抽象对应三种组合粒度：Tool 封装「单个原子能力」（schema + 执行逻辑）；Agent 封装「自主决策循环」（模型决定何时调哪个 Tool、何时停）；Chain 封装「确定性流程」（开发者写死调用顺序，LLM 只是节点）。三类场景弃用框架直接裸调 SDK：① 链路极短（一两次 LLM 调用），框架抽象纯开销；② 需要精细控制 messages 构造、重试、流式输出，框架封装反而碍事；③ 生产排障要求链路透明，框架深层 stack trace 无法归因。判断标准一句话：说不清框架替你做了什么，就裸调。

追问问题回答要点

Q10 · 为什么选 LangGraph：State / Node / Edge 建模方法

选 LangGraph 的原因：LangChain 原生 Agent 是黑盒循环，没有显式状态，难插入人工干预、难断点恢复；LangGraph 把执行建模成显式状态图——State 是共享数据结构（TypedDict/Pydantic，含 messages、当前意图、工具结果等），Node 是处理单元（LLM 调用、工具执行、校验），Edge 是流转规则（固定边走主流程、条件边做分支）。建模顺序：先列「全流程要携带哪些上下文」定 State 字段，再把每个可独立验证的步骤拆成 Node，最后画流转条件。收益：每步可检查、可回放、可 checkpoint，天然支持 HITL 与断点续跑。

追问链：

追问问题回答要点
State 字段怎么设计？三类：会话类（messages）、任务类（当前意图、计划列表、中间结果）、治理类（步数、预算、错误栈）。messages 用追加型 reducer，防覆盖丢失。
Node 粒度多大合适？一个 Node 只做一件事且有可验证输出：意图识别、一次工具调用、结果校验。一个 Node 混两种职责就是拆分信号。
LangGraph 和 CrewAI 的层次差异？LangGraph 是显式状态机编排，流程可见可控可恢复；CrewAI 是角色协作抽象，搭建快但流程隐式。复杂生产链路优先 LangGraph。

Q11 · conditional edge、HITL 与崩溃后 checkpoint 恢复

conditional edge 是一个「读 State 返回下一节点名」的路由函数，注册时给出分支映射；路由逻辑可以是规则或 LLM 判断，但映射必须覆盖所有分支并带 fallback。HITL 两种做法：interrupt_before 在指定节点前阻塞、等外部指令恢复，适合通用「确认再执行」；自定义确认节点能承载更复杂交互（修改参数、拒绝、换分支）。checkpoint 机制把每步执行后的完整图状态存入 Checkpointer（本地调试 MemorySaver，生产用 Postgres/Redis）；进程崩溃后按 thread_id 从最近 checkpoint 恢复状态、断点续跑，不必从头执行——这是长流程任务选 LangGraph 的核心理由。

追问链：

追问问题回答要点
路由函数返回了未知节点名怎么办？直接报错，所以映射必须有默认分支，路由函数输出先过白名单校验，非法值落到 fallback 节点。
interrupt 能等多久？状态在 checkpointer 里持久化，等几小时到几天都可以，适合人工审批流；注意恢复时工具结果的时效性要重新校验。
生产 checkpointer 用什么存储？单机调试 MemorySaver；生产用 Postgres（事务性、可按 thread 查询审计）或 Redis（快），thread_id 作键，定期清理过期 thread。
❌ 长流程编排不配 checkpoint，崩溃后只能从头重跑，人工确认也没地方挂起 → ✅ 生产链路默认挂 Checkpointer，State 里只放可序列化状态，崩溃按 thread_id 恢复——容错与 HITL 都建立在这一点上。

Q12 · 自写 harness 的 resolver 上下文注入与 RAG 检索的粒度区别

两者是不同层的事：RAG 检索是「知识层」——按 query 语义从外部知识库召回相关片段，解决「模型不知道什么」；harness 的 resolver 是「执行上下文层」——在 Agent 每步执行前，按当前任务状态动态组装该步所需的上下文（会话状态、可用工具清单、前序结论、剩余预算），解决「模型这一步该看什么」。粒度区别：RAG 单位是知识 chunk、触发条件是语义相似度；resolver 单位是「执行步骤」、触发条件是状态机位置与任务阶段。自写 harness 时 resolver 是 prompt 工程的核心——它决定每一步喂什么、不喂什么，避免全量上下文塞给所有步骤。

追问链：

追问问题回答要点
为什么不把所有内容都塞进上下文？注意力稀释 + 成本双杀：与当前步骤无关的内容既烧 token 又干扰决策；resolver 的价值就是「每步最小必要上下文」。
resolver 算不算一种检索？它可以把 RAG 作为素材来源之一，但还要做筛选、压缩、排序——RAG 是供应商，resolver 是装配工。
怎么验证 resolver 做得好不好？看两个指标：每步上下文 token 数（应显著低于全量塞入）与步骤成功率（不能下降），两者 A/B 对比。

Q13 · Chunking 策略：100 字还是 500 字

不定死字数，按「信息完整性 × 检索粒度」的权衡定：切太小（100 字）语义被切断，召回碎片、答案质量崩；切太大（500+ 字）检索精度稀释、夹带无关内容、浪费上下文。实操依据三条：① 优先语义边界（段落、标题、条款）而非固定长度，先按自然边界切、超长再二次切；② 常规 chunk 控制在 200~400 token，overlap 10%~15% 防边界信息丢失；③ 每个 chunk 带 metadata（标题层级、doc_id、更新时间），检索时用父子块或标题注入还原上下文。一句话：字数是结果不是依据，语义完整性才是依据。

追问链：

追问问题回答要点
文档里有表格怎么切？表格转 Markdown/结构化文本后整表作为一个 chunk，不拆行，附「表格说明」metadata；超宽表按列组拆分并保留表头。
父子块（parent-child）解决什么？小块负责搜（命中精准）、大块负责答（上下文完整）：检索命中小 chunk，返回给 LLM 的是其父块。
怎么验证切分效果好？不看 chunk 数量，看检索指标：标注评测集上的命中率 / recall@k，按指标调切分参数与 overlap。
❌ 拍一个字数全库一刀切，不同文档形态用同一策略 → ✅ 先看文档形态（手册/FAQ/规章），语义边界优先 + metadata + 评测集调参；切分策略是调出来的不是猜出来的。

Q14 · 向量 + BM25 混合召回融合、Reranker 位置与延迟压缩

双路召回分工：向量管语义相近（同义、换说法），BM25 管精确匹配（编号、型号、专有名词），各取 top-k（如各 50 条）。融合常用 RRF（Reciprocal Rank Fusion，score = Σ 1/(k+rank)）——不归一化分数、只用名次，天然免疫两路分数量纲不一致的问题，稳定好调。Reranker 位置：融合之后、截断之前，用 cross-encoder 对 top 50~100 候选精排，输出 top 5~8 进 prompt。延迟压缩三招：① 双路召回并行而非串行；② rerank 用蒸馏小模型或量化部署、控制候选量；③ 高频查询结果缓存。典型线上水平：召回段 50ms 内、精排 100~200ms，全链路可压在亚秒级。

追问链：

追问问题回答要点
为什么不用归一化加权求和？向量余弦相似度与 BM25 分数分布完全不同，归一化对离群值敏感、权重难调；RRF 只用名次，免去调权重的痛苦。
Reranker 延迟高怎么办？控制候选量（精排上限约百条）、换蒸馏/量化模型、热门 query 缓存；仍不够就分段返回：先给粗排结果，精排结果异步补充。
向量检索用什么索引？HNSW（召回率高、内存占用大）或 IVF-PQ（超大规模、省内存）；调参看两个指标：召回率与 P99 延迟。

Q15 · 知识库日更：增量更新与 doc_id upsert、软删除边界

不要每晚全量重建——耗时长、新旧内容不一致的窗口大。增量流程：① 每篇文档有稳定 doc_id（业务主键，不是自增 ID 也不是内容哈希），chunk ID = doc_id + 序号；② 文档变更时重新切块，按 doc_id 先删该文档旧 chunk 再写新的（upsert 语义），避免新旧并存；③ 带版本号与生效时间，异常可按版本回滚；④ 删除文档走软删除：先标记 deleted、检索层立即过滤，观察期后再物理删除，防误删可反悔。边界一句话：upsert 解决「同一文档更新」，软删除解决「文档消失但要留后悔药」。

追问链：

追问问题回答要点
为什么不用内容哈希当 doc_id？哈希随内容变化，同一文档更新一次就变成「新文档」，旧 chunk 成孤儿无法覆盖；业务主键（文档编号/URL/业务 ID）才稳定。
软删除期间怎么保证检索不到？chunk 上带 deleted 标记，检索层（metadata filter）硬过滤，不依赖「召回后再筛」——后者容易被 rerank 捞回来。
索引更新有延迟怎么办？向量库写入到可检索有段构建延迟，关键文档要写后校验：按 doc_id 反查确认可见，再对外宣布更新完成。
❌ 知识库只做全量重建——重建窗口内用户检索到新旧混杂内容，出问题还无法定位版本 → ✅ 以 doc_id 为锚做增量 upsert + 软删除观察期，全程版本化可回滚；全量重建只作周期性校验手段，不作日常机制。

Q16 · 检索 chunk 互相冲突听谁的 + LLM-as-judge 三元组评估

冲突消解优先级链：① 先按 metadata 规则过滤——时间新者优先、权威来源（官方文档）优先于衍生内容、密级/版本高的优先；② 规则判不了的做语义去重聚类，同一观点保留一条代表；③ prompt 注入冲突处理指令——明确告诉模型「遇到冲突以更新时间新、来源权威的为准，或明确告知存在多个版本」。LLM-as-judge 做 RAG 三元组评估：用强模型当裁判，对每个样本打三个维度——Context Relevance（召回内容与 query 相关吗）、Groundedness（答案是否有召回内容支撑、无幻觉）、Answer Relevance（答案是否答了问题），每维 0/1 或 1~5 分，批量跑评测集得到可持续监控的质量曲线。

追问链：

追问问题回答要点
LLM-as-judge 可信吗？相对排序上与人工评估一致性高，绝对分数有偏；关键是用固定 rubric、同一裁判模型版本，用于趋势对比而非纠结绝对值。
裁判模型自己犯错怎么办？定期抽样人工校准（每周几十到百条）、重要评估换更强裁判或多裁判投票；把裁判分歧大的样本送去人工复核。
三元组评估的数据从哪来？线上抽样 query + 标注「正确 chunk + 参考答案」；冷启动可用 LLM 基于文档生成 QA 对再人工审核入库。
❌ 冲突 chunk 直接全塞进 prompt 让模型「自由发挥」→ ✅ 先用 metadata 优先级链过滤，再用指令约束消解，至少要让模型知道「存在冲突」；否则模型随机选一个且不会告诉你。

Q17 · RAG 权限隔离：普通用户不能检索到高管薪资类文档

权限在检索层拦，不在回答层拦：① 文档与 chunk 入库时打权限 metadata（部门、密级、ACL 标签）；② 查询时把用户身份解析为角色/权限集合；③ 检索引擎以权限集合做硬过滤（metadata filter），无权限文档根本不进候选集。三原则：检索前隔离（召回后再过滤就晚了，prompt 注入还可能把内容套出来）、默认拒绝（未打标的文档默认最小可见）、全程审计（每次查询用了什么权限集、命中哪些文档全部落日志）。高管薪资这类高敏内容再叠加敏感主题黑名单 + 回答侧审查双保险。

追问链：

追问问题回答要点
为什么不能让 LLM 判断「该不该说」？模型判断是概率性的，且可被 prompt 注入诱导泄露；权限是确定性规则，必须落在检索层的硬过滤上。
权限过滤会不会拉低召回？会，但这是应有的收窄；高权限用户可建独立索引视图，普通用户链路不受影响。
权限变更怎么同步？权限变化触发 metadata 更新（重新打标或重建该文档索引）；高敏文档权限收紧要即时生效，不能等夜间任务。

五、记忆与状态存储

记忆与状态题的答法固定：先分层（短期/长期/工作状态），再答三个工程问题（存什么、存哪、何时读），最后落到存储选型的取舍。

Q18 · Agent 跑 50 轮后上下文溢出，短期与长期记忆怎么存

溢出处理三层：① 压缩——截断前先摘要（近 N 轮保原文、更早的压成要点），工具返回主动压缩（2000 token 原始结果换成 200 token 要点）；② 外置——任务状态、已确认结论写外部存储（Redis/状态表），上下文只保留引用，需要时再注入；③ 结构化——用「目标 / 已确认结论 / 待验证假设」固定区域的工作记忆，每轮更新区域而非无限追加。短期与长期分工：短期记忆 = messages + 工作状态，会话内有效、结束即归档；长期记忆 = 用户偏好与历史结论经 Embedding 进向量库、结构化事实进关系库，新会话开始时按语义检索注入。

追问链：

追问问题回答要点
压缩什么时候触发？不等爆仓：设水位线（如窗口的 70%）到了就压一次；工具返回在用完当轮后立即压缩，从源头控制增速。
压缩丢信息怎么办？必然丢，所以关键事实另走结构化抽取通道（写状态表/KV），摘要只处理叙述性内容，两条通道互补。
长会话每轮带全量历史成本很高？是，滑窗 + 摘要同时是成本手段；再叠加 Prompt Caching 复用稳定前缀，缓存命中部分价格约为正常输入的十分之一。
❌ 上下文溢出只答「换更大窗口的模型」→ ✅ 大窗口不解决注意力稀释与成本线性增长；压缩 + 外置 + 结构化三板斧才是正解，窗口大小只是缓冲。

Q19 · Redis 在 Agent 项目里存什么，为什么不选 PostgreSQL

Redis 管三类「热状态」：① 会话状态——对话上下文、工作记忆快照，TTL 自动过期天然匹配会话生命周期；② 缓存——高频 query 的意图识别结果、工具调用结果、语义缓存，毫秒级读取；③ 短时中间态——任务进度、熔断计数、限流计数器。这类数据寿命短、读写频、KV 形态，Redis 的内存读写 + TTL 是天然匹配；PG 的强项是事务、复杂查询与持久化，适合存业务数据、审计日志和 checkpoint（LangGraph 的 Postgres checkpointer 正是此用途）。正确分工：Redis 管热快、PG 管持久、向量库管语义检索，各就各位。

追问链：

追问问题回答要点
会话状态 TTL 设多长？按业务会话时长定（车载场景常见 30 分钟~2 小时），每次访问刷新 TTL，避免对话中途过期丢状态。
Redis 挂了状态丢怎么办？会话级状态接受「重开会话」；关键任务进度另写 PG 兜底（双写或 checkpoint 落库），丢数据的容忍度在设计时就定好。
PG 能不能替代 Redis？能但不值：同等读写频率下延迟与资源差一个量级，且 PG 没有原生 TTL，过期清理要额外写定时任务。

Q20 · Supervisor 模式 vs CrewAI 角色模式，共享 State vs 消息队列

选型看控制需求：Supervisor 模式（中心调度者拆任务、派发、汇总）链路清晰、责任可追溯、好审计，生产首选；CrewAI 角色模式（各 Agent 扮演角色按流程描述协作）搭建快、适合创意/调研类弱流程任务，但流程隐式、难排查。通信选型看依赖：强依赖紧耦合（前一步输出直接喂后一步）用共享 State（LangGraph 思路，简单直接、无中间件）；Agent 间相互独立、要解耦削峰、跨服务部署才上消息队列。车载实时场景优先共享 State——消息队列带来额外延迟与运维成本，没信号不要引入。

追问链：

追问问题回答要点
Supervisor 自己卡住或乱派怎么办？Supervisor 也带步数预算与超时，汇总质检连续不达标就强制收敛输出，可降级人工；调度决策全部落 trace 可追责。
共享 State 并发写会乱吗？用追加型 reducer + 字段所有权（每个 Agent 只写自己负责的字段）；并行分支先汇合再写共享字段。
什么时候消息队列才值得？三个信号同时出现：Agent 独立部署扩缩容、流量峰谷需要缓冲、跨语言跨服务；否则共享 State 足够。
❌ 一上来就拆五六个 Agent「显得架构先进」→ ✅ 先从单 Agent 跑通，出现三个信号（上下文撑爆、需要专业分工、子任务可并行）再拆；每个 Agent 的协调成本都比想象的大。

Q21 · Agent 无限循环防御：step 数、token 预算、cycle detection

三重防御全部做在编排层，绝不依赖模型自觉：① 步数上限——max_steps 常见 15~25，超限强制收敛并汇总已有结果；② token 预算——单任务累计 token 封顶，达线先压缩历史、再超限终止，配合成本看板实时告警；③ 循环检测——记录调用指纹（工具名 + 参数哈希），连续 3 次相同指纹直接终止或强制换路；再加一道整体超时（按场景 30 秒~2 分钟）。线上配置原则：先紧后松，每次触发防御都落 trace 供复盘——被防御拦下的次数本身就是调参依据。

追问链：

追问问题回答要点
强制终止后直接报错给用户？不要：收敛后把已完成部分汇总成「部分结果 + 说明」，体验远好于硬报错；任务状态标记未完成，支持续跑。
token 预算值怎么定？从成本目标倒推：月度预算 ÷ 任务量 = 单任务上限，再按 P95 加安全系数；高价值任务单独放宽并单独监控。
循环检测误报怎么办？指纹只含核心参数、忽略时间戳等噪声字段；连续 3 次相同才是强信号，2 次仅告警，可叠加「结果是否有变化」辅助判断。
❌ 把防御寄托在 prompt 里写「你要懂得适时停止」→ ✅ prompt 约束是概率性的，步数/预算/指纹检测是确定性硬闸门，必须落在编排代码里，prompt 只是辅助。

Q22 · AI 工作流与自主 Agent 的边界

边界判断两问：流程是否可枚举、错误代价是否可控。流程确定（步骤可枚举、分支有限）用 workflow，LLM 只在节点内做处理；流程开放、需要动态决策才交给 Agent。三类任务坚决不交给 Agent 自动跑：① 不可逆高危操作——支付、删除、车控写操作，必须人工确认或硬规则闸门；② 要求 100% 可复现的流程——审计、合规场景要确定性重放，概率性系统不满足；③ 安全攸关的实时控制——制动、转向类链路不进任何概率性系统。总原则：Agent 做建议与草稿，人与规则做最终审批和执行闸门。

追问链：

追问问题回答要点
「人工确认」怎么落地不毁体验？按风险分级：低风险自动执行 + 留痕，中风险异步确认（其余步骤先行），高风险同步阻断确认；车载场景用语音快捷确认。
混合架构里 Agent 越权执行怎么办？工具层权限白名单 + 操作级审批属性，Agent 只能发出「意图」，真正执行要过执行网关校验，网关不认 Agent 身份只认权限。
这个边界是不是太保守？保守是特性：先用边界把流程钉死，再随数据积累逐步放开 Agent 自主范围——先放开再收回的代价远大于反过来。

Q23 · 子 Agent 职责拆分与跨角色优先级扯皮

职责拆分三原则：① 按能力域拆不按任务量拆——车控 Agent、信息 Agent、媒体 Agent 各管自己的工具集与领域知识；② 每个子 Agent 可独立评估——有自己的评测集与指标，出问题能定位到具体角色；③ 接口契约先行——输入输出 schema 先冻结，内部实现各自演进。与算法、后端、产品扯皮优先级时用数据对齐而不是立场对齐：把线上 badcase、失败率、成本数据摆出来，按「用户影响面 × 严重度 ÷ 实现成本」排序；仍有分歧就上升到共同业务目标（本季度主打指标是准确率、成本还是新场景）裁决。

追问链：

追问问题回答要点
拆完子 Agent 衔接处体验变差？设统一 Supervisor 做路由与汇总，子 Agent 不直接面向用户；衔接传结构化上下文摘要，不传原始聊天记录。
评估口径谁说了算？平台方定统一评估框架与发布门禁，各子 Agent 团队维护各自领域用例；口径争议用冻结的基线集裁决。
小团队人手不够怎么拆？先单 Agent + 工具分组，逻辑分区、物理不拆；某个工具组复杂度爆了再真正独立成子 Agent，避免组织架构绑架技术架构。

Q24 · token 成本月 5 万刀怎么砍：模型分级路由 + 语义缓存

先立成本看板再动刀，四层组合：① 模型分级路由——按任务难度分流：简单意图、格式转换走小模型或端侧模型，复杂推理、多步编排走大模型，路由用规则 + 小分类器低成本实现；流量通常呈二八分布，头部简单任务占比大，这一层通常能砍掉约一半；② 语义缓存——高频相似 query（Embedding 相似度超阈值）直接命中缓存答案，车载场景重复问法多，命中率可观；③ 上下文瘦身——历史压缩、工具结果要点化、稳定前缀吃 Prompt Caching；④ 预算治理——单任务 token 预算 + 每日成本看板 + 告警。落地顺序：先治理看清大头，再上路由（收益最大），缓存与瘦身跟进。

追问链：

追问问题回答要点
路由错了代价是什么？误路由不对称：简单题给大模型是浪费钱，复杂题给小模型是坏体验；所以路由宁保守（不确定给大模型），同时抽样回流校正路由模型。
语义缓存会不会返回过时答案？缓存带 TTL 与失效联动：知识类答案绑定知识库版本，版本更新即失效；实时状态类 query（天气、车况）不进缓存。
Prompt Caching 能省多少？看前缀重复率：Agent 的 system prompt + 工具定义天然稳定，缓存命中部分价格约为正常输入的十分之一，高频链路收益显著。
❌ 砍成本只答「换小模型」→ ✅ 小模型只是分级路由里的一招；先有成本看板定位大头，再分层（路由/缓存/压缩/预算）出组合拳，每层给预期降幅。

Q25 · 上线后可观测选型（LangSmith / Langfuse / OTel）与 trace 必埋字段

选型看三点：LangSmith 与 LangChain 生态调试体验最好，SaaS 托管开箱即用；Langfuse 开源自部署、评估与 prompt 管理完善，适合数据合规要求高的企业；OTel（GenAI 语义约定）是厂商中立标准，适合已有 APM 体系、要把 Agent trace 与存量监控打通的公司——自研倾向「OTel 打底 + 评估平台补足」。trace 必埋字段：trace_id/span_id 父子关系、session_id 与 user_id（没有会话维度没法排查）、每次 LLM 调用的模型名/输入输出 token/延迟/成本、工具调用的名称/入参/出参/错误码、意图识别结果与路由决策、prompt 版本号。原则：trace 不打业务字段等于白打——线上排查永远从「哪个用户、哪个场景」开始查。

追问链：

追问问题回答要点
trace 数据量太大成本怎么控？分级采样：默认低比例采样，错误 trace、低分会话、成本异常任务全量记录；告警靠聚合指标，定位靠全量明细。

❌ trace 只记模型输入输出，没有业务字段 → ✅ session_id、user_id、意图、prompt 版本、工具入参出参、成本必须埋全；排查是「用户 + 时间」维度的检索，只有技术字段定位不到人。

Q26 · 座舱场景端云协同切分

切分看三个硬约束：时延、隐私、离线可用。端侧（车载小模型 + 规则 + 缓存）：车控类（空调、车窗、座椅，「我有点冷」→ 调温）、高频固定话术、安全快速通道——毫秒级响应、断网可用；云端（大模型）：开放域对话、复合意图拆解、RAG 知识问答、多步任务编排。协同机制：端侧先拦截，高置信本地执行；低置信或复杂意图上云，云端返回结构化计划（其中车控子指令回传端侧执行）。隐私：语音、位置等敏感数据脱敏后再上云，或只传意图特征不传原始音频；离线：核心车控与高频功能必须有纯端兜底，断网时优雅降级而不是报错。
意图类型位置依据
车控类（空调/车窗/座椅）端侧小模型 + 规则毫秒级时延、安全相关、必须离线可用
高频固定话术（导航回家/播放音乐）端侧缓存 + 小模型命中率高、零云端成本
复杂复合意图云端大模型拆解、端侧执行子指令拆解需强推理、执行需低时延
开放域问答 / 知识检索云端 + RAG知识库在云端、模型能力要求高
隐私敏感（位置/通讯录）端侧本地处理优先合规约束、数据不出车

追问链：

追问问题回答要点
端侧小模型用多大？常见 0.5B~3B 量级的蒸馏模型或专用意图分类器，量化后部署以适配车端算力；大参数模型上车既不必要也不现实。
端云判断不一致怎么办？建一致性评测集（同一批 query 两端对比）持续校准；冲突时一般云端为权威，但安全相关车控指令端侧有否决权。
断网怎么降级？功能分级：P0 车控纯端可用；P1 功能给端侧兜底话术（告知当前网络下不可用）；P2 功能入口优雅隐藏，不让用户看到报错。
❌ 为了「端侧智能」把大参数模型塞上车 → ✅ 车端算力、内存、功耗都受限，端侧只适合蒸馏小模型 + 规则 + 缓存；重推理永远在云端，端云协同的本质是各干各的活。

Q27 · 从零搭座舱 Agent 平台，第一年只做三件事做哪三件

第一年只打地基不追新：① 打通主链路 + 意图底座——语音/文本输入 → 意图路由 → 高频场景（车控、导航、音乐、电话）端到端跑通，同步建评测集与准确率基线，这是后续一切优化的度量基础；② 工具接入标准与治理——把车控、搜索、媒体等核心工具按统一规范（MCP / 统一 FC 规范）注册，带权限、审计、版本管理，后续扩展是「加工具」而不是「重构接入层」；③ 可观测与安全底线——trace 全链路、成本看板、循环防御、高危操作审批闸，保证放量时看得见、管得住、停得下。理由：这三件事是所有后续能力的前置依赖，地基不牢，越早上高级特性欠的债越多。

Q29 · AI 新技术引入生产的决策清单

我的清单六问：① 问题是否存在——它解决哪个线上指标痛点，基线能否量化；② 成熟度——有无生产级案例、社区与厂商维护是否活跃、接口是否稳定；③ 集成成本——能否小规模灰度验证、有没有回滚路径、现有评测集可否直接作验收标准；④ 运维与合规成本——数据是否出境、新增多少依赖、团队学习曲线多陡；⑤ 退出成本——半年后若弃用，要迁移多少代码与数据；⑥ 团队掌握度——是否至少一人能讲清底层原理与失败模式。六问全过先在低风险场景试点，用数据说话再扩量；任何一问不过就缓一缓，不被热度绑架。

Q30 · Python 深拷贝浅拷贝区别与装饰器底层实现

浅拷贝（copy.copy、切片）复制外层容器，内层嵌套对象仍是共享引用——修改嵌套的可变对象两边一起变；深拷贝（copy.deepcopy）递归复制所有层、完全独立，并用 memo 字典处理循环引用。装饰器本质是高阶函数：接收函数、返回新函数，惯用 functools.wraps 保留原函数元信息；@deco 语法糖等价于 func = deco(func)。项目实战场景：@retry(times=3) 包装工具调用函数，统一实现失败重试 + 指数退避 + 耗时日志，避免每个工具各写一遍重试逻辑。
import functools, time

def retry(times=3, backoff=2.0):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            delay = 1.0
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception:
                    if i == times - 1:
                        raise
                    time.sleep(delay)
                    delay *= backoff
        return wrapper
    return deco

追问链：

追问问题回答要点
functools.wraps 保留什么？__name__、__doc__ 等元信息；不写则装饰后函数签名与文档丢失，依赖元信息的机制（如工具自动注册、文档生成）会出错。
深拷贝有什么坑？文件句柄、数据库连接等资源对象无法 deepcopy，会直接报错；设计状态快照时把可序列化数据与资源对象分开。
还有哪些装饰器实战场景？计时上报（自动把耗时打到监控）、权限校验（敏感工具前置检查）、参数校验（schema 校验统一封装）、@lru_cache 缓存确定性结果。

Q31 · 手撕两数之和（O(n)，不硬搜）

思路：一次遍历哈希表。遍历时用字典记录「值 → 下标」；对当前元素先查 target - num 是否已在表中，在则直接返回两个下标，不在则记录自己继续。每个元素进出表各一次，时间 O(n)、空间 O(n)。不用暴力双循环（O(n²)）；也不用排序法——排序破坏原下标对应关系，还得额外记录原始位置。
def two_sum(nums, target):
    seen = {}
    for i, num in enumerate(nums):
        need = target - num
        if need in seen:
            return [seen[need], i]
        seen[num] = i
    return []

追问链：

追问问题回答要点
为什么边遍历边查，而不是先建表再查？边查边建保证表里只有当前元素之前的下标，天然避免「同一元素用两次」，逻辑更简洁。
有重复值怎么办？两数之和只需任意一组合法解，先命中先返回即正确；只有要求全部解时才需要专门处理重复。
扩展到三数之和呢？排序 + 双指针 O(n²)，重点是去重逻辑；哈希也能做但去重更繁琐。

Q32 · 手撕最简 ReAct loop 伪代码骨架

骨架是 think → act → observe 三态循环：think 由模型根据历史输出思考与动作；act 由外层代码解析动作、执行工具（stub 字典模拟）；observe 把结果写回历史，进入下一轮。两个终止条件：模型给出 final_answer、达到 max_steps 强制终止。核心认知：循环由外层代码驱动，模型每轮只被调用一次做决策——骨架里用 stub 替代真实模型与工具，重点展示状态切换与终止防御。
def react_loop(question, max_steps=5):
    history = [f"Question: {question}"]
    for step in range(max_steps):
        # think：模型决策下一步（此处用 stub 替代真实 LLM）
        thought, action = stub_llm(history)
        if action["tool"] == "final_answer":
            return action["content"]          # 终止条件①：模型给出最终答案
        # act：外层代码执行工具（stub 字典替代真实工具注册表）
        result = stub_tools[action["tool"]](**action["params"])
        # observe：结果回填历史
        history.append(f"Thought: {thought}")
        history.append(f"Observation: {result}")
    return "达到最大步数，强制终止"          # 终止条件②：步数上限防御

追问链：

追问问题回答要点
stub_llm 里写什么？按 history 内容返回预设决策序列（第一轮返回工具动作、第二轮返回 final_answer），验证的是循环机制而非模型能力。
真实实现还要加什么？重复动作检测（同工具 + 同参数连续出现直接终止）、整体超时；生产环境三者齐上，替换 stub 为真实 LLM 调用与工具注册表。
为什么终止条件不能只靠模型输出？模型是否说「我说完了」是概率性的；max_steps 与指纹检测是确定性闸门，必须落在循环代码里。

Q33 · 手撕区间最大并发数（会议室 II 变形）

思路：事件扫描线。每个工具调用区间 [start, end) 拆成两个事件：开始 +1、结束 -1；全部事件按时间排序（同一时刻结束事件排前，避免多算重叠），顺序扫描累加计数，过程中的最大值即峰值并发。时间复杂度 O(n log n)（排序主导）、空间 O(n)。比最小堆写法更直观，也更容易说清峰值出现在哪个时刻。
def max_concurrency(intervals):
    events = []
    for s, e in intervals:
        events.append((s, 1))    # 开始：并发 +1
        events.append((e, -1))   # 结束：并发 -1
    events.sort(key=lambda x: (x[0], x[1]))  # 同时刻结束(-1)排前
    cur = peak = 0
    for _, delta in events:
        cur += delta
        peak = max(peak, cur)
    return peak

追问链：

追问问题回答要点
为什么同时刻结束排前？一个区间结束与另一个开始同刻发生时，通常认为不重叠（资源可复用），结束排前避免多算一步；若业务定义同刻算重叠则改为开始排前——口径要主动说清。
最小堆写法怎么做？按开始时间排序，维护结束时间最小堆：每来一个新区间先弹出所有已结束的堆顶，堆大小即当前并发，全程取最大；复杂度同为 O(n log n)。
这道题在线上的实际用途？用历史工具调用区间算峰值并发，定工具服务的连接池与容量规划，也用来校验限流与熔断阈值是否设得合理。

被追问「准确率怎么算的」，如何给评测口径？

固定三段式：先说评测集来源——线上真实日志分层抽样 + 明确 guidelines 的人工标注 + 双人校验；再说指标口径——分类别 precision/recall 与 macro-F1，并解释为什么不看 accuracy（头部意图占大头时全猜头部也能拿到高 accuracy，指标好看但无信息量）；最后说可比性——冻结基线集保证版本间可比，滚动追加 badcase 保证覆盖新问题。三段说完，追问自然落到「评测集怎么更新」「标注不一致怎么办」这些你有准备的区域。

端云协同类问题的分层答法用什么框架？

三层框架：先讲约束层——时延（车控要毫秒级）、隐私（数据不出车）、离线（断网可用），这三个约束决定一切切分；再讲切分层——给一张表：车控与高频固定话术放端侧小模型，开放域与复杂推理放云端；最后讲协同层——端侧先拦截、云端返回结构化计划、端侧执行子指令，以及断网时的降级路径。按「约束 → 切分 → 协同」层层递进，答案自带结构，不容易被追问打散。

被问具体数字记不准时，怎么给量级 + 推导？

现场推导永远比背数字可信：token 消耗可以推「每轮携带完整历史，输入随步数呈等差和增长」；成本优化先按二八律拆流量结构，再说每层优化作用在哪一段流量上。引用记忆中的数据时加限定词（「量级上」「典型配置是」），并主动说明数字与哪些因素相关（窗口大小、步数、缓存命中率）——展示的是推导能力与数字敏感度，而不是背诵能力。

如何展示线上踩坑复盘而不是背概念？

每个坑按五段式讲：现象（什么告警或 badcase）、根因（哪一层机制缺失）、对策（改了什么）、效果（哪个指标变化）、沉淀（加了什么监控或流程防止再犯）。比如「Agent 无限循环导致 token 暴涨」：现象是成本告警，根因是缺确定性终止条件，对策是步数 + 预算 + 调用指纹三重防御，沉淀是 token 消耗实时看板与阈值告警。五段讲完，坑就变成了工程资产，而不是故事。
