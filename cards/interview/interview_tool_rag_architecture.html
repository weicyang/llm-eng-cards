IE-03 · 100+ 工具API的 Tool RAG 架构

核心问题

100+ 工具描述全塞 Prompt 会"爆炸"：

  • 塞不下 - 几万字 Token 成本极高，响应极慢
  • 记不住 - "迷失中间"（Lost in the Middle）
  • 会幻觉 - 选择太多反而不知道选谁（自助餐悖论）

解决方案：Tool RAG

核心思路：别全给，要什么给什么 — 基于检索的工具调用。

Step 0: 离线准备

将 100+ 工具的功能描述 → Embedding 向量化 → 存入向量数据库

（类比图书馆：先把书编号存索引）

Step 1: 用户提问

"帮我查一下现在的金价，算算买10克要多少钱"

Step 2: 向量检索（灵魂步骤）

系统计算用户问题与工具描述的相似度：

  • "查金价" → 匹配
  • "calculator" → 匹配
  • "查天气"、"查股票"... 98个 → 不匹配，丢弃

结果：Token 节省 90%，Prompt 变得干净清亮

Step 3: 动态拼装 Prompt

只将筛选出的 2 个工具定义拼入 Prompt。

Step 4: 大模型决策

在 2 个工具中选择 → 很难选错 → 准确率上升，延迟下降。

高频考点

三个核心点

  1. 思维转变 - 从 All-in 变成按需检索（少即是多）
  2. 核心技术 - Tool RAG，核心组件是向量数据库
  3. 解决痛点 - 节约 Token + 治好模型的选择困难症
