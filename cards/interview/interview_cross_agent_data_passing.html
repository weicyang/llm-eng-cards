IA-07 · 跨 Agent 结构化数据传递

提问：在多 Agent 协同场景下，你怎么保证跨 Agent 结构化数据传递的稳定性？

核心观点

核心矛盾：大模型输出的不确定性 vs 系统协同要求的确定性。模型多吐一个空格、把 JSON 写在 Markdown 代码块里，下游 Agent 就解析报错。解法是三层架构：架构层（黑板模式 + 标准协议）→ 工程层（强类型校验 + 自愈机制 + 熔断降级）→ 模型层（Tool Use + 受限解码）。

三层防御架构

Layer 1: 架构层

  • 黑板模式 / 共享状态机：Agent A 把结果填到 state 对应格子，Agent B 只读需要的格子。避免点对点杂乱通信
  • 标准化通信协议：消息带 header（来源、背景、时间戳）+ body（结构化 payload），下游不仅知道"是什么"还知道"为什么"

Layer 2: 工程层

  • 强类型反序列化校验：用 Pydantic 等库过 schema，校验失败不直接报错
  • 自行反思机制：把报错堆栈塞回发出数据的 Agent，让它自己改
  • 熔断机制：重试 3 次还搞不定 → 止损（返回默认值 / 切更强模型 / 人工介入）

Layer 3: 模型层

  • 原生工具调用（Tool Use）：模型对工具调用做过专门微调，JSON 稳定性比 prompt 里求它高一个量级
  • 受限解码（Constrained Decoding）：生成 token 时修改 logits 概率分布，强制只吐出合法字符。物理级 100% 格式正确

四大心法

心法要点
认知维度从"求模型输出正确"转向"靠系统保证正确"
防御前置受限解码的收益 > 事后反思修复
工程陷阱主动抛出幻觉字段、Markdown 污染、死循环重试等痛点
数据解耦通过数据契约协作，降低节点间耦合

高频问答

Q1: 为什么跨 Agent 数据传递不能直接传长字符串？

两个问题：(1) 上下文太乱，信息密度稀；(2) 格式不确定，模型可能多吐空格、把 JSON 包在 Markdown 代码块里。解法：引入黑板模式（共享状态机），Agent 之间不直接通信，而是通过公共 state 读写，数据流转路径清晰。加上标准化协议（header + body），解决隐性上下文丢失。

Q2: 受限解码（Constrained Decoding）的原理是什么？

在模型生成 token 时，修改 logits 概率分布。例如 JSON 下一个字符必须是双引号，就把词表中除双引号以外的所有字符概率设为负无穷。基于有限状态机或正则约束实现。这是物理级保证，哪怕 7B 小模型也能输出完美格式。

Q3: 模型一直改不对 JSON 怎么办？

三层兜底：(1) 自行反思：把报错堆栈塞回模型让它自己改；(2) 熔断机制：重试 3 次还不对就止损；(3) 降级逻辑：返回默认值 / 切更强模型 / 人工介入。这是工业级项目的底线。

Q4: 回答的核心公式是什么？

稳定性 = 受限生成（模型层）+ 严格安检（工程层）+ 全局状态管理（架构层）。展示从底座模型到业务架构的全局防御思维，而非简单的"优化 prompt"。
