IA-16 · Agent 海量 Skill 加载方案

提问：Agent 如何加载海量 Skill？

核心观点

核心结论：海量 Skill 不能全量塞进 Prompt。真正稀缺的不是 token，而是模型的注意力预算。Skill 数量一多，系统必须改成按需逐层加载。

为什么全量加载会失效

当 Skill 数量从十几个增长到上百个时，问题不再只是上下文贵，而是模型很难在一大堆工具说明里做出稳定选择。字幕里强调了两个后果：

  • 上下文里信息过多，模型知道“有很多工具”，却分不清当前到底该用哪一个
  • 工具说明写得越细，决策噪声越大，最终表现成选错 Skill 或调用参数错误

因此高分答案不能只说“做个 RAG 检索 Skill”，而是要回答 Skill 如何被分层暴露、如何避免一次性把所有说明塞给模型。

三层渐进式披露架构

层级职责输出内容
L1 元数据索引层快速知道系统里有哪些 Skill名称、标签、适用场景、输入输出概览
L2 意图理解层判断当前任务需要哪些能力候选 Skill 集合、路由结果、优先级
L3 深水执行层只对命中的 Skill 加载完整说明完整参数、边界条件、Few-shot、必要 RAG 片段

这套架构的重点是“先知道大概，再理解意图，最后展开细节”。模型在每一层只看自己真正需要的信息，所以上下文利用率和调用精度都会更稳。

工程难点

冷启动延迟

如果每次都重新检索和组装 Skill，上线后会出现首轮响应慢的问题。字幕提到的方向是结合 Prompt Cache 或 KV Cache，让稳定的公共部分尽量复用。

Skill 切换后的状态续接

切到新 Skill 时，如果历史任务状态没有保留下来，模型很容易“重新理解一遍”。因此除了 Skill 描述本身，还要保存任务快照，让新一轮执行能接上旧状态。

高频问答

Q1: 为什么不能把 100 个 Skill 全写进 System Prompt？

因为问题不只是 token 成本，更是注意力预算有限。Skill 越多，模型对每条说明分到的注意力越少，最终会出现工具选择准确率下降、参数格式错误、明明有工具却不会用的情况。

Q2: 海量 Skill 的标准架构应该怎么答？

可以按三层答：L1 建元数据索引，L2 做意图理解和候选筛选，L3 再加载完整 Skill 说明和必要示例。核心是按需逐层披露，而不是一次性全量暴露。

Q3: Skill RAG 和文档 RAG 有什么不同？

文档 RAG 解决的是内容检索，Skill RAG 检索的是工具能力、参数约束和成功样例。它服务的是“该调用谁、怎么调用”，而不是“该读哪段知识”。

Q4: 什么时候不需要这套复杂架构？

当 Skill 数量还很少、模型全量读取也稳定时，直接写进 Prompt 反而最简单。只有当技能规模突破临界点，出现失忆、误选或延迟成本明显上升时，渐进式加载才值得引入。
