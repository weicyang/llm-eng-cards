IL-03 · 单头 vs 多头 — MHA/MQA/GQA/MLA 演进

核心问题

去掉多头只用单头，Transformer 会出现什么核心问题？这里考的是：懂不懂多头本质，清不清楚工程落地难点。

单头的致命问题

单头好比一个员工同时跑销售、写代码、扫地 — 忙不过来。

  • 表达能力坍缩 - Softmax 强制平摊概率，哪儿都没关注到
  • 过平滑现象 - 输出信息变得非常模糊

多头 = 专家团队：有的盯语法（归纳头），有的盯代词指代，各司其职。

显存瓶颈与演进路线

多头虽好，但 KV Cache 是显存杀手（128K 上下文场景）。

架构KV策略显存效果
MHA 每个 Query 头独立 KV 最大 最佳
MQA 所有 Query 共享一组 KV 极小 有点笨，效果差
GQA 分组共享（如8个Query共享一对KV） 适中 当前主流（开源模型标配）
MLA 低秩矩阵分解压缩 KV 比MQA还小 超越MHA（极致降维打击）

GQA 详解

目前大模型界的"当红辣子鸡"：

  • 不像 MHA 每个 Query 有独立 KV
  • 不像 MQA 全挤在一起
  • 分组共享 - 8个 Query 头一组，共享一对 KV
  • 保留足够强大的信息检索能力 + 显存可控

MLA 详解

"数学魔法"：

  • 利用低秩矩阵分解，把 KV 压缩成很小的向量
  • 计算时动态解压
  • 用比 MQA 还小的显存，跑出超越 MHA 的性能

高频考点

满分回答三步

  1. 理论 - 单头导致表达空间坍缩和注意力分布冲突
  2. 工程 - 多头虽好但 KV Cache 是显存杀手，限制长文本
  3. 演进 - MHA → MQA → GQA → MLA 的权衡博弈
