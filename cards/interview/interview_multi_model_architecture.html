IE-01 · 多模型支持架构怎么设计？

核心问题

在实际开发中，经常遇到这样的问题：

  • 一开始用 GPT，后来业务要求换 Claude 或 DeepSeek
  • 一个系统里不只用一家模型（简单场景省钱用便宜的，复杂推理用能力强的）
  • 不同租户的要求不一样

如果代码里写死了某个模型的 SDK，每次换模型都要"伤筋动骨"改代码。

解决方案：模型网关层（三层架构）

核心思路：做一层模型网关层，像一个"万能插线板"，分为上中下三层。

上层：业务层

这一层特别"懒"，只认两个通用能力：

  • 对话（chat）
  • 向量化（embedding）

业务代码永远只调 chat 和 embedding 这两个接口，至于后面是 GPT 还是 Claude，完全不关心。

好处：未来就算把底下的模型全部换一遍，上面的代码一行都不用动。这就是"业务和模型解耦"。

中层：路由层（智能路由）

路由层的工作是把上层的请求"聪明地"分配给合适的模型。路由策略主要基于四个维度：

  1. 租户 - VIP 租户分配专属低延迟模型，普通用户走共享资源
  2. 场景 - 简单意图（如"今天天气怎么样"）走 DeepSeek（省钱快速），复杂任务（如"分析合同风险"）走 Claude 或 GPT
  3. 成本 - 根据预算动态选择模型
  4. 延迟 - 实时监控模型延迟和错误率

自动切换：如果某个模型变慢或挂了，路由层立刻把流量切换到备用模型，用户完全无感知。

动态配置：路由策略可以做成动态配置，运营同学点点鼠标就能调，不用重启服务。

底层：适配器层

这一层是一个一个独立的适配器，每个适配器只负责跟一个模型打交道：

  • GPT 适配器
  • Claude 适配器
  • Gemini 适配器
  • DeepSeek 适配器

适配器的核心工作：翻译

不同模型有不同的 API 格式、认证方法、参数名称。适配器把这些"千奇百怪"的东西全部翻译成网关内部统一的标准格式。

插拔式扩展：市面上出了新模型？只需要写一个新的适配器，往里面一插就完事了，上层和中层完全不受影响。

架构优势总结

层级 职责 特点
上层（业务层） 统一接口（chat/embedding） 业务和模型解耦，代码不用改
中层（路由层） 智能路由分配 精细控制成本，自动切换备用模型
底层（适配器层） 模型适配和翻译 新模型即插即用，扩展性强

高频考点

这道题考察什么？

  1. 系统设计能力 - 能否设计出可扩展、可维护的架构
  2. 解耦思维 - 理解"业务和模型解耦"的重要性
  3. 实际经验 - 是否真的在多模型项目中踩过坑
  4. 工程化思维 - 考虑成本、延迟、可靠性等多个维度

标准回答思路

第一步：说明问题背景 - 多模型场景下的痛点（写死 SDK、换模型要改代码、不同场景用不同模型）

第二步：提出解决方案 - 模型网关层，三层架构（业务层、路由层、适配器层）

第三步：详细说明每层职责 - 上层统一接口、中层智能路由、底层灵活适配

第四步：总结优势 - 业务解耦、成本可控、即插即用、自动切换

延伸思考

在实际落地时，还可以进一步思考：

  • 路由策略怎么动态调优？ - 可以根据历史数据自动调整路由权重
  • 模型效果怎么在线对比？ - A/B 测试，同时调用多个模型对比结果
  • 如何做 fallback 机制？ - 主模型失败时自动切换到备用模型
  • 如何监控和告警？ - 实时监控各模型的延迟、错误率、成本
