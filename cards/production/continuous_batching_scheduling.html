30 · 连续批处理

迭代级调度 / 队列模型与抢占 / Chunked Prefill / 调度预算 / 吞吐与延迟权衡 / 饥饿治理

推理引擎的性能上限不是由算子写得多快决定的，而是由"每一次前向传播里塞进了哪些请求、各塞了多少 token"这个每秒执行数十次的调度决策决定的。

大模型推理引擎有两层截然不同的优化：一层是算子层（FlashAttention、量化内核、算子融合），另一层是调度层（谁进批、谁被踢出、每步给多少预算）。前者的收益通常是 20%~50% 的常数级改善，后者的收益却常常是数倍——因为调度层决定的是 GPU 在这一秒里究竟有没有在做有效计算。本文聚焦调度层，从静态批处理的失效讲到迭代级调度，再到生产引擎里真实存在的队列、抢占、预算与饥饿问题。基础的 KV Cache 机制与 Prefill/Decode 阶段划分可参见 DP08 · KV Cache 与推理优化，本文默认读者已经理解这两个概念。

一、静态批处理的浪费：GPU 气泡从哪里来

最朴素的批处理叫 静态批处理（Static Batching），也叫请求级批处理：调度器凑齐 N 个请求组成一个 batch，一次性交给执行引擎，等这 N 个请求全部生成完毕才回收资源、组织下一批。它之所以曾经是默认做法，是因为在 CNN、BERT 这类单次前向就出结果的模型上它完全合理——batch 内每个样本的计算量一样，同进同出，没有浪费。

问题出在生成式模型的多迭代特性上。一个请求要经过一次 prefill 加上几十到几千次 decode 迭代才能结束，而每个请求的输出长度事先无法预知：有人问"今天星期几"生成 8 个 token 就结束，有人要求写一篇长文生成 2000 个 token。静态批处理把这些请求绑在同一根绳上，短请求生成完 EOS 后既不能返回给客户端，也不能释放显存，只能陪着最长的那个请求空转到底。

静态批处理把一群跑步速度不同的人用绳子绑在一起，最慢的那个决定了所有人的成绩，而且中途没人能加入。

二、迭代级调度：Orca 的关键一跃

2022 年 OSDI 上的 Orca（Yu et al., 首尔大学 & FriendliAI）系统性地解决了这个问题，提出了 迭代级调度（Iteration-level Scheduling）。它的思路直白得近乎粗暴：既然请求的粒度太粗，那就把调度粒度降到一次前向传播。调度器不再"交出一个批然后等结果"，而是每次只让引擎跑一次迭代，跑完立刻收回控制权，重新决定下一次迭代该带谁上路。

调度粒度的下沉

控制权回到调度器手里的频率，从"每个请求一次"变成了"每个 token 一次"。这个改变带来两个直接后果：生成出 EOS 的请求可以在下一次迭代边界立刻返回并释放 KV 显存；新到达的请求最多等一次迭代（几十毫秒）就能被接纳。padding 气泡因此从结构性问题变成了不存在的问题。

Selective Batching：让不同阶段的请求同批

迭代级调度落地时撞上了一个张量形状难题。要把多个请求打成一个批，就得把各自的 [L, H] 张量拼成 [B, L, H]，这要求所有请求的 L 相同。但迭代级调度下，批里有的请求在 prefill（L=2048），有的在 decode（L=1），有的 decode 进度是第 37 步而另一个是第 400 步——形状根本对不齐。

Orca 的答案是 Selective Batching（选择性批处理）：把算子分成"可批"和"不可批"两类分别处理。Linear、LayerNorm、GeLU、残差加这些逐 token 独立的算子，把所有请求的 token 拉平成一个 [ΣL, H] 的二维张量一起算，GPU 完全不关心这些 token 来自哪个请求；只有 Attention 算子必须按请求拆开单独算，因为每个请求要访问自己那份 K/V 上下文，算完再合并回扁平张量。由于 Attention 只占模型总算力的一小部分，拆开算的损失远小于批处理带来的收益。

算子类别代表算子能否跨请求合批处理方式
逐 token 独立Linear / QKV 投影 / FFN可以拉平为 [ΣL, H] 一次 GEMM
逐 token 归一化LayerNorm / RMSNorm可以同上，沿 H 维归一化不跨 token
逐元素运算GeLU / SiLU / 残差加可以同上
跨 token 依赖Attention (QKT + softmax + AV)不可以按请求拆分，各自读自己的 KV，用融合内核并行

Orca 的实测收益：论文在 GPT-3 175B 上对比 NVIDIA FasterTransformer，在相同延迟水平下吞吐提升 36.9 倍。这个数字之所以夸张，是因为它同时消掉了三件事：批内 padding 气泡、批间排队等待、以及为凑批而人为压低的并发度。业界后来实现的 Continuous Batching 在更现实的负载下通常报告 2~8 倍吞吐提升，但方向是一致的——收益来自调度，不来自内核。

Continuous Batching 的准入与退出

Orca 的机制被工业界称为 Continuous Batching（TensorRT-LLM 里叫 In-flight Batching），今天 vLLM、SGLang、TGI、TensorRT-LLM 全部默认开启。它的生命周期管理可以概括成两个动作：

  • 退出：每步执行完成后检查终止条件（采样出 EOS、达到 max_tokens、命中 stop 字符串、客户端断连）。命中即从 running 移除，立刻归还其占用的全部 KV 块到空闲池，结果立即流式返回。
  • 准入：每步调度时用剩余的 token 预算和空闲 KV 块去接纳 waiting 队列中的请求。准入不是"看槽位有没有空"，而是"KV 块分配器能不能给它分出块来"——这是很多人对 Continuous Batching 的第一个误解。

Continuous Batching 不是"批更大"，而是"批的成员在每一步都可以变"，GPU 因此永远不必为一个已经结束的请求空转。

三、调度器的队列模型与抢占策略

理解生产引擎的调度行为，最有效的切入点是看它的状态机和队列。以 vLLM V1 调度器为例，一个请求的状态迁移如下。

请求状态机与队列流转（vLLM V1） 新请求到达 │ ▼ ┌──────────────────────────────────┐ │ WAITING（waiting 队列） │ ←──────────┐ │ FCFS 或 Priority 排序 │ │ └───────────────┬──────────────────┘ │ │ 准入：KV 块分配成功 │ 抢占： │ 且 token 预算够 │ 释放全部 KV 块 ▼ │ 重置 computed ┌──────────────────────────────────┐ │ 插回队首 │ RUNNING（running 列表） │ ────────────┘ │ 每步领 token 预算，推进 prefill │ PREEMPTED │ 或 decode │ （块池耗尽 / └───────────────┬──────────────────┘ 高优先级插队） │ EOS / max_tokens / stop ▼ ┌──────────────────────────────────┐ │ FINISHED │ → 归还 KV 块，流式返回 └──────────────────────────────────┘ 另有 WAITING_FOR_REMOTE_KVS：PD 分离场景下等待远端 KV 传输到位

一步调度里究竟发生了什么

调度器每一步的工作是一个带预算的贪心分配过程，顺序很关键：

阶段动作产出
① 初始化预算设定本步 token_budget、running 请求数上限、encoder 预算本步资源天花板
② 调度 running已在跑的请求优先领预算：decode 请求领 1 个（有投机解码则 1+draft），prefill 请求领一个 chunk各请求本步 token 数
③ 分配 KV 槽调用块管理器为新 token 申请块（命中前缀缓存则跳过计算）新块映射表
④ 必要时抢占分配失败 → 挑选牺牲者，释放其 KV 块并踢回 waitingpreempted 列表
⑤ 接纳 waiting用剩余预算接纳新请求或被抢占的请求本步新增请求
⑥ 打包输出汇总块 id、token 数、连接器元数据SchedulerOutput

这里有一个常被忽略但极其重要的设计：KV 块分配发生在调度过程中，而不是调度之后。调度器不是先拍脑袋组好批、再祈祷显存放得下，而是一边决策一边真实申请块，申请不到就当场触发抢占。这意味着调度的实际约束是空闲 KV 块数量，而不只是 FIFO 顺序或并发数上限。

调度器不是排队叫号机，而是一个每 30 毫秒重新做一次的背包问题求解器，背包容量是 KV 块数和 token 预算。

抢占：recompute 还是 swap

当块池耗尽而 running 里的请求还需要新块时，调度器必须牺牲某个正在跑的请求把显存腾出来。历史上有两条路径。

维度Recompute（重算）Swap（换出到 CPU）
做法直接丢弃 KV 块，num_computed_tokens 归零，恢复时重跑 prefill把 KV 块通过 PCIe 拷到 host 内存，恢复时再拷回
释放显存速度立即（只改指针）慢，受 PCIe 带宽限制（约 25~60 GB/s）
恢复代价重跑整段 prefill，算力浪费拷回耗时，且换出/换回都占用带宽
对 GPU 流水的干扰无额外传输，可与其他请求并行拷贝期间与 decode 争抢 PCIe 和内存带宽
vLLM V1 现状默认且唯一模式已移除

vLLM V1 最终把 swap 路径整个砍掉、只保留 recompute，原因是工程实践反复证明：在有前缀缓存和分页显存的前提下，重算一段 prefill 往往比把几个 GB 的 KV 通过 PCIe 搬两趟更便宜，而且 recompute 不会污染宝贵的内存带宽——decode 阶段本来就是带宽瓶颈，swap 等于在最紧张的资源上再压一层负载。

但 recompute 有个恶性副作用：抢占循环。一个请求被抢占、重新排队、重新 prefill、又因为块不够再次被抢占——同一段 prefill 被算了三四遍，GPU 看起来 100% 忙碌，实际有效吞吐却在下降。这是生产环境最隐蔽的性能杀手，因为常规监控只看得到 GPU 利用率高，看不到里面有多少是无效重算。

生产案例（抢占风暴）：某文档问答服务用 vLLM 部署 Qwen2.5-32B（2×H100，TP=2），gpu-memory-utilization 设为 0.95，max-num-seqs 设为 384。上线后监控显示 GPU 利用率稳定在 96%，但吞吐只有压测值的 61%，p99 TTFT 从 1.2 秒恶化到 9.4 秒。排查发现 vllm:num_preemptions_total 每分钟增长 800 多次，平均每个请求被抢占 2.7 次，等于同一批 prompt 的 prefill 被重复计算近 3 遍。根因是并发数设得远超 KV 块池能承载的量：32B 模型权重占 64 GB，留给 KV 的只剩约 85 GB，而 384 路并发在平均 6K 上下文下需要 130 GB。把 max-num-seqs 降到 160、gpu-memory-utilization 回调到 0.92 后，抢占次数降到每分钟 4 次以下，吞吐回升 63%，p99 TTFT 回到 1.5 秒。并发上限不是越大越好，超过 KV 容量的那部分并发是负收益。

四、Chunked Prefill：让长 prompt 不再阻塞 decode

迭代级调度解决了请求之间的公平，但还有一个更棘手的问题：prefill 和 decode 抢同一块 GPU。一个 32K token 的长 prompt 做 prefill，如果当作一个原子的前向步来跑，可能占用 800 毫秒到 2 秒。在这段时间里，批里所有正在 decode 的请求一个 token 都吐不出来——用户看到的是流式输出突然卡住两秒。这就是批处理层的队头阻塞，也是最常见的"服务器明明不忙但输出一卡一卡"的成因。

长 prompt 阻塞 decode 的对比 【未分块】一个 32K prefill 作为原子步执行 step k : [decode×48] → 30 ms ✓ 流畅 step k+1 : [prefill 32768 tok] → 1850 ms ✗ 全体卡死 step k+2 : [decode×48] → 30 ms └─ 48 个用户的 token 流断了 1.85 秒 【Chunked Prefill】budget=4096，长 prompt 切成 8 片，与 decode 拼车 step k : [decode×48 = 48 tok] + [prefill chunk 4048 tok] → 245 ms step k+1 : [decode×48 = 48 tok] + [prefill chunk 4048 tok] → 245 ms ... step k+7 : [decode×48 = 48 tok] + [prefill chunk 4048 tok] → 245 ms └─ 每步都有 decode token 产出，ITL 抖动被压在 245 ms 内 └─ 长 prompt 的 TTFT 变成 8×245 = 1.96 s（略有增加） 本质：把"一个人卡所有人 1.85 秒"换成"这个人自己慢 0.11 秒"

调度策略：decode 优先，prefill 填缝

Chunked Prefill（分块预填充）的机制是把长 prompt 切成若干片，每片与 decode token 一起塞进同一个前向步。vLLM V1 里这已经是默认且不可关闭的行为，其调度顺序固定为：先把所有待处理的 decode 请求排完，剩下的 token 预算再分给 prefill，装不下就自动切块。

这个顺序带来两重收益。一是延迟层面，decode 永远优先意味着 ITL（Inter-Token Latency，token 间延迟） 有确定的上界，不会被任何长 prompt 打断。二是算力层面的互补：decode 是访存密集型（GPU 算力利用率常低于 10%），prefill 是计算密集型，把两者放进同一个内核批次，prefill 的矩阵乘正好填满 decode 空转的计算单元，等于免费获得了一部分 prefill 吞吐。这也是为什么关闭 chunked prefill 会显著掉吞吐。

对比维度关闭 Chunked Prefill开启 Chunked Prefill
单步耗时随最长 prompt 剧烈波动被 max_num_batched_tokens 钉死在上界
ITL 抖动大，长 prompt 到达时出现秒级卡顿小且可预测
长 prompt 的 TTFT较低（一步算完）略高（分摊到多步）
GPU 算力利用decode 步严重欠载compute-bound 与 memory-bound 混合，利用率更高
参数约束max_num_batched_tokens 必须 ≥ max_model_len两者解耦，预算可远小于上下文长度

Chunked Prefill 是拿"长 prompt 发送者自己多等一点"去换"其他所有人的输出流不被打断"，代价分摊给了肇事者而不是无辜者。

它和 PD 分离是什么关系

Chunked Prefill 和 PD 分离（Prefill/Decode Disaggregation） 解决的是同一个问题的两个层次：前者在单卡内部用时间片缓解 prefill 与 decode 的干扰，后者在集群层面用空间隔离彻底消除干扰。Chunked Prefill 部署成本为零、默认开启，应当是所有服务的起点；只有当单卡上即使分块也无法同时满足 TTFT 和 TPOT 两个 SLO 时，才需要升级到 PD 分离，详见 DP12 · Prefill / Decode 分离架构。

为什么加大 batch 提吞吐却抬高 ITL

这个权衡的物理根源在 Roofline（屋顶线模型）。decode 阶段每一步都要把整个模型权重从 HBM 读一遍，这个读取量与 batch size 无关；而算术运算量与 batch size 成正比。所以在带宽受限区间内，batch 从 1 涨到 64，单步耗时几乎不变，吞吐却涨了 64 倍——这是"免费午餐"区间。

单步耗时 ≈ max( 权重读取量 / 带宽 , batch × 每请求算力 / FLOPS )
带宽项恒定 ────── 算力项随 batch 线性增长

但 batch 继续增大会跨过拐点：算力项超过带宽项后，单步耗时开始随 batch 线性增长，吞吐涨幅趋缓，而每个用户感受到的 ITL 却在实打实地变长。更麻烦的是，batch 越大 KV Cache 占用越多，逼近块池上限后抢占频率上升，有效吞吐甚至会掉头向下。

调参的正确顺序：从 SLO 倒推，不从吞吐正推

常见错误是先跑一遍压测找 tokens/s 最大的配置然后上线，结果线上用户体验反而变差。正确做法是先定 SLO 再定预算：

  1. 明确 ITL SLO，例如"p99 相邻 token 间隔不超过 60 ms"。因为最坏情况下一个 decode token 要等一整个前向步，单步耗时必须小于 ITL SLO。
  2. 在候选预算（2048 / 4096 / 8192 / 16384）上分别实测单步耗时，画出预算-步长曲线。
  3. 选满足 SLO 的最大预算——这样在不违背延迟承诺的前提下拿到最高吞吐。
  4. 用 KV 容量公式反推 max_num_seqs：可用KV显存 ÷ 每请求平均KV大小，再打 0.8 的安全折扣。
  5. 用真实流量回放（而不是等长的合成 prompt）验证，重点看 num_preemptions_total 和 kv_cache_usage_perc 两个指标。

吞吐是给财务看的，延迟是给用户看的；调参要从用户的延迟承诺倒推预算，而不是从压测报告的峰值吞吐正推。

生产案例（预算调优）：某企业 RAG 问答服务用 vLLM 部署 Llama-3.1-8B（单卡 H100），平均 prompt 6.5K token、输出 320 token，日请求 42 万次。初始沿用默认 max_num_batched_tokens=2048，实测吞吐 4,100 tok/s，GPU SM 利用率仅 47%，长 prompt 的 TTFT 中位数 3.8 秒（6.5K prompt 要切成 4 步以上才能填完）。团队按 SLO 倒推法重新调参：ITL SLO 定为 p99 ≤ 55 ms，实测 8192 预算下单步 41 ms、16384 预算下单步 79 ms，于是选定 8192，同时把 max_num_seqs 从 256 降到 144（按 KV 容量反推）。结果吞吐升至 11,300 tok/s（+176%），TTFT 中位数降到 1.1 秒，p99 ITL 实测 48 ms 守住 SLO，单位 token 成本下降 64%。默认值是为延迟调的，不是为吞吐调的，绝大多数团队从未动过这个旋钮。

  • 先测单步耗时曲线，再按 ITL SLO 选最大可行的 token 预算
  • 用 KV 容量反推 max_num_seqs，宁可留 20% 余量
  • 把 num_preemptions_total 接入告警，抢占率是首要健康指标
  • 用真实流量回放调参，prompt 长度分布要还原线上重尾特征
  • 开启前缀缓存，共享的系统提示可直接省掉整段 prefill
  • 交互与离线流量拆成两个实例组，各用各的预算配置
  • 不要只看 tokens/s 峰值选配置，那个点的 ITL 往往已经爆了
  • 不要把 max_num_seqs 设成一个"看起来很大"的数，超出 KV 容量必抢占
  • 不要把 gpu_memory_utilization 拉到 0.98，长 prompt 峰值会直接 OOM
  • 不要用等长合成 prompt 压测后就上线，它掩盖了长短混合下的调度问题
  • 不要在同一实例里混跑"秒回聊天"和"批量摘要"两类流量
  • 不要看到 GPU 利用率 95% 就认为健康，抢占重算同样烧满 SM

六、公平性、饥饿与生产调参实战

调度器优化吞吐时，天然会牺牲一部分请求的体验。理解这些不公平从哪来，才能有针对性地治理。

三类典型的饥饿

饥饿类型成因表现缓解手段
长请求反复被抢占上下文越长占块越多，越容易被选为牺牲者，重算后又被抢占长请求延迟方差极大，偶发超时给被抢占请求重入队加权；限制单请求最大上下文
优先级反转running 列表被 max_num_seqs 占满，高优请求即使排在队首也进不来VIP 流量延迟和普通流量一样差允许高优 waiting 请求抢占最低优 running 请求

第一类值得展开。抢占本身是必要的泄压阀，但朴素实现会形成负反馈：请求 A 被抢占后 KV 块归还给块池，A 回到 waiting 队列；此时若排序只按到达时间，一个更早到达但从未开始的请求 B 会排在 A 前面被接纳，B 的新块把 A 刚释放的块吃掉，A 只能继续等——等到再次被接纳时，它那段已经算过的 prefill 必须从零重来。请求越长越容易反复踩这个坑。

工程上的修法是给被抢占的请求一个有界的重入队优先级加成：在排序键里加入抢占次数这一维，让被抢占过的请求优先于同优先级的新请求回到 running，从而保住它已完成的计算。加成必须封顶（例如最多按 3 次计），否则一个永远放不下的超长请求会反过来把整个队列锁死，形成活锁。

被抢占请求的重入队排序（有界加成） 排序键 = ( 用户优先级, -min(抢占次数, 3), 到达时间, 请求ID ) ↑ ↑ ↑ 严格遵守用户 保护已完成的 同档位内 定义的优先级 prefill 计算 仍按 FCFS 场景：A 被抢占过 1 次(已算 4K prefill)，B 是新请求(到达更早) ───────────────────────────────────────────────────────── 无加成： key(B)=(0, 0, t=10) < key(A)=(0, 0, t=12) → B 先进 结果：A 的 4K prefill 被浪费，需重算 有加成： key(A)=(0,-1, t=12) < key(B)=(0, 0, t=10) → A 先进 结果：A 保住已算部分，B 稍后进入，总算力消耗更低 注意：加成不跨优先级档 —— 高优先级的新请求依然排在 低优先级的被抢占请求之前，用户语义不被破坏

抢占是泄压阀不是惩罚机制，被抢占过的请求应该更容易回来，否则系统会陷入"反复算同一段 prefill"的空转。

优先级调度与它的坑

把排序策略从 FCFS 换成 priority 后，waiting 队列变成按 (优先级, 到达时间) 排序的堆。但只改队列排序解决不了全部问题：如果瓶颈是 max_num_seqs 已满而不是 KV 块不足，调度器的接纳循环会直接跳出，高优请求只能干等低优请求自然结束。要真正保障优先级，必须允许高优 waiting 请求主动抢占优先级最低的 running 请求。

实现这件事有两个容易踩的细节。其一，判定是否可抢必须严格比较优先级数值，不能复用带到达时间兜底的通用比较逻辑——否则同优先级的两个请求会因为到达时间差异互相抢占，在调度步之间来回拉锯（ping-pong），谁都推进不了。其二，抢占应该放在其他准入检查之后，避免为一个本步无论如何都进不来的请求白白牺牲一个正在跑的请求。

生产案例（优先级隔离）：某 AI 客服平台在同一个 vLLM 集群上同时承接实时人工坐席辅助（要求 TTFT < 800 ms）和夜间批量工单摘要（无延迟要求，prompt 长达 24K token）。混跑期间实时流量的 p99 TTFT 高达 6.7 秒，严重违约，原因是批量任务的长 prefill 持续吃满 token 预算，且 running 槽位被 200 多个批量请求长期占据。改造分三步：一是切到 priority 调度策略并允许高优请求抢占；二是把 long_prefill_token_threshold 设为 2048、max_long_partial_prefills 设为 1，限制同一步里只能有一个长 prefill 推进；三是给批量任务单独设置较低的 max_num_seqs 配额。改造后实时流量 p99 TTFT 降到 640 ms（下降 90%），批量任务的完成时间从 4.1 小时延长到 5.3 小时（可接受），集群 GPU 数量未变，避免了为隔离而新增 8 张卡的支出。

Q&A

Continuous Batching 和把 batch size 调大是一回事吗？
不是，两者正交。调大 batch size 改变的是"一次装多少个请求"，Continuous Batching 改变的是"批的成员能不能中途变动"。静态批处理即使 batch 开到 256，只要有一个请求要生成 2000 个 token，其余 255 个槽位在它们各自结束后就一直空转到最后，利用率反而更差。Continuous Batching 把调度粒度降到一次前向传播，请求生成出 EOS 就立刻离开并归还 KV 块，等待中的请求马上补位，所以批是"满的且一直在换人"。实践中两者要一起用：Continuous Batching 提供动态换人的能力，batch 上限决定同时能装多少人，后者必须按 KV 容量来定而不是越大越好。
Orca 的 Selective Batching 为什么必要？直接把所有请求 padding 到同一长度不行吗？
padding 方案在迭代级调度下代价高得离谱。批里可能同时有一个在做 8K prefill 的请求和 40 个只处理 1 个 token 的 decode 请求，若统一 padding 到 8192，那 40 个 decode 请求各自要浪费 8191 个位置的算力，等于把批处理的收益全部抵消。Selective Batching 的做法是按算子性质分治：Linear、LayerNorm、GeLU 这类逐 token 独立的算子，把所有请求的 token 拉平成一个 [ΣL, H] 二维张量一起算，完全不需要形状对齐；只有 Attention 因为要各读各的 KV 上下文而必须按请求拆开，用融合内核为每个请求分配独立线程块并行处理，算完再合并回扁平张量。由于 Attention 只占总算力的小部分，这个拆分的开销远小于 padding 的浪费。
为什么 vLLM V1 只保留 recompute 抢占而删掉了 swap？
Swap 是把被抢占请求的 KV 块通过 PCIe 拷到主机内存，恢复时再拷回来。它的问题有三层：一是 PCIe 带宽只有 25~60 GB/s，搬几个 GB 的 KV 需要上百毫秒，释放显存的速度跟不上抢占的紧急程度；二是拷贝会占用内存带宽，而 decode 阶段本身就是带宽瓶颈，等于在最紧张的资源上再加负载，会拖慢批里所有其他请求；三是它带来一套额外的状态管理复杂度（换出块的追踪、部分换出、换回失败处理）。相比之下 recompute 只需丢弃块指针、把已计算 token 数归零，释放是瞬时的，重算又能享受分页显存和前缀缓存的加速。工程权衡下来，重跑一段 prefill 通常比搬两趟 KV 更便宜，所以 V1 直接砍掉了 swap 路径。
Chunked Prefill 会不会让长 prompt 的 TTFT 变差？这个代价值得吗？
会变差，但通常值得。长 prompt 的 prefill 被切成多片后要跨多个调度步才能完成，每步还要和 decode token 分享预算，所以它自己的 TTFT 会上升，典型幅度在 5%~20%。换来的是批里其他所有正在 decode 的请求不再被打断——不分块时一个 32K prefill 可能让全体用户的输出流卡住一两秒，分块后单步耗时被 max_num_batched_tokens 钉在上界，ITL 抖动可预测。这笔交易的本质是把成本从"无辜的其他用户"转移到"发送长 prompt 的那个人"身上，符合公平直觉。而且分块还带来一个额外好处：prefill 是计算密集型、decode 是访存密集型，混进同一批能填满 decode 空转的计算单元，整体吞吐反而更高。如果确实无法接受长 prompt 的 TTFT 上升，正确的升级路径是 PD 分离而不是关掉分块。
max_num_batched_tokens 和 max_num_seqs 有什么区别？该先调哪个？
前者是每步的 token 预算，控制单个前向步能处理多少个 token（decode 的和 prefill chunk 共享这个预算），它直接决定单步耗时，因而决定 ITL 上界。后者是 running 列表能同时容纳多少个请求，它决定并发度和 KV 显存压力。调参顺序应该是先定 max_num_batched_tokens：从 ITL SLO 出发，实测各候选值下的单步耗时，选满足 SLO 的最大值。再定 max_num_seqs：用"可用 KV 显存 ÷ 每请求平均 KV 大小"反推并打八折。原因是前者受延迟约束、后者受显存约束，两个约束彼此独立；若顺序颠倒，很容易设出一个并发很高但每步都在抢占的配置。
为什么增大 batch 能提吞吐，却会抬高 ITL？临界点在哪？
根源在 decode 阶段是访存受限的。每个 decode 步都必须把整个模型权重从显存读一遍，这个读取量与 batch size 无关；而算术运算量与 batch size 成正比。所以在 batch 较小时，单步耗时被"读权重"这一项主导，batch 从 8 涨到 64 单步耗时几乎不变，吞吐却涨了 8 倍，这是免费午餐区间。越过某个拐点后，算术项超过访存项，单步耗时开始随 batch 线性增长，吞吐涨幅趋缓而 ITL 实打实变长。拐点位置取决于模型大小、GPU 的算力/带宽比和序列长度，7B 模型在 H100 上大致落在 batch 64~128 之间，必须实测。还要注意第三个区间：batch 大到 KV 块池装不下时会触发抢占重算，此时有效吞吐会掉头下降，是必须避开的区域。
线上 GPU 利用率一直 95% 以上，吞吐却上不去，可能是什么原因？
最常见的元凶是抢占重算风暴。当并发数超过 KV 块池能承载的量，调度器会不断抢占正在跑的请求腾显存，被抢占的请求丢弃 KV 后重新排队、重新 prefill，然后可能再次被抢占。同一段 prompt 的 prefill 被算了两三遍，GPU 的计算单元确实是满负荷的，所以利用率指标很好看，但其中相当比例是无效重算。诊断方法是看抢占计数器（vLLM 里是 vllm:num_preemptions_total）和 KV Cache 使用率：如果抢占每分钟数百次、KV 使用率长期贴着 100%，基本可以确诊。处置方式是降低 max_num_seqs 到 KV 容量能支撑的水平，或者把 gpu_memory_utilization 从 0.95 回调到 0.92 留出缓冲，也可以通过 KV 量化和前缀缓存来扩大有效容量。GPU 利用率永远不能单独作为健康判据。
长请求总是被反复抢占导致超时，怎么治？
这是抢占机制的负反馈效应：上下文越长占的 KV 块越多，越容易被挑为牺牲者；被抢占后如果队列只按到达时间排序，更早到达但尚未开始的新请求会排在它前面把块吃掉，它只能继续等，等到再被接纳时那段已算的 prefill 必须从零重来。治理方式有三层。调度层面，给被抢占的请求一个有界的重入队优先级加成，让它优先于同优先级的新请求返回 running，从而保住已完成的计算；加成必须封顶（比如最多按 3 次抢占计），否则一个永远放不下的超长请求会锁死整个队列。容量层面，从根上减少抢占——降并发、开 KV 量化、开前缀缓存。业务层面，对超长上下文请求单独限流或路由到独立实例组，避免它们和短请求争抢同一个块池。
开启 priority 调度策略后，高优先级请求仍然排队很久，为什么？
因为把队列排序改成按优先级，只解决了"谁先被考虑接纳"，没解决"接纳不进去怎么办"。如果此刻的瓶颈是 running 列表已经装满到 max_num_seqs，调度器的接纳循环会直接跳出，高优请求哪怕排在队首也只能等某个低优请求自然生成完 EOS 才有空位——这就是优先级反转。要真正兑现优先级承诺，调度器必须支持高优 waiting 请求主动抢占优先级最低的 running 请求。实现时有两个坑：一是判定可抢必须严格比较优先级数值，不能用带到达时间兜底的通用比较，否则同优先级的两个请求会因到达时间不同互相抢占、在调度步之间来回拉锯；二是抢占动作要放在其他准入检查通过之后，避免为一个本步反正也进不来的请求白白牺牲一个正在跑的请求。
怎么从零开始给一个新服务定调度参数？
按五步走。第一步定 SLO，明确 TTFT 和 ITL 的 p99 目标，这是所有决策的锚点。第二步测单步耗时，在 2048、4096、8192、16384 几个候选预算下分别实测一次前向步的耗时，因为最坏情况下一个 decode token 要等一整个前向步，单步耗时必须小于 ITL SLO。第三步选预算，取满足 SLO 的最大值，这样在守住延迟承诺的前提下拿到最高吞吐。第四步算并发，用"总显存 × 利用率 − 权重 − 激活预留 = 可用 KV 空间"，再除以每请求的平均 KV 大小，结果打八折作为 max_num_seqs。第五步做真实流量回放，用线上采样的 prompt 长度分布（不要用等长合成数据，它会掩盖长短混合下的调度问题）跑压测，重点观察抢占次数和 KV 使用率，二者异常就回退并发。上线后持续监控这两个指标即可。
