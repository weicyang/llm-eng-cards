一、为什么需要推理框架：三大痛点

推理框架之间的差异不是简单的"谁快谁慢"，而是每家都在回答一个不同的问题：vLLM 回答"显存碎片和调度空转怎么办"，SGLang 回答"重复计算怎么办"，TGI 回答"如何低成本接入企业体系"，llama.cpp 回答"没有 GPU 怎么办"。选型的本质，是先搞清楚你的负载被哪个问题卡住。

先铺垫瓶颈背景（详细推导见姊妹篇《大模型推理性能瓶颈分析》）：LLM 推理分为 Prefill（预填充，一次性并行处理全部输入 token，算力密集）和 Decode（逐 token 生成，每步都要把全部权重从显存读一遍，显存带宽密集）两个阶段。为了不让 Decode 每步重算历史注意力，必须维护 KV Cache——缓存每一层注意力的 Key/Value 向量，其显存占用随序列长度和并发数线性增长。单个请求运行时 GPU 利用率极低，只有把多个请求攒成 batch 才能摊薄权重读取成本。这三个事实，直接决定了推理框架要解决的三大痛点。

朴素部署的三个坑

直接拿 Hugging Face transformers 的 model.generate() 起服务，会立刻撞上三堵墙：

  • 显存碎片严重：朴素实现按"最大可能长度"（如 4096 token）为每个请求预分配连续 KV Cache，而多数请求实际只用 200~500 token，60~70% 的显存被"占着不用"。一台 80GB 显存的机器理论能扛 100 并发，实际往往只能扛 30 个。
  • 静态批处理空转：凑齐一批请求一起跑、一起结束，短请求被迫等长请求，GPU 大量时间在"跑了一半干等"。
  • 共享前缀重复计算：所有用户共用同一段 System Prompt（动辄上千 token），朴素实现每次都重新算一遍这段 KV Cache，纯浪费。

四大框架分别从一个方向突破：vLLM 用分页显存 + 迭代级调度解决前两个痛点，SGLang 用前缀树解决第三个，TGI 把重心放在生态集成与企业运维，llama.cpp 则彻底换赛道——让模型离开 GPU 也能跑。

💡 知识要点：判断选型的第一步不是看 benchmark 排行榜，而是给负载画像——并发量多大、prompt 前缀重复率高不高、上下文多长、有没有 GPU、数据能不能出域。这五个问题的答案，基本就锁定了候选框架的范围。
把四个框架想成四种交通工具：vLLM 是高速公路（大运量、高时速），SGLang 是带 ETC 专用道的高速公路（重复路线自动免费），TGI 是品牌 4S 店专车（服务全套、省心但贵一点），llama.cpp 是越野车（慢一些，但没有路的地方只有它能去）。没有最好的车，只有对的路。

二、vLLM：PagedAttention 与吞吐之王

vLLM 由 UC Berkeley 团队于 2023 年开源，是当前生产环境部署 LLM API 的事实标准。它的立身之本是 PagedAttention——借鉴操作系统虚拟内存分页机制来管理 KV Cache：把 GPU 显存切成固定大小的物理块（Block，典型容量 16 个 token 的 KV），每个请求持有自己的"逻辑块序列"，再通过一张块表（Block Table）映射到实际物理块。请求用了多少 token 就占多少块，生成完立刻归还，彻底摆脱"按最大长度预分配"的浪费模式。

传统连续分配（预分配 max_seq_len = 4096 tokens）： 请求A(实际 300 tok): [███░░░░░░░░░░░░░░░░░░░] 占 4096 位空间，浪费 93% 请求B(实际 800 tok): [██████░░░░░░░░░░░░░░░░] 占 4096 位空间，浪费 80% 请求C(排队中): 剩余空间全是碎片，无法分配 → 并发被"假性占满"压低 PagedAttention 分页分配（Block = 16 tokens）： 逻辑视图 Block Table 物理显存（无需连续） 请求A: 逻辑块 0~18 A → [7, 23, 41, ...] → [7]A [23]A [41]A ... 请求B: 逻辑块 0~49 B → [2, 8, 55, ...] → [2]B [8]B [55]B ... 请求C: 按需增长 C → 从空闲块池取用 → 随取随还，零等待 结果：显存浪费从 60-80% 压到 4% 以下，同硬件并发提升 2-4 倍

第二件武器是连续批处理（Continuous Batching）：不再等整个 batch 跑完，而是每个生成步骤（iteration）都允许完成的请求退出、新请求插入 Prefill，GPU 永不空转。PagedAttention 管"空间"，连续批处理管"时间"，两者叠加构成了 vLLM 的吞吐护城河。

分配方式显存浪费可支撑并发典型吞吐表现
传统连续预分配60-80%低（被碎片锁死）基准（HF generate）
PagedAttention 分页<4%提升 2-4 倍对朴素实现最高 24 倍，对 HF Transformers 14-24 倍

数字说明一切：PagedAttention 原始论文在变长序列负载上报告了相对朴素实现最高 24 倍的吞吐提升；工程实践中 vLLM 相对 HF Transformers 原生推理通常有 14-24 倍差距，单卡支撑 100+ 并发请求。更关键的是它开源了 OpenAI 兼容 API，几乎成为所有 RAG 框架的默认后端。

生产案例：金融问答机器人 8×H800A 调优实录。某金融客户在自有 8×H800A 节点上部署 Qwen3-72B-Instruct（AWQ 4-bit 权重），要求 P95 首 token 延迟 ≤800ms、200 RPS 持续。基线 vLLM（仅开张量并行）只有 1820 tok/s，P95 TTFT 1.4 秒，GPU 利用率约 62%。三步调优后脱胎换骨：① 打开迭代级连续调度，吞吐升至 3120 tok/s，TTFT 降到 0.9 秒；② 针对约 800 token 的共享 System Prompt 开启前缀缓存，缓存命中率从 12% 拉到 71%，TTFT 进一步降到 380ms；③ 权重与 KV 换 FP8，吞吐冲到 4520 tok/s，单卡权重占用从 38GB 降到 31GB，BLEU/ROUGE 回归偏差 <0.3%。最终单节点日处理约 3.9 亿 token，相当于替代 6 台 A100 节点——而这一切不需要换任何硬件。

PagedAttention 的伟大之处不在算法本身有多精妙，而在于它把操作系统几十年沉淀的内存管理智慧（分页、按需分配、用后归还）平移到了显存。显存是推理系统里最贵的资源，谁把显存利用率从 30% 拉到 90%+，谁就能在同一块卡上卖出 3 倍的服务。

三、SGLang：RadixAttention 与前缀复用

SGLang 由 LMSYS（Vicuna、Chatbot Arena 背后的团队）于 2024 年推出，它不打算在所有场景替代 vLLM，而是专攻 vLLM 早期没解决好的一个问题：多请求之间的共享前缀。其核心创新 RadixAttention 把所有请求的 KV Cache 组织成一棵基数树（Radix Tree）：多个请求开头相同的 token 序列共享同一条树路径，KV 只计算一次、只存储一份；树节点按 LRU 策略淘汰，请求结束后 KV 不立即销毁，后续请求还能"捡现成的"。

Radix Tree 前缀共享（SGLang 的 KV Cache 组织方式）： [根] │ ┌──────────┴──────────┐ │ System Prompt │ ← 全部请求共享：只算一次、只存一份 │ (1000 tokens) │ └──────────┬──────────┘ ┌────────────────┼────────────────┐ │ │ │ [Few-shot 示例] [对话历史·用户X] [对话历史·用户Y] │ │ │ [查询 q1] [第 3 轮提问] [第 5 轮提问] • 100 个用户带同一 System Prompt → 前缀 KV 只存 1 份（vLLM 早期要存 100 份） • 用户 X 的第 4 轮：前 3 轮 KV 树中命中，Prefill 只算增量部分 • 缓存感知调度器优先安排"共享前缀更长"的请求，进一步推高命中率

这套机制同时省下两种成本：显存（按所有请求前缀的并集存储，而非各自求和，高重复场景省 50-80%）和计算（命中即跳过 Prefill，直接省掉首 token 前的那段等待）。配合缓存感知调度，实际命中率相当可观：

负载类型典型前缀缓存命中率收益来源
Few-shot 批量提示85-95%固定示例前缀几乎全命中
多轮对话75-90%历史轮次逐轮累积复用
代码分析 / Agent 循环60-80%共享 System Prompt + 工具上下文
混合生产流量50-70%视业务前缀重复率而定

性能数据层面，2025-2026 年的多方基准显示 SGLang 在 H100 上跑 Llama-2-70B（batch 256）可达约 16,200 tok/s，较 vLLM 的约 12,500 tok/s 高 29%，输出 token 速率更是高出约一倍，TTFT 领先 15-23%；在前缀重度负载（RAG、多轮）上提升最高可达 6.4 倍；作为 DeepSeek 官方推荐引擎，跑 DeepSeek V3 有 3.1 倍优势。但必须说清边界：当 prompt 毫无共享时（纯批处理、每个请求都不同），RadixAttention 收益归零，有实测在这种负载下 vLLM 反而小幅反超（60 vs 52.7 tok/s）。

SGLang 的第二张牌是约束解码（Constrained Decoding）带来的结构化输出加速：内置压缩有限状态机（FSM），在解码时逐步屏蔽不合法 token，保证 JSON / 正则输出 100% 合法，且语法掩码生成与模型前向重叠执行，比普通 guided decoding 快约 3 倍。无约束生成时 LLM 的 JSON 合规率通常只有 90-94%，靠事后校验重试要额外付出 20-50ms；FSM 约束下合规率升到 96-98%，整个重试类别直接消失。

生产案例：多轮客服对话机器人从 vLLM 迁移到 SGLang。某客服平台的对话机器人平均每会话 12 轮、共享约 1500 token 的 System Prompt 与业务知识前缀，原先跑在 vLLM 上，每轮都要对大段重复前缀重算 Prefill，高峰期 TTFT 恶化到 600ms 以上。在同一 H100 集群、同一模型、同一流量下切换到 SGLang 后：前缀缓存命中率稳定在 80% 左右，TTFT 降到约 260ms（-57%），总吞吐提升 30% 以上，按新流量峰值核算直接退租了约四分之一的 GPU 实例，每月节省五位数美元级开销——而应用层只改了 base URL（两者 API 均为 OpenAI 兼容）。
vLLM 的哲学是"用完即还"——请求结束，KV Cache 立即释放；SGLang 的哲学是"先别扔"——KV Cache 从单请求的消耗品变成了跨请求的资产。多轮对话、Agent、RAG 这些负载天然前缀重复，谁复用得越狠，谁就越省。

四、TGI：Hugging Face 生态的稳妥之选

TGI（Text Generation Inference）是 Hugging Face 在 2022 年推出的推理服务，设计目标非常明确：让 HF Hub 上的任何模型"一键"变成生产级 API。它当然也支持连续批处理、量化（GPTQ/AWQ）与流式输出这些现代引擎的标配，但它的核心卖点从来不是极限吞吐，而是生态集成与企业级运维特性。

能力类别TGI 提供对企业的意义
模型接入直接读 Hub 模型 ID 自动下载，兼容 safetensors / 量化配置 / chat template零格式转换成本，Hub 模型即取即用
服务协议HTTP + gRPC 双协议、SSE 流式响应对接既有微服务体系
运维特性Token 鉴权、Prometheus metrics、健康检查、优雅重启直接嵌入现有监控与发布流程
性能能力连续批处理、张量并行、多格式量化中并发场景完全够用

性能定位需要客观看待。2025 年 11 月的一项系统性对比研究（LLaMA-2 7B~70B，多并发档位压测）显示：高并发下 vLLM 吞吐优势最大可达 24 倍（小模型极端负载），在 LLaMA-2-13B 最优并发下为 8,934 vs 3,187 tok/s（约 2.8 倍）。但同一研究也指出，在单用户、交互式的中低并发场景，TGI 的尾延迟反而更低更稳。换句话说，TGI 的调度策略更偏"保个体体验"而非"榨极限吞吐"。

场景是否适合 TGI原因
公司已是 HF 全家桶（数据集/Transformers/Hub）✅ 非常适合迁移成本几乎为零
快速 POC，不想折腾框架✅ 适合Docker 一键起，企业特性现成
追求极限吞吐的高并发 API⚠️ 不是首选高并发吞吐落后 vLLM/SGLang
单用户交互式应用、对尾延迟敏感✅ 可考虑中低并发尾延迟表现稳
TGI 卖的不是"最快"，而是"最顺"。当团队的模型来自 Hub、监控用 Prometheus、流程要审计鉴权时，TGI 把推理服务变成了 HF 生态里一个"原生零件"。选型时如果性能差距在可接受范围内，组织惯性和集成成本往往才是决定项。

五、llama.cpp：GGUF 量化与端侧部署

llama.cpp 是 Georgi Gerganov 于 2023 年初启动的个人项目，如今已成为"让大模型离开 GPU"的事实标准——Ollama 的底座正是它。设计哲学与前三者完全不同：用纯 C++ 重写整个推理栈，零外部依赖，针对各种 CPU 指令集（AVX2、AVX512、ARM NEON）手工优化矩阵乘法内核，再配上 CUDA / Metal / Vulkan 后端，让同一套二进制在服务器、MacBook、树莓派和手机上都能跑。

它的模型载体是 GGUF（GPT-Generated Unified Format）——把权重、量化方案、分词器与元数据打包进单个文件，支持 mmap 按需加载，是开源量化模型的事实交换格式（HF 官方与各大模型仓库均直接提供）。配套的 量化档位体系是端侧部署的核心抓手：把 FP16 权重压到 3~8 bit，体积砍掉一半以上，换来 CPU/低显存设备上的可运行性。

量化档位比特数体积（相对 FP16）质量损失典型用途
Q8_08-bit约 50%几乎无损质量优先、资源尚可
Q5_K_M5-bit约 33%极小精度与体积平衡
Q4_K_M4-bit约 25-30%<2%（困惑度保留 ~99%）默认甜点，最常用
Q3_K_S3-bit约 20%可感知极端压缩、内存受限
Q2_K2-bit约 15%明显退化只追求"能跑"

端侧性能比很多人想象得好：4 核 Xeon + OpenBLAS 编译的 llama.cpp 跑 Mistral 7B Q4_K_M 可稳定输出 52 tok/s（Q2_K 更快到 68 tok/s 但质量下滑）；BLAS 加速编译比朴素编译快 2-3 倍；Llama-3 8B 量化到 Q4 后内存占用不到 6GB，跑在一台每月 10 美元的 CPU 云服务器上毫无压力。Apple Silicon 的统一内存架构更是如鱼得水——M3 Max（128GB 统一内存）可以直接跑 70B 模型，这让 llama.cpp 在 Mac 用户中极其流行。但边界同样清晰：llama-server 提供 OpenAI 兼容接口，却没有 vLLM 式的连续批处理，并发调度能力弱，在 DeepSeek-R1-32B 的 A100 对比测试中吞吐约 1,100 tok/s（SGLang 2,850、vLLM 2,400），高并发生产 API 不是它的战场。

场景是否适合 llama.cpp说明
个人本地 / Mac 玩模型✅ 首选Metal 后端吃满统一内存
边缘 / 嵌入式（树莓派、Jetson、手机）✅ 首选ARM NEON 优化、二进制极小
离线 / 隐私敏感（数据不出设备）✅ 首选断网可用，无按 token 计费
高并发生产 API❌ 不适合无连续批处理，并发吞吐撑不住
多卡 GPU 大集群❌ 不适合非其设计目标
llama.cpp 把一件事做到了极致："先跑起来"。它不追求数据中心里每瓦特的极限吞吐，而是把 7B 模型塞进 MacBook、把 4-bit 模型塞进 6GB 内存——当部署环境没有 GPU 时，它常常是唯一的答案，而不是退而求其次的答案。

选型决策的上一层还有一个更根本的问题：要不要自建。云托管 API（OpenAI、Claude、国内各家大模型云服务）与自建推理服务的边界，主要由调用量级、数据合规与控制力需求决定：

  • 用真实业务流量分布在候选框架上压测，再定版本号
  • 统一走 OpenAI 兼容 API，为后续换框架留一条 base URL 的后路
  • vLLM/SGLang 上线即开前缀缓存，这是几乎免费的性能
  • 端侧部署默认 Q4_K_M，编译时开 BLAS/Metal，服务加 --mlock 防换页
  • 监控显存利用率、KV 缓存命中率与 TTFT P95，而不只是 GPU 利用率
  • 不要只看单一 benchmark 数字下单（版本、卡型、负载形状都会改写结论）
  • 不要用 llama.cpp 扛高并发生产 API（没有连续批处理）
  • 不要在纯唯一 prompt 的批处理上为前缀缓存多付复杂度
  • 不要在没算清调用量拐点前盲目自建（低流量时云 API 更便宜）
  • 不要忽视 KV Cache 量化等特性的版本差异（"支持"二字各版本含义不同）
  • 不要把 MoE 大模型直接上生产（专家并行配置复杂，先在测试环境跑通）
选型决策 80% 由负载形状决定，15% 由硬件与预算决定，只剩 5% 留给框架的纸面差距。框架每年都在互相学习对方的优点，但"你的 prompt 前缀重复率高不高""有没有 GPU""数据能不能出域"这三个问题的答案，明年也不会变。

Q&A

PagedAttention 和 RadixAttention 的本质区别是什么？

两者解决的是不同层次的问题。PagedAttention 解决"单个请求内部的显存碎片"：把 KV Cache 切成固定大小的块按需分配，用块表做逻辑到物理的映射，把显存浪费从 60-80% 压到 4% 以下。RadixAttention 解决"多个请求之间的重复计算"：把所有请求的 KV 组织成基数树，相同前缀只计算一次、只存一份，请求结束后还按 LRU 保留供后续复用。两者并不冲突——SGLang 底层同样是分页显存管理，只是在分页之上又加了一层跨请求的前缀树索引。一句话：PagedAttention 让每个请求少占显存，RadixAttention 让多个请求少做重复功。

为什么多轮对话场景下 SGLang 的首 token 延迟能比 vLLM 低 2-3 倍？

多轮对话的每一轮请求都要携带完整的历史上下文，而相邻两轮之间大部分内容是重复的。没有跨请求缓存的引擎每次都要对这大段重复前缀重新做 Prefill，首 token 延迟随轮数越滚越长。SGLang 的基数树会在树中命中前几轮已经算好的 KV，Prefill 只需要计算本轮新增的少量 token，再配合缓存感知调度器把共享前缀长的请求优先排上，命中率可达 75-90%。这就是"历史越长越省"的反直觉现象：对话越深入，RadixAttention 的相对优势越大。

TGI 的吞吐不是最强的，为什么仍有团队选它？

因为选型不只看吞吐。TGI 直接读 HF Hub 模型 ID 自动部署，兼容 safetensors、量化配置和 chat template，省掉格式转换；自带 Token 鉴权、Prometheus 指标、健康检查、gRPC/SSE 等企业级特性，能无缝嵌进既有监控与发布流程。对已经深度使用 Hugging Face 生态的团队，这些集成价值远超百分之几十的吞吐差距。实测也显示在中低并发的单用户交互场景，TGI 的尾延迟反而更稳。它的定位是"最顺"而不是"最快"。

llama.cpp 能不能用来做高并发生产服务？

不建议。llama.cpp 的设计目标是让模型在 CPU 和端侧设备上跑起来，它的 llama-server 虽然提供 OpenAI 兼容接口，但缺少 vLLM 式的连续批处理，请求调度能力弱，并发一多吞吐就撑不住。同一硬件的对比测试里它的吞吐只有 vLLM/SGLang 的一半不到。它的正确战场是：个人本地使用、Mac 上的 Metal 加速、树莓派/手机等嵌入式设备、以及对数据不出域有硬要求的离线场景。高并发在线服务还是 GPU + vLLM/SGLang 的组合。

自建推理服务和直接调用云 API，边界在哪里？

主要看三个变量：调用量级、数据合规、控制力需求。POC 阶段和日调用几百万 token 以内，云 API（OpenAI、Claude、国内各家大模型云服务）按量付费、零运维，是最优解；成本随调用量线性上涨，但绝对值可控。当日调用量稳定到数千万 token 级别，自建的 GPU 摊销成本开始低于 API 账单；当数据有出域红线（金融、医疗、军工、核心工艺文档），自建几乎是唯一选择；当需要微调模型、冻结版本、定制量化时，也只有自建能满足。实践中常见路径是先用云 API 验证业务，流量和合规压力上来后再迁移自建，接口走 OpenAI 兼容协议可以把迁移成本压到最低。

GGUF 量化档位这么多，为什么默认推荐 Q4_K_M？

Q4_K_M 是精度、体积、速度三者的平衡点。它采用 K-quant 分组混合精度策略，把关键权重保留更高精度，困惑度能保留约 99%，而体积只有 FP16 的 25-30%，质量损失通常不到 2%。往上 Q8_0 几乎无损但体积只省一半，端侧设备常常装不下；往下 Q2_K/Q3_K_S 体积更小、速度更快，但质量退化肉眼可见，只适合"能跑就行"的场景。所以 CPU 和端侧部署默认从 Q4_K_M 起步，再根据实测质量上下调一档。

网上的 vLLM vs SGLang 基准数字能直接拿来选型吗？

不能直接照搬，只能当参考量级。推理框架的吞吐和延迟对引擎版本、GPU 驱动、量化格式、请求分布极其敏感，同样配置换个版本结果漂移 20-50% 很常见，各家的"官方基准"又往往挑了对自己有利的负载。靠谱的做法是：先明确自己的负载形状（输入/输出长度分布、并发量、前缀重复率），然后在候选框架上用真实流量分布做压测，锁死版本号和硬件配置再对比。架构层面的结论（谁擅长前缀复用、谁擅长高并发、谁能跑 CPU）比具体数字稳定得多，应该以架构结论圈定候选，用自测数字做最终裁决。

既有前缀重度的多轮流量，又有唯一 prompt 的批处理流量，怎么选？

混合负载下越来越常见的做法是双引擎 + 路由层：多轮对话、RAG、Agent 这类前缀重度流量路由到 SGLang，吃满 RadixAttention 的缓存红利；prompt 互不重复的批量生成任务路由到 vLLM，发挥它的吞吐与生态优势。两个引擎都提供 OpenAI 兼容 API，应用层只面对一个统一入口，切换与灰度都只是路由配置的改动。代价是要维护两套推理后端的版本与监控，团队规模小、负载单一时不建议过早引入这套复杂度。
