32 · 流式传输

Streaming Five Layers — 为什么必须流式 / 四大协议选型 / 五层技术架构 / 断点续传与容灾 / 生产级技术栈 / 能力评估

大模型流式传输不是一个单独的技术问题，而是一个五层递进的工程体系：从 EventSource 三行代码起步，到断线重连的数据丢失陷阱，到断点续传的三种补救方案，再到 WebSocket 双向协议替代，最终在生产级技术栈中将心跳保活、rAF 批量渲染、Markdown 分段、本地缓存兜底融合为一套完整方案。每一层都是前一层的"缺陷补丁"。

一、为什么 LLM 必须流式输出：四大数据铁证

传统请求-响应模型对大模型场景极不友好。完整生成可能需要 8-30s，而用户期望立刻看到反馈。以下是 2026 年生产环境的实测数据：

指标非流式流式差距
首字延迟 TTFT8-30s150-300ms10-100x 改善
用户感知速度"系统卡死了""正在生成"体感天壤之别
中途可中断不可能随时停止节省无效 token 费用
用户放弃率TTFT > 1.5s 时激增200ms 几乎为零直接影响留存
核心感知定律：10 秒完整生成 + 200ms TTFT 的体感速度，远快于 4 秒完整生成 + 3 秒 TTFT。用户容忍生成时间，但无法容忍空白等待。流式传输在不加速模型的前提下，带来 10-20x 的感知响应提升。

TTFT 阈值与用户行为

传统 HTTP 模型（致命）: [用户请求] ───── 8~30s 空白等待 ─────> [完整响应一次性返回] ↑ ↑ 用户以为系统挂了 终于看到内容 流式传输模型（生产级）: [用户请求] ─200ms─> [token1] [token2] [token3] ... [tokenN] [DONE] ↑ ↑ 用户立即开始阅读，感知延迟极低
流式输出的本质：将"等待结果"转化为"观察过程"。就像看厨师做菜 vs 等外卖送到——前者即使总时长更长，体验也远胜后者。流式传输的本质矛盾：用户期望 200ms 内看到第一个 token，但完整生成可能需要 10-30 秒。传统 HTTP 请求-响应模型彻底失效——必须边生成边传输，而这条"流水线"要对抗断线重连丢数据、Nginx 缓冲吞噬、DOM 渲染风暴、网关超时等十几种工程灾难。

三、第一层：EventSource 基础——三行代码与六大特性

EventSource 是浏览器原生提供的 SSE（Server-Sent Events）客户端 API。它基于 HTTP 长连接，服务端单向推送文本事件流，客户端通过 onmessage 监听数据到达。2026 年 OpenAI、Anthropic、Google 等主流大模型 API 的 stream: true 模式全部基于 SSE 协议。

最小可用实现（三行代码）

// 三行代码跑通流式传输 const es = new EventSource('/api/chat/stream?prompt=hello'); es.onmessage = (e) => { output.textContent += e.data; }; es.addEventListener('done', () => es.close());

这三行代码完成了：建立连接 → 监听消息 → 流结束关闭。但生产环境中，这远远不够。

EventSource 六大特性与生产限制

特性行为生产环境影响

仅支持 GET标准 API 不支持 POST 方法Prompt 超过 2KB 无法放 URL，需 polyfill
纯文本传输只传输 UTF-8 文本LLM 场景足够，不需要二进制
HTTP/1.1 长连接每个 EventSource 占一个 TCP 连接同域名最多 6 个并发（HTTP/2 下无此限制）

EventSource 的"自动重连"给了开发者虚假的安全感——断了会自动连上没错，但重连后服务端会从零开始生成。你已经看了 30 秒的内容（可能多达 500 个 token），全部丢失，用户看到内容突然跳回开头。这就是为什么"三行代码"在生产中不可用，必须叠加断点续传机制。

SSE 事件流格式

SSE 协议数据格式（服务端响应体）: event: token ← 自定义事件类型（可选） id: chunk_001 ← 事件ID（可选，用于断点续传） retry: 3000 ← 重连间隔毫秒（可选） data: {"content":"你"} ← 数据负载（必须） ← 空行 = 一条事件结束 id: chunk_002 data: {"content":"好"} id: chunk_003 data: {"content":"，"} event: done data: [DONE] ← 流结束标记

Fetch + ReadableStream 替代方案

由于 EventSource 不支持 POST，实际生产中大量项目使用 Fetch ReadableStream 替代原生 EventSource，以获得 POST 能力和更细粒度的控制：

// Fetch + ReadableStream：支持 POST，可自定义 Header const resp = await fetch('/api/chat', { method: 'POST', headers: {'Content-Type':'application/json'}, body: JSON.stringify({ prompt, history, stream: true }) }); const reader = resp.body.getReader(); const decoder = new TextDecoder(); while (true) { const { done, value } = await reader.read(); if (done) break; output.textContent += decoder.decode(value, { stream: true }); }

HTTP 方法仅 GETGET / POST / PUT 全支持
自定义 Header不支持完全支持（Authorization 等）
自动重连内置需手动实现
断点续传Last-Event-ID（非强制）完全自定义
中止控制只能 close()AbortController 精确控制
适用场景简单通知流LLM 对话流（主流选择）
实践结论：2026 年实际生产中，约 70% 的 AI 对话产品使用 Fetch + ReadableStream 而非原生 EventSource。原因很简单——LLM API 的 prompt 通常远超 2KB，必须用 POST；同时需要 Authorization header 传递 API Key。原生 EventSource 更适合轻量级通知推送场景。

四、第二层：断线重连陷阱——已观看 30 秒内容为何丢失

EventSource 的自动重连是 LLM 流式传输中最常被忽视的"地雷"。断线后浏览器确实会自动重连，但重连的行为与开发者的期望完全不同。

Last-Event-ID 机制与局限

SSE 规范设计了 Last-Event-ID 机制：客户端断线重连时，自动在请求头中附带最后接收到的事件 ID。但这个机制存在严重的实际限制：

Last-Event-ID 是 SSE 协议的内置续传机制：EventSource 断线重连时自动把最后收到的 id 字段作为 Last-Event-ID 请求头发给服务端。服务端据此从队列中重放遗漏事件——这是协议级别的断点续传，无需额外编码。它在传统消息队列场景（如日志推送、股票行情）中非常有效，因为服务端可以缓存消息。但在 LLM 流式场景中，服务端通常"边生成边丢弃"——它不记得已经发了哪些 token，也无法精确"从第 N 个 token 继续"。
限制说明影响
非强制支持规范标注 Last-Event-ID 为"建议"而非"必须"大多数 LLM API 不实现此机制
服务端需缓存服务端必须缓存已发送的事件才能重放LLM 生成是流式的，通常不缓存
LLM 不可重现大模型每次生成结果不同（temperature > 0）即使从断点续传，内容也会不一致
仅 GET 可携带Last-Event-ID 通过 HTTP 头传递POST 场景（Fetch 方案）不触发此机制

核心矛盾：LLM 单次生成耗时 10-60 秒，而移动端断线间隔可能只有 3-5 秒。这意味着一次完整生成过程中，可能断线 3-10 次。没有断点续传机制，用户体验将是灾难级的。

五、第三层：断点续传三种方案——从"能续"到"可靠续"

断点续传是让流式传输从"能用"到"可靠"的关键跳跃。核心思路：客户端记录已接收进度，断线重连时告知服务端从断点继续。

双机制总览：消息 ID 与 Token 计数

机制原理实现要点
消息 ID 续传每条事件携带递增 ID，客户端记录最大 ID服务端缓存已生成片段，重连时从 last_id 开始重放
Token 计数续传客户端记录已接收 token 数，重连时传入服务端跳过前 N 个 token，从第 N+1 个开始发送

以下三种生产方案，本质上是这两种机制的具体落地形态。

方案一：接收长度续接

客户端记录已接收内容的字符数或 token 数，重连时通过 lastReceivedLength 参数告知服务端跳过前面的内容。

方案一：接收长度续接流程 Client Server | | |── POST /stream {prompt:"写一篇文章"} ──→| |←── chunk: "大模型技术" | 已接收 5 字符 |←── chunk: "正在改变" | 已接收 9 字符 | ✕✕✕ 断线 ✕✕✕ | |── POST /stream {prompt, lastLen:9} ─→| 跳过前 9 字符 |←── chunk: "世界格局" | 从第 10 字符继续 |←── chunk: "..." |
优点缺点
实现最简单大模型输出有随机性（temperature > 0 时每次不同）
客户端只需计数服务端需要"跳过前 N 字符"的能力
不需要额外存储token 和字符的映射关系不稳定
接收长度续接在 temperature=0（确定性输出）时效果尚可，但大多数 LLM 对话使用 temperature=0.7-1.0，每次生成内容不同。"跳过前 9 个字符"后接上的内容，可能和前面的逻辑完全不连贯。因此这个方案在生产中很少单独使用。

方案二：消息 ID 续接

服务端为每个发出的 chunk 分配唯一递增 ID（如 chunk_001、chunk_002），客户端记录最后收到的 ID。重连时传入 lastEventId（GET 场景下即 last_id 参数或 Last-Event-ID 请求头），服务端从缓存中回放该 ID 之后的内容。

方案二：消息 ID 续接流程 Client Server（带缓存） | | |── POST /stream {prompt} ────────────→| 开始生成 + 分配 ID |←── id:chunk_001 data:"大模型" | 缓存 chunk_001 |←── id:chunk_002 data:"技术" | 缓存 chunk_002 |←── id:chunk_003 data:"正在" | 缓存 chunk_003 | ✕✕✕ 断线 ✕✕✕ | |── POST /stream {prompt,lastId:003} ─→| 从缓存回放 |←── id:chunk_003 data:"正在" (重放) | 先重放已缓存的 |←── id:chunk_004 data:"改变世界" | 然后继续新生成 |←── id:chunk_005 data:"..." |
优点缺点
精确断点续传，不丢不错服务端必须缓存已发出的 chunk（内存开销）
支持去重（相同 ID 直接跳过）需要管理缓存生命周期（生成完成后释放）
与 SSE Last-Event-ID 规范兼容实现复杂度中等
消息 ID 续接是目前最成熟的方案。Anthropic 和 OpenAI 的内部实现都基于此思路——每个 chunk 携带序列号，服务端在 Redis 或内存中缓存当前会话的完整输出，直到客户端确认收到或会话超时（通常 120 秒）。

方案三：客户端缓存 + resume_token

客户端将已接收的内容存入 localStorage 或 IndexedDB，配合服务端返回的 resume_token（会话恢复令牌），断线后完全由客户端恢复，无需服务端回放。

方案三：客户端缓存续传流程 Client (localStorage) Server | | |── POST /stream {prompt} ────────────→| |←── resume_token:"sess_abc123" | 生成会话令牌 |←── chunk:"大模型技术" | → 存入 localStorage |←── chunk:"正在改变" | → 追加到 localStorage | ✕✕✕ 断线 ✕✕✕ | | (从 localStorage 恢复已显示内容) | |── POST /stream {resume:"sess_abc123"}→| 识别会话，继续生成 |←── chunk:"世界格局" | → 追加到 localStorage |←── [DONE] | → 清除 localStorage
优点缺点
断线瞬间用户体验无损（已读内容不消失）需要管理 localStorage 容量和过期
服务端压力小（无需长期缓存）resume_token 需要安全的生成和验证机制
适合移动端弱网环境多标签页需要同步 localStorage 状态

生产推荐：通用场景首选消息 ID 续接（方案二），移动端叠加客户端缓存（方案三）实现无缝体验。接收长度续接（方案一）仅适合 temperature=0 的确定性场景或快速原型验证。实际产品中常将方案二和方案三组合使用——服务端保证数据完整，客户端保证视觉连续。

六、客户端容灾——本地缓存、智能拼接与移动端退避

网络断线不只发生在服务端，客户端同样需要容灾。客户端容灾的核心是在本地保存已接收内容，即使连接完全中断也能保留用户体验。

客户端容灾三层防线: ┌──────────────────────────────────────────────┐ │ 第一层：内存缓冲区 │ │ 已接收 token 实时追加到 tokens[] │ │ 断线瞬间：tokens.join('') 立即展示 │ ├──────────────────────────────────────────────┤ │ 第二层：持久化存储 │ │ 每 N 个 token 写入 localStorage/IndexedDB │ │ 页面刷新/浏览器崩溃后仍可恢复 │ ├──────────────────────────────────────────────┤ │ 第三层：去重拼接 │ │ 重连后用 last_id 请求续传 │ │ 服务端返回的新内容自动拼接，不重复 │ └──────────────────────────────────────────────┘

三种存储方案对比

方案容量速度持久性适用场景
内存数组无限制极快页面关闭即丢失单次对话实时缓冲
localStorage~5MB快（同步）持久短文本缓存
IndexedDB数百 MB较快（异步）持久长对话、多会话缓存
生产级容灾标准：10 秒内断线→自动重连 + last_id 续传（用户无感知）；超过 10 秒→展示已接收部分 + "响应中断"提示；连续 3 次重连失败→降级为非流式 POST 请求。用户永远不应看到空白加载圈。

移动端特殊挑战

移动端网络环境恶劣：Wi-Fi 到蜂窝网络切换时连接必定中断，地铁/电梯场景频繁断线。关键应对策略：

  • 指数退避 + 抖动：重连间隔 1s → 2s → 4s → 8s，叠加随机抖动防止万人同时重连的"雷群效应"
  • 部分结果展示：超时 10 秒无新 token，立即展示已有内容，不再让用户等待
  • 降级兜底：3 次 SSE 失败后切换为标准 POST 请求，用户失去打字机效果但仍能获得完整回答

七、第四层：WebSocket 双向通信与心跳保活

当 SSE 的单向推送无法满足需求时（中途取消生成、实时语音交互、多人协作编辑），需要升级到 WebSocket 双向通信协议。但它带来的工程复杂度也成倍增加。

JSON-RPC over WebSocket：大厂方案

JSON-RPC 是一种轻量级远程过程调用协议，将其叠加在 WebSocket 上，可以在双向通信的基础上获得结构化的请求-响应语义。这是 Anthropic Claude 实时 API、Google Gemini Live API 等大厂产品的底层通信模式。

JSON-RPC over WebSocket 消息格式: // 客户端请求（带 method + params + id） {"jsonrpc":"2.0", "id":1, "method":"chat.generate", "params":{"prompt":"你好","stream":true}} // 服务端流式响应（带 id 关联） {"jsonrpc":"2.0", "id":1, "result":{"seq":1,"data":"你"}} {"jsonrpc":"2.0", "id":1, "result":{"seq":2,"data":"好"}} // 客户端中途取消 {"jsonrpc":"2.0", "id":2, "method":"chat.cancel", "params":{"original_id":1}} // 服务端确认取消 {"jsonrpc":"2.0", "id":2, "result":{"cancelled":true}}

心跳保活——WebSocket 的生命线

大多数反向代理和网关默认 60 秒无数据即断开连接。LLM 生成可能在两个 token 之间间隔超过 60 秒（特别是思考型模型）。心跳机制是防止网关误杀连接的唯一手段。

心跳保活流程: Client Proxy/Gateway Server | | | |<══════ token data ═══════════>|<════════════════════| | | | | ... 30 秒无数据 ... | | | | | |<──────── ping ───────────────>| ← 客户端主动心跳 | |───────── pong ───────────────>| ← 服务端回复 | | | ← 网关重置超时计时 | | | | |<══════ token data ═══════════>|<════════════════════|

SSE 场景下则由服务端主动发心跳：每 15-30 秒发送一条心跳事件（SSE 注释格式 : heartbeat\n\n），防止 Nginx / 负载均衡器因超时（默认 60s）切断空闲连接。

SSE 服务端心跳时序（防止中间件超时切断）: t=0s Server → Client: data: 第一个 token t=1s Server → Client: data: 第二个 token ... t=15s Server → Client: : heartbeat ← 心跳（SSE注释格式） t=16s Server → Client: data: 继续生成 ... t=30s Server → Client: : heartbeat ← 第二次心跳 ... 若 Nginx proxy_read_timeout = 60s: 没有心跳 → 第 60s 连接被切断 → 用户看到生成中断 有心跳 → 连接持续存活 → 生成完整完成
心跳间隔必须小于网关超时的一半。网关默认 60 秒超时，心跳应设为 15-30 秒：设太短浪费带宽，设太长网关可能先超时。生产环境中最常见的 WebSocket "莫名断线"，90% 都是心跳缺失导致网关超时。

组件一：心跳保活

服务端每 15-30 秒发送心跳事件（SSE 注释 : heartbeat\n\n 或 WebSocket ping/pong），防止 Nginx / 负载均衡器因超时（默认 60s）切断空闲连接。心跳时序图与间隔推导详见"七、第四层"章节。

组件二：requestAnimationFrame 批量 DOM 更新

LLM 常规每秒产生 20-50 个 token，高优化推理场景（vLLM + 投机解码等）可达 50-80 个 token/秒。如果每个 token 都触发一次 DOM 更新和 React 重渲染，浏览器主线程将被淹没（每秒 20-80 次重排）。使用 requestAnimationFrame（rAF）将多个 token 合并到一帧内更新，是解决渲染风暴的核心手段。

rAF 批量更新 vs 逐 token 更新: 逐 token 更新（卡顿）: token到达 → setState → render → DOM → paint (16ms) token到达 → setState → render → DOM → paint (16ms) token到达 → setState → render → DOM → paint (16ms) → 每秒 50 次 render → 主线程阻塞 → 页面冻结 rAF 批量更新（流畅）: token到达 → 存入 buffer token到达 → 存入 buffer token到达 → 存入 buffer rAF 回调 → flush buffer → 一次 setState → 一次 render → 每秒最多 60 次 render → 与屏幕刷新同步 → 流畅
渲染策略每秒 render 次数主线程占用用户体验
逐 token setState20-50 次高（80%+）明显卡顿
throttle 50ms固定 20 次中（40-60%）轻微延迟
rAF 批量最多 60 次（与帧同步）低（20-30%）丝滑流畅
rAF + React.memo最多 60 次（局部更新）极低（10-15%）极致流畅
requestAnimationFrame 的精妙之处在于它"不创造新的渲染"，而是"把已有的渲染对齐到屏幕刷新周期"。它在浏览器下一次重绘前执行回调，天然对齐 60fps（~16ms/帧）——将 16ms 内到达的所有 token 攒到缓冲区一次性更新 DOM，渲染次数从每秒 50-80 次降到最多 60 次，既不多（浪费性能）也不少（保证及时）。移动端 Compose 类似，用 ~48ms 的 chunked 窗口做批量更新。

组件三：实时 Markdown 渲染（分层选型）

LLM 输出通常包含 Markdown 格式（代码块、列表、表格等）。流式场景下不能等全部生成完再渲染，也不能每来一个字符就全量解析。核心结论按输出体积分三层：<3KB 短输出，累积重渲染完全可接受；3-15KB 常规对话，用 Streamdown / Ant Design X 类分段方案（分段冻结——已完成块缓存 HTML 不再重新解析，仅解析新块，输出 O(n) 性能）；15KB+ 长文档/代码生成，必须增量解析（Incremark 等）才能保持 60fps。详细方案对比与性能数据见 ST18 · Markdown 流式渲染技术解析。

无论哪一层，都要处理"片段不完整"问题——流式传输中 Markdown 片段经常不完整：收到 ```pyth 时不知道是行内代码还是代码块的开头，收到 **bold 时不知道粗体何时结束。错误渲染会导致页面闪烁。

不完整片段错误渲染正确策略
```pyth当成行内代码渲染检测到可能的代码块开头，暂缓冲不渲染
**bold显示原始星号等待 ** 闭合后再渲染粗体
| col1 |显示为普通文本等待表格行完成后批量渲染
[link显示断链等待 ]() 完整后再渲染链接
渲染策略分层结论：<3KB 累积重渲染可接受（现代解析器如 marked 处理几千字的重渲染只需亚毫秒级）；3-15KB 用 Streamdown 类分段方案；15KB+ 必须增量解析，避免 O(n²) 全量重解析造成的冻结——详见 ST18 · Markdown 流式渲染技术解析。共同原则：渲染前必须检测未闭合标记（如未配对的 ``` 或 **），不要在半截 Markdown 上做渲染决策。

组件四：本地缓存兜底

即使网络层和续传层全部失效，客户端通过 localStorage 保底存储已接收内容，确保用户刷新页面后不丢失对话记录。

本地缓存兜底策略: 正常运行: token 到达 → 渲染到 DOM → 同时写入 localStorage [DONE] 到达 → 标记完成 → localStorage 可清理 断线时: localStorage 中已有内容 → 立即恢复显示 用户看到"网络中断，正在重连..." 重连成功 → 续传补全 重连失败 → 用户可选择"查看已接收内容" 页面刷新时: 检查 localStorage → 有未完成的流 → 恢复显示 用户可手动点击"重新生成"或"继续"

组件五：手动重试机制

当自动重连 3 次仍失败时，给用户一个显眼的"重试"按钮。这看似简单，但很多产品忘记做——用户在断线后只能无奈刷新整个页面。

组件六：AbortController 中止控制

用户点击"停止生成"时，使用 AbortController 中止 HTTP 请求，立即释放网络连接和服务器计算资源。这是 Fetch API 提供的原生能力，EventSource 不具备。

十、服务端基础设施——Nginx 配置与超时对抗

即使前端代码写得完美无缺，服务端基础设施的一个错误配置就能让所有努力白费。以下是最常见的生产级配置问题。

Nginx 缓冲——最常见的生产灾难

Nginx 默认会缓冲上游响应，导致 SSE 事件被攒够一定量后才一次性发送。用户看到的不是逐 token 流出，而是"等很久然后突然出现一大段"——完全丧失流式体验。这是最常见的生产灾难，因为很多开发者在本地开发时直连后端（没有 Nginx），一切正常；上线后经过 Nginx 代理才发现流式失效。

Nginx 反代 SSE 关键配置

配置项推荐值作用
proxy_buffering off必须该路径下彻底禁止 Nginx 缓冲上游响应
proxy_buffer_size 4k推荐减小缓冲区避免延迟
X-Accel-Buffering: no应用层响应头告知 Nginx 该请求禁用缓冲
proxy_read_timeout300s延长读超时（LLM 生成可能 60s+）

  • 根据场景选协议：80% 用 SSE，双向需求（取消/语音/协作）用 WebSocket
  • 始终实现断点续传（消息 ID + Last-Event-ID）
  • 客户端本地缓存（localStorage/IndexedDB）+ 指数退避重连
  • requestAnimationFrame 批量 DOM 更新
  • Markdown 渲染分层选型：<3KB 累积重渲染 / 3-15KB Streamdown 类分段 / 15KB+ 增量解析
  • Nginx 配置 X-Accel-Buffering: no + proxy_buffering off
  • 15-30 秒心跳防网关超时
  • 提供手动重试按钮，AbortController 支持取消生成
  • chunk 携带 seq 序列号便于续传
  • 不要以为 EventSource 自动重连就够了（重连会从头开始）
  • 不要在每个 token 到达时立即更新 DOM / setState（渲染风暴）
  • 不要忽略 Nginx/代理缓冲配置（内容攒堆出现）
  • 不要在 WebSocket 场景忘记心跳保活
  • 不要在半截 Markdown 上做渲染决策
  • 不要用 SSE 传输 > 2KB 的 prompt（用 Fetch+POST）
  • 不要忽略用户中途取消时的后端资源释放（15-20% 费用浪费）
  • 不要不设超时检测（服务端卡死用户无感知）
  • 不要用 innerHTML 直接拼接（XSS 风险）
  • 不要忽略移动端弱网场景，生成中断后无任何错误提示
合格前端工程师的最低标准是第三层：不仅能让 token 流式展示，还要在断线时本地缓存拼接、配合 last_id 去重续传。架构师级则要求掌握混合协议选型、全链路性能优化和生产级容灾体系。

十二、常见问答

为什么 2026 年几乎所有 LLM API（OpenAI、Anthropic、Google）都选择了 SSE 而不是 WebSocket？
因为 LLM token 流是天然的单向传输——客户端发一个 prompt，服务端回一串 token，SSE 完美匹配这个模式。SSE 有三大不可替代优势：(1) 基于 HTTP，天然穿透企业防火墙、CDN、代理——WebSocket 需要协议升级，约 15% 的企业网络会阻断；(2) 内置自动重连和 Last-Event-ID，水平扩展无需 sticky session——WebSocket 需要从零实现重连逻辑、心跳、消息队列；(3) 调试友好——SSE 是纯文本 HTTP 响应，用 curl 就能测试，WebSocket 需要专门工具。WebSocket 的全双工能力在纯 token 流场景完全用不上，却引入了心跳维护、手动重连、代理兼容性差等额外复杂度。只有当需要中途取消生成、实时语音、协作编辑等双向交互时，WebSocket 才值得引入。
EventSource 和 Fetch+ReadableStream 在 LLM 场景中到底该选哪个？
生产中推荐 Fetch+ReadableStream。原因有四：(1) LLM 的 prompt 通常超过 2KB（URL 长度限制），必须用 POST，而原生 EventSource 仅支持 GET；(2) 需要 Authorization header 传 API Key，EventSource 不支持自定义 header；(3) Fetch 提供 AbortController 中止能力，可以随时取消生成；(4) 可以完全自定义请求头和数据格式控制。缺点是丧失了 EventSource 的自动重连和 Last-Event-ID 内置机制，需要全部手动实现。原生 EventSource 更适合简单的通知推送场景（构建状态更新、日志流等）。实测 2026 年约 70% 的 AI 对话产品使用 Fetch + ReadableStream。
EventSource 的自动重连为什么是"假安全"？生产环境该怎么补救？
EventSource 断线后确实会自动重连，但重连时会重新发起请求——服务端不知道之前已发了多少内容，会从头开始生成。结果就是用户已经看到的内容被"刷新"，之前接收的 500 个 token 全部丢失。补救方案是叠加消息 ID 续传：每条 SSE 事件带上递增 id 字段，客户端记录最后收到的 id，重连时通过 Last-Event-ID 请求头告知服务端从断点继续。服务端需要缓存已生成的片段（内存队列或 Redis Stream）来支持重放。
Nginx 默认缓冲对 SSE 有什么影响？为什么是最常见的生产灾难？
Nginx 默认会缓冲上游响应到一定大小（默认 4k/8k）后才转发给客户端。对 SSE 来说，这意味着多个 data: 事件被攒在缓冲区里，直到缓冲区满了才一次性发送。用户看到的现象是"等了好久，然后突然出现一大段文字"——完全丧失了流式体验。这是最常见的生产灾难，因为很多开发者在本地开发时直连后端（没有 Nginx），一切正常；上线后经过 Nginx 代理才发现流式失效。解决方案是在响应头加 X-Accel-Buffering: no，或在 Nginx 配置 proxy_buffering off。
心跳间隔应该设多少？为什么不直接把超时时间设得很大？
大多数反向代理（Nginx、ALB、CloudFlare）默认空闲超时为 60 秒——如果 60 秒内连接上没有任何数据流动，代理会主动断开连接。心跳间隔必须小于这个超时值，推荐 15-30 秒，留出安全余量。设太短（如 5 秒）会浪费带宽和服务端 CPU；设太长（如 55 秒）可能在网络抖动时来不及保活就被断开。LLM 场景特别需要心跳，因为思考型模型在两个 token 之间的间隔可能超过 60 秒。那为什么不直接设 proxy_read_timeout=3600s？会带来两个问题：(1) 真正的死连接（客户端已离开）会占用服务端资源长达一小时，在高并发场景下导致连接池耗尽；(2) 中间链路上的每一层（CDN、负载均衡、防火墙）都有自己的超时设置，你无法控制所有层。心跳每 15-30 秒发一个小数据包，动态重置所有中间层的计时器，既保持连接活跃，又不会让死连接长期占用资源。
每个 token 到达时更新 DOM 为什么会导致卡顿？rAF 批量渲染会让用户看到"跳跃式"输出吗？
LLM 常规每秒生成 20-50 个 token，高优化推理场景可达 50-80 个。每个 token 触发一次 DOM 更新意味着浏览器每秒要执行 20-80 次重排（reflow）和重绘（repaint）。在 60fps 的标准下，每帧只有 ~16ms 的预算——如果一帧内有 2-3 次 DOM 更新，很容易超出预算导致掉帧。解决方案是用 requestAnimationFrame 做批量更新：将 16ms 内到达的所有 token 攒到缓冲区，在下一帧的 rAF 回调中一次性更新 DOM。rAF 回调频率与屏幕刷新率同步（60Hz = 每 16.7ms 一帧），人类视觉暂留约 50-100ms，完全无法感知 16.7ms 级别的更新间隔，因此不会产生跳跃感。实测 rAF 批量渲染的视觉体验与逐 token 渲染完全一致，但性能提升 3-10 倍。如果模型输出速度特别快（每秒 100+ token），可以额外叠加 throttle 将更新频率限制在每 30-50ms 一次。移动端 Compose/React Native 同理，使用 ~48ms 的 chunked 窗口做批量状态更新，将重渲染频率控制在 ~20 次/秒。
流式传输中 Markdown 片段不完整怎么处理？累积重渲染还是增量解析？
流式 Markdown 面临上下文不确定性：收到 ```pyth 时不知道是代码块还是行内代码，收到 **bold 时不知道粗体何时结束。关键在渲染前检测未闭合的标记（如未配对的 ``` 或 **），对不完整部分暂用纯文本显示或补一个合理的临时版本。至于渲染策略，要按输出体积分层选择：<3KB 的短输出，累积重渲染完全可接受——现代解析器（如 marked）处理几千字的重渲染只需亚毫秒级；3-15KB 的常规对话，用 Streamdown 类分段方案（分段冻结，已完成块缓存 HTML 不再重解析）；15KB+ 的长文档/代码生成，必须增量解析（Incremark 等）才能避免 O(n²) 全量重解析冻结、保持 60fps。详见 ST18 · Markdown 流式渲染技术解析。
用户中途取消生成时，后端应该怎么处理才不浪费资源？
这是生产环境中的成本黑洞：用户点了"停止生成"，但后端 LLM 还在继续生成剩余 token，白白消耗 GPU 算力和 API 费用。SSE 场景下客户端关闭连接，服务端需要在 async generator 中检测连接断开（如 FastAPI 的 Request.is_disconnected()），立即终止 LLM 调用并释放资源。WebSocket 场景下客户端发送 cancel 帧，服务端收到后停止生成。关键是在 finally 块中确保清理：关闭 LLM stream、释放 KV Cache、记录已消耗的 token 数用于计费。实测显示，不处理取消的系统中 15-20% 的 token 费用花在了用户根本不会看到的内容上。
为什么大模型的断点续传比普通文件下载复杂得多？
文件下载是确定性的——同一文件的第 1000 字节永远是同一个字节。但 LLM 生成是概率性的（temperature > 0），同一 prompt 每次生成结果不同。如果断线后服务端"从头重新生成"，续接的内容与前文逻辑可能不连贯。因此 LLM 断点续传的核心不是"从第 N 个字节继续下载"，而是"服务端必须记住这次生成进行到哪里了，并从那个位置精确继续"——这需要会话状态管理和 chunk 缓存机制。
移动端弱网环境下的流式传输有什么特殊考虑？
移动端面临三大特殊挑战：(1) 网络切换——WiFi 到 4G 切换时 TCP 连接断开，需要快速重连（指数退避从 500ms 起步）；(2) 系统休眠——Android Doze 模式和 iOS 后台限制会冻结网络连接，恢复后需要 resume_token 续传；(3) 连接不稳定——地铁、电梯场景下可能每 3-5 秒断一次。推荐方案：SSE + 客户端 localStorage 缓存（保证断线瞬间内容不消失）+ resume_token（服务端识别会话继续生成）+ 指数退避重连（1s→2s→4s→8s 加随机抖动，避免频繁重试加剧网络拥塞和雷群效应）。
如何监控生产环境中流式传输的健康状况？
需要监控五个关键指标：(1) TTFT（Time to First Token）——首 token 延迟，P50 应 < 300ms，P99 应 < 1s；(2) 断线率——每千次请求的断线次数，桌面 < 1 次，移动端 < 50 次；(3) 续传成功率——断线后成功续传的比例，应 > 99%；(4) 渲染帧率——rAF 回调频率，应稳定在 55-60 FPS；(5) 完成率——流式传输正常完成（收到 [DONE]）的比例，应 > 98%。建议在客户端埋点上报这些指标，配合 Grafana 仪表盘实时观察。
多标签页场景下 SSE 连接数耗尽怎么处理？
HTTP/1.1 下同域名最多 6 个 TCP 连接，每个 EventSource 占用一个。如果用户打开 7 个标签页，第 7 个的 SSE 请求会被浏览器排队等待。解决方案有四种：(1) 升级到 HTTP/2——多路复用共享单个 TCP 连接，理论连接数上限 100+；(2) 使用 SharedWorker——多个标签页共享同一个 Worker 中的 SSE 连接，通过 postMessage 分发数据；(3) 使用 BroadcastChannel API 在标签页间同步状态，只保持一个活跃连接；(4) 限制同域连接数，非活跃标签页降级为轮询。
