投机解码的收益不由"加速比"这个营销数字决定，而由"目标模型每做一次前向，最终能落地几个 token"决定——这个数叫接受长度，它会随并发上升、随上下文变长而缩水，所以投机解码在生产里从来不是一个开关，而是一组需要按负载动态调节的旋钮。

到 2026 年，投机解码已经从论文里的加速技巧变成了推理引擎的默认推荐配置：vLLM、SGLang、TensorRT-LLM 三家主线都把 EAGLE-3 系的实现合进了主干，SGLang 官方文档直接把 --speculative-algorithm EAGLE3 标注为"最佳速度/质量"选项，vLLM 也在 2026 年上半年把 EAGLE 3.1 的支持并入了主线。技术可用性早已不是问题，真正的问题变成了工程问题：该选哪条路线、参数怎么定、什么时候必须让它退让、怎么判断它是不是在帮倒忙。这四件事是本文的全部内容。

本文不讲入门原理。草稿-验证的基本形态、修正拒绝采样的接受判据与数学证明、经典 draft-target 双模型的选择策略，都在 DP08 · KV Cache 与推理优化 第六节讲过了，这里默认读者已经理解"小模型猜、大模型验、猜错回退"这条链路。本文从"它已经能跑了，怎么把它调对"这一步开始。

一、无损加速与两个真指标

先用两段话把原理带过，因为后面所有的调参判断都建立在这两段之上。投机解码让一个便宜的草稿器先猜出 k 个候选 token，然后让目标模型一次前向并行验证这 k 个位置。验证使用修正拒绝采样：逐位置比对目标分布与草稿分布，接受前缀里概率相容的部分，在第一个被拒绝的位置改用目标分布重新采样，该位置之后的草稿全部丢弃。它之所以有收益，是因为 decode 阶段是访存受限的——把整个模型权重从显存读一遍的开销与本步处理 1 个还是 8 个 token 几乎无关，所以"验证 k 个"和"生成 1 个"的耗时接近。详细的接受判据与分布等价性证明见 DP08。

无损：这是它和量化的根本分野

修正拒绝采样带来一个非常重要的工程性质：输出分布严格不变。同样的种子、同样的采样参数，开投机和不开投机采出来的 token 序列在分布意义上完全一致。这一点让投机解码在风险属性上和量化完全不是一类东西。量化是拿精度换速度，任何一次量化上线都必须配一轮完整的质量回归，因为你永远不能保证某个业务场景不会正好落在被损失的那部分精度上；而投机解码在实现正确的前提下不需要担心答案变差——它要担心的是速度不升反降。

投机解码不是"用小模型代替大模型答题"，而是"让小模型先把答案写在草稿纸上，大模型只做批改"——批改一整页和批改一行的成本几乎一样，所以只要小模型的正确率够高，这笔账就是赚的。

加速比是营销数字，接受率和接受长度才是工程量

公开材料里最常见的表述是"提速 2 倍""提速 3.5 倍"。这类数字几乎不可复现，因为它高度依赖批大小、数据集、输出长度和硬件——同一个 EAGLE-3 检查点在批大小 1 上可能报 3.5 倍，在批大小 64 上就掉到 1 倍以下。真正能在你自己的服务上测量、并且能直接指导调参的，是下面两个量。

接受率（acceptance rate）指单个草稿位置通过验证的概率，通常按位置分别统计，记作 α。它衡量的是草稿器和目标模型有多像，是草稿器质量的直接体现。接受长度（accept length，也叫 acceptance length / AL）指目标模型每完成一次前向验证、最终真正落地到输出里的 token 数。它衡量的是你这一步究竟赚了多少，是接受率与草稿长度共同作用的结果，也是唯一能和吞吐直接对应的量。

收益的粗略心算

如果草稿是一条链（而不是树），并且各位置的接受概率近似相同为 α，那么接受长度有一个非常好用的闭式：把"接受 0 个""接受 1 个"……的期望加起来，就是一条等比数列。

AL = 1 + α + α² + … + αk = (1 − αk+1) / (1 − α)

净加速 ≈ AL / (1 + 草稿与验证的相对开销)

第一项那个 1 就是兜底 token：即使第一个草稿就被拒绝，目标模型的重采样结果依然是一个有效输出，所以 AL 永远不小于 1，投机解码在理论上不会比普通解码产出更少的 token。它变成负收益只能通过一条路径——分母上的开销项。

这张表最该记住的不是那些绝对值，而是最后一列揭示的规律：第 k 个草稿位置的边际贡献是 αk，指数衰减；而它的成本是线性的——每加一个草稿位置就要多跑一次草稿器前向。两条曲线必然相交，交点就是最优草稿长度。α 越低，交点越靠前。这就是为什么 SGLang 的自动默认值对 Llama 系给 --speculative-num-steps 5，而对接受率通常偏低的其他模型族只给 3。

把这个心算落到实际：假设你的 EAGLE-3 检查点在业务数据上量到 α ≈ 0.78、k = 3，那么 AL ≈ 2.8；再假设单发场景下草稿器加验证带来约 15% 的额外时间，净加速约 2.8 / 1.15 ≈ 2.4 倍。这个推算能在你还没做完整压测之前，就先判断出"报出来的 3.5 倍"在你的场景里是否可信。真正的测量口径（TTFT 与 ITL 该怎么分开看、长度分布怎么构造、饱和点怎么找）见 DP16 · 推理服务压测方法论，本文只讲这些数字怎么读。

二、三条路线怎么选

2026 年生产环境里真正在跑的投机解码方案，可以归成三条路线。它们的差别不在"验证"那一半——验证逻辑几乎一样——而在草稿从哪里来。这个差别决定了三件事：接受率能有多高、草稿本身要花多少钱、以及你需不需要动目标模型。

EAGLE-3：在目标模型的特征空间里打草稿

EAGLE 系的核心洞察是：让草稿器去猜 token 太难了，但让它去猜目标模型的中间特征要容易得多。所以 EAGLE 把自回归过程搬到了特征空间——草稿器接收目标模型的隐藏状态，在特征层面自回归地往前推 k 步，每一步都把上一步的特征作为输入，最后再经由目标模型的 lm_head 落成 token 候选。EAGLE-3 相对前代的关键改动是不再只用一层的特征，而是把低、中、高三个层次的隐藏状态融合后再喂给草稿器，从而拿到更完整的上下文信息。

它的工程画像非常适合生产：草稿头只有目标模型 2%~5% 的参数量，训练成本远低于维护一个独立的十亿级草稿模型；显存开销典型在 +20% 左右（草稿权重加上草稿自己的 KV 缓存）；接受率在业务数据上通常落在 0.75~0.80，配 k=3 的草稿长度对应接受长度约 2.7~2.9，实测加速约 2 倍。代价是它和目标模型绑定——换目标模型、甚至只是目标模型换了量化格式，草稿检查点都需要重新训练或至少重新验证。

Medusa-2：不动目标模型的那条路

Medusa 的做法完全不同：它不做自回归，而是在目标模型的 final hidden 上并排接出若干个独立的解码头，第 i 个头直接预测"未来第 i 个位置"。这些头在一次前向里全部出结果，所以草稿生成的成本接近于零。为了从多个头的候选里挑出最优组合，Medusa 配了两个机制：树注意力（tree attention）把多个候选分支组织成一棵树，用一个精心设计的注意力掩码让目标模型在一次前向里并行验证所有分支；典型接受（typical acceptance）放宽了严格的拒绝采样判据，只要草稿 token 在目标分布里"足够典型"就接受，用一点分布上的松动换更长的接受长度。

Medusa 的结构性弱点也很清楚：头与头之间不建模依赖。head3 在预测第 3 个位置时并不知道 head1、head2 实际给出了什么，所以它只能预测"从当前状态出发第 3 个位置的边缘分布"，越靠后越不准。这直接压低了接受长度，典型值落在 2.2~2.8 之间，比 EAGLE-3 系明显短。它最大的优点是可后挂：不必微调目标模型本体，只训练那几个头，对"目标模型是外部提供的、权重不能动"的场景几乎是唯一选择。

Lookahead / N-gram：几乎免费的那条路

第三条路线干脆不用任何神经网络做草稿：直接拿已生成文本（有时也包括 prompt）里的 n-gram 做候选，命中就把后续片段作为草稿一起送去验证。SGLang 里对应 --speculative-algorithm NGRAM，vLLM 里对应 method: "ngram" 加 prompt_lookup_min / prompt_lookup_max 两个窗口参数。它的接受率典型在 0.55 上下、加速约 1.3 倍，但开销仅约 +5%，且完全不占额外显存、不需要训练。

它的收益分布极不均匀，这一点比平均值更重要。公开基准（SpecDecode-Bench，2026）在 vLLM 上观察到 n-gram 的单步接受跨度可以从 1.1 一路波动到 15.0，而 EAGLE 稳定在 2.7~7.4——n-gram 是"爆发式"的：在代码编辑、长文档摘要、结构化输出这类输出大量复用输入的任务上它可能反超所有神经草稿方案，而在开放式对话上它几乎不命中。所以 n-gram 不是"弱化版 EAGLE"，而是一个适用面完全不同的工具。

选型结论

把上面的对比压成一条决策链：默认上 EAGLE-3，它在接受长度、显存开销、生态成熟度三个维度上都没有明显短板，三大框架都有一等公民级的支持；目标模型不能改动（供应商提供的权重、合规要求下不允许微调本体）时用 Medusa-2，接受长度短一些但可后挂；低资源或任务本身 n-gram 重复度高时用 Lookahead，它不需要训练、不占显存，在代码编辑这类任务上性价比反而最高。如果目标模型很大（70B 以上）且你手上正好有同族的小模型，独立草稿模型这条老路仍然值得一测，因为草稿相对成本随目标模型变大而显著下降。

三条路线的区别可以用"草稿纸从哪来"概括：EAGLE-3 请了一个懂行的助手现写，Medusa-2 让四个互不通气的人同时各写一句，N-gram 直接翻旧稿抄。助手最准但要付工资，抄旧稿最便宜但只在重复的活儿上有用。

三、接受率为什么会掉

接受率是收益的源头，所以"它为什么掉"是投机解码调优里最有价值的一个问题。答案在多数情况下可以归到同一条主线上：草稿器看不到目标模型足够的上下文表示。草稿器之所以敢猜，是因为它拿到了目标模型的某种内部状态作为条件；这个条件越贫瘠、越陈旧、越偏离训练时的分布，草稿就越像在瞎猜。

注意力漂移：草稿器的"视野"不够

把 Medusa 那种结构想清楚就能看到问题所在。它的每个头只能看到当前这一个位置的 final hidden，然后要预测未来第 3、第 4 个位置。目标模型在真正走到第 3 个位置时，会重新对整个上下文做一遍注意力，得到一个与"第 0 位的 final hidden"相当不同的状态；而草稿头对此一无所知。这种"草稿器所依据的状态"与"目标模型实际会处于的状态"之间的偏离，可以统称为 注意力漂移（attention drift）——草稿走得越远，漂移越大，接受率沿位置衰减越快。

EAGLE-3低/中/高多层隐藏状态融合后的特征草稿器拿到更完整的上下文表示训练与推理的上下文分布仍会不一致
更进一步的方案把目标模型的上下文隐藏状态经草稿器自己的 KV 投影后注入草稿器各层草稿器每一层都被目标模型的状态约束实现复杂度与显存开销上升

最后那一行值得展开，因为它是这条主线的逻辑终点。既然草稿质量取决于草稿器能看到多少目标模型的上下文，那最彻底的做法就是把目标模型的上下文隐藏状态直接送进草稿器的注意力里：让这些隐藏状态经过草稿器自己的 K/V 投影矩阵，变成草稿器各层可以直接注意到的键值对，这类做法可以统称为 KV 注入（KV injection）。这样草稿器不只是在"起点"被目标模型初始化了一次，而是在每一层、每一步都持续被目标模型的状态约束着。代价是草稿器不再是一个可以随便替换的小挂件，它对目标模型内部结构的耦合更深了。

草稿器不是"另一个更笨的模型"，而是"目标模型的一个外推器"。它能外推多准，几乎完全取决于你给它看了目标模型多少内部状态——这是评估任何一个新的投机解码方案时最先该问的问题。

一个可复用的设计维度

把上面这条线抽象出来，你会得到一个在读任何新论文、评估任何新方案时都能直接套用的判据：这个方案让草稿器看到了目标模型的多少上下文？以什么形式看到？看到的是一次性快照还是持续更新的？三条路线在这个维度上的位置一目了然——N-gram 看到零，Medusa 看到一个点，EAGLE-3 看到一个融合特征，KV 注入类方案看到整段上下文。接受长度的排序基本就是这个顺序。这也解释了为什么单纯把草稿模型做大往往收效甚微：问题不在草稿器的容量，而在它的输入信息量。

其他会压低接受率的因素

除了结构性的漂移，还有几类工程原因会让接受率低于预期，排查时值得逐条过。训练分布不匹配是最常见的：草稿检查点是在通用对话数据上训的，你的业务是中文法律文书或 SQL 生成，接受率自然低——这也是 SpecForge 这类草稿训练框架存在的理由，用自己的业务数据（最好是通过目标模型生成的 on-policy 数据）重训草稿头，接受率通常有可观提升。聊天模板与系统提示的变化影响也比直觉大：vLLM 团队在 EAGLE 3.1 的说明里明确指出，投机解码在受控环境表现良好，但在不同聊天模板、超长输入或分布外系统提示下性能常常退化，EAGLE 3.1 的改动（FC 归一化、post-norm 隐藏状态回传）就是专门针对这类鲁棒性问题的。采样温度也是一个旋钮：温度越高目标分布越平，草稿越难命中，接受率会随温度上升而下降。

四、与连续批处理的相互作用

这一节是投机解码在生产里最容易出错的地方，也是最需要克服直觉的地方。调度器的内部机制——迭代级调度、waiting/running/preempted 队列、Chunked Prefill、token 预算——在 DP11 · Continuous Batching 与推理调度策略 里已经详细讲过，本节只讲投机解码这一个旋钮和调度器之间的相互影响，不重复调度器本身。

冲突的根源：投机是拿算力换访存

回到第一节那个"验证 k 个和生成 1 个耗时接近"的前提——它成立的条件是 GPU 处在访存受限区间。批大小很小时，decode 步的绝大部分时间花在把权重从 HBM 搬到计算单元上，SM 大量空转，此时多验证几个位置几乎是免费的，草稿器那几次小前向也是从空转里抠出来的。但连续批处理的全部意义就是把批堆大、把 GPU 从访存受限推向算力受限。一旦跨过那个拐点，SM 不再空转，投机解码多要求的那 k 倍验证计算和 k 次草稿前向就变成了真金白银的算力支出，而它们要和批里的真实请求抢同一批 SM。

"高并发就该禁用投机解码"是过度简化

网上流传的处置方案通常是一句话：批大小超过 32 就把投机解码关掉。vLLM 里确实有这个开关，disable_by_batch_size（旧版独立标志是 --speculative-disable-by-batch-size），文档描述是"当排队请求数超过该值时，对新到达的请求禁用投机解码"。这个开关有它的价值，作为兜底保护完全合理。但把它当成唯一答案是过度简化，因为真正随负载恶化的是"固定的多 token 草稿"，不是投机本身。

看回上面那张图的算式：净收益 ≈ AL / (1 + 开销)。高并发下 AL 从 2.9 掉到 1.9，开销从 8% 涨到 80%，用 k=5 的长草稿算出来的净收益确实掉到 1.0 附近甚至以下。但开销这一项是随 k 线性增长的——把 k 从 5 降到 1，草稿器只跑一次，开销大约回到 15%~20% 的量级，而 AL 在 k=1 时是 1 + α，α 就算掉到 0.6 也还有 1.6。1.6 / 1.2 ≈ 1.33，仍然明显在盈亏平衡线之上。换句话说，高并发下正确的动作是把草稿缩短，而不是把投机关掉。关掉等于主动放弃这剩下的三成收益。

这也是 SGLang 文档里那条"MTP 场景常配很小的 speculative_num_steps / topk / num_draft_tokens"建议背后的逻辑，以及为什么 topk=1（纯链式草稿、不长树）在高并发下是一个特别有用的配置：树注意力能提高接受率，但树的每个额外分支都要占验证槽位，在算力受限区间里这笔交易不再划算。

更进一步：用置信度头做动态草稿长度

按并发分档已经比一刀切好得多，但它仍然是粗粒度的——同一个并发档位里，不同请求、同一请求的不同位置，草稿的成功概率相差极大。一句陈述句的中段几乎可以随便猜，而一个转折处、一个列表的起点、一个需要做算术的位置，草稿几乎必错。理想的做法是逐步决定这一步该草稿几个 token。

实现这件事的一个干净思路是给草稿器额外加一个 置信度头（confidence head）：草稿器在产出第 i 个草稿 token 的同时，输出一个标量 ci，估计"这个 token 能通过目标模型验证"的条件概率。由于草稿是链式的，第 i 个 token 被接受的前提是前 i−1 个都被接受，所以整块草稿的存活概率就是这些置信度的累积乘积。这个乘积单调递减，一旦跌破阈值就说明再往后草稿的期望收益已经小于成本，当场停止即可。

这个思路的价值在于它把决策从全局静态配置下沉到了每一步的局部判断。按并发分档只能回答"这一档大概该猜几个"，置信度头能回答"此时此刻这个请求该猜几个"。SGLang 已经有沿着这个方向的实现（自适应投机解码需配 --speculative-eagle-topk 1，以及按批大小自动调参的 AutoSpec 控制器），vLLM 侧也有类似的动态草稿长度工作。落地时要注意两点：置信度头本身要额外训练且必须校准（一个系统性高估的置信度会让动态调节变成永远选最长），阈值本身是一个需要按负载调的旋钮，高并发下应该调高（更保守）。

示例场景（同一配置在两种负载下差异巨大）：某代码补全服务用 SGLang 部署 Qwen3-32B（4×H100，TP=4），配 EAGLE-3 草稿检查点，参数取 --speculative-num-steps 5 --speculative-eagle-topk 4 --speculative-num-draft-tokens 16。背景与问题：灰度期只有内部十几个人在用，实测单用户输出速率从 41 tok/s 涨到 94 tok/s（+129%），接受长度稳定在 3.1，团队据此在评审里写下"投机解码带来 2.3 倍加速"。全量上线后并发涨到 48 路，聚合吞吐只从 3,850 tok/s 涨到 5,620 tok/s（+46%），接受长度掉到 2.2，p99 ITL 反而比灰度期恶化了 30%——评审时承诺的数字对不上，业务方开始质疑这个优化是否值得。方案：放弃单一静态配置，改为按调度器上报的 running 请求数分三档动态调 speculative_num_steps：≤8 路用 5 步、8~32 路用 3 步、>32 路用 1 步并把 topk 压到 1（纯链式，关掉树）；同时把 disable_by_batch_size 设在 96 作为兜底，而不是设在 32 就一刀切关闭。效果：低峰时段保持 +120% 的单用户提速，高峰时段聚合吞吐改善从 +46% 提到 +58%，p99 ITL 从 79 ms 降到 61 ms，草稿器在高峰的算力占用从 31% 降到 9%。关键教训是：单发场景量出来的加速比不能拿去做容量规划，两种负载必须分别压测、分别配参。

投机解码是在"GPU 反正闲着"的时候偷跑几步。批越大，GPU 越不闲，能偷的就越少——但"能偷的变少"不等于"该停止偷"，正确反应是每次少偷几步，而不是彻底不偷。

还有两个容易被忽略的相互作用

第一是显存。草稿器的权重和它自己的 KV 缓存都要从同一块显存里出，等于把 KV 块池压小了。DP11 里讲过，并发数一旦超过 KV 块池能承载的量就会触发抢占重算风暴，GPU 利用率看着很高而有效吞吐在掉。开投机解码之后 KV 池变小，原来安全的 max_num_seqs 就可能变得不安全，所以开投机解码之后必须重新核算并发上限，而不是沿用之前的配置。

第二是 CUDA Graph 的捕获范围。投机解码让每一步实际提交给模型的 token 数从 batch 变成了大约 batch × (k+1)，形状空间比不开投机时大得多。如果 CUDA Graph 的捕获批量范围是按不开投机时的形状设的，投机后相当一部分实际形状会落在捕获范围之外，退化成 eager 执行，单步开销显著上升。这类问题的症状很有欺骗性：接受长度指标一切正常，吞吐却上不去。所以 SGLang 的官方示例里几乎总会同时出现 --cuda-graph-max-bs-decode，这不是装饰。

五、长上下文退化与分层策略

如果只允许记住这一节的一句话，那就是：投机解码的收益随上下文长度单调下降，在很长的上下文上它经常是净负收益。这一点与"并发升高收益下降"是两个独立的衰减轴，需要分别处置。工程上常见的经验区间是：几千 token 的上下文能拿到接近满额的收益，一两万 token 时收益明显收窄，超过 32K 之后加速基本消失甚至倒挂。

为什么长上下文会吃掉收益

原因有三层，混在一起才造成了那么大的落差。

第一层是草稿器的外推问题。草稿头通常是在中短长度的数据上训练的，让它在 30K 上下文上工作，本身就是一次分布外外推：位置编码超出了它见过的范围，需要注意的上下文远比训练时长，融合特征里携带的信息也被摊薄。vLLM 团队在 EAGLE 3.1 的说明里把这一类问题概括为"训练时到推理时的外推能力不足"，而 EAGLE 3.1 的改动正是冲着它去的——官方数据（vLLM 官方博客，2026-05）称在长上下文负载上接受长度相比 EAGLE 3 最多可提升到 2 倍。注意这句话的方向：它说明长上下文退化主要是草稿检查点的问题，换一个训练得更好的检查点可以缓解，不是投机解码这个机制的固有上限。作为对照，AMD 与 vLLM 团队（2026-07）在他们的 EAGLE-3 配方上报告接受长度从 1K 到 32K 提示几乎持平（2.69 到 2.65）——所以"长上下文一定退化"并不是定律，退化程度高度依赖草稿检查点的训练配方。

第二层是显存的挤占效应。长上下文本身就是 KV 显存的大户，再叠加草稿器的权重与草稿 KV，KV 块池被压缩得更狠。结果不是"投机解码变慢了"，而是"并发承载能力下降、抢占变多"，收益从吞吐的另一头漏掉。这类损失在接受长度指标上完全看不出来，只能通过抢占计数器和 KV 使用率发现。

第三层是分母变大。上下文越长，目标模型一次前向本身就越贵（注意力的成本随上下文增长），而草稿器的成本也同步上升。净加速那个式子的分子（接受长度）在退化，分母（相对开销）在膨胀，两头一起挤。

按上下文长度分档

处置方式是把"开不开投机"从一个全局布尔值变成一个按上下文长度分档的策略。这件事有两种实现路径，取决于你的引擎能力和流量画像。

长上下文下的投机解码像是在一场已经很长的会议里插话：上下文越长，你越猜不准别人下一句要说什么，而每次猜错的代价还更高。此时最优策略不是猜得更小心，而是干脆不猜。

与量化组合时必须做质量回归

投机解码本身是无损的，但这个"无损"的前提是验证时用的目标模型分布，就是你上线服务的那个目标模型分布。一旦叠加量化，这个前提会以两种方式被破坏。一种是目标模型被量化了而草稿检查点是针对全精度目标训练的，此时草稿器对齐的是一个已经不存在的分布，接受率会无声地下滑；AMD 与 vLLM 的配方里专门提到要"针对确切的 MXFP4 验证器做冷启动训练"，就是为了避免这个错配。另一种更隐蔽：某些实现为了拿更长的接受长度会使用典型接受这类放宽的判据，它本身就不再严格保分布，与量化叠加后误差来源变成两个，谁贡献了质量下降变得难以归因。

所以规则很简单：投机解码单独上线可以不做质量回归，但和量化一起上线必须做，而且要在同一批评测集上跑三个配置（仅量化、仅投机、量化+投机）才能把责任分清。量化本身的选型与精度损失评估见 DP13 · 模型量化。

示例场景（长上下文误开投机导致净负收益）：某企业长文档问答服务用 vLLM 部署 Qwen3-32B（2×H100，TP=2），平均 prompt 27K token、输出 380 token。背景与问题：团队在短上下文的客服场景上验证过 EAGLE-3 有 +85% 的吞吐收益，于是把同一套配置（num_speculative_tokens: 5）复制到长文档服务，上线后聚合吞吐从 2,180 tok/s 掉到 1,790 tok/s，负 18%，p99 TTFT 也涨了 22%。因为大家的先验是"投机解码不会更慢"，这个问题排查了两天。排查过程：第一步看接受长度，从短上下文场景的 2.9 掉到 1.35——草稿基本没猜对，五步草稿里平均只活了 0.35 个，等于每步白算 4.6 次草稿前向。第二步看抢占计数器，每分钟 210 次（此前接近 0），原因是草稿权重加草稿 KV 吃掉约 11 GB，KV 块池缩小了约 12%，而 max_num_seqs 沿用了开投机之前的值。第三步用 nsys 看到有约 34% 的 decode 步没有命中 CUDA Graph：投机后实际形状是 batch × 6，超出了原先按不开投机捕获的批量范围，这部分步骤退化成了 eager。方案：按 prompt 长度在网关分流，>16K 走未开投机的实例组、≤16K 走开投机的实例组；开投机那组重新按缩小后的 KV 池反推 max_num_seqs（从 128 降到 96）并扩大 CUDA Graph 捕获范围；同时把长上下文那组的草稿检查点升级验证排期，等接受长度实测能站上 2.0 再考虑开启。效果：长上下文实例组关闭投机后吞吐回到 2,225 tok/s（相对最初基线 +2%），短上下文实例组保留投机拿到 +85%，加权后整体吞吐较改造前提升 27%，抢占次数回落到每分钟 3 次以下。教训是：投机解码的配置不能跨场景复制，接受长度必须在目标场景的真实长度分布上重新量一遍。

六、落地参数与踩坑清单

这一节只讲 vLLM 和 SGLang 里与投机解码直接相关的参数怎么配，不做框架横评——两家在架构、生态、适用场景上的完整对比见 DP05 · 大模型推理框架选型。

vLLM：一个 JSON 配置块

vLLM 现在把投机解码的全部配置收在 --speculative-config 一个 JSON 参数里，这也是官方推荐的前向兼容写法；早期版本那套独立标志（--speculative-model、--num-speculative-tokens、--speculative-disable-by-batch-size 等）在过渡版本里仍可用，但新部署不建议再写。

vllm serve Qwen/Qwen3-32B --tensor-parallel-size 4 \
  --speculative-config '{"method":"eagle3",
    "model":"<eagle3-draft-ckpt>",
    "num_speculative_tokens":3,
    "disable_by_batch_size":96}'
vLLM 参数（speculative_config 内）作用取值建议
method算法：eagle / eagle3 / ngram / medusa / mtp 等默认 eagle3；无检查点时退 ngram
model草稿检查点路径。给了 model 时 method 常可自动识别必须与目标模型同族、同词表
num_speculative_tokens草稿长度 k3~5 起步，按接受率实测收敛
disable_by_batch_size排队请求数超过该值时对新请求禁用投机兜底保护，别设太低（见下文）
prompt_lookup_min / prompt_lookup_maxn-gram 方法的匹配窗口下界与上界用 ngram 时必填 max，典型 2~4
disable_padded_drafter_batch关闭草稿批的输入补齐，允许变长序列仅 EAGLE 系有效，且需后端支持

关于 disable_by_batch_size：不少博客建议在生产里设成 32。这个值作为兜底没问题，但如第四节论证过的，批大到 32 时更优的动作是把 k 压到 1~2 而不是整体关闭。所以更合理的用法是把这个阈值设得高一些（作为"再往上就真的不划算了"的保险丝），同时用分档调 k 覆盖中高并发区间。

SGLang：三个参数控制一棵草稿树

SGLang 的参数更细，因为它把草稿树的形状完全暴露给了用户。核心是四个：--speculative-algorithm 选算法（EAGLE3 / EAGLE / STANDALONE / NGRAM / DFLASH 等），--speculative-draft-model-path 给草稿检查点，然后 --speculative-num-steps、--speculative-eagle-topk、--speculative-num-draft-tokens 三个共同决定树的形状。较早的 SGLang 版本里这些标志有 --speculative-algo、--speculative-draft 这样的短别名，遇到旧文档或旧脚本时按上面的语义对应即可。

python3 -m sglang.launch_server --model Qwen/Qwen3-32B \
  --speculative-algorithm EAGLE3 \
  --speculative-draft-model-path <eagle3-draft-ckpt> \
  --speculative-num-steps 3 --speculative-eagle-topk 4 \
  --speculative-num-draft-tokens 16 \
  --mem-fraction-static 0.7 --cuda-graph-max-bs-decode 8
SGLang 参数控制什么调大的后果官方自动默认值
--speculative-num-steps草稿器自回归的深度（即草稿长度 k）投机范围变大，但拒绝级联的风险上升Llama / Grok 系为 5；多数其他模型为 3
--speculative-eagle-topk每一步的分支因子（树的宽度）候选更多样、接受率更高，但显存与算力开销上升Llama / Grok 系为 4；多数其他模型为 1
--speculative-num-draft-tokens一次验证能并行处理的最大草稿 token 数（树的总容量）可评估更深的树，但显存占用上升Llama / Grok 系为 8；多数为 4。topk=1 时自动取 num_steps+1
--speculative-draft-model-quantization草稿模型的量化方式设 unquant 可强制草稿不量化（即使目标模型已量化）跟随目标模型
--speculative-token-mapFR-Spec 的高频 token 子表，降低 lm_head 开销—仅 EAGLE-2 有效，EAGLE-3 会忽略

三个树参数之间有一条硬约束需要理解：num_steps 是深度、eagle_topk 是每层宽度，而 num_draft_tokens 是验证阶段的容量上界，它必须能装下你想要的那棵树，否则树会被截断、白算的分支变多。SGLang 文档明确说明这三个参数应当全都不设（走自动调参）或全都显式设，只设其中一两个是最容易产生怪异行为的做法。要找最优组合，官方给了 bench_speculative.py 脚本在批大小 × steps × topk × num_draft_tokens 的网格上扫；更新的版本还提供了 --auto-spec 这类运行时自动调参控制器，按观测到的接受率为不同批大小挑参数。

真实社区案例（接受长度随运行时长单调衰减）：vLLM 仓库 issue #41838（2026）记录了一个非常值得警惕的失效模式。背景：用户在 vLLM 0.17.1 上用 EAGLE/EAGLE3 草稿模型提供长期在线服务，配置里同时开了 --enable-prefix-caching 与 --kv-cache-dtype fp8。问题：接受长度在服务运行过程中平滑且单调地衰减，且永远不会自行恢复——只有完全重启服务才能回到初始的高值；衰减幅度与各 prompt 类型的流量成正比，只有高流量的 prompt 类型受影响。这类问题极难发现，因为它不报错、不告警，服务在功能上完全正常，只是越跑越慢。方案与效果：社区定位到与投机批次里的前缀缓存复用路径相关，最终在 0.19.1 上完整修复（单独打补丁到 0.17.1 无效，说明还牵涉其他版本间的改动）。这个案例给出一条明确的运维要求：接受长度必须作为一个长期在线指标持续监控，而不是只在压测时量一次。一个只在上线当天量过接受长度的服务，无法区分"投机解码没用"和"投机解码曾经有用但已经悄悄失效"。

上线前必测的四件事

测什么怎么测通过标准
接受率（按位置）用业务真实 prompt 采样，分别统计第 1~k 个草稿位置的通过率首位 > 0.7；若首位 < 0.5 则草稿检查点不可用
接受长度引擎指标直接读，按上下文长度档位分别统计> 2.0 才有明显收益；< 1.5 建议关闭
单发负载吞吐并发 1，看单用户输出速率与 p99 ITL相对基线的提升即"最好情况"，用于设定预期上界
高并发负载吞吐按线上真实并发峰值压测，看聚合吞吐、抢占次数、KV 使用率聚合吞吐不得低于基线；抢占次数不得显著上升
输出质量回归仅在与量化叠加、或使用典型接受这类放宽判据时需要与"仅目标模型"基线在评测集上无统计显著差异

这里要特别强调"单发与高并发两种负载都要测"。绝大多数关于投机解码的翻车，根子都在只测了其中一种：只测单发会得到一个乐观得离谱的加速比，拿去做容量规划会严重高估；只测高并发会得出"没什么用"的结论，白白放弃低峰时段的大幅体验改善。压测的具体口径——TTFT 与 ITL 怎么分开度量、长度分布怎么还原线上重尾特征、饱和点怎么定位——见 DP16 · 推理服务压测方法论；本文只给"投机解码这个特性额外需要看哪些量"。

  • 把接受长度当成一等公民指标接入长期监控和告警，而不是只在压测时看一眼
  • 单发和高并发两种负载分别压测、分别配参，报告里必须写清数字来自哪种负载
  • 高并发时压缩草稿长度与树宽度（k 降到 1~2、topk 降到 1），把整体关闭留作兜底
  • 按上下文长度分档：短上下文开满，超长上下文走未开投机的实例组
  • 开投机之后按缩小后的 KV 池重新反推 max_num_seqs
  • 用 bench_speculative.py 或自动调参器在批大小 × 树形状的网格上扫，别手猜
  • 和量化叠加上线时跑三配置对照（仅量化 / 仅投机 / 两者），把质量责任分清
  • 草稿检查点用业务数据重训一版再评估，通用检查点的接受率不代表你的场景
  • 不要把公开材料里的"2 倍""3.5 倍"当规划依据，那些数字的批大小口径通常没写
  • 不要把在短上下文场景验证过的配置直接复制到长上下文服务
  • 不要一看到高并发就把投机解码整体关掉，先试着把草稿缩短
  • 不要只设 --speculative-num-steps 而让 topk 和 num-draft-tokens 走自动值，三个要么全设要么全不设
  • 不要在只看接受长度正常就断定配置健康，CUDA Graph 未命中会悄悄吃掉全部收益
  • 不要跨模型族混用草稿检查点，词表和版本必须严格对齐
  • 不要期望投机解码改善 TTFT，它只作用于 decode 阶段
  • 不要在没有长期监控的情况下认为"上线时测过就一直有效"

投机解码在生产里不是一个开关，而是一组需要按负载和上下文长度分档的旋钮。任何"开/关"式的二元决策，都必然在某一段流量上留下明显的浪费。

Q&A

投机解码会不会让输出质量变差？它和量化的风险有什么本质区别？
在实现正确的前提下不会。投机解码使用修正拒绝采样来验证草稿：逐位置比对目标模型分布与草稿分布，只接受概率相容的前缀，在第一个被拒绝的位置改用目标模型分布重新采样。这套判据在数学上保证最终每个 token 的分布与直接从目标模型采样完全一致，所以它是无损加速。这一点让它和量化在风险属性上完全不同——量化是拿数值精度换速度，任何一次量化上线都必须做完整的质量回归；而投机解码要担心的从来不是"答案变差"，而是"速度不升反降"。两个例外需要注意：一是某些实现使用典型接受这类放宽的判据来换更长的接受长度，它本身就不再严格保分布；二是与量化叠加时，草稿器对齐的目标分布可能不是你实际上线的那个量化后的分布，这两种情况都需要做质量回归。
接受率和接受长度是什么关系？生产里该盯哪一个？
接受率是单个草稿位置通过验证的概率，通常记作 α，它衡量的是草稿器与目标模型的分布贴合度，也就是草稿器的质量。接受长度是目标模型每完成一次前向验证、最终真正落地到输出里的 token 数，它衡量的是这一步实际赚了多少。两者的关系在链式草稿下有闭式：接受长度等于 1 加上 α 的各次幂之和，也就是 (1 − α 的 k+1 次幂) / (1 − α)，其中 k 是草稿长度。那个常数 1 是兜底 token——即使第一个草稿就被拒绝，目标模型的重采样结果依然是有效输出。生产里两个都要盯但用途不同：接受率用来判断草稿检查点本身够不够好、要不要重训；接受长度用来判断当前配置的收益，因为它能直接和吞吐对应。如果只能选一个长期监控，选接受长度。
为什么说"加速比"这个数字不可信？公开材料里的 2 倍、3.5 倍该怎么读？
因为加速比是一个综合结果，它同时依赖批大小、任务类型、上下文长度、输出长度和硬件，其中任何一项变化都能让它翻倍或减半。同一个 EAGLE-3 检查点在批大小 1 上可能报 3.5 倍，在批大小 64 上就掉到 1 倍附近甚至以下；同一个检查点在代码任务上接受长度可达 3.3，在开放式写作上只有 2.0 出头。所以读到一个加速比时，第一件事是找它的批大小口径和数据集，绝大多数博客不写这两项。正确的读法是把它当作"最好情况的上界"，然后用接受长度做换算：净加速大致等于接受长度除以（1 加上草稿与验证的相对开销）。这个换算能让你在还没压测之前，就先判断某个宣称的数字在自己的负载上是否可能。
EAGLE-3 和 Medusa-2 该怎么选？
默认选 EAGLE-3，除非你不能改动目标模型。两者的结构性差别决定了性能差别：EAGLE-3 是在目标模型的多层融合特征空间里自回归地打草稿，每一步都以上一步的特征为条件，所以草稿内部有依赖建模，接受长度通常能到 2.7 到 3.2；Medusa-2 是在 final hidden 上并排接出若干独立解码头，第 i 个头直接预测未来第 i 个位置，头与头之间互不知情，越靠后的头越不准，接受长度典型只有 2.2 到 2.8。代价方面，EAGLE-3 的草稿器要跑 k 次前向且显存开销约 +20%，Medusa-2 一次前向出全部候选、草稿成本接近零、显存开销更小。Medusa-2 最大的优势是可后挂：不必微调目标模型本体，只训练那几个头，所以当目标模型是外部提供的、权重不允许改动，或者显存极度紧张时，它是更现实的选择。
高并发下到底该不该关掉投机解码？
通常不该关，该缩短。投机解码的收益前提是 GPU 处在访存受限区间——此时 SM 大量空转，多验证几个位置几乎免费。连续批处理会把 GPU 推向算力受限，跨过拐点后草稿的每次前向都在和真实请求抢 SM，收益确实会收窄。但要看清楚衰减来自哪里：草稿开销是随草稿长度 k 线性增长的，而接受长度在 k=1 时是 1 加 α，即使 α 掉到 0.6 也还有 1.6。把 k 从 5 降到 1，开销大约从 80% 回落到 20% 量级，净收益仍在 1.3 倍左右，明显好于关闭。所以生产做法是按 running 请求数分档调 k 与树宽度（高并发时把 topk 压到 1、走纯链式），把 vLLM 的 disable_by_batch_size 设在一个较高的阈值作为兜底保险丝，而不是设在 32 就一刀切关闭。真正随负载恶化的是"固定的长草稿"，不是投机本身。
草稿长度 k 设多少合适？为什么不能一直往大调？
因为收益和成本的增长方式不同。第 k 个草稿位置对接受长度的边际贡献是 α 的 k 次幂，指数衰减；而它的成本是线性的，每加一个位置就要多跑一次草稿器前向。两条曲线必然相交，交点就是最优 k，而 α 越低交点越靠前。举个具体例子：α = 0.85 时把 k 从 5 加到 7 能多拿 0.70 个 token，值得；α = 0.60 时同样的操作只能多拿 0.08 个 token，纯粹是浪费两次前向。实践中的起点是 3 到 5（SGLang 的自动默认值对 Llama 系给 5、对多数其他模型给 3），然后在自己的业务数据上量接受率再收敛。还要叠加负载维度：低并发可以用 4 到 5，接近拐点时降到 2 到 3，算力受限区间降到 1 到 2。
为什么上下文一长，投机解码的加速就消失了？
有三层原因叠加。第一是草稿器的外推问题：草稿头通常在中短长度数据上训练，在很长的上下文上工作属于分布外外推，位置编码超出见过的范围、融合特征携带的信息被摊薄，接受率下滑。第二是显存挤占：长上下文本身就是 KV 显存大户，再加上草稿权重与草稿 KV，KV 块池被进一步压缩，如果并发上限没有相应下调就会触发抢占重算，收益从吞吐的另一头漏掉——这类损失在接受长度指标上完全看不出来。第三是分母变大：上下文越长，目标模型一次前向本身越贵，草稿器成本也同步上升。需要补充一点：这不是机制的固有上限而是检查点的问题。vLLM 官方博客（2026-05）称 EAGLE 3.1 在长上下文负载上的接受长度相比 EAGLE 3 最多可提升到 2 倍，AMD 与 vLLM 团队（2026-07）也报告过他们的配方从 1K 到 32K 提示接受长度几乎持平。所以退化程度高度依赖草稿检查点的训练配方，换检查点值得一试。
SGLang 里 num-steps、eagle-topk、num-draft-tokens 三个参数是什么关系？
它们共同定义了一棵草稿树的形状。--speculative-num-steps 是深度，也就是草稿器自回归往前推几步；--speculative-eagle-topk 是每一步的分支因子，也就是树的宽度，调大能提高候选多样性和接受率，但显存与算力开销上升；--speculative-num-draft-tokens 是验证阶段能并行处理的最大草稿 token 数，相当于树的总容量上界，它必须装得下你想要的那棵树，否则树会被截断、白算的分支变多。官方自动默认值对 Llama / Grok 系是 5 / 4 / 8，对多数其他模型是 3 / 1 / 4；当 topk 设为 1（纯链式，不长树）时 num-draft-tokens 会自动取 num-steps + 1。最重要的一条使用纪律是：这三个参数要么全都不设走自动调参，要么全都显式设置，只设其中一两个最容易产生怪异行为。要找最优组合可以用官方的 bench_speculative.py 在批大小与树形状的网格上扫，新版本还提供了按观测接受率自动调参的运行时控制器。
开了投机解码之后接受长度指标正常，但吞吐没提升，可能是什么原因？
最典型的元凶是 CUDA Graph 捕获范围不足。投机解码让每步实际提交给模型的 token 数从 batch 变成大约 batch × (k+1)，形状空间比不开投机时大得多；如果 CUDA Graph 的捕获批量范围还是按不开投机时的形状设的，相当一部分实际形状会落在捕获范围之外，退化成 eager 执行，单步开销显著上升。这个症状特别有欺骗性，因为接受长度这个指标只反映"草稿猜得准不准"，完全看不出执行路径退化了。诊断方法是用 profiler 看 decode 步的 CUDA Graph 命中率，处置方法是调大捕获上限（SGLang 里是 --cuda-graph-max-bs-decode）。第二个常见原因是显存挤占引发的抢占风暴：草稿权重与草稿 KV 压缩了 KV 块池，而并发上限沿用了开投机之前的值，此时要看抢占计数器和 KV 使用率，并按缩小后的 KV 池重新反推并发上限。
服务跑了几个小时后越来越慢，重启就恢复，和投机解码有关吗？
很可能有关，而且这是一类真实存在过的失效模式。vLLM 仓库 issue #41838（2026）记录了这个现象：在 0.17.1 上用 EAGLE / EAGLE3 草稿模型长期在线服务时，接受长度会平滑且单调地衰减，永远不会自行恢复，只有完全重启服务才能回到初始高值，且衰减幅度与各 prompt 类型的流量成正比。社区定位到与投机批次里的前缀缓存复用路径相关，最终在 0.19.1 上完整修复。这类问题极难发现，因为它不报错、不告警、功能完全正常，只是越跑越慢。它给出的运维要求很明确：接受长度必须作为长期在线指标持续监控并设告警，而不是只在压测时量一次。一个只在上线当天量过接受长度的服务，根本无法区分"投机解码没用"和"投机解码曾经有用但已经悄悄失效"。
投机解码和量化能同时开吗？需要注意什么？
能，而且在生产里经常一起用，但组合之后必须做质量回归。原因是投机解码"无损"的前提是验证时用的目标模型分布，就是你实际上线的那个目标模型分布。一旦叠加量化，这个前提会以两种方式被破坏：一是目标模型被量化了而草稿检查点是针对全精度目标训练的，草稿器对齐的是一个已经不存在的分布，接受率会无声下滑（AMD 与 vLLM 的配方里专门提到要针对确切的量化验证器做冷启动训练，就是为了避免这个错配）；二是如果实现使用了典型接受这类放宽判据，它本身已不严格保分布，与量化叠加后误差来源变成两个，难以归因。所以规则是：投机解码单独上线可以不做质量回归，和量化一起上线必须做，并且要在同一评测集上跑三个配置（仅量化、仅投机、量化加投机）才能把责任分清。另外别忘了显存账——量化省下来的显存有一部分会被草稿器吃掉，并发上限要重新核算。
