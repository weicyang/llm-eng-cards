D03 · 数据预处理

Data Preprocessing — 高质量数据是 AI 系统的基石

一、数据预处理的重要性

模型能力的上限由架构决定，实际表现由数据决定。数据中心 AI 说的就是这件事：同样是一周时间，花在清洗数据上的收益通常比花在调超参上高一个数量级。

Garbage In, Garbage Out

数据质量直接决定模型输出质量。无论模型架构多先进，如果输入数据存在噪声、缺失或格式混乱，最终效果必然大打折扣。

从原始文件到可检索内容的完整链路

PDF / Word / HTML / 图片 / 音频 / 视频 │ ▼ ┌─────────────────────────────────────────┐ │ ① 路由 按扩展名与探测结果选解析器 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ② 解析 文档解析 / OCR / ASR │ │ 产出: 文本 + 版面 + 元数据 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ③ 清洗 Unicode 归一化 → 去标签 │ │ → 去控制字符 → 语言检测 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ④ 统一 一律转成 Markdown 中间格式 │ │ 标题层级 / 列表 / 表格 / 代码 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ⑤ 质量门 打分 + 去重 (MinHash/LSH) │ │ 低分样本转人工复核队列 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ⑥ 分块 策略可配 + 元数据随块携带 │ └───────────────────┬─────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ ⑦ 入库 Embedding → 向量库 upsert │ │ 以文档 ID 为主键，保证幂等 │ └─────────────────────────────────────────┘ 每一步的产物都落盘保留，任一环节出问题 都能从上一步的中间结果重跑，而不必回到原始文件。

预处理在不同场景中的关键作用

场景预处理重点影响
RAG 检索增强生成分块策略、元数据保留、去噪检索精度 & 生成质量

统计显示：数据科学家 60%-80% 的时间花在数据预处理上，而非模型调优。

  • 能举例说明"数据质量差"如何影响 RAG 系统？ — 分块不合理导致上下文碎片化、噪声导致检索偏移
  • 预处理在 ML Pipeline 中的位置：Data Source → Preprocessing → Feature Engineering → Model
  • 理解"数据中心 AI"(Data-Centric AI) 理念：改善数据比改善模型更高效

二、文档解析

PDF、Word、HTML 解析难度的差别，本质是它们各自保留了多少 语义结构：HTML 有 DOM 树，Word 有样式层级，而 PDF 只剩"在某个坐标用某个字体画某个字符"——结构得靠你从坐标里重新猜回来。

HTML 清洗

使用 BeautifulSoup / trafilatura / readability-lxml 提取正文内容，去除导航栏、广告、脚本等噪声。

Word/PPT 解析

python-docx 处理 Word 文档；python-pptx 处理演示文稿；注意保留标题层级和列表结构。

表格提取

  • Camelot — 基于 PDF 坐标，适合规则表格
  • Tabula — Java 底层，需要 JVM 环境
  • Table Transformer — 基于深度学习的表格检测与结构识别

  • 如何处理扫描件 PDF？ — 先 OCR 再解析，或使用 Unstructured 的 hi_res 策略
  • 比较 PyMuPDF 与 pdfplumber 的取舍：速度 vs 表格精度

三、OCR (光学字符识别)

OCR 的准确率往往不是模型决定的，是输入图像决定的。一张倾斜 3 度、带摩尔纹的扫描件，换再强的模型也救不回来——先做图像矫正和 版面分析，才是投入产出比最高的一步。

主流 OCR 引擎

引擎特点语言支持
Tesseract开源、LSTM 模型、社区活跃100+ 语言
PaddleOCR轻量、中文优化、端到端80+ 语言，中文最佳
EasyOCRPyTorch 实现，简单易用80+ 语言
云服务 OCR高精度、按量计费Google Vision / Azure AI / 百度 OCR

版面分析 (Layout Analysis)

在 OCR 之前进行版面分析，识别文档区域（标题、正文、表格、图片）：

  • LayoutParser — 基于 Detectron2 的版面检测
  • DocTR — 端到端文档识别（检测 + OCR）
  • PP-StructureV2 — PaddleOCR 的版面分析模块

OCR 链路：从像素到有序文本

扫描图 / 拍照图 │ ▼ ┌──────────────────────────────────────────┐ │ ① 图像预处理 │ │ 灰度化 → 二值化 (Otsu / 自适应阈值) │ │ 去噪 (中值滤波) → 倾斜校正 (霍夫变换) │ │ 分辨率不足时先超分，OCR 建议 ≥ 300 DPI │ └──────────────────┬───────────────────────┘ ▼ ┌──────────────────────────────────────────┐ │ ② 版面分析 │ │ ┌──────────────────────────────┐ │ │ │ [页眉] │ │ │ │ [标题] │ │ │ │ [正文栏1] [正文栏2] │ │ │ │ [表格区] │ │ │ │ [图片] [图注] │ │ │ │ [页脚 / 页码] │ │ │ └──────────────────────────────┘ │ │ 输出每个区域的 类型 + bbox + 阅读序号 │ └──────────────────┬───────────────────────┘ ▼ ┌──────────────────────────────────────────┐ │ ③ 分区域识别 │ │ 正文区 → 文本行检测 → 逐行识别 │ │ 表格区 → 单元格结构识别 → 按行列还原 │ │ 图片区 → 交给 Caption 模型，不进 OCR │ │ 每条结果附带置信度 │ └──────────────────┬───────────────────────┘ ▼ ┌──────────────────────────────────────────┐ │ ④ 后处理 │ │ 低置信度片段打标记 → 进人工复核队列 │ │ 常见混淆纠错 (0/O、1/l、rn/m) │ │ 语言模型纠错，页眉页脚按版面标签剔除 │ └──────────────────┬───────────────────────┘ ▼ 按阅读顺序拼接的纯文本 + 每段的来源坐标 没有第 ② 步的后果: 双栏论文会把左右两栏逐行交替拼在一起， 读起来每句话都断在半截，后续分块和检索全部作废。

手写体识别

手写识别准确率通常低于印刷体，可用 TrOCR（Microsoft）或专用手写模型增强。对关键场景建议人工复核。

# PaddleOCR 示例
from paddleocr import PaddleOCR
ocr = PaddleOCR(use_angle_cls=True, lang='ch')
result = ocr.ocr('document.png', cls=True)
for line in result[0]:
    text, confidence = line[1][0], line[1][1]
    print(f"{text} ({confidence:.2%})")
  • OCR 精度如何评估？ — 字符级准确率 (CER)、词级准确率 (WER)
  • 如何提升 OCR 质量？ — 图像预处理（二值化、去噪、倾斜校正）+ 后处理（拼写检查、NLP 纠错）
  • 版面分析的意义：决定阅读顺序，区分正文与页眉页脚

四、文本清洗

文本清洗最容易犯的错不是洗得不干净，是洗过头：把全角括号、表格里的竖线、代码里的缩进一并抹平之后，内容看着是"整洁"了，检索时却再也对不上原文了。

去除特殊字符 / HTML 标签

import re
from bs4 import BeautifulSoup

def clean_text(raw):
    # 去除 HTML 标签
    text = BeautifulSoup(raw, "html.parser").get_text()
    # 去除控制字符
    text = re.sub(r'[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]', '', text)
    # 合并多余空白
    text = re.sub(r'\s+', ' ', text).strip()
    return text

Unicode 归一化

使用 unicodedata.normalize('NFKC', text) 统一全角/半角字符、兼容性分解。中文场景需注意繁简转换（opencc）。

分句分段

  • 规则方法：基于标点（。！？）+ 换行符
  • 统计方法：nltk.sent_tokenize、spaCy sentencizer
  • 中文分句：pkuseg、正则匹配中文标点

语言检测

langdetect / fasttext lid 模型 / lingua-py — 用于多语言文档的路由与过滤。

  • 为什么需要 Unicode 归一化？ — 同一字符多种编码（如"ﬁ" vs "fi"），影响匹配和检索
  • 分句与分块的区别：分句是 NLP 基础操作，分块是面向检索/LLM 的工程操作
  • 清洗过度 vs 不足的权衡：过度清洗丢失语义，不足清洗引入噪声

五、格式统一

把所有格式统一成 Markdown，不是因为 Markdown 好看，而是因为它是少数几种既保留了标题层级、又能被大模型直接读懂的格式——中间格式选错，后面每一步都要为它擦屁股。

Markdown 标准化

将各类文档统一转为 Markdown 中间格式，保留结构信息：

  • 标题层级 → # / ## / ###
  • 列表 → 有序/无序列表
  • 表格 → Markdown table 或 JSON
  • 代码块 → fenced code blocks

元数据保留

预处理不应丢弃有价值的元数据：

元数据类型示例用途
文档元数据标题、作者、创建时间过滤、排序
结构元数据章节层级、页码分块参考、定位
来源元数据URL、文件路径溯源、去重
  • 为什么选择 Markdown 作为中间格式？ — 人类可读、保留结构、LLM 友好、工具生态丰富
  • 元数据在 RAG 中的作用：支持混合检索（metadata filtering + semantic search）
  • JSON 模式输出的可靠性：使用 Pydantic / JSON Schema 约束 + 重试机制

六、多模态数据处理

多模态处理的关键抉择只有一个：把图片翻译成文字、塞进同一个向量空间，还是给图片单独建一个空间。前者工程简单、可检索性好，后者信息损失小但复杂度翻倍——多数团队应该先选前者。

图像描述生成 (Image Captioning)

  • BLIP-2 / LLaVA / GPT-4V — 为图片生成文字描述
  • 应用：将文档中的图表转为文字，使 LLM 能"理解"图片内容
  • 对比图 → 结构化描述 → 嵌入索引

音频转文字 (ASR)

# OpenAI Whisper 示例
import whisper
model = whisper.load_model("large-v3")
result = model.transcribe("meeting.mp3", language="zh")
print(result["text"])
# 支持时间戳、多语言、说话人分离(需额外工具)

视频帧提取

视频处理流程：关键帧提取 → OCR/Caption → 音轨 ASR → 时间对齐 → 合并文本

  • ffmpeg — 帧提取、音频分离
  • scenedetect — 场景切换检测
  • 采样策略：固定间隔 vs 场景变化 vs 运动检测
  • 多模态 RAG 如何处理图片？ — 方案A：图片转文字描述后索引；方案B：多模态 Embedding（CLIP）
  • Whisper 的局限：长音频需分段、噪声环境精度下降、说话人分离需 pyannote
  • 视频帧采样策略的选择依据：信息密度、存储成本、处理时间

七、数据分块 (Chunking)

分块 是在两种失败之间找平衡：块太小，一个答案被切成两半，检索到哪半都答不全；块太大，一个块里混着三个主题，向量被平均成一个没有指向性的中间值。

分块策略对比

策略原理优点缺点
固定长度分块按字符/Token 数切分简单、可预测可能切断语义
语义分块按 Embedding 相似度切分语义完整计算开销大
递归分块按分隔符层级递归切分平衡长度与语义依赖分隔符质量
Markdown Header 分块按标题层级切分保留文档结构仅适用于结构化文档
代码分块按函数/类/模块切分保留代码逻辑需要 AST 解析

Overlap 策略

相邻块之间保留重叠部分（通常 10%-20%），防止关键信息被切断：

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=64,        # ~12% overlap
    separators=["\n\n", "\n", "。", "；", " "],
    length_function=len
)
chunks = splitter.split_text(document)

四种分块策略的切点差异

同一段原文，四种切法的落刀位置: 原文 ## 安装步骤 · 先下载安装包 · 然后执行 install.sh · 注意需要 root 权限 ## 常见问题 · 报错 permission denied 时 · 检查是否用 sudo 运行 固定长度 (每 40 字硬切) ├────────────────┤├────────────────┤├────────────────┤ 切点落在句子中间，"注意需要" 和 "root 权限" 被分到两个块 递归分块 (按 \n\n → \n → 。→ 空格 逐级降级) ├──────────────────────┤├──────────────────────┤ 优先在段落边界下刀，长度不够再降级到句号，通用且够用 Markdown 标题分块 (按 ## 切) ├────── 安装步骤 ──────┤├────── 常见问题 ──────┤ 切点与作者的语义边界完全重合，前提是文档真有标题 语义分块 (逐句算相邻 Embedding 余弦相似度) 句1─句2─句3 │ 句4─句5 相似度 0.91 0.88 │ 0.42 │ 0.89 ▲ 相似度骤降处 = 话题切换点 检索时的 Parent-Child 组合: 索引侧 检索命中 返回给 LLM ┌────────┐ │ 子块 1 │ ──┐ ├────────┤ │ 用小块算相似度 ┌──────────────┐ │ 子块 2 │ ──┼─► 精确定位到子块 2 ─►│ 父块 (完整章节) │ ├────────┤ │ └──────────────┘ │ 子块 3 │ ──┘ └────────┘ 同属一个父块 小块保证检索精度，大块保证上下文完整， 代价是要多存一层父子映射关系。

分块大小选择

经验法则：检索场景 256-512 tokens；生成场景 512-1024 tokens；需根据 Embedding 模型最大输入长度和检索精度权衡。

  • 分块大小如何影响 RAG 效果？ — 太小丢失上下文，太大引入噪声、降低检索精度
  • 语义分块的实现思路：滑动窗口计算相邻句子 Embedding 余弦相似度，相似度骤降处切分
  • 何时用递归分块 vs 语义分块？ — 递归分块通用高效，语义分块适合无明确结构的长文本
  • Parent-Child 分块策略：小块检索 + 大块返回，兼顾精度与上下文

八、数据质量评估

质量评估最有价值的产出不是那个分数本身，而是被打了低分的那一小撮样本——它们几乎总能精确指向上游某个解析器的一个具体 bug，比任何抽样统计都管用。

质量维度

维度检查内容方法
完整性缺失字段、截断内容、空白页Schema 验证、长度统计
准确性OCR 错误、乱码、编码问题字符分布检测、拼写检查
一致性重复数据、格式不统一、矛盾信息去重 (MinHash/SimHash)、规则校验
时效性过期内容、版本冲突时间戳检查、增量对比

自动质量评分

def quality_score(chunk):
    scores = {
        "length": min(len(chunk) / 200, 1.0),
        "language": detect_language_confidence(chunk),
        "encoding": check_encoding_issues(chunk),
        "info_density": compute_entropy(chunk) / max_entropy,
    }
    return sum(scores.values()) / len(scores)

人工抽检

自动化筛选 + 人工审核结合：对低质量评分、边界 case 进行人工复核，持续校准自动评分规则。

  • 如何大规模去重？ — MinHash + LSH 近似去重，适合百万级文档
  • 数据质量与模型质量的关系：质量提升 10% 通常比模型参数翻倍效果更好
  • 质量评估应放在 Pipeline 哪个阶段？ — 清洗后、入库前，作为 Gate 机制

九、ETL 管道

预处理管道的健壮性几乎等价于 幂等性：只要重跑一遍不会产生第二份数据，任何失败就都只是"再跑一次"，而不是一次需要人工收拾的数据事故。

批处理 vs 流处理

特性批处理流处理
延迟高（定时触发）低（近实时）
吞吐高中等
复杂度较低较高
适用场景知识库初始化、定期更新实时文档索引、新闻流
工具Airflow, Prefect, DagsterKafka, Flink, Celery

编排工具

  • Apache Airflow — DAG 编排、社区大、插件丰富
  • Prefect — Python 原生、动态 DAG、现代 UI
  • Dagster — 资产导向、类型系统、可观测性强
入库一律用文档 ID 做 upsert

以稳定的来源标识（文件路径哈希 + 块序号）为主键写向量库。重跑同一批文档只会覆盖，不会翻倍。

中间产物全部落盘

解析结果、清洗后 Markdown、分块 JSON 各存一份。改了分块策略只需从 Markdown 重跑，不必重新解析几万个 PDF。

每个块都带上溯源元数据

来源路径、页码、标题路径、处理时间戳跟着块一起进库。答案出错时能一秒定位到原文，也支持按来源做增量删除。

别在管道里悄悄丢弃失败样本

解析异常只 catch 不记录，最后表现为"知识库里就是查不到那份文档"。失败样本要进死信队列并有计数告警。

别用文件修改时间当唯一水位线

同步工具、容器挂载、批量拷贝都会改写 mtime，导致要么全量重跑要么漏处理。用内容哈希配合修改时间双重判断。

别在没有评估集的情况下调分块参数

chunk_size 从 512 改成 1024 到底变好还是变坏，只能靠一组带标准答案的查询来回答，凭感觉调等于随机游走。

    watermark = get_last_watermark()
    # 2. 仅获取新增/修改的文档
    new_docs = source.get_changes_since(watermark)
    # 3. 预处理 & 入库
    processed = preprocess(new_docs)
    upsert_to_vectordb(processed)
    # 4. 更新水位线
    update_watermark(new_docs.latest_timestamp)

关键设计原则：幂等性（重复执行不会产生副作用）、可观测性（日志/指标/告警）、容错性（断点续传、重试机制）。

  • 为什么需要幂等性？ — 失败重试时不会产生重复数据或副作用
  • Airflow vs Prefect 选择：团队规模、Python 熟练度、动态 DAG 需求
  • 增量更新中如何处理文档删除？ — 软删除标记 + 定期清理；或 CDC (Change Data Capture)
  • 如何监控 ETL 管道健康？ — 处理延迟、失败率、数据量波动告警

Q&A（Top 10）

什么是"Garbage In, Garbage Out"？在 AI 系统中如何体现？

GIGO 指输入数据质量差，输出结果必然差。在 AI 系统中：RAG 若索引了噪声数据，检索结果不相关导致幻觉；训练数据有标注错误，模型学到错误模式；微调数据格式不一致，模型输出不稳定。解决方案是建立系统化的数据预处理管道，在数据进入模型前确保质量。

比较 PyMuPDF、pdfplumber 和 Unstructured 三种 PDF 解析方案的适用场景？

PyMuPDF(fitz)：速度最快，适合大批量纯文本 PDF 提取，API 简洁但表格解析能力一般。pdfplumber：表格提取精确，能获取字符坐标信息，适合含复杂表格的 PDF，但速度较慢。Unstructured：统一抽象层，自动检测文档类型并选择最优解析器，支持 OCR 策略配置，适合构建通用文档处理管道，但引入额外依赖。选择建议：简单文本用 PyMuPDF，复杂表格用 pdfplumber，通用管道用 Unstructured。

RAG 系统中，分块大小如何选择？有什么经验法则？

分块大小需平衡检索精度与上下文完整性。经验法则：检索为主的场景用 256-512 tokens（小块更精确）；生成为主的场景用 512-1024 tokens（大块上下文更完整）。需考虑：①Embedding 模型最大输入长度；②LLM Context Window 容量；③文档本身特点（技术文档可小些，叙事文本需大些）。建议用评估集 A/B 测试不同分块大小的检索效果。Parent-Child 策略可兼得：小块检索定位，返回其父块提供完整上下文。

语义分块 (Semantic Chunking) 的原理是什么？与递归分块有何区别？

语义分块：将文本按句拆分，计算相邻句子的 Embedding 余弦相似度，当相似度低于阈值（即话题切换）时切分。优势是切分点与语义边界对齐。递归分块：按分隔符层级（如 \n\n → \n → 。→ 空格）递归切分，直到块大小满足要求。优势是实现简单、速度快、可预测。区别：语义分块依赖 Embedding 模型有额外计算开销，但对非结构化长文本效果更好；递归分块通用性强，是 LangChain 默认策略，适合大多数场景。

如何处理多模态文档中的图片和表格？

图片处理方案：①生成文字描述（BLIP-2/GPT-4V）后当文本索引；②使用多模态 Embedding（CLIP）直接嵌入向量空间；③OCR 提取图中文字。表格处理方案：①转为 Markdown 表格保留结构；②转为自然语言描述（"该表显示了…"）；③保留为结构化 JSON 并在检索时特殊处理。选择依据：图片信息密度高时用 Caption；表格数据精确时保留结构化格式；综合场景可同时索引多种表示。

OCR 质量如何提升？从预处理到后处理有哪些手段？

预处理：图像二值化（Otsu/自适应阈值）、去噪（中值滤波/形态学操作）、倾斜校正（霍夫变换检测角度）、分辨率增强（超分辨率模型）。OCR 阶段：选择适合的引擎（中文用 PaddleOCR，多语言用 Tesseract）、配置合适的 PSM 模式、使用版面分析确定阅读顺序。后处理：拼写检查纠错、NLP 语言模型纠错、正则规则修正常见错误模式、置信度过滤（低于阈值标记待审核）。系统层面：建立反馈闭环，收集人工修正的 case 持续优化。

ETL 管道中的"幂等性"是什么？为什么重要？

幂等性指同一操作执行多次与执行一次的结果相同。在 ETL 管道中，网络故障、超时等导致任务需要重试，如果操作非幂等（如不检查就 INSERT），重试会导致重复数据。实现幂等的方法：①使用 UPSERT 而非 INSERT；②处理前检查文档 hash 是否已存在；③使用唯一标识符作为去重键；④事务性地更新水位线。在向量数据库场景：以文档 ID 为主键执行 upsert，确保重新处理不会产生重复向量。

Unicode 归一化有哪几种形式？为什么在文本处理中必须做？

四种形式：NFC（规范组合）、NFD（规范分解）、NFKC（兼容组合）、NFKD（兼容分解）。实践中多用 NFKC：将兼容字符统一（如全角"Ａ"→半角"A"，连字"ﬁ"→"fi"，圈数字"①"→"1"）。必须做的原因：①相同视觉字符可能有不同 Unicode 编码，导致字符串比较失败；②影响检索精度（用户查询与索引内容编码不一致）；③影响去重判断。中文场景额外注意：繁简转换（opencc）、异体字处理。建议在 Pipeline 最前端统一执行归一化。

如何设计一个生产级的文档预处理 Pipeline？

设计要点：①输入层：支持多格式（PDF/HTML/Word/图片），使用工厂模式按文件类型路由到对应解析器；②解析层：文档解析 + OCR + 版面分析，输出统一中间格式（Markdown + 元数据 JSON）；③清洗层：Unicode 归一化、去噪、语言检测、质量评分；④分块层：可配置的分块策略，保留元数据与层级关系；⑤输出层：生成 Embedding，写入向量数据库，更新索引；⑥工程保障：幂等处理、断点续传、监控告警、日志追踪、增量更新。技术选型：Prefect/Airflow 编排 + Redis 消息队列 + S3 中间存储。

批处理与流处理在数据预处理中如何选择？可以混合使用吗？

选择依据：数据时效性要求（实时索引需流处理）、数据量（大批量初始化用批处理更高效）、复杂度预算（流处理运维成本更高）。典型混合架构（Lambda/Kappa）：批处理负责全量重建和历史数据回填；流处理负责增量更新和实时文档索引。实现示例：用 Airflow 每日全量跑质量检查和重建索引；用 Kafka + Celery worker 实时处理新上传文档。关键是保证两条路径的处理逻辑一致（代码复用），最终结果可合并且不冲突。
