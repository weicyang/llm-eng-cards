D05 · 搜索引擎基础

Search Engine Fundamentals — 从爬虫到语义搜索的完整知识图谱

一、搜索引擎架构

四段流水线的分工很清楚：爬虫决定你有什么，索引决定你能多快找到，召回决定漏不漏，排序决定准不准。

全流程概览

┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  爬虫     │───▶│  索引     │───▶│  检索     │───▶│  排序     │
│ Crawler   │    │ Indexer   │    │ Retrieval │    │ Ranking   │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
     │                │                │                │
 网页抓取         构建倒排索引      查询匹配         相关性排序
 URL管理          文本分析          候选召回         多信号融合
 去重/Robots      压缩存储          布尔/短语        L2R模型

各模块详解

  • 爬虫 (Crawler/Spider)：从种子URL出发，BFS/DFS抓取；需处理robots.txt、去重（SimHash/URL规范化）、增量抓取
  • 索引 (Indexer)：核心是构建倒排索引；包含文本分析（分词、去停用词、词干化）、文档解析
  • 检索 (Retrieval)：根据查询词在倒排索引中查找匹配文档，返回候选集（召回阶段）
  • 排序 (Ranking)：对候选文档进行相关性打分；从传统 TF-IDF/BM25 到现代 Learning to Rank

倒排索引的核心地位

倒排索引是搜索引擎的心脏。它将"文档→词项"的正排关系翻转为"词项→文档列表"，使得查询可以在 O(1) 时间定位到相关文档集合，是实现高效全文检索的基础数据结构。

💡 关键要点

  • 能画出搜索引擎四阶段流水线，说明各阶段核心任务
  • 解释为什么倒排索引比正排索引更适合搜索场景
  • 爬虫去重策略：URL归一化、内容指纹（SimHash）、布隆过滤器
  • 召回 vs 排序的区别：召回追求高召回率，排序追求高精度

二、倒排索引 (Inverted Index)

倒排索引就是把"这篇文章有哪些词"反过来记成"这个词出现在哪些文章里"，于是查询从扫全库变成了求几条列表的交集。

查询 "搜索 引擎" │ ▼ 分析器：分词 → 去停用词 → 小写 / 词干归一化 ["搜索", "引擎"] │ ▼ 词典（Term Dictionary，FST / 前缀树）定位词项，O(词长) 不是 O(词表大小) "搜索" ──▶ Posting List: [doc1:3, doc4:1, doc7:2] "引擎" ──▶ Posting List: [doc1:2, doc3:1, doc7:5] │ ▼ 求交（Skip List 直接跳过不可能命中的区段，避免逐条比对） 候选 [doc1, doc7] │ ▼ 逐条打分 BM25(q, d)，只算候选，不算全库 doc7: 8.4 doc1: 6.1 │ ▼ Top-K 小顶堆 ──▶ 用正排 / DocValues 取原文做摘要与高亮 ──▶ 返回 Posting List 落盘前先 Delta Encoding 再 VByte：排序后的 DocID 差值小，压缩比才上得去

核心结构

词项 (Term)        →  Posting List
─────────────────────────────────────────
"搜索"            →  [doc1:3, doc4:1, doc7:2]
"引擎"            →  [doc1:2, doc3:1, doc7:5]
"算法"            →  [doc2:4, doc5:1, doc6:3]

每个Posting = (文档ID, 词频TF [, 位置信息])

Posting List 详解

字段说明用途
DocID文档标识符定位文档
TF (Term Frequency)该词在文档中出现次数相关性打分
Position词在文档中的位置列表短语查询/邻近查询
Payload自定义附加信息boost权重等

压缩技术

  • Delta Encoding (差值编码)：存储文档ID差值而非绝对值 
    原始: [101, 105, 108, 115, 120]
差值: [101,   4,   3,   7,   5]  ← 数值更小，压缩率更高
  • VByte (Variable Byte Encoding)：用可变长度字节编码整数 
    每字节7位存数据 + 1位标志(是否最后一字节)
小数字 → 1字节, 大数字 → 多字节
例: 130 → [0x01, 0x82] (需要2字节)
  • 其他压缩：PForDelta、Simple9/16、Roaring Bitmap

索引构建过程

  1. 文档收集与预处理（分词、去停用词、词干化/lemmatization）
  2. 为每个文档生成(term, docID, position)三元组
  3. 按 term 排序，合并相同 term 的 posting
  4. 对 posting list 做压缩（Delta + VByte）
  5. 写入磁盘（分块构建 → 多路归并，处理内存限制）

💡 关键要点

  • 倒排索引 vs 正排索引：正排是 doc→terms，倒排是 term→docs
  • Delta Encoding 为什么有效：排序后的 DocID 差值小，压缩比高
  • Skip List 在倒排索引中的作用：加速多关键词 AND 查询的交集运算
  • 索引更新策略：全量重建 vs 增量索引（索引合并策略）
  • 内存受限时如何构建大规模索引：SPIMI/BSBI 算法

三、TF-IDF

TF-IDF 的全部智慧就一句话：一个词在这篇里出现得越多越重要，在全库里出现得越普遍越不重要。

公式推导

TF(t,d) = 词项t在文档d中出现的次数 / 文档d的总词数

IDF(t) = log(N / df(t))
  N = 文档总数, df(t) = 包含词项t的文档数

TF-IDF(t,d) = TF(t,d) × IDF(t)

变体形式

TF 变体公式特点
原始频率f(t,d)简单但偏向长文档
对数TF1 + log(f(t,d))抑制高频词影响
布尔TF1 if t∈d else 0只关心是否出现
归一化TFf(t,d) / max(f(t',d))消除文档长度差异

为什么有效

  • TF的直觉：一个词在文档中出现越多次，该文档与这个词的相关性越高
  • IDF的直觉：在越少文档中出现的词，区分度越高（"的"出现在所有文档中→无用；"量子计算"只出现在少数文档→有区分力）
  • 组合效果：同时考虑词的文档内重要性和全局稀有性

局限性

一句话：TF 线性增长无饱和（高频词霸榜）、未做文档长度归一化（长文档天然占优）、参数固化，且无法捕捉词序与语义。BM25 用 k1 词频饱和与 b 长度归一化修复了前两大缺陷，缺陷的量化分析与 BM25 改进详解见 G05 · TF-IDF 与 BM25 算法对比。

💡 关键要点

  • 能手写 TF-IDF 公式并解释每个部分的意义
  • IDF 为什么取 log：压缩数值范围，避免极端值
  • TF-IDF 的局限引出 BM25 的改进方向
  • 实际中 IDF 的平滑处理：log((N - df + 0.5)/(df + 0.5))

四、BM25

BM25 相对 TF-IDF 只改了两件事——让词频饱和有上限、让长文档吃点亏，而这两件事恰好是 TF-IDF 最疼的两个地方。

公式推导

BM25(q, d) = Σ IDF(t) × [ f(t,d) × (k1 + 1) ] / [ f(t,d) + k1 × (1 - b + b × |d|/avgdl) ]

其中：
  f(t,d) = 词项t在文档d中的词频
  |d| = 文档d的长度(词数)
  avgdl = 平均文档长度
  k1 = TF饱和参数 (典型值: 1.2~2.0)
  b = 文档长度归一化参数 (典型值: 0.75)
  IDF(t) = log((N - df(t) + 0.5) / (df(t) + 0.5) + 1)

相对 TF-IDF 的两大改进

改进1：TF 饱和 (Saturation)

当 k1 固定时，TF 分数随词频增加趋向上界 (k1+1)，不再线性增长——词出现 100 次不应比 50 次重要 2 倍。k1 控制饱和速度：k1 → 0 接近布尔模型（只关心是否出现），k1 → ∞ 退化为原始 TF（线性增长）。

改进2：文档长度归一化

参数 b 控制长度惩罚力度：b = 0 完全不考虑文档长度，b = 1 完全按比例归一化（默认 0.75）。直觉：长文档自然包含更多词 → 同样词频在长文档中的权重应适当降低。

k1/b 在不同语料库上的调参经验、词频饱和的实测数据（高频词干扰降 37%）与 BM25F/BM25+ 等变体详解，见 G05 · TF-IDF 与 BM25 算法对比。

Elasticsearch 中的 BM25

  • Elasticsearch 5.0+ 将默认相似度模型从 TF-IDF 切换为 BM25
  • 默认参数：k1=1.2, b=0.75
  • 可在 mapping 中自定义："similarity": {"my_bm25": {"type":"BM25","k1":1.5,"b":0.8}}

示例场景：一个技术文档站的站内搜索，语料里既有 200 字的 FAQ，也有 2 万字的手册章节。问题：用默认 b=0.75 时，长手册章节几乎垄断首屏——它们碰巧包含更多查询词，而用户真正想要的往往是那条短 FAQ。方案：把 b 提到 0.9 加重长度惩罚，同时用 BM25F 给 title 字段 3 倍权重。效果：人工评测的 NDCG@10 从 0.61 升到 0.74，首屏点击率提升约 18%。

💡 关键要点

  • 手写 BM25 公式，解释 k1 和 b 的物理含义
  • BM25 vs TF-IDF：饱和效应 + 长度归一化
  • k1=0 退化为 IDF-only，k1→∞ 退化为线性TF
  • 为什么 Elasticsearch 默认使用 BM25 而非 TF-IDF
  • BM25F：字段级 BM25 扩展（title权重 > body权重）

五、Elasticsearch / Lucene

一个 ES 索引 = 若干 Shard，一个 Shard = 一个 Lucene 索引 = 若干不可变 Segment。所谓"近实时"的那 1 秒，就是 refresh 生成新 Segment 的节奏。

index 请求 │ ▼ Translog（先追加落盘，宕机可重放，保证不丢） │ ▼ Memory Buffer ──refresh（默认 1s）──▶ 新 Segment 进 FS Cache，此刻起可被搜到 │ flush（默认 30 分钟或 translog 写满） │ └──▶ Segment 真正落盘 + 清空 translog │ ▼ merge：小 Segment 合并成大 Segment 被标记删除的文档要到这一步才真正消失 一次搜索 = 遍历该 Shard 的每个 Segment 各取 Top-K ──▶ 归并 ──▶ 再跨 Shard 归并 所以 Segment 数量直接决定搜索延迟：refresh 越频繁，小 Segment 越多，查询越慢

架构概览

Elasticsearch Cluster
├── Node 1 (Master Eligible)
│   ├── Index: products
│   │   ├── Shard 0 (Primary)
│   │   └── Shard 2 (Replica)
│   └── Index: logs
│       └── Shard 1 (Primary)
├── Node 2 (Data Node)
│   ├── Shard 1 (Primary)
│   └── Shard 0 (Replica)
└── Node 3 (Coordinating)
    └── 路由请求、合并结果

每个 Shard = 一个完整的 Lucene Index
Lucene Index = 多个 Segment (不可变)
Segment = 倒排索引 + 正排数据 + DocValues

Shard 与 Replica

概念说明目的
Primary Shard数据的主分片水平扩展写入/存储
Replica Shard主分片的副本高可用 + 读取负载均衡
SegmentLucene最小索引单元(不可变)近实时搜索(refresh)

示例场景：一个日志检索集群，每天写入约 2 亿条，索引按天切分。问题：为了"实时看日志"把 refresh_interval 设成 200ms，结果每个 Shard 积累出上万个小 Segment，一次搜索要遍历全部 Segment，P99 从 300ms 涨到 4s，merge 线程长期打满 CPU。方案：写入高峰期把 refresh_interval 放宽到 30s，昨日索引写完后执行 force merge 到 1 个 Segment 并置为只读。效果：单 Shard 的 Segment 数从上万降到个位数，P99 回到 350ms，CPU 占用下降约四成。

分析器 (Analyzer)

Analyzer = Character Filter → Tokenizer → Token Filter

示例：自定义中文分析器
{ "analyzer": { "my_chinese": {
    "type": "custom", "tokenizer": "ik_max_word",
    "filter": ["lowercase", "stop", "synonym"],
    "char_filter": ["html_strip"] } } }

流程: "<p>搜索引擎优化</p>"
  → html_strip: "搜索引擎优化"
  → ik_max_word: ["搜索引擎", "搜索", "引擎", "优化"]
  → lowercase/stop: ["搜索引擎", "搜索", "引擎", "优化"]

与向量搜索的集成

  • Elasticsearch 8.x 原生支持 dense_vector 字段类型
  • 支持 kNN 搜索 (HNSW 算法) + 与传统BM25的混合查询
  • 向量维度支持到 4096 维 (适配大语言模型 embedding)
// kNN + BM25 混合查询

    "field": "embedding",

    "k": 10,

  },

}

💡 关键要点

  • Shard数量设置后不可变，Replica数量可动态调整
  • Segment不可变 → 删除用标记位 → Merge时真正删除
  • near-realtime搜索原理：refresh(默认1s)生成新Segment
  • 分析器三层架构：CharFilter → Tokenizer → TokenFilter
  • filter vs must：filter不参与打分 + 可缓存，性能更好

六、语义搜索

稠密检索解决的是"说法不同但意思相同"，稀疏检索解决的是"这几个字必须一模一样"。稀疏的短板是词汇鸿沟，稠密的短板是精确匹配，两边刚好互补。

查询 q │ ┌─────────────┴─────────────┐ ▼ ▼ BM25 倒排召回 Dense 向量召回 Top-100 Top-100（HNSW / IVF） 精确词、型号、报错码强 同义词、跨语言、口语化表述强 │ │ └─────────────┬─────────────┘ ▼ RRF 融合：score(d) = Σᵢ 1 / (k + rankᵢ(d)) k 常取 60 只看名次不看分数，天然规避两路分数量纲不一致的问题 ▼ Cross-Encoder 精排（query 与 doc 拼接后联合编码） ▼ Top-10 ──▶ 返回用户 / 送入 LLM

Dense Retrieval (Bi-Encoder)

查询 Query  ──→  [Encoder_Q] ──→  q ∈ ℝᵈ
                                        ↓
                                   cos(q, d) → score
                                        ↑
文档 Doc    ──→  [Encoder_D] ──→  d ∈ ℝᵈ

训练目标: 相关(q,d⁺)的相似度 > 不相关(q,d⁻)的相似度
损失函数: InfoNCE / Triplet Loss / Contrastive Loss

代表模型: DPR, ColBERT, E5, BGE, GTE

稀疏 vs 稠密检索对比

维度稀疏检索 (BM25)稠密检索 (Dense)
表示方式高维稀疏向量(词袋)低维稠密向量(embedding)
匹配方式精确词汇匹配语义相似度
优势精确匹配强、可解释、零样本泛化语义理解、同义词/跨语言
劣势词汇鸿沟(vocabulary mismatch)需要训练数据、领域适配
索引倒排索引ANN索引(HNSW/IVF)
延迟极低(毫秒级)较低(需ANN加速)
存储较小(压缩倒排)较大(浮点向量)

Hybrid Search (BM25 + Dense)

一句话：BM25 与 Dense 并行召回，再将两路结果融合排序——主流融合是 RRF（只看排名不看分数，规避两路分数量纲不一致），也可用线性加权或级联，实测混合 Recall@10 比单一方法高 10-15%。融合算法对比、分数归一化与生产级调参，详见 G07 · RAG 混合检索避坑指南。

💡 关键要点

  • Bi-Encoder vs Cross-Encoder：效率vs精度的权衡
  • 稠密检索为什么需要hard negatives训练
  • 混合搜索为什么通常优于单一模式：互补性（精确匹配+语义理解）
  • ColBERT的late interaction设计：token级交互，比Bi-Encoder精度更高
  • ANN索引(HNSW/IVF)如何加速稠密检索

七、Learning to Rank (LTR)

Learning to Rank 的三种范式，区别只在于喂给模型的是一个文档、一对文档，还是一整个列表——粒度越大，越接近真正要优化的排序指标。

三种范式

范式输入损失函数代表模型
Pointwise单个(q,d)对回归/分类Loss线性回归, GBDT
Pairwise文档对(d₁,d₂)偏序LossRankSVM, RankNet, LambdaRank
Listwise整个文档列表直接优化排序指标LambdaMART, ListNet, SoftRank

Pointwise

  • 将排序问题转化为回归/分类问题
  • 输入：特征向量x(q,d)，标签y∈{0,1,2,3,4}(相关度等级)
  • 缺点：忽略文档间的相对顺序，不直接优化排序指标

Pairwise

  • 学习文档间的偏序关系：d₁ 应排在 d₂ 前面
  • RankNet损失：L = -y·log(P) - (1-y)·log(1-P)，其中 P = σ(s₁-s₂)
  • 优点：直接建模相对顺序；缺点：文档对数量O(n²)，头部位置权重不够

Listwise → LambdaMART

  • LambdaRank：在RankNet梯度上乘以|ΔNDCG|，让交换排名对NDCG影响大的文档对获得更大梯度
  • LambdaMART = LambdaRank + MART(GBDT)：工业界经典，微软Bing搜索长期使用
  • 特征工程：BM25分、PageRank、CTR、文档质量、查询-文档匹配度等

评估指标

NDCG@k = DCG@k / IDCG@k
DCG@k = Σᵢ₌₁ᵏ (2^relᵢ - 1) / log₂(i + 1)

MRR = 1/|Q| × Σ 1/rank_i (第一个相关文档的排名倒数)

MAP = 1/|Q| × Σ AP(q) (各查询Average Precision的均值)
指标特点适用场景
NDCG考虑多级相关度+位置折扣多级标注的排序评估
MRR只关心第一个正确结果问答/导航型查询
MAP二值相关+所有位置信息检索标准评测

💡 关键要点

  • 三种范式的核心区别：输入粒度（单文档/文档对/文档列表）
  • LambdaMART为什么在工业界广泛使用：可解释性+效果好+特征工程灵活
  • NDCG公式手推：DCG + IDCG归一化
  • NDCG vs MAP：是否支持多级相关度
  • 深度LTR模型趋势：BERT-based reranker（Cross-Encoder精排）

八、搜索与 RAG

在 RAG 里，检索后端唯一的 KPI 是"含答案的那一段有没有进 Top-K"，而不是相似度数字多好看。融合两路召回时优先用 RRF，它只依赖名次，不需要给分数做归一化。

搜索引擎作为 RAG 检索后端

RAG 中的最佳实践

  • Chunking策略：固定大小滑动窗口 / 语义分段 / 递归字符分割
  • 多路召回：BM25(精确匹配) + Dense(语义) + Sparse Embedding(学习型稀疏)
  • Reranker精排：Cross-Encoder对Top-K重新打分，提升精度
  • 上下文压缩：提取与Query最相关的句子片段，减少Token消耗
  • 先用一批真实 query 建评测集，用 Recall@K 决定召回策略，而不是凭感觉调参
  • 召回阶段宁可多召（K=50~100），把精度交给 Reranker
  • 混合检索用 RRF 融合名次，避免 BM25 分数与余弦相似度直接相加
  • chunk 里保留标题和章节路径，检索和生成两个阶段都用得上
  • 不要只上稠密检索，型号、报错码、专有名词这类精确匹配它最容易漏
  • 不要在召回阶段用 Cross-Encoder，对十万级候选跑交叉编码是算不完的
  • 不要把 chunk 切得过小，句子级切分会让上下文断裂、答案拼不完整
  • 不要每次查询都跑 HyDE，多一次 LLM 调用的延迟未必换得回召回提升

💡 关键要点

  • RAG中搜索引擎的角色：高效召回相关文档片段
  • HyDE的原理及为什么在某些场景下有效
  • ES vs 向量数据库的选型决策树
  • Chunking大小对RAG效果的影响：过大→噪声多，过小→上下文不足
  • Reranker在RAG中的位置：召回后、送入LLM前

Q&A（Top 10）

Q1: 倒排索引和正排索引有什么区别？各自适合什么场景？

正排索引 (Forward Index)：文档ID → 词项列表。给定文档ID，快速获取该文档的所有词项。适合已知文档ID需要获取内容的场景。

倒排索引 (Inverted Index)：词项 → 文档ID列表。给定查询词，快速找到包含该词的所有文档。适合全文检索场景。

搜索引擎以倒排索引为核心，因为用户输入关键词→找文档是最常见的操作模式。正排索引用于文档摘要生成、高亮显示等已知文档的后处理。

Q2: BM25相比TF-IDF有哪些改进？为什么效果更好？

两大改进：① TF 饱和——词频贡献有上界 (k1+1)，避免高频词导致分数畸高；② 文档长度归一化——通过 b 和 avgdl 惩罚过长文档。本质是让评分符合词频边际效用递减、且对不同长度文档公平比较。改进的量化实测数据（高频词干扰降 37%、MS MARCO MRR@10 +48%）与 k1/b 调参详解，见 G05 · TF-IDF 与 BM25 算法对比。

Q3: Elasticsearch的Shard和Segment有什么区别？

Shard (分片)：ES层面的概念，是数据分布的基本单位。一个Index被切分为多个Shard分布在不同节点上，实现水平扩展。Shard数创建后不可修改。

Segment (段)：Lucene层面的概念，是最小的索引单元。每个Shard包含多个Segment。Segment一旦写入即不可变(immutable)，新文档写入新Segment，删除只是标记。

关键区别：Shard解决分布式扩展问题，Segment解决并发写入和近实时搜索问题。Segment定期merge以减少碎片和清理已删除文档。

Q4: 稠密检索(Dense Retrieval)和稀疏检索(BM25)各自的优缺点？什么时候用混合搜索？

一句话：稀疏(BM25)精确匹配强、无需训练、可解释，但有词汇鸿沟（不懂同义词）；稠密语义理解强、支持跨语言，但精确匹配弱、需训练数据。大多数真实查询同时需要精确匹配与语义理解，故用混合搜索，以 RRF 或线性加权融合两路结果。BM25 与向量检索互补性的详细论证见 G05 · TF-IDF 与 BM25 算法对比，融合方法细节见 G07 · RAG 混合检索避坑指南。

Q5: 解释LambdaMART的核心思想，为什么在工业界广泛使用？

核心思想：LambdaMART = LambdaRank + GBDT。LambdaRank的关键insight是：在计算文档对的梯度时，乘以交换这两个文档排名后NDCG的变化量|ΔNDCG|。这样头部位置的错误排序获得更大的梯度，直接优化了NDCG指标。

工业界广泛使用的原因：

  • 效果好：直接优化最终评估指标(NDCG)，排序质量高
  • 可解释性：基于GBDT，特征重要性透明
  • 灵活性：可接入数百个异构特征(文本、行为、质量等)
  • 效率高：推理速度快，适合在线服务
  • 成熟稳定：经过大规模生产环境验证（Bing、Yahoo等）
Q6: NDCG和MAP指标有什么区别？各自适合什么场景？

NDCG (Normalized Discounted Cumulative Gain)：

  • 支持多级相关度标注(0-4级)
  • 位置折扣：排名越靠后，贡献衰减越大(log折扣)
  • 通过IDCG归一化到[0,1]
  • 适合：有精细相关度标注的排序评估

MAP (Mean Average Precision)：

  • 只支持二值相关(相关/不相关)
  • 计算每个相关文档位置的精确率，取平均
  • 适合：二值相关标注、传统信息检索评测(TREC)

核心区别：NDCG适合"多级相关"场景(搜索)，MAP适合"是否相关"的二值场景(问答/去重)。

Q7: 在RAG系统中，如何选择搜索引擎还是向量数据库作为检索后端？

选搜索引擎(ES/OpenSearch)的情况：

  • 需要混合查询(关键词+语义+结构化过滤)
  • 已有ES基础设施和运维经验
  • 文档有丰富的元数据需要过滤
  • 需要全文高亮、聚合分析等附加功能

选向量数据库(Milvus/Pinecone)的情况：

  • 纯语义搜索为主
  • 向量规模极大(亿级别)
  • 需要最优的向量检索性能(QPS/延迟)
  • 从零开始搭建，无历史包袱

最佳实践：很多生产系统采用"ES做全文+过滤，向量DB做语义召回，Reranker做融合精排"的三层架构。

Q8: 什么是HyDE？为什么在某些RAG场景中有效？

HyDE (Hypothetical Document Embeddings)：

  1. 用户输入Query
  2. LLM根据Query生成一个"假设性答案"(即使可能不完全准确)
  3. 将假设答案编码为向量，用该向量检索真实文档

为什么有效：

  • Query通常很短(3-5词)，embedding信息量有限
  • 假设答案是完整段落，与目标文档的文体/长度/语义更接近
  • 解决了query-document的表示不对称问题(asymmetry gap)

局限：增加一次LLM调用延迟；如果LLM生成方向错误，会误导检索。适合对延迟不敏感的离线/异步RAG场景。

Q9: Elasticsearch分析器(Analyzer)的三层架构是什么？中文搜索需要注意什么？

三层架构：

  1. Character Filter：字符级预处理(html_strip去标签, mapping替换字符)
  2. Tokenizer：分词(standard/ik_max_word/jieba等)
  3. Token Filter：词级后处理(lowercase/stop/synonym/stemmer)

中文搜索注意事项：

  • 必须使用中文分词器(ik_smart/ik_max_word/jieba)，standard按字切分不可用
  • ik_max_word(细粒度) vs ik_smart(粗粒度)：索引时用max_word保证召回，查询时用smart保证精度
  • 同义词词典/自定义词典需要维护
  • 拼音分词器处理拼音搜索需求
Q10: 搜索系统中的召回(Recall)和排序(Ranking)阶段有什么区别？为什么要分两阶段？

召回阶段：

  • 目标：从海量文档(亿级)中快速筛选候选集(千级)
  • 追求高召回率，可容忍一定误差
  • 模型轻量(BM25/Bi-Encoder)，延迟要求严格(ms级)

排序阶段：

  • 目标：对候选集精细排序，输出最终结果(Top-10)
  • 追求高精度/NDCG，精排模型可以重
  • 模型复杂(Cross-Encoder/LambdaMART)，延迟相对宽松

为什么分两阶段：计算效率。对10亿文档跑Cross-Encoder不现实(O(N)×高复杂度)。用轻量模型先过滤到千级候选，再用重模型精排，是计算资源和排序质量的最优平衡。实际工业系统甚至是多阶段漏斗：粗召回→粗排→精排→重排。
