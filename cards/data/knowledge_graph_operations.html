D07 · 知识图谱生产运维与质量评测

三类漂移 / 增量构图代价 / 实体冲突消解 / 图质量指标 / GraphRAG-Bench 三阶段评测 / 图版本化与回滚

知识图谱的难点从来不是把它建出来——那件事现在用大模型一个流水线就能跑完。难的是让它在半年后依然可信：实体在改名、关系在过期、每一次增量更新都在悄悄降低图的质量，而这些退化不会报错，只会让检索结果一点点变差，直到有人发现答案早就不对了。

这张卡讲的是图谱上线之后的事。怎么从零建一张图——三元组、命名实体识别、关系抽取、知识表示学习——在 D02 知识图谱；GraphRAG 的抽取与社区摘要在 G21；轻量变体的选型在 G28；图存储引擎在 B04。这里只回答一个问题：图已经跑起来了，怎么让它不烂掉。

一、上线之后才出现的三类漂移

图谱建成的那一刻是它质量的最高点，之后只会下降。原因不难理解：图是对某个时间切片上的世界的描述，而世界一直在变。把这种退化拆开看，有三种形态，它们的检测方法和处置成本完全不同。

三类漂移里最危险的是关系过时，因为它不会让系统"找不到答案"，而是让系统"自信地给出旧答案"。缺实体至少还会退化成召回不足，用户能感知到；关系过时给出的是格式完整、语气笃定、内容错误的回答，最难被发现。

时效性是图 RAG 的公认弱项

这不是某个实现的问题，而是这条技术路线的共性短板，学界已经量化过。GraphRAG-Bench 论文（厦门大学与香港理工大学，ICLR 2026，arXiv:2506.05690）在综述前人工作时引用了两组数据：在 Natural Questions 上，GraphRAG 的准确率比普通向量 RAG 低 13.4%；而在需要实时知识更新的时效性问题上，准确率下降达 16.6%。另一组来自不同研究的数据显示，图检索在 HotpotQA 的多跳问题上把推理深度提升了 4.5%，代价是平均延迟高出 2.3 倍。

这两组数字放在一起，给出了图谱运维的基本判断：图结构换来的是推理深度，付出的是时效性和延迟。所以运维的重点不是让图变得更大更全，而是让那部分会过期的知识及时失效。

二、增量构图：三条路径的代价不对称

知识库更新会转化成对图的三种操作：追加新文档、更新已有文档、删除文档。多数团队只为第一种做了设计，结果在后两种上翻车。它们的代价差异比直觉大得多。

三条路径的处理链路 ① 追加（便宜） 新文档 ──▶ 抽实体关系 ──▶ 与已有节点匹配 ──▶ 缝进图 │ └─ 只需处理新增部分 ② 更新（中等） 改动文档 ──▶ 重抽 ──▶ diff 出变化的三元组 │ ├─ 新增的：直接加 ├─ 消失的：不能直接删！见 ③ └─ 改值的：需要判断是纠错还是时序变化 ③ 删除（最贵） 删除文档 ──▶ 找出该文档支撑的所有三元组 │ ▼ ┌──────────────────────┐ │ 逐条检查证据来源 │ │ │ │ 边 A ← 只有这篇文档支撑 │──▶ 可以删 │ 边 B ← 还有另外 3 篇支撑│──▶ 不能删， │ │ 只减一个来源 └──────────────────────┘ │ ▼ 还要检查：删完之后有没有节点变成孤岛

为什么删除最难

核心原因是证据溯源（provenance）：图里的一条边通常由多篇文档共同支撑。删掉其中一篇，这条边不一定该消失——它可能还有另外三篇文档在支撑。如果建图时没有记录"这条边是由哪些 chunk 抽出来的"，删除操作就无法正确执行，只剩两个糟糕的选择：要么保守地什么都不删（图里残留已被删除文档的知识，在合规场景下这是事故），要么激进地把相关边全删（误伤其他文档提供的正确知识）。

操作需要触及的范围成本主要风险
追加新文档抽出的实体与关系，加上与之匹配的已有节点与新增量线性相关新实体与已有实体重名，静默产生重复节点
更新该文档的全部三元组，做一次 diff约为重抽一遍该文档把"事实发生了变化"误判为"之前抽错了"，丢掉时序信息
删除该文档支撑的所有边，逐条回查其他证据来源取决于溯源索引的完备程度无溯源时无法正确执行；漏删在合规场景是事故
社区重算（若有社区层）全图与语料总量相关，与增量无关成本与增量大小脱钩，加一篇文档也可能触发全量重算

建图时多存一份"每条边由哪些 chunk 支撑"的溯源索引，成本是存储上的几个百分点；不存的话，删除功能基本就做不了。这是知识图谱工程里回报率最高的一个前期决定，而它常常被跳过，因为在建图阶段没人想到删除。

示例场景：某企业内部制度图谱在建设时只做了追加路径。半年后法务要求下线一批已废止的旧制度文件，团队才发现无法定位这些文件贡献了哪些边——最终只能全量重建，耗时三天并中断了依赖该图的问答服务。补做溯源索引后，同类下线操作的耗时降到分钟级，代价是图存储体积增加约 8%。这 8% 如果在第一天就付，能省掉后面所有的麻烦。

更新里的一个隐蔽陷阱

文档更新时 diff 出"某条三元组的值变了"，有两种完全不同的解释：一种是之前抽错了现在纠正（应该覆盖旧值），另一种是事实本身发生了变化（应该保留旧值并加时间戳，形成时序关系）。把后者当成前者处理，图就丢失了历史——你再也回答不了"这家公司去年的负责人是谁"。区分方法通常要看源文档的性质：如果是同一份文档被修订，多半是纠错；如果是新版本文档描述了新状态，多半是事实变化。这个判断做不到全自动，但至少应该把它显式化，而不是默认覆盖。

三、实体冲突消解：合并是有损操作

实体冲突有两个方向，工程上经常被混为一谈，但它们的错误代价完全不对称。

方向问题例子后果
同实体不同名（需要合并）一个实体被建成多个节点"苹果公司""Apple Inc."" AAPL"图被切碎，每个节点只连着部分证据，多跳路径断裂
同名不同实体（需要拆分）多个实体被合成一个节点两个都叫"张伟"的员工；作为公司和作为水果的"苹果"关系错连，检索返回完全无关的内容

这两类错误的可修复性差别巨大：漏合并是无损的，过度合并是有损的。没合并的两个节点后来发现是同一个，随时可以合；错误合并的两个实体一旦融成一个节点，它们各自的边就混在了一起，事后几乎无法准确拆回。所以消解策略的默认倾向应该是保守——宁可漏合，不可错合。

三种策略与它们的适用边界

策略做法成本适用
规则与词典维护别名表、缩写映射、大小写与标点归一低，但需人工维护实体集合稳定、命名有规范的领域（如产品目录、组织架构）

上下文仲裁把候选节点的邻居关系一并交给大模型判断是否同一实体高，每次判断一次调用只用于灰区样本，不做全量

实践中三者是组合使用的：规则先扫掉最明显的一批（成本几乎为零），嵌入相似度处理大部分，剩下的灰区交给上下文仲裁或人工。关键是阈值要设得保守，并把灰区显式留出来——很多系统的问题不在于用了嵌入相似度，而在于把阈值调得太松，把"可能是"当成"就是"。

在线仲裁还是离线批处理

时机优点缺点建议
在线（写入时判断）图始终保持一致，无脏数据窗口拖慢写入；单条决策看不到全局，容易误判只做规则与词典这类确定性高的部分
离线（定期批处理）能看到全量分布，聚类质量更好；可人工复核两次批处理之间图里存在重复节点嵌入聚类与灰区仲裁放这里
示例场景：某医疗知识图谱把嵌入相似度阈值从 0.92 降到 0.85 以提高合并率，节点数如愿减少了约 12%，但两个月后发现两种症状名相近的不同疾病被合并成了一个节点，导致问答系统把两种疾病的治疗方案混着返回。回滚时才意识到合并操作没有留痕，无法定位到底哪些节点是那次批处理合并的，最终只能从三个月前的图快照重建并重放增量。这次事故之后团队立了一条规矩：任何自动合并都写一条可逆的合并记录。

四、图质量仪表盘：该盯的五个指标

要发现静默的质量退化，得有量化指标。GraphRAG-Bench 为图构建阶段设计了一组结构性指标，可以直接拿来当运维仪表盘的骨架，再补上几个运维视角的指标。

本节的指标定义与参考数值来自 GraphRAG-Bench 论文（arXiv:2506.05690，ICLR 2026）及其官方评测仓库 · 数值依语料领域差异很大，下表的"参考区间"只用于说明量级，不能当作跨语料的达标线。

指标衡量什么偏低意味着偏高意味着
节点数 / 边数知识覆盖范围与语义连接密度抽取太保守，大量知识没进图可能混入噪声实体，不一定是好事
平均度全局连通性，跨节点遍历是否高效图碎片化，多跳检索无路可走连接稠密，但要警惕虚假关联
平均聚类系数局部连通性，子图是否内聚缺少紧密社区，不适合局部推理子图连贯，利于局部推理
非孤立实体占比有多少节点真正参与了关系网络大量孤岛节点，等于白抽—
平均连通分量大小图被切成了多少个互不相连的块知识被割裂在小岛上—

参考数值：什么叫"稀疏得没法用"

论文对现有主流基准语料做了结构分析，结果很能说明问题。UltraDomain 虽然平均实体数（170.6）和关系数（73.2）看着不低，但平均度最高只有 0.86，平均连通分量大小仅 2.7，非孤立实体占比约 40%，只有 9% 的实体度数大于 3。这样的图本质上是一堆两两配对的孤岛，几乎没有可供遍历的路径——建了图但享受不到图的好处。

作为对照，GraphRAG-Bench 自建的语料在医疗与小说两个子集上的平均度分别是 1.05 和 2.27，非孤立实体占比 0.48 和 0.66，平均分量大小 3.15 和 3.99。差距不在数量级上，但结构质量的差别足以改变结论。

看图质量先看非孤立实体占比，它比节点总数诚实得多。抽出十万个实体听着很厉害，如果六成是孤岛，那就是十万个躺在库里不产生任何检索价值的字符串——你花了 LLM 的钱，买到的是一张向量库都不如的表。

更大的图不等于更好的图

这是 GraphRAG-Bench 明确写进结论建议里的一条：关系更多不等于性能更好，优质的图需要的是紧密连接的社区，那种结构里蕴含着隐式的多跳知识，同时便于快速遍历。论文观察到 HippoRAG 2 构建的图明显更稠密——在小说数据集上每万 token 语料平均产出 523 个节点、2310 条边，医疗数据集上是 598 个节点、3979 条边——而它的检索召回率也确实高于其他基线。但这里的因果是"结构质量高导致效果好"，不是"边多导致效果好"。

示例场景：某团队发现图谱多跳召回不理想，于是放宽了关系抽取的提示词，要求模型尽可能多抽关系。边数涨了 2.6 倍，但检索准确率反而下降——新增的边大量是"相关""涉及"这类语义空洞的泛关系，它们在图上制造了大量虚假路径，让 PageRank 类的传播算法把不相关的节点也顶了上来。回退后改成收紧关系类型白名单，边数只有原来的 1.3 倍，召回和准确率同时改善。教训是：加边之前先问这条边承载了什么可用于推理的信息。

五、评测：基准量的到底是什么

图质量指标只能说明图建得好不好，说明不了系统答得对不对。要评测端到端效果，需要覆盖全链路的基准。GraphRAG-Bench 的设计思路值得借鉴，因为它明确地把评测拆成了三个阶段——这正是自建评测体系时最该照搬的结构。

检索侧的两个指标必须成对看：证据召回率高但上下文相关性低，说明系统靠"多捞"来保证不漏，代价是塞了一堆废料进上下文；反过来则是捞得精准但会漏。只看其中一个，优化方向一定会跑偏。

四档任务：难度分层比总分更有用

GraphRAG-Bench 把问题按认知难度分成四档，而不是笼统地给一个总分。这个设计直接催生了它最重要的一条观察。

任务档位要求主要指标
事实检索从语料里定位一个明确事实准确率、ROUGE-L
复杂推理串联多个相互关联的事实准确率、ROUGE-L
上下文归纳综合大范围内容做总结准确率、覆盖度
创造性生成基于语料生成新内容准确率、忠实度、覆盖度

论文在这套分层下得到的第一条观察是：在不需要跨概念推理的简单事实检索任务上，普通 RAG 与 GraphRAG 打平甚至更好。这与前面提到的 Natural Questions 上低 13.4% 是同一个现象的不同侧面。它对运维的意义很直接——如果你的线上问题里事实检索占大头，那么图谱的投入很难在总分上体现出来，评测时应该按档位分开看，否则简单问题会把复杂问题上的提升稀释掉。

一个容易被忽略的成本项：上下文膨胀

论文的另外两条观察讲的是 token 开销。GraphRAG 因为要把实体、关系和原文片段一起送进上下文，prompt 长度显著高于普通 RAG：微软 GraphRAG 的 global 模式最高可达 4 万 token，LightRAG 约 1 万 token 量级，HippoRAG 2 相对紧凑，约 1 千 token 量级。更麻烦的是这个长度随任务难度单调上升——微软 GraphRAG global 模式从简单任务的 7,800 token 一路涨到复杂任务的 4 万 token。

过长的上下文不只是贵，它还会引入冗余信息、拉低上下文相关性，反过来损害答案质量。所以论文给出的建议之一是主动管理上下文增长：给图检索设搜索边界，别让它无限扩散。这一点在运维上应该落成一个硬指标——监控每次查询实际送进模型的 token 数，设上限并告警。

还有一条对选型有影响的发现：GraphRAG 对底层模型能力的依赖比普通 RAG 强得多。论文用 Qwen2.5 系列做了对照，普通 RAG 从 3B 到 14B 的平均分基本持平（56.13 到 59.10），而 GraphRAG 涨幅明显（57.08 到 63.91），拐点出现在 7B——低于这个规模，模型没有足够的推理能力去消化图结构带来的上下文，图就白建了。

六、版本化、回滚与运维实践

前面五节的所有问题最终都汇到同一个工程需求上：图必须是可回滚的。因为图的退化是静默的，等你发现问题时，往往已经过去了好几轮增量更新，唯一可靠的补救就是回到某个已知良好的版本再重放。

三种版本化方案

方案做法存储成本回滚粒度适用
定期快照按天或按周对全图打快照高，与图规模和保留期成正比快照点图规模中等、更新不频繁
变更日志记录每次增删改的操作流水，支持重放与逆放低单次操作更新频繁、需要精确定位
影子图双写新版本在与线上隔离的另一份图上构建，跑完验证再整体切换约两倍版本级重大变更（换抽取模型、改 schema）

实践中通常是快照加变更日志的组合：快照提供便宜的粗粒度还原点，变更日志负责在快照之间做精确重放。影子图只在重大变更时启用——比如换了抽取用的大模型，或者调整了关系类型白名单，这类改动会影响全图，值得先在影子图上跑一遍质量门禁再切。

门禁里最有价值的一项是回归问题集上的证据召回率。维护一组几十到几百条的固定问题，每条标注好正确答案应该依赖哪些证据；每次图变更后重跑一遍，看证据还能不能被捞回来。这个信号比任何结构指标都直接——结构指标告诉你图看起来正常，回归集告诉你图还能不能用。

  • 建图第一天就记录每条边的证据来源，这是删除功能的前提
  • 给时效性关系打时间戳，定期统计过期边占比
  • 实体合并保留可逆的操作记录，别做不留痕的原地融合
  • 消解阈值设保守，把灰区显式留出来交人工或延后处理
  • 维护固定的回归问题集，每次图变更后跑一遍证据召回
  • 评测按任务难度分档看，别用总分掩盖分项退化
  • 监控每次查询送入模型的 token 数并设上限
  • 别把"节点数增长"当成质量改善的证据
  • 别为了提高召回放宽关系抽取，泛关系会制造虚假路径
  • 别在写入路径上做嵌入相似度合并，单条决策看不到全局分布
  • 别默认文档更新就是纠错，那会丢掉事实的时序变化
  • 别只测最终答案，那样定位不了瓶颈在哪一阶段
  • 别在 7B 以下的模型上指望图结构带来收益
  • 别在没有快照和变更日志的情况下跑批量合并

知识图谱运维和数据库运维的心智模型是一样的：你不是在维护一份数据，你是在维护一条能把数据恢复到任意时点的链路。区别只在于图的损坏不会抛异常，所以质量门禁得由你自己造出来。

Q&A

知识图谱上线后最常见的质量退化是什么？
是关系过时，也就是那些带时效性的关系（任职、隶属、持股、价格、职责）仍然停留在建图时的旧值。它之所以比实体缺失更危险，是因为缺实体会退化成"找不到答案"，用户能感知；而关系过时给出的是格式完整、语气笃定、内容错误的回答，很难被发现。这不是某个实现的缺陷而是路线共性：GraphRAG-Bench 论文引用的数据显示，图 RAG 在需要实时知识更新的时效性问题上准确率下降达 16.6%，在 Natural Questions 上整体比普通向量 RAG 低 13.4%。运维上的对策是给关系打时间戳，把"超过有效期的边占比"做成常规监控指标，而不是等用户投诉。
为什么从图谱里删除一份文档的知识那么难？
因为一条边通常由多篇文档共同支撑，删掉其中一篇不代表这条边就该消失。要正确执行删除，必须能回答"这条边是由哪些 chunk 抽出来的、去掉这一篇之后还有没有其他证据"，这需要建图时就记录证据溯源。没有溯源索引的话只剩两个糟糕选项：保守地什么都不删，让已删除文档的知识残留在图里（合规场景下这是事故）；或者激进地把相关边全删，误伤其他文档提供的正确知识。溯源索引的存储开销通常只有个位数百分比，但它是删除功能能否实现的分水岭，值得在建图第一天就做。
实体合并的阈值该往松还是往紧调？
往紧。核心理由是两类错误的可修复性完全不对称：漏合并是无损的——两个节点后来发现是同一个，随时可以合；过度合并是有损的——两个实体一旦融成一个节点，它们各自的边混在一起，事后几乎无法准确拆回。所以默认倾向应该是保守，把既不能确认也不能排除的灰区显式留出来，建"疑似同一"的软链接并进人工复核队列，而不是让算法猜。另外无论阈值怎么设，每次自动合并都要写一条可逆的操作记录，否则出问题时你连"哪些节点是那批合并的"都查不到，只能从旧快照重建。
怎么判断一张知识图谱的结构质量够不够用？
先看非孤立实体占比，它比节点总数诚实得多——抽出十万个实体，如果六成是孤岛，那就是十万个不产生任何检索价值的字符串。接着看平均度（衡量全局连通性，决定跨节点遍历是否走得通）和平均聚类系数（衡量局部内聚，决定适不适合局部推理）。有个现成的反面参照：GraphRAG-Bench 论文分析现有基准语料时发现，UltraDomain 的平均度最高只有 0.86、平均连通分量大小 2.7、非孤立实体约 40%、只有 9% 的实体度数大于 3——这种图本质上是一堆两两配对的孤岛，建了但享受不到图的好处。作为对照，该基准自建语料的平均度在 1.05 到 2.27 之间。
多抽一些关系能不能提高图 RAG 的效果？
通常不能，而且经常适得其反。GraphRAG-Bench 把这条明确写进了结论建议：关系更多不等于性能更好，优质的图需要的是紧密连接的社区，那种结构蕴含隐式的多跳知识且便于快速遍历。放宽抽取提示词换来的往往是"相关""涉及"这类语义空洞的泛关系，它们在图上制造大量虚假路径，让相关性传播类算法把不相关的节点顶上来，召回涨了准确率反而掉。论文里 HippoRAG 2 确实构建了更稠密的图（小说数据集每万 token 语料约 523 节点、2310 边）且效果更好，但因果是"结构质量高导致效果好"，不是"边多导致效果好"。加边之前应该先问这条边承载了什么可用于推理的信息。
评测图 RAG 系统时，为什么不能只看最终答案的准确率？
因为答错了你定位不了瓶颈在哪一段。GraphRAG-Bench 的设计值得照搬：把评测拆成图构建、知识检索、最终生成三个阶段分别打指标。构建阶段看节点数边数、平均度、平均聚类系数；检索阶段看上下文相关性和证据召回率；生成阶段才看答案正确性、ROUGE-L、覆盖度、忠实度。检索侧的两个指标还必须成对看——证据召回高但上下文相关性低，说明系统靠"多捞"来保证不漏，代价是塞了一堆废料进上下文；反过来则是捞得精准但会漏。只盯一个，优化方向一定跑偏。另外任务难度也要分档统计，否则简单问题会把复杂问题上的提升稀释掉。
图谱变更前应该卡哪些质量门禁？
四项结构指标加一项端到端回归。结构侧检查非孤立实体占比没有下降、平均度没有显著下降、节点数变化落在预期区间——这三条能拦住大部分"抽取配置改坏了"的情况。但最有价值的是第四项：在固定的回归问题集上跑证据召回率。维护几十到几百条问题，每条标注正确答案应该依赖哪些证据，每次图变更后重跑一遍看证据还能不能被捞回来。结构指标告诉你图看起来正常，回归集告诉你图还能不能用，后者才是真正的验收标准。重大变更（换抽取模型、改 schema、调关系白名单）建议先在影子图上构建并跑完门禁，通过后再切换，不通过就阻断并保留影子图供排查。
小参数模型上做图 RAG 值得吗？
7B 以下基本不值得。GraphRAG-Bench 用 Qwen2.5 系列（3B、7B、14B）做过对照实验，普通 RAG 的平均分从 3B 到 14B 基本持平（56.13 到 59.10），说明它对模型规模不敏感；而 GraphRAG 的涨幅明显（57.08 到 63.91），拐点出现在 7B。原因是图检索送进上下文的不只是文本片段，还有实体、关系和结构信息，模型需要足够的推理能力才能把这些结构化上下文消化成答案——能力不够时，多出来的结构信息只是噪声。所以在小模型上部署图 RAG，很可能付出了建图的成本却拿不到收益，这种场景下普通向量 RAG 是更划算的选择。
