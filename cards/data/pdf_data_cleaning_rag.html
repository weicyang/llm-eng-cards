D06 · PDF 数据清洗（RAG 场景）

PDF Data Cleaning for RAG — 从原始 PDF 到高质量结构化文本的完整链路

一、PDF 数据清洗概述

PDF 难在它是给打印机看的，不是给程序看的。整套清洗工作说到底只在做一件事：把"坐标加字符"重新猜回"标题、段落、表格、代码"。

为什么 PDF 清洗是 RAG 的核心难题

PDF 是"显示格式"而非"语义格式"——它只描述"在坐标(x,y)用字体F画字符C"，没有段落、标题、表格的显式语义标记。直接提取文本会丢失结构、引入噪声，导致 RAG 检索精度急剧下降。

PDF 文档的 5 种典型场景

场景特征清洗难度典型来源
常规 PDF有文本层、无干扰元素⭐Word/LaTeX 导出
PDF + 水印/广告有文本层，含遮罩/Banner/水印⭐⭐⭐网络下载的技术书
含表格的 PDF表格结构复杂，需恢复行列关系⭐⭐⭐报告、论文、规格书
扫描版 PDF整页是位图，无文本对象层⭐⭐⭐⭐扫描件、拍照件
扫描版 + 水印/广告/导航栏位图上叠加广告像素或矢量层⭐⭐⭐⭐⭐网络流传的扫描书

核心原则：宁可少提取，不引入噪声。所有清洗操作应仅打标志，不直接删除数据，保留用户手动恢复的可能性。

  • PDF 为什么比 HTML 难解析？ — PDF 是面向渲染的格式，没有 DOM 树，文字块之间无父子/兄弟关系
  • 数据清洗在 RAG Pipeline 中的位置：PDF → 清洗/去噪 → Markdown → 分块 → Embedding → 向量库
  • "文本零损失"原则：清洗只打标记不删内容，最终输出时才按标记过滤，确保误判可逆

二、常规 PDF 的处理流水线

十个阶段听着复杂，其实只做两件事：先给每个文字块贴标签（标题 / 正文 / 代码 / 噪声），再按标签决定输出什么。这样拆开之后，中间任何一步判错，下一步都还有机会兜回来。

启发式布局分类算法

1. 统计全文档所有字体大小出现次数
2. 水印过滤：出现页数 ≥ 总页数×70% AND 字体 >20pt → 排除
3. 正文字体 = 出现次数最多的非水印字体
4. 标题判定：
     ≥1.8× 正文字体 → TITLE（# 一级标题）
     ≥1.4× 正文字体 → HEADING（## 二级标题）
5. 代码块：等宽字体 OR 字体名匹配 monospace 白名单
6. 列表项：以 • - （ 数字 等起头
7. 其余 → PARAGRAPH

文字提取核心实现

文字提取基于 PyMuPDF（import fitz）：调用 page.get_text("dict", flags=fitz.TEXT_PRESERVE_WHITESPACE) 直接从 PDF 对象层读取，得到 blocks → lines → spans 的嵌套结构。过滤掉非文本块（type != 0）后，遍历到 span 粒度，记录每段文字的文本、字体名、字号与 bbox。由于读取的是"字符流"而非"渲染结果"，这一步不受任何视觉遮罩影响，随提取附带的元数据则是后续布局分类与噪声检测的基础。

封装 TextBlock 时，从原始字段派生出两个布尔标志，它们是整个下游链路的起点：

实现要点说明
get_text("dict") 模式保留字体名/字号/bbox 元数据，是布局分类的输入；TEXT_PRESERVE_WHITESPACE 保留空白以便对齐判断
过滤 type != 0dict 结构中 type 0 才是文本块，图像块直接跳过（另行处理）
三级迭代 blocks → lines → spansspan 是携带字体信息的最小单元，在此层停下可保留最大灵活性
加粗判断检查 span["font"] 是否含 "Bold"，作为标题识别的辅助信号
等宽判断span["flags"] 第 3 位为等宽标志（flags & (1 << 3)），是代码块识别的第一道防线

for block_data in text_dict.get("blocks", []):
    if block_data.get("type") != 0:   # 仅保留文本块
        continue
    for line in block_data.get("lines", []):
        for span in line.get("spans", []):
            # text/font/size/bbox + 加粗/等宽标志
  • 为什么用 get_text("dict") 而非 get_text("text")？ — dict 模式保留字体名/大小/bbox 等元数据，是后续布局分类的基础
  • 启发式布局分类 vs AI 模型分类的 trade-off：启发式零依赖、速度快、可解释，但对复杂版面力不从心
  • 为什么正文字体定义为"出现次数最多的字体"？ — 统计假设：正文占文档绝大多数内容

三、水印与广告清洗（有文本层的 PDF）

广告盖住正文只是渲染层面的事。文本对象 和 绘图对象 在文件里各存各的，你读字符流的时候，那块遮罩根本不存在。

核心原理：PDF 是分层文件

PDF 内部有三类独立对象：

对象类型包含信息提取 API
文本对象 (Text Spans)字符串 + 字体 + 字号 + bbox + 颜色page.get_text("dict")
绘图对象 (Drawings)矩形/路径 + 填充色 + 透明度page.get_drawings()
图像对象 (Images)嵌入位图 + bbox + 尺寸page.get_images(full=True)

"广告盖住正文" = 上层绘图对象（深色/半透明矩形）画在下层文本对象之上。视觉上覆盖，但在文件层面两个对象各自独立存在，文字永远不会因为上面有遮罩而消失。

页面对象的叠放次序与各自的读取口

渲染时看到的 (自下而上叠放): ┌────────────────────────────────────────┐ │ z=3 文本对象：广告文案 "扫码进群" │ ← 要去掉的是它 ├────────────────────────────────────────┤ │ z=2 绘图对象：半透明深色矩形 (Banner) │ ← 视觉上的遮挡来自它 ├────────────────────────────────────────┤ │ z=1 文本对象：正文与代码 │ ← 要保住的是它 ├────────────────────────────────────────┤ │ z=0 图像对象：底纹 / 插图 │ └────────────────────────────────────────┘ ▼ 光栅化 ┌──────────────────┐ │ 人眼看到：代码被 │ │ 一块横幅盖住了 │ └──────────────────┘ 解析时分三个口子各读各的，彼此互不影响: page.get_text("dict") ──► z=1 与 z=3 的全部文字 (z=2 那块矩形对它完全不可见) page.get_drawings() ──► z=2 的矩形：bbox / 填充色 / 透明度 page.get_images(full=True) ──► z=0 的位图 比对之后各自的归宿: z=3 广告文案 多页重复 + 固定位置 ──► is_advertisement = True ──► 输出时丢弃 z=2 遮罩矩形 宽度超过页宽 50% ──► 记为 overlay 区域 z=1 被盖正文 与 overlay 相交 ──► is_overlay_recovered = True ▲ 这个标志故意不写进输出层的过滤条件里 ───┘ 所以被盖住的正文照常输出，一个字都不少。

Overlay 恢复的三道保险

恢复被广告盖住的正文，其实不需要任何"恢复"操作——文字自始至终独立存在于文本层。工程上的做法是设计三道保险，确保正文在任何一个环节都不会被误删：

保险层做法关键点
1. 解析层用 page.get_text("dict") 直接读字符流遮罩只影响渲染，对文字提取毫无影响
2. 检测层对被遮罩覆盖的块只打 is_overlay_recovered = True 标志，绝不删除文字检测结论只是一个 flag，数据原封不动
3. 输出层过滤条件只检查 is_advertisement / is_header / is_footer / is_watermarkis_overlay_recovered 故意不在过滤条件里 → 被遮盖正文照样输出，只有广告文本本身被过滤
  • 广告完全盖住代码为什么还能恢复？ — PDF 文本层与绘图层独立，读文本层不受视觉遮挡影响
  • 噪声检测中"正文保护"为什么必须最后执行？ — 前置策略可能误标正文，最后兜底清除确保不丢内容
  • is_overlay_recovered 为什么不放在过滤条件里？ — 被覆盖的是正文，应该保留；覆盖它的广告文本才应该去除
  • 如何区分"广告文字"和"被广告盖住的正文"？ — 广告文字高频重复，正文唯一；结合位置+频率+内容特征综合判断

四、表格提取

表格提取的难点不是找到表格，是判断"这一格属于哪一行哪一列"：有线条时靠几何求交点，没线条时靠 x 坐标聚类，两者都失效时才轮到 AI 版面模型出场。

def detect_grid(drawings, page_w, page_h):
    """利用 PDF 矢量绘图对象中的线段构建表格网格"""
    h_lines = [d for d in drawings if d.bbox.height < 2]  # 水平线
    v_lines = [d for d in drawings if d.bbox.width < 2]   # 垂直线
    rows = cluster_y_coordinates(h_lines)  # 行边界
    cols = cluster_x_coordinates(v_lines)  # 列边界
    return rows, cols

方案 C：使用 pdfplumber 提取（最划算的 MVP）

不想自建线条几何分析时，pdfplumber 是最划算的起步方案：pdfplumber.open(pdf_path) 打开文档后，逐页调用 page.extract_tables() 直接得到 List[List[str]] 的行列数据，再交给 render_markdown_table() 输出 GFM 表格。它内部封装了 lattice（靠线条）与 stream（靠空白对齐）两种策略，能覆盖大多数常规表格场景，适合先跑通 MVP 再决定是否自建。

  • 表格内容如何最优地进入 RAG 向量库？ — 逐行平铺为句子（"类型int，大小4"）效果远优于直接嵌入 Markdown 表格

五、扫描版 PDF 处理

扫描件的分流判断只有一句话：这一页有没有字符对象。没有字符只有图，就必须走 OCR；而从这一步开始，数据质量的上限由图像质量决定，不再由后面的算法决定。

扫描版 PDF 的特征识别

扫描版判定是流水线的分流点，判断信号是两个 API 的组合：先用 page.get_text("dict") 检查页面是否存在 type 0 文本块，再用 page.get_images(full=True) 统计嵌入图像数量。"无文本层 + 有图像"同时成立，说明整页是位图，需要走 OCR 路径。判定逐页进行，混合文档（部分页原生、部分页扫描）按页分别分流。

信号API 判断含义
无文本层get_text("dict") 中不存在 type 0 块（has_text = False）PDF 未存储任何字符对象
有图像get_images(full=True) 返回非空页面内容以位图形式存在
结论not has_text and len(images) > 0 → 扫描页进入 OCR 链路，否则走原生文本链路

OCR 处理链路

步骤操作工具
1. 图像预处理二值化、去噪、倾斜校正、分辨率增强OpenCV
2. 版面分析识别文档区域（标题/正文/表格/图片）PP-StructureV2 / DocLayout-YOLO
3. 文字识别OCR 识别 + 置信度输出PaddleOCR / Tesseract
4. 结果结构化OCR 结果包装为统一 TextBlock 格式自定义转换
5. 后续流水线进入与原生 PDF 相同的下游处理通用 pipeline

PaddleOCR 集成示例

PaddleOCR 在启动时初始化为全局单例——PaddleOCR(use_angle_cls=True, lang='ch', use_gpu=False)：use_angle_cls 开启文字方向分类以应对倒置/侧置扫描件，lang='ch' 加载中文模型，use_gpu 按硬件条件开关。模型加载是高成本操作，单例复用避免逐页重复加载。对每页图像调用 ocr.ocr(page_image_path, cls=True)，返回的每一行结果是"四点 bbox + (text, confidence)"结构。

集成层的核心工作是把 OCR 输出包装成与原生 PDF 同结构的 TextBlock，让下游流水线对来源透明：

实现要点说明
初始化参数use_angle_cls=True 处理旋转，lang='ch' 中文场景，use_gpu 控制推理速度
bbox 转换四点坐标 [[x1,y1],...,[x4,y4]] → 取左上/右下两点构成轴对齐矩形，与原生 PDF 坐标系统一
置信度保留line[1][1] 是识别置信度，留作低质量区域（如半透明水印）标记的依据
统一结构封装为与原生 TextBlock 相同的 text/bbox/confidence 字段，下游不区分 OCR 还是原生来源

result = ocr.ocr(page_image_path, cls=True)

    bbox, (text, confidence) = line[0], line[1]

  • 如何判断一个 PDF 是扫描版？ — page.get_text() 为空 + page.get_images() 非空 → 扫描版
  • OCR 精度如何保障？ — 图像预处理（去噪/二值化/校正）+ 高 DPI 渲染 + 后处理纠错
  • 扫描版 PDF 走完 OCR 后如何与原生 PDF 统一？ — OCR 结果包装成同结构 TextBlock（含 bbox），下游逻辑不区分来源
  • PaddleOCR vs Tesseract：中文场景 PaddleOCR 精度显著更高；Tesseract 多语言覆盖广

六、扫描版 PDF + 水印/广告/导航栏

扫描件上的广告能不能去掉，只取决于它还是不是一个独立图层。是，那只是排版问题；已经压进同一张位图，就是 信息论 意义上的不可逆——这时诚实地标出缺失区域，比用 inpainting 编一段出来强得多。

子情况物理状态恢复可能方案
A. 广告已 flatten 进位图像素覆盖，信息损毁❌ 不可逆标记 + 人工补录
B. 多个 image XObject 叠加背景图和广告是独立图层✅ 可救图像层分离，仅 OCR 底图
C. 扫描底图 + 矢量广告底图是位图，广告是矢量绘图层✅ 可救OCR 底图，矢量层不进 OCR
D. 半透明水印覆盖OCR 部分能看见底层文字⚠️ 低准确率OCR + 低置信度标记

图像层分离方案（处理子情况 B+C）

当 page.get_images(full=True) 返回多张图像时，说明广告与底图以独立图层存在，可以做物理分离。思路非常直观：用 page.get_image_rects() 取每张图的包围矩形，按 get_area() 降序排序——面积最大的一张视为底图（正文载体），其余视为广告/Logo/横幅等覆盖层；然后只对底图做 OCR，从源头切断广告像素对识别的干扰；最后把 OCR 结果与覆盖层区域逐一比对，bbox.intersects() 命中的文本打上 is_overlay_obscured 标记，交给下游按不确定内容处理。

步骤做法关键点
枚举图层get_images(full=True) + get_image_rects()取得全部 image XObject 及其页面位置
识别底图按矩形面积降序，取最大者底图覆盖页面大部分区域，小图多为广告/Logo
选择性 OCRocr_provider.recognize(base_image) 仅识别底图广告图层不进入 OCR 输入，噪声源头隔离
不确定标记与 overlay 矩形相交 → is_overlay_obscured = True宁可保守标记可能受影响的区域，不盲目信任

像素级广告检测（处理子情况 A）

对已经 flatten 进位图的广告，只能靠图像级启发式。核心洞察是：广告通常使用高饱和度的鲜艳色块，而正文多为黑白——于是先用 cv2.cvtColor() 转到 HSV 色彩空间，用 cv2.inRange() 提取高饱和、高亮度像素形成掩码，再用 cv2.findContours()（RETR_EXTERNAL 只取外轮廓）提取连通块，最后用 cv2.boundingRect() 加页面面积比过滤出候选广告矩形。注意：检测只负责"圈出可疑区域"并打标记，不删除任何像素，与文本零损失原则保持一致。

步骤API关键点
色彩空间转换cv2.cvtColor(img, cv2.COLOR_BGR2HSV)饱和度通道在 HSV 中比 BGR 更易分离
饱和度掩码cv2.inRange(hsv, (0,80,80), (180,255,255))只保留高饱和、高亮度像素
轮廓提取cv2.findContours() + RETR_EXTERNAL + CHAIN_APPROX_SIMPLE只取最外层轮廓，避免嵌套干扰
面积过滤cv2.boundingRect()，保留面积占页面 0.5%~50% 的矩形过小是装饰、过大是底图，适中矩形才是疑似广告

导航栏清洗

导航栏（目录栏、侧边栏）是扫描书常见噪声源，识别策略：

  • 位置启发式：固定出现在页面左侧/右侧 15% 区域，或顶部/底部 10% 区域
  • 内容特征：含 URL、页码模式（"第X页"、"Page N"）、章节目录样式
  • 频率检测：同位置同内容在 ≥80% 页面重复出现
  • 面积比：占页面面积 <15% 且位于页边

信息论限制：广告像素已 flatten 进位图时，被覆盖的原文真的丢失了。正确做法是标记缺失区域告知用户，而非用 inpainting 猜测（猜出来的 OCR 结果几乎是垃圾）。

  • 如何判断 PDF 是"多图层叠加"还是"已 flatten"？ — page.get_images(full=True) 返回多个 image → 多图层；仅 1 个 → 大概率 flatten
  • 为什么不推荐用 inpainting 恢复被覆盖文字？ — inpainting 填充的是"视觉合理"的像素，不是真实文字；OCR 识别出来是乱码
  • 导航栏与正文的区分困难在哪？ — 目录型导航可能含有正文内容的标题，需结合位置+频率+内容综合判断
  • 最佳实践：标记 + 人工确认 — 对无法恢复的区域，输出 [此处可能因遮挡丢失内容] 占位符

七、代码块识别与保护

代码块被误删不是因为算法差，是因为 } 和 return 0; 在统计特征上和页脚长得一模一样。所以保护代码靠的不是更聪明的判断，而是更多层的兜底。

代码块的 6 层识别链路

技术类 PDF 中代码块容易被切碎、被噪声检测误标为广告。需要从识别到输出的全链路保护：

层位置作用
Layer 1PDF 解析从 FontDescriptor.Flags 第 3 位读取等宽标志
Layer 2布局分类等宽字体 + 字号 ≤ 正文 → BlockType.CODE
Layer 3噪声保护代码模式（{/}/return/关键字）跳过噪声检测
Layer 4跨页合并保护CODE 块永不参与跨页段落拼接
Layer 5Markdown 重构连续 CODE 块合并为单一 ``` 围栏
Layer 6语义分块保护永不在代码围栏中间切 chunk

代码模式识别（防误删）

噪声检测依赖"高频重复"启发式，而 }、return 0; 这类代码短行天然容易被误标。解法是在噪声检测前加一道"代码特征豁免"判断（looks_like_code），识别三类特征，命中即跳过全部噪声策略：

特征类别判断方式典型例子
孤立代码标点strip 后与标点集合全等匹配{、}、};、);、*/、//
C/C++ 注释行以 // 、/* 、* 开头// initialize variables
含关键字的短行行长度 ≤ 40 且包含编程关键字int 、return、#include、class 、def 、import 、struct 、for (

设计意图：40 字符阈值保证"只豁免短行"——包含关键字的长段正文（如讲解编程概念的段落）不会被跳过，避免豁免机制本身成为漏检盲区。

连续代码块合并输出

PyMuPDF 常把一段代码切成 N 个 block（每行一个），输出时需要一个"围栏状态机"把它们重新合并：维护布尔标志 in_code_block，按阅读顺序遍历块，状态只在 CODE/非 CODE 的边界处切换——进入时开围栏、离开时关围栏。这样 N 个连续 CODE 块被合并为单一 fenced code block，普通文本照常输出。

当前状态遇到的块动作
围栏外CODE 块先输出 ``` 开围栏，再追加行内容（rstrip 去尾空白）
围栏内CODE 块直接追加行内容，状态不变
围栏内非 CODE 块先输出 ``` 关围栏，再输出普通文本
围栏外非 CODE 块直接输出普通文本
if block.block_type == BlockType.CODE:

        lines.append("```")       # 进入围栏的转换

    in_code_block = False
  • 为什么代码容易被噪声检测误标？ — 代码短行（}/return 0;）在多页重复出现，触发"重复=广告"启发式
  • Layer 3 的 _looks_like_code() 覆盖哪些场景？ — 孤立标点、注释行、含关键字短行、以 ;/{/} 结尾的行
  • 为什么 CODE 块不参与跨页合并？ — 避免一段代码被错误粘到上一页的散文里
  • chunking 时为什么哪怕超出 max_chunk_size 也不在代码中间切？ — 半段代码无法理解，对 RAG 检索无意义

八、多栏布局与阅读顺序恢复

多栏 PDF 里肉眼一秒就能看出的阅读顺序，程序必须从坐标里重新推导。这一步一旦推错，后面所有的分块和检索，都建立在一段被打乱的文字上，且从结果里几乎看不出原因。

多栏检测算法

多栏检测采用最简单有效的"页面中线二分"启发式：为每个文字块计算 x 中心点 (bbox.x0 + bbox.x1) / 2，与页面中线比较后分到左栏/右栏；宽度超过 70% 页宽的块视为全宽块（跨栏标题、分隔线等），不参与分栏。分栏完成后各栏内按 bbox.y0 排序，按左栏 → 右栏拼接，全宽块再按自身 y 坐标插入合并序列的正确位置，最终把序号写回每个块的 reading_order 字段，供 Markdown 输出阶段直接使用。

步骤做法关键点
块分类x 中心点与页面中线比较中线左侧入左栏，右侧入右栏
全宽识别block_width > page_width × 0.7跨栏内容不进任何一栏，单独处理
栏内排序各栏按 bbox.y0 升序恢复垂直阅读顺序
全宽插入按 y 坐标插入合并序列保证跨栏内容与双栏内容的相对位置正确
序号写回block.reading_order = i输出阶段按此字段顺序生成 Markdown

跨页文本合并

条件（同时满足才合并）：

  • 第 N 页最后一个内容块不以句号/感叹号/问号结尾
  • 第 N+1 页第一个内容块以小写字母或接续标点开头
  • 两个块均为 PARAGRAPH 类型（CODE/HEADING/TITLE 不参与）
  • 多栏检测的核心启发式是什么？ — 按文字块的 x 中心点与页面中线比较聚类
  • 全宽块（如跨栏标题）如何处理？ — 宽度 >70% 页宽视为全宽，按 y 坐标插入正确位置
  • 两栏以上（杂志三栏）的局限：简单中线二分法失效，需更复杂的 x 坐标 DBSCAN 聚类
  • 跨页合并为什么排除 CODE/HEADING？ — 代码不应跨页拼接，标题是独立语义单元

九、语义分块（面向 RAG）

面向 RAG 的分块要认一个优先级：结构边界 永远压过长度边界。标题和代码围栏是作者亲手划下的语义分界线，而 max_chunk_size 只是防止块过大的兜底约束。

分块规则

规则说明目的
# 或 ## 标题遇到标题立即开启新 chunk保持主题一致性
代码块 ```永不在代码块中间切割保持代码完整性
超出最大长度在段落边界（空行）切割控制 chunk 大小
过短 chunk<100字合并入前一个 chunk避免碎片化

分块实现

分块器实现为一个行级状态机（SemanticChunker 类，构造参数 max_chunk_size=1500）：逐行扫描 Markdown，每一行经过一条固定顺序的判断链，"结构边界"的优先级始终高于"长度边界"——标题和代码围栏都是天然的语义边界，长度超限只是兜底手段。

判断顺序触发条件动作
1. 围栏状态跟踪行以 ``` 开头翻转 in_code_block 状态，本行直接收录
2. 代码保护当前处于围栏内本行直接收录，不参与任何切分判断
3. 标题边界行以 # 或 ## 开头已有内容打包为 chunk（_make_chunk），以该标题开启新 chunk
4. 普通收录以上均不满足追加行内容，然后检查长度
5. 长度兜底累计长度超过 max_chunk_size_find_paragraph_boundary() 找最近的段落边界（空行）切割，不在段落中间下刀

两个最容易忽略的细节：围栏状态用"遇到 ``` 就翻转"而非计数，天然支持"关闭后再开启"的多代码块场景；标题判断发生在收录之前，保证标题是 chunk 的首行，检索时利于 chunk 主题的表达。"标题驱动 + 代码保护 + 段落边界兜底"的组合，是零外部依赖下的 RAG 分块通用配方；对无标题的长文本则需回退到语义相似度分块（见下方要点）。

  • 为什么用标题驱动分块？ — 标题天然是语义边界，一个标题下的内容主题一致
  • max_chunk_size 为什么设 1500 字？ — 平衡：太小丢上下文，太大降检索精度；匹配主流 Embedding 模型输入长度
  • 代码块不拆分会不会导致超大 chunk？ — 会。但半段代码无意义，宁可超限也不切碎代码
  • 这种分块策略的缺点？ — 依赖标题结构，对无标题的长文本效果差，此时应回退到语义相似度分块

十、工程实践与设计原则

整套系统其实只靠一条原则撑着：文本零损失——检测只打标记，不删数据。误判了还能改回来，删掉了就真没了。

核心设计原则

原则实现收益
文本零损失所有检测仅打标志，不删数据误判可逆，不丢正文
多重防御单层判错时下一层兜底整体鲁棒性
保守策略宁可保留噪声也不误删正文用户可手动清理，丢失无法恢复
原始不可变编辑结果存独立文件随时一键 revert
统一数据模型OCR/原生 PDF 输出同结构下游逻辑不区分来源
检测结论一律写成布尔字段

让"判断"和"删除"分处两个阶段，真正决定丢什么的只有输出层一处。改判定规则时不用担心已经被删掉的内容找不回来。

把 Debug 叠框图当成一等公民

把各类 bbox 按颜色画回渲染图，一眼就能看出是版面分类错了还是噪声策略过激。没有它，调参基本靠猜。

OCR 与原生解析输出同一种结构

统一封装成带 bbox 和置信度的 TextBlock，下游的去噪、排序、分块全部复用同一套代码，扫描件和原生 PDF 只在入口分叉一次。

别用 inpainting 去"恢复"被覆盖的文字

填出来的是视觉上合理的像素，不是原来的字。OCR 读出来是似是而非的乱码，比留个空位危害大得多——错误答案比没有答案更难被发现。

别把噪声阈值调到"看起来很干净"

噪声标记率超过 15% 通常意味着正文在被误删。宁可留下几行页眉，也不要丢掉一段代码。

别把用户的修改直接写回原文件

编辑结果存成独立文件（如 output.edited.md），原始产物保持不可变。这样任何时候都能 diff 和一键回滚。

质量验证指标

  • 文字完整度：输出 Markdown 字数 vs 原文预估字数（不应过度缩减）
  • 噪声过滤率：被标记噪声的文字块占比（正常 5%-15%，过高说明误标）
  • 代码块完整性：所有 ``` 围栏正确配对闭合
  • 分块均匀度：chunk 长度标准差，过大说明分块不均
  • 人工抽检得分：随机抽取 chunks 对照原 PDF 评分

场景瓶颈优化手段

  • 如何评估 PDF 清洗质量？ — 文字完整度 + 噪声过滤率 + 代码完整性 + 人工抽检

Q&A（Top 10）

PDF 文档有文本层和扫描版两种，它们的清洗策略有何本质区别？

有文本层的 PDF 可以直接通过 API（如 PyMuPDF 的 get_text("dict")）读取字符流，文字在对象层面始终完整，即使被广告遮盖也能恢复。扫描版 PDF 整页是位图，必须先 OCR 才能得到文字，且如果广告像素直接覆盖了正文像素，信息在物理上已经损毁，无法恢复。策略差异：原生 PDF 重点在去噪和结构恢复；扫描版重点在 OCR 精度和图层分离。

广告完全盖住了正文代码，为什么还能恢复？请解释 PDF 的分层原理。

PDF 内部是分层结构：文本对象、绘图对象、图像对象各自独立存在。"广告盖住正文"在文件层面 = 一个绘图对象（半透明/深色矩形）的 z-order 在文本对象之上。用 get_text("dict") 直接读字符流时，完全绕过了绘图层的遮盖效果。关键实现：解析层读文本流（不受影响）→ 检测层从绘图层识别遮罩并打标记 → 输出层不过滤 is_overlay_recovered 的文字块。三道保险确保文字零损失。

设计一个 PDF 噪声检测系统，你会用哪些策略？如何防止误删正文？

7 策略：①重复文本检测（同文本≥30%页出现）；②固定位置检测（同文本同位置）；③页眉页脚（位置区域+导航内容特征）；④水印（超大字体+高频出现）；⑤遮罩/Banner（绘图对象的颜色/透明度/面积分析）；⑥高频兜底（≥80%页同文本同位置）；⑦正文保护（白名单+区域保护）。防误删核心：所有检测只打标志不删数据；CODE/TITLE/HEADING 块永远清除噪声标志；最后一步 _protect_body_text 兜底。宁可漏检不误删。

技术类 PDF 中代码块为什么容易被误判为噪声？如何解决？

原因：代码短行如 }、return 0; 在多页重复出现，触发"重复=广告"启发式；代码常落在页面底部，触发页脚检测。解决方案是 6 层防御：①从 PDF 字体 flag 读等宽位；②布局分类标记为 CODE；③噪声检测遇代码模式跳过；④跨页合并拒绝 CODE 参与；⑤Markdown 输出合并连续 CODE 为单一围栏；⑥分块永不在代码内切割。设计理念：层层递进，任一层出错下一层兜底。

扫描版 PDF 有广告覆盖时，什么情况可以恢复，什么情况不可以？

可恢复：①多 image XObject 叠加（广告和底图是独立图层），分离后只 OCR 底图；②扫描底图+矢量广告层，矢量层不进 OCR 输入。不可恢复：广告已 flatten 进位图（像素覆盖=信息损毁，信息论意义上不可逆）。判断方法：page.get_images() 返回多张图→可救；仅1张→已 flatten。不推荐 inpainting：填充的是"视觉合理"的像素而非真实文字，OCR 结果是乱码。最佳实践：标记缺失区域 + 让用户手动补录。

PDF 表格提取有哪些方案？各适用什么场景？

6 种方案：A.线条几何网格重建（适合完整网格表、半边框表）；B.文本 bbox 列对齐（适合无线条伪表格）；C.pdfplumber extract_tables（最划算 MVP，覆盖 70% 场景）；D.AI 版面模型+结构识别（工业级，覆盖合并单元格/嵌套表）；E.跨页表合并（检测相邻页表格连续性）；F.扫描表 OCR + PP-Structure。推荐路径：先上 pdfplumber 解决大多数场景，再按需引入 AI 模型处理复杂表格。RAG 场景建议额外做"表格平铺"：逐行转为自然语言句子，提升 embedding 效果。

启发式布局分类是如何工作的？与 AI 版面模型相比各有什么优劣？

启发式方法：统计全文档字体大小频率，最高频为正文字体；≥1.8x 正文=TITLE，≥1.4x=HEADING；等宽字体+小字号=CODE；以列表符号开头=LIST_ITEM。优点：零外部依赖、速度极快（纯 CPU 毫秒级）、完全可解释可调试。缺点：对复杂版面（杂志、混合图文）效果差，无法识别表格区域。AI 版面模型（DocLayout-YOLO/LayoutParser）能处理任意复杂版面，但需要 GPU、模型文件、推理耗时。折中方案：启发式为默认，AI 模型为可选增强。

如何设计 RAG 场景下的语义分块策略？需要考虑哪些约束？

核心策略：以标题（#/##）为自然切分点开新 chunk；代码围栏内不切割（保持完整性）；超出 max_size 在段落边界切割；过短 chunk 合并入前一个避免碎片化。约束考量：①Embedding 模型最大输入长度（通常 512-8192 tokens）；②检索精度（chunk 越小越精确但丢上下文）；③内容完整性（代码/表格不可拆）；④与索引粒度匹配。进阶优化：Parent-Child 策略（小块检索+大块返回）、chunk overlap 防信息切断、metadata 保留（heading/来源/页码）辅助过滤。

多栏 PDF 的阅读顺序如何恢复？有什么边界情况？

核心算法：按文字块 x 中心点与页面中线比较，分为左栏/右栏/全宽块；各栏内按 y 排序；全宽块按 y 坐标插入正确位置；最终合并为 左栏→右栏 的阅读序。边界情况：①跨栏标题/图片（宽度>70%页宽视为全宽）；②三栏以上版面（中线二分法失效，需 DBSCAN 聚类）；③侧边注释/脚注（位置在边栏但不是主内容流）；④表格跨栏（整个表格宽度可能横跨两栏）。当前主流开源方案大多只支持 1-2 栏，杂志级复杂版面仍需 AI 辅助。

如果让你从零设计一个面向 RAG 的 PDF 清洗系统，架构如何设计？

分层架构：①解析层：PyMuPDF 提取文本/绘图/图像三类对象，检测 is_scanned 分流；②布局层：启发式分类（默认）或 AI 版面模型（可选），输出 BlockType；③去噪层：多策略检测 + 正文保护白名单，所有操作仅打标志；④结构恢复层：阅读顺序排序 + 跨页合并 + 表格重建；⑤输出层：按标志过滤噪声，生成结构化 Markdown；⑥分块层：标题驱动+代码保护+大小控制，输出 chunks.json。工程保障：异步处理+WebSocket进度推送+原始文件不可变+编辑层隔离+Debug可视化+质量评分。技术栈：FastAPI + PyMuPDF + PaddleOCR(可选) + asyncio + 文件存储。
