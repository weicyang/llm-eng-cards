G28 · 轻量 GraphRAG 变体选型

LightRAG 去社区化 / HippoRAG 2 个性化 PageRank / LazyGraphRAG 延迟摘要 / 增量更新代价 / 评测口径矛盾 / 三维决策

微软 GraphRAG 用"预先给全图生成社区摘要"换来了全局洞察能力，代价是索引账单和增量更新的噩梦。后来的每一个变体，本质上都在回答同一个问题：这份摘要能不能不预先做？LightRAG 的答案是不做，HippoRAG 2 的答案是换个机制做，LazyGraphRAG 的答案是等到有人问了再做。

这张卡假设你已经知道 GraphRAG 是什么。它的实体抽取、Leiden 社区检测、Local/Global Search 双路径在 G21 GraphRAG 里讲过，经典知识图谱的三元组与嵌入推理在 D02 知识图谱，图存储引擎选型在 B04 图数据库。这里只讲后来者：它们各自砍掉了 GraphRAG 的哪一块，砍掉之后失去了什么。

一、轻量派从哪来：索引账单压垮了谁

要理解这些变体为什么长成现在这样，得先看清 GraphRAG 的成本结构。它的索引流程有五步：切块、LLM 抽实体与关系、建图、跑社区检测、为每一个社区生成摘要。前四步的成本还算可控，第五步是账单的主体——每个社区都要调一次大模型写摘要，而一个中等规模语料能产出成百上千个社区。

社区摘要是 GraphRAG 全局洞察能力的来源，也是它一切麻烦的来源：加一批新文档，社区结构就变了，旧摘要全部作废，得重新聚类、重新写一遍。这不是实现上的瑕疵，是设计的必然后果——预计算的东西，一旦底层变了就得重算。

三条不同的破局思路

看清病根之后，三个变体的取舍就有了统一的解释框架。它们都同意"社区摘要太贵"，但对"那全局洞察怎么办"给出了不同答案。

二、LightRAG：砍掉社区层

LightRAG 是港大 HKUDS 团队的方案，定位就是 Microsoft GraphRAG 的轻量替代。它的核心决定只有一个：不做社区检测，也不做社区摘要。索引从五步变成三步——抽实体关系、建图、存向量。

双层关键词检索：在查询时拼全局视角

砍掉社区摘要之后，"回答宏观问题"的能力从哪来？LightRAG 的做法是把查询拆成两层关键词：低层关键词指向具体实体（比如某个公司名、某条法规编号），高层关键词指向抽象概念（比如"合规风险""市场竞争"）。两层分别去检索，再把结果拼起来。

LightRAG 的四种检索模式共享同一套索引 用户查询 │ ┌─────────┴─────────┐ │ LLM 拆两层关键词 │ └─────────┬─────────┘ │ ┌─────────┬───────┴───────┬─────────┐ ▼ ▼ ▼ ▼ ┌────────┐┌────────┐ ┌────────┐┌────────┐ │ naive ││ local │ │ global ││ hybrid │ │纯向量 ││低层关键││ │高层关键││ 两层并 │ │ ││词→实体 ││ │词→关系 ││ 用 │ └───┬────┘└───┬────┘ └───┬────┘└───┬────┘ │ │ │ │ └─────────┴──────┬───────┴─────────┘ ▼ ┌────────────────────┐ │ 同一套索引 │ │ 实体+关系图 / 向量 │ └────────────────────┘ 对比 GraphRAG：Local Search 走图遍历、Global Search 走社区摘要， 两条路径背后是完全不同的数据结构，切换代价大。 LightRAG 四种模式只是查询路径不同，索引不用重建。

LightRAG 的"轻"不在模型小，而在于它把全局视角从"预先算好存起来"改成了"用的时候现拼"。代价是拼出来的全局视角不如预先精心总结的那份深，好处是加数据的时候没有任何东西需要作废。

增量更新：从级联重建变成直接追加

这是 LightRAG 最实在的工程价值。新文档进来时，走的流程和首次索引完全一样——抽实体关系、缝进已有的图——没有任何"作废重算"的环节。官方仓库还说明了删除场景：删文档时可以利用构建阶段的 LLM 缓存快速重建受影响的实体与关系。

被砍掉的那部分：实体消歧

表格最后一行值得单独说。GraphRAG 有多层实体消歧策略，LightRAG 用的是朴素名称匹配——同一个实体在不同文档里叫法不同（"苹果公司""Apple Inc.""AAPL"），LightRAG 大概率会把它们当成三个不同的节点。这在实体命名规范的语料里问题不大，在人名地名混乱的语料里会显著拉低图质量。选型时这一条常被成本数字盖过去，但它直接决定了图能不能用。

示例场景：某券商研报知识库最初上 GraphRAG，8 万篇研报的首次索引跑了 11 小时、花掉四位数美元，团队认了。真正劝退的是第二个月——新增 3000 篇研报，社区结构变化触发全量摘要重建，成本几乎与首次索引持平。切到 LightRAG 后每月增量的边际成本降到两位数美元，但随之出现新问题：同一家公司在研报里的七八种简称被建成了独立节点，不得不额外做一层别名归一化的预处理。省下来的钱，有一部分变成了数据清洗的工作量。

三、HippoRAG 2：用个性化 PageRank 做联想

HippoRAG 2 出自俄亥俄州立 OSU-NLP 团队的论文《From RAG to Memory: Non-Parametric Continual Learning for Large Language Models》（arXiv:2502.14802）。它的出发点跟 LightRAG 不太一样——不是嫌贵，是嫌图 RAG 在基础事实检索上反而不如普通 RAG。

这篇论文最诚实的一句话是它的问题陈述：图结构确实改善了"归纳总结"和"联想"能力，但在"这个事实在哪篇文档里"这种基础任务上，图 RAG 的表现明显低于标准向量 RAG。加了图反而退步，这才是它要修的东西。

机制：把段落也放进图里，再让相关性在图上扩散

HippoRAG 2 的离线索引分三步：用 LLM 做 OpenIE（开放域信息抽取，不预设 schema）从每个段落抽三元组，形成无 schema 的开放知识图；用编码器检测短语节点之间的同义关系，相似度超阈值就加一条同义边；最后把原始段落也作为段落节点并入图中，与它抽出的概念之间连上下文边。

HippoRAG 2 在线检索流程 查询 │ │ ① Query-to-Triple：整句查询直接匹配三元组 │ （不是先做 NER 再查，而是整句嵌入匹配） ▼ ┌──────────────────────┐ │ 候选三元组 + 候选段落 │ └──────────┬───────────┘ │ ② 识别记忆（recognition memory） │ LLM 当过滤器，剔掉不相关的三元组 ▼ ┌──────────────────────┐ │ 种子节点 seed nodes │ ← 短语节点与段落节点都可以当种子 └──────────┬───────────┘ │ ③ Personalized PageRank │ 从种子出发，相关性沿边扩散 ▼ ┌─────────────────────────────────────┐ │ 开放知识图 │ │ │ │ [短语节点]──关系边──[短语节点] │ │ │ │ │ │ 同义边 上下文边 │ │ │ │ │ │ [短语节点] [段落节点] │ └──────────┬──────────────────────────┘ │ ④ 按 PPR 得分排序，取 top 段落 ▼ 送给 LLM 生成答案

个性化 PageRank（PPR）是这套机制的核心。普通 PageRank 算的是全图节点的绝对重要性，个性化版本则偏向一组指定的种子节点——相关性从种子出发沿边扩散，离种子近、连接紧密的节点得分高。用它做检索的直觉是：你问"爱因斯坦和量子力学的争论"，种子落在这两个概念上，PPR 会自动把与两者都强连接的那些段落顶上来，即使那些段落里一次都没出现完整的查询词。这就是所谓的联想式检索。

两处关键改进

改进HippoRAG 1 的问题HippoRAG 2 的做法
段落深度整合图里只有短语节点，段落游离在外段落作为节点入图，PPR 直接对段落打分

论文报告的核心结论是：在联想记忆类任务上比当时最强的嵌入模型提升约 7%，同时在事实性和归纳总结类任务上也不低于标准 RAG——也就是补上了前面说的那个退步。实验中用 Llama-3.3-70B-Instruct 同时承担抽取和三元组过滤，检索器用 NV-Embed-v2。

HippoRAG 2 和 LightRAG 的分工可以这么理解：LightRAG 优化的是"建图和查询要便宜"，HippoRAG 2 优化的是"多跳问题要答得准"。前者是工程账，后者是效果账。它们不是同一条赛道上的竞品。

四、LazyGraphRAG：把 LLM 全推到查询时

LazyGraphRAG 是微软自己给 GraphRAG 打的补丁，2024 年 11 月由 GraphRAG 原班人马（Darren Edge、Ha Trinh、Jonathan Larson 等）发布。它的思路最激进：索引阶段一次 LLM 都不调。

用经典 NLP 换掉 LLM 抽取

既然 LLM 抽实体贵，那就不用 LLM。LazyGraphRAG 的索引只做两件事：把文本块嵌入向量，以及用名词短语抽取加共现统计建一张概念图——都是前深度学习时代的经典 NLP 技术，成本几乎为零。社区检测照跑（那本来就是纯图算法，不花 LLM 钱），但不再为社区生成摘要。

三种索引策略的 LLM 调用分布 索引阶段 查询阶段 ┌────────────────────────┬──────────────────────┐ │ │ │ GraphRAG │ ████████████████████ │ ██████ │ │ 抽实体+社区摘要，全量 │ 遍历社区摘要 │ │ │ │ LightRAG │ ██████ │ █ │ │ 只抽实体关系 │ 一次调用 │ │ │ │ LazyGraphRAG │ (空) │ ████████ │ │ 名词短语+共现，零调用 │ 只对查询触及的区域做 │ │ │ 相关性测试与摘要 │ └────────────────────────┴──────────────────────┘ 总成本的差别不只是搬运：GraphRAG 为整个语料付费， LazyGraphRAG 只为被问到的那部分付费。 语料里大部分内容从来没被任何查询触及过 —— 那部分钱就省下来了。

微软官方博客给出的数字是：LazyGraphRAG 的索引成本与向量 RAG 相同，即完整 GraphRAG 的 0.1%。查询侧，在最低预算档下达到与 GraphRAG Global Search 相当的答案质量而查询成本低 700 倍；把预算提到中档（500 次相关性测试）时，用 GraphRAG Global Search 约 4% 的成本，在局部和全局查询上都优于后者。

LazyGraphRAG 的省钱逻辑和缓存的省钱逻辑是同一个：不要为没人用的东西提前付费。GraphRAG 给语料里每一个社区都写了摘要，但一次典型查询可能只碰到其中百分之几——剩下的摘要是纯浪费。把生成推迟到查询时，等于把"全量预计算"换成了"按需计算"。

可调的成本-质量旋钮

LazyGraphRAG 有一个主参数叫相关性测试预算（relevance test budget），控制查询时愿意花多少次 LLM 调用去筛选相关内容。预算调高，质量上升成本上升；调低则相反。这个设计的价值在于它把成本-质量权衡收敛成了一个可以按业务场景调的旋钮，而不是要换整套架构。

它的代价

索引不产出社区摘要，意味着你失去了一份"数据集语义结构的目录"。GraphRAG 的社区摘要除了服务查询，本身也是可浏览的资产——运营同学可以翻一遍摘要，快速了解这批语料里有哪些主题。LazyGraphRAG 把这份资产变成了按需生成的临时产物，看不到全貌。对于以探索性分析为目的的场景，这个损失是实的。

五、为什么两份评测能得出相反结论

如果你同时读过 LightRAG 论文和几篇多跳问答的对比测评，会遇到一个尖锐的矛盾：前者说 LightRAG 全面胜过 GraphRAG，后者的表里 LightRAG 的分数低到不像话。这一节专门拆这个矛盾，因为看不懂它，就没法正确使用任何一份评测数据。

那这两份数据还能不能用

能用，但只能用来回答各自对应的问题。想知道"用户问开放式分析问题时，哪个方案的回答更有信息量"，看口径一；想知道"用户问需要串联多个文档才能答的事实问题时，哪个方案更可能给出正确答案"，看口径二。真正危险的用法是拿其中一份去做全局结论——比如看到 F1 表就断定 LightRAG 不能用，或者看到胜率表就以为它在事实问答上也强。

另外要注意，第三方复现的分数普遍低于原作者自测，这在图 RAG 领域尤其明显，因为配置项多（抽取模型、chunk 大小、检索模式、prompt 模板）且很多论文没有完整公开。看到某个方案在第三方表里异常低，第一反应应该是"配置或答案格式对不上"，而不是"这个方案不行"。HippoRAG 2 论文本身也印证了这一点——它明确指出图 RAG 方法在基础事实任务上会退步，说明这类落差是这个技术路线的共性问题，不是某一家的实现缺陷。

混合架构：不必二选一

生产系统里常见的做法是分层：稳定的核心知识（产品手册、法规条文）走 GraphRAG 做一次深度索引，动态数据（工单、日志、新闻）走 LightRAG 持续追加，前面挂一个查询路由判断该走哪条路。这个架构的代价是要维护两套索引和一个路由器，收益是把各自的长处都拿到了。路由怎么做、什么时候值得上，G21 的混合路由一节有更细的讨论。

  • 选型前先统计真实用户问题的类型分布，多跳占比低就别上图
  • 把索引成本按"每月增量"算，而不是只算首次索引
  • 引用评测数字时连带说明任务类型和评分方式
  • 语料实体命名混乱时，先做别名归一化再上 LightRAG
  • 先用小样本语料跑通全流程算清单价，再决定全量索引
  • 把成本-质量旋钮（如相关性测试预算）暴露成可配置项
  • 别拿单一榜单分数下全局结论，先看它测的是什么任务
  • 别忽略隐藏成本：抽实体的一次性账单和消歧的人工投入
  • 别在实体关系稀疏的语料上建图，边少的图没有检索价值
  • 别把 GraphRAG 的社区摘要当成免费副产品，它是账单主体
  • 别默认第三方复现分数就是方案的真实水平
  • 别为了追新换架构，先确认现有方案的瓶颈到底在哪

Q&A

LightRAG 相比 Microsoft GraphRAG 到底"轻"在哪？
轻在砍掉了整个社区层。GraphRAG 的索引有五步，其中第五步"为每个社区生成摘要"要逐社区调用大模型，是账单的主体；LightRAG 的索引只有三步——抽实体关系、建图、存向量，完全不做社区检测和摘要。这带来两个连锁效果：一是索引成本降低约两个数量级（论文实验中 100 万 token 语料从 20~50 美元降到 0.15 美元量级），二是增量更新从"拆社区、重生成全部摘要"变成"把新实体直接缝进老图"。代价是失去了预计算的全局视角，LightRAG 改用查询时的双层关键词检索现场组装，在需要深度归纳的宏观问题上不如 GraphRAG 的社区摘要。
为什么 LightRAG 在有些评测里赢 GraphRAG，在另一些里分数低得离谱？
因为两类评测的口径完全不同，不可直接比较。LightRAG 官方报告的是 LLM 两两对比的胜率，任务是长文摘要式问答，评的是全面性、多样性这类维度，LightRAG 总体胜率约 54.8%。而多跳问答榜单用的是 F1，任务是答案为一个短实体的事实问题，与标准答案做词级匹配——在这类表里 LightRAG 的 HotpotQA 只有 2.4 分。差距的根源在于 LightRAG 按设计输出的是详尽的实体关系描述，而 F1 要的是"1987 年"这样的精确短答案，详尽反而被扣分。所以正确的用法是按问题类型选数据：想知道开放式分析问题答得好不好看胜率，想知道事实问题答得对不对看 F1。
HippoRAG 2 的个性化 PageRank 具体解决什么问题？
解决的是"答案分散在多个文档、任何单篇都不完整"的多跳检索问题。普通 PageRank 算全图节点的绝对重要性，个性化版本会偏向一组指定的种子节点，让相关性从种子出发沿边扩散。HippoRAG 2 的做法是：先把查询整句匹配到图里的三元组和段落上得到候选，再用一个 LLM 做"识别记忆"过滤掉不相关的三元组，剩下的作为种子跑 PPR，最后按得分取 top 段落。这样即使某个段落里一次都没出现完整的查询词，只要它与种子概念连接紧密就能被顶上来——这就是联想式检索。论文报告它在联想记忆类任务上比当时最强的嵌入模型提升约 7%。
LazyGraphRAG 的索引成本真能降到 0.1% 吗？
按微软官方博客的口径是的，它的索引成本与向量 RAG 相同，即完整 GraphRAG 的 0.1%。实现方式是索引阶段一次 LLM 都不调：用名词短语抽取和共现统计这类经典 NLP 技术建概念图，社区检测照跑（那本来就是纯图算法不花钱），但不生成社区摘要。所有生成式工作推迟到查询时，只对查询实际触及的语料区域做相关性测试和摘要。省钱的本质和缓存一样——不为没人用的东西提前付费，因为一次典型查询往往只碰到语料里百分之几的内容。代价是失去了可浏览的语义结构目录，无法在提问前先了解这批语料有哪些主题。
三个变体里，增量更新能力怎么排序？
LightRAG 和 LazyGraphRAG 都很好，但好的原因不同；GraphRAG 最差。LightRAG 是结构上就没有需要作废的预计算产物，新文档走的流程和首次索引一样，直接把新实体缝进老图，边际成本等于抽取那几个新文档的成本。LazyGraphRAG 是因为索引本身就近乎免费（不调 LLM），所以哪怕整个重建一次也没什么压力。GraphRAG 的问题在于社区摘要是全局预计算的——加一批数据社区结构就变了，旧摘要作废，需要重新聚类并重生成摘要，LightRAG 论文的实验里这一次更新约耗 1399 × 2 × 5000 token。如果你的知识库是日级或周级更新，GraphRAG 的这个特性基本就是劝退项。
什么情况下这些图 RAG 方案一个都不该用？
当用户问题里跨实体、跨文档的比例很低时。图结构的价值来自"把散落在多处的关联串起来"，如果九成问题是"这个套餐怎么退订"这类单篇文档就能答的单跳问题，那么建图带来的检索提升微乎其微，而成本要多出一到两个数量级。第二种情况是语料本身实体关系稀疏——一堆互不相干的独立条目，抽出来的图边很少，几乎退化成孤立节点集合，检索时没有可传播的路径。所以选型的第一步不是比较哪个方案分数高，而是统计自家用户真实问题的类型分布；这一步跳过去，后面选得再仔细也是在优化一个不该存在的系统。
LightRAG 的实体消歧弱，实际会造成什么后果？
同一个实体在不同文档里的不同叫法会被建成多个独立节点，图因此被切碎。比如"苹果公司""Apple Inc."" AAPL"在朴素名称匹配下就是三个节点，各自只连着自己那部分文档抽出的关系，检索时无论命中哪一个都只能看到全貌的三分之一，多跳路径也会因为节点没打通而断掉。GraphRAG 有多层消歧策略，这方面明显更稳。实践中的应对是在索引前加一层别名归一化预处理——维护实体别名词典，或者用嵌入相似度做一轮聚类合并。需要提醒的是这笔工作量往往会抵消掉一部分省下来的索引成本，选型时应该把它算进总账，而不是只看索引单价。
生产环境能不能同时用多个方案？
可以，而且是成熟系统里的常见做法。典型的分层架构是：稳定的核心知识（产品手册、法规条文、组织架构）走 GraphRAG 做一次深度索引，享受社区摘要带来的宏观归纳能力，反正它不怎么变，预计算的钱只付一次；动态数据（工单、日志、新闻、研报）走 LightRAG 持续追加，享受零成本增量；前面挂一个查询路由，根据问题类型判断该查哪一路，或者两路都查再融合。代价是要维护两套索引、一个路由器和一套融合逻辑，运维复杂度明显上升，所以只在两类知识的更新频率差异确实很大时才值得。如果你的语料是均质的，选一个方案做好比拼装两个更划算。
