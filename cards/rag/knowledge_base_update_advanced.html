G17 · RAG 知识库更新机制

Knowledge Base Update — 先删后增 / 内容哈希 / 灰度更新 / 变化感知

知识库更新的核心挑战不是"怎么写入新数据"，而是"如何确保旧数据被彻底清理、新数据被可靠写入，且整个过程可回滚"。

一、更新问题的本质与核心挑战

文档更新会导致 chunk 边界和数量发生变化，这使得"局部更新"变得极其困难。假设原始文档被切割为 5 个 chunk（C1-C5），更新后的文档内容变化可能导致同样的内容被重新切割为 6 个 chunk（C1'-C6'），原第 3 个 chunk 的内容可能横跨新版本的第 3、4 个 chunk。

原始文档 (v1): ┌─────┬─────┬─────┬─────┬─────┐ │ C1 │ C2 │ C3 │ C4 │ C5 │ → 向量库中 5 个向量 └─────┴─────┴─────┴─────┴─────┘ 更新后文档 (v2) — 内容增删导致 chunk 边界漂移: ┌──────┬──────┬──────┬──────┬──────┬──────┐ │ C1' │ C2' │ C3' │ C4' │ C5' │ C6' │ → 6 个向量 └──────┴──────┴──────┴──────┴──────┴──────┘ 问题: C3 的内容现在分散在 C3' 和 C4' 中 直接"更新 C3"无法解决这个问题

三种更新操作

操作类型触发条件复杂度风险等级
文档新增全新文档入库低 — 切割 + 向量化 + 插入低
文档修改已有文档内容变更高 — 需识别旧 chunk 并清理高
文档删除文档从知识库移除中 — 需定位所有关联 chunk极高（僵尸 chunk 风险）

生产级 RAG 系统的更新原则：不是更新单个 chunk，而是确保"变化感知 → 旧数据清理 → 新数据写入"的完整流程可靠性。任何环节的遗漏都会导致检索结果中出现过时或矛盾的信息。

把"更新 chunk"的思维转换为"替换整个文档的所有 chunk"——先删后增是保证一致性的唯一可靠方式。

为什么不能"就地更新"单个 chunk？

直觉上似乎可以只更新内容变化的 chunk，但这种方式存在严重的边界漂移问题：

  • 边界不对齐 — 修改了文档开头的一段话，可能导致后续所有 chunk 的边界都向后偏移一个句子
  • 新增/删除段落 — 在文档中间插入一段内容，导致该位置之后的所有 chunk 边界全部变化
  • 切分策略变化 — 即使是同一段内容，在不同上下文中可能被切割到不同的 chunk 中

这些边界漂移问题使得"逐 chunk 对比并更新"的逻辑极其复杂，且容易出现遗漏——这正是先删后增方案被广泛采用的根本原因。

二、先删后增：生产级更新核心流程

先删后增（Delete-then-Insert）是生产级 RAG 系统的标准更新模式。核心思想是：当检测到文档变化后，不尝试逐 chunk 比较和更新，而是先删除旧文档关联的所有 chunk，再重新切割新文档并写入。

┌─────────────────┐ │ 文档变化检测 │ │ (内容哈希对比) │ └────────┬────────┘ │ 确认变化 ▼ ┌──────────────────────────────┐ │ Step 1: 删除旧数据 │ │ DELETE FROM vectors │ │ WHERE source_doc_id = 'doc_01' │ └──────────────┬───────────────┘ ▼ ┌──────────────────────────────┐ │ Step 2: 重新切割新文档 │ │ new_chunks = split(new_doc) │ └──────────────┬───────────────┘ ▼ ┌──────────────────────────────┐ │ Step 3: 生成 embedding │ │ vectors = embed(new_chunks) │ └──────────────┬───────────────┘ ▼ ┌──────────────────────────────┐ │ Step 4: 写入向量库 │ │ INSERT vectors + metadata │ └──────────────┬───────────────┘ ▼ ┌──────────────────────────────┐ │ Step 5: 验证一致性 │ │ 检查 chunk 数量 / 元数据完整性 │ └──────────────────────────────┘

先删后增的优势

  • 避免新旧内容混杂——不会出现旧 chunk 和新 chunk 同时存在于向量库中的情况
  • chunk 边界自动对齐——新文档按最新策略切割，无需与旧 chunk 逐一对应
  • 实现简单——相比逐 chunk 对比（chunk 级增量更新），先删后增的代码复杂度低一个数量级

先删后增的代价

  • 重新向量化整个文档——即使只改了一句话，也需要重新计算所有 chunk 的 embedding
  • 短暂的数据空窗期——删除旧 chunk 到写入新 chunk 之间存在检索不可用的窗口
  • embedding API 调用成本——大规模文档更新时成本线性增长
# 先删后增的核心代码逻辑
def update_document(doc_id: str, new_content: str):
    # Step 1: 删除旧 chunk
    vector_store.delete(filter={"source_doc_id": doc_id})
    
    # Step 2: 切割新文档
    new_chunks = text_splitter.split(new_content)
    
    # Step 3: 向量化 + 写入
    for i, chunk in enumerate(new_chunks):
        embedding = embed_model.embed(chunk)
        vector_store.upsert(
            id=f"{doc_id}_chunk_{i}",
            vector=embedding,
            metadata={"source_doc_id": doc_id, "chunk_index": i}
        )
更新策略一致性保证计算成本实现复杂度推荐场景
全量重建最高极高（全部文档）低初始化 / 更换模型
先删后增（文档级）高中（仅变化文档）低通用生产系统
逐 chunk 增量更新中低（仅变化 chunk）高超大文档 / 高频更新

先删后增用"稍高的计算成本"换取"绝对的数据一致性"——在绝大多数生产场景中，这是一笔划算的交易。

三、变化感知机制：内容哈希与元数据追踪

在决定"是否要更新"之前，系统需要先知道"哪些文档发生了变化"。变化感知机制负责检测文档的新增、修改和删除。

内容哈希（Content Hash）

内容哈希是变化感知的核心手段：对文档内容计算哈希值（如 MD5、SHA-256），将哈希值持久化存储，后续通过对比哈希值判断文档是否被修改。

import hashlib

def compute_content_hash(content: str) -> str:
    return hashlib.sha256(
        content.encode('utf-8')
    ).hexdigest()

# 首次入库时记录
registry["doc_01"] = {
    "content_hash": "a3f2b8c...",
    "chunk_ids": ["doc_01_chunk_0", "doc_01_chunk_1", ...],
    "ingested_at": "2026-01-15T10:30:00"
}

性能优化：多级过滤

对于大规模知识库（数万篇文档），逐一计算哈希值的成本较高。生产系统通常采用多级过滤策略：

  1. 第一级：文件系统元数据过滤 — 对比 last_modified 时间戳，仅对修改时间变化的文档计算哈希
  2. 第二级：文件大小预筛 — 文件大小未变化且修改时间未变化的文档直接跳过
  3. 第三级：内容哈希精确对比 — 对通过前两级过滤的文档计算哈希并对比
过滤层级检测方式速度准确度成本
第一级last_modified 时间戳极快中（可能误报）几乎为零
第二级文件大小极快中几乎为零
第三级内容哈希较慢精确需读取全文

ID 设计规范

为了精准定位和删除文档关联的所有 chunk，ID 设计需要包含文档溯源信息：

  • 方案一：chunk ID 包含文档 ID — 如 product_manual_chunk_001，通过前缀匹配即可定位所有关联 chunk
  • 方案二：元数据中存储来源文档 ID — 在 chunk 的 metadata 中设置 source_doc_id 字段，通过向量库的 filter 功能查询

推荐使用方案二（元数据存储），因为大多数向量数据库（Pinecone、Milvus、Qdrant）都支持基于 metadata filter 的高效删除操作，且 ID 命名可以更灵活。

变化感知机制是更新系统的"触发器"——它决定了哪些文档需要重新处理，直接影响更新效率和计算成本。

四、触发机制：轮询 vs 事件驱动

知识库更新需要一个触发机制来感知外部数据变化。两种主流方案各有适用场景：

定时轮询（Polling）

按固定间隔（如每 5 分钟、每小时、每天）扫描文档源，检测变化并触发更新。

  • 实现简单：一个定时任务 + 变化检测逻辑
  • 延迟可控：更新延迟 = 轮询间隔，如每 5 分钟轮询则最大延迟 5 分钟
  • 资源可预测：CPU 和网络开销固定在轮询时间点
  • 适用场景：内部知识库、低频更新（文档变化频率 < 每小时 10 次）

事件驱动（Event-Driven）

通过 Webhook 或消息队列（Kafka/RabbitMQ）实时接收文档变化事件，立即触发更新。

  • 实时性高：文档变化后毫秒级触发更新
  • 资源高效：无变化时不消耗计算资源
  • 架构复杂度高：需要集成事件源、消息队列、消费者
  • 适用场景：客服知识库、实时性要求高的场景、文档变化频率高的系统

选择触发机制的核心考量：更新频率和实时性需求。低频率用轮询（简单可靠），高频率用事件驱动（高效实时）。

五、自动化更新工作流

触发机制解决"何时感知到变化"，而从变化检测到发布上线的完整链路，需要一条自动化流水线来可靠落地。

手动更新知识库的三大风险：忘记删除旧文档的向量（僵尸 chunk）、分块参数不一致（新旧文档分块大小不同）、更新后不验证就上线（检索退化无人知晓）。自动化流水线将这三个人为风险降为零。

生产案例：金融企业自动化的实际效果

某金融企业 RAG 系统日均更新 200+ 篇合规文档。手动更新时代：更新失败率 8%，平均每次更新需要 2 人 / 3 小时，每月因旧文档未删除导致的"过时回答"投诉约 15 次。部署自动化流水线后：更新失败率降至 0.1%，人工干预从每天 2 次降至每周 1 次，过时回答投诉降为 0 次。全量更新（50 万文档）从人工的 8 小时缩短至自动化的 2.5 小时（含质量校验）。

六、特殊场景：删除、重建与灰度更新

文档删除与僵尸 Chunk 清理

文档删除时必须同步清理向量库中的关联 chunk，否则会产生 僵尸 chunk——已被删除的文档的内容仍然作为 chunk 存在于向量库中，继续参与检索和生成。

僵尸 chunk 是 RAG 系统中最危险的"静默错误"：系统不会报错，但会基于过时的信息给出错误的回答。在金融合规和医疗领域，一条僵尸 chunk 可能导致严重的法律或安全风险。

# 文档删除的安全清理流程
def delete_document(doc_id: str):
    # 1. 查询关联 chunk 数量（审计用）
    count = vector_store.count(
        filter={"source_doc_id": doc_id}
    )
    
    # 2. 删除所有关联 chunk
    vector_store.delete(
        filter={"source_doc_id": doc_id}
    )
    
    # 3. 从注册表中移除
    registry.remove(doc_id)
    
    # 4. 验证删除完成
    assert vector_store.count(
        filter={"source_doc_id": doc_id}
    ) == 0

某企业知识库的真实审计数据印证了问题的严重性：6 个月内累积了约 12,000 条残留向量（占总向量的 8%），导致检索结果中约 5% 的 Top-5 命中指向已删除的文档。用户反馈"回答引用的文档打不开"，正是僵尸 chunk（也称"幽灵向量"）积累的典型症状。

最后一道防线：每次更新后执行"僵尸 chunk 扫描"——遍历向量库中所有唯一的 source_doc_id，验证其对应文档仍存在于文档库中，不存在则清除。这是防止僵尸 chunk 随时间积累的有效手段。

全量重建

全量重建是指清空向量库后重新处理所有文档。虽然成本最高，但在以下场景中是必要的：

  • 更换 embedding 模型 — 不同模型的向量空间不兼容，必须全量重新向量化
  • 更换 chunk 切分策略 — 如从固定长度切割切换到语义边界切割
  • 知识库规模较小（几十篇文档）— 全量重建的成本可以忽略
  • 数据一致性出现严重问题 — 需要"干净重启"

增量 vs 全量：30% 变更率阈值

除了上述必须全量重建的场景，同一模型下出现大批量文档变更时，还需要在"逐文件增量处理"与"全量重建"之间做选择。经验阈值是变更率 30%：变更文档占比低于 30% 走增量更新，达到或超过 30% 则切换全量重建。

阈值背后是两条成本曲线的交叉点——"增量的逐文件开销 vs 全量的批处理效率"：增量更新需要对每个变更文件单独执行切割与向量化，存在 Embedding API 调用的启停开销；全量更新可以批量并行处理，吞吐率更高。当变更比例超过 30% 时，增量的逐文件开销接近甚至超过全量的批处理时间。

注意 20%-40% 之间存在灰色区间：两种策略的成本差距不大，建议优先选全量以获得更干净的向量库状态，避免增量累积的碎片化问题。具体阈值需结合实际数据量、Embedding API 吞吐率和网络延迟调优。

灰度更新（Blue-Green Deployment for RAG）

灰度更新借鉴了软件发布中的蓝绿部署思想：同时保留新旧两个版本的知识库，通过验证后再切换线上流量。

灰度更新流程: Phase 1: 并行写入 ┌─────────────────┐ ┌─────────────────┐ │ v_old (活跃) │ │ v_new (验证中) │ │ version=old │ │ version=new │ │ ← 线上检索 │ │ ← 离线测试 │ └─────────────────┘ └─────────────────┘ Phase 2: 验证通过 → 切换流量 ┌─────────────────┐ ┌─────────────────┐ │ v_old (待删除) │ │ v_new (活跃) │ │ version=old │ │ version=new │ │ ← 保留 7 天 │ │ ← 线上检索 │ └─────────────────┘ └─────────────────┘ Phase 3: 清理旧版本 删除 version=old 的所有 chunk

灰度更新的实施要点：

阶段操作持续时间回滚能力
并行写入新文档同时写入新旧两个版本视验证周期直接丢弃 v_new
质量验证在 v_new 上运行测试 query，对比回答质量通常 3-7 天不切换即回滚
流量切换将线上检索路由切换到 v_new瞬间（路由变更）路由回切到 v_old
旧版清理确认稳定后删除 v_old 数据切换后 7-30 天清理前可随时回切

灰度更新的核心理念：永远保留"后悔药"——在确认新版本质量达标之前，旧版本始终保持可用，确保任何异常都能秒级回滚。

版本管理：文档语义化版本与单库 vs 双库

灰度更新解决的是向量库的发布安全，完整的更新体系还需要文档库层面的版本管理。文档版本管理采用语义化版本（如 v1.0、v1.1、v2.0），每次更新递增版本号；每个主版本保留完整快照（如 v1.0_snapshot/），支持回滚到历史状态。生产环境始终使用 latest 标签指向最新稳定版本，开发/测试环境可以指向特定版本号。

向量库的版本管理则有两种核心方案，与灰度更新直接对应：

  • 方案一：单库 + 版本标签 — 在向量库中维护 doc_version 元数据字段，查询时通过过滤条件 WHERE doc_version = 'latest' 只返回当前版本的向量；旧版本向量保留在库中用于回滚。优点是存储成本低、实现简单；缺点是旧版本数据堆积会导致库体积膨胀，查询时有额外过滤开销。
  • 方案二：双库切换（灰度更新的完整形态） — 维护两个独立向量库（production 和 staging），更新时先写入 staging 库，完成质量校验后将 production 指针原子切换到 staging 库；旧 production 库保留作为回滚目标。优点是实现零停机更新、切换瞬间完成；缺点是存储翻倍、运维复杂度增加。

生产建议：文档量 < 50 万且更新频率低的系统用单库方案即可；文档量 > 50 万或有高可用要求（SLA ≥ 99.9%）的系统应投入双库方案。双库方案的核心价值不仅是零停机，更在于"先验证再上线"的安全机制——staging 库可以跑完整的回归测试后再切换。

七、Chunk 级增量更新与实时 Embedding Pipeline

Chunk 级增量更新

对于超大文档（如技术手册、法律条文），文档级先删后增的成本较高。Chunk 级增量更新通过对比每个 chunk 的哈希指纹，仅更新发生变化的 chunk。

Chunk 级增量更新原理: 当前 chunk 指纹: {C1:h001, C2:h002, C3:h003, C4:h004, C5:h005} 新版 chunk 指纹: {C1:h001, C2:h999, C3:h003, C5:h005, C6:h006} │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ 跳过 更新 跳过 保留 新增 (未变) (内容变) (未变) (未变) (新chunk) 旧版独有: C4 → 删除 新版独有: C6 → 新增 哈希变化: C2 → 更新 哈希相同: C1, C3, C5 → 跳过

LangChain 的 Index API 和 LlamaIndex 的 DocumentStore 都内置了 chunk 级增量更新能力，通过 Record Manager 组件跟踪每个 chunk 的源文档 ID、哈希指纹和时间戳。

实时 Embedding Pipeline

对于高频更新的场景（如客服知识库、实时文档协作），需要构建流式 embedding pipeline：

  • 使用 CDC（Change Data Capture）捕获文档源的行级变化
  • 通过消息队列（Kafka/Confluent）将变化事件流式传输
  • 流式处理引擎（如 Apache Flink）实时执行切割、embedding 生成和向量库 upsert
  • 上下文同步延迟从小时级降至毫秒级

  • 严格执行先删后增流程，确保数据一致性
  • 对高风险场景（金融、医疗）实施灰度更新
  • 设置更新后的自动化验证（chunk 数量检查、抽样检索测试）
  • 记录完整的更新审计日志（谁更新了什么、何时、影响了多少 chunk）
  • 不要尝试"就地更新"单个 chunk——边界漂移问题会导致新旧内容混杂
  • 不要在删除文档时忘记清理向量库——僵尸 chunk 是静默的定时炸弹
  • 不要在更换 embedding 模型后只做增量更新——必须全量重建
  • 不要忽略更新过程中的数据空窗期——生产系统需要灰度策略或双写
  • 不要假设"删除成功了"——每次删除后必须验证 count == 0

RAG 知识库更新的最高原则：宁可多花一次 embedding 的计算成本，也不要让新旧数据混杂——数据一致性的价值远大于节省的那点计算费用。

三重质量校验与通过标准

上表的监控指标用于更新过程的持续监测，发布前的校验还需要一组明确的通过标准——更新完成 ≠ 更新成功，发布前必须验证三件事：分块没丢（完整性）、向量没坏（一致性）、检索没退化（有效性）：

  • 校验一：分块完整性检查 — 逐文档对比更新前后的分块数。如果某篇文档的分块数异常变化（如从 50 块变成 3 块），说明文档解析失败——常见原因是 PDF 表格解析异常或编码问题。规则：任何文档分块数变化超过 ±30% 需要人工审查。
  • 校验二：向量维度一致性检查 — 随机抽样 100 个新向量，验证维度是否与模型配置一致。例如 bge-large-zh 输出 1024 维，如果库中存了 512 维向量，说明存在截断或配置错误；维度不一致会导致距离计算错误或写入失败。
  • 校验三：检索召回率抽检 — 维护一个包含 20-50 条标准 query 的测试集，每个 query 标注"应该命中的文档"；更新后自动运行测试集，对比更新前后的 Top-5 命中率，命中率下降超过 10% 即自动触发回滚。

def update_with_monitoring(doc_id: str, new_content: str):

监控的核心原则：每次更新都应产生可追踪的指标——触发次数、跳过次数、删除 chunk 数、新增 chunk 数、耗时。当这些指标出现异常波动时，系统应自动告警并暂停后续更新，直到人工排查确认。

Q&A

先删后增过程中的"数据空窗期"如何处理？
有三种策略消除空窗期：(1) 双写策略——先将新 chunk 写入向量库（使用临时 version=new 标签），等写入完成后删除旧 chunk（version=old），最后将新 chunk 标签改为 active；(2) 事务性操作——部分向量库（如 Qdrant、Milvus）支持批量操作，可以在一个事务中同时执行删除和插入；(3) 灰度切换——维护两个独立的 collection，切换时只需修改检索路由，实现零停机更新。推荐策略 (3)，它在可靠性和实现复杂度之间取得了最佳平衡。
内容哈希应该对整个文档还是每个 chunk 计算？
两个层级都需要：(1) 文档级哈希用于快速判断"文档是否有变化"——如果文档哈希未变则直接跳过，避免不必要的切割和向量化；(2) Chunk 级哈希用于 chunk 级增量更新——精确识别哪些 chunk 内容发生了变化。实践中推荐先用文档级哈希做粗筛，仅对变化的文档进一步做 chunk 级对比。这样可以在大规模知识库中显著降低更新开销，因为大部分文档在两次更新之间并未变化。
更换 embedding 模型后，能否只做增量更新？
不能。不同 embedding 模型的向量空间完全不同——例如 OpenAI text-embedding-3-small 生成 1536 维向量，text-embedding-3-large 生成 3072 维向量，维度不兼容；即使维度相同，不同模型的语义编码方式也不同，导致新旧向量在同一个索引中无法正确比较相似度。正确做法是全量重建：清空向量库 → 用新模型重新向量化所有文档 → 写入新向量。对于大规模知识库，可以分批执行全量重建（如每次处理 1000 篇文档），配合灰度切换策略逐步迁移。
向量数据库中的 soft delete 和 hard delete 有什么区别？该用哪种？
Soft delete 将向量标记为"已删除"但不立即释放存储空间，检索时自动过滤。Hard delete 立即移除向量和索引节点。区别在于：(1) Soft delete 速度快但占空间——适合高频更新场景，删除的向量会在后台 compaction 时清理；(2) Hard delete 释放空间但有延迟——修改索引结构（如 HNSW 图）需要时间。推荐策略：日常更新使用 soft delete（速度快，不影响检索性能），定期维护任务中执行 compaction 回收空间（如每天凌晨低峰期）。
灰度更新中如何验证新版本的质量？
验证流程包含三个层面：(1) 基础验证——检查新版本的 chunk 数量、文档覆盖率、元数据完整性是否符合预期；(2) 检索验证——在预定义的测试 query 集上对比新旧版本的 recall@k、MRR 等指标，确保新版本不低于旧版本；(3) 端到端验证——模拟真实用户查询，对比新旧版本生成的回答质量（可使用 LLM 自动评分或人工抽检）。建议至少运行 3-7 天的验证期，覆盖业务的各种查询模式后再切换流量。
如何防止并发更新导致的数据不一致？
并发更新的核心风险是"两个更新进程同时操作同一文档"导致 chunk 重复或丢失。解决方案：(1) 分布式锁——在更新文档前获取以 doc_id 为 key 的分布式锁（如 Redis SETNX），确保同一文档同一时间只有一个更新进程；(2) 版本号机制——每个文档维护递增版本号，更新时带上版本号，后到的更新如果发现版本号已被更新则自动重试或放弃；(3) 事件排序——在消息队列中使用 doc_id 作为 partition key，确保同一文档的事件按顺序消费。推荐组合使用方案 (1) + (3)。
CDC 实时管道适用于什么规模的系统？小团队有必要上吗？
CDC 实时管道的投入产出比取决于更新频率和实时性需求。建议：(1) 文档更新 < 每天 100 次 → 用定时轮询足够，无需 CDC；(2) 文档更新 100-1000 次/天 → 用事件驱动（Webhook + 消息队列），不一定需要完整 CDC；(3) 文档更新 > 1000 次/天或要求秒级延迟 → 部署完整 CDC 管道（如 Debezium + Kafka + Flink）。小团队如果文档量在几百篇、更新频率低于每天几十次，完全可以用定时轮询 + 先删后增搞定，无需过度工程化。
向量维度不一致通常是什么原因导致的？
常见原因有四种：① Embedding 模型配置错误（如模型输出 1024 维但代码中截断为 512 维，常见于手动设置 dimension 参数时）；② 向量化过程中 GPU OOM 导致部分向量未完整计算，被填充为零向量或默认值；③ 向量库 Schema 配置与模型不匹配（如建库时设了 512 维但模型实际输出 1024 维）；④ 批量处理时某批次失败，重试逻辑未正确覆盖失败批次。维度不一致会导致向量无法正确存储或距离计算结果错误，是必须在质量校验阶段拦截的问题。
全量更新期间（通常数小时），检索服务是否完全不可用？
取决于是否采用双库方案。如果直接在 production 库上全量重建（清空后重写），服务确实不可用。双库方案下，全量更新在 staging 库执行，production 库继续服务；更新完成后原子切换指针（通常 < 100ms），用户完全无感知。建议在业务低峰期（如凌晨）执行全量更新，即使使用双库方案也应避免在高峰期进行——因为全量更新会大量消耗 Embedding API 的配额，可能影响在线检索的性能。
增量更新累积多次后，向量库会不会出现"碎片化"问题？
会的。长期增量更新会导致三个碎片化问题：① 同一文档的向量分散在不同时间写入，可能在向量库的物理存储上不连续，影响检索效率；② 删除操作留下的"空洞"降低存储利用率（类似磁盘碎片）；③ 分块策略微调后，新旧文档的分块粒度不一致。建议每 3-6 个月做一次全量重建（即使不需要换模型），清理碎片、统一分块策略、重建索引。这就像数据库的 VACUUM 操作。
