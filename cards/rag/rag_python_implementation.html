G13 · 用 Python 构建 RAG 系统

RAG 全流程回顾 → 项目搭建 → Embedding → 向量数据库 → Cross Encoder 重排 → LLM 生成答案

RAG 的本质是一个"两级漏斗"：先用便宜快速的 Embedding 从海量文档中粗筛出 Top-K 候选，再用精确但昂贵的 Cross Encoder 精排出 Top-N，最后只把这几段最相关的内容喂给 LLM——检索的精度决定了答案的上限。

一、RAG 全流程回顾

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是大模型的两大顽疾：知识有截止日期、对企业私有数据一无所知。它的思路很直接——回答前先去知识库里"查资料"，再带着资料作答。整个系统分为离线准备和在线回答两大阶段。

┌──────────────────── 准备阶段（离线，提问前完成） ────────────────────┐ │ │ │ 原始文档 ──→ 分片(Chunking) ──→ Embedding 向量化 ──→ 存入向量数据库 │ │ │ └──────────────────────────────┬─────────────────────────────────────┘ │ ┌──────────────────────────────▼─────────────────────────────────────┐ │ 回答阶段（在线，每次提问触发） │ │ │ │ 用户问题 ──→ 向量化 ──→ 召回 Top-K ──→ Cross Encoder 重排 Top-N │ │ │ │ │ ▼ │ │ LLM 生成答案 ←── 拼接 Prompt（Top-N 片段 + 问题） │ └────────────────────────────────────────────────────────────────────┘
阶段环节操作
准备阶段（提问前）分片将资料切分成多个片段（chunk）
索引每个片段经 Embedding 模型生成向量，存入向量数据库
回答阶段（提问后）召回用户问题转为向量，从向量数据库检索 Top-K 相似片段
重排用 Cross Encoder 对 Top-K 精排，筛选 Top-N
生成将 Top-N 片段 + 用户问题发给 LLM，生成最终答案

把 RAG 想象成开卷考试：准备阶段是"把教材撕成卡片编好目录"，回答阶段是"按考题翻出最相关的几张卡片，照着卡片答题"。卡片撕得好不好、翻得准不准，直接决定答题质量。

RAG = 准备阶段（离线构建知识库）+ 回答阶段（在线检索+生成）。核心组件：分片器 + Embedding 模型 + 向量数据库 + Cross Encoder + LLM。

二、项目搭建与依赖选型

本视频选择"轻量全家桶"：用 uv 管理 Python 项目，全部核心组件本地可跑，除 LLM 生成外不依赖任何云服务。

mkdir rag && cd rag
uv init .
rm main.py   # 删除模板生成的文件
# 安装四个核心依赖
uv add sentence-transformers chromadb cross-encoder openai
依赖在系统中的角色选择理由
sentence-transformersEmbedding 模型（召回）本地推理、模型库丰富，all-MiniLM-L6-v2 仅 22M 参数
chromadb向量数据库（存储与检索向量）嵌入式、零运维，pip 安装即用，适合原型与中小规模
cross-encoder重排模型（精排）与 sentence-transformers 同源，API 一致易集成
openaiLLM 生成最终答案API 稳定；也可无缝替换为本地模型或其他厂商 API

这套选型的精髓是"能本地就本地"：Embedding 和重排都在本机 CPU 上跑，只有最后一步生成答案才调用 LLM API——敏感文档不出内网，成本也降到最低。

开发环境推荐使用 Jupyter Notebook 作为交互式开发环境：RAG 的每个环节（分片效果、向量相似度、重排分数）都需要反复观察中间结果，Notebook 的"逐格执行 + 即时输出"特性非常适合 AI 领域的调试和验证，等流程跑通后再整理成脚本。

中文场景注意：all-MiniLM-L6-v2 是英文模型，中文知识库应换用 bge-small-zh-v1.5、m3e 等中文 Embedding 模型，否则召回质量会明显下降。

三、准备阶段：分块与向量化

Chunking（分块）是 RAG 的第一个质量关口：文档切得太大，一个 chunk 里混杂多个主题，向量被"稀释"导致召回不准；切得太小，片段丢失上下文，模型拿到也答不完整。业界常见的平衡点是 256~512 token 一块，并留 10%~20% 的重叠防止关键句被拦腰切断。

参数常见取值权衡
chunk 大小256~512 token（约 400~800 汉字）太小丢语境，太大稀释语义焦点
重叠（overlap）10%~20%防止关键信息恰好被切在边界上
切分依据优先段落/标题/句子边界语义边界优于机械的固定长度
元数据保留标题、来源、章节号重排和生成时可辅助判断可信度

3.1 一个最小可用的分块器

def chunk_text(text, size=400, overlap=60):
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start += size - overlap   # 后退 overlap 个字符，保证重叠
    return chunks

3.2 Embedding 模型选型

Embedding（向量化）把每个 chunk 映射为高维空间中的一个点，语义相近的文本距离更近。模型选型直接决定召回质量：

模型维度 / 规模适用场景
all-MiniLM-L6-v2384 维 / 22M 参数英文、轻量、CPU 秒级编码，本视频首选
bge-small-zh-v1.5512 维 / 33M 参数中文知识库，本地部署友好
text-embedding-3-small1536 维 / API 服务免本地运维，按量付费

Embedding 模型不是越大越好——22M 的 MiniLM 配合合理的分块策略，往往比"大模型 + 粗糙分块"召回更准。分块质量是地基，模型只是上层建筑。

存入 ChromaDB 时务必记录每个向量对应的 chunk 原文与元数据——检索返回的只是向量 ID 和距离，答案生成阶段需要凭 ID 取回原文。

四、回答阶段：召回、重排与生成

回答阶段的核心是"两级漏斗"：Embedding 负责从几千个 chunk 里快速捞出 Top-K 候选（粗筛），Cross Encoder 再对这几个候选做精确打分排序（精排）。两者分工的根本原因在于架构差异。

Bi-Encoder（Embedding 召回）——快，可预计算： query ──→ [ Encoder ] ──→ 向量q ┐ ├─→ 余弦相似度 ──→ Top-K 候选 doc ──→ [ Encoder ] ──→ 向量d ┘ (所有 doc 向量离线算好) Cross Encoder（精排）——准，必须成对推理： [ query ⊕ doc 拼接 ] ──→ [ Encoder ] ──→ 相关性分数 (0~1) (query 与 doc 联合编码，无法预计算，每对都要过一次模型)
维度Embedding（Bi-Encoder）Cross Encoder
处理方式分别编码 query 和 document联合编码 (query, document) 对
速度快（document 向量可预计算，检索只是近邻查找）慢（每对需单独过一次模型推理）
精度中等（两段文本各自压缩成一个向量，信息有损）更高（词级交互注意力，能捕捉细粒度匹配）
角色粗筛：从海量文档中召回大量候选精排：从少量候选中选出最好的

4.1 Top-K 与 Top-N 的取值

参数推荐值理由
召回数 K10~20粗筛阶段宁多勿漏，漏掉的片段重排救不回来
精排数 N3~5太多会稀释 LLM 注意力、推高 token 成本
相似度阈值按业务标定全部候选都低于阈值时，应返回"未找到相关资料"而非硬答

4.2 重排的关键代码

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
pairs = [(query, doc) for doc in top_k_docs]      # K 个候选对
scores = reranker.predict(pairs)                  # 逐对打分
top_n = [doc for _, doc in sorted(zip(scores, top_k_docs),
                                  reverse=True)][:3]

为什么不能只用一个精确模型？算笔账：1 万个 chunk 全部用 Cross Encoder 逐一打分要推理 1 万次，而 Embedding 召回只需 1 次向量查询 + 20 次重排推理——两级漏斗用 1% 的算力换来了接近全量精排的效果。

最后的生成环节很朴素：把 Top-N 片段按重排分数从高到低拼进 prompt，附上用户问题，交给 LLM。一个值得加上的约束是"只根据提供的资料回答，资料不足时明说"——这能显著降低 RAG 场景下的幻觉率。

五、关键参数与业界基准

RAG 调优不能靠猜。Anthropic 在 2024 年 9 月发布的 Contextual Retrieval（上下文检索）实践中，用同一套评测基准对比了多种检索方案，给出了目前业界引用最广的一组数字。

检索方案top-20 检索失败率（相对朴素 Embedding）
朴素 Embedding 召回基准线
Contextual Embeddings + Contextual BM25（混合检索）失败率降低 49%
上述方案 + Reranking（重排）失败率降低 67%
Contextual Retrieval 混合检索流水线（Anthropic 方案） 原始文档 ──→ 分块 ──→ LLM 为每块补上下文说明（平均约 59 token） │ ┌────────────────────┴────────────────────┐ ▼ ▼ Contextual Embedding Contextual BM25 （语义向量索引，懂"意思"） （关键词倒排索引，认"原词"） └────────────────────┬────────────────────┘ ▼ 合并两路结果（混合检索，-49%） ▼ Cross Encoder 重排（再降，累计 -67%） ▼ Top-N ──→ LLM 生成

这组数字里藏着三个关键结论：

  • 混合检索优于单一向量检索：Embedding 擅长语义相似，BM25（经典的关键词加权检索算法）擅长精确词匹配（如产品型号、错误码），两者互补。用户搜"ERR-4012 错误码"时，向量检索可能不如关键词检索准。
  • 重排的收益是决定性的：仅加一步 Cross Encoder 重排，失败率从 -49% 进一步降到 -67%，几乎贡献了全程一半的收益——这正是本视频把重排作为独立环节的原因。
  • 上下文补充四两拨千斤：Contextual Retrieval 的做法是让 LLM 为每个 chunk 生成一句"它在整篇文档中的位置与作用"的说明（官方测算平均约 59 token），拼在 chunk 前再做 Embedding。借助 Prompt Caching，处理整个知识库的成本约 1 美元/百万 token 级别。

这组基准给出的调优优先级非常清晰：先补关键词混合检索，再加重排，最后才考虑换更贵的 Embedding 模型——前两步的性价比远高于第三步。

六、生产案例与调优实践

RAG 的坑几乎都不在"能不能跑通"，而在"跑得准不准"——两个真实案例分别展示了检索侧和工程侧的典型解法。

案例一：Anthropic Contextual Retrieval 官方实验。背景：Anthropic 内部知识库问答系统需要检索公司文档，朴素 Embedding 方案下，正确答案经常不在 top-20 召回结果里。问题：chunk 脱离原文后语义不完整——一句"它比上一版本快 3 倍"单独看根本不知道"它"是谁。方案：①让 LLM 为每个 chunk 生成约 59 token 的上下文说明并拼回 chunk；②叠加 BM25 做混合检索；③最后加 Cross Encoder 重排。效果：top-20 检索失败率先降 49%（混合检索），再降 67%（叠加重排）；借助 Prompt Caching，为整个知识库补上下文的成本控制在约 1 美元/百万 token 级别。
案例二：本视频的最小本地系统。背景：小团队想给内部技术文档做问答，但没有 GPU、没有专职运维，文档还涉及内部信息不宜上云。问题：主流 RAG 方案动辄依赖云端 Embedding API + 托管向量库，成本和数据合规都过不了关。方案：采用视频的轻量栈——22M 参数的 MiniLM 做 Embedding、嵌入式 ChromaDB 做向量库、ms-marco-MiniLM 做重排，全部在 CPU 本地运行，仅生成答案一步调用 LLM API。效果：数千篇文档的索引在数分钟内完成，单次"召回 + 重排"端到端约 200 毫秒级，除 LLM API 调用外零额外成本，敏感文档全程不出内网。

  • 先建 20~50 条"问题→正确 chunk"的评测集，再动手调参
  • 中文场景优先选 bge/m3e 等中文 Embedding 模型
  • 给 chunk 保留标题、来源等元数据，供重排与引用展示
  • 召回为空或分数过低时，让系统明说"未找到相关资料"
  • 不要一上来就换最大的 Embedding 模型——先查分块和重排
  • 不要用固定长度硬切 Markdown/代码（按标题与段落边界切）
  • 不要跳过重排直接把 Top-20 全塞给 LLM（噪音稀释注意力）
  • 不要混用不同 Embedding 模型分别处理 query 和文档（向量空间不一致）

Q&A

用 Python 构建 RAG 系统的完整流程是什么？
分为两大阶段。①准备阶段（离线）：将文档分片（Chunking，常用 256~512 token、10%~20% 重叠），每个片段经 Embedding 模型（如 sentence-transformers 的 all-MiniLM-L6-v2）生成向量，存入向量数据库（如 ChromaDB）。②回答阶段（在线）：用户问题经同一 Embedding 模型转为向量，从向量库检索 Top-K 相似片段（召回，K 常取 10~20），用 Cross Encoder 对候选精排取 Top-N（重排，N 常取 3~5），最后将 Top-N 片段拼接用户问题发给 LLM 生成答案。关键设计是 Embedding 粗筛快但精度一般、Cross Encoder 精排慢但精度高，两者配合实现速度与精度的平衡。
Embedding 模型和 Cross Encoder 在 RAG 中各扮演什么角色？
Embedding（Bi-Encoder）分别将 query 和 document 编码为向量，通过余弦相似度快速检索。它的优势在于所有 document 向量可以离线预计算，检索时只需算一次 query 向量再做近邻查找，速度极快，适合从海量文档中粗筛候选。Cross Encoder 将 query 和 document 拼接后联合编码，输出一个精确的相关性分数，词级交互注意力让它能捕捉细粒度匹配，精度更高但每对都要单独推理，速度慢，只适合对少量候选精排。所以 RAG 系统让两者分工：Embedding 召回 Top-10~20，Cross Encoder 精排取 Top-3~5，用约 1% 的算力换取接近全量精排的效果。
为什么召回和重排要用两个模型，而不是直接用一个最精确的模型？
因为精度和算力是矛盾的。Cross Encoder 虽然精确，但它无法预计算——每来一个 query，都要和库里每个文档成对推理一次。假设知识库有 1 万个 chunk，全量精排就是 1 万次模型推理，单次查询可能要几十秒，生产环境完全不可接受。而 Embedding 方案中，1 万个文档向量可以离线算好存进向量库，在线只需 1 次向量查询就能从 1 万块中捞出 Top-20，再对这 20 个候选做 Cross Encoder 精排，总共约 21 次计算。这就是"两级漏斗"的精髓：用便宜的粗筛把候选集压缩到精确模型负担得起的规模。
chunk 切多大合适？切分策略怎么选？
业界常见的平衡点是 256~512 token 一块（约 400~800 汉字），并保留 10%~20% 的重叠。背后的权衡是：chunk 太小会丢失上下文（一句"它快 3 倍"单独成块毫无意义），太大则一个块里混杂多个主题，向量被稀释导致召回不准。策略上优先按语义边界切分——Markdown 按标题、代码按函数、文章按段落，而不是机械的固定长度硬切。重叠的作用是防止关键信息恰好被切在边界上。实操建议：先用默认值跑通，再用"问题→正确 chunk"评测集验证，召回片段答非所问就调小，信息残缺就调大。
为什么问题向量化必须用和文档相同的 Embedding 模型？
因为不同 Embedding 模型学出的向量空间完全不同——同一个模型把语义相近的文本映射到相近的位置，但模型 A 的向量空间和模型 B 的向量空间在数学上没有任何对应关系。用模型 A 编码的文档向量和用模型 B 编码的 query 向量做余弦相似度，得到的距离是随机噪音，检索结果会完全失效。这个错误在升级模型时最容易犯：换了新的 Embedding 模型却只改了 query 侧，忘了全量重建文档索引。正确做法是：每次更换 Embedding 模型，必须用新模型把整个知识库重新向量化一遍。
Top-K 和 Top-N 怎么取值？取错了会怎样？
推荐召回 K 取 10~20、精排 N 取 3~5。K 的原则是"宁多勿漏"：粗筛阶段漏掉的片段，后面再精确的重排也救不回来，所以 K 要大到有把握覆盖正确答案；但 K 太大（比如 100）会拖慢重排速度。N 的原则是"少而精"：塞给 LLM 的片段太多会稀释它的注意力（Lost in the Middle 现象），还推高 token 成本，3~5 个高相关片段通常足够。调参信号很直观：重排后答案仍漏要点就增大 K 或 N，答案掺杂无关信息就减小 N 或检查重排模型是否太弱。所有取值最终都应以评测集分数为准，而不是拍脑袋。
检索到了相关片段，但 LLM 答案还是不准，可能是什么原因？
问题出在生成环节而非检索环节，常见原因有三类。①片段顺序问题：LLM 对长上下文中间位置的信息利用率低（Lost in the Middle），最相关的片段应放在最前或最后。②缺少生成约束：没有明确要求"只根据提供的资料回答，资料不足时明说"，模型会自作主张地用预训练知识补全，引入幻觉。③片段本身的问题：chunk 虽然相关但信息残缺（比如只有结论没有数据），这时需要回到分块环节加大 chunk 或补充元数据。排查方法：先人工检查 Top-N 片段里是否真的包含答案——包含但答错是生成问题，不包含则是检索问题，两条路的解法完全不同。
