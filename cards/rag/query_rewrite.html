G12 · Query Rewrite 查询改写

Query Rewriting — 语义鸿沟、规则/NLP/大模型三大改写方案、工业级混合架构、HyDE / Multi-Query / Step-back 高级技术

Query Rewrite 的本质：弥合用户口语表达和知识库专业术语之间的语义鸿沟，让检索能找到"意思对但字面不同"的文档。改写质量直接决定召回质量——再好的检索算法也无法弥补"问错了问题"的错误。

一、语义鸿沟：为什么 Query 需要改写？

语义鸿沟的根源：用户用"怎么报销"提问，知识库文档叫"差旅费用报销流程管理办法 v2.3"——两者说的是同一件事，但在向量空间中的余弦相似度可能只有 0.3-0.5，远低于匹配阈值。

在实际 RAG 系统中，未改写的自然语言 query 与知识库内容的语义匹配度通常只有 0.3-0.5，经过改写后可提升到 0.6-0.8，直接导致检索召回率相差 2-3 倍。

二、三大主流改写方案

三种方案的关系：规则改写是"查字典"（快但死板），NLP 改写是"请翻译"（准但需培训），大模型改写是"问专家"（强但贵）——工业界的选择是三个都用，按难度分层。

方案 1：规则改写 — 快速启动的兜底层

规则改写的核心是两张表：同义词映射表（"报销" → ["费用报销", "差旅报销", "报销流程"]）和精确匹配表（"怎么报销" → "费用报销流程操作指南"）。实现简单、延迟几乎为零，是任何改写架构的第一层防线。

规则改写的致命缺陷是规则膨胀：刚开始 50 条规则覆盖 30% 的 query，半年后膨胀到 500+ 条却只覆盖 45%，因为规则之间会产生冲突和重叠，维护成本指数增长。

规则改写的定位：不是主力改写方案，而是"兜底层"——精确命中高频 query 时直接返回，避免后续更昂贵的计算。30% 的高频 query 可以被规则引擎覆盖。

方案 2：传统 NLP 改写 — 结构化场景的中间方案

传统 NLP 改写的 pipeline 包含四步：NER（命名实体识别）提取关键实体 → 意图分类器判断 query 类型 → 同义词扩展（WordNet/领域词典）→ 模板填充生成改写结果。

优势是结构化场景下效果稳定（如客服系统的"退款/换货/投诉"三类意图），成本可控。劣势是跨领域需要重新训练 NER 和意图分类器，上下文融合能力弱（难以处理多轮对话中的"它"指代什么）。

方案 3：大模型改写 — 当前工业界主流

大模型改写是当前工业界的主流方案，核心能力有三个：

能力说明示例
跨轮语义补全自动关联历史对话上下文历史: "我想了解报销" → 当前: "那差旅呢？" → "差旅费用报销流程"
多路查询扩展单问题拆解为多个检索路径"怎么报销" → "费用报销流程" / "报销审批标准" / "报销操作指南"

大模型改写的 Prompt 设计要点：temperature 设为 0.1（改写不需要创造性，需要准确性）；明确要求"生成 1-3 个不同角度的改写结果"；传入最近 2-4 轮历史对话用于上下文融合；要求"直接输出改写结果，每行一个，不要解释"以减少 token 消耗。

三、工业级混合架构：三层改写引擎

混合架构的核心洞察：80% 的 query 是简单的（规则可处理），15% 是常规的（轻量模型足够），只有 5% 是复杂的（需要大模型）——三层架构用最低成本覆盖全部场景。

缓存策略

企业知识库场景中，约 30-40% 的 query 是高频重复的。用 LRU 缓存改写结果（TTL=1 小时），可以将 LLM 调用减少 30-40%，显著降低成本和延迟。缓存 key 为 hash(query + context_last_2_turns)，确保同一 query 在不同上下文下不会返回错误缓存。

四、四种高级改写技术

四种高级技术各解决一种特定的语义鸿沟：HyDE 解决"问句 vs 陈述句"的风格差异，Multi-Query 解决"单角度不够"的覆盖问题，Step-back 解决"太具体找不到"的粒度问题，Decomposition 解决"太复杂拆不开"的复杂度问题。

4.1 HyDE（假设性文档嵌入）

HyDE 的策略非常反直觉：不是改写 query 本身，而是让 LLM 先生成一个假设性回答，然后用这个回答的 embedding 去检索。核心原理是 query 和文档之间存在"表达不对称"——query 是短、口语化的问句，文档是长、规范化的陈述句，而假设性回答与文档的风格更接近。

4.2 Multi-Query（多角度查询扩展）

Multi-Query 将单一 query 拆解为多个不同角度的检索查询，每个查询走独立的检索路径，最终合并结果。例如 "怎么报销" 被拆解为三个角度：①具体操作（"费用报销的具体操作步骤"）②制度规范（"公司费用报销管理制度和审批标准"）③相关概念（"费用报销的定义、适用范围和条件"）。

4.3 Step-back Prompting（退一步改写）

Step-back Prompting 对过于具体的 query 先"退一步"生成更高层次的问题，然后同时用原始 query 和高层次 query 检索。例如 "Llama 3.1 405B 在 MMLU 上的分数是多少？" → Step-back 为 "Llama 3.1 模型的性能评估结果"，同时检索具体分数和整体评估报告。

4.4 Query Decomposition（问题拆解）

Query Decomposition 将复杂的多意图 query 拆解为多个简单子查询，分别检索后合并结果。例如 "对比 GPT-4 和 Claude 3 在代码生成和数学推理上的表现" → 四个子查询："GPT-4 代码生成评估"、"Claude 3 代码生成评估"、"GPT-4 数学推理结果"、"Claude 3 数学推理结果"。

HyDE 为什么有效？核心原因是 query 和 document 的表达方式天然不对称——用户问"怎么报销"（动词短语），文档写"差旅报销流程管理办法"（名词短语）。HyDE 让 LLM 先生成一段类似文档风格的"假设性回答"，然后用这段回答的 embedding 去检索，匹配度大幅提升。在某些场景下比直接 query 检索提升 5-15% 召回率。但局限在于：如果 LLM 生成的假设性回答有事实错误，可能误导检索方向。

五、实践建议与常见陷阱

Query Rewrite 的实施不是一步到位，而是渐进式的——先用规则引擎快速上线，再逐步加入 NLP 和大模型能力，每一层都要有评估数据支撑。

实施路线图

Query Rewrite 渐进式实施路线: Phase 1 (快速启动): ├── 建立规则引擎 (同义词表 + 精确匹配) ├── 收集高频 query 日志 └── 效果: 召回率 +5-10% Phase 2 (NLP 增强): ├── 训练领域 NER 模型 ├── 训练意图分类器 ├── 构建领域同义词词典 └── 效果: 召回率 +15-20% Phase 3 (LLM 改写): ├── 设计改写 Prompt ├── 接入 LLM API + A/B 测试 └── 效果: 召回率 +25-35% Phase 4 (混合架构): ├── 整合三层引擎 + 智能路由 ├── 缓存高频 query 改写结果 └── 效果: 召回率 +30-40%, 延迟可控

生产案例：某电商 RAG 系统

背景：日均 8 万次商品咨询，上线 Query Rewrite 前搜索零结果率高达 18%。

改造方案：三层混合架构 + HyDE + Multi-Query 三路并行（原文 + 同义词 + HyDE）。

效果：搜索零结果率从 18% 降至 3%（降幅 83%）。HyDE 将查询"iPhone 16 续航"改写为假设性文档"iPhone 16 电池容量 3500mAh，视频播放可达 22 小时"，召回相关性从 0.42 提升至 0.81。三路并行总延迟仅增加 15ms（HyDE 用小模型生成，耗时 <10ms），NDCG@10 提升 34%。

Step-back Prompting 补充：将复杂查询"对比 AWS 和 Azure 的 GPU 实例性价比"拆解为三个子查询，答案完整度从 45% 提升至 89%。

Q&A

Query Rewrite 为什么是 RAG 系统中最容易被忽略但最关键的环节？

因为它是 RAG pipeline 的"入口阀门"——改写质量直接决定了后续检索和生成的质量上限。如果用户说"怎么报销"而知识库文档叫"差旅费用报销流程管理办法"，不做改写的余弦相似度可能只有 0.3，远低于匹配阈值，再好的 Reranker 也救不回来。实际系统中，未改写 query 的 Top-5 召回率通常只有 60% 左右，加上改写后可以提升到 85%，差距 25 个百分点。而且改写是唯一能在检索前干预的环节——分块、Embedding、索引都是离线做的，只有改写是在线实时的。

三大改写方案如何选择？工业界为什么偏爱混合架构？

三大方案各有适用场景：①规则改写——部署极快、延迟几乎为零，但只能处理简单场景，规则会膨胀 ②传统 NLP——结构化场景效果好、成本可控，但跨领域需重新训练 ③大模型改写——语义理解能力最强，支持多轮上下文融合，但延迟和成本较高。工业界偏爱混合架构的原因：80% 的 query 是简单的（规则可处理），15% 是常规的（轻量模型足够），只有 5% 需要大模型。混合架构用 120ms 的平均延迟（vs 纯大模型 850ms）和 $800/月成本（vs $3000/月）实现了比纯大模型还高 2-3% 的召回率。

HyDE 的核心原理是什么？什么情况下会失效？

HyDE (Hypothetical Document Embeddings) 的核心原理：不直接用 query 的 embedding 检索，而是让 LLM 先生成一个"假设性回答"，用这个回答的 embedding 去检索。解决的问题是 query-document 表达不对称——query 是短、口语化的问句，文档是长、规范化的陈述句，两者在向量空间中距离较远。假设性回答的风格更接近文档，匹配度更高。失效场景：①精确关键词查询（如 "torch.nn.Linear 参数"），假设性文档可能偏离精确术语 ②LLM 对领域完全不了解时，假设性文档质量极差 ③事实性错误会误导检索。改进：生成 3-5 个假设文档取 embedding 均值减少偏差。

多轮对话中的 Query Rewrite 有什么特殊挑战？

核心挑战是指代消解和上下文补全。用户第一轮问"我想了解报销制度"，第二轮问"那差旅呢？"——如果不传入上下文，"那差旅呢？"是一个完全不完整的 query。LLM 改写需要：①传入最近 2-4 轮历史对话 ②在 Prompt 中明确要求"融合上下文补全当前查询的完整语义" ③生成的改写结果应该是"差旅费用报销流程"而非简单的"差旅"。另一个挑战是意图切换——用户可能从"报销"话题突然跳到"请假"，此时不应该继续融合上一轮上下文。解决方案：让 LLM 判断当前 query 是否与上一轮话题相关，不相关则独立改写。

如何评估 Query Rewrite 的效果？有哪些量化指标？

四个核心量化指标：①召回率提升——改写后 Top-K 命中率 vs 改写前，目标 +15-30% ②准确率提升——改写后 Top-1 正确答案率 vs 改写前，目标 +10-20% ③回答质量——LLM-as-Judge 评分 (1-5 分)，目标 +0.5-1.0 分 ④延迟开销——改写引入的额外延迟，目标 <500ms (P95)。评估方法：A/B 测试是最可靠的方式——将用户随机分为改写组和无改写组，对比以上指标。注意：改写质量不能只看改写结果本身（如改写后的 query 是否"看起来更好"），而要看对最终回答质量的端到端影响。同时要监控"改写退化率"——改写后效果反而变差的 query 比例，应控制在 <5%。

工业级 Query Rewrite 系统的缓存策略如何设计？

缓存设计需要考虑三个维度：①缓存 key——hash(query + 最近 2 轮上下文)，确保同一 query 在不同上下文下返回不同结果 ②TTL（过期时间）——通常设为 1 小时，因为知识库可能随时更新 ③缓存大小——LRU 策略，max_size=10000，覆盖 Top 30-40% 的高频 query。效果：企业知识库场景中约 30-40% 的 query 是高频重复的，缓存可以将 LLM 调用减少 30-40%。额外优化：对知识库更新事件触发缓存失效（而非等 TTL 自然过期），确保改写结果与最新知识库一致。
