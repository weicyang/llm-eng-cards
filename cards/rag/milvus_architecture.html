G30 · Milvus：从单机到分布式的向量数据库

向量检索 vs 关系库 / Lite·Standalone·Distributed / QueryNode·DataNode·IndexNode / HNSW·IVF / 混合检索

Milvus 不是「会算余弦的 MySQL」。它把近似最近邻、标量过滤和存算分离做成了可水平扩展的检索引擎——向量是一等公民，关系字段只是过滤器。

一、为什么不能拿 MySQL 硬扛向量

关系库擅长精确匹配：主键、B+ 树、事务。Agent 的 RAG 和长期记忆要的是另一件事：把 query 编成向量，在百万到百亿条候选里找「最像」的 k 条。这是 ANN（Approximate Nearest Neighbor，近似最近邻：用可控误差换掉暴力扫描，把检索从 O(N) 降到近对数级）问题。MySQL 8 之后也能塞向量插件，但索引种类、过滤与 ANN 的协同、以及写入/检索独立扩容，都不是它的设计中心。

能力MySQL / pgvectorMilvus
主索引对象行 / 标量，向量是附加列向量集合是一等公民
规模百万级常见，再大要自己分片官方路径覆盖到百亿向量
扩容整库一起撑检索、写入、建索引分开扩
混合检索先过滤再扫，或插件 knn标量过滤 + 多路向量 + RRF/加权融合
Zilliz / LF AI 路径上的 Milvus 被定位成「从笔记本原型到数百亿向量集群同一套 API」。这不是营销口号，而是三种部署形态共享同一套 Collection / 搜索语义——换形态不必换查询语言。百万到十亿是常见生产跳档；过了十亿还用单机 Standalone，查询延迟和重建索引窗口都会按数据量线性恶化。

关系库问「等于多少」，向量库问「像到什么程度」。把后者硬塞进前者，短期能跑通 demo，长期会在索引和扩容上还债。

二、三种部署：Lite / Standalone / Distributed

视频从单机讲到分布式，对应官方三条产品线。Milvus Lite 是 Python 库，适合 Notebook 和边缘；Standalone 把核心打进一个 Docker，单机内存够就能扛中小生产；Distributed 跑在 Kubernetes 上，组件冗余、按角色扩容。

规模阶梯（同一套 SDK 语义） Jupyter / 单元测试 └─ Milvus Lite（进程内库） 单机生产、不想上 K8s └─ Standalone = Milvus 进程 + etcd + 对象存储 十亿级 / 要弹性 └─ Distributed Access : Proxy Coord : Root / QueryCoord / DataCoord Worker : QueryNode / DataNode / IndexNode Deps : etcd + S3/MinIO + Pulsar/Kafka
形态依赖适合别用在
Lite几乎无本地原型、CI多副本、高可用
StandaloneDocker + 磁盘中小流量、单机可接受宕机窗口要在线无损升集群（官方不支持热升级成 Distributed）
DistributedK8s + 对象存储 + MQ检索/写入要分开扩、要冗余只有几千条向量的玩具项目
Standalone 不能「在线升级」成 Distributed。业务真要过这道坎，需要 backup / VTS 迁数据，而不是改一个配置开关。选型时把 12 个月后的量级想清楚。

三种形态差的是运维拓扑，不是「会不会搜向量」。先用 Lite 验证召回，再用 Standalone 接流量，量上来再拆 Distributed。

三、分布式核心：存算分离与三类节点

2.x 把系统拆成无状态微服务：Proxy 入口转发；QueryNode 扛搜索；DataNode 写增量与持久化；IndexNode 离线建索引。元数据进 etcd，大文件进对象存储，近期变更走 Pulsar/Kafka。计算节点挂了可以拉起新的，数据还在对象存储里。

Client │ gRPC / REST ▼ Proxy ──分发──────────────┐ │ │ ├─ insert/upsert ──► DataNode ──► 对象存储（数据/索引文件） │ │ │ └─► MQ（流式增量） ├─ build index ──────► IndexNode ──► 写回对象存储 └─ search/query ─────► QueryNode ◄── 加载 segment + 过滤位图 │ ▼ TopK + 标量过滤结果
节点忙的时候在干什么独立扩容的意义
QueryNode加载 segment、ANN、过滤QPS 涨了只加检索节点
DataNode吃写入、刷盘、compaction导入高峰不必拖垮查询
IndexNodeHNSW/IVF 等重计算建索引是 CPU/GPU 爆的活，不该跟查询抢槽
搜索、插入、建索引被刻意设计成可并行的三条流水线。生产上常见事故是「导入一波新文档，查询延迟跟着炸」——那通常是这三条还绑在同一台机器上，Standalone 阶段就要开始监控，而不是等 Distributed 才发现。经验阈值：导入占满 CPU 超过数分钟、P99 搜索从几十毫秒跳到秒级，就是该把 IndexNode / DataNode 拆走的信号。

存算分离的直觉：节点是牲口，对象存储是粮仓。牲口可以换，粮仓不能丢。

四、索引、过滤与混合检索

Milvus 支持 FLAT、IVF、HNSW、PQ、磁盘 ANN、GPU 索引等。过滤不是「先 ANN 再扔掉不匹配的行」这么简单：常见路径是标量先生成 bitset，再交给 ANN 在搜索中跳过无效点（in-filtering），避免召回一堆权限不对的邻居。多向量字段（照片 + 声音 + 指纹）走混合搜索，再用 RRF（Reciprocal Rank Fusion，按排名倒数融合多路结果，不依赖不可比的原始分数）或加权分融合。

调参没有全局最优。IVF 的 nlist 决定桶数，nprobe 决定搜几个桶：nprobe 加倍通常换来召回上升和延迟上升，必须在黄金集上画曲线。HNSW 的 M / efConstruction 决定图密度，内存往往按「每向量数百字节」往上走，十亿级就要认真考虑 PQ 或 DiskANN。没有至少 50–100 条带标注的真实 query，这些旋钮都是噪声。

索引直觉代价
FLAT暴力比，准数据一大就扫不动
IVF先聚类再在少数桶里搜要调 nlist/nprobe
HNSW多层图跳走内存吃得狠，构建慢
PQ / DiskANN压缩或把图放到盘上精度和延迟要重新标定
按召回率标定 nprobe / ef，用固定黄金集回归；权限、租户、时间过滤做成标量字段，让 bitset 进 ANN，而不是在应用层二次过滤。
默认 HNSW 一把梭，也不测过滤后召回还剩多少。应用层再滤一遍，等于把已经很贵的 TopK 浪费在无权限文档上。

索引选的是「误差换速度」的汇率。没有黄金 query 集，这个汇率是拍脑袋。

五、RAG / Agent 场景怎么选

Agent 记忆和 RAG 都是「写入频率中等、查询要稳、要带元数据过滤」。起步 Lite 或 Standalone 足够；文档量过百万、要多副本或多租户，再上 Distributed。和 FAISS（库不是库）、Chroma（轻量嵌入库）、pgvector（事务友好）的分工：要事务和已有 Postgres 就 pgvector；要单机实验用 FAISS/Chroma；要检索当核心服务、还要独立扩 QueryNode，再上 Milvus。

热更新不要跟「升集群」绑在一起。影子 Collection + 别名切换，可以在 Standalone 上把新 embedding 模型灰度出去；失败切回旧别名，用户无感。Distributed 解决的是 QPS 和容量，不是版本纪律。没有黄金 query 集（至少几十到上百条带标注的真实问句），换索引参数等于蒙眼调 nprobe。

组件更合适的选择别指望它
pgvector已有 Postgres、要事务、百万级以下独立扩检索节点、百亿向量
Chroma / FAISS本地实验、嵌入式检索多租户 SLA、在线无损扩容
Milvus Standalone中小生产、同一套 API 试水热升级成集群
Milvus Distributed检索是核心 SLA、写入与查询要拆开几千条向量的玩具项目
选型决策 只要事务 + 已有 PG？ ──是──► pgvector │否 只要本地 demo / <10 万条？ ──是──► Chroma / Lite │否 检索是核心 SLA、要独立扩容？ ├─ 是 → Milvus Distributed（或云托管 Zilliz） └─ 否 → Standalone，把 backup 策略先写进 runbook
官方文档写明 Standalone 与集群功能对齐，但不能在线升集群。RAG 热更新（影子索引、别名切换）可以在 Collection / 别名层做，不必等 Distributed。先保证「新索引可切、可回滚」，再谈节点数。

向量库选型看的是「检索是不是你的核心 SLA」，不是 GitHub star。SLA 不在检索上，就别为 Distributed 付运维税。

六、上线前的运维清单

架构选对了仍可能被运维拖死。Standalone 要把磁盘、etcd、对象存储的备份写进 runbook；Distributed 要把 QueryNode 副本数、导入限流、索引构建窗口写成告警，而不是等用户先报「搜索变慢」。

检查项建议基线失败信号
黄金 query 集50–100 条真实问句 + 标注文档换索引只看延迟、不看召回
过滤字段租户 / 权限 / 时间做成标量应用层二次过滤导致有效 TopK 变空
导入窗口与查询高峰错开，或独立 DataNodeP99 从几十毫秒跳到秒级
备份与别名影子 Collection 可切回一次重建失败导致全站不可检索
容量按 12 个月向量条数量级选型Standalone 撑到十亿还没迁云
先用 Lite 验证召回，再用 Standalone 接小流量，量上来再拆 Distributed。每一步都带着同一套黄金集走。
生产第一天就上 K8s 全集群，或反过来把百万级检索长期绑在 MySQL 插件上。两头都贵。

运维清单比架构图更能决定 RAG 稳不稳：召回集、过滤字段、导入窗口、回滚别名，缺一项都会在流量上来后爆。

Q&A

为什么向量检索不能靠 MySQL 的普通索引？
B+ 树解决的是有序比较和等值查找。高维向量没有「按某一列排序就能剪枝」的性质，距离计算是全维参与的。暴力算 N 条还能凑合，到百万以上必须靠 ANN 图或倒排桶。MySQL 即使加了向量插件，也缺少独立的 Query/Data/Index 扩容和成熟的混合检索流水线，所以能做 demo，很难当检索 SLA 的主引擎。
Lite、Standalone、Distributed 怎么挑？
Lite 给开发和测试；Standalone 给单机可接受短暂不可用的中小生产；Distributed 给需要把检索、写入、建索引分开扩、并且要冗余的场景。三者查询语义尽量保持一致，但 Standalone 不能热升级成集群，迁过去要走备份/VTS。按 12 个月数据量和可用性要求选，不要按「听起来更高级」选。
QueryNode、DataNode、IndexNode 为什么要拆开？
三条流水线的资源曲线完全不同：查询要低延迟内存和 CPU，写入要吞吐和刷盘，建索引是突发重计算。绑在一起时，一次全量导入就会把查询尾延迟打穿。拆开之后可以只给 IndexNode 加 GPU、只给 QueryNode 加副本，这是云原生向量库相对「单进程搜库」的核心收益。
标量过滤应该放在 ANN 前还是后？
生产上更常见的是把过滤条件变成 bitset，在 ANN 过程中跳过无效点，而不是先取 TopK 再在应用层丢掉。后过滤会让有效召回远小于 K，权限场景尤其明显。Milvus 的 filter search 就是把「像」和「允许看」放进同一次检索，避免浪费已经很贵的图遍历。
HNSW 是不是默认最优？
内存够、数据中等、要高召回时 HNSW 很强，但构建慢、内存大。超大规模或成本敏感要用 IVF、PQ、DiskANN 或 GPU 索引，并用黄金集标定。没有召回率曲线就选 HNSW，等于把容量规划交给默认参数。索引是汇率，不是信仰。
RAG 热更新要不要上 Distributed？
不一定。热更新首先是版本和别名：旁路建新 Collection，校验后再切别名，失败回滚。这在 Standalone 也能做。Distributed 解决的是流量和容量，不是「能不能蓝绿」。先把增量 embedding、缓存失效、别名切换做对，再根据 QPS 和数据量决定要不要拆节点。
etcd、对象存储、消息队列各自存什么？
etcd 存小而关键的元数据：Collection 定义、节点拓扑、租约。对象存储（S3/MinIO）存 segment 数据和索引文件，节点挂了可以换新节点重新加载。Pulsar/Kafka 这类 log broker 扛近期增量，让 DataNode 和 QueryNode 跟上写入。三者缺一，要么丢拓扑，要么丢数据，要么丢「刚写入还没刷盘」的那一截。
混合检索的 RRF 和加权融合怎么选？
多路分数不可比时用 RRF，只看排名倒数，少调参。各路分数经过校准、你知道哪路更重要时再用加权。照片+声音+指纹这类多向量字段，先保证每路自己的召回，再融合；不要把三路向量拼成一个超长向量指望一次 ANN 搞定。黄金集要按「融合后」标注，而不是只评单路。
什么时候该从 Standalone 迁走？
出现这几类信号就该规划 Distributed 或托管：导入和查询互相踩踏、单机内存放不下 HNSW、需要多副本扛磁盘故障、租户隔离要独立扩 QueryNode。迁之前先做 backup/VTS 演练，因为没有在线升级开关。数据还在十万级、单机 P99 稳定时，迁集群只是提前交运维税。
