G14 · RAG 处理 Word 文档

Word Document Processing — 结构保留 / 表格按行切分 / OCR关联 / 语义Chunk切分

Word 文档不是"带格式的文字"，而是"半结构化的知识容器"。标题层级表达信息从属关系，表格承载结构化数据，图片传达文字无法描述的视觉信息。简单转纯文本丢掉的不是格式，而是语义关系——这才是 RAG 系统检索质量崩塌的根源。

一、Word 文档的特殊性：为什么不能简单转文本

在企业 RAG 系统中，Word 文档（.docx）是最常见的知识载体之一。与 PDF 相比，Word 文档有一个"隐藏优势"——它的底层是 XML 结构化存储（Office Open XML 格式），包含丰富的语义标注信息。但大多数 RAG 管道在第一步就把这些结构信息全部丢弃了。

Word 文档包含的六大结构化元素

元素类型语义价值丢失后果典型场景
标题层级 (H1-H6)信息从属关系无法定位"某章节下的某规则"制度文件、操作手册
表格结构化数据关系行列关系散乱，数据无法精确匹配报价单、参数表、流程图
图片视觉信息（流程图、截图）图片内容完全丢失操作截图、架构图
页眉页脚文档元数据（版本、密级）丢失文档来源和版本信息公司制度文件、合同
批注/修订审阅意见和变更历史无法区分最终版本和草稿合同审批、方案评审
样式标记段落角色（正文/注释/引用）无法区分正文和辅助信息学术论文、技术文档

实测数据：某银行将 200 份内部制度 Word 文档直接转纯文本后入库，用户提问"差旅报销中一线城市住宿标准是多少"时，RAG 系统召回的 Top-5 结果中有 3 条来自错误的章节——因为"差旅报销→住宿标准→一线城市"这个层级路径在纯文本中已不可区分，系统只能靠关键词模糊匹配。

三大核心问题

  1. 结构保留：如何在不破坏语义关系的前提下提取文档内容？标题层级、表格行列、图文对应关系都需要保留。
  2. 非正文内容处理：页眉页脚、批注、修订痕迹中哪些该保留、哪些该丢弃？处理不当会引入噪声或丢失关键元数据。
  3. 语义完整性保障：切分为 chunk 后，每个 chunk 是否仍然是一个语义完整的知识单元？跨段落引用的信息能否被正确关联？

核心认知：Word 文档处理的目标不是"提取文字"，而是"还原知识单元"。一个标题路径（如"差旅报销→住宿标准→一线城市"）加上其下属内容（表格或段落），构成一个完整的、可独立回答问题的知识单元。这就是 RAG chunk 的理想形态。

二、六步解决方案：从 Word 到可检索知识单元

以下是一套经过生产验证的 Word 文档处理流水线，覆盖从文档解析到检索优化的完整链路。每一步都针对前述三大问题中的一个或多个。

Step 1：文档解析与结构保留

Word 文档的底层是 Office Open XML 格式，每个段落都有明确的样式标记（w:pStyle），可以直接读取标题层级。推荐使用 python-docx 或 Unstructured 库进行解析，而非简单的文本提取。

关键操作是构建语义路径（Semantic Path）：从根标题到当前段落的完整路径。例如"差旅报销→住宿标准→一线城市→600元/天"。这个路径会被附加到每个 chunk 的元数据中，使检索时能精确定位信息来源。

生产数据：在 500 份企业制度文档的测试中，保留语义路径的检索方案 Recall@5 达到 87.3%，而纯文本方案的 Recall@5 仅为 62.1%。差距最大的场景是"跨章节同名概念"——多个章节都提到"标准"，纯文本方案无法区分是哪个章节的标准。

Step 2：表格处理——按行转结构化文本

表格是 Word 文档中信息密度最高的元素，也是最容易被错误处理的元素。常见的错误做法是将整个表格转成一个长字符串或按列拼接，导致行列对应关系丢失。

正确做法是将每行视为独立语义单元：表头作为键（Key），每行数据作为值（Value），组合成结构化的 Key-Value 文本。这样每一行都可以被独立检索和回答问题。

处理方式示例输出检索效果问题
整表拼接"城市 标准 北京 600 上海 600 广州 500"差无法区分哪个城市对应哪个标准
按列拼接"城市:北京,上海,广州 | 标准:600,600,500"中索引对应关系靠推理，容易出错
按行转 KV"一线城市住宿标准: 北京=600元/天, 上海=600元/天"优每行独立可检索，语义完整

表格处理的核心原则：一个表格行回答一个问题。用户问"北京住宿标准是多少"时，系统应该能直接召回"北京=600元/天"这一行，而不是把整个表格都返回。按行切分使得每个 chunk 精准对应一个可回答的知识点。

表格行级切块的完整原则（行原子性、KV 富化、业务分组、父子分层）见 G15 · 跨页表格处理全流程。

Step 3：图片 OCR 提取并关联原段落

Word 文档中的图片（操作截图、流程图、架构图）通常包含关键信息。处理策略分两层：

  • OCR 提取：使用 Tesseract 或 PaddleOCR 从图片中提取文字内容
  • 段落关联：将 OCR 结果与图片前后的文字段落关联，形成完整的上下文。图片的 alt text 和前后段落的标题路径也作为关联元数据

如果图片是纯图形（如流程图无文字），则使用多模态模型（如 GPT-4o）生成图片描述，并将描述文本作为一个 chunk 入库。实测中，OCR 关联处理使涉及图片内容的问答准确率从 12%（完全不处理）提升到 71%。

Step 4：页眉页脚与批注过滤

页眉页脚和批注中混杂着有价值的元数据和无意义的噪声。处理策略需要区分对待：

元素类型保留策略处理方式示例
页眉-文档标题保留为全局元数据附加到每个 chunk 的 source 字段"XX公司差旅管理办法 V2.3"
页眉-密级标识保留为安全元数据附加到每个 chunk 的 security_level 字段"内部-机密"
页脚-页码丢弃过滤"第 3 页 / 共 15 页"
批注-审阅意见仅保留最终修订版本接受所有修订，删除批注文本保留"标准修改为600"的最终文本
修订痕迹接受最终版本使用 accept_all_revisions() 处理删除红色删除线标记

批注和修订的处理原则："只保留最终真相"。一份经过 5 轮审批的合同可能包含 200 条批注和修订痕迹，但最终用户只需要知道最终条款是什么。在 RAG 场景中，保留中间版本反而会引入噪声——系统可能召回已经被否决的旧条款来回答问题。

三、语义 Chunk 切分策略

语义切分 vs 固定长度切分

通用切分原则——按语义边界而非 token 数切割、内容过长时段落兜底、chunk 大小的精度/上下文权衡——已在 G08 · RAG 文档切割技术方案中系统阐述。Word 文档自带可靠的标题层级，是结构化切分的理想载体，此处只记录 Word 特有的实现：

  1. 以标题层级为主边界：每个 H2/H3 标题下的内容作为一个或若干个 chunk。一个 H3 下的所有内容通常构成一个完整的知识点。
  2. 段落为次边界：如果一个标题下的内容过长（超过 800 token），则在段落边界处进一步切分，而非在句子中间截断。
  3. 表格行独立成 chunk：如 Step 2 所述，每行 KV 结构独立成 chunk，不与相邻文本合并。
  4. 补充上下文路径：每个 chunk 的开头自动加上其语义路径前缀，如"差旅费管理办法 > 住宿标准 > 一线城市"。
切分策略平均 chunk 大小Recall@5MRR适用场景
固定 256 token256 tokens58.2%0.41简单 FAQ 文档
固定 512 token + 10% overlap512 tokens64.7%0.48通用文本
段落边界切分~380 tokens72.1%0.56叙事性文档
标题层级语义切分~450 tokens82.6%0.67结构化制度文档
语义切分 + metadata 补充~450 tokens87.3%0.73企业知识库（推荐）

Metadata 补充策略

每个 chunk 除了正文内容外，还需要附加以下元数据字段：

Metadata 字段内容示例检索用途
semantic_path"差旅管理>住宿标准>一线城市"精确匹配 + 层级过滤
doc_title"XX公司差旅费管理办法"来源追溯
doc_version"V2.3"版本过滤
section_heading"一线城市住宿标准"上下文补全
chunk_type"text" / "table_row" / "image_desc"类型过滤
security_level"internal" / "public"权限控制

Metadata 的真正价值在于"缩小检索范围"。当用户问"一线城市住宿标准"时，系统可以先用 semantic_path 过滤出"住宿标准"相关的 chunk（从 2000 个 chunk 缩小到 50 个），再在这 50 个 chunk 中做向量检索。这种"先过滤后检索"的两阶段策略比直接在 2000 个 chunk 中检索的准确率高 15-20 个百分点。

四、检索优化：多路召回与重排序

Word 文档处理完成后，检索阶段需要针对 Word 文档的特点做专项优化。核心挑战是：Word 文档中既有精确数据（如"600元/天"），又有描述性文本（如"员工出差应优先选择经济型交通工具"），单一检索方式难以同时覆盖两种查询模式。

BM25 + 向量检索 多路召回

BM25 关键词检索擅长精确匹配——用户搜"600"就能命中包含"600"的 chunk。向量检索擅长语义匹配——用户搜"住宿费用上限"能命中"住宿标准"相关的 chunk，即使没有出现"费用上限"这四个字。两路并行召回，取并集后交给重排序器。

┌──────────────────────────────────────────────────────────────────┐ │ 多路召回 + 重排序检索流程 │ ├──────────────────────────────────────────────────────────────────┤ │ │ │ 用户查询: "一线城市住宿标准是多少" │ │ │ │ │ ├──▶ [Metadata 过滤] semantic_path LIKE '%住宿标准%' │ │ │ 从 2000 chunks → 50 chunks │ │ │ │ │ ├──▶ [BM25 关键词检索] │ │ │ 关键词: "一线城市" + "住宿" + "标准" │ │ │ Top-20 结果 (精确匹配优先) │ │ │ │ │ ├──▶ [向量语义检索] │ │ │ Embedding("一线城市住宿标准是多少") │ │ │ Top-20 结果 (语义相似优先) │ │ │ │ │ └──▶ [结果合并] 并集 ~30-35 chunks │ │ │ │ │ ▼ │ │ [Cross-Encoder 重排序] │ │ 对每个 (query, chunk) 对计算精确相关性分数 │ │ Top-5 送入 LLM 生成答案 │ │ │ │ 最终召回: │ │ #1 "差旅管理>住宿标准>一线城市: 北京600元,上海600元,广州500元" │ │ #2 "差旅管理>住宿标准>一线城市: 超标部分由个人承担" │ │ #3 "差旅管理>住宿标准>说明: 标准含早餐费用" │ │ │ └──────────────────────────────────────────────────────────────────┘

Cross-Encoder 重排序

多路召回返回的 30-35 个候选 chunk 质量参差不齐——BM25 可能因为关键词匹配召回了语义不相关的结果，向量检索可能召回了语义相似但不精确的结果。Cross-Encoder 重排序器（如 bge-reranker-v2）对每个 (query, chunk) 对做精细的相关性打分，然后按分数降序排列，取 Top-5 送入 LLM。

实测效果：在 200 份企业制度文档的测试集上，BM25 单独的 Recall@5 为 68.2%，向量检索单独为 74.5%，两路召回合并后为 81.3%，加上 Cross-Encoder 重排序后达到 87.3%。每一步提升都是显著的，尤其 Cross-Encoder 贡献了 6 个百分点的提升。

检索方案Recall@5MRR延迟 P50延迟 P99
BM25 单独68.2%0.5215ms45ms
向量检索单独74.5%0.5835ms120ms
BM25 + 向量 双路召回81.3%0.6450ms150ms
双路召回 + Cross-Encoder87.3%0.73180ms450ms

检索优化的关键洞察：不同检索方式解决不同类型的查询。"北京住宿标准多少钱"是精确查询（BM25 强项），"出差住什么档次的酒店"是语义查询（向量检索强项），"住宿超标怎么处理"是跨章节查询（Metadata 路径过滤强项）。多路召回不是"冗余"，而是"互补"。

生产部署的关键指标

推荐的生产实践：
  • 解析阶段保留完整标题路径作为 metadata
  • 表格按行转 KV 结构，每行独立成 chunk
  • 图片做 OCR + 段落关联，无法 OCR 的用多模态模型描述
  • 接受所有修订后入库，丢弃中间版本
  • 语义切分 + metadata 补充，chunk 大小 300-600 token
  • BM25 + 向量双路召回 + Cross-Encoder 重排序
  • 每个 chunk 附加 security_level 做权限控制
常见的反模式：
  • Word 转纯文本后直接入向量库
  • 整个表格作为一个 chunk 存储
  • 忽略图片内容，只处理文字
  • 保留批注和修订痕迹导致新旧信息混淆
  • 固定 512 token 切分，不考虑语义边界
  • 只用向量检索，不做关键词检索
  • 忽略文档版本，新旧文档混合索引

六、核心结论：将半结构化文档还原为可检索知识单元

整套方案的核心思想可以浓缩为一句话：Word 文档处理的本质不是"提取文字"，而是"还原知识单元"。

常见问题

Word 文档和 PDF 的处理策略有什么本质区别？
核心区别在于结构信息的可获得性。Word 文档底层是 XML 格式，标题层级、表格边界、样式标记都是显式标注的，可以直接程序化读取。PDF 本质上是"画布"——文字按照坐标位置排列，标题层级和表格结构需要推断（通过字体大小、位置等启发式规则）。因此 Word 文档的结构保留率可以接近 100%，而 PDF 通常在 80-90%。如果条件允许，优先获取 Word 源文件而非 PDF。
嵌套表格和合并单元格怎么处理？
嵌套表格需要递归处理——外层表格的每个单元格如果包含子表格，则先处理子表格再嵌入。合并单元格的处理策略是"展开还原"——将合并单元格的内容复制到所有被合并的位置。例如一个"住宿标准"单元格横跨 3 行，处理后每行都独立包含"住宿标准"这个信息。实现上 python-docx 的 cell.merged_cells 属性可以检测合并关系，处理时需要小心边界情况。
一份文档有多个版本时怎么处理？是保留所有版本还是只保留最新版？
推荐策略是"最新版为主 + 历史版可查"。具体实现：每个 chunk 的 metadata 中加入 doc_version 和 is_latest 字段。默认检索时只召回 is_latest=true 的结果（用户看到最新内容），但支持管理员通过 metadata 过滤查询历史版本（如"V2.0 中的住宿标准是什么"）。这需要在索引时同时保留所有版本，但通过 metadata 过滤控制默认行为。
如何处理 Word 文档中的公式和特殊符号？
Word 中的公式使用 OMML（Office Math Markup Language）编码，可以通过 python-docx 或 Mathpix API 转换为 LaTeX 格式。转换后的 LaTeX 文本可以直接作为 chunk 内容入库。特殊符号（如化学式、数学符号）建议使用 Unicode 标准化处理。如果公式是图片形式嵌入的，则走 OCR 路径。实测中 Mathpix 的公式识别准确率达 97%，优于 Tesseract 的 82%。
语义切分时如果一个 H3 下的内容太短（不到 100 token），要和相邻章节合并吗？
不建议合并。短 chunk 虽然信息量少，但语义完整——它精确对应一个知识点。合并会破坏语义边界，导致检索精度下降。正确做法是保持短 chunk 独立，通过 metadata 中的 semantic_path 建立上下文关联。检索时如果召回了短 chunk，可以通过其 semantic_path 自动扩展召回同一路径下的相邻 chunk（类似 Parent Document Retriever 策略）。这样既保持了检索精度，又补全了上下文。
大规模处理时，增量更新怎么做？新文档进来需要全量重新处理吗？
不需要全量重新处理。增量更新策略：① 新文档走完整六步流水线，新生成的 chunk 带上 doc_id + doc_version 入索引；② 文档更新时，先按 doc_id 删除旧 chunk，再处理新版本文档入库（delete-then-insert 模式）；③ 对于小范围修订（如修改一个表格数值），可以精确定位到受影响的 chunk 做局部更新。建议维护一份文档清单（doc_id, version, status），每次更新时对比差异，只处理变化的文档。500 份文档库中，通常每次更新只涉及 5-10 份文档。
表格特别大（超过 50 行）时，按行切分会产生太多 chunk 吗？
50 行的表格按行切分产生 50 个 chunk，看起来很多，但实际上这不是问题。每个 chunk 都很小（通常 20-50 token），在检索时向量库处理小 chunk 的效率反而更高。真正的优化点在于"分组索引"——将逻辑相关的行（如同一部门的数据行）用 group_id 关联，检索时召回一行后自动扩展同组的其他行。如果表格确实巨大（500+ 行），可以考虑在表格级别创建一个摘要 chunk（"本表格包含 XX 部门的 500 条产品报价记录"），作为导航入口。
总结：Word 文档 RAG 处理的核心在于将半结构化文档还原为可检索的知识单元。六步流水线——文档解析保留结构路径、表格按行转 KV、图片 OCR 关联段落、页眉批注智能过滤、语义边界切分、BM25 + 向量 + Cross-Encoder 多路召回重排序——协同工作，将端到端问答准确率从纯文本方案的 54.2% 提升至 83.7%。记住：80% 的信息损失发生在文档解析阶段，这是 ROI 最高的优化环节。
