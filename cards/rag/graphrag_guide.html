G21 · GraphRAG

知识图谱增强的检索生成 — 解决向量 RAG 的"死穴"：全局总结 + 多跳推理

一、为什么需要 GraphRAG？

向量 RAG 的致命盲区：它把文档切成独立的语义片段，无法理解实体之间的关系网络。问"LangChain 和 LlamaIndex 哪个更适合企业级？"时，向量检索只能找到分别提到两者的文档片段，无法推理它们的异同。

向量 RAG 的三大局限

问题类型向量 RAG 表现根本原因
全局总结（"项目涉及哪些技术？"）差答案分散在多个 chunk，单次检索无法覆盖全局
多跳推理（"A 的老板的部门做什么项目？"）差需要跨文档连接实体关系链
关系查询（"谁和谁合作过？"）中等关系信息在 embedding 中被压缩/丢失
精确事实（"X 的成立时间？"）好直接检索包含答案的 chunk 即可

多跳查询窘境：O(n) 补召 vs O(1) 子图检索

普通 RAG 处理多跳查询: 用户查询: "拍视频强 + 续航好 + 口碑稳的手机" │ ▼ 独立召回三个条件的相关文本块 │ ▼ 无法确认不同条件是否指向同一实体 │ ▼ 需要多次补召和人工比对 │ ▼ 延迟和 Token 消耗指数级增长 O(n) GraphRAG 处理同一查询: 预构建实体关系图: 手机 A ──→ 影像旗舰 + 5500mAh + 4.8 分好评 │ ▼ 一次性子图检索 → 明确关联 → 复杂度恒定 O(1) （避免多次补召带来的噪声累积）
维度普通 RAG（多跳查询）GraphRAG（多跳查询）
检索方式各条件独立召回、结果分散，需多次补召和人工比对一次性子图检索，获取完整关系链
实体确认无法确认不同条件是否指向同一实体，答案可能张冠李戴关系边明确标注归属，答案准确无歧义
复杂度O(n)，延迟和 Token 消耗随跳数增长O(1)，复杂度恒定，成本可控

GraphRAG 的核心思路：用知识图谱（Knowledge Graph）以结构化的方式表示实体和关系，天然适合多跳推理和全局理解。Microsoft Research 2024 年发布的 GraphRAG 论文引爆了这个方向。

GraphRAG 不是 Vector RAG 的替代品，而是互补。最佳实践是两者结合：向量检索处理语义查询（"什么是 X？"），图检索处理关系和全局查询（"X 和 Y 什么关系？""全局有哪些？"）。

二、实体关系抽取：从文本到图

实体抽取是 GraphRAG 最贵的一步：用 LLM 从每个 chunk 中提取实体和关系，每 1000 个 chunk 约需 $5-20（GPT-4o）。抽取质量直接决定后续所有环节的效果。

LLM 驱动的知识抽取

传统方法用 NLP pipeline（NER + 关系抽取），现代方法直接用 LLM 做端到端的抽取。关键是设计清晰的 prompt，定义实体类型（人物、组织、技术、产品、概念）和关系类型（开发了、属于、使用、合作、基于），要求 LLM 输出结构化的 JSON。

抽取准确率基准与图融合

知识图谱构建流水线（离线阶段）: 原始文档集（PDF / HTML / 数据库） │ ▼ Step 1: 实体抽取（Entity Extraction） LLM 识别: 人名 / 机构 / 概念 / 数值指标 输出: [{name: "手机A", type: "Product"}, {name: "5500mAh", type: "Spec"}] 准确率: ~92%（GPT-4 级别） │ ▼ Step 2: 关系抽取（Relation Extraction） "手机A" ──[HAS_FEATURE]──→ "影像旗舰" "手机A" ──[HAS_BATTERY]──→ "5500mAh" 准确率: ~85% │ ▼ Step 3: 图融合（Graph Fusion） 多篇文档的抽取结果合并: 实体去重 + 关系合并 冲突消解: 同一实体不同描述取最新 / 置信度最高 │ ▼ 统一知识图谱 → 写入图数据库（Neo4j / NebulaGraph）

LLM 驱动的全自动抽取流程可达 80-90% 自动化，剩余 10-20% 需要人工校验（特别是领域专业术语和歧义实体）。关系抽取准确率（~85%）低于实体抽取（~92%），关系边是图质量问题的主要来源，应作为校验重点。

抽取策略对比

策略方法适用场景优缺点
逐 chunk 抽取每个 chunk 独立送 LLM通用，最简单实现简单，但可能遗漏跨段落关系
上下文增强给 LLM 前后文辅助需要跨段落实体消歧效果更好，但增加 token 消耗
多轮抽取先抽实体，再抽关系复杂文档更精确，但 LLM 调用次数翻倍
Schema-guided预定义实体/关系类型领域特定（医学/法律）抽取一致性高，但灵活性低

实体消歧：最容易出错的环节

同一实体在不同 chunk 中可能有不同表述："GPT-4" / "GPT4" / "gpt-4o" / "OpenAI 的最新模型"。如果不合并，图中会出现多个重复节点，关系链断裂。解决方法：基于字符串相似度（Levenshtein）、embedding 相似度、或用 LLM 判断是否同一实体，选择最常见/最完整的名称作为规范名。

  • 实体消歧是 GraphRAG 中最容易出错的环节，直接影响图的质量
  • 开源替代：Llama 3 70B / Qwen 72B 可本地部署做抽取，成本远低于 GPT-4o
  • 成本优化：用轻量模型（GPT-4o-mini）做初步抽取，只对困难 case 用强模型

三、Microsoft GraphRAG 核心创新

Microsoft GraphRAG 的核心创新不是"用图做检索"，而是"层次化社区摘要"——用 Leiden 算法将图划分为社区，再用 LLM 为每个社区生成摘要，使得全局性问题可以通过遍历摘要来回答。

整体流程

Microsoft GraphRAG Pipeline: 1. Source Documents → Text Chunks（300-600 tokens） 2. Text Chunks → Entity/Relationship Extraction（LLM） 3. Entities + Relationships → Knowledge Graph 4. Graph → Community Detection（Leiden 算法） 5. Communities → Community Summaries（LLM） 6. Query → Local Search / Global Search 核心创新: Community Detection + Hierarchical Summarization

社区检测（Leiden 算法）

Leiden 算法将知识图谱划分为多个"社区"——紧密相连的实体归为一组（类似主题聚类）。与 Louvain 算法相比，Leiden 保证每个社区内部高度连通，质量更优。层次化检测产生多层社区结构：

  • Level 0：最细粒度（3-5 个实体一组）
  • Level 1：中等粒度（10-20 个实体）
  • Level 2：最粗粒度（整个主题域）

社区摘要：将图结构凝聚为叙述

对每个社区用 LLM 生成摘要，描述该群组的核心主题和关键信息。摘要包含群组标题、2-3 段摘要、3-5 个关键发现。社区摘要的价值：将分散的实体关系凝聚为可理解的叙述，支持全局查询（"这个领域的主要参与者有哪些？"），多层摘要支持不同粒度的回答。

社区摘要让"全景式"问题变得可回答：传统向量 RAG 需要检索所有相关 chunk 才能回答全局问题，GraphRAG 只需遍历数百个社区摘要（每个摘要已经概括了一个主题），效率提升数十倍。
  • Leiden 算法比 Louvain 更优：保证每个社区内部高度连通
  • 社区摘要的成本：每个社区一次 LLM 调用，数百个社区可能需要 $10-50
  • 层次化结构让系统能在不同 zoom level 回答问题

四、Local Search vs Global Search

两种查询模式解决不同类型的问题：Local Search 从特定实体出发遍历邻居（类似传统图查询），Global Search 遍历所有社区摘要做 Map-Reduce（GraphRAG 最大创新）。

查询模式对比

模式适用问题检索方式示例成本
Local Search关于特定实体/关系的具体问题从 query 实体出发，遍历 1-2 跳邻居"LangChain 用了哪些组件？"低
Global Search需要全局概览的总结性问题遍历所有社区摘要，Map-Reduce"这个代码库的主要架构是什么？"高

Local Search：从起点遍历邻居

流程：从 query 中识别实体 → 在图中找到对应节点 → 遍历 1-2 跳邻居收集上下文 → 可选结合向量检索补充 → 送 LLM 生成。适合具体问题："LangChain 支持哪些向量数据库？""张三和李四是什么关系？"

Global Search：Map-Reduce 遍历社区

流程：Map 阶段——每个社区摘要独立回答问题，过滤无关社区；Reduce 阶段——合并所有有关社区的回答，综合生成全面连贯的总结。适合全局问题："这个项目涉及哪些技术栈？""有哪些主要的参与方？"

  • Global Search 是 GraphRAG 最大创新：利用社区摘要回答"全景式"问题
  • Global Search 成本更高（遍历所有社区），但能回答向量 RAG 完全无法处理的问题
  • 实际应用：通常先做意图识别——具体问题走 Local，总结性问题走 Global

五、图构建与存储

图存储的选择决定了系统的扩展性：NetworkX 适合原型和小规模（内存图），Neo4j 适合生产环境（持久化、索引、Cypher 查询），Nebula Graph 适合超大规模分布式场景。

存储方案对比

工具类型特点适用场景
NetworkXPython 图计算库轻量、内存图、API 简单原型/小规模（<10K 节点）
Neo4j图数据库持久化、索引、Cypher 查询语言生产环境（最成熟）
Nebula Graph分布式图数据库高性能、可扩展、开源超大规模（亿级节点）
MemGraph内存图数据库极快、兼容 Cypher低延迟场景

Neo4j + LangChain 集成

Neo4j 是最成熟的图数据库，配合 LangChain 的 GraphCypherQAChain，可以实现"自然语言 → Cypher 查询 → 结果 → 自然语言回答"的完整链路。LLM 自动生成 Cypher 查询语句，准确率约 70-85%，复杂查询可能出错，需要 fallback 机制。

图构建 Pipeline

端到端流程：文档加载（PDF/HTML/Markdown → 纯文本）→ 文本分块（300-600 tokens）→ 实体抽取（每个 chunk → LLM）→ 实体消歧（合并同义实体）→ 图构建（entities 为节点，relationships 为边）→ 社区检测（Leiden 算法）→ 社区摘要（LLM 生成）→ 索引存储（图数据库 + 向量索引）。

图构建质量：四维评估

图构建质量直接决定查询效果——错误的关系比没有关系更危险，不要跳过质量校验。建议上线前做质量门禁（Quality Gate），不达标则不上线：

评估维度评估方法生产标准
实体覆盖率随机抽样 500 段文本，统计被正确抽取的实体占实际存在实体的比例≥ 90%
关系准确率人工标注 200 条关系作为金标准，计算抽取关系的 Precision/Recall/F1F1 ≥ 0.82
图连通性检查最大连通分量占比；占比 <60% 说明图谱碎片化严重，需加强跨文档实体链接≥ 60%
端到端查询验证构建 50 条标准多跳查询测试集，对比 GraphRAG 与人工专家的回答一致率≥ 75%

失效场景：GraphRAG 何时不灵

  • 简单事实查询——"X 的价格是多少"单条文档即可回答，图遍历反而增加延迟（图遍历 120ms vs 直接检索 30ms）
  • 高度动态数据——如实时股票行情，图谱构建速度跟不上数据更新频率，关系边频繁失效
  • 非结构化创意内容——诗歌、小说等文学文本，实体间关系模糊且主观，难以构建高质量图谱
  • 数据量极小——文档少于 1,000 篇时，图构建的固定成本无法被查询量摊薄，ROI 为负

核心判断标准：如果查询通常只涉及单一文档且不需要跨文档推理，普通 RAG 性价比更高。

增量更新是 GraphRAG 的最大挑战：新文档加入时需要重新抽取、消歧，可能影响社区结构，需要全量或半全量重建。向量 RAG 只需对新 chunk 做 embedding 即可增量更新。
  • 图构建成本主要在 LLM 调用：1000 个 chunk × $0.01/chunk = $10，对比向量 RAG 仅 $1-5
  • 建议起步路线：NetworkX 原型 → 验证价值 → Neo4j 生产化
  • Microsoft graphrag 库适合快速验证，但定制性有限

六、GraphRAG vs Vector RAG：如何选择？

不是"哪个更好"的问题，而是"什么场景用哪个"。80% 的查询是简单事实问答时，Vector RAG 就够了；只有关系/全局查询占比 >20% 时，GraphRAG 的投入才值得。

何时选择 GraphRAG？

  • 文档有丰富的实体关系（人物/组织/项目/技术之间有明确关系）
  • 用户常问全局性问题（"涉及哪些""总共有多少""主要有哪些"）
  • 需要多跳推理（"A 的合作方 B 使用了什么技术？"）
  • 知识更新不频繁（图重建成本高，不适合实时更新场景）

混合架构设计

推荐架构：先做意图路由——具体问题走 Vector RAG（快、便宜），关系查询走 Graph Local Search，全局总结走 Graph Global Search，混合问题两路结果合并。判断是否需要 GraphRAG 的渐进策略：先跑 Vector RAG，分析 bad case 中有多少是关系/全局问题，如果 >20% 就值得引入 GraphRAG。

向量检索与图遍历有两种互补的结合方式：① 向量预筛选 + 图遍历——先用向量检索找到"入口节点"（最相关的实体），再从入口节点出发沿关系边扩展；② 图遍历 + 向量精排——图遍历得到候选集后再用向量相似度精排。生产验证（生物医药场景）：向量预筛选将图遍历的起始节点从全量 50 万个缩减至 50 个，遍历时间从 2s 降至 120ms。核心洞见：向量检索擅长"找到起点"，图遍历擅长"沿路径发现"。注意不要全量图遍历——应从向量检索的 Top 节点出发，控制遍历深度。

三级路由：生产环境 Query Router

混合路由策略: 用户查询 → Query Router → 智能分流 │ ├── 简单查询 → ElasticSearch（毫秒级响应） │ 例: "iPhone 16 价格" │ ├── 单跳语义 → 普通 RAG（平衡精度与成本） │ 例: "RAG 是什么" │ └── 多跳推理 → GraphRAG（解决复杂关联） 例: "A 基因的突变影响哪些药物的代谢途径" 三种方案共存互补，按查询复杂度动态选择最优方案

  • 盲目上 GraphRAG（成本高、复杂度高）
  • 80%+ 简单事实查询也用 GraphRAG（杀鸡用牛刀）
  • 忽略实体消歧（重复节点导致关系链断裂）

  • 渐进策略：先跑 Vector RAG，分析 bad case 中有多少是关系/全局问题，再决定是否引入
  • 混合架构是最佳实践：Vector RAG + GraphRAG 通过意图路由分流

七、多跳推理与 TCO 成本分析

关键不是比较构建成本，而是计算总拥有成本（TCO）：GraphRAG 的图构建是一次性投入，但每次查询都是 O(1)；传统 RAG 每次多跳查询都需要 O(n) 次补召。多跳密集场景下，GraphRAG 的边际成本优势显著。

方案总成本公式多跳场景表现
GraphRAG图构建成本（一次性）+ 单次查询成本 × 查询量O(1) 恒定
传统 RAG（单次简单查询成本 + 补召成本 × 补召次数）× 查询量O(n) 指数增长
关键洞察：当系统存在大量多跳查询时，GraphRAG 的边际成本优势显著。图构建是一次性投入，但每次查询都是 O(1)，而传统 RAG 每次多跳查询都需要 O(n) 次补召。在生物医药等需要跨文献追溯关系链的场景，GraphRAG 的 ROI 远超传统 RAG。

生产环境 TCO 测算实例

以日均 10,000 次多跳查询为例：传统 RAG 每次查询平均需要 3.2 次补召，每次补召消耗 ~2,000 tokens，月 Token 成本约 $1,920；GraphRAG 图构建一次性 $2,400，之后每次查询仅需单次图遍历（~500 tokens），月 Token 成本约 $150。第 2 个月起 GraphRAG 总成本即低于传统 RAG。

图构建/维护成本—$2,400 + $200/月一次性 + 增量更新

八、生产案例

案例一：某生物医药知识库

背景：从 Naive RAG 升级为 GraphRAG，处理跨文献关系链查询（如"A 基因的突变会影响哪些药物的代谢途径？"）。

效果：多跳推理问题答案准确率从 22% 提升至 71%。Naive RAG 只能检索到包含"A 基因"的文档，无法找到"A 基因 → 蛋白质 B → 药物 C 代谢酶"这种跨文档的关系链。GraphRAG 通过图遍历直接走这条路径，检索命中率 95%。

构建成本：知识图谱构建（实体抽取 + 关系抽取）耗时 48 小时（用 GPT-4 处理 10 万篇论文），API 成本 $2,400。构建完成后查询延迟仅 120ms（图遍历 vs 向量检索的 800ms）。

ROI：图谱构建一次性投入 $2,400，每月节省人工检索时间 200 小时（研究员不再需要手动跨文献追溯关系链）。

案例二：某券商合规审计知识图谱

背景：头部券商合规部门需要对 5 万份监管文件（法规、处罚案例、内部制度）进行多跳关联查询，典型问题如"某基金经理的关联方中，哪些曾受到证监会处罚？处罚涉及的基金产品目前是否仍在销售？"——涉及 4-5 跳的关系链追溯。

技术方案：使用 Neo4j 存储合规知识图谱（32 万实体 + 89 万关系边），LLM 自动抽取准确率 88%，人工校验团队（3 名合规专家）耗时 2 周完成质量审核。在线查询采用向量预筛选 + 图遍历的混合架构，入口节点定位 <50ms，图遍历平均 3-4 跳。

效果数据：

  • 多跳合规查询准确率：从 Naive RAG 的 18% 提升至 76%（提升 4.2 倍）
  • 平均查询延迟：95ms（对比传统 RAG 的 3,200ms，提速 33 倍）
  • 合规审查效率：单次关联方审查从 4 小时缩短至 15 分钟
  • 月均节省合规人力：320 工时（相当于 2 名全职合规专员的工作量）
关键数据对比：该券商合规图谱上线 6 个月后，累计发现 47 条此前人工审查遗漏的关联方风险链路，直接避免了 3 笔潜在违规投资，涉及金额超过 ¥2.8 亿。
核心价值：GraphRAG 解决向量检索的"关系盲区"——向量检索只能找到"提到相同内容"的文档，而图遍历能发现"A 影响 B，B 关联 C"这种跨文档的推理链。多跳推理场景下准确率提升 3 倍以上。

Q&A

GraphRAG 和传统向量 RAG 的本质区别是什么？各适合什么场景？

本质区别在于信息组织方式：向量 RAG 将文档视为独立的语义片段（chunk），通过相似度匹配检索；GraphRAG 将文档中的知识提取为结构化的实体-关系图谱，通过图遍历和推理检索。向量 RAG 适合：事实性 QA（"X 是什么？"）、语义相似的内容检索、实现简单/成本低。GraphRAG 适合：全局总结性问题（"涉及哪些技术？"）、多跳推理（"A 的合作方做了什么？"）、实体关系查询。最佳实践：两者混合使用，通过意图路由分流不同类型的查询。判断是否需要 GraphRAG：分析 bad case 中有多少是关系/全局类问题——如果 >20% 就值得投入。

Microsoft GraphRAG 的 Community Detection + Summarization 具体是怎么工作的？

流程：①从文档中用 LLM 抽取实体和关系构建知识图谱②使用 Leiden 算法对图做层次化社区检测——将紧密相连的实体聚为一个社区（类似主题聚类）③对每个社区用 LLM 生成摘要描述（概括该群组的核心主题和关键发现）④建立多层社区结构（粗→细）。查询时：Local Search 从查询实体出发遍历邻居获取 context；Global Search 用 Map-Reduce 方式遍历所有社区摘要。核心创新：社区摘要将分散的图结构凝聚为可理解的叙述，使得"全局总结类"问题可以通过遍历摘要来回答，而非需要看遍所有原始文档。

如何用 LLM 做知识图谱的实体关系抽取？有哪些挑战？

方法：给 LLM 提供文本 chunk + 结构化 prompt（定义实体类型和关系类型），要求输出 JSON 格式的实体和关系列表。关键挑战：①实体消歧：同一实体的不同表述需要合并（"GPT-4""gpt4""OpenAI模型"→同一实体）②抽取一致性：不同 chunk 中 LLM 对同一关系的表述可能不一致③幻觉：LLM 可能"发明"原文中不存在的关系④成本：大规模文档集的逐 chunk 抽取费用高⑤Schema 设计：实体/关系类型的定义影响后续查询能力。缓解策略：严格的 prompt 约束 + 多次采样投票 + 后处理验证 + Schema-guided 抽取。

GraphRAG 的 Local Search 和 Global Search 分别适合什么类型的问题？

Local Search：适合关于特定实体/关系的具体问题。方法是从 query 中识别实体 → 在图中找到对应节点 → 遍历 1-2 跳邻居收集上下文 → 送 LLM 生成。例如："LangChain 支持哪些向量数据库？""张三和李四是什么关系？"。Global Search：适合需要全局概览的总结性问题。方法是用 Map-Reduce：每个社区摘要独立回答 → 过滤无关社区 → 合并所有有关社区的回答 → 综合生成。例如："这个项目涉及哪些技术栈？""有哪些主要的参与方？"。Global Search 成本更高（遍历所有社区），但能回答向量 RAG 完全无法处理的问题。

构建 GraphRAG 系统的成本主要在哪里？如何优化？

成本主要在索引构建阶段（LLM 调用）：①实体关系抽取：每个 chunk 一次 LLM 调用（最大开销）②实体消歧：需要两两比较或聚类③社区摘要生成：每个社区一次 LLM 调用。估算：1000 个 chunk × $0.01-0.03/chunk = $10-30（GPT-4o），如果文档量大可达数百美元。优化方法：①用轻量模型做初步抽取（GPT-4o-mini / 本地 Llama 3），只对困难case用强模型②批量处理降低 API 开销③增量更新而非全量重建④预定义 Schema 减少 LLM 抽取的不确定性⑤缓存：相同/相似 chunk 不重复抽取。对比：向量 RAG 索引成本仅 $1-5（只需 embedding），GraphRAG 贵 10-50 倍。但注意索引成本与总拥有成本（TCO）的区别：图构建是一次性投入，每次多跳查询都是 O(1)，多跳密集场景下边际成本反而更低（详见第七节）。

GraphRAG 的增量更新为什么困难？有什么解决方案？

困难原因：①新文档加入时需要重新做实体抽取和关系抽取②新实体可能与已有实体重复（需要重新消歧）③新关系可能改变社区结构（需要重新做社区检测和摘要生成）。解决方案：①定期全量重建（如每周/每月）而非实时更新②分层更新：只更新受影响的社区（新实体所属的社区），其他社区保持不变③使用向量索引 + 图索引的混合存储，新文档先加入向量索引（增量快），定期批量加入图索引④对于实时性要求不高的场景（如企业知识库），接受小时级延迟。生产经验：采用增量更新 + 定期全量重建的双轨策略——增量更新约 200 次后，实体消歧误差会累积到约 3%，触发一次全量重建即可将误差归零；维护成本约为初始构建成本的 5-8%/月。关键认知：GraphRAG 不适合需要实时更新的高频场景（如新闻、股票），更适合相对稳定的知识管理场景。

如何评估 GraphRAG 系统的图构建质量？

图构建质量直接决定 GraphRAG 的查询效果，推荐从四个维度评估：(1) 实体覆盖率 — 随机抽样 500 段文本，统计被正确抽取的实体占实际存在实体的比例，生产标准 ≥ 90%；(2) 关系准确率 — 人工标注 200 条关系作为金标准，计算抽取关系的 Precision/Recall/F1，生产标准 F1 ≥ 0.82；(3) 图连通性 — 检查图中最大连通分量的占比，占比 <60% 说明图谱碎片化严重，需要加强跨文档实体链接；(4) 端到端查询验证 — 构建 50 条标准多跳查询测试集，对比 GraphRAG 与人工专家的回答一致率，生产标准 ≥ 75%。建议在图构建完成后先做质量门禁（Quality Gate），不达标则不上线。

GraphRAG 在哪些场景下效果不佳甚至不如普通 RAG？

GraphRAG 不适合以下场景：(1) 简单事实查询 — "X 的价格是多少"，单条文档即可回答，图遍历反而增加延迟（120ms vs 30ms）；(2) 高度动态数据 — 如实时股票行情，图谱构建速度跟不上数据更新频率，关系边频繁失效；(3) 非结构化创意内容 — 诗歌、小说等文学文本，实体间关系模糊且主观，难以构建高质量图谱；(4) 数据量极小 — 文档少于 1,000 篇时，图构建的固定成本无法被查询量摊薄，ROI 为负。核心判断标准：如果查询通常只涉及单一文档且不需要跨文档推理，普通 RAG 性价比更高。

GraphRAG 的图遍历和向量检索可以结合使用吗？

可以且推荐结合。两种结合方式：(1) 向量预筛选 + 图遍历 — 先用向量检索找到"入口节点"（最相关的实体），再从入口节点出发做图遍历（沿关系链扩展）；(2) 图遍历 + 向量精排 — 图遍历找到候选实体/文档集合，再用向量相似度对候选精排。生产验证：生物医药场景中，向量预筛选将图遍历的起始节点从全量 50 万个缩减至 50 个，遍历时间从 2s 降至 120ms。核心洞见：向量检索擅长"找到起点"，图遍历擅长"沿路径发现"，两者互补。
