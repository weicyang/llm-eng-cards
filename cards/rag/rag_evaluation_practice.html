EV03 · RAG 性能评估指标（实战篇）

RAG Evaluation in Practice — 三步落地评测：评测集构建 → 分层指标 → 业务验证

核心直觉：RAG 有两个核心出错点：没拿到对的资料（检索问题）和资料对了模型乱编（生成问题）。必须分层拆解，不能只看最终答案。

二、Step 1 · 构建有业务分布的评测集

关键认知：不建好测试集，跑再花哨的指标都是自嗨。评测集是一切指标的基础。

数据来源

方式做法注意事项
真实日志抽取从用户日志中抽 50~100+ 条问题覆盖高频、长尾、多跳推理、模糊意图
LLM 反向生成基于文档库让 LLM 生成问题必须人工逐条抽检，剔除原文没依据的假问题

数据分布控制

  • 按业务场景分层（售前、售后、政策等）
  • 按问题长度分层
  • 按所需 chunk 跨度分层（单 chunk vs 跨 chunk）
  • 避免测试集全是简单直给的问题

每条样本三要素

  1. 用户问题：真实或合成的查询
  2. 标准答案（或答案要点）：用于评估生成质量
  3. 必须召回的参考 chunk 列表：用于评估检索质量

示例场景：一个售后知识库 RAG，上线前用 40 条自己写的问题测，条条命中，团队据此判断可以发布。上线两周后转人工率 34%，与测前预期严重不符。复盘发现测试集里 38 条都是"单 chunk 直给"的标准表述，而真实日志里 41% 的问题需要跨 chunk 拼答案（比如同时用到退款条件和到账时效），另有 23% 带错别字或口语缩写。方案是重建评测集：从三个月日志里按业务场景 × 问题长度 × chunk 跨度分层抽 120 条，其中跨 chunk 类占到 40%，每条补齐标准答案与必须召回的 chunk 列表。用新评测集重跑，Context Recall 只有 0.53——问题终于在离线阶段暴露出来了。改进 chunk 策略与召回通道后 Recall 到 0.81，转人工率降到 12%。代价是评测集从"一下午写完"变成需要两人三天标注，且每季度要跟着业务补一轮。

三、Step 2 · 分层评测（检索 + 生成）

检索质量指标

指标含义低分诊断
Context Precision（检索精确率）召回的 chunk 中有多少是真正相关的。类比：搜索引擎返回 10 条结果，有几条是你真正需要的？问"退款到账"却召回"发票规则"
Context Recall（检索召回率）回答所需的全部信息是否都被召回了。类比：图书馆有没有把所有相关书籍都找出来，还是漏了几本关键的？需同时用退款条件+到账时间，只召回一个
Hit Rate至少一个相关 chunk 被召回的比例整体召回能力
MRR第一个相关 chunk 的排名位置排序质量

生成质量指标

指标含义低分诊断
Faithfulness生成内容是否忠实于检索到的上下文文档写"3-7 工作日"，模型说"当天到账"
Answer Relevance回答是否与用户问题相关问"怎么申请退款"，答"退款规则"
关键洞察：单点测试满分但分层指标低 = 测试集太简单或分布歪了，一上真实复杂问题就崩。

指标组合诊断结论排查方向
Faithfulness 高 + Answer Relevance 低 检索回的上下文不对 检查参考 chunk 准确性、召回策略是否有偏

七、Do / Don't

  • 先建评测集再跑指标
  • 检索/生成分层评测
  • 从指标组合反推问题根因
  • 业务指标作为终极裁判
  • 人工抽检兜底
  • 分层抽样控制数据分布
  • 只看准确率/召回率背指标
  • 用 demo 几条 case 代表整体
  • 忽略测试集代表性
  • 不区分检索问题和生成问题
  • 合成问题不抽检
  • 测试集全是简单直给问题

生产案例

生产验证：某客服 RAG 系统建立 RAGAS 评估体系后，每周跑 500 条测试查询自动评估。3 个月数据趋势：Faithfulness 从 0.72 提升至 0.91（修复了 LLM 幻觉问题），Answer Relevance 从 0.65 提升至 0.85（优化了 Prompt 指令），Context Recall 从 0.58 提升至 0.82（改进了 Chunk 策略和 Embedding 模型）。关键发现：Faithfulness < 0.7 时用户投诉率 3x 于正常水平（LLM "编造"信息直接导致错误答案）。建立了"评估驱动开发"流程 — 每次改动前先跑评估，指标下降则回滚，确保线上质量持续上升。

RAG 评测的核心原则：必须分层拆解（检索质量 vs 生成质量），不能只看最终答案。Context Relevance 低说明检索有问题，Faithfulness 低说明模型在编造——两者的修复路径完全不同。

Q&A

为什么不能只看准确率和召回率？

RAG 有两个核心出错点：检索不到对的资料、资料对了模型乱编。只看最终答案无法区分问题在哪一层。必须分层评测——检索看 Context Precision/Recall，生成看 Faithfulness/Answer Relevance，才能精准定位问题并优化。

评测集怎么构建才能保证代表性？

① 从真实用户日志抽取 50~100+ 条问题，覆盖高频/长尾/多跳推理/模糊意图。② 用 LLM 反向生成补充，但必须人工逐条抽检剔除假问题。③ 按业务场景、问题长度、chunk 跨度做分层抽样，避免测试集偏向简单问题。每条样本包含三要素：问题、标准答案、必须召回的参考 chunk。

Faithfulness 高但 Answer Relevance 低说明什么？

说明模型忠实于检索到的上下文（没有乱编），但检索回来的内容跟用户问题不相关。排查方向：① 检查测试集里该问题的参考 chunk 是否准确，② 检查召回策略是否有偏（如关键词匹配偏向、Embedding 语义偏移），③ 检查 Reranker 排序逻辑。

网页版 demo 测试满分为什么不能代表线上效果？

因为 demo 测试问题太干净（标准表述、单一意图），真正上线后面对口语化表达、错别字、意图混合、长尾问题，效果会断崖式下降。必须用有业务分布的评测集 + 线上 Bad Case 率/转人工率/追问率等业务指标来验证，业务指标才是终极裁判。

RAGAS、DeepEval、TruLens 怎么选？

RAGAS：适合快速验证，Faithfulness/Recall/Precision/Relevance 四件套开箱即用。DeepEval：适合嵌入 CI/CD 流水线，自动化回归测试。TruLens：偏线上观测和链路分析，适合生产环境监控。三者可组合使用，离线用 RAGAS，CI 用 DeepEval，线上用 TruLens。

Context Precision 和 Context Recall 双低，应该按什么顺序排查？

双低意味着检索管线整体有问题，但排查顺序不能乱，否则会在错误的层反复调参。第一步先排除评测集本身的问题：抽 10 条样本人工确认"必须召回的 chunk"标注是否正确，标注错了指标就是假的。第二步查 chunk 切分，直接打开索引里的原始 chunk 看——如果发现句子被截断、表格被劈成两半、页眉页脚混在正文里，那么后面无论换什么模型都白搭，因为答案在库里就是不完整的。第三步查 Embedding 与召回通道，典型症状是业务黑话搜不到（用户搜"退单"、文档写"逆向订单"），这时该考虑领域微调或补一路 BM25。第四步才轮到 Reranker，而且要注意 Reranker 只能改善 Precision，救不了 Recall——候选集里本来没有的东西，精排也变不出来。一个实用的判别技巧：把 K 放大到 100 再看 Recall，如果 Recall 明显回升，说明是排序问题；如果仍然很低，说明是索引侧（切分或 Embedding）的问题。
