G29 · RAG 优化 17 策略

从文档解析到答案生成的全链路优化指南 — 按 ROI 排序，逐层叠加

RAG 优化的本质是"先解决垃圾进，再解决找不准，最后优化答不好"。跳过基础层直接上高级策略是最常见的反模式。

RAG（Retrieval-Augmented Generation）的本质是"开卷考试" — 模型不需要记住所有知识，而是实时从知识库中检索相关内容来辅助回答。17 个策略按优化阶段分类，覆盖文档解析 → Chunk 切分 → Embedding → 检索 → 重排序 → 生成全链路。

一、文档解析层（策略 1-4）

文档解析是 RAG 链路的源头 — 解析质量差，后面所有优化都是"在垃圾上雕花"。70% 的 RAG 问题可以追溯到解析和分块阶段。

策略 1：智能分块

按语义边界切分文档，而非按固定字数。固定字数分块会在句子或段落中间切断，导致信息不完整。RecursiveCharacterTextSplitter 按层级分隔符（段落 → 句子 → 词）逐级尝试切割，优先保持大结构完整。中文文档需要特别加入中文标点作为分隔符。

关键参数：chunk_size 通常为 256-1024 tokens，overlap 为 chunk_size 的 10-20%。chunk_size 应该匹配用户期望问的问题的"答案粒度" — 太大语义被稀释，太小信息断裂。

策略 2：元数据增强

为每个 chunk 添加结构化元数据（来源文档、时间、标签、标题层级），使检索时可以按元数据预过滤。例如查询"最新的退货政策"时，先按时间过滤最近 3 个月的文档，再做向量检索，大幅减少噪声。

策略 3：多模态解析

将图片、表格、公式等非文本内容转换为文本表示。表格可转为自然语言描述，图片可用 LLM 生成描述，公式可保留 LaTeX 表示。不处理多模态内容意味着丢失了文档中大量的结构化知识。

策略 4：层级索引

建立文档/章节/段落三级索引。粗粒度检索先定位到文档或章节，细粒度检索再精确定位到段落。对于大型知识库（万级文档），层级索引可以将检索时间从 O(N) 降到 O(log N)，同时提高检索精度。

二、检索层（策略 5-9）

检索层是 RAG 的核心引擎 — 找对了文档，生成层只需要"忠实复述"即可；找错了文档，再好的 LLM 也无能为力。

策略 5：混合检索

将向量检索（语义匹配）和 BM25（关键词匹配）融合。向量检索擅长语义匹配（"怎么退货" ≈ "退款流程"），但对精确关键词匹配弱（产品型号、人名）。BM25 擅长精确匹配但对语义理解差。两者通过 RRF（Reciprocal Rank Fusion）算法融合排序，互补优势。

RRF 融合公式：score(doc) = Σ 1/(k + rank_i)
其中 k 通常取 60，rank_i 是文档在第 i 个检索器中的排名

策略 6：查询改写（HyDE）

用户的查询通常简短模糊（如"怎么部署"），与文档的正式表述有语义鸿沟。HyDE（Hypothetical Document Embeddings）让 LLM 先生成一个"伪答案"（假设性的完整回答），再用伪答案去检索。伪答案更贴近文档的表述方式，检索效果更好。代价是多一次 LLM 调用（~500ms）。

策略 7：查询分解

将复杂的多跳问题拆为多个子问题分别检索。例如"LangChain 和 LlamaIndex 哪个更适合企业级应用？"可拆为：①LangChain 的企业级特性 ②LlamaIndex 的企业级特性 ③两者的企业级对比。每个子问题独立检索，结果合并后送入 LLM 做比较分析。

策略 8：查询扩展

用同义词和相关概念扩展查询，提升召回率。例如用户问"AI 编程助手"，扩展为"AI 编程助手 OR 代码补全 OR Copilot OR Cursor"。可通过 LLM 生成扩展词，或从知识图谱中提取相关概念。注意扩展过多会引入噪声，通常扩展 2-3 个同义词即可。

策略 9：重排序（Re-ranking）

用 Cross-Encoder 对初检结果做精细排序。初筛（向量检索）速度快但精度有限，重排序对"问题-文档"对做深度理解打分，过滤噪音。实测精度提升 15-30%，延迟仅增加约 50-200ms。

用户 Query ↓ 混合检索（向量 + BM25，快但粗）→ Top-20 候选 ↓ Cross-Encoder 重排序（慢但精）→ Top-3~5 精选 ↓ 送入 LLM 生成回答
重排序是 RAG 优化中 ROI 最高的策略：仅增加 50ms 延迟，准确率可提升 11 个百分点。相当于先用粗网捕鱼，再用细筛精选。

三、Embedding 层（策略 10-12）

Embedding 是文档和查询的"通用语言" — 把文本变成向量，让机器能计算语义距离。Embedding 质量直接决定了检索的语义理解能力。

策略 10：领域微调

用领域数据微调 Embedding 模型，使其更好地捕捉领域特定的语义关系。通用模型在垂直领域（如医学、法律、金融）表现往往不佳，因为训练数据中相关领域文本较少。微调后，"心肌梗死"和"心梗"的向量距离会显著缩小。典型微调数据量：5000-10000 对领域内查询-文档对。

策略 11：多向量索引

同一文档生成多个向量（标题向量、摘要向量、正文向量），查询时与最匹配的向量对齐。标题向量适合粗粒度检索（"这个文档讲什么？"），正文向量适合精确检索（"具体怎么操作？"）。解决单一向量无法同时表达文档全局语义和局部细节的问题。

策略 12：稀疏-稠密融合

将 SPLADE（稀疏表示，类似学习的 BM25）与稠密向量融合。稀疏表示擅长精确关键词匹配和词汇扩展，稠密向量擅长语义理解。两者融合后，既能精确匹配关键词，又能理解语义，类似混合检索在向量层面的实现。

四、生成层（策略 13-15）

生成层优化的核心矛盾：给 LLM 足够上下文让它理解，但不能太多让它迷失；要求它忠实复述检索内容，但不能太死板。

策略 13：上下文压缩

检索结果直接送入 LLM 往往包含大量冗余和噪声。上下文压缩通过去重、摘要、提取关键段落等方式，将检索结果浓缩为高质量上下文。长上下文下 LLM 可能出现"Lost in the Middle"问题 — 对中间位置的信息关注度降低，压缩可以缓解这一问题。

策略 14：忠实性约束

在 Prompt 中明确要求"仅基于提供的上下文回答，如果上下文中没有相关信息，请说'我不确定'"。配合降低 Temperature（如 0.1）减少生成随机性，可显著提升 Faithfulness（忠实性）。这是对抗幻觉最直接、成本最低的手段。

忠实性约束是 P0 必做策略中成本最低的：只需修改 Prompt 模板，零额外延迟，即可将幻觉率降低 30-50%。配合 citation 要求（"引用具体段落"），效果更佳。

策略 15：答案验证

生成回答后，自动检查答案是否有检索依据。可以用另一个 LLM 判断"这个回答是否完全基于提供的上下文"，或通过提取答案中的事实陈述逐条验证。无依据的回答可以标记为"低置信度"或直接要求重新生成。这相当于在输出端加了一道质检关卡。

五、系统层（策略 16-17）

系统层优化不改变回答质量，但直接影响用户体验和运营成本 — 延迟降 1 秒，用户满意度可能提升 20%。

策略 16：缓存优化

高频查询结果缓存，避免重复计算。语义缓存（基于 embedding 相似度匹配）可以命中相似但不完全相同的查询。例如"如何申请退款"和"退款流程怎么走"语义相似，可以复用缓存结果。缓存命中率通常可达 30-50%，直接降低 LLM 调用成本。

策略 17：异步预取

预测用户下一步可能问的问题并提前预检索。例如用户看完"产品介绍"后大概率会问"价格"和"如何购买"，可以异步预检索这两个方向的文档。配合流式输出（streaming），可以将用户感知延迟降低 40-60%。

六、优化优先级与 ROI 排序

不要一次性上所有策略。从 P0 开始，每上一个策略就跑评测验证效果，确认有效再加下一个。避免过度工程化。

Q&A

RAG 优化应该从哪里开始？P0 策略为什么是这四个？

P0 四个策略覆盖了 RAG 全链路的核心环节：智能分块（源头质量）、混合检索（召回完整性）、重排序（精度）、忠实性约束（生成质量）。它们 ROI 最高且互不冲突。关键原则是从 P0 开始逐层叠加，每层跑评测验证效果后再加下一层。跳过基础层直接上高级策略（如跳过 Chunk 优化直接上 Reranker）是最常见的反模式 — 垃圾进垃圾出。

混合检索为什么比单一向量检索好？RRF 融合的原理是什么？

向量检索擅长语义匹配（"怎么退货" ≈ "退款流程"），但对精确关键词匹配弱（产品型号、人名）。BM25 擅长精确匹配但对语义理解差。两者互补：语义相似 + 关键词精确命中 = 更全面的召回。RRF（Reciprocal Rank Fusion）不依赖分数归一化（BM25 和向量相似度分数量纲不同），只看排名：score = Σ 1/(k + rank_i)，k 通常取 60。实践建议：BM25 + 向量各取 Top-20，RRF 融合后取 Top-5。

重排序为什么 ROI 最高？Cross-Encoder 和 Bi-Encoder 有什么区别？

初检用 Bi-Encoder（query 和 document 独立编码，计算快但交互弱）快速召回候选。重排序用 Cross-Encoder（query 和 document 拼接后一起过 Transformer，深度理解交互关系）精排，精度远高于 Bi-Encoder。相当于先用粗网捕鱼，再用细筛精选。重排序仅增加 50ms 延迟（Top-20 候选），但准确率可提升 11pp，是 RAG 优化中投入产出比最高的策略。

评估驱动开发怎么落地？怎么避免"改了 A 好了但 B 变差了"？

评估驱动开发 = 每次改动前先跑自动评估（如 RAGAS 四维指标），指标下降则回滚。落地步骤：①构建黄金测试集（200-500 条人工标注的查询-答案对）②接入评估框架（RAGAS/DeepEval），CI/CD 中自动跑评估 ③设定指标阈值（如 Faithfulness ≥ 0.85），低于阈值则阻断部署。避免"改了 A 好了 B 变差"：用消融实验（每次只改一个变量），在相同评估集上对比，确保净效果为正。生产数据：某系统实施后 3 个月内 Faithfulness 从 0.72 提升至 0.91。

HyDE 查询改写的原理和代价是什么？什么场景值得用？

原理：用户查询通常简短模糊，与文档正式表述有语义鸿沟。HyDE 先让 LLM 生成"伪答案"（假设性完整回答），再用伪答案的 embedding 去检索。伪答案更贴近文档表述，检索效果更好。代价：多一次 LLM 调用（~500ms + token 成本）。值得用的场景：复杂查询、用户表述与文档措辞差异大、对检索质量要求高。不值得用：简单事实查询（直接向量检索就够）、实时性要求极高的场景。

忠实性约束的 Prompt 应该怎么写？Temperature 怎么设？

核心 Prompt 要素：①"仅基于提供的上下文回答"②"如果上下文中没有相关信息，请说'我不确定'"③"引用具体段落编号作为依据"。Temperature 建议 0.1（事实性回答），创意性回答可放宽到 0.3-0.5。配合 citation 要求效果更佳 — 要求 LLM 标注每个陈述的来源段落，既约束了忠实性，也方便用户验证。实测可将幻觉率降低 30-50%，且零额外延迟。

上下文压缩有哪些具体方法？怎么避免压缩过度导致信息丢失？

常见方法：①提取式摘要（抽取关键句子）②LLM 摘要（让模型提炼要点）③去重（移除重复内容）④相关性过滤（只保留与 query 相关的段落）。避免过度压缩：保留 Top-3~5 个最相关的完整段落而非片段，对压缩前后的 Faithfulness 做对比验证。注意"Lost in the Middle"问题 — 长上下文中间位置的信息容易被忽略，将最相关内容放在开头和结尾。

语义缓存和精确缓存有什么区别？缓存一致性怎么保证？

精确缓存：query 完全相同时命中（hash 匹配），零误判但命中率低。语义缓存：query embedding 相似度 > 阈值时命中（如 cosine > 0.95），命中率高但有误判风险。一致性保证：①知识库更新时主动失效相关缓存 ②设定 TTL（如 24 小时过期）③对高风险场景（如医疗/法律）禁用缓存或降低相似度阈值。实践中语义缓存命中率 30-50%，可直接降低 LLM 调用成本 30%+。
