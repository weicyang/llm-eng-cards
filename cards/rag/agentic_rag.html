G20 · Agentic RAG

Agentic RAG — 给 RAG 注入 Agent 灵魂，从"检索-生成"升级为自主解决问题的专家 / 五大 Agentic 模式 / 自适应检索 / 成本 Trade-off / 评估体系

Agentic RAG 的本质是把 RAG 从"一次检索定终身"升级为"多轮迭代、自主决策"的智能体。核心价值：查询规划（拆解复杂问题）+ 自适应检索（置信度低于阈值时自动重试）+ 知识整合（多源去重合并）。代价：Token 消耗 3~10 倍，延迟 2~5 倍。只在多跳推理、模糊查询、高风险场景中才值得投入。

一、RAG 演进：从 Naive 到 Agentic

RAG 的演进路径清晰可循：Naive RAG → Advanced RAG → Modular RAG → Agentic RAG。每一步都在解决上一代的核心痛点。理解演进路径才能判断你的场景需要哪一级。

阶段核心特征解决的痛点遗留问题
Naive RAG固定管道：分块→检索→生成模型幻觉（提供外部知识）检索不精准、无法自我修正
Advanced RAG预检索优化（查询改写、HyDE）+ 后检索优化（Rerank、压缩）检索精度不足管道仍然固定，无法适应查询复杂度
Modular RAG模块化组件（可插拔检索器、生成器）灵活性不足缺乏自主决策能力
Agentic RAG注入 Agent 能力：规划、反思、工具调用、多 Agent 协作一次性流程无法应对复杂任务成本高、延迟大

传统 RAG 的致命痛点

传统 RAG 对每个查询执行完全相同的固定管道——无论是简单的"退款流程是什么"还是复杂的"分析特斯拉 2024 年 Q3 营收下滑原因及竞品表现"，都走同一套检索→生成流程。这导致三个致命问题：

痛点表现影响量化
检索相关性差关键词匹配但语义不符，或完全不相关复杂查询准确率 ~34%
缺乏意图理解用户提问模糊（"那个报错怎么修"），缺失上下文~40% 查询需要用户澄清
无法处理复杂任务多步推理问题无法拆解，一次性流程无法应对多跳问题解决率 < 30%
生产数据：某金融研报分析系统在 Naive RAG 阶段，简单查询（如"什么是 P/E ratio"）准确率 89%，但复杂查询（如"分析特斯拉 2024 Q3 营收下滑原因及竞品表现"）准确率仅 34%。差距的根本原因：复杂查询需要跨多个文档、多个时间维度推理，而 Naive RAG 的单次检索只能命中表面相关内容。

二、Agentic RAG 五大核心模式

2025-2026 年生产环境中收敛出五种标准的 Agentic RAG 模式：Self-RAG、Corrective RAG (CRAG)、Adaptive RAG、ReAct RAG、Multi-Hop RAG。每种模式解决不同的痛点，选择取决于查询复杂度分布。

┌─────────────────── Agentic RAG 五大模式 ───────────────────┐ │ │ │ ① Self-RAG (自我反思) │ │ 检索 → 评估相关性 → 相关则生成 → 不相关则重新检索 │ │ 模型自身发射反思 token：Retrieve / IsRel / IsSup / IsUse │ │ │ │ ② Corrective RAG / CRAG (纠错路由) │ │ 检索 → 检索评估器打分 → 高分:正常使用 │ │ → 低分:切换替代检索(Web搜索/SQL) │ │ → 模糊:知识精炼后再用 │ │ │ │ ③ Adaptive RAG (自适应路由) │ │ 复杂度分类器 → A类(简单): 不检索,LLM直接回答 │ │ → B类(中等): 单次检索 │ │ → C类(复杂): 多步迭代检索 │ │ │ │ ④ ReAct RAG (推理+行动循环) │ │ Thought → Action(检索/计算/SQL) → Observation → 循环 │ │ │ │ ⑤ Multi-Hop RAG (多跳分解) │ │ 复杂问题 → 分解为子问题 → 分别检索 → 汇总推理 │ │ │ └─────────────────────────────────────────────────────────────┘

Self-RAG：让模型学会说"我不确定"

机制概述：LLM 在生成过程中发射反思 token（Retrieve/ISREL/ISSUP/ISUSE），自评估检索必要性、文档相关性、生成忠实度与答案效用。完整机制字典见 G18 · 高级 RAG 模式；反思 token 训练、自适应推理流程与生产部署的深度内容见 G19 · Self-RAG 系统设计核心。

Adaptive RAG：根据复杂度动态选择策略

机制概述：轻量复杂度分类器将查询分为 A/B/C 三类（直接回答 / 单次检索 / 多步迭代），基准测试 F1 达 50.91 而平均推理仅 1.03 步——准确率最高且效率接近单步方法。完整机制字典见 G18 · 高级 RAG 模式。

三、Agentic RAG 核心工作流

┌─────────────────────────────────────────────────────────────┐ │ Agentic RAG 完整工作流 │ ├─────────────────────────────────────────────────────────────┤ │ │ │ 用户提问 │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ 1 · 查询理解与分类（Query Understanding） │ │ │ │ 复杂度分类器 → A/B/C 类 │ │ │ │ 意图识别 → 事实查询 / 对比分析 / 因果推理 │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ 2 · 查询规划（Query Planning） │ │ │ │ A类: 直接生成答案 │ │ │ │ B类: 查询重写 → 单次检索 │ │ │ │ C类: 问题分解 → 子问题1 + 子问题2 + 子问题3 │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ 3 · 自适应检索（Adaptive Retrieval） │ │ │ │ 首次检索 → 置信度评分 │ │ │ │ 置信度 ≥ 0.7 → 进入生成阶段 │ │ │ │ 置信度 < 0.7 → 修改关键词 + 扩大范围 → 二次检索 │ │ │ │ 最多 3 轮（防止无限循环） │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ 4 · 知识整合（Knowledge Integration） │ │ │ │ 多源文档去重 → 矛盾检测 → 一致性报告 │ │ │ │ 3 次检索的 15 篇文档 → 去重合并 → 8 篇核心证据 │ │ │ └───────────────────────────────────────────────────────┘ │ │ ↓ │ │ ┌───────────────────────────────────────────────────────┐ │ │ │ 5 · 生成与自我验证（Generation + Self-Check） │ │ │ │ 基于整合后的证据生成答案 │ │ │ │ 自我验证: 答案是否有证据支撑? 是否有遗漏? │ │ │ │ 不合格 → 回到步骤 3 补充检索 │ │ │ └───────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────┘

自适应检索：置信度判断机制

自适应检索的核心是"判断检索结果够不够好"。三种判断机制：置信度评分、覆盖度检查、一致性验证。只有通过了评估，才进入生成阶段；否则修改策略重新检索。

判断机制原理阈值不通过时的动作
置信度评分LLM 对检索结果与查询的相关性打分（0-1）< 0.7 触发重试修改关键词 + 扩大时间范围
覆盖度检查分析检索结果是否覆盖查询中所有关键实体缺失 > 30% 实体补充检索缺失实体
一致性验证检测多篇文档之间是否存在矛盾信息存在矛盾额外检索仲裁 + 标注不确定性

知识整合：多源去重与矛盾处理

当 Agentic RAG 经过多轮检索后，会收集到大量可能重复甚至矛盾的文档。知识整合器负责三项工作：去重（识别语义相似的文档片段，只保留信息最丰富的一份）、矛盾检测（发现文档 A 说"营收增长 15%"但文档 B 说"营收下滑 8%"，标记矛盾并尝试仲裁）、一致性报告（将整合后的证据按时间线和主题组织，标注确定性等级）。

生产案例：某金融研报分析系统从 Naive RAG 升级为 Agentic RAG 后，复杂查询的答案准确率从 34% 提升至 78%。核心改进：(1) 查询规划器将"分析特斯拉 2024 年 Q3 营收下滑原因及竞品表现"拆解为 3 个子查询，分别检索财报、新闻和竞品数据；(2) 自适应检索 — Agent 首次检索后判断置信度仅 0.45（低于阈值 0.7），自动触发二次检索（换关键词 + 扩大时间范围），最终置信度提升至 0.88；(3) 知识整合器将 3 次检索的 15 篇文档去重合并为 8 篇核心证据。延迟代价：端到端从 2s 增至 6s（3 次检索），但用户愿意等待。

四、成本与质量的 Trade-off

Agentic RAG 不是免费的午餐——Token 消耗是传统 RAG 的 3~10 倍，延迟是 2~5 倍。关键问题是：什么场景下这个代价是值得的？

成本量化对比

方案简单查询准确率复杂查询准确率P50 延迟Token 成本/查询
Naive RAG89%34%~2s1x 基线
Advanced RAG（+Rerank）92%45%~3s1.5x
Self-RAG91%58%~3.5s2x
Adaptive RAG93%65%~3s（自适应）2.5x（自适应）
Agentic RAG（全模式）94%78%~6s5~10x

什么时候值得上 Agentic RAG？

场景推荐方案原因
FAQ 机器人Naive RAG / Advanced RAG查询简单固定，不值得多花 Token
客服问答Advanced RAG + Adaptive大部分查询简单，少量需要多步
金融研报分析Agentic RAG多跳推理、跨文档对比，质量优先
法律文档分析Agentic RAG高风险决策，准确率至关重要
医疗诊断辅助Agentic RAG + Human-in-the-Loop生命安全，必须最高准确率
Agentic RAG ROI = (复杂查询准确率提升 × 业务价值) / (额外 Token 成本 + 延迟代价) 当复杂查询占比 > 20% 且单次错误成本 > ¥100 时，ROI > 1
行业数据：Gartner 预测超过 40% 的 Agentic AI 项目将在 2027 年底前被取消，原因包括成本失控、ROI 不清晰和风险管控不足。反面案例：Harvey AI 的 Agentic RAG 法律系统报告幻觉率仅 0.2%，服务 700+ 法律客户；Deutsche Telekom 用 Agentic RAG 处理 200 万+ 客户对话，可接受答案率 89%。成败关键在于：是否在正确的场景使用正确的策略。
  • 先用 Naive RAG 建立 baseline，再逐步升级
  • 用复杂度分类器路由不同策略（别对简单查询用重炮）
  • 设置最大迭代次数（如 3 次）防止无限循环——各系统上限设置不同（2-5 次常见），按成本预算定
  • 构建黄金数据集（Golden Dataset）做量化评估
  • 监控 Token 成本和延迟的实时指标
  • 不要对所有查询都用 Agentic RAG（成本爆炸）
  • 不要忽略 Human Handoff 机制（Agent 搞不定时转人工）
  • 不要虚假量化（"准确率从 65% 到 95%"无法验证）
  • 不要不建评估体系就上线
  • 不要忽略 Token 成本的监控和预算限制

五、评估体系

没有评估体系的 Agentic RAG 就像没有温度计的炼丹——你不知道自己是在进步还是退步。必须构建黄金数据集，用标准化框架（RAGAS、TruLens）量化评估。

核心评估指标

指标含义评估对象Agentic RAG 目标值
Faithfulness生成内容是否有检索证据支撑生成质量> 0.90
Context Relevance检索结果与查询的相关性检索质量> 0.80
Answer Relevancy最终答案是否回答了用户的问题端到端质量> 0.85
Context Precision检索结果中相关文档的比例检索效率> 0.80

评估工具栈

2026 年的生产评估栈收敛为三件套：Ragas（开源 RAG 评估框架，支持 Faithfulness/Context Relevance 等指标）、Arize Phoenix（LLM 可观测性平台，追踪每步推理过程）、Langfuse（开源 LLM 监控，记录每次 Agent 调用的 Token 消耗和延迟）。三者组合可以覆盖"质量指标 + 过程追踪 + 成本监控"的完整评估需求。

生产实践：某金融系统的 Agentic RAG 评估流程：(1) 构建 500 条黄金数据集（覆盖简单/中等/复杂三类查询），由领域专家标注标准答案；(2) 每日自动回归测试，任何指标下降 > 2% 触发告警；(3) 每周 Bad Case 分析会，从 Phoenix 追踪中找出失败根因（60% 的失败来自"检索评估器误判"——把相关文档标记为不相关导致不必要的二次检索）；(4) Token 预算告警：单次查询 Token 消耗超过 ¥1 时自动降级到 Advanced RAG 策略。

六、Agentic RAG vs Multi-Agent RAG

Agentic RAG 和 Multi-Agent RAG 是两个不同维度的概念：前者是"单个 Agent 的自循环能力"，后者是"多个 Agent 的协作架构"。简单场景用 Agentic RAG 足够，复杂场景（多数据源、多步骤）才需要 Multi-Agent RAG。

维度Agentic RAG（单 Agent）Multi-Agent RAG
架构单 Agent 自循环（检索→评估→再检索）多 Agent 协作（检索Agent + 验证Agent + 生成Agent）
适用复杂度中等（单领域多步推理）高（跨领域、多数据源）
上下文共享单一上下文窗口各 Agent 独立上下文
延迟2~5x（自循环）3~10x（协作+通信）
扩展性受上下文窗口限制可独立扩展每个 Agent
典型框架Self-RAG, CRAG, Adaptive RAGLangGraph, CrewAI + RAG
生产案例：某欧洲银行在审计合规场景部署 Agentic RAG + 知识图谱，三年节省超过 2000 万欧元。架构演进路径：Phase 1 — Naive RAG（合规检查准确率 67%）→ Phase 2 — Advanced RAG + Rerank（74%）→ Phase 3 — Agentic RAG（Self-RAG + 知识图谱导航，准确率 91%）。关键成功因素：(1) 知识图谱作为额外的"结构化检索工具"，Agent 可以沿图谱边遍历相关法规条文；(2) Self-RAG 确保每条合规判断都有法规引用支撑（Faithfulness > 0.95）；(3) 设置 Human Handoff——当 Agent 置信度 < 0.6 时自动转交合规专家审核。

七、从 Naive RAG 迁移到 Agentic RAG

不要一步到位地从 Naive RAG 跳到 Agentic RAG——正确的迁移路径是渐进式的：先优化检索（Advanced RAG），再添加自适应路由（Adaptive RAG），最后引入完整的 Agentic 循环。每一步都需要量化验证收益后再进入下一步。

2026 年推荐技术栈

基于生产验证的技术选型：编排框架用 LangGraph（状态图驱动，支持循环和条件分支）或 LlamaIndex Workflows（事件驱动，检索优化更强）；检索栈用混合检索（BM25 + Embedding）+ Voyage AI rerank-2.5（比 Cohere Rerank v3.5 高 10-12%）；评估栈用 Ragas + Phoenix + Langfuse 三件套。

迁移案例：某法律科技公司从 Naive RAG 到 Agentic RAG 的迁移历时 10 周，按四个阶段渐进推进。Phase 1 后准确率从 67% 提升至 78%（+11pp）；Phase 2 后平均延迟从 3.2s 降至 2.1s（简单查询走快速通道）；Phase 3 后复杂查询准确率从 78% 提升至 87%；Phase 4 后达到 91%。关键教训：Phase 2 的复杂度分类器初期准确率仅 72%，导致 28% 的查询被错误路由。团队花了额外 2 周构建 1000 条标注数据训练分类器，准确率提升至 91% 后系统才真正稳定。
  • 渐进式迁移，每阶段量化验证后再进入下一阶段
  • Phase 1 就开始建立评估体系（黄金数据集）
  • 为复杂度分类器构建专门的训练数据
  • 每阶段都设置 Token 预算和延迟 SLA
  • 保留 Naive RAG 作为降级方案
  • 不要一步跳到完整 Agentic RAG（风险太高）
  • 不要在没有评估体系的情况下迁移
  • 不要忽略复杂度分类器的准确率（它是整个系统的基石）
  • 不要在 Phase 3/4 时忘记设置迭代上限
  • 不要移除旧管道（保留作为降级方案）

八、生产案例

案例一：金融研报分析系统
某金融研报分析系统从 Naive RAG 升级为 Agentic RAG 后，复杂查询（需多步推理）的答案准确率从 34% 提升至 78%。核心改进：(1) 查询规划器将复杂问题拆解为 3 个子查询，分别检索财报、新闻和竞品数据；(2) 自适应检索 — Agent 首次检索后判断置信度仅 0.45（低于阈值 0.7），自动触发二次检索（换关键词 + 扩大时间范围），最终置信度提升至 0.88；(3) 知识整合器将 3 次检索的 15 篇文档去重合并为 8 篇核心证据。延迟代价：端到端从 2s 增至 6s（3 次检索），但用户愿意等待（因为答案质量大幅提升）。Token 成本约为 Naive RAG 的 6 倍。
案例二：企业级 Agentic 检索系统（Microsoft）
Microsoft 2026 年发表的 AgenticRAG 系统在三个基准上展示了显著收益：BRIGHT 长上下文检索 Recall@1 达到 49.6%（比最佳 Embedding 基线高 21.8pp），WixQA 企业 QA 事实性评分 0.96（+13% 相对提升），FinanceBench 金融文档 QA 正确率 92%（距 Oracle 仅差 2pp）。消融实验揭示：最关键的因素是从单次检索切换为 Agentic 工具调用（性能提升 5.9 倍），其次是多查询搜索和文档内导航。系统仅由 4 个工具（search、find、open、summarize）组成，无需模型微调、无需图谱构建、无需自定义 Embedding 索引——直接在现有企业搜索基础设施上叠加 Agentic 层。

Q&A（8 题）

Agentic RAG 和传统 RAG 的核心区别是什么？
传统 RAG 是线性流程：用户提问→向量化→检索→生成答案，对所有查询走同一条管道。Agentic RAG 注入了 Agent 能力：① 查询重写（模糊→专业描述），② 问题分解（复杂→子问题分别检索汇总），③ 动态决策（查知识库/调 SQL/请求人工），④ 自我反思（检索结果不够就重新检索）。本质是从"阅读器"升级为自主解决问题的专家。生产数据：复杂查询准确率从 34% 提升至 78%，代价是延迟 2s→6s、Token 6x。
Self-RAG、CRAG、Adaptive RAG 三者如何选择？
根据核心痛点选择：(1) Self-RAG — 解决"生成内容缺乏证据支撑"的问题，通过反思 token 让模型自我评估，适合需要高 Faithfulness 的场景（如法律、医疗）；(2) CRAG — 解决"检索质量不稳定"的问题，通过评估器+纠错路由在检索不佳时切换替代方案，适合多数据源场景；(3) Adaptive RAG — 解决"所有查询用同一策略效率低"的问题，通过复杂度分类器动态路由，适合查询复杂度差异大的系统。三者可以组合使用。详细机制对比见 G19 第四章 · Self-RAG vs CRAG vs Adaptive-RAG 对比。
Agentic RAG 的自适应检索是怎么判断"检索结果不够好"的？
三种判断机制：(1) 置信度评分 — LLM 对检索结果与查询的相关性打分（0-1），低于阈值（如 0.7）触发二次检索；(2) 覆盖度检查 — 分析检索结果是否覆盖了查询中所有关键实体/概念，缺失则补充检索；(3) 一致性验证 — 多篇文档之间是否存在矛盾信息，矛盾时需要额外检索来仲裁。生产数据：自适应检索使答案准确率从 34% 提升至 78%，代价是延迟从 2s 增至 6s（平均 3 次检索）。
Agentic RAG 和 Multi-Agent RAG 有什么区别？什么时候该用哪个？
Agentic RAG = 单个 Agent 具备自主检索-反思-再检索能力（自循环）。Multi-Agent RAG = 多个专业 Agent 协作（如一个负责检索、一个负责验证、一个负责生成）。选择依据：(1) 单领域多步推理用 Agentic RAG（如跨文档的金融分析）；(2) 跨领域多数据源用 Multi-Agent RAG（如同时需要 SQL 数据库 + 文档库 + 实时新闻）。Agentic RAG 是"一个人多角色"，Multi-Agent RAG 是"多个人各一个角色"。
Agentic RAG 的 Token 成本如何控制？
四个控制手段：(1) 复杂度分类 — 对简单查询不走 Agentic 路径（Adaptive RAG 策略），60%+ 查询只需 1x Token；(2) 迭代上限 — 设置最大检索轮次为 3 次，防止无限循环（各系统上限设置不同，2-5 次常见，按成本预算定）；(3) Token 预算 — 单次查询 Token 消耗超过阈值（如 ¥1）时自动降级到 Advanced RAG；(4) 上下文压缩 — 每轮检索后对历史上下文做摘要压缩，避免 Token 浪费。生产系统目标：平均 Token 成本控制在 Naive RAG 的 3~5 倍（而非理论最高的 10 倍）。
实践中怎么避免虚假量化？
不要写"准确率从 65% 提升到 95%"这类无法验证的描述。应该：① 构建黄金数据集（人工标注 GT，至少 500 条覆盖三类查询）；② 用 RAGAS/TruLens 等评估框架给出具体指标（Faithfulness、Context Relevance、Answer Relevancy）；③ 说明评估方法而非只说数字（评测集构成、评估工具、置信区间）；④ 展示 Bad Case 分析和迭代过程（60% 的失败来自什么根因）。
Agentic RAG 的延迟问题如何解决？
四个优化方向：(1) 复杂度路由 — 60%+ 简单查询走快速通道（1~2s），只有复杂查询才走完整 Agentic 路径（6s）；(2) 并行子查询 — 问题分解后的多个子查询并发检索（而非串行）；(3) 缓存 — 对高频查询缓存检索结果和中间状态（Redis），命中率约 30%；(4) 流式输出 — 在检索和推理过程中先输出"思考过程"，降低用户感知的等待时间。综合优化可将加权平均延迟从 6s 降至 ~3.5s。
Human Handoff 机制在 Agentic RAG 中怎么实现？
Human Handoff 是 Agentic RAG 的安全网——当 Agent 无法给出可靠答案时，自动将问题转交人工处理。触发条件：(1) 置信度低于最低阈值（如 < 0.6）；(2) 达到最大迭代次数仍未收敛；(3) 检测到高风险场景（如涉及法律条款、财务决策）。实现方式：Agent 输出结构化报告（已收集的证据 + 不确定的部分 + 推荐的人工审核方向），连同对话历史一起转交。生产数据：Human Handoff 覆盖了约 8% 的查询，但这 8% 恰恰是最高价值的查询。
