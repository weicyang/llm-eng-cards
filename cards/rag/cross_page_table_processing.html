G15 · 跨页表格处理

先拼表后切块 / 续表四要素 / 结构修复三操作 / 双索引问答

跨页表格的本质矛盾是：表格是"逻辑对象"，而 PDF 分页是"物理排版"。页边界由打印需求决定，与语义毫无关系。因此正确顺序永远是——先把碎片重组回完整逻辑表，再谈切块与检索；反过来做，后面每一步都在为前面的错误还债。

一、跨页表格的语义断裂问题

跨页表格之所以难，根源在 PDF 格式的底层事实：文件只有一组把字符摆放在 (x, y) 坐标上的绘图指令，不存在"段落"与"表格"的语义结构，按页读取的解析器拿到的只是页面图形碎片，而不是"某张表的第 N 行"（PDF 解析难点与通用清洗流水线的系统论述见 D06 · PDF 数据清洗（RAG 场景）· 第一章）。在这个前提下，看分页对表格造成的具体伤害：

当一张逻辑表从第 5 页延续到第 6 页时，按页切分的管道会把它斩成两段。最典型的伤害场景：续页上只剩 华北 760 +5% 这样的裸数据，而"地区 / 收入 / 同比 / 单位：万元"这套表头留在了上一页。检索器即便命中了这个 chunk，大模型面对"760"也无法回答"这是哪个地区的什么指标"——于是要么拒答，要么编造。这就是语义断裂：物理上每页都有字，逻辑上信息已经残缺。

断裂的伤害是沿着管道逐级放大的：坏的解析产生残缺文本，残缺文本切出噪声 chunk，噪声 chunk 嵌入出无意义的向量，向量召回失败，最终表现为大模型幻觉。很多团队把表格问答不准归咎于 embedding 模型或 top-k 设置，实际上根因在上游的提取阶段——垃圾进，垃圾出。

公开基准数据印证了"结构感知"的价值：在 NVIDIA 2024 年的 RAG 分块基准中，按版面（页面/元素）切块的方案取得 0.648 的 top-1 准确率，且方差 0.107 为所有切块器中最低，全面优于按固定 token 长度切分的所有方法。对表格密集文档，结论更直接——切块的边界必须跟着表格结构走，而不是跟着字数走。

核心原则：先恢复完整逻辑表

正确的处理顺序只有一种：先拼表、再修复、后切块。即把分散在多页上的表格片段，依据位置、列结构、表头与上下文证据，重组为一张语义完整的逻辑表；随后修复重复表头、断行等瑕疵；最后才基于行列关系（而非页面边界）做结构化切块。每个最终产出的 chunk 都必须自带完整表头、主键标识、计量单位与数据来源，做到任何一个 chunk 被单独检索到，都能脱离原文档独立被理解。

判断表格管道好坏的一条金标准：随机抽出一个 chunk，遮住来源文档，问自己"这行数字的指标名、年份、单位、口径是什么"——答不出来，就是断裂没修干净。

二、页面解析与跨页拼表

全流程分四步走：页面解析 → 跨页拼表 → 结构修复 → 结构化切块。先看总览，再逐个拆解前两步。

两条解析路线

解析路线由文档形态决定。文本型 PDF 有内嵌文本层，字形坐标与边框线段都是精确数据，直接用坐标聚类即可还原单元格；扫描件没有文本层，必须先经 OCR（光学字符识别，把图像中的文字转为带坐标的文本）再做版面分析（layout analysis，用模型检测出页面中的表格、标题、正文等区域），由表格结构识别模型重建行列。关键纪律：无论哪条路线，每个表格片段都必须携带页码、边界框（bbox）、所在章节等元数据——这些是后续续表判断和证据链回溯的全部依据。

表格识别工具对比

选工具的核心问题不是"哪个最强"，而是"哪个能接住跨页"。一份公开的医学文献 PDF 表格提取实测给出了很扎眼的数字：在跨页表格场景下，Camelot 成功率 0%——它把每页识别为独立表格，完全不做跨页处理；pdfplumber 约 70%，需要自己写合并逻辑；PyMuPDF 约 80%，定制能力最强。也就是说，跨页合并几乎总是要自己建的一层，工具只决定你拿到的碎片质量。

值得一提的是模型化路线的进展：MinerU 的合并流程会先统一跨页列数、检测重复表头行，再修复跨页合并单元格的 colspan/rowspan，并识别"（续）"这类续表标记；ChatDOC 开源的 OCRFlux 则直接把"跨页表格合并"立为独立任务，发布了 1000 样本的中英文评测集。这条路线的方向很明确——把续表判断从手写规则升级为端到端模型。

续表判断四要素

续表判断要回答一个问题：上一页底部的表格片段与下一页顶部的表格片段，是不是同一张逻辑表？判断错了两个方向都致命：漏并造成断裂（假阴性），误并把两张独立表拼成一张（假阳性）。工程上稳定的做法是四要素加权评分：

要素检查点权重可量化信号
位置上页表格贴近页底 → 下页表格贴近页顶0.25表格底边距页底距离、顶边距页顶距离
列结构列数 / 列宽 / 各列数据类型一致0.35列数相等、列边界横向重合率、逐列类型一致率
表头重复表头（去重）或无表头（继承）0.25下页首行与上页表头相似度 ≥ 0.9，或首行全为数据型
上下文表名 / 章节 / 统计周期一致0.15同一章节标题下、出现"续表/（续）"、周期字样一致
S = 0.25 × 位置分 + 0.35 × 列结构分 + 0.25 × 表头分 + 0.15 × 上下文分 
def cont_score(a, b):
    s  = 0.25 * pos_score(a, b)     # 上页贴底 → 下页贴顶
    s += 0.35 * col_score(a, b)     # 列数 / 列宽 / 列类型
    s += 0.25 * header_score(a, b)  # 重复表头 or 无表头续页
    s += 0.15 * ctx_score(a, b)     # 章节 / 续表标记 / 统计周期
    return s

权重设计的逻辑：列结构是最硬的证据（两张无关表恰好列数、列宽、类型全同的概率很低），故权重最高；位置是必要不充分条件（续表几乎必然出现在页底页首，但页底页首也可能是巧合）；上下文是辅助佐证。四个分数各自归一化到 0~1，可按语料分布回归微调权重。

置信度阈值与灰区人工复核

评分算出来之后不直接行动，而是按置信度分三档处理：高分档自动合并，低分档果断分开，中间灰区进入人工复核队列。这套"自动 + 灰区兜底"的机制是生产系统敢上线的前提——它把不确定样本从"听天由命"变成"可计量、可消化"的运营成本。

阈值不是拍脑袋定的：上线前用 100~200 张人工标注的跨页表对做标定，画 S 值与合并正确率的关系曲线，取"自动合并正确率 ≥ 99%"对应的分数做上阈值、"误并率 ≥ 5%"对应的分数做下阈值。灰区占比通常落在 5%~10%，按单条 10 秒的人工复核成本计算，一份 5000 表的年报库也就 1~2 小时工作量，换来的是误并率趋近于零。

生产案例：某券商研究所将 217 份上市公司年报（约 4.8 万页、6300 张表，其中跨页表占 34%）接入 RAG 知识库。基线方案按页切分、仅靠文本相似度去重，跨页合并准确率只有 62%——错误中 17% 是相邻独立表被误并、21% 是无表头续页被漏并，数值类问答准确率仅 47%。切换为四要素评分 + 双阈值机制后：合并准确率升至 97.3%，灰区样本占比 6.8%（约 140 条，人工复核平均 11 秒/条），数值类问答准确率升至 89%。

续表判断宁可保守，不可激进：漏并一张表，检索时还有机会靠上下文补救；误并两张表，污染的是入库后的永久数据，且极难被发现——用户只会觉得"答案总是差一点"。

三、结构修复三操作

拼起来的表还是"毛坯"：续页带着重复的表头和页眉页脚，跨页断行把一条记录切成两半，多级表头仍以 colspan 的形态蜷在结构里。结构修复就是三道精加工工序，顺序固定：先去噪，再补行，最后展平——顺序颠倒会互相干扰（比如先展平多级表头会让重复表头的比对基准错位）。

操作触发条件判断依据典型误伤
删除重复表头 / 页眉页脚续页片段首行或页边区域存在冗余文本与首页表头相似度 ≥ 0.9；位于固定页边位置；"第 X 页共 Y 页"等正则模式；"（续）"标记误删真实数据行（如每页都出现的"合计"行）
合并跨页断行上页末行 / 下页首行单元格不完整单元格数少于总列数；行高明显偏矮；纵向位置贴页边；两半文本拼接后语义通顺把两条不同记录强行拼成一行
展开多级表头表头存在 colspan / rowspan 层级上级单元格跨多列（"2024 年"罩住"收入/成本/利润"）展开方向写反，指标与年份错配

操作一：删除重复表头与页眉页脚

规范的长表在每页续排时会重复印刷表头，方便纸质阅读；页眉页脚则承载页码、公司名、密级等信息。这些内容在逻辑表中只应出现一次。识别依据有三层：文本层（与首页表头逐单元格比对，相似度 ≥ 0.9 判重）、位置层（页眉页脚固定在页面上/下边距区域，跨页重复出现）、模式层（正则匹配"第 X 页"、"机密"、"（续表）"等字样）。注意一个反直觉的坑：有些报表的"小计"行也会每页出现，它是真实数据，不能仅凭"重复出现"就删——必须叠加"位于表头区（表格第一行）"的位置约束。

操作二：合并跨页断行

排版引擎在分页时会把放不下一整行的单元格内容推到下一页，形成断行。修复依据是单元格坐标：若上页末行的单元格数少于表列数、且下页首行恰好补足缺额、且两者纵向位置都紧贴页边，则按列对齐把两半合并为一行。合并后要做一次校验：该行的列数等于总列数，且各列数据类型与列定义一致（数值列不出现文字）。对无法确信的断行（比如两半都能独立成行），保留拆分状态并打上待审标记，交给灰区流程处理。

操作三：展开多级表头

财报中常见"年份 → 指标"的两级表头：上层"2024 年"横跨三列，下层是"收入 / 成本 / 利润"。这种结构对纸质阅读友好，对检索与计算却是毒药——"收入"两列并排存在，不带上层限定就无法区分。展开规则是把层级路径压平成复合列名：

2024 年 → [收入, 成本, 利润] ⟶ 2024-收入 | 2024-成本 | 2024-利润

三级表头（年份 → 地区 → 指标）同理递归展开为"2024-华东-收入"。展平后的表变成一维结构，每一列都有全局唯一、自解释的名字，既能直接进 DataFrame 做聚合，也能让行级 chunk 的 KV 表述无歧义。

公开研究验证了结构修复的回报：2026 年发表于 Emerging Science Journal 的一项工作，针对含嵌套表头的复杂表格文档，用 Camelot 高保真提取后做结构感知切块（保留学期、科目、学分、类别等字段关系），在 RAGAS 评测中取得 0.73 的答案准确率，显著高于标准解析 + 常规切块的多个基线。结论很清晰：解析质量与切块策略必须同时过关，表格语义关系才保得住。

结构修复的检验方法只有一个：把修复后的表渲染出来，与原件逐页对照十分钟。任何"看起来自动做对了"的管道，没经过人眼抽检就不算验证过。

四、结构化切块四原则

拿到完整逻辑表之后，切块的目标从"控制长度"变成"保持语义"。四条原则按优先级排列：

原则含义违反后果典型场景
行原子性一行记录是不可再分的最小单元，绝不从行中间切断数值与指标名分离，产生"裸数字"碎片所有表格切块的底线约束
业务分组同部门 / 同产品 / 同地区的行优先落在同一 chunk对比类问题需要跨 chunk 拼数据，召回不全分地区收入表、分产品成本表
列族分割宽表按业务指标族纵向切块（收入族 / 风险族 / 人员族）单 chunk 塞 40 列，embedding 被无关列稀释监管报表、经营月报等超宽表
父子分层超大表建"摘要父块 + 明细子块"两级结构整表塞不进上下文，只存明细又丢全局视角上千行的披露明细表

行原子性与 KV 富化

行原子性是四条原则中唯一没有例外的硬约束。在此基础上，行级 chunk 不应是原始行文本，而要做 KV 富化：把表头语义注入每一行，展开成自解释的陈述。TableRAG 的实验表明，带 schema 富化的行嵌入在检索上稳定优于整表直接嵌入——因为"华东 1250 +18%"这样的向量没有语义锚点，而"地区=华东，收入=1250 万元，同比=+18%"能被"华东收入增长"这类查询稳稳命中。

行 chunk = "表3-分地区收入 | 地区=华东, 收入=1250万元, 同比=+18% | 来源: 2024年报 p.12"

业务分组与列族分割

业务分组利用表内天然的分节信号（小计行、空行、缩进的层级行）把同组数据保持在同一 chunk，使"华东和华南谁增速快"这类组内对比问题一次召回即完整。列族分割针对的是宽表：一张 40 列的经营月报，按"财务指标 / 风险指标 / 人力指标"纵向切成三个 chunk 族，每个 chunk 携带完整主键列（月份、机构）+ 本族指标列。用户问不良率时，检索器只需要命中风险族，不必拖着 30 个无关列一起进上下文。

父子分层

超过一定规模（经验值：50 行以上或 2000 token 以上）的表，单层切块顾此失彼。父子分层给出两级结构：父块存表的摘要——表名、全部列名、行数、时间范围、一句话主题；子块存行组明细。检索时子块负责命中，命中后按需上卷取回父块甚至整表，交给问答层处理。这一机制把"检索粒度"和"回答所需上下文"解耦，是大表场景的标准解。

  • 每个 chunk 注入完整表头、主键、单位、来源页码
  • 用小计行 / 空行等天然分节信号做分组边界
  • 宽表先按业务列族纵切，再按行组横切
  • 大表建父子两级：摘要块定位，明细块命中
  • 切块参数用真实表格语料回归验证后再固化
  • 按固定 token 数对表格做滑窗切割
  • 把 Markdown 表格当普通段落递归切分
  • 行 chunk 只存裸数据，不注入列名与单位
  • 为省存储丢弃"合计 / 小计"等汇总行
  • 整表直接 embedding，指望一个大向量扛所有查询

切块不是把表"剁碎"，而是把表"分装"——每个分装袋上都贴着完整的成分标签（表头、单位、口径、来源），拿走任何一袋都能独立食用。

五、双索引与问答策略

表格问答的查询谱系很宽：从"华东收入是多少"的点查，到"三大事业部收入合计"的聚合，单一索引无法两头兼顾——行级索引粒度细但缺全局，表级索引有全局但定位粗。答案是两套索引并行建设、按问题类型路由。

两条问答路径

简单查询走行级路径：点查与组内对比问题由行级索引直接召回行组，LLM 阅读召回文本作答。行组里已包含表头与单位，回答不需要额外上下文。聚合分析走表级路径：一旦问题涉及求和、均值、排序、多期对比，就不该让 LLM 跨 chunk 读数字做算术——正确做法是表级索引定位整表、取回全量行进入 DataFrame 或 SQL，由计算引擎得出精确结果，LLM 只负责把数字翻译成结论。分工的原则一句话：检索负责找对表，代码负责算对数，模型负责讲清话。

df = load_rows(table_id="T12")          # 表级索引命中后取回全表
ans = (df[df["年度"] == 2024]
         .groupby("事业部")["收入"]
         .sum())                         # 精确聚合，不依赖模型算术
问题类型示例路由计算方式
点查"华东区 2024 收入是多少"行级索引 → 召回行组LLM 直读

生产案例：某股份制银行的财报问答系统中，聚合类问题占总查询量的 38%。早期方案用纯文本 chunk 让 LLM 跨片段读数字做加法，聚合答案错误率高达 41%，错误集中在跨 chunk 漏行与数字误读。切换为双索引 + DataFrame 计算后，聚合错误率降至 3.2%（剩余错误全部来自检索未命中而非计算），平均响应时间从 6.8 秒降到 3.4 秒——模型不再需要通读长表，只消化计算结果。同领域的公开研究也指向同一结论：FinStat2SQL 这类"先结构化入库、再文本转 SQL"的管道，让微调后的 7B 小模型就能在财报问答上取得 61.33% 准确率、响应控制在 4 秒内。

还有一层常被忽略的设计：证据链。表级索引命中时，返回给用户的不应只有答案，还应附"来源文档 + 页码 + 表号"；行级命中时附原文行快照。财务与合规场景里，一个不可回溯的数字答案等于没有答案。

让 LLM 做算术，就像让诗人做审计——不是不努力，是工种不对。聚合永远交给代码，模型只负责把算好的数字讲成人话。

用例集应固化为回归测试：每次调整解析工具、评分权重或阈值后全量重跑，任何一项回退即阻断发布。此外建议每月从生产语料中随机抽 30~50 张表做人眼巡检——自动指标能抓住"断了"，但抓不住"接歪了"。

经验数值：在标注集上，四要素评分的区分度通常很明显——真续表对的 S 值中位数约 0.92，非续表对约 0.45，0.85 / 0.6 的双阈值在两分布之间留出了充足的安全间距。若你的语料上两个分布重叠严重（如大量同模板表格），优先加固列结构分的细粒度（逐列类型 + 列宽重合率），而不是盲目调阈值。

测试跨页管道有个"反向技巧"：专门构造坏输入——故意把两张无关表排成跨页形态、故意删掉续页表头——看管道会不会上当。能被对抗样本打穿的管道，生产语料迟早也会打穿它。

Q&A

为什么不直接把按页切分的表格碎片入库，让大模型在回答时自己拼接？
这条路在工程上走不通，原因有三。其一，检索是概率性的，跨页的两个碎片相似度不同，很可能只召回一半，模型拿到的永远是残缺上下文；其二，即使两个碎片都被召回，模型判断"这两段是否同一张表"仍需重复做续表判断，等于把入库期一次能解决的问题推到每次查询时重复支付成本；其三，碎片化表格的向量质量差，"华北 760 +5%"这类裸数据行根本无法被"华北收入"稳定命中。先拼表后切块是把结构问题一次性解决在离线阶段，让在线检索面对的每个 chunk 都是自解释的完整单元。
两张表列结构完全相同但其实是独立的表，续表判断如何避免误并？
这是续表判断的假阳性难题，靠单一信号无法解决，必须多要素交叉验证。列结构只是四要素之一（权重 0.35），还要看：位置要素——上一张表是否真的贴近页底（若它只占页面上半部分，后面还跟着正文，则几乎不可能续页）；表头要素——下页表若带有完整的新表头和表题，说明是新表；上下文要素——章节标题是否变化、有无"续表"标记。加权评分低于阈值时不合并，落入灰区的由人工裁决。另外可以在用例集中固化"同构相邻独立表"这类对抗样本做回归，确保评分函数对它有足够区分度。
Camelot、pdfplumber、MinerU 之间应该怎么选？
选型的第一问题不是精度，而是跨页与扫描件支持。公开实测显示 Camelot 对跨页表基本无解（每页识别为独立表），它适合文本型 PDF 中带完整边框的规整表格，且可视化调试体验好；pdfplumber 基于字符坐标，容差参数可调，适合金融报表这类复杂版式，但跨页合并要自己写；PyMuPDF 速度快、API 扩展性强，适合需要深度定制的批量管道；MinerU 走版面分析模型路线，有框表用 UNet、无框表用 SLANet+，内置跨页合并与表头去重，扫描件也能处理，适合财报、论文等端到端场景。实践上常见组合：文本页走 pdfplumber/PyMuPDF 定制管道，扫描页与复杂版式走 MinerU 或 Unstructured 的 hi_res 策略。
合并后的完整大表应该作为一个 chunk 整体入库吗？
不应该。整表入库的问题：超过 embedding 模型输入上限时会被截断；即使塞得下，几百行数据算出的向量是所有行的平均语义，点查时相似度反而不高；每次命中都把整表灌进上下文也浪费 token。正确做法是双轨：表级索引存表的摘要信息（表名、字段、时间范围、行数），行级索引存 KV 富化后的行组；大表再叠加父子分层——父块摘要定位、子块明细命中。这样点查走行级、聚合经表级取回全表计算，两种查询各走各的最短路径。
聚合类问题为什么不能直接让 LLM 跨 chunk 读数字计算？
三个原因。第一，召回不保证完整：求和需要的行分散在多个 chunk，检索 top-k 很可能漏掉其中几块，漏行的加法结果是系统性偏低的，且模型无法察觉自己漏了；第二，LLM 的算术不可靠，长表格中跨行读数容易串行、误读小数点与负号；第三，成本与延迟差——让模型通读几千 token 的表格做加法，远不如 DataFrame 一次 groupby。生产数据也支持这一分工：某银行系统将聚合计算从 LLM 转移到 DataFrame 后，聚合错误率从 41% 降到 3.2%，响应时间从 6.8 秒降到 3.4 秒。模型的职责是解释算好的结果，不是执行计算。
扫描件里的跨页表格处理流程有什么不同？
主干流程相同（解析 → 拼表 → 修复 → 切块），差异集中在第一步和误差预算上。扫描件没有文本层，必须先 OCR 加版面分析：表格区域由检测模型框出，行列结构由表格识别模型重建，字符坐标来自 OCR，精度通常在 95%~99%，低于文本型 PDF 的坐标级精度。这带来两个连锁影响：一是列结构对比要放宽容差（OCR 可能把列内文字识别错位），续表评分中的列宽对齐应基于检测框而非字符框；二是断行判断更依赖版面模型的行检测框。工程上建议对扫描件单独标定阈值，并把 OCR 置信度低的单元格标记出来，在灰区复核时优先展示。
置信度的双阈值应该怎么定？灰区人工复核的成本扛得住吗？
阈值要用标注数据标定，而不是拍脑袋：先人工标注 100~200 个跨页表对（含真续表与非续表），计算每对的评分 S，画出 S 与合并正确率的关系。上阈值取"自动合并正确率不低于 99%"的分数点（常见 0.85 左右），下阈值取"误并率升到 5%"的分数点（常见 0.6 左右）。灰区成本是可控的：生产语料上灰区占比一般在 5%~10%，以 5000 张表的年报库为例约 140~300 条待审，单条复核 10~15 秒，总计 1~2 人时。比起误并污染整个知识库后的排查成本，这是极便宜的保险。随着复核数据回流，阈值还可以周期性再标定。
多级表头展开后，原始表格结构信息还需要保留吗？
需要，保留在元数据而非正文里。展开的目的是让每一列获得全局唯一的自解释列名（"2024-华东-收入"），服务于检索与计算；但证据链要求答案能回溯到原件形态，因此逻辑表应同时保存两份表示：展平后的二维结构用于 DataFrame 计算与行级 KV 富化，原始层级结构（含 colspan/rowspan）作为元数据留存，供前端渲染原件样式的引用快照。这样用户追问"这个数在原文哪里"时，系统能展示与纸质文档一致的层级表头视图，而不是一个展平后的工程结构。
