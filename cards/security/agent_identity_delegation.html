SEC15 · Agent 身份与多跳委托

人 → Agent → 子 Agent → 工具 → 资源 / RFC 8693 Token Exchange / scope 真子集衰减 / MCP Gateway 作为 PEP / 短 TTL 与撤销级联

鉴权回答「这张票能不能进门」；委托回答「这张票是谁让谁、替谁、干哪一件具体的事」。Agent 一旦能调工具，缺的不是另一套 OAuth 教程，而是一条会变窄、能追回人、能整链作废的身份链。

MCP Server 怎么配 OAuth、沙箱怎么选、控制面要不要熔断，本库已经有专卡：A15 · MCP Server 生产级鉴权、SEC09 · Agent Sandbox 架构、A67 · AI 控制平面、SEC08 · 跨协议安全。本卡不重复那些平面，只补它们之间那条没人管的轴：身份如何从人传到动作，并且每跳都只能变窄。

一、动作能发生之后，真正的问题是凭谁的名义

聊天机器人答错一句话，丢的是面子。Agent 调错一次付款接口，丢的是钱。差别不在模型更聪明，而在工具调用把「生成文本」变成了「以某张凭据执行副作用」。这时候身份层要回答四个问题，缺一个都会在事故里变成「谁都有理、谁都追不到」：

  1. 发起者是谁：交互用户，还是定时任务那种非人账号？
  2. 当前执行者是谁：编排器、子 Agent，还是某个 MCP Server？
  3. 这一跳被允许做哪一件事：不是「能访问财务系统」，而是 ledger:ListAccounts 这一类操作级 scope。
  4. 出事之后日志里能不能从工具调用走回那个点击「同意」的人？

生产里最常见的失败不是「没做登录」，而是把一把长寿命的 service account 钥匙交给整个 Agent 运行时。模型、子 Agent、被注入的网页内容，共享同一把钥匙。间接注入一旦成功，攻击者用的是合法凭据，ACL 检查全部放行。

层它管什么不管什么
A15 鉴权MCP Server 认不认这张票票是怎么从人衰减到这一跳的
SEC09 沙箱代码跑在哪一类隔离里隔离里的进程持有谁的身份
A67 控制面要不要熔断、限配额熔断时撤销哪一条委托链
本卡 身份谁替谁、跳数、scope 子集、归因工具参数怎么校验（见 A31 / SEC03）

身份不是登录模块的附属功能。它是 Agent 每调用一次工具都要重新计算的授权信封：主体、演员链、受众、过期时间、允许的操作集合。

聊天机器人 vs Agent：爆炸半径差在「凭据会不会被动作复用」 【聊天】用户 → LLM → 文本 凭据停在「调模型」这一跳，答错不触发写操作 【Agent】用户 → 编排器 → 子 Agent → MCP 工具 → 业务 API 若全程复用同一把 SA 钥匙： 注入成功 = 合法调用 = 审计只看见服务账号

二、两轴模型：persona × credential

企业里 MCP 爆发之后，每个团队自己发明一套认证：有的裸奔、有的 API Key、有的上了完整 OAuth。2026 年一篇面向生产部署的 MCP Gateway 论文把现场收成两轴交叉：persona（交互用户 vs 自动化非人）× credential（无认证 / 静态或动态 Key / 授权码+PKCE / client credentials / 平台应用上下文）。同一入口必须同时服务「人在 IDE 里点同意」和「夜间批处理没有人点同意」。

Persona典型流量推荐凭据失败模式
交互用户IDE / 网页 Agent授权码 + PKCE，必要时 Device Code把用户 SSO 令牌原样转发给下游
非人账号Cron、流水线、回调client credentials 或平台应用上下文把 CI 机器人做成「全能财务账号」
用户→服务账号人授权、机器代跑长任务RFC 8693 兑换出 OBO 令牌兑换时不收缩 scope，变成提权

RFC 8693 Token Exchange 的用法是：入口拿用户的 subject_token，Gateway 作为演员，兑出一张新票。新票带 nested act 声明（谁在这条链上演过），受众绑到即将调用的那一个资源，TTL 按秒计而不是按小时计。

新票.scope ⊆ 上一跳.scope ⊆ 用户当初同意的 scope
且 新票.aud = 本跳资源 且 TTL 以秒计

BYOT / GYOT / 完全代兑换三种供票模型可以并存，但下游永远不该看到用户的原始 access token。看见的只能是「这一跳专用」的委托票。

三、多跳委托链与 scope 衰减

单 Agent 调一个只读工具，静态 RBAC 勉强够用。一旦出现「主 Agent 派生子 Agent、子 Agent 再调 MCP、MCP 再打内部 API」，静态授权只回答了签发瞬间，没有回答每一跳是否把权限收窄。记录委托链 ≠ 衰减委托链：nested act 可以写满演员名单，如果每一跳仍拿着「读写财务」的大票，名单只是事后故事，不是控制。

合法链：权限只减不增 人 (scope: ledger.read, ledger.pay, crm.read) │ 兑换：只给编排器 ledger.read + crm.read，TTL 60s ▼ 编排器 │ 兑换：只给调研子 Agent crm.read，TTL 15s ▼ 子 Agent │ 兑换：只给 MCP 工具 crm.ListNotes，TTL 5s ▼ MCP → 资源 非法链（应在兑换点拒绝） 子 Agent 申请 ledger.pay ← 父级没有，直接 403 深度 6 的嵌套兑换 ← 超过策略上限（通常 3–5）
策略要强制的不变量违反时的现象
子集规则子 scope 是父 scope 的真子集或相等中的「更具体操作」子 Agent 比人还能付款
深度上限典型 3–5 跳，再深几乎都是异常扇出委托链变成蠕虫
受众绑定每张票的 aud 只能是本跳资源票被拿到别的 API 重放
发送方约束mTLS 或 DPoP，票不能被抄走重放日志里的票在别的进程里还能用
示例场景：内部助手把「财务只读 SA」配进所有子 Agent。一次间接注入让调研子 Agent 调用了付款工具。因为子 Agent 持有的票和编排器一样宽，PEP 认为合法。审计日志主体是 sa-finance-readonly——名字在撒谎，权限早就不只读了。修复是：付款 scope 只出现在人工确认节点兑换出的 5 秒票上，调研子 Agent 的票里根本没有这个字符串。

衰减必须由基础设施在兑换时计算，不能指望模型「自觉少要权限」。模型要权限的方式是生成工具调用，生成行为不受 RBAC 约束。

四、MCP Gateway 作为唯一 PEP

PEP（Policy Enforcement Point）必须是工具调用的唯一咽喉。Agent 运行时直连几十个 MCP Server，等于每个 Server 自己解释「这张票够不够」——解释口径一散，孤儿控制项就会出现（SEC08 讨论过协议组合里的责任真空）。Gateway 做四件事：验入站票、问策略引擎（常见是 OPA）这次工具调用是否允许、按 RFC 8693 兑出本跳票、把完整演员链写入 trace。

两条网关，不要揉成一个进程里的两摊 if 用户请求 │ ├─ LLM 推理网关（S08）→ 多厂商模型、虚拟钥、语义缓存 │ └─ MCP / 工具网关（本卡）→ 身份兑换、scope 衰减、工具级审计 │ ▼ MCP Server 集群（A15 负责 Server 自己怎么验票）
对象LLM 推理网关MCP 工具网关
保护的资源模型 API 与账单内部系统与副作用
失败默认可降级到小模型 / 只读缓存必须失败关闭，禁止「先做了再审计」
TTL 量级会话或分钟级虚拟钥秒级、单工具

生产上一个可执行的默认：Gateway 兑出的票 TTL 五秒、audience 绑到具体后端、scope 绑到这一次工具名。票即使泄漏，爆破窗口是一次操作、五秒、一个服务。

MCP Server 是资源服务器，不要再让它同时当身份发行方。发行放在 Gateway，Server 只验证「这张票是不是给我的、是不是还活着、操作在不在 scope 里」。

五、撤销级联、深度上限与审计归因

人离职、会话被标为注入、编排器密钥泄漏，这三类事件要求的不是「下次别发新票」，而是已经发出去的子票立刻失效。实现上需要一张委托登记表：父票 ID、子票 ID、深度、过期时间。父节点一撤销，沿边做级联。短 TTL 是第一道；登记表是 TTL 还没到时的第二道。

事件必须发生的动作只做会话踢出不够的原因
用户撤销同意级联所有 act 链上的票子 Agent 可能还拿着 60s 的旧票在跑
注入检出冻结该 session 的兑换入口模型还在同会话里继续生成工具调用
SA 轮转旧 kid 立即拒绝，不等自然过期长任务会把旧票用到结束

审计归因的最低字段：发起用户、每一位 act 演员、工具名、资源 aud、兑换时间、决策（允许/拒绝 + 策略理由）。缺演员链时，事后只能看见服务账号，和第一节的事故同构。

示例场景：将 MCP 直连改成 Gateway 后，工具调用 PEP 命中率从「各 Server 自行判断」变成 100% 过咽喉。一次注入演练里，调研子 Agent 申请 ledger.pay 在兑换点被拒（父 scope 无此值），端到端从「付款接口被合法打到」变为「策略拒绝 + 完整 act 链进 trace」。演练窗口内平均票 TTL 从 12 小时降到 8 秒；误拒绝集中在「工具名与 scope 字符串没对齐」这一类配置债，用工具目录生成 scope 后误拒下降到可忽略。

深度上限不是性能旋钮，是蠕虫刹车。合法业务很少需要五跳以上的身份转发；超过它，优先当成扇出异常而不是「再放宽一点」。

六、落地清单与关闭条件

工具调用只出 Gateway；兑换时强制 scope 子集、aud 绑定、秒级 TTL。

交互流量与非人流量用两套 persona，禁止共用一把全能 SA。

撤销走登记表级联；审计字段固定包含用户 + act 链 + 工具名。

不要把用户 access token 转发给 MCP Server。

不要在 Prompt 里写「请只用只读工具」来代替 scope。

不要让每个 MCP Server 自己发明一套身份语义。

什么时候不要上这套：单用户、单工具、无副作用的本地实验。一旦出现多租户、写操作、子 Agent 或把 MCP 暴露给非信任内容，身份链就从「可选项」变成「事故后唯一能讲清楚的东西」。

落地顺序建议先做「工具调用必须过 Gateway + 禁止转发用户原始 token」，再做秒级 TTL 与登记表级联。前两步已经能挡住最常见的 SA 共用；后两步是事故演练之后才证明有必要的成本。不要一上来上完整 RFC 8693 而 MCP Server 还在裸奔。

Q&A

A15 已经讲了 OAuth，为什么还要单独一张身份卡？
A15 解决的是 MCP Server 如何验证调用方、如何做 RBAC 与字段脱敏，停在「这一跳的门卫」。本卡解决的是门卫拿到的那张票从哪来、经过几个人、每一跳有没有变窄、出事怎么追回点击同意的人。没有委托链，Server 验的是一把被整个运行时共用的 SA，验得再严也挡不住合法凭据上的注入。
记录 nested act 是不是就等于做了最小权限？
不是。act 是叙事，衰减是控制。可以在 JWT 里写满演员而每张票仍携带「读写财务」。最小权限发生在 Token Exchange 的策略计算：子 scope 必须是父 scope 的子集，audience 必须换绑，TTL 必须缩短。基础设施拒绝违规兑换，而不是事后读日志感叹。
为什么 TTL 要到五秒这种量级？
工具调用是瞬时动作。票活过这次调用，就给泄漏和重放留窗口。五秒覆盖一次 RPC 的抖动足够，覆盖不了「子 Agent 拿着票去扫整个网段」。更长的任务用多次兑换或绑定 session 的短票刷新，而不是一张八小时的万能票。
LLM 网关和 MCP 网关能否合并成一个服务？
进程可以部署在一起，职责不能混。模型调用失败可以降级；工具调用失败必须失败关闭。TTL、缓存、重试语义完全相反。混在一个 if/else 里的结果，通常是把工具调用也做成「重试三次」，于是付款被打三次。
非人账号怎么做委托？没有人点同意。
persona 走非人轴：client credentials 或平台应用上下文，签发时就把允许的工具目录写死，并且仍然走 Gateway 兑换出单工具短票。禁止「CI 机器人 = 财务 SA」。人授权的长任务用用户→服务账号的 OBO 兑换，任务结束后级联撤销。
深度上限 3–5 会不会卡合法的多 Agent 业务？
多数生产拓扑是编排器一层、专家一层、工具一层，三跳已经够用。更深往往是递归派生子 Agent。与其放宽深度，不如把「专家调用专家」改成编排器扇出，状态放在中心任务表（见 A47），身份链保持扁平。真要第四跳，用例外名单而不是全局 +1。
什么信号说明该上 Gateway，而不是继续在每个 Server 里加鉴权？
出现以下任一即可：内部 MCP 超过「一个人能记住的认证方式」；有写操作；有子 Agent；有不可信内容进入上下文。这时每个 Server 自建鉴权一定漂移。Gateway 换来的是统一兑换、统一审计、统一撤销，代价是多一跳延迟，通常远小于一次越权事故。
DPoP / mTLS 和短 TTL 还要同时上吗？
短 TTL 减泄漏窗口，发送方约束减重放。只做短 TTL，票在五秒内仍可被另一个进程重放。高风险写操作两条都要；只读内网可以先 TTL。不要用「我们已经 mTLS 了」当理由发八小时票。
