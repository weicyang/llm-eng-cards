SEC07 · Agent 数据安全防护体系

数据脱敏三层防护 / 越权调用防御 / 违规内容防控 / 金融级增强方案

Agent 数据安全的本质，是给一个"概率性大脑"套上"确定性笼子"：模型可以出错，但正则、白名单、权限引擎和审计日志这些确定性组件，必须保证每一次错误的代价都被控制在可接受范围内。

本文边界：本卡是运行时数据安全的工程真源，负责 PII、越权、违规输出和审计；模型如何通过 RLHF / DPO / Constitutional AI 降低有害行为概率，以及 Guardrails 框架如何选型，见 SEC04 · 模型安全与对齐。

一、Agent 数据安全全景

传统聊天机器人最坏的结果是"说错话"，而 Agent 手里拿着真实世界的钥匙——它能查数据库、调客户信息接口、发起业务操作。一旦防线被突破，损失不再是口碑问题，而是真金白银的泄露与违规。行业的部署速度已经跑在了安全治理前面：

生产现状（Gravitee 对 900+ 企业技术决策者的调研）：80.9% 的技术团队已进入 AI Agent 测试或生产部署阶段，但仅 14.4% 的组织在 Agent 上线前拿到了完整安全审批；88% 的组织在过去一年确认或怀疑发生过 Agent 安全事件；更扎眼的是，45.6% 的团队仍用共享 API Key 为 Agent 调用做认证，仅 47.1% 的 Agent 被主动监控。非人类身份（NHI）与人类身份的比例已达 50:1，传统 IAM 体系"登录时一次性授权"的假设在 Agent 场景全面失效。

Agent 场景下的数据安全风险可以收敛为三类，分别对应数据流的三个关口：PII（Personally Identifiable Information，个人可识别信息，如手机号、身份证号、银行卡号）在输入端被送进模型，是隐私泄露的源头；工具调用发生在推理过程中，是越权访问的通道；生成内容在输出端返回用户，是违规输出的出口。三关各有一道核心防线，合起来就是后文的主线。

威胁类型典型场景主要危害核心防线
隐私泄露用户把完整身份证号贴进对话框；模型复述出其他客户的手机号合规处罚、客户信任崩塌输入/输出双向脱敏
越权访问销售 Agent 被诱导查询非本人负责的客户档案批量数据外泄、商业损失工具白名单 + 行级权限隔离
违规输出Agent 输出未公开报价、虚假营销话术、内部机密监管风险、商誉受损提示词约束 + 内容审核 + 黑名单

Agent 之所以比传统应用危险，还有一个结构性原因：权限继承。以 MCP 协议为例，其默认授权模型是"全有或全无"的——一个通过认证的连接就能访问服务端暴露的全部工具，Agent 会默认继承宿主应用的完整权限集。这就制造了困惑代理人问题（Confused Deputy）：Agent 本身持有合法凭证，攻击者不需要偷钥匙，只需要通过提示注入"指挥"拿着钥匙的 Agent 去开错误的门。OWASP 发布的 Agentic 应用十大风险将其归类为 ASI03（身份与权限滥用），并把"缺少可观测性与审计轨迹"单列为 ASI10——两者一个管"事前拦不住"，一个管"事后查不清"。

Agent 数据流三关 · 纵深防御全景 用户 ──→ 【第一关 · 输入】 ──→ 【第二关 · 访问】 ──→ 【第三关 · 输出】 ──→ 用户 │ │ │ 前后端双重正则 动态权限校验 二次扫描 PII 脱敏 会话关联数据 规则库拦截 （手机号/身份证/ 行级过滤注入 违规内容审核 银行卡/地址） 人工复核开关 关键词黑名单 │ │ │ ▼ ▼ ▼ 入口拦得住 取数拿得少 出口带不走 ───────────────────────────────────────────────────────────────── 【全链路审计】会话ID / 操作人 / 参数 / 决策 —— 贯穿三关 实时拦截是下限，事后追溯是底线

三关之上再叠一层审计，构成纵深防御（Defense in Depth）：每一层都不指望拦住所有攻击，而是让攻击者每前进一格都要突破一种不同机制。正则拦不住的，权限层兜底；权限层漏掉的，输出扫描补刀；全都漏掉的，审计日志保证能查出来、能定责。后文四节依次展开三关的技术细节，第五节讲金融政务场景如何在此骨架上加装增强件。

单层防御一定会被绕过，这不是悲观而是工程事实——安全体系的价值不在于任何一道墙有多厚，而在于攻击者每突破一层留下的痕迹越来越多、成本越来越高。

二、数据脱敏三层防护

脱敏体系沿着数据流布设三道关卡：输入层在数据进入模型前拦截，访问权限层在模型取数时约束范围，输出层在结果返回用户前二次扫描。三层各司其职，缺任何一层都有明确的泄漏路径。本节统一维护字段策略、误杀指标与占位符还原等工程细节；内容安全等级为何这样划分，见 SEC04 第四节。

2.1 输入层：前后端双重正则拦截

输入层采用前后端双重正则匹配。前端负责体验：用户粘贴手机号的瞬间就替换为 138****5678，即时反馈、避免误操作。但前端拦截只是"提醒"而非"保障"——攻击者可以绕过页面直接调用 API，浏览器插件、脚本同样能篡改请求。因此后端必须用同一套甚至更严格的规则再扫一遍，双重校验是纵深而不是冗余。

敏感字段被识别后直接替换为格式保留脱敏结果（Format-Preserving Masking，掩码后长度与结构不变，如 11 位手机号仍是 11 位），确保原始数据不会完整传输至大模型。四类高频敏感字段的识别要点如下：

字段类型正则要点校验增强主要误杀来源
手机号1[3-9]\d{9} 加 \b 边界上下文锚点（"电话""联系"）订单号、资产编号等 11 位数字串
身份证号18 位：前 17 位数字 + 末位数字/XISO 7064 MOD 11-2 校验位 + 行政区划码 + 出生日期合法性极少（校验位抗误报能力强）

详细地址无固定格式，正则能力有限NER 模型 + 上下文线索易漏报，需语义层补充

正则的固有短板是"只认形状不认真假"：一个匹配 11 位数字的模式，无法区分手机号和恰好同形的订单号。解法之一是校验位（Check Digit）验证——绝大多数国家级、金融级标识符都内置了数学自检机制，正则负责圈出"可能是标识符"的候选，校验位负责裁决"它真的是"。以身份证为例，GB 11643 规定前 17 位按固定权重加权求和、对 11 取模后映射出第 18 位校验码：

W = [7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]   # GB 11643 固定权重
M = "10X98765432"                            # 校验码映射表
def id_card_valid(s):
    if len(s) != 18 or not s[:17].isdigit():
        return False
    total = sum(int(c) * w for c, w in zip(s[:17], W))
    return M[total % 11] == s[-1].upper()

但校验位只能压低误杀、不能消灭误杀——随机数字串通过 Luhn 的概率约为十分之一。更深的短板在无结构 PII：姓名、散文式地址没有任何"形状"可匹配。生产级的检测引擎因此普遍采用级联架构：正则在每个字节上跑（结构化数据召回率可达 96–99%，亚毫秒延迟），正则没覆盖的文本交给命名实体识别（NER，Named Entity Recognition，用模型标注 PERSON/LOCATION 等实体）补位，把无结构 PII 的召回率从正则的 50–65% 拉到 92–96%，代价是 15–40ms 延迟；只有高风险样本（上传文档、跨租户检索结果）才升级到小型守卫模型做上下文裁决。纯规则方案在 LLM 场景的处境有研究给出了量化参照：传统基于规则的 DLP 误报率可达 40% 以上，而"正则 + 上下文 NER + 语义匹配"的组合能把误报压到 12% 以内。2026 年 OpenAI 开源的 Privacy Filter 正是这条路线的产品化——15 亿参数（激活约 5000 万）的小模型、支持 128k 上下文、单次前向标注 8 类 PII，且可本地部署让 PII 不出域。

生产案例（误杀权衡）：某股份制银行信用卡客服 Agent 上线初期，手机号正则的误杀率高达 4.7%——大量 11 位订单编号被误判脱敏，导致客服答非所问、工单回流。团队随后叠加 Luhn 校验、BIN 前缀白名单与"卡号/还款"上下文锚点三重验证，误杀率降至 0.6%，同时保持隐私泄露事件为零。经验：脱敏系统的 KPI 必须同时盯"漏报"与"误杀"，只盯一个必然在另一个上翻车。
研究数据（SafeGPT，arXiv 2026）：这个"输入侧检测脱敏 + 输出侧审核改写 + 人工反馈回路"的双侧护栏系统，在企业场景实测精度 92%、召回 87%、误报率低于 12%，对照组传统 DLP 精度仅 68%、误报率 24%；其输出过滤器修复了 84% 的违规输出，人工反馈回路让误报率每月再降 34%。端到端测试中，有护栏组实现零泄漏、合规率 91%，无护栏组则出现 23 起泄漏事件、合规率仅 47%。数字说明两件事：双侧防护的收益是数量级的；误报率必须靠反馈回路持续压降，不存在一次调优到位。

2.2 访问权限层：动态校验与会话关联

脱敏管住的是"用户喂进来的数据"，但 Agent 更多时候是主动"去取数据"——查数据库、调客户信息接口。这一层的核心机制是动态权限校验：权限不在登录时一次性发放，而是在每次取数时实时裁决。具体落地为会话关联——每个会话绑定明确的客户上下文（会话 ID ↔ 客户 ID ↔ 操作人），数据库与客户信息接口在查询时强制注入行级过滤条件，Agent 仅能访问当前会话关联的客户数据。即使模型被诱导生成了一条针对其他客户的查询，数据层也会因"该客户不在当前会话授权范围"而直接拒绝。

动态校验相比静态授权的关键优势在于上下文感知：同一个 Agent、同一个工具，在会话 A 里能查客户 C001，切到会话 B 就只能查 C002。权限随会话生灭，不存在"一次授权、长期有效"的凭证被滥用的窗口。金融、政务类场景还会在此层额外挂载人工复核开关——高风险取数与变更操作先经人工确认再放行，脱敏规则集也支持不停机热更新，细节见第五节。

2.3 输出层：二次扫描与规则库

有人会觉得输入层已经脱敏了，输出层再扫一遍是浪费。实际上输出层有输入层管不到的三条泄漏路径：其一，RAG 检索注入——模型从知识库取回的文档里可能带着别的客户的联系方式；其二，模型记忆——训练语料中的 PII 可能被特定提示"背"出来；其三，多轮拼接——两轮对话各说半个卡号，单看都合规，拼起来就是完整卡号。因此模型返回内容必须二次扫描，检测到完整隐私信息立即拦截展示。

工程上通常维护一套敏感信息拦截规则库，对金融账号等关键字段实施强制过滤，规则库版本化、可热更新。若业务需要把真实值回显给用户（例如客服确认后回拨电话），则采用占位符还原方案：入站时把真实值替换为 <PHONE_1> 类占位符，原始值与占位符的映射加密存储在 Redis 等外部存储中，出站审核通过后再按映射还原。流式输出是这一层的工程难点：逐 token 审不现实，全量审又破坏流式体验，常见折中是按句/按段缓冲审核，高风险场景宁可牺牲流式也要先审后回。

三层脱敏的分工可以记成一句话：输入层防"用户把秘密说出去"，权限层防"模型把别人的秘密拿进来"，输出层防"模型把任何秘密带出门"。

三、越权调用防御

如果说脱敏管的是"数据内容"，越权防御管的就是"动作资格"。Agent 的每次工具调用都要回答三个问题：它有没有资格调这个工具？它有没有资格看这批数据？这次调用该不该留下证据？对应的机制依次是白名单、数据可见范围、全链路日志。

3.1 工具白名单：默认拒绝

白名单机制遵循默认拒绝（Default-Deny）原则：每个 Agent 绑定一份可调用工具清单，清单之外的工具即使被模型生成了调用指令，也会在网关层被阻断，根本到不了工具服务端。这与黑名单"列举禁止项"的思路相反——黑名单永远列不全，白名单只需要守住边界。业界实践表明，仅有工具级白名单还不够，完整的权限执行是分四层递进的，AWS 基于 Cedar 策略语言的参考实现给出了清晰范本：

执行层校验内容拦截位置解决的问题
工具白名单该 Agent 能否调这个工具（信任分、命名空间、生命周期阶段）网关层收敛"全表面继承"，限制爆炸半径
逐操作授权这次具体操作（读/写/删）是否允许调用前审批同一工具不同动作风险不同
委派链校验多 Agent 委派跳数是否超限（硬上限 5 跳）、子任务是否为目标 Agent 注册能力的子集策略引擎防权限沿委派链放大
发起者回溯回溯校验发起链路的人类用户角色与 MFA 状态令牌校验防长期凭证被盗用、防横向越权

四层校验按序执行、任何一层拒绝即整体终止——这正是最小权限原则在链式场景的落地：每个节点在每一时刻只持有完成当前任务所必需的权限，一分不多。

3.2 数据可见范围：销售类 Agent 的行级隔离

白名单回答"能不能调工具"，数据可见范围回答"调了能看到什么"。典型场景是销售类 Agent：即便 query_customer 在白名单内，也不意味着销售能查全公司的客户。落地方式是在参数层注入强制过滤——查询条件必须携带 owner_id = 当前操作人，由数据层执行而非信任模型自觉。模型生成的任何绕过尝试（显式指定他人客户 ID、拼接 SQL 片段）都会在参数校验或行级权限处被拦下。工具白名单限动作，行级过滤限数据，两者叠加才能封死"合法工具 + 非法目标"的横向越权路径。

3.3 全链路日志：审计追溯与异常告警

每次工具调用必须记录完整日志。OWASP 对 Agentic 应用的建议给出了最小字段集：以结构化 JSON 记录Agent ID、工具名、查询参数、执行结果、耗时、时间戳，并关联会话 ID 与操作人。更进一步的做法是语义级审计——不仅记录"调用了什么"，还记录 Agent 的意图与选择该工具的推理理由，让事后审计能还原"为什么调"，而不只是一串无意义的 API 流水。日志本身要防篡改：采用追加写入（append-only）加哈希链，或 WORM（Write Once Read Many）存储；SOC 2 等合规框架通常要求至少 12 个月的日志留存作为审计证据。

在日志之上做实时监测：为每个 Agent 建立行为基线（调用频率、常见参数分布、活跃时段），偏离基线的模式——例如 1 分钟内遍历式查询上百客户、非工作时段的批量导出——触发告警乃至自动熔断。治理层面还应配置经定期演练的"紧急停止"能力，保证异常 Agent 能在分钟级被下线。告警不是终点，每条告警都要能一键回溯到完整会话上下文，这才是"支持事后审计追溯"的完整含义。

生产案例（白名单 + 审计）：某 CRM SaaS 厂商为销售 Agent 上线工具白名单与行级数据过滤后，首月即阻断 17 次越权调用尝试，其中 2 次被事后复盘确认为检索文档中的提示注入诱导——若按旧的"宿主应用全权限继承"模式，这两次都会直接命中生产客户库。同期，全链路日志把一起客户数据争议排查的定责时间从约 2 天压缩到 15 分钟：凭会话 ID 即可拉出完整调用链、参数快照与授权决策记录。

白名单决定 Agent"能做什么"，数据范围决定它"能看什么"，审计日志决定出事时"能不能查清"——前两者降低事故概率，第三者决定事故代价，一个都不能省。

四、违规内容防控体系

隐私与越权管的是数据，违规内容管的是"话"。虚假营销、泄露内部机密、输出未公开报价，任何一条落到客户或监管眼里都是事故。防控体系按三道闸串联：预置约束层减少违规生成，实时审核层拦截违规出境，业务规则层兜住行业特定的红线词。

4.1 预置约束层：系统提示词硬约束

第一道闸成本最低：在系统提示词中硬性声明禁止输出虚假营销、内部机密等内容，并给出拒答模板。但要清醒——提示词约束是概率性的，模型在长上下文、多轮诱导、角色扮演攻击下仍可能越界。它的定位是"让违规更少被生成"，而不是安全边界，绝不能作为唯一防线。工程上的正确姿势是把约束写得具体可判定（列出类别 + 示例 + 拒答话术），而不是堆砌"请注意安全"这类模糊指令。可编程 Guardrails 与 Prompt 规则的完整差异见 SEC04 第五节。

4.2 实时审核层：内容安全 API 先审后回

第二道闸是接入内容安全 API：模型输出先经审核分类器裁决，确认安全后再返回用户。Safe / Caution / Blocked / Critical 等策略等级统一见 SEC04 第四节；本节只负责检测器选型、阈值和出站执行。选型上有一条明确的性价比结论——专用安全分类器显著优于"拿通用大模型当裁判"：

生产基准（BELLS-O，ICML 2026 Workshop）：这项覆盖 17 家供应商 28 个监督系统的独立运营基准显示，内容审核任务上头部专用防护系统（LlamaGuard-4、ShieldGemma-2、Lakera Guard）检测率约 95%，与前沿大模型的 94% 持平，误报率同样 ≤2%，但平均延迟仅 30–45ms（快 5–10 倍），每千 token 成本约为后者的十分之一。越狱检测任务的权衡则反转：前沿大模型检测率更高、误报更低，但成本高 10–50 倍、延迟高 5–10 倍。结论：日常内容审核用小而专的分类器，越狱防御按预算与风险等级决定叠加大模型。

流式输出是审核层的工程难点：逐 token 审不现实，全量审又破坏流式体验。常见折中是分段缓冲审核（按句/按段放行）或"先流式后抽审"，金融等高风险场景则宁可牺牲流式也要先审后回。误报率（False Positive，把正常内容误判为违规）在这一层是核心运营指标：一个每三次合法请求就拒一次的审核器不是护栏而是故障，业界经验是把误报压到 2% 以内才可接受，并按内容类别分别设定阈值——过度拦截营销咨询损失的是转化，漏放违规承诺招来的是监管。

4.3 业务规则层：行业关键词黑名单

第三道闸面向行业特定红线：配置未公开报价、核心技术参数等关键词黑名单，命中后立即终止任务并记录异常会话，用于后续规则优化与复盘。黑名单词典要版本化管理、支持热更新——业务红线变化很快（比如某款产品发布前其代号就是禁词）。需要注意的是谐音、拆字、符号间隔等变体绕过，因此黑名单只做确定性兜底，变体识别交给第二道闸的语义分类器，两层互补而非替代。

防线机制生效位置延迟局限
系统提示词硬约束指令约束模型生成生成前≈0概率性，可被注入绕过

三道闸的容错逻辑：闸一降低违规"出生率"，闸二拦截违规"出境"，闸三对行业红线"一票否决"——模型越不可控，越要把确定性规则往后放。

五、技术实现与增强防护

前四节拆开讲了每道防线，这一节把它们装回去：正则、权限、日志、审核四类技术如何组合成一个整体，实时拦截与事后追溯两种能力如何互相喂养，金融政务等高合规场景又需要加装哪些增强件。

5.1 组合技术栈：各司其职，互为兜底

组合的价值不在于任何单一技术有多强，而在于确定性与概率性机制的分工：正则、白名单、行级过滤、黑名单是确定性裁决，说拦就拦，没有"大概率"；NER、守卫模型、审核分类器是概率性识别，负责把确定性规则够不着的语义空间补上。概率性组件的输出永远只用于"拦截或升级人工"，不用于"放行"——放行由确定性规则背书，这是整套体系不因模型出错而崩盘的底层逻辑。

5.2 实时拦截与事后追溯：双能力闭环

请求流（输入 / 工具调用 / 输出） │ ┌───────────────┴───────────────┐ ▼ ▼ 【实时路 · 拦截】 【追溯路 · 审计】 正则 / 白名单 / 权限 / 全量结构化日志 审核 API —— 毫秒级裁决 （会话ID/操作人/参数/ 命中 → 阻断 / 改写 / 告警 结果/耗时/决策） │ │ ▼ ▼ 违规到不了用户 哈希链防篡改 · 长期留存 基线偏离 → 异常告警 一键回溯完整会话上下文 ──────────────────────────────────────────────────────────── 两路共用同一套判定标准，并互相喂养： 追溯路复盘出的漏拦样本 → 反哺实时路的规则与模型 实时路积累的误报案例 → 校准追溯路的告警阈值

只有实时拦截没有追溯，出了事无法定责、无法举证，监管检查时更说不清"你如何知道系统在受控运行"；只有追溯没有拦截，等于把每一单事故都变成既定损失。双能力闭环的关键动作是定期复盘：把追溯路发现的漏拦样本报给实时路补规则，把实时路的误报案例拿来校准告警阈值——安全体系不是部署出来的，是运营出来的。

5.3 金融政务增强：人工复核与特殊规则

金融、政务场景的合规要求显著高于通用场景：泄露一次客户账户信息的代价可能是监管处罚加牌照风险。在通用骨架之上，这类场景需要加装四类增强件。

Q&A

输入层已经脱敏了，为什么输出层还要二次扫描？
因为输入层只管"用户喂进来的"，而输出端至少有三条输入层管不到的泄漏路径：一是 RAG 检索注入，模型从知识库取回的文档可能带着其他客户的联系方式；二是模型记忆，训练语料中的 PII 可能被特定提示"背"出来；三是多轮拼接，两轮对话各说半个卡号，单看都合规、拼起来就是完整卡号。所以输出必须重跑一遍规则库再返回用户——这不是冗余，而是覆盖不同泄漏面的独立关卡。
正则与识别模型结合时，误杀和漏检的权衡怎么处理？
正则对结构化数据能做到 96–99% 召回且亚毫秒完成，但对姓名、地址这类无结构 PII 召回率只有 50–65%；NER 模型能把这部分拉到 92–96%，代价是 15–40ms 延迟和 5–15% 的生产误报率。生产答案是级联：正则全量跑、NER 补位、守卫模型只裁决高风险样本，让多数请求在第一层就提前退出。误报则靠反馈回路持续压降——SafeGPT 的实测是人工反馈让误报率每月下降 34%。核心认知：召回目标定得越高，越要准备为误报付出审核成本，两个指标必须同时上仪表盘。
工具白名单为什么比黑名单可靠？
黑名单的思路是"列举禁止项"，但禁止项永远列不全——新工具、新参数组合不断出现，任何遗漏都是缺口。白名单的思路是"列举允许项"，默认拒绝：每个 Agent 绑定可调用工具清单，清单外的工具即使被模型生成了调用指令，也会在网关层被阻断，根本到不了工具服务端。边界是有限的、可验证的，这正是最小权限原则在 Agent 上的落地——每个节点每一刻只持有完成当前任务所必需的权限。
动态权限校验与传统登录时授权有什么本质区别？
传统 RBAC 在登录时一次性发放权限，凭证长期有效，被盗用或滥用的窗口很大。动态校验则在每次取数时实时裁决：会话绑定客户上下文（会话 ID ↔ 客户 ID ↔ 操作人），数据库查询强制注入行级过滤条件，Agent 只能触碰当前会话关联的数据。权限随会话生灭，同一个 Agent 在会话 A 能查 C001、切到会话 B 就只能查 C002，不存在"一次授权、长期有效"的滥用窗口。即使模型被诱导生成针对其他客户的查询，数据层也会直接拒绝。
内容安全审核层，选专用分类器还是通用大模型？
BELLS-O 基准（17 家供应商、28 个系统）给出的结论很明确：内容审核任务上，头部专用护栏（LlamaGuard-4、ShieldGemma-2、Lakera Guard 等）检测率约 95%，与前沿大模型 94% 持平、误报率同样 ≤2%，但延迟仅 30–45ms（快 5–10 倍）、每千 token 成本约为后者的十分之一——日常审核用小而专的分类器是压倒性选择。但在越狱检测上权衡反转：前沿大模型检测率更高、误报更低，代价是成本高 10–50 倍、延迟高 5–10 倍，适合按预算在高风险面上叠加，而不是全量铺开。
为什么系统提示词的安全约束不能算安全边界？
因为提示词约束是概率性的：模型在长上下文、多轮诱导、角色扮演攻击、检索内容携带注入指令等情况下仍可能越界，它只能降低违规内容被生成的概率，无法保证零违规。真正的安全边界必须由确定性组件承担——审核 API、关键词黑名单、权限引擎，它们的裁决不依赖模型"自觉"。正确的定位是：提示词约束是第一道便宜但不保险的闸，让后两道闸的压力变小；把它当唯一防线，等于把安全寄托在模型的概率行为上。框架层如何把安全规则变成可测试的强制 Rails，见 SEC04 · Guardrails 框架。
落地一套 Agent 数据安全防护体系，应该从哪里开始？
按五步路线推进：先摸底盘点，产出敏感字段清单与工具清单，形成风险台账；再上输入输出脱敏（双重正则 + 校验位 + 输出二次扫描，目标误杀率 <1%）；然后建白名单与审计（工具层默认拒绝 + 行级数据过滤 + 全链路日志，目标越权调用 100% 阻断可追溯）；接着补内容防控（提示词约束 + 审核 API + 行业黑名单，目标拦截率 ≥95%、误报 ≤2%）；最后金融政务场景加装人工复核开关、规则热更新与数据不出域。原则是"先收口、再精检、后兜底"——动作面没收敛之前，检测和审计的投入都会被旁路稀释。
Agent 数据安全和模型安全与对齐是什么关系？
二者不是替代关系。模型对齐通过安全训练和红队评估降低模型做错事的概率；Agent 数据安全假设模型仍可能出错，用脱敏、权限、审核和审计限制错误的实际代价。模型侧方法、发布门禁与 Guardrails 框架见 SEC04 · 模型安全与对齐，本卡负责这些策略在运行时数据流上的确定性落地。
