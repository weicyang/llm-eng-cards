一、工具调用安全威胁全景

Function Calling 和 MCP 赋予了 LLM 与外部系统交互的能力。这既是 Agent 的核心能力，也是最大的安全风险点——一旦被攻破，攻击者可以直接操控真实世界的系统。

核心原则：永远不要信任 LLM 的工具调用决策。LLM 是概率模型，不是安全边界——它的每一个工具调用请求都必须经过独立的权限校验、参数验证和安全审计。

二、FC / MCP 权限管控

权限校验必须挂在执行入口，而不是挂在工具清单上。给模型看什么工具属于提示层约束——它只降低误调概率；真正决定能不能执行的是调用发生那一刻的独立鉴权。把"没告诉模型这个工具存在"当成权限控制，等于把安全性寄托在攻击者猜不到工具名上。

权限管控是安全架构的基石，核心思想：最小权限 + 动态授权。

每个 MCP Server 都是外部信任边界，应被视为"不完全可信"。安全攻击面比 FC 更大——除了应用层安全，还需要 Server 身份认证、供应链安全、通信加密。

三、执行隔离边界

涉及代码执行、文件操作或网络请求的工具必须进入独立执行边界。调用侧只负责三件事：执行前完成权限与参数预检查，执行后验证结果格式与安全性，并把完整证据交给审计链路。运行时隔离强度不能用“Docker 即安全”简化判断——普通容器共享宿主内核，不是任意不可信代码的完整安全边界。

工具调用与 Sandbox 的职责交界： SEC03 调用路径：权限校验 → 参数校验 → 结构化执行请求 │ ▼ SEC09 执行边界：运行时隔离 → 出口/凭证裁决 → 产出验证 │ ▼ SEC03 审计路径：结果校验 → 调用日志 → 异常检测
运行时选择、默认拒绝网络、只读工作区、seccomp、资源上限、一次性环境与快照恢复的权威说明见 SEC09 四平面、运行时选型和出口与凭证。

四、参数校验与注入防御

参数校验的门槛不是"看起来像不像攻击"，而是"符不符合这个字段本来允许的形状"。白名单 Schema 先把取值空间压到极小，注入特征库只是兜底——顺序反过来，你就永远在追着新的绕过写正则。

LLM 生成的工具参数是不可信输入，可能包含注入攻击载荷。必须多层防御。

示例场景：一个数据分析助手开放了"按条件查询订单表"的工具，参数是一段由模型生成的 SQL WHERE 子句，服务端做了关键词黑名单，拦 DROP、DELETE、UNION。问题：一次红队测试里，攻击者在上传的 CSV 备注列埋了一句指令，诱导模型生成带 OR 1=1 的条件；这个载荷不含任何黑名单关键词，顺利通过校验，单次查询把 47 万行订单全量返回并进入模型上下文，随后被要求"总结成表格发到指定邮箱"。整条链路的每一步在日志里都是"成功"。方案：取消自由文本 SQL，工具参数改成结构化字段（字段名走枚举、操作符走枚举、值走类型校验），服务端用参数化查询拼装；同时给查询工具加返回行数上限 1000 行，超限直接截断并标记；外发类工具（邮件、Webhook）与读取类工具之间加链式升级检测。效果：同一批 12 个绕过用例在结构化改造后全部被 Schema 层拒绝，无需依赖特征库；即便后续出现新的绕过手法，单次泄露面也被行数上限压在 1000 行以内。

五、工具链路审计与监控

工具调用审计和普通接口日志的关键差别在于要记"为什么"。同一个删除调用，来自用户明确指令还是来自检索文档里的一句话，安全含义完全不同，而这个区别只存在于当时的上下文里。不落决策依据，事后你只能看到一串合法调用，永远复盘不出攻击是从哪一环进来的。

完整的审计是安全事件的"黑匣子"——事后追溯 + 日常异常检测。

5.1 审计日志四层信息

信息层记录内容用途
用户层user_id / session_id / 原始请求谁发起了什么请求
推理层LLM reasoning / 完整 Prompt 上下文为什么决定调用这个工具
调用层工具名 / 参数 / 结果 / 耗时实际执行了什么
安全层权限检查 / 参数验证 / 异常分数安全校验结果

5.2 六类异常模式检测

示例场景：一个运维 Agent 接了 18 个工具，其中包含重启服务和清理磁盘两个写操作，审计只记录了工具名、参数和返回码。问题：某次夜间出现一批异常的清理调用，删掉了一个业务目录。复盘时发现日志里这些调用全部权限合法、参数合法、返回成功，看不出任何异常；由于没有记录当时的调用链上下文，团队花了 6 小时逐条比对会话记录，才定位到是一份被改过的运行手册文档被检索进上下文，里面写着"如遇磁盘告警请清理该目录"。方案：审计补齐推理层字段（触发本次调用的上下文片段摘要、来源标记、模型给出的理由），并对"外部文档触发的写操作"单独打标；再加一条会话级规则，读取类调用密集之后紧跟外发或删除类调用时触发人工确认。效果：定位同类问题的时间从 6 小时降到 15 分钟以内，因为日志里直接能看到"这次删除的依据来自外部文档"；上线后的两个月内该规则拦下 3 次由文档内容触发的写操作，均确认为误触发并修正了文档。

5.3 危险操作风险分级

操作风险应按可逆性与目标资源判定：查询可自动执行，创建/写入必须限域并留痕，删除、发送、支付和生产部署必须人工确认；极高风险场景再叠加 MFA 与不可逆警告。完整审批流、超时默认拒绝和 break-glass 留痕见 SEC09 第四节。

LLM 可以建议操作，但不能自主执行高风险操作。关键原则：确认信息必须展示操作详情和潜在影响，让用户做出知情决策。

Q&A

FC 和 MCP 工具调用的安全区别是什么？

FC 是 LLM 内置的工具调用机制，安全边界在应用层（参数校验、权限检查）。MCP 引入了独立的 Server 概念，安全挑战更复杂：①Server 身份认证（OAuth/mTLS）；②供应链攻击风险（第三方 Server）；③通信安全（加密+签名）；④能力管理（Server 声明需安全消费）。MCP 的攻击面比 FC 更大，因为引入了独立的信任边界。

如何防止 LLM 被诱导调用危险工具？

多层防御：①工具集最小化——根据任务和角色动态提供最小工具集；②权限校验——每次调用独立校验，不信任 LLM 的决策；③参数校验——白名单 Schema + 注入检测；④危险操作门控——高风险操作必须人工确认；⑤行为监控——检测异常调用模式（如从只读快速升级到写入）。核心原则：LLM 的决策只是"建议"，不是"授权"。

MCP Server 的供应链安全如何保障？

六项措施：①Server 白名单——只允许审核过的 Server 接入；②签名验证——发布时签名，加载时验证完整性；③能力声明审核——安全团队审核 Server 声明的能力；④版本管理——更新时安全扫描+回归测试；⑤运行时监控——实际行为与声明一致；⑥隔离执行——每个 Server 在独立沙箱运行。类比 npm/Docker 供应链安全——信任但验证。

沙箱执行如何设计？

调用侧应在执行前完成权限和参数校验、执行后验证输出并记录审计；真正的隔离设计还要同时决定运行时边界、网络出口、凭证注入、工作区生命周期和发布验证。普通 Docker 容器不能单独作为不可信代码的安全边界，完整选型与参考架构见 SEC09 · Agent Sandbox 架构详解。

如何审计 Agent 的工具调用链路？

记录四层信息：①用户层（who + session）；②推理层（LLM reasoning + Prompt 上下文）；③调用层（工具名、参数、结果、耗时）；④安全层（权限检查、参数验证、异常分数）。审计日志必须不可篡改（append-only + 哈希链）。异常检测：建立行为基线，检测偏离（高频调用、参数异常、链式升级）。关键：审计不仅事后追溯，也要实时告警。

危险操作要人工确认，但这会拖慢 Agent。哪些该拦、哪些该放？

判断标准是可逆性和爆炸半径，而不是操作听起来危不危险。可逆且影响可控的操作直接放行——查询、生成草稿、写入带版本的临时区域，出错了回退一下就行，为它们加确认只会训练用户闭眼点"同意"，反而毁掉确认机制本身的价值。不可逆或影响外溢的操作必须拦：删除、发送给外部收件人、支付、生产环境部署、修改权限配置，这几类的共同点是一旦执行就无法靠系统内部动作撤销。中间地带用限域代替确认更划算，比如写操作限定在指定命名空间内、批量操作设条数上限、超出范围才升级为确认。还有两点常被忽略：一是确认框必须展示具体做什么、影响多少条记录，只写"是否继续"等于没确认；二是确认要有超时且超时默认拒绝，否则挂起的审批会变成绕过点。工程上建议把这套判定写成工具注册时的元数据字段，而不是散落在业务代码里的 if 判断，这样新增工具时会被强制回答"这个操作可逆吗"。
