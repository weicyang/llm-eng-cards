HC10 · Claude Code 入门指南

环境搭建 → 基础交互 → 复杂任务处理 → 终端控制 → MCP/Skill/Hook/图片/上下文处理/后台任务

Claude Code 不是"帮你写代码的 AI"，而是一个住在你终端里的编程智能体——它自己读文件、自己跑命令、自己派子代理、自己管理记忆，你要做的是定义目标和握好权限刹车。

一、环境搭建与登录

Claude Code 是 Anthropic 推出的终端式 Agentic Coding（智能体编程，AI 自主规划并执行任务、而非仅提供代码建议的编程范式）工具，2025 年 2 月以研究预览发布，同年 5 月正式 GA。与 IDE 插件不同，它直接运行在命令行里，天然能读写文件、执行终端命令、全项目搜索——这让它特别适合批量重构、CI 集成这类自动化场景。

# 安装（需要 Node.js 18+）
npm install -g @anthropic-ai/claude-code

# 创建项目并启动
mkdir my-todo && cd my-todo
claude

# 登录方式：① 订阅（Pro/Max 配额）
# ② API Key（按 Token 计费） ③ 第三方模型（GLM/MiniMax 等，走环境变量）
登录方式计费模式适用人群
订阅（Pro/Max）固定月费 + 用量配额使用频率稳定的个人开发者
API Key按 Token 计费，用多少付多少用量波动大、团队集成、自动化脚本
第三方模型接入按第三方定价国内网络环境、成本敏感、数据合规要求
关键认知：Claude Code 是通用编程智能体，不绑定 Claude 模型。你可以用其他模型驱动它（如国产 GLM、MiniMax），只需设置环境变量。工具层（文件操作、终端、调度）与模型层解耦——这正是 Eng-05 中 GLM 5.2 能在 Claude Code 上无人值守跑 13 小时的前提。

Claude Code 是"底盘"，模型是"发动机"。底盘负责调度、文件、权限、记忆；发动机负责理解和生成。发动机可以换，底盘不变。

二、四大核心模块总览

44 分钟的视频覆盖了完整的能力地图，归纳为四大模块：

┌─────────────────────────────────────────────────────┐ │ Claude Code 总体架构 │ ├─────────────────────────────────────────────────────┤ │ 接口层 终端对话 │ 图片输入 │ 后台任务 │ │ ───────────────────────────────────────────────── │ │ Agent 循环 任务拆解 → 工具调用 → 观察结果 → 下一步 │ │ │ │ │ ├── Sub Agent 并行（复杂任务分解） │ │ └── Hook 拦截（事件前后插入检查） │ │ ───────────────────────────────────────────────── │ │ 能力扩展 MCP Server │ Agent Skill │ 权限模式 │ │ ───────────────────────────────────────────────── │ │ 上下文管理 自动累积 → 自动压缩（95% 阈值） │ │ ───────────────────────────────────────────────── │ │ 模型推理层 Claude │ GLM │ MiniMax（可替换） │ └─────────────────────────────────────────────────────┘
模块内容解决什么问题
1. 基础交互项目创建、基础命令、对话交互能上手
2. 复杂任务多步骤任务分解、Sub Agent 并行、代码审查干大事
3. 终端控制权限管理、命令执行、沙箱隔离不出事
4. 高级功能MCP Server、Agent Skill、Hook、图片输入、上下文管理、后台任务扩边界

四大模块一句话记住：先学会聊天（基础交互），再学会派活（复杂任务），然后学会踩刹车（终端控制），最后学会加装备（高级功能）。

Agent 循环层是核心中的核心："拆解 → 执行 → 观察 → 调整"不断循环——Claude Code 不是一次性把任务做完，而是根据每一步工具执行的结果持续修正。所有高级功能都是对这个循环的扩展：Sub Agent 把循环并行化，Hook 在循环中插入检查点，上下文管理保证循环不"失忆"。

三、复杂任务处理：Sub Agent 并行

面对复杂项目，Claude Code 会自动拆解成多个子任务，启动多个 Sub Agent（子代理，由主代理启动、各自拥有独立上下文窗口的执行单元）并行处理，最后汇总结果。就像项目经理给团队成员分派工作：每个成员独立工作，最后汇报结论。

用户："审查这个功能的代码，输出审查报告" │ ↓ ┌───────────────┐ │ 主 Agent │ 任务拆解 + 分派 └───┬───┬───┬───┘ ↓ ↓ ↓ 3 个 Sub Agent 并行执行 ┌────────┐┌────────┐┌────────┐ │Sub Agent││Sub Agent││Sub Agent│ │安全审查 ││性能审查 ││逻辑审查 │ └───┬────┘└───┬────┘└───┬────┘ └─────────┼─────────┘ ↓ 主 Agent 合并 3 份结论 ↓ 输出 1 份结构化报告
维度主 AgentSub Agent
上下文完整会话历史全新独立上下文，只拿到子任务描述
职责拆解、分派、合并执行单个子任务
生命周期贯穿整个会话按需创建，任务完成即销毁
可见范围Sub Agent 的最终结论只有自己子任务相关的内容

Sub Agent 最有价值的地方不是"并行快"，而是"上下文隔离"——每个 Sub Agent 从干净上下文出发，不被主会话的无关历史污染；主 Agent 只接收浓缩结论，自己的上下文也保持清爽。

这个设计直接决定了复杂任务的处理质量：没有 Sub Agent 时，主代理要把所有文件读进自己的上下文，可能还没读完一半上下文就满了；有了 Sub Agent，主代理上下文里只有"任务描述 + 结论摘要"，腾出空间做决策。代码审查、多模块探索、批量文档生成，都是典型的受益场景。

四、终端控制与权限管理

Claude Code 会在你的终端里执行真实命令——写文件、跑脚本、装依赖。权限系统是"AI 自动化"和"失控"之间的刹车：默认每个敏感操作都会请求确认，你可以通过模式切换调整松紧（快捷键 shift+tab 循环切换）。

权限模式行为适用场景
default文件修改、命令执行逐一请求确认日常开发、不熟悉的项目
acceptEdits自动批准文件编辑，命令仍会询问可信的重构任务
Plan Mode只规划不执行，输出执行方案供审阅高风险操作前的预审
bypassPermissions跳过所有确认，完全自主执行沙箱、容器、无人值守长跑
bypassPermissions 相当于把机器完全交出去——只在隔离环境（Docker、虚拟机、一次性工作区）或无人值守长跑场景使用（参考 Eng-05 的 13 小时实测）。千万不要在存有重要数据的主力机上直接开。

自动化能力越强，刹车越值钱。权限模式的本质是用"确认成本"换"安全边际"——环境越隔离，越可以放手。

权限之外，Claude Code 的终端控制还包括命令执行策略：哪些命令可以并行跑、哪些要等结果、长时间运行的进程怎么处理——这些共同决定了 Agent 循环的稳定性。批量任务再结合后台执行（见第 6 节），可以避免阻塞交互式终端。

五、高级功能：MCP / Skill / Hook / 图片输入

三大扩展机制解决的问题不同，不要混用：

机制解决什么加载时机典型用途
MCP Server接入外部工具与数据源启动时注册，工具描述进上下文GitHub、数据库、内部 API
Agent Skill注入操作规范与流程指南按需加载，不用不加载代码审查流程、发布检查单
Hook在特定事件点插入自定义逻辑事件触发（工具调用前后等）审计日志、权限管控、格式检查
# 一条命令注册 MCP Server
claude mcp add fetch uvx mcp-server-fetch

# Skill：目录里放 SKILL.md，按需自动加载
~/.claude/skills/
└── code-review/
    └── SKILL.md   # 审查步骤、判断标准、输出模板

Skill 的"按需加载"是省 Token 的关键：与系统提示词（每次都全量加载）不同，Skill 只在任务匹配时才被读入上下文，所以你可以放心地配置几十个 Skill 而不担心上下文爆炸。Hook 则常用于治理场景——比如在文件写入前拦截检查敏感路径、在工具调用后写审计日志。

Claude Code 还支持图片输入：直接把截图或设计稿粘贴进对话，模型会理解图片内容并生成对应代码。这让"截图生成页面"成为可用的工作流，但要注意模型对视觉细节的理解有限，复杂设计仍需人工微调。

MCP 扩展"能做什么"，Skill 扩展"怎么做好"，Hook 扩展"做完前后查什么"。一个长手脚，一个长方法，一个长规矩。

六、上下文管理与后台任务

Claude Code 执行过程中会不断累积工具执行结果，把上下文窗口填满。内置的 auto compact（自动压缩，上下文占用超过阈值时自动总结历史、保留关键决策的机制）会在上下文使用率超过 95% 时触发：把历史对话总结为精简摘要，丢弃原始详细内容，保留关键决策和结论。这保证了 Agent 可以长时间稳定运行，不会因为上下文溢出而"忘记"目标。

上下文管理与执行方式决策图： 上下文快满了，但任务还没完？ ├── 历史都是本任务的 → 等 auto compact（95% 自动触发） └── 想主动瘦身 → /compact（手动总结） 切换到无关的新话题？ └── /clear（清空上下文重新开始） 任务大、可并行？ └── Sub Agent（上下文隔离，只合并结论） 任务长、不想占着终端？ └── 无头模式 + 系统级后台执行
手段触发方式效果适用
/clear手动清空全部上下文话题切换
/compact手动立即总结历史主动瘦身
auto compact95% 自动总结 + 丢细节 + 留决策长任务持续运行
Sub Agent自动拆解从一开始就隔离上下文复杂并行任务
后台任务无头 + shell 后台不占用交互终端批量重构、CI
# 无头模式：适合脚本和 CI
claude -p "总结本周提交记录并生成周报"

# 长任务交给系统级后台执行
nohup claude -p "重构整个项目的错误处理" > task.log 2>&1 &
背景：某团队要在一个 10 万+ 行的单体仓库里做跨模块错误处理重构，预计连续执行数小时。
问题：工具执行结果（文件内容、命令输出）累积极快，200K 上下文窗口几十分钟就被填满，溢出后 Agent 会"忘记"重构目标。
方案：依赖 auto compact 在 95% 阈值自动总结，保留关键决策（已改哪些模块、统一错误格式是什么），配合 git 提交把检查点外置。
效果：连续执行数小时无目标漂移，20+ 个相关模块全部完成重构，每次压缩只丢细节、不丢方向。
背景：一个 30+ 文件的功能 PR 需要完整代码审查，覆盖安全、性能、逻辑三个维度。
问题：主 Agent 串行审查要把所有 diff 读进单一上下文，预计 40+ 分钟，且中途上下文非常拥挤。
方案：主 Agent 并行派出 3 个 Sub Agent，各负责一个维度，各自用独立上下文只读相关 diff，最后主 Agent 合并三份结论。
效果：审查时间从约 40 分钟压缩到约 10 分钟，主 Agent 上下文只增加三份摘要，三个维度的判断标准互不干扰。
  • 切换话题时用 /clear 清空上下文
  • 把关键决策外置到文档（配合 git 提交）
  • 大型并行任务用 Sub Agent
  • 高风险操作先用 Plan Mode 审方案
  • 不要在同一会话里做无关任务
  • 不要在主力机上开 bypassPermissions
  • 不要把所有规范塞进系统提示词（用 Skill）
  • 不要无视上下文占用警告

上下文管理的本质是"记什么、忘什么"：auto compact 忘细节、记决策；Sub Agent 忘全局、只看自己的活；/clear 全忘、重新开始。记忆管得好，Agent 才跑得远。

Q&A

Claude Code 的核心架构是什么？
Claude Code 是通用编程智能体，核心架构分为四层：① 模型推理层 — 可用 Claude 或其他模型（GLM/MiniMax）驱动；② Agent 循环层 — "拆解 → 执行 → 观察 → 调整"持续修正，复杂任务自动拆解给 Sub Agent 并行；③ 能力扩展层 — MCP 接入外部工具，Skill 注入规范，Hook 插入检查点；④ 上下文管理层 — 上下文超过 95% 时 auto compact 自动压缩历史。对应四大功能模块：基础交互、复杂任务处理、终端控制、高级功能。
Claude Code 如何管理上下文？auto compact 机制是什么？
Claude Code 执行过程中，工具执行结果（文件内容、命令输出）会不断累积到上下文中。当上下文使用率超过 95% 时，auto compact 机制自动触发：① 把历史对话总结为精简摘要；② 丢弃原始详细内容；③ 保留关键决策和结论。这保证 Agent 可以长时间稳定运行，不会因上下文溢出而目标漂移。配合手动的 /clear（话题切换时清空）和 /compact（主动瘦身），构成完整的上下文治理工具箱。
订阅和 API Key 计费如何选择？
订阅（Pro/Max）是固定月费加用量配额，适合使用频率稳定的个人开发者——成本可预期，不用盯着 Token 账单。API Key 按 Token 计费、用多少付多少，适合用量波动大、团队集成和自动化脚本场景——不用时零成本。此外 Claude Code 支持第三方模型驱动（GLM、MiniMax 等），通过环境变量配置即可，适合国内网络环境和有数据合规要求的团队。按使用频率和合规约束选择即可，三者可以随时切换。
Sub Agent 和自己开多个 Claude Code 会话有什么本质区别？
本质区别是"有没有统一调度者"。Sub Agent 由主 Agent 自动拆解分派，每个 Sub Agent 只拿到子任务描述和干净的上下文，完成后结论自动合并回主 Agent 的上下文——全程不需要人工搬运。自己开多个会话则是你手动拆任务、手动复制结果，会话之间互不知道对方的存在。Sub Agent 的价值不只是并行加速，更是上下文隔离：每个 Sub Agent 不被无关历史污染，主 Agent 只存浓缩结论，两边的上下文都保持清爽。
Agent Skill 相比把所有规范写进系统提示词，省在哪里？
系统提示词是每次会话都全量加载的，内容越多，每次调用固定消耗的 Token 越多。Skill 是按需加载：技能以 SKILL.md 文件存放在 ~/.claude/skills/ 目录下，Claude Code 只在任务匹配时才把对应 Skill 读入上下文。这意味着你可以同时配置几十个 Skill（代码审查流程、发布检查单、日志排查规范），但只有当前任务相关的一两个会占用上下文。这种"索引 + 按需读取"的设计，正是上下文工程的标准做法。
Hook 机制的典型用途有哪些？
Hook 在特定事件点（工具调用前后、会话开始等）拦截并触发自定义脚本，典型用途是治理与自动化：① 审计日志 — 记录每次文件写入和命令执行，便于事后追溯；② 权限管控 — 工具调用前检查是否涉及敏感路径，命中则拒绝；③ 质量门禁 — 代码写入后自动跑 lint 或格式检查，不通过就把错误反馈给 Agent 让它自我修正。Hook 和 Skill 的分工：Skill 是"告诉 Agent 该怎么做"，Hook 是"Agent 做完后强制检查"，后者更可靠。
Claude Code 能用国产模型吗？需要注意什么？
可以。Claude Code 是通用编程智能体，不绑定 Claude 模型，通过环境变量配置 base URL 和密钥即可接入 GLM、MiniMax 等国产模型。需要注意三点：① 工具层（文件操作、终端、调度）由 Claude Code 本身提供，换模型不影响这些能力；② 不同模型在指令遵循和长上下文上的能力差异，会直接影响长任务效果——Eng-05 实测中 GLM 5.2 靠大窗口和指令遵循改进，在 40 万+ 行项目上完成了 13 小时无人值守执行；③ 长跑场景建议配合进度外置和 git 检查点，不要只依赖模型能力。
