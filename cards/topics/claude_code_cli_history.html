HC05 · Agent 时代的 CLI 路线：命令行工具演进

Terminal / Shell / CLI 概念辨析 · 批处理到云原生的演进 · Agent 闭环与可机读证据 · Agent 友好 CLI 六条清单 · 窄腰层判断

CLI 回归不是复古，而是工程事实：聊天框适合模型"说"，CLI 才方便 Agent 真正"做"——文本输入、命令动作、证据反馈、管道组合、OS 边界，恰好压成 Agent 需要的统一闭环。

一、三个概念辨析：Terminal、Shell、CLI

讨论"为什么 Agent 时代大家都在做 CLI"之前，先把三个常被混用的词掰清楚：Terminal（终端）是承载输入输出的窗口或设备，Shell（壳层）是解释并执行命令的程序，CLI（Command Line Interface，命令行界面）则是用文本命令与软件交互的方式。三者是"舞台—翻译—语言"的关系：Terminal 提供舞台，Shell 负责翻译，CLI 是那套被说出来的语言。

概念本质代表一句话定位
Terminal输入输出的承载层iTerm、Windows Terminal、TTY看得见的那块"黑框"
Shell解释命令的程序bash、zsh、PowerShell把一行文本变成一组动作
CLI交互方式的约定git、docker、kubectl用文本命令驱动软件
TUI终端里的图形界面Claude Code、htop带面板与快捷键，底座仍是 Shell

Claude Code、Codex CLI 今天已经是带面板、状态和快捷键的 TUI（Text User Interface，终端图形界面），但它们真正依赖的底座，仍然是 Shell、文件系统和一整套命令行工具。看懂这一点，才能理解 CLI 为什么"老树开新花"。

六十年演进：从批处理到云原生

最早的计算机谈不上命令行：人把程序打在卡片上交给机器批处理（Batch Processing，把一批作业集中顺序执行），结果晚点再拿回来，人和机器之间没有实时对话。直到分时系统（Time-Sharing，让多个用户通过终端共享一台主机）出现，人才可以输入一行命令、马上看到一行结果。到了 Unix，Shell 完成关键升级：它不只是启动程序的入口，还是一门可以组合程序的控制语言。

命令行的六十年演进 ────────────────────────────────────────────────────── 1960s 批处理 卡片提交 → 排队执行 → 次日取结果 │ 人机无实时对话 ▼ 1960s-70s 分时 终端输入 → 即时回显 │ 人第一次"对话"机器 ▼ 1970s Unix stdin / stdout / stderr / 退出码 / 管道 │ 小工具接成工作流，Shell 成为控制语言 ▼ 1980s-90s GUI 按钮与窗口兴起，CLI 退居幕后 │ 但脚本、CI、远程运维离不开它 ▼ 2000s+ 云原生 Git / Docker / K8s / Terraform 全是一等公民 │ 服务器不需要屏幕，自动化不点鼠标 ▼ 2025+ Agent 敲命令的主角，从人变成了模型 ──────────────────────────────────────────────────────

stdin、stdout、stderr、退出码、重定向、管道，这几个设计看起来朴素，却把一堆小工具接成了工作流。GUI 兴起后命令行也没有消失，因为两者解决的是不同的成本：GUI 解决人的发现成本——按钮摆在那里，不会写命令也能点；CLI 解决系统的组合成本——一个命令能进脚本、进 CI、跑远程机器，还能把输出交给下一个程序。

一个跨越近五十年的伏笔：1978 年 Bourne 对 Unix Shell 的定义里，就已经同时强调了控制流、环境、重定向和进程管道。今天 Agent 框架消费的"执行—观察—组合"能力，几乎全部来自这份 1970 年代的设计遗产。变化的不是命令行突然变好用，而是"把人的意图翻译成精确语法"这份苦活，从人转移给了模型。
时代人机交互方式CLI 的角色
批处理时代卡片提交、离线等待尚未登场
分时时代终端即时对话唯一交互入口
Unix 时代管道组合小工具程序间的通用协议
GUI 时代鼠标点击窗口退居脚本与运维幕后
云原生时代声明式配置 + 命令基础设施的一等公民
Agent 时代模型生成并执行命令Agent 的执行通道与证据来源

CLI 原本最劝退人的门槛——记忆命令语法、手写精确参数——恰好被大模型吃掉了。门槛被吃掉的那一刻，CLI 的全部工程优势都变成了 Agent 的红利。

二、Agent时代CLI回归的工程原因

很多文章会说"CLI 快、轻量、极客"，这个解释太浅了。Agent 选择 CLI，不是因为终端酷，而是 CLI 天然提供了一套可执行、可观察、可组合的反馈系统。你让 Claude Code 修一个登录 Bug，它不是吐一段代码就完事，而是顺着仓库继续干：用搜索命令定位调用链、读取文件、修改代码、跑单测、看报错、再读 diff，直到证据说明任务完成。

统一闭环的五个维度

这里最值钱的不是某一条命令，而是 CLI 把整个软件工具链压成了统一结构。输入、动作、反馈、组合、边界五件事，全部落在同一套语法里：

Agent + CLI 的闭环 ────────────────────────────────────────────────────── [意图/任务] │ 文本或文件传入（需求、路径、参数） ▼ [Agent 推理] ──────────────┐ │ 生成并执行命令 │ ▼ │ [工具链执行] │ git / 编译器 / 测试 / 数据库 │ │ │ ▼ │ [证据回流] │ stdout / stderr / 退出码 / │ 测试报告 / diff │ └────────────────────────┘ 验证失败不是模糊的"不对"， 而是下一轮推理直接消费的证据 ──────────────────────────────────────────────────────
闭环维度在 CLI 中的形态对 Agent 的意义
输入文本或文件：需求、路径、参数明确传入，无歧义
动作命令：Git、编译器、测试框架、云平台动作被命名、可枚举
反馈stdout、stderr、退出码、测试报告、diff机器可判定成败
组合管道与脚本成功交互可固化为流程
边界工作目录、文件权限、网络策略、沙箱OS 兜底限制爆炸半径

其中反馈这一环最关键。CLI 的三类输出本质上是可机读证据（Machine-Readable Evidence，无需人类解释就能被程序判定真伪的信号）：stdout 给结果、stderr 给诊断、退出码（Exit Code，进程结束时返回的整数，0 通常代表成功）给成败。对模型来说，退出码 1 比任何自然语言描述都更像"确定的事实"。

两家头部公司同时用脚投票：2025 年 2 月，Anthropic 把 Claude Code 作为终端里的研究预览发布；同年 4 月，OpenAI 上线开源的 Codex CLI，5 月才推出 Codex Web。这不是谁抄谁，而是两家公司同时撞上了同一个工程事实——聊天框适合模型"说"，CLI 才方便 Agent 真正"做"。

CLI 是可递归的

更狠的一点是，Agent 不只会调用 CLI，它自己也能变成 CLI 的一环。交互工具因此变成脚本组件，可以进 CI、定时任务和无人值守流程——这是网页聊天框很难自然做到的：

cat build-error.txt | claude -p "定位根因并给出修复建议"
git diff | codex exec "检查这次修改是否引入并发问题"

当一个工具既能被 Agent 调用、又能把 Agent 装进管道，它就具备了"乐高属性"：自动化系统的复杂度可以靠组合增长，而不是靠重写。

三、GUI没有输：它只是更适合人

GUI 最大的优势，是把功能摊开给人看：设计稿、数据大盘、复杂表格、可视化调试，这些场景让人直接看，比读几百行文本舒服得多。讨论 Agent 与界面的关系时，先要破除"CLI 要干掉 GUI"的误解。

"猜像素"的困境

Agent 操作 GUI，很多时候是在"猜像素"：按钮换个位置、弹窗多一层、页面加载慢一点，执行路径就变了。它当然可以靠 Computer Use（让模型看屏幕截图、移动鼠标键盘来操作图形界面的能力）完成任务，但这条通道有四个结构性短板：延迟高、状态隐蔽、难并行、难精确复现。

维度CLI 操作GUI 操作（Computer Use）
动作定位命令被命名，git status 永远在原地靠坐标识别，按钮换位置就失效
状态可见性stdout / stderr 全量文本可读大量状态藏在渲染层，截图只见冰山一角
并行能力多进程天然并行，无焦点冲突一个屏幕一次焦点，难以并行
可复现性同一命令确定性强加载时序、动画都会改变路径
适合场景Agent 批量执行与取证没有 API 也没有 CLI 的最后一公里

反过来看 CLI 的确定性：git status 不会因为窗口缩放就跑到右上角，退出码 1 也比截图里一行红字更容易判断。对需要成千上万次重复执行的 Agent 来说，确定性和可复现性就是成本。

人与 Agent 的两层分工 ────────────────────────────────────────────────────── 上层：人类监督界面 IDE / 桌面 App / Web 面板 看计划 · 审 diff · 做授权 · 收通知 ▲ 审批与证据向上呈现 │ ▼ 任务与权限向下分发 下层：Agent 执行与取证 CLI / API / MCP 跑命令 · 读输出 · 改文件 · 出报告 ────────────────────────────────────────────────────── 不是 CLI 干掉 GUI，而是人看上层、Agent 跑下层

真正的分工不是谁替代谁：人用 App、IDE、Web 看计划、审 diff、做授权；Agent 在下面用 CLI、API、MCP 执行和取证。审批和证据在两层之间往返。

四、Agent友好CLI设计六条清单

别因为 Agent 能跑命令，就觉得所有 CLI 都天然可靠。大量老工具默认操作者是人：会弹交互确认、输出彩色进度条、把错误混进 stdout，甚至失败了还返回 0。人能凭经验看懂，Agent 接进流水线就容易翻车。真正 Agent 友好的 CLI，至少要满足六条：

条目缺失时的翻车现场实现要点
--json 输出模型从花哨日志里猜字段，猜错就执行错提供 --json 或稳定 Schema
流分离错误混进 stdout，结果被污染stdout 放结果、stderr 放诊断、退出码真实
dry-run / 幂等失败后无法安全重试，只能人工收拾提供 --dry-run、diff 和幂等操作
非交互模式半夜卡在"是否继续？Y/n"，整条流水线挂起支持非交互、超时和取消
权限收口一次误操作波及全库凭证按任务、目录、命令、时间收口
可审计出事后不知道谁改了什么明确记录谁执行了什么、改了哪里、依据是什么

一个对比：同一命令的两种输出

# 面向人的输出：Agent 只能靠正则猜
$ deploy status
[OK] prod v2.3.1  healthy

# 面向 Agent 的输出：字段即结构
$ deploy status --json
{"env":"prod","version":"v2.3.1","healthy":true}
$ deploy status --json > /dev/null; echo $?
0
  • 结果走 stdout，诊断走 stderr，成败看退出码
  • 提供 --json 并承诺字段稳定
  • 危险操作默认 dry-run，写操作保证幂等
  • 所有确认项提供 --yes 或环境变量旁路
  • 记录审计日志：执行者、命令、目标、依据
  • 把彩色进度条写进 stdout 供管道消费
  • 出错仍然返回退出码 0
  • 强制交互确认，没有非交互旁路
  • 凭证全局共享，不设作用域和时限
  • 失败信息只给人看，不给结构化原因
能力越强，边界越贵：这也是为什么 Claude Code 和 Codex 都在权限模型上花重力气。Agent 越能干，误操作和提示注入（Prompt Injection，恶意内容诱导模型执行非预期操作）的爆炸半径越大。没有边界的 CLI，不是自动化，是把生产事故也自动化。

检验一个 CLI 是否 Agent 友好的土办法：把它接进一个无人值守的凌晨定时任务。凡是会让你爬起来敲键盘的地方，都是 Agent 的翻车点。

五、CLI不是终局：窄腰层与三层分工

判断要分两半：终端不是终局，CLI 也不会成为所有人的最终界面；但 CLI 不会消失，它会换一种身份长期存在。

纯终端为什么不够

当 Agent 从一次处理一个任务，变成同时管理十几个长期任务，纯终端很快就不够用：你需要任务队列、并行状态、权限面板、diff 审核、通知和跨设备接力。OpenAI 后来做 Codex App，本身就在说明——终端适合启动和执行，但不一定适合人监督一支 Agent 队伍。同时，CLI 也不是所有工具的最佳协议：API 和 MCP（Model Context Protocol，为模型提供标准化工具与数据接口的协议）有明确 Schema，通常比解析自然语言日志更稳；Computer Use 则负责那些既没有 API、也没有 CLI 的最后一公里。

CLI 是 Agent 世界的"窄腰层" ────────────────────────────────────────────────────── 上层入口（无限多） 中间交接层（收敛） 下层工具（无限多） ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ IDE 插件 │ │ │ │ Git │ │ 桌面 App │ ───▶ │ CLI / 结构化 │ ───▶ │ 测试框架 │ │ 网页面板 │ │ 命令与结果 │ │ 数据库 │ │ 手机 │ │ （窄腰） │ │ 容器 / 云服务 │ └──────────────┘ └──────────────┘ └──────────────┘ 并行通道：API / MCP / Computer Use 长期共存 ──────────────────────────────────────────────────────

窄腰层（Narrow Waist，借鉴互联网 IP 层的说法：上层应用与下层介质都可以无限多样，只要中间有一层统一协议）正是 CLI 在 Agent 世界的定位：上面可以是 IDE、桌面 App、网页、手机，下面可以接 Git、测试、数据库、容器和云服务，中间都能通过命令和结构化结果完成交接。

通道Schema 强度生态成熟度适用场景
CLI弱到中（靠 --json 补齐）最高，几乎所有开发工具执行、取证、脚本化
API强（OpenAPI 等规范）高，云服务标配结构化读写、跨系统集成
MCP强（标准工具 Schema）快速成长中Agent 原生工具接入
Computer Use无（像素级）早期无 API 无 CLI 的最后一公里
终局判断：真正的终局不是 CLI，而是所有软件都长出一套 Agent 能调用、能验证、能审计、也能被安全关住的接口。CLI 只是最早准备好的那一个。未来的竞争不只是给人写得顺不顺手，还要看能不能被 Agent 稳定调用——结构化输出会越来越重要，权限和沙箱会从附加功能变成默认能力。
层次角色代表形态关注点
人类监督层看、审、批Codex App、IDE 面板计划可读、diff 可审、授权可控
Agent 编排层拆解、调度、收敛Agent Loop、工作流任务队列、重试、停止条件
工具执行层干活、取证CLI、API、MCP确定性、可审计、权限收口

窄腰层的含义是：上层入口可以无限多，下层工具可以无限多，只要中间的交接层统一。CLI 赢了上半场——它是执行层最成熟的通道；但下半场属于所有把"可被 Agent 调用"做成默认能力的接口。

Q&A

为什么 Claude Code 和 Codex 都选择从 CLI 起步，而不是先做网页？
因为 CLI 提供了 Agent 闭环所需的全部要素：文本输入明确、动作是命令、反馈是 stdout/stderr/退出码这类机器可判定的证据、管道可以固化流程、OS 提供权限与沙箱边界。网页聊天框适合模型输出内容，但难以直接驱动 Git、编译器、测试框架这条工具链。2025 年 2 月 Claude Code 以终端研究预览发布，4 月 Codex CLI 开源、5 月才有 Codex Web，两家公司的产品节奏本身就说明了这个工程判断。
Terminal、Shell、CLI 到底有什么区别？
Terminal 是承载输入输出的终端（窗口或设备），Shell 是解释命令的程序（bash、zsh、PowerShell），CLI 是用文本命令与软件交互的方式（git、docker 这类工具的界面形态）。三者分别是舞台、翻译和语言。Claude Code 这类产品表面是带面板的 TUI，底座依赖的仍然是 Shell、文件系统和命令行工具链。
"CLI 提供反馈系统"具体指什么？
指 CLI 把软件工具链压成了统一结构：输入是文本或文件，动作是命令，反馈是标准输出、错误输出、退出码、测试报告和 diff，组合靠管道和脚本，边界由操作系统兜底。对 Agent 来说，验证失败不是一句模糊的"不对"，而是下一轮推理能直接消费的证据。这套结构让 Agent 可以"定位—修改—跑测试—看报错—再改"，直到证据说明任务完成。
GUI 操作为什么被叫"猜像素"？Computer Use 成熟后 CLI 会不会过时？
GUI 操作依赖屏幕坐标与视觉识别：按钮换位置、弹窗多一层、加载慢一点，执行路径就变了，所以像"猜像素"。Computer Use 通道延迟高、状态隐蔽、难并行、难精确复现，更适合没有 API 也没有 CLI 的最后一公里。CLI 的动作是被命名的——git status 不会因窗口缩放而移动，退出码比截图中的红字更易判定。两者是分工而非替代：人看 GUI，Agent 跑 CLI。
要把一个现有 CLI 改造成 Agent 友好，最小该做哪几件事？
优先级最高的四件：一，提供 --json 输出并承诺字段稳定，别让模型从日志里猜字段；二，stdout 只放结果、stderr 放诊断、退出码真实反映成败；三，提供非交互模式与超时取消，避免卡在"是否继续？Y/n"；四，危险操作提供 --dry-run 和幂等语义，失败后可安全重试。权限收口与审计日志是第二批，但只要进入生产流水线就必须补上。
为什么说 CLI 是"窄腰层"？它会被 MCP 取代吗？
窄腰层借自互联网 IP 层的概念：上层入口（IDE、App、网页、手机）与下层工具（Git、测试、数据库、容器、云服务）都可以无限多样，只要中间有一层统一的交接协议。CLI 正是这条最成熟的交接通道。MCP 有更强的 Schema，在 Agent 原生工具接入上更有优势，但存量工具链几乎都长在 CLI 上，两者会长期共存；API 和 Computer Use 也各有分工。被取代的不是 CLI，而是"不可被 Agent 调用"的接口。
Agent 自动执行命令，怎么防止把生产事故也自动化？
靠边界设计而不是靠模型自觉：工作目录与文件权限限制能碰什么，网络策略限制能连什么，容器和沙箱限制爆炸半径，凭证按任务、目录、命令和时间收口；同时要求输出可审计——明确谁执行了什么、改了哪里、依据是什么。Claude Code 和 Codex 都在权限模型上投入重力气，原因就是 Agent 越能干，误操作和提示注入的爆炸半径越大。没有边界的 CLI 不是自动化，是把生产事故也自动化。
