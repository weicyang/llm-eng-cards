Tool Search Tool — 延迟加载名单、三步取回 schema、提示词缓存保全、与 RAG 式工具检索的取舍

与其把上百本工具说明书全塞进模型的书桌，不如只放一张目录卡：模型想用哪本，报个名字，系统当场把那一本递过去。

一、工具预算：装不下的说明书

一个真正干活的编码 Agent，可用工具的数量远超直觉。除了内置的文件读写、命令执行、代码搜索，接上几个 MCP Server 之后，GitHub 的 issue/PR/review 操作、Slack 的频道与消息、Jira 的工单、内部数据库的查询接口会一股脑加进来，几十上百个工具是常态。

问题在于，每个工具进入上下文的成本不是「一个名字」，而是一整份 JSON Schema：名称、自然语言描述、参数列表、每个参数的类型与枚举值、必填项、返回结构说明。一个描述写得认真的工具，几百到上千 token 是很正常的。上百个工具乘一遍，在模型看到用户第一句话之前，上下文就已经被吃掉几万 token。

全量加载模式下，上下文窗口的实际分配： ┌──────────────────────────── 200K 上下文窗口 ────────────────────────────┐ │ │ │ ████████████████████████ 工具定义 ~55K ████ │ 系统提示 │ 对话历史与代码 │ │ (GitHub / Slack / Jira / DB ... 上百份 schema)│ ~5K │ ~140K │ │ │ └────────────────────────────────────────────────────────────────────────┘ ↑ 用户还没开口，四分之一的窗口已经被说明书占满 ↑ 而这一轮真正会用到的，往往只有其中 2~3 个工具

更麻烦的是第二重损耗。工具定义不只是占地方，它还是干扰源。当上下文里同时躺着 github_search_issues、github_search_pull_requests、jira_search_issues、linear_search_issues 四个名字相近、描述雷同的工具时，模型选错的概率显著上升。选错工具之后要么报参数错误、要么返回空结果，Agent 再自我纠正一轮，一次任务凭空多出两三次往返。

工具装载有两笔账：一笔是 token 账，一笔是注意力账。前者花钱，后者花正确率，而后者往往更贵。

两种成本的量级对比

成本维度表现形式随工具数增长的方式用户端可感知的症状
Token 占用每轮请求都要重新计费的 schema 前缀线性增长（每个工具几百到上千 token）账单变高、可用对话轮数变少
选择干扰相似工具之间的误选与反复试探接近平方增长（两两之间都可能混淆）Agent 兜圈子、调用失败后重试
首轮延迟超长前缀的预填充时间线性增长第一个字吐出来变慢

业界对这件事有个共识性的经验值：一次性放进上下文的工具超过十来个，模型的工具选择准确率就开始下滑。Claude Code 默认在上下文中常驻的核心工具也就是这个量级——文件读、文件写、编辑、Bash、Grep、Glob 这些高频项。剩下的怎么办？这就是 Tool Search 要回答的问题：它是一套让「工具定义按需进入上下文」的服务端机制，模型先看到名字，需要时再取回完整说明书。

二、三步流程：发现、取回、调用

Tool Search 的核心动作只有一个：把工具集合切成常驻与延迟加载两部分。常驻的那几个照旧带完整 schema 进上下文；其余的在请求里标上 defer_loading: true，模型初始只知道它们的存在，拿不到参数细节。

这里有个容易搞混的点值得先讲清楚：defer_loading 控制的是「什么进入上下文窗口」，而不是「什么发给 API」。客户端每一轮请求仍然要把所有工具的完整定义都放在 tools 数组里上传——服务端需要它们来执行检索和展开引用。省下来的是模型那一侧的上下文，不是网络传输。

Tool Search 三步流程（以调用一个未加载的工具为例）： [用户] "帮我看看这个 PR 上有哪些未解决的评论" │ ▼ ┌────────────────────────────────────────────────────┐ │ 上下文里此刻只有：ToolSearch + Read/Write/Bash ... │ │ 延迟名单里有 120 个工具，模型只见其名不见其详 │ └────────────────────────────────────────────────────┘ │ │ ① 发现：需要一个不在上下文里的工具 │ 模型不报错，而是发出 tool_use 请求 → ▼ { "type":"tool_use", "name":"tool_search_tool_regex", "input": { "query": "pull request review comment" } } │ │ ② 取回：在本地/服务端工具库里按名字与描述匹配 │ 命中项以 tool_reference 块返回（默认上限 5 个） ▼ tool_reference → 展开为完整 schema，追加进"对话正文" │ │ ③ 调用：模型此时已掌握参数结构，直接发起真实调用 ▼ { "type":"tool_use", "name":"github_list_review_comments", "input": { "repo":"...", "pull_number": 482 } }

三步各自在哪一侧发生

步骤发起方执行方产物失败时的表现
① 发现模型——一个指向 ToolSearch 的 tool_use 请求模型误以为无工具可用，改用自然语言搪塞
② 取回ToolSearch 工具服务端 / 客户端工具库tool_reference 块，展开为完整 schema检索未命中，返回空列表，模型需换关键词重搜
③ 调用模型真实工具执行器正常的工具调用与结果与普通工具调用无异

检索方式目前有两种口径：正则匹配适合模型已经知道大致名字、要精确定位的场景（比如它记得有个工具叫 AskUserQuestion）；BM25 关键词检索适合模型只知道「我要做什么」、不知道工具叫什么的场景。两者的差别在于召回宽度，而不是机制本身。

模型碰到「我需要一个此刻手里没有的工具」时，正确反应不是报错，而是先去查目录——ToolSearch 就是那个目录检索工具，它是唯一必须常驻的工具。

有一条硬性约束：ToolSearch 自己绝不能被标记为延迟加载。否则模型会陷入「要用检索工具去找检索工具」的死结。同理，最高频的三到五个工具也应该保持常驻——如果每次读文件都要先搜一次工具，多出来的那一轮往返会把节省的 token 收益吃干净。

三、延迟加载为什么不打穿缓存

这是整套机制里最精妙、也最容易被忽略的一环。要理解它，得先明白提示词缓存的工作方式：服务端会把请求开头一段固定不变的内容（系统提示 + 工具定义 + 早期对话）哈希成一个前缀键，命中则跳过重复的预填充计算，成本可以降到原价的十分之一量级。

关键在于前缀缓存是逐字节严格匹配的。工具定义恰恰位于系统提示区，是前缀的一部分。这意味着在朴素实现下，任何工具的增、删、改，哪怕只是给某个参数补一句描述，都会让整段前缀的哈希变化，后面所有缓存全部作废。

缓存前缀的构成，以及 defer_loading 的位置： 朴素实现（全部工具进前缀） ┌─────────────── 参与哈希的缓存前缀 ───────────────┐ │ 系统提示 │ 工具A 工具B 工具C ... 工具Z │ ← 动一个字，整段作废 └──────────────────────────────────────────────────┘ │ 对话正文 │ Tool Search（延迟工具被剔除出前缀） ┌────── 参与哈希的缓存前缀 ──────┐ │ 系统提示 │ ToolSearch + 常驻工具 │ ← 稳定不变，缓存长期有效 └────────────────────────────────┘ │ 对话正文 │ │ ... user/assistant ... │ │ [tool_reference → 工具K 的 │ │ 完整 schema 就地展开] │ ← 落在正文里 │ ... 继续对话 ... │ └─────────────────────────────┘

做法是：带 defer_loading: true 的工具在渲染工具区、计算缓存键之前就被剔除，它们根本不出现在前缀里。当检索命中某个工具时，它的完整定义被就地展开在对话正文中——也就是说，新增的内容追加在缓存边界之后，而不是插进前缀中间。前缀纹丝不动，缓存继续有效。

Anthropic 官方文档口径：延迟工具在缓存键计算前就被从渲染的工具区剥离；因此向请求中新增延迟工具不会让已有缓存条目失效，并且在「发现该工具的那一轮」和「实际调用它的那一轮」之间，缓存都保持有效。

三种工具装载策略对缓存的影响

策略工具定义所在位置新增一个工具的后果缓存命中率
全量加载系统提示前缀前缀哈希变化，全部缓存作废低（工具集一改就归零）
客户端手动裁剪系统提示前缀（每轮不同子集）子集一变就作废，抖动更频繁极低
Tool Search 延迟加载常驻部分在前缀，其余在对话正文前缀不变，缓存保留高（稳定前缀长期复用）

缓存前缀像一摞已经装订好的书页：往后面加页没关系，往中间插页就得整本重排。延迟加载做的事，就是把所有新增内容都赶到装订线之后。

值得对比一提的是同族的上下文编辑机制（清理陈旧的工具调用结果）。它和 Tool Search 优化的是同一个窗口的两个不同部位：Tool Search 收敛的是「进来时就存在」的工具定义，上下文编辑收敛的是「跑着跑着攒下来」的历史结果。而且两者对缓存的态度是相反的——上下文编辑会主动改写正文、必然打断缓存，所以它才需要一个「至少清出多少 token 才值得触发」的阈值参数；Tool Search 则从设计上完全避开了这笔代价。

两种上下文收敛机制的分工

对比项Tool Search上下文编辑（清理工具结果）
收敛对象工具定义（请求一开始就存在）历史工具调用结果（运行中累积）
触发时机模型主动检索时上下文超过配置阈值时自动触发
对缓存的影响不破坏前缀，缓存保留改写正文，清理点之后的缓存需重建
信息是否丢失不丢，只是按需取回丢，被清理的结果以占位文本替代
典型收益省下几万 token 的固定开销让长任务不至于撞上窗口上限

四、收益与代价

Tool Search 的收益是双份的，一份省 token，一份提准确率，两份都有官方数据背书。

Anthropic 官方数据：在接入 GitHub、Slack 等多个常用平台工具的场景下，全量工具定义原本约消耗 5.5 万 token，开启 Tool Search 后降至约 8.7 千 token，降幅超过 85%；同时，由于上下文中同时可见的工具变少、彼此不再混淆，工具选择准确率明显上升——Opus 4.5 在相关评测上从 79.5% 提升到 88.1%。

收益拆解

指标开启前开启后变化受益方式
工具定义 token 开销约 55,000约 8,700下降 >85%每轮请求的固定成本直接砍掉大半
工具选择准确率（Opus 4.5）79.5%88.1%+8.6 个百分点误选减少 → 重试轮次减少

代价也要说清楚，主要是三条。

第一条是多一跳往返。每次触发检索，就多一轮「模型发出检索请求 → 服务端返回 schema → 模型再发真实调用」的交互。这一跳的开销通常在数百毫秒到一两秒之间，取决于检索是在服务端完成还是要回到客户端工具库。对于交互式编码场景，用户能感知到；对于批量跑的长任务，可以忽略。

第二条是检索可能不命中。工具能不能被找到，完全取决于它的名字和描述写得好不好。一个叫 process_data_v2、描述写着「处理数据」的工具，几乎不可能被任何合理的查询召回。命中失败之后模型会换关键词重试，重试也失败就退回自然语言回答——问题被静默地降级掉了，比直接报错更难排查。

第三条是召回上限——一次检索最多返回多少个候选工具，默认通常是 5 个，模型也可以在检索输入里自行指定。如果一个语义空间里挤了二十个近义工具，真正需要的那个很可能被挤出前几名，模型只能换关键词再搜一次。

Tool Search 把「一次性的空间成本」换成了「按需触发的时间成本」。工具越多、每轮真正用到的比例越低，这笔交换就越划算。

什么时候这笔交换不划算

场景工具总数单轮实际使用比例建议
单一用途的小 Agent< 10高（大部分都会用到）不开，全量加载更简单也更快
接了 1~2 个 MCP Server10 ~ 30中可选：把高频的常驻，长尾的延迟
企业级多平台集成> 50低（每轮只用 2~3 个）强烈建议开启，收益最大
延迟极度敏感的实时交互不限不限谨慎：多一跳往返可能不可接受，考虑扩大常驻集

五、横向对比：其他「工具太多」解法

「工具超出上下文预算」不是 Anthropic 独有的问题，业界至少有四类解法。理解它们的差别，才能判断 Tool Search 的位置。

四类解法在「决策权归属」这条轴上的分布： 客户端决策 ←─────────────────────────────────────→ 模型自主决策 ┌──────────────┐ ┌──────────────┐ ┌─────────────┐ ┌──────────────┐ │ 静态分组 │ │ RAG 式检索 │ │ Tool Search │ │ 代码模式 │ │ (预设工具集) │ │ (语义预筛) │ │ (模型自查) │ │ (工具即 API) │ ├──────────────┤ ├──────────────┤ ├─────────────┤ ├──────────────┤ │ 人工按场景 │ │ 用 query 的 │ │ 模型发现缺 │ │ 只给一个执行 │ │ 划好几套工具 │ │ embedding 先 │ │ 工具时自己 │ │ 环境，工具以 │ │ 集，按路由 │ │ 挑 top-k 工具│ │ 发检索请求 │ │ 函数形式被 │ │ 切换 │ │ 再进上下文 │ │ │ │ 代码调用 │ └──────────────┘ └──────────────┘ └─────────────┘ └──────────────┘ 可控性最高 自动化中等 自动化高 灵活性最高 泛化最差 前置猜测有误差 多一跳延迟 实现最重

四类解法逐项对比

解法谁来决定加载哪些工具缓存友好度优点软肋
静态分组路由人工规则 / 前置分类器差（每组前缀不同）完全可控、零额外延迟跨组任务直接失败；规则维护成本随场景增长
RAG 式工具检索客户端用用户 query 做向量召回差（每轮工具集都可能变）不需要模型配合，任何模型都能用用「用户问什么」猜「模型要用什么」，中间隔了一层规划，猜不准
MCP 工具列表分页客户端分批拉取工具清单中解决协议层的传输膨胀只解决「列表怎么传」，没解决「上下文放不下」；分页边界外的工具模型仍不可见
Tool Search模型自己，在需要的那一刻好（前缀稳定）决策发生在规划之后，最接近真实需求多一跳往返；依赖工具命名与描述质量
代码执行模式模型写代码时按需 import好工具组合、循环、条件判断都能表达需要沙箱；对模型的代码能力要求高

RAG 式工具检索和 Tool Search 看起来很像，实际差别很关键：前者在模型思考之前做检索，后者在模型思考之后做检索。用户说「把这个 bug 修了并同步给团队」，向量检索只能从这句话里猜关键词；而模型已经规划出「先读代码、再改、最后发 Slack 通知」之后，它非常清楚自己缺的是一个发消息的工具，检索请求的精度完全不是一个量级。

RAG 式工具检索是「猜你要用什么」，Tool Search 是「你说你要用什么」。前者的误差来自猜，后者没有这个误差。

协议层的分页机制则是另一个维度的事。MCP 侧的工具列表分页解决的是「一个 Server 有几百个工具时，tools/list 响应太大」的传输问题，它并不改变这些工具最终要不要进上下文。两者可以叠加使用：分页管传输，延迟加载管上下文。MCP 的协议分层与工具注册机制见 《A12 · MCP 核心架构》——那张卡讲的是工具怎么被声明、发现和调用的协议规范，本文讲的是这些工具真正进入模型上下文时的预算管理，一个在协议层，一个在推理层。

六、落地清单：什么规模值得开

把前面的分析收成可执行的判断。开不开 Tool Search，本质上看三个数：工具总数、单轮使用率、延迟容忍度。

预期收益 ≈ (工具总数 − 常驻数) × 单个 schema 均值 × 缓存未命中率 − 触发检索次数 × 单跳延迟成本

常驻集怎么划

工具类别常驻还是延迟判断依据
ToolSearch 本身必须常驻否则无法自举，模型永远搜不到任何工具
文件读写、编辑、命令执行常驻几乎每轮都用，延迟加载纯亏
代码搜索（Grep / Glob）常驻高频，且是其他动作的前置
第三方平台操作（GitHub / Slack / Jira）延迟数量大、单轮命中率低，收益集中在这里
低频运维与管理类工具延迟可能几十轮才用一次
危险操作（删除、部署、支付）延迟 + 独立确认不常驻还有个附带好处：降低被无意触发的概率

常驻集指的是不加延迟标记、每轮都完整进入上下文的那一小撮工具，它的大小是整个方案唯一需要反复调的参数。控制在三到五个是个稳妥的起点：太少，日常动作都要先搜一次，延迟叠加得很难受；太多，又回到了「上下文被 schema 挤占」的老路。

工具命名与描述：检索命中率的真正瓶颈

延迟加载把工具的可发现性完全押在了名字和描述上。这一点必须重视——在全量加载模式下，写得再烂的描述模型至少还能看到参数结构去猜；一旦延迟加载，描述烂就等于工具不存在。

  • 名字带上动词 + 领域对象：github_create_pull_request 而不是 gh_pr_new
  • 描述第一句直接说清「什么时候该用它」，把可能的检索关键词自然写进去
  • 近义工具在描述里互相划边界：「查 issue 用本工具；查 PR 请用 github_search_pull_requests」
  • 用真实任务样本跑一遍召回测试，统计每个工具能否被典型 query 检索到
  • 把高频三到五个工具保持常驻，其余全部延迟
  • 观测「检索次数 / 任务数」这个比值，异常高说明常驻集划错了
  • 用内部缩写、版本号后缀命名：svc_q_v3 这种名字检索不到
  • 描述只写一句「处理数据」「调用接口」这类同义反复
  • 把 ToolSearch 自己标成延迟加载（直接死锁）
  • 给不到 10 个工具的小 Agent 也开延迟加载，白白多一跳
  • 让多个工具的描述高度雷同，导致召回排序随机化
  • 开启后不监控降级路径——检索失败是静默的，不看指标发现不了
示例场景：某团队给内部编码 Agent 接入了四个 MCP Server，共 137 个工具。上线后发现即使开了延迟加载，仍有约一成任务在检索环节兜圈子。排查后定位到两批工具：一批沿用了内部服务代号命名（如 atlas_query），另一批描述是从接口文档里直接抄的字段说明、完全没写用途。把这两批工具的名字改成动词短语、描述首句统一改写成「用于……时」的句式之后，检索一次命中的比例回到了正常水平。这说明延迟加载的上限不由机制决定，由工具元数据的质量决定。

开启延迟加载之后，工具的名字和描述从「给人看的注释」变成了「给检索用的索引」。它们从文档降级成了基础设施。

Q&A

Tool Search 到底省的是什么？请求体不是照样要传所有工具定义吗？
省的是模型上下文，不是网络传输。客户端每一轮请求确实仍要把所有工具的完整定义放进 tools 数组上传，因为服务端需要它们来执行检索和展开引用。但标了 defer_loading 的工具会在渲染系统提示时被剔除，不进入模型实际看到的上下文窗口，因此既不计入输入 token 计费，也不占用注意力。传输量和上下文占用是两笔独立的账，Tool Search 优化的是后者。
为什么延迟加载能保住提示词缓存？
提示词缓存是对请求开头一段固定内容做逐字节哈希，命中则跳过重复预填充。工具定义位于系统提示区，属于前缀，所以朴素实现下任何工具增删都会让整段前缀失效。延迟加载的做法是在计算缓存键之前就把这些工具从渲染的工具区剥离，它们根本不出现在前缀里；当检索命中某个工具时，它的完整定义被就地展开在对话正文中，也就是追加在缓存边界之后。前缀不变，缓存自然继续有效，而且在发现工具和调用工具的这两轮之间都保持有效。
它和 RAG 式的工具检索有什么本质区别？
区别在于检索发生在模型思考之前还是之后。RAG 式方案是客户端拿用户的原始提问做向量召回，挑出 top-k 个工具再送进上下文，本质是用「用户问了什么」去猜「模型会用什么」，中间隔着一层任务规划，猜不准是常态。Tool Search 是模型自己完成规划、明确知道缺哪个能力之后主动发起检索，查询语义直接来自真实需求。另外 RAG 式方案每轮的工具集都可能变化，前缀跟着抖动，缓存几乎没法复用；延迟加载则完全避开了这个问题。
ToolSearch 自己可以延迟加载吗？常驻集应该放多少个工具？
绝对不行。ToolSearch 是整套机制的自举入口，如果它自己也被延迟，模型就得先找到检索工具才能检索，直接死锁。除它之外，建议把最高频的三到五个工具也保持常驻，通常是文件读写、编辑、命令执行和代码搜索这类几乎每轮都会用的动作。常驻集太小的症状是每任务平均检索次数超过两次，说明日常动作也在触发检索；太大则回到了上下文被 schema 挤占的老问题。可以先按经验划分，再用真实调用频次分布来校准。
开启之后为什么有些工具模型死活找不到？
检索命中完全依赖工具的名字和描述。用内部服务代号命名的工具（比如 atlas_query）、或者描述只写「处理数据」这种同义反复的工具，任何合理的查询都召回不了。另一类常见原因是同一语义空间里挤了太多近义工具，而检索默认只返回有限条数的匹配，真正需要的那个被挤出了前几名。修复方式是把名字改成「动词 + 领域对象」的形式，描述首句直接说明使用时机，并在近义工具的描述里互相划清边界。更麻烦的是检索失败往往是静默的，模型会退回自然语言回答而不是报错，所以必须监控一次命中率才能发现。
什么规模的工具集才值得开启？小项目开了会不会反而更慢？
会。判断标准看三个数：工具总数、单轮实际使用比例、延迟容忍度。工具不到十个、且大部分每轮都会用到的小 Agent，开了纯粹是每次多一跳往返，全量加载更简单也更快。接了一两个 MCP Server、总数在十到三十之间的属于可选区间，可以只把明确低频的长尾工具标为延迟。真正收益最大的是企业级多平台集成场景：工具超过五十个、单轮只用得上两三个，这时省下的 token 和减少的选择干扰都很可观。此外，对首字延迟极度敏感的实时交互场景要谨慎，可以通过扩大常驻集来减少触发检索的频率。
准确率提升是怎么来的？工具变少了模型不是选择更受限吗？
受限的是「同时可见」的工具数量，不是「可用」的工具数量——需要时随时能检索取回，能力边界没有收窄。准确率提升来自干扰的减少：当上下文里同时躺着四五个名字相近、描述雷同的搜索类工具时，模型误选的概率显著上升，而误选之后要经历参数报错、返回空结果、自我纠正的一整轮，成本很高。延迟加载让每次进入视野的候选集变小且语义集中，选择难度自然下降。Anthropic 官方给出的数据是 Opus 4.5 的工具选择准确率从 79.5% 提升到 88.1%。
Tool Search 和上下文编辑（清理工具结果）是同一类东西吗？
不是，两者收敛的是上下文窗口的不同部位。Tool Search 处理的是「请求一开始就存在」的工具定义，属于静态开销；上下文编辑处理的是「跑着跑着累积起来」的历史工具调用结果，属于动态膨胀。两者对缓存的态度也相反：上下文编辑会改写正文，必然让清理点之后的缓存失效，所以它需要一个「至少清出多少 token 才值得触发」的阈值来权衡；Tool Search 从设计上就避开了这笔代价。还有一个关键差别是信息是否可逆——被上下文编辑清掉的结果是真的丢了，只留一段占位文本；而延迟加载的工具随时可以再检索回来。实践中两者通常一起用。
