GE03 · 从 Prompt 到 Graph 的工程范式实践

五大设计层级 / 六大必设计对象 / 五大约束机制 / Graph 的能力边界

Prompt 控制一次回答，Loop 控制一个节点的行为，Graph 控制整个系统的拓扑。可靠性从来不是模型给不了的，而是控制流没有显性化——把"接下来做什么"从模型脑子里搬进一张可检查、可恢复、可审批的图里。

一、范式转型：Loop 时代结束

2023 年以来的 AI 工程经历了多次层级跃迁：从 Prompt Engineering（写好一次指令）到 Context Engineering（管好模型能看到的信息），再到 Harness Engineering（设计智能体运行的约束环境），再到 2026 年 6 月由 Peter Steinberger、Boris Cherny、Addy Osmani 几乎同周点燃的 Loop Engineering（设计自动提示智能体的循环系统）。而仅仅一个月后，2026 年 7 月，Peter Steinberger 公开宣布 Loop Engineering 时代结束——他的依据是 LongGraph 类图编排引擎的内部使用量已超过 6500 万次：当图的运行时已经成为基础设施，"循环"就不再是架构，而只是图里的一个节点。

规模信号：LangGraph 自 2024 年 1 月发布以来已成为图编排的事实标准，月下载量达数千万级，被 Klarna、Replit、Elastic 等公司用于生产；Gartner 数据显示，使用多智能体编排框架的企业 AI 项目占比从 2023 年的 12% 升至 2025 年的 45%。行业分析同时指出，30%~40% 被放弃的 agentic AI 项目源于编排与架构失败，而非模型能力不足——这正是范式从 Loop 转向 Graph 的根本动力。

本质关系：Loop 是 Graph 的子集

这不是简单的"新一代替代旧一代"。从图论角度看，一个自修正循环就是一个带自环的有向图——只有一个节点、一条指回自己的边。Loop 没有消失，它被收编了：在 Graph 工程里，循环成为某个节点内部的局部机制，而节点之间的调度、分支、汇合、暂停由图的拓扑统一管理。

Loop 时代：单节点自环 Graph 时代：拓扑统管一切 ┌─────────────────────┐ ┌────────┐ 条件边 ┌──────────┐ │ 提示 Prompt │ │ 规划节点 │ ───────▶ │ 执行节点A │ │ ↓ │ └───┬────┘ └────┬─────┘ │ 执行 Act │ │ ┌────┴─────┐ │ ↓ │ ───▶ │ │ 执行节点B │ 并行扇出 │ 观察 Observe │ ┌───▼────┐ └────┬─────┘ │ ↓ │ │ 验证节点 │ ◀─────────────┘ │ 重复（while True） │ └───┬────┘ └─────────────────────┘ │ 通过 ──▶ 审批节点(Interrupt) ──▶ END 控制流藏在循环体里 控制流显式声明在边上 Loop ⊂ Graph：循环只是图中的一条自环边

Loop 为什么撑不住：复合失败的数学

Loop 在小任务上工作得很好，但当任务步骤变多时，三种结构性缺陷会同时爆发。第一是状态不透明：循环反复原地修改同一个上下文对象，五轮之后没人能回答"第 3 步为什么选了工具 X"，因为那段信息已被第 4 步覆盖。第二是隐式分支：散落在循环体里的 if 语句制造出十几条隐藏路径，你以为有一个工作流，实际有十七个，且一个都没测过。第三是重试纠缠：循环体内的副作用（数据库写入、消息发送）会随重试再执行一遍。

更致命的是复合失败的概率账：假设单步成功率高达 95%，五步流水线的整体成功率只剩约 77%，十步降到 60%，二十步跌破 36%。这就是生产环境中复杂任务失败率远超团队预期的原因——它不是模型问题，是概率论问题。

端到端成功率 = (单步成功率)步骤数
0.95⁵ ≈ 77% ｜ 0.95¹⁰ ≈ 60% ｜ 0.95²⁰ < 36%

Loop 问的是"下一步做什么"，Graph 回答的是"什么依赖什么"。前者把逻辑藏在顺序里，后者把逻辑声明在拓扑上——这个差别就是全部的产品价值。

二、五大设计层级：从指令到拓扑

Graph 工程不是凭空出现的第五层，而是叠在既有四层之上的封顶结构。理解它的关键是：前面的层没有消失，而是被逐层包裹继续生效——图里的每个节点内部仍然有 Prompt、有 Context 注入、有自己的 Harness 约束、甚至有自己的 Loop。

Prompt定义任务目标模型指令、输出格式约束、少样本示例单次模型响应
Context提供信息上下文RAG 检索注入、工具 Schema、记忆读取模型能看到什么

各层解决什么失灵

每一层的出现都对应一种具体的失灵模式。Prompt 层解决"模型不知道该干什么"；Context 层解决"模型知道该干什么但手头没材料"；Loop 层解决"一次做不对"——生成器自评倾向于自我表扬，因此 Loop 的核心设计是生成/评估分离，让独立的怀疑者角色去挑刺；Harness 层解决"做的时候越界"——把散落在提示词里的软约束下沉为运行时的硬约束，例如工具白名单、单次调用 token 上限；Graph 层解决的是前面四层都碰不到的问题：多个节点之间的顺序、依赖、并行、汇合与恢复。

生产注脚：Loop 层的规模化代表是 Stripe 的自动合并流水线——每周合并超过 1300 个机器编写的 PR，靠的就是"发现任务→派发→验证→合并"的自运行循环。但这条流水线本身就是一个被 Harness 严格约束的图：验证不通过的 PR 走错误边回退，合并动作前有审批门。层级越高，约束越硬。

五层的关系像俄罗斯套娃：Prompt 是最里面那层，Graph 是最外面那层。你没法跳过里层直接做外层——一个节点内部的 Prompt 写不好，图设计得再漂亮也只是把错误调度得更快。

三、六大必设计对象：图的骨架

一张生产级 Graph 有六个必须显式设计的对象：State（状态）、Node（节点）、Edge（边）、Reducer（合并器）、Checkpoint（检查点）、Interrupt（中断）。它们分别回答六个问题：信息放在哪、活由谁干、下一步去哪、并行写入怎么合并、崩了从哪续、什么时候停下来等人。

┌──────────── State：图内唯一真相源（先于节点定义）────────────┐ │ 带类型 Schema：user_request / task_plan / evidence / ... │ ▼ │ START ──▶ [Node 判断] ──── Edge：确定性路由条件 ────▶ [Node 执行A] ──────┤ │ 写局部更新 写局部更新 │ │ └────────── Reducer：并行写入合并策略 ◀─────────┘ │ │ │ 每个超步结束 ──▶ Checkpoint：快照落盘（崩溃恢复） │ │ │ [Node 审批] ── Interrupt：暂停等人 ── resume ────────────┘

State：先于节点定义的唯一真相源

State 是贯穿整个图的共享记录，必须在画任何节点之前先定义。它把节点的输入输出全部显性化：谁读了什么、谁写了什么，在 Schema 上一目了然。工程上的黄金法则是"不在 State 里的东西就等于不存在"——禁止全局变量、禁止隐藏上下文，节点只通过合并局部更新（patch）的方式修改 State。这样做的直接收益是减少把完整对话历史塞给每个节点的需要，从源头抑制上下文膨胀。

class WorkflowState(TypedDict):
    user_request: str
    task_plan: list[str]
    evidence: Annotated[list[str], operator.add]  # Reducer：追加合并
    draft: str                                    # 默认 Reducer：覆盖
    retry_count: int

Node：按可验收性划分，而不是按功能划分

节点是有限界的执行单元，内容可以是一次 LLM 调用、一个完整的工具使用智能体、一个纯 Python 函数、一次数据库查询、一套测试，甚至是一次人工审批请求。划分节点的核心标准是可验收性：一个节点必须能独立回答"它做对了吗"。判断发票金额是否超过审批阈值不需要 LLM，用确定性代码即可；判断一封邮件是不是退款请求才需要模型。已知业务规则留在确定性节点里，只在需要语义理解、生成、规划或处理歧义的地方才引入 LLM 节点。

Edge：优先用代码做路由

边定义节点之间的依赖与控制规则，常见类型包括直接边、条件边、并行边、回环边、错误边、人工控制边和事件触发边。路由函数本质上是 State → 下一条边名 的纯函数。关键设计原则：能用确定性代码判断的路由，绝不用模型判断——"测试失败走修复节点、构建成功走发布节点"这类条件是纯代码逻辑；只有语义级的分流（这个问题属于退款还是技术支持）才交给 LLM 分类器。每多一处模型路由，就多一处不可复现的分支。

  • 直接边 / 条件边：固定流程与规则分支的骨架，条件边是 State 到边名的纯函数映射
  • 并行边 / 动态扇出（Send）：把一批子任务同时派发给多个执行节点，配合 Reducer 汇合
  • 回环边：验证不过就回炉重做——这正是被收编进图里的 Loop，且带次数上限
  • 错误边：重试耗尽后进入降级或人工兜底路径，阻断失败级联
  • 人工控制边 / 事件触发边：衔接 Interrupt 审批与外部事件（Webhook、定时器）

Reducer：并行扇出的合并规则

当图做扇出/扇入（fan-out/fan-in，把一路并行拆成多路再汇合）时，多个节点会在同一个超步里写同一个 State 键。没有 Reducer 时默认行为是覆盖——后写的赢，前面分支的成果凭空消失。以 LangGraph 为例，每个 State 键可以挂独立的 Reducer：标注 Annotated[list, operator.add] 的键会追加合并（适合证据列表、消息流），普通键则覆盖（适合草稿、计数器终值）。自定义 Reducer 还能实现去重、取最大值、按优先级合并等策略。

Checkpoint：把"重头再来"变成"断点续跑"

Checkpoint 在每个超步（super-step，图中一批可并行节点完成一次状态提交的执行单位）结束时把 State 快照落盘，按 thread_id 组织成线程。它一次解锁四种能力：崩溃后从最后成功步骤恢复；人工审批的持久暂停；时间旅行调试——回放任意历史步骤；以及在任意检查点分叉状态探索替代路径。更精细的机制是待写入保留：若某超步中一个节点失败，同一超步里已成功节点的写入会被保存，恢复时不重跑它们。

生产案例（成本账）：一个复杂智能体工作流要做 20 次 LLM 调用，每次 0.05 美元。没有 Checkpoint 时，进程在第 18 步崩溃意味着重跑全部 20 次调用，白白烧掉 1 美元；有 Checkpoint 时从第 18 步恢复，只为剩余 2 次调用付 0.1 美元。国内某 Agent 团队落地"检查点恢复 + 状态机快照"后，故障重启恢复时间从分钟级降至秒级；另一套分层超时 + 断点续跑方案把系统可用性从 78% 提升到 99.5%。

Interrupt：把人工审批建模成一等公民

高风险操作（对外付款、删除数据、给客户发邮件）前必须有人类把关，但"等人"可能持续数小时甚至数天，进程不可能一直阻塞。Interrupt 的解法是：节点内调用 interrupt(payload)，运行时把当前 State 通过 Checkpointer 落盘后无限期等待；审批人通过外部系统做出决定后，用 Command(resume=决定) 重新唤起图，interrupt 调用就地返回该决定，流程继续。Oracle 公开的差旅审批工作流就是这个模式：生成审批摘要 → checkpoint 到数据库 → interrupt 等审批人 → 用同一 thread_id 恢复并写入最终业务记录。

Interrupt 的工程规则有四条，全部指向同一个本质——它不是"暂停一个函数"，而是持久状态机上的检查点：不要把 interrupt 调用包进 try/except（暂停机制依赖异常传播）；不要调换同一节点内多个 interrupt 的顺序（恢复时按顺序重放）；payload 保持 JSON 可序列化、不传复杂对象；interrupt 之前已执行的副作用必须幂等（恢复时节点会在中断点之前重新执行）。

框架实现对照：六对象并非某一框架的私产

六大对象是图/工作流工程的通用抽象层，在不同运行时里有对应实现，选框架本质上是在选持久化形态与生态绑定。

差异在抽象侧重：LangGraph 围绕 LLM 节点做了深度优化（消息流、流式 token、模型分层），Temporal 带着微服务世界的持久化执行基因（付费客户已超 3000 家，含 Nvidia、Netflix），云托管服务则用灵活性换运维成本。六对象的设计方法是可移植的——用其中任何一家把图设计清楚，迁移到另一家主要是机械翻译工作。

六大对象的记忆锚点：State 是账本，Node 是工人，Edge 是路线图，Reducer 是仲裁员，Checkpoint 是存档点，Interrupt 是门禁。账本不先立，其余五样全是乱账。

四、可靠性五大约束机制

Graph 提供了骨架，可靠性来自约束。生产实践收敛出五大约束机制，前两条管"结果可信"，后三条管"过程可控"。

约束机制解决的问题落地要点
验收证据回溯"做完了"不等于"做对了"每个节点产出可验证证据（测试结果/校验记录），验收节点按证据回溯而非听信自述
节点类型隔离生成者自评必然自我表扬判断 / 执行 / 验证三类节点物理分离，验证节点由独立的怀疑者角色承担
幂等性保障重试造成重复副作用请求级幂等键（UUID 贯穿全程）；无法幂等的外部调用走 outbox 表 + 补偿事务
资源预算限制循环失控烧穿 Token 与时间次数上限（递归限制）、时间超时（分层超时）、Token 预算（单步约为模型上限的 70%）
State-Context 分离上下文膨胀拖垮每一跳State 只存结构化事实，长文档/原始材料放外部存储，按需注入

验收证据回溯与节点类型隔离

验收证据回溯要求每个执行节点的产出都附带可查验的证据——测试通过记录、编译日志、Schema 校验结果——验收节点依据证据链做判断，而不是采信执行者的自我陈述。判断/执行/验证三类节点隔离的经验依据来自生成器/评估器分离：让智能体给自己的输出打分时，它会系统性地倾向于自我表扬；而调教一个独立的怀疑者评估器，比让生成器变得自我批判容易得多。这就是验证节点必须与生成节点物理分离、而不是写在同一个提示词里当"自检步骤"的原因。

幂等性：重试的前提条件

图引擎的容错依赖重试，但重试只在节点幂等（idempotency，同一操作执行一次与执行多次产生相同结果）时才安全。生产系统通常三层设防：给每次调用携带由图运行 ID + 步骤号派生的确定性幂等键，服务端先查键再执行；对不支持幂等的外部 API 采用 outbox 模式——先把调用意图写入本地表，由独立处理器发出并记录结果，崩溃也不丢不重；对天然不可逆的动作（已发出的邮件）准备同样幂等的补偿动作（发更正通知）。Saga 编排模式在月处理超千万次智能体交互的系统中验证了这套组合拳。

执行层保障：Loop 级与 Graph 级双层防线

┌──────────────────────── Graph 级：多节点拓扑管理 ────────────────────────┐ │ 并行调度 · 错误边回退 · 全局预算 · Checkpoint 恢复 · Interrupt 审批 │ │ │ │ ┌──────────── Loop 级：单节点内自修正 ────────────┐ │ │ │ 提示 ──▶ 执行 ──▶ 检查 ──▶ 反馈 │ │ │ │ ▲ │ │ │ │ │ └──── 未达标则重跑（retry_count 上限 N）◀──┘ │ │ └────────────────────────────────────────────────┘ │ │ │ │ Node1(含Loop) ──▶ Node2(含Loop) ──▶ 验证节点 ──▶ 审批 ──▶ END │ └──────────────────────────────────────────────────────────────────────────┘
层级职责典型机制失守后果
Loop 级单节点内把活干对提示→执行→检查→反馈循环、独立评估器、重试上限节点产出质量差，污染下游所有节点
Graph 级多节点之间不出乱子确定性路由、并行合并、容错回退、状态快照、预算熔断复合失败级联，局部错误放大为全局事故

两层防线各管一段、互为兜底：Loop 级保证单点质量，Graph 级保证单点质量不够时系统不崩。一个常见的误区是把所有可靠性都压给 Loop——在节点内疯狂加自检——结果循环越套越深，提示词膨胀到四千 token、单步延迟 45 秒，最后还是靠图级的错误边和预算熔断才稳住。经验数据：分层超时策略（工具调用级、节点思考级、任务级三层独立超时）配合图级熔断，是可用性提升最显著的单点改造。

可靠性公式：单节点质量决定下限，图的约束决定上限。Loop 级管"一次做对"，Graph 级管"错了也不炸"。

五、能力边界与协作策略

Graph 工程是控制流工程，不是智能本身。它的能力范围非常清晰：管控确定性流程——节点调度顺序、状态转移、并行汇合、重试回退、预算熔断，这些全部是图的领地；而模型固有缺陷——幻觉、数据偏见、推理错误——图无法消除，只能验证与兜底。把 Graph 当成提升模型智商的手段，是这一范式最常见的误用。

问题类型确定性交给谁具体手段
节点执行顺序 / 依赖确定Graph拓扑声明、普通边
规则化路由（金额阈值、测试成败）确定Graph（代码）条件边纯函数实现
语义理解 / 意图分类非确定模型LLM 节点 / 分类器边
内容生成 / 规划非确定模型生成节点 + 独立验证节点
幻觉抑制混合双重保险模型侧检索增强 + 图侧证据验证门
数据偏见—模型 / 数据层Graph 无能为力，需训练与数据治理

Graph 护栏 vs 纯模型：可靠性的量化对比

回到复合失败的数学。纯模型驱动的 Loop 里，每一步的成功率就是模型当次的发挥，十步任务的端到端成功率约为 0.95 的十次方 ≈ 60%。Graph 护栏做的事情是提高"有效单步成功率"：节点失败后有受控重试（如最多 3 次、指数退避），重试仍失败走错误边进入降级路径或人工兜底，而不是级联崩溃。假设受控重试把单步有效成功率从 95% 提到 99.5%，同样的十步任务端到端成功率就从 60% 回到 95% 以上——这就是护栏的价值：不改变模型，改变失败的传播方式。

生产案例（护栏效果）：行业调研显示 57% 的组织已有某种形态的生产级智能体，但工程负责人对各组件成熟度评分时，可观测性始终垫底——系统"平均表现好、边缘死得惨"。引入图级约束（每超步快照、全链路追踪、预算熔断）的团队，故障定位从"翻日志猜迭代"变为"回放指定检查点"，配合分层超时将可用性从 78% 提升至 99.5% 的案例已在多个团队复现。

双重保险：确定性给 Graph，非确定性给模型

正确的协作策略是分工而非二选一：凡是能写成规则的——顺序、阈值、重试次数、审批门槛、预算——全部下沉到图里用代码表达；凡是需要理解与创造的——读懂需求、写方案、解释歧义——留给模型节点。两边互为保险：图保证模型即使犯错也在受控范围内传播（错误边 + 验证门拦截），模型的语义能力弥补图无法处理模糊地带的缺口。这条边界也决定了 Graph 工程的职业定位：它不替代模型工程，它是模型能力进入生产环境的准入安检。

Graph 治不了模型的病，但能防止病扩散。确定性逻辑交给图是免费午餐，非确定性推理留给模型是必要成本，双重保险才是生产级。

六、实施路径：护栏而非疫苗

图工程对行业的定位要清醒：它是系统护栏，不是万能疫苗。护栏的意思是——车（模型）本身必须能开，护栏只保证冲出路面时不坠崖；指望 Graph 拯救一个能力不达标的模型，只会得到一个更精密地生产错误答案的系统。

阶段动作验收标准
① 画拓扑先设计 Graph 再实现 Edge：列出全部节点与分支，画出完整流程图任何一次真实任务都能在图上走完一条路径
② 立 State定义带类型 Schema，明确每个键的读写方与 Reducer节点间零隐式传参，"不在 State 即不存在"
③ 拆节点按可验收性划分判断 / 执行 / 验证节点，确定性逻辑用代码节点每个节点可独立测试、可独立判定对错
④ 接持久化挂 Checkpointer（开发用 SQLite、生产用 Postgres），高风险点插 Interrupt杀进程后能从最后检查点续跑；审批可跨天恢复
⑤ 收紧约束从 Prompt 到 Graph 逐级收紧：加预算、幂等键、证据回溯、错误边单步预算熔断生效；重复执行无重复副作用

"先设计 Graph 再实现 Edge"是这一路径中最反直觉也最重要的一条：多数团队的失败路径是先写节点、边跑边补路由，最后拓扑是长出来的而不是设计出来的，隐藏分支遍地。正确顺序是先穷举节点与分支（此时边只是纸上的线），确认覆盖所有真实路径后，再逐条把边实现为确定性函数。"分层约束逐级收紧"则意味着不要一步到位：先靠 Prompt 层跑通，观察哪里失灵，再在失灵处叠加 Loop、Harness、Graph 层的约束——每加一层都应对应一个已观测到的具体失败模式。

  • State Schema 先于一切节点代码落笔
  • 规则化路由一律用纯函数条件边
  • 高风险副作用节点前插 Interrupt 审批
  • 每个 LLM 节点设 Token/次数/时间三重预算
  • 生产 Checkpointer 用 Postgres 等持久存储
  • 验证节点与生成节点物理隔离、角色对立
  • 不要在 while 循环里堆 if 分支制造隐式拓扑
  • 不要让模型决定可以写成代码的路由
  • 不要在没有 Reducer 的键上做并行扇出
  • 不要用内存 Checkpointer 跑生产环境
  • 不要把完整对话历史塞进每个节点（State-Context 不分）
  • 不要指望 Graph 修复幻觉——它只能拦截，不能根治

最后算一笔护栏的投资回报账。图工程的成本有三项：前期设计（画拓扑、立 State）、运行时开销（检查点存储、验证节点的额外调用）、认知负担（团队需理解图语义）。对应的收益是：崩溃重跑成本从全量降到剩余步骤、故障定位从小时级翻日志变为分钟级回放检查点、高风险操作获得完整审计链。经验阈值是：当系统满足"单任务步骤数 ≥10、单次运行成本达美元级、含外部副作用"三条中的任意一条时，收益端就开始明显压过成本端；三条全不满足时，先用 Loop + Harness 把问题跑出来再说。

实施顺序口诀：先画图、再立账（State）、后招工（Node）、修路（Edge）、设卡（Checkpoint/Interrupt）、收网（约束）。护栏是给会开的车装的，不是给不会开的车装的。

Q&A

Loop 工程和 Graph 工程是代际替代关系吗？
不是替代，是收编。从图论角度看，一个自修正循环就是一个带自环边的单节点有向图，所以 Loop 天然是 Graph 的子集。Graph 工程出现后，循环没有消失，而是退居为节点内部的局部机制；节点之间的调度、分支、汇合、暂停则上收到图的拓扑层统一管理。实践中五层架构（Prompt/Context/Loop/Harness/Graph）是包裹关系：图里的每个节点内部仍然跑着自己的 Prompt、上下文注入和自修正循环。
为什么 State 必须先于节点定义？
因为 State 是图内唯一真相源，节点的输入输出契约全写在 State Schema 上。先定义 State 能带来三个直接收益：一是把节点间的信息流全部显性化，禁止全局变量和隐式传参，"不在 State 里的东西就等于不存在"；二是让每个节点只通过局部更新合并的方式改状态，避免多节点原地变异同一个对象造成状态混乱；三是从源头抑制上下文膨胀——节点按需读取 State 中的结构化事实，而不是每个节点都背着完整对话历史。反过来先写节点再补 State，得到的 Schema 必然是迁就实现的流水账。
边（Edge）的路由为什么优先用代码而不是模型判断？
因为路由是整个系统里被遍历次数最多的决策点，它的不确定性会被每一跳放大。"测试失败走修复节点、金额超阈值走审批节点"这类条件是纯确定性逻辑，用纯函数实现可复现、可单测、零成本；交给模型判断则每次路由都是一次采样，分支不可复现、调试无从下手。只有语义级分流（用户意图属于退款还是咨询）才值得引入 LLM 分类器。工程经验是：每把一处确定性路由替换成模型路由，就多一个无法枚举测试的隐藏分支。
Reducer 主要解决什么问题？纯串行图需要它吗？
Reducer 解决并行写入冲突：当图做扇出/扇入时，多个节点在同一个超步里写同一个 State 键，默认覆盖语义会让后写的分支抹掉先写分支的成果。框架里每个 State 键可以挂独立 Reducer——追加合并适合证据列表和消息流，覆盖适合草稿这类"只留最新"的字段，还可以自定义去重、取极值等策略。纯串行图确实很少触发写冲突，但显式声明 Reducer 仍是好习惯：一是拓扑将来大概率会演化出并行分支，二是它强制你思考每个键的合并语义，避免"默认覆盖"埋雷。
Checkpoint 的存储怎么选？不做 Checkpoint 的实际代价是什么？
选型按环境分：开发调试用内存或 SQLite 检查点即可，生产必须用 Postgres 等持久化存储，并保证 checkpoint 写入与业务数据同库或同事务边界，方便审计。不做 Checkpoint 的代价可以直接算钱：一个 20 次 LLM 调用、单次 0.05 美元的工作流，在第 18 步崩溃后只能从头重跑，浪费 1 美元；有检查点则只重付剩余 2 次的 0.1 美元。此外 Checkpoint 还是人工审批、时间旅行调试、状态分叉的共同前提——它是图工程里投入产出比最高的单一组件。
Interrupt 和"阻塞等待用户输入"有什么本质区别？
阻塞等待要求进程活着并占用资源，审批等待数小时到数天完全不可行；Interrupt 是持久化暂停——触发时运行时把当前 State 经 Checkpointer 落盘，进程可以直接退出，图无限期挂起；审批人在外部系统做出决定后，用同一个 thread_id 携带恢复指令重新唤起，interrupt 调用就地返回审批结果继续执行。所以 Interrupt 必须建模为图的一等对象并与 Checkpoint 绑定：没有检查点的中断无法跨进程恢复，没有中断的检查点则缺少人类把关的入口。两者合起来才构成完整的 human-in-the-loop。
Graph 工程能消除模型幻觉吗？
不能消除，只能拦截与兜底。Graph 是控制流工程，管的是节点调度、状态转移、重试回退这类确定性问题；幻觉和数据偏见是模型内部的生成缺陷，图结构碰不到。图能做的是双重保险里的那一重：设置独立的验证节点按证据回溯、在高风险副作用前插人工审批、用错误边把可疑输出导入降级路径。正确预期是——Graph 让幻觉造成的损害可控、可回滚、可追责，但根治幻觉仍要靠检索增强、模型选型与数据治理。
什么情况下不值得上 Graph 工程？
三类情况不值得。一是任务步骤少（三五步以内）、单步失败重跑成本低，此时一个带重试的 Loop 加 Harness 约束就够了，上 Graph 属于过度设计；二是需求极不稳定、流程本身每周都在变，过早固化拓扑反而成为迭代负担，应先用 Loop 快速试错；三是底层模型能力明显不达标——图是护栏不是疫苗，节点里的模型干不好活，图设计得再精密也只是更稳定地输出错误。判断标准很朴素：只有当复合失败率、崩溃重跑成本、人工审批需求中至少一项真实出现时，Graph 的投入才开始回本。
Graph 工程和传统工作流引擎（Airflow、BPMN）有什么区别？
两者思想同源——把控制流显式化——但设计目标不同。传统工作流引擎假设每个步骤的执行体是确定性的（SQL 任务、数据管道），状态轻量、失败模式单一。图工程框架为 LLM 工作流而生：节点执行时间跨度从秒到小时、输出非确定、人工审批可能等待数天、token 成本需要逐步计量。因此图框架提供了传统引擎没有的一等公民能力——非确定输出的 Reducer 合并、可跨进程暂停恢复的 Interrupt、消息流式输出、模型分层调度。工程经验是可迁移的：熟悉 Airflow 或 Step Functions 的团队，可以把图工程理解为"工作流引擎加上 LLM 原生扩展"。
