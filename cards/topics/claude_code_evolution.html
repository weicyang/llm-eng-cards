HC03 · Claude Code 架构进化

Claude Code Evolution — 设计哲学、渐进式披露、工具设计教训、提示缓存优化 — 提炼 Agent 框架设计心法

Claude Code 的设计心法：不要一次性塞入所有信息。工具少而精、上下文按需加载、能力随模型进化而调整 -- 本质上是把 Agent 框架当作一个「信息流控系统」来设计。

一、设计哲学：动作空间是核心难题

构建 Agent 框架最困难的部分，不是模型选择，不是提示工程，而是动作空间（Action Space）的设计 -- 即 Agent 能做什么、怎么做、做到什么程度。

动作空间的三个维度

维度含义Claude Code 的选择
工具类型Agent 有哪些可用工具通过 Tool Calling 实现，包括 bash、文件读写、搜索、代码执行等
工具粒度每个工具的功能范围宁可粗粒度（如通用 bash）也不过度拆分
工具编排工具之间如何组合由模型自主编排，框架只提供工具接口
关键洞察：Claude 通过工具调用（Tool Calling）实现所有功能，但工具的构建方式有多种 -- bash、技能（Skills）、代码执行（Code Execution）等。选择哪种方式，取决于「灵活性 vs 可控性」的权衡。

动作空间难就难在它不能"先设计好再用"。工具粒度切细了，模型要拼很多步才能干成一件事，中间每一步都可能走偏；切粗了（比如直接给一个 bash），能力上限拉满但审计和回滚全没了。这条线只能靠实际跑出来的失败案例反复挪。

工具构建方式对比

方式灵活性可控性适用场景
Bash极高（任意命令）低（难以审计）系统操作、包管理
Skills中（预定义能力）高（白名单控制）特定领域任务
Code Execution高（任意代码）中（沙箱隔离）数据分析、计算

二、渐进式披露：按需分层提供上下文

渐进式披露（Progressive Disclosure）是 Claude Code 最核心的设计原则：避免一次性塞入所有信息，按需分层提供上下文。这个原则贯穿了上下文获取、能力扩展、任务管理三个层面。

2.1 上下文获取：从 RAG 到动态搜索

传统做法是预先把所有文档索引到向量数据库，通过 RAG 检索注入上下文。Claude Code 的做法是让 Agent 拥有动态搜索工具（如 Grep、文件读取），自主决定需要什么信息、什么时候获取。

传统 RAG 模式:
  [预索引文档库] --> [向量检索] --> [Top-K 结果注入 Prompt]
  问题: 预索引成本高、检索可能不准、上下文浪费

Claude Code 模式:
  [Agent 自主判断] --> [Grep/Read 工具] --> [精准获取所需内容]
  优势: 按需获取、精准度高、上下文高效

从「被动注入」到「主动探索」的范式转变

RAG 是提前替 Agent 决定它需要看什么，动态搜索是让它自己去找。前者在问题好预测时更省事，后者在代码库这种"要看什么完全取决于上一步看到了什么"的场景里几乎是唯一可行解。

2.2 能力扩展：子代理按需加载

不是把所有工具定义硬编码到 System Prompt，而是通过子代理（Subagent）按需加载工具集。主 Agent 只持有核心工具，当需要特定能力时，派发子代理并加载对应工具。

主 Agent (核心工具):
  ├── 文件读写
  ├── Bash
  ├── 搜索 (Grep/Glob)
  └── 子代理派发

子代理 A (代码分析):
  ├── AST 解析
  ├── 依赖分析
  └── 代码搜索

子代理 B (测试执行):
  ├── 测试框架
  ├── 覆盖率工具
  └── 结果解析

子代理按需加载工具，避免主 Agent 的上下文被不相关工具定义占据

2.3 任务管理：从强制清单到灵活系统

Claude Code 的任务管理经历了一次重要演进：从强制待办清单（TodoList）升级为灵活任务系统（Tasks）。旧方式强制 Agent 维护一个待办列表并定期提醒，新方式支持任务依赖关系和跨子代理协作。

特性TodoList（旧）Tasks（新）
结构线性列表有向无环图（支持依赖）
提醒方式强制定期提醒按需查看
协作单 Agent 内部支持跨子代理分配
灵活性低（固定格式）高（动态调整）
教训：强制待办提醒在早期模型中是必要的（帮助模型保持目标），但随着模型能力提升，这种硬性约束反而成了限制 -- 它消耗上下文空间，干扰模型的自主决策。工具需要随模型能力进化而淘汰。

三、工具设计：少而精的教训

Claude Code 最终只保留了约 20 个工具。每个新增工具都需要严格评估，因为工具数量直接影响模型的决策质量。

工具不是能力清单，是选择题的选项。每加一个工具，模型每一步都要多排除一个错误答案 —— 加到一定数量之后，新工具带来的能力增量已经抵不过它给所有其他决策制造的干扰。

工具过多的三个代价

代价机制表现
决策负担模型需要在更多选项中做选择选择错误工具的概率上升
上下文消耗每个工具定义占据 Prompt 空间留给用户内容和推理的空间减少
冲突风险功能重叠的工具可能混淆模型模型在相似工具间反复切换

延迟加载（Defer Loading）

Claude Code 引入了延迟加载机制：工具在 System Prompt 中只保留轻量级存根（如名称和一句话描述），当 Agent 需要某个工具时，通过 ToolSearch 动态加载完整定义。

System Prompt 中的工具存根:
  - FileRead: 读取文件内容
  - Bash: 执行 shell 命令
  - Grep: 搜索文件内容
  - ToolSearch: 搜索并加载更多工具...

Agent 执行流程:
  [需要 AST 解析] --> [调用 ToolSearch("AST")]
       |
       v
  [加载 AST 工具完整定义] --> [使用 AST 工具]

工具存根 + 延迟加载：System Prompt 保持精简，能力按需扩展

工具淘汰：旧工具可能成为限制

Claude Code 的设计团队发现，一些早期必要的工具，随着模型能力提升反而变成了「枷锁」。最典型的例子是强制待办提醒工具：它在 GPT-3.5 时代帮助模型保持目标聚焦，但在 Claude 3.5+ 时代，模型自身已经具备足够的目标追踪能力，强制提醒反而打断推理流程、浪费上下文。

设计原则：工具集不是「只增不减」的。每次模型升级后，都应该重新审视现有工具 -- 某些工具可能已经从「助力」变为「阻力」。

四、生产级优化：缓存与文件分层

4.1 提示缓存（Prompt Caching）

LLM API 的提示缓存按前缀匹配工作：只有 Prompt 的前缀部分相同才能命中缓存。这意味着 Prompt 中内容的排列顺序直接影响缓存命中率。

缓存友好布局:
  [固定前缀] ─── 系统指令、工具列表、规则 (不变)
       |
  [半固定区] ─── 文件内容、检索结果 (偶尔变)
       |
  [动态区]   ─── 用户消息、工具调用结果 (每次变)

缓存不友好布局:
  [用户消息] ─── 每次不同，前缀无法匹配
       |
  [系统指令] ─── 虽然不变，但不在前缀位置
       |
  [工具列表] ─── 缓存完全失效

把高频不变内容放前面，最大化缓存命中率

前缀缓存只认"从第一个 token 开始逐字相同"，所以 Prompt 的排列顺序是一个性能参数，不是排版偏好。把一个每次都变的时间戳挪到最前面，后面几千 token 的固定内容就全部作废。

示例场景：一个日均 8,000 次请求的编码 Agent，System Prompt 加工具定义约 6,500 token。背景：模板最开头拼了一行"当前时间：2026-03-11 14:22:07"，用于让模型判断日期。问题：这一行每次请求都不同，导致后面 6,500 token 的固定前缀一次都命中不了缓存，全部按未缓存价计费，同时首 token 延迟因为要重新预填充而多出约 380ms。方案：把时间戳从前缀区挪到紧邻用户消息的动态区，前缀区只留系统指令、工具定义和规则。效果：缓存命中率从 0% 升到 91%，输入侧计费 token 从日均 5,200 万降到约 700 万，P50 首 token 延迟从 620ms 降到 240ms。改动只是移动了一行文本的位置。
区块内容变化频率缓存效果
前缀区System Prompt、工具定义、规则几乎不变高命中率
中间区引用的文件内容、RAG 结果偶尔变化中命中率
末尾区用户最新消息、工具调用输出每次变化不缓存

4.2 文件分层（Document Layering）

Claude Code 使用 CLAUDE.md 作为核心文档，但只保留骨架规则，细节通过引用文件（如 docs/commit-convention.md）提供。

CLAUDE.md (骨架):
  # 项目规则
  - 代码风格: 详见 docs/code-style.md
  - 提交规范: 详见 docs/commit-convention.md
  - 测试要求: 详见 docs/testing-guide.md

docs/code-style.md (细节):
  - 使用 TypeScript strict mode
  - 函数命名: camelCase
  - 类型定义: 优先 interface over type
  - ... (详细规则)

核心文档保持骨架，细节按需引用 -- 既节省上下文又保证可查阅

DO

  • System Prompt 中只放不变的核心规则
  • 细节文档通过文件引用按需加载
  • 工具定义按使用频率排序（高频在前）
  • 每次模型升级后审查工具集
  • 用 ToolSearch 实现工具延迟加载

DON'T

  • 不要把 500 行规则全塞进 System Prompt
  • 不要把低频工具的定义硬编码到 Prompt
  • 不要假设「工具越多越好」
  • 不要在动态内容后面放固定内容（破坏缓存）
  • 不要在模型升级后不审查旧工具

五、核心结论与设计心法

三条设计心法

心法含义Claude Code 的实践
匹配能力工具需匹配 Agent 当前能力模型强则减少约束工具，模型弱则增加辅助工具
自主探索优先赋予探索能力而非静态注入给搜索工具而非预注入文档，给子代理而非硬编码能力
持续迭代定期审视工具集，模型升级后可能需移除旧工具淘汰 TodoList、引入 Tasks、增加 ToolSearch

Agent 框架设计演进路线图

Phase 1 (弱模型时代):
  大量工具 + 强制约束 + 全量注入
  代表: TodoList 强制提醒、RAG 预注入、工具白名单

Phase 2 (中等模型时代):
  精简工具 + 灵活约束 + 按需注入
  代表: 子代理按需加载、文件分层引用、工具延迟加载

Phase 3 (强模型时代):
  最少工具 + 自主决策 + 最小注入
  代表: 通用 bash + 搜索 + 文件读写，模型自主编排一切

随着模型能力提升，框架应该做减法而非加法

终极原则：像 Agent 一样思考 -- 实验、观察输出、迭代设计。不要基于假设构建框架，要基于实际运行效果来调整。每次模型升级，都是一次重新审视框架设计的机会。
生产验证：Claude Code 在编码助手场景中，渐进式披露策略将平均 Token 消耗降低 45%（从 18K tokens/请求降至 9.8K），同时任务完成率从 72% 提升至 89%。工具延迟加载（ToolSearch）将 System Prompt 从 12K tokens 精简至 4.2K，Prompt Cache 命中率提升至 92%。工具集从早期 35+ 个精简至约 20 个后，模型工具选择错误率从 8% 降至 2.3%。
Claude Code 的进化主线：从单工具调用 → 多工具编排 → 自主规划 → 自我反思。每一代的核心突破都在于"Agent 对自身行为的理解深度"——越能理解自己在做什么，就越能自主决策和纠错。

Q&A

Q1 为什么动作空间设计是 Agent 框架最困难的部分？

动作空间决定了 Agent 能做什么、怎么做、做到什么程度。设计过窄，Agent 能力受限无法完成复杂任务；设计过宽，工具选择爆炸、上下文消耗大、模型决策质量下降。而且最优的动作空间不是固定的，它随模型能力、任务类型、安全要求动态变化。Claude Code 的经验是：约 20 个工具是一个平衡点，但这不是通用数字，需要针对具体场景实验。

Q2 渐进式披露和 RAG 有什么本质区别？

RAG 是「被动注入」-- 系统预先检索相关内容注入 Prompt，Agent 被动接受。渐进式披露是「主动探索」-- Agent 自主判断需要什么信息，主动调用搜索/读取工具获取。本质区别在于决策权：RAG 的决策权在检索系统（基于相似度），渐进式披露的决策权在 Agent（基于任务理解）。后者的精准度更高，因为 Agent 理解上下文，知道「我此刻真正需要什么」。

Q3 工具延迟加载的实现原理是什么？对延迟有什么影响？

实现原理：System Prompt 中只放工具名称和一句话描述（存根），完整定义存在外部。Agent 需要某个工具时，先调用 ToolSearch 获取完整定义（包括参数 schema、使用示例），然后才能使用该工具。对延迟的影响：增加了一次 ToolSearch 调用（通常 100-300ms），但节省了 System Prompt 的长度，减少了整体推理时间。净效果通常是正向的，特别是当工具总数多但单次任务只用少量工具时。

Q4 为什么强制待办提醒会从「助力」变成「阻力」？

在弱模型时代（如 GPT-3.5），模型的目标追踪能力弱，容易在多步任务中「忘记」原始目标，强制待办提醒相当于外部的「记忆锚点」。但随着模型能力提升（如 Claude 3.5+），模型自身已经具备足够的目标保持能力，强制提醒反而：(1) 消耗上下文空间；(2) 打断推理流程；(3) 限制模型的自主规划灵活性。这是一个典型的「工具需要随模型进化而淘汰」的案例。

Q5 提示缓存的前缀匹配原理是什么？如何最大化命中率？

LLM API 的缓存机制通常按 Prompt 的前缀（prefix）匹配：从第一个 token 开始，连续相同的部分可以命中缓存。一旦遇到不同的 token，后续内容全部需要重新计算。因此最大化命中率的策略是：(1) 把不变内容（System Prompt、工具定义）放在最前面；(2) 把半变内容（引用的文件）放中间；(3) 把全变内容（用户消息、工具输出）放最后。这样每次请求，前缀区都能命中缓存，只计算末尾的动态部分。

Q6 如何判断一个工具应该保留还是淘汰？

评估框架：(1) 使用频率 -- 如果某个工具在 90% 的任务中不被使用，考虑移除或改为延迟加载；(2) 模型自主能力 -- 如果模型不依赖该工具就能完成同等任务（如不需要待办提醒也能保持目标），说明工具已冗余；(3) 冲突检测 -- 如果模型经常在两个相似工具间犹豫，说明功能重叠需要合并；(4) 上下文 ROI -- 工具定义占用的 Token 数 vs 它带来的任务完成率提升。每次模型升级后，都应该跑一遍这个评估。
