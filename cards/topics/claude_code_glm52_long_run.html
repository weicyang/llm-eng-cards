HC11 · Claude Code 长时自治运行与 GLM 5.2

按字幕重构：GLM 5.2 真正抬高的，是 Claude Code 的长时工程可用性；长时任务的上限，最终由运行时、任务拆解和上下文治理决定。

长时执行不是"让模型多聊一会儿"，而是一个系统工程问题：把任务拆成可验收的最小单元、把进度外置到文件、让运行时循环驱动执行——模型只需要"够用托底"，剩下的交给工程。

一、这场13小时实测证明了什么

本视频的核心不是"GLM 5.2 答得更好"的能力展示，而是一场完整的 长时执行（Long-Running，智能体长时间无人值守、持续推进任务的执行模式）实测：把 GLM 5.2 接入 Claude Code，让它在 40 多万行 TypeScript 的真实项目上自动运转，全程无人值守 13 小时。

实测数据含义
40 万+ 行 TypeScript对象不是 demo，而是大规模真实代码库
13 小时无人值守系统具备长时间持续推进的能力
30+ 份 spec 文件（需求/设计说明文档）不是"上来就写代码"，而是先规划、先拆解
443 个带验收标准的任务每个任务可独立检查是否完成，循环执行有"裁判"
这类成果的关键，不是一次性代码生成，而是让模型在非常长的时间里保持目标一致。四组数字合起来证明一件事：Agent 已经具备从"聊几轮"到"交付完整工程流程"的过渡条件——前提是工程方法跟上。

13 小时 × 443 个任务，意味着系统平均约 1.7 分钟闭环一个任务——这不是"模型写得快"，而是"循环没停、没跑偏、没谎报完成"。

二、全流程：需求分析 → 任务拆解 → 开发 → 测试

视频把完整的长时执行流程抽象为四个阶段，缺一个都会让循环跑不稳：

┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ 需求分析 │ → │ 任务拆解 │ → │ 开发 │ → │ 测试 │ │ 读代码库 │ │ 写 spec │ │ go 循环 │ │ 独立评估 │ │ 明确目标 │ │ 拆任务 │ │ 逐个执行 │ │ 不过则返工 │ └────────────┘ └────────────┘ └────────────┘ └────────────┘ │ │ ↓ │ 30+ spec、443 任务 ←── 反馈驱动修正 ─────────┘ （每个任务带验收标准）
阶段Agent 做什么产出
需求分析阅读代码库与架构，明确迁移/开发目标全局理解、约束清单
任务拆解把目标拆成最小单元，每个附上验收标准30+ 份 spec 文件、443 个任务条目
开发go 循环：读进度 → 执行任务 → 更新进度代码改动、git 提交
测试独立评估验收标准是否满足通过/不通过结论 + 反馈

四个阶段的顺序不能颠倒：没有需求分析，拆解就会跑偏；没有拆解，开发就是一团乱麻；没有独立测试，"完成"只是 Agent 的一面之词。

最容易被忽略的是"测试"阶段的独立性——评估不是执行 Agent 干完活后的自我表态，而是一个独立的判断步骤：不达标就带着反馈进入下一轮。这种"执行-评估分离"是降低假阳性（谎报完成）的核心机制，也是 443 个任务能逐个闭环的原因。

三、长时执行的六个工程方法

13 小时能跑下来，靠的不是一句超级提示词，而是六个具体的工程方法：

go 命令循环（每轮执行一次）： ┌──────────────────────────────────────────┐ │ ① 读进度文件（当前哪个任务没做完） │ │ ↓ │ │ ② 执行当前任务（按 spec 与验收标准） │ │ ↓ │ │ ③ 独立评估（是否通过验收？） │ │ ├── 未达标 → 带着反馈进入下一轮 │ │ └── 达标 → git commit（留检查点） │ │ ↓ │ │ ④ 更新进度文件 → 回到 ① │ └──────────────────────────────────────────┘
方法具体做法解决什么问题
最小单元拆解任务拆到可独立验证的粒度，每个附验收标准模型"谎报完成"
进度外置任务状态写入进度文件，每轮先读进度再执行上下文压缩后状态丢失
go 命令循环把"读进度 → 执行 → 评估 → 更新"封装成循环命令长时执行需要人不断推动
bypass permissionsshift+tab 切换到 bypass permissions 模式权限弹窗打断无人值守执行
单行启动提示词提示词压成单行（go 会把提示词塞进 hook 的 JSON，换行会导致格式报错）hook JSON 解析失败
git 检查点每完成一个功能就 git commit跑偏后无法回滚

进度外置的本质是"不信记忆，信文件"：上下文会被压缩、会话会丢，但进度文件永远在。13 小时后 Agent 还能从断点继续，靠的就是记忆放在脑子外面。

两个细节特别能体现工程味道：一是启动提示词必须压成单行，因为 go 命令会把提示词塞进 hook 的 JSON 数据里，换行会直接破坏格式——这种坑在任何官方文档里都找不到，只能靠踩；二是开跑前要用 shift+tab 切到 bypass permissions，否则每隔几分钟弹一次权限确认，13 小时无人值守就成了笑话。当然，bypass permissions 的前提是工作区隔离可控。

四、模型与运行时的分工

视频给出的结论非常工程化：长时执行能力不是模型的独角戏，而是模型与运行时的合奏。Context Engineering（上下文工程，系统性地管理模型能看到的信息以维持其行为稳定）是两者的结合点。

┌───────────────────────┐ ┌───────────────────────┐ │ 模型层（GLM 5.2） │ │ 运行时层（Claude Code）│ │ │ │ │ │ 理解代码与需求 │ │ 任务调度（go 循环） │ │ 生成代码改动 │ ←──→ │ 文件读写 │ │ 遵循任务指令 │ │ 进度管理 │ │ 长上下文保持 │ │ 验收组织 │ │ │ │ 权限 / 检查点 │ └───────────────────────┘ └───────────────────────┘ 模型负责"想" 运行时负责"管" 模型能力决定下限：理解不了代码，一切无从谈起 运行时设计决定上限：没有调度、进度、验收， 再强的模型也只是"聊天顾问"，不是"工程师"
维度模型层职责运行时层职责
理解读代码、理解需求提供文件访问、搜索工具
生成写代码、写 spec落盘、格式校验
指令遵循遵循验收标准与约束把 spec 与进度注入上下文
状态短期工作记忆长期进度文件、git 历史
质量自我检查独立评估、反馈闭环
分工一句话：模型管理解/生成/遵循指令，Claude Code 管调度/文件/执行/进度/验收。模型是工程师的脑子，运行时是工程师的工位、流程和质检体系——脑子再强，没有工位和质检，交付照样不靠谱。

不要问"哪个模型更聪明"，要问"哪个模型够用托底"。过了托底线之后，模型能力的边际收益，远低于运行时设计的边际收益。

五、为什么长上下文能力决定 Agent 上限

视频给出了一个对比鲜明的对照实验：同样的任务，旧的 200K 上下文模型跑到中途直接上下文爆炸报错，无法跑完全程；换成 GLM 5.2 后才完成全程。差距不在"200K 不够大"这个数字本身——而在于长时执行中，日志、历史对话、工具结果、规划文件会持续累积，模型在长上下文中抓重点的能力，决定了它 13 小时后还能不能做对事。

维度旧 200K 模型GLM 5.2
长时结果中途上下文爆炸报错13 小时跑完全程
上下文窗口200K，长时任务捉襟见肘大窗口，容错空间更高
指令遵循长历史中容易目标漂移有改进，能遵循 spec 与验收标准
工程意义只能做短任务或重度人工干预具备长时执行托底资格
背景：作者需要在一个 40 万+ 行 TypeScript 的真实项目上完成大规模迁移与开发，预期全程由 Agent 自动完成。
问题：旧的 200K 上下文模型执行到中途就报上下文爆炸错误——任务拆解好了，却跑不到终点，长时执行半途而废。
方案：换用 GLM 5.2（大窗口 + 指令遵循改进），并配套任务拆解、进度外置、go 循环、bypass permissions、单行提示词、git 检查点六件套。
效果：13 小时无人值守，产出 30+ 份 spec 文件和 443 个带验收标准的任务，全程跑完无需人工接管。

"名义窗口大小"和"长任务中的真实可用性"是两回事：前者是装得下多少，后者是装完之后还能不能找到重点。旧模型爆炸不是因为装不下，而是因为装完后丢了焦点。

六、演示：OpenClaw 的能力与边界

视频的演示环节把 Python 版 OpenClaw 接入网页对话，具体展示了"Agent 能做什么、边界在哪里"：

能力演示表现背后机制
长期记忆记得自己叫"小白虾"，叫用户"老板"记忆模块持久化人设
工具调用能查天气接了天气 MCP 插件
技能扩展能用 skill 生成图片、读写文件加载了对应 Skill
能力边界答不出今天日期没装日期插件——是工具缺失，不是模型不行
背景：演示中 Agent 接了记忆模块（人设：自己叫"小白虾"，叫用户"老板"）和天气 MCP 插件，还能用 skill 生成图片、读写文件。
问题：用户问"今天几号"，Agent 答不出来——很多人第一反应是"模型太笨"。
方案：真实原因是只装了天气插件、没装日期插件；模型本身不知道实时日期，工具集里也没有能查日期的工具。
效果：这个案例精确划出了 Agent 的能力边界：能力 = 模型能力 × 工具配置，缺一个就露怯。补一个日期 MCP 插件即可解决，完全不需要升级模型。

视频也诚实指出了 GLM 5.2 的能力边界：它仍是纯文本模型，页面审美偏弱，无法靠截图定位前端 bug。这意味着视觉验证环节仍然需要人参与——长时执行自动化的是"可验证"的部分，"不可验证"的部分要交还给人。

日期问题的本质：Agent 的能力边界 = 模型能力 × 工具配置。别把工具缺失怪到模型头上，也别指望模型硬扛工具该干的事。

七、长时执行工程清单

方法字幕传达的核心含义
先规划再执行先整理代码库与架构，再进入迁移与开发，不让模型"直接开写"
任务必须可验收每个任务有明确完成标准，否则循环执行容易漂移
进度必须外置让模型从任务文件读取未完成项，而不是只依赖聊天上下文记忆
执行必须闭环完成后要验证，未达标则带着反馈进入下一轮修正
长上下文决定上限真正的长任务能力，取决于长时间保持注意力的能力
  • 先把复杂任务拆成几十上百个可验收的小任务
  • 把 spec、任务状态、验收标准写入外部文件
  • 每完成一个功能就 git commit，留回滚检查点
  • 用长上下文能力维持目标一致性
  • 不要把长时执行能力理解成"模型更会聊天"
  • 不要只看参数和窗口大小，忽略长时可用性
  • 不要省略规划、验收与恢复机制
  • 不要在非隔离环境开 bypass permissions

长时执行 = 可验收的任务 + 外置的进度 + 闭环的评估 + 可控的权限。四样缺一样，模型再强也会中途趴窝。

Q&A

这场 13 小时实测本质上证明了什么？
它证明的不是"GLM 5.2 答得更好"，而是"GLM 5.2 足以支撑 Claude Code 持续完成真实工程任务"。关键证据有三组：① 对象是 40 万+ 行 TypeScript 的真实项目，不是 demo；② 过程是 13 小时无人值守的循环执行，不是聊几轮；③ 产出是 30+ 份 spec 文件和 443 个带验收标准的任务，接近完整的软件工程流程。换句话说，开源模型的价值正在从"陪聊"转向"给 Agent 托底"，而托底的关键是长上下文与指令遵循，不是跑分。
为什么要把进度外置到文件，而不是依赖聊天记录？
聊天记录是不可靠的长期记忆：Claude Code 在上下文超过 95% 时会触发自动压缩，历史细节被总结成摘要，会话也可能因各种意外中断。如果 Agent 只靠聊天记忆知道自己"做到哪了"，压缩之后状态就丢了，循环会重复做已完成的任务或漏掉未完成的。把任务状态写入外部进度文件，每轮先读进度再执行，即使上下文被压缩、会话重启，下一轮依然能从断点精确继续。这是 13 小时长时执行能成立的关键设计。
go 命令循环是怎么工作的？为什么需要独立评估？
go 命令封装了一个闭环：① 读进度文件，拿到当前未完成的任务；② 按 spec 和验收标准执行任务；③ 独立评估验收标准是否满足；④ 未达标就带着反馈进入下一轮，达标就更新进度并 git commit，然后回到 ① 处理下一个任务。之所以需要独立评估，是因为执行任务的 Agent 很容易"自我感觉良好"——它主观认为做完了，但客观上未必。把执行和评估分开，只有通过验收才算完成，这是降低假阳性（谎报完成）的核心机制。
为什么要把启动提示词压成单行？
这是实践中踩出来的坑：go 命令会把启动提示词塞进 hook 的 JSON 数据结构里，而 JSON 字符串对换行敏感——带换行的提示词会直接破坏格式导致报错。所以作者把提示词压成单行。这类问题在任何官方文档里都查不到，它只存在于具体工程实现的接缝处。这也提醒我们：长时执行系统由很多这样的脆弱接缝组成，每一个接缝的鲁棒性都决定整体能不能跑满 13 小时。
长时执行为什么要切到 bypass permissions？有什么风险？
Claude Code 默认在修改文件、执行命令等敏感操作前请求确认。人机交互时这是安全网，但 13 小时无人值守场景下，每隔几分钟弹一次确认就意味着没人点、执行停摆。所以开跑前用 shift+tab 切到 bypass permissions 模式，让 Agent 完全自主执行。风险也很明显：Agent 可以执行任意危险操作。因此前提是工作区隔离可控（容器、虚拟机、一次性目录），并配合 git 检查点随时回滚。存有重要数据的主力机绝不能这么干。
为什么说长上下文能力决定 Agent 的上限？
因为长时执行中，日志、历史对话、工具结果、规划文件会持续累积进上下文。视频的对照实验说得很清楚：旧的 200K 模型在同一任务上中途上下文爆炸报错，而 GLM 5.2 靠更大的窗口和指令遵循改进跑完了全程。这说明名义窗口大小不等于长时可用性——前者是装得下多少，后者是装完之后还能不能找到重点。模型在长历史中丢失焦点，就会做错误的事，此时运行时调度再完美也救不回来。所以长上下文能力是上限，不是起点。
GLM 5.2 的能力边界在哪？哪些事必须留给人？
视频诚实指出了三条边界：① GLM 5.2 仍是纯文本模型，看不懂截图，无法靠截图定位前端 bug；② 页面审美偏弱，生成的 UI 需要人来把关；③ 能力受工具配置约束——演示中 Agent 答不出今天日期，是因为只装了天气 MCP 插件、没装日期插件。所以长时执行自动化的是"可验证"的部分（代码、测试、进度），而"不可验证"的部分（视觉效果、审美判断）要交还给人。人机分工的边界，就是"可验证性"的边界。
