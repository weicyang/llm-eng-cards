HO01 · OpenClaw 架构与实现

开源 Agent-Native 运行时 — 四层架构、三级记忆、Gateway-Pi 执行链路、沙箱隔离、混合搜索、多 Agent 路由、自进化机制

一、OpenClaw 是什么

OpenClaw 是一个开源、可自托管的 Agent-Native 运行时，由社区于 2026 年 2 月发起。它不是 chatbot 封装器，而是一个完整的 Agent OS — 提供从消息接入、模型调用、工具执行到记忆管理的全栈运行环境。

OpenClaw 的本质是"Agent 的操作系统" — 不是某个具体的 AI 模型，而是让任何模型都能变成 Agent 的运行时平台。类比 Android：Gateway = 运营商适配层，记忆系统 = 手机存储，工具生态 = App Store，多平台支持 = 跨设备。

特性说明
Agent-Native为"自主行动"设计的运行时，不是为"对话"设计
Self-Hosted单机部署、完全可控，无需依赖第三方 SaaS
Multi-Platform20+ 消息平台（Slack/Discord/Telegram/WeChat/WhatsApp/CLI 等）
Local-First本地优先，多端联动
自进化Agent 可修改自己的核心文件（AGENTS.md/SOUL.md/MEMORY.md）

三、Gateway：系统的单一控制平面

Gateway 是 OpenClaw 的心脏，充当系统的单一控制平面。所有功能模块围绕它运转。

"单一"这个词是理解 Gateway 的关键：20+ 个平台的消息形态各不相同，但都要先被 Channel Adapter 归一化成同一种内部消息，再进入同一条路由链路。这样一来，鉴权、限流、会话归属、工具策略这些横切逻辑只需要实现一遍，新增一个平台只是多写一个适配器，不需要碰核心。下图是一条消息从平台到工具执行的完整穿越路径：

┌───────────────────────────────────────────────────────────────────────┐ │ Gateway：单进程 Daemon，:18789 WebSocket │ └───────────────────────────────────────────────────────────────────────┘ Slack Discord Telegram WeChat CLI …（20+ 平台） │ │ │ │ │ └────────┴────┬────┴─────────┴───────┘ │ 各平台原生事件 ▼ ┌────────────────────┐ │ Channel Adapters │ 归一化：{platform, channel_id, user_id, │ │ text, attachments, mention?} └─────────┬──────────┘ ▼ ┌────────────────────┐ │ Auth / 提及门控 │ 不该回的消息在这里就被丢弃 └─────────┬──────────┘ ▼ ┌────────────────────┐ sessionKey = │ Session Manager │ agent:<name>:<platform>:<type>:<id> │ │ 同 key 复用会话，超时归档 └─────────┬──────────┘ ▼ ┌────────────────────┐ │ Router（7 层优先级）│ peer → peer.parent → guild+roles │ │ → guild → team → channel → default └─────────┬──────────┘ ▼ ┌────────────────────┐ ┌──────────────────┐ │ Pi Agent │◄──────►│ Memory Layer │ │ （Agentic Loop） │ │ SQLite+FTS5+vec │ └─────────┬──────────┘ └──────────────────┘ ▼ ┌────────────────────┐ ┌──────────────────┐ │ Tool Registry │───────►│ Sandbox（Docker）│ │ allow/deny 策略 │ │ off/non-main/all │ └────────────────────┘ └──────────────────┘ ▲ ┌─────────┴──────────┐ │ Cron Scheduler │ 单定时器，按 nextRunAtMs 唤醒 └────────────────────┘ 也从这里注入 systemEvent

Gateway 的价值不在于它做了多少事，而在于它是唯一入口——所有消息、所有定时触发、所有工具调用都必须经过同一个进程，于是"谁在什么时候被允许做什么"只有一处判定，也只有一处可以观测。

维度实现
运行环境Node ≥ 22，作为 Daemon 常驻后台
通信协议WebSocket（双向持久连接），默认端口 :18789
消息格式JSON-RPC style（method + params + id）
核心服务Session Manager、Router、Auth Module、Channel Adapters、Tool Registry、Memory Layer、Cron Scheduler

Gateway 生命周期

  1. 启动：加载配置 → 初始化 WebSocket 服务 → 注册 Channel Adapters → 启动 Cron
  2. 运行：接收消息 → 路由到 Agent → 执行 ReAct 循环 → 返回结果 → 更新记忆
  3. 健康检查：支持 --deep 深度检查、Channel 探测、网络网关发现

路由策略

Gateway 的路由决定了"哪条消息交给哪个 Agent 处理"：

  • 按 (platform, channel_id, user_id) 组合创建独立 Session
  • Session 内有独立记忆空间
  • Session 超时自动归档（可配置 TTL）
单 Daemon 架构降低部署复杂度（一个进程搞定），适合单机/小团队，避免分布式一致性问题。Gateway 类比 Service Mesh（Envoy/Istio）：做流量路由、认证、可观测性 — 但服务对象是 Agent 而非微服务。

四、Agentic Loop：事件驱动的推理循环

OpenClaw 的推理循环是事件驱动的四层架构：

① 主循环 (run.ts)
→
② 尝试层 (attempt.ts)
→
③ 事件订阅 (subscribe.ts)
→
④ 工具循环 (SDK)
层级职责核心逻辑
主循环错误处理、重试、profile 轮换while(true) 无限循环，每次检查重试次数限制
尝试层单次 LLM 调用的完整生命周期准备阶段→会话初始化→执行推理→返回结果
事件订阅处理流式响应和工具调用message_start/update/end、tool_execution、agent_start/end
工具循环当模型返回 tool_use 时自动执行由底层 SDK 自动管理

主循环的错误处理

错误类型处理方式
Context Overflow自动压缩后重试
Auth FailureProfile 轮换（切换到备用 API Key）
Timeout重试或报错
达到最大迭代强制退出并反馈失败原因

尝试层的四阶段

  1. 准备：创建 workspace 和 session，解析 tools，构建 system prompt
  2. 会话初始化：createAgentSession()，设置 streamFn，安装事件订阅器
  3. 执行推理：await activeSession.prompt()，处理事件流
  4. 返回结果：assistantTexts（生成文本）、toolMetas（工具调用元数据）、usage（token 统计）
OpenClaw 默认 ReAct（思考→行动→观察），可通过 prompt 切换 plan-first（先规划再执行，适合复杂任务）。max_iterations（通常 10-20）防止 Agent 无限循环。

五、Cron 定时系统：单定时器 + Heartbeat

核心设计

  • 单一定时器：只维护一个定时器，基于最近任务的 nextRunAtMs
  • 最大延迟 60 秒：防止时钟漂移
  • 错误指数退避：30s → 1min → 5min → 15min → 60min
  • 自动清理：卡住的任务 2 小时超时自动清理

两种执行模式

模式Session TargetPayload用途
Main Session"main"systemEvent注入系统事件到主会话
Isolated Agent"isolated"agentTurn独立 Agent 会话执行

任务持久化与恢复

  • 存储位置：~/.openclaw/cron/jobs.json
  • 原子写入：临时文件 + rename，防止写入中断导致数据损坏
  • 启动恢复：加载存储 → 清理卡住的任务 → 运行错过的任务 → 重新计算下次运行时间 → 启动定时器
  • 运行日志：~/.openclaw/cron/runs/<jobId>.jsonl，自动裁剪（默认 2MB，保留 2000 行）

与 Heartbeat 集成

定时任务通过 Heartbeat 机制唤醒 Agent：

  • next-heartbeat：等待下次心跳执行
  • now：立即触发心跳

六、工具系统：Skill 与 Tool 的分层架构

Tool 是 Agent 已经"长在身上"的执行器官（exec、read、browser），Skill 则是一份操作说明书（SKILL.md），教会大模型如何组合这些器官来完成特定任务。99% 的"装了技能没用"现象，根因在于 SKILL.md 的写法不够清晰。

Skill vs Tool 的核心边界

维度Tool（工具）Skill（技能）
本质执行器官（函数/命令）说明书（SKILL.md）
可否被调用直接可调用需先被加载阅读
谁发起调用Agent 核心引擎直接调用模型阅读后明白如何调用 Tool
能否独立存在可以依赖 Tool 才能完成动作
示例exec、write、browser"抓取微信公众号文章"技能

快速判断方法：执行 openclaw tools list 看到 Tool，执行 openclaw skills list 看到 Skill。一个 Skill 可引用多个 Tool，反之不能。

渐进式披露：三层加载机制

第一层：索引层 → 第二层：定义层 → 第三层：执行层

传统 Agent 面临的最大问题之一是工具越加越多，效果反而变差。模型面对大量工具描述时，既理解任务又判断该用哪个工具，注意力被稀释。渐进式披露正是为了解决这个问题：

层级加载时机加载内容
索引层系统启动时仅读取极简的能力索引（Skill 名字 + 一行描述），预判"哪些 Skill 可能对当前任务有用"
定义层用户输入匹配到某场景时加载对应 Skill 的完整定义（SKILL.md 全文内容）
执行层真正执行时引入具体上下文、参数和中间结果

效果：Agent 启动更快、对话成本更低、工具选择准确率明显提升——模型不再在一堆工具中"猜"，而在少量强相关的能力中"选"。

示例场景：一个自托管实例装了 40 个 Skill，覆盖运维、爬取、报表三类任务。背景：早期版本把所有 SKILL.md 全文都拼进系统提示。问题：单个 SKILL.md 平均 1,400 token，40 个就是约 5.6 万 token 常驻上下文；每轮对话都要重付这笔输入，而且模型在 40 份说明书里挑执行步骤时容易串台——测下来"选错 Skill 或混用两个 Skill 步骤"的比例约 18%。方案：改成索引层只放"名字 + 一行描述"，命中场景后才加载全文。效果：常驻部分从约 5.6 万 token 降到约 1,200 token（40 行索引），降幅 98%；单轮平均只加载 1.3 份完整 SKILL.md，选错率从 18% 降到 4% 左右，因为候选集从 40 缩到了 2 以内。

SKILL.md 格式规范

Skill 的核心文件是 SKILL.md，包含 YAML frontmatter（元数据）和 Markdown 内容（使用说明）：

---
name: my-custom-skill
description: 技能功能的简洁描述（用于索引层判断是否加载）
version: 1.0.0
metadata:
  openclaw:
    requires:
      bins: ["curl", "jq"]  # 声明此技能依赖的系统命令
---

# 技能标题

## 使用场景
当用户提到【场景描述】时，使用此技能。

## 执行步骤
1. 使用 `read` 工具读取配置文件
2. 使用 `exec` 工具调用 `curl -X GET '...'`
3. 使用 `write` 工具将结果写入报告文件

## 异常处理
- API 返回 401 → 提示用户检查 API Key
- 网络超时 → 重试最多 3 次

## 可用工具参考
本技能使用：`read`、`write`、`exec`

SKILL.md 五要素

要素作用
描述信息清晰简述 Skill 的功能和使用场景（决定索引层是否加载）
触发器定义哪些用户输入或意图会激活此 Skill

ClawHub 技能生态

截至 2026 年 2 月，ClawHub 收录 5705 个社区技能，筛选后 2868 个入选热门列表（过滤垃圾/恶意/重复技能）。官方内置 53 个经过安全校验的核心技能。

2026 年 2 月 ClawHavoc 事件：安全研究团队在 ClawHub 发现 396 个恶意技能，通过伪造前置条件诱导用户下载含木马的技能包。安装任何社区技能前都应审核 SKILL.md 内容和权限范围。

Tool Use 协议

Agent 通过 SKILL.md 理解"怎么做"后，真正的执行依赖底层 Tool 调用，遵循三步标准流程：

  1. 构造请求：Agent 引擎构造 Tool 调用请求（Tool 名称 + JSON 参数）
  2. 安全检查：Gateway 的 Tool 策略层基于 allow/deny 配置和沙箱策略进行过滤
  3. 结果回写：执行结果写入会话转录（role: "tool" 消息），供模型下一轮读取

每条 Tool 调用有唯一的 toolCallId 关联请求和结果，确保多轮并行调用中不会混淆。

七、Sandbox 沙箱系统：三重安全防护

Skills 的执行安全依赖三重防护——沙箱隔离决定 Tool 在哪里运行（Docker 容器或宿主机），Tool 策略决定哪些 Tool 可用，提升执行则作为仅限 exec 的逃生通道。三者独立但协同，构成"三层大坝"。
官方明确声明：这不是完美的安全边界，但当模型做出愚蠢行为时，它能实质性地限制文件系统和进程访问。绝不能把沙箱当作唯一的防线。

第一重：沙箱隔离（在哪里运行）

模式行为适用场景
"off"不隔离，所有工具直接在主机运行仅限开发测试，高风险
"non-main"仅隔离非主会话（默认）群聊访问自动沙箱化
"all"所有会话都在容器中运行多用户生产环境，最安全

隔离范围覆盖：工具执行（exec、read、write、edit）、浏览器进程、CDP 端点。作用域 scope 决定容器数量：

作用域容器数量
"session"每个会话一个容器（默认）
"agent"每个 Agent 一个容器
"shared"所有会话共享一个容器

第二重：工具策略（什么能跑）

即使启用沙箱，没有工具策略限制，模型仍可通过 exec 执行任意危险命令。

{
  "tools": {
    "deny": ["exec", "apply_patch", "browser"],
    "allow": ["read", "write", "edit", "filesystem"]
  }
}

核心规则：

  • deny 永远优先——无论 allow 如何配置，deny 列表中的工具都被硬性阻止
  • 如果 allow 非空，其他所有未明确允许的工具都被视为阻止
  • /exec 命令无法绕过被策略拒绝的 exec 工具——硬性阻断

隔离时工具过滤顺序（从宽到窄）：全局策略 → Agent 策略 → Sandbox 策略（只能进一步限制）→ 子 Agent 策略。

这个顺序有个重要含义：策略是单调收窄的，下游只能删不能加。所以调试"某个工具为什么用不了"时，正确的做法是从最窄的一层往回看，而不是去最外层加 allow——外层加了也没用，任何一层的 deny 都会一票否决。

┌──────────────────────────────────────────────────────────────────────┐ │ 工具可用集合的逐层收窄（每层只能做减法） │ └──────────────────────────────────────────────────────────────────────┘ 全部内置 + MCP 工具 {exec, read, write, edit, apply_patch, browser, canvas, image, mcp:*} │ │ ① 全局策略 deny:[apply_patch] ▼ {exec, read, write, edit, browser, canvas, image, mcp:*} │ │ ② Agent 策略 allow:[exec,read,write,edit,browser] │ （allow 非空 ⇒ 未列出的一律视为拒绝） ▼ {exec, read, write, edit, browser} │ │ ③ Sandbox 策略 deny:[browser]（容器内无 CDP 端点） ▼ {exec, read, write, edit} │ │ ④ 子 Agent 策略 deny:[exec]（委派任务不给执行权） ▼ 子 Agent 实际可用：{read, write, edit} ── 三重防护分别管什么 ────────────────────────────────────────────── 沙箱隔离 → "在哪里跑" off / non-main / all 工具策略 → "什么能跑" deny 优先，一票否决 提升执行 → "能不能出去" 仅 exec，会话级临时开启，超时自动关 注意：/elevated on 作用在最后一层之外，它不改变上面的集合； 若 exec 在任一层被 deny，提升执行同样无效。

第三重：提升执行（受控逃生通道）

仅针对 exec 工具。在沙箱中运行时，某些任务需要访问宿主机真实资源（如读取实时数据），提升执行提供受控突破：

# 在聊天对话中启用提升执行
/elevated on
  • 退出会话或超时后自动关闭
  • 仍可能被审批（approval）策略拦截
  • 不会绕过工具策略的 deny 配置——如果 tools.deny 含 exec，/elevated on 也无效

安全限制

  • 禁止的绑定挂载：系统路径（/etc、/proc、/sys、/dev、/root、/boot）、Docker socket、根文件系统
  • 禁止的网络模式：host（绕过网络隔离）、container:<id>（命名空间加入）
  • 默认安全配置：只读根文件系统、无网络、丢弃所有能力

第四重：Cell Isolation（Pi-embedded 进程级隔离）

当执行层通过 Pi-embedded 在本地设备上运行时，还有一层进程级沙箱——Cell Isolation：

步骤行为目的
1. 环境快照记录执行前的环境状态基线对比
2. 创建 venv独立 Python 虚拟环境依赖隔离，互不干扰
3. 安装依赖动态安装技能所需的包按需加载
4. 执行代码在隔离环境中运行技能权限可控
5. 恢复快照无论成功与否，恢复到初始状态环境纯净

诊断命令

openclaw sandbox explain --session main

实时查看当前会话的三重防护生效情况：沙箱模式/范围/工作区权限、是否被隔离、工具 allow/deny 配置及来源、提升执行阈值。沙箱权限配置混乱时最快的定位入口。

八、记忆管理：三级存储 + 混合搜索

OpenClaw 没有盲目追随纯向量数据库方案，而是创造性地提出三级记忆架构，模拟人类记忆的分层特性——从瞬时的工作记忆，到短期的情景记忆，再到长期的语义记忆。文件即真相，索引辅助检索。

存储层：SQLite + 向量的融合

每个 Agent 对应一个独立的 SQLite 数据库，表结构兼顾全文搜索和向量相似度搜索：

表用途关键设计
files文件元数据path + mtime + hash，用于增量索引（只重索引变化的文件）
chunks文本块存储大文件切分 + 文本块哈希去重 + JSON 序列化向量（如 1536 维）
chunks_fts全文搜索引擎SQLite FTS5 扩展，支持 BM25 排序
chunks_vec向量搜索引擎sqlite-vec 扩展，余弦距离计算

优雅降级机制

sqlite-vec 是 C 语言编写的 SQLite 扩展，并非所有系统都能安装。系统设计了优雅降级：

路径条件性能
快速路径sqlite-vec 可用数据库内直接计算余弦距离，毫秒级
回退路径sqlite-vec 不可用全量加载到内存，JavaScript 暴力计算，秒级

确保任何环境下都能正常工作，只是性能有差异。

混合搜索机制

用户查询
→
关键词提取 (FTS)
+

→ 并行搜索 →
加权融合
→
MMR 去重 + 时间衰减
→
Top-K 结果
搜索类型优势劣势
向量搜索理解语义、容错性强、同义词处理对精确 token 弱（ID、代码符号）
BM25 搜索精确匹配、高信号 token不理解语义
示例场景：用 OpenClaw 管一台家庭服务器，日志里记过一次"给 nas-01 的 smb 服务开了 ipv6，改的是 /etc/samba/smb.conf 第 42 行"。背景：检索一开始只走向量。问题：三个月后问"smb.conf 那次 ipv6 是怎么改的"，向量检索把语义相近的十几条"网络配置"日志都排在前面，真正那条因为篇幅短、向量不突出，排在第 14 位，超出 Top-8 窗口，Agent 回答"没有相关记录"。这类含精确标识（文件路径、行号、主机名）的查询失败率约 30%。方案：加上 BM25 并行检索再加权融合，让 smb.conf 这种高信号 token 走精确匹配通道。效果：该条记录升到第 1 位；同类含标识符查询的失败率从约 30% 降到 6% 左右。同时 MMR 把十几条同质的"网络配置"日志压缩到 2 条，Top-8 里腾出的位置留给了真正不同的内容。

还有两个容易被忽略的细节：增量索引靠 files 表里的 mtime 和 hash 判断，只有变化的文件才重新切块和求向量，所以万级文件的工作区重启后几秒就能就绪；而优雅降级保证了 sqlite-vec 装不上时系统不是报错而是变慢——回退到内存暴力计算，从毫秒级掉到秒级，但功能完整。

MMR 去重与时间衰减

  • MMR（Maximal Marginal Relevance）：在相关性和多样性之间取平衡，λ=0.7
  • 时间衰减：decayedScore = score × e^(-λ × ageInDays)，半衰期 30 天
  • 常青文件：MEMORY.md 和非日期命名文件不参与衰减

九、Session 管理

Session Key 规范

所有 sessionKey 遵循统一格式：

  • agent:main:main — 默认 Agent 的主会话
  • agent:ops:work — ops Agent 的主会话
  • agent:main:telegram:direct:user123 — Telegram DM 会话
  • agent:main:discord:group:guild789 — Discord 群组会话
  • agent:main:cron:daily-backup:run:uuid — Cron 任务运行会话
  • agent:main:subagent:child-session — 子代理会话

会话类型

类型识别模式示例
direct包含 :direct: 或 :dm:telegram:direct:user123
group包含 :group:discord:group:guild789
channel包含 :channel:slack:channel:C123
cronrest 以 cron: 开头cron:backup
subagent包含 :subagent:subagent:child
thread包含 :thread: 或 :topic:discord:group:123:thread:456

会话新鲜度策略

会话类型默认过期时间
direct（DM）24 小时
group（群组）4 小时
thread（线程）24 小时

线程派生机制

  • 当父会话 token 超过阈值（默认 100,000）时跳过派生，避免上下文溢出
  • 派生会话记录 parentSession 链接，支持追溯
  • /new 或 /reset 后保留用户设置的 thinkingLevel、verboseLevel 等
  • 清空 token 统计和压缩计数，确保干净的会话状态

关键设计决策

  1. 大小写不敏感的键匹配：所有 sessionKey 统一转为小写
  2. 会话归档：重置或删除时，对话文件移动到 .archived/ 目录
  3. 投递路由持久化：内部 webchat/系统消息不应覆盖已知的外部投递路由
  4. Cron 会话清理：定期删除过期的 cron 运行会话，归档对话文件

工作区

工作区是 Agent 的文件系统级隔离环境，包含引导文件、记忆、身份和工具配置：

  • 默认路径：~/.openclaw/workspace
  • 每个工作区包含：AGENTS.md、SOUL.md、TOOLS.md、IDENTITY.md、USER.md、MEMORY.md

Channels：多平台连接

十三、Gateway-Pi 执行架构：云端大脑 + 本地肢体

OpenClaw 最硬核的创新是Gateway-Pi 架构：将"思考"（LLM 推理）放在云端或高性能机器，将"执行"（文件操作、系统调用）交给用户本地设备上的轻量级代理。完美平衡算力需求与数据隐私。

步骤组件行为

  • 心跳机制：所有 Pi-embedded 节点定期向 Gateway 发送心跳包
  • 失联处理：节点失联后，Gateway 将后续指令智能路由到其他可用节点
  • 场景覆盖：轻松应对本地设备休眠、网络抖动等不稳定因素

十五、实践建议

  • 用 Gateway 作为单一控制平面，避免分布式一致性问题
  • 用 Sandbox 隔离工具执行，减少"爆炸半径"
  • 把重要信息写入 MEMORY.md（常青文件，不参与时间衰减）

  • 用 Skills 按需扩展 Agent 能力
  • 用多 Agent 路由实现不同频道的专属 Agent
  • 让 Agent 通过自进化机制持续学习

  • 不要把所有记忆都放在对话里（压缩会丢失）
  • 不要忽略 Session 新鲜度策略（会导致上下文溢出）

常见问题

OpenClaw 和 LangGraph/CrewAI 有什么区别？
OpenClaw 是运行时（runtime，管"怎么跑"），LangGraph/CrewAI 是编排框架（orchestration，管"跑什么"）。OpenClaw 提供完整的 session 管理、工具沙箱、记忆层和多平台路由，开箱即用。LangGraph 需要你自己搭建这些基础设施。
为什么 OpenClaw 用单 Daemon 而不是微服务？
单机部署降低运维复杂度，适合个人/小团队。避免分布式一致性问题（CAP 定理的坑）。所有模块在一个进程内通信，延迟低、调试简单。当需要扩展时，可以通过 Nodes 机制跨设备分布式协作。
记忆系统为什么用 Markdown 文件而不是数据库？
"文件即真相"的设计哲学：人类可读可编辑、Git 可追踪、Agent 自组织。SQLite + 向量嵌入只是索引层，真正的数据在 Markdown 文件中。这样即使索引损坏，数据也不会丢失。
混合搜索（向量+BM25）为什么比纯向量搜索好？
向量搜索擅长语义理解（"Mac Studio gateway host" ≈ "运行 gateway 的机器"），但对精确 token 弱（ID、代码符号、错误字符串）。BM25 擅长精确匹配。两者结合后，既能理解语义又能精确匹配，通过加权融合和 MMR 去重得到最优结果。
Sandbox 的三种模式怎么选？
开发调试用 "off"（不隔离，最快）；生产环境用 "non-main"（默认，仅隔离非主会话）；高安全要求用 "all"（所有会话都隔离）。容器作用域通常选 "session"（每个会话一个容器），资源共享场景选 "shared"。
自进化机制会不会让 Agent "学坏"？
自进化通过文件系统持久化，人类可以随时审查和修改 AGENTS.md、SOUL.md、MEMORY.md。安全边界（openBoundaryFile）防止路径遍历攻击，文件大小限制（2MB）防止无限膨胀。关键行为变更可以通过 Git 追踪。
多 Agent 路由的 7 层优先级怎么配置？
从高到低：精确对等匹配 → 父对等匹配 → 公会+角色 → 公会 → 团队 → 频道 → 默认 Agent。配置通过 binding 规则定义，支持按平台、频道、用户、角色等维度精确路由。
