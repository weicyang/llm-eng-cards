Bun Zig→Rust 百万行两周 · 机械裁判与反向验证 · 六步迁移流水线 · 59 亿 token 与 16.5 万美元账本 · 别修代码，修产生代码的循环

让规模迁移成立的，不是"Claude 一次把代码翻译对了"，而是把迁移改造成一条可以反复运行、机械验收、失败后继续收敛的生产线——人负责规则、裁判和异常模式，Agent 负责把队列烧完。

一、两个数字开场：规模与结果

Anthropic 官方博客给出的不是几千行 Demo，而是百万行生产代码的语言级迁移。两个案例先把规模摆出来：

案例迁移内容耗时规模验收结果
BunZig → Rust（Jarred Sumner 主导）不到两周约 100 万行合并前 CI 原有测试全部通过；合并后暴露 19 个回归，已全部修复
Anthropic LabsPython → TypeScript（Mike Krieger 主导）一个周末16.5 万行数百个 Agent、8 道阶段闸门、3 轮对抗审查，逐条 diff 新旧程序命令输出
生产案例 · Bun：Jarred Sumner 用 Claude Code 把 Bun 从 Zig 迁到 Rust，不到两周产出 100 万行代码，合并前 CI 中原有测试全部通过，合并后只暴露了 19 个回归且已全部修掉。整个迁移消耗 59 亿 uncached input tokens 与 6.9 亿 output tokens，按 API 价格约 16.5 万美元——而过去同等规模的人工迁移通常是一个 4 年、300 万到 400 万美元的项目。
生产案例 · Anthropic Labs：Mike Krieger 用一个周末把 Python 代码库迁成 16.5 万行 TypeScript。过程中跑了数百个 Agent、设置 8 道阶段闸门、进行 3 轮对抗审查，最后逐条 diff 新旧程序的命令输出。由于没有现成的跨语言测试，团队做了 7 个真实场景的 parity harness，把 Python 和 TypeScript 输出逐项比较，任何行为差异都算 Bug。Anthropic 过去一个月一共迁了 10 个代码包，每个包都有数万到数十万行。

注意这个结论的分量：这不是"模型翻译得准"，而是迁移被工程化了。真正让规模迁移成立的，是一条可以反复运行、机械验收、失败后继续收敛的流水线。

人不再追着每个文件改。人负责规则、裁判和异常模式，Agent 负责把队列烧完——这是整篇博客最核心的角色重分配。

二、为什么代码迁移特别适合多Agent

大规模迁移刚好满足 Agent 最喜欢的四个条件，这也是它比普通"批量翻译代码"能走得远的原因：

条件具体表现对流水线的意义
工作能并行上千个文件、crate、模块可切成独立批次不需要一个 Agent 从头写到尾
旧代码就是规格需求文档可能缺，但原程序已把行为写出来可同时对照源语言、目标语言和真实输出
有机械裁判编译器、冒烟测试、完整测试套件、输出 diff明确告诉 Agent 对或错，失败自动进下一轮队列
规则可向后传播发现边界问题后写回迁移规则后面的 Agent 全部按新规则执行，错误不重犯

规则向后传播（Backward Propagation of Rules，把某个批次发现的解法写回规则手册，使后续所有批次自动受益）是这条流水线与普通并行翻译的根本区别：并行只负责提速，统一规则和机械验收才负责不失控。一个 Agent 发现 Zig 手动内存管理的某个边界问题，不是只补当前文件，而是把解法写进规则手册，后面 1447 个文件全部按新规则执行。

判断一件事适不适合交给 Agent 队列，就看四问：能不能切块并行？规格在哪里？裁判是谁？教训能不能变成规则？四问都有答案，才谈得上规模化。

三、动手前先造机械裁判

Anthropic 把强裁判列为前置条件：没有它，你连"迁完了"是什么意思都说不清。很多旧测试会直接调用源语言内部函数，换语言后根本跑不了。正确做法是先把测试分类，挑出可以通过外部接口表达的行为，再改造成能同时打在新旧程序上的可移植测试。

机械裁判的验收回路 ────────────────────────────────────────────────────── 旧程序 ──┐ ├──▶ [可移植测试 / parity harness] ──▶ 输出逐项比较 新程序 ──┘ │ ├── 一致 ──▶ 该批次通过 └── 差异 ──▶ 算作 Bug，进修复队列 反向验证（裁判自身的体检）： 原程序 ──▶ 必须通过 故意破坏的程序 ──▶ 必须失败 ────────────────────────────────────────────────────── 抓不住已知错误的测试，不是裁判，只是安慰剂

裁判还必须做一次反向验证（Mutation Testing 的思想：用已知错误的版本检验测试本身是否具备捕获能力）——原程序应该通过，故意破坏的程序必须失败。抓不住已知错误的测试，不是裁判，只是安慰剂。Mike Krieger 的项目没有现成跨语言测试，就做了 7 个真实场景的 parity harness（Parity Harness，一致性测试框架，让新旧两个程序吃同样的输入、逐项比较输出），把 Python 和 TypeScript 输出逐项比较，任何行为差异都算 Bug。

为什么裁判必须前置：迁移的每一步——试迁、批量翻译、编译修复、行为对齐——都要回答同一个问题"这批算不算过"。如果裁判在迁移之后才补，等于先跑完比赛再定规则，所有"通过"都不可信。Bun 案例合并前 CI 全绿、合并后只有 19 个回归，靠的正是裁判先于翻译就位。

先造裁判，再开工。没有裁判的迁移不叫迁移，叫"把一种语言的问题翻译成另一种语言"。

四、六步迁移流水线

六步里最重要的工作都发生在大规模翻译之前。顺序不能反：先定默认规则，再找默认规则盖不住的差距。

第一步：规则手册、依赖图、差距清单

规则手册先规定类型、惯用法和架构怎么映射；依赖图决定哪些文件先迁、哪些必须放在同一批；差距清单专门记录无法直接翻译的隐性知识——比如 Zig 的手动内存管理怎么落到 Rust 所有权，Python 的动态对象怎么变成 TypeScript 接口。

第二步：小样本把规则撞一遍

Bun 迁移的做法是三 Agent 对照实验：一个 Agent 按规则翻 3 个文件，另一个 Agent 像资深 Rust 工程师一样翻同样的文件，第三个 Agent 比较差异并补规则。

小样本撞规则：三 Agent 对照实验 ────────────────────────────────────────────────────── 同样的 3 个源文件 │ │ ▼ ▼ [Agent A] [Agent B] 按规则手册翻译 像资深 Rust 工程师一样翻译 │ │ └────────┬───────────┘ ▼ [Agent C] 比较差异 ──▶ 补充规则手册 │ ▼ 只跑 3 个文件，提前抓到 2 个会扩散到 1448 个文件的关键问题；试迁代码全部丢弃 ──────────────────────────────────────────────────────
生产案例 · 3 个文件的杠杆：Bun 迁移只跑了一轮 3 个文件的小样本实验，就提前抓到两个会扩散到 1448 个文件的关键问题。这里最反直觉的是：试迁出来的代码全部扔掉——这一轮的产物不是代码，是更可靠的规则。结构不保留的重设计也一样：先让对抗 Agent 攻击设计文档，再做一次可丢弃的端到端迁移。

第三步：把翻译任务铺开

批处理脚本从磁盘重建待办队列，"目标文件存在"才算完成，所以任务天然可以暂停、恢复。分工上：高吞吐翻译交给较小模型，写规则和做审查留给更强模型；两个独立审查 Agent 意见不一致时，再交给第三个 Agent 仲裁。如果同一种错误反复出现，别手补十个文件——给规则手册加一句，再重新生成受影响的那一批。

第四到第六步：编译、运行、对齐行为

编译错误由 fixer agents 分批处理；崩溃交给冒烟测试；最后把新旧程序放到同一套测试或真实场景里比行为。昂贵的全量构建由单独的 build daemon（Build Daemon，专门串行执行构建的服务，避免多个 Agent 并发抢占构建资源）串行执行，避免几十个 Agent 同时抢着重编。

步骤关键产物执行者易错点
一、定规则规则手册 / 依赖图 / 差距清单强模型 + 人审顺序反了：先找差距后定默认规则
二、撞规则更可靠的规则（代码丢弃）三 Agent 对照实验舍不得扔试迁代码
三、铺翻译磁盘可重建的任务队列小模型翻译 + 双审查 + 仲裁同类错误逐个手补
四、修编译编译通过的批次fixer agents 分批多 Agent 抢全量构建
五、跑冒烟崩溃清单收敛测试 + 修复队列把偶发崩溃当通过
六、比行为新旧输出一致parity harness / 同场测试只比编译不比行为

这个阶段人的注意力不该放在某一个红叉上，而要看哪些红叉总以同一种方式出现：单点失败交给 loop 消耗，重复模式才值得人修改上游规则。

看红叉的方式决定你是监工还是工程师：盯单个红叉，你在给 Agent 打工；盯红叉的重复模式，Agent 在给你打工。

五、算清账：成本、收益与四要素告诫

AI 把语言迁移从"多年豪赌"变成了"昂贵但可以重跑的工程实验"——注意"昂贵"两个字，它不等于免费。

项目AI 迁移（Bun）传统人力迁移
耗时不到两周约 4 年
成本约 16.5 万美元（按 API 价格）300 万～400 万美元
token 消耗59 亿 uncached input + 6.9 亿 output—
最坏情况删掉分支，改好规则再跑一次维护两套半成品几年，骑虎难下
收益指标迁移前迁移后
Bun 内存占用（2000 次重复构建基准）6745 MB609 MB
Bun 二进制体积（Linux / Windows）基准缩小 19%，部分真实负载快 2%～5%
Python→TS 编译耗时（每平台）约 8 分钟，整个矩阵等 30 分钟约 2 秒，启动快 6 倍
部署链路独立部署流水线一条直接删掉
账本的两面：收益是真实的——Bun 的 2000 次重复构建基准内存从 6745 MB 降到 609 MB，Python→TS 项目编译从 8 分钟降到 2 秒。但边界也是真实的：Bun 迁移后仍有约 4% 的 Rust 代码在 unsafe 块里，说明迁移不会凭空消灭底层边界问题。效果不能只看行数，要看内存、体积、启动速度、维护链路这些迁移的真正动机。
  • 先确认业务收益：性能、内存、维护成本有明确动机
  • 裁判先行：测试可移植化 + 反向验证
  • 把 token 预算当成项目预算的一部分算清楚
  • 保留审查能力：双审查 + 仲裁 + 人工看重复模式
  • 失败预案是"删分支、改规则、重跑"
  • 因为"Claude 能迁"就迁，没有业务动机
  • 跳过裁判直接批量翻译
  • 不设 token 预算，跑到哪算哪
  • 让翻译模型兼任规则和审查
  • 把试迁代码当资产保留，规则错误被固化
四要素告诫：业务收益、测试裁判、Token 预算、审查能力，四样缺一个，都可能把漂亮 Demo 变成昂贵烂尾。

AI 迁移改变的不是"能不能"，而是失败的价格：从"维护两套半成品几年"变成"删掉分支再跑一次"。敢重跑，才敢开工。

六、别修代码，修产生代码的循环

原文最值钱的一句话可以翻成：别修代码，修产生代码的循环。这句话改写的不是"AI 会不会翻译 Rust"，而是大项目的风险结构：以前人怕迁到 90% 后骑虎难下，现在可以先把裁判和规则做扎实，再让机器反复重跑。

旧风险结构新风险结构
迁到 90% 骑虎难下裁判和规则先做扎实，机器反复重跑
失败代价：两套半成品维护几年失败代价：删分支、改规则、再跑一次
人追着每个文件改人盯重复模式，改上游规则
经验留在个人手里经验写进规则手册，向后传播

由此得到三条可迁移的原则，它们适用于任何想让 Agent 队列完成的工程任务：

  • 代码可以重生成——产物廉价，所以质量把关放在生成循环上，而不是逐行人审；
  • 规则必须能解释——规则手册是人能读懂、能 review、能修改的，不是模型黑盒里的倾向；
  • 结果必须由机器验——编译器、测试、输出 diff 说了算，"感觉差不多"不算通过。
方法论的外推：这套"规则手册 + 机械裁判 + 并行队列 + 规则向后传播"的结构，并不绑定编程语言迁移。任何满足四条件的工作——可并行切块、旧实现即规格、有机械裁判、教训能变规则——都可以套用：框架升级、API 换版、批量重构、测试补齐。差别只在裁判的造价。

修一个文件是 O(1)，修一条规则是 O(N)。当你手里有 1448 个文件时，唯一划算的维修对象是产生它们的循环。

Q&A

这套方法论只适用于编程语言迁移吗？
不是。它适用于所有满足四个条件的工作：可并行切块（上千个文件能切成独立批次）、旧实现就是规格（原程序的行为即需求）、有机械裁判（编译器、测试、输出 diff 能判定对错）、教训能变成规则（解法写回规则手册让后续批次受益）。框架升级、API 换版、批量重构、测试补齐都可以套用同一结构：规则手册、依赖图、小样本撞规则、批量队列、机械验收。真正的门槛是裁判的造价，而不是场景本身。
试迁产物为什么全部扔掉？这不是浪费吗？
因为试迁这一轮的产物不是代码，而是更可靠的规则。Bun 迁移用 3 个文件的小样本实验就提前抓到两个会扩散到 1448 个文件的关键问题；如果保留试迁代码，这些在规则不完善阶段产生的偏差会被当成资产固化下来，后面还要花更多力气返工。扔掉代码、留下规则，再让全部文件在正确规则下统一生成，总成本反而最低。这和"别修代码，修产生代码的循环"是同一个逻辑。
为什么要两个独立审查 Agent 加一个仲裁，而不是直接用一个最强的模型？
单模型审查的问题是错误模式单一：它漏掉的问题会系统性地漏掉，且无人质疑。两个独立审查 Agent 意见不一致时，本身就暴露了规则手册的模糊地带，这时交给第三个 Agent 仲裁，裁决的结论还可以反哺规则。这等于把代码审查从"一个人的判断"变成"分歧驱动的收敛机制"，和人类工程里交叉 review 的价值一致——分歧比一致更有信息量。
build daemon 串行化构建，看起来是瓶颈，为什么反而更好？
昂贵的全量构建如果放开并发，几十个 Agent 会同时抢着重编，资源互相踩踏，每个构建都变慢，失败原因还难以归因。build daemon 把构建串行化成公共服务：Agent 提交构建请求、等结果、继续干别的活，构建环境状态一致，失败可复现。表面是瓶颈，实际是把稀缺资源从"抢占模式"改成"排队模式"，总吞吐量反而更高——这和数据库连接池是同一个思想。
为什么高吞吐翻译用较小模型，写规则和审查用更强模型？
因为两类工作的错误代价不同。翻译是规则已经定型后的机械执行，错了会被编译器和测试抓住，可以批量重跑，适合成本更低、速度更快的小模型；而规则和审查决定的是整条流水线的方向，一条错误规则会扩散到上千个文件，必须用更强的模型加人工审查。用模型能力匹配错误代价，是这条流水线的成本控制核心，也解释了 59 亿 token 的消耗为什么仍然比人力便宜一个数量级。
什么是反向验证？为什么裁判本身也需要被验证？
反向验证指用已知错误的版本检验测试的捕获能力：原程序必须通过测试，故意破坏过的程序必须失败。如果一套测试连故意注入的已知错误都抓不住，它在真实迁移中的"全部通过"就毫无意义——抓不住已知错误的测试不是裁判，只是安慰剂。这与变异测试（mutation testing）的思想一致：先证明裁判有判罚能力，再让裁判上岗。很多旧测试直接调用源语言内部函数，换语言后跑不了，需要先改造成能打在新旧两套程序上的可移植测试。
什么条件下不建议启动 AI 大规模迁移？
四要素缺任何一个都建议缓行：没有明确的业务收益（性能、内存、维护成本没有真实动机），迁移只是技术自嗨；造不出机械裁判（行为无法用测试或输出 diff 判定），"迁完了"无法定义；token 预算没有算进项目账，可能跑到一半骑虎难下；团队没有审查能力，规则和 diff 没人看得懂。另外要留意边界：Bun 迁移后仍有约 4% 的 Rust 代码在 unsafe 块里，说明迁移不会凭空消灭底层边界问题。漂亮 Demo 和可交付工程之间的距离，就是这四要素。
