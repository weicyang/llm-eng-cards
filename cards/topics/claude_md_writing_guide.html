CLAUDE.md 不是玄学提示词，而是写给 Claude Code 的"工作说明书"：README 告诉人怎么理解项目，Prompt 告诉模型这次要做什么，CLAUDE.md 告诉 Claude Code 在这个项目里怎么干活。

一、为什么你总在重复教育Claude Code

几乎每个用 Claude Code 写代码的人都遇到过这种循环：第一轮告诉它"这个项目用 pnpm，不要用 npm"，过一会儿它又开始建议 npm install；告诉它"不要直接改数据库表结构"，修着修着它又想动 schema；告诉它"改完要跑单测"，它代码改完就准备收工。

很多人会归因为"模型不听话"，但更大的问题是：你把项目长期规则，当成了临时聊天内容。临时聊天内容会被上下文挤压、压缩，随任务变长而越来越不稳定。你以为 Claude Code"记得"这些规则，其实它只是在当前上下文里还看得到；一旦上下文压缩、裁剪、切换任务，规则就可能丢。

规则载体生命周期稳定性可共享结局
聊天里口头交代单次会话随上下文压缩衰减否每个新任务重说一遍
CLAUDE.md跨任务、跨成员每次进项目自动读取进 Git 全员共享规则沉淀为工程资产
一个典型开场：改一个老项目的接口，你往往要先交代 6 条前置约束——框架是 VuePress 1.x 不要按 2.x 写、命令要在 docs/ 目录下执行、依赖版本别乱升、不要改部署脚本、Markdown 图片必须有 ALT、改完要跑 npm run build。这些话每次开新任务都要说一遍，任务跑久了还会被文件内容和错误日志淹没。CLAUDE.md 的价值就是把这 6 条从"每次口头交代"变成"一次沉淀、永久生效"。

所以 CLAUDE.md 更像新人进组前的项目交接文档：项目怎么启动、哪些目录放什么、哪些地方不能动、常见坑在哪里、提 PR 前要跑什么检查。你不能指望 Claude Code 每次都自己摸索一遍——摸索会浪费 token，也会制造风险。

模型不是不听话，是那些规则只活在"当前上下文"里。想让规则活得比会话长，就得把它写进文件，而不是打进聊天框。

二、CLAUDE.md是什么：与README/Prompt/Memory的区别

CLAUDE.md 是一个普通的 Markdown 文件，Claude Code 会自动读取它，把内容作为项目上下文（模型推理时能"看到"的全部信息的总和）的一部分。三个关键词：它是普通 Markdown——不是 JSON、不是 YAML，不需要复杂语法；它是给 Claude Code 看的——要写能直接影响行动的信息，不写愿景长文；它会进入上下文——规则参与后续推理，也因此占上下文窗口。这最后一点决定了写法原则：短、准、可执行，不是越长越好。

# 项目说明

- 使用 pnpm 管理依赖
- 开发命令：pnpm dev
- 构建命令：pnpm build
- 不要直接修改数据库 schema

四个容易混淆的载体

载体读者典型内容生效范围是否进 Git
README人项目介绍、功能说明、安装与使用文档对外理解项目是
Prompt当前会话的模型"修登录失败，但不要改后端接口"仅当前任务否
CLAUDE.mdClaude Code命令、结构、规范、禁区、验证、坑跨任务稳定项目级应进
用户级 Memory你个人的 Agent"回答用中文""先看计划再改代码"跨项目的个人习惯否

判断标准很简单：只对这次任务生效的要求放 Prompt；跨任务都稳定的项目规则放 CLAUDE.md——比如项目统一用 TypeScript、测试命令是什么、API 层统一走 src/api、UI 组件不直接请求接口、禁止提交真实 token；而你的个人习惯放用户级记忆。Claude Code 的 memory 本身分用户级、项目级、企业级多个层级，CLAUDE.md 就是其中最常用的项目记忆（Project Memory，以文件形式沉淀、可版本化的项目规则集）。

一句话区分：README 告诉人怎么理解项目，Prompt 告诉模型这次要做什么，CLAUDE.md 告诉 Claude Code 在这个项目里怎么干活。

三、四级存放位置：规则放对层

CLAUDE.md 最容易乱的地方不是写什么，而是放在哪。Claude Code 的 memory 不止一个位置，常见有四级，放错层和没写一样有害。

层级路径适合放什么是否进仓库
用户级~/.claude/CLAUDE.md跨项目个人偏好：中文回复、先看计划再改代码否
项目级./CLAUDE.md 或 ./.claude/CLAUDE.md团队共享规则：架构、命令、风格、禁区是
子目录级frontend/CLAUDE.md 等模块专属规则：本模块命令与坑是
import 引用用 @path 引入其他文件个人项目偏好、长文档的关键段落视文件而定
记忆加载机制 ────────────────────────────────────────────────────── ~/.claude/CLAUDE.md 用户级：个人习惯（不进仓库） │ ▼ repo/CLAUDE.md 项目级：团队共享规则（进 Git） │ 从当前工作目录往上查找 ▼ repo/frontend/CLAUDE.md 子目录级：模块规则 │ 读取对应子树文件时才纳入上下文 ▼ @~/.claude/my-prefs.md import：个人偏好旁路 ────────────────────────────────────────────────────── 前端任务不背后端细节，文档任务不背数据库规则

子目录级的加载机制值得注意：官方文档提到，Claude Code 会从当前工作目录往上查找记忆；当前工作目录下更深层的 CLAUDE.md，通常在 Claude 读取对应子树文件时才纳入上下文。这正是大项目的解药——不要让前端任务背着后端所有细节跑，也不要让文档任务背着数据库规则跑。

私人偏好：从 CLAUDE.local.md 到 import

以前常用 CLAUDE.local.md 放个人项目偏好，现在更推荐在项目记忆里用 @path import（在 CLAUDE.md 中用 @路径 语法引入另一个文件的内容）引入个人文件：

# 个人偏好

- @~/.claude/my-project-preferences.md

请参考 @README.md 了解项目概览。
测试规范见 @docs/testing.md。

这样个人规则不用进仓库，也更适合多 worktree 场景。但 import 要克制——能引用关键文档很好，滥用 import 就会把上下文变成垃圾桶。

规则放错层和没写一样有害：个人偏好进了团队仓库就是污染，团队规则留在个人电脑里就是孤岛。

四、该写六类与不该写五类

判断一条信息该不该写进 CLAUDE.md，只有一个标准：它是否会反复影响 Claude Code 的行动？会，就值得写；只对当前任务有效，放 Prompt；只是给人看的背景，放 README。

该写的六类

类别写法要点示例
常用命令写完整命令，注明执行目录所有命令在 docs/ 下执行：cd docs && npm run dev
项目结构写目录职责，不贴完整文件树src/api/：接口封装，组件不要直接调用 fetch
编码规范写具体规则，不写抽象要求API 错误统一通过 handleApiError() 处理
禁止事项明确边界，减少乱动不要提交 .env、token、密钥
验证流程什么改动跑什么检查修改公共组件后，运行组件测试和构建
常见坑人踩过一次、AI 不知道的坑VuePress 1.x 插件名不要写成 2.x 的

不该写的五类

类别反例正确处理
完整接口文档几十个接口的字段与错误码全贴进来只写"API 文档见 docs/api.md"
历史流水账2025-01-03 修了登录问题……写成结论：登录态统一由 authStore 管理
空泛口号写高质量代码、注意性能改成可执行规则：超 100 条数据必须分页
过期规则项目已换 pnpm，文件里还写 npm随项目演进更新，定期清理
太细的临时任务今天先修用户 A 的导出 bug留在当前对话，任务结束即失效
过期规则比没有规则更危险：项目已经从 npm 换成 pnpm，但 CLAUDE.md 里还写着 npm，Claude Code 会很听话地继续错——它会忠实地执行每一条写下来的规则，包括错的。同理，一句"支付模块的金额单位是分，不是元"可能避免很多次事故，而一条过期的"金额用元"会稳定地制造事故。CLAUDE.md 不是写完就不管的配置文件，是要随项目演进的活文档。
  • 写会反复影响行动的规则，一条一行
  • 命令写全：执行目录 + 完整命令
  • 禁止事项单独成节、措辞明确
  • 踩坑之后立刻沉淀成一句话规则
  • 长文档用链接或 import 引用
  • 把接口文档、变更历史整段搬进来
  • 写"保持代码优雅"这类不能执行的口号
  • 把单次任务的要求留在文件里污染后续任务
  • 个人偏好提交进团队仓库
  • 只加不删，任由文件长成十几屏

别写流水账，写结论。历史只有凝固成规则，才对下一次行动有价值。

五、短准硬写法：正反例与可抄模板

写法上记住三个词：短——不写长篇大论；准——每条都和行动有关；硬——尽量写成明确约束，而不是温柔建议。写 CLAUDE.md 不是为了显得你很懂 AI，而是为了让 AI 少猜。

软规则（低效）问题硬规则（可执行）
尽量注意测试"尽量"无法判定是否执行修改业务逻辑后，必须运行相关测试；无法运行时在最终回复说明原因
代码要符合项目风格"风格"没有定义新增 API 请求必须放在 src/api/，页面组件只能调用封装后的 API 方法
保持代码优雅不能指导任何行动列表页超过 100 条数据时使用分页；公共逻辑被两个以上模块复用时抽到 src/hooks/
注意安全范围不明不要提交 .env、token、密钥；不要升级核心依赖版本，除非用户明确要求

可以直接套用的模板结构

好 CLAUDE.md 的结构固定为六类：项目是什么、命令怎么跑、目录怎么分、代码怎么写、什么不能做、改完怎么验。其他内容能不放就不放：

# 项目工作说明

## 项目概述
- 本项目是 XXX 应用，技术栈 XXX；代码在 src/，测试在 tests/。

## 常用命令
- 安装依赖：pnpm install
- 本地开发：pnpm dev
- 单元测试：pnpm test
- 构建检查：pnpm build
## 目录结构
- src/components/：通用组件
- src/pages/：页面入口
- src/api/：接口封装

## 编码规范
- 新增 API 请求必须放在 src/api/。
- 页面组件不要直接调用 fetch。
## 禁止事项
- 不要提交 .env、token、密钥。
- 不要修改数据库 schema，除非用户明确要求。
- 不要删除用户已有改动。

## 验证要求
- 修改业务逻辑后，运行相关测试。
- 如果测试无法运行，在最终回复里说明原因。

模板的价值是结构而不是文字，你真正要做的是把每一条改成自己项目里的真实规则——假的规范，比没有规范更坑。

好规则的标准是能被违反、也能被检查：一条写不出"违反了会怎样"的规则，大概率是口号。

六、大项目拆分、上下文算账与团队维护

小项目一个根 CLAUDE.md 就够了，大项目尤其是 monorepo 一定要拆。一个有 Web 前端、Node 后端、移动端、文档站、基础组件库的仓库，如果所有规则都写进根文件，最后一定变成十几屏——Claude Code 每次做一个小任务，都要背着一堆无关规则跑。

monorepo 拆分结构 ────────────────────────────────────────────────────── repo/ ├── CLAUDE.md 全局规则（几屏以内） │ ├── 包管理器 / Git 流程 │ ├── 安全要求 / 全局禁止事项 │ └── 通用验证方式 ├── apps/web/CLAUDE.md 模块规则 ├── apps/admin/CLAUDE.md 本模块目录职责 ├── packages/ui/CLAUDE.md 本模块启动/测试命令 └── docs/CLAUDE.md 本模块常见坑 ────────────────────────────────────────────────────── 处理具体模块时，拿到的是更相关的上下文
文件职责内容
根 CLAUDE.md全局约束包管理器、Git 流程、安全要求、全局禁止事项、通用验证
模块 CLAUDE.md模块细节目录职责、启动命令、测试命令、本模块常见坑

上下文窗口：CLAUDE.md 不是免费空间

上下文窗口（Context Window，模型单次推理能处理的全部 token 容量）就像一张工作台：项目规则放上去，模型就能看到；但放太多，工具输出、文件内容、用户要求就会被挤。官方资料提到 Claude Code 会对 CLAUDE.md 使用 prompt caching（提示缓存，复用已处理过的前缀以降低重复读取的计费与延迟），但要特别注意：缓存降低的是计费压力，不代表不占上下文空间，也不代表信息越多越好。一份 300 行的 CLAUDE.md，即使全部命中缓存，模型每次也要在大量规则里找重点，结果是重要规则被淹没、无关规则干扰当前任务。

上下文窗口这张"工作台" ────────────────────────────────────────────────────── ┌───────────────────────────────────────────────┐ │ 上下文窗口（固定容量） │ │ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ │ │CLAUDE.md│ │文件内容 │ │命令输出 │ ┌──────┐ │ │ │项目规则 │ │被读代码 │ │测试日志 │ │用户 │ │ │ │ │ │ │ │ │ │要求 │ │ │ └─────────┘ └─────────┘ └─────────┘ └──────┘ │ └───────────────────────────────────────────────┘ 规则放太多 ──▶ 文件内容、工具输出、用户要求被挤出 缓存只降计费压力，不释放工作台面积 ──────────────────────────────────────────────────────
一个典型的上下文污染案例：某团队的 monorepo 根 CLAUDE.md 一路长到 300 行，其中约 250 行是各模块的专属细节——改一个前端按钮，也要背着数据库迁移规范和文档站图片规则。拆分后根文件压到约 50 行全局规则，5 个模块文件各自维护细节，每个小任务携带的无关规则从 250 行降到接近 0。上下文管理的目标不是让模型看见更多，而是让它看见更有价值的信息。

团队维护流程

如果团队已经大量使用 AI 编程，应该把 CLAUDE.md 当成工程资产维护，不要让它变成某个人电脑里的私货：

动作做法原因
进仓库团队共享规则全部进 Git全员拿到同一套规则
分层放个人偏好放用户级 memory不污染团队项目文件
过审查规则变更像代码一样 review写错了就是把错误流程自动化
沉淀坑连续犯错的坑写成一句话规则一次沉淀，长期避坑
定期删清理过期命令、失效目录、重复规则越短越准，越有用

CLAUDE.md 是活的工程资产，不是一次性配置文件：它要进 Git、过 review、随项目演进，越短越准越有用。

Q&A

已经有 README 了，还需要 CLAUDE.md 吗？
需要，两者读者不同。README 写给人看：项目介绍、功能说明、安装方式、贡献指南；CLAUDE.md 写给 Agent 看：任务从哪个目录入手、改代码前先看哪些文件、用哪个命令验证、哪些文件不能碰、遇到某类错误先检查哪里。这些信息对人友好的表述对 Agent 并不高效，Agent 需要的是能直接执行的行动约束。两者可以并存，必要时用 @README.md 的 import 引用，而不是复制粘贴。
CLAUDE.md 写得很长，会让 Claude Code 变强还是变弱？
大概率变弱。CLAUDE.md 会进入上下文窗口，过长的规则清单会带来两个问题：重要规则被淹没，模型每次要在大量规则里找重点；无关规则干扰当前任务，比如前端任务背着数据库规则跑。经验上根文件控制在几屏以内，每条规则一行说明，长文档用链接或 import 引用，低频规则下沉到对应子目录。目标是让模型看见更有价值的信息，而不是更多信息。
个人偏好能不能直接写进项目的 CLAUDE.md？
不建议。项目级 CLAUDE.md 应该进 Git、团队共享，写的是团队规则；像"回答用中文""先看计划再改代码"这类个人习惯会污染团队文件。正确做法分两层：跨项目的个人偏好放用户级 ~/.claude/CLAUDE.md；针对某个项目的个人偏好用 @path import 引入个人文件，既不进仓库，也更适合多 worktree 场景。早期的 CLAUDE.local.md 方案现在也推荐迁移到 import。
prompt caching 既然能缓存 CLAUDE.md，是不是写多长都无所谓？
不是。缓存降低的是重复读取带来的计费压力和延迟，但 CLAUDE.md 的内容依然占据上下文窗口、参与每一轮推理。一份 300 行的文件即使全部命中缓存，模型也要在大量规则里找重点，结果是重要规则被淹没、无关规则干扰任务。缓存解决的是钱的问题，不是注意力的问题——上下文空间是工作台，规则太多就会挤掉文件内容、工具输出和用户要求。
子目录的 CLAUDE.md 什么时候会被加载？
Claude Code 会从当前工作目录往上查找记忆，保证全局规则始终在场；而当前工作目录下更深层的 CLAUDE.md，通常在 Claude 读取对应子树文件时才纳入上下文。这意味着 frontend/CLAUDE.md 的规则主要在前端任务里生效，文档任务不会被它拖累。大仓库应该利用这个机制：根文件写全局规则，子目录文件写模块规则，让每个任务只背相关的上下文。
CLAUDE.md 和 Memory 是什么关系？
CLAUDE.md 本身就是 Claude Code 记忆体系的一种载体。Memory 有多个层级：用户级存个人跨项目习惯，项目级存团队共享规则（即进 Git 的 CLAUDE.md），企业级存组织统一约束。CLAUDE.md 属于项目级记忆，定位是"写给 Claude Code 的项目交接文档"。判断信息放哪里的标准：个人习惯放用户级，团队规则放项目级，只对单次任务有效的要求直接写 Prompt。
团队里怎么维护 CLAUDE.md 才不会烂掉？
五个动作：一，团队共享规则全部进 Git，别留在个人电脑里；二，个人偏好放用户级 memory，不污染仓库；三，规则变更像代码一样审查，尤其禁止事项和测试命令——写错了就是把错误流程自动化；四，踩坑之后及时沉淀，比如"支付模块金额单位是分不是元"一句话能避免很多次错误；五，定期删：清理过期命令、不存在的目录、重复规则和临时任务残留。过期规则比没有规则更危险，CLAUDE.md 必须随项目演进。
