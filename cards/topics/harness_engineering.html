HH03 · Harness Engineering 概念、实战与争议

Prompt Engineering → Context Engineering → Harness Engineering 演进 → 驾驭系统 vs 提示模型 → 争议分析

Harness Engineering 不是又一种"写提示词的技巧"，而是给大模型套上的一整套缰绳与鞍具——把提示词、上下文、工具、评估和反馈循环组装成一个可复现、可度量、可迭代的工程系统，让 Agent 在生产环境里跑得稳，而不是偶尔跑得快。

一、三代"工程"的演进

大模型应用开发的关注点，在短短几年里经历了三次跃迁：先是怎么把话说好，再是怎么把信息喂好，最后是怎么让整个系统跑好。这三代"工程"对应着 AI 应用从玩具走向生产的三个阶段。

概念大致时间核心思想解决的问题
Prompt Engineering（提示词工程）2022~2023调整提示词让模型更听话模型无引导乱说话、格式不稳定
Context Engineering（上下文工程）2024~2025精心管理进入模型的所有信息上下文窗口有限，塞太多反而效果差
Harness Engineering（驾驭工程）2026 起设计整个驾驭系统（模型+工具+流程+评估）让 AI Agent 真正可靠落地生产

三代工程不是新词替换旧词，而是关注范围逐层放大：PE 管"一句话"，CE 管"所有输入"，HE 管"整个系统的运行与迭代"。外圈天然包含内圈。

从"调提示词"到"管上下文"再到"驾驭整个系统"——三者不是替代关系，而是层层递进：Harness Engineering 包含前两者，是更高层次的系统工程。

"Harness Engineering"这个词在 2026 年 2 月集中爆发：HashiCorp 联合创始人 Mitch Hashimoto 发表博文《Harness engineering: leveraging Codex in an agent-first world》，几乎同期 OpenAI 以同名文章分享了 Codex 团队的实践。它出现的背景是：当 Agent 开始连续自主工作几十分钟甚至几小时，单靠提示词和上下文管理已经兜不住底——你需要一整套"缰绳"。

二、Harness 的本义与系统组成

Harness（驾驭）一词来源于马具——控制马的缰绳和鞍具。在大模型语境中：你不需要训练一匹新马（模型），而是给它配上一套好的马具（驾驭系统），让马（模型）按预期方向奔跑。换句话说，Harness 是"模型权重之外的一切工程设施"。

模型是发动机，Harness 是方向盘、刹车、仪表盘和导航。发动机再强，没有方向盘也只会原地打转——这就是为什么同一个模型在不同系统里表现天差地别。

2.2 边界：什么不属于 Harness

理解 Harness 的关键是划清边界：模型预训练、SFT、RLHF 这些"改马本身"的工作不属于 Harness；而模型之外所有"让马跑对方向"的工程设施都属于 Harness。这也解释了为什么 Harness Engineering 不需要你懂模型内部结构——它是应用层的系统工程，面向的是任何团队都能掌控的那部分。

一个实用的自检方法：如果某个组件在"换一个更强的模型"之后仍然有价值，它大概率属于 Harness；如果模型一升级它就没用了（比如某些弥补模型短处的提示词补丁），它只是临时拐杖。

三、核心机制：约束、护栏与评估闭环

Harness 之所以能让 Agent 可靠，靠的不是某一项黑科技，而是一套"约束—执行—校验—反馈"的闭环机制。模型每一步的输出都被系统接管：推理前有门禁，执行时有Guardrails（护栏，在模型行动路径上设置的硬性约束，越界即拦截），推理后有校验，失败后还有回流。

可靠的 Agent 不是"模型从不犯错"，而是"错误永远出不了笼子"——护栏负责拦截，评估负责发现，反馈负责让同类错误不再犯第二次。

3.2 为什么"评估"是 Harness 的分水岭

提示词工程时代，改一句 prompt 好不好往往靠"感觉变好了"；Harness 时代，任何改动都要先过 Eval 集——一组固定的输入与预期输出，每次变更后自动重跑并对比分数。没有评估，反馈循环就无从谈起，系统就退回了碰运气模式。这也是 Harness Engineering 与前辈们最本质的区别：它把 AI 开发从"手艺活"变成了"可度量的工程"。

护栏不是越多越好。每加一道校验都会增加延迟和误拦概率：把只读查询也拦下来等人工确认，Agent 就失去了存在意义。正确做法是按"破坏力"分级——不可逆操作（删除、支付、发布）重护栏，可逆操作轻护栏或事后审计。

四、生产实战：两份来自一线的数据

概念再好听也要看落地。2026 年前后，OpenAI 和 Anthropic 分别公开了各自的 Harness 实践数据，这是目前最有分量的两份一线证据。

判断一个新概念是不是炒作，就看一线团队愿不愿意拿生产数字背书——OpenAI 和 Anthropic 都给了，而且数字指向同一个结论：系统级工程的收益远大于单点提示词优化。

案例一：OpenAI Codex 团队的"Agent-first 代码库"。背景：Codex 团队决定让 Agent 成为主要代码贡献者，人类转为审查者。问题：Agent 单次产出不可控，直接放手必然失控。方案：构建完整 Harness——用 AGENTS.md 沉淀项目约定作为"入职手册"，把 linter、类型检查和 CI 测试改造成 Agent 的自动审查官，配合 Eval 集持续度量每次变更。效果：5 个月内产出近 100 万行代码，几乎全部由 Agent 生成并通过自动化校验，人类工程师从"写代码"转为"设计系统与审查结果"。
案例二：Anthropic 多智能体研究系统。背景：复杂研究问题（如"对比三家竞品的技术路线"）单 Agent 串行处理又慢又容易丢信息。问题：拆成多个子 Agent 并行后，token 消耗和协调成本飙升，且子 Agent 容易各自跑偏。方案：设计 orchestrator-worker 式 Harness——主 Agent 负责拆解任务与汇总，子 Agent 并行检索，所有结论必须附带可核查的引用，主 Agent 对引用做交叉验证。效果：token 消耗约为单 Agent 的 15 倍，但在可并行的研究任务上速度和质量显著更优，因此团队只在高价值任务上启用这套重 Harness，并给每次运行设置预算上限。

  • 用 linter/测试/类型检查等确定性工具做"审查官"
  • 给不可逆操作加人工确认，给可逆操作留审计日志
  • 把失败案例系统性回流，变成新的测试用例
  • 不要在没有评估的情况下"凭感觉"调 prompt 上线
  • 不要给所有操作都加最重的护栏（延迟和误拦会杀死体验）
  • 不要对低价值任务使用 15 倍成本的多智能体 Harness
  • 不要把 Harness 当成一次性工程——它需要随模型升级持续迭代

五、争议：噱头还是突破？

Harness Engineering 走红之后，社区迅速分成两派。把双方论点摆在一起看，会发现争论的焦点其实不是"这些东西有没有用"，而是"给旧组件起个新名字算不算创新"。

争论双方其实没有根本分歧：反对派说的是"没有新零件"，支持派说的是"终于有了图纸"。零件确实都是现成的，但把零件组装成可靠系统的方法论，本身就是工程价值。

立场核心论点依据
支持方这是系统级工程，不是简单调 prompt将 AI 开发从"碰运气"升级为可复现的工程实践；评估与反馈循环是此前缺失的关键环节
支持方一线数据证明有效OpenAI 5 个月近 100 万行代码、Anthropic 公开多智能体 Harness 架构
反对方换汤不换药拆开看本质还是 Prompt + Context + 工具调用 + 测试，没有新的核心技术
反对方过度包装的炒作周期AI 圈"三天一重磅、五天一炸裂"，新名词的半衰期越来越短
客观评价：Harness Engineering 的价值不在于发明了什么新技术，而在于提供了一个系统化的思维框架。它提醒开发者：不要只关注 prompt 写得好不好，而要关注整个系统是否可靠、可评估、可迭代。类比软件工程史——"DevOps"出现时也没有发明任何新工具，但它把构建、测试、部署、监控串成一套方法论，其价值已被整个行业验证。

对务实的开发者来说，更实际的态度是：不必纠结名词新旧，而是对照 Harness 的五个组件（提示词、工具、编排、评估、反馈）给自己的系统做一次体检——哪一环缺失，哪一环就是当前的瓶颈。多数团队的短板不在提示词，而在评估和反馈这两环。

六、落地路线图：从 0 搭一个最小 Harness

Harness 不需要一步到位。按下面的层级逐级搭建，每一级都有明确的验收标准，避免"为了 Harness 而 Harness"的过度设计。

最小可用 Harness = 一个带重试的执行循环 + 一套能跑分的测试集。先让系统"错了能发现、发现了能改"，再谈编排和多智能体。

层级做什么验收标准
L0 裸调用直接调用模型 API流程能跑通
L1 提示词工程System Prompt + Few-shot + 输出格式约束输出格式稳定率 > 95%
L2 上下文工程接入 RAG / Memory，长历史自动压缩长对话不降智、引用可溯源
L3 工具与编排MCP/函数调用 + 工作流状态机 + 沙箱护栏多步任务可自动完成且不出笼
L4 评估与反馈固定 Eval 集 + 失败案例回流 + 监控告警每次变更可量化对比，回归可追溯

6.1 最小 Harness 循环的代码骨架

def harness_loop(task, max_turns=10):
    context = build_context(task)          # 上下文工程：装配输入
    for _ in range(max_turns):
        action = llm(context, tools)       # 模型只做决策
        if action.is_final:
            return validate(action.output) # 输出校验：结构/引用断言
        result = sandbox.run(action)       # 护栏内执行：越界即拦截
        context = update(context, result)  # 反馈回写：结果进入上下文

注意这个骨架里的关键设计：模型只负责"决定做什么"，真正的执行由 sandbox.run 完成，执行结果再回写上下文——决策与执行分离，正是 Harness 可控性的来源。

  • 从 L1/L2 开始逐级搭建，每级有验收标准再升级
  • 把项目约定写进固定文件（AGENTS.md/CLAUDE.md），而不是每次手敲
  • 先给最危险的 1~2 个操作加护栏，再逐步扩展
  • 不要跳过 L1~L3 直接做多智能体编排
  • 不要把护栏规则硬编码进 prompt（模型会忘，用代码强制执行）
  • 不要等"完美 Harness"上线——先跑起来，用失败案例驱动迭代

Q&A

Harness Engineering 与 Prompt/Context Engineering 有什么区别？
三者是层层递进的关系：①Prompt Engineering 关注"怎么把一句话说清楚"（调整提示词）；②Context Engineering 关注"怎么管理所有输入信息"（上下文窗口有限，需要策略性选择/压缩）；③Harness Engineering 关注"怎么让整个 AI 系统可靠落地"（模型+工具+流程+评估+反馈循环）。Harness 包含前两者，是更高层次的系统工程。核心差异在于：PE 和 CE 主要调整"给模型什么"，HE 设计"整个系统怎么运行、怎么评估、怎么迭代"。
Harness Engineering 为什么有争议？它的真正价值是什么？
争议原因在于：反对方认为它没有新的核心技术，只是将 Prompt Engineering、Context Engineering、工具调用、评估框架整合在一起，换了个名字炒作；支持方则认为它提供了系统化思维框架。它的真正价值有三点：①将 AI 开发从"碰运气"升级为可复现的工程实践；②强调评估和反馈循环（这是 PE/CE 长期缺少的环节）；③提醒开发者关注整体系统可靠性而非仅关注 prompt 质量。OpenAI 用此方法 5 个月产出近 100 万行代码的案例，证明了系统级工程的实际价值。
"Harness 是模型之外的一切"怎么理解？
Harness 指的是模型权重之外的所有工程设施：提示词模板、上下文管理、工具集成、流程编排、护栏、评估和反馈循环。划清这条边界有两个实用意义：第一，它明确了职责——模型负责生成与决策，系统负责约束与校验，出了问题先查系统而不是怪模型；第二，它让 Harness 成为任何团队都能做的事，不需要懂预训练或微调。一个自检标准是：如果某个组件在换用更强模型后依然有价值，它就属于 Harness；如果只是弥补当前模型短处的临时补丁，那只是拐杖。
评估框架为什么是 Harness 区别于传统提示词工程的关键？
提示词工程时代，一次修改好不好往往靠主观感觉；而 Harness 要求任何改动先过固定 Eval 集——一组确定的输入与预期输出，变更后自动重跑并对比分数。没有评估就没有反馈循环：你不知道哪次修改引入了回归，失败案例也无法系统性地转化为改进信号，整个系统就退回了碰运气模式。可以说评估框架是 Harness 的"仪表盘"，它把 AI 开发从手艺活变成了可度量的工程。多数团队的真实短板也恰恰在这里：提示词写得很勤，测试集一个没有。
护栏（Guardrails）在 Harness 中扮演什么角色？应该怎么设置？
护栏是设置在模型行动路径上的硬性约束，越界即被系统拦截，典型形式包括权限白名单、危险操作人工确认、沙箱执行和输出结构校验。它的核心价值是把"模型可能犯错"变成"错误出不了笼子"。但护栏不是越多越好：每道校验都增加延迟和误拦概率，把只读操作也拦下来等审批，Agent 就失去了意义。正确做法是按破坏力分级——删除、支付、发布这类不可逆操作用重护栏，可逆操作轻护栏或仅做事后审计。
小团队没有精力做完整 Harness，应该先做哪一环？
建议按"L1 提示词 → L2 上下文 → L3 工具护栏 → L4 评估"的顺序逐级搭建，但如果只能选一个增量，优先做评估。理由很简单：没有评估，你连"系统现在到底有多不可靠"都不知道，后续所有优化都是盲调。最小起步方案是：收集 20~50 个真实任务作为固定测试集，写清楚每个任务的验收标准，每次改动后跑一遍对比通过率。这个投入一两天就能完成，却能立刻让迭代从"凭感觉"变成"看分数"，是性价比最高的一环。
Harness Engineering 会让模型本身变得不重要吗？
不会，两者是乘法关系而非替代关系。模型能力是基数，Harness 是放大器：强模型配烂 Harness 照样频繁翻车，弱模型配好 Harness 也能在特定场景稳定产出，但 Harness 无法凭空创造模型不具备的推理能力。更现实的规律是：模型每升级一代，一部分"弥补短处"的 Harness 组件会过时（比如纠正格式的补丁），但评估、护栏、反馈这些"系统工程"组件的价值会一直保留。所以正确的姿势是：投资那些不随模型升级而贬值的 Harness 组件，把临时补丁标记为可丢弃。
