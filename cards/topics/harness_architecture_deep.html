HH02 · Agent Harness 工程方法

Harness Engineering — Agent = Model + Harness，从概念到企业级落地的完整拆解

核心公式：Agent = Model + Harness。Model 提供基础智能能力，Harness 将智能转化为实际工作能力。效能关键在系统整体配合，而非单一模型能力。

二、Harness 工程方法的核心思想

1. 上下文重置机制

解决 AI 长任务执行中的逻辑断裂问题。将任务打包成结构化数据文件，采用接力赛模式传递任务状态。

2. 对抗性架构

角色职责
生成器负责执行
评估器负责质量把控

评估器四项硬标准：设计质量、原创性、工艺、功能性。严厉惩罚 AI 批量生产的设计模式。

3. 三智能体协作模式

┌─────────────────────────────────────────────────────────┐ │ 三智能体协作流程 │ ├─────────────────────────────────────────────────────────┤ │ │ │ 规划师 → 制定产品规格 │ │ ↓ │ │ 生成器 → 编写代码 │ │ ↓ │ │ 评估器 → 自动化测试 + 找 Bug │ │ 特别强调：评估器要实际操作应用 │ │ │ └─────────────────────────────────────────────────────────┘

4. 动态调整策略

  • 随着模型能力增强，简化不必要的流程
  • 将工程精力转向更具挑战性的场景
  • 从"老师"角色转变为"侦察兵"角色

五、企业级 Harness 三层架构

企业级 Harness Coding 不是让 AI 裸奔写代码。真正的 Harness 至少需要三层：人类需求层、工程契约层、代码执行层。

第一层：人类需求层

解决"人类到底想要什么"的问题。很多 AI Coding 失败不是模型写不出代码，而是需求从一开始就没被说清楚。

要素必须明确的内容
为什么做业务动机和目标
做什么范围边界，不做什么
输入输出接口契约和数据格式
验收标准可度量的完成条件
核心原则：人类负责想清楚方向，AI 负责把方向翻译成工程动作。如果人类自己都没想清楚，AI 只会把不确定性放大。

第二层：工程契约层

人类需求是业务语言，代码实现需要工程语言。这一层把需求翻译成可执行的"工程合同"。

  • 设计方案：改哪个模块、新增什么接口
  • 错误码定义：异常场景怎么处理
  • 测试覆盖：哪些场景必须覆盖
  • 架构约束：哪些规则不能破坏

AI 可以起草契约，但人类必须 Review——方向对不对、边界有没有漏、验收标准是否可验证。

第三层：代码执行层

只有前两层对齐后，AI 才能进入代码实现。但即使到了这里，也要拆分角色：

角色职责为什么分离
规划 Agent任务拆分、依赖分析聚焦全局视野
实现 Agent编写代码和测试聚焦局部执行
评估 Agent外部视角审查不让模型既当运动员又当裁判

六、10 步 Harness 流水线

企业级 Harness 的实际运行流程，从需求到验收的完整闭环：

关键设计：双 Agent 验收（测试 Agent + 架构 Agent）确保代码既满足功能需求，又不破坏架构规范。经验沉淀：打回次数过多时，AI 偏航记录自动沉淀到文档，避免同类错误再次发生。

七、AbstractFilesystem：可插拔文件系统

个人 Agent 用本地目录就够了，但企业级场景需要分布式存储。AbstractFilesystem 让同一套 Agent 逻辑在不同物理存储间无缝切换。

设计思想

对上层：Agent 调用统一的 read/write/ls/grep 接口，不关心"文件"实际落在哪。

对下层：可适配本机磁盘、远端对象存储（OSS）、KV 数据库（Redis）、沙箱文件系统，甚至通过 CompositeFilesystem 把不同路径路由到不同后端。

三种部署模式

模式物理存储适用场景
Local本机磁盘个人代理（如 OpenClaw）
Remote远端 OSS/KV企业级多副本部署
Sandbox隔离沙箱文件系统不信任输入下的安全执行
为什么重要：AgentScope Java 用这一层抽象解决了"个人助手型 Agent 和企业级 Agent 是两种工程形态"的核心矛盾——同一份 Agent 逻辑，无需修改即可适配个人开发环境与企业分布式部署。

八、企业级场景分层

不是所有 Agent 都需要完整的 Harness。根据场景复杂度选择合适的 Harness 深度：

场景典型应用核心 Harness 能力关键约束
个人代理OpenClaw、Coding Agent持续记忆、本地 Shell 执行、工作区配置单用户、本机运行

企业在线服务交易 Agent、审批 Agent默认安全边界（不暴露 Shell）、多实例共享记忆、会话跨请求连续稳定安全、API 驱动

九、双层记忆沉淀机制

Harness 的记忆不是简单的"存对话历史"，而是分两层沉淀：

工作记忆（流水账）

每轮对话结束后，自动提炼本次对话的新事实，写入工作区记忆文件。这层记忆是原始记录，保留完整细节。

长期记忆（精炼）

后台周期性地将流水账合并成精炼的长期记忆。过时的、低价值的信息被丢弃，高价值的经验被保留。

层级写入时机内容容量
工作记忆每轮对话结束新事实、新发现、新偏好无硬上限
长期记忆后台周期合并提炼后的核心经验字符上限（控制 token 成本）
设计要点：工作记忆保证"不丢事实"，长期记忆保证"不爆上下文"。全文检索工具允许 Agent 从工作记忆中回捞旧事实，兼顾完整性和效率。

十、核心要点总结

Harness 工程方法核心：
  • 公式：Agent = Model + Harness，Harness 是将智能转化为工作能力的工程系统
  • 四层架构：文件系统（基础）→ Bash 执行（代码）→ 沙箱验证（安全）→ 记忆搜索（知识）
  • 三大机制：上下文重置（接力赛模式）、对抗性架构（生成器+评估器）、三智能体协作（规划/生成/评估）
  • 成本洞察：完整 Harness 6h/$200 vs 单一 Agent 20min/$9，成本差 20 倍但质量天壤之别

十一、执行可靠性：六维稳定性机制

Harness 的另一半价值在运行时：它是 AI Agent 的可靠执行引擎，专注解决长链路 IO 系统中的稳定性问题——为 Agent 提供有状态、可恢复、可追踪、可编排的执行环境，而不是简单的重试机制。长链路任务的每一步都可能遭遇模型超时、网络抖动、工具崩溃、进程中断，任何一环失控都会让整条任务链前功尽弃。执行可靠性由六个维度的机制协同兜底：

┌────────────────────────────────────────────────────────────┐ │ 长链路执行可靠性：六维机制 │ ├────────────────────────────────────────────────────────────┤ │ │ │ ① 分层超时 模型 30s / 搜索 10s / DB 3s │ │ │ Running → Timeout → Retry，进程不崩 │ │ ▼ │ │ ② 执行抖动 网络波动自动重试 / 参数错误立即终止 │ │ │ 软失败：单工具失败不拖垮整体 │ │ ▼ │ │ ③ 工具故障 隔离上下文 + 结构化 Result + 小模型兜底 │ │ ▼ │ │ ④ 中断恢复 Redis 快照 + 事件记录，断点续传 │ │ ▼ │ │ ⑤ 一致性 显式状态机 + 唯一调用编号幂等 │ │ ▼ │ │ ⑥ 上下文 动态组装 + 记忆三层 │ │ │ └────────────────────────────────────────────────────────────┘
六维机制不是六个孤立功能，而是一张兜底网：超时控制"卡住"，抖动恢复控制"重试"，故障隔离控制"止损"，中断恢复保证"续跑"，状态机与幂等保证"不乱"，上下文管理保证"不迷"。缺任何一维，长链路任务都可能在生产环境里翻车。

1. 分层超时：给每类调用定不同的"耐心"

长链路任务里不同调用的天然耗时差异极大，用一个统一超时值必然顾此失彼：设太短会误杀正常的大模型调用，设太长会让卡死的数据库查询拖住整个流程。分层超时按调用类型设置独立阈值：

调用类型超时阈值设计考量
大模型调用30 秒生成式推理天然慢，给足耐心避免误杀
Web 搜索10 秒外部服务，超时即换策略
数据库查询3 秒内部调用，超过 3 秒基本意味着查询本身有问题

超时后的关键设计是状态转换而非进程崩溃：任务在状态机内从 Running 进入 Timeout，再由调度器决定是否 Retry——进程始终活着，上下文不丢，避免了"一超时就整条任务重来"的浪费。

Running ──超过阈值──▶ Timeout ──调度器决策──▶ Retry ──▶ Running ▲ │ └────────────────── 重试成功 ────────────────┘ （全程状态机内流转，进程不崩溃，任务上下文保留）

2. 执行抖动：自适应恢复与软失败

执行过程中的失败不是一类问题，必须先按错误性质分类再决定动作——这就是自适应恢复：

  • 网络波动等瞬时错误：自动重试。这类错误下一次很可能就成功，重试是廉价且有效的。
  • 参数错误等确定性错误：立即终止该分支。重试一百次结果也一样，只会白白消耗时间和 token，正确动作是把错误信息抛回给规划层重新决策。

配套的软失败设计让单工具失败不影响整体任务流：搜索工具挂了，任务可以降级为基于已有上下文继续推进，而不是整条链路直接中止。硬失败（整体中止）只留给真正不可恢复的场景。

错误类型典型例子处理策略
瞬时错误网络抖动、限流自动重试
确定性错误参数错误、权限不足立即终止该分支，上报规划层
单工具故障某工具不可用软失败，任务流降级继续

3. 工具故障：隔离执行与结构化返回

工具故障是长链路中最常见的失败源，Harness 用三道防线应对：

  • 隔离执行上下文：每个工具运行在独立环境里，一个工具的崩溃或污染不会波及主流程和其他工具。
  • 统一结构化 Result：所有工具的返回被规范成结构化的 Result 对象，替代自由文本。上层流程可以程序化地判断成功/失败、提取错误原因，而不是靠模型去"读"一段不知道格式的返回。
  • 快速失败 + 小模型兜底：工具失败时快速走降级路径——先查缓存记忆拿历史结果，或交给小模型兜底产出近似结果，不让主任务卡死等待。
"统一返回结构"看似是小事，实际是可靠性的地基：自由文本返回让上层无法做分支决策，只能把判断权交给模型，等于把不确定性重新引入系统；结构化 Result 让"失败"成为可编程处理的状态，而非需要猜的文本。

4. 中断恢复：快照 + 事件记录，断点续传

进程被杀、机器重启、用户主动中断——长链路任务不能一中断就从头再来。恢复机制有两层：

  • Redis 快照：实时保存三类关键状态——当前步骤状态、任务规划、已取得的工具结果。进程重启后从快照恢复，已花的时间和 token 不作废。
  • 事件记录：关键动作序列化存储，构成可回放的执行轨迹。恢复时重放事件流，从最后一个成功的调用点之后继续，实现断点续传。
执行中 ──实时写入──▶ Redis 快照（步骤状态 / 任务规划 / 工具结果） │ ├──关键动作──▶ 事件记录（序列化存储） │ 中断 / 崩溃 │ ▼ 恢复：读快照 + 重放事件 ──▶ 从断点继续执行

5. 多步一致性：显式状态机 + 幂等

多步任务的两个隐患是流程乱跳和重复执行，分别由两个机制约束：

  • 显式状态机：规划 → 调用 → 更新 → 推理 → 执行，每一步都是明确的状态，流转路径写死在状态机里。任何时刻都能回答"现在处于哪个阶段、下一步该去哪"，非法跳转直接被拒绝。
  • 幂等性设计：每次调用分配唯一调用编号。中断恢复后重发的请求，引擎识别出该编号已执行过，直接返回已有结果而不是重复执行——避免"恢复一次、副作用翻倍"（比如重复下单、重复写库）。
显式状态机解决"流程会不会乱"，幂等解决"动作会不会重"。前者让执行可追踪，后者让重试敢放心用——没有幂等，任何自动重试都是潜在的事故源。

6. 上下文动态组装与记忆三层

长链路任务的上下文管理不能"一次塞满"，而要按需供给：按当前步骤动态组装所需的上下文片段，避免无关内容挤占宝贵的上下文预算。记忆则按用途分三层：

记忆层内容特点
短期记忆原始对话窗口保持对话连贯，随会话滑动
长期记忆稳定事实和用户偏好跨任务复用，沉淀不流失
运行时记忆任务临时状态服务当前任务，任务结束即清理
动态组装 + 记忆三层，本质是让上下文"够用但不超载"：短期保连贯、长期保经验、运行时报任务，各司其职。它与前文的六维机制合在一起，才构成 Harness 作为分布式 Runtime 的完整可靠性底座。

六维机制合在一起值多少

示例场景：一条"抓取 40 个网页 → 抽字段 → 写库 → 生成周报"的长链路任务，跑满一次约 26 分钟、涉及 180 次工具调用。背景：最初的实现只有一层全局 120 秒超时，失败后无差别整条重跑，最多三次。问题：数据库写入偶发 5 秒抖动会被判定为整体失败，重跑时已写入的记录被再写一遍，一周内出现 7 次重复数据；全局超时一触发，前 20 分钟的抓取结果全部作废，单次失败的沉没成本约 12 万 token。方案：换成分层超时（模型 30s / 搜索 10s / DB 3s）+ 状态机内 Running → Timeout → Retry 的状态转换 + 每次调用带唯一编号做幂等去重 + Redis 按步落断点快照。效果：重跑范围从"全部 180 次调用"缩到"失败的那一次"，端到端成功率从 71% 升到 96%，重复写入归零，单次任务的平均 token 消耗下降 38%。

生产案例

生产验证：Harness AI 的循环探测中间件在编码 Agent 中的效果：(1) 未部署前，12% 的任务陷入 Doom Loop（平均消耗 45,000 tokens 后仍无进展）；(2) 部署后（阈值 N=10），死循环检出率 96%，平均在第 11 次修改时触发反思指令，其中 68% 的 Agent 在反思后成功切换策略；(3) Token 浪费从月均 $3,200 降至 $180（降幅 94%）。Build to Delete 验证：在 GPT-5 测试中，死循环率从 12% 降至 3%，中间件触发频率降低 75%。关键设计哲学：工程护栏是临时支架，模型进步后应逐步退场。

Q&A

为什么 Agent 需要 Harness 而不是直接用模型？

Model 只提供基础智能能力，Harness 将智能转化为实际工作能力。没有 Harness 的 Agent 就像没有赛道的赛车——引擎再强也跑不出成绩。Harness 提供文件系统、执行环境、安全隔离、记忆管理四大能力，确保任务的连贯性、安全性和可验证性。

对抗性架构为什么需要评估器实际操作应用？

评估器如果只看代码不实际操作，就无法发现真正的 Bug。比如 UI 渲染问题、交互逻辑错误、边界条件异常，只有实际操作应用才能发现。四项硬标准（设计质量、原创性、工艺、功能性）都需要实际体验来验证，不能只靠静态代码审查。

上下文重置机制怎么解决长任务的逻辑断裂？

长任务执行中，AI 的上下文窗口会逐渐被历史信息填满，导致逻辑断裂。上下文重置机制将任务打包成结构化数据文件，采用接力赛模式传递任务状态——每个阶段结束时，将关键状态写入文件，下一阶段从文件中恢复状态重新开始，保证任务连贯性。

Harness 的动态调整策略是什么意思？

随着模型能力增强（如从 GPT-3.5 到 GPT-4 到 Claude），之前必要的流程可能变得多余。动态调整意味着：① 简化模型已经能做好的部分，② 将工程精力转向更具挑战性的场景，③ 角色从"老师"（教模型怎么做）转变为"侦察兵"（发现模型做不好的地方并补强）。

长链路任务中断后恢复，怎么避免已完成的步骤被重复执行？

靠快照和幂等两层机制配合。Redis 快照实时保存步骤状态、任务规划和工具结果，恢复时直接读回，已花的时间和 token 不作废；同时每个关键动作被序列化为事件记录，恢复时从最后一个成功调用点之后续传。在此基础上，每次调用都带唯一调用编号，恢复后重发的请求被引擎识别为已执行过，直接返回已有结果而不重复执行，从而避免重复下单、重复写库这类副作用翻倍的问题。

Q5：Harness 架构的可观测性怎么做？需要监控哪些指标？

Harness 可观测性三层指标：(1) 模型层 — 每步推理延迟、Token 消耗、输出质量评分（LLM-as-Judge）；(2) Harness 层 — 循环探测触发率、工具调用成功率、上下文压缩比、护栏拦截次数；(3) 业务层 — 任务完成率、用户满意度、端到端延迟。关键告警规则：循环探测触发率 >20%（说明模型可能退化）、工具调用失败率 >5%（可能是 API 问题）、上下文压缩比 >3:1（可能丢失关键信息）。生产实践：Grafana 仪表盘 + Prometheus 指标采集 + PagerDuty 告警，故障平均发现时间 2 分钟。
