HC08 · Claude Code 动态工作流：运行时生成 Harness

Dynamic Workflows — 单上下文三大失败模式 / agent·parallel·pipeline 三原语 / 六种编排模式 / 触发·监控·恢复·沉淀 / 适用边界

一句话本质：动态工作流不是"更聪明的提示词"，而是 Claude 针对当前任务现场写一个可执行的 JavaScript harness 并真的跑起来——把一个上下文扛不动的大任务，拆给一队互相隔离、上下文干净的子 Agent，由确定性代码（而不是模型的自觉）决定什么时候算干完。

一、默认 harness 只为写代码调优

harness（直译"挽具/外壳"）指模型之外的那层编排系统：控制 Claude 读什么、什么时候动手、产出怎么验证、什么时候算完成。Claude Code 自带的 harness 打磨得很成熟，但它有个前提——它是冲着"写代码"这件事调出来的。很多任务确实长得像写代码，所以默认 harness 也能凑合用；但深度调研、安全审计、多 Agent 分工、代码评审这类任务，"最佳跑法"和写代码并不一样。

过去要把这些任务做到极致，只有一条路：开发者在 Claude Code 之上手搓一套定制 harness——每个场景一次 bespoke 工程投入。动态工作流（Dynamic Workflows）把这件事翻转了：这套针对任务的 harness 不用你手搓，Claude 分析完任务后自己现写一套。

默认模式：一套 harness 想套住所有任务 ┌────────────────────────────────────────────┐ │ 默认 Claude Code harness（为写代码定制） │ │ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │ 写代码 │ │ 调研 │ │ 审计 │ │ 评审 │ │ │ └──────┘ └──────┘ └──────┘ └──────┘ │ │ ✅ 量身 ⚠️ 将就 ⚠️ 将就 ⚠️ 将就 │ └────────────────────────────────────────────┘ ↓ 动态工作流 ↓ ┌────────────────────────────────────────────┐ │ Claude 先分析任务，再为每类任务现写外壳： │ │ 调研任务 → harness-A（深挖 + 引用核验） │ │ 审计任务 → harness-B（扇出 + 对抗验证） │ │ 评审任务 → harness-C（分模块 + 汇总评分） │ └────────────────────────────────────────────┘
任务类型与"写代码"的差异理想 harness 形态
深度调研要多路并行搜集、交叉核验，而非串行改文件扇出多路探查 + 汇总时核对出处
安全审计要求全覆盖、不能"差不多就行"，还要独立复核按文件分片并行 + 对抗验证
多 Agent 分工需要明确的角色划分与交接协议按角色生成子 Agent + 栅栏汇合
代码评审评审者不能给自己打分生成与验证彻底分家

默认 harness 是"成衣"，动态工作流是"量体裁衣"——而且裁缝就是 Claude 自己。你只负责说清楚什么算成功、信任边界在哪，剩下那套外壳它自己搭。

二、单上下文的三大失败模式

为什么非得折腾？因为默认 harness 让 Claude 在同一个上下文窗口里既做规划又做执行。短任务没问题，但任务一长、一分散、一对抗，三个失败模式会准时冒出来。动态工作流的解法不是"叮嘱模型别偷懒"，而是结构性地让偷懒、自夸、跑偏无处发生。

失败模式典型表现根因工作流的结构性解法
agentic laziness（偷懒）审 50 个文件，审到第 35 个就宣布"干完了"上下文塞满后，模型把"差不多"当成"做完"分片隔离：没有任何一个 Agent 握着整个任务，每片有独立验收标准
self-preferential bias（自夸）让 Claude 验自己的活，它偏向维护自己之前的结论如同学生给自己打分，天然护短对抗验证：验活的和干活的是两个互不通气的 Agent
goal drift（跑偏）对话拉长、反复压缩摘要后，边界约束被一点点丢掉每次摘要压缩都是有损的，"不要做 X"这类约束最先丢失短窗口 + 目标重申：每个子 Agent 的干净上下文里都重新写明目标
关键洞察：三个毛病都不是"模型坏了"，而是"单上下文"这种结构的必然产物。所以解法也必须是结构的：隔离让偷懒无处藏（每个子任务有明确的完成定义），独立验证 Agent 让自夸消失（反驳失败才算数），每个窗口都短让跑偏被摁住（目标在每个新窗口里被重申）。更重要的是——什么时候算"干完"由确定性的脚本判断，不再由模型自己宣布。

这就像管理一个团队：不是反复叮嘱一个人"你要认真、要客观、要不忘初心"，而是把工作拆给互相隔离的专人，再安排一个独立的质检员。制度比自觉可靠。

三、工作流是真代码，不是提示词

很多人一听"工作流"就以为是"一段精心调过的提示词"。不是。动态工作流是 Claude 现场生成、然后真的拿去执行的 JavaScript 文件。这个文件在后台的运行时里跑，与你的对话分离——普通会话里 Claude 必须在同一个上下文里既持计划又干活；而在工作流里，计划搬进了代码：循环、分支、中间结果全活在脚本变量里，你的对话上下文最后只接收最终答案。

脚本里只有三块基本积木（外加 JSON、Math、Array 等标准 JS 辅助数据处理）：

原语语义类比关键能力
agent(prompt, opts)开一个子 Agent：给它干净独立的上下文窗口和聚焦目标派一名专员去办一件事可用 JSON Schema 约束输出结构；可指定用哪个档位的模型；编码任务可给独立 git worktree
parallel(...)一道栅栏（barrier）：几个任务全部跑完才放行等所有专员回来才开汇总会并行提速，汇合点做结构化合并
pipeline(items, ...)让一批东西流水线式过几道工序工厂流水线：A 项先走，B 项慢也不挡道各项独立推进，总耗时约等于最慢单链而非所有步骤之和
// Claude 为"50 个文件安全审计"现写的工作流（示意）
const reports = parallel(files.map(f =>
  agent(`审计 ${f} 的安全风险，按 schema 输出`,
        { model: "sonnet", schema: FindingSchema })));
const verdicts = parallel(reports.map(r =>
  agent(`尝试反驳这些发现：${JSON.stringify(r)}`,
        { model: "opus" })));
return synthesize(reports, verdicts);
动态工作流的运行结构 ┌──────────────────────────────────────────────────────┐ │ 你的对话上下文（保持干净，只拿最终答案） │ └──────────────┬──────────────────────▲────────────────┘ │ 触发 │ 最终结果 ▼ │ ┌──────────────────────────────────────────────────────┐ │ 工作流运行时（后台执行 Claude 现写的 JS） │ │ · 循环 / 分支 / 中间结果全在脚本变量里 │ │ · 脚本本身【没有】文件系统/shell 权限，只负责编排 │ │ │ │ agent() ──► 子Agent A（干净上下文·弱模型·worktree-1）│ │ agent() ──► 子Agent B（干净上下文·强模型·worktree-2）│ │ parallel() ─► 栅栏：全部完成再放行 │ │ pipeline() ─► 各项独立过工序 │ └──────┬───────────────┬───────────────┬───────────────┘ ▼ ▼ ▼ 读文件/写文件 跑命令 验证产出 （真正动手的是子 Agent，不是编排脚本）
"是模板不是死脚本"：保存下来的工作流再次运行时，会根据当下的具体任务自适应调整（开几个子 Agent、哪步用强模型哪步用便宜模型、要不要 worktree 隔离，都由 Claude 临场决定），而不是一行不差地重放。这正是它与用 Agent SDK 或 claude -p 预先写死的静态工作流的本质区别。
维度静态工作流（Agent SDK / claude -p）动态工作流
编写者开发者预先手写Claude 针对当前任务现写
覆盖面必须兼顾所有边界情况，趋于通用只为这一个任务定制
类比通用框架为这份工作专门写的脚本
失败模式任务形状不合时只能削足适履形状随任务而变
维护成本模型升级后编排代码可能变死重每次现写，天然跟随模型能力

判断一次编排"值不值"的朴素标准：计划如果只存在于模型的脑子里，它会随上下文一起衰减；计划一旦变成代码，就获得了代码的确定性。动态工作流做的事，就是把"计划"从易碎的上下文搬进坚固的代码。

四、六种可复用的编排模式

实战里反复出现的编排被归纳成六类。这六种模式是动态工作流最长效的资产——即使你不用这个功能，"把大任务拆给一队隔离的 Claude 再汇总"的思路也值得内化：

模式怎么跑适合场景
分类即处理（classify-and-act）先分流，再把每一类路由给专门的 Agent工单 triage、产出归档、后台分诊
扇出+汇总（fan-out-and-synthesize）拆成多份并行各跑一个 Agent，栅栏处统一汇总安全审计、跨模块独立评审、深度调研
对抗验证（adversarial verification）一个 Agent 提出，另一个专挑刺，两边不共享上下文根因排查、结论复核、事实核查
生成+筛选（generate-and-filter）先广撒网生成一堆候选，再按标准筛掉弱的取名、方案探索、测试用例生成
锦标赛（tournament）多个 Agent/模型同题竞赛，裁判两两比较选优模型路由、方案择优（两两比较优于直接打分）
跑到收工（loop-until-done）反复"动手—检查—修复"，直到满足明确停止条件开放式排查、偶现 bug 复现、清扫式发现
对抗验证模式：一个结论只有在"反驳失败"之后才算数 ┌──────────────┐ ┌──────────────┐ │ 提出者 Agent │ 结论草稿 │ 反驳者 Agent │ │ 上下文 A │ ───────────► │ 上下文 B │ │（不许看 B） │ │（不许看 A） │ └──────────────┘ └──────┬───────┘ ▲ │ 反驳意见 │ 反驳成立 → 打回重做 │ └─────────────────────────────┘ 反驳失败 ▼ ✅ 结论成立，进入汇总 要点：干活的与验活的彻底分家、互不通气

六种模式与三大失败模式存在清晰的对应关系，这也是选型时的第一抓手：

你担心的问题首选模式原因
覆盖不全（偷懒）扇出+汇总分片并行，每片独立验收，总数可核对
结论不可信（自夸）对抗验证 / 锦标赛判断者不是生产者
方向跑偏（漂移）跑到收工停止条件是脚本里的硬判断，不靠模型宣布
候选质量参差生成+筛选宽度与严格度分开两个阶段控制
生产案例（据第三方报道）：Bun 运行时的 Zig→Rust 移植。这是动态工作流类"Agent 集群 + 对抗验证"打法被反复引用的标志性工程：整个移植产出约 75 万行 Rust 代码，测试通过率 99.8%，从启动到合并仅用 11 天。这类"几十万行级、逐模块可独立验证、需要反复回归核对"的迁移，正是单上下文绝无可能扛下、而扇出+验证编排如鱼得水的任务形状。

六种模式不是六个 API，而是六种"组织形状"。选模式就是回答一个问题：这份工作的信任结构应该长什么样——谁干活、谁验收、验收不通过怎么办。

五、触发、监控、恢复与沉淀

动态工作流的完整生命周期有四个环节，理解它们才能把功能用顺：

环节操作方式价值
触发直接说"给这个任务做一套工作流"，或在提示中带上 ultracode 关键词 / 把 effort 调到 ultracode 档，让 Claude 自己判断何时该上工作流显式触发可控，自动触发省心
监控/workflows 打开运行面板：每个阶段、每个子 Agent、每次工具调用和 token 消耗都可见，还能暂停、跳过卡住的、重试单个 Agent队伍再大也有全景观测点
恢复每次运行有 ID，被用户操作或退出终端打断后，恢复会话即可接着跑：跑过的阶段走缓存，只补没干完的长任务不怕中断
沉淀面板里按 s 存到 ~/.claude/workflows；把 JS 文件丢进 Skill 文件夹即可分享给队友一次漂亮的根因排查 → 一套"根因排查工作流"模板
沉淀的复利效应：一次漂亮的迁移可以沉淀成"迁移工作流"，一次漂亮的排查可以沉淀成"根因排查工作流"。团队层面，工作流文件就是可版本化、可评审、可分发的编排资产——这是它比"一次性调好的提示词"高一个维度的地方。

注意"恢复走缓存"这个细节：阶段级缓存意味着中断的代价趋近于零，这直接改变了你对"多大的任务敢一次跑"的心理阈值——敢跑更大的活，因为失败不再等于从头再来。

七、适用边界：别滥用，很烧 token

动态工作流要协调一整队 Agent，token 消耗远高于普通单 Agent 会话。一个诚实的判断标准只有一句话：这个任务，是不是真的需要比"一个上下文窗口"更多的算力？

✅ 值得上工作流❌ 别上工作流
50 个文件的安全审计（要求全覆盖）两行的 bug 修复
上千行的排序打分（如简历/工单批量评估）改一个文件的局部重构
高不确定、需反复探索的深度调研问一个有明确答案的问题
高风险、必须独立验证的改动一次性的临时脚本
高复用、值得沉淀成模板的流程你自己都说不清成功标准的活
典型成本对比（示意场景）：修复一个两行 bug，单 Agent 会话可能几百个 token、几毛钱内搞定；若误上工作流，光"生成 harness + 派生子 Agent + 验证"就是数十倍的 token 开销，收益为零。反过来，50 文件审计若硬用单上下文，常见结局是审到第 35 个文件就宣布完成——覆盖率 70% 的审计在安全上等于没审，因为攻击者只需要找到那 30% 的漏网之鱼。此时工作流多花的 token 买的是"全覆盖 + 独立复核"，是风险对价而不是浪费。

它与其他编排方式的分工也可以一句话讲清：角色固定的长期协作用 Agent Teams，角色需要临场拆解的用动态工作流；而在"要不要上编排"之前，先问"到底需不需要 Agent"——这与 Agent vs Workflow 的判断一脉相承。

  • 先写清"什么算成功、什么算完成"，再触发工作流
  • 高风险任务显式要求对抗验证："别让干活的验自己的活"
  • 把漂亮的一次运行按 s 沉淀成模板，分享给团队
  • 用 /workflows 面板盯 token 曲线，及时暂停跑偏的运行
  • 读取不可信外部内容的 Agent 与执行高权限动作的 Agent 严格分开（隔离模式）
  • 别用工作流干单文件、两行改动级别的活
  • 别把保存的工作流当死脚本期待逐行重放——它是自适应模板
  • 别在成功标准模糊时启动：脚本无法判断"收工"条件会烧钱空转
  • 别忽略 research preview 状态就上生产关键路径
  • 别把预览期的并发数、版本号等细节写进长期文档

这条演进线值得记住：不写 Prompt 写 Loop → 平台托管 harness → 模型自己现写 harness。编排正在从"人来设计架构"挪到"模型临场决定"，人退到定义成功标准与信任边界的位置。

Q&A

动态工作流和"写一段更好的提示词"本质区别在哪？

提示词只是给模型的输入，执行计划仍然活在上下文窗口里，会随对话变长而衰减、被摘要压缩丢失；动态工作流是 Claude 现场生成并真实执行的 JavaScript 文件，循环、分支、中间结果都在脚本变量里，"是否完成"由确定性代码判断而非模型自我宣布。前者影响的是模型"怎么想"，后者改变的是任务"怎么被组织和验收"，属于两个层面的东西。

为什么"审 50 个文件审到 35 个就说干完了"不能靠叮嘱模型解决？

因为这不是态度问题而是结构问题：单一上下文塞满后，模型的注意力与自我监控能力会随之下降，把"差不多"当成"做完"是长上下文的系统性倾向，再强的"请一定要认真"提示也只能边际缓解。工作流的解法是结构性的——把 50 个文件拆成独立分片交给多个上下文干净的子 Agent，每片有自己的完成定义，最后由脚本核对数量。偷懒需要的"糊弄空间"被隔离机制直接拆掉了。

agent()、parallel()、pipeline() 该怎么选？

三者是互补原语而非互斥选项：agent() 负责"开一个干净的专人去干一件事"，是所有编排的原子单位；parallel() 是栅栏，用于"必须等所有分支都完成才能汇总"的场景，如扇出审计后的统一合并；pipeline() 是流水线，用于"一批条目各自独立通过多道工序"的场景，各项进度互不阻塞，总耗时趋近最慢单链。典型组合是：parallel 包一批 agent 做扇出，pipeline 串多道工序做增量处理，最后再用 agent 做汇总或验证。

对抗验证模式为什么要求两个 Agent 互不共享上下文？

共享上下文会引入"礼貌性一致"与先入为主：反驳者一旦看到提出者的完整推理链，容易被叙述说服，退化成复述而不是独立检验。彻底分家后，反驳者只拿到结论本身，必须从证据出发独立重建判断，挑刺才是真挑刺。这与"让学生互评时先收走答卷署名"是同一个道理——程序隔离保证判断独立，结论只有在反驳失败后才算数。

保存下来的工作流再次运行时，是逐行重放吗？

不是。保存的工作流是"模板"而不是"死脚本"：再次运行时 Claude 会根据当下任务的具体参数重新决定开几个子 Agent、哪步用什么档位的模型、要不要 worktree 隔离等。你沉淀的是编排形状与验收标准，不是执行细节。这也意味着分享工作流给队友时，对方拿到的是会自适应的资产，而不是一个环境稍变就崩的脆弱脚本。

什么信号出现时说明"该上工作流了"？

五个信号：①任务量超出单窗口承载力（几十个文件、上千条记录）；②要求全覆盖而非抽样（安全审计、逐项核验）；③结论高风险、需要独立复核才敢采信；④路径高度不确定，需要反复探索试错；⑤这个流程以后还要反复跑，值得沉淀成模板。反之，两行 bug、单文件改动、成功标准说不清的任务，上工作流纯属烧钱。核心判据始终是：任务是否真的需要比一个上下文窗口更多的算力。

动态工作流和静态工作流（Agent SDK / claude -p）如何取舍？

静态工作流由开发者预先手写，必须覆盖所有边界情况，因此趋于通用，适合流程高度固定、需要严格可预测性的场景；动态工作流为当前任务定制，形状随任务而变，适合任务形状多变或一次一样式的复杂工作。还要考虑维护成本：模型升级后，为上一代模型弱点打的补丁可能变成死重，静态编排代码要人肉跟进，而动态工作流每次现写、天然跟随模型能力。实践中两者并存：把反复出现、已验证的形状沉淀成模板，模板内部仍允许临场自适应。
