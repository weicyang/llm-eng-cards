一、DeerFlow 是什么

DeerFlow 全称 Deep Exploration and Efficient Research Flow，由字节跳动开源，是一个 Super Agent Harness，为 AI 智能体提供运行时基础设施。2026 年 2 月 28 日发布当天登顶 GitHub Trending 第一名。

DeerFlow 不是框架，是平台——框架提供积木让你自己搭，Harness 提供开箱即用的运行时环境。

Harness vs Framework 核心区别

维度Framework（框架）Harness（运行时平台）
设计理念提供积木，自己搭Batteries included，开箱即用
执行环境你自己搞定自带沙箱、文件系统、进程隔离
决策权开发者写流程Agent 自主规划、拆解、执行
扩展方式插件/中间件Skills + MCP Server + 子智能体
Opinionated 程度低（灵活但需要胶水代码）高（约定优于配置，但可替换）

三、核心引擎：LangGraph + Lead Agent + 中间件

3.1 LangGraph 图驱动编排

DeerFlow 不是手写 while 循环，而是构建在 LangGraph 之上。核心抽象是 StateGraph：

  • 节点（Node）：图中的计算单元，接收当前状态、执行操作、返回状态更新
  • 边（Edge）：节点之间的连接，定义执行顺序
  • 条件边（Conditional Edge）：根据当前状态动态决定下一个节点
  • 状态（State）：TypedDict，在整个图执行过程中传递和更新
LangGraph 图就像工厂流水线：每个节点是一道工序，条件边是质检岗（合格往前走、不合格回点重做），状态是产品卡片记录当前状态。

DeerFlow 使用 create_react_agent() 工厂函数自动构建 ReAct 图，不需要手动定义图结构，只需提供模型、工具、中间件和状态模式。

3.2 ThreadState：7 个自定义字段

DeerFlow 扩展了 LangGraph 默认的 AgentState，新增了 7 个字段：

3.3 Lead Agent：大脑的核心循环

Lead Agent 是系统的指挥中心，通过 make_lead_agent() 工厂函数创建：

  1. 模型选择：三层优先级回退（请求参数 > 自定义 Agent 配置 > 全局默认模型）
  2. Thinking 模式：让模型在回答前进行深度推理，不支持时静默降级
  3. 工具集动态组装：根据配置动态加载内置工具、MCP 工具、社区工具
  4. 系统提示词模板化：角色 + 记忆 + 思考方式 + 技能 + 关键提醒

3.4 11 层中间件系统

中间件是 Agent 的"神经系统"，处理所有横切关注点：

四、Sub-Agent 系统

4.1 单层委派模型

Lead Agent 是编排者，Sub-Agent 是执行者。关键设计：

  • 不可嵌套：Sub-Agent 无法再创建 Sub-Agent，task 工具在子 Agent 工具列表中被显式排除
  • 两种类型：general-purpose（通用型，50 轮）和 bash（命令执行型，30 轮）
  • 并发限制：最多 3 个 Sub-Agent 并行执行，在线程池和 Middleware 两层同时生效

4.3 上下文隔离与 trace_id

Sub-Agent 的上下文与 Lead Agent 完全隔离，这是刻意设计：

  • 防止 Sub-Agent 误操作主对话状态
  • 多 Sub-Agent 并行时不互相干扰
  • 通过 trace_id 建立精确追踪链路，从 Lead Agent 通过每个 Sub-Agent

五、Skills 体系：能力的核心扩展单元

Skills 是 DeerFlow 最重要的扩展机制。其核心特点：

  • 技能是 Markdown，不是代码：非开发者也能编写和贡献技能
  • 渐进式加载：只加载当前任务需要的技能，不会一次性加载全部
  • 资源存储：技能可以带有模板、配置、引用资源等附属文件

两级加载：第一级只加载技能名称和描述（索引），第二级在匹配到任务后加载完整内容与资源。这保证了上下文窗口不被未使用的技能消耗。

这里的关键词是索引常驻与正文按需：常驻的那部分决定了 Agent "知道自己会什么"，按需的那部分才是真正花钱的内容。技能库可以长到几百个，只要索引条目足够短，常驻开销就是线性可控的。

示例场景：一个内置 63 个技能的部署，每个技能的完整规则平均 2,800 token。背景：初版为省事把全部技能正文塞进 system prompt。问题：常驻开销约 176,000 token，一个 200K 窗口刚启动就只剩 12% 可用，多轮之后必然触发摘要；而实测单次会话平均只会用到 1.8 个技能，超过 96% 的常驻内容整场都没被引用过。方案：改成两级加载，索引里每个技能只留名称加一句话描述（约 40 token），正文等匹配上再读。效果：常驻开销从 176,000 token 降到约 2,500 token，可用窗口从 12% 回到 98%；技能匹配准确率没有下降，因为决定匹配的本来就是那句描述，而不是正文。

六、记忆系统

6.1 三层记忆架构

层类型内容作用
①用户画像偏好、习惯、身份信息让 Agent 越用越懂你
②时间线历史事件、操作记录保持会话之间的连贯性
③事实库用户确认的事实避免重复问询相同信息

6.2 记忆更新流水线

记忆更新采用异步流水线，不阻塞主对话：

  1. 提取 → 从对话中抽取新信息
  2. 分类 → 判断属于哪个记忆层
  3. 去重 → 检查是否已存在相同记忆
  4. 原子写入 → 持久化到存储

四步流水线里最容易被省掉、也最不该省的是去重。少了它，记忆库会以每次会话若干条的速度线性膨胀，同一条偏好换几种措辞反复出现；而记忆是要注入上下文的，重复条目吃掉的是每一轮的窗口预算。

异步这件事同样有代价：主对话不等记忆写完就返回，意味着写入可见性是延迟的 —— 用户上一句刚说的偏好，下一句不一定生效。工程上要么接受这个延迟，要么给关键类别开一条同步写入的快路，不能假装它不存在。

记忆是 Agent 在长时间跨度任务中保持一致性的关键。DeerFlow 的三层记忆让 Agent 能在会话之间保持连贯性，而不是每次都从零开始。

七、沙箱与工具生态

7.1 Sandbox 抽象层

Sandbox 是 Agent 执行代码和文件操作的安全隔离环境，提供三种实现：

实现场景特点
Local Sandbox开发调试本地目录隔离，轻量快速
Docker Sandbox单机部署容器隔离，资源限制
K8s Sandbox生产环境Pod 隔离，弹性伸缩

7.2 工具生态三层结构

层来源示例
内置工具DeerFlow 自带bash、ls、read_file、write_file、str_replace、search
社区工具community/ 目录Tavily、Jina、InfoQuest 等搜索与数据服务
MCP 工具外部 MCP Server无限扩展，通过 MCP 协议接入任意服务
MCP（Model Context Protocol）是 DeerFlow 的无限工具扩展机制。通过启动外部 MCP Server，Agent 可以调用几乎任何服务，且新增工具不需要修改 Agent 代码。

7.3 虚拟路径映射

Sandbox 使用虚拟路径映射将 Agent 的逻辑路径与物理路径解耦：

  • /mnt/user-data/workspace/ → 工作目录
  • /mnt/user-data/uploads/ → 用户上传文件
  • /mnt/user-data/outputs/ → 产出物输出
虚拟路径映射：Agent 眼里的世界，与它实际落在哪里 Agent 看到的（三种部署下完全一致） /mnt/user-data/workspace/ 工作目录，读写都在这 /mnt/user-data/uploads/ 用户上传的原始文件 /mnt/user-data/outputs/ 要交付出去的产出物 │ 同一套提示词、同一段代码 ┌─────────┼──────────────────────┬────────────────────┐ ▼ ▼ ▼ Local Sandbox Docker Sandbox K8s Sandbox ./threads//workspace 容器内 /workspace Pod 挂载卷 ./threads//uploads volume 挂载 PVC 子路径 ./threads//outputs 容器销毁即回收 Pod 回收即释放 开发调试用 单机部署用 生产用 这层映射买到的三件事： ① 提示词不用按环境分版本 —— 路径是常量，不是变量 ② 换部署形态不用改 Agent 代码，只换 Sandbox 实现类 ③ 线程之间天然隔离 —— 每个 thread 的物理根目录各不相同 Agent 就算想跨线程读文件，逻辑路径里也没有那个入口

虚拟路径的价值不在"好看"，在于它把部署形态从提示词里彻底赶了出去。一旦 Agent 的提示词里出现过一次真实物理路径，这套提示词就绑死在那一种部署上，换环境就得改文案 —— 而改文案是没法做单元测试的。

这样无论底层是 Local、Docker 还是 K8s，Agent 的代码和提示词都不需要修改。

八、Context Engineering

DeerFlow 的 Context Engineering 是其在长任务中保持效果的核心。包括四个层面：

层面机制解决问题
上下文注入记忆、技能、上传文件按需注入系统提示词Agent 不会"忘事"
上下文压缩SummarizationMiddleware 在消息过长时自动摘要防止上下文窗口溢出
上下文隔离Sub-Agent 独立上下文，不污染主对话多任务并行不互扰
上下文进化技能渐进式加载，按需扩展上下文窗口高效利用

四者回答的是四个不同的问题：注入决定"放什么进来"，压缩决定"放不下时先扔什么"，隔离决定"哪些内容压根不用进主窗口"，进化决定"什么时候才进来"。只做其中一两个的系统，长任务跑到中后段一定会露馅 —— 通常先垮的是隔离那一环，因为它最容易被"顺手让子任务把过程也回传一下"给破坏掉。

示例场景：一次需要调研 12 个竞品并出对比报告的长任务，Lead 派出 3 批共 12 个 Sub-Agent。背景：为方便排查，早期实现让每个 Sub-Agent 把完整执行过程一并回传给 Lead。问题：单个子任务的过程平均 18,000 token，12 个就是 21.6 万 token 全部涌进主上下文，第 7 个子任务返回时就顶穿了窗口，触发摘要；摘要之后前 6 个竞品的结论被压成了两三句话，最终报告里这 6 家的对比明显比后 6 家粗糙。方案：把回传内容限制成结构化结论（每个子任务不超过 1,200 token），完整过程写进各自 trace 文件，需要时按 trace_id 单独去读。效果：主上下文的子任务占用从 21.6 万 token 降到 1.4 万，整任务不再触发摘要，12 个竞品的结论粒度一致；排查能力没有丢失，只是从"堆在主上下文里"改成了"按需从 trace 里捞"。

九、从 v1 到 v2：一次从头重写

DeerFlow v1（2025年 5 月）定位为 Deep Research 框架。社区把它用在了很多意料之外的场景：

  • 数据分析——把 CSV 丢进去让 Agent 自动建模
  • PPT 生成——一句话生成完整演示文稿
  • 内容工厂——批量生成产品文案和 SEO 文章
  • 运维巡检——每天自动检查服务器状态并生成报告

这证明了 DeerFlow 的本质是 Harness，Deep Research 只是第一个 Skill。团队在 2026 年春节期间从头重写，v2 与 v1 不共享任何代码。

十、实践建议

  • 用 Skills 而不是硬编码来扩展 Agent 能力
  • 利用中间件模式处理横切关注点
  • 让 Sub-Agent 处理可并行的复杂任务
  • 用 Sandbox 抽象层而不是直接操作文件系统
  • 依赖 MCP 来扩展工具生态
  • 不要把所有逻辑写在主循环中，会迅速膨胀
  • 不要在 Sub-Agent 中再创建 Sub-Agent，避免递归嵌套
  • 不要一次性加载所有技能，会浪费上下文窗口
  • 不要跳过沙箱直接让 Agent 操作宿主机
  • 不要忽略中间件顺序，Clarification 必须放最后

常见问题

DeerFlow 和 LangChain/LlamaIndex 有什么区别？
LangChain/LlamaIndex 是框架，提供积木让你自己搭。DeerFlow 是 Harness，提供开箱即用的 Agent 运行时环境，包含沙箱、记忆、技能系统和子智能体编排。
为什么选择 LangGraph 而不是手写 while 循环？
图抽象带来三个关键能力：自动状态快照实现断点恢复；图拓扑可视化便于调试监控；条件边路由与节点逻辑解耦。这些对生产级 Agent 至关重要。
Sub-Agent 为什么不能嵌套？
单层委派避免了递归嵌套带来的复杂度和资源消耗问题。如果 Lead Agent 拆解的子任务还需要进一步拆解，应该在 Lead Agent 层面拆得更细，而不是让 Sub-Agent 再拆。
DeerFlow 的 Skills 和 MCP 工具有什么关系？
Skills 是能力的核心扩展单元，定义"做什么"（Markdown 文件）；MCP 是工具扩展机制，提供"怎么做"的能力。Skill 可以调用 MCP 工具，两者是上层编排与底层执行的关系。
DeerFlow 的实际用例有哪些？
市场调研报告（多子智能体并行搜索分析）、代码库分析（clone + 架构解析）、品牌网站生成（CAREN 案例）、数据分析、PPT 生成、内容工厂、运维巡检。共同特点是长时间运行、自主决策、产出完整交付物。
中间件顺序为什么很重要？
ClarificationMiddleware 必须放最后，因为它可能通过 Command(goto=END) 拦截整个图执行。ThreadData 必须放第一，因为后续中间件依赖工作目录。Sandbox 必须在 ThreadData 之后，因为它需要工作目录路径。
