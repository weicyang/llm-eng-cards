一、Config 系统：17 子配置 + 热重载

DeerFlow 的 Config 不是一坨硬编码常量，而是一套声明式 + 多层回退 + 运行时热重载的配置系统。改一行 YAML 不用重启，切一个模型不用改代码。

DeerFlow 的 Middleware 不是松散的插件集合，而是严格有序的 14 层洋葱模型：请求从外向内穿透，响应从内向外回溯。顺序写死在源码中，错一层就崩。

三、10 层 System Prompt 解剖

Lead Agent 的 System Prompt 不是一段固定文本，而是由 10 层模板按优先级动态组装。每层都有明确的注入时机和内容边界。

10 层模板组装

层名称注入时机内容Token 预算
1Identity始终角色定义："你是 DeerFlow，一个 Super Agent"~50
2Core Principles始终行为准则：准确性优先、透明性、安全性~100
3Tool Usage始终工具使用规范：必须先搜索再行动~80
4Memory Context记忆启用时用户记忆注入（三级记忆摘要）~200
5Skills Context有 Skills 时可用 Skills 列表和描述~150
6Tool Context有工具时工具列表和使用示例~200
7Sandbox Info沙箱启用时沙箱能力说明和限制~80
8SubAgent Protocol多 Agent 时Sub-Agent 委派协议和格式~100
9Output Format始终输出格式要求：Markdown、代码块~60
10Dynamic Injection运行时用户自定义 prompt 片段~100

→
按序拼接
→
Token 预算裁剪
→
最终 System Prompt

Token 预算裁剪策略

优先级裁剪顺序（先裁的）原因
最后裁剪Identity + Core Principles核心身份不可丢
中间裁剪Tool Context + Skills Context工具描述可简化
最先裁剪Memory Context + Dynamic Injection记忆摘要可缩短

这张裁剪表实际定义的是一套分层预算：Identity 与 Core Principles 属于不可裁剪段，无论预算多紧都原样保留；Tool Context 和 Skills Context 属于可降级段，超预算时先把完整工具描述换成签名行；Memory Context 与 Dynamic Injection 属于弹性段，直接按条数截断。三段各自持有独立配额，避免了"记忆一多就把身份定义挤掉"这种最难排查的故障。

示例场景：一个接了 34 个工具、开着三层记忆的 Agent，10 层模板一次性拼完约 21,000 token，占 128K 窗口的 16%。背景：早期实现按拼接顺序做尾部截断，谁在后面谁先被砍。问题：Memory Context 恰好排在 Identity 之后，某次记忆积累到 9,000 token 时把后半段的 Core Principles 顶出了窗口，Agent 当场丢失"不得直接改生产配置"这条硬约束，连续三轮尝试写线上文件。方案：改成上表的优先级裁剪 —— 不可裁剪段独占 4,000 token 配额并最先落位，弹性段拿剩余额度按置信度排序截断。效果：System Prompt 的 P99 长度从 31,000 token 稳定到 12,800 token，核心约束被挤掉的情况归零，同时单次请求的固定开销下降约 39%。

四、SubAgent 并发执行引擎

SubAgent 不是"开新线程跑任务"那么简单。DeerFlow 定义了6 种生命周期状态、线程安全的状态同步、三种执行模式，构成一个完整的并发状态机。

六、三级记忆架构：上下文 + 历史分层 + 事实列表

DeerFlow 的记忆不是"短期 + 长期"两层的粗放设计，而是用户上下文（实时） + 历史分层（沉淀） + 事实列表（检索）的三级结构化体系。记忆不是信息堆砌，而是有骨架的状态管理。

七、断点续跑：五层架构 + 双模式持久化

DeerFlow 的断点续跑不是"try-except + 重试"，而是LangGraph 原生 Checkpointer + ThreadState 唯一可信源 + SubAgent 无独立断点 + 双模式持久化的四位一体设计。进程重启后，从最后成功的 step 继续。

"SubAgent 无独立断点"这条原则是整套设计里最反直觉、也最关键的一处。子代理看起来天然应该各存各的快照，但一旦这么做，主图快照与子代理快照就会各有各的时间戳，恢复时必然出现快照错位。DeerFlow 的解法是让子代理只往 ThreadState 里回写结果，快照点始终只有一个，代价是子代理中途的进度会丢，换来的是恢复语义永远唯一。

示例场景：一条派出 6 个 SubAgent 并行调研的任务，整条链路约 40 分钟。背景：早期版本给每个 SubAgent 各配一份独立 checkpoint。问题：进程在第 28 分钟被 OOM 杀掉时，主图快照停在 super-step 7，而 3 个子代理的快照分别停在各自的第 4、6、9 步，恢复后主图按 step 7 重新派发任务，那 3 个子代理却从自己的断点继续，同一份调研结果被写入两次，人工对账花了两小时。方案：取消子代理独立快照，全部状态经 SubagentResult → _background_tasks → ThreadState 单向汇聚，恢复时只反序列化一份 ThreadState，COMPLETED 的直接跳过、RUNNING/FAILED 的整体重启。效果：恢复后的结果重复率从 23% 降到 0，恢复逻辑的代码量减少约一半；代价是未完成子代理的中途进度不保留，实测平均多花 3.4 分钟重跑，换掉了对账成本。

八、Do / Don't

  • 使用 Config 系统管理所有参数，避免硬编码
  • 严格遵守 14 层 Middleware 顺序
  • SubAgent 状态通过 ThreadState 统一管理
  • 生产环境使用 Docker 或 E2B 沙箱
  • 启用三级记忆提升个性化交互质量
  • 生产环境配置 Postgres Checkpointer
  • 利用防抖队列减少 LLM 调用开销
  • 为 System Prompt 设置 Token 预算裁剪策略
  • 不要随意调整 Middleware 顺序（隐式依赖）
  • 不要给 SubAgent 维护独立断点（多快照冲突）
  • 不要跳过沙箱直接操作宿主机
  • 不要把所有记忆不加裁剪地注入 Prompt
  • 不要用 InMemory Checkpointer 跑生产（重启丢数据）
  • 不要频繁同步更新记忆（阻塞交互）
  • 不要在 SubAgent 中再创建 SubAgent
  • 不要忽略 Clarification 中间件的位置约束

九、常见问题 Q&A

为什么 14 层 Middleware 顺序不能调？
DeerFlow 部分中间件存在隐式状态依赖：ThreadData 注入 thread_id 后，Sandbox 才能创建工作目录；Memory 注入后，SubAgent 才有上下文。这是"僵硬但安全"的工程选择，避免了隐式约定带来的维护风险。
SubAgent 为什么没有独立断点？
如果 SubAgent 有独立快照，主线程和子线程的快照可能不一致（比如主线程已记录"子任务完成"但子线程快照还在"执行中"）。DeerFlow 选择"ThreadState 唯一可信源"，所有子代理状态最终同步到主线程，由主线程统一快照，彻底避免多快照冲突。
三级记忆和 OpenClaw 的三级记忆有什么区别？
OpenClaw 的三级记忆是"工作记忆/情景记忆/语义记忆"（模拟人类认知），存储介质是 SQLite + 向量。DeerFlow 的三级记忆是"用户上下文/历史分层/事实列表"（面向用户画像），存储介质是 JSON 文件 + LLM 结构化抽取。两者设计目标不同：OpenClaw 面向通用 Agent 运行时，DeerFlow 面向 Super Agent 的个性化交互。
Config 热重载的边界在哪里？
涉及运行时状态的配置（Sandbox 类型、Checkpoint 后端）不能热重载，因为切换需要重建进程/连接。不涉及运行时状态的配置（模型参数、Skills 目录、Middleware 顺序）可以热重载，下次调用时自动生效。
记忆更新的防抖窗口设多大合适？
取决于对话频率。高频场景（客服机器人）建议 30-60 秒，避免每句话都触发 LLM 更新；低频场景（研究助手）建议 5-10 秒，保证记忆时效性。防抖窗口过短会导致 LLM 调用过载，过长会导致记忆滞后。
断点续跑时 SubAgent 处于 RUNNING 状态怎么办？
续跑时检查 SubAgent 状态：如果 COMPLETED 则跳过；如果 RUNNING/FAILED/TIMED_OUT，根据业务逻辑决定是否重启。DeerFlow 默认策略是重启 RUNNING 状态的 SubAgent（因为进程已重启，之前的执行上下文已丢失）。
