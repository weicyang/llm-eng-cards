HH04 · Harness 与 Prompt / Context Engineering 的关系

PE/CE/HE 层层递进 → AI IDE 差异本质 → AI程序员仍需人类的原因 → 驾驭系统全景

三代"工程"是三个同心圆：Prompt Engineering 管好一句话，Context Engineering 管好所有输入，Harness Engineering 管好整个系统的运行与迭代——HE ⊃ CE ⊃ PE，外层包含内层，范围越大越接近真正的系统工程。

一、三代工程的层层递进

大模型本质是预测下一个字词的统计模型，给它的指令越精准、上下文越丰富，输出就越靠谱。围绕"如何让输出更靠谱"这件事，工程界的关注范围经历了三次扩张，形成了三代"工程"。

概念关注范围核心动作局限
Prompt Engineering单次对话的提示词角色设定 / 背景补充 / 历史引用 / 参考文档 / 输出格式只调一次对话，管不了多步任务
Context Engineering所有输入信息的系统化管理RAG 检索 / Memory / 摘要压缩 / 工具选择只管理信息输入，管不了执行与校验
Harness Engineering整个 AI 应用系统模型 + 工具 + 流程 + 评估 + 反馈 + 编排无（本身就是系统工程方法论）
三代工程的包含关系与决策路径 ┌───────────────────────────────────────────────┐ │ Harness Engineering │ │ ┌───────────────────────────────────────┐ │ │ │ Context Engineering │ │ │ │ ┌───────────────────────────────┐ │ │ │ │ │ Prompt Engineering │ │ │ │ │ └───────────────────────────────┘ │ │ │ └───────────────────────────────────────┘ │ └───────────────────────────────────────────────┘ HE ⊃ CE ⊃ PE 症状 → 该补哪一层： 输出格式不稳、风格漂移 ──→ 补 PE（提示词/示例/格式约束） 答非所问、幻觉、知识过期 ──→ 补 CE（检索/记忆/压缩） 多步任务不可靠、出错没人兜底 ──→ 上 HE（工具/护栏/评估/反馈）

判断该用哪代工程，看症状就够了：说错话是 PE 的事，记不住事是 CE 的事，办不成事还闯祸，就该 HE 出场了。

简记：PE = 调一句话说得好；CE = 管所有信息管得好；HE = 驾驭整个系统跑得好。三者是包含关系：HE ⊃ CE ⊃ PE。

需要强调的是，"包含"意味着做好 HE 的团队一定同时精通 PE 和 CE——提示词和上下文管理是 Harness 的输入层，是整套系统的地基。跳过地基直接搭上层建筑，是实践中最常见的失败模式。

二、Prompt Engineering：把一句话说清楚

PE 是最早被系统化的方向，核心命题只有一个：如何在一轮对话内，让模型准确理解你的意图并稳定输出。它的所有技巧都围绕"单次输入的质量"展开。

PE 的本质是"降低单次沟通的歧义"——你给模型的每一个字都在压缩它的猜测空间，猜测空间越小，输出越稳定。

手段做法解决什么问题
角色设定"你是资深后端工程师，熟悉 Go 与分布式系统"输出风格与专业度漂移
Few-shot（少样本示例）给 2~3 个"输入→输出"样例再提问格式不稳定、理解偏差
输出格式约束指定 JSON Schema、Markdown 结构、字段清单下游程序解析失败
思维链引导"先分析约束条件，再给出结论"复杂推理跳步出错
边界声明"不知道就说不知道，不要编造"幻觉、过度自信

PE 的天花板也很明显：它只作用于"这一轮对话"。一旦任务跨越多轮、需要外部知识、或要调用工具执行，再精妙的提示词也无能为力——这时就需要把关注范围从"一句话"扩大到"所有输入信息"。

PE 没有过时：即使到了 Harness 时代，System Prompt 依然是 Harness 输入层的核心组件。区别在于，PE 时代它是"全部"，HE 时代它只是"五分之一"。

三、Context Engineering：管好所有输入信息

当任务复杂到单次提示词装不下时，工程重心转向了"进入模型窗口的一切信息"：哪些该检索进来、哪些该记住、哪些该压缩、哪些工具描述该挂载。这就是 Context Engineering 的战场。

上下文窗口是模型的"工作记忆"，CE 就是这份工作记忆的调度员——不是塞得越满越好，而是在有限预算内装入当前任务最需要的信息。

上下文装配流水线（CE 核心机制） ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │ RAG 检索 │ │ 长期记忆 │ │ 工具结果 │ │ 历史摘要 │ │ 外部知识 │ │ Memory │ │ 函数返回 │ │ 压缩旧对话│ └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ └──────┬────┴──────┬────┴──────┬────┘ ▼ ▼ ▼ ┌──────────────────────────────────────┐ │ 上下文装配器：筛选 → 排序 → 压缩 → 截断 │ └──────────────────┬───────────────────┘ ▼ ┌──────────────────────────────────────┐ │ 最终 Prompt：窗口预算内的最优信息组合 │ └──────────────────────────────────────┘
机制管理对象典型手段
RAG 检索外部知识（文档、代码库）向量检索 + 关键词检索 + 重排
Memory跨会话的用户偏好与事实摘要存储、按需召回
压缩过长的对话历史滚动摘要、滑动窗口、重要性筛选
工具筛选工具/函数描述清单只挂载当前任务可能用到的工具

CE 兴起的直接原因是Lost in the Middle（中间迷失）现象：上下文越长，模型对中间位置信息的利用率越低。窗口从 4K 涨到 200K 并没有让问题消失——把 10 万字全塞进去，效果往往不如精选 3000 字。所以 CE 的核心动作永远是"筛选"而不是"堆砌"。

四、Harness Engineering：驾驭整个系统

PE 管一句话、CE 管所有输入，但当 Agent 要连续执行几十步、调用十几个工具时，光管好输入仍然不够——执行过程谁来约束？输出错了谁来发现？发现了怎么改进？这些问题催生了 Harness Engineering：把模型、工具、流程、评估、反馈组装成一个可控的整体。

如果 PE 是"写一封好信"、CE 是"整理好全部材料"，HE 就是"运营一家公司"——材料只是输入，公司还要有流程、有质检、有复盘，才能持续稳定地交付。

┌──────────────────────── Harness 系统全景 ────────────────────────┐ │ │ │ 输入层 ──→ ┌──────────┐ ┌──────────┐ │ │ │ 提示词模板 │ │ 上下文装配 │ ← PE + CE 的主场 │ │ └─────┬────┘ └─────┬────┘ │ │ └──────┬──────┘ │ │ ▼ │ │ 执行层 ──→ ┌─────────────┐ │ │ │ 大模型推理 │ │ │ └──────┬──────┘ │ │ ▼ │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ 工具调用/沙箱 │ → │ 权限护栏/审批 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ 编排层 ──→ Agent 工作流 / 状态机 / 子任务拆分 / 自动重试 │ │ │ │ 评估层 ──→ Eval 测试集 / A/B 实验 / 线上指标监控 │ │ │ │ 反馈层 ──→ 失败案例回流 → 修正提示词/上下文/工具 → 下一轮循环 │ └─────────────────────────────────────────────────────────────────┘
层级包含内容对应的工程传统
输入层提示词模板、上下文装配PE + CE（前两代的积累）
执行层模型推理、工具调用、沙箱、权限审批传统软件安全工程
编排层工作流、状态机、重试、子任务拆分分布式系统与流程引擎
评估层Eval 集、A/B 实验、监控告警质量工程与可观测性
反馈层失败回流、自动修正、人工标注入库闭环控制与持续集成

注意这张全景图的结构：PE 和 CE 并没有被抛弃，而是被"收编"为 Harness 的输入层。Harness 真正新增的，是执行层的护栏、编排层的工作流、以及评估层与反馈层构成的Agent Loop（智能体循环，Agent 感知—决策—执行—复盘的持续运转闭环）。

五、AI IDE 差异的本质：Harness 质量之争

很多开发者有过同样的体验：同一个模型（比如 Claude Sonnet），在裸 API 里表现平平，换到 Cursor 或 Claude Code 里却像换了个脑子。差异不在模型本身，而在于 IDE 提供的 Harness 质量不同。

AI IDE 本质上就是一个打包好的 Harness 系统——它替你预装了提示词模板、上下文管理、工具集成和护栏。你感受到的"IDE 差异"，其实是"别人家 Harness 设计水平"的差异。

差异点说明用户的直接感知
System Prompt 设计不同 IDE 的内置提示词质量不同回答风格、稳定性、遵循指令的程度
上下文管理策略有的自动压缩与筛选，有的靠手动管理长会话是否"降智"、跨文件修改准不准
工具集成能力MCP Server 支持程度、终端/浏览器接入深度能不能真正动手改文件、跑命令
代码理解深度项目级索引 vs 文件级索引、符号解析能力大型重构是否靠谱
护栏与确认机制危险操作拦截、diff 预览、回滚能力敢不敢放手让它连续执行

5.1 主流 AI IDE 的 Harness 侧写

IDEHarness 核心手段定位特点
Claude CodeCLAUDE.md 项目约定 + 权限分级确认 + Hooks 钩子终端原生、约定驱动、可脚本化扩展
Cursor.cursor/rules 规则文件 + 全项目索引 + Tab 智能补全IDE 深度集成、编辑体验顺滑
ClineMCP 生态 + Plan/Act 双模式 + 逐步确认开源免费、可自托管、社区活跃
案例：OpenAI Codex 团队的 Harness 实践。背景：Codex 团队让 Agent 成为代码库的主要贡献者。问题：同一个模型在"裸调用"和"有组织的系统"中产出质量天差地别，直接放手必然失控。方案：构建完整 Harness——AGENTS.md 沉淀项目约定、linter 与 CI 充当自动审查官、Eval 集度量每次变更。效果：5 个月内产出近 100 万行代码，几乎全部由 Agent 生成并通过自动校验。这个案例说明：模型能力是公开商品，Harness 质量才是团队真正的护城河——IDE 之争的本质正在于此。

六、为什么 AI 程序员仍需人类

既然 Harness 这么强，AI 程序员会不会很快取代人类？恰恰相反——Harness 越强大，对人类工程师的要求反而越高，只是工作内容发生了迁移。

AI 接管的是"执行"，人类保留的是"判断"：判断该建什么系统、判断结果对不对、判断出了问题谁负责——这三件事目前没有任何模型能签字画押。

关键环节为什么 AI 做不了人类做什么
架构决策系统设计、技术选型需要经验、权衡与担责定方向、选技术栈、画边界
业务理解AI 不理解需求背后的真正意图与商业约束澄清需求、定义验收标准
质量把关代码审查、安全审计需要人类的最终判断Review 关键变更、对结果负责
Harness 设计搭建和优化 AI 开发系统本身就是高难度工程设计提示词体系、工具、评估与反馈机制
案例：Anthropic 多智能体研究系统的"预算教训"。背景：Anthropic 构建了 orchestrator-worker 式多智能体系统处理复杂研究任务。问题：系统能力很强，但 token 消耗约为单 Agent 的 15 倍，若无控制会"用力过猛"烧掉预算。方案：由人类工程师设计任务分级策略——只在高价值、可并行的研究任务上启用重 Harness，并为每次运行设置预算上限与引用核查。效果：成本与收益重新对齐。启示：决定"何时用、用多重"的永远是人类的工程判断——AI 不会替你做 ROI 分析，这正是人类不可替代的位置。
  • 把工作重心迁移到"设计 Harness"：写清约定、建好评估、管好工具权限
  • 在架构决策、业务澄清、最终审查这三个环节保持亲力亲为
  • 用 CLAUDE.md / AGENTS.md 等约定文件沉淀团队知识，让 Agent 继承
  • 给 Agent 的每次重任务设置预算与验收标准
  • 不要把"AI 能写代码"误解为"不需要人审查"——生成越快，审查越关键
  • 不要只做提示词调优员：PE 技巧的半衰期很短，系统能力才保值
  • 不要在没有验收标准的情况下让 Agent 长时间自主运行
  • 不要指望模型自己判断"这个任务值不值得花 15 倍成本"
AI 程序员不是替代程序员，而是让程序员的工作重心从"写代码"转向"驾驭 AI 写代码"——这恰恰就是 Harness Engineering 的核心思想。

Q&A

PE、CE、HE 三者的关系是什么？
三者是层层递进的包含关系（HE ⊃ CE ⊃ PE）：①Prompt Engineering 关注单次对话的提示词设计（角色/背景/格式/约束）；②Context Engineering 关注所有输入信息的系统化管理（RAG 检索、Memory、摘要压缩、工具筛选）；③Harness Engineering 关注整个 AI 应用系统的设计（模型+工具+流程+评估+反馈+编排）。PE 解决"怎么把一句话说清楚"，CE 解决"怎么管理所有信息"，HE 解决"怎么让整个系统可靠运行"。做好 HE 的团队必然同时精通 PE 和 CE，因为输入层是整套系统的地基。
为什么同样的大模型在不同 AI IDE 中效果差很多？
因为差异不在模型本身，而在 IDE 提供的 Harness 质量：①System Prompt 设计质量不同（内置提示词越好，模型表现越稳定）；②上下文管理策略不同（有的自动压缩筛选，有的靠手动）；③工具集成能力不同（MCP 支持程度、终端与浏览器接入深度）；④代码理解能力不同（项目级索引 vs 文件级索引）。AI IDE 本质上是一个打包好的 Harness 系统，它替你预装了提示词模板、上下文管理、工具集成和护栏。你感受到的"IDE 差异"，其实是各家 Harness 设计水平的差异。
实践中怎么判断该补 PE、CE 还是 HE？
看症状就行：如果问题是"输出格式不稳、风格漂移、不遵循指令"，补 PE——加角色设定、Few-shot 示例和格式约束；如果问题是"答非所问、编造事实、知识过期、长对话降智"，补 CE——上 RAG 检索、记忆管理和历史压缩；如果问题是"多步任务中途跑偏、工具调用出错没人兜底、改了 A 坏了 B"，那就必须上 HE——加工具护栏、工作流编排、Eval 评估和失败回流。多数真实系统是三层问题叠加，正确的做法是从内向外逐层补齐，而不是跳过 PE/CE 直接堆多智能体。
"AI IDE 本质是 Harness 系统"这句话怎么理解？
裸模型 API 只提供"推理"这一个动作，而 IDE 要解决的是"如何帮用户可靠地完成开发任务"——这中间的差值全部由 Harness 填充：预装的 System Prompt、项目索引与上下文装配、终端/文件/浏览器工具、权限确认与 diff 预览、以及错误恢复机制。所以 IDE 之间的竞争，表面上是产品体验之争，底层是 Harness 工程质量之争。这也解释了为什么同一模型换个 IDE 像换了个脑子：模型没变，变的是包裹模型的那整套缰绳。对用户的启示是：评估 IDE 时不要只看它接了哪个模型，要看它的约定文件、索引深度和护栏机制。
既然 HE 包含 PE 和 CE，是不是可以跳过前两者直接做 Harness？
不可以，这是实践中最常见的失败模式。PE 和 CE 构成 Harness 的输入层：提示词质量差，模型连单步指令都执行不稳，再好的编排也只是把错误放大到整个流程；上下文管理差，Agent 每一步都在错误的信息上做决策，护栏和评估只能事后收拾残局。正确的路径是从内向外逐层搭建：先让单次输出稳定（PE），再让输入信息精准（CE），然后加工具与护栏（执行层），最后建评估与反馈（HE 的增量价值所在）。地基不牢时，上层建筑越复杂，崩塌得越彻底。
AI 程序员越来越强，人类工程师的工作重心会怎么变？
工作重心会从"写代码"迁移到"驾驭 AI 写代码"，具体落在四个位置：①架构决策——系统设计、技术选型需要经验与担责，AI 给不了最终判断；②业务理解——澄清需求背后的真实意图、定义验收标准；③质量把关——审查关键变更、做安全审计、对结果签字负责；④Harness 设计——这本身就是高难度工程，包括提示词体系、工具权限、评估集和反馈机制的搭建。Anthropic 多智能体系统的案例很能说明问题：系统 token 消耗是单 Agent 的 15 倍，决定"何时值得用、预算多少"的永远是人类的 ROI 判断。生成越快，审查与设计能力越值钱。
