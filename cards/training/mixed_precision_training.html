Mixed Precision Training — 用更少的位数做更快的训练

一、浮点数基础

同样是 16 位，FP16 和 BF16 的差别只在于这 16 个格子怎么在"范围"和"刻度"之间分账：指数位决定动态范围（能表示多大、多小），尾数位决定精度（能分辨多细）。混合精度的所有麻烦，都是这笔分账的后果。

┌─┬────────┬────────────────────────┐ FP32 32 bit │S│ E (8) │ M (23) │ 范围 ±3.4e38 刻度最细 └─┴────────┴────────────────────────┘ ┌─┬─────┬──────────┐ FP16 16 bit │S│E (5)│ M (10) │ 范围 ±65504 刻度较细 └─┴─────┴──────────┘ ┌─┬────────┬───────┐ BF16 16 bit │S│ E (8) │ M (7) │ 范围 ±3.4e38 刻度较粗 └─┴────────┴───────┘ ┌─┬────┬───┐ FP8 8 bit │S│E(4)│M 3│ 范围 ±448 刻度很粗 (E4M3) └─┴────┴───┘ 指数位 ──▶ 决定"能表示多大 / 多小"（动态范围，够不够用） 尾数位 ──▶ 决定"能分辨多细"（精度，准不准） BF16 与 FP32 的指数位数完全相同 ⇒ 两者互转只是补零 / 截断低 16 位尾数， 不存在"转过去就溢出"的问题；FP16 的 5 位指数才是后面一切补丁的根源。

IEEE 754 标准

浮点数由三部分组成：符号位 (Sign)、指数位 (Exponent)、尾数位 (Mantissa/Fraction)。数值 = (-1)^S × 2^(E-bias) × (1 + M)。

各精度位分配

FP16161510±65504~3.3 位十进制

关键对比：FP16 指数位只有 5 位，动态范围小（容易溢出）；BF16 保持 FP32 相同的 8 位指数，范围一样大但精度较低；FP8 在 H100 上用于前向/反向加速。
💡 知识要点
  • 能画出 FP32/FP16/BF16 的位布局
  • 理解"动态范围"取决于指数位数，"精度"取决于尾数位数
  • BF16 = "截断版 FP32"（直接砍掉低 16 位尾数）

二、为什么用混合精度

低精度买到的是三样东西：Tensor Core 的算力翻倍、激活值显存对半、分布式通信量对半。三样里只有第三样是"顺带的"，前两样才是把混合精度做成标配的真正理由。

核心收益

  • 内存减半：FP16/BF16 参数占 FP32 一半空间 → 同 GPU 可训练更大 batch/模型
  • Tensor Core 加速：NVIDIA Tensor Core 对 FP16/BF16 矩阵乘法有专门硬件路径，吞吐量 2-8× 于 FP32 CUDA Core
  • 通信带宽减半：分布式训练中 AllReduce 传输量减少 50%
  • 训练大模型的必要条件：LLM (7B+) 若全 FP32 连单卡都放不下

💡 知识要点
  • 混合精度不只是"省显存"，更是利用 Tensor Core 加速计算
  • A100 默认对 FP32 矩阵乘法使用 TF32（19位），已是"隐式混合精度"
  • 通信减半对多机训练意义重大（带宽往往是瓶颈）

三、FP16 训练的问题

FP16 训练翻车只有两种死法：大数撞上 65504 变成 inf，小数掉到 6e-8 以下变成 0。两种死法的共同点是——梯度携带的信息在到达优化器之前就已经丢了，而 loss 曲线未必立刻告诉你。

溢出 (Overflow)

FP16 最大值仅 65504。前向/反向中如果某个激活值或梯度 > 65504 就会变为 inf，随后传播导致 NaN。

下溢 (Underflow)

FP16 最小正次正规数约 6×10⁻⁸。许多梯度本身量级在 10⁻⁵ ~ 10⁻⁸ 之间，转为 FP16 后直接变为 0 → 梯度消失。

小梯度丢失

实验表明：直接用 FP16 训练时，约 5% 的梯度值落在 FP16 可表示的最小值以下，被截断为零。这些小梯度累积起来对参数更新有显著贡献。

数值不稳定操作

  • exp()：指数函数很容易溢出
  • softmax：需要先减去 max 再求 exp
  • sum reduction：大量小值相加在低精度下误差累积
  • LayerNorm：方差计算对精度敏感
💡 知识要点
  • FP16 训练失败的两大原因：溢出（变 inf/NaN）和下溢（梯度归零）
  • Loss Scaling 解决下溢，保留 FP32 Master Weights 解决精度丢失
  • 某些操作（softmax, norm, loss）必须在 FP32 下进行

四、Loss Scaling

损失缩放是把梯度临时放大到 FP16 能表示的区间里算完、更新前再缩回来。放大倍数只作用于"存储与传输"这一段，不改变数学上的更新量——所以它不是近似，是无损的搬运。

FP16 能表示的正数区间（横轴为对数刻度） ← 下溢盲区 →│←──────────── 可精确表示 ────────────→│← 溢出 → 0 ─────────────┼──────────────────────────────────────┼──────────▶ 6e-8 65504 未缩放：真实梯度分布整体偏左，左半截直接被四舍五入成 0 ▁▂▃▅▇▅▃▂▁ ────────────┴─────────┴──────────────────────────────────────── 1e-10 1e-6 └── 这一段全部归零，信息永久丢失 ──┘ 乘上 S = 2^15 后：整条分布右移，完整落进可表示区间 ▁▂▃▅▇▅▃▂▁ ─────────────────────────────────┴─────────┴────────────────── 3e-6 3e-2 └── 全部保留 ──┘ 更新前再 ÷ S 还原真实量级 ⇒ 缩放只发生在中间过程，结果不变。 S 太大 ─▶ 分布右端撞上 65504，出现 inf ─▶ 动态策略把 S 减半并丢弃本步。 S 太小 ─▶ 保护不足，左半截仍在归零 ─▶ 连续若干步无异常则把 S 翻倍。
示例场景：某团队在 8×V100 上做 7B 模型的 FP16 微调。背景——V100 没有原生 BF16，只能走 FP16 + GradScaler 这条路。问题——前 200 步一切正常，之后 loss 变成 NaN；回看日志发现 GradScaler 的 scale 从 65536 一路减半掉到 256 仍未稳定，跳步率（skipped steps）高达 18%，等于近五分之一的数据白跑。方案——先把初始 scale 从 2^16 降到 2^12 让它别一上来就撞顶，再加 1.0 的梯度裁剪压住尖峰，最后用二分法定位到一处残差累加在 FP16 下溢出、给该模块单独套 autocast(enabled=False)。效果——scale 稳定在 2^13~2^14 区间不再单调下滑，跳步率降到 0.5% 以下，训练跑完全程无 NaN。

核心思想

在反向传播前将 loss 乘以一个较大的 Scale Factor（如 1024 或 65536），使梯度整体放大，避免下溢到 FP16 的"盲区"。更新参数前再除以同一 Scale Factor 恢复真实梯度。

# 伪代码
scaled_loss = loss * scale_factor
scaled_loss.backward()          # FP16 梯度被放大
optimizer.step(grad / scale_factor)  # 恢复真实梯度后更新 FP32 参数

动态 Loss Scaling

固定 Scale Factor 可能太大（导致溢出）或太小（保护不足）。动态策略：

  1. 初始 Scale Factor = 2¹⁵ 或 2¹⁶
  2. 每 N 步（如 2000 步）若无 inf/NaN → Scale Factor × 2（放大）
  3. 若检测到 inf/NaN → Scale Factor / 2（缩小），并跳过本次参数更新

溢出检测与回退

if any(grad == inf or grad == NaN):
    scale_factor /= 2
    skip this optimizer step   # 不更新参数
else:
    optimizer.step(grad / scale_factor)
    if consecutive_ok_steps >= growth_interval:
        scale_factor *= 2
💡 知识要点
  • Loss Scaling 本质：在 FP16 可表示范围内"挪动"梯度分布
  • 动态 Scaling 通过"试探+回退"自动找到合适的缩放因子
  • 检测到 overflow 时必须跳过当前 step（否则污染参数）
  • BF16 由于范围够大，通常不需要 Loss Scaling

五、AMP (Automatic Mixed Precision)

AMP 是两个独立零件的组合：autocast 负责"这个算子该用什么精度"，GradScaler 负责"梯度别掉到 0"。用 BF16 时第二个零件可以整个拿掉，这就是 BF16 代码更短的原因。

PyTorch AMP API

import torch
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()

for data, target in dataloader:
    optimizer.zero_grad()

    with autocast(dtype=torch.float16):   # 自动选择精度
        output = model(data)
        loss = criterion(output, target)

    scaler.scale(loss).backward()         # 缩放 loss → FP16 梯度
    scaler.step(optimizer)                # unscale → 检测 inf → 更新
    scaler.update()                       # 调整 scale factor

autocast 上下文管理器

autocast 自动将支持的操作转为 FP16（或 BF16），不支持的保持 FP32。程序员无需手动管理每个 op 的精度。

白名单 / 黑名单

类别操作精度
白名单 (FP16)matmul, conv, linear, BMMFP16 ✓
黑名单 (FP32)softmax, layer_norm, batch_norm, loss functions, exp, log, powFP32 保持
灰名单element-wise ops (ReLU, dropout, add)跟随输入精度

GradScaler 内部流程

  1. scaler.scale(loss)：loss × current_scale
  2. .backward()：梯度全部 × current_scale（FP16 下不会下溢）
  3. scaler.step(optimizer)：先 unscale_（梯度 / scale），检查 inf/NaN，无异常则 optimizer.step()
  4. scaler.update()：根据是否检测到 inf 调整 scale_factor
💡 知识要点
  • AMP = autocast（精度选择）+ GradScaler（Loss Scaling）
  • 白名单是计算密集型 ops（受益于 Tensor Core），黑名单是精度敏感 ops
  • autocast 只影响前向；反向自动匹配前向的精度
  • PyTorch 2.0+ 推荐 torch.amp.autocast(device_type='cuda', dtype=torch.bfloat16)

六、BF16 vs FP16

BF16 = FP32 的范围 + 更粗的刻度。范围够大所以不会下溢，于是损失缩放、溢出检测、跳步回退这一整套补丁可以一起删掉——BF16 的价值一半在数值，一半在少了一堆要调的旋钮。

BF16 的核心优势

对比维度FP16BF16
指数位5 位8 位
尾数位10 位7 位
动态范围±65504±3.4×10³⁸（同 FP32）
是否需要 Loss Scaling必须通常不需要
精度较高较低（但够用）

硬件支持

  • A100 / H100：原生 BF16 Tensor Core，吞吐与 FP16 相同
  • V100：不支持 BF16（只能用 FP16）
  • TPU：Google 从 TPUv2 起就使用 BF16

LLM 训练标配 BF16

GPT-3、LLaMA、PaLM 等大模型均使用 BF16 训练。原因：

  • 不需要 Loss Scaling → 代码更简单、训练更稳定
  • 范围与 FP32 相同 → 几乎不会 overflow
  • 精度损失在统计意义上可忽略（大模型的梯度噪声远大于 BF16 量化噪声）
# BF16 训练（PyTorch）— 不需要 GradScaler
with torch.amp.autocast(device_type='cuda', dtype=torch.bfloat16):
    output = model(data)
    loss = criterion(output, target)
loss.backward()
optimizer.step()
💡 知识要点
  • BF16 = FP32 的范围 + 较低的精度 → 不需要 Loss Scaling
  • LLM 训练首选 BF16（前提是硬件支持）
  • 如果用 V100 只能选 FP16 + GradScaler
  • BF16 转 FP32 只需补零（低位尾数），转换极快

七、FP8 训练

位数越少，越依赖"先量尺寸再装箱"。FP8 的 ±448 窗口装不下任何未经缩放的真实张量，所以必须逐张量算缩放因子；而为了不多跑一遍前向去取最大值，就用上一步的历史最大值来估——这就是延迟缩放。

两种 FP8 格式

格式指数尾数范围用途
E4M343±448前向（权重 & 激活）
E5M252±57344反向（梯度）

E4M3 精度更高（3 位尾数），适合表示权重和激活；E5M2 范围更大（5 位指数），适合梯度（梯度分布方差大）。

Transformer Engine

NVIDIA Transformer Engine 是 FP8 训练的软件框架，集成在 Megatron-LM / NeMo 中：

  • 自动对 Linear 层使用 FP8 GEMM
  • 管理 per-tensor scaling factor
  • 提供 FP8 与 BF16/FP16 之间的自动转换

延迟缩放 (Delayed Scaling)

FP8 范围极小，必须为每个 tensor 维护一个 scaling factor。延迟缩放策略：

  1. 使用前几次迭代中的 amax（绝对值最大值）历史来计算当前 scale
  2. scale = FP8_MAX / amax_history.max()
  3. 延迟一步应用（当前 step 的 amax 用于下一步的 scale 计算）

这避免了需要两次 pass（先算 amax 再做计算）的开销。

H100 FP8 Tensor Core

H100 FP8 算力高达 ~2000 TFLOPS（是 BF16 的约 2×），使训练速度可再翻倍。目前 FP8 训练还在早期阶段，主要用于大规模 LLM pre-training。

💡 知识要点
  • E4M3 用于前向（精度优先），E5M2 用于反向（范围优先）
  • FP8 必须做 per-tensor scaling（不像 BF16 可以不 scale）
  • 延迟缩放 = 用历史 amax 估算当前 scale，避免额外 pass
  • Transformer Engine 自动管理 FP8 ↔ higher precision 转换

八、Master Weights

FP16 负责快，FP32 的主权重副本负责不把小的更新量四舍五入成零。两份权重不是冗余，是分工：一份用来算得快，一份用来记得准。

┌────────────────────────────────┐ │ FP32 Master Weights W │ ◀── 唯一的"真相副本" │ FP32 Adam 状态 m, v │ 优化器只读写这里 └───────────────┬────────────────┘ │ cast（每步开始，只读） ▼ ┌────────────────────────────────┐ │ FP16 / BF16 Weights w │ 参与实际计算的工作副本 └───────────────┬────────────────┘ ▼ autocast：matmul / conv / linear 走低精度 ┌───────────────┐ │ Forward │ ──▶ loss（黑名单算子已提回 FP32） └───────────────┘ │ │ × S 仅 FP16 需要 ┌──────────────┐ ▼ │ Backward │ ◀── scaled_loss └──────┬───────┘ ▼ FP16 梯度，已放大 S 倍（躲开下溢盲区） ┌──────────────────┐ │ 扫描 inf / NaN │ └───┬──────────┬───┘ 有 │ │ 无 ▼ ▼ S ← S / 2 grad ÷ S ──▶ 转 FP32 丢弃本步 │ W 保持不动 ▼ │ ┌────────────────────────┐ │ │ FP32 下更新 W、m、v │ └──────────────┴───────────┬────────────┘ │ ▲──────── 回到顶部 ─────┘ 关键：低精度只出现在"算"的路径上，"记"的路径（W / m / v）全程 FP32。
示例场景：显存账必须分两侧算，否则容量预估一定对不上。背景——某团队按"混合精度显存减半"的说法给 7B 模型（70 亿参数）规划单卡容量。问题——纯 FP32 训练的参数侧固定开销是 4（权重）+ 4（梯度）+ 4（Adam m）+ 4（Adam v）= 16 字节/参数，约 112 GB；换成 FP16 混合精度后是 2（FP16 权重）+ 2（FP16 梯度）+ 4（FP32 主权重）+ 4 + 4 = 16 字节/参数，还是 112 GB，一个字节没省。照"减半"假设排的容量一上机就 OOM。方案——把混合精度重新定位成"激活侧减半 + 算力翻倍"，参数侧的 112 GB 交给优化器状态分片和 8-bit 优化器去解决，两条账分开核算。效果——预估与实测对上了；同时也解释了为什么长序列、大 batch 场景下混合精度的显存收益远比短序列明显——激活值随 batch × 序列长度增长，早已远大于参数侧。

为什么优化器状态保持 FP32

参数更新公式：w = w - lr × grad。当 lr × grad 的量级 < FP16 精度（约 2⁻¹⁰ ≈ 0.001 的相对误差）时，w - lr×grad 在 FP16 下等于 w（更新被吞掉）。

混合精度训练的完整流程

# 训练循环
# 1. FP32 master weights → 拷贝为 FP16 weights
w_fp16 = w_fp32.half()

# 2. FP16 前向传播
with autocast():
    loss = model_fp16(x)

# 3. FP16 反向传播（带 loss scaling）
scaled_loss = loss * scale_factor
scaled_loss.backward()  # grad 是 FP16

# 4. FP32 参数更新
grad_fp32 = grad_fp16.float() / scale_factor
w_fp32 = w_fp32 - lr * grad_fp32   # 在 FP32 下更新

# Adam 的 m, v 也是 FP32

对比纯 FP32 训练（4 + 4 + 4 + 4 = 16 bytes）似乎没省，但激活值内存减半是最大收益（激活 >> 参数），且计算速度提升 2×+。

💡 知识要点
  • Master Weights 必须 FP32：否则小学习率更新会被精度吞掉
  • Adam 的 m/v 也必须 FP32（它们量级比参数小很多）
  • 混合精度的真正显存收益来自激活值减半（activation checkpointing 配合效果更好）
  • 能画出 FP16 forward → FP16 backward → FP32 update 的完整数据流

九、混合精度最佳实践

一条判据就能覆盖大半场景：算子是"乘加密集"的就交给低精度换速度，算子要"求和、求指数、求方差"的就留在 FP32 保正确。AMP 的黑白名单本质上就是这条判据的清单化。

  • 硬件有原生 BF16 就直接上 BF16，省掉损失缩放这一整套要调的旋钮
  • 必须走 FP16 时用动态损失缩放，让它自己找工作点
  • 把 softmax、LayerNorm、loss、以及一切求和归约留在 FP32
  • 主权重和 Adam 的 m、v 一律 FP32，这是精度底线不是优化项
  • 把跳步率当一等监控指标，它比 loss 曲线更早暴露数值问题
  • 梯度累加放在 unscale 之后、FP32 缓冲区里做，避免多步累加误差
  • 定位不明 NaN 用二分法逐段关 autocast，比通读代码快得多
  • 不要在没有原生 BF16 的老卡上指定 bfloat16，拿不到 Tensor Core 加速
  • 不要在检测到 inf/NaN 后照常 optimizer.step()，NaN 会经动量传染到之后每一步
  • 不要照抄别人的初始 scale 常数，不同模型的梯度量级能差几个数量级
  • 不要把 Embedding、归一化层硬塞进低精度换速度，它们不吃 Tensor Core 却最先出问题
  • 不要只看 loss 没炸就断定精度没问题，小梯度静默归零时 loss 往往只是"收敛得慢"
  • 不要在低精度下做长序列的 sum / mean 归约，累加误差会随长度线性放大
  • 不要把损失缩放当成万能解药，它治下溢，不治梯度爆炸

数值稳定的 Softmax

# 不安全
softmax(x) = exp(x) / sum(exp(x))   # exp(x) 可能溢出

# 安全版本（PyTorch 默认实现）
x_stable = x - x.max(dim=-1, keepdim=True)
softmax(x) = exp(x_stable) / sum(exp(x_stable))

在 AMP 中，softmax 被放在黑名单中自动用 FP32 计算。

数值稳定的 LayerNorm

LayerNorm 涉及方差计算 var = mean((x - mean)²)。在 FP16 下如果 x 值较大，(x-mean)² 容易溢出。PyTorch 的 nn.LayerNorm 在 AMP 下自动提升为 FP32。

Gradient Accumulation 注意事项

  • 梯度累加发生在 FP16/BF16 空间时，多步累加误差会放大
  • 推荐：在 FP32 空间做累加（unscale 后累加到 FP32 buffer）
  • PyTorch GradScaler 的 unscale_ 在 step() 内调用，多步累加时只在最后一步调用 scaler.step()
for i, (data, target) in enumerate(dataloader):
    with autocast():
        loss = model(data, target) / accumulation_steps
    scaler.scale(loss).backward()

    if (i + 1) % accumulation_steps == 0:
        scaler.step(optimizer)
        scaler.update()
        optimizer.zero_grad()

常见 NaN 排查

症状可能原因解决方案
训练初期 NaN初始 scale factor 太大降低初始 scale（如 2¹²）
Loss 突然 NaN梯度爆炸 → FP16 溢出Gradient Clipping + 降低 LR
某层持续 NaN该层对 FP16 精度敏感用 autocast(enabled=False) 强制 FP32
Scale factor 持续下降模型不稳定 / LR 过大检查模型架构和超参数
Loss 不收敛但无 NaN小梯度被下溢吞掉增大 scale factor 初始值

其他实践建议

  • 使用 torch.autograd.detect_anomaly() 定位 NaN 源头
  • 对于自定义 CUDA kernel，确保输入输出精度匹配
  • Embedding 层通常保持 FP32（离散查表不受益于 Tensor Core）
  • 分布式训练中 AllReduce 在 FP16 下做，但 ring buffer 可用 FP32 避免累加误差
💡 知识要点
  • Softmax/LayerNorm/Loss 必须 FP32 — 这是 AMP 黑名单的设计原因
  • Gradient Accumulation 与 Loss Scaling 的交互：只在最终 step 做 unscale + update
  • NaN 排查第一步：检查 scale factor 是否在持续下降
  • 遇到不明 NaN：逐层关闭 autocast 二分定位

十、Q&A

Q1: 混合精度训练为什么叫"混合"？具体混合了什么？

混合的是 FP16（或 BF16）和 FP32 两种精度。前向传播和反向传播使用 FP16 以加速计算和减少显存，参数更新和优化器状态使用 FP32 以保证数值精度。"混合"意味着同一训练过程中不同阶段、不同操作使用不同精度。

Q2: Loss Scaling 为什么能解决梯度下溢问题？

FP16 的最小正次正规数约为 6×10⁻⁸，许多梯度值低于此阈值会被截为 0。Loss Scaling 在反向传播前将 loss 放大（如 ×1024），使所有梯度整体放大相同倍数，将原本会下溢的小梯度"抬升"到 FP16 可表示的范围内。更新参数时再除以相同的 scale factor 恢复真实值。本质上是在 FP16 的有限动态范围内"挪动窗口"覆盖梯度分布。

Q3: BF16 为什么不需要 Loss Scaling？

BF16 有 8 位指数（与 FP32 相同），动态范围达 ±3.4×10³⁸，梯度不论多小都不会下溢到 0（因为范围足够覆盖任何正常梯度值）。FP16 只有 5 位指数，范围仅 ±65504，这才是需要 Loss Scaling 的根本原因。BF16 牺牲的是尾数精度（7 位 vs FP16 的 10 位），但对深度学习训练来说精度影响可忽略。

Q4: 为什么优化器状态（Adam 的 m 和 v）必须用 FP32？

Adam 的动量 m 和 v 通过指数移动平均积累梯度信息，量级可能远小于参数本身。如果用 FP16 存储：(1) m/v 的更新量可能小于 FP16 精度而被吞掉；(2) v 作为分母，精度不够会导致学习率不稳定。此外参数更新 w = w - lr*m/√v 中的增量通常很小，在 FP16 下可能 w - delta == w（精度不够表示差异）。

Q5: autocast 是如何决定哪些操作用 FP16 哪些保持 FP32 的？

PyTorch 维护了三个列表：(1) 白名单 — 计算密集型操作（matmul, conv, linear）自动用 FP16，这些操作受益于 Tensor Core 加速；(2) 黑名单 — 精度敏感操作（softmax, layernorm, loss）保持 FP32；(3) 灰名单 — element-wise 操作跟随输入精度。autocast 上下文内 PyTorch dispatcher 会拦截算子调用，根据列表自动 cast 输入 tensor 的精度。

Q6: 动态 Loss Scaling 检测到 overflow 时为什么要跳过整个 step？

因为一旦梯度中出现 inf/NaN，任何基于该梯度的参数更新都会"污染"模型权重。即使只有一个参数的梯度溢出，经过 optimizer（如 Adam）的动量累积，NaN 会传播到 m/v 中，进而影响后续所有 step。所以必须整个 step 作废，将 scale factor 减半后重新尝试。这次的梯度信息虽然丢失了，但模型参数保持了正确状态。

Q7: FP8 训练为什么需要 per-tensor scaling 而不是像 BF16 那样全局处理？

FP8 的动态范围极小（E4M3 仅 ±448），不同 tensor（权重、激活、梯度）的数值分布差异巨大。如果用统一 scale，要么大值溢出要么小值下溢。Per-tensor scaling 为每个 tensor 维护独立的 scale factor（= FP8_MAX / tensor_amax），将每个 tensor 的值域都映射到 FP8 能精确表示的范围内。延迟缩放则用历史 amax 估算，避免当前 step 需要两次 pass。

Q8: 混合精度训练的内存到底省在哪里？

参数相关内存（master weights + optimizer states）仍是 FP32 共 12 bytes/param，加上 FP16 参数和梯度共 16 bytes/param。看似没省。真正的节省来自：(1) 激活值内存减半 — 这在大 batch 或长序列时是主要显存消耗（远大于参数本身）；(2) FP16 梯度通信量减半（分布式训练）；(3) 更快的计算意味着可以用 activation checkpointing 换回更多显存。

Q9: 使用混合精度训练时如何排查持续出现的 NaN？

排查步骤：(1) 检查 GradScaler 的 scale factor 是否持续下降（说明频繁 overflow）；(2) 用 torch.autograd.detect_anomaly() 定位产生 NaN 的第一个操作；(3) 逐层用 with autocast(enabled=False) 强制 FP32，二分法定位问题层；(4) 检查是否有自定义操作未正确处理精度转换；(5) 考虑降低学习率或加 gradient clipping；(6) 检查数据中是否有异常值（极大/极小）进入模型。

Q10: TF32 是什么？它和混合精度训练的关系是什么？

TF32 (TensorFloat-32) 是 NVIDIA Ampere 架构引入的 19 位格式（1 位符号 + 8 位指数 + 10 位尾数）。A100 默认将 FP32 的矩阵乘法用 TF32 Tensor Core 执行——输入截断为 TF32 精度做乘法，累加器仍用 FP32。这是一种"隐式混合精度"：用户代码仍写 FP32，但硬件自动以较低精度计算。与显式 AMP 的区别是：TF32 不需要任何代码修改，但加速幅度（~2×）小于 FP16/BF16 AMP（~3-4×）。可通过 torch.backends.cuda.matmul.allow_tf32 = False 关闭。
