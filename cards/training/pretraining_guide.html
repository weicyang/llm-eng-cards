W02 · 预训练流程与并行策略

Pre-training Pipeline — 从数据到基础模型的完整链路

一、预训练目标

"预测下一个 token"之所以够用，是因为这个目标把语法、事实、推理、风格全都折叠成了同一个可微的损失：想把下一个词猜准，模型就不得不顺带把它们都学会。目标简单，但它逼出来的东西不简单。

预训练是一条从原始网页到可用基座模型的长流水线， 每一段的产出都是下一段的输入，任何一段返工代价都极高： 原始语料（网页 / 代码 / 书籍 / 论文 / 多语） │ ▼ ① 清洗：格式、语种、启发式质量规则、毒性、PII 干净文本 │ ▼ ② 去重：精确去重 ─▶ MinHash + LSH 近似去重 低重复语料 │ ▼ ③ 配比：按能力预算给各来源定权重（决定能力画像） 混合语料 │ ▼ ④ Tokenize ＋ 打包成定长序列 ＋ 分片落盘 token 分片（此后训练只顺序读，不再做任何在线处理） │ ▼ ⑤ 训练：并行策略 ＋ 学习率调度 ＋ 梯度裁剪 ┌──────────────────────────────────────────────┐ │ 每 N 步：写 checkpoint（异步、分片） │ │ 每 M 步：跑轻量评测 ＋ 看 loss / 梯度范数 / MFU│ │ 一旦 loss spike：回滚最近 checkpoint，跳过该批 │ └──────────────────────┬───────────────────────┘ ▼ 基座模型（Base Model） │ ▼ 进入 SFT 与偏好对齐 这条线上有两个"不可逆"的点：③ 配比一旦定下，跑完才知道能力画像； ④ 分片一旦落盘，改配比就要重新 tokenize 全量数据。所以前三步要慢做。

1.1 Next Token Prediction (Causal LM)

自回归语言模型的核心训练目标：给定前缀序列 x1, x2, …, xt-1，预测下一个 token xt。目标函数为对数似然的最大化：

L = -∑ log P(x_t | x_1, x_2, ..., x_{t-1}; θ)

训练时通过 Causal Mask（下三角注意力掩码）确保每个位置只能关注其左侧的 token，从而实现自回归生成。

1.2 为什么简单的语言建模目标如此有效？

  • 隐式多任务学习 — 为了准确预测下一个 token，模型需要理解语法、语义、推理、世界知识等，相当于同时学习了无数个子任务。
  • 无限扩展的无监督数据 — 不需要人工标注，互联网文本天然构成训练样本，可无限扩展数据规模。
  • Scaling Law 验证 — Kaplan et al. (2020) 和 Hoffmann et al. (2022, Chinchilla) 证明了在足够数据和算力下，模型性能随参数量/数据量/计算量呈幂律增长。
  • 信息压缩视角 — 预测下一个 token 本质上是对数据进行压缩，模型被迫构建高效的世界模型来最小化预测误差。

💡 知识要点

  • 能完整写出 Causal LM 的损失函数
  • 理解 Causal Mask 的作用与实现方式（下三角矩阵）
  • 区分 CLM vs MLM (BERT) 的训练目标差异及其对生成能力的影响
  • 解释 Scaling Law 的核心发现：参数量、数据量、计算量三者之间的关系

二、数据准备

数据准备的产出不是"一堆文本"，而是"一串顺序已经定死的 token 流"。清洗决定信噪比，去重决定记忆与泛化的配比，配比决定能力画像——三件事都在训练开始前就已经把上限焊死了。

MinHash + LSH：把 O(n²) 的两两比较降到接近 O(n) ① Shingling：每篇文档 ──▶ n-gram 集合 doc A = { w1w2w3, w2w3w4, w3w4w5, ... } ② MinHash：用 k 个哈希函数各取集合最小值，得到定长签名 doc A ──▶ [ 17, 4, 902, 33, ... ] （k 常取 128 或 256） 核心性质：两个签名逐位相等的比例 ≈ 两集合的 Jaccard 相似度 于是"比较集合"变成"比较 k 个整数" ③ LSH 分桶：把 k 位签名切成 b 段、每段 r 位，逐段哈希进桶 [ 17 4 902 33 ][ 88 1 47 6 ][ ... ] band 1 band 2 │ │ ▼ ▼ 桶 #3af 桶 #c02 只要任意一段完全相同就落进同一个桶 ─▶ 成为候选对 调 b 与 r 就是在调"召回 vs 计算量"：段越多越敏感，候选对也越多 ④ 精算：只对同桶内的候选对算真实 Jaccard，超过阈值（常用 0.8）判为重复 ⑤ 连通分量：判重关系当作图的边，每个连通分量里只留一篇代表 两个必须抽样人工核对的边界： 阈值偏高 ─▶ 漏（改写、模板化内容留了下来） 阈值偏低 ─▶ 误杀（同主题但内容不同的文档被一起删掉）

2.2 数据清洗流程

典型清洗 Pipeline：

Raw Data → 语言识别 → URL/HTML 清洗 → 去重(Exact/Fuzzy)
         → 质量过滤(Perplexity/分类器) → 毒性过滤 → 个人信息移除 → 最终数据集
  • Exact Dedup：基于 hash 的精确去重（文档级 / 段落级）
  • Fuzzy Dedup (MinHash + LSH)：将文档转化为 n-gram 集合 → 计算 MinHash 签名 → LSH 分桶 → 相似度阈值过滤（通常 Jaccard > 0.8）
  • 质量评分：使用 fastText 分类器 或 KenLM Perplexity 打分，过滤低质量文本

2.3 MinHash 去重详解

# MinHash 去重核心流程
1. 对每个文档提取 n-gram (通常 5-gram)
2. 对每个 n-gram 集合计算 K 个 hash 函数的最小值 → 签名向量 (K维)
3. 将签名向量切分为 B 个 band，每个 band 含 R 行 (K = B × R)
4. 同一 band 内签名完全相同的文档放入同一桶
5. 对桶内文档对计算精确 Jaccard 相似度
6. 相似度 > 阈值的文档保留一个，其余删除

# 参数选择
- K=128, B=20, R=5 → 候选对阈值约 ≈ (1/20)^(1/5) ≈ 0.55
- 实际使用中常见 Jaccard 阈值 0.7~0.9

2.4 数据配比策略

  • 经验法则：Web 数据 ≈ 60-70%，Books ≈ 10-15%，Code ≈ 10-15%，Wikipedia ≈ 5%，学术 ≈ 5%
  • Upsampling：对高质量小规模数据源（如 Wikipedia）进行重复采样，提升其在整体数据中的占比
  • DoReMi（Xie et al., 2023）：使用小规模代理模型自动学习最优数据配比
  • 数据配比对最终模型能力影响显著：Code 数据占比提升可增强推理能力（GPT-4 Technical Report 间接证实）

三、课程学习 (Curriculum Learning)

课程学习赌的是"顺序本身有信息"：同一批数据换个喂法，优化轨迹就不同。收益真实但不稳定，所以它更常被用在训练末段的退火——最后那几个百分点的 token 里塞高质量数据，性价比明显高于全程排课表。

3.1 数据排列顺序的影响

研究表明，训练数据的呈现顺序会显著影响模型收敛速度和最终性能。随机 shuffle 是 baseline，但有策略地组织数据顺序可以带来收益。

3.2 由易到难 (Easy-to-Hard)

  • 核心思想：先用"简单"样本（短文本、低困惑度、结构清晰）训练，逐步引入"困难"样本（长文本、高困惑度、噪声多）
  • 难度衡量：文本长度、语言模型困惑度、n-gram 丰富度、领域复杂度
  • 效果：加速早期收敛，某些场景下可提升最终性能 1-3%

3.3 数据混合调度 (Data Mixing Schedule)

  • 静态混合：整个训练过程中各数据源比例固定
  • 动态混合：随训练进度调整数据源配比，例如：
    • 早期多用 Web 数据 → 后期增加 Code/Math 占比（增强推理）
    • 早期多语言混合 → 后期增加目标语言占比
  • GLaM / PaLM 实践：根据各数据源上的 validation loss 动态调整权重

💡 知识要点

  • Curriculum Learning 对预训练的收益是否一致？实际中更多使用随机 shuffle
  • 动态数据混合与静态混合的权衡：实现复杂度 vs 性能提升
  • 如何定义样本"难度"？不同定义对训练行为的影响

四、分布式并行策略

4.1 Data Parallelism (DP)

  • 每个 GPU 持有完整模型副本，对不同 mini-batch 并行前向/反向传播
  • 反向传播后通过 AllReduce 同步梯度
  • 优点：实现简单，线性加速
  • 瓶颈：每个 GPU 需容纳完整模型 + 优化器状态 → 大模型放不下

4.2 Tensor Parallelism (TP)

  • 将单个算子（如矩阵乘法）沿行或列维度切分到多个 GPU
  • 例如：将 Y = XA 中的 A 沿列切分为 [A₁, A₂]，两个 GPU 分别计算 XA₁ 和 XA₂
  • 需要 AllReduce / AllGather 在每层之间同步中间结果
  • 要求 高带宽互连（NVLink），通常在同节点内使用（TP=4 或 TP=8）

4.3 Pipeline Parallelism (PP)

  • 将模型按层切分，不同层组放在不同 GPU 上
  • 使用 micro-batch 流水线调度减少 GPU 空闲（bubble）
  • 调度策略：GPipe（同步）、1F1B（one-forward-one-backward，减少峰值显存）
  • Bubble Ratio ≈ (pp_degree - 1) / num_micro_batches

4.4 ZeRO (Zero Redundancy Optimizer)

阶段分片内容通信量显存节省
ZeRO-1优化器状态 (Optimizer States)与 DP 相同约 4×
ZeRO-2优化器状态 + 梯度 (Gradients)与 DP 相同约 8×
ZeRO-3优化器状态 + 梯度 + 参数 (Parameters)1.5× DP线性于 GPU 数

4.5 3D 并行

实际大模型训练通常组合使用 DP + TP + PP（即 3D 并行）：

总 GPU 数 = DP_degree × TP_degree × PP_degree

典型配置 (LLaMA-65B, 2048 GPUs):
- TP = 8   (节点内, 8卡 NVLink 互连)
- PP = 4   (跨 4 个节点, 流水线)
- DP = 64  (2048 / 8 / 4 = 64 路数据并行)

4.6 各策略适用场景对比

策略切分维度通信模式适用场景瓶颈
DP数据 (Batch)AllReduce 梯度模型放得下单卡显存
TP模型 (算子内)AllReduce / AllGather 每层节点内高带宽通信延迟
PP模型 (层间)点对点发送激活值跨节点、层数多Bubble 时间
ZeRO状态 / 梯度 / 参数AllGather + ReduceScatter显存不足时替代 TP通信开销
3D 并行数据+算子+层混合千卡大模型训练调参复杂

五、训练稳定性

Loss Spike 多数不是"模型坏了"，而是某个批次的梯度尖峰恰好穿过了当前的学习率窗口。三道防线各管一段：梯度裁剪管幅度，warmup 管早期最脆弱的那几千步，回滚 checkpoint 管已经发生的事故。

示例场景：checkpoint 策略把故障损失砍掉一个数量级。背景——某 512 卡训练任务，集群平均每 8 小时左右出一次硬件或通信故障，需要从最近的 checkpoint 重启。问题——初始策略是每 6 小时同步写一次全量 checkpoint。一次故障平均要重跑约 3 小时，折算成 3 × 512 ≈ 1,536 卡时的直接损失；更糟的是同步写盘期间全部 GPU 空等约 8 分钟，一天光是存盘就白扔近 30 分钟算力。方案——改成每 30 分钟一次、分布式分片写、且与训练异步重叠（GPU 只负责把张量拷到主机内存，落盘交给后台线程），同时只保留最近 3 份加每 6 小时一份长期存档以控制存储。效果——单次故障的平均重跑损失降到约 15 分钟 × 512 ≈ 128 卡时，是原来的十分之一以下；存盘造成的 GPU 空等从 8 分钟压到 20 秒量级。这也解释了为什么大规模训练里 checkpoint 不算备份，而算训练本身的一部分。

5.1 Loss Spike 处理

  • 现象：训练过程中 loss 突然飙升，然后缓慢恢复或不恢复
  • 常见原因：数据质量问题（异常样本）、学习率过大、数值溢出（fp16 下溢/上溢）、梯度爆炸
  • 处理方法：
    • 从最近的健康 checkpoint 回退，跳过问题数据
    • 降低学习率重新训练
    • 增加梯度裁剪强度
    • PaLM 论文做法：记录 spike 对应的数据 batch，从前一个 checkpoint 跳过该 batch 继续训练

5.2 梯度裁剪 (Gradient Clipping)

# 全局梯度范数裁剪
total_norm = sqrt(sum(p.grad.norm(2)^2 for p in parameters))
if total_norm > max_norm:
    scale = max_norm / total_norm
    for p in parameters:
        p.grad *= scale

# 常见配置: max_norm = 1.0

5.3 学习率调度：Warmup + Cosine Decay

# 典型 LR Schedule
Phase 1 — Linear Warmup:  lr = lr_max × (step / warmup_steps)
Phase 2 — Cosine Decay:   lr = lr_min + 0.5×(lr_max - lr_min)×(1 + cos(π × progress))

# 常见配置
lr_max = 3e-4 (小模型) ~ 1.5e-4 (大模型)
warmup_steps = 2000
lr_min = lr_max × 0.1

Warmup 的作用：训练初期参数随机，梯度方差大，小学习率可以稳定早期训练方向。

5.4 权重初始化

  • GPT 系列：残差连接前的线性层权重缩放 1/√(2N)，N 为层数
  • μP (Maximal Update Parameterization)：通过调整初始化和学习率，使超参数可从小模型直接迁移到大模型
  • 实践建议：Embedding 层使用 N(0, 0.02)，其余层使用 Xavier/He 初始化

六、Checkpoint 与恢复

大规模训练里 checkpoint 不是备份，是训练的一部分：它直接决定故障之后要重跑多少小时。存得太密浪费带宽和 GPU 等待，存得太稀就是拿算力赌运气——间隔应该由集群的平均故障间隔倒推，而不是凭习惯设一个整数。

  • checkpoint 间隔按集群平均故障间隔倒推，而不是随手填 6 小时
  • 异步 + 分片写，让 GPU 只负责拷到主机内存，落盘交后台
  • 断点续训必须一起恢复优化器状态、学习率调度进度和数据读取位置
  • 把 grad_norm、loss、MFU、跳步率做成同一张看板，异常要能对齐时间轴
  • 每隔固定步数跑一轮轻量评测，别等训练结束才发现能力凹陷
  • 训练前用小模型把整条管线（含恢复流程）端到端跑通一遍
  • 保留最近若干份滚动 checkpoint 加稀疏的长期存档，兼顾恢复与存储
  • 不要只存权重不存优化器状态，Adam 的动量丢了等于从零重启
  • 不要在恢复时重置数据读取位置，会造成部分数据重复、部分从未被看到
  • 不要遇到 loss spike 就硬扛，回滚几十分钟通常比赌自愈划算
  • 不要在没有 warmup 的情况下直接用峰值学习率起步
  • 不要只看 loss 曲线判断健康，梯度范数往往比 loss 更早示警
  • 不要中途改数据配比却不记录切换步数，事后无法归因
  • 不要把评测集和训练语料放在同一套清洗流程里，污染一次就再也说不清

6.1 Checkpoint 策略

  • 保存内容：模型参数、优化器状态（momentum, variance）、学习率调度器状态、RNG 状态、当前 step/epoch、数据加载器状态
  • 保存频率：通常每 500-2000 步保存一次，平衡存储成本与恢复粒度
  • 异步保存：将 checkpoint 写入后台线程，避免阻塞训练
  • 滚动覆盖：只保留最近 N 个 checkpoint + 关键里程碑 checkpoint

6.2 断点续训 (Resume from Checkpoint)

  • 恢复模型参数 + 优化器状态 + LR scheduler 状态
  • 数据加载器恢复：需要记录已消费的数据样本索引，确保不重复/不遗漏
  • RNG 状态恢复：确保 Dropout、数据增强等随机操作的可复现性
  • 注意：修改并行策略（如 TP/PP degree 变化）后需要进行 checkpoint resharding

6.3 Checkpoint 合并

  • 分布式 Checkpoint：TP/PP 训练时每个 rank 保存自己的 shard，合并为完整 checkpoint 用于推理或不同并行度的训练
  • 合并操作：将切分的参数张量沿正确维度拼接（TP 列切分 → concat along dim=1）
  • 工具：Megatron-LM 提供 tools/checkpoint_converter.py，DeepSpeed 提供 zero_to_fp32.py

七、训练监控

MFU 是唯一能把"钱花得值不值"讲清楚的指标：实际吞吐除以硬件理论峰值，直接回答"有多少算力真的进了模型"。loss 告诉你方向对不对，MFU 告诉你效率高不高，两者缺一不可。

示例场景：MFU 从 30% 提到 45%，训练周期缩掉三分之一。背景——某团队在 128 卡上训练一个中等规模模型，loss 曲线健康，但按 6ND 公式反推发现墙钟时间比理论值长了一倍多，实测 MFU 只有约 30%。问题——分三块定位：一是 micro-batch 设得过小、GPU 大量时间在等数据搬运而不是算矩阵乘；二是注意力用的是朴素实现，长序列下显存带宽成为瓶颈；三是为了省显存把 activation checkpointing 开在了所有层上，白白多算了一整遍前向。方案——换成融合的 FlashAttention 实现腾出显存，把省下的显存用来增大 micro-batch，再把 activation checkpointing 从"全开"改成只对显存占用最大的若干层选择性开启，并让数据加载与计算重叠。效果——MFU 从约 30% 升到约 45%，同样的 token 预算下墙钟时间缩短约三分之一，硬件成本等比例下降。这里值得记住的是：MFU 低的原因几乎从不是"卡不行"，而是显存、带宽、重计算三者之间的配比没调好。

九、预训练成本估算

6ND 让预训练成本从玄学变成算术：总计算量 ≈ 6 × 参数量 × token 数，除以（卡数 × 单卡算力 × MFU）就是墙钟时间。公式里唯一不由硬件决定的量是 MFU，所以工程优化的靶心也就只有它。

从"我要训一个多大的模型"到"要花多少钱"，只有四步算术： ① 总计算量 C ≈ 6 · N · D N = 参数量，D = 训练 token 数 6 的来历：前向 2 次乘加 ＋ 反向 4 次，合计每参数每 token 6 FLOPs ② 有效算力 P_eff = G · P_peak · MFU G = GPU 数，P_peak = 单卡 BF16 峰值算力，MFU = 实际利用率 MFU 是唯一能靠工程改动的因子，典型区间 0.3 ~ 0.5 ③ 墙钟时间 T = C / P_eff = 6 · N · D / (G · P_peak · MFU) ④ 费用 Cost = G · T · 单卡时价 ───────────────────────────────────────────────────────── 四个杠杆，两个方向： N 参数量 ─┐ ├─▶ 决定 C（需求侧，由 Chinchilla 比例把两者绑在一起） D token 数┘ G 卡数 ─┐ ├─▶ 决定 P_eff（供给侧） MFU ─┘ 加卡花钱，提 MFU 花人力 注意 G 与 T 在费用里相乘：单纯加卡缩短的是墙钟时间，总费用几乎不变； 真正降总价的只有提高 MFU，或者减少 N · D 这个乘积。

9.1 FLOPs 计算公式 (6ND)

C ≈ 6 × N × D

其中:
  C = 总计算量 (FLOPs)
  N = 模型参数量
  D = 训练 token 数

# 系数 6 的来源:
# 前向传播 ≈ 2ND (每个参数参与一次乘法和一次加法)
# 反向传播 ≈ 4ND (梯度计算约为前向的 2 倍)
# 合计 ≈ 6ND

9.2 GPU 小时估算

GPU 小时 = C / (GPU_FLOPs × MFU × 3600)

# 示例：LLaMA-2 70B
N = 70 × 10^9
D = 2 × 10^12 tokens
C = 6 × 70e9 × 2e12 = 8.4 × 10^23 FLOPs

# 使用 A100 (312 TFLOPS), MFU = 45%
GPU_实际算力 = 312e12 × 0.45 = 140.4 TFLOPS
GPU_秒 = 8.4e23 / 140.4e12 ≈ 5.98 × 10^9 秒
GPU_小时 ≈ 1,661,538 GPU-hours

# 使用 2048 块 A100
墙钟时间 ≈ 1,661,538 / 2048 ≈ 811 小时 ≈ 34 天

Q&A

Q1：为什么大模型预训练几乎都采用 Next Token Prediction 而不是 MLM？

核心原因：

  • 生成能力：CLM 天然支持自回归生成，训练目标与推理时的生成方式一致；MLM 需要额外适配才能用于文本生成。
  • Scaling 效果更好：实验表明在相同计算预算下，CLM 在大规模时表现更优。GPT-3 证明了 CLM 的 few-shot 能力随规模增长而涌现。
  • 训练效率：CLM 每个 token 都参与损失计算（序列中每个位置都要预测），而 MLM 只对被 mask 的 15% token 计算损失。
  • 简单统一：一个目标函数覆盖所有能力，无需设计复杂的预训练任务组合。
Q2：MinHash 去重中，Band 数 B 和每个 Band 的行数 R 如何影响去重效果？

设签名长度 K = B × R，两个文档的真实 Jaccard 相似度为 s：

  • 成为候选对的概率 ≈ 1 - (1 - s^R)^B
  • 增大 R：提高阈值 → 更少误检（false positive），但可能漏检（false negative）
  • 增大 B：降低阈值 → 更少漏检，但更多误检
  • 实际选择需平衡：对于去重任务，通常倾向于低 false negative（不遗漏近似重复），因此适当增大 B

例：K=128, B=32, R=4 → 阈值约 0.5；K=128, B=16, R=8 → 阈值约 0.7

Q3：Tensor Parallelism 和 Pipeline Parallelism 分别适用于什么场景？能否混用？
  • TP 适用场景：节点内高带宽互连（NVLink），单层参数量大需要切分。TP 通信频繁（每层前向/反向各需一次 AllReduce），要求延迟极低。
  • PP 适用场景：跨节点互连（InfiniBand），层数多。PP 只需在流水线边界传递激活值，通信量相对小但有 bubble 开销。
  • 混用（3D 并行）：这是大模型训练的标准做法。节点内使用 TP（利用 NVLink），跨节点使用 PP + DP。例如 LLaMA-65B 使用 TP=8（节点内）× PP=4 × DP=64。
  • 关键设计原则：通信密集的并行维度放在高带宽互连上。
Q4：ZeRO-3 和 Tensor Parallelism 都能解决模型放不下单卡的问题，如何选择？
  • ZeRO-3：将参数分片存储在不同 GPU，使用时通过 AllGather 收集。优点是实现简单（DeepSpeed 一行配置），不需要修改模型代码。缺点是通信量 = 1.5× DP，且每次前向/反向都需要 AllGather 全量参数。
  • TP：将计算本身切分，每个 GPU 只计算部分结果。通信量相对固定（每层两次 AllReduce），计算和通信可以 overlap。缺点是需要适配模型代码。
  • 选择建议：节点内优先 TP（通信效率高），跨节点可用 ZeRO-3（不受带宽限制太多）。实际中两者可结合使用。
Q5：训练中出现 Loss Spike 怎么办？具体排查步骤是什么？

排查步骤：

  1. 检查数据：定位 spike 对应的 batch，检查是否有异常样本（超长文本、乱码、重复 token）
  2. 检查梯度范数：spike 前是否出现梯度范数异常增大
  3. 检查数值：是否有 NaN/Inf 出现（fp16 溢出）
  4. 检查学习率：LR schedule 是否异常

处理方法：

  1. 回退到 spike 前最近的 checkpoint
  2. 跳过问题数据 batch（PaLM 论文做法）
  3. 如果频繁 spike：降低学习率、增强梯度裁剪、检查数据质量
  4. 考虑切换到 BF16（动态范围更大，不易溢出）
Q6：为什么需要 Learning Rate Warmup？去掉会怎样？
  • 原因：训练初期参数随机初始化，梯度方差很大且方向不稳定。如果直接使用大学习率，可能导致参数更新过大，模型陷入不好的 loss landscape 区域，甚至发散。
  • Warmup 作用：小学习率让模型先"探索"loss landscape 的大致方向，逐步增大学习率以加速训练。类比开车：先低速观察路况再加速。
  • 去掉 Warmup 的后果：
    • 小模型可能影响不大（loss landscape 较简单）
    • 大模型大学习率下容易训练不稳定、早期 loss spike
    • Adam 优化器的二阶矩估计在初期不准确，需要时间积累，Warmup 正好提供了这个缓冲期
Q7：如何计算预训练所需的总 FLOPs？系数 6 怎么来的？

公式：C ≈ 6 × N × D（N = 参数量，D = 训练 token 数）

系数 6 的推导：

  • 前向传播 ≈ 2N FLOPs/token：Transformer 的计算主体是矩阵乘法，对于形状为 [m, k] × [k, n] 的矩阵乘，计算量为 2mkn。模型的总参数量 N ≈ 12 × L × d²（L 层，维度 d），前向一个 token 约需 2N 次浮点运算。
  • 反向传播 ≈ 4N FLOPs/token：反向传播需要计算损失对参数的梯度和对输入的梯度，各自需要一次矩阵乘，因此约为前向的 2 倍。
  • 合计：(2 + 4) × N × D = 6ND

注意：此公式是近似值，未包含 Attention 计算、LayerNorm、激活函数等开销，实际 FLOPs 可能偏高 5-10%。

Q8：Chinchilla Scaling Law 的核心结论是什么？对预训练实践有什么指导？

核心结论（Hoffmann et al., 2022）：

  • 在固定计算预算下，模型参数量 N 和训练数据量 D 应大致等比例扩展：D ≈ 20 × N
  • 这意味着之前许多模型（如 GPT-3 175B 仅用 300B tokens）是"undertrained"的

实践指导：

  • 70B 模型应使用至少 1.4T tokens 训练
  • LLaMA 遵循此原则：7B 用 1T tokens，65B 用 1.4T tokens
  • LLaMA-2 更进一步：所有尺寸都用 2T tokens，超过 Chinchilla optimal（但推理时更高效）
  • 近期趋势：过度训练（over-training）小模型可能比 Chinchilla optimal 大模型在推理效率上更优
Q9：MFU（Model FLOPs Utilization）是什么？影响 MFU 的因素有哪些？

定义：MFU = 模型实际计算的 FLOPs / (GPU 理论峰值 FLOPs × 训练时间)

影响因素：

  • 通信开销：TP/DP/PP 的通信占比越大，MFU 越低。通信与计算的 overlap 能力直接影响 MFU。
  • 显存 IO：Attention 计算中的显存读写（FlashAttention 可显著减少）
  • CUDA Kernel 效率：fused kernels、TensorCore 利用率
  • Pipeline Bubble：PP 的空闲时间
  • 数据加载：数据预处理和 IO 如果成为瓶颈会降低 MFU
  • Batch Size：过小的 batch size 导致 GPU 利用率低

业界参考：PaLM 在 6144 TPU v4 上达到 46.2% MFU，Megatron-LM 在 A100 上可达 50%+。

Q10：从零开始预训练一个 7B 模型，你会如何规划整个流程？

完整流程规划：

  1. 数据准备（2-4 周）
    • 收集数据：Common Crawl + Books + Code + Wikipedia + 学术论文
    • 清洗 Pipeline：语言识别 → 去重（MinHash）→ 质量过滤 → 毒性过滤
    • Tokenizer 训练：BPE/SentencePiece，词表 32K-64K
    • 目标：至少 1-2T tokens 的高质量数据
  2. 超参数设计
    • 架构：LLaMA-style（RMSNorm, SwiGLU, RoPE, GQA）
    • 学习率：3e-4, Warmup 2000 steps, Cosine Decay
    • Batch Size：逐步递增，最终 ~4M tokens/batch
    • 使用 μP 从小模型迁移超参数
  3. 基础设施与并行策略
    • 7B 模型可用 64-128 块 A100，约 20-30 天
    • 并行策略：TP=1-2 + DP（7B 单卡放得下），或 FSDP/ZeRO-2
    • 框架：Megatron-LM 或 PyTorch FSDP
  4. 训练与监控
    • Checkpoint 每 1000 步保存
    • 监控 Loss/Grad Norm/MFU
    • Loss spike 应急预案
  5. 评估
    • 训练中：validation perplexity，few-shot benchmark（MMLU, HellaSwag）
    • 训练后：全面 benchmark 评估

预估成本：6 × 7e9 × 1e12 = 4.2e22 FLOPs → ~83K A100-hours → ~$125K-170K
