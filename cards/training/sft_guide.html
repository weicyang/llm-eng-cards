W03 · SFT 监督微调

Supervised Fine-Tuning — 让预训练模型学会"听话"

一、SFT 在 LLM 训练流程中的位置

监督微调不注入新知识，它改的是模型的应答方式。预训练决定它知道什么，SFT 决定它愿意用什么格式把知道的东西讲出来——把这两件事分清，超参数和数据量的取值就都有了依据。

三个阶段，各自改变模型的哪一层属性： ┌─────────────────────────────────────────────────────────────┐ │ ① 预训练 Pre-training │ │ 数据：数万亿 token 无标注文本 目标：next-token 预测 │ │ 改变的是：世界知识、语言能力 成本：数百万美元级 │ │ 产出：Base Model —— 会续写，但不会"应答" │ └───────────────────────────┬─────────────────────────────────┘ ▼ ┌─────────────────────────────────────────────────────────────┐ │ ② 监督微调 SFT │ │ 数据：数千 ~ 数十万条 指令-回复对 目标：模仿学习 │ │ 改变的是：应答格式、指令遵循、风格 成本：数百 ~ 数千美元 │ │ 产出：Instruct Model —— 会应答，但对"好坏"没有偏好排序 │ └───────────────────────────┬─────────────────────────────────┘ ▼ ┌─────────────────────────────────────────────────────────────┐ │ ③ 偏好对齐 RLHF / DPO │ │ 数据：偏好对（同一问题的优劣回复） 目标：偏好优化 │ │ 改变的是：在多个"都能答"之间挑哪个 成本：中等 │ │ 产出：Aligned Model —— 会答，且答得符合人类偏好 │ └─────────────────────────────────────────────────────────────┘ 一条贯穿三段的规律：越往后，数据量越小、单条数据越贵、 对数据质量越敏感 —— 因为改的东西从"知识"变成了"行为"。

三阶段概览

阶段目标数据成本
Pre-train学习语言知识、世界知识数万亿 Token 无标签文本极高（数百~千万美元）
SFT学会对话格式，遵循指令数千~数十万条指令-回答对中等（数小时~数天 GPU）
RLHF对齐人类价值观、提高回答质量偏好排序数据较高（需要 Reward Model）

SFT 的核心作用

  • 格式对齐：预训练模型只会"续写"，SFT 让模型学会"问→答"的交互格式
  • 能力激发：预训练已经学会的能力（推理、翻译、编程），通过 SFT 以指令方式"解锁"
  • 行为控制：引导模型以特定风格（简洁/详细/安全）进行回答
  • 不注入新知识：SFT 主要调整模型的输出行为，而非灌入大量新知识
  • SFT 不改变模型的知识储备，而是改变模型的表达方式和行为模式
  • SFT 的关键洞察：预训练模型已具备强大能力，SFT 只需很少的数据就能激活这些能力
  • 高频问题：SFT 和 Pre-train 的核心区别？→ Pre-train 学知识，SFT 学格式与行为

二、指令数据构造

指令数据要的是"任务类型的覆盖面"，不是条数。同一类任务的第 500 条样本几乎不携带新信息，而完全缺失的那类任务连一条都没有——所以扩数据之前，先画一张任务类型直方图。

指令格式

标准的 SFT 数据通常包含三个字段：

{
  "instruction": "将以下句子翻译成英文",
  "input": "今天天气真好",
  "output": "The weather is really nice today."
}

其中 input 可以为空（零输入任务，如"讲一个笑话"）。

GPT-4 蒸馏用 GPT-4 批量生成高质量回答作为训练标签Alpaca、Vicuna

  • ShareGPT — 真实用户与 ChatGPT 的多轮对话，质量高但有版权争议
  • OpenAssistant — 社区众包的多轮对话，含多语言
  • FLAN Collection — Google 整合 1800+ NLP 任务，规模最大

  • 高频问题：GPT-4 蒸馏数据的法律/伦理问题？→ OpenAI ToS 限制商用

三、全参数微调 vs PEFT

全参数微调和 参数高效微调 的取舍多数时候不在效果，而在"要不要为每个下游任务养一份完整权重"。LoRA 真正卖的是可插拔与存储成本：一个基座配几十个几十兆的适配器，和几十份几十 GB 的权重，是两种完全不同的运维形态。

同一个线性层，两种微调方式的参数流向： ① 全参数微调 —— 直接改 W x ──▶ ┌───────────────┐ ──▶ h │ W (d × k) │ │ ✎ 可训练 │ 要训练、要存优化器状态的参数量 = d·k └───────────────┘ 每个任务产出一份完整权重（数十 GB） ② LoRA —— 冻结 W，另开一条低秩旁路 ┌───────────────┐ x ──┬──────▶│ W (d × k) │──────┬──▶ h │ │ ❄ 冻结 │ │ │ └───────────────┘ │ │ │ 相加 │ ┌─────────┐ ┌─────────┐ │ └──▶│ A (d×r) │──▶│ B (r×k) │──┘ │ ✎ 可训练 │ │ ✎ 可训练 │ └─────────┘ └─────────┘ r ≪ min(d, k)，常取 8 / 16 / 32 h = W·x + (B·A)·x ← 训练时只有 A、B 拿到梯度 可训练参数量 = r·(d + k)，相比 d·k 通常小两到三个数量级 A 初始化为随机小值、B 初始化为零 ⇒ 训练起点与原模型完全一致 ───────────────────────────────────────────────────────────── 运维形态的差别（这才是选型的真正理由）： 全参数：基座 ─▶ 任务1 权重(全量) 任务2 权重(全量) 任务3 权重(全量) 每份都要单独部署、单独占显存 LoRA： 基座（一份，常驻显存） ├── 适配器1（几十 MB） ┐ ├── 适配器2（几十 MB） ├─ 可热插拔，可多适配器共享同一基座 └── 适配器3（几十 MB） ┘ 也可以在上线前把 B·A 合并回 W，做到推理零额外开销

全参数微调 (Full Fine-Tuning)

  • 更新模型的所有参数，表达能力最强
  • 需要完整的优化器状态（Adam 需要 2× 参数量的额外显存）
  • 典型显存需求：7B 模型 ≈ 60–80 GB（fp16 + Adam）
  • 适合：数据量充足、计算资源充裕、追求极致性能的场景

参数高效微调 (PEFT)

方法可训练参数核心思路
LoRA~0.1%–1%在权重矩阵旁加低秩分解 ΔW = BA
QLoRA~0.1%–1%4-bit 量化 + LoRA，显著降低显存
Prefix Tuning~0.1%在注意力层前加可训练前缀向量
Adapter~1%–5%在 Transformer 层中插入小型适配模块
IA³<0.01%学习激活值的缩放因子

如何选择？

场景推荐方案理由
显存 ≤ 24 GB (单卡)QLoRA4-bit 量化大幅降低显存需求
多任务部署LoRA不同任务共享基座模型，只需切换 LoRA 权重
追求最佳性能全参数微调无信息瓶颈，表达能力最强
快速实验迭代LoRA / QLoRA训练速度快，占用少
70B+ 超大模型QLoRA + DeepSpeed全参数微调成本过高
  • LoRA 的数学本质：W' = W + BA，其中 B ∈ Rd×r，A ∈ Rr×k，r 为秩（通常 8–64）
  • QLoRA 三大创新：4-bit NormalFloat、Double Quantization、Paged Optimizers
  • 全参数微调 vs LoRA 性能差距通常在 1–3% 以内，但资源消耗差 10–50 倍
  • 高频问题：LoRA 的 rank 怎么选？→ 简单任务 r=8，复杂任务 r=32–64

四、Chat 模板

Chat 模板是模型与推理框架之间的一份协议。训练时用哪套特殊 token 划分角色边界，推理时就必须一字不差地拼出同一套；差一个空格，模型就可能不知道该在哪里停下来。

示例场景：离线评测全绿，一上线就停不下来。背景——某团队微调了一个对话模型，训练与离线评测都用自己写的脚本拼 prompt，指标正常，于是直接接入了推理服务。问题——上线后约三成的请求出现"模型答完继续自问自答"，把用户的下一轮问题自己编出来接着答。排查发现训练时 assistant 段以 <|im_end|> 结尾，而推理框架读的是权重目录里那份没更新过的 chat_template，拼出来的结束标记是 </s>。模型从未在这个 token 上学过"该停了"，于是就继续续写。离线评测因为用的是训练脚本同一套拼接逻辑，完全掩盖了这个问题。方案——把 tokenizer_config.json 里的 chat_template 与训练脚本统一到同一份来源，并补一条端到端 smoke test：用真实推理框架（而不是训练代码）拼 prompt，断言输出里不出现新的角色标记。效果——续写率降到 0，并且此后任何模板改动都会在 CI 上先炸而不是在线上炸。这类事故的共同特征是：训练侧和推理侧各有一份"真相"，而没人比对过。

为什么需要 Chat 模板？

LLM 本质上处理的是一维 Token 序列，Chat 模板将多角色对话结构化地编码为 Token 序列，让模型能区分"谁在说话"。模板不匹配会导致模型行为异常。

主流模板对比

ChatML (OpenAI / Qwen)

<|im_start|>system
你是一个有用的助手。<|im_end|>
<|im_start|>user
你好<|im_end|>
<|im_start|>assistant
你好！有什么可以帮助你的？<|im_end|>

LLaMA 2 Chat

[INST] <<SYS>>
你是一个有用的助手。
<</SYS>>

你好 [/INST] 你好！有什么可以帮助你的？ </s>

Vicuna / ShareGPT

A chat between a curious user and an AI assistant.

USER: 你好
ASSISTANT: 你好！有什么可以帮助你的？</s>

特殊 Token 的重要性

  • <|im_start|> / <|im_end|>：标记消息边界，模型依赖这些 Token 判断何时停止生成
  • <s> / </s>：BOS / EOS Token，控制序列起止
  • 这些 Token 在 Tokenizer 中通常是 added_tokens，不可拆分

模板不匹配的后果

  • 🔴 模型不知道何时停止生成（缺少 EOS Token → 无限输出）
  • 🔴 角色混淆（模型同时扮演 user 和 assistant）
  • 🔴 系统提示失效（system 消息位置错误 → 模型忽略安全策略）
  • 🔴 推理时格式与训练时不一致 → 性能显著下降
  • Chat 模板本质是一种序列化协议，将结构化对话转为扁平 Token 流
  • Hugging Face tokenizer.apply_chat_template() 可自动应用正确模板
  • 高频问题：推理时模板和训练时不一致会怎样？→ 输出质量下降、停止异常、角色混乱
  • 不同模型家族的模板不通用，必须与模型训练时的模板保持一致

五、多轮对话训练

多轮训练要回答一个具体问题：一段 n 轮对话是拆成 n 条样本，还是算成一条？拼成一条省下的算力相当可观，前提是 loss 必须精确落在每一轮的 assistant 段上——否则模型会顺带学会替用户说话。

多轮拼接方式

多轮对话在训练时需要拼接为一条完整序列：

[BOS] system_msg [SEP] user_1 [SEP] assistant_1 [SEP] user_2 [SEP] assistant_2 [EOS]

关键决策：如何处理多轮中每一轮的 loss 计算？

Loss Masking（在 assistant 回复上计算 loss）

标准做法是只在 assistant 的 Token 上计算 loss，将 system、user 部分的 loss 掩码为 0：

Tokens:   [SYS] 你是助手 [USER] 你好 [ASST] 你好！请问有什么...
Labels:    -100  -100     -100  -100  你好！ 请问  有什么...

-100 是 PyTorch CrossEntropyLoss 的默认 ignore_index，这些位置不参与梯度计算。

Packing（序列打包）

问题：短对话浪费 GPU 算力（大量 padding Token）。

Packing 解决方案：将多个短样本拼接到一个 max_length 的序列中：

| Sample A tokens... | Sample B tokens... | Sample C tokens... | PAD |
  ← attention_mask 和 position_id 需要正确分隔 →
  • 需要使用 block-diagonal attention mask 防止不同样本间的交叉注意力
  • 或使用 Flash Attention 2 的 cu_seqlens 参数高效实现
  • Packing 可提升训练吞吐量 2–5 倍
  • 多轮对话训练的核心：每一轮 assistant 回复都应计算 loss，而非只计算最后一轮
  • Packing 的注意力隔离非常重要，否则不同样本的信息会"泄露"
  • 高频问题：Packing 时不做注意力隔离会怎样？→ 不同样本互相影响，训练不稳定
  • position_ids 在 Packing 时也需要重置，否则位置编码会出错

六、Loss Masking 策略

不在 prompt 上算 loss，是因为你不想让模型学会"编题目"。它该学的是"给定题目怎么答"这个条件分布，而不是题目本身长什么样——Loss Masking 就是把这个区别写进梯度里。

为什么不在 instruction/input 上算 loss？

  • 训练目标不匹配：我们希望模型学会"根据指令生成回答"，而非"复读指令"
  • 噪声引入：指令部分的 Token 分布与回答不同，同时优化会互相干扰
  • 浪费算力：指令部分的梯度不贡献于生成能力的提升

三种策略对比

策略Loss 计算范围效果
Completion-only只在 assistant 回复上✅ 推荐，效果最好，训练最高效
Full Sequence整条序列（含 instruction）⚠️ 小数据集时可能有帮助（正则化效果）
Weightedinstruction 低权重 + completion 高权重🔶 折中方案，实际很少使用

实现方式

# HuggingFace TRL 的 DataCollatorForCompletionOnlyLM
from trl import DataCollatorForCompletionOnlyLM

response_template = "\n### Response:"
collator = DataCollatorForCompletionOnlyLM(
    response_template=response_template,
    tokenizer=tokenizer
)
  • Completion-only Loss 是当前 SFT 的标准做法
  • 少数研究表明：在数据极少（<1000 条）时，Full Sequence Loss 可能有轻微正则化效果
  • 高频问题：如果在整条序列上算 loss，模型会学到什么不好的行为？→ 可能学会"复读"指令
  • Loss Masking 的实现依赖正确的模板解析——模板错误 → Masking 位置错误 → 训练失败

七、超参数选择

SFT 只跑 1~3 个 epoch，因为它学的是格式而不是知识，格式几遍就学会了。再往后跑，模型开始逐字背样本，表现为训练 loss 继续降、输出多样性同步塌缩——这时候 loss 已经不再是好消息。

示例场景：多跑 epoch 换来的是"更听话但更呆"。背景——某团队用 8,000 条领域指令数据微调一个 3B 模型，为了"训得更充分"把 epoch 数设成了 8，学习率 2e-5。问题——训练 loss 一路降到 0.2，看起来很漂亮；但抽样 200 条不同问题后发现约 40% 的回复以同一句开场白起头，distinct-2 从 0.71 掉到 0.38；同时通用能力基准掉了约 4 个点，模型开始把领域术语硬套到无关问题上。方案——epoch 数回到 2，学习率从 2e-5 降到 1e-5，并在训练集里混入约 10% 的通用指令数据作为"锚"，同时把输出多样性和通用基准一起纳入每轮的评测看板。效果——distinct-2 回升到 0.66，通用基准的损失从 4 个点收窄到不足 1 个点，而领域任务准确率与跑 8 个 epoch 的版本基本持平。也就是说，多出来的 6 个 epoch 只买到了过拟合。

为什么 SFT 只需 1–3 个 Epoch？

  • SFT 数据量小（数千~数万条），多轮训练极易过拟合
  • SFT 目标是调整行为模式而非学习新知识，少量更新即可
  • 过拟合的表现：训练 loss 持续下降，但评估指标停滞或下降（Alignment Tax）
  • 实验表明：很多场景下 1 个 Epoch 就能达到最佳效果

学习率的重要性

  • 学习率太高 → 灾难性遗忘，模型丢失预训练知识
  • 学习率太低 → 收敛过慢，SFT 效果不明显
  • LoRA 的学习率通常比全参数微调高 5–10 倍（如 1e-4 ~ 3e-4）
  • SFT 超参数的核心原则：小学习率 + 少轮次 + 大 batch
  • 高频问题：为什么 SFT 学习率比预训练低得多？→ 避免破坏预训练学到的知识表示
  • 高频问题：如何判断 SFT 是否过拟合？→ 训练 loss 下降但 eval loss 上升 / 输出多样性降低
  • Warmup 的作用：在模型还不稳定时用小学习率过渡，防止初期梯度爆炸

八、SFT 的问题与对策

灾难性遗忘和对齐税是同一件事的两种说法：参数被拉向新分布，旧分布上的能力就退。所有缓解手段本质上都是"别拉太远"——小学习率、少轮次、混入通用数据、或者干脆只训一小部分参数。

  • 训练与推理共用同一份 chat 模板来源，并用推理框架跑端到端 smoke test
  • loss 只落在 assistant 段，且务必把结束标记包含进去
  • epoch 数从 2 起步，靠验证集和输出多样性决定要不要加
  • 用序列打包提升吞吐，同时按样本切断注意力和重置位置编码
  • 混入 5%~10% 通用指令数据当锚，压住通用能力的退化
  • 每轮同时看两条线：指令遵循是否变好、基础能力是否变差
  • 先按任务类型统计覆盖直方图，缺哪类补哪类
  • 不要为了"训得充分"堆 epoch，SFT 阶段过拟合的代价是多样性塌缩
  • 不要在 prompt 段上算 loss，那会让模型学着自己编题目
  • 不要只用训练脚本做离线评测，它会掩盖模板与推理侧不一致的问题
  • 不要沿用预训练的学习率量级，SFT 常用值要小一到两个数量级
  • 不要只看领域指标就宣布成功，通用基准掉了同样是回归
  • 不要在打包后忘记切断跨样本注意力，那等于让样本互相泄题
  • 不要把"数据量翻倍"当默认改进手段，先确认多样性和纯净度已到位

灾难性遗忘 (Catastrophic Forgetting)

现象：SFT 后模型在某些预训练任务上性能下降。

原因：SFT 数据分布窄，梯度更新偏向 SFT 任务，覆盖预训练知识。

对策：

  • 混入一定比例的预训练数据（如 5%–10%）
  • 使用较小的学习率
  • 减少训练轮次（1–2 个 Epoch）
  • 使用 LoRA 等 PEFT 方法（冻结大部分参数）
  • Elastic Weight Consolidation (EWC) 等正则化方法

对齐税 (Alignment Tax)

  • 定义：为了让模型"对齐"人类偏好，牺牲了部分基础能力
  • 例如：SFT 后模型变得更"安全"，但可能拒绝正常请求或代码能力下降
  • 缓解方法：在 SFT 数据中加入多样化任务（代码、数学、推理等）

数据质量 > 数据数量

LIMA 论文的核心发现（Less Is More for Alignment）：

  • 仅用 1000 条精心策划的数据，就训练出了媲美 GPT-3.5 的模型
  • 启示：预训练已经注入了绝大部分知识，SFT 只需要少量高质量数据来"激活"
  • 数据质量的标准：格式规范、回答准确、多样性高、无矛盾

常见数据问题

问题影响解决方案
标签噪声模型学到错误模式多人标注 + 一致性检查
数据不平衡某些任务过强，其他退化任务采样均衡化
回答过长/过短模型输出长度偏差控制回答长度分布
格式不统一模型输出格式混乱严格统一 Chat 模板
  • 灾难性遗忘是 SFT 的头号问题，LoRA 天然缓解此问题（冻结主参数）
  • LIMA 论文是高频考点：证明了 SFT 阶段数据质量远比数量重要
  • 高频问题：如何平衡安全性和有用性？→ 多样化 SFT 数据 + 细粒度的安全策略
  • 实践中混入预训练数据（Replay）是防止遗忘的最有效手段之一

九、评估 SFT 效果

评估 SFT 必须同时盯两条线：指令遵循有没有变好，基础能力有没有变差。只看前者，就会把"更听话但更笨"当成成功——而这恰好是 SFT 最容易产出的那种失败。

主流评估方法

评估方法类型说明
MT-Bench自动（GPT-4 打分）80 道多轮问题，GPT-4 1–10 打分，考察多轮对话能力
AlpacaEval自动（GPT-4 对比）与 GPT-4 回答对比的胜率，简单高效
Arena ELO人工（匿名投票）Chatbot Arena 中用户盲评，最贴近真实使用体验
MMLU / HellaSwag自动（选择题）评估知识保留，检测是否发生灾难性遗忘
HumanEval / MBPP自动（代码执行）评估代码生成能力是否受损

人工评估 vs 自动评估

维度人工评估自动评估
成本高（需要专家标注）低（API 调用）
可复现性低（主观性强）高（确定性结果）
可信度最高（真实用户感受）中等（与人类偏好相关但不完全一致）
速度慢（数天~数周）快（数分钟~数小时）
偏见标注者偏见GPT-4 偏好更长/更结构化的回答

评估最佳实践

  • 开发阶段用自动评估（MT-Bench / AlpacaEval）快速迭代
  • 发布前用人工评估做最终质量把关
  • 同时监控基础能力指标（MMLU 等），防止灾难性遗忘
  • 关注输出的多样性和一致性，过拟合模型往往输出模式单一
  • MT-Bench 和 AlpacaEval 是目前最主流的 SFT 自动评估方案
  • Arena ELO 被认为是最可靠的评估，但成本高、速度慢
  • 高频问题：GPT-4 自动评估有什么偏见？→ 偏好更长、格式更好的回答（length bias）
  • 评估 SFT 时要同时看指令遵循能力和基础能力保留两个维度

🎯 Q&A

Q1SFT 和预训练的核心区别是什么？

预训练的目标是让模型学习语言知识和世界知识，使用海量无标签文本，通过 next-token prediction 进行自监督学习。

SFT 的目标是让模型学会"听话"——遵循指令、以对话格式回答问题。使用的是精心构造的指令-回答对，数据量远小于预训练（数千~数万条 vs 数万亿 Token）。

核心洞察：SFT 不注入新知识，而是改变模型的行为模式和表达方式，将预训练阶段学到的能力以指令方式"解锁"。LIMA 论文表明，仅 1000 条数据即可完成有效的行为对齐。

Q2LoRA 的原理是什么？为什么有效？

LoRA（Low-Rank Adaptation）在冻结原始权重 W 的基础上，添加一个低秩分解的增量：W' = W + BA，其中 B ∈ Rd×r，A ∈ Rr×k，r ≪ min(d, k)。

有效的原因：

  • 研究发现预训练模型的权重更新具有低秩特性（intrinsic low rank）
  • SFT 只需微调模型行为，不需要大幅改变权重 → 低秩增量足够表达
  • 推理时可将 BA 合并回 W，无额外推理开销
  • 可训练参数仅 0.1%–1%，显存节省 10 倍以上
Q3什么是 Loss Masking？为什么只在 assistant 回复上计算 loss？

Loss Masking 指在计算训练损失时，将不需要学习的 Token 位置标记为 -100（PyTorch 的 ignore_index），这些位置不参与梯度计算。

只在 assistant 回复上计算 loss 的原因：

  • SFT 的目标是训练模型生成高质量回答，不是让模型学会"复读指令"
  • 指令部分的 Token 分布与回答不同，同时优化会互相干扰
  • 减少不必要的梯度计算，提高训练效率
  • 这种做法称为 Completion-only Loss，是目前 SFT 的标准做法
Q4Chat 模板不匹配会导致什么问题？如何避免？

模板不匹配的后果：

  • 模型不知何时停止生成（缺少正确的 EOS Token → 无限输出）
  • 角色混淆（模型可能同时生成 user 和 assistant 的内容）
  • 系统提示失效（安全策略可能被忽略）
  • 输出质量显著下降

如何避免：

  • 使用 Hugging Face 的 tokenizer.apply_chat_template() 自动应用正确模板
  • 确保推理时的模板与训练时完全一致
  • 在模型卡片中明确记录使用的 Chat 模板
Q5如何防止 SFT 中的灾难性遗忘？

灾难性遗忘指 SFT 后模型在预训练任务上性能下降。主要对策包括：

  • 混入预训练数据：在 SFT 数据中混入 5%–10% 的预训练数据（Replay）
  • 小学习率：使用 1e-5 ~ 5e-5，远低于预训练学习率
  • 少训练轮次：1–3 个 Epoch，避免过度拟合 SFT 数据
  • 使用 PEFT：LoRA 等方法冻结大部分参数，天然减轻遗忘
  • 多任务 SFT：使用多样化任务数据，保持模型各方面能力
  • 正则化：EWC、L2 正则化等约束参数变化幅度
Q6LIMA 论文的核心结论是什么？有什么启示？

LIMA（Less Is More for Alignment）的核心结论：仅用 1000 条精心策划的高质量数据，就能训练出媲美 GPT-3.5 的对话模型。

启示：

  • 预训练阶段已经注入了绝大部分知识和能力
  • SFT 的本质是教模型"如何表达"，而非"学什么新东西"
  • 数据质量远比数据数量重要——1000 条高质量数据 > 10 万条低质量数据
  • 数据筛选和质量控制是 SFT 成功的关键

这被称为浅层对齐假说（Superficial Alignment Hypothesis）。

Q7SFT 的学习率为什么通常设为 1e-5 ~ 5e-5？

SFT 学习率远低于预训练（预训练通常 1e-4 ~ 3e-4），原因包括：

  • 保护预训练知识：大学习率会大幅改变模型权重，导致灾难性遗忘
  • SFT 的目标简单：只需微调行为模式，不需要大幅更新参数
  • 数据量小：小数据 + 大学习率 → 严重过拟合
  • 收敛快：预训练模型已在良好的 loss landscape 位置，微小更新即可达到目标

注意：LoRA 的学习率通常高于全参数微调（1e-4 ~ 3e-4），因为只更新少量参数，每个参数需要更大的更新步幅。

Q8Packing 是什么？有什么好处和注意事项？

Packing（序列打包）是将多个短样本拼接成一个长序列的训练技巧，以减少 padding Token 的浪费。

好处：

  • 提升 GPU 利用率，训练吞吐量提高 2–5 倍
  • 减少内存浪费（消除大量 padding）

注意事项：

  • 必须使用 block-diagonal attention mask，防止不同样本间的交叉注意力
  • position_ids 需要在每个样本边界处重置
  • Loss Masking 必须正确设置，只在每个样本的 assistant 部分计算 loss
  • Flash Attention 2 的 cu_seqlens 可以高效实现样本隔离
Q9全参数微调和 QLoRA 在 7B 模型上的显存需求分别是多少？

全参数微调（FP16 + Adam）：

  • 模型参数：7B × 2 bytes = 14 GB
  • Adam 优化器状态（momentum + variance）：7B × 2 × 4 bytes = 56 GB
  • 梯度：7B × 2 bytes = 14 GB
  • 总计：约 80+ GB（需要多卡或 80 GB A100）

QLoRA（4-bit 量化 + LoRA rank=16）：

  • 量化模型参数：7B × 0.5 bytes ≈ 3.5 GB
  • LoRA 参数 + 优化器状态：约 0.5–1 GB
  • 总计：约 6–10 GB（单张消费级 GPU 即可）

这使得在 RTX 3090/4090（24 GB）上微调 7B 甚至 13B 模型成为可能。

Q10如何评估 SFT 模型的效果？有哪些主流基准？

评估 SFT 效果需要从指令遵循能力和基础能力保留两个维度考量：

指令遵循评估：

  • MT-Bench：80 道多轮问题，GPT-4 打分（1–10），考察推理、写作、编程等 8 个维度
  • AlpacaEval：与参考回答（GPT-4）对比的胜率，支持 length-controlled 版本
  • Arena ELO：Chatbot Arena 中用户匿名盲评，最贴近真实使用体验

基础能力评估：

  • MMLU：57 个学科的选择题，检测知识保留
  • HumanEval / MBPP：代码生成 Pass@k
  • GSM8K：数学推理能力

最佳实践：开发迭代用自动评估（快），发布前用人工评估（准）。注意 GPT-4 评估存在 length bias（偏好更长的回答）。
