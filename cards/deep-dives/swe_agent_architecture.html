SWE-agent 架构深度解析

从 Agent-Computer Interface 到 Retry/Reviewer：研究型软件工程智能体的完整运行时
事实基线：当前工作区 SWE-agent 1.1.0，Python ≥ 3.11，SWE-ReX ≥ 1.4.0

SWE-agent 的核心不是“让模型写代码”，而是设计一套对模型友好的 Agent-Computer Interface（ACI）。 它将任务装配、模型决策、命令解析、工具安装、沙箱执行、状态回灌、提交协议、轨迹记录和批量评测组成一个可配置、可复现的实验系统。当前完整实现的价值在研究透明度与可替换性；若目标只是轻量生产使用，官方已建议优先评估 mini-SWE-agent。

零、阅读约定与分模块学习路线

本文只把当前源码能够证明的行为称为架构事实，并将四类能力分开描述：

默认主链DefaultAgent单任务、单动作的模型—环境循环；默认配置采用 function calling、工具 Bundle 与 Docker 部署。
可选能力配置启用RetryAgent、Reviewer/Chooser、ActionSampler、历史裁剪、OpenPR、Local/Modal deployment 等。
外部系统SWE-ReX / LiteLLM部署运行时与模型路由已外置，本仓库通过稳定接口调用，而不是自行实现容器引擎或每家模型 SDK。
维护边界源码现状README 明确主开发转向 mini-SWE-agent；文档、入口和类型存在少量漂移，二次开发前应锁定版本。

一、项目定位与维护状态

1.1 软件边界

SWE-agent 是面向仓库级软件任务的研究型 Agent Runtime。输入可以是 GitHub Issue、文本、文件、SWE-bench 或多模态问题；输出不是“聊天回答”，而是目标仓库中的补丁、执行轨迹和结构化退出状态。它既支持单次修复，也支持批量 benchmark、多 attempt 评审选优和轨迹回放。

1.2 ACI 为什么是核心

模型直接操作原始 Shell 时会面临工具描述不稳定、输出过长、编辑粒度粗、状态不可见和提交协议模糊等问题。SWE-agent 把这些约束编码成 Tool Bundle、Command Schema、Parser、state command、Observation 模板与 submission sentinel，使模型看到的是一种“为 LM 重新设计的计算机接口”。

论文出处：John Yang、Carlos E. Jimenez、Alexander Wettig、Kilian Lieret、Shunyu Yao、Karthik Narasimhan、Ofir Press，SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering，NeurIPS 2024。arXiv:2405.15793 · NeurIPS 官方 PDF

1.3 论文提出的四条 ACI 原则

  1. 动作简单、易懂：减少参数与文档负担，让模型可靠选择和调用。
  2. 动作紧凑、高效：把导航、编辑等关键操作合并为尽可能少的步骤，而不是迫使模型跨多轮拼装高阶操作。
  3. 环境反馈信息充分但简洁：明确呈现当前状态和最近动作的效果，同时避免无关上下文。
  4. 护栏抑制错误传播并加速恢复：例如用语法检查拒绝错误编辑，并把可执行的错误反馈交还模型。

1.6 当前维护含义

二、总体架构与依赖方向

这套分层的真正目的不是"代码整洁"，而是把「谁能被换掉」写死在依赖方向里：模型可换、解析器可换、工具集可换、部署后端可换，唯独 Agent 主循环不该被这些替换波及。研究型系统的价值就在于做消融实验时只动一层，所以依赖必须单向。

五、配置与对象装配子文档

5.1 配置合并

console script 指向 sweagent.run.run:main。顶层入口只识别子命令，随后延迟导入具体实现。BasicCLI 先解析一个或多个 --config，按顺序深合并 YAML；没有显式配置时加载 config/default.yaml；剩余参数由 Pydantic Settings 作为强类型 CLI 覆盖。

路径相对 SWE_AGENT_CONFIG_ROOT 或仓库根解析，配置目录、工具目录和轨迹目录也可通过 SWE_AGENT_*_DIR 变量替换。未知字段通常被 extra="forbid" 拒绝，这让配置错误尽早暴露。

5.3 默认配置的真实含义

默认配置不是“最小 Agent”：它使用面向 Anthropic 风格 ACI 的 system/instance 模板，启用内置 Bash，加载 registry、edit_anthropic 和 review_on_submit_m Bundle，采用 function calling，并给最后两条用户/工具消息添加 cache-control。默认 Environment 是 Python 3.11 Docker deployment。

六、Run 编排层子文档

6.1 RunSingle

RunSingle.from_config 负责加载环境变量、推导输出目录、创建 Agent 与 SWEEnv、保存可回放配置，并挂接 SaveApplyPatchHook；OpenPR 按配置启用。run() 的职责是完整资源生命周期：启动环境、通知 Hook、运行 Agent、保存预测、关闭环境。

6.2 RunBatch

RunBatch 是薄调度器：它不会改写 Agent 的决策逻辑。每个实例都创建独立 Agent 与 Env；并发使用 ThreadPoolExecutor 而非进程池。初始随机延迟用于缓解多个容器同时启动的惊群问题。

6.3 生命周期完整性

单实例 RunSingle.run 的关闭逻辑不是整体包在 finally 中；Batch 的单实例执行则显式在 finally 关闭 Env。若二次开发强化可靠性，应统一资源管理语义。

七、DefaultAgent 主循环子文档

7.1 Setup：构造可工作的世界

  1. 安装 Tool Bundles，并初始化工具环境变量、registry 与 state 文件。
  2. 记录 SWE-agent/SWE-ReX 版本和 commit hash。
  3. 把问题正文放入环境变量，方便容器工具访问。
  4. 按顺序加入 system、demonstration、instance 和可选 strategy 消息。
  5. 通过工具 state command 采集初始工作目录、diff 等状态，填充 Jinja 模板。

7.2 Step：一次完整决策

一步之内被刻意分成两条互不干扰的写入路径：一条喂模型（History，可裁剪、可临时替换、可被处理器改写），一条喂人（Trajectory，只追加、不修饰、每步落盘）。之所以不合并成一份记录，是因为它们的失败模式相反——上下文治理希望尽量少留，审计和复现希望一个字节都别丢。

┌──────────────────────── DefaultAgent.step() 一轮 ────────────────────────┐ │ │ │ 正式 History ──filter(本 Agent 消息)──► HistoryProcessor 链 ──► 模型输入 │ │ ▲ (LastN / ClosedWindow / │ │ │ RemoveRegex / CacheControl) │ │ │ │ │ │ │ ▼ │ │ │ forward_with_handling │ │ │ │ │ │ │ ┌───────────────┴────────────────┐ │ │ │ ▼ ▼ │ │ │ 可恢复异常 模型响应 │ │ │ (格式错 / 拦截 / Bash 语法错) │ │ │ │ │ ▼ │ │ │ │ Parser：恰好一个 action │ │ │ │ blocklist + 多行保护 │ │ │ ┌──────┴──────┐ │ │ │ │ │ 临时 History │◄──── 错误模板 ▼ │ │ │ │ 副本重询 │ (≤ max_requeries) SWEEnv 执行 │ │ │ └──────┬──────┘ │ │ │ │ │ 修正成功才落回正式 History ▼ │ │ │ │ Observation + │ │ │ ▼ state command │ │ └──── assistant(thought/action) + tool(observation) ◄───┘ │ │ │ │ │ ▼ │ │ StepOutput 补全 ──► submission? exit_status? edited files? model stats? │ │ │ │ │ ▼ │ │ TrajectoryStep 追加 ──► 每步重写 .traj（进程被杀也保住已完成的步骤） │ │ │ │ │ done == false ? 回到循环顶 : 进入终止协议 │ └──────────────────────────────────────────────────────────────────────────┘

每轮先从正式 History 中筛出当前 Agent 的消息，再链式应用 HistoryProcessor。forward_with_handling 调用模型并处理可恢复异常；forward 将模型响应解析为唯一动作，做 blocklist 和多行命令保护，然后通过 SWEEnv 执行。

执行完成后，Agent 把 assistant 的 thought/action 与工具 observation 分别加入 History，更新 submission、exit_status、edited files 和模型统计，再追加 TrajectoryStep。每一步后都会重写轨迹文件，因此进程中断时通常仍保留最近完成的步骤。

7.3 终止不是自然语言判断

默认完成协议由 submit 工具生成 /root/model.patch，并在输出中写入特殊 submission sentinel。ToolHandler 检出该标志后读取 patch，将 done 设为真并写入结构化 exit_status。主动执行 exit 则产生 exit_command，不等于成功提交。

把"完成"交给一个必须由工具写出的哨兵串，而不是让模型说一句"我做完了"，是因为自然语言的完成声明既不可验证也不可复现。哨兵串的好处是它同时携带副作用：要产生它就必须真的跑过 submit，patch 也就必然已经落在磁盘上——声明和证据是同一个动作。

这张表真正的设计点是第三列：格式错误走临时 History 副本，其它错误直接结束。原因是格式错误属于"模型没听懂协议"，把失败示范留在正式对话里会让它照着错的样子继续错；而超时、超预算这类错误是环境和资源的事实，模型看到反而有助于调整策略。判断标准是"这条错误信息对后续决策有用吗"，不是"错误严不严重"。

8.1 Autosubmit 的工程意义

Agent 失败不代表已完成修改毫无价值。环境存活时，系统会暂存 Git diff 到 /root/model.patch 并走统一提交解析；环境死亡时尝试从最近 Trajectory state 的 diff 恢复。这是一种“最大化保留部分成果”的降级策略，而不是成功保证。

示例场景：一次批跑里某个实例把 per_instance_cost_limit 用尽时，Agent 已经改好了两个源文件、正在跑第三轮测试。没有 Autosubmit 的话这次 attempt 的产出是 0；有了它，系统在退出前把当前 Git diff 落成 model.patch，仍然产出一份可评测的补丁——它可能通不过测试，但至少进入了 preds.json，能被统计成"提交了但未 resolved"，而不是"什么都没发生"。这个区分对分析失败原因很关键：预算耗尽和模型放弃是两类完全不同的问题，混在一个空结果里就看不出来了。

九、RetryAgent 与评审选优子文档

RetryAgent 是 DefaultAgent 之上的 test-time scaling 外环。每次 attempt 都是独立 DefaultAgent，输出写入 attempt_N；重试前通过 SWEEnv.hard_reset 完整重启部署并恢复仓库，避免前一尝试污染下一次。

hard_reset 看着很浪费——整个部署重启一遍，只为了再试一次。但如果不重启，上一次 attempt 留下的半成品改动、被污染的依赖、跑歪的测试缓存都会成为下一次的隐藏输入，Best-of-N 就退化成了"一次越走越远的连续尝试"。选优的前提是候选之间相互独立，这个代价买的就是独立性。

十、Context Engineering子文档

10.1 上下文组成

模型输入由 system prompt、demonstrations、instance/strategy、历轮 assistant action、工具 observation 组成。模板变量来自问题陈述、Repo 名称、工具文档、工具环境变量和 state command 输出。多模态问题会将允许的 base64 图片 Markdown 转换为 provider 可接受的 image_url 内容。

软件 Agent 的上下文里最占地方的从来不是问题描述，而是工具输出：一次 cat 大文件、一次全量测试日志就能顶掉几十轮对话。所以这一层要治理的对象是 Observation，不是 Prompt——把 system prompt 抠短几百 token 的收益，比不上正确折叠一条旧的 diff 输出。

10.2 HistoryProcessor 链

处理器作用代价/边界
LastNObservations保留最近 N 个 Observation，旧输出替换为省略摘要会改变历史前缀，可能破坏 prompt cache
ClosedWindow同文件只保留最新窗口，旧窗口降为行数摘要依赖窗口输出格式
TagToolCallObservations按工具名给 Observation 加 keep/remove 标签需要与裁剪器组合
RemoveRegex移除历史中的重复大块内容，例如旧 diff正则过宽可能丢关键信息
ImageParsing将内嵌图片转为多模态消息受 MIME 和 provider 能力限制
CacheControl给最近用户/工具消息添加 ephemeral cache 标记是缓存优化，不是压缩

默认配置只启用 CacheControl，不代表项目没有裁剪能力，也不代表默认已经压缩历史。Context Window 在模型调用前通过 token counter 预检，超限后进入 autosubmit 终态。

默认只开 CacheControl 而不开裁剪，是一个偏向研究可比性的选择：裁剪会改写历史前缀，让每一轮的输入都和上一轮对不上，既打掉 prompt cache，也让实验之间难以归因。默认配置宁可撞上 context 上限走 autosubmit，也不愿意默默改掉模型看到的东西——出错要出得看得见，这是实验系统和生产系统的取向差别。

示例场景：某个团队为了省钱，在默认配置上加了 LastNObservations(N=5)，结果账单不降反升。原因是每多一步就有一条旧 Observation 被替换成省略摘要，历史前缀随之变化，Anthropic 的 prompt cache 从第二步起就再也没命中过——省下的那点输出 token，远不够补上全价重算前缀的开销。正确的做法是先用 TagToolCallObservations 只标记那些确实巨大的工具输出（比如全量测试日志），再针对性折叠，让绝大多数轮次的前缀保持字节一致。

十一、模型抽象与成本治理子文档

11.1 LiteLLM 适配层

生产模型统一通过 LiteLLM 调用。SWE-agent 将内部 History 转为 provider message，传入 function tools、temperature、top-p、fallbacks 和 completion kwargs；对上下文、认证、权限、内容策略等错误做分类，Tenacity 只重试被认为是暂态的错误。

十二、Tool Bundle 与 Agent-Computer Interface子文档

ACI 这个概念之所以成立，是因为模型面对的"计算机"完全由我们定义：命令叫什么名字、报错长什么样、一次能看多少行、状态从哪里读回来，全是可设计项。把它们当成接口设计问题而不是 prompt 调优问题，收益才是可累积的——换个模型，接口还在。

12.1 Bundle 是部署单元，不是 Python 插件

每个根目录 tools/<name> 可以包含声明工具的 config.yaml、进入 PATH 的 bin/、可选 install.sh 与库文件。Bundle 在 Agent setup 时上传到目标 deployment 的 /root/tools/<name>，设置权限与 PATH，并用 which 验证工具存在。

12.2 Command Schema 到 Shell

Command 声明名称、参数、必填性、调用格式和可选的多行终止符。FunctionCallingParser 要求模型每次恰好发出一个 tool call，验证 JSON 参数后按照 invoke format 转换为 Shell 字符串。其它 parser 支持 thought/action code block、XML、JSON 或 Bash block，用于适配不同模型能力。

12.3 State 与 Registry

Bundle 的 state command 把工作目录、diff、打开窗口等写入 /root/state.json，ToolHandler 在每步执行后读取并注入后续模板。/root/.swe-agent-env 保存 registry variables，解决工具子进程不能持久修改父 Shell 环境的问题。

12.4 默认工具组合

默认组合提供 Bash、registry、结构化文件编辑和提交前审查。仓库还包含 diff_state、filemap、forfeit、image_tools、search、submit、web_browser、windowed editing 等 Bundle，可按实验配置替换 ACI。

十三、SWEEnv 与 SWE-ReX子文档

13.1 薄封装边界

SWEEnv 不实现 Docker API，而是包装 SWE-ReX 的 AbstractDeployment 和 Runtime。它提供同步的 start/reset/communicate/read/write/interrupt/close API；内部通过 asyncio.run 驱动 SWE-ReX 异步接口。

13.2 启动与重置

  1. 启动 deployment，创建读取 /root/.bashrc 的持久 Bash session。
  2. 设置 locale、pager 和 pip 等环境变量。
  3. 把 GitHub/Local 仓库复制到目标环境，或使用镜像中的 pre-existing repo。
  4. 执行 Repo 的 reset commands 回到 base commit。
  5. 触发环境 Hook，随后执行 post-startup commands。

13.3 Deployment 的真实差异

Deployment适用场景安全含义
Docker（默认）本地复现、SWE-bench 镜像提供容器隔离，但网络、挂载、capability 和资源限制仍取决于配置
Modal 等远端弹性计算与远程任务隔离和凭据边界由平台与 SWE-ReX 实现
Local低开销开发Agent 动作更接近宿主机，风险显著高于 Docker
Dummy测试不代表生产执行语义

十四、Batch、Benchmark 与并发子文档

14.1 实例归一化

文件、Hugging Face、SWE-bench、expert file 和 SWE-Smith 最终都变成相同 BatchInstance。Agent 因而不需要知道任务来自哪个 benchmark。公共选择流程是正则 filter、固定 seed=42 的 shuffle、再按 Python slice 取子集。

14.2 并发模型

多 worker 使用线程池；每个线程拥有独立 Agent、SWEEnv、日志过滤器和输出目录。共享数据仅限全局成本、进度管理和 API key 分配等少数结构，并通过锁或 thread-local 保护。human 模型禁止多线程。

14.3 断点与跳过

若实例目录已有非空、可解析且带有效 exit_status 的轨迹，默认跳过。空文件、坏 JSON、缺失 exit_status 或 early_exit 会被删除并重跑。redo_existing 可强制重做。

14.4 评测外环

所有实例结束后合并 .pred 为 preds.json。SWE-bench evaluate 模式通过 RunHook 周期性或最终调用 sb-cli，生成 results.json。需要区分三个概念：Agent 完成、成功提交 patch、benchmark 实际 resolved。

16.2 Inspector

Textual CLI 和 Web Inspector 只读消费轨迹，可将问题陈述、submission、gold/test patch 和 results.json 组合成展示步骤。它们不参与 Agent 决策，也不能被视为在线 memory。

16.3 可复现性

轨迹中的 SWE-agent/SWE-ReX 版本 hash、resolved config、模型参数、完整 query/action/observation 和日志共同构成复现实验所需的证据链。ReplayModel 可以重发既有动作验证 Tool/Environment 行为，但不会复现原 LLM 的随机推理。

十七、安全边界子文档

边界已有机制不能保证什么
执行隔离默认 Docker / 可选远端 deployment不自动限制网络、文件挂载、CPU/内存、Linux capabilities
命令拦截前缀 blocklist、standalone blocklist、条件正则不是完整策略引擎；Bash 可通过其它写法实现同类效果
交互命令禁用 vim、裸 shell、pager 等易阻塞程序不能检测所有等待输入的程序
资源治理命令超时、总执行时长、成本和 API 调用硬停不能替代 deployment 级资源 quota
密钥SecretStr、.env、环境变量引用propagate_env_variables 会进入容器，debug 日志可能暴露值
代码发布OpenPR 仅对 submitted patch，默认 draft 和额外检查模型生成代码仍需人工/CI 审查
最重要的安全结论：ToolFilter 是可用性和误操作保护，不是安全沙箱。真正的信任边界是 SWE-ReX deployment 配置、容器权限、网络策略、挂载和凭据最小化。

blocklist 之所以不能当安全边界，不是因为它写得不够全，而是因为它拦的是"字符串长什么样"，而 Bash 有无穷多种写法表达同一个语义。任何基于命令文本的过滤都是在和一个图灵完备的解释器比谁的想象力更丰富——这场比赛没法赢。能赢的地方在下面一层：进程根本没有那个 capability、网络根本不通、目录根本没挂载。

17.1 安全落地实践

  • 把真正的限制下沉到 deployment：网络 egress 策略、只读挂载、非 root 用户、CPU/内存 quota、drop 掉不需要的 Linux capabilities。
  • 给容器发短期、最小权限的凭据，任务结束即失效，而不是把宿主机的长期 API key 通过 propagate_env_variables 传进去。
  • 把 Trajectory、Observation 和日志纳入脱敏流程——完整 query 会被逐步落盘，密钥一旦进过上下文就会进 .traj。
  • 把 ToolFilter 定位成"防手滑"：拦 vim、裸 shell、pager 这类会挂起会话的交互式程序，这是它真正擅长的事。
  • OpenPR 保持 draft，把模型生成的补丁当作待审代码走正常 CI 与人工审查。
  • 不要用 Local deployment 跑不受信任的任务：Agent 的动作直接落在宿主机上，blocklist 是唯一屏障，而它挡不住等价写法。
  • 不要靠往 blocklist 里补正则来"加固"，新增一条规则通常只意味着多了一种被绕开的写法没被想到。
  • 不要开 debug 级日志跑带凭据的任务，传播进容器的环境变量可能被原值打印出来。
  • 不要把"默认 Docker"等同于"已隔离"：默认配置不限制网络、挂载和资源，隔离程度取决于你怎么配。
  • 不要在 Hook 里做未加保护的外部 I/O，Hook 是同步广播的，它抛出的异常会打到主链上。

核心架构取舍

  • 记录优先：每步持久化和完整 query 牺牲磁盘/隐私，换取研究可解释性。
  • 外置基础设施：SWE-ReX 与 LiteLLM 减少自建适配，却引入外部版本兼容面。

二十、测试与验证策略

二十一、当前风险与技术债

21.1 论文明确的局限（2024）

  • 最终 ACI 工具集仍小；论文把 web browsing、静态/动态分析、故障定位和 fuzzing 测试生成列为未来扩展，而非已验证能力。
  • ACI 设计和案例分析主要依靠人工查看轨迹、总结重复行为并调参；如何自动化接口设计仍未解决。
  • 实验范围限于软件工程与代码生成；四条 ACI 原则能否迁移到其它数字工作领域尚未验证。

这些是论文对研究范围与方法的限制。论文附录另讨论执行 LM 代码、恶意数据/基础设施和现实部署滥用风险；其 Docker 缓解措施也明确不是硬件虚拟化级隔离。

分享时应强调的五个结论

  1. Agent Runtime 的价值在“模型—工具—环境”的协议，而不是某个固定 Prompt。
  2. History 决定行为，Trajectory 决定可解释性；二者必须分离。
  3. 工具 Bundle 是 ACI 实验的最小部署单元，SWE-ReX 才是真正的执行边界。
  4. Retry/Reviewer 是测试时扩展，不是角色化多 Agent；必须纳入总预算。
  5. 研究可用不等于生产安全：blocklist、日志密钥、资源关闭和维护状态都需补强。

二十三、知识要点 Q&A

History 和 Trajectory 到底差在哪，为什么不能合成一份？
History 是"模型下一轮会看到什么"，Trajectory 是"人类事后能审计什么"。两者的目标是冲突的：上下文治理希望尽量少留——旧 Observation 折叠、重复 diff 删掉、窗口只保留最新的；审计和复现希望一个字节都别丢，包括那些被裁掉的内容和被拒绝的错误尝试。合成一份就必须二选一。最能说明问题的是格式错误重询：错误的模型输出和纠错模板会写进 Trajectory 供分析，但只在临时 History 副本里流转，纠正成功后正式 History 里干干净净，看不到失败示范。
submit 工具为什么要用哨兵串，模型说一句"我改完了"不行吗？
不行，因为自然语言的完成声明既不可验证也不可复现。哨兵串的关键性质是它带副作用：要让这个字符串出现在输出里，就必须真的执行 submit 工具，而该工具会把 Git diff 写成 /root/model.patch。也就是说声明和证据是同一个动作产生的，ToolHandler 检出哨兵后直接去读那个文件即可，不需要相信模型。反过来，模型主动执行 exit 得到的是 exit_command 而不是成功提交——终态分类因此是结构化的，批量统计时"完成""提交""resolved"能被清楚地分开。
RetryAgent 算多 Agent 协作吗？
不算。多 Agent 协作的特征是角色分工和相互通信，比如一个负责规划、一个负责实现、一个负责评审，它们共享任务但看到不同的视角。RetryAgent 里的每个 attempt 都是完全相同的 DefaultAgent 配置，默认顺序执行，attempt 之间通过 hard_reset 刻意切断一切联系——上一次的改动、依赖状态、测试缓存都被清掉。它做的是独立采样加结果选择，属于 test-time scaling，成本换成功率。Reviewer 和 Chooser 也不是"评审员角色"，而是选择器，它们不参与解题。
为什么加了 HistoryProcessor 裁剪反而可能更贵？
因为裁剪会改写历史前缀，而 prompt cache 的命中条件是前缀逐字节相同。以 LastNObservations 为例，每往前走一步就有一条旧 Observation 从完整内容变成省略摘要，于是这一轮的输入和上一轮缓存下来的前缀在中间某处就分叉了，缓存从分叉点之后全部失效，需要按全价重新 prefill。省下的是几千输出 token，付出的是每轮重算整个前缀。正确的顺序是先定位真正巨大的输出（用 TagToolCallObservations 按工具名标记，比如全量测试日志），只折叠这些，让绝大多数轮次的前缀保持不变。
Tool Bundle 和普通的"函数工具"有什么不同？
普通函数工具是进程内的一个可调用对象，注册进去就能用。Bundle 是一个部署单元：它包含 config.yaml 声明、要进 PATH 的可执行文件、可选的 install.sh 和依赖库，在 Agent setup 阶段被整体上传到目标环境并安装，最后用 which 验证确实可执行。这个差别源于执行边界——工具真正运行的地方是容器里的 Bash session，不是 SWE-agent 进程。因此工具可以用任何语言写，也因此需要 /root/.swe-agent-env 这种 registry 文件：子进程改不了父 Shell 的环境变量，跨调用的状态只能落到文件里再读回来。
ToolFilter 的 blocklist 能不能当安全沙箱用？
不能，而且这不是"再多写几条正则就好"的问题。blocklist 匹配的是命令文本长什么样，但 Bash 是图灵完备的，同一个语义有无穷多种写法——变量拼接、base64 解码后执行、写进脚本再跑，都能绕过前缀匹配。真正的信任边界在下面一层：SWE-ReX 的 deployment 配置决定了进程有没有那个 capability、网络通不通、哪些目录被挂载进来。blocklist 的合理定位是防手滑和防挂起，比如拦掉 vim、裸 shell、pager 这类会让会话卡死等输入的交互式程序。
Agent 完成、成功提交、benchmark resolved 为什么要分成三个指标？
它们统计的是三件不同的事，混用会让失败分析完全失真。"完成"指 Agent 主循环正常走到终态，但终态可能是 exit_cost 或 exit_format。"成功提交"指最终产出了非空 patch，注意 Autosubmit 在预算耗尽、上下文超限时也会抢救出一份 diff，所以提交不代表 Agent 认为自己做完了。"resolved"是 SWE-bench 用测试判定补丁真的修好了问题。三者依次收窄：提交率低说明是运行时或预算问题，提交率高但 resolved 低说明是模型能力或 ACI 设计问题——只看一个数字分不出该改哪里。
这套架构里哪些部分值得直接借鉴到自研 Agent？
最值得抄的是三个协议层面的设计。一是 History 与 Trajectory 分离，它让上下文优化和可观测性不再互相牵制。二是结构化的 exit_status taxonomy 加 Autosubmit 降级，失败被分成可归因的类别，且尽量保住部分成果。三是工具以部署单元而非进程内函数的形式存在，让执行边界显式可配。相对不值得直接抄的是 agents.py 的组织方式——主循环、错误策略、提交管理和轨迹写入聚在一起，作为研究代码可读，但生产化时应该拆开；资源关闭也没有统一到 try/finally，这是已知的技术债。
