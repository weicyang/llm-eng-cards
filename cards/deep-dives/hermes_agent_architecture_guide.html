01

Hermes Agent 是什么？

一句话定义：Hermes Agent 是 Nous Research 开源的 自进化个人 AI 代理运行时（Agent Runtime）—— 同一个“大脑”可以同时住在你的终端、Telegram、桌面应用和 IDE 里， 长期记住你、自己攒技能、还能定时替你干活。
先澄清：它“不是”什么
  • 不是代码补全插件。它不寄生在编辑器里做行级建议，而是一个能独立生活在你服务器上的完整代理。
  • 不是模型聊天 UI 外壳。普通 Chat UI 的价值在“渲染对话”，Hermes 的价值在“对话之外的全部运行时”：工具、审批、持久会话、记忆、自治任务。
  • 不是一次性任务脚本。它的设计目标不是“跑完一个 issue 就退出”，而是长期常驻——你可以把它扔在一台 $5 的 VPS 上，人在 Telegram 里随时找它。

它解决什么问题？

直接用“模型 + 聊天框”的局限
  • 关掉窗口，上下文就没了，下次从零开始；
  • 只能在厂商网页里用，进不了你的消息软件；
  • 模型只能“说”，不能安全地“做”（跑命令、改文件）；
  • 换个模型厂商，整个体验推倒重来。
Hermes 的回答
  • 会话持久化：所有对话进 SQLite，随时恢复、全文搜索；
  • 多表面（Multi-surface）：CLI、TUI、Telegram 等约 20 个平台、Web Dashboard、桌面端、IDE 协议，共享同一个大脑；
  • 工具 + 审批 + 沙箱：40+ 工具，危险操作要过审批，命令可以跑在 Docker/远程环境里；
  • 模型自由：OpenAI、Anthropic、Gemini、Bedrock、OpenRouter、自建端点，一条命令切换。

30 秒看懂整体架构

整个系统可以压缩成一张“三层夹心”图：上面是很多入口，中间是一个窄核心，下面是一块共享地基。就这么简单，后面所有章节都是在放大这张图的某一块。

图 1 · 30 秒架构总览：多表面 → 窄腰核心 → 能力边缘 → 共享地基
💡 类比理解 · 什么是“窄腰” 想象一家连锁酒店：客人可以从 App、电话、前台、旅行社任何一个渠道订房（表面层）， 但订单最终都进同一套中央预订系统（窄腰），再分发到各酒店的保洁、餐饮、维修（能力边缘）。 Hermes 的 AIAgent 就是这套中央系统——所有入口共用一个大脑， 所以你在 CLI 里聊到一半的会话，换到 Telegram 上能接着聊。

02

一条消息的旅程

🎬 场景

凌晨一点，你躺在沙发上，给部署在 VPS 上的 Hermes 发了条 Telegram 消息： “服务器有点慢，帮我看看怎么回事。” 下面这 6 步，就是这条消息从进门到变成回复的全过程。

1

消息进门 Gateway Adapter · 平台翻译官

Hermes 的 Gateway 是一个常驻进程，里面插着约 20 个平台适配器（Telegram、Discord、Slack、飞书……）。 每个平台的“方言”不同——Telegram 给你的是带语音条的 Update 对象，Slack 给你的是另一种事件。 Adapter 的职责只有一个：把方言翻译成标准事件，然后交给后面的统一流程。

💡 类比酒店前台的接待员：不管客人说英语还是日语，登记到系统里的都是同一张标准订单。
▸ 源码入口：gateway/platforms/base.py（适配器基类）· plugins/platforms/（各平台适配器）· gateway/run.py → GatewayRunner（常驻进程总管）
2

确认“这是哪场对话” Session Key → 持久会话

系统根据 profile + 平台 + 聊天 + 用户 + 话题 拼出一个 session key， 再去 SessionDB 里查出（或创建）对应的持久会话 ID。这一步决定了三件事： 加载哪份历史、和谁互斥（同一个会话内消息串行排队，不同会话可以并行）、回复发回给谁。 顺带，/approve、/stop 这类控制命令会被识别出来绕过排队—— 不然审批指令自己被卡在队里就尴尬了。

💡 类比报出你的病历号：医院立刻调出全部既往记录，而且不会把你的治疗和别人搞混。
▸ 源码入口：gateway/session.py（会话上下文）· hermes_state.py → SessionDB（会话真相源）
3

唤醒大脑 build_turn_context · 备好上下文

真正干活前，系统先做一轮“备料”：从 SessionDB 恢复历史消息，恢复那份字节级冻结的 System Prompt （这是省钱的命根子，3.2 节细讲），把你的新消息持久化，再把长期记忆（Memory）里和当前话题相关的内容预取出来。 如果历史已经把上下文窗口塞得差不多了，还会在这里先做一次预防性压缩。

💡 类比医生接诊前先翻病历夹：既往病史、过敏史、上次开的药，一样不落摆上桌。
▸ 源码入口：agent/turn_context.py → build_turn_context()
4

核心循环开工 Agent Loop · 想 → 做 → 看 → 再想

现在进入整个系统的心跳——一个同步的 while 循环：把上下文发给模型； 模型若返回 tool_calls（这里它会说“我要在服务器上跑 top 和 df -h”）， 就执行工具、把结果按顺序追加回消息列表，再发给模型；模型若直接返回文本，循环结束。 循环有预算上限（IterationBudget），防止模型无限“折腾”。本例中 Hermes 跑了几个诊断命令， 发现是某个进程吃满了内存，于是组织好结论。

💡 类比修车师傅：听异响（调模型）→ 拆盖检查（调工具）→ 看结果 → 再判断，直到找到毛病或确认“查不出来”。
▸ 源码入口：agent/conversation_loop.py → run_conversation()（循环主体）· run_agent.py → AIAgent（公共门面）
5

动手，但有人盯着 Approval + Environment · 副作用的守门员

工具要产生真实副作用（执行命令、写文件）时，会先过审批管线： 绝对危险的模式直接拦死（hardline，连“全自动模式”都绕不过）；其余按配置走 人工确认（manual，默认）、小模型辅助判断（smart）或放行（off）。 通过后，命令还要选个“动手的地方”——本机、Docker、还是 SSH 到远端服务器。 本例中你在 Telegram 里点了 Approve，命令在目标服务器上执行，输出被截断保护后带回。

💡 类比手术分级审批：拔智齿签字就行，开胸手术必须家属到场；而且手术在哪间手术室做，也是单独决定的。
▸ 源码入口：tools/approval.py（审批模式与硬拦截）· tools/environments/（local / docker / ssh / modal / daytona… 执行后端）
6

收尾与送达 finalize_turn · 记账 + 投递

循环结束后，finalize_turn 做收尾：把这一轮的所有消息（包括“实际发给模型的字节”这份重放视图） 刷进 SessionDB，累计 token 消耗与花费，顺手触发记忆同步和会话标题生成。 最后，回复文本经投递模块适配成 Telegram 消息格式，发回你的手机——从你发消息到收到回复，全程可能只花了几十秒。

💡 类比诊毕：写好病历归档、划价记账，然后把诊断结果用短信发给病人。
▸ 源码入口：agent/turn_finalizer.py → finalize_turn() · gateway/delivery.py（出站投递）

旅程回顾：一张图看完

把刚才 6 步压成一张图。实线是每次都会走的主链路，虚线是按需触发的旁路—— 窗口快满了才压缩、主模型挂了才 Fallback、后台任务完成了才回流：

图 2 · 一条消息的旅程全景：实线主链路 + 三条按需旁路
这一段最值得记住的
  • 入口五花八门，但进屋后走的是同一条走廊：标准事件 → 会话身份 → Turn 准备 → 核心循环 → 收尾投递。
  • 会话是一等公民：先有身份，才谈得上干活；同一会话串行，跨会话并行。
  • 危险副作用永远隔着审批 + 执行环境两道门。
03

七大核心模块详解

这一章是全文最长的部分，但不需要全部读完——每个模块都自成一体，挑你感兴趣的往下钻即可。 如果只有 15 分钟，建议读 3.1（心跳）和 3.2（省钱命根子）。

3.1 AIAgent 与 Agent Loop —— 整个系统的心跳

💡 类比理解 AIAgent 像一位全科家庭医生：你从任何渠道（诊所、电话、上门）找他，都是同一位医生看诊； 他出诊前会把听诊器、病历夹、处方权限一次性备齐（装配），看诊过程（循环）全神贯注，看完写病历归档（收尾）。

先破除一个直觉：AIAgent（run_agent.py）虽然是所有表面共同调用的公共门面， 但它早已不是一个臃肿的“上帝类”——装配逻辑拆到了 agent/agent_init.py， 循环主体拆到了 agent/conversation_loop.py，Turn 的备料与收尾分别在 agent/turn_context.py 和 agent/turn_finalizer.py。 门面只负责“把这些零件组装成一个会话期稳定的运行时”。

关键概念 · 冻结的运行时快照

会话开始时，init_agent() 会把这个会话的能力边界一次性固化： 用哪个 Provider、哪些工具、什么 Prompt 层级、压缩与记忆策略。之后整个会话期间，这套快照保持稳定。 这解释了一个让新人意外的设计：会话中途改工具集，默认要等下一个会话才生效（除非显式加 --now）—— 因为工具 Schema 是 Prompt 前缀的一部分，中途换掉会让缓存全部作废。

图 3 · Agent Loop：想 → 做 → 看 → 再想，直到给出结论或预算耗尽

循环本身是一个同步的 while——这是刻意为之：同步核心让所有表面（CLI、Gateway、桌面端） 共享同一套简单可靠的状态机，把复杂性（排队、并发、推送）推到外围的桥接层去解决。

循环怎么结束？发生了什么
正常完成模型返回最终文本，没有 tool_calls
预算耗尽迭代次数达到上限（Grace Call 之后仍未收口）
软中断你发了 /stop，循环在安全点退出，已做的工作保留
硬取消直接打断当前请求
窗口溢出上下文超限 → 触发压缩后重试，而不是直接报错
限流/鉴权失败进入重试或 Provider Fallback（见 3.4）
▸ 源码入口：run_agent.py → AIAgent（门面）· agent/agent_init.py → init_agent()（装配）· agent/conversation_loop.py → run_conversation()（循环主体）· agent/iteration_budget.py（预算与 Grace Call）
小澄清：子代理的预算和父代理共享吗？

不共享。agent/iteration_budget.py 里父代理的预算来自配置（默认 500 次迭代）， 而每个子代理有独立预算，由 delegation.max_iterations 控制（默认 50）。 这样“让子代理去查个资料”不会因为主会话预算大而变得失控。另外注意： 构造参数里那个 max_iterations=90 只是函数签名的兜底默认，真实运行时由配置决定——读代码时别被它误导。

3.2 Prompt Cache 与上下文压缩 —— 最省钱的设计，和唯一允许“重写历史”的例外

💡 类比理解 把每次模型调用想象成去印刷厂印一本书：前 300 页（System Prompt + 历史对话）每次都一样。 Prompt Cache 就是印刷厂把你上次的印版留着——只要前 300 页一个字节都不变， 这次就直接翻印，又快又便宜；可如果你偷偷改了一个标点，整版作废，从头制版，全价。

理解了这一点，Hermes 里一大批“看起来很保守”的设计就都顺理成章了。 模型厂商对重复前缀收费更低、响应更快，命中条件苛刻：字节级一致。 所以 Hermes 的 System Prompt 被拆成三层，三层在会话期内全部冻结：

层内容比喻
Stable身份（SOUL.md）、工具行为规范、技能索引身份证——永远不变
Context调用方补充说明、项目上下文文件（AGENTS.md 等）工作证——入职时发，当班期间不变
VolatileMEMORY.md 快照、USER.md 画像、技能索引等当日备忘——每天开工前写好，开工后不改
那动态内容（比如“现在几点了”、刚召回的记忆）放哪？

绝不塞进冻结的前缀。它们以 sidecar 的形式挂在用户消息一侧（数据库里的 api_content 字段记录“实际发给模型的字节”），随 Turn 注入。这样前缀岿然不动，缓存天天命中。 同理：技能斜杠命令被解析成普通用户消息，而不是修改 System Prompt； 改工具集、换模型这类会破坏前缀的命令，默认下个会话才生效。

常见误解：“Volatile 层”听起来是每轮都变的？

恰恰相反。这里的 volatile 只表示“内容属性上偏动态”（记忆快照、用户画像这类东西跨会话会更新）， 但在一个会话之内它同样被冻结，是缓存前缀的一部分。名字确实有点误导，记住行为就好。

上下文压缩：唯一被允许的“重写历史”

长会话迟早把模型的上下文窗口塞满。压缩是整个 Hermes 中唯一被允许重组已发送历史的路径， 因为它有正当理由：窗口装不下了。默认策略可以概括成四步：

  • 清理：先廉价地砍掉陈旧工具输出里的冗余（这步不用模型）；
  • 分区：把历史分成 Head / Middle / Tail，保护最近 20 条消息（protect_last_n=20）和真实用户锚点；
  • 摘要：请一个辅助小模型把中段压成结构化摘要（目标 / 约束 / 进展 / 决定 / 下一步）；
  • 重装：拼回一条合法的消息序列（摘要替换中段），清理孤儿工具调用。

触发阈值很克制：上下文达到窗口的 50% 才动手（threshold_percent=0.50）， 压缩目标是把活跃上下文降到约 20%（summary_target_ratio=0.20）。 而且默认是 in-place 压缩：会话 ID 不变，旧消息只是被标记为“已归档”（软删除，仍可搜索）—— 你的聊天记录不会“断成两截”。

常见误解：压缩 = 换新会话？

不是。那是旧式 Rotation 模式（会创建子会话并用 parent_session_id 串成谱系链）。 当前默认 in_place=true：同一会话内软归档，不新增会话节点。 读老文章或旧讨论时看到“压缩轮换 Session ID”，说的是遗留行为。

▸ 源码入口：agent/system_prompt.py（三层组装）· agent/prompt_caching.py（出站缓存标记）· agent/conversation_compression.py（压缩编排）· agent/context_compressor.py → ContextCompressor（默认阈值都在这里）

3.3 工具系统 —— 注册了 ≠ 模型看得到

💡 类比理解 餐厅的后厨能力清单（会做 200 道菜）和今天递给你的菜单（只有 30 道）是两回事。 后厨清单是 Registry，今天的菜单是 Toolset——模型只能从菜单上点菜。

这是 Hermes 工具系统最重要的一个区分，也是新手最容易混淆的地方。整条管线分四段：

  • 注册（Registry）：每个 tools/*.py 顶层调用 registry.register()， 靠 AST 扫描自动发现。它回答“进程里有什么、怎么调”；
  • 圈选（Toolset）：toolsets.py 里的 TOOLSETS 定义不同场景的工具名单 （核心清单是 _HERMES_CORE_TOOLS）。它回答“这个会话的模型能看到什么”；
  • 门控（check_fn）：每个工具可附带一个可达性检查——依赖装了吗、服务通了吗。 结果缓存 30 秒。注意它不是权限闸门，也不能用来判断“这个请求来自桌面端还是 CLI”；
  • 执行：模型点菜后，经过 middleware / hook / 审批，才分发到具体 handler， 结果统一是 JSON 字符串。
为什么这么抠？—— 每个工具 Schema 都是要付费的

工具的 Schema（名字、参数、描述）会随每一次 API 请求发送。 注册 100 个工具全部暴露，等于每轮对话都为 100 份 Schema 付 token 钱，还会挤占上下文、 干扰模型选择。所以 Hermes 的态度是：能力往边缘放，核心菜单保持小。这个原则被总结成一张 Footprint Ladder（足迹阶梯）：

新需求来了，先考虑成本例子
① 扩展已有代码几乎为零给现有工具加个参数
② CLI 命令 + Skill 文档不进 Prompt写一份“如何部署”的技能文档
③ check_fn 门控的工具条件暴露装了 docker 才出现的容器工具
④ Plugin用户目录，opt-in新的搜索后端、新的平台
⑤ MCP Server外部进程接入第三方工具生态
⑥ 核心工具（tools/ 常驻）永久成本，最后手段所有会话都需要的底层能力
小澄清：todo、memory 这些“内置工具”为什么不走普通分发？

它们是 agent-level 工具：todo、memory、session_search、 delegate_task 这几个工具的操作对象是代理自己的状态（待办、记忆、会话、子代理）， 必须在 Loop 内部被拦截处理，而不能像普通工具那样丢给外部 handler。排障时如果发现 “工具注册了却没生效”，先查 Toolset 名单，再查 check_fn，最后才怀疑 Registry。

▸ 源码入口：tools/registry.py（注册表 + check_fn TTL）· toolsets.py（TOOLSETS 与核心清单）· model_tools.py → get_tool_definitions() / handle_function_call()（编排薄层）

3.4 Provider 与 Transport —— 翻译公司 + 供应商管理

💡 类比理解 Hermes 核心永远只说一种“普通话”（OpenAI 风格的消息格式）。要和对岸的法国厂商、德国厂商做生意， 就雇翻译公司（Transport）现场互译；而“跟哪家公司的哪个账户签合同、钱付给谁”， 是供应商管理（Provider）的事。翻译和签合同，是两件独立的事。

新手最常见的混淆是把 Provider 和 api_mode 当成一回事。在 Hermes 里它们是两个正交的维度：

维度回答的问题例子
Provider凭据、默认端点、模型目录、计费路由OpenAI / Anthropic / OpenRouter / Bedrock / 自建端点
api_mode请求长什么样、消息怎么编码、流式事件怎么解析五种协议形状（下表）
api_mode对应的协议形状
chat_completionsOpenAI Chat Completions 兼容（最常见的“普通话”）
anthropic_messagesAnthropic 原生 Messages API
codex_responsesOpenAI Responses API
bedrock_converseAWS Bedrock Converse
codex_app_serverCodex app-server（含原生压缩能力）

Transport（agent/transports/）的职责被刻意压得很窄：只做格式转换—— 把统一消息和工具定义转成厂商格式，再把厂商响应归一化回来。连接、重试、限流退避、 Fallback 全部由运行时层负责。当主模型限流或故障时，Hermes 会走有界的 Fallback： 临时切到备用路径，并保留“原配”快照（Primary Runtime），风头过后还能切回去。 要付出的代价是：换了 Provider 通常意味着缓存冷启动——这是前缀缓存机制的固有成本，不是设计失误。

▸ 源码入口：providers/base.py → ProviderProfile（供应商声明）· agent/transports/base.py → ProviderTransport（翻译接口）· agent/agent_init.py（api_mode 解析）
小澄清：想接一个新模型厂商，应该改哪里？

绝大多数情况写一个 Provider Plugin（放 plugins/model-providers/，声明凭据、端点、模型目录）就够了。 只有当对方是一种全新的协议形状（现有五种 api_mode 都套不上）时，才需要新增 Transport。 往核心代码里堆厂商专属分支，是被开发规范明确拒绝的做法。

3.5 SessionDB —— 会话的记忆库

💡 类比理解 SessionDB 是医院的中央病历档案室：不管你从哪个门进来、挂了哪个科， 所有诊疗记录最终都归档到这里；它同时备有三种查阅视角——给病人看的版本、 给医保复核看的“原始处方单”、以及压缩归档柜。

整个 Hermes 的会话真相源只有一个：state.db（SQLite，WAL 模式）。 它存的东西远超“聊天记录”：会话元数据、完整消息、token 用量与花费、 Gateway 的路由映射、压缩锁、异步委托的投递状态……全在这里。

同一条消息，三种视图
  • 展示视图：用户界面渲染用的内容（内部上下文可以隐藏）；
  • 重放视图：api_content 保存“实际发给模型的字节”，用于精确复现和 Provider 保真；
  • 压缩视图：旧消息不删除，只标记 active=0 / compacted=1 软归档，搜索仍可达。

两个值得知道的细节：

  • 全文搜索是认真的：FTS5 索引支持单词、子串和中文（仓库里甚至有一个自研的 CJK 分词 C 扩展 native/fts5_cjk/）。索引坏了可以重建——消息表才是权威，索引只是加速器；
  • 一切按 Profile 隔离：所有路径必须从 get_hermes_home() 派生， 所以你可以用 hermes -p work / hermes -p life 跑两个互不可见的世界： 各自的配置、密钥、会话、记忆、技能、定时任务。
▸ 源码入口：hermes_state.py → SessionDB · hermes_state_schema.py / hermes_state_search.py（建表与搜索 mixin）· hermes_constants.py → get_hermes_home()
小澄清：批跑/训练轨迹也存在 SessionDB 吗？

不。batch_runner.py 生成的批量轨迹（用于研究/训练）走独立文件管线， 不写入 SessionDB——不然你的个人会话库会被实验数据淹没。 SessionDB 只承载“真实的对话人生”。

3.6 Memory 与 Skills —— 从对话到积累

💡 类比理解 Memory 是便利贴（“用户不吃辣”“项目在 us-east-1”），记的是关于你的事实； Skills 是操作手册（“部署流程：先跑 X，再跑 Y”），记的是怎么干活。 而 Curator 是定期整理手册的图书管理员：过期的手册下架封存，但从不当场销毁。
机制记什么什么时候用
Memory · 本地快照MEMORY.md 长期事实、USER.md 用户画像新会话开始时注入前缀（Volatile 层）
Memory · 外部召回Honcho / Mem0 等后端（最多接一个）每个 Turn 开始前按话题预取，注入当前 Turn
Skills按需加载的程序性知识（SKILL.md）稳定 Prompt 里只有紧凑索引，匹配到任务才加载全文
SessionDB 历史原始对话全文恢复会话、全文搜索（它是记录，不是记忆）

agent/memory_manager.py 里的 MemoryManager 编排整个生命周期： Turn 开始前预取召回 → 循环中提供记忆工具 → Turn 结束后同步沉淀。两个克制的默认值值得注意： 定时任务默认不同步记忆（防止半夜跑的 Cron 任务污染你的用户画像）； 外部记忆服务挂了也不影响主流程——内置记忆照常工作。

Skills 的妙处在于省钱地“知道怎么做”：几百份技能文档不可能全塞进 Prompt， 所以只有“标题 + 一句话摘要”组成的索引常驻，模型觉得某个技能匹配当前任务时， 才用 skill_view 把全文调出来——这是典型的渐进披露（Progressive Disclosure）。 后台的 Curator 则在空闲窗口做卫生：长期没用的技能 Active → Stale → Archived， Pinned 的豁免，归档随时可恢复，绝不自动删除。

▸ 源码入口：agent/memory_manager.py → MemoryManager · agent/memory_provider.py（外部记忆接口）· tools/skills_tool.py（技能加载）· agent/curator.py（技能卫生）

3.7 委托与自治 —— 你睡觉，它干活

💡 类比理解 Delegation 是把活儿当场分给同事（他可以立刻汇报，也可以回头再报）； Cron 是定了个闹钟，到点自动做一件事； Kanban 是一块白板，贴满带依赖关系的便签，谁空了谁认领一张。 三者都复用同一个大脑，但持久性和语义完全不同，不能混着用。

委托（delegate_task）有两种玩法：同步委托阻塞等待子代理交结果，适合“顺手查个资料”； 后台委托立刻返回一个句柄，子代理在后台跑，完成后进入完成队列—— 注意一个关键设计：完成事件不会插进正在进行的对话，而是等父会话空闲时， 以一个全新的 Turn 回流。为什么？直接往进行中的工具序列里塞结果， 会产生孤儿工具结果、打乱角色交替顺序、还会让 Prompt 前缀突变击穿缓存。

防失控的默认值

子代理默认是 Leaf 角色（不能再往下委托）， 委托深度默认只有 1 层（父 → 子，孙子辈默认被拒绝），并发子任务默认 3 个， 子代理迭代预算默认 50。想让子代理继续分解任务？可以，但要显式把它设为 Orchestrator 并调深度上限。

Cron 和 Kanban 才是“重启也不丢活儿”的自治系统：

维度CronKanban
触发方式时间驱动（“每天 8 点”）依赖驱动（“A 完成后轮到 B”）
工作单元每次 fire 创建一个独立会话Board 上的任务节点，可认领/回收
存储Profile 内的 jobs.json每个 Board 一个独立 SQLite
恢复语义原子认领 + 心跳，错过有追赶窗口Owner 死亡/心跳过期自动回收，连续失败自动 Block
适合低频定时任务多步骤、多 Worker 的任务图
一条重要的耐久性边界

后台委托依赖当前进程活着——进程重启，没跑完的子任务就没了 （完成投递状态有持久化，能恢复的是“已完成的交付”）。所以规则很简单： 要求“重启后还能接着跑”的活儿，一律升级到 Cron 或 Kanban， 而不是指望把 Delegation 改造成分布式调度器。

▸ 源码入口：tools/delegate_tool.py（同步委托）· tools/async_delegation.py（后台委托与完成队列）· cron/scheduler.py → tick()（定时调度）· hermes_cli/kanban_db.py（看板持久化）
04

设计哲学与边界

理解了“怎么跑”，再看“为什么这么设计”。Hermes 的架构可以用五条铁律概括—— 你会发现，前面章节里那些“看起来保守”的选择，全部能从这五条推出来。

铁律一 · 缓存优先于即时动态性

Prompt Cache 是成本与延迟的第一性约束。会话期内 System Prompt 与工具集保持字节稳定； 动态内容走用户消息侧的 sidecar；命令变更默认延迟到下个会话。唯一例外是上下文压缩—— 因为它有正当理由：窗口装不下了。

铁律二 · 窄腰核心，表面只是投影

所有表面（CLI、TUI、Gateway、Dashboard、Desktop、ACP、API）最终都调用同一个 AIAgent。UI 层负责“把状态投影给人”，不负责重新实现会话逻辑。 所以你在 CLI 里聊一半，换到 Telegram 能无缝继续——状态在大脑里，不在遥控器里。

铁律三 · 能力属于 Session，不属于进程环境变量

“能不能用桌面相关工具”由谁在连接（Session 属性）决定， 而不是由后端进程的环境变量决定——因为后端进程完全可能跑在另一台机器上。 用 HERMES_DESKTOP=1 这类环境变量给工具开门，是被开发规范明确禁止的捷径。

铁律四 · 异步结果必须走“新 Turn”

后台任务完成、委托结果回流，都以一个全新的 Turn 进入会话， 绝不插进正在进行的工具调用序列。这保住了三样东西：角色严格交替的消息序列、 不出现孤儿工具结果、以及 Prompt 前缀的字节稳定。

铁律五 · 可恢复归档，优先于删除

压缩是软归档不删消息；Curator 归档技能但绝不自动删除； 写文件前有影子 Git 恢复点（Checkpoint）。在这个系统里， “后悔药”是一等公民，而“永久删除”几乎不存在。

常见误解澄清

误解一：“Dashboard 的聊天页面是 React 写的？”

不是。Dashboard 的 /chat 页是用 xterm.js 通过 WebSocket 连一个 PTY 桥， 里面跑的是真正的 hermes --tui。所以聊天语义要扩展，应该去改 Ink TUI， 而不是在 Dashboard 里重写一遍——那会制造两套永远漂移的聊天实现。 桌面端（Desktop）才是独立的 React/Electron 聊天面，走 JSON-RPC 连无头后端。

误解二：“check_fn 可以当权限闸门用？”

不行。check_fn 是进程级、带 30 秒缓存的可达性门（依赖装没装、服务通不通）， 它看不到“这个请求来自哪个会话、哪个用户”。权限是 Toolset 圈选和审批管线（Approval）的职责。 混用这三层是排障时最常见的坑。

误解三：“YOLO 全自动模式能绕过一切限制？”

不能。hardline（绝对危险模式）任何情况下都拦死，YOLO 也绕不过。 而且 YOLO 开关在进程导入时就冻结——运行中的技能或消息无法把它打开， 这是专门防提示注入提权的设计。

误解四：“Hermes 有一篇官方架构论文？”

没有。Hermes 3/4 的 Technical Report 是模型训练报告，不是这个软件系统的架构文档。 想理解 Hermes 的架构，权威来源只有两个：源码本身，和仓库里的 AGENTS.md（开发宪法）与 docs/ 设计文档。

5.3 常见问题

Q：run_agent.py 和 cli.py 怎么都上万行？代码是不是失控了？

这是历史累积的“门面大文件”，但核心实现已经持续拆分：AIAgent 的循环、装配、 收尾都搬进了 agent/ 包。项目规范明确鼓励继续拆窄，读代码时以 agent/ 下的模块为准，别被门面文件的体积吓到。

Q：中途更新了 MEMORY.md，当前会话会立刻“想起来”吗？

不会。当前会话的前缀是冻结的（铁律一）。新内容会在下一个会话随 Volatile 层注入， 或以外部召回的形式在下一个 Turn 以 sidecar 进来。这是“缓存稳定”换来的代价，属于设计内行为。

Q：模型报错、限流了，会话会坏掉吗？

不会。错误被分类处理：限流/鉴权走有界重试与 Provider Fallback；上下文溢出触发压缩后重试； 工具执行失败通常作为 observation 回填给模型，让它自己换个姿势再试。 会话消息始终完整落在 SessionDB 里。

Q：插件随便装，安全吗？

有几道默认防线：项目目录里的插件必须显式 opt-in 才加载； 插件覆盖内置工具默认被禁止；MCP Server 需要信任审计。 但任何能执行代码的扩展机制都不是零风险的——装之前看一眼它是基本原则。

Q：Hermes 算“多智能体系统”吗？

算，但很克制：有委托子代理（Leaf/Orchestrator 角色、深度与并发上限）， 有 Kanban 多 Worker 协作；但没有“一群 Agent 自由对话”的 swarm 玩法。 设计取向是可控的分治，不是热闹的群聊。

Q：想给项目贡献代码，从哪下手？

先读根目录 AGENTS.md（开发宪法），按 Footprint Ladder 选最小落点； 测试必须走 scripts/run_tests.sh（约 17k 个测试，CI 同构环境）； 行为契约测试验证“数据之间的关系”，不要写冻结工具数量或读取源码文本的测试。

★ 读完如果只记三句话

一、缓存前缀是一等公民。Hermes 里大多数“保守”设计——冻结的 Prompt、 延迟生效的命令、新 Turn 回流——都是对字节稳定前缀的守护，因为那是成本与延迟的命根子。

二、窄腰让十个入口共用一个大脑。表面只管投影，能力长在边缘， 状态沉入 SessionDB——这是“换端续聊、越用越懂你”的物理基础。

三、它不是任务工具，是长期居民。对话留下记录，经验长成技能， 约定变成定时任务。理解 Hermes，本质上是理解“一个 AI 如何长期生活”。
