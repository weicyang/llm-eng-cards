DeepSeek Harness
深度架构解析

它不是“一个更大的 Agent 类”，而是一棵由 Cordis 组合的插件树：以 append-only Session 作为事实源，以 ReactLoopAgent 维持极薄的 Turn/Step 控制环，以能力接缝替换模型、执行和持久化实现，并向 Web、Headless、ACP 与 JSON-RPC SDK 投射同一运行内核。

01 · FACT BASELINE

事实基线与阅读边界

本文基于仓库中的实现、包级说明、生成图和架构文档交叉核验。版本来自根 package.json：0.1.0-rc.5，Node.js 引擎为 ^22.19.0 || >=24.0.0。本机环境无法取得 Git SHA，因此不虚构提交基线。

CODE FACT

代码事实

类、事件、状态、配置优先级和失败行为，按当前实现描述；文档和代码冲突时以实现为准。

OPTIONAL

可选能力

Compaction、E2B、Workflow、Goals、Skills、自修改等都依赖 bundle/preset，不等于基础主链默认启用。

DEPLOYMENT

部署选择

RUNTIME

运行状态

Turn、Step、Inbox claim、Activation 与 Fiber 状态是瞬时控制态；SessionEvent 才是可恢复事实。

预发布兼容立场：这是开发者预览。Session 格式版本保持 0 且不承诺兼容；SQLite 用单调递增的 schema version。旧或未知格式会被拒绝，而不是静默迁移。
02 · MENTAL MODEL

用五条主线理解整个系统

把 Harness 想成一台「事件录音机 + 极薄调度器」：SessionEvent 日志录下发生过的一切，ReactLoopAgent 只负责决定下一步问谁、做什么，其余能力全是可插拔的插件。

下面这张图是全篇的坐标系。左侧是组合期（进程启动时一次性完成），中间是运行期主链（每个 Turn 反复走），右侧是事实面（append-only 日志与它派生的所有读模型）。后续每一节都在给这张图的某个方块做放大。

一切皆插件

核心循环、会话、模型、工具、权限、持久化和产品面都由 Cordis 插件贡献。组合关系位于 YAML 与作用域中，不埋在单体入口。

日志是事实，UI 是投影

SessionEvent 追加后成为权威历史。模型消息、会话列表、标题、统计和 ConversationNode 都由日志折叠得出。

Loop 只管编排

ReactLoopAgent 维护 Turn/Step、Inbox 和错误边界；压缩、审批、重试、后台任务等能力通过事件扩展点加入。

能力以三角色成缝

Service Definition 定义协议，Provider 绑定实现，Consumer 使用抽象。只提供接口或只做适配器都不是完整接缝。

同核多壳

Web、Headless、ACP、JSON-RPC SDK 都调用同一个 ctx.agents/ctx.sessions 核心，差异集中在协议、呈现与交互。

模型可见即已记录

任何进入下一次模型请求的动态输入，都必须能从 Session log 重建；否则恢复后的上下文会与运行时漂移。

04 · CORDIS KERNEL

Cordis：插件树而不是依赖注入容器 详细设计

Context 同时承担服务仓库、事件总线、作用域树和生命周期所有者。插件不是“启动时调用一次的函数”，而是在某个 Context 中注册一组可撤销的贡献。

普通 DI 容器只回答“这个接口由谁实现”，Cordis 还要回答“这份实现什么时候消失”——所以每次注册都返回一个 disposer，插件卸载即等于把它注册过的一切原样撤回。

这个差别决定了整套架构能不能做「每会话不同工具集」。一个 Fiber（Cordis 里一个插件实例的运行体，带 PENDING/LOADING/ACTIVE/FAILED/DISPOSED 状态）被 dispose 时，它注册的事件监听、工具、适配器要一次性全部撤销；否则切换 preset 之后旧工具还留在 schema 里，模型会去调一个已经不存在的能力。传统 DI 容器把「注册」当成一次性副作用，做不到这一点。

概念职责架构后果
Service / provide把能力发布到 Context；同名 Service 在组合时选择 Provider。Consumer 面向稳定接口，执行位置和厂商实现可以替换。
inject声明插件激活前必须可见的服务依赖。加载器按依赖图激活；缺失依赖留在 PENDING，启动器最终 fail loud。
事件模式emit 广播、waterfall 可改写链、parallel 并发、serial 有序等待。Extension point 的时间语义属于公开协议；waterfall listener 必须调用 next() 才会委托。
effect / disposer注册事件、工具、适配器等贡献并返回清理动作。热重载、preset 切换和 Agent dispose 不泄漏旧注册。
Fiber 状态PENDING → LOADING → ACTIVE；失败进入 FAILED；卸载经 UNLOADING 到 DISPOSED。配置解析成功不代表插件真正激活；运行时必须核验最终状态。
Scopeglobal、preset、agent Context 形成继承链。每会话可拥有不同工具和 prompt，同时继承全局基础设施。
能力接缝示例：ctx.subprocess 是 Definition；subprocess-local 与 subprocess-e2b 是 Provider；bash、terminal、LSP 是 Consumer。替换 Provider 时，Consumer 不需要感知进程是在宿主机还是云沙箱。
05 · BOOT & COMPOSITION

Profile / Bundle / Preset：三种不同组合尺度 详细设计

Profile选择产品形态和 bundle 集合。Profile 根保持空 entry table，避免它在 patch 体系外偷偷成为另一处真相。
Bundle可安装的 patch-layer 包。dsh-base 提供共享 core spine，dsh-web-app、dsh-headless 叠加产品差异。
Preset面向单个会话/Agent 的插件 roster。Web 会话由 preset provider mount agent.cordis.yml，形成 agent-local Context。
Home / CLI Patch部署和临时覆盖。顺序是 bundles → profile patch → home patch → --patch；后写覆盖整个 entry row，不做 config 深合并。
Derived Overlay启动器还会注入 shipped preset roots 与 telemetry disabled 等派生行。它们不是用户文件，却是最终生效配置的一部分。

真实启动链

环境分层进程环境变量优先，其次 cwd 的 .env，最后是 DSH_HOME 的 .env；已定义值不会被低优先级覆盖。
Profile 解析与 bundle 发现读取 profile metadata、解析安装包路径、加载各 bundle patch。
Compose按 entry id 合成行；禁用、删除与 config 都是显式 patch 语义。
Boot创建根 Context 与 Loader，挂载 include，等待 fibers 收敛。
激活断言发现 PENDING 或 FAILED 就终止，防止“服务器启动了但核心能力没装上”的半活状态。
产品差异：Web 通过 per-session preset roster 创建 Agent；Headless bundle 直接在 host context 创建一次性 Agent，不经过该 roster。两者共享 Agent API，但装配路径不同。
06 · AGENT & INBOX

Agent Registry 负责拥有，Inbox 负责输入意图 详细设计

Agent Service Definition 暴露创建、查询、发送、取消和销毁等操作；ReactLoopAgent 是当前具体实现。Registry 负责 AgentHandle 生命周期和创建事务，循环本身不负责全局查找。

followup

下一 Turn

进入 next-turn 队列并唤醒 Agent。适合新的用户问题、idle 后恢复以及完成通知。

steer

下一 Step

进入 next-step 并唤醒。用于运行中的方向修正；不会改写正在进行的模型请求，但会影响后续 step。

inject

静默注入

同样进入 next-step，但不唤醒 idle Agent。适合后台结果在自然检查点被消费。

Inbox 不是普通数组：splice 写入 durable 事件，claim 建立消息所有权。Turn 打开后先 claim 所有 next-step，再 claim 至多一个 next-turn；这样 queued followup 不会在它所属的 turn 之前被误消费。

创建事务：会话、作用域、preset、Agent 实例和 Handle 必须一起成功。中途失败会反向 dispose 已创建资源，避免留下“有 Session 无 Agent”或“有工具注册无 Handle”的孤儿。
07 · TURN / STEP STATE MACHINE

Turn 是用户意图边界，Step 是一次模型调用边界 详细设计

Turn 是「用户按了一次回车」，Step 是「模型被叫了一次」。一个 Turn 里可以有零个 Step（输入全被拒），也可以有十几个 Step（反复调工具）——把这两个尺度混成一个计数器，超时、计费和打断就全会错位。

idle │ wake（followup 到达 / 外部唤醒） ▼ turn/start ──► claim 输入：先取全部 next-step，再至多取 1 条 next-turn │ （顺序反了，排队的 followup 会抢在它自己的 turn 之前被消费） ▼ ┌───────────────── Step 循环 ─────────────────────────────────┐ │ ① 组装 system prompt + 动态上下文 │ │ ② agent/pre-step ── waterfall，监听器可 rewrite / reject │ │ ③ step/start ── 被接纳的输入原子批量写 user/message │ │ ④ 构造 request：deriveMessages() + tools schema + 路由 │ │ ⑤ llm/stream ── BlockAssembler 收敛 content/推理/toolcall│ │ └─ 出错 ─► agent/request-error ─► 退避 / 换路由 / 压缩后重试│ │ ⑥ 工具调度：并发组 + 独占 barrier，结果按 tool-call 顺序落日志 │ │ ⑦ step/end ── 额外上下文转入 next-step │ └───────────────┬─────────────────────────────────────────────┘ │ 还有 next-step？──是──► 回到 ① │ 否 ▼ agent/turn-stopping（serial）── 插件的最后一次插话机会 │ 期间又被 steer？──是──► 回到 ① │ 否 ▼ turn/end ──► idle
阶段关键动作持久事件 / 失败语义
Wake & Open TurnAgent 从 idle 进入 running；先写 turn/start，再 claim 输入。即使首批输入被拒绝，也存在零 Step 的完整 Turn。
Pre-step组装 system prompt 与动态上下文，然后进入 agent/pre-step waterfall，监听器可 rewrite/reject。当前实现中 prompt assemble 发生在 step/start 之前；这点与一份旧生命周期图顺序不同。
Open Step写 step/start；被接纳的输入以原子批次追加为 user/message。从此模型可见输入可由日志重建。
Requestderive history、render prompt、解析 provider/model、生成 tool schemas；执行 request/header/context 扩展点。运行时检查发送给 LLM 的 messages 与 deriveMessages() 相符。
StreamAdapter 通过 llm/stream 产生 chunks；BlockAssembler 收敛内容、推理和 tool calls。chunk 可用于实时 UI，最终 assistant message 与 usage 写日志。
Tools调度独占与可并发调用，执行完整工具管线；结果按模型调用顺序追加。一个工具失败通常成为结构化 tool result，不破坏同批其他调用的日志配对。
Close Step追加 step/end；额外上下文转入 next-step。concludesTurn 是终止意图，仍需通过 stopping checkpoint。
Turn stopping当无 next-step 时触发 serial agent/turn-stopping；之后再次检查 steering。插件可在最后检查点注入工作；真正无工作才写 turn/end 并 idle。

错误、取消与销毁

agent/request-error 在 step 内处理请求错误。重试插件可改写路由或要求压缩后重试；无法恢复时 step 与 turn 以错误原因闭合。取消负责中断当前操作并收敛事件，dispose 进一步禁止新工作、等待队列/资源清空并释放整个 Agent Context。二者不是同义词。

08 · SESSION & CONTEXT

Append-only 原始历史与可替换模型表层 详细设计

Session 同时解决审计、恢复、流式 UI 和模型历史，但不把它们混成一份可变 message 数组。核心技巧是区分“原始事件日志”和“当前模型表层”。

日志是账本，Session Surface（当前对模型可见的消息投影）是余额。压缩只改余额、不撕账页——这样审计能看到原文，模型看到的却是被摘要过的短历史。

写入侧（append-only，seq 单调递增，永不原地修改） turn/start ─ step/start ─ user/message ─ llm/chunk ─ assistant/message ─ tool/call ─ tool/result ─ approval/* ─ compaction/* ─ step/end ─ turn/end │ ▼ ┌── SessionEvent[] ──┐ │ seq | type | data │ ← 唯一事实源 └──────────┬─────────┘ ┌────────────────────┼────────────────────┬──────────────────┐ ▼ ▼ ▼ ▼ surfaceOp 折叠 ConversationNode JSONL / SQLite stats / title （append 追加， Assembler → Web UI Coordinator 批量 从事件派生， replace 换摘要） ACP 文本更新 复制 + flush 检查点 不是新事实源 │ ▼ deriveMessages() ← 纯函数，保证 tool_call ↔ tool_result 配对与批次原子性 │ ▼ 下一次 LLM request 的 messages 不变量：模型可见 ⇔ 已记录。任何绕过日志直接改 request 的插件， 都会让 fork / resume / replay / UI 对账在同一处开始漂移。
log-only

原始日志

每个事件拥有连续 seq、明确 type 与 typed payload。Turn/Step 边界、stream chunks、审批、计划、todo、遥测输入等都可以保留，而不一定进入模型。

model-visible

Session Surface

surfaceOp: append 增加消息；replace 用摘要替换一段当前表层。原事件仍在日志中，审计和调试信息不丢失。

projection

deriveMessages()

纯折叠函数把 surface 映射为 LLM messages，维持 tool call/result 配对和批次原子性。恢复后不依赖内存缓存重建对话。

request snapshot

Header 与 Context

Epoch header 固定路由身份；request context 记录本次 system prompt、tools 和可解释元数据。二者服务于精确复现与诊断。

Fork 与 Resume

Fork 创建新的 Session 身份并记录 lineage/seed boundary，而不是在同一个日志中回滚。Resume 先从 persistence 载入、修复未闭合生命周期，再重建 Agent；可续跑的 Activation、Goal 等能力必须重新授权，不能仅凭旧事件自动恢复外部执行权。

不变量：“模型可见 ⇔ 已记录”不是建议，而是运行时关系。新插件如果直接修改最终 LLM request，却不追加可重建事件，会让崩溃恢复、fork、replay 和 UI 对账全部失真。
09 · SYSTEM PROMPT & LLM

Prompt 是注册表投影，LLM 是可路由流式能力 详细设计

System Prompt

SystemPrompt Service 维护 section registry。基础身份、工具约束、agent instructions、动态运行环境和插件说明由独立贡献者注册，通过 waterfall 组装为最终文本。工具 schema 来自 Tool Registry；因此 Prompt 与工具集合随 agent scope/preset 变化，而不是全局常量。

LLM Adapter Registry

层作用失败边界
Provider routeagent.options.provider 选择已注册 Adapter；model 与 provider 配置显式解析。无 Provider 或配置歧义尽早失败，不静默选择“第一个”。
PrepareAdapter 把统一 Request 转为供应商参数；credentials 由引用解析，wire 侧不暴露 secret。配置/凭证错误在可解析的最早点报错。
Streamllm/stream waterfall 承载实际流；DeepSeek 与 PI-AI provider 可并存。中断信号、transport error 和 provider error 保留可分类信息。
AssembleBlockAssembler 把增量内容、推理、tool calls 和 usage 收敛为稳定事件。非法工具参数在模型 JSON 边界验证，不把 hostile input 交给 typed tool body。
Retryagent/request-error 允许重试插件决定退避、route 修复或 compaction。重试仍位于当前 step；最终失败必须闭合生命周期。
10 · TOOL PIPELINE

工具不是函数表，而是可治理的执行协议 详细设计

工具调用的危险不在「执行」那一瞬间，而在参数从模型 JSON 边界流进宿主机的那一段路。所以管线把校验、审批、Guard（只能拒绝或弃权、不能放行的单调决策器）拆成独立阶段，任何一环都能在不改工具实现的前提下加约束。

调度

普通工具受并发上限约束；独占工具形成 barrier。结果可以并行产生，但按模型 tool-call 顺序写入，保证确定性历史。

结果协议

模型可见内容、运行元数据、UI presentation 意图分离。finalize 之后只有 content 能进模型，避免日志/UI 私有字段泄漏。

额外上下文

工具可产生 additional context，但它必须被转成下一 step 的已记录输入，不能作为隐藏的内存旁路。

Code Mode

模型通过受约束程序组合工具，降低大量 schema 占用和往返；执行仍走 Tool Registry 与安全管线，不获得旁路权限。

UI Presentation

工具注册时声明 generic / terminal / diff 及 locations。呈现函数只由 args 推导，客户端无需理解 provider 内部实现。

Hook Bridges

Claude Code / Codex hook wire protocol 在 pre/post 等位置接入；桥接失败与 tool body 失败有独立诊断。

  • 把新能力做成 Tool Registry 的 Consumer，让它自动继承并发调度、审批、sandbox 与快照测试。
  • 工具产生的额外上下文，转成 next-step 的已记录输入；模型看得见的东西必须在日志里找得到。
  • finalize 时严格区分 model-visible content 与运行元数据，UI 字段不要顺手塞进模型可见结果。
  • 需要长时间跑的工具改用 Job producer，让它在 busy 时 inject、idle 时 followup。
  • 不要在 tool body 里直接读写全局 process.env 或裸调 child_process，那样会绕开执行世界的成对替换，E2B 下必然错位。
  • 不要用 Guard 去「修正」工具身份或参数——它只能 deny/abstain，改写会让审计记录和实际执行对不上。
  • 不要为了省一次往返，把两个语义不同的操作合并成一个带 mode 开关的工具，审批粒度会随之崩掉。
  • 不要把超长工具输出直接塞回模型，先走 spill 落文件、只回摘要与引用位置。
11 · EXECUTION & SECURITY

把执行位置与安全决策拆成正交维度 详细设计

FS、subprocess、shell、terminal 和 LSP 构成一个执行世界。Local 与 E2B 通过替换成对 Provider 改变执行位置；sandbox、approval 和 permission preset 决定允许什么。

“在哪执行”和“允许执行什么”是两个旋钮。把它们拧成一个，就会得到那种最难查的 bug：UI 显示只读、沙箱也确实只读，但某个工具用的还是本机 FS Provider，于是它照样把文件写进了宿主机。

能力Definition / ProviderConsumer 与关键保证
Filesystemctx.fs；local sandbox FS 或 E2B FS。read/write/search/patch 工具；workspace root 和路径策略一致。
Subprocessctx.subprocess；local process-tree 或 E2B commands。shell、LSP、hooks；超时与 dispose 必须等待进程树收敛。

安全决策链

Sandbox

Policy 解析为 read-only、workspace-write、danger-full-access。Linux 可用 bwrap/Landlock，macOS 用 Seatbelt，Windows 用 ACL；不可满足请求时失败封闭。

Approval

审批是一次性交互 seam。无 answerer 时返回 unavailable，而不是默认同意；“允许一次”不升级后续调用。

Permission Preset

把 sandbox 与 approval 作为一组用户策略切换，防止 UI 显示“只读”但执行 Provider 仍保持写权限。

Monotonic Guards

多个 guard 只能 deny 或 abstain；后续 guard 不能推翻已拒绝决定，也不能改写 tool identity 来规避审计。

Environment Scrub

子进程默认清洗 KEY、SECRET、TOKEN、PASSWORD、DSH_* 等变量；这是降低误泄漏，不是对同 UID 恶意代码的秘密隔离。

Teardown

先 graceful cancel，再 hard kill，最后等待整棵进程树和后台 reader 退出。达到 quiescence 后才完成 dispose。

示例场景：某团队把 Harness 接进 CI，用 workspace-write 跑自动改测试用例。上线第一周有 3 次任务把改动写到了仓库外的临时目录——排查后发现是只替换了 ctx.fs 的 E2B Provider，ctx.subprocess 仍是 local，工具里所有走 shell 的重定向（> /tmp/out）都落在宿主机。改成 FS 与 subprocess 成对切换后，跨界写入归零；同时把 permission preset 从「手工勾选两个开关」收敛成一个下拉项，避免运维再次只拧一半。
信任边界：dynamic Cordis、shell 和任意本地代码具有相近的宿主权限；credentials redaction 保护协议与日志，但无法阻止同一 OS 用户读取其可访问的凭证文件。
12 · CONTEXT PRESSURE

压缩、裁剪、Spill 与溢出恢复 详细设计

Compaction（上下文压缩）不是「删历史」，而是「换一份更短的当前视图」。删日志会同时毁掉审计、fork 血缘和崩溃修复；换 surface 只影响下一次请求里模型读到什么。

Compaction 是 Consumer/Provider seam：触发器判断 token pressure 或捕获 context-overflow，Provider 负责生成摘要。它通过 compaction/start|summary|end 建立锁与可观测阶段，再追加带 surfaceOp: replace 的用户消息替换旧表层。

三种手段的成本完全不同，实践中按序尝试而不是一上来就摘要：先做 tool-result pruning（几乎零成本，但要守住 tool call 与 result 的配对），再做 Spill（把超长输出写进执行世界的文件，模型只拿摘要和路径），最后才是需要额外一次模型调用的摘要式压缩。

Tool-result pruning

优先裁剪高体积、低复用的旧工具输出，但必须保持 assistant tool call 与 tool result 配对，不制造 LLM 非法历史。

Spill

超长结果可写到执行世界中的文件，模型只接收摘要与引用位置；原始 SessionEvent 仍保留可审计描述。

Overflow recovery

请求已经被 Provider 判为上下文溢出时，request-error 插件可触发一次修复性压缩并重试当前 step。

示例场景：一个跑代码库迁移的长任务，单个 Turn 里累计 40 多次 grep/read，工具输出占了上下文的七成。开启 tool-result pruning 后，历史里只保留最近 8 次工具原文、更早的替换为「已裁剪，见 seq #N」占位，单步输入 token 从约 12 万降到约 4 万，且因为配对关系没被破坏，模型没有出现「引用了一个不存在的 tool_call_id」这类硬错误。真正需要摘要式压缩的次数从每 20 步一次降到每 60 步一次。
一致性关键：压缩改变“模型当前看到什么”，不改写“历史上发生过什么”。直接删除 JSONL/SQLite 事件会破坏序号、审计、fork lineage 和读模型。

14 · DURABILITY

Persistence Seam、崩溃修复与读模型 详细设计

JSONL Provider

Header 记录 format version、cwd、lineage 和 seed boundary；事件逐行编码，可选 zstd。恢复时容忍最后一条 torn tail，但不吞掉中间损坏。

SQLite Provider

sessions 与 events 表按 session/seq 建索引；application id 防止误开其他数据库；schema version 单调递增且不做旧版本迁移。

Coordinator

监听 session/event 做有界批量复制；session/flush 是语义检查点。它必须处理背压与 teardown，而不能无限缓存。

Crash repair

恢复时识别未闭合 tool call、step 和 turn，合成错误结果及 turn/end {interrupted}。修复只补生命周期，不伪造模型内容。

派生数据

Projection/Cache 提供 Session 读模型；query 支持列表与筛选；title 从历史派生；stats/telemetry 消费事件。它们都不是新的事实源。Telemetry 是 best-effort，没有 durable outbox：丢失遥测不能阻塞 Agent，但也不能把其计数当作计费级账本。

15 · MULTI-SURFACE

16 · ENGINEERING GOVERNANCE

架构由门禁和文档共同维持 详细设计

Type Safety

全仓 strict/noImplicitAny；事件通过 declaration merging 扩展；跨边界 id 使用 brand；闭合 union 用 assertNever。

Source / Artifact Plane

静态检查从 clean tree 通过 tsconfig paths 指向 src；只有声明依赖的 gate 才读取 lib。源码执行保持 ESM-only。

Coverage

非平凡能力同时规划 unit、e2e 与 keyless snapshot。用户可见行为必须有真实 runnable example 的 transcript，不用 mock fixture 代替。

Documentation

代码变更同步更新 README 与 JSDoc；非平凡决策写 Agent Note；已归档 Note 冻结，不作为当前事实继续编辑。

Package Hygiene

包名、peer dependency、ESM exports、publint、knip、NodeNext consumer 与重复代码都有顶层 gate。

Vendoring

Cordis 固定上游 SHA，变更走 manifest + sync 流程并重放本地 patch；不能把 vendor 当普通 workspace 随手修改。

常用验证按变更面选择：pnpm run test、test:coverage、test:e2e、test:snapshot、typecheck、lint、build、hygiene、doc-sync。CI 拥有全平台矩阵，本地应运行覆盖当前 diff 的最小充分集合。

17 · TRADE-OFFS & LIMITS

关键设计权衡与当前局限 详细设计

选择收益代价 / 限制
所有能力插件化可替换、可按 preset 隔离、可测试装配。启动图复杂；错误常来自“插件未激活”而非普通调用栈，需要 Fiber 诊断。
Append-only Session恢复、审计、replay 与多 UI 投影共享事实。必须管理日志增长；每个模型可见插件都要设计事件；格式演进更严格。
薄 Agent Loop高级能力可独立演进，不产生巨型状态机。行为分散在多个 waterfall/listener，理解时间语义必须同时看扩展点。
整行 patch 替换配置结果可预测，不受隐式深合并影响。覆盖一项配置时需重述该行其他字段；运维需要理解 entry id。
本地与 E2B 同接口工具生态无需两套实现。成对替换 FS/process 才能保持一个世界；只换一半会产生路径与进程错位。
预发布拒绝迁移快速修正基础格式，不背负兼容 shim。升级可能无法打开旧 Session，需要显式导出或重新开始。
Telemetry best-effort不让观测阻塞用户任务。不能保证逐事件送达，不适合作为计费或合规权威记录。

19 · Q&A

组内分享常见问题

为什么不用一份 messages 数组直接持久化？
一份可变数组无法同时保留 stream、审批、tool lifecycle、压缩前历史、计划与 UI 状态。Session log 保存事实，surface 只描述当前模型视图，二者通过纯投影连接。
Turn 与 Step 的区别对业务有什么影响？
Turn 对应一次用户意图处理窗口，可包含多次“模型→工具→模型”往返；Step 严格对应一次模型请求。计费、超时、steering 和生命周期事件如果混淆这两个尺度，会产生错误状态。
为什么 followup、steer、inject 要分三种？
它们表达“属于下一 turn 还是当前 turn 的下一 step”以及“是否需要立即唤醒”两个正交意图。单一 send API 只加字符串会丢失时序意图，造成后台通知抢 turn 或 idle Agent 不必要唤醒。
Compaction 是否会破坏审计？
不会。它通过 surface replace 改变后续 LLM 看到的历史，但原始事件仍在 append-only log 中。审计可查看原文，模型请求重建使用当前表层。
E2B 是否把整个 Harness 搬到远端？
不是。Host 上仍运行 Cordis、Agent、Session 和 LLM 适配器；E2B Provider 只把 FS 和 subprocess 执行世界搬到 sandbox。Consumer 通过同一接口操作远端工作区。
Approval 与 Sandbox 是否重复？
不重复。Approval 决定用户是否授权一次意图，Sandbox 决定即使授权后操作在技术上能触达什么。高风险操作通常需要两者共同约束。
插件加载成功为什么能力仍可能不可用？
YAML 可解析只说明 entry 被读到。Fiber 还可能因 inject 缺失留在 PENDING，或 apply 时进入 FAILED。启动器最终断言所有预期 entry 已激活，避免半活。
如何判断一个状态应该写 SessionEvent？
只要它影响未来模型请求、恢复行为、用户可见状态或外部副作用解释，就应持久化。纯缓存、锁和临时 stream 聚合器可以保持 runtime-only。
为什么旧 Session 直接拒绝而不是迁移？
当前仍是预发布阶段，团队选择先修正基础格式，避免兼容层固化错误抽象。SQLite schema 版本和 Session format 明确检测旧格式并报错。
