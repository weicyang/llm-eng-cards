OpenClaw 架构全链路深度解析

从多渠道接入、Gateway 控制面到 Agent Runtime、上下文、记忆、工具安全、自动化和跨设备执行的源码级团队分享

核心结论：OpenClaw 不是“把聊天接口套在 LLM 外面”，也不是旧文章所说的“Gateway-Pi 云端大脑 + 本地 Cell”。它是一个以 Gateway 为单一控制面、以持久 Session 为连续性主轴、以插件和工具策略为能力边界、面向个人设备长期运行的 AI Assistant Runtime。Gateway 只负责控制面；真正的产品是跨渠道、跨设备、可持续记忆并能够安全行动的个人助手。

阅读约定与分模块学习路线

本文以当前工作区源码与官方文档交叉核验，代码版本基线为 2026.7.2。为避免把历史实现、默认行为和可选插件混成一层，统一使用四种标记：

代码事实当前主链可以从当前源码、schema 和测试定位到的运行时行为。
可选能力显式启用例如 sandbox、QMD、Honcho、LanceDB、OpenShell、Cron trigger script。
边界事实所有权说明 core、plugin、channel、Gateway、node 各自负责什么。
历史/迁移非稳态例如 sessions.json、auth JSON、cron jobs JSON 和旧 Pi 命名。

一、项目定位：个人 AI Assistant Runtime

README 对 OpenClaw 的定义是“运行在自己设备上的个人 AI 助手”。它回答用户已经使用的渠道，能在 macOS、iOS、Android 上听说交互，也能提供 Canvas。这个定位比“Agent OS”更准确，因为代码边界始终围绕个人助手运行时，而不是通用操作系统内核。

维度当前定位架构结果
产品长期在线的个人 AI 助手必须有持久 Session、跨渠道 continuity、记忆和后台自动化
控制面单个常驻 Gateway统一持有连接、协议、路由、配置、调度和状态发布
数据主权Local-first / self-hosted配置、工作区和 SQLite 状态默认落在本机
扩展方式Plugin + Skill + MCP + Node核心保持插件无关，能力通过公开 SDK 和 manifest 注册
交互面多 Channel + 多平台 App渠道只负责运输和平台呈现，产品决策留在核心/owner plugin
最重要的心智模型：Gateway 像家庭 AI 的控制平面；Agent 是带 workspace、auth、session store 的 persona；Channel 是交通系统；Tool 是可执行器官；Skill 是操作知识；Plugin 是运行时代码扩展；Node 是受配对和授权控制的设备能力宿主。

二、总体架构：五个运行平面

看懂 OpenClaw 的关键是认清一件事：Gateway（单一常驻控制面进程）掌管的是「谁能进来、这条消息归谁、现在能不能跑」，它自己从不推理。模型只在 Agent Runtime 那一层出现，而且拿不到任何路由和投递的决定权。

四、Gateway：单一控制平面子文档

Gateway 是一个常驻 Node.js 进程。启动主链从 CLI 懒加载 startGatewayServer，依次完成数据库版本预检、配置和 secrets 快照、插件 bootstrap、HTTP/WSS 创建、upgrade/WS handler 挂载、监听、prepared runtime 与 channels、plugin services、scheduled services 和 config reloader。监听可早于所有 sidecar ready，但 readiness 会持续为 false，依赖 sidecar 的 RPC 返回可重试的 startup unavailable。懒加载设计避免简单 CLI 调用加载完整运行图。

单端口多路复用

表面用途
WebSocketoperator/node 控制协议、RPC、server-push event
HTTP health/health、/healthz、/ready、/readyz
OpenAI-compatible APImodels、embeddings、chat completions、responses
Control UI静态 SPA 与同一 WS 后端
Hooks / Plugin routes外部事件接入与插件自有 HTTP 表面

运行时快照

Gateway 不在每次请求时扫描磁盘。启动时先发布静态 prepared model runtime，再启动 Channels。配置 reload 在同步提交边界让旧 prepared store 失效并门控读取，同时发布配置、owner state 与 lane；随后刷新替代 generation。若提交后的刷新或不可逆 owner 替换失败，受管重启负责恢复，而不是让请求混用新旧 generation。

文档漂移：类型和部分文档仍展示 reload 的 hot/restart 模式与可配置 debounce；当前运行时只实际接受 off 或 hybrid，其他值归一为 hybrid，debounce 固定 300ms。

五、Gateway Protocol、鉴权与配对子文档

协议不是宽松的“JSON-RPC style”，而是 TypeBox 定义、代码生成和运行时校验的闭合 WS 协议。当前普通 operator/UI 使用 v4；Node 与轻量 probe 可在 N-1（v3）窗口内兼容。

Gateway → event connect.challenge {nonce, ts} Client → req connect {minProtocol, maxProtocol, role, scopes, auth, device…} Gateway → res hello-ok {server, features, snapshot, auth, policy} 之后：req {id, method, params} ↔ res {ok, payload|error}，并接收 event stream
守卫行为
Payloadpre-auth 64KiB；handshake 后由 hello-ok policy 宣告，服务器基线 25MiB payload / 50MiB buffered
Auth modenone、token、password、trusted-proxy；非 loopback 暴露必须建立可信 auth
Device proof连接 challenge nonce 必须进入签名；v3 签名还绑定 platform 与 deviceFamily
Pairing新 device ID 需批准；Gateway 发 device token 供后续连接
Scopeoperator.read/write/admin/approvals/pairing/talk.secrets；缺 scope 返回结构化 FORBIDDEN
Idempotencysend、agent 等有副作用方法要求 key，Gateway 做短期去重
Broadcast事件按 scope 和 session subscription 过滤，未知事件族默认 fail-closed

Node 的 capability/command/permission 是声明，不是授权本身；Gateway 还要检查 server allowlist、配对批准和执行时策略。Worker 使用独立、闭合的连接类型，并不伪装成普通 node/operator role。

六、Channel 消息全链路子文档

平台事件 → 持久化入站准入 / tombstone / 确认 → 插件归一化 + allowlist + mention/command 门控 → resolveAgentRoute + sessionKey + 投递上下文 → runChannelInboundEvent 内核 → recordInboundSession → dispatchReplyFromConfig / Agent Runtime → 消息适配器 / 呈现 / 分块 / 媒体 / 线程 → 平台发送 + 确认

为什么要 Durable Ingress

Telegram、Discord、Slack 都先把平台事件放进有去重和恢复语义的 ingress 流程，避免“网络 ACK 成功但 Agent 尚未接管”导致消息丢失，也避免重试造成重复执行。三者复用同一 generic seam，但 update id、snowflake、Events API delivery id、lane key 和 ACK 时机各自由平台插件负责。

Turn Kernel

runChannelInboundEvent 把 ingest、classify、preflight、resolve/assemble、dispatch、finalize 做成统一内核。一次事件的 admission 可能是 drop、handled、observeOnly 或 dispatch；未提及群消息、未授权控制命令、bot loop、outbound echo 都可在模型调用前结束。

Transport-only 原则

Channel plugin 负责平台限制、原生回调、presentation 和物理发送，不负责产品命令树、provider 选择或 feature policy。回复路线由 host 配置确定，模型不能随意把 Telegram 入站改投到 Slack。

Session Key（把渠道、账号、对端、线程压成一个字符串的会话标识）既是连续性的锚，也是并发的锁——同一个 key 上的请求严格串行。所以「DM 要不要合流到一条会话」这个看似产品化的选择，同时也决定了并发粒度。

Session Key

  • 默认 DM：agent:<agentId>:<mainKey>，所有 DM 合流到 main。
  • 可选隔离：per-peer、per-channel-peer、per-account-channel-peer。
  • 群/频道：agent:<id>:<channel>:<kind>:<peerId>。
  • Slack 通常追加 thread；Telegram topic 内嵌 topic；Discord 当前用 thread snowflake 作为 channel peer，并非文档旧写法。

Lifecycle

默认 reset mode 是 none，Session 不会按 24h/4h 自动过期。可显式配置 daily 或 idle；daily 依据 sessionStartedAt，idle 依据真实用户交互的 lastInteractionAt，heartbeat/cron/系统事件不会续命。Session 通过 per-session lane 串行，SQLite transcript 写入还由跨进程文件锁保护。

权威存储

Session 行、路由、transcript event、conversation delivery 和 FTS 均位于 per-agent openclaw-agent.sqlite。旧 sessions.json 与 JSONL 是迁移输入、归档或离线维护，不再是运行时热路径。

八、Agent Runtime：外环恢复 + 内环 Tool Loop子文档

Gateway agent/chat.send → agentCommand（准备 session、模型、thinking、timeout） → runEmbeddedAgent（session lane + global lane） → runPreparedEmbeddedLoop（attempt / compaction / auth rotation / model fallback） → selectAgentHarness（openclaw 或 plugin harness） → runEmbeddedAttempt（session、tools、stream） → AgentSession.prompt → Agent.prompt → agentLoop → 模型流 → 工具调用 → 执行 → 观察 → 下一轮 → 订阅流 → 终态 → 投递 / agent.wait

为什么要两层循环？因为「这次模型调用失败了要不要换个模型」和「模型这轮想调哪个工具」是两个完全不同时间尺度的问题。混在一个循环里，重试逻辑会和工具调度纠缠成谁也改不动的状态机。

双层 Loop

层负责不负责

事件流

Runtime 把事件桥接成 lifecycle、assistant、tool 和 compaction stream。Tool 只有在模型 stop reason 为 tool use 时执行；可并行，但声明为 sequential 的工具强制串行。最终回复还会过滤精确 NO_REPLY、去掉 message tool 已经发送过的重复确认，并在必要时生成工具错误 fallback。

终态归一

完成、hard timeout、timeout、cancel、abort、blocked、abandoned、failed 进入统一终态模型。hard timeout 和 cancel 具有 sticky 优先级，防止晚到的普通“成功”覆盖真实终止原因。agent.wait 只等待 runId 的终态，等待超时不会停止底层执行。

“Pi Runtime”现状：产品 runtime id 已是 openclaw；pi 仅是 legacy alias。当前 agent loop 已由 OpenClaw 自有 @openclaw/agent-core 和 embedded runner 组织，旧文章不能再把 Pi 当独立执行层。

九、模型、Provider、Harness 与 Failover子文档

Provider、Model、Agent Runtime/Harness 和 Channel 是四个不同维度。Model/provider 配置决定推理路由；Harness（会话管理器，封装某个执行 Runtime 的原生契约，决定一次 prepared turn 具体怎么跑）决定如何执行 Agent 协议；Channel 仅负责消息运输。

Failover 的设计原则只有一句：它是故障恢复，不是替用户做决定。所以它只对当前这一轮生效，下一轮仍从用户选的模型重新开始——一次临时的 503 不应该永久改变这个会话的行为和成本。

Harness 选择

  1. model-scoped agentRuntime 优先。
  2. 其次 provider-scoped runtime。
  3. auto 让已注册 plugin harness 依据有效 provider route 声明支持；无人认领才回 built-in openclaw。
  4. 显式指定的 plugin runtime 不可用时 fail-closed，不悄悄换 built-in。

两阶段 Failover

  1. 当前 Provider 内轮换 auth profile，并应用 cooldown/disabled 状态。
  2. 只有 failover-worthy 错误且候选链允许时，才进入下一个 model fallback。

Configured default 可以使用 configured fallbacks；agent primary 只有显式配置 fallbacks 才允许；用户通过模型选择器或 /model 写入的 session override 默认严格，失败就报告，不用无关模型“替用户成功”。Fallback 只对当前 turn 生效，不改写下一 turn 的选择。

若所有候选都仅因 overload 失败，且尚未产生 tool 副作用或 assistant 输出，系统可对完整链做有界指数退避重试；一旦已经有可见副作用，就不会冒重复执行风险。

Codex app-server 属插件 harness。已直接核验 sibling Codex 的 thread/start 与 model/list 协议；这些字段只用于证明 Codex Harness 边界，不提升为跨 Provider 的通用契约。

十、Context Engineering：模型实际看到了什么子文档

Context 是「这一轮塞给模型的那一大坨字节」，Memory 是「存在磁盘上的长期事实」。两者的关系是：Memory 经过检索之后可能变成 Context 的一小部分——但 Context 里绝大多数内容（system prompt、tool schema、transcript）跟 Memory 毫无关系。

Context 是一次 run 发给模型的全部内容，不等于 Memory。它由 OpenClaw 每次动态构建：

默认通常关闭；特定 Anthropic 缓存场景可自动开自动开启，新配置默认 safeguard
目的轻量释放窗口语义压缩并保持会话连续

Compaction（把较老的对话摘要成一段并写回 transcript 的语义压缩）会保持 assistant tool call 与对应 tool result 配对，保留最近尾部；上下文溢出走压缩后重试，而不是误判为模型 fallback。压缩前默认运行一次 silent memory flush——这一步的意义在于：压缩之后细节就找不回来了，得先给记忆层一次「把值得留的事实写下来」的机会。

示例场景：一个接了 6 个 MCP server 的 Agent，光 tool schema 就占掉约 18k token，加上 AGENTS/SOUL/TOOLS 等 bootstrap 文件约 15k，模型还没看到用户第一句话，窗口已经用掉 33k。表现出来是「每轮都很贵、稍微聊几句就触发 compaction」。用 context report 拆解后做了两件事：把 3 个低频 MCP server 从默认 agent 的 allowlist 里摘掉（需要时用独立 agent），并把两个超过 20,000 字符上限、正在被截断的 bootstrap 文件拆成按需 read 的 Skill。常驻开销降到约 9k，compaction 触发频率下降一个数量级。这里的通用教训是：tool schema 是隐藏但真实计费的上下文，排查窗口问题必须先看它。

十一、Memory：Markdown 产品面 + SQLite 检索面子文档

OpenClaw 的“记忆”不是简单三级概念，而是两个互补面：

人类可编辑产品面MEMORY.md 保存精选长期事实；memory/YYYY-MM-DD.md 保存工作日志；可选 DREAMS.md 保存 dreaming 审阅产物。
机器检索与状态面per-agent SQLite 保存 chunk、source、FTS、vector、embedding cache、index state；索引可以重建，Markdown 仍是用户资产。

默认内置检索链

Memory Flush 与 Dreaming

接近 compaction 时，memory-core 生成受限 housekeeping turn，只开放 read/write，将耐久事实 append 到当日日志。Dreaming 是默认关闭的后台 consolidation：收集 recall signal、评分、达到阈值后晋升到 MEMORY.md，并把审阅面写入 DREAMS.md。

Backend 插件

memory-core 是默认 slot；QMD 提供本地 sidecar、rerank 和 query expansion；Honcho/LanceDB 是可安装插件；memory-wiki 在 active memory plugin 旁增加带 provenance 的知识库层，而不是替换 recall owner。

十二、Tool、Skill、Plugin、MCP：四层能力模型子文档

概念本质如何进入 Runtime安全边界

SkillSKILL.md 操作知识先注入 name/description/location/version，按需 read 全文可见性 allowlist 不等于 shell 授权

Skill 加载优先级

从高到低：workspace skills → workspace .agents/skills → personal ~/.agents/skills → managed ~/.openclaw/skills → bundled → extra directories/plugin skills。同名时高优先级覆盖低优先级；agent skill allowlist 是最终可见集合，不与 defaults 自动合并。

Plugin 能注册什么

Channel、Provider、Agent Harness、Tool、Skill、Hook、Service、Gateway method、HTTP route、Memory/Context slot、speech/voice/media 等。插件生产代码不得深导入 core src/**；跨边界只允许公开 openclaw/plugin-sdk/*。

Tool Policy 是多层 AND 过滤

顺序大致为 profile → provider profile → global allow/deny → provider allow/deny → agent → group → sender → sandbox → owner-only → subagent → runtime → inherited。Deny 永远优先；空 allow 表示不额外收紧，而不是“禁用全部”。MCP/LSP 后追加的工具还会再做一次最终 effective policy。

Browser 在 catalog 中可见，但实际由 browser plugin 注册，不是 agent-core 的硬编码工具；sandbox 默认 deny browser、canvas、nodes、cron、gateway 等高影响能力。

十三、Sandbox、Tool Policy、Elevated 与 Approval子文档

把这四层想成机场安检的四道关：Tool Policy 决定这趟航班存不存在，Sandbox 决定登机口在国内还是国外，Elevated 是一张明确写着「允许出境」的特批，Approval 是这一次到底放不放行。任何一道都不能替代另外三道。

模型想调一个工具 │ ① Tool Policy —— 这个工具在本次 run 里「存在」吗？ │ 多层 AND 过滤，Deny 永远优先： │ profile → provider profile → global allow/deny → provider allow/deny │ → agent → group → sender → sandbox → owner-only → subagent │ → runtime → inherited →（MCP/LSP 后注册的工具再走一次最终 pass） │ 注意：空 allow 表示「不额外收紧」，不是「全部禁用」 │ ├─ 不存在 → 模型根本看不到这个工具，谈不上调用 ▼ 存在 ② Sandbox —— 它在「哪里」执行？ │ mode 默认 off；开启后 backend = docker / ssh / openshell │ scope = agent（默认）/ session / shared 决定实例数量 │ workspaceAccess 默认 none；ro 时 write/edit/apply_patch 直接禁用 │ Gateway 自己永远在 host，sandbox 只搬动工具执行 ▼ ③ Elevated —— 这次 exec 是否被显式允许逃出 sandbox？ │ 只影响 exec；永远不能绕过 ① 的 deny ▼ ④ Approval —— 这一次高风险执行，operator 批不批？ │ 可持久化等待决策；node 侧还要绑定 prepared run plan ▼ 执行（host / docker / ssh / openshell / node） 默认值容易记反，列在这里：mode=off · scope=agent · backend=docker workspaceAccess=none · docker network=none · root 只读 · capabilities drop ALL

这四者解决不同问题，不能互相替代：

机制回答的问题关键事实
Tool Policy哪些工具存在deny/allow 多层过滤，最先阻断
Sandbox工具在哪里运行只移动工具执行；Gateway 永远在 host
Elevatedexec 是否显式逃出 sandbox只影响 exec，永不绕过 tool deny
Approval这一次高风险执行是否获准可持久化等待 operator 决策；node 还绑定 prepared run plan

三种 Backend

  • Docker：本地 namespace，支持 sandbox browser；适合本机隔离。
  • SSH：首次 seed 后远程 workspace 成为 canonical，不自动同步回本机。
  • OpenShell：managed remote sandbox，可选 mirror 或 remote 模式。

Scope 决定实例数量：agent、session 或 shared。WorkspaceAccess 为 ro 时禁止 write/edit/apply_patch；额外 bind 是刺穿 sandbox 文件视图的显式能力，因此对系统路径、Docker socket、credential roots、symlink parent 与保留目标有严格校验。

示例场景：一个把 Agent 接进公司 Slack 公开频道的部署，管理员以为「Workspace 限定在 ~/agent-work 就等于隔离了」。实际上 workspace 只是 cwd 与资产边界，绝对路径照样能读到 host——某次用户随口让 Agent「看看这台机器上有哪些配置文件」，它就把 ~/.ssh 目录列表贴进了公开频道。修复不是加一条 prompt 禁令（不可信输入下 prompt 约束等于没有），而是三处配置：sandbox 打开并设 workspaceAccess: ro、把 exec 类工具从该 agent 的 allowlist 移除、给剩余高影响工具挂 approval。判断标准是：任何能接触不可信输入的会话，都不该在 mode: off 下运行。
  • 面向不可信输入（公开群、Webhook、多用户 DM）的会话，先开 sandbox 再谈体验。
  • 用 effective tools / sandbox explain 之类的诊断面确认实际生效策略，而不是靠读配置文件推断。
  • 凭据一律走 SecretRef，让失败能按 owner 隔离成 configured-unavailable，而不是整个 Gateway 起不来。
  • 新增能力先问它属于 Tool、Skill、Plugin 还是 MCP，选错扩展面的代价会一直摊在核心里。
  • 不要把 Workspace 当安全边界——它只是 cwd 与资产范围，绝对路径依然能触达 host。
  • 不要指望 Skill 能授权：它只教模型怎么做事，能不能做由 tool policy、sandbox、approval 共同决定。
  • 不要用空的 allow 列表表达「全部禁用」，那被解释成「不额外收紧」，结果与预期完全相反。
  • 不要把 node 声明的 capability/command 当授权，它只是声明；真正的门是配对批准与服务端 allowlist。
  • 不要再往 JSON/JSONL sidecar 里写新的运行时状态，SQLite 才是权威，双写只会制造两份都不可信的事实。
Sandbox 不是完美安全边界。真正的防线是入口 allowlist、最小 tool policy、审批、凭证隔离、OS/container 边界和可观测性共同组成的纵深防御。

十四、Cron、Heartbeat、Hooks 与 Background Tasks子文档

Cron

Cron 运行在 Gateway 进程中，权威状态位于 shared SQLite。支持 at/every/cron 时间计划，以及 on-exit/stream 事件计划；payload 有 systemEvent、agentTurn、command、script；delivery 有 announce、webhook、none。每次执行都会创建 task ledger 记录。

执行类型语义
Main session向 cron-owned wake lane 注入 system event，可请求 heartbeat
Isolated每次新 session/transcript，运行独立 agent turn
Current/custom session绑定现有或命名持久 session
CommandGateway host 确定性进程，不调用模型
Script/trigger需显式开启危险自动化门，带 tool budget 和 timeout

Timer 最大 delay 60 秒；递归错误退避为 30s、60s、5m、15m、60m。启动时过期 isolated turn 会改期，而不是在 channel connect 窗口里立即重放。

Heartbeat

Heartbeat 默认轮询 agent 基础 Session，不是精确 scheduler；heartbeat.isolatedSession:true 可改为新的 cron-style isolated Session。默认间隔 30m、默认 target none；当 Cron 正在运行或排队时会 defer。Outcome 写入 per-agent heartbeat_outcomes，而不是 Cron task ledger。

三种容易混淆的 Hook

  • Internal hooks：Gateway command/session/message 生命周期脚本。
  • Inbound HTTP hooks：/hooks/wake、/hooks/agent、mapped hook。
  • Plugin typed hooks：有优先级和 block/cancel 合并语义的 runtime middleware。

Cron completion webhook 是第四个独立概念：它是 outbound delivery，不是 inbound hooks token。

十五、Nodes、Companion Apps 与跨设备执行子文档

Node 通过同一 Gateway WS 连接但声明 role: node，发布 caps、commands、permissions。它可以提供 camera、screen、location、canvas、system.run、MCP 等能力。Gateway 把这些视为声明，并用 device pairing、node capability approval、server command allowlist 与执行期 permission 再次校验。

Agent / Operator 请求 node.invoke → 校验方法 + operator scope → 捕获配对 generation → 节点在线？否则 APNs 唤醒 + 有界重连等待 → 对照已批准表面校验命令 → 节点执行本地能力 → node.invoke.result / progress → Gateway 恢复工具/运行

macOSOperator UI + 可选 Mac Node Mode + 可托管 Gateway菜单栏、voice/canvas、本地能力

十六、配置、SecretRef、Doctor 与 SQLite子文档

Config Load

openclaw.json (JSON5) → include + 环境变量替换 → 重复 agent 目录检查 → Zod 根 schema + 插件校验 → 物化规范配置 → 发布运行时快照 失败 → InvalidConfigError（恢复：doctor/手动）

运行时只读取当前规范形状，不为旧键保留 silent fallback。Shipped config 变更由 openclaw doctor --fix 或 plugin doctor contract 迁移；这使主运行链保持单一 canonical path。

SecretRef

Secret 可以来自 env、file 或 exec provider。解析按 owner 建立 assignment：Gateway 自身 ingress auth 无法建立时拒绝启动；已知 channel/provider/account owner 的 secret 失败可只把该能力标记为 configured-unavailable；unknown owner fail-closed。Reload 只有 ref 与 provider 未变化时才能保留 last-known-good。

Q&A

OpenClaw 与 LangGraph/CrewAI 的核心区别是什么？

OpenClaw 首先是可运行、可运维的个人助手系统：Gateway、channels、sessions、memory、tools、sandbox、cron、nodes 和 apps 都是产品主链。LangGraph/CrewAI 更偏应用编排框架，通常需要自行建设这些控制面和运行时设施。

为什么 Gateway 不拆成微服务？

个人/小团队自托管最重要的是部署、恢复和一致性。单进程 + SQLite 减少分布式协调；渠道和设备通过插件/协议扩展。若要更强隔离，优先使用多 Gateway、多 host 或 cloud worker，而不是先拆内部服务。

Workspace 是安全沙箱吗？

不是。Workspace 默认只是 cwd 与资产边界；绝对路径仍可能访问 host。要形成执行隔离必须启用 sandbox，并结合 tool policy、approval 和 OS/container 权限。

Memory 为什么既有 Markdown 又有 SQLite？

Markdown 是用户可读、可编辑、可审计的知识产物；SQLite 是运行时索引、FTS、向量、cache 和 session 状态。索引可重建，二者不是双写同一权威数据。

Skill 能授予 Tool 权限吗？

不能。Skill 只教模型如何做事；Tool 是否可见和可执行由 effective tool policy、sandbox、approval、plugin ownership 与 sender context 决定。

为什么模型 fallback 不直接永久切换 session？

Fallback 是失败恢复，不应替代用户选择。它只对当前 turn 生效；下一 turn 仍从 selected model 开始，避免一次临时服务故障永久改变行为和成本。

Node 是否等于远程 Agent？

不是。Node 是设备能力宿主，发布受限 command/capability；Agent persona、session、routing 和推理所有权仍在 Gateway/Agent Runtime。Cloud worker 是另一条闭合执行协议。

生产环境最小安全基线是什么？

非 loopback Gateway auth、DM pairing/allowlist、多用户 DM 隔离、最小 agent/tool allowlist、不可信会话 sandbox、exec approval、SecretRef、插件来源审查，以及 health/doctor/audit 监控。

附录 A · 术语对照表

本表汇总全文出现的核心术语。术语在正文中保留英文原貌，此处给出中文释义，方便非本项目工程师查阅。

术语中文释义
Gateway网关 / 控制面：单一常驻进程，统一负责接入、鉴权、路由、会话、调度与状态发布
Agent Runtime代理运行时：把已准入、已路由的请求准备为可执行 turn 的完整执行体系
Agent Loop代理循环：agent-core 内层"模型流 → 工具调用 → 观察 → 下一轮"的核心循环
Embedded Runner内嵌运行器：OpenClaw 外层恢复循环，负责 Harness、认证、重试、Compaction 与终态
Harness会话管理器：封装具体执行 Runtime 与 native 契约，决定一次 prepared turn 如何执行
Channel消息渠道：纯运输层，负责平台事件接入与回复投递，不拥有产品命令树
Provider模型提供商：提供 LLM 能力的厂商插件（OpenAI、Anthropic 等）
Plugin / Skill / Tool插件（运行时代码扩展）/ 技能（操作知识）/ 工具（可执行器官）
Session / Session Key会话 / 会话键：标识一段连续对话，是连续性（continuity）的主轴
Context Engineering上下文工程：组装发给模型的系统提示、历史与工具清单
Compaction上下文压缩：对话过长时压缩旧消息以腾出上下文空间
Failover / Fallback故障切换 / 回退：主模型失败时按候选链自动切换到备用模型
Tool Policy工具策略：多层 allow/deny 决策链，决定 AI 能使用哪些工具
Approval审批：高风险操作需人类确认后才执行
Sandbox沙箱：OS 级隔离环境，限制工具执行范围（默认 off / scope agent）
Ingress / Drain入站 / 泵送：消息先持久化入队（durable），再由 drain 认领分发，防崩溃丢失
Admission准入：请求进入运行前的资格与并发控制
Binding / Route绑定 / 路由：把渠道账户映射到某个 Agent 的规则（9 级优先级）
Terminal Outcome终态：运行结束的统一归一结果（完成/失败/取消/超时）
Stream Bridge流桥：对模型流逐层包装（修复、超时看门狗、诊断）的适配层
Reply Shaping回复整形：把 AI 回复格式化为目标渠道支持的形状并去重
Projection投影：把运行内部状态归约为对外可见的 transcript / 事件
Prepared Runtime预备运行时：启动时发布、供请求复用的稳定运行时快照
Snapshot / Generation快照 / 代：配置与运行时状态的版本化发布单元
Hot Reload热重载：配置变更时失效旧 store 并发布新 generation（当前仅 off / hybrid）
SecretRef密钥引用：按所有者隔离的凭据引用，失败时最小化隔离
Doctor诊断修复：openclaw doctor --fix，负责配置迁移与修复
MCP模型上下文协议：连接 AI 与外部工具/数据的开放协议
Node节点：受配对与授权控制的设备能力宿主（跨设备执行）
Cron / Heartbeat / Hooks定时任务 / 心跳 / 钩子：后台自动化触发机制
Canonical Config规范配置：运行时只消费当前规范形状，旧形状仅在 doctor 中迁移
Local-first / Self-hosted本地优先 / 自托管：配置、工作区与 SQLite 状态默认落在本机

更完整的入门级术语表与类比解释，参见《OpenClaw 架构入门指南》（openclaw_architecture_guide.html）附录 A。
