1. 模块定位

Channel 消息链是“平台事件 ↔ OpenClaw turn”的适配层。插件接收原始平台 envelope、收集平台可证明的 sender/mention/thread facts、提供 outbound adapter；Core 拥有 durable ingress、公共 gate、route/session 投影、Agent dispatch、消息 receipt 与 durable delivery。证据：src/channels/AGENTS.md:1-24、src/channels/plugins/types.plugin.ts:47-114、docs/plugins/sdk-channel-plugins.md:19-35

边界Channel plugin 负责Core/相邻 owner 负责
Ingress 传输Webhook/socket/polling、签名/token 校验、raw envelope、平台 ack/cursor。SQLite queue、claim/recovery、lane、retry/dead-letter。
身份与事实平台 sender/channel/thread/mention/reply facts、稳定 ID 规范化。统一 allowlist/access group/mention/command 决策。
路由平台 conversation grammar、target/thread 解析 hook。Agent binding、session key、store path 与 delivery context。
Turn组装平台 ctx 与 delivery adapter。record、queue/adoption、Agent/tool loop、finalize。
Presentation把 portable presentation/action 映射为 buttons/blocks/components；执行平台限制。产品命令树、portable action 类型、reply payload。
Outbound调用平台 SDK、thread/reply/media/formatting、返回 receipt。durable intent、hook、retry/reconcile、audit 与最终 delivery result。
Transport-only 不等于“无策略”。插件仍拥有平台身份规范、DM/group 配置解释、native mention、thread grammar 和 API 限制；但不得拥有产品命令树、provider/model policy、Agent queue 或 feature-specific menu 推断。Typed presentation action 在 Core 声明，transport 只做原生编码。

3. 核心概念与术语

Durable-before-ack先把 raw envelope 写入 shared SQLite，再向平台 ack/推进 cursor；崩溃后由新 drain 恢复。
Event ID 与逻辑 replay keytransport delivery ID 用于 queue tombstone；当平台会用不同 event ID 表达同一逻辑消息（Slack message/app_mention twins）时另加 logical guard。
Lane同 conversation/chat/topic 的 claim 串行，不同 lane 可并行；它只保护 admission/dispatch ordering，不包裹整个 Agent turn。
AdoptionSession/reply lane 已持久接管 turn 的时刻。Ingress 在 adoption 完成 tombstone，不等待模型 settle。
Admissiondispatch | observeOnly | handled | drop 的闭合结果；preflight 可以在 Agent 前终止。
Route / Session / 投递上下文Route 选择 agent/session；Session 是持久对话；Delivery Context 携带 channel/to/account/thread，三者不可互换。
Presentationportable blocks/actions 与 channelData；插件按平台 capability 渲染，不从任意字符串猜产品命令。
Receipt一次逻辑发送产生的全部 platform message IDs、parts、thread/reply/edit/delete tokens；是 commit/audit 的确认依据。

5. 完整运行流程

5.1 成功路径：平台事件到确认回复

  1. Transport 验证并保留 raw envelope。Telegram webhook 先验 secret/body；Slack Receiver 包装 Events API；Discord 在 MESSAGE_CREATE gateway boundary 传 raw APIMessage。规范化延后到 durable claim。extensions/telegram/src/webhook.ts:450-487、extensions/slack/src/monitor/ingress.ts:324-338、extensions/discord/src/monitor/ingress.ts:146-153
  2. 持久化追加 后才 ack。Queue 插入 pending row；冲突返回 pending/claimed/completed/failed。Telegram 这之后回 200 或 polling 推进 offset；Slack 执行原 ack；Discord listener await append 后立即释放 Gateway event loop。src/channels/message/ingress-queue.ts:573-660、extensions/telegram/src/webhook.ts:481-493、extensions/slack/src/monitor/ingress.ts:269-275、extensions/discord/src/monitor/listeners.ts:68-77
  3. Claim 与 lane。Drain 恢复 stale claim，按 conversation lane 选择最早 pending；active/claimed/retry-delay lane 都阻塞同 lane 后继，不同 lane 最多按 startLimit 并行。src/channels/message/ingress-drain.ts:697-817
  4. Normalize 与 gates。Plugin 从 raw event 提取 body/media/sender/thread/mention facts；共享 access、command、mention policy 做准入。未提及群消息可记 history 后 drop；授权 command 可以显式 bypass mention。src/channels/turn/kernel.ts:189-250、src/channels/mention-gating.ts:157-181
  5. Route/Session/投递上下文。Plugin conversation grammar 产出 agent/session route；Core 设置 routeSessionKey、store path、FinalizedMsgContext，保留 account/to/thread 作为 delivery context。src/channels/turn/lifecycle.ts:21-47、src/channels/route-projection.ts:63-107
  6. Turn adoption 与 Agent dispatch。Core 先记录 inbound session；当 reply lane 接管时调用 onAdopted，Ingress tombstone 完成并释放 lane。Agent turn 可继续很久，Channel 不再持有 transport claim。src/channels/message/ingress-drain.ts:495-518、src/channels/turn/lifecycle.ts:132-227
  7. Presentation 与 durable outbound。Final ReplyPayload 经 transform、portable presentation、chunk/media/thread 规划；只有 adapter 声明所需 capability 才创建 durable send。平台发送返回聚合 MessageReceipt，随后 commit/audit。src/channels/turn/durable-delivery.ts:134-235、src/channels/message/types.ts:73-94

5.3 恢复路径：重启、重试、未知发送

  • 进程在 append 后、adopt 前崩溃：新 drain 回收过期 claim，重新 dispatch；tombstone 后同 event ID 不再 dispatch。src/channels/message/ingress-drain.test.ts:47-82
  • Turn deferred：claim 继续持有且 watchdog 继续；reply lane 后续 adopt 则 complete，未获得 lane 则 abandon/release 并增加 attempt。src/channels/message/ingress-drain.ts:519-549、src/channels/message/ingress-drain.test.ts:163-197
  • 瞬时 dispatch 失败：按 attempt floor + age gate 退避/release；达到策略或分类为 auth/invalid-event 时 dead-letter。人工 resubmit 重置 attempts 后只 dispatch 一次。src/channels/message/ingress-drain.ts:399-429、src/channels/message/ingress-drain.test.ts:85-123
  • 发送部分成功：错误标记 sentBeforeError/visibleReplySent，禁止 legacy fallback 重发；若 adapter 支持 reconcileUnknownSend，durable queue 可在重启后判定 sent/not_sent/unresolved。src/channels/turn/durable-delivery.ts:111-131、src/channels/message/types.ts:278-312

10. 安全与信任边界

  1. 先验证 transport，再写 queue。Webhook secret/signature、Slack/Discord installation identity、Telegram token 均由插件 owner 验证；Core queue 不把“可 JSON 化”当作可信。
  2. Raw envelope 是不可信输入。持久化后仍需 version/identity decode；normalize 只提取 owner 可证明字段，不把任意 nested object 注入 prompt。
  3. 访问控制早于 Agent。DM/group policy、allowlist、sender/actor identity、mention 与 command gate 在 route/dispatch 前终止。
  4. Native action 保持 typed。Approval/command/URL/web-app/select action 在 channel encoding 前必须可区分；raw callback data 不进入普通文本 turn。
  5. Route 不是授权。Session/delivery context 只回答“去哪”；Tool Policy、Approval、Sandbox 和 provider auth 仍由相邻 owner 执行。
  6. Outbound media 受 access policy。插件通过显式 media source params、local roots/readFile hook 获取媒体，不能任意读取 Gateway 文件系统。

禁止的捷径：Channel 不得因 callback value 以 / 开头就猜测命令，也不得把产品特性菜单硬编码到 Telegram/Discord/Slack transport。Core/owner plugin 产生 typed portable action，transport 只做原生映射。证据：AGENTS.md:98-101。

Telegram：extensions/telegram/src/telegram-ingress-spool.ts:84-120、extensions/telegram/src/outbound-adapter.ts:39-64；Discord：extensions/discord/src/monitor/ingress.ts:15-69、extensions/discord/src/outbound-adapter.ts:114-149；Slack：extensions/slack/src/monitor/ingress.ts:18-149、extensions/slack/src/outbound-adapter.ts:278-403。

核心权衡：平台在 ingress/ack/thread/presentation 上差异巨大，但 adoption、retry、dead letter、Turn Kernel 与 durable receipt 只保留一套。代价是 adapter capability 和生命周期契约较多；收益是可靠性 bug 能在 Core 修一次，而不是三个插件各造一套 claim loop。
已知限制与证据缺口：Durable ingress 保证 transport event 在 tombstone 窗口内不重复 dispatch，不保证任意 pre-adoption业务副作用 exactly-once；outbound 只有声明并实现 reconcile 的 adapter 才能消除部分未知发送。未现场验证三平台 API/UI、限流、真实重投、附件大文件与 thread 权限错误。
