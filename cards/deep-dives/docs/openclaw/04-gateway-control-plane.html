一句话目标：Gateway 是 OpenClaw 的单进程控制面与网络入口；它把配置、插件、Channel、RPC、事件和后台服务组织成一个有 generation 边界、可观察、可热更新、可优雅关闭的运行时，但不替代 Agent、Session、Channel 或数据库各自的业务所有权。

1. 模块定位

Gateway 是常驻 Node.js 进程中的控制平面。CLI 通过轻量入口动态导入完整服务器实现，避免只需要类型、连接信息或简单命令的调用方加载整张启动依赖图。真正的生命周期入口是 startGatewayServer()。证据：src/gateway/server.ts:1-35、src/gateway/server.impl.ts:579-582

边界Gateway 负责Gateway 委托/不负责
网络入口绑定 host/port，承载 HTTP、WebSocket upgrade、Control UI、探针、Hooks 与插件路由。不实现各平台协议；Telegram/Discord/Slack 等连接由 Channel plugin 所有。
控制请求注册 RPC descriptor，认证后按 Role、Scope、启动状态、限流和 admission 调度 handler。具体业务由对应 handler、Agent Runtime、Session、Node 或 plugin 执行。
运行时发布组织配置快照、插件 registry、prepared model runtime、Channel/service generation 的发布与退休。模型解析与 prepared store 的内部算法位于 src/agents/。
事件总线把内部生命周期投影为有 Scope、订阅、序列号和背压规则的 WS 事件。不是持久事件日志；客户端发现 gap 后必须重新读取权威状态。
后台服务决定启动/停止顺序，保存 cron、heartbeat、health monitor 等运行句柄。业务状态仍由 Cron、Task、Session、Channel 和 SQLite owner 管理。
进程生命周期启动失败清理、drain、shutdown event、资源关闭和 restart handoff。launchd、systemd、Windows Scheduled Task 的拉起策略由 daemon/OS supervisor 所有。
明确排除：第 5 章负责握手、Frame Schema、Device Proof、Pairing 与协议版本；第 7 章负责 Session 与路由；第 8 章负责 Agent Loop；第 14 章负责 Cron/Heartbeat/Hook 的业务语义。本章只说明 Gateway 如何承载、编排和隔离这些 owner。

3. 核心概念与术语

Gateway generation从一次 startGatewayServer 到对应 close 的完整生命周期。内部 principal、pinned registry、socket、timer 与 sidecar 都绑定这一代；关闭后不能继续 dispatch。
Runtime config snapshot通过加载、校验、SecretRef 激活和启动覆盖得到的当前内存配置。成功 reload 才发布；无效磁盘内容不会替换活动快照。
Prepared runtime generation预解析的 provider/auth/model/catalog 事实。Gateway 拥有启动和 reload 时机；src/agents/ 拥有具体 store 和 materialization。
Sidecar依附 Gateway 生命周期、但不是监听 socket 本身的服务，例如 Channels、plugin services、memory startup、Gmail watcher 和清理任务。
Readiness ≠ LivenessLiveness 只证明进程能处理浅 HTTP；Readiness 还检查 startup sidecars、draining 和 Channel 运行状态。
Root work admission请求与后台事务进入 Gateway 根工作集合的门。Suspend/restart/close 通过关闭或等待该门，避免新工作越过生命周期边界。
Advertised methods客户端发现用的保守列表，不等于把所有内部 helper 自动暴露为 RPC。真正 dispatch 以 attached/live 方法 registry 为准。
Hot reload recovery debt配置已提交但后续 owner 替换失败时，当前进程被视为可能不一致；受管重启承担恢复责任，而不是静默继续。

5. 完整运行流程

5.1 正常启动与 ready 路径

CLI → 懒加载 server.impl → 归一化 state 目录 + DB schema 预检 → 读取/校验 config 快照 → 激活 Gateway 拥有的密钥与认证 → 引导 plugin 元数据/运行时 → 解析 bind/auth/TLS/HTTP 设置 → 创建 ChannelManager + 实时状态 → 创建 HTTP(S) 服务器 + noServer WebSocketServer → 挂载 upgrade handlers → 启动早期运行时 + 订阅 + handlers + 请求上下文 → 挂载 WS 连接/消息 handlers → 监听每个已解析的 host → 标记内部 dispatch 就绪 → 发布预备模型运行时 → 恢复主 sessions → 启动 Channels → 启动 plugin 服务与可选 sidecars → 标记 sidecars 就绪 → 激活 heartbeat/recovery/pricing；延后 maintenance/Cron → 启动 config reloader → readiness 达到 true 条件
  1. Fail-fast preflight。先检查 shared/per-agent SQLite schema；发现由更高版本写入的 schema 立即拒绝，无法静态判断的 DB 才继续到真实 open。src/gateway/server.impl.ts:583-625
  2. 构造有效配置。配置读取、Control UI origin seed、SecretRef 激活、auth override 和诊断开关先完成；之后才解析 bind、TLS 和 HTTP feature。src/gateway/server.impl.ts:656-790、src/gateway/server.impl.ts:1043-1145
  3. 先挂 handler，再暴露端口。WebSocketServer({noServer:true}) 与 HTTP upgrade handler 在 listen 前建立，避免连接到达但 upgrade 尚未安装导致 1006。多 bind host 中可信 loopback alias 优先占用。src/gateway/server-runtime-state.ts:285-338、src/gateway/server-runtime-state.ts:442-509
  4. 控制面先可连接，业务能力分阶段 ready。监听成功后内部 dispatch 才启用；sidecar 尚未完成时 readiness 为 false，依赖 sidecar 的 RPC 返回带 retryable/retryAfterMs 的 UNAVAILABLE。src/gateway/server.impl.ts:2130-2174、src/gateway/server-methods.ts:947-959
  5. Prepared runtime 先于 Channel。静态 provider/model/auth 事实先发布，随后标记上次重启遗留的 main session，再启动 Channel；单个 Channel 失败记录日志但不让整个控制面退出。src/gateway/server-startup-post-attach.ts:638-681
  6. Plugin service 在 Channel 之后。Channel 完成或被显式跳过后释放 account-start barrier，再启动 plugin services；失败隔离为 null handle。src/gateway/server-startup-post-attach.ts:683-707
  7. 定时服务受双门控制。post-attach 返回且 sidecars ready 后才启动 heartbeat、session delivery recovery、outbound recovery 和 pricing；Cron/maintenance 再以低优先级延迟启动。src/gateway/server.impl.ts:2182-2210、src/gateway/server.impl.ts:2328-2485
  8. 最后建立 reload owner。配置 watcher 获得当前 snapshot、活动 runtime state、Channel/plugin 替换函数与受管重启回调。src/gateway/server.impl.ts:2347-2436

5.2 一次 RPC 的成功路径

WS frame 请求 → frame/schema 校验（第 5 章） → attached/live 方法 registry → Role + Scope 授权 → pairing generation / 启动可用性 → 控制面写入限流 → root work 准入 → handler 所有者 → response + 可选 events → 释放准入

Registry 把 core、plugin 和 aux handler 统一成 descriptor。若连接附带的 registry 不拥有某个方法，dispatch 会从 live plugin registry 重建，避免插件 reload 后新 RPC 不可达；授权和实际 handler 始终来自同一 registry snapshot。证据：src/gateway/server-methods.ts:875-928

5.4 配置热更新与恢复路径

文件系统/写入通知 → debounce 300 ms → 读取完整快照 + includes + plugin 安装记录 → 拒绝缺失/无效/已被取代的候选 → diff 路径 → reload 计划 ├─ none：仅发布 source/lifecycle 通知 ├─ hot：预检所有可能失败的替换 │ → 同步提交边界 │ → 退役旧的预备运行时 + 发布 config/state/lanes │ → 刷新预备运行时 + 重启选定的所有者 │ → 提交后失败：请求受管 restart └─ restart：校验候选 → 延后至活跃工作排空 → 通知后继者

当前运行时只把 off 和 hybrid 当作有效 mode；其他类型值回落到 hybrid，debounce 固定为 300 ms。hybrid 并不表示所有字段热更新：planner 按最长前缀规则把变更分成 hot、restart 或 none，插件/Channel 可贡献更窄规则。证据：src/gateway/config-reload-settings.ts:11-20、src/gateway/config-reload-plan.ts:68-143、src/gateway/config-reload-plan.ts:150-242

提交边界不是“旧 prepared runtime 与新配置永远同时可读”。实际做法是在同步 commit edge 将旧 prepared store 标记 stale 并门控等待替代，然后发布 config、state 与 lane；紧接着刷新新 prepared runtime。若刷新或不可逆 owner 替换在 commit 后失败，reloader 记录 recovery debt 并请求受管重启。证据：src/gateway/server-reload-handlers.ts:635-697、src/gateway/server-reload-handlers.ts:711-789、src/gateway/server-reload-handlers.ts:952-965

5.5 优雅关闭与重启路径

  1. close prelude 立即禁止新 generation dispatch，使 Cron reconciliation、延迟 Channel recovery 和内部 principal 无法进入退休 context。
  2. 停止 config watcher，并等待最后一个 reload transaction；随后清理 gateway-lifetime/post-ready sidecars。
  3. 执行 gateway_stop plugin hook；hook 失败只记录 warning。
  4. 重启场景先等待 pending replies、active runs 和 queued turns；预算耗尽时标记 main session recovery，再 abort 可中止工作。
  5. 广播规范化 shutdown metadata，停止 plugin services、Channels、Cron/heartbeat/timers，关闭 WS client 与 HTTP server。
  6. 释放 pinned registry、MCP/LSP runtime、Secret snapshot、rate limiter 和 fallback context；单步失败继续后续清理并汇总 warning。

证据：src/gateway/server.impl.ts:1429-1584、src/gateway/server.impl.ts:2505-2533；关闭预算与 warning：src/gateway/server-close.ts:36-54、src/gateway/server-close.ts:85-107、src/gateway/server-close.ts:223-256。

6. 数据与状态模型

Gateway 同时持有可重建的进程内控制状态和跨重启持久业务状态。两者不能混写：socket/client、cache、timer 与 registry 属于 generation；Session、Cron、Approval、Audit 等权威行属于其 SQLite owner。

7.2 RPC registry 与授权顺序

Core method 通过 descriptor 明确 owner、scope 和分类；plugin method 来自 active registry；没有 descriptor 的 aux handler 默认按 admin 收紧。连接的 Role/Scope、Node pairing generation、startup availability、write rate limit 和 root admission 都在业务 handler 之前执行。证据：src/gateway/server-methods.ts:320-356、src/gateway/server-methods.ts:875-1005

7.3 广播、订阅与确认语义

  • Scope fail-closed：内置事件必须出现在 guard 表；未知非 plugin.* 事件不广播。Plugin event 只能使用 plugin.* namespace 且必须声明 read/write/admin scope。
  • Session 隔离：声明 session-scoped capability 的浏览器客户端只收到 authoritative subscription registry 中匹配 session 的事件，避免 sibling tab 泄露。
  • 序列号：普通广播按 client 递增 seq；targeted event 不携带全局序列。服务端不 replay。
  • 背压：连接 bufferedAmount 超过 50 MiB 时，可丢事件的流跳过该帧但推进 seq；不可丢事件关闭慢消费者，code 1008。
  • 幂等：agent/chat.send 等副作用请求以协议 idempotency identity 进入 dedupe；重复请求返回 cached/reserved/terminal 结果。它是短期进程内保护，不是跨重启 exactly-once。

事件目录：src/gateway/server-methods-list.ts:38-81；guard/订阅/背压：src/gateway/server-broadcast.ts:33-150、src/gateway/server-broadcast.ts:206-267；dedupe identity：src/gateway/server-methods/agent-dedupe.ts:5-24。

9. 并发、性能与资源

机制真实行为开发含义
Lazy loadingserver implementation、HTTP endpoint handler、Hooks、plugin HTTP、模型 pricing 等按需导入。不要从轻量 entry 静态导入完整 runtime；修改 lazy boundary 后需 build 验证 dynamic import。
Listener 幂等startListeningPromise 合并并发启动；一旦失败，该 runtime state 由 startup owner 整体销毁。不要在失败 state 上局部重试 bind。
多 bind host每个 resolved host 有独立 HTTP server，共享 WS/runtime state；必要的 loopback alias 先绑定。close 必须遍历全部 HTTP server；部分 alias 失败只在允许时降级。
请求 admissionHTTP、RPC、independent background work 都进入 Gateway work fence；restart/suspend 可等待或阻止新工作。新增副作用入口必须接入对应 admission helper。
Control-plane write 限流按 method + device/IP 建 60 秒窗口，每窗口 30 次；最多保留 10,000 个 bucket，过期 bucket 由 maintenance 清理。只保护 descriptor 标记的 control-plane write；客户端应遵守结构化 retryAfterMs。
Pre-auth WS 预算默认每 IP 32 条未认证连接；未知 IP 共用 fail-closed bucket。message handler 惰性导入期间只排队 16 帧，溢出 close 1008。新增握手前工作不得绕开 budget，也不能扩大无界内存队列。
配置 transaction候选按 epoch 串行；新候选可 supersede 旧候选；stop 等待活动 transaction。不要在 watcher 回调外平行修改 runtime owners。
事件背压25 MiB post-auth payload 基线；50 MiB per-connection send buffer；pre-auth 64 KiB。大结果应分页/流式；事件需声明能否 dropIfSlow。
Health 合并并发普通/敏感 refresh 各共享一个 Promise；缓存命中后仍后台刷新。健康检查避免重复昂贵 probe。
低优先级维护post-ready timer 与 idle task 使用 unref timer；busy 时延迟 retained plugin cleanup。非紧急维护不得与 turn 热路径争用。
Close budgetsWS、HTTP、MCP/LSP、hook 和 restart drain 均有源码定义的有界等待。资源 stop API 必须可等待、可超时且可重复调用。

10. 安全与信任边界

  1. Bind 前安全配置。非 loopback 需要实际可用的 shared secret 或可信代理；trusted-proxy 必须有 allowlisted proxy；Tailscale funnel 必须 password auth。配置缺失时拒绝绑定，而不是先监听再警告。src/gateway/server-runtime-config.ts:125-185
  2. 浏览器 origin。非 loopback Control UI 必须显式 allowed origins，除非操作者启用标记为危险的 Host-header fallback。src/gateway/server-runtime-config.ts:140-174
  3. 协议认证与授权分离。握手建立 client identity；每个 RPC 再按 Role、Scope 和动态 pairing generation 判断。通过握手不等于获得所有方法。src/gateway/server-methods.ts:320-356、src/gateway/server-methods.ts:928-945
  4. 事件最小披露。广播在 server 端按 Scope/Role/subscription 过滤；Readiness 细节只向本地直连或已认证 remote caller展示。src/gateway/server-broadcast.ts:101-150、src/gateway/server-http.ts:242-267
  5. Generation 隔离。内部 principal 在 bind 后才可用，close prelude 立即失效；reload 后 stale auth client 被断开，旧 plugin registry 被 release。src/gateway/server.impl.ts:1154-1157、src/gateway/server.impl.ts:1429-1437
  6. Secret 不写回事件。健康 snapshot 只有 admin caller 才可看到 config path、state dir 和 auth mode；readiness 对未认证 remote caller隐藏 subsystem 名。src/gateway/server/health-state.ts:24-55

15. 设计权衡与已知限制

问题当前选择收益成本/失败模式重新评估条件
个人部署的控制面复杂度单进程模块化单体。部署简单、低延迟、共享 transaction/admission。composition root 大；单进程故障影响面广。出现必须独立扩缩容或强故障域隔离的 owner。
HTTP 与 WS 部署主端口复用。只需一个入口、auth 和 tunnel。router/auth 顺序更敏感；辅助 sandbox/worker 仍需额外 port。安全域或流量特征要求物理 listener 分离。
启动速度lazy import + 分阶段 ready。轻量 CLI 快，socket 可较早接受控制请求。“listening”不等于所有业务 ready；客户端必须处理 retryable unavailable。客户端普遍无法正确处理 phased readiness。
配置更新一致性planner + transaction + stale gate + restart recovery。大部分变化无需手工重启，避免混 generation。实现复杂；commit 后 owner 失败需要 recovery debt。配置面缩小到只需 immutable restart，或可引入更简单 owner protocol。
事件可靠性有序 best-effort WS，不持久 replay。低开销，适合 UI/状态投影。断线和慢消费者会 gap。事件本身成为不可丢业务事实；届时应引入 owner-owned durable ledger，而非无限内存队列。
多 Gateway单机通常一个；通过 port/config/state/workspace 隔离多个实例。支持 rescue/isolation 而不引入集群协调。没有自动跨实例一致性或 failover；误连会造成 auth/state 混淆。需要同一业务状态的 active-active 集群。
当前限制：server.impl.ts 仍是超大 composition root，并带有 grandfathered max-lines 抑制；它准确表达全生命周期，但增加了变更审查成本。拆分必须保持单一 owner 和现有顺序，不应为了文件变小引入第二套启动路径。src/gateway/server.impl.ts:2535
