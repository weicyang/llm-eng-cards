1. 模块定位

核心结论：Trae 的提示工程是“文本指导 + Tool API 描述 + Runtime 协议”三层协作。System Prompt 能诱导模型按步骤工作，但不能保证执行顺序、路径安全、验证真实发生或任务完成；可执行约束必须由 Tool、Executor 和 Agent Loop 落地。
边界负责委托明确不负责
trae_agent/prompt/拥有 TRAE_AGENT_SYSTEM_PROMPT 文本。消息装配交给 TraeAgent.new_task。不生成 Tool JSON Schema，不执行工具，不判定终态。trae_agent/prompt/agent_prompt.py:4-53
TraeAgent创建 System/User 初始消息，定义默认工具集合、task_done 完成信号和 must_patch 门禁。循环交给 BaseAgent，协议转换交给 Provider Adapter。不持有 Provider 原生完整历史。trae_agent/agent/trae_agent.py:21-27,102-178,228-249
Tool / ProviderTool 提供名称、描述、参数；Adapter 转成 Provider 原生 Schema 和消息。执行副作用交给具体 Tool。Schema 不等于授权、沙箱或业务完成证明。
相邻模块Context、Agent Loop、Tool Framework、Provider Adapter 分别拥有历史、循环、执行和协议。详见 05 Context Engineering、07 Agent Loop、04 Tool Framework、13 Provider 抽象层。本页不重复其内部资源生命周期。

3. 核心概念与术语

术语当前准确含义不要混淆为
系统提示词文本（System Prompt）一个英文字符串常量，描述绝对路径、Bug 修复步骤、验证、总结、Sequential Thinking 和 task_done 使用建议。可执行策略、状态机、权限系统。
任务/用户提示词（Task/User Prompt）new_task 动态拼接 Project Root 与可选 Issue；传入的 task 字段本身不直接拼入该消息。System Prompt 或 CLI 原始命令的逐字镜像。trae_agent/agent/trae_agent.py:103-144
API Tool SchemaTool 的 name/description/JSON Schema，经 Provider Adapter 放入请求的 tools/function declarations。自然语言 Prompt 文本；它不写入 System Prompt。
运行时协议ToolCall 解析、Executor 路由、task_done 检测、must_patch 检查、最大步数和异常终态。模型“应当”遵循的建议。
规划（Planning）System Prompt 的方法步骤和 Sequential Thinking Tool 描述中的“planning and design”。强制进入/退出的 Planning 状态；AgentStepState 没有 PLANNING。trae_agent/agent/agent_basics.py:19-35
ReflectBaseAgent 提供失败结果反思 Hook。Trae 默认阶段；TraeAgent.reflect_on_result() 恒返回 None。trae_agent/agent/trae_agent.py:176-178
Compaction对历史做摘要、裁剪或替换的 Context 策略。Prompt 中要求简洁、Lakeview 摘要或局部 Tool 输出截断；当前主 Prompt/Runtime 没有通用 Compaction。

4. 架构组成

4.1 Trae System Prompt

TRAE_AGENT_SYSTEM_PROMPT 包含七段工作指导：理解问题、探索定位、先复现、诊断、实现、严格验证和总结；另要求所有带 file_path 的工具使用基于 Project Root 的绝对路径，建议充分使用 Sequential Thinking，并在确认解决后调用 task_done。这是固定文本，没有模板变量、Provider 分支、语言选择或配置覆盖接口。trae_agent/prompt/agent_prompt.py:4-53

“must / should” 不等于强制：Prompt 写了“必须先创建复现脚本”“验证后才能 task_done”，但 Runtime 不检查是否创建过脚本、是否执行过测试，也不维护规划阶段。它只对 task_done ToolCall 与可选非测试 Patch 做有限门禁。

4.2 初始消息与工作区约束

new_task 每次创建两条内部消息：System 内容来自 get_system_prompt()；User 内容包含 [Project root path]，Docker 模式使用字面量 \workspace，有 Issue 时再拼接 [Problem statement]。缺少 extra_args 或 project_path 会在请求 Provider 前拒绝。trae_agent/agent/trae_agent.py:122-144,172-174

4.3 Tool 描述、Schema 与真实执行

默认工具名称为 edit、sequentialthinking、json_edit、task_done、bash；但当配置已构造非空 _tools 时使用配置集合。每个 Tool 的描述和参数通过 Tool.get_input_schema() 进入 API Schema。OpenAI 模式把所有字段列为 required，并用 nullable 表达可选项，同时加 additionalProperties:false；其他 Provider 使用普通 required 集合。trae_agent/agent/trae_agent.py:21-27,112-119；trae_agent/tools/base.py:120-175

task_done 的 Schema 无参数，描述要求验证后调用，执行本身只返回 “Task done.”；Agent 在执行 Tool 之前就根据 ToolCall 名称识别完成。因此完成语义主要由 Agent Hook 拥有，不由 Tool 的输出拥有。trae_agent/tools/task_done_tool.py:9-33；trae_agent/agent/base_agent.py:225-236

4.4 Sequential Thinking 与 Lakeview Prompt

System Prompt 指导模型按需调用 sequentialthinking，Tool 自己保存 thought_history 和 branches，并校验字段类型与最小编号；它是可调用 Tool，不会控制 BaseAgent 状态转换，也不会自动触发。trae_agent/tools/sequential_thinking_tool.py:32-98,101-157,163-247,277-319

Lakeview 的两个 Prompt 只把已发生的 Step 转成短任务描述与标签。它们不进入主 _initial_messages，不产生 Agent Reflection，也不压缩 Provider History。trae_agent/utils/lake_view.py:16-55,94-175,194-209

5. 完整运行流程

5.1 正常成功路径

1创建任务
new_task 选择工具，组装固定 System Prompt 与动态 Project Root/Issue User Message。
2首轮适配
BaseAgent 传两条初始消息和 Tool 对象；Adapter 分离/保留 System，并单独生成 Provider Tool Schema。
3模型决策
模型可输出文本和 ToolCall；Planning/复现/验证顺序只由 Prompt 引导，不由状态机校验。
4工具执行
非 task_done ToolCall 经 Executor 路由；结果转换为下一轮 Provider 原生 Tool Result。
5继续循环
Trae 不追加 Reflection；下一轮只有 Tool Result 或 Runtime 的固定未完成消息作为增量。
6完成信号
响应中任一 ToolCall 名为 task_done 即触发完成候选。trae_agent/agent/trae_agent.py:228-233
7Runtime 门禁
must_patch != "true" 时直接完成；否则读取 Git diff、移除测试路径 Patch，非空才完成。
8终态
成功写入 AgentExecution.final_result；内容来自模型 response content，而不是 task_done Tool 输出。

5.2 拒绝与提前结束路径

触发所属层即时行为最终影响
缺 Project PathRuntime 输入准入AgentError，不发送 Prompt。任务未开始。
模型无 ToolCall 且未完成Runtime 回路追加固定 User Message：尚未完成。继续至完成/异常/最大步数。trae_agent/agent/base_agent.py:314-325
task_done + must_patch + 空非测试 PatchRuntime 强制门禁追加 “ERROR! Your Patch is empty...” User Message。拒绝完成并继续。trae_agent/agent/trae_agent.py:235-249
达到 max_stepsRuntime 终态不再请求模型。Execution ERROR。trae_agent/agent/base_agent.py:179-181
Provider/Schema/Tool 异常Adapter 或 ExecutorProvider 异常可通用重试；Tool 异常归一为失败 Result。重试耗尽则 Step ERROR；Tool 失败继续下一轮。

5.3 重试、恢复与降级

Provider 请求会按相同 Prompt、历史和 Schema 重试，最多 max_retries + 1 次；Prompt 不参与错误分类、降级或跨 Provider 切换。Tool 失败以 Result 返回，但 Trae 的 Reflection Hook 返回 None，因此没有默认自动反思文本，恢复依赖模型读取 Tool Error 后自行改进。trae_agent/utils/llm_clients/retry_utils.py:13-55；trae_agent/agent/base_agent.py:337-352

9. 并发、性能与资源

  • 主 Prompt 在每个任务首轮进入 Provider History；后续步骤依赖 Provider 历史复用，不由 BaseAgent 重发完整文本。
  • Tool Schema 每轮按当前 Tool 列表重新构建并发送；工具描述越长、工具越多，请求固定负载越大，但仓库没有 Schema Token 预算或按需工具发现。
  • System Prompt 与 Tool Schema 都没有缓存层或版本哈希；Tool 的 cached properties 只缓存单个 Tool 实例的 name/description/parameters。
  • Sequential Thinking 的 thought_history 是无锁可变内存；当前单 Agent 串行 Tool 回路通常不并发访问，但同一实例不应跨并发任务共享。
  • parallel_tool_calls 可并发执行副作用工具；Prompt 中的顺序指导不会强制它们串行。trae_agent/tools/base.py:238-244
  • 没有 Prompt 长度预检、通用 Compaction、历史 Pruning、背压或 Context Window 余量计算；无法从源码给出容量或延迟数字。

10. 安全与信任边界

威胁面当前数据流/行为现有控制缺口与开发要求
用户 Prompt InjectionIssue 文本直接进入 User Message，可要求忽略 System、泄露数据或调用危险工具。角色优先级由 Provider 协议表达；没有内容过滤。System Prompt 不是可靠防线；高风险工具需独立授权、路径和命令策略。
仓库内容 Injection模型通过 Bash/Edit/View 读取 README、源码、测试或恶意指令文件；Tool Result 回到历史。内容被标记为 Tool Result，但未做“数据而非指令”隔离。把仓库内容视为不可信；不要因文件内文字扩大权限或泄露 Secret。
Tool 参数与副作用模型生成参数，Executor 调用 Shell、文件编辑、Docker 或 MCP。JSON Schema 约束基础形状；具体 Tool 有局部校验。Schema 不授权副作用；OpenAI strict 也不阻止危险但合法的命令。需要最小权限、确认/allowlist、沙箱和审计。
绝对路径规则System 要求使用 Project Root 拼绝对路径。仅自然语言约束；不同 Tool 有自己的路径实现。不能据此断言防目录穿越或限制在 Workspace；必须在 Tool/Executor 层规范化和校验。
Prompt/代码外发System、Issue、Schema、源码和 Tool Result 可发送给配置的 Endpoint。无字段级脱敏或域名 allowlist。自定义 base_url 是高信任配置；发送前治理 Secret、许可证和数据驻留。
完成欺骗模型可在未测试时调用 task_done。Tool 描述要求先验证；可选 must_patch 只检查非测试 diff。Runtime 不证明测试执行、结果通过、Patch 正确或副作用安全；关键场景需可验证验收门禁。
Sequential Thinking 数据thought 文本回传为 Tool Result/保存在内存，可能含敏感分析。无脱敏、保留策略或访问控制。Trajectory/日志和 Provider 数据政策需覆盖该内容。
Fail-open 边界：提示遵循失败通常不会触发结构化错误；模型跳过复现、测试或规划仍可继续。Fail-closed 边界：缺 Project Path 会拒绝启动，未知 Tool 返回失败 Result，must_patch 精确启用时空非测试 Patch 拒绝完成。两者不能混写成“Prompt 已保障安全”。

兼容性重点不是 Prompt 字符串能否被所有 Provider“原样发送”，而是语义在不同原生协议中是否保留。OpenAI/Ollama/OpenAI-compatible 保留 system role；Anthropic/Google 将其移入独立字段。修改 System Prompt 时必须在这些路径分别验证，不能把一个 Provider 的成功当作统一契约。

12. 可观测性与排障

12.1 当前可见信号

  • Trajectory 的 LLM Interaction 记录本轮内部消息、归一响应、Provider、Model 与可用 Tool 名；不是 Provider 原生 HTTP 请求或完整 Tool Schema 快照。
  • Agent Step 记录 LLM response、ToolCall/Result、reflection 与 error；Trae 默认 reflection 为 None。
  • Lakeview 可展示“正在做什么”的短摘要和标签，但不证明真实流程满足 Prompt，也不进入主模型 Context。
  • Console 展示 Step/Token/Tool 状态；没有 Prompt 版本、System 文本哈希、Schema 哈希、Injection 告警或“已完成测试”结构化字段。

15. 设计权衡与已知限制

当前选择收益成本/失败模式何时重新评估
单一固定 System Prompt行为基线简单、可读、易修改。无法按任务/Provider/语言版本化；修改影响全局且缺快照测试。需要专业 Agent、A/B 评估或稳定版本治理时。
自然语言工作流程指导无需复杂编排，可让模型灵活调整。Planning、复现、验证均可能跳过；难以形成可审计保证。任务需要合规门禁、确定性阶段或高风险副作用时。
Tool 描述与 Schema 独立于 PromptProvider 原生 Function Calling，参数结构清晰。多 Provider Schema 方言、每轮负载、描述与执行可能漂移。工具数量增长、按需发现或严格能力治理时。
task_done Tool 作为完成信号比自然语言关键词明确，Provider 可结构化返回。Tool 自身不验证；混合 ToolCalls 被短路；验证要求主要靠描述。需要结构化验收证据、人工确认或事务完成时。
must_patch 的最小 Runtime 门禁可拒绝没有非测试变更的完成。不证明正确性；依赖 Git diff；字符串布尔值；只过滤启发式测试路径。需要可重复验收、非 Git 工作区或多产物任务时。
Trae 覆写关闭 Reflect避免把框架生成的额外文本混入历史，回路简单。失败 Tool Result 没有显式反思阶段。评估证明结构化 Reflect 能提升恢复且不引入漂移时。
Provider 保留原生 System 语义适配各 SDK 的最佳协议形状。同一 Prompt 的位置、历史和 Tool strict 行为并不完全等价。需要统一请求快照、迁移或跨 Provider 一致性认证时。

当前已证实的限制

  • Planning 是 Prompt/Tool 描述约束，不是 Agent 强制状态机。
  • Trae 默认不执行 Reflect；框架虽有 Hook 和 REFLECTING 枚举，Trae override 恒返回 None。
  • Prompt 层没有通用 Context Compaction、Pruning、Token 预算或摘要回灌。
  • System Prompt 不动态注入 Tool Schema；两者由 Provider 请求的不同部分承载。
  • 验证前不得完成、绝对路径和方法步骤主要是软约束；Runtime 只实现有限准入和 Patch 门禁。
  • Provider 对 System role、Tool Schema strict、内建 Tool 与消息历史的适配存在实质差异。
  • 没有 Prompt 版本、哈希、行为评估门禁、Injection 检测或通用 Tool 权限策略。
