1. 模块定位

准确定义：Docker 模式是 trae-cli run 的可选 Tool 执行后端。Agent、LLM Provider、Trajectory、Console、MCP 发现以及未被代理的 Tool 仍运行在 Host Python 进程。
边界负责委托明确不负责
CLI四种来源互斥校验、Docker 可达性探测、首次工具打包、把工作区放入临时字典。配置解析给 Config；生命周期给 Agent。不拥有容器运行循环，也不提供 Docker YAML Schema。
DockerManager构建/加载/创建/接入、RW mount、工具复制、持久 Bash、执行和有条件清理。镜像与容器语义给 Docker daemon/SDK/CLI。不做 Tool 参数校验、策略授权、资源配额或网络策略。
DockerToolExecutor按精确 Tool 名路由，翻译名为 path 的参数，组装命令，统一返回 ToolResult。其余 Tool 给本地 ToolExecutor。不是通用“任意 Tool 容器化”框架。
BaseAgent选择 Executor、任务前启动、任务 finally 中按 docker_keep 决定 stop。Tool 语义给具体 Tool/Executor。默认不强制销毁容器，不校验镜像可信度。

公共跨界接口是 DockerManager.start/execute/stop 和 Executor 的 sequential_tool_call/parallel_tool_call/close_tools。trae_agent/agent/base_agent.py:24-73,147-207；trae_agent/agent/docker_manager.py:10-242

2. 系统位置与依赖

trae-cli run四选一参数 + working-dir
→
Agent / BaseAgentHost 进程与生命周期
→
DockerToolExecutor三类远端 / 其余本地
→
DockerManagerSDK + docker CLI + pexpect
→
Container/workspace + /agent_tools
Host 控制面LLM 请求、Agent Loop、Tool Schema、CLI 和 Trajectory 不搬入容器；Docker 只承接指定 Tool 的副作用。
兄弟实现无 Docker 配置时使用本地 ToolExecutor；其并行入口用 asyncio.gather，Docker 包装器则把同一入口改为串行。
外部依赖docker==7.1.0 与 pexpect==4.9.0 锁定在 evaluation extra；Manager 同时调用系统 docker CLI。
平台边界持久 Shell 硬编码 /bin/bash、docker exec -it 与 PTY prompt；镜像必须具备相应 Linux 用户空间行为。

依赖声明见 pyproject.toml:29-42、锁文件 uv.lock:327-338,951-960。尽管属于 extra，BaseAgent 顶层导入 DockerManager，因此未安装这些依赖时普通本地路径也可能在模块导入期失败；“可选后端”不等于“依赖加载完全延迟”。

3. 核心概念与术语

术语当前含义易错结论
Docker 模式四个 CLI 来源参数任一非空后构造 docker_config。不是默认模式，也不支持 interactive 命令启用。
Managed container本次从 image/build/load 创建，_is_managed=True。“managed”不表示默认自动删除；默认 docker_keep=True。
Attached container按 ID 获取已有容器，_is_managed=False。不会新增 Workspace mount；即使调用 stop 也不停止/删除该容器。
工作区挂载（Workspace Mount）仅新建容器且 CLI 原始 working_dir 非空时，把 Host 路径以 rw bind mount 到 /workspace。不是只读副本；未显式传 -w 时 CLI 后续虽把任务路径设为 cwd，早先写入 Docker 字典的仍是 null，因此不挂载。
Tool copyHost trae_agent/dist 经 docker cp 复制到 /agent_tools。不是 mount，不会随 Host 打包产物变化自动同步。
Path translation仅顶层参数名恰为 path 且位于 Host 工作区内时映射到容器根。不是通用路径重写；file_path、命令文本和嵌套字段不翻译。
Sandbox在容器 namespace/文件系统环境中执行部分命令。源码没有声明或实现完整的恶意代码安全边界。

4. 架构组成

4.1 CLI 选择与预检

run 接受 image、container ID、Dockerfile、image tar 四种互斥来源。命中后调用系统 docker version，再以目录存在性判断是否需要运行 PyInstaller 构建。没有来源时完全走本地 Executor。trae_agent/cli.py:53-116,126-275

4.2 Agent 装配

Agent → TraeAgent → BaseAgent 原样传递字典和 docker_keep。BaseAgent 始终先创建本地 Tool 列表与 ToolExecutor，Docker 模式再套一层代理；因此本地回退是组合关系，不是另一个 Agent。trae_agent/agent/agent.py:14-57；trae_agent/agent/base_agent.py:29-73

4.3 DockerManager

Manager 保存 SDK client、来源、工作区、工具目录、container/shell 句柄和所有权标志。start() 先解析来源，再创建/接入容器，随后复制工具并启动持久 Bash。四种来源虽在 CLI 互斥，但构造器本身只检查“至少一个”，不再次执行互斥校验。trae_agent/agent/docker_manager.py:18-43,45-126

当前工作区没有独立的 docker_utils.py 或 docker_config Schema；相关 helper、临时字典和生命周期分别落在 cli.py、docker_manager.py、base_agent.py 与 docker_tool_executor.py。本文不把历史/设想中的同名模块写成当前实现。

4.4 DockerToolExecutor

容器代理名单在 BaseAgent 中硬编码为 bash、str_replace_based_edit_tool、json_edit_tool。第一类直接发送命令，后两类调用复制的可执行文件；sequentialthinking、task_done、CKG、MCP 和任何新增 Tool 仍由 Host Executor 运行。trae_agent/agent/base_agent.py:65-71；trae_agent/tools/docker_tool_executor.py:57-163

实现范围缺口：json_edit_tool 的公共参数名是 file_path，但翻译器只识别 path；当前代理会把 Host 路径原样传给容器。该差异由 trae_agent/tools/json_edit_tool.py 的 Schema/测试与代理实现共同证明，不能把 JSON 路径翻译描述为已完成。

5. 完整运行流程

5.1 新建容器成功路径

1触发
run 收到一个 Docker 来源；互斥通过后形成临时 docker_config。
2预检
检查 CLI/daemon；打包目录不满足条件时同步运行 PyInstaller 和文件复制命令。
3工作区
CLI 先把原始 working-dir（可能为 null/相对路径）写入 Docker 字典，之后才创建并绝对化任务路径；Docker 模式不执行 Host chdir，也不回写规范化值。
4装配
BaseAgent 创建 Manager 与代理；此时容器尚未启动。
5启动
任务执行前 build/load（如需）、containers.run 创建 sleep infinity 容器并 RW mount 到 /workspace。
6工具准备
docker cp 复制二进制；pexpect 运行 docker exec -it … /bin/bash 并等待 $ 或 #。
7执行
每个 Tool Call 依次路由；命令后发送 marker，匹配退出码并过滤回显，生成 ToolResult。
8结束
若 docker_keep=False，finally 关闭 PTY、停止并删除 managed container；默认 true 则容器继续运行。

5.2 拒绝与提前结束

  • 同时给多个来源：CLI 在配置和 Agent 构造前打印错误并退出，不创建容器。trae_agent/cli.py:225-240
  • Docker CLI 缺失、daemon 不可达或权限不足：预检退出；但该探测只证明一次 docker version，不证明后续 build/run/cp/exec 权限。
  • Dockerfile/image tar 的 Click 类型先验证文件存在并解析绝对路径；image 字符串和 container ID 没有 CLI 格式校验。
  • 普通任务输入/配置错误可能发生在 Agent 创建前；已创建 Manager 也不代表已经分配容器。

5.3 故障恢复路径

Tool 命令构造或执行异常被代理捕获并转换为失败 ToolResult，Agent 可在下一步继续；若持久 Shell 已死亡，下次执行尝试重启。相反，DockerManager.start() 在 BaseAgent 主 try/finally 之前调用，启动阶段异常不会进入 Agent 的有条件 stop；若容器已创建后工具复制或 Shell 启动失败，当前实现没有回滚清理。trae_agent/agent/base_agent.py:147-188；trae_agent/agent/docker_manager.py:121-126,204-224

7. 接口、协议与事件

接口输入输出/状态变化错误语义
DockerManager(...)四来源、workspace、tools、interactive创建 SDK client；不启动容器无来源 ValueError；daemon 初始化错误可直接抛出
start()实例配置image/container/shell 依次就绪只专门打印并重抛三类 Docker 错误；其他异常原样传播
execute(command, timeout=300)Shell 字符串(exit_code, output)无 container 抛 RuntimeError；超时返回 -1，不抛错
stop()无关闭 shell；managed container stop/remove；清空句柄清理 DockerException 只打印，不继续抛
DockerToolExecutor.*ToolCall[]保持输入顺序的 ToolResult[]单个 Docker 调用异常转失败结果，不中断后续调用

Shell 协议为：发送原命令，再发送 echo ---CMD_DONE---$?，用正则提取退出码，最后再次等待 prompt。Marker 固定且没有每调用 nonce；命令自身输出相同片段或 prompt 匹配异常都可能破坏帧边界。trae_agent/agent/docker_manager.py:204-242

命令构造不是结构化 argv：编辑代理把参数拼入 Shell 字符串；多数值只用单引号包裹，未转义值内单引号，列表甚至未整体引用。来自模型的参数可能改变命令语义。容器限制了部分影响范围，但 RW mount、网络和容器身份仍使其成为安全问题。trae_agent/tools/docker_tool_executor.py:103-142

9. 并发、性能与资源

  • Docker 模式全串行：无论 Model 的 parallel_tool_calls 为真或假，Docker Executor 的 parallel 入口都委托 sequential；连本应在 Host 执行的 Tool 也与容器 Tool 一起按列表顺序执行。trae_agent/tools/docker_tool_executor.py:57-75
  • 本地兄弟行为：普通 ToolExecutor.parallel_tool_call 使用 asyncio.gather；因此切换 Docker 会改变多 Tool Call 的时序与延迟，不只是执行位置。trae_agent/tools/base.py:238-244
  • 同步阻塞：SDK build/run、subprocess.run、pexpect 和命令等待都是同步调用，直接发生在 async Agent Loop 中；没有线程池、队列或背压机制。
  • 共享 Shell：单任务所有 Docker Tool Call 复用一个 PTY，保留 cwd、export、后台进程和 shell options；没有并发锁，包装器靠串行调用维持单写者假设。
  • 资源限制缺口：containers.run 没有 CPU、memory、pids、磁盘、ulimit、runtime、read-only rootfs、tmpfs 或日志大小限制；命令超时也不等于进程资源限制。
  • 残留资源：默认保留 managed container；Dockerfile 的 UUID image tag、加载的 image、打包产物、容器内后台进程和 Host Workspace 改动都没有统一回收策略。

10. 安全与信任边界

结论：当前 Docker 模式不能被描述为完整安全边界。它把三类 Tool 的进程放进容器，但没有把 Agent 全部副作用、Host 工作区、网络、身份、Secret、资源耗尽和镜像供应链纳入强制策略。
边界源码实际配置保护仍然存在的风险/缺口
Workspace显式传 -w 时整个目录以 rw 挂到 /workspace；省略时当前实现不 mount容器看不到未挂载 Host 路径（除 daemon/平台额外授予）有 mount 时可删除、篡改工作区；无 mount 时 Agent Prompt 仍声明容器项目根，形成可用性与路径误导
网络containers.run 未传 network/network_mode没有项目级显式保证使用 daemon 默认网络行为；无 egress allowlist、DNS 策略或离线模式
UID/权限未传 user、cap_drop、security_opt、privileged未显式开启 privileged进程使用 image 默认用户，常可能是 root；RW mount 文件所有权和权限可受影响
环境变量/Secret新容器未传 environment 或 env_fileHost Agent API Key 不被该调用主动注入image 自带 ENV、attached container 既有 Secret、工作区文件和 Tool 输出仍可能泄密；Host 本地 Tool/MCP 不受容器隔离
镜像信任接受可变 image 名、任意 Dockerfile、任意 tar、任意 container IDDockerfile build context 由用户指定无 digest pin、签名/SBOM/漏洞扫描、来源策略或构建网络限制；镜像代码与 entry filesystem 被信任
Tool copyHost 二进制复制到固定目录避免在镜像内安装 Python 包无 hash/签名、权限固定或只读 mount；attached container 可预置/替换路径
命令输入Bash 原样执行；编辑参数拼接 Shell 字符串异常转 ToolResult无 approval、allowlist、转义保证；命令注入仍在容器和 RW mount 范围内生效
资源/超时每调用 pexpect 等待 300 秒Host 等待有上限超时不 kill 命令/进程/容器；无 CPU/memory/pids/disk 限制，DoS 风险仍在
Docker 控制面Host 进程可访问 daemon，并运行 CLI/SDK由外部 Docker 权限控制Docker daemon 权限本身通常是高信任能力；项目没有最小授权代理

新容器调用只传 image、command、detach、volumes 和 working_dir。安全评审不能把 Docker 平台可能存在的外部默认值写成本项目保证。trae_agent/agent/docker_manager.py:89-120

12. 可观测性与排障

现象优先检查可能原因修复方向
普通本地模式导入即报 docker/pexpect 缺失安装 extras 与 import 栈BaseAgent 顶层导入 Manager，而依赖只列 evaluation extra安装对应 extra；长期应改为延迟导入/专用 docker extra
Docker configured correctly 后仍失败失败阶段是 build/run/cp/exec 哪一步预检仅验证 version，后续权限/镜像/TTY 不同用同一身份逐步验证对应操作
容器运行但编辑工具不存在/agent_tools 与 Host dist首次构建半成品、cp 失败、镜像架构/动态依赖不兼容重建打包产物并在目标镜像内直接执行
编辑 Host 路径失败参数名、Host root、容器 mount仅 path 翻译；路径不在 root 或 attach 无 mount核对真实 Tool Schema；不要假设 file_path 会翻译
JSON edit 找不到文件Tool Call 的 file_path当前翻译器不处理该字段这是实现缺口；使用容器路径或修复结构化路径映射
超时后下一条输出混乱容器进程与 PTY marker旧命令未终止，固定 marker 留在流中停止命令或重建 shell/container，再继续
任务结束后容器仍在--docker-keep 与 managed 状态默认 true，或 attach 不归当前 Manager 删除新容器明确传 false；外部容器由原 owner 清理
Host 文件权限/内容变化workspace diff、UID/GIDRW mount + image 默认用户备份/修复权限；未来显式 user 与最小 mount

最小只读检查顺序

docker version
docker ps --no-trunc
docker inspect <container-id>
docker exec <container-id> /bin/bash -lc 'id; pwd; ls -ld /workspace /agent_tools'
docker diff <container-id>

命令用于诊断，不应把 inspect 中的 Secret 原样贴入日志或工单。项目自身主要以 print、CLI Console、Tool Result 和 Trajectory 暴露状态，没有结构化 Docker event、container label、指标或 Secret 脱敏层。

15. 设计权衡与已知限制

当前选择收益成本/失败模式何时重新评估
包装现有 ToolExecutorAgent Loop 与 Tool Schema 基本复用，本地 Tool 可继续工作执行边界是混合的，容易把 Host Tool 误认为已隔离需要强隔离或统一远程执行协议时
三类硬编码代理实现直接、范围小新增 Tool 默认落到 Host；Schema 漂移（如 file_path）没有编译期检查代理类型增加或插件化时
持久 Bash + marker保留 shell 状态，避免每调用创建 exec固定 marker、prompt、超时残留与命令注入面多租户、不可信命令或可靠取消成为要求时
全 Docker 模式串行避免共享 PTY 并发写冲突，结果顺序稳定Host-only Tool 也失去并行，长命令阻塞后续调用需要吞吐时应先拆成独立 exec/session，而非直接并发共享 PTY
RW Workspace mount改动立即回到 Host，符合编码任务目标没有隔离、审阅后提交或自动回滚处理不可信仓库/模型、多租户或需要审批时
默认 keep=true便于事后进入容器排障和复用现场容器、进程和磁盘长期残留；不是安全默认批处理、CI、共享 daemon 或成本敏感环境
SDK + CLI + pexpect 混合分别复用 build/run、cp、交互 Shell 能力错误模型、 quoting、平台兼容与权限面分裂需要可移植测试、结构化执行或远程 daemon 时

当前限制，不是路线图承诺

源码没有实现：完整 Tool 隔离、网络策略、非 root 强制、Secret 注入/脱敏、镜像验证、资源配额、只读根文件系统、命令 kill、启动事务回滚、容器 label/GC、Docker 配置 Schema、interactive Docker、通用 Tool adapter 或 daemon 集成测试。本文把它们列为评审缺口，不代表维护者已经承诺交付。
