1. 模块定位

核心定义：BaseAgent.execute_task() 拥有步数受限的模板循环；TraeAgent 只提供软件工程任务的初始化、完成判定、空 Patch 反馈与清理 Hook。
边界负责明确不负责
BaseAgent单步创建、LLM 调用、Tool 路由、结果反馈、Step/Execution 状态、步数上限与基础清理。不拥有具体 Provider 历史格式，不判断 Patch 业务有效性。trae_agent/agent/base_agent.py:147-352
TraeAgent初始消息、task_done 信号、must_patch、Git Diff、MCP 生命周期。不实现通用 Tool 路由；默认不反思 Tool 失败。trae_agent/agent/trae_agent.py:102-258
Provider Client保存 Provider 原生 message_history，把增量消息与 Tool Result 转成协议格式。BaseAgent 不维护一份统一完整历史。
Tool Executor / ToolExecutor 路由与异常归一化；具体 Tool 拥有副作用。task_done 成功信号不会进入 Executor。

本页聚焦循环工程；CLI 装配、完整 Tool 内部实现、Provider 协议细节、Docker 和 Trajectory 分别属于相邻模块。评估目录不是该 Runtime 的外环。

3. 核心概念与术语

术语当前准确含义常见误解
Step一次 LLM 响应，加上零个或多个 Tool Call/Result；不是单个 Tool Call。trae_agent/agent/agent_basics.py:38-56把 Tool 数量当作 Step 数。
ObservationToolResult 被包装成下一轮增量 LLMMessage(role="user", tool_result=...)。BaseAgent 内的一份完整对话。
反思（Reflection）Tool 执行后的可选字符串 Hook；基础类可汇总失败，Trae 覆写后固定返回 None。Trae 默认每步都有独立 Reflect 阶段。
规划（Planning）System Prompt 七步指导与可选 Sequential Thinking Tool 所引导的模型行为。Runtime 中存在 Planner 状态、阶段门禁或强制先规划。
完成信号Trae LLM 响应中任一 Tool Call 名称等于 task_done。执行 TaskDoneTool.execute() 后才完成。
取消主循环没有取消令牌、专用取消状态或取消检查点。把 MCP 初始化局部捕获 CancelledError 当作全任务取消协议。

4. 架构组成

execute_task创建 AgentExecution，运行最多 max_steps 轮，捕获单步异常并收尾。状态、时间与资源生命周期在此汇合。
_run_llm_step更新 Console、同步调用 Provider、累计 Usage，先判定完成，再选择空 Patch 反馈或 Tool 处理。trae_agent/agent/base_agent.py:209-236
_tool_call_handler无 Tool Call 时反馈“未完成”；有调用时执行、记录 Result、可选 Reflection，再返回下一轮增量消息。
_finalize_step无条件把 Step 置为 COMPLETED，记录 Trajectory、更新 Console、追加到 Execution；这会覆盖之前写入的 ERROR。
Trae Hooksllm_indicates_task_completed、_is_task_completed、task_incomplete_message、reflect_on_result。
Provider HistoryOpenAI、Anthropic、Google、Ollama 与兼容客户端各自累加输入和 assistant/tool 帧；Tool Result 在下一轮 chat() 时入历史。
Tool Executor 快照风险：ToolExecutor 构造时持有原始 self._tools 列表，MCP 通过同一列表 extend 可被看到；但 tools 属性首次访问后会缓存名称映射，之后再添加工具不会自动刷新映射。trae_agent/tools/base.py:182-203

5. 完整运行流程

5.1 成功路径：Tool 迭代后发出 task_done

1初始化
new_task 写入 System/User 增量消息；execute_task 创建 AgentExecution(IDLE)，随后置为 RUNNING。
2Think
创建 AgentStep(THINKING)；Provider 把本轮增量消息并入自己的历史并返回 LLMResponse。
3Tool
若没有 task_done，按配置并行或串行执行所有 Tool Call；未知 Tool 与 Tool 异常都转成失败 Result。
4Observation
每个 Result 包装成下一轮消息；Trae 的 Reflection 恒为 None，不会追加反思 assistant 消息。
5Finalize
Step 标为 COMPLETED 并写入 Trajectory/Execution；下一轮 Provider 将 Observation 并入完整历史。
6完成短路
任一 Tool Call 名为 task_done 且 Patch 条件通过：Execution 置 COMPLETED/success=true，该响应中的所有 Tool Call 都不执行。
7清理
Docker 按 docker_keep 决定停止；关闭 Tool、清理 MCP、更新时间；Trae finalize Trajectory 并可选写 Patch。
批次短路语义：只要响应的 Tool Call 列表中含 task_done，完成分支优先于 _tool_call_handler。同一响应里与它并列的编辑、测试或其他 Tool Call 也不会执行。trae_agent/agent/base_agent.py:225-236；trae_agent/agent/trae_agent.py:228-244

5.2 提前结束与继续路径

输入/现象决策状态写入下一步/终态
LLM 无 Tool Call，且无 Trae 完成信号_tool_call_handler(None)Step 最终 COMPLETED；无 Tool Result。注入 “It seems that you have not completed the task.”，继续下一步。
task_done + must_patch=true + 空/测试-only Diff_is_task_completed=falseExecution 保持 RUNNING。注入固定空 Patch 错误，继续；该批次其他 Tool 不执行。
未知 Tool名称小写并移除下划线后仍无匹配失败 ToolResult 写入 Step。作为 Observation 回到 Provider，任务继续。
达到最大步数且未成功循环退出后检查final_result 固定文本；AgentState=ERROR。正常走资源清理并返回失败 Execution。
单步 LLM/内部异常内层 except ExceptionAgentState=ERROR、Step.error；finalize 后 Step.state 被改回 COMPLETED。结束循环并清理。

5.3 恢复与降级

Tool 失败是可反馈、可由模型下一轮纠正的软失败；Provider 重试发生在各 Adapter 的 retry_with(..., max_retries) 内。Runtime 没有跨 Provider 故障转移、失败步骤重放、检查点恢复或幂等保证。MCP 单 Server 连接失败会清理该 Client 并跳过，但取消也在该局部被清理后 continue，不会传播成全任务取消。trae_agent/agent/trae_agent.py:72-100

6. 数据与状态模型

状态对象关键字段所有者/生命周期持久性
AgentExecutiontask、steps、final_result、success、total_tokens、execution_time、agent_state每次 execute_task 新建并返回。内存；Trajectory 保存部分映射。
AgentStepstate、tool_calls/results、llm_response、reflection、error每轮新建，finalize 后追加。内存及 Trajectory；thought/llm_usage 当前未赋值。
Provider historyProvider 原生消息、assistant Tool Call、Tool Result具体 Client；默认 reuse_history=true。仅进程内，无统一清空/Checkpoint。
Tool 资源Tool 实例、Executor 映射、Docker/MCP 客户端Agent 生命周期，清理所有权分散。副作用可能持久，控制对象不持久。

实际状态转换

层级路径注意
ExecutionIDLE → RUNNING → COMPLETED | ERROR外层异常分支可能留下 RUNNING，因为只写 final_result。
Step 正常THINKING → CALLING_TOOL → [REFLECTING] → COMPLETEDTrae 默认没有 REFLECTING。
Step 异常THINKING/CALLING_TOOL → ERROR → COMPLETED最后一步是实现缺陷，不代表异常已恢复。
异常状态覆盖缺陷：内层异常先写 step.state=ERROR，随后 _finalize_step() 无条件写 COMPLETED；因此诊断必须同时检查 step.error 与 execution.agent_state。trae_agent/agent/base_agent.py:173-178,238-244

没有数据库、事务、锁、迁移或可恢复快照。Trajectory 是审计记录，不是可用于恢复循环的 Checkpoint。

7. 接口、协议与事件

接口/协议输入输出与可空性失败语义
execute_task()已由 new_task 设置的内部状态AgentExecution多数异常归一进 Execution，但启动 Docker、关闭 Tool 等位置仍可向上抛。
_run_llm_step()Step、增量消息、Execution下一轮增量 LLMMessage[]Provider/转换异常交由单步异常分支。
llm_indicates_task_completed()LLMResponseTrae：Tool Call 可空；按名称精确匹配 task_done。没有 Tool Call 即 false。
ToolExecutorToolCall[]同序 ToolResult[]未知 Tool/执行异常返回 success=false，不抛出普通 Exception。
观察事件Step/Execution/LLM/Tool 状态Console 更新、Trajectory 写盘、Tool 副作用没有独立事件总线或确认/重放协议。

Provider 历史回写契约

BaseAgent 每轮只传本轮增量消息。Provider Client 先追加增量输入，再在解析响应时追加 assistant 文本或 Tool Call；下一轮 ToolResult 再被转成 Provider 对应的 tool/function response。OpenAI、Anthropic、Google 和 OpenAI-compatible Client 明确如此。trae_agent/utils/llm_clients/openai_client.py:62-135,166-209；trae_agent/utils/llm_clients/anthropic_client.py:53-124,155-220；trae_agent/utils/llm_clients/google_client.py:49-135,171-229

Provider 差异：Ollama Client 会累加输入消息，但当前响应解析后没有把 assistant 文本或 Tool Call 追加回 message_history；这与其他 Adapter 不同，不能笼统声称所有 Provider 都保存完整 assistant 历史。trae_agent/utils/llm_clients/ollama_client.py:71-144

9. 并发、性能与资源

  • LLM 热路径：chat() 是同步调用，虽处于 async 方法中仍会阻塞事件循环。
  • 本地 Tool：并行模式使用 asyncio.gather，结果按输入顺序返回；多个有副作用的 Tool 不存在事务隔离。trae_agent/tools/base.py:238-244
  • Docker Tool：parallel_tool_call() 直接委托串行路径。trae_agent/tools/docker_tool_executor.py:57-75
  • 资源清理：BaseAgent 停 Docker、关闭 Tool、清 MCP；Agent 门面再次兜底 MCP；Trae finalize Trajectory。
  • 无背压：没有任务队列、有界历史、通用工具超时预算或上下文压缩；max_steps 仅限制 LLM 轮数。
资源创建正常清理缺口
Docker主 try 之前 start()docker_keep=false 时 finally stop启动抛错会绕过该 finally。
ToolAgent 构造循环 try/finally 之后 _close_tools()close 抛错会阻止时间/MCP/Console 收尾。
MCPAgent.run 在循环前BaseAgent 与 Agent.run 双层 suppress cleanup动态工具列表/Executor 缓存未统一重置。
Provider historyClient 构造，chat 累加无任务结束清空复用 Agent 时可能跨任务保留。

10. 安全与信任边界

边界当前机制风险与 Fail 决策
模型 → Tool名称路由与 Tool 自身参数处理没有人工审批、命令允许列表或循环级权限策略；Prompt 指令不是安全边界。
Tool 并发配置可并行执行同批 Tool文件/Shell 副作用可竞态；失败 Result 不回滚已成功副作用。
task_done名称精确匹配并在执行前短路结构化信号降低文本误判，但模型可在未真正验证时调用；Tool 描述/Prompt 的“先验证”无法 Runtime 强制。
Patch 门禁可选非测试 Diff 非空检查对“是否存在 Diff”采用失败关闭，但对正确性采用失败放行、测试、安全与恶意变更。
历史与记录Provider history、Trajectory 保存消息和 Tool 输出可能包含源码、路径、命令输出和 Secret；Loop 本身没有脱敏。

Host Tool 可直接修改工作区或执行 Shell；Docker 模式只改变执行位置，不自动证明工作区只读、网络关闭或最小权限。本模块不把 Sandbox 能力扩大解释为 Agent Loop 的授权系统。

11. 失败、恢复与兼容

故障/现象检测即时行为状态影响重试/恢复与运维
无 Tool Calltool_calls is None/[]注入未完成提示Step COMPLETED，Execution RUNNING模型下一轮重试；反复发生会耗尽 max_steps。
空 Patchmust_patch + 过滤后 Diff 为空注入空 Patch 错误保持 RUNNING继续编辑；检查 Git 工作区/base_commit。
未知 Tool归一化名称不在映射失败 ToolResult任务继续检查工具注册、MCP 动态注册与名称缓存。
Tool 抛 ExceptionExecutor 捕获转换失败 Result任务继续；Trae 无 Reflection模型可修正参数；副作用是否已发生由具体 Tool 决定。
Provider/解析异常Step.error/Trajectory单步异常分支结束循环Agent ERROR；Step 最终显示 COMPLETED修复网络、凭证、响应或消息转换后从头重跑。
最大步数固定 final_result终止并清理ERROR/success=false先定位循环原因，再考虑调整预算。
取消没有主循环协议asyncio.CancelledError 不被 except Exception 归一；清理可因取消传播而不完整无 CANCELLED 状态/标准结果依赖上层进程中断与增量 Trajectory；不能 Resume。
Docker 启动失败启动异常在主 try 前向上抛没有 Execution 返回检查 daemon/镜像并人工确认残留。
Tool close 失败清理异常向上抛可能丢失 execution_time、MCP 清理和最终 Console 更新人工释放资源；应引入分层 suppress/ExitStack。
外层异常终态缺陷：execute_task 的外层 except Exception 只写 final_result，没有把 agent_state 统一改为 ERROR。若异常发生在内层之外，Execution 可能仍为 RUNNING。trae_agent/agent/base_agent.py:183-200
无 Cancel / Checkpoint：Schema 中没有 CANCELLED 状态，主循环没有取消令牌、周期检查、状态快照或恢复入口；Trajectory 增量 JSON 只能用于调查，不能重新装载 Provider/Tool 状态继续执行。

12. 可观测性与排障

现象先检查可能原因修复方向
持续输出“not completed”Trajectory 的响应 Tool CallProvider/模型未生成 Tool Call；task_done 未注册或模型不支持核对 Tool Schema、supports_tool_calling 与 Prompt；不要只提高 max_steps。
调用 task_done 仍继续must_patch、Git Diff、base_commit空 Patch、仅测试 Patch、路径非 Git 仓库或 git 命令失败在项目路径执行只读 diff 检查，核对过滤规则。
同批编辑没有发生响应是否同时含 task_done完成判定先于所有 Tool 执行并短路要求模型先执行编辑/测试，下一轮单独 task_done；或修改协议并加测试。
Step=completed 但有 errorstep.error 与 Execution state_finalize_step 覆盖 ERROR以 error 为准；修复 finalize 状态保留。
Console 一直等待Execution 是否仍 RUNNING外层异常未写 ERROR统一异常终态；检查清理阶段异常。
未知 MCP Tool工具列表、Executor 缓存创建时机Server 未发现、未 allow，或名称映射在动态扩展前已缓存核对 MCP 初始化并刷新 Executor 映射。
上下文异常增长/串话Provider message_history默认复用历史且任务结束不清空在明确任务边界调用受控 history reset；增加隔离测试。

主要证据面是 Console 状态、Trajectory 的 llm_interactions/agent_steps、Provider 日志与工作区副作用。Trajectory 每次 LLM 交互和 Step 都保存，异常前通常有部分证据；保存失败只打印 Warning。trae_agent/utils/trajectory_recorder.py:77-128,130-230

15. 设计权衡与已知限制

当前选择收益成本/失败模式何时重评
模板方法钩子通用循环与 Trae 业务判定分离Hook 顺序隐含，缺少类型化阶段事件出现多个 Agent 子类或复杂工作流时。
task_done 前置短路完成信号无需真实副作用同批其他 Tool 被丢弃；验证仅靠模型自律需要原子完成/验证协议时。
Provider 持有完整历史贴合各 Provider 原生帧跨 Provider 一致性、压缩、任务隔离困难实现统一 Context Engine 时。
Tool 失败转 Observation模型可自愈，不因单工具失败立即结束可能重复副作用并耗尽步骤高风险 Tool 或要求事务语义时。
Prompt 引导 Planning实现简单、模型可灵活调整无法保证复现、测试、顺序或 Sequential Thinking 使用合规、审计或确定性流程要求提高时。
分散式清理局部代码直接启动/关闭异常有遗漏，重复清理所有权模糊引入统一生命周期管理器或长期服务时。

当前限制（不是 Roadmap 承诺）

  • Trae reflect_on_result() 固定返回 None；基础类的失败 Reflection 在当前具体 Agent 不可达。
  • 无 Tool Call 不是成功也不是错误，只消耗一步并注入提示。
  • 无统一取消令牌、CANCELLED 终态、任务级超时、检查点或恢复。
  • 异常 Step 状态会被 finalize 覆盖；外层异常可能保留 RUNNING Execution。
  • 没有通用上下文压缩、跨 Provider 故障转移、工具副作用事务或自动回滚。
  • Prompt Planning 与“验证后才能 task_done”属于模型指导，不是 Runtime 强制。
