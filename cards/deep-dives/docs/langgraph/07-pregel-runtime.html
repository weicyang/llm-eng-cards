1. 模块定位

Pregel Runtime 是编译后图的本地执行所有者：它借用 Google Pregel/Bulk Synchronous Parallel（BSP，批量同步并行）的离散超级步与屏障思想，把 actor 与 Channel 组织成 Plan、Execution、Update 三阶段；执行期产生的 Channel 更新直到下一步才可见，终止条件是没有可执行 actor 或超过步数预算。libs/langgraph/langgraph/pregel/main.py:454-477

边界本模块负责委托或明确不负责
入口规范化 config、建立 sync/async Loop、驱动 Runner、生成本地输出StateGraph 构图与 compile 由第 04/05 章负责
状态在内存 Channel map 上推进版本和超级步Channel reducer 语义由 Channel 实现；不是共享 dict 即时修改
持久化决定何时调用 saver 的 put_writes/put数据库事务、序列化与历史保留由 saver 实现
执行并发运行当前任务集，屏障后合并 writes节点函数、Tool、网络和业务副作用不由 Runtime 回滚
进程边界当前 Python 进程内的本地 PregelAPI Server / Platform task queue、SDK transport、Auth 不在本章

普通用户通常经 Graph API 或 Functional API 间接使用 Pregel；直接构造 Pregel 是高级接口。libs/langgraph/langgraph/pregel/main.py:516-523

名称相同不代表系统边界相同：本章所述当前 Python Runtime 是进程内图执行器，不承诺 Google 2010 Pregel 的集群图分区、master/worker 协调、跨 worker 消息路由、worker 故障检测/重分配或其性能与扩展性结果。

3. 核心概念

Superstep / 超级步

一次“选任务—并发执行—屏障合并”的原子可见性单位；不是 Python 调用栈深度。

BSP

Bulk Synchronous Parallel（批量同步并行）：兄弟任务读同一稳定快照，写在屏障后统一生效。

Loop

拥有 checkpoint、Channel、step/status、pending writes 和中断/终止决策。

Runner

并发执行 Loop 选出的 task，提交 task 级 writes，聚合异常、interrupt 与 timeout。

apply_writes 先按 task path 排序，再更新 versions_seen、消费触发 Channel、按 Channel 分组并调用 update；因此确定性来自稳定顺序和 reducer 契约，不来自线程完成顺序。libs/langgraph/langgraph/pregel/_algo.py:253-269 libs/langgraph/langgraph/pregel/_algo.py:284-323

3.1 经典 Pregel 与 LangGraph Runtime 映射

Google 2010 Pregel 是面向大规模图处理的 vertex-centric 集群系统；LangGraph 采用其 BSP 组织原则来执行有环 agent/workflow。下表是概念类比，不是实现等价。

经典 Pregel当前 LangGraph Runtime 中最接近的概念必须保留的差异
Vertex：带 value、出边和 active 状态，由统一 Compute 处理PregelNode/actor：订阅 Channel、以 Runnable 执行并产生 writes。libs/langgraph/langgraph/pregel/main.py:479-485节点是工作流执行单元，不是被分区图数据中的一条 vertex；不同节点也不必共享同一个计算函数。
Message：超级步 S 发出，在 S+1 交给目标 vertexChannel update 与 task write：task 先缓冲写，屏障后按 Channel reducer 合并。libs/langgraph/langgraph/pregel/main.py:487-493 libs/langgraph/langgraph/pregel/_algo.py:294-323Channel 是带值、版本与更新函数的状态/通信抽象；task write 还含控制记录，不等于跨机器消息包。
Superstep / global barrier：活跃 vertex 并行计算，消息到下一步可见Plan → Execution → Update；兄弟 task 读稳定快照，after_tick 才统一应用 writes。libs/langgraph/langgraph/pregel/main.py:464-474 libs/langgraph/langgraph/pregel/_loop.py:683-718二者共享 BSP 可见性边界；LangGraph 的 barrier 是本次 Loop 的逻辑屏障，不证明存在集群级全局同步协议。

Worker / partition / distributed model：master 划分图并把 partitions 分配给集群 workers同步路径提交到进程内 BackgroundExecutor，异步路径提交协程/async task 到 AsyncBackgroundExecutor。libs/langgraph/langgraph/pregel/_loop.py:1685-1698 libs/langgraph/langgraph/pregel/_loop.py:1943-1958当前 Python library Runtime 主要是单进程 executor/async task 调度；API Server 或平台能力不能反推为该本地类的分布式语义。

3.2 为什么选择 structured discrete steps

LangChain 官方设计长文把“结构化为离散步骤”视为其余能力的前提：一个不可分割的大 while 循环难以生成可移植 checkpoint，也难以在不同机器、不同时间恢复或插入 human-in-the-loop。选择算法后，BSP/Pregel 同时允许 cycles，并通过隔离同一步的节点状态、屏障和确定顺序合并来避免由节点启动/完成时序造成的数据竞争；这也是早期无明确算法的并发节点曾出现非确定行为后采用该模型的动机。

这里的“确定性并发”只约束 Runtime 的任务选择、步骤可见性与 writes 合并顺序。LLM 输出、节点内部随机性、非结合/非交换 reducer、时间与网络输入以及外部副作用仍可能让业务结果非确定。

5. 完整运行流程

5.1 正常成功路径

  1. invoke 本身不另建执行引擎，而是消费 stream；values 返回最后状态，其他 mode 收集 chunks。libs/langgraph/langgraph/pregel/main.py:3883-3957
  2. stream/astream 合并 config、校验 key、解析 checkpointer/store/cache/durability，建立 Runtime 与 Loop。libs/langgraph/langgraph/pregel/main.py:2538-2613
  3. Loop 进入时读取指定或最新 checkpoint；无记录则使用 step=-2 的空 checkpoint，重建 Channel map，再调用 _first。sync 与 async 分别调用 get_tuple/aget_tuple。libs/langgraph/langgraph/pregel/_loop.py:1629-1708 libs/langgraph/langgraph/pregel/_loop.py:1887-1968
  4. _first 把新 input 映射成 Channel writes，应用后保存 source=input checkpoint；恢复输入则标记中断版本并输出已有值。libs/langgraph/langgraph/pregel/_loop.py:945-1035
  5. tick 通过 prepare_next_tasks 选任务；无任务设为 done。Runner 仅执行 not t.writes 的 task。libs/langgraph/langgraph/pregel/_loop.py:599-681 libs/langgraph/langgraph/pregel/main.py:2959-2984
  6. 所有 task 完成后，after_tick 合并 writes、发 values、清空 pending writes、保存 source=loop checkpoint，再检查 interrupt_after。libs/langgraph/langgraph/pregel/_loop.py:683-726
  7. 下一次 tick 无 task 时正常结束，Loop 输出最终 Channel 值并触发 chain end。

5.2 拒绝、提前结束与终止路径

  • recursion_limit < 1 在创建 Loop 前直接 ValueError；checkpointer 存在却无 configurable coordinate 也被拒绝。libs/langgraph/langgraph/pregel/main.py:2563-2593
  • 没有新 input 且未被判定为恢复时，_first 抛 EmptyInputError。libs/langgraph/langgraph/pregel/_loop.py:1031-1035
  • 步数越界把 status 设为 out_of_steps，入口随后抛 GraphRecursionError；它限制超级步，不是函数递归。libs/langgraph/langgraph/pregel/_loop.py:606-609 libs/langgraph/langgraph/pregel/main.py:3001-3011
  • interrupt_before 在任务执行前抛 GraphInterrupt；顶层 Loop 退出钩子抑制它并形成可恢复暂停，而不是普通失败。libs/langgraph/langgraph/pregel/_loop.py:666-671 libs/langgraph/langgraph/pregel/_loop.py:1335-1359
  • drain 请求在完成当前超级步后、准备出下一批 task 时生效，status 变为 draining，入口抛 GraphDrained。libs/langgraph/langgraph/pregel/_loop.py:652-659 libs/langgraph/langgraph/pregel/main.py:3012-3015

5.3 Partial failure 与恢复路径

  1. 兄弟任务中一个成功、一个失败时，Runner 分别提交成功 Channel write 与失败 ERROR，然后重新抛失败；尚未跨过 after_tick 屏障，所以整体 checkpoint 仍位于该步之前。libs/langgraph/langgraph/pregel/_runner.py:342-358 libs/langgraph/langgraph/pregel/_runner.py:584-613
  2. 相同 thread 以 None 或 Command 恢复时，_first 识别 continuation。libs/langgraph/langgraph/pregel/_loop.py:851-872
  3. tick 把 pending writes 重新挂到同 task；跳过 ERROR/INTERRUPT/RESUME，使成功 task 因已有 writes 不再执行，失败 task 保持空 writes 后重跑。libs/langgraph/langgraph/pregel/_loop.py:661-664 libs/langgraph/langgraph/pregel/_loop.py:736-749
  4. 失败 task 最终成功后，屏障一次性合并旧成功 write 与新 write，形成新 checkpoint。同步和异步测试都证明成功兄弟只调用一次。libs/langgraph/tests/test_pregel.py:927-987 libs/langgraph/tests/test_pregel_async.py:1843-1908

6. 数据与状态模型

状态Owner / 生命周期变化点
channels每个 Loop 从 checkpoint 重建的内存 map_first 与 after_tick/apply_writes
channel_versionsCheckpoint；每个 Channel 的版本consume/update/finish 返回变化时推进

checkpoint_pending_writes加载自 saver，并在 task commit 时追加恢复重放；成功屏障后清空

Checkpointer 分别保存 Checkpoint（Channel 状态与版本）和 task 级 pending writes；两者都不包含 Python 栈帧。Runtime 不能自动回滚已经发生的 HTTP、数据库或文件副作用；恢复时业务节点可能重跑。

9. 并发、性能与资源

Runner 可并发运行当前超级步的任务，但 Channel 在步骤内保持不可变，步骤 N 的写只在 N+1 可见。同步和异步主循环都明确执行 tick → runner → after_tick。libs/langgraph/langgraph/pregel/main.py:2959-2988 libs/langgraph/langgraph/pregel/main.py:3431-3462

  • 执行器：sync Loop 使用 BackgroundExecutor，async Loop 使用 AsyncBackgroundExecutor；资源随 context stack 退出。libs/langgraph/langgraph/pregel/_loop.py:1685-1698 libs/langgraph/langgraph/pregel/_loop.py:1943-1958
  • 队列：sync 使用 SyncQueue，async 使用 AsyncQueue；messages/custom/subgraph 时用单个 waiter 促使输出并发排出。libs/langgraph/langgraph/pregel/main.py:2748-2749 libs/langgraph/langgraph/pregel/main.py:2935-2957 libs/langgraph/langgraph/pregel/main.py:3392-3429
  • 取消：普通 task 失败时 Runner 取消剩余 inflight；GraphInterrupt 被聚合后统一上抛。libs/langgraph/langgraph/pregel/_runner.py:650-690
  • 背压边界：代码提供队列/信号量唤醒，但不声明固定容量或端到端背压 SLA；慢消费者的内存影响需按应用实测。

不要把“并发 task”解释为“分布式 worker”。当前代码展示的是单个 Python Runtime 实例通过 executor 或 asyncio 调度任务；本章没有发现图 partition、master/worker 协议、跨节点消息传输或故障 worker 重分配实现，也不据 Google Pregel 论文推导 LangGraph 的吞吐、延迟或横向扩展指标。

10. 安全与信任边界

  • Runtime 校验 output key、recursion_limit 和 checkpointer coordinate，但不会把节点输入变成可信数据；业务 Schema、Tool policy 与外部系统授权仍由上层负责。libs/langgraph/langgraph/pregel/main.py:2563-2593
  • Checkpoint 是可执行状态输入；反序列化 allowlist、加密与数据库访问控制属于 saver/serde 边界，本地 Pregel 不提供 Auth。
  • 未知 Channel write 会被 warning 后忽略，而非法 reducer/Channel 更新可抛异常；扩展 Channel 时不可把忽略警告当作权限控制。libs/langgraph/langgraph/pregel/_algo.py:294-313
  • RunControl 的 drain signal 是单属性写，文档限定单 run 使用；复用已经 drained 的实例会让后续运行保持 drained。libs/langgraph/langgraph/runtime.py:79-104
副作用节点必须使用幂等键、事务或补偿机制。pending writes 能防止已成功 task 在特定恢复路径重复执行，但无法证明远端副作用与 task write 原子提交。

15. 设计权衡与已知限制

  • BSP 换确定边界：稳定快照和屏障让并发推理清晰，代价是慢 task 拖住整个超级步，且兄弟写不能立即互见。
  • 离散步骤换可恢复结构：把 agent 拆成节点/超级步，才能在边界流式观察、checkpoint、interrupt 和恢复；代价是不能把任意 Python 栈帧或一个大循环中的任意指令位置透明序列化。
  • 确定性合并换调度自由：task path 稳定排序使 reducer 输入不依赖完成先后，但不会消除 LLM、节点代码、外部输入或副作用本身的非确定性。libs/langgraph/langgraph/pregel/_algo.py:253-256
  • pending writes 换细粒度恢复：成功 task 可跳过，代价是 saver 必须正确保存 task_id/channel/value，业务副作用仍需自行保证幂等。
  • async durability 换吞吐：checkpoint 与下一步重叠，但进程灾难窗口里 durable head 可能落后内存进度；代码只保证 put 的顺序，不承诺外部副作用原子性。libs/langgraph/langgraph/pregel/_loop.py:1199-1209
  • exit durability 换更少中间 checkpoint：退出集中保存，运行中历史与恢复粒度更弱；DeltaChannel 还需累积 writes 与锚点处理。libs/langgraph/langgraph/pregel/_loop.py:1217-1315
  • cooperative drain 换一致边界：不破坏当前步，但无法保证立刻停机；长节点必须另配 timeout/cancellation 与幂等策略。
  • 复用 Pregel 语义而非复刻集群系统：本地 Runtime 获得 cycles、稳定快照和逻辑 barrier，但当前 Python 实现没有经典 Pregel 的图 partition、master/worker、跨 worker message transport 与透明 worker recovery；需要分布式执行时必须单独审计实际 Server/Platform 部署面，不能由类名推断。

当前证据没有给出固定队列容量、最大并发数、吞吐、延迟或恢复时间 SLA；这些必须在目标 executor、saver、节点负载和部署环境中测量。

17. 术语表

术语本章含义
Actor / PregelNode订阅 Channel、执行 Runnable 并产生 writes 的运行单元。
BSPBulk Synchronous Parallel，任务并发执行、屏障统一提交的批量同步并行模型。
SuperstepPlan、Execution、Update 组成的一轮；recursion_limit 约束的核心单位。
Loop拥有一次运行的 checkpoint、Channel、tasks、step 与 status 的状态机。
Runner执行当前 task 集、处理重试/异常/取消并提交 task writes 的并发组件。
tick检查步数和终止条件、准备任务、恢复 pending writes、执行前中断的阶段。
after_tick跨过超级步屏障后合并 writes、输出 values、保存 checkpoint 的阶段。
Pending write挂在某 checkpoint 与 task id 下、尚未统一进入下个整体 checkpoint 的 task 级写。
Partial failure同一超级步中部分 task 已成功写出、另一些失败，整体尚未跨屏障。
Durabilitycheckpoint 持久化与执行同步关系：sync、async 或 exit。
Drain在超级步边界停止启动下一批任务的协作式终止；不是立即取消当前 task。
PULL / PUSHPULL 由 Channel/边触发；PUSH 由 Send 或 Functional API task 调用产生。
Stable snapshot同一超级步内所有兄弟 task 读取的稳定 Channel 视图。
Vertex-centric经典 Pregel 以 vertex 及其本地状态/消息为计算中心；LangGraph 的 PregelNode 只是可类比的执行 actor，并非图数据 partition 中的 vertex。
Worker / Partition经典 Pregel 的集群执行与图划分单位；当前本地 Python Runtime 没有与之等价的公开运行时组件。
CheckpointChannel 值、版本、versions_seen、metadata 等超级步边界状态；不含 Python 栈帧。
Replay / ResumeReplay 从历史点形成执行分支；Resume 在当前 thread 上继续 pending task/interrupt，二者不可混同。
