Runtime、错误处理与执行韧性

从节点运行依赖、重试与 attempt timeout，到可恢复 error handler 和 cooperative drain，建立一套不掩盖副作用与持久化边界的开发心智模型。

1. 模块定位：把“如何执行”与“失败后怎么办”连起来

本章 Owner 是运行期依赖注入和 task 级韧性：Runtime 暴露当前 run/node 的依赖与身份；RetryPolicy、TimeoutPolicy 约束一次节点执行；Runner 把最终失败路由到 handler；Loop 负责 pending writes、恢复与 drain 安全边界。公共类型的当前基线可见 libs/langgraph/langgraph/runtime.py:26-125 与 libs/langgraph/langgraph/types.py:418-514。

职责本章负责委托/排除
节点运行依赖context、Store、stream writer、heartbeat、执行身份、run controlState 的 Channel 合并属于 Pregel/Channel；业务依赖生命周期由调用方管理
执行策略task/node retry、单 attempt 的 run/idle timeout整次 API 请求 SLA、分布式队列租约、进程 kill 不在本地策略内
错误恢复最终异常、ERROR/ERROR_SOURCE_NODE、handler PUSH 与恢复业务补偿、外部事务、幂等键仍由应用设计
优雅退出RunControl.request_drain() 在超级步边界停止后续任务信号注册、宽限期和强制取消由宿主进程负责

包版本和依赖下限来自 libs/langgraph/pyproject.toml:5-33。本地开源 Runtime 不等于 LangGraph API Server：ServerInfo 只是 Server 可注入的元数据，本地运行通常为 None。libs/langgraph/langgraph/runtime.py:60-76

2. 系统位置与依赖：Builder 配策略，Pregel 执行并落 writes

StateGraph.add_node / set_node_defaults │ retry_policy / timeout / error_handler ▼ CompiledStateGraph(Pregel) ── 构造 Runtime + RunControl │ ▼ PregelLoop.tick ──► PregelRunner.tick / atick │ ├─► run_with_retry / arun_with_retry │ ├─ 成功：普通 writes │ ├─ timeout：NodeTimeoutError → retry policy │ └─ 最终失败：ERROR + ERROR_SOURCE_NODE │ └─► error-handler PUSH task │ └─► handler writes / Command RunControl.request_drain ──► 下一超级步边界 ──► GraphDrained / 可恢复 checkpoint

StateGraph 在 compile 时把节点级配置与默认配置合并；节点显式值优先。普通节点才继承默认 error_handler 与 cache policy，而 retry/timeout 也可应用到 handler。libs/langgraph/langgraph/graph/state.py:1285-1344

同步与异步主链是兄弟实现：Pregel 分别把 loop.schedule_error_handler 和 loop.aschedule_error_handler 交给 Runner。libs/langgraph/langgraph/pregel/main.py:2923-2931、libs/langgraph/langgraph/pregel/main.py:3378-3386

下游副作用有三类：节点写入由 put_writes 进入 task 级 pending writes；成功后 Channel 在屏障处合并；有 checkpointer 时错误标记可跨进程恢复。Store 与 Cache 是可选依赖，不是 Runtime 自身的持久状态。

3. 核心概念：Runtime 不是 RunnableConfig

3.1 两个表面的分工

概念承载内容典型用法不要放什么
Runtime[ContextT]类型化 context、Store、custom stream、heartbeat、previous、ExecutionInfo、ServerInfo、RunControl业务依赖、身份、进度、流事件与协作 draincallbacks、tags、recursion_limit 等 Runnable 调度配置
RunnableConfigrun_id、callbacks、tags、metadata、recursion_limit、configurable 等Runnable 调度、追踪与 checkpointer 定位不要假设它等同类型化业务 context

Runtime 的公共说明明确不含 config；节点需要配置时应显式声明 config: RunnableConfig，或调用 get_config()。libs/langgraph/langgraph/runtime.py:124-141。内部目前把 Runtime 放进 config 的私有 configurable 槽位供传播，但这是实现桥梁，不会把两种公共契约合并；get_runtime() 的实现也明确留下未来解耦注释。libs/langgraph/langgraph/runtime.py:296-310

3.2 ExecutionInfo、ServerInfo 与 RunControl

  • ExecutionInfo 是 frozen、只读的节点执行快照：checkpoint/task/thread/run 身份，加上从 1 起的 node_attempt 与首次 attempt 时间。libs/langgraph/langgraph/runtime.py:26-57
  • ServerInfo 承载 assistant_id、graph_id 和可选认证用户；它是元数据，不是本地鉴权器。libs/langgraph/langgraph/runtime.py:60-76
  • RunControl 是单 run、可跨线程写入的 drain 信号；已 drain 的实例不能复用。libs/langgraph/langgraph/runtime.py:79-104

3.3 attempt、run timeout 与“整轮 run”

术语陷阱：TimeoutPolicy.run_timeout 不是整次图运行、也不是“包含所有重试的总预算”。它是单个 node attempt 的硬 wall-clock 上限；每次 retry 都开启新的 attempt。libs/langgraph/langgraph/types.py:451-480

5. 三类完整运行路径

路径 A — 正常成功：Runtime 注入到屏障提交

  1. 触发/输入：invoke/ainvoke 接收 State input、RunnableConfig 和可选 context/control。
  2. 规范化：Pregel 构造 run-scoped Runtime；task 准备后，重试层补齐 ExecutionInfo。当分布式执行绕过本地 task 准备时，_ensure_execution_info 从 config 回填。libs/langgraph/langgraph/pregel/_retry.py:520-540
  3. 执行：Runner 调用 sync/async retry 函数；节点读取稳定 State 快照，通过 Runtime 使用 context/Store/stream writer。
  4. 写入：节点输出先进入 task writes；Runner 成功 commit，空输出也写入 NO_WRITES 标记，再由 Loop 在超级步屏障处理。libs/langgraph/langgraph/pregel/_runner.py:604-613
  5. 终态：若没有 next task，Loop 先判定 done；因此 terminal step 内提出 drain 仍正常返回结果。libs/langgraph/langgraph/pregel/_loop.py:652-659

路径 B — 校验拒绝/提前结束：不启动不安全执行

  1. 策略校验拒绝：数值 timeout 被规范化为 run_timeout，非正数抛 ValueError；run/idle 都为空则策略归一化为 None。libs/langgraph/langgraph/types.py:483-514
  2. 同步目标拒绝：节点配置 timeout 时，Pregel validate 要求原生 async；同步函数无法安全地在进程内取消，因此 compile/declaration 阶段拒绝。libs/langgraph/langgraph/pregel/_utils.py:125-137、libs/langgraph/langgraph/_internal/_timeout.py:8-25
  3. 提前 drain：若 control 在首个 pending task 前已 drain，Loop 将状态置为 draining，主入口抛 GraphDrained，节点不执行。libs/langgraph/langgraph/pregel/_loop.py:652-659、libs/langgraph/langgraph/pregel/main.py:3012-3015

路径 C — 重试、handler 与崩溃恢复

  1. 失败与重试：异常依次匹配 policy 列表中的第一个适用项；未匹配或达到 max_attempts 就向 Runner 抛出。间隔按 backoff 上升、受 max_interval 限制，可加 jitter。libs/langgraph/langgraph/pregel/_retry.py:641-682
  2. 最终失败落 writes：普通异常追加 ERROR；若 task 有 handler，再追加源节点名 ERROR_SOURCE_NODE，然后调用 put_writes。libs/langgraph/langgraph/pregel/_runner.py:574-603
  3. 先 durable、后调度：有 checkpointer 时，Loop 等待包含 ERROR_SOURCE_NODE 的 put_writes future 完成，再创建 handler task。libs/langgraph/langgraph/pregel/_loop.py:1572-1599
  4. handler PUSH：task id 以 checkpoint、handler 名、step、PUSH、失败 task id 稳定派生；metadata 的 trigger 明确是 PUSH。libs/langgraph/langgraph/pregel/_algo.py:1137-1161
  5. 崩溃恢复：恢复时扫描成对的 ERROR_SOURCE_NODE/ERROR，给原 task 放入非空 ERROR writes 使 Runner 跳过它，再重建空 writes 的 handler task；原副作用节点不会因 handler 崩溃而重复执行。libs/langgraph/langgraph/pregel/_loop.py:751-816

6. 数据与状态模型：哪些是瞬时对象，哪些能恢复

数据Owner/生命周期是否持久化关键语义
Runtime一次 graph run；子图继承/merge对象本身不写 checkpoint承载依赖与控制，不是 State Channel
ExecutionInfotask/attempt 只读快照由 checkpoint/config 身份重建node_attempt 从 1 开始；首次时间跨 retry 保持
task writesRunner/Loop有 checkpointer 时由 put_writes 保存attempt 失败或重试前旧 writes 被清空，避免泄漏半成品
ERROR失败 task 的 pending write可持久化携带异常；跨 serializer 后类型可能退化为字符串表示
ERROR_SOURCE_NODE仅有 handler 的失败 task可持久化恢复路由标记，不是 State key
RunControl单 run 的内存信号不直接持久化drain 后由 checkpoint 保存已完成进度；resume 应使用新 control

ERROR、ERROR_SOURCE_NODE 是控制类 pending writes，apply_writes 不会把它们当成用户 Channel 更新。libs/langgraph/langgraph/pregel/_algo.py:298-309。恢复重放普通成功 writes 时也显式跳过 ERROR、source、interrupt、resume 控制信号。libs/langgraph/langgraph/pregel/_loop.py:736-749

持久化限定：“错误先持久化再运行 handler”只在配置 checkpointer 时具备跨进程耐久性；没有 checkpointer，标记只服务当前 Loop 的内存执行。Checkpoint 不保存 Python 栈帧，恢复依赖 task 身份与 pending writes 重建。

跨 checkpointer 序列化后，恢复测试只保证 NodeError.node 和错误内容可用，不保证原异常 Python 类型仍在。libs/langgraph/tests/test_retry.py:2689-2744

7. 接口、协议与事件：节点如何声明所需能力

7.1 节点签名与公共对象

  • runtime: Runtime[Context]：注入 context、Store、stream writer、heartbeat、执行信息和 control。
  • config: RunnableConfig：独立注入回调、tags、metadata、run/configurable 值；handler 也能接收它，真实测试验证 thread_id 保留。libs/langgraph/tests/test_retry.py:2452-2479
  • error: NodeError：仅 error handler 使用，包含失败节点名和异常对象。libs/langgraph/langgraph/errors.py:148-165

7.2 timeout 事件与进度信号

refresh_on="auto" 把本 attempt 的 writes、stream、child task 和后代 LangChain callback 视为进度；"heartbeat" 只认 runtime.heartbeat()。handler 被 inline 安装到本节点后代的 callback 链，兄弟节点事件不会互相续命。libs/langgraph/langgraph/pregel/_retry.py:128-134、libs/langgraph/langgraph/pregel/_retry.py:274-285

watchdog 区分 idle 与 run，只有 watchdog 自己的 asyncio.TimeoutError 转成 NodeTimeoutError；节点内部主动抛出的 TimeoutError 原样传播，避免误分类。超时时先关闭 scope、清空 writes、取消后台 task。libs/langgraph/langgraph/pregel/_retry.py:460-502

7.3 取消与 bubble-up

框架为停止兄弟 task 发起的 CancelledError 继续传播；节点代码自己抛出的 CancelledError 会转换为 NodeCancelledError，进入普通失败路径，防止 run 被误报成功。libs/langgraph/langgraph/pregel/_retry.py:777-794。GraphInterrupt、ParentCommand、GraphDrained 属于 GraphBubbleUp 控制流，不应由普通 error handler 吞掉。Runner 的路由条件明确排除它。libs/langgraph/langgraph/pregel/_runner.py:220-240

9. 并发、性能与资源：取消只能与代码协作

9.1 retry 与并发 task

每个 task 独立执行 retry；同一超级步的其他 task 可能仍在运行。Runner 在并发 future 完成时可立即调度对应 handler，已处理异常不会触发停止其他兄弟 task 的 fatal 路径。libs/langgraph/langgraph/pregel/_runner.py:277-335

重试等待发生在 worker/coroutine 内：sync 使用 time.sleep，async 使用 asyncio.sleep。没有全局“整轮 retry wall-clock budget”；最坏耗时还包括每个 attempt 的运行时间和所有退避。

9.2 cooperative timeout

timeout watchdog 依赖 asyncio cancellation。阻塞 GIL 的 CPU 工作或同步 time.sleep() 不会及时让出事件循环，因此不能保证在截止时刻中断。公共类型直接声明这一限制。libs/langgraph/langgraph/types.py:451-465。需要硬隔离时应使用进程、外部 job/queue 或具备服务端 deadline 的 I/O，而不是把线程取消当作强杀。

9.3 cooperative drain

request_drain() 只设置原因字符串，不取消当前 in-flight task。Loop 在准备出下一批 task、确认仍有任务后检查信号，因此当前超级步可完成，终态 step 正常结束，下一超级步不启动。libs/langgraph/langgraph/runtime.py:90-104、libs/langgraph/langgraph/pregel/_loop.py:599-659

这也允许当前 Functional task 在 drain 请求后完成其已在进行的 child call 调度；sync/async 真实测试分别覆盖这一点。libs/langgraph/tests/test_pregel.py:140-159、libs/langgraph/tests/test_pregel_async.py:235-255

drain 不是 kill：宿主应实现“先 drain → 等宽限期 → 再 cancel/终止”的外层协议。同步函数在线程中运行时，即使 async 调用方取消，线程仍可能继续完成副作用；测试明确观察到 orphaned thread 继续运行。libs/langgraph/tests/test_runtime.py:829-875

10. 安全与信任边界

  • ServerInfo 不是授权：本地实现从 configurable 读取 Server 放入的 assistant/graph/user 元数据；没有这些键就返回 None。应用不能仅因对象存在就跳过权限校验。libs/langgraph/langgraph/pregel/main.py:4306-4334
  • Secret 不进 State：密钥、数据库连接与租户能力应经 Runtime context 注入，避免进入 Channel、stream 或 checkpoint；Runtime 文档把 context 定义为 run dependencies。libs/langgraph/langgraph/runtime.py:198-207
  • error 可能泄密：ERROR 会交给 checkpointer serializer，handler 又能读取异常文本。不要在异常消息中拼接 token、原始认证头或敏感 payload。
  • predicate 必须 fail-closed：自定义 retry_on 应只允许已知瞬时错误；权限、校验、配额和业务拒绝不应通过重试绕过。
  • handler 是普通能力主体：它能读 State/Runtime 并产生 writes 或 Command，应接受与普通节点相同的最小权限、timeout 与审计；不能将它视为可信的“异常后门”。

handler 的默认 cache policy 不继承是正确性与安全边界：失败节点 State 可能变化，而相同 cache key 会复用错误的补偿结果。源码在 compile 时显式跳过 handler cache default。libs/langgraph/langgraph/graph/state.py:1322-1338

11.1 禁止递归捕获

Runner 收集所有 handler 节点名，_should_route_to_error_handler 对这些节点固定返回 false；因此 node handler 失败不会落到 graph default，default handler 也不会捕获自己。libs/langgraph/langgraph/pregel/_runner.py:141-174。真实测试要求两种 handler 失败都直接暴露。libs/langgraph/tests/test_retry.py:2399-2445

11.2 handler 默认不缓存，但并非不可配置

自动生成的 node/default handler spec 初始化为 cache_policy=None，而 set_node_defaults(cache_policy=...) 只传播给 regular node。libs/langgraph/langgraph/graph/state.py:871-890、libs/langgraph/langgraph/graph/state.py:1298-1338。底层 task 准备仍能处理有效 cache policy，所以“默认不缓存”不能误写成内核永久禁止；若扩展层强行启用，必须证明 key 含完整失败上下文且补偿无副作用。

11.3 drain 的可恢复终态

GraphDrained 继承 GraphBubbleUp，表示在超级步边界提前退出；说明承诺 checkpoint 已保存并可后续恢复。libs/langgraph/langgraph/errors.py:50-64。即使 durability 为 exit，测试也验证 drain 后用相同 thread 从已完成节点继续。libs/langgraph/tests/test_runtime.py:172-202

14.1 推荐节点模式

  1. 把只读业务依赖放入类型化 Runtime context，把 trace/config 键放在 RunnableConfig，不要互相偷取私有槽位。
  2. 只为可重复的瞬时错误设置 retry；在外部写操作中使用由 ExecutionInfo.task_id 与业务键组合出的幂等键。
  3. 异步长任务同时设置合理的 run_timeout 和 idle_timeout；只有业务进度才 heartbeat。
  4. handler 输出状态化的降级结果或 Command；避免在 handler 内做无幂等保护的第二次不可逆写。
  5. 进程退出时创建每 run 独立 control，先 request drain，再由宿主计时并最终 cancel；resume 使用新 control。
禁止捷径：不要在 handler 内递归调用原节点模拟 retry；不要把 ERROR 当普通 State Channel；不要缓存有副作用的 handler；不要为同步阻塞函数伪装 async 以绕过 timeout 校验；不要复用已 drain 的 RunControl。

15. 设计权衡与已知限制

问题当前选择收益成本/失败模式重评条件
如何传运行依赖Runtime 与 RunnableConfig 分离，内部借 config 传播业务类型清晰，兼容 Runnable 生态内部实现仍耦合 private configurable公共 Runtime context manager 可独立传播
timeout 如何实现async cooperative cancellation不强杀进程，清理路径可执行阻塞 GIL/线程无法及时终止引入隔离 worker/租约型执行器
handler 何时执行最终异常 writes durable 后立即 PUSH同 run 低延迟恢复，崩溃窗口可重建checkpointer latency 位于失败路径；handler 可与兄弟并发需要队列化补偿或严格串行语义
为何禁止递归捕获handler 节点永不路由到 handler终止条件明确，不会无限补偿handler 故障直接失败，需要运维修复若引入独立、有限状态的补偿编排器
drain 如何停机超级步边界协作停止保留已完成 writes，可 resume长节点延迟退出；不是强制终止宿主要求严格 shutdown deadline

当前限制：没有覆盖所有重试的总 run budget；timeout 只支持可原生 async 的节点链；RunControl 只有单向 drain，没有 reset；ERROR 跨 serializer 后异常类型可能变化；本地实现没有定义远程 Server 的队列、租约、部署信号与 SLA。

有意排除：Streaming v1/v2/v3 背压、checkpoint 数据库事务、Interrupt/time-travel、RemoteGraph transport 和 ToolNode error policy 分属相邻模块，本章只说明它们与 Runtime/error control 的接缝。

17. 术语表

术语本章含义
RuntimeLangGraph 注入节点/中间件的 run-scoped 依赖集合；不等于 RunnableConfig。
RunnableConfigLangChain Runnable 的运行配置，承载 callbacks、tags、metadata、run_id、recursion_limit 和 configurable 等。
ExecutionInfo当前 checkpoint/thread/run/task/node attempt 的只读执行身份。
ServerInfoLangGraph Server 可注入的 assistant、graph 与 user 元数据；不是本地授权机制。
RunControl一次 run 的协作控制面；当前只提供单向 drain 请求。
attempt节点的一次实际执行。首次为 1，每次 retry 递增。
RetryPolicy异常匹配、最大 attempt、退避、上限与 jitter 的策略。
run timeoutTimeoutPolicy.run_timeout；单个 attempt 的不可刷新 wall-clock 硬上限，不是整图 run 总预算。
idle timeout单个 attempt 在无可观测进度情况下允许的最长间隔。
heartbeat节点显式报告业务仍在推进的信号；只刷新 idle timeout。
cooperative cancellation协作式取消；依赖协程让出控制并响应 cancellation，不能安全强杀阻塞线程/GIL 工作。
cooperative drain协作式排空；让 in-flight 工作完成，在安全超级步边界停止后续调度并保留恢复点。
ERROR失败 task 的控制类 pending write，携带异常或其序列化表示。
ERROR_SOURCE_NODE表明失败来自哪个、且已配置 handler 的原节点的控制标记，用于恢复时避免重跑原节点。
NodeError注入 error handler 的失败上下文，包含源节点名与错误对象。
PUSH task不是由 Channel PULL 触发、而是动态立即创建的任务；error handler 以稳定 PUSH task 调度。
pending writestask 级、尚未合并到超级步 checkpoint State 的 writes；可由 checkpointer 单独保存。
GraphBubbleUpInterrupt、ParentCommand、GraphDrained 等框架控制流基类；普通 error handler 不捕获。
idempotency幂等性；同一 task/业务操作重复执行不会造成额外外部效果，是安全 retry/resume 的应用责任。
