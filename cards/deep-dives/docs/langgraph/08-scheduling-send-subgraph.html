调度、Send 与子图：从触发到可恢复任务身份

本文建立一套开发级心智模型：Pregel 如何把 Channel/Edge 触发变成 PULL task，把动态 Send 与 Functional API 调用变成 PUSH task；这些任务如何获得稳定身份、跨 checkpoint 恢复，并在 waiting edge、嵌套 namespace 与 Command.PARENT 中保持边界清晰。

1. 模块定位

本模块拥有“下一超级步有哪些 task、每个 task 的输入和身份是什么”的决策。prepare_next_tasks 明确返回 PUSH 与 PULL 的并集；它消费 TASKS Channel 中的动态包，同时根据 Channel version 与节点 trigger 生成订阅任务。证据：libs/langgraph/langgraph/pregel/_algo.py:392-435、libs/langgraph/langgraph/pregel/_algo.py:441-513

职责本模块负责委托对象明确不负责
任务选择PULL/PUSH 生成、输入装配、稳定 task idLoop 提供 checkpoint、step、pending writes节点业务逻辑和 reducer 实现
动态扇出Send(node,arg) 转 PUSH taskRunner 并发执行；Channel 在屏障合并跨机器队列和服务端调度
静态汇合waiting edge 编译为 NamedBarrier ChannelChannel 保存 seen set任意动态 fan-out 的自动计数 join
嵌套执行task namespace、父 checkpoint 映射、bubble-up 路由Checkpointer 持久化；子图自身执行Store 记忆、Cache 命中和远程 Server
边界要点：调度不是修改一份共享 Python dict。兄弟 task 读取同一超级步的稳定 Channel 快照，各自积累 writes，屏障后才统一合并。

2. 系统位置与依赖

StateGraph.compile ├─ attach_edge / attach_branch → trigger Channel、TASKS writes └─ Pregel.stream / invoke → PregelLoop.tick → prepare_next_tasks ├─ PULL: Channel version > versions_seen └─ PUSH: TASKS 中 Send / Call → PregelRunner.tick（并发执行） → apply_writes（稳定排序、屏障合并） → checkpoint / 下一超级步 嵌套节点 → 子图 PregelLoop → GraphInterrupt / ParentCommand └─ GraphBubbleUp 向父层传播

PULL 的上游是静态 Edge/Branch 生成的 trigger Channel；PUSH 的上游是 Send write 或 Functional API 的 Call。下游统一成为 PregelExecutableTask，由 Runner 执行并提交 writes。Runner 的职责定义包括并发执行、提交 writes、输出让步及必要时中断其他任务。证据：libs/langgraph/langgraph/pregel/_runner.py:135-180。

当前包要求 Python ≥3.10，并依赖 langgraph-checkpoint、langchain-core 与 xxhash；稳定 task id 的新 checkpoint 版本使用 XXH3。证据：libs/langgraph/pyproject.toml:5-32、libs/langgraph/langgraph/pregel/_algo.py:548-550。

3. 核心概念

概念准确含义容易混淆之处
PULL task节点订阅的至少一个 trigger Channel 出现未见版本后，按节点名拉取当前快照输入不是线程“拉队列”，也不是每轮无条件运行
PUSH task带显式参数的动态调用；来源是 Send 或 Functional Call不是普通 Edge 的别名
task idcheckpoint id、namespace、step、节点、任务类型及稳定路径部件的确定性摘要稳定指同一 checkpoint/路径重建一致，不是跨不同 checkpoint 永久不变
waiting edgeadd_edge([A,B], C)：A、B 均到达后 C 才可触发与 Send fan-out 后“等任意数量任务”不是同一能力
namespace嵌套图/节点/task 的 checkpoint 路径，task id 以 : 附着在 frame 上不同于用户业务 Store namespace
GraphBubbleUp中断、drain、父命令等控制流异常的共同基类不是应交给普通 node error handler 的业务错误

Send 的参数状态可以不同于主图状态，典型用途是 map-reduce：同一节点接收多份参数并行执行，结果写回带 reducer 的主图 Channel。证据：libs/langgraph/langgraph/types.py:704-747。

4. 架构组成

prepare_next_tasks

先按 TASKS Channel 顺序枚举 Send，再扫描被更新 Channel 对应的候选节点；候选集合有映射时排序，最后以 task id 为 key 返回。

libs/langgraph/langgraph/pregel/_algo.py:437-513

prepare_single_task

按路径首项分派 Functional PUSH、Send PUSH 或 PULL，并注入 task id、read/send 函数、Runtime、checkpoint map 与 namespace。

libs/langgraph/langgraph/pregel/_algo.py:524-595

NamedBarrierValue

保存预期 names 与 seen set；seen 等于 names 才 available，consume 后清空，以支持下一轮汇合。

libs/langgraph/langgraph/channels/named_barrier_value.py:13-81

ParentCommand 路由

子图 writer 发现 Command.PARENT 后抛 ParentCommand；retry 层按 namespace 逐层重写目标，直到最近父图消费。

libs/langgraph/langgraph/graph/state.py:1756-1772、libs/langgraph/langgraph/pregel/_retry.py:618-631

稳定 task id 的组成

  • PULL：checkpoint_id + checkpoint_ns + step + node + PULL + sorted(triggers)。libs/langgraph/langgraph/pregel/_algo.py:597-624
  • Send PUSH：checkpoint_id + checkpoint_ns + step + target node + PUSH + Send index。libs/langgraph/langgraph/pregel/_algo.py:961-997
  • Functional PUSH：再纳入父 task path 的规范字符串与该父 task 的 PUSH write 序号。libs/langgraph/langgraph/pregel/_algo.py:800-843

checkpoint v1 使用基于 SHA-1 的 UUID 形状摘要，v2 以后使用 XXH3-128；二者都把 namespace bytes 与稳定 parts 拼接为 UUID 形状字符串。证据：libs/langgraph/langgraph/pregel/_algo.py:1395-1409。

5. 完整运行流程

5.1 正常路径：Send fan-out → reducer 聚合

  1. 条件路由返回多个 Send("worker", arg)；branch writer 将它们写入 TASKS Channel。
  2. 屏障后，下一次 prepare_next_tasks 按 TASKS 中的 index 创建多个 PUSH task；每个 task 的输入是自己的 packet.arg。libs/langgraph/langgraph/pregel/_algo.py:441-466、libs/langgraph/langgraph/pregel/_algo.py:961-970
  3. Runner 并发执行这些 task；task 只向本地 writes deque 写入，deque.extend 被用于线程安全提交。libs/langgraph/langgraph/pregel/_algo.py:1060-1082
  4. 超级步结束后 apply_writes 合并结果；目标 state key 必须使用能处理多写的 reducer，否则并发更新会失败。Send 自身只负责 fan-out，不负责 reduce。
  5. 下一个 PULL 节点看到聚合 Channel 的新版本后被触发。

5.2 正常路径：Functional task

@task 调用从当前 Runnable config 取出 CONFIG_KEY_CALL，返回可同步等待也可 await 的 future；调度器将 Call 识别为 Functional PUSH，运行函数后把结果写到 RETURN。同步 task 不支持 timeout 时会在调用边界拒绝。证据：libs/langgraph/langgraph/pregel/_call.py:200-242、libs/langgraph/langgraph/pregel/_call.py:253-298。

5.3 拒绝与提前结束路径

  • PULL 节点不存在、checkpoint 无可比较版本、trigger 未前进或输入不可用时，任务不生成；这是无工作，不是错误。libs/langgraph/langgraph/pregel/_algo.py:597-646
  • Send index 越界、TASKS 不可用或目标进程无 runnable 时直接忽略；非法 packet 类型、未知节点名和非法 PUSH path 记录 warning 后忽略。libs/langgraph/langgraph/pregel/_algo.py:961-1000
  • Functional callable 无名称时抛 ValueError，同步 task 配 timeout 时抛不支持错误。libs/langgraph/langgraph/pregel/_algo.py:826-830、libs/langgraph/langgraph/pregel/_call.py:276-287
  • 根图收到 Command.PARENT 没有父层可路由，输入映射直接抛 InvalidUpdateError("There is no parent graph")。libs/langgraph/langgraph/pregel/_io.py:56-72

5.4 恢复与错误路径

恢复时同一 checkpoint 与 task path 会重建相同 id，使 pending writes 能归属到原 task，已经成功的 fan-out 不必因兄弟 task 中断而重复副作用。Send 去重恢复由 sync/async 用例覆盖。证据：libs/langgraph/tests/test_large_cases.py:4645-4683、libs/langgraph/tests/test_pregel_async.py:2530-2565。

普通异常按 RetryPolicy 匹配重试，每次尝试前清空旧 writes；ParentCommand 和其他 GraphBubbleUp 不进入普通重试匹配，而是作为控制流上抛。证据：libs/langgraph/langgraph/pregel/_retry.py:600-682。

9. 并发、性能与资源

并发单位是当前超级步的 task 集合，不是任意时刻对 state 的并发 mutation。PUSH 与 PULL 可以处于同一集合，Runner 负责并发执行；task 的 writes 隔离到各自 deque，屏障后合并。证据：libs/langgraph/langgraph/pregel/_runner.py:135-180、libs/langgraph/langgraph/pregel/_algo.py:706-759。

  • 确定性：候选 PULL 节点在优化路径排序；trigger 也排序；PUSH identity 使用持久顺序 index 或父 path+index，避免线程完成先后影响身份。libs/langgraph/langgraph/pregel/_algo.py:475-492、libs/langgraph/langgraph/pregel/_algo.py:613-623
  • 取消：任一未处理失败可令 Runner 取消仍在 flight 的 future 并重抛；异步取消是协作式，外部副作用仍需幂等。libs/langgraph/langgraph/pregel/_runner.py:650-685
  • 背压：本地调度器不定义分布式队列容量；大量 Send 会直接扩大下一超级步 task 数。应在路由前分批、限制输入规模或把外部工作移交有容量控制的系统。
  • 资源：input cache 在一次 task preparation 中复用节点输入读取；它不是跨 step Cache。libs/langgraph/langgraph/pregel/_algo.py:437-465
Send 顺序是恢复身份的一部分。对同一逻辑输入若恢复时生成不同顺序或数量，会得到不同 PUSH id；动态路由函数必须确定性，或把决定结果持久化为独立节点输出。

10. 安全与信任边界

Send.node 与 Command.goto 是本地图内路由能力，不是授权系统。运行时会拒绝/忽略不存在的节点，但不会判断调用者是否有业务权限；把用户输入直接作为目标名之前，应用必须用 allowlist 映射到已批准节点。证据：libs/langgraph/langgraph/pregel/_algo.py:971-984、libs/langgraph/langgraph/pregel/_io.py:56-72。

  • 有 checkpointer 时，Send arg、Functional task 输入/输出及 Channel writes 必须可由配置 serializer 安全处理；本模块不提供 Auth 或 Encryption。
  • checkpoint_ns 是内部定位符，不应作为租户隔离边界或接受外部直接写入。
  • fan-out 会放大外部 API、Tool 与数据库副作用；在路由前做数量、成本、权限和参数校验，失败默认应 fail-closed。
  • GraphBubbleUp 是可信控制流。普通 error handler 不应吞掉它；Runner 也显式排除这类异常的 error-handler 路由。libs/langgraph/langgraph/pregel/_runner.py:221-228、libs/langgraph/langgraph/pregel/_runner.py:296-303

17. 术语表

术语本文含义
BSP / Bulk Synchronous Parallel批量同步并行：同一超级步读取稳定快照，并行计算后在屏障统一合并。
PULL由 Channel/Edge 版本触发、按节点订阅读取输入的 task。
PUSH由 Send 或 Functional Call 携带显式参数创建的 task。
Send指定目标节点、自定义参数和可选 timeout 的动态调度包。
fan-out / fan-in把一份工作展开为多 task / 汇总多 task 的结果；fan-in 通常依赖 reducer 或静态 barrier。
Functional task@task 包装的函数调用，在 Pregel 内核中编码为带 Call 的 PUSH task。
task id从 checkpoint、namespace、step、节点和路径稳定派生的任务身份。
waiting edge多个静态前驱全部完成后才触发目标节点的边。
NamedBarrierValue保存预期 names 与已见 names、全部到齐才可读的 Channel。
reducer定义同一 Channel 多个 update 如何聚合的函数；Send 不替代 reducer。
checkpoint namespace区分嵌套图、task frame 与重复子图调用的持久化路径。
pending writes绑定 checkpoint 与 task id 的中间写，用于错误、中断和恢复去重。
GraphBubbleUp需要跨 task/子图边界传播、不能作为普通业务错误处理的控制流异常基类。
Command.PARENT把 update/goto 发送到最近父图的目标标记。
ParentCommand承载父图 Command 并逐层重写 namespace 的 GraphBubbleUp 子类。
superstep / 超级步一次 task 选择、并行执行、屏障合并和 checkpoint 推进周期。
