1. 模块定位

Functional API 是 LangGraph 的编排表面：开发者用普通 Python 的 if、循环、函数调用和 future 等待表达控制流，装饰器把入口转换成真正的 Pregel，把 task 调用转换成由 Runner 调度的 PUSH 任务。它不是脱离图运行时的“快捷执行器”。libs/langgraph/langgraph/func/__init__.py:516-620

负责委托明确不负责
装饰入口、推断输入/输出类型、创建 START/END/PREVIOUS Channel执行、并发、retry、cache、timeout 给 Pregel Runner定义 StateGraph 的 Node/Edge/Reducer DSL
把 task 调用参数封装为 Call 并返回 futuretask id、pending writes、恢复给 Loop/Checkpointer提供跨机器队列、鉴权或 exactly-once 外部副作用
通过 entrypoint.final 分离调用返回值与下次 previousinterrupt/stream/config/runtime 注入给共享公共协议自动补偿已经提交的数据库、HTTP 或文件副作用
选择边界：控制流天然由代码表达、希望把耗时步骤变成 durable task 时使用 Functional API；需要显式状态 Schema、reducer、可视化路由、多 actor 或声明式审计时优先 Graph API。两者可互相嵌套，但共享 Runtime 不等于共享同一种状态建模方式。

3. 核心概念

概念精确定义易混点
entrypoint类形态装饰器；调用后把单个用户函数包装为单节点 Pregel不是一个只执行函数的 wrapper
task把函数包装为 _TaskFunction；调用产生可等待的 future调用瞬间不是普通 Python 直接调用
Call内部载体，保存 func、(args, kwargs)、retry/cache/callback/timeout不是公共 Send，但同属 PUSH 调度

entrypoint.finalvalue 返回调用者，save 写 PREVIOUS两者都允许显式为 None

Call 的输入严格保存为 (args, kwargs)，functional PUSH 的 runnable 在执行前再 explode 参数；结果通过保留的 RETURN write 交回父 future。libs/langgraph/langgraph/pregel/_algo.py:120-152 libs/langgraph/langgraph/pregel/_call.py:200-242

4. 架构组成

4.1 _TaskFunction 与 task decorator

_TaskFunction.__call__ 不运行用户函数，而是把函数、实参和策略送入 _call_with_options；task 还提供同步/异步清 cache API，cache namespace 使用函数 identifier，动态函数回退为 __dynamic__。libs/langgraph/langgraph/func/__init__.py:59-106

4.2 entrypoint Pregel 外壳

entrypoint 节点订阅 START，writers 同时把结果映射到 END 与 PREVIOUS；START 是 EphemeralValue，END/PREVIOUS 是 LastValue。默认 stream_mode="updates" 且 stream_eager=True。libs/langgraph/langgraph/func/__init__.py:531-609

4.3 Runner call bridge

Runner 给当前任务 config 注入 CONFIG_KEY_CALL。每次调用用 scratchpad 的 call_counter() 取得顺序号，交 Loop 的 accept_push 构造稳定子任务；已运行 task 直接从 RETURN/ERROR writes 完成 future，否则提交执行。libs/langgraph/langgraph/pregel/_runner.py:700-786

4.4 functional PUSH materializer

prepare_push_task_functional 使用 checkpoint、namespace、step、函数名、父 path 与调用序号生成 task id，注入 task-local scratchpad、Runtime、Store、Checkpointer 和 checkpoint map，并按 call 级策略覆盖图级策略。libs/langgraph/langgraph/pregel/_algo.py:800-933

5. 完整运行流程

5.1 正常成功路径

  1. 调用 workflow.invoke(input) 或 ainvoke，Pregel 把 input 写 START，调度 entrypoint PULL task。
  2. entrypoint 内调用 decorated task；get_config() 找到 Runner 注入的 call bridge，立即得到 future。libs/langgraph/langgraph/pregel/_call.py:276-298
  3. Runner 用父 scratchpad call counter 创建 Call，Loop 以 PUSH path 接受并注册 task。libs/langgraph/langgraph/pregel/_runner.py:718-733 libs/langgraph/langgraph/pregel/_loop.py:550-587
  4. functional task runnable 执行并写 RETURN；commit 先调用 task 级 put_writes，链式 future 后完成，保证结果/stream 提交顺序。libs/langgraph/langgraph/pregel/_call.py:200-242 libs/langgraph/langgraph/pregel/_runner.py:604-613
  5. 父函数等待 future，最终值写 END；保存值写 PREVIOUS。invoke 返回 END，后续同 thread 从 PREVIOUS 注入 previous。

5.2 拒绝与提前结束路径

  • entrypoint 没有任何参数：装饰时抛 ValueError；生成器/异步生成器直接抛 NotImplementedError。libs/langgraph/langgraph/func/__init__.py:525-543
  • 同步 task/entrypoint 配 timeout：装饰时拒绝，因为进程内同步函数不能安全取消；不会“尽力超时后继续”。libs/langgraph/langgraph/func/__init__.py:224-246
  • 同步运行上下文调用 async task：Runner 抛 RuntimeError("In an sync context async tasks cannot be called")。libs/langgraph/langgraph/pregel/_runner.py:700-717
  • 空 Command、无 checkpointer 的 resume、多 pending interrupt 却给单值都 fail closed。libs/langgraph/langgraph/pregel/_loop.py:902-931

5.3 Interrupt 与恢复路径

  1. entrypoint 或 child task 调用 interrupt(value)，GraphInterrupt 由 commit 保存为 INTERRUPT pending write；child call path 的 interrupt 由父任务统一对外呈现。libs/langgraph/langgraph/pregel/_runner.py:574-603 libs/langgraph/langgraph/pregel/_loop.py:1417-1451
  2. 客户端以同一 thread 发送 Command(resume=...)；Loop 先持久化 RESUME，再从 entrypoint 开头重跑。libs/langgraph/langgraph/types.py:851-871 libs/langgraph/langgraph/pregel/_loop.py:902-951
  3. 相同父 path 与 call 顺序产生相同 task id；Loop 把成功 task 的 pending writes 重放到内存 task，Runner 直接从 RETURN 完成 future，不重做已成功 task。libs/langgraph/langgraph/pregel/_algo.py:831-846 libs/langgraph/langgraph/pregel/_loop.py:736-749
  4. 先前失败/中断的 task 不重放 ERROR/INTERRUPT，因而按规则重试或再次中断；这不是恢复 Python 栈帧。
恢复约束：恢复依赖调用路径与调用序号稳定。修改分支、循环次数或 task 调用顺序会改变后续 functional task 的身份；发布代码变更后恢复旧 checkpoint 必须做兼容验证。已成功 LangGraph task 可跳过，不代表 task 内外部副作用天然 exactly-once。

9. 并发、性能与资源

  • 并行来源：先创建多个 task futures，再集中 .result() 或 asyncio.gather，Runner 可并发执行；先创建一个并立即等待会串行化。同步测试明确说明 mapper stream 顺序不确定。libs/langgraph/tests/test_pregel.py:1277-1314
  • 线程安全边界：每个 task 有独立 writes deque；注入的 send 使用 deque.extend，源码标记线程安全。外部数据库和文件不受此保护。libs/langgraph/langgraph/pregel/_algo.py:893-925
  • 失败传播：未处理异常使 Runner 停止其他任务并取消 inflight futures；取消是尽力而为，阻塞同步函数不能安全抢占。libs/langgraph/langgraph/pregel/_runner.py:616-697
  • async 取消：异步 child future 取消会向 source future 传播；跨 event loop 时用 thread-safe callback。libs/langgraph/langgraph/_internal/_future.py:82-124
  • stream 不缓冲到结尾：同步 Functional 测试验证两个慢 task 更新分开到达。libs/langgraph/tests/test_pregel.py:6269-6304
  • 资源预算：大量未等待 future 会占用 executor/task、内存、pending writes 与外部连接；源码不声明 Functional API 自带背压容量，应用应限制 fan-out。
并发失败安全：一个 sibling 失败后，另一个可能已完成并提交副作用，也可能只收到取消请求。恢复能重用已持久化 RETURN，但不能回滚外部世界。设计 task 时使用幂等键（可由 thread/task/run 身份派生）、事务或补偿流程。

10. 安全与信任边界

输入与序列化类型注解主要用于 JSON schema 与 serde allowlist，不自动执行完整业务校验。启用 checkpointer 时 task 输入输出必须可序列化。libs/langgraph/langgraph/func/__init__.py:150-156
反序列化strict msgpack allowlist 是可选防线；升级 schema、移动类型模块或恢复旧 checkpoint 前应做 migration 测试。libs/langgraph/langgraph/func/__init__.py:610-619
Secret不要把密钥放进 entrypoint 返回、PREVIOUS、task args、interrupt value 或 stream chunk；这些表面可能进入 checkpoint、trace 或客户端。
权限与租户本地 Functional API 不提供 Auth 或多租户隔离。Store namespace、thread_id 的授权与工具副作用策略必须由应用/Server 边界实施。

task 允许类方法、partial 和 callable object，并尝试生成稳定 identifier；动态/本地函数可能退化为动态身份。不要把可调用对象名称或 cache key 当安全授权依据。libs/langgraph/langgraph/pregel/_call.py:84-154

15. 设计权衡与已知限制

代码控制流 vs 图可见性Python 分支与循环开发自然，但静态图只能看到 entrypoint 外壳，运行前难以完整展示动态 task DAG。
稳定 call 序号 vs 演进自由父 path + 顺序号让恢复可重放，却使流程代码重排成为 checkpoint 兼容事件。libs/langgraph/langgraph/pregel/_algo.py:831-846
future 易用性 vs 资源无界批量创建 future 很适合 fan-out；核心源码未声明固定容量或业务背压策略，调用方必须限流。
task 级 durable writes vs 外部一致性RETURN 可避免成功 task 重算；外部副作用仍需事务、幂等键或补偿。
统一 Runtime vs 不同 State 模型Functional 与 Graph API 共用 Pregel/checkpoint/interrupt/stream，但 Functional 的主要持久值是 input/output/previous/task writes，不等同 StateGraph reducer map。
async timeout vs sync 拒绝只支持可协作取消的 async timeout 是保守且安全的选择；同步阻塞工作需外部进程/作业系统管理。libs/langgraph/langgraph/func/__init__.py:158-169

当前生成器 entrypoint 明确不支持；若需要业务进度流，使用注入的 Runtime.stream_writer/StreamWriter 或把进度拆成 task，而不是依赖 yield。libs/langgraph/langgraph/func/__init__.py:525-529

17. 术语表

术语本章含义
Functional API用 Python 函数控制流表达工作流、由 entrypoint/task 映射到 Pregel 的公开编程表面。
Entrypoint一次 Functional 工作流的入口函数及其生成的单节点 Pregel。
Task可独立调度、重试、缓存、持久化结果并返回 future 的函数调用。
PUSH Call由正在运行的父任务主动创建、携带 Call 的 Pregel PUSH 任务。
PULL由 Channel 版本与图触发关系选出的普通节点任务；entrypoint 自身从 START 以此方式触发。
Future代表尚未完成 task 结果的对象；同步用 .result()，异步可 await。
Call counter父 scratchpad 中按调用顺序递增的序号，是 functional task 稳定身份的一部分。
RETURN writefunctional task 的保留结果 write，用于恢复和完成父 future。
Previous同一 thread 上一轮 entrypoint 保存到 PREVIOUS Channel 的值。
entrypoint.final把当前调用返回值 value 与供下一轮读取的 save 分离的泛型数据类。
Pending writes绑定 checkpoint 与 task id 的中间写；承载 RETURN、ERROR、INTERRUPT、RESUME 等恢复证据。
Durable execution依靠 checkpoint 与 task writes 在进程/时间边界后恢复执行；不承诺外部副作用 exactly-once。
Checkpoint namespace区分入口、嵌套任务和子图持久化作用域的路径。
Interrupt / Resume可持久暂停并用 Command(resume=...) 从任务开头重跑、消费已保存恢复值的协议。
Graph APIStateGraph 的声明式 Node/Edge/Channel/Reducer 表面；与 Functional API 共享 Pregel 内核。
Exactly-once副作用恰好发生一次的强保证；LangGraph task 恢复去重本身不提供该保证。
