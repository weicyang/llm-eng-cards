3. 核心概念

Transport（传输）

实际发给 LiteLLM 的 provider、model、api_base、凭据与 kwargs。OpenHands 前缀只在此边界转换。

Capability（能力）

模型是否支持 Responses、reasoning、采样参数、显式缓存、vision 等。查询使用 canonical model，不等同于 transport model。

Chat Completions

以 messages 和 OpenAI chat tool schema 调用，流式 chunk 最后由 LiteLLM 重建成 ModelResponse。

Responses API

将 system 内容映射到 instructions，其余映射到 input[]，输出 item 再恢复为 SDK Message。

Native function calling

provider 原生接收 tools/tool_choice，并返回结构化 tool call。

Non-native function calling

把工具契约嵌入 prompt，用 stop words 限制文本，再将模型文本解析回结构化 tool call。

能力解析的优先级是：显式 capability_overrides → LiteLLM/model metadata → SDK 内置 fallback；布尔解析保留显式 False，Responses 的 metadata endpoint 列表一旦存在，其“缺少 Responses”也具有权威性。openhands-sdk/openhands/sdk/llm/utils/model_features.py:255-277 openhands-sdk/openhands/sdk/llm/utils/model_features.py:331-346 openhands-sdk/openhands/sdk/llm/utils/model_features.py:349-405

9. 并发、性能与资源

  • 同步/异步对称：四入口共享准备、校验、options、Telemetry 和 Tenacity decorator；异步 transport 直接 await litellm.acompletion/aresponses，并非把主请求放进线程。openhands-sdk/openhands/sdk/llm/llm.py:1614-1716 openhands-sdk/openhands/sdk/llm/llm.py:1885-2055
  • 第三方包装器兼容：异步 Chat/Responses 若收到同步 iterable，会在 executor 中一次性转换成 list，避免直接阻塞 event loop；代价是失去逐 chunk 的实时回调和增加内存峰值。openhands-sdk/openhands/sdk/llm/llm.py:2241-2256 openhands-sdk/openhands/sdk/llm/llm.py:1980-2012
  • 背压：callback 在读取下一 chunk 前同步执行或 await，因此慢 callback 会自然拖慢消费；源码没有独立 token queue 或丢弃策略。
  • 流式内存：Chat 为重建最终响应会保留所有 chunks；Responses 保留完成的 output items。长输出的峰值由 provider chunk 数与内容决定，源码没有独立上限。
  • 锁：runtime metadata cache 使用 class-level thread lock，只保护 cache 字段；网络 I/O 不在锁内。openhands-sdk/openhands/sdk/llm/llm.py:646-665
  • 重试预算：等待为指数退避；同步与异步 coroutine 都由 Tenacity 原生包装。fallback 在主重试耗尽后再启动，整体最坏耗时还包括每个 fallback 自身重试。

15. 设计权衡与已知限制

问题当前选择与收益成本/失败模式重评条件
一个门面支持两套 API调用方获得统一 Message/Tool/Response两套序列化、stream 与 provider 差异都集中在大类中Responses 与 Chat 契约分歧使共享层持续产生条件分支
能力与 transport 分离proxy alias 可用 canonical model 查能力配置错误会造成错误能力声明provider 提供稳定、可认证的 runtime capability discovery
non-native tool prompt mock无原生 function calling 的模型仍能用于 Agent解析脆弱，stop words 依 provider，不能当安全边界目标模型普遍可靠支持 native tools
收集 stream 后返回完整响应保持非流式与流式统一返回契约及 usage长输出占内存；callback 是串行背压点出现超长流或需要零拷贝下游
异步 fallback 运行同步 fallback复用成熟策略并避免 event loop 阻塞executor 线程、async callback 被 cast 为 sync callback，复杂回调可能不适用fallback 需要原生异步凭据刷新或高并发 streaming

fallback per call下一请求自动回到主模型，避免永久漂移主 provider 长故障时每次都先付出主重试延迟需要 circuit breaker、健康评分或全局路由器
Router 统一外观同步 Chat completion 可按消息选择候选模型，调用方仍使用 LLM 类型active_llm 可变且并发调用会互相覆盖；async/Responses 入口当前未接入选择逻辑需要跨四入口一致路由、并发安全的 per-call selection 或 route-aware capabilities

17. 术语表

术语本文含义
LLMLarge Language Model，大语言模型；本文也指 SDK 的 LLM 调用门面。
Chat Completions以 messages/choices 为核心的 OpenAI 兼容调用协议。
Responses API以 instructions/input/output items 为核心、可表达 reasoning item 的调用协议。
LiteLLMSDK 下游的多 provider 适配库，负责 provider 推断、HTTP 调用、stream 与 cost catalog 等。
Provider模型服务提供方或 LiteLLM 路由类型；不同于模型本身的 capability。
Transport真正发给 LiteLLM 的 model/provider/api_base/credentials/kwargs 组合。
Capability / Model Feature模型是否支持 Responses、reasoning、vision、采样参数、缓存等的规范判断。
Canonical model用于能力查找的规范模型名；可与 proxy transport model 不同。
Native function calling供应商原生接收工具 schema 并返回结构化 tool call。
Non-native function calling用 prompt 和解析器模拟工具调用协议，也称 prompt-mocked tool calling。
Streaming在完整响应完成前逐 chunk/delta 消费输出；最终仍重建完整 response。
Token callback请求内接收 stream chunk 的同步或异步回调，不是持久化 Conversation Event。
Telemetry采集单次成功响应 latency、usage、cost，并选择性记录 completion 的运行组件。
Metrics实例内累积 cost、token usage、latency 的结构化统计及 snapshot/diff/merge 能力。
Retry同一 LLM 请求因白名单瞬时错误在 Tenacity 边界内重新 attempt。
Fallback主模型 retry 耗尽后，按 profile 顺序尝试其他 LLM；每个新请求仍从主模型开始。
SigV4AWS Signature Version 4；Bedrock IAM 凭据签名方式，不等同于 LiteLLM 的 Bedrock bearer token。
Prompt cacheprovider 对输入前缀的缓存能力；SDK 仅在 feature 支持且配置启用时放置显式标记。
Negative cache运行时 metadata 探测失败后的短期失败缓存，避免持续请求不可用上游。
RouterLLM继承 LLM 并在当前同步 completion() 入口按 messages 选择候选 LLM 的路由基类。
MultimodalRouter图片或 secondary 输入容量不足时选 primary，否则选 secondary 的内置 RouterLLM。
Backpressure下游 callback/消费者速度反过来限制 stream 读取速度；本实现通过串行调用自然产生。
