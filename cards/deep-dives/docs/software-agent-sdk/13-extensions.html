扩展生态：Skill、Plugin、Marketplace 与 Subagent

本章解释扩展内容如何被发现、规范化、合并、注册和执行，并明确 “内容扩展”“能力打包”“来源目录”“委派运行时”“外部 Agent 协议适配” 之间不能混写的边界；现有委派能力不等于完整异步、多 Agent 容错调度系统。

1. 模块定位

扩展生态不是一个单一加载器，而是四种不同抽象的协作：Skill 提供可披露知识， Plugin 把多类扩展规范化为内存对象，Marketplace 解析名字到来源，Subagent registry 把定义解析为 Agent factory；真正运行委派任务的 TaskManager 属于 Tools 包。Plugin 还可携带 Hook，但 Hook 的执行策略由 Hooks 子系统拥有。 openhands-sdk/openhands/sdk/plugin/plugin.py:36-71 openhands-tools/openhands/tools/task/manager.py:95-110

论文基线：官方论文 arXiv:2511.03690 §4.5 用“blocking sub-agent delegation（阻塞式子 Agent 委派）”展示 Tool 扩展性：父 Agent 等待子任务完成，论文还把异步委派、动态调度和容错恢复列为 可由自定义 Tool 继续扩展的方向，而不是已经交付的核心协调器。论文 §7 更明确说明 基线实现聚焦 single-agent conversations（单 Agent 会话），完整多 Agent 协调机制仍需进一步设计。当前源码中的 Task/Subagent 与 ACP 是后续或并行扩展； 不能用它们反向改写论文当时的完成度。

3. 核心概念

Skill：提示上下文，不是 Agent

AgentSkills 格式的 Skill 总是以名称和描述出现在 <available_skills>，完整正文按需通过 invoke_skill 取得；有 trigger 时也可自动注入。旧 OpenHands Skill 无 trigger 时直接成为 常驻仓库上下文。描述上限为 1024 字符，提示目录刻意不暴露 location，避免模型绕过 invoke_skill。 openhands-sdk/openhands/sdk/skills/skill.py:178-235 openhands-sdk/openhands/sdk/skills/skill.py:1431-1511

Plugin：能力包与格式中立模型

Plugin 统一承载 manifest、skills、hooks、MCP server map、agents 与 commands；磁盘布局由 PluginFormat 策略解释。当前格式 registry 只注册 Claude Code 兼容格式；Agent Plugins v1 适配器已经存在，但因 mcp.json 与客户端扩展加载尚未完成而未启用。 openhands-sdk/openhands/sdk/plugin/plugin.py:1-27 openhands-sdk/openhands/sdk/plugin/format/__init__.py:19-26 openhands-sdk/openhands/sdk/plugin/format/__init__.py:62-81

Marketplace：目录与解析器，不是安装隔离层

Marketplace manifest 列出 Plugin 和独立 Skill；注册项给出 source/ref/repo_path 以及是否自动加载。Registry 延迟 fetch、进程对象内缓存 manifest，并将 plugin 或 plugin@marketplace 解析为 PluginSource。 未限定名称命中多个市场时必须报歧义，不能按迭代顺序静默选择。 openhands-sdk/openhands/sdk/marketplace/types.py:168-215 openhands-sdk/openhands/sdk/marketplace/registry.py:120-149 openhands-sdk/openhands/sdk/marketplace/registry.py:185-231

Subagent：专用 Agent + 独立 LocalConversation

Registry 中保存的是 AgentFactory(factory_func, definition)。TaskManager 用父 LLM 的副本调用 factory，再新建一个 LocalConversation；因此 Subagent 不是 Conversation 子类，而是一次委派中使用的 Agent 配置。Task 是运行记录， 只保留 id、conversation_id、结果/错误和可被回收的 Conversation 引用。 openhands-sdk/openhands/sdk/subagent/registry.py:49-58 openhands-tools/openhands/tools/task/manager.py:64-92 openhands-tools/openhands/tools/task/manager.py:361-378

ACP：外部 Agent 后端，不是多 Agent 协调器

ACPAgent 是 AgentBase 子类。它通过 Agent Client Protocol 启动并连接 Claude Code、Gemini CLI 等兼容 server；server 管理自己的 LLM、 工具和执行，而 OpenHands 转发用户消息、收集更新并把一个完整 assistant turn 映射为一次 step。它扩展的是“Agent 实现来自哪里”，不是“多个 Agent 如何协作”。 openhands-sdk/openhands/sdk/agent/acp_agent.py:1-14 openhands-sdk/openhands/sdk/agent/acp_agent.py:1535-1562 openhands-sdk/openhands/sdk/agent/acp_agent.py:2588-2750

4. 架构组成

发现层

Skills、Plugins、file agents 各有目录规则和同名合并规则。单个坏文件通常记录 warning 后跳过。

格式层

PluginFormat 将不同磁盘协议变成统一 Plugin；检测顺序是格式优先级。

合并层

Plugin Skill/MCP 是同名后写覆盖，Hook 是连接；Agent registry 则是 first registration wins。

执行层

Task Tool 把 Action 转为 TaskManager 的阻塞调用，并将成功或错误封装为 Observation。

治理层

权限策略和 Hook 配置进入子 LocalConversation；二者不是 Tool 白名单的替代品。

恢复层

显式插件保存 resolved ref；环境插件重新发现；Task resume 用原 conversation UUID 重建会话。

三层事实不要合并：论文 §4.5 的基线是父调用阻塞等待子 Agent； 当前 TaskExecutor 仍明确是 blocking only，TaskManager.start_task() 同步运行并返回最终 Task；Subagent registry 只解析 Agent factory；ACPAgent 只适配一个外部 Agent server。三者组合后仍没有统一的异步任务队列、持久调度器、 跨 Agent 事件仲裁或 exactly-once 副作用协议。 openhands-tools/openhands/tools/task/impl.py:1-38 openhands-tools/openhands/tools/task/manager.py:164-201 openhands-sdk/openhands/sdk/subagent/registry.py:49-58

15. 设计权衡与已知限制

懒加载降低构造副作用，但把失败推迟到首次交互

好处是构造器不做网络/磁盘 I/O，Agent 能在 Plugin 完整合并后一次初始化； 成本是配置错误可能直到第一条消息才暴露。需要启动期预检的部署应显式做 discovery/fetch 验证，而不是假设构造成功等于可运行。

Registry first-wins 简单可解释，但全局状态受导入时序影响

RLock 保证原子性，不能让“程序注册必然优于内置”脱离调用顺序成立。所有 非 programmatic 来源用 if-absent，谁先注册谁保留；agent-server 若在每会话发现前 已注册 builtins，builtins 也会占据名称。需要严格租户隔离时，应重新评估进程级 registry，而不是继续叠加来源条件。

Plugin 合并与 agent 注册采用相反冲突策略

Skill/MCP 后写覆盖便于显式插件定制，Hook 连接保留所有治理，agent first-wins 防止低优先级来源替换 factory。统一成单一“最后写”规则会更短，却会破坏安全和 来源可解释性。

恢复确定性分层

显式 Plugin 固定 resolved ref，环境 Plugin 和 project Skill 反映当前磁盘； Task resume 固定 Conversation UUID，但仍会经过当前运行时的扩展发现。若需要完全 可复现，必须固定所有远端 ref，并把环境扩展版本纳入部署快照。目前没有统一扩展 lockfile、签名验证或跨进程 Marketplace cache。

故障隔离不等于副作用回滚

Task 异常被包装为 ERROR，父循环可继续；但父子共享 Workspace，子工具在失败前 已产生的文件或外部系统副作用不会由 TaskManager 事务回滚。可重试性必须按工具 幂等性和实际 Observation 判断。

委派扩展不等于完整多 Agent 系统

论文 §4.5 的 blocking delegation 证明“可通过 Tool 扩展委派”，论文 §7 则保留了完整协调设计问题。当前 TaskManager 增加独立 EventLog、错误 Observation、 resume 和 metrics/trace 关联，ACPAgent 增加外部 Agent 协议适配；这些是有价值的 演进，但 Task 调用仍阻塞，TaskManager 没有持久任务队列或自身调度上限，父子默认 共享 Workspace，失败前副作用不能事务回滚。本文因此不把当前能力描述为异步、 动态、容错的通用多 Agent orchestration。 openhands-tools/openhands/tools/task/manager.py:164-201 openhands-tools/openhands/tools/task/manager.py:380-478 openhands-tools/openhands/tools/task/manager.py:295-330

17. 术语表

AgentSkills
一种 Skill 目录/元数据规范；本仓库以 SKILL.md、description 和可选资源目录表达，并支持渐进披露。
Ambient Plugin（环境插件）
从用户、项目或 enabled 安装目录自动发现的 Plugin；不记录 resolved ref，恢复时重新发现。
Explicit Plugin（显式插件）
通过 Conversation 的 plugins 参数或运行时 load_plugin 明确附加的 Plugin。
First registration wins
首次注册胜出；Subagent registry 中已有名称不会被后续非强制来源覆盖。
Last-wins
后写胜出；Plugin Skill 与 MCP server 同名时使用后加载值，与 agent registry 规则不同。
Factory
接收 LLM 并返回完整 Agent 的函数；registry 同时保存 factory 和 AgentDefinition。
Marketplace
扩展目录，保存 Plugin/Skill 名称与来源；不等于包管理器、沙箱或信任认证。
PluginFormat
插件磁盘格式适配策略；负责检测、读取各组件并产出格式中立 Plugin。
Progressive disclosure（渐进披露）
先向模型提供 Skill 名称和摘要，真正需要时再装入全文，以减少固定 prompt 体积。
Resolved ref
远端 branch/tag 解析后的确定提交标识，用于显式插件恢复时固定内容。
Subagent
由专用 Agent 配置驱动、在独立 LocalConversation 中运行的委派执行者；不是 Conversation 子类。
Task
TaskManager 对一次委派的运行记录，包含 task id、conversation UUID、状态、结果或错误。
Blocking delegation
阻塞式委派；父工具调用等待子会话结束并取得结果。上层可以并行调度多个调用，但单个 TaskExecutor 不是异步任务提交 API。
ACP
Agent Client Protocol，Agent 客户端协议；ACPAgent 用它连接管理自身 LLM、工具与执行的外部 Agent server，不定义多 Agent 协调。
Multi-agent orchestration
多 Agent 编排；通常还需要任务调度、事件仲裁、取消、权限、持久队列和故障恢复等协调机制，不能仅由“存在子会话”推断已经具备。
Hook
挂接消息、工具、会话和停止边界的治理处理器；Plugin 可携带 Hook，但 Hook 也可独立配置。
MCP
Model Context Protocol，模型上下文协议；Plugin/Skill 可贡献 server 配置，真正连接与工具执行由 MCP 子系统负责。
LLM
Large Language Model，大语言模型；子 Agent 默认复制父 LLM 配置并独立计量，显式 profile 可替代它。
Fail-open / fail-closed
依赖失败时继续还是拒绝运行。本模块按来源区分：环境发现多为继续，显式插件初始化多为抛错停止。
