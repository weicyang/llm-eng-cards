05 Cordis 插件内核

解释服务发现、类型事件、作用域和可逆生命周期如何把整个 Harness 组织成插件树。

1. 模块定位

Cordis 位于所有 Harness 包之下。Context 同时是服务仓库、事件总线、作用域节点和 effect 所有者；Harness 的核心循环、模型、工具和产品面都只是其上的插件贡献。

边界说明
负责Cordis 位于所有 Harness 包之下。Context 同时是服务仓库、事件总线、作用域节点和 effect 所有者；Harness 的核心循环、模型、工具和产品面都只是其上的插件贡献。
委托插件把能力协议交给 Service Definition，把实现交给 Provider，把使用行为交给 Consumer；产品组合决定哪个 Provider 可见。
不负责本模块不拥有 Agent 的 Turn/Step，也不拥有某个工具或模型的业务协议。

2. 系统位置与依赖

Cordis YAML Loader、函数插件或 Service 类 ↓ Cordis 插件内核 ↓ Service、typed event、effect disposer 与子 Context

依赖方向遵循显式 Service、Event、Tool 或 wire 接口；实现包不得从相邻模块私有状态反推所有权。兄弟 Provider 共享同一公共协议，产品组合负责选择实现。

3. 核心概念

  • Context：服务、事件和生命周期的共同作用域。
  • inject：插件激活前必须满足的服务依赖。
  • waterfall：监听器可改写结果且必须调用 next() 才委托下游。
  • Fiber：插件从 pending 到 active，再经 unloading 收敛到 disposed 的生命周期实例。
当前事实当前事实：由当前工作区实现或公共类型直接证明。
运行态运行态：只存在于进程内，不是恢复后的事实来源。
持久事实持久事实：追加到 SessionEvent log，恢复和投影都从这里派生。

4. 架构组成

#组件与职责生命周期与故障隔离
1Service registry：发布和解析 ctx key。由 owning plugin 的 effect 管理，失败不发布半状态。
2Event dispatcher：提供 emit、waterfall、parallel、serial 四种时序。由 owning plugin 的 effect 管理，失败不发布半状态。
3Effect owner：登记 disposer，使卸载和 HMR 可逆。由 owning plugin 的 effect 管理，失败不发布半状态。
4Scope library：把注册和事件绑定到 global、preset 或 agent 继承链。由 owning plugin 的 effect 管理，失败不发布半状态。

5. 完整运行流程

成功路径

  • Loader 解析 entry 并导入插件。
  • inject 依赖全部可见后 Fiber 执行 apply。
  • 插件通过 effect 注册服务、事件或工具。
  • Fiber 进入 ACTIVE，消费者从自己的 Context 解析能力。

拒绝或提前结束

  • 缺少 inject 时 Fiber 保持 PENDING，启动断言最终报错。
  • 插件 apply 抛错时 Fiber 进入 FAILED，不发布半套能力。

恢复、中断或降级

  • 卸载先阻止新贡献，再逆序运行 disposer。
  • 所有 effect 清理完成后 Fiber 才进入 DISPOSED；重新装载创建新 Fiber。

6. 数据与状态模型

Context/Fiber/effect 是运行态；只有插件自己追加的 SessionEvent 或外部存储是持久态。服务是否存在不能替代关系不变量。

状态发布只能发生在提交点之后；缓存、UI 和查询视图从权威事件或 Service 状态派生，不能建立第二条写路径。

7. 接口、协议与事件

Service 发布与解析、Context 继承、typed event dispatch 和 disposer 是核心接口。waterfall 的 next()、serial 的有序等待以及 parallel 的并发等待是调用者可依赖的时间语义。

调用者必须保留身份、取消、错误和时序语义；跨进程或模型 JSON 输入在边界验证，同进程 typed interface 信任 TypeScript。

8. 配置与默认行为

Cordis 自身由 entry row 和 inject 关系驱动；具体 Config 归各插件所有。配置被 Loader 解析不等于 Fiber 已激活。

原则默认/优先级失败行为
显式 resolve由 owning implementation 在执行前解析缺失 referent 或歧义 fail loud
Composition后层 row 覆盖前层，agent scope 可 shadow global不静默 deep merge 或选择第一个 Provider

9. 并发、性能与资源

parallel 监听器并发等待；serial 监听器按注册顺序等待；waterfall 是显式委托链。卸载必须等待由 effect 拥有的异步资源收敛。

只记录源码定义的队列、锁、预算和超时；没有实测证据时不承诺吞吐、延迟或 SLA。

10. 安全与信任边界

Context 是进程内信任域，不是隔离边界。动态插件与宿主代码权限相同；安全约束必须由 sandbox、approval 或进程边界实施。

Prompt、UI 隐藏和 schema omission 不是权限强制；安全决策必须在执行副作用的 operation 中实施。

11. 失败、恢复与兼容

故障/现象检测与即时行为恢复/运维
PENDINGPENDING：检查缺失 inject 或错误 scope。检查对应事件、Fiber/Agent 状态和 owner 日志；修复配置或使 lifecycle 收敛。
FAILEDFAILED：检查插件 apply 日志和配置验证。检查对应事件、Fiber/Agent 状态和 owner 日志；修复配置或使 lifecycle 收敛。
卸载不结束卸载不结束：检查 disposer 是否仍持有任务、socket 或子进程。检查对应事件、Fiber/Agent 状态和 owner 日志；修复配置或使 lifecycle 收敛。

当前为预发布版本；涉及 Session/SQLite 等格式时按 owner 的版本拒绝策略处理，不假设存在迁移。

14. 开发与扩展指南

变更目标同步修改必要证明
新增服务先定义当前 Consumer 所需的最小接口。更新 owner 类型/实现、README/JSDoc、相关事件或 Config。unit + real composition；模型可见变化加 keyless snapshot。
所有 register 返回 disposer 并用 ctx.effect/ctx.on 归属。更新 owner 类型/实现、README/JSDoc、相关事件或 Config。unit + real composition；模型可见变化加 keyless snapshot。
新增 waterfall listener 必须测试 next() 委托和短路。更新 owner 类型/实现、README/JSDoc、相关事件或 Config。unit + real composition；模型可见变化加 keyless snapshot。

15. 设计权衡与已知限制

统一插件模型带来可替换性和 agent-local 组合，但调用关系分布在 entry、inject 和事件监听器中。诊断必须查看 Fiber 状态，不能只看 import 是否成功。

重评条件：当前 Consumer、恢复不变量、安全边界或部署拓扑发生变化，并有源码与测试证明原选择不再满足。
