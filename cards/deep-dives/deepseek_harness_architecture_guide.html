01

DeepSeek Harness 是什么？

一句话说清：DeepSeek Harness 是一个"插件式 Agent 运行框架"。 它不是"一个更大的 Agent 类"，而是一棵用 Cordis 插件内核组装起来的树： 核心循环、会话记录、模型调用、工具、权限、持久化、甚至你看到的网页界面， 全部是挂在树上的插件。换一个模型、换一个沙箱、加一种新能力， 都是"换零件 / 加零件"，而不是拆开重写。

"Harness" 直译是"挽具"——套在马身上、让马力变成可控牵引力的装备。这个比喻很贴切：大模型本身像一匹有力但不受控的马，Harness 做的事就是给它套上缰绳和车架，让它的力量变成可编排、可审计、可替换、可恢复的 Agent 执行过程。

问题为什么"一个大 Agent 类"不够用
最朴素的 Agent 写法是一个大循环类：读消息 → 调模型 → 调工具 → 写回去。问题很快出现：
  • 换模型厂商、换执行沙箱、换存储后端，都要动核心代码；
  • 崩溃之后没法恢复，因为"发生过什么"只存在于内存里；
  • 加压缩、加审批、加后台任务，全往循环里塞，最后变成没人敢碰的巨型状态机；
  • 同一个核心想同时服务网页、命令行、编辑器协议，代码互相纠缠。
答案Harness 的四个选择
  • 一切皆插件：能力做成可替换的"接缝"，用声明式配置装配；
  • 日志即事实：所有交互追加进一本不可篡改的 Session 账本，恢复、审计、UI 全从账本重算；
  • 主循环极薄：循环只管"何时开始、何时结束"，压缩、重试、后台任务都挂在公开扩展点上；
  • 同核多壳：Web、命令行、ACP、SDK 四个产品面共享同一个内核。

先澄清：它"不是"什么
  • 不是模型：它不提供智能，智能来自 DeepSeek 等外部模型；它负责的是把模型"挽"起来干活。
  • 不是聊天产品本身：它可以装配成 Web 聊天应用，也可以是一次性命令行任务、编辑器背后的自动化服务。产品形态是"装配结果"，不是内核。
  • 不是以"多 Agent 协作"为主链路的框架：主链路上只有一个 Agent 在循环；Subagent、Workflow 等协作能力是可选扩展，且全部复用既有扩展点，不改动主循环。
  • 不是安全隔离系统：它内置沙箱与审批，但插件运行时与宿主代码权限相同；真正的隔离边界是操作系统沙箱和进程边界（3.8 节详述）。

02

一次任务的完整旅程

抽象的架构很难记住，故事好记。假设你在终端里敲下这样一条命令：

# 一次性（headless）模式：接收一个任务，跑完，打印结果
$ pnpm dsh --profile headless "给重试逻辑补单元测试"

从回车到输出答案，系统内部会依次发生下面七件事。每一步标注了"谁负责"：

启动装配：把插件树拼出来
Boot · Profile / Bundle / Preset

启动器先读环境变量和 .env（进程环境变量 > 当前目录 .env > DSH_HOME 的 .env），再按固定顺序叠加配置：bundles → profile patch → home patch → 命令行 --patch。--profile headless 选中 headless 这组 bundle，合成出最终的插件清单。注意：后一层是整行替换前一层，不做"智能合并"。

激活断言：拒绝"半活"启动
Cordis Loader · Fiber

Loader 按依赖图逐个激活插件（每个插件的生命周期实例叫 Fiber）。全部就位后，启动器做一次断言：只要还有插件卡在 PENDING（依赖缺失）或 FAILED（激活出错），就直接终止启动——宁可启动失败，也不允许"服务器起来了但核心能力没装上"的半活状态。

创建 Agent：一次事务，全成或全不成
Agent Registry

Registry 以事务方式创建：Session（账本）→ 作用域与 preset（这个 Agent 专属的能力集合）→ Agent 实例 → AgentHandle（交给调用者的"遥控器"，含销毁权）。任何一步失败，已创建的资源全部反向回收，不会留下"有账本没 Agent"这种孤儿。

消息进 Inbox：贴上"下一轮处理"的便签
Inbox

你的任务文本通过 send 进入 Agent 的收件箱（Inbox），路由类型是 followup——意思是"作为下一个 Turn 的输入，并唤醒 Agent"。Inbox 的每次写入本身也会记入账本，所以"收到过什么消息"事后可查。

Turn 打开，Step 循环开始
ReactLoopAgent · Turn / Step

Agent 被唤醒，先写一条 turn/start 事件（一个 Turn = 处理你这条意图的完整周期），然后进入 Step 循环：组装 system prompt → 通过 pre-step 检查点（插件可在此改写或拒绝）→ 写 step/start → 向模型发起一次流式请求（一个 Step = 一次模型调用加它的工具执行）。模型返回的每个 chunk 边流式输出、边在后台收敛成完整回复。

工具执行：过安检、干活、验收
Tool Pipeline · Sandbox · Approval

模型决定调用工具（读文件、改代码、跑测试）。每个调用都走同一条管线：参数校验 → guard / 审批检查 → 沙箱包装 → 真正执行 → 输出验收。结果按模型调用的顺序写回账本（即使并行执行，历史也保持确定）。工具结果回来后若模型还想继续，就再进一个 Step——这就是"思考 → 行动 → 观察"的循环。

收敛落盘：检查点确认无债，账本入账
turn-stopping · Persistence

当模型不再发起新调用，循环进入 turn-stopping 检查点：插件在这里做最后确认（还有没有未完成的后台工作？要不要继续？）。确认无工作后写 turn/end，Agent 回到 idle。全程事件通过持久化层批量写入磁盘（JSONL 或 SQLite）；headless 产品面则把最后一段助手文本打印给你。

回头看这趟旅程：配置决定装配什么，Cordis 负责激活与卸载，Registry/Inbox 管所有权和投递，Turn/Step 管节奏，工具管线与沙箱管安全，Session 账本从头记到尾。接下来第三章就把这些角色逐个打开。

03

八大核心模块详解

每个模块按同一套问法讲清楚：它是干什么的？为什么这么设计？新手最容易误会什么？

3.1 Cordis 插件内核：一切皆插件的地基

干什么：Cordis 是垫在整个 Harness 最下面的插件运行框架（vendored 在仓库 vendor/ 目录，锁定上游版本）。它把核心循环、会话、模型、工具、权限、产品面统统组织成一棵可装配、可卸载的插件树。理解它只需要四个词：

  • Context：一个"四合一"容器——既是服务仓库（插件把能力发布到这里），又是事件总线（插件之间靠事件通信），又是作用域树（global / preset / agent 三层继承），还是生命周期所有者（谁注册的东西谁负责回收）。
  • inject：插件声明"我需要哪些服务先就位"。Loader 按依赖图决定激活顺序；依赖缺失的插件停留在 PENDING 状态，等启动断言报错。
  • effect / disposer：插件的每一次贡献（注册服务、监听事件、挂工具）都叫一个 effect，并且必须返回一个"清理动作"（disposer）。所以注册永远是可撤销的——热重载、preset 切换、Agent 销毁都不泄漏旧注册。
  • waterfall：四种事件时序（广播 emit、可改写链 waterfall、并发 parallel、有序 serial）中最特别的一种——每个监听器可以改写结果，但必须调用 next() 才会把请求传给下一环；不调用就是拦截。
类比把一个插件想象成一名员工，而不是一段启动时跑一次的脚本：入职审批（PENDING，等依赖到位）→ 正式上岗（ACTIVE，通过 effect 登记一项项职责）→ 离职时按登记清单逐项交接（逆序运行 disposer）→ 全部交接完才算离职（DISPOSED）。重新录用走的是全新的入职流程（新 Fiber）。
新手最容易误会
  • 把 Cordis 当成普通 DI 容器：它还同时是事件总线、作用域树和生命周期所有者；而且"配置文件被解析成功"不等于"插件真的激活了"——排障要看 Fiber 的最终状态。
  • 以为插件里跑代码就和宿主隔离：Context 是进程内的信任域，不是安全边界。动态插件与宿主代码权限相同，隔离要靠 3.8 节的沙箱与进程边界。

3.2 启动装配：Profile / Bundle / Preset 三种尺度

干什么：回答"这次启动到底装哪些插件"。配置分三种尺度，各管一段：

概念尺度白话解释
Bundle分发一组可安装的插件包，是组合的"原料"。仓库自带三个：dsh-base（共享核心）、dsh-web-app（Web 产品）、dsh-headless（一次性任务）。
Profile部署一个命名的产品形态，列出有序的 bundle 清单并承载部署补丁。--profile headless 选的就是它。
Preset会话单个 Agent / Session 的插件名单。Web 模式下每个会话由自己的 preset 装配出专属能力集合。

叠加顺序是固定的：bundles → profile patch → home patch → --patch，最后再注入少量派生行。两条铁律：

  • 整行替换，不做深合并：后一层按 entry id 整行覆盖前一层。想改某个配置项，必须把那一行完整重写——配置结果因此完全可预测，没有隐藏的合并规则。
  • 配置错、依赖缺，一律大声失败：不静默选择"第一个能用的 Provider"，不带着残缺能力启动。
类比装机：Bundle 是一个个软件安装包，Profile 是这桌机器的"配置清单 + 补丁"，Preset 是每个使用者登录后自己的"应用桌面"。整行替换好比"整个软件换新版本"，而不是"拆开软件改一个零件"。

装配的产物是两级插件树：Host Context 跑产品基础设施（所有会话共享），Agent Context 跑单个会话的专属能力（每个会话一棵子树，互不干扰）。

3.3 Agent 与 Inbox：谁拥有 Agent，消息怎么送

干什么：这一层在具体的循环之前，只管两件事——所有权（谁创建、谁销毁）和投递（外部消息怎么排队进来）。

  • AgentHandle：创建 Agent 成功后，只有创建者能拿到这个句柄。句柄带着销毁权（dispose capability）——别人即使知道 Agent 的 id，也没有遥控器。
  • Inbox：Agent 的收件箱，所有待处理消息在这里排队，写入本身是持久事件。
  • 三种投递路由，都是统一原语 send(message, target, wakeup) 的固定组合：
路由含义典型用途
followup进"下一 Turn"队列，并唤醒 Agent新的用户问题；旅程第 4 步走的就是它
steer进"下一 Step"队列，并唤醒运行中的方向修正："顺便也改一下文档"
inject进"下一 Step"队列，不唤醒后台任务的结果投递，等 Agent 自然醒来消费
类比Inbox 像办公桌上两个有序收件盘，三种路由是三种便签："这单做完后处理"（followup）、"下一步立刻处理"（steer）、"放到下一步但别叫醒我"（inject）。最后一种意味着：如果人正闲着，文件就一直躺在盘子里。
新手最容易误会
  • 把 send 当成"请求/响应"：返回的 MessageId 只是投递回执，不是"模型的回答"。想确认某条消息产生了结果，上层要自己建立观察机制；whenIdle 也只证明整机空闲，不证明某条消息被处理出结果。
  • 以为 inject 也会叫醒 Agent：不会。这正是它和 steer 的区别，也是新手排障时"消息怎么一直没被消费"的头号原因。
packages/core/agent

3.4 Turn / Step：主循环的心跳

干什么：ReactLoopAgent 是 Agent 接口的默认实现，负责把一次用户意图拆成若干轮"问模型 + 跑工具"。它的核心只有两把尺子：

  • Turn：一次用户意图的处理窗口。你发一条消息、它从开始处理到最终答复，是一个 Turn。
  • Step：一次模型请求加它的工具执行。一个 Turn 包含零个或多个 Step——模型每用一次工具、结果回来再问一次模型，就多一个 Step。
图 2 · Turn 是意图边界，Step 是模型调用边界。计费、超时、中断如果混淆这两把尺子，就会得到错误的状态。

循环本体薄得惊人：它不管 prompt 内容、不管模型怎么调、不管工具权限、不管存储——这些全部委托给其他模块，通过事件扩展点接入。它只保证三件事：

  • 生命周期闭合：每个 Turn / Step 在成功、失败、取消三条路径下都必须有始有终；
  • 重试不开新 Turn：模型请求失败后由 agent/request-error 扩展点决定退避重试还是压缩重试，重试发生在原 Step 内；
  • 结束前最后一道岗：turn-stopping 串行检查点确认没有遗留工作，才允许写 turn/end。
新手最容易误会
  • "一条用户消息 = 一次模型请求"：错。一个 Turn 可以有零个 Step（被拒），也可以有很多个 Step（每次工具结果回来都可能再进一个）。
  • "循环是大脑，什么都管"：恰恰相反，它故意做得薄。压缩、重试、后台任务、目标驱动全是插件——这也是第四章"薄主循环"决策的直接体现。

3.5 Session：一本只往后写的账本

干什么：Session 是每个 Agent 的权威交互历史。它同时解决审计、恢复、流式 UI 和模型历史四件事——诀窍是把"原始日志"和"当前模型看到的表层"分成两层：

  • SessionEvent log（账本）：每条事件带连续编号 seq，只追加、永不涂改。Turn/Step 边界、流式 chunk、审批决定、计划与待办……统统可以记进来。Session.append 是唯一写入口。
  • Surface（表层）：账本中"当前对模型可见"的消息序列。append 往表层加消息，replace 用摘要替换一段——被替换的原文仍躺在账本里。
  • deriveMessages()（投影）：一个纯函数，把当前表层折叠成合法的模型对话历史。恢复会话时不靠任何内存缓存，重算即可。
图 3 · 账本是事实，表层是视图，模型历史是投影。三层各司其职，审计与压缩因此不打架。

由此得到一条贯穿全系统的铁律："模型可见 ⇔ 已记录"。任何会进入下一次模型请求的内容，必须能到账本里写成事件；否则崩溃恢复、fork、重放会对不上账。反过来，UI 状态、临时锁这类东西用"仅记录"事件就好，不必进入模型视野。

两个常被问到的机制：resume（恢复）是从账本重算出相同的表层——如果恢复后发现模型上下文和之前不一样，那说明某个地方存在"绕过日志直达模型"的旁路，这是 bug 而不是特性；fork（分叉）是复制账本的某个前缀（seed）另起一个新 Session 并记录血缘关系，原账本一个字节都不动。

新手最容易误会
  • "UI 里看到的 = 模型看到的"：不一定。"仅记录"（log-only）事件只进账本、不进 deriveMessages()；两边不一致时，要分别核对 log-only 与 surface 事件。
  • "恢复 / 分叉会修改历史"：不会。resume 是重算，fork 是复制前缀另起炉灶，账本永远只追加。

3.6 Prompt 与 LLM：组装说明书，接上电源

干什么：两个独立的半边。SystemPrompt 注册表负责把"你是谁、行为规则"拼成请求前缀；LlmRuntime 负责"问哪家模型、怎么问"。循环只是把两者写进请求头。

  • system prompt 不是写死的文字：各个插件向注册表登记 section（带稳定 key 和顺序），pre-step 阶段按当前 agent scope 解析、投影成这一段请求的前缀——不同 Agent 拿到不同的"员工手册"。默认包含 Harness 身份与运行时上下文，persona 默认为空。
  • LLM 是可插拔的适配器：系统用统一词汇表（Message / ContentBlock / ToolSchema）描述请求，供应商差异全部收进 Adapter。流式返回的每个 StreamChunk（增量文本、推理、工具调用、用量）边记录边由 BlockAssembler 收敛成一条完整助手消息。
  • 失败要趁早：缺 provider/model、未知 adapter、凭证解析失败，都在真正调用之前报错，不留"跑到一半才发现没法问模型"的残局。
  • 重试有预算：网络/供应商错误交给 agent/request-error 扩展点；Provider 的重试策略默认最多 2 次（起始延迟 500ms、封顶 10000ms），预算耗尽后原错误沿链上抛——不会无限自动恢复。
类比system prompt 像入职手册：各部门把自己那章（section）交上来，按固定顺序装订，不同岗位（agent scope）发不同版本。Adapter 像万能转换插头：上层永远是同一种插头（统一词汇表的请求），插头把电流转成各国插座的规格（供应商协议）。
新手最容易误会
  • "接一个新模型厂商要改核心代码"：不用，注册一个 adapter 即可，循环一行不动。
  • "prompt 是一段固定文案"：它是按作用域动态投影出来的。

3.7 工具管线：所有人走同一条安检通道

干什么：工具不是"模型可以随便调的函数列表"。每个工具由一个 ToolDefinition 定义——模型 schema、执行函数、规范输出、UI 呈现意图，四者绑在一起，是文档里说的"模型能力的窄腰"。所有调用必须通过同一条管线，谁也不能走侧门：

  • ① Schema 校验：模型给的参数先在边界验证并冻结；不合法（INVALID_ARGS）在产生任何副作用之前就失败。
  • ② Pre-execute：审批与策略的时点在这里（3.8 节的两把钥匙之一）。
  • ③ Guards：一组"单调守卫"——只能拒绝或弃权，不能放行改写。多个守卫的意见只会越来越严，不会越来越松。
  • ④ Execute：沙箱包装后真正执行工具体。
  • ⑤ Post + Finalize：输出必须通过 output schema 验证（INVALID_TOOL_OUTPUT 拦住坏值进入模型或重放）；finalize 只能改给模型看的内容，不能改错误身份。

三个值得记住的设计：

  • 拒绝是结构化结果，不是崩溃：审批或 guard 拒绝会被转成一个 error result，tool call / result 的配对依然完整，模型看得懂"为什么没干成"。
  • 并发产生、顺序提交：只有分类器明确说"并发安全"的工具才能重叠执行，其余一律独占；结果按模型调用的顺序写回——即使并行干活，历史依然确定。
  • UI 呈现是纯函数：工具怎么渲染由 args/result 纯投影出来，重放时不依赖任何外部状态。
类比机场安检通道：乘客（调用）不能从侧门登机，必须统一过值机（schema）、安检（guard/审批）、登机口（执行）、行李核对（输出验收）。把某个登机口从指示牌上抹掉，并不等于物理封锁了跑道——这就是"隐藏 ≠ 禁止"。
新手最容易误会
  • "不把工具写进 schema，模型就调不到，等于安全"：文档反复强调——schema omission、prompt 约束、UI 隐藏都不是权限强制；强制点在真正执行副作用的那一步。
  • "并行工具会写出乱序历史"：不会，提交是按序的。
  • "执行完就结束了"：还有输出验收和 post 阶段，坏输出进不了模型。

3.8 执行世界与安全：两把钥匙（重点）

这一节回答 Agent 安全最核心的问题：模型让机器干活时，活儿到底在哪里干、能干到什么范围、这次干之前要不要经人点头？Harness 的答案是三层：一个"执行世界"的概念，加上 Sandbox 与 Approval 两把各管各的钥匙。

先说"执行世界"：FS 和进程必须成对

文件系统能力（ctx.fs）和子进程能力（ctx.subprocess）共同圈出一个执行世界——路径和进程必须落在同一个环境里。shell、terminal、LSP 这些上层能力都只是这对能力的消费者。执行世界有两种实现：

  • Local：本机文件系统 + 本机进程树；
  • E2B（可选）：远端沙箱的文件系统 + 远端进程。

部署时两者必须成对选择。只换一半的典型故障是"路径存在但命令看不到"——文件写在远端，命令却在本机找。同样要记住：用 E2B 只是把执行世界搬到了远端，Agent、Session、LLM 仍然在本地，不是"整个 Agent 上云"。

钥匙一：Sandbox 决定技术天花板

沙箱回答"技术上最多能碰到什么"。三档模式，默认非常保守：

档位含义备注
read-only只读，不能改任何文件默认档；未配置 workspaceRoot 时以 process.cwd() 为界
workspace-write可写工作区，工作区之外仍受限常规开发任务的常用档
danger-full-access不设限必须显式选择，名字自带警告

隔离靠操作系统原生机制：Linux 使用 Landlock / bwrap，macOS 使用 Seatbelt（sandbox-exec），Windows 使用 ACL。关键语义是 fail closed（宁可拒绝，不可做错）：找不到可用的沙箱后端时返回 SANDBOX_UNAVAILABLE，禁止裸执行——绝不会出现"沙箱不可用那就直接跑"的降级。

钥匙二：Approval 决定这次给不给

审批回答"用户是否授权这一次意图"。默认策略是 ask（问一次）；每次工具意图产生一个决策：allow / deny / unavailable。同样 fail closed：没有应答者时返回 unavailable，不默认放行——"没人回复"不等于"同意"。并且批准一次只是这一次，不会把后续调用升级成自动放行。

图 4 · 两把钥匙各管各的。技术天花板（Sandbox）× 单次授权（Approval），都采用 fail closed。

还有三件事，决定这套安全是否真的成立

  • 环境清洗：默认把 KEY / SECRET / TOKEN / PASSWORD / DSH_* 一类环境变量从子进程环境里洗掉。注意它的定位：这是降低误泄露，不是隔离——同一个操作系统用户下的代码仍能看到同样的资源。
  • 进程树与收尾：工具超时的动作是先发协作式取消信号，再强制杀整棵进程树，然后等所有进程和输出读取器真正安静下来（quiescence）。销毁（dispose）是一个完整的生命周期事务，不允许"父进程退了就当完事了"。
  • 信任边界：动态加载的 Cordis 插件、shell 能力、本机代码，权限都约等于宿主进程本身。prompt 指令、UI 隐藏、schema 隐藏全都不是权限强制——安全决策必须落在真正执行副作用的 executor / Provider 里。
类比厂区门禁 + 作业审批单：门禁（Sandbox）决定你的工卡物理上能刷开哪些车间，审批单（Approval）决定主管批不批你今天这一次动火。门禁刷不开的门，批了也没用；门禁能进的房间，动火前照样要单独审批。
安全误解清单（自查用）
  • ❌ "有沙箱就不需要审批" → 两者正交：沙箱内的合法操作也可能需要用户点头。
  • ❌ "没人应答审批 = 默认放行" → 返回 unavailable，不放行；沙箱后端缺失同理，禁止裸执行。
  • ❌ "用了 E2B，整个 Agent 上云" → 只有 FS + subprocess 成对搬走，大脑留在本地。
  • ❌ "默认配置很宽松" → 默认是 read-only + ask，相当保守；放开需要显式选择。
  • ❌ "环境变量脱敏就是安全隔离" → 只是降低误泄露，不隔离同 UID 代码。

04

设计哲学与边界

八个模块看完，你会发现它们背后只有五个反复出现的设计决策。理解了这五条，就理解了 Harness 为什么长成这样、以及它愿意付出什么代价。

决策一一切皆插件

换来：任何能力（模型、工具、压缩、产品面）都可替换、可演进、可按会话装配；核心代码不随能力增长而膨胀。
付出：调用关系分布在 entry、inject 和事件监听器里，排障必须看 Fiber 状态和 dump-config，不能只看 import 是否成功。

决策二账本是唯一事实

换来：崩溃恢复、审计、fork、重放、流式 UI，全部从一本 append-only 账本重算；"模型可见 ⇔ 已记录"让模型行为永远可追溯。
付出：日志会增长。对策不是删除，而是压缩三件套：

  • compaction（压缩）：当估算的上下文压力达到阈值（默认约 80% 容量），把一段旧对话生成摘要替换进表层——被盖住的原文一字不删，只是不再给模型看（默认保留约 16%）；
  • pruning（裁剪）：更便宜的先行手段——超长的旧工具结果缩成"头 4096 + 尾 1024"字符，不生成摘要；
  • overflow 恢复：请求被判定为上下文溢出时，自动压缩并重试一次；只有表层真的推进了才算重试成功，防止原地打转。
决策三能力接缝必须三角色齐全

每个可替换的能力都是一个接缝：Service Definition（合同）+ Provider（实现）+ Consumer（使用方），缺一不可——不允许"只定义没人实现"或"实现了没人用"的半套接缝。部署可变的选项由拥有方显式解析成不可变规格（spec），禁止在运行函数里偷偷写"没传就用默认值"。

决策四薄主循环 + 扩展点

主循环只管节奏与闭合。于是所有高级能力都能"挂"进来而不改循环：Subagent（派子任务）、Workflow（后台线程长任务）、Jobs（后台生产者）、Goals（目标驱动多轮）、Skills（可发现的能力目录）、甚至自修改（Agent 挂载自己的插件）——它们全部通过四种既有挂载点实现：用工具启动、用 Inbox 续跑、用 SessionEvent 记账、用 effect 管生命周期。没有为任何一个高级能力在循环里加过状态分支。

决策五同核多壳

四个产品面共享同一个 agents / sessions 内核，各自只负责自己的协议：

图 5 · 行为不漂移的秘诀：权威状态永远在内核，浏览器和客户端看到的都只是投影。注意 SDK 的 send 返回的仍是投递回执，不是答案。

有得必有失：权衡速览

决策换来付出什么时候重新评估
一切皆插件可替换、可按会话装配调用关系分散，诊断要看 Fiber装配复杂度持续超过可诊断性时
append-only 账本恢复、审计、重放、fork日志增长，事件设计必须克制恢复不变量或存储成本出现结构性矛盾时
薄主循环改动的爆炸半径小完整行为分布在多个监听器上跨插件检查点成本超过内聚收益时
接缝三角色齐全避免供应商分叉与半套抽象小能力也要补齐三个角色——（这是合入门槛，不是可选项）
同核多壳四个产品面行为一致每个协议要各自定义投递与完成语义强行统一导致 UI / 传输概念互相泄漏时
预发布拒绝旧格式地基可以随时改对升级遇旧数据只能导出或用匹配构建第一个正式 tagged release 之后
边界诚实的"不是"
  • 插件内替换 Provider 不等于安全隔离；真实边界是操作系统沙箱与进程边界（见 3.8）。
  • 无实测证据不承诺吞吐、延迟、SLA 数字。
  • 预发布立场：Session 格式版本保持 0，SQLite 单调升级，遇到未知旧格式明确拒绝而不是假装损坏或尝试迁移。

常见问题

为什么 Session 不直接用一个 messages 数组？
因为流式 chunk、工具调用配对、审批决定、计划与待办这些事实都要被记录、被恢复、被审计，而"模型对话历史"只是其中一种视图。messages 数组做不了 append-only 账本；有了账本，messages 反而可以随时重算出来。
Turn 和 Step 是一回事吗？
不是。Turn 是用户意图的处理窗口（工单），Step 是其中一次模型请求及其工具执行（工单里的一个回合）。一个 Turn 有零个或多个 Step。计费、超时、中断的语义都依赖这个区分。
为什么 inject 进去的消息半天不被消费？
inject 的设计就是"进下一步队列但不唤醒Agent"，适合后台任务结果这类"等你自然醒来再看"的输入。如果 Agent 一直空闲，消息就会安静地待在队列里。想唤醒，用 steer 或 followup。
上下文压缩会不会破坏审计？
不会。压缩只是用摘要替换表层里的一段可见序列，账本原文一字不删；摘要本身作为新的模型可见事件也被完整记录（用了哪个 provider/model、花了多少 token）。审计永远以账本为准。
插件明明"加载成功"了，为什么能力不可用？
"import 成功"和"激活成功"是两回事。查三处：Fiber 停在 PENDING（inject 依赖没就位）、FAILED（apply 抛错）、或启动断言拦下了半活启动。用 dump-config 确认最终配置、再看 Fiber 状态与 agent scope。
用了 E2B，是不是整个 Agent 都在云上跑？
不是。只有 FS 与 subprocess 这对 Provider 换成了远端实现（且必须成对），Agent、Session、LLM 都留在本地。执行世界搬了家，大脑没搬。

三句话带走 DeepSeek Harness
  1. 一切皆插件：能力不是写进巨型类的代码，而是挂在 Cordis 插件树上、可装配可卸载的贡献。
  2. 账本即事实：append-only 的 Session 日志是唯一事实源——模型看到什么、UI 显示什么、崩溃后恢复什么，全是它的投影。
  3. 安全在执行点决定：沙箱管技术天花板，审批管单次授权，两把钥匙都 fail closed；隐藏从来都不等于禁止。
