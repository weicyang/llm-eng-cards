TG01 · Cache 全景指南

从 GPU 显存到业务层 — KV Cache / Prompt Cache / Semantic Cache / Redis 缓存全链路解析

Cache 的本质都是"空间换时间"，但在不同层次有不同表现：KV Cache 在 GPU 显存层加速单次推理，Prompt Cache 在 API 层复用跨请求计算，Semantic Cache 在业务层跳过整次模型调用，Redis 在传统缓存层减少数据库访问。理解这四层，就掌握了 AI 系统缓存的全部核心。

一、Cache 全景图：三层缓存体系

在 AI 系统中，缓存不是单一的"加个 Redis"，而是一个多层体系[3]：

层级名称复用对象直接收益适用场景
L1Prompt Cache稳定前缀的 K/V 矩阵输入成本降低 67-90%固定 System Prompt、统一工具定义
L2Semantic Cache整条问答结果跳过整次模型调用客服 FAQ、制度问答、标准解释
L3KV Cache推理中间状态（K/V 矩阵）提升吞吐、降低延迟自建推理服务、长上下文生成
用户请求流程： 请求到达 │ ├──→ L2 Semantic Cache：语义匹配命中？ → 直接返回缓存答案（跳过模型） │ ├──→ L1 Prompt Cache：前缀匹配命中？ → 跳过 Prefill，节省输入计算 │ └──→ L3 KV Cache：推理层复用 K/V → 加速 Decode 阶段 │ └──→ 传统 Redis Cache：缓存业务数据、会话状态
关键认知：热点问题越多，L2 价值越高；稳定模板越多，L1 价值越高；自建推理越多，L3 价值越高[3]。

二、KV Cache：推理层加速引擎

KV Cache 的本质：用空间换时间 — 缓存已计算的 Key/Value 向量，避免自回归生成时对相同 token 重复做矩阵乘法[1]。

2.1 原理

Transformer 的自回归生成每产生一个新 token，都需要对之前所有 token 做 Attention 计算。如果不缓存，每步都要重新计算所有 Key 和 Value — 计算量随序列长度平方增长[6]。

无 KV Cache（每步重算）： Step 1: 计算 token₁ 的 K, V → 生成 token₂ Step 2: 重新计算 token₁, token₂ 的 K, V → 生成 token₃ → O(n²) 重复计算 有 KV Cache（增量追加）： Step 1: 计算 token₁ 的 K, V → 缓存 → 生成 token₂ Step 2: 复用缓存 + 只算 token₂ 的 K, V → 追加 → 生成 token₃ → O(n) 增量计算

2.2 显存开销

模型层数KV Heads单 token KV 大小4K 上下文32K 上下文
LLaMA 7B3232~0.5 MB~2 GB~16 GB
LLaMA 70B808 (GQA)~0.2 MB~0.8 GB~6.4 GB
LLaMA 70B (MHA)8064~1.6 MB~6.4 GB~51 GB

公式：2 × 层数 × KV_Heads × Head_Dim × seq_len × dtype_bytes[1][6]

2.3 核心痛点：显存碎片化

传统方案为每个请求预分配连续显存块（按最大上下文长度），导致 60-80% 的显存被浪费[1][4]：

碎片类型成因影响
内部碎片预分配 > 实际使用长度预留但未用的空间不可复用
外部碎片请求结束后留下不连续空洞新请求无法利用分散小块

2.4 三大优化策略

PagedAttention (vLLM)[1][4][6]：借鉴 OS 虚拟内存分页，将显存切分为固定大小 Block，按需分配非连续 Block，通过 Block Table 映射逻辑→物理地址。显存利用率从 20-40% 提升至 95%+。

GQA / MQA[1][6]：多个 Query Head 共享一组 KV，直接减少 KV Cache 大小。

方案KV HeadsCache 压缩比质量影响代表模型
MHAN（全量）1x基准LLaMA 1
GQAG（分组）N/G 倍<1%LLaMA 2/3, Mistral, Qwen
MQA1（全共享）N 倍轻微下降Falcon 40B

KV 量化 + 窗口丢弃[1][4]：

策略显存节省质量影响适用场景
FP16→INT850%<1%通用生产
FP16→INT4/NF475%1-3%长上下文 / 资源受限
滑动窗口 + Attention Sink固定窗口大小丢失长距离依赖流式推理（StreamingLLM）

2.5 策略叠加效果

生产级 KV Cache 优化 = 四层策略叠加 Layer 1: 模型层 → GQA (8 groups) → KV Cache 减少 8x Layer 2: 存储层 → INT8 量化 → 再减少 2x Layer 3: 管理层 → PagedAttention → 消除碎片化 (3-5x) Layer 4: 逻辑层 → Attention Sink + 窗口 → 控制长序列增长 综合效果（70B 模型，32K 上下文）： 未优化: ~51 GB/请求 → 不可能部署 优化后: ~0.8 GB/请求 → 8×A100 可跑 100 并发

2.6 商业用法

对自建推理服务（vLLM/TGI 集群），KV Cache 直接关系到单位 GPU 能承载多少请求[3]。

示例场景：Llama 3 70B 部署在 A100 80GB×8 上，最初按最大上下文静态预分配 KV Cache，单卡只能跑 1 个并发，单位请求成本 $0.08。改成 PagedAttention 分页分配 + GQA（8 组）+ INT8 量化三层叠加后，单卡并发提升到 16 个，单位请求成本降到 $0.005，降幅 94%。真正的杠杆不是换更强的卡，而是把原本被碎片和冗余 KV 占住的显存还给并发[1]。

2.7 使用陷阱

  • 静态预分配：按最大长度预留连续显存，碎片化浪费 60-80%[4]
  • 跳过 GQA 直接窗口丢弃：质量损失更大，应按三级降级顺序：量化→GQA→窗口丢弃[4]
  • 忽视显存监控：>90% 利用率时应自动触发降级策略[4]

三、Prompt Cache：跨请求复用

Prompt Cache 的核心：多个请求共享相同的系统提示词前缀，每次都重新做 Prefill 计算是巨大的浪费，把前缀的 K/V 缓存下来直接复用[5]。

3.1 与 KV Cache 的区别

维度KV CachePrompt Cache
优化阶段Decode（逐 token 生成）Prefill（输入处理）
生命周期单次对话结束销毁长期驻留（LRU 淘汰）
匹配方式无需匹配（顺序追加）精确前缀匹配
复杂度降级O(n²) → O(n)O(n²) → O(1)（命中部分）
收益来源推理延迟降低API 成本降低（Token 单价降至 10%）

两者互补而非竞争：KV Cache 节省"输出生成"时间，Prompt Cache 节省"输入处理"成本[2][5]。

3.2 前缀匹配机制

Prompt Cache 按最长前缀匹配工作 — 从请求第一个字节到缓存断点必须完全一致[2][5]。位置编码敏感（第 i 个 token 的 K 向量编码了位置信息），所以只能前缀匹配，不能任意子串匹配。

请求结构（从前往后）： ┌──────────────────────────────────────────────┐ │ System Prompt + 工具定义 → CLAUDE.md → Session │ │ ← 稳定内容放前面 ──→ ← 可变内容放后面 ──→ │ └──────────────────────────────────────────────┘ 缓存命中：前缀完全匹配 → 跳过 Prefill → Token 单价降至 10% 缓存击穿：任何前缀变动 → 后续缓存全部作废

3.3 Claude Code 团队的五大原则

Claude Code 团队将缓存命中率设为 SEV 事故级别告警（掉几个点就是成本翻倍）[2]：

原则做法反模式
稳定内容前置System Prompt + 工具定义放最前前缀里塞时间戳、用户 ID
信息更新走 message 层用 system-reminder 标签注入新信息每次更新 System Prompt
工具集保持稳定状态切换通过工具调用表达动态加载/卸载工具
不切模型切便宜模型需重建 prefix 更贵动态切模型
压缩继承 prefix继承父对话 prefix，仅追加压缩指令重新构建对话历史

3.4 商业用法

最适合模板稳定、前缀高度一致的 SaaS 产品（客服、文案生成、报表总结）[3]。

示例场景：一个 AI 编程助手日均 50 万次 API 调用，System Prompt 加工具定义固定占 6K token。把这段前缀冻结、把用户仓库信息全部挪到消息层之后，缓存命中率稳定在 92%，TTFT 从 800ms 降到 120ms，年化成本减少约 $180K。注意收益几乎全来自"前缀不动"这一条纪律，而不是缓存本身有多聪明[5]。

3.5 使用陷阱

  • System Prompt 塞时间戳：每次请求 prefix 不同，缓存全部作废[2]
  • 工具序列化顺序漂移：功能等价但 prefix 不同[2]
  • 频繁修改 System Prompt：每次修改使缓存失效[5]
  • 用户特有内容放前缀位置：破坏共享性[5]

四、Semantic Cache：语义级缓存

Semantic Cache 通过向量相似度匹配，命中时直接返回缓存的完整答案，跳过整次模型调用。收益最大但风险也最高 — 对的答案会被放大，错的答案也会被放大[3]。

4.1 工作原理

用户提问 "运费怎么算" │ ├──→ Embedding 向量化 │ ├──→ 向量数据库中查找相似问题（cosine similarity > 阈值） │ ├──→ 命中 → 直接返回缓存答案（跳过模型调用） │ └──→ 未命中 → 正常调用模型 → 结果写入缓存

4.2 适用 vs 不适用

适合不适合关键设计
标准 FAQ、静态制度、低个性化问答个性化强、强实时、与订单状态强绑定相似度阈值、TTL、版本隔离

4.3 商业用法

高频重复问答场景价值极高，前提是问题分布足够集中。

示例场景：某客服机器人日均 180 万次咨询，头部 200 个问题占了 61% 的流量。对这批标准 FAQ 启用 Semantic Cache（相似度阈值 0.95、缓存键带知识库版本号）后，整体请求命中率 47%，输入 Token 成本下降 38%，P95 延迟从 6.9s 降到 2.4s。能拿到这个收益的关键是流量本身高度集中——如果长尾占比大，同样的阈值只会换来一堆勉强命中的错答案[3]。

4.4 使用陷阱

  • 阈值过低：不相似的问题也命中，返回错误答案
  • TTL 过长：过时政策被快速复制给大量用户[3]
  • 无版本隔离：新旧口径混用，错误答案持续命中[3]
  • 只看命中率：不看错误答案是否被放大 — 命中率高但答错更多，这种缓存没有商业价值[3]

4.5 解决方法

陷阱解决方法
错误答案放大灰度启用 + 热点抽检 + 可快速清空命中池[3]
知识过期缓存键带知识库版本号，按版本隔离[3]
个性化不匹配先从标准 FAQ 和低风险场景试点[3]
模型版本差异不同模型单独命中池[3]

五、L1 进程缓存 / L2 Redis 缓存 / 向量缓存

前面三层缓存省的是"模型算力"，这一层省的是"数据库和网络往返"，两者不能互相替代。语义缓存命中之后，业务侧照样要读会话状态、用户画像、限流计数——这些如果每次都打 DB，省下来的模型延迟会被数据层原封不动地吃回去。

5.1 多级缓存架构

在 AI 系统的业务层，传统多级缓存依然重要[7]：

层级介质延迟容量典型用途
L1 进程缓存应用进程内存~0.1ms极小（MB 级）热点配置、模型路由表、高频工具描述
L2 Redis 缓存Redis 内存~1ms中等（GB 级）会话状态、用户画像、Embedding 向量
向量数据库Milvus/Pinecone 等~10ms大（TB 级）Semantic Cache、RAG 检索

5.2 Redis 在 AI 系统中的角色

Redis 在 AI 系统中远不止"加个缓存"，承担多种角色[7]：

用途Redis 数据结构说明
会话状态存储Hash / StringAgent 多轮对话的中间状态
缓存命中率计数String (INCR)实时监控缓存效果
分布式限流String + Lua控制 API 调用频率
幂等性保证SETNX + TTL防止 AI 请求重复执行[8]
缓存穿透防护BloomFilter拦截不存在数据的查询[7]

5.3 缓存三大经典问题

问题定义解决方案
缓存穿透查询不存在的数据，直接打到 DB布隆过滤器 + 缓存空值[7]
缓存击穿热点 Key 过期瞬间大量请求打到 DB互斥锁 (SETNX) + 逻辑过期[7]
缓存雪崩大量 Key 同时过期TTL 加随机偏移 + 多级缓存 + 限流[7]

5.4 向量缓存

向量缓存是 Semantic Cache 的底层实现，也用于 RAG 检索加速：

  • Embedding 缓存：高频查询的向量结果缓存到 Redis 或专用向量库
  • ANN 索引：HNSW / IVF 等近似最近邻算法，在精度和速度间权衡
  • 缓存键：查询文本的 Embedding 向量 + 相似度阈值

六、商业用法与成本收益

决定先做哪一层的不是技术难度，而是"你的重复发生在哪一层"：整条请求重复就上 L2，只有前缀重复就上 L1，自己扛 GPU 才轮得到 L3。在没有重复的那一层上使劲，投入再大也换不来命中率。

6.1 各层缓存的 ROI 对比

缓存层常见收益区间适合什么项目风险
Prompt Cache (L1)输入成本下降 40-90%System Prompt 稳定、模板化强[8]前缀变动导致全部失效
Semantic Cache (L2)跳过整次调用，省 100%高频重复 FAQ[3]错误答案放大
KV Cache (L3)吞吐提升 3-5x自建推理服务[1]显存管理复杂度
Redis 缓存DB 压力降低 50%+通用后端[7]穿透/击穿/雪崩

6.2 优化优先级

商业化场景里，最高 ROI 往往不是"微调提示词"，而是先把重复请求拦掉、把简单请求分流掉[8]：

优化优先级： 1. 缓存复用（最高 ROI） → 立刻减少重复输入/输出成本 2. 模型路由 → 让简单任务用便宜模型 3. 上下文压缩 → 减少输入 Token 4. 输出控制 → 减少输出成本和时延

7.2 Agent 特有陷阱

Claude Code 团队踩过的三大坑[2]：

坑原因后果

八、优化方案总结

8.1 全链路优化路线图

Step 1: 稳定前缀标准化 → 吃 Prompt Cache 红利（L1） ├── 固定 System Prompt，动态内容后置 ├── 工具定义序列化顺序固定 └── 监控命中率，低于 70% 排查前缀一致性 Step 2: 高频 FAQ 语义缓存（L2） ├── 先从标准 FAQ 和低风险场景试点 ├── 缓存键带版本号 + TTL └── 灰度启用 + 热点抽检 Step 3: 自建推理 KV Cache 优化（L3） ├── PagedAttention 消除碎片化 ├── GQA 减少 KV head 数量 ├── INT8/FP8 量化压缩 └── 三级降级策略：量化 → GQA → 窗口丢弃 Step 4: 传统缓存加固 ├── Redis 多级缓存（L1 进程 + L2 Redis） ├── 布隆过滤器防穿透 └── TTL 随机偏移防雪崩

8.2 Do / Don't 总结

  • 稳定前缀标准化，先吃 Prompt Cache 红利
  • 语义缓存先从标准 FAQ 试点
  • 缓存键带版本号 + 模型版本隔离
  • 同时监控命中率 + 错误率 + 节省成本
  • KV Cache 三级降级策略自动触发
  • 灰度启用 + 热点抽检 + 快速清空机制
  • PagedAttention + GQA + 量化叠加使用
  • System Prompt 塞动态时间戳
  • 只看命中率不看错误答案放大
  • 缓存永不过期，假设知识永远正确
  • 所有场景统一用一套语义阈值
  • 动态加载/卸载工具破坏 prefix
  • 静态预分配 KV Cache（碎片化 60-80%）
  • 跳过 GQA 直接窗口丢弃（质量损失大）

Q&A

KV Cache 和 Prompt Cache 是同一层优化吗？
不是。KV Cache 优化 Decode 阶段（逐 token 生成），存储单次对话中已生成 token 的 K/V 矩阵，将单步复杂度从 O(N²) 降到 O(N)。Prompt Cache 优化 Prefill 阶段（输入处理），存储跨请求共享的前缀 K/V 矩阵，命中部分复杂度从 O(N²) 降到 O(1)。两者互补：一个减少推理延迟，一个减少 API 调用费用[5]。
缓存击穿对 Agent 为什么是致命问题？
Agent 是长会话系统，每次对话可能涉及数十轮交互。如果缓存击穿，每次都按完整 Token 计费，成本指数级增长。Claude Code 团队将缓存命中率设为 SEV 事故级别告警 — 掉几个点就意味着成本翻倍。缓存命中率从 45% 优化至 91% 后，月成本从 $8,500 降至 $2,200（降幅 74%）[2]。
Semantic Cache 价值高但风险也最高，为什么？
因为它省掉的是整次模型调用，收益最大；但复用的也是整条最终答案，一旦答案过期或不适用于当前用户，就会把错误直接放大。所以 Semantic Cache 非常依赖版本隔离、阈值设置和场景边界管理。必须先证明它不会放大错误，再追求更高命中率[3]。
PagedAttention 为什么能提升 3-5 倍吞吐？
传统方案为每个请求预分配连续显存块（按最大长度），碎片化导致利用率仅 20-40%。PagedAttention 借鉴 OS 虚拟内存分页，将显存切分为固定 Block 按需分配，利用率接近 100%。同等 GPU 下可容纳 3-5 倍并发请求。加上 Block 共享（Beam Search、Prefix Caching），额外收益更大[1][6]。
为什么"切便宜模型"可能反而更贵？
切换模型（如从 Sonnet 切到 Haiku）需要重建 prefix，而重建 prefix 的成本可能超过使用便宜模型节省的钱。正确做法是不切模型，改用子 Agent 独立运行 — 子 Agent 有自己的 prefix，不影响主对话的缓存[2]。
缓存上线前最重要的三件事是什么？
三个商业问题必须先解决：(1) 一致性 — 按知识版本、租户、模型版本分桶缓存；(2) 收益归因 — 记录命中率、节省 Token、节省时延；(3) 风险隔离 — 灰度启用、热点抽检、可快速清空。很多团队只看命中率，命中率高但答错更多，这种缓存没有商业价值[3]。
