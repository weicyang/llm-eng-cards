TG04 · AI Token 节省与优化完全指南

从 Token 机制到系统级降本：Prompt 压缩 / 三级缓存 / 推理加速 / 上下文工程 / 模型路由 / 预算熔断——六层优化体系全景解析

Token 是新的电费。 从计量到熔断，六层防御体系可将 LLM 账单降低 40%~90%。核心公式：总成本 = 上下文体积 × 模型单价 × 调用轮数——压缩每一项乘数，就是降本。[1]

一、Token 基础与成本公式

1.1 什么是 Token？

Token 是大模型 tokenizer 将文本切分后的最小处理单元，不等于字也不等于词[8]。例如：

  • "Hello World" = 2 个 Token
  • "你好世界" = 4 个 Token
  • "unbelievable" = 3 个 Token（"un" + "believ" + "able"）

1.2 三种主流分词算法

算法原理代表模型特点
BPE贪心合并高频相邻字符对GPT 系列（cl100k_base）自底向上，Byte-level 256 基础 token[9]
WordPiece基于语言模型似然度合并BERT 系列近似互信息 PMI
Unigram自顶向下裁剪，移除损失最小的 tokenLLaMA（SentencePiece）训练时可随机采样分词方案增强鲁棒性

1.3 成本公式与计费规则

总成本 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价

关键事实：

  • 输出 Token 定价通常是输入的 2~4 倍（输出为自回归逐个生成，计算密集度更高）[1]
  • 同样语义的中文文本比英文多消耗 2~3 倍 Token[8]
  • 缓存命中时，输入 Token 价格可降至正常的 1/4[18]

1.5 隐藏的 Token 消耗

  • Context Inflation：Prompt 从 800 tokens 无感知膨胀至 18,800 tokens（23 倍），因工具 Schema、Few-shot 示例、对话历史不断堆积[1]

二、Prompt 压缩与瘦身

Prompt 压缩是 ROI 最高的优化手段——零基础设施改动，节省可达 74%[1]。
Prompt 之所以能压掉七成还不掉质量，是因为膨胀出来的部分大多不是信息，而是历史包袱——上个季度为了修某个 bad case 追加的规则、早就没人看的示例、复制粘贴带进来的字段说明。压缩不是"把话说短"，而是把这些已经失效的补丁清理掉；真正承载判断口径的那几百个 token，一个都不该动。

2.1 压缩三板斧

手段做法节省比例
删除冗余示例对话移除 Few-shot 中的标准题，只留高价值边界样本~75%
合并重复安全指令多条相似的防护规则合并为一条精炼指令~87%
工具 Schema 瘦身精简 JSON Schema 描述，去除冗余字段说明~54%

合计效果：从 4,342 tokens 降至 980 tokens，节省 74%[1]。

2.2 Prompt 精简实操

精简版（47 tokens）：
Expert developer. Python/JS/TS. Write clean, commented code. Acknowledge uncertainty. Be concise.[25]
冗余版（312 tokens）：
You are an expert software developer with extensive experience in Python, JavaScript, TypeScript, and various other programming languages...[25]

2.3 输出端控制——让模型"说短话"

由于输出 Token 定价是输入的 2~4 倍，控制输出长度比压缩输入更有成本效益[1]：

  • 设置 max_tokens 参数为最紧值
  • 在 Prompt 中显式要求简洁："Answer in 3 sentences or fewer"[22]
  • 使用结构化输出（JSON/CSV），天然比自由文本更短[22]

2.4 Prompt 分层管理

把 Prompt 拆为五层资产：身份层 / 任务层 / 规则层 / 示例层 / 协议层。稳定规则常驻前缀（利于 Prompt Cache 命中），易变策略通过检索或配置动态注入[7]。

Prompt 膨胀的长期风险：增加更多规则虽然短期降低部分错误，但会导致 Prompt 膨胀 → 成本上升 → 指令冲突。增加更多示例短期输出更稳，但示例过旧会误导模型[7]。

2.5 Few-shot 样本精选

优先放高价值边界样本（高客诉、高金额、边界拒答、格式易漂移），而不是"最好回答"的标准题[7]。3 个精选边界样本的效果往往优于 10 个标准样本。

三、三级缓存架构

三级缓存叠加可拦截 40%~60% 重复计算[10]。缓存不是"加个 Redis"，而是把重复请求、热点任务和昂贵上下文变成可复用资产[4]。
三级缓存不是三选一，而是一张从严到松的漏网：L1 要求字节完全一致，命中少但绝对安全；L2 放宽到语义相似，命中翻几倍但可能答错；L3 Prefix Cache 只复用前缀的 K/V，不猜答案，所以命中率最高、风险最低。请求先过最严的一层，漏下去的再交给下一层，这样既拿到高命中率，又把"猜错答案"的风险限制在中间那一层。

3.1 L1：精确匹配缓存

  • 原理：对请求做精确哈希匹配，完全相同的输入直接返回缓存结果
  • 命中率：5%~15%
  • 成本节省：100%（完全跳过模型调用）
  • 延迟：降至 <50ms[1]

3.2 L2：语义缓存（Semantic Cache）

  • 原理：对请求做 Embedding，计算余弦相似度，相似问法复用之前的答案
  • 命中率：15%~35%（相似度阈值 >= 0.95 时安全）
  • 成本节省：100%（跳过整次模型调用）
  • 延迟：~100ms[1]
语义缓存风险最高——一旦阈值过低或 TTL 过长，过时答案被大规模复制。必须按知识版本、租户、模型版本分桶缓存，并配备热键巡检[4]。

3.3 L3：Prefix Cache（Prompt Cache）

  • 原理：复用系统提示词前缀的 K/V 矩阵，命中缓存时跳过 Prefill 计算
  • 命中率：40%~90%（取决于 Prompt 结构）
  • 成本节省：50%~90%（OpenAI 官方数据：降低最高 90%）[26]
  • 延迟降低：最高 80%[26]
Prompt 结构优化——把稳定内容前置，动态内容后置： ┌─────────────────────────────────────────┐ │ System Prompt（固定，~2K tokens） │ ← 缓存命中区 │ 工具定义（固定，~1K tokens） │ ← 缓存命中区 │ Few-shot 示例（偶变，~1K tokens） │ ← 缓存命中区 ├─────────────────────────────────────────┤ │ RAG 检索结果（常变，~2K tokens） │ ← 每次不同 │ 用户输入（常变，~200 tokens） │ ← 每次不同 └─────────────────────────────────────────┘

3.4 三级缓存综合收益

缓存层级命中率成本节省延迟适用场景
L1 精确匹配5%~15%100%<50ms完全重复请求
L2 语义缓存15%~35%100%~100ms高频重复 FAQ
L3 Prefix Cache40%~90%50%~90%降低 80%模板稳定的 SaaS
生产案例：客服 FAQ 改造——日均 180 万次咨询，整体请求命中率 47%，输入 Token 成本下降 38%，P95 延迟从 6.9 秒降至 2.4 秒[4]。

3.5 缓存上线三件事

  1. 一致性：按知识版本、租户、模型版本分桶缓存
  2. 收益归因：记录命中率、节省 Token、节省时延
  3. 风险隔离：灰度启用、热点抽检、可快速清空[4]

四、推理引擎层优化

推理层优化主要面向自建推理服务（vLLM/TGI），核心目标是降低每 Token 的 GPU 计算成本[4]。

4.1 KV Cache：空间换时间的核心

自回归生成中，已生成 token 的 K/V 不会改变。把它们缓存在 GPU 显存里复用，就是 KV Cache，总计算量从 O(n²) 降到 O(n)[12]。

KV Cache 大小 = 2 × 层数 × Head数 × Head Dim × 序列长度 × 精度字节数

以 LLaMA-2 7B 为例，seq_len=4096 下单条序列约 2GB，batch_size=32 时总 KV Cache 达 64GB[12]。

4.2 PagedAttention：消灭显存碎片

PagedAttention 借鉴 OS 虚拟内存分页机制，将 KV Cache 切分为固定 Block，按需分配[12]：

  • 显存利用率从 20~40% 提升到 >95%
  • 并发数提升 2~4 倍
  • Copy-on-Write 机制节省 55% 显存[12]

4.3 GQA / MQA / MLA：KV Head 压缩

技术原理压缩比质量损失
GQA（LLaMA-2 70B）多 Query 头共享 KV，8 组8x<1%[14]
MQA（PaLM, Falcon）所有 head 共享一组 KV32x有一定损失[15]
MLA（DeepSeek）低秩压缩 KV压缩到 MHA 的 5~13%极低[14]

4.4 KV Cache 压缩技术汇总

方法压缩比说明
FP8 量化2x精度损失极小[12]
INT4 量化4x需 group-wise 量化
H2O（Heavy Hitter Oracle）5x保留注意力得分最高的 token，压缩到 20%
StreamingLLM固定大小保留前 k 个 Sink Token + 最近 W 个窗口 Token[12]

4.5 FlashAttention：IO-aware 加速

标准注意力矩阵在 128K token 下约 30GB FP16，瓶颈在数据搬运（memory-bound）而非算力[15]。FlashAttention 通过分块计算 + 算子融合：

  • HBM IO 降低 80%
  • 显存从 O(N²) 降至 O(N)
  • 加速 2~7.6 倍[14]

4.6 Speculative Decoding（投机解码）

Speculative Decoding 让小模型快速生成候选 token，大模型并行验证。不改变输出分布，实际加速 2~3 倍，最优可达 3~4 倍[12]。

推理层这一串技术看着零散，其实都在解同一个矛盾：Decode 阶段每生成一个 token 都要把整个模型权重和 KV Cache 从显存搬一遍，算力大量闲置，瓶颈在带宽。量化和 GQA 缩小要搬的数据，FlashAttention 减少搬运次数，投机解码则让一次搬运顺带产出多个 token。判断一项优化值不值得做，先问它减少的是计算量还是搬运量——后者通常收益更直接。

4.7 量化——降低部署成本

方案位宽7B 模型内存精度损失推理速度
FP16/BF1616 bit~14 GB可忽略~2x

GPTQ/AWQ 4-bit4 bit~4 GB小~3~4x

量化选型决策树：

4-bit 是精度与压缩的甜蜜点，精度损失 < 1% perplexity[13]。

4.8 综合效果

Llama 3 70B 全栈优化：并发吞吐量提升约 20~30 倍[14]。70B 模型、32K 上下文、100 并发场景：未优化需 5.1TB 显存，四层策略叠加后仅需 80GB[14]。

五、上下文工程（Context Engineering）

从"写好一条提示"升级为"设计信息流动结构"。第一性原理：最小化高信号 Token 集合——注意力预算有限，信息越多不等于越好[5]。

5.1 为什么需要上下文工程？

  • 注意力稀释：Transformer O(n²) 注意力机制导致文本越长，每个 token 分配到的注意力权重越小
  • Lost in the Middle：128K 窗口中，模型对前 10% 和后 10% 信息回忆准确率约 90%，中间 50% 降至 40%~60%[6]
  • 成本平方增长：上下文翻倍，计算成本和延迟近似翻倍
把上下文窗口当成会议室而不是硬盘：容量再大，同时坐进来的人越多，每个人能分到的发言时间越少。所以"能塞进 128K"和"模型真的用得上这 128K"是两回事——上下文工程要优化的从来不是塞进去多少，而是让真正决定答案的那几段信息，出现在模型注意力还够用的位置上。

5.2 Context Engineering 四大策略

策略核心思想典型技术
保存 Context记忆库持久化，跨会话复用ChatGPT Memory、外部文件[17]
选择 Context按需获取最相关信息RAG 检索、工具筛选、.cursorrules
压缩 Context对历史消息做总结压缩小模型摘要、滑动窗口、关键信息提取[19]
隔离 Context多 Agent 系统各 Sub Agent 独立上下文子 Agent 架构、主 Agent 只看摘要[17]

5.3 上下文压缩三大方法

5.3.1 摘要压缩

  • 提取式摘要：按关键词/段落重要性筛选
  • 生成式摘要：用小模型对历史消息生成摘要（成本极低）[19]
  • 递归摘要：超长文本分段摘要后再汇总

5.3.2 结构化压缩

实体-关系抽取、事件抽取、表格化——将自由文本转为结构化数据，Token 效率提升 3~5 倍[19]。

5.3.3 增量压缩

多轮对话中只维护变化部分（差异压缩），不重复全量上下文[19]。

5.4 结构化填表（Schema）——摘要的进阶方案

开放式"请总结"指令导致关键要素随机丢失（保留率仅 47%），强制模型按预设 Schema 模板输出可将保留率提升至 98%[3]。

  • 必要性原则：只包含后续任务真正需要的字段（5~9 个为宜）
  • 类型约束：每个字段有明确类型
  • 可验证性：字段值可被程序化检查

5.5 水位线触发机制

上下文压缩触发策略（四级水位线）： 60% ████████░░░░ 预警：记录日志 70% █████████░░░ 轻度压缩：摘要历史对话 85% ███████████░ 重度压缩：仅保留关键信息 100% ████████████ 紧急重置：清空 + 从外部文件恢复[3]

5.6 "硬盘换内存"——外部记忆系统

将记忆负担从昂贵的上下文窗口转移到廉价持久的文件系统，每轮任务结束后主动清空上下文，通过读取外部文件恢复状态[6]：

  • 持久化日志（PROGRESS.md）：记录当前做到哪一步
  • 功能清单（TODO.md）：明确任务状态
  • 关键决策（DECISIONS.md）：记录设计取舍
  • 错误记录（ERRORS.md）：防止同一错误重复犯

上下文窗口（128K）成本极高、会话结束即丢；文件系统成本几乎为零、容量无限、永久保存[6]。

实战效果：从全量加载迁移到上下文工程，Token 消耗从 24K 降至 6.8K（降幅 72%），Prompt Cache 命中率从 45% 提升至 91%，长文本任务完成率从 58% 提升至 87%[5]。

六、系统级降本策略

6.1 智能模型路由

核心思想：不是所有请求都需要最贵的模型[23]。分类器判断任务难度，简单任务走小模型，复杂任务走大模型。

智能路由决策流： 用户请求 → 复杂度分类器 → ┬→ 简单任务 → GPT-4o-mini ($0.15/M) ├→ 中等任务 → GPT-4o ($2.50/M) └→ 复杂任务 → Claude Opus ($5.00/M) 成本节省：25%~70%[1]
路由策略适用场景成本降低
规则路由明确的意图分类（FAQ、闲聊、复杂分析）30%~50%
分类器路由需 ML 判断复杂度50%~80%[20]
级联路由先小模型尝试，失败再升级40%~60%
生产案例：某电商客服引入混合路由后月成本从 12 万降至 3.2 万（降低 73%），客户满意度从 4.1 提升到 4.3[10]。

6.2 Batch API——非实时场景利器

对非实时场景使用批量接口，成本直接降低 50%[20]。适合：

  • 离线数据分析与报告生成
  • 批量文档处理（合同审查、数据清洗）
  • 模型评测与回归测试

6.3 工具返回结果过滤

工具调用返回的原始数据往往非常冗长（JSON Schema、API 响应等），在注入上下文前进行摘要或关键字段提取，可减少 60%~80% 的 Token 消耗[20]。

6.4 预算熔断机制

三级预警，防止灾难性成本爆炸[1]：

级别阈值动作
🟡 黄灯预算消耗 70%限制并发数
🟠 橙灯预算消耗 90%强制降级小模型
🔴 红灯预算消耗 100%暂停所有请求，人工审批

6.5 Token 计量——看清成本分布

包装 API 调用，记录每次请求的 Token 消耗、延迟、成本。运行一周即可看清成本分布，这是一切优化的前提[1]。

关键指标：cost per request（每次请求成本）和 cost per useful answer（每次有效回答成本）[20]。

七、Agent 场景专项优化

Agent 任务是 Token 消耗的"超级放大器"——单任务（10 步推理）消耗 50,000~100,000 tokens，比单轮对话（~2,000 tokens）放大 25~50 倍[1]。
Agent 的成本不是线性叠加而是累进的：第 N 步要把前面 N-1 步的思考、工具调用和返回结果全部重新发一遍，所以总消耗大致按步数的平方走。这也解释了为什么"限制最大步数"比"压缩单步 Prompt"有效得多——砍掉后面几步，省下的是那几步各自携带的整段历史。

7.1 Agent 成本放大器

  • 多步推理：每一步都携带完整历史上下文
  • 工具调用：工具 Schema + 返回结果占据大量 Token
  • 重试机制：失败重试时重复消耗 Token
  • 空转问题：连续 3 步状态快照相似度 > 90% 则触发告警[2]

7.2 Agent 治理三板斧

手段做法效果

7.4 循环退出条件

Agent 必须设置明确的退出机制，避免无限循环消耗 Token[2]：

  • 正常退出：任务完成
  • 超时退出：如 20 轮上限
  • 空转退出：连续 N 步无进展自动终止
生产案例：Agent 产品月支出从 5,600 元飙升至 84,000 元，经治理（子 Agent 隔离 + 工具结果裁剪 + 中间状态压缩）后降至 32,000 元[1]。

Q&A

优化 Token 消耗会影响模型输出质量吗？
合理的优化不会。Prompt 压缩去除的是低信息量冗余内容，模型对精炼指令的理解反而更准确。但过度压缩（删除关键约束条件、核心上下文）会导致输出质量下降。建议每次压缩后做 A/B 测试，监控关键质量指标。
Prefix Cache 和 Semantic Cache 应该同时用吗？
是的，它们解决不同层面的问题。Prefix Cache 优化"同一系统提示词的重复计算"（命中率最高），Semantic Cache 优化"相似问题的重复回答"（需要 Embedding 基础设施）。建议先上 Prefix Cache（零代码），再上 Semantic Cache（需要工程投入）。
模型路由的分类器会不会本身消耗很多 Token？
不会。分类器通常用极小模型（甚至规则引擎），每次分类消耗的 Token 不到 100 个，成本可忽略不计。相比把简单问题发给旗舰模型（几千 Token），路由的 ROI 非常高。典型实现：先用 GPT-4o-mini 做意图分类，再路由到合适模型。
Agent 场景和普通对话的优化策略有什么不同？
Agent 场景有三大特殊挑战：①多步推理导致上下文指数增长（每步都携带完整历史）；②工具调用返回的数据非常冗长；③存在"空转"风险（Agent 循环但无进展）。因此 Agent 需要专项治理：子 Agent 隔离（主 Agent 只看摘要）、工具结果裁剪（丢弃冗余字段）、中间状态压缩（定期摘要）、循环退出条件（超时 + 空转检测）。
如何评估优化效果？应该看哪些指标？
核心指标有三个：①cost per request（每次请求成本）——直接衡量优化效果；②cost per useful answer（每次有效回答成本）——结合质量评估；③Prompt Cache 命中率——衡量缓存效率。建议搭建 Token 计量 Dashboard，按场景、模型、时间段维度追踪，每周复盘 Top 10 高消耗场景。
中文场景的 Token 优化有什么特殊之处？
中文 Token 效率天然低于英文（同样语义多消耗 2~3 倍 Token），因此：①优先选择中文优化过的模型（如 Qwen-2、ChatGLM，fertility 接近 1.5）；②Prompt 尽量精炼，避免冗长中文描述；③考虑中英混合 Prompt（技术术语用英文，减少 Token 数）；④RAG 检索结果做中文摘要后再注入上下文。
