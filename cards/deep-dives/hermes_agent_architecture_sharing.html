Hermes Agent 架构深度解析

从稳定前缀到自治任务：一个“窄腰、长会话、多表面”的自进化 Agent Runtime
基于 Hermes Agent 0.20.1 工作区源码快照与官方开发文档核验

一句话定义：Hermes Agent 不是单纯的代码助手，也不是某个模型的 UI 外壳；它是一套跨 CLI、消息平台、桌面、IDE 与 API 复用的个人 Agent Runtime。它把模型调用、工具执行、持久会话、记忆、技能、自主任务和多 Agent 委托收敛到同一个窄核心，同时把平台、Provider 和长尾能力推到可插拔边缘。

本文以当前工作区源码行为为事实基线。官方文档用于交叉验证，但当文档与代码演进不同步时，以代码和最新专项文档为准。特别是压缩默认已采用 in_place=true，不应继续把“每次压缩必然轮换 Session ID”当作当前默认行为。

一、项目定位与设计哲学

1.1 产品定位

Hermes 的核心用户场景不是“一次性解决一个仓库 Issue”，而是让同一个 Agent 长期生活在用户的终端、服务器和消息平台中。它需要同时解决三类问题：一是把模型转化为可执行行动；二是把一次对话变成可恢复的长期关系；三是把学到的流程沉淀成 Skills 和 Memory，再进入后续会话。

Hermes = Multi-surface Shell + Persistent Agent Runtime + Capability Edge + Autonomous Work

Hermes 的所有设计取舍，几乎都能倒推回一句话：这个 Agent 要活很久。活得久，就必须让前缀字节稳定（否则每轮都冷缓存）、让历史可归档而不是可删除、让能力长在边缘而不是核心。

“活很久”带来的第一个硬约束是 Prompt Cache（Provider 对请求前缀的复用机制，命中要求模型、账户、Endpoint 与前缀字节完全一致）。一次性任务型 Agent 可以每轮重建 system prompt，代价只是一次冷请求；长会话 Agent 如果这么做，用户每说一句话都在为整段历史重新付全价。于是「配置改动默认下一 Session 生效」这种看起来不够灵活的产品行为，其实是成本模型逼出来的。

1.2 两条支配性原则

Prompt Cache 是成本与延迟边界长会话必须复用字节稳定的前缀。中途重建 system prompt、切换 toolset 或回写旧历史都会让缓存失效；因此只有压缩等显式路径允许重组过去上下文。
Core 是窄腰，能力长在边缘每个模型工具 Schema 都要随每次 API 请求发送。能用已有工具、CLI+Skill、服务门控、Plugin 或 MCP 解决的能力，不进入核心工具面。

二、系统全景与进程拓扑

代码事实Hermes 复用的是 Agent Core，而不是强迫所有表面使用同一 UI。Classic CLI、TUI、Desktop、Gateway、ACP 和 API 拥有不同进程边界，但最终都将一轮工作交给 AIAgent.run_conversation()。

  • 共享：SessionDB、Provider 解析、AIAgent、工具注册表、Slash 命令定义、审批语义、压缩与 Memory 生命周期。

三、入口、路由与会话身份

3.1 统一命令入口

hermes_cli/main.py 是命令级入口，负责尽早应用 Profile、加载配置并选择 Classic CLI、Ink TUI、Gateway、Dashboard/Serve、ACP 或其他子命令。Profile 必须在核心模块导入前写入 HERMES_HOME，这样模块级路径缓存天然落在正确实例中。

3.2 Gateway 消息链

Adapter 归一化事件：平台 Webhook、轮询或 WebSocket 统一为 MessageEvent 与 SessionSource。
构造 session key：组合 profile、platform、DM/group、chat、user、thread，形成平台侧并发与隔离键。
双护栏分流：Adapter 先检查活跃 Session，Runner 再处理控制命令；审批、停止和新会话命令必须绕过两层排队。
SessionStore 映射：把平台 session key 映射到可恢复的 SessionDB durable ID。
线程执行 Agent：asyncio 进程不直接阻塞在同步模型循环，Runner 将 run_conversation 放入执行器。
Adapter 回传：流式增量、工具进度、审批请求和最终文本重新映射为平台能力。

3.3 三种 Session 身份

身份用途常见错误
Durable Session ID历史、导航、持久化、恢复拿运行时临时 ID 查询数据库
Runtime Session ID当前进程流式订阅、事件路由窗口重连后继续当作永久身份
Lineage Root / Compression Identity跨旧式旋转压缩追踪会话家族把父子链当成当前默认每次都发生
当前默认压缩是 in-place：旧消息软归档，durable ID 不变。parent_session_id 仍为兼容旧式 in_place=false、分支和历史恢复服务，但不是“每次压缩都会产生新会话”的证明。

四、AIAgent 装配：从配置到冻结运行时 子文档

run_agent.py 中的 AIAgent 是公共门面；大部分新实现已经拆到 agent/。构造阶段通过 agent_init.init_agent() 把一次会话的能力边界固化下来。

4.2 为什么工具集在会话中冻结

工具 Schema 是 system/prefix 语义的一部分。中途安装 Skill、切换 Toolset 或改变服务可用性，如果立刻重建模型可见工具列表，会破坏缓存并让历史中的工具能力与当前请求不一致。因此改变 Prompt/Toolset 的 Slash 命令默认延迟到下一 Session；只有显式 --now 才承担立即失效成本。

Hermes 的“运行时对象可重建”与“会话前缀必须稳定”并不冲突。Gateway 可以每个 Turn 构建新的 AIAgent 实例，只要它从 SessionDB 恢复完全相同的 system prompt 和会话状态，Provider 仍可命中前缀缓存。

五、Agent Loop：可中断的模型—工具状态机 子文档

这个循环真正难的不是「调模型、调工具、再调模型」，而是三件事同时发生时怎么收场：用户在打断、预算在耗尽、Provider 在报错。Hermes 的做法是把它们全部建模成显式终态，而不是散落的 try/except。

5.1 一次 Turn 的真实调用链

AIAgent.run_conversation → SessionCoordinator 获取本会话执行权 → build_turn_context → 恢复/构建 system prompt → 持久化用户消息 → Memory prefetch / plugin user-side context → preflight compression → conversation_loop → 准备请求 / 角色修复 / cache markers → interruptible streaming API call → 文本终态 或 tool_calls → 工具执行与 Observation 回填 → 继续下一次模型调用 → finalize_turn → 处理预算、未闭合工具序列、持久化、trajectory 与清理

5.2 循环终止与继续条件

事件行为会话结果
模型返回最终文本记录 assistant，结束循环成功终态
模型返回 tool_calls执行工具、按原顺序写入 tool results回到模型
上下文溢出/413分类错误，尝试压缩后重试冷前缀后继续
限流/鉴权/服务错误刷新凭据、轮换账户或激活 fallback可能切 Provider

5.3 IterationBudget

产品配置通常由 agent.max_turns 注入较高上限；循环同时检查 API 调用计数和 Budget Remaining。Grace Call 允许在预算刚好耗尽时再做一次不继续扩散工具调用的收口。委托子 Agent 使用自己的 delegation.max_iterations，不是简单共享父 Agent 的同一个剩余计数器。

5.4 并行工具

多个独立 Tool Call 可通过线程池并行，但结果必须按模型原始调用顺序回填。Interactive、审批、状态相关或有依赖的工具会强制串行；执行器还支持分段策略，在可并行组和必须串行点之间切分。

内部消息采用 OpenAI 风格作为中间表示。正常序列是 User → Assistant；有工具时是 Assistant(tool_calls) → Tool… → Assistant。连续 Tool 结果允许，连续 User/Assistant 必须合并或修复。异步完成事件不得插入正在进行的工具序列。

六、Prompt Assembly 与缓存边界 子文档

6.1 三层 system prompt

层内容生命周期
StableSOUL/默认身份、工具行为、Skills 索引、环境和平台提示会话期冻结
Context调用方 system message、项目上下文文件会话开始解析
VolatileMEMORY/USER 快照、外部 Memory 静态块、时间/Session/Provider 信息名字“volatile”不代表每 Turn 改写；仍冻结在该会话前缀

6.2 项目上下文优先级

项目规则不是全部叠加，而是按优先级选择首个匹配：.hermes.md/HERMES.md（可向上到 Git Root）→ 当前目录 AGENTS.md → CLAUDE.md → Cursor Rules。SOUL.md 独立占据身份槽，避免重复注入。内容会做安全扫描、Frontmatter 处理和按模型窗口缩放的截断。

6.3 API-call-time 注入

Memory Recall、Gateway Session Overlay、pre_llm_call 插件上下文和 Prefill 等动态材料不回写冻结的 system prompt，而是进入当前用户消息的 api_content sidecar 或请求期消息。展示内容可以保持干净，同时数据库保留实际发给 Provider 的字节以支持稳定 Replay。

6.4 Anthropic Prompt Caching

Hermes 使用最多四个断点：system prompt 一个稳定断点，加最近三条非 system 消息的滚动断点。缓存命中依赖模型、账户、Endpoint 和前缀字节完全一致；切模型、Fallback、Credential Pool 轮换或重组中段历史都会造成冷请求。

断点像书签：书签之前的内容按缓存价结算，书签之后按全价。所以架构目标不是「让 prompt 更短」，而是「让书签尽量往后挪、且中间那段永远不要被改写」。

┌─ 断点 1（会话期冻结，命中率最高）────────────────────────────┐ │ system prompt │ │ Stable ：SOUL/身份 · 工具行为 · Skills 索引 · 环境提示 │ │ Context ：调用方 system message · 项目上下文文件 │ │ Volatile ：MEMORY/USER 快照 · Provider 信息 │ │ （名字叫 volatile，但同样冻结在本会话前缀里） │ │ + tool schemas（Toolset 决定；会话中途变更即整段失效） │ └───────────────────────────────────────────────────────────────┘ ├─ 历史消息（不打断点，靠前缀连续性搭便车） │ user / assistant / tool … ├─ 断点 2 ┐ ├─ 断点 3 ├─ 最近三条非 system 消息上的滚动断点 └─ 断点 4 ┘ ▲ │ 动态材料不回写冻结区，而是挂到当前用户消息的 api_content sidecar： │ Memory Recall · Gateway Session Overlay · pre_llm_call 插件上下文 · Prefill 会让整条前缀作废的动作（每一条都对应一个产品决策）： 切模型 / fallback ──► Provider cache key 变了 Credential Pool 轮换 ──► 账户维度的 cache key 变了 会话中途改 Toolset ──► 断点 1 内容变了（所以 Slash 命令默认下一会话生效） 重组中段历史 ──► 只有压缩这一条被允许的路径，且它自己就要付一次重建成本
示例场景：一个每天上百轮的 Telegram 长会话，system prompt 约 9k token、历史 30k token。团队最初把「当前时间」写进 stable 层，结果每轮 system prompt 字节都不同，缓存命中率长期在 0%——单轮输入按全价 39k token 结算。把时间戳挪进当前用户消息的 api_content sidecar 后，断点 1 变回字节稳定，命中率升到 90% 以上，长会话的输入侧账单降到原来的三分之一左右。这类问题的排查信号很明确：Usage 里 cache_read 恒为 0，而 input 随历史线性增长。
Prompt Cache 不只是“省 Token”的优化，它反向塑造了命令语义、Memory 注入位置、异步事件回流方式、Toolset 生命周期和压缩事务。它是 Hermes 架构中最重要的非功能约束。

七、上下文压缩：唯一被允许重组历史的主路径 子文档

压缩是整套架构里唯一被授权「改写过去」的路径。正因为只有它有这个权力，其他所有需要往历史里塞东西的功能（Memory 召回、异步完成、插件上下文）才必须另找位置，而不是顺手改一改旧消息。

这里要区分两个容易混的词：In-place 压缩（同一 Durable Session ID 下把旧消息标为 active=0, compacted=1，内容不删、仍可 FTS 搜索）是当前默认；Session Lineage（旧式旋转压缩产生新 Session ID 并用 parent_session_id 串成父子链）只在关闭 in-place 或做分支时才出现。把后者当成「每次压缩都会发生的事」，会让会话统计和历史导航全部算错。

7.1 双层触发

层默认角色Token 依据
Agent Context Engine正常的 Loop 内压缩，阈值可配置并可按模型覆盖优先使用 API 实际 Usage
Gateway Session Hygiene进入 Agent 前的高水位安全网，避免隔夜累计直接打爆窗口上轮实际值，缺失时粗估

7.2 默认 Compressor 的四阶段

廉价清理旧 Tool Output：受保护尾部之外的长结果先替换为占位，减少摘要输入。
计算 Head/Middle/Tail：保留开头、按 Token Budget 和最少消息数保护最近尾部，并保证至少保留真实用户锚点。
结构化摘要 Middle：辅助模型产出 Goal、Constraints、Progress、Decisions、Files、Next Steps、Critical Context。
重装合法消息序列：摘要角色根据邻接关系选择，清理孤儿 tool call/result，提交压缩事务。

7.3 In-place 与 Legacy Rotation

默认 compression.in_place=true：同一 Session ID 下把旧消息标为 active=0, compacted=1，新消息列表包含 Head、Summary、Tail。旧内容不删除，仍可搜索。关闭该选项时，才使用新 Session ID 与 parent_session_id 链。

7.4 特殊 Provider 路径

  • Codex app-server：真实上下文归 Codex Thread 所有，本地改 transcript 无法缩短服务端线程，因此通过 app-server 原生 compaction 事件处理。
  • Responses Native Compaction：符合模型与路由条件时可让服务端生成 opaque compaction item；Hermes 保留 replay sidecar，并以本地 Compressor 作后备。
  • 失败风险：若摘要模型窗口小于主模型，完整 Middle 可能放不进去；这会显著降低压缩质量，必须作为部署校验项。
示例场景：某团队把摘要模型配成一个 32k 窗口的便宜模型，主模型窗口 200k。平时没问题，直到一次长任务里 Middle 段本身就有 60k token——摘要调用直接 413，压缩事务回滚，主循环随后又因为上下文溢出再触发一次压缩，形成每分钟数次的失败循环，单会话白烧掉约 40 次无效调用。修复有两步：把摘要模型换成与主模型同窗口档位，并在阶段一「廉价清理旧 Tool Output」上把保护尾部之外的长结果先替换为占位，使进入摘要的 Middle 稳定在 15k 以内。部署校验里应当直接断言「摘要模型窗口 ≥ 主模型压缩阈值」，这是最容易被漏掉的一项。
压缩降低后续 Token，但需要一次摘要调用、事务提交和缓存重建。过早压缩会损失细节，过晚压缩会增加成本与溢出风险。阈值必须结合模型窗口、Provider 路由和任务 Tool Output 分布评估。

八、Provider Runtime 与 Transport 抽象 子文档

8.1 两个维度不要混淆

Provider 决定凭据、默认 Base URL、模型目录和商业路由；api_mode 决定请求协议、消息格式、工具格式、流式事件与响应归一化。同一个产品 Provider 可能随认证路径落到不同模式。

api_mode职责主要适配
chat_completionsOpenAI-compatible Chat CompletionsOpenRouter、自定义 Endpoint、多数 Provider
anthropic_messagesNative Anthropic MessagesSystem/Content Block、cache_control、tool use 转换
codex_responsesOpenAI Responses/Codexinput items、reasoning/replay sidecars、原生 compaction
bedrock_converseAWS Bedrock ConverseBedrock 请求/响应归一化
codex_app_server外部 Codex Agent Thread整 Turn 旁路 Hermes 主 Loop 的部分语义

8.2 Resolution Ladder

显式运行时请求优先，其次是保存的 config.yaml Provider/Model，再到对应密钥环境变量和 Provider 默认值。保存配置高于随手 Shell Export，避免旧环境变量静默劫持用户刚选择的 Endpoint。API Key 必须与 Base URL 绑定，防止 OpenRouter、AI Gateway 或 OpenAI Key 泄漏到错误主机。

8.3 Transport 的窄职责

agent/transports/ 负责 messages/tools 转换、API kwargs 和 response normalization；Client 构建、Streaming 取消、凭据刷新、重试、缓存和 Fallback 仍由 Runtime 编排。这样避免把业务状态机复制到每个 Provider Adapter。

8.4 Fallback 的代价

错误分类器区分限流、鉴权、Billing、上下文溢出、内容策略和服务错误。可恢复路径会先刷新凭据或轮换账户，再按配置链激活 Fallback。切换 Provider 可能同时改变 model、client、api_mode 和缓存策略，因此下一请求通常是冷缓存；这不是实现缺陷，而是 Provider Cache Key 的固有限制。

九、工具运行时：注册、暴露、调用 子文档

9.1 四阶段管线

tools/*.py 顶层 registry.register() → discover_builtin_tools() 用 AST 找出真正注册工具的模块 → toolsets.resolve_toolset() 决定本 Session 的能力范围 → registry.get_definitions() 执行 check_fn 并生成模型 Schema → model tool_call → agent-level intercept 或 handle_function_call() → middleware / pre-hook / approval / registry.dispatch / post-hook → JSON Tool Result 回填历史

Registry（进程里注册了什么）和 Toolset（这个会话允许模型看见什么）必须分开，因为前者是进程级、后者是会话级——合成一个，就等于让每个会话为所有插件的 Schema 付 token。

9.2 为什么既要 Registry 又要 Toolset

Registry 回答“进程里注册了什么以及如何调用”；Toolset 回答“这个 Session 的模型允许看到什么”。自动发现只完成注册，不代表暴露。新增内置工具如果没有进入某个 Toolset，模型永远看不到；反过来，注册很多插件/MCP 工具也不意味着每个会话都支付 Schema 成本。

9.3 check_fn 的正确含义

check_fn 用于服务可达、依赖存在或用户 Opt-in；结果有进程级 TTL 缓存。它不适合表达“当前请求来自 Desktop”这类 Session 身份，因为同一 Gateway 进程可同时服务 CLI、Desktop 和远程客户端。表面能力应由 Session Source 选择 Toolset。

9.4 Agent-level Tools

todo、memory、session_search、delegate_task 等虽然注册 Schema，但调用会在 Agent Loop 中短路，因为它们需要 AIAgent 本地状态、SessionDB、父子运行时或专门生命周期。直接走通用 Registry Handler 会得到保护性错误。

9.5 Tool Search 分层披露

当 Plugin/MCP 工具过多时，Hermes 可只向模型暴露 tool_search/tool_describe/tool_call 桥接面，按需发现具体 Schema。底层调用仍校验工具是否属于本 Session 已授权的可延迟集合，不能借 Tool Search 绕过 Toolset。

  • 按 Footprint Ladder 从下往上选：先想能不能用现有工具加参数，再想 CLI+Skill，最后才考虑核心工具。
  • 用 check_fn 表达「服务是否可达 / 依赖是否安装」，让不可用的能力自动从 Schema 里消失。
  • 表面差异（Desktop 独有能力、Webhook 受限能力）用 Session Source 选 Toolset 表达。
  • MCP 工具多的时候开 Tool Search 分层披露，让常驻 Schema 保持在可控体积。
  • 不要用 check_fn 判断「请求来自哪个客户端」——同一个 Gateway 进程会同时服务 CLI、Desktop 和远程客户端，进程级缓存的结果对谁都不对。
  • 不要在会话中途悄悄改模型可见工具列表，那会直接击穿 system prompt 断点，代价远大于省下的一次重启。
  • 不要给 agent-level tool（todo、memory、delegate_task 等）走通用 Registry Handler，它们需要 AIAgent 本地状态，只会拿到保护性错误。
  • 不要把「远端文件读不到」当成缺工具，去加一个新的文件工具——那是 Environment 抽象没对齐，加工具只会让两套语义永久分叉。

十、执行环境、审批与副作用边界 子文档

10.1 七类 Terminal Backend

后端隔离/位置适用场景
Local宿主机低延迟开发，依赖命令审批
Docker本机容器可复现依赖与文件系统隔离

File Tools 与 Terminal 共享环境选择，使“读远端文件”和“在远端执行命令”落在同一个 Workspace 语义中。修复远程文件不可见问题应优先修挂载/环境抽象，而不是向核心添加重复文件工具。

10.2 审批管线

危险命令先经过硬拒绝规则、用户拒绝规则、危险模式和永久 Allowlist，再由 CLI/Gateway/Desktop 的审批回调与可选 Smart Approval 决策。Gateway 审批等待属于 Human-in-the-loop 状态；/approve、/deny 以及明确的 yes/no 必须绕过活跃会话排队，否则 Agent 会永久等不到回答。

10.3 Checkpoint 不是模型工具

写文件前的 CheckpointManager 使用影子 Git 等机制保存恢复点，对模型透明。它不等于 Session Checkpoint，也不进入工具 Schema；它是文件副作用层的安全网。

10.4 威胁边界

  • Webhook 等不可信入口默认使用收窄的 Safe Toolset，避免第三方内容直接获得 Terminal/File。
  • Plugin 覆盖内置工具必须显式开启 allow_tool_override。
  • MCP 需要 Server Trust、路径、工具 include/exclude 与运行方式审计。
  • 容器不是自动安全：挂载、网络、Secrets、资源限制和镜像供应链仍由部署方负责。
  • .env 只放 Secrets；超时、阈值、功能开关和显示设置进入 config.yaml。

十一、Skills、Plugins 与 MCP：能力如何长在边缘 子文档

11.1 Skills 是按需加载的程序性记忆

Skills 用紧凑索引进入稳定 Prompt，完整 SKILL.md 只有在匹配任务时通过 skill_view 加载。Skill Slash Command 解析后作为普通 User Message 提交，不修改 System Prompt；这既保留 Prompt Cache，也让执行轨迹与用户指令遵守相同角色规则。

11.2 通用 Plugin

PluginManager 从用户目录、项目目录（显式 Opt-in）、仓库 Bundled 和 Python Entry Point 发现插件。PluginContext 可注册 Tool、Hook、CLI Command、Gateway Platform 以及多种 Provider。Hooks 覆盖 LLM/Tool/Session/API 生命周期，但兼容策略要求新增字段以可选 Keyword 方式扩展，不能破坏旧插件签名。

11.3 Specialized Providers

类型发现/优先级选择语义
Model Provider独立懒发现；用户同名可覆盖 Bundled按 provider ID 解析 Profile
Memory ProviderBundled-first，防掉落目录影子覆盖单选 External Provider
Context Engine显式配置，不自动激活单选，默认 Compressor
Browser/Web/Image/TTS 等各自 Registry/ABC配置选择，按需懒依赖

11.4 MCP 生命周期

MCP 不在 model_tools Import 时同步发现，避免 Gateway Event Loop 被外部 Server 启动阻塞。各入口在合适的启动阶段显式发现；每个 Server 形成 mcp-<name> Toolset。大量工具可以延迟披露，Session 结束/进程退出时由 Client Lifecycle 清理。

Skill 解决“模型需要知道如何做”；Plugin/MCP 解决“运行时需要新的结构化能力”；Provider ABC 解决“同一类别有多个实现”。先判断问题属于知识、能力还是策略，再选扩展面。

十二、SessionDB、FTS 与持久状态 子文档

12.1 SQLite 是会话真相源

state.db 存储 Session 元数据、完整消息、模型/计费 Usage、System Prompt 去重、Gateway Routing、Compression Locks 和 Async Delegation。WAL 允许多读单写；应用层使用短 SQLite Timeout、带随机抖动的重试和 BEGIN IMMEDIATE，降低多个 Hermes 进程同时写入的锁车队效应。

12.2 消息的双重视图

  • 展示视图：content/display_kind/display_metadata 面向 UI，可隐藏 Memory Fence 等内部上下文。
  • API Replay 视图：api_content 保存实际发送字节，另有 reasoning、Codex item 等 Sidecar。
  • 压缩视图：active/compacted 区分当前 Prompt 与仍可搜索的历史。

12.3 FTS5

消息内容、工具名和工具调用进入 FTS5；标准 Unicode61、Trigram 和 CJK 索引覆盖单词、子串与中文检索。重建期间用 High-water/Progress 元数据门控 Trigger，防止后台重建与实时写入双重索引或漏删。

12.4 恢复语义

数据库层提供 Schema Reconcile、迁移、损坏隔离、FTS 重建、孤儿压缩会话修复和 Gateway Session 收养。Resume 受最大消息数保护，防止异常大历史一次性拖垮进程。Batch/RL Trajectory 不写入 SessionDB，以免训练数据和用户会话互相污染。

所有持久路径必须从 get_hermes_home() 派生。Profile 的配置、密钥、Session、Memory、Skills、Cron、Kanban 与 Logs 相互隔离；只有 Profile 管理根目录有意锚定用户 HOME，便于从任一 Profile 枚举全部实例。

十三、Memory 与自进化学习闭环 子文档

13.1 两类 Memory

类型内容注入时机
Local SnapshotMEMORY.md 与 USER.md 中稳定事实新 Session 的 System Prompt Volatile Tier
External RecallHoncho、Mem0、Supermemory 等 Provider 查询结果当前 Turn 的 User-side api_content

13.2 MemoryManager 生命周期

Session 初始化：选择最多一个 External Provider，加载静态 System Prompt Block。
Turn Start：对非琐碎 Prompt 执行 Prefetch，将召回结果包在 Memory Fence 中。
Tool Loop：Provider 可贡献自己的 Tool Schema，由 Manager 专门分发。
Turn End：同步当前对话并排队下一次 Prefetch；Shutdown 有界等待。
Pre-compress：在上下文丢失前给 Provider 刷新/保存机会。

agent_context 区分 primary、subagent、cron、flush；Cron 默认 skip_memory=true，子 Agent 通常不把临时探索写进用户画像，避免自治任务污染长期身份。

13.3 Skills 学习闭环与 Curator

Hermes 可在复杂任务后创建 Skill，将可重复步骤从会话经验转为程序性知识。Usage Sidecar 跟踪 View/Use/Patch 与最后活动时间；Curator 在 Gateway 空闲窗口运行，对 Agent-created Skills 做 Active → Stale → Archived 转换。Pinned Skill 永远豁免自动归档；Archive 可恢复，系统不以自动删除作为治理手段。

Memory 回答“关于用户和世界，哪些事实以后仍有用”；Skill 回答“遇到这类任务，应该遵循什么流程”。前者是事实性长期上下文，后者是按需披露的程序性能力，两者的成本模型和更新机制不同。

十四、Delegation、execute_code 与后台任务 子文档

14.1 子 Agent 角色

角色能力限制目的
Leaf聚焦任务、Terminal/File/execute_code 等移除再次委托、Memory、Clarify、Send Message、Cron，防无限扩散与交互死锁
Orchestrator可继续委托并汇总子任务受最大 Spawn Depth 与并发上限控制

14.2 同步与后台

同步委托阻塞父 Tool Call，子 AIAgent 在线程池完成后把摘要作为 Tool Result 返回。后台委托立即返回 Handle；Daemon Executor 运行子任务，将结果写入 Async Delegation 状态和 Completion Queue。父会话空闲时，以一个新的 Turn 接收完成事件。

后台任务的难点不在「怎么跑」，而在「跑完之后结果从哪个门进来」。Hermes 选择让它敲正门——开一个新 Turn，而不是从后窗翻进一个早就关闭的 tool call。

14.3 为什么完成事件必须开新 Turn

若把异步结果强行追加为 Tool Message，原始 Tool Call 早已完成或当前会话可能正在另一轮，会产生孤儿 Tool Result、连续角色或过去上下文突变。新 User-side Turn 同时满足角色合法、Prompt Cache 可预测和用户可见的时间顺序。

14.4 execute_code

execute_code 允许在沙箱 Python 中以 RPC 方式批量调用已授权工具，把多个机械步骤折叠为一次模型回合。它降低上下文往返成本，但不扩大授权面：可调用工具仍来自当前 Session 的解析结果，并受审批与环境边界约束。

14.5 耐久性边界

后台委托与 Background Terminal 本质上仍依赖当前进程执行。数据库可恢复“已完成但未交付”的结果，却不会在进程死亡后自动重跑任意子 Agent。真正需要跨重启保证的任务应使用 Cron 或具有自身租约/认领模型的 Kanban——它们都建立在 Lease / Claim（带过期时间的跨进程任务所有权，超时后可被其他 Worker 回收）之上，这是「进程可以死、任务不能丢」的最小机制。

十五、Cron 与 Kanban：两种自治工作模型 子文档

15.1 Cron：时间驱动的独立 Agent Session

Cron Job 存储在 Profile 内的 jobs.json，支持周期、Cron 表达式、自然语言 Every 和一次性时间。Ticker 先在锁内认领并推进 next_run_at，再执行任务；Catch-up、Grace Window 和 Claim TTL 处理错过与多进程竞争。每次 Fire 创建独立 source=cron Session，不把投递内容硬插进目标聊天历史。

  • 可附加 Skills、工作目录、Model/Provider、Fallback、前置脚本和 context_from。
  • no_agent=true 时脚本输出就是整个任务结果。
  • 硬中断约束防止失控 Loop 长期占用 Scheduler。
  • Delivery 是出站副作用，不等于目标 Session 的上下文延续。

15.2 Kanban：依赖驱动的耐久多 Agent Board

Kanban 使用每 Board 独立 SQLite，任务、依赖、Run、Comment、Event、Attachment 与 Notification 都持久化。Dispatcher 回收失效 Claim、把父任务已完成的节点提升为 Ready、原子认领并启动指定 Profile Worker。连续失败达到阈值会自动 Block，避免无休止重试。

十六、多端 UI、协议与状态权威 子文档

16.1 TUI

Ink/React 负责终端渲染，Python tui_gateway 负责 Session、AIAgent 与 Slash。二者通过 Stdio ND-JSON-RPC 通信：请求包括 Session Create/Resume、Prompt Submit、Slash、Approval、Interrupt；事件包括 Message Delta/Complete、Tool Progress、Clarify、Secret 和 Session Info。Slash Worker 子进程复用 Classic CLI 命令实现，避免在 TypeScript 复制完整命令控制器。

16.2 Dashboard

Dashboard 的 /chat 用 xterm.js 通过 WebSocket 连接 PTY Bridge，后端实际 Spawn hermes --tui。浏览器发送原始 PTY 字节与 Resize 控制帧。因此主 Transcript、Composer 和 Slash 语义应在 Ink 扩展，而不是在 Dashboard React 再实现一套聊天。

16.3 Desktop

Desktop 是独立 Electron + React Chat Surface。Electron 管机器能力和后端生命周期；Renderer 管体验与短期 UI 状态；Headless Backend 管 Session、Tool 与模型。Renderer 通过共享 JsonRpcGatewayClient 连接 hermes serve，没有 Dashboard 前端运行时依赖。Desktop Slash Palette 策展 Built-in 噪音，但必须放行 Skills 与 Quick Commands。

16.4 ACP 与 API

ACP 通过 Stdio JSON-RPC 把 Hermes 暴露给 VS Code、Zed、JetBrains，处理 Editor Permission、Edit Approval、Streaming 与 Cancel。API Server 提供 OpenAI-compatible Chat/Responses/Run 与 SSE，同时支持 Hermes Session Header 延续。两者复用 Core，但表面权限和事件格式独立。

16.5 状态权威原则

Backend 权威跨表面可变的 Session、模型、历史、工具结果。
Electron 权威本机进程、文件系统、窗口、安装更新与原生能力。
Renderer 权威当前窗口展示、临时交互、未提交 Draft。
Session Source 权威“谁在连接”决定 Desktop/Project 工具；不能用后端进程环境变量替代。

十七、并发、恢复与可观测性 子文档

17.1 并发边界

  • SessionCoordinator / Active Session：同一会话单写，跨会话可并行。
  • SQLite：WAL + 应用抖动重试；Compression 使用跨进程 Lease。
  • Tool Execution：线程池并行，但 Interactive/Dependent Tools 串行，Result 顺序稳定。
  • Async Bridge：根据当前线程是否已有 Event Loop，选择持久 Loop、一次性线程或 Thread-local Loop。
  • Compression Commit Fence：Hard Interrupt 与压缩提交互斥，防止半提交上下文。

17.2 错误与恢复层次

17.3 可观测性

hermes_logging 写 Agent/Error/Gateway 日志并带 Session Context；SessionDB 累加 input/output/cache/reasoning Token 与估算/实际成本；可选 Trajectory 输出 ShareGPT 风格样本，用于调试、训练和压缩分析。Plugin Hooks 可接观测后端，但任何外发 Telemetry 必须显式 Opt-in。

Hermes 的可观测事实分散在日志、SessionDB、Trajectory、Delegation Live Log、Cron Ledger 和 Kanban Events 中。这符合各子系统的耐久性边界，但统一诊断需要关联 Profile、Session、Task、Delegation/Run ID；不能只看单个文本日志。

18.1 最值得学习的取舍

  • 缓存优先于即时动态性：配置变更默认下一 Session 生效。
  • 独立 Session 优先于历史注入：Cron 和异步完成通过新 Turn/独立 Session 保持消息不变量。
  • 结构化 Registry 优先于条件分支：Provider/Tool/Plugin 用注册表减少核心耦合。
  • 边缘扩展优先于核心工具：Schema 成本成为架构决策的量化指标。
  • 可恢复归档优先于自动删除：压缩软归档、Curator Archive、Kanban Event Ledger。

19.2 排障从哪一层开始

  1. 确认入口、Profile、HERMES_HOME 与 Session Source。
  2. 确认 durable/runtime/session key 是否混用，SessionDB 是否恢复了正确 System Prompt。
  3. 检查本 Session 的 Toolset 与 check_fn，不要只看 Registry 是否注册。
  4. 按 api_mode 而不是 Provider 名追踪消息转换与 Streaming。
  5. 区分 Context Overflow、Provider Error、Tool Error、Approval Wait 与 Interrupt。
  6. 遇到异步问题同时关联 Completion Queue、Delegation/Process ID 和父 Session。
  7. 遇到压缩问题检查 in-place 模式、Summary Model 窗口、Tool Pair 对齐和 Commit Lock。

19.3 测试策略

关键边界需要真实路径测试：临时 HERMES_HOME 下导入真实模块、走真实 Provider Resolver/Tool Discovery/SessionDB，而不是只 Mock 内部函数。行为契约应验证“数据之间的关系”——例如所有可见 Tool 必须属于授权 Toolset、压缩后消息角色合法——而不是冻结当前工具数量、Provider 列表或 Schema Version。

Q&A

Hermes 的 Agent Loop 是异步的吗？
核心 run_conversation 是同步状态机。Gateway/TUI 用 asyncio 接入多会话，再把同步 Agent 放到执行器线程；异步 Tool Handler 由桥接层适配。这种设计使核心在 CLI、Gateway、ACP 和 Batch 中保持一致。
为什么 Memory 更新后不会立即出现在 System Prompt？
System Prompt 在会话期冻结以保护 Provider Prefix Cache。稳定事实写盘后在新 Session 或显式重建时成为新快照；当前 Turn 的动态 Recall 通过 User-side api_content 注入。
压缩是否一定生成新的 Session ID？
不是。当前默认 compression.in_place=true，同一 Durable ID 下软归档旧消息。只有关闭该选项或走旧式旋转路径时才通过 parent_session_id 形成链。
为什么后台委托完成后不能直接追加 Tool Result？
原 Tool Call 可能早已闭合，当前会话也可能处于另一轮。直接追加会产生孤儿 Tool、角色错序和缓存前缀突变；Completion Queue 在会话空闲时开启新 Turn 更安全。
新增一个第三方系统集成应该放进 tools/ 吗？
通常不应该。先评估 CLI+Skill、Standalone Plugin 或 MCP。只有对几乎所有用户都基础、无法由现有工具表达且值得永久 Schema 成本的能力，才考虑 Core Tool。
Dashboard 和 Desktop 是否共享同一聊天前端？
不共享。Dashboard 嵌入真实 Ink TUI 的 PTY；Desktop 是独立 React Chat Surface。它们共享 Python Backend 和 JSON-RPC 能力，但 UI、状态权威和进程模型不同。
Hermes 的长期任务能否在进程重启后继续执行？
普通后台委托/进程不能保证重跑。它们可以耐久交付已完成结果，但执行本身依赖进程。跨重启任务应使用 Cron，依赖驱动的多 Worker 工作应使用 Kanban。
Hermes Agent 有官方论文吗？
当前未发现软件本身的官方论文。Hermes 4 Technical Report 是模型报告；架构应引用官方仓库、开发文档和源码，而不是把模型论文当成 Agent Runtime 论文。
