01

SWE-agent 是什么？

一句话说清：SWE-agent 是一个能自主修复 GitHub Issue 的"AI 软件工程师"，也是一套为研究而生的 Agent 运行时。 你交给它一个 Issue 和一个代码仓库，它会自己开一个 Docker 容器当"工位"，自己读代码、自己敲命令、自己写修复，最后交给你一份 patch（代码补丁）和一份完整的"工作记录"。

它由普林斯顿 NLP 组开源，论文发表在 NeurIPS 2024，用 Python 写成。和大多数"拿来就用"的工具不同，SWE-agent 从第一天起就是一个研究项目：它想回答的核心问题是——大模型和计算机之间的那层"接口"该怎么设计，才能让 AI 真正干好软件工程这件事？

这层接口有个专属名字：ACI（Agent-Computer Interface，智能体-计算机接口）。就像人机界面（HCI）设计得好，人用起来效率翻倍一样，ACI 设计得好，模型干活的成功率也会大幅上升。这是整个项目最核心的理念，我们第 3.3 节会专门讲。

朴素做法直接给模型一个 shell
最直觉的做法是把 bash 开放给大模型：想干嘛就敲命令。听起来能力无限，实际灾难不断——命令敲错一个字符、输出刷屏撑爆上下文、遇到交互式程序直接卡死、干完了还不知道怎么"交卷"。模型的大部分精力都浪费在"和计算机搏斗"上。
SWE-agent 的答案精心设计每一层
给模型一套量身定制的工具（ACI 工具箱）、一个隔离的容器工位（Docker）、一套预算护栏（钱和时间都有上限）、一套交卷协议（sentinel 握手），外加全程留痕（轨迹文件）。每一步都可控、可复盘、可重放。
背景补充：什么是 SWE-bench？
SWE-bench 是同一团队更早发布的评测基准：收集了 12 个热门 Python 开源仓库的 2294 个真实 GitHub Issue。每个任务给 Agent 一个 Issue 和对应版本的代码库，Agent 产出 patch，由仓库自带的真实测试用例判定是否"解决"（resolved）。它是这个领域最主流的考卷，SWE-agent 就是在它上面被反复检验的。后文出现的"resolved 率"都指这个考试的成绩。

先澄清：它"不是"什么
  • 不是聊天机器人：它不为"对话"设计，而为"完成任务"设计。交互是手段，patch 是目的。
  • 不是多智能体系统：默认主链路上只有一个 Agent 从头循环到尾，没有一群 Agent 分工协作（多尝试选优的 RetryAgent 是可选外环，见 3.8）。
  • 不是还在密集迭代的产品：官方 README 明确说明，团队当前的主力开发已转向更精简的 mini-swe-agent。SWE-agent 今天的价值在于：它是 ACI 理念的完整参照实现，也是大量研究复现的基准。
  • 不是安全沙箱：它内置的命令黑名单（blocklist）只是防止模型误用容器不支持的命令，真正的安全边界要靠容器、网络与凭据配置自己搭建（第 4 章细说）。
02

一次 Issue 修复的完整旅程

抽象的架构很难记住，故事好记。我们跟着官方教程里那个真实的小任务走完全程：

场景test-repo 仓库有一个除零崩溃的 Issue
SWE-agent/test-repo 是官方准备的玩具仓库，它的 Issue #1 报告了一个 ZeroDivisionError。你敲下这样一条命令，然后泡了杯咖啡：
sweagent run --problem_statement.github_url=https://github.com/SWE-agent/test-repo/issues/1 \
  --env.repo.github_url=https://github.com/SWE-agent/test-repo --agent.model.name=gpt-4o
一条命令进门，分发到"单任务模式"
sweagent/run/run.py → main()

命令行的入口是 sweagent，它背后其实是一个子命令家族：run（单个任务，本次的主角）、run-batch（批量跑基准）、inspector（网页回放）、run-replay（重放轨迹）等十几个。入口函数用 argparse 解析出子命令，把参数交给对应的运行类。

命令里那三个 --xxx.yyy 参数分别指定了任务说明（GitHub Issue 地址）、代码仓库和模型——这三样正是"AI 工程师开工"所需的全部材料。

蓝图变大楼：配置装配
run/common.py → run/run_single.py · RunSingle.from_config()

SWE-agent 的所有行为都由配置驱动。这一步把 YAML 配置文件（如 config/default.yaml）和命令行上的点号参数深合并成一棵配置树，再由 Pydantic 强类型校验（拼错的字段名会被当场拒绝），最后由 from_config 这条"总装线"产出三大件：一个 DefaultAgent（干活的人）、一个 SWEEnv（工位管理员）、一组 Hook（挂在流程各处的观察哨）。

类比理解像装修：YAML 是设计蓝图，命令行参数是"这面墙临时改个颜色"的现场变更，from_config 是施工总队——最后交付的是一套可以直接开工的班子，而不是一堆散件。
准备工位：拉起容器、克隆仓库
environment/swe_env.py → SWEEnv.start()

Agent 绝不会在你的主机上乱来。SWEEnv 会通过外部库 SWE-ReX 启动一个全新的容器（默认镜像 python:3.11），在里面开一个持久的 bash 会话，把目标仓库克隆进去并重置到干净状态。之后模型发出的每一条命令，都只发生在这间"隔离工位"里。

类比理解新员工入职第一天，公司先给他一间独立办公室和一台干净的电脑——他怎么折腾都影响不到别人。
开工布置：安装工具、注入任务
agent/agents.py → DefaultAgent.setup()

setup() 做三件事：把配置里选定的工具 Bundle（bash、文件编辑器、submit 等）上传进容器并装好；把 Issue 正文作为 PROBLEM_STATEMENT 写入环境变量；把"岗位说明书"（system prompt）和任务说明放进对话历史。布置完毕，Agent 正式上岗。

心跳循环启动：思考 → 行动 → 观察
agents.py → run() / step() / forward()

这是整个系统的心脏，每一圈走四步：问模型（带上全部对话历史，模型以 function calling 方式回答"我想做什么"）→ 解析（ToolHandler 把模型的回答解析成一条命令）→ 执行（命令进容器跑，结果作为 observation 拿到）→ 记账（写回 History 和轨迹文件）。然后进入下一圈。

注意关键分工：模型只负责"说"，工具才负责"做"。模型输出的是"我想查看 division.py 的第 1 到 30 行"这样的意图，真正动手的是容器里的工具脚本。它的幻觉被挡在执行的边界之外。

源码入口：sweagent/agent/agents.py → DefaultAgent.run() / step() / forward()
交卷握手：sentinel 协议
tools/tools.py → check_for_submission_cmd()

SWE-agent 判断"任务完成"靠的不是模型说一句"我做完了"，而是一次协议握手：模型执行 submit 命令（默认配置下还会被要求二次确认），工具脚本在输出中打印一个特殊暗号 <<SWE_AGENT_SUBMISSION>>，Agent 看到暗号，才去容器里读取 /root/model.patch 作为最终答案。没对上暗号，一律视为还没做完。

类比理解像机场安检的对暗号：不是你说"我没带危险品"就放行，而是仪器扫出特定信号才算数。自然语言可以撒谎，协议不会。
归档：patch、轨迹、回放
run/common.py → save_predictions() · inspector/server.py

任务结束，三份产物落盘：<id>.traj 是全程"飞行记录仪"（每一步的思考、动作、观察、环境状态），<id>.pred 是预测记录，<id>.patch 是真正的代码补丁。想看它到底干了什么？一条 sweagent inspector --data_path … 打开网页回放，每一步都可点开细看。

类比理解医生写完出院小结，同时把完整病历归档——你随时能回看它每一步是怎么想的。

03

九大核心模块详解

下面把系统拆成九个模块逐个看。不需要全部读完——挑你感兴趣的部分即可。每个模块都配了生活类比和源码入口；想看行号级的实现细节，循着附录 C 的链接去读源码审计级的模块文档。

3.1 配置装配 —— 蓝图变大楼

类比理解配置系统像装修工程：YAML 文件是设计蓝图，可以叠好几份（后面的覆盖前面的）；命令行参数是"这面墙临时改个颜色"的现场变更，优先级最高；最后施工总队（from_config）把它们变成一支能立刻开工的队伍——Agent、环境、Hook 一次配齐。

合并规则只有两条，记住就够用：

优先级从高到低
命令行点号参数（--agent.model.name=gpt-4o） ＞ 多个 --config YAML 文件（按顺序深合并，后者覆盖前者） ＞ 代码内置默认值

配置树由 Pydantic 做强类型校验：字段名拼错、类型不对，启动时就报错，而不是跑到一半才炸。选择"用哪个 Agent、哪个模型、哪种任务源"靠的是配置对象里的 type 字段——写 agent.type: retry 就装配 RetryAgent，写 instances.type: swe_bench 就从 SWE-bench 装载考题，代码里的对应实现会被自动选中。

还要提醒一句：默认配置并不是"裸 Agent"。config/default.yaml 已经带上了完整装备——bash、Anthropic 风格文件编辑器、带二次确认的 submit、function calling 解析器、prompt cache 优化，一应俱全。想要极简版可以用 config/bash_only.yaml；想复刻论文时代的老配置则是 config/sweagent_0_7/07.yaml——三者不可互换。

源码入口：sweagent/run/common.py → BasicCLI.get_config() · sweagent/run/run_single.py → RunSingle.from_config() · 默认配置见 config/default.yaml

3.2 DefaultAgent 主循环 —— 系统的心跳

类比理解一位经验丰富的医生看诊，靠的不是一次性给出答案，而是一个循环：问诊（思考）→ 开检查单（行动）→ 看报告（观察）→ 再问诊……直到确诊开方。DefaultAgent 的主循环就是这个循环。
图 3 · 心跳循环。模型只"说"，工具才"做"——意图与现实之间永远隔着一层 ToolHandler。

循环内部有几个方法，各管一段（读源码时按这条线走）：setup() 负责开工布置；forward() 走一圈"问模型→解析→执行"；forward_with_handling() 给这一圈套上错误处理——模型输出格式不对就重新提问（默认最多 3 次，配置项 max_requeries），并把失败信息塞回去让它自我纠正；step() 在外面再包一层"记账"（更新历史、写轨迹、通知 Hook）；run() 则是 setup + 不停 step 直到任务结束。

值得注意：SWE-agent 没有 "最多走 N 步"这样的步数上限。它的预算护栏是时间和钱：单实例总执行时长默认 1800 秒、单实例成本默认 3 美元（见 3.6）。理由很实在——同样一步，跑测试和改一行代码的开销天差地别，按资源设限比按步数设限更合理。

任务怎么结束？不是"聊完为止"

一个 Agent 循环的收尾方式，比想象中讲究。SWE-agent 里一条任务有以下结局：

结局触发方式exit_status
正常交卷执行 submit，暗号握手成功，读到 patchsubmitted
认输放弃执行 exit_forfeit（白旗），"这题我不会"exit_forfeit
直接离场模型输出 exit，不带答案走人exit_command
被动保底钱花光 / 时间耗尽 / 上下文撑爆 / 环境崩溃 → autosubmit：自动 git diff 把手头改动存成 patch 再退出exit_cost / exit_total_execution_time / exit_context / …

其中 autosubmit（自动保底交卷）是很体现性格的设计：哪怕任务失败了，也尽量不浪费已经做对的部分。它会在退出前把当前工作区的改动打包成 patch——做了一半，也算一半的成果。

小澄清：为什么"循环"比"更聪明的模型"更重要？
单次调用再聪明，也会猜错。循环的意义在于：每一步的真实反馈都能纠正上一步的猜测。命令报错了？把报错喂回去再想。文件找错了？换个方向再搜。智能来自闭环反馈，而不是某一次天才的灵光一现。这也是为什么 SWE-agent 把那么多精力花在"观察结果怎么回流、格式错了怎么重问"这些循环细节上。
源码入口：sweagent/agent/agents.py → DefaultAgent.run() / step() / forward() / forward_with_handling() / handle_action()

3.3 工具与 ACI —— 整个项目的灵魂

类比理解招来一位新同事，你是丢给他一把什么都能干、但什么都不顺手的"瑞士军刀"，还是给他一套按他的工作专门设计的称手工具？SWE-agent 选择了后者——这套为 AI 量身定制的工具界面，就叫 ACI（Agent-Computer Interface，智能体-计算机接口）。

ACI 是 SWE-agent 论文（NeurIPS 2024）提出的核心概念。它的出发点很朴素：大模型并不是在"裸电脑"上干活，它看到的每一个命令、每一份输出，都是有人设计过的。这层界面设计的好坏，直接决定成功率。论文的消融实验给出了直观证据：同样的模型，用精心设计的 ACI 工具箱能解决 SWE-bench Lite 上 18.0% 的 Issue，换成裸 shell 只剩 11.0%——光换界面，就差出 7 个百分点（论文时期的历史数字）。

图 4 · 界面即生产力。同样的模型，换一套为它设计的接口，成功率显著上升。

ACI 的设计原则翻译成大白话就是四条：把常见操作变简单（改代码不该靠整文件重写）、用合适的抽象给信息（给行号窗口，不给原始字节流）、把搜索和导航连起来（搜到就能直接跳过去看）、为模型的犯错方式兜底（输出裁剪、格式纠错、黑名单拦截）。

默认工具箱里有什么

工具干什么一句话
bash执行任意 shell 命令万能的手，跑测试、搜代码、装依赖全靠它
str_replace_editor查看 / 创建 / 精确替换文件内容Agent 的笔，只改该改的地方（view / create / str_replace 等子命令）
submit交卷（默认版本要求二次确认）按下交卷铃，打印 sentinel 暗号
registry 小助手读写环境变量式的状态便签脚本之间传小纸条用的

仓库里还有一整套可选 Bundle：文件搜索（search）、窗口式编辑（windowed 系列）、认输（forfeit）、浏览器操作（web_browser）、图像查看（image_tools）等等，按需在配置里加装。

Bundle：工具是"部署单元"，不是 Python 插件

这是新手最容易读错的一点。SWE-agent 的一个工具（Bundle）就是一个目录：一份 config.yaml（声明有哪些命令、参数、文档）、一个 bin/ 文件夹（真正干活的 shell/Python 脚本）、可选一个 install.sh。启动时，这些文件被上传进容器（放到 /root/tools/、加进 PATH、跑一遍安装脚本）。之后模型"调用工具"的方式，就是在容器里执行一条 shell 命令。

类比理解Bundle 不是往主机上 pip install 一个插件，而是把一整个工具箱搬进办公室。工具箱里装的是扳手还是螺丝刀（bash 脚本还是 Python 脚本）都行，只要外面贴着统一的标签（config.yaml 里的命令声明）。

这么设计的好处：工具与 Agent 本体彻底解耦，加一个工具不用改一行 Agent 代码；工具的文档（docstring）会被自动整理给模型看——工具描述本身就是提示词的一部分，这正是 ACI 的精髓。

模型怎么"说话"，系统怎么"听懂"

默认配置用 function calling（函数调用）模式：模型不是输出自由文本，而是通过各家 API 提供的结构化机制"勾选"一个工具并填好参数——就像填表格而不是写信，格式天然可靠。负责"听懂"的是 ToolHandler：校验命令是否被黑名单拦截、拆解多行命令、送进容器执行、盯着输出里的 sentinel 暗号。想换成老式的纯文本解析（如 thought_action），改一行配置即可——解析器也是可插拔的。

铁律黑名单 ≠ 安全沙箱
工具黑名单（blocklist）的用途写在源码注释里：拦截容器环境不支持的命令（比如交互式的 vim），防止模型卡死——它是"误操作保护"，不是防御恶意模型的机制。真正决定安全边界的是：容器本身、目录挂载、网络出口和凭据配置。
源码入口：sweagent/tools/bundle.py（Bundle）· sweagent/tools/tools.py → ToolHandler · sweagent/tools/parsing.py（解析器）· 仓库顶层 tools/ 目录（各 Bundle 实物）

3.4 SWEEnv 与 SWE-ReX —— 隔离病房与施工队

类比理解让一个会执行任意命令的 AI 直接在你的主机上跑 bash，就像让实习生直接操作生产数据库——刺激但危险。SWEEnv 就是那间隔离病房：所有命令都在一间可随时丢弃的容器病房里进行，主机毫发无伤。而真正盖病房、管设备的"施工队"，是另一个独立的开源库 SWE-ReX。

读源码前必须知道一个分工：SWE-agent 自己并不实现容器操作。启动 Docker、在容器里开 shell、传文件这些脏活累活，全部委托给 SWE-ReX（一个专门做"远程代码执行"的库）。SWEEnv 只是挡在前面的一层同步门面：SWE-ReX 的接口是异步的（async），而 SWE-agent 的主流程是同步的，SWEEnv 就在中间做翻译——每次调用时用 asyncio.run 把异步调用"包"成同步结果。

类比理解SWEEnv 是工地上的对讲机：你（Agent）对着它喊一句"把砖搬过去"，它负责翻译成施工队（SWE-ReX）听得懂的调度指令，再把结果大声报回来。你不需要知道施工队内部怎么排班。

一次 start() 启动会按顺序走完这几步：

步骤做什么关键参数
① 拉起 deployment启动容器（默认镜像 python:3.11）由 SWE-ReX 的部署配置决定
② 开 bash 会话在容器里建一个持久 shell，加载 /root/.bashrc会话启动超时 10 秒
③ 克隆仓库把目标代码库复制进容器—
④ 重置仓库还原到干净状态，保证起点一致超时 120 秒
⑤ 收尾命令执行用户自定义的 post-startup 命令每条超时 500 秒

日常执行命令时，默认的单条命令超时是 25 秒——模型跑一条命令最多等这么久，防止卡死整个循环。

还有个重要方法 hard_reset()：它做的事简单粗暴——把容器整个关掉，再重新 start 一遍。什么时候用？RetryAgent 的多次尝试之间（见 3.8），保证第 N 次尝试面对的是一间全新病房，而不是上次搞得一团糟的现场。

工位可以开在哪？默认是本地 Docker；因为走的是 SWE-ReX 的部署抽象，同一套代码也能把工位开到 Modal 等云端平台上跑；跑测试时还可以用不启动任何容器的 Dummy 模式。

小澄清：SWEEnv 是 Docker 的封装吗？
不完全是。SWEEnv 封装的是 SWE-ReX 的 deployment/runtime 抽象，Docker 只是这个抽象的一种落地方式。所以你在 swe_env.py 里找不到任何 docker SDK 调用——它们都藏在 SWE-ReX 库里。理解这一点，就不会奇怪"为什么环境层代码这么薄"。
源码入口：sweagent/environment/swe_env.py → SWEEnv.start() / reset() / hard_reset() / communicate()

3.5 上下文与 History —— 记忆管理与两本账

类比理解想象一位员工的两份记录：手里的记事本（History）——他每次开口说话前看一眼，决定接下来做什么；公司的归档档案（Trajectory）——事无巨细全部存档，供日后审计。SWE-agent 特意维护两本账，绝不混用。

History（对话历史）是模型每次提问的"全部材料"：一个消息列表，每条消息带角色（role）和类型标记（思考 thought / 动作 action / 观察 observation）。每次问模型前，Agent 都会把这本记事本递过去。

但记事本不能越写越厚不管。于是有了一群"校对员"——HistoryProcessor（历史处理器），它们在记事本递给模型之前做最后一轮加工。默认配置只启用了一位：cache_control。

处理器做什么一句话
cache_control给最近 2 条消息打上"缓存标记"（默认配置）不缩小内容，只是告诉 API"这段可以复用缓存"，省钱
LastNObservations只保留最近 N 条观察，更早的换成一句摘要"旧报告不用细看了，知道结论就行"
ClosedWindow非当前窗口打开过的文件内容替换成一行摘要配合窗口式编辑，防止旧文件内容堆积
RemoveRegex按正则删内容（默认删掉历史里的 diff 块）补丁已经落盘了，聊天记录里不必留全文
Tag / ImageParsing给条目打标签 / 把 base64 图片转成多模态格式特殊场景的辅助工序
常见误解：cache_control 是在"压缩上下文"吗？
不是。它一个字都没删，只是给消息打上一个供 API 侧识别的缓存标记（Anthropic 的 prompt caching 机制）：被标记的前缀内容在计费时按缓存价走，从而省钱、降延迟。真正在"控制体积"的是单条观察的硬性裁剪——任何工具输出超过约 10 万字符就会被剪掉并附一句"内容已截断"的提示。另外注意：代码层面的默认值其实是"不做任何加工"，是随仓库的 config/default.yaml 启用了 cache_control——"代码默认"和"配置默认"是两回事，读源码时要分清。

为什么要两本账？

因为它们服务的目标相反：模型需要"精简的现在"——上下文越干净，决策越准、花钱越少；审计需要"完整的现场"——出了错要能逐步回看它当时看到了什么、想到了什么。如果只用一份数据，要么模型被垃圾淹没，要么审计缺东少西。于是 SWE-agent 让 History 决定"下一步问什么"，让 Trajectory 负责"事后查什么"，各走各的（Trajectory 的细节见 3.7）。

源码入口：sweagent/agent/history_processors.py（全部处理器）· sweagent/types.py（HistoryItem / StepOutput 等数据契约）

3.6 模型层与成本治理 —— 翻译公司、占线客服与总账房

类比理解模型层像一家翻译公司：SWE-agent 只说一种"内部普通话"，而 LiteLLM 这家外包公司会一百多种"方言"（各家模型 API）。你想换 GPT 还是 Claude，只是换一位译员，业务流程一个字不用改。

实现上，SWE-agent 把模型调用完全托付给 LiteLLM：统一了各家 API 的调用格式、错误类型和计费信息。所以切换模型真的只要改一个配置项 --agent.model.name=…，业务代码零改动。

围绕这位"译员"，还有三个配套角色：

占线客服自动重试
API 调用遇到网络抖动、限流这类临时性错误会自动重试：默认最多 20 次，每次随机等待 10–120 秒（越等越久）。但认证失败、配置错误这类"重试也没用"的错误会被立刻识别，绝不空耗。上下文超长也不重试——重试救不了"话太多"，只会交给上层走保底交卷（见 3.2）。
总账房全局统计
一份全局账本（加锁保护）累计着所有实例的总花费和最近一次调用时间。它支撑两种预算：per_instance_cost_limit（单个任务最多花 3 美元，默认值）和 total_cost_limit（所有任务加起来的上限，默认 0 = 不启用）。批量运行时，总预算一破，整批立刻停下。
铁面会计算不清钱就不许跑
有个很"轴"的设计：如果你设置了成本上限，但当前模型无法计算成本（比如 LiteLLM 没有该模型的价格表），系统不会"先跑跑看"，而是直接报错退出，并提示你把限额设为 0 来自担风险。宁可拒绝启动，不做无预算约束的燃烧。

把 3.2 的护栏汇总一下，你就得到完整的"预算安全网"：单命令超时 25 秒 → 单实例总时长 1800 秒 → 单实例 3 美元 → （可选）全局总预算，层层收紧。任何一层被突破，任务都会体面退出并尽量保住已有成果（autosubmit）。

源码入口：sweagent/agent/models.py（LiteLLM 调用 · 重试 · 全局账本 · 成本检查）

3.7 轨迹与 Inspector —— 飞行记录仪与回放剧场

类比理解每架飞机都带黑匣子：不管飞行中发生什么，它只管忠实记录。SWE-agent 的 .traj 文件就是黑匣子——而 Inspector，是机场里那间能逐帧回放黑匣子的事故调查室。

Agent 每走完一步，就会把当前全部记录覆写进轨迹文件（注意：是每步整体重写，不是追加日志行）。一次任务跑完，输出目录里通常有三份产物：

产物内容用途
<id>.traj每一步的思考、动作、观察、环境状态、最终预测，外加本次运行的完整配置审计、复盘、生成演示数据
<id>.pred结构化的"答卷回执"（实例 ID + 提交的 patch）批量运行后合并成 preds.json 供评测
<id>.patch真正的代码补丁（git diff 格式）拿去 review / 应用 / 打分

目录命名本身就是一份"出生证明"：trajectories/<用户名>/<配置文件名>__<模型名>___<任务ID>/——看一眼路径就知道这次运行用了什么配置、什么模型、修的是哪个任务。

Inspector 是一个只读的网页回放器：一条 sweagent inspector --data_path <轨迹目录> --port 8000，浏览器里就能逐个打开轨迹，每一步的模型输出、命令、观察结果都能展开细看，还能并排对照"标准答案补丁"（如果提供了数据集）。它只实现了读取（GET 请求），不会改动任何文件；但也正因如此，把它部署在共享网络里时请注意端口暴露范围。另有终端版查看器 sweagent inspect，不开浏览器也能看。

想更进一步"重演"一次运行？sweagent run-replay 会从轨迹里取出当时发出的每条动作，用一个"只会照本宣科"的 Replay 模型替代真实模型，在环境里把动作重新执行一遍——常用于生成带真实环境输出的演示数据，或者调试工具与环境行为。

小提醒回放 ≠ 可复现
replay 能证明"这些动作在这些环境上会跑出这些结果"，但不能证明"换个模型/换个镜像版本还能得到同样的动作序列"——模型采样、镜像漂移都是不可固定的变量。别把回放当成确定性复现。
源码入口：sweagent/agent/agents.py（轨迹写入）· sweagent/inspector/server.py（网页回放）· sweagent/run/run_replay.py（重放）

3.8 RetryAgent 与 Reviewer —— "多跑几遍，选最好的"

类比理解不放心一次成稿的质量？那就让同一位工程师把任务独立重做 N 遍，再请一位评审把最好的那份挑出来。用算力换命中率——这就是 RetryAgent 的全部思想。

RetryAgent 是一个可选的外环（配置 agent.type: retry 启用，默认主链路不用它）。它自己不写代码，只负责指挥：让一个普通的 DefaultAgent 反复尝试（attempt），每次尝试之间调用 hard_reset() 把容器彻底重启、Agent 对象整个重建——保证第 N 次尝试完全不知道前 N-1 次发生过什么，互不污染。预算也重新算账：剩余的时间和费用额度会按次分摊下去，越到后面每次尝试能花的钱越少。

挑"最好的一份"有两种玩法：

玩法怎么做适用直觉
ScoreRetryLoop（边跑边打分）每次尝试一交卷，评审模型（Reviewer）立刻打分；分数达到门槛、或尝试次数/预算用尽就停，最后取最高分那份"质量够好就提前收工"
ChooserRetryLoop（最后集中选）只管收集所有提交，跑完后让挑选模型（Chooser）对比全部候选，选出索引"先都做完，再货比三家"

工程上还有一套完整的"评审失灵预案"：评审模型全部调用失败？给该次尝试记个惩罚分 −100；挑选器解析失败或给出无效索引？退回取第一份提交；连"取最优"本身都抛异常？用第 0 次尝试兜底。无论评审环节怎么坏，主流程都能带着一份真实提交走出来——这是很值得学习的降级设计。

定位提醒：它是研究工具，不是默认能力
RetryAgent 对应的是论文里的 "test-time scaling"（推理时扩展）研究方向——探究"多花 N 倍算力能换多少成功率"。日常修单个 Issue 用不到它；它的主战场是批量评测实验。另外据源码审计，这套外环目前缺少专门的聚焦测试，属于文档明确标注的薄弱区。
源码入口：sweagent/agent/agents.py → RetryAgent · sweagent/agent/reviewer.py（打分与挑选循环）

3.9 Batch 与 Benchmark —— 开考与批卷

类比理解单个任务是一对一服务，run-batch 是开考场：几百道 SWE-bench 真题排队入场，多个工位（worker）并行开考，交卷的卷子统一收上来批阅。

考题从哪来？任务源（InstanceSource）支持五种：SWE-bench 数据集、本地文件、HuggingFace 数据集、专家集、SWE-Smith 合成集。考题进来后先按 ID 排序，再用固定随机种子（42）打乱——顺序随机但每次运行都一样，保证实验可对照。

考场的三条运行规则：

规则一每个考生一套全新桌椅
每个实例都会新建一个 Agent 和一个环境（深拷贝配置），绝不共享。这是批处理结果可信的前提——上一题的残留不会影响下一题。并行度由 num_workers 控制，默认只有 1（想提速自己调大）。
规则二做过的题不重做（断点续跑）
开考前会检查：这道题的轨迹文件存在、内容完好、且有明确的退出状态？那就跳过。轨迹损坏或状态不明？删掉重跑。这意味着批量实验中断后，直接重跑同一条命令就能接着来，不浪费已完成的算力。
规则三全局红线一碰就收摊
单题失败不影响其他题继续考；但碰到全局预算耗尽或配置级错误这类红线，整批立即停止——继续跑只会继续烧钱或继续出错。

收卷后，每道题的 .pred 回执被合并成一份 preds.json，拿去给官方评测脚本批卷；.patch 则由各题的保存 Hook 分别落盘。

三个最容易混淆的词

状态含义谁判定
completed任务跑完了（不管结局是交卷、认输还是超时）SWE-agent 自己
submitted产出了一份 patch（哪怕是 autosubmit 保底的半成品）SWE-agent 自己
resolvedpatch 真正修好了 Issue（测试用例通过）基准的官方评测脚本

三者是层层递进、判定者不同的概念。看任何"SWE-agent 解决了 X%"的数字，先问清楚它说的是哪一个。论文报告的标志性成绩是 SWE-bench 全集 12.47%（286/2294）、Lite 子集 18.0%——注意这是论文时期的历史实验数字，且今天的模型早已大幅刷新了这个榜单。

顺带认识：Hooks（观察点）
批量运行里那些"保存 patch""统计耗时"的动作，是通过 Hook 机制挂在流程各处的：Run 层（任务开始/结束/跳过/完成）、Agent 层（每一步的问模型前后、动作执行前后）、环境层（启动/关闭）都有对应事件，注册的 Hook 会被同步顺序调用。注意两点：Hook 抛异常会直接影响主流程（它不是"旁路通知"）；批处理多线程下，同一批 Hook 会被多个工位同时调用，涉及每题私有状态的实现必须自己做线程隔离（内置的 patch 保存 Hook 就是这么做的）。
源码入口：sweagent/run/run_batch.py（考场调度）· sweagent/run/batch_instances.py（考题装载）· sweagent/run/hooks/apply_patch.py（patch 保存）

设计哲学与常见误解

四条铁律

铁律一界面设计是一等公民
工具的描述文档不是附录，而是提示词的一部分；命令的形态、输出的裁剪、交卷的协议，全部是为模型的认知特点量身定做的。这就是 ACI：与其等一个更强的模型，不如先把"模型与计算机对话的方式"设计好。
铁律二模型只判断，工具才执行
模型永远不直接接触文件系统或 shell——它输出的只是"意图"，要经过解析、校验、黑名单三道关口，才会在隔离容器里变成现实。意图与现实之间，永远隔着一层系统。
铁律三结束靠协议，不靠自然语言
"我做完了"这句话在 SWE-agent 里没有任何效力。任务是否完成，取决于 sentinel 暗号是否出现、patch 文件能否读到。把不可靠的自然语言承诺，换成可验证的机械协议。
铁律四智能来自模型，可靠来自系统
格式写错有重询、命令超时有拦截、钱烧完了有保底交卷、环境崩了有轨迹留证——模型负责"想对"，系统负责"想错了也不至于灾难"。这套兜底网络，才是研究级运行时和玩具 demo 的分水岭。

常见误解三连

常见误解一：SWE-agent 有 max_steps（最大步数）吧？
没有。翻遍源码也找不到步数上限。它的预算观是按资源而非按次数：总执行时长（默认 1800 秒）+ 单实例成本（默认 3 美元）+ 单命令超时（25 秒）。理由前面说过：一步的成本差异太大，数步数不如数钱和数时间。
常见误解二：工具是 Python 插件，加载进 Agent 进程里执行？
不是。Bundle 是上传到容器里的部署单元（目录 = 声明 + 脚本 + 安装脚本），模型通过在容器里跑 shell 命令来"调用"它。Agent 进程里只有"命令的文本"在流动，真正执行发生在容器的另一个世界里。这个边界正是安全与解耦的来源。
常见误解三：这个项目还在活跃开发，可以直接用于生产？
官方 README 写得很清楚：团队当前的主力开发已转向 mini-swe-agent（更精简的实现），并推荐新项目使用它。SWE-agent 1.1 的定位是研究基准与完整参照实现：学习架构、复现论文、对比实验，它是绝佳材料；上生产前请仔细评估，并自建安全边界。
常见误解四：配置文件都能混用，0.7 时代的配置拿来就用？
不能。default.yaml（当前默认，function calling + 编辑器工具）、bash_only.yaml（极简裸 shell）、sweagent_0_7/07.yaml（复刻论文时代，窗口编辑器 + 演示教学）是三套不同的实验设定，工具、解析器、提示词全不一样，跑出的结果不可互相比较。做实验时先确认自己用的是哪套。

# 3. 跑官方玩具任务（约一杯咖啡的时间与几美分）

5.3 常见问题

Q：我想给 Agent 加一个新工具，要改代码吗？
通常不用。新建一个 Bundle 目录：写好 bin/ 里的脚本，再写一份 config.yaml 声明命令名、参数和文档字符串，最后在运行配置里把它加进 agent.tools.bundles 即可。工具的 docstring 会自动成为模型看到的说明书。
Q：怎么换模型？只能用 OpenAI 吗？
凡是 LiteLLM 支持的模型都能用（OpenAI、Anthropic、本地模型等），只需改 --agent.model.name。注意：成本限额依赖 LiteLLM 的价格表，冷门模型可能因"算不出钱"而拒绝启动——见 3.6 的铁面会计。
Q：命令是 run 还是 run-single？
单任务命令是 sweagent run（别名 r），不存在 run-single 子命令。批量是 run-batch。完整子命令家族还包括 replay、inspect、inspector、compare-runs、quick-stats、shell 等，跑 sweagent --help 一眼看全。
Q：任务失败了，patch 一定没有吗？
不一定。很多失败路径会走 autosubmit：把当时工作区的改动用 git diff 打包成 patch 再退出（exit_status 会记录原因，如 submitted (exit_cost)）。所以看到非 submitted 状态也别急着删目录，先看看有没有保住半成品。
Q：我想复现论文里的结果，该用哪个配置？
用 config/sweagent_0_7/07.yaml——它是论文时代配置的复刻（窗口式编辑器 + thought/action 文本解析 + 演示教学）。默认配置 default.yaml 是后续演进出的新默认（function calling + str_replace_editor），两者结果不可直接对比。
Q：怎么调试"环境/工具行为"而不烧 API 的钱？
用 sweagent run-replay：从已有轨迹里取出动作序列，用"照本宣科"的 Replay 模型重放，模型调用完全免费。另外 sweagent shell 可以直接开一个环境 shell 手动敲命令，验证工具脚本行为。

读完如果只记三句话
  1. 界面设计和模型能力同等重要——ACI 告诉我们：给模型一套称手的接口，比等一个更聪明的模型更现实。这是 SWE-agent 留给整个领域最重要的思想。
  2. 主链只有一个循环，可靠性全靠工程兜底——预算护栏、格式重询、保底交卷、协议终止：模型负责聪明，系统负责不出事。
  3. 全程留痕、一切可回放——两本账（History 与 Trajectory）+ 黑匣子式轨迹文件，让每次运行都能被审计、被复盘、被学习。这是研究型系统的尊严。
