第 1 章 · OpenClaw 是什么？

一句话定义

OpenClaw 是一个运行在你自己设备上的 AI 助手网关。 它让你通过已有的聊天工具（Telegram、WhatsApp、Discord、Slack、微信……） 与 AI 对话，而这个 AI 不只是"聊天"——它能帮你执行命令、搜索网页、操作文件、 定时跑任务，像一个真正的私人助理。

想象你雇了一位全能管家。你不需要去他的办公室——你通过微信、电话、 甚至门铃都能联系他。他背后有一个调度中心（Gateway）， 一个会思考的大脑（Agent），和一整套工具箱（Plugins）。 OpenClaw 就是这位管家的"操作系统"。

它解决什么问题？

直接用 ChatGPT / Claude 的局限
  • 只能在官方 App/网页里用，无法接入你日常的消息工具
  • AI 只能"说"，不能"做"——无法在你的电脑上执行操作
  • 数据在云端，隐私不可控
  • 无法同时使用多个 AI 模型，也无法在模型之间自动切换
OpenClaw 的答案
  • 多渠道统一接入：20+ 消息渠道，一个 AI 助手全覆盖
  • 真正的执行力：AI 可以运行命令、浏览网页、读写文件
  • 自托管：所有数据在你自己的设备上
  • 多模型自由：40+ AI 提供商，自动故障切换
  • 插件化：100+ 插件，能力可无限扩展

第 2 章 · 一条消息的旅程

假设你在 Telegram 上给你的 OpenClaw 助手发了一条消息：

"帮我查一下明天北京的天气"

这条消息会经历 5 个阶段。我们逐步拆解。

Step 1 · 消息进门 —— Channel 插件

1

Telegram 插件收到消息

OpenClaw 启动时，Gateway 会启动所有已配置的渠道插件。Telegram 插件 通过 Telegram Bot API 的长轮询（getUpdates）持续监听新消息。 你的消息到达后，插件做的第一件事不是"处理"，而是存起来。

它把原始消息写入一个 SQLite 持久化队列（叫做 Ingress Spool）。 为什么？因为如果此刻系统崩溃了，消息不会丢。重启后，队列里没处理完的 消息会被重新"泵送"出来继续处理。这就是所谓的 "先持久化，再确认"（durable-before-ack）原则。

extensions/telegram/src/bot-core.ts → monitor.ts → telegram-ingress-spool.ts
这就像餐厅的取号系统。你到了餐厅，不是直接冲进厨房喊"给我来份牛排"， 而是先在前台取一个号（写入队列）。即使前台电脑重启了，你的号还在。 等叫到你的号（drain 泵送），服务员才会把你的需求送进厨房。

消息从队列中被"认领"（claim）后，Telegram 插件会做一些预处理： 解析文本、聚合媒体（比如你同时发了 3 张图）、检查你有没有权限跟这个 bot 说话。 然后，它把消息交给核心的入站分发逻辑。

src/channels/message/ingress-drain.ts → inbound-reply-dispatch.ts

Step 2 · 前台接待 —— Gateway 路由与鉴权

2

Gateway 决定"这条消息该给谁处理"

Gateway 是整个系统的中枢——一个常驻进程，监听一个端口（默认 18789）， 同时提供 WebSocket、HTTP API、健康检查、Control UI 等多种服务。

对于你的消息，Gateway 要做两件事：

  1. 鉴权：确认这条消息来自合法的渠道和账户
  2. 路由：决定由哪个 Agent 来处理

路由规则是一个 9 层优先级匹配——从最精确到最宽泛：

优先级匹配维度例子
1（最高）精确 peer指定某个用户 ID → 某个 Agent
2父级 peer线程继承父消息的路由
3peer 通配符某渠道的所有用户 → 某 Agent
4Guild + 角色Discord 服务器 + 特定角色
5Guild整个 Discord 服务器
6TeamSlack 工作区
7Account特定 bot 账户
8Channel渠道级兜底
9（最低）Default默认 Agent（通常是 "main"）
src/routing/resolve-route.ts → resolveAgentRoute()

在你的场景中，如果没有特殊配置，消息会命中第 9 层——默认 Agent。 路由结果还包含一个 Session Key（会话键）， 格式类似 agent:main:telegram:peer:12345， 用来标识"这是 main Agent 和 Telegram 用户 12345 之间的对话"。

小澄清：被路由到的 "Agent" 从哪来？

它不是一份内置的角色清单。OpenClaw 代码里并没有"张三 Agent、李四 Agent"这种现成可选的角色—— Agent 是你自己配置出来的"人格实例"，每个实例有独立的工作区、模型、工具权限和会话记忆。

  • 默认只有 1 个：即使零配置，也始终存在一个 id 为 main 的默认 Agent，所有消息都交给它
  • 其余由你创建：openclaw agents add work --model anthropic/claude-sonnet-4，或在 openclaw.json 的 agents.entries 里配置
  • bindings 决定归属：上表的路由匹配到的 binding 里写着 agentId，那就是选中的 Agent；没匹配到就用默认
src/routing/session-key.ts（DEFAULT_AGENT_ID = "main"）· src/agents/agent-scope-config.ts · docs/concepts/multi-agent.md

Step 3 · 大脑思考 —— Agent Runtime

3

Agent 的"想 → 做 → 看"循环

消息到达 Agent Runtime 后，进入一个双层循环：

让我们拆解这个循环里发生了什么：

① 组装上下文（Context Assembly）

Agent 不是"裸"调用 LLM 的。它会精心准备一份"工作材料"：

  • 系统提示（System Prompt）：告诉 AI "你是谁、你能做什么、你的规则是什么"
  • 对话历史：你和它之前说过的话（太长时会自动压缩）
  • 工具清单：当前可用的工具列表和参数说明
  • Memory：如果配置了记忆系统，还会注入相关记忆
src/agents/embedded-agent-runner/run/attempt-system-prompt.ts + attempt-prompt-assembly.ts + attempt-tool-catalog.ts

② 调用 LLM（Model Stream）

组装好的上下文被发送给 AI 模型。OpenClaw 通过一个统一的 StreamFunction 接口与所有模型通信——无论底层是 OpenAI、 Anthropic 还是 Google，上层代码看到的都是同一种流式事件格式。

对于你的"查天气"请求，LLM 大概率会回复："我需要调用搜索工具"， 并附带一个 tool_call（工具调用请求）。

packages/agent-core/src/agent-loop.ts → streamAssistantResponse()

③ 执行工具（Tool Execution）

Agent 收到 LLM 的工具调用请求后，会：

  1. 在工具注册表中查找对应工具
  2. 校验参数是否合法
  3. 检查 Tool Policy（这个工具是否被允许使用）
  4. 如果需要人类审批（Approval），暂停等待
  5. 执行工具，收集结果

在你的场景中，Agent 可能调用了一个搜索工具，返回了明天北京的天气预报。

packages/agent-core/src/agent-loop.ts → executeToolCalls()

④ 观察结果，决定继续还是结束

工具结果被塞回上下文，LLM 再看一遍。如果信息够了，LLM 会生成最终文本回复； 如果不够（比如搜索失败了），它可能再调用另一个工具。 这个循环会一直转，直到 LLM 认为任务完成。

外层恢复循环做了什么？

内层循环外面还套了一层"保险"。所有"决定怎么办"的智能基本都在这里：

  • 模型 Failover：当前模型故障（API 限流、服务过载）时，自动切到备用模型重试
  • 用户实时换模型：运行中用户切换模型时，重启 attempt（最多 5 次）
  • 抢占式压缩：在 attempt 之前/之间主动触发上下文压缩（Compaction）
  • 决策模型切换：内层 prepareNextTurn 切到哪个模型，由这层的回调决定

一句话：内层是忠实的"执行引擎"（跑 turn、应用结果），外层是"决策者"（切哪个模型、要不要压缩、失败怎么重试）。你作为用户，完全感知不到这些。

src/agents/command/run-embedded-attempt.ts → src/agents/model-fallback.ts · src/agents/embedded-agent-runner/run/preemptive-compaction.ts

Step 4 · 动手干活 —— 工具与插件

4

工具从哪里来？

OpenClaw 的工具有三个来源：

  • 核心工具：内置的 bash 命令执行、文件读写等
  • 插件工具：由插件注册的（如浏览器控制、Tavily 搜索）
  • MCP 工具：通过 Model Context Protocol 连接的外部服务

每个工具都有一个 execute() 方法。Agent 调用工具时， 实际上就是调用这个方法，传入参数，等待结果。 工具可以并行执行（互不依赖时），也可以串行执行（有依赖时）。

src/agents/agent-tools.ts（核心工具注册）· extensions/（插件工具）· src/agents/mcp-stdio.ts（MCP）

Step 5 · 回复送达 —— 状态持久化与投递

5

回复回到你的手机

Agent 生成最终回复后，系统做三件事：

  1. 持久化：把这次对话记录、工具调用、token 用量写入 SQLite
  2. 整形（Reply Shaping）：把回复格式化为目标渠道支持的格式 （Telegram 支持 Markdown，WhatsApp 不支持，等等）
  3. 投递：通过 Telegram 插件的出站接口，把回复发回给你

投递时还有一个去重机制：如果 Agent 在执行过程中已经通过 "message 工具"主动发过消息了，最终投递会跳过重复内容，避免你收到两遍。

src/agents/command/delivery.ts → deliverAgentCommandResult()
完整旅程回顾
你的消息 "帮我查一下明天北京的天气"
  │
  ├─① Telegram 插件收到 → 写入 SQLite 队列（防丢失）
  ├─② Gateway 路由 → 9 层匹配 → 交给 "main" Agent
  ├─③ Agent 组装上下文 → 调用 LLM → LLM 说"我要搜索"
  ├─④ 执行搜索工具 → 拿到天气数据 → 塞回上下文 → LLM 生成回复
  └─⑤ 持久化记录 → 格式化 → 通过 Telegram 发回给你

你收到："明天北京晴，最高温 32°C，建议做好防晒。"

第 3 章 · 五大核心模块详解

第 2 章走完了消息旅程。这一章我们把每个"方块"打开，看看里面的设计思想。 不需要全部读完——挑你感兴趣的部分即可。

3.1 Gateway：为什么需要一个"总机"？

Gateway 是 OpenClaw 的总机——一个常驻进程，所有渠道连接、客户端控制、设备能力都汇聚到它。 而且一台机器只能有一个：像 WhatsApp 这类渠道一次只允许一个会话，多开会被服务端踢下线。 所以它必须"一直在线、独一无二"。

为什么非得有一个常驻总机

这不是图方便，而是硬约束。三件事决定了 Gateway 必须是一个长期存活、独占的进程：

  • 有状态会话独占：WhatsApp(Baileys) 等渠道维持的是长连接会话，一台主机只能开一个，第二个进程去连会把前一个顶掉；
  • 长连接需要人持有：各 provider / 渠道的连接要有人持续维护、掉线重连；
  • 它是事件总线：Gateway 不只做请求 / 响应，还主动推送事件（agent / chat / presence / health / heartbeat / cron），客户端订阅后即可实时感知。

这三点合起来就是答案：因为要独占会话、持有长连接、广播事件，所以必须有一个常驻且唯一的总机。 它走类型化 WebSocket 协议，入站帧经 JSON Schema 校验，副作用方法（send / agent）还要求幂等键以安全重试。

一个端口，三种"客人"

Gateway 在同一个 WebSocket 服务器（默认 127.0.0.1:18789）上，同时接待三类连接者：

客人是谁来做什么
渠道 ChannelsWhatsApp / Telegram / Slack / Discord 等消息进出：把用户消息送进来，把回复发出去
控制端 Clientsmac app / CLI / Web UI / 自动化操作员发指令、看状态、订阅事件
节点 NodesmacOS / iOS / Android / headless 设备以 role: node 接入，把 camera / screen / canvas / location 变成 agent 可调用的能力

最有意思的是 Nodes：你的手机、电脑不再是被动终端，而是把摄像头、屏幕录制、画布、定位贡献给 agent 当"手脚"。

单端口具体跑了哪些服务？

"一个端口"不是只干一件事，而是多路复用——同一个端口同时提供：

服务用途
WebSocket API渠道连接、Agent 通信、事件推送
HTTP APIWebhook 接收、Canvas 托管
健康检查/healthz（存活）/ /readyz（就绪）
Control UI内置管理界面
Canvas HostAgent 生成的 HTML 应用托管
节点命令远程执行系统命令
src/gateway/server.impl.ts（服务组装）· src/gateway/protocol/schema.ts（协议定义）

怎么保持长期可用

既然必须常驻，Gateway 在韧性上下了功夫：由 launchd / systemd 守护、崩溃自动拉起； 支持 SIGUSR1 进程内重启；safe restart 会先排空在途工作再重启，避免打断正在跑的任务；配置变更热重载，无需重启。

渠道掉线了怎么办？指数退避重连

渠道断连后不会疯狂重试（那会打爆服务端），而是指数退避：等待时间逐次翻倍，直到上限后趋于稳定。 同时有每小时重启次数上限兜底，防止某个坏渠道把整个 Gateway 拖垮。

src/gateway/channel-health-monitor.ts（健康监控 + 退避 + 每小时上限）
谁能连进来？设备配对与信任

所有 WS 连接者（operators + nodes）在 connect 时都带设备身份。新设备需要配对审批， 通过后 Gateway 颁发 device token 供后续连接；还要对 connect.challenge 随机数签名。 本机 loopback 可自动批准以保持顺滑，非本地连接始终需要显式审批。

3.2 Agent Runtime：AI 的"工作循环"

把 Agent Runtime 想象成一个公司。
外层恢复循环是项目经理——他不亲自干活，但负责"如果张三请假了， 让李四顶上"（模型 Failover）。
内层 Agent Loop是员工——他拿到任务后，"想一步 → 做一步 → 看结果 → 再想下一步"，直到任务完成。

内层循环的关键设计

  • 流式响应：LLM 的回复是一个字一个字"流"回来的， 用户可以实时看到 AI 在"打字"
  • 工具并行：如果 LLM 一次请求了多个工具调用， 互不依赖的会并行执行，节省时间
  • 终止判断：每个工具可以标记"到此为止"（terminate）， 所有工具都说"完了"时，循环结束
  • turn 边界 hook：每轮结束调用 prepareNextTurn， 内层只"应用"上层返回的新模型/思考级别，自己不做决策
"钩子（hook）"是什么？怎么触发的？

钩子是内层循环在固定位置预留的一个"挂载点"：内层只定义 "何时调"（每轮结束时），"调了做什么"（切到哪个模型） 则由上层注入的函数决定——这就是"控制反转"。代码里 config.prepareNextTurn?.() 的 ?. 表示"上层提供了就调，没提供就跳过"。

触发时机：不是事件驱动，也不是用户主动触发，而是内层循环 每轮结束自动执行的固定步骤：一轮跑完 → 发出 turn_end → 自动调 prepareNextTurn → 若上层返回新模型就应用 → 再判断要不要进下一轮。 全程不重启 run、不重建上下文，只在 turn 边界无缝换掉下一轮的模型，所以叫"温和切换"。

packages/agent-core/src/agent-loop.ts:397（触发点）· src/agents/sessions/sdk.ts:153（上层注入的 hook 实现）
常见误解澄清：上下文压缩（Compaction）不在内层循环

内层循环（agent-core）完全不做压缩，agent-loop.ts 里没有任何压缩逻辑。 压缩由上层触发：外层 embedded runner 做"抢占式压缩"，SDK 会话层在 run 结束后做"基线自动压缩"； 真正执行（调模型生成摘要）用的是 agent-core 提供的纯函数，但调用方是上层。 内层循环只是被包裹着跑，对压缩毫无感知。

packages/agent-core/src/harness/compaction/compaction.ts（纯函数）· src/agents/embedded-agent-runner/run/preemptive-compaction.ts（外层触发）

上下文工程（Context Engineering）

"给 LLM 看什么"是一门学问。OpenClaw 的上下文组装会注入：

  • 运行时信息（当前时间、操作系统、工作目录）
  • 可用工具和技能（Skills）列表
  • Memory 系统中的相关记忆
  • Agent 的身份和规则（来自配置文件）
  • 沙箱状态（哪些操作被限制）

这些内容按确定性顺序排列——这一点很重要， 因为 LLM 提供商的提示缓存（Prompt Cache）依赖稳定的字节序列。 顺序一变，缓存就失效，成本就上去了。

packages/agent-core/src/agent-loop.ts（内层循环）· src/agents/embedded-agent-runner/（外层编排）

谁来跑这个循环？—— Harness 与执行后端

上面说的"内层循环 / 外层循环"讲的是循环怎么跑。 还有一个问题：这个循环由谁来跑？ 答案就是一个叫 Harness 的东西。

把一次 AI 回复想成"炒一盘菜"。OpenClaw 核心负责备料—— 选好哪个模型（model）、备好认证、整理好对话历史、列好可用工具、定好沙箱和审批策略。 料备齐后，交给 Harness（执行器）下锅翻炒： 驱动模型输出、处理工具调用、把这盘菜（一个完成的 turn）端回来。 所以 Harness ≠ 模型——它是"跑循环的那段代码"，不是"被调用的那个大脑"。

要理解 Harness，先记住 OpenClaw 把"AI 怎么回复"拆成了四个互不干扰的层：

层决定什么类比
Provider怎么认证、怎么发现/命名模型食材供应商

关键点：选哪个模型（Model）和用哪个执行器（Harness）是两件独立的事。 Provider / Model 两层详见 3.4 模型与 Provider； 本节只聚焦第三层——Harness。

OpenClaw 没有自己的模型，为什么还有自己的 Harness？

正因为没有自己的模型，才需要一个 Harness。 Harness 是"跑循环的执行器"，不是模型本身。OpenClaw 的内置 Harness （id 就叫 openclaw）是一段通用循环代码： 上一层把模型解析好（哪家 provider、哪个 model、认证、思考级别都备齐）， 它拿过来就能驱动任意 provider 的任意模型——它不挑模型，挑模型是上一层的事。

这段通用循环干的全是"执行/调度"：调 provider 解析好的 API、驱动流式输出、 跑 OpenClaw 原生工具循环、拥有对话历史（transcript）、跑上下文压缩和插件 hook。 所以"没有自己的模型"和"有自己的 Harness"完全不矛盾—— Harness 是让别家模型跑起来的那台引擎。

src/agents/harness/builtin-openclaw.ts（内置 openclaw harness，runAttempt 即嵌入式 runner）

双层循环的"归属"：外层永远 OpenClaw，内层看 Harness

回到开头的公司类比。两层循环的所有权是这样的：

  • 外层（项目经理）永远归 OpenClaw：重试、模型 Failover、 上下文压缩、最终答案补齐——不管用哪个 Harness，这层都是 OpenClaw 自己在编排。
  • 内层（员工）归 Harness 所有：那个"模型↔工具"的实际迭代由谁驱动， 取决于选了哪个 Harness。

OpenClaw 目前有三个嵌入式 Harness（都实现同一个接口、注册进同一张表）：

Harness来源内层 loop 在哪跑
openclaw 内置（核心） OpenClaw 进程内，自己驱动 provider API + 原生工具循环
codex 插件 委托给远端 Codex app-server（走网络），OpenClaw 只做镜像/桥接
copilot 插件 委托给本地 GitHub Copilot CLI/SDK 进程（不走网络）

注意"嵌入式（embedded）"只表示它作为一个 Harness 注册进 OpenClaw、参与统一选择， 并不代表循环一定在本地跑——codex 实际上是把内层 loop 委托给了远端。

Harness 是可配的，但粒度是 provider/model，不是全局开关

选哪个 Harness 按 4 级优先级解析：

  1. Model 级：agents.defaults.models["provider/model"].agentRuntime（支持 provider 通配）
  2. Provider 级：models.providers.<provider>.agentRuntime
  3. auto 模式：插件 Harness 按自己声明的 providerIds 认领 （比如 openai/* 在 auto 下会被 codex 认领）
  4. 兜底：没人认领就回 openclaw

一条铁律：显式指定 id 是 fail-closed 的——你明确配了 codex， 它要么走 codex、要么报错，绝不会悄悄回退到 openclaw。 另外 copilot 只能显式选，auto 永远不会自动挑它。

常见误解澄清：claude-cli 不是 Harness，是"CLI 后端"

还有个 claude-cli，容易被误以为是第四个 Harness——它不是。 它不进 Harness 注册表、不参与统一选择，走的是一条独立的"CLI 后端"路径。 文档明确写着：claude-cli is not an embedded harness id。

原理：OpenClaw 直接起一个本地 claude CLI 子进程， 把整个 turn 甩给它。这个子进程自己跑完整个 agent loop（模型调用 + 工具执行）， OpenClaw 只捕获它的输出、把事件镜像进会话记录。 而且它是在外层编排循环启动之前就短路返回的—— 所以 claude-cli 是"one-shot 单循环"：内层 loop 归 CLI，外层那套重试/压缩编排根本不包裹它， OpenClaw 只剩一层"镜像 + 投递"的薄壳。

深入：为什么 codex / copilot 能进 Harness 统一选择，claude-cli 不行？

既然 codex / copilot 也把内层 loop 委托给了外部运行时，凭什么它俩能作为 Harness 参与统一选择，claude-cli 却只能走独立路径？关键不在"loop 在不在本地跑"， 而在有没有实现 AgentHarness 契约、能不能被外层 loop 接回去。

AgentHarness 的核心是 runAttempt(prepared) → result 这个签名。 它的形状预设了几件事：

  • Harness 跑在 OpenClaw 外层 loop 内部，会被反复调用 （重试、压缩恢复、最终答案补齐都会再调一次 runAttempt）
  • OpenClaw 拥有 transcript、驱动动态工具、跑插件 hook（before / after_tool_call）
  • Harness 消费 OpenClaw 准备好的 prepared attempt，返回结构化结果供外层恢复机制读取

codex / copilot 满足这个契约：它俩不仅实现了 runAttempt， 还主动把外部运行时接回 OpenClaw——copilot 有专门的 hooks-bridge、tool-bridge、dual-write-transcripts 桥接层， 把 hook、工具、对话历史都同步回 OpenClaw。所以即便内层 loop 委托出去了， OpenClaw 的外层编排（恢复 / 补齐 / hook）依然能包裹它们。

claude-cli 把这个形状反过来了：它是一个外部黑盒子进程， 自己拥有整个 turn（自己的模型 loop、自己的工具执行、自己的内部 transcript）。 OpenClaw 没法增量驱动它，更没法"调多次 runAttempt 做恢复"； canonical 线程状态归 CLI 自己，OpenClaw 只能镜像不能改写； 动态工具、hook、上下文压缩也都不在 CLI 里跑。形状对不上 runAttempt 契约， 所以它只能在外层 loop 启动之前短路，作为独立的 CLI 后端路径。

一句话：能不能进 Harness 统一选择，看的是"能不能被外层 loop 反复调用、 并把 hook / transcript / 工具接回 OpenClaw"。codex / copilot 接回了， claude-cli 是个 one-shot 黑盒没接回——这就是分野。

3.3 插件系统：如何做到"核心不变，能力无限"

插件系统就像 USB 接口。你的电脑（核心）不需要知道插上的是键盘、 鼠标还是U盘——只要设备遵循 USB 协议（Plugin SDK）， 插上就能用。OpenClaw 的核心代码里没有任何一个具体插件的名字。

插件的三种角色

角色做什么例子
Provider 提供 AI 模型能力 OpenAI、Anthropic、Google、Ollama（40+）
Channel 提供消息渠道 Telegram、Discord、Slack、WhatsApp（20+）
Tool 提供工具能力 浏览器控制、搜索、代码执行、MCP 服务

插件的一生

  1. 发现（Discovery）：系统扫描 5 个来源（内置、工作区、全局、npm 包、bundle）， 找到所有插件候选
  2. 清单验证（Manifest）：读取 openclaw.plugin.json， 检查插件的 ID、版本、依赖——此时不执行任何插件代码
  3. 加载（Loading）：动态 import() 插件模块
  4. 注册（Registration）：插件调用 api.registerProvider()、 api.registerChannel() 等方法，向核心注册自己的能力

插件与核心的边界

这是 OpenClaw 架构中最重要的设计决策之一：

铁律：插件只能通过 Plugin SDK 与核心通信
  • 插件不能直接 import 核心的 src/ 内部模块
  • 插件不能访问其他插件的内部实现
  • 核心不能引用具体插件的内部代码
  • 所有通信通过 openclaw/plugin-sdk/* 子路径导出

3.4 模型与 Provider：AI 大脑的"供应商管理"

想象你开了一家翻译公司。客户（Agent）不关心你用的是张三还是李四来翻译—— 他只要提交原文，拿到译文。你的公司（ApiRegistry）管理着所有翻译员（Provider）， 如果张三生病了（API 限流），自动把活儿派给李四（Failover）。

统一抽象：一个 StreamFunction 统治一切

所有 AI 提供商的差异（OpenAI 用 Completions API、Anthropic 用 Messages API、 Google 用 Generative AI API）被封装在一个统一的接口后面： 

// 伪代码：所有 Provider 都实现这个签名
type StreamFunction = (
  model: Model,        // 归一化的模型描述
  context: Context,    // 系统提示 + 消息 + 工具
  options: Options     // 温度、最大 token 等
) => EventStream       // 统一的流式事件

上层的 Agent Loop 完全不知道底层是哪家模型。它只看到统一的 text_delta（文字片段）、toolcall_delta（工具调用片段）、 done（完成）事件。

Failover：一个挂了，自动换下一个

你可以在配置中指定一个模型候选链： 

// openclaw.json（示意）
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "anthropic/claude-sonnet-4",
        "fallbacks": ["openai/gpt-4.1", "google/gemini-2.5-pro"]
      }
    }
  }
}

当主模型返回限流（429）、过载（529）或认证错误时，Failover 机制会：

  1. 把错误分类（是暂时的还是永久的？）
  2. 如果是暂时的，等一个冷却期后自动尝试下一个候选
  3. 记录每次尝试的详情，方便排查
  4. 所有候选都失败时，抛出一个汇总错误

3.5 状态与存储：数据存在哪里？

OpenClaw 的存储策略是一条分工原则： 机器管理的运行时状态（队列、缓存、索引、插件 KV）一律放 SQLite； 人类要读、要改、要审计的权威内容（记忆 Markdown、配置、凭据）留在文件。 两者各司其职，不是"谁取代谁"。

状态放哪：SQLite 与文件分工

放 SQLite（机器状态）放文件（人类权威资产）
渠道入站队列、全局运行时状态、插件 KV、对话记录、缓存、各类索引 记忆 MEMORY.md / memory/*.md、引导文件（AGENTS.md 等）、配置 openclaw.json、凭据、日志

SQLite 集中在两个库：共享库 state/openclaw.sqlite（全局状态、插件 KV、入站队列） 与 Agent 私有库 agents/<id>/agent/openclaw-agent.sqlite（对话、缓存、私有状态）。

为什么机器状态用 SQLite，而不是 JSON 文件？

SQLite 提供事务保证（写入要么全成功要么全失败）、并发安全和查询能力； JSON 文件在崩溃时可能只写一半，导致数据损坏。所以凡是被程序高频读写、不需要人直接看的状态，都进 SQLite。

反过来，人类要读、要改、要审计、要版本化的内容刻意保留为文件：记忆 Markdown 是权威知识， 引导文件每个 turn 都被读取并驱动行为，配置和凭据需要可见可改。判断标准就一句： 机器派生状态 → SQLite；人类权威内容 → 文件。

第 4 章 · 安全与信任

一个能执行命令、操作文件的 AI 助手，安全是头等大事。 OpenClaw 用分层防御来应对。

洋葱模型：层层设防

每一层都独立生效，任何一层被绕过，下一层仍然有效。

Tool Policy：AI 能用哪些工具？

Tool Policy 是一个多层 allow/deny 决策链。 一个工具能不能被调用，要经过多道关卡：

  1. 全局配置的策略
  2. Agent 级别的策略
  3. Provider 级别的策略（某些模型提供商限制特定工具）
  4. 群组/发送者级别的策略（不同用户组权限不同）
  5. 沙箱策略（沙箱内进一步限制）
  6. 子代理策略（子 Agent 比父 Agent 权限更小）

规则很简单：所有激活的策略必须同时允许，工具才能执行。 任何一层说"不行"，就不行。

src/agents/tool-policy.ts · src/agents/tool-policy-match.ts · src/agents/agent-tools.policy.ts

Approval：危险操作需要人类点头

即使 Tool Policy 允许了某些工具，对于高风险操作（比如删除文件、执行系统命令）， 系统会暂停执行，通过消息渠道向用户发送审批请求：

"AI 想要执行 rm -rf /tmp/old-data，是否允许？ [允许] [拒绝]"

用户回复"允许"后，工具才会继续执行。这确保了人类始终对危险操作有最终控制权。

沙箱 vs 审批：到底怎么判定？

很多人以为"某个工具要不要沙箱、要不要审批"是按工具名查表决定的——其实不是。 沙箱和审批是两套独立机制，判定的维度完全不同：

沙箱 Sandbox审批 Approval
管什么工具在哪里跑（宿主 vs 隔离容器）工具让不让跑（执行前要不要人确认）
判定维度按会话 + mode按策略 + 逐条命令
默认状态关（mode=off）全放行（security=full + ask=off）
判定函数shouldSandboxSessionrequiresExecApproval

注意：两者默认都是"不限制"，需要用户主动配置才生效。 而且判定主要不是看"哪个工具"，而是看"哪个会话 / 什么命令 / 什么策略"。

沙箱怎么判定——只看 sandbox.mode 和会话身份：

  • off（默认）→ 永不沙箱
  • all → 所有会话都沙箱
  • non-main → 只有"非 main 会话"沙箱，main 会话直接在宿主跑

一旦某个会话被判为沙箱化，里面的 exec/process 会改在 Docker 容器内执行 （只读根文件系统、无网络、非 root 用户），文件类工具则经过受限的文件系统桥访问。

审批怎么判定——主战场是 exec（shell 命令）工具，看两个正交的策略维度：

  • security：deny（禁止）/ allowlist（仅白名单）/ full（全放行）
  • ask：off（不问）/ on-miss（没命中白名单才问）/ always（总是问）

判定逻辑（requiresExecApproval）可以浓缩成三句话：

  1. ask=always → 每次都要审批
  2. 之前已经"永久允许"过（allow-always）→ 不再问
  3. ask=on-miss 且 security=allowlist，而命令没命中白名单 → 需要审批
白名单匹配看的是解析后的可执行文件真实路径（realpath），而不是原始命令字符串—— 这样 git 才不会被人用 PATH 劫持成别的二进制蒙混过关。

两者是叠加的独立防线：沙箱管"在哪跑"，审批管"让不让跑"，可以同时生效。 完整的决策链路、elevated 提权、ACP 工具风险分类等细节，见 子文档 13 · Sandbox 与审批。

常见问题

Q: OpenClaw 和 LangChain / AutoGPT 有什么区别？

LangChain 是一个开发框架（库），你用它的组件来构建自己的 AI 应用。 OpenClaw 是一个完整的运行时产品——它已经是一个可以运行的 AI 助手， 你通过配置和插件来定制它，而不是从零构建。 类比：LangChain 是乐高积木，OpenClaw 是一辆组装好的车（你可以换零件）。

Q: 为什么用 SQLite 而不是 PostgreSQL / Redis？

OpenClaw 是自托管的单用户系统，运行在你自己的设备上。 SQLite 是零配置的嵌入式数据库，不需要额外安装和运维。 对于单进程、单用户的场景，SQLite 的性能完全够用， 而且天然支持事务和崩溃恢复。

Q: 插件和扩展（extensions/）是什么关系？

extensions/ 目录下的每个子目录就是一个插件。 "插件"（Plugin）是面向用户的术语，"扩展"（Extension）是内部目录命名。 在文档和 UI 中统一使用"插件"。

Q: 什么是 MCP？

MCP（Model Context Protocol）是一个开放协议，让 AI 模型能连接外部工具和数据源。 OpenClaw 既可以作为 MCP 客户端（调用外部 MCP 服务提供的工具）， 也可以作为 MCP 服务端（把自己的能力暴露给其他 AI 应用）。

Q: 什么是 Harness？

Harness 是跑一个"已准备好"的 agent turn 的低层执行器—— 驱动模型输出、处理工具调用、把完成的 turn 交回来。 它不是模型，也不是封装 API 差异的适配层（那是 Provider / StreamFunction 层）。 OpenClaw 内置一个 id 为 openclaw 的 Harness，另有 codex / copilot 插件 Harness； 详见 3.2 Agent Runtime 的"谁来跑这个循环"小节。

Q: 什么是 Session Key？

Session Key 是一个字符串，唯一标识一段对话。 格式：agent:<agentId>:<channel>:<peerKind>:<peerId>。 比如 agent:main:telegram:peer:12345 表示 "main Agent 与 Telegram 用户 12345 的对话"。 同一个 Session Key 下的消息共享对话历史和上下文。

写在最后

OpenClaw 是一个架构成熟度很高的项目。它的核心设计思想可以浓缩为三句话：

  1. 核心保持无知：核心不知道任何具体插件的存在，所有能力通过注册注入
  2. 消息不会丢失：从入站到投递，每个环节都有持久化保障
  3. AI 不是无约束的：分层安全模型确保人类始终有最终控制权

理解这三点，你就抓住了这个项目的灵魂。剩下的，都是实现细节。
