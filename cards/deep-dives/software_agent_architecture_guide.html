01

这个 SDK 是什么？

一句话说清：Software Agent SDK 是一套用来搭建"软件工程 AI 员工"的地基。 它本身不是一个终端产品，而是一个 Python 工具包：四行核心代码 —— 一个 LLM（大脑）、一个 Agent（岗位说明书）、一个 Conversation（一次工作过程）、一个 Workspace（工地）—— 就能拼出一个会读代码、改文件、跑命令的智能体；而状态恢复、可配置的安全确认、远程执行这些生产级能力，地基已经替你打好了。

它是 OpenHands 团队开源的智能体基础设施，用 Python 写成，整个仓库由四个可独立分发的包组成。你可以把它理解成：别人给你造好的"AI 员工管理系统" —— 你只需要定义这个员工用什么大脑（LLM）、带什么工具（Tools）、在哪块工地上干活（Workspace），剩下的"怎么思考、怎么记账、出错怎么兜底、怎么远程上班"，系统都有标准答案。

从零自己写一个能改代码的 Agent 要踩的坑
对话历史越来越长怎么办？进程崩了怎么接着上次干？模型把工具参数写错了怎么救？危险命令（比如 rm -rf）怎么拦住？同一个 Agent 怎么部署成服务给多人用？……每一个问题，都够一个团队折腾几个月。
SDK 的方式这些问题都有现成的、经过源码审计的答案
上下文超长了有 Condenser（压缩器）自动摘要；崩溃后可从已持久化的状态与事件恢复 SDK 会话；工具参数错误有分层的恢复阶梯；启用确认模式后，符合策略的危险操作可进入"确认流"等人点头；要部署，可以使用 Agent Server。
先澄清：它"不是"什么
  • 不是聊天机器人 UI。它没有界面，只有协议和运行时。你看到的任何产品形态（CLI、Web、IDE 插件）都是别人基于它搭的上层。
  • 不是"乐高零件袋"。它带有明确的主张：事件必须记成树、状态必须集中在 Conversation、同步和异步必须对称。你是在一套成熟的工作流程上做定制，而不是从零拼装。
  • 不等同于 OpenHands。OpenHands 这个产品是建在这套 SDK 上的"样板房"；SDK 是可复用的地基本身。
论文谱系先分清 V1、V0 与 CodeAct
直接描述这套 SDK 的是 MLSys 2026 Software Agent SDK 论文： 它解释为什么从 V0 的单体、强制沙箱重构为四包、可选隔离、事件溯源与双层组合。 ICLR 2025 OpenHands 论文 讲的是旧 V0 平台； ICML 2024 CodeAct 论文 讲的是“用可执行代码作为动作”的研究思想。后两篇不能用来推断当前 Agent、EventLog、Workspace 或 REST API。

02

一条任务的完整旅程

本篇故事线一个真实的代码修改任务
假设你有一个 Python 项目，想让你的 AI 员工干这件事：
"把 utils.py 里的 fetch_data() 函数改成异步版本，并让所有相关测试通过。"
接下来，我们跟着这条任务走一遍完整旅程。每一步都对应源码里的一个真实位置。
开工 —— 创建一个 Conversation
Conversation 工厂 · 分流 Local / Remote

你写下这样一段代码：Conversation(agent=agent, workspace="./my_project")。注意 —— Conversation 并不是一个普通类，而是一个工厂：它会看你给的"工地"是什么类型，再决定造出哪种会话。

传入的是本地路径或 LocalWorkspace，就造一个 LocalConversation（在你自己的机器上干活）；传入的是 RemoteWorkspace，就造一个 RemoteConversation（把活儿发给远程的 Agent Server 去干）。两种会话用法几乎一样，但内部机制差别很大 —— 远程的故事我们放到 3.7 节再讲，本篇先跟本地这条线。

源码入口：openhands-sdk/openhands/sdk/conversation/conversation.py → Conversation.__new__()（按 workspace 类型分流）

接单 —— send_message 只是"开单据"
LocalConversation.send_message()

你调用 conversation.send_message("把 fetch_data() 改成异步并跑通测试")。很多人以为这一步 Agent 就开始干活了 —— 并没有。这一步只做三件事：

  • 把你的话包装成一条 Message；
  • 如果上一次会话已经 FINISHED 或 STUCK，把状态复位回 IDLE（相当于"翻篇，重新上工"）；
  • 发出一条 MessageEvent，写进事件账本。

就像餐厅服务员把点菜单夹进票夹 —— 菜还没开始炒。真正开火，是下一步。

源码入口：openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py → send_message()

开火 —— run() 心跳循环与 Agent.step()
LocalConversation.run() · Agent.step()

你调用 conversation.run()。这是一个 while True 的心跳循环，每一轮都干同一件事：请 Agent.step() 走一步。一步的内部流程是：

  1. 组装上下文：从事件账本的活跃分支生成 View（LLM 能"看见"的对话历史），再拼上系统提示词；
  2. 调用 LLM：把上下文发给大脑，拿回响应；
  3. 分类响应：用 classify_response() 把响应归成四类（见表下）；
  4. 分派处理：有工具调用就执行工具；有最终答复就收工。
响应类型含义系统的反应
TOOL_CALLS大脑说"我要用工具"执行工具，把结果记入账本，继续下一轮
CONTENT大脑给出了最终答复标记 FINISHED，准备收工
REASONING_ONLY只思考，没说话也没动手发一条"纠正性提醒"（nudge），请它给出实际输出
EMPTY空响应同上，提醒一下再来

源码入口：local_conversation.py → run() · openhands-sdk/openhands/sdk/agent/agent.py → step() · agent/response_dispatch.py → classify_response()

动手 —— 工具执行，先过 PreToolUse，再记账和执行
ParallelToolExecutor · Action ⇄ Observation

大脑第一步的响应是 TOOL_CALLS：先看一眼 utils.py。系统先构造 ActionEvent 并运行 PreToolUse Hook；Hook 放行后，动作才落进账本，再由安全分析器与确认策略决定等待还是执行。正常完成的工具调用会追加一个通过 action_id 回指动作的 ObservationEvent；崩溃边界允许暂时存在未配对 Action，恢复逻辑会显式处理。

如果大脑一次要求多个工具（比如"同时读三个文件"），ParallelToolExecutor 会并行执行它们；需要独占同一资源的工具则由资源锁排队，防止打架。

于是账本里依次多了：ActionEvent(FileEditor view utils.py) → ObservationEvent(48 行代码) → ActionEvent(FileEditor str_replace …) → ObservationEvent(修改成功) → ActionEvent(Terminal pytest …) → ObservationEvent(7 passed)。

源码入口：openhands-sdk/openhands/sdk/agent/parallel_executor.py → ParallelToolExecutor.execute_batch() · 配对逻辑见 conversation/state.py → get_unmatched_actions()

打盹与自愈 —— 恢复机制在后台待命
Condenser · 重试 / Fallback / Nudge

这条任务一路顺利，但真实世界里 Agent 随时会摔跤，而系统早就备好了兜底：对话历史太长快撑爆上下文窗口了，Condenser（压缩器）会自动把旧历史摘要成一份小结（注意：只压缩"给大脑看的视图"，账本原文一字不动）；LLM 的 API 报了临时错误，重试与 fallback 会自动换姿势再来；大脑连续放空，系统会 nudge 它一下。这一切对 run() 循环是透明的 —— 心跳照旧。

另一种"暂停"是故意的：应用启用确认模式后，如果某个动作被安全策略判定需要人点头，状态会切到 WAITING_FOR_CONFIRMATION，循环退出等你。你确认后再次 run()，Agent 会先执行那些等待中的动作，再继续心跳。默认配置使用 NeverConfirm，不会要求确认。

交卷 —— FINISHED，但门口还有一道岗
Stop Hooks · 持久化落盘

测试全绿之后，大脑返回 CONTENT："已完成，共修改 2 个文件。"状态切到 FINISHED。但循环不会立刻退出 —— 门口站着 Stop Hooks（停止钩子）：你可以配置一段脚本在 Agent 宣布完成时做检查（比如"跑一遍 lint"），如果钩子返回"不同意"，状态会被拨回 RUNNING，Agent 继续加班。钩子放行后，循环才真正退出。

此时已持久化的 base_state.json（状态快照）与事件文件可用于恢复 SDK 会话状态、事件历史和待处理 Action。两条写入路径不构成跨文件事务，也不会回滚或重放命令、文件修改、HTTP 请求等外部副作用。

源码入口：Stop hook 判定见 local_conversation.py → run() 的 FINISHED 分支 · 持久化见 conversation/state.py

八大核心模块详解

第 2 章走完了任务旅程。这一章我们把地图上的每个区域打开，看看设计者是怎么想的。不需要全部读完 —— 挑你感兴趣的部分即可。每节结尾都有源码入口和深度文档链接，想钻多深都行。

3.1 Agent / Conversation / LLM —— 岗位说明书、上班过程与租来的大脑

Analogy → 类比理解 想象一家公司雇了一名新员工：Agent 是岗位说明书 —— 写明了这个岗位用什么大脑、带什么工具、遵守什么守则，打印归档后不许再改；Conversation 是这位员工某一天的上班过程 —— 干到哪了、记了什么账、现在什么状态，全在这一天里；LLM 是从外包公司按小时租来的大脑 —— 它本身不记事，每次被问都是看着你递过去的材料现场作答。

这三者的分工是整个 SDK 最重要的设计决策：声明和策略放 Agent，会话事实和进度放 Conversation，模型能力与调用级运行态封装在 LLM。Agent 的字段被冻结（Pydantic frozen 模型），Conversation 因而能围绕独立 State 暂停、恢复和分叉；复用同一个 Agent 时仍要知道嵌套 LLM 的 Metrics、缓存和 fallback 状态可能被共享。

角色管什么可变吗类比
Agent用哪个 LLM、带哪些工具、提示词怎么拼、安全策略是什么冻结，创建后不可改岗位说明书
Conversation执行状态、事件账本、心跳循环、恢复与中断全部可变状态的家这一天的上班过程
LLM模型调用、重试、fallback、用量指标不承载会话事实，但持有 Metrics、缓存与路由等运行态租来的大脑

心跳的核心是 Agent.step() —— 每被调用一次就走"组装上下文 → 调 LLM → 分类响应 → 分派处理"一圈：

图 3 · 心跳一圈：TOOL_CALLS 走 ④ 回到 ①；CONTENT 是唯一的"正常出口"。REASONING_ONLY / EMPTY 则在 ③ 处被提醒后重新进圈。
常见误解澄清："Agent 是冻结的" ≠ "整个对象图都不可变"
冻结的只是 Agent 这一层的 Pydantic 字段。它内部引用的 LLM 并不是冻结模型 —— LLM 身上还挂着调用指标（Metrics）、临时缓存和 fallback 状态这些运行期的可变数据。所以准确的说法是：配置层冻结，运行态有自己明确的归属（指标归 LLM，事实归 Conversation）。想"修改"一个 Agent？正确姿势是用它的字段拷贝出一个新的 Agent，而不是原地改。

源码入口：openhands-sdk/openhands/sdk/agent/agent.py → Agent · conversation/conversation.py → Conversation.__new__() · conversation/impl/local_conversation.py → LocalConversation

3.2 状态机与事件树 —— 像 Git 一样记账

Analogy → 类比理解 事件账本不像流水账，更像 Git 仓库：每条事件是一个 commit，记录着自己的 parent_id（父提交）；当前"读到哪了"由一个像 HEAD 的指针 leaf_event_id 标记；fork（分叉）就是开新分支去试另一种走法，navigate（导航）就是切分支。根节点的"父提交"是一个哨兵值 __root__，相当于空提交。

为什么不是简单的列表？因为 Agent 需要试错：走了一半发现路不对，可以回到某个节点换个方向重来 —— 之前发生的事不能被抹掉（它们是已经发生的"事实"），只能开新分支。于是"事件是树，不是列表"成了整个系统的关键不变量：LLM 看到的上下文、会话恢复、可视化回放，都只是"从 HEAD 沿父指针走到根"这条活跃分支的不同读法。

图 4 · 事件树：每条事件带 parent_id；fork 开分支，navigate 切分支；EventLog 公共 API 只追加，不原地更新已有事件。

会话"现在处于什么状况"，由一个八态状态机描述：

状态大白话含义属于终态吗
IDLE还没开工（或刚被"翻篇"）否
RUNNING心跳循环正在跑否
PAUSED被暂停 / 被中断，随时可继续否
WAITING_FOR_CONFIRMATION卡在安全确认，等人点头否
FINISHEDAgent 宣布干完了（注意：不代表任务成功，见第 4 章）是
ERROR出错终止（比如迭代数达到上限，默认 500 轮）是
STUCK卡死检测器判定"原地打转"是
DELETING会话正在被删除否

账本怎么落盘？答案朴素得可爱：没有数据库。状态快照存成一份 base_state.json，事件逐条存成小文件（events/event-NNNNN.json）。恢复一次会话 = 把状态快照和事件文件读回来，再让 Agent 校验（verify）一遍。这也意味着你随时可以用文本工具直接"翻账本"排障。

小澄清：Action 和 Observation 为什么必须成对？
正常工具动作（Action）会有回执（Observation），Observation 通过 action_id（以及 LLM 侧的 tool_call_id）回指动作。如果动作写入后进程就崩了，账本上会留下未配对 Action。恢复后的 run() 会扫描这些动作（get_unmatched_actions()）并重新分派，结构错误则由错误事件收口；这会修复 LLM 所需的工具历史结构，但不能证明崩溃前的外部副作用尚未发生，因此非幂等工具需要额外核对。

源码入口：openhands-sdk/openhands/sdk/conversation/state.py → ConversationExecutionStatus · conversation/event_store.py → EventLog · event/base.py → parent_id

3.3 上下文工程 —— 给"金鱼记忆"的大脑递材料

Analogy → 类比理解 LLM 每次调用都是"现场作答"，它能看到什么，完全取决于你递过去的材料。这份材料叫 View —— 就像数据库里的视图（View）：它不存储数据，只是按规则从底层数据（事件树的活跃分支）投影出来的一份"只读呈现"。而 Condenser 是材料太厚时的真空压缩袋：把旧材料抽真空压成一份摘要，原件依然完好地躺在账本里。

每次 Agent.step() 组装上下文时，系统做三件事：

  1. 生成 View：从活跃分支把事件翻译成 LLM 对话消息。这不是简单拼接 —— View 有一套严格规则：Observation 不能凭空出现、同一批工具调用必须原子呈现、工具调用与回执必须配对……这些规则保证了递到大脑面前的历史永远是"合法"的。
  2. 拼装系统提示词：由一个 PromptSection 注册表按顺序组装 —— 有静态段落（环境信息、人格设定），也有动态段落（比如当前可用的技能列表，每次调用现场解析）。
  3. 按需瘦身：如果历史超过预算，Condenser 出场。

Condenser 家族有几款现成实现：RollingCondenser（滚动窗口，旧消息滚出去）和 LLMSummarizingCondenser（请 LLM 把旧历史写成一份摘要）等，还能用 Pipeline 把它们串起来。压缩发生时，系统会在账本里记一条 Condensation 事件 —— 压缩本身也是"发生过的事实"。

常见误解澄清：压缩会删事件吗？—— 不会
Condenser 只是 View 的转换器：它改变"这次给大脑看什么"，从不触碰账本。事件文件一条不少，随时可以 fork 回压缩前的分支、完整回放。把"上下文管理"和"事实存储"彻底分开，是这套设计能兼顾省 token 与可恢复的关键。
顺带一提Skills 的"渐进披露"
给 Agent 装了很多技能（Skills）时，系统不会把所有技能全文塞进提示词 —— 那会瞬间撑爆上下文。默认只注入每个技能的一行简介（规范上限 1024 字符），Agent 觉得哪个有用，再通过 invoke_skill 把全文"借阅"进来。像图书馆：书架上只摆目录，要书再去找管理员。

3.4 LLM 调用管道 —— 翻译公司与五层安全网

Analogy → 类比理解 各家模型厂商的 API 方言都不一样。LLM 类就是一家翻译公司：你对它说同一种"普通话"（SDK 的统一调用方式），它内部的译员（LiteLLM 传输层）负责翻译成各家方言。每个资深译员手边还有一本国别手册（model features，模型特性注册表），记着"这家要额外带这个参数、那家不支持图片"之类的差异 —— 而不是把所有 if-else 都塞进前台接待员（主调用逻辑）的脑子里。

这家翻译公司对内有两个门面：Chat Completions 和 Responses 两套 API，各配同步与异步版本（completion() / acompletion()、responses() / aresponses()）。默认会自动挑合适的 API。两扇门最终都汇聚到同一条传输通道，重试逻辑对两条路一视同仁。

真正值钱的是出错时的分层恢复阶梯 —— 从轻到重共五级：

层级触发场景系统的动作类比
1 · Retry网络抖动、限流等临时错误自动重试（带退避）电话占线，稍等重拨
2 · Fallback主模型持续不可用切换到备用模型继续这个译员病了，换一个顶上
3 · Nudge模型返回空响应或只思考不输出发一条纠正性提醒再问一次"麻烦给个准话"
4 · Condense上下文太长被拒绝先压缩历史再重试材料太厚，先做摘要再递
5 · Hard error以上都救不回来抛错终止，状态进入 ERROR上报主管，人工介入
小澄清："上下文太长"和"历史格式坏了"是两种病
模型报"历史不合法"（比如工具回执缺失或重复）时，系统不会把它当成"上下文溢出"去盲目压缩，而是归类为专门的 LLMMalformedConversationHistoryError 单独处理 —— 日志里也能看出这是"历史坏了"而不是"历史长了"。分清楚病因，才能对症下药。
工程细节同步与异步完全对称
SDK 里每个异步方法都有同步孪生兄弟：acompletion ↔ completion、acondense ↔ condense、astep ↔ step、arun ↔ run。重试机制天然兼容两者。所以写脚本可以用同步版图省事，做服务就用异步版提吞吐 —— 语义一模一样。

源码入口：openhands-sdk/openhands/sdk/llm/llm.py → completion() / _transport_call() · 模型特性见 llm/utils/model_features.py

3.5 工具体系 —— USB 接口与共享吊塔的工地

Analogy → 类比理解 每个工具都像一个 USB 设备：想接入系统，必须符合统一接口 —— 一份"铭牌"（ToolSpec：名字、描述、参数 schema）加一个"执行器"（拿到动作、返回回执）。插座（注册表）不关心你是键盘还是硬盘，只认接口。而并行执行像一个有多台设备共享一台吊塔的工地：谁要用吊塔（独占资源），先登记，调度器按登记排队，绝不撞车。

一个工具从定义到被调用，走这样一条链：

环节角色大白话

Agent.tools_map这个员工领到的工具包名字 → 工具定义的映射，Agent 创建时装配
ToolExecutor执行器真正动手：接收 Action，返回 Observation
ParallelToolExecutor并行调度员一批动作同时开工，用资源锁防冲突，保证回执顺序合法

工具干什么

3.6 安全、确认与 Hooks —— 先开单，后开火

Analogy → 类比理解 一家靠谱的餐厅，服务员不会喊一声"做红烧肉"厨师就直接开火。SDK 会先构造点单信息并让 PreToolUse 门禁检查；门禁放行后才把 ActionEvent 写入账本，随后由安全分析与确认策略决定等待还是执行。确认并非默认开启，只有配置确认模式后，需要顾客点头的动作才会暂停。

具体走一遍：Agent 提出一批工具调用后，系统构造 Action 并先运行 PreToolUse；被拒绝的 Action 不写入 EventLog。放行的 Action 持久化后，系统再问 SecurityAnalyzer（安全分析器）："这批动作风险几何？"分析器给出风险等级（没配分析器就是"未知"）。接着 ConfirmationPolicy（确认策略） 根据风险等级拍板：

策略行为
AlwaysConfirm每个动作都问 —— 最谨慎
NeverConfirm从不打断 —— 全自动（用于可信环境）
ConfirmRisky只拦高风险动作 —— 常用折中

默认行为：ConversationSettings.confirmation_mode 关闭，运行态使用 NeverConfirm；因此仅配置风险分析不等于启用了人工确认。

需要确认时，状态切到 WAITING_FOR_CONFIRMATION，run() 循环退出。你确认后再次调用 run()，Agent 在下一步开头看到账本上那些"待执行的动作"，就当作你已点头，继续执行。"先持久化再确认"不是实现细节，而是刻意设计：哪怕确认到一半进程崩了，重启后那些动作依然原样在账本上等着你，不会丢、不会重复开单。

另一个守门机制是 Hooks（钩子） —— 在生命周期的关键节点上可以挂你自己的脚本或提示词，像安在各个门口的门禁：

门口你能做什么
会话开始 / 结束时初始化环境、收尾检查（Stop hook 可以拒绝收工，让 Agent 继续干）
收到消息时改写或增强用户输入
工具执行前后拦截、审计、补充上下文
常见误解澄清：Workspace 不是"安全沙箱"的同义词
安全是分工的：SecurityAnalyzer 管风险判定，ConfirmationPolicy 管要不要问人，Hooks 管自定义门禁，Workspace 管的是"命令在哪里执行"（本地 / Docker / 云端）。把 Agent 放进 Docker 工作区确实能隔离破坏面，但那是部署选择，不是 SDK 默认的安全承诺 —— 别把"在容器里跑"当成唯一防线。

源码入口：openhands-sdk/openhands/sdk/security/confirmation_policy.py · security/analyzer.py → analyze_pending_actions() · hooks/manager.py · 示例 examples/01_standalone_sdk/04_confirmation_mode_example.py 与 33_hooks/

3.7 远程执行与 Agent Server —— 控制塔与"别信第一声'完成'"

Analogy → 类比理解 本地会话是你亲自在工地盯着；远程会话则像遥控一个外包团队：Agent Server 是控制塔，REST API 是指令通道（"开工""暂停""查进度"），WebSocket 是实时雷达屏（事件和状态一有变化就推送过来）。你手里的 RemoteConversation 是个遥控器 —— 用法和本地几乎一样，但每一次"看起来完成了"，都要等控制塔的权威广播才算数。

openhands-agent-server 包把整套 SDK 装进一个 FastAPI 服务里：create_app() 应用工厂组装约二十组 REST 路由（统一挂在 /api/* 前缀下：会话、事件、工具、文件、设置……），外加独立的 WebSocket 路由（事件流在 /sockets/events/{conversation_id}）。服务内部由 ConversationService（管会话生命周期）和 EventService（管事件流转与广播）分头打理，还支持"暖池"模式（deferred init）：先占个坑不干活，等真正分配了用户再初始化，加快调度。

远程模式下最精妙的设计是完成屏障（completion barrier）。为什么？回看 3.6 节：Agent 喊出 FINISHED 后，Stop hook 有权拒绝放行，状态会被拨回 RUNNING。也就是说 —— 第一次收到的 FINISHED 可能只是"狼来了"。于是遥控器端定了三条规矩：

信号可信度处理方式
WS 推送的字段级 FINISHED只当"提示"不作数，继续等
run 结束后的 WS 全量状态快照权威信号收到即核对事件、确认完成
REST 轮询到终态且始终没有 WS 快照兜底信号连续 30 秒（TERMINAL_HARD_FALLBACK_SECS）才接受，防止无限挂起

顺带区分两个容易混的"停"：pause（暂停）是按下暂停键，稍后可以从容继续；interrupt（中断）是取消正在进行的那次运行 —— 底层直接取消异步任务，取消信号从 LLM 的 HTTP 流一路贯穿到会话循环，最后状态落到 PAUSED 并记一条中断事件。快、狠、但可恢复。

源码入口：openhands-agent-server/openhands/agent_server/api.py → create_app() · openhands-sdk/openhands/sdk/conversation/impl/remote_conversation.py → _wait_for_run_completion()

3.8 扩展生态 —— 小抄、插件包与外包小队

Analogy → 类比理解 想让这位 AI 员工变得更强，有四种互不冲突的路子：Skills 是"小抄"（按任务现查现用的操作手册）；Plugins 是"插件包"（成捆地加装技能、钩子和工具）；Subagent 是"外包小队"（把子任务整个委托出去，独立开工、独立记账）；MCP 是"外部工具集装箱"（接入别人按标准协议发布的工具服务）。
机制是什么什么时候物化（真正生效）
Skills带触发条件的操作手册；简介常驻提示词，全文按需借阅（见 3.3）Agent 主动 invoke_skill 或消息命中触发词时
Plugins技能 + 钩子 + 工具的打包分发单元，可从本地或远程装载第一次发消息时懒加载 —— 创建会话后立刻查插件是查不到的
Subagent由 Task 工具发起的独立子会话（有自己的事件账本），干完把结果汇报回来主 Agent 决定委派时
MCP接入外部 MCP 服务器发布的工具，支持运行时动态发现与刷新会话初始化连接 MCP 服务器时
容易踩的坑MCP 配置有三种形状，只认一种规范形
SDK 自己的配置形状是扁平的服务器映射（dict[str, MCPServer]）；网上常见的 .mcp.json 那种 {"mcpServers": {...}} 包一层的写法，是旧格式的兼容入口，系统会自动拆包；而 FastMCP 的类型化配置只在真正建立连接的那一刻才被构造出来。三种形状各管一段，写配置时认准"服务器映射"这一种就不会错。

还有两件"后勤"值得知道：Settings（设置）是这套系统的装备清单 —— 可序列化配置收敛在 AgentSettings 与 ConversationSettings 两个规范模型中，持久化形状带着 schema_version 迁移链和黄金样本兼容门禁；Secrets（密钥）则统一走加密/脱敏管道，序列化时默认打码。

设计哲学与常见误解

八个模块看完，最后用四条"铁律"把它们串起来。这四条是设计者在无数次权衡后立下的规矩 —— 读源码时遇到不理解的设计，回头看看这四条，多半能想通。

铁律 1协议与实现分离，四包各管一段
SDK 定义协议与编排，Tools 提供能力，Workspace 提供执行环境，Agent Server 提供远程运行时。依赖方向永远是单向的：上层可以用下层，下层绝不反向 import 上层。这让"换个工具包""换个部署形态"都变成拔插头换插座，而不是拆房子。
铁律 2可变状态只有一个家
Agent 的 Pydantic 字段冻结、事件不可变，会话事实集中在 Conversation 的 ConversationState 里。想知道"这次会话现在什么情况"，只问它一个；想恢复、分叉、持久化，也以它为权威。 但这不是“整个对象图都不可变”：当前 LLM 仍维护 Metrics、缓存、fallback 和 Router 的 active_llm 等运行态。官方论文中的 immutable components 是设计概括，读代码时应以这个更精确的边界为准。
铁律 3同步与异步，永远成对出现
从 LLM 调用到 condenser 到 Agent.step 再到 run，每一层都有同步/异步两个孪生版本，基类提供默认委托，你自定义的子类不用改就能同时跑两条路。写脚本图省事用同步，做服务要吞吐用异步。
铁律 4向后兼容是硬约束，不是口号
公开 API 的废弃必须给出至少跨越 5 个 minor 版本的移除缓冲期；历史事件格式的兼容是永久义务（旧账本必须永远读得懂）；持久化设置带版本号迁移链，由 CI 的黄金样本门禁把守。升级 SDK，你的旧会话、旧配置不该出事。
常见误解一：事件账本 = 某个数据库？—— 真不是
没有 SQLite、没有 Postgres。落盘形状就是 base_state.json 加一叠逐条的事件 JSON 文件。恢复 = 读回快照与事件 + Agent 校验。这个"朴素到可以 cat"的设计，换来了排障透明（随时翻账本）、部署零依赖（不需要数据库运维）和格式永久可控（JSON 文本就是最好的长期存档）。代价是大规模检索要靠代码而非 SQL —— 这是刻意的取舍。
常见误解二：FINISHED = 任务成功？—— 差得远
FINISHED 的准确含义只有一句：Agent 决定不再继续了（它给出了 CONTENT 响应）。测试跑没跑通、改得对不对，状态机一概不知。想要"真正的验收"，得靠 Stop hooks 在收工门口做检查（不合格就拒停，Agent 继续加班），或者引入专门的评审机制。另外记住 3.7 节的教训：远程模式下，第一声 FINISHED 连"它决定停了"都不一定算数。
常见误解三：升级 SDK 只需要看 changelog？—— 先认清四种"兼容表面"
这个仓库把"兼容"拆成四条独立的战线：Python API（类和方法，有弃用缓冲期）、Field 默认值（Pydantic 字段默认值变更会被单独标记和通告）、REST/OpenAPI 契约（服务端接口，同样有 5 个 minor 的缓冲）、持久化格式（设置带迁移链，事件永久兼容）。你的集成面碰到的是哪一条战线，升级时就要看哪一条的规则 —— 笼统地问"这个版本有没有 breaking change"是没有标准答案的。

5.3 常见问题

这和 LangChain / LangGraph 有什么区别？
简单说：那边更像"零件库 + 图编排框架"，你自己决定怎么拼；这边是一套带有强烈主张的完整运行时 —— 事件必须是树、状态必须集中、恢复/确认/远程都有内置的标准答案，还配了可直接部署的 Agent Server。如果你想要"开箱即用的软件工程 Agent 基础设施"，选它；如果你想从零自由编排任意形状的图，那边更灵活。两者不是同一层次的东西。
OpenHands 和这个 SDK 是什么关系？
SDK 是地基，OpenHands 产品是建在地基上的房子。这个仓库里的 openhands-agent-server 就是"把房子交付出去的脚手架"：把 SDK 装进 REST/WebSocket 服务，配上 Docker 镜像和二进制发布。
我想给 Agent 加一个自己的工具，麻烦吗？
不麻烦：实现一个工具类（提供 ToolSpec 铭牌 + 执行逻辑），放进 Agent(tools=[...]) 即可。照抄 examples/01_standalone_sdk/02_custom_tools.py 起步。细节看子文档 09。
pause 和 interrupt 到底有什么区别？
pause 是"按暂停键"：循环停在干净的位置，随时继续；interrupt 是"取消正在进行的那次运行"：直接取消底层异步任务，取消信号从模型 HTTP 流一路传到会话循环，状态落到 PAUSED 并记一条中断事件。一个温和，一个果断，但都不毁数据 —— 账本永远完整。
会话跑到一半进程崩了，之前的工作白费吗？
不会。所有事件和状态快照都在落盘（3.2 节）。重启后从持久化目录恢复会话，系统还会主动修补"孤儿动作"（发出了但没回执的工具调用），保证恢复后的历史对 LLM 依然合法。试试 10_persistence.py 这个例子。
我要把它用在生产环境，还要关心什么？
三件事：部署（用 agent-server 的 Docker 镜像或二进制，注意 warm-pool/deferred init 配置）、密钥管理（Secrets 默认脱敏，配置好加密与注入方式）、升级纪律（第 4 章的四条兼容表面，尤其是持久化格式的迁移链）。分别看子文档 14、16、17。

读完如果只记三句话
  1. Agent 是岗位说明书，Conversation 是上班过程，事件账本是工作日志 —— 配置冻结、状态集中、事实不可变，全部机制都从这三个角色的分工长出来。
  2. 事件不是列表，是一棵像 Git 的树 —— 上下文、恢复、分叉，都只是"从 HEAD 走到根"这条活跃分支的不同读法；EventLog 公共 API 采用追加语义，试错靠开分支。
  3. "完成"从来不是一声吆喝 —— Stop hook 能拒停，远程的第一声 FINISHED 不作数，真正的收工要等权威的全量快照。这套系统对"状态"的较真，就是它敢承诺可恢复的底气。
