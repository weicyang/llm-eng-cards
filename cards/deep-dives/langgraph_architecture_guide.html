01

LangGraph 是什么？

一句话说清：LangGraph 是一个用来构建"有状态、可暂停、可恢复"的 AI 工作流与 Agent 的执行内核。 你向它声明"有哪些步骤、步骤之间怎么走"（一张图），它负责把这张图可靠地跑起来——该并行的并行、该存档的存档、该停下来等人的停下来；哪怕进程崩溃、服务器重启，也能从上次的存档点继续执行。

它由 LangChain 团队开源，用 Python 编写，当前核心包版本 langgraph 1.2.11。名字里的 "Graph" 来自 Google 的 Pregel 图计算论文——但别被学术背景吓到，你只需要记住：它把一张"流程图"变成了带游戏存档的耐久执行引擎。

传统方式裸代码写 AI 流程的痛
状态存在内存变量里 → 进程一崩全丢；"暂停等人工审批、批完再继续"要自己写序列化；想并行跑两个步骤要自己处理同步；失败之后从哪恢复全靠运气。每做一个严肃的 Agent，都在重新发明一遍轮子。
LangGraph 的方式声明图，运行时兜底
你只声明节点和边，剩下的交给运行时：状态自动管理并在每一步之后存档；interrupt() 一行代码实现暂停等人；并行节点的输出按你预先声明的规则自动合并；全程每一步都可回放、可审计。
类比理解 把 LangGraph 想象成 AI 流程的游戏存档系统：你写的图 = 游戏剧本；每一轮执行（superstep，超级步）= 一次自动存档；checkpoint = 存档文件；interrupt() = 剧情暂停等玩家做选择。游戏崩溃了，重开是从上次存档继续——而不是从头再打一遍。

先澄清：它"不是"什么
  • 不是开箱即用的 Agent / 聊天机器人：仓库里没有一个"助手产品"，连 ReAct Agent 也只是用同一套机制编译出来的一张"示例图"。
  • 不是 LangChain：LangChain 负责调用模型与工具生态，LangGraph 负责"把这些能力组合成可靠的流程"。两者是搭档，不是替代关系。
  • 不是跨机器的分布式集群：本仓库运行时的并发在进程之内；队列、多租户、部署属于单独部署的 LangGraph Server（不在本仓库内）。
  • 不是让模型变聪明的魔法：它不提升 LLM 的输出质量，只是把模型的不确定性关进可审计、可恢复的状态机里。
02

一次退款审批的完整旅程

抽象的架构很难记住，故事好记。我们跟着一个真实场景走完全程——走完这一遍，LangGraph 的核心机制你就都见过了。

场景电商客服系统收到一笔退款申请
金额 ¥3000，超过了"¥1000 以下免审批"的规则。要求：查订单 → 风控判断 → 暂停下来等人工审批 → 批准后执行退款并通知用户。棘手的地方在于：审批人可能两小时后才回复——你的程序总不能开着等两小时。这正是"有状态、可暂停、可恢复"的主场。
画一张图：声明节点与连线
StateGraph · 声明式 DSL

节点就是普通 Python 函数，职责只有一个：读当前状态，返回一小块"增量"（partial update，局部更新）。我们用 add_node 登记四个节点——fetch_order（查订单）、risk_check（风控）、human_approval（人工审批）、execute_refund（执行退款）；用 add_edge 连起固定流程，再给金额判断加一条条件边。最后调用 compile(checkpointer=...)——蓝图变成可执行的东西。

类比理解像写剧本：先定角色（节点）和走位（边），再交给导演（compile）检查一遍走位有没有断档，然后才能开机。

checkpointer 参数就是"存档插件"：测试用内存版（InMemorySaver），本地用 SQLite，生产用 Postgres——后面 3.4 节细说。

源码入口：libs/langgraph/langgraph/graph/state.py（StateGraph / compile）
启动执行：一次 invoke，一个"存档槽"
graph.invoke · thread_id

调用 graph.invoke(输入, {"configurable": {"thread_id": "refund-001"}})。这里的 thread_id（线程 id）相当于存档槽的名字：同一个 thread_id 的多次调用，续写的是同一段故事。后面审批人回复时，就是靠它找回这次执行的存档。

超级步 1：查订单 → 合并 → 存档
Pregel Loop · 第 1 圈

运行时不是"顺着边一个节点一个节点地跑"，而是按超级步（superstep）推进。这一步里只有 fetch_order 被触发；它返回 {"order": {...}}——注意它交出的只是"增量"。这一步的所有任务结束后，系统才在屏障处把增量统一合并进状态（Channel，3.2 节细说），并写下第一个 checkpoint（存档）。

类比理解回合制游戏：本回合该行动的单位并行行动，全部结束后裁判统一结算、存档，再进下一回合。
超级步 2：风控 → interrupt() 全场暂停
risk_check · human_approval · interrupt

risk_check 判断金额超过阈值，图走到 human_approval。这个节点里调用了一行 interrupt({"订单": ..., "问题": "是否批准退款？"})——运行时立刻"冻结"现场：把当前进度写成 checkpoint，把中断信息（__interrupt__，附带你要展示给审批人的内容）返回给调用方，然后这次调用就结束了。

关键interrupt 不是 sleep，是"存档离场"
只要配的是持久化 saver（SQLite / Postgres），此时你甚至可以让进程退出、服务器重启。等两小时还是两天，都不占用任何算力——因为执行上下文不在内存里，而在磁盘上的 checkpoint 里。
源码入口：libs/langgraph/langgraph/types.py（interrupt / Command / Send）
审批通过：从存档里捡起来继续
Command(resume=...) · 同一 thread_id

两小时后，审批系统回调你的服务。你只需再次调用：graph.invoke(Command(resume="approved"), 同一个 thread_id)。运行时加载 checkpoint、重建状态，重新进入 human_approval 节点——这一次 interrupt() 不再暂停，而是直接返回 "approved"，图继续往下走。

重要澄清恢复不是"从暂停的那行代码继续"
checkpoint 保存的是可序列化的状态，不保存 Python 的执行现场（栈帧）。所以节点在恢复时会从头重新执行，直到 interrupt() 调用处"原地"拿到你传入的 resume 值。推论：interrupt 之前的副作用（写数据库、发 HTTP 请求）会被再执行一次——它们必须幂等，或者干脆挪到 interrupt 返回之后。
超级步 3：执行退款 → 完成，全程留痕
execute_refund · END · state API

execute_refund 执行完毕，图到达 END，返回最终状态。想审计？graph.get_state(config) 查看最新状态，graph.get_state_history(config) 列出所有历史存档——你甚至可以指定某个旧存档从那里"开新分支"重跑（time-travel，时间旅行），比如回到审批前改选"拒绝"看看会发生什么。

03

六大核心模块详解

下面把系统拆成六个模块逐个看。不需要全部读完——挑你感兴趣的部分即可。每个模块都配了一个生活类比和源码入口，方便你想深入时知道从哪下手。

3.1 StateGraph —— 蓝图与验收员

类比理解StateGraph 是建筑蓝图：记录了有几个房间、走廊怎么连——但蓝图不能住人，它不能直接被调用。compile() 是施工加验收：检查每条边的两端都存在、中断配置合法，然后交钥匙——产出的 CompiledStateGraph 继承自运行时引擎 Pregel，从此自带 invoke / stream / 状态查询的全部能力。

图的"原料"是 Schema（状态结构声明）。新手期只需要关心一个：State——所有节点共享的可变状态，通常就是一个 TypedDict。每个字段默认对应一种叫 LastValue（只保留最后一次值）的 Channel；如果这个字段会被多个节点并行写（比如消息列表），就要给它配一个 reducer（合并函数），写作 Annotated[list, add_messages] 这种形式——细节在 3.2。

构件干什么一句话
add_node登记一个节点（普通函数即可）角色进场
add_edge固定走向：A 跑完必到 B走廊
add_conditional_edges看当前状态决定下一步去哪岔路口
START / END入口与出口（保留节点）大门与退场
Command一个返回值同时表达"改状态 + 跳到哪 + 提供恢复值"节点的万能指令单
Send向同一节点扇出多份输入（map-reduce 的基础）一把钥匙开 N 扇门
小澄清：compile() 到底干了什么？
按顺序大致是：校验节点/边/中断配置 → 确定输入、输出和流式通道 → 合并全局与节点级的 retry / cache / timeout 策略 → 把每个节点包装成带"读什么、写什么"契约的 Pregel 节点 → 把边和分支翻译成触发关系。编译不执行任何模型或工具，也不把 Python 函数变成什么静态计划——它造出的是"触发关系图"，动态分支和中断仍然在运行时决定。
源码入口：libs/langgraph/langgraph/graph/state.py（StateGraph · compile · CompiledStateGraph）

3.2 Channel —— 状态不是大 dict，是一组"有合并规则的盒子"

类比理解两个节点同时干活，结果怎么合？LangGraph 的答案：状态不是一个大 dict，而是拆成一个个盒子，每个盒子上写着"多人往里扔东西时怎么合并"。这个盒子就是 Channel。

你在 Schema 里写的每个字段，编译时都会解析成一个 Channel。最常用的几种：

Channel合并规则什么时候用
LastValue只保留最后一个值；同一步被两个节点写会直接报错标量状态、单一来源（默认）
BinaryOperatorAggregate把本步每份写入依次喂给你的 reducer 聚合消息列表、计数、集合（Annotated[T, reducer]）
EphemeralValue只活一个超级步，下一步自动清空入口输入、一次性触发信号
Topic / NamedBarrierValue收集多份值 / 等所有指定来源到齐才可读Send 扇出的任务队列、多前驱汇合

这套设计把"并行的意外"变成了"显式的契约"：两个节点同时写一个字段，结果不取决于谁先跑完，而取决于你声明的 reducer；如果你没声明（LastValue），系统宁可大声报错也不让数据悄悄错乱。顺带一提：同一超级步里，兄弟节点看不到彼此刚写的值——大家读的都是本步开始时的稳定快照，写统一在屏障后合并，这从机制上避免了执行顺序带来的数据竞争。

小澄清：reducer 有什么讲究？
reducer 最好满足结合律（怎么分组算结果都一样），最好也满足交换律——因为并行任务的写入顺序只保证确定性排序，你的业务语义不应该依赖"谁先到"。像 operator.add（列表拼接）、消息去重合并这类都是安全的选择。
源码入口：libs/langgraph/langgraph/channels/（last_value.py · binop.py · topic.py · named_barrier_value.py）

3.3 Pregel 运行时 —— 超级步的心跳

类比理解回合制策略游戏。每一回合（超级步）：① 读取上一回合结束时的稳定盘面 → ② 判定哪些单位这回合该行动 → ③ 这些单位并行行动 → ④ 全部结束后裁判统一结算 → ⑤ 存档 → ⑥ 进入下一回合。同一回合内，单位之间互相看不到对方的动作——这一下消灭了一大类数据竞争问题。
图 3 · 超级步循环：读快照 → 备任务 → 并行跑 → 屏障合并 → 存档 → 下一圈。这就是 Pregel 运行时的全部心跳。

每圈"谁该行动"由两类任务组成：

类型来源白话
PULL边和状态（Channel）版本变化自动触发"轮到你了"——大多数节点属于这种
PUSHSend(node, arg) 扇出、Functional API 的 task 调用"加塞一个临时任务"，同一节点可以被塞多份不同输入
小澄清：superstep、node、task——三个概念啥区别？

它们不在同一个维度：node 是图上的"角色"（建图时声明的一个函数），superstep 是运行时的"一回合"（Pregel 主循环转一圈），task 是某一回合里的具体执行单元（"用这份输入跑这个节点"）。就像回合制游戏：角色定义在游戏开始前，回合里多个角色可以同时行动，同一个角色也能在多回合里反复登场。

NodeTaskSuperstep
是什么图上声明的计算单元一次具体的节点调用实例一次完整的循环迭代：备任务→执行→合并→存档
存在于建图时（静态）运行时（动态）——task 每轮按需生成，superstep 是时间单位
数量关系一个 superstep 可含 1 或 N 个 task（没有任务就没有这一轮）；同一 node 可在多个 superstep 反复跑（循环图）recursion_limit 数的是 superstep，不是 node
边界职责只管"读状态 → 交增量"屏障合并 + checkpoint 存档发生在这里

那为什么很多资料说"一个 node 就是一个超步"？因为在串行线性图（A→B→C）里，一个超步恰好只跑一个 node、它跑完就写一次存档——这是常见图形状下的性质，是巧合，不是定义。一旦出现并行（一轮两个 node）、Send 扇出（同 node 一轮多个 task）或循环（同 node 跨多轮），这个等式立刻失效。

两个易忽略的点：① 同一轮并行的两个 task 读的是同一份快照——谁也不看见谁的写入，合并后才可见（这正是并行安全的来源）；② Send 给同一节点扇出 N 份输入，就是同一轮的 N 个 task。源码：pregel/_loop.py 的 tick()+after_tick() 合起来就是一圈，_algo.py 的 prepare_next_tasks() 决定"这轮谁行动"。

易踩坑recursion_limit 限制的是超级步数
它不是 Python 递归深度。带循环的图（比如 ReAct 循环）完全合法；报 GraphRecursionError 通常说明你的循环没收敛，或者限额与工作量不匹配——而不是"递归写错了"。
源码入口：libs/langgraph/langgraph/pregel/（main.py 入口 · _loop.py 的 tick()/after_tick() · _algo.py 的 prepare_next_tasks()/apply_writes()）

3.4 Checkpoint —— 存档系统与 Durable Execution

类比理解游戏存档文件。要唯一定位一个存档，需要三个坐标：thread_id（哪一局的存档槽）+ checkpoint_ns（哪个子关卡——用来区分嵌套的子图）+ checkpoint_id（这一局里的第几个存档）。Durable Execution（耐久执行）就是靠它实现的：崩了重开，从存档继续。
存档里有什么作用
channel_values状态的快照——每个"盒子"里当前装的是什么
channel_versions每个盒子更新到了第几版，判断"数据变没变"
versions_seen每个节点已经"看过"哪个版本——决定下一圈该唤醒谁
pending writes任务级的中间写：成功结果、错误、中断标记……恢复时用来跳过已成功的任务
✗ Python 执行现场不保存栈帧——这正是"恢复后节点从头重跑"的根本原因

持久化分两层：put_writes 在每个任务完成时立刻记下它的中间写；put 在整个超级步结束后写下完整的新存档。好处是：同一步里部分节点成功、部分失败时，恢复可以跳过已成功的，只重跑失败的。

存档插件（Saver）存哪适用
InMemorySaver内存测试与调试——进程退出即清空，不是生产存储
SqliteSaver单个 SQLite 文件本地开发、低并发
PostgresSaverPostgres 分表存储生产环境——首次使用要显式调用 setup() 建表
小澄清：Checkpoint 是按超级步存的吗？——实际是两层

"CP 只按超级步存"是个常见误解，实际是两层：task 级——每个 task 一结束，它的 writes 立刻通过 put_writes 记为 pending writes；superstep 级——整轮全部跑完、合并之后，才由 put 写完整快照（_loop.py 的 after_tick() 里，源码注释就叫 # finish superstep）。

为什么不能只在超级步边界存？为了部分失败的恢复粒度：假设一轮里 3 个 task 成功了 2 个、失败了 1 个，进程崩了——恢复时加载上一步的完整存档，再凭 pending writes 认出"哪些已经成功"，只重跑失败的那 1 个。如果只有超级步级存档，崩溃就得整轮全部重来。

例外：durability 设为 exit 时，put_writes 也不立即落盘（攒到图退出统一写），那种模式本来就不追求中途可恢复。一句话记忆：superstep 是存档点，task 是存档点之间的进度条。

小澄清：存档的"时机"也能调？
能。durability（持久化时机）有三档：sync（下一步开始前必须落盘，恢复点最强）、async（落盘与下一步重叠，吞吐更高）、exit（图退出时才统一落盘）。默认是 async。另外提醒一句：启用了 checkpointer 但不传 thread_id，是建立不起可恢复线程的。
源码入口：libs/checkpoint/langgraph/checkpoint/（base 合约 · memory 内存实现）· libs/checkpoint-sqlite/ · libs/checkpoint-postgres/

3.5 Interrupt 与 Stream —— 与人类交互的接口

LangGraph 把"等人"做成了第一公民机制，分两种用法：

用法在哪声明语义
静态：interrupt_before / aftercompile 或调用时"在某节点执行前 / 执行后暂停"——适合固定的审批点
动态：interrupt(value)节点代码内部"运行到这一行时暂停"，并把 value 抛给调用方展示——适合"看了数据才知道要不要问人"

两者都用 Command(resume=...) 恢复（见第 2 章 Step 5）。而 Command 本身是个多面手，四个维度可以组合：update（改状态）、resume（递交恢复值）、goto（跳到指定节点或 Send）、graph（作用于当前图或上抛父图）。

小澄清：interrupt 中断在半路，存档怎么写？

结论先行：不写新的完整 checkpoint——那个超级步没走完（异常抛出后，负责合并与存档的 after_tick() 被整个跳过），状态没变化，本来也不需要新存档。但中断信息不会丢：它被转成一条 task 级写入，挂在上一份完整存档上。

# 中断后的磁盘状态： 上一份完整 checkpoint（上一个超级步的状态快照，原封不动） └─ pending writes: (task_id, "__interrupt__", Interrupt(value=..., id=...))

机制：节点里 interrupt(value) 抛出异常 → 执行器把它转成对保留通道 __interrupt__ 的写入（_runner.py 的 commit()，注释就叫 "save interrupt to checkpointer"）→ 走 put_writes 立即落盘。静态 interrupt_before 更简单：在准备任务的 tick() 里就抛出，一个任务都没跑，"上一份存档 + 中断点配置"已完整描述暂停位置。

恢复时加载存档和 pending writes、重建那个被中断的 task，interrupt() 原地返回 resume 值，这一步走完才产生新的完整存档——这正是"恢复后节点从头跑"（第 4 章误解二）和"第一次调用返回里带 __interrupt__"背后的机制。

再说 Streaming（流式输出）：它不是"加个日志开关"，而是运行时的数据平面——你想看什么粒度，就订阅什么 mode：

mode输出什么典型用途
values每步之后的完整状态状态全量视图
updates每个节点产出的增量UI 增量刷新、执行轨迹
messagesLLM 的逐 token 消息聊天打字机效果
custom节点通过 stream_writer 主动发的自定义事件进度条、业务事件
debug组合调试事件开发期全景（数据量最大）
小澄清：time-travel 是调试玩具还是正经能力？
正经能力。指定历史 checkpoint_id 从旧状态继续执行，等于 replay（重放）或 fork（分叉）：回到审批前改选"拒绝"、回到出错前换个输入重试，都走这条路。它和 update_state 一样，都是在历史线上创建新的存档节点，而不是原地修改数据库记录。
源码入口：libs/langgraph/langgraph/types.py（interrupt · Command · Send）· libs/langgraph/langgraph/stream/

3.6 上层建筑：Prebuilt、Functional API、SDK / CLI

前面五个模块是内核。这一节看三类"建在内核之上 / 伸向内核之外"的东西。

Prebuilt预制房：ReAct Agent 只是一张编译好的图
create_react_agent 没有引入任何新机制——它就是用 StateGraph 帮你画好了一张"模型思考 → 有工具调用就去执行工具 → 回来接着想……"的循环图；ToolNode 负责并行执行模型发起的多个工具调用。注意：它已被标记迁往 langchain.agents.create_agent——内部结构仍值得读（是理解"Agent 循环如何降解为普通图"的最好样例），但新项目请先评估目标 API。
Functional API写成函数的样子，跑同一个内核
@entrypoint 把一个普通 Python 函数包装成可执行的图；函数里的 @task 调用会变成可并行的任务。控制流天然就是 if/else 和 for，适合"用代码表达流程更顺手"的场景；需要可视化、显式路由、统一状态结构时，还是选 StateGraph。两者共用同一套 Pregel / checkpoint / interrupt / streaming——Functional 不是"轻量但不可恢复"的旁路。
SDK / RemoteGraph / CLI远程边界：Server 在另一个仓库
生产级部署通常跑在 LangGraph Server（本仓库之外）上。sdk-py 提供 threads / runs / store 等 HTTP/SSE/WebSocket 客户端；RemoteGraph 把"远程图"包装成可以塞进本地图里的节点——但真正的执行、存档、排队都发生在 Server 端；cli 则把 langgraph.json 编译成本地开发服务或容器镜像（new / dev / validate / build / up / deploy）。
展开看：ReAct 预制图长什么样
# create_react_agent 编译出的图，骨架就这么简单： START → agent（调用模型） │ 模型输出里有 tool_calls 吗？ 有 ────┴──── 没有 ▼ ▼ ToolNode 结束（END） （并行跑工具） │ └──────► 回到 agent（下一圈思考）
所谓"Agent 循环"，在 LangGraph 里就是一张带条件边和循环的普通图——因此它自动获得存档、中断、流式和恢复能力，一行额外代码都不用写。
源码入口：libs/prebuilt/langgraph/prebuilt/（chat_agent_executor.py · tool_node.py）· libs/langgraph/langgraph/func/ · libs/sdk-py/ · libs/cli/
04

设计哲学与边界

理解了"怎么跑"，再看"为什么这么设计"。下面四条是贯穿整个项目的铁律，也是新手最容易读偏的地方。

4.1 确定性骨架 + Agentic 决策

流程的骨架——节点、边、审批点——是显式、可审计的；LLM 则在节点内部决定"下一步去哪"（通过条件边、Command、Send 在运行时动态改变走向）。模型的不确定性被关在确定性的骨架里：你可以不知道模型会输出什么，但永远知道流程可能走到哪、必须经过哪些关卡。

4.2 状态是一等公民，执行现场不是

所有可恢复性都建立在"可序列化、带版本的状态"之上，而不是"函数执行到哪一行"。这是同一个设计决策的两面：正因为 checkpoint 只保存状态不保存栈帧，才能跨进程、跨机器、跨时间恢复——代价是"恢复后节点从头重跑"，副作用的幂等管理成了你的责任。

4.3 本仓库 ≠ LangGraph 的全部

本仓库 = 核心运行时 + 持久化实现 + Python SDK + CLI。生产环境的队列、多租户、鉴权、托管部署属于仓库之外的 LangGraph Server / 平台层。读代码时如果觉得"这个功能怎么没有"，很可能它本来就在 Server 侧。反过来：SDK 能调用的服务端能力，也不等于本地运行时自带。

4.4 版本并存是常态，读码先问"默认吗、稳定吗"

create_react_agent 正在迁往 LangChain；Streaming 有 v1 / v2 / v3 三代接口并存（v3 仍是实验面）；DeltaChannel 还是 beta。源码里存在某个能力，不等于它默认启用、更不等于它是新项目的推荐选择。对外集成时固定接口版本，别依赖"默认值永远不变"。

常见误解一：Checkpointer 可以顺便当长期记忆库？
不可以。Checkpointer 服务的是单条执行线程的恢复；跨会话的用户记忆应放进 Store（namespace + key + value，可选语义检索）。一个管"执行到哪了"，一个管"记住了什么"——混用会让记忆和线程生命周期绑死。另有一个 Cache（节点结果缓存），管的是"同样的输入别重复算"，三者职责互不重叠。
常见误解二：interrupt 之后是从断点"继续"？
不是"继续"，是"带着答案重走"。节点从头重新执行，interrupt() 调用处直接拿到 resume 值。请把每个 interrupt 点看成"可重放边界"：边界之前的副作用会被再执行一次，要么幂等，要么挪到边界之后。
常见误解三：节点并行跑，一切自动安全？
状态合并是安全的——由 Channel reducer 保证，写错了会大声报错。但外部世界的副作用（两个工具同时写同一个数据库、同时调同一个外部 API）不受 Channel 保护，需要你在工具层自己做幂等键、锁或依赖拆分。

5.1 先跑起来：20 行的"人工审批"最小版

这是第 2 章故事的极简版（去掉查订单和风控，只保留审批与执行）。第一次 invoke 会停在 interrupt，第二次用 Command(resume=...) 恢复：

# pip install langgraph from typing_extensions import TypedDict from langgraph.graph import StateGraph, START, END from langgraph.checkpoint.memory import InMemorySaver from langgraph.types import interrupt, Command class State(TypedDict): amount: int approved: bool def human_approval(state: State): # 运行到这里会暂停，把括号里的内容抛给调用方；恢复时返回审批结果 decision = interrupt({"amount": state["amount"], "question": "是否批准退款？"}) return {"approved": decision == "approved"} def execute_refund(state: State): print(f"已退款 ¥{state['amount']}") g = StateGraph(State) g.add_node("human_approval", human_approval) g.add_node("execute_refund", execute_refund) g.add_edge(START, "human_approval") g.add_edge("human_approval", "execute_refund") g.add_edge("execute_refund", END) graph = g.compile(checkpointer=InMemorySaver()) cfg = {"configurable": {"thread_id": "t1"}} print(graph.invoke({"amount": 3000, "approved": False}, cfg)) # 停在 interrupt print(graph.invoke(Command(resume="approved"), cfg)) # 恢复并跑完

跑起来后，重点看两处：第一次 invoke 的返回里带着 __interrupt__（里面就是你 interrupt 时抛出的内容）；第二次 invoke 之后"已退款 ¥3000"被打印。注意：InMemorySaver 把存档放在内存里，本示例支持的是同一进程内的暂停-恢复；想跨进程重启恢复，把 saver 换成 SqliteSaver / PostgresSaver 即可，代码其余部分一行不用改。

5.4 常见问题（FAQ）

恢复之后，某个节点为什么"多执行了一次"？
这是机制不是 bug：恢复时中断所在的节点从头重跑（checkpoint 不保存栈帧）。该节点在 interrupt 之前的副作用会再执行一次——把它们做成幂等，或挪到 interrupt 返回之后。
必须连 LangSmith 才能用吗？
不必须。本地核心完全独立运行；LangSmith 提供的是可观测、评估与部署等增强能力，属于集成层，不是运行前提。
checkpointer 怎么选？
调试用 InMemorySaver（进程退出即清空）；单机本地用 SqliteSaver；生产用 PostgresSaver——记得首次显式调用 setup() 建表，并且调用时务必带上 thread_id。
设了 interrupt_before，为什么有时不暂停？
静态中断只在"目标节点被触发、且相关状态自上次中断后确实变化过"时生效——这是刻意设计，防止恢复后立刻在原地再次中断。先确认触发条件和状态版本，再怀疑配置。
我想给系统加新能力，从哪下手？
最常见的需求（加业务节点）零门槛——节点就是普通函数。更深的扩展面（自定义 Channel / Saver / Store / 缓存 / 工具治理 / 流转换器）各需要实现哪个接口、最低要验证什么，见深度解析的第十八章扩展点清单。
