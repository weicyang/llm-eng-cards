CHAPTER 00

阅读约定与核心结论

本文不是 API 清单，也不逐文件复述实现。它以一次 Agent 运行的真实主链为骨架， 再把状态、上下文、工具、安全、远程执行和工程治理放回这条主链中解释。类名和方法名用于 定位实现边界，而不是替代源码。

一句话心智模型
SDK 定义协议与编排，Tools 提供能力，Workspace 提供执行环境，Agent Server 提供远程运行时；无状态的 Agent 驱动有状态的 Conversation，所有可恢复语义落在事件树和状态快照上。

Agent 是配置

Agent 的 Pydantic 字段被冻结，持有 LLM、工具规格、Condenser、Context 与策略；会话事实不写入 Agent 字段。

Conversation 是运行时

拥有状态、事件树、Workspace、回调、插件生命周期、锁和中断任务。

Event 是事实

消息、Action、Observation、压缩、Hooks 与状态更新都通过事件表达和传播。

四条主线

  1. 控制线：Conversation 状态机决定什么时候继续、暂停、确认、结束或报错。
  2. 数据线：活跃事件分支经 View 与 Condenser 转成 LLM Messages。
  3. 执行线：LLM tool call 变成 Action，经 PreToolUse、安全与确认后，由 ToolExecutor 在当前执行环境中产生副作用；具体工具不保证经 Workspace API 转发。
  4. 传播线：事件写入本地 EventLog，或经 EventService 通过 WebSocket 镜像到远程客户端。

CHAPTER 01

项目定位与设计原则

这个仓库不是面向最终用户的完整 IDE 产品，而是可复用的 Agent 基础设施。 它需要同时服务本地脚本、容器化工作区、远程 SaaS、CLI 和其他下游应用，因此核心代码刻意保持 产品中立：SDK 的 Settings schema 描述结构与语义，但不承载 GUI 排序、图标和交互组件。

官方论文与证据优先级
直接描述本仓库 V1 架构的是 MLSys 2026 论文 The OpenHands Software Agent SDK: A Composable and Extensible Foundation for Production Agents。 ICLR 2025 的 OpenHands 平台论文 描述旧 V0，ICML 2024 的 CodeAct 论文 解释代码动作思想；后两者只能用于理解历史，不是当前 API、类结构或部署契约。 本文仍按“当前源码与测试 ＞ Schema/协议 ＞ 官方论文 ＞ 既有文章”的顺序裁决冲突。

从 V0 问题到 V1 原则

强制沙箱 → 可选隔离

默认本地同进程便于开发和 MCP 接入；需要安全或资源边界时再切换 Docker、Cloud 或其他远端 Workspace。

配置蔓延 → 状态集中

Agent 配置与 Conversation 会话事实分离，以 EventLog 与状态快照支撑恢复；但“不可变”不能扩写到整个嵌套对象图。

核心与应用混杂 → 关注点分离

CLI、GUI、SaaS 和评测不再把产品分支塞进 Agent 核心，而是共同消费 SDK 边界。

单体扩展 → 双层组合

部署层组合 SDK、Tools、Workspace、Server；能力层替换 Tool、LLM、Context、安全策略与 Agent。

协议与实现分离

Tool 是可持久化规格，具体实现通过 registry 延迟解析；SDK 不反向依赖工具包。

RemoteWorkspace 定义远端协议，Docker/Cloud/Apptainer 等后端在独立包实现。

可变状态集中

Agent 字段被冻结；事件、HEAD、secrets、执行状态与待确认动作集中在 ConversationState。

LLM 当前不是 frozen 模型，还持有 Metrics、运行时元数据缓存和 fallback 临时状态；它不属于会话事实，但也不能被描述为深度不可变对象。

同步/异步对称

关键路径都有 sync/async 版本；基类通常允许异步方法委托同步实现，自定义扩展不必一次实现两套。

兼容性优先

公共 Python API、REST、Settings 持久化和历史事件分别有清晰的演进策略与 CI 门禁。

设计洞察
“稳定”不是靠禁止变化，而是把变化限制在明确边界：模型差异进入 feature registry， 工具差异进入 registry，持久化变化进入 migration，部署差异进入 Workspace。

CHAPTER 03

核心运行时心智模型

Agent 是「怎么想」的声明（模型、工具规格、策略），ConversationState 是「发生过什么」的事实（事件树、进度、预算）。SDK 的大部分复杂度都来自坚持这条分界线——因为只有事实是可序列化、可恢复的。

Conversation(...) ← 唯一公共入口，按 Workspace 类型分流 │ ┌────┴──────────────────────────┐ ▼ ▼ LocalConversation RemoteConversation （进程内执行 Agent） （HTTP/WS 代理到 agent-server） │ │ 状态是镜像，不是本体 │ └─ WS 事件流 + REST 状态，最终 reconcile ▼ ┌─ Agent（声明层，可序列化，跨会话复用）──────────────────────┐ │ LLM + model features + retry/fallback │ │ Tool 规格（Tool(name, params)，还不是可执行体） │ │ Condenser · AgentContext · Critic · 提示词安全策略 │ └───────────────────────────┬──────────────────────────────────┘ │ AgentBase._initialize —— 两者的接缝 │ 把规格解析成绑定当前 State 的 ToolDefinition │ 并把运行期 MCP 工具并入 tools_map ▼ ┌─ ConversationState（事实层，落盘，恢复的唯一依据）──────────┐ │ EventLog（全部事件）+ leaf_event_id（当前 HEAD） │ │ 活跃 View = path_to_root(leaf) │ │ execution_status · 迭代 · 预算 · 统计 │ │ workspace · secrets · SecurityAnalyzer · ConfirmationPolicy │ │ pending / blocked actions · 持久化回调 │ └──────────────────────────────────────────────────────────────┘ 落盘形状：base_state.json（快照） + events/event-NNNNN-id.json（逐事件） 恢复：读快照 + 重放事件 → 重建 View → agent.verify 校验类型与工具兼容

3.2 Agent 与 State 的边界

Agent / LLM：声明、模型与策略

  • LLM 及其模型能力、重试和 fallback
  • 工具规格、过滤规则、内置工具
  • Condenser、AgentContext、Critic
  • Agent 提示词安全策略与工具准入声明

ConversationState：事实与进度

  • 事件树、当前 leaf/HEAD、活跃 View
  • 执行状态、迭代、预算、统计

CHAPTER 04

从用户消息到完成：端到端执行主链 子文档

4.1 初始化不是构造时一次性完成

LocalConversation 构造时创建或恢复 State，并组装事件回调链；插件、文件型 agents、MCP 与 hooks 则在第一次 send_message() 或 run() 时懒加载。 这样构造对象本身不必完成网络或磁盘扩展发现，也能保存 plugin 的解析结果用于确定性恢复。 

Conversation(...)
  → ConversationState.create()          新建或恢复 base_state + EventLog
  → 组装 _on_event 回调链

send_message(...)
  → 确保 Agent/Plugins 已准备
  → 可选追加 user message skill suffix
  → MessageEvent(source="user")
  → hooks / callbacks / append_event

run() 或 arun()
  → execution_status = RUNNING
  → while:
      → Agent.step() / Agent.astep()
      → 根据响应产生事件或执行工具
      → 检查确认、预算、迭代、卡住和终止条件

4.2 Agent 的一步

检查未匹配 Action
→
View + Condenser
→
LLM Completion
→
响应分类
→
Event / Tool Batch

一步开始时优先处理历史中尚未得到 Observation 的 Action。这是恢复与确认机制的关键： Action 已经持久化，但执行可能因用户确认、进程重启或中断而延后。只有没有 pending action 时才发起新 LLM 调用。

响应分类处理状态结果
TOOL_CALLS解析并写 ActionEvent，经过 Hooks/确认后并行执行继续、等待确认或 Finish
CONTENT写 Agent MessageEvent通常 FINISHED
REASONING_ONLY保留消息并注入环境提示，要求给出可执行动作继续
EMPTY注入纠正性反馈继续或达到上限

4.3 同步与异步

sync : LocalConversation.run  → Agent.step  → LLM.completion/responses
async: LocalConversation.arun → Agent.astep → LLM.acompletion/aresponses
                                             → LiteLLM async transport

async 不是简单在线程池包住整个同步循环：LLM、Condenser、工具批处理和 token callback 都有异步通道。 Tenacity 能原生包装 coroutine，所以重试逻辑没有另造一条“async retry”实现。

CHAPTER 05

状态机、事件树与恢复 子文档

5.1 执行状态机

IDLE ── run ──► RUNNING ──┬──► FINISHED
                           ├──► WAITING_FOR_CONFIRMATION
                           ├──► PAUSED
                           ├──► ERROR
                           └──► STUCK

FINISHED / STUCK ── send_message ──► IDLE
删除生命周期：DELETING
is_terminal = FINISHED | ERROR | STUCK     （IDLE 不是终态）

FINISHED 表示当前任务完成，不等于 Conversation 永久关闭；新的用户消息可以让会话回到 IDLE。WAITING_FOR_CONFIRMATION 是显式中间态，下一次 run 才执行已确认的 pending actions。

把事件记成树而不是列表，换来的是一个很实际的能力：可以退回某一步换个走法，而不丢掉原来那条路的记录。代价是「历史」从此有两个含义——磁盘上的全部事件，和当前分支上模型能看到的那部分。

e1 ── e2 ── e3 ── e4 ── e5 ← 原分支（仍在磁盘上） │ └── e3' ── e4' ← fork 后的新分支 ▲ leaf_event_id（当前 HEAD） path_to_root(leaf) = [e1, e2, e3', e4'] ← 这才是发给 LLM 的活跃分支 navigate / fork 只改 HEAD，从不删除旁支 ┌─ 事件的两个人群 ───────────────────────────────────────────┐ │ LLM 可见：SystemPrompt · Message · Action · Observation │ │ AgentError · UserReject → 可转成 Messages │ │ 仅运行时：Interrupt · Pause · Condensation · HookExecution │ │ ConversationStateUpdate → 服务客户端与观测 │ └─────────────────────────────────────────────────────────────┘ │ ▼ View：从活跃分支派生的只读投影，额外维持 provider 要求的结构 · Observation 唯一性 · 批次原子性 · tool_call ↔ tool_result 配对 · tool loop 原子性 Action–Observation 配对不变量 未匹配的 Action = 「还有活没干完」的判定依据 中断时给未执行的调用补 AgentErrorEvent ——否则下次发给严格 provider 的 tool history 结构直接畸形，400 起步

5.2 事件不是列表，而是树

每个事件带 parent_id。State 的 leaf_event_id 指向当前 HEAD， path_to_root(leaf) 形成活跃分支；fork 和 navigate 不会删除旁支，只改变当前 HEAD。 发给 LLM 的 View 来自活跃分支，而不是磁盘上全部事件。

LLM 可见事件

SystemPrompt、Message、Action、Observation、AgentError、UserReject 等可转换为 Messages。

控制与观测事件

Interrupt、Pause、Condensation、HookExecution、ConversationStateUpdate 等服务运行时与客户端。

5.3 Action–Observation 配对不变量

每个可执行 Action 最终都应有对应 Observation。确认前、执行中断或崩溃恢复时， 未匹配 Action 是系统判断“还有工作待完成”的依据。中断会给尚未执行的调用补 AgentErrorEvent，避免下一次发给严格 provider 的 tool history 结构畸形。

5.4 持久化形状

  • base_state.json：Agent、执行状态、secrets、HEAD 等状态快照。
  • events/event-NNNNN-id.json：独立事件文件组成 EventLog。
  • 恢复时读取快照和事件，重建 View，并通过 agent.verify 检查类型和工具兼容。
历史事件兼容是永久义务
公共 API 可以在完整弃用窗口后移除，但已经持久化的旧事件必须始终可加载； deprecated field handler 不能按普通技术债清理。
CHAPTER 06

上下文工程：View、Prompt Sections 与 Skills 子文档

6.1 View 是受约束的 LLM 历史

View 是从活跃事件分支派生的只读模型，并通过属性系统维持 provider 需要的结构： Observation 唯一性、批次原子性、tool call matching 和 tool loop 原子性。 这层约束把“事件记录正确”与“LLM 历史合法”分离，恢复时可以重建和修复 View。

System Prompt 拆成 STATIC 与 DYNAMIC 两个 cache tier，不是为了代码整洁，而是为了让缓存断点落在一个真正稳定的位置——所有随会话变化的内容（仓库信息、skills catalog、日期）都必须排在静态段之后，否则前缀每次都不同，缓存等于没有。

6.2 Prompt Registry

System Prompt 不是单个巨型模板，而由 PromptSection 注册表组合。 每个 section 有 guard 与 render，并标记 STATIC 或 DYNAMIC cache tier。

层典型内容目的
StaticAgent 能力边界、工具使用原则、通用行为指令跨会话稳定，利于 prompt cache
Dynamic仓库信息、skills catalog、secrets 名称、日期、memory、用户 suffix随会话与环境变化
User suffix触发后的 skill 正文、任务特定附加上下文按需披露，避免常驻 token 成本

6.3 Progressive Disclosure

AgentSkills 先以名称和不超过 1024 字符的 description 出现在 <available_skills> 中；只有触发器命中或模型调用 invoke_skill 后，完整内容才进入上下文。Skill location 故意不直接暴露， 以维持统一调用入口和可观测性。

这个机制叫 Progressive Disclosure（渐进披露：能力目录常驻上下文，正文按需加载）。 它把「模型知道有这个能力」和「模型手上有这个能力的完整说明」拆成两件事——前者是每轮都要付的固定成本， 后者只在真正用到时才付。技能库越大，这个拆分省下的 token 越多。

示例场景：一个装了 40 个 Skill 的 Agent，如果把所有 SKILL.md 正文都塞进 system prompt， 按每篇约 1,200 token 计就是 48k 常驻开销，且每一轮都要重付。改用渐进披露后，常驻部分只剩 40 条 「名称 + ≤1024 字符描述」，约 6k token；一次任务平均只会触发 1–2 个 Skill 正文加载，实际峰值在 9k 上下。 省下的不只是钱：注意力不再被 38 篇无关文档稀释，工具选择的准确率也跟着回升。 代价是多一次 invoke_skill 往返，以及必须把 description 写到「光看这一句就能判断该不该用」的程度。
上下文工程的目标
不是把所有信息塞给模型，而是在结构合法、token 可控、缓存友好和任务相关之间做可恢复的选择。

CHAPTER 08

Condenser 与分层恢复策略 子文档

8.1 Condenser 是 View 转换器

CondenserBase.condense 接收 View，返回新的 View 或一条 Condensation。 RollingCondenser 区分 soft/hard 策略；LLMSummarizingCondenser 根据事件数、token 或显式 CondensationRequest 调用独立摘要 LLM；PipelineCondenser 可以组合多个阶段。

Condenser 的定位很克制：它是一个 View → View 的转换器，不碰 EventLog。所以压缩失败最坏也只是这一轮 View 没变短，磁盘上的事实一个字都没丢。

下面这张阶梯表最值得记住的是它的排序逻辑：越靠上的手段越便宜、越不改变历史。 遇到一次 provider 报错时，正确的反应顺序是先问「这是不是瞬时故障」（retry）， 再问「换个模型行不行」（fallback），然后才是「要不要往历史里写点东西」（nudge / condensation）。 直接跳到压缩，既贵又会不可逆地丢掉细节。

8.2 错误恢复阶梯

层级触发动作是否改变历史
Transport retry连接、限流、超时、服务不可用、空响应Tenacity 指数退避；确定性空响应可调整 temperature否
Fallback主模型失败且配置备用策略选择备用 LLM，合并成本否
Soft nudge函数参数错误、内容策略、无动作写纠正性用户消息，继续循环新增事件
Condensation上下文超限或历史畸形重建 View，发 CondensationRequest，摘要/裁剪产生压缩事件
Hard error无法恢复或没有合适 condenser状态 ERROR，ConversationErrorEvent记录失败
Malformed history 不等于 context overflow
两者都可能通过压缩恢复，但错误类型独立，便于识别 tool_result 缺失、重复等事件流问题， 不应把所有 provider 400 都归因于 token 超限。

并行执行工具的真正难点不是并发本身，而是「两个工具会不会踩到同一个东西」。SDK 的答案是让工具自己申报要用的资源，不申报的一律按工具名整体互斥——保守，但绝不会错。

9.2 并行工具与资源锁

一次模型响应可以包含多个 tool calls。ParallelToolExecutor 并发执行，但通过 DeclaredResources 避免冲突：

  • 工具未声明资源：按 tool:<name> 互斥，安全但保守。
  • 声明空资源集合：允许无锁并行，适合只读 grep 或独立终端池。
  • 声明具体 key：按文件路径、终端 session 等粒度加锁。
  • Observation 按原 tool call 顺序发出，使历史稳定、可复现。

CHAPTER 10

安全分析、确认策略与 Hooks 子文档

SecurityAnalyzer 回答「这件事有多危险」，ConfirmationPolicy 回答「多危险才需要问人」。两个问题分开，就能在不改分析逻辑的前提下，让同一个 Agent 在开发机上一路放行、在生产环境上逢写必问。

10.1 两阶段工具执行

LLM tool_calls
  → 构造 ActionEvent
  → PreToolUse Hook
      └─ 拒绝：不写入 EventLog
  → 放行的 ActionEvent 持久化
  → SecurityAnalyzer 评估风险
  → ConfirmationPolicy.should_confirm(risk)
      ├─ 否：执行
      └─ 是：WAITING_FOR_CONFIRMATION
              ├─ 用户确认 → 下次 run 执行 pending action
              └─ 用户拒绝 → UserRejectObservation

SecurityAnalyzer 与 ConfirmationPolicy 分责：前者判断风险，后者决定哪些风险必须确认。 分析器异常时倾向 HIGH 风险，属于 fail-safe；但默认 policy 是 NeverConfirm，因此分析失败并不自动阻断。 单独的 Finish/Think 调用通常不要求确认。

10.2 Hooks 是生命周期控制面

Hooks 可介入 UserPromptSubmit、PreToolUse、PostToolUse、SessionStart、SessionEnd 和 Stop。 PreToolUse block 与用户拒绝共享 Observation 语义，但带不同 rejection source；Stop hook 甚至可以拒绝 Agent 结束，把状态从 FINISHED 拉回 RUNNING 并注入反馈。

execute_tool 的边界
直接调用 Conversation 的工具执行旁路不会经过完整 Agent loop 与确认流程。 它适合受控程序化调用，不应被误认为与模型发起工具调用拥有相同安全语义。
示例场景：一个团队把 SDK 接进 CI 做自动修复，验收时发现「安全分析明明标了 HIGH，动作还是执行了」。 根因不是分析器失灵，而是默认 ConfirmationPolicy 是 NeverConfirm—— 分析器 fail-safe 地把异常判为 HIGH 是一回事，有没有人拦是另一回事，这两层默认值恰好一松一紧。 修法是给 CI 环境显式换成按风险等级确认的 policy，并把无人值守场景的「确认」实现为直接拒绝而不是无限等待 （否则 pipeline 会挂在 WAITING_FOR_CONFIRMATION 直到超时）。 这里的一般规律是：fail-safe 的默认值只在有人看着的时候才成立，自动化场景必须重新审一遍每一层默认。
  • 把风险判定（SecurityAnalyzer）和拦截阈值（ConfirmationPolicy）分开配置，按环境切换后者而不是改前者。
  • 工具尽量声明精确的 DeclaredResources，把并行粒度交给运行时决定。
  • 用 Hooks 表达组织级规则（禁止 force push、写操作前必须跑测试），而不是把它们塞进 system prompt。
  • 新增 provider 特例优先进 model_features 能力注册表，别散落进 LLM 主链的 if 分支。
  • 不要用 execute_tool 旁路替代正常工具调用，它绕过了 Hook 与确认，两者安全语义完全不同。
  • 不要把所有 provider 400 都当成上下文超限去压缩——malformed history 是独立错误类型，压缩治不了它的根因。
  • 不要清理已持久化事件的 deprecated field handler，旧事件必须永远可加载，这条兼容义务没有弃用窗口。
  • 不要在 Bedrock IAM/SigV4 模式下把 LLM.api_key 当 bearer token 转发，认证方式不同，只会得到难查的 403。
  • 不要假设 FINISHED 意味着会话结束，Stop hook 可以把它拉回 RUNNING，客户端状态机要能接住这种回退。
CHAPTER 11

Workspace、远程执行与 Git Worktree 子文档

11.1 统一工作区接口

BaseWorkspace 为显式调用方提供 working directory、命令、文件和 Git 能力；具体 ToolExecutor 通常由 Agent 在当前进程直接调用，并不保证通过 Workspace 方法执行。 LocalWorkspace 的显式 API 直接操作主机；RemoteWorkspace 把相应命令、文件和 Git 请求映射到 agent-server。 Docker/Cloud 等后端的职责是启动或获得一个远端执行环境，再复用 RemoteWorkspace 协议。

11.2 路径有两种语义

  • Source/Wire：is_absolute_path_source 识别 POSIX 和 Windows 形式；远程 URL 使用 slash-normalized path。
  • Host filesystem：本地写盘和 File Editor 必须遵循当前主机原生绝对路径语义。

这一区分防止 POSIX 主机把 C:\... 当成可创建的本地路径，也防止 Windows 反斜杠泄漏到远程 Git API query。

11.3 Conversation Worktree

服务端可为 Git workspace 创建 /tmp/conversation-worktrees/<conversation_id>/<repo_name>。 如果初始 workspace 指向仓库子目录，工作树内保留同样相对路径。这样每个会话拥有隔离分支， 又不必复制整个仓库对象库。

14.1 服务分层

OH_DEFERRED_INIT 让进程先以 dormant 状态启动，编排器再通过 POST /api/init 注入用户配置。状态为 dormant → initializing → ready， 初始化失败回滚 dormant；未 ready 的 /api/* 返回 503。

探测只看状态码
5xx handler 可能重写响应 detail；warm-pool 编排器应把 HTTP 503 作为权威信号。

14.4 并发与资源生命周期

  • Conversation lease 防止共享存储上多实例同时拥有同一会话。
  • Idle eviction 卸载无 run、无外部 WS 的内存对象，下次请求再 hydrate。
  • 若恢复时状态仍是 RUNNING，视为前进程异常退出，转 ERROR 并修补 orphan actions。
  • 异步路由不能在 event loop 上直接等待 ConversationState 的同步 FIFO lock，应移入 worker thread。
CHAPTER 15

RemoteConversation：状态镜像与终止竞态 子文档

15.1 远程路径

RemoteConversation
  → POST /api/conversations
  → WebSocket connect + auth + initial full state
  → POST /events                    send_message
  → POST /run                       server EventService.run
       → LocalConversation.arun
       → events via PubSub / WS
  ← RemoteEventsList + RemoteState
  ← post-run FULL_STATE snapshot    authoritative completion

远程客户端不执行 Hooks、LLM 或工具，只保存服务端状态的镜像。REST 用于命令和补偿式查询， WebSocket 用于低延迟事件传播；结束前会 reconcile 事件列表，弥补断线或分页差异。

15.2 为什么第一次 FINISHED 不可信

Agent step 可以先把状态设为 FINISHED；run 循环随后才执行 Stop hooks。 若 Stop hook 拒绝停止，状态会回到 RUNNING 并再跑一轮。因此字段级 WS 或 REST 看到的 FINISHED 只是 hint，不是 run task 已退出的证明。

  1. 客户端在 POST /run 后才 arm completion gate，忽略连接时的初始快照。
  2. EventService 等 arun 结束并 flush pending events 后发布完整状态快照。
  3. armed 后收到的 post-run FULL_STATE 且状态非 RUNNING，才是权威完成信号。
  4. ERROR/STUCK 仍可立即抛错。
  5. 若 WS 丢失，REST 连续报告终态 30 秒后启用 hard fallback，防止永久挂起。

15.3 Interrupt 全链路

RemoteConversation.interrupt
  → REST interrupt
  → ConversationService
  → EventService.interrupt
  → LocalConversation.interrupt
      → CancellationToken.cancel()
      → asyncio Task.cancel()
  → CancelledError 沿 LLM/Agent 传播
  → arun 捕获：PAUSED + InterruptEvent + orphan action 修补
  → post-run full state

Pause 只是请求在当前 step 自然结束后暂停；Interrupt 取消在途 async task，并通知可中断工具， 因而语义和成本不同。

Pydantic secret 的序列化、解密和 redaction 统一由 pydantic_secrets.py 完成。没有 cipher 时不应假装能恢复明文； LookupSecret 的 hostless URL 由 agent-server 注入的 OH_INTERNAL_SERVER_URL 解析到当前实例。

16.4 四种兼容表面

  • Python API：公共导出和类成员移除需弃用，移除版本至少晚 5 个 minor；破坏变化至少 MINOR bump。
  • Pydantic Field default：作为行为兼容变化单独报告并要求 release note。
  • REST/OpenAPI：不兼容替换同样需要 5 minor runway；优先 additive 或 versioned contract。
  • Event persistence：比 API 更严格——历史数据必须永久可加载。

CHAPTER 18

设计模式、关键权衡与二次开发 子文档

18.1 可识别的架构模式

Event Sourcing Lite

事件是可恢复事实，但仍保留 base_state 快照加速加载，不追求纯事件溯源。

Ports and Adapters

LLM transport、Workspace、ToolExecutor、SecurityAnalyzer 都通过边界接口替换。

Registry / Plugin

工具、prompt sections、subagents、marketplace 用注册与发现扩展，核心主链保持稳定。

State Machine

运行、确认、暂停、终止和删除都有显式状态，避免靠散落布尔值推断。

Bulkhead

子 Agent 独立 Conversation；并行工具按资源锁隔离；server lease 防双 owner。

Layered Recovery

retry、fallback、nudge、condensation、hard error 各处理不同故障域。

18.2 关键权衡

选择获得代价
Agent 字段冻结配置替换显式、会话状态边界清晰嵌套 LLM 并非深度冻结，仍需管理 Metrics、缓存和 fallback 临时状态
事件文件逐条持久化增量写入、分支与恢复自然大量会话需要 catalog/cache/eviction 优化
工具批次并行降低多只读操作延迟必须声明资源，否则只能保守互斥
懒加载插件构造轻、可解析远端来源首次交互前扩展状态尚未物化
REST + WS 双通道控制可靠、事件低延迟需要 reconcile、arming 和终止竞态处理

18.3 二次开发入口

  1. 加工具：定义 Action/Observation、ToolDefinition/Executor、资源声明并注册。
  2. 换模型策略：优先扩 model features、RouterLLM 或 FallbackStrategy。
  3. 加上下文：用 PromptSection、Skill 或 AgentContext suffix，不直接拼巨型 system prompt。
  4. 加安全策略：实现 SecurityAnalyzer/ConfirmationPolicy 或 lifecycle hooks。
  5. 加执行后端：实现 BaseWorkspace/RemoteWorkspace，而不是让工具感知容器厂商。
  6. 加远程产品：消费 Agent Server REST/WS，保留 full-state completion 语义。

APPENDIX

术语、关键不变量与事实索引

关键不变量

  1. Agent 的 Pydantic 字段被冻结，ConversationState 承载会话事实；LLM 当前不是 frozen 模型，拥有独立运行时状态。
  2. LLM 上下文来自事件树活跃分支的 View，不是全量事件列表。
  3. 可执行 Action 最终必须匹配 Observation；中断和恢复需要修补 orphan action。
  4. 确认发生在 ActionEvent 持久化之后、ToolExecutor 执行之前。
  5. Stop hook 可以推翻 FINISHED；远程完成以 post-run full-state snapshot 为准。
  6. 历史事件兼容处理器永久保留；Settings 不兼容变化走显式版本迁移。
  7. MCP 的公共配置是 SDK MCPServer map，FastMCP 只存在于连接边界。
  8. 本地文件路径按 host-native 语义，wire path 按跨平台 slash-normalized 语义。

术语速查

View 与 EventLog 有什么区别？
EventLog 保存全部事件树；View 是当前 leaf 到 root 的活跃分支经过属性约束后的 LLM 输入视图。
Pause 与 Interrupt 有什么区别？
Pause 等当前 step 自然结束；Interrupt 取消在途 async task 和可中断工具，最终都进入 PAUSED，但响应速度与副作用不同。
ToolSet 与 MCP Tool 有什么区别？
ToolSet 是一个本地工具规格展开多个 ToolDefinition 的模式；MCP Tool 来自远端 MCP server 动态发现，但最终也适配为 ToolDefinition/Executor。
为什么 RemoteConversation 不能只轮询 REST？
REST 状态可能先于 Stop hook 完成显示 FINISHED，也不能保证最终事件已通过 WS 到达；完整状态快照和 reconcile 提供结束屏障。
为什么 Agent 的字段被冻结，而 LLM 不是？
Agent 是「声明」，冻结它可以保证一次会话期间模型、工具规格和策略不会被悄悄改掉，恢复时也能凭同一份声明重建可执行体。LLM 之所以不是深度冻结，是因为它必须携带运行期状态：Metrics 累计、prompt cache 命中信息、fallback 当前落在哪个候选上。把这些塞进冻结对象会逼出一堆重建开销。实践上的含义是：改配置要替换整个 Agent 对象，而不是原地改字段；但读 LLM 上的统计数据是安全的，它本来就在变。
并行工具执行会不会破坏历史的可复现性？
不会，因为执行顺序和记录顺序是两件事。ParallelToolExecutor 可以按 DeclaredResources 分组并发跑，但 Observation 严格按原始 tool call 顺序写入事件树。这样同一份输入重放时得到的历史是一致的，View 里 tool_call 与 tool_result 的配对关系也稳定。真正的风险在别处：如果工具没有正确申报资源，两个并发写同一文件的调用会互相覆盖——那是数据竞争，不是历史顺序问题，得靠资源声明而不是靠排序解决。
什么时候该写一个新工具，什么时候该写一个 Skill？
判断标准是「模型缺的是能力还是知识」。缺能力——运行时根本没有办法做这件事（访问某个内部系统、操作某种文件格式）——才写工具，代价是每次请求都要携带它的 schema。缺知识——工具都在，只是不知道该按什么顺序、遵守什么约定去组合——那就写 Skill，它通过渐进披露只在触发时才进入上下文，常驻成本接近于零。一个实用的反问：如果把这段内容读给一个熟练工程师听，他能用现有工具做出来吗？能，就是 Skill。
