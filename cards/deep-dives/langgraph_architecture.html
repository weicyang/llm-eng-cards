阅读约定与分模块学习路线

LangGraph 不是“一个现成 Agent”，而是把状态、控制流、并发、持久化和人工介入组合成可恢复执行的底层编排内核。理解它的最快路径不是从 `create_react_agent` 开始，而是先建立 Channel 与 Pregel 超级步的心智模型，再回头看 ReAct 只是如何被编译成一张普通图。
代码事实可选能力实验特性远程服务边界弃用 / 迁移

本文用上述标记避免五类常见混淆：存在实现不代表默认启用；SDK 能调用的服务端能力不等于本地 OSS Runtime 自带；实验 API 不应视为稳定契约；兼容层仍可用不代表它是新项目首选；官方产品描述必须由当前代码确认。

一、项目定位与设计哲学

LangGraph 的目标是为长时间、带状态、可中断的工作流和 Agent 提供低层基础设施。它借鉴 Pregel 的 Bulk Synchronous Parallel（BSP）执行模型、Apache Beam 的数据流思想和 NetworkX 的图构建接口，但把这些概念重构为适配 LLM 应用的 Python Runtime。

LangGraph = Graph DSL + Channel State Model + Pregel Scheduler + Durable Checkpoint + Interrupt/Resume + Streaming

LangGraph 解决的不是「怎么让模型调工具」，而是「一个跑了二十分钟、在第十九分钟崩掉的流程，怎么从第十八分钟接着跑」。所有让人觉得绕的设计——Channel、超级步、pending writes——都是为了让状态能被序列化、被重放。

这里有个反直觉的地方值得先说清：LangGraph 明确不保存 Python 调用栈。一个中断后恢复的节点是从函数第一行重新执行的，而不是从 interrupt() 那一行继续。原因很实在——栈帧没法跨进程、跨机器、跨版本迁移，而一份只包含 Channel（状态 key 的值容器，自带更新合并语义与单调版本号）值与版本号的快照可以。这个取舍决定了后面几乎所有 API 的形状。

三、核心心智模型：图只是表面，Channel 才是状态机

用户看到的是 Node 和 Edge，运行时看到的是“订阅哪些 Channel、被什么 Channel 版本变化触发、读什么输入、向哪些 Channel 写什么值”的 Process 集合。节点函数遵循 State -> Partial<State>，返回的局部更新先成为 writes，直到当前超级步所有任务结束才统一应用。

StateGraph Builder Pregel Runtime Node A ──edge──► Node B compile Process A: subscribe / read / write │ reducer state schema ─────► Process B: triggers / channels └ conditional / Send Channel versions + versions_seen 超级步 n：读稳定快照 → 并行执行所有已触发任务 → 收集 writes 屏障： 对 writes 确定性排序并按 reducer 合并 → checkpoint 超级步 n+1：只有看见新 Channel 版本的订阅者才被调度

Node 和 Edge 是给人看的，调度器眼里只有版本号：每个 Channel 有一个单调递增的 version，每个节点记着自己「消费到第几号」。两者不相等，节点就该跑；相等，就跳过。整个执行模型可以压缩成这一句话。

超级步 n 开始 channel_versions : {messages: 7, plan: 3, docs: 5} versions_seen[node]: {agent: {messages: 7, plan: 3}, retriever: {messages: 5}} ▲ ▲ agent 已消费最新 → 不触发 retriever 落后 2 版 → 触发 ┌── 调度：updated_channels → trigger_to_nodes 索引挑候选 ──┐ │ PULL task：由订阅的 Channel 版本变化触发 │ │ PUSH task：由 Send(node, arg) 或 @task 调用产生 │ └───────────────────────┬───────────────────────────────────┘ ▼ 并行执行（进程内线程池 / 当前 event loop） 每个 task 读的是超级步开始时的稳定快照 → 兄弟节点互相看不见对方本步的写入（这是特性，不是延迟） │ ▼ writes 先落 pending_writes（task 粒度，可单独恢复） ════════════ 屏障 barrier：所有 task 结束才继续 ════════════ ▼ apply_writes：按 task path 稳定排序 → 按 Channel 分组 LastValue → 同步内多写直接报 InvalidUpdateError BinaryOperatorAggregate → 逐个喂给 reducer NamedBarrierValue → 收齐命名前驱才放行 未被写的订阅 Channel → 收到空更新以推进生命周期 ▼ channel_versions 推进 → 写 checkpoint（按 durability 决定时机） ▼ 超级步 n+1：只有 versions_seen 落后的订阅者被调度 确定性来自：稳定的 task path 排序 + 可结合的 reducer ——而不是「线程谁先跑完」。

这解释了三个关键性质：

  1. 同一超级步隔离：普通节点不会立即看到兄弟节点刚写的值，避免执行顺序造成隐式数据竞争。
  2. 并发写必须定义语义：LastValue 不允许同一步多个普通更新；`Annotated[T, reducer]` 生成聚合 Channel。
  3. 恢复发生在边界：Checkpoint 记录 Channel/版本和任务写；动态 interrupt 恢复时节点从头执行，而不是续接到 Python 函数某一行。

四、StateGraph DSL：Schema、Node、Edge 与 Branch 子文档

4.1 Schema 是运行契约

`StateGraph[StateT, ContextT, InputT, OutputT]` 分离四种类型：可变共享 State、run-scoped 且不可由节点更新的 Context、外部 Input 和最终 Output。State 可由 TypedDict、Pydantic、dataclass 或 root schema 描述；每个 key 在构图时解析为 Channel 或 ManagedValue。

构件语义设计注意
普通字段默认 `LastValue`同一步多写会触发 InvalidUpdateError
`Annotated[value, reducer]``BinaryOperatorAggregate` 或 DeltaChannelreducer 应满足结合性，最好满足交换性，避免并行结果依赖排序
ManagedValue运行时计算，不进入普通 checkpoint state如 RemainingSteps / IsLastStep
`context_schema`每次 run 注入的只读上下文替代逐步弃用的 `config_schema`

4.2 控制流构件

  • `add_node`：将 callable/Runnable 包装为 StateNodeSpec，可带 retry、cache、timeout、error handler。
  • `add_edge`：普通边；多起点 waiting edge 用 NamedBarrier 等待所有前驱。
  • `add_conditional_edges`：BranchSpec 在节点写入后读取 fresh state，返回目标名或 `Send`。
  • `START` / `END`：保留控制节点；至少需要从 START 可达的入口。
  • `Command`：一个返回值同时表达 state update、resume 和 goto；`Command.PARENT` 可把控制上抛父图。
条件边读取的是“当前节点 writes 临时应用到 Channel 副本后的状态”，不是等到下一超级步才看见自己的输出；这由 `local_read(..., fresh=True)` 支持。它既保持兄弟隔离，又允许路由依赖本节点刚产生的更新。

五、Compile：从声明式图到可执行 Pregel 子文档

`StateGraph` 是 builder，不能直接 invoke。`compile()` 首先校验 source/target/interrupt 节点，然后构建 `CompiledStateGraph`；后者继承 `Pregel`，因此获得 invoke、stream、batch、async、状态查询和更新能力。

StateGraph.compile(checkpointer, cache, store, interrupt_*, transformers) 1. ensure_valid_checkpointer + 可选严格 msgpack allowlist 2. validate：入口、边、分支目标、interrupt 节点 3. 确定 input / output / stream channels 4. 合并全局与节点级 retry/cache/timeout/error handler 5. 创建 CompiledStateGraph(Pregel) 6. 注入 START: EphemeralValue(input_schema) 7. attach_node → PregelNode + ChannelRead + ChannelWrite 8. attach_edge / waiting edge / branch → trigger channels 9. validate compiled graph

编译不会执行模型或工具，也不会把 Python 函数转成静态计划。它生成的是一个带触发关系和读写契约的运行图；动态分支、Command、Send、subgraph 和 interrupt 仍在运行时决定。

`compile(checkpointer=None)` 对子图表示可继承父图 checkpointer；`False` 才是显式禁用；`True` 表示子图自行持久化。这不是简单的布尔开关。

六、Channel：值容器、合并策略与调度版本 子文档

Channel核心语义典型用途
LastValue保留最后一次值，每超级步最多一个普通更新标量状态、唯一生产者
BinaryOperatorAggregate把本步每个 update 依次传入 reducer消息列表、计数、集合合并
EphemeralValue只保留前一超级步的值，之后清空START 输入、边触发信号
Topic收集一个或多个值，可配置累积`Send` 任务队列、消息主题
NamedBarrierValue收齐命名值后可读多前驱 join
UntrackedValue不跟踪 checkpoint 版本无需耐久恢复的运行值
DeltaChannel（beta）大部分 checkpoint 只存 delta sentinel，沿祖先 writes 重放大聚合状态降低快照写放大

6.1 `apply_writes` 的一致性职责

任务按稳定 path 排序后，系统分组每个 Channel 的 writes，调用 Channel.update，推进 `channel_versions`；即使节点没有写某订阅 Channel，某些 Channel 仍会接收空更新以完成生命周期。`versions_seen[node][channel]` 让调度器判断“该节点是否已经消费这个版本”。

6.2 DeltaChannel 的空间—读取权衡

DeltaChannel 通过周期性 `_DeltaSnapshot` 加中间 pending writes 重建值；metadata 的 counters 同时按更新次数和超级步跨度触发快照，系统还有最大祖先步数界限。删除、复制、裁剪 checkpoint 时必须保留重建链，否则可能静默得到空状态，因此它要求 saver 实现 `get_delta_channel_history` 合约。

七、Pregel Runtime：一次 invoke/stream 如何运行 子文档

7.1 Loop 生命周期

Pregel.stream / astream → 规范化 config、context、stream modes、durability → SyncPregelLoop / AsyncPregelLoop.__enter__ → checkpointer.get_tuple(thread_id/ns/id) → channels_from_checkpoint + pending_writes → _first(input 或 Command) → while loop.tick(): prepare_next_tasks(PUSH ∪ PULL) interrupt_before? PregelRunner.tick：执行所有未完成 task loop.after_tick() apply_writes → stream values → checkpoint → interrupt_after? → status: done / interrupt / out_of_steps / draining / error → 输出最终 channels；按 durability 完成持久化

超级步（Superstep）是这套 Runtime 的时间单位：读快照、并行跑、屏障合并、落 checkpoint。所有「什么时候能看到别人的写」「什么时候能恢复」这类问题，答案都是同一个——超级步边界。

7.2 BSP 屏障为何重要

Runner 可并发运行本超级步的节点，但 `after_tick()` 只在它们完成后执行统一合并。这样“并发”不意味着共享 dict 的竞态；并发冲突被转化为 Channel reducer 的显式契约。确定性依赖任务 path 排序与 reducer 设计，不依赖线程完成顺序。

7.3 递归限制

`recursion_limit` 实际限制超级步数，不是 Python 递归深度。循环图正常存在；达到 stop 后抛 GraphRecursionError，通常说明终止条件没有收敛或 limit 与工作量不匹配。

八、调度、并发、Send 与子图 子文档

8.1 两类任务

类型来源输入/身份
PULL边和 Channel 版本变化触发订阅节点按 PregelNode 的 channel 订阅读取；task id 含 checkpoint、namespace、step、node、trigger
PUSH`Send(node,arg)` 或 Functional API `task` 调用携带自定义 arg；同一节点可被扇出多次；按父 task path 和序号稳定标识

`prepare_next_tasks` 返回 PUSH 与 PULL 的并集。`Send` 是 map-reduce 的基础：条件路由返回多个 Send，下一超级步并发执行同一节点的不同输入，再通过 reducer 聚合。

PULL 是「订阅到货就干活」，PUSH 是「点名指派带参数的活」。map-reduce 之所以能用一个普通节点表达，就是因为同一个节点可以被 PUSH 扇出成 N 个各自带输入的 task，最后靠 reducer 收口。

8.2 子图 namespace

每个嵌套任务生成 checkpoint namespace；父图传入 checkpointer、store、stream 和 runtime。子图 interrupt 会以 GraphBubbleUp 上抛，不能被 ToolNode 的普通错误处理吞掉。`Command.PARENT` 允许子图更新或跳转到最近父图。

8.3 Waiting edge 与 barrier

多源边不是“任一到达就运行”，而是利用 NamedBarrierValue 收齐前驱标记后触发目标；动态 `Send` 则不天然形成固定 barrier，聚合依赖状态 reducer 和后续路由设计。

九、Checkpoint 与 Durable Execution 子文档

Checkpoint 是超级步边界的持久化协议。主键不是单一 id，而是 `thread_id + checkpoint_ns + checkpoint_id`；thread 表示一条持续会话/执行线，namespace 区分子图，checkpoint_id 选择该线上的具体历史点。

持久化对象/字段作用
`channel_values`当前可持久化 Channel 的快照或 Delta sentinel
`channel_versions`每个 Channel 单调版本，判断数据是否变化
`versions_seen`每个节点已经消费到的 Channel 版本，决定下步触发
`CheckpointTuple.pending_writes`task 级中间写，包括结果、ERROR、INTERRUPT、RESUME、SCHEDULED；它不属于 `Checkpoint` TypedDict 本体
`metadata`source(input/loop/update/fork)、step、parents、run_id、Delta counters

只保存「整帧快照」的系统，一步里挂掉一个节点就得把整步重跑；LangGraph 额外保存 task 粒度的 pending writes（单个任务已完成的中间写，绑定 checkpoint 与 task id），于是恢复时能精确跳过已经成功的那几个节点。

主键：thread_id + checkpoint_ns + checkpoint_id │ │ └─ 该线上的具体历史点（选它 = 时间旅行） │ └─ 子图命名空间（嵌套图各有各的历史） └─ 一条会话 / 执行线 超级步 n 执行中 task A ── 成功 ──► put_writes(checkpoint_n, task_A, [writes]) ← 立刻落盘 task B ── 成功 ──► put_writes(checkpoint_n, task_B, [writes]) task C ── 抛错 ──► put_writes(checkpoint_n, task_C, [ERROR, ERROR_SOURCE_NODE]) │ 进程此刻崩溃 ✗ │ ── 恢复 ────────────────────────────────────────────────────── get_tuple(thread, ns) → checkpoint_n + 它的 pending_writes A、B 的 writes 已存在 → 直接复用，节点不再执行（副作用不重复） C 没有成功写 → 只重跑 C ▼ 全部完成 → apply_writes → put(checkpoint_{n+1}) ← 整帧快照 持久化的四样东西（注意 pending_writes 不在 Checkpoint TypedDict 本体里） channel_values 当前 Channel 快照，或 DeltaChannel 的 sentinel channel_versions 每个 Channel 的单调版本 versions_seen 每个节点消费到哪一版 → 决定下一步谁被调度 metadata source(input/loop/update/fork) · step · parents · run_id durability 决定 put() 什么时候真正落盘： sync 下一超级步开始前等它写完 恢复点最强，写延迟进主路径 async 与下一超级步重叠 吞吐高，灾难时可能落后一个边界 exit 图退出时统一写 运行中几乎没有恢复能力

9.1 为什么既有 `put_writes` 又有 `put`

`put_writes` 在 task 完成时保存中间写；`put` 在超级步结束后保存新的整体 checkpoint。若同一步部分节点成功、部分失败，恢复时可把成功节点的 pending writes 重新应用并跳过它们，只重跑失败/未完成任务。这比仅保存整帧更接近幂等的 durable execution。

9.2 Durability 模式

模式语义取舍
`sync`下一超级步开始前等待 checkpoint 持久化恢复点最强，写延迟进入主路径
`async`持久化与下一超级步重叠吞吐更高，进程灾难时可能落后一个边界
`exit`图退出时统一持久化运行中恢复能力最低；Delta writes 用锚点与退出累积处理

Durability（checkpoint 落盘时机）是这套系统里最容易被默认值带偏的一个旋钮：它不改变任何业务语义，只改变「崩溃时你丢多少进度」。短任务用 exit 无所谓，长扇出任务用 exit 等于放弃了 durable execution 的全部收益。

示例场景：一条文档处理流水线，用 Send 对 200 个分片扇出到同一个「抽取 + 写库」节点，单次全跑约 11 分钟。上线初期用 durability="exit"，结果每次中途失败都要从头重跑 200 个分片，其中已经写过库的分片再写一遍产生重复行。改成 sync 后，恢复只重跑失败的那 3 个 task，平均恢复耗时从 11 分钟降到 20 秒上下；代价是每个超级步多约 40ms 的写盘延迟。真正消除重复行的是另一步：给写库操作加上以 ExecutionInfo 里 task 身份派生的幂等键——因为 checkpoint 只保证「不重复调度」，不保证「外部副作用只发生一次」。
无 checkpointer 时 durability 没有持久化对象；启用 checkpointer 却不传 `configurable.thread_id`，则无法建立可恢复线程。InMemorySaver 适合测试与调试，不是多进程生产存储。

十、SQLite、Postgres、Serde 与 Conformance 子文档

10.1 SQLite

`SqliteSaver` 使用 checkpoints/writes 两表，将 checkpoint 整包序列化为 BLOB；同步和异步分别由 `SqliteSaver` 与 `AsyncSqliteSaver` 提供。它轻量、易嵌入，适合本地开发和低并发；WAL 改善读写，但单文件锁模型不适合高并发服务。

10.2 Postgres

`PostgresSaver` 把 checkpoints、checkpoint_blobs、checkpoint_writes 分表：标量可留在 JSONB，复杂值按 Channel/version 写 blob 并复用；读取时 join 版本与 blob，再聚合 pending writes。`setup()` 必须显式执行迁移。ShallowPostgresSaver 只保留 thread/namespace 最新点，节省空间但放弃完整时间旅行。

10.3 Serde 与安全

默认 JsonPlusSerializer 支持常见 Python/LangChain 类型；EncryptedSerializer 可包装 CipherProtocol。严格 msgpack allowlist 限制可反序列化模块，减少把 checkpoint 当任意对象载入通道的攻击面。服务端 at-rest Encryption DSL 属于 SDK/API Server 层，不能与 saver serde 加密混为一谈。

10.4 Conformance

`checkpoint-conformance` 用能力声明验证 PUT、LIST、DELETE、COPY、PRUNE、DELTA_HISTORY 等合约。自研 saver 应把 conformance 作为 CI，而非只实现 `get/put` 后依赖偶然通过的简单图测试。

十一、Interrupt、Human-in-the-loop 与 Time-travel 子文档

Interrupt（把当前可恢复状态交还调用方、等待 Command(resume=...) 的暂停协议）不是断点调试，更像「把这一节点整段重放一遍，只是这次那几个 interrupt 调用直接返回上次存好的答案」。所以危险的从来不是中断本身，而是中断之前那些已经发生过的副作用。

11.1 静态中断

`interrupt_before` / `interrupt_after` 在 compile 或 stream 时指定。Loop 在任务执行前或 apply/checkpoint 后调用 `should_interrupt`；只有 Channel 自上次 interrupt 后发生版本更新且命中目标节点才暂停，防止原地恢复后立刻重复中断。

11.2 动态 `interrupt(value)`

节点内部调用 `interrupt` 时，scratchpad 按调用顺序分配 index；没有可用 resume 值就抛 GraphInterrupt，并持久化带稳定 id 的 Interrupt。客户端以同一 thread 调用 `Command(resume=value)`；节点从头重跑，之前的 interrupt 调用按 index 返回已保存值。

恢复不是从函数行号继续。中断之前的数据库写、HTTP 请求和文件副作用会再次执行，必须前移到独立节点、使用幂等键，或将副作用放在 interrupt 返回之后。多个 pending interrupt 时应传 `{interrupt_id: value}` 映射，单值恢复会被拒绝。
示例场景：一个退款审批流程把「创建退款单 → interrupt() 等人工确认 → 调支付网关打款」写在同一个节点里。测试环境每天审批量个位数，一直没发现问题；灰度到日均约 300 单后，财务发现当天有 12 笔重复退款单。根因就是恢复语义：审批人点确认后节点从头重跑，「创建退款单」这一句又执行了一遍。修法是把节点拆成三个——创建（幂等键 = 订单号 + 业务日期）、审批（节点体内只有 interrupt()，没有任何副作用）、打款——重复单据随即归零。判断标准很简单：一个包含 interrupt() 的节点，它前面的每一行都要能被安全地执行任意多次。

11.3 Command 的四个维度

  • `update`：按 State schema 写 Channel；
  • `resume`：向 pending interrupt 提供值；
  • `goto`：发往节点名或 Send；
  • `graph`：当前图或 `Command.PARENT`。

11.4 Time-travel 与分叉

指定历史 checkpoint_id 读取旧状态后继续执行属于 replay/fork。Runtime 会清理不应复用的旧 RESUME，必要时先写 fork checkpoint，避免后续 interrupt 仍挂到旧分支。`update_state` 也创建 source=update/fork 的历史节点，而非原地修改数据库记录。

`Runtime.store` 把 Store 注入节点；ToolNode 的 InjectedStore/ToolRuntime 可把它注入工具且不暴露给模型 schema。Store 以 batch/abatch 为核心，get/put/search/delete/list_namespaces 是便捷封装。长期记忆应设计 namespace 隔离、租户授权、TTL 和 embedding 演进。

12.1 节点缓存

CachePolicy 默认基于节点输入生成 key，并可设 TTL。命中时恢复缓存 writes，stream 标记 cached。缓存的是节点输出更新，不是整个图；包含时间、随机数、外部权限或副作用的节点必须谨慎定义 key 或禁用缓存。

13.1 三代接口并存

默认 `stream` 是 v1 tuple/dict 兼容表面；`version="v2"` 返回 typed `StreamPart` 并可把 Pydantic/dataclass state 映射回声明类型；`stream_events(version="v3")` 使用 StreamMux 和 per-run transformers 生成 GraphRunStream，当前仍属实验面。subgraphs=True 时 namespace 前缀保留嵌套来源。

stream mode 不是「日志详细程度」的旋钮，而是在选订阅哪一条数据平面：values 每步给你整份状态，updates 只给增量，tasks 和 checkpoints 给的是调度与持久化事实。选错了，代价直接体现在传输量上——大 state 用 values 逐步全量推送，成本随状态体积线性上涨。

13.2 背压与生命周期

同步/异步实现使用队列把 Loop 产生的 chunks 交给调用方；客户端消费速度、取消和生成器关闭会影响任务清理。远程 SDK 再把这些语义映射到 SSE/WS，并增加 cursor/reconnect buffer，不应把远程传输细节等同本地队列。

十四、Runtime 注入、错误处理与执行韧性 子文档

14.1 Runtime

`Runtime[ContextT]` 聚合 context、store、stream_writer、previous、ExecutionInfo、ServerInfo、user、heartbeat 和 RunControl。它不直接包含 RunnableConfig；需要 config 的节点应显式声明参数或使用 config API。ExecutionInfo 暴露 checkpoint/thread/run/node/attempt 等只读身份，便于幂等与观测。

14.2 Retry

RetryPolicy 定义初始间隔、backoff、最大间隔、最大尝试、jitter 和 retry_on。Runner 以 task attempt 为单位重试；应只重试瞬时失败，业务校验错误或已发生不可逆副作用的操作不能盲目重试。

14.3 Timeout

TimeoutPolicy 的 `run_timeout` 是单个 node attempt 的硬 wall-clock 上限，`idle_timeout` 是同一 attempt 的无进度窗口；每次 retry 都重新开始 attempt，当前没有覆盖所有重试的总 run budget。异步超时依赖协作式取消；阻塞 GIL 的 CPU 任务或 `time.sleep` 不能被及时打断，应移到进程池/外部作业。

14.4 Error handler node

StateGraph 可配置节点级或默认 error handler。失败 task 的 ERROR 与 ERROR_SOURCE_NODE 先持久化，恢复时原节点被标记为已处理，再调度 handler PUSH task，避免崩溃窗口造成原副作用节点重跑。handler 自身不会递归捕获 handler 错误，缓存也默认不应用于 handler。

14.5 Cooperative drain

RunControl.request_drain 让 Loop 在安全边界进入 draining，适合服务滚动退出；它不是立即 kill，长阻塞节点仍需 timeout/cancellation 配合。

十五、Functional API：另一种表面，同一个 Runtime 子文档

`@entrypoint` 把普通函数包装为 Pregel；`@task` 调用产生 PUSH Call，结果可像 future 一样在 entrypoint 中等待。它适合控制流天然由代码表达的工作流，StateGraph 更适合需要可视化、显式路由和统一 state schema 的场景。

Functional API 不是“轻量但不可恢复”的旁路。它把 task 调用编码为 PUSH task，并使用相同 task id、checkpoint namespace 和 pending write 机制。

16.1 Message state

`messages: Annotated[Sequence[BaseMessage], add_messages]` 使用消息 id 做追加/替换；model 节点先验证每个 AIMessage tool_call 都有对应 ToolMessage，避免 provider 拒绝不完整历史。RemainingSteps 是 ManagedValue，用来在循环耗尽前输出合适终态。

16.2 ToolNode

  • 同步通过 executor.map、异步通过 asyncio.gather 并行 tool calls；每次调用生成独立 ToolRuntime。
  • InjectedState、InjectedStore 和 ToolRuntime 在执行前注入，不进入 LLM 看到的工具 schema。
  • `wrap_tool_call` / `awrap_tool_call` 可实现工具级重试、缓存、权限、参数改写和短路。
  • 普通异常可按类型转为 `ToolMessage(status="error")`；GraphInterrupt/GraphBubbleUp 必须上抛。
  • 工具可返回 ToolMessage 或 Command；多个 parent Send Command 会被合并。

十七、RemoteGraph、SDK、CLI 与服务端边界 子文档

17.1 RemoteGraph

`RemoteGraph` 实现 PregelProtocol，把 invoke/stream/state API 转成 SDK 请求，因此远程图可作为节点或子图组合。它不复制远程执行器；checkpoint、队列和真正节点执行发生在 Server。远程流需要映射 mode、namespace 和 interrupt，协议错误与网络取消是额外失败面。

17.2 Python SDK

`LangGraphClient` 聚合 assistants、threads、runs、crons、store。Runs 支持 create/stream/wait/cancel/join，Threads 支持 state/history/update，transport 包含 HTTP/SSE 和异步 WebSocket。异步客户端的 `url=None` 可尝试进程内 ASGI transport，但依赖另装的 `langgraph_api`；同步客户端省略 URL 时使用本地默认地址。

18.1 推荐的工程分层

API / UI / Event Consumer │ Application Graph（业务状态、路由、HITL policy） │ Domain Nodes（LLM、检索、工具、审批、补偿） │ LangGraph Runtime（Pregel / Channel / Checkpoint） │ Infrastructure（Model / DB / Queue / Store / Observability） 原则：把不可逆副作用做成独立、可幂等节点；把人类审批放在副作用之前； 把跨 thread 知识放 Store；把执行位置放 Checkpointer；不要把二者混为一个“memory”。
  • 并发写同一个 state key 时，显式声明 Annotated[T, reducer]，并保证 reducer 可结合、最好可交换。
  • 把不可逆副作用（打款、发邮件、建资源）拆成独立节点，并用 ExecutionInfo 的 task 身份派生幂等键。
  • 跨会话的用户事实放 Store（跨 thread 的 namespace KV，可带向量索引与 TTL），执行位置放 Checkpointer，两者职责不要混。
  • 自研 Saver 一律把 checkpoint-conformance 挂进 CI，重点覆盖 pending writes 与 Delta 历史。
  • 不要在含 interrupt() 的节点里，把副作用写在中断之前——恢复会让它再执行一次。
  • 不要把 Checkpointer 当长期记忆库用，它的生命周期绑定 thread，跨会话检索不是它的职责。
  • 不要给带时间、随机数或外部权限的节点开缓存，CachePolicy 默认按输入生成 key，会稳定地返回过期结果。
  • 不要在 ToolNode 的错误处理里吞掉 GraphInterrupt / GraphBubbleUp，那会让子图的人工介入永远等不到回应。
  • 不要把官方博客里的 Big-O 表或本机 benchmark 当作生产 SLA，仓库本身没有给出可直接采用的延迟与吞吐承诺。

以下只描述当前实现能直接解释的增长项。令 `A` 为本超级步 active tasks 数、`U` 为上一步 updated channels 数、`N` 为节点数、`C` 为 Channel 数、`W` 为本步 writes 数；节点内部 LLM、工具、网络和 reducer 自身成本另计。

阶段当前实现可解释的成本与限制
规划下一步优先用 `updated_channels → trigger_to_nodes` 索引收集候选节点；索引不可用时退化为扫描全部 processes，再为候选任务准备输入。`libs/langgraph/langgraph/pregel/_algo.py:392-513`候选发现约随 `U` 及其触发集合增长，fallback 随 `N` 增长；还要叠加每个候选任务读取输入 Channel 的成本，不能笼统写成当前版本恒定 `O(1)`。
执行 active tasks单 task 有 fast path；多 task 提交进程内 executor 或 event-loop tasks，并等待完成/失败/超时。`libs/langgraph/langgraph/pregel/_runner.py:176-289`，`libs/langgraph/langgraph/pregel/_executor.py:40-72,122-166`调度工作量至少随 `A` 增长；无依赖 task 的墙钟时间通常受最慢 task、`max_concurrency`、线程池、event loop、GIL 和外部服务容量共同约束，不能由 `A` 单独预测。
屏障合并先按 task path 排序，再扫描 triggers/writes 分组更新；每个有值 Channel 执行 reducer，并向本步未更新 Channel 发送空更新。`libs/langgraph/langgraph/pregel/_algo.py:232-345`排序引入 `O(A log A)` 比较量，分组至少扫描 `W`，空更新路径扫描 `C`；真正耗时还取决于 reducer 是否复制大对象。
Checkpoint / 恢复普通进入路径读取指定或最新 `CheckpointTuple`；超级步按 durability 创建并提交新 checkpoint。`libs/langgraph/langgraph/pregel/_loop.py:1132-1179,1629-1679`普通恢复不要求重放全部历史，但延迟和空间随当前快照、pending writes、序列化器及 saver 后端变化；DeltaChannel 还可能沿祖先 writes 重建，不能据“最新 checkpoint”推导固定延迟。

19.3 三类性能证据必须分开

  • 官方设计分析：官方长文给出了按 nodes、edges、channels、active nodes、history、threads 分解的 Big-O 表。它是作者对当时架构与优化的设计说明；当前源码已有 `updated_channels` 快路径、DeltaChannel、durability 等具体分支，因此该表只能作为设计背景，不能写成 `langgraph 1.2.11` 的 API 保证、回归阈值或生产 SLA。
  • 仓库 benchmark：`libs/langgraph/bench/` 使用 pyperf 覆盖 fan-out/subgraph、ReAct、宽 State/dict、Pydantic State、长顺序图、首事件延迟、编译和 serde allowlist；另有 DeltaChannel 专项脚本测量多 Channel、快照频率、turn 深度、存储和 Python heap。它们是本地微基准/专项基准，不是远程平台、模型质量或生产 SLA。`libs/langgraph/bench/__main__.py:99-163`、`libs/langgraph/bench/__main__.py:467-520`、`libs/langgraph/tests/test_delta_channel_benchmark.py:1-18`。
  • 实测 SLA：仓库没有给出可直接采用的 latency/throughput SLA。生产目标必须在自己的模型、状态大小、并发、saver、网络与部署拓扑下定义 percentile、错误率、恢复时间和成本预算，再以固定 workload 持续压测；不得把博客 Big-O 或一次本机 benchmark 数字替代 SLA。

19.4 故障定位顺序

  1. 先看 thread/checkpoint_ns/checkpoint_id 是否命中预期历史。
  2. 看 `tasks` stream：哪个节点因哪些 trigger 被调度。
  3. 看 pending writes：成功结果是否已持久化、失败是否有 ERROR_SOURCE_NODE。
  4. 看 Channel versions/versions_seen：为何节点没有再次触发或重复触发。
  5. 再检查 reducer、Command goto、interrupt id 和 subgraph namespace。
  6. 最后区分本地 Runtime 异常与远程 transport/Server 异常。

二十、版本迁移、设计权衡与当前局限

Prebuilt 迁移`create_react_agent`、AgentState 和 HumanInterrupt 类型逐步迁往 LangChain agents；新代码应评估目标 API。
Streaming 并存v1 兼容、v2 typed、v3 experimental；对外协议要固定版本，不要依赖默认值永远不变。
DeltaChannel beta节省写放大但提高 saver、prune 和恢复复杂度；未压测前不要默认用于所有 reducer。
Config 演进`context_schema` 替代 `config_schema`；Runtime 与 RunnableConfig 的职责继续分离。

20.1 经典 Pregel、官方设计与当前本地 Runtime

边界经典 Google PregelLangGraph 官方设计说明当前开源本地 Runtime
计算对象与同步面向大规模图处理：vertex 在一系列全局 supersteps 中并行计算、收发 message，并在 barrier 同步；master/worker 负责分区与协调。来源：Malewicz et al., SIGMOD 2010。把 Agent 拆为离散 nodes；node 订阅带版本的 Channels，同一步读取隔离状态，结束后按确定顺序应用 updates。来源：官方 Building LangGraph 长文。PULL/PUSH tasks 读取 Channel 快照，`PregelRunner` 并发执行，`apply_writes` 在屏障排序并合并。`libs/langgraph/langgraph/pregel/_runner.py:135-138,176-289`，`libs/langgraph/langgraph/pregel/_algo.py:232-345,392-513`。
分布式执行论文系统是分布式 Pregel 集群，关注 worker 分区、机器间通信和故障恢复。官方长文讨论 runtime 与 Platform，并明确 task queue 由 Platform 提供；不要因此推断 Python library 自带分布式 worker。不是分布式 Pregel 集群。同步任务使用当前进程的 executor，异步任务使用当前 event loop；`RemoteGraph` 是 Server API 客户端，不是本地 Loop 的跨机调度器。`libs/langgraph/langgraph/pregel/_executor.py:40-72,122-166`，`libs/langgraph/langgraph/pregel/remote.py:118-150`。
恢复与交付语义论文用 checkpoint 和 worker recovery 恢复图计算，但这不等于任意外部系统副作用的 exactly-once 事务。官方设计目标是降低失败后的重试次数与重试成本，未把通用 exactly-once 声明为六项能力之一。不提供端到端 exactly-once。Runner 会把 task writes/ERROR/INTERRUPT 持久化，恢复可复用已记录结果；但“节点副作用 + saver 写入”没有跨外部 DB/HTTP/文件的原子事务，崩溃窗口和 retry 仍要求幂等键、去重或补偿。`libs/langgraph/langgraph/pregel/_runner.py:578-613,741-754`。
暂停与 continuation经典 Pregel 恢复的是分布式图计算状态/超级步，不是保存某个 Python 函数的调用栈。官方长文明确拒绝依赖不可跨机器、跨时间移植的 live generator/subroutine state，选择可序列化 checkpoint。不是 Python continuation。Checkpoint schema 只记录 Channel 值、版本、`versions_seen`，pending writes 位于 `CheckpointTuple`；`interrupt()` resume 从节点开头重跑并按调用序号取 resume 值，不保存 frame、instruction pointer 或局部变量栈。`libs/checkpoint/langgraph/checkpoint/base/__init__.py:92-146`，`libs/langgraph/langgraph/types.py:851-970`。
因此，“受 Pregel 启发”准确描述了 superstep、并行计算和 barrier 合并的算法血缘，不意味着当前本地包复刻了 Google 的分布式集群，也不自动附带服务端队列、端到端 exactly-once 或语言级 continuation。
LangGraph 最值得复用的不是某个 Agent 模板，而是把不确定的 LLM 决策约束在可版本化 State、显式 Channel 合并、可重放超级步和可审核 interrupt 协议中。它把“Agent 循环”提升为耐久状态机，但不会替你解决工具权限、业务幂等、上下文压缩、模型质量或外部系统一致性。

Q&A

StateGraph 与普通 DAG 引擎最本质的区别是什么？

它允许循环、动态 Send/Command、Channel reducer、任务级 pending writes 和 interrupt/resume；调度依据 Channel 版本而不只是一次性拓扑排序。

为什么 resume 后节点会从头执行？

Checkpoint 保存可序列化状态和任务写，不保存 Python 栈帧。重新进入节点并由 scratchpad 返回已记录的 resume 值，才能跨进程、跨时间恢复。

Checkpointer 能当长期记忆数据库吗？

不应。它服务执行线程和恢复；跨会话用户事实应放 BaseStore，并由节点按 namespace 检索。

并行节点写同一 key 一定安全吗？

只有该 key 的 Channel 明确定义允许多写的 reducer 才安全。LastValue 在同一步多写会报错；外部副作用不受 Channel 保护。

什么时候用 Functional API？

控制流天然是 Python 函数、希望逐步引入 durable task 时。需要可视化路由、统一共享状态和多 actor 时优先 StateGraph。

本地 LangGraph 是否必须连接 LangSmith？

不必须。本地核心可独立运行；LangSmith 提供可观测、评估和部署产品能力，是集成层而非 Pregel 的运行前提。
